<HeroCard label="Part 4 · Chapter 11" title="AWS Identity: Roles, Credentials and Testing Against a Fake Cloud">

The previous chapter used S3, SQS and DynamoDB with dummy credentials and never asked who the program was. Every real AWS bug that matters starts there. "AccessDenied" is rarely a missing permission: it is usually the right code running as the wrong identity, or the right identity with a policy that doesn't say what you think.

This chapter is about identity from the Go side: how the SDK decides who you are, how a role session gets renewed, how to write a policy as data and lint it, and how to test all of it locally. It then does something less comfortable. It measures what the local emulator **doesn't** enforce, so that a green local test stops meaning "the permissions are right".

Four stops:

1. **Who you are.** `GetCallerIdentity`, roles, `AssumeRole`, and credentials that renew themselves.
2. **The credential chain.** The order the SDK looks, run eleven ways.
3. **Policies as code.** Build least privilege from structs, lint it, and find out what a local AWS actually enforces.
4. **Testing against a local cloud.** A real endpoint, a mock, and the bug only one of them found.

Everything here is defensive: it is about least privilege and about knowing what your tests can and can't prove.

## Who You Are

*Stop 1 of 4.*

### Step 1: Ask AWS who you are

Before any permission question, ask the only question that always works: who am I? `sts:GetCallerIdentity` needs no IAM permission at all, which is exactly why it is the first call every debugging session should make. Half of all "AccessDenied" tickets turn out to be the right code running as the wrong identity.

The helper every program in this chapter shares is deliberately boring:

```go noverify title="internal/lab/lab.go · lines 19–24"
// Load resolves configuration exactly the way production code does: the
// default credential chain, the default region chain, and the standard
// AWS_ENDPOINT_URL override. There is no "if local" branch in the code.
func Load(ctx context.Context, opts ...func(*config.LoadOptions) error) (aws.Config, error) {
	return config.LoadDefaultConfig(ctx, opts...)
}
```

There is no `if local { ... }` branch. The SDK reads `AWS_ENDPOINT_URL` from the environment, so the *same binary* talks to LocalStack when that variable is set and to real AWS when it is not. That is the property that makes local testing trustworthy: the code under test is the code you ship.

Now the program. It asks who we are, creates a role, and assumes it. A **role** is an identity with no password and no long-lived keys. Nothing can log in as it. Instead a role has a *trust policy* (who may become it) and *permission policies* (what it may do once someone has). Compare an IAM **user**, whose access keys sit in `~/.aws/credentials` until somebody rotates them: a leaked user key is valid until a human notices, a leaked role session is dead in at most `DurationSeconds`.

The trust policy is built from the structs in `internal/policy`, not pasted as a string, so a typo is a compile error and the JSON is always well formed:

```go noverify title="internal/policy/policy.go · lines 33–59"
type Statement struct {
	Sid       string     `json:"Sid,omitempty"`
	Effect    string     `json:"Effect"`
	Principal Principal  `json:"Principal,omitempty"`
	Action    StringList `json:"Action,omitempty"`
	Resource  StringList `json:"Resource,omitempty"`
	Condition Cond       `json:"Condition,omitempty"`
}

type Document struct {
	Version   string      `json:"Version"`
	Statement []Statement `json:"Statement"`
}

// Version is the only policy language version you should ever write.
// "2008-10-17" (the old default) silently disables policy variables.
const Version = "2012-10-17"

func New(stmts ...Statement) Document { return Document{Version: Version, Statement: stmts} }

func (d Document) JSON() string {
	b, err := json.MarshalIndent(d, "", "  ")
	if err != nil {
		panic(err) // a struct of strings cannot fail to marshal
	}
	return string(b)
}
```

`AssumeRole` then trades our long-lived identity for a short-lived one. The optional `Policy` field is a **session policy**: it can only *narrow* the role. Per the AWS documentation the effective permissions are the intersection of the role's permission policies and the session policy, so a session policy can never grant anything the role lacks. That makes it the right tool for a service that holds a broad role but hands each request a narrow slice.

Read the output line by line. The base identity is `...:root` (LocalStack's default test account). After `AssumeRole` the caller ARN changes to `arn:aws:sts::<account>:assumed-role/<role>/<session-name>`: that session name is what shows up in CloudTrail, so make it say who or what acted (a request ID, a user ID), never just `session`.

Look at the last line. We assumed the role with the **wrong ExternalId** and got `err=<nil>`. The trust policy says `sts:ExternalId` must equal `chapter-external-id`; real AWS would refuse this call (reasoned from the policy, not observed here). LocalStack community accepted it. The ExternalId is the guard against the *confused deputy* problem when a third party assumes a role in your account, and you cannot test that guard here. Step 5 collects all such gaps in one table.

### Step 2: Temporary credentials expire, so let the SDK renew them

Temporary credentials are three values: access key ID, secret, and a **session token**, plus an expiry. The session token is the part people forget; without it, the key is rejected. Because they expire, a long-running Go service must keep renewing them, and the SDK does that with two layers:

- `stscreds.AssumeRoleProvider` knows *how* to get credentials (call `AssumeRole`).
- `aws.CredentialsCache` knows *when*: it stores the result and calls the provider again only once the credentials are within `ExpiryWindow` of expiring, and it makes concurrent callers share one refresh.

You normally never build these yourself (the default config does it for you when a profile has `role_arn`), but building them by hand lets us count the calls. `stscreds` only needs a one-method interface, so a counting wrapper is five lines:

```go noverify title="cmd/refresh/main.go · lines 20–30"
// countingSTS wraps the STS client so we can SEE every AssumeRole call the
// provider makes. stscreds only needs this one-method interface.
type countingSTS struct {
	inner *sts.Client
	calls atomic.Int32
}

func (c *countingSTS) AssumeRole(ctx context.Context, in *sts.AssumeRoleInput, o ...func(*sts.Options)) (*sts.AssumeRoleOutput, error) {
	c.calls.Add(1)
	return c.inner.AssumeRole(ctx, in, o...)
}
```

```go noverify title="cmd/refresh/main.go · lines 53–62"
	counter := &countingSTS{inner: sts.NewFromConfig(cfg)}
	provider := stscreds.NewAssumeRoleProvider(counter, aws.ToString(role.Role.Arn), func(o *stscreds.AssumeRoleOptions) {
		o.RoleSessionName = "refresh-demo"
		o.Duration = 5 * time.Second // real AWS refuses < 900s; see NOTES
	})
	// CredentialsCache is what makes it "automatic": it calls the provider
	// again only when the cached credentials are within ExpiryWindow of expiring.
	creds := aws.NewCredentialsCache(provider, func(o *aws.CredentialsCacheOptions) {
		o.ExpiryWindow = 2 * time.Second
	})
```

Real AWS refuses `DurationSeconds` below 900 (documented; not tested against real AWS here). LocalStack accepted 5 seconds, which lets us watch several renewals in 14 seconds. `expires in` below is measured against `Credentials.Expires`, which the cache has already pulled forward by the expiry window, so it counts down from 3s rather than 5s:

## The Credential Chain

*Stop 2 of 4.*

### Step 3: The default credential chain, one source at a time

When you write `config.LoadDefaultConfig(ctx)` with no options, the SDK walks a fixed list and stops at the first source that has credentials. Reading `config/resolve_credentials.go` in v1.33.6, the order is:

1. Environment variables `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` (and `AWS_SESSION_TOKEN`).
2. A web identity token: `AWS_WEB_IDENTITY_TOKEN_FILE` + `AWS_ROLE_ARN` (this is what EKS IRSA injects).
3. The shared config and credentials files, selected by `AWS_PROFILE` (default `default`). Inside a profile, in order: `source_profile` + `role_arn` (assume a role), static keys, `credential_source`, a profile web identity token, SSO, `credential_process`.
4. Only if the profile supplied nothing: container credentials (`AWS_CONTAINER_CREDENTIALS_RELATIVE_URI` or `..._FULL_URI`, ECS task roles and EKS Pod Identity), and finally the EC2 instance metadata service (IMDS).

Two consequences are worth memorising. Environment variables beat everything, even an explicit `AWS_PROFILE`. And a stale profile file on a server silently beats the instance role you thought you were using. The program that proves each claim only prints which link answered:

### Step 4: Policy as code, and a linter that reads it back

A policy is data, and data you build by string concatenation eventually ships with a stray comma or `"Resource": "*"` nobody meant. Building it from Go structs buys compile-time structure and, more usefully, lets us write tests and a linter against the same types. `StringList` exists because IAM accepts `"Action": "s3:GetObject"` and `"Action": ["s3:GetObject"]` interchangeably, and a parser has to accept both:

```go noverify title="internal/policy/policy.go · lines 9–25"
// StringList marshals as a JSON array and unmarshals from either a bare
// string or an array, because IAM accepts both spellings.
type StringList []string

func (s *StringList) UnmarshalJSON(b []byte) error {
	var one string
	if err := json.Unmarshal(b, &one); err == nil {
		*s = StringList{one}
		return nil
	}
	var many []string
	if err := json.Unmarshal(b, &many); err != nil {
		return fmt.Errorf("expected string or []string: %w", err)
	}
	*s = many
	return nil
}
```

The least-privilege policy used in this chapter. One bucket, one key prefix, writes only with server-side encryption, and a `Deny` that makes plain HTTP impossible. It names the actions it needs rather than `s3:*`, and every write carries a `Condition`:

```go noverify title="internal/policy/policy.go · lines 84–117"
// UploadsOnly is the least-privilege policy used through the chapter: one
// bucket, one prefix, encrypted writes only, TLS only.
func UploadsOnly(bucket string) Document {
	bucketARN := "arn:aws:s3:::" + bucket
	return New(
		Statement{
			Sid:      "ReadWriteUploadsPrefix",
			Effect:   "Allow",
			Action:   StringList{"s3:GetObject", "s3:PutObject"},
			Resource: StringList{bucketARN + "/uploads/*"},
			Condition: Cond{
				"StringEquals": {"s3:x-amz-server-side-encryption": {"AES256"}},
			},
		},
		Statement{
			Sid:      "ListUploadsPrefix",
			Effect:   "Allow",
			Action:   StringList{"s3:ListBucket"},
			Resource: StringList{bucketARN},
			Condition: Cond{
				"StringLike": {"s3:prefix": {"uploads/*"}},
			},
		},
		Statement{
			Sid:      "DenyPlainHTTP",
			Effect:   "Deny",
			Action:   StringList{"s3:*"},
			Resource: StringList{bucketARN, bucketARN + "/*"},
			Condition: Cond{
				"Bool": {"aws:SecureTransport": {"false"}},
			},
		},
	)
}
```

The linter reads only `Allow` statements, because a `Deny` can never grant anything. It flags `Action:"*"` and `service:*`, `Resource:"*"`, `Principal:"*"` in trust policies, an old `Version`, and write-capable statements with no `Condition`:

```go noverify title="internal/policy/lint.go · lines 43–85"
func Lint(d Document) []Finding {
	var out []Finding
	if d.Version != Version {
		out = append(out, Finding{High, "(document)", "version", fmt.Sprintf("Version is %q, want %q", d.Version, Version)})
	}
	for i, s := range d.Statement {
		id := s.Sid
		if id == "" {
			id = fmt.Sprintf("#%d", i)
		}
		if s.Effect != "Allow" {
			continue
		}
		write := false
		for _, a := range s.Action {
			switch {
			case a == "*":
				out = append(out, Finding{High, id, "action-star", `Action "*" grants every API in every service`})
			case strings.HasSuffix(a, ":*"):
				out = append(out, Finding{Warn, id, "action-service-star", fmt.Sprintf("%q grants every %s API", a, strings.TrimSuffix(a, ":*"))})
			}
			if isWrite(a) {
				write = true
			}
		}
		for _, r := range s.Resource {
			if r == "*" {
				out = append(out, Finding{High, id, "resource-star", `Resource "*" applies to every resource in the account`})
			}
		}
		for k, v := range s.Principal {
			for _, p := range v {
				if p == "*" {
					out = append(out, Finding{High, id, "principal-star", fmt.Sprintf("Principal %s:\"*\" lets anyone assume this", k)})
				}
			}
		}
		if len(s.Condition) == 0 && write && len(s.Principal) == 0 {
			out = append(out, Finding{Warn, id, "no-condition", "write-capable Allow with no Condition"})
		}
	}
	return out
}
```

Plain statement of the evidence: on LocalStack community 3.8.1, with these services (s3, sqs, dynamodb, iam, sts), **IAM permission policies, session policies, conditions, and trust-policy conditions (ExternalId) were not enforced** in any request we tried. Writes to a bucket the role has no access to succeeded; a `Condition` requiring encryption was ignored; a missing `s3:DeleteObject` did not stop a delete. `SimulatePrincipalPolicy`, the API that would let you evaluate policies offline, answered with an internal 500 wrapping `NoSuchEntity` on a role that exists (the endpoint looked the ARN up as a policy), so it is not a usable substitute either.

What *was* real: the IAM and STS control plane. Roles, policies, attachments and assumed-role sessions were created, listed, returned byte-identical, and deleted. So local testing here validates **your code's use of the API** and the **shape** of your policy documents. It cannot validate that the policy is *sufficient*. Two practical rules follow:

- Test policies where they are enforced: real AWS (a sandbox account) or the IAM policy simulator, with `iam:SimulatePrincipalPolicy` or Access Analyzer's policy validation in CI. The Go linter above catches the dangerous shapes without needing any endpoint.
- Never let a green LocalStack test be the evidence that "the Lambda has the permissions it needs". It tells you nothing about that.

LocalStack's own documentation says IAM enforcement is a Pro feature (`ENFORCE_IAM`); we did not test Pro.

			}

		}

		}

	}

### Step 7: The surprises

**Surprise 1: `AWS_ENDPOINT_URL` does not reach the STS client the config loader builds for itself.** Step 3 case 5a: a profile with `role_arn` and `source_profile`, `AWS_ENDPOINT_URL` set, and LocalStack running. The call failed with `InvalidClientTokenId` (HTTP 403). The proof is case `5a-proof`: pointing `AWS_ENDPOINT_URL` at a dead port gives the *identical* error, so something else answered. In `config.go` the resolver list runs `resolveCredentials` before `resolveBaseEndpoint`, so the STS client created inside `LoadDefaultConfig` to perform the profile's `AssumeRole` has no base endpoint yet and goes to the real `sts.us-east-1.amazonaws.com`, which rightly rejected the dummy key. That means a "local" run of this configuration quietly sends a request to the real service. With dummy credentials it is harmless; with real ones it is a real AssumeRole in a real account. The fix is the **service-specific** variable, which the STS client reads itself: `AWS_ENDPOINT_URL_STS` (case 5b and case 6 both succeed with it). Always set the per-service variable for `STS` when the credential chain itself uses assume-role or web identity.

**Surprise 2: a bucket name made from `t.Name()` is not a valid bucket name.** During development the first run of the table test failed on one subtest only:

```text
create bucket iamsec-testprefix-localstack-1,005-ke-f80e6dff: ... api error InvalidBucketName: The specified bucket is not valid.
```

Subtest names contain commas, spaces, `/` and capitals; bucket names allow only lowercase letters, digits, `-` and `.`. (This transcript is from the development run, not from `out.txt`, because the fix is in `lab.Name`.) The three other subtests had names that happened to survive. The fix is to map every other rune to `-` and cap the length (the 63-character limit is real S3 behaviour):

```go noverify title="internal/lab/lab.go · lines 26–45"
// Name returns a unique, DNS-safe resource name: iamsec-<label>-<8 hex>.
func Name(label string) string {
	b := make([]byte, 4)
	_, _ = rand.Read(b)
	// Bucket names allow only a-z, 0-9, "-" and ".". t.Name() produces
	// "/", ",", " " and capitals, so map everything else to "-".
	label = strings.Map(func(r rune) rune {
		if r >= 'a' && r <= 'z' || r >= '0' && r <= '9' || r == '-' {
			return r
		}
		if r >= 'A' && r <= 'Z' {
			return r + 'a' - 'A'
		}
		return '-'
	}, label)
	if len(label) > 30 {
		label = label[:30]
	}
	return fmt.Sprintf("%s%s-%s", Prefix, label, hex.EncodeToString(b))
}
```

Each of these passes locally and fails, or behaves differently, in a real account. The defence is the same in all four: say in the test what the local endpoint cannot prove, and cover that part elsewhere.

<UnderTheHood title="Trust policies, session policies, and the confused deputy">

Three separate documents decide whether a call succeeds, and they answer different questions. Nothing in this section was run against real AWS; it is how the documents are specified.

**The trust policy** is attached to the role and answers *who may become this role*. It is the policy `AssumeRole` is checked against, which is why it has a `Principal`. The ExternalId condition lives here.

**Permission policies** are attached to the role (or user) and answer *what may this identity do*. They have no `Principal`, because the principal is whoever holds the role.

**A session policy**, passed to `AssumeRole`, answers *what may this one session do*. By the AWS documentation the effective permissions are the **intersection** of the role's permission policies and the session policy, so it can only narrow. A service that holds a broad role can hand each request a narrow slice without minting a new role.

**The confused deputy.** Suppose a third-party service assumes a role in your account on your behalf. A different customer of that service could trick it into assuming *your* role by quoting your role ARN. The ExternalId is a shared secret, unique per customer, that you require in the trust policy: the deputy can only present the ID that belongs to the customer it's acting for. It protects you only if the trust policy checks it, which is exactly the part LocalStack did not enforce.

**Where the credentials live on AWS.** On EC2, the instance metadata service hands out role credentials (which is why a laptop with nothing configured waits on it). On EKS, IRSA injects a web identity token file and a role ARN, which is case 6 in the chain. On ECS and EKS Pod Identity, a local HTTP endpoint serves them, case 7. The Go code is the same in every one of them: that was the point of the chain.

</UnderTheHood>

## Exercises

<Exercise n={1} title="Make the lint stricter" level="medium">

The linter flags `Principal: "*"` in a trust policy. Write the test case and say what else in a trust policy is dangerous even without a wildcard principal.

<Solution>

A trust policy with `"Principal": {"AWS": "*"}` lets any AWS account assume the role, so the test builds exactly that and expects a `principal-star` HIGH finding. Also dangerous without a wildcard: a trust policy naming another account's `:root` with no `sts:ExternalId` condition (the confused-deputy hole for third-party access) and one that trusts a whole account where a single role would do. The linter can flag the second as a WARN ("trusts an entire account root with no Condition").

</Solution>

</Exercise>

<Exercise n={2} title="Two pages of mock" level="easy">

The mock test `two scripted pages` caught the pagination bug but `one page of three` didn't. What does that tell you about when a mock test is worth writing?

<Solution>

A mock only encodes what you already believe. It caught the bug because someone who knew S3 paginates scripted a truncated first page. So write mock tests for behaviours you can name in advance (a throttling error, a partial `DeleteObjects` failure, a second page), and use a real endpoint to find the ones you can't. The mock is cheap and exact for faults; the real endpoint is the only thing that can surprise you.

</Solution>

</Exercise>

<Exercise n={3} title="Where do permissions get tested?" level="hard">

If a local run can't verify permissions, where would you? Name two checks that belong in CI and say what each can and can't catch.

<Solution>

(1) The linter from this chapter on every policy document in the repository: catches `*` actions and resources, missing conditions and old versions, with no AWS access, but says nothing about whether the policy is sufficient. (2) A run in a sandbox AWS account (or the IAM policy simulator, `iam:SimulatePrincipalPolicy`, or Access Analyzer's policy validation): evaluates the real policy language, so it catches a missing action or a condition that never matches, but it needs credentials and is slower. Neither replaces the other: the linter finds dangerous grants, the enforced environment finds missing ones.

</Solution>

</Exercise>

<Recap>

- **Ask who you are first.** `sts:GetCallerIdentity` needs no permission. A role has no keys: a trust policy says who may become it, and `AssumeRole` returns a short-lived session (access key, secret, session token, expiry). A session policy can only narrow, never widen.
- **Let the SDK renew.** `stscreds` plus `CredentialsCache` gave **5 renewals in 14 seconds, each exactly one STS call**. Keeping three strings from one `Retrieve` is how services start failing with `ExpiredToken`.
- **The credential chain is an order**, measured over eleven cases: environment, web identity, profile, container, IMDS. Environment variables **beat `AWS_PROFILE`**; a stale profile file beats a task role; a laptop with IMDS on stalls for 4 to 5 s. Disable IMDS off EC2.
- **Build policies from structs and lint them.** The good policy had **0 findings**, the bad one **6**; `Deny` statements are never findings. No AWS access needed.
- **A local AWS is not an enforcement test.** On LocalStack 3.8.1 **six forbidden requests all succeeded**, a **wrong ExternalId was accepted**, and `SimulatePrincipalPolicy` returned a 500. Local tests check your use of the API and the shape of your policies, never that the policy is sufficient.
- **Test with a real endpoint for service behaviour and a mock for faults.** The first draft of `purge` deleted **1,000 of 1,005 keys** and reported success; a one-page mock passed, the real endpoint failed. Prefix resources, clean up in `t.Cleanup`, and make skips fail in CI.
- **`AWS_ENDPOINT_URL` doesn't reach the STS client the config loader builds for itself**, so an assume-role profile quietly called real AWS. Set `AWS_ENDPOINT_URL_STS` as well.

</Recap>
