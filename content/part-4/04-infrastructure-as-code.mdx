<HeroCard label="Part 4 · Chapter 4" title="Infrastructure as Code">

A real system is hundreds of pieces: servers, databases, DNS records, load balancers, queues, the settings inside each. Set them up by hand and you get a system nobody can rebuild, where production drifts away from staging one "quick fix" at a time. **Infrastructure as code** writes the desired system down in files, keeps them in git, and lets a tool make reality match. Terraform is the tool most of the industry uses, and OpenTofu is its open-source fork; both are written in Go, and every resource they manage comes from a **provider**, a Go program.

So in this chapter we don't just use Terraform: we write a provider. It manages keys in the server you built in the Build Your Own Redis track, and it's small enough to read in one sitting, yet it uses the same framework as the AWS and Kubernetes providers.

Six stops:

1. **Desired state.** What "declarative" means, and what problem it solves.
2. **Plan and apply.** The first run, and the state file it leaves behind.
3. **Three truths.** Configuration, state and reality, and what happens when someone changes things by hand.
4. **How providers work.** A separate process, spoken to over gRPC.
5. **Writing the provider.** Schema, configure, and the four CRUD methods, bit by bit.
6. **Testing it for real.** An acceptance test that runs Terraform itself.

## Desired State

*Stop 1 of 6.*

### Step 1: steps against states

There are two ways to tell a computer what you want. **Imperative**: a list of steps. "Create a key called `config:rate_limit` with value 100." Run it twice and you get an error, or two of something; run it after someone changed the key and it doesn't notice. **Declarative**: a description of the end state. "A key called `config:rate_limit` should exist, with value 100." The tool works out the steps: create it if it's missing, change it if it's wrong, do nothing if it's right.

A Terraform configuration is declarative. Here is the one this chapter uses:

```hcl title="config/main.tf"
terraform {
  required_providers {
    kv = {
      source = "gobible/kv"
    }
  }
}

provider "kv" {
  address = "kv:6380"
}

resource "kv_key" "greeting" {
  name  = "config:greeting"
  value = "Ẹ káàárọ̀"
}

resource "kv_key" "rate_limit" {
  name  = "config:rate_limit"
  value = "100"
}
```

A `terraform` block says which providers the configuration needs (`gobible/kv`: ours). A `provider` block configures one. Each `resource` block declares one thing that should exist: `resource "kv_key" "rate_limit"` is a resource of **type** `kv_key` with the local **name** `rate_limit`, so its **address** is `kv_key.rate_limit`. Nothing here says "create". It says what should be true.

### Step 2: why that matters

Because the file describes an end state, running the tool again is always safe. If nothing changed, it does nothing. Because the file lives in git, every change to the infrastructure is a commit with an author, a review and a way back. And because the same file can be applied again and again, staging and production can be built from the same code. That's the whole promise: infrastructure you can **review**, **reproduce** and **repair**, the way you already treat application code.

## Plan & Apply

*Stop 2 of 6.*

### Step 1: plan

`tofu plan` compares the configuration with what exists and prints what it would do, without doing it. Against an empty server:

```text

Warning: Provider development overrides are in effect

The following provider development overrides are set in the CLI
configuration:
 - gobible/kv in /plugins

The behavior may therefore not match any released version of the provider and
applying changes may cause the state to become incompatible with published
releases.

OpenTofu used the selected providers to generate the following execution
plan. Resource actions are indicated with the following symbols:
  + create

OpenTofu will perform the following actions:

  # kv_key.greeting will be created
  + resource "kv_key" "greeting" {
      + name  = "config:greeting"
      + value = "Ẹ káàárọ̀"
    }

  # kv_key.rate_limit will be created
  + resource "kv_key" "rate_limit" {
      + name  = "config:rate_limit"
      + value = "100"
    }

Plan: 2 to add, 0 to change, 0 to destroy.

─────────────────────────────────────────────────────────────────────────────

Note: You didn't use the -out option to save this plan, so OpenTofu can't
guarantee to take exactly these actions if you run "tofu apply" now.
```

The warning at the top appears because we load our provider from a local folder instead of a registry (stop 4 explains how); OpenTofu prints it on every command, and it's left out of the outputs below. Then the plan itself: two `+` resources, "2 to add". Reviewing this before anything changes is the point: in a team, the plan is what gets read in the pull request.

### Step 2: apply

`tofu apply` makes the same plan and, once approved, carries it out:

```text

plan. Resource actions are indicated with the following symbols:
  + create

OpenTofu will perform the following actions:

      + name  = "config:greeting"
      + value = "Ẹ káàárọ̀"
    }

  + resource "kv_key" "rate_limit" {
      + name  = "config:rate_limit"
      + value = "100"
    }

Plan: 2 to add, 0 to change, 0 to destroy.
kv_key.greeting: Creating...
kv_key.rate_limit: Creating...
kv_key.rate_limit: Creation complete after 0s [name=config:rate_limit]
kv_key.greeting: Creation complete after 0s [name=config:greeting]

```

```text
$ redis-cli GET config:greeting
Ẹ káàárọ̀
$ redis-cli GET config:rate_limit
"100"
```

Both keys are on the server, including the Yoruba greeting. Apply once more with nothing changed:

```text

kv_key.greeting: Refreshing state... [name=config:greeting]
kv_key.rate_limit: Refreshing state... [name=config:rate_limit]

No changes. Your infrastructure matches the configuration.

OpenTofu has compared your real infrastructure against your configuration and
found no differences, so no changes are needed.

Apply complete! Resources: 0 added, 0 changed, 0 destroyed.
```

"No changes." Before planning, OpenTofu **refreshed** each resource ("Refreshing state...") by asking the provider what the server holds now, found it matched the configuration, and did nothing. That's the declarative promise, measured.

### Step 3: the state file

Where did OpenTofu remember that these two keys are **its** keys? In the **state file**, `terraform.tfstate`, JSON written after every apply. Its header and one of the two resources:

```text
{
  "version": 4,
  "terraform_version": "1.12.6",
  "serial": 1
}
{
  "mode": "managed",
  "type": "kv_key",
  "name": "rate_limit",
  "provider": "provider[\"registry.opentofu.org/gobible/kv\"]",
  "instances": [
    {
      "schema_version": 0,
      "attributes": {
        "name": "config:rate_limit",
        "value": "100"
      },
      "sensitive_attributes": []
    }
  ]
}
```

State maps each address in the configuration (`kv_key.rate_limit`) to the real thing it manages (the key `config:rate_limit`) and records its attributes as last seen. Without it, the tool couldn't tell "a key I created and should update" from "a key someone else created that I should leave alone", or know what to delete when a resource disappears from the configuration. In a team, state lives in a shared backend (an S3 bucket, a database, Terraform Cloud) with a lock, so two people can't apply at once.

## Three Truths

*Stop 3 of 6.*

### Step 1: config, state, reality

At any moment there are three versions of the truth: the **configuration** (what should exist), the **state** (what Terraform last saw), and the **real system**. Every command moves information between them:

- **refresh** reads reality into state (the provider's `Read`);
- **plan** compares the configuration with the refreshed state;
- **apply** changes reality to match the configuration, and records the result in state.

### Step 2: changes you make

Change `value = "100"` to `"250"` and plan:

```text

kv_key.greeting: Refreshing state... [name=config:greeting]
kv_key.rate_limit: Refreshing state... [name=config:rate_limit]

OpenTofu used the selected providers to generate the following execution
plan. Resource actions are indicated with the following symbols:
  ~ update in-place (current -> planned)

OpenTofu will perform the following actions:

  # kv_key.rate_limit will be updated in-place
  ~ resource "kv_key" "rate_limit" {
        name  = "config:rate_limit"
      ~ value = "100" -> "250"
    }

Plan: 0 to add, 1 to change, 0 to destroy.

─────────────────────────────────────────────────────────────────────────────
```

`~` is an **update in place**: the key stays, its value changes. Now change the key's **name**, from `config:greeting` to `config:welcome`:

```text

kv_key.rate_limit: Refreshing state... [name=config:rate_limit]
kv_key.greeting: Refreshing state... [name=config:greeting]

OpenTofu used the selected providers to generate the following execution
plan. Resource actions are indicated with the following symbols:
-/+ destroy and then create replacement

OpenTofu will perform the following actions:

  # kv_key.greeting must be replaced
-/+ resource "kv_key" "greeting" {
      ~ name  = "config:greeting" -> "config:welcome" # forces replacement
        # (1 unchanged attribute hidden)
    }

Plan: 1 to add, 0 to change, 1 to destroy.

─────────────────────────────────────────────────────────────────────────────
```

`-/+` is a **replacement**: destroy, then create. A key can't be renamed in place, so the provider marks `name` as "requires replace" (stop 5 shows the line) and the plan says so: `# forces replacement`. After applying:

```text
$ redis-cli GET config:greeting
(nil)
$ redis-cli GET config:welcome
Ẹ káàárọ̀
```

The old key is gone and the new one holds the value. On real infrastructure the difference between `~` and `-/+` is the difference between changing a setting and deleting a database, which is why reading the plan matters.

### Step 3: changes someone else makes

Now someone "fixes" things by hand, outside Terraform:

```text
$ redis-cli SET config:rate_limit 5000   # someone "fixes" it by hand
OK
$ redis-cli DEL config:welcome
(integer) 1
```

The next plan:

```text

kv_key.greeting: Refreshing state... [name=config:welcome]
kv_key.rate_limit: Refreshing state... [name=config:rate_limit]

OpenTofu used the selected providers to generate the following execution
plan. Resource actions are indicated with the following symbols:
  + create
  ~ update in-place (current -> planned)

OpenTofu will perform the following actions:

  # kv_key.greeting will be created
  + resource "kv_key" "greeting" {
      + name  = "config:welcome"
      + value = "Ẹ káàárọ̀"
    }

  # kv_key.rate_limit will be updated in-place
  ~ resource "kv_key" "rate_limit" {
        name  = "config:rate_limit"
      ~ value = "5000" -> "250"
    }

Plan: 1 to add, 1 to change, 0 to destroy.

─────────────────────────────────────────────────────────────────────────────
```

This is **drift**, and the plan caught both kinds: a value changed behind Terraform's back (`"5000" -> "250"`, it will set it back) and a resource deleted behind its back (it will create it again). Apply, and the server matches the configuration once more. That's the other half of infrastructure as code: the files aren't just how you build the system, they're how you notice when it has wandered off.

### Step 4: adopting what already exists

A key created by hand, `feature:dark_mode`, isn't Terraform's. Add a resource block for it and plan, and Terraform wants to **create** it, not knowing it's already there:

```text

kv_key.rate_limit: Refreshing state... [name=config:rate_limit]
kv_key.greeting: Refreshing state... [name=config:welcome]

OpenTofu used the selected providers to generate the following execution
plan. Resource actions are indicated with the following symbols:
  + create

OpenTofu will perform the following actions:

  # kv_key.dark_mode will be created
  + resource "kv_key" "dark_mode" {
      + name  = "feature:dark_mode"
      + value = "on"
    }

Plan: 1 to add, 0 to change, 0 to destroy.

─────────────────────────────────────────────────────────────────────────────
```

`tofu import` adopts it instead: it records the existing key in state under the address, using the provider's `Read` to fill in its attributes:

```text

  Prepared kv_key for import

Import successful!

The resources that were imported are shown above. These resources are now in
your OpenTofu state and will henceforth be managed by OpenTofu.
```

```text

kv_key.rate_limit: Refreshing state... [name=config:rate_limit]
kv_key.greeting: Refreshing state... [name=config:welcome]

No changes. Your infrastructure matches the configuration.

OpenTofu has compared your real infrastructure against your configuration and
```

No changes: the key is managed now, without being recreated. This is how teams bring hand-built infrastructure under code one resource at a time.

## How Providers Work

*Stop 4 of 6.*

### Step 1: a plugin is a separate program

Terraform and OpenTofu know nothing about keys, cloud VMs or DNS. Everything they manage comes from **providers**, and a provider is a separate executable. Run ours directly and it says so:

```text
$ ./terraform-provider-kv
This binary is a plugin. These are not meant to be executed directly.
Please execute the program that consumes these plugins, which will
load any plugins automatically
(exit status 1)
```

The core starts it as a child process, with a "magic cookie" in its environment to prove it's being run by Terraform or OpenTofu. The provider then opens a Unix socket and prints one line on standard output saying where to find it. Started that way by hand:

```text
$ TF_PLUGIN_MAGIC_COOKIE=d602bf8f… PLUGIN_PROTOCOL_VERSIONS=6 ./terraform-provider-kv
1|6|unix|/tmp/plugin2446974509|grpc|
```

`1` is the plugin system's own protocol version, `6` the Terraform plugin protocol version, then the network type, the socket's path and `grpc`. The core connects to that socket and from then on they speak **gRPC**: "what's your schema?", "plan this resource", "apply this change". With `TF_LOG=DEBUG`, one `tofu plan` showed it:

### Step 2: why this design

Separate processes mean a crashing provider can't take the core down, providers can be written and released independently (there are thousands in the public registry), and in principle in any language that speaks gRPC, though in practice nearly all are Go, using HashiCorp's framework. It's the same plugin system (hashicorp/go-plugin) Vault and Packer use.

### Step 2: the provider block

```go noverify title="terraform-provider-kv/internal/provider/provider.go · lines 16–35"
// kvProvider holds nothing: each run of the plugin configures a client.
type kvProvider struct{}

func New() provider.Provider { return &kvProvider{} }

func (p *kvProvider) Metadata(_ context.Context, _ provider.MetadataRequest, resp *provider.MetadataResponse) {
	resp.TypeName = "kv" // resources are named kv_<something>
}

// The provider block in a configuration: provider "kv" { address = "..." }
func (p *kvProvider) Schema(_ context.Context, _ provider.SchemaRequest, resp *provider.SchemaResponse) {
	resp.Schema = schema.Schema{
		Attributes: map[string]schema.Attribute{
			"address": schema.StringAttribute{
				Description: "host:port of a Redis-speaking server.",
				Required:    true,
			},
		},
	}
}
```

`Metadata` names the provider `kv`, which is why resources are called `kv_key`. `Schema` declares what the `provider "kv"` block accepts: one required string, `address`. The framework validates the configuration against it before our code sees anything.

```go noverify title="terraform-provider-kv/internal/provider/provider.go · lines 37–55"
type providerConfig struct {
	Address types.String `tfsdk:"address"`
}

// Configure turns the provider block into a client that every resource
// receives.
func (p *kvProvider) Configure(ctx context.Context, req provider.ConfigureRequest, resp *provider.ConfigureResponse) {
	var cfg providerConfig
	resp.Diagnostics.Append(req.Config.Get(ctx, &cfg)...)
	if resp.Diagnostics.HasError() {
		return
	}
	client := redis.NewClient(&redis.Options{Addr: cfg.Address.ValueString(), Protocol: 2})
	if err := client.Ping(ctx).Err(); err != nil {
		resp.Diagnostics.AddError("cannot reach the kv server", err.Error())
		return
	}
	resp.ResourceData = client
}
```

`Configure` reads the block into a Go struct (the `tfsdk` tags map attributes to fields), makes a go-redis client, checks the server answers `PING`, and hands the client to every resource via `resp.ResourceData`. A wrong address fails here, once, with a clear error, instead of in every resource. `Protocol: 2` keeps go-redis from opening with the `HELLO 3` handshake our server doesn't implement (lesson 10 of the Redis track).

### Step 4: Create and Read

```go noverify title="terraform-provider-kv/internal/provider/key_resource.go · lines 58–91"
// Create runs on apply for a key that isn't in state yet: SET it.
func (r *keyResource) Create(ctx context.Context, req resource.CreateRequest, resp *resource.CreateResponse) {
	var plan keyModel
	resp.Diagnostics.Append(req.Plan.Get(ctx, &plan)...)
	if resp.Diagnostics.HasError() {
		return
	}
	if err := r.client.Set(ctx, plan.Name.ValueString(), plan.Value.ValueString(), 0).Err(); err != nil {
		resp.Diagnostics.AddError("SET failed", err.Error())
		return
	}
	resp.Diagnostics.Append(resp.State.Set(ctx, plan)...)
}

// Read runs on every plan: what does the server hold now? A key that has
// gone is removed from state, so the plan offers to create it again.
func (r *keyResource) Read(ctx context.Context, req resource.ReadRequest, resp *resource.ReadResponse) {
	var state keyModel
	resp.Diagnostics.Append(req.State.Get(ctx, &state)...)
	if resp.Diagnostics.HasError() {
		return
	}
	v, err := r.client.Get(ctx, state.Name.ValueString()).Result()
	if errors.Is(err, redis.Nil) {
		resp.State.RemoveResource(ctx)
		return
	}
	if err != nil {
		resp.Diagnostics.AddError("GET failed", err.Error())
		return
	}
	state.Value = types.StringValue(v) // whatever is there now, even if someone changed it
	resp.Diagnostics.Append(resp.State.Set(ctx, state)...)
}
```

`Create` gets the planned values, sends `SET`, and saves the plan as the new state. `Read` is the one that matters most: it runs on every refresh, and it must report **reality**, not echo state back. A key that's gone makes it call `RemoveResource`, which is how the deleted greeting turned into `+ create` in stop 3; a changed value is written into state as found, which is how `"5000" -> "250"` appeared. A provider whose `Read` just returned the state it was given would never see drift.

### Step 5: Update, Delete and import

```go noverify title="terraform-provider-kv/internal/provider/key_resource.go · lines 93–122"
// Update runs on apply when the value changed: SET the new one.
func (r *keyResource) Update(ctx context.Context, req resource.UpdateRequest, resp *resource.UpdateResponse) {
	var plan keyModel
	resp.Diagnostics.Append(req.Plan.Get(ctx, &plan)...)
	if resp.Diagnostics.HasError() {
		return
	}
	if err := r.client.Set(ctx, plan.Name.ValueString(), plan.Value.ValueString(), 0).Err(); err != nil {
		resp.Diagnostics.AddError("SET failed", err.Error())
		return
	}
	resp.Diagnostics.Append(resp.State.Set(ctx, plan)...)
}

// Delete runs on destroy, or before a replacement: DEL the key.
func (r *keyResource) Delete(ctx context.Context, req resource.DeleteRequest, resp *resource.DeleteResponse) {
	var state keyModel
	resp.Diagnostics.Append(req.State.Get(ctx, &state)...)
	if resp.Diagnostics.HasError() {
		return
	}
	if err := r.client.Del(ctx, state.Name.ValueString()).Err(); err != nil {
		resp.Diagnostics.AddError("DEL failed", err.Error())
	}
}

// ImportState adopts a key that already exists: tofu import kv_key.x <name>.
func (r *keyResource) ImportState(ctx context.Context, req resource.ImportStateRequest, resp *resource.ImportStateResponse) {
	resource.ImportStatePassthroughID(ctx, path.Root("name"), req, resp)
}
```

`Update` runs for `~` changes; `Delete` for destroys, and for the first half of a `-/+`. `ImportState` takes the ID the user typed (`tofu import kv_key.dark_mode feature:dark_mode`) and puts it in the `name` attribute; the framework then calls `Read` to fill in the rest, which is exactly what the import output showed. Build it for the containers with `GOOS=linux GOARCH=arm64 CGO_ENABLED=0 go build -o ../bin/terraform-provider-kv .` (use `amd64` on an Intel machine).

<UnderTheHood title="What the framework does between gRPC and your methods">

The plugin protocol is defined in protocol buffers (`tfplugin6.proto`): RPCs like `GetProviderSchema`, `ValidateResourceConfig`, `PlanResourceChange`, `ApplyResourceChange`, `ReadResource` and `ImportResourceState`, carrying values encoded as msgpack or JSON against the schema. `terraform-plugin-go` implements that gRPC server; `terraform-plugin-framework` sits on top, turning a `PlanResourceChange` into calls to your plan modifiers, an `ApplyResourceChange` into `Create`, `Update` or `Delete` depending on the prior and planned state, and converting between wire values and your `types.String` fields. That's why a provider this small can be a first-class citizen: the protocol work is all in the libraries.

</UnderTheHood>

## Exercises

<Exercise n={1} title="A time to live" level="medium">

Add an optional `ttl_seconds` attribute to `kv_key`. You'll need `EXPIRE` and `TTL` on the server first (Redis track lesson 8, exercise 2). What should `Read` do with the TTL counting down, so that every plan doesn't show a change?

<Solution>

Store the configured `ttl_seconds` in state as given, and in `Read` only check that the key still has an expiry (TTL greater than 0), not its exact remaining seconds, which change every second. If `Read` wrote the live TTL into state, every plan would show `ttl_seconds` changing: perpetual drift, a classic provider bug.

</Solution>

</Exercise>

<Exercise n={2} title="A data source" level="easy">

Add a `kv_key` **data source** that reads a key Terraform doesn't manage, so a configuration can use its value elsewhere (`data.kv_key.x.value`).

<Solution>

Implement `datasource.DataSource` with `Metadata`, `Schema` (`name` required, `value` computed), `Configure` and `Read` (`GET`, error if missing), and return it from the provider's `DataSources`. A data source only reads; it never appears in plans as a change.

</Solution>

</Exercise>

<Exercise n={3} title="Plan against a real Redis" level="easy">

Start Redis 8 on the network and point the provider's `address` at it. What changes?

<Solution>

Nothing in the provider: it only uses `SET`, `GET` and `DEL`, which Redis has. You can drop `Protocol: 2` too, because Redis understands `HELLO 3`. That's the benefit of our server speaking the real protocol: the same client code works against both.

</Solution>

</Exercise>

<Exercise n={4} title="Two people, one state" level="medium">

What goes wrong if two people run `tofu apply` at the same time with local state files, and how do remote backends prevent it?

<Solution>

Each has their own `terraform.tfstate`; both plan against their own view, both apply, and each state now misses the other's changes, so the next plan by either person tries to undo the other's work. A remote backend (S3 with a lock, Postgres, Terraform Cloud) keeps one shared state and takes a lock for the whole plan-and-apply, so the second `apply` waits or fails with "state locked".

</Solution>

</Exercise>

<Recap>

- **Infrastructure as code** describes the end state in files; the tool works out the steps. Applying twice is safe: the second apply found "No changes".
- **State** maps each resource address to the real object it manages; without it the tool couldn't update, delete or tell its objects from anyone else's.
- **Three truths**: refresh reads reality into state, plan compares configuration with state, apply changes reality. A value changed and a key deleted with `redis-cli` both appeared in the next plan as **drift**.
- `~` updates in place; `-/+` destroys and recreates (our `name` has `RequiresReplace`); `tofu import` adopts what already exists.
- A **provider** is a separate Go program the core starts and speaks **gRPC** to over a Unix socket: three processes in one plan, protocol version 6.
- `Read` must report reality: that's the whole of drift detection. An acceptance test ran real Terraform through create, update, import and destroy in 3.3 s, and the same binary worked under OpenTofu 1.12.6 and Terraform 1.16.4.

</Recap>
