## Processes

*Stop 1 of 5.*

### Step 1: a process is a running program, with a number

When you run `api`, the kernel creates a **process**: the program's code loaded into memory, plus everything the kernel keeps about it while it runs. It names the process with a number, the **PID** (process ID), and remembers which process started it, the **parent** (its PID is the **PPID**).

The kernel publishes what it knows about every process as files under `/proc/<pid>/`. Nothing there is on disk: reading those files asks the kernel. Here's `rates`, running in a container, seen through them:

```text
$ grep -E '^(Name|State|PPid|Threads|VmRSS)' /proc/8/status
Name:	rates
State:	S (sleeping)
PPid:	7
VmRSS:	    8528 kB
Threads:	5
$ readlink /proc/8/exe
/bin2/rates
$ tr '\0' ' ' < /proc/8/cmdline
/bin2/rates -addr 127.0.0.1:9090 
$ ls /proc/8/task
10 11 12 13 8 
```

Four things worth noticing:

- **`State: S (sleeping)`**. An idle server spends nearly all its time asleep, waiting for a connection. `R` means running on a CPU right now.
- **`Threads: 5`**, and `/proc/8/task` lists five IDs. One Go program is one process, but the Go runtime runs it on several OS threads (goroutines are spread across them). Each thread has its own ID, and the first one's ID is the PID.
- **`exe`** is a link to the binary that's running and **`cmdline`** holds its arguments, separated by zero bytes, which is why we pipe it through `tr`.
- **`PPid: 7`**: the shell that started it.

`ps`, `top` and `htop` are just programs that read these files. When a server misbehaves and you have nothing else, `/proc/<pid>/` has the answers.

### Step 2: starting another program, the way os/exec does

A Go service starts other programs more often than you'd think: a backup job calls `pg_dump`, a report service calls `wkhtmltopdf`, a CI runner calls `git`. In Go that's `os/exec`. `cmd/spawn` starts a child, looks at it through `/proc/<pid>/stat`, and then does the one thing people forget:

```go noverify title="svc/cmd/spawn/main.go · lines 28–46"
func main() {
	fmt.Printf("spawn: pid %d, parent %d\n", os.Getpid(), os.Getppid())

	cmd := exec.Command("sleep", "1")
	if err := cmd.Start(); err != nil {
		panic(err)
	}
	pid := cmd.Process.Pid
	time.Sleep(100 * time.Millisecond) // let it get going
	st, ppid := stat(pid)
	fmt.Printf("child %d started:        state %s, parent %s\n", pid, st, ppid)

	time.Sleep(2 * time.Second) // sleep 1 has exited by now
	st, _ = stat(pid)
	fmt.Printf("child %d exited, no Wait: state %s\n", pid, st)

	err := cmd.Wait()
	st, _ = stat(pid)
	fmt.Printf("child %d after Wait:      state %s, err %v, exit code %d\n", pid, st, err, cmd.ProcessState.ExitCode())
```

`cmd.Start` returns as soon as the child is running; it doesn't wait for it to finish. `stat` (lines 15–26 of the same file) reads the state letter and the parent's PID from `/proc/<pid>/stat`. Run in a container:

```text
spawn: pid 7, parent 1
child 13 started:        state S, parent 7
child 13 exited, no Wait: state Z
child 13 after Wait:      state gone, err <nil>, exit code 0
child 14 sent SIGTERM:    err signal: terminated, exit code -1, signal 15, a shell reports 143
```

Line by line:

1. `spawn` is PID 7. Its parent is PID 1, the container's init (we ran it with `docker run --init`, more on that in stop 3).
2. The child, PID 13, is sleeping, and its parent is 7: `spawn` itself.
3. After two seconds, `sleep 1` has finished. But the process isn't gone: its state is **`Z`, a zombie.**
4. Only after `cmd.Wait()` does it disappear from `/proc`.

<Define term="zombie">
A **zombie** is a process that has finished but whose parent hasn't collected its exit status yet. The kernel frees almost everything it held (its memory, its open files), but keeps its PID and a small record with its exit status, because the parent might still ask for it. The parent collects it with the `wait` family of system calls; in Go, `cmd.Wait()`. That's called **reaping**. A zombie can't be killed, because it's already dead: the only fix is for its parent to reap it, or to die itself.
</Define>

A zombie costs only a PID. But PIDs are limited (the kernel's `pid_max`, and a container's `pids.max` from chapter 1), so a service that starts children in a loop and never calls `Wait` slowly uses them all up, and then nothing on the machine can start a process. The rule: **every `cmd.Start()` needs a `cmd.Wait()`**. `cmd.Run()` and `cmd.Output()` call both for you.

### Step 3: fork, exec, and why Go doesn't have fork

On Unix, starting a program has always been two steps. **fork** makes a copy of the calling process; **exec** replaces the copy's program with a new one. The split is deliberate: between the two, the child can set itself up (redirect its output to a file, change directory, drop privileges) with ordinary code, before the new program starts.

Go can't offer a plain `fork`. A Go program is several threads, and `fork` copies only the thread that called it, into a child whose other threads (the ones running the garbage collector and the scheduler, maybe holding locks) have vanished. So Go only does fork and exec *together*, in `os/exec`, with nothing but careful, lock-free code between them. `strace` shows how, on Go 1.27 (the `CLONE_THREAD` lines, which are the runtime starting its own threads, and `SIGURG`, the signal Go uses to preempt goroutines, are filtered out):

Copying a service's memory just to throw it away would be slow, and with a big heap, very slow.
- **`execve("/usr/bin/sleep", ...)`** in PID 77 is the exec.

- For the second child you can see the kill: `SIGTERM`, `killed by SIGTERM`, and `waitid` returning `CLD_KILLED` with `si_status=SIGTERM`.

<UnderTheHood title="Exit status versus killed by a signal">

A process ends one of two ways. Either it calls `exit(n)` itself (Go's `os.Exit(n)`, or returning from `main`, which is `exit(0)`), or a signal kills it. `wait` tells the parent which, and the number: `CLD_EXITED` with a status, or `CLD_KILLED` with a signal. In Go it's `cmd.ProcessState.Sys().(syscall.WaitStatus)`, with `Exited()`, `ExitStatus()`, `Signaled()` and `Signal()`.

Shells, Docker and Kubernetes squeeze both into one number: an exit status stays itself (0 to 255), and death by signal N is reported as **128 + N**. That's where the famous numbers come from:

| Number | Meaning | Usually |
|---|---|---|
| 0 | exited 0 | success |
| 1 | exited 1 | the program reported an error (Go's `log.Fatal`) |
| 2 | exited 2 | a Go panic, or a Go program dumping its goroutines on SIGQUIT |
| 137 | 128 + 9, SIGKILL | the OOM killer, or a stop that ran out of time |
| 143 | 128 + 15, SIGTERM | stopped with the default action: no handler |

Go's `ExitCode()` returns −1 for a process killed by a signal, since it has no exit code. You build the lab's `exitCode` function from exactly this.

</UnderTheHood>

## File Descriptors

*Stop 2 of 5.*

### Step 1: everything is a number in one table

When a process opens a file, the kernel doesn't hand back the file. It adds an entry to the process's **file descriptor table** and hands back the entry's index, a small integer: the **file descriptor**, or fd. Every later `read`, `write` and `close` names the file by that number.

"Everything is a file" is the Unix slogan, and it's really about this table: a network connection, a listening socket, a pipe to a child process, a timer, even the Go runtime's network poller each get an fd, and all of them count against the same limit. `cmd/fds` opens one file, one TCP listener and one pipe, then prints its own table from `/proc/self/fd`, where each entry is a link to what the fd refers to:

```go noverify title="svc/cmd/fds/main.go · lines 15–37"
func main() {
	f, _ := os.Open("/etc/hostname")
	ln, _ := net.Listen("tcp", "127.0.0.1:8080")
	r, w, _ := os.Pipe()
	defer f.Close()
	defer ln.Close()
	defer r.Close()
	defer w.Close()

	ents, _ := os.ReadDir("/proc/self/fd")
	var fds []int
	for _, e := range ents {
		n, _ := strconv.Atoi(e.Name())
		fds = append(fds, n)
	}
	sort.Ints(fds)
	for _, n := range fds {
		target, err := os.Readlink("/proc/self/fd/" + strconv.Itoa(n))
		if err != nil {
			continue // the directory we were reading, already closed
		}
		fmt.Printf("fd %2d -> %s\n", n, target)
	}
```

```text
$ ulimit -n
1048576
$ fds
fd  0 -> /dev/null
fd  1 -> pipe:[18337]
fd  2 -> pipe:[18338]
fd  3 -> /sys/fs/cgroup/cpu.max
fd  4 -> /etc/hostname
fd  5 -> anon_inode:[eventpoll]
fd  6 -> anon_inode:[eventfd]
fd  7 -> socket:[21584]
fd  8 -> pipe:[21588]
fd  9 -> pipe:[21588]
RLIMIT_NOFILE: soft 1048576, hard 1048576
```

That's more than the four things we opened. Reading the table:

| fd | what | who opened it |
|---|---|---|
| 0, 1, 2 | stdin, stdout, stderr | inherited from the parent: every process starts with these three |
| 3 | `/sys/fs/cgroup/cpu.max` | the Go runtime: since Go 1.25 it keeps the cgroup's CPU limit open, to re-read it and adjust GOMAXPROCS (chapter 1) |
| 4 | `/etc/hostname` | our `os.Open` |
| 5 | `eventpoll` | the Go runtime's network poller (epoll): one fd that watches all the others |
| 6 | `eventfd` | the runtime's way to wake the poller |
| 7 | `socket` | our TCP listener |
| 8, 9 | `pipe` | the two ends of our `os.Pipe` |

The kernel always hands out the **lowest free number**, which is why the numbers are packed together, and why a closed fd's number is reused by the next open.

### Step 2: the limit, and what Go does about it

The table has a maximum size per process, the resource limit **`RLIMIT_NOFILE`** (`ulimit -n` in a shell). Each limit has two values: the **soft** limit, which is what's enforced, and the **hard** limit, the ceiling a process may raise its own soft limit to. Opening one more file than the soft limit fails with `EMFILE`, which Go prints as **`too many open files`**.

Docker's default is generous: 1,048,576, the first line of the output above. But plenty of places set a soft limit of 1024, a number that dates from the `select` system call, which can't handle fd numbers of 1024 or more. Here's a container started with soft 1024, hard 4096:

```text
$ ulimit -Sn; ulimit -Hn
1024
4096
$ fds | tail -1
RLIMIT_NOFILE: soft 4095, hard 4096
```

The shell says 1024, but the Go program sees **4095**. Go raises its own soft limit at startup, since Go 1.19, because Go never uses `select`, and a limit of 1024 is easy to hit (gofmt walking a big tree in parallel did). It sets it to one below the hard limit, not equal to it, so that it can tell if someone changes the limit from outside, and it puts the old limit back for programs it starts with os/exec, which might use `select`.

So for a Go service **the hard limit is the one that matters**. Set it where the service is started: `docker run --ulimit nofile=N:N`, `LimitNOFILE=` in a systemd unit (stop 5), or the container runtime's defaults in Kubernetes.

### Step 3: the leak

Now the incident. Here's `api`'s handler as it was first written. It calls `rates` and passes the answer on; if `rates` answers with an error, it returns 502:

```go noverify title="svc/cmd/api/main.go · lines 18–33"
func quote(ratesURL string) http.HandlerFunc {
	return func(w http.ResponseWriter, r *http.Request) {
		cur := r.URL.Query().Get("cur")
		resp, err := client.Get(ratesURL + "/rate?cur=" + url.QueryEscape(cur))
		if err != nil {
			http.Error(w, err.Error(), http.StatusBadGateway)
			return
		}
		if resp.StatusCode != http.StatusOK {
			http.Error(w, "rates: "+resp.Status, http.StatusBadGateway)
			return
		}
		defer resp.Body.Close()
		io.Copy(w, resp.Body)
	}
}
```

It works. Every test passes. It has a leak you can't see by reading the happy path: when `rates` answers anything but 200, the function returns at line 28, and the `defer resp.Body.Close()` on line 30 has not run yet, so it never will. The response body is never closed.

An unclosed body means the TCP connection to `rates` is never given back: the HTTP client can't reuse it for the next request (someone might still read it) and can't close it either. So it stays open, holding an fd, forever. Each request for a currency `rates` doesn't know costs one fd.

### Step 4: the fix, and measuring it

Move the `defer` to the first moment you have a body, right after the error check:

```go noverify title="svc/cmd/api/main.go · lines 18–33"
func quote(ratesURL string) http.HandlerFunc {
	return func(w http.ResponseWriter, r *http.Request) {
		cur := r.URL.Query().Get("cur")
		resp, err := client.Get(ratesURL + "/rate?cur=" + url.QueryEscape(cur))
		if err != nil {
			http.Error(w, err.Error(), http.StatusBadGateway)
			return
		}
		defer resp.Body.Close() // on every path, the error ones too
		if resp.StatusCode != http.StatusOK {
			http.Error(w, "rates: "+resp.Status, http.StatusBadGateway)
			return
		}
		io.Copy(w, resp.Body)
	}
}
```

The general rule: **once a function has a resource, the very next line is its `defer Close()`**. Anything in between is a path that can return without it. The `bodyclose` linter (in `golangci-lint`) catches the HTTP case.

<Callout kind="pro" title="Watching fds in production">

You don't need a load test to see this. `ls /proc/<pid>/fd | wc -l` is the count; `grep 'open files' /proc/<pid>/limits` is the limit. Go's Prometheus client exports both as `process_open_fds` and `process_max_fds`, so an alert on their ratio (say, above 80%) warns you hours before the service falls over. Raising the limit hides a leak for a while; it never fixes one.

</Callout>

## Signals

*Stop 3 of 5.*

### Step 1: how you ask a process to stop

A **signal** is a small notification the kernel delivers to a process: a number, nothing else. Some come from the kernel itself (a segmentation fault is `SIGSEGV`), most come from other processes through the `kill` system call. For operating services, five matter:

| Signal | Number | Who sends it | Default action |
|---|---|---|---|
| `SIGTERM` | 15 | `docker stop`, Kubernetes, `systemctl stop`, `kill` | end the process |
| `SIGINT` | 2 | Ctrl-C in a terminal | end the process |
| `SIGKILL` | 9 | the OOM killer, and anyone out of patience | end the process; **can't be caught, blocked or ignored** |
| `SIGQUIT` | 3 | `Ctrl-\` in a terminal | end the process (Go: after printing every goroutine's stack) |
| `SIGHUP` | 1 | a closed terminal; by convention, "reload your config" | end the process |

A process can install a **handler** for any signal except `SIGKILL` (and `SIGSTOP`), and then the signal runs the handler instead of the default action. That's the entire protocol for stopping a service politely: the orchestrator sends **SIGTERM**, which the service may handle, waits a **grace period** (10 s for `docker stop`, 30 s in Kubernetes, 90 s by default in systemd), and if the process is still there, sends **SIGKILL**, which it may not.

### Step 2: what happens to a request in flight

The test: `rates` runs with `-delay 3s`, so every quote takes 3 seconds. We start a request, and half a second later run `docker stop` on the `api` container, timing it. First, `api` as it was in stop 2, with no signal handling:

Three results, one per run:

1. **No handler**: `docker stop` took 0.4 s and the exit code is **143**, which is 128 + 15: killed by SIGTERM. The request in flight got nothing: curl's exit 52 means the server closed the connection without a reply. The Go runtime does install a handler for SIGTERM at startup (it has to, to support `signal.Notify`), but when your code hasn't asked for the signal, the handler restores the default action and sends the signal again, so the process dies of it, exactly as a C program would.
2. **With a handler** (the code is in step 3): `docker stop` took 3.0 s, the time the request needed to finish. It got its **HTTP 200**, and the exit code is **0**. The log shows why: `shutting down`, then two seconds later `stopped cleanly`.
3. **With a handler, but `docker stop -t 1`**: a 1-second grace period for a 3-second request. The service started shutting down, and Docker sent SIGKILL at 1.3 s: exit code **137**, and the request was cut off anyway. The grace period is a contract. Your drain time must fit inside it.

(Chapter 1 reported a Go program with no handler exiting with status 2 on SIGTERM. On this machine, Go 1.27 on Linux 6.12, it died of the signal, 143, both as PID 1 and not. Either way the request is lost, and "143 or 2 in the dashboards" is the symptom to look for.)

### Step 3: graceful shutdown in Go

Here's the final `main`. First, turn the signal into a context:

```go noverify title="svc/cmd/api/main.go · lines 49–52"
	// ctx is cancelled by the first SIGTERM (docker stop, kubectl delete,
	// systemctl stop) or SIGINT (Ctrl-C).
	ctx, stop := signal.NotifyContext(context.Background(), syscall.SIGTERM, syscall.SIGINT)
	defer stop()
```

`signal.NotifyContext` returns a context that is cancelled when SIGTERM or SIGINT arrives. Asking for the signals is what switches off the default action: from now on SIGTERM means "cancel `ctx`" instead of "die". Since Go 1.26, `context.Cause(ctx)` says which signal it was, which is where the log's `cause="terminated signal received"` comes from.

Next, start the server in its own goroutine, so `main` is free to wait for either of two things:

```go noverify title="svc/cmd/api/main.go · lines 54–67"
	mux := http.NewServeMux()
	mux.HandleFunc("GET /quote", quote(*ratesURL))
	srv := &http.Server{Addr: *addr, Handler: mux}
	errc := make(chan error, 1)
	go func() { errc <- srv.ListenAndServe() }()

	select {
	case err := <-errc: // the server failed on its own, e.g. the port is taken
		slog.Error("serve", "err", err)
		os.Exit(1)
	case <-ctx.Done():
	}
	stop() // from here on, a second signal kills the process the default way
	slog.Info("shutting down", "cause", context.Cause(ctx))
```

The `select` waits for the server to fail on its own (the port is taken: exit 1, loudly) or for the signal. Then `stop()` un-registers the signals. That's deliberate: if shutdown hangs, a second Ctrl-C or SIGTERM gets the default action again and kills the process, instead of being swallowed.

Last, the shutdown itself:

```go noverify title="svc/cmd/api/main.go · lines 69–80"
	sctx, cancel := context.WithTimeout(context.Background(), *grace)
	defer cancel()
	if err := srv.Shutdown(sctx); err != nil {
		slog.Error("shutdown", "err", err) // the grace period ran out
		os.Exit(1)
	}
	if err := <-errc; !errors.Is(err, http.ErrServerClosed) {
		slog.Error("serve", "err", err)
		os.Exit(1)
	}
	slog.Info("stopped cleanly")
}
```

`srv.Shutdown` closes the listener, so new connections are refused, closes idle keep-alive connections, and waits for requests in flight to finish. It gives up when its context does: `-grace 8s` by default, deliberately shorter than Docker's 10 s, so the service gives up on its own and logs it, rather than being SIGKILLed mid-sentence. If it finishes, `ListenAndServe` has returned `http.ErrServerClosed`, which is the normal case, and `main` returns: exit 0.

<Callout kind="note" title="Kubernetes adds one more step">

In Kubernetes, SIGTERM and "stop sending traffic to this pod" happen at the same time, and the second takes a moment to reach every load balancer. For a second or two after SIGTERM, new requests can still arrive. The usual answer is a `preStop` hook that sleeps a few seconds before SIGTERM is sent, or a readiness endpoint that starts failing as soon as `ctx` is cancelled while the server keeps serving a few more seconds. Either way: `terminationGracePeriodSeconds` must be longer than the sleep plus your `Shutdown` timeout.

</Callout>

### Step 4: PID 1, and the shell in the middle

In a container, the first process is **PID 1** of its PID namespace, and the kernel treats PID 1 specially: **a signal whose action is the default is not delivered to it at all**. Only signals PID 1 has a handler for get through. (That's why a PID 1 that crashes can't take its container down by accident, and also why so many containers ignore `docker stop`.) Our Go `api` is fine as PID 1 because it has a handler.

But containers often don't run the service directly. They run a script:

```sh title="svc/deploy/start.sh"
#!/bin/sh
# A typical container entrypoint: some setup, then start the service.
echo "start.sh: preparing config"
/bin2/api -rates http://p4c02-rates:9090
```

The shell runs the script, starts `api` as its child, and waits. Now the shell is PID 1, and `api` is PID 6 or 7. Three runs of the same test:

The shell, as PID 1 with no handler for SIGTERM, never received it; it certainly didn't pass it on to `api`, which never logged `shutting down`. Docker waited its 10 seconds and SIGKILLed everything. The request happened to finish because it only needed 3 s; one that needed 11 would have been cut off. And every deploy of this service now takes 10 seconds longer per container than it should.
- **`--init`**: Docker makes its small init program (tini) PID 1, and it forwards signals to its child. But its child is the shell, not `api`. The shell, no longer PID 1, dies of the SIGTERM at once; tini sees its only child exit and exits too; the kernel kills the rest of the container. **0.6 s, 143, and the request cut off.** `--init` fixes zombies and signal forwarding, but it can't fix a shell that doesn't pass signals on.
- **`exec`**: one word fixes it. `exec /bin2/api ...` makes the shell *replace itself* with `api` (it's the `execve` from stop 1, without the clone), so `api` is PID 1, handles SIGTERM itself: **3.0 s, exit 0, HTTP 200.**

```sh title="svc/deploy/start-exec.sh"

# The same entrypoint, but the shell replaces itself with the service.
echo "start.sh: preparing config"

```

If your service starts child processes of its own, also run it with `--init` (or tini) so someone reaps the zombies from stop 1.

### Step 5: SIGKILL, and SIGQUIT for when it's stuck

**SIGKILL** is the one signal nothing can intercept: no handler runs, no `defer` runs, buffers aren't flushed, the kernel just removes the process. That's why it's the last resort after a grace period, and why the OOM killer uses it. If your service needs to do something before it dies (flush a batch, release a lock), it has to do it on SIGTERM, because there may be nothing after.

**SIGQUIT** is Go's gift to operators. When a service is stuck (no errors, no progress, CPU at zero), send it SIGQUIT and the Go runtime prints the stack of **every goroutine** to stderr, then exits with status 2:

```text

runtime.gopark(0x75132dc13e68?, 0x2?, 0x88?, 0x3b?, 0x75132dc13cf4?)
```

## Memory Limits

### Step 1: the cgroup's hard limit

Chapter 1 showed that a container's memory limit is a number in its cgroup's `memory.max` file, and that a group that goes over it has a process killed by the kernel's **OOM killer**, with SIGKILL. Here's what that means for a Go service, measured.

`cmd/cache` behaves like a service with an in-memory cache: it builds a **60 MiB** cache that it keeps, then serves 400,000 "requests", each building a 16 KiB response and throwing it away. It prints the Go heap and the cgroup's own count of the container's memory, `memory.current`:

```go noverify title="svc/cmd/cache/main.go · lines 47–64"
	var ms runtime.MemStats
	runtime.ReadMemStats(&ms)
	fmt.Printf("cache built       heap %5.1f MiB  GCs %4d  cgroup memory.current %5.1f MiB\n",
		float64(ms.HeapAlloc)/(1<<20), ms.NumGC, cgroupMiB("memory.current"))
	start := time.Now()
	for i := 1; i <= *requests; i++ {
		resp := make([]byte, 16<<10) // one response, garbage right after
		copy(resp, template)
		sink = resp
		if i%50_000 == 0 {
			runtime.ReadMemStats(&ms)
			fmt.Printf("%6d responses  heap %5.1f MiB  GCs %4d  cgroup memory.current %5.1f MiB\n",
				i, float64(ms.HeapAlloc)/(1<<20), ms.NumGC, cgroupMiB("memory.current"))
		}
	}
	runtime.ReadMemStats(&ms)
	fmt.Printf("done in %v: %d GCs, cgroup memory.peak %.1f MiB of memory.max %.0f MiB\n",
```

Five runs, top to bottom.

**1 GiB limit.** The live data is 60 MiB, yet the container peaked at **175.7 MiB**. That's how Go's garbage collector works by default: with `GOGC=100`, it lets the heap grow to twice the live data before collecting (60 MiB live, so a target of about 120 MiB of heap), and the runtime's own overhead and freed memory it hasn't returned to the kernel yet come on top. The GC made only 102 collections.

**100 MiB limit.** The same program in a 100 MiB container. The cache fits, 68.7 MiB after it's built. But once requests start, the heap heads for its target of 120 MiB, crosses 100, and the kernel kills it: **exit code 137, `OOMKilled true`**. It never printed its first progress line. Nothing in the program is wrong: it never had more than 60 MiB of data it needed. It died of garbage it would have collected a moment later.

<Define term="GOMEMLIMIT">
**GOMEMLIMIT** (Go 1.19+) is a **soft memory limit** for the Go runtime: the total memory it may map (heap, stacks, runtime structures). As the total approaches it, the GC collects more often, whatever `GOGC` says. It's soft because the runtime won't crash to respect it: if the live data alone doesn't fit, it goes over rather than collecting forever. Set it with the environment variable (`GOMEMLIMIT=90MiB`) or `debug.SetMemoryLimit`.
</Define>

### Step 2: telling the GC about the limit

The Go runtime doesn't read `memory.max` (it does read `cpu.max`, for GOMAXPROCS, but not the memory limit). So you tell it, with `GOMEMLIMIT`, a little below the container's limit, leaving room for what the runtime doesn't count: the binary's own code, the kernel's page cache for files it reads, thread stacks.

**`GOMEMLIMIT=90MiB`** in the same 100 MiB container: `memory.current` held at **88 to 90 MiB** for all 400,000 requests, and the program finished. The price is in the GC count: **442 collections** instead of 102, because the GC runs whenever the heap nears the limit instead of when it has doubled. It took 1.19 s against 0.67 s without a limit. Memory traded for CPU, which is the right trade when the alternative is being killed.

**`GOMEMLIMIT=80MiB`**: more headroom (77 to 79 MiB), more collections, **914**, and 2.58 s.

**`GOMEMLIMIT=50MiB`**, set *below* the 60 MiB of live data. The limit can't be met, and the runtime knows it: it went over (the heap stayed at 63 to 73 MiB) and kept working, with **2,433 collections** and 5.21 s. The GC caps itself at roughly half the CPU in this state, so the service slows down instead of spinning forever. A soft limit that's too low turns an OOM kill into a slow service: better, but you'll see it in latency.

(Two runs report `memory.peak` 100.0 MiB although `memory.current` never went past about 90. At the limit, the kernel first reclaims memory it can take back, such as cached pages of the binary, and only kills if that fails. Those runs brushed the limit and were saved by reclaim.)

<Gotcha>

**GOMEMLIMIT doesn't cover everything the container is charged for.** It counts memory the Go runtime maps. The cgroup also counts the page cache of files the service reads and writes, memory used by cgo libraries, and, if your service shells out, its children. The 90% rule (a 512 MiB container gets `GOMEMLIMIT=460MiB`) is a starting point; watch `memory.current` (or `container_memory_working_set_bytes` in Kubernetes) against the limit, and lower it if the gap is too thin.

</Gotcha>

## systemd

*Stop 5 of 5.*

### Step 1: who starts the service when there's no Docker?

On a plain Linux server (a VM, bare metal, the machine under your Kubernetes nodes) the process that starts services is **systemd**, which is PID 1 of the whole machine. It does for a service what Docker and Kubernetes do for a container: starts it at boot, restarts it when it crashes, stops it with SIGTERM then SIGKILL, collects its logs, and puts it in its own cgroup. You describe the service in a **unit file**.

The minimum, what most people write the first time:

```ini title="svc/deploy/api-plain.service"
[Unit]
Description=Meridian quote API (first try)

[Service]
ExecStart=/usr/local/bin/api -rates http://127.0.0.1:9090

[Install]
WantedBy=multi-user.target
```

It works. It runs `api` as root, with access to the whole filesystem and every capability, never restarts it, and gives it no memory limit. Here's the unit this chapter uses, in three parts. First, what to run and when:

```ini title="svc/deploy/api.service · lines 1–18"
[Unit]
Description=Meridian quote API
Wants=rates.service
After=rates.service
# If it has been restarted 5 times within 60 s, stop trying.
StartLimitIntervalSec=60s
StartLimitBurst=5

[Service]
Type=exec
ExecStart=/usr/local/bin/api -addr :8080 -rates http://127.0.0.1:9090 -grace 8s

# Crash? Start it again, 2 s later.
Restart=on-failure
RestartSec=2s

# systemctl stop sends SIGTERM, waits this long, then sends SIGKILL.
TimeoutStopSec=10s
```

- **`Type=exec`**: the service counts as started once the binary has been exec'd. (`Type=simple` counts it before, so a typo in the path looks like a successful start.)
- **`Restart=on-failure`**: if it exits with a non-zero status or is killed by a signal, start it again after **`RestartSec=2s`**. The two `StartLimit` lines stop a service that crashes on startup from being restarted in a tight loop forever; they belong in `[Unit]`, which is the next step's story.
- **`TimeoutStopSec=10s`**: how `systemctl stop` works is exactly `docker stop`: SIGTERM, wait this long, SIGKILL. `api`'s own `-grace 8s` fits inside it.

Then its resources, the things stops 2 and 4 were about:

```ini title="svc/deploy/api.service · lines 20–23"
# Resources: a cgroup memory limit, the GC told about it, and room for fds.
MemoryMax=256M
Environment=GOMEMLIMIT=230MiB
LimitNOFILE=65536
```

systemd puts every service in its own cgroup, so **`MemoryMax=`** is `memory.max` for this service, **`GOMEMLIMIT`** is set to 90% of it, and **`LimitNOFILE=`** sets the fd limit, soft and hard.

Then the sandbox:

```ini title="svc/deploy/api.service · lines 25–50"
# Sandboxing: a throwaway user, a read-only system, no privileges.
DynamicUser=yes
NoNewPrivileges=yes
ProtectSystem=strict
ProtectHome=yes
PrivateTmp=yes
PrivateDevices=yes
ProtectKernelTunables=yes
ProtectKernelModules=yes
ProtectKernelLogs=yes
ProtectControlGroups=yes
ProtectClock=yes
ProtectHostname=yes
ProtectProc=invisible
ProcSubset=pid
RestrictAddressFamilies=AF_INET AF_INET6 AF_UNIX
RestrictNamespaces=yes
RestrictRealtime=yes
RestrictSUIDSGID=yes
LockPersonality=yes
MemoryDenyWriteExecute=yes
CapabilityBoundingSet=
SystemCallArchitectures=native
SystemCallFilter=@system-service
SystemCallFilter=~@privileged @resources
UMask=0077
```

Each line takes away something `api` doesn't need. **`DynamicUser=yes`** runs it as a user that systemd creates when it starts and deletes when it stops, so it owns nothing on the machine. **`ProtectSystem=strict`** mounts the whole filesystem read-only for it. **`CapabilityBoundingSet=`** (empty) drops every root capability. **`SystemCallFilter=`** installs a seccomp filter that allows the system calls ordinary services use and kills the process on anything else, such as loading a kernel module. **`RestrictAddressFamilies=`** allows IPv4, IPv6 and Unix sockets, and nothing more exotic. If an attacker finds a bug in `api`, this is the difference between owning the process and owning the server.

### Step 2: check the unit before you trust it

`systemd-analyze verify` reads a unit the way systemd will. The first draft of this unit had the two `StartLimit` lines under `[Service]`:

## Exercises

<Exercise n={1} title="Log your limits at startup" level="easy">

`api` logs its `nofile` limit when it starts. Extend it to log the cgroup's memory limit too (`/sys/fs/cgroup/memory.max`, which holds a number of bytes or the word `max`) and the `GOMEMLIMIT` the runtime is actually using. Then warn if `GOMEMLIMIT` is unset or higher than the cgroup limit.

<Solution>

Read the file with `os.ReadFile`, trim it, and treat `max` as no limit. `debug.SetMemoryLimit(-1)` returns the current limit without changing it (a negative argument means "just report"); with no `GOMEMLIMIT` it's `math.MaxInt64`. Log both with `slog.Info`, and `slog.Warn` if the runtime's limit is `math.MaxInt64` or larger than the cgroup's. On a Mac or any machine without the file, skip the check instead of failing: the service has to start there too.

</Solution>

</Exercise>

<Exercise n={2} title="Fail readiness before you stop" level="medium">

Add `GET /healthz` to `api`: 200 while serving, 503 from the moment `ctx` is cancelled. Then, before calling `srv.Shutdown`, keep serving for a configurable `-drain-delay` (say 5 s) so a load balancer has time to notice the 503 and stop sending traffic. Test it with a loop of curls during `docker stop`.

<Solution>

Keep an `atomic.Bool` named `stopping`. The health handler returns 503 when it's set. After `<-ctx.Done()`: `stopping.Store(true)`, `time.Sleep(*drainDelay)`, then `Shutdown` as before. The grace period must now cover both: 5 s of delay plus up to 8 s of shutdown is 13 s, so `docker stop -t 15`, `TimeoutStopSec=15s`, or `terminationGracePeriodSeconds: 15`. During the delay, requests still get answers, which is the point: the orchestrator's view of the pod catches up while nothing is refused.

</Solution>

</Exercise>

<Exercise n={3} title="Type=notify" level="medium">

With `Type=exec`, systemd considers `api` started as soon as the binary runs, before it's listening. With `Type=notify`, the service tells systemd when it's ready, by sending the datagram `READY=1` to the Unix socket named in the `NOTIFY_SOCKET` environment variable. Implement it with the standard library only, and send it after `net.Listen` succeeds.

<Solution>

Split `ListenAndServe` into `ln, err := net.Listen("tcp", *addr)` and `go srv.Serve(ln)`, so you know the port is open. Then: read `os.Getenv("NOTIFY_SOCKET")`; if it's empty, you aren't under systemd, so do nothing. If it starts with `@`, replace that with a zero byte (an abstract socket). `net.DialUnix("unixgram", nil, &net.UnixAddr{Name: name, Net: "unixgram"})`, write `READY=1`, close. On shutdown, send `STOPPING=1` the same way. In the unit, change `Type=exec` to `Type=notify`: systemd creates the socket and sets `NOTIFY_SOCKET` itself. `systemctl start api` then waits until the datagram arrives.

</Solution>

</Exercise>

<Exercise n={4} title="A Go PID 1 that reaps" level="hard">

Stop 1 showed that a process nobody waits for stays a zombie, and chapter 1 that a Go PID 1 doesn't reap orphans. Write the reaping loop yourself: on `SIGCHLD`, call `syscall.Wait4(-1, &ws, syscall.WNOHANG, nil)` until it returns 0. Then start a child with `os/exec` and call `cmd.Wait()`. What goes wrong, and what does that tell you about using tini?

<Solution>

The loop reaps *every* child, including the one os/exec started, so `cmd.Wait()` finds its child already reaped and fails with `ECHILD` ("no child processes"), and its exit status is gone. A reaper and os/exec fight over the same children. You could track which PIDs are yours, but the simple, robust answer is the one tini gives: a tiny separate PID 1 that reaps orphans and forwards signals, with your Go service as its only child, so the service's own `Wait` calls are left alone. That's `docker run --init`, or tini in the image's `ENTRYPOINT`.

</Solution>

</Exercise>

func readRate(path string) (float64, error) {

<Recap>

- **Processes**: `/proc/<pid>/` is the kernel's view of every process: state, parent, threads (a Go process had 5), binary, arguments. `os/exec` starts a child with a vfork-style `clone` then `execve`, and waits on a pidfd. A child nobody waits for stays a **zombie** (state `Z`) until `cmd.Wait()`. Death by signal N is reported as **128 + N**: 143 for SIGTERM, 137 for SIGKILL.
- **File descriptors**: files, sockets, pipes and the runtime's poller share one table per process. Go raises its soft `RLIMIT_NOFILE` to the hard limit minus one, so the hard limit is what counts. One unclosed response body per failed request took `api` to **1,024 of 1,024** fds in 1,250 requests, and then good requests failed too; `defer resp.Body.Close()` straight after the error check kept it at **9**.
- **Signals**: `docker stop`, Kubernetes and `systemctl stop` send SIGTERM, wait, then SIGKILL. With no handler, `api` died at once (**143**) and cut off the request in flight; with `signal.NotifyContext` and `srv.Shutdown`, it finished the request and exited **0** in 3.0 s. PID 1 only gets signals it handles: a shell entrypoint without `exec` made stop take **10.7 s** and end in **137**. SIGQUIT dumps every goroutine.
- **Memory limits**: 60 MiB of cache peaked at **175.7 MiB** with default GC settings and was **OOM-killed (137)** in a 100 MiB container; `GOMEMLIMIT=90MiB` held it at **88 to 90 MiB** with 442 GCs instead of 102. Too low a GOMEMLIMIT slows the service rather than killing it.
- **systemd**: a unit with `Restart=on-failure`, `TimeoutStopSec`, `MemoryMax`, `GOMEMLIMIT`, `LimitNOFILE` and a sandbox. `systemd-analyze verify` caught a key in the wrong section; `security` went from **9.6 UNSAFE** to **1.2 OK**. Killed, it was back in 2.2 s; stopped, it drained and exited 0.

</Recap>
