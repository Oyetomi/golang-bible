<HeroCard label="Part 4 · Chapter 5" title="Kubernetes from the Inside">

Most people meet Kubernetes as YAML: write a Deployment, `kubectl apply`, and pods appear. Why they appear, and why they come back when they die, is the part that matters when something goes wrong. The answer is one idea repeated everywhere: **controllers**. The cluster stores what you want; dozens of small loops each watch one kind of thing and keep changing the world until it matches.

This chapter learns that idea by writing a controller. It's an **operator** (a controller for your own kind of resource) that runs the Redis track's kv server when you ask for a `KVServer`, keeps it the way you asked, and cleans up when you delete it. Along the way it hits a bug that nearly every first operator has, and we measure it and fix it.

Six stops:

1. **A database of intentions.** What Kubernetes stores, and who acts on it.
2. **The controller pattern.** Watches, a work queue, and why reconciling is level-triggered.
3. **A resource of our own.** A `KVServer` type in Go, and the CRD generated from it.
4. **The reconciler.** Desired state, actual state, and the writes in between, bit by bit.
5. **Running it.** Creating, drifting, stopping, restarting and deleting, all measured.
6. **A quiet operator.** Twelve writes that changed nothing, and a test against a real API server.

## Intentions

*Stop 1 of 6.*

### Step 1: a Deployment is a wish

Here is the kv server with nothing but Kubernetes' own objects: a **Deployment** that says "keep one pod like this running", and a **Service** that gives it a stable name.

```yaml title="k8s/deployment.yaml"
# The kv server with nothing but Kubernetes' own objects: a Deployment that
# keeps one pod running, and a Service that gives it a stable name.
apiVersion: apps/v1
kind: Deployment
metadata:
  name: kv
spec:
  replicas: 1
  selector:
    matchLabels:
      app: kv
  template:
    metadata:
      labels:
        app: kv
    spec:
      containers:
        - name: kv
          image: kv-server:lesson10
          imagePullPolicy: Never # loaded into the cluster with kind load
          ports:
            - containerPort: 6380
          readinessProbe:
            tcpSocket:
              port: 6380
            periodSeconds: 1
---
apiVersion: v1
kind: Service
metadata:
  name: kv
spec:
  selector:
    app: kv
  ports:
    - port: 6380
```

`kubectl apply` doesn't start anything itself. It stores these two objects in the **API server**, which keeps them in etcd, a replicated key-value store. From then on, other programs do the work: the Deployment controller sees a Deployment with no pods and creates a ReplicaSet, the ReplicaSet controller creates a pod, the scheduler picks a node for it, and the kubelet on that node starts the container. None of them talk to each other. Each watches the API server and acts on what it sees.

### Step 2: measured

On a kind cluster (Kubernetes 1.37.0 in a Docker container), apply it, then delete the pod:

```text
$ kubectl apply -f k8s/deployment.yaml
deployment.apps/kv created
service/kv created
$ kubectl get pods -l app=kv
NAME                  READY   STATUS    RESTARTS   AGE
kv-5b967567d8-hxj99   1/1     Running   0          1s
$ kubectl delete pod kv-5b967567d8-hxj99
pod "kv-5b967567d8-hxj99" deleted from default namespace
$ kubectl get pods -l app=kv
NAME                  READY   STATUS        RESTARTS   AGE
kv-5b967567d8-hxj99   1/1     Terminating   0          2s
kv-5b967567d8-x6pgp   1/1     Running       0          1s
a new pod was Ready 0.6 s after the delete
```

A new pod was ready **0.6 seconds** after the delete. Nobody told Kubernetes to replace it: the ReplicaSet controller saw one pod where one was wanted, then zero, and made one. (The old pod sits in `Terminating` because our server doesn't handle `SIGTERM`, so Kubernetes waits out the 30-second grace period before killing it; chapter 2 showed the fix.)

From inside the cluster, the Service name reaches it, and a client pod running the real `redis-cli` talks to it:

```text
$ kubectl exec cli -- redis-cli -h kv -p 6380 SET greeting "Ẹ káàárọ̀"
OK
$ kubectl exec cli -- redis-cli --raw -h kv.default.svc.cluster.local -p 6380 GET greeting
Ẹ káàárọ̀
```

### Step 3: what "healed" doesn't mean

Now delete the pod again, after storing something:

```text
$ kubectl exec cli -- redis-cli --no-raw -h kv -p 6380 SET greeting "Ẹ káàárọ̀"
OK
$ kubectl delete pod kv-5b967567d8-f2r8c
pod "kv-5b967567d8-f2r8c" deleted from default namespace
$ kubectl exec cli -- redis-cli --no-raw -h kv -p 6380 GET greeting
(nil)
```

`(nil)`. Kubernetes replaced the **pod**, not the **data**: our server keeps everything in memory, and a new pod is a new, empty process. Self-healing restores the intention ("one pod running this image"), nothing more. Keeping data across restarts is the server's job (the Redis track's persistence module) or a volume's.

## Controllers

*Stop 2 of 6.*

### Step 1: watch, queue, reconcile

Every controller has the same shape:

- It **watches** the API server for changes to the kinds it cares about. The API server streams events: added, modified, deleted.
- Each event puts the affected object's **key** (namespace and name) on a **work queue**. The queue holds each key at most once, so ten events for one object while the worker is busy become a single entry.
- A worker takes a key and calls **Reconcile**: read the object's desired state, read the actual state, and make changes until they match.

The crucial detail is what Reconcile is **not** given: the event. It gets only the key. It can't know whether it was called because someone scaled a Deployment, deleted a pod, or the controller just started, and it doesn't need to: it looks at the whole desired state and the whole actual state every time. That's called **level-triggered** (acting on the current level) as opposed to **edge-triggered** (acting on each change), and it's what makes controllers robust: a missed event, a crash or a restart just means the next reconcile fixes everything at once.

### Step 2: an operator is just a controller for your own kind

Kubernetes ships controllers for its built-in kinds. An **operator** is a controller you write for a kind you define, usually encoding what a human operator would do for some piece of software: create its pieces, keep them configured, repair them. Ours will turn a `KVServer` into a Deployment and a Service, and hold them there.

## A Resource

*Stop 3 of 6.*

### Step 1: the type, in Go

A custom resource starts as a Go type:

```go noverify title="kv-operator/api/v1alpha1/kvserver_types.go · lines 5–40"
// KVServerSpec is what the user asks for.
type KVServerSpec struct {
	// Image is the kv server's container image.
	// +kubebuilder:default="kv-server:lesson10"
	Image string `json:"image,omitempty"`

	// Port is the TCP port the server listens on, and the Service exposes.
	// +kubebuilder:default=6380
	// +kubebuilder:validation:Minimum=1024
	// +kubebuilder:validation:Maximum=65535
	Port int32 `json:"port,omitempty"`
}

// KVServerStatus is what the operator reports back.
type KVServerStatus struct {
	// ReadyReplicas is how many of the server's pods are ready: 0 or 1.
	ReadyReplicas int32 `json:"readyReplicas"`
	// Endpoint is the address clients inside the cluster connect to.
	Endpoint string `json:"endpoint,omitempty"`
	// ObservedGeneration is the spec generation this status describes.
	ObservedGeneration int64 `json:"observedGeneration,omitempty"`
}

// KVServer runs one kv server: a Deployment with one pod, and a Service.
// +kubebuilder:object:root=true
// +kubebuilder:subresource:status
// +kubebuilder:resource:shortName=kvs
// +kubebuilder:printcolumn:name="Ready",type=integer,JSONPath=`.status.readyReplicas`
// +kubebuilder:printcolumn:name="Endpoint",type=string,JSONPath=`.status.endpoint`
type KVServer struct {
	metav1.TypeMeta   `json:",inline"`
	metav1.ObjectMeta `json:"metadata,omitempty"`

	Spec   KVServerSpec   `json:"spec,omitempty"`
	Status KVServerStatus `json:"status,omitempty"`
}
```

Every Kubernetes object has the same outline: `TypeMeta` (its kind and API version), `ObjectMeta` (name, namespace, labels, owner references), a **spec** (what the user wants) and a **status** (what the controller observed). Users write the spec; only the controller writes the status. The `// +kubebuilder:` comments are **markers**: `default=6380`, `Minimum=1024`, `subresource:status`, extra columns for `kubectl get`. They mean nothing to the Go compiler; a code generator reads them.

### Step 2: generating the CRD

`controller-gen`, installed as a Go tool (`go get -tool sigs.k8s.io/controller-tools/cmd/controller-gen`), reads the types and markers and writes two things: `zz_generated.deepcopy.go` (Kubernetes needs every type to be deep-copyable) and the **CustomResourceDefinition**, the YAML that teaches the API server the new kind. The spec part of the generated schema:

```yaml title="kv-operator/config/crd/kv.gobible.dev_kvservers.yaml · the spec schema"
          spec:
            description: KVServerSpec is what the user asks for.
            properties:
              image:
                default: kv-server:lesson10
                description: Image is the kv server's container image.
                type: string
              port:
                default: 6380
                description: Port is the TCP port the server listens on, and the Service
                  exposes.
                format: int32
                maximum: 65535
                minimum: 1024
                type: integer
            type: object
```

The markers became OpenAPI: defaults, a minimum and a maximum. Installing it:

```text
$ kubectl apply -f config/crd/
customresourcedefinition.apiextensions.k8s.io/kvservers.kv.gobible.dev unchanged
$ kubectl get crd kvservers.kv.gobible.dev
NAME                       SCOPE        VERSIONS            CREATED AT
kvservers.kv.gobible.dev   Namespaced   v1alpha1(storage)   2026-09-28T02:26:14Z
```

### Step 3: the API server enforces it

The schema is enforced by the API server itself, before any controller sees the object:

```text
$ kubectl apply -f - <<EOF
apiVersion: kv.gobible.dev/v1alpha1
kind: KVServer
metadata:
  name: web
spec:
  port: 80
EOF
The KVServer "web" is invalid: spec.port: Invalid value: 80: spec.port in body should be greater than or equal to 1024
```

No operator code ran. A good CRD rejects bad input at the door, so the reconciler can trust what it reads.

## The Reconciler

*Stop 4 of 6.*

### Step 1: read the desired state

```go noverify title="kv-operator/internal/controller/kvserver_controller.go · lines 30–41"
// Reconcile is called whenever a KVServer, or anything it owns, changes. It
// doesn't ask what changed: it compares the whole desired state with the
// whole actual state and fixes any difference.
func (r *KVServerReconciler) Reconcile(ctx context.Context, req ctrl.Request) (ctrl.Result, error) {
	logger := log.FromContext(ctx)

	var kvs kvv1.KVServer
	if err := r.Get(ctx, req.NamespacedName, &kvs); err != nil {
		// Deleted: its Deployment and Service go with it (owner references).
		return ctrl.Result{}, client.IgnoreNotFound(err)
	}
	labels := map[string]string{"app.kubernetes.io/name": "kv", "app.kubernetes.io/instance": kvs.Name}
```

`Reconcile` receives only `req.NamespacedName`, the key. It fetches the `KVServer`; if it's gone (`NotFound`), there's nothing to do, because its Deployment and Service are deleted with it (step 4 shows how). The labels identify the pieces this `KVServer` owns.

### Step 2: the Deployment, exactly one replica

```go noverify title="kv-operator/internal/controller/kvserver_controller.go · lines 43–85"
	// The Deployment: exactly one replica, whatever anyone else set.
	wantDep := appsv1.DeploymentSpec{
		Replicas: ptr.To[int32](1), // one store: replicas would be separate, disagreeing stores
		Selector: &metav1.LabelSelector{MatchLabels: labels},
		Template: corev1.PodTemplateSpec{
			ObjectMeta: metav1.ObjectMeta{Labels: labels},
			Spec: corev1.PodSpec{Containers: []corev1.Container{{
				Name:            "kv",
				Image:           kvs.Spec.Image,
				ImagePullPolicy: corev1.PullIfNotPresent,
				Args:            []string{"-addr", fmt.Sprintf("0.0.0.0:%d", kvs.Spec.Port)},
				Ports:           []corev1.ContainerPort{{ContainerPort: kvs.Spec.Port}},
				ReadinessProbe: &corev1.Probe{
					ProbeHandler:  corev1.ProbeHandler{TCPSocket: &corev1.TCPSocketAction{Port: intstr.FromInt32(kvs.Spec.Port)}},
					PeriodSeconds: 1,
					// Kubernetes' defaults, written out: DeepDerivative skips
					// empty strings and nil pointers, but compares numbers
					// exactly, so a 0 here would never match the server's 1.
					TimeoutSeconds:   1,
					SuccessThreshold: 1,
					FailureThreshold: 3,
				},
			}}},
		},
	}
	dep := &appsv1.Deployment{ObjectMeta: metav1.ObjectMeta{Name: kvs.Name, Namespace: kvs.Namespace}}
	op, err := controllerutil.CreateOrUpdate(ctx, r.Client, dep, func() error {
		dep.Labels = labels
		// The API server fills in defaults we never set (termination message
		// path, protocol, ...). DeepDerivative ignores fields left empty in
		// wantDep, so we only overwrite the spec when something we care about
		// differs. Otherwise every reconcile would write an update.
		if !equality.Semantic.DeepDerivative(wantDep, dep.Spec) {
			dep.Spec = wantDep
		}
		return controllerutil.SetControllerReference(&kvs, dep, r.Scheme)
	})
	if err != nil {
		return ctrl.Result{}, err
	}
	if op != controllerutil.OperationResultNone {
		logger.Info("deployment "+string(op), "name", dep.Name)
	}
```

`wantDep` is the whole desired Deployment spec. **One replica, always**, because our server has no replication: three replicas behind one Service would be three separate stores, and a `SET` on one and a `GET` on another would disagree. The operator encodes that knowledge so users can't get it wrong.

`controllerutil.CreateOrUpdate` fetches the Deployment (or starts from an empty one), runs the function we give it to set the fields we care about, and then creates it, updates it or does nothing, depending on whether anything changed. Inside, `DeepDerivative` and the probe's written-out defaults are the fix from stop 6; for now, read them as "only overwrite the spec if it differs". `SetControllerReference` records the `KVServer` as the Deployment's **owner**.

### Step 3: the Service, and the status

```go noverify title="kv-operator/internal/controller/kvserver_controller.go · lines 87–112"
	// The Service: a stable name in front of the pod.
	wantSvc := corev1.ServiceSpec{
		Selector: labels,
		Ports:    []corev1.ServicePort{{Port: kvs.Spec.Port, TargetPort: intstr.FromInt32(kvs.Spec.Port)}},
	}
	svc := &corev1.Service{ObjectMeta: metav1.ObjectMeta{Name: kvs.Name, Namespace: kvs.Namespace}}
	op, err = controllerutil.CreateOrUpdate(ctx, r.Client, svc, func() error {
		svc.Labels = labels
		if !equality.Semantic.DeepDerivative(wantSvc, svc.Spec) {
			svc.Spec.Selector, svc.Spec.Ports = wantSvc.Selector, wantSvc.Ports
		}
		return controllerutil.SetControllerReference(&kvs, svc, r.Scheme)
	})
	if err != nil {
		return ctrl.Result{}, err
	}
	if op != controllerutil.OperationResultNone {
		logger.Info("service "+string(op), "name", svc.Name)
	}

	// Report what we found.
	kvs.Status.ReadyReplicas = dep.Status.ReadyReplicas
	kvs.Status.Endpoint = fmt.Sprintf("%s.%s.svc:%d", svc.Name, svc.Namespace, kvs.Spec.Port)
	kvs.Status.ObservedGeneration = kvs.Generation
	return ctrl.Result{}, r.Status().Update(ctx, &kvs)
}
```

The Service is the same pattern. Last, the reconciler reports what it found: ready replicas, the endpoint clients should use, and `observedGeneration`, the spec version this status describes, so a client can tell whether the operator has caught up with its last edit. Status goes through `r.Status().Update`, a separate subresource, so users editing the spec and the operator writing status never overwrite each other.

### Step 4: what triggers it

```go noverify title="kv-operator/internal/controller/kvserver_controller.go · lines 114–122"
// SetupWithManager wires the reconciler to its triggers: KVServers, and the
// Deployments and Services they own.
func (r *KVServerReconciler) SetupWithManager(mgr ctrl.Manager) error {
	return ctrl.NewControllerManagedBy(mgr).
		For(&kvv1.KVServer{}).
		Owns(&appsv1.Deployment{}).
		Owns(&corev1.Service{}).
		Complete(r)
}
```

`For(&KVServer{})` watches `KVServer`s. `Owns(&Deployment{})` watches Deployments too, and maps each event to its **owner's** key, through the owner reference `SetControllerReference` wrote. So a change to the Deployment, including someone scaling or deleting it, reconciles the `KVServer` that owns it.

### Step 5: main

```go noverify title="kv-operator/cmd/operator/main.go · lines 19–49"
func main() {
	// controller-runtime serves Prometheus metrics on :8080 by default; "0"
	// turns that off, so the operator can't clash with anything on the port.
	metricsAddr := flag.String("metrics-addr", "0", "address for the metrics endpoint, or 0 for none")
	flag.Parse()
	ctrl.SetLogger(zap.New(zap.UseDevMode(true)))
	log := ctrl.Log.WithName("setup")

	scheme := runtime.NewScheme()
	_ = clientgoscheme.AddToScheme(scheme) // Deployments, Services, ...
	_ = kvv1.AddToScheme(scheme)           // KVServer

	mgr, err := ctrl.NewManager(ctrl.GetConfigOrDie(), ctrl.Options{
		Scheme:  scheme,
		Metrics: metricsserver.Options{BindAddress: *metricsAddr},
	})
	if err != nil {
		log.Error(err, "creating the manager")
		os.Exit(1)
	}
	r := &controller.KVServerReconciler{Client: mgr.GetClient(), Scheme: mgr.GetScheme()}
	if err := r.SetupWithManager(mgr); err != nil {
		log.Error(err, "setting up the controller")
		os.Exit(1)
	}
	log.Info("starting")
	if err := mgr.Start(ctrl.SetupSignalHandler()); err != nil {
		log.Error(err, "running")
		os.Exit(1)
	}
}
```

The **manager** holds the shared pieces: a client, the watches and their caches, and the controllers. `GetConfigOrDie` reads your kubeconfig, the same one `kubectl` uses. The metrics flag is there because of the first run, which died within a second:

```text
2026-09-28T03:28:29+01:00	INFO	Starting workers	{"controller": "kvserver", "controllerGroup": "kv.gobible.dev", "controllerKind": "KVServer", "worker count": 1}
2026-09-28T03:28:29+01:00	INFO	Shutdown signal received, waiting for all workers to finish	{"controller": "kvserver", "controllerGroup": "kv.gobible.dev", "controllerKind": "KVServer"}
2026-09-28T03:28:29+01:00	ERROR	setup	running	{"error": "failed to start metrics server: failed to create listener: listen tcp :8080: bind: address already in use"}
```

controller-runtime serves Prometheus metrics on port 8080 by default, and another program on this machine already had it. The manager treats a failed runnable as fatal and shuts everything down, which is why the log says "Shutdown signal received" although nobody sent a signal. Now the metrics server is off unless you ask for it.

## A Quiet Operator

*Stop 6 of 6.*

### Step 1: twelve writes that changed nothing

The first working version of the reconciler set the whole spec on every call:

```go noverify title="kv-operator/internal/controller/kvserver_controller.go · the first version"
op, err := controllerutil.CreateOrUpdate(ctx, r.Client, dep, func() error {
	dep.Labels = labels
	dep.Spec.Replicas = ptr.To[int32](1) // one store: replicas would be separate, disagreeing stores
	dep.Spec.Selector = &metav1.LabelSelector{MatchLabels: labels}
	dep.Spec.Template.Labels = labels
	dep.Spec.Template.Spec.Containers = []corev1.Container{{
		Name:            "kv",
		Image:           kvs.Spec.Image,
		ImagePullPolicy: corev1.PullIfNotPresent,
		Args:            []string{"-addr", fmt.Sprintf("0.0.0.0:%d", kvs.Spec.Port)},
		Ports:           []corev1.ContainerPort{{ContainerPort: kvs.Spec.Port}},
		ReadinessProbe: &corev1.Probe{
			ProbeHandler:  corev1.ProbeHandler{TCPSocket: &corev1.TCPSocketAction{Port: intstr.FromInt32(kvs.Spec.Port)}},
			PeriodSeconds: 1,
		},
	}}
	return controllerutil.SetControllerReference(&kvs, dep, r.Scheme)
})
```

It worked, and its log looked busy. `podkill.sh` counts the operator's writes after deleting the server's pod once:

```text
one pod deleted: the operator reported 12 Deployment/Service updates in the next 10 s
the Deployment's spec generation stayed at 1 -> 1: none of them changed anything
```

**Twelve** updates, and the spec's `generation` (which the API server increments on every real spec change) didn't move. Why? The API server **fills in defaults** for fields we never set: every container port gets `protocol: TCP`, every probe a timeout of 1 second, and many more. Our function replaced the container list with one without those fields, so `CreateOrUpdate` saw a difference from what the server held, and sent an update. The API server applied the defaults again, found the result identical, and changed nothing. Every pod status change reconciled the `KVServer`, and every reconcile sent pointless writes. On a cluster with hundreds of objects, that's load on the API server and etcd for nothing.

### Step 2: compare only what you set

The fix has two parts, both in the reconciler above. First, build the desired spec separately and only assign it if it differs, using `equality.Semantic.DeepDerivative`, which ignores fields the desired value leaves empty:

```text
one pod deleted: the operator reported 6 Deployment/Service updates in the next 10 s
the Deployment's spec generation stayed at 1 -> 1: none of them changed anything
```

Half. A debug build printed which part still differed: the readiness probe. `DeepDerivative` skips empty strings, nil pointers and empty slices and maps, but it compares numbers exactly (in apimachinery's `deepValueDerive`, a number falls through to plain `==`). Our probe left `TimeoutSeconds`, `SuccessThreshold` and `FailureThreshold` at 0, and the server's defaults are 1, 1 and 3. Second part of the fix: write those defaults out explicitly (lines 58–63 above):

```text
one pod deleted: the operator reported 0 Deployment/Service updates in the next 10 s
the Deployment's spec generation stayed at 1 -> 1: none of them changed anything
```

**Zero.** The operator now writes only when something it owns is actually wrong. The same trap exists in most operators, and the symptom is always the same: an operator that logs "updated" when nothing changed.

<UnderTheHood title="The cache behind the client">

`mgr.GetClient()` doesn't send every `Get` to the API server. Reads come from an in-memory cache, kept up to date by the same watches that trigger reconciles (an informer per kind); only writes go to the API server. That's why a reconcile can read freely, and also why a write that changes nothing is worth avoiding: reads are local, writes are a round trip to the API server and a transaction in etcd. It also means a reconcile can read slightly stale data right after its own write, which is fine for a level-triggered loop: if something's still wrong, the event from that write triggers another reconcile.

</UnderTheHood>

### Step 3: a test against a real API server

**envtest** runs a real `kube-apiserver` and `etcd` on your machine, with no nodes (so no pods ever run), which is exactly what a controller test needs: real API semantics, defaults, validation and owner references. `go tool setup-envtest use` downloaded the Kubernetes 1.37.0 binaries.

## Exercises

<Exercise n={1} title="Handle SIGTERM" level="easy">

Deleted pods sat in `Terminating` for 30 seconds. Make the kv server shut down on `SIGTERM` (chapter 2's `signal.NotifyContext`), rebuild the image, load it into kind, and measure how long a deleted pod now takes to disappear.

<Solution>

Wrap `Serve` so a `SIGTERM` closes the listener and returns, and `main` exits. Kubernetes sends `SIGTERM` first and only kills the container when the grace period (30 s by default) runs out, so once the server exits on `SIGTERM` the pod is gone as soon as the process ends, instead of after the full 30 seconds. Measure it the way `selfheal.sh` does, polling until the old pod no longer exists.

</Solution>

</Exercise>

<Exercise n={2} title="A condition in the status" level="medium">

Add a `Conditions []metav1.Condition` field to the status and set a `Ready` condition (`True`/`False` with a reason) with `meta.SetStatusCondition`. Why do conditions beat a single `phase` string?

<Solution>

Add `// +listType=map` and `// +listMapKey=type` markers, regenerate, and in `Reconcile` call `meta.SetStatusCondition(&kvs.Status.Conditions, metav1.Condition{Type: "Ready", Status: ..., Reason: "PodReady", ObservedGeneration: kvs.Generation})`. Conditions can describe several independent facts at once (Ready, Degraded, Progressing), each with a reason, a message and a transition time, and tools like `kubectl wait --for=condition=Ready` understand them.

</Solution>

</Exercise>

<Exercise n={3} title="Persistence" level="hard">

Once the Redis track's persistence module gives the server an append-only file, add a `storage` field to the spec and have the operator create a PersistentVolumeClaim and mount it. Show that the greeting survives a pod deletion.

<Solution>

Create a PVC with `CreateOrUpdate` (owned by the `KVServer` like the rest), add a volume and a volumeMount to the container, and pass the file path as a flag. On kind, the default storage class provisions a host-path volume. Repeat stop 1's experiment: `GET greeting` after deleting the pod now returns the value.

</Solution>

</Exercise>

<Exercise n={4} title="Edge-triggered, on purpose" level="medium">

Rewrite `Reconcile` as if it only reacted to "KVServer created" (create the Deployment) and did nothing otherwise. Which of stop 5's experiments break?

<Solution>

All the drift experiments: a scaled or deleted Deployment is never repaired, and a restart after missed changes fixes nothing. Only creation works. That's the practical difference between edge- and level-triggered: an edge-triggered controller is only as good as the events it happened to receive.

</Solution>

</Exercise>

<Lab

  difficulty="guided"

  verify="self-check"
  expect="ALL CHECKS PASS"

  starter={`package main

import "fmt"

// Deployment is the part of a real Deployment this lab cares about.
type Deployment struct {
	Replicas     int
	Image        string
	ProbeTimeout int // 0 means "not set": the API server stores 1 instead
}

// Spec is what a KVServer asks for.
type Spec struct{ Image string }

// Reconcile makes the cluster's Deployment \`name\` match spec: exactly one
// replica, spec.Image, a probe timeout of 1 s. It runs after any change,
// never knows which one, and must leave a matching Deployment alone (no
// write at all), repair one that drifted, and recreate one that's gone.
func Reconcile(c *Cluster, name string, spec Spec) {
	dep, ok := c.Get(name)
	if !ok {
		return
	}
	want := Deployment{Replicas: 1, Image: spec.Image}
	if want != dep {
		c.Update(name, want)
	}
}

// ── below this line: do not edit ──

// Cluster stands in for the API server: it stores Deployments, fills in
// defaults on every write, and counts writes.
type Cluster struct {
	deps   map[string]Deployment
	writes int
}

func (c *Cluster) Get(name string) (Deployment, bool) { d, ok := c.deps[name]; return d, ok }
func (c *Cluster) Create(name string, d Deployment)   { c.write(name, d) }
func (c *Cluster) Update(name string, d Deployment)   { c.write(name, d) }
func (c *Cluster) write(name string, d Deployment) {
	if d.ProbeTimeout == 0 {
		d.ProbeTimeout = 1 // the API server's default
	}
	c.deps[name] = d
	c.writes++
}

func main() {
	ok := true
	fail := func(f string, a ...any) { fmt.Printf("FAIL "+f+"\\n", a...); ok = false }
	c := &Cluster{deps: map[string]Deployment{}}
	spec := Spec{Image: "kv-server:lesson10"}
	want := Deployment{Replicas: 1, Image: "kv-server:lesson10", ProbeTimeout: 1}

	step := func(name string, maxWrites int) {
		before := c.writes
		Reconcile(c, "cache", spec)
		d, found := c.Get("cache")
		if !found || d != want {
			fail("%s: Deployment is %+v (exists: %v), want %+v", name, d, found, want)
		}
		if w := c.writes - before; w > maxWrites {
			fail("%s: %d writes, want at most %d", name, w, maxWrites)
		}
	}

	step("a new KVServer", 1)
	step("nothing changed", 0)
	step("nothing changed, again", 0)

	d, _ := c.Get("cache")
	d.Replicas = 3 // someone ran kubectl scale
	c.deps["cache"] = d
	step("scaled to 3 by hand", 1)

	delete(c.deps, "cache") // someone ran kubectl delete deployment
	step("Deployment deleted", 1)

	spec.Image = "kv-server:lesson11" // the user edits the KVServer
	want.Image = spec.Image
	step("new image", 1)
	step("settled", 0)

		fmt.Println("ALL CHECKS PASS")

}`}

<Recap>

- Kubernetes stores **intentions**; controllers make them true. A deleted pod was replaced in **0.6 s**, but its in-memory data was gone: the intention was "a pod", not "your data".
- A controller **watches**, queues **keys** (one entry per object, however many events), and **reconciles** whole desired against whole actual state: **level-triggered**, so missed events and restarts repair themselves.
- A custom resource is a Go type with markers; **controller-gen** generates the CRD, and the API server enforces its schema (port 80 was rejected before any operator code ran).
- Our operator holds one replica (0.1 s to undo a scale), recreates a deleted Deployment (ready in 0.6 s), catches up after a restart, and leaves deletion to the **garbage collector** via owner references.
- Writing defaulted fields made **12 pointless writes** per pod deletion; comparing with `DeepDerivative` and writing numeric defaults out made it **0**. An envtest test against a real API server passed in 8.6 s.

</Recap>
