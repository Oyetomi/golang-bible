Read enough Go job listings and one pattern shows up whatever the company: the Go runs on a cloud, and the cloud is usually AWS. Part 4 has so far built the layers under your service (containers, Linux, networks, Kubernetes, SRE, delivery). This chapter builds the layer next to it: the managed services your service calls.

Three of them, because between them they cover most of what a backend asks a cloud for: **S3** to keep files, **SQS** to hand work to another process, **DynamoDB** to keep records that must scale and stay correct. The same ledger domain as Part 3 runs through all three, and every claim comes from a program you can run.

You do not need an AWS account. The programs run against a local AWS emulator, and the chapter is blunt about what that proves and what it can't.

Four stops:

1. **A local AWS.** What we run, and why it is an older version than you'd expect.
2. **S3.** Credentials, objects, presigned URLs, multipart uploads, errors and retries.
3. **SQS.** Polling, the visibility timeout, dead letters, duplicates and a clean shutdown.
4. **DynamoDB.** Table design, conditional writes, transactions, pagination and optimistic locking.

## A Local AWS

*Stop 1 of 4.*

Real AWS costs money, needs an account and is slow to reset. **LocalStack** is an emulator: one container that answers the AWS APIs on `localhost:4566`, so the SDK talks to it exactly as it would to the real thing. The Go code does not change. Only an environment variable does: `AWS_ENDPOINT_URL=http://127.0.0.1:4566`.

```bash title="the local cloud"
docker run -d --name localstack -p 127.0.0.1:4566:4566 \
  -e SERVICES=s3,sqs,dynamodb,iam,sts localstack/localstack:3.8
```

Note the version. When this chapter was written, the `latest` LocalStack image printed *"License activation failed"* and quit: recent versions require an account and an auth token. The pinned 3.8 community image still runs without one, so every output below is from **LocalStack 3.8.1**. That matters for what you can believe:

- **It speaks the API, not the enforcement.** Requests that real AWS would reject (a tampered presigned URL, a policy violation) are often accepted here. The chapter says so wherever it bites.
- **Timing is the emulator's, not AWS's.** Latencies and rates here are for comparing one design against another on the same machine, never for quoting.
- **Real AWS adds failure modes this chapter cannot show**: throttling, regional outages, eventual consistency in places. The programs are written to handle them (typed errors, retries), but those paths are only exercised where we could force them.

Every resource the programs create has a prefix and is deleted when the program ends, because a shared emulator accumulates debris.

## S3

*Stop 2 of 4.*

### Step 1: Build a client, and see where its credentials came from

The SDK is a set of small modules: `config` loads settings, `service/s3` is the client, and the rest is plumbing. `config.LoadDefaultConfig` is the entry point. It builds an `aws.Config` by walking a fixed order of sources. For credentials that order is the **default credential chain**:

1. environment variables (`AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`)
2. the shared files `~/.aws/credentials` and `~/.aws/config` (profile chosen by `AWS_PROFILE`)
3. web identity, SSO or container credentials, when configured
4. the EC2 instance metadata service (IMDS), which is how code running on AWS gets a role without any secret in the image

The point of the chain is that the same binary runs on your laptop, in CI and on AWS, and you change the environment, not the code.

The endpoint works the same way. The SDK reads `AWS_ENDPOINT_URL` (or per service, `AWS_ENDPOINT_URL_S3`) by itself, so the code never mentions LocalStack. The old `EndpointResolverWithOptions` is deprecated; if you must set an endpoint in code, the replacement is the `BaseEndpoint` field on `s3.Options`. The one S3-specific thing set in code is `UsePathStyle`: real S3 addresses `bucket.s3.amazonaws.com/key`, which needs wildcard DNS, so LocalStack wants `host:4566/bucket/key`.

```go noverify title="awsx/awsx.go · lines 16–27"
func New(ctx context.Context, opts ...func(*config.LoadOptions) error) (*s3.Client, aws.Config, error) {
	cfg, err := config.LoadDefaultConfig(ctx, opts...)
	if err != nil {
		return nil, cfg, err
	}
	client := s3.NewFromConfig(cfg, func(o *s3.Options) {
		// LocalStack serves buckets at http://host:4566/bucket/key, not
		// http://bucket.host:4566/key. Harmless against real AWS.
		o.UsePathStyle = true
	})
	return client, cfg, nil
}
```

The probe asks the config for a credential and prints its `Source`:

### Step 3: A presigned GET URL, fetched with plain net/http

A presigned URL is a request signed ahead of time, with the signature moved into the query string. Whoever holds the URL can make exactly that request until it expires, with no credentials of their own. The SDK exposes this as `s3.NewPresignClient`. The consumer is an ordinary HTTP client:

```go noverify title="cmd/presign/main.go · lines 26–40"
func fetch(label, url string) {
	resp, err := http.Get(url) // no SDK, no credentials: the URL is the credential
	if err != nil {
		fmt.Printf("%-9s transport error: %v\n", label, err)
		return
	}
	defer resp.Body.Close()
	b, _ := io.ReadAll(resp.Body)
	text := strings.TrimSpace(string(b))
	if len(text) > 90 {
		text = text[:90] + "..."
	}
	fmt.Printf("%-9s HTTP %d  %s\n", label, resp.StatusCode, strings.ReplaceAll(text, "\n", " "))
}

```


What to read in this output:

- the URL carries `X-Amz-Expires=2` (seconds), `X-Amz-SignedHeaders=host` and a signature;
- presigning a different key gives a completely different signature. The signature is an HMAC over the canonical request (method, path, query, host), so it cannot be moved onto another URL.

**What LocalStack did not do.** The `anon` request succeeded on a private bucket. The `tampered` URL failed only because `other.txt` does not exist (404 `NoSuchKey`, not a signature error). The `expired` request, made 3 seconds after a 2-second URL, still returned 200. LocalStack community 3.8 does not validate presigned signatures or expiry by default. Real S3 answers 403 for the anonymous request, for a signature replayed on another key, and (`Request has expired`) after expiry. We could not verify that 403 behaviour here, so read that sentence as AWS documentation, not as measured output.

### Step 4: Multipart upload of a 25 MB object

A single `PutObject` is capped at 5 GB and cannot resume. The multipart API splits an object into parts (5 MiB minimum, except the last), uploads them independently and in parallel, then stitches them with `CompleteMultipartUpload`. The transfer manager does all of that: it switches to multipart above a size threshold, runs `Concurrency` workers, and aborts the upload on failure so orphaned parts do not accumulate.

The test object is 26,337,857 bytes of `crypto/rand` data (25 MiB plus 123,457 bytes, so the last part is short). Its sha256 is computed locally, without the SDK, and compared after every download.

```go noverify title="cmd/multipart/main.go · lines 91–130"
	for _, conc := range []int{1, 8} {
		tm := transfermanager.New(client, func(o *transfermanager.Options) {
			o.PartSizeBytes = partSize
			o.Concurrency = conc
		})
		var ups, dls []time.Duration
		var parts int
		var etag string
		for run := 0; run < 5; run++ {
			key := fmt.Sprintf("big-c%d-r%d.bin", conc, run)
			keys = append(keys, key)
			src, err := os.Open(f.Name())
			must(err)
			t0 := time.Now()
			out, err := tm.UploadObject(ctx, &transfermanager.UploadObjectInput{
				Bucket: aws.String(bucket), Key: aws.String(key), Body: src})
			must(err)
			ups = append(ups, time.Since(t0))
			src.Close()
			parts, etag = len(out.CompletedParts), aws.ToString(out.ETag)

			dst, err := os.CreateTemp("", "s3sec-dl-*.bin")
			must(err)
			t0 = time.Now()
			_, err = tm.DownloadObject(ctx, &transfermanager.DownloadObjectInput{
				Bucket: aws.String(bucket), Key: aws.String(key), WriterAt: dst})
			must(err)
			dls = append(dls, time.Since(t0))
			dst.Close()
			if got := sum(dst.Name()); got != want {
				fmt.Println("CHECKSUM MISMATCH", key)
				os.Exit(1)
			}
			os.Remove(dst.Name())
		}
		fmt.Printf("\nconcurrency=%d part=%dMiB  parts uploaded=%d  etag=%s\n", conc, partSize>>20, parts, etag)
		fmt.Printf("  upload   median of 5: %v   (all: %v)\n", med(ups), round(ups))
		fmt.Printf("  download median of 5: %v   (all: %v)\n", med(dls), round(dls))
		fmt.Printf("  sha256 of all 5 downloads == local file: true\n")
	}
```

With 40 ms per request, 1 worker uploaded in 612 ms and 8 workers in 305 ms; downloads were 444 ms vs 298 ms. That is the realistic shape: concurrency hides latency, it does not add bandwidth. It is not 8x because 6 parts means at most 6 are in flight, and the final `CompleteMultipartUpload` is serial.

The 60 stderr lines per run are the SDK's logger saying `Skipped validation of multipart checksum.` Each download of a multipart object prints one per part (10 downloads x 6 parts). The uploader attaches a CRC32 per part, a composite value that cannot be compared with a whole-object checksum, so the SDK says it is not checking end to end. That is why this chapter compares sha256 itself.

### Step 5: Errors and retries

Every service error is a typed value that also satisfies `smithy.APIError`. Use `errors.As`, never string matching:

```go noverify title="cmd/errs/main.go · lines 55–79"

	// 1. Missing key: GetObject returns the typed *types.NoSuchKey.
	_, err = client.GetObject(ctx, &s3.GetObjectInput{Bucket: aws.String(bucket), Key: aws.String("nope")})
	var nsk *types.NoSuchKey
	fmt.Println("GetObject missing key")
	fmt.Println("  errors.As(*types.NoSuchKey):", errors.As(err, &nsk))
	var ae smithy.APIError
	if errors.As(err, &ae) {
		fmt.Printf("  smithy.APIError code=%q message=%q fault=%v\n", ae.ErrorCode(), ae.ErrorMessage(), ae.ErrorFault())
	}

	// 2. HeadObject on a missing key: no body to parse -> NOT NoSuchKey.
	_, err = client.HeadObject(ctx, &s3.HeadObjectInput{Bucket: aws.String(bucket), Key: aws.String("nope")})
	fmt.Println("HeadObject missing key")
	fmt.Println("  errors.As(*types.NoSuchKey):", errors.As(err, &nsk))
	fmt.Println("  errors.As(*types.NotFound): ", func() bool { var nf *types.NotFound; return errors.As(err, &nf) }())
	if errors.As(err, &ae) {
		fmt.Printf("  smithy.APIError code=%q\n", ae.ErrorCode())
	}

	// 3. Missing bucket.
	_, err = client.ListObjectsV2(ctx, &s3.ListObjectsV2Input{Bucket: aws.String("s3sec-no-such-bucket")})
	var nsb *types.NoSuchBucket
	fmt.Println("ListObjectsV2 missing bucket")
	fmt.Println("  errors.As(*types.NoSuchBucket):", errors.As(err, &nsb))
```

**The surprise.** `HeadObject` on a missing key does not give you `*types.NoSuchKey`. A HEAD response has no body, so the SDK has no XML error code to parse, only the status, and the error is `*types.NotFound` (code `"NotFound"`). Code that checks `NoSuchKey` around a `HeadObject` never matches and treats a missing file as a hard failure. The fix is to check both types, or branch on `ae.ErrorCode()` being `NoSuchKey` or `NotFound`.

The second half of the output shows the default retryer. `retry.NewStandard()` is what the SDK installs: 3 attempts in total (not 3 retries), exponential backoff with jitter capped at 20 s, and a client-side token bucket that stops retrying when the service is failing broadly. A custom `http.RoundTripper` that returns 503 for the first n requests shows it: fail twice and the third call succeeds (3 HTTP calls); fail five times and you get `*retry.MaxAttemptsError` with `Attempt == 3`, still only 3 HTTP calls. To change the budget use `config.WithRetryMaxAttempts(5)`.

### Step 1: pay for the wait once, not every 100 ms

An SQS queue is a pull system: nothing is pushed to you. A consumer calls `ReceiveMessage`, and by default (`WaitTimeSeconds=0`, *short polling*) the call answers immediately, empty or not. A loop around it is a meter running: every empty answer is a billed request that returned nothing. With `WaitTimeSeconds` up to 20 (*long polling*) the server parks the request until a message arrives or the wait expires, so an idle consumer costs one call per 20 s and a busy one still gets its message the instant it lands.

Every program shares one tiny client that wraps the HTTP transport and counts real requests, so the numbers below are API calls, not guesses.

```go noverify title="sqs/client.go · lines 105–117"

		MaxNumberOfMessages:         max,
		WaitTimeSeconds:             wait,
		MessageSystemAttributeNames: []types.MessageSystemAttributeName{types.MessageSystemAttributeNameAll},
	})
	if err != nil {
		return nil, err
	}
	return out.Messages, nil
```

### Step 2: at-least-once is not a slogan, it is the visibility timeout

When a consumer receives a message, SQS does not remove it. It *hides* it for the queue's visibility timeout and waits for `DeleteMessage`. If the delete never comes, because the process crashed, was OOM-killed or lost its network, the timeout expires and the message becomes visible again for the next consumer. That is the whole mechanism behind "at-least-once": the broker prefers delivering a message twice to losing it once. Exactly-once is something *you* build on top (Step 4).

To make it real, `cmd/redeliver` creates a queue with `VisibilityTimeout=5`, sends a payment, and starts a *child process* (consumer A) that receives it and calls `os.Exit(1)` before deleting. The parent, consumer B, long-polls and times the reappearance from the instant A received.

Now the worker pool. Two rules make shutdown safe. First, bound concurrency by reserving a slot *before* receiving, so you never hold messages you cannot start (an idle in-flight message burns its visibility timeout).
```go noverify title="sqs/worker.go · lines 32–83"
func (p *Pool) Run(ctx context.Context) {
	slots := make(chan struct{}, p.Concurrency)
	var wg sync.WaitGroup
	// Work runs on its own context: cancelling ctx stops *receiving*, never
	// the handlers or their deletes.
	work := context.WithoutCancel(ctx)
	for ctx.Err() == nil {
		// Reserve a slot first, so we never receive more than we can start.
		select {
		case slots <- struct{}{}:
		case <-ctx.Done():
			break
		}
		if ctx.Err() != nil {
			break
		}
		n := 1
		for n < 10 && n < p.Concurrency {
			select {
			case slots <- struct{}{}:
				n++
				continue
			default:
			}
			break
		}
		msgs, err := Receive(ctx, p.Client, p.URL, int32(n), p.Wait)
		for i := len(msgs); i < n; i++ {
			<-slots // give back slots we did not use
		}
		if err != nil {
			continue // ctx cancelled mid-poll, or a transient error: loop re-checks ctx
		}
		for _, m := range msgs {
			p.Stats.Received.Add(1)
			wg.Add(1)
			go func() {
				defer wg.Done()
				defer func() { <-slots }()
				if err := p.Handle(work, m); err != nil {
					p.Stats.Failed.Add(1) // no delete: SQS redelivers after the visibility timeout
					return
				}
				p.Stats.Processed.Add(1)
				if err := Delete(work, p.Client, p.URL, m); err == nil {
					p.Stats.Deleted.Add(1)
				}
			}()
		}
	}
	wg.Wait()
}
```

### Step 1: Design the table around the questions you will ask

DynamoDB stores items in partitions chosen by hashing the **partition key**; inside a partition, items are kept sorted by the **sort key**. You cannot join, and you cannot cheaply ask a question the key does not answer. So you do not design tables from entities; you design from access patterns. Ours are: "get one account", "list one account's entries, newest first or in pages", "move money between two accounts".

One table, two item types sharing a partition. The account is `pk=ACCT#id, sk=ACCT`. Each entry is `pk=ACCT#id, sk=ENT#<timestamp>#<txid>`. Because the timestamp is zero-padded and fixed width, lexicographic sort order equals time order, and "all entries of one account" is a single-partition Query with `begins_with(sk, "ENT#")`. The balance lives on the account item so a debit touches exactly one item.

### Step 3: Conditional writes are the concurrency primitive

DynamoDB has no locks you can take and no multi-statement session. What it has is a check-and-write that happens atomically on the server: `ConditionExpression`. ```go noverify title="ddb/ops.go · lines 28–51"

```go noverify title="ddb/ops.go · lines 28–51"
// The check and the write are ONE operation on the server: nothing can
// interleave between them.
func Debit(ctx context.Context, c *dynamodb.Client, table, id string, amt int64) error {
	cond := expression.Name("balance").GreaterThanEqual(expression.Value(amt))
	upd := expression.Set(expression.Name("balance"), expression.Name("balance").Minus(expression.Value(amt))).
		Add(expression.Name("version"), expression.Value(1))
	expr, err := expression.NewBuilder().WithCondition(cond).WithUpdate(upd).Build()
	if err != nil {
		return err
	}
	_, err = c.UpdateItem(ctx, &dynamodb.UpdateItemInput{
		TableName: aws.String(table), Key: key(id),
		ConditionExpression:       expr.Condition(),
		UpdateExpression:          expr.Update(),
		ExpressionAttributeNames:  expr.Names(),
		ExpressionAttributeValues: expr.Values(),
	})
	if IsConditionFailed(err) {
		return ErrInsufficient
	}
	return err
}
```

### Step 4: TransactWriteItems for a transfer

A transfer touches two accounts, so one conditional update is not enough. `TransactWriteItems` commits up to 100 writes (the documented limit; I did not test it) across items, all or nothing. Ours has four: guarded debit, guarded credit (`attribute_exists(pk)`, so money cannot be sent to a typo), and one ledger entry per side with `attribute_not_exists(pk)`.

```go noverify title="ddb/ops.go · lines 108–135"
// (guarded: the account must exist), and one ledger entry per side. All four
// writes commit or none do. token makes a retry of the same call a no-op.
func Transfer(ctx context.Context, c *dynamodb.Client, table, from, to string, amt int64, txid, token string, at time.Time) error {
	debit := &types.Update{
		TableName: aws.String(table), Key: key(from),
		ConditionExpression:                 aws.String("balance >= :amt"),
		UpdateExpression:                    aws.String("SET balance = balance - :amt ADD version :one"),
		ExpressionAttributeValues:           amtVals(amt),
		ReturnValuesOnConditionCheckFailure: types.ReturnValuesOnConditionCheckFailureAllOld,
	}
	credit := &types.Update{
		TableName: aws.String(table), Key: key(to),
		ConditionExpression:       aws.String("attribute_exists(pk)"),
		UpdateExpression:          aws.String("SET balance = balance + :amt ADD version :one"),
		ExpressionAttributeValues: amtVals(amt),
	}
	eFrom, _ := attributevalue.MarshalMap(NewEntry(from, -amt, txid, at))
	eTo, _ := attributevalue.MarshalMap(NewEntry(to, amt, txid, at))
	_, err := c.TransactWriteItems(ctx, &dynamodb.TransactWriteItemsInput{
		ClientRequestToken: aws.String(token),
		TransactItems: []types.TransactWriteItem{
			{Update: debit}, {Update: credit},
			{Put: &types.Put{TableName: aws.String(table), Item: eFrom, ConditionExpression: aws.String("attribute_not_exists(pk)")}},
			{Put: &types.Put{TableName: aws.String(table), Item: eTo, ConditionExpression: aws.String("attribute_not_exists(pk)")}},
		},
	})
	return err
}
```

Reading it:

- **A**: both balances move, both entries exist, and both versions went to 2 in one commit.

### Step 5: Query, pagination, and why Scan is a trap

A Query reads one partition, in sort order, and charges only for what it reads. A response is capped at 1 MB or at your `Limit`, whichever comes first. If there is more, `LastEvaluatedKey` is non-nil and you pass it back as `ExclusiveStartKey`. The loop is the whole API:

Observations from this run:

- Query with `Limit=100` walked 13 pages for 1,200 entries. The 13th page is empty with a nil `LastEvaluatedKey`: when the count is an exact multiple of `Limit`, DynamoDB cannot know it was the end until it looks. Do not treat an empty page as an error.

The gap grows with every account the table gains, while a Query stays the same size forever. That is why Scan is a trap: it is fine in a test with 20 rows and an outage in production.

### Step 6: Optimistic locking with a version attribute

When you must read, compute in Go, and write (for example, applying a fee schedule), use the version as a compare-and-swap: write only if `version` is still what you read, and retry on `ConditionalCheckFailedException`.

```go noverify title="ddb/ops.go · lines 82–106"
// It returns how many times it had to retry.
func AdjustOptimistic(ctx context.Context, c *dynamodb.Client, table, id string, delta int64) (retries int, err error) {
	for {
		a, err := GetAccount(ctx, c, table, id, true)
		if err != nil {
			return retries, err
		}
		_, err = c.UpdateItem(ctx, &dynamodb.UpdateItemInput{
			TableName: aws.String(table), Key: key(id),
			ConditionExpression: aws.String("version = :v"),
			UpdateExpression:    aws.String("SET balance = :b, version = :n"),
			ExpressionAttributeValues: map[string]types.AttributeValue{
				":v": &types.AttributeValueMemberN{Value: itoa(a.Version)},
				":b": &types.AttributeValueMemberN{Value: itoa(a.Balance + delta)},
				":n": &types.AttributeValueMemberN{Value: itoa(a.Version + 1)},
			},
		})
		if IsConditionFailed(err) {
			retries++
			continue
		}
		return retries, err
	}
}

```

Twenty writers each add 5 to one account:

<UnderTheHood title="Where a local AWS stops telling the truth">

Everything above ran against an emulator, and it is worth being exact about where that ends.

**It did not enforce signatures or expiry.** A presigned URL for a private bucket returned 200 to an anonymous request, a URL for a different key failed only because that key does not exist, and a URL used after its 2-second expiry still worked. Real S3 refuses all three with a 403. The chapter's S3 stop reports what LocalStack did; the 403 behaviour is from the AWS documentation, not measured here.

**It did not throttle.** DynamoDB on-demand tables and SQS can both return throttling errors under load on real AWS. The default retryer in the SDK handles some of them (3 attempts, exponential backoff with jitter, measured above against a server we made fail on purpose), but we couldn't provoke the real thing.

**Timings are the emulator's.** Query was faster than Scan here and read far fewer items; both facts hold on AWS, but the milliseconds don't carry over. Compare designs, don't quote numbers.

**What the local run is good for.** It checks that your code uses the API correctly: that you handle the typed errors, that your condition expressions are valid, that your consumer deletes what it should and only that. That's most of what goes wrong in practice, and it is what the programs in this chapter verified.

**One finding about re-running.** DynamoDB remembers a transaction's `ClientRequestToken` for ten minutes, even across a deleted and re-created table. The first version of the transfer program used a fixed token, and running it a second time within ten minutes turned its first transaction into a silent no-op. The fix was a token that includes a per-run ID. In production this is the feature: a retry with the same token must be harmless. In a demo it is a trap.

</UnderTheHood>

## Exercises

<Exercise n={1} title="Shorten a visibility timeout" level="medium">

A queue has VisibilityTimeout=30. Your handler occasionally takes 45 seconds. List two different ways to stop the message being delivered to a second consumer, and say which you'd choose.

<Solution>

Raise the queue's VisibilityTimeout above the worst-case handler time (say 120 s), or have the handler call `ChangeMessageVisibility` to extend the timeout while it works (a heartbeat). A larger timeout is simplest but delays redelivery after a real crash by that much. The heartbeat keeps recovery fast but needs a goroutine per in-flight message and handling for the case where the extension itself fails. For handlers whose time is bounded, raise the timeout; for handlers whose time varies widely, heartbeat. In both cases the handler must still be idempotent, because neither removes duplicates entirely.

</Solution>

</Exercise>

<Exercise n={2} title="A hot account" level="hard">

The optimistic-locking program had 20 writers on one item and needed about 100 retries. Rewrite the update so it needs none, and say when you could not.

<Solution>

Use the atomic form: `SET balance = balance + :d` in a single `UpdateItem`, which DynamoDB applies server-side with no read first. Two concurrent adds both land. You can't use it when the new value depends on logic you must run in Go over the old value (applying a tiered fee schedule, for instance), or when the update needs a cross-item invariant; there, keep the version attribute and accept retries, or move that logic into a transaction with conditions on every item involved.

</Solution>

</Exercise>

<Exercise n={3} title="Add the dead-letter alarm" level="easy">

The DLQ in the SQS stop is only useful if someone looks at it. What would you alarm on, and what retention should the DLQ have compared with the main queue?

<Solution>

Alarm on the DLQ's `ApproximateNumberOfMessagesVisible` being above 0 for a few minutes (any message there means a payment failed three times and a human must look). Give the DLQ a longer retention than the main queue (for example 14 days against 4): messages keep their original enqueue timestamp, so a DLQ with the same retention can expire a message almost as soon as it arrives, taking the evidence with it.

</Solution>

</Exercise>
