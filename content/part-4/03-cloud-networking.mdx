<HeroCard label="Part 4 · Chapter 3" title="Cloud Networking: A Packet's Journey from DNS to Pod">

Someone types `http://shop.internal/` and presses Enter. A few milliseconds later, a Go handler in a container on some machine runs, and the page comes back. In between, the request passed through half a dozen systems, each of which can be slow, wrong or down: a DNS server, a TCP connection, a load balancer, a router, a NAT gateway, a bridge, a network namespace. When a request fails at 3 a.m., "the network" isn't an answer. You need to know **which hop**, and to know that, you need to know what each hop does.

In this chapter we follow one request, hop by hop, and **build or watch every hop for real**. We write an authoritative DNS server and a load balancer in Go, capture the TCP handshake with `tcpdump`, and build a small cloud network (two subnets, a router, a NAT gateway and a Kubernetes-style Service) out of the same Linux pieces AWS, GCP and Kubernetes use underneath. Every number in the chapter was measured, and every output was pasted from a real run.

Five stops, in the order the request meets them. If you get lost, come back here:

1. **DNS.** How `shop.internal` becomes an IP address, what Go's resolver actually sends, and why an answer can be stale.
2. **TCP.** The handshake, what a new connection costs, and how Go's connection pool saves (or wastes) it.
3. **The load balancer.** One address in front of many servers: round robin, health checks, layer 4 against layer 7, and what happens to requests when a server dies.
4. **The private network.** A VPC built from namespaces, a bridge and routes, and the NAT that lets a private subnet reach the internet.
5. **Into the pod.** How a packet crosses the bridge into a container, how a Kubernetes Service is a few NAT rules, and the whole journey in one capture.

## DNS

*Stop 1 of 5.*

Before the client can send a single byte to `shop.internal`, it needs an IP address. Names are for people; the network only routes addresses. The **Domain Name System** turns one into the other, and because every request starts with it, a slow, wrong or stale DNS answer breaks everything after it.

### Step 1: what a lookup really does

<Define term="DNS resolver">
A **resolver** is the program that finds the answer for you. Your service doesn't do the work itself: it sends one question to the resolver named in `/etc/resolv.conf`, and the resolver (a **recursive** resolver, such as the one in your VPC, your ISP's, or 8.8.8.8) walks the DNS tree on your behalf and caches what it learns. The servers it asks along the way are **authoritative**: each one owns part of the tree and answers only for that part.
</Define>

The walk is easy to do by hand. `dig` is the standard DNS query tool, and `+norecurse` tells a server "don't look it up for me, just tell me what you know". Here's `go.dev`, resolved the way a recursive resolver does it, starting from one of the 13 root server addresses:

Three questions, three kinds of answer:

1. The **root** server doesn't know `go.dev`, but it knows who runs `.dev`: five name servers (NS records), which it will vouch for for 172,800 seconds, two days.
2. A **`.dev` server** doesn't know the address either, but knows who runs `go.dev`: four Google Cloud DNS servers, for 10,800 seconds (three hours).
3. **`go.dev`'s own server** is authoritative: it answers with four A records (IPv4 addresses), valid for **300 seconds**.

Each hop took 111 to 136 ms from this laptop. A resolver that did this for every request would add a third of a second to each one, which is why every resolver **caches**: it keeps each answer for as long as its **TTL** (time to live, the second column) allows. The root and TLD answers change rarely and have long TTLs, so after the first lookup a resolver usually only has to make the last hop, and usually not even that.

### Step 2: an authoritative server in Go

Inside a company, names like `shop.internal` or `orders.prod.svc.cluster.local` aren't on the public internet. Some server inside the network is authoritative for them: Route 53 private zones in AWS, Cloud DNS private zones in GCP, CoreDNS in Kubernetes. CoreDNS is written in Go, and so is ours. It uses `github.com/miekg/dns`, the DNS library CoreDNS is built on (v1.1.73; a rewrite is in progress at `codeberg.org/miekg/dns`).

The records come from a flag, turned into a table from name to addresses:

```go noverify title="hops/cmd/dns/main.go · lines 61–73"
// parse turns "a.shop.internal.=10.0.0.1,10.0.0.2;b.shop.internal.=10.0.0.3"
// into a table from lower-case name to addresses.
func parse(s string) map[string][]net.IP {
	zone := map[string][]net.IP{}
	for rec := range strings.SplitSeq(s, ";") {
		name, ips, _ := strings.Cut(rec, "=")
		name = dns.Fqdn(strings.ToLower(name))
		for ip := range strings.SplitSeq(ips, ",") {
			zone[name] = append(zone[name], net.ParseIP(ip))
		}
	}
	return zone
}
```

`dns.Fqdn` adds the trailing dot. In DNS every full name ends in `.`, the root: `shop.internal.` is the fully qualified form of `shop.internal`, and that dot will matter in Step 4.

The handler gets every question the server receives:

```go noverify title="hops/cmd/dns/main.go · lines 23–41"
	var queries atomic.Int64
	dns.HandleFunc(".", func(w dns.ResponseWriter, req *dns.Msg) {
		n := queries.Add(1)
		q := req.Question[0]
		m := new(dns.Msg)
		m.SetReply(req)
		m.Authoritative = true // we own this zone: this answer is the truth
		ips, ok := zone[strings.ToLower(q.Name)]
		switch {
		case !ok:
			m.Rcode = dns.RcodeNameError // NXDOMAIN: no such name
		case q.Qtype == dns.TypeA:
			for _, ip := range ips {
				m.Answer = append(m.Answer, &dns.A{
					Hdr: dns.RR_Header{Name: q.Name, Rrtype: dns.TypeA, Class: dns.ClassINET, Ttl: uint32(*ttl)},
					A:   ip,
				})
			}
		} // any other type (AAAA...) for a name we know: no error, no answers
```

What to notice:

- `m.SetReply(req)` copies the question and the query's **ID** into the reply. The client matches replies to questions by that 16-bit ID, because UDP has no connection to do it.
- `m.Authoritative = true` sets the **aa** flag: "I own this name; this is the truth, not something I cached".
- A name we don't have gets **NXDOMAIN** ("no such domain"). A name we do have, asked for a type we don't have (an IPv6 **AAAA** record, say), gets NOERROR with no answers. Those are different, and resolvers treat them differently.

The rest of the handler says how long "nothing here" may be cached, then logs the query and sends the reply:

```go noverify title="hops/cmd/dns/main.go · lines 42–58"
		if len(m.Answer) == 0 && dns.IsSubDomain("shop.internal.", q.Name) {
			// Say who is in charge of the zone, and for how long a cache
			// may remember "nothing here" (RFC 2308).
			m.Ns = append(m.Ns, &dns.SOA{
				Hdr: dns.RR_Header{Name: "shop.internal.", Rrtype: dns.TypeSOA, Class: dns.ClassINET, Ttl: uint32(*ttl)},
				Ns:  "ns.shop.internal.", Mbox: "ops.shop.internal.",
				Serial: 1, Refresh: 3600, Retry: 600, Expire: 86400, Minttl: uint32(*ttl),
			})
		}
		log.Printf("query %d: %s %s from %s: %s, %d answer(s)",
			n, dns.TypeToString[q.Qtype], q.Name, w.RemoteAddr(), dns.RcodeToString[m.Rcode], len(m.Answer))
		w.WriteMsg(m)
	})

	log.Printf("authoritative for shop.internal. on %s (udp), TTL %ds", *addr, *ttl)
	srv := &dns.Server{Addr: *addr, Net: "udp"}
	log.Fatal(srv.ListenAndServe())
```

An empty answer carries the zone's **SOA** (start of authority) record, whose last field tells caches how long they may remember the "no" (RFC 2308). Without it, a cache has to ask again every time. `dns.Server` with `Net: "udp"` reads datagrams on port 53 and calls the handler for each.

### Step 3: what Go's resolver sends

Now the same question from Go. `net.Resolver` is what `http.Get`, `net.Dial` and every Go client use to turn a host name into addresses:

```go noverify title="hops/cmd/lookup/main.go · lines 19–25"
	r := &net.Resolver{PreferGo: true} // Go's resolver, not the C library's
	if *server != "" {
		r.Dial = func(ctx context.Context, network, _ string) (net.Conn, error) {
			var d net.Dialer
			return d.DialContext(ctx, network, *server)
		}
	}
```

`PreferGo: true` asks for Go's own resolver, written in Go, instead of calling the C library's `getaddrinfo` through cgo. With `CGO_ENABLED=0`, as here, there's no C library to call, so Go's resolver is the only one; with cgo, Go picks one by looking at `/etc/nsswitch.conf` and `/etc/resolv.conf`. You can see which one it picked with `GODEBUG=netdns=go+1` or `netdns=cgo+1`. The `Dial` override sends the queries to our server instead of the one in `/etc/resolv.conf`. Then it looks the name up 100 times, timing each:


2. **Go doesn't cache.** Every lookup went to the server. Go's resolver reads `/etc/resolv.conf` and `/etc/hosts` (and re-reads them when they change), but it keeps no answers. Caching is the job of the resolver it talks to. If that resolver is far away or slow, every new connection your service opens pays for it.

### Step 4: the search list, and why Kubernetes pods ask five times

`/etc/resolv.conf` can say more than which server to ask. Inside a Kubernetes pod it looks like the one below (with the cluster DNS service's address as the name server; here it's our server on port 53):

```text
$ cat /etc/resolv.conf   # the shape of a Kubernetes pod's
nameserver 127.0.0.1
search default.svc.cluster.local svc.cluster.local cluster.local
options ndots:5
```

`search` lists suffixes to try, so that a pod can say `orders` and reach `orders.default.svc.cluster.local`. `ndots:5` says when to try them **first**: if the name has fewer than five dots, it's treated as a short name and the search list comes first. `shop.internal` has one dot. ### Step 5: caching, and answers that go stale

In production there is almost always a cache between your service and the authoritative server: the VPC resolver in AWS, `systemd-resolved` on many Linux hosts, NodeLocal DNSCache in Kubernetes. We'll put `dnsmasq`, a small caching resolver, on `127.0.0.1:53`, forwarding `shop.internal` to our server, and point `/etc/resolv.conf` at it. Now `lookup` runs without `-server`, exactly as a normal Go program would:

```text
$ cat /etc/resolv.conf
nameserver 127.0.0.1
$ bin/lookup -n 100   # no -server: Go reads /etc/resolv.conf
lookup 1: [10.10.0.2] <nil> in 1.668ms
lookup 2: [10.10.0.2] <nil> in 100µs
lookup 3: [10.10.0.2] <nil> in 84µs
100 lookups, average 105µs
$ grep -c query /tmp/dns.log   # queries that reached our server
2
$ dig shop.internal +noall +answer
shop.internal.		30	IN	A	10.10.0.2
$ dig shop.internal +noall +answer
shop.internal.		25	IN	A	10.10.0.2
$ dig shop.internal +noall +answer
shop.internal.		20	IN	A	10.10.0.2
```

This time 100 lookups sent **2 queries** to our server: the first A and AAAA. The other 99 lookups were answered from dnsmasq's memory. And the TTL is counting down: 30, then 25, then 20 seconds, five seconds apart. The cache will serve this answer until it reaches zero, and only then ask again.

That's the price of caching. Right after the third `dig`, the script moved `shop.internal` to a new address, `10.10.0.3`, on the authoritative server, and asked every half second which address clients were getting:

```text
$ kill $DNS; bin/dns -addr 127.0.0.1:5300 -ttl 30 -a 'shop.internal.=10.10.0.3' &   # the record moves
  0.0s after the change: clients get 10.10.0.2
 19.7s after the change: clients get 10.10.0.3
```

For **19.7 seconds** after the change, clients were still sent to the old address: the 20 seconds of TTL the cached answer had left when the record moved. The authoritative server knew the new address the whole time. Nobody asked it.

This is how DNS failover works, and why it's slow. When a database fails over to a new address, or a service moves, clients follow only once every cache in between has let the old answer expire. The TTL you set is the longest you're willing to wait. Low TTLs (5 to 60 seconds) mean faster failover and more queries; long TTLs mean fewer queries and slow moves. And there's a second, Go-specific delay on top: an `http.Client` that already has keep-alive connections open to the old address keeps using them. It only looks the name up again when it opens a new connection. Stop 2 is about those connections.

## TCP

*Stop 2 of 5.*

The client has an address. Now it needs a **connection**: HTTP/1.1 and HTTP/2 both run over TCP, and TCP won't carry a byte of your request until both ends have agreed to talk. That agreement costs time, and how often your service pays it is decided by Go's connection pool.

2. **`[S.]`**, server to client: SYN-ACK, "fine, mine start at 1960245724, and I acknowledge yours".
3. **`[.]`**, client to server: ACK. The connection is open. This is the **three-way handshake**, and the client couldn't send its request until it finished: **one full round trip** before the first byte of HTTP.
4. **`[P.]` length 95**: the request, `GET / HTTP/1.1`. The server ACKs it, then sends **`[P.]` length 152**: the response, headers and body.
5. The **second request** goes out on the same connection, with no handshake: `seq 96:191` continues where the first left off.
6. **`[F.]`** both ways: the client closes, the server closes, the last ACK. (The client exited, so the kernel closed its socket.)

`tcpdump` shows sequence numbers relative to the first one (`seq 1:96`), which is easier to read; `-S` shows the real ones. On loopback the handshake takes 55 microseconds and nobody notices. Across a real network, it costs one **round-trip time (RTT)**: under a millisecond inside one data centre, 1 to 2 ms between availability zones, 60 to 150 ms across an ocean.

### Step 2: timing a request with httptrace

`net/http/httptrace` lets a client hook into each phase of a request: when the DNS lookup starts and ends, when the TCP connect starts and ends, whether it got a new connection or a reused one, and when the first byte of the response arrived. `cmd/client` records them:

```go noverify title="hops/cmd/client/main.go · lines 22–46"
func get(client *http.Client, url string, drain bool) (timing, error) {
	var t timing
	var dnsStart, connStart time.Time
	trace := &httptrace.ClientTrace{
		DNSStart:     func(httptrace.DNSStartInfo) { dnsStart = time.Now() },
		DNSDone:      func(httptrace.DNSDoneInfo) { t.dns = time.Since(dnsStart) },
		ConnectStart: func(_, _ string) { connStart = time.Now() },
		ConnectDone:  func(_, _ string, _ error) { t.connect = time.Since(connStart) },
		GotConn:      func(info httptrace.GotConnInfo) { t.reused = info.Reused },
	}
	req, _ := http.NewRequest("GET", url, nil)
	req = req.WithContext(httptrace.WithClientTrace(req.Context(), trace))
	start := time.Now()
	trace.GotFirstResponseByte = func() { t.firstByte = time.Since(start) }
	resp, err := client.Do(req)
	if err != nil {
		return t, err
	}
	if drain {
		io.Copy(io.Discard, resp.Body) // read to the end...
	}
	resp.Body.Close() // ...and close, so the connection can be reused
	t.total = time.Since(start)
	return t, nil
}
```

What to notice:

- `httptrace.WithClientTrace` puts the hooks in the request's context; the `http.Transport` calls them as it goes.
- `GotConn` reports `Reused`: whether the transport took a connection from its **pool** of idle keep-alive connections, or had to dial a new one.
- After the response, it reads the body to the end and closes it. Hold on to that; it matters in Step 3.

With `DisableKeepAlives`, every request paid for the handshake: **20 new connections, 44.4 ms on average**, almost twice as long. Nothing else changed: same server, same network, same bytes of HTTP. The difference is one round trip per request. With TLS (HTTPS), a new connection costs another round trip on top for the TLS 1.3 handshake, so reuse matters even more.

### Step 3: how Go's pool loses connections

Go's `http.Transport` keeps connections open between requests and reuses them, as long as you let it. Two common mistakes stop it, both measured here.

**Not reading the body.** A connection can only go back into the pool once the response has been read to the end; until then there are unread bytes in the way of the next response. If you `Close` a body you didn't read, the transport can't reuse the connection and closes it. `/big` returns 256 KB:

```text
$ bin/client -url http://127.0.0.1:8080/big -n 20 -drain=false
request 1: reused=false dns=0s        connect=21.732ms  first byte=45.018ms  total=45.079ms
request 2: reused=false dns=0s        connect=22.894ms  first byte=46.817ms  total=46.885ms
request 3: reused=false dns=0s        connect=22.12ms   first byte=44.561ms  total=44.604ms
request 4: reused=false dns=0s        connect=21.196ms  first byte=42.49ms   total=42.528ms
20 requests, 20 new connections, average 43.74ms
$ bin/client -url http://127.0.0.1:8080/big -n 20 -drain=true
request 1: reused=false dns=0s        connect=21.338ms  first byte=45.808ms  total=139.658ms
request 2: reused=true  dns=0s        connect=0s        first byte=23.235ms  total=93.227ms
request 3: reused=true  dns=0s        connect=0s        first byte=25.116ms  total=48.428ms
request 4: reused=true  dns=0s        connect=0s        first byte=23.176ms  total=23.253ms
20 requests, 1 new connections, average 32.374ms
```

Without reading the body: **20 requests, 20 new connections**. With `io.Copy(io.Discard, resp.Body)` before `Close`: **1**. (With a tiny body the mistake is hidden: the transport reads a small body along with the headers, so the connection is reused either way. It shows up in production, on the endpoint with the big responses.) Reading the body to the end isn't free, as the slower first requests with `-drain=true` show: 256 KB has to cross a 20 ms link. But it's cheaper than a new connection on every request, and on a real server the bytes arrive anyway.

**A pool too small for your concurrency.** `Transport.MaxIdleConnsPerHost` is how many idle connections the pool keeps per host, and its default, `http.DefaultMaxIdleConnsPerHost`, is **2**. With 20 goroutines sending requests at once, 20 connections are busy; when their requests finish, only 2 fit back in the pool and the other 18 are closed. Then the next 18 requests dial again. The server's count of accepted connections, printed as it shuts down, tells the real story:

```text
$ bin/client -url http://127.0.0.1:8080/ -c 20 -n 50 -idle 2
1000 requests, 51 new connections, average 26.05ms
$ tail -1 /tmp/web.log   # the server, on shutdown
2026/09/28 00:11:51 web-1: shut down (<nil>), 465 connections accepted in all
$ bin/client -url http://127.0.0.1:8080/ -c 20 -n 50 -idle 20
1000 requests, 20 new connections, average 24.886ms
$ tail -1 /tmp/web.log   # the server, on shutdown
2026/09/28 00:12:54 web-1: shut down (<nil>), 20 connections accepted in all
```

Same 1,000 requests from 20 goroutines. With the default pool the server accepted **465 connections**; with `MaxIdleConnsPerHost` set to 20, it accepted **20**. That's 445 extra handshakes, and 445 sockets left in `TIME_WAIT` on the side that closed, which on a busy service is how you run out of ephemeral ports. (The client counted only 51 "new connections" in the first run, fewer than the server's 465, because while a request waits for a connection, the transport both dials a new one and waits for an idle one to come back, and uses whichever is ready first. The extra dialled connection goes into the pool, or, when the pool is full, is closed.)

<UnderTheHood title="Why a connection closes with TIME_WAIT">

The side that sends the first FIN (here, the client when it closes a connection it can't pool) keeps the connection's four-tuple (source address and port, destination address and port) in the **`TIME_WAIT`** state for a while after it closes: 60 seconds on Linux. It's there so that a late, delayed packet from the old connection can't be mistaken for part of a new one that happens to reuse the same four-tuple. A client talking to one server address can only have one connection per local port, and Linux hands out ports from `net.ipv4.ip_local_port_range`, 28,232 of them by default. A client that opens and closes hundreds of connections a second to the same backend can fill that range with `TIME_WAIT` sockets, and then `connect` fails with `EADDRNOTAVAIL`, "cannot assign requested address". The fix is not a kernel setting; it's reusing connections.

</UnderTheHood>

## The Load Balancer

*Stop 3 of 5.*

`shop.internal` resolves to one address, `10.10.0.2`, but the shop runs on several servers, so that one can die, or be redeployed, without taking the shop down. The thing listening at that one address and spreading requests across the servers is a **load balancer**. In AWS it's an ALB or an NLB, in Kubernetes an Ingress controller or a Service, and in front of many Go services it's Envoy or nginx. We'll write one in Go, because `net/http/httputil` has the hard part built in, and then break it.

### Step 1: a reverse proxy, round robin

A load balancer that understands HTTP is a **reverse proxy**: it accepts the client's request, sends a copy to a backend, and copies the backend's response back. Each backend gets its own `httputil.ReverseProxy`:

```go noverify title="hops/cmd/lb/main.go · lines 53–71"
func newBackend(raw string) *backend {
	u, err := url.Parse(raw)
	if err != nil {
		log.Fatal(err)
	}
	b := &backend{url: u}
	b.healthy.Store(true)
	b.proxy = &httputil.ReverseProxy{
		Rewrite: func(pr *httputil.ProxyRequest) {
			pr.SetURL(u)       // send it to this backend
			pr.SetXForwarded() // and tell it who the client was
		},
		ErrorHandler: func(w http.ResponseWriter, r *http.Request, err error) {
			log.Printf("proxy to %s: %v", u.Host, err)
			w.WriteHeader(http.StatusBadGateway) // 502
		},
	}
	return b
}
```

What to notice:

- `Rewrite` changes the outgoing request before it's sent. `pr.SetURL(u)` points it at the backend (scheme, host, and the path joined onto the backend's). `pr.SetXForwarded()` adds `X-Forwarded-For` (the client's address), `X-Forwarded-Host` and `X-Forwarded-Proto`, because the backend will now see every connection coming from the balancer, not from the client. (`Rewrite` arrived in Go 1.20 as a safer alternative to the older `Director` hook: before it runs, the proxy removes any `X-Forwarded-*` headers the client sent, so a client can't forge them.)
- `ErrorHandler` runs when the backend can't be reached or the connection fails mid-request. It answers **502 Bad Gateway**: "the server behind me failed".

The pool holds the backends and a counter. The first version of `pick` takes turns from the counter until it finds a healthy backend:

```go noverify title="hops/cmd/lb/main.go · lines 22–39, first version"
type pool struct {
	backends []*backend
	next     atomic.Uint64
}

// pick returns the next healthy backend in round-robin order, or nil if
// none is healthy. Skipping a sick backend uses up its turn, so the load
// stays even across the healthy ones.
func (p *pool) pick() *backend {
	n := uint64(len(p.backends))
	for range n {
		b := p.backends[(p.next.Add(1)-1)%n]
		if b.healthy.Load() {
			return b
		}
	}
	return nil
}
```

`atomic.Uint64` because every request runs on its own goroutine: two requests picking at the same moment must get different turns. `ServeHTTP` picks and forwards, or answers **503 Service Unavailable** if nothing is healthy:

```go noverify title="hops/cmd/lb/main.go · lines 44–51"
func (p *pool) ServeHTTP(w http.ResponseWriter, r *http.Request) {
	b := p.pick()
	if b == nil {
		http.Error(w, "no healthy backend", http.StatusServiceUnavailable)
		return
	}
	b.proxy.ServeHTTP(w, r)
}
```

### Step 2: layer 4 and layer 7

That's the defining property of a **layer-7** balancer (layer 7 is the application layer, HTTP here): it terminates the client's connection, reads each request, and can route by anything in it, such as the path, a header or a cookie. Our Go balancer, AWS's ALB, Envoy and nginx work this way. The price is that it must parse every request, and it holds two connections per request in flight: one to the client, one to the backend.

A **layer-4** balancer works at the transport layer: it sees TCP connections, not requests. It picks a backend when a connection opens and then passes bytes back and forth without looking at them. AWS's NLB, the Linux kernel's IPVS, and (as Stop 5 shows) a Kubernetes Service work this way. It's small enough to write whole:

```go noverify title="hops/cmd/l4/main.go · lines 24–49"
	var next atomic.Uint64
	for {
		client, err := ln.Accept()
		if err != nil {
			log.Fatal(err)
		}
		target := backends[(next.Add(1)-1)%uint64(len(backends))] // per connection
		go pipe(client, target)
	}
}

func pipe(client net.Conn, target string) {
	defer client.Close()
	server, err := net.Dial("tcp", target)
	if err != nil {
		log.Print(err)
		return
	}
	defer server.Close()
	log.Printf("connection %s -> %s", client.RemoteAddr(), target)
	go func() {
		io.Copy(server, client) // client to backend, until the client hangs up
		server.Close()
	}()
	io.Copy(client, server) // backend to client
}
```

The choice is made **once per connection**, in the accept loop. `pipe` copies both directions until one side hangs up. Now the same two tests through the layer-4 balancer on port 7000:

```go noverify title="hops/cmd/lb/main.go · lines 27–42"
// pick returns the next healthy backend in round-robin order, or nil if
// none is healthy. It takes one turn from the counter and spends it on the
// backends that are up right now, so each healthy backend gets an equal
// share, and a request never misses a healthy backend.
func (p *pool) pick() *backend {
	up := make([]*backend, 0, len(p.backends))
	for _, b := range p.backends {
		if b.healthy.Load() {
			up = append(up, b)
		}
	}
	if len(up) == 0 {
		return nil
	}
	return up[(p.next.Add(1)-1)%uint64(len(up))]
}
```

Each call builds the list of healthy backends and uses the counter to index it, so each healthy backend gets an equal share, and a request can't miss when one is up. (The list is a small allocation per request; a balancer with many backends would keep the healthy list up to date in the health checker instead.) Once more:

```go noverify title="hops/cmd/web/main.go · lines 68–77"
	<-ctx.Done()
	draining.Store(true) // health checks now fail, so the balancer stops sending
	log.Printf("%s: SIGTERM, failing health checks for %v", *name, *drain)
	time.Sleep(*drain)
	shutdown, cancel := context.WithTimeout(context.Background(), 10*time.Second)
	defer cancel()
	err := srv.Shutdown(shutdown) // stop accepting; wait for requests in flight
	log.Printf("%s: shut down (%v), %d connections accepted in all", *name, err, conns.Load())
```

`srv.Shutdown` closes the listener, so no new connections are accepted, closes idle connections, and waits for requests in flight to finish. With `-drain 0` it starts right away:

## The Private Network

*Stop 4 of 5.*

So far everything ran on one machine's loopback. In a cloud, the balancer and the servers are separate machines in a **VPC** (virtual private cloud): a private network with its own address range, split into **subnets**, with **route tables** that say where packets go, and a **NAT gateway** that lets machines in a private subnet reach the internet without being reachable from it. Those words sound like cloud products, but every one of them is an old Linux networking idea. In this stop we build a small VPC out of them, inside the lab container, one `ip` command at a time.

The plan: a **public subnet** `10.10.0.0/24` for the load balancer, a **private subnet** `10.10.1.0/24` for two app servers, and the container itself as the **router** between them and the NAT gateway to the outside.

### Step 1: a machine is a network namespace

Chapter 1 gave a process its own network namespace and found it empty. That's our starting point: each "machine" in the VPC is a network namespace. `ip netns add` creates one and gives it a name:

```text
$ ip netns add app1
$ ip netns exec app1 ip -br link
lo               DOWN           00:00:00:00:00:00 <LOOPBACK> 
tunl0@NONE       DOWN           0.0.0.0 <NOARP> 
gre0@NONE        DOWN           0.0.0.0 <NOARP> 
gretap0@NONE     DOWN           00:00:00:00:00:00 <BROADCAST,MULTICAST> 
erspan0@NONE     DOWN           00:00:00:00:00:00 <BROADCAST,MULTICAST> 
ip_vti0@NONE     DOWN           0.0.0.0 <NOARP> 
ip6_vti0@NONE    DOWN           :: <NOARP> 
sit0@NONE        DOWN           0.0.0.0 <NOARP> 
ip6tnl0@NONE     DOWN           :: <NOARP> 
ip6gre0@NONE     DOWN           :: <NOARP> 
```

A loopback interface (`lo`), down, and the inert tunnel devices this kernel creates in every new namespace, also down. No addresses, no routes. A process started in this namespace with `ip netns exec app1 …` (a Go service, say) sees exactly this, and nothing of the container's own network.

### Step 2: a subnet is a bridge and some cables

<Define term="veth pair">
A **veth pair** is two virtual network interfaces joined like the two ends of a cable: a packet sent into one comes out of the other. Put one end in a namespace and the other somewhere else, and you've connected them.
</Define>

<Define term="bridge">
A Linux **bridge** is a virtual network switch. Interfaces attached to it (its **ports**) can exchange Ethernet frames with each other. Like a hardware switch, it learns which MAC address lives behind which port by watching traffic, and forwards each frame only to the port it needs to go to.
</Define>

The private subnet: a bridge with an address (it will be the router's address on this subnet), and for each machine a veth pair with one end, named `eth0`, inside the machine's namespace, and the other end plugged into the bridge:

```text
$ ip link add br-priv type bridge
$ ip addr add 10.10.1.1/24 dev br-priv
$ ip link set br-priv up
$ ip netns add app2
$ ip link add veth-app1 type veth peer name eth0 netns app1
$ ip link set veth-app1 master br-priv up
$ ip -n app1 addr add 10.10.1.10/24 dev eth0
$ ip -n app1 link set eth0 up
$ ip -n app1 link set lo up
$ ip link add veth-app2 type veth peer name eth0 netns app2
$ ip link set veth-app2 master br-priv up
$ ip -n app2 addr add 10.10.1.11/24 dev eth0
$ ip -n app2 link set eth0 up
$ ip -n app2 link set lo up
```

`10.10.1.1/24` means the address `10.10.1.1` on a network whose first 24 bits are fixed: everything from `10.10.1.0` to `10.10.1.255`. That's the subnet's **CIDR block**, exactly what you type when you create a subnet in a VPC. Now look from inside app1:

```text
$ ip -n app1 -br addr show dev eth0
eth0@if13        UP             10.10.1.10/24 fe80::18ab:d1ff:fe59:1753/64 
$ ip -n app1 route
10.10.1.0/24 dev eth0 proto kernel scope link src 10.10.1.10 
$ ip netns exec app1 ping -c 2 10.10.1.11
PING 10.10.1.11 (10.10.1.11) 56(84) bytes of data.
64 bytes from 10.10.1.11: icmp_seq=1 ttl=64 time=0.197 ms
64 bytes from 10.10.1.11: icmp_seq=2 ttl=64 time=0.052 ms

--- 10.10.1.11 ping statistics ---
2 packets transmitted, 2 received, 0% packet loss, time 1023ms
rtt min/avg/max/mdev = 0.052/0.124/0.197/0.072 ms
$ ip -n app1 neigh
10.10.1.11 dev eth0 lladdr 2e:07:82:2b:dc:3b REACHABLE 
$ bridge fdb show br br-priv | grep -v permanent
1a:ab:d1:59:17:53 dev veth-app1 master br-priv 
2e:07:82:2b:dc:3b dev veth-app2 master br-priv 
```

app1 has an address, and one route, which the kernel added by itself: `10.10.1.0/24 dev eth0`, "the whole subnet is directly on this cable". So pinging app2 works. Before the first ping could go, app1 had to find app2's MAC address with **ARP** ("who has 10.10.1.11?"), and `ip neigh` shows the answer it cached. The bridge's forwarding table (`bridge fdb`) shows what it learned from the same traffic: which MAC address is behind which veth.

### Step 3: routes between subnets

The public subnet is built the same way, with its own bridge and a namespace for the load balancer. Then, from app1, try to reach it:

```text
$ ip link add br-pub type bridge
$ ip addr add 10.10.0.1/24 dev br-pub
$ ip link set br-pub up
$ ip netns add lb
$ ip link add veth-lb type veth peer name eth0 netns lb
$ ip link set veth-lb master br-pub up
$ ip -n lb addr add 10.10.0.2/24 dev eth0
$ ip -n lb link set eth0 up
$ ip -n lb link set lo up
$ ip netns exec app1 ping -c 2 -W 1 10.10.0.2
ping: connect: Network is unreachable
```

`Network is unreachable`: app1's only route covers `10.10.1.0/24`, and `10.10.0.2` isn't in it. A packet with no matching route isn't sent at all. Every machine needs a **default route**, "anything else, send to the router", pointing at the router's address on its own subnet. In a VPC, that's the `0.0.0.0/0` line of the subnet's route table:

```text
$ ip -n app1 route add default via 10.10.1.1
$ ip -n app2 route add default via 10.10.1.1
$ ip -n lb route add default via 10.10.0.1
$ sysctl -w net.ipv4.ip_forward=0
net.ipv4.ip_forward = 0
$ ip netns exec app1 ping -c 2 -W 1 10.10.0.2
PING 10.10.0.2 (10.10.0.2) 56(84) bytes of data.

--- 10.10.0.2 ping statistics ---
2 packets transmitted, 0 received, 100% packet loss, time 1062ms
$ sysctl -w net.ipv4.ip_forward=1
net.ipv4.ip_forward = 1
$ ip netns exec app1 ping -c 2 -W 1 10.10.0.2
PING 10.10.0.2 (10.10.0.2) 56(84) bytes of data.
64 bytes from 10.10.0.2: icmp_seq=1 ttl=63 time=0.025 ms
64 bytes from 10.10.0.2: icmp_seq=2 ttl=63 time=0.072 ms

--- 10.10.0.2 ping statistics ---
2 packets transmitted, 2 received, 0% packet loss, time 1039ms
rtt min/avg/max/mdev = 0.025/0.048/0.072/0.023 ms
```

With routes in place but `ip_forward` set to 0, the ping still failed: the packets reached the router, and the router, being a normal Linux host, dropped packets that weren't addressed to it. `net.ipv4.ip_forward=1` turns it into a router, and the ping went through. Note `ttl=63` in the replies, one less than the 64 Linux starts with: each router a packet crosses decrements its TTL (in IP, "time to live" is a hop count), which is how `traceroute` works.

### Step 4: out to the internet, through NAT

Now app1 tries to reach a real address on the internet, `1.1.1.1`. The container's own routing table sends anything else out of `eth0`, towards Docker's network:

```text
$ ip route
default via 172.17.0.1 dev eth0 
10.10.0.0/24 dev br-pub proto kernel scope link src 10.10.0.1 
10.10.1.0/24 dev br-priv proto kernel scope link src 10.10.1.1 
172.17.0.0/16 dev eth0 proto kernel scope link src 172.17.0.2 
$ ip netns exec app1 ping -c 3 -W 1 1.1.1.1
PING 1.1.1.1 (1.1.1.1) 56(84) bytes of data.

--- 1.1.1.1 ping statistics ---
3 packets transmitted, 0 received, 100% packet loss, time 2051ms
$ cat /tmp/icmp1.txt   # tcpdump -i eth0 icmp, during that ping
00:16:26.364987 IP 10.10.1.10 > 1.1.1.1: ICMP echo request, id 543, seq 1, length 64
00:16:27.391495 IP 10.10.1.10 > 1.1.1.1: ICMP echo request, id 543, seq 2, length 64
00:16:28.416233 IP 10.10.1.10 > 1.1.1.1: ICMP echo request, id 543, seq 3, length 64
```

**100% packet loss**, and `tcpdump` on the container's `eth0` shows why. The router did forward the pings, but they left with source address `10.10.1.10`. That's a **private address** (the `10.0.0.0/8` range is reserved for private networks, RFC 1918), and nothing outside knows how to route a reply to it. The packets went out; no answer could ever come back.

<Define term="NAT">
**Network address translation** rewrites addresses in packets as they pass through a router. **Source NAT** (SNAT) replaces the source address of outgoing packets with the router's own public address, and remembers the connection, so that replies to that address can be translated back and sent to the right private machine. **MASQUERADE** is SNAT that uses whatever address the outgoing interface has. This is what a NAT gateway is.
</Define>

One `iptables` rule: for packets from the private subnet leaving through `eth0`, masquerade:

```text
$ iptables -t nat -A POSTROUTING -s 10.10.1.0/24 -o eth0 -j MASQUERADE
$ ip netns exec app1 ping -c 2 -W 2 1.1.1.1
PING 1.1.1.1 (1.1.1.1) 56(84) bytes of data.
64 bytes from 1.1.1.1: icmp_seq=1 ttl=62 time=137 ms
64 bytes from 1.1.1.1: icmp_seq=2 ttl=62 time=135 ms

--- 1.1.1.1 ping statistics ---
2 packets transmitted, 2 received, 0% packet loss, time 1005ms
rtt min/avg/max/mdev = 134.779/135.690/136.602/0.911 ms
$ cat /tmp/icmp2.txt   # tcpdump -i eth0 icmp, during that ping
00:16:30.468069 IP 172.17.0.2 > 1.1.1.1: ICMP echo request, id 549, seq 1, length 64
00:16:30.604580 IP 1.1.1.1 > 172.17.0.2: ICMP echo reply, id 549, seq 1, length 64
00:16:31.472737 IP 172.17.0.2 > 1.1.1.1: ICMP echo request, id 549, seq 2, length 64
00:16:31.607391 IP 1.1.1.1 > 172.17.0.2: ICMP echo reply, id 549, seq 2, length 64
```

The same ping, and now it works: **135 ms**, to Cloudflare and back. On `eth0` the requests now leave with source **`172.17.0.2`**, the container's own address, and the replies come back to it. The kernel rewrote the source on the way out, and the destination on the way back.

How does it know which private machine a reply belongs to? **conntrack**, the kernel's connection tracking table. Every connection through the NAT gets an entry holding the original addresses and the translated ones:

```text
$ ip netns exec app1 curl -s -o /dev/null -w '%{http_code} from %{remote_ip}' http://1.1.1.1/; echo
301 from 1.1.1.1
$ conntrack -L -p tcp --dport 80
tcp      6 59 CLOSE_WAIT src=10.10.1.10 dst=1.1.1.1 sport=34324 dport=80 src=1.1.1.1 dst=172.17.0.2 sport=80 dport=34324 [ASSURED] mark=0 use=1
conntrack v1.4.8 (conntrack-tools): 1 flow entries have been shown.
$ iptables -t nat -L POSTROUTING -v -n
Chain POSTROUTING (policy ACCEPT 0 packets, 0 bytes)
 pkts bytes target     prot opt in     out     source               destination         
    2   144 MASQUERADE  all  --  *      eth0    10.10.1.0/24         0.0.0.0/0           
```

Read the conntrack line in two halves. The first half is the connection as app1 sent it: `src=10.10.1.10 dst=1.1.1.1 sport=34324 dport=80`. The second is what a reply must look like: from `1.1.1.1` to **`172.17.0.2`**, port 34324. When a packet matching the second half arrives, the kernel rewrites its destination back to `10.10.1.10` and routes it into the private subnet.

And the rule's counter says **2 packets**, although dozens crossed the NAT. The `nat` table is consulted only for the **first packet of each connection**: two connections here, the ping and the `curl`. Every later packet is translated from the conntrack entry, without looking at the rules. That's also why a NAT gateway has a limit on simultaneous connections: each one is a table entry, and a port on the public address.

Here is the whole VPC vocabulary, next to what we built:

| In a cloud VPC | What it is in Linux | What we ran |
|---|---|---|
| Instance, pod, container | A network namespace | `ip netns add app1` |
| Its network interface (ENI) | One end of a veth pair | `ip link add veth-app1 type veth peer name eth0 netns app1` |
| Subnet, with its CIDR block | A bridge with an address | `ip link add br-priv type bridge`, `ip addr add 10.10.1.1/24` |

## Into the Pod

*Stop 5 of 5.*

The last hop: from the subnet into the process. This is the part a Kubernetes **CNI plugin** (container network interface) does every time a pod starts, and it's exactly what we did for app1. The reference `bridge` plugin creates a network namespace's veth pair, attaches the host end to a bridge (`cni0`), assigns the pod an address from the node's range, and sets a default route; Docker does the same with `docker0`. So a pod is, network-wise, app1.

Follow the one SYN, `seq 1047203637`:

1. **`veth-lb In`**: it leaves the balancer's namespace through its cable and arrives at the host end.
2. **`br-pub In`**: the bridge hands it to the router (the root namespace), because it's addressed to the router's MAC: the balancer's default gateway.
3. The router looks up `10.10.1.10`: on `br-priv`. It doesn't know app1's MAC yet, so it sends an **ARP request** out of `br-priv`, and the bridge floods it to every port, **`veth-app2`** and **`veth-app1`**. Only app1 answers, **`veth-app1 In`**: `10.10.1.10 is-at 1a:ab:d1:59:17:53`.
4. **`br-priv Out`**, **`veth-app1 Out`**: the SYN goes out, with a new source MAC (`4e:ea:6a:d7:ee:3c`, the router's on this subnet) but the same IP addresses and sequence number. A router rewrites the Ethernet header at every hop; the IP header's addresses stay the same unless NAT changes them.
5. **`veth-app1 In`**: app1's SYN-ACK, on its way back.

That is how a packet gets into a container: a route to the bridge, ARP for the address, and a veth cable into the namespace, where the kernel's TCP stack in that namespace hands it to the socket our Go program is listening on.

### Step 2: a Service is a few NAT rules

A Kubernetes **Service** gives a set of pods one stable virtual address, the **ClusterIP**, like `10.96.0.10`. Pods come and go and change addresses; the ClusterIP doesn't. Here is the surprising part: that address isn't on any interface anywhere. In its default `iptables` mode, **kube-proxy** implements a Service as NAT rules on every node, which rewrite the destination of any packet for the ClusterIP to one of the pods' addresses. That's **destination NAT** (DNAT), and we can write the same rules by hand:

```text
$ iptables -t nat -N SVC-SHOP
$ iptables -t nat -A SVC-SHOP -p tcp -m statistic --mode random --probability 0.5 -j DNAT --to-destination 10.10.1.10:8080
$ iptables -t nat -A SVC-SHOP -p tcp -j DNAT --to-destination 10.10.1.11:8080
$ iptables -t nat -A PREROUTING -d 10.96.0.10/32 -p tcp --dport 80 -j SVC-SHOP
$ ip addr | grep -c 10.96.0.10
0
```

A chain, `SVC-SHOP`, with two rules. The first matches half the time (`statistic --mode random --probability 0.5`) and sends the connection to app1; whatever is left goes to app2. kube-proxy writes exactly this pattern, with one rule per pod and the probabilities chosen so each pod gets an equal share (1/3, then 1/2, then the rest, for three pods). A `PREROUTING` rule sends every TCP packet for `10.96.0.10:80` into the chain. And `grep -c` confirms that `10.96.0.10` is on no interface: **0**. Now 1,000 requests to it, each a new `curl` and so a new connection:

### Step 3: when the client pod is on the same bridge

One more pod, app3, on the private subnet, calling the Service. It works, split between the two backends as before. Then the script turns off one kernel setting, `net.bridge.bridge-nf-call-iptables`, only in this container's network namespace:

With the setting off, **20 of 20 requests failed**, and the capture on app3's cable shows exactly how. app3 sent its SYN to `10.96.0.10`. The router DNATed it to `10.10.1.11` and forwarded it onto the bridge. But web-2's reply went **straight back across the bridge** to app3, which is on the same subnet, without passing through the router, so nothing translated it back: app3 received a SYN-ACK from `10.10.1.11`, a machine it had never talked to, and answered it with a reset (`Flags [R]`).

Setting it back, the requests worked again.

1. **ARP** for the default gateway, then **DNS**: two queries in parallel, `A?` and `AAAA?` for `shop.internal.` The flags `*-` mean an authoritative answer: `A 10.10.0.2` for the A query; no answers and one authority record (the SOA) for the AAAA. The client's trace says the lookup took 4.3 ms.
2. **TCP to the balancer**: SYN, SYN-ACK, ACK, then `GET /`, 94 bytes.
3. **The balancer's own connection** to web-1 in the private subnet: a new handshake, from `10.10.0.2` port 54504, through the router, then the forwarded request. It's **184 bytes**, not 94, because the proxy added its `X-Forwarded-*` headers. web-1 answers `200 OK`, and the balancer relays it to the client.
4. **The second request** on the same client connection (no handshake: 1.8 ms in total instead of 13.0 ms). The balancer sends it to **web-2**, round robin, on a new backend connection.
5. The client closes its connection. The balancer's connections to web-1 and web-2 stay open in its pool for the next requests.

## Exercises

<Exercise n={1} title="What TLS adds" level="easy">

Give `cmd/web` a `-tls` flag that serves HTTPS with a self-signed certificate (generate one at startup with `crypto/x509` and `crypto/ecdsa`, or run `ListenAndServeTLS` with files made by `openssl`), and teach `cmd/client` to skip verification for this test only (`tls.Config{InsecureSkipVerify: true}`). Add `TLSHandshakeStart` and `TLSHandshakeDone` to the trace, run it over the 20 ms loopback, and compare new and reused connections again.

<Solution>

A new HTTPS connection costs one round trip for TCP and, with TLS 1.3, one more for the TLS handshake before the request can go, so expect the first request to take about three round trips (around 60 ms here) and reused ones one round trip, as before. The gap between `-reuse=false` and the default grows accordingly, which is why keeping connections alive matters even more for HTTPS. (With TLS 1.2, the handshake takes two round trips.)

</Solution>

</Exercise>

<Exercise n={2} title="Retry on another backend" level="medium">

When the balancer can't even connect to a backend (`connection refused`), nothing was sent, so the request can safely go to another backend. Make `cmd/lb` do that: mark the backend unhealthy at once (a **passive** health check) and retry the request on the next healthy one. Rerun the `kill -9` experiment. How many 502s are left?

<Solution>

In `ErrorHandler`, check `errors.Is(err, syscall.ECONNREFUSED)` (or that the error is a `*net.OpError` with `Op == "dial"`). If so, `b.healthy.Store(false)`, pick another backend, and call its `proxy.ServeHTTP(w, r)` if the request has no body, or `r.GetBody` can recreate it. Only the requests that were in flight at the moment of the kill should still fail; the ones sent to the dead backend afterwards are rescued. Don't retry after a request may have reached the backend (a timeout, or a reset mid-response) unless the method is idempotent: a retried POST can charge a card twice. This is what nginx's `proxy_next_upstream` and Envoy's retry policies configure.

</Solution>

</Exercise>

<Exercise n={3} title="Least connections" level="medium">

Round robin assumes every request costs the same. Add a second policy to `cmd/lb`, **least connections**: pick the healthy backend with the fewest requests in flight (an `atomic.Int64` per backend, incremented before `proxy.ServeHTTP` and decremented after). Then start web-2 with a handler that is ten times slower and compare the two policies with `cmd/load`.

<Solution>

With round robin, both backends get the same number of requests, so the slow one builds up a queue and the average latency is dominated by it. With least connections, requests pile up less on the slow backend (it always has more in flight), so the fast one takes most of the traffic. Break ties by round robin, or the first backend in the list gets every request when all are idle. For big pools, "power of two choices" (pick two at random, take the less busy) gets nearly the same result without scanning every backend.

</Solution>

</Exercise>

<Exercise n={4} title="A client that follows DNS" level="medium">

Run `cmd/client` in a loop against `shop.internal` with a keep-alive connection while you change the record from Stop 1 to point at another server. How long does the client keep talking to the old address? Then set `Transport.IdleConnTimeout` to a few seconds, or close idle connections periodically with `client.CloseIdleConnections()`, and measure again.

<Solution>

As long as the keep-alive connection stays open and busy, the client never looks the name up again, so it can keep using the old address long after the DNS TTL has expired: in a busy loop, indefinitely. Closing idle connections forces a new dial, which does a new lookup. Services that must follow DNS changes (a database failover behind a DNS name, for instance) need both a short TTL and connections that don't live forever: `IdleConnTimeout` for idle ones, and a maximum connection age for busy ones.

</Solution>

</Exercise>

<Exercise n={5} title="A second Service, three pods" level="hard">

Add a third pod to the private subnet and a Service `10.96.0.20:80` in front of all three, written the way kube-proxy writes it. What probability must each rule have for an even split? Check with 3,000 connections and the rules' counters. Then call the Service from one of its own pods, and explain what you see.

<Solution>

The rules are tried in order, so the first must match 1/3 of the time, the second 1/2 of what's left, and the last everything else: `--probability 0.33333`, `--probability 0.5`, then no match condition. Expect about 1,000 each. Calling the Service from a pod that is also a backend fails whenever the rule picks that same pod: the packet is DNATed back to its own sender, whose reply never passes back through the NAT. This is **hairpin** traffic; kube-proxy handles it by masquerading packets whose source and destination pod are the same, and the bridge plugin by enabling `hairpin_mode` on the bridge port.

</Solution>

</Exercise>

// Backend is one instance behind the balancer.
type Backend struct {
	Name    string
	healthy bool
}

// Pool is the balancer's list of backends. Next is called by every request
// goroutine, SetHealthy by the health checker's goroutine, all at once.
type Pool struct {
	backends []*Backend
	next     int
}

func NewPool(names ...string) *Pool {
	p := &Pool{}
	for _, n := range names {
		p.backends = append(p.backends, &Backend{Name: n, healthy: true})
	}
	return p
}

// SetHealthy records a health-check result. Unknown names are ignored.
func (p *Pool) SetHealthy(name string, ok bool) {
	for _, b := range p.backends {
		if b.Name == name {
			b.healthy = ok
		}
	}
}

// Skipping an unhealthy backend must keep the load even across the rest.
func (p *Pool) Next() (*Backend, error) {
	i := p.next
	p.next++
	for range len(p.backends) {
		b := p.backends[i%len(p.backends)]
		if b.healthy {
			return b, nil
		}
		i++ // try the one after it
	}
	return p.backends[0], nil
}

		}

	}

<Recap>

- **DNS**: a recursive resolver walks root → TLD → authoritative (111 to 136 ms per hop from this laptop) and caches by TTL. Our Go authoritative server with `miekg/dns` answered `dig` with the `aa` flag. Go's resolver sent **200 queries for 100 lookups** (A and AAAA) and caches nothing; with a Kubernetes-style search list and `ndots:5`, **800**, and with a trailing dot, 200 again. Behind a cache (dnsmasq), 100 lookups sent **2**, and after a record changed, clients got the old address for **19.7 s**: the TTL the cached answer had left.
- **TCP**: the handshake is one round trip before any HTTP. With a 20 ms round trip, reused connections averaged **25.0 ms** a request and new ones **44.4 ms**. Not reading a 256 KB body cost **20 connections instead of 1**; the default `MaxIdleConnsPerHost` of 2 with 20 goroutines made the server accept **465 connections** instead of 20.
- **Load balancer**: `httputil.ReverseProxy` with `Rewrite` is a layer-7 balancer: **6,054 / 6,054** from one connection. A layer-4 balancer picks per connection: **16,518 / 0**. A `kill -9` without health checks failed **27,928** requests and kept failing; with checks, **4,819**, all within a second. Taking a new counter turn per try produced **110 false 503s**; one turn per request, none. In-flight requests: `kill -9` lost **15**, an immediate `Shutdown` **7**, failing the health check and waiting 2 s before `Shutdown`, **0**.
- **Private network**: a namespace is a machine, a bridge and veth pairs are a subnet, default routes and `ip_forward` make a router, and `MASQUERADE` is a NAT gateway: pings to 1.1.1.1 went from **0 of 3** answered to **135 ms**, and conntrack held the mapping. The `nat` table sees only a connection's first packet.
- **Into the pod**: a packet reaches a container by route, ARP and veth, exactly as a CNI plugin wires it. A Kubernetes Service is DNAT rules for an address on no interface: **486 / 514** over 1,000 connections, and still one pod per connection. With `bridge-nf-call-iptables=0`, a pod on the same bridge failed **20 of 20** calls to the Service, reset by its own un-NATed reply.

</Recap>
