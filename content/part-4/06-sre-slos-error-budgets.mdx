<HeroCard label="Part 4 · Chapter 6" title="SRE: SLOs, Error Budgets & Alerts">

"Is the service up?" is the wrong question: everything is a little bit down, some of the time. Site reliability engineering, the discipline Google named in the early 2000s, replaces it with better ones. **How reliable must it be** (an objective, chosen on purpose)? **How reliable is it** (a measurement)? And **how much unreliability can we still afford** this month (a budget)? Alerts then page a human only when that budget is in real danger, and never for noise.

This chapter does all of it to one real server, the one from the Build Your Own Redis track: it gets metrics, an SLO, alerts that are unit-tested before they ever run, and a rehearsed incident on a real Prometheus.

Five stops:

1. **Budgets.** SLIs, SLOs and the error budget, in numbers.
2. **Measuring.** Metrics in Go with `client_golang`, and the choices that make them trustworthy.
3. **Burn-rate alerts.** Why "error rate above 1%" is a bad alert, and the two-window rule that replaced it.
4. **A rehearsed incident.** Five percent of commands failing on purpose, watched by a real Prometheus.
5. **After the incident.** What the budget says, and how to write it up without blame.

</HeroCard>

## Budgets

*Stop 1 of 5.*

### Step 1: indicators and objectives

A **service level indicator** (SLI) is a measurement of what users experience, as a ratio of good events to all events. For our server, the obvious one is availability: of all the commands it received, how many did it answer without failing? A **service level objective** (SLO) is the target for that ratio over a window: "99.9% of commands succeed, measured over 30 days".

The SLO is a choice, and a trade. 100% is never the right number: users can't tell the difference between 99.99% and 100% because their own networks and devices fail more often than that, and every extra nine costs far more engineering, and forbids far more change, than the one before.

### Step 2: the budget

The **error budget** is what the SLO allows to go wrong: 1 minus the SLO. Here's what that means over 30 days, and how fast different **burn rates** (multiples of "spending exactly the budget by the end of the month") use it up:

```go noverify title="kv/cmd/budget/main.go"
// budget prints what an availability SLO allows over 30 days, and how fast
// each burn rate spends it.
package main

import (
	"fmt"
	"time"
)

const window = 30 * 24 * time.Hour

func main() {
	fmt.Println("SLO       error budget   = full outage of")
	for _, slo := range []float64{0.99, 0.999, 0.9995, 0.9999} {
		budget := 1 - slo
		outage := time.Duration(float64(window) * budget)
		fmt.Printf("%-8s  %6.2f%%        %v\n", fmt.Sprintf("%.2f%%", slo*100), budget*100, outage.Round(time.Second))
	}

	fmt.Println("\nburn rate   budget gone in   budget spent per hour")
	for _, burn := range []float64{1, 3, 6, 14.4, 50} {
		gone := time.Duration(float64(window) / burn)
		perHour := burn / (30 * 24) * 100
		fmt.Printf("%5.1fx      %-15v  %.2f%%\n", burn, gone.Round(time.Minute), perHour)
	}
}
```

```text
SLO       error budget   = full outage of
99.00%      1.00%        7h12m0s
99.90%      0.10%        43m12s
99.95%      0.05%        21m36s
99.99%      0.01%        4m19s

burn rate   budget gone in   budget spent per hour
  1.0x      720h0m0s         0.14%
  3.0x      240h0m0s         0.42%
  6.0x      120h0m0s         0.83%
 14.4x      50h0m0s          2.00%
 50.0x      14h24m0s         6.94%
```

A 99.9% SLO allows **43 minutes 12 seconds** of complete outage a month, or the same number of failures spread out (0.1% of all commands). Burning at 1× spends exactly the budget in 30 days. At **14.4×** it's gone in **50 hours**, 2% of the month's budget every hour. Those numbers are where the alerts in stop 3 come from.

The budget turns reliability into a negotiation instead of an argument. While budget remains, the team ships features, runs experiments and takes risks. When it's spent, the priority shifts to reliability work until it recovers. Both sides agreed to the number in advance.

## Measuring

*Stop 2 of 5.*

### Step 1: counters and a histogram

Prometheus pulls metrics: every few seconds it requests `/metrics` from each target and stores the numbers as time series. `client_golang` is the Go library for exposing them:

```go noverify title="kv/server/metrics.go · lines 9–28"
// Metrics is what the server reports to Prometheus: how many commands it
// answered, how each one ended, and how long it took.
type Metrics struct {
	Commands *prometheus.CounterVec   // kv_commands_total{command, result}
	Duration *prometheus.HistogramVec // kv_command_duration_seconds{command}
}

func NewMetrics(reg prometheus.Registerer) *Metrics {
	m := &Metrics{
		Commands: prometheus.NewCounterVec(prometheus.CounterOpts{
			Name: "kv_commands_total",
			Help: "Commands answered, by command and result (ok, client_error, server_error).",
		}, []string{"command", "result"}),
		Duration: prometheus.NewHistogramVec(prometheus.HistogramOpts{
			Name: "kv_command_duration_seconds",
			Help: "Time from reading a command to having its reply ready.",
			// 50 µs to 50 ms: an in-memory store should live at the bottom.
			Buckets: []float64{.00005, .0001, .00025, .0005, .001, .0025, .005, .01, .025, .05},
		}, []string{"command"}),
	}
```

A **counter** only goes up: `kv_commands_total`, labelled by command and result. Prometheus computes rates from it (`rate(...[5m])` is "per second, averaged over 5 minutes"), and a counter survives a restart gracefully, because `rate` notices the reset. A **histogram** counts observations into buckets: how many commands took under 50 µs, under 100 µs, and so on up to 50 ms. Buckets are chosen for the thing measured; for an in-memory store, microseconds.

<UnderTheHood title="What rate() actually computes">

`rate(kv_commands_total[5m])` looks at the samples of each series inside the last 5 minutes. It takes the difference between the last and the first, and if the counter ever went **down** in between (the process restarted and counted from zero again), it adds back the value just before the drop, so a restart doesn't show up as negative traffic. It then extrapolates that increase to the edges of the window, because scrapes rarely land exactly on them, and divides by the window's length in seconds. That's why `increase()` over a counter of whole commands can return a fraction, and why a window needs at least two samples: with a 1 s scrape interval, the rehearsal's 5-second window has about five.

</UnderTheHood>

### Step 2: whose fault was it?

```go noverify title="kv/server/metrics.go · lines 41–64"
// result classifies a reply. A client's mistake (wrong arguments, a value
// that isn't a number) is its own problem; only our failures count against
// the server's availability.
func result(reply string) string {
	switch {
	case !strings.HasPrefix(reply, "-"):
		return "ok"
	case strings.HasPrefix(reply, "-ERR internal"):
		return "server_error"
	default:
		return "client_error"
	}
}

// commandLabel keeps the label set small: known commands by name, anything
// else as "other", so a client sending random words can't create unlimited
// time series.
func commandLabel(name string) string {
	switch n := strings.ToUpper(name); n {
	case "PING", "SET", "GET", "DEL", "INCR":
		return n
	}
	return "other"
}
```

Two decisions here make the SLI honest. First, `result` separates **client errors** from **server errors**. A client that sends `INCR` on a word gets an error, but the server did its job correctly, so it shouldn't spend the server's budget. Only `-ERR internal` counts as a failure. Second, `commandLabel` limits the `command` label to a fixed set. Every distinct label value is a separate time series stored in Prometheus; labelling by the raw command name would let any client create unlimited series just by sending random words. This is called **cardinality**, and runaway cardinality is one of the classic ways to take down a monitoring system.

### Step 3: recording every command

```go noverify title="kv/server/server.go · lines 78–93"
// run answers one command, injecting chaos if asked to, and records it.
func (s *Server) run(args []string) string {
	start := time.Now()
	var reply string
	if rate := math.Float64frombits(s.chaos.Load()); rate > 0 && rand.Float64() < rate {
		reply = errorReply("internal error (chaos)")
	} else {
		reply = s.do(args)
	}
	if s.Metrics != nil {
		cmd := commandLabel(args[0])
		s.Metrics.Commands.WithLabelValues(cmd, result(reply)).Inc()
		s.Metrics.Duration.WithLabelValues(cmd).Observe(time.Since(start).Seconds())
	}
	return reply
}
```

`run` wraps lesson 10's `do`: it times the command, classifies the reply and increments the right series. It also holds the rehearsal switch: with a chaos rate set, that fraction of commands fails with an internal error on purpose. `main` serves `/metrics` next to the Redis port, and a `POST /chaos?rate=0.05` endpoint to flip the switch while serving:


### Step 4: a series that didn't exist

The first rehearsal showed a problem in the first lines of its log:

```text
   0s  healthy    errors 1h-window      -     5m-window      -     alerts: none
   5s  healthy    errors 1h-window      -     5m-window      -     alerts: none
  10s  healthy    errors 1h-window      -     5m-window      -     alerts: none
  16s  healthy    errors 1h-window      -     5m-window      -     alerts: none
```

While the server was perfectly healthy, the error ratio wasn't 0%: it was **missing**. A labelled counter series only exists once it has been incremented, so before the first failure there was no `result="server_error"` series at all, and a ratio over it had no value. Dashboards show a gap exactly when things are fine, and an alert written as "error ratio > X" can't tell "healthy" from "not reporting". The fix is to create every combination at zero when the server starts:

```go noverify title="kv/server/metrics.go · lines 29–39"
	reg.MustRegister(m.Commands, m.Duration)
	// Create every series now, at zero. Otherwise the server_error series
	// doesn't exist until the first failure, and an error ratio computed
	// from it has no value at all while everything is healthy.
	for _, cmd := range []string{"PING", "SET", "GET", "DEL", "INCR", "other"} {
		for _, res := range []string{"ok", "client_error", "server_error"} {
			m.Commands.WithLabelValues(cmd, res)
		}
	}
	return m
}
```

## Burn-Rate Alerts

*Stop 3 of 5.*

### Step 1: what's wrong with "errors above 1%"

The obvious alert, "page if the error ratio is above 1% for 5 minutes", fails both ways. A 2% blip for 5 minutes pages someone at 3 a.m. although it spent 0.2% of the month's budget. And a steady 0.5%, which would spend 5 times the budget over the month, never pages at all. The alert should depend on how fast the **budget** is burning, and whether that's still happening.

### Step 2: recording rules

```yaml title="prometheus/slo-rules.yml · the SLI"
# SLO: 99.9% of commands answered without a server error, over 30 days.
# The error budget is the other 0.1%.
groups:
  - name: kv-slo-sli
    rules:
      # Error ratio over each window the alerts need: server errors / all commands.
      - record: kv:error_ratio:rate5m
        expr: sum(rate(kv_commands_total{result="server_error"}[5m])) / sum(rate(kv_commands_total[5m]))
      - record: kv:error_ratio:rate30m
        expr: sum(rate(kv_commands_total{result="server_error"}[30m])) / sum(rate(kv_commands_total[30m]))
      - record: kv:error_ratio:rate1h
        expr: sum(rate(kv_commands_total{result="server_error"}[1h])) / sum(rate(kv_commands_total[1h]))
      - record: kv:error_ratio:rate6h
        expr: sum(rate(kv_commands_total{result="server_error"}[6h])) / sum(rate(kv_commands_total[6h]))
      - record: kv:error_ratio:rate3d
        expr: sum(rate(kv_commands_total{result="server_error"}[3d])) / sum(rate(kv_commands_total[3d]))
```

Recording rules compute the error ratio over each window Prometheus needs, once, so every alert reads a precomputed series.

### Step 3: multi-window, multi-burn-rate

```yaml title="prometheus/slo-rules.yml · the alerts"
  - name: kv-slo-alerts
    rules:
      # Burn rate = error ratio / 0.001. At 14.4x, 2% of a 30-day budget goes in
      # one hour. Both windows must agree: the long one says it's serious, the
      # short one says it's still happening.
      - alert: KVErrorBudgetFastBurn
        expr: kv:error_ratio:rate1h > 14.4 * 0.001 and kv:error_ratio:rate5m > 14.4 * 0.001
        labels:
          severity: page
        annotations:
          summary: "kv is burning its error budget 14.4x too fast (2% of the month's budget per hour)"
      - alert: KVErrorBudgetSlowBurn
        expr: kv:error_ratio:rate6h > 6 * 0.001 and kv:error_ratio:rate30m > 6 * 0.001
        labels:
          severity: page
        annotations:
          summary: "kv is burning its error budget 6x too fast (5% of the month's budget in 6 hours)"
      - alert: KVErrorBudgetTicket
        expr: kv:error_ratio:rate3d > 1 * 0.001 and kv:error_ratio:rate6h > 1 * 0.001
        labels:
          severity: ticket
        annotations:
          summary: "kv is spending its error budget faster than it earns it"
```

This is the scheme from Google's SRE workbook. The **fast burn** pages when the last hour burned at 14.4× (2% of the month's budget in that hour). The **slow burn** pages at 6× over six hours (5% of the budget), catching slower leaks. The **ticket** goes to a queue, not a pager, at 1× over three days: the budget is being spent at least as fast as it's earned. And each alert has a **short window** alongside its long one: the long window decides whether it's serious, the short one whether it's **still happening**.

### Step 4: alerts with unit tests

Alert rules are code, so they get tests. `promtool test rules` replays synthetic time series through the real rule engine and checks which alerts are firing at given moments:

```yaml title="prometheus/slo-rules_test.yml · the outage case"
  # 2. An outage: from minute 60, 5% of commands fail (burn rate 50x).
  #    The fast-burn page must fire within the hour, the slow one later.
  - interval: 1m
    input_series:
      - series: 'kv_commands_total{command="GET",result="ok"}'
        values: '0+1000x60 60000+950x120'
      - series: 'kv_commands_total{command="GET",result="server_error"}'
        values: '0+0x60 0+50x120'
    alert_rule_test:
      - eval_time: 62m          # 2 minutes in: the 5m window agrees, the 1h one not yet
        alertname: KVErrorBudgetFastBurn
        exp_alerts: []
      - eval_time: 80m          # 20 minutes in: 1h ratio = 20/60 * 5% = 1.67% > 1.44%
        alertname: KVErrorBudgetFastBurn
        exp_alerts:
          - exp_labels:
              severity: page
            exp_annotations:
              summary: "kv is burning its error budget 14.4x too fast (2% of the month's budget per hour)"
```

`'0+1000x60 60000+950x120'` is promtool's series notation: start at 0 and add 1,000 per minute for 60 minutes, then continue from 60,000 adding 950 a minute. So the server errors go from 0 a minute to 50 a minute: a 5% outage starting at minute 60. The test says the page must **not** have fired 2 minutes in and **must** have fired 20 minutes in. The file has two more cases, a healthy 0.05% and a slow 0.7% leak that should page on six hours but not on one:

## A Rehearsed Incident

*Stop 4 of 5.*

### Step 1: scaling the clock

Burn-rate alerts are designed around hours and days, which makes them hard to watch. The rehearsal keeps the rules exactly as they are and divides every **window** by 60: the 1-hour window becomes 1 minute, 5 minutes becomes 5 seconds, 6 hours becomes 6 minutes. Prometheus scrapes and evaluates every second. So in the output below, read seconds as minutes. The thresholds (14.4× and 6×) don't change. The 3-day ticket alert is left out: its window would need 72 real minutes of history.

```yaml title="prometheus/prometheus.yml"
# Scrape the kv server every second and evaluate the rehearsal rules every
# second, so a scaled-down hour takes a real minute.
global:
  scrape_interval: 1s
  evaluation_interval: 1s
rule_files:
  - slo-rules-rehearsal.yml
scrape_configs:
  - job_name: kv
    static_configs:
      - targets: ["kv:9121"]
```

### Step 2: the run

## After the Incident

*Stop 5 of 5.*

### Step 1: what the budget says

On the rehearsal's clock, 90 seconds at 5% stands for 90 minutes at 5%: the same as 4.5 minutes of complete outage, **10.4% of the month's 43 minutes 12 seconds**. That's the number that matters, not "there was an incident". A team with 90% of its budget left carries on shipping; one that had already spent 95% would stop and fix things. The decision was made in advance, when the SLO was agreed.

### Step 2: a blameless postmortem

After a real incident, the team writes it up: what happened, when, what it cost, how it was detected, and what changes. **Blameless** means the document describes what the system and the process did, never who is at fault: people who fear blame hide the details that prevent the next incident. Here is the one for this rehearsal, every number from the run above:

```markdown title="postmortems/2026-09-28-kv-5pct-errors.md"

- 4,520 of 719,188 commands in the run failed with a server error (0.63%

- Error budget: 90 minutes at 5% is 4.5 minutes of full outage, 10.4% of
```

## Exercises

<Exercise n={1} title="A latency SLO" level="medium">

Write an SLI for latency: the fraction of commands answered within 1 ms, from the histogram. Add recording rules and a fast-burn alert for an SLO of 99% under 1 ms.

<Solution>

`sum(rate(kv_command_duration_seconds_bucket{le="0.001"}[5m])) / sum(rate(kv_command_duration_seconds_count[5m]))` is the good fraction; 1 minus it is the "error" ratio to compare with 14.4 × 0.01. The bucket boundaries decide which thresholds you can express: an SLO at 1 ms works because 0.001 is a bucket, and 0.8 ms wouldn't.

</Solution>

</Exercise>

<Exercise n={2} title="Test the ticket" level="easy">

Add a promtool test case where server errors run at 0.2% for four days. Which alerts fire, and when?

<Solution>

At 0.2% the burn rate is 2×: too slow for either page (14.4× and 6×), fast enough for the ticket (1× over 3 days and 6 hours). With `values: '0+998x5760'` and `'0+2x5760'` (4 days of minutes), the ticket fires once both windows have history, and the pages stay quiet at every evaluation.

</Solution>

</Exercise>

<Exercise n={3} title="Budget remaining" level="medium">

Write a recording rule for the error budget remaining this month, as a fraction, and alert when it goes below 25%.

<Solution>

`1 - (sum(increase(kv_commands_total{result="server_error"}[30d])) / sum(increase(kv_commands_total[30d]))) / 0.001`. It's a rolling 30 days rather than a calendar month, which is what most teams use. Below 0.25, the policy the team agreed (freeze risky launches, prioritise reliability) kicks in.

</Solution>

</Exercise>

<Lab
  title="Page Only When It Matters"
  archetype="fix-it"
  difficulty="guided"
  points={100}
  hintCost={10}
  verify="self-check"
  expect="ALL CHECKS PASS"
  objective="ErrorRatio counts clients' mistakes as failures, divides by the wrong total, panics when there's less history than the window, and returns NaN with no traffic. FastBurn checks only the one-hour window, so it keeps paging after recovery. Fix both so they page on a real outage, stay quiet for client mistakes, and stop paging when the errors stop."
  starter={`package main

import "fmt"

// Minute is one minute of a server's traffic.
type Minute struct{ OK, ClientErrors, ServerErrors int }

// ErrorRatio is the fraction of commands in the last n minutes of history
// (all of it, if there's less) that failed because of the server. A
// client's mistake was still served correctly, so it counts as served, not
// failed. No traffic at all means no failures: 0.
func ErrorRatio(history []Minute, n int) float64 {
	var ok, bad int
	for _, m := range history[len(history)-n:] {
		ok += m.OK
		bad += m.ServerErrors + m.ClientErrors
	}
	return float64(bad) / float64(ok)
}

// FastBurn reports whether to page: the error budget (1 - slo) is burning
// at least 14.4 times too fast over the last 60 minutes AND over the last
// 5 minutes, so the page stops as soon as the problem does.
func FastBurn(history []Minute, slo float64) bool {
	return ErrorRatio(history, 60) > 14.4*(1-slo)
}

// ── below this line: do not edit ──

func run(minutes int, m Minute) []Minute {
	h := make([]Minute, minutes)
	for i := range h {
		h[i] = m
	}
	return h
}

func main() {
	ok := true
	fail := func(f string, a ...any) { fmt.Printf("FAIL "+f+"\\n", a...); ok = false }
	near := func(a, b float64) bool { return a-b < 1e-9 && b-a < 1e-9 }
	safely := func(name string, f func()) {
		defer func() {
			if p := recover(); p != nil {
				fail("%s: panic: %v", name, p)
			}
		}()
		f()
	}
	const slo = 0.999

	safely("ratio", func() {
		h := run(10, Minute{OK: 990, ClientErrors: 5, ServerErrors: 5})
		if r := ErrorRatio(h, 10); !near(r, 0.005) {
			fail("ErrorRatio with 5 server errors in 1000 commands a minute = %v, want 0.005", r)
		}
	})
	safely("short history", func() {
		h := run(3, Minute{OK: 999, ServerErrors: 1})
		if r := ErrorRatio(h, 60); !near(r, 0.001) {
			fail("ErrorRatio over 60 minutes with only 3 minutes of history = %v, want 0.001", r)
		}
	})
	safely("no traffic", func() {
		if r := ErrorRatio(run(10, Minute{}), 5); r != 0 {
			fail("ErrorRatio with no traffic = %v, want 0", r)
		}
	})
	safely("client mistakes", func() {
		h := run(120, Minute{OK: 950, ClientErrors: 50})
		if FastBurn(h, slo) {
			fail("5%% client mistakes and no server errors paged someone")
		}
	})
	safely("outage", func() {
		h := append(run(60, Minute{OK: 1000}), run(20, Minute{OK: 950, ServerErrors: 50})...)
		if !FastBurn(h, slo) {
			fail("20 minutes at 5%% server errors didn't page")
		}
	})
	safely("recovered", func() {
		h := append(run(60, Minute{OK: 1000}), run(30, Minute{OK: 950, ServerErrors: 50})...)
		h = append(h, run(10, Minute{OK: 1000})...)
		if FastBurn(h, slo) {
			fail("still paging 10 minutes after the errors stopped")
		}
	})

	if ok {
		fmt.Println("ALL CHECKS PASS")
	}
}`}
  verifier="Checks ErrorRatio on a known mix, on a history shorter than the window and on no traffic, then FastBurn on two hours of 5% client mistakes, a 20-minute outage at 5% server errors, and ten minutes after a 30-minute outage. Prints ALL CHECKS PASS."
  hints={[

    "Clamp n to len(history) before slicing, and return 0 when there were no commands at all.",
    "Page only when both the 60-minute and the 5-minute ratios exceed 14.4 × (1 − slo)."

<Recap>

- An **SLI** is good events over all events; an **SLO** is its target over a window; the **error budget** is what the SLO allows to fail: 43 min 12 s a month at 99.9%.
- **Burn rate** is how fast the budget is spent: 14.4× uses 2% of a month's budget per hour and all of it in 50 hours.
- Honest metrics: count **server** errors only against the SLO, keep label **cardinality** bounded, and create every series at **zero** (the first rehearsal's error ratio was blank, not 0%).
- **Multi-window, multi-burn-rate** alerts page when a long window says it's serious and a short one says it's still happening. promtool tests proved the rules, and a single-window version was still paging 10 minutes after recovery.
- In a **rehearsed incident** on Prometheus 3.15.0 (windows scaled 60×), 5% failures paged in 21 s (21 min), matching the promtool test, and the page stopped 6 s after the fix. It spent 10.4% of the month's budget, written up in a **blameless postmortem**.

</Recap>
