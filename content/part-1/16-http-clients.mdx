## The Default Client Is a Trap

Here's the scene. Your checkout service is calling an exchange-rate API to convert USD to EUR before charging a card. You reach for the obvious thing:

```go
// exchangerate.go — the thing that will haunt you
package main

import (
	"fmt"
	"io"
	"net/http"
)

func fetchRate(from, to string) ([]byte, error) {
	// http.Get uses http.DefaultClient — and DefaultClient has NO timeout.
	resp, err := http.Get("https://api.example.com/rates/" + from + "/" + to)
	if err != nil {
		return nil, err
	}
	defer resp.Body.Close()
	return io.ReadAll(resp.Body)
}

func main() {
	data, err := fetchRate("USD", "EUR")
	if err != nil {
		fmt.Println("error:", err)
		return
	}
	fmt.Printf("got %d bytes\n", len(data))
}
```

What's wrong with it? Everything you can't see. The call to `http.Get` uses the package-level `http.DefaultClient`, which is defined as:

```go
// From the Go standard library — net/http/client.go
var DefaultClient = &Client{}
```

<Define term="http.Client (and the no-timeout trap)" since="Reliability Patterns (Part 2)">
`http.Client` is the struct you use to make HTTP requests. Its zero value (`&http.Client{}`) has **no timeout** — if the server never responds, the call blocks forever. In a server handling concurrent requests, one hung downstream call becomes one blocked goroutine per in-flight request, draining file descriptors until the process dies. Always set `Timeout` on any client that calls an external API. `http.DefaultClient` is exactly this zero value — it is safe only for one-off scripts, never for production services.
</Define>

An empty `&http.Client{}`. Zero fields set. **No timeout.** If the exchange-rate server stops responding, your goroutine blocks forever — or rather, until the OS eventually gives up (which could be minutes). In a request handler, that's a leaked goroutine. Under traffic, it's a leaked goroutine for every concurrent checkout.

The fix is exactly one change: **build your own client.**

```go
// exchangerate.go — the right way
package main

import (
	"fmt"
	"io"
	"net/http"
	"time"
)

// Build ONE client at package level and reuse it.
// Never create a new http.Client per request.
var httpClient = &http.Client{
	Timeout: 5 * time.Second, // end-to-end: dial + TLS + headers + body
}

func fetchRate(from, to string) ([]byte, error) {
	resp, err := httpClient.Get("https://api.example.com/rates/" + from + "/" + to)
	if err != nil {
		return nil, fmt.Errorf("fetchRate: %w", err)
	}
	defer resp.Body.Close()
	return io.ReadAll(resp.Body)
}

func main() {
	data, err := fetchRate("USD", "EUR")
	if err != nil {
		fmt.Println("error:", err)
		return
	}
	fmt.Printf("got %d bytes\n", len(data))
}
```

`http.Client.Timeout` is the end-to-end deadline: it starts the moment the `Get` call is made and covers dialing, the TLS handshake, sending the request, and reading the full response body. If *anything* in that chain takes longer than five seconds, the whole call returns an error. Your goroutine is never parked forever again.

## Timeouts at Every Layer

The `Client.Timeout` is a blunt instrument. It covers the entire round trip. Sometimes you need surgical precision: what if the dial takes ages but the response streams fine? What if TLS negotiation stalls? What if headers arrive but the body never finishes?

`http.Transport` exposes those knobs. Here's the full picture:

```go
// payment/client.go — surgical timeouts for each phase
package payment

import (
	"net"
	"net/http"
	"time"
)

// NewClient builds a production-grade HTTP client for the payment API.
// Inject this via dependency injection — never use a package-level global
// in library code.
func NewClient() *http.Client {
	transport := &http.Transport{
		// How long to wait for a TCP connection to be established.
		DialContext: (&net.Dialer{
			Timeout:   3 * time.Second,
			KeepAlive: 30 * time.Second,
		}).DialContext,

		// How long the TLS handshake may take.
		TLSHandshakeTimeout: 5 * time.Second,

		// How long to wait for the server's first response byte (headers).
		ResponseHeaderTimeout: 5 * time.Second,

		// How long an idle connection can sit in the pool.
		IdleConnTimeout: 90 * time.Second,

		// Connection pool tuning (covered in the next section).
		MaxIdleConns:        100,
		MaxIdleConnsPerHost: 10,
	}

	return &http.Client{
		// End-to-end timeout: the outer safety net.
		// Must be larger than the sum of your inner timeouts.
		Timeout:   10 * time.Second,
		Transport: transport,
	}
}
```

**Which one to set when?**

| Situation | Reach for |
|---|---|
| Simple script or tool | `Client.Timeout` alone is usually enough |
| Service calling external APIs | `Client.Timeout` + `ResponseHeaderTimeout` at minimum |
| High-stakes financial calls | All four transport timeouts + `Client.Timeout` |
| Per-request dynamic deadline | `context` with `WithTimeout` or `WithDeadline` (see Section 4) |

<Callout kind="note" title="Client.Timeout vs. a context deadline">

`Client.Timeout` is a static ceiling on the whole client for every request it makes. A `context.WithTimeout` deadline is per-request and propagates cancellation to everything downstream that receives the context — database calls, sub-requests, log flushes. In a real service handler, you typically carry both: the client's static `Timeout` as the outer safety net, and a per-request context deadline from the incoming HTTP request's context for fine-grained propagation. Section 4 covers this precisely.

</Callout>

## Transport and Connection Pooling

<Define term="http.Transport (connection pool and keep-alive)">
`http.Transport` is the layer beneath `http.Client` that actually manages TCP connections. It maintains a **connection pool** keyed by host — when a request finishes, the connection goes back into the pool and the next request to the same host reuses it, skipping the TCP handshake and TLS negotiation entirely. The pool is the reason you must create one `http.Client` at startup and reuse it: a brand-new client has a brand-new, empty pool, so every request pays the full dial + TLS cost. **On the job:** at 100 requests per second to a payment API, a per-request client means 100 new TLS handshakes per second — 5–10x slower than a pooled client and far more load on the remote service.
</Define>

Here is the mistake I see constantly, and it makes me genuinely, personally sad:

```go
// checkout handler — DO NOT DO THIS
func handleCheckout(w http.ResponseWriter, r *http.Request) {
	client := &http.Client{Timeout: 5 * time.Second} // new client per request!
	resp, err := client.Get("https://payment.example.com/charge")
	// ...
}
```

Every request creates a fresh `http.Client` with a fresh `http.Transport`. The transport has a connection pool — but a brand-new pool. Every request opens a brand-new TCP connection, does a fresh TLS handshake, sends the request, then *discards* the connection. At 100 requests per second that's 100 new TCP + TLS round trips per second to your payment API. You've implemented the slowest possible billing system.

**One client. Reused everywhere.** The transport's connection pool is the whole point.

```go
// payment/client.go — ONE client, reused for the life of the service
package payment

import (
	"net"
	"net/http"
	"time"
)

// Client wraps http.Client with payment-API-specific defaults.
type Client struct {
	http *http.Client
	base string
}

// NewClient constructs a Client. Call it once at startup; inject it everywhere.
func NewClient(baseURL string) *Client {
	tr := &http.Transport{
		DialContext: (&net.Dialer{
			Timeout:   3 * time.Second,
			KeepAlive: 30 * time.Second, // keeps idle TCP connections alive
		}).DialContext,
		MaxIdleConns:        100, // total idle connections across all hosts
		MaxIdleConnsPerHost: 10,  // idle connections to ONE host (payment API)
		IdleConnTimeout:     90 * time.Second,
	}
	return &Client{
		http: &http.Client{Timeout: 8 * time.Second, Transport: tr},
		base: baseURL,
	}
}
```

Now let's talk about what the pool actually does.

<Define term="The drain-and-close body rule">
After every HTTP response, you must **close the body**; to reuse the connection, you must also read the body to completion before closing it. If you close without draining, the transport usually discards the connection — it cannot reuse a TCP stream that still has bytes pending. The idiom is `defer resp.Body.Close()` plus `io.Copy(io.Discard, resp.Body)` for any path where you don't need the bytes. **On the job:** skipping `Close` leaks resources; skipping the drain sacrifices keep-alive reuse and forces extra dials under load.
</Define>

<UnderTheHood title="How http.Transport pools connections (Go 1.26 baseline)">

`http.Transport` is the real workhorse. It maintains an **idle connection pool** keyed by `{scheme, host, port}` (the "canonical address"). When you make a request:

1. The transport checks the pool for an idle connection to that host. If one exists, it grabs it and skips the TCP + TLS overhead entirely.
2. If none are available and the pool isn't full, it dials a new connection.
3. After the response body is fully read and closed, the connection is returned to the pool, ready for the next request.

The pool's size is controlled by two fields:

- **`MaxIdleConns`** — the absolute cap on idle connections across *all* hosts. Default 100. Zero means no limit (dangerous under load).
- **`MaxIdleConnsPerHost`** — idle connections to a *single* host. Default 2, which is surprisingly small for a high-throughput service calling one payment API. Setting it to match your expected concurrency (e.g. 10–20) prevents "connection churn" — the transport repeatedly opening and closing connections because the two idle slots are always taken.

The pool key includes the full authority (`host:port`) and the scheme. `http://payment.example.com` and `https://payment.example.com` use separate pools. Connections are not shared between clients — each `http.Client` with its own `http.Transport` has its own pool.

**The body-must-be-closed-and-drained rule.** This is where engineers cause themselves pain. The transport can only return a connection to the pool after the response body is fully consumed *and* closed. If you close the body without reading it, the transport has to *discard* the connection — it can't reuse an open TCP stream that still has bytes in it. The pattern is:

```go
resp, err := client.Do(req)
if err != nil { return err }
defer resp.Body.Close()
// Read the full body (or io.Copy to io.Discard if you don't need it)
_, _ = io.Copy(io.Discard, resp.Body)
```

Forgetting to close the body leaks resources. Closing without draining does not usually leak the file descriptor, but it prevents connection reuse, so the transport opens a new connection for the next request. Under load that becomes avoidable dial churn, TLS handshakes, and pool pressure.

**`KeepAlive` on the dialer** sends TCP keepalive probes on idle connections, detecting when a middlebox (load balancer, NAT gateway) silently closes the connection beneath you. Setting it to 30 seconds means the transport detects dead idle connections before trying to use them, avoiding the "stale connection" error your next request would otherwise get.

**Go 1.26 note — `net.Dialer` context-aware dial methods.** As of Go 1.26, `net.Dialer` gained explicit `DialTCP` and related methods that accept a `context.Context` directly, giving you per-dial cancellation without wrapping in `DialContext`. For most services the `DialContext` field on `http.Transport` is still the right integration point, but if you are building a custom transport or a raw TCP dialer, the new methods are the cleaner API.

</UnderTheHood>

## Context-Aware Requests

<Define term="Context deadline" since="The context Package, In Depth (Part 1)">
A **context deadline** (set via `context.WithTimeout` or `context.WithDeadline`) is an absolute timestamp attached to a `context.Context`. When the deadline expires, `ctx.Done()` is closed and every operation carrying that context — HTTP calls, database queries, downstream sub-requests — is signalled to cancel. Unlike `http.Client.Timeout` (which is a static per-client ceiling), a context deadline is **per-request** and propagates automatically through the entire call tree. **On the job:** in a payment service handler, the gateway gives you a 3-second context; threading it into every downstream call ensures that when the customer times out, *all* the work for that request stops — no zombie goroutines charging cards after the customer already got a 504.
</Define>

Your checkout service receives an HTTP request with a context. That context has a deadline: if the customer waits more than 3 seconds, the gateway cancels the whole thing. Your downstream payment call should be cancelled *at the same moment* — not left running like a zombie goroutine after the customer already got a timeout page.

The answer is `http.NewRequestWithContext`:

```go
// checkout/handler.go — propagating the request context to every downstream call
package checkout

import (
	"context"
	"encoding/json"
	"fmt"
	"io"
	"net/http"
)

type PaymentResponse struct {
	TransactionID string `json:"transaction_id"`
	Status        string `json:"status"`
}

func chargeCard(ctx context.Context, client *http.Client, amount int) (*PaymentResponse, error) {
	// Build the request AND attach the caller's context.
	req, err := http.NewRequestWithContext(ctx, http.MethodPost,
		"https://payment.example.com/charge", nil)
	if err != nil {
		return nil, fmt.Errorf("chargeCard: build request: %w", err)
	}

	// Context cancellation (customer timeout, gateway cancellation)
	// will automatically abort this HTTP call.
	resp, err := client.Do(req)
	if err != nil {
		return nil, fmt.Errorf("chargeCard: do request: %w", err)
	}
	defer resp.Body.Close()

	if resp.StatusCode != http.StatusOK {
		// Drain the error body so the connection can return to the pool.
		_, _ = io.Copy(io.Discard, resp.Body)
		return nil, fmt.Errorf("chargeCard: unexpected status %d", resp.StatusCode)
	}

	var pr PaymentResponse
	if err := json.NewDecoder(resp.Body).Decode(&pr); err != nil {
		return nil, fmt.Errorf("chargeCard: decode: %w", err)
	}
	// Drain any trailing bytes so the connection returns to the pool.
	_, _ = io.Copy(io.Discard, resp.Body)
	return &pr, nil
}
```

<Callout kind="note" title="http.NewRequest vs http.NewRequestWithContext">

`http.NewRequest` attaches `context.Background()` — a context that is never cancelled. Use it only in tests or tools that truly have no caller context. In any server handler or service function, use `http.NewRequestWithContext` and pass the context you received. If you don't have a context, acquire one with `context.WithTimeout` or `context.WithDeadline`. The context chapter covers the full story (Part 1, Chapter 6).

</Callout>

## Retries

<Define term="Retry with exponential backoff and jitter" since="Reliability Patterns (Part 2)">
A **retry** re-sends a failed request, hoping a transient error (network hiccup, momentary overload) has cleared. **Exponential backoff** makes each successive retry wait longer (100ms → 200ms → 400ms…) so you don't hammer a struggling server. **Jitter** adds randomness to that wait so thousands of retrying clients don't all fire at the same millisecond — the "thundering herd" that turns a brief overload into a sustained outage. **On the job:** retrying without backoff+jitter at scale is actively harmful — it amplifies the load at exactly the moment the server is already struggling.
</Define>

The payment API is flaky. Your exchange-rate provider returns 500s every few minutes. You need to retry — but not blindly, and not in a way that makes a struggling server worse.

Two rules before you write a single line of retry logic:

1. **Only retry idempotent requests.** A `GET` is always safe to retry. A `POST /charge` is not — retrying might double-charge the customer. For non-idempotent writes, use an idempotency key (Part 3 covers this in depth). For now, limit retries to `GET` and `HEAD`, or to writes that explicitly fail at the network level (connection refused, timeout) where you can be sure the server never saw the request.

2. **Exponential backoff with jitter.** Retrying immediately at full speed against an overloaded server makes things *worse*. Back off exponentially (wait longer each retry) and add random jitter so thousands of retrying clients don't all slam the server at the same millisecond — the "thundering herd" problem.

```go
// retry/retry.go — idempotency-aware retry with backoff+jitter
package retry

import (
	"context"
	"fmt"
	"io"
	"math/rand"
	"net/http"
	"time"
)

// Config holds retry policy parameters.
type Config struct {
	MaxAttempts int           // total tries (first attempt + retries)
	BaseDelay   time.Duration // initial wait between retries
	MaxDelay    time.Duration // cap on the wait
}

// DefaultConfig is a reasonable baseline for calling external APIs.
var DefaultConfig = Config{
	MaxAttempts: 3,
	BaseDelay:   200 * time.Millisecond,
	MaxDelay:    2 * time.Second,
}

// Do executes req with retry logic.
// Only retries on network errors and 5xx responses.
// The request must be idempotent (GET, HEAD) or the caller must guarantee safety.
func Do(ctx context.Context, client *http.Client, req *http.Request, cfg Config) (*http.Response, error) {
	var (
		resp *http.Response
		err  error
	)

	for attempt := 0; attempt < cfg.MaxAttempts; attempt++ {
		if attempt > 0 {
			// Exponential backoff: 200ms, 400ms, 800ms… capped at MaxDelay.
			delay := cfg.BaseDelay * time.Duration(1<<uint(attempt-1))
			if delay > cfg.MaxDelay {
				delay = cfg.MaxDelay
			}
			// Jitter: +/- 20% so clients don't sync up.
			jitter := time.Duration(rand.Int63n(int64(delay) / 5))
			if rand.Intn(2) == 0 {
				delay += jitter
			} else {
				delay -= jitter
			}

			select {
			case <-ctx.Done():
				return nil, fmt.Errorf("retry: context cancelled during backoff: %w", ctx.Err())
			case <-time.After(delay):
			}
		}

		// Clone the request context from the outer context so cancellation propagates.
		r := req.WithContext(ctx)

		resp, err = client.Do(r)
		if err != nil {
			// Network error (timeout, connection refused) — always retry.
			continue
		}

		// Drain + close so the connection returns to the pool on non-success responses.
		if resp.StatusCode < 500 {
			// 2xx, 3xx, 4xx: don't retry. 4xx is a client error — retrying won't help.
			return resp, nil
		}

		// 5xx: drain and retry.
		_, _ = io.Copy(io.Discard, resp.Body)
		resp.Body.Close()
	}

	if err != nil {
		return nil, fmt.Errorf("retry: all %d attempts failed: %w", cfg.MaxAttempts, err)
	}
	return resp, fmt.Errorf("retry: all %d attempts returned 5xx", cfg.MaxAttempts)
}
```

<Callout kind="warn" title="Deep reliability lives in Part 2">

What we have here is a clean, intro-level retry with backoff. Part 2's "Reliability Patterns" chapter adds the full story: **circuit breakers** (stop retrying when a downstream is clearly broken), **adaptive timeouts**, **retry budgets**, per-key rate limiting, and using `golang.org/x/sync/errgroup` to fan out and cancel peers when one attempt succeeds. If you're building a payment gateway today, bookmark that chapter. For now, the rule is: backoff + jitter + idempotency awareness. You won't embarrass yourself.

</Callout>

## Decoding Responses Safely

The exchange-rate API responds with JSON. You have three enemies: a non-200 status you forgot to check, a body that's 500 MB of garbage from a misconfigured upstream, and a `Content-Type` that doesn't match what you expect. All three are real production bugs.

Here is the full, safe decoding pattern:

```go
// rates/client.go — safe response decoding
package rates

import (
	"encoding/json"
	"fmt"
	"io"
	"net/http"
	"strings"
)

// ExchangeRate is what the API returns.
type ExchangeRate struct {
	From string  `json:"from"`
	To   string  `json:"to"`
	Rate int64   `json:"rate_millionths"` // e.g. 1_082_300 = 1.0823 USD/EUR
}

const maxBodyBytes = 1 << 20 // 1 MiB — a rate response has no business being larger

func fetchRate(client *http.Client, url string) (*ExchangeRate, error) {
	resp, err := client.Get(url)
	if err != nil {
		return nil, fmt.Errorf("fetchRate: request: %w", err)
	}
	defer resp.Body.Close()

	// Step 1: check the status code BEFORE touching the body.
	if resp.StatusCode != http.StatusOK {
		// Drain the error body (for connection reuse) then return.
		body, _ := io.ReadAll(io.LimitReader(resp.Body, 4096))
		return nil, fmt.Errorf("fetchRate: server returned %d: %s", resp.StatusCode, body)
	}

	// Step 2: verify Content-Type — reject HTML error pages masquerading as JSON.
	ct := resp.Header.Get("Content-Type")
	if !strings.Contains(ct, "application/json") {
		_, _ = io.Copy(io.Discard, resp.Body)
		return nil, fmt.Errorf("fetchRate: unexpected Content-Type %q", ct)
	}

	// Step 3: cap the body size with io.LimitReader — never trust the server.
	limited := io.LimitReader(resp.Body, maxBodyBytes)

	// Step 4: stream-decode with json.Decoder — no buffering the whole body into []byte first.
	var rate ExchangeRate
	if err := json.NewDecoder(limited).Decode(&rate); err != nil {
		return nil, fmt.Errorf("fetchRate: decode: %w", err)
	}
	return &rate, nil
}
```

Each step stops a different attack:

<ConceptGrid cols={3}>
  <ConceptCard label="Check status first">A 503 or 404 body might be an HTML error page. Decoding it as JSON gives a confusing error. Check status, drain, return early.</ConceptCard>
  <ConceptCard label="io.LimitReader">Wraps the body so reads stop at your byte ceiling. Without it, a malicious or misconfigured server can stream gigabytes into your process until it OOMs.</ConceptCard>
  <ConceptCard label="json.Decoder (streaming)">Reads from the reader incrementally. `io.ReadAll + json.Unmarshal` buffers the entire body in memory first. For large responses, streaming is the only sane choice.</ConceptCard>
  <Gotcha>Never skip the status code check. `json.Decoder` will try to parse an HTML error page and return a cryptic `invalid character` error that tells you nothing about the actual 503 the server sent.</Gotcha>
</ConceptGrid>

**`io.ReadAll` vs. `json.Decoder` — when to use which:**

<BeforeAfter
  badLabel="io.ReadAll (buffers all)"
  goodLabel="json.Decoder (streaming)"
  bad={`body, _ := io.ReadAll(resp.Body)
json.Unmarshal(body, &rate)`}
  good={`limited := io.LimitReader(resp.Body, 1<<20)
json.NewDecoder(limited).Decode(&rate)`}
/>

`io.ReadAll` is fine when:
- The response body is small (a few KB) and you already know that.
- You need the raw bytes for something else (signature verification, logging).

`json.Decoder` (streaming) is better when:
- The body can be large or unbounded.
- You can decode in a single pass without needing the raw bytes.
- You want to start decoding before the full body arrives.

<Callout kind="note" title="io.ReadAll is ~2x faster in Go 1.26">

As of Go 1.26, `io.ReadAll` was reworked to use a smarter initial buffer strategy, yielding roughly 2x throughput and ~50% fewer allocations on typical response bodies. If your code already uses `io.ReadAll` for small, known-size payloads (webhook bodies, auth tokens, error previews), you get this improvement for free with no code change. The streaming `json.Decoder` path is still preferable for large or unbounded bodies — but the performance gap between the two has narrowed for the small-body case.

</Callout>

```go
package main

import (
	"context"
	"fmt"
	"io"
	"net/http"
	"net/http/httptest"
	"sync/atomic"
	"time"
)

func getWithRetry(ctx context.Context, client *http.Client, url string, maxAttempts int) (*http.Response, error) {
	base := 100 * time.Millisecond
	maxDelay := 1 * time.Second

	for attempt := 0; attempt < maxAttempts; attempt++ {
		if attempt > 0 {
			delay := base * time.Duration(1<<uint(attempt-1))
			if delay > maxDelay {
				delay = maxDelay
			}
			select {
			case <-ctx.Done():
				return nil, fmt.Errorf("context cancelled during backoff: %w", ctx.Err())
			case <-time.After(delay):
			}
		}

		req, err := http.NewRequestWithContext(ctx, http.MethodGet, url, nil)
		if err != nil {
			return nil, err
		}

		resp, err := client.Do(req)
		if err != nil {
			fmt.Printf("attempt %d: error: %v\n", attempt+1, err)
			continue
		}
		if resp.StatusCode >= 500 {
			_, _ = io.Copy(io.Discard, resp.Body)
			resp.Body.Close()
			fmt.Printf("attempt %d: 5xx %d\n", attempt+1, resp.StatusCode)
			continue
		}
		return resp, nil
	}
	return nil, fmt.Errorf("all %d attempts failed", maxAttempts)
}

func main() {
	var n atomic.Int32
	srv := httptest.NewServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		if n.Add(1) < 3 {
			w.WriteHeader(503)
			return
		}
		fmt.Fprintln(w, "ok")
	}))
	defer srv.Close()

	ctx := context.Background()
	client := &http.Client{Timeout: 3 * time.Second}
	resp, err := getWithRetry(ctx, client, srv.URL, 5)
	if err != nil {
		fmt.Println("error:", err)
		return
	}
	defer resp.Body.Close()
	body, _ := io.ReadAll(resp.Body)
	fmt.Println("response:", string(body))
}

The `select` with `ctx.Done()` is critical — if the context is cancelled during the backoff sleep, the function returns immediately rather than waiting the full delay. This is what makes retries context-aware.

	"net/http/httptest"
	"strings"
	"sync/atomic"
	"time"
)

type RateService struct {
	client *http.Client
	base   string
}

func NewRateService(baseURL string) *RateService {
	tr := &http.Transport{
		DialContext: (&net.Dialer{
			Timeout:   3 * time.Second,
			KeepAlive: 30 * time.Second,
		}).DialContext,
		MaxIdleConnsPerHost: 5,
		IdleConnTimeout:     60 * time.Second,
	}
	return &RateService{
		client: &http.Client{Timeout: 6 * time.Second, Transport: tr},
		base:   baseURL,
	}
}

type rateResponse struct {
	Rate int64 `json:"rate_millionths"`
}

func (s *RateService) FetchRate(ctx context.Context, from, to string) (int64, error) {
	url := fmt.Sprintf("%s/rates/%s/%s", s.base, from, to)
	baseDelay := 200 * time.Millisecond

	for attempt := 0; attempt < 3; attempt++ {
		if attempt > 0 {
			delay := baseDelay * time.Duration(1<<uint(attempt-1))
			select {
			case <-ctx.Done():
				return 0, fmt.Errorf("FetchRate: context done in backoff: %w", ctx.Err())
			case <-time.After(delay):
			}
		}

		req, err := http.NewRequestWithContext(ctx, http.MethodGet, url, nil)
		if err != nil {
			return 0, fmt.Errorf("FetchRate: build request: %w", err)
		}

		resp, err := s.client.Do(req)
		if err != nil {
			continue // network error: retry
		}

		if resp.StatusCode >= 500 {
			_, _ = io.Copy(io.Discard, resp.Body)
			resp.Body.Close()
			continue
		}

		// Non-retryable path: handle here, close explicitly (no defer inside a loop).
		if resp.StatusCode != http.StatusOK {
			b, _ := io.ReadAll(io.LimitReader(resp.Body, 512))
			resp.Body.Close()
			return 0, fmt.Errorf("FetchRate: status %d: %s", resp.StatusCode, b)
		}
		ct := resp.Header.Get("Content-Type")
		if !strings.Contains(ct, "application/json") {
			_, _ = io.Copy(io.Discard, resp.Body)
			resp.Body.Close()
			return 0, fmt.Errorf("FetchRate: unexpected content-type %q", ct)
		}

		var r rateResponse
		err = json.NewDecoder(io.LimitReader(resp.Body, 64*1024)).Decode(&r)
		_, _ = io.Copy(io.Discard, resp.Body) // drain trailing bytes
		resp.Body.Close()
		if err != nil {
			return 0, fmt.Errorf("FetchRate: decode: %w", err)
		}
		return r.Rate, nil
	}
	return 0, fmt.Errorf("FetchRate: all 3 attempts failed")
}

func main() {
	var calls atomic.Int32
	srv := httptest.NewServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		n := calls.Add(1)
		if n < 3 {
			w.WriteHeader(503)
			return
		}
		w.Header().Set("Content-Type", "application/json")
		fmt.Fprintln(w, `{"rate_millionths":1082300}`)
	}))
	defer srv.Close()

	svc := NewRateService(srv.URL)
	rate, err := svc.FetchRate(context.Background(), "USD", "EUR")
	if err != nil {
		fmt.Println("error:", err)
		return
	}
	fmt.Printf("rate: %d millionths (%.4f)\n", rate, float64(rate)/1_000_000)
}
```

This is production-grade. Dependency injection via constructor, context at every call site, status and content-type validation, streaming decode, retries that respect context. The only thing it's missing is a circuit breaker — which Part 2 covers.

</Solution>

<Recap>

- **`http.DefaultClient` has no timeout.** Build your own `&http.Client{Timeout: ...}` and inject it. Never create a new client per request.
- **Timeouts layer:** `Client.Timeout` is the end-to-end deadline; `Transport` fields (dial, TLS, response-header) guard individual phases. Set them surgically, and make `Client.Timeout` larger than any individual phase.
- **One transport, one pool.** `http.Transport` maintains a connection pool keyed by host. `MaxIdleConnsPerHost` controls how many idle connections are kept per host — default 2 is too low for high-concurrency services.
- **Drain before close.** Read (or discard) the full response body before calling `Close()`, or the connection cannot be returned to the pool. `io.Copy(io.Discard, resp.Body)` is the idiom.
- **`http.NewRequestWithContext`** threads cancellation and deadlines from the caller into the outbound request. Use it in every server handler and service function. Never use `http.NewRequest` when you have a context.
- **Retry idempotent requests only** — `GET` and `HEAD` are safe; `POST /charge` is not without an idempotency key. Exponential backoff + jitter prevents thundering-herd pile-ons.
- **Decode defensively:** check status before touching the body, gate on `Content-Type`, wrap with `io.LimitReader`, stream with `json.Decoder`. For small, fixed-size payloads where you need raw bytes, `io.ReadAll` is fine — and as of Go 1.26 it is roughly 2x faster with ~50% fewer allocations than before.

</Recap>
