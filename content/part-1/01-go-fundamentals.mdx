## Packages and main

*Stop 1 of 5.*

### Step 1: the smallest real program

```go
package main

import "fmt"

func main() {
	subtotal := 1499 // a $14.99 item, in cents
	fmt.Println("subtotal in cents:", subtotal)
}
```

Read it one line at a time:

- **`package main`**: every Go file starts by saying which package it belongs to. A package named `main` is special: it's the one Go turns into a program you can run. Any other name makes a library.
- **`import "fmt"`**: use another package. `fmt` (short for "format") prints and formats text. After importing it, you reach its contents with a dot: `fmt.Println`.
- **`func main() { … }`**: a function named `main`, taking nothing and returning nothing. When the program starts, Go calls it. When it returns, the program ends.
- **`subtotal := 1499`**: make a variable named `subtotal` holding `1499`. (Step 1 of the next stop unpacks `:=`.)
- **`// a $14.99 item…`**: a comment, for humans. Go ignores everything after `//` on the line.
- **`fmt.Println(…)`**: call the function `Println` from package `fmt`. It prints its arguments separated by spaces and ends the line.

<GoPlayground>

```go
package main

import "fmt"

	subtotal := 1499 // a $14.99 item, in cents
	fmt.Println("subtotal in cents:", subtotal)
}
```

</GoPlayground>

We store money as a whole number of **cents** (`1499`, not `14.99`). Stop 2 shows, with real output, why that's not pedantry.

<Define term="Package">
Go's unit of code: a directory of `.go` files that share one namespace. You import it by path (`"fmt"`, `"net/http"`) and use its names with a dot (`fmt.Println`). A name starting with a **capital letter** is **exported** (usable from other packages); lowercase names are private to their package. That capital letter is Go's only public/private keyword.
</Define>

### Step 2: the compiler is strict on purpose

Add an import you don't use, or a variable you never read, and Go refuses to build. These are errors, not warnings:

```text
./main.go:5:2: "os" imported and not used
./main.go:10:2: declared and not used: tax
```

It feels fussy for a day. Then you realise every Go codebase you ever open has no dead imports and no forgotten variables, because it can't.

### Step 3: what runs, in what order

`main` isn't quite the first thing that happens. Before it, Go sets up every package: first package-level variables, then any `func init()`:

<GoPlayground>

```go

func describe(s string) string {
	fmt.Println("1.", s, "initialised")
	return s
}

func init() {
	fmt.Println("2. init() runs")
}

func main() {
	fmt.Println("3. main() runs")
}
```

</GoPlayground>

```text

2. init() runs
3. main() runs
```

## Variables and Types

*Stop 2 of 5.*

### Step 1: four ways to make a variable, one habit

```go
var count int        // name, then type; no value, so it starts at 0
var price int = 1499 // name, type, value (the type is redundant here)
var price = 1499     // Go infers the type from the value: int
price := 1499        // short form: declare + infer; only inside functions
```

**Reading tip:** Go puts the **name before the type**: `var count int` reads "variable `count`, of type `int`". (C and Java put the type first; Go chose the order you'd say out loud.)

You'll use `:=` most of the time inside functions. At package level (outside any function), you must use `var`.

<Define term="Variable and :=">
A variable is a named slot holding a value of one fixed type. `price := 1499` **declares** a new variable, **infers** its type from the right-hand side (`int`), and stores the value. `=` without the colon **assigns** to a variable that already exists. Mixing them up is the source of the shadowing bug in Stop 3.
</Define>

### Step 2: the basic types

Go is **statically typed**: every variable's type is fixed when the program compiles, and the compiler checks every use.

<ConceptGrid cols={3}>
  <ConceptCard label="int">A whole number. Its size is the machine's word: 64 bits on today's servers and laptops (±9.2 quintillion), 32 bits on some small devices. Use <code>int64</code> when the size must be fixed, like money stored in a database.</ConceptCard>
  <ConceptCard label="float64">A number with a fractional part, like <code>3.14</code>. Fine for measurements and graphics. Wrong for money (Step 3).</ConceptCard>
  <ConceptCard label="string">A read-only sequence of bytes, usually UTF-8 text: <code>"checkout"</code>.</ConceptCard>
  <ConceptCard label="bool"><code>true</code> or <code>false</code>. Numbers aren't booleans in Go: `if 1 {}` doesn't compile.</ConceptCard>
  <ConceptCard label="byte / rune"><code>byte</code> is an 8-bit number (an alias for <code>uint8</code>). <code>rune</code> is a Unicode code point (an alias for <code>int32</code>). Step 4 shows why you need both.</ConceptCard>
  <ConceptCard label="uint">An integer that can't be negative. Tempting for counts, but <code>uint(2) - 3</code> wraps around to a huge number. Use <code>int</code> unless you have a specific reason.</ConceptCard>
  <Gotcha>Go never converts between number types for you. <code>var a int = 5; var b int64 = a</code> doesn't compile; write <code>int64(a)</code>. It's a little more typing and a whole category of silent bugs gone.</Gotcha>
</ConceptGrid>

### Step 3: why money is integer cents

Here are three ordinary money calculations in `float64`, run:

<GoPlayground>

```go
package main

import "fmt"

func main() {
	coffee, muffin := 1.10, 2.20
	total := coffee + muffin
	fmt.Println(total, total == 3.30) // a $1.10 coffee and a $2.20 muffin

	price := 1.15
	fmt.Println(price*100, int(price*100)) // converting $1.15 to cents

	var sum float64
	for range 10 {
		sum += 0.10 // ten 10-cent items
	}
	fmt.Println(sum, sum == 1.0)

	cents := 110 + 220 // the same coffee and muffin, in cents
	fmt.Println(cents, cents == 330)
}
```

</GoPlayground>

```text
3.3000000000000003 false
114.99999999999999 114
0.9999999999999999 false
330 true
```

Look at the second line: converting $1.15 to cents with `int(price*100)` gives **114**. A cent vanished, and nothing crashed. `float64` stores numbers in binary, and most decimal fractions (0.1, 1.15) have no exact binary form, the way 1/3 has no exact decimal form. Every calculation rounds a little, and money makes the rounding visible.

Integers are exact. So: **store money as a whole number of the smallest unit (cents), and only format it as dollars when printing.** Part 3 builds a full money type on this rule.

<Define term="Integer cents">
Money held as a whole number of the smallest currency unit: `$14.99` is `1499`. Display it with `fmt.Sprintf("$%d.%02d", cents/100, cents%100)` (the lab in ch0 handles negative amounts too). Integer arithmetic is exact; binary floating point isn't.
</Define>

<Callout kind="note" title="A surprise: 0.1 + 0.2 == 0.3 is true in Go">

Write `fmt.Println(0.1+0.2 == 0.3)` and Go prints `true`, unlike most languages. That's because `0.1` and `0.2` written directly in code are **untyped constants**, and Go computes constant arithmetic exactly, at compile time. Put them in `float64` variables first (`a, b := 0.1, 0.2`) and `a+b == 0.3` is `false`, with `a+b` printing `0.30000000000000004`. Real prices come from variables, not constants, which is why the program above goes wrong.

</Callout>

### Step 4: a string is a window onto bytes

A Go `string` is two things: a pointer to some bytes, and a length. 16 bytes on a 64-bit machine, however long the text. The bytes can't be changed: `s[0] = 'X'` doesn't compile.

That has one consequence everyone trips over: **`len(s)` counts bytes, not characters.**

## Zero Values

*Stop 3 of 5.*

<ELI5
  concept="Zero values"
  analogy="Every new form arrives already filled in with sensible blanks, never with someone else's scribbles."
  role="reader"
>

In C, a variable you declare but don't set holds whatever was last in that memory. Reading it is a bug that might only show up on Tuesdays.

Go doesn't allow that. Every variable starts at its type's **zero value**: `0` for numbers, `""` for strings, `false` for booleans, and `nil` ("nothing yet") for pointers, slices, maps, channels, functions and interfaces.

</ELI5>

This is why an accumulator needs no setup:

```go
func cartTotalCents(prices []int) int {
	var total int // starts at exactly 0
	for _, p := range prices {
		total += p
	}
	return total
}
```

The Go proverb is **"make the zero value useful."** The standard library follows it: a `bytes.Buffer` or a `sync.Mutex` you just declared is ready to use, with no constructor. When you design your own types (ch2), aim for the same.

### Step 2: two traps that remain

**A nil map can be read but not written.**

<GoPlayground>

```go
package main

import "fmt"

func main() {
	var stock map[string]int
	fmt.Println(stock["hat"], len(stock), stock == nil) // reading a nil map is fine

	defer func() { fmt.Println("recovered:", recover()) }()
	stock["hat"] = 3 // writing panics
}
```

</GoPlayground>

```text
0 0 true
recovered: assignment to entry in nil map
```

Make maps before writing: `stock := make(map[string]int)` or `stock := map[string]int{}`. Slices don't have this trap, because `append` works on a nil slice.

**`:=` inside a block makes a new variable.** This one compiles, passes `go vet`, and loses an error:

<GoPlayground>

```go
package main

import (
	"errors"
	"fmt"
)

func lookup(code string) (int, error) {
	if code != "SAVE10" {
		return 0, errors.New("unknown coupon")
	}
	return 1000, nil
}

func main() {
	discount, err := 0, error(nil)
	if code := "BOGUS"; code != "" {
		discount, err := lookup(code) // := declares NEW discount and err, inside this block only
		if err != nil {
			fmt.Println("inside the block:", err)
		}
		fmt.Println("inner discount:", discount)
	}
	fmt.Println("after the block:", discount, err) // the outer ones never changed
}
```

</GoPlayground>

```text
inside the block: unknown coupon
inner discount: 0
after the block: 0 <nil>
```

The inner `discount, err :=` **shadows** the outer variables: same names, new variables, gone when the block ends. The fix is `=` instead of `:=`. When a value "doesn't stick", look for a stray `:=`.

<Callout kind="advanced" title="Go 1.26: new(value)">

`new(T)` allocates a zeroed `T` and gives you a pointer to it. Since Go 1.26 it also accepts a value: `p := new(1499)` is a `*int` pointing at 1499. Pointers come properly in ch3; this is just so the form doesn't surprise you.

</Callout>

**Recap.** Every variable starts at its zero value, so accumulators and many standard types work with no setup. Nil maps panic on write; `:=` in an inner block shadows instead of assigning.

## Control Flow

*Stop 4 of 5.*

### Step 1: `if`

No parentheses around the condition, braces always required, and an optional **init statement** before the condition:

```go
if total := cartTotalCents(prices); total >= freeShippingCents {
	fmt.Println("free shipping")
} else {
	fmt.Println("add", freeShippingCents-total, "cents for free shipping")
}
// total doesn't exist here: it was scoped to the if/else
```

**Reading tip:** `if A; B {` means "do A, then test B". You'll use it constantly as `if err := f(); err != nil {`.

### Step 2: `for` is the only loop

```go
for i := 0; i < 3; i++ { … } // init; condition; post
for i := range 3 { … }       // i = 0, 1, 2 (Go 1.22+)
for balance > 0 { … }        // condition only: Go's "while"
for { … }                    // forever, until break or return
for i, p := range prices { … } // each index and value of a slice
```

### Step 3: integer division, carefully

`7/2` is `3`: dividing integers drops the fraction. With negatives, Go **truncates toward zero**: `-7/2` is `-3` and `-7%2` is `-1` (the remainder keeps the sign of the left side). That's exactly why a naive money formatter prints a refund of -4299 cents as `$-42.-99` (the ch0 lab).

### Step 4: `switch`

A cleaner stack of `if`/`else`. Cases don't fall through to the next one (unlike C), and a `switch` with no value tests each case as a condition:

```go
switch {
case total == 0:
	fmt.Println("empty cart")
case total < freeShippingCents:
	fmt.Println("add more for free shipping")
default:
	fmt.Println("free shipping")
}
```

**Recap.** `if` has no parentheses and an optional init statement. `for` is the only loop: three-part, condition-only, infinite, or `range`. Integer division truncates toward zero. `switch` cases don't fall through.

## Functions

*Stop 5 of 5.*

### Step 1: reading a signature

```go
func applyCoupon(totalCents int, code string) (int, error) {
```

Left to right:

- `func` — this is a function.
- `applyCoupon` — its name (lowercase, so private to this package).
- `(totalCents int, code string)` — two **parameters**: `totalCents` of type `int` and `code` of type `string`. Name, then type, as with variables.
- `(int, error)` — it **returns two values**: an `int` and an `error`.

If consecutive parameters share a type you can write it once: `func add(a, b int) int`.

### Step 2: two return values, and errors as values

Go has no exceptions. A function that can fail returns its result **and** an error, and the caller checks the error immediately:

```go
func applyCoupon(totalCents int, code string) (int, error) {
	discount, ok := coupons[code]
	if !ok {
		return 0, fmt.Errorf("unknown coupon %q", code)
	}
	return totalCents - discount, nil // nil error: success
}

newTotal, err := applyCoupon(3997, "SUMMER")
if err != nil {
	return err // or handle it: but decide, here, now
}
```

<Define term="Errors as values">
In Go an error is an ordinary value of the built-in `error` interface type, returned like any other result. `nil` means success. Handling it is ordinary control flow (`if err != nil`), so every way a function can fail is visible where it's called. Ignoring it with `_` is allowed, and is how a bad coupon becomes a silently wrong total (this chapter's lab).
</Define>

<UnderTheHood title="Why no exceptions?">

Go's designers left out `try`/`catch` deliberately:

- **Visible control flow.** With exceptions, any call might jump out of the current function to a handler far away, skipping the rest. With returned errors, the only ways out of a function are the ones you can see: `return`, and (rarely) `panic`.
- **Failure is normal.** A timeout, a declined card or an unknown coupon isn't exceptional in a backend; it happens every minute. Treating it as a value makes you decide what to do about it where it happens.
- **Cheap.** Returning an error is returning one more value. No stack unwinding, no hidden cost.

The price is `if err != nil` everywhere. Part 2, Chapter 2 shows how to make errors carry context (`fmt.Errorf("…: %w", err)`) and how to inspect them (`errors.Is`, `errors.As`).

</UnderTheHood>

<Callout kind="note" title="Coming in ch2: named results and defer">

Go also lets you name return values and schedule clean-up with `defer`. Both have sharp edges worth a proper explanation, so they get one in Intermediate Go rather than half of one here.

</Callout>

<Exercise n={4} title="Apply a coupon, handle the error" level="hard">

Write `applyCoupon(totalCents int, code string) (int, error)`: `"SAVE10"` takes off 1000 cents; any other code is an error made with `fmt.Errorf`. Call it with a good and a bad code and handle both. Bonus: what should happen if the discount is larger than the total?

<Solution>

```go
package main

import "fmt"

func applyCoupon(totalCents int, code string) (int, error) {
	if code != "SAVE10" {
		return 0, fmt.Errorf("unknown coupon %q", code)
	}
	return max(totalCents-1000, 0), nil // never below zero
}

func main() {
	if newTotal, err := applyCoupon(3997, "SAVE10"); err != nil {
		fmt.Println("error:", err)
	} else {
		fmt.Println("new total:", newTotal) // new total: 2997
	}

	if _, err := applyCoupon(3997, "BOGUS"); err != nil {
		fmt.Println("error:", err) // error: unknown coupon "BOGUS"
	}
}
```

`%q` prints the code in quotes, which makes empty or space-padded codes obvious in logs. The bonus: without a floor, a $10 coupon on a $5 cart produces a negative total, which a payments system might treat as a refund. `max` (a built-in since Go 1.21) clamps it at zero; whether to reject such a coupon instead is a business decision worth asking about.

</Solution>

</Exercise>

<Recap>

- A program is `package main` with `func main()`. Imports bring in packages; **capitalised names are exported**. Unused imports and variables don't compile. Package variables and `init()` run before `main`.
- **Names come before types.** `:=` declares and infers (inside functions); `=` assigns. Go never converts number types implicitly.
- **Money is integer cents**: in `float64`, `1.10 + 2.20` is `3.3000000000000003` and `int(1.15*100)` is `114`.
- A **string** is a pointer and a length over read-only bytes; `len` counts bytes (`len("café")` is 5).
- Every variable starts at its **zero value**. Traps: writing to a **nil map** panics; `:=` in an inner block **shadows** instead of assigning.
- `if` takes an init statement; **`for` is the only loop**; integer division truncates toward zero; `switch` doesn't fall through.
- Functions return multiple values; failures come back as **`(result, error)`**, checked right away.

</Recap>
