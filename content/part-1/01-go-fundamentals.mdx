Here is the smallest real Go program that compiles and runs:

```go title="main.go"
package main

import "fmt"

func main() {
	subtotal := 1499 // a $14.99 item, in cents
	fmt.Println("subtotal in cents:", subtotal)
}
```

Three pieces, and every one of them is load-bearing. Let me break it down — one idea at a time.

- **`package main`** — every Go file belongs to a package. The package named `main` is special: it's the one Go turns into an executable program. No `main` package, no runnable binary.
- **`import "fmt"`** — you pull in other packages by importing them. `fmt` ("format") is the standard library's printing and formatting package. Go is famously strict here: import something you don't use and the compiler *refuses to build*. Not a warning. A hard error. Good. Sloppiness shouldn't compile.
- **`func main()`** — the entry point. When you run the program, the Go runtime calls `main` for you. It takes no arguments and returns nothing. Execution starts at its first line and walks downward.

<Define term="Package">
A **package** is Go's unit of code organisation — a folder of `.go` files that share a namespace. You import a package by its path (`"fmt"`, `"net/http"`) and call its exported names with a dot (`fmt.Println`). The special package named `main` is what Go compiles into a runnable binary; every other package is a library. Why it matters: packages are Go's only access-control boundary — a name starting with a capital letter is exported (visible to other packages); lowercase is private.
</Define>

This whole program compiles and runs on its own, so it gets a runner. Hit it.

<Callout kind="pro" title="The line that trips up beginners">

`subtotal := 1499` uses the **short variable declaration** `:=`. It does two things at once: it *declares* a new variable and *infers* its type from the value on the right. We'll dissect it in the next section — but notice you never wrote the word `int` anywhere. Go did that for you, and it was right.

### Under the Hood: there is no virtual machine

<UnderTheHood title="From source to a single static binary">

When you run `go build` (all examples in this course use **Go 1.26**, the current stable release as of early 2026), Go's compiler turns your source straight into **native machine code**, and the linker bundles it — *plus the Go runtime itself* (the scheduler, the garbage collector, the memory allocator) — into **one self-contained executable**. No interpreter. No JVM. No `node_modules`. No shared-library scavenger hunt on the production box.

That's why a Go service deploys as a single file you can `scp` to a server, or drop into a `FROM scratch` Docker image that's a few megabytes total. The "runtime" isn't a program you install — it's a library statically linked *inside your binary*. When the OS loads that binary, the runtime boots up first, then it calls your `main`.

Hold onto this picture. When we reach the scheduler and the garbage collector later in Part 2, we're talking about code that's *shipping inside every binary you build* — not some external daemon.

</UnderTheHood>

## Variables and Types

Go is **statically typed**: every variable has a type that's fixed at compile time. But Go is also smart enough to figure most of them out, so you rarely have to nag it.

There are several ways to make a variable. You should know all of them and reach for the shortest one that's clear:

```go
var count int                 // explicit type, no value → gets the zero value (0)
var price int = 1499          // explicit type and value (the type is redundant here)
var price = 1499              // type inferred from the value → int
price := 1499                 // short form: declare + infer, only inside functions
```

That last form, `:=`, is the one you'll use 90% of the time. The catch: `:=` only works **inside a function**. At package level (outside any function) you must use `var`.

<Define term="Variable / := short declaration">
A **variable** is a named slot that holds a value of a fixed type. The short form `price := 1499` is a **declare-and-assign**: Go creates the variable, figures out its type from the right-hand side (`int` here), and fills it in — all in one line. The longer `var price int = 1499` says the same thing with more ceremony. Use `:=` inside functions (where you declare things); use `var` at package level or when you want the zero value with no initial assignment.
</Define>

This is where the amateur reveals themselves. They learned C, so they write loops and declarations like they're being charged by the keystroke in the *wrong* direction:

<BeforeAfter
  badLabel="C-brain"
  goodLabel="Go-brain"
  bad={`var total int = 0
for i := 0; i < len(prices); i = i + 1 {
	total = total + prices[i]
}`}

for _, p := range prices {

Both compute the same cart total. One of them makes me wince. The right-hand version says exactly what it means — "for each price `p`, add it to the total" — and it can't go out of bounds, because there's no index to get wrong. Idiomatic Go isn't about cleverness. It's about leaving nothing for a tired engineer at 2 a.m. to misread.

Here are the basic types you'll actually use on the job. Memorize the grid; I'll quiz you.

<ConceptGrid cols={3}>
  <ConceptCard label="int / int64">Whole numbers. `int` is the default machine-word integer — 64 bits on most server and laptop targets, but 32 bits on some platforms. Use `int64` when stored money or counters need a fixed width.</ConceptCard>
  <ConceptCard label="string">Immutable bytes commonly used for UTF-8 text. `"checkout"`. You cannot change a byte in place — more on why in a moment.</ConceptCard>
  <ConceptCard label="bool">`true` or `false`. No, `0` is not false. This isn't C. Don't even try it.</ConceptCard>
  <ConceptCard label="float64">Decimals, like `3.14`. Great for physics and graphics. A *felony* for money. We'll cover why in Part 3.</ConceptCard>
  <ConceptCard label="byte / rune">A `byte` is an 8-bit value (an alias for `uint8`); a `rune` is a Unicode code point (`int32`). They matter the instant you touch strings seriously.</ConceptCard>
  <ConceptCard label="uint">An unsigned integer — can't go negative. Tempting for "a count can't be negative," but it bites you on subtraction. Reach for `int` by default.</ConceptCard>
  <Gotcha>Never store money in a `float64`. `0.1 + 0.2` is not `0.3` in binary floating point — it's `0.30000000000000004`. Spread that across a million transactions and you've invented free money (or destroyed real money). Integer cents. Always.</Gotcha>
</ConceptGrid>

<Define term="Integer cents (the money rule)" since="Numbers, Overflow & Monetary Arithmetic (Part 3)">
**Never store money as a decimal.** Store it as a whole number of the smallest currency unit — cents for USD, pence for GBP, and so on. `$14.99` is stored as `1499` in an integer type such as `int64`. You display it as dollars only when printing: `fmt.Sprintf("$%d.%02d", cents/100, cents%100)`. Why: binary floating-point cannot represent most decimal fractions exactly, so `float64` arithmetic on prices silently gains or loses fractions of a cent — and those errors compound. Integer arithmetic is exact. This is not a preference; it is a rule every production payments system follows.
</Define>

### Under the Hood: a string is a window, not a buffer

<UnderTheHood title="What a string really is">

A Go `string` is a tiny, **read-only** two-word header: a pointer to some bytes, and a length. That's it. The bytes are **immutable** — once a string exists, you cannot reach in and change byte 3. Try `s[0] = 'X'` and the compiler stops you cold. Strings are often UTF-8 text, and string literals in source usually are, but a string can contain arbitrary bytes.

This has a consequence beginners trip over constantly: **`len(s)` returns the number of *bytes*, not characters.**

```go
s := "café"
fmt.Println(len(s)) // 5, not 4 — the 'é' is two bytes in UTF-8
```

The string "café" is four *characters* but five *bytes*, because `é` is encoded as two bytes in UTF-8. If you want to count characters (runes), you range over the string or use `utf8.RuneCountInString`. Why does Go do it this way? Because making the byte length cheap and the string immutable means strings can be sliced and passed around cheaply. Speed and safety, paid for with one sharp edge you now know about.

</UnderTheHood>

## Zero Values

Now the feature that separates Go from the languages that haunt your nightmares.

<Define term="Zero value">
In Go, every type has a **zero value** — the value a variable gets when you declare it without assigning anything. Numbers get `0`, strings get `""`, booleans get `false`, and pointer/slice/map types get `nil`. There is no "undefined" or "garbage" like in C. Why it matters: you can declare an accumulator with `var total int` and immediately start adding to it, because Go guarantees it starts at exactly `0`. Well-designed Go types are built so their zero value is already useful — you declare and go.
</Define>

In Go, **a variable declared without a value is never garbage and never undefined.** It gets its type's **zero value** — a sensible, defined default. This is a deliberate, load-bearing design decision, and it shows up everywhere in idiomatic Go.

<ConceptGrid cols={3}>
  <ConceptCard label="numbers → 0">`int`, `float64`, `byte`, and friends all start at `0`.</ConceptCard>
  <ConceptCard label={'string → ""'}>The empty string. Length 0. Never `nil`.</ConceptCard>
  <ConceptCard label="bool → false">Every freshly declared bool is `false`.</ConceptCard>
  <ConceptCard label="pointers, slices, maps → nil">Reference-like types start as `nil` — the typed "nothing." (We'll meet these properly next chapter.)</ConceptCard>
</ConceptGrid>

<Callout kind="advanced" title="Go 1.26: new() now takes an initial value">

Pointers — and the `new` builtin that creates them — belong to a later chapter. But here's a small Go 1.26 upgrade worth knowing exists: `new` now accepts an optional initializer expression, so you can write `p := new(1499)` to get a `*int` pointing directly at `1499`, instead of allocating and then assigning in two steps. You don't need this yet, but notice how it rhymes with the zero-value philosophy: the old `new(int)` gave you a zeroed `*int`, and the new form just lets you name a better starting value. Come back to this when we cover pointers and data semantics.

</Callout>

Why should you care? Because it means you can declare your accumulator and *just start using it*:

```go
func cartTotalCents(prices []int) int {
	var total int // zero value is 0 — exactly the right starting point
	for _, p := range prices {
		total += p
	}
	return total
}
```

No `total = 0` ceremony. No "is this initialized?" dance. The zero value is the right value, so the code is shorter *and* safer. The Go proverb is: **"Make the zero value useful."** Great Go types are designed so that a freshly declared one already works. You'll feel the full weight of this when we design structs.

<Gotcha>

There's a twin trap. `:=` always declares a **new** variable. Inside a nested block, `:=` can accidentally create a *second* variable that **shadows** the outer one — your assignment goes into the shadow and vanishes when the block ends. The compiler won't always save you. When a value mysteriously "doesn't stick," suspect a stray `:=` where you meant `=`.

</Gotcha>

## Control Flow

Go's control flow is aggressively minimal, and I mean that as the highest compliment. Fewer constructs, fewer ways to be wrong.

**`if`** needs no parentheses, always needs curly braces, and can run a little **init statement** first — perfect for the error-handling pattern you'll write ten thousand times:

```go
if total := cartTotalCents(prices); total > freeShippingThreshold {
	fmt.Println("free shipping unlocked")
}
// `total` only exists inside the if/else — scoped tight, the way it should be
```

**`for`** is the *only* loop in Go. There is no `while`. There is no `do-while`. There's just `for`, wearing different outfits:

```go
for i := 0; i < 3; i++ { }   // classic three-part loop
for online {              }   // condition-only — this is Go's "while"
for {                     }   // no condition — loops forever (until break/return)
for i, p := range prices  { } // range — over slices, maps, strings, channels
```

**`switch`** is Go's clean answer to a stack of `if/else`. No fall-through by default (a feature — you almost never want C's accidental fall-through), and cases can be any value, not just integers:

```go
switch {
case total == 0:
	fmt.Println("empty cart")
case total < freeShippingThreshold:
	fmt.Println("add more for free shipping")
default:
	fmt.Println("free shipping")
}
```

## Functions

A function packages logic behind a name. The signature is read left to right: name, parameters with their types, then the return type(s).

```go
func cartTotalCents(prices []int) int {
	total := 0
	for _, p := range prices {
		total += p
	}
	return total
}
```

`prices []int` is a parameter named `prices` of type "slice of int." The lone `int` after the parentheses is the return type. Simple. Now the part that makes people fall in love with Go:

<Define term="Function / multiple return values">
A **function** packages a reusable piece of logic behind a name. In Go the signature reads left to right: `func name(param type) returnType`. The standout feature is that Go functions can **return more than one value** — the convention is always `(result, error)`. This is how Go handles errors: no exceptions, no thrown values, no hidden control flow. The caller receives both values and is forced to acknowledge the error right there. If you ignore it with `_`, you're making a deliberate, visible choice — not accidentally swallowing a failure.
</Define>

**Functions can return multiple values.** This is how Go does errors — no exceptions, no hidden control flow. A function returns its result *and* an error, side by side, and you deal with the error right there:

```go
func applyCoupon(total int, code string) (int, error) {
	discount, ok := coupons[code]
	if !ok {
		return 0, fmt.Errorf("unknown coupon %q", code)
	}
	return total - discount, nil
}

// at the call site, you handle the error immediately — every time:
newTotal, err := applyCoupon(3997, "SUMMER")
if err != nil {
	// deal with it now; do not pretend it can't happen
	return err
}
```

That `if err != nil` check is the heartbeat of every Go program ever written. It looks repetitive. It *is* repetitive. And it's why Go services don't fall over from some exception thrown nine stack frames away that nobody caught. We'll go deep — *very* deep — on errors next chapter. For now, just internalize the shape: **result, error, check.**

<Callout kind="note" title="Named returns and `defer` (a teaser)">

Go also lets you *name* your return values, and run cleanup with `defer` that fires when the function exits. They're genuinely useful and have a few sharp edges, so I'm not going to half-explain them here and let you build bad habits. They get the real treatment in **Intermediate Go** and again in the **context** chapter. Out of scope here — on purpose, not by accident.

</Callout>

<Exercise n={3} title="Free shipping?" level="medium">

Write `qualifiesForFreeShipping(totalCents int) bool` that returns `true` when the total is at least `5000` cents ($50.00). Then call it from `main` and print the result for a `3997`-cent cart.

<Solution>

```go
package main

import "fmt"

func qualifiesForFreeShipping(totalCents int) bool {
	return totalCents >= 5000
}

func main() {
	fmt.Println(qualifiesForFreeShipping(3997)) // false
}
```

A boolean expression like `totalCents >= 5000` *is* a `bool` — just return it directly. No `if x { return true } else { return false }` nonsense; that's the kind of thing that makes me reach for the red pen.

</Solution>

</Exercise>

<Exercise n={4} title="Apply a coupon, handle the error" level="hard">

Write `applyCoupon(totalCents int, code string) (int, error)`. It knows one coupon: `"SAVE10"` takes `1000` cents off. Any other code returns an error built with `fmt.Errorf`. In `main`, call it once with a good code and once with a bad one, and handle both results with the `result, err` pattern.

<Solution>

```go
package main

import (
	"fmt"
)

func applyCoupon(totalCents int, code string) (int, error) {
	if code != "SAVE10" {
		return 0, fmt.Errorf("unknown coupon %q", code)
	}
	return totalCents - 1000, nil
}

func main() {
	if newTotal, err := applyCoupon(3997, "SAVE10"); err != nil {
		fmt.Println("error:", err)
	} else {
		fmt.Println("new total:", newTotal) // 2997
	}

	if _, err := applyCoupon(3997, "BOGUS"); err != nil {
		fmt.Println("error:", err) // error: unknown coupon "BOGUS"
	}
}
```

Note the `if init; condition` form scoping `newTotal` and `err` to exactly where they're used, and `%q` quoting the bad code in the message. That's not showing off — that's just how a professional writes it.

</Solution>

</Exercise>

<Recap>

You now own the bedrock:

- Every program is a **`package`**; the **`main`** package with a `main()` func is what runs. Go compiles to **one static binary** with the runtime baked in.
- Variables are **statically typed** but usually **inferred** with `:=`. Reach for the short form inside functions; use `var` at package level.
- Every type has a **useful zero value** — `0`, `""`, `false`, `nil` — so you declare and go. Watch out for `:=` **shadowing**.
- **`for`** is the only loop. `if` takes an init statement and always needs braces. `switch` doesn't fall through.
- Functions **return multiple values**, and that's how Go does errors: **result, error, check** — every single time.
- And the rule we'll repeat until you say it in your sleep: **money is integer cents, never a float.**
