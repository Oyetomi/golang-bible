## Reflection

Let me set the scene, because we never learn dark arts in a vacuum.

You're building a generic JSON serializer for your fintech service. Not `encoding/json` — *your own*, so you understand how the standard library works under the hood. Your `Serialize(v interface{}) string` function needs to handle any type thrown at it: `Payment`, `Account`, `TransferRequest` — structs you've never seen. At compile time, you have *no idea* what fields they'll have.

That's the problem reflection solves: **introspecting and manipulating types and values at runtime**, when you cannot know the shape at compile time.

### The Reflect Laws

Before any code, you need the three laws of reflection tattooed on your brain. Rob Pike wrote them. I'm endorsing them personally, which makes them twice as authoritative.

**Law 1:** Reflection goes from interface value to reflection object.  
**Law 2:** Reflection goes from reflection object back to interface value.  
**Law 3:** To modify a reflection object, the value must be settable (addressable).

That's it. Three laws. Everything else is a consequence.

### reflect.Type and reflect.Value

<Define term="Reflection (reflect.Type / reflect.Value)" since="This chapter">
**Reflection** is the ability to inspect and manipulate a program's own types and values at runtime — without knowing their shapes at compile time. The `reflect` package exposes this through two types: **`reflect.Type`** describes the *shape* of a type (its kind, name, fields, and methods), and **`reflect.Value`** holds an actual runtime value that you can read or write through. Why it matters: reflection is how `encoding/json`, ORMs, and struct validators handle *any* user-defined type without requiring glue code per struct. The cost: every reflect operation bypasses the compiler's type-safety checks, so mistakes surface as runtime panics rather than compile errors.
</Define>

The `reflect` package gives you two core types. **`reflect.Type`** describes the *shape* of a type — its kind, name, fields, methods. **`reflect.Value`** holds an actual *value* at runtime and lets you read or write it.

You get them from a concrete value via `reflect.TypeOf` and `reflect.ValueOf`:

```go
package main

import (
	"fmt"
	"reflect"
)

// Payment represents an outbound payment in our fintech service.
type Payment struct {
	ID     string `json:"id"`
	Amount int64  `json:"amount_cents"`
	Status string `json:"status"`
}

func main() {
	p := Payment{ID: "pay_001", Amount: 9999, Status: "pending"}

	t := reflect.TypeOf(p)   // reflect.Type — the shape
	v := reflect.ValueOf(p)  // reflect.Value — the data

	fmt.Println("Type name:", t.Name())         // Payment
	fmt.Println("Kind:", t.Kind())              // struct
	fmt.Println("Num fields:", t.NumField())    // 3

	for i := 0; i < t.NumField(); i++ {
		field := t.Field(i)             // reflect.StructField — the shape of field i
		value := v.Field(i)             // reflect.Value — the actual value of field i
		tag := field.Tag.Get("json")    // read the struct tag
		fmt.Printf("  %-12s %-8s tag=%q  value=%v\n",
			field.Name, field.Type.Kind(), tag, value)
	}
}
```

### Struct Tags

<Define term="Struct Tag">
A **struct tag** is the raw string literal that appears after a field declaration in backticks — e.g. `` `json:"amount_cents" db:"amount"` ``. The compiler ignores it entirely; it is stored verbatim in the type's runtime metadata. Libraries that use reflection (such as `encoding/json`, GORM, and validator) read these tags at runtime via `reflect.StructTag.Get("key")` to customize their behavior per field — mapping JSON key names, column names, or validation rules — without you writing any glue code per struct.
</Define>

Struct tags are those backtick strings after a field declaration: `` `json:"amount_cents"` ``. They're invisible to the compiler — they live in the type's metadata, readable only at runtime via reflection. They're how `encoding/json`, `gorm`, `validate`, and a dozen other libraries customize behavior per-field without you writing glue code.

The format is a key:"value" pair. Multiple tags sit space-separated in the same string: `` `json:"amount_cents" db:"amount"` ``. `reflect.StructTag.Get("json")` returns `"amount_cents"`. The `reflect` package handles the parsing.

<Callout kind="note" title="Struct tag format — the spec is strict">

The convention is `key:"value"`. The `reflect` package's `Tag.Lookup` and `Tag.Get` methods understand *exactly* this format. Anything outside it (`key=value`, missing quotes) silently returns an empty string — `go vet` can catch malformed tags, so always run it.

</Callout>

### A Real-World Scenario: Struct-to-Map via Reflection

Here's the kind of function that actually justifies reflection — a generic struct serializer that walks any struct and returns a `map[string]any`, using JSON tags as keys:

```go
package main

import (
	"fmt"
	"reflect"
)

// structToMap converts any exported-field struct to map[string]any.
// It uses the "json" struct tag as the map key; falls back to field name.
// Non-addressable (value) reflect.Values are read-only — that's fine here
// because we're only reading.
func structToMap(v any) map[string]any {
	rv := reflect.ValueOf(v)
	rt := reflect.TypeOf(v)

	// Dereference a pointer if needed — callers may pass &Payment{} or Payment{}
	if rv.Kind() == reflect.Pointer {
		rv = rv.Elem()
		rt = rt.Elem()
	}

	if rv.Kind() != reflect.Struct {
		panic("structToMap: expected a struct or *struct")
	}

	out := make(map[string]any, rt.NumField())
	for i := 0; i < rt.NumField(); i++ {
		sf := rt.Field(i)
		// Skip unexported fields — CanInterface returns false for them.
		if !sf.IsExported() {
			continue
		}
		key := sf.Tag.Get("json")
		if key == "" || key == "-" {
			key = sf.Name // fall back to field name if no tag
		}
		out[key] = rv.Field(i).Interface() // Interface() boxes the value back to any
	}
	return out
}

type TransferRequest struct {
	FromAccount string `json:"from_account"`
	ToAccount   string `json:"to_account"`
	AmountCents int64  `json:"amount_cents"`
	Reference   string `json:"reference"`
	internal    string // unexported — skipped
}

func main() {
	req := TransferRequest{
		FromAccount: "acct_A",
		ToAccount:   "acct_B",
		AmountCents: 50000,
		Reference:   "invoice-99",
		internal:    "secret",
	}

	m := structToMap(req)
	for k, val := range m {
		fmt.Printf("  %s: %v\n", k, val)
	}
}
```

<Callout kind="note" title="Go 1.26: reflect iterator methods — range over fields directly">

The `for i := 0; i < rt.NumField(); i++` loop above is the classic form — clear, but boilerplate. Go 1.26 adds iterator methods (`Type.Fields()`, `Value.Fields()`, `Type.Methods()`, `Value.Methods()`) that return rangeable iterators compatible with the `iter.Seq` pattern from Go 1.23:

```go
// Go 1.26+: range directly over struct field descriptors — no index counter.
for sf := range rt.Fields() {
    if !sf.IsExported() {
        continue
    }
    key := sf.Tag.Get("json")
    out[key] = rv.Field(sf.Index[0]).Interface()
}
```

`sf.Index[0]` is the field's position in the struct (a `[]int` to support embedded fields; `[0]` is the top-level index). The classic `for i` loop still compiles; the iterator form is preferred in new Go 1.26+ code for readability. The examples in this chapter use the classic form so they run on older toolchains without modification.

</Callout>

<Callout kind="pro" title="Go 1.25: reflect.TypeAssert[T] — zero-allocation type extraction">

Before Go 1.25, extracting a typed value from a `reflect.Value` meant boxing it back through an interface and then asserting:

```go
// Old round-trip: boxes to any, then asserts — may allocate unnecessarily.
amount := v.Field(1).Interface().(int64)
```

Go 1.25 adds `reflect.TypeAssert[T](v reflect.Value) (T, bool)`, which performs the same conversion as `v.Interface().(T)` while avoiding unnecessary allocations:

```go
// Go 1.25+: direct extraction, no interface round-trip.
amount, ok := reflect.TypeAssert[int64](v.Field(1))
```

This matters in hot paths — serializers and ORMs that extract scalar fields from thousands of structs per second. The old form still works; use `TypeAssert[T]` when allocation pressure matters and the type is known at the call site.

</Callout>

<UnderTheHood title="How the interface (type, value) representation makes reflection possible">

Every Go interface value is a **two-word header** in memory:

```
┌──────────────┬──────────────┐
│  type pointer│  data pointer│
│  (itab/type) │  (or value)  │
└──────────────┘──────────────┘
```

The **type pointer** points to a runtime type descriptor (`*_type` in the runtime source) that holds the type's name, kind, size, and — for structs — a list of field descriptors including their names, types, offsets, and tag strings. This descriptor is generated by the compiler and baked into your binary.

When you call `reflect.TypeOf(x)`, the function receives `x` as an `interface{}`. It reads the type pointer from that header and wraps it in a `reflect.Type` value. When you call `reflect.ValueOf(x)`, it reads *both* words and wraps them in a `reflect.Value`.

This means:

- **Type metadata is always there**, even in a non-reflect program — it's what makes type assertions (`x.(T)`) and type switches work.
- **Reflection doesn't add runtime overhead at import time** — it uses metadata the compiler already generates.
- **The cost comes from the reflect operations themselves**: they go through interface calls, bounds-check pointer arithmetic, and runtime dispatch that the compiler cannot inline or optimize away. A hand-written struct access is a single load instruction; `reflect.Value.Field(i).Interface()` is dozens. (As of Go 1.26, the reflect package has been progressively optimized, but it will never match a direct field access.)

The `encoding/json` package pays this cost — it traverses your struct *once* at first use, caches the result in a `sync.Map`, and replays the cached plan on every subsequent encode. That caching pattern is why the first call is slow and later calls aren't terrible.

</UnderTheHood>

### When Reflection Is Justified — and When It's a Code Smell

<ConceptGrid cols={2}>
  <ConceptCard label="Justified: serializers">Encoding/decoding (JSON, XML, YAML, protobuf), ORMs mapping SQL rows to structs, struct validators — any library that must handle *unknown* user-defined types by convention, not by interface. The cost is paid once; users get a zero-ceremony API.</ConceptCard>
  <ConceptCard label="Justified: code generation inputs">Reflection-based tools that inspect types to *generate* fast code (like `sqlc` or `go generate` helpers). You pay the reflection cost at dev time, not at runtime.</ConceptCard>
  <ConceptCard label="Code smell: avoided interfaces">If you're using `reflect.TypeOf(x).Name()` to dispatch on type names at runtime, you almost certainly want a type switch or a small interface instead. That's what they're for.</ConceptCard>
  <ConceptCard label="Code smell: general-purpose utilities">A `Map(slice, fn)` that reflects over the slice to apply `fn` is worse than a generic function (Go 1.18+) in every way: slower, no compile-time safety, more lines.</ConceptCard>
  <Gotcha>Reflection defeats the compiler's type-safety guarantees. `v.Field(5)` on a three-field struct panics at runtime — not a compile error. `v.Field(i).SetInt(42)` panics if the field isn't settable (isn't addressable via a pointer). Every reflect operation that can panic *will* panic if you pass the wrong kind. Recover from panics in library code, not in application code. And test every reflect path with every Kind you promise to handle.</Gotcha>
</ConceptGrid>

## Profiling Toolchain

Let me describe a real incident. A payment API endpoint that processes incoming webhooks — it's fast in staging, brutal in production at 500 req/s. The on-call engineer spends two hours guessing: "maybe it's the DB connection pool," "maybe it's the JSON decoder," "maybe it's the mutex." Two hours of guessing.

That's not how I operate, and it's not how *you're* going to operate.

**You measure first. Always.** Optimization without a profiler is superstition.

<Define term="Profiling (pprof, CPU vs. heap)" since="Performance Engineering (Part 2, Chapter 10)">
**Profiling** is the act of measuring where a running program spends its time or memory, so you fix the actual bottleneck rather than guessing. Go's built-in profiler (`runtime/pprof`, `net/http/pprof`) supports two profiles you'll reach for first: a **CPU profile** samples the call stack ~100 times per second to rank which functions burn the most CPU; a **heap profile** records allocation call sites to show which code paths hammer the garbage collector. Both are read with `go tool pprof`. Why it matters: a Meridian webhook handler that's fast in staging can crater at 500 req/s in production — and the only way to know *why* is a profile, not a guess. The deep dive — flame graphs, the execution tracer, and GC pressure analysis — is **Performance Engineering (Part 2, Chapter 10)**.
</Define>

### The Two Profiles You'll Use Most

Go ships a full profiling toolchain in the standard library. No third-party dependencies. Two profiles matter most at this stage:

- **CPU profile** — where is time being spent? Which functions are on the call stack when the program is burning CPU cycles?
- **Heap profile** — where is memory being allocated? Which call sites are hammering the garbage collector?

(Block and mutex profiles exist too; they're covered in depth in **Part 2, Chapter 8 — Performance Engineering**, along with the execution tracer. We'll link forward where it matters.)

### runtime/pprof — The Foundation

`runtime/pprof` lets you write profiles to any `io.Writer` from code you control:

```go
package main

import (
	"encoding/json"
	"log"
	"net/http"
	"os"
	"runtime/pprof"
	"time"
)

// simulateWork mimics a slow JSON-heavy webhook handler.
// We'll profile this to find where the time goes.
func processWebhooks(count int) {
	type Webhook struct {
		ID      string            `json:"id"`
		Payload map[string]string `json:"payload"`
	}

	for i := 0; i < count; i++ {
		wh := Webhook{
			ID:      "wh_" + string(rune('A'+i%26)),
			Payload: map[string]string{"event": "payment.completed", "amount": "9999"},
		}
		// Allocates a new []byte every call — a classic hot allocation.
		_, err := json.Marshal(wh)
		if err != nil {
			log.Println("marshal error:", err)
		}
	}
}

func main() {
	// ── CPU profile ──────────────────────────────────────────
	cpuFile, err := os.Create("cpu.prof")
	if err != nil {
		log.Fatal("could not create cpu.prof:", err)
	}
	defer cpuFile.Close()

	if err := pprof.StartCPUProfile(cpuFile); err != nil {
```

## unsafe

We've reached the deep end. No floaties.

`unsafe` is a built-in package that escapes Go's type system. Not bends it. *Escapes* it. The compiler treats `import "unsafe"` specially — it doesn't even appear in your `go.mod`, because it's part of the language itself. And it earns that special status: it lets you do things no other package can.

Three things specifically: **`unsafe.Pointer`**, **`uintptr`**, and the size/layout intrinsics.

<Define term="unsafe.Pointer">
**`unsafe.Pointer`** is a special pointer type that can hold the address of any value and can be freely converted to *any* other pointer type. That is exactly what makes it unsafe: you can tell the compiler a pointer points to a `float32` when it actually points to a `uint32`, or walk to an arbitrary memory offset, and the compiler will believe you. The garbage collector *does* trace `unsafe.Pointer` as a live reference — so the GC will not collect the object beneath it — but it provides zero type-safety guarantees. The Go spec defines six legal conversion patterns; breaking them produces silent memory corruption. Always run `go vet` (it enforces these patterns via the `unsafeptr` analysis pass).
</Define>

<Define term="uintptr (and why it is not a pointer)">
**`uintptr`** is an unsigned integer type that is wide enough to hold a memory address — but it is **not** a pointer. The garbage collector does not trace through `uintptr` values. If the only thing holding a memory address is a `uintptr` variable, the object at that address is invisible to the GC and can be collected or relocated at any moment. The only safe use of `uintptr` in an `unsafe.Pointer` chain is as part of a single expression — never stored to a variable across a GC-safe point. In short: `unsafe.Pointer` is a safe-to-hold reference (the GC sees it); `uintptr` is just a number (the GC ignores it). Mixing them carelessly is how you get a dangling pointer with no compiler warning.
</Define>

<Callout kind="warn" title="These tools defeat the compiler's guarantees">

`unsafe` operations are not checked for type safety at compile time. The garbage collector will not protect you from invalid pointer arithmetic. `go vet` enforces the `unsafe.Pointer` conversion rules — use it, always. These tools should appear in your codebase *only* with profiler evidence that the safe alternative is genuinely too slow, or when implementing something the safe language simply cannot express (like a zero-copy string↔[]byte conversion).

</Callout>

### The Three Intrinsics: Sizeof, Offsetof, Alignof

These are compile-time constants — the compiler computes them, not your running program:

```go
package main

import (
	"fmt"
	"unsafe"
)

// AccountBad is a struct we might pack into a shared-memory ring buffer.
// Field ordering matters for padding — let's see why.
type AccountBad struct {
	Active  bool  // 1 byte, then 7 bytes of padding
	Balance int64 // 8 bytes — must be 8-byte aligned
	Code    byte  // 1 byte, then 7 bytes of padding
}
// Total: 1+7+8+1+7 = 24 bytes

type AccountGood struct {
	Balance int64 // 8 bytes — no padding needed at start
	Code    byte  // 1 byte
	Active  bool  // 1 byte, then 6 bytes of padding
}
// Total: 8+1+1+6 = 16 bytes — same data, 33% smaller

func main() {
	fmt.Printf("AccountBad:  size=%d  align=%d\n",
		unsafe.Sizeof(AccountBad{}), unsafe.Alignof(AccountBad{}))
	fmt.Printf("AccountGood: size=%d  align=%d\n",
		unsafe.Sizeof(AccountGood{}), unsafe.Alignof(AccountGood{}))

	// Offsetof tells you exactly where in the struct each field starts.
	fmt.Printf("AccountGood.Balance offset: %d\n", unsafe.Offsetof(AccountGood{}.Balance))
	fmt.Printf("AccountGood.Code    offset: %d\n", unsafe.Offsetof(AccountGood{}.Code))
	fmt.Printf("AccountGood.Active  offset: %d\n", unsafe.Offsetof(AccountGood{}.Active))
}
```

### unsafe.Pointer and the Conversion Rules

`unsafe.Pointer` is a pointer type that can hold the address of any value — and *can be converted to any pointer type*. This is what makes it unsafe: you can lie to the type system about what a pointer points to.

The Go spec defines **six legal conversion patterns** for `unsafe.Pointer`. Breaking them gives you memory corruption; the GC may move or collect the thing you're pointing at. `go vet` enforces these rules via the `go/analysis/passes/unsafeptr` pass (introduced in Go 1.22, still active and expanded in Go 1.26).

Here's the most common legitimate pattern — converting between two pointer types that genuinely share the same memory layout:

```go
package main

import (
	"fmt"
	"unsafe"
)

// int32Header has the same memory layout as a float32 —
// both are 4 bytes, same alignment. This lets us inspect
// a float32's raw IEEE 754 bits without any copying.
func float32Bits(f float32) uint32 {
	// Pattern: *T1 → unsafe.Pointer → *T2
	// Legal only when T1 and T2 share the same memory layout.
	return *(*uint32)(unsafe.Pointer(&f))
}

func main() {
	f := float32(1.5)
	bits := float32Bits(f)
	fmt.Printf("%.1f → bits: 0x%08X\n", f, bits)
	// IEEE 754: sign=0, exp=127, mantissa=0x400000 → 0x3FC00000
}
```

### uintptr Is Not a Pointer — and the GC Will Not Save You

<UnderTheHood title="Why uintptr is not a pointer (the GC can move objects underneath it)">

`uintptr` is just an integer wide enough to hold an address. The garbage collector does **not** treat it as a live reference.

Go's GC is a **concurrent tri-color mark-sweep collector** (non-moving through Go 1.26, though the `unsafe.Pointer` conversion rules are written to be safe even against a future moving collector — and `go vet` enforces them accordingly). More practically right now: the GC may *collect* an object if no pointer-typed variable holds a reference to it.

```go
// WRONG — do not do this.
u := uintptr(unsafe.Pointer(&myStruct))
// ...some other code...
p := (*MyStruct)(unsafe.Pointer(u)) // ILLEGAL: u is not a GC root.
// myStruct could have been collected between line 1 and here.
```

The moment `u` is the only thing holding the address and it's a `uintptr`, the GC considers `myStruct` unreachable. It is free to reclaim or relocate it. Your `u` becomes a dangling integer pointing at garbage.

**The rule:** `uintptr` must never be stored across a GC-safe point. The only legal use of `uintptr` in an `unsafe.Pointer` chain is as part of a single expression — never stored to a variable between the `unsafe.Pointer` conversion and its use. `go vet` catches the most obvious violations (since Go 1.22, and still enforced in Go 1.26).

```go
// CORRECT — all in one expression, no intermediate uintptr variable.
field := (*FieldType)(unsafe.Pointer(
    uintptr(unsafe.Pointer(&myStruct)) + unsafe.Offsetof(myStruct.Field),
))
```

Even this pattern is risky. Prefer `unsafe.Offsetof` directly and only reach for pointer arithmetic when you have profiler evidence that a safe alternative is the bottleneck.

</UnderTheHood>

### The Zero-Copy []byte → string Trick

Here's a real hot-path optimization you'll see in the standard library and high-performance Go code: converting `[]byte` to `string` without copying the bytes.

Normally, `string(b)` where `b` is a `[]byte` allocates a new backing array and copies every byte. For a hot path — say, a JSON parser calling `string(buf)` millions of times — that's a lot of GC pressure.

The `unsafe` version:

```go
package main

import (
	"fmt"
	"unsafe"
)

// bytesToString converts a []byte to string without allocating.
// DANGER: the returned string shares the []byte's backing array.
// If the []byte is modified after this call, the string changes too —
// silently, with no compiler protection. Only use when:
//   1. You have profiler evidence the allocation matters.
//   2. You guarantee the []byte will not be mutated for the string's lifetime.
//   3. The string does not escape the current scope (e.g., passed to fmt.Println is fine;
//      stored in a map that outlives the []byte is a bug waiting to happen).
func bytesToString(b []byte) string {
	if len(b) == 0 {
		return ""
	}
	// A string header is (ptr, len). A slice header is (ptr, len, cap).
	// They share the same first two fields, so we can reinterpret safely
	// as long as the underlying bytes live at least as long as the string.
	return unsafe.String(&b[0], len(b))
	// Go 1.20+ ships unsafe.String and unsafe.SliceData for exactly this pattern.
	// Prefer them over the older *(*string)(unsafe.Pointer(&b)) hack.
}

func main() {
	buf := []byte("payment_completed")
	s := bytesToString(buf)
	fmt.Println(s)
	fmt.Println("allocated:", false) // no allocation — trust the profiler to confirm

	// Mutation danger — DO NOT DO THIS IN PRODUCTION:
	buf[0] = 'X'
	fmt.Println("mutated s:", s) // s is now "Xayment_completed" — UB in disguise
}
```

### Where the Standard Library Uses unsafe

The stdlib doesn't use `unsafe` because it's sloppy — it uses it because it's measured, has invariants it can guarantee, and controls both sides of the data:

- **`strings.Builder`** uses it to convert its internal `[]byte` to `string` without copying when you call `.String()` — it has the invariant that it never hands out the buffer.
- **`sync.Map`** uses it for atomic pointer operations in its internal slots.
- **`reflect`** uses it extensively to reach into memory at computed offsets.
- **`runtime`** uses it for everything — it *is* the thing that owns memory.

You are not the runtime. Don't use `unsafe` because it feels powerful. Use it when the profiler shows the allocation or the copy is genuinely the bottleneck, you understand the ownership invariant, and you've written tests that will catch the UB if the invariant breaks.

<Callout kind="advanced" title="Go 1.26 (experimental): runtime/secret — secure memory erasure">

Go 1.26 ships an experimental `runtime/secret` package for securely erasing cryptographic temporaries from memory. The problem it solves: a plain `clear(slice)` or zeroing a `[]byte` can be elided by the compiler as a dead-store if the variable isn't used afterward. `runtime/secret` provides wrappers that are guaranteed not to be optimized away — the same guarantee that C's `explicit_bzero` or Rust's `zeroize` provide.

This belongs in a narrower category than general `unsafe` use: cryptographic key material, TLS session secrets, and plaintext PINs/passwords. The deep coverage is in the **Security for Financial Systems** chapter (Part 3, Chapter 10). If you're erasing sensitive buffers today, `runtime/secret` is worth tracking — but it's experimental in 1.26, so treat it as preview API.

</Callout>

```go
type Payment struct {
	ID     string
	Amount int64
}

func setField(v any, name string, value any) {
	rv := reflect.ValueOf(v)
	if rv.Kind() != reflect.Pointer || rv.Elem().Kind() != reflect.Struct {
		panic("setField: v must be a pointer to a struct")
	}
	rv = rv.Elem() // dereference the pointer — now we can set fields

	fv := rv.FieldByName(name)
	if !fv.IsValid() {
		panic(fmt.Sprintf("setField: no field %q", name))
	}
	if !fv.CanSet() {
		panic(fmt.Sprintf("setField: field %q is not settable (unexported?)", name))
	}
	fv.Set(reflect.ValueOf(value))
}

func main() {
	p := &Payment{ID: "p1", Amount: 5000}
	setField(p, "Amount", int64(12000))
	fmt.Printf("%+v\n", *p) // {ID:p1 Amount:12000}
}
```

The key insight: you must pass a *pointer* (`&p`) so the reflected value is addressable. A non-pointer value is not addressable, so `CanSet()` returns false. `fv.Set(reflect.ValueOf(value))` panics if types don't match exactly — `int64` vs `int` are different kinds.

</Solution>

</Exercise>

<Exercise n={4} title="Measure struct padding with unsafe" level="hard">

Write a function `printLayout[T any](name string)` (using generics) that prints a type's size, alignment, and for each exported field: its name, offset, and size. Use `unsafe.Sizeof`, `unsafe.Offsetof`, and `unsafe.Alignof`. Then define two structs — one padded, one tight — and compare them.

<Solution>

```go
package main

import (
	"fmt"
	"reflect"
	"unsafe"
)

func printLayout[T any](name string) {
	var zero T
	rt := reflect.TypeOf(zero)
	fmt.Printf("=== %s ===\n", name)
	fmt.Printf("  sizeof=%d  alignof=%d\n", unsafe.Sizeof(zero), unsafe.Alignof(zero))

	for i := 0; i < rt.NumField(); i++ {
		sf := rt.Field(i)
		if !sf.IsExported() {
			continue
		}
		// unsafe.Offsetof requires a field selector expression, not an index.
		// We use reflect to get the offset instead — a safe approximation.
		fmt.Printf("  [+%d] %s  size=%d\n", sf.Offset, sf.Name, sf.Type.Size())
	}
	fmt.Println()
}

type Padded struct {
	Active  bool
	Balance int64
	Code    byte
}

type Tight struct {
	Balance int64
	Code    byte
	Active  bool
}

func main() {
	printLayout[Padded]("Padded")
	printLayout[Tight]("Tight")

	saving := unsafe.Sizeof(Padded{}) - unsafe.Sizeof(Tight{})
	fmt.Printf("Saving per struct instance: %d bytes (%.0f%%)\n",
		saving,
		float64(saving)/float64(unsafe.Sizeof(Padded{}))*100)
}
```

`reflect.StructField.Offset` gives you the field offset without needing a compile-time field selector expression. In real code, `unsafe.Offsetof` is the compile-time version — use it in `unsafe.Pointer` arithmetic. `reflect`'s `.Offset` is the runtime mirror.

</Solution>

</Exercise>

<Exercise n={5} title="Implement a safe bytesToString with a mutation guard" level="hard">

Implement `safeBytesToString(b []byte) (s string, assertNotMutated func())`. The main function returns the zero-copy string *and* a closure that panics if the original slice has been mutated (by comparing a hash of the original bytes to the current bytes). This makes the dangerous pattern *detectable* in tests. Use `unsafe.String` (Go 1.20+) for the conversion.

<Solution>

```go
package main

import (
	"fmt"
	"hash/fnv"
	"unsafe"
)

// safeBytesToString returns a zero-copy string and a guard function.
// Call assertNotMutated() in tests after any code that might have mutated b.
func safeBytesToString(b []byte) (string, func()) {
	if len(b) == 0 {
		return "", func() {}
	}

	// Capture a hash of the original bytes at conversion time.
	h := fnv.New64a()
	h.Write(b)
	originalHash := h.Sum64()

	s := unsafe.String(&b[0], len(b))

	assertNotMutated := func() {
		h2 := fnv.New64a()
		h2.Write(b)
		if h2.Sum64() != originalHash {
			panic("safeBytesToString: backing []byte was mutated — string is now corrupt")
		}
	}

	return s, assertNotMutated
}

func main() {
	buf := []byte("payment_completed_v2")
	s, assertOK := safeBytesToString(buf)
	fmt.Println("string:", s)

	// Safe use:
	assertOK() // no panic — buf hasn't changed
	fmt.Println("guard check passed")

	// Simulate a mutation bug:
	buf[0] = 'X'
	defer func() {
		if r := recover(); r != nil {
			fmt.Println("caught mutation:", r)
		}
	}()
	assertOK() // panics — buf was mutated, string is corrupt
}
```

This pattern is excellent for testing code that uses zero-copy conversions: wrap the unsafe call, pass the guard to a `t.Cleanup`, and mutation bugs surface as test failures instead of silent data corruption. The hash check is O(n) — only used in test paths.

</Solution>

</Exercise>

<Recap>

- **Reflection** (`reflect.Type`, `reflect.Value`) lets you introspect and manipulate types at runtime. It works because every interface value carries a two-word header: type pointer + data pointer. The type pointer leads to a runtime type descriptor that holds field names, kinds, offsets, and struct tags.
- **`reflect.TypeOf`** gives you the shape; **`reflect.ValueOf`** gives you the data. To *set* fields, you must work through a pointer (Law 3 of reflection: settability requires addressability).
- **Struct tags** (the backtick strings after fields) live in the type descriptor and are readable only via reflection. `encoding/json`, ORMs, and validators all rely on them.
- Reflection is justified for **serializers, ORMs, and tools that handle unknown types**. It's a code smell when a plain interface or generic function would do the job — because reflection is slower and defeats compile-time safety.
- **Go 1.25:** `reflect.TypeAssert[T](v)` returns `(T, bool)` from a `reflect.Value` without the unnecessary allocations that `.Interface().(T)` can require.
- **Go 1.26:** `Type.Fields()`, `Value.Fields()`, `Type.Methods()`, `Value.Methods()` return rangeable iterators — cleaner than the classic `for i := 0; i < t.NumField(); i++` loop.
- **CPU profiles** (`runtime/pprof`, `net/http/pprof`) tell you where time is spent. **Heap profiles** tell you where allocations happen. Read them with `go tool pprof`; as of Go 1.26, the web UI opens with the flame graph view by default. Deep pprof, the execution tracer, and flame graph interpretation are **Part 2, Chapter 8**.
- **`unsafe.Sizeof/Offsetof/Alignof`** are compile-time constants for struct layout inspection. Sort struct fields by alignment (largest first) to eliminate padding.
- **`unsafe.Pointer`** can convert between any pointer types — which is exactly why it's unsafe. Follow the six legal conversion patterns; `go vet` enforces them via the `unsafeptr` analysis pass.
- **`uintptr` is not a pointer.** The GC does not trace through it. Never store an address as a `uintptr` across a GC-safe point.
- **Zero-copy `[]byte` → `string`**: use `unsafe.String(&b[0], len(b))` (Go 1.20+). The invariant you must maintain: the `[]byte` must not be mutated and must outlive the string. Use `sync.Pool` to amortize the allocation; use the zero-copy trick only when profiler evidence says the copy is the bottleneck.
- **Go 1.26 (experimental):** `runtime/secret` provides secure-erasure wrappers for cryptographic temporaries — coverage in Part 3, Chapter 10.
- **These tools defeat the compiler's guarantees.** Use them only with profiler evidence and a clear, tested invariant. `go vet` is your first line of defense.

</Recap>
