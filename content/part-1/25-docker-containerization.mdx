## What a Container Is

*Stop 1 of 5.*

### Step 1: a process with a private view

The most common misconception: **a container is not a virtual machine.** A VM emulates hardware and boots a whole guest OS. A container is a Linux process, the same kind as your shell, that the kernel isolates and constrains.

<Define term="Container">
An ordinary Linux process (or process tree) that the kernel **isolates** with namespaces (its own view of process IDs, network, filesystem, hostname) and **constrains** with cgroups (limits on CPU, memory, I/O). No hypervisor, no guest OS: it shares the host's kernel.
</Define>

On a Mac or Windows machine, Docker Desktop runs a small Linux VM and your containers are processes inside *that*. The containers themselves are still just processes.

### Step 2: namespaces decide what it can see

A **namespace** gives a process its own copy of something that's normally global. Docker uses these by default:

<ConceptGrid cols={3}>
  <ConceptCard label="PID">The container's first process sees itself as PID 1 and can't see the host's processes.</ConceptCard>
  <ConceptCard label="Network">Its own interfaces, routes and ports. Port 8080 inside isn't host port 8080 until you publish it with <code>-p</code>.</ConceptCard>
  <ConceptCard label="Mount">Its own filesystem tree. Its <code>/</code> is the image, not the host's disk.</ConceptCard>
  <ConceptCard label="UTS">Its own hostname.</ConceptCard>
  <ConceptCard label="IPC">Its own shared-memory and message-queue objects.</ConceptCard>
  <ConceptCard label="cgroup">Its own view of the cgroup tree, so it sees its limits as the whole world.</ConceptCard>
  <Gotcha>The **user** namespace (root inside mapped to a nobody outside) exists but is *off* by default in Docker. Root in a default container is root on the host's kernel, which is why Stop 4 makes the ledger run as a non-root user.</Gotcha>
</ConceptGrid>

### Step 3: cgroups decide what it can use

**Control groups** limit and account for resources. `docker run --memory=64m` writes a number into the container's cgroup, and you can read it back from inside:

```bash
$ docker run --rm --memory=64m alpine:3.22 cat /sys/fs/cgroup/memory.max
67108864
```

That's 64 × 1024 × 1024. Go past it and the kernel's OOM killer ends the process (exit code 137), the same mechanism that kills any runaway Linux process. When a service is OOM-killed, the first question is "what limit did we set?", before "is there a leak?". Stop 4 shows how Go reads these limits.

### Step 4: images vs containers

<Define term="Image vs. Container">
An **image** is a read-only stack of filesystem layers plus metadata (entrypoint, environment, user, exposed ports). You build it, tag it, push it; it never runs. A **container** is an instance of an image: Docker adds a thin writable layer on top and starts the process. Many containers share one image's layers.
</Define>

<UnderTheHood title="OverlayFS: layers without copies">

The layered filesystem on modern Linux is **OverlayFS**. It stacks read-only **lower** directories (the image layers) under one writable **upper** directory (the container's layer) and shows them as one tree.

- **Reads** look in the upper layer first, then down through the image layers. Nothing is copied.
- **Writes** to a file from a lower layer first **copy it up** into the upper layer, then modify the copy. The image is never changed, which is why the first write to a large file is slow.
- **Deleting** a lower-layer file writes a "whiteout" marker in the upper layer. This is why `RUN rm big-file` in a later Dockerfile step never shrinks an image: the file still sits in the earlier layer.
- **Removing the container** deletes the upper layer. Data that must survive lives in a **volume**, which bypasses OverlayFS.

</UnderTheHood>

**Recap.** A container is a process: namespaces control what it sees, cgroups control what it uses, OverlayFS gives it an image as its root. Images are read-only layers; containers add one writable layer.

## Images, Layers & the Cache

*Stop 2 of 5.*

### Step 1: which instructions make layers

Instructions that change files (`RUN`, `COPY`, `ADD`) each add a **layer**: the set of files that step changed. The rest (`ENV`, `EXPOSE`, `CMD`, `USER`, `WORKDIR`'s metadata) only change the image's configuration and show as `0B` in `docker history`. Here's the start of the naive ledger image's history, top line newest:

```text
0B      CMD ["/app/ledger"]
0B      EXPOSE [8080/tcp]
244MB   RUN /bin/sh -c go build -o ledger ./cmd/ledger
78.8MB  RUN /bin/sh -c go mod download
41kB    COPY . .
8.19kB  WORKDIR /app
...
290MB   COPY /target/ /          (the Go toolchain, inside golang:1.27-alpine)
9.31MB  ADD alpine-minirootfs-3.24.2-aarch64.tar.gz
```

Notice the 244 MB `go build` layer: 16 MB of it is the binary, the rest is Go's build cache in `/root/.cache/go-build`, frozen into the image.

### Step 2: the cache rule

When you rebuild, BuildKit reuses a step's cached result if the step's instruction, and everything it depends on (for `COPY`, the copied files' contents), is unchanged. The first step that misses invalidates **every step after it**. So order matters: things that rarely change go first.

### Step 3: the cache that layer order can't fix

Why is the "good" Dockerfile still at 21 seconds? Because each `RUN go build` starts with an **empty Go build cache**. On your laptop, a rebuild after a one-line edit takes a second or two: Go reuses compiled packages from `~/.cache/go-build`. Inside a Docker build that directory starts empty every time the step reruns, so pgx, go-redis and the standard library get compiled from scratch.

BuildKit's **cache mounts** fix that: a directory that persists between builds on the build machine but never goes into the image:

```dockerfile
RUN --mount=type=cache,target=/go/pkg/mod \
    --mount=type=cache,target=/root/.cache/go-build \
    CGO_ENABLED=0 go build -o /out/ledger ./cmd/ledger
```

The measurements, same one-line edit each time:

| Dockerfile | Rebuild after editing one .go file |
|---|---|
| Naive (`COPY . .` first) | 28.9 s |
| Manifests first | 21.7 s |
| Manifests first + cache mounts | **2.7 s** |
| Nothing changed at all | 1.7 s |

Layer order saved the module download (about 7 s here, far more on a slow network or with many modules). Cache mounts saved the compile. You want both. BuildKit has been Docker's default builder since Docker 23, and the `# syntax=docker/dockerfile:1` line at the top of a Dockerfile makes sure `--mount` is understood.

<Callout kind="warn" title="Cache mounts live on the builder">

A cache mount survives between builds on the same machine. A fresh CI runner starts with an empty one, so in CI you also export the build cache (`docker buildx build --cache-to/--cache-from`, or your CI's Docker cache integration). ch27 sets this up.

</Callout>

### Step 4: build arguments and the cache

An `ARG` used by a step is part of that step's cache key. Declare version-stamping arguments **after** the expensive steps, right before the build that uses them:

```dockerfile
COPY . .
ARG VERSION=dev
RUN go build -ldflags="-X main.version=${VERSION}" -o /out/ledger ./cmd/ledger
```

Rebuilding with a new `--build-arg VERSION=v9` reported `go mod download` as `CACHED` and reran only the build.

## Multi-Stage Builds

*Stop 3 of 5.*

### Step 1: build in one image, run in another

The naive image ships everything it took to build: the Go toolchain (277 MB), the module cache (75 MB), the build cache (216 MB) and the source. Production needs one file.

<Define term="Multi-Stage Build">
A Dockerfile with several `FROM` lines. Each stage starts a fresh filesystem. You compile in a stage that has the toolchain, then `COPY --from=<stage>` only the outputs into a final stage. Only the last stage becomes the image; the others are discarded.
</Define>

```dockerfile
# syntax=docker/dockerfile:1

# ── Stage 1: build ───────────────────────────────────────────────
FROM golang:1.27-alpine AS build
WORKDIR /src

# Dependencies first: this layer is reused until go.mod or go.sum change.
COPY go.mod go.sum ./
RUN --mount=type=cache,target=/go/pkg/mod \
    go mod download

# Then the source, which changes on every commit.
COPY . .
ARG VERSION=dev
ARG COMMIT=unknown
RUN --mount=type=cache,target=/go/pkg/mod \
    --mount=type=cache,target=/root/.cache/go-build \
    CGO_ENABLED=0 go build -trimpath \
      -ldflags="-s -w -X main.version=${VERSION} -X main.commit=${COMMIT}" \
      -o /out/ledger ./cmd/ledger \
 && CGO_ENABLED=0 go build -trimpath -ldflags="-s -w" -o /out/healthcheck ./cmd/healthcheck

# ── Stage 2: run ─────────────────────────────────────────────────
FROM scratch
COPY --from=build /etc/ssl/certs/ca-certificates.crt /etc/ssl/certs/
COPY --from=build /out/ledger /out/healthcheck /
USER 65532:65532
EXPOSE 8080
HEALTHCHECK --interval=10s --timeout=5s --start-period=5s --retries=3 \
  CMD ["/healthcheck", "http://localhost:8080/health"]
ENTRYPOINT ["/ledger"]
```

The health checker, `cmd/healthcheck/main.go`:

```go noverify
// healthcheck exits 0 if the URL answers 200 within 3 seconds, 1 otherwise.
// It exists because a scratch image has no curl or wget to do this.
package main

import (
	"net/http"
	"os"
	"time"
)

func main() {
	if len(os.Args) != 2 {
		os.Stderr.WriteString("usage: healthcheck URL\n")
		os.Exit(2)
	}
	client := &http.Client{Timeout: 3 * time.Second}
	resp, err := client.Get(os.Args[1])
	if err != nil {
		os.Stderr.WriteString(err.Error() + "\n")
		os.Exit(1)
	}
	resp.Body.Close()
	if resp.StatusCode != http.StatusOK {
		os.Stderr.WriteString("status " + resp.Status + "\n")
		os.Exit(1)
	}
}
```

### Step 3: why static matters, and the image that silently isn't

A **dynamically linked** binary needs the C library and the dynamic loader (`ld-linux…so`) at runtime. `scratch` has neither. Build the same ledger in the Debian-based `golang:1.27` image, where cgo is on by default, and copy it into `scratch`:

```text
$ ldd ledger
	linux-vdso.so.1
	libc.so.6 => /lib/aarch64-linux-gnu/libc.so.6
	/lib/ld-linux-aarch64.so.1
$ docker run --rm dyn
exec /ledger: no such file or directory
```

"No such file" names the binary, which is right there. The missing file is the *loader* the binary asks for. `CGO_ENABLED=0` makes the linker produce a static binary that needs nothing, and Go's standard library has pure-Go versions of what cgo would be used for (notably the DNS resolver).

A detail that surprises people: in `golang:1.27-alpine`, `go env CGO_ENABLED` already prints `0`, because the image has no C compiler and Go turns cgo off when it can't find one. The naive image's binary was static by accident. Set `CGO_ENABLED=0` anyway: builds shouldn't depend on which image happens to lack `gcc`. ch26 covers linking properly.

### Step 4: what scratch doesn't have

An empty image is empty. Three things Go programs commonly expect, each verified:

| Missing | Symptom in `scratch` | Fix |
|---|---|---|
| CA certificates | `tls: failed to verify certificate: x509: certificate signed by unknown authority` | `COPY --from=build /etc/ssl/certs/ca-certificates.crt /etc/ssl/certs/` |
| Time zone database | `unknown time zone Europe/London` from `time.LoadLocation` | build with `-tags timetzdata`, or `import _ "time/tzdata"` (adds about 400 KB) |
| A shell and tools | no `docker exec … sh`, no `curl` for healthchecks | ship Go tools like `healthcheck`; debug with `docker debug` or an ephemeral debug container |

<Define term="scratch vs distroless">
`scratch` is Docker's empty base. Google's **distroless** images add a little: `gcr.io/distroless/static-debian12` (about 2 MB) has CA certificates, time zone data and an `/etc/passwd` with a `nonroot` user, but no shell, package manager or libc. Its `:nonroot` tag runs as UID 65532 by default. For binaries that need glibc, `distroless/base-debian12` adds it.
</Define>

Either is a good default for Go. `scratch` makes you list every file; distroless saves the certificate and time zone steps.

**Recap.** Compile in a toolchain stage, copy only outputs into `scratch` or distroless: 772 MB → 24 MB. The binary must be static (`CGO_ENABLED=0`), or `scratch` answers `no such file or directory`. Bring CA certificates and time zone data yourself.

### Step 1: PID 1 and docker stop

`docker stop` sends **SIGTERM** to the container's PID 1, waits 10 seconds, then sends **SIGKILL**. Your ch19 server shuts down gracefully on SIGTERM, *if it receives it*. Whether it does depends on one line of the Dockerfile:

The details, because they're subtle:

- **Exec form** (`ENTRYPOINT ["/ledger"]`) runs the binary directly as PID 1. **Shell form** (`CMD /ledger`) runs `/bin/sh -c "/ledger"`.
- Whether the shell stays around depends on the shell. Alpine's busybox `sh` replaces itself with the last command it runs, so on Alpine even `CMD ./migrate && ./ledger` happened to leave the ledger as PID 1. Debian's `dash` kept itself as PID 1 for the same line (measured: 10.16 s, exit 137), and any shell stays when there's work after the binary, as in `CMD /ledger; echo exited`. Don't depend on which shell you got: use exec form. (In `scratch` there's no shell, so shell form can't start at all.)
- The kernel doesn't apply default signal actions to PID 1. Go is safe anyway: its runtime handles SIGTERM itself, so a Go program with no signal code still exits (code 143 = 128 + 15) instead of hanging. But only `signal.NotifyContext` plus `Shutdown` (ch19) lets in-flight requests finish.
- If PID 1 must be a script (to run migrations first, say), end it with `exec /ledger` so the binary replaces the shell, or run `docker run --init` to put a tiny init process in front.

### Step 2: don't run as root

Without a `USER` line, the process runs as UID 0. The naive image's `id`:

```text
uid=0(root) gid=0(root) groups=0(root),1(bin),2(daemon),3(sys),4(adm),6(disk),10(wheel),...
```

With the default configuration there's no user namespace, so that's root on the host's kernel, protected only by the other namespaces, dropped capabilities and seccomp. An escape bug in the kernel or runtime gives the attacker root. `USER 65532:65532` costs nothing: a Go server on port 8080 doesn't need root (ports below 1024 would, which is one reason containers listen on 8080).

### Step 3: Go reads the CPU limit, not the memory limit

A `scratch` program that prints what the runtime thinks it has, run with and without limits:

```go noverify
package main

import (
	"fmt"
	"os"
	"runtime"
	"runtime/debug"
)

func main() {
	fmt.Println("CPUs the machine has:", runtime.NumCPU())
	fmt.Println("GOMAXPROCS:          ", runtime.GOMAXPROCS(0))
	limit := debug.SetMemoryLimit(-1) // -1 reads the current limit without changing it
	fmt.Println("memory limit (bytes):", limit, "| GOMEMLIMIT env:", os.Getenv("GOMEMLIMIT"))
}
```

```text
$ docker run --rm mp
CPUs the machine has: 8
GOMAXPROCS:           8
memory limit (bytes): 9223372036854775807 | GOMEMLIMIT env:

$ docker run --rm --cpus=2 --memory=256m mp
CPUs the machine has: 8
GOMAXPROCS:           2
memory limit (bytes): 9223372036854775807 | GOMEMLIMIT env:

$ docker run --rm --cpus=2 --memory=256m -e GOMEMLIMIT=230MiB mp
GOMAXPROCS:           2
memory limit (bytes): 241172480 | GOMEMLIMIT env: 230MiB
```

- **CPU:** since Go 1.25 the runtime reads the cgroup CPU limit, so `--cpus=2` gives `GOMAXPROCS=2` automatically. Before that, a service on a 64-core node with a 2-CPU limit ran 64 threads' worth of parallel work and was throttled constantly (the `go.uber.org/automaxprocs` package existed to fix this).
- **Memory:** the runtime does **not** read `--memory`. Its limit stays "unlimited" (the max int64), so the garbage collector can let the heap grow past 256 MB and the kernel OOM-kills the container. Set **`GOMEMLIMIT`** to roughly 90% of the container's limit, leaving room for memory the Go heap doesn't count. Part 2, Chapter 10 explains how the GC uses it.

**Recap.** Use exec form so the Go process is PID 1 and gets SIGTERM (0.21 s stop vs 10.18 s and SIGKILL). Run as a non-root UID. Go follows the CPU limit by itself; set `GOMEMLIMIT` for the memory limit.

## Docker Compose

*Stop 5 of 5.*

### Step 1: one file for the whole local stack

The ledger needs Postgres and Redis. Starting three containers by hand, with the right network, volumes and order, every day, isn't engineering.

<Define term="Docker Compose">
A YAML file (`compose.yaml`) describing several containers (image or build, environment, ports, volumes, dependencies) that `docker compose up` creates and starts together on a private network. It's a local development and single-host tool; production orchestration is ch27.
</Define>

This is the file used for the measurements in this chapter; `docker compose up` brought all three services to `healthy`:

```yaml
# Local development stack for the Meridian ledger. Not a production config.
services:
  ledger:
    build:
      context: .
      args:
        VERSION: dev
    ports:
      - "8080:8080"
    environment:
      DATABASE_URL: postgres://ledger:secret@postgres:5432/ledger?sslmode=disable
      REDIS_ADDR: redis:6379
    depends_on:
      postgres:
        condition: service_healthy
      redis:
        condition: service_healthy

  postgres:
    image: postgres:18-alpine
    environment:
      POSTGRES_USER: ledger
      POSTGRES_PASSWORD: secret # dev only
      POSTGRES_DB: ledger
    ports:
      - "5432:5432" # so psql on your laptop can reach it
    volumes:
      - pg_data:/var/lib/postgresql
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U ledger -d ledger"]
      interval: 2s
      timeout: 3s
      retries: 15
      start_period: 5s

  redis:
    image: redis:8-alpine
    volumes:
      - redis_data:/data
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 2s
      timeout: 3s
      retries: 15

volumes:
  pg_data:
  redis_data:
```

### Step 2: service names are hostnames

Compose puts every service on one private network, and Docker's embedded DNS server (at `127.0.0.11`, written into each container's `/etc/resolv.conf`) resolves service names to container addresses:

```text
$ docker run --rm --network c25_default alpine:3.22 nslookup postgres
Name:	postgres
Address: 172.18.0.2
```

That's why `DATABASE_URL` says `@postgres:5432`: not `localhost`, which inside the ledger container is the ledger container itself. With `CGO_ENABLED=0`, Go's own resolver reads `/etc/resolv.conf` and asks `127.0.0.11` directly.

Only `ports:` publishes a container port on your machine. Redis has no `ports:` entry, so the ledger can reach it but your laptop can't: exactly the exposure it needs.

Plain `depends_on: [postgres]` only waits until the Postgres **container has started**, not until it accepts connections. `condition: service_healthy` waits for its `healthcheck` to pass. Don't substitute `sleep 5`: it's too long on a fast machine, too short on a slow one, and it tends to migrate into production scripts.

Your service should still tolerate a dependency that's briefly down, because in production nothing orders startup for you. The ledger's `sql.Open` doesn't connect at all (ch18), and `/health` reports 503 until both answer, which is the behaviour you want.

### Step 4: volumes

`pg_data` and `redis_data` are **named volumes**: Docker-managed storage that outlives containers. `docker compose down` keeps them; `down -v` deletes them.

One version-specific detail, checked against the image: the `postgres:18` images keep data in `/var/lib/postgresql/18/docker` and declare the volume at `/var/lib/postgresql`. Older guides (and Postgres 17 and earlier) mount `/var/lib/postgresql/data`; with 18, mount the parent as above so the data lands in your volume.

```bash
docker compose up -d --build   # build the ledger, start everything in the background
docker compose ps              # status, including (healthy)
docker compose logs -f ledger  # follow one service's logs
docker compose down            # stop and remove containers; volumes kept
docker compose down -v         # …and delete the volumes (wipes the database)
```

<Callout kind="note" title="Local development, not production">

This file publishes Postgres on your laptop, hard-codes a password, and has no TLS. That's fine for development and wrong anywhere else. Production (secrets from a secret manager, resource limits, rolling deploys, probes wired to `/health`) is ch27.

</Callout>

**Recap.** Compose runs the stack on a private network where service names are hostnames. `depends_on` with `condition: service_healthy` plus real healthchecks orders startup; named volumes keep data between runs.

## Exercises

<Exercise n={1} title="Spot the cache-busting Dockerfile" level="easy">

This Dockerfile re-downloads every module and recompiles everything on each source change. Fix the order, and make the compile incremental too.

```dockerfile
FROM golang:1.27-alpine AS build
WORKDIR /app
COPY . .
RUN go mod download
RUN CGO_ENABLED=0 go build -o /api ./cmd/api
FROM scratch
COPY --from=build /api /api
ENTRYPOINT ["/api"]
```

<Solution>

`COPY . .` comes before `go mod download`, so any source change invalidates the download. Copy the manifests first, and give the build a cache mount:

```dockerfile
# syntax=docker/dockerfile:1
FROM golang:1.27-alpine AS build
WORKDIR /app
COPY go.mod go.sum ./
RUN --mount=type=cache,target=/go/pkg/mod go mod download
COPY . .
RUN --mount=type=cache,target=/go/pkg/mod \
    --mount=type=cache,target=/root/.cache/go-build \
    CGO_ENABLED=0 go build -o /api ./cmd/api

FROM scratch
COPY --from=build /api /api
ENTRYPOINT ["/api"]
```

On the ledger, the same two changes took a one-line-edit rebuild from 28.9 s to 2.7 s.

</Solution>

</Exercise>

<Exercise n={2} title="HTTPS from scratch" level="easy">

A service in `FROM scratch` fails every call to a payment provider with `x509: certificate signed by unknown authority`. Explain, and fix it two different ways.

<Solution>

Go's TLS client verifies servers against the system's CA certificates, which on Linux it looks for in files like `/etc/ssl/certs/ca-certificates.crt`. `scratch` has no files, so no certificate is trusted.

Fix 1, copy the bundle from the build stage:

```dockerfile
FROM scratch
COPY --from=build /etc/ssl/certs/ca-certificates.crt /etc/ssl/certs/
COPY --from=build /out/api /api
ENTRYPOINT ["/api"]
```

Fix 2, use a base that has it: `FROM gcr.io/distroless/static-debian12:nonroot`.

(A third option exists: importing `golang.org/x/crypto/x509roots/fallback` compiles a root bundle into the binary, used only when the system has none. It works, but the bundle is only as fresh as your last build.)

</Solution>

</Exercise>

<Exercise n={3} title="Stop in under a second" level="medium">

A teammate's image uses `CMD ./migrate && ./ledger`, and every deploy pauses about ten seconds per container before the old one dies. Explain what's happening and fix it without giving up the migration step.

<Solution>

Shell form runs `/bin/sh -c "./migrate && ./ledger"`. The shell must stay alive to run the second command after the first, so it's PID 1 and the ledger is its child. `docker stop` sends SIGTERM to the shell, which doesn't forward it; after 10 seconds Docker sends SIGKILL, and in-flight requests die with the ledger.

Use a small entrypoint script that ends in `exec`, so the ledger *replaces* the shell as PID 1:

```sh
#!/bin/sh
set -e
./migrate
exec ./ledger "$@"
```

```dockerfile
COPY entrypoint.sh /entrypoint.sh
ENTRYPOINT ["/entrypoint.sh"]
```

This needs a shell in the image (so distroless or Alpine rather than scratch). Alternatives: run migrations as a separate one-off container or job before the deploy (the usual production answer, ch27), or keep shell form but add `docker run --init`, which puts a minimal init in front that forwards signals.

</Solution>

</Exercise>

<Exercise n={4} title="Fix the Compose race" level="medium">

The worker below starts before Postgres accepts connections and crashes on its startup ping. Fix it.

```yaml
services:
  worker:
    build: .
    environment:
      DATABASE_URL: postgres://app:secret@postgres:5432/app
  postgres:
    image: postgres:18-alpine
    environment:
      POSTGRES_USER: app
      POSTGRES_PASSWORD: secret
      POSTGRES_DB: app
```

<Solution>

```yaml
services:
  worker:
    build: .
    environment:
      DATABASE_URL: postgres://app:secret@postgres:5432/app
    depends_on:
      postgres:
        condition: service_healthy
    restart: on-failure # belt and braces for later restarts of postgres
  postgres:
    image: postgres:18-alpine
    environment:
      POSTGRES_USER: app
      POSTGRES_PASSWORD: secret
      POSTGRES_DB: app
    volumes:
      - pg_data:/var/lib/postgresql
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app -d app"]
      interval: 2s
      timeout: 3s
      retries: 15
      start_period: 5s
volumes:
  pg_data:
```

`condition: service_healthy` needs something to check, so Postgres gets a `healthcheck`. Better still, make the worker retry its first connection with backoff for a few seconds: ordering only helps at `compose up`, not when Postgres restarts later.

</Solution>

</Exercise>

<Exercise n={5} title="Version-stamped images" level="hard">

Make `make image VERSION=v1.4.0` produce `ledger:v1.4.0`, whose `/version` returns `{"commit":"<git sha>","version":"v1.4.0"}`, without invalidating the module download when only the version changes.

<Solution>

The Dockerfile in Stop 3 already has the pieces (lines 14–19): `ARG VERSION` and `ARG COMMIT` after `COPY . .`, passed to `-ldflags "-X main.version=… -X main.commit=…"`, and package-level `var version, commit string` in `main`. The Makefile passes them in:

```makefile
VERSION ?= dev
COMMIT  := $(shell git rev-parse --short HEAD)

image:
	docker build \
	  --build-arg VERSION=$(VERSION) \
	  --build-arg COMMIT=$(COMMIT) \

```

Built this way, `curl localhost:8080/version` returned `{"commit":"abc123","version":"v1.4.0"}`, and a rebuild with a different `VERSION` showed `go mod download` as `CACHED`. `-X` only sets **string variables** (not constants) and needs the full import path for non-main packages, e.g. `-X meridian/ledger/internal/build.Version=v1.4.0`. ch26 also covers `runtime/debug.ReadBuildInfo`, which gets the commit from the VCS stamp Go embeds automatically.

<Recap>

- A **container** is a host process with **namespaces** (what it sees) and **cgroups** (what it uses), rooted in an OverlayFS image. Not a VM.
- File-changing instructions make **layers**; the first changed step invalidates the rest. Manifests before source, plus **BuildKit cache mounts**: 21.7 s → 2.7 s per edit.
- **Multi-stage** builds ship only outputs: 772 MB → 24 MB. The binary must be **static** (`CGO_ENABLED=0`) or scratch says `no such file or directory`.
- `scratch` lacks **CA certificates** and **time zone data**: copy the bundle, build with `-tags timetzdata`, or use **distroless**.
- **Exec form** makes Go PID 1 so it receives SIGTERM (0.21 s stop vs 10.18 s + SIGKILL). Run as a **non-root UID**.
- Go follows the cgroup **CPU** limit since 1.25; set **`GOMEMLIMIT`** for the memory limit yourself.
- **Compose**: service names are DNS names, `depends_on` + `service_healthy` orders startup, named volumes keep data (Postgres 18 mounts `/var/lib/postgresql`).
