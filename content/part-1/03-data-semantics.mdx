## Value vs Pointer Semantics

Here's the scenario. You're on the payments team. You've got a `Transaction` type that your handlers read, validate, and pass around for processing. A new engineer touches it. Suddenly, a transaction that should have been declined gets approved. The logs say the validation ran. The validation *says* it rejected it. And yet: approved. Money went somewhere it shouldn't.

That's a value/pointer semantics bug. I've seen it a dozen times. It always comes from someone who doesn't truly understand what happens when Go copies a value or follows a pointer. Today, that's not you.

### The Copy: what value semantics actually means

<Define term="Value semantics">
A variable holds the **value itself**, not a reference to it. Assignment and function calls copy every byte. Mutations to the copy are invisible to the original. **Why it matters:** small, immutable types are safe to share freely — the caller can never be surprised by a callee that modifies its own copy.
</Define>

In Go, **assignment copies.** Full stop. When you write `b := a`, Go copies every byte of `a` into `b`. They share nothing. Mutating `b` cannot affect `a`. This is **value semantics** — the name says it: you're working with the *value*, not with a reference to the original.

```go
package main

import "fmt"

// Transaction represents a payment record.
// amount is in cents — never a float.
type Transaction struct {
	ID       int64
	Amount   int64  // cents
	Approved bool
}

func main() {
	original := Transaction{ID: 1001, Amount: 5000, Approved: false}

	// Assignment copies every field.
	copy := original

	// Mutating copy has zero effect on original.
	copy.Approved = true

	fmt.Println("original.Approved:", original.Approved) // false
	fmt.Println("copy.Approved:    ", copy.Approved)     // true
}
```

Every field gets duplicated. The two variables occupy different addresses in memory. This is safe, predictable, and exactly what you want — *unless* you intended for both variables to observe the same mutation.

### The Pointer: what pointer semantics actually means

<Define term="Pointer semantics">
A variable holds an **address** pointing at a value elsewhere in memory. Assignment copies the address, not the data, so both sides share the same underlying value. Mutations through a pointer are visible to every holder of that address. **Why it matters:** required when a type is large (copying is expensive), has a managed lifecycle, or must be mutated by multiple parts of the program — but it introduces shared mutable state, which demands discipline.
</Define>

A pointer holds an address — where in memory a value lives. When you assign a pointer, you copy the address, not the value. Both variables now *point at the same underlying data*. Mutating through one is visible through the other.

```go
package main

import "fmt"

type Transaction struct {
	ID       int64
	Amount   int64
	Approved bool
}

func approve(tx *Transaction) {
	// tx is a pointer — we're operating on the original, not a copy.
	tx.Approved = true
}

func main() {
	tx := Transaction{ID: 1001, Amount: 5000, Approved: false}

	// Pass the address with &.
	approve(&tx)

	// tx itself has changed — approve mutated the original.
	fmt.Println("tx.Approved:", tx.Approved) // true
}
```

### When to use value semantics vs pointer semantics

<Define term="Method receiver (value vs pointer)">
The receiver is the implicit first argument of a method — `(t Transaction)` is a **value receiver** (method gets a copy; mutations are lost), `(t *Transaction)` is a **pointer receiver** (method operates on the original; mutations persist). **Why it matters:** the method set of a type changes depending on which kind you use, affecting which interfaces the type satisfies. Inconsistency between methods on the same type is a reliable source of subtle bugs.
</Define>

This is the decision you make *once per type*, and then you commit to it. Mixing both on one type is the source of the bug at the top of the section. Here's the rule of thumb:

<ConceptGrid cols={2}>
  <ConceptCard label="Use value semantics when…">The type is small (fits in a few words), immutable or safely copyable, and has no identity beyond its data. Think: `int`, `time.Time`, a `Point{X, Y int}`, a `Money{Amount int64, Currency string}`. Copying is cheap and correct.</ConceptCard>
  <ConceptCard label="Use pointer semantics when…">The type is large (copying is expensive), has a lifecycle you manage explicitly (open/close, acquire/release), must be shared and mutated by multiple parts of the program, or wraps OS resources. Think: `*http.Request`, `*sql.DB`, `*os.File`.</ConceptCard>
  <ConceptCard label="Method receivers follow the same rule">If a method mutates the receiver, it must use a pointer receiver `(t *Transaction)`. If all methods on a type use pointer receivers, never call a method on a non-addressable copy — it silently operates on a temporary. Consistency is the law.</ConceptCard>
  <Gotcha>Once you choose pointer semantics for a type, ALL methods should use pointer receivers. Mixing pointer and value receivers on one type means the method set changes depending on whether you hold a value or a pointer — and it breaks interface satisfaction in ways that will make you question your career choices.</Gotcha>
</ConceptGrid>

<UnderTheHood title="What 'copy' really costs — and what the compiler does about it">

When you pass a value type to a function, the Go compiler emits a `MOVQ` (or equivalent) for each word-sized chunk of the struct. A 3-field `Transaction` holding two `int64`s and one `bool` (24 bytes after padding — we'll prove this shortly) means the compiler copies 24 bytes per call. For tight loops processing millions of transactions, this adds up.

The compiler is not naive about this. **Escape analysis** (full treatment in Part 2, Chapter 8) decides whether a value lives on the stack or escapes to the heap. Values that don't outlive their function stay on the stack — allocation is practically free (a stack pointer bump), and there's no GC pressure. The moment you take the address of a local value and that address escapes the function (returned, passed to a goroutine, stored in a heap-allocated struct), Go allocates it on the heap and the GC must eventually collect it.

The practical implication: for small structs that don't escape, passing by value is often *faster* than passing a pointer, because:
1. The value lives entirely in registers or on the stack — no heap round-trip.
2. The CPU can prefetch predictable stack data efficiently.
3. There's no pointer indirection (an extra memory read to dereference).

For large structs or structs that must escape anyway, pointers win. Profiler first — never guess. *(Escape analysis: `go build -gcflags="-m" ./...` prints every escape decision. Full mechanical-sympathy story: Part 2, Chapter 10.)*

Go 1.25/1.26 note: the compiler stack-allocates slice backing stores in more situations than before, reducing heap escapes and GC pressure without any code changes on your part. Go 1.26 also made the Green Tea GC the default; its overhead reduction is workload-dependent, especially around marking/scanning many small objects. Full treatment in Part 2, Chapter 10. Don't bake performance assumptions into your architecture; profile with your target Go version.

</UnderTheHood>

## Struct Layout & Alignment

Now the part that trips up even experienced engineers. Your `Transaction` struct doesn't just *hold* your fields — it lays them out in memory according to rigid rules, and those rules can silently make your struct larger than you think.

<Define term="Struct alignment and padding">
**Alignment** is the requirement that a value of size N start at a memory address divisible by N — e.g., an `int64` must sit at a multiple-of-8 address. **Padding** is the invisible zero-bytes the compiler inserts between struct fields to satisfy alignment. The compiler never reorders your fields; it pads between them as declared. **Why it matters:** poor field ordering can silently inflate a struct's size by 40–60%, increasing memory use, GC pressure, and cache misses — with no warning from the compiler.
</Define>

### What alignment is and why the hardware demands it

Modern CPUs read memory in **word-sized chunks** (typically 8 bytes on 64-bit systems). For performance and correctness, hardware often requires that a value of size N be stored at a memory address that's a multiple of N. This requirement is called **alignment**.

- An `int64` (8 bytes) must start at an address divisible by 8.
- An `int32` (4 bytes) must start at an address divisible by 4.
- A `bool` (1 byte) can sit anywhere.

When the Go compiler lays out a struct, it honors these alignment requirements by inserting invisible **padding bytes** between fields. The size of your struct on disk, in memory, or over the wire may be larger than you expect.

Let's prove it with `unsafe.Sizeof`:

```go
package main

import (
	"fmt"
	"unsafe"
)

// Padded: fields ordered smallest-to-largest creates maximum padding waste.
type TransactionPadded struct {
	Approved bool   // 1 byte
	// 7 bytes of PADDING inserted here (to align ID to 8 bytes)
	ID       int64  // 8 bytes
	// 0 padding
	Amount   int64  // 8 bytes
}

// Packed: reordered largest-to-smallest, interior padding eliminated.
// Trailing padding is still 7 bytes (struct total must be multiple of largest alignment),
// but there is no interior padding — same total size, zero waste between fields.
type TransactionPacked struct {
	ID       int64  // 8 bytes
	Amount   int64  // 8 bytes
	Approved bool   // 1 byte
	// 7 bytes of trailing padding
}

func main() {
	fmt.Println("TransactionPadded size:", unsafe.Sizeof(TransactionPadded{}))  // 24
	fmt.Println("TransactionPacked size:", unsafe.Sizeof(TransactionPacked{}))  // 24

	// Now a dramatically worse example:
	type WastefulEvent struct {
		Flag1  bool   // 1 byte + 7 pad
		Amount int64  // 8 bytes
		Flag2  bool   // 1 byte + 7 pad
		Count  int64  // 8 bytes
		Flag3  bool   // 1 byte + 7 pad
	}

	type EfficientEvent struct {
		Amount int64  // 8 bytes
		Count  int64  // 8 bytes
		Flag1  bool   // 1 byte
		Flag2  bool   // 1 byte
		Flag3  bool   // 1 byte
		// 5 bytes trailing pad
	}

	fmt.Println("WastefulEvent size: ", unsafe.Sizeof(WastefulEvent{}))  // 40
	fmt.Println("EfficientEvent size:", unsafe.Sizeof(EfficientEvent{})) // 24
}
```

### The padding rule you can apply immediately

The practical heuristic: **order your struct fields largest to smallest.** Group all your `int64`/`float64`/pointer fields first, then `int32`/`uint32`, then `int16`/`uint16`, then `bool`/`int8`/`byte`. This isn't always perfect but it eliminates the catastrophic cases.

If you want the compiler to catch bad ordering automatically, `golangci-lint` ships `fieldalignment` — a linter that flags structs where reordering would shrink them. Add it to your CI. You can also run the analyzer directly:

```
go install golang.org/x/tools/go/analysis/passes/fieldalignment/cmd/fieldalignment@latest
fieldalignment -fix ./...
```

<UnderTheHood title="Alignment rules, struct padding, and why the compiler never reorders for you">

The Go spec defers alignment requirements to the target architecture, but in practice on amd64 (and arm64):

- `bool`, `int8`, `uint8`, `byte`: size 1, alignment 1
- `int16`, `uint16`: size 2, alignment 2
- `int32`, `uint32`, `float32`, `rune`: size 4, alignment 4
- `int64`, `uint64`, `float64`, `complex64`, pointer, `uintptr`: size 8, alignment 8
- `int`, `uint`: same as the native word size (8 bytes on 64-bit)
- A struct's alignment is the maximum alignment of any of its fields.
- A struct's total size is padded up to a multiple of its own alignment.
- Arrays have the same alignment as their element type.
- Interface values are two words (type pointer + data pointer or value).

Why doesn't the compiler reorder fields automatically, the way some C compilers do with `-fpack-struct`? Because **Go guarantees the field layout** — the fields of a Go struct appear in memory in exactly the order you declared them, with padding inserted between fields as needed. This matters for interoperability: `unsafe.Pointer` arithmetic, C interop via `cgo`, `syscall.Syscall`, and binary serialization formats all depend on knowing *exactly* where a field sits. Silently reordering fields to save space would break those invariants. The compiler respects your ordering and inserts the minimum padding needed to satisfy alignment; it is never permitted to reorder. The job of choosing a good layout belongs to you.

`unsafe.Sizeof` reports the size of a value including padding. `unsafe.Offsetof` gives the byte offset of a specific field. `unsafe.Alignof` gives the alignment requirement. These are resolved at compile time — no runtime cost.

Go 1.26 note: the `unsafe` package semantics have not changed, but the `fieldalignment` analyzer continues to be maintained under `golang.org/x/tools`.

</UnderTheHood>

## Data-Oriented Design

Here's where the philosophy kicks in. Most engineers model data the way they'd model it in a UML diagram: every entity is a struct, every entity has a pointer to the next one, and the whole system is a beautiful web of references.

The hardware hates this. And the garbage collector hates it even more.

<Define term="Data-oriented design — AoS vs SoA">
**Data-oriented design** means shaping data structures around how they are *accessed*, not just how they are modeled. The two layouts are: **Array of Structs (AoS)** — `[]Transaction`, each element holds all fields together; and **Struct of Arrays (SoA)** — parallel slices per field (`[]int64` for amounts, `[]bool` for flags). **Why it matters:** when a hot loop touches only a subset of fields (e.g., just `Amount` across 1M records), SoA loads only the needed field into cache — 8 amounts per 64-byte cache line vs. ~2 full structs. Wrong layout = 10–50× slower without touching the algorithm.
</Define>

### The scenario: scanning a million transactions

You're building a fraud detection pipeline. Every night, you scan a month's worth of transactions — a million records — looking for anomalies. The hot loop reads the `Amount` and `Currency` fields of every transaction and computes aggregate statistics. Profile this naively and you'll find your program spending most of its time not *computing* but *waiting for memory*.

**The problem is cache misses.** A modern CPU L1 cache line is commonly 64 bytes. When the CPU loads data, it loads an entire cache line at once. If your data is laid out *contiguously* — each element right next to the previous one — each cache line load gives you multiple useful elements to process. If your data is pointer-chained — every element is a separate heap allocation scattered across memory — each element is a potential cache miss, and the CPU can stall for tens to hundreds of nanoseconds depending on platform, locality, and memory pressure.

This is the **Array of Structs (AoS) vs. Struct of Arrays (SoA)** design choice, and it can determine whether a hot loop is merely fast or orders of magnitude slower despite using the same algorithm.

```go
package main

import (
	"fmt"
	"unsafe"
)

// AoS: Array of Structs.
// Each Transaction is a struct; we keep a slice of them.
// To scan amounts across all records, the CPU walks through all fields.
type TransactionAoS struct {
	ID       int64   // 8
	Amount   int64   // 8 — the field we care about most
	Currency [3]byte // 3 — "USD", "EUR", etc.
	Approved bool    // 1
	// 4 bytes trailing pad
}

// SoA: Struct of Arrays.
// Each field has its own slice. Scanning amounts is purely sequential reads.
type TransactionStore struct {
	IDs       []int64
	Amounts   []int64   // hot field — contiguous, cache-friendly
	Currencies [][3]byte
	Approved  []bool
}

func main() {
	aos := TransactionAoS{}
	fmt.Println("TransactionAoS size:", unsafe.Sizeof(aos), "bytes per element")
	// The hot field (Amount) is 8 bytes out of 24 — only 33% of each cache-line load
	// is data we actually need in the fraud scan.

	// In a TransactionStore, iterating Amounts scans 8-byte elements packed tightly —
	// 8 amounts per 64-byte cache line — 100% utilization.
	fmt.Println("int64 size:", unsafe.Sizeof(int64(0)), "— 8 per 64-byte cache line")
}
```

### Concrete vs pointer-chained data

The other dimension of data-oriented design: **prefer `[]Transaction` over `[]*Transaction`** when you own the lifecycle and don't need stable addresses.

<BeforeAfter
  badLabel="Pointer-chained (scattered heap)"
  goodLabel="Concrete slice (contiguous memory)"
  bad={`// []*Transaction: each pointer is 8 bytes,

This isn't about micro-optimization. A fraud detection pipeline scanning 1M records can be **10–50× faster** with contiguous layout vs. pointer-chained layout, purely because cache utilization goes from ~33% to near 100% for the hot field. The algorithm is identical. The data layout is everything.

### When NOT to use SoA / contiguous layout

Data-oriented design isn't "always use SoA." It's "design data around how it's accessed." If you always fetch a complete transaction record — ID, Amount, Currency, Approved, all together — then `[]Transaction` (AoS) is correct, because each cache line brings you everything you need for one record. SoA wins when your hot path **touches only a subset of fields** across many records.

<ConceptGrid cols={3}>
  <ConceptCard label="Hot field scanning → SoA">`[]int64` for amounts, `[]bool` for approval flags. Your scan touches 100% of what it loads.</ConceptCard>
  <ConceptCard label="Whole-record access → AoS">`[]Transaction` — load one struct, use all its fields. One allocation, one cache-line neighborhood.</ConceptCard>
  <ConceptCard label="Pointer-chained only when necessary">Use `[]*T` when T is large and mutated independently, when stable addresses are required (concurrent goroutines holding references), or when T has a non-value lifecycle (implements `io.Closer`, etc.).</ConceptCard>
  <Gotcha>Premature SoA is as harmful as premature optimization. Splitting a struct into parallel slices makes insertion/deletion harder, breaks at-a-glance clarity, and is wrong if your access pattern is whole-record. Profile first; reach for SoA when the profiler shows hot-field scans eating time.</Gotcha>

<Define term="Escape analysis — stack vs heap" since="Performance Engineering (Part 2, Chapter 10)">
**Escape analysis** is the compiler pass that decides whether a value lives on the **stack** (cheap: a pointer bump, no GC) or the **heap** (allocated by the runtime, tracked and collected by the GC). A value "escapes" to the heap when it must outlive the function that created it — returned by address, stored in a heap struct, passed to a goroutine closure, or boxed into an `any`. **Why it matters:** taking a pointer when you didn't need to can silently push a value to the heap, adding GC pressure and destroying cache locality. Use `go build -gcflags="-m" ./...` to see every escape decision.
</Define>

<UnderTheHood title="Stack vs heap — where does your data actually live?">

Every goroutine starts with a small stack (about 2 KB in current Go implementations) that grows dynamically. Local variables that don't outlive their declaring function can live entirely on the stack — allocation is extremely cheap, often just a stack-pointer adjustment, with no GC involvement. The exact instruction sequence is architecture- and compiler-dependent.

The heap is where data lives when it *must* outlive the function that created it, or when the compiler cannot prove it doesn't escape. Heap allocation calls into the runtime allocator, the GC must scan and eventually collect the memory, and the address is effectively random (poor cache locality for scattered small allocations).

**Escape analysis** decides which is which. The compiler runs escape analysis during compilation — you can see its decisions with `go build -gcflags="-m" ./...`. Common escape triggers:

- Taking the address of a local variable and returning it: `return &x`
- Storing a pointer in a slice or map that outlives the function
- Passing a value to an `any` parameter (may box it on the heap)
- Passing a value to a goroutine closure

**As of Go 1.25/1.26**, the compiler stack-allocates some slice backing stores in more situations than before — so some short-lived slices that previously escaped to the heap now stay on the stack. The full treatment of escape analysis and when to exploit this lives in **Part 2, Chapter 10: Performance Engineering**.

The key insight: `[]Transaction` — a slice of structs — has one backing array with all elements packed contiguously. If the slice escapes, that backing array is **one** heap allocation. `[]*Transaction` with N separately allocated elements requires one backing array for the pointers plus N individual struct allocations scattered at random addresses. The GC must track all of those object allocations separately.

**Go 1.26 GC note:** Go 1.26 made the Green Tea GC the default collector, improving locality and scalability for marking/scanning many small objects. Contiguous layouts like `[]Transaction` produce fewer, larger allocations — meaning less work for the GC regardless of which collector version is running. The full GC tuning story is in **Part 2, Chapter 10**.

<Exercise n={1} title="Spot the copy bug" level="easy">

The following `setLimit` function is supposed to update a `RateLimit`'s `MaxPerMinute` field, but it doesn't work. Explain why, then fix it.

```go
type RateLimit struct {
    UserID       int64
    MaxPerMinute int
    Enabled      bool
}

func setLimit(rl RateLimit, max int) {
    rl.MaxPerMinute = max
}

func main() {
    limit := RateLimit{UserID: 42, MaxPerMinute: 100, Enabled: true}
    setLimit(limit, 500)
    fmt.Println(limit.MaxPerMinute) // prints 100, not 500
}
```

<Solution>

```go
package main

import "fmt"

type RateLimit struct {
	UserID       int64
	MaxPerMinute int
	Enabled      bool
}

// Fix: take a pointer receiver so the function mutates the original.
func setLimit(rl *RateLimit, max int) {
	rl.MaxPerMinute = max
}

func main() {
	limit := RateLimit{UserID: 42, MaxPerMinute: 100, Enabled: true}
	setLimit(&limit, 500)
	fmt.Println(limit.MaxPerMinute) // 500
}
```

`setLimit` received a copy of `limit`. Setting `rl.MaxPerMinute` wrote to the copy and the copy was discarded on return. Changing the parameter to `*RateLimit` and passing `&limit` at the call site means the function operates on the original. This is the canonical fix for the "mutation didn't stick" bug.

	"fmt"
	"unsafe"

// Original layout — lots of padding.
type OrderEventBad struct {
	Processed bool   // 1 + 7 pad
	OrderID   int64  // 8
	Retried   bool   // 1 + 7 pad

	Source    byte   // 1 + 7 pad

type OrderEventGood struct {
	OrderID   int64  // 8
	Amount    int64  // 8
	Processed bool   // 1
	Retried   bool   // 1
	Source    byte   // 1

<Exercise n={5} title="Value semantics for a Money type" level="hard">

Design a `Money` type (integer cents + ISO 4217 currency code as a `[3]byte`) with value semantics:
- It should be immutable after construction — all operations return a new `Money`.
- Add `Add(other Money) (Money, error)` that returns an error if the currencies differ.
- Add `String() string` that formats as `"USD 14.99"`.

<Solution>

```go
package main

import (
	"fmt"
	"unsafe"
)

// Money uses value semantics — all operations return new values.
// Currency is [3]byte to avoid a string allocation and keep the type
// small enough to pass by value efficiently.
type Money struct {
	Amount   int64   // 8 bytes — cents
	Currency [3]byte // 3 bytes — e.g. "USD", "EUR"
	// 5 bytes trailing pad → total 16 bytes
}

func NewMoney(cents int64, currency string) (Money, error) {
	if len(currency) != 3 {
		return Money{}, fmt.Errorf("currency must be a 3-char ISO code, got %q", currency)
	}
	var cur [3]byte
	copy(cur[:], currency)
	return Money{Amount: cents, Currency: cur}, nil
}

// Add returns a new Money; value semantics — original is untouched.
func (m Money) Add(other Money) (Money, error) {
	if m.Currency != other.Currency {
		return Money{}, fmt.Errorf("currency mismatch: %s vs %s",
			string(m.Currency[:]), string(other.Currency[:]))
	}
	return Money{Amount: m.Amount + other.Amount, Currency: m.Currency}, nil
}

func (m Money) String() string {
	return fmt.Sprintf("%s %d.%02d", string(m.Currency[:]), m.Amount/100, m.Amount%100)
}

func main() {
	a, _ := NewMoney(1499, "USD")
	b, _ := NewMoney(999, "USD")
	sum, err := a.Add(b)
	if err != nil {
		fmt.Println("error:", err)
		return
	}
	fmt.Println(sum)              // USD 24.98
	fmt.Println(a)                // USD 14.99 — unchanged (value semantics)
	fmt.Println("size:", unsafe.Sizeof(Money{})) // 16
}
```

`Money` is 16 bytes — `int64` (8) + `[3]byte` (3) + 5 bytes trailing padding. All operations return new `Money` values; the receiver is never modified. This is correct value semantics: you can pass `Money` by value freely, copy it everywhere, and it's safe, predictable, and cheap.

The mental model is now yours. Here's what you absorbed:

- **Value semantics = copy.** Every assignment, every function argument copies the entire value. Mutations are invisible to the caller. This is safe, stack-friendly, and the right default for small types.
