<HeroCard label="Part 1 · Chapter 3" title="Data Semantics & Data-Oriented Design">

Everyone learns to write Go. Fewer learn what their Go does to memory: what gets copied, what gets shared, where a value lives, and how its bytes are arranged. That knowledge explains a whole family of bugs ("my change didn't stick", "my change leaked into someone else's copy") and, later, most of Go performance work.

The running example is a payments service's `Transaction`. Every size, offset and timing below was measured on Go 1.27, including one benchmark that turned out far less dramatic than the folklore, which is itself the lesson.

2. **Struct layout and alignment.** Why the same fields can take 24 or 40 bytes.
3. **Data-oriented design.** Arranging data for the loop that reads it, with real measurements.

## Value vs Pointer Semantics

*Stop 1 of 3.*

### Step 1: assignment copies

In Go, `b := a` copies `a`'s bytes into `b`. After that they're independent:

<GoPlayground>

```go
package main

import "fmt"

type Transaction struct {
	ID       int64
	Amount   int64 // cents
	Approved bool
}

func main() {
	original := Transaction{ID: 1001, Amount: 5000}
	clone := original // copies every field
	clone.Approved = true
	fmt.Println("original.Approved:", original.Approved)
	fmt.Println("clone.Approved:   ", clone.Approved)
}
```

</GoPlayground>

```text
original.Approved: false
clone.Approved:    true
```

<Define term="Value semantics">
Working with the value itself: assignment and function arguments copy it, and changes to a copy never reach the original. Safe to hand to anyone, because nobody can change your copy.
</Define>

The same rule applies to function arguments, which is how a real bug happens. A validator takes a `Transaction`, marks it approved, and the caller never sees it:

<Define term="Pointer semantics">
Working through an address: `&tx` makes a pointer (8 bytes on a 64-bit machine), copying it copies only the address, and every copy leads to the same value. Changes through any of them are visible to all. That's what you want for things with identity (an account, a database connection) and exactly what makes unsynchronised sharing between goroutines dangerous (ch4).
</Define>

### Step 2: the copy that secretly shares

A struct copy copies its fields, but some fields are themselves little headers pointing elsewhere: slices, maps, pointers, channels. Copy the struct and you copy the header; the data behind it is shared.

<GoPlayground>

```go
package main

import "fmt"

type Order struct {
	ID   int64
	Tags []string
}

func main() {
	a := Order{ID: 1, Tags: []string{"new", "web"}}
	b := a // copies ID, and copies the slice HEADER (pointer, len, cap)

	b.ID = 2            // separate: b has its own ID
	b.Tags[0] = "FRAUD" // shared: both headers point at the same array
	fmt.Println(a.ID, a.Tags, "|", b.ID, b.Tags)

	b.Tags = append(b.Tags, "extra") // no room: b gets a new array
	b.Tags[1] = "app"                // now only b changes
	fmt.Println(a.Tags, "|", b.Tags)
}
```

</GoPlayground>

```text
1 [FRAUD web] | 2 [FRAUD web]
[FRAUD web] | [FRAUD app extra]
```

`b.ID = 2` didn't touch `a`, but `b.Tags[0] = "FRAUD"` did: that's the "value" type that isn't fully a value. After the `append` needed more room, `b` got its own array and the two separated. If a copy must be fully independent, copy those fields explicitly (`slices.Clone`, `maps.Clone`).

### Step 3: choosing, per type

<ConceptGrid cols={2}>
  <ConceptCard label="Value semantics when…">The type is small and has no identity beyond its data: <code>time.Time</code>, a <code>Point</code>, a <code>Money</code>. Methods return new values instead of changing the receiver. Safe to copy, safe to share.</ConceptCard>
  <ConceptCard label="Pointer semantics when…">The value has identity or a lifecycle (<code>*os.File</code>, <code>*sql.DB</code>, an <code>Account</code> whose balance changes), must be changed by methods, or contains something that must not be copied (a <code>sync.Mutex</code>).</ConceptCard>
  <ConceptCard label="Then be consistent">Decide once per type. If its methods need pointer receivers, give them all pointer receivers, and pass <code>*T</code> around.</ConceptCard>
  <Gotcha>Copying a struct that contains a <code>sync.Mutex</code> copies the lock's state, giving two locks that no longer protect the same thing. <code>go vet</code>'s copylocks check reports it. Types with locks use pointer semantics.</Gotcha>
</ConceptGrid>

### Step 4: stack or heap?

Where does a value live? Go decides, not you. A value that doesn't outlive its function can live in the function's **stack frame**, which costs almost nothing and disappears on return. A value whose address outlives the function must live on the **heap**, where the garbage collector tracks it. The compiler's **escape analysis** makes the call, and will tell you:

```go
func sumLocal() int64 {
	tx := Transaction{ID: 1, Amount: 500} // never leaves the function
	return tx.Amount
}

func newTx(id int64) *Transaction {
	tx := Transaction{ID: id} // its address is returned
	return &tx
}

func approve(tx *Transaction) { tx.Approved = true } // only uses the pointer
```

```text
$ go build -gcflags=-m .
./main.go:17:2: moved to heap: tx
./main.go:21:14: tx does not escape
```

`newTx`'s `tx` must outlive the call, so it's **moved to heap**. `approve`'s pointer parameter **does not escape**: it's used and forgotten, so the caller's value can stay on its stack. `sumLocal`'s `tx` isn't mentioned at all, because it never needed a decision.

A consequence people get backwards: passing a pointer to a small struct is not automatically faster than copying it. The copy of a 24-byte value is a few register moves; a pointer may force the value onto the heap and adds an indirection on every access. Pick semantics for correctness (identity, mutation), and let the profiler (Part 2, Chapter 10) tell you about speed.

**Recap.** Assignment and arguments copy. Pointers copy an address, so changes are shared. A struct copy still shares whatever its slice, map and pointer fields point to. Choose value or pointer semantics per type, consistently. Escape analysis decides stack or heap (`-gcflags=-m` shows it).

## Struct Layout & Alignment

*Stop 2 of 3.*

### Step 1: why fields can't start just anywhere

A CPU reads memory in aligned chunks. An 8-byte `int64` is read fastest (and on some CPUs, only) when its address is a multiple of 8. So Go gives every type an **alignment**: `int64` and pointers 8, `int32` 4, `bool` and `byte` 1. To keep every field aligned, the compiler inserts unused **padding** bytes between fields. It never reorders fields to avoid that; it lays them out exactly as you wrote them.

<Define term="Alignment and padding">
**Alignment**: the multiple a value's address must be (8 for `int64`). **Padding**: unused bytes the compiler inserts so each field starts at an aligned offset, plus trailing bytes so the struct's size is a multiple of its largest alignment (so arrays of it stay aligned).
</Define>

### Step 2: same fields, 40 bytes or 24

Does 16 bytes matter? For one value, no. For a slice of ten million events, it's 160 MB, and fewer bytes per element means more elements per cache line in every loop that scans them (Stop 3).

### Step 3: the rule, and the tool

**Order fields from largest alignment to smallest**: 8-byte fields (`int64`, `float64`, pointers, strings, slices, maps, interfaces: all built from 8-byte words), then 4, 2, 1. It won't always be optimal, but it removes the bad cases. To check automatically, the `fieldalignment` analyzer reports structs that could shrink, and can fix them:

```bash
go run golang.org/x/tools/go/analysis/passes/fieldalignment/cmd/fieldalignment@latest ./...
```

Readability still counts: grouping related fields together is sometimes worth a few bytes, and for a struct you create a handful of times it certainly is. Save reordering for types you hold millions of.

<UnderTheHood title="The alignment table, and why Go never reorders">

On amd64 and arm64:

- `bool`, `int8`, `uint8`/`byte`: size 1, alignment 1
- `int16`, `uint16`: 2, 2
- `int32`, `uint32`, `float32`, `rune`: 4, 4
- `int64`, `uint64`, `float64`, `int`, `uint`, pointers, `uintptr`: 8, 8
- `string` (2 words), slice (3 words), interface (2 words): alignment 8
- `complex64`: size 8, alignment 4; `complex128`: size 16, alignment 8
- A struct's alignment is its largest field's; its size is rounded up to a multiple of that.

Go keeps declaration order because code depends on it: `unsafe.Offsetof`, cgo structs shared with C, `syscall` structures and binary encodings all need fields exactly where they were declared. `unsafe.Sizeof`, `Alignof` and `Offsetof` are evaluated at compile time.

</UnderTheHood>

**Recap.** Fields are aligned to their size, and Go pads between them rather than reordering. Order large to small (40 → 24 bytes above), check with `unsafe.Sizeof` or `fieldalignment`, and only bother for types you have many of.

## Data-Oriented Design

*Stop 3 of 3.*

### Step 1: the loop decides the layout

<Define term="Cache line">
The unit a CPU moves between memory and its caches: 64 bytes on most CPUs (128 on Apple's M-series performance cores). Reading one byte brings its whole line into cache, so the neighbouring bytes are nearly free to read next; and a steady walk through memory lets the hardware **prefetcher** fetch lines before you ask.
</Define>

A fraud scanner sums the `Amount` of a million transactions every few seconds. Four ways to hold the data:

- **AoS** (array of structs): `[]Transaction`, each 24 bytes (`ID`, `Amount`, `Currency`, `Approved`) side by side.
- **SoA** (struct of arrays): a separate `[]int64` of just the amounts.
- **Pointers, in allocation order**: `[]*Transaction`, each allocated one after another.
- **Pointers, shuffled**: the same pointers in random order, as you get when records arrive over time or come out of a map.

<Define term="AoS vs SoA">
**Array of structs**: one slice whose elements hold every field. **Struct of arrays**: one slice per field. AoS suits code that uses whole records; SoA suits code that scans one field across many records.
</Define>

### Step 2: the measurement

A million records, each layout summed with `testing.Benchmark`, on the Apple Silicon Mac used for this book:

<GoPlayground>

```go
package main

import (
	"fmt"
	"math/rand/v2"
	"testing"
)

type Transaction struct {
	ID       int64
	Amount   int64
	Currency [3]byte
	Approved bool
}

const n = 1_000_000

func main() {
	aos := make([]Transaction, n)
	amounts := make([]int64, n)
	inOrder := make([]*Transaction, n)
	for i := range n {
		aos[i].Amount = int64(i % 1000)
		amounts[i] = int64(i % 1000)
		inOrder[i] = &Transaction{Amount: int64(i % 1000)}
	}
	scattered := make([]*Transaction, n)
	copy(scattered, inOrder)
	rand.Shuffle(n, func(i, j int) { scattered[i], scattered[j] = scattered[j], scattered[i] })

	var sink int64
	run := func(name string, f func() int64) {
		r := testing.Benchmark(func(b *testing.B) {
			for b.Loop() {
				sink += f()
			}
		})
		fmt.Printf("%-28s %6.2f ms per scan\n", name, float64(r.NsPerOp())/1e6)
	}
	run("SoA []int64", func() (s int64) {
		for _, a := range amounts {
			s += a
		}
		return
	})
	run("AoS []Transaction", func() (s int64) {
		for i := range aos {
			s += aos[i].Amount
		}
		return
	})
	run("[]*Transaction, in order", func() (s int64) {
		for _, t := range inOrder {
			s += t.Amount
		}
		return
	})
	run("[]*Transaction, shuffled", func() (s int64) {
		for _, t := range scattered {
			s += t.Amount
		}
		return
	})
	_ = sink
}
```

</GoPlayground>

```text
SoA []int64                    0.44 ms per scan
AoS []Transaction              0.80 ms per scan
[]*Transaction, in order       0.64 ms per scan
[]*Transaction, shuffled       3.14 ms per scan
```

Read it carefully, because it's more interesting than the folklore:

- **SoA is 1.8× faster than AoS.** Real, and not the "10–50×" you'll see claimed. This machine has large caches and aggressive prefetching; on a busy server with smaller caches the gap is usually wider, but it's a factor, not an order of magnitude.
- **Pointers in allocation order roughly matched AoS** (slightly faster in this run). Objects allocated one after another usually sit one after another in memory, so both the pointer slice and the objects are walked in order, and the prefetcher handles two predictable streams well. Don't read much into a difference that small; the point is that a pointer by itself isn't what's slow.
- **Shuffled pointers are 7× slower than SoA and 4× slower than AoS.** That's the real cost: not the pointer, but **unpredictable** access. Long-lived services drift toward it as objects are created and freed at different times.

The lesson isn't "always use SoA". It's: **know what your hot loop reads, measure, and prefer layouts where it walks memory in order.**

### Step 3: pointers cost the garbage collector too

Speed of the loop isn't the only cost. `[]Transaction` is one allocation with no pointers inside, which the garbage collector can skip over entirely. `[]*Transaction` with a million elements is a million and one allocations, each of which the collector must find and mark on every cycle. For large, long-lived collections, fewer pointers means shorter, cheaper garbage collections (Part 2, Chapter 10 measures it).

### Step 4: when not to do this

<ConceptGrid cols={3}>
  <ConceptCard label="Hot single-field scans → SoA">A loop over millions of records touching one or two fields. Parallel slices, walked in order.</ConceptCard>
  <ConceptCard label="Whole-record use → AoS">Code that reads most fields of each record. <code>[]T</code> keeps each record's fields on the same line.</ConceptCard>
  <ConceptCard label="Pointers when they mean something">Shared identity, values changed through many references, large values moved around often, or types that must not be copied.</ConceptCard>
  <Gotcha>SoA makes code harder: inserting or deleting means updating every slice in step, and a record is no longer one value you can pass around. Reach for it after a profile shows a hot scan, not before.</Gotcha>
</ConceptGrid>

<UnderTheHood title="The memory hierarchy, roughly">

Approximate costs on a modern CPU (they vary a lot between machines):

- Register: well under 1 ns
- L1 cache (tens of KB per core): ~1 ns
- L2 cache (hundreds of KB to a few MB): ~3–5 ns
- L3 / system cache (tens of MB, shared): ~10–40 ns
- Main memory: ~80–120 ns

A sequential walk mostly pays L1 prices because the prefetcher hides the rest; a random walk over data larger than the caches pays main-memory prices on many steps. That's the whole difference between the first and last lines of the benchmark. Part 2, Chapter 10 profiles real services with `pprof` and covers false sharing, where two goroutines slow each other down by writing to the same cache line.

</UnderTheHood>

<Exercise n={1} title="Spot the copy bug" level="easy">

`setLimit` should change a `RateLimit`'s `MaxPerMinute`, but the caller still sees 100. Why? Fix it.

```go
type RateLimit struct {
	UserID       int64
	MaxPerMinute int
	Enabled      bool
}

func setLimit(rl RateLimit, max int) {
	rl.MaxPerMinute = max
}
```

<Solution>

```go
package main

import "fmt"

type RateLimit struct {
	UserID       int64
	MaxPerMinute int
	Enabled      bool
}

func setLimit(rl *RateLimit, max int) {
	rl.MaxPerMinute = max
}

func main() {
	limit := RateLimit{UserID: 42, MaxPerMinute: 100, Enabled: true}
	setLimit(&limit, 500)
	fmt.Println(limit.MaxPerMinute) // 500
}
```

`setLimit` changed its own copy. Taking `*RateLimit` and passing `&limit` makes it change the caller's. (Alternatively, keep value semantics and return the new value: `func withLimit(rl RateLimit, max int) RateLimit`.)

</Solution>

</Exercise>

<Exercise n={2} title="The copy that shares" level="easy">

`Snapshot` returns a copy of an order "so callers can't change the original". A caller then sets `snap.Tags[0] = "FRAUD"`, and the original changes. Explain, and fix `Snapshot`.

<Solution>

```go
package main

import (
	"fmt"
	"slices"
)

type Order struct {
	ID   int64
	Tags []string
}

func (o *Order) Snapshot() Order {
	c := *o                       // copies ID and the slice header
	c.Tags = slices.Clone(o.Tags) // give the copy its own array
	return c
}

func main() {
	o := &Order{ID: 1, Tags: []string{"new", "web"}}
	snap := o.Snapshot()
	snap.Tags[0] = "FRAUD"
	fmt.Println(o.Tags, snap.Tags) // [new web] [FRAUD web]
}
```

`*o` copies the struct, but its `Tags` field is a slice header, so both headers pointed at one array. Cloning the slice (and any maps, with `maps.Clone`) makes the copy independent. Note `slices.Clone` is shallow too: a slice of pointers would still share the pointed-to values.

</Solution>

</Exercise>

<Exercise n={3} title="Measure and pack a struct" level="medium">

Print the size of this struct, reorder it to 24 bytes, and print both.

```go
type OrderEvent struct {

	OrderID   int64
	Retried   bool
	Amount    int64
	Source    byte

```

<Solution>

```go
package main

import (
	"fmt"
	"unsafe"

type OrderEventBad struct {
	Processed bool
	OrderID   int64
	Retried   bool
	Amount    int64
	Source    byte
}

type OrderEventGood struct {
```

<Exercise n={4} title="Benchmark it yourself" level="medium">

Put `sumAoS` and `sumSoA` in a `_test.go` file with `BenchmarkSumAoS` and `BenchmarkSumSoA` over a million records, run `go test -bench=Sum`, and compare with the numbers in Stop 3. Then shrink the input to 1,000 records. What happens to the gap, and why?

<Solution>

```go
package scan

import "testing"

type Transaction struct {
	ID       int64
	Amount   int64
	Currency [3]byte
	Approved bool
}

func sumAoS(txs []Transaction) (sum int64) {
	for i := range txs {
		sum += txs[i].Amount
	}
	return
}

func sumSoA(amounts []int64) (sum int64) {
	for _, a := range amounts {
		sum += a
	}
	return
}

const n = 1_000_000 // then try 1_000

func BenchmarkSumAoS(b *testing.B) {
	txs := make([]Transaction, n)
	for i := range txs {
		txs[i].Amount = int64(i)
	}
	for b.Loop() { // Go 1.24+: setup above isn't timed, and the result can't be optimised away
		sumAoS(txs)
	}
}

func BenchmarkSumSoA(b *testing.B) {
	amounts := make([]int64, n)
	for i := range amounts {
		amounts[i] = int64(i)
	}
	for b.Loop() {
		sumSoA(amounts)
	}
}
```

With a million records (24 MB for AoS) the data doesn't fit in the fastest caches and SoA wins by moving a third of the bytes. With 1,000 records (24 KB) everything stays in L1 after the first pass, memory traffic stops mattering, and the two converge. Layout matters in proportion to how much data the loop walks.

</Solution>

</Exercise>

<Exercise n={5} title="A value-semantics Money type" level="hard">

Design `Money` (integer cents plus a 3-letter currency code in a `[3]byte`) with value semantics: operations return new values, `Add` errors on mismatched currencies, `String` prints `USD 14.99`. Show it's 16 bytes, and that `==` works on it.

<Solution>

```go
package main

import (
	"fmt"
	"unsafe"
)

type Money struct {
	Amount   int64   // cents
	Currency [3]byte // "USD": an array, so Money stays comparable and pointer-free
}

func NewMoney(cents int64, currency string) (Money, error) {
	if len(currency) != 3 {
		return Money{}, fmt.Errorf("currency must be a 3-letter code, got %q", currency)
	}
	var c [3]byte
	copy(c[:], currency)
	return Money{Amount: cents, Currency: c}, nil
}

func (m Money) Add(o Money) (Money, error) {
	if m.Currency != o.Currency {
		return Money{}, fmt.Errorf("currency mismatch: %s vs %s", m.Currency[:], o.Currency[:])
	}
	return Money{Amount: m.Amount + o.Amount, Currency: m.Currency}, nil
}

func (m Money) String() string {
	return fmt.Sprintf("%s %d.%02d", m.Currency[:], m.Amount/100, m.Amount%100)
}

func main() {
	a, _ := NewMoney(1499, "USD")
	b, _ := NewMoney(999, "USD")
	sum, _ := a.Add(b)
	fmt.Println(sum, a)                                           // USD 24.98 USD 14.99
	fmt.Println(sum == Money{Amount: 2498, Currency: a.Currency}) // true
	fmt.Println("size:", unsafe.Sizeof(Money{}))                  // 16
}
```

8 bytes of cents + 3 of currency + 5 of padding = 16. Because both fields are comparable (an array, not a slice), `==` compares Money values directly and `Money` can be a map key. With a `string` currency it would still be comparable but 24 bytes and contain a pointer; with a `[]byte` it wouldn't be comparable at all. (Negative amounts need the sign handling from ch0's lab; Part 3 builds the full type.)

</Solution>

</Exercise>

<Recap>

- **Value semantics = copy.** Assignment and arguments copy; changes to a copy never reach the original. Safe to share, cheap for small types.
- **Pointer semantics = shared.** Copying a pointer copies an address; changes are seen by everyone holding it. Use for identity, lifecycle, mutation, and types that mustn't be copied.
- A struct copy **still shares** what its slice, map and pointer fields point to; clone them when you need independence.
- **Escape analysis** puts values that outlive their function on the heap (`go build -gcflags=-m`: "moved to heap"). Choose semantics for correctness, not guessed speed.
- **Fields keep their order and are padded to alignment**: the same five fields took 40 or 24 bytes. Order large to small; check with `unsafe.Sizeof` or `fieldalignment`.
- **Design for the hot loop.** Measured: SoA 1.8× faster than AoS for a one-field scan; shuffled pointers 4–7× slower than contiguous data. Measure before restructuring.

</Recap>
