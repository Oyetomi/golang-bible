## Structs

Here's the scenario. You're building a banking backend. Your first task: represent a customer account. An account has an ID, an owner's name, and a balance. You could pass three loose values to every function — but that's the kind of chaos that makes incident reports at 3am. You need one *thing* that holds all three, travels together, and has behavior attached.

That thing is a **struct**.

<Define term="struct" since="Data Semantics & Data-Oriented Design (Part 1, Chapter 3)">
A **struct** is a named collection of typed fields grouped into one value. You define it once with `type Account struct { ... }`; the compiler fixes the memory layout. Pass a struct around and you get a copy of every field — that copy semantics story (when copying is right vs. when you need a pointer) goes deep in the next chapter.
</Define>

### Fields and Composite Literals

A struct is a named collection of typed fields. You define it once; the compiler locks in the layout.

```go
// Account holds everything about one customer's bank account.
// Balance is stored in cents — never a float. Ever.
type Account struct {
	ID      string
	Owner   string
	Balance int // cents
}
```

This definition is non-runnable on its own — it's a type declaration. But creating and using one absolutely is:

```go
package main

import "fmt"

type Account struct {
	ID      string
	Owner   string
	Balance int // cents — Part 3 will use a proper money type
}

func main() {
	// Composite literal: name every field explicitly.
	// If you add a new field later, the compiler catches every site
	// that forgot to include it — positional literals don't do that.
	acc := Account{
		ID:      "acct-001",
		Owner:   "Alex Rivera",
		Balance: 250000, // $2,500.00
	}

	fmt.Printf("Account: %+v\n", acc)
	fmt.Printf("Owner: %s, Balance: $%d.%02d\n",
		acc.Owner, acc.Balance/100, acc.Balance%100)
}
```

- **Named field syntax** (`ID: "acct-001"`) is mandatory in production code. Positional `Account{"acct-001", "Alex Rivera", 250000}` works but breaks silently if someone reorders the fields later.
- **`%+v`** prints field names alongside values — indispensable for quick debugging.

### Zero-Value Structs

Here's the beautiful part. A struct's zero value is a struct where every field is *its* zero value. No garbage. No undefined memory. Just `""`, `0`, `false`, and `nil` exactly where you'd expect them.

```go
package main

import "fmt"

type Account struct {
	ID      string
	Owner   string
	Balance int
}

func main() {
	var draft Account // zero value: {ID:"" Owner:"" Balance:0}
	fmt.Printf("zero: %+v\n", draft)

	// Now populate it field by field — perfectly valid.
	draft.ID = "acct-002"
	draft.Owner = "Sam Chen"
	// Balance stays 0 — correct starting point for a new account.
	fmt.Printf("ready: %+v\n", draft)
}
```

A `Balance` of `0` is the right starting value for a new account. That's the Go proverb in action: **make the zero value useful**. When you design your own structs, ask yourself: "Does an all-zero instance of this type make sense?" If yes, you're done. If not, you probably need a constructor function — and that's fine too.

<Callout kind="tip" title="Go 1.26: new(expr) for optional pointer fields">

Go has always had a built-in `new(T)` that allocates a zeroed `T` and returns `*T`. Go 1.26 extends it to accept an **initial value expression**: `new(expr)` allocates a value of the same type as the expression, initialises it to that value, and returns a pointer to it.

This is handy when a struct field is intentionally a pointer (to signal "optional / unset"):

```go
type Profile struct {
	Name string
	Age  *int // nil means "not provided"
}

years := 34
p := Profile{
	Name: "Alex Rivera",
	Age:  new(years), // Go 1.26 — allocates an int, sets it to 34, stores the pointer
}
```

Before Go 1.26 you needed either `&years` (which can alias the local variable in subtle ways if you reuse `years`) or a helper like `func intPtr(n int) *int { return &n }(34)`. `new(expr)` is cleaner. The version is Go 1.26 — on older toolchains, keep using `&years` or a helper.

</Callout>

### Embedding and Composition (Not Inheritance)

Go has no inheritance. This is intentional and wonderful. Instead of `Account extends BaseEntity`, Go uses **embedding** — you include one struct inside another, and its fields and methods are promoted directly.

```go
package main

import "fmt"

// AuditInfo is embedded in any struct that needs audit fields.
// No inheritance, no base class, no virtual dispatch table.
type AuditInfo struct {
	CreatedBy string
	UpdatedBy string
}

type Account struct {
	AuditInfo        // embedded: fields promoted, not named
	ID      string
	Owner   string
	Balance int
}

func main() {
	acc := Account{
		AuditInfo: AuditInfo{CreatedBy: "system", UpdatedBy: "system"},
		ID:        "acct-003",
		Owner:     "Jordan Kim",
		Balance:   0,
	}

	// Access promoted fields directly — as if they were on Account.
	fmt.Println("created by:", acc.CreatedBy) // promoted from AuditInfo
	fmt.Printf("%+v\n", acc)
}
```

## Methods

A struct with fields but no behavior is just data. Methods give it behavior — they're functions with an extra **receiver** argument that binds them to a type.

<Define term="method (value receiver vs pointer receiver)">
A **method** is a function with a receiver — an extra first argument that binds the function to a specific type. `func (a Account) Summary() string` is a **value receiver**: Go passes a copy of `Account` and the method cannot mutate the original. `func (a *Account) Deposit(n int) error` is a **pointer receiver**: Go passes the address, so writes go to the real struct. Rule of thumb: read-only behavior uses value receivers; state-mutating behavior uses pointer receivers. Pick one and stay consistent across all methods of the type.
</Define>

### Value Receivers

A value receiver gets a **copy** of the struct. The method can read every field but cannot mutate the original.

```go
package main

import "fmt"

type Account struct {
	ID      string
	Owner   string
	Balance int
}

// Summary has a value receiver — it gets a copy of Account.
// It cannot change acc.Balance — any write goes into the copy and is thrown away.
func (a Account) Summary() string {
	return fmt.Sprintf("[%s] %s: $%d.%02d",
		a.ID, a.Owner, a.Balance/100, a.Balance%100)
}

func main() {
	acc := Account{ID: "acct-001", Owner: "Alex Rivera", Balance: 250000}
	fmt.Println(acc.Summary())
}
```

### Pointer Receivers

A pointer receiver gets the **address** of the struct. Mutations through it persist to the original. This is how you implement any method that changes state.

```go
package main

import (
	"errors"
	"fmt"
)

type Account struct {
	ID      string
	Owner   string
	Balance int
}

func (a Account) Summary() string {
	return fmt.Sprintf("[%s] %s: $%d.%02d",
		a.ID, a.Owner, a.Balance/100, a.Balance%100)
}

// Deposit has a pointer receiver — it can mutate the original Account.
// The method is defined on *Account, not Account.
func (a *Account) Deposit(amountCents int) error {
	if amountCents <= 0 {
		return errors.New("deposit amount must be positive")
	}
	a.Balance += amountCents // writes through the pointer to the real struct
	return nil
}

// Withdraw similarly needs a pointer receiver — it changes Balance.
func (a *Account) Withdraw(amountCents int) error {
	if amountCents <= 0 {
		return errors.New("withdrawal amount must be positive")
	}
	if amountCents > a.Balance {
		return fmt.Errorf("insufficient funds: have %d cents, need %d", a.Balance, amountCents)
	}
	a.Balance -= amountCents
	return nil
}

func main() {
	acc := Account{ID: "acct-001", Owner: "Alex Rivera", Balance: 250000}
	fmt.Println("before:", acc.Summary())

	if err := acc.Deposit(50000); err != nil { // $500
		fmt.Println("deposit error:", err)
		return
	}
	fmt.Println("after deposit:", acc.Summary())

	if err := acc.Withdraw(10000); err != nil { // $100
		fmt.Println("withdraw error:", err)
		return
	}
	fmt.Println("after withdrawal:", acc.Summary())
}
```

### The Receiver Intuition

The rule is simple: **if the method needs to mutate the struct, or if the struct is large enough that copying it is wasteful, use a pointer receiver**. Otherwise, a value receiver is fine and communicates "this method is read-only."

There's one more hard rule: **be consistent within a type**. If any method on a type uses a pointer receiver, use pointer receivers on *all* methods of that type. Mixing the two makes the method set hard to reason about and breaks interface satisfaction in subtle ways (the full story is in the Data Semantics & Data-Oriented Design chapter — I'm giving you the practical rule now and the deep mechanics next time).

## Interfaces

This is the section that separates Go engineers who *get it* from the ones still writing Java in a Go-shaped box. Pay attention.

<Define term="interface (consumer-defined)" since="Idiomatic Go & the Go Mindset (Part 2, Chapter 1)">
An **interface** is a set of method signatures. In Go, satisfaction is **implicit**: any type that has the right methods satisfies the interface — no `implements` keyword, no declaration at the type site. Crucially, the **consumer** (the package that needs the behavior) defines the interface, not the producer (the package that provides the concrete type). This keeps packages decoupled and interfaces small. A `Ledger` interface defined in the payment service contains only the methods that service actually calls — the Postgres implementation satisfies it for free without importing or knowing about the interface.
</Define>

### The Consumer Defines the Interface

In most languages, the *producer* declares the interface: `class Account implements IAccount { ... }`. The type author announces what contracts it satisfies.

Go flips this on its head. **The consumer defines the interface.** If your `PaymentProcessor` package needs something that can post a debit, you write that interface in *your* package. Any type from anywhere — even packages you don't own — that has a `PostDebit` method with the right signature automatically satisfies it. No declaration. No `implements` keyword. No coupling between packages.

This is called **implicit interface satisfaction**, and it is the single most powerful design mechanism in Go.

<BeforeAfter
  badLabel="Producer-declared (not Go)"
  goodLabel="Consumer-defined (Go way)"
  bad={`// In the account package — producer decides the contract.
type IAccount interface {
    Deposit(int) error
    Withdraw(int) error

type Account struct { ... }
func (a *Account) Deposit(n int) error  { ... }

    Withdraw(amountCents int) error
}

// Any type with a matching Withdraw method satisfies Debitable.
// The account package doesn't need to know this interface exists.
func (l *Ledger) PostDebit(src Debitable, amountCents int) error {
    return src.Withdraw(amountCents)
}`}
/>

Why does this matter? Because:

1. **It decouples packages.** The `ledger` package doesn't import `account`. You can swap in any type that satisfies the interface — a real `Account`, a test double, a mock, a different implementation entirely.
2. **Small interfaces.** Because you define the interface where you use it, you define only what you need. The `Debitable` interface above has one method. That's intentional.
3. **Retroactive satisfaction.** You can make a third-party type satisfy your interface without touching its source. If `database/sql.Tx` happens to have the methods you need, it satisfies your interface for free.

### Implicit Satisfaction in Practice

Let's build the `Ledger` scenario end to end:

```go
package main

import (
	"errors"
	"fmt"
)

// --- account package (inline for the example) ---

type Account struct {
	ID      string
	Owner   string
	Balance int
}

func (a Account) Summary() string {
	return fmt.Sprintf("[%s] %s: $%d.%02d",

		return errors.New("withdrawal amount must be positive")

	if amountCents > a.Balance {
		return fmt.Errorf("insufficient funds: have %d cents, need %d", a.Balance, amountCents)

	a.Balance -= amountCents
	return nil

// It says: "I need something I can call Withdraw on."

	Withdraw(amountCents int) error

// Creditable is defined HERE too.

	Deposit(amountCents int) error
}

// It doesn't care about Account specifically — it cares about the contract.

	if err := src.Withdraw(amountCents); err != nil {
		return fmt.Errorf("debit failed: %w", err)

	if err := dst.Deposit(amountCents); err != nil {
		// In real fintech you'd need to reverse the debit here.

		return fmt.Errorf("credit failed: %w", err)

	return nil
```

### The Nil-Interface Trap (Intro)

This one bites every Go engineer exactly once, and I'd rather you bite it here than in production at 11pm.

An interface value is two words internally: a **type pointer** (which concrete type is stored) and a **data pointer** (where the value lives). A `nil` interface has *both* words as `nil`. But there's a trap: a non-nil interface can hold a nil pointer. The classic manifestation comes up with error returns:

```go
package main

import "fmt"

// LookupError is a custom error type (pointer receiver).
type LookupError struct {
	ID string
}

func (e *LookupError) Error() string {
	return fmt.Sprintf("account %s not found", e.ID)
}

// findAccount tries to find an account. Returns a *LookupError on failure.
// THIS IS WRONG — see the trap below.
func findAccountBad(id string) *LookupError {
	if id != "acct-001" {
		return &LookupError{ID: id}
	}
	return nil
}

// wrapFindBad wraps findAccountBad but returns error (the interface).
func wrapFindBad(id string) error {
	err := findAccountBad(id)
	// BUG: even when err is nil *LookupError, this returns a non-nil error interface!
	// The interface value has type=*LookupError, data=nil.
	return err
}

// findAccountGood returns the interface type directly — correct.
func findAccountGood(id string) error {
	if id != "acct-001" {
		return &LookupError{ID: id}
	}
	return nil // returns a true nil interface — both words zero
}

func main() {
	// Bad version:
	errBad := wrapFindBad("acct-001")
	fmt.Println("bad:", errBad != nil) // prints: true — a lie!

	// Good version:
	errGood := findAccountGood("acct-001")
	fmt.Println("good:", errGood != nil) // prints: false — correct
}
```

<UnderTheHood title="Interface internals: the itable and data word (Go 1.26+)">

Under the hood, every non-empty interface value is exactly **two machine words** — let's call them `itab` and `data`.

**`itab`** (the interface table pointer) — points to a structure that contains:
- A pointer to the **type metadata** of the concrete type (its size, alignment, GC shape, name)
- A pointer to the **method table**: the actual function pointers for every method the interface requires, pre-resolved at the time the value was assigned to the interface

**`data`** — holds a pointer to the concrete value. If the value fits in one word (a pointer, a small integer), the compiler may store it directly here without a heap allocation. If it doesn't fit, it escapes to the heap and `data` holds the address.

What makes the nil-interface trap possible is this layout:

| Scenario | `itab` | `data` | `iface == nil`? |
|---|---|---|---|
| True nil interface (`return nil`) | `nil` | `nil` | `true` |
| Non-nil interface, non-nil value | `&itab` | `&value` | `false` |
| Non-nil interface, nil pointer | `&itab` | `nil` | **`false` — the trap** |

In the trap scenario, `itab` is set (the type is known) but `data` is a nil pointer. The Go runtime's nil check looks *only* at the `itab` word. It's non-nil, so `err != nil` is `true`, even though dereferencing `data` would panic.

**Interface dispatch cost:** calling a method through an interface is slightly more expensive than a direct call — the runtime must load the `itab`, index into the method table, and make an indirect call. For hot paths called millions of times per second, this can matter. `pprof` will tell you when it does — don't guess.

**Method sets and addressability:** only `*T` (pointer-to-T) has the full method set (both value and pointer receivers). `T` only has the value-receiver methods. This is why `&Account{}` satisfies `Debitable` (which requires a pointer-receiver `Withdraw`) but `Account{}` does not. The Data Semantics & Data-Oriented Design chapter goes deep on why; remember the rule for now.

</UnderTheHood>

## Errors

Go's error handling is not a flaw. It's a philosophy. The philosophy is: **every error is visible, every error is deliberate, and no error hides in a stack frame nobody checked**. If that sounds boring, good. Boring is what runs in production.

<Define term="error (the error interface)" since="Error Handling at Scale (Part 2, Chapter 2)">

A `nil` error means "no error" — the entire `if err != nil` idiom works because of this. ### The `error` Interface

`error` is just an interface in the standard library:

```go
type error interface {
    Error() string
}
```

That's it. Any type that has an `Error() string` method is an error. This means:

- You can create errors trivially (`errors.New`, `fmt.Errorf`)
- You can create rich typed errors with extra fields
- The `nil` of an error interface value means "no error" — the entire error-handling pattern hinges on this

### Creating Errors: `errors.New` and `fmt.Errorf`

```go
package main

	"errors"
	"fmt"

	balance, ok := accounts[id]
	if !ok {
		// errors.New for a simple static message
		return 0, errors.New("account not found")
	}
	return balance, nil
}

func applyFee(id string, accounts map[string]int, feeCents int) error {
	balance, ok := accounts[id]
	if !ok {
		// fmt.Errorf for a message with dynamic context
		return fmt.Errorf("applyFee: account %q does not exist", id)
	}
	if balance < feeCents {
		return fmt.Errorf("applyFee: account %q has %d cents, fee is %d cents",
			id, balance, feeCents)
	}
	accounts[id] = balance - feeCents
	return nil
}

func main() {
	accounts := map[string]int{
		"acct-001": 250000,
		"acct-002": 500,

	if b, err := findBalance("acct-001", accounts); err != nil {
		fmt.Println("error:", err)

		fmt.Printf("balance: $%d.%02d\n", b/100, b%100)
```

### The `result, error, check` Pattern in Depth

You saw this pattern in Go Fundamentals but let's make it explicit. Every time a function can fail, it returns `(T, error)`. Every time you call that function, you check the error *immediately* and *completely*. No deferring, no ignoring, no `_`.

```go
// The three-line rhythm of Go error handling:
result, err := someOperation()
if err != nil {
    return ..., fmt.Errorf("context: %w", err) // wrap and propagate, or handle
}
// Use result here — safe, because err is nil.
```

The wrapping with `%w` is important and we'll cover it in a moment. First, the cardinal sin:

### Sentinel Errors and `errors.Is`

Sometimes the *caller* needs to distinguish between types of errors. "Account not found" should be handled differently than "insufficient funds." **Sentinel errors** are package-level error values you compare against:

```go
package main

import (
	"errors"
	"fmt"
)

// ErrNotFound is a sentinel error — an exported variable callers can
// compare against. Convention: Err prefix + noun phrase.
var ErrNotFound = errors.New("account not found")

// ErrInsufficientFunds is another sentinel.
var ErrInsufficientFunds = errors.New("insufficient funds")

func findAccount(id string, db map[string]int) (int, error) {
	balance, ok := db[id]
	if !ok {
		return 0, ErrNotFound // return the sentinel, not a new error
	}
	return balance, nil
}

func withdraw(id string, db map[string]int, amount int) error {
	balance, err := findAccount(id, db)
	if err != nil {
		return fmt.Errorf("withdraw %s: %w", id, err) // wrap with %w
	}
	if amount > balance {
		return fmt.Errorf("withdraw %s: %w", id, ErrInsufficientFunds)
	}
	db[id] = balance - amount
	return nil
}

func main() {
	db := map[string]int{"acct-001": 10000}

	err := withdraw("acct-999", db, 1000)

	// errors.Is unwraps the error chain to find ErrNotFound.
	// Even if err is wrapped with fmt.Errorf + %w, Is finds the sentinel.
	if errors.Is(err, ErrNotFound) {
		fmt.Println("handled: account does not exist, redirect to onboarding")
		return
	}
	if errors.Is(err, ErrInsufficientFunds) {
		fmt.Println("handled: show the user their balance and ask them to top up")
		return
	}
	if err != nil {
		fmt.Println("unhandled error:", err)
	}
}
```

### Wrapping with `%w` and `errors.As`

`fmt.Errorf("context: %w", err)` wraps an error with additional context while preserving the original as the unwrappable inner cause. The chain is: `outer message → wrapped inner error → ... → sentinel`.

For richer typed errors where you need to extract data, use `errors.As`:

```go
package main

import (
	"errors"
	"fmt"
)

// InsufficientFundsError is a typed error — it carries extra context.
type InsufficientFundsError struct {
	AccountID string
	HaveCents int
	NeedCents int
}

func (e *InsufficientFundsError) Error() string {
	return fmt.Sprintf("account %s: need %d cents, have %d cents",
		e.AccountID, e.NeedCents, e.HaveCents)
}

func debit(id string, db map[string]int, amount int) error {
	balance, ok := db[id]
	if !ok {
		return fmt.Errorf("debit: account %q not found", id)
	}
	if amount > balance {
		// Return the typed error — callers can extract Have/Need
		return fmt.Errorf("debit: %w", &InsufficientFundsError{
			AccountID: id,
			HaveCents: balance,
			NeedCents: amount,
		})
	}
	db[id] = balance - amount
	return nil
}

func main() {
	db := map[string]int{"acct-001": 500}

	err := debit("acct-001", db, 2000)
	if err != nil {
		// errors.As unwraps the chain looking for an *InsufficientFundsError.
		// If found, it assigns it to `ife` — typed, with all its fields.
		var ife *InsufficientFundsError
		if errors.As(err, &ife) {
			fmt.Printf("insufficient funds: account=%s have=%d need=%d\n",
				ife.AccountID, ife.HaveCents, ife.NeedCents)
			// Now you can surface a tailored UI message, log the shortfall, etc.
		} else {
			fmt.Println("other error:", err)
		}
	}
}
```

```go
		if errors.As(err, &ife) {

				ife.AccountID, ife.HaveCents, ife.NeedCents)
		} else {
			fmt.Println("other error:", err)
		}
	}
}
```

## Slices & Maps

Last chapter you used `[]int` and `map[string]int` without looking under the hood. That ends now. These aren't magic — they're data structures with specific costs and specific gotchas, and knowing their internals is the difference between writing fast, correct Go and writing slow, surprising Go.

<Define term="slice (header: pointer / length / capacity)" since="Performance Engineering (Part 2, Chapter 10)">
A **slice** is a three-word header: a **pointer** to an underlying array, a **length** (how many elements are visible), and a **capacity** (how many the array can hold before a reallocation). Copying a slice copies the header — both copies share the same backing array until one of them appends past capacity and triggers a fresh allocation. This shared-array aliasing is the source of a whole class of subtle bugs. The full escape-analysis and allocation story is Part 2 Performance Engineering.
</Define>

### The Slice Header: Pointer, Length, Cap

A slice is **three words**: a pointer to the underlying array, a length, and a capacity.

```go
package main

import "fmt"

func main() {
	// make([]int, length, capacity) — allocates an array, returns a slice header
	s := make([]int, 3, 6)

	fmt.Printf("len=%d  cap=%d  ptr=%p\n", len(s), cap(s), s) // len=3 cap=6

	// s holds indices 0..2. The underlying array has room for 6.
	s[0], s[1], s[2] = 100, 200, 300

	// Slice of a slice — new header, same underlying array.
	sub := s[1:3]
	fmt.Printf("sub  len=%d  cap=%d  val=%v\n", len(sub), cap(sub), sub)

	// Modifying sub modifies s — they share the array!
	sub[0] = 999
	fmt.Println("s after modifying sub:", s) // s[1] is now 999
}
```

### Append and the Aliasing Gotcha

`append` adds elements to a slice. When there's room in the underlying array (`len < cap`), it writes in place and returns a new header with `len+1`. When there's no room, it allocates a new, larger array, copies everything over, and returns a header pointing at the new array.

```go
package main

import "fmt"

func main() {
	s := make([]int, 3, 3) // len=3 cap=3 — full
	s[0], s[1], s[2] = 1, 2, 3

	// Append to a full slice: allocates a new array.
	// s2 points to the new array; s still points to the old one.
	s2 := append(s, 4)

	s2[0] = 999 // modifying s2 — does it affect s?
	fmt.Println("s:", s)   // [1 2 3]  — no, different arrays
	fmt.Println("s2:", s2) // [999 2 3 4]

	// BUT: if cap > len, append reuses the array.
	t := make([]int, 3, 6) // len=3 cap=6 — room to grow
	t[0], t[1], t[2] = 1, 2, 3
	t2 := t[:3]      // t2 is a slice of the same array, len=3 cap=6

	t3 := append(t2, 4) // appends in place — no reallocation
	t3[0] = 999          // now modifies the shared array!
	fmt.Println("t:", t)   // [999 2 3] — t[0] changed because t3 shares its array
	fmt.Println("t3:", t3) // [999 2 3 4]
}
```

<UnderTheHood title="Slice internals: the header, growth, and escape analysis (Go 1.26+)">

A slice value is three machine words: a pointer to the backing array, a length (`int`), and a capacity (`int`). The old `reflect.SliceHeader` type exposed these as `Data uintptr`, `Len int`, `Cap int`, but it was deprecated in Go 1.20 for most direct use. The safe way to get the data pointer is `unsafe.SliceData`; use the built-in `len` and `cap` for the other two fields. Conceptually the layout is unchanged: the data pointer addresses the first element when capacity is nonzero.

**Growth strategy (Go 1.18+ — changed from Go 1.17 and earlier):** Current Go doubles capacity for small slices, then transitions smoothly toward ~1.25x growth for larger slices. If the requested new length is already bigger than double the old capacity, the runtime uses the requested length. The exact formula is in `runtime/slice.go` — the point is that growth is amortized O(1) for append but individual calls that trigger reallocation are O(n).

**Stack vs. heap:** Small slices with a known compile-time length may live entirely on the stack — the compiler's escape analysis decides. A slice passed to another goroutine, returned from a function, or whose length is unknown at compile time escapes to the heap. `go build -gcflags="-m"` shows the escape analysis decisions. We go very deep on escape analysis in the Part 2 performance chapter.

**The three-index slice `s[low:high:max]`:** sets the capacity of the returned slice to `max-low`. Use this to prevent unintentional aliasing — any append to the sub-slice beyond `max` will allocate a fresh array instead of writing into the parent's space.

**`copy` builtin:** `copy(dst, src)` is the idiomatic way to get a fully independent slice. It returns the number of elements copied (min of the two lengths) and never panics. Memory allocation is your responsibility — `dst` must already be the right length.

</UnderTheHood>

### Maps: Swiss Tables and Unspecified Iteration

<Define term="map" since="Concurrency: Goroutines, Channels & Select (Part 1, Chapter 4)">
A **map** is Go's built-in hash table: `map[KeyType]ValueType`. Under the hood, as of Go 1.24, the standard runtime uses a Swiss Table-style implementation with groups of eight key-value slots and control bytes for fast probing. Two things that trip beginners: (1) accessing a missing key returns the zero value silently — always use the comma-ok idiom to distinguish "key absent" from "key present with zero value"; and (2) maps are **not safe for concurrent access** — a concurrent write races with any other access, and the runtime often terminates the program when it detects map misuse. Concurrent map patterns are covered in the Concurrency chapter.
</Define>

A map in Go is a hash table. As of Go 1.24's standard runtime, it is backed by a Swiss Table-style structure: groups of eight slots plus a control word, probed by hash fragments rather than by linked-list chaining.

### The Comma-Ok Idiom

Accessing a map key that doesn't exist returns the zero value for the value type — not a panic, not an error. That means `balances["acct-999"]` returns `0` silently. To distinguish "key exists with value 0" from "key doesn't exist," use the **comma-ok** idiom:

```go
package main

import "fmt"

func main() {
	balances := map[string]int{
		"acct-001": 250000,
		"acct-002": 0, // legitimately zero balance
	}

	// Without comma-ok: can't tell zero-value from missing
	b := balances["acct-002"]
	fmt.Println("acct-002 naive:", b) // 0 — is this zero balance or missing?

	// With comma-ok: two values — the value AND a bool indicating existence
	b2, ok := balances["acct-002"]
	fmt.Printf("acct-002: val=%d  exists=%v\n", b2, ok) // val=0 exists=true

	b3, ok := balances["acct-999"]
	fmt.Printf("acct-999: val=%d  exists=%v\n", b3, ok) // val=0 exists=false
}
```

<UnderTheHood title="Map internals: Swiss tables, growth, and unspecified iteration (Go 1.26+)">

As of Go 1.24, the standard runtime map design is based on Swiss Tables. Internally, it uses:
- **Slots**: storage locations for key-value pairs.
- **Groups**: eight slots plus a control word.
- **Control bytes**: metadata that says whether a slot is empty/deleted/used and stores hash bits for fast rejection.
- **Tables/directories**: runtime structures that select and grow storage as the map changes.
- A per-map hash seed used by the runtime's probing and iteration behavior.

**How a lookup works:** hash the key, use hash bits to choose the table/group probe path, compare the group's control bytes first, then compare full keys only for plausible matches. The useful mental model is still "hash → small group scan → possible probe," not linked-list chaining.

**Growth:** when the table becomes too full for efficient probing, the runtime grows or splits internal storage and spreads the cost across later operations. Treat the exact load thresholds as implementation details, not language guarantees.

**Why iteration order is unsafe to depend on:** the Go spec says map iteration order is **not specified**. The runtime also deliberately varies iteration order so programs that accidentally depend on order fail early. Programs that depend on order are buggy by spec.

**Maps are not safe for concurrent use.** Concurrent reads are fine only when there are no concurrent writes. Concurrent writes, or a concurrent read and write, are data races; the runtime often detects map misuse and terminates the process with a fatal error, but you must not rely on detection for correctness. For concurrent maps, use `sync.RWMutex` or `sync.Map`. This is the Part 1 Chapter 4 Concurrency chapter's territory — just know the footgun exists.

</UnderTheHood>

```go
			fmt.Println("graceful: account does not exist, prompting registration")
		} else {
			fmt.Println("unexpected error:", err)
		}
	}

	acc, err := LookupAccount("acct-001", db)
	if err != nil {
		fmt.Println("error:", err)
		return
	}
	fmt.Printf("found: %s balance $%d.%02d\n",
		acc.ID, acc.Balance/100, acc.Balance%100)
}
```

`errors.Is` unwraps the `fmt.Errorf` chain and finds `ErrAccountNotFound` at the bottom. The `==` check would fail because the outer error is the wrapped `"lookup acct-999: ..."` value.

</Solution>

</Exercise>

<Exercise n={5} title="Slice append aliasing" level="hard">

Create a slice `ledger` of five `int` values (transaction amounts in cents). Take a sub-slice `recent := ledger[3:]` (the last two transactions). Append a new transaction to `recent`. Show — with printed pointer addresses and lengths — whether `recent`'s append wrote into `ledger`'s backing array or triggered a reallocation. Then repeat with `ledger` originally created as `make([]int, 5, 5)` (cap exactly 5) and explain the difference.

<Solution>

```go
package main

import (
	"fmt"
	"unsafe"
)

func main() {
	// Case 1: literal slice — len=cap=5, no room beyond index 4
	ledger1 := []int{100, 200, 300, 400, 500}
	recent1 := ledger1[3:] // len=2, cap=2 (cap of parent minus start offset = 5-3=2)
	fmt.Printf("Case 1 BEFORE: ledger1 ptr=%p len=%d cap=%d\n",
		unsafe.SliceData(ledger1), len(ledger1), cap(ledger1))
	fmt.Printf("Case 1 BEFORE: recent1 ptr=%p len=%d cap=%d\n",
		unsafe.SliceData(recent1), len(recent1), cap(recent1))

	recent1 = append(recent1, 600) // cap exceeded → new allocation
	fmt.Printf("Case 1 AFTER:  recent1 ptr=%p len=%d cap=%d val=%v\n",
		unsafe.SliceData(recent1), len(recent1), cap(recent1), recent1)
	fmt.Println("ledger1 unchanged:", ledger1)

	fmt.Println()

	// Case 2: make with extra capacity — cap=8, room to grow
	ledger2 := make([]int, 5, 8)
	ledger2[0], ledger2[1], ledger2[2], ledger2[3], ledger2[4] = 100, 200, 300, 400, 500
	recent2 := ledger2[3:5:5] // three-index: cap pinned to 5-3=2, same as Case 1

	fmt.Printf("Case 2 BEFORE: ledger2 ptr=%p len=%d cap=%d\n",
		unsafe.SliceData(ledger2), len(ledger2), cap(ledger2))
	fmt.Printf("Case 2 BEFORE: recent2 ptr=%p len=%d cap=%d\n",
		unsafe.SliceData(recent2), len(recent2), cap(recent2))

	recent2 = append(recent2, 600) // cap=2, exceeded → new array (three-index saved us)
	recent2[0] = 999                // write into new array
	fmt.Printf("Case 2 AFTER:  recent2 ptr=%p len=%d val=%v\n",
		unsafe.SliceData(recent2), len(recent2), recent2)
	fmt.Println("ledger2 unchanged:", ledger2) // three-index prevented aliasing
}
```

Case 1: `ledger1` has `cap=5`, so `recent1 = ledger1[3:]` has `cap=2`. `append` exceeds it and reallocates. Safe. Case 2 with no three-index: `ledger2[3:]` would have `cap=5` (using the parent's remaining cap), and appending would write into `ledger2[5]` — inside the backing array but past len. The **three-index slice** `[3:5:5]` caps it at 2, matching Case 1 and guaranteeing a fresh allocation on append. Always use the three-index form when you need aliasing isolation.

</Solution>

</Exercise>

<Recap>

Five pillars. All yours now.

- **Structs** are named collections of typed fields. Use composite literals with named fields always. Zero values are valid and useful by design. Embedding is composition — not inheritance; fields and methods are promoted at compile time with no runtime overhead.
- **Methods** bind behavior to types. Value receivers get a copy; pointer receivers get the address and can mutate. Be consistent within a type. The full method-set rules and data-semantics story are in Data Semantics & Data-Oriented Design.
- **Interfaces** in Go are defined by the **consumer**, not the producer. Satisfaction is implicit — any type with the right methods qualifies, no declaration needed. This decouples packages, enables small interfaces, and lets third-party types plug in for free. The interface value is two words (itab + data); a nil pointer in a non-nil interface is the source of the nil-interface trap.
- **Errors** are the `error` interface — `Error() string`. Create them with `errors.New` or `fmt.Errorf`. Wrap with `%w` to preserve the chain. Use `errors.Is` for sentinel comparison, `errors.As` for typed extraction (Go 1.26 adds the generic `errors.AsType[T]` shorthand). Never discard errors with `_`. The full error-at-scale treatment is Part 2.
- **Slices** are three-word headers (ptr/len/cap). `append` reuses the backing array if there's capacity, reallocates if there isn't. Sub-slices share the backing array. Always use the returned value from `append`. **Maps** are hash tables with unspecified iteration order. Use comma-ok to distinguish missing keys from zero values. Maps are not safe for concurrent use.

</Recap>
