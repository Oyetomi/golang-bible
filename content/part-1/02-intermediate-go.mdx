## Structs

*Stop 1 of 5.*

### Step 1: one type for things that belong together

An account has an ID, an owner and a balance. Passing three loose values to every function invites mixing them up. A **struct** groups them into one value:

```go
// Account is one customer's bank account.
type Account struct {
	ID      string
	Owner   string
	Balance int // cents, never a float (ch1)
}
```

**Reading tip:** `type Account struct { … }` reads "declare a new type named `Account`, which is a struct with these fields". Each field is name then type, like variables.

<Define term="struct">
A type made of named, typed **fields** stored together in one value. Assigning or passing a struct copies all of its fields (ch3 is about when that's what you want).
</Define>

You create one with a **composite literal**, and reach fields with a dot:

<GoPlayground>

```go
package main

import "fmt"

type Account struct {
	ID      string
	Owner   string
	Balance int // cents
}

func main() {
	acc := Account{
		ID:      "acct-001",
		Owner:   "Alex Rivera",
		Balance: 250000, // $2,500.00
	}

	fmt.Printf("%+v\n", acc) // %+v prints field names too
	fmt.Printf("Owner: %s, Balance: $%d.%02d\n", acc.Owner, acc.Balance/100, acc.Balance%100)
}
```

</GoPlayground>

```text
{ID:acct-001 Owner:Alex Rivera Balance:250000}
Owner: Alex Rivera, Balance: $2500.00
```

### Step 2: named or positional literals?

You can also write `Account{"acct-001", "Alex Rivera", 250000}`, listing values in field order. The two forms fail differently when the struct changes:

| Change to the struct | Named literal `Account{ID: …, Owner: …}` | Positional literal `Account{"a", "b", 1}` |
|---|---|---|
| A field is added | Compiles; the new field is left at its zero value | Compile error: `too few values in struct literal` |
| Two same-typed fields are swapped (`ID`, `Owner`) | Still correct | Compiles, and **silently swaps the values** |
| Fields are renamed | Compile error at every use | Compiles, possibly wrong |

Named literals are the norm, because silent swaps are the worse failure. The price is that adding a field won't force you to visit every literal; if a new field must always be set, give the type a constructor function.

### Step 3: the zero value is a usable account

<GoPlayground>

```go
package main

import "fmt"

type Account struct {
	ID      string
	Owner   string
	Balance int
}

func main() {
	var draft Account // every field at its zero value
	fmt.Printf("zero:  %+v\n", draft)

	draft.ID = "acct-002"
	draft.Owner = "Sam Chen"
	fmt.Printf("ready: %+v\n", draft) // Balance 0 is right for a new account
}
```

</GoPlayground>

```text
zero:  {ID: Owner: Balance:0}
ready: {ID:acct-002 Owner:Sam Chen Balance:0}
```

When you design a struct, ask: does the all-zero value make sense? If it does, users can just declare one. If it doesn't (say, it needs a map that must be made), provide a `NewAccount(…)` function.

<Callout kind="tip" title="Go 1.26: new(value) for optional pointer fields">

A pointer field is a common way to say "optional": `nil` means "not provided". Since Go 1.26, `new` accepts a value, so filling one no longer needs a temporary variable:

```go
type Profile struct {
	Name string
	Age  *int // nil means "not provided"
}

p := Profile{Name: "Alex Rivera", Age: new(34)} // *int pointing at 34
```

</Callout>

### Step 4: embedding, not inheritance

Go has no classes and no inheritance. To reuse fields and methods, you **embed** one struct in another by listing its type without a field name:

<GoPlayground>

```go
package main

import (
	"fmt"
	"unsafe"
)

type AuditInfo struct {
	CreatedBy string
	UpdatedBy string
}

type Account struct {
	AuditInfo // embedded: no field name, just the type
	ID        string
	Owner     string
	Balance   int
}

func main() {
	acc := Account{
		AuditInfo: AuditInfo{CreatedBy: "system", UpdatedBy: "system"},
		ID:        "acct-003",
		Owner:     "Jordan Kim",
	}
	fmt.Println(acc.CreatedBy)           // promoted: as if it were Account's own field
	fmt.Println(acc.AuditInfo.CreatedBy) // the long form, same field

	fmt.Println("size:", unsafe.Sizeof(acc),
		"| CreatedBy at", unsafe.Offsetof(acc.CreatedBy),
		"| ID at", unsafe.Offsetof(acc.ID),
		"| Balance at", unsafe.Offsetof(acc.Balance))
}
```

</GoPlayground>

```text
system
system
size: 72 | CreatedBy at 0 | ID at 32 | Balance at 64
```

The last line is the real layout on a 64-bit machine. The embedded `AuditInfo` isn't a separate object somewhere else: its two strings are the first 32 bytes of the `Account` itself.

**Recap.** A struct groups named fields into one value. Prefer named literals (positional ones can silently swap same-typed fields). Zero-value structs should be usable. Embedding places one struct inside another and promotes its fields and methods at compile time.

## Methods

*Stop 2 of 5.*

### Step 1: a function with a receiver

A **method** is a function attached to a type. The extra parameter before the name, the **receiver**, says which type:

```go
func (a Account) Summary() string {
//   ^^^^^^^^^^ receiver: this method belongs to Account, and calls it "a"
	return fmt.Sprintf("[%s] %s: $%d.%02d", a.ID, a.Owner, a.Balance/100, a.Balance%100)
}
```

You call it with a dot: `acc.Summary()`.

### Step 2: copy or address?

The receiver is a parameter, and Go passes parameters by **copy**. So the question every method answers is: does it get a copy of the struct, or its address?

<Define term="value receiver vs pointer receiver">
`func (a Account) …` has a **value receiver**: the method gets a copy, and changes to it are lost. `func (a *Account) …` has a **pointer receiver**: the method gets the struct's address (`*Account` is "pointer to Account"), and changes go to the caller's struct.
</Define>

<Define term="pointer" since="Data Semantics (ch3)">
A value holding the memory address of another value. `&acc` is a pointer to `acc`, of type `*Account`. Writing through it changes the one real `acc`. The zero value is `nil`, pointing at nothing. ch3 covers when to share with pointers and when to copy.
</Define>

Here's the bug that a value receiver causes, next to the fix:

<GoPlayground>

```go
package main

import "fmt"

type Account struct{ Balance int }

func (a Account) DepositBroken(n int) { a.Balance += n } // value receiver: changes a copy
func (a *Account) Deposit(n int)      { a.Balance += n } // pointer receiver: changes the original

func main() {
	acc := Account{Balance: 1000}

	acc.DepositBroken(500)
	fmt.Println("after DepositBroken:", acc.Balance)

	acc.Deposit(500) // Go passes &acc for you, because acc is a variable
	fmt.Println("after Deposit:      ", acc.Balance)
}
```

</GoPlayground>

```text
after DepositBroken: 1000
after Deposit:       1500
```

```go
package main

import (
	"errors"
	"fmt"
)

type Account struct {
	ID      string
	Owner   string
	Balance int
}

func (a Account) Summary() string {
	return fmt.Sprintf("[%s] %s: $%d.%02d", a.ID, a.Owner, a.Balance/100, a.Balance%100)
}

func (a *Account) Deposit(amountCents int) error {
	if amountCents <= 0 {
		return errors.New("deposit amount must be positive")
	}
	a.Balance += amountCents
	return nil
}

func (a *Account) Withdraw(amountCents int) error {
	if amountCents <= 0 {
		return errors.New("withdrawal amount must be positive")
	}
	if amountCents > a.Balance {
		return fmt.Errorf("insufficient funds: have %d cents, need %d", a.Balance, amountCents)
	}
	a.Balance -= amountCents
	return nil
}

func main() {
	acc := Account{ID: "acct-001", Owner: "Alex Rivera", Balance: 250000}
	fmt.Println("before:          ", acc.Summary())
	if err := acc.Deposit(50000); err != nil {
		fmt.Println("deposit error:", err)
	}
	fmt.Println("after deposit:   ", acc.Summary())
	if err := acc.Withdraw(10000); err != nil {
		fmt.Println("withdraw error:", err)
	}
	fmt.Println("after withdrawal:", acc.Summary())
	if err := acc.Withdraw(1_000_000); err != nil {
		fmt.Println("withdraw error:", err)
	}
}
```

### Step 4: two rules and a compile error

**Choose a pointer receiver** when the method changes the receiver, or when the struct is large enough that copying it on every call is wasteful. **Be consistent**: if some methods of a type need pointers, give them all pointer receivers, so the type has one clear way to be used.

<Define term="method set">
The methods callable on a value, which is what the compiler checks when you assign it to an interface. The method set of `Account` has only its value-receiver methods; the method set of `*Account` has both. So only `*Account` satisfies an interface requiring `Deposit` (Stop 3 relies on this).
</Define>

The convenience of "Go takes the address for you" only works when there *is* an address. A value stored in a map has none you can take, because the map may move it:

```go
m := map[string]Account{"a": {}}
m["a"].Deposit(5)     // cannot call pointer method Deposit on Account
m["a"].Balance = 3    // cannot assign to struct field m["a"].Balance in map
```

The fix is to store pointers (`map[string]*Account`), or to copy out, change, and store back.

<QuickCheck
  question="An Account has a Deposit method that increases Balance. Which receiver must it use?"

/>

**Recap.** A method is a function with a receiver. Value receivers get a copy; pointer receivers get the address and can change the original. Go takes a variable's address automatically, but not a map element's. Keep a type's receivers consistent.

## Interfaces

This is the section that separates Go engineers who *get it* from the ones still writing Java in a Go-shaped box. It's also the one people rush, so we won't. *Stop 3 of 5.*

Here's the route through this stop, one idea per step. If you lose the thread, come back to this list:

1. **What an interface is.** A list of methods, and any type that has those methods fits. You never declare that it fits.
2. **Who writes the interface.** The code that *uses* the behavior, not the code that provides it.
3. **What an interface variable holds.** A box with two slots: *which type* is inside, and *the value itself*. **Everything after this depends on this picture.**
4. **`any`.** The interface with no methods, so every type fits.
5. **The nil trap.** What `== nil` asks about that box, and how a nil pointer can go in and leave the box non-nil.
6. **Under the hood.** The real memory layout and what a method call costs.

<Define term="interface (consumer-defined)" since="Idiomatic Go & the Go Mindset (Part 2, Chapter 1)">
An **interface** is a set of method signatures. In Go, satisfaction is **implicit**: any type that has the right methods satisfies the interface — no `implements` keyword, no declaration at the type site. Crucially, the **consumer** (the package that needs the behavior) defines the interface, not the producer (the package that provides the concrete type). This keeps packages decoupled and interfaces small. A `Ledger` interface defined in the payment service contains only the methods that service actually calls — the Postgres implementation satisfies it for free without importing or knowing about the interface.
</Define>

### The Consumer Defines the Interface

*Steps 1 and 2 of 6.*

In most languages, the *producer* declares the interface: `class Account implements IAccount { ... }`. The type author announces what contracts it satisfies.

Go flips this on its head. **The consumer defines the interface.** If your `PaymentProcessor` package needs something that can post a debit, you write that interface in *your* package. Any type from anywhere — even packages you don't own — that has a `PostDebit` method with the right signature automatically satisfies it. No declaration. No `implements` keyword. No coupling between packages.

This is called **implicit interface satisfaction**, and it is the single most powerful design mechanism in Go.

<BeforeAfter
  badLabel="Producer-declared (not Go)"
  goodLabel="Consumer-defined (Go way)"
  bad={`// In the account package — producer decides the contract.
type IAccount interface {
    Deposit(int) error
    Withdraw(int) error
    Summary() string
}

// Account declares it satisfies IAccount.
// This couples the type to the interface at definition time.
type Account struct { ... }
func (a *Account) Deposit(n int) error  { ... }
func (a *Account) Withdraw(n int) error { ... }
func (a *Account) Summary() string      { ... }`}
  good={`// In the ledger package — the CONSUMER defines exactly what it needs.
// It doesn't import the account package at all.
type Debitable interface {
    Withdraw(amountCents int) error
}

// Any type with a matching Withdraw method satisfies Debitable.
// The account package doesn't need to know this interface exists.
func (l *Ledger) PostDebit(src Debitable, amountCents int) error {
    return src.Withdraw(amountCents)
}`}
/>

Why does this matter? Because:

1. **It decouples packages.** The `ledger` package doesn't import `account`. You can swap in any type that satisfies the interface — a real `Account`, a test double, a mock, a different implementation entirely.
2. **Small interfaces.** Because you define the interface where you use it, you define only what you need. The `Debitable` interface above has one method. That's intentional.
3. **Retroactive satisfaction.** You can make a third-party type satisfy your interface without touching its source. If `database/sql.Tx` happens to have the methods you need, it satisfies your interface for free.

### Implicit Satisfaction in Practice

Let's build the `Ledger` scenario end to end:

<GoPlayground>

```go
package main

import (
	"errors"
	"fmt"
)

// --- account package (inline for the example) ---

type Account struct {
	ID      string
	Owner   string
	Balance int
}

func (a Account) Summary() string {
	return fmt.Sprintf("[%s] %s: $%d.%02d",
		a.ID, a.Owner, a.Balance/100, a.Balance%100)
}

func (a *Account) Deposit(amountCents int) error {
	if amountCents <= 0 {
		return errors.New("deposit amount must be positive")
	}
	a.Balance += amountCents
	return nil
}

func (a *Account) Withdraw(amountCents int) error {
	if amountCents <= 0 {
		return errors.New("withdrawal amount must be positive")
	}
	if amountCents > a.Balance {
		return fmt.Errorf("insufficient funds: have %d cents, need %d", a.Balance, amountCents)
	}
	a.Balance -= amountCents
	return nil
}

// --- ledger package (inline for the example) ---

// Debitable is defined HERE, by the consumer of the behavior.
// It says: "I need something I can call Withdraw on."
type Debitable interface {
	Withdraw(amountCents int) error
}

// Creditable is defined HERE too.
type Creditable interface {
	Deposit(amountCents int) error
}

// PostTransfer moves money from src to dst.
// It doesn't care about Account specifically — it cares about the contract.
func PostTransfer(src Debitable, dst Creditable, amountCents int) error {
	if err := src.Withdraw(amountCents); err != nil {
		return fmt.Errorf("debit failed: %w", err)
	}
	if err := dst.Deposit(amountCents); err != nil {
		// In real fintech you'd need to reverse the debit here.
		// That's the saga pattern — Part 3. Note it, don't ignore it.
		return fmt.Errorf("credit failed: %w", err)
	}
	return nil
}

func main() {
	alice := &Account{ID: "acct-001", Owner: "Alice", Balance: 500000}
	bob := &Account{ID: "acct-002", Owner: "Bob", Balance: 100000}

	fmt.Println("before:", alice.Summary(), "|", bob.Summary())

	// *Account satisfies both Debitable and Creditable — implicitly.
	// No `implements` declaration anywhere.
	if err := PostTransfer(alice, bob, 50000); err != nil {
		fmt.Println("transfer error:", err)
		return
	}

	fmt.Println("after:", alice.Summary(), "|", bob.Summary())
}
```

</GoPlayground>

### What an Interface Variable Actually Holds

*Step 3 of 6.* Slow down here. This is the picture everything else depends on, and the nil trap in step 5 is confusing only if you skip it.

When you write `var d Debitable`, what is `d`? It isn't an `Account`, and it can't be, because `d` must be able to hold *any* type with a `Withdraw` method: an `*Account` today, a test fake tomorrow, a `*sql.Tx` wrapper next week. Those types have different sizes and different `Withdraw` code. So Go can't store the value in `d` and forget about it. `d` must also remember **what kind of thing it's holding**, or it won't know *which* `Withdraw` to run when you call `d.Withdraw(...)`.

So an interface variable is a **box with two slots**:

<Define term="dynamic type / dynamic value">
An interface variable holds two things. Its **dynamic type** is the concrete type currently stored in it (for example `*Account`). Its **dynamic value** is the value of that type (for example the pointer to Alice's account). They're called *dynamic* because they change at runtime every time you assign something new. The interface's own **static type** (`Debitable`) never changes; it only decides *what's allowed in*.
</Define>

| Slot | Answers the question | Example after `d = alice` |
|---|---|---|
| **type** | "What kind of thing is in here, and so which methods do I call?" | `*Account` |
| **value** | "Which actual thing is it?" | the pointer to Alice's account |

Take it one line at a time. Step through the animation and watch both slots:

### The Empty Interface and `any`

*Step 4 of 6.* With the two-slot box in mind, `any` is easy: it's a box that accepts every type, because it requires no methods.

<Define term="any (the empty interface)">
`any` is an alias for `interface{}` — an interface with **zero** methods. Because every type in Go has at least zero methods, every type satisfies `any`. It is the escape hatch for genuinely heterogeneous data: JSON decoders, log fields, generic containers in older code. The cost is that all static type information is thrown away — you must recover it at runtime with a type assertion (`v.(int)`, which panics if wrong) or a type switch. Prefer a named interface whenever you can name the behavior you need. `any` is a last resort.
</Define>

`interface{}` — written as `any` since Go 1.18 — is an interface with *zero* methods. Every type in Go satisfies it, because every type has at least zero methods. You'll see it in JSON decoding, generic logging, and old stdlib APIs.

### The Nil-Interface Trap

*Step 5 of 6.* This one bites every Go engineer exactly once, and I'd rather it bite you here than in production at 11pm. We'll do it in four steps: two kinds of nil, the smallest code that shows the trap, *why* Go works this way, and how it gets into real code.

#### Step 1: There are two different "nils"

The word `nil` means different things depending on the variable's type, and that's where the confusion starts.

- A **pointer** is one thing: an address. A nil pointer points at nothing. `p == nil` asks: *"does this pointer point anywhere?"*
- An **interface** is the two-slot box from step 3. `err == nil` asks: *"is this box completely empty?"* It does **not** ask whether the thing inside the box is nil.

<Define term="typed nil">
A **typed nil** is a nil pointer (or nil map, slice, func, or channel) that has been put into an interface. The interface's type slot records the pointer's type, for example `*LookupError`, and its value slot holds the nil pointer. The box isn't empty, because it knows what type it holds, so `== nil` on the interface is `false`, even though the pointer inside is nil.
</Define>

#### Step 2: The smallest code that shows it

Forget functions and error handling for a moment. Here's the whole trap in two lines:


The second line is an **assignment into an interface**, and assigning into an interface always fills the type slot with the type of the thing you assigned. You assigned a `*LookupError`, so the type slot says `*LookupError`, even though that pointer is nil. Step through it:

#### Step 3: Why Go doesn't just treat it as nil

Your first reaction is probably "that's a bug in Go, it should just say nil." It isn't, and seeing why makes the rule easy to remember.

In Go, **you can call a method on a nil pointer.** The method runs, and it's up to the method to handle a nil receiver. That's legal and sometimes useful. Here, a nil `*AuditLog` means "no log yet, zero entries":

```go
func (l *AuditLog) Count() int {
	if l == nil {
		return 0 // a nil log has zero entries, no crash
	}
	return len(l.entries)
}
```

Put a nil `*AuditLog` into a `Counter` interface and call `Count()`. It works and returns `0`, because the type slot tells Go *which* `Count` to run. Now call `Count()` on a truly empty `Counter`. There's no type in the box, so Go has no idea which method to run, and the program panics:

<GoPlayground>

```go

	entries []string
}

func (l *AuditLog) Count() int {
	if l == nil {
		return 0
	}
	return len(l.entries)
}

type Counter interface {
	Count() int
}

func main() {
	var log *AuditLog // nil pointer
	var c Counter = log

	fmt.Println("c == nil:", c == nil)
	fmt.Println("c.Count():", c.Count()) // Go knows which method to run

	var empty Counter // truly empty: no type, no value
	fmt.Println("empty == nil:", empty == nil)
	fmt.Println("empty.Count():", empty.Count()) // no type means no method: panic
}
```

So the two boxes really are different. One can still run methods and the other can't, and `== nil` reports that difference. A box holding a typed nil is a working value. Only an empty box is nil.

There's a second way it gets in: a helper that **returns** the concrete pointer type, whose result you pass straight through:

```go
	if !strings.HasPrefix(id, "acct-") {
```

It's the same mechanism: a `*LookupError` gets assigned into an `error`, and the type slot fills.

**The rule:** a function whose result is an interface (`error` or one of your own) must say **`return nil`** to mean "nothing". Don't return a pointer variable that *happens* to be nil. Also, make your helpers return `error`, not `*MyError`, so there's never a concrete pointer to leak.

<UnderTheHood title="Interface internals: the itab and data words">

*Step 6 of 6.* The "two slots" from step 3 are real. Every interface value is exactly **two machine words**, which the runtime calls `tab` and `data`.

**`tab`**, the type word, is the type slot. For an interface with methods (like `error` or `Debitable`), it points to an **itab** (interface table), which is built once per (interface, concrete type) pair and cached. The itab contains:
- a pointer to the concrete type's **type metadata** (its size, alignment, GC shape, name). This is what `%T` prints.
- the **method table**: function pointers for every method the interface requires, already looked up, so a call doesn't have to search for the method by name.

For the empty interface `any`, there are no methods to look up, so the first word points straight at the type metadata. The runtime calls that layout `eface` and the method-carrying one `iface`. The rules in this section apply the same way to both.

**`data`**, the value word, is the value slot. It usually holds a pointer to the concrete value. A pointer-shaped value (like `*Account`) is stored directly. Other values are generally copied to memory the word points at, which can cost a heap allocation when the value escapes.

Here's the nil trap in terms of those words:

| Scenario | `tab` (type slot) | `data` (value slot) | `iface == nil`? |
|---|---|---|---|
| Bare `nil` assigned / zero value | `nil` | `nil` | `true` |
| Non-nil pointer assigned | `&itab{*Account, ...}` | pointer to Alice | `false` |
| Nil pointer assigned (typed nil) | `&itab{*LookupError, ...}` | `nil` | **`false`: the trap** |

Go never builds an interface with an empty type word and a non-empty data word, so checking `== nil` comes down to checking the type word. That's why the value word being `nil` can't make `err == nil` true.

**Interface dispatch cost:** calling a method through an interface is slightly more expensive than a direct call. The runtime loads the itab, takes the function pointer from its method table, and makes an indirect call, which the compiler usually can't inline. For hot paths called millions of times per second this can matter. `pprof` will tell you when it does, so don't guess.

**Method sets and addressability:** only `*T` (pointer-to-T) has the full method set (both value and pointer receivers). `T` only has the value-receiver methods. This is why `&Account{}` satisfies `Debitable` (which requires a pointer-receiver `Withdraw`) but `Account{}` does not. The Data Semantics & Data-Oriented Design chapter explains why. For now, remember the rule.

</UnderTheHood>

### Step 4: errors that carry data

When a caller needs details (how much was missing?), define an error **type**, and use `errors.As` to find it in the chain and get it back with its fields:

<GoPlayground>

```go
package main

import (
	"errors"
	"fmt"
)

type InsufficientFundsError struct {
	AccountID string
	HaveCents int
	NeedCents int
}

func (e *InsufficientFundsError) Error() string {
	return fmt.Sprintf("account %s: need %d cents, have %d cents", e.AccountID, e.NeedCents, e.HaveCents)
}

func debit(id string, db map[string]int, amount int) error {
	balance := db[id]
	if amount > balance {
		return fmt.Errorf("debit: %w", &InsufficientFundsError{AccountID: id, HaveCents: balance, NeedCents: amount})
	}
	db[id] = balance - amount
	return nil
}

func main() {
	err := debit("acct-001", map[string]int{"acct-001": 500}, 2000)

	var ife *InsufficientFundsError
	if errors.As(err, &ife) { // finds it in the chain and fills ife
		fmt.Println("short by", ife.NeedCents-ife.HaveCents, "cents")
	}

	if e, ok := errors.AsType[*InsufficientFundsError](err); ok { // Go 1.26: same, without the variable
		fmt.Println("account", e.AccountID)
	}
}
```

</GoPlayground>

```text
short by 1500 cents
account acct-001
```

## Slices & Maps

*Stop 5 of 5.*

### Step 1: a slice is a view onto an array

<Define term="slice">
A small value with three fields: a **pointer** to an underlying array, a **length** (how many elements you can see), and a **capacity** (how many the array has room for from that point). Copying or re-slicing a slice copies those three fields; the elements stay where they are, shared.
</Define>

<GoPlayground>

```go
package main

import "fmt"

func main() {
	s := make([]int, 3, 6) // length 3, room for 6
	s[0], s[1], s[2] = 100, 200, 300
	fmt.Println("s:", s, "len", len(s), "cap", cap(s))

	sub := s[1:3] // a new view of the SAME array, starting at s[1]
	fmt.Println("sub:", sub, "len", len(sub), "cap", cap(sub))

	sub[0] = 999 // writes into the shared array
	fmt.Println("s after sub[0] = 999:", s)
}
```

</GoPlayground>

```text
s: [100 200 300] len 3 cap 6
sub: [200 300] len 2 cap 5
s after sub[0] = 999: [100 999 300]
```

`sub` has capacity 5 because the array continues for five slots from where `sub` starts.

### Step 2: what `append` does

`append(s, x)` returns a slice with `x` added. How depends on capacity:

- **Room left (len < cap):** write `x` into the next slot of the *same* array; return a header with length + 1.
- **No room:** allocate a bigger array, copy everything over, add `x`, return a header pointing at the *new* array.

That's why you must always write `s = append(s, x)`: the result may point somewhere else. Growing a slice from empty one element at a time on Go 1.27, the capacities went:

```text
4 8 16 32 64 128 256 512 848 1280 1792 2560
```

Doubling while small, then growing by smaller factors (about 1.25× for large slices), so appends cost amortised constant time without wasting too much memory. The exact numbers depend on element size and the allocator's size classes; don't write code that depends on them.

<UnderTheHood title="Where slices live">

A slice header is three machine words (24 bytes on 64-bit). The array it points to lives on the stack if the compiler can prove it doesn't outlive the function and has a known size; otherwise on the heap. `go build -gcflags=-m` prints those decisions ("escapes to heap"). `unsafe.SliceData(s)` gives the array's address if you ever need to prove two slices share it. Part 2, Chapter 10 covers allocation in depth.

</UnderTheHood>

### Step 4: maps

<Define term="map">
Go's built-in hash table, `map[KeyType]ValueType`. Lookups, inserts and deletes take constant time on average. Since Go 1.24 the runtime uses a "Swiss table" design: slots in groups of eight, with a byte of metadata per slot that lets a lookup skip most comparisons.
</Define>

Three behaviours to know:

**1. A missing key gives the zero value.** Use the **comma-ok** form to tell "absent" from "present and zero":

<GoPlayground>

```go
package main

import (
	"fmt"
	"maps"
	"slices"
)

func main() {
	balances := map[string]int{"acct-003": 0, "acct-001": 250000, "acct-002": 175000}

	b, ok := balances["acct-003"]
	fmt.Println("acct-003:", b, ok) // present, and zero
	b, ok = balances["acct-999"]
	fmt.Println("acct-999:", b, ok) // absent

	// 2. Iteration order is unspecified. For stable output, sort the keys (Go 1.23+):
	for _, id := range slices.Sorted(maps.Keys(balances)) {
		fmt.Println(id, balances[id])
	}
}
```

</GoPlayground>

```text

acct-999: 0 false
acct-001 250000
acct-002 175000
acct-003 0
```

The same `value, ok :=` shape appears in type assertions (`v, ok := x.(T)`) and channel receives (`v, ok := <-ch`).

**3. Maps aren't safe for concurrent use.** Reading from several goroutines is fine; any write at the same time as another access is a data race, and the runtime usually stops the program with `fatal error: concurrent map writes`, which `recover` can't catch. ch4 shows the fixes (a mutex, or `sync.Map`).

<QuickCheck
  question={'balances := map[string]int{"acct-002": 0}. What does balances["acct-999"] return?'}
  options={["An error", "0, the same as for acct-002: only the comma-ok form tells them apart", "It panics", "nil"]}
  answer={1}
  explain="A lookup of a missing key returns the value type's zero value. v, ok := m[k] adds a bool that says whether the key was there."
/>

**Recap.** A slice is a pointer, length and capacity over a shared array; `append` writes in place when there's room and copies when there isn't, so always keep its result, and use `s[a:b:c]` or a clone to avoid shared writes. Maps return zero for missing keys (use comma-ok), iterate in random order (sort keys), and need a lock for concurrent writes.

```go
package main

import (
	"errors"
	"fmt"
)

type Account struct {
	ID      string
	Balance int
}

func (a *Account) Deposit(n int) error {
	if n <= 0 {
		return errors.New("deposit: must be positive")
	}
	a.Balance += n
	return nil
}

func (a *Account) Withdraw(n int) error {
	if n <= 0 {
		return errors.New("withdraw: must be positive")
	}
	if n > a.Balance {
		return errors.New("withdraw: insufficient funds")
	}
	a.Balance -= n
	return nil

	Withdraw(int) error
```

`ledger := []int{100, 200, 300, 400, 500}` is built with extra capacity (`make([]int, 5, 8)` then filled). A function receives `recent := ledger[3:5]` and appends a transaction. Show that this writes into `ledger`'s array, then fix it two ways.

```go
	"fmt"
	"slices"

	copy(ledger, []int{100, 200, 300, 400, 500})

	recent := ledger[3:5]        // len 2, cap 5
	recent = append(recent, 600) // room: writes into ledger's array at index 5
```

- **Structs** group named fields; prefer named literals (positional ones silently swap same-typed fields). Make zero values useful. **Embedding** puts one struct inside another (CreatedBy at offset 0 of Account) and promotes its fields and methods: composition, not inheritance.
- **Methods** have receivers. Value receivers get a copy (a `Deposit` on one changes nothing); pointer receivers change the original. Go takes a variable's address for you, not a map element's. Keep receivers consistent.
- **Interfaces** are method lists satisfied implicitly and declared by their users. An interface value holds a type and a value; a nil pointer inside makes it non-nil.
- **Errors** are values of the `error` interface. Wrap with `%w`; test with `errors.Is` (sentinels) and `errors.As`/`errors.AsType` (types with fields). `==` misses wrapped errors.
- **Slices** are pointer + length + capacity over a shared array. `append` writes in place when there's room, so keep its result and use `s[a:b:c]` or `slices.Clone` to stop shared writes. **Maps** return zero for missing keys (comma-ok), iterate in random order, and need locking for concurrent writes.

</Recap>
