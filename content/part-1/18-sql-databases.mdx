## The Pool and the Driver

*Stop 1 of 8.*

### Step 1: why a database connection is expensive

Before your program can send a single query, it has to open a connection to Postgres: a TCP handshake, usually a TLS handshake, then logging in. That's several network round trips, and on the Postgres side each connection is a whole operating-system process with its own memory. Opening one per query would be slow for you and punishing for the database.

So Go keeps connections open and reuses them.

### Step 3: the real pool, runnable

There's no Postgres in the browser sandbox, so this program registers a tiny pretend driver whose every query takes 100 ms. Everything else, the pool, the cap, the waiting, the statistics, is the real `database/sql`.

<GoPlayground>

```go
package main

import (
	"context"
	"database/sql"
	"database/sql/driver"
	"errors"
	"fmt"
	"sync"
	"sync/atomic"
	"time"
)

// A pretend database driver: every "query" just takes 100 ms.
// It exists so the REAL database/sql pool has something to manage.
var dials atomic.Int32

type slowDriver struct{}

func (slowDriver) Open(string) (driver.Conn, error) {
	dials.Add(1) // a real driver would do TCP + TLS + auth here
	return slowConn{}, nil
}

type slowConn struct{}

func (slowConn) ExecContext(ctx context.Context, _ string, _ []driver.NamedValue) (driver.Result, error) {
	select {
	case <-time.After(100 * time.Millisecond):
		return driver.RowsAffected(0), nil
	case <-ctx.Done():
		return nil, ctx.Err()
	}
}
func (slowConn) Prepare(string) (driver.Stmt, error) { return nil, errors.New("not supported") }
func (slowConn) Close() error                        { return nil }
func (slowConn) Begin() (driver.Tx, error)           { return nil, errors.New("not supported") }

func main() {
	sql.Register("slow", slowDriver{})
	db, _ := sql.Open("slow", "")
	defer db.Close()
	fmt.Println("after sql.Open, connections dialled:", dials.Load())

	db.SetMaxOpenConns(3) // at most 3 connections, ever
	db.SetMaxIdleConns(3) // keep all 3 when idle

	// Nine handlers each run one 100 ms query at the same moment.
	start := time.Now()
	var wg sync.WaitGroup
	for range 9 {
		wg.Go(func() { db.ExecContext(context.Background(), "UPDATE ...") })
	}
	wg.Wait()

	s := db.Stats()
	fmt.Println("9 queries took:        ", time.Since(start).Round(50*time.Millisecond))
	fmt.Println("connections dialled:   ", dials.Load())
	fmt.Println("had to wait for a conn:", s.WaitCount)
	fmt.Println("idle in the pool now:  ", s.Idle)
}
```

</GoPlayground>

```text
connections dialled:    3
had to wait for a conn: 6
idle in the pool now:   3
```

Nine 100 ms queries through three connections: three rounds, 300 ms, only three handshakes, and six queries that waited their turn. Against a real Postgres, the same experiment printed the same numbers. `db.Stats()` is worth exporting to your metrics: a climbing `WaitCount` is the first sign the pool is too small or queries are too slow.

### Step 4: the knobs

<Define term="database/sql (the standard DB interface)">
`database/sql` is Go's standard package for relational databases. It defines one API (`*sql.DB`, `*sql.Rows`, `*sql.Tx`) that works with any registered driver: Postgres, MySQL, SQLite. `*sql.DB` is not a connection but a **pool** of them, safe to share between goroutines. Open it once per database per process.
</Define>

| Setting | Default | What it does | A starting point |
|---|---|---|---|
| `SetMaxOpenConns(n)` | 0 = **unlimited** | Hard cap on connections, busy + idle | Postgres `max_connections` ÷ app replicas, minus headroom |
| `SetMaxIdleConns(n)` | 2 | How many to keep open while idle | Roughly your normal concurrency |
| `SetConnMaxLifetime(d)` | 0 = forever | Retire a connection this long after it was opened | 5–30 min, so failovers and config changes get picked up |
| `SetConnMaxIdleTime(d)` | 0 = forever | Close a connection idle this long | Below any load balancer or firewall idle timeout |

The unlimited default on `MaxOpenConns` is the trap. Under a spike, every waiting goroutine opens its own connection until Postgres refuses new ones (`too many connections`), and then *every* request fails, not just the extra ones. Set the cap before the first query.

<Gotcha>With 10 app replicas and `SetMaxOpenConns(25)` each, you can open 250 connections. Postgres's default `max_connections` is 100. Do the multiplication before you deploy; many teams put a pooler such as PgBouncer in front when the math doesn't work.</Gotcha>

```go noverify
package main

import (
	"context"
	"database/sql"
	"fmt"
	"log"
	"time"

	_ "github.com/jackc/pgx/v5/stdlib" // registers the "pgx" driver
)

func main() {
	// Parses the connection string and builds the pool. Dials nothing.
	db, err := sql.Open("pgx", "postgres://ledger:secret@localhost:5432/ledger")
	if err != nil {
		log.Fatal(err)
	}
	defer db.Close()

	db.SetMaxOpenConns(25)
	db.SetMaxIdleConns(10)
	db.SetConnMaxLifetime(30 * time.Minute)
	db.SetConnMaxIdleTime(5 * time.Minute)

	ctx, cancel := context.WithTimeout(context.Background(), 3*time.Second)
	defer cancel()
	if err := db.PingContext(ctx); err != nil {
		log.Fatalf("cannot reach database: %v", err)
	}
	fmt.Println("pool ready")
}
```

</CodeWalk>

Pointed at a port where nothing listens, `sql.Open` returned `nil`, and `PingContext` returned `dial tcp 127.0.0.1:1: connect: connection refused`. That's the whole reason to ping.

### Step 6: the driver

<Define term="Driver (pgx)">
A **driver** implements the `database/sql/driver` interfaces for one database's wire protocol. `database/sql` does the pooling and the API; the driver does the talking. For Postgres, `pgx` (`github.com/jackc/pgx/v5`) is the usual choice today.
</Define>

`pgx` can be used two ways:

```go noverify
// 1. Behind database/sql: the standard *sql.DB API, driver name "pgx".
import _ "github.com/jackc/pgx/v5/stdlib"

db, err := sql.Open("pgx", connString)

// 2. Directly, with pgx's own pool and API.
import "github.com/jackc/pgx/v5/pgxpool"

pool, err := pgxpool.New(ctx, connString) // sizes come from pgxpool.Config or the URL
```

<ConceptGrid cols={3}>
  <ConceptCard label="Binary protocol">pgx exchanges most types in Postgres's binary format (integers, timestamps, UUIDs), skipping text parsing and formatting.</ConceptCard>
  <ConceptCard label="Statement cache">pgx prepares each distinct SQL string once per connection and reuses the plan afterwards, automatically.</ConceptCard>
  <ConceptCard label="Postgres types">UUIDs, `jsonb`, arrays, ranges and composite types map to Go types. A Go slice can be passed straight to `= ANY($1)`.</ConceptCard>
  <ConceptCard label="COPY">`CopyFrom` bulk-loads rows with Postgres's COPY protocol, far faster than many INSERTs.</ConceptCard>
  <ConceptCard label="pgxpool">pgx's own pool adds a minimum connection count, health checks and per-connection setup hooks, which `sql.DB` doesn't have.</ConceptCard>
  <ConceptCard label="lib/pq">The older pure-`database/sql` driver. It spent years in maintenance mode and has since resumed releases; it's fine in existing code. New services usually pick pgx for the features above.</ConceptCard>
</ConceptGrid>

This chapter uses the `database/sql` API, because it's what you'll meet in most codebases and it works with any driver. Where pgx changes something, I'll say so.

**Recap.** `sql.DB` is a pool: open it once, cap it with `SetMaxOpenConns`, and `PingContext` at startup, because `sql.Open` connects to nothing.

## Querying Safely

*Stop 2 of 8.*

Our ledger has two tables:

```sql
CREATE TABLE accounts (
    id            UUID        PRIMARY KEY DEFAULT gen_random_uuid(),
    owner         TEXT        NOT NULL,
    balance_cents BIGINT      NOT NULL DEFAULT 0,
    currency      CHAR(3)     NOT NULL DEFAULT 'USD',
    created_at    TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE TABLE transactions (
    id           UUID        PRIMARY KEY DEFAULT gen_random_uuid(),
    from_account UUID        REFERENCES accounts(id),
    to_account   UUID        NOT NULL REFERENCES accounts(id),
    amount_cents BIGINT      NOT NULL CHECK (amount_cents > 0),
    note         TEXT,
    created_at   TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```

Money is stored as whole cents in a `BIGINT`, never as a floating-point number, for the same reason as in every earlier chapter: floats can't represent 0.10 exactly.

### Step 1: the three calls

| Call | Returns | Use it for |
|---|---|---|
| `db.QueryContext(ctx, sql, args...)` | `*sql.Rows` | A `SELECT` that can return many rows |
| `db.QueryRowContext(ctx, sql, args...)` | `*sql.Row` | A query that returns at most one row |
| `db.ExecContext(ctx, sql, args...)` | `sql.Result` | `INSERT`, `UPDATE`, `DELETE`: no rows back |

All three take a `context.Context` first. When it's cancelled (the client hung up, a deadline passed), pgx tells Postgres to stop the query and returns the connection. Against real Postgres, `SELECT pg_sleep(5)` with a 200 ms context returned `context deadline exceeded` after 200 ms, and `pg_stat_activity` showed the server had stopped the sleep too.

### Step 2: SQL injection, and why placeholders fix it

<ELI5
  concept="Why placeholders stop SQL injection"
  analogy="Handing over a form and its answers separately, instead of one sentence."
  role="reader"
>

Building a query with `fmt.Sprintf` mixes two different things into one string: your **instructions** and the user's **data**. The database parses the whole string as instructions. If the data contains something that looks like SQL, it becomes SQL.

A placeholder query keeps them apart. The SQL text travels with `$1` in it, and the value travels separately. By the time the value arrives, the statement has already been parsed and its shape is fixed. The value can't become a new clause, because the parser is already finished.

</ELI5>

<Define term="Parameterized query (SQL injection defense)">
A **parameterized query** sends the SQL text (with placeholders `$1`, `$2`, …) and the values separately. The database parses the SQL alone, then binds the values as data. User input can't change the statement's structure, so SQL injection is impossible for anything passed as a parameter. Postgres uses `$1`; MySQL and SQLite use `?`.
</Define>

<BeforeAfter

query := fmt.Sprintf(

Placeholders stand in for **values** only. You can't write `ORDER BY $1` to choose a column or `FROM $1` to choose a table. If a column name really comes from user input, compare it against a fixed allow-list in Go and paste in only the allowed name.

The loop always has the same shape, with three rules:

```go
func FindAccountsByOwner(ctx context.Context, db *sql.DB, owner string) ([]Account, error) {
	rows, err := db.QueryContext(ctx,
		`SELECT id, owner, balance_cents, currency FROM accounts WHERE owner = $1`,
		owner,
	)
	if err != nil {
		return nil, fmt.Errorf("query accounts: %w", err)
	}
	defer rows.Close() // rule 1: always give the connection back

	var accounts []Account
	for rows.Next() {
		var a Account
		// rule 2: one destination per column, in SELECT order
		if err := rows.Scan(&a.ID, &a.Owner, &a.BalanceCents, &a.Currency); err != nil {
			return nil, fmt.Errorf("scan account: %w", err)
		}
		accounts = append(accounts, a)
	}
	// rule 3: Next returns false on errors too; ask why it stopped
	if err := rows.Err(); err != nil {
		return nil, fmt.Errorf("iterate accounts: %w", err)
	}
	return accounts, nil
}
```

`&a.ID` is the address of the struct's field, so `Scan` can write into it. If the number of destinations doesn't match the number of columns, `Scan` returns an error.

### Step 4: one row, or none

`QueryRowContext` is for "at most one row". Its errors are delayed until `Scan`, and "no match" arrives as `sql.ErrNoRows`:

```go
var ErrNotFound = errors.New("account not found")

func BalanceOf(ctx context.Context, db *sql.DB, id string) (int64, error) {
	var cents int64
	err := db.QueryRowContext(ctx,
		`SELECT balance_cents FROM accounts WHERE id = $1`, id,
	).Scan(&cents)
	if errors.Is(err, sql.ErrNoRows) {
		return 0, fmt.Errorf("account %s: %w", id, ErrNotFound)
	}
	if err != nil {
		return 0, fmt.Errorf("balance: %w", err)
	}
	return cents, nil
}
```

Translating `sql.ErrNoRows` into your own `ErrNotFound` keeps `database/sql` out of your callers: an HTTP handler can map `ErrNotFound` to a 404 without importing anything SQL.

### Step 5: NULL

SQL's `NULL` means "no value", and a plain Go `string` or `int64` has no way to say that. Scanning `NULL` into one is an **error**, not a panic and not a zero value. Against Postgres, pgx reported:

```text
sql: Scan error on column index 0, name "text": converting NULL to string is unsupported
```

A `NULL` timestamp into a plain `time.Time` fails the same way. For nullable columns, scan into one of two things:

```go
var note sql.NullString // .Valid is false for NULL; .String holds the text otherwise
var noteP *string       // nil for NULL; points at the text otherwise

err := db.QueryRowContext(ctx,
	`SELECT note, note FROM transactions WHERE id = $1`, txID,
).Scan(&note, &noteP)
```

`sql.Null[T]` (Go 1.22) is the generic version: `sql.Null[time.Time]`, `sql.Null[int64]` and so on, each with `.V` and `.Valid`. Pick one style per codebase and stick to it.

<Callout kind="tip" title="Go 1.26: errors.AsType for driver errors">

Postgres reports constraint violations with a five-character code; `23505` is "unique violation". pgx returns them as `*pgconn.PgError`. Go 1.26 added `errors.AsType`, which finds a wrapped error of a given type in one expression:

```go noverify
if pgErr, ok := errors.AsType[*pgconn.PgError](err); ok && pgErr.Code == "23505" {
	return ErrDuplicate // e.g. that email is already registered
}
```

Before 1.26 you declared `var pgErr *pgconn.PgError` and called `errors.As(err, &pgErr)`. Against Postgres, inserting a duplicate key gave `pgErr.Code == "23505"` and `pgErr.ConstraintName == "uniq_pkey"`.

</Callout>

### Step 1: why two writes need to be one

A transfer is two writes: take 30.00 from Alice, give 30.00 to Bob. If the process dies between them, 30.00 has vanished. No ordering fixes that; there's always a gap.

<ELI5
  concept="What a transaction actually guarantees"
  analogy="A pencil draft that is either inked in full or rubbed out entirely."
  role="reader"
>

Everything between `BeginTx` and `Commit` is a draft. Your transaction sees its own changes; nobody else does, and nothing is permanent. `Commit` makes the whole draft real at once. `Rollback`, or a crash, or a dropped connection, throws the whole draft away. There's no moment when half of it happened.

</ELI5>

### Step 2: the transfer in Go

The idiom: begin, `defer tx.Rollback()`, do the work, `Commit`. Watch line 10: that deferred rollback is the whole safety net.

```go
var ErrInsufficientFunds = errors.New("insufficient funds or no such account")

// TransferFunds moves amountCents from src to dst: all of it, or none of it.
func TransferFunds(ctx context.Context, db *sql.DB, src, dst string, amountCents int64) error {
	tx, err := db.BeginTx(ctx, nil)
	if err != nil {
		return fmt.Errorf("begin: %w", err)
	}
	// If we return before Commit, for any reason, undo everything.
	defer tx.Rollback()

	res, err := tx.ExecContext(ctx,
		`UPDATE accounts SET balance_cents = balance_cents - $1
		 WHERE id = $2 AND balance_cents >= $1`,
		amountCents, src,
	)
	if err != nil {
		return fmt.Errorf("debit: %w", err)
	}
	if n, err := res.RowsAffected(); err != nil || n != 1 {
		return ErrInsufficientFunds
	}

	res, err = tx.ExecContext(ctx,
		`UPDATE accounts SET balance_cents = balance_cents + $1 WHERE id = $2`,
		amountCents, dst,
	)
	if err != nil {
		return fmt.Errorf("credit: %w", err)
	}
	if n, err := res.RowsAffected(); err != nil || n != 1 {
		return fmt.Errorf("credit: no account %s", dst)
	}

	if _, err := tx.ExecContext(ctx,
		`INSERT INTO transactions (from_account, to_account, amount_cents) VALUES ($1, $2, $3)`,
		src, dst, amountCents,
	); err != nil {
		return fmt.Errorf("record: %w", err)
	}
	return tx.Commit()
}
```

<Callout kind="note" title="Isolation levels: a signpost">

`BeginTx(ctx, nil)` uses Postgres's default isolation, **Read Committed**: each statement sees what was committed before it started. Stronger levels (`sql.LevelRepeatableRead`, `sql.LevelSerializable`, passed in `&sql.TxOptions{Isolation: …}`) prevent subtler anomalies at the cost of retries. `SELECT … FOR UPDATE`, optimistic locking and the full story are in Part 3's Transactions & Consistency chapter.

</Callout>

<Define term="Transaction (Tx) — ACID intro" since="Transactions, Consistency & Sagas (Part 3)">
A **transaction** groups statements into one unit. **ACID** names its guarantees: **Atomicity** (all or nothing), **Consistency** (constraints hold before and after), **Isolation** (concurrent transactions don't see each other's uncommitted work), **Durability** (once committed, it survives a crash). In Go: `db.BeginTx`, statements through the returned `*sql.Tx`, then `Commit` or `Rollback`.
</Define>

Keep transactions short. A transaction holds row locks until it ends, so an HTTP call made inside one makes every other writer to those rows wait for that call.

### Step 2: the lock that takes sites down

Most `ALTER TABLE` statements need Postgres's strongest lock, **ACCESS EXCLUSIVE**, which conflicts with everything, even plain `SELECT`s. Usually it's held for a millisecond and nobody notices. The danger is what happens while the ALTER is *waiting* for that lock.

Locks are granted in a queue. If a long-running query is reading `accounts`, the ALTER waits for it, and every query that arrives *after* the ALTER waits behind the ALTER. On the million-row table, a lookup that normally took 0.3 ms waited **2.5 seconds** behind a queued `ALTER TABLE … ADD COLUMN`, a change that itself takes about a millisecond. Press play:

### Step 3: which changes are cheap

What Postgres has to do for a change decides how long it holds that lock. Measured on the million-row `accounts` table (Postgres 14):

| Change | What Postgres does | Measured |
|---|---|---|
| `ADD COLUMN note TEXT` (nullable, no default) | Updates the catalog only | ~1 ms |
| `ADD COLUMN metadata JSONB NOT NULL DEFAULT '{}'` | Constant default: stored once in the catalog (Postgres 11+) | ~1 ms |
| `ADD COLUMN ref UUID DEFAULT gen_random_uuid()` | Volatile default: **rewrites every row** under the exclusive lock | 4.9 s |
| `ALTER COLUMN … SET NOT NULL` | **Scans every row** under the exclusive lock to check | 215 ms here; minutes on big tables |
| `CREATE INDEX` | Blocks writes for the whole build | seconds to hours |
| `CREATE INDEX CONCURRENTLY` | Builds while reads and writes continue | slower, but no blocking |

Two safe replacements for the expensive rows:

```sql
-- NOT NULL without a long exclusive lock (Postgres 12+):
ALTER TABLE accounts ADD CONSTRAINT nickname_not_null
    CHECK (nickname IS NOT NULL) NOT VALID;               -- instant: checks new rows only
ALTER TABLE accounts VALIDATE CONSTRAINT nickname_not_null; -- scans, but reads and writes continue
ALTER TABLE accounts ALTER COLUMN nickname SET NOT NULL;  -- instant: Postgres trusts the valid CHECK
ALTER TABLE accounts DROP CONSTRAINT nickname_not_null;

-- Indexes: never block writes.
CREATE INDEX CONCURRENTLY idx_accounts_owner ON accounts (owner);
```

Measured: the `NOT VALID` step took 3 ms, `VALIDATE` 84 ms (without blocking traffic), and the final `SET NOT NULL` 0.3 ms. One catch: `CREATE INDEX CONCURRENTLY` can't run inside a transaction block, and some migration tools wrap each file in one (goose does, unless the file says `-- +goose NO TRANSACTION`).

### Step 4: expand, migrate, contract

The other half of zero downtime is your own code. During a rolling deploy, old and new versions of your service run **at the same time**, against the same schema. Any change that breaks the old version breaks production for the length of the rollout.

Renaming `balance_cents` to `amount_cents` in one step does exactly that: the moment the rename lands, every old replica's queries fail with `column "balance_cents" does not exist`. Instead, split it into steps that are each safe for whatever code is running:

| Step | Schema | Code | Safe because |
|---|---|---|---|
| 1. Expand | `ADD COLUMN amount_cents BIGINT` (nullable) | unchanged | Old code never mentions the new column |
| 2. Dual-write | unchanged | Deploy v2: writes **both** columns, still reads the old one | v1 and v2 both work with both columns present |
| 3. Backfill | `UPDATE … SET amount_cents = balance_cents` in batches | unchanged | Small batches, each its own short transaction |
| 4. Switch reads | unchanged | Deploy v3: reads the new column, still writes both | Every row now has the new column filled |
| 5. Contract | `SET NOT NULL` (the safe way), later `DROP COLUMN balance_cents` | Deploy v4: stops writing the old column | Nothing reads or writes the old column any more |

The backfill runs as its own job, in batches, so no single statement holds locks for long:

```go
// backfill copies balance_cents into amount_cents, batch rows at a time.
// Each ExecContext is its own short transaction.
func backfill(ctx context.Context, db *sql.DB, batch int) error {
	for {
		res, err := db.ExecContext(ctx, `
			UPDATE accounts SET amount_cents = balance_cents
			WHERE id IN (
				SELECT id FROM accounts WHERE amount_cents IS NULL LIMIT $1
			)`, batch)
		if err != nil {
			return err
		}
		if n, _ := res.RowsAffected(); n == 0 {
			return nil // nothing left to copy
		}
		time.Sleep(50 * time.Millisecond) // leave room for real traffic (and replicas)
	}
}
```

On the million-row table with batches of 20,000, this took 52 batches and about 13 seconds, with the table fully usable throughout.

<Callout kind="warn" title="Never rename or drop a column in one step">

Old replicas are still running while a migration lands. Rename, drop, or change a type in place and they fail immediately. Add first, move the code, then remove, one safe step at a time.

</Callout>

**Recap.** Migrations are numbered files that only go forward. Set `lock_timeout` so a waiting ALTER can't stall the table; prefer the cheap forms of each change; and split breaking changes into expand, dual-write, backfill, switch, contract.

## Data-Access Choice

*Stop 5 of 8.*

You've written queries by hand with `database/sql`. That's always an option. Three popular tools sit on top:

### sqlc: write SQL, get typed Go

`sqlc` reads your schema and your queries, and **generates** Go functions for them before your program is compiled:

```sql
-- queries/accounts.sql
-- name: GetAccount :one
SELECT id, owner, balance_cents, currency FROM accounts
WHERE id = $1;

-- name: ListAccountsByOwner :many
SELECT id, owner, balance_cents, currency FROM accounts
WHERE owner = $1;
```

`sqlc generate` then writes ordinary Go, roughly:

```go noverify
// Generated. Do not edit.
func (q *Queries) GetAccount(ctx context.Context, id uuid.UUID) (Account, error)
func (q *Queries) ListAccountsByOwner(ctx context.Context, owner string) ([]Account, error)
```

Column types come from the schema (`BIGINT` → `int64`, `TEXT` → `string`; a `UUID` becomes `uuid.UUID` or `pgtype.UUID` depending on configuration). Misspell a column and `sqlc generate` fails on your machine, not with a `Scan` error in production.

### sqlx: less boilerplate, checked at run time

`sqlx` extends `database/sql` with scanning into structs by column name:

```go noverify
type Account struct {
	ID           string `db:"id"`
	Owner        string `db:"owner"`
	BalanceCents int64  `db:"balance_cents"`
	Currency     string `db:"currency"`
}

var accounts []Account
err := db.SelectContext(ctx, &accounts,
	`SELECT id, owner, balance_cents, currency FROM accounts WHERE owner = $1`, owner)
```

Mistakes surface when the query runs, and not all of them as errors. A selected column with no matching field is an error (`missing destination name ownr in *[]main.Account`, from a real run). A struct field with no matching column is silently left at its zero value.

### ORMs: GORM, ent

ORMs generate SQL from method calls. They're quick to start with, and they hide the SQL, which is exactly what you need to see when a query is slow or firing a hundred times (Stop 6).

  <ConceptCard label="database/sql">No dependencies, full control, the most typing. Good for a handful of queries.</ConceptCard>
  <ConceptCard label="sqlc">You write SQL; mistakes are caught at generate time; the output is plain readable Go. A strong default for new services.</ConceptCard>

**Recap.** Pick by where you want mistakes caught: sqlc at generate time, sqlx and `database/sql` at run time, ORMs whenever the generated SQL surprises you.

## Performance: EXPLAIN and N+1

### Step 1: what an index is

<Define term="Index (database B-tree)">
An **index** is a separate, sorted structure (usually a B-tree) that maps a column's values to where the matching rows live. A query filtering on that column can walk the tree in a few steps instead of reading the whole table. The price: every INSERT, UPDATE and DELETE also updates the index.
</Define>

### Step 2: reading `EXPLAIN ANALYZE`

`EXPLAIN` shows the plan Postgres chose; `EXPLAIN ANALYZE` also runs it and reports what really happened. Without an index:

```sql
EXPLAIN ANALYZE SELECT id, balance_cents FROM accounts WHERE owner = 'ada';
```

```text
 Gather  (cost=1000.00..16517.45 rows=1 width=24) (actual time=21.653..22.729 rows=3 loops=1)
   Workers Planned: 2
   Workers Launched: 2
   ->  Parallel Seq Scan on accounts  (cost=0.00..15517.35 rows=1 width=24) (actual time=18.327..18.327 rows=1 loops=3)
         Filter: (owner = 'ada'::text)
         Rows Removed by Filter: 333333
 Planning Time: 1.209 ms
 Execution Time: 22.737 ms
```

Read it from the innermost line out:

- **`Parallel Seq Scan on accounts`**: read the whole table, split across workers. "Seq Scan" on a big table in a hot query is the thing to look for.
- **`Filter` / `Rows Removed by Filter: 333333`**: each of the 3 processes (`loops=3`) threw away a third of a million rows.
- **`cost=…`** is the planner's estimate in arbitrary units; **`actual time=…`** is milliseconds. **`rows=1`** estimated vs **`rows=3`** actual: close enough. Estimates wildly off from actuals mean stale statistics (run `ANALYZE`).

Then the fix, as a migration:

```sql
CREATE INDEX CONCURRENTLY idx_accounts_owner ON accounts (owner);
```

```text
 Index Scan using idx_accounts_owner on accounts  (cost=0.42..8.44 rows=1 width=24) (actual time=0.063..0.065 rows=3 loops=1)
   Index Cond: (owner = 'ada'::text)
 Planning Time: 0.338 ms
 Execution Time: 0.356 ms
```

`Index Scan using idx_accounts_owner` with an `Index Cond`: 22.7 ms became 0.36 ms, about 60× faster, and the gap grows with the table. Index the columns your hot queries filter and join on; don't index everything, because each index slows every write.

### Step 3: the N+1 query

<Define term="N+1 query problem">
The **N+1 problem** is fetching a list with one query, then running one more query **per item**: 1 + N round trips. Each round trip pays network latency, so the cost grows with the list even when every query is fast. The fix is one query that fetches everything, with a JOIN or `= ANY($1)`.
</Define>

It hides in innocent-looking loops: load 100 accounts, then ask for each one's transaction count. Press play to compare one courier making 1 + N trips against one making a single trip:

When you already have a list of IDs, pgx lets you pass a Go slice as a Postgres array, so one placeholder covers any number of IDs:

```go
func CountTransactionsFrom(ctx context.Context, db *sql.DB, accountIDs []string) (int, error) {
	var n int
	err := db.QueryRowContext(ctx,
		`SELECT count(*) FROM transactions WHERE from_account = ANY($1)`,
		accountIDs, // a []string becomes a Postgres text[]
	).Scan(&n)
	return n, err
}
```

That's safer and simpler than building `IN ($1, $2, $3, …)` strings by hand, and the SQL text stays the same whatever the list length, so its prepared plan is reused.

<UnderTheHood title="How pgx sends a query (pgx v5)">

By default pgx uses Postgres's **extended protocol** with a per-connection statement cache. The first time a connection sees a SQL string, pgx sends **Parse** (the SQL) and **Describe**, and caches the prepared statement. Every later run of the same SQL on that connection sends only **Bind** (the values) and **Execute**. With 25 connections, each distinct query is prepared at most 25 times, once per connection, then reused.

This is why building SQL strings dynamically hurts twice: it risks injection, and every distinct string is a new cache entry. `= ANY($1)` keeps one string for every list length.

Behind PgBouncer in transaction mode, server-side prepared statements used to break, because consecutive statements could land on different server connections. PgBouncer 1.21+ can track them; with older versions, set pgx's `default_query_exec_mode=exec` or `simple_protocol` in the connection string.

</UnderTheHood>

**Recap.** Read `EXPLAIN ANALYZE` from the inside out; a `Seq Scan` on a big table in a hot path usually wants an index, built `CONCURRENTLY`. A query inside a loop is N+1: replace it with a JOIN or `= ANY($1)`.

## Read Replicas

*Stop 7 of 8.*

### Step 1: scale reads by copying the database

Most traffic is reads. A **read replica** is a second Postgres server that continuously receives the primary's **write-ahead log** (WAL, the ordered record of every change) and replays it, keeping a copy of the data. Writes go to the primary; reads can go to any replica.

```go noverify
type Cluster struct {
	primary  *sql.DB
	replicas []*sql.DB
	next     atomic.Uint64
}

func (c *Cluster) Writer() *sql.DB { return c.primary }

// Reader spreads reads across the replicas in turn.
func (c *Cluster) Reader() *sql.DB {
	if len(c.replicas) == 0 {
		return c.primary
	}
	return c.replicas[c.next.Add(1)%uint64(len(c.replicas))]
}
```

<Define term="Read-after-write anomaly">
A user writes something, then immediately reads from a replica that hasn't received the write yet, and their own change appears missing. Nothing is lost; the read was just served from a copy a few milliseconds behind.
</Define>

### Step 3: fixing it

**Route a user's reads to the primary for a short window after they write.** Remember when each user last wrote, and check it when choosing a pool:

```go noverify
type ReadRouter struct {
	cluster   *Cluster
	mu        sync.Mutex
	lastWrite map[string]time.Time // user ID -> time of their last write
	window    time.Duration        // e.g. 5 * time.Second
}

// RecordWrite notes that userID just wrote. Call it after a successful Commit.
func (r *ReadRouter) RecordWrite(userID string) {
	r.mu.Lock()
	defer r.mu.Unlock()
	r.lastWrite[userID] = time.Now()
}

// DBFor returns the primary if userID wrote recently, otherwise a replica.
func (r *ReadRouter) DBFor(userID string) *sql.DB {
	r.mu.Lock()
	t, ok := r.lastWrite[userID]
	r.mu.Unlock()
	if ok && time.Since(t) < r.window {
		return r.cluster.Writer()
	}
	return r.cluster.Reader()
}
```

This map lives in one process. With several app replicas, a user's next request may land on another instance, so real deployments keep the timestamp in a cookie or in Redis. The map also needs its old entries cleared out, like the Pokedex cache in ch17.

Other options:

- **Measure the lag and choose.** On the primary, `SELECT client_addr, replay_lag FROM pg_stat_replication;` shows how far behind each replica is. Services can skip replicas that are lagging beyond a threshold.
- **Synchronous replication.** With `synchronous_standby_names` configured and `synchronous_commit = remote_apply`, a `COMMIT` waits until a standby has *applied* the change. No lag for that standby, at the cost of a network round trip on every commit. Worth it on some money paths; overkill for most reads.

<Callout kind="warn" title="Replicas and migrations">

Physical replicas receive schema changes through the WAL, so you don't migrate them separately. But lag applies to DDL too: for a moment the primary has the new column and a replica doesn't. With expand-contract (Stop 4) that's harmless, because no code needs the new column until a later deploy. Long-running queries on a replica can also delay replaying the change, and Postgres may cancel them to catch up.

</Callout>

## Document Databases

*Stop 8 of 8.*

You now know relational Go well. The last stop is knowing when **not** to reach for SQL.

<Define term="Document database">
A **document database** (MongoDB is the best known) stores self-contained JSON-like documents, with nested fields and arrays, grouped into **collections**. Documents in one collection needn't share a schema, and related data is usually **embedded** in one document instead of spread across tables and joined.
</Define>

<Define term="BSON">
**BSON** is MongoDB's binary encoding: JSON's model plus extra types such as ObjectId, dates and 64-bit integers. In Go you tag struct fields `bson:"..."` the way you tag them `json:"..."`.
</Define>

### Step 1: the same order, two shapes

<GoPlayground>

```go
package main

import (
	"encoding/json"
	"fmt"
)

// ── Relational shape: normalized across two tables, joined on order_id ──
type OrderRow struct {
	ID       int
	Customer string
}
type ItemRow struct {
	OrderID int
	SKU     string
	Qty     int
}

// ── Document shape: ONE self-contained document, items embedded ──
// (bson tags are how MongoDB's Go driver maps fields — shown here as JSON.)
type OrderDoc struct {
	ID       int        `bson:"_id" json:"_id"`
	Customer string     `bson:"customer" json:"customer"`
	Items    []LineItem `bson:"items" json:"items"`
}
type LineItem struct {
	SKU string `bson:"sku" json:"sku"`
	Qty int    `bson:"qty" json:"qty"`
}

func main() {
	// Relational: 1 order row + N item rows. Reading the order means a JOIN.
	order := OrderRow{ID: 1, Customer: "ada"}
	items := []ItemRow{{1, "SKU-A", 2}, {1, "SKU-B", 1}}
	fmt.Println("RELATIONAL — two tables, join on order_id:")
	fmt.Printf("  orders:      %+v\n", order)
	fmt.Printf("  order_items: %+v\n", items)

	// Document: the same order as ONE embedded document — one read, no join.
	doc := OrderDoc{ID: 1, Customer: "ada", Items: []LineItem{{"SKU-A", 2}, {"SKU-B", 1}}}
	b, _ := json.MarshalIndent(doc, "", "  ")
	fmt.Println("\nDOCUMENT — one collection, one read, no join:")
	fmt.Println(string(b))
}
```

</GoPlayground>

Same information. The document is one read with no join, but the items now live *inside* the order. The relational version can answer "every order containing SKU-A" directly and update an item in one place.

<ConceptGrid cols={2}>
  <ConceptCard label="Relational (Postgres) fits when…">Data has real relationships, invariants span rows (a transfer touches two accounts), queries slice the data many ways, and correctness beats raw write throughput.</ConceptCard>
  <ConceptCard label="Document (MongoDB) fits when…">Each record is a self-contained tree read and written as a unit, its shape varies or changes quickly, and you want easy horizontal scale-out: catalogs, CMS pages, profiles, event payloads.</ConceptCard>
  <Gotcha>Embedding duplicates data. A value copied into a million documents needs a million writes to change; in a relational column it's one `UPDATE`. Model for how the data is **written**, not just the convenient read.</Gotcha>
</ConceptGrid>

### Step 2: MongoDB from Go

The official driver is at v2 (`go.mongodb.org/mongo-driver/v2`). The shape mirrors `database/sql`: connect once, get a collection, insert and query with `bson`-tagged structs. It needs a running MongoDB, so it isn't runnable here (it does compile against driver v2.9):

```go title="orders.go"
package catalog

import (
	"context"

	"go.mongodb.org/mongo-driver/v2/bson"
	"go.mongodb.org/mongo-driver/v2/mongo"
	"go.mongodb.org/mongo-driver/v2/mongo/options"
)

type Order struct {
	ID       string     `bson:"_id"`
	Customer string     `bson:"customer"`
	Items    []LineItem `bson:"items"`
}

type LineItem struct {
	SKU string `bson:"sku"`
	Qty int    `bson:"qty"`
}

// OrdersCollection connects once and returns the orders collection.
// (In driver v2, Connect takes no context; the first operation connects.)
func OrdersCollection(uri string) (*mongo.Collection, error) {
	client, err := mongo.Connect(options.Client().ApplyURI(uri))
	if err != nil {
		return nil, err
	}
	return client.Database("shop").Collection("orders"), nil
}

// InsertOrder writes the whole order, items embedded, as one document.
func InsertOrder(ctx context.Context, c *mongo.Collection, o Order) error {
	_, err := c.InsertOne(ctx, o)
	return err
}

// FindOrder reads it back in one round trip, no join.
func FindOrder(ctx context.Context, c *mongo.Collection, id string) (Order, error) {
	var o Order
	err := c.FindOne(ctx, bson.M{"_id": id}).Decode(&o)
	return o, err
}
```

`bson.M` is a `map[string]any` used as a query document: `{"_id": id}` means "where `_id` equals id".

<Callout kind="warn" title="Why Meridian's ledger is never in MongoDB">

Not because MongoDB lacks transactions: it has had multi-document ACID transactions since 4.0. It's about **fit**. MongoDB's design centre is the single document as the unit of atomic change; multi-document transactions are the exception, with extra cost and caveats. A double-entry ledger touches at least two accounts on every write and must balance globally, with a permanent audit trail. That's the relational model's home ground. Choose the database whose defaults match your invariant: for money, SQL; for a product catalog, perhaps MongoDB.

</Callout>

<Exercise n={1} title="Pool arithmetic" level="easy">

Postgres has `max_connections = 100`. You run 4 replicas of your service, and a migration job plus admin tools need up to 10 connections. Write the pool settings for each replica, with a comment explaining each number.

<Solution>

```go
func configurePool(db *sql.DB) {
	// (100 - 10 reserved) / 4 replicas = 22.5, round down.
	db.SetMaxOpenConns(22)
	// Keep most of them warm; the steady load needs ~15 at once.
	db.SetMaxIdleConns(15)
	// Pick up failovers and config changes within half an hour.
	db.SetConnMaxLifetime(30 * time.Minute)
	// Below the load balancer's idle timeout (350 s on an AWS NLB).
	db.SetConnMaxIdleTime(5 * time.Minute)
}
```

Always multiply per-replica pool size by the replica count, and remember deploys: during a rolling update, old and new replicas are both running, so the peak can be higher still. If the numbers don't fit, a pooler such as PgBouncer lets many client connections share fewer server connections.

</Solution>

</Exercise>

<Exercise n={2} title="Safe account lookup" level="easy">

Write `GetAccountByOwner(ctx context.Context, db *sql.DB, owner string) (id string, balance int64, err error)`. Use a placeholder and `QueryRowContext`, and return a package-level `ErrNotFound` (wrapped) when no account matches.

<Solution>

```go
var ErrNotFound = errors.New("account not found")

func GetAccountByOwner(ctx context.Context, db *sql.DB, owner string) (string, int64, error) {
	var id string
	var balance int64
	err := db.QueryRowContext(ctx,
		`SELECT id, balance_cents FROM accounts WHERE owner = $1 ORDER BY created_at LIMIT 1`,
		owner,
	).Scan(&id, &balance)
	if errors.Is(err, sql.ErrNoRows) {
		return "", 0, fmt.Errorf("owner %q: %w", owner, ErrNotFound)
	}
	if err != nil {
		return "", 0, fmt.Errorf("get account: %w", err)
	}
	return id, balance, nil
}
```

`ORDER BY created_at` makes "first" mean something: without an `ORDER BY`, `LIMIT 1` returns whichever row Postgres finds first, which can change between runs.

</Solution>

</Exercise>

<Exercise n={3} title="Two ways to say NULL" level="easy">

Write `FormatNote(note sql.NullString) string` and `FormatNotePtr(note *string) string`. Each returns the note, or `"(no note)"` for NULL.

<Solution>

```go
package main

import (
	"database/sql"
	"fmt"
)

// FormatNote handles the sql.NullString style.
func FormatNote(note sql.NullString) string {
	if note.Valid {
		return note.String
	}
	return "(no note)"
}

// FormatNotePtr handles the pointer style.
func FormatNotePtr(note *string) string {
	if note != nil {
		return *note
	}
	return "(no note)"
}

func main() {
	fmt.Println(FormatNote(sql.NullString{String: "rent payment", Valid: true}))
	fmt.Println(FormatNote(sql.NullString{}))

	s := "rent payment"
	fmt.Println(FormatNotePtr(&s))
	fmt.Println(FormatNotePtr(nil))
}
```

Both styles are common; `sql.Null[T]` (Go 1.22) is the generic form of the first.

</Solution>

</Exercise>

<Exercise n={4} title="Find the N+1" level="medium">

This function works and is slow. Say how many queries it sends for 100 accounts, then rewrite it as one query.

```go
func OwnersWithTransactions(ctx context.Context, db *sql.DB) ([]string, error) {
	rows, err := db.QueryContext(ctx, "SELECT id, owner FROM accounts LIMIT 100")
	if err != nil {
		return nil, err
	}
	defer rows.Close()
	var owners []string
	for rows.Next() {
		var id, owner string
		rows.Scan(&id, &owner)
		var count int
		db.QueryRowContext(ctx,
			"SELECT count(*) FROM transactions WHERE from_account = $1", id,
		).Scan(&count)
		if count > 0 {
			owners = append(owners, owner)
		}
	}
	return owners, rows.Err()
}
```

<Solution>

1 query for the list plus 1 per account: **101** for 100 accounts. It also holds one connection for the outer `rows` while borrowing a second for each inner query, so with a small pool it can deadlock waiting for itself.

```go
func OwnersWithTransactions(ctx context.Context, db *sql.DB) ([]string, error) {
	rows, err := db.QueryContext(ctx, `
		SELECT DISTINCT a.owner
		FROM accounts a
		JOIN transactions t ON t.from_account = a.id
		LIMIT 100`)
	if err != nil {
		return nil, fmt.Errorf("query owners: %w", err)
	}
	defer rows.Close()

	var owners []string
	for rows.Next() {
		var owner string
		if err := rows.Scan(&owner); err != nil {
			return nil, fmt.Errorf("scan owner: %w", err)
		}
		owners = append(owners, owner)
	}
	return owners, rows.Err()
}
```

The inner `JOIN` keeps only accounts with at least one matching transaction; `DISTINCT` removes duplicates when an account has several. One round trip, whatever the size.

</Solution>

</Exercise>

<Exercise n={5} title="A safe NOT NULL" level="hard">

`accounts.metadata JSONB` exists and is nullable, and every running version of the service now writes it. Write the migration that makes it `NOT NULL` without holding an ACCESS EXCLUSIVE lock for a full table scan, and say why each statement is safe.

<Solution>

```sql
-- 000007_metadata_not_null.up.sql
SET lock_timeout = '2s';

-- Existing NULLs must go first (run as a batched job on big tables).
UPDATE accounts SET metadata = '{}' WHERE metadata IS NULL;

-- Instant: checks only rows written from now on.
ALTER TABLE accounts ADD CONSTRAINT metadata_not_null
    CHECK (metadata IS NOT NULL) NOT VALID;

-- Scans the table, but with a lock that allows reads and writes.
ALTER TABLE accounts VALIDATE CONSTRAINT metadata_not_null;

-- Instant on Postgres 12+: the valid CHECK proves no NULLs exist.
ALTER TABLE accounts ALTER COLUMN metadata SET NOT NULL;
ALTER TABLE accounts DROP CONSTRAINT metadata_not_null;
```

```sql
-- 000007_metadata_not_null.down.sql
ALTER TABLE accounts ALTER COLUMN metadata DROP NOT NULL;
```

Why it's only safe once every version writes `metadata`: an old version that inserts without it would now fail the constraint. `lock_timeout` makes each short exclusive step give up rather than queue traffic behind it if a long query is in the way. On a big table, run the `UPDATE` as a batched backfill instead of one statement (Stop 4).

</Solution>

</Exercise>

<Recap>

- **`sql.DB` is a pool.** Open once, `SetMaxOpenConns` before the first query (the default is unlimited), and `PingContext` at startup, because `sql.Open` connects to nothing.
- **pgx** is the usual Postgres driver: behind `database/sql` or through `pgxpool`.
- **Placeholders** for every value. SQL text and values travel separately, so input can never become SQL.
- **Rows:** `defer rows.Close()`, scan in SELECT order, check `rows.Err()`. An unclosed `Rows` holds a connection until the pool runs dry.
- **NULL** scans into `sql.Null*`, `sql.Null[T]` or a pointer; into a plain type it's an error.
- **Transactions:** `BeginTx`, `defer tx.Rollback()`, everything through `tx`, `Commit`. Guards like `balance_cents >= $1` plus row locks keep concurrent writers correct.
- **Migrations** go forward only. Set `lock_timeout`; prefer constant defaults, `NOT VALID` checks and `CREATE INDEX CONCURRENTLY`; break renames into expand, dual-write, backfill, switch, contract.
- **sqlc** catches SQL mistakes at generate time; sqlx and `database/sql` at run time; ORMs hide the SQL.
- **`EXPLAIN ANALYZE`**: a `Seq Scan` in a hot path usually wants an index. A query in a loop is **N+1**: use a JOIN or `= ANY($1)`.
- **Replicas** scale reads but lag; route a user's reads to the primary briefly after they write.
- **Documents vs relations:** choose the database whose defaults protect your invariant.

</Recap>
