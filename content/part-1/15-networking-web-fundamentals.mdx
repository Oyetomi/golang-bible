## TCP/UDP & Sockets

*Stop 1 of 5.*

Here's the scenario: your payment service needs to receive checkout requests from a web frontend. Before a single HTTP byte flows, the OS has to set up a communication channel between two machines. That channel is built on **TCP** — and understanding TCP is understanding why your service can handle thousands of concurrent connections without data corruption.

### What a socket actually is

<Define term="Socket">
A **socket** is a file descriptor — an integer handle the OS kernel gives you — that represents one end of a network connection. From your program's perspective, writing to a socket is almost identical to writing to a file; the kernel handles turning those bytes into network packets. Every socket is identified by a **5-tuple** (protocol, source IP, source port, destination IP, destination port) that uniquely identifies the connection. **Why it matters:** without sockets, two programs on different machines have no channel to exchange bytes. In Go, `net.Conn` wraps the raw socket fd so you never touch the syscall directly.
</Define>

A **socket** is a file descriptor — an integer handle the OS kernel gives you — that represents one end of a network connection. From your program's perspective, writing to a socket is almost identical to writing to a file; the kernel handles turning those bytes into network packets.

Every socket is identified by a **5-tuple**:

- Protocol (TCP or UDP)
- Source IP address
- Source port
- Destination IP address
- Destination port

That 5-tuple uniquely identifies one connection across the entire internet. When ten thousand browsers connect to your checkout service on port 443, they all target the same destination IP:port — but each one has a different *source* port, making every connection distinct.

  <ConceptCard label="Port">A 16-bit number (0–65535) that identifies a specific service on a host. Ports below 1024 require root on Linux. Your Go server calls `net.Listen("tcp", ":8080")` to claim one.</ConceptCard>

  <ConceptCard label="TCP">Transmission Control Protocol — a reliable, ordered, byte-stream protocol. The OS guarantees delivery and ordering; you never see dropped or reordered bytes.</ConceptCard>
  <ConceptCard label="UDP">User Datagram Protocol — fire-and-forget datagrams. Faster, lower overhead, but no delivery guarantees. DNS, video streaming, and QUIC run over UDP.</ConceptCard>

</ConceptGrid>

### The TCP 3-way handshake

<Define term="TCP — Transmission Control Protocol">
**TCP** is the internet's reliable byte-stream protocol. Before any data flows, two hosts negotiate a connection via the **3-way handshake** (SYN → SYN-ACK → ACK). After that, the OS presents your program with an ordered byte stream, retransmitting lost data and hiding duplicate packets from the application; otherwise the connection fails with an error. **Why it matters for Meridian:** a `POST /transfers` that loses a byte mid-stream would corrupt the JSON body and produce an undecodable request. TCP makes that impossible at the OS level, so your Go handler either sees ordered bytes or an error.
</Define>

TCP connections don't just open — they are *negotiated*. Before a single byte of your HTTP request travels, the client and server exchange three packets to agree that both sides are alive and ready. This is the **3-way handshake**: SYN → SYN-ACK → ACK.

The sequence numbers exist so both sides can detect out-of-order, missing, or duplicated packets and fix them — *automatically, at the OS level*, before your code sees anything. That's what makes TCP a *reliable* stream.

### Reliable streams vs. UDP datagrams

<Define term="UDP — User Datagram Protocol">
**UDP** is a connectionless, fire-and-forget protocol. You send a datagram; it may arrive, arrive out of order, arrive twice, or vanish — the OS makes no promises. In exchange, there's no handshake, no retransmission overhead, and no ordering wait. **Why it matters:** DNS queries, video streaming, and QUIC (HTTP/3) all run over UDP because they either tolerate packet loss or implement their own reliability. Payment flows use TCP — you never want "did the charge arrive?" to be answered with "we're not sure."
</Define>

TCP and UDP solve fundamentally different problems:

### A tiny Go TCP echo server and client

Let's make it concrete. Here's a minimal TCP echo server — it accepts a connection, reads whatever the client sends, writes it back, and closes. The `net` package gives you sockets without touching any syscall directly.

```go
package main

import (
	"fmt"
	"io"
	"net"
	"os"
)

// echoServer listens on :9000 and echoes bytes back to each client.
func echoServer() {
	// net.Listen returns a Listener — the listening socket.
	ln, err := net.Listen("tcp", ":9000")
	if err != nil {
		fmt.Fprintln(os.Stderr, "listen:", err)
		os.Exit(1)
	}
	defer ln.Close()
	fmt.Println("echo server listening on :9000")

	for {
		// Accept blocks until a new TCP connection arrives.
		// Returns a net.Conn — the connected socket for THIS client.
		conn, err := ln.Accept()
		if err != nil {
			fmt.Fprintln(os.Stderr, "accept:", err)
			continue
		}
		// Handle each connection concurrently — one goroutine per client.
		// This is Go's idiomatic pattern: goroutines are cheap.
		go handleConn(conn)
	}
}

func handleConn(conn net.Conn) {
	defer conn.Close() // always close when done
	// io.Copy reads from conn until EOF and writes each chunk back.
	// For an echo server: read what client sent, write it straight back.
	if _, err := io.Copy(conn, conn); err != nil {
		fmt.Fprintln(os.Stderr, "copy:", err)
	}
}

func main() {
	echoServer()
}
```

<UnderTheHood title="What the kernel does with a socket">

When your Go code calls `net.Listen`, the runtime calls the `socket(2)`, `bind(2)`, and `listen(2)` syscalls. The OS allocates a **socket data structure** in kernel space containing:

- **Send buffer** — bytes your program has written but the kernel hasn't confirmed the remote TCP stack received yet.
- **Receive buffer** — bytes the remote sent that your program hasn't `Read` yet.
- **State machine** — the TCP state (LISTEN, SYN_RECEIVED, ESTABLISHED, TIME_WAIT, etc.).

Go registers every socket with the **netpoller**, a thin wrapper around `epoll` (Linux), `kqueue` (macOS/BSD) or `IOCP` (Windows), once, when the connection is created. When `conn.Read()` finds no data yet, the goroutine doesn't block the OS thread. The goroutine is parked (marked non-runnable) and the OS thread is released back to the Go scheduler to run other goroutines. When the kernel signals "data ready," the netpoller wakes the goroutine and it resumes — on whatever OS thread is available.

This is why a Go server can handle 100,000 concurrent connections with a handful of OS threads: sleeping connections cost one goroutine stack (~2 KB, grown on demand) plus a kernel fd entry, not an OS thread (typically 1–8 MB stack). The full GMP scheduler story (how goroutines, OS threads and logical processors interlock) is Part 2, Chapter 5. We're linking forward, not hand-waving.

**Context-aware dial methods (Go 1.26):** as of Go 1.26, `net.Dialer` gains explicit context-aware variants — `DialTCP`, `DialUDP`, `DialIP`, and `DialUnix` — that accept a `context.Context` directly. Previously, these protocol-specific forms required calling the generic `DialContext` and then type-asserting the returned `net.Conn`. With Go 1.26 you can write `dialer.DialTCP(ctx, "tcp", laddr, raddr)` and get a `*net.TCPConn` back immediately, without a type assertion. Useful when you need to set TCP-specific socket options before the first byte flows.

</UnderTheHood>

## HTTP/1.1 vs HTTP/2

*Stop 2 of 5.*

<Define term="HTTP/1.1 vs HTTP/2" since="HTTP Clients (Part 1)">
**HTTP** (HyperText Transfer Protocol) is the application-layer protocol browsers and servers use to exchange requests and responses over TCP. **HTTP/1.1** (1999/2014) is text-based: each request is an ASCII header block followed by a body, and responses must be returned in the order requests were sent on a given connection — one slow response blocks every request behind it (**head-of-line blocking**). **HTTP/2** (2015) rewires the transport: it uses binary frames and multiplexed **streams**, so many requests fly concurrently over a single TCP connection without any ordering constraint. Go's `net/http` speaks HTTP/2 automatically when TLS is configured — zero code change. **Why it matters:** HOL blocking is a real latency killer for Meridian's dashboard pages; HTTP/2 eliminates it without changing a line of handler code.
</Define>

Your checkout service doesn't speak raw TCP to browsers — it speaks **HTTP**. But HTTP has evolved dramatically, and understanding the difference between HTTP/1.1 and HTTP/2 explains real performance characteristics you'll observe and tune in production.

HTTP/1.1 (RFC 9110/9112, 2022 — the current restatement of the protocol first standardised as RFC 2616 in 1999, still dominant) is a **text protocol**: every request and response is human-readable ASCII headers followed by an optional body. **Keep-alive** (persistent connections, on by default in HTTP/1.1) means one TCP connection can serve multiple requests sequentially, avoiding repeated 3-way handshakes. But "sequentially" is the operative word.

### Head-of-line blocking: HTTP/1.1's fatal flaw

Requests on one HTTP/1.1 connection must be answered **in order**. If request 1 is a slow database query and requests 2–5 are tiny image fetches, requests 2–5 are *stuck waiting* even though they could complete instantly. This is **head-of-line blocking** (HOL blocking).

### HTTP/2: multiplexing and binary framing

HTTP/2 (RFC 7540, 2015) keeps the same semantics — methods, headers, status codes — but rewrites the transport layer completely:

<ConceptGrid cols={3}>
  <ConceptCard label="Binary Framing">HTTP/2 encodes everything in binary frames, not text. Frames have a type, flags, a stream ID, and a payload. Parsing is faster and less error-prone than ASCII parsing.</ConceptCard>
  <ConceptCard label="Streams">Each request/response pair is a numbered **stream** within one TCP connection. Streams are independent and interleaved — no ordering constraint between them.</ConceptCard>
  <ConceptCard label="Multiplexing">Multiple streams coexist concurrently on one connection. Stream 1 can be a slow DB query; streams 3, 5, 7 return instantly without waiting. HOL blocking is eliminated at the HTTP layer.</ConceptCard>
  <ConceptCard label="Header Compression (HPACK)">HTTP headers repeat massively across requests (User-Agent, Cookie, Host). HPACK compresses them with a shared dictionary, slashing wire overhead.</ConceptCard>
  <ConceptCard label="Server Push">Server can proactively send resources the client will need (e.g., CSS/JS) before the client asks. Rarely used well in practice; largely superseded by HTTP/3 and preload hints.</ConceptCard>
  <Gotcha>HTTP/2 eliminates HTTP-layer HOL blocking but NOT TCP-layer HOL blocking. If a single TCP packet is lost, ALL streams on that connection stall until retransmission. HTTP/3 fixes this by running over QUIC (UDP), where each stream has independent delivery.</Gotcha>
</ConceptGrid>


Go's `net/http` package speaks HTTP/2 automatically when TLS is configured — you don't write any HTTP/2-specific code. The runtime negotiates the protocol via **ALPN** (Application-Layer Protocol Negotiation) during the TLS handshake.

**HTTP/3 / QUIC** (a brief note): HTTP/3 runs over **QUIC**, which is a reliable-but-multiplexed protocol built *on top of UDP*. QUIC implements per-stream loss recovery, eliminating TCP's HOL blocking entirely. Go has early standard-library QUIC support (`golang.org/x/net/quic`) and third-party implementations. The full story belongs in a dedicated networking deep-dive; the key insight is: HTTP/3 = HTTP/2's semantics + QUIC's transport.

## DNS

<Define term="DNS — Domain Name System">
**DNS** is the internet's distributed phone book: it translates human-readable hostnames (`payments.example.com`) into the IP addresses that routers actually forward packets to. DNS is a hierarchy — recursive resolver → root name servers → TLD server → authoritative name server — with every answer cached by a **TTL** (time-to-live) measured in seconds. DNS queries use **UDP** (fast, no handshake) and fall back to TCP for large responses. **Why it matters:** a cold DNS lookup adds 50–200ms before your TCP connection even starts. A misconfigured TTL (too short) hammers resolvers on every request; a stale TTL (too long) means traffic still hits the old server after a failover. Both kill Meridian's uptime SLA.
</Define>

Your browser knows it wants `payments.example.com` — but routers only understand IP addresses. **DNS (Domain Name System)** is the distributed phone book that translates names to addresses. Every HTTP request you've ever made starts with a DNS lookup.

### The DNS resolution hierarchy

DNS is not one server — it's a hierarchy of servers, each responsible for a slice of the namespace:

<ConceptGrid cols={3}>
  <ConceptCard label="Recursive Resolver">The first stop — usually your ISP's or a public resolver like 8.8.8.8 (Google) or 1.1.1.1 (Cloudflare). It does the work of walking the hierarchy on your behalf, then caches the result.</ConceptCard>
  <ConceptCard label="Root Name Servers">13 clusters of root servers (a.root-servers.net through m.root-servers.net) that know which TLD server (.com, .io, .net) to ask. They don't know IP addresses — only referrals.</ConceptCard>
  <ConceptCard label="TLD Name Server">The authoritative server for a top-level domain. The .com TLD server knows which name server is authoritative for example.com.</ConceptCard>
  <ConceptCard label="Authoritative Name Server">The definitive source for a domain's records. Your DNS provider (Cloudflare, Route53, etc.) runs this. It returns the actual IP address.</ConceptCard>
  <ConceptCard label="TTL (Time To Live)">Every DNS record carries a TTL in seconds. Resolvers cache the answer for that duration. Short TTL = fast propagation of changes; long TTL = fewer queries, more cache hits.</ConceptCard>
  <Gotcha>DNS is UDP by default (port 53). Responses over 512 bytes fall back to TCP. DNS over HTTPS (DoH) and DNS over TLS (DoT) are modern encrypted alternatives. Unencrypted DNS exposes every domain you visit to your network path.</Gotcha>
</ConceptGrid>

### Common DNS record types

<ConceptGrid cols={3}>
  <ConceptCard label="A record">Maps a hostname to an IPv4 address. `payments.example.com → 93.184.216.34`</ConceptCard>
  <ConceptCard label="AAAA record">Maps a hostname to an IPv6 address. `payments.example.com → 2606:2800:21f:cb07::1`</ConceptCard>
  <ConceptCard label="CNAME record">An alias — points one hostname to another. `www.example.com → example.com`. The resolver then looks up the target. CNAMEs cannot coexist with other records at the zone apex.</ConceptCard>
  <ConceptCard label="MX record">Mail exchanger — where email for a domain should go. Not directly relevant to HTTP but on every DNS exam.</ConceptCard>
  <ConceptCard label="TXT record">Arbitrary text. Used for SPF/DKIM email validation, domain ownership proofs (for TLS certificate issuance), and service discovery.</ConceptCard>
  <ConceptCard label="NS record">Identifies the authoritative name servers for a domain. This is the answer the TLD server returns, pointing you to the authoritative server.</ConceptCard>
</ConceptGrid>

## TLS & HTTPS

*Stop 4 of 5.*

<Define term="TLS / HTTPS handshake">
**TLS** (Transport Layer Security) is a cryptographic protocol that runs on top of TCP and wraps all bytes in encryption. **HTTPS** is simply HTTP carried over TLS. Before any HTTP data flows, the two sides run the **TLS handshake** — an exchange that: (1) negotiates cipher suites, (2) proves the server's identity via a certificate signed by a trusted CA, and (3) derives a shared symmetric session key using ephemeral Diffie-Hellman (so the secret is never transmitted). TLS 1.3 completes this in **1 round-trip**. After the handshake, every byte — URL path, headers, body — is AES-GCM encrypted and integrity-checked. **Why it matters:** Meridian's payment endpoints carry card numbers and account balances. Without TLS, any router between the browser and your server can read or modify them. With TLS, eavesdroppers see only ciphertext.
</Define>

DNS gave you the IP. TCP gave you a connection. But everything so far is **in the clear** — anyone on the network path (your ISP, a coffee-shop router, a nation-state) can read every byte. **TLS (Transport Layer Security)** fixes that. It runs on top of TCP and wraps all subsequent bytes in encryption.

### What TLS actually secures (and what it doesn't)

<ConceptGrid cols={3}>
  <ConceptCard label="Confidentiality">An eavesdropper on the wire sees only ciphertext. Your HTTP headers, body, and even the URL path are encrypted. Only the IP address and port are visible.</ConceptCard>
  <ConceptCard label="Integrity">A message authentication code (MAC) on every record means an attacker can't silently modify bytes in transit. Tampering is detected and the connection is terminated.</ConceptCard>
  <ConceptCard label="Authentication">The server's certificate proves it's actually `payments.example.com` and not an impostor. A certificate authority (CA) vouches for the binding of domain name to public key.</ConceptCard>
  <ConceptCard label="SNI: what TLS does NOT hide">Server Name Indication (SNI) is sent in the ClientHello in plaintext so the server knows which certificate to present. Your ISP (and anyone on the path) sees the hostname you're connecting to — just not the URL path or body. Encrypted Client Hello (ECH) is the evolving fix.</ConceptCard>
  <ConceptCard label="TLS 1.3">The current standard (2018). Cuts the handshake to 1 round-trip (vs. 2 in TLS 1.2), removes weak cipher suites, mandates perfect forward secrecy. Go's `crypto/tls` introduced TLS 1.3 support in Go 1.12 and made it the default in Go 1.13.</ConceptCard>
  <Gotcha>HTTPS authenticates the SERVER to you — not you to the server. The padlock means "this server is who it claims to be and the traffic is encrypted." It does NOT mean the server is trustworthy, safe, or not running a scam. Phishing sites have HTTPS too.</Gotcha>
</ConceptGrid>

### Go's HTTPS server — zero extra effort

Go's `net/http` package handles TLS transparently. Provide a certificate and key, call `ListenAndServeTLS`:

```go
package main

import (
	"fmt"
	"net/http"
)

func checkoutHandler(w http.ResponseWriter, r *http.Request) {
	// By the time we're here: TLS is done, HTTP/2 is negotiated,
	// the request is parsed. We just handle business logic.
	fmt.Fprintf(w, `{"order_id":"ord-001","ok":true}`)
}

func main() {
	mux := http.NewServeMux()
	mux.HandleFunc("/checkout", checkoutHandler)

	// ListenAndServeTLS loads the cert/key, configures TLS 1.3 by
	// default, negotiates HTTP/2 via ALPN, and starts accepting.
	// For local dev: use mkcert to generate cert.pem and key.pem.
	if err := http.ListenAndServeTLS(":8443", "cert.pem", "key.pem", mux); err != nil {
		panic(err)
	}
}
```

<UnderTheHood title="Diffie-Hellman key exchange and perfect forward secrecy">

TLS 1.3 mandates **ephemeral Diffie-Hellman** for all key exchanges (ECDHE — Elliptic Curve DH). Here's the magic: the client generates a *temporary* DH key pair per connection. The server does the same. They exchange public keys, and both sides independently compute the same shared secret using their own private key and the other side's public key — *the shared secret is never transmitted*.

Because the private keys are ephemeral (discarded after the handshake), an attacker who records today's traffic and later steals the server's long-term private key *cannot* decrypt old sessions. The ephemeral keys are gone. This is **perfect forward secrecy (PFS)**. TLS 1.2 made PFS optional; TLS 1.3 made it mandatory, which is why TLS 1.2 RSA key exchange (where the pre-master secret is encrypted with the server's long-term key) is now considered legacy.

Go's `crypto/tls` implements all of this in pure Go, audited, with hardware acceleration for AES-GCM where available. You do not touch any of this directly — `ListenAndServeTLS` does it correctly by default, including ALPN negotiation for HTTP/2.

**Post-quantum key exchange (Go 1.24):** as of Go 1.24, `crypto/tls` enables hybrid post-quantum key exchange (`X25519MLKEM768`) by default in TLS 1.3 handshakes whenever `Config.CurvePreferences` is nil. The client advertises both classical X25519 and the ML-KEM-768 post-quantum component; the server selects it if supported. No code change is needed — you get quantum-resistant key exchange for free when both sides are Go 1.24+. If you need to opt out (e.g., for compatibility testing), set the GODEBUG `tlsmlkem=0` or set `tls.Config.CurvePreferences` explicitly.

</UnderTheHood>

<Define term="Reverse Proxy / Load Balancer">
A **reverse proxy** is a server that sits in front of your application servers and forwards incoming requests to one of them on the client's behalf. Clients talk to the proxy (they may not even know your Go server exists); the proxy talks to your backends. A **load balancer** is a reverse proxy whose primary job is distributing traffic across a pool of backend instances — choosing one via round-robin, least-connections, or consistent hashing. It also performs **health checks** (removing unhealthy instances from rotation) and typically **TLS termination** (decrypting HTTPS so backends receive plain HTTP internally). **Why it matters:** without a load balancer, one Go instance handles all of Meridian's traffic — one deploy kills the service. With a load balancer, you deploy a new instance, verify it's healthy, drain the old one, and users never see a blip.
</Define>

### The latency budget

Each hop adds time. On a typical request to a well-run backend:

<UnderTheHood title="How Go's netpoller integrates blocking reads with the scheduler">

When your handler calls `db.QueryRowContext(ctx, ...)`, under the hood a TCP read syscall is issued on the database connection. Instead of blocking the OS thread, the Go runtime:

1. Tries the read. The connection's fd was registered with `epoll` (via the **netpoller**) when the connection was created, so there's nothing to set up now.
2. Gets `EAGAIN` (no data yet), so it parks the goroutine on that connection's poll descriptor: it's now waiting, in no run queue.
3. Returns the OS thread (M) to the scheduler, which immediately picks up another runnable goroutine.

When Postgres sends the response, the kernel marks the fd ready in epoll. There's no special netpoller goroutine: whenever the scheduler looks for work (and periodically from `sysmon`), it asks epoll which fds are ready and puts the goroutines waiting on them back in a run queue. The next available P picks it up and execution continues exactly where it left off.

The result: one OS thread services *many* concurrent database-waiting goroutines. You do not need a thread pool. You do not need async/await syntax. The scheduler handles it transparently.

The full GMP model (G goroutines, M OS threads, P logical processors, work-stealing, `sysmon` preemption) is Part 2, Chapter 5. We're deliberately keeping the preview brief here: know it exists, know what it buys you, learn the machinery in depth when it's the subject.

</UnderTheHood>

<Exercise n={1} title="TCP echo client" level="easy">

Write a program that connects to `127.0.0.1:9000` via TCP, sends the string `"ping"`, reads back the response, and prints it. Assume a server is running there (you can use the echo server from the TCP section). Use `net.Dial`, write with `fmt.Fprintf`, and read with `bufio.NewReader`.

<Solution>

```go
package main

import (
	"bufio"
	"fmt"
	"io"
	"net"
	"os"
	"time"
)

func main() {
	conn, err := net.Dial("tcp", "127.0.0.1:9000")
	if err != nil {
		fmt.Fprintln(os.Stderr, "dial:", err)
		os.Exit(1)
	}
	defer conn.Close()

	// Set a deadline so we don't hang forever if the server is slow.
	conn.SetDeadline(time.Now().Add(5 * time.Second))

	fmt.Fprintf(conn, "ping")
	// Signal end-of-write so the echo server's io.Copy sees EOF and responds.
	conn.(*net.TCPConn).CloseWrite()

	resp, err := io.ReadAll(bufio.NewReader(conn))
	if err != nil {
		fmt.Fprintln(os.Stderr, "read:", err)
		os.Exit(1)
	}
	fmt.Printf("response: %s\n", resp)
}
```

`conn.SetDeadline` is critical in production — never leave a network read without a timeout or a context deadline. Naked reads can hang indefinitely if the server stops responding.

</Solution>

</Exercise>

<Exercise n={2} title="HTTP/1.1 raw request" level="medium">

Using only `net.Dial` (not `net/http`), open a TCP connection to `example.com:80` and manually write a valid HTTP/1.1 GET request. Read back at least the first line of the response (the status line) and print it. This exercise is about *seeing* HTTP as text on a socket.

<Solution>

```go
package main

import (
	"bufio"
	"fmt"
	"net"
	"os"
)

func main() {
	conn, err := net.Dial("tcp", "example.com:80")
	if err != nil {
		fmt.Fprintln(os.Stderr, "dial:", err)
		os.Exit(1)
	}
	defer conn.Close()

	// A minimal HTTP/1.1 request — CRLF line endings are required by spec.
	request := "GET / HTTP/1.1\r\n" +
		"Host: example.com\r\n" +
		"Connection: close\r\n" + // tell server to close after response
		"\r\n"

	if _, err := fmt.Fprint(conn, request); err != nil {
		fmt.Fprintln(os.Stderr, "write:", err)
		os.Exit(1)
	}

	// Read just the status line to see the raw HTTP response.
	scanner := bufio.NewScanner(conn)
	if scanner.Scan() {
		fmt.Println("Status line:", scanner.Text()) // e.g. "HTTP/1.1 200 OK"
	}
}
```

`Connection: close` tells the server to close the connection after responding — without it, HTTP/1.1 keep-alive means the server waits for more requests and your read hangs.

</Solution>

<Exercise n={3} title="HTTP client with timeout and context" level="medium">

Write a `fetchCheckoutStatus(ctx context.Context, orderID string) ([]byte, error)` function that uses `net/http` to GET `https://httpbin.org/get?order_id=<orderID>`. Pass the context through correctly so cancellation propagates. Use a custom `http.Client` with a 5-second timeout (not the default client, which has no timeout).

<Solution>

```go
package main

import (
	"context"
	"fmt"
	"io"
	"net/http"
	"os"
	"time"
)

// httpClient is a package-level client with a timeout.
// In production: inject this as a dependency, don't use http.DefaultClient.
var httpClient = &http.Client{
	Timeout: 5 * time.Second,
}

func fetchCheckoutStatus(ctx context.Context, orderID string) ([]byte, error) {
	url := "https://httpbin.org/get?order_id=" + orderID

	// http.NewRequestWithContext wires the context into the request lifecycle.
	// If ctx is cancelled, the request and underlying TCP connection are torn down.
	req, err := http.NewRequestWithContext(ctx, http.MethodGet, url, nil)
	if err != nil {
		return nil, fmt.Errorf("build request: %w", err)
	}

	resp, err := httpClient.Do(req)
	if err != nil {
		return nil, fmt.Errorf("do request: %w", err)
	}
	defer resp.Body.Close()

	if resp.StatusCode != http.StatusOK {
		return nil, fmt.Errorf("unexpected status %d", resp.StatusCode)
	}

	body, err := io.ReadAll(resp.Body)
	if err != nil {
		return nil, fmt.Errorf("read body: %w", err)
	}
	return body, nil
}

func main() {
	ctx, cancel := context.WithTimeout(context.Background(), 10*time.Second)
	defer cancel()

	body, err := fetchCheckoutStatus(ctx, "ord-001")
	if err != nil {
		fmt.Fprintln(os.Stderr, "error:", err)
		os.Exit(1)
	}
	fmt.Printf("%.200s\n", body) // truncate for readability
}
```

Always pass the context from the caller through `NewRequestWithContext`. The `http.Client.Timeout` is a hard wall-clock limit; the context gives you *caller-controlled* cancellation (e.g., when the user navigates away).

</Solution>

</Exercise>

<Exercise n={4} title="Concurrent DNS lookups" level="medium">

Write a program that looks up the A records for three domains concurrently — `google.com`, `cloudflare.com`, and `github.com` — using `net.DefaultResolver.LookupHost`. Use goroutines and a `sync.WaitGroup`. Print each result (domain → IPs) as it arrives. Use a context with a 3-second timeout.

<Solution>

```go
package main

import (
	"context"
	"fmt"
	"net"
	"sync"
	"time"
)

func main() {
	domains := []string{"google.com", "cloudflare.com", "github.com"}

	ctx, cancel := context.WithTimeout(context.Background(), 3*time.Second)
	defer cancel()

	var wg sync.WaitGroup
	for _, domain := range domains {
		wg.Add(1)
		go func(d string) {
			defer wg.Done()
			addrs, err := net.DefaultResolver.LookupHost(ctx, d)
			if err != nil {
				fmt.Printf("%s: error: %v\n", d, err)
				return
			}
			fmt.Printf("%s: %v\n", d, addrs)
		}(domain)
	}
	wg.Wait()
}
```

DNS lookups block on I/O — the ideal workload for goroutines. The context timeout cancels all three lookups if any one takes too long. Since Go 1.22, loop variables are per-iteration, so the old `domain := domain` re-declaration is no longer needed; the example passes `domain` as a parameter to be explicit about the value captured by each goroutine.

</Solution>

</Exercise>

<Exercise n={5} title="TLS connection inspector" level="hard">

Write a program that opens a TLS connection to `google.com:443` using `tls.Dial`, then prints: the negotiated TLS version, the cipher suite name, the server's certificate Subject, and whether the certificate chain is verified. Do NOT skip certificate verification (`InsecureSkipVerify` is forbidden — that's exactly the kind of sloppy security that makes me weep).

<Solution>

```go
package main

import (
	"crypto/tls"
	"fmt"
	"os"
)

func main() {
	// tls.Dial performs the TCP connect AND the TLS handshake.
	// It verifies the certificate chain against the system root CAs by default.
	conn, err := tls.Dial("tcp", "google.com:443", &tls.Config{
		// MinVersion enforces no TLS < 1.2. TLS 1.3 will be preferred automatically.
		MinVersion: tls.VersionTLS12,
	})
	if err != nil {
		fmt.Fprintln(os.Stderr, "tls dial:", err)
		os.Exit(1)
	}
	defer conn.Close()

	state := conn.ConnectionState()

	// tls.VersionName is Go 1.21+; for older versions use a map lookup.
	versionNames := map[uint16]string{
		tls.VersionTLS10: "TLS 1.0",
		tls.VersionTLS11: "TLS 1.1",
		tls.VersionTLS12: "TLS 1.2",
		tls.VersionTLS13: "TLS 1.3",
	}

	fmt.Printf("TLS version    : %s\n", versionNames[state.Version])
	fmt.Printf("Cipher suite   : %s\n", tls.CipherSuiteName(state.CipherSuite))
	// HandshakeComplete is true once the TLS handshake has finished.
	// Certificate verification either succeeded (tls.Dial returned nil error)
	// or the whole Dial call would have failed — so reaching this line means
	// the cert chain was already verified against the system root CAs.
	fmt.Printf("Handshake complete : %v\n", state.HandshakeComplete)

	if len(state.PeerCertificates) > 0 {
		cert := state.PeerCertificates[0]
		fmt.Printf("Server cert CN : %s\n", cert.Subject.CommonName)
		fmt.Printf("Issuer         : %s\n", cert.Issuer.CommonName)
		fmt.Printf("Expires        : %s\n", cert.NotAfter.Format("2006-01-02"))
	}
}
```

`InsecureSkipVerify: true` disables ALL certificate verification — an instant and complete defeat of TLS's authentication guarantee. Never ship that in production. If you need to trust a custom CA (internal PKI), add it to `tls.Config.RootCAs`, don't skip verification.

</Solution>

<Recap>

The network stack is not magic — and now you know every layer:

- A **socket** is a kernel file descriptor identified by a 5-tuple. Go's `net.Conn` wraps it; `net.Listen` and `net.Dial` are the two primitives.
- **TCP's 3-way handshake** (SYN → SYN-ACK → ACK) establishes a reliable byte stream before any application data flows. Reliable means ordered, deduplicated, and retransmitted by the OS — your code never sees dropped packets.
- **UDP** is connectionless, unreliable by design — lower overhead, used for DNS, QUIC/HTTP/3, and streaming where the application layer manages reliability.
- **HTTP/1.1** is a text protocol with keep-alive, but head-of-line blocking means one slow request stalls everything behind it on a connection.
- **HTTP/2** solves HOL blocking with binary framing and independent numbered **streams** multiplexed over one TCP connection. Go's `net/http` speaks HTTP/2 automatically when TLS is configured.
- **HTTP/3** runs over **QUIC** (on UDP), eliminating TCP-layer HOL blocking too — streams have independent loss recovery.
- **DNS** is a distributed hierarchy: recursive resolver → root → TLD → authoritative. Every step is cached by TTL. Cold lookups add 50–200ms; warm cache adds zero.
- **TLS 1.3** secures confidentiality, integrity, and server authentication in 1 RTT. It uses ephemeral Diffie-Hellman for **perfect forward secrecy**. SNI is still sent in plaintext — TLS doesn't hide *who* you talk to, only *what* you say.
- The **full request journey** — DNS → TCP → TLS → LB → app → DB → response — is a gauntlet of sequential round-trips. CDN edge termination, caching, and connection reuse are how modern systems make that gauntlet fast.
- Go's **netpoller** (epoll/kqueue) means `conn.Read()` parks the goroutine, not the OS thread — giving you cheap concurrency for I/O-bound workloads without a callback or async/await syntax.
- As of **Go 1.26**, `net.Dialer` has explicit context-aware `DialTCP`/`DialUDP`/`DialIP`/`DialUnix` methods that return the concrete type directly, without a type assertion.
- As of **Go 1.24**, `crypto/tls` enables hybrid post-quantum key exchange (`X25519MLKEM768`) by default in TLS 1.3 — quantum-resistant key establishment at no code cost (`tlsmlkem=0` to opt out).
