## Scaffold

Every production CLI has the same skeleton problem: how do you wire flags, I/O, and program structure before you've written any real logic? Do it wrong and you're trapped — a global `os.Stdin` call buried inside your parser makes testing a nightmare. Do it right and every piece is independently testable.

Here's the scenario. A fintech startup processes millions of transactions per day. Each is written as one JSON line to a log file:

```
{"account":"acct_001","amount_cents":1499,"type":"debit"}
{"account":"acct_002","amount_cents":5000,"type":"credit"}
{"account":"acct_001","amount_cents":200,"type":"debit"}
```

The ops team needs daily summaries — per account, total debits/credits, min/max amounts. They need it fast, they need it scriptable, and right now they have a Python script that takes four minutes on a large file. You're going to replace it with a Go binary that takes seconds, reads from a file or stdin, and is testable without touching the filesystem.

<Define term="CLI / flag parsing" since="Go Fundamentals: Syntax, Types & Control Flow (Part 1)">
A **CLI (command-line interface)** is a program you invoke from the shell by name, optionally followed by **flags** — named options like `-workers 4` or `-json`. Go's standard `flag` package reads those flags from `os.Args` and stores the parsed values in typed pointers you dereference after `flag.Parse()`. Why it matters: a well-designed flag surface is the difference between a tool that's trivially testable (pass any reader, any writer) and one that's hard-wired to `os.Stdin` and impossible to test without spawning a subprocess.
</Define>

### Flags first

```go
// main.go — the wiring layer. No logic lives here; only flag parsing and plumbing.
package main

import (
	"context"
	"flag"
	"fmt"
	"io"
	"os"
	"os/signal"
	"syscall"

	"github.com/you/txstat/aggregate"
	"github.com/you/txstat/parse"
	"github.com/you/txstat/report"
)

func main() {
	// Define flags before parsing. Keep defaults sensible so the tool
	// works out of the box with no arguments.
	workers := flag.Int("workers", 4, "number of concurrent aggregation workers")
	jsonOut := flag.Bool("json", false, "emit JSON instead of a human-readable table")
	top := flag.Int("top", 0, "show only the top N accounts by total (0 = all)")
	file := flag.String("file", "", "input file (default: read from stdin)")
	flag.Parse()

	// Wire up cancellation so Ctrl-C flushes and exits cleanly.
	ctx, stop := signal.NotifyContext(context.Background(), syscall.SIGINT, syscall.SIGTERM)
	defer stop()

	// Open the input — file or stdin. The rest of the program only sees
	// an io.Reader, which means tests can pass any reader they like.
	var r io.Reader = os.Stdin
	if *file != "" {
		f, err := os.Open(*file)
		if err != nil {
			fmt.Fprintf(os.Stderr, "txstat: open: %v\n", err)
			os.Exit(1)
		}
		defer f.Close()
		r = f
	}

	// Parse, aggregate, report — three clearly separated stages.
	records, errs := parse.Stream(ctx, r) // channel of parsed records
	stats, err := aggregate.Run(ctx, records, *workers)
	if err != nil {
		fmt.Fprintf(os.Stderr, "txstat: aggregate: %v\n", err)
		// Drain parse errors too before we exit.
		for e := range errs {
			fmt.Fprintf(os.Stderr, "txstat: parse: %v\n", e)
		}
		os.Exit(1)
	}
	// Surface any parse errors that didn't kill the run.
	for e := range errs {
		fmt.Fprintf(os.Stderr, "txstat: parse warning: %v\n", e)
	}

	if err := report.Write(os.Stdout, stats, *top, *jsonOut); err != nil {
		fmt.Fprintf(os.Stderr, "txstat: report: %v\n", err)
		os.Exit(1)
	}
}
```

<UnderTheHood title="How flag.Parse() and os.Args work">

When you call `flag.Parse()`, Go's `flag` package reads `os.Args[1:]` — everything after the binary name. Each element is either a flag (`-workers 4` or `-workers=4`) or a positional argument.

**How flag values are stored.** `flag.Int("workers", 4, "…")` allocates an `int`, registers it by name in the default `FlagSet`, and returns a pointer to that int. When `Parse()` sees `-workers 8`, it writes `8` through that pointer. You dereference it after `Parse()` returns with `*workers`. This is why you must call `flag.Parse()` before using any flag value — the pointer's target is still the default until then.

**`FlagSet` is the real type.** `flag.Parse()` is just a method call on the package-level `flag.CommandLine` — a `*flag.FlagSet` pre-initialized with the binary name. In tests you create your own `FlagSet` so you can parse flags without touching `os.Args` and without exiting the test process when a required flag is missing (the default `ExitOnError` would call `os.Exit(2)` — fatal for a test). Use `flag.NewFlagSet("test", flag.ContinueOnError)` in tests.

**`os.Args` is a plain slice.** `os.Args[0]` is the executable path; `os.Args[1:]` is everything the shell passed. On Linux the kernel fills the `argv` array; the Go runtime copies it into the slice. There's nothing magic here — `flag` just iterates it.

**POSIX vs. GNU style.** Go's `flag` package is intentionally minimal and non-POSIX: it accepts `-flag value`, `-flag=value`, and `--flag value` (double-dash works), but it does *not* support combined single-letter flags like `-abc` meaning `-a -b -c`. That's a deliberate trade-off for simplicity. If you need subcommands and GNU-style parsing, reach for `github.com/spf13/cobra` — but for most CLIs, `flag` is exactly enough.

</UnderTheHood>

## Parse

<Define term="stdin / stdout / bufio">
**`stdin`** is the default source of bytes a program reads from (the terminal, or a pipe from another command). **`stdout`** is where it writes results. In Go, both are `*os.File` values (`os.Stdin`, `os.Stdout`) that implement `io.Reader` and `io.Writer` — meaning any function that accepts those interfaces works equally well with a file, a pipe, or a test's `strings.NewReader`. **`bufio`** wraps an `io.Reader` with a buffer and a line scanner: instead of issuing one read syscall per byte, it reads a large chunk, then hands your code one line at a time. Without buffering, reading a 50 GB file line-by-line would drown the kernel in syscalls. Why it matters: accepting `io.Reader` instead of `*os.File` is the single change that makes every I/O function in this project independently testable without touching the filesystem.
</Define>

The parser lives in its own package so it's testable without running the full program. Its job: read an `io.Reader` line by line, parse each JSON record, and emit a channel of results. Errors go on a separate channel so the caller can decide whether a bad line is fatal.

```go
// parse/parse.go
package parse

import (
	"bufio"
	"context"
	"encoding/json"
	"fmt"
	"io"
)

// Record is a single transaction as parsed from one input line.
// Amount is in integer cents — never float. A $14.99 charge is 1499.
type Record struct {
	Account     string `json:"account"`
	AmountCents int64  `json:"amount_cents"` // integer cents, always
	Type        string `json:"type"`         // "debit" or "credit"
}

// Stream reads r line by line, parses each line as a Record, and sends the
// result on the returned channel. Parse errors go on the error channel.
// Both channels are closed when r is exhausted or ctx is cancelled.
// Callers must drain both channels to avoid goroutine leaks.
func Stream(ctx context.Context, r io.Reader) (<-chan Record, <-chan error) {
	out := make(chan Record, 64)  // buffered — don't block the scanner
	errc := make(chan error, 16) // errors are infrequent; small buffer is fine

	go func() {
		defer close(out)   // always close; callers range over this
		defer close(errc)

		sc := bufio.NewScanner(r)
		for sc.Scan() {
			// Respect cancellation between lines — a large file should
			// be interruptible without waiting for EOF.
			select {
			case <-ctx.Done():
				return
			default:
			}

			var rec Record
			if err := json.Unmarshal(sc.Bytes(), &rec); err != nil {
				// Wrap the error with context so the caller knows which line.
				errc <- fmt.Errorf("parse: %w", err)
				continue // skip the bad line, keep going
			}
			if rec.Account == "" {
				errc <- fmt.Errorf("parse: missing account field")
				continue
			}
			out <- rec
		}
		if err := sc.Err(); err != nil {
			errc <- fmt.Errorf("scan: %w", err)
		}
	}()

	return out, errc
}
```

### The cents rule

Notice `AmountCents int64` — not `float64`. This isn't a style choice. It's correctness. Financial systems that use float arithmetic have a long, storied history of inventing or destroying fractions of cents at scale. An `int64` holding cents can represent every amount up to about $92 trillion without losing a single cent. A `float64` can't reliably represent `0.1`. We enforce this at the type level in the parser so the rest of the program never has to think about it.

<Callout kind="warn" title="Amount fields from external APIs are often strings">

Some payment APIs send `"amount": "14.99"` — a decimal string to avoid the float problem on the wire. If your input uses that format, parse it as a string and convert: multiply by 100 and round, or use `strconv.ParseFloat` then `math.Round`. Never store the float; convert to `int64` cents immediately in the parser. The fuzz test below will make sure your conversion is correct under adversarial input.

</Callout>

## Concurrency

<Define term="Worker pool" since="Concurrency Patterns (Part 2)">
A **worker pool** is a fixed set of goroutines that all read from the same shared channel. You control concurrency by controlling the pool size, not by spawning one goroutine per record (which would launch millions and exhaust memory). Each worker loops: receive a record, process it, loop back. When the channel closes, workers exit. Why it matters: unbounded goroutine spawning crashes under large workloads; a bounded pool gives you parallel throughput with predictable resource usage. The pattern goes deep in Concurrency Patterns (Part 2).
</Define>

Now the reason ops is going to love this tool. A 50 GB transaction file has millions of records. Parsing them sequentially is fine — the bottleneck is disk I/O, not CPU. But *aggregating* them — computing per-account stats — can be done in parallel if we shard work by account. We'll use a classic bounded worker pool: a fixed number of goroutines draining a shared jobs channel.

```go
// aggregate/aggregate.go
package aggregate

import (
	"context"
	"fmt"
	"sync"

	"github.com/you/txstat/parse"
)

// Stats holds per-account aggregated data.
type Stats struct {
	Account    string
	TotalCents int64 // algebraic sum: credits add, debits subtract
	MinCents   int64 // smallest single amount seen (by absolute value)
	MaxCents   int64 // largest single amount seen
	Count      int
}

// Run consumes records from the channel, aggregates them with `workers`
// goroutines, and returns a map keyed by account ID.
// It is safe to call with a cancelled context — it drains the channel
// and returns whatever was aggregated before cancellation.
func Run(ctx context.Context, records <-chan parse.Record, workers int) (map[string]*Stats, error) {
	if workers < 1 {
		workers = 1
	}

	// Each worker gets its own local map — no locks on the hot path.
	// We merge the local maps at the end under a single lock pass.
	type result struct {
		local map[string]*Stats
		err   error
	}

	resultc := make(chan result, workers)
	var wg sync.WaitGroup

	for range workers {
		// wg.Go (new in Go 1.25) spawns a goroutine and calls Add(1)/Done()
		// for you — no more manual bookkeeping, no risk of mismatched pairs.
		wg.Go(func() {
			local := make(map[string]*Stats)
			for {
				select {
				case rec, ok := <-records:
					if !ok {
						// Channel closed — all records consumed.
						resultc <- result{local: local}
						return
					}
					apply(local, rec)
				case <-ctx.Done():
					// Cancelled — ship what we have.
					resultc <- result{local: local, err: ctx.Err()}
					return
				}
			}
		})
	}

	// Close resultc after all workers finish so we can range over it safely.
	go func() {
		wg.Wait()
		close(resultc)
	}()

	// Merge all local maps into one global map.
	global := make(map[string]*Stats)
	var firstErr error
	for r := range resultc {
		if r.err != nil && firstErr == nil {
			firstErr = r.err
		}
		merge(global, r.local)
	}
	return global, firstErr
}

// apply updates account stats for one record.
// Called only from within one goroutine's local map — no synchronization needed.
func apply(m map[string]*Stats, rec parse.Record) {
	s, ok := m[rec.Account]
	if !ok {
		s = &Stats{
			Account:  rec.Account,
			MinCents: rec.AmountCents,
			MaxCents: rec.AmountCents,
		}
		m[rec.Account] = s
	}
	s.Count++
	switch rec.Type {
	case "credit":
		s.TotalCents += rec.AmountCents
	case "debit":
		s.TotalCents -= rec.AmountCents
	}
	if rec.AmountCents < s.MinCents {
		s.MinCents = rec.AmountCents
	}
	if rec.AmountCents > s.MaxCents {
		s.MaxCents = rec.AmountCents
	}
}

// merge folds src into dst.
func merge(dst, src map[string]*Stats) {
	for acct, s := range src {
		if d, ok := dst[acct]; ok {
			d.TotalCents += s.TotalCents
			d.Count += s.Count
			if s.MinCents < d.MinCents {
				d.MinCents = s.MinCents
			}
			if s.MaxCents > d.MaxCents {
				d.MaxCents = s.MaxCents
			}
		} else {
			dst[acct] = s
		}
	}
}

// CentsToDisplay formats integer cents as a human-readable dollar string.
// $-14.99 for a net debit of 1499 cents. Never uses float arithmetic.
func CentsToDisplay(cents int64) string {
	sign := ""
	if cents < 0 {
		sign = "-"
		cents = -cents
	}
	return fmt.Sprintf("%s$%d.%02d", sign, cents/100, cents%100)
}
```

```go
package main

import (
	"context"
	"fmt"
	"sync"
)

// Minimal self-contained demo of the worker pool pattern.
// Each worker holds its own local map; we merge at the end.

type record struct {
	account string
	cents   int64
}

type stats struct {
	total int64
	count int
}

func run(ctx context.Context, records <-chan record, workers int) map[string]*stats {
	type result struct{ local map[string]*stats }
	resultc := make(chan result, workers)
	var wg sync.WaitGroup

	for range workers {
		// wg.Go (Go 1.25) handles Add(1)/Done() automatically.
		wg.Go(func() {
			local := make(map[string]*stats)
			for {
				select {
				case r, ok := <-records:
					if !ok {
						resultc <- result{local}
						return
					}
					s := local[r.account]
					if s == nil {
						s = &stats{}
						local[r.account] = s
					}
					s.total += r.cents
					s.count++
				case <-ctx.Done():
					resultc <- result{local}
					return
				}
			}
		})
	}
	go func() { wg.Wait(); close(resultc) }()

	global := make(map[string]*stats)
	for r := range resultc {
		for acct, s := range r.local {
			if g, ok := global[acct]; ok {
				g.total += s.total
				g.count += s.count
			} else {
				global[acct] = s
			}
		}
	}
	return global
}

func main() {
	data := []record{
		{"acct_001", 1499},
		{"acct_002", 5000},
		{"acct_001", 200},
		{"acct_003", 7500},
	}
	ch := make(chan record, len(data))
	for _, r := range data {
		ch <- r
	}
	close(ch)

	result := run(context.Background(), ch, 3)
	for acct, s := range result {
		fmt.Printf("%s: total=%d count=%d\n", acct, s.total, s.count)
	}
}
```

<UnderTheHood title="Why local maps beat a shared mutex map">

The naive approach to a concurrent aggregator is one `sync.Mutex`-protected global map. Workers lock, update, unlock. This *works*, but under a high record rate the mutex becomes a bottleneck: every goroutine serializes at exactly the one place where they could run in parallel.

**The local-map pattern** sidesteps this entirely. Each goroutine owns data that no other goroutine touches — this is called *confinement*. The Go memory model guarantees that writes done by a goroutine before it sends on a channel happen-before the receive of that value. So when a worker sends its local map on `resultc`, the merge goroutine is guaranteed to see all its writes — no mutex needed, zero contention.

**Why not `sync.Map`?** `sync.Map` is designed for append-heavy workloads where the set of keys stabilizes after a warm-up (think HTTP handler route tables). For our workload — many updates to a small set of keys — a plain map behind a mutex, or the local-map-then-merge pattern, is almost always faster. Profile first; reach for `sync.Map` when you have profiler evidence.

**Channel overhead.** A channel is not free: each send/receive involves the Go runtime scheduler. Buffering the records channel (we use 64 here) amortizes the scheduler cost by letting the parser run ahead of the workers. The buffer size is a tuning parameter — measure under your real workload.

**GOMAXPROCS.** As of Go 1.25, Go's default `GOMAXPROCS` is container-aware: it considers logical CPUs, CPU affinity, and Linux cgroup CPU quota. Four workers on a four-core machine with no tighter quota can genuinely run in parallel on different OS threads. On a single-core or one-CPU-quota environment, the workers still run concurrently (interleaved by the scheduler) but not in parallel. The code is correct either way.

**`wg.Go` (new in Go 1.25).** The worker-pool code uses `wg.Go(func(){...})` instead of the older `wg.Add(1)` / `defer wg.Done()` pair. `wg.Go` calls `Add(1)` before launching the goroutine and `Done()` when it returns — eliminating the risk of a mismatched pair (e.g., calling `Add` after the goroutine has already exited). It's a small API but it removes a whole class of WaitGroup misuse.

</UnderTheHood>

<Define term="Graceful shutdown (SIGINT / context)" since="The context Package, In Depth (Part 1)">
**SIGINT** is the Unix signal sent when you press Ctrl-C. A program that ignores it exits immediately, possibly mid-write, leaving partial output. **Graceful shutdown** means the program catches the signal, cancels a `context.Context`, and waits for every goroutine to finish its current unit of work and clean up before exiting. In Go, `signal.NotifyContext` wires an OS signal to a context's cancel function in one call. Why it matters: a tool that can't be safely interrupted is not production-ready — ops will Ctrl-C it the moment a run goes wrong, and you need to guarantee you never leave half-written output or leaked goroutines behind.
</Define>

### Graceful cancellation on SIGINT

The `signal.NotifyContext` call in `main.go` wires up SIGINT (Ctrl-C) to the context. When the signal fires, `ctx.Done()` closes. Both the parser's goroutine and every worker goroutine check `ctx.Done()` in their select loops. They ship what they have and exit cleanly — no abandoned goroutines, no half-written output.

<UnderTheHood title="signal.NotifyContext and os/signal under the hood">

`signal.NotifyContext(ctx, sig...)` is a thin wrapper introduced in Go 1.16. It creates a child context and registers a channel with the OS signal machinery via `signal.Notify`. When one of the listed signals arrives, the runtime's signal handler (a dedicated goroutine that sits on a `sigqueue`) writes to the registered channel. The wrapper reads that channel and calls the context's cancel function — which closes `ctx.Done()`. All goroutines blocking on `ctx.Done()` in a select statement are unblocked immediately.

The `defer stop()` call is important: it tells the runtime to stop forwarding those signals to this context's channel, releasing the channel and preventing a goroutine leak inside the signal package itself. Miss it and the signal package holds a reference to your channel forever.

On Linux, signals arrive as POSIX signals delivered to the process. Go's runtime catches them in a signal handler written in assembly (`sigtramp`), marshals them into the internal `sigqueue`, and unblocks the signal-receiving goroutine. On Windows, `os/signal` maps to `SetConsoleCtrlHandler` for SIGINT.

</UnderTheHood>

## Output

Two output formats: a human-readable table for the terminal, and JSON for piping into other tools. Both write to an `io.Writer` — the real binary passes `os.Stdout`, the tests pass a `bytes.Buffer`.

```go
// report/report.go
package report

import (
	"encoding/json"
	"fmt"
	"io"
	"sort"
	"text/tabwriter"

	"github.com/you/txstat/aggregate"
)

// Write formats stats and writes to w. top limits output to the N
// accounts with the highest absolute total (0 = all).
func Write(w io.Writer, stats map[string]*aggregate.Stats, top int, asJSON bool) error {
	// Sort by absolute total descending for a consistent, useful ordering.
	sorted := make([]*aggregate.Stats, 0, len(stats))
	for _, s := range stats {
		sorted = append(sorted, s)
	}
	sort.Slice(sorted, func(i, j int) bool {
		ai, aj := sorted[i].TotalCents, sorted[j].TotalCents
		if ai < 0 { ai = -ai }
		if aj < 0 { aj = -aj }
		if ai != aj { return ai > aj }
		return sorted[i].Account < sorted[j].Account // stable tie-break
	})
	if top > 0 && top < len(sorted) {
		sorted = sorted[:top]
	}

	if asJSON {
		return writeJSON(w, sorted)
	}
	return writeTable(w, sorted)
}

func writeTable(w io.Writer, rows []*aggregate.Stats) error {
	tw := tabwriter.NewWriter(w, 0, 0, 2, ' ', 0)
	fmt.Fprintln(tw, "ACCOUNT\tNET TOTAL\tMIN\tMAX\tCOUNT")
	fmt.Fprintln(tw, "-------\t---------\t---\t---\t-----")
	for _, s := range rows {
		fmt.Fprintf(tw, "%s\t%s\t%s\t%s\t%d\n",
			s.Account,
			aggregate.CentsToDisplay(s.TotalCents),
			aggregate.CentsToDisplay(s.MinCents),
			aggregate.CentsToDisplay(s.MaxCents),
			s.Count,
		)
	}
	return tw.Flush()
}

type jsonRow struct {
	Account       string `json:"account"`
	NetTotalCents int64  `json:"net_total_cents"`
	MinCents      int64  `json:"min_cents"`
	MaxCents      int64  `json:"max_cents"`
	Count         int    `json:"count"`
}

func writeJSON(w io.Writer, rows []*aggregate.Stats) error {
	out := make([]jsonRow, len(rows))
	for i, s := range rows {
		out[i] = jsonRow{
			Account:       s.Account,
			NetTotalCents: s.TotalCents,
			MinCents:      s.MinCents,
			MaxCents:      s.MaxCents,
			Count:         s.Count,
		}
	}
	enc := json.NewEncoder(w)
	enc.SetIndent("", "  ")
	return enc.Encode(out)
}
```

```go
// TestRunRace verifies that concurrent aggregation produces the correct totals

func TestRunRace(t *testing.T) {
	// 1000 records, 10 accounts, 4 workers — enough to stress the scheduler.
	const numRecords = 1000
	const numAccounts = 10
	const workers = 4

	// Each account receives 100 debit records of 100 cents each.

	records := make(chan parse.Record, numRecords)
```

<Define term="Golden-file test" since="Testing in Go (Part 1)">
A **golden file** is a file on disk holding the known-correct output of a function — the "gold standard" the output must match. The test calls the function, captures its output into a buffer, then diffs the buffer against the file. If the output changes unexpectedly, the test fails. To update intentionally, run with an environment variable (e.g. `UPDATE_GOLDEN=1`) and the test overwrites the file. Why it matters: for formatting-heavy output like a tabular report, manually asserting every field is brittle and verbose. The golden file captures the whole output in one shot and makes any regression immediately visible as a diff.
</Define>

### Golden-file test for report output

A golden file is the saved, known-good output of a function. The test runs the function and diffs against the file. If the output changes, the test fails — and you update the golden file deliberately, not accidentally.

<Solution>

The cleanest approach is a filtering goroutine between the parse and aggregate stages — this keeps each stage's responsibilities clear.

```go
// In main.go, after calling parse.Stream:
minAmount := flag.Int("min-amount", 0, "skip records below this amount in cents")
flag.Parse()
// ... existing code ...
records, errs := parse.Stream(ctx, r)
if *minAmount > 0 {
    records = filterByMinAmount(ctx, records, int64(*minAmount))
}
stats, err := aggregate.Run(ctx, records, *workers)

// The filter stage — a goroutine that gates records.
func filterByMinAmount(ctx context.Context, in <-chan parse.Record, min int64) <-chan parse.Record {
    out := make(chan parse.Record, 64)
    go func() {
        defer close(out)
        for {
            select {
            case rec, ok := <-in:
                if !ok {
                    return
                }
                if rec.AmountCents >= min {
                    out <- rec
                }
            case <-ctx.Done():
                return
            }
        }
    }()
    return out
}
```

<Exercise n={4} title="Context timeout on slow input" level="medium">

Modify `parse.Stream` to accept a per-record timeout: if the scanner hasn't produced a new line within `N` milliseconds, cancel the context. Write a test using a slow `io.Reader` (a reader that sleeps between reads) to verify that the timeout fires and `ctx.Err()` is returned by the aggregator.

<Solution>

```go
// A slow reader for testing:
type slowReader struct {
    data  []byte
    pos   int
    delay time.Duration
}

func (s *slowReader) Read(p []byte) (int, error) {
    if s.pos >= len(s.data) {
        return 0, io.EOF
    }
    time.Sleep(s.delay)
    n := copy(p, s.data[s.pos:s.pos+1]) // one byte at a time
    s.pos += n
    return n, nil
}

func TestStreamTimeout(t *testing.T) {
    ctx, cancel := context.WithTimeout(context.Background(), 50*time.Millisecond)
    defer cancel()

    // The slow reader will take much longer than 50ms to emit a full line.
    r := &slowReader{
        data:  []byte(`{"account":"a","amount_cents":100,"type":"debit"}`),
        delay: 10 * time.Millisecond, // 10ms per byte × 48 bytes = 480ms total
    }

    records, errs := parse.Stream(ctx, r)
    for range records {} // drain
    for range errs {}    // drain

    if ctx.Err() == nil {
        t.Error("expected context to be cancelled by timeout")
    }
}
```

The `select { case <-ctx.Done(): return }` inside `Stream`'s scan loop is what makes this test meaningful — without it, the goroutine would ignore the timeout and leak.

</Solution>

<Exercise n={5} title="Per-account report as a histogram" level="hard">

Add a `-histogram` flag. When set, after the stats table, print an ASCII bar chart showing each account's absolute net total as a horizontal bar, scaled so the largest value fills 40 characters. Use only stdlib. Write a golden-file test for the histogram output.

<Solution>

```go
// In report/report.go:
func writeHistogram(w io.Writer, rows []*aggregate.Stats) error {
    if len(rows) == 0 { return nil }
    // Find the maximum absolute total for scaling.
    var maxAbs int64
    for _, s := range rows {
        abs := s.TotalCents
        if abs < 0 { abs = -abs }
        if abs > maxAbs { maxAbs = abs }
    }
    const width = 40
    fmt.Fprintln(w, "\nHistogram (absolute net total):")
    for _, s := range rows {
        abs := s.TotalCents
        if abs < 0 { abs = -abs }
        barLen := int(float64(abs) / float64(maxAbs) * width)
        bar := strings.Repeat("█", barLen)
        fmt.Fprintf(w, "%-12s |%s| %s\n", s.Account, bar, CentsToDisplay(s.TotalCents))
    }
    return nil
}
```

The golden-file test pattern is identical to the table golden test — run with `UPDATE_GOLDEN=1` to seed, then lock it in by removing the env variable. The histogram uses integer scaling throughout: `int64(abs)` over `int64(maxAbs)`, multiplied by `width` — no float math ever touches the financial data.

You just built a real tool. Let's make sure you know what you actually did:

- **Module layout:** three packages, each with one job. `parse` reads; `aggregate` computes; `report` formats. `main` wires them together with flags and I/O. No logic in `main`.
- **`flag` parsing:** `flag.Int/Bool/String` allocate pointers, `flag.Parse()` fills them from `os.Args[1:]`. In tests, use `flag.NewFlagSet` to avoid touching `os.Args` and to avoid `os.Exit`.
- **`io.Reader` for testability:** the whole program only touches `os.Stdin` and `os.Stdout` in `main`. Every function accepts `io.Reader` and `io.Writer` so tests pass `strings.NewReader` and `bytes.Buffer`.
- **Bounded worker pool:** N goroutines drain a shared channel, each with a private local map. Merge at the end — zero lock contention on the hot path.
- **Graceful cancellation:** `signal.NotifyContext` wires SIGINT to a context; every goroutine checks `ctx.Done()` in a select. Cancel once, everything tears down cleanly.
- **Integer cents, always:** `int64` throughout; `CentsToDisplay` only at the moment of output. No float ever touched the math.
- **The test suite:** table-driven parser tests, a `-race` correctness test for the aggregator, golden-file tests for report output, and a fuzz test for the parser — all passing under `go test -race ./...`.
