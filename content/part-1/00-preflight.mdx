## The Toolchain

<Define term="The Go toolchain" since="Building & Shipping Go Binaries (Part 1)">
The **Go toolchain** is the single `go` binary that ships with every Go installation. It contains the compiler, linker, test runner, formatter, static analyzer, and module manager — invoked as subcommands (`go build`, `go test`, `go vet`, …). One install, everything included. Goes deeper in Building & Shipping Go Binaries.
</Define>

Let's start with the thing you run every single day: the `go` command. It's not a dozen separate tools — it's one binary that does everything. Here's the subset that matters right now.

<ConceptGrid cols={3}>
  <ConceptCard label="go run">`go run main.go` compiles your program into a temp binary and immediately executes it. Perfect for quick iteration. Not for production deployment — the compiled artifact is thrown away.</ConceptCard>
  <ConceptCard label="go build">`go build` compiles your package into a binary on disk. For a `main` package, you get an executable named after the module (or the directory). This is what you ship.</ConceptCard>
  <ConceptCard label="go test">`go test ./...` finds every `_test.go` file in every package under the current directory and runs them. The `./...` pattern is the idiomatic "all packages." Learn it by heart.</ConceptCard>
  <ConceptCard label="go vet">`go vet ./...` runs Go's built-in static analyzer. It catches real bugs the compiler misses — unreachable code, mismatched `Printf` format strings, a mutex copied by value. Always run it.</ConceptCard>
  <ConceptCard label="go fmt">`go fmt ./...` (or `gofmt -w .`) reformats your source to the one true style. There is no debate about where the brace goes. Go decided for you. Comply.</ConceptCard>
  <ConceptCard label="go fix">`go fix ./...` migrates your code to modern Go idioms — updating deprecated APIs and rewriting patterns the toolchain no longer recommends. As of Go 1.26, it's the official home for Go's "modernizer" passes. Run it when upgrading a module's Go version.</ConceptCard>
  <ConceptCard label="go doc">`go doc fmt.Println` prints the documentation for any symbol from any package — standard library or your own. As of Go 1.25, `go doc -http` opens a browsable docs server locally. Faster than searching the web.</ConceptCard>
  <Gotcha>`go run` recompiles from scratch on every invocation. It is fast, but not *instantaneous* for large programs. Use `go build` and run the resulting binary when you need to iterate on performance or compare before/after.</Gotcha>
</ConceptGrid>

Here's a tiny program — a backend service's healthcheck handler stub — that we can use to watch the toolchain in action across this whole chapter:

```go title="healthcheck/main.go"
package main

import (
	"fmt"  // standard library: formatting and printing
	"os"   // standard library: OS-level calls (exit codes, env vars)
)

// version is injected at build time via -ldflags (we'll see this shortly).

func main() {
	fmt.Printf("healthcheck service version=%s\n", version)
	os.Exit(0) // explicit success — unambiguous in scripts and containers
}
```

<Callout kind="pro" title="go build -ldflags: inject values at link time">

That `version = "dev"` variable? In production, teams inject the real Git SHA at build time — no source file touched:

```
go build -ldflags="-X main.version=$(git rev-parse --short HEAD)" -o healthcheck .
```

The linker replaces the string at link time. Your binary bakes in exactly which commit produced it, for free, at no runtime cost.

## Go Modules

Before Go modules (pre-1.11), everyone put their code in `$GOPATH/src/github.com/you/yourproject` and dependency management was a collective nightmare. Modules ended that. Understanding the before-and-after will keep you from being confused by ancient Stack Overflow answers.

### GOPATH: the old world (2 minutes of history)

In the GOPATH era, all Go code on your machine lived under one directory tree — typically `~/go`. Your project was at `$GOPATH/src/github.com/yourorg/yourservice`. Dependencies were fetched with `go get` and landed in `$GOPATH/src` alongside your own code. There was no versioning, no lockfile, and no isolation between projects. Two projects that needed different versions of the same library would fight each other. It was, and I say this with professional authority, a mess.

### Modules: the new world (Go 1.11+, required since 1.16)

<Define term="A Go module (go.mod)" since="Building & Shipping Go Binaries (Part 1)">
A **module** is the unit of versioning and distribution in Go. It's a directory tree of Go source files with a `go.mod` file at the root. `go.mod` declares the module's own import path, the minimum Go version it needs, and its direct dependencies with their minimum versions. The module system replaced the old GOPATH arrangement in Go 1.11 and has been required since 1.16.
</Define>

A **module** is a directory tree of Go source code with a `go.mod` file at its root. The `go.mod` file declares:

1. The module's own import path (e.g. `github.com/acme/payments`)
2. The minimum Go version this module requires
3. Its direct dependencies with their minimum required versions

You can put your module *anywhere* on disk. No GOPATH constraint.

```
go mod init github.com/acme/healthcheck
```

That single command creates a `go.mod`. Here's what it looks like for our healthcheck service:

```go title="go.mod"
module github.com/acme/healthcheck

go 1.25.0

// No dependencies yet — this module is stdlib-only.
```

When you add a dependency (say, a request router):

```
go get github.com/go-chi/chi/v5@v5.2.1
```

Go adds it to `go.mod` and pins the exact checksum in `go.sum`. The `go.sum` file is a cryptographic ledger — every module version you depend on has its expected SHA-256 hash. Tamper with a dependency and the build fails. This is the supply-chain security you didn't have with GOPATH.

<ConceptGrid cols={2}>
  <ConceptCard label="go.mod">Your module's manifest. Declares the module path, minimum Go version, and direct dependencies with minimum versions. Commit this file.</ConceptCard>
  <ConceptCard label="go.sum">The cryptographic lockfile. Every dependency version has a SHA-256 hash. Go verifies it on every build. Commit this file too — it protects the supply chain.</ConceptCard>
  <ConceptCard label="go get">Adds or upgrades a dependency. `go get package@version`. Version can be a semver tag (`v1.2.3`), a branch (`@main`), or a full commit hash.</ConceptCard>
  <ConceptCard label="go mod tidy">Removes unused dependencies from `go.mod` / `go.sum` and adds any missing ones. Run it before every commit. CI should fail if tidy produces a diff.</ConceptCard>
  <Gotcha>Semantic versioning has one sharp Go-specific edge: a module at v2 or higher **must** change its module path to include `/v2` (e.g. `github.com/acme/payments/v2`). This lets a codebase import v1 and v2 of the same module simultaneously. If you see an import path ending in `/v2`, that's why.</Gotcha>
</ConceptGrid>

Here's a small but complete module you can scaffold and build right now. It has a `go.mod`, one source file, and one test:

```go title="main.go"
package main

import "fmt"

// CentsToDollars formats an integer cent amount as a currency string.
// We store money as integer cents — more on why in Part 3.
func CentsToDollars(cents int) string {
	dollars := cents / 100
	remainder := cents % 100
	return fmt.Sprintf("$%d.%02d", dollars, remainder)
}

func main() {
	fmt.Println(CentsToDollars(4299)) // $42.99
	fmt.Println(CentsToDollars(100))  // $1.00
	fmt.Println(CentsToDollars(5))    // $0.05
}
```

## Cross-Compilation & Env

Here's where Go earns its production reputation. Building a Linux ARM64 binary from your macOS laptop takes one command:

```
GOOS=linux GOARCH=arm64 go build -o healthcheck-linux-arm64 .
```

No cross-compiler toolchain. No Docker. No fuss. Go ships with support for every major OS/arch combination baked in, and it produces **statically linked** binaries that need nothing installed on the target machine.

<Define term="GOOS and GOARCH" since="Building & Shipping Go Binaries (Part 1)">
**GOOS** and **GOARCH** are environment variables that tell the Go compiler which OS and CPU architecture to target. Set them before `go build` and you get a binary for that platform — no cross-compiler, no container required. `GOOS=linux GOARCH=arm64` builds for Linux on Apple Silicon/AWS Graviton. The full matrix of supported pairs is printed by `go tool dist list`.
</Define>

The two environment variables every Go developer should know:

<ConceptGrid cols={2}>
  <ConceptCard label="GOOS">Target operating system. Common values: `linux`, `darwin` (macOS), `windows`, `freebsd`. Defaults to the machine you're building on.</ConceptCard>
  <ConceptCard label="GOARCH">Target CPU architecture. Common values: `amd64` (x86-64), `arm64` (Apple Silicon, AWS Graviton), `386`, `arm`. Defaults to the machine you're building on.</ConceptCard>
  <ConceptCard label="GOBIN">Where `go install` puts installed binaries. Defaults to `$GOPATH/bin` (typically `~/go/bin`). Add this to your `$PATH` so installed tools are available.</ConceptCard>
  <ConceptCard label="GOPATH">The old workspace root. Still used as the default location for the module cache and installed binaries. On a modules-era project, you almost never set it manually — the default is fine.</ConceptCard>
  <Gotcha>`CGO_ENABLED=0` is often necessary when cross-compiling. If your code (or a dependency) calls into C libraries via cgo, the cross-compile will fail without the right C toolchain. Setting `CGO_ENABLED=0` forces a pure-Go build. For most backend services, this is exactly what you want — and it makes the binary fully static.</Gotcha>
</ConceptGrid>

Here's the combination that produces a minimal, self-contained Docker image:

```
CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build -o healthcheck .
```

Then in your `Dockerfile`:

```
FROM scratch
COPY healthcheck /healthcheck
ENTRYPOINT ["/healthcheck"]
```

That `FROM scratch` image is the most minimal image possible — no OS, no shell, no libc. Your binary is the only thing in it. This works *only* because Go produces a static binary with the runtime baked in. We'll build on this in the Docker chapter in Part 1.

<UnderTheHood title="What GOOS/GOARCH really do — and why CGO changes everything">

When the Go compiler builds your code, it uses your `GOOS` and `GOARCH` values to select the right **platform-specific assembly stubs** and **OS syscall wrappers** from the standard library. The bulk of the standard library is pure Go and compiles on every platform. Only a thin layer (the `syscall` package and a few others) is platform-specific, and Go ships with prewritten versions for every supported combination.

The complication is **cgo** — Go's foreign-function interface for calling C code. When you import a package that uses cgo (even transitively — `database/sql` drivers, for instance, sometimes pull it in), the Go toolchain invokes your system's C compiler for those files. Cross-compiling with cgo means you need a C compiler *targeting* the destination OS/arch, which is a whole separate setup. `CGO_ENABLED=0` tells the Go toolchain: "don't invoke the C compiler at all; if any package tries to use cgo, it's a compile error." Most standard library code has pure-Go fallbacks; the packages that don't are usually the ones you know about.

**Go version note:** The set of supported `GOOS`/`GOARCH` pairs expands with each release. As of Go 1.26, `go tool dist list` prints the full matrix (over 50 combinations). Check it if you're targeting something exotic.

</UnderTheHood>

<Define term="A static binary">
A **static binary** contains everything it needs to run: your compiled code, all imported packages, and the Go runtime (scheduler, garbage collector, memory allocator). Unlike a Java `.jar` (needs a JVM) or a Node app (needs the `node` runtime plus `node_modules`), a Go static binary runs on a bare machine with nothing else installed. It's why Go is the language of choice for CLIs and container images deployed `FROM scratch`.
</Define>

Let's make this concrete and then tie it back to the animated pipeline we already saw.

When you run `go build -o healthcheck .` on the healthcheck package, you get a **single, statically linked native binary**. No install step. No runtime dependency on the server. No "but what version of the JVM do you have?" No `node_modules`. Copy it to the target machine. Run it.

<UnderTheHood title="The runtime baked into your binary">

Every Go binary contains a copy of the Go runtime — roughly 200–300 KB of compiled code that provides:

- **The goroutine scheduler (GMP model):** multiplexes potentially millions of goroutines onto a small, fixed-size pool of OS threads. We'll go very deep on this in Part 2's scheduler chapter.
- **The garbage collector (tri-color concurrent mark-sweep):** reclaims heap memory without stopping the world for meaningful durations. Also covered deeply in Part 2.
- **The memory allocator:** a size-class allocator (inspired by TCMalloc) that makes small allocations nearly free.
- **The stack manager:** each goroutine starts with a tiny (2–4 KB) stack that grows and shrinks on demand via contiguous-stack copying.

None of this lives in a separate process. None of it requires an install. It's compiled into the binary, initialized before `main` is called, and runs alongside your code for the life of the process.

This is why `go build` produces a binary that is self-contained in a way that JVM or Node.js programs simply are not. It's also why Go binaries tend to be 5–15 MB rather than a few KB — the runtime is part of the payload. That tradeoff has made Go the language of choice for CLIs and microservices that deploy as container images: one `COPY` and you're done.

**Go version note:** Stack sizes, GC algorithm details, and scheduler behavior have changed significantly across versions. This chapter assumes Go 1.26. The GMP scheduler gained asynchronous preemption in Go 1.14 (a goroutine in a tight CPU loop no longer starves other goroutines). The GC gained `GOMEMLIMIT` in Go 1.19. These details matter in Part 2 — flagging them here so nothing surprises you later.

</UnderTheHood>

<Callout kind="note" title="go vet, go fmt, and go fix: non-negotiable hygiene">

Before you `go build` anything you intend to commit, run these two:

```
go vet ./...
go fmt ./...
```

`go vet` catches real bugs. `go fmt` removes all style arguments from code review. Both are zero-cost. Wire them into your editor's save hook and your CI pipeline's first step — you'll never think about them again. Every chapter from here uses code that would pass both.

When upgrading to a new Go version, also run `go fix ./...`. New in Go 1.26, it's the official modernizer: it rewrites deprecated API calls and outdated patterns to current idioms, so your codebase stays current without manual archaeology.

</Callout>

## Reading the Docs

Here's a confession most tutorials are too proud to make: **everybody drowns in `pkg.go.dev` at first.** You look up one function, it returns a type you've never seen, you open that type, it has a field of *another* type, you open that — and twenty minutes later you have thirty tabs open and no idea what you were originally trying to do. Definitions of definitions of definitions. I'm going to fix that permanently, because reading docs well is the single highest-leverage skill that separates an engineer from someone who just copies Stack Overflow.

The root error is simple: **you're reading a reference like it's a book.** `pkg.go.dev` is a lookup table, not a tutorial. You don't read it cover to cover. You go in for one thing, get it, and leave.

<Define term="pkg.go.dev / godoc" since="Pre-flight (Part 1)">
**`pkg.go.dev`** is the official documentation site for every public Go package; **godoc** is the tooling that generates it. Crucially, the docs aren't written separately — they're extracted directly from the **doc comments** in the package's source code. The site for the standard library shows the exact same text you'd get from `go doc` in your terminal, for the Go version that package targets.
</Define>

<Define term="Doc comment & synopsis" since="Pre-flight (Part 1)">
A **doc comment** is the `//` comment placed immediately above an exported declaration. Go has a hard convention: it **starts with the symbol's name**, and its **first sentence is a complete summary** (the *synopsis*) — e.g. *"ReadFile reads the named file and returns the contents."* This is why you can triage any function by reading one sentence: the language *designs* that sentence to stand alone.
</Define>

### The five rules

**1. Anchor on ONE task — never 'understand the package.'**
Not "learn `net/http`." Instead: *"GET a URL, read the body."* You read only the path that serves that task. A task is a destination; without one, every link looks equally worth clicking, and that's how you drown.

**2. First sentence only, to triage.**
Every Go doc's opening sentence is a designed, standalone summary. Read it, decide *is this my function?*, and move on. You do not read the rest of a doc block unless you've committed to using that symbol.

**3. Signature → Example → prose, in that order.**
For any function: read the **signature** (what goes in, what comes out — that's 80% of what you need), then the runnable **Example** on the page, and only fall back to the prose if you're still confused. Examples are faster than definitions because they're real, working code.

**4. Black-box every type until it blocks you.**
A type you *receive* is a name plus what it represents — not a door you must open. `http.Get` hands you `*Response`; you need `.Body` and maybe `.StatusCode`. You do **not** need to expand `Response` → `Header` → `MIMEHeader`. Treat `io.Reader` as "a thing I can `Read()` from." Open a type only when you are actually blocked without its internals.

**5. Two-hop depth limit + a breadcrumb.**
Allow yourself **two hops**: task → function → maybe one type. Past that, jot the name on a scratch line ("come back IF needed") and climb back. Literally indent your trail so the way out is visible:

```text
task: GET url, read body
  http.Get -> (*Response, error)
    Response.Body -> io.ReadCloser   <- STOP. black-box. Read + Close, that's it.
```

### Black-boxing, proven

Rule 4 sounds like a shortcut you'll pay for later. It isn't — it's how Go is *designed* to be used. You program against a type's **contract**, not its guts. Watch one function consume three completely different concrete types it knows nothing about, purely because each satisfies the one-line contract of `io.Reader`:

<GoPlayground>

```go
package main

import (
	"bytes"
	"fmt"
	"io"
	"strings"
)

// countBytes works on ANY io.Reader. We never open io.Reader's definition —
// we only need its contract: "a thing you can Read from." That is black-boxing.
func countBytes(r io.Reader) (int, error) {
	b, err := io.ReadAll(r)
	return len(b), err
}

func main() {
	// Three unrelated concrete types. All satisfy io.Reader. We used each one
	// correctly knowing only its first-sentence doc — never its internals.
	srcs := []io.Reader{
		strings.NewReader("hello"),                          // a string as a reader
		bytes.NewBufferString("from the docs"),              // a byte buffer
		io.LimitReader(strings.NewReader("0123456789"), 4),  // a capped reader
	}
	for _, r := range srcs {
		n, _ := countBytes(r)
		fmt.Printf("%d bytes\n", n)
	}
}
```

</GoPlayground>

Four lines of doc-reading (`strings.NewReader`, `bytes.NewBufferString`, `io.LimitReader`, `io.ReadAll`), zero type-definitions opened, and it works. That's the whole game.

<Callout kind="tip" title="go doc — the terminal antidote to tab-drowning">

The browser invites rabbit holes because everything is a hyperlink. The `go doc` command does not — it prints **one symbol at a time**, offline, for the exact Go version you have installed. There is nothing to click, so you can't fall in.

```text
go doc net/http              # package synopsis + the index
go doc net/http.Get          # one function: signature + its doc
go doc net/http.Response     # a type: its fields + method list (one level, no deeper)
go doc -all net/http | less   # the whole package, piped to a pager you control
go doc -src net/http.Get     # drop to the source — only when prose is genuinely ambiguous
```

Live in `go doc` and the drowning problem mostly disappears: the tool enforces the two-hop discipline for you.

</Callout>

<UnderTheHood title="Why these tricks work: where the docs actually come from">

The reading rules aren't folklore — they exploit how Go documentation is *generated*.

- **Docs are extracted from source.** `go doc` and `pkg.go.dev` read the `//` comment sitting directly above each exported declaration. There is no separate documentation to drift out of date; the comment *is* the doc.
- **The synopsis is a contract.** Convention (enforced by `go vet`/lint tooling) is that a doc comment begins with the symbol's name and that its first sentence summarizes it. That's *why* first-sentence triage is reliable — the language guarantees that sentence stands alone.
- **Examples are tested code.** The runnable Examples on a page come from `func ExampleXxx()` functions in the package's `_test.go` files, each ending in an `// Output:` comment. The toolchain **compiles and runs them as tests** — if an example's printed output stops matching its `// Output:` line, the build fails. So unlike a random blog snippet, an Example on `pkg.go.dev` is *guaranteed to compile and produce what it claims* for that version.
- **`// Deprecated:` is structured.** A paragraph beginning `Deprecated:` is a recognized convention; tools surface it and editors strike the symbol through. Always scan for it before adopting an API.
- **Go 1.19+ doc comments are rich.** Modern doc comments support links, lists, and headings, and `gofmt` reformats them — so the prose you read is structured, not a wall of text.

Read the docs knowing they're machine-extracted, contract-shaped, and test-verified, and you trust the right parts (synopsis, signature, examples) instead of spelunking the prose.

</UnderTheHood>

Watch a struggling junior — thirty browser tabs, depth-first, and "wait, what was I doing?" The difference isn't intelligence or memory. It's **traversal discipline.** You now have it; the only thing left is to refuse, every time, to open the type you don't need.

## Exercises

Beginner or not, you type the code. Reading doesn't build muscle memory. The compiler does.

<Exercise n={1} title="Initialize a module" level="easy">

On your machine (not in the playground): create a new directory `hello-preflight`, `cd` into it, and run `go mod init github.com/yourname/hello-preflight`. Open `go.mod` and read it. What is the `go` directive set to?

Then create `main.go` with `package main` and a `main()` that prints `"pre-flight complete"`. Run it with `go run .`.

<Solution>

```go
// main.go
package main

import "fmt"

func main() {
	fmt.Println("pre-flight complete")
}
```

```
# go.mod after go mod init with Go 1.26:
module github.com/yourname/hello-preflight

go 1.25.0
```

The `go` directive is set by the toolchain that ran `go mod init`. As of Go 1.26, the toolchain deliberately writes `go 1.(N-1).0` — one version behind itself — to maximize compatibility with slightly older toolchains. It's the *minimum* required version; nothing stops you from using a newer toolchain to build it.

</Solution>

</Exercise>

<Exercise n={2} title="Cross-compile for Linux" level="easy">

Using the `main.go` from Exercise 1 (or any Go file with a `main` package), cross-compile it for `linux/amd64`:

```
GOOS=linux GOARCH=amd64 go build -o hello-linux .
```

Run `file hello-linux` (on macOS/Linux). What does it report? Why can't you execute it directly on macOS?

<Solution>

```
$ file hello-linux
hello-linux: ELF 64-bit LSB executable, x86-64, version 1 (SYSV), statically linked, ...
```

It's an ELF binary — the Linux executable format. macOS uses Mach-O. You can't run an ELF binary natively on macOS because the OS kernel doesn't know how to load it. That's the whole point: you'd copy `hello-linux` to a Linux machine (or a Linux container) and run it there. The binary has no external dependencies, so it "just works" on any Linux/amd64 system, regardless of what's installed.

</Solution>

</Exercise>

<Exercise n={3} title="Audit your dependency chain" level="medium">

Create a Go module that imports `golang.org/x/text/cases` (a dependency with a `go.sum` entry). Then run:

```
go mod tidy
cat go.sum
```

How many hash lines does `go.sum` contain? Why does `go.sum` have *more* lines than the single dependency you added?

<Solution>

```go
// main.go
package main

import (
	"fmt"
	"golang.org/x/text/cases"
	"golang.org/x/text/language"
)

func main() {
	c := cases.Title(language.English)
	fmt.Println(c.String("payment webhook received")) // Payment Webhook Received
}
```

After `go mod tidy`, `go.sum` typically contains many lines — often 10–30 for a module with transitive dependencies. Each line covers either the `.zip` hash or the `go.mod` hash of a dependency. `golang.org/x/text` itself depends on `golang.org/x/net` in some versions, which depends on further modules. Go records *all* of them — direct and transitive — so the supply chain is fully locked, not just the top level.

</Solution>

</Exercise>

<Exercise n={4} title="Inject version with ldflags" level="medium">

Add a package-level `var version = "dev"` to a `main.go`. Build it once normally, run it, and observe the output. Then build it again with:

```
go build -ldflags="-X main.version=1.2.3" -o myapp .
```

Run `./myapp`. What changed, and why does this work without modifying source?

<Solution>

```go
package main

import "fmt"

var version = "dev"

func main() {
	fmt.Printf("myapp version=%s\n", version)
}
```

First build: prints `myapp version=dev`.
Second build: prints `myapp version=1.2.3`.

The `-X main.version=1.2.3` linker flag tells the linker to find the symbol named `main.version` in the binary and replace its initial string value. This happens at link time — no source file is modified, and the string is baked into the read-only data section of the binary. In real deployments, teams substitute the Git commit SHA: `-X main.version=$(git rev-parse --short HEAD)`, giving every running binary a directly traceable provenance.

</Solution>

</Exercise>

<Exercise n={5} title="Write go vet past a bug" level="hard">

The following program has a bug that `go vet` will catch. Identify it, explain why `go vet` (not just the compiler) catches it, and fix it.

```go
package main

import "fmt"

func main() {
	name := "Alice"
	amount := 4299
	fmt.Printf("payment from %s: $%d.%d\n", name, amount) // something's wrong here
}
```

<Solution>

```go
package main

import "fmt"

func main() {
	name := "Alice"
	amount := 4299
	// Fixed: provide all three arguments the format string expects.
	fmt.Printf("payment from %s: $%d.%02d\n", name, amount/100, amount%100)
}
```

The bug: the format string has three verbs (`%s`, `%d`, `%d`) but only two arguments (`name`, `amount`) are supplied. The compiler won't catch this because `fmt.Printf` takes a variadic `interface{}` — it has no way to statically check argument counts. `go vet`'s `printf` analyzer does: it parses the format string and counts verbs, then compares against the argument list. Output from the broken version: `payment from Alice: $42%!(EXTRA)` — the runtime will complain, but it won't crash. `go vet ./...` would catch this before it ever runs. I also fixed the format to actually print cents correctly: `$42.99` instead of `$4299`.

</Solution>

</Exercise>

<Recap>

- **`go run`**, **`go build`**, **`go test`**, **`go vet`**, **`go fmt`**: the five commands you will use every single day. Commit them to muscle memory. Add **`go fix`** to your toolchain-upgrade checklist — new in Go 1.26 as the home for all modernizer passes.
- **Go modules** replaced GOPATH. `go.mod` declares your module path and minimum Go version. `go.sum` is the cryptographic lockfile. Commit both. Run `go mod tidy` before every commit.
- **`GOOS` + `GOARCH`** control cross-compilation. Set them as environment variables, point the same `go build` command at your target platform, and get a static binary for any supported OS/arch — no cross-compiler needed.
- **`CGO_ENABLED=0`** produces a fully static binary with no C runtime dependency. Essential for `FROM scratch` Docker images.
- **`go build` produces one self-contained static binary** with the Go runtime (scheduler, GC, allocator) baked in. No install step, no shared libraries, no runtime to manage on the server. That's the superpower.
- **`-ldflags "-X pkg.Var=value"`** injects string values at link time — the standard way to bake a Git SHA into your binary without touching source.

You now have every toolchain concept you need to follow the rest of this course. Chapter 1 is next, and it starts at `package main` and doesn't look back.

</Recap>
