## The Toolchain

*Stop 1 of 5.*

### Step 1: one command, many jobs

<Define term="The Go toolchain">
Everything you need to build Go ships as one `go` command with subcommands: compile, link, test, format, vet, manage dependencies, read documentation. No separate build system, formatter or test runner to choose.
</Define>

<ConceptGrid cols={3}>
  <ConceptCard label="go run .">Build the package and run it immediately. For trying things.</ConceptCard>
  <ConceptCard label="go build">Build and leave an executable on disk. For shipping.</ConceptCard>
  <ConceptCard label="go test ./...">Run the tests in every package below here. <code>./...</code> means "this directory and everything under it".</ConceptCard>
  <ConceptCard label="go vet ./...">Find likely bugs the compiler allows, such as a <code>Printf</code> with the wrong number of arguments (Exercise 5).</ConceptCard>
  <ConceptCard label="gofmt -w . / go fmt ./...">Rewrite code into the one standard layout. Nobody argues about brace placement in Go.</ConceptCard>
  <ConceptCard label="go fix ./...">Since Go 1.26, the home of the "modernizers": rewrites older idioms into current ones. Run it after raising your module's Go version.</ConceptCard>
  <ConceptCard label="go doc">Documentation for any package or symbol, offline: <code>go doc fmt.Println</code>. <code>go doc -http</code> (Go 1.25+) serves browsable docs locally.</ConceptCard>
  <ConceptCard label="go mod / go get">Create modules and add or upgrade dependencies (Stop 2).</ConceptCard>
  <Gotcha><code>go test</code> runs a few of vet's checks automatically, including the <code>Printf</code> one. A test run can fail on a formatting bug even though every assertion passes.</Gotcha>
</ConceptGrid>

### Step 2: what `go run` does

A tiny program to follow through the toolchain:

<GoPlayground>

```go
package main

import (
	"fmt" // formatting and printing
	"os"  // talking to the operating system: exit codes, environment
)

// version can be replaced at build time with -ldflags (Stop 4).
var version = "dev"

func main() {
	fmt.Printf("healthcheck service version=%s\n", version)
	os.Exit(0) // explicit success, for scripts and containers
}
```

</GoPlayground>

`go run` isn't an interpreter. It compiles and links a real executable, then runs it:

## Go Modules

*Stop 2 of 5.*

<ELI5
  concept="Go modules"
  analogy="A shopping list that records the exact brand and size, plus a fingerprint of each tin, so the next person gets identical tins."
  role="reader"
>

A module is a folder with a `go.mod` file, which answers three questions. **Who am I?** The `module` line is your import path. **Which Go?** The `go` line is the minimum language version. **What do I need?** `require` lines list dependencies at exact versions.

Next to it, `go.sum` holds a **fingerprint** (a cryptographic hash) of every dependency's code. If a download ever doesn't match its fingerprint, the build stops.

Commit both files. `go.mod` says which versions; `go.sum` proves they're the same bytes you saw.

</ELI5>

### Step 1: before modules

Until Go 1.11, all Go code on a machine lived in one tree, `$GOPATH/src`, and `go get` fetched whatever each dependency's latest code was. No versions, no lockfile, no way for two projects to need different versions of one library. Old Stack Overflow answers about `GOPATH/src` come from that world. Modules arrived in Go 1.11 and became the default in Go 1.16.

### Step 2: making a module

<Define term="Module">
A tree of Go packages versioned together, with a `go.mod` at its root. It can live anywhere on disk. Its **module path** (like `github.com/acme/healthcheck`) is the prefix of every import path inside it.
</Define>

```bash
$ go mod init github.com/yourname/hello-preflight
go: creating new go.mod: module github.com/yourname/hello-preflight
$ cat go.mod
module github.com/yourname/hello-preflight

go 1.27.0
```

The `go` line is the version of the toolchain that created it, and it's a **minimum**: newer toolchains build it fine, and an older one will download a newer toolchain if needed (Go 1.21+ toolchain management).

### Step 3: adding a dependency

Write code that imports a package you don't have, then let `go mod tidy` resolve it:

```go
package main

import (
	"fmt"

	"golang.org/x/text/cases"
	"golang.org/x/text/language"
)

func main() {
	c := cases.Title(language.English)
	fmt.Println(c.String("payment webhook received")) // Payment Webhook Received
}
```

```text
$ go mod tidy

go: found golang.org/x/text/language in golang.org/x/text v0.42.0

$ cat go.mod
module example.com/text

go 1.27.0

require golang.org/x/text v0.42.0

$ cat go.sum

golang.org/x/text v0.42.0/go.mod h1:ojzP1Z+2QtioaF8DTtO8K5q7JWVVYwZKenzujK0Zd0E=
```

### Step 4: what a mismatch looks like

Change one character of that hash in `go.sum` and build:

```text
$ go build .
verifying golang.org/x/text@v0.42.0: checksum mismatch
	downloaded: h1:JbOZXgfeCPU9gacVtYliJqOhD+zhrEqK4LfdpmlUZqI=
	go.sum:     h1:AAAAAAAAAAAAgacVtYliJqOhD+zhrEqK4LfdpmlUZqI=

SECURITY ERROR
This download does NOT match an earlier download recorded in go.sum.
The bits may have been replaced on the origin server, or an attacker may
have intercepted the download attempt.
```

That's the protection GOPATH never had: if the code for a version you've used ever changes, the build refuses. `go mod verify` checks everything in your module cache the same way (`all modules verified`).

<ConceptGrid cols={2}>
  <ConceptCard label="go get pkg@version">Add or change a dependency: <code>@v1.2.3</code>, <code>@latest</code>, a branch (<code>@main</code>) or a commit hash.</ConceptCard>
  <ConceptCard label="go mod tidy">Make <code>go.mod</code>/<code>go.sum</code> match your imports: add what's missing, drop what's unused. Many CI setups fail if it would change anything.</ConceptCard>
  <ConceptCard label="go mod graph / why">Show who requires what (<code>go mod why -m module</code> answers "why is this here?").</ConceptCard>
  <ConceptCard label="// indirect">A dependency of a dependency, listed because Go records every module the build needs (Exercise 3).</ConceptCard>
  <Gotcha>From v2 on, a module's path must end in the major version: <code>github.com/redis/go-redis/v9</code>. A breaking change gets a new import path, so v8 and v9 can even coexist in one program.</Gotcha>
</ConceptGrid>

**Recap.** `go.mod` names the module, the minimum Go version and exact dependency versions; `go.sum` holds hashes that make any change to downloaded code a hard error. Code comes through a proxy, is checked against a public log, and lives in a shared, read-only cache.

## Cross-Compilation & Env

*Stop 3 of 5.*

### Step 1: building for a different machine

```bash
GOOS=linux GOARCH=arm64 go build -o healthcheck-linux-arm64 .
```

That produces a Linux ARM64 executable on a Mac, with nothing extra installed.

<Define term="GOOS and GOARCH">
Environment variables naming the target operating system (`linux`, `darwin`, `windows`, …) and CPU architecture (`amd64`, `arm64`, …). They default to the machine you're on. `go tool dist list` shows every supported pair: 47 in Go 1.27.
</Define>

It works because Go's runtime and standard library are written in Go (plus a little assembly) and Go has its own linker, so no target-specific C toolchain is needed. The one exception is **cgo** (calling C from Go), which is switched off automatically when you cross-compile. ch26 covers the details, including why that same switch decides whether a binary can run in an empty container.

### Step 2: the environment the go command reads

`go env` prints every setting. The few you'll meet:

<ConceptGrid cols={2}>
  <ConceptCard label="GOPATH">Default `~/go`. No longer where your code lives; it now holds the module cache (`~/go/pkg/mod`) and installed tools (`~/go/bin`).</ConceptCard>
  <ConceptCard label="GOBIN">Where <code>go install</code> puts programs (default <code>$GOPATH/bin</code>). Add it to your <code>PATH</code>.</ConceptCard>
  <ConceptCard label="GOTOOLCHAIN">Which Go toolchain to use. By default the go command switches to a newer one if <code>go.mod</code> asks for it, downloading it as a module.</ConceptCard>
  <ConceptCard label="GOPROXY / GOPRIVATE">Where modules come from (default <code>proxy.golang.org</code>), and which paths are private and should skip the proxy and checksum database.</ConceptCard>
  <ConceptCard label="CGO_ENABLED">Whether cgo may be used. On for native builds when a C compiler is installed; off when cross-compiling.</ConceptCard>
  <Gotcha>Set variables for one command by prefixing them (<code>GOOS=linux go build</code>). <code>go env -w NAME=value</code> changes the default permanently, which is easy to forget and confusing later.</Gotcha>
</ConceptGrid>

**Recap.** `GOOS` and `GOARCH` pick the target; Go needs no cross-toolchain unless cgo is involved. `go env` shows the settings, and `GOPATH` now just holds caches and tools.

<Define term="Self-contained binary">
An executable that needs no separate runtime installed: no JVM, no Node.js, no Python. A Go binary contains its runtime. On Linux, a Go binary built without cgo is also **statically linked**: it doesn't even need the system's C library. (macOS binaries always use the system library `libSystem`, and cgo builds on Linux link the C library dynamically; ch26 shows both.)
</Define>

### Step 2: the runtime you just shipped

<UnderTheHood title="What the runtime does">

- **Scheduler:** runs many goroutines on a few operating-system threads (Part 2, Chapter 5).
- **Garbage collector:** frees unreachable memory while your program runs. Go 1.26 made the new "Green Tea" collector the default, which scans small objects in memory-order batches for better cache use.
- **Memory allocator:** fast per-thread caches of size classes, descended from TCMalloc's design.
- **Goroutine stacks:** each starts small (2 KB by default) and grows by copying to a bigger stack when needed.

It's all compiled in and set up before `main` runs. That's why even "hello" is megabytes, and why deploying Go is "copy one file". The details of these parts change between releases; this book targets Go 1.27.

</UnderTheHood>

### Step 3: stamping a version at link time

Remember `var version = "dev"`? The linker can replace it:

```bash
$ go build -ldflags="-X main.version=1.2.3" -o healthcheck . && ./healthcheck
healthcheck service version=1.2.3
```

No source file changes. Since Go 1.24, `go build` also records the module version from git tags automatically; ch26 covers both.

<Callout kind="note" title="Before every commit">

```bash
gofmt -l .      # lists files that aren't formatted (fix with gofmt -w .)
go vet ./...    # likely bugs
go test ./...   # tests
```

Make your editor format on save and your CI run all three. After raising the `go` line in `go.mod`, also run `go fix ./...`.

</Callout>

**Recap.** `go build` links your code, its imports and the runtime into one file (2.4 MB for hello). On Linux without cgo it's fully static. `-ldflags -X` sets string variables at link time.

## Reading the Docs

*Stop 5 of 5.*

Almost everyone drowns in `pkg.go.dev` at first. You look up one function, it returns a type you don't know, you open that type, it has a field of *another* type… twenty minutes later there are thirty tabs and you've forgotten the question. The mistake is reading a reference like a book. It's a lookup table: go in for one thing, get it, leave.

<Define term="pkg.go.dev and go doc">
`pkg.go.dev` is the documentation site for public Go packages. Its text isn't written separately: it's extracted from the **doc comments** in the source, the same text `go doc` prints in your terminal.
</Define>

<Define term="Doc comment and synopsis">
The `//` comment directly above an exported declaration. By convention it starts with the name being documented and its first sentence summarises it: "ReadFile reads the named file and returns the contents." That first sentence, the **synopsis**, is designed to stand alone.
</Define>

### Step 1: drowning vs surfacing

The task: fetch a URL and read the response body.

### Step 2: five rules

1. **Anchor on one task,** never "understand the package". A task tells you which links to ignore.
2. **Read the first sentence only, to triage.** It's designed to tell you whether this is your function.
3. **Signature, then Example, then prose.** Inputs and outputs are most of what you need; runnable examples beat paragraphs.
4. **Black-box every type until it blocks you.** A type you receive is a name and what it's for, not a door you must open.
5. **Two hops, and a breadcrumb.** Task → function → at most one type. Write down anything deeper and come back only if needed:

```text
task: GET url, read body
  http.Get -> (*Response, error)
    Response.Body -> io.ReadCloser   <- stop: Read it, Close it
```

### Step 3: black-boxing works because Go is built for it

You program against what a type *does*, not what's inside it. One function, three unrelated types, zero type definitions opened:

<GoPlayground>

```go
package main

import (
	"bytes"
	"fmt"
	"io"
	"strings"
)

// countBytes works on anything you can Read from. It never needs to know what.
func countBytes(r io.Reader) (int, error) {
	b, err := io.ReadAll(r)
	return len(b), err
}

func main() {
	for _, r := range []io.Reader{
		strings.NewReader("hello"),                         // a string
		bytes.NewBufferString("from the docs"),             // a byte buffer
		io.LimitReader(strings.NewReader("0123456789"), 4), // a capped reader
	} {
		n, _ := countBytes(r)
		fmt.Printf("%d bytes\n", n)
	}
}
```

</GoPlayground>

```text
5 bytes
13 bytes
4 bytes
```

Each constructor was used from its one-sentence summary alone.

<Callout kind="tip" title="go doc: documentation without tabs">

```bash
go doc net/http              # package summary and index
go doc net/http.Get          # one function: signature and doc
go doc net/http.Response     # one type: fields and methods, one level only
go doc -src net/http.Get     # the source, when the prose is ambiguous
go doc -http                 # a local pkg.go.dev for your own module (Go 1.25+)
```

It prints one thing at a time for the exact Go version you have, with nothing to click, so the two-hop rule enforces itself.

</Callout>

<UnderTheHood title="Why these habits are safe">

- **The docs are the source.** The comment above a declaration *is* its documentation, so it moves with the code.
- **The synopsis is a convention the tools rely on.** `go doc` and pkg.go.dev show the first sentence in listings; linters (not `go vet`) flag comments that don't start with the name.
- **Examples are tests.** Examples on pkg.go.dev come from `func ExampleXxx()` in `_test.go` files, ending with an `// Output:` comment. `go test` runs them and fails if the output differs, so an Example compiles and prints what it claims for that version.
- **`Deprecated:` is structured.** A paragraph starting `Deprecated:` is recognised by tools; editors strike the name through. Check for it before adopting an API.

</UnderTheHood>

## Exercises

Type these on your own machine. Reading doesn't build muscle memory; the compiler does.

<Exercise n={1} title="Initialize a module" level="easy">

Make a directory `hello-preflight`, run `go mod init github.com/yourname/hello-preflight` inside it, and read `go.mod`. What's on the `go` line? Add a `main.go` that prints `pre-flight complete`, and run it twice with `go run .`. Why is the second run faster?

<Solution>

```go
package main

import "fmt"

func main() {
	fmt.Println("pre-flight complete")
}
```

```text
module github.com/yourname/hello-preflight

go 1.27.0
```

The `go` line is the version of the toolchain that ran `go mod init`: a minimum, not a pin. The second run is faster because compiled packages (and, since Go 1.24, the `go run` executable) come from the build cache: 3.66 s, then 0.46 s, then 0.09 s on the machine used for this chapter.

</Solution>

</Exercise>

<Exercise n={2} title="Cross-compile for Linux" level="easy">

Build the program for `linux/amd64` and run `file` on the result. What does it say, and why can't macOS run it?

<Solution>

```text
$ GOOS=linux GOARCH=amd64 go build -o hello-linux .
$ file hello-linux
hello-linux: ELF 64-bit LSB executable, x86-64, version 1 (SYSV), statically linked, Go BuildID=…
```

ELF is Linux's executable format; macOS loads Mach-O files and makes different system calls, so it can't run it. Copy it to any 64-bit x86 Linux machine or container and it runs with nothing installed: "statically linked" means it doesn't even need the C library.

</Solution>

</Exercise>

<Exercise n={3} title="Read your go.sum" level="medium">

Make two modules: one using `golang.org/x/text/cases`, one using `github.com/redis/go-redis/v9`. Run `go mod tidy` in each and count the lines of `go.sum`. Why does one have 2 lines and the other 22?

<Solution>

`golang.org/x/text` v0.42.0 has no dependencies of its own, so `go.sum` has exactly two lines: the hash of its code and the hash of its `go.mod`.

`go-redis/v9` v9.22.0 needs other modules, and `go.mod` lists them as `// indirect`:

```text
require github.com/redis/go-redis/v9 v9.22.0

require (
	github.com/cespare/xxhash/v2 v2.3.0 // indirect
	go.uber.org/atomic v1.11.0 // indirect
	golang.org/x/sys v0.30.0 // indirect
)
```

`go.sum` then holds code hashes for every module the build uses and `go.mod` hashes for modules Go had to read to work out the versions, including ones only go-redis's own tests need (`go mod graph` shows `github.com/bsm/ginkgo/v2` among them). 22 lines in total. Every module that can influence your build is fingerprinted, not only the one you asked for.

</Solution>

</Exercise>

<Exercise n={4} title="Stamp a version" level="medium">

With `var version = "dev"` in `main.go`, build normally and run; then build with `-ldflags="-X main.version=1.2.3"` and run. What changed, and what are the limits of `-X`?

<Solution>

The first build prints `version=dev`, the second `version=1.2.3`. The linker set the variable's initial value; no source changed. Limits: `-X` only sets package-level **string variables** (not constants, not ints), and the name must be the full import path plus the variable (`main.version` for package main, `github.com/acme/app/internal/build.Version` otherwise). A typo is silently ignored, so print the value in a test or at startup.

</Solution>

</Exercise>

<Exercise n={5} title="What vet catches" level="hard">

What's wrong here? Does the compiler catch it? What does it print, and how does `go vet` report it?

```go novet
package main

import "fmt"

func main() {
	name := "Alice"
	amount := 4299
	fmt.Printf("payment from %s: $%d.%d\n", name, amount) // something's wrong here
}
```

<Solution>

Three verbs, two arguments. The compiler accepts it, because `Printf` takes `...any` and the format string is just a string to it. At runtime `fmt` marks the gap instead of crashing:

```text
payment from Alice: $4299.%!d(MISSING)
```

`go vet` parses the format string and reports it before anything runs:

```text
main.go:8:35: fmt.Printf format %d reads arg #3, but call has 2 args
```

The fix also formats the cents properly:

```go
package main

import "fmt"

func main() {
	name := "Alice"
	amount := 4299
	fmt.Printf("payment from %s: $%d.%02d\n", name, amount/100, amount%100) // $42.99
}
```

`go test` runs this vet check too, so a package with this bug fails its tests.

</Solution>

</Exercise>

<Recap>

- One **`go`** command: `run`, `build`, `test`, `vet`, `fmt`, `fix`, `doc`, `mod`. `go run` compiles and links a real executable; the **build cache** makes repeats fast (3.66 s → 0.09 s).
- **`go.mod`** names the module, the minimum Go version and exact dependency versions; **`go.sum`** fingerprints them, and a mismatch stops the build with `SECURITY ERROR`. Commit both; run `go mod tidy`.

- **`go build`** produces one file with the runtime inside (2.4 MB for hello); on Linux without cgo it's fully static. **`-ldflags -X`** stamps string variables.
- **Docs**: one task, synopsis, signature, Example, black-box types, two hops. Use `go doc`.

</Recap>
