## Handlers, Routing & Middleware

The scenario: Meridian's payments service needs a REST API — account lookups, `POST /transfers`, and a live statement stream. Let's stand it up correctly — no guessing, no cowboy wiring — starting from the one interface that governs everything in `net/http`.

**On the job:** Every production Go HTTP service you'll encounter is built on exactly this interface. Get the wiring wrong and you end up with a global mux, no method matching, and zero middleware — and you discover that at code review, not at 3 a.m.

### The `http.Handler` interface

<Define term="handler / http.Handler" since="HTTP Servers: JSON, Streaming & WebSockets (this chapter)">
A **handler** is any value that knows how to respond to an HTTP request. In Go, the `http.Handler` interface has one method — `ServeHTTP(ResponseWriter, *Request)` — and everything in `net/http` speaks it: a function, a struct, a middleware chain, the mux itself. You need it because every incoming request needs *something* that takes the request, does the work, and writes the response — and the single interface lets all these shapes be composed and wrapped uniformly.
</Define>

Every HTTP handler in Go satisfies a single interface:

```go
// From the standard library — the one interface to rule them all.
type Handler interface {
    ServeHTTP(ResponseWriter, *Request)
}
```

That's it. One method. `ResponseWriter` is where you write the response; `*Request` carries the incoming request. Anything that has `ServeHTTP(ResponseWriter, *Request)` is a valid HTTP handler — a struct, a closure, a middleware chain — all the same interface.

`http.HandlerFunc` is a function type that satisfies `Handler`:

```go
// HandlerFunc is a function that IS an http.Handler.
// You don't implement a struct — you write a func with the right signature.
type HandlerFunc func(ResponseWriter, *Request)

func (f HandlerFunc) ServeHTTP(w ResponseWriter, r *Request) { f(w, r) }
```

So you can write a plain function and adapt it with `http.HandlerFunc(myFunc)`. In practice, `http.HandleFunc` does this for you on the default mux. We'll use our own mux below, which is the correct production approach.

### `ServeMux` and Go 1.22+ routing

<Define term="ServeMux (router)">
A **ServeMux** is a request multiplexer — a table that maps URL patterns to handlers. When a request arrives, the mux finds the longest matching pattern and calls that handler's `ServeHTTP`. You need one because a real API has tens of routes, and wiring them by hand into a single `ServeHTTP` is a maintenance disaster. Go 1.22's `ServeMux` also matches on HTTP method (`GET /api/accounts/{id}`) and extracts named wildcards via `r.PathValue`.
</Define>

`http.ServeMux` is Go's built-in router. Before Go 1.22, it was minimal: exact paths and trailing-slash prefix matches. Go 1.22 gave it a major upgrade — **method + path patterns, named wildcards, and precedence rules**.

Go 1.26 changes one existing behavior: ServeMux's automatic subtree-root redirects now use **307 Temporary Redirect** instead of 301. The redirect applies when you register a subtree pattern with a trailing slash (or `...` wildcard) and a client requests the subtree root without the slash. For example, registering `/assets/` redirects `/assets` to `/assets/` unless `/assets` is registered separately.

```go
package main

import (
    "context"
    "fmt"
    "log/slog"
    "net/http"
    "os"
    "os/signal"
    "time"
)

func main() {
    mux := http.NewServeMux()

    // Go 1.22: "METHOD /path" — method is part of the pattern.
    mux.HandleFunc("GET /api/accounts/{id}", getAccount)
    mux.HandleFunc("POST /api/accounts", createAccount)

    // Meridian payments API: transfer creation and lookup.
    mux.HandleFunc("POST /api/transfers", createTransfer)
    mux.HandleFunc("GET /api/transfers/{txID}", getTransfer)

    // Wildcard {id} is captured via r.PathValue("id").
    // A trailing {id...} would match the rest of the path.
    mux.HandleFunc("GET /api/transactions/{txID}", getTransaction)

    srv := &http.Server{
        Addr:              ":8080",
        Handler:           mux,
        ReadHeaderTimeout: 5 * time.Second,  // Slowloris mitigation — always set
        ReadTimeout:       10 * time.Second,
        WriteTimeout:      30 * time.Second,
        IdleTimeout:       120 * time.Second,
    }

    // Graceful shutdown: wait for OS signal, then drain in-flight requests.
    go func() {
        slog.Info("listening", "addr", srv.Addr)
        if err := srv.ListenAndServe(); err != nil && err != http.ErrServerClosed {
            slog.Error("server error", "err", err)
            os.Exit(1)
        }
    }()

    quit := make(chan os.Signal, 1)
    signal.Notify(quit, os.Interrupt)
    <-quit

    ctx, cancel := context.WithTimeout(context.Background(), 15*time.Second)
    defer cancel()
    if err := srv.Shutdown(ctx); err != nil {
        slog.Error("shutdown error", "err", err)
    }
    slog.Info("server stopped cleanly")
}

func getAccount(w http.ResponseWriter, r *http.Request) {
    id := r.PathValue("id") // Go 1.22 wildcard extraction
    fmt.Fprintf(w, "account: %s\n", id)
}

func createAccount(w http.ResponseWriter, r *http.Request) {
    w.WriteHeader(http.StatusCreated)
}

func createTransfer(w http.ResponseWriter, r *http.Request) {
    // Full implementation shown in the Advanced JSON section.
    w.WriteHeader(http.StatusAccepted)
}

func getTransfer(w http.ResponseWriter, r *http.Request) {
    id := r.PathValue("txID")
    fmt.Fprintf(w, "transfer: %s\n", id)
}

func getTransaction(w http.ResponseWriter, r *http.Request) {
    id := r.PathValue("txID")
    fmt.Fprintf(w, "transaction: %s\n", id)
}
```

### Middleware — `func(http.Handler) http.Handler`

<Define term="middleware">
**Middleware** is a function that wraps a handler, runs code before and/or after it, and returns a new handler. The canonical Go signature is `func(http.Handler) http.Handler`. You need it because cross-cutting concerns — authentication, logging, rate limiting, request IDs — belong *outside* your business logic, applied uniformly at the routing layer. Middleware composes like Russian dolls: stack them with a `chain` helper, and they execute in order on every matching request.
</Define>

Middleware is a function that wraps a handler, runs code before and/or after it, and returns the wrapped handler. The canonical signature is `func(http.Handler) http.Handler`.

```go
// logging middleware — wraps any handler, logs every request.
func logging(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        start := time.Now()
        next.ServeHTTP(w, r) // call the inner handler
        slog.Info("request",
            "method", r.Method,
            "path", r.URL.Path,
            "duration", time.Since(start),
        )
    })
}

// auth middleware — checks the Authorization header first.
func requireAuth(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        token := r.Header.Get("Authorization")
        if token == "" {
            http.Error(w, "unauthorized", http.StatusUnauthorized)
            return // short-circuit — inner handler never runs
        }
        next.ServeHTTP(w, r)
    })
}

// chain applies middleware right-to-left so the first listed runs outermost.
func chain(h http.Handler, mw ...func(http.Handler) http.Handler) http.Handler {
    for i := len(mw) - 1; i >= 0; i-- {
        h = mw[i](h)
    }
    return h
}

// usage: every request hits logging, then auth, then the real handler.
mux.Handle("GET /api/accounts/{id}", chain(
    http.HandlerFunc(getAccount),
    logging,
    requireAuth,
))
```

### Graceful shutdown

A production HTTP server must drain in-flight requests before dying. `Server.Shutdown` does it:

```go
// Shutdown waits up to ctx's deadline for active connections to finish,
// then closes everything. New connections are refused immediately.
// Call this after you receive an OS signal.
ctx, cancel := context.WithTimeout(context.Background(), 15*time.Second)
defer cancel()
if err := srv.Shutdown(ctx); err != nil {
    slog.Error("forced shutdown", "err", err)
}
```

The 15-second timeout means: give in-flight requests up to 15 seconds to finish, then hard-close anything that's still open. Wire it to `os.Interrupt` (Ctrl-C) and Kubernetes `SIGTERM` so rolling deploys drain cleanly.

<UnderTheHood title="net/http: one goroutine per connection">

When a new TCP connection is accepted, `net/http` spawns **one goroutine** to own it for its lifetime — the `conn.serve` goroutine. That goroutine reads requests off the connection in a loop, calls your handler's `ServeHTTP` synchronously, and writes the response. For HTTP/1.1, the goroutine handles one request at a time (pipelining is the exception). For HTTP/2, `net/http` runs a multiplexing layer so multiple streams share one connection; each stream gets its own goroutine calling your handler.

`ResponseWriter` is backed by a `bufio.Writer` — writes are buffered until the handler returns or you call `Flush()`. The first call to `Write` or `WriteHeader` freezes the response status; calling `WriteHeader` after `Write` is a no-op (and logs a warning). This is why you must set headers **before** writing the body.

The `Shutdown` method calls `Close` on the underlying `net.Listener` (stops accepting new connections), then polls until all `conn.serve` goroutines finish or the context is cancelled. It uses a `sync.WaitGroup` inside the server to track active connections. Go 1.22+ `Shutdown` also respects HTTP/2 `GOAWAY` graceful close. (Note: this is a conceptual model of the implementation as of Go 1.26; the exact internals are implementation-defined and may change.)

</UnderTheHood>

## Advanced JSON

Meridian's API speaks JSON. But the naive `json.Marshal` / `json.Unmarshal` approach will get you into trouble the moment a field is optional, a payload is polymorphic, or a client sends hostile input. Let's go deeper.

**On the job:** The `POST /transfers` handler is hit by both internal services and third-party integrations. Every one of them is a potential attacker or a misconfigured client. Safe JSON decoding is not optional — it is the first gate.

### Custom `MarshalJSON` and `UnmarshalJSON`

Implement `json.Marshaler` and `json.Unmarshaler` on your types for full control:

```go
package main

import (
    "encoding/json"
    "fmt"
    "time"
)

// Money is an integer number of cents. Never a float.
// We want JSON to serialize as a decimal string ("12.34"), not an integer.
// This prevents floating-point rounding errors in client code.
type Money int64

func (m Money) MarshalJSON() ([]byte, error) {
    // Render as "12.34" — two decimal places, always.
    dollars := m / 100
    cents := m % 100
    if cents < 0 {
        cents = -cents
    }
    s := fmt.Sprintf("%d.%02d", dollars, cents)
    return json.Marshal(s) // produces `"12.34"` (quoted string in JSON)
}

func (m *Money) UnmarshalJSON(data []byte) error {
    var s string
    if err := json.Unmarshal(data, &s); err != nil {
        return fmt.Errorf("Money: expected a quoted decimal string, got: %w", err)
    }
    // Strip optional leading minus before parsing magnitude.
    neg := len(s) > 0 && s[0] == '-'
    if neg {
        s = s[1:]
    }
    var dollars, cents int64
    if _, err := fmt.Sscanf(s, "%d.%02d", &dollars, &cents); err != nil {
        return fmt.Errorf("Money: invalid format %q", s)
    }
    v := dollars*100 + cents
    if neg {
        v = -v
    }
    *m = Money(v)
    return nil
}

// Transfer is Meridian's core domain object — the payload for POST /transfers.
type Transfer struct {
    ID          string    `json:"id"`
    FromAccount string    `json:"from_account"`
    ToAccount   string    `json:"to_account"`
    Amount      Money     `json:"amount"`
    CreatedAt   time.Time `json:"created_at"`
}

func main() {
    xfer := Transfer{
        ID:          "TXN-001",
        FromAccount: "ACC-100",
        ToAccount:   "ACC-200",
        Amount:      Money(1234), // $12.34
        CreatedAt:   time.Now(),
    }
    b, _ := json.Marshal(xfer)
    fmt.Println(string(b))
    // {"id":"TXN-001","from_account":"ACC-100","to_account":"ACC-200","amount":"12.34","created_at":"..."}

    var xfer2 Transfer
    _ = json.Unmarshal(b, &xfer2)
    fmt.Println(xfer2.Amount) // 1234 (cents)
}
```

### `json.RawMessage` for deferred and polymorphic decoding

Sometimes you don't know the shape of a field until you've read another field. `json.RawMessage` lets you defer decoding — capture the raw JSON bytes first, then decode into the right type once you know what it is.

```go
package main

import (
    "encoding/json"
    "fmt"
)

// Event is a polymorphic envelope. The "type" field tells us
// what shape "payload" has — we can't decode both in one pass.
type Event struct {
    Type    string          `json:"type"`
    Payload json.RawMessage `json:"payload"` // raw bytes, decoded later
}

type DepositPayload struct {
    AccountID string `json:"account_id"`
    AmountCents int64 `json:"amount_cents"`
}

type WithdrawalPayload struct {
    AccountID string `json:"account_id"`
    AmountCents int64 `json:"amount_cents"`
    AtmID     string `json:"atm_id"`
}

func handleEvent(data []byte) error {
    var ev Event
    if err := json.Unmarshal(data, &ev); err != nil {
        return err
    }
    switch ev.Type {
    case "deposit":
        var p DepositPayload
        if err := json.Unmarshal(ev.Payload, &p); err != nil {
            return err
        }
        fmt.Printf("deposit: account=%s amount=%d cents\n", p.AccountID, p.AmountCents)
    case "withdrawal":
        var p WithdrawalPayload
        if err := json.Unmarshal(ev.Payload, &p); err != nil {
            return err
        }
        fmt.Printf("withdrawal: account=%s amount=%d atm=%s\n",
            p.AccountID, p.AmountCents, p.AtmID)
    default:
        return fmt.Errorf("unknown event type: %q", ev.Type)
    }
    return nil
}
```

### `omitempty` gotchas and struct embedding

`omitempty` skips a field when it holds the zero value — but the zero value depends on the type:

<ConceptGrid cols={3}>
  <ConceptCard label="int / bool / string → omitted when zero">`omitempty` omits `0`, `false`, and `""`. This is usually what you want.</ConceptCard>
  <ConceptCard label="pointer → omitted when nil">Use a pointer field (`*string`, `*int64`) when you need to distinguish zero from absent.</ConceptCard>
  <ConceptCard label="struct → NEVER omitted">`omitempty` does NOT omit a non-pointer struct even if all its fields are zero. Use `*MyStruct` if you need true omission.</ConceptCard>
  <Gotcha>A `time.Time` zero value (`0001-01-01`) is NOT omitted by `omitempty` because `time.Time` is a struct, not a primitive. Use `*time.Time` or implement `MarshalJSON` to emit `null` for the zero value.</Gotcha>
</ConceptGrid>

Struct embedding flattens fields into the parent's JSON, but can produce surprises with custom marshalers:

```go
type Base struct {
    ID        string    `json:"id"`
    CreatedAt time.Time `json:"created_at"`
}

// Embedding Base is fine — its fields are promoted into Transaction's JSON.
type Transaction struct {
    Base                    // promoted: id, created_at appear at the top level
    Amount    Money         `json:"amount"`
    Reference string        `json:"reference,omitempty"` // omitted when ""
}
```

### Decoding untrusted input safely

A client sending you JSON is a client you cannot trust. Three rules for every handler that decodes a request body:

**Rule 1: limit the body size.** Without a size limit, a client sends a 1 GB body and your server allocates 1 GB of memory. Use `http.MaxBytesReader` on the request body before decoding.

**Rule 2: reject unknown fields.** By default, `json.Decoder` silently ignores JSON keys it doesn't recognize. A typo in a field name sends the data into a black hole. Use `d.DisallowUnknownFields()` to return an error instead.

**Rule 3: decode once, into a strict shape.** Never decode into `map[string]interface{}`. Decode into a typed struct with exactly the fields you expect.

```go
// decodeJSON decodes r.Body into v, applying all three safety rules.
func decodeJSON(w http.ResponseWriter, r *http.Request, v any) bool {
    // Rule 1: limit body to 1 MiB — adjust per your API contract.
    r.Body = http.MaxBytesReader(w, r.Body, 1<<20)

    d := json.NewDecoder(r.Body)

    // Rule 2: reject unexpected fields.
    d.DisallowUnknownFields()

    if err := d.Decode(v); err != nil {
        http.Error(w, "bad request: "+err.Error(), http.StatusBadRequest)
        return false
    }
    return true
}

// Usage in a handler — POST /transfers in Meridian's payments API.
func createTransferHandler(w http.ResponseWriter, r *http.Request) {
    var req struct {
        FromAccount string `json:"from_account"`
        ToAccount   string `json:"to_account"`
        AmountCents int64  `json:"amount_cents"`
        Reference   string `json:"reference"`
    }
    if !decodeJSON(w, r, &req) {
        return // already wrote the error response
    }
    // req is now safe to use — size-bounded and field-validated.
    w.WriteHeader(http.StatusAccepted)
    json.NewEncoder(w).Encode(map[string]string{"status": "accepted"})
}
```

<UnderTheHood title="How json.Decoder streams and where it allocates">

`json.Decoder` wraps an `io.Reader` and reads ahead in 512-byte chunks (internally a `bufio.Reader`). It does not load the entire body into memory before parsing — it streams token by token. This is why `MaxBytesReader` is the right tool: it wraps the body's `Read` method and returns an error the moment the byte count exceeds your limit, aborting the decode mid-stream.

`DisallowUnknownFields` adds a check in the decoder's internal `Object` parsing loop: after matching a JSON key to a struct field, if no match is found, it returns an error rather than skipping the key. The decoder uses reflection (via `encoding/json`'s internal `structFields` cache, built lazily and stored in a `sync.Map`) to map JSON keys to struct fields. The cache is built once per type, so the reflection cost is paid only on first use — subsequent decodes into the same struct type are faster. (This is a simplified model of the Go 1.26 implementation; the exact cache strategy is implementation-defined.)

**Forward look — `encoding/json/v2` (Go 1.25, experimental):** Go 1.25 shipped `encoding/json/v2` behind `GOEXPERIMENT=jsonv2`. It redesigns the API around `json.Marshal`/`json.Unmarshal` with stricter defaults (unknown fields rejected by default, deterministic map key ordering, better error messages), improved performance, and a cleaner streaming API. It is not yet the default in Go 1.26 — standard `encoding/json` is still what you ship with. Keep an eye on it; it will likely graduate to stable in a future release.

</UnderTheHood>

<Define term="streaming response / NDJSON" since="Batch & Large-File Processing (Part 3)">
A **streaming response** writes data to the client incrementally as it is produced, rather than buffering the full payload in memory first. **NDJSON** (Newline-Delimited JSON) is the wire format: one complete JSON object per line, separated by `\n`, with no enclosing array. You need it whenever the result set is unbounded or large — Meridian's statement export, a reconciliation dump, a live event feed — because allocating 400 MB per request to build a single JSON array is a month-end outage waiting to happen.
</Define>

Here's the scenario: Meridian's account-statement endpoint needs to stream up to 100,000 transfers for a monthly report. Naively, you fetch all rows from the database, marshal them into a JSON array, and write the whole thing at once. Your server allocates hundreds of megabytes per request, and the client waits for the entire response before it can show a single row. That's a crime against memory and a crime against UX.

The fix is **streaming**: write rows to the client as they come out of the database. `json.Encoder` lets you marshal one object at a time. NDJSON (newline-delimited JSON) is the format — one JSON object per line, no enclosing array.

**On the job:** Statement export endpoints are almost always written the naive way first. They pass load tests with 10-row accounts and blow up in production when a customer with 80,000 transfers hits the endpoint at month-end. Stream from the start.

### Streaming with `json.Encoder` and NDJSON

```go
package main

import (
    "database/sql"
    "encoding/json"
    "net/http"
)

// Transfer is Meridian's domain object — one row in the account statement.
type Transfer struct {
    ID          string `json:"id"`
    AmountCents int64  `json:"amount_cents"`
    Reference   string `json:"reference"`
}

// streamStatement fetches Meridian transfer rows from the DB and streams
// them as NDJSON (one JSON object per line). Memory usage stays flat
// regardless of how many rows the account has.
func streamStatement(db *sql.DB) http.HandlerFunc {
    return func(w http.ResponseWriter, r *http.Request) {
        // Tell the client this is NDJSON — one JSON object per line.
        w.Header().Set("Content-Type", "application/x-ndjson")

        // Grab the Flusher interface so we can flush each row immediately.
        flusher, ok := w.(http.Flusher)
        if !ok {
            http.Error(w, "streaming unsupported", http.StatusInternalServerError)
            return
        }

        accountID := r.PathValue("accountID")
        rows, err := db.QueryContext(r.Context(),
            `SELECT id, amount_cents, reference
               FROM transfers
              WHERE from_account = $1 OR to_account = $1
              ORDER BY created_at`,
            accountID)
        if err != nil {
            http.Error(w, "query failed", http.StatusInternalServerError)
            return
        }
        defer rows.Close()

        enc := json.NewEncoder(w) // writes to the ResponseWriter directly

        for rows.Next() {
            var xfer Transfer
            if err := rows.Scan(&xfer.ID, &xfer.AmountCents, &xfer.Reference); err != nil {
                // We've already started writing — can't change the status.
                // Log the error and close the stream.
                return
            }
            // Encode appends a newline automatically — that's the ND in NDJSON.
            if err := enc.Encode(xfer); err != nil {
                return
            }
            // Flush pushes this row to the client immediately.
            // Without this, the ResponseWriter buffers until the handler returns.
            flusher.Flush()
        }
    }
}
```

<Callout kind="warn" title="You can't write headers after writing the body">

The moment you call `w.Write(...)` or `w.WriteHeader(...)`, the HTTP headers are frozen and sent. If an error occurs mid-stream, you cannot change the 200 status to 500 — the client has already seen the 200. **Log the error and close the connection.** This is why you must handle any setup errors (like the DB query failing) *before* starting to write rows.

<UnderTheHood title="ResponseWriter buffering and http.Flusher">

`http.ResponseWriter` in `net/http` is backed by a `bufio.Writer` (typically 4 KB). Writes go into the buffer and are flushed to the network automatically when the buffer fills or the handler returns. For streaming you need to flush manually: `w.(http.Flusher).Flush()` calls through to `bufio.Writer.Flush()` which calls the underlying TCP `Write` syscall. Go 1.8+ guarantees that the concrete `ResponseWriter` implements `http.Flusher` for HTTP/1.1. For HTTP/2 it also flushes the frame to the network. The type assertion `flusher, ok := w.(http.Flusher)` is the safe way — some testing `ResponseWriter` implementations (like `httptest.Recorder`) implement `Flusher` but don't actually push bytes anywhere, which is fine for tests.

**Prefer `http.ResponseController` (Go 1.20+):** Rather than type-asserting to `http.Flusher` directly, wrap the `ResponseWriter` in an `http.ResponseController`. It exposes `Flush()`, `SetReadDeadline()`, and `SetWriteDeadline()` through a clean API that works correctly with wrapped `ResponseWriter` types (middleware that embeds a `ResponseWriter` sometimes breaks type assertions):

```go
rc := http.NewResponseController(w)
enc := json.NewEncoder(w)
for _, xfer := range rows {
    enc.Encode(xfer)
    rc.Flush() // no type assertion needed
}
```

## Server-Sent Events

<Define term="server-sent events (SSE)">
**Server-sent events** are a browser-native protocol for one-way, server-to-client streaming over a plain HTTP connection. The server sets `Content-Type: text/event-stream` and keeps the connection open, writing text frames (`id:`, `event:`, `data:`, blank line) as events happen. The client's `EventSource` API reconnects automatically using the last `id:` it saw. You need SSE when the server pushes data the client only reads — live dashboards, notifications, audit feeds — and you want the simplicity of HTTP (works through proxies and CDNs) without the complexity of WebSockets.
</Define>

Server-sent events (SSE) give you a **one-way live stream** from server to client. Think: Meridian's operations dashboard showing live transfer events without the client polling every second — new `POST /transfers` completions appear the moment they're processed. The client opens one HTTP connection and keeps reading; the server pushes updates as they happen.

SSE uses plain HTTP with `Content-Type: text/event-stream`. Each event is a few lines of text terminated by a blank line. The browser (or any SSE client) reconnects automatically if the connection drops, using the last `id:` it received.

**On the job:** SSE is the right tool for Meridian's ops dashboard — operations staff watch transfer completions and failure alerts in real time. It is not the right tool for the trading desk where clients also need to send back filter selections. Know which direction data flows before you pick the technology.

```go
package main

import (
    "fmt"
    "net/http"
)

// TransferEvent is a completed Meridian transfer — pushed live to the ops dashboard.
type TransferEvent struct {
    ID          string
    FromAccount string
    ToAccount   string
    AmountCents int64
}

// sseHandler streams live transfer completion events to the operations dashboard.
func sseHandler(events <-chan TransferEvent) http.HandlerFunc {
    return func(w http.ResponseWriter, r *http.Request) {
        flusher, ok := w.(http.Flusher)
        if !ok {
            http.Error(w, "SSE not supported", http.StatusInternalServerError)
            return
        }

        // SSE headers — these must be set before any Write.
        w.Header().Set("Content-Type", "text/event-stream")
        w.Header().Set("Cache-Control", "no-cache")
        w.Header().Set("Connection", "keep-alive")
        // CORS if needed: w.Header().Set("Access-Control-Allow-Origin", "*")

        var eventID int
        for {
            select {
            case <-r.Context().Done():
                // Client disconnected or server shutting down.
                return
            case ev, ok := <-events:
                if !ok {
                    return // channel closed — stream is over
                }
                eventID++
                // SSE format: id, event type, data, blank line.
                fmt.Fprintf(w, "id: %d\n", eventID)
                fmt.Fprintf(w, "event: transfer\n")
                fmt.Fprintf(w, "data: {\"id\":%q,\"from\":%q,\"to\":%q,\"amount_cents\":%d}\n\n",
                    ev.ID, ev.FromAccount, ev.ToAccount, ev.AmountCents)
                flusher.Flush() // push this event to the client NOW
            }
        }
    }
}

func main() {
    // In production this channel is fed by Meridian's event bus / DB listener.
    events := make(chan TransferEvent, 16)

    // Simulate a feed of live transfer completions.
    go func() {
        for i := 1; ; i++ {
            events <- TransferEvent{
                ID:          fmt.Sprintf("TXN-%04d", i),
                FromAccount: "ACC-100",
                ToAccount:   "ACC-200",
                AmountCents: int64(i * 1000),
            }
            time.Sleep(500 * time.Millisecond)
        }
    }()

    mux := http.NewServeMux()
    mux.Handle("GET /api/transfers/events", sseHandler(events))
    http.ListenAndServe(":8080", mux)
}
```

## WebSockets

<Define term="WebSocket">
A **WebSocket** is a full-duplex, persistent connection between client and server. After an HTTP upgrade handshake, both ends can send frames at any time over a single TCP connection — no request/response cycle, no polling. You need it when the client and server both send in real time: Meridian's trading desk dealers send filter updates back to the server while the server pushes rate ticks to them. SSE only goes one way; WebSockets go both.
</Define>

Full-duplex. Bidirectional. One persistent connection, both ends sending whenever they want. For Meridian's trading desk — where dealers send filter updates (which currency pairs to watch) and the server pushes matching rate ticks in real time — this is your tool.

WebSockets start as an HTTP request and upgrade to the WebSocket protocol. After the upgrade, the connection bypasses the normal HTTP request/response cycle entirely.

**On the job:** WebSocket connections linger for hours. A server that doesn't enforce write deadlines will accumulate goroutines blocked on a single slow client. In a payments system, that slow client can be a mobile app on a flaky cellular connection — and it will block your goroutine until the TCP stack times out, which can take minutes.

### The HTTP Upgrade handshake

<Define term="the HTTP upgrade handshake">
The **HTTP upgrade handshake** is how a plain HTTP connection becomes a WebSocket. The client sends `GET /ws` with `Upgrade: websocket`, `Connection: Upgrade`, and a `Sec-WebSocket-Key` header. The server validates the key and responds `101 Switching Protocols` — after which HTTP is over. The TCP connection is **hijacked** from `net/http` and handed directly to the WebSocket layer; frames (not HTTP packets) now flow in both directions. You need to understand this because after the 101, `net/http`'s `WriteTimeout` no longer applies — the connection is outside its control, and you must enforce deadlines yourself.
</Define>

```
Client → GET /ws HTTP/1.1
         Upgrade: websocket
         Connection: Upgrade
         Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
         Sec-WebSocket-Version: 13

Server → HTTP/1.1 101 Switching Protocols
         Upgrade: websocket
         Connection: Upgrade
         Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo=
```

After the 101, HTTP is over. The TCP connection is **hijacked** from `net/http` and handed to the WebSocket layer. Frames (not HTTP packets) flow in both directions.

### Using `coder/websocket`

The `coder/websocket` package (module path `github.com/coder/websocket`) is context-aware, doesn't require goroutines for lifecycle management, and handles the upgrade cleanly. We'll use it here. It was formerly published as `nhooyr.io/websocket` — the same library, renamed when it moved under the Coder org, so older code and tutorials you find will still import the `nhooyr.io` path. (`gorilla/websocket` is the older alternative — battle-tested but not context-aware.)

```go
package main

import (
    "context"
    "encoding/json"
    "log/slog"
    "net/http"
    "time"

    "github.com/coder/websocket"
    "github.com/coder/websocket/wsjson"
)

// MarketTick is a market-data update pushed to the client.
type MarketTick struct {
    Symbol    string  `json:"symbol"`
    PriceCents int64  `json:"price_cents"`
    Timestamp int64   `json:"ts"`
}

// ClientFilter is a message the client sends to adjust what it sees.
type ClientFilter struct {
    Symbols []string `json:"symbols"`
}

func wsHandler(ticks <-chan MarketTick) http.HandlerFunc {
    return func(w http.ResponseWriter, r *http.Request) {
        // Accept upgrades the connection. Options control origins, compression.
        c, err := websocket.Accept(w, r, &websocket.AcceptOptions{
            OriginPatterns: []string{"localhost:*"},
        })
        if err != nil {
            slog.Error("ws accept", "err", err)
            return
        }
        defer c.CloseNow() // always clean up

        ctx := r.Context()

        // Read goroutine: receive filter updates from the client.
        // Use context cancellation so it tears down when the write side dies.
        readCtx, cancelRead := context.WithCancel(ctx)
        defer cancelRead()

        filterCh := make(chan ClientFilter, 1)
        go func() {
            defer cancelRead()
            for {
                var f ClientFilter
                if err := wsjson.Read(readCtx, c, &f); err != nil {
                    return // client closed or context done
                }
                select {
                case filterCh <- f:
                default: // drop if the handler is behind — market data is live
                }
            }
        }()

        // Current filter — starts accepting all symbols.
        filter := ClientFilter{Symbols: []string{}}

        // Write loop: push market ticks to the client.
        for {
            select {
            case <-readCtx.Done():
                c.Close(websocket.StatusNormalClosure, "bye")
                return
            case f := <-filterCh:
                filter = f // update the active filter
            case tick := <-ticks:
                if !matchesFilter(tick, filter) {
                    continue
                }
                // wsjson.Write encodes v as JSON in a Text frame.
                writeCtx, cancel := context.WithTimeout(readCtx, 5*time.Second)
                err := wsjson.Write(writeCtx, c, tick)
                cancel()
                if err != nil {
                    return
                }
            }
        }
    }
}

func matchesFilter(tick MarketTick, f ClientFilter) bool {
    if len(f.Symbols) == 0 {
        return true // empty filter = accept all
    }
    for _, s := range f.Symbols {
        if s == tick.Symbol {
            return true
        }
    }
    return false
}
```

### Read/write goroutine model and ping/pong

WebSocket connections need keepalives: `ping` frames from the server, `pong` frames from the client. `coder/websocket` handles ping/pong automatically when you use its built-in `CloseRead` mechanism or set a read deadline. Always set a **write deadline** before writing to prevent a slow client from blocking your goroutine forever:

```go
// Always set a write deadline — a slow or malicious client holds the goroutine otherwise.
writeCtx, cancel := context.WithTimeout(ctx, 5*time.Second)
err := wsjson.Write(writeCtx, c, tick)
cancel()
if err != nil {
    // Client too slow or gone — tear down the handler.
    return
}
```

### When to choose SSE vs WebSockets vs polling

<ConceptGrid cols={3}>
  <ConceptCard label="Polling">Simple. Client asks every N seconds. Works everywhere. Best for low-frequency, low-latency-requirement data (daily reports). Wastes bandwidth at high frequency.</ConceptCard>
  <ConceptCard label="SSE (text/event-stream)">Server pushes one-way over HTTP. Works through proxies and CDNs. Best for live dashboards, notifications, audit feeds where the client only watches. Auto-reconnect built in.</ConceptCard>
  <ConceptCard label="WebSockets">Full duplex. Client and server both send freely. Best for interactive real-time features: trading, collaborative editing, chat, multi-player. Proxy-hostile (needs upgrade support).</ConceptCard>
  <Gotcha>WebSockets are overkill for dashboards that only receive data. SSE is simpler, proxy-friendly, and reconnects automatically. Reach for WebSockets only when the client genuinely needs to send messages back to the server in real time.</Gotcha>
</ConceptGrid>

<UnderTheHood title="HTTP hijacking and how WebSockets bypass net/http">

When `websocket.Accept` (or `gorilla/websocket`'s `Upgrader.Upgrade`) is called, it uses `http.Hijacker` — an interface that `net/http`'s concrete `ResponseWriter` implements. `Hijack()` returns the raw `net.Conn` and a `bufio.ReadWriter`, removing the connection from `net/http`'s management entirely. From that moment on, `net/http` forgets about that connection: no more buffering, no more request/response framing, no timeout from `WriteTimeout`. The WebSocket library owns the `net.Conn` directly and reads/writes raw WebSocket frames (defined by RFC 6455).

This is why `Server.WriteTimeout` does NOT protect WebSocket connections after the upgrade — the connection is no longer under `net/http`'s control. You must enforce write timeouts manually using `context.WithTimeout` on every write, as shown above. The `ReadTimeout` similarly has no effect post-upgrade; the WebSocket library's own read context handles it.

`http.Hijacker` is only available on HTTP/1.1 connections. HTTP/2 has its own server-push mechanism and cannot be hijacked in the same way. Most WebSocket deployments use HTTP/1.1 for the upgrade specifically because of this. As of Go 1.26, `net/http` does not natively support WebSockets over HTTP/2.

</UnderTheHood>

## Server Hardening

You've built the handler. You've wired the middleware. Now you're going to skip the part that every junior engineer skips — and that every security postmortem traces back. The default `http.Server` has **no timeouts**. None. A client that sends one byte per minute will hold a goroutine and a TCP connection open indefinitely. A thousand of them will stop your server from accepting legitimate traffic. This attack has a name: Slowloris. And it works on unprotected Go servers out of the box.

**On the job:** You won't spot this in local dev or in a load test with well-behaved clients. It shows up in a production incident when someone opens 10,000 slow connections and your server stops accepting real traffic. Operations pages you. The postmortem says "no timeouts configured." Senior engineers set these reflexively.

### The timeout knobs

`http.Server` exposes five timeout fields. None of them have a default:

| Field | What it covers | Recommended starting value |
|---|---|---|
| `ReadHeaderTimeout` | Time to receive the complete request headers | 5 s — set this first, always |
| `ReadTimeout` | Time to receive headers + full request body | 10–30 s depending on expected payloads |
| `WriteTimeout` | Time to write the full response | 30–60 s; for streaming/SSE, set to 0 and control per-write with `context.WithTimeout` |
| `IdleTimeout` | How long a keep-alive connection may sit idle between requests | 60–120 s |
| _(body cap)_ | `http.MaxBytesReader` on the request body | 1 MiB for API handlers; 0 for streaming |

`ReadHeaderTimeout` is the cheap, must-set Slowloris mitigation: Go reads headers in a tight loop from the TCP buffer, so this timeout fires before any user-land handler code runs. It costs almost nothing but closes the attack surface.

`ReadTimeout` covers the entire read phase including the body. For handlers that stream large uploads, set `ReadTimeout` to 0 and use `http.MaxBytesReader` to cap individual request bodies instead.

`WriteTimeout` covers the write phase. Set it to 0 for SSE and WebSocket handlers — those connections intentionally live beyond a normal write window, and the handlers control their own deadlines per-write via `context.WithTimeout`.

### Capping request bodies with `http.MaxBytesReader`

Even with `ReadTimeout` set, an attacker can send a 2 GB request body inside the timeout window if your upstream connection is fast. `http.MaxBytesReader` wraps the body's `Read` method and returns an error the moment the byte count exceeds your limit:

```go
// In every handler that decodes a request body:
r.Body = http.MaxBytesReader(w, r.Body, 1<<20) // 1 MiB cap
```

For multipart uploads (file ingestion, NACHA batch files), do not load the entire multipart into memory. Use `r.ParseMultipartForm(maxMemory)` — it spills to a temp file on disk when the in-memory threshold is exceeded — and validate each part's size before reading:

```go
// Cap multipart memory to 32 MiB; larger parts spill to temp files.
if err := r.ParseMultipartForm(32 << 20); err != nil {
    http.Error(w, "bad multipart", http.StatusBadRequest)
    return
}
file, header, err := r.FormFile("upload")
if err != nil {
    http.Error(w, "missing file", http.StatusBadRequest)
    return
}
defer file.Close()
// Validate the stated size — do NOT trust Content-Length alone.
if header.Size > 100<<20 { // 100 MiB hard cap per file
    http.Error(w, "file too large", http.StatusRequestEntityTooLarge)
    return
}
```

A client that omits `Content-Length` and streams slowly can still OOM a server that reads multipart naively. Cap every part before reading.

### Secure response headers as middleware

Timeouts and body caps protect the *server*. The next layer protects the *client* — specifically, the browser that renders responses from Meridian's API and its admin console. A handful of response headers tell the browser to refuse a list of attacks it would otherwise happily perform on your users' behalf. They cost nothing to set and they belong in **one** middleware applied to every route — not sprinkled per-handler where someone will forget half of them.

<Define term="secure response headers" since="HTTP Servers: JSON, Streaming & WebSockets (this chapter)">
**Secure response headers** are HTTP response headers that instruct the browser to enforce a security policy on the content you return — which scripts may run (`Content-Security-Policy`), whether to second-guess your declared content type (`X-Content-Type-Options`), how much referrer information to leak (`Referrer-Policy`), and who may embed your pages in a frame (`X-Frame-Options` / CSP `frame-ancestors`). You need them because the browser's *defaults* are permissive for backwards compatibility, and a single missing header is the difference between an XSS payload that fizzles and one that drains an account.
</Define>

The four that matter most for a JSON/admin surface like Meridian's:

<ConceptGrid cols={2}>
  <ConceptCard label="X-Content-Type-Options: nosniff">Forbids **MIME sniffing** — the browser guessing a response's type by peeking at its bytes instead of trusting your `Content-Type`. Without it, a JSON endpoint that reflects user input can be coaxed into being interpreted as HTML/JavaScript. `nosniff` makes the browser honor the declared type, full stop.</ConceptCard>
  <ConceptCard label="Content-Security-Policy">An allowlist of where scripts, styles, images and frames may load from. A strict policy like `default-src 'none'` on a pure JSON API means even if an attacker reflects a `<script>` into a response, the browser refuses to execute it — CSP is the backstop that turns "XSS" into "nothing happened."</ConceptCard>
  <ConceptCard label="Referrer-Policy">Controls how much of the current URL is sent in the `Referer` header on outbound requests. For a fintech app, a URL can carry an account ID or a one-time token; `no-referrer` or `strict-origin-when-cross-origin` stops that from leaking to third-party domains and analytics.</ConceptCard>
  <ConceptCard label="X-Frame-Options / frame-ancestors">Stops **clickjacking**: an attacker embedding Meridian's console in an invisible iframe on their own page and tricking a logged-in user into clicking a transfer button. `X-Frame-Options: DENY` (and its modern CSP equivalent `frame-ancestors 'none'`) forbids framing entirely.</ConceptCard>
  <Gotcha>Set these in middleware, before the handler writes anything. Once a handler calls `w.Write` the headers are frozen and sent — a security-headers middleware that runs *after* the body is written sets nothing. It must wrap the handler and set headers on the way in.</Gotcha>
</ConceptGrid>

The middleware is tiny — it sets the headers on `w.Header()` and then calls the inner handler. Because it sets headers *before* `next.ServeHTTP` writes the body, the headers are in place when the response is flushed:

<GoPlayground>

```go
package main

import (
	"fmt"
	"net/http"
	"net/http/httptest"
)

// secureHeaders sets defensive response headers on every request, then
// calls the next handler. It runs on the way IN, so the headers are set
// before the inner handler writes the body and freezes them.
func secureHeaders(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		h := w.Header()
		// Don't MIME-sniff — honor the declared Content-Type.
		h.Set("X-Content-Type-Options", "nosniff")
		// Pure JSON API: forbid loading any sub-resource, and forbid framing.
		h.Set("Content-Security-Policy", "default-src 'none'; frame-ancestors 'none'")
		// Belt-and-braces clickjacking defense for older browsers.
		h.Set("X-Frame-Options", "DENY")
		// Don't leak account IDs or tokens in the URL to other origins.
		h.Set("Referrer-Policy", "no-referrer")
		next.ServeHTTP(w, r)
	})
}

func getAccount(w http.ResponseWriter, r *http.Request) {
	w.Header().Set("Content-Type", "application/json")
	fmt.Fprint(w, `{"account":"ACC-100","balance_cents":420000}`)
}

func main() {
	// Wrap the mux once — every route inherits the headers. (Here we wrap a
	// single handler for a self-contained demo; in production secureHeaders
	// wraps the whole mux: secureHeaders(mux).)
	h := secureHeaders(http.HandlerFunc(getAccount))

	req := httptest.NewRequest("GET", "/api/accounts/ACC-100", nil)
	rec := httptest.NewRecorder()
	h.ServeHTTP(rec, req)

	for _, k := range []string{
		"X-Content-Type-Options",
		"Content-Security-Policy",
		"X-Frame-Options",
		"Referrer-Policy",
	} {
		fmt.Printf("%-24s %s\n", k+":", rec.Header().Get(k))
	}
	fmt.Println("body:", rec.Body.String())
}
```

<Callout kind="note" title="Tune CSP to the surface — a JSON API is not an SPA">

`default-src 'none'` is the correct, locked-down policy for a **pure JSON API** that never renders HTML. The moment you serve an actual web app (the admin console, a docs page), `'none'` will break it — the browser will refuse to load your own scripts and styles. Then you loosen it deliberately: `default-src 'self'; script-src 'self'; frame-ancestors 'none'`, and add explicit origins for any CDN you actually use. The principle is the same as least-privilege scopes in OAuth2 — start at `none`, open exactly what the page needs, and nothing more. Auth & API Design (Chapter 20) covers the CSRF/`SameSite` side of browser hardening that pairs with these headers.

</Callout>

<Callout kind="warn" title="WriteTimeout and streaming don't mix">

If you set `WriteTimeout` to 30 s on a server that also handles SSE or WebSocket connections, those handlers will be forcibly closed after 30 seconds — regardless of whether they're still actively pushing data. The fix: use a single `http.Server` for short-lived API routes with a `WriteTimeout`, and a **separate `http.Server`** on a different port (or route prefix) for streaming/WebSocket routes with `WriteTimeout: 0`. The streaming handlers control their own write deadlines per-message via `context.WithTimeout`.

</Callout>

<UnderTheHood title="How net/http enforces timeouts">

Timeouts in `http.Server` are implemented via `net.Conn.SetDeadline` on the underlying TCP connection. When `ReadHeaderTimeout` is set, the `conn.serve` goroutine calls `SetReadDeadline` before entering the header-read loop, then resets it to zero (or applies `ReadTimeout`) after headers are read. When `WriteTimeout` is set, it calls `SetWriteDeadline` before calling `ServeHTTP`. Because these are set on the `net.Conn` directly, they fire at the OS level — blocked `Read` and `Write` calls return `net.Error` with `Timeout() == true`. This is why a `WriteTimeout` fires even if your handler is in a `json.Encode` call — the underlying `Write` syscall times out.

For WebSocket connections, `Hijack()` hands you the raw `net.Conn`, and the server no longer sets deadlines on it. You call `SetDeadline` yourself (or use `context.WithTimeout` which the WebSocket library translates to a deadline under the hood). As of Go 1.26, this behaviour is unchanged from Go 1.22. (This is a conceptual model; exact implementation details are subject to change between Go versions.)

</UnderTheHood>

The Reliability Patterns chapter (Part 2) covers how to tune `ReadTimeout` and `WriteTimeout` in the context of p99 latency budgets, circuit breakers, and retry back-off — because the right value for a batch-import endpoint is nothing like the right value for a health-check endpoint. See [Reliability Patterns](/part-2/reliability-patterns).

</Callout>

<Exercise n={1} title="Middleware that logs response status codes" level="easy">

Write a `statusLogging` middleware with signature `func(http.Handler) http.Handler`. It must capture the HTTP response status code written by the inner handler and log it with `slog.Info`. Hint: wrap `http.ResponseWriter` in a struct that overrides `WriteHeader`.

<Solution>

```go
package main

import (
    "log/slog"
    "net/http"
    "net/http/httptest"
    "fmt"
)

type statusRecorder struct {
    http.ResponseWriter
    status int
}

func (sr *statusRecorder) WriteHeader(code int) {
    sr.status = code
    sr.ResponseWriter.WriteHeader(code)
}

func statusLogging(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        rec := &statusRecorder{ResponseWriter: w, status: http.StatusOK}
        next.ServeHTTP(rec, r)
        slog.Info("response", "method", r.Method, "path", r.URL.Path,
            "status", rec.status)
    })
}

func main() {
    h := statusLogging(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        w.WriteHeader(http.StatusTeapot)
        fmt.Fprintln(w, "I'm a teapot")
    }))

    req := httptest.NewRequest("GET", "/brew", nil)
    w := httptest.NewRecorder()
    h.ServeHTTP(w, req)
    fmt.Println("status:", w.Code) // 418
}
```

The key insight: `WriteHeader` is the only way to set the status code. If the inner handler never calls it explicitly, the default 200 is used when the first `Write` happens. We initialize `status` to 200 so a handler that skips `WriteHeader` still logs correctly.

</Solution>

</Exercise>

<Exercise n={2} title="Safe JSON decode helper" level="easy">

Write a `decodeJSON[T any](r *http.Request) (T, error)` generic function that limits the body to 512 KB, disallows unknown fields, and returns the decoded value or an error. No `http.ResponseWriter` in the signature — just parse and return.

<Solution>

```go
package main

import (
    "encoding/json"
    "fmt"
    "io"
    "net/http"
    "net/http/httptest"
    "strings"
)

func decodeJSON[T any](r *http.Request) (T, error) {
    var zero T
    // We can't call MaxBytesReader without a ResponseWriter, so use LimitReader.
    limited := io.LimitReader(r.Body, 512<<10)
    d := json.NewDecoder(limited)
    d.DisallowUnknownFields()
    var v T
    if err := d.Decode(&v); err != nil {
        return zero, fmt.Errorf("decode: %w", err)
    }
    return v, nil
}

type CreateAccountReq struct {
    OwnerName string `json:"owner_name"`
    Currency  string `json:"currency"`
}

func main() {
    body := strings.NewReader(`{"owner_name":"Alice","currency":"USD"}`)
    req := httptest.NewRequest("POST", "/api/accounts", body)

    got, err := decodeJSON[CreateAccountReq](req)
    fmt.Println(err, got) // <nil> {Alice USD}

    // Unknown field — should error.
    body2 := strings.NewReader(`{"owner_name":"Bob","currency":"USD","evil":true}`)
    req2 := httptest.NewRequest("POST", "/api/accounts", body2)
    _, err2 := decodeJSON[CreateAccountReq](req2)
    fmt.Println("unknown field err:", err2 != nil) // true
}
```

Generics make the decode helper reusable for any request shape without reflection tricks or `interface{}`. The caller gets a fully typed result.

</Solution>

</Exercise>

<Exercise n={3} title="Custom JSON marshaler for a Money type" level="medium">

Implement `MarshalJSON` and `UnmarshalJSON` on a `Money int64` type so that `1234` marshals to the string `"12.34"` and back. Negative amounts (`-1234`) should marshal to `"-12.34"`. Write a round-trip test in `main`.

<Solution>

```go
package main

import (
    "encoding/json"
    "fmt"
)

type Money int64

func (m Money) MarshalJSON() ([]byte, error) {
    sign := ""
    v := int64(m)
    if v < 0 {
        sign = "-"
        v = -v
    }
    s := fmt.Sprintf("%s%d.%02d", sign, v/100, v%100)
    return json.Marshal(s)
}

func (m *Money) UnmarshalJSON(data []byte) error {
    var s string
    if err := json.Unmarshal(data, &s); err != nil {
        return fmt.Errorf("Money: expected string, got: %w", err)
    }
    neg := false
    if len(s) > 0 && s[0] == '-' {
        neg = true
        s = s[1:]
    }
    var d, c int64
    if _, err := fmt.Sscanf(s, "%d.%02d", &d, &c); err != nil {
        return fmt.Errorf("Money: bad format %q", s)
    }
    result := d*100 + c
    if neg {
        result = -result
    }
    *m = Money(result)
    return nil
}

func main() {
    cases := []Money{0, 1234, -1234, 100, 9999}
    for _, m := range cases {
        b, err := json.Marshal(m)
        if err != nil {
            fmt.Printf("marshal %d: err %v\n", m, err)
            continue
        }
        var m2 Money
        if err := json.Unmarshal(b, &m2); err != nil {
            fmt.Printf("unmarshal %s: err %v\n", b, err)
            continue
        }
        ok := m == m2
        fmt.Printf("% 6d → %s → % 6d  round-trip=%v\n", m, b, m2, ok)
    }
}
```

The negative case is the tricky one: after the sign is stripped, `Sscanf` parses the magnitude, and we negate at the end. Don't try `%d.%02d` on a negative string — the format doesn't handle the sign.

</Solution>

</Exercise>

<Exercise n={4} title="NDJSON streaming statement handler with httptest" level="medium">

Write an `http.HandlerFunc` that streams a slice of Meridian transfers as NDJSON (the account-statement export), one per line, with a flush after each. Test it using `httptest.NewRecorder`. Parse each line from the response body individually to verify the format is correct.

<Solution>

```go
package main

import (
    "bufio"
    "encoding/json"
    "fmt"
    "net/http"
    "net/http/httptest"
    "strings"
)

// Transfer is Meridian's statement row.
type Transfer struct {
    ID          string `json:"id"`
    AmountCents int64  `json:"amount_cents"`
}

func statementHandler(xfers []Transfer) http.HandlerFunc {
    return func(w http.ResponseWriter, r *http.Request) {
        w.Header().Set("Content-Type", "application/x-ndjson")
        rc := http.NewResponseController(w)
        enc := json.NewEncoder(w)
        for _, xfer := range xfers {
            if err := enc.Encode(xfer); err != nil {
                return
            }
            rc.Flush() // push each row immediately
        }
    }
}

func main() {
    xfers := []Transfer{
        {ID: "TXN-001", AmountCents: 1000},
        {ID: "TXN-002", AmountCents: -500},
        {ID: "TXN-003", AmountCents: 25000},
    }

    req := httptest.NewRequest("GET", "/api/accounts/ACC-100/statement", nil)
    w := httptest.NewRecorder()
    statementHandler(xfers)(w, req)

    fmt.Println("status:", w.Code) // 200

    scanner := bufio.NewScanner(strings.NewReader(w.Body.String()))
    var decoded []Transfer
    for scanner.Scan() {
        line := scanner.Text()
        var xfer Transfer
        if err := json.Unmarshal([]byte(line), &xfer); err != nil {
            fmt.Println("parse err:", err)
            continue
        }
        decoded = append(decoded, xfer)
    }
    fmt.Printf("received %d transfers\n", len(decoded))
    for _, xfer := range decoded {
        fmt.Printf("  %s: %d cents\n", xfer.ID, xfer.AmountCents)
    }
}
```

`bufio.Scanner` splits on newlines by default — exactly right for NDJSON. Each scan gives one complete JSON object. Note the use of `http.NewResponseController(w).Flush()` (Go 1.20+) instead of a type assertion to `http.Flusher` — it works correctly even when the `ResponseWriter` is wrapped by middleware. The `httptest.Recorder` implements the interface; the call is a no-op but the pattern is identical to production.

</Solution>

</Exercise>

<Exercise n={5} title="WebSocket echo server with httptest" level="hard">

Using `github.com/coder/websocket` (or `gorilla/websocket`), write a WebSocket echo handler that reads a JSON message from the client, appends `" (echoed)"` to a `text` field, and writes it back. Test it with `httptest.NewServer` (WebSocket requires a real TCP listener — `httptest.NewRecorder` won't do). The test should upgrade, send a message, read the echo, and close cleanly.

<Solution>

```go
// NOTE: run locally with: go get github.com/coder/websocket
// This will not compile in the playground — github.com/coder/websocket is an external dep.
package main

import (
    "context"
    "fmt"
    "log"
    "net/http"
    "net/http/httptest"

    "github.com/coder/websocket"
    "github.com/coder/websocket/wsjson"
)

type Msg struct {
    Text string `json:"text"`
}

func echoHandler(w http.ResponseWriter, r *http.Request) {
    c, err := websocket.Accept(w, r, nil)
    if err != nil {
        return
    }
    defer c.CloseNow()
    ctx := r.Context()

    var m Msg
    if err := wsjson.Read(ctx, c, &m); err != nil {
        return
    }
    m.Text += " (echoed)"
    wsjson.Write(ctx, c, m)
    c.Close(websocket.StatusNormalClosure, "")
}

func main() {
    srv := httptest.NewServer(http.HandlerFunc(echoHandler))
    defer srv.Close()

    // Convert http:// to ws://
    wsURL := "ws" + srv.URL[len("http"):]

    ctx := context.Background()
    c, _, err := websocket.Dial(ctx, wsURL, nil)
    if err != nil {
        log.Fatal(err)
    }
    defer c.CloseNow()

    if err := wsjson.Write(ctx, c, Msg{Text: "hello"}); err != nil {
        log.Fatal(err)
    }

    var reply Msg
    if err := wsjson.Read(ctx, c, &reply); err != nil {
        log.Fatal(err)
    }
    fmt.Println(reply.Text) // hello (echoed)
    c.Close(websocket.StatusNormalClosure, "")
}
```

`httptest.NewServer` starts a real TCP listener — required for WebSockets because the upgrade needs an actual connection to hijack. The URL swap from `http://` to `ws://` tells the dialer to speak WebSocket. For TLS, use `httptest.NewTLSServer` and `wss://`.

</Solution>

</Exercise>

<Recap>

You now own the full HTTP server stack — and the hardening layer that seniors set without being asked:

- **`http.Handler` / `HandlerFunc`** — the one interface; every handler, middleware, and mux satisfies it. Go 1.22's `ServeMux` adds method + path patterns and `r.PathValue` wildcards. Go 1.26 changes automatic subtree-root slash redirects from 301 to 307.
- **Middleware** as `func(http.Handler) http.Handler` — wraps handlers, runs code before/after, short-circuits with `return`. Chain with a helper; order matters (outermost runs first in, last out).
- **Graceful shutdown** via `Server.Shutdown(ctx)` — drains in-flight requests, stops accepting new ones; wire to `os.Interrupt` and `SIGTERM`.
- **Custom JSON marshalers** give you full control over serialization. `json.RawMessage` defers decoding for polymorphic payloads. `omitempty` is a struct footgun — use pointers when you need true absence. `encoding/json/v2` (Go 1.25 experimental) improves performance and strictness; watch its graduation.
- **Safe JSON decoding**: `http.MaxBytesReader` limits body size, `DisallowUnknownFields` rejects unknown keys, and a typed struct enforces the schema. Three lines that close a class of vulnerabilities. Go 1.25 adds `net/http.CrossOriginProtection` for CSRF on state-mutating routes.
- **NDJSON streaming** with `json.Encoder` + `http.ResponseController.Flush()` keeps memory flat for large result sets (Meridian's statement export). Each row is encoded and flushed immediately — the client receives data before the query finishes.
- **SSE** (`text/event-stream`) is one-way server push over plain HTTP — Meridian's ops dashboard uses it for live transfer events. Auto-reconnects via `Last-Event-ID`. One goroutine per connection, blocked on a channel select.
- **WebSockets** are full-duplex after the HTTP 101 Upgrade handshake. `http.Hijacker` removes the connection from `net/http`'s control — `WriteTimeout` no longer applies. Use context deadlines on every write. Read goroutine + write loop is the standard model.
- **Server hardening**: `ReadHeaderTimeout` (set this first — Slowloris mitigation), `ReadTimeout`, `WriteTimeout`, `IdleTimeout` — none have defaults. `http.MaxBytesReader` caps request bodies. `ParseMultipartForm` spills large uploads to disk. A separate server instance for streaming routes avoids `WriteTimeout` killing long-lived connections.
- **Secure response headers** in one middleware: `X-Content-Type-Options: nosniff` (no MIME sniffing), a strict `Content-Security-Policy` (`default-src 'none'` for a pure JSON API), `Referrer-Policy` (don't leak account IDs/tokens), and `X-Frame-Options: DENY` / CSP `frame-ancestors 'none'` (anti-clickjacking). Set them on the way in, before the handler freezes the headers.
