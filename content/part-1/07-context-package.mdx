## What context.Context Is

Here's the setup, and I want you to feel it before I give you any code.

You're the on-call engineer at a fintech company. Your `/checkout` handler does three things in sequence: it checks fraud signals, it calls the payment processor, and it updates the ledger. Each call can take up to 200ms on a good day. The client browser sets a 2-second timeout and — bang — disconnects after 400ms because the user rage-tapped Back.

What happens to the three in-flight goroutines your handler spawned? Without `context`, the answer is: *nothing*. They keep running. They hammer the downstream services. They hold DB connections. They hold memory. Multiply by 10 000 concurrent users, add a traffic spike, and your service is on its knees.

**That is the problem `context.Context` solves.** It gives every goroutine in a call tree a shared, cooperative cancellation signal that the caller controls.

### The interface

`context.Context` is a Go interface with four methods:

```go
// The full context.Context interface — nothing hidden here.
type Context interface {
    // Done returns a channel that is closed when this context is cancelled
    // or its deadline expires. Nil if this context can never be cancelled.
    Done() <-chan struct{}

    // Err returns nil if Done is not yet closed. After Done is closed,
    // Err returns Cancelled or DeadlineExceeded — never anything else.
    Err() error

    // Deadline returns the time when this context will be cancelled
    // automatically, if one is set.
    Deadline() (deadline time.Time, ok bool)

    // Value returns the value associated with this context for key,
    // or nil if no value is associated with key.
    Value(key any) any
}
```

Four methods. That's the whole API surface. Notice what's missing: there is no `Cancel()` method on the interface. Cancellation is controlled by the *creator* of the context, not by whatever function *receives* it. A function that gets a `ctx context.Context` can only *observe* — it can never cancel upstream.

The `ctx` **value flows down** the call tree — creator to handler to DB driver:

<Define term="context.Context">
A Go interface with four methods — `Done()`, `Err()`, `Deadline()`, `Value()` — that every function doing I/O or spawning goroutines accepts as its first argument. It is the shared, cooperative cancellation signal for a call tree: the creator controls cancellation; every function downstream can only observe it. Without it, a disconnected client leaves orphaned goroutines running until your service falls over.
</Define>

<Define term="cancellation" since="Concurrency: Goroutines, Channels & Select (Part 1)">
Telling every goroutine in a call tree to stop work and return — cooperatively, not forcibly. A goroutine is cancelled when it sees `ctx.Done()` close and returns `ctx.Err()` to its caller. Go has no mechanism to kill a goroutine from outside; cancellation only works if every goroutine in the tree selects on `ctx.Done()`.
</Define>

<Define term="deadline / timeout">
A **deadline** is a wall-clock moment after which the context cancels itself (`context.WithDeadline`). A **timeout** is a duration from now — shorthand for a deadline (`context.WithTimeout(parent, 200*time.Millisecond)`). Both return a `CancelFunc` you must call. If you do not, the deadline timer and the child's slot in the parent cancel list stay alive until the deadline fires or the parent itself cancels.
</Define>

<Define term="the Done() channel">
A `<-chan struct{}` returned by `ctx.Done()`. It is `nil` for `context.Background()` (never fires) and lazily allocated the first time it is called on a cancellable context. When the context is cancelled or its deadline fires, the runtime **closes** the channel — not sends to it. A channel close broadcasts to every goroutine blocking on it simultaneously, at O(1) cost, which is why one `cancel()` call tears down an entire goroutine tree.
</Define>

<Define term="context value (request-scoped)">
Data attached with `context.WithValue(parent, key, val)` and retrieved with `ctx.Value(key)`. It is a linked list of key–value pairs layered on the parent. Use it for request metadata that must cross API boundaries where a function parameter is not feasible — a request ID, a trace span, an authenticated user. Never use it for required function arguments, configuration, or dependencies; those belong in function parameters where the type system can enforce their presence.
</Define>

<Define term="context leak (forgetting cancel())">
When a `With*`-derived context's `CancelFunc` is never called, the context's resources — its slot in the parent's cancel list, and any deadline timer created by `WithTimeout`/`WithDeadline` — stay alive until the deadline fires or the parent context cancels. Under load, each leaked context is a small allocation and retained timer work. Multiply by requests per second and it is a slow memory bleed that kills services by 3 a.m. The fix is always: `defer cancel()` as the very next line after every `With*` call.
</Define>

## Cancellation, Deadlines & Timeouts

You build a context tree by wrapping parent contexts with the four `With*` constructors. Each one returns a new child context and — critically — a `CancelFunc` you must store and eventually call.

### WithCancel — manual cancellation

```go
package main

import (
	"context"
	"fmt"
	"time"
)

func fetchFraudScore(ctx context.Context, accountID string) error {
	// Simulate a slow fraud-scoring service.
	select {
	case <-time.After(300 * time.Millisecond):
		fmt.Println("fraud score fetched for", accountID)
		return nil
	case <-ctx.Done():
		// The context was cancelled before we finished.
		return ctx.Err()
	}
}

func main() {
	// WithCancel: we control exactly when to cancel.
	ctx, cancel := context.WithCancel(context.Background())
	defer cancel() // always — even if we cancel manually below

	go func() {
		time.Sleep(100 * time.Millisecond)
		fmt.Println("client disconnected — cancelling")
		cancel() // manual cancellation: client hung up
	}()

	err := fetchFraudScore(ctx, "acc-8821")
	if err != nil {
		fmt.Println("fraud check aborted:", err) // context.Canceled
		return
	}
}
```

### WithTimeout and WithDeadline — time-based cancellation

`WithTimeout` is shorthand for `WithDeadline(ctx, time.Now().Add(d))`. They do the same thing: cancel the child context automatically when the clock runs out.

```go
package main

import (
	"context"
	"fmt"
	"time"
)

func callPaymentProcessor(ctx context.Context, amount int64) error {
	// Simulate the processor taking 250ms.
	select {
	case <-time.After(250 * time.Millisecond):
		fmt.Printf("processor accepted $%d.%02d\n", amount/100, amount%100)
		return nil
	case <-ctx.Done():
		return fmt.Errorf("payment processor: %w", ctx.Err())
	}
}

func main() {
	// Give the payment processor at most 200ms.
	ctx, cancel := context.WithTimeout(context.Background(), 200*time.Millisecond)
	defer cancel() // always defer cancel — even though the timer fires on its own

	err := callPaymentProcessor(ctx, 4999) // $49.99
	if err != nil {
		fmt.Println("payment failed:", err) // payment failed: payment processor: context deadline exceeded
	}
}
```

### All four constructors at a glance

<ConceptGrid cols={2}>
  <ConceptCard label="WithCancel(parent)">Returns a child that is cancelled when `cancel()` is called, or when `parent` is cancelled — whichever comes first. Use when you control the cancellation trigger (e.g., a client disconnect signal).</ConceptCard>
  <ConceptCard label="WithTimeout(parent, d)">Returns a child that cancels itself after duration `d`, or when `parent` cancels, or when `cancel()` is called. Use for hard SLAs on a single operation.</ConceptCard>
  <ConceptCard label="WithDeadline(parent, t)">Returns a child that cancels at wall-clock time `t`. Use when you need to cancel at a specific moment (e.g., "end of business day batch window").</ConceptCard>
  <ConceptCard label="WithValue(parent, key, val)">Attaches a value to the context tree. Returns a child with no cancellation change. The key should be an unexported type — see the "Values & Their Misuse" section for the full story.</ConceptCard>
  <Gotcha>When you call `context.WithTimeout(parent, d)` and the parent already has a deadline that fires *sooner*, the child inherits that sooner deadline. Your `d` is an upper bound, not a guarantee. Always check `ctx.Deadline()` if you need to know the actual expiry.</Gotcha>
</ConceptGrid>

## How Cancellation Signals

This is the section most tutorials rush past, and that's a crime. Let me show you exactly what happens inside a cancelled context — because once you see it, the select pattern writes itself.

### The Done() channel is closed, not sent to

`ctx.Done()` returns a receive-only channel of type `<-chan struct{}`. When the context is cancelled, the runtime **closes** that channel — it does not send a value. A closed channel can be received on immediately by any number of goroutines; that's the broadcast mechanism. Every goroutine blocking on `<-ctx.Done()` wakes up at the same instant when the context is cancelled.

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"time"
)

// fanOutCheckout fans work out to fraud checking and payment processing
// in parallel, cancelling both if either fails or the context expires.
func fanOutCheckout(ctx context.Context, accountID string, amountCents int64) error {
	// A child context lets us cancel both goroutines if one fails.
	ctx, cancel := context.WithCancel(ctx)
	defer cancel()

	var wg sync.WaitGroup
	errs := make(chan error, 2) // buffered so goroutines don't block

	wg.Add(2)

	// Goroutine 1: fraud check
	go func() {
		defer wg.Done()
		select {
		case <-time.After(180 * time.Millisecond): // simulates 180ms work
			fmt.Println("fraud: OK")
		case <-ctx.Done():
			errs <- fmt.Errorf("fraud check: %w", ctx.Err())
			return
		}
	}()

	// Goroutine 2: payment processor
	go func() {
		defer wg.Done()
		select {
		case <-time.After(350 * time.Millisecond): // simulates 350ms work — too slow
			fmt.Println("payment: OK")
		case <-ctx.Done():
			errs <- fmt.Errorf("payment: %w", ctx.Err())
			return
		}
	}()

	// Close errs when all goroutines finish so the range below terminates.
	go func() {
		wg.Wait()
		close(errs)
	}()

	for err := range errs {
		if err != nil {
			cancel() // cancel the sibling
			return err
		}
	}
	return nil
}

func main() {
	// 200ms deadline: fraud check succeeds; payment processor is too slow.
	ctx, cancel := context.WithTimeout(context.Background(), 200*time.Millisecond)
	defer cancel()

	err := fanOutCheckout(ctx, "acc-8821", 4999)
	if err != nil {
		fmt.Println("checkout failed:", err)
	}
}
```

### ctx.Err() — two possible answers

After `Done()` is closed, `ctx.Err()` tells you *why*:

- `context.Canceled` — someone called `cancel()` explicitly.
- `context.DeadlineExceeded` — the wall-clock deadline or timeout fired.

That distinction matters at the call site: a `DeadlineExceeded` often warrants a user-facing "took too long, try again" message; a `Canceled` is usually silent cleanup. Always check `errors.Is(err, context.DeadlineExceeded)` rather than string-comparing the error message.

### WithCancelCause and Cause — knowing *why* it was cancelled (Go 1.20+)

`ctx.Err()` tells you *that* the context was cancelled, but only in two coarse categories: `Canceled` or `DeadlineExceeded`. Sometimes you need the *reason* — the specific error that caused the cancellation. Go 1.20 added `context.WithCancelCause` and `context.Cause` for exactly this.

```go
// WithCancelCause returns a child context and a cause-aware cancel function.
ctx, cancel := context.WithCancelCause(parent)

// Call it with a specific error to record the cause.
cancel(errors.New("fraud score service unavailable"))

// Later, anywhere that holds ctx:
cause := context.Cause(ctx)   // → "fraud score service unavailable"
err   := ctx.Err()            // → context.Canceled (unchanged)
```

`context.Cause(ctx)` walks the context chain to find the first cause set by a `CancelCauseFunc`. If the context was cancelled the old-fashioned way (a plain `CancelFunc`, or a deadline expiry), `Cause` returns the same value as `ctx.Err()`.

```go
package main

import (
	"context"
	"errors"
	"fmt"
)

var ErrUpstreamDown = errors.New("upstream service unavailable")

func callFraudService(ctx context.Context) error {
	// Simulate detecting that the upstream is down.
	return ErrUpstreamDown
}

func main() {
	ctx, cancel := context.WithCancelCause(context.Background())
	defer cancel(nil) // nil cause = plain Canceled if not already cancelled

	err := callFraudService(ctx)
	if err != nil {
		// Cancel with a specific cause so the caller knows exactly what happened.
		cancel(fmt.Errorf("fraud check: %w", err))
	}

	fmt.Println("ctx.Err():", ctx.Err())          // context.Canceled
	fmt.Println("context.Cause:", context.Cause(ctx)) // fraud check: upstream service unavailable
	fmt.Println("is upstream:", errors.Is(context.Cause(ctx), ErrUpstreamDown)) // true
}
```

<Callout kind="note" title="WithCancelCause vs plain WithCancel">

Use `WithCancelCause` any time callers downstream need to distinguish *why* a context was cancelled beyond just "canceled" vs "deadline exceeded." It costs nothing extra — the cause is stored as a single `error` field in the cancel context. If you call `cancel(nil)`, `context.Cause` returns `context.Canceled`, identical to the plain `WithCancel` behavior.

</Callout>

<Callout kind="advanced" title="os/signal.NotifyContext now exposes the signal as the cause (Go 1.26)">

`os/signal.NotifyContext` is the idiomatic way to cancel a context on SIGINT, SIGTERM, or other OS signals — common in graceful-shutdown code. As of **Go 1.26**, `context.Cause(ctx)` returns an error describing the signal that fired:

```go
package main

import (
	"context"
	"fmt"
	"os"
	"os/signal"
	"syscall"
	"time"
)

func main() {
	// NotifyContext cancels ctx when SIGINT or SIGTERM arrives.
	// Since Go 1.26, the cancellation cause identifies the signal.
	ctx, stop := signal.NotifyContext(context.Background(), os.Interrupt, syscall.SIGTERM)
	defer stop()

	// ... start servers, workers, etc. ...

	<-ctx.Done() // blocks until a signal arrives

	cause := context.Cause(ctx)
	fmt.Printf("shutting down: received signal (%v)\n", cause)
	// e.g. "shutting down: received signal (interrupt)"

	stop() // de-register the signal handler; further signals terminate normally

	// run graceful shutdown with a fresh context
	shutdownCtx, cancel := context.WithTimeout(context.Background(), 10*time.Second)
	defer cancel()
	_ = shutdownCtx // pass to server.Shutdown, DB.Close, etc.
}
```

Before Go 1.26, `context.Cause(ctx)` did not identify which signal cancelled a `NotifyContext`. Now it returns an error describing the `os.Signal` that fired, so you can log the exact signal that triggered the shutdown.

</Callout>

<UnderTheHood title="How Done() is lazily created and how the cancel tree is wired (Go 1.26)">

The `Done()` channel is **not** allocated when you call `context.WithCancel`. The internal `cancelCtx` struct stores a `chan struct{}` field that starts `nil`. The first call to `Done()` on a given context creates the channel and stores it — that lazy creation avoids allocating a channel for contexts that never actually need cancellation signalling (common in code that propagates a context but never selects on Done).

**The propagation tree is a linked list of parents.** Each `cancelCtx` holds a pointer to its parent. When `cancel()` is called, it:
1. Closes `c.done` (the channel).
2. Walks its slice of registered children and cancels each one recursively.
3. Removes itself from the parent's child list.

In Go 1.7–1.21, the child-registration walked the parent chain at construction time via `propagateCancel`. In **Go 1.22**, the propagation was overhauled: instead of a global `sync.Mutex` over the tree, each `cancelCtx` now uses its own fine-grained lock, reducing contention under high-concurrency workloads with many child contexts.

**Go 1.21 added two new constructors worth knowing:**

- `context.WithoutCancel(parent)` — returns a child that is *never* cancelled, even when `parent` is. Use it to spawn a goroutine that should outlive the request (e.g., an audit-log write you commit even if the HTTP handler times out). Dangerous if misused — that goroutine needs its own lifetime management.
- `context.AfterFunc(ctx, f)` — registers a function `f` to run in its own goroutine when `ctx` is done. Returns a stop function; call it to prevent `f` from running if `ctx` hasn't fired yet. This is a cleaner alternative to `go func() { <-ctx.Done(); cleanup() }()`.

**context.Background() and context.TODO()** are both `*emptyCtx` values, a private type that implements `Context` with all no-op methods. Their `Done()` returns `nil` always, which is why selecting on `context.Background().Done()` never fires.

The `hchan` underlying `Done()` uses a zero-size element type (`struct{}`), so the channel carries no data payload — it exists purely as a coordination primitive. Closing it is O(1) in the runtime scheduler: the runtime walks the blocked receivers list and makes each one runnable. This is why a single close broadcasts to arbitrarily many goroutines with constant overhead.

</UnderTheHood>

## Propagation in Practice

Let's cement the three propagation paths you'll encounter daily: goroutine trees, HTTP handlers, and database calls.

### Goroutine trees — the real scenario

The checkout fan-out above is the canonical pattern. A few sharper rules to internalize:

**Rule 1: Always pass the *derived* context to child goroutines, not a fresh one.** Passing `context.Background()` to a child severs it from the parent's deadline — the parent's cancellation can no longer reach it.

**Rule 2: When you fan out and want to cancel siblings on the first error, make a child context before spawning.**

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"time"
)

// processTransfer fans out three checks in parallel.
// If any check fails (or the context expires), the others are cancelled.
func processTransfer(ctx context.Context, fromAcc, toAcc string, cents int64) error {
	ctx, cancel := context.WithTimeout(ctx, 150*time.Millisecond)
	defer cancel()

	type result struct{ name string; err error }
	ch := make(chan result, 3)

	checks := []struct {
		name string
		work func() error
	}{
		{"balance", func() error {
			time.Sleep(80 * time.Millisecond)
			return nil // sufficient balance
		}},
		{"fraud", func() error {
			time.Sleep(200 * time.Millisecond) // too slow — will be cancelled
			return nil
		}},
		{"compliance", func() error {
			time.Sleep(60 * time.Millisecond)
			return nil
		}},
	}

	for _, c := range checks {
		go func() {
			done := make(chan error, 1)
			go func() { done <- c.work() }()
			select {
			case err := <-done:
				ch <- result{c.name, err}
			case <-ctx.Done():
				ch <- result{c.name, fmt.Errorf("%s: %w", c.name, ctx.Err())}
			}
		}()
	}

	var errs []error
	for i := 0; i < 3; i++ {
		r := <-ch
		if r.err != nil {
			errs = append(errs, r.err)
		}
	}
	return errors.Join(errs...)
}

func main() {
	ctx := context.Background()
	err := processTransfer(ctx, "acc-001", "acc-002", 50000) // $500.00
	if err != nil {
		fmt.Println("transfer failed:", err)
		return
	}
	fmt.Println("transfer OK")
}
```

### HTTP handlers — r.Context() and server-side cancellation

Every `*http.Request` carries a context that the `http.Server` cancels when the client disconnects. You get it with `r.Context()` and you pass it everywhere downstream.

```go
package main

import (
	"context"
	"fmt"
	"net/http"
	"time"
)

func checkoutHandler(w http.ResponseWriter, r *http.Request) {
	// r.Context() is already wired to the server's cancellation.
	// When the client disconnects, this context is cancelled automatically.
	ctx := r.Context()

	// Add a 200ms hard deadline for the entire handler.
	ctx, cancel := context.WithTimeout(ctx, 200*time.Millisecond)
	defer cancel()

	if err := processCheckout(ctx, r.URL.Query().Get("account")); err != nil {
		if ctx.Err() != nil {
			// Context expired — this is an expected timeout, not a bug.
			http.Error(w, "request timed out", http.StatusGatewayTimeout)
			return
		}
		http.Error(w, "checkout failed: "+err.Error(), http.StatusInternalServerError)
		return
	}

	fmt.Fprintln(w, "OK")
}

func processCheckout(ctx context.Context, accountID string) error {
	select {
	case <-time.After(150 * time.Millisecond): // simulate work
		return nil
	case <-ctx.Done():
		return ctx.Err()
	}
}

func main() {
	http.HandleFunc("/checkout", checkoutHandler)
	fmt.Println("listening on :8080")
	// http.ListenAndServe(":8080", nil)
	// (Commented out so the playground terminates cleanly.)
	fmt.Println("(server not started in playground mode)")
}
```

### Database calls — QueryContext and ExecContext

Every method in `database/sql` has a context-aware variant: `QueryContext`, `QueryRowContext`, `ExecContext`, `BeginTx`. Pass your `ctx` and the driver cancels the in-flight network call when the context fires.

```go
package main

import (
	"context"
	"database/sql"
	"fmt"
	"time"
)

// fetchAccount queries the ledger for an account balance.
// ctx carries the caller's deadline — if the query takes too long, it's aborted.
func fetchAccount(ctx context.Context, db *sql.DB, accountID string) (int64, error) {
	var balanceCents int64

	// QueryRowContext cancels the underlying Postgres network read
	// when ctx.Done() fires — no goroutine leak inside the driver.
	err := db.QueryRowContext(ctx,
		`SELECT balance_cents FROM accounts WHERE id = $1 FOR SHARE`,
		accountID,
	).Scan(&balanceCents)

	if err != nil {
		return 0, fmt.Errorf("fetchAccount %s: %w", accountID, err)
	}
	return balanceCents, nil
}

// postTransfer wraps a transfer in a transaction with a deadline.
func postTransfer(ctx context.Context, db *sql.DB, from, to string, cents int64) error {
	ctx, cancel := context.WithTimeout(ctx, 500*time.Millisecond)
	defer cancel()

	tx, err := db.BeginTx(ctx, nil)
	if err != nil {
		return fmt.Errorf("begin: %w", err)
	}
	defer tx.Rollback() // safe no-op if Commit succeeds

	// Debit and credit — both inside the same context-aware transaction.
	if _, err = tx.ExecContext(ctx,
		`UPDATE accounts SET balance_cents = balance_cents - $1 WHERE id = $2`,
		cents, from,
	); err != nil {
		return fmt.Errorf("debit: %w", err)
	}

	if _, err = tx.ExecContext(ctx,
		`UPDATE accounts SET balance_cents = balance_cents + $1 WHERE id = $2`,
		cents, to,
	); err != nil {
		return fmt.Errorf("credit: %w", err)
	}

	return tx.Commit()
}

func main() {
	fmt.Println("context-aware DB calls: QueryRowContext / ExecContext / BeginTx")
	fmt.Println("Pass ctx as first argument — the driver cancels the network read on deadline.")
	_ = postTransfer // illustrative; no real DB in playground
}
```

## Values & Their Misuse

`context.WithValue` is the one constructor that gets weaponized. Let me be very clear about what it's for, and very clear about what it is not.

**What it's for:** request-scoped values that cross API boundaries where adding a function parameter isn't feasible. The canonical examples are a request ID for logging, an authenticated user identity, and a trace span.

**What it is not:** a backdoor for optional parameters, configuration, or anything that could be a normal function argument.

### The typed-key pattern — the only right way

If you use a plain string or built-in type as a context key, any other package using the same string will collide with you. The fix is a private, unexported type:

```go
package main

import (
	"context"
	"fmt"
)

// requestKey is an unexported type. No other package can construct a key
// of this exact type — guaranteed no collision, even if they use the same string.
type requestKey struct{}

// userKey separates user identity from requestID — different types, different slots.
type userKey struct{}

// WithRequestID attaches a request ID to the context.
func WithRequestID(ctx context.Context, id string) context.Context {
	return context.WithValue(ctx, requestKey{}, id)
}

// RequestIDFromContext retrieves the request ID, with a typed ok return.
func RequestIDFromContext(ctx context.Context) (string, bool) {
	id, ok := ctx.Value(requestKey{}).(string)
	return id, ok
}

// WithUserID attaches an authenticated user ID.
func WithUserID(ctx context.Context, userID int64) context.Context {
	return context.WithValue(ctx, userKey{}, userID)
}

func UserIDFromContext(ctx context.Context) (int64, bool) {
	id, ok := ctx.Value(userKey{}).(int64)
	return id, ok
}

func handlePayment(ctx context.Context) {
	reqID, _ := RequestIDFromContext(ctx)
	userID, _ := UserIDFromContext(ctx)
	fmt.Printf("[req=%s user=%d] processing payment\n", reqID, userID)
}

func main() {
	ctx := context.Background()
	ctx = WithRequestID(ctx, "req-f4a9b2")
	ctx = WithUserID(ctx, 1042)
	handlePayment(ctx)
}
```

<UnderTheHood title="How context.Value walks the parent chain">

`context.WithValue` wraps the parent in a `valueCtx` struct:

```go
// simplified from src/context/context.go
type valueCtx struct {
    Context        // the parent
    key, val any
}

func (c *valueCtx) Value(key any) any {
    if c.key == key {
        return c.val
    }
    return value(c.Context, key) // recurse to parent
}
```

Every `WithValue` call adds one node to the linked list. A `Value(key)` call walks the list from tail to head until it finds a matching key or hits `emptyCtx`, which always returns nil. The comparison uses `==`, so your key type must be comparable — another reason to use an unexported zero-size struct type rather than a string.

Since Go 1.21, `context.WithValue` panics if `key` is nil or not comparable. Go 1.22 tightened the `context` package's internal locking for the cancel tree but did not change `Value` semantics. Those semantics remain unchanged through Go 1.26.

</UnderTheHood>

## The First-Argument Convention

There's one law, and it is not optional.

**`ctx context.Context` is always the first parameter of any function that does I/O, makes a network call, touches a database, blocks on a goroutine, or calls another function that follows this convention.**

```go
// Correct — context is first, always.
func FetchBalance(ctx context.Context, db *sql.DB, accountID string) (int64, error)
func PostLedgerEntry(ctx context.Context, tx *sql.Tx, entry LedgerEntry) error
func SendWebhook(ctx context.Context, client *http.Client, url string, body []byte) error

// Wrong — context buried in the middle or at the end.
func FetchBalance(db *sql.DB, accountID string, ctx context.Context) (int64, error) // ← no
```

The convention exists so that you can scan any function signature and immediately know: "does this function respect cancellation?" If `ctx context.Context` is the first argument, yes. If it's not there, the function is either a pure computation (fine) or it's a goroutine-leaker pretending to be a computation (not fine).

<Callout kind="warn" title="context.Context in structs — still no">

The convention is *first argument*, not *struct field*. A `context.Context` stored in a struct has an opaque lifetime — you can't tell from the outside when it was created, what deadline it carries, or whether it's already expired. Thread it through function calls. Always.

</Callout>

### The two classic leaks — and how to never ship them

**Leak 1: forgetting `defer cancel()`**

Every `With*` constructor allocates a slot in the parent's child list. `WithTimeout` and `WithDeadline` additionally register an internal timer. If you never call `cancel()`, those resources live until the deadline fires or the *parent* context is cancelled — which may be never.

```go
// LEAKED — the child context and timer live longer than necessary
func badHandler(ctx context.Context) {
    ctx, _ = context.WithTimeout(ctx, 5*time.Second) // cancel discarded!
    doWork(ctx)
    // timer + parent child entry: still retained until deadline/parent cancel
}

// CORRECT
func goodHandler(ctx context.Context) {
    ctx, cancel := context.WithTimeout(ctx, 5*time.Second)
    defer cancel() // ← first line, every time, no exceptions
    doWork(ctx)
}
```

**Leak 2: ignoring `ctx.Done()` in a goroutine**

If your goroutine does not select on `ctx.Done()`, cancellation cannot reach it. The goroutine runs to completion regardless of what the caller does — you've broken the contract.

```go
// LEAKED — ignores the context entirely
func leakyWorker(ctx context.Context) {
    go func() {
        result := expensiveAPICall() // blocks forever if the API hangs
        process(result)
    }()
    // goroutine leaks if ctx is cancelled while expensiveAPICall blocks
}

// CORRECT — the goroutine respects the context
func cleanWorker(ctx context.Context) {
    go func() {
        done := make(chan string, 1)
        go func() { done <- expensiveAPICall() }()
        select {
        case result := <-done:
            process(result)
        case <-ctx.Done():
            return // context cancelled — clean exit
        }
    }()
}
```

<Exercise n={1} title="WithTimeout the right way" level="easy">

Write a function `slowLookup(ctx context.Context, key string) (string, error)` that simulates a 200ms lookup. In `main`, call it with a 100ms deadline and print the result or error. Make sure you `defer cancel()`.

<Solution>

```go
package main

import (
	"context"
	"fmt"
	"time"
)

func slowLookup(ctx context.Context, key string) (string, error) {
	select {
	case <-time.After(200 * time.Millisecond):
		return "value-for-" + key, nil
	case <-ctx.Done():
		return "", fmt.Errorf("lookup %q: %w", key, ctx.Err())
	}
}

func main() {
	ctx, cancel := context.WithTimeout(context.Background(), 100*time.Millisecond)
	defer cancel()

	val, err := slowLookup(ctx, "account-balance")
	if err != nil {
		fmt.Println("error:", err)
		return
	}
	fmt.Println("value:", val)
}
```

The 200ms work timer loses the race to the 100ms deadline, so `ctx.Done()` fires first. `ctx.Err()` returns `context.DeadlineExceeded`, which is wrapped with `%w` so callers can use `errors.Is`.

</Solution>

</Exercise>

<Exercise n={2} title="Typed context key" level="easy">

Define an unexported type for a context key. Write `WithTraceID(ctx, id string) context.Context` and `TraceIDFromContext(ctx) (string, bool)`. Demonstrate in `main` that the value round-trips correctly.

<Solution>

```go
package main

import (
	"context"
	"fmt"
)

type traceKey struct{}

func WithTraceID(ctx context.Context, id string) context.Context {
	return context.WithValue(ctx, traceKey{}, id)
}

func TraceIDFromContext(ctx context.Context) (string, bool) {
	id, ok := ctx.Value(traceKey{}).(string)
	return id, ok
}

```

The unexported `traceKey{}` struct is the zero-size sentinel key. Any package that tries to retrieve the value with a plain `"traceID"` string or any other type will get nil — no collision is possible.

</Solution>

<Exercise n={3} title="Fan-out with early cancellation" level="medium">

Write `fanOut(ctx context.Context, tasks []string) ([]string, error)` that runs each task in a separate goroutine (simulate 80ms per task) and returns all results. If the context is cancelled before all tasks finish, cancel the remaining work and return the context error. Test with a 150ms deadline and five tasks.

<Solution>

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"time"
)

func runTask(ctx context.Context, task string) (string, error) {
	select {
	case <-time.After(80 * time.Millisecond):
		return "done:" + task, nil
	case <-ctx.Done():
		return "", ctx.Err()
	}
}

func fanOut(ctx context.Context, tasks []string) ([]string, error) {
	type result struct {
		val string
		err error
	}
	ch := make(chan result, len(tasks))
	var wg sync.WaitGroup

	for _, t := range tasks {
		wg.Add(1)
		go func() {
			defer wg.Done()
			v, err := runTask(ctx, t)
			ch <- result{v, err}
		}()
	}

	go func() { wg.Wait(); close(ch) }()

	var results []string
	for r := range ch {
		if r.err != nil {
			return nil, r.err
		}
		results = append(results, r.val)
	}
	return results, nil
}

func main() {
	ctx, cancel := context.WithTimeout(context.Background(), 150*time.Millisecond)
	defer cancel()

	tasks := []string{"fraud", "kyc", "credit", "compliance", "risk"}
	results, err := fanOut(ctx, tasks)
	if err != nil {
		fmt.Println("fan-out aborted:", err)
		return
	}
	fmt.Println("results:", results)
}
```

With a 150ms deadline and 80ms per task, most tasks will complete but the deadline cuts them off before all five finish. Goroutines that lose the race return `ctx.Err()` instead of a result.

</Solution>

</Exercise>

<Exercise n={4} title="context.AfterFunc for cleanup" level="medium">

Use `context.AfterFunc` (Go 1.21+) to register a cleanup function that prints `"audit log flushed"` when the context is cancelled. Show that the cleanup runs even if the main goroutine has already returned from its work.

<Solution>

```go
package main

import (
	"context"
	"fmt"
	"time"
)

func main() {
	ctx, cancel := context.WithTimeout(context.Background(), 50*time.Millisecond)
	defer cancel()

	// AfterFunc registers a goroutine that runs when ctx is done.
	// The stop function prevents it from running if we call it before ctx is done.
	stop := context.AfterFunc(ctx, func() {
		fmt.Println("audit log flushed")
	})
	_ = stop // we're not stopping it in this example

	// Simulate work that finishes before the timeout.
	time.Sleep(20 * time.Millisecond)
	fmt.Println("work done — waiting for context to expire")

	// Wait long enough for the timeout to fire and AfterFunc to run.
	time.Sleep(100 * time.Millisecond)
}
```

`context.AfterFunc` is cleaner than `go func() { <-ctx.Done(); cleanup() }()` because it returns a stop function, supports multiple registrations on the same context, and its goroutine is only started when the context is cancelled — not before.

</Solution>

</Exercise>

<Exercise n={5} title="Fix the leaking handler" level="hard">

The function below has two context bugs: it discards the cancel function from `WithTimeout`, and it spawns a goroutine that never watches `ctx.Done()`. Fix both so no goroutines leak when the context is cancelled.

```go
func leakyHandler(ctx context.Context, accountID string) error {
    ctx, _ = context.WithTimeout(ctx, 2*time.Second) // bug 1
    results := make(chan string, 1)
    go func() {
        time.Sleep(3 * time.Second) // simulates slow external call
        results <- "balance: 10000"
    }()
    select {
    case r := <-results:
        fmt.Println(r)
        return nil
    case <-ctx.Done():
        return ctx.Err()
    }
    // bug 2: goroutine in the go func above will keep running after ctx.Done()
}
```

<Solution>

```go
package main

import (
	"context"
	"fmt"
	"time"
)

func fixedHandler(ctx context.Context, accountID string) error {
	// Fix 1: store and defer cancel.
	ctx, cancel := context.WithTimeout(ctx, 2*time.Second)
	defer cancel()

	results := make(chan string, 1)
	go func() {
		// Fix 2: make the goroutine respect context cancellation.
		select {
		case <-time.After(3 * time.Second): // simulate slow call
			results <- "balance: 10000"
		case <-ctx.Done():
			// Context was cancelled — return without sending to results.
			// The buffered channel prevents this goroutine from blocking.
			return
		}
	}()

	select {
	case r := <-results:
		fmt.Println(r)
		return nil
	case <-ctx.Done():
		return ctx.Err()
	}
}

func main() {
	ctx, cancel := context.WithTimeout(context.Background(), 500*time.Millisecond)
	defer cancel()

	err := fixedHandler(ctx, "acc-8821")
	if err != nil {
		fmt.Println("handler:", err)
	}
}
```

Bug 1: the discarded `_` means the deadline timer and the child context entry in the parent's cancel list are not cleaned up promptly. `defer cancel()` fixes it. Bug 2: the inner goroutine blocks on `time.Sleep`, which is not context-aware. Wrapping it in a `select` with `ctx.Done()` lets it exit as soon as the context fires, returning the goroutine stack to the runtime.

</Solution>

</Exercise>

<Recap>

You now own `context.Context` — not just the API surface, but the mechanism underneath:

- **`context.Context` is the cancellation backbone** of every request tree. It flows *down* through function arguments; cancellation signals flow *up* through the closed `Done()` channel.
- **`context.Background()`** is the root — never cancelled, carries nothing, starts every real tree. **`context.TODO()`** is a marker for future plumbing.
- **Four constructors:** `WithCancel` (manual trigger), `WithTimeout` (duration from now), `WithDeadline` (wall-clock time), `WithValue` (request-scoped data). Every `With*` call returns a `CancelFunc` — `defer cancel()` is mandatory, immediately, no exceptions.
- **`Done()` is a lazily-created channel that is *closed* on cancellation** — not sent to. A single close broadcasts to every goroutine blocking on `<-ctx.Done()`, instantly and at O(1) cost.
- **`ctx.Err()`** returns `context.Canceled` (manual cancel) or `context.DeadlineExceeded` (timer fired). Use `errors.Is` to distinguish them.
- **Propagation paths:** `r.Context()` in HTTP handlers (auto-cancelled on client disconnect), `QueryContext`/`ExecContext`/`BeginTx` in `database/sql`, and explicit `<-ctx.Done()` in every goroutine you spawn.
- **Values:** request-scoped only. Typed unexported key structs, no collision. Never pass configuration or dependencies through context — function parameters exist for a reason.
- **The two classic leaks:** discarding `cancel()` (retains child context and timer resources longer than necessary) and spawning goroutines that don't watch `ctx.Done()` (leaks the goroutine stack, the connection, and your sanity).
- **Go 1.20+:** `context.WithCancelCause` / `context.Cause` — cancel with a specific error so callers can distinguish *why* a context was cancelled, beyond the coarse `Canceled`/`DeadlineExceeded` split.
- **Go 1.21+:** `context.WithoutCancel` (child that outlives its parent) and `context.AfterFunc` (run a function in a goroutine when ctx fires). Go 1.22 tightened the cancel tree's internal locking.
- **Go 1.26:** `os/signal.NotifyContext` now uses `WithCancelCause` internally — `context.Cause(ctx)` returns an error identifying the OS signal that triggered graceful shutdown.

</Recap>
