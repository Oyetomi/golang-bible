### Step 1: never store the password, store a hash

<MentalModel

<Define term="Password hashing (bcrypt / argon2id)" since="Security for Financial Systems (Part 3)">
A **password hash** turns a password into a fixed-size value that can't be turned back. Login re-hashes what the user typed and compares. **bcrypt**, **scrypt**, **argon2id** and **PBKDF2** differ from ordinary hashes like SHA-256 in one deliberate way: they are **slow** (and, except PBKDF2, **memory-hungry**), with a tunable cost, so guessing passwords from a stolen database is expensive.
</Define>

### Step 2: why a fast hash is a crime

Every database eventually leaks. When yours does, the attacker takes each stored hash and tries billions of likely passwords against it offline, on their own hardware, with no rate limit. The only thing you control is **how expensive each guess is**.

A **salt**, a random value stored next to each hash and mixed into it, stops precomputed tables and makes identical passwords hash differently. It doesn't make each guess any slower. Measure the difference yourself: this runs a salted SHA-256 and a salted PBKDF2 with 600,000 iterations (the current OWASP recommendation for PBKDF2) for 200 ms each. `crypto/pbkdf2` joined the standard library in Go 1.24.

<GoPlayground>

```go
package main

import (
	"crypto/pbkdf2"
	"crypto/rand"
	"crypto/sha256"
	"fmt"
	"time"
)

// guessesPerSecond runs hash on candidate passwords for 200 ms and scales up.
func guessesPerSecond(hash func(guess string)) int {
	n, start := 0, time.Now()
	for time.Since(start) < 200*time.Millisecond {
		hash(fmt.Sprintf("guess-%d", n))
		n++
	}
	return n * 5
}

func main() {
	salt := make([]byte, 16)
	rand.Read(salt)

	fast := guessesPerSecond(func(g string) {
		sha256.Sum256(append(salt, g...)) // a general-purpose hash, salted
	})
	slow := guessesPerSecond(func(g string) {
		pbkdf2.Key(sha256.New, g, salt, 600_000, 32) // a password hash
	})

	fmt.Printf("salted SHA-256:           %12d guesses/second on ONE core\n", fast)
	fmt.Printf("PBKDF2-SHA256, 600k iter: %12d guesses/second on ONE core\n", slow)
	fmt.Printf("the slow hash costs an attacker about %dx more per guess\n", fast/max(slow, 1))
}
```

</GoPlayground>

```text
PBKDF2-SHA256, 600k iter:           15 guesses/second on ONE core
the slow hash costs an attacker about 404231x more per guess
```

Your numbers will differ, but the ratio won't: six million guesses a second against a few dozen, on one CPU core. A GPU rig multiplies the first number by thousands. A user logging in once pays 65 ms and never notices; an attacker testing a billion passwords pays for it a billion times.

```go
package main

import (
	"errors"
	"fmt"
	"log"

	"golang.org/x/crypto/bcrypt"
)

// HashPassword returns a bcrypt hash that includes its own salt and cost.
func HashPassword(plain string) ([]byte, error) {
	return bcrypt.GenerateFromPassword([]byte(plain), 12) // ~260 ms on a laptop core
}

// CheckPassword returns nil if plain matches the stored hash.
func CheckPassword(plain string, hashed []byte) error {
	return bcrypt.CompareHashAndPassword(hashed, []byte(plain))
}

func main() {
	hash, err := HashPassword("hunter2-but-actually-strong-42!")
	if err != nil {
		log.Fatal(err) // includes "password length exceeds 72 bytes"
	}

	// Store this whole string.
	fmt.Printf("stored: %s\n", hash)

	for _, attempt := range []string{"hunter2-but-actually-strong-42!", "wrong"} {
		err := CheckPassword(attempt, hash)
		switch {
		case err == nil:
			fmt.Println(attempt, "-> login OK")
		case errors.Is(err, bcrypt.ErrMismatchedHashAndPassword):
			fmt.Println(attempt, "-> wrong password")
		default:
			log.Fatal(err) // corrupted hash or similar: a server fault
		}
	}

	// A second hash of the same password is different (new salt),
	// and still verifies.
	again, _ := HashPassword("hunter2-but-actually-strong-42!")
	fmt.Println("same as before?", string(again) == string(hash))
}
```

</CodeWalk>

Measured with `x/crypto` v0.57: cost 10 took 93 ms and cost 12 took 259 ms. Pick the highest cost your login endpoint can afford (roughly 250 ms is a common target) and revisit it as hardware improves.

<Callout kind="pro" title="Constant-time comparison">

`CompareHashAndPassword` compares in constant time: it doesn't stop at the first differing byte, so response timing can't reveal how much of a guess was right. For other secrets (API keys, HMAC tags, tokens) use `crypto/subtle.ConstantTimeCompare` or `hmac.Equal`, never `==` or `bytes.Equal`.

</Callout>

<UnderTheHood title="argon2id: you store the parameters too">

`golang.org/x/crypto/argon2` gives you the raw function, `argon2.IDKey(password, salt, time, memory, threads, keyLen)`, and leaves the storage format to you. Store the parameters **with** each hash, in the standard PHC string format, so you can change them later without breaking old hashes:

```text
$argon2id$v=19$m=65536,t=3,p=2$<base64 salt>$<base64 hash>
```

RFC 9106 suggests `t=3, m=64 MiB` as a starting point when memory is limited. Tune time and memory until one hash takes around 100–300 ms on your production hardware, and compare the result with `subtle.ConstantTimeCompare`. Many teams use a small wrapper library (such as `alexedwards/argon2id`) that handles the format for them.

</UnderTheHood>

### Step 4: proving the email address is theirs

A hashed password proves nothing about whether `ada@example.com` belongs to the person who just signed up. Until they click a link sent to that address, the account is unverified.

<Define term="Transactional email">
A **transactional email** is a one-to-one message triggered by a user action (verify your address, reset your password, a receipt), as opposed to bulk marketing. It has to arrive quickly and reliably; a verification email that arrives ten minutes late loses the signup.
</Define>

The flow is split in two by the user's inbox, which can mean minutes or hours of real time. Press play:

```go
package main

import (
	"crypto/rand"
	"crypto/sha256"
	"crypto/subtle"
	"encoding/hex"
	"fmt"
	"time"
)

// newVerificationToken returns the raw token to EMAIL and the digest to STORE.
func newVerificationToken() (token, digest string) {
	token = rand.Text() // Go 1.24: 26 characters, 130 bits of randomness
	sum := sha256.Sum256([]byte(token))
	return token, hex.EncodeToString(sum[:])
}

func main() {
	token, digest := newVerificationToken()
	fmt.Println("store in the database: digest", digest[:16]+"…", "expires", time.Now().Add(24*time.Hour).Format("2006-01-02 15:04"))
	fmt.Println("put in the email link: https://api.meridian.example/v1/verify?token=" + token)

	// Later, on the click: hash what came in the URL and compare with the stored digest.
	sum := sha256.Sum256([]byte(token))
	ok := subtle.ConstantTimeCompare([]byte(hex.EncodeToString(sum[:])), []byte(digest)) == 1
	fmt.Println("click matches stored digest:", ok)
}
```

</GoPlayground>

`crypto/rand.Text` (Go 1.24) returns a random string drawn from `crypto/rand`, ready to use as a token. Why is SHA-256 fine for the token when it was a crime for passwords? Because the token is 130 random bits, not something a human chose: there's no list of likely guesses to try, so speed doesn't help the attacker.

<Callout kind="warn" title="Five rules for any emailed token">

1. **`crypto/rand` only**, never `math/rand`: a predictable token is a free account.
2. **Store the hash**, not the token.
3. **Expire it** (24 hours is typical for verification, less for password resets).
4. **Single use**: consume it in the same transaction that makes the change.
5. **Same response either way**: if `POST /users` says "email already registered", attackers learn who has an account. Always answer "if that address is valid, you'll receive a link", and email the existing user instead.

</Callout>

Sending uses `net/smtp`, which is deliberately minimal (it's frozen), or more often your provider's HTTP API:

```go
package mailer

import (
	"fmt"
	"net/smtp"
)

type SMTPMailer struct {
	addr string // "smtp.provider.example:587"
	auth smtp.Auth
	from string
}

func NewSMTPMailer(host, port, user, pass, from string) *SMTPMailer {
	return &SMTPMailer{addr: host + ":" + port, auth: smtp.PlainAuth("", user, pass, host), from: from}
}

// Send submits one message. SendMail upgrades to TLS with STARTTLS when the
// server offers it, and PlainAuth refuses to send the password unencrypted.
func (m *SMTPMailer) Send(to string, msg []byte) error {
	if err := smtp.SendMail(m.addr, m.auth, m.from, []string{to}, msg); err != nil {
		return fmt.Errorf("send mail to %s: %w", to, err)
	}
	return nil
}
```

Run the send from a background job, never inside the signup request: otherwise your signup latency and error rate become your mail provider's. Retries and dead-lettering for that job are in Part 2's Background Jobs chapter.

**Recap.** Store passwords with a slow, salted password hash (argon2id or bcrypt); verification tokens are random, stored hashed, expiring and single-use.

## Sessions and Tokens

*Stop 2 of 8.*

### Step 1: two ways to remember a login

<ELI5
  concept="Sessions vs tokens"
  analogy="A cloakroom ticket versus a festival wristband."
  role="reader"
>

Both prove you're allowed in. They differ in **where the truth lives**.

A **session** is a cloakroom ticket. The stub says only `#42`; the real record sits in the cloakroom's book, and staff look it up every time. Lose the ticket and they can void `#42` on the spot.

A **token** is a festival wristband with your details printed on it and a hologram that proves it isn't forged. Nobody phones head office; the wristband carries its own proof. But if you're thrown out, the wristband is still on your arm and still works until it expires.

</ELI5>

<Define term="Session vs token">
A **session** is a server-side record (in a database or Redis) keyed by a random ID that the browser holds in a cookie. The server looks it up on every request, so deleting it revokes access instantly. A **token** such as a JWT is a signed, self-contained credential: the server checks the signature and needs no lookup, which suits many replicas, but it stays valid until it expires.
</Define>

The difference shows up the moment someone logs out, or an admin locks a stolen account:

That's why token systems use **short-lived access tokens** (5–15 minutes) plus a **refresh token** that's stored server-side like a session: the refresh token can be revoked, and a stolen access token is only useful for minutes. It's also why many web apps simply use sessions: a Redis lookup is cheap, and "log out everywhere" works.

### Step 2: the session cookie

```go
http.SetCookie(w, &http.Cookie{
	Name:     "__Host-session", // __Host-: Secure, Path=/, no Domain, enforced by browsers
	Value:    rand.Text(),      // an opaque random ID; the real data stays server-side
	Path:     "/",
	HttpOnly: true,             // JavaScript can't read it, so XSS can't steal it
	Secure:   true,             // HTTPS only
	SameSite: http.SameSiteLaxMode, // not sent on cross-site POSTs (Stop 7)
	MaxAge:   24 * 60 * 60,
})
```

Each attribute closes one hole. `HttpOnly` keeps it away from injected scripts, `Secure` keeps it off plain HTTP, `SameSite` stops other sites triggering requests that carry it, and the `__Host-` name prefix tells the browser to refuse the cookie unless it's `Secure`, host-only and `Path=/`, so a sibling subdomain can't overwrite it.

<Callout kind="warn" title="Don't keep tokens in localStorage">

Any script on your page can read `localStorage`, including one injected through an XSS bug. For browser apps, keep credentials in `HttpOnly` cookies. Bearer tokens in an `Authorization` header are for non-browser clients: mobile apps, CLIs, other services.

</Callout>

### Step 3: what a JWT is

<Define term="JWT — JSON Web Token (header.payload.signature)" since="Security for Financial Systems (Part 3)">
A **JWT** is three base64url-encoded parts joined by dots: a **header** (which algorithm signed it), a **payload** of claims (who, what, until when), and a **signature** over the first two. The payload is encoded, not encrypted: anyone holding the token can read it. The signature only proves the first two parts weren't changed by someone without the key.
</Define>

```text
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9 . eyJzdWIiOiJ1c2VyXzEyMyIsImV4cCI6MTcxOTk5OTk5OX0 . SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c
{"alg":"HS256","typ":"JWT"}            {"sub":"user_123","exp":1719999999}               HMAC-SHA256(part1 + "." + part2, key)
```

Two signing families:

- **HS256** (HMAC): one shared secret signs and verifies. Simple, but every service that verifies can also mint.
- **RS256 / ES256** (public-key): a private key signs; anyone with the public key can verify but not mint. Right when one service issues tokens and many check them. Public keys are usually published at a JWKS URL (`/.well-known/jwks.json`).

### Step 4: the real attack is letting the token choose

Look at the header again: `{"alg":"HS256"}`. The token tells the verifier how it was signed, and the token was written by whoever sent it. Every famous JWT attack is the verifier believing that header.

The nastiest is **algorithm confusion**. A service issues RS256 tokens and publishes its public key, as it should. A verifier that follows the header will, when shown `"alg":"HS256"`, run HMAC, keyed with the only key it has: the public one. The attacker has that key too (it's public), so they can sign anything. This program does it with real RSA keys:

<GoPlayground>

```go
package main

import (
	"crypto"
	"crypto/hmac"
	"crypto/rand"
	"crypto/rsa"
	"crypto/sha256"
	"crypto/x509"
	"encoding/base64"
	"encoding/json"
	"encoding/pem"
	"errors"
	"fmt"
	"strings"
)

var b64 = base64.RawURLEncoding

// token builds header.payload.signature, signing with sign().
func token(alg, payload string, sign func([]byte) []byte) string {
	head := b64.EncodeToString([]byte(`{"alg":"` + alg + `","typ":"JWT"}`))
	body := b64.EncodeToString([]byte(payload))
	return head + "." + body + "." + b64.EncodeToString(sign([]byte(head+"."+body)))
}

func hs256(key []byte) func([]byte) []byte {
	return func(msg []byte) []byte {
		m := hmac.New(sha256.New, key)
		m.Write(msg)
		return m.Sum(nil)
	}
}

func split(tok string) (alg string, signed, sig []byte, err error) {
	p := strings.Split(tok, ".")
	if len(p) != 3 {
		return "", nil, nil, errors.New("malformed")
	}
	h, _ := b64.DecodeString(p[0])
	var head struct{ Alg string }
	json.Unmarshal(h, &head)
	sig, err = b64.DecodeString(p[2])
	return head.Alg, []byte(p[0] + "." + p[1]), sig, err
}

// verifyByHeader lets the TOKEN choose the algorithm. The only key it holds is
// the RSA public key, which it uses for whichever algorithm the header names.
func verifyByHeader(tok string, pub *rsa.PublicKey, pubPEM []byte) error {
	alg, signed, sig, err := split(tok)
	if err != nil {
		return err
	}
	switch alg {
	case "RS256":
		sum := sha256.Sum256(signed)
		return rsa.VerifyPKCS1v15(pub, crypto.SHA256, sum[:], sig)
	case "HS256": // "we support HMAC too" — keyed with... the key we have
		if !hmac.Equal(sig, hs256(pubPEM)(signed)) {
			return errors.New("bad HMAC")
		}
		return nil
	}
	return fmt.Errorf("unsupported alg %q", alg)
}

// verifyPinned decides the algorithm itself: RS256, nothing else.
func verifyPinned(tok string, pub *rsa.PublicKey) error {
	alg, signed, sig, err := split(tok)
	if err != nil {
		return err
	}
	if alg != "RS256" {
		return fmt.Errorf("alg %q rejected: this service only accepts RS256", alg)
	}
	sum := sha256.Sum256(signed)
	return rsa.VerifyPKCS1v15(pub, crypto.SHA256, sum[:], sig)
}

func main() {
	priv, _ := rsa.GenerateKey(rand.Reader, 2048)
	der, _ := x509.MarshalPKIXPublicKey(&priv.PublicKey)
	pubPEM := pem.EncodeToMemory(&pem.Block{Type: "PUBLIC KEY", Bytes: der}) // published at /jwks

	// The real issuer signs with the PRIVATE key.
	real := token("RS256", `{"sub":"ada","role":"user"}`, func(msg []byte) []byte {
		sum := sha256.Sum256(msg)
		s, _ := rsa.SignPKCS1v15(rand.Reader, priv, crypto.SHA256, sum[:])
		return s
	})
	// The attacker has only the PUBLIC key, and uses it as an HMAC secret.
	forged := token("HS256", `{"sub":"attacker","role":"admin"}`, hs256(pubPEM))

	fmt.Println("header-chooses verifier:  real ->", verifyByHeader(real, &priv.PublicKey, pubPEM),
		"| forged ->", verifyByHeader(forged, &priv.PublicKey, pubPEM))
	fmt.Println("pinned RS256 verifier:    real ->", verifyPinned(real, &priv.PublicKey),
		"| forged ->", verifyPinned(forged, &priv.PublicKey))
}
```

```go
	"crypto/rand"
	"errors"
	"fmt"

	"github.com/golang-jwt/jwt/v5"

// In production: loaded from your secret store. Here: 32 fresh random bytes.
var signingKey = func() []byte { b := make([]byte, 32); rand.Read(b); return b }()

type Claims struct {
	Role string `json:"role"`
	jwt.RegisteredClaims
}

// MintToken issues a token for userID, valid for ttl.
func MintToken(userID, role string, ttl time.Duration) (string, error) {
	now := time.Now()
	claims := Claims{
		Role: role,
		RegisteredClaims: jwt.RegisteredClaims{
			Subject:   userID,
			Issuer:    "meridian-auth",
			IssuedAt:  jwt.NewNumericDate(now),
			ExpiresAt: jwt.NewNumericDate(now.Add(ttl)),
		},
	}
	return jwt.NewWithClaims(jwt.SigningMethodHS256, claims).SignedString(signingKey)
}

// VerifyToken checks the signature AND our policy, then returns the claims.
func VerifyToken(tok string) (*Claims, error) {
	claims := &Claims{}
	_, err := jwt.ParseWithClaims(tok, claims,
		func(*jwt.Token) (any, error) { return signingKey, nil },
		jwt.WithValidMethods([]string{"HS256"}), // exactly the algorithm we issue
		jwt.WithExpirationRequired(),            // no exp, no entry
		jwt.WithIssuer("meridian-auth"),
	)
	if errors.Is(err, jwt.ErrTokenExpired) {
		return nil, fmt.Errorf("token expired: %w", err)
	}
	if err != nil {
		return nil, fmt.Errorf("invalid token: %w", err)
	}
	return claims, nil
}

func main() {
	good, _ := MintToken("user_123", "user", 15*time.Minute)
	c, err := VerifyToken(good)
	fmt.Println("fresh HS256 token:", c.Subject, c.Role, err)

	hs512, _ := jwt.NewWithClaims(jwt.SigningMethodHS512, jwt.MapClaims{
		"sub": "user_123", "iss": "meridian-auth", "exp": time.Now().Add(time.Hour).Unix(),
	}).SignedString(signingKey)
	_, err = VerifyToken(hs512)
	fmt.Println("HS512, same key:  ", err)

	noExp, _ := jwt.NewWithClaims(jwt.SigningMethodHS256, jwt.MapClaims{
		"sub": "user_123", "iss": "meridian-auth",
	}).SignedString(signingKey)
	_, err = VerifyToken(noExp)
	fmt.Println("no exp claim:     ", err)
}
```

### Step 1: two questions, two status codes

### Step 2: permissions, not role checks

Scattering `if role == "admin"` through handlers works until the third role, or the "admin who may not delete". The model that scales names **capabilities**:

<Define term="Permission-based access control (RBAC)">
A **permission** is a narrow capability code such as `transactions:read` or `transactions:write`. **Roles** are named bundles of permissions (admin = read + write, auditor = read). Each endpoint declares the one permission it needs, and one middleware checks the caller's set. Adding a role is a data change, not a code change.
</Define>

```go
package main

import (
	"fmt"
	"net/http"
	"net/http/httptest"
	"slices"
)

// Permissions is the set of capability codes a user holds.
type Permissions []string

func (p Permissions) Includes(code string) bool { return slices.Contains(p, code) }

// userPerms stands in for a users -> roles -> permissions lookup in the database.
var userPerms = map[string]Permissions{
	"admin-ada":    {"transactions:read", "transactions:write"},
	"auditor-finn": {"transactions:read"},
}

// requirePermission lets next run only if the caller holds code.
func requirePermission(code string, next http.HandlerFunc) http.HandlerFunc {
	return func(w http.ResponseWriter, r *http.Request) {
		// In a real service the user comes from the authentication middleware,
		// via the request context. A header keeps this demo self-contained.
		caller := r.Header.Get("X-User")
		if !userPerms[caller].Includes(code) {
			http.Error(w, "missing permission "+code, http.StatusForbidden)
			return
		}
		next(w, r)
	}
}

func createTransfer(w http.ResponseWriter, r *http.Request) {
	fmt.Fprint(w, `{"transfer_id":"txn_1","status":"created"}`)
}

func main() {
	mux := http.NewServeMux()
	mux.HandleFunc("POST /v1/transfers", requirePermission("transactions:write", createTransfer))

	for _, user := range []string{"admin-ada", "auditor-finn"} {
		req := httptest.NewRequest("POST", "/v1/transfers", nil)
		req.Header.Set("X-User", user)
		rec := httptest.NewRecorder()
		mux.ServeHTTP(rec, req)
		fmt.Printf("%-12s -> %d %s", user, rec.Code, rec.Body.String())
		fmt.Println()
	}
}
```

## OAuth2 and OIDC

*Stop 4 of 8.*

### Step 1: three parties, two channels

"Log in with GitHub" means the user proves who they are **to GitHub**, and GitHub tells you. Your app never sees their GitHub password.

<Define term="OAuth2 — authorization-code flow">
**OAuth2** lets a user grant your app limited access to their account on another service. In the **authorization-code flow**, the browser carries only a short-lived, single-use **code** back to your app; your **server** then exchanges that code, together with your client secret and a PKCE verifier, for tokens, directly with the provider. **OIDC** (OpenID Connect) adds an `id_token`, a signed JWT that says who the user is.
</Define>

Three parties: the **user** (in their browser), your app (the **client**), and the **provider** (GitHub, Google). Two channels: the **front channel** runs through the browser, where anything can be seen or tampered with; the **back channel** is your server talking directly to the provider. Press play:

### Step 2: the two values that make it safe

- **`state`** is a random value you generate, remember for this browser, and require back on the callback. Without it, an attacker can complete a login flow with *their* GitHub account and trick Ada's browser into finishing it, silently linking the attacker's identity to Ada's Meridian session.
- **PKCE** (Proof Key for Code Exchange, "pixie") is a random **verifier** you keep, whose SHA-256 **challenge** you send at the start. The provider only exchanges the code if the same verifier comes back. It was invented for mobile apps that can't keep a secret, and current guidance (the OAuth 2.0 Security Best Current Practice, RFC 9700) recommends it for every client, including servers.

`golang.org/x/oauth2` handles the protocol; you supply both values:

```go
var cfg = &oauth2.Config{
	ClientID:     os.Getenv("GITHUB_CLIENT_ID"),
	ClientSecret: os.Getenv("GITHUB_CLIENT_SECRET"),
	RedirectURL:  "https://meridian.example/auth/github/callback",
	Scopes:       []string{"read:user", "user:email"},
	Endpoint:     github.Endpoint,
}

// shortCookie remembers a value for this browser for 10 minutes. SameSite=Lax,
// not Strict: the callback is a cross-site navigation FROM GitHub, and a Strict
// cookie would not be sent on it.
func shortCookie(name, value string) *http.Cookie {
	return &http.Cookie{Name: name, Value: value, Path: "/auth/github", MaxAge: 600,
		HttpOnly: true, Secure: true, SameSite: http.SameSiteLaxMode}
}

func handleLogin(w http.ResponseWriter, r *http.Request) {
	state := rand.Text()                  // ties the callback to this browser (CSRF)
	verifier := oauth2.GenerateVerifier() // PKCE: proves we started the flow
	http.SetCookie(w, shortCookie("oauth_state", state))
	http.SetCookie(w, shortCookie("oauth_verifier", verifier))
	url := cfg.AuthCodeURL(state, oauth2.S256ChallengeOption(verifier))
	http.Redirect(w, r, url, http.StatusFound)
}

func handleCallback(w http.ResponseWriter, r *http.Request) {
	st, err := r.Cookie("oauth_state")
	if err != nil || subtle.ConstantTimeCompare([]byte(st.Value), []byte(r.FormValue("state"))) != 1 {
		http.Error(w, "state mismatch", http.StatusBadRequest)
		return
	}
	v, err := r.Cookie("oauth_verifier")
	if err != nil {
		http.Error(w, "missing verifier", http.StatusBadRequest)
		return
	}
	// Back channel: our server, the code, our secret AND the PKCE verifier.
	tok, err := cfg.Exchange(r.Context(), r.FormValue("code"), oauth2.VerifierOption(v.Value))
	if err != nil {
		http.Error(w, "code exchange failed", http.StatusBadGateway)
		return
	}
	// Use tok to call GitHub's API for the user, then start YOUR own session.
	fmt.Fprintln(w, "signed in; token expires", tok.Expiry)
}
```

`AuthCodeURL` with `S256ChallengeOption` produced a redirect URL like `…?client_id=…&code_challenge=CJKZ…&code_challenge_method=S256&response_type=code&state=…` in a real run.

### Step 3: scopes, tokens and OIDC

- **Scopes** are what you're asking for. Request the minimum (`read:user`, not `repo`): users see the list on the consent screen, and a leaked token can do only what its scopes allow.
- The provider's **access token** is for calling the provider's API. Don't hand it to your frontend or use it as your own session: after the callback, start your own session.
- With **OIDC**, the provider also returns an `id_token`: a JWT signed by the provider, containing `sub` (a stable user ID), `email` and `email_verified`. Verify it like any JWT, against the provider's published keys, checking `iss` and that `aud` is your client ID; `github.com/coreos/go-oidc` does this. Store `sub` as the link to your user, never the email address, which can change or be reassigned.

## Passkeys and MFA

*Stop 5 of 8.*

### Step 1: why a correct password isn't enough

Monday, 03:40. Meridian's login endpoint takes forty thousand attempts an hour, and 0.8% **succeed**: correct email-and-password pairs harvested from another company's breach and replayed by bots, because people reuse passwords. This is **credential stuffing**. Your hashing, sessions and tokens all work exactly as designed, and you lose anyway, because the password was never a secret only you and the user shared.

<Define term="Multi-factor authentication (MFA)">
**MFA** requires proof from two or more different **categories**: something you **know** (password, PIN), something you **have** (phone, security key), something you **are** (fingerprint, face). Two proofs from the same category, like a password plus a security question, are still one factor.
</Define>

For a fintech it's not optional: the EU's PSD2 Strong Customer Authentication rules require two independent factors for payments.

### Step 2: TOTP, the offline code

The six-digit code in an authenticator app is **TOTP** (RFC 6238). At enrolment, server and phone share a random secret (via a QR code). Then both compute `HMAC-SHA1(secret, floor(unixTime / 30))`, cut it down to six digits, and compare. No network, no SMS: the clock is the only message, which is why it works in airplane mode.

<GoPlayground>

```go
package main

import (
	"crypto/hmac"
	"crypto/sha1"
	"encoding/binary"
	"fmt"
)

// totp computes an RFC 6238 code: HMAC-SHA1 over the time-step
// counter, dynamically truncated to 6 decimal digits.
func totp(secret []byte, unixTime int64) string {
	counter := uint64(unixTime / 30) // 30-second time step

	var msg [8]byte
	binary.BigEndian.PutUint64(msg[:], counter)

	mac := hmac.New(sha1.New, secret)
	mac.Write(msg[:])
	sum := mac.Sum(nil) // 20 bytes

	// Dynamic truncation (RFC 4226 §5.3): the low nibble of the
	// last byte picks an offset; read 31 bits from there.
	off := sum[len(sum)-1] & 0x0f
	code := binary.BigEndian.Uint32(sum[off:off+4]) & 0x7fffffff
	return fmt.Sprintf("%06d", code%1_000_000)
}

func main() {
	// The shared secret, provisioned once via the QR code.
	// Real secrets: 20 random bytes from crypto/rand.
	secret := []byte("meridian-demo-secret")

	// Friday 2026-06-12, 09:00:00 UTC.
	const now int64 = 1781254800

	fmt.Println("server accepts any of these (clock-skew window):")
	for _, t := range []int64{now - 30, now, now + 30} {
		fmt.Printf("  step %d -> %s\n", t/30, totp(secret, t))
	}
}
```

</GoPlayground>

The server accepts the current step and one either side, for clock drift and slow thumbs, compares in constant time, and **rate-limits hard**: a million possible codes is nothing against an unthrottled endpoint. SHA-1 is fine here: HMAC doesn't depend on the collision resistance that broke SHA-1 for certificates.

Two storage rules. The TOTP secret must be *recoverable* (the server recomputes codes), so encrypt it at rest rather than hashing it. **Recovery codes** are the opposite: they're passwords, so hash them and burn each on use.

### Step 3: every relayable factor can be phished

A pixel-perfect page at `meridian-payments.app` proxies the real login live: the victim types their password and fresh TOTP code into the wrong site, and the attacker replays both within the 30-second window. TOTP proved possession **to whoever asked**; the human was supposed to check the domain, and humans fail that check at 3 a.m.

- **SMS** codes are worse: SIM swaps and network interception led NIST (SP 800-63B, 2017) to restrict them.
- **Push approvals** fall to "MFA fatigue": bomb the victim with prompts until they tap Approve. That's how Uber's internal network was breached in 2022.

### Step 4: passkeys take the human out of the check

<Define term="Passkey (WebAuthn credential)">
A **passkey** is a public/private key pair the user's device creates for exactly one website. The private key stays in the device's secure hardware or synced keychain; the server stores only the public key. To log in, the server sends random bytes, the device signs them after a Face ID, fingerprint or PIN unlock, and the server checks the signature.
</Define>

### Step 5: step-up for dangerous actions

MFA is a freshness property, not a one-time gate. Record *how* and *when* the user last authenticated strongly, and demand it again before high-value actions:

```go noverify
func requireFreshMFA(maxAge time.Duration, next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		sess := sessionFrom(r.Context())
		if !sess.MFA || time.Since(sess.AuthTime) > maxAge {
			// A distinct code tells the client to re-prompt the passkey, not log out.
			writeError(w, http.StatusForbidden, "step_up_required",
				"fresh strong authentication required for this action")
			return
		}
		next.ServeHTTP(w, r)
	})
}
```

## REST Design

Auth decides who may call the API. The rest of the chapter makes the API itself predictable.

### Step 1: resources and methods

The URL names a **thing**; the method says what to do with it.

<BeforeAfter
  badLabel="Actions in the URL"

  bad={`POST /getAccount?id=123

Plural nouns, IDs in the path, nesting only for real ownership and no deeper than two levels. Methods carry meaning that clients and proxies rely on: `GET` must never change anything (browsers prefetch it and caches store it), and `PUT` and `DELETE` are **idempotent** (doing them twice has the same effect as once), while `POST` is not (Stop 7).

### Step 4: versioning

You will change the API; old clients will keep calling the old one. The common strategies:

<ConceptGrid cols={3}>
  <ConceptCard label="In the path">`/v1/accounts`, `/v2/accounts`. Explicit, easy to route and test. The usual default.</ConceptCard>
  <ConceptCard label="In a header">`API-Version: 2026-01-01` (Stripe's date-based style). Clean URLs, finer-grained changes, more routing logic.</ConceptCard>
  <ConceptCard label="In the query">`?v=2`. Easy to add and easy to forget. Mostly seen in legacy APIs.</ConceptCard>
</ConceptGrid>

Most changes shouldn't need a new version: **adding** an optional field or a new endpoint is backward compatible. Removing or renaming a field, changing a type, or tightening validation is breaking. When you do retire a version, announce it with the `Deprecation` and `Sunset` response headers and a published date.

### Step 5: pagination that doesn't drift

<Define term="Pagination — offset vs cursor">
**Offset pagination** (`?limit=20&offset=40`) skips N rows. </Define>

A keyset cursor needs an order that's **unique and stable**. Random UUIDs aren't ordered by time, so sort by `(created_at, id)` and put both in the cursor:

```sql
SELECT id, amount_cents, created_at
FROM transfers
WHERE account_id = $1
  AND (created_at, id) < ($2, $3)   -- the cursor: the last row of the previous page
ORDER BY created_at DESC, id DESC
LIMIT 21;                           -- one extra row tells you whether there's a next page
```

Encode the cursor (for example base64 of `created_at|id`) so clients treat it as an opaque token rather than building their own. Offset pagination is still fine for small admin tables where "jump to page 7" matters.

### Step 6: sorting without SQL injection

A `?sort=-created_at` parameter looks harmless, but placeholders only bind **values**; they can't stand in for a column name or `ASC`/`DESC`. So the tempting fix is string-building the `ORDER BY`, and now `?sort=amount; DROP TABLE transfers --` is SQL.

<Define term="Safe sorting — column safelist">
A **sort safelist** is the fixed set of sort values an endpoint accepts. The client's value is checked for membership, then mapped to a column and direction you wrote. Nothing from the client is pasted into SQL.
</Define>

<GoPlayground>

```go
package main

import (
	"fmt"
	"strings"
)

// sortColumns maps each accepted client value to SQL WE wrote.
var sortColumns = map[string]string{
	"created_at":   "created_at",
	"amount_cents": "amount_cents",
}

// orderBy returns a safe ORDER BY clause, or ok=false for anything unknown.
func orderBy(sort string) (clause string, ok bool) {
	dir := "ASC"
	if rest, desc := strings.CutPrefix(sort, "-"); desc {
		sort, dir = rest, "DESC"
	}
	col, ok := sortColumns[sort]
	if !ok {
		return "", false
	}
	// id breaks ties, so equal values come back in a stable order across pages.
	return fmt.Sprintf("ORDER BY %s %s, id %s", col, dir, dir), true
}

func main() {
	for _, s := range []string{"-amount_cents", "created_at", "amount_cents; DROP TABLE transfers --", "password"} {
		if clause, ok := orderBy(s); ok {
			fmt.Printf("%-40q -> %s\n", s, clause)
		} else {
			fmt.Printf("%-40q -> 422 invalid sort value\n", s)
		}
	}
}
```

### Step 1: a timeout is not a failure, it's an unknown

<Define term="Idempotency key" since="Idempotency &amp; Exactly-Once Semantics (Part 3)">

</Define>

Clients retry after timeouts, and they're right to: the request may or may not have happened. The server's job is to make "maybe twice" become "exactly once". package main

```go
import (
	"fmt"
	"sync"
	"sync/atomic"
	"time"
)

var charges atomic.Int32 // how many times money actually moved

func charge() string {
	time.Sleep(20 * time.Millisecond) // the real work takes a moment
	return fmt.Sprintf("txn_%d", charges.Add(1))
}

// checkThenAct: look for the key, and if it's missing, do the work and store.
// The gap between the check and the store is where duplicates slip in.
type checkThenAct struct {
	mu   sync.Mutex
	done map[string]string
}

func (s *checkThenAct) handle(key string) string {
	s.mu.Lock()
	res, ok := s.done[key]
	s.mu.Unlock()
	if ok {
		return res
	}
	res = charge() // two retries can both get here
	s.mu.Lock()
	s.done[key] = res
	s.mu.Unlock()
	return res
}

// claimFirst: atomically claim the key BEFORE doing the work. Later arrivals
// wait for the first one's result instead of doing the work again.
type claimFirst struct {
	mu      sync.Mutex
	entries map[string]*entry
}

type entry struct {
	ready  chan struct{}
	result string
}

func (s *claimFirst) handle(key string) string {
	s.mu.Lock()
	e, seen := s.entries[key]
	if !seen {
		e = &entry{ready: make(chan struct{})}
		s.entries[key] = e // the claim: in the same critical section as the check
	}
	s.mu.Unlock()
	if seen {
		<-e.ready // someone else is doing it (or did it): wait for their answer
		return e.result
	}
	e.result = charge()
	close(e.ready)
	return e.result
}
```

### Step 2: idempotency in production

An in-memory map works for one process. With several replicas the claim must live in the database, and it should be part of the same transaction as the transfer:

```sql
CREATE TABLE idempotency_keys (
    key          TEXT PRIMARY KEY,          -- the unique index IS the claim
    request_hash BYTEA NOT NULL,            -- SHA-256 of the request body
    status       INT,                       -- NULL while in progress
    response     JSONB,
    created_at   TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
-- In the transfer's transaction:
INSERT INTO idempotency_keys (key, request_hash) VALUES ($1, $2)
ON CONFLICT (key) DO NOTHING;   -- 0 rows inserted means someone already claimed it
```

Three behaviours clients rely on (Stripe's API is the reference design):

- **Same key, same body** after completion: return the stored status and body, with a header such as `Idempotent-Replayed: true`.
- **Same key, still in progress**: return `409 Conflict` so the client retries a little later (or wait briefly, as the demo does).
- **Same key, different body**: the client has a bug; return `422` rather than silently replaying an unrelated result. That's what `request_hash` is for.

Expire keys after a day or so. In Meridian's double-entry ledger (Part 3), a duplicate transfer means books that don't balance, so this goes in from day one.

### Step 3: CSRF, the cookie's side effect

<Define term="CSRF — cross-site request forgery">
**CSRF** abuses **ambient credentials**: a browser attaches a site's cookies to every request to that site, including requests triggered by a different, malicious site. A logged-in user who visits `evil.example` can have their browser send `POST /transfers` to Meridian with the session cookie attached. An `Authorization: Bearer` header is not ambient: another site's page can't make the browser add it, so header-token APIs are largely immune.
</Define>

Defenses for cookie-based auth, in the order to apply them:

1. **`SameSite` cookies.** `Lax` (the browser default for cookies without the attribute) isn't sent on cross-site POSTs or fetches; `Strict` isn't sent on any cross-site request, even following a link. Never put a state change behind `GET`: `Lax` still sends cookies on cross-site top-level GETs.
2. **`http.CrossOriginProtection`** (Go 1.25). Rejects non-safe methods (anything but GET, HEAD and OPTIONS) that the browser marks cross-origin via `Sec-Fetch-Site`, or whose `Origin` doesn't match `Host`. Non-browser clients send neither header and pass.
3. **Anti-CSRF tokens**, for older browsers or defense in depth: a random per-session token the page echoes in a header (`X-CSRF-Token`), compared in constant time. A cross-site page can't read it, so it can't send it.

```go
cop := http.NewCrossOriginProtection()
cop.AddTrustedOrigin("https://app.meridian.example") // our own web app on another origin
handler := cop.Handler(mux)                         // cross-origin POST/PUT/PATCH/DELETE -> 403
```

### Step 4: CORS, and the reflected-origin trap

CORS is the opposite direction: it's how your server tells the browser that another origin **may read** your responses. The fatal mistake is echoing whatever `Origin` arrives into `Access-Control-Allow-Origin` while also sending `Access-Control-Allow-Credentials: true`. Then any website can make a logged-in user's browser call your API with their cookies **and read the answer**.

<Define term="CORS misconfiguration">
The browser's same-origin policy stops `evil.com` from reading responses from `api.meridian.example`. CORS relaxes that exactly as far as `Access-Control-Allow-Origin` says. Dangerous patterns: reflecting the request's `Origin`; loose matching such as `strings.HasSuffix(origin, "meridian.example")` (which also matches `evilmeridian.example`); and any of these combined with `Allow-Credentials: true`. Use an exact-match allow-list.
</Define>

<GoPlayground>

```go
package main

import (
	"fmt"
	"net/http"
	"net/http/httptest"
)

// VULNERABLE: reflects whatever Origin the request sends AND allows credentials.
func corsVuln(next http.HandlerFunc) http.HandlerFunc {
	return func(w http.ResponseWriter, r *http.Request) {
		w.Header().Set("Access-Control-Allow-Origin", r.Header.Get("Origin")) // reflect = allow all
		w.Header().Set("Access-Control-Allow-Credentials", "true")
		next(w, r)
	}
}

// SAFE: allow only exact, known origins.
var allowedOrigins = map[string]bool{"https://app.example.com": true}

func corsSafe(next http.HandlerFunc) http.HandlerFunc {
	return func(w http.ResponseWriter, r *http.Request) {
		if origin := r.Header.Get("Origin"); allowedOrigins[origin] {
			w.Header().Set("Access-Control-Allow-Origin", origin)
			w.Header().Set("Access-Control-Allow-Credentials", "true")
		}
		w.Header().Add("Vary", "Origin") // the answer depends on Origin: tell caches
		next(w, r)
	}
}

func secret(w http.ResponseWriter, r *http.Request) { fmt.Fprint(w, `{"email":"victim@example.com"}`) }

func probe(label string, h http.HandlerFunc, origin string) {
	req := httptest.NewRequest("GET", "/me", nil)
	req.Header.Set("Origin", origin)
	rec := httptest.NewRecorder()
	h(rec, req)
	canRead := rec.Header().Get("Access-Control-Allow-Origin") == origin &&
		rec.Header().Get("Access-Control-Allow-Credentials") == "true"
	fmt.Printf("%-4s Origin=%-26s -> that site can read the logged-in response: %v\n", label, origin, canRead)
}

func main() {
	evil := "https://evil.attacker.com"
	probe("VULN", corsVuln(secret), evil)
	probe("SAFE", corsSafe(secret), evil)
	probe("SAFE", corsSafe(secret), "https://app.example.com")
}
```

</GoPlayground>

```text
VULN Origin=https://evil.attacker.com  -> that site can read the logged-in response: true
SAFE Origin=https://evil.attacker.com  -> that site can read the logged-in response: false
SAFE Origin=https://app.example.com    -> that site can read the logged-in response: true
```

<Callout kind="note" title="Real case: chained client-side bugs">

A disclosed Zoho account takeover chained a permissive CORS policy (one Zoho origin could read another's responses) with a DOM-XSS and an unchecked `postMessage` handler: the attacker's page read the victim's inbox cross-origin, took the login code from it, and logged in as them. The CORS half was the server's decision, and an exact-match allow-list would have broken the chain.

</Callout>

**Recap.** Claim idempotency keys atomically, store the response, and reject reuse with a different body. CSRF is a cookie problem: `SameSite`, `CrossOriginProtection`, then tokens. CORS decides who may read your responses: exact-match allow-lists only.

## OpenAPI and GraphQL

*Stop 8 of 8.*

### Step 1: a contract clients can generate code from

OpenAPI is a machine-readable description of your API: endpoints, parameters, request and response schemas, auth. With it, partners generate typed clients, docs stay current, and CI can catch a breaking change before it ships.

Two workflows:

1. **Spec-first.** Write `openapi.yaml`, generate Go types and server interfaces with `oapi-codegen`, implement the interfaces. The spec is the source of truth.
2. **Code-first.** Annotate handlers and generate the spec (`swaggo/swag`).

Spec-first keeps the contract reviewable on its own. A `go:generate` line regenerates the types whenever the spec changes:

```go noverify
//go:generate go tool oapi-codegen -config oapi.yaml openapi.yaml
package api

// Generated from openapi.yaml: do not edit.
type Transfer struct {
	ID          string `json:"id"`
	FromAccount string `json:"from_account"`
	ToAccount   string `json:"to_account"`
	AmountCents int64  `json:"amount_cents"`
	Status      string `json:"status"`
}
```

`go tool` runs a tool declared in your `go.mod` (Go 1.24's `tool` directive), so every developer gets the same generator version. Serve the spec itself at a stable URL such as `/openapi.json`, embedded into the binary with `//go:embed` (next chapter).

### Step 2: what GraphQL solves, and what it costs

**It solves:** over-fetching (a client wants 3 of 30 fields), under-fetching (a screen needs data from five resources, which is five REST calls), and discoverability (the schema describes itself).

**It costs:**

- **Server-side N+1.** A resolver runs per item; without batching (the dataloader pattern), a list of 100 accounts with a nested field fires 100 queries.
- **Caching.** Queries usually go over POST to one URL, so HTTP and CDN caching mostly don't apply.
- **Cost control.** One query can fan out into thousands of resolver calls. You need depth and complexity limits.

<ConceptGrid cols={3}>
  <ConceptCard label="REST fits">Stable shapes, service-to-service calls, cacheable reads, auditable operations. Meridian's ledger API.</ConceptCard>
  <ConceptCard label="GraphQL fits">Many clients (web, iOS, Android, partners) needing different projections of the same data, and a frontend team that changes screens faster than the backend can add endpoints.</ConceptCard>
  <Gotcha>GraphQL's N+1 is invisible in the query text: it's in the resolvers. If you adopt GraphQL, batching and query-cost limits are part of the job from day one.</Gotcha>
</ConceptGrid>

**Recap.** Publish an OpenAPI contract and generate from it. Choose GraphQL when many clients need different shapes of the same data and you're ready to run resolvers, batching and cost limits.

<Exercise n={3} title="Idempotency middleware" level="medium">

Write `Idempotent(next http.Handler) http.Handler` for a single process. A request with an `Idempotency-Key` header runs `next` at most once per key; concurrent and later requests with the same key get the first response (status and body) plus `Idempotent-Replayed: true`. Prove it with 5 concurrent requests.

<Solution>

```go
package main

import (
	"fmt"
	"net/http"
	"net/http/httptest"
	"sync"
	"sync/atomic"
	"time"
)

type result struct {
	done   chan struct{}
	status int
	body   []byte
}

type idempotency struct {
	mu   sync.Mutex
	keys map[string]*result
}

func (s *idempotency) Idempotent(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		key := r.Header.Get("Idempotency-Key")
		if key == "" {
			next.ServeHTTP(w, r)
			return
		}
		s.mu.Lock()
		res, seen := s.keys[key]
		if !seen {
			res = &result{done: make(chan struct{})}
			s.keys[key] = res // claim before doing the work
		}
		s.mu.Unlock()

		if seen {
			<-res.done
			w.Header().Set("Idempotent-Replayed", "true")
			w.WriteHeader(res.status)
			w.Write(res.body)
			return
		}
		rec := httptest.NewRecorder() // capture the first response
		next.ServeHTTP(rec, r)
		res.status, res.body = rec.Code, rec.Body.Bytes()
		close(res.done)

		for k, vs := range rec.Header() {
			w.Header()[k] = vs
		}
		w.WriteHeader(res.status)
		w.Write(res.body)
	})
}

func main() {
	var runs atomic.Int32
	create := http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		n := runs.Add(1)
		time.Sleep(20 * time.Millisecond)
		w.WriteHeader(http.StatusCreated)
		fmt.Fprintf(w, `{"transfer_id":"txn_%d"}`, n)
	})
	h := (&idempotency{keys: map[string]*result{}}).Idempotent(create)

	var wg sync.WaitGroup
	for range 5 {
		wg.Go(func() {
			r := httptest.NewRequest("POST", "/v1/transfers", nil)
			r.Header.Set("Idempotency-Key", "key-abc-123")
			rec := httptest.NewRecorder()
			h.ServeHTTP(rec, r)
			fmt.Println(rec.Code, rec.Header().Get("Idempotent-Replayed"), rec.Body.String())
		})
	}
	wg.Wait()
	fmt.Println("handler ran", runs.Load(), "time(s)")
}
```

The handler runs once; one caller gets the original response and four get the replay. Across several replicas the claim must move into the database (Stop 7, Step 2).

</Solution>

</Exercise>

<Exercise n={4} title="Cursor pagination" level="medium">

Write `paginate(ts []Transfer, after string, limit int) Page` over a slice already sorted newest first, where each `Transfer` has an `ID`. Return up to `limit` items after the cursor, `HasMore`, and `NextCursor`. Walk every page.

<Solution>

```go
package main

import "fmt"

type Transfer struct {
	ID          string
	AmountCents int64
}

type Page struct {
	Data       []Transfer
	NextCursor string
	HasMore    bool
}

func paginate(ts []Transfer, after string, limit int) Page {
	start := 0
	if after != "" {
		for i, t := range ts {
			if t.ID == after {
				start = i + 1
				break
			}
		}
	}
	window := ts[start:]
	hasMore := len(window) > limit // the "fetch limit+1" trick
	if hasMore {
		window = window[:limit]
	}
	p := Page{Data: window, HasMore: hasMore}
	if hasMore {
		p.NextCursor = window[len(window)-1].ID
	}
	return p
}

func main() {
	ts := []Transfer{{"t5", 5000}, {"t4", 4000}, {"t3", 3000}, {"t2", 2000}, {"t1", 1000}}
	cursor := ""
	for page := 1; ; page++ {
		p := paginate(ts, cursor, 2)
		fmt.Printf("page %d: %v more=%v next=%q\n", page, p.Data, p.HasMore, p.NextCursor)
		if !p.HasMore {
			break
		}
		cursor = p.NextCursor
	}
}
```

In SQL the loop over `ts` becomes `WHERE (created_at, id) < ($1, $2) ORDER BY created_at DESC, id DESC LIMIT $3 + 1`.

</Solution>

**Auth**
- Hash passwords with a slow, salted password hash: **argon2id** or **bcrypt** (72-byte limit). A fast hash lets attackers test millions of guesses per second per core.
- Emailed tokens: `crypto/rand` (`rand.Text`), stored hashed, expiring, single use; same response whether or not the email exists.
- **Sessions** revoke instantly; **JWTs** skip the lookup but live until `exp`, so pair short access tokens with revocable refresh tokens. Cookies: `HttpOnly`, `Secure`, `SameSite`, `__Host-`.
- A JWT's payload is readable by anyone. The algorithm and key are server policy: `jwt.WithValidMethods`, `jwt.WithExpirationRequired`, issuer checks; never trust `alg`, `kid`, `jwk` or `jku` from the token.
- **Authentication** fails with 401, **authorization** with 403. Gate each endpoint with one required permission, look permissions up server-side, and scope queries to what the caller owns.
- **OAuth2 code flow**: `state` against CSRF, **PKCE** so a stolen code is useless, then your own session keyed by the provider's `sub`.
- **MFA** needs different factor categories. TOTP and push can be relayed by a phishing proxy; **passkeys** can't, because the browser signs the real origin. Step-up for dangerous actions; recovery as strong as the factors.

**API design**
- Resource URLs and honest status codes; one error envelope; add fields rather than versioning; `Deprecation`/`Sunset` when you must.
- **Keyset cursors** on a unique order for live data; safelist every sort key and clamp page sizes.
- **Idempotency keys**, claimed atomically with the check, replaying the stored response and rejecting a different body.
- CSRF is a cookie problem (`SameSite`, `CrossOriginProtection`, tokens); CORS needs an exact-match allow-list.
- Publish an **OpenAPI** contract; choose **GraphQL** only with batching and cost limits in the plan.
