## The stdlib flag package, in depth

You used `flag.Int`, `flag.String`, and `flag.Bool` in the project chapter. That's the surface. Let's go to depth, because the stdlib `flag` package has sharp capabilities that most engineers never discover — and knowing its limits is exactly what tells you when to reach for a framework.

<Define term="The flag package">
Go's **`flag`** package, in `stdlib` since day one, parses command-line arguments from `os.Args`. You register typed pointers (`flag.String`, `flag.Int`, `flag.Bool`, `flag.Duration`, `flag.Var`) before calling `flag.Parse()`. After parsing, dereference the pointers to read values. The underlying engine is a **`flag.FlagSet`** — a named registry of flags; `flag.Parse()` just calls the package-level `flag.CommandLine` FlagSet. Understanding `FlagSet` directly is what lets you build per-subcommand parsers and testable flag logic without touching `os.Args` in tests. Why it matters: for a single-command tool, `flag` is perfect and zero-dependency. Its limit is that it has no concept of nested subcommands — implementing those by hand with multiple `FlagSet` instances is exactly what frameworks like Cobra formalize.
</Define>

### Every flag type you actually need

`flag` ships typed constructors for the values you use day-to-day. Each returns a pointer to the parsed value:

```go
// Standard types — all return a pointer to the parsed value.
timeout  := flag.Duration("timeout", 30*time.Second, "request deadline")
workers  := flag.Int("workers", 4, "pool size")
verbose  := flag.Bool("verbose", false, "log verbosely")
endpoint := flag.String("endpoint", "https://api.meridian.io", "API base URL")
```

`flag.Duration` is underused and excellent — it parses Go duration strings (`5s`, `2m30s`, `100ms`) straight to `time.Duration`. No manual parsing needed.

### Custom flag.Value: a cents amount flag

The real power move: implement `flag.Value` to teach the `flag` package a new type. Any type that satisfies the two-method interface gets first-class treatment as a flag — printed in usage, set by the parser, validated at parse time.

<Define term="flag.Value">
**`flag.Value`** is the interface `flag` uses for custom flag types. Implement two methods: `String() string` (the default/current value, used in `-help` output) and `Set(s string) error` (called by the parser with the raw string from `os.Args`). Return a non-nil error from `Set` to reject the value — the parser prints usage and exits. Why it matters: it lets you parse rich types (amounts in cents, lists of strings, log levels) directly into your own types rather than accepting a raw `string` and converting later. Validation moves from your business logic into the flag registration, so bad CLI input fails fast with a clear message.
</Define>

```go
// CentsFlag parses a dollar amount like "50.00" or "5000" (cents) into int64 cents.
// Satisfies flag.Value so it plugs straight into the flag package.
type CentsFlag struct {
	Cents int64
}

func (c *CentsFlag) String() string {
	if c.Cents == 0 {
		return "0"
	}
	return fmt.Sprintf("%d.%02d", c.Cents/100, c.Cents%100)
}

func (c *CentsFlag) Set(s string) error {
	// Accept either integer cents ("5000") or decimal dollars ("50.00").
	if strings.Contains(s, ".") {
		f, err := strconv.ParseFloat(s, 64)
		if err != nil {
			return fmt.Errorf("invalid amount %q: %w", s, err)
		}
		// Convert to cents via rounding — still never store a float.
		c.Cents = int64(math.Round(f * 100))
		return nil
	}
	n, err := strconv.ParseInt(s, 10, 64)
	if err != nil {
		return fmt.Errorf("invalid cents %q: %w", s, err)
	}
	c.Cents = n
	return nil
}
```

Register it with `flag.Var`:

```go
var amount CentsFlag
flag.Var(&amount, "amount", "transfer amount in dollars (e.g. 50.00) or cents (e.g. 5000)")
flag.Parse()
fmt.Println("cents:", amount.Cents) // 5000
```

### FlagSet for manual subcommand dispatch

Before Cobra existed, teams built subcommand CLIs by hand using `flag.FlagSet` — one per subcommand. It's more ceremony than a framework, but zero dependencies and it runs anywhere:

```go
func main() {
	if len(os.Args) < 2 {
		fmt.Fprintln(os.Stderr, "usage: meridian <command> [flags]")
		os.Exit(1)
	}

	switch os.Args[1] {
	case "accounts":
		runAccounts(os.Args[2:])
	case "transfer":
		runTransfer(os.Args[2:])
	default:
		fmt.Fprintf(os.Stderr, "unknown command %q\n", os.Args[1])
		os.Exit(2)
	}
}

func runTransfer(args []string) {
	fs := flag.NewFlagSet("transfer", flag.ExitOnError)
	var amount CentsFlag
	from := fs.String("from", "", "source account ID (required)")
	to   := fs.String("to", "", "destination account ID (required)")
	fs.Var(&amount, "amount", "amount in dollars or cents")
	fs.Parse(args) // args is os.Args[2:] — already stripped the subcommand

	// Validate required flags by hand.
	if *from == "" || *to == "" {
		fs.Usage()
		os.Exit(2)
	}
	fmt.Printf("transfer %d cents from %s to %s\n", amount.Cents, *from, *to)
}
```

### Positional args and flag.Args()

After `flag.Parse()`, everything that wasn't consumed as a flag or its value ends up in `flag.Args()` — a `[]string` of positional arguments. This is how you make a tool that accepts both `--json` and a list of account IDs:

```go
flag.Parse()
accounts := flag.Args() // e.g. ["acct_001", "acct_002"]
```

<Callout kind="warn" title="Flags must come before positional args">
Go's `flag` package stops at the first non-flag argument. So `meridian accounts list acct_001 --json` will *not* parse `--json` — `acct_001` terminates flag parsing. The convention is `meridian accounts list --json acct_001`. Cobra handles this more flexibly with `cobra.Command.TraverseChildren`.
</Callout>

### The limits of flag — what motivates a framework

The stdlib `flag` package is honest about what it is: a simple, flat, single-level parser. It gives you:

- Named flags with types and defaults
- A usage string auto-generated from flag registrations
- Custom flag types via `flag.Value`
- Positional args via `flag.Args()`

What it does *not* give you:

- Nested subcommands (e.g., `meridian accounts list` vs. `meridian accounts create`)
- Persistent flags that automatically propagate to all subcommands
- Auto-generated help trees that show subcommands and their own flags
- Required-flag enforcement built in
- Shell completion generation

For a tool with two or three subcommands, hand-rolling with `FlagSet` is completely reasonable — less code, no dependencies. Once you have four or more subcommands, especially nested ones, a framework pays for itself in the first afternoon.

**`On the job:`** The `kubectl` team wrote their own subcommand library before Cobra existed, then migrated. You don't have to repeat that arc. Use `flag` for focused single-command tools; reach for Cobra when you need a subcommand hierarchy.

<Define term="Cobra" since="Building & Shipping Go Binaries (Part 1)">
**Cobra** (`github.com/spf13/cobra`) is the CLI framework behind `kubectl`, `gh`, `docker`, `hugo`, `helm`, and hundreds of other production Go tools. It wraps Go's `flag.FlagSet` in a tree of `cobra.Command` structs — each command declares its own flags, help text, argument validators, and a `RunE` function. Cobra auto-generates help/usage output, propagates persistent flags down the command tree, and can generate shell completions for bash, zsh, fish, and PowerShell. Why it matters: Cobra doesn't add magic — it formalizes exactly the boilerplate you'd write by hand with `flag.FlagSet`, so you can focus on command logic instead of dispatch machinery.
</Define>

### The command tree

A Cobra CLI is a tree of `cobra.Command` values. The root command becomes your binary name; sub-commands hang off it; sub-sub-commands hang off those.

```go
// needs: go get github.com/spf13/cobra
// Not runnable in the playground — requires the cobra module.

package main

import (
	"fmt"
	"os"

	"github.com/spf13/cobra"
)

func main() {
	if err := rootCmd.Execute(); err != nil {
		os.Exit(1)
	}
}

// rootCmd is the top-level "meridian" command.
var rootCmd = &cobra.Command{
	Use:   "meridian",
	Short: "Meridian operator CLI",
	Long:  "Manage Meridian accounts, transfers, and the ledger from the command line.",
}
```

### Sub-commands: accounts list and transfer create

Each `cobra.Command` gets a `Use` string (the sub-command name plus argument placeholders), a `Short` (one-line help), and either `Run` (no error return) or `RunE` (returns `error` — prefer this):

```go
// Not runnable in the playground — requires the cobra module.

var accountsCmd = &cobra.Command{
	Use:   "accounts",
	Short: "Manage Meridian accounts",
}

var accountsListCmd = &cobra.Command{
	Use:   "list",
	Short: "List all accounts",
	RunE: func(cmd *cobra.Command, args []string) error {
		// Dereference the local flag registered below.
		limit, _ := cmd.Flags().GetInt("limit")
		fmt.Printf("listing accounts (limit=%d)\n", limit)
		return nil
	},
}

func init() {
	// Wire the tree: root → accounts → list
	rootCmd.AddCommand(accountsCmd)
	accountsCmd.AddCommand(accountsListCmd)

	// Local flag — only visible on the `list` sub-command.
	accountsListCmd.Flags().Int("limit", 20, "max accounts to return")
}
```

Now `meridian accounts list --limit 50` works and `meridian accounts --help` lists the `list` sub-command automatically. Cobra generates all of that.

<Define term="Subcommand">
A **subcommand** is a named dispatch point inside a CLI that scopes its own set of flags and logic. In `meridian accounts list`, `accounts` is a sub-command grouping account-related operations, and `list` is the leaf sub-command that runs. Subcommands let a single binary grow to dozens of operations without collapsing into a flat flag namespace where `--transfer` and `--verify-ledger` live side by side and confuse everyone including the author.
</Define>

### Local vs. persistent flags

This is the distinction that separates people who understand Cobra from people who copy-paste it.

<Define term="Persistent vs. local flag">
A **local flag** (added with `cmd.Flags()`) is visible only on that exact command — it appears in that command's `--help` and nowhere else. A **persistent flag** (added with `cmd.PersistentFlags()`) is inherited by every sub-command in the subtree rooted at that command. The canonical use: put auth tokens, `--config`, and `--output-format` on the root command as persistent flags so every sub-command gets them automatically. Put `--limit` or `--amount` as local flags on the specific commands that need them.
</Define>

```go
// Not runnable in the playground — requires the cobra module.

func init() {
	// Persistent: available to root AND every sub-command.
	rootCmd.PersistentFlags().String("token", "", "Meridian API token (or set MERIDIAN_TOKEN)")
	rootCmd.PersistentFlags().String("output", "table", "output format: table or json")

	// Local: only the transfer create sub-command sees these.
	transferCreateCmd.Flags().String("from", "", "source account ID (required)")
	transferCreateCmd.Flags().String("to", "", "destination account ID (required)")
	transferCreateCmd.Flags().String("amount", "", "transfer amount (e.g. 50.00)")
	// MarkRequired makes Cobra enforce the flag before RunE is called.
	_ = transferCreateCmd.MarkFlagRequired("from")
	_ = transferCreateCmd.MarkFlagRequired("to")
	_ = transferCreateCmd.MarkFlagRequired("amount")
}
```

### PersistentPreRun: cross-cutting setup

Here's a pattern every production Cobra CLI uses: `PersistentPreRun` runs before the `RunE` of every command in the subtree. This is where you put auth loading, config file reading, and telemetry initialization — once, not repeated in every command:

```go
// Not runnable in the playground — requires the cobra module.

var rootCmd = &cobra.Command{
	Use:   "meridian",
	Short: "Meridian operator CLI",
	PersistentPreRun: func(cmd *cobra.Command, args []string) {
		// This runs before every sub-command's RunE.
		// Load the API token from --token flag or the environment.
		token, _ := cmd.Flags().GetString("token")
		if token == "" {
			token = os.Getenv("MERIDIAN_TOKEN")
		}
		if token == "" {
			fmt.Fprintln(os.Stderr, "error: MERIDIAN_TOKEN not set; use --token or set the env var")
			os.Exit(1)
		}
		// Store it somewhere the RunE functions can reach — typically a global
		// client or a value embedded in the context. We'll use a package var here
		// for clarity; in production, inject via a client struct.
		apiClient = newMeridianClient(token)
	},
}
```

### The full meridian transfer create example

```go
var transferCreateCmd = &cobra.Command{
	Use:   "create",
	Short: "Create a new transfer",
	Long:  "Create a transfer between two Meridian accounts. Amount must be positive.",
	// Args validates positional arguments — RunE won't fire if this returns an error.
	Args: cobra.NoArgs,
	RunE: func(cmd *cobra.Command, args []string) error {
		from, _   := cmd.Flags().GetString("from")
		to, _     := cmd.Flags().GetString("to")

		}

		fmt.Printf("creating transfer: %s → %s, amount=%d cents\n",
			from, to, amt.Cents)
		// In a real tool: call apiClient.CreateTransfer(ctx, from, to, amt.Cents)
		return nil
	},
}
```

<UnderTheHood title="How Cobra wraps flag.FlagSet under the hood">

Every `cobra.Command` holds two `*flag.FlagSet` values: one for local flags and one for persistent flags. When Cobra resolves a command path (e.g., `transfer create`), it **merges** the persistent FlagSets from every ancestor into a combined FlagSet before calling the target command's flag parser. This is why `--token` registered on the root command is visible to `transfer create` — Cobra's merge step adds it to the target command's flag parsing context.

`cmd.Flags()` returns the merged FlagSet (local + inherited persistent). `cmd.LocalFlags()` returns only the flags registered directly on this command. This matters when you're generating help text or shell completions programmatically.

Required flags (`MarkFlagRequired`) are enforced by checking the merged FlagSet *after* parsing but *before* calling `PersistentPreRun` or `RunE`. Cobra checks whether each required flag's `Changed` field is true (set to true by the FlagSet when a value is parsed). An unset required flag returns an error that Cobra wraps into a usage message.

**Args validators** (`cobra.NoArgs`, `cobra.ExactArgs(n)`, `cobra.MinimumNArgs(n)`) run as a function call between flag parsing and `PersistentPreRun`. Cobra provides them as named constructors that return `cobra.PositionalArgs` — a function type that takes `(cmd, args)` and returns `error`.

**`RunE` vs. `Run`.** Always prefer `RunE`. When `Run` (no error return) is used and something goes wrong, you have to call `os.Exit` directly, which skips all deferred cleanup and makes testing harder. `RunE` returning a non-nil error lets Cobra print the error and set the exit code, and lets tests assert on the returned error without spawning a subprocess.

</UnderTheHood>

## urfave/cli — the lighter alternative

> needs `go get github.com/urfave/cli/v2` — snippets in this section are not runnable in the playground.

<Define term="urfave/cli">
**`urfave/cli`** (`github.com/urfave/cli/v2`) is the other major Go CLI framework. Where Cobra leans into a tree of structs with `init()` wiring, urfave/cli uses a declarative `cli.App` with `cli.Command` slices and action functions. It's lighter (no code-generation companion, smaller API surface), has built-in shell completion, and makes simple apps feel slightly less ceremonial. It's the framework behind a number of popular dev tools and is particularly popular for smaller microservice operator CLIs.
</Define>

The same `meridian transfer create` in urfave/cli:

```go

package main

import (
	"fmt"
	"os"

	"github.com/urfave/cli/v2"
)

func main() {
	app := &cli.App{
		Name:  "meridian",
		Usage: "Meridian operator CLI",
		Flags: []cli.Flag{
			// Persistent equivalent: flags on cli.App are available everywhere.
			&cli.StringFlag{Name: "token", EnvVars: []string{"MERIDIAN_TOKEN"}, Usage: "API token"},
		},
		Commands: []*cli.Command{
			{
				Name:  "transfer",
				Usage: "Manage transfers",
				Subcommands: []*cli.Command{
					{
						Name:  "create",
						Usage: "Create a new transfer",
						Flags: []cli.Flag{
							&cli.StringFlag{Name: "from", Required: true, Usage: "source account"},
							&cli.StringFlag{Name: "to", Required: true, Usage: "dest account"},
							&cli.StringFlag{Name: "amount", Required: true, Usage: "amount (e.g. 50.00)"},
						},
						Action: func(c *cli.Context) error {
							fmt.Printf("transfer %s → %s amount=%s\n",
								c.String("from"), c.String("to"), c.String("amount"))
							return nil
						},
					},
				},
			},
		},
	}
	if err := app.Run(os.Args); err != nil {
```

### Cobra vs. urfave/cli: the honest comparison

Neither is wrong. Pick based on your team's constraints:

<ConceptGrid cols={2}>
  <ConceptCard label="Pick Cobra when...">You need a large subcommand tree with inherited persistent flags, generated shell completions, and man pages. Your tool resembles `kubectl` or `gh` in scope. Your team is already familiar with Cobra. Most Go CLI tools in the ecosystem use Cobra, so contributors onboard faster.</ConceptCard>
  <ConceptCard label="Pick urfave/cli when...">Your tool has a modest number of commands.   <Gotcha>Neither framework is a dependency you should add carelessly. For a tool with one command and three flags, `flag` from stdlib is still the right answer — zero dependencies, ships in the Go toolchain, and requires nothing. Add a framework when the subcommand tree earns it.</Gotcha>
</ConceptGrid>

## Config integration & the precedence story

A mature CLI reads configuration from multiple sources. The operator should be able to set `--token` on the command line, fall back to `MERIDIAN_TOKEN` in the environment, fall back to `~/.config/meridian/config.yaml`, and ultimately fall back to a compiled-in default. This layering has a name.

<Define term="Config precedence (flags > env > file > default)">
**Config precedence** is the priority order in which a CLI resolves a configuration value when it's available from multiple sources. The convention, codified by the 12-factor app and enforced by every serious CLI, is: **flags beat environment variables beat config files beat compiled-in defaults**. Each layer overrides the one below. Why it matters: operators in a container deployment can set env vars without touching the binary; they can override with explicit flags in CI without modifying environment setup. Getting the precedence wrong means an env var silently overrides a flag the operator just typed — a confusing, maddening experience.
</Define>

### Wiring Viper with Cobra

**Viper** (`github.com/spf13/viper`) is the companion to Cobra for config file reading. It knows about YAML, TOML, JSON, and `.env` files, and it provides the glue to implement the precedence story correctly.

```go
// Not runnable in the playground — requires cobra and viper modules.

package main

import (
	"fmt"

	"github.com/spf13/cobra"
	"github.com/spf13/viper"
)

func init() {
	// Register the flag on the root command.
	rootCmd.PersistentFlags().String("token", "", "Meridian API token")

	// Bind the flag to a Viper key.
	// Now viper.GetString("token") checks, in order:
	//   1. --token flag (highest priority)
	//   2. MERIDIAN_TOKEN env var
	//   3. token key in the config file
	//   4. the flag's default value (empty string)
	_ = viper.BindPFlag("token", rootCmd.PersistentFlags().Lookup("token"))
	viper.SetEnvPrefix("MERIDIAN")     // env var: MERIDIAN_TOKEN
	viper.AutomaticEnv()               // read MERIDIAN_* vars automatically

	// Config file: ~/.config/meridian/config.yaml
	viper.SetConfigName("config")
	viper.SetConfigType("yaml")
	viper.AddConfigPath("$HOME/.config/meridian")
	_ = viper.ReadInConfig() // ok if missing — operator may not have one
}

// In PersistentPreRun, viper.GetString("token") returns the highest-priority value:
var rootCmd = &cobra.Command{
	Use: "meridian",
	PersistentPreRun: func(cmd *cobra.Command, args []string) {
		token := viper.GetString("token")
		if token == "" {
			fmt.Fprintln(cmd.ErrOrStderr(), "error: API token required (--token or MERIDIAN_TOKEN)")
			cmd.PrintErrln("tip: add 'token: yourtoken' to ~/.config/meridian/config.yaml")
			_ = cmd.Help()
			// In production: os.Exit(1) here. Skipped to keep snippet readable.
		}
	},
}
```

### Doing it without Viper

For smaller tools you don't need Viper. Implement precedence by hand in `PersistentPreRun` — it's about ten lines:

```go
// Not runnable in the playground.

func resolveToken(cmd *cobra.Command) string {
	// 1. Explicit flag — highest priority.
	if t, _ := cmd.Flags().GetString("token"); t != "" {
		return t
	}
	// 2. Environment variable.
	if t := os.Getenv("MERIDIAN_TOKEN"); t != "" {
		return t
	}
	// 3. Config file — read once at startup, stored in a package-level var.
	if cfg.Token != "" {
		return cfg.Token
	}
	// 4. Default — empty string signals "not configured."
	return ""
}
```

**`On the job:`** The cross-reference here is intentional. Viper and the full configuration story — vault integration, secret rotation, validate-at-startup patterns — live in the **Configuration & Secrets Management** chapter (Part 2). What matters right now is understanding *where* config resolution lives in a CLI: in `PersistentPreRun`, before any `RunE` runs.

<Callout kind="pro" title="Validate config at startup, fail fast">

A CLI that reads a config file should validate it immediately, at startup, before running any command. If the config is malformed or a required value is missing, print a clear error and exit with a non-zero code. Do not let a bad config surface as a cryptic API error three commands deep. The `PersistentPreRun` hook is the right place — it runs before any command's logic, and its error return propagates cleanly.

</Callout>

Sometimes a CLI needs to talk *back* to the operator — confirm before an irreversible action, show a progress spinner during a long API call, or surface a dashboard of live account states. This is where interactive prompts and terminal UIs come in.

### Full TUIs with Bubble Tea

When the CLI needs to display live-updating information — a streaming feed of recent transfers, a dashboard of account balances, a transaction ledger that updates in real time — you need a full terminal UI. This is what Bubble Tea is built for.

<Define term="TUI / Bubble Tea (the Elm architecture)">
A **TUI** (terminal user interface) is a full-screen interactive program that runs inside a terminal emulator, handling keyboard input and rendering frames of output — think `htop`, `k9s`, or the interactive Git UI `lazygit`. **Bubble Tea** (`github.com/charmbracelet/bubbletea`) is the Go library for building TUIs. It implements the **Elm architecture**: your application is a **Model** (all state), an **Update** function (pure: takes a Model and a Msg, returns a new Model and a command to run), and a **View** function (pure: takes a Model, returns a string to render). The runtime loops: receive a `Msg` (keypress, timer, API response), call `Update`, render with `View`. Why it matters: the pure functional model makes TUIs testable — you can test Update by asserting on the returned Model without a real terminal. Bubble Tea is used for `gh`, the Charm toolchain, and dozens of developer tools.
</Define>

Here is the smallest complete Bubble Tea Model for a live Meridian account dashboard:

```go
// Not runnable in the playground — requires github.com/charmbracelet/bubbletea.

package main

import (
	"fmt"
	"time"

	tea "github.com/charmbracelet/bubbletea"
)

// Model holds all application state — the Elm equivalent of the Redux store.
type model struct {
	accounts []accountRow
	cursor   int
	loading  bool
	err      error
}

type accountRow struct {
	ID    string
	Cents int64
}

// tickMsg is sent on a timer to trigger a refresh.
type tickMsg time.Time

// fetchedMsg carries the result of an async API fetch.
type fetchedMsg struct {
	accounts []accountRow
	err      error
}

// Init returns the initial command to run when the program starts.
// We kick off a tick immediately so the first fetch happens right away.
func (m model) Init() tea.Cmd {
	return tick()
}

func tick() tea.Cmd {
	return tea.Tick(5*time.Second, func(t time.Time) tea.Msg {
		return tickMsg(t)
	})
}

// Update is pure: given the current Model and a Msg, return a new Model + next Cmd.
func (m model) Update(msg tea.Msg) (tea.Model, tea.Cmd) {
	switch msg := msg.(type) {
	case tea.KeyMsg:
		switch msg.String() {
		case "q", "ctrl+c":
			return m, tea.Quit
		case "up", "k":
			if m.cursor > 0 {
				m.cursor--
			}
		case "down", "j":
			if m.cursor < len(m.accounts)-1 {
				m.cursor++
			}
		}

	case tickMsg:
		m.loading = true
		// Return a command that fetches accounts and emits a fetchedMsg.
		return m, fetchAccounts()

	case fetchedMsg:
		m.loading = false
		if msg.err != nil {
			m.err = msg.err
			return m, tick() // retry on next tick
		}
		m.accounts = msg.accounts
		m.err = nil
		return m, tick() // schedule the next refresh
	}
	return m, nil
}

// fetchAccounts returns a Cmd that fetches accounts asynchronously.
// The Cmd runs in a goroutine managed by the Bubble Tea runtime.
func fetchAccounts() tea.Cmd {
	return func() tea.Msg {
		// In a real tool: call apiClient.ListAccounts(ctx).
		// Stub here for illustration.
		return fetchedMsg{
			accounts: []accountRow{
				{"acct_001", -169900},
				{"acct_002", 500000},
			},
		}
	}
}

// View is pure: given the Model, return the string to render.
// Bubble Tea prints this to stdout and clears the previous frame.
func (m model) View() string {
	if m.err != nil {
		return fmt.Sprintf("Error: %v\nPress q to quit.\n", m.err)
	}
	s := "Meridian Account Dashboard\n\n"
	for i, a := range m.accounts {
		cursor := "  "
		if i == m.cursor {
			cursor = "> "
		}
		sign := ""
		cents := a.Cents
		if cents < 0 {
			sign = "-"
			cents = -cents
		}
		s += fmt.Sprintf("%s%s  %s$%d.%02d\n", cursor, a.ID, sign, cents/100, cents%100)
	}
	if m.loading {
		s += "\nRefreshing...\n"
	}
	s += "\n↑/↓ to move  q to quit\n"
	return s
}

func main() {
	p := tea.NewProgram(model{loading: true})
	if _, err := p.Run(); err != nil {
		fmt.Println("error:", err)
	}
}
```

<Callout kind="pro" title="Bubble Tea commands are goroutine-safe">

Bubble Tea `Cmd` functions run in managed goroutines. You never spawn goroutines yourself in a Bubble Tea program — you return a `Cmd` from `Update`, and the runtime runs it for you and delivers the result as a `Msg`. This means your `Model` and `Update` are always called from a single goroutine — no synchronization needed on the model. It's the same guarantee the Elm runtime gives: `Update` is never concurrent.

</Callout>

**`On the job:`** `gh` (the GitHub CLI) uses Bubble Tea for its interactive PR selection, issue lists, and checkout flows. `k9s` (Kubernetes terminal UI) is built on a similar architecture. When an operator needs to browse 500 Meridian accounts or watch a streaming ledger update in real time, a TUI eliminates the need for a web dashboard for internal tooling.

## Shell completions & shipping

The difference between a good CLI and a great one is often nothing more than whether pressing Tab works.

<Define term="Shell completion">
**Shell completion** is the behavior where pressing Tab after partially typing a command or flag causes the shell to complete it or list options. For `meridian tran<Tab>` to complete to `meridian transfer`, and `meridian transfer create --fr<Tab>` to expand to `--from`, the shell needs a **completion script** — a file of shell functions that the shell sources at startup. Cobra generates these scripts automatically for bash, zsh, fish, and PowerShell. Why it matters: without completions, operators type full flag names from memory and make typos. With completions, the CLI is self-documenting and pleasant to use. It's a one-function call in Cobra and zero effort for users who install via Homebrew or a package manager.
</Define>

### Cobra auto-generates completions

```go
// Not runnable in the playground — requires the cobra module.

// Cobra's completion command is registered automatically if you add it:
rootCmd.AddCommand(rootCmd.GenCompletionCmd(true))

// Or call the generation functions directly:
// rootCmd.GenBashCompletionFile("meridian.bash")
// rootCmd.GenZshCompletionFile("meridian.zsh")
// rootCmd.GenFishCompletionFile("meridian.fish", true)
// rootCmd.GenPowerShellCompletionFile("meridian.ps1")

// Expose it as a sub-command: `meridian completion bash >> ~/.bash_profile`
var completionCmd = &cobra.Command{
	Use:   "completion [bash|zsh|fish|powershell]",
	Short: "Generate shell completion script",
	Args:  cobra.ExactArgs(1),
	RunE: func(cmd *cobra.Command, args []string) error {
		switch args[0] {
		case "bash":
			return cmd.Root().GenBashCompletion(os.Stdout)
		case "zsh":
			return cmd.Root().GenZshCompletion(os.Stdout)
		case "fish":
			return cmd.Root().GenFishCompletion(os.Stdout, true)
		case "powershell":
			return cmd.Root().GenPowerShellCompletionWithDesc(os.Stdout)
		default:
			return fmt.Errorf("unknown shell %q", args[0])
		}
	},
}
```

The operator runs `meridian completion zsh > ~/.zsh/completions/_meridian` once. After that, `meridian <Tab>` shows all subcommands; `meridian transfer create --<Tab>` shows `--from`, `--to`, `--amount`.

### Dynamic completions

For flags whose valid values come from an API (e.g., `--from` should complete with real account IDs), Cobra lets you register a completion function per flag:

```go
// Not runnable in the playground — requires the cobra module.

_ = transferCreateCmd.RegisterFlagCompletionFunc("from",
	func(cmd *cobra.Command, args []string, toComplete string) ([]string, cobra.ShellCompDirective) {
		// Call the API to get account IDs matching toComplete.
		accounts := fetchAccountIDsForCompletion(toComplete)
		return accounts, cobra.ShellCompDirectiveNoFileComp
	})
```

Now `meridian transfer create --from acct_<Tab>` queries the API and returns matching account IDs. This is the pattern `kubectl` uses for `kubectl get pods <Tab>` completing with real pod names from the cluster.

Cobra also generates man pages (`cmd.GenManTree(dir)`), which `Homebrew` and Linux package managers install automatically. One call, zero manual formatting.

<Exercise n={1} title="Implement a LogLevelFlag" level="easy">

Implement a `flag.Value` type called `LogLevelFlag` that parses the strings `"debug"`, `"info"`, `"warn"`, `"error"` (case-insensitive) into an `int` level (0, 1, 2, 3). `String()` should return the current level name. `Set()` should return an error for any unrecognized level. Register it with `flag.Var` and demonstrate parsing `--log-level warn`.

<Solution>

```go
package main

import (
	"flag"
	"fmt"
	"strings"
)

type LogLevelFlag struct {
	Level int
	name  string
}

var levelNames = map[string]int{
	"debug": 0,
	"info":  1,
	"warn":  2,
	"error": 3,
}

func (l *LogLevelFlag) String() string {
	if l.name == "" {
		return "info"
	}
	return l.name
}

func (l *LogLevelFlag) Set(s string) error {
	lower := strings.ToLower(s)
	n, ok := levelNames[lower]
	if !ok {
		return fmt.Errorf("unknown log level %q: must be debug, info, warn, or error", s)
	}
	l.Level = n
	l.name = lower
	return nil
}

func main() {
	fs := flag.NewFlagSet("demo", flag.ContinueOnError)
	var level LogLevelFlag
	fs.Var(&level, "log-level", "log level: debug, info, warn, error")

	if err := fs.Parse([]string{"--log-level", "warn"}); err != nil {
		fmt.Println("error:", err)
		return
	}
	fmt.Printf("log level: %s (%d)\n", level.String(), level.Level)
}
```

The key move: `levelNames` is a map for O(1) lookup rather than a `switch`, and `strings.ToLower` makes it case-insensitive without duplicating entries. `flag.NewFlagSet` with `ContinueOnError` lets the test assert on the returned error instead of calling `os.Exit`.

</Solution>

</Exercise>

<Exercise n={2} title="Add a nested Cobra subcommand" level="medium">

Without writing code, design the full command tree for a `meridian` CLI with these requirements: list accounts, create an account, get a single account; create and list transfers; verify the ledger; generate shell completions. Sketch which flags are persistent (on root) vs. local to each command. State your rationale.

<Solution>

```
meridian
├── [persistent flags on root]
│   --token     string  API token or MERIDIAN_TOKEN env
│   --output    string  table|json (default: table)
│   --endpoint  string  API base URL
│
├── accounts
│   ├── list    [--limit int, --cursor string for pagination]
│   ├── get     <account-id>  [no extra flags — ID is a positional arg]
│   └── create  --name string --currency string (required)
│
├── transfer
│   ├── list    [--account string filter, --limit int]
│   └── create  --from string --to string --amount string (all required)
│
├── ledger
│   └── verify  --from-date string --to-date string --account string
│
└── completion  [bash|zsh|fish|powershell]
```

**Rationale:**
- `--token`, `--output`, `--endpoint` are persistent on root: every command needs auth and output format.
- Account ID in `accounts get` is a positional arg, not a flag — positional args suit direct object identifiers that have no ambiguity.
- `transfer create` flags are all local and all required: `MarkFlagRequired` enforces them.
- `ledger verify` date flags are optional (default to a sensible range); `--account` could be required or optional depending on whether cross-account verification is supported.
- `completion` is a leaf with a positional shell-name argument — standard Cobra pattern.

</Solution>

<Exercise n={4} title="Implement config precedence by hand" level="medium">

Write a `resolveConfig` function that returns a `Config` struct with `Token string` and `Endpoint string`, resolving them in order: CLI flags (passed as `*string` pointers), then environment variables (`MERIDIAN_TOKEN`, `MERIDIAN_ENDPOINT`), then a `config` struct from a parsed config file, then compiled-in defaults. Use only stdlib — no Viper.

<Solution>

```go
package main

import (
	"fmt"
	"os"
)

type Config struct {
	Token    string
	Endpoint string
}

type fileConfig struct {
	Token    string
	Endpoint string
}

// resolveConfig applies flag > env > file > default precedence.
// flagToken and flagEndpoint are the values from flag.String; they are
// empty strings if the operator did not set them.
func resolveConfig(flagToken, flagEndpoint string, file fileConfig) Config {
	pick := func(flag, env, fileval, def string) string {
		if flag != "" {
			return flag
		}
		if e := os.Getenv(env); e != "" {
			return e
		}
		if fileval != "" {
			return fileval
		}
		return def
	}

	return Config{
		Token:    pick(flagToken, "MERIDIAN_TOKEN", file.Token, ""),
		Endpoint: pick(flagEndpoint, "MERIDIAN_ENDPOINT", file.Endpoint, "https://api.meridian.io"),
	}
}

func main() {
	// Simulate: --token not set, env has a value, file has a fallback.
	os.Setenv("MERIDIAN_TOKEN", "tok_from_env")

	cfg := resolveConfig(
		"",        // flag not set
		"",        // flag not set
		fileConfig{Token: "tok_from_file", Endpoint: "https://staging.meridian.io"},
	)
	fmt.Printf("token=%s endpoint=%s\n", cfg.Token, cfg.Endpoint)
	// Output: token=tok_from_env endpoint=https://staging.meridian.io
	// (env beats file; endpoint not in env so file value is used)
}
```

The `pick` helper makes the precedence explicit and readable. Notice the compiled-in default for `Endpoint` (layer 4) means the program works out of the box with no configuration at all.

</Solution>

<Exercise n={5} title="Write a Bubble Tea counter model" level="hard">

Implement a minimal Bubble Tea `model` for a simple counter that increments on the `+` key, decrements on `-`, resets on `r`, and quits on `q`. `View()` should display the current count and available keys. Test `Update` directly without running a real Bubble Tea program — call `Update` with synthetic `tea.KeyMsg` values and assert on the returned model's count. Requires `go get github.com/charmbracelet/bubbletea`.

<Solution>

```go
// go get github.com/charmbracelet/bubbletea — not runnable in the playground.

package main

import (
	"fmt"
	"testing"

	tea "github.com/charmbracelet/bubbletea"
)

type model struct {
	count int
}

func (m model) Init() tea.Cmd { return nil }

func (m model) Update(msg tea.Msg) (tea.Model, tea.Cmd) {
	switch msg := msg.(type) {
	case tea.KeyMsg:
		switch msg.String() {
		case "+":
			m.count++
		case "-":
			m.count--
		case "r":
			m.count = 0
		case "q", "ctrl+c":
			return m, tea.Quit
		}
	}
	return m, nil
}

func (m model) View() string {
	return fmt.Sprintf("count: %d\n\n+ increment  - decrement  r reset  q quit\n", m.count)
}

// TestUpdate exercises Update without a real terminal.
func TestUpdate(t *testing.T) {
	m := model{}

	key := func(s string) tea.Msg {
		return tea.KeyMsg{Type: tea.KeyRunes, Runes: []rune(s)}
	}

	next, _ := m.Update(key("+"))
	m = next.(model)
	if m.count != 1 {
		t.Errorf("after +: count = %d, want 1", m.count)
	}

	next, _ = m.Update(key("+"))
	m = next.(model)
	next, _ = m.Update(key("-"))
	m = next.(model)
	if m.count != 1 {
		t.Errorf("after ++-: count = %d, want 1", m.count)
	}

	next, _ = m.Update(key("r"))
	m = next.(model)
	if m.count != 0 {
		t.Errorf("after reset: count = %d, want 0", m.count)
	}
}

func main() {
	p := tea.NewProgram(model{})
	if _, err := p.Run(); err != nil {
		fmt.Println("error:", err)
	}
}
```

The key insight: because `Update` is a pure function (no side effects, returns a new model), you can test it by calling it directly with synthetic messages. No terminal, no goroutines, deterministic. This is the Elm architecture's biggest practical win.

</Solution>

</Exercise>

<Recap>

- **`flag.FlagSet`** is the real engine under `flag.Parse()`. Create one per subcommand for hand-rolled dispatch. Custom types via `flag.Value` (`String()`, `Set()`) let the parser validate rich inputs — amounts in cents, log levels, lists — at parse time.
- **Cobra** formalizes the FlagSet-per-subcommand pattern into a tree of `cobra.Command` structs. Persistent flags propagate down the tree; `PersistentPreRun` runs before every command's `RunE` for cross-cutting setup like auth. Use `RunE` (not `Run`) so errors propagate cleanly.
- **urfave/cli** is the lighter alternative: declarative `cli.App`, built-in `EnvVars` per flag, less boilerplate. Pick Cobra for large trees; urfave/cli for smaller operator tools.
- **Config precedence**: flags beat env vars beat config files beat defaults. Viper implements this with `viper.BindPFlag` + `viper.AutomaticEnv`. Without Viper, implement it explicitly in `PersistentPreRun` — explicit is better.
- **Bubble Tea** implements the Elm architecture (Model/Update/View) for full TUIs. `Update` is a pure function — testable without a real terminal. Commands (`tea.Cmd`) are managed goroutines that deliver results as `Msg` values.
- **Shell completions** are free with Cobra: `cmd.Root().GenBashCompletion(os.Stdout)`. Dynamic completions via `RegisterFlagCompletionFunc` let Tab-complete query live API data.
- The Go CLI ecosystem is not an accident. Static binaries, fast startup, goroutine-based concurrency for streaming, and a rich stdlib that doesn't need a runtime — that's why `kubectl`, `docker`, `gh`, and `terraform` all wrote Go.

</Recap>
