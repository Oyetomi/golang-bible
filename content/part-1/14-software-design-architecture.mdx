## SOLID in Go

<Define term="SOLID" since="Design Patterns, the Go Way (Part 1, Chapter 11)">
Five design principles (Single Responsibility, Open/Closed, Liskov Substitution, Interface Segregation, Dependency Inversion) that keep code changeable without cascading breakage. Go maps some beautifully (ISP, DIP) and ignores others (inheritance-based OCP). Use them as a **diagnostic**, not a religion: when a change breaks three things at once, ask which principle was violated.
</Define>

<Define term="Single Responsibility Principle (SRP)">
A type has **one reason to change** — not one method, one *reason*. `LedgerService` recording transactions is one responsibility. `LedgerService` also sending email is a second. When the email provider changes, the ledger logic shouldn't need a rewrite. If removing a feature requires touching the type, the type owns too many jobs.
</Define>

<Define term="Dependency Inversion Principle (DIP)">
High-level modules (domain business logic) must **not import** low-level modules (databases, HTTP clients). Both depend on an **abstraction** — an interface — that the high-level module defines. In Go: the domain package declares `type EntryWriter interface{...}`; the Postgres package implements it. The import arrow points *inward*, toward the domain, always.
</Define>

Let me set the scene with something real. You're building a ledger service — the kind that records every financial transaction for an account. It starts simple: one file, one struct, everything in `main`. Then product adds reporting. Then compliance wants an audit trail. Then you need to swap SQLite for Postgres. Then a third service needs to call you over gRPC.

You're six months in and every change breaks three other things. That's not a Go problem. That's a design problem, and the five SOLID principles are the diagnostic tool you reach for first.

SOLID comes from object-oriented languages, so let's be upfront: **Go maps some of them beautifully and ignores others entirely**. I'll tell you which is which, because I don't teach from dogma — I teach from reality.

### Single Responsibility Principle

**One type, one reason to change.** Not "one function," not "one file" — one *reason to change*. This is the easiest principle to understand and the most violated one in every Go codebase I've ever had to rescue.

Here's the classic sin in our ledger service:

```go
// BAD: LedgerService does everything — it's three different jobs in a trench coat.
type LedgerService struct {
	db *sql.DB
}

// Records a transaction AND formats a PDF report AND sends email.
func (s *LedgerService) PostAndReport(entry Entry) error {
	// post to DB...
	// render PDF...
	// send email via SMTP...
	return nil
}
```

SRP in Go doesn't mean "one method per struct." It means asking: *if this requirement changes, which types have to change?* When the answer is more than one, you've violated SRP. Keep cutting.

### Open/Closed Principle

**Open for extension, closed for modification.** In class-based languages this means inheritance. In Go, it means **interfaces**. You write code that accepts a behavior via an interface, and new behaviors arrive by implementing that interface — you never touch the original.

```go
// The LedgerWriter interface is closed for modification — it never changes.
// Every new storage backend extends the system by implementing it.
type LedgerWriter interface {
	Save(ctx context.Context, entry Entry) error
}

// PostgresStore: implements LedgerWriter with Postgres.
type PostgresStore struct{ db *sql.DB }

func (s *PostgresStore) Save(ctx context.Context, e Entry) error { /* ... */ return nil }

// AuditStore: wraps any LedgerWriter to also write to an immutable audit log.
// Extension via composition — no modification of PostgresStore.
type AuditStore struct {
	inner LedgerWriter
	audit AuditLogger
}

func (a *AuditStore) Save(ctx context.Context, e Entry) error {
	if err := a.inner.Save(ctx, e); err != nil {
		return err
	}
	return a.audit.Log(ctx, e)
}
```

The `AuditStore` is the decorator pattern from the previous chapter applied as OCP. You composed your way to a new behavior, zero modifications to existing code.

### Liskov Substitution Principle

**Any value of an interface can replace any other.** In Go this is just the type system. If `PostgresStore` implements `LedgerWriter`, you can use it anywhere a `LedgerWriter` is expected. The compiler enforces this at compile time.

The Go-specific LSP trap: methods with **pointer receivers vs value receivers**. If your interface method set requires a pointer receiver, a value of that type won't satisfy the interface — the compiler will tell you, loudly. That's actually LSP being enforced for you.

<Callout kind="warn" title="LSP and nil interface gotcha">

LSP pairs with the infamous **typed nil trap**. A `*PostgresStore` that is `nil` satisfies the `LedgerWriter` interface — the interface value is non-nil. Then your code calls `.Save()` on it and panics. The rule: never return a concrete nil pointer through an interface. Return a plain `nil` error interface instead. This is covered in depth in the Error Handling chapter (Part 2, Chapter 2).

</Callout>

### Interface Segregation Principle

**This one is Go's strongest hand.** ISP says: don't force a client to depend on methods it doesn't use. In class-based languages, fat interfaces are a plague. In Go, **interfaces are defined by the consumer, not the implementor**, and they're so lightweight that a one-method interface is completely normal.

<BeforeAfter

The Go proverb: **"The bigger the interface, the weaker the abstraction."** A one-method interface like `io.Reader` is the most powerful interface in the standard library precisely because it's so small that everything can satisfy it.

### Dependency Inversion Principle

**High-level modules should not depend on low-level modules. Both should depend on abstractions.** This is the one that matters most for architecture, and it's where most teams get it catastrophically wrong.

In our ledger service the wrong direction looks like this: the domain (business logic) imports the database package. Now the domain *depends on* a specific database. Swap Postgres for MySQL and you're refactoring the domain.

The right direction: **the domain defines an interface (the abstraction), and the database implements it.** The dependency arrow *inverts* — the DB package depends on the domain, not the other way around.

<UnderTheHood title="How Go interfaces work at the machine level">

A Go interface value is **two machine words**: a pointer to the *type descriptor* (the itable — interface table) and a pointer to the *data*. The itable is generated at compile time for each concrete-type/interface pair and caches the function pointers for each method.

When the compiler sees `var w LedgerWriter = &PostgresStore{db}`, it:
1. Verifies at compile time that `*PostgresStore` has a `Save` method with the right signature — no itable needed yet.
2. At the assignment site, it generates a small itable for the `(*PostgresStore, LedgerWriter)` pair and sets the first word of the interface value to point to it.
3. The second word points to the `PostgresStore` value (or a copy of it, if non-pointer).

**Calling a method through an interface** is therefore a double-pointer dereference: load the itable pointer, load the function pointer at the right offset, call it. This is *slightly* more expensive than a direct call, but the compiler can devirtualize (inline the real function) when the concrete type is visible at the call site.

The important implication: **there is zero runtime registration**. A type satisfies an interface the instant it has the right methods. The itable is built by the compiler, not by some `Register()` call. This is why Go's implicit interface satisfaction is both fast and correct — it's all verified at compile time, and the performance cost is a single extra indirection when the concrete type can't be devirtualized.

*Note: itable generation and devirtualization behavior applies to the unified IR compiler pipeline (`cmd/compile`), current as of Go 1.26.*

</UnderTheHood>

## Package Design

<Define term="Package / dependency direction">
A Go **package** is the unit of compilation, namespacing, and design. **Dependency direction** is the direction the `import` arrows point in your import graph. The rule: arrows must always flow from outer layers (HTTP, DB) toward inner layers (domain). A domain package that imports a DB package has a reversed arrow — it is coupled to infrastructure detail it should never know about. The Go compiler enforces no cycles, but direction is your problem.
</Define>

<Define term="Coupling vs cohesion">
**Coupling** is how much one package depends on the internals of another — low coupling means changes don't ripple. **Cohesion** is how related the things inside a package are — high cohesion means the package has one clear job. The goal is always: **high cohesion, low coupling**. A `util/` or `helpers/` package is typically low cohesion (everything dumps in) and high coupling (everything imports it). Split by domain concept, not by type category.
</Define>

Packages in Go are the atomic unit of design. Not classes, not modules — **packages**. Get this right and everything else falls into place. Get it wrong and you'll have import cycles that make you want to quit the industry.

### One clear purpose per package

A package is a namespace, a compilation unit, and a design boundary. The question to ask for every package: **"What is this package *for*?"** If the answer has an "and" in it, split the package.

Our ledger service packages might look like this:

- `ledger` — the domain: types, business rules, interfaces
- `postgres` — implements `ledger.EntryWriter` against Postgres
- `http` — HTTP adapter that calls the domain
- `cmd/ledger` — wires everything together and calls `main`

Each package answers one question. No package is a dumping ground.

### No import cycles — the Go compiler enforces this

Go's compiler **refuses to compile circular imports**. Package A cannot import package B if B imports A. This is not a limitation — it's the compiler protecting you from a design smell. If you've reached for an import cycle, you have two packages that are secretly one package, or you have a dependency that belongs in a third package.

The fix for every import cycle: **extract the shared type or interface into a third package that both depend on**, or merge the two packages. Usually the former.

```go
// cycle-breaker: the domain package declares the types both sides need.
// Neither 'postgres' nor 'http' import each other — they both import 'ledger'.

// package ledger
type Entry struct {
	ID          string
	AccountID   string
	AmountCents int64
}

type EntryWriter interface {
	Save(ctx context.Context, e Entry) error
}

// package postgres   (imports ledger, NOT http)
type Store struct{ db *sql.DB }
func (s *Store) Save(ctx context.Context, e ledger.Entry) error { /* ... */ return nil }

// package http      (imports ledger, NOT postgres)
type Handler struct{ writer ledger.EntryWriter }
func (h *Handler) Post(w http.ResponseWriter, r *http.Request) { /* ... */ }
```

### The `internal/` directory

<Define term="internal/ directory">
A **compiler-enforced** encapsulation boundary. Any package whose path contains `internal/` can only be imported by code rooted at the parent directory. External modules — other services, other teams — get a hard build error if they try to import it. Use it for implementation packages you aren't willing to commit to as a stable public API. The result: you can refactor freely without breaking external callers, because there are none.
</Define>

Go has a built-in mechanism for encapsulation at the package level: **`internal/`**. Any code inside an `internal/` directory can only be imported by code in the parent directory tree.

```
ledger-service/
├── cmd/
│   └── ledger/
│       └── main.go          ← can import internal/
├── internal/
│   ├── domain/              ← your core types and interfaces
│   ├── postgres/            ← DB adapter
│   └── httpapi/             ← HTTP adapter
└── go.mod
```

External consumers — other services, other modules — cannot import your `internal/` packages. This is the Go toolchain enforcing your API surface. What's in `internal/` is yours to change without fear of breaking external callers.

<Callout kind="pro" title="internal/ is your friend, not a smell">

Some engineers treat `internal/` as a confession of messiness. Wrong. It's a *contract*: these packages are implementation details. Use it liberally. The only packages that should be publicly importable are the ones you're deliberately committing to support as a stable API.

</Callout>

### Package naming

Go package names follow three rules the standard library never breaks:
1. **Lowercase, single word** — `ledger`, `postgres`, `httpapi`, not `LedgerService` or `http_api`.
2. **Named for what it provides**, not what it does — `ledger` not `process`, `postgres` not `database`.
3. **No stutter** — if your package is named `ledger`, don't call the main type `LedgerEntry`. Call it `Entry`. The caller writes `ledger.Entry` — the package name is the prefix.

<Define term="Hexagonal Architecture (Ports and Adapters)" since="Microservices (Part 1, Chapter 22)">
An architectural pattern that divides a service into three concentric zones: the **domain** (pure business logic, no infrastructure imports), **ports** (interfaces the domain defines — what it needs from the world), and **adapters** (implementations of those ports that connect to real infrastructure: HTTP handlers, Postgres stores, gRPC clients). The key rule: all dependency arrows point inward. Swap any adapter without touching a line of domain code. If it takes more than an afternoon to swap your database, you don't have hexagonal — you have layers with the same tangled dependencies renamed.

**On the job:** Meridian's ledger service serves HTTP today but will need a gRPC interface for an internal settlement service next quarter. With a hexagonal domain, a new `GRPCAdapter` implements the same port — the domain changes nothing.
</Define>

Now we're at the architecture pattern that changes everything. Let me make it concrete with our ledger service, then animate a full request through every layer.

**Hexagonal architecture** (also called **Ports and Adapters**, coined by Alistair Cockburn) divides your service into three concentric zones:

1. **The Domain** — pure business logic and types. Knows nothing about HTTP, databases, or any external technology. Defines *ports* (interfaces) that describe what it needs from the outside world.
2. **Ports** — the interfaces the domain declares. `EntryWriter`, `EntryReader`, `AuditLogger`. The domain owns these.
3. **Adapters** — the implementations of those ports that connect to real infrastructure. `PostgresStore` implements `EntryWriter`. `HTTPHandler` calls into the domain. Each adapter translates between the domain's language and a specific technology's language.

Here's the key insight that makes this click: **the domain is the inside, and everything else is outside**. Adapters can be swapped. The domain is stable.

```go
// package domain — the pure inside. No DB imports, no HTTP imports.

// Entry is a domain type. It lives here, defined by business rules.
type Entry struct {
	ID          string
	AccountID   string
	AmountCents int64 // never a float — not here, not anywhere
	Description string
}

// EntryWriter is a PORT — an interface the domain defines and depends on.
// The domain declares what it needs; it doesn't care how it's fulfilled.
type EntryWriter interface {
	Save(ctx context.Context, entry Entry) error
}

// LedgerService is the domain logic. It depends on the PORT, not an adapter.
type LedgerService struct {
	store EntryWriter // injected at startup
}

// PostEntry enforces business rules before delegating to the port.
func (s *LedgerService) PostEntry(ctx context.Context, e Entry) error {
	if e.AmountCents == 0 {
		return fmt.Errorf("entry amount cannot be zero: account %s", e.AccountID)
	}
	if e.AccountID == "" {
		return fmt.Errorf("entry must have an account ID")
	}
	return s.store.Save(ctx, e) // calls through the port
}
```

This is not abstraction for its own sake. It's **load-bearing structure**. When compliance demands you also write every entry to an immutable audit log, you wrap the `EntryWriter` port with an `AuditingStore` decorator — the domain changes nothing. When you need to test the domain in isolation, you swap `PostgresStore` for `InMemoryStore` — five lines of code, no Docker container.

<UnderTheHood title="Why the Go compiler makes hexagonal architecture free">

In Java or C#, implementing an interface requires an explicit `implements` declaration. In Go, **interface satisfaction is structural and implicit** — no registration, no declaration. This has a profound consequence for hexagonal architecture:

Your domain defines `type EntryWriter interface { Save(...) error }`. Your Postgres adapter, written entirely independently, has `func (s *Store) Save(...) error`. Go's compiler silently notes that `*Store` satisfies `EntryWriter` at the assignment site. Zero boilerplate. Zero coupling between the interface definition and the implementation file.

This means you can define a domain port *after* writing the adapter, or have an adapter implement a port it's never directly imported — the compiler sorts it out. This is a design decision that makes the ports-and-adapters pattern natural in Go and awkward in languages that require explicit declaration.

*The implicit satisfaction is verified at compile time, not at runtime — a `*Store` that's missing the `Save` method produces a compile error the moment you try to assign it to an `EntryWriter`, not a surprise nil-pointer panic at 3am.*

</UnderTheHood>

<Callout kind="tip" title="Errors crossing port boundaries — Go 1.26">

When an adapter returns an error through a domain port, the domain often needs to distinguish infrastructure errors (DB timeout) from domain violations (duplicate entry). As of Go 1.26, `errors.AsType[T]` makes typed unwrapping more ergonomic — instead of declaring a variable first, you can write:

```go
if dbErr, ok := errors.AsType[*pq.Error](err); ok {
    // handle Postgres-specific error
}
```

This is covered in depth in the Error Handling chapter (Part 2, Chapter 2). The architectural rule remains: the domain should never import the concrete error type from the adapter package. Wrap adapter errors in domain-defined error types before returning them through the port.

</Callout>

## Domain Modeling

<Define term="Domain model" since="Representing Money & Domain Types (Part 3, Chapter 1)">
The **domain model** is the Go code that expresses business concepts and enforces business rules — independent of any database, HTTP framework, or external service. It contains your types (`Account`, `Entry`, `Money`), your rules ("an entry amount cannot be zero"), and your ports (interfaces describing what the domain needs from outside). The domain model must compile and be testable with no infrastructure whatsoever. If your domain package imports `database/sql` or `net/http`, it is not a domain model — it is a service layer.
</Define>

The domain is where business rules live and where the language needs to match the business. Good domain modeling means your Go code can be *read aloud* to a domain expert and they understand it.

### Entities vs. value objects

Two kinds of things live in your domain:

**Entities** have identity — they're tracked by ID through their entire lifecycle. An `Account` is an entity. Two accounts with different IDs are different accounts even if they have the same balance.

**Value objects** have no identity — two values with the same data are the same thing. An `AmountCents` of `1000` and another `AmountCents` of `1000` are identical and interchangeable.

```go
// Entity: Account has identity (AccountID). Two accounts are different even
// if their balances are equal.
type Account struct {
	ID           string // identity
	OwnerName    string
	BalanceCents int64
}

// Value object: Money has no identity. $10.00 is $10.00 wherever it appears.
// In Go, value objects are typically small structs with value semantics.
// We'll expand this enormously in Part 3 — but plant the flag now.
type Money struct {
	AmountCents int64
	Currency    string // "USD", "EUR"
}

// Value objects should be comparable and immutable.
func (m Money) Add(other Money) (Money, error) {
	if m.Currency != other.Currency {
		return Money{}, fmt.Errorf("currency mismatch: %s != %s", m.Currency, other.Currency)
	}
	return Money{AmountCents: m.AmountCents + other.AmountCents, Currency: m.Currency}, nil
}
```

### Keeping business rules in the domain

This is the rule that gets violated more than any other: **if it's a business rule, it lives in the domain — never in the HTTP handler, never in the SQL query.**

```go
// WRONG: business rule in the HTTP handler
func (h *Handler) Transfer(w http.ResponseWriter, r *http.Request) {
	// ... decode request ...
	if amount <= 0 { // this is a business rule — it doesn't belong here
		http.Error(w, "amount must be positive", 400)
		return
	}
	if from == to { // also a business rule
		http.Error(w, "cannot transfer to same account", 400)
		return
	}
	h.store.Transfer(ctx, from, to, amount) // ... etc
}

// RIGHT: business rule in the domain service
func (s *TransferService) Transfer(ctx context.Context, from, to string, amount Money) error {
	if amount.AmountCents <= 0 {
		return fmt.Errorf("transfer amount must be positive, got %d cents", amount.AmountCents)
	}
	if from == to {
		return fmt.Errorf("cannot transfer to the same account: %s", from)
	}
	// proceed with transfer...
	return nil
}
```

The HTTP handler now has one job: translate HTTP ↔ domain. The business rule runs regardless of whether the call came from HTTP, gRPC, a CLI, or a test.

### From requirements to design

Everything above tells you what a *good* design looks like. It does not tell you how to *arrive* at one. So let me show you the part most engineers skip — the part where they go straight from a one-line ticket to typing `func` and then wonder, three weeks later, why the whole thing has to be rewritten.

Here's a real ticket: **"Let users schedule recurring transfers."** That's it. That's the whole request. An amateur opens an editor. You don't. You design the *right* application before you design the application right.

<Define term="Functional vs. nonfunctional requirements">
A **functional requirement** says what the application must *do* — "a user can schedule a transfer to repeat weekly." A **nonfunctional requirement** is a *constraint* on how it does it — "a scheduled transfer must never fire twice for the same period," "the scheduler must survive a process restart." Functional requirements become your types and methods; nonfunctional requirements become your invariants, your idempotency keys, and your test cases. Miss the nonfunctional ones and you ship a scheduler that double-charges every customer the first time a pod restarts.
</Define>

**Step 1 — validate the requirements before you write a line of Go.** The ticket is ambiguous, and ambiguity is where bugs are born. You go back with questions: Recurring how — daily, weekly, monthly? What happens on the 31st in February? Can a user pause one? What if the source account is empty when it fires? Each answer is a requirement you'd otherwise have *invented* — wrongly — at the keyboard. Validating requirements is cheap; backtracking out of a shipped design is not.

**Step 2 — textual analysis: nouns become types, verbs become behavior.** Read the validated requirements as plain English and underline the **nouns** — they are your candidate types. Underline the **verbs** — they are your candidate methods and ports. "A *user* schedules a recurring *transfer* on a *schedule*; the *scheduler* fires *due* transfers" hands you the model almost for free:

```go
// Nouns → types. (Money stays cents; never a float — you know this by now.)
type Schedule struct {
	Interval  Interval  // "daily" | "weekly" | "monthly"
	NextRunAt time.Time // when it fires next
}

type RecurringTransfer struct {
	ID       string
	FromAcct string
	ToAcct   string
	Cents    int64
	Schedule Schedule
	Paused   bool
}

// Verbs → behavior. "fire due transfers" and "save" are ports the
// domain defines; "schedule" and "pause" are domain methods.
type TransferRunner interface { // a port — what the domain needs from the world
	Execute(ctx context.Context, t RecurringTransfer) error
}

func (t *RecurringTransfer) Pause()       { t.Paused = true }
func (t *RecurringTransfer) Due(now time.Time) bool {
	return !t.Paused && !now.Before(t.Schedule.NextRunAt)
}
```

Notice what fell out: `RecurringTransfer` and `Schedule` are **entities and value objects** (the distinction you just learned). `TransferRunner` is a **port** (Dependency Inversion in action). You didn't decide that — the requirements decided it, and the analysis surfaced it.

**Step 3 — design, code, *test*, then loop.** Good design is not a waterfall where you draw the perfect diagram, implement it, and ship. It is iterative. You sketch the types, write a test that encodes one requirement ("a paused transfer is never due"), implement just enough to pass it, and look at what the code is telling you. Often it tells you the design is wrong — and you **backtrack**.

## Project Layout

Alright. Let's talk about the thing that generates more heated arguments in the Go community than anything except tabs-vs-spaces. (It's tabs. The formatter decided. Move on.)

### The honest take on the "standard layout"

You've seen the "golang-standards/project-layout" repository. It has tens of thousands of stars and the word "standard" in its name. I need you to know something: **it is not the Go team's standard**. It is one contributor's opinion, presented with an authoritative name, and the Go team has explicitly said it does not represent official guidance.

Here's what the repo recommends that causes the most cargo-culting:

```
myapp/
├── cmd/
├── pkg/        ← the source of the drama
├── internal/
└── ...
```

The `pkg/` directory convention says: "put your public Go packages here." But **it's redundant**. A Go package is public when it's exported (capital letter identifiers) and not inside `internal/`. You don't need a folder called `pkg` to make that happen. The Go standard library doesn't use it. Most well-regarded Go projects don't use it. It's a habit imported from languages that need a separate convention for distinguishing public vs. private.

### When `cmd/` + `internal/` is enough

For the vast majority of services — including ledger services, blog aggregators, payment processors — the `cmd/` + `internal/` layout is everything you need:

- **`cmd/<servicename>/main.go`** — the composition root. Wire up the DB, create the domain service, inject it into the HTTP handler, start the server. This is the *only* place that knows about all the concrete types. Keep it thin.
- **`internal/domain/`** — pure domain: types, entities, value objects, ports (interfaces), and domain services. Nothing from outside goes here.
- **`internal/postgres/`** — implements the domain's ports against Postgres. Imports `internal/domain` and `database/sql` or `pgx`. That's it.
- **`internal/httpapi/`** — the HTTP adapter. Imports `internal/domain`, handles request parsing and response writing. No DB imports.

If you're building a library that other modules will import (not a service), you don't use `internal/` for the public API — you put the public packages at the root or in a subdirectory, with no `pkg/` intermediary required.

```go
// cmd/ledger/main.go — the composition root.
// This is the one place that knows about all the concrete types.
// Everything else gets an interface.
func main() {
	// 1. Load config and connect to infrastructure
	db, err := sql.Open("pgx", os.Getenv("DATABASE_URL"))
	if err != nil {
		log.Fatal(err)
	}

	// 2. Build adapters (implement domain ports)
	store := postgres.NewStore(db)

	// 3. Build domain service (inject port implementations)
	ledgerSvc := domain.NewLedgerService(store)

	// 4. Build HTTP adapter (inject domain service)
	handler := httpapi.NewHandler(ledgerSvc)

	// 5. Start the server
	log.Fatal(http.ListenAndServe(":8080", handler))
}
```

<Callout kind="warn" title="The myth of the 'models' package">

The other cargo-cult to eliminate immediately: the `models/` package that everything imports. When `domain`, `http`, `postgres`, and `cmd` all import `models`, you've re-invented the global namespace. Every type change breaks everything. Instead, own your types in the package that has the most knowledge of them — usually the domain — and let adapters translate at their boundaries.

## Designing for Testability

This is the payoff. Everything we've done — small interfaces, dependency injection, hexagonal layers, domain purity — was secretly all about this: **making your code trivially testable without a database, a message queue, or a running HTTP server.**

### Dependency injection creates seams

A **seam** (term from Michael Feathers' *Working Effectively with Legacy Code*) is a place in your code where you can change behavior without changing the code itself. In Go, seams are created by accepting interfaces.

Every place `LedgerService` accepts an `EntryWriter` is a seam. In tests, you inject a fake. In production, you inject the Postgres store. The `LedgerService` doesn't know or care which one it got.

```go
// A fake that satisfies EntryWriter — perfect for tests.
// No Postgres. No Docker. No network.
type FakeStore struct {
	Entries []Entry
	Err     error // inject an error to test error paths
}

func (f *FakeStore) Save(_ context.Context, e Entry) error {
	if f.Err != nil {
		return f.Err
	}
	f.Entries = append(f.Entries, e)
	return nil
}

// The test: pure Go, no infrastructure, runs in milliseconds.
func TestLedgerService_PostEntry_RejectsZeroAmount(t *testing.T) {
	store := &FakeStore{}
	svc := domain.NewLedgerService(store)

	err := svc.PostEntry(context.Background(), Entry{
		AccountID: "acct-001", AmountCents: 0,
	})

	if err == nil {
		t.Fatal("expected an error for zero-amount entry, got nil")
	}
	if len(store.Entries) != 0 {
		t.Fatalf("expected nothing saved, got %d entries", len(store.Entries))
	}
}
```

### Hexagonal architecture makes integration tests trivial

When your adapters implement clean interfaces, integration tests against a real DB are also easy to isolate. You test the *adapter* in isolation against a real (but ephemeral) Postgres, separately from testing the *domain* against a fake. Each kind of test does one job:

<ConceptGrid cols={3}>
  <ConceptCard label="Unit tests (milliseconds)">Test domain logic with fake adapters. Fast, no infrastructure, run on every save. `go test ./internal/domain/...`</ConceptCard>
  <ConceptCard label="Adapter tests (seconds)">Test Postgres adapter against a real DB (testcontainers-go spins one up). Slow but real. `go test ./internal/postgres/...`</ConceptCard>
  <ConceptCard label="Integration tests (seconds)">Test the full wired service end-to-end — but only a few happy paths. Catch wiring bugs. Rarely run in dev, always in CI.</ConceptCard>
  <Gotcha>If your unit tests require a running database, your architecture has leaked. The domain importing a concrete DB type is the root cause. Fix the dependency direction first; the tests become fast as a consequence.</Gotcha>
</ConceptGrid>

### The fake vs. mock debate

I know what you're about to ask. "Why write a `FakeStore` by hand when a mock framework like `gomock` or `testify/mock` can generate it?"

Both have a place, but here's the reality: **a hand-written fake is often better**. A fake is a real implementation that happens to be in-memory — it can have state, it can enforce the same invariants as the real implementation, and it's easy to read. A generated mock records calls and returns pre-programmed answers — it's coupled to the exact call sequence and breaks when you refactor a method without changing behavior.

The rule: use fakes for domain ports (they're stable interfaces); use mocks when you need to verify that a *specific call was made in a specific way* and the interface is too large to fake cheaply. And define those mocks in the test file, not globally. The Testing in Go chapter goes deep on this — treat this section as the motivating context.

<Exercise n={1} title="Map a SOLID violation" level="easy">

You're given this struct from a payments service:

```go
type PaymentProcessor struct {
	db      *sql.DB
	mailer  *smtp.Client
	logger  *log.Logger
}

func (p *PaymentProcessor) ChargeAndNotify(userID string, cents int64) error {
	// charge the card, record to DB, send receipt email, log everything
	return nil
}
```

Name which SOLID principle(s) are violated and explain exactly why. No code needed — just the analysis.

<Solution>

**Single Responsibility Principle** — `PaymentProcessor` has at least three reasons to change: (1) how charging works, (2) how email is sent, (3) how logging is done. When the email provider changes, `PaymentProcessor` has to change — but it shouldn't need to.

**Interface Segregation** — `PaymentProcessor` is a concrete struct, not an interface, but the callers of `ChargeAndNotify` are forced to depend on a type that carries DB, mail, and logging concerns — even if they only need charging.

**Dependency Inversion** — `PaymentProcessor` depends directly on `*sql.DB` and `*smtp.Client` (low-level, concrete infrastructure) rather than on interfaces. The domain is coupled to the infrastructure layer.

The fix: define a `ChargeRecorder` interface and a `Notifier` interface, inject them into a slimmer `Charger` struct, and move the logging to the adapter layer.

</Solution>

<Exercise n={2} title="Define a port" level="easy">

For the ledger service, define the following domain ports as Go interfaces in a package named `domain`. Each interface should be as small as possible (ISP):

1. `EntryWriter` — can save a new entry
2. `EntryReader` — can fetch all entries for a given account ID
3. `AuditLogger` — can append an immutable audit event (no return value — fire and forget, but it can error)

<Solution>

```go
package domain

import "context"

// Entry is a ledger entry. AmountCents is positive for credits, negative for debits.
type Entry struct {
	ID          string
	AccountID   string
	AmountCents int64
	Description string
}

// AuditEvent is an immutable record of something that happened.
type AuditEvent struct {
	ActorID   string
	Action    string
	EntryID   string
}

// EntryWriter is the port for persisting new ledger entries.
// Implemented by PostgresStore, InMemoryStore, etc.
type EntryWriter interface {
	Save(ctx context.Context, entry Entry) error
}

// EntryReader is the port for reading ledger history.
// A reporting service only needs this — not Save or Delete.
type EntryReader interface {
	FindByAccount(ctx context.Context, accountID string) ([]Entry, error)
}

// AuditLogger is the port for appending to the immutable audit log.
type AuditLogger interface {
	Log(ctx context.Context, event AuditEvent) error
}
```

Each interface has exactly one method. A reconciliation service that needs both reading and writing composes them: `type ReconcilerStore interface { EntryReader; EntryWriter }`.

</Solution>

<Exercise n={3} title="Implement a fake adapter" level="medium">

Implement an `InMemoryStore` that satisfies both `EntryWriter` and `EntryReader` from Exercise 2. It must:
- Store entries in a slice (thread-unsafe is fine here — we'll add locking in the concurrency chapter)
- Return only entries matching the requested account ID
- Be injectable into a `LedgerService`

Write a small `main` that wires it together and posts two entries for account `"acct-001"` and one for `"acct-002"`, then reads back account `"acct-001"` entries.

```go
package main

import (
	"context"
	"fmt"
)

type Entry struct {
	ID          string
	AccountID   string
	AmountCents int64
	Description string
}

type EntryWriter interface {
	Save(ctx context.Context, entry Entry) error
}

type EntryReader interface {
	FindByAccount(ctx context.Context, accountID string) ([]Entry, error)
}

// InMemoryStore satisfies both ports — no SQL, no Docker, no problem.
type InMemoryStore struct {
	entries []Entry
}

func (s *InMemoryStore) Save(_ context.Context, e Entry) error {
	s.entries = append(s.entries, e)
	return nil
}

func (s *InMemoryStore) FindByAccount(_ context.Context, accountID string) ([]Entry, error) {
	var result []Entry
	for _, e := range s.entries {
		if e.AccountID == accountID {
			result = append(result, e)
		}
	}
	return result, nil
}

type LedgerService struct {
	writer EntryWriter
	reader EntryReader
}

func NewLedgerService(w EntryWriter, r EntryReader) *LedgerService {
	return &LedgerService{writer: w, reader: r}
}

func (s *LedgerService) PostEntry(ctx context.Context, e Entry) error {
	if e.AmountCents == 0 {
		return fmt.Errorf("amount cannot be zero")
	}
	return s.writer.Save(ctx, e)
}

func (s *LedgerService) GetHistory(ctx context.Context, accountID string) ([]Entry, error) {
	return s.reader.FindByAccount(ctx, accountID)
}

func main() {
	store := &InMemoryStore{} // implements both EntryWriter and EntryReader
	svc := NewLedgerService(store, store)

	ctx := context.Background()
	entries := []Entry{
		{ID: "e1", AccountID: "acct-001", AmountCents: 100000, Description: "salary"},
		{ID: "e2", AccountID: "acct-001", AmountCents: -5000,  Description: "coffee"},
		{ID: "e3", AccountID: "acct-002", AmountCents: 200000, Description: "bonus"},
	}
	for _, e := range entries {
		if err := svc.PostEntry(ctx, e); err != nil {
			fmt.Println("error:", err)
		}
	}

	history, err := svc.GetHistory(ctx, "acct-001")
	if err != nil {
		fmt.Println("error:", err)
		return
	}
	fmt.Printf("acct-001 has %d entries:\n", len(history))
	for _, e := range history {
		fmt.Printf("  %s: %+d cents\n", e.Description, e.AmountCents)
	}
	// acct-002 entries are invisible here — correct isolation
}
```

<Exercise n={4} title="Fix the dependency direction" level="medium">

The following code has a backwards dependency — the domain imports the DB package. Fix it so the dependency points inward, using an interface defined in the domain. You should be able to swap the DB implementation without touching `LedgerService`.

```go

	"context"
```

<Solution>

```go
// FIXED: domain defines the interface; the db package implements it.

// package domain — no db import
package domain

import (
	"context"
	"fmt"
)

type Entry struct {
	ID          string
	AccountID   string
	AmountCents int64
}

// EntryWriter is the PORT. Domain owns it. No import of the db package.
type EntryWriter interface {
	Save(ctx context.Context, entry Entry) error
}

// LedgerService depends on the interface (abstraction), not the concrete type.
type LedgerService struct {
	store EntryWriter
}

func NewLedgerService(store EntryWriter) *LedgerService {
	return &LedgerService{store: store}
}

func (s *LedgerService) PostEntry(ctx context.Context, e Entry) error {
	if e.AmountCents == 0 {
		return fmt.Errorf("amount cannot be zero")
	}
	return s.store.Save(ctx, e)
}

// ─────────────────────────────────────────────────────────────────────────
// package db  (separate package, imports domain)
package db

import (
	"context"
	"database/sql"
	"github.com/myapp/domain" // arrow now points INWARD
)

type PostgresStore struct{ db *sql.DB }

// PostgresStore implicitly satisfies domain.EntryWriter — no declaration needed.
func (s *PostgresStore) Save(ctx context.Context, e domain.Entry) error {
	_, err := s.db.ExecContext(ctx,
		"INSERT INTO entries(id, account_id, amount_cents) VALUES ($1, $2, $3)",
		e.ID, e.AccountID, e.AmountCents,
	)
	return err
}
```

The import graph is now: `db → domain`, never `domain → db`. The domain can be compiled, tested, and reasoned about without the `db` package existing at all.

<Exercise n={5} title="Wire the full composition root" level="hard">

Write a `main.go` that wires up the complete hexagonal service:

- A `LedgerService` with the domain's business rules

- Proper context propagation (`r.Context()` → domain → store)

```go
package main

import (
	"context"
	"encoding/json"
	"fmt"
	"log"
	"net/http"
)

// Domain types and port
type Entry struct {
	ID          string `json:"id"`
	AccountID   string `json:"account_id"`
	AmountCents int64  `json:"amount_cents"`
	Description string `json:"description"`
}

type EntryWriter interface {
	Save(ctx context.Context, e Entry) error
}

// Domain service
type LedgerService struct{ store EntryWriter }

func NewLedgerService(s EntryWriter) *LedgerService { return &LedgerService{store: s} }

func (s *LedgerService) PostEntry(ctx context.Context, e Entry) error {
	if e.AmountCents == 0 {
		return fmt.Errorf("amount_cents cannot be zero")
	}
	if e.AccountID == "" {
		return fmt.Errorf("account_id is required")
	}
	return s.store.Save(ctx, e)
}

// In-memory adapter
type InMemoryStore struct{ entries []Entry }

func (s *InMemoryStore) Save(_ context.Context, e Entry) error {
	s.entries = append(s.entries, e)
	log.Printf("stored entry id=%s account=%s amount=%d", e.ID, e.AccountID, e.AmountCents)
	return nil
}

// HTTP adapter — the only layer that knows about HTTP
type Handler struct{ svc *LedgerService }

func NewHandler(svc *LedgerService) *Handler { return &Handler{svc: svc} }

func (h *Handler) ServeHTTP(w http.ResponseWriter, r *http.Request) {
	if r.URL.Path != "/entries" || r.Method != http.MethodPost {
		http.NotFound(w, r)
		return
	}

	var e Entry
	if err := json.NewDecoder(r.Body).Decode(&e); err != nil {
		http.Error(w, "invalid JSON: "+err.Error(), http.StatusBadRequest)
		return
	}

	// Pass the request context — carries deadline and cancellation
	if err := h.svc.PostEntry(r.Context(), e); err != nil {
		// Domain errors → 400 Bad Request
		http.Error(w, err.Error(), http.StatusBadRequest)
		return
	}

	w.WriteHeader(http.StatusCreated)
	json.NewEncoder(w).Encode(map[string]string{"status": "ok", "id": e.ID})
}

// Composition root — the only place that knows all concrete types
func main() {
	store := &InMemoryStore{}
	svc := NewLedgerService(store)
	handler := NewHandler(svc)

	log.Println("ledger service listening on :8080")
	log.Fatal(http.ListenAndServe(":8080", handler))
}
```

<Recap>

You now have the architectural skeleton that every serious Go service is built on:

- **SOLID in Go**: SRP (one reason to change per type), OCP (extend via interfaces, not modification), LSP (the type system enforces this), ISP (small consumer-defined interfaces — Go's strongest SOLID card), DIP (domain defines ports; adapters implement them; the arrow always points inward).
- **Package design**: one clear purpose per package, no import cycles (the compiler enforces this), `internal/` for encapsulation, no stutter naming, no global `models/` dump.
- **Hexagonal/ports-and-adapters**: the domain is the inside; ports are interfaces the domain defines; adapters (HTTP, DB, gRPC) are on the outside, implementing those ports. Dependency arrows always point toward the domain.
- **Domain modeling**: entities have identity, value objects don't. Business rules live in the domain — never in handlers or SQL. Money is never a float (Part 3 goes much deeper).
- **Project layout**: `cmd/` + `internal/` is enough for most services. `pkg/` is cargo-cult. Merge similar packages, don't create packages for naming's sake.
- **Testability**: hexagonal architecture creates seams automatically. Fakes are cheap to write, fast to run, and more reliable than mocks for stable domain ports. Unit-test the domain with fakes; integration-test adapters with real infrastructure.

This architecture scales directly to microservices (Part 1, Chapter 21) — when the ledger service goes remote, you add a gRPC adapter implementing the same port. The domain doesn't notice.
