## SOLID in Go

<Define term="SOLID" since="Design Patterns, the Go Way (Part 1, Chapter 13)">
Five design principles (Single Responsibility, Open/Closed, Liskov Substitution, Interface Segregation, Dependency Inversion) that keep code changeable without cascading breakage. Go maps some beautifully (ISP, DIP) and ignores others (inheritance-based OCP). Use them as a **diagnostic**, not a religion: when a change breaks three things at once, ask which principle was violated.
</Define>

<Define term="Single Responsibility Principle (SRP)">
A type has **one reason to change** — not one method, one *reason*. `LedgerService` recording transactions is one responsibility. `LedgerService` also sending email is a second. When the email provider changes, the ledger logic shouldn't need a rewrite. If removing a feature requires touching the type, the type owns too many jobs.
</Define>

<Define term="Dependency Inversion Principle (DIP)">
High-level modules (domain business logic) must **not import** low-level modules (databases, HTTP clients). Both depend on an **abstraction** — an interface — that the high-level module defines. In Go: the domain package declares `type EntryWriter interface{...}`; the Postgres package implements it. The import arrow points *inward*, toward the domain, always.
</Define>

Let me set the scene with something real from Meridian. You're building a ledger service — the kind that records every financial transaction for a customer account. It starts simple: one file, one struct, everything in `main`. Then product adds reporting. Then compliance wants an audit trail. Then you need to swap SQLite for Postgres. Then a third service needs to call you over gRPC.

You're six months in and every change breaks three other things. That's not a Go problem. That's a design problem, and the five SOLID principles are the diagnostic tool you reach for first.

SOLID comes from object-oriented languages, so let's be upfront: **Go maps some of them beautifully and ignores others entirely**. I'll tell you which is which, because I don't teach from dogma — I teach from reality.

### Single Responsibility Principle

**One type, one reason to change.** Not "one function," not "one file" — one *reason to change*. This is the easiest principle to understand and the most violated one in every Go codebase I've ever had to rescue.

Here's the classic sin in our ledger service:

```go
// BAD: LedgerService does everything — it's three different jobs in a trench coat.
type LedgerService struct {
	db *sql.DB
}

// Records a transaction AND formats a PDF report AND sends email.
func (s *LedgerService) PostAndReport(entry Entry) error {
	// post to DB...
	// render PDF...
	// send email via SMTP...
	return nil
}
```

SRP in Go doesn't mean "one method per struct." It means asking: *if this requirement changes, which types have to change?* When the answer is more than one, you've violated SRP. Keep cutting.

### Open/Closed Principle

**Open for extension, closed for modification.** In class-based languages this means inheritance. In Go, it means **interfaces**. You write code that accepts a behavior via an interface, and new behaviors arrive by implementing that interface — you never touch the original.

```go
// The LedgerWriter interface is closed for modification — it never changes.
// Every new storage backend extends the system by implementing it.
type LedgerWriter interface {
	Save(ctx context.Context, entry Entry) error
}

// PostgresStore: implements LedgerWriter with Postgres.
type PostgresStore struct{ db *sql.DB }

func (s *PostgresStore) Save(ctx context.Context, e Entry) error { /* ... */ return nil }

// AuditStore: wraps any LedgerWriter to also write to an immutable audit log.
// Extension via composition — no modification of PostgresStore.
type AuditStore struct {
	inner LedgerWriter
	audit AuditLogger
}

func (a *AuditStore) Save(ctx context.Context, e Entry) error {
	if err := a.inner.Save(ctx, e); err != nil {
		return err
	}
	return a.audit.Log(ctx, e)
}
```

The `AuditStore` is the decorator pattern from the previous chapter applied as OCP. You composed your way to a new behavior, zero modifications to existing code.

### Liskov Substitution Principle

**Any value of an interface can replace any other.** In Go this is just the type system. If `PostgresStore` implements `LedgerWriter`, you can use it anywhere a `LedgerWriter` is expected. The compiler enforces this at compile time.

The Go-specific LSP trap: methods with **pointer receivers vs value receivers**. If your interface method set requires a pointer receiver, a value of that type won't satisfy the interface — the compiler will tell you, loudly. That's actually LSP being enforced for you.

<Callout kind="warn" title="LSP and nil interface gotcha">

LSP pairs with the infamous **typed nil trap**. A `*PostgresStore` that is `nil` satisfies the `LedgerWriter` interface — the interface value is non-nil. Then your code calls `.Save()` on it and panics. The rule: never return a concrete nil pointer through an interface. Return a plain `nil` error interface instead. This is covered in depth in the Error Handling chapter (Part 2, Chapter 2).

</Callout>

### Interface Segregation Principle

**This one is Go's strongest hand.** ISP says: don't force a client to depend on methods it doesn't use. In class-based languages, fat interfaces are a plague. In Go, **interfaces are defined by the consumer, not the implementor**, and they're so lightweight that a one-method interface is completely normal.

The Go proverb: **"The bigger the interface, the weaker the abstraction."** A one-method interface like `io.Reader` is the most powerful interface in the standard library precisely because it's so small that everything can satisfy it.

### Dependency Inversion Principle

**High-level modules should not depend on low-level modules. Both should depend on abstractions.** This is the one that matters most for architecture, and it's where most teams get it catastrophically wrong.

In our ledger service the wrong direction looks like this: the domain (business logic) imports the database package. Now the domain *depends on* a specific database. Swap Postgres for MySQL and you're refactoring the domain.

The right direction: **the domain defines an interface (the abstraction), and the database implements it.** The dependency arrow *inverts* — the DB package depends on the domain, not the other way around.

<UnderTheHood title="How Go interfaces work at the machine level">

A Go interface value is **two machine words**: a pointer to the *type descriptor* (the itable — interface table) and a pointer to the *data*. The itable for a concrete-type/interface pair caches the function pointers for each method; the compiler emits the ones it can see statically, and the runtime builds and caches any others on first use (interface-to-interface conversions, reflection) — never through an explicit registration call.

When the compiler sees `var w LedgerWriter = &PostgresStore{db}`, it:
1. Verifies at compile time that `*PostgresStore` has a `Save` method with the right signature — no itable needed yet.
2. At the assignment site, it generates a small itable for the `(*PostgresStore, LedgerWriter)` pair and sets the first word of the interface value to point to it.
3. The second word points to the `PostgresStore` value (or a copy of it, if non-pointer).

**Calling a method through an interface** is therefore a double-pointer dereference: load the itable pointer, load the function pointer at the right offset, call it. This is *slightly* more expensive than a direct call, but the compiler can devirtualize (inline the real function) when the concrete type is visible at the call site.

The important implication: **there is zero runtime registration**. A type satisfies an interface the instant it has the right methods. The itable is built by the compiler, not by some `Register()` call. This is why Go's implicit interface satisfaction is both fast and correct — it's all verified at compile time, and the performance cost is a single extra indirection when the concrete type can't be devirtualized.

*Note: itable generation and devirtualization behavior applies to the unified IR compiler pipeline (`cmd/compile`), current as of Go 1.26.*

</UnderTheHood>

## Domain-Driven Design in Go

<Define term="Domain Model" since="Representing Money & Domain Types (Part 3, Chapter 1)">
The **domain model** is the pure Go code that expresses business concepts and enforces invariants — completely decoupled from databases, HTTP routers, serialization tags, or third-party SDKs. It consists of Value Objects, Entities, Aggregates, Domain Events, and Domain Services. If your domain package imports `database/sql`, `github.com/gin-gonic/gin`, or `stripe-go`, it is not a domain model — it is a leaky script.
</Define>

<Define term="Value Object">
An immutable type defined entirely by its attributes rather than an identity token. Two value objects with identical fields are equal and interchangeable. In Go, Value Objects are modeled as structs with **unexported fields**, a **validating constructor**, **value receiver methods**, and **no setter methods**. Any operation that transforms a Value Object returns a brand-new instance.
</Define>

<Define term="Entity">
A domain object defined by its **thread of identity** that runs continuously through time and across multiple state transitions. Two accounts with identical owners, balances, and currencies are distinct if their `AccountID` values differ. Entities possess mutable state that can only be altered through domain methods that guard business invariants.
</Define>

<Define term="Aggregate & Aggregate Root">
A cluster of associated Entities and Value Objects that are treated as a single transactional consistency boundary. The **Aggregate Root** is the sole gateway entity through which external code may command mutations. Outside callers are strictly forbidden from modifying the internal entities directly. All operations within the boundary succeed or fail atomically.
</Define>

<Define term="Domain Event">
A record of an immutable domain fact that occurred in the past (e.g., `TransferInitiated`, `FundsLocked`, `AccountOverdrawn`). Domain events are captured inside Aggregate Roots during state transitions and published after the transaction commits, decoupling side effects (audit trails, push notifications, webhooks) from core domain invariants.
</Define>

In financial systems at Meridian, bugs aren't just stack traces — they are multi-million dollar regulatory fines, double-spend vulnerabilities, and irreversible ledger drift. Tactical Domain-Driven Design (DDD) provides the rigorous vocabulary and structural guardrails needed to make impossible states unrepresentable in Go.

Let's dissect how DDD concepts map cleanly and idiomatically into Go without Java-style ceremony.

### 1. Value Objects in Go

In Go, primitive obsession is the fastest route to bankruptcy. Passing raw `int64` or `string` values for money or account numbers allows an engineer to accidentally pass an `accountID` into a `cents` parameter or pass a negative number to a debit calculation.

A proper Go Value Object satisfies four rules:
1. **Unexported fields**: Prevents external code from mutating fields directly after instantiation.
2. **Validating constructor**: Guarantees that an invalid Value Object can never exist in memory.
3. **Value equality**: Comparable using Go's standard `==` operator or a dedicated `Equals()` method.
4. **Immutability with value semantics**: Methods use value receivers (`func (m Money) Add(...)`) and return new instances.

```go
package domain

import (
	"errors"
	"fmt"
)

// Money is an immutable Value Object.
// Fields are unexported to prevent illegal external mutations.
type Money struct {
	subunits int64  // amount in minor currency units (e.g. cents)
	currency string // ISO-4217 code (e.g. "USD", "EUR")
}

// NewMoney is the validating constructor. It is the ONLY way to create Money.
func NewMoney(subunits int64, currency string) (Money, error) {
	if subunits < 0 {
		return Money{}, errors.New("subunits cannot be negative for base money amount")
	}
	if len(currency) != 3 {
		return Money{}, fmt.Errorf("invalid ISO-4217 currency code: %s", currency)
	}
	return Money{
		subunits: subunits,
		currency: currency,
	}, nil
}

// Subunits returns the internal value. No setter is ever exposed.
func (m Money) Subunits() int64  { return m.subunits }
func (m Money) Currency() string { return m.currency }

// Add returns a NEW Money instance, preserving immutability.
func (m Money) Add(other Money) (Money, error) {
	if m.currency != other.currency {
		return Money{}, fmt.Errorf("currency mismatch: %s != %s", m.currency, other.currency)
	}
	return Money{
		subunits: m.subunits + other.subunits,
		currency: m.currency,
	}, nil
}

// Equals checks value equality.
func (m Money) Equals(other Money) bool {
	return m.subunits == other.subunits && m.currency == other.currency
}

func (m Money) String() string {
	return fmt.Sprintf("%s %.2f", m.currency, float64(m.subunits)/100.0)
}
```

### 2. Entities in Go

Unlike `Money`, an `Account` or `Transfer` is not defined by its values. If a customer changes their legal name, the account remains the exact same entity.

```go
package domain

import (
	"time"
)

// AccountID is a strongly-typed Value Object for entity identity.
type AccountID string

func (id AccountID) String() string { return string(id) }

// AccountStatus represents lifecycle stages.
type AccountStatus string

const (
	StatusActive    AccountStatus = "ACTIVE"
	StatusSuspended AccountStatus = "SUSPENDED"
	StatusClosed    AccountStatus = "CLOSED"
)
```

Entities have identity equality (`a.id == b.id`), track mutable state across their lifespan, and enforce business rules whenever their state changes.

### 3. Aggregates & Aggregate Roots

Here is where junior engineers fail: they treat every database table as an independent entity and let services update rows arbitrarily.

In Meridian's core banking engine, an `Account` is an **Aggregate Root**. An Account contains internal `Hold` records (temporary funds reservations for card authorizations) and `LedgerEntry` records. 

**The Golden Invariant Rule**: External callers (application services, HTTP handlers) are strictly forbidden from modifying `Hold` or `LedgerEntry` slices directly. They can only issue commands to the `Account` root:

```
┌─────────────────────────────────────────────────────────────┐
│                    ACCOUNT AGGREGATE                        │
│                                                             │
│  ┌───────────────────────────────────────────────────────┐  │
│  │ Account (Aggregate Root)                              │  │
│  │   - ID: AccountID                                     │  │
│  │   - AvailableBalance: Money                           │  │
│  │   - Status: AccountStatus                             │  │
│  │                                                       │  │
│  │   [Methods]:                                          │  │
│  │     + Debit(amount, reason)                           │  │
│  │     + PlaceHold(holdID, amount)                       │  │
│  │     + ReleaseHold(holdID)                             │  │
│  │     + CaptureHold(holdID)                             │  │
│  └───────────────┬───────────────────────┬───────────────┘  │
│                  │                       │                  │
│                  ▼                       ▼                  │
│       ┌─────────────────────┐ ┌──────────────────────┐      │
│       │ Holds ([]Hold)      │ │ Entries ([]Entry)    │      │
│       │ (Internal Entities) │ │ (Audit trail)        │      │
│       └─────────────────────┘ └──────────────────────┘      │
└─────────────────────────────────────────────────────────────┘
```

If a debit request arrives, the Aggregate Root calculates:
`Available Funds = Total Balance - Sum(Active Holds)`
If the invariant fails, the debit is rejected immediately in memory before any database lock or query executes.

Let's see this in a complete, runnable Go implementation:

```go
package main

import (
	"errors"
	"fmt"
	"time"
)

// ── VALUE OBJECT: Money ──────────────────────────────────
type Money struct {
	subunits int64
	currency string
}

func NewMoney(subunits int64, currency string) (Money, error) {
	if subunits < 0 {
		return Money{}, errors.New("subunits cannot be negative")
	}
	return Money{subunits: subunits, currency: currency}, nil
}

func (m Money) Subunits() int64  { return m.subunits }
func (m Money) Currency() string { return m.currency }

func (m Money) Add(other Money) (Money, error) {
	if m.currency != other.currency {
		return Money{}, fmt.Errorf("currency mismatch: %s != %s", m.currency, other.currency)
	}
	return Money{subunits: m.subunits + other.subunits, currency: m.currency}, nil
}

func (m Money) Sub(other Money) (Money, error) {
	if m.currency != other.currency {
		return Money{}, fmt.Errorf("currency mismatch: %s != %s", m.currency, other.currency)
	}
	if m.subunits < other.subunits {
		return Money{}, errors.New("insufficient funds for subtraction")
	}
	return Money{subunits: m.subunits - other.subunits, currency: m.currency}, nil
}

// ── DOMAIN EVENT ─────────────────────────────────────────
type DomainEvent interface {
	EventName() string
	OccurredAt() time.Time
}

type FundsHeldEvent struct {
	AccountID string
	HoldID    string
	Amount    Money
	Timestamp time.Time
}

func (e FundsHeldEvent) EventName() string      { return "account.funds_held" }
func (e FundsHeldEvent) OccurredAt() time.Time { return e.Timestamp }

// ── INTERNAL ENTITY: Hold ────────────────────────────────
type Hold struct {
	ID        string
	Amount    Money
	Active    bool
	CreatedAt time.Time
}

// ── AGGREGATE ROOT: Account ──────────────────────────────
type Account struct {
	id             string
	balance        Money
	holds          map[string]Hold
	uncommittedEvs []DomainEvent
}

func NewAccount(id string, initialBalance Money) *Account {
	return &Account{
		id:      id,
		balance: initialBalance,
		holds:   make(map[string]Hold),
	}
}

// AvailableBalance calculates balance minus active holds.
func (a *Account) AvailableBalance() Money {
	heldSubunits := int64(0)
	for _, h := range a.holds {
		if h.Active {
			heldSubunits += h.Amount.Subunits()
		}
	}
	return Money{
		subunits: a.balance.Subunits() - heldSubunits,
		currency: a.balance.Currency(),
	}
}

// PlaceHold enforces the business invariant: cannot hold more than available.
func (a *Account) PlaceHold(holdID string, amount Money) error {
	if amount.Currency() != a.balance.Currency() {
		return fmt.Errorf("hold currency %s does not match account %s", amount.Currency(), a.balance.Currency())
	}
	avail := a.AvailableBalance()
	if avail.Subunits() < amount.Subunits() {
		return fmt.Errorf("cannot hold %d cents: only %d cents available", amount.Subunits(), avail.Subunits())
	}

	a.holds[holdID] = Hold{
		ID:        holdID,
		Amount:    amount,
		Active:    true,
		CreatedAt: time.Now(),
	}

	// Record domain event
	a.uncommittedEvs = append(a.uncommittedEvs, FundsHeldEvent{
		AccountID: a.id,
		HoldID:    holdID,
		Amount:    amount,
		Timestamp: time.Now(),
	})

	return nil
}

// PopEvents drains uncommitted domain events after persistence.
func (a *Account) PopEvents() []DomainEvent {
	events := a.uncommittedEvs
	a.uncommittedEvs = nil
	return events
}

func main() {
	usd100, _ := NewMoney(10000, "USD") // $100.00
	acct := NewAccount("acct-meridian-99", usd100)

	fmt.Printf("Initial Available: %d cents\n", acct.AvailableBalance().Subunits())

	// Authorize a $40 card swipe
	hold40, _ := NewMoney(4000, "USD")
	err := acct.PlaceHold("hold-001", hold40)
	fmt.Println("Place $40 hold:", err)
	fmt.Printf("Remaining Available: %d cents\n", acct.AvailableBalance().Subunits())

	// Attempt an unauthorized $70 charge (40 + 70 = 110 > 100)
	hold70, _ := NewMoney(7000, "USD")
	err = acct.PlaceHold("hold-002", hold70)
	fmt.Println("Place $70 hold (expected rejection):", err)

	// Check domain events
	events := acct.PopEvents()
	fmt.Printf("Recorded %d uncommitted domain event(s):\n", len(events))
	for _, e := range events {
		fmt.Printf(" - Event [%s] at %s\n", e.EventName(), e.OccurredAt().Format("15:04:05"))
	}
}
```

### 4. Domain Events: Decoupling Side Effects

Notice how the `Account` aggregate recorded `FundsHeldEvent` without knowing anything about Kafka, Amazon SNS, or Postgres outbox tables.

When an aggregate mutates:
1. It records domain events in an unexported slice (`uncommittedEvs`).
2. The Application Service saves the aggregate and its events to the database inside a single atomic transaction.
3. The events are published to an event bus or background workers after the database transaction commits.

This guarantees that if the transaction aborts, no ghost events are published, and your compliance and notification services remain 100% consistent with the ledger.

### 5. Domain Services vs. Application Services

One of the biggest confusions in Go software design is knowing where logic belongs.

<ConceptGrid cols={2}>
  <ConceptCard label="Domain Service (Pure Logic)">
    - **Pure business calculation** across multiple aggregates.
    - **Zero I/O**: No database calls, no HTTP clients, no context timeouts.
    - Example: `FeeCalculationService` determining foreign exchange margins and compliance tiers between two accounts.
  </ConceptCard>
  <ConceptCard label="Application Service (Use Case / Orchestrator)">
    - **Workflow Coordinator**: Controls the execution flow.
    - **Performs I/O**: Loads aggregates from repository ports, begins transactions, commits Units of Work, publishes domain events.
    - Example: `TransferMoneyUseCase` coordinating debit, credit, fee, and audit steps.
  </ConceptCard>
  <Gotcha>Never let a Domain Service import a database driver or perform network requests. If it performs I/O, it is an Application Service or an Adapter.</Gotcha>
</ConceptGrid>

```go
// DOMAIN SERVICE: Pure business rule spanning two accounts.
// Notice: Zero I/O, zero network, zero SQL. Pure math and domain logic.
type FXSettlementDomainService struct{}

func (s *FXSettlementDomainService) CalculateExchange(
	sourceBal Money, 
	targetCurrency string, 
	rate float64,
) (converted Money, fee Money, err error) {
	if rate <= 0 {
		return Money{}, Money{}, errors.New("exchange rate must be positive")
	}
	rawSubunits := float64(sourceBal.Subunits()) * rate
	feeSubunits := int64(float64(sourceBal.Subunits()) * 0.01) // 1% platform fee

	converted, err = NewMoney(int64(rawSubunits)-feeSubunits, targetCurrency)
	if err != nil {
		return Money{}, Money{}, err
	}
	fee, err = NewMoney(feeSubunits, sourceBal.Currency())
	return converted, fee, err
}
```

## Package by Feature vs. Package by Layer

<Define term="Package by Layer">
Organizing Go code horizontally by technical role: `controllers/`, `services/`, `repositories/`, `models/`. In Go, this creates horizontal coupling, forces almost all types and functions to be exported, encourages circular dependencies, and concentrates disparate domain models into an unmaintainable `models/` dumping ground.
</Define>

<Define term="Package by Feature">
Organizing Go code vertically by cohesive business capability: `accounts/`, `transfers/`, `settlement/`, `compliance/`. Each package owns its domain models, repository interfaces, SQL implementations, and transport adapters. Implementation details remain unexported (`private`), and cross-feature interaction happens via explicit interfaces or domain events.
</Define>

If you come from Ruby on Rails, Django, or Spring Boot, your default instinct is to create a folder for every architectural layer. In Go, **Package by Layer is an anti-pattern**.

Let's look at why layering fails in Go, and how packaging by feature gives you modular, scalable code.

### The Layered Trap

```
# BAD: Package by Layer (Horizontal Slicing)
meridian/
├── controllers/
│   ├── account_handler.go
│   └── transfer_handler.go
├── services/
│   ├── account_service.go
│   └── transfer_service.go
├── repositories/
│   ├── account_repo.go
│   └── transfer_repo.go
└── models/               ← THE DUMPSTER: Every struct in the company lives here
    ├── account.go
    ├── transfer.go
    └── user.go
```

Why does this fall apart?
1. **Low Cohesion**: To understand or modify the "Transfer" feature, you must open files in four different packages.
2. **Loss of Encapsulation**: Because `repositories` needs to return `models.Account`, and `controllers` needs to accept `models.Account`, every single field on `Account` must be exported (`Public`). Any developer in any package can mutate `account.Balance = -999999` with zero compiler resistance.
3. **Import Cycle Hell**: The moment `services.AccountService` needs `services.TransferService`, and `services.TransferService` needs `services.AccountService`, the Go compiler aborts with an import cycle error.

### The Feature-Driven Architecture

```
# GOOD: Package by Feature (Vertical Slicing)
meridian/
├── internal/
│   ├── accounts/         ← Cohesive feature package
│   │   ├── account.go    ← Domain aggregate (unexported fields!)
│   │   ├── handler.go    ← HTTP transport adapter
│   │   ├── postgres.go   ← Database persistence
│   │   ├── service.go    ← Application use cases
│   │   └── testing.go    ← In-memory fakes for other packages
│   ├── transfers/        ← Cohesive feature package
│   │   ├── transfer.go   ← Domain logic
│   │   ├── service.go    ← Use case
│   │   └── postgres.go   ← Storage
│   ├── compliance/       ← Cohesive feature package
│   │   └── aml_check.go
│   └── platform/         ← Shared infrastructure only
│       ├── database/     ← Connection pooling, migrations
│       └── money/        ← Universal Money Value Object
└── cmd/
    └── meridian-api/
        └── main.go       ← Composition root
```

### Eliminating Circular Dependencies Between Features

What happens when `transfers` needs to debit an `account` from the `accounts` package?

If `transfers` imports `accounts`, and `accounts` imports `transfers`, the compiler rejects the build. There are three idiomatic ways to resolve this:

1. **Consumer-Defined Interface**: `transfers` declares an interface describing only what it needs:
   ```go
   package transfers

   type AccountDebitor interface {
       DebitAccount(ctx context.Context, accountID string, cents int64) error
   }
   ```
2. **Shared Domain Kernel / Value Objects**: Move universal primitive Value Objects (like `Money` or `Currency`) to `internal/platform/money`. Both `accounts` and `transfers` import `money`, but neither imports each other.
3. **Event-Driven Decoupling**: When a transfer completes, `transfers` publishes a `TransferCompletedEvent`. The `compliance` or `notifications` package listens to this event on an in-memory or Kafka bus. Zero direct package imports!

### The Four Quadrants of Ports & Adapters

Let's nail down the formal terminology once and for all:

1. **Inbound Ports (Driving / Primary Ports)**:
   - Interfaces that define the use cases exposed by the application.
   - Example: `TransferUseCase`, `AccountQuerier`.
   - The application service implements these interfaces.
2. **Outbound Ports (Driven / Secondary Ports)**:
   - Interfaces that define what the domain needs from the outside world.
   - Example: `AccountRepository`, `PaymentGateway`, `EventPublisher`.
   - The domain declares these interfaces; external adapters implement them.
3. **Primary Adapters (Driving Adapters)**:
   - Entry points that trigger business workflows from external actors.
   - Example: HTTP REST handlers, gRPC services, CLI commands, Kafka message consumers.
   - They parse requests, map DTOs into domain commands, and call Inbound Ports.
4. **Secondary Adapters (Driven Adapters)**:
   - Infrastructure implementations that satisfy Outbound Ports.
   - Example: `PostgresAccountRepository`, `StripePaymentGateway`, `KafkaEventPublisher`.

```go
	if !ok {

	return &copy, nil
```

## Unit of Work Pattern in Go

<Define term="Unit of Work">
A design pattern that maintains a list of database operations affected by a business transaction and coordinates the writing out of changes and the resolution of concurrency problems. In Go, the Unit of Work pattern allows multiple distinct repositories to execute within a single atomic database transaction (`BEGIN ... COMMIT / ROLLBACK`) without leaking `*sql.Tx` or SQL drivers into the domain layer.
</Define>

In a fintech system, multi-repository operations are everywhere. Consider a funds transfer between two customers at Meridian:
1. `AccountRepository.Save(source)` (Debit)
2. `AccountRepository.Save(target)` (Credit)
3. `LedgerRepository.RecordEntries(entries)` (Double-entry audit records)
4. `OutboxRepository.QueueEvent(event)` (Transactional outbox for Kafka)

If step 2 fails due to a constraint violation and each repository uses its own `*sql.DB` connection, step 1 has already committed! Money has vanished from the source account without reaching the target.

### The Anti-Pattern: Leaking `*sql.Tx`

Amateur Go developers try to solve this by passing `*sql.Tx` across their interfaces:

```go
// BAD: Domain interfaces now depend directly on database/sql!
type AccountRepository interface {
    SaveWithTx(ctx context.Context, tx *sql.Tx, acct *Account) error
}
```

This destroys Hexagonal Architecture. The domain now knows that Postgres exists. You can no longer write in-memory fakes for unit testing without mocking low-level SQL transaction handles.

### The Idiomatic Go Solution: Closure-Based Unit of Work

The clean way to handle transactions in Go is a closure-based **Unit of Work** that provides a transaction-scoped **Repository Registry**:

```go
// Outbound Port: UnitOfWork
type UnitOfWork interface {
	Do(ctx context.Context, fn func(txRepo Registry) error) error
}

// Registry provides access to all repositories running inside the active transaction.
type Registry interface {
	Accounts() AccountRepository
	Ledger() LedgerRepository
	Outbox() OutboxRepository
}
```

Let's see this pattern in action with full rollback protection:

<GoPlayground>

```go
package main

import (
	"context"
	"errors"
	"fmt"
)

// ── DOMAIN ───────────────────────────────────────────────
type Account struct {
	ID      string
	Balance int64
}

type LedgerEntry struct {
	AccountID string
	Amount    int64
	Type      string
}

// ── OUTBOUND PORTS ───────────────────────────────────────
type AccountRepository interface {
	Get(ctx context.Context, id string) (*Account, error)
	Update(ctx context.Context, acct *Account) error
}

type LedgerRepository interface {
	Record(ctx context.Context, entry LedgerEntry) error
}

type RepositoryRegistry interface {
	Accounts() AccountRepository
	Ledger() LedgerRepository
}

type UnitOfWork interface {
	Do(ctx context.Context, fn func(r RepositoryRegistry) error) error
}

// ── APPLICATION SERVICE ──────────────────────────────────
type TransferService struct {
	uow UnitOfWork // Depends on UoW port
}

func NewTransferService(uow UnitOfWork) *TransferService {
	return &TransferService{uow: uow}
}

func (s *TransferService) Transfer(ctx context.Context, fromID, toID string, cents int64) error {
	// Execute all repository operations inside an atomic Unit of Work
	return s.uow.Do(ctx, func(r RepositoryRegistry) error {
		source, err := r.Accounts().Get(ctx, fromID)
		if err != nil {
			return err
		}
		target, err := r.Accounts().Get(ctx, toID)
		if err != nil {
			return err
		}

		if source.Balance < cents {
			return fmt.Errorf("insufficient funds: balance %d < %d", source.Balance, cents)
		}

		source.Balance -= cents
		target.Balance += cents

		if err := r.Accounts().Update(ctx, source); err != nil {
			return err
		}
		if err := r.Accounts().Update(ctx, target); err != nil {
			return err
		}

		// Record double-entry ledger records
		_ = r.Ledger().Record(ctx, LedgerEntry{AccountID: fromID, Amount: -cents, Type: "DEBIT"})
		_ = r.Ledger().Record(ctx, LedgerEntry{AccountID: toID, Amount: cents, Type: "CREDIT"})

		return nil
	})
}

// ── SECONDARY ADAPTER: In-Memory Unit of Work with Rollback ──
type InMemoryUoW struct {
	accounts map[string]Account
	ledger   []LedgerEntry
}

func NewInMemoryUoW() *InMemoryUoW {
	return &InMemoryUoW{
		accounts: make(map[string]Account),
		ledger:   make([]LedgerEntry),
	}
}

type memoryRegistry struct {
	uow *InMemoryUoW
	// Transaction-local staging buffers
	stagedAccounts map[string]Account
	stagedLedger   []LedgerEntry
}

func (reg *memoryRegistry) Accounts() AccountRepository {
	return &memAccountRepo{reg: reg}
}

func (reg *memoryRegistry) Ledger() LedgerRepository {
	return &memLedgerRepo{reg: reg}
}

type memAccountRepo struct{ reg *memoryRegistry }

func (r *memAccountRepo) Get(_ context.Context, id string) (*Account, error) {
	if a, ok := r.reg.stagedAccounts[id]; ok {
		copy := a
		return &copy, nil
	}
	if a, ok := r.reg.uow.accounts[id]; ok {
		copy := a
		return &copy, nil
	}
	return nil, errors.New("account not found")
}

func (r *memAccountRepo) Update(_ context.Context, acct *Account) error {
	r.reg.stagedAccounts[acct.ID] = *acct
	return nil
}

type memLedgerRepo struct{ reg *memoryRegistry }

func (r *memLedgerRepo) Record(_ context.Context, entry LedgerEntry) error {
	r.reg.stagedLedger = append(r.reg.stagedLedger, entry)
	return nil
}

func (u *InMemoryUoW) Do(_ context.Context, fn func(r RepositoryRegistry) error) error {
	// 1. Begin simulated transaction (create staging area)
	reg := &memoryRegistry{
		uow:            u,
		stagedAccounts: make(map[string]Account),
		stagedLedger:   make([]LedgerEntry, 0),
	}

	// 2. Execute business operations
	err := fn(reg)
	if err != nil {
		// ROLLBACK: discard staging buffers
		fmt.Println("[UoW] Transaction aborted -> Rollback executed! Staged changes discarded.")
		return err
	}

	// 3. COMMIT: apply staged changes atomically to root state
	for k, v := range reg.stagedAccounts {
		u.accounts[k] = v
	}
	u.ledger = append(u.ledger, reg.stagedLedger...)
	fmt.Println("[UoW] Transaction committed successfully!")
	return nil
}

func main() {
	uow := NewInMemoryUoW()
	uow.accounts["alice"] = Account{ID: "alice", Balance: 5000} // $50.00
	uow.accounts["bob"] = Account{ID: "bob", Balance: 1000}     // $10.00

	svc := NewTransferService(uow)

	ctx := context.Background()

	// 1. Successful transfer ($20 from Alice to Bob)
	fmt.Println("--- Test 1: Valid Transfer $20 ---")
	_ = svc.Transfer(ctx, "alice", "bob", 2000)
	fmt.Printf("Alice Balance: %d, Bob Balance: %d, Ledger entries: %d\n",
		uow.accounts["alice"].Balance, uow.accounts["bob"].Balance, len(uow.ledger))

	// 2. Failed transfer ($100 from Alice -> exceeds balance)
	fmt.Println("\n--- Test 2: Overdraft Transfer $100 ---")
	err := svc.Transfer(ctx, "alice", "bob", 10000)
	fmt.Println("Error:", err)
	fmt.Printf("Alice Balance: %d, Bob Balance: %d (Unchanged!), Ledger entries: %d\n",
		uow.accounts["alice"].Balance, uow.accounts["bob"].Balance, len(uow.ledger))
}
```

## Dependency Injection & Wiring

<Define term="Composition Root">
The unique, centralized location in an application where the dependency graph is assembled. In Go, the composition root is `main.go` inside the `cmd/` directory. It is the **only** package in the entire application that is permitted to know about concrete adapter types (`*sql.DB`, `PostgresAccountRepo`, `StripeClient`).
</Define>

Dependency Injection (DI) simply means passing dependencies into structs via constructors (`NewService(repo)`) rather than having the struct create or fetch its dependencies internally.

In the Go ecosystem, there are three primary approaches to dependency injection:
1. **Manual Constructor Wiring** (The Idiomatic Standard)
2. **Compile-Time Code Generation** (`google/wire`)
3. **Runtime Reflection Containers** (`uber-go/fx`, `uber-go/dig`)

Let's evaluate them objectively.

### 1. Manual Composition Root (Idiomatic Go)

In 95% of Go production systems, plain Go constructor calls in `main.go` are vastly superior to any framework:

```go
// cmd/meridian-api/main.go
func main() {
	ctx := context.Background()

	// 1. Infrastructure
	db, err := sql.Open("pgx", os.Getenv("DATABASE_URL"))
	if err != nil {
		log.Fatalf("db connection failed: %v", err)
	}

	// 2. Driven Adapters (Outbound)
	accountRepo := postgres.NewAccountRepo(db)
	auditLogger := cloudwatch.NewAuditLogger()
	stripeGateway := stripe.NewClient(os.Getenv("STRIPE_KEY"))

	// 3. Domain / Application Services (Inbound)
	transferService := transfers.NewService(accountRepo, auditLogger, stripeGateway)

	// 4. Driving Adapters (Inbound)
	httpHandler := httpapi.NewTransferHandler(transferService)

	// 5. Server Startup
	server := &http.Server{
		Addr:    ":8080",
		Handler: httpHandler,
	}
	log.Fatal(server.ListenAndServe())
}
```

**Why Manual Wiring Wins in Go:**
- **Instant Compile Errors**: If a constructor changes or a dependency is missing, the compiler stops you at build time with an exact line number.
- **Traceability**: You can command-click / F12 jump directly from a handler to its underlying service and repository.
- **Zero Reflection Overhead**: No reflection, no startup lag, no dynamic type assertions.

### 2. Google Wire: Compile-Time Code Generation

When dependency graphs grow to hundreds of services, writing manual constructors can become tedious. Google created **Wire** (`github.com/google/wire`) to automate wiring **at compile time**.

Unlike Java Spring or reflection tools, Wire is a code generator. You define provider sets in a `wire.go` file:

```go
//+build wireinject

package main

import (
	"github.com/google/wire"
	"meridian/internal/accounts"
	"meridian/internal/postgres"
)

func InitializeTransferService(db *sql.DB) *transfers.Service {
	wire.Build(
		postgres.NewAccountRepo,
		wire.Bind(new(transfers.AccountRepository), new(*postgres.AccountRepo)),
		transfers.NewService,
	)
	return nil
}
```

Running `wire` generates a plain Go file (`wire_gen.go`) containing the exact constructor calls you would have written by hand. If a dependency is missing or cyclic, `wire` fails during `go generate` — never in production.

### 3. Why Reflection Containers (Uber Fx / Dig) are Anti-Patterns

Reflection-based containers like `uber-go/fx` resolve dependencies dynamically at runtime using `reflect.TypeOf`.

## Project Layout in Production

Now let's bring everything together into a production-grade directory layout for a scalable Meridian service.

### Demystifying the `pkg/` Myth

The widely circulated `golang-standards/project-layout` repository lists a `pkg/` directory. **The Go core team does not endorse this.** In Go, package visibility is governed by two simple rules:
1. Code inside `internal/` can **only** be imported by packages in the same module.
2. Code outside `internal/` can be imported by any external module.

You do not need a folder named `pkg/` to make packages public.

### The Production Blueprint

```
│   └── ledger-api/
```

### Eliminating the `utils/` and `models/` Dumping Grounds

When engineers don't know where to put a function, they create `utils/` or `helpers/`. When they don't know where to put a struct, they put it in `models/`.

These are symptoms of structural decay:
- Instead of `utils.FormatDate(t)`, place formatting methods in domain Value Objects: `period.Format()`.
- Instead of `models.User`, place the entity inside `internal/users/user.go`.
- If a package name is an adjective or generic noun (`common`, `helpers`, `data`), delete it and redistribute its types to cohesive domain feature packages.

## Designing for Testability

The ultimate payoff of SOLID, DDD, and Hexagonal Architecture is **frictionless testability**.

When your domain relies on Outbound Ports (interfaces) and receives dependencies via constructor injection, you can test complex business logic in sub-millisecond in-memory unit tests.

### Seams via Interfaces

A **seam** is a boundary where behavior can be substituted without modifying production source code. Every Outbound Port in your domain is a test seam:

```go
// Domain Port
type LedgerWriter interface {
	Save(ctx context.Context, e Entry) error
}

// In Tests: Inject FakeLedgerWriter
// In Production: Inject PostgresLedgerWriter
```

### Hand-Written Fakes vs. Mock Frameworks

While libraries like `gomock` or `testify/mock` generate mocks that record call counts and parameters, **hand-written in-memory fakes** are almost always superior for domain testing:

<ConceptGrid cols={2}>
  <ConceptCard label="Hand-Written Fakes (Preferred)">
    - Real in-memory state (slices, maps).
    - Can enforce domain invariants in test harnesses.
    - Does not break when internal method calling orders change during refactoring.
    - Zero code generation required.
  </ConceptCard>
  <ConceptCard label="Generated Mocks (Use Sparingly)">
    - Rigidly records expected call counts (`.Expect().Times(1)`).
    - Couples tests to implementation mechanics rather than business outcomes.
    - Breaks frequently during benign refactoring.
  </ConceptCard>
  <Gotcha>Use Fakes for domain repositories and use cases. Reserve Mocks only for third-party HTTP/gRPC clients (e.g. testing network timeout error handling when calling Stripe).</Gotcha>
</ConceptGrid>

```go
import (
	"errors"
	"fmt"
	"strings"
)

type Currency struct {
	code string
}

func NewCurrency(code string) (Currency, error) {
	code = strings.ToUpper(strings.TrimSpace(code))
	if len(code) != 3 {
		return Currency{}, fmt.Errorf("invalid ISO currency code: %s", code)
	}
	return Currency{code: code}, nil
}

func (c Currency) Code() string { return c.code }

type Account struct {
	id          string
	balanceCent int64
	currency    Currency
}

func NewAccount(id string, initialBalance int64, currency Currency) (*Account, error) {
	if id == "" {
		return nil, errors.New("account ID cannot be empty")
	}
	if initialBalance < 0 {
		return nil, errors.New("initial balance cannot be negative")
	}
	return &Account{
		id:          id,
		balanceCent: initialBalance,
		currency:    currency,
	}, nil
}

func (a *Account) ID() string          { return a.id }
func (a *Account) BalanceCents() int64 { return a.balanceCent }
func (a *Account) Currency() Currency  { return a.currency }

func (a *Account) Debit(cents int64) error {
	if cents <= 0 {
		return errors.New("debit amount must be positive")
	}
	if a.balanceCent < cents {
		return fmt.Errorf("insufficient funds: available %d, requested %d", a.balanceCent, cents)
	}
	a.balanceCent -= cents
	return nil
}
```

```go
	Save(ctx context.Context, entry Entry) error

type InMemoryStore struct {
	entries []Entry

func (s *InMemoryStore) Save(_ context.Context, e Entry) error {

	return nil

	var result []Entry
	for _, e := range s.entries {
		if e.AccountID == accountID {
			result = append(result, e)
		}
	}
	return result, nil
}

	writer EntryWriter
	reader EntryReader

	return &LedgerService{writer: w, reader: r}

	if e.AmountCents == 0 {
		return fmt.Errorf("amount cannot be zero")
	}
	return s.writer.Save(ctx, e)
}

func (s *LedgerService) GetHistory(ctx context.Context, accountID string) ([]Entry, error) {
	return s.reader.FindByAccount(ctx, accountID)
}
```

<Exercise n={5} title="Implement a Closure-Based Unit of Work" level="hard">

Implement a thread-safe in-memory `UnitOfWork` runner in Go that coordinates atomic operations across two repository interfaces (`AccountRepo` and `AuditRepo`). If the closure returns an error, any staged changes must not be applied to the primary store.

<Solution>

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"sync"
)

type Account struct {
	ID      string
	Balance int64
}

type AccountRepo interface {
	Get(id string) (*Account, error)
	Set(a Account)
}

type AuditRepo interface {
	Log(msg string)
}

type Registry interface {
	Accounts() AccountRepo
	Audit() AuditRepo
}

type MemoryUoW struct {
	mu       sync.Mutex
	accounts map[string]Account
	logs     []string
}

func NewMemoryUoW() *MemoryUoW {
	return &MemoryUoW{
		accounts: make(map[string]Account),
		logs:     make([]string, 0),
	}
}

type txRegistry struct {
	uow            *MemoryUoW
	stagedAccounts map[string]Account
	stagedLogs     []string
}

func (r *txRegistry) Accounts() AccountRepo { return &txAccountRepo{reg: r} }
func (r *txAuditRepo) Log(msg string)       { r.reg.stagedLogs = append(r.reg.stagedLogs, msg) }

type txAccountRepo struct{ reg *txRegistry }

func (r *txAccountRepo) Get(id string) (*Account, error) {
	if a, ok := r.reg.stagedAccounts[id]; ok {
		copy := a
		return &copy, nil
	}
	if a, ok := r.reg.uow.accounts[id]; ok {
		copy := a
		return &copy, nil
	}
	return nil, errors.New("not found")
}

func (r *txAccountRepo) Set(a Account) {
	r.reg.stagedAccounts[a.ID] = a
}

type txAuditRepo struct{ reg *txRegistry }

func (r *txRegistry) Audit() AuditRepo { return &txAuditRepo{reg: r} }

func (u *MemoryUoW) Do(_ context.Context, fn func(r Registry) error) error {
	u.mu.Lock()
	defer u.mu.Unlock()

	reg := &txRegistry{
		uow:            u,
		stagedAccounts: make(map[string]Account),
		stagedLogs:     make([]string, 0),
	}

	if err := fn(reg); err != nil {
		// Rollback staged changes
		return err
	}

	// Commit staged changes
	for k, v := range reg.stagedAccounts {
		u.accounts[k] = v
	}
	u.logs = append(u.logs, reg.stagedLogs...)
	return nil
}

func main() {
	uow := NewMemoryUoW()
	uow.accounts["acct-1"] = Account{ID: "acct-1", Balance: 500}

	// Successful Tx
	_ = uow.Do(context.Background(), func(r Registry) error {
		a, _ := r.Accounts().Get("acct-1")
		a.Balance += 500
		r.Accounts().Set(*a)
		r.Audit().Log("added 500")
		return nil
	})
	fmt.Println("Committed Balance:", uow.accounts["acct-1"].Balance) // 1000

	// Failed Tx (Rollback)
	_ = uow.Do(context.Background(), func(r Registry) error {
		a, _ := r.Accounts().Get("acct-1")
		a.Balance += 10000
		r.Accounts().Set(*a)
		return errors.New("something went wrong")
	})
	fmt.Println("Balance After Rollback:", uow.accounts["acct-1"].Balance) // 1000
}
```

<Exercise n={6} title="Wire the Full Composition Root" level="hard">

Write a complete `main.go` that wires a Hexagonal architecture service:
- HTTP handler at `POST /entries` decoding JSON into domain `Entry`
- `LedgerService` enforcing domain business rules
- In-memory store adapter
- Context propagation (`r.Context()` -> domain -> store)
- HTTP status codes: `201 Created` on success, `400 Bad Request` on domain validation failure

<Solution>

```go
package main

import (
	"context"
	"encoding/json"
	"fmt"
	"log"
	"net/http"
)

type Entry struct {
	ID          string `json:"id"`
	AccountID   string `json:"account_id"`
	AmountCents int64  `json:"amount_cents"`
	Description string `json:"description"`
}

type EntryWriter interface {
	Save(ctx context.Context, e Entry) error
}

type LedgerService struct{ store EntryWriter }

func NewLedgerService(s EntryWriter) *LedgerService { return &LedgerService{store: s} }

func (s *LedgerService) PostEntry(ctx context.Context, e Entry) error {
	if e.AmountCents == 0 {
		return fmt.Errorf("amount_cents cannot be zero")
	}
	if e.AccountID == "" {
		return fmt.Errorf("account_id is required")
	}
	return s.store.Save(ctx, e)
}

type InMemoryStore struct{ entries []Entry }

func (s *InMemoryStore) Save(_ context.Context, e Entry) error {
	s.entries = append(s.entries, e)
	log.Printf("stored entry id=%s account=%s amount=%d", e.ID, e.AccountID, e.AmountCents)
	return nil
}

type Handler struct{ svc *LedgerService }

func NewHandler(svc *LedgerService) *Handler { return &Handler{svc: svc} }

func (h *Handler) ServeHTTP(w http.ResponseWriter, r *http.Request) {
	if r.URL.Path != "/entries" || r.Method != http.MethodPost {
		http.NotFound(w, r)
		return
	}

	var e Entry
	if err := json.NewDecoder(r.Body).Decode(&e); err != nil {
		http.Error(w, "invalid JSON: "+err.Error(), http.StatusBadRequest)
		return
	}

	if err := h.svc.PostEntry(r.Context(), e); err != nil {
		http.Error(w, err.Error(), http.StatusBadRequest)
		return
	}

	w.WriteHeader(http.StatusCreated)
	json.NewEncoder(w).Encode(map[string]string{"status": "ok", "id": e.ID})
}

func main() {
	store := &InMemoryStore{}
	svc := NewLedgerService(store)
	handler := NewHandler(svc)

	log.Println("ledger service listening on :8080")
	log.Fatal(http.ListenAndServe(":8080", handler))
}
```

<Recap>

You now have the complete architectural foundation that powers enterprise Go engineering:

- **SOLID in Go**: SRP (one reason to change), OCP (extend via interfaces), LSP (structural substitution), ISP (small consumer-defined interfaces), DIP (domain defines ports, adapters implement them).
- **Domain-Driven Design**: Value Objects (immutable, unexported fields, validating constructors), Entities (identity across time), Aggregates & Roots (transactional consistency boundaries protecting invariants), Domain Events (decoupling side effects), Domain Services (pure multi-aggregate calculations) vs Application Services (use case orchestration).
- **Package by Feature**: Vertical slicing beats horizontal layering. High cohesion, strong encapsulation of unexported structs, and zero circular import cycles.
- **Hexagonal Architecture**: Inbound Ports (use cases), Outbound Ports (repositories/gateways), Primary Adapters (HTTP/gRPC/Kafka consumers), Secondary Adapters (Postgres/Stripe). Dependencies point strictly inward.
- **Unit of Work**: Coordinate multi-repository transactions atomically via closures and repository registries without leaking `*sql.Tx` into domain packages.
- **Dependency Injection**: Explicit manual composition root in `cmd/.../main.go` and compile-time code generation (Google Wire) beat magic runtime reflection containers (`uber-go/fx`).
- **Testability**: Interfaces create seams. Hand-written fakes provide ultra-fast (&lt;1ms) in-memory domain unit tests; testcontainers verify real SQL adapters.
