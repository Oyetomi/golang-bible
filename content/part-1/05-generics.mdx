## Reading the Syntax

Here's the scenario that makes generics feel necessary instead of academic.

You're building a payments platform. You have `[]Transaction`, `[]Account`, and `[]AuditEntry` — all slices of different types — and you keep writing the same `Map`, `Filter`, and `Reduce` functions for each. Three times. With copy-paste drift. When a bug appears in one, you hunt the other two.

Before generics, your options were: copy-paste (criminal), an interface (loses type information), or reflection (slow and unreadable). After generics, you write the function once and the compiler enforces type-safety at every call site.

<Define term="Type parameter" since="this chapter">
A **type parameter** is a compile-time placeholder for a concrete type, written in square brackets after a function or type name — e.g. `[T any]`. The caller fills it in (either explicitly or by inference) and the compiler generates type-safe code for that specific type. Without type parameters you need one copy of the function per type; with them, you write it once.
</Define>

<Define term="Instantiation" since="this chapter">
**Instantiation** is the act of supplying a concrete type for a type parameter, producing a specific version of the generic function or type. It can be *explicit* (`Min[int](a, b)`) or *inferred* (`Min(a, b)` when `a` and `b` are `int`). Instantiation is a compile-time operation — no runtime overhead from resolving the type.
</Define>

### Type parameters: the square-bracket annotation

A **type parameter** is a placeholder type, announced in square brackets right after the function name, that the caller fills in with a real type.

```go
// Min returns the smaller of two values.
// T is the type parameter. "ordered" is a constraint (more on that shortly).
func Min[T interface{ ~int | ~float64 | ~string }](a, b T) T {
    if a < b {
        return a
    }
    return b
}
```

Read it left to right:
- `func Min` — a function named Min
- `[T interface{ ~int | ~float64 | ~string }]` — "I accept a type parameter `T` that must satisfy this constraint"
- `(a, b T)` — two parameters, both of type `T`
- `T` — the return type, same `T` the caller supplies

**Instantiation** is when you provide the concrete type. It can be explicit or inferred:

```go
// Explicit instantiation — you tell the compiler what T is:
result := Min[int](100, 200)

// Inferred instantiation — Go figures out T from the arguments:
result := Min(100, 200)  // Go sees two int literals → T = int
```

### A complete runnable example

Let's make this real with our payments scenario. `Map` over a `[]Transaction` slice to extract amounts:

```go
package main

import "fmt"

// Transaction is what our payments service actually works with.
type Transaction struct {
	ID     string
	Amount int // cents, always
	Status string
}

// Map applies f to every element of src and returns the results.
// S is the element type; R is the result type — they can differ.
func Map[S, R any](src []S, f func(S) R) []R {
	out := make([]R, len(src))
	for i, v := range src {
		out[i] = f(v)
	}
	return out
}

func main() {
	txns := []Transaction{
		{ID: "tx-001", Amount: 4999, Status: "settled"},
		{ID: "tx-002", Amount: 12500, Status: "pending"},
		{ID: "tx-003", Amount: 750, Status: "settled"},
	}

	// Extract amounts — S=Transaction, R=int, inferred from the closure.
	amounts := Map(txns, func(t Transaction) int { return t.Amount })
	fmt.Println("amounts (cents):", amounts) // [4999 12500 750]

	// Extract IDs — S=Transaction, R=string.
	ids := Map(txns, func(t Transaction) string { return t.ID })
	fmt.Println("IDs:", ids) // [tx-001 tx-002 tx-003]
}
```

## Constraints and Type Sets

Here's the thing most tutorials get wrong: they tell you a constraint is "an interface," then move on. That's leaving out the entire point. A **constraint** defines a **type set** — the exact set of types that are allowed as a type argument. Understanding type sets is what separates someone who *uses* generics from someone who *commands* them.

<Define term="Constraint" since="this chapter">
A **constraint** is an interface that restricts which concrete types may be used as a type argument. It sits in the square brackets: `[T Constraint]`. The compiler enforces the constraint at every instantiation — if the type doesn't satisfy it, you get a compile error. Constraints can restrict by method set, by concrete type union (`int | string`), by underlying type (`~int`), or any combination. They exist purely at compile time; they have zero runtime cost.
</Define>

<Define term="Type set" since="this chapter">
A **type set** is the set of all concrete types that satisfy a given constraint. `any` has the infinite type set (every type). `comparable` has the type set of all types supporting `==`. `interface{ ~int | ~string }` has the type set of every named type built on `int` or `string`. When you instantiate a generic function, the compiler checks whether your concrete type is in the constraint's type set. If not, compile error.
</Define>

<Define term="any" since="this chapter">
**`any`** is a predeclared alias for `interface{}` (introduced in Go 1.18). As a constraint, it means "this type parameter can be any type." You cannot call methods on `T` or use operators like `+` or `<` when constrained by `any` — you can only store, pass, and return values of type `T`. Use `any` when the operation is purely structural (a container that holds values without operating on them).
</Define>

<Define term="comparable" since="this chapter">
**`comparable`** is a predeclared constraint that allows types supporting `==` and `!=`. It is the minimum requirement for using `T` as a map key. `comparable` does *not* imply ordering — you cannot use `<` or `>` on a `comparable` `T`. All basic types (`int`, `string`, `bool`, pointers, arrays of comparable types, structs whose all fields are comparable) satisfy `comparable`. Interfaces and slices do not.
</Define>

<Define term="The ~ (underlying-type) operator" since="this chapter">
The **`~` operator** in a type constraint means "any type whose underlying type is this." For example, `~int` matches `int` itself and also any named type defined as `type Cents int`, `type UserID int`, etc. Without `~`, only the exact predeclared type matches. With `~`, your generic function works with the domain types Meridian actually uses (`type Cents int`, `type AccountID string`) without requiring unsafe casts.
</Define>

### The `any` and `comparable` built-ins

Go ships two predeclared constraints you'll use constantly:

- **`any`** — an alias for `interface{}`. Allows literally any type. Use when you don't need to call any methods or apply any operators on `T`.
- **`comparable`** — allows types that support `==` and `!=`. Required when you want to use `T` as a map key or compare values.

```go
// Cache requires K to be comparable (map key) and V can be anything.
type Cache[K comparable, V any] struct {
    data map[K]V
}
```

### Interface-as-constraint: methods in the type set

Any interface can be a constraint. When you write `[T fmt.Stringer]`, the type set is "every type that has a `String() string` method." You can then call `t.String()` inside the function body — the compiler knows it's safe because the constraint guarantees it.

```go
package main

import "fmt"

// Render prints any value that knows how to describe itself.
func Render[T fmt.Stringer](v T) {
	fmt.Println(v.String())
}

type Amount struct{ Cents int }

func (a Amount) String() string {
	return fmt.Sprintf("$%d.%02d", a.Cents/100, a.Cents%100)
}

func main() {
	Render(Amount{Cents: 4999}) // $49.99
}
```

### Union elements: `|` in a type set

What if you need to allow `<` or `+` across a set of types? Interfaces expressing methods can't help — Go operators aren't methods. Instead, a constraint can list concrete types with `|`:

```go
// Numeric allows integer and float types to be used with arithmetic.
type Numeric interface {
    int | int8 | int16 | int32 | int64 |
    uint | uint8 | uint16 | uint32 | uint64 |
    float32 | float64
}

func Sum[T Numeric](values []T) T {
    var total T // zero value of T — always 0 for numerics
    for _, v := range values {
        total += v
    }
    return total
}
```

The constraint `Numeric` defines the type set `{int, int8, …, float64}`. Only those exact types may be used as `T`.

### The `~` operator: underlying type matching

Now the sharp tool that unlocks idiomatic Go. When you define a named type:

```go
type Cents int
```

`Cents` has the **underlying type** `int`. It can use all the same arithmetic operators as `int`, but it is *not* `int` — they're different types. If your constraint says `int`, `Cents` is rejected. If your constraint says `~int`, it means "any type whose underlying type is `int`," and `Cents` is accepted.

**Precise definition:** `~T` in a type set means "all types whose underlying type is `T`." Every named type has exactly one underlying type, which is the type you'd get by peeling away all type definitions until you reach a predeclared type or composite type literal.

```go
type Cents int      // underlying type: int
type Dollars int    // underlying type: int
type UserID string  // underlying type: string

// Without ~: only bare int and string work.
type Ordered interface{ int | float64 | string }

// With ~: named types built on int/float64/string also work.
type Ordered interface{ ~int | ~float64 | ~string }

func Min[T Ordered](a, b T) T {
    if a < b { return a }
    return b
}

// Now this works:
a, b := Cents(499), Cents(999)
fmt.Println(Min(a, b)) // 499  ← Cents satisfies ~int
```

### The `golang.org/x/exp/constraints` package

The extended library ships pre-built constraints covering the common cases. As of Go 1.26, these still live outside stdlib, but they're widely used when you need finer-grained splits:

```go
import "golang.org/x/exp/constraints"

// constraints.Ordered = ~int | ~int8 | ... | ~float64 | ~string
// constraints.Integer = ~int | ~int8 | ... | ~uint64
// constraints.Float   = ~float32 | ~float64
// constraints.Signed  = ~int | ~int8 | ~int16 | ~int32 | ~int64

func Max[T constraints.Ordered](a, b T) T {
    if a > b { return a }
    return b
}
```

<Callout kind="note" title="golang.org/x/exp/constraints vs. the standard library">

As of Go 1.26, the `constraints` package lives in `golang.org/x/exp/constraints`, *not* `slices` or `cmp`. Go 1.21 added `cmp.Ordered` to the standard library — it's the same idea (`~int | ... | ~string`) but in `cmp`. For new code on Go 1.21+, prefer `cmp.Ordered` from stdlib; reach for `golang.org/x/exp/constraints` only when you need the finer-grained splits (`constraints.Integer`, `constraints.Float`, etc.).

</Callout>

Let's put it all together: `Filter` and `Reduce` over our transaction slice:

```go
package main

import (
	"cmp"
	"fmt"
)

type Transaction struct {
	ID     string
	Amount int // cents
	Status string
}

// Filter returns elements of src for which keep returns true.
func Filter[T any](src []T, keep func(T) bool) []T {
	out := make([]T, 0, len(src))
	for _, v := range src {
		if keep(v) {
			out = append(out, v)
		}
	}
	return out
}

// Reduce folds src into a single value of type R.
func Reduce[T, R any](src []T, init R, fn func(R, T) R) R {
	acc := init
	for _, v := range src {
		acc = fn(acc, v)
	}
	return acc
}

// Max returns the larger of two cmp.Ordered values.
func Max[T cmp.Ordered](a, b T) T {
	if a > b {
		return a
	}
	return b
}

func main() {
	txns := []Transaction{
		{ID: "tx-001", Amount: 4999, Status: "settled"},
		{ID: "tx-002", Amount: 12500, Status: "pending"},
		{ID: "tx-003", Amount: 750, Status: "settled"},
		{ID: "tx-004", Amount: 8800, Status: "settled"},
	}

	// Keep only settled transactions.
	settled := Filter(txns, func(t Transaction) bool {
		return t.Status == "settled"
	})

	// Sum their amounts.
	totalCents := Reduce(settled, 0, func(acc int, t Transaction) int {
		return acc + t.Amount
	})

	fmt.Printf("settled total: $%d.%02d\n", totalCents/100, totalCents%100)

	// Largest single amount across all transactions.
	maxAmount := Reduce(txns[1:], txns[0].Amount, func(acc int, t Transaction) int {
		return Max(acc, t.Amount)
	})
	fmt.Printf("max transaction: $%d.%02d\n", maxAmount/100, maxAmount%100)
}
```

  <Gotcha>A constraint with union elements (`int | string`) cannot also list methods — that combination is only valid as a constraint, not as a regular interface value. You cannot write `var x interface{ int | string }` as a variable type. Use it only in square brackets.</Gotcha>

</ConceptGrid>

## Type Inference and Its Limits

<Define term="Type inference" since="this chapter">
**Type inference** is the compiler's ability to deduce a type parameter's concrete type from the surrounding context — specifically, from the types of the arguments at the call site. When you call `Map(txns, func(t Transaction) int {...})`, the compiler sees `txns` is `[]Transaction` and infers `S = Transaction`; it sees the closure returns `int` and infers `R = int`. Inference is a compile-time mechanism — it adds zero overhead. When it fails (no arguments, ambiguous types, or generic *types* rather than functions), you must supply the type argument explicitly.
</Define>

Type inference is what makes generics pleasant instead of verbose. The compiler deduces type arguments from context so you don't have to write them. But inference has limits, and knowing those limits saves you from fighting the compiler blind.

### How inference works

The Go compiler performs **type unification**: it walks your function's parameter types and return type, matches them against the actual argument types at the call site, and solves for each type parameter.

```go
func Map[S, R any](src []S, f func(S) R) []R

// At the call site:
Map(txns, func(t Transaction) int { return t.Amount })
// The compiler sees:
//   src has type []Transaction → S = Transaction
//   f   has type func(Transaction) int → R = int
// Both inferred. No [Transaction, int] needed.
```

Inference works when:
- Type parameters appear in **function parameter types** (not just return types).
- The arguments at the call site carry enough type information to solve the system.

### When you must write type arguments explicitly

**Case 1: The type parameter appears only in the return type.**

```go
func Zero[T any]() T {
    var z T
    return z
}

// Inference fails — there are no arguments to unify against.
// You must write:
z := Zero[int]()    // explicit
z := Zero[Transaction]()
```

**Case 2: The inference is ambiguous or the constraint requires disambiguation.**

```go
func As[To, From any](v From) To {
    // (hypothetical — this would use reflection or unsafe in reality)
    panic("illustration only")
}

// Both To and From can't always be inferred from one argument.
// You may need: As[string, []byte](data)
```

**Case 3: You're instantiating a generic type (not a function).**

Generic types must always be fully instantiated — no inference for type declarations:

```go
type Stack[T any] struct{ items []T }

// Always explicit:
var s Stack[int]
s2 := Stack[Transaction]{}
```

Let me show a realistic case where inference works and where it breaks, using our cache scenario:

```go
package main

import "fmt"

// Cache is a typed in-memory store.
// K must be comparable (map key); V can be anything.
type Cache[K comparable, V any] struct {
	data map[K]V
}

func NewCache[K comparable, V any]() *Cache[K, V] {
	return &Cache[K, V]{data: make(map[K]V)}
}

func (c *Cache[K, V]) Set(key K, value V) {
	c.data[key] = value
}

func (c *Cache[K, V]) Get(key K) (V, bool) {
	v, ok := c.data[key]
	return v, ok
}

func main() {
	// Generic TYPE — must be explicit. No inference for type literals.
	userCache := NewCache[string, int]() // K=string, V=int

	userCache.Set("alice-session-count", 42)
	userCache.Set("bob-session-count", 7)

	if count, ok := userCache.Get("alice-session-count"); ok {
		fmt.Println("alice sessions:", count)
	}

	// Method calls infer from arguments — no explicit types needed.
	userCache.Set("charlie-session-count", 3) // K and V inferred from receiver type
}
```

## Generic Types and Data Structures

Functions were warmup. Generic *types* are where you build the reusable containers that your team uses for years without knowing (or caring) what's inside.

### Part 1: A generic Stack

A stack is the most instructive starting point — it's simple enough to be readable and concrete enough to be useful. Our payments platform uses a stack to track operation steps for reversible saga transactions.

```go
package main

import (
	"errors"
	"fmt"
)

// Stack[T] is a last-in, first-out container.
// T can be any type — it imposes no constraint beyond existence.
type Stack[T any] struct {
	items []T
}

// Push adds v to the top of the stack.
func (s *Stack[T]) Push(v T) {
	s.items = append(s.items, v)
}

// Pop removes and returns the top element.
// Returns an error if the stack is empty.
func (s *Stack[T]) Pop() (T, error) {
	if len(s.items) == 0 {
		var zero T // the zero value of T — clean way to return "nothing"
		return zero, errors.New("stack is empty")
	}
	top := s.items[len(s.items)-1]
	s.items = s.items[:len(s.items)-1]
	return top, nil
}

// Len returns the number of items.
func (s *Stack[T]) Len() int { return len(s.items) }

// SagaStep models one reversible step in a distributed transaction.
type SagaStep struct {
	Name       string
	CompensateFn func() error // what to call if a later step fails
}

func main() {
	// A type-safe stack of saga steps — no interface{} in sight.
	var ops Stack[SagaStep]

	ops.Push(SagaStep{Name: "debit-sender", CompensateFn: func() error {
		fmt.Println("reversing debit on sender")
		return nil
	}})
	ops.Push(SagaStep{Name: "credit-receiver", CompensateFn: func() error {
		fmt.Println("reversing credit on receiver")
		return nil
	}})

	fmt.Println("saga steps queued:", ops.Len())

	// Simulate rollback — pop in reverse order.
	for ops.Len() > 0 {
		step, _ := ops.Pop()
		fmt.Printf("compensating: %s\n", step.Name)
		step.CompensateFn()
	}
}
```

### Part 2: A generic Set

Our platform needs to deduplicate transaction IDs before batch-processing — across multiple types. A generic `Set[T comparable]` does it once.

```go
package main

import "fmt"

// Set[T] is an unordered collection with no duplicates.
// T must be comparable so it can be a map key.
type Set[T comparable] struct {
	m map[T]struct{} // the idiomatic empty-struct map — zero allocation per value
}

// NewSet allocates an empty Set.
func NewSet[T comparable]() Set[T] {
	return Set[T]{m: make(map[T]struct{})}
}

// Add inserts v. Silently ignores duplicates.
func (s *Set[T]) Add(v T) {
	s.m[v] = struct{}{}
}

// Contains reports whether v is in the set.
func (s *Set[T]) Contains(v T) bool {
	_, ok := s.m[v]
	return ok
}

// Len returns the number of distinct elements.
func (s *Set[T]) Len() int { return len(s.m) }

// Values returns a slice of all elements (order not guaranteed).
func (s *Set[T]) Values() []T {
	out := make([]T, 0, len(s.m))
	for v := range s.m {
		out = append(out, v)
	}
	return out
}

func main() {
	// Deduplicate a batch of incoming transaction IDs.
	incoming := []string{
		"tx-001", "tx-002", "tx-001", "tx-003", "tx-002", "tx-004",
	}

	seen := NewSet[string]()
	var unique []string
	for _, id := range incoming {
		if !seen.Contains(id) {
			seen.Add(id)
			unique = append(unique, id)
		}
	}

	fmt.Println("unique IDs to process:", unique)
	fmt.Println("duplicates dropped:", len(incoming)-len(unique))
}
```

### Part 3: A typed Cache with a TTL constraint

Here is the `Cache[K, V]` we sketched in the inference section, fleshed out into something production-adjacent — used in the platform's rate-limiter to track per-account request counts:

```go
package main

import (
	"fmt"
	"sync"
	"time"
)

// entry wraps a value with an expiry timestamp.
type entry[V any] struct {
	value     V
	expiresAt time.Time
}

// TTLCache[K, V] is a concurrency-safe cache with per-entry TTL.
// K must be comparable; V can be any type.
type TTLCache[K comparable, V any] struct {
	mu   sync.Mutex
	data map[K]entry[V]
}

func NewTTLCache[K comparable, V any]() *TTLCache[K, V] {
	return &TTLCache[K, V]{data: make(map[K]entry[V])}
}

// Set stores value under key, expiring after ttl.
func (c *TTLCache[K, V]) Set(key K, value V, ttl time.Duration) {
	c.mu.Lock()
	defer c.mu.Unlock()
	c.data[key] = entry[V]{value: value, expiresAt: time.Now().Add(ttl)}
}

// Get retrieves the value. Returns (zero, false) if missing or expired.
func (c *TTLCache[K, V]) Get(key K) (V, bool) {
	c.mu.Lock()
	defer c.mu.Unlock()
	e, ok := c.data[key]
	if !ok || time.Now().After(e.expiresAt) {
		delete(c.data, key) // evict the stale entry
		var zero V
		return zero, false
	}
	return e.value, true
}

func main() {
	// Rate-limiter uses a cache of account → request count in the current window.
	limiter := NewTTLCache[string, int]()

	limiter.Set("account-alice", 0, 60*time.Second)
	limiter.Set("account-bob", 0, 60*time.Second)

	// Simulate five requests from alice in the window.
	for i := 0; i < 5; i++ {
		count, _ := limiter.Get("account-alice")
		limiter.Set("account-alice", count+1, 60*time.Second)
	}

	if count, ok := limiter.Get("account-alice"); ok {
		fmt.Println("alice requests this window:", count) // 5
	}

	// bob's count is separate — no type confusion possible.
	limiter.Set("account-bob", 1, 60*time.Second)
	if count, ok := limiter.Get("account-bob"); ok {
		fmt.Println("bob requests this window:", count) // 1
	}
}
```

## Generics vs Interfaces

Here's where I'm going to be honest with you, because I'm not the kind of instructor who sells you one tool and pretends it solves everything. Generics and interfaces both eliminate repeated code, but they make *different* trade-offs, and choosing the wrong one is a design smell that will chase your team for years.

### The honest comparison

**Use an interface when:**
- The concrete types that satisfy it aren't known at compile time (plugins, handlers, user-provided types).
- You need to store heterogeneous values in one collection (`[]io.Reader`).
- The behavior is what matters, not the exact type.
- You want dynamic dispatch — the "which implementation?" decision at runtime.

**Use generics when:**
- You know the types at compile time and want the compiler to enforce them.
- You need to preserve the exact type through a container (`Stack[Transaction]`, not `Stack[any]`).
- You want operators (`<`, `+`) that interfaces can't express through methods.
- Performance matters and you want to avoid interface boxing (see the UnderTheHood section).

Let's see the trade-off in a concrete scenario. Our platform has a `Repository` that different storage backends implement. Should it be generic or interface-based?

**If the diversity is in the behavior and known only at runtime → interface.**
**If the diversity is in the data type and known at compile time → generic.**

When in doubt, start with an interface. Generics add compile-time type safety at the cost of more complex signatures. Reach for them when you feel the type-assertion pain of `interface{}` or when you need operators that interfaces can't express.

## Self-Referential Generic Types

Go 1.26 unlocks a language feature that the generics design deliberately held back until the type-checker was proven stable enough to handle it: a generic type may now refer to **itself** in its own type-parameter constraint. This makes self-referential constraints — where a method must return the same concrete type as the receiver — expressible directly in the type system, without awkward workarounds.

### Why self-referential constraints matter

Consider a `Numeric` or monoid-style API where you want a type to define an `Add` method that returns the same type. Before Go 1.26, you had two unsatisfying options:

- Use `any` and lose type safety — the method could return a completely different type.
- Thread an extra type parameter through every call site — verbose and leaky.

Go 1.26 lets you write the constraint once, cleanly:

```go
// Adder[A] is a self-referential constraint (new in Go 1.26).
// Any type T that satisfies Adder[T] has an Add method
// that takes and returns the same concrete type T.
type Adder[A Adder[A]] interface {
    Add(A) A
}
```

Read `Adder[A Adder[A]]` like this: "`A` must satisfy `Adder[A]`" — `A` is constrained by the very interface it's being used in. The type-checker resolves this recursion at compile time.

### A worked example: fixed-precision amounts

Our payments platform needs fixed-point `Amount` values that can be summed generically. The `Add` method must return `Amount` — not some other type. Self-referential constraints express this exactly:

<GoPlayground>

```go
package main

import "fmt"

// Adder is a self-referential generic constraint (Go 1.26).
// A type satisfying Adder[T] has Add(T) T — it accepts and returns
// its own concrete type, enforced at compile time.
type Adder[A Adder[A]] interface {
	Add(A) A
}

// Amount is a fixed-point payment amount in minor currency units (cents).
type Amount struct{ Cents int }

// Add returns a new Amount whose value is the sum of a and b.
// This satisfies Adder[Amount]: Add takes Amount and returns Amount.
func (a Amount) Add(b Amount) Amount {
	return Amount{Cents: a.Cents + b.Cents}
}

// Sum folds a slice of Adder values into one, starting from zero.
// T must satisfy Adder[T] — meaning T.Add(T) returns T.
func Sum[T Adder[T]](zero T, values []T) T {
	result := zero
	for _, v := range values {
		result = result.Add(v)
	}
	return result
}

func main() {
	payments := []Amount{
		{Cents: 4999},  // $49.99
		{Cents: 12500}, // $125.00
		{Cents: 750},   // $7.50
	}

	total := Sum(Amount{}, payments)
	fmt.Printf("total: $%d.%02d\n", total.Cents/100, total.Cents%100)
	// total: $182.49
}
```

</GoPlayground>

(Heads-up: this needs a **Go 1.26** toolchain. Go 1.26 lifted the rule that a generic type couldn't refer to itself in its type-parameter list; on an older compiler — including the embedded playground until it updates — it errors with `invalid recursive type: Adder refers to itself`. The code is correct for the course's target version.)

The compiler resolves `T Adder[T]` at the `Sum[Amount]` call site. It verifies that `Amount.Add(Amount) Amount` satisfies the constraint — the return type is the same concrete type, not a widened interface. That guarantee is what self-referential constraints buy you.

<Callout kind="advanced" title="Self-Referential Constraints — Go 1.26">

Before Go 1.26, writing `type Adder[A Adder[A]] interface { ... }` was a compile error: the type-checker rejected generic types that referenced themselves in their own type-parameter list. Go 1.26 lifts this restriction, allowing **F-bounded quantification** — a pattern well-known in Haskell's `Num` typeclass and Rust's `Add` trait, now available in Go.

**When to reach for it:**

- Numeric / algebraic abstractions (`Add`, `Mul`, `Zero`, `One`) where the method must return the same concrete type.
- Builder-style APIs where each chained method returns `Self`.
- Ordered domain types where `Compare(Self) int` must be enforced structurally.

**When not to:**

Self-referential constraints deepen signature complexity. If the concrete types are always known at the call site and you don't need the polymorphic abstraction, skip the constraint entirely and use plain method dispatch. As always: start simple, generify when the duplication becomes painful.

</Callout>

### The problem generics create for a compiler

In C++, templates are fully specialized: `vector<int>` and `vector<string>` generate completely separate machine code for every method. That's called **monomorphization**. It's fast at runtime but makes binaries large and compile times slow ("template bloat").

Go chose a middle path: **GC-shape stenciling**.

### What is a GC shape?

The name comes from the garbage collector's view of a type — its size, alignment, and where pointers live — but the **gcshape grouping** the compiler uses to decide which instantiations share a stencil is deliberately stricter than raw layout. The rule is precise: **two concrete types are in the same gcshape group if and only if they have the same underlying type, or they are both pointer types.**

This means:
- All pointer types (`*T`; slices, maps, channels, and interfaces are pointer-shaped too) share **one** group — every pointer instantiation in your whole program reuses a single stencil.
- A named type shares a group with its underlying type: `Cents` (`type Cents int`) and `int` share one stencil.
- Different built-in types do **not** share, even at the same size: `int`, `int64`, and `float64` are three separate groups (8 bytes each on amd64, but the design keeps fundamentally different types apart so a stencil never has to carry two types' operator behavior).
- `struct{ a int; b *string }` is its own group.

### The stencil: one machine-code body per GC shape

For a generic function like:

```go
func Min[T cmp.Ordered](a, b T) T {
    if a < b { return a }
    return b
}
```

The compiler emits **one stencil (one machine-code function body) per gcshape group**, not one per concrete type. The stencil receives a **dictionary** — a small runtime struct containing type-specific information (like how to compare two values of type `T` using `<`).

So across the types `int`, `int64`, `Cents`, `float64`:
- `int`, `Cents`, and `Dollars` (all with underlying type `int`) share one stencil.
- `int64` gets its own stencil — a different underlying type, even though it's also 8 bytes.
- `float64` gets its own stencil (different underlying type and machine representation for `<`).
- `string` gets its own stencil (two-word header, `<` is lexicographic).

### What's in the dictionary?

The dictionary is a compiler-generated struct passed as an implicit first argument. It contains:
- Pointers to type-specific functions (the `<` comparator for `Ordered`, the `==` for `comparable`, etc.).
- Metadata for reflection-like operations (type size, alignment, GC bitmap).
- Itab pointers for interface constraints.

The stencil calls through the dictionary for type-specific operations. Think of it as a vtable, but per-call-site rather than per-value.

### What this costs — and when it doesn't

**Cost:** Every call through a dictionary has one additional pointer indirection compared to a fully-specialized (monomorphized) call. For a comparison function called inside a tight loop over millions of transactions, that indirection lands in the CPU's instruction cache — typically not a bottleneck, but measurable in microbenchmarks.

**When it specializes fully:** As of Go 1.21+, the compiler *can* specialize (skip the dictionary) when the instantiation is visible — i.e., the concrete type is known in the same package. This is an optimization the compiler applies opportunistically. It's not guaranteed and not documented as a stable behavior. Assume dictionary dispatch; treat full specialization as a bonus.

**Pointer shapes share one stencil always:** All pointer-like types — `*T`, slices, maps, channels, interfaces — share a single stencil. This is the most important special case: a `Cache[string, *Transaction]` and a `Cache[string, *Account]` share machine code, differentiated only by their dictionaries.

**Version note:** GC-shape stenciling is the Go 1.18–1.26 implementation strategy. It has evolved between releases; the compiler specializes more aggressively in later versions. The semantics of generics (what code is *correct*) are stable. The *performance model* is not a language guarantee.

</UnderTheHood>

### The allocation question: does boxing happen?

When you store a value of type `T any` inside a generic container, does it escape to the heap (like an `interface{}` would)?

Short answer: **no boxing for concrete scalar types**. The generic container stores `T` by value in the underlying array. A `Stack[int]` has `[]int` internally — no interface, no heap allocation per element, no indirection. A `Stack[*Transaction]` stores `[]*Transaction` — pointers, stored by value in the slice.

Boxing *does* happen if `T` is itself an interface type: `Stack[io.Reader]` stores `[]io.Reader`, each element being an interface word (type pointer + data pointer). But that's the interface's cost, not generics'.

```go
package main

import "fmt"

type Stack[T any] struct{ items []T }

func (s *Stack[T]) Push(v T)        { s.items = append(s.items, v) }
func (s *Stack[T]) Pop() (T, error) {
	if len(s.items) == 0 { var z T; return z, fmt.Errorf("empty") }
	top := s.items[len(s.items)-1]
	s.items = s.items[:len(s.items)-1]
	return top, nil
}

func main() {
	// Stack[int] — items slice holds int values directly. No boxing.
	var intStack Stack[int]
	intStack.Push(100)
	intStack.Push(200)
	v, _ := intStack.Pop()
	fmt.Println("popped:", v) // 200

	// Stack[string] — items slice holds string headers (ptr+len). No extra boxing.
	var strStack Stack[string]
	strStack.Push("tx-settled")
	s, _ := strStack.Pop()
	fmt.Println("popped:", s) // tx-settled
}
```

## The Modern Generic Stdlib: slices, maps, cmp

Here's the part your colleagues who learned generics in 2022 probably missed. Go 1.21 shipped three packages that are generics in daily use — not as an abstraction you write, but as APIs you call every day. They replaced a decade of hand-rolled sort comparators, map-key extractors, and three-way comparison functions. By the Go 1.26 baseline this course runs on, using these is the idiomatic path. Not knowing them means writing code that's longer, slower, and reviewed with a polite wince.

**On the job:** You reach for `slices.SortFunc` whenever you need a sorted list of domain objects. You reach for `maps.Keys` whenever you need a reproducible iteration order. If you're still writing a manual `less(i, j int) bool` closure for `sort.Slice`, you owe your team an explanation.

### `cmp` — three-way comparison and the `Ordered` constraint (Go 1.21)

The `cmp` package defines `Ordered` — the constraint for all types that support `<`, `>`, `<=`, `>=`. It also provides two functions you'll use everywhere:

- **`cmp.Compare[T Ordered](x, y T) int`** — returns -1, 0, or +1. This is the canonical three-way comparator used by `slices.SortFunc`, `slices.BinarySearch`, and anywhere you need a consistent ordering.
- **`cmp.Or[T comparable](vals ...T) T`** (added in Go 1.22, a release after `cmp.Ordered`/`cmp.Compare`) — returns the first non-zero value. Useful for fallback chains (e.g. `cmp.Or(envValue, flagValue, defaultValue)`).

```go
import "cmp"

// cmp.Ordered is the stdlib constraint: ~int | ~int8 | ... | ~float64 | ~string
// Use it instead of rolling your own Numeric/Ordered interface.
func earliest[T cmp.Ordered](a, b T) T {
    if cmp.Compare(a, b) < 0 {
        return a
    }
    return b
}
```

The `cmp.Ordered` constraint uses `~` internally, so Meridian's `type Cents int` satisfies it without any adapter.

### `slices` — the generic slice toolkit (Go 1.21)

The `slices` package is what `sort.Slice` should have been from day one. Every function is generic, every signature is clear, and there are no hidden allocations from turning your comparator into an `interface{}`.

Key functions on `[]Transaction`:

| Function | What it does |
|---|---|
| `slices.Sort(s)` | Sorts in-place for `cmp.Ordered` element types |
| `slices.SortFunc(s, cmp)` | Sorts in-place with a `func(a, b T) int` comparator |
| `slices.BinarySearch(s, v)` | Binary search on a sorted slice; returns index + found bool |
| `slices.Contains(s, v)` | Reports whether `v` is in `s` (comparable elements) |
| `slices.Index(s, v)` | Returns the index of the first `v`, or -1 |
| `slices.Clone(s)` | Returns a shallow copy |
| `slices.Reverse(s)` | Reverses in-place |

Notice: none of these take `i, j int` indices, none return `bool` for less-than, none require you to implement an interface. They take the value directly. That's what generics buy you.

### `maps` — safe map utilities (Go 1.21)

The `maps` package provides functions that were previously painful boilerplate:

- **`maps.Keys[M ~map[K]V, K comparable, V any](m M) iter.Seq[K]`** — returns an **iterator** over the keys (order undefined). Collect with `slices.Collect`, or sort directly with `slices.Sorted(maps.Keys(m))` for reproducible order. (The old `golang.org/x/exp/maps.Keys` returned a `[]K`; the stdlib version, added in Go 1.23, returns an `iter.Seq[K]`.)
- **`maps.Values[M ~map[K]V, K comparable, V any](m M) iter.Seq[V]`** — returns an iterator over the values.
- **`maps.Clone[M ~map[K]V, K comparable, V any](m M) M`** — shallow copy of the map.

Notice the `~map[K]V` constraint — the `~` means named map types like `type AccountMap map[string]Account` work without conversion.

### Putting it together: sorting and searching Meridian transactions

package main

import (
	"cmp"
	"fmt"
	"maps"
	"slices"
)

type Transaction struct {
	ID     string
	Amount int // cents
	Status string
}

func main() {
	txns := []Transaction{
		{ID: "tx-003", Amount: 750, Status: "settled"},
		{ID: "tx-001", Amount: 4999, Status: "settled"},
		{ID: "tx-004", Amount: 8800, Status: "pending"},
		{ID: "tx-002", Amount: 12500, Status: "pending"},
	}

	// Sort by amount ascending using slices.SortFunc + cmp.Compare.
	// Before Go 1.21 this was: sort.Slice(txns, func(i, j int) bool { return txns[i].Amount < txns[j].Amount })
	slices.SortFunc(txns, func(a, b Transaction) int {
		return cmp.Compare(a.Amount, b.Amount)
	})

	fmt.Println("sorted by amount:")
	for _, t := range txns {
		fmt.Printf("  %s  $%d.%02d  [%s]\n", t.ID, t.Amount/100, t.Amount%100, t.Status)
	}

	// slices.Contains checks membership — no manual loop needed.
	ids := slices.Collect(func(yield func(string) bool) {
		for _, t := range txns {
			if !yield(t.ID) {
				return
			}
		}
	})
	fmt.Println("\ncontains tx-002:", slices.Contains(ids, "tx-002"))
	fmt.Println("contains tx-099:", slices.Contains(ids, "tx-099"))

	// maps.Keys extracts keys for reproducible ordered output.
	balances := map[string]int{
		"alice": 150000,
		"bob":   42500,
		"carol": 98000,
	}
	keys := slices.Sorted(maps.Keys(balances))
	fmt.Println("\naccounts (sorted):")
	for _, k := range keys {
		fmt.Printf("  %s: $%d.%02d\n", k, balances[k]/100, balances[k]%100)
	}

	effectiveStatus := cmp.Or("", "", "settled") // first two are empty — falls through to "settled"
	fmt.Println("\neffective status:", effectiveStatus)
}

### Secondary sort: amount then ID

Chaining comparators is where `cmp.Compare` really shines. Compare by amount first; if equal, compare by ID. No booleans, no index arithmetic — just add comparisons:

```go
slices.SortFunc(txns, func(a, b Transaction) int {
    // Primary: amount ascending
    if n := cmp.Compare(a.Amount, b.Amount); n != 0 {
        return n
    }
    // Secondary: ID ascending (lexicographic tiebreak)
    return cmp.Compare(a.ID, b.ID)
})
```

The pattern is idiomatic Go 1.21+. `n != 0` short-circuits on the primary key; if both amounts are equal, the secondary key decides. You can chain as many comparisons as you need.

<Exercise n={3} title="Generic Map + Filter pipeline" level="medium">

Using the `Map` and `Filter` functions from earlier in the chapter, write a pipeline that:
1. Starts with `[]Transaction` (at least 4 entries, mix of `"settled"` and `"pending"`).
2. Filters to only `"settled"` transactions.
3. Maps to amounts in cents.
4. Prints the total.

Do not write any new generic functions — compose the ones you already have.

<Solution>

```go
package main

import "fmt"

type Transaction struct {
	ID     string
	Amount int
	Status string
}

func Map[S, R any](src []S, f func(S) R) []R {
	out := make([]R, len(src))
	for i, v := range src {
		out[i] = f(v)
	}
	return out
}

func Filter[T any](src []T, keep func(T) bool) []T {
	out := make([]T, 0, len(src))
	for _, v := range src {
		if keep(v) {
			out = append(out, v)
		}
	}
	return out
}

func Reduce[T, R any](src []T, init R, fn func(R, T) R) R {
	acc := init
	for _, v := range src {
		acc = fn(acc, v)
	}
	return acc
}

func main() {
	txns := []Transaction{
		{ID: "tx-001", Amount: 4999, Status: "settled"},
		{ID: "tx-002", Amount: 12500, Status: "pending"},
		{ID: "tx-003", Amount: 750, Status: "settled"},
		{ID: "tx-004", Amount: 3300, Status: "settled"},
		{ID: "tx-005", Amount: 8800, Status: "pending"},
	}

	settled := Filter(txns, func(t Transaction) bool {
		return t.Status == "settled"
	})

	amounts := Map(settled, func(t Transaction) int {
		return t.Amount
	})

	total := Reduce(amounts, 0, func(acc, amt int) int {
		return acc + amt
	})

	fmt.Printf("settled total: $%d.%02d\n", total/100, total%100)
	// Expected: tx-001 (4999) + tx-003 (750) + tx-004 (3300) = 9049 cents = $90.49
}
```

This is the whole point of generic utility functions: compose them freely without losing type information. The compiler tracked every type through all three stages.

<Exercise n={4} title="Constrained Set union/intersection" level="medium">

Extend the `Set[T comparable]` type from the chapter with two methods:
- `Union(other Set[T]) Set[T]` — returns a new set containing all elements from both.
- `Intersection(other Set[T]) Set[T]` — returns elements present in both.

Test with `Set[string]` using transaction status tags.

<Solution>

```go
package main

import "fmt"

type Set[T comparable] struct {
	m map[T]struct{}
}

func NewSet[T comparable](elems ...T) Set[T] {
	s := Set[T]{m: make(map[T]struct{})}
	for _, e := range elems {
		s.m[e] = struct{}{}
	}
	return s
}

func (s *Set[T]) Add(v T)          { s.m[v] = struct{}{} }
func (s *Set[T]) Contains(v T) bool { _, ok := s.m[v]; return ok }

func (s Set[T]) Union(other Set[T]) Set[T] {
	result := NewSet[T]()
	for k := range s.m {
		result.m[k] = struct{}{}
	}
	for k := range other.m {
		result.m[k] = struct{}{}
	}
	return result
}

func (s Set[T]) Intersection(other Set[T]) Set[T] {
	result := NewSet[T]()
	for k := range s.m {
		if other.Contains(k) {
			result.m[k] = struct{}{}
		}
	}
	return result
}

func (s Set[T]) Values() []T {
	out := make([]T, 0, len(s.m))
	for k := range s.m {
		out = append(out, k)
	}
	return out
}

func main() {
	// Tags from two different audit runs.
	runA := NewSet("settled", "pending", "refunded")
	runB := NewSet("settled", "failed", "refunded")

	fmt.Println("union:", runA.Union(runB).Values())        // all 4 unique statuses
	fmt.Println("intersection:", runA.Intersection(runB).Values()) // settled, refunded
}
```

`Union` and `Intersection` take `Set[T]` by value — the method receiver is also value, not pointer, because they don't mutate `s`. Consistent value semantics throughout.

</Solution>

<Exercise n={5} title="Zero-allocation Pair and Result types" level="hard">

Write two generic structs:

1. `Pair[A, B any]` — holds two values of (potentially) different types. Add a `Swap() Pair[B, A]` method.
2. `Result[T any]` — either a value `T` or an `error` (never both). Add:
   - `OK(v T) Result[T]` constructor
   - `Err(e error) Result[T]` constructor
   - `Unwrap() (T, error)` — returns the value and error
   - `Must() T` — returns the value or panics with the error

Use `Result[int]` to wrap the output of a function that might fail, like parsing a transaction amount.

<Solution>

```go
package main

import (
	"fmt"
	"strconv"
)

// Pair holds two values of (potentially) different types.
type Pair[A, B any] struct {
	First  A
	Second B
}

func MakePair[A, B any](a A, b B) Pair[A, B] { return Pair[A, B]{a, b} }

// Swap returns a new Pair with the types reversed.
func (p Pair[A, B]) Swap() Pair[B, A] { return Pair[B, A]{p.Second, p.First} }

// Result is either a value T or an error — never both.
type Result[T any] struct {
	val T
	err error
}

func OK[T any](v T) Result[T]       { return Result[T]{val: v} }
func Err[T any](e error) Result[T]  { return Result[T]{err: e} }

func (r Result[T]) Unwrap() (T, error) { return r.val, r.err }

func (r Result[T]) Must() T {
	if r.err != nil {
		panic(r.err)
	}
	return r.val
}

// parseAmount parses a string like "49.99" into cents.
func parseAmount(s string) Result[int] {
	f, err := strconv.ParseFloat(s, 64)
	if err != nil {
		return Err[int](fmt.Errorf("invalid amount %q: %w", s, err))
	}
	return OK(int(f * 100))
}

func main() {
	p := MakePair("tx-001", 4999)
	fmt.Println("pair:", p.First, p.Second) // tx-001 4999
	swapped := p.Swap()
	fmt.Println("swapped:", swapped.First, swapped.Second) // 4999 tx-001

	good := parseAmount("49.99")
	cents, err := good.Unwrap()
	fmt.Println("parsed cents:", cents, "err:", err) // 4999 <nil>

	bad := parseAmount("not-a-number")
	val, err := bad.Unwrap()
	fmt.Println("bad parse:", val, "err:", err)
	// 0  invalid amount "not-a-number": ...
}
```

`Result[T]` is a poor-man's `sum type` — Go doesn't have those natively, but this generic struct gets you 80% of the way there with full type safety. `Must()` is for tests and situations where the error is truly impossible; never use it in production request paths.

</Solution>

</Exercise>

<Recap>

You now command generics — not just the syntax, but the whole story:

- **Type parameters** (`[T any]`, `[K comparable, V any]`) appear in square brackets after the function or type name. They're compile-time placeholders filled in by instantiation.
- **Constraints** define **type sets** — the exact types allowed as `T`. `any` means everything; `comparable` means `==`/`!=`; a union like `int | float64` means exactly those; an interface means everything implementing it.
- The **`~` operator** expands a type set to include named types with the same underlying type. Without `~`, `type Cents int` doesn't satisfy `int`. With `~int`, it does. Use `~` almost always.
- **Type inference** deduces type arguments from function arguments. It works when type parameters appear in parameter types; it fails for return-only params and generic type literals (which always need explicit args).
- **Generic types** (`Stack[T]`, `Set[T comparable]`, `TTLCache[K, V]`) preserve type information through containers — no boxing, no type assertions, no runtime panics.
- **Generics vs interfaces**: use interfaces for runtime polymorphism and heterogeneous collections; use generics for compile-time type safety, preserved type identity, and operators that interfaces can't express.
- **Self-referential generic types (Go 1.26):** A generic type may now reference itself in its own type-parameter constraint — e.g. `type Adder[A Adder[A]] interface { Add(A) A }`. This enables F-bounded quantification: constraints that guarantee a method returns the same concrete type as the receiver. Use it for numeric/algebraic APIs, builder chains, and ordered domain types.
- **Under the hood (Go 1.18+)**: **GC-shape stenciling** generates one machine-code body per GC shape (not per type), with a **dictionary** carrying type-specific operations. Pointer-shaped types all share one stencil. Scalar types share a stencil when they have the **same underlying type** (e.g. `int` and a named `type Cents int`) — different built-ins like `int` and `int64` do *not* share, even at the same size. Dictionary dispatch adds one pointer indirection vs. fully monomorphized code — measurable in benchmarks, invisible in most production paths.
- **The modern generic stdlib (Go 1.21+):** The `slices`, `maps`, and `cmp` packages are generics in daily production use. `slices.SortFunc` + `cmp.Compare` replaces `sort.Slice`; `slices.Contains` / `slices.BinarySearch` replace manual loops; `maps.Keys` / `maps.Values` / `maps.Clone` eliminate boilerplate map iteration. `cmp.Ordered` is the stdlib constraint for ordered types (use it instead of rolling your own). These are the APIs you reach for first — implement your own generic utilities only when the stdlib doesn't cover it.

</Recap>
