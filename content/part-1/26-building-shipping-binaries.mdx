## Cross-Compilation

*Stop 1 of 5.*

### Step 1: two environment variables

Meridian's ledger ships to three places: `linux/amd64` servers, `linux/arm64` (AWS Graviton) servers, and developers' Macs. In most compiled languages that means three build machines or a cross-compiler per target. In Go:

<Define term="Cross-compilation (GOOS / GOARCH)">
Building for a different OS or CPU than the machine you're on. `GOOS` names the target operating system (`linux`, `darwin`, `windows`, …); `GOARCH` names the CPU architecture (`amd64`, `arm64`, `riscv64`, …). Set them and `go build` emits a native binary for that target. `go tool dist list` prints every supported pair: 47 in Go 1.27.
</Define>

### Step 2: why nothing needs installing

A typical C or Rust program leans on the target's C library and linker, so building for another platform needs that platform's libraries and tools (a "sysroot" and a cross-linker). Go avoids both:

- **The runtime is Go.** The scheduler, garbage collector and allocator are written in Go plus a little assembly, and the toolchain ships source for every supported target.
- **System calls are made directly.** On Linux, Go's `syscall` package talks to the kernel itself, with no C library in between.
- **Go has its own linker,** which writes ELF (Linux), Mach-O (macOS) and PE (Windows) files without asking the host's `ld`.

So a cross build is just "compile for a different back end, link a different file format". That holds as long as **cgo** stays out of it, which Stop 2 is about.

<ConceptGrid cols={3}>

  <ConceptCard label="File-name constraints">Files ending <code>_linux.go</code> or <code>_arm64.go</code> are compiled only for that target.</ConceptCard>
  <ConceptCard label="//go:build lines">Explicit conditions such as <code>//go:build linux &amp;&amp; !arm64</code> at the top of a file.</ConceptCard>

</ConceptGrid>

## The cgo Static-Binary Trap

*Stop 2 of 5.*

<ELI5
  concept="Why your static binary suddenly isn't static"
  analogy="A suitcase packed for a self-contained trip, with one appliance that needs the hotel's adapter."
  role="reader"
>

A Go binary is usually self-contained: copy it anywhere with the same OS and CPU and it runs. **cgo** (Go calling C) quietly breaks that. When cgo is used, the binary is linked against the system's C library and needs that library, plus a small program called the **dynamic loader**, on whatever machine runs it.

`scratch` has neither. So the binary is in the image, yet the kernel can't start it, and the error message names the binary rather than the missing loader.

</ELI5>

### Step 1: when is cgo on?

`CGO_ENABLED` decides whether cgo may be used. Its **default** is where the confusion starts, so here it is, measured:

| Situation | Default `CGO_ENABLED` | Result |
|---|---|---|
| Native build, and a C compiler is installed (Mac with Xcode tools, `golang:1.27` Debian image) | `1` | cgo used if any package needs it |
| Native build, no C compiler (`golang:1.27-alpine`) | `0` | Go turns cgo off by itself |
| Cross-compiling (`GOOS`/`GOARCH` differ from the host) | `0` | static, unless you force cgo on |

That third row is why every cross build in Stop 1 said "statically linked". Forcing `CGO_ENABLED=1` for a Linux target on a Mac fails at once, because the Mac's C compiler can't build Linux C code:

```text
$ CGO_ENABLED=1 GOOS=linux GOARCH=arm64 go build ./cmd/ledger
linux_syscall.c:73:13: error: implicit declaration of function 'setresuid' [-Werror,-Wimplicit-function-declaration]
```

### Step 2: which imports pull cgo in

With cgo *allowed*, it's only *used* if some package in the build needs it. You never write `import "C"`, but two standard-library packages have cgo implementations they prefer. Five tiny programs, built in the `golang:1.27` image (cgo on), checked with the tool below:

```text
hello (fmt only)                 static: runs in scratch
imports net                      dynamic: needs /lib/ld-linux-aarch64.so.1 and [libc.so.6]
imports os/user                  dynamic: needs /lib/ld-linux-aarch64.so.1 and [libc.so.6]
net, -tags netgo,osusergo        static: runs in scratch
os/user, -tags netgo,osusergo    static: runs in scratch
```

`net` links the C library's resolver (`getaddrinfo`) for DNS, and `os/user` links its user lookups. Almost every service imports `net` (through `net/http`, database drivers, Redis clients), so with cgo on, almost every service is dynamic. The `netgo` and `osusergo` build tags select the pure-Go versions; `CGO_ENABLED=0` selects them automatically and also forbids any other cgo.

### Step 3: what the kernel does with a dynamic binary

You don't need `ldd` (which isn't in minimal images, and runs the loader itself) to tell the two apart. The standard library can read ELF headers, from any OS:

`isstatic/main.go`

```go noverify
// isstatic reports whether Linux binaries need a dynamic loader.
// It reads the ELF program headers: a PT_INTERP entry names the loader
// the kernel must run first. No PT_INTERP means the binary is static.
package main

import (
	"debug/elf"
	"fmt"
	"os"
)

func main() {
	for _, path := range os.Args[1:] {
		f, err := elf.Open(path)
		if err != nil {
			fmt.Printf("%-14s not an ELF binary: %v\n", path, err)
			continue
		}
		interp := ""
		for _, p := range f.Progs {
			if p.Type == elf.PT_INTERP {
				b := make([]byte, p.Filesz)
				p.ReadAt(b, 0)
				interp = string(b[:len(b)-1]) // drop the trailing NUL
			}
		}
		libs, _ := f.ImportedLibraries()
		if interp == "" {
			fmt.Printf("%-14s static: runs in scratch\n", path)
		} else {
			fmt.Printf("%-14s dynamic: needs %s and %v\n", path, interp, libs)
		}
		f.Close()
	}
}
```

Run on the Mac against three ledger builds:

```text
$ go run ./isstatic ledger-static ledger-cgo ledger-darwin
ledger-static  static: runs in scratch
ledger-cgo     dynamic: needs /lib/ld-linux-aarch64.so.1 and [libc.so.6]
ledger-darwin  not an ELF binary: bad magic number '[207 250 237 254]' in record at byte 0x0
```

The last line is a reminder that macOS binaries are Mach-O files, and they're never fully static: Go on macOS always calls the system through `libSystem`, even with `CGO_ENABLED=0` (`otool -L` lists it). "Static" is a Linux (and BSD) idea.

### Step 4: the rule

For Linux release builds and containers, **set `CGO_ENABLED=0` explicitly.** Don't depend on the defaults in the table: the same Dockerfile gives a static binary in `golang:1.27-alpine` and a dynamic one in `golang:1.27`.

<BeforeAfter
  badLabel="relies on the default"
  goodLabel="says what it means"
  bad={`FROM golang:1.27 AS build
RUN go build -o /out/ledger ./cmd/ledger
# cgo on (gcc present) + net imported
# = dynamic. In scratch:
# exec /ledger: no such file or directory`}
  good={`FROM golang:1.27 AS build

When you genuinely need cgo (SQLite via `mattn/go-sqlite3`, a C library with no Go equivalent), build in an image with the same C library as the one you run on, and ship on `distroless/base` (glibc) rather than `scratch`. Or pick a pure-Go alternative (`modernc.org/sqlite`) and keep the static build.

**Recap.** cgo defaults to on for native builds with a C compiler present, and `net` or `os/user` then make the binary dynamic. A dynamic binary names a loader in `PT_INTERP`; `scratch` doesn't have it, hence "no such file or directory". Set `CGO_ENABLED=0` explicitly.

## Build Metadata & Stamping

*Stop 3 of 5.*

A payment fails in production at 3 a.m. First question: which build is running? A binary should be able to answer that about itself.

### Step 1: what Go records for you

Every binary built in module mode carries **build info**: the Go version, the main module and its version, every dependency's version, and the build settings. Inside a git checkout it also records the commit. Read it from outside with `go version -m`, or from inside with `runtime/debug.ReadBuildInfo`:

```text
$ go version -m ledger-linux-arm64
ledger-linux-arm64: go1.27.0
	path	meridian/ledger/cmd/ledger
	mod	meridian/ledger	v1.4.2
	dep	github.com/jackc/pgx/v5	v5.11.0	h1:IzBBtyK9AHqf98cctWFifYSci2hgQR/cd56wB4p+ogg=
	…
	build	-trimpath=true
	build	CGO_ENABLED=0
	build	GOARCH=arm64
	build	GOOS=linux
	build	GOARM64=v8.0
	build	vcs=git
	build	vcs.revision=e1a4d84912b8d728ad279fe1b6558671510b21c8
	build	vcs.time=2026-09-26T12:57:39Z
	build	vcs.modified=false
```

The `mod` line's version is newer than most tutorials know about. **Since Go 1.24, `go build` sets the main module's version from git**, instead of always writing the placeholder `(devel)`. Four builds of the ledger repository showed every case:

| Checkout state | Recorded version |
|---|---|
| Exactly at tag `v1.4.2`, clean | `v1.4.2` |
| At `v1.4.2` with uncommitted edits | `v1.4.2+dirty` |
| One commit after `v1.4.2` | `v1.4.3-0.20260926125742-0afed8922e5d` (a pseudo-version: next patch, timestamp, 12-character commit) |
| Built with `-buildvcs=false`, or via `go run` | `(devel)` |

`vcs.*` settings have been recorded since Go 1.18. `go run` and `go test` don't record VCS information, and in a Docker build the `.git` directory usually isn't in the build context at all, so there the version is `(devel)` and the revision is missing. That's the gap `-ldflags -X` fills.

### Step 2: stamping your own values with `-X`

<Define term="-ldflags -X (build stamping)">
`-ldflags` passes flags to the linker. `-X importpath.name=value` sets a **package-level string variable** at link time. The variable must be a `var` of type `string` (not a constant) whose initial value, if any, is a constant expression. For package `main` the import path is `main`; for anything else it's the full path, e.g. `-X meridian/ledger/internal/build.Version=v1.4.2`.
</Define>

```go
package main

// Set at link time: -ldflags "-X main.version=v1.4.2 -X main.commit=0afed89"
var (
	version = "dev"
	commit  = "unknown"
)
```

```bash
go build -ldflags "-X main.version=v1.4.2 -X main.commit=$(git rev-parse --short HEAD)" ./cmd/ledger
```

ch25's Docker build used exactly this, passing `--build-arg VERSION` through to `-X`, and `/version` answered `{"commit":"abc123","version":"v1.4.2"}`.

Resist stamping a **build time** with `$(date)`. It makes every build's bytes different (Stop 4), and `vcs.time`, the commit's timestamp, already tells you how old the code is.

The same data from inside a program. Run it here and you'll see `(devel)`, because `go run` doesn't record VCS information:

<GoPlayground>

```go
package main

import (
	"fmt"
	"runtime/debug"
)

func main() {
	info, ok := debug.ReadBuildInfo()
	if !ok {
		fmt.Println("no build info (not built in module mode)")
		return
	}
	fmt.Println("go:     ", info.GoVersion)
	fmt.Println("module: ", info.Main.Path, info.Main.Version)

		switch s.Key {
		case "CGO_ENABLED", "GOOS", "GOARCH", "-trimpath", "vcs.revision", "vcs.modified":

		}
	}
}
```

</GoPlayground>

On a Mac, `go run .` printed `module: bi (devel)`, `CGO_ENABLED=1`, `GOOS=darwin`; adding `CGO_ENABLED=0 go run -trimpath .` added `-trimpath=true` and flipped `CGO_ENABLED=0`. The settings are the build's own record of how it was made.

### Step 3: `-s -w`

`-s` drops the symbol table and `-w` drops DWARF debug information. Measured on the linux/arm64 ledger:

| Flags | Size |
|---|---|
| none | 17.2 MB |
| `-w` | 13.3 MB |
| `-s` | 11.9 MB |
| `-s -w` | 11.9 MB |

`-s` alone gives the same result as both, because since Go 1.22 `-s` also implies `-w`; `-s -w` remains the common spelling. Stripped binaries still print full panic stack traces (Go keeps its own function tables for that), but debuggers like Delve and profilers that need DWARF lose information, so keep debug builds unstripped.

**Recap.** Go records the Go version, dependencies, build settings and, in a git checkout, the commit and (since 1.24) a tag-derived module version. `-X` stamps what Go can't see, like a CI-provided release version. Don't stamp timestamps. `-s` shrinks the binary about 30%.

## Reproducible Builds

*Stop 4 of 5.*

<Define term="Reproducible build">
Building the same source with the same toolchain and flags produces **bit-for-bit identical** output, whoever builds it and wherever. Then anyone can rebuild a release and compare checksums, and a signature on one build vouches for all of them.
</Define>

Since Go 1.21 the toolchain itself is reproducible, and Go builds are deterministic by default. What leaks the builder's environment into the bytes is mostly **file paths**.

### Step 1: the experiment

Same commit, cloned to two different directories, built for linux/arm64 with and without `-trimpath`; then built once more inside a Linux container at a third path:

```text
1e5b14476a269830  ledger-plain      (path A, no -trimpath)
cdbb76b3ccce1bc4  clone-plain       (path B, no -trimpath)
8861f5432cd24f9d  ledger-trim       (path A, -trimpath)
8861f5432cd24f9d  clone-trim        (path B, -trimpath)
8861f5432cd24f9d  (Linux container, /work/somewhere/else, -trimpath)
```

(First 16 hex digits of each SHA-256.) Without `-trimpath` the binaries differ. With it, a Mac and a Linux container produced the same bytes.

### Step 2: the other ingredients

- **The same toolchain.** A different Go version compiles differently. Pin it: the `go` line in `go.mod` sets the minimum, and a `toolchain` line (Go 1.21+) picks the exact release the `go` command should use, downloading it if needed:

  ```text
  module meridian/ledger

  go 1.27

  toolchain go1.27.0
  ```

- **The same flags and environment.** `CGO_ENABLED`, `GOOS`, `GOARCH`, `-ldflags` and tags all change the output. Put them in one script or config (GoReleaser, next stop) rather than typing them.
- **No timestamps or random values in `-X`.** `-X main.buildTime=$(date)` guarantees every build differs.
- **cgo off.** With cgo, the host's C compiler and libraries become inputs too.

To make `-trimpath` the default for every command in a CI job, set `GOFLAGS=-trimpath`.

<Callout kind="note" title="Supply chain beyond the binary">

`go.sum` pins each dependency's content hash, the module proxy and checksum database make those hashes globally consistent, and `govulncheck` checks what you depend on for known vulnerabilities. That broader story is Part 2, Chapter 15.

</Callout>

**Recap.** Go builds are deterministic; absolute paths are what differ between machines. `-trimpath` plus a pinned toolchain and fixed flags gave identical bytes on a Mac and in a Linux container. Keep timestamps out of `-X`.

<Exercise n={2} title="A /version endpoint from build info" level="medium">

Write an HTTP handler that returns JSON with `version`, `go`, `revision` and `dirty`, using `debug.ReadBuildInfo` and an optional `-X`-stamped `version` variable, and never panics when the information is missing.

<Solution>

```go
package main

import (
	"encoding/json"
	"fmt"
	"net/http"
	"net/http/httptest"
	"runtime/debug"
)

var version = "" // optional: -ldflags "-X main.version=v1.4.2"

func versionHandler(w http.ResponseWriter, r *http.Request) {
	resp := map[string]any{"version": "dev", "go": "unknown", "revision": "unknown", "dirty": false}
	if info, ok := debug.ReadBuildInfo(); ok {
		resp["go"] = info.GoVersion
		if v := info.Main.Version; v != "" && v != "(devel)" {
			resp["version"] = v
		}
		for _, s := range info.Settings {
			switch s.Key {
			case "vcs.revision":
				resp["revision"] = s.Value
			case "vcs.modified":
				resp["dirty"] = s.Value == "true"
			}
		}
	}
	if version != "" {
		resp["version"] = version // an explicit stamp wins
	}
	w.Header().Set("Content-Type", "application/json")
	json.NewEncoder(w).Encode(resp)
}

func main() {
	rec := httptest.NewRecorder()
	versionHandler(rec, httptest.NewRequest("GET", "/version", nil))
	fmt.Print(rec.Body.String())
}
```

Under `go run` this prints `{"dirty":false,"go":"go1.27.0","revision":"unknown","version":"dev"}`. Built from a clean tagged checkout, `version` and `revision` fill in with no flags at all. Serve it on an internal port: dependency versions and commits help attackers too.

</Solution>

</Exercise>

<Exercise n={3} title="Prove a build is reproducible" level="medium">

Write a script that checks a commit builds reproducibly: clone it into two temporary directories, build each with the release flags, and compare SHA-256 sums.

<Solution>

```bash
#!/bin/sh
set -eu
rev=${1:-HEAD}
repo=$(git rev-parse --show-toplevel)
a=$(mktemp -d); b=$(mktemp -d)
git clone -q "$repo" "$a/src"; git -C "$a/src" checkout -q "$rev"
git clone -q "$repo" "$b/src"; git -C "$b/src" checkout -q "$rev"

build() {
  (cd "$1/src" && CGO_ENABLED=0 GOOS=linux GOARCH=arm64 \
    go build -trimpath -ldflags "-s -w" -o "$1/ledger" ./cmd/ledger)
}
build "$a"; build "$b"

sha_a=$(shasum -a 256 "$a/ledger" | cut -d' ' -f1)
sha_b=$(shasum -a 256 "$b/ledger" | cut -d' ' -f1)
echo "$sha_a"; echo "$sha_b"
[ "$sha_a" = "$sha_b" ] && echo reproducible || { echo DIFFERENT; exit 1; }
```

Drop `-trimpath` and it prints `DIFFERENT`, because the two directories' paths end up in the binaries. The strongest version of this check runs the second build on a different machine or OS, as Stop 4 did with a Linux container.

</Solution>

</Exercise>

<Exercise n={5} title="When you need cgo" level="hard">

The ledger adds `mattn/go-sqlite3` (a cgo SQLite binding) for a local cache. Builds for scratch now fail. Give two ways forward and what each costs.

<Solution>

1. **Switch to a pure-Go driver**, `modernc.org/sqlite` (SQLite translated to Go). The build stays static, cross-compilation keeps working, and `scratch` still works. Costs: a larger binary and some performance difference from the C original; measure for your workload.

2. **Keep cgo and build for it.** Build in an image with a C compiler and the same C library family you'll run on (for example `golang:1.27` for glibc), with `CGO_ENABLED=1`, and run on `gcr.io/distroless/base-debian12` (which contains glibc) instead of `scratch`. Costs: cross-compiling now needs a C cross-compiler for each target (or native builders per architecture, or `zig cc` as a cross C compiler), `-trimpath` alone no longer makes builds reproducible because the C toolchain is an input, and you inherit C-library security updates.

A third option, fully static cgo binaries against musl (`-ldflags '-linkmode external -extldflags "-static"'` on Alpine), exists but has sharp edges: glibc doesn't support static linking well (notably for DNS and user lookups), which is why it's usually done with musl.

</Solution>

</Exercise>

<Recap>

- **Cross-compile** with `GOOS`/`GOARCH`: 47 targets, no cross-toolchain, because Go's runtime, system calls and linker don't need the target's C tools.
- **cgo** defaults on for native builds when a C compiler exists, and off when cross-compiling or when none exists. Importing `net` or `os/user` with cgo on makes a **dynamic** binary.
- A dynamic binary names a loader in **`PT_INTERP`**; `scratch` lacks it, hence `no such file or directory`. Set **`CGO_ENABLED=0`** explicitly. macOS binaries always use `libSystem`.
- Go records build info: settings, dependencies, and in git checkouts the commit and (since 1.24) a tag-derived version like `v1.4.2+dirty`. Read it with `go version -m` or `debug.ReadBuildInfo`; stamp the rest with **`-X`**, never with timestamps.
- **`-trimpath`** removes absolute paths: the same commit built identical bytes on a Mac and in a Linux container. Pin the toolchain, fix the flags.
- **GoReleaser** turns a tag into six static, stamped builds, archives, checksums and a release.

</Recap>
