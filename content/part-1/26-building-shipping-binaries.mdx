## Cross-Compilation

Picture the ledger service we've been building throughout Part 1. It needs to ship on three targets: the ops team runs `linux/amd64` servers in AWS, the fintech client's on-prem boxes are `linux/arm64` (Graviton), and one rogue architect insists on `darwin/arm64` for local staging. In most languages, "build for three platforms" means setting up three CI machines or fighting Docker multi-arch rigs. In Go, it means one command on your laptop.

<Define term="Cross-compilation (GOOS / GOARCH)" since="Building & Shipping Go Binaries (this chapter)">
**Cross-compilation** means building a binary for a different OS or CPU than the machine you are building on — for example, producing a `linux/arm64` binary on a macOS laptop. `GOOS` names the target operating system; `GOARCH` names the target CPU. Set them before `go build` and the Go toolchain emits a native binary for that target with no external cross-toolchain. This matters because your development machine is rarely the same architecture as your production servers, and Go is the only mainstream language where cross-compilation works out of the box, in seconds, for all first-tier targets.
</Define>

Two environment variables are all it takes:

- **`GOOS`** — the target operating system (`linux`, `darwin`, `windows`, `freebsd`, …)
- **`GOARCH`** — the target CPU architecture (`amd64`, `arm64`, `arm`, `386`, `riscv64`, …)

Set them, run `go build`, get a native binary for that target. No cross-compiler. No sysroot. No `crosstool-ng`. Nothing to install.

```bash title="Build for three platforms — from one laptop"
# Linux / AMD64 (your AWS servers)
GOOS=linux GOARCH=amd64 go build -o ledger-linux-amd64 ./cmd/ledger

# Linux / ARM64 (Graviton)
GOOS=linux GOARCH=arm64 go build -o ledger-linux-arm64 ./cmd/ledger

# macOS / Apple Silicon (local staging)
GOOS=darwin GOARCH=arm64 go build -o ledger-darwin-arm64 ./cmd/ledger
```

Run `go tool dist list` to see the full supported matrix — as of Go 1.26 it's over 50 OS/arch combinations:

```bash
go tool dist list
# android/amd64
# android/arm64
# darwin/amd64
# darwin/arm64
# linux/amd64
# linux/arm64
# linux/riscv64
# windows/amd64
# windows/arm64
# ... (50+ more)
```

<UnderTheHood title="Why Go cross-compiles so easily — the pure-Go runtime">

Most languages require a cross-toolchain because their runtime is written in C and must be compiled *for* the target with a matching C compiler and sysroot. Go's runtime — the scheduler, GC, memory allocator, stack management — is written almost entirely in **Go itself** (and a small amount of hand-written architecture-specific assembly that ships with the toolchain). When you install the Go toolchain, you get the source for every OS/arch combination. Running `go build` for a different target just picks a different code-generation backend inside the same `gc` compiler binary, emits the matching runtime, and links everything together.

**The key insight**: when `CGO_ENABLED=0` (which we'll cover in depth next), there is *no external linker call*. The Go toolchain uses its own linker, which knows how to emit ELF (Linux), Mach-O (macOS), or PE/COFF (Windows) without any host-side system libraries. You're not asking the host OS's `ld` to do anything. That's why it works cross-platform without a cross-toolchain. As of Go 1.26, this covers all first-tier platforms (linux/amd64, linux/arm64, darwin/arm64, windows/amd64, etc.).

</UnderTheHood>

  <ConceptCard label="GOARCH">Target CPU architecture. Controls code generation and which `_amd64.go` / `_arm64.go` assembly stubs are selected. Becomes `runtime.GOARCH`.</ConceptCard>
  <ConceptCard label="go tool dist list">Lists all valid `GOOS/GOARCH` combinations the installed toolchain can target. Filter with `grep` for what you need: `go tool dist list | grep linux`.</ConceptCard>

</ConceptGrid>

<Define term="CGO_ENABLED — static vs dynamic binary" since="Building & Shipping Go Binaries (this chapter)">
`CGO_ENABLED` is a build environment variable that controls whether the Go toolchain is allowed to call into C code via cgo. When it is `1` (the default for host builds), any package that uses cgo — including `net` and `os/user` from the standard library — will link against the system C library (libc), producing a **dynamically linked** binary that depends on libc being present at runtime. When it is `0`, the toolchain uses pure-Go reimplementations of those packages and its own linker, producing a **fully static** binary with no external `.so` dependencies. Why it matters: `FROM scratch` and distroless container images contain no libc, no dynamic linker, nothing. A dynamically linked Go binary in a scratch image crashes at startup with `no such file or directory` — the binary is there, its runtime dependency is not. `CGO_ENABLED=0` is the fix.
</Define>

**On the job:** Every time someone on your team says "the container crashes immediately" after a `FROM scratch` deploy, the first question is: was it built with `CGO_ENABLED=0`? It is the number-one cause of scratch container launch failures for Go services.

Stop. Read this section twice. This is the most important thing in the chapter, and it is the most common reason a `FROM scratch` or distroless Docker container crashes at runtime with a message like `exec /app: no such file or directory` — not because your binary doesn't exist, but because the dynamic linker the binary depends on doesn't exist in the container.

Here is what happens by default, and most Go engineers don't realize it until it bites them.

**`CGO_ENABLED` defaults to `1`** when you build for the host OS/arch. The moment cgo activates — sometimes just because you imported `net` or `os/user` and didn't opt out — Go calls into libc for certain operations (DNS resolution, user lookups). Your binary gets *dynamically linked* against glibc. Check it yourself:

```bash
# Build WITHOUT explicitly setting CGO_ENABLED (defaults to 1):
go build -o ledger ./cmd/ledger

# Inspect the dynamic dependencies:
ldd ledger
# linux-vdso.so.1 (0x00007ffe...)
# libc.so.6 => /lib/x86_64-linux-gnu/libc.so.6 (0x00007f...)
# /lib64/ld-linux-x86-64.so.2 (0x00007f...)
```

Now drop that binary into a `FROM scratch` image (which has *zero* OS files, including zero libc). When the container starts, the Linux kernel tries to load the dynamic linker (`/lib64/ld-linux-x86-64.so.2`) to resolve the library dependencies. It's not there. Your container dies instantly with `no such file or directory` — the binary file exists, but its *runtime dependency* doesn't.

Here's the fix. One variable. Build with `CGO_ENABLED=0`:

```bash
CGO_ENABLED=0 go build -o ledger ./cmd/ledger

# Now inspect:
ldd ledger
# not a dynamic executable
# (or: statically linked)
```

With `CGO_ENABLED=0`, the Go toolchain uses its own pure-Go implementations of everything: the pure-Go DNS resolver, the pure-Go user-lookup, the Go linker instead of the system linker. The result is a **fully static binary** — no `.so` dependencies, no dynamic linker needed, no libc required. Drop it in `FROM scratch`. It runs.

<Callout kind="warn" title="The invisible cgo activations — net and os/user">

You don't have to call `import "C"` yourself for cgo to activate. Two standard library packages activate cgo by default when `CGO_ENABLED=1`:

- **`net`** — uses the system resolver (`getaddrinfo` via libc) unless you force the pure-Go resolver with `-tags netgo`.
- **`os/user`** — uses libc's `getpwuid_r` / `getgrnam_r` unless you force `-tags osusergo`.

If your service makes any network call or looks up users, it links against libc — silently. The belt-and-suspenders fix when you need scratch/distroless images: `CGO_ENABLED=0 go build -tags netgo,osusergo ./...`. The `-tags` are redundant when `CGO_ENABLED=0` (the pure-Go paths are chosen unconditionally), but they're good documentation of intent.

</Callout>

Now for the full correct Dockerfile pattern. This is the one you'll write from now on:

```dockerfile title="Dockerfile — correct multi-stage build for scratch"
# Stage 1: build a truly static binary
FROM golang:1.26-alpine AS builder

WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download

COPY . .

RUN CGO_ENABLED=0 GOOS=linux GOARCH=amd64 \
    go build \
    -trimpath \
    -ldflags="-s -w" \
    -o /out/ledger \
    ./cmd/ledger

# Stage 2: zero-footprint runtime image
FROM scratch

COPY --from=builder /out/ledger /ledger
COPY --from=builder /etc/ssl/certs/ca-certificates.crt /etc/ssl/certs/

ENTRYPOINT ["/ledger"]
```

Note the `ca-certificates.crt` copy — even a static Go binary needs the OS certificate bundle to verify TLS. `scratch` doesn't have one. Alpine's builder stage does; copy it in. This is the other thing people forget.

<UnderTheHood title="What cgo actually changes in the link step">

When `CGO_ENABLED=1`, the build process has an extra step: the Go compiler generates C wrapper stubs for any `import "C"` usage, invokes the system C compiler (`gcc` or `clang`) to compile them, and then calls the **system linker** (`ld`) instead of Go's own linker to produce the final binary. Because the system linker is involved, it can resolve symbols from dynamic libraries (`.so` / `.dylib`), and those libraries get recorded as runtime dependencies in the binary's ELF/Mach-O dynamic section.

When `CGO_ENABLED=0`, Go's own linker runs exclusively. It knows about ELF, Mach-O, and PE formats, and it links all Go packages — including the pure-Go reimplementations of `net` and `os/user` — into a single self-contained object with no external symbol references. No `.so` entries in the ELF dynamic section, no `PT_INTERP` segment pointing at `ld-linux.so`. The kernel can exec it directly.

**Cross-compilation corollary**: `CGO_ENABLED=0` is also required for cross-compilation in most cases, because the system C compiler on your Mac doesn't know how to compile for `linux/arm64` unless you've installed a cross-toolchain. When cgo is off, there's no C compilation step, so no cross-toolchain is needed. This is why `CGO_ENABLED=0 GOOS=linux GOARCH=arm64 go build` works out of the box and `CGO_ENABLED=1 GOOS=linux GOARCH=arm64 go build` doesn't (without significant extra setup). As of Go 1.26, cross-compilation with `CGO_ENABLED=0` is officially first-class and fully supported for all tier-1 targets.

</UnderTheHood>

## Build Metadata & Stamping

Your ledger service is in production. A transaction fails and the on-call engineer needs to know: which build is running? What commit? When was it deployed? If the binary can't answer those questions itself, you're flying blind.

Go gives you two mechanisms. Use both.

<Define term="-ldflags (build stamping)" since="Building & Shipping Go Binaries (this chapter)">
`-ldflags` passes flags directly to the Go linker at build time. The most useful sub-flag is `-X pkg.Var=value`, which **injects a string value into a named package-level variable** without any source code change. You use it to stamp a binary with its version, commit hash, and build timestamp at the moment you build it. The variable exists in source with a safe zero-value default (e.g. `"dev"`); CI overwrites it with the real tag and commit. Why it matters: a binary that cannot tell you what version it is makes incident response and rollback guesswork. `-s` and `-w` are commonly combined with `-X`: `-s` strips the symbol table; `-w` strips DWARF debug info. Both shrink the binary for production; omit them in dev builds where you want `delve` to work.
</Define>

### Stamping with `-ldflags -X`

The linker can inject string values directly into package-level variables at build time. This is how every serious Go service ships version information:

```go title="cmd/ledger/version.go"
package main

// These are set by the linker at build time via -ldflags.
// Their zero values ("dev", "none", "unknown") are safe defaults for local development.
var (
	version   = "dev"
	commit    = "none"
	buildTime = "unknown"
)
```

```bash title="Stamping the binary at build time"
go build \
  -ldflags="-X main.version=1.4.2 \
             -X main.commit=$(git rev-parse --short HEAD) \
             -X main.buildTime=$(date -u +%Y-%m-%dT%H:%M:%SZ)" \
  -o ledger \
  ./cmd/ledger
```

The `-X main.version=1.4.2` flag tells the linker to replace the string value of `main.version` at link time. No source code changes, no generated files, no init functions — the variable just has the right value when `main()` starts.

<Define term="runtime/debug.ReadBuildInfo" since="Building & Shipping Go Binaries (this chapter)">
`runtime/debug.ReadBuildInfo()` reads the build metadata that the Go toolchain automatically embeds in binaries: the Go version, module path, and dependency versions (present since the Go modules era), plus VCS fields (`vcs.revision`, `vcs.time`, `vcs.modified` — auto-embedded since Go 1.18). It returns a `*debug.BuildInfo` and a bool. The `Settings` slice contains key-value pairs for every build setting recorded — including `CGO_ENABLED`, `GOOS`, `GOARCH`, and the VCS fields. You use it in a `/debug/version` HTTP endpoint so ops can confirm exactly which build is handling traffic, which commit it was built from, and whether the working tree was dirty.
</Define>

### Reading VCS info with `runtime/debug.ReadBuildInfo`

Since Go 1.18, the toolchain automatically embeds **version-control** metadata in every binary built from a VCS checkout — the commit hash, whether there were uncommitted changes, the build timestamp, and more. The module path and dependency versions have been part of `BuildInfo` since module builds existed (well before 1.18); 1.18 added the VCS fields on top. You read it all with `runtime/debug.ReadBuildInfo()`:

<GoPlayground>

```go
package main

import (
	"fmt"
	"runtime/debug"
)

// Simulate the ldflags-stamped variables (in a real binary these are set by -ldflags)
var (
	version   = "dev"
	commit    = "none"
	buildTime = "unknown"
)

func buildInfo() string {
	info, ok := debug.ReadBuildInfo()
	if !ok {
		return "build info unavailable"
	}

	// Extract VCS settings Go embedded automatically (available since Go 1.18)
	vcsRevision := "(unknown)"
	vcsTime := "(unknown)"
	vcsDirty := false
	for _, s := range info.Settings {
		switch s.Key {
		case "vcs.revision":
			vcsRevision = s.Value
		case "vcs.time":
			vcsTime = s.Value
		case "vcs.modified":
			vcsDirty = s.Value == "true"
		}
	}

	dirty := ""
	if vcsDirty {
		dirty = " (dirty)"
	}

	return fmt.Sprintf(
		"version=%s commit=%s buildTime=%s | vcs.revision=%s%s vcs.time=%s go=%s",
		version, commit, buildTime,
		vcsRevision, dirty, vcsTime,
		info.GoVersion,
	)
}

func main() {
	// In the playground there's no VCS context, so vcs fields will be "(unknown)".
	// In a real binary built from a git repo they carry the real commit/time/dirty flag.
	fmt.Println(buildInfo())
}
```

</GoPlayground>

The `info.Settings` slice contains all build settings Go recorded — including `GOOS`, `GOARCH`, `CGO_ENABLED`, and the VCS fields. A running service can expose this on an internal `/debug/version` endpoint, letting ops confirm exactly which build is handling traffic.

<Callout kind="pro" title="Go 1.18+ embeds VCS automatically — no extra build step needed">

Since Go 1.18, if you build from a git repository, Go embeds `vcs.revision` (full commit hash), `vcs.time` (commit timestamp), and `vcs.modified` (whether there were uncommitted changes) automatically — with no `-ldflags` required. The `-ldflags -X` approach adds *your own* version string (like a SemVer tag) on top of what Go already embeds. The combination gives you both a human-readable release label and the exact commit for forensics.

</Callout>

### Stripping symbols: `-s -w`

You'll often see `-ldflags="-s -w"` alongside the stamping flags:

- **`-s`** — strip the symbol table and debug information from the binary (shrinks the binary significantly)
- **`-w`** — strip DWARF debugging information

Use these for production release builds. Omit them for development builds where you want `delve` to work properly. Note: as of Go 1.25, the default debug format is DWARF5, which is more compact; `-w` still strips it entirely when you need the smallest possible binary.

<Exercise n={2} title="Expose build info over HTTP" level="medium">

Write a handler `versionHandler` that calls `runtime/debug.ReadBuildInfo()` and responds with a JSON object containing `version`, `goVersion`, `vcsRevision`, and `vcsDirty`. Use `encoding/json` and the standard `net/http` types. Assume `version` is a package-level var stamped by `-ldflags`.

<Solution>

```go
package main

import (
	"encoding/json"
	"net/http"
	"runtime/debug"
)

var version = "dev"

type versionResponse struct {
	Version     string `json:"version"`
	GoVersion   string `json:"goVersion"`
	VCSRevision string `json:"vcsRevision"`
	VCSDirty    bool   `json:"vcsDirty"`
}

func versionHandler(w http.ResponseWriter, r *http.Request) {
	resp := versionResponse{Version: version}

	if info, ok := debug.ReadBuildInfo(); ok {
		resp.GoVersion = info.GoVersion
		for _, s := range info.Settings {
			switch s.Key {
			case "vcs.revision":
				resp.VCSRevision = s.Value
			case "vcs.modified":
				resp.VCSDirty = s.Value == "true"
			}
		}
	}

	w.Header().Set("Content-Type", "application/json")
	_ = json.NewEncoder(w).Encode(resp)
}
```

Wire it: `http.HandleFunc("GET /debug/version", versionHandler)`. Internal only — don't expose this on the public port. The `encoding/json/v2` package landed as an experiment in Go 1.25 (`GOEXPERIMENT=jsonv2`); for production use `encoding/json` is still the stable choice here.

</Solution>

## Reproducible Builds

<Define term="Reproducible build (-trimpath)" since="Tooling & Engineering Hygiene (Part 2)">
A **reproducible build** produces bit-for-bit identical binaries whenever the same source, toolchain version, and build flags are used — regardless of who builds it or where. Without it, two CI runs on the same commit can produce binaries with different SHA256 checksums, making supply-chain audits and artifact signing meaningless. The primary culprit in Go is absolute source paths embedded in debug info. `-trimpath` removes them, recording only module-relative paths. Pinning the Go toolchain version via the `toolchain` directive in `go.mod` eliminates the other main source of non-determinism.
</Define>

Here is the uncomfortable truth: two engineers running `go build` on the same commit, on different machines, at different times, may produce binaries with different checksums. The binary behavior is identical, but the bytes differ — embedded timestamps, absolute paths in debug info, and subtle toolchain differences all contaminate the output. That's a supply-chain problem: you can't audit what you shipped.

Go 1.26 gives you the tools to fix this.

### `-trimpath`

The single most important flag for reproducibility. Without it, the binary embeds **absolute source paths** (e.g., `/home/abbey/src/ledger/cmd/ledger/main.go`) in the debug information. Those differ by developer. With `-trimpath`, all paths are recorded relative to the module root:

```bash
go build -trimpath -o ledger ./cmd/ledger
```

Always use `-trimpath` for release builds. It also slightly reduces binary size, and it prevents leaking your CI machine's directory structure in the binary.

### Pinned toolchain via `go.mod`

Go 1.21 introduced the `toolchain` directive in `go.mod`, letting you pin the exact Go toolchain version:

```text title="go.mod (excerpt)"
module github.com/yourco/ledger

go 1.26

toolchain go1.26.0
```

With this in place, anyone who runs `go build` (or any `go` command) in this module gets Go 1.26.0 specifically — no "works on my machine" toolchain drift. The Go toolchain will download the pinned version automatically if needed.

### `GOFLAGS` for defaults

If you want `-trimpath` to be the default for all builds in a CI environment without modifying every build script:

```bash
export GOFLAGS="-trimpath"
go build -o ledger ./cmd/ledger  # implicitly adds -trimpath
```

<Callout kind="note" title="Reproducibility and supply-chain hygiene (see Part 2)">

Full reproducibility goes deeper: `go.sum` pins dependency checksums, module proxies cache exact zip files, `govulncheck` scans for known CVEs. All of that lives in the **Tooling & Engineering Hygiene** chapter in Part 2 (`tooling-engineering-hygiene`), which is the right home for the broader supply-chain story. Here we're covering the binary build side.

</Callout>

## Releasing with GoReleaser

<Define term="GoReleaser" since="Building & Shipping Go Binaries (this chapter)">
**GoReleaser** is a release automation tool for Go projects. A single `.goreleaser.yaml` config drives the whole release pipeline: cross-compile for every `GOOS`/`GOARCH` pair, produce `.tar.gz`/`.zip` archives, generate a SHA256 checksum file, and create a GitHub (or GitLab/Gitea) release with all artifacts attached — triggered by pushing a git tag. It injects the version tag, commit hash, and build date into your `-ldflags` automatically via template variables. Why it matters: doing this by hand means forgetting a checksum, shipping a non-static binary for one platform, or mis-stamping the version. GoReleaser makes the release repeatable and auditable, and it is the standard last-mile tool for any Go CLI or service distributed as a binary.
</Define>

You have a ledger CLI. You want tagged releases on GitHub: checksummed `linux/amd64` and `linux/arm64` and `darwin/arm64` binaries, a `CHANGELOG` entry, a GitHub release with assets attached, and a Homebrew formula. Doing this by hand is tedious and error-prone. **GoReleaser** handles all of it in one `goreleaser release` command triggered by a git tag.

Install it:

```bash
# macOS
brew install goreleaser

# Linux / CI
curl -sfL https://goreleaser.com/static/run | bash
```

Initialize a config at the repo root:

```bash
goreleaser init
# creates .goreleaser.yaml
```

Here is the `.goreleaser.yaml` for the ledger service, annotated:

```yaml title=".goreleaser.yaml"
version: 2

# Which Go binary to build and which targets to cross-compile
builds:
  - id: ledger
    binary: ledger
    main: ./cmd/ledger
    env:
      - CGO_ENABLED=0          # static binary — required for scratch images
    goos:
      - linux
      - darwin
      - windows
    goarch:
      - amd64
      - arm64
    flags:
      - -trimpath              # reproducible — strip absolute paths
    ldflags:
      # stamp version, commit, build time into the binary
      - -s -w
      - -X main.version={{ .Version }}
      - -X main.commit={{ .Commit }}
      - -X main.buildTime={{ .Date }}

# Produce a SHA256 checksum file alongside the archives
checksum:
  name_template: "{{ .ProjectName }}_checksums.txt"
  algorithm: sha256

# Create a GitHub Release and upload the archives + checksum
release:
  github:
    owner: yourco
    name: ledger

# Optional: generate a Homebrew formula for the macOS binaries
brews:
  - name: ledger
    homepage: https://github.com/yourco/ledger
    repository:
      owner: yourco
      name: homebrew-tap
```

To make a release: tag, push, let GoReleaser run (typically in CI):

```bash
git tag v1.4.2
git push origin v1.4.2

# In CI (or locally with a GITHUB_TOKEN env var set):
goreleaser release --clean
```

GoReleaser runs `go build` for every `goos`/`goarch` combination, packages them as `.tar.gz` / `.zip`, generates `ledger_checksums.txt` with SHA256 hashes, and creates the GitHub release with all assets attached. The `{{ .Version }}`, `{{ .Commit }}`, and `{{ .Date }}` template variables are filled in automatically from the git tag and commit.

- `-s -w` — strip symbol table and DWARF, smallest possible binary

<Recap>

You now own the full binary shipping pipeline:

- **Cross-compilation**: `GOOS` + `GOARCH` + `go build` = a native binary for any of 50+ targets, from any machine, in seconds — because Go's runtime is pure Go and its own linker needs no cross-toolchain when cgo is off.
- **The cgo static-binary trap**: `CGO_ENABLED` defaults to `1`. Even innocuous imports (`net`, `os/user`) can silently link against libc, making your binary dynamically linked — which crashes instantly in `FROM scratch` / distroless images. Fix: `CGO_ENABLED=0`. Always. For containers.
- **Build stamping**: `-ldflags "-X main.version=..."` injects strings at link time. `runtime/debug.ReadBuildInfo()` reads them back plus the VCS metadata Go has embedded automatically since 1.18 (`vcs.revision`, `vcs.time`, `vcs.modified`).
- **Reproducibility**: `-trimpath` removes absolute source paths, `toolchain go1.26.0` in `go.mod` pins the toolchain. Two machines, same commit, same binary.
- **GoReleaser**: one YAML config turns a tagged commit into cross-compiled archives, SHA256 checksums, and a GitHub release — the last mile for any CLI or service shipped as a binary.

</Recap>
