## The testing Package

*Stop 1 of 12.*

<Define term="Unit test (testing.T)" since="Testing in Go (this chapter)">
A **unit test** exercises one function or method in isolation — no real database, no real network, no real clock. It receives a `*testing.T`, calls your code with controlled inputs, and fails if the output is wrong. The point: instant, deterministic feedback on a single unit of behaviour. Get it wrong and you find out in milliseconds, not in a production incident at 3 a.m.
</Define>

Every Go test lives in a file whose name ends in `_test.go`. The build tool ignores these files during normal builds and includes them only when you run `go test`. That's the whole contract — no test runner to install, no config file, no decorators. Just files and the `testing` package.

Here's the minimal shape:

```go
// ledger_test.go
package ledger_test // use the _test suffix for black-box testing (recommended)

import "testing"

func TestDeposit(t *testing.T) {
    t.Log("testing the Deposit function") // only shown on failure or with -v
}
```

The function name **must** start with `Test` (capital T), and its only parameter is `*testing.T`. That's it. The Go tool finds and runs it automatically.

Run it with:

```
go test ./...          # run all tests in this module
go test -v ./...       # verbose: show names + logs even on pass
go test -run TestDeposit ./... # run only tests matching a regex
```

### The three testing types at a glance

<ConceptGrid cols={3}>
  <ConceptCard label="*testing.T">Unit and integration tests. `t.Errorf` marks a failure but keeps running; `t.Fatalf` marks a failure and stops the current test immediately.</ConceptCard>
  <ConceptCard label="*testing.B">Benchmarks — functions starting with `Bench`. The test runner controls loop count via `b.N` and reports ns/op, allocs/op, B/op.</ConceptCard>
  <ConceptCard label="*testing.F">Fuzz targets — functions starting with `Fuzz`. You provide seed corpus entries; the engine mutates inputs to find panics or failed invariants.</ConceptCard>
  <Gotcha>Never call `os.Exit` in a test function — it bypasses `t.Cleanup`, skips deferred calls, and corrupts the test runner's output. Use `t.Fatalf` to stop a test; let `TestMain` call `os.Exit(m.Run())`.</Gotcha>
</ConceptGrid>

### TestMain — suite-level setup and teardown

`TestMain` runs before the test suite and hands you the entire binary's lifecycle. The classic use: start a real database once, run all tests, shut it down.

```go
// ledger_integration_test.go
package ledger_test

import (
    "os"
    "testing"
)

// TestMain is the test binary's entry point when present.
// m.Run() returns the exit code; we must call os.Exit with it.
func TestMain(m *testing.M) {
    // suite-level setup goes here — e.g., start a Postgres container
    setup()

    code := m.Run() // runs all Test*, Bench*, Fuzz* in this package

    // suite-level teardown — guaranteed to run even if tests panic
    teardown()

    os.Exit(code)
}

func setup()    { /* start testcontainer, run migrations */ }
func teardown() { /* stop container */ }
```

### t.Helper and t.Cleanup

Two unsung heroes you'll use constantly:

- **`t.Helper()`** — marks a function as a test helper. When a test fails inside it, the stack trace points to the *caller* (the actual test line), not to the helper. This is the difference between `assert.go:12` and `ledger_test.go:47` in your failure output. Always call it at the top of any helper function.
- **`t.Cleanup(fn)`** — registers a function to run when the test (and all its subtests) finish, regardless of pass/fail. Like `defer`, but scoped to the test. Use it to close files, cancel contexts, stop servers — anything you'd put in a `defer` but need in a helper where `defer` would be tricky.

```go
// createTestLedger is a test helper that sets up a fresh in-memory ledger.
func createTestLedger(t *testing.T) *Ledger {
    t.Helper() // ← marks this as a helper for cleaner failure output

    l := NewLedger()
    t.Cleanup(func() {
        // runs when the calling test finishes — even if it fails
        l.Close()
    })
    return l
}
```

<Callout kind="pro" title="t.Helper() is not optional">
If you skip `t.Helper()`, every failure in your helper prints the helper's line number. With a codebase full of helpers, this is maddening — the failure points nowhere useful. Always mark helpers. It costs one line.
</Callout>

<ELI5
  concept="Table-driven tests"
  analogy="One inspection checklist, run against every item on the line."
  role="reader"
>

The obvious way to test five cases is to write five test functions. They end up near-identical, and when the function's signature changes you edit five copies and miss one.

A table-driven test flips it. You write the **cases** as data — a slice of structs, one row per case with its input and expected output — and the **procedure** once, as a loop over that slice. Adding a sixth case is a new row, not a new function.

Two things make it worth doing beyond tidiness. Each row runs inside `t.Run(tc.name, ...)`, so a failure names the exact row that broke rather than a line number. And because the cases are data, the interesting ones — the zero amount, the negative transfer, the value one cent under the limit — sit in a list you can read top to bottom and notice what is missing.

This is the default shape for a Go test. If you find yourself copying a test function and editing two literals, you wanted a table.

</ELI5>

## Table-Driven Tests

*Stop 2 of 12.*

<Define term="Table-driven test" since="Testing in Go (this chapter)">
A **table-driven test** defines a slice of test cases (the "table") — each row is one scenario: inputs, expected outputs, and a name. A single `for` loop iterates the rows and runs each as a named subtest via `t.Run`. One function, every edge case named and visible. Get one wrong and the failure output tells you exactly which row: `--- FAIL: TestDeposit/negative_amount`. Without table-driven tests you write a separate `TestDeposit_NegativeAmount`, `TestDeposit_Zero`, etc. — duplicate setup, harder to compare cases at a glance, impossible to add a new case without a new function.
</Define>

The single most important testing pattern in Go. Not optional. Not a style preference. The canonical way to test any function with multiple inputs.

**The scenario:** Our ledger's `Deposit(accountID string, amountCents int64) error` function needs to be correct across many inputs — positive amounts, zero, negative, the account not existing. Writing a separate `TestDeposit_*` for each case means duplicating setup code and making it hard to see the full behavior at once. Table-driven tests fix this.

```go
// ledger_test.go
package ledger_test

import (
    "errors"
    "testing"
)

func TestDeposit(t *testing.T) {
    // The test table — each row is one scenario.
    // Named fields prevent positional mistakes when the table grows.
    tests := []struct {
        name        string
        accountID   string
        amountCents int64
        wantErr     bool
    }{
        {
            name:        "valid deposit",
            accountID:   "acc-001",
            amountCents: 10000, // $100.00 in cents
            wantErr:     false,
        },
        {
            name:        "zero amount",
            accountID:   "acc-001",
            amountCents: 0,
            wantErr:     true, // zero is not a valid deposit
        },
        {
            name:        "negative amount",
            accountID:   "acc-001",
            amountCents: -500,
            wantErr:     true,
        },
        {
            name:        "unknown account",
            accountID:   "does-not-exist",
            amountCents: 1000,
            wantErr:     true,
        },
    }

    for _, tc := range tests {
        tc := tc // capture range variable — required before Go 1.22 (see Gotcha)
        t.Run(tc.name, func(t *testing.T) {
            ledger := newTestLedger(t) // helper sets up fresh state + Cleanup
            err := ledger.Deposit(tc.accountID, tc.amountCents)

            // Check the error expectation first.
            if tc.wantErr {
                if err == nil {
                    t.Fatalf("Deposit(%q, %d) expected error, got nil",
                        tc.accountID, tc.amountCents)
                }
                return // don't check balance if we expected failure
            }
            if err != nil {
                t.Fatalf("Deposit(%q, %d) unexpected error: %v",
                    tc.accountID, tc.amountCents, err)
            }
        })
    }
}
```

package main

import (
	"errors"
	"fmt"
)

// Minimal in-memory ledger for demo purposes.
type Ledger struct {
	accounts map[string]int64
}

func NewLedger(accounts ...string) *Ledger {
	m := make(map[string]int64)
	for _, a := range accounts {
		m[a] = 0
	}
	return &Ledger{accounts: m}
}

func (l *Ledger) Deposit(accountID string, amountCents int64) error {
	if amountCents <= 0 {
		return errors.New("deposit amount must be positive")
	}
	if _, ok := l.accounts[accountID]; !ok {
		return fmt.Errorf("account %q not found", accountID)
	}
	l.accounts[accountID] += amountCents
	return nil
}

func main() {
	// Simulate what the test runner does for each table row.
	ledger := NewLedger("acc-001")

	tests := []struct {
		name        string
		accountID   string
		amountCents int64
		wantErr     bool
	}{
		{"valid deposit", "acc-001", 10000, false},
		{"zero amount", "acc-001", 0, true},
		{"negative amount", "acc-001", -500, true},
		{"unknown account", "does-not-exist", 1000, true},
	}

	for _, tc := range tests {
		err := ledger.Deposit(tc.accountID, tc.amountCents)
		gotErr := err != nil
		status := "PASS"
		if gotErr != tc.wantErr {
			status = "FAIL"
		}
		fmt.Printf("[%s] %s: err=%v wantErr=%v\n", status, tc.name, err, tc.wantErr)
	}
}

### Subtests and t.Run

`t.Run(name, func)` creates a **subtest** — a named child of the parent test. Every row in the table becomes a subtest. This gives you:

1. **Individual failure reporting** — `--- FAIL: TestDeposit/zero_amount` instead of "TestDeposit failed."
2. **Selective re-running** — `go test -run TestDeposit/zero_amount` runs only that row.
3. **Parallel subtests** — each subtest can be parallelized independently.

Without `t.Parallel()`, subtests are simple: `t.Run` runs the subtest to completion, then returns, and the loop moves to the next row. One at a time, in order. A failing row is reported by name and doesn't stop the others.

### Parallelism with t.Parallel

Add `t.Parallel()` at the top of a subtest and it can run at the same time as the other parallel subtests:

```go
for _, tc := range tests {
    t.Run(tc.name, func(t *testing.T) {
        t.Parallel()               // pause here; resume alongside the others
        ledger := newTestLedger(t) // each subtest needs its OWN state
        err := ledger.Deposit(tc.accountID, tc.amountCents)
        // ... assertions
    })
}
```

(On Go 1.22+ each iteration gets its own `tc`, so the old `tc := tc` line is no longer needed. You'll still see it in older code.)

The part nobody tells you is **when** parallel subtests run. It isn't when `t.Run` is called. Here's the real order, from running a test with three parallel subtests on Go 1.27:

```text
A : started, calling t.Parallel()
parent: t.Run returned for A
B : started, calling t.Parallel()
parent: t.Run returned for B
C : started, calling t.Parallel()
parent: t.Run returned for C
parent: function body ends
parent: defer runs (DB closed!)
A : resumed, running
C : resumed, running
B : resumed, running
A : done
C : done
B : done
parent: t.Cleanup runs
```

<Gotcha>
**`defer` in the parent of parallel subtests runs before they do.** Close shared resources with `t.Cleanup(...)`, which waits for all subtests. And give each parallel subtest its own mutable state (its own ledger, its own map); shared state between parallel subtests is a data race.
</Gotcha>

<Define term="Benchmark (testing.B)" since="Performance Engineering (Part 2)">
A **benchmark** is a test function that starts with `Bench` and takes `*testing.B`. Instead of asserting correctness, it measures speed: the test runner calls your loop repeatedly, calibrates iteration count, and reports **ns/op** (nanoseconds per call), **B/op** (bytes allocated), and **allocs/op** (heap allocations). Why it matters: without a benchmark, "this change makes it faster" is a guess. With one, it's a number. For Meridian's `Transfer` hot path — called thousands of times per second — one extra heap allocation per call means thousands of extra GC objects per second, which means latency spikes at load.
</Define>

A benchmark is a function that starts with `Bench` and takes `*testing.B`. The runner calls your function repeatedly, calibrating the iteration count until it gets a stable measurement. Since Go 1.24, the preferred way to write the benchmark loop is `b.Loop()` — it replaces older `b.N` loop idioms. `b.Loop()` returns true on each iteration and false when the benchmark is done; in Go 1.26, code inside the loop is no longer blocked from inlining.

**Scenario:** Our ledger's hot path is `Transfer(from, to string, amountCents int64) error`. Before optimizing, we measure.

```go
// ledger_bench_test.go
package ledger_test

import (
    "testing"
)

func BenchmarkTransfer(b *testing.B) {
    // Setup runs ONCE — not counted in the measurement.
    ledger := newBenchLedger(b)

    b.ReportAllocs() // report allocations per operation in the output
    b.ResetTimer()   // don't count the setup time above

    // Go 1.24+: b.Loop() is the preferred form. It handles iteration count
    // and timer management; Go 1.26 no longer blocks inlining inside the body.
    for b.Loop() {
        _ = ledger.Transfer("acc-001", "acc-002", 100)
    }
    // Older style (still valid): for i := 0; i < b.N; i++ { ... }
}
```

<Define term="Fuzzing (testing.F)" since="Testing in Go (this chapter)">
**Fuzzing** is automated adversarial input generation. You provide seed inputs; the Go fuzzer (built in since 1.18) mutates them — flipping bytes, trying extreme values, splicing corpus entries — and runs your target function with each mutation. When a mutation causes a panic or violates an invariant you declared, it saves the failing input to disk as a permanent regression. Why it matters for fintech: a human test author thinks of `0`, `-1`, and `10000`. The fuzzer thinks of `"\x80"`, `"9223372036854775808"`, and `"-0"`. Parser bugs that would never appear in a hand-written test matrix appear in seconds.
</Define>

Fuzzing is automated input generation designed to find crashes, panics, and violated invariants. You write a seed corpus; the engine mutates it toward inputs that break your code. Fuzzing has been built into the `go test` runner since Go 1.18 — no external tool required.

**Scenario:** Our `ParseTransferRequest(raw string) (TransferRequest, error)` function accepts a comma-separated string: `"acc-001,acc-002,10000"`. Money math bugs often hide in edge cases that humans don't think to test — overflow, empty strings, negative values sneaking through a parser. The fuzzer will think of them for you.

```go
// transfer_fuzz_test.go
package ledger_test

import (
    "testing"
)

// FuzzParseTransferRequest is a fuzz target.
// The corpus seeds below are the starting inputs; the engine mutates them.
func FuzzParseTransferRequest(f *testing.F) {
    // Seed corpus — at least one valid and one invalid case.
    f.Add("acc-001,acc-002,10000")    // valid
    f.Add("acc-001,acc-002,-500")     // negative amount — should error
    f.Add(",,")                        // empty fields — should error
    f.Add("acc-001,acc-002,99999999999999999999") // overflow candidate

    // f.Fuzz is called with mutated versions of the corpus above.
    // The engine explores variations: flipped bytes, removed chars, huge numbers.
    f.Fuzz(func(t *testing.T, raw string) {
        req, err := ParseTransferRequest(raw)
        if err != nil {
            return // an error is a valid, expected outcome — not a failure
        }
        // Invariant: a successfully parsed transfer must have positive cents.
        // If the parser returns no error but amountCents ≤ 0, the fuzzer found a bug.
        if req.AmountCents <= 0 {
            t.Errorf("parsed a non-positive amount without error: %q → %d",
                raw, req.AmountCents)
        }
    })
}
```

Run in seed-corpus-only mode (fast, no mutation):

```
go test -run FuzzParseTransferRequest ./...
```

Run the fuzzer (mutations, potentially long — stop with Ctrl+C):

```
go test -fuzz=FuzzParseTransferRequest -fuzztime=60s ./...
```

When the fuzzer finds a failing input, it saves it to `testdata/fuzz/FuzzParseTransferRequest/` — a regression file that's replayed on every `go test` run forever after.

<UnderTheHood title="How Go's fuzzer works (introduced Go 1.18, refined through 1.26)">

Go's built-in fuzzer (introduced in Go 1.18) uses **coverage-guided mutation**. After each input, the runtime compares which code branches were hit against previously seen coverage. If a mutation hits a new branch, it becomes part of the mutation pool — the engine prefers mutations that explore new code paths.

Internally, the fuzzer instruments your binary with coverage counters at compile time (the same infrastructure as `-cover`). The engine maintains a **corpus directory** on disk (`testdata/fuzz/<FuzzFuncName>/`) — so findings survive across runs and are version-controlled as regressions. The Go team explicitly designed this to be simple: no separate binary, no config file, no server. Run `go test -fuzz=Name` and the same `go test` tool does both normal tests and fuzzing. The corpus seeds (from `f.Add(...)`) are always run as ordinary subtests even without `-fuzz`, giving you instant regression coverage.

The mutation strategy is informed by the types: for `string` inputs, the engine tries byte flips, insertions, deletions, length extremes, and known dangerous values (empty, max-int representation). For `int` types, it covers 0, -1, MinInt, MaxInt. For `[]byte`, it tries corpus splicing. It's not symbolic — it's probabilistic, but extremely effective at finding parser and math bugs.

For fintech: fuzz every money parser — `ParseTransferRequest`, any function that reads an amount from a string, wire, or external API. The fuzzer will find integer overflow candidates, sign-flip edge cases, and missing validation guards faster than any manual test matrix.

<Define term="Race detector (-race)" since="Advanced Concurrency & Correctness (Part 2)">
The **race detector** (`go test -race`) instruments every memory read and write in your binary at compile time. At runtime it tracks which goroutine last touched each memory location and reports a **data race** whenever two goroutines access the same address concurrently without a synchronization point (mutex, channel, or atomic) establishing a happens-before relationship. Why it matters: a data race on Meridian's balance field is not a theoretical concern — it is a live mechanism for creating or destroying money. Two goroutines read the same balance, both see "sufficient funds," both commit; one transfer's debit is lost. The race detector catches this the first time it happens in a test, before it happens in production.
</Define>

The race detector is a runtime tool that instruments your binary and reports when two goroutines access the same memory location concurrently without synchronization. In fintech, a race on a balance field is not a theoretical concern — it's a real mechanism for creating or destroying money.

**Scenario:** Two goroutines attempt to transfer money from the same account simultaneously. Without a lock, both read the balance, both see "enough funds," and both commit — the account goes negative.

            defer wg.Done()

    total := ledger.Balance("acc-001") + ledger.Balance("acc-002")

package main

import (
	"fmt"
	"sync"

// SafeLedger is the race-free version.
type SafeLedger struct {
	mu       sync.Mutex
	accounts map[string]int64
}

func NewSafeLedger(initial map[string]int64) *SafeLedger {
	cp := make(map[string]int64, len(initial))
	for k, v := range initial {
		cp[k] = v
	}
	return &SafeLedger{accounts: cp}
}

func (l *SafeLedger) Transfer(from, to string, cents int64) error {
	l.mu.Lock()
	defer l.mu.Unlock()
	if l.accounts[from] < cents {
		return fmt.Errorf("insufficient funds")
	}
	l.accounts[from] -= cents
	l.accounts[to] += cents
	return nil
}

	l.mu.Lock()
	defer l.mu.Unlock()
	return l.accounts[id]
}

	ledger := NewSafeLedger(map[string]int64{"a": 100_000, "b": 0})

	if total == 100_000 {
		fmt.Println("Books balance. Race-free.")
	} else {
		fmt.Printf("BUG: expected 100000, got %d\n", total)
	}
}

<UnderTheHood title="How the race detector works — shadow memory and happens-before">

The race detector (enabled with `-race`) is an implementation of **ThreadSanitizer (TSan)** built into the Go toolchain. When you compile with `-race`, the compiler instruments every memory access — every read and write — with metadata calls. At runtime, a **shadow memory** region tracks the last few accesses to every 8-byte word of memory: which goroutine, which point in that goroutine's vector clock (a logical clock that tracks what each goroutine has seen from every other), and whether it was a read or write.

On every access, the runtime checks the shadow: "Has any other goroutine accessed this address since we last synchronized?" Synchronization (mutex lock/unlock, channel sends/receives, `sync/atomic` operations, `sync.WaitGroup` Done/Wait) establishes a **happens-before edge** — the runtime knows that everything goroutine A did before the mutex unlock is visible to goroutine B after it locks. Without that edge, a concurrent read-write to the same address is a race.

The instrumented binary is roughly **2–20× slower** and uses **5–10× more memory** — which is why you don't ship it to production, but it's acceptable for `go test -race`. In CI, always run `-race`. In fintech, `-race` is not optional — it's the first thing the PR pipeline checks.

Note: The race detector is a dynamic tool — it only catches races that *actually happen* during a specific run. A clean `-race` report does not prove absence of races; it proves the code paths exercised during that run were race-free. That's why you pair it with broad tests and load tests (`go test -race -count=50`).

As of Go 1.25, `go build -asan` (the AddressSanitizer mode) additionally enables **memory-leak detection** by default, on top of the use-after-free and out-of-bounds checks `-asan` already performed. This complements `-race` — use `-race` for goroutine data races, `-asan` when debugging cgo or unsafe pointer code for memory-safety violations.

</UnderTheHood>

<Callout kind="pro" title="Go 1.25: go vet's waitgroup analyzer catches WaitGroup bugs at compile time">

The race detector is dynamic — it only sees races that actually happen during a run. Some concurrency bugs are catchable *statically*, before you even run the tests. Go 1.25 added a **`waitgroup` analyzer** to `go vet` (which `go test` runs automatically) that flags the single most common `sync.WaitGroup` misuse: calling `wg.Add(1)` **inside** the goroutine instead of before launching it.

```go
// go vet flags this: Add(1) runs on the new goroutine, which may start
// AFTER wg.Wait() has already seen a zero counter and returned.
go func() {
    wg.Add(1) // ← "WaitGroup.Add called from inside new goroutine"
    defer wg.Done()
    doWork()
}()
```

The correct form is `wg.Add(1)` before the `go` statement — or better, `wg.Go(func(){ doWork() })` (Go 1.25), which does the `Add`/`Done` pairing for you and sidesteps the bug entirely. Go 1.25 also shipped a `hostport` analyzer: pass `fmt.Sprintf("%s:%d", host, port)` to `net.Dial` and vet reports `address format "%s:%d" does not work with IPv6` (use `net.JoinHostPort`) — run `go vet ./...` in CI alongside `-race` and you catch both the static and the dynamic class of concurrency mistake.

</Callout>

Coverage tells you which lines of your code were executed during a test run. More importantly, it tells you which lines were *not*. Use it to find gaps, not to chase a percentage.

```
go test -cover ./...
# output: ok  ledger   0.312s  coverage: 84.1% of statements

go test -coverprofile=coverage.out ./...
go tool cover -html=coverage.out   # opens an HTML report in your browser
```

The HTML report highlights every line: green (covered), red (not covered). The uncovered red lines are where you're flying blind.

```
go test -covermode=atomic -race ./...

Use `-covermode=atomic` when running with `-race` — it uses atomic operations for the coverage counters instead of the default simple increment, which would itself be a race.

## Concurrency Testing with synctest

*Stop 7 of 12.*

Time-dependent concurrent code is the hardest category to test reliably. A test that spins up a ticker, waits for a timeout, or races a context deadline has two enemies: **flakiness** (the goroutine scheduler doesn't guarantee ordering) and **slowness** (you can't make a 30-second timeout test fast without removing the timeout).

Go 1.25 graduated `testing/synctest` from an experimental package to **general availability**. It solves both problems.

### The core idea: a bubble with virtual time

`synctest.Test(t, func(t *testing.T) { ... })` runs your test function in a **bubble** — an isolated execution environment with a **virtual clock**. Inside the bubble:

- `time.Now()`, `time.Sleep`, timers, tickers, and `context.WithTimeout` all use the fake clock.
- When every goroutine inside the bubble is blocked (waiting on a channel, sleeping, or blocked on I/O), the fake clock **jumps forward** to the next scheduled wake-up instantly.
- `synctest.Wait()` waits until all goroutines inside the bubble are blocked — a clean synchronization point before you advance state.

This makes a test that "waits 30 seconds for a timeout" complete in **microseconds**.

```go
// transfer_timeout_test.go
package ledger_test

import (
    "context"
    "errors"
    "testing"
    "testing/synctest"
    "time"
)

// processTransfer waits for a slow downstream call (10 s) unless the
// context's deadline comes first.
func processTransfer(ctx context.Context, amountCents int64) error {
    select {
    case <-time.After(10 * time.Second): // the slow path
        return nil
    case <-ctx.Done():
        return ctx.Err()
    }
}

func TestTransferTimeout(t *testing.T) {
    synctest.Test(t, func(t *testing.T) {
        ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
        defer cancel()

        start := time.Now() // the bubble's fake clock
        err := processTransfer(ctx, 10_000)

        if !errors.Is(err, context.DeadlineExceeded) {
            t.Fatalf("want DeadlineExceeded, got %v", err)
        }
        t.Log("virtual time passed:", time.Since(start)) // 5s
    })
}
```

```text
$ go test -v -run TestTransferTimeout
    transfer_timeout_test.go:31: virtual time passed: 5s
--- PASS: TestTransferTimeout (0.00s)
```

Five seconds of virtual time in 0.00 seconds of real time. There's no `synctest.Wait()` here and no extra goroutine: the test goroutine blocks inside `processTransfer`'s `select`, it's the only goroutine in the bubble, so the clock jumps straight to the earliest timer (the 5 s deadline).

Run it normally:

```
go test -run TestTransferTimeout_Synctest ./...
```

No special flags. The bubble is entered by `synctest.Test`; the fake clock and `synctest.Wait()` are the only APIs you need.

</Callout>

### synctest.Wait — the synchronization primitive

`synctest.Wait()` blocks the caller until every other goroutine in the bubble is **durably blocked** — blocked in a way only another bubble goroutine can release: a channel operation, a `select`, `time.Sleep`, `sync.Cond.Wait`, or `sync.WaitGroup.Wait`. (A goroutine blocked on a `sync.Mutex`/`RWMutex` lock or sitting in a syscall is **not** durably blocked — those can be released from outside the bubble, so they don't count.) It is the bubble's equivalent of `wg.Wait()` — a checkpoint before you make assertions or advance the virtual clock.

The pattern:

1. Start goroutines inside the bubble.
2. Call `synctest.Wait()` — let them reach their first block.
3. Trigger a state change: close a channel, cancel a context, or **advance the clock by sleeping in the test goroutine**. Time only moves when every goroutine in the bubble, the test's own included, is blocked. Calling `synctest.Wait()` twice in a row does NOT move time (an earlier version of this example did exactly that, and it fails with "expected a tick, got none").
4. Call `synctest.Wait()` again — let goroutines react.
5. Assert the outcome.

```go
synctest.Test(t, func(t *testing.T) {
    ticks := make(chan time.Time, 1)
    go func() {
        ticker := time.NewTicker(1 * time.Second)
        defer ticker.Stop()
        ticks <- <-ticker.C // wait for one tick and send it
    }()

    time.Sleep(1 * time.Second) // now EVERY goroutine is blocked, so the clock jumps 1s
    synctest.Wait()             // let the woken worker finish sending on ticks

    select {
    case <-ticks:
        // tick received — test passes
    default:
        t.Fatal("expected a tick, got none")
    }
})
```

<UnderTheHood title="How synctest's fake clock works (Go 1.25)">

Inside a `synctest` bubble, the Go runtime swaps the clock source used by `time.Now()`, `time.Sleep`, `time.NewTimer`, `time.NewTicker`, and `context.WithDeadline`/`WithTimeout` to a **fake clock** that starts at **midnight UTC on 1 January 2000** in every bubble (so tests don't depend on today's date). The fake clock does not advance on its own — it only jumps when the runtime detects that **all goroutines in the bubble are blocked**.

"All goroutines blocked" means every goroutine is **durably blocked** — waiting on something only another bubble goroutine can release: a channel operation (`<-ch`, `ch<-`), a `select`, `time.Sleep`, `sync.Cond.Wait`, or `sync.WaitGroup.Wait`. (A goroutine blocked acquiring a `sync.Mutex`/`RWMutex`, or parked in a syscall, does **not** count — those can be unblocked from outside the bubble.) When this condition holds, the runtime advances the fake clock to the soonest scheduled wake-up event (the nearest timer or ticker expiry) and unblocks the corresponding goroutines.

`synctest.Wait()` is layered on top: it is itself a blocking point, but it also signals to the runtime that the caller considers all currently-running goroutines to have "settled." Combined, this gives you deterministic control over virtual time without any real-time delays.

This design means tests using `synctest` are both **instant** (no real sleeping) and **deterministic** (goroutine scheduling inside the bubble is fully reproducible), which eliminates the entire class of time-dependent flaky tests.

</UnderTheHood>

<ELI5
  concept="Dependency injection, and why it makes tests possible"
  analogy="A kettle with a plug, instead of one wired into the wall."
  role="reader"
>

A function that reaches out and builds its own database connection is wired into the wall. To test it you need the wall — a real Postgres, real network, real slowness — and you cannot make it fail on demand.

**Dependency injection** just means handing the thing in instead of building it inside. The function takes an interface describing what it needs — "something I can call `SaveTransfer` on" — and the caller decides what to plug in. Production plugs in Postgres. The test plugs in a small fake that records what it was asked to do, or returns an error on the third call so you can prove your retry logic works.

Nothing clever is happening. The function stopped choosing its own collaborators, so a test can choose them instead. In Go the interface is usually small and declared where it is *used*, not where it is implemented — one or two methods describing what this code needs, nothing more.

</ELI5>

## Mocking and DI

*Stop 8 of 12.*

<Define term="Test double / fake (vs mock)" since="Testing in Go (this chapter)">
A **test double** is any object that stands in for a real dependency in a test. A **fake** is a simple working implementation — a hand-written struct that implements the same interface as the real database, but stores data in a map. A **mock** is a generated or framework-controlled object that records calls and lets you assert on them (exact argument values, call count, call order). In Go, the idiomatic choice is the fake: define a small interface in the consuming package, implement it with a struct in the test file. No code generation, no reflection, no magic — any engineer can read and debug it. Reach for a mock framework only when the interface is large, you need precise call-order assertions across many tests, or the fake would require significant logic of its own to be useful.
</Define>

Go's answer to mocking is not a framework. It's an **interface defined by the consumer** and a **hand-written fake** that implements it. No reflection magic. No code generation (unless you want it). Just a struct with the same methods.

**The scenario:** `TransferService` needs to write to a database. In tests, we don't want a real database — we want a fake that we control completely.

```go
// The interface is defined here, in the package that USES it — not in ledger storage.
// This is the Go proverb: "accept interfaces, return structs."
type LedgerStore interface {
    Deposit(ctx context.Context, accountID string, cents int64) error
    Withdraw(ctx context.Context, accountID string, cents int64) error
    Balance(ctx context.Context, accountID string) (int64, error)
}

// TransferService depends on the interface, not the concrete Postgres implementation.
type TransferService struct {
    store LedgerStore // injected — we control this in tests
}

func NewTransferService(store LedgerStore) *TransferService {
    return &TransferService{store: store}
}
```

The fake lives in the test file (or a `testdata/` package):

```go
// fakeLedgerStore is a hand-written test double — simple, debuggable, no magic.
type fakeLedgerStore struct {
    accounts map[string]int64
    mu       sync.Mutex
    // record calls for assertion
    calls    []string
}

func (f *fakeLedgerStore) Deposit(_ context.Context, id string, cents int64) error {
    f.mu.Lock()
    defer f.mu.Unlock()
    f.calls = append(f.calls, "Deposit:"+id)
    if cents <= 0 {
        return errors.New("invalid amount")
    }
    f.accounts[id] += cents
    return nil
}

func (f *fakeLedgerStore) Withdraw(_ context.Context, id string, cents int64) error {
    f.mu.Lock()
    defer f.mu.Unlock()
    f.calls = append(f.calls, "Withdraw:"+id)
    if f.accounts[id] < cents {
        return errors.New("insufficient funds")
    }
    f.accounts[id] -= cents
    return nil
}

func (f *fakeLedgerStore) Balance(_ context.Context, id string) (int64, error) {
    f.mu.Lock()
    defer f.mu.Unlock()
    return f.accounts[id], nil
}
```

Now the test is pure, fast, and deterministic:

```go
func TestTransfer_InsufficientFunds(t *testing.T) {
    store := &fakeLedgerStore{
        accounts: map[string]int64{"sender": 100, "receiver": 0},
    }
    svc := NewTransferService(store)
    ctx := context.Background()

    err := svc.Transfer(ctx, "sender", "receiver", 500) // more than balance
    if err == nil {
        t.Fatal("expected insufficient-funds error, got nil")
    }
    // Assert the store received the right calls in the right order.
    if len(store.calls) == 0 || store.calls[0] != "Withdraw:sender" {
        t.Errorf("unexpected call sequence: %v", store.calls)
    }
}
```

## Integration Tests

*Stop 9 of 12.*

Unit tests with fakes are fast and precise. But they test your code in isolation — they don't verify that your SQL queries actually work against real Postgres, that your Redis pipeline actually pipelines, or that your Kafka consumer offset handling is correct. **Integration tests** exercise your code against real dependencies in ephemeral containers.

**The tool: testcontainers-go** (`github.com/testcontainers/testcontainers-go`). It spins up Docker containers from within your Go test code, gives you a real connection string, and tears them down when the test finishes.

```go
// ledger_integration_test.go
//go:build integration
// +build integration

package ledger_test

import (
    "context"
    "testing"

    "github.com/testcontainers/testcontainers-go"
    "github.com/testcontainers/testcontainers-go/modules/postgres"
    "github.com/jackc/pgx/v5/pgxpool"
)

func TestDeposit_Integration(t *testing.T) {
    ctx := context.Background()

    // Spin up a real Postgres — takes a few seconds the first time (image pull).
    pgContainer, err := postgres.RunContainer(ctx,
        testcontainers.WithImage("postgres:16-alpine"),
        postgres.WithDatabase("ledger_test"),
        postgres.WithUsername("test"),
        postgres.WithPassword("test"),
        testcontainers.WithWaitStrategy(/* wait for port to be ready */),
    )
    if err != nil {
        t.Fatalf("start postgres container: %v", err)
    }
    t.Cleanup(func() { _ = pgContainer.Terminate(ctx) })

    connStr, err := pgContainer.ConnectionString(ctx, "sslmode=disable")
    if err != nil {
        t.Fatalf("get connection string: %v", err)
    }

    pool, err := pgxpool.New(ctx, connStr)
    if err != nil {
        t.Fatalf("connect: %v", err)
    }
    t.Cleanup(pool.Close)

    // Run migrations against the real DB.
    if err := runMigrations(ctx, pool); err != nil {
        t.Fatalf("migrate: %v", err)
    }

    // Now test against the real Postgres store.
    store := NewPostgresLedgerStore(pool)
    svc := NewTransferService(store)

    if err := store.CreateAccount(ctx, "acc-001", 0); err != nil {
        t.Fatalf("create account: %v", err)
    }
    if err := svc.Deposit(ctx, "acc-001", 10_000); err != nil {
        t.Fatalf("deposit: %v", err)
    }
    bal, err := store.Balance(ctx, "acc-001")
    if err != nil {
        t.Fatalf("balance: %v", err)
    }
    if bal != 10_000 {
        t.Errorf("balance: got %d, want 10000", bal)
    }
}
```

Note the build tag `//go:build integration` — integration tests are slow (container startup) and require Docker. Separate them from unit tests so `go test ./...` stays fast.

Run them explicitly:

```
go test -tags=integration -v ./...
```

<Define term="httptest" since="HTTP Servers: JSON, Streaming & WebSockets (Part 1)">
**`net/http/httptest`** is a stdlib package that lets you test HTTP handlers without binding to a real port or opening a network socket. `httptest.NewRecorder()` gives you an in-memory `http.ResponseWriter` you can inspect after the handler runs — status code, headers, body. `httptest.NewServer(handler)` goes one step further: it spins up a real HTTP server on a random local port so you can exercise your full middleware stack with an actual `http.Client`. ### httptest — testing HTTP handlers without a real server

The `net/http/httptest` package lets you test HTTP handlers in process — no binding to a port, no network round-trips. Two tools:

1. **`httptest.NewRecorder()`** — an in-memory `http.ResponseWriter` you can inspect after the handler runs.
2. **`httptest.NewServer(handler)`** — spins up a real HTTP server on a random port; use its `.URL` as the base URL in your client. Perfect for testing your full stack including middleware.

```go
func TestDepositHandler(t *testing.T) {

        accounts: map[string]int64{"acc-001": 0},

    handler := NewDepositHandler(store)

### Golden files — locking down complex output

When a handler response, a report, or a serialized format is large or complex enough that you don't want to hardcode the expected output inline, use **golden files**: on first run (or with `-update` flag), write the actual output to disk; on subsequent runs, compare actual vs. the stored file.

```go
// testdata/golden/deposit_response.json — committed to version control

func TestDepositHandler_Golden(t *testing.T) {
    // ... set up and call the handler
    got := rec.Body.Bytes()

    goldenPath := filepath.Join("testdata", "golden", "deposit_response.json")

    if *updateGolden {
        // go test -run TestDepositHandler_Golden -update — update the golden file
        if err := os.WriteFile(goldenPath, got, 0644); err != nil {
            t.Fatal(err)
        }
        return
    }

    want, err := os.ReadFile(goldenPath)
    if err != nil {
        t.Fatalf("golden file missing — run with -update to create it: %v", err)
    }
    if !bytes.Equal(got, want) {
        t.Errorf("response mismatch:\\n--- want\\n%s\\n+++ got\\n%s", want, got)
    }
}

var updateGolden = flag.Bool("update", false, "update golden files")
```

Golden files are committed to version control. Any change to the output requires an intentional `-update` run — making regressions visible in PR diffs.

<Callout kind="pro" title="Golden files for API contracts">
Golden files are excellent for API contract tests. When a JSON response changes shape, the PR diff includes the golden file change — reviewers immediately see exactly what changed in the API. This beats comparing inline strings in test files for any response more than two fields wide.
</Callout>

## stdlib vs testify

*Stop 11 of 12.*

The `testing` package is powerful enough to test anything. `testify` (`github.com/stretchr/testify`) adds sugar. Here's the honest take:

<BeforeAfter
  badLabel="stdlib (verbose for assertions)"
  goodLabel="testify/assert (sugar where it earns it)"
  bad={`// Without testify — correct but repetitive for comparisons
if got != want {
    t.Errorf("Balance: got %d, want %d", got, want)
}
if err == nil {
    t.Fatal("expected error, got nil")
}
if !reflect.DeepEqual(gotSlice, wantSlice) {
    t.Errorf("slice mismatch:\\ngot:  %v\\nwant: %v", gotSlice, wantSlice)
}`}
  good={`// With testify — same semantics, less ceremony for comparison assertions
assert.Equal(t, want, got, "Balance mismatch")
require.Error(t, err, "expected non-nil error")
assert.ElementsMatch(t, wantSlice, gotSlice)
// require.* stops the test on failure (like t.Fatalf)
// assert.* records failure and continues (like t.Errorf)`}
/>

**My recommendation:**

1. **Default to stdlib + table-driven tests.** The patterns in this chapter work perfectly without testify. No dependency, no import, no magic. Any Go engineer can read the tests on day one.
2. **Add testify's `assert`/`require` packages** when your assertion code is getting repetitive and the calls map directly to what you're checking (`require.NoError`, `assert.Equal`, `assert.ElementsMatch`). These are assertion sugar — they don't change test structure.
3. **Do not use `testify/mock`** until hand-written fakes become genuinely painful (many methods, complex call assertion). Prefer fakes first.
4. **Never use testify/suite** — it wraps `testing.T` in a way that makes `-run` filtering, `t.Parallel()`, and subtests more awkward, not less. The struct-based test suite pattern adds Go overhead for something Go's runner handles natively.

## The Full Picture — Unit, Integration, E2E

*Stop 12 of 12.*

<ConceptGrid cols={3}>
  <ConceptCard label="Unit tests">Fast, isolated, deterministic. Exercise one function or method with controlled inputs. Use fakes for dependencies. Run on every save. Your primary feedback loop.</ConceptCard>
  <ConceptCard label="Integration tests">Slower, real dependencies in containers. Verify that your SQL, Redis commands, Kafka consumer logic, etc. work against the actual system. Run in CI, gated behind a build tag.</ConceptCard>
  <ConceptCard label="End-to-end (E2E) tests">Slowest. Drive the full system — real services, real network, real database — usually via HTTP clients or test scripts. Catch integration mismatches that survive unit and integration tests. Run pre-deploy, not per commit.</ConceptCard>
  <Gotcha>The testing pyramid is real. If 80% of your tests are E2E, they'll be slow, flaky, and hard to debug. Keep the base (unit) wide, the middle (integration) selective, and the top (E2E) narrow. A failing unit test should point at the exact function. A failing E2E test should confirm a user-visible breakage, not debug it.</Gotcha>
</ConceptGrid>

    "sync"
    "testing"

var transferPool = sync.Pool{
    New: func() any { return new(TransferRequest) },
}

func parseIntoPooled(raw string) (*TransferRequest, error) {
    req := transferPool.Get().(*TransferRequest)
    // reset fields before use
    req.From = ""
    req.To = ""
    req.AmountCents = 0
    // parse into *req ... (same logic as ParseTransferRequest)
    parsed, err := ParseTransferRequest(raw)
    if err != nil {
        transferPool.Put(req) // return it on error too
        return nil, err
    }
    *req = parsed
    return req, nil
}

    b.ReportAllocs()
    b.ResetTimer()
    // b.Loop() is the Go 1.24+ preferred form — no manual b.N management.

}

    b.ResetTimer()

            transferPool.Put(req) // return to pool after use
        }
    }

For a fintech transfer API handling thousands of requests per second, this is a meaningful optimization. Measure first with `-benchmem`; optimize if the allocation count is a real bottleneck in your pprof profile.

<Recap>

You now test Go the way it was designed to be tested. Here's what you own:

- **`*testing.T`, `*testing.B`, `*testing.F`** — the three testing types. `TestMain` for suite-level setup. `t.Helper()` for clean failure output. `t.Cleanup()` for guaranteed teardown.
- **Table-driven tests with `t.Run`** — the canonical pattern. Every behavior gets a named row. Individual subtests fail and can be re-run in isolation.
- **`t.Parallel()`** — parallel subtests for speed. Capture loop variables (`tc := tc`) before Go 1.22; in 1.22+ it's automatic.
- **Benchmarks** — use `b.Loop()` (Go 1.24+) as the preferred loop form; `b.ReportAllocs()`; `b.ResetTimer()` after setup. Read `ns/op` and `allocs/op`. Lower allocations usually matter more than lower nanoseconds at scale. Note: `testing.AllocsPerRun` panics under `t.Parallel()` as of Go 1.25.
- **Fuzzing** — `f.Add` seeds, `f.Fuzz` invariants. Run with `-fuzz=Name`. Failing inputs saved to `testdata/fuzz/` for permanent regression. Required for money math parsers.
- **The race detector** — `-race` instruments every memory access. A data race on a ledger balance is not theoretical — it creates or destroys money. Run `-race` in CI, always. Complement it with `-asan` (Go 1.25+) for memory-safety checks in cgo or unsafe code.
- **Coverage** — `-cover`, `-coverprofile`, `go tool cover -html`. Use `-covermode=atomic` with `-race`. Chase meaningful branch coverage, not a percentage. Use `t.Attr()` (Go 1.25) to attach metadata and `t.ArtifactDir()` (Go 1.26) to save test artifacts to CI.
- **`testing/synctest`** (Go 1.25, GA) — test time-dependent concurrent code with a fake clock and `synctest.Wait()`. Deterministic, instant, no flakiness.
- **Mocking via interfaces and DI** — define small interfaces in the consuming package. Write hand-written fakes. Use testify/mock when fakes become painful.
- **Integration tests with testcontainers** — real containers, real Postgres, gated behind build tags. Use `TestMain` for one container per suite, not one per test.
- **`httptest`** — `NewRequest` + `NewRecorder` for in-process handler tests. `NewServer` for full-stack tests with a real client.
- **Golden files** — write expected output to `testdata/`, compare on subsequent runs, update with `-update`. Version-controlled API contracts.
- **stdlib vs testify** — default to stdlib + table-driven. Add `assert`/`require` where assertion code gets noisy. Skip testify/suite and testify/mock until hand-written fakes genuinely hurt.
