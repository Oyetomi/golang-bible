## The Red-Green-Refactor Loop

Before a single line of code, let me show you the *situation*. You're an engineer at Meridian. A transfer request lands: amount, source account, destination account. Before you wire up database calls, HTTP handlers, or any of that, you need a function that says yes or no — a **validator**. Right now it doesn't exist. How do you build it?

The TDD answer: write a failing test first. Watch it fail (red). Write the minimum code to make it pass (green). Clean it up while it stays green (refactor). Repeat for every rule, one at a time.

### The three steps, explained

The loop has exactly three steps, and every one of them is deliberate:

**1 — Red: write a failing test first.**

Before you write a single line of production code, write a test that describes the behavior you want. Run it. It must fail — if it passes before you write anything, either the behavior already exists (good to know) or the test is wrong (fix it before proceeding). A test that cannot fail is worthless: it tells you nothing.

The red step forces you to think about the *interface* first. What does this function take? What does it return? What is the caller's experience? You become your own first user before the code exists, and that changes what you build.

**2 — Green: write the *minimum* code to make it pass.**

Not the "best" code. The *minimum* code. If a hardcoded return value makes the test green, write that — then immediately write the next test to force you out of the lie. The discipline of minimum code keeps you from over-engineering before you know what the next requirement actually is. Solve what the test asks for. Nothing more.

**3 — Refactor: clean up while the tests stay green.**

Once green, you have a safety net. Rename a confusing variable. Extract a helper. Eliminate duplication. The tests tell you if you broke something. This is the only time in professional software engineering where you can refactor with genuine confidence — because the test is watching every move.

Then: write the next failing test. Repeat.

**"Never write production code without a failing test demanding it."** That is the discipline. Every line of your validator exists because a test required it.

<Callout kind="pro" title="Fail for the right reason">

A test that fails because the function doesn't exist yet is a valid red. A test that fails because the assertion is backwards is a bug in the test. Before moving to green, make sure you understand *why* the test is red. "Undefined: Validate" tells you the code is missing. "got nil, want error" tells you the code runs but returns the wrong thing. Both are red, but only the second means your production code is in play.

</Callout>

## Tests Drive Design

Here's what nobody tells you when they pitch TDD as a "testing practice": it's actually a **design practice**. The red step is not just about catching bugs. It's about forcing you to use your own API before it exists.

**On the job:** You're adding the Meridian transfer validator. Without TDD, you might write a `ValidateTransfer` function with five parameters, a config struct, and a context — because "that's how production code usually looks." Then the test is awkward to set up, and you don't notice until your second user (another engineer) tries to call it.

With TDD: you write the test first. You type the call site. Immediately, `AmountCents int64, FromID string, ToID string, CurrencyCode string` starts to feel like too much. You reorganize into a `TransferRequest` struct before the function exists. The test tells you what ergonomic looks like.

### TDD nudges you toward better design

Three patterns that emerge *naturally* when you write tests first:

**Small functions with clear inputs and outputs.** If your function is hard to test — lots of setup, lots of globals — it's hard to test *because it's doing too much*. TDD surfaces that immediately. You split it because you're tired of writing test setup.

**Interface-shaped dependencies.** If `Validate` needs to check a balance, and you write the test first, you can't call a real database. So you define an interface — `BalanceStore` — and pass a fake. The interface is naturally minimal: only what the validator needs, nothing more. This is the consumer interface pattern from Go idioms. TDD builds it automatically.

**Injectable, global-free code.** "No globals — inject deps" is a Go proverb. TDD enforces it. A function that reads a global config is painful to test (you mutate globals between tests — a race waiting to happen). TDD makes you pass config as a parameter because you have to.

<UnderTheHood title="Why consumer interfaces and TDD fit Go's philosophy">

Go's interface system is **implicit**: a type satisfies an interface by having the right methods — no declaration required. This is central to why TDD feels natural in Go.

When you write a test first and need a fake database, you define the interface in the *consumer* package (the validator), not in the storage package. The interface has exactly the methods the test calls — nothing else. This is the **interface segregation** principle without ceremony: TDD builds it automatically because you only call what you need.

The pattern: `BalanceStore` has one method, `Balance(ctx context.Context, id string) (int64, error)`. The real Postgres implementation satisfies it implicitly. The test fake satisfies it with three lines. No registration, no code generation, no framework.

The allocation cost here is ordinary Go interface cost, not a special testing tax. Escape analysis looks at each call site and may keep concrete values on the stack when it can prove they do not outlive the function. A fake that satisfies a tiny consumer-owned interface is usually just normal Go code; measure hot paths with benchmarks before assuming the interface itself is expensive.

The broader point: Go was designed for large codebases where many packages interact through interfaces. TDD and Go's implicit interfaces are a natural pairing — the discipline enforces the design pattern the language was built for.

</UnderTheHood>

## Grow It Rule by Rule

Time to build something real. We're growing the **Meridian transfer validator** from nothing, one rule at a time. Each cycle: write the failing test, watch it fail for the right reason, write minimum code to pass, refactor.

Five rules total:
1. Amount must be positive (cents, never zero or negative)
2. Balance must be sufficient (source account has enough)
3. Accounts must differ (source ≠ destination)
4. Currencies must match (no cross-currency transfers at this layer)
5. Amount must be a whole number of cents (never fractional — integer-only, defended at the type level)

We'll run through all five cycles. The tests are shown as `_test.go` (non-runnable in the playground — Codapi runs `go run`, not `go test`); the validator itself ships as a runnable playground at the end so you can see it exercised.

### Cycle 1 — Amount must be positive

**The test (write this first):**

```go
// validator_test.go
package validator_test

import "testing"

func TestValidate_AmountPositive(t *testing.T) {
	tests := []struct {
		name    string
		amount  int64
		wantErr bool
	}{
		{"positive cents", 5000, false},
		{"zero cents", 0, true},
		{"negative cents", -100, true},
	}
	for _, tc := range tests {
		t.Run(tc.name, func(t *testing.T) {
			req := TransferRequest{
				From:     "acc-001",
				To:       "acc-002",
				Amount:   tc.amount,
				Currency: "USD",
			}
			err := Validate(req, nil)
			if (err != nil) != tc.wantErr {
				t.Errorf("Validate amount=%d: got err=%v, wantErr=%v",
					tc.amount, err, tc.wantErr)
			}
		})
	}
}
```

**Run:** `go test ./...` → compile error. `Validate` and `TransferRequest` don't exist. RED.

**Minimum code to pass (green):**

```go
// validator.go
package validator

import "errors"

// TransferRequest holds everything the validator needs to inspect.
type TransferRequest struct {
	From     string
	To       string
	Amount   int64  // cents — never float
	Currency string
}

// BalanceStore is the only storage capability Validate needs.
// Defined here in the consumer package — the real DB satisfies it implicitly.
type BalanceStore interface {
	Balance(id string) (int64, error)
}

// Validate returns an error if the transfer request violates any rule.
func Validate(r TransferRequest, store BalanceStore) error {
	if r.Amount <= 0 {
		return errors.New("amount must be positive cents")
	}
	return nil
}
```

**Run:** `go test ./...` → PASS. GREEN.

**Refactor:** Nothing to clean yet — the code is already minimal. Move on.

```go
func TestValidate_SufficientBalance(t *testing.T) {

				To:       "acc-002",
				Amount:   tc.amount,
				Currency: "USD",
			}
			err := Validate(req, store)
			if (err != nil) != tc.wantErr {
				t.Errorf("Validate balance: got err=%v, wantErr=%v", err, tc.wantErr)
			}
		})
	}
}

// fakeStore is the hand-written test double — no framework, just a struct.
type fakeStore struct {
	balances map[string]int64
}

func (f *fakeStore) Balance(id string) (int64, error) {
	b, ok := f.balances[id]
	if !ok {
		return 0, fmt.Errorf("account %q not found", id)
	}

```

**Run:** FAIL — `Validate` ignores the store. RED.

**Minimum code:**

```go
func Validate(r TransferRequest, store BalanceStore) error {
	if r.Amount <= 0 {
		return errors.New("amount must be positive cents")
	}
	if store != nil {
		bal, err := store.Balance(r.From)
		if err != nil {
			return fmt.Errorf("balance lookup: %w", err)
		}
		if bal < r.Amount {
			return errors.New("insufficient balance")
		}
	}
	return nil
}
```

**Run:** PASS. GREEN. **Refactor:** pull the balance check into a named helper `checkBalance` — tests still pass.

### Cycle 3 — Accounts must differ

```go
func TestValidate_AccountsDiffer(t *testing.T) {
	store := &fakeStore{balances: map[string]int64{"acc-001": 99999}}

	req := TransferRequest{
		From:     "acc-001",
		To:       "acc-001", // same — should error

	if err := Validate(req, store); err == nil {
```

**Run:** FAIL (nil, want error). RED.

**Minimum code:** add `if r.From == r.To { return errors.New(...) }` before the balance check.

**Run:** PASS. GREEN. **Refactor:** no structural change needed.

### Cycle 4 — Currencies must match

```go
func TestValidate_CurrencyMatch(t *testing.T) {
	store := &fakeStore{balances: map[string]int64{
		"acc-usd": 50000,
		"acc-eur": 50000,
	}}

	tests := []struct {
		name     string
		from     string
		to       string
		currency string
		wantErr  bool
	}{
		{"matching USD", "acc-usd", "acc-usd-2", "USD", false},
		{"empty currency rejected", "acc-usd", "acc-usd-2", "", true},
	}
	// (In a real system the store would carry currency per account;
	// here we validate that the request currency is at least non-empty.)
	for _, tc := range tests {
		t.Run(tc.name, func(t *testing.T) {
			req := TransferRequest{
				From:     tc.from,
				To:       tc.to,
				Amount:   1000,
				Currency: tc.currency,
			}
			if err := Validate(req, store); (err != nil) != tc.wantErr {
				t.Errorf("currency=%q: got err=%v, wantErr=%v",
					tc.currency, err, tc.wantErr)
			}
		})
	}
}
```

**Run:** FAIL (nil for empty currency). RED. **Minimum code:** `if r.Currency == "" { return errors.New("currency required") }`. **Run:** PASS. GREEN.

### Cycle 5 — Integer cents, never fractional

This rule is defended at the *type level*: `Amount` is `int64`. You cannot represent `$4.999` or `0.001`. But we add an explicit test to document the contract and lock it in — and we use `int64` in the struct to make the intent undeniable.

```go
func TestValidate_IntegerCents(t *testing.T) {
	// The type system prevents float64 at compile time.
	// This test documents the cent-level minimum granularity:
	// 1 cent is the smallest valid transfer amount.
	store := &fakeStore{balances: map[string]int64{"acc-001": 99999}}

	req := TransferRequest{
		From:     "acc-001",
		To:       "acc-002",
		Amount:   1, // 1 cent — valid
		Currency: "USD",
	}
	if err := Validate(req, store); err != nil {
		t.Errorf("1-cent transfer should be valid: %v", err)
	}
}
```

**Run:** PASS immediately. This test is green before we add code — which is *correct*: `int64` already prevents fractional cents at the type level. The test documents the contract. We keep it.

<Callout kind="warn" title="Money is integer cents — always">

`Amount int64` in `TransferRequest` is not a style preference. Floating-point money is how you get `$14.9999999999998` silently crossing a ledger boundary. The type system is your first line of defense: `int64` for cents means the compiler refuses a `float64`. Your validator never sees a fraction. State this in a comment on the struct field — future engineers will thank you or, more likely, you'll thank yourself at 2 a.m.

</Callout>

Now the complete, runnable validator — exercised via a `main` that replays all five rules and prints PASS/FAIL:

<GoPlayground>

```go
package main

import (
	"errors"
	"fmt"
)

// TransferRequest is everything the validator inspects.
// Amount is int64 cents — never float64. 1 cent minimum granularity.
type TransferRequest struct {
	From     string
	To       string
	Amount   int64  // cents, never float
	Currency string
}

// BalanceStore is defined by the consumer (this package), not the storage layer.
// Any type with a Balance method satisfies it — including test fakes.
type BalanceStore interface {
	Balance(id string) (int64, error)
}

// Validate enforces all five Meridian transfer rules.
func Validate(r TransferRequest, store BalanceStore) error {
	// Rule 1: amount must be positive cents.
	if r.Amount <= 0 {
		return errors.New("amount must be positive cents")
	}
	// Rule 2: currency must be specified.
	if r.Currency == "" {
		return errors.New("currency is required")
	}
	// Rule 3: accounts must differ.
	if r.From == r.To {
		return errors.New("source and destination accounts must differ")
	}
	// Rule 4: balance must be sufficient.
	if store != nil {
		bal, err := store.Balance(r.From)
		if err != nil {
			return fmt.Errorf("balance lookup: %w", err)
		}
		if bal < r.Amount {
			return fmt.Errorf("insufficient balance: have %d cents, need %d",
				bal, r.Amount)
		}
	}
	// Rule 5: int64 type prevents fractional cents at compile time.
	// No runtime check needed — the type system enforces it.
	return nil
}

// fakeStore is a hand-written test double that implements BalanceStore.
type fakeStore struct {
	balances map[string]int64
}

func (f *fakeStore) Balance(id string) (int64, error) {
	b, ok := f.balances[id]
	if !ok {
		return 0, fmt.Errorf("account %q not found", id)
	}
	return b, nil
}

func check(label string, req TransferRequest, store BalanceStore, wantErr bool) {
	err := Validate(req, store)
	got := err != nil
	if got == wantErr {
		if err != nil {
			fmt.Printf("PASS  %-40s → error: %v\n", label, err)
		} else {
			fmt.Printf("PASS  %-40s → ok\n", label)
		}
	} else {
		fmt.Printf("FAIL  %-40s → got err=%v, wantErr=%v\n", label, err, wantErr)
	}
}

func main() {
	store := &fakeStore{balances: map[string]int64{
		"acc-001": 10000, // $100.00 in cents
		"acc-002": 5000,
	}}

	fmt.Println("=== Meridian Transfer Validator — all five rules ===\n")

	// Rule 1: positive amount
	check("zero amount (want error)",
		TransferRequest{From: "acc-001", To: "acc-002", Amount: 0, Currency: "USD"},
		store, true)
	check("negative amount (want error)",
		TransferRequest{From: "acc-001", To: "acc-002", Amount: -500, Currency: "USD"},
		store, true)
	check("positive amount (want ok)",
		TransferRequest{From: "acc-001", To: "acc-002", Amount: 5000, Currency: "USD"},
		store, false)

	// Rule 2: currency required
	check("empty currency (want error)",
		TransferRequest{From: "acc-001", To: "acc-002", Amount: 1000, Currency: ""},
		store, true)

	// Rule 3: accounts must differ
	check("same account (want error)",
		TransferRequest{From: "acc-001", To: "acc-001", Amount: 1000, Currency: "USD"},
		store, true)

	// Rule 4: sufficient balance
	check("insufficient balance (want error)",
		TransferRequest{From: "acc-002", To: "acc-001", Amount: 9999, Currency: "USD"},
		store, true)
	check("exact balance (want ok)",
		TransferRequest{From: "acc-002", To: "acc-001", Amount: 5000, Currency: "USD"},
		store, false)

	// Rule 5: integer cents (type-level — 1 cent is valid)
	check("1 cent transfer (want ok)",
		TransferRequest{From: "acc-001", To: "acc-002", Amount: 1, Currency: "USD"},
		store, false)

	fmt.Println("\nAll rules verified. The type system prevents float64 entirely.")
}
```

## Table-Driven TDD and Test Doubles

Once you have a few cycles under your belt, two techniques compound your velocity: **growing the table** instead of writing new test functions, and **faking dependencies** with hand-written structs instead of a mock framework.

### Growing the table

In TDD, the test table starts with one row per cycle and *grows* as you discover new rules. You don't write the full table upfront — you don't know all the cases yet. You add a row, watch it fail, make it pass, refactor, add another row.

```go
// validator_test.go — the table grows with each TDD cycle
func TestValidate(t *testing.T) {
	store := &fakeStore{balances: map[string]int64{
		"acc-rich": 100000,
		"acc-poor": 50,
	}}

	tests := []struct {
		name    string
		req     TransferRequest
		wantErr bool
	}{

	for _, tc := range tests {
		t.Run(tc.name, func(t *testing.T) {
			err := Validate(tc.req, store)
			if (err != nil) != tc.wantErr {
				t.Errorf("got err=%v, wantErr=%v", err, tc.wantErr)
			}
		})
	}
}
```

The table is now the **documentation** of the validator's behavior. Every rule is a row. New rules become new rows — and you TDD each one by adding the row (watch it fail), then writing the minimum code.

### Test doubles via interfaces — no framework needed

The `fakeStore` you saw above is a **test double** — a stand-in for the real `BalanceStore` (Postgres in production). Hand-written. No `mockgen`, no `testify/mock`. Here's the pattern in full:

```go
// The interface — defined in the consumer package, shaped by what Validate actually calls.
type BalanceStore interface {
	Balance(id string) (int64, error)
}

// The fake — three fields, one method. Enough to drive five rule cycles.
type fakeStore struct {
	balances map[string]int64
	// Optional: record calls for assertion.
	calls    []string
}

func (f *fakeStore) Balance(id string) (int64, error) {
	if f.calls != nil {
		f.calls = append(f.calls, id)
	}
	b, ok := f.balances[id]
	if !ok {
		return 0, fmt.Errorf("account %q not found", id)
	}
	return b, nil
}
```

You can also make the fake *configurable* — return a preset error to test the "balance lookup fails" path:

```go
type fakeStore struct {
	balances map[string]int64
	err      error // if non-nil, Balance always returns this error
}

func (f *fakeStore) Balance(id string) (int64, error) {
	if f.err != nil {
		return 0, f.err
	}
	b, ok := f.balances[id]
	if !ok {
		return 0, fmt.Errorf("account %q not found", id)
	}
	return b, nil
}
```

Now testing the "DB is down" path is one line: `store := &fakeStore{err: errors.New("connection refused")}`.

<Callout kind="note" title="When to reach for a mock framework">

Hand-written fakes are the right default for small interfaces like `BalanceStore`. Reach for a framework (`gomock`, `testify/mock`) when: (1) the interface has eight methods and you only care about two, (2) you need to assert exact call sequences across many tests, or (3) the interface is from a third-party library and a realistic fake would be hundreds of lines. Start with fakes. Add a framework when fakes *hurt*, not before.

</Callout>

## The Testing Pyramid — Honest Take

<ConceptGrid cols={3}>
  <ConceptCard label="Unit tests (wide base)">Fast, isolated, deterministic. One function, controlled inputs, fakes for deps. Milliseconds per test. Run on every file save. Your primary feedback loop. The validator tests you just wrote are all unit tests.</ConceptCard>
  <ConceptCard label="Integration tests (middle)">Slower — real deps in containers. Verify your SQL queries, Redis pipelines, Kafka offset handling against the actual system. Run in CI on every PR, gated behind a build tag so they don't slow your local loop.</ConceptCard>
  <ConceptCard label="End-to-end tests (narrow top)">Slowest. Drive the full Meridian stack — real services, real network, real database. Catch integration mismatches that survive unit and integration tests. Run pre-deploy, not per commit. Keep this layer thin.</ConceptCard>
  <Gotcha>If 80% of your tests are E2E, they will be slow, flaky, and point you at the wrong layer when they fail. A failing unit test names the function. A failing E2E test names a symptom. Build the pyramid right: wide unit base, selective integration middle, narrow E2E top.</Gotcha>
</ConceptGrid>

### When TDD genuinely helps

TDD shines brightest for code with **clear rules, pure logic, and minimal external state**. The Meridian validator is the canonical example: five rules, no ambiguity, no UI, no network. Every new rule starts as a test. You can't build the wrong thing because the test specifies exactly what "right" means before you start.

More categories where TDD earns its keep:

- **Money math.** Every arithmetic function that touches cents: fee calculations, split transfers, coupon application, rounding rules. The rules are exact; the tests are exact; the feedback is instant.
- **Parsers and serializers.** A function that turns a string into a structured request has a crisp contract. Fuzz it and TDD it — they compose naturally.
- **State machines.** Transfer statuses (`pending → processing → settled → failed`) are just rules. TDD builds the transition table while keeping illegal states caught immediately.
- **Pure algorithms.** Sorting, batching, aggregation. No deps to fake; tests run in microseconds.

### When TDD gets in the way

TDD is a discipline, not a commandment. The engineers who apply it dogmatically to everything produce slow feedback loops and fragile test suites. Here's the honest map:

**Exploratory / prototype code.** You don't know the right shape yet. Writing tests for an API you haven't designed slows exploration. Spike first — write throwaway code without tests — then TDD the parts that survive into production.

**UI and visual code.** Testing whether a button *looks right* via TDD is theater. Test the logic behind the button (event handlers, state transitions, data formatting) with unit tests; use manual or screenshot tests for the visual layer.

**Integration glue.** Code whose only job is wiring two libraries together — a Postgres driver to your repository layer — is often better tested with a real integration test than a sea of fakes. TDD with fakes for glue code tests the glue's test, not the glue's behavior.

**Pure throwaway scripts.** A one-shot data migration, a CLI tool you'll run once, CI helper scripts. Test the *logic* inside them if it's reusable; don't TDD the scaffolding.

<Callout kind="pro" title="The honest TDD adoption advice">

Start with TDD for the layer you're building today, not your entire codebase. Pick the next function you need to write — if it has clear rules and no UI, TDD it. Run the red-green-refactor loop five times. Then decide if it helped. Adoption by experience beats adoption by mandate every time. I've seen teams mandate TDD on everything and produce test suites full of tests that test nothing — because they were written to satisfy a process, not to catch bugs. Don't be those people.

</Callout>

<UnderTheHood title="What the Go test runner does in go test — and why it makes TDD fast">

When you run `go test ./...`, the Go tool compiles a separate test binary for each package. The binary includes all `*_test.go` files plus the package under test, and links in the `testing` package. There is no external test runner, no config file, and no startup overhead beyond compilation.

As of Go 1.26, the test cache (`GOCACHE`) stores passing test results and skips re-running tests whose inputs (source files, build flags, environment) haven't changed. `go test` with a cold cache compiles and runs; with a warm cache it exits instantly with a `(cached)` tag. This cache is precise: touching any source file in the package invalidates only that package's cache entry.

The incremental compilation model matters for TDD: with a small, focused package (your validator), the compile-test cycle is typically under a second. That tight feedback loop — write test, see red, write code, see green — is only possible because Go's compiler is this fast. In languages with slower build times, TDD's rhythm breaks down. Go's compile speed is not an accident; it was a design goal, and TDD is one of its beneficiaries.

For the red-green loop specifically: compile errors are a *valid red state*. The Go compiler's error messages are precise enough that a compile-error red tells you exactly what's missing. "undefined: Validate" on line 12 of your test is the same useful signal as "got nil, want error." Both mean: write code.

</UnderTheHood>

<Exercise n={3} title="Add a sixth validator rule — TDD a daily limit" level="medium">

Add a sixth rule to the Meridian transfer validator: **a single transfer may not exceed 1,000,000 cents ($10,000.00)**. This is a simple constant cap — no store call needed.

TDD it: add rows to the table first (over-limit, exactly-at-limit, under-limit), run to get red, then add the minimum check to `Validate`.

<Solution>

```go
// Add these rows to the test table:
{"over daily limit", TransferRequest{From: "acc-rich", To: "acc-poor", Amount: 1_000_001, Currency: "USD"}, true},
{"exactly at limit", TransferRequest{From: "acc-rich", To: "acc-poor", Amount: 1_000_000, Currency: "USD"}, false},
{"under limit",      TransferRequest{From: "acc-rich", To: "acc-poor", Amount: 999_999, Currency: "USD"}, false},

// And add to Validate (minimum code — one new const and one conditional):
const maxTransferCents int64 = 1_000_000 // $10,000.00 per transfer

func Validate(r TransferRequest, store BalanceStore) error {
	if r.Amount <= 0 {
		return errors.New("amount must be positive cents")
	}
	if r.Amount > maxTransferCents {
		return fmt.Errorf("amount %d exceeds per-transfer limit of %d cents",
			r.Amount, maxTransferCents)
	}
	if r.Currency == "" {
		return errors.New("currency is required")
	}
	if r.From == r.To {
		return errors.New("source and destination accounts must differ")
	}
	if store != nil {
		bal, err := store.Balance(r.From)
		if err != nil {
			return fmt.Errorf("balance lookup: %w", err)
		}
		if bal < r.Amount {
			return fmt.Errorf("insufficient balance: have %d cents, need %d", bal, r.Amount)
		}
	}
	return nil
}
```

The constant belongs above the balance check — a transfer over the hard limit should be rejected before hitting the store. Order of checks is itself a design decision that TDD surfaces: the test for "over limit" will pass regardless of balance, which tells you the order is correct.

</Solution>

<Recap>

- **TDD is red → green → refactor, repeated.** Write a failing test (red), write minimum code to pass (green), clean up while green (refactor). Never write production code without a failing test demanding it.
- **The red step is a design step.** Writing the test first forces you to use your own API before it exists — surfacing awkward signatures, pushing you toward small injectable functions and consumer-defined interfaces.
- **Grow the validator test-by-test.** The Meridian transfer validator grew through five cycles: positive amount → sufficient balance → accounts differ → currency required → integer cents. Each rule was a failing test before it was a line of production code.
- **Table-driven TDD:** the table starts with one row and *grows* — one row per cycle. It becomes the living documentation of your function's behavior contract.
- **Test doubles via interfaces, hand-written.** Define the interface in the consumer package, shaped by what the test calls. Write a simple `fakeStore` struct. No framework until fakes genuinely hurt.
- **The testing pyramid:** lots of fast unit tests, fewer integration tests, fewest E2E. TDD builds the unit base — wide, fast, decisive.
- **TDD helps most** for pure logic with clear rules: validators, money math, parsers, state machines. **TDD gets in the way** for exploratory prototypes, pure UI/visual code, integration glue, and throwaway scripts. Be pragmatic, not dogmatic.
- **Money is integer cents. Always.** `int64` in the struct is the first line of defense. The type system is a rule you never have to test.

</Recap>
