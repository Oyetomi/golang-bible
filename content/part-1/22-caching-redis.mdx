## Why Caching

Let me set the scene.

It's 9:03 a.m. on a Monday. Meridian's platform just opened trading hours and every single user simultaneously hits the account dashboard — the same user profile rows from the `accounts` table, the same `JOIN` against plan details, the same `ORDER BY`. Your database has answered that question 40,000 times today and every answer was *identical*. Every query scanned the same pages off disk. Every connection was held for the same 18 milliseconds. The database is panting like a dog in July.

That is the problem caching solves: **don't do expensive work you already did**.

**On the job:** This exact scenario — the 9 a.m. trading-hour surge where a popular read path expires just as load spikes — is when you get paged. Getting caching wrong means DB connection exhaustion under predictable load. Getting it right means the DB barely notices.

<Define term="Cache" since="Caching & Redis (this chapter)">
A **cache** is a fast, temporary store that holds a copy of data so you can serve repeat reads without re-running the original expensive operation. When a request arrives, you check the cache first (a **hit** — return instantly) and only fall back to the database on a **miss**. The cache is always secondary — the database is the source of truth. A cache can be discarded and rebuilt at any time.
</Define>

<Define term="Redis" since="Caching & Redis (this chapter)">
**Redis** (Remote Dictionary Server) is an open-source, in-memory data structure store used as a cache, message broker, and queue backend. It processes commands in an event loop and is commonly fast enough for sub-millisecond simple operations on a local network, with throughput in the hundreds of thousands of operations per second on suitable hardware. For Meridian, Redis is the distributed caching tier shared across all service replicas — fast enough to absorb the dashboard read load at 9am without the database noticing.
</Define>

<Define term="TTL (time-to-live)" since="Caching & Redis (this chapter)">
A **TTL** is the duration after which a cache entry is considered expired and discarded. Every cached value is a promise with an expiry date. Setting a TTL of 5 minutes means you accept that cached data may be up to 5 minutes stale. If no TTL is set, the entry lives until evicted or explicitly deleted — a common source of serving permanently stale data.
</Define>

<Define term="Cache invalidation" since="Caching & Redis (this chapter)">
**Cache invalidation** is the act of removing or updating a cache entry when the underlying data changes, so future reads get fresh data instead of a stale copy. It is genuinely hard because you must invalidate at the right moment — too late and you serve lies; too early and you thrash the cache. The two main strategies are: let the TTL expire naturally (accept bounded staleness) or delete the key explicitly on every write (immediate consistency). At Meridian: write to the database first, then invalidate — never the reverse.
</Define>

<Define term="Cache-aside (lazy loading)" since="Caching & Redis (this chapter)">
**Cache-aside** is the most common caching pattern: the application code owns the cache relationship. On a read, check the cache; on a miss, go to the database, store the result in the cache, and return it. On a write, update the database and then invalidate (or update) the cache key. The cache is populated lazily — only on a miss — rather than eagerly pre-loaded. It matters because it keeps the application in control of exactly what gets cached and for how long.
</Define>

<Define term="Cache stampede / thundering herd" since="Caching & Redis (this chapter)">
A **cache stampede** (also called a thundering herd) occurs when a heavily-read cache key expires and many concurrent requests all miss simultaneously, then all independently run the same expensive database query. At Meridian's 9am peak, a single expired dashboard key can translate to 500 simultaneous `SELECT` queries — enough to exhaust the connection pool and take the database down. It is the most common caching failure in production.
</Define>

<Define term="Singleflight" since="Concurrency Patterns (Part 2)">
**Singleflight** (`golang.org/x/sync/singleflight`) is a Go package that deduplicates concurrent function calls sharing the same key. When N goroutines all call `group.Do("key", fn)` simultaneously, exactly **one** runs `fn`; the others block and receive the same result when it returns. For caching, this collapses a stampede of N concurrent cache misses into a single database call. It is the standard fix for the thundering herd problem in Go services.
</Define>

Caching sits between the caller (your HTTP handler) and the source of truth (the database) and answers known questions from fast memory. The benefits come in three flavors.

<ConceptGrid cols={3}>
  <ConceptCard label="Latency reduction">A Redis GET is often under 1ms over a local network. A Postgres query against a warm index might be 5–20ms. Against a cold query plan or a heavy JOIN, it's 100ms+. Caching turns a slow path into a fast one for every repeat read.</ConceptCard>
  <ConceptCard label="Load shedding">Ten thousand requests per second hitting Redis is trivial — Redis is a single-threaded in-memory store that handles hundreds of thousands of ops/sec. Ten thousand requests per second hitting Postgres is a crisis. Caching keeps your DB breathing during traffic spikes.</ConceptCard>
  <ConceptCard label="Protecting the DB">Databases are stateful, hard to scale horizontally, and expensive to run. They are the thing you protect. A cache is a sacrificial shield — it can be blown away and rebuilt, because the DB is the source of truth. The cache is expendable. The DB is not.</ConceptCard>
  <Gotcha>Caching does not make incorrect data correct — it makes incorrect data *faster*. A cache is only as trustworthy as its invalidation discipline. Serve stale data long enough and your users start making decisions on lies. The discipline to know *what* to cache, *how long* to cache it, and *when to bust it* is what separates good engineers from people who've never been paged at 2 a.m. over stale prices.</Gotcha>
</ConceptGrid>

### The cost you're actually paying

Before you cache everything in sight, understand what you're signing up for. A cache introduces a second system that must be kept consistent with the first. Every cached piece of data is a potential lie — a promise that this is still true. Your job is to manage that promise honestly.

The trade-off: **freshness vs. speed vs. load**. You are permanently choosing somewhere on that triangle. Pure freshness (no cache) costs speed and load. Pure speed (long TTL, no invalidation) costs freshness. Good caching is knowing where on that triangle each piece of data actually belongs — and being honest about it.

<Callout kind="pro" title="The rule of caching discipline">

Only cache data that is either (a) expensive to compute and stable for a known window, or (b) read many times between writes. If data changes on every read or after every write, a cache adds complexity without benefit. If data must always reflect the authoritative value (like a money balance — we'll cover this), a cache is a trap.

</Callout>

## Caching Layers

Caching isn't one thing. There are multiple layers where you can intercept a request and serve a pre-computed answer — each with different trade-offs in latency, consistency, scope, and complexity.

<ConceptGrid cols={3}>
  <ConceptCard label="In-process (L1)">Data stored directly in your Go process's heap — a `sync.Map`, a plain `map` protected by a `sync.RWMutex`, or a library like `patrickmn/go-cache` or `dgraph-io/ristretto`. Fastest possible: a memory read. Scope is one process — every replica has its own copy. Works brilliantly for small, infrequently changing, read-heavy data like config, feature flags, or a small product list.</ConceptCard>
  <ConceptCard label="Distributed (L2)">A dedicated caching service — Redis or Memcached — shared across all replicas. Millisecond latency over the network instead of nanoseconds in-process, but consistent across every instance and far larger capacity than one process's heap. This is the workhorse tier for most backend services.</ConceptCard>
  <ConceptCard label="CDN / edge (L3)">HTTP-layer caching at a CDN edge node for public, cacheable responses. Covered in depth in the previous chapter (File Servers & CDNs). Relevant here because caching strategy at the CDN layer (Cache-Control headers, cache busting via versioned URLs, purge APIs) is the same discipline applied at the edge rather than inside your service.</ConceptCard>
  <Gotcha>In-process cache + multiple replicas = cache incoherence. Each pod has its own snapshot. When a product price changes, you must either accept that different pods serve different prices for a few seconds (often fine), or use a distributed cache so all replicas share the same view (required when consistency matters). Pick your layer based on your consistency requirement, not just your latency requirement.</Gotcha>
</ConceptGrid>

### Tying back to the CDN chapter

In the previous chapter (File Servers & CDNs) we set `Cache-Control: public, max-age=3600` on static assets and used versioned URLs to bust the CDN cache when assets changed. That *is* caching strategy — just applied at the HTTP layer. The same principles apply here: TTLs express how long you trust the data, versioned keys / fingerprinted URLs bust the cache explicitly, and `stale-while-revalidate` is the HTTP equivalent of serving from cache while refreshing in the background. Keep that mental model — it's the same problem.

## Redis as the Workhorse

Redis (Remote Dictionary Server) is an in-memory data structure store. It's not a database in the ACID sense — it's a fast, specialized tool for holding data that you can afford to reconstruct if it disappears. In production, you will use it for caching, session storage, rate-limiting counters, pub/sub, job queues (Asynq, later in the course), and distributed locks.

<UnderTheHood title="What Redis actually is under the hood (Go 1.26 baseline)">

Redis is a single-threaded event loop written in C. All command processing is serial — no locking, no concurrency inside the server. This sounds like a liability but is a superpower: no mutex contention, no deadlocks, predictable latency. The single thread reads commands from a non-blocking socket, executes them against the in-memory hash table, and writes responses. I/O multiplexing (epoll/kqueue) lets one thread manage thousands of client connections simultaneously.

Data lives in a hash table keyed by string. The value can be one of several internal encodings — plain string, integer, list, hash, sorted set, hyperloglog, stream, and more — but from the client's perspective they're all keyed by a string key. Redis selects a compact encoding (e.g. `listpack` for small hashes and sorted sets) that the server transparently promotes to a more general structure when the set grows.

**TTL** is implemented as a separate dictionary mapping keys to expiry timestamps. Two strategies run concurrently: (1) lazy expiry — check on access, discard if expired; (2) active expiry — a background job periodically samples random keys and discards expired ones. This means a key *can* persist past its TTL briefly if it's never accessed and the sampler hasn't hit it yet — in practice not a problem for caching, but relevant for strict expiry guarantees.

**Eviction** is triggered when `maxmemory` is reached. The policy (`allkeys-lru`, `volatile-lru`, `allkeys-lfu`, `noeviction`, etc.) determines which key gets dropped. For pure caching, `allkeys-lru` (evict least-recently-used among all keys) or `allkeys-lfu` (evict least-frequently-used) are the standard choices.

**Persistence** is optional: RDB snapshots (fork + write a point-in-time dump) and AOF (append-only log of every write command). For a pure cache, persistence is often disabled — the cache can always be reconstructed from the DB. Enabling RDB on a warm-up schedule reduces cache coldness after a restart.

Go 1.26 note: nothing about Go's runtime directly affects Redis internals, but the `go-redis` client uses Go's net/http-style connection pooling and goroutines for concurrent pipelining — the client-side mechanics we'll cover below are very much Go runtime territory. This description is a conceptual model of Redis's event loop; exact implementation details are version-specific to Redis itself, not Go.

</UnderTheHood>

### Core data types

You need to know six types cold. Everything else is a specialization.

<ConceptGrid cols={3}>
  <ConceptCard label="String">The universal type. Stores bytes — JSON, plain text, integers, binary blobs. Commands: `GET`, `SET`, `INCR`, `APPEND`. A `SET key value EX 60` sets a string with a 60-second TTL. The workhorse for caching serialized Go structs.</ConceptCard>
  <ConceptCard label="Hash">A map within a key — `HSET user:42 name Alice age 30`. Useful when you want to store and update individual fields of a struct without serializing and deserializing the whole thing. Commands: `HGET`, `HSET`, `HMGET`, `HDEL`.</ConceptCard>
  <ConceptCard label="List">An ordered sequence of strings, push/pop from either end. Natural job queue: `LPUSH queue job`, `BRPOP queue 0` (blocking pop). Commands: `LPUSH`, `RPUSH`, `LPOP`, `LRANGE`.</ConceptCard>
  <ConceptCard label="Set">Unordered collection of unique strings. Useful for tracking membership — active sessions, unique visitors. Commands: `SADD`, `SISMEMBER`, `SMEMBERS`, `SINTERSTORE`.</ConceptCard>
  <ConceptCard label="Sorted Set">Like a Set but every member has a score (float). Sorted by score. Perfect for leaderboards, rate-limiting windows, delayed jobs. Commands: `ZADD`, `ZRANGE`, `ZRANGEBYSCORE`.</ConceptCard>
  <ConceptCard label="Streams">Append-only log with consumer groups — Redis's answer to Kafka for lightweight message passing. Beyond caching scope; mentioned for completeness. Commands: `XADD`, `XREAD`, `XREADGROUP`.</ConceptCard>
</ConceptGrid>

### Driving Redis from Go with `go-redis`

The canonical Go client is `github.com/redis/go-redis/v9`. It wraps every Redis command as a typed Go method, handles connection pooling, and supports pipelining and pub/sub natively.

```go
package main

import (
	"context"
	"fmt"
	"time"

	// go get github.com/redis/go-redis/v9
	"github.com/redis/go-redis/v9"
)

func main() {
	// Connect. UniversalClient covers standalone, sentinel, and cluster.
	rdb := redis.NewClient(&redis.Options{
		Addr:     "localhost:6379",
		Password: "",
		DB:       0,
	})
	ctx := context.Background()

	// SET with a 60-second TTL — e.g. a Meridian account profile.
	err := rdb.Set(ctx, "profile:42", `{"id":42,"name":"Alice","plan":"Business"}`, 60*time.Second).Err()
	if err != nil {
		panic(err)
	}

	// GET — returns redis.Nil if the key is missing or expired.
	val, err := rdb.Get(ctx, "profile:42").Result()
	if err == redis.Nil {
		fmt.Println("cache miss")
	} else if err != nil {
		panic(err)
	} else {
		fmt.Println("cache hit:", val)
	}

	// TTL — how long does this key have left?
	ttl, _ := rdb.TTL(ctx, "profile:42").Result()
	fmt.Println("ttl:", ttl) // e.g. 59s
}
```

### Pipelining: batching commands to cut round-trips

Every Redis command is a round-trip: send, wait, receive. If you need to set 100 keys, 100 round-trips at 0.5ms each is 50ms. A pipeline batches commands into one write and one read, cutting that to ~0.5ms total.

```go
package main

import (
	"context"
	"fmt"
	"time"

	"github.com/redis/go-redis/v9"
)

// batchCacheProducts writes multiple product entries in a single pipeline.
// Without pipelining: N round-trips at ~0.5ms each = N×0.5ms.
// With pipelining: 1 round-trip regardless of N.
func batchCacheProducts(ctx context.Context, rdb *redis.Client, products map[string]string) error {
	pipe := rdb.Pipeline()
	for key, val := range products {
		// Queue the command — nothing is sent yet.
		pipe.Set(ctx, key, val, 5*time.Minute)
	}
	// Flush the pipeline: one network write, one network read.
	_, err := pipe.Exec(ctx)
	return err
}

func main() {
	rdb := redis.NewClient(&redis.Options{Addr: "localhost:6379"})
	ctx := context.Background()

	products := map[string]string{
		"product:1": `{"id":1,"name":"Meridian Starter Plan"}`,
		"product:2": `{"id":2,"name":"Meridian Business Plan"}`,
		"product:3": `{"id":3,"name":"Meridian Enterprise Plan"}`,
	}

	if err := batchCacheProducts(ctx, rdb, products); err != nil {
		fmt.Println("error:", err)
		return
	}
	fmt.Println("3 keys cached in one pipeline round-trip")
}
```

### An in-process cache demo (fully runnable in the sandbox)

Here's a self-contained example you can actually run: a naive in-process cache with TTL eviction, demonstrating the GET/SET/miss pattern without any external dependency.

```go
package main

import (
	"fmt"
	"sync"
	"time"
)

// entry is one cached item with its expiry.
type entry struct {
	value     string
	expiresAt time.Time
}

// Cache is a simple in-memory TTL cache.
// In production, use Redis for this — this is pedagogical.
type Cache struct {
	mu    sync.RWMutex
	items map[string]entry
}

// NewCache creates an empty cache.
func NewCache() *Cache {
	return &Cache{items: make(map[string]entry)}
}

// Set stores a value with a TTL.
func (c *Cache) Set(key, val string, ttl time.Duration) {
	c.mu.Lock()
	defer c.mu.Unlock()
	c.items[key] = entry{value: val, expiresAt: time.Now().Add(ttl)}
}

// Get returns (value, true) on a hit, ("", false) on a miss or expired key.
func (c *Cache) Get(key string) (string, bool) {
	c.mu.RLock()
	e, ok := c.items[key]
	c.mu.RUnlock()
	if !ok || time.Now().After(e.expiresAt) {
		return "", false // miss or expired
	}
	return e.value, true
}

func main() {
	c := NewCache()

	// Warm the cache with a Meridian account profile.
	c.Set("profile:42", `{"id":42,"name":"Meridian Account Profile"}`, 2*time.Second)

	if val, ok := c.Get("profile:42"); ok {
		fmt.Println("HIT:", val)
	}

	// Wait for expiry.
	time.Sleep(3 * time.Second)

	// MISS — key expired.
	if _, ok := c.Get("profile:42"); !ok {
		fmt.Println("MISS: key expired, go to the database")
```

## Cache Strategies

There are four patterns for keeping a cache and a database in sync. Each has a different read path, write path, and consistency profile. Know all four. Pick based on your workload.

### Cache-aside (lazy loading)

The application code owns the cache. On a read: check the cache first; on a miss, go to the database, populate the cache, return the result. On a write: write to the database, then *invalidate* (or update) the cache.

This is the most common pattern and the one you'll use 80% of the time. At Meridian, the account profile read path (`GET /accounts/{id}/profile`) uses cache-aside: profile data is read on every dashboard load but updated rarely, so caching it for 5 minutes cuts database load dramatically.

**On the job:** Cache-aside is correct for read-heavy, infrequently-written data. If your write rate approaches your read rate, you're adding cache churn with little benefit. Measure before you cache.

### Read-through

Similar to cache-aside, but the *cache layer* handles the DB fallback — not the application. Your application only ever talks to the cache; on a miss, the cache fetches from the DB itself. Libraries like `ristretto` with a `Loader` func implement this pattern.

In Go, the distinction is mostly architectural: cache-aside logic lives in your service code (explicit), read-through logic lives in the cache client (implicit). Read-through is cleaner when many code paths need the same entity — you can't forget the fallback because the cache handles it.

### Write-through

On every write, the application writes to both the cache and the database *synchronously* — the cache is always up to date. Reads are always cache hits (no cold misses). The trade-off: every write is slower (two writes instead of one), and you bear the cost of caching data that may only be read once.

Write-through is the right choice when read latency is more critical than write latency, and when you can afford to keep every written value in cache.

### Write-behind (write-back)

The application writes to the cache immediately and returns. The cache asynchronously flushes writes to the database in the background. This gives the lowest write latency but the highest risk: if the cache crashes before flushing, you lose writes. Only appropriate for data where some loss is acceptable. For financial data: never.

  <ConceptCard label="write-through vs. write-behind">Write-through: synchronous, safe, slower writes, always warm cache. Write-behind: asynchronous, fast writes, risk of data loss. ## Invalidation — The Hard Part

Phil Karlton's famous quip: there are only two hard problems in computer science — cache invalidation and naming things. He was right. Invalidation is where good caching discipline ends and subtle production bugs begin.

### TTL: time-based expiry

The simplest strategy: every cache entry has a time-to-live. When it expires, the next read is a miss and the value is refreshed from the database. You accept that cached data may be up to TTL seconds stale.

**Choosing a TTL** is a business decision disguised as a technical one:
- Product catalog that changes a few times a day → TTL of 5–15 minutes is fine.
- Exchange rate that changes every second → TTL of 1–5 seconds, or skip caching entirely.
- User session → TTL that matches your session expiry.
- Account balance → no TTL will make this safe; don't cache the authoritative balance (more soon).

### Explicit invalidation (cache busting)

When data changes, actively delete or update the cache key. This gives you immediate consistency rather than waiting for TTL expiry.

```go
// InvalidateProduct deletes the cache entry for a product.
// Call this on every write to the products table.
func InvalidateProduct(ctx context.Context, rdb *redis.Client, id int) error {
	key := fmt.Sprintf("product:%d", id)
	// DEL returns the number of keys deleted (0 if not present — not an error).
	return rdb.Del(ctx, key).Err()
}
```

<Callout kind="warn" title="The delete-then-write race">

Naively: delete the cache key, then update the database. Problem: between delete and DB update, a concurrent reader misses the cache, reads the *old* value from the database (update not yet committed), and re-populates the cache with stale data. The key is now fresh again with the old value.

The safer order for cache-aside: **write to the DB first, then invalidate the cache**. On the next read, the miss fetches the already-committed new value. This is a narrower race window but not zero — for truly strict consistency, you need distributed transactions or a queue, which is Part 3 territory.

</Callout>

### Versioned keys

Instead of invalidating, you change the key. The old key simply ages out via TTL; the new key starts fresh. Useful for bulk invalidation — change a version prefix and every old key becomes unreachable.

```go
// productKey generates a versioned cache key for a product.
// Bump version in config to invalidate all cached products at once.
func productKey(version, id int) string {
	return fmt.Sprintf("v%d:product:%d", version, id)
}
```

### Failure mode 1: cache stampede (thundering herd)

**On the job:** A stampede is not a theoretical concern — it is the most common caching failure in production. It happens every time a heavily-read key expires under load. At Meridian, the 9 a.m. trading-hour surge is the predictable trigger: every connected client loads the same account dashboard, the same profile TTL expires, and 500 goroutines all slam the database simultaneously.

Here is the scenario in full. It's 9:00 a.m. Meridian's account dashboard TTL expires. At that exact moment, 500 concurrent requests all miss the cache simultaneously. All 500 goroutines see a miss. All 500 go to the database. All 500 fire the same `SELECT` against the accounts table. The database goes from idle to 500 parallel queries in milliseconds. It falls over. Your service falls over.

This is a **cache stampede** — also called a thundering herd. It's not hypothetical; it happens any time a popular key expires under load.

<Callout kind="tip" title="sync.WaitGroup.Go — new in Go 1.25">

Go 1.25 added `wg.Go(func())` to `sync.WaitGroup`. It calls `wg.Add(1)`, launches the function in a new goroutine, and calls `wg.Done()` when the function returns. This replaces the three-line `wg.Add(1)` / `go func() { defer wg.Done(); ... }()` idiom you'll see in older code. All WaitGroup examples in this chapter use `wg.Go`.

</Callout>

### The `singleflight` fix

`golang.org/x/sync/singleflight` collapses duplicate concurrent calls into one. If 500 goroutines all call `group.Do("account:dashboard", fetchFromDB)` simultaneously, exactly *one* goroutine executes `fetchFromDB`. The other 499 block and wait. When the one goroutine returns, all 500 receive the same result. One DB query. Zero stampede.

<UnderTheHood title="How singleflight works inside (Go 1.26 baseline)">

`singleflight.Group` maintains a `map[string]*call` protected by a `sync.Mutex`. A `call` is a struct holding the in-flight request's `WaitGroup`, the result value, and the error. This is a conceptual model — treat it as such; the exact implementation is in `golang.org/x/sync/singleflight` and may evolve.

When you call `group.Do(key, fn)`:
1. Lock the mutex.
2. Look up the key in the map.
3. If a `call` exists (an in-flight request for this key): increment its `WaitGroup` counter, unlock the mutex, and call `c.wg.Wait()` — you block.
4. If no `call` exists: create a new `call`, add it to the map, unlock the mutex, and run `fn()` in the *current* goroutine. The function is not spawned in a new goroutine — it runs inline.
5. When `fn()` returns, store the result in `c.val` and `c.err`, remove the key from the map (while holding the mutex), then call `c.wg.Done()` — all waiting goroutines unblock and receive the same `c.val` / `c.err`.

The result is shared by value copy — every caller gets the same value. `shared` (the third return) is `true` if at least one other goroutine was waiting.

One important subtlety: `Do` blocks the calling goroutine (not a new one). If you're calling it from an HTTP handler, the handler goroutine itself blocks. For long-running fetches you may prefer `DoChan`, which returns a `<-chan Result` and lets you `select` on cancellation too. `DoChan` is the right choice for `context`-cancellable paths.

`singleflight` does *not* retry on error. If the one in-flight call fails, all waiters receive the error. For cache warming, handle errors in the caller and fall back gracefully — don't let one DB blip propagate to a thousand handlers.

`golang.org/x/sync/singleflight` is still the canonical tool as of Go 1.26 — there is no equivalent in the standard library.

</UnderTheHood>

### Failure mode 2: cache penetration

A user requests `product:99999` — a product that doesn't exist. Cache miss, DB miss, nothing to cache. If an attacker hammers your service with thousands of non-existent IDs, every request punches through to the database. Your cache provides zero protection.

The fix: cache negative results too. Store a sentinel value (e.g., `"__NOT_FOUND__"`) with a short TTL for missing keys.

```go
// cacheNegative caches a sentinel value for keys that don't exist in the DB.
// This prevents repeated DB lookups for non-existent resources.
func (s *ProductStore) GetProduct(
	ctx context.Context,
	rdb CacheClient,
	db DBClient,
	id int,
) (*Product, error) {
	key := fmt.Sprintf("product:%d", id)

	val, err := rdb.Get(ctx, key).Result()
	if err == nil {
		if val == "__NOT_FOUND__" {
			return nil, nil // fast negative — no DB hit
		}
		var p Product
		json.Unmarshal([]byte(val), &p)
		return &p, nil
	}

	// DB lookup.
	p, err := db.FindProduct(ctx, id)
	if err != nil {
		// not found — cache the sentinel for 60s
		rdb.Set(ctx, key, "__NOT_FOUND__", 60*time.Second)
		return nil, nil
	}
	b, _ := json.Marshal(p)
	rdb.Set(ctx, key, string(b), 5*time.Minute)
	return p, nil
}
```

### Failure mode 3: hot keys

A single Redis key receives an outsized share of all traffic — for example, the home page product list, or a viral item in a flash sale. Redis is fast but not infinitely so. A single key can become a bottleneck if enough goroutines hammer it simultaneously.

Mitigations:
- **Local read-through**: cache the hot key in-process (L1) with a very short TTL (1–5 seconds). Absorbs most of the Redis traffic.
- **Key replication**: write the value to N keys (`product:list:shard:0` … `:N-1`) and read from a random shard. Spreads the read load.
- **Read replicas**: Redis Cluster or sentinel with read replicas can distribute reads.

<Callout kind="warn" title="The stale-vs-correct trade-off: always be explicit">

Every TTL is a commitment to a maximum staleness window. `max-age=300` means you accept data up to 5 minutes old. That's fine for a product catalog. It is not fine for an account balance, an order status the user is waiting on, or a risk limit. Before you set a TTL, write down the business consequence of serving a 5-minute-old value. If the answer is "none, users won't notice," cache it. If the answer is "a user could over-spend their limit," do not cache the authoritative value — or cache a read-only derived form with explicit staleness guarantees documented in your service contract.

</Callout>

## Caching in Fintech

Here is where everything gets serious. I need you to hear this clearly.

**On the job:** The worst production incident I have seen from caching in fintech was not a stampede — it was a payment authorization that read a cached balance. A user had a zero balance; the cached value said otherwise. The payment went through. The reversal took three days and two engineering escalations to untangle. Don't be that engineer.

**Never cache an authoritative account balance.**

Not with a 1-second TTL. Not with explicit invalidation. Not with singleflight. The ledger balance is the source of truth. It is the thing every financial decision depends on. If your service reads a stale balance — even for 100 milliseconds — a user could authorize a payment they cannot cover, or be blocked from a payment they can make. That is a financial error. In regulated environments, it is an audit finding.

At Meridian: you may cache the account *profile* (name, plan tier, notification prefs) for 5 minutes — it is read-heavy and financially inert. You must *never* cache `accounts.balance_cents` as the input to a payment authorization. The profile is safe to cache. The balance is not.

<Callout kind="warn" title="The one rule you cannot cache around">

The authoritative balance lives in the database, in a transaction, with `SELECT ... FOR UPDATE` semantics. Full stop. No cache sits between a payment authorization and the balance check. This is not a performance problem to optimize — it's a correctness constraint. Accept the DB latency or redesign the architecture (read replicas, CQRS) to solve it honestly.

</Callout>

### What you CAN cache safely in fintech

Just because you can't cache the balance doesn't mean you cache nothing. There's plenty of derived, read-only, or bounded-staleness data that's safe and valuable to cache.

<ConceptGrid cols={2}>
  <ConceptCard label="Product / instrument catalog">Product names, descriptions, fee schedules, supported currencies. These change infrequently (a few times per day at most). Cache with a 5–15 minute TTL. Explicit invalidation on admin writes.</ConceptCard>
  <ConceptCard label="FX rates (bounded staleness)">Exchange rates change constantly, but for *display* purposes (showing the user what their GBP is worth in USD) you can serve a rate that's up to 30–60 seconds stale, as long as *transactions* always use a freshly fetched rate at execution time. Cache the display rate; never cache the execution rate.</ConceptCard>
  <ConceptCard label="User profile / preferences">Name, address, notification settings. These are read on every page load and change rarely. Cache with a 1–5 minute TTL, invalidate on profile update. Safe: this data doesn't affect financial correctness.</ConceptCard>
  <ConceptCard label="Risk-limit thresholds">Configured limits like daily transfer caps may be safe to cache for a few seconds as *read-mostly* config — but invalidate immediately on limit changes, and always re-read before the final authorization decision. Treat with care.</ConceptCard>
  <Gotcha>Never cache a derived balance that becomes the input to a financial decision. "Cache the balance for display, then re-read it for the transaction" is fine — but you must re-read it. If your code has a path that authorizes a payment using the cached value, you have a financial bug. Test this path explicitly.</Gotcha>
</ConceptGrid>

### The right architecture: cache at the read model, not the write model

In a CQRS (Command Query Responsibility Segregation) architecture (covered in depth in Part 3's Event-Driven Architecture & Kafka chapter), you have a strict write model (the ledger) and a read model (derived views). **The cache belongs on the read model**. The write path (posting a transaction, authorizing a payment) always goes straight to the database. The read path (rendering the Meridian dashboard, showing recent transfers, displaying the "available balance" estimate for UI purposes) can be aggressively cached.

```go
// MeridianSafeBalanceRead returns the authoritative balance from the DB — never cached.
// Use this before any financial decision at Meridian (payment auth, limit checks).
// The FOR UPDATE lock prevents concurrent reads from seeing uncommitted writes.
func MeridianSafeBalanceRead(
	ctx context.Context,
	db *sql.DB,
	accountID int64,
) (int64, error) {
	var balanceCents int64
	// SELECT ... FOR UPDATE ensures we see committed data and hold a row lock
	// for the duration of any surrounding transaction.
	err := db.QueryRowContext(
		ctx,
		"SELECT balance_cents FROM accounts WHERE id = $1 FOR UPDATE",
		accountID,
	).Scan(&balanceCents)
	return balanceCents, err
}

// MeridianCachedDisplayBalance returns a best-effort balance for UI display only.
// This value MAY be up to 30 seconds stale. Never use for payment authorization.
func MeridianCachedDisplayBalance(
	ctx context.Context,
	rdb *redis.Client,
	db *sql.DB,
	accountID int64,
) (int64, error) {
	key := fmt.Sprintf("meridian:display_balance:%d", accountID)

	if val, err := rdb.Get(ctx, key).Int64(); err == nil {
		return val, nil // display HIT — may be slightly stale, that's fine
	}

	// Miss: read authoritative balance and cache for 30 seconds.
	balance, err := MeridianSafeBalanceRead(ctx, db, accountID)
	if err != nil {
		return 0, err
	}
	rdb.Set(ctx, key, balance, 30*time.Second)
	return balance, nil
}
```

```go
	defer a.mu.Unlock()

		return fmt.Errorf("insufficient funds: have %d, need %d", a.balance, cents)
```

<Exercise n={1} title="Build a TTL cache with eviction" level="easy">

Extend the `Cache` struct from this chapter to add a `Delete(key string)` method and a `Len() int` method that only counts non-expired keys. Write a `main` that sets three keys, deletes one, sleeps past the TTL of another, and verifies `Len()` returns 1.

<Solution>

```go
package main

import (
	"fmt"
	"sync"
	"time"
)

type entry struct {
	value     string
	expiresAt time.Time
}

type Cache struct {
	mu    sync.RWMutex
	items map[string]entry
}

func NewCache() *Cache { return &Cache{items: make(map[string]entry)} }

func (c *Cache) Set(key, val string, ttl time.Duration) {
	c.mu.Lock()
	defer c.mu.Unlock()
	c.items[key] = entry{value: val, expiresAt: time.Now().Add(ttl)}
}

func (c *Cache) Get(key string) (string, bool) {
	c.mu.RLock()
	e, ok := c.items[key]
	c.mu.RUnlock()
	if !ok || time.Now().After(e.expiresAt) {
		return "", false
	}
	return e.value, true
}

// Delete removes a key immediately — for explicit invalidation.
func (c *Cache) Delete(key string) {
	c.mu.Lock()
	defer c.mu.Unlock()
	delete(c.items, key)
}

// Len counts only non-expired keys.
func (c *Cache) Len() int {
	c.mu.RLock()
	defer c.mu.RUnlock()
	n := 0
	now := time.Now()
	for _, e := range c.items {
		if now.Before(e.expiresAt) {
			n++
		}
	}
	return n
}

func main() {
	c := NewCache()
	c.Set("a", "alpha", 5*time.Minute)   // survives
	c.Set("b", "beta", 100*time.Millisecond) // will expire
	c.Set("c", "gamma", 5*time.Minute)   // will be deleted

	c.Delete("c")
	time.Sleep(200 * time.Millisecond) // let "b" expire

	fmt.Println("Len:", c.Len()) // 1 — only "a" remains
}
```

`Delete` explicitly invalidates a key. `Len` scans and counts only live entries. In production, a background goroutine or periodic scan would remove expired entries from the map to free memory — this implementation lazily leaves stale entries until they're explicitly read or the Len scan discards them.

</Solution>

<Exercise n={2} title="Cache-aside GetOrSet helper" level="medium">

Write a generic function `GetOrSet[T any](ctx context.Context, c *Cache, key string, ttl time.Duration, fetch func() (T, error)) (T, error)` that implements the cache-aside pattern: check the cache first (unmarshal JSON), on a miss call `fetch`, marshal the result, cache it, and return. Use `encoding/json`. Then write a `main` that calls it twice for the same key and verifies the second call doesn't re-execute `fetch`.

<Solution>

```go
package main

	"context"
	"encoding/json"
	"fmt"
	"sync"
	"time"
)

type entry struct {
	value     string
	expiresAt time.Time
}

	mu    sync.RWMutex
	items map[string]entry
}

func NewCache() *Cache { return &Cache{items: make(map[string]entry)} }

func (c *Cache) Set(key, val string, ttl time.Duration) {
	c.mu.Lock()
	defer c.mu.Unlock()
	c.items[key] = entry{value: val, expiresAt: time.Now().Add(ttl)}

	if !ok || time.Now().After(e.expiresAt) {
		return "", false
	}

}

// GetOrSet is a generic cache-aside helper.
func GetOrSet[T any](
	ctx context.Context,
	c *Cache,
	key string,
	ttl time.Duration,
	fetch func() (T, error),
) (T, error) {
	// Check cache first.
	if raw, ok := c.Get(key); ok {
		var v T
		if err := json.Unmarshal([]byte(raw), &v); err == nil {
			return v, nil
		}
	}
	// Miss: call the fetch function.
	v, err := fetch()
	if err != nil {
		return v, err
	}
	// Populate the cache.
	b, err := json.Marshal(v)
	if err != nil {
		return v, err
	}
	c.Set(key, string(b), ttl)
	return v, nil
}

type Product struct {
	ID   int    `json:"id"`
	Name string `json:"name"`
}

func main() {
	c := NewCache()
	calls := 0

	fetch := func() (Product, error) {
		calls++
		fmt.Println("  DB fetch called (call #", calls, ")")
		return Product{ID: 1, Name: "Meridian Starter Plan"}, nil
	}

	ctx := context.Background()

	p1, _ := GetOrSet(ctx, c, "product:1", 5*time.Minute, fetch)
	fmt.Println("First call:", p1)

	p2, _ := GetOrSet(ctx, c, "product:1", 5*time.Minute, fetch)
	fmt.Println("Second call:", p2)

	fmt.Println("fetch called", calls, "time(s) — should be 1")
}
```

Generics (`[T any]`) let one function handle any JSON-serializable type without per-type boilerplate. The second call goes straight to the cache; `fetch` is never called again. This is the idiomatic Go pattern for a cache-aside read layer.

</Solution>

```go
		result := `[{"id":1},{"id":2}]`
		s.cache.Set(key, result, 5*time.Minute)
		return result, nil
	})
	if err != nil {
		return "", err
	}
	return v.(string), nil
}

	// wg.Go (Go 1.25) — calls Add(1) and launches the goroutine; Done is called automatically.

			store.GetProductList(context.Background())
		})

	wg.Wait()

	fmt.Printf("DB calls: %d (expected: 1)\n", calls)
```

```go
	for i := 0; i < 10; i++ {
		_, err := svc.Get(99999)
		if err == nil {
			fmt.Println("unexpected hit")
		}
	}

	fmt.Printf("\nDB calls: %d (expected: 1)\n", svc.dbCalls)
	if svc.dbCalls != 1 {
		fmt.Println("FAIL: DB was hit more than once")
	} else {
		fmt.Println("PASS: sentinel cached — only one DB call for 10 requests")
	}
}
```

After the first miss, the sentinel `"__NOT_FOUND__"` is stored in the cache with a 60-second TTL. Every subsequent request for the same non-existent ID hits the sentinel fast path and never touches the DB. This closes the cache penetration vector for non-existent resource attacks.

<Recap>

You've earned this:

- **Why caching**: latency, load shedding, protecting the database. A cache is a shield. The database is what you're protecting.
- **Caching layers**: in-process (fastest, per-process), distributed/Redis (milliseconds, shared), CDN (HTTP-layer, same discipline). Pick the layer based on your consistency requirement.
- **Redis**: event-loop command execution, low-latency simple operations, six core types. `go-redis/v9` is the idiomatic Go driver. Set TTLs. Use `allkeys-lru` for a pure cache. Pipeline batch writes.
- **Strategies**: cache-aside (lazy, most common), read-through (cache owns the fallback), write-through (sync, safe), write-behind (async, risky). Pick based on read/write ratio and durability needs.
- **Invalidation**: TTLs (accept bounded staleness), explicit delete (bust on write, write DB first), versioned keys (bulk invalidation by changing a prefix). Write to DB first, then invalidate.
- **Stampede / thundering herd**: concurrent misses all hammering the DB. Fix: `singleflight.Group.Do` (from `golang.org/x/sync/singleflight`, still the canonical tool as of Go 1.26) collapses N concurrent calls to one in-flight request. Every other caller blocks and receives the same result. Use `wg.Go` (Go 1.25) for the launcher goroutines — it replaces `wg.Add(1)` + `defer wg.Done()`.
- **Cache penetration**: non-existent keys punching through to DB on every request. Fix: cache a negative sentinel with a short TTL.
- **Hot keys**: single popular key overloading Redis. Fix: promote to L1 in-process cache or use key replication.
- **Fintech rule**: never cache an authoritative balance. At Meridian: cache the account profile safely; never cache `balance_cents` as input to payment authorization. Cache derived/display data with explicit staleness documentation. The write path always goes to the database.
