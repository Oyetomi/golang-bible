<HeroCard label="Part 1 · Chapter 22" title="Caching & Redis">

Here's the thing: every fast system has the same secret. It's not a clever algorithm. It's knowing when **not** to go to the database.

That's caching: answering a question from fast memory because you already answered it a moment ago. Done right, the database barely notices the 9 a.m. rush. Done wrong, the system confidently serves stale answers, or falls over the instant a popular entry expires. We'll do it right, with Redis as the shared cache, `go-redis` as the driver, and `singleflight` to stop a stampede. And you'll learn the one thing Meridian must never cache.

Every program here ran on Go 1.27 (Redis code against `go-redis` v9.22 and an in-memory Redis, `miniredis`), and the outputs are real.

## Why Caching

*Stop 1 of 6.*

### Step 1: the same question, forty thousand times

9:03 a.m., Monday. Every Meridian user opens the dashboard: the same profile rows, the same join against plan details. The database has answered that question 40,000 times this morning, and every answer was identical.

<Define term="Cache">
A **cache** is a fast, temporary copy of data you've already fetched or computed, kept so repeat reads skip the expensive work. A read that finds its answer in the cache is a **hit**; one that doesn't is a **miss**, and falls back to the real source. The database stays the source of truth: a cache can be thrown away and rebuilt at any time.
</Define>

<Define term="TTL (time-to-live)">
A **TTL** is how long a cached entry may be used before it expires. A 5-minute TTL is a promise you're making: "this answer may be up to 5 minutes old, and that's acceptable."
</Define>

<Define term="Cache-aside (lazy loading)">
**Cache-aside** is the most common pattern: on a read, check the cache; on a miss, read the database, store the answer in the cache, and return it. On a write, update the database, then delete the cached entry. Your application code manages the cache directly.
</Define>

### Step 2: what you buy, and what you pay

<ConceptGrid cols={3}>
  <ConceptCard label="Latency">A Redis `GET` on the same network is typically well under a millisecond; a query with a join can be tens of milliseconds, and an in-process map read is nanoseconds.</ConceptCard>
  <ConceptCard label="Load">Every hit is a query the database didn't run. That's capacity you get back for writes and the queries you can't cache.</ConceptCard>
  <ConceptCard label="Protection">Databases are the hardest part of the system to scale. A cache is a disposable shield in front of them.</ConceptCard>
  <Gotcha>A cache doesn't make wrong data right; it makes it faster. Every cached value is a claim that it's still true, and you're responsible for that claim.</Gotcha>
</ConceptGrid>

The trade is permanent: **freshness against speed and load**. Cache something only if it's (a) expensive to produce and stable for a known window, or (b) read many times between writes. If it must always be exactly current (Meridian's account balance, Stop 6), a cache is a trap.

**Recap.** A cache keeps a disposable copy close to the reader. Hits save latency and database load; the price is that cached answers can be stale.

## Caching Layers

*Stop 2 of 6.*

### Step 1: three places to keep a copy

<ConceptGrid cols={3}>
  <ConceptCard label="In-process (L1)">A map with a mutex, or a library such as `ristretto`, inside each Go process. A read is a memory access. But each replica has its own copy, and it's lost on restart.</ConceptCard>
  <ConceptCard label="Distributed (L2)">Redis, Valkey or Memcached, shared by every replica. A network round trip away, but one copy for everyone, far more capacity, and it survives your deploys.</ConceptCard>
  <ConceptCard label="CDN / edge (L3)">HTTP caching near users for public responses: ch21's `Cache-Control` and fingerprinted URLs.</ConceptCard>
</ConceptGrid>

A request tries the fastest layer first, and a hit in a slower layer is copied into the faster one on the way back. Watch what that does with two replicas:

That's fine for a product description and wrong for a price at checkout. Choose the layer by how much inconsistency the data can tolerate, then by speed. Short L1 TTLs (seconds) in front of Redis are a common compromise for very hot keys.

**Recap.** L1 is per-process and fastest; L2 is shared and consistent across replicas; L3 is the CDN. Each layer you add is another copy that can disagree.

## Redis as the Workhorse

*Stop 3 of 6.*

### Step 1: what Redis is

<Define term="Redis">
**Redis** is an in-memory data store: keys map to strings, hashes, lists, sets, sorted sets and streams, all held in RAM, with optional persistence to disk. It executes commands one at a time on a single main thread, which makes each command atomic and latency predictable. It's used as a cache, for sessions, rate-limit counters, queues and locks.
</Define>

Two notes on the landscape. Redis changed its license in 2024, and the Linux Foundation's **Valkey** fork is a drop-in replacement many clouds now run (Redis 8 later added an open-source AGPL option). The protocol and `go-redis` work with both.

<UnderTheHood title="Inside the server">

**One thread executes commands.** A single event loop reads requests from thousands of connections (epoll/kqueue) and runs them one at a time, so there are no locks inside the server and every command is atomic. Redis 6+ can use extra threads for network I/O, but command execution stays single-threaded. The flip side: one slow command (`KEYS *` over millions of keys, a long Lua script) stalls **every** client. Use `SCAN` to iterate.

**Expiry is lazy and sampled.** A key past its TTL is removed when someone touches it, and a background task samples keys with TTLs and removes expired ones, so memory is reclaimed even for keys nobody reads.

**Eviction happens at `maxmemory`.** The policy decides what goes: `allkeys-lru` or `allkeys-lfu` for a pure cache, the `volatile-*` variants to evict only keys that have a TTL, and `noeviction` (errors on write) for data you can't lose. `noeviction` on a cache turns "memory full" into "every write fails".

**Persistence is optional.** RDB snapshots and an append-only log exist; a pure cache often disables both, because the database can rebuild it.

</UnderTheHood>

### Step 2: the data types

<ConceptGrid cols={3}>
  <ConceptCard label="String">Any bytes: JSON, a number, a blob. `SET key value EX 60` stores with a 60-second TTL. `INCR` makes it a counter. The usual type for caching a serialized struct.</ConceptCard>
  <ConceptCard label="Hash">Fields within a key: `HSET user:42 name Ada plan pro`. Read or update one field without rewriting the whole value.</ConceptCard>
  <ConceptCard label="List">Push and pop at either end: a simple queue (`LPUSH` / `BRPOP` blocks until an item arrives).</ConceptCard>
  <ConceptCard label="Set">Unique members, fast membership tests: `SADD`, `SISMEMBER`.</ConceptCard>
  <ConceptCard label="Sorted set">Members ordered by a score: leaderboards, sliding-window rate limits, scheduled jobs (`ZADD`, `ZRANGEBYSCORE`).</ConceptCard>
  <ConceptCard label="Stream">An append-only log with consumer groups: lightweight messaging (`XADD`, `XREADGROUP`).</ConceptCard>
</ConceptGrid>

### Step 3: `go-redis`

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"time"

	"github.com/redis/go-redis/v9"
)

func main() {
	rdb := redis.NewClient(&redis.Options{Addr: "localhost:6379"}) // a pool, like sql.DB
	ctx := context.Background()

	// SET with a TTL.
	if err := rdb.Set(ctx, "profile:42", `{"id":42,"plan":"Business"}`, time.Minute).Err(); err != nil {
		panic(err)
	}

	// GET. A missing (or expired) key is the error redis.Nil, not an empty string.
	val, err := rdb.Get(ctx, "profile:42").Result()
	switch {
	case errors.Is(err, redis.Nil):
		fmt.Println("miss")
	case err != nil:
		fmt.Println("redis error:", err) // Redis is down: fall back to the database
	default:
		fmt.Println("hit:", val)
	}

	ttl, _ := rdb.TTL(ctx, "profile:42").Result()
	fmt.Println("ttl:", ttl)
}
```

Run against a Redis server, it printed `hit: {"id":42,"plan":"Business"}` and `ttl: 1m0s`; a `GET` of a missing key returned an error for which `errors.Is(err, redis.Nil)` was true. Treat `redis.Nil` (a miss) and any other error (Redis unreachable) differently: a cache outage should make you slower, not broken.

`redis.NewClient` returns a connection pool, like `sql.DB`: create one at startup and share it. `redis.NewUniversalClient` picks a standalone, Sentinel or Cluster client from the same options.

```go
func cacheProducts(ctx context.Context, rdb *redis.Client, products map[string]string) error {
	pipe := rdb.Pipeline()
	for key, val := range products {
		pipe.Set(ctx, key, val, 5*time.Minute) // queued, not sent
	}
	_, err := pipe.Exec(ctx) // one write, one read
	return err
}
```

A pipeline isn't a transaction: other clients' commands can run between yours. When you need all-or-nothing, use `rdb.TxPipelined` (`MULTI`/`EXEC`) or a Lua script.

In Go, generics let one helper do this for any type. This version runs in the sandbox, with a map standing in for Redis:

<GoPlayground>

```go
package main

import (
	"encoding/json"
	"fmt"
	"sync"
	"time"
)

type entry struct {
	raw       []byte
	expiresAt time.Time
}

// Cache is a stand-in for Redis: bytes in, bytes out, with a TTL.
type Cache struct {
	mu    sync.Mutex
	items map[string]entry
}

func (c *Cache) Get(key string) ([]byte, bool) {
	c.mu.Lock()
	defer c.mu.Unlock()
	e, ok := c.items[key]
	if !ok || time.Now().After(e.expiresAt) {
		return nil, false
	}
	return e.raw, true
}

func (c *Cache) Set(key string, raw []byte, ttl time.Duration) {
	c.mu.Lock()
	defer c.mu.Unlock()
	c.items[key] = entry{raw, time.Now().Add(ttl)}
}

// GetOrLoad is cache-aside for any type T.
func GetOrLoad[T any](c *Cache, key string, ttl time.Duration, load func() (T, error)) (T, error) {
	if raw, ok := c.Get(key); ok {
		var v T
		if json.Unmarshal(raw, &v) == nil {
			return v, nil // hit
		}
	}
	v, err := load() // miss: go to the source of truth
	if err != nil {
		return v, err
	}
	if raw, err := json.Marshal(v); err == nil {
		c.Set(key, raw, ttl)
	}
	return v, nil
}

type Profile struct {
	ID   int    `json:"id"`
	Plan string `json:"plan"`
}

func main() {
	c := &Cache{items: map[string]entry{}}
	queries := 0
	load := func() (Profile, error) {
		queries++
		return Profile{ID: 42, Plan: "Business"}, nil // pretend this is a 15 ms query
	}

	for range 3 {
		p, _ := GetOrLoad(c, "profile:42", 5*time.Minute, load)
		fmt.Printf("%+v\n", p)
	}
	fmt.Println("database queries:", queries)
}
```

### Step 2: the other three strategies

| Strategy | Read path | Write path | Use it for |
|---|---|---|---|
| **Cache-aside** | App checks cache, loads on miss | Write DB, then delete the key | Most read-heavy data |
| **Read-through** | App asks the cache; the cache loads on miss | Same as cache-aside | When many code paths read the same entity (the loader lives in one place) |
| **Write-through** | Always a hit | Write DB **and** cache, synchronously | Data read immediately after it's written |
| **Write-behind** | Always a hit | Write the cache, flush to the DB later | Counters and analytics you can afford to lose |

Write-behind acknowledges a write before the database has it. If the cache node dies first, the write is gone. For money, never.

<QuickCheck
  question="In cache-aside, when does an entry get into the cache?"
  options={["On every database write", "At application startup", "On a miss, after the database returns the value", "A background job pre-warms it"]}
  answer={2}
  explain="Cache-aside fills lazily: the first request to miss loads from the database and stores the result, so the cache holds exactly what's being read."
/>

**Recap.** Cache-aside: check, load on miss, store; on writes, update the database then delete the key. Read-through moves the loader into the cache layer; write-through keeps it warm; write-behind trades durability for speed.

## Invalidation — The Hard Part

*Stop 5 of 6.*

<ELI5
  concept="Why invalidation is the hard part"
  analogy="A note on the fridge that nobody updates when the plan changes."
  role="reader"
>

Putting something in a cache is easy. The hard part is taking it out at the right moment, because the cache has no idea the underlying data changed.

Two habits cover most of it. **Expiry** is a note with a date on it: after 60 seconds it's thrown away regardless, so staleness is bounded even when you miss a change. **Deletion** is tearing the note down when you change the plan: the code that writes the new value also deletes the cached one. Use both, so a missed deletion is a bounded bug instead of a permanent one.

</ELI5>

### Step 1: expiry, deletion, versions

<Define term="Cache invalidation">
**Invalidation** is removing (or replacing) a cached entry because the data behind it changed. The tools: a **TTL** (bounded staleness, no coordination), **explicit deletion** on write (fresher, but every write path must remember), and **versioned keys** (change the key's version prefix and every old entry becomes unreachable at once).
</Define>

Choosing a TTL is a business decision: how old may this answer be before someone is harmed? A plan catalog: 5–15 minutes. A display exchange rate: seconds. A session: its session lifetime. An account balance used for payment decisions: no TTL is short enough (Stop 6).

Deleting on write, in the right order:

```go
func (s *Service) UpdatePrice(ctx context.Context, planID string, cents int64) error {
	// 1. The database first: it's the truth.
	if _, err := s.db.ExecContext(ctx,
		`UPDATE plans SET price_cents = $1 WHERE id = $2`, cents, planID); err != nil {
		return err
	}
	// 2. Then drop the cached copy, so the next read reloads it.
	return s.rdb.Del(ctx, "plan:"+planID).Err()
}
```

Delete **before** the write, and a reader can miss, read the old row, and re-cache it before your write lands. After is safer. But not perfectly safe.

```go
	})
```

What to do about it, cheapest first:

- **Always set a TTL.** It turns this race from "wrong forever" into "wrong for at most N seconds". This alone is enough for most data.
- **Delete again shortly after the write** ("delayed double delete"), catching a reader that was mid-flight.
- **Store a version with the value** (the row's `updated_at` or a version number) and have writers or readers refuse to overwrite a newer entry with an older one.
- **Update the cache from the database's change stream** (Postgres logical replication, an outbox; Part 3) instead of from request handlers.

<Define term="Singleflight">
**Singleflight** (`golang.org/x/sync/singleflight`) deduplicates concurrent calls by key: while one call for key `k` is running, other callers of `Do(k, fn)` wait and receive its result instead of running `fn` again. It stores nothing afterwards; it only merges work that is in flight right now.
</Define>

The mechanism is small enough to write yourself, and that's the best way to understand it. This is a stdlib version of the idea (the real package adds error handling, `DoChan` and `Forget`), measured against 500 simultaneous misses:

<GoPlayground>

```go
package main

import (
	"fmt"
	"sync"
	"sync/atomic"
	"time"
)

var dbQueries atomic.Int32

// loadDashboard is the expensive query behind the hottest key of the day.
func loadDashboard() string {
	dbQueries.Add(1)
	time.Sleep(20 * time.Millisecond)
	return `{"plans":["Starter","Business"]}`
}

// flight is a tiny version of golang.org/x/sync/singleflight.Group:
// concurrent calls with the same key share ONE execution of fn.
type flight struct {
	mu    sync.Mutex
	calls map[string]*call
}

type call struct {
	wg  sync.WaitGroup
	val string
}

func (f *flight) Do(key string, fn func() string) string {
	f.mu.Lock()
	if c, ok := f.calls[key]; ok { // someone is already fetching: wait for them
		f.mu.Unlock()
		c.wg.Wait()
		return c.val
	}
	c := &call{}
	c.wg.Add(1)
	f.calls[key] = c
	f.mu.Unlock()

	c.val = fn() // only the first caller gets here
	c.wg.Done()

	f.mu.Lock()
	delete(f.calls, key) // the NEXT miss (after a future expiry) fetches again
	f.mu.Unlock()
	return c.val
}

func stampede(name string, get func() string) {
	dbQueries.Store(0)
	var wg sync.WaitGroup
	for range 500 { // 9:00:00: the key just expired and 500 requests arrive
		wg.Go(func() { get() })
	}
	wg.Wait()
	fmt.Printf("%-18s 500 concurrent misses -> %d database queries\n", name, dbQueries.Load())
}

func main() {
	stampede("no protection:", loadDashboard)

	f := &flight{calls: map[string]*call{}}
	stampede("with singleflight:", func() string { return f.Do("dashboard", loadDashboard) })
}
```

```text
with singleflight: 500 concurrent misses -> 1 database queries
```

In a real service, use the package, with the cache in front of it:

```go
import "golang.org/x/sync/singleflight"

type DashboardStore struct {
	rdb   *redis.Client
	db    *sql.DB
	group singleflight.Group
}

func (s *DashboardStore) Get(ctx context.Context) (string, error) {
	const key = "dashboard:v1"
	if v, err := s.rdb.Get(ctx, key).Result(); err == nil {
		return v, nil // hit: singleflight never involved
	}
	// Miss: at most one load per key per process at a time.
	ch := s.group.DoChan(key, func() (any, error) {
		v, err := loadDashboard(context.WithoutCancel(ctx), s.db) // don't let the first caller's cancel kill everyone's load
		if err == nil {
			s.rdb.Set(context.WithoutCancel(ctx), key, v, 5*time.Minute+jitter())
		}
		return v, err
	})
	select {
	case r := <-ch:
		if r.Err != nil {
			return "", r.Err
		}
		return r.Val.(string), nil
	case <-ctx.Done():
		return "", ctx.Err() // this caller gives up; the load continues for the others
	}
}
```

Details that matter in production:

- **`DoChan` + `select`** lets each caller honour its own context. With plain `Do`, every waiter is stuck until the load finishes.
- **`context.WithoutCancel`** (Go 1.21) keeps the load running if the first caller disconnects; otherwise one impatient client fails the load for everyone waiting on it.
- **Singleflight is per process.** Twenty replicas can still send twenty queries. That's usually fine; when it isn't, add a short Redis lock (`SET key NX EX 10`) so only one replica rebuilds, or refresh hot keys *before* they expire.
- **Add jitter to TTLs** (`5*time.Minute + rand.N(30*time.Second)`), so keys written together don't all expire together.
- Errors are shared too: if the one load fails, every waiter gets the error. Don't cache errors by accident.

### Step 4: two more failure modes

**Cache penetration** is requests for keys that don't exist: a miss in the cache, a miss in the database, nothing to cache, so every request reaches the database. Attackers do this deliberately with random IDs. The fix is to cache "not found" briefly, but *only* for a real not-found:

```go
p, err := s.loadProduct(ctx, id)
switch {
case errors.Is(err, ErrNotFound):
	s.rdb.Set(ctx, key, notFoundMarker, 60*time.Second) // a genuine absence: cache it briefly
	return nil, ErrNotFound
case err != nil:
	return nil, err // a database error: DON'T cache anything
}
```

Caching the marker on *any* error would turn a two-second database blip into a minute of "product not found" for real products.

**Hot keys** are single keys receiving a large share of all traffic (the home page, a viral product). Put a short L1 cache (1–5 seconds) in front of Redis for them, or spread reads across several copies of the key.

<Callout kind="warn" title="Write the staleness down">

Every TTL is a commitment: "this may be N seconds old". Before setting one, write down what goes wrong if a reader gets an N-second-old value. "Nobody notices" means cache it. "A customer overspends their limit" means don't.

</Callout>

**Recap.** Invalidate with TTL plus delete-after-write, and know the race that survives it. Stop stampedes with singleflight (`DoChan`, `WithoutCancel`, jittered TTLs). Cache "not found" only for genuine absences.

### Step 2: what you can cache

<ConceptGrid cols={2}>

Add `Delete(key string)` and `Len() int` (counting only unexpired entries) to a TTL cache. Set three keys, delete one, let another expire, and show `Len()` is 1.

```go
package main

import (
	"fmt"
	"sync"
	"time"
)

type entry struct {
	value     string
	expiresAt time.Time
}

type Cache struct {
	mu    sync.RWMutex
	items map[string]entry
}

func NewCache() *Cache { return &Cache{items: make(map[string]entry)} }

func (c *Cache) Set(key, val string, ttl time.Duration) {
	c.mu.Lock()
	defer c.mu.Unlock()
	c.items[key] = entry{value: val, expiresAt: time.Now().Add(ttl)}
}

// Delete removes a key immediately: explicit invalidation.
func (c *Cache) Delete(key string) {
	c.mu.Lock()
	defer c.mu.Unlock()
	delete(c.items, key)
}

// Len counts only unexpired entries.
func (c *Cache) Len() int {
	c.mu.RLock()
	defer c.mu.RUnlock()
	n, now := 0, time.Now()
	for _, e := range c.items {
		if now.Before(e.expiresAt) {
			n++
		}
	}
	return n
}

func main() {
	c := NewCache()
	c.Set("a", "alpha", 5*time.Minute)
	c.Set("b", "beta", 50*time.Millisecond)
	c.Set("c", "gamma", 5*time.Minute)

	c.Delete("c")
	time.Sleep(100 * time.Millisecond) // let "b" expire

	fmt.Println("Len:", c.Len())
}
```

Expired entries still occupy the map until something removes them; a real cache runs a periodic sweep (like ch17's reaper) or uses a library with bounded size.

Write a `ProductService.Get(id)` that caches found products for 5 minutes and genuine not-founds for 60 seconds, but caches nothing when the database returns another error.
```go
package main

import (
	"errors"
	"fmt"
	"time"
)

var (
	ErrNotFound = errors.New("not found")
	ErrDBDown   = errors.New("database unavailable")
)

const notFoundMarker = "\x00not-found"

type entry struct {
	raw       string
	expiresAt time.Time
}

type ProductService struct {
	cache    map[string]entry
	db       map[int]string
	dbCalls  int
	failNext bool // simulate one transient database error
}

func (s *ProductService) load(id int) (string, error) {
	s.dbCalls++
	if s.failNext {
		s.failNext = false
		return "", ErrDBDown
	}
	if v, ok := s.db[id]; ok {
		return v, nil
	}
	return "", ErrNotFound
}

func (s *ProductService) Get(id int) (string, error) {
	key := fmt.Sprint("product:", id)
	if e, ok := s.cache[key]; ok && time.Now().Before(e.expiresAt) {
		if e.raw == notFoundMarker {
			return "", ErrNotFound
		}
		return e.raw, nil
	}
	v, err := s.load(id)
	switch {
	case errors.Is(err, ErrNotFound):
		s.cache[key] = entry{notFoundMarker, time.Now().Add(60 * time.Second)}
		return "", err
	case err != nil:
		return "", err // transient: cache nothing
	}
	s.cache[key] = entry{v, time.Now().Add(5 * time.Minute)}
	return v, nil
}

func main() {
	s := &ProductService{cache: map[string]entry{}, db: map[int]string{1: `{"id":1}`}}

	for range 10 {
		s.Get(99999)
	}
	fmt.Println("10 requests for a missing ID -> database calls:", s.dbCalls)

	s.dbCalls, s.failNext = 0, true
	_, err := s.Get(1)
	fmt.Println("during the blip:", err)
	v, err := s.Get(1)
	fmt.Println("retry:", v, err, "(database calls:", s.dbCalls, ")")
}
```

```go
	defer s.mu.Unlock()
	if e, ok := s.cache[id]; ok && time.Now().Before(e.expiresAt) {
		fmt.Println("  hit")
		return e.p, true
	}
	fmt.Println("  miss: reading the database")
	p, ok := s.db[id]
	if ok {
		s.cache[id] = entry{p, time.Now().Add(5 * time.Minute)}
	}
	return p, ok
}

func (s *ProductService) Update(p Product) {
	s.mu.Lock()
	defer s.mu.Unlock()
	s.db[p.ID] = p        // 1. the source of truth first
	delete(s.cache, p.ID) // 2. then drop the cached copy
}

func main() {
	s := &ProductService{
		db:    map[int]Product{1: {1, "Starter", 999}},
		cache: map[int]entry{},
	}
	p, _ := s.Get(1)
	fmt.Println(p)
	p, _ = s.Get(1)
	fmt.Println(p)

	s.Update(Product{1, "Starter", 1499})
	p, _ = s.Get(1)
	fmt.Println("after update:", p)
}
```

One lock around everything makes this example race-free, which is exactly what a real Redis-plus-database setup can't do: there, Stop 5's race is possible, and the TTL is what bounds it.

</Solution>

</Exercise>

<Exercise n={5} title="Jittered TTLs" level="hard">

You cache 1,000 product keys in one batch job at 03:00 with a 1-hour TTL, and at 04:00 every one of them expires in the same second. Write `ttlWithJitter(base time.Duration, spread float64) time.Duration` using `math/rand/v2`, and show the spread of expiry times for 1,000 keys with and without jitter.

<Solution>

```go
package main

import (
	"fmt"
	"math/rand/v2"
	"time"
)

// ttlWithJitter returns base plus up to spread×base of random extra time.
func ttlWithJitter(base time.Duration, spread float64) time.Duration {
	extra := time.Duration(float64(base) * spread)
	if extra <= 0 {
		return base
	}
	return base + rand.N(extra)
}

func spreadOf(ttls []time.Duration) time.Duration {
	lo, hi := ttls[0], ttls[0]
	for _, t := range ttls {
		lo, hi = min(lo, t), max(hi, t)
	}
	return hi - lo
}

func main() {
	fixed := make([]time.Duration, 1000)
	jittered := make([]time.Duration, 1000)
	for i := range 1000 {
		fixed[i] = time.Hour
		jittered[i] = ttlWithJitter(time.Hour, 0.1)
	}
	fmt.Println("fixed TTLs:    all 1000 keys expire within", spreadOf(fixed))
	fmt.Println("jittered TTLs: 1000 keys expire spread over", spreadOf(jittered).Round(time.Second))
}
```

With 10% jitter, the expiries spread over about six minutes instead of one instant: the database sees a trickle of reloads instead of a wall.

</Solution>

<Recap>

- A **cache** is a disposable copy close to the reader: hits save latency and database load; the price is staleness you must bound.
- **Layers:** in-process (fastest, per replica), Redis/Valkey (shared), CDN (HTTP). Every layer is another copy that can disagree.
- **Redis** executes commands one at a time in RAM. From Go: one `go-redis` client, `errors.Is(err, redis.Nil)` for a miss, pipelines for round trips, `SCAN` not `KEYS`, `allkeys-lru` for a cache.
- **Strategies:** cache-aside (most common), read-through, write-through, write-behind (never for money).
- **Invalidation:** TTL plus delete-after-write. A slow reader can still re-cache an old value; the TTL bounds it, and versions or change streams close it.
- **Stampedes:** singleflight collapses concurrent misses (`DoChan`, `context.WithoutCancel`), it's per process, and jittered TTLs stop mass expiry. Cache "not found" only for genuine absences.
- **Fintech:** display values can be cached with documented staleness; payment decisions use the database, atomically.

</Recap>
