## Functional Options

<Define term="Functional Options" since="Design Patterns, the Go Way (Part 1, Chapter 13 — this chapter)">
A **functional option** is a function with the signature `func(*Config)` that mutates a private configuration struct. Instead of a constructor that takes fifteen arguments, you define one constructor plus a set of `With*` functions — each returning an option. Callers compose exactly what they need; the rest stays at its safe default. **Why it matters:** telescoping constructors (`NewClientWithTimeoutAndRetries`) explode combinatorially and cannot be composed at runtime. Functional options scale to any number of knobs with zero breaking changes to existing call sites.
</Define>

Picture this: you are building an HTTP client for your payment gateway. You need timeouts, retry counts, a base URL, optional tracing, maybe a custom transport. The naive approach is a struct with fifteen fields and a constructor that takes fifteen arguments. The *slightly-less-naive-but-still-wrong* approach is fifteen separate `NewClientWith*` constructors.

Both are embarrassing. Let me show you the right way.

### The telescoping constructor problem

<Define term="Closure">
A **closure** is a function value that captures variables from the scope where it was created — and keeps them alive for as long as the function value exists. When `WithTimeout(30*time.Second)` returns `func(c *config) { c.timeout = d }`, that inner function *closed over* the parameter `d`; call it minutes later, from another package, and `d` is still there. Why it matters: closures are the engine of half this chapter — functional options, middleware, and command queues are all "behavior plus captured state" packaged as a plain function value, with no class or interface ceremony.
</Define>

The **functional options** pattern replaces a proliferating family of constructors with a single constructor that accepts a **variadic** list of `Option` functions — the `opts ...Option` parameter means the caller may pass zero, one, or twenty — each of which mutates a private `config` struct. Here is the full, runnable implementation:

```go
package main

import (
	"fmt"
	"net/http"
	"time"
)

// config holds every tunable knob for our payment client.
// It is unexported — callers never touch it directly.
type config struct {
	baseURL    string
	timeout    time.Duration
	retries    int
	httpClient *http.Client
}

// Option is a function that mutates a config.
// This is the type alias that makes the pattern legible.
type Option func(*config)

// WithTimeout returns an Option that sets the request timeout.
func WithTimeout(d time.Duration) Option {
	return func(c *config) {
		c.timeout = d
	}
}

// WithRetries returns an Option that caps retry attempts.
func WithRetries(n int) Option {
	return func(c *config) {
		if n < 0 {
			n = 0
		}
		c.retries = n
	}
}

// WithHTTPClient injects a custom *http.Client (useful in tests).
func WithHTTPClient(hc *http.Client) Option {
	return func(c *config) {
		c.httpClient = hc
	}
}

// PaymentClient wraps a configured HTTP client for our gateway.
type PaymentClient struct {
	cfg *config
}

// NewPaymentClient builds a PaymentClient from a base URL
// plus any number of functional options.
func NewPaymentClient(baseURL string, opts ...Option) *PaymentClient {
	// Start from safe, production-ready defaults.
	cfg := &config{
		baseURL: baseURL,
		timeout: 10 * time.Second,
		retries: 3,
	}
	// Apply each option in order — last one wins on conflicts.
	for _, o := range opts {
		o(cfg)
	}
	if cfg.httpClient == nil {
		cfg.httpClient = &http.Client{Timeout: cfg.timeout}
	}
	return &PaymentClient{cfg: cfg}
}

func main() {
	// Production client: tight timeout, more retries.
	prod := NewPaymentClient(
		"https://api.stripe.com",
		WithTimeout(30*time.Second),
		WithRetries(5),
	)
	fmt.Printf("prod: base=%s timeout=%s retries=%d\n",
		prod.cfg.baseURL, prod.cfg.timeout, prod.cfg.retries)

	// Test client: zero retries, custom transport (you'd mock http.Client here).
	test := NewPaymentClient(
		"http://localhost:8080",
		WithRetries(0),
	)
	fmt.Printf("test: base=%s timeout=%s retries=%d\n",
		test.cfg.baseURL, test.cfg.timeout, test.cfg.retries)
}
```

<UnderTheHood title="How closures capture state">

Each `WithTimeout(d)` call allocates a new function value on the heap — a **closure**. The closure captures the variable `d` (in this case, the `time.Duration` argument) by reference at the moment `WithTimeout` returns. When the constructor loops over `opts` and calls `o(cfg)`, the closure's captured `d` is read and written into `cfg.timeout`.

The compiler performs **escape analysis** to decide whether the closed-over variable lives on the stack or must be heap-allocated. A closure that outlives the function that created it (as our `Option` values do — they're passed to the constructor) causes its captures to escape to the heap. This is one or two small allocations per option, which is entirely acceptable; the composability and testability you get in return are worth far more.

The `func(*config)` signature is the *entire* abstraction. No interface, no reflection, no registry — just a first-class function type. Go's type system makes this as lightweight as it gets.

</UnderTheHood>

## Accept Interfaces Return Structs

<Define term="Accept Interfaces, Return Structs" since="Structs, Methods, Interfaces & Errors (Part 1, Chapter 2)">
**Accept interfaces** in function parameters — your function asks for the narrowest behavior it needs (e.g. `io.Reader`), so callers can pass any type that satisfies it. **Return structs** (concrete types) from constructors — so callers get the full API without artificial restriction. **Why it matters:** accepting a concrete `*sql.DB` couples your function to one implementation forever and blocks testing. Returning an interface hides methods the concrete type has, forcing callers into type assertions they should never need.
</Define>

This is the single most-quoted Go design proverb, and the most consistently misunderstood. Let me fix that right now.

The rule has two halves:

1. **Accept interfaces** — your function parameters should be interface types where possible, so callers can pass anything that satisfies the contract. This is where you *consume* behavior.
2. **Return structs** (or concrete types) — your function's return type should be the concrete thing it actually creates, so callers get the full API without artificial restriction.

Here is the anti-pattern that violates both:

<BeforeAfter
  badLabel="Anti-pattern: return interface, accept concrete"
  goodLabel="Idiomatic: accept interface, return struct"
  bad={`// Returning an interface boxes the caller in —
// they can't call any method the interface doesn't declare.
// And accepting *os.File instead of io.Reader ties the
// implementation to one specific reader forever.
func ProcessPaymentLog(f *os.File) PaymentProcessor {
    // ...
}

// Callers can only call whatever PaymentProcessor declares,
// even if the real type has useful extra methods.`}
  good={`// Accept the narrowest interface that expresses what you need.
// io.Reader can be a file, a network conn, a bytes.Buffer, a test stub.
// Return the concrete *PaymentLogProcessor so callers get its full API.
func NewPaymentLogProcessor(r io.Reader) *PaymentLogProcessor {
    // ...
}

// In tests: pass bytes.NewReader([]byte{...}) — no file needed.
// In production: pass the real *os.File.
// Caller gets *PaymentLogProcessor and can call every method on it.`}
/>

The reason returning an interface is harmful: it *hides* the return type. If you return `io.ReadCloser` but the concrete type also implements `io.Seeker`, callers can never use `Seek` without a type assertion — and you've forced them into that corner for no reason. Return the concrete struct; let callers decide what interface to store it in.

```go
package main

import (
	"bytes"
	"fmt"
	"io"
	"strings"
)

// PaymentLogProcessor reads a payment log line-by-line.
// Its only requirement: something it can read bytes from.
type PaymentLogProcessor struct {
	r       io.Reader // private: we only need to read
	lineNum int
}

// NewPaymentLogProcessor accepts any io.Reader — file, buffer, network conn.
// It returns the concrete *PaymentLogProcessor so callers get the full API.
func NewPaymentLogProcessor(r io.Reader) *PaymentLogProcessor {
	return &PaymentLogProcessor{r: r}
}

// Next reads the next line from the log. Returns ("", io.EOF) when done.
func (p *PaymentLogProcessor) Next() (string, error) {
	buf := make([]byte, 0, 64)
	b := make([]byte, 1)
	for {
		_, err := p.r.Read(b)
		if err != nil {
			if len(buf) > 0 {
				p.lineNum++
				return string(buf), nil
			}
			return "", err
		}
		if b[0] == '\n' {
			p.lineNum++
			return string(buf), nil
		}
		buf = append(buf, b[0])
	}
}

// LineNumber reports which line was last read.
func (p *PaymentLogProcessor) LineNumber() int { return p.lineNum }

func main() {
	// In a unit test we'd use bytes.NewReader or strings.NewReader — no file needed.
	log := strings.NewReader("txn=1 amount=9900\ntxn=2 amount=4500\n")
	proc := NewPaymentLogProcessor(log)

	for {
		line, err := proc.Next()
		if err == io.EOF {
			break
		}
		fmt.Printf("line %d: %s\n", proc.LineNumber(), line)
	}

	// bytes.Buffer also satisfies io.Reader:
	proc2 := NewPaymentLogProcessor(bytes.NewBufferString("txn=3 amount=2000\n"))
	line, _ := proc2.Next()
	fmt.Println("from buffer:", line)
}
```

<Callout kind="pro" title="Define interfaces at the consumer, not the producer">

The idiomatic Go way: the *caller* defines the interface it needs, right next to where it uses it. The implementation never declares "I implement X" — it just has the right methods. This is the opposite of Java, where the producer declares `implements Serializable` and you drag that declaration everywhere.

A one-method interface is a feature, not a failure of ambition. `io.Reader`, `io.Writer`, `fmt.Stringer` — the smallest useful contracts in the entire standard library are one method each. Match that discipline.

</Callout>

## Dependency Injection

<Define term="Dependency Injection (via interfaces)" since="Software Design & Architecture (Part 1, Chapter 14)">
**Dependency injection** means passing a service's collaborators in from the outside — as constructor arguments — instead of reaching for package-level globals or calling `New*()` internally. In Go the idiomatic form is: define a minimal interface next to the consumer, accept that interface in the constructor, and inject real or fake implementations at the call site. **Why it matters:** global deps are invisible (you can't see what a function depends on), untestable (no substitute without a real DB/network), and cause race conditions in parallel tests. Injected interfaces make every dependency explicit, swappable, and mockable with a five-line fake.
</Define>

Dependency injection sounds like a framework. In Go it is not. It is just: **pass the thing as a parameter instead of reaching for a global**.

The real-world scenario: your `OrderService` needs a database, a payment gateway client, and a mailer. The wrong way is to call package-level globals from inside the service methods. The right way is to put those dependencies in the struct and inject them at construction time.

Here is the testable pattern in full:

```go
package main

import (
	"context"
	"errors"
	"fmt"
)

// --- Domain ---

type Order struct {
	ID          string
	AmountCents int
	Token       string
}

// --- Consumer-defined interfaces (defined HERE, next to the consumer) ---

type OrderStore interface {
	SaveOrder(ctx context.Context, o Order) error
}

type ChargeGateway interface {
	Charge(ctx context.Context, amountCents int, token string) error
}

// --- The service ---

type OrderService struct {
	store   OrderStore
	gateway ChargeGateway
}

func NewOrderService(store OrderStore, gw ChargeGateway) *OrderService {
	return &OrderService{store: store, gateway: gw}
}

func (s *OrderService) PlaceOrder(ctx context.Context, o Order) error {
	// Charge first — if it fails, we never persist the order.
	if err := s.gateway.Charge(ctx, o.AmountCents, o.Token); err != nil {
		return fmt.Errorf("charge failed: %w", err)
	}
	if err := s.store.SaveOrder(ctx, o); err != nil {
		return fmt.Errorf("save failed: %w", err)
	}
	return nil
}

// --- Fake implementations for tests (or for main, here) ---

type fakeStore struct{ saved []Order }

func (f *fakeStore) SaveOrder(_ context.Context, o Order) error {
	f.saved = append(f.saved, o)
	return nil
}

type fakeGateway struct{ shouldFail bool }

func (f *fakeGateway) Charge(_ context.Context, amountCents int, token string) error {
	if f.shouldFail {
		return errors.New("card declined")
	}
	fmt.Printf("  charged %d cents on token %s\n", amountCents, token)
	return nil
}

func main() {
	ctx := context.Background()
	store := &fakeStore{}
	gw := &fakeGateway{}
	svc := NewOrderService(store, gw)

	err := svc.PlaceOrder(ctx, Order{ID: "ord_1", AmountCents: 9900, Token: "tok_visa"})
	fmt.Println("place order err:", err)
	fmt.Println("orders saved:", len(store.saved))

	// Now simulate a declined card:
	gw.shouldFail = true
	err = svc.PlaceOrder(ctx, Order{ID: "ord_2", AmountCents: 4500, Token: "tok_bad"})
	fmt.Println("declined err:", err)
	fmt.Println("orders saved (should still be 1):", len(store.saved))
}
```

<UnderTheHood title="Interface values — the two-word secret">

An interface value in Go is exactly **two machine words**: a pointer to the *type descriptor* (also called the itab for non-empty interfaces) and a pointer to the *concrete data*. When you assign `var gw ChargeGateway = &fakeGateway{}`, Go writes the address of the `fakeGateway` type's method table into word one, and the address of your `fakeGateway` instance into word two.

This is why Go interfaces have *zero overhead* for dependency injection: you are not building a vtable at runtime, not allocating a proxy object, not using reflection. A method call through an interface does one pointer indirection (itab → method pointer) and then a direct call. That is the entire cost.

It also explains the **typed nil trap**: if you return a `*fakeGateway` that happens to be nil inside an interface, the interface value's type word is non-nil even though the data word is nil — so `err != nil` is `true` even though the wrapped pointer is zero. The error-handling chapter covers this in full depth; bookmark it.

## Worker Pools

<Define term="Worker Pool / Fan-In / Fan-Out" since="Concurrency Patterns (Part 2, Chapter 6)">
A **worker pool** is a fixed set of N goroutines that all read from one shared job channel, bounding how much memory and CPU you use regardless of how many jobs arrive. **Fan-out** is distributing one stream of work to multiple goroutines in parallel. **Fan-in** is merging the results from multiple parallel goroutines back into one output channel. **Why it matters:** spawning one goroutine per job works fine at 100 jobs; at 50,000 it exhausts memory. Processing jobs sequentially misses the overnight window. A pool gives you the throughput without the blowup.
</Define>

Your payment batch processor needs to reconcile 50,000 transactions overnight. Spawning 50,000 goroutines would exhaust memory. Doing them one-by-one would miss the window. You need **bounded parallelism**: a fixed-size pool of worker goroutines, each pulling from a shared job queue.

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"time"
)

// ReconcileJob is one unit of work — one transaction to reconcile.
type ReconcileJob struct {
	TxnID       string
	AmountCents int
}

// ReconcileResult carries the outcome back to the coordinator.
type ReconcileResult struct {
	TxnID string
	Err   error
}

// RunWorkerPool launches numWorkers goroutines, fans out jobs,
// collects results, and returns when all jobs are done.
func RunWorkerPool(
	ctx context.Context,
	jobs []ReconcileJob,
	numWorkers int,
) []ReconcileResult {
	jobCh := make(chan ReconcileJob, len(jobs))   // buffered: won't block senders
	resultCh := make(chan ReconcileResult, len(jobs))

	// --- Fan out: start N workers ---
	// wg.Go (Go 1.25) calls Add(1) and launches the goroutine in one step.
	// `for range numWorkers` (Go 1.22) counts N times, no index needed.
	var wg sync.WaitGroup
	for range numWorkers {
		wg.Go(func() {
			for job := range jobCh { // blocks until a job arrives or channel closes
				select {
				case <-ctx.Done():
					resultCh <- ReconcileResult{TxnID: job.TxnID, Err: ctx.Err()}
					continue
				default:
				}
				// Simulate reconciliation work (network call, DB write, etc.)
				time.Sleep(5 * time.Millisecond)
				resultCh <- ReconcileResult{TxnID: job.TxnID}
			}
		})
	}

	// --- Send all jobs ---
	for _, j := range jobs {
		jobCh <- j
	}
	close(jobCh) // signal workers: no more jobs

	// --- Wait for workers, then close results ---
	go func() {
		wg.Wait()
		close(resultCh)
	}()

	// --- Collect ---
	var results []ReconcileResult
	for r := range resultCh {
		results = append(results, r)
	}
	return results
}

func main() {
	jobs := make([]ReconcileJob, 12)
	for i := range jobs {
		jobs[i] = ReconcileJob{TxnID: fmt.Sprintf("txn_%02d", i+1), AmountCents: 1000 * (i + 1)}
	}

	ctx := context.Background()
	results := RunWorkerPool(ctx, jobs, 4) // 4 workers, 12 jobs
	fmt.Printf("processed %d jobs with 4 workers\n", len(results))
	for _, r := range results {
		if r.Err != nil {
			fmt.Printf("  FAIL %s: %v\n", r.TxnID, r.Err)
		}
	}
}
```

<Callout kind="tip" title="sync.WaitGroup.Go — new in Go 1.25">

Before Go 1.25, launching a pooled goroutine required three lines: `wg.Add(1)`, then `go func() { defer wg.Done(); ... }()`. The boilerplate was easy to get wrong — forget the `Add` and `Wait` returns early; forget the `defer Done` and the pool never shuts down.

As of Go 1.25, `wg.Go(func() { ... })` does both in one call: it increments the counter and starts the goroutine. The examples in this chapter use this form. If you are reading code written before Go 1.25, the three-line pattern is correct — just more verbose.

## Fan-In and Fan-Out

**Fan-out** splits one stream of work across multiple goroutines. **Fan-in** merges multiple streams back into one. Together they are the pipeline architecture for every high-throughput Go service.

Real scenario: your fraud-detection pipeline ingests a stream of payment events, fans them out to three parallel analyzers (velocity check, geo-anomaly check, device fingerprint check), and fans their verdicts back into one decision stream.

```go
package main

import (
	"fmt"
	"sync"
)

type PaymentEvent struct {
	TxnID  string
	UserID string
	Amount int
}

type Verdict struct {
	TxnID   string
	Checker string
	Flagged bool
}

// fanOut distributes events from `in` to `n` output channels.
func fanOut(in <-chan PaymentEvent, n int) []<-chan PaymentEvent {
	outs := make([]chan PaymentEvent, n)
	for i := range outs {
		outs[i] = make(chan PaymentEvent, 4)
	}
	go func() {
		defer func() {
			for _, o := range outs { close(o) }
		}()
		i := 0
		for e := range in {
			outs[i%n] <- e // round-robin
			i++
		}
	}()
	result := make([]<-chan PaymentEvent, n)
	for i, o := range outs { result[i] = o }
	return result
}

// checker simulates one fraud analysis lane.
func checker(name string, in <-chan PaymentEvent) <-chan Verdict {
	out := make(chan Verdict, 4)
	go func() {
		defer close(out)
		for e := range in {
			// Stub: flag anything over $500 (50000 cents) as suspicious.
			out <- Verdict{TxnID: e.TxnID, Checker: name, Flagged: e.Amount > 50000}
		}
	}()
	return out
}

// fanIn merges multiple verdict channels into one.
func fanIn(channels ...<-chan Verdict) <-chan Verdict {
	merged := make(chan Verdict, 8)
	var wg sync.WaitGroup
	// wg.Go (Go 1.25) combines Add(1) + goroutine launch. Since Go 1.22
	// `ch` is a fresh variable per iteration — no `ch := ch` shadow needed.
	for _, ch := range channels {
		wg.Go(func() {
			for v := range ch {
				merged <- v
			}
		})
	}
	go func() { wg.Wait(); close(merged) }()
	return merged
}

func main() {
	// Source: a stream of payment events.
	source := make(chan PaymentEvent, 5)
	events := []PaymentEvent{
		{TxnID: "t1", UserID: "u1", Amount: 9900},
		{TxnID: "t2", UserID: "u2", Amount: 75000}, // suspicious
		{TxnID: "t3", UserID: "u1", Amount: 2500},
		{TxnID: "t4", UserID: "u3", Amount: 99999}, // suspicious
		{TxnID: "t5", UserID: "u4", Amount: 14999},
	}
	for _, e := range events { source <- e }
	close(source)

	// Fan out to 3 checker lanes.
	lanes := fanOut(source, 3)
	velocity := checker("velocity", lanes[0])
	geo      := checker("geo-anomaly", lanes[1])
	device   := checker("device-fp", lanes[2])

	// Fan in all verdicts.
	verdicts := fanIn(velocity, geo, device)

	for v := range verdicts {
		if v.Flagged {
			fmt.Printf("FLAGGED by %s: %s\n", v.Checker, v.TxnID)
		}
	}
}
```

<Define term="Middleware / Decorator (via closures)" since="HTTP Servers: JSON, Streaming & WebSockets (Part 1, Chapter 19)">
A **middleware** is a function with the signature `func(http.Handler) http.Handler`. It takes the next handler, returns a *new* handler that does something before or after calling the original. This is the **decorator pattern**: each middleware *wraps* the previous one, forming a chain. In Go, closures make it effortless — the returned handler captures `next` in its environment and calls it when the request arrives. **Why it matters:** logging, auth, rate limiting, and tracing are *cross-cutting concerns* — they need to run on every request. Without middleware you copy that logic into every handler. With a chain, each concern lives in one place, is independently testable, and can be added or removed without touching handlers.
</Define>

Every HTTP service needs cross-cutting concerns applied to every handler: logging, auth checks, rate limiting, request tracing. Doing this inside each handler is a crime. The Go way: **middleware as a function that wraps a handler function**.

The type is `func(http.Handler) http.Handler`. That's it. A middleware takes a handler, returns a *new* handler that does something before or after calling the original.

```go
package main

import (
	"fmt"
	"log"
	"net/http"
	"time"
)

// Handler is the type we're decorating — a standard http.HandlerFunc.
// We use http.Handler (the interface) for maximum composability.

// LoggingMiddleware wraps a handler and logs the request duration.
// It is a closure: `next` is captured and called inside the returned handler.
func LoggingMiddleware(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		start := time.Now()
		next.ServeHTTP(w, r)  // call the INNER handler
		log.Printf("[LOG] %s %s took %v", r.Method, r.URL.Path, time.Since(start))
	})
}

// AuthMiddleware checks for a valid API key before calling the next handler.
func AuthMiddleware(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		key := r.Header.Get("X-API-Key")
		if key != "secret-key-abc" {
			http.Error(w, "unauthorized", http.StatusUnauthorized)
			return // short-circuit — next is never called
		}
		next.ServeHTTP(w, r)
	})
}

// Chain applies middleware in declaration order (outermost first).
// The request passes through each layer before reaching the handler.
func Chain(h http.Handler, middlewares ...func(http.Handler) http.Handler) http.Handler {
	// Apply in reverse so the first middleware listed is the outermost.
	for i := len(middlewares) - 1; i >= 0; i-- {
		h = middlewares[i](h)
	}
	return h
}

// PaymentsHandler is the real business logic — clean, no cross-cutting noise.
func PaymentsHandler(w http.ResponseWriter, r *http.Request) {
	fmt.Fprintln(w, "Payment accepted")
}

func main() {
	// Compose: every request hits Logging → Auth → PaymentsHandler.
	handler := Chain(
		http.HandlerFunc(PaymentsHandler),
		LoggingMiddleware,
		AuthMiddleware,
	)

	// In a real server: http.Handle("/payments", handler)
	// Here we simulate a request manually.
	fmt.Println("Middleware chain built. In production: http.Handle(\"/payments\", handler)")
	fmt.Println("Chain: LoggingMiddleware → AuthMiddleware → PaymentsHandler")
	_ = handler
}
```

<UnderTheHood title="Why closures make the decorator pattern effortless">

Each middleware function `LoggingMiddleware(next http.Handler) http.Handler` returns a new closure — an anonymous function value that *captures `next`* in its environment. The `next` variable lives on the closure's heap-allocated environment, not on any stack. When `ServeHTTP` is called later (possibly from a completely different goroutine), the closure reads `next` from that environment and calls it.

This is the **decorator pattern** from the GoF book — but in Go it costs exactly one function allocation per middleware level, no interface boilerplate, no anonymous inner class. The same closure mechanism that powers functional options powers middleware chains. Both patterns exploit the same language feature: first-class function values that capture their lexical environment.

Closures are allocated on the heap when they escape (as middleware closures always do — they outlive the function that created them). The escape is cheap, and the function-call overhead is a single indirect call through the captured `next` pointer — negligible compared to any real handler work.

</UnderTheHood>

## GoF Patterns in Go

Let me be direct: most of the Gang of Four patterns exist to solve problems that Go's language features simply do not have. Go has first-class functions, implicit interface satisfaction, and composition over inheritance. Several GoF patterns collapse into nothing.

### Singleton — and why you almost certainly don't need one

The Java Singleton's entire job is to ensure a class is instantiated exactly once. In Go, **package-level variables are already initialized exactly once** by the runtime. `sync.Once` handles the lazy case.

```go
package main

import (
	"fmt"
	"sync"
)

// --- Package-level singleton: initialized once by the runtime. ---
// Fine for truly global, immutable config. Still better to inject it.
var defaultLogger = newLogger("INFO")

type Logger struct{ level string }

func newLogger(level string) *Logger { return &Logger{level: level} }
func (l *Logger) Log(msg string)     { fmt.Printf("[%s] %s\n", l.level, msg) }

// --- Lazy singleton with sync.Once (for expensive initialization) ---
var (
	dbOnce     sync.Once
	dbInstance *fakeDB
)

type fakeDB struct{ dsn string }

func GetDB() *fakeDB {
	dbOnce.Do(func() {
		// This runs exactly once, even across a thousand goroutines.
		dbInstance = &fakeDB{dsn: "postgres://..."}
		fmt.Println("DB connected (runs once)")
	})
	return dbInstance
}

func main() {
	defaultLogger.Log("using package-level logger")

	// All three calls to GetDB return the same instance.
	db1 := GetDB()
	db2 := GetDB()
	db3 := GetDB()
	fmt.Printf("db1 == db2: %v, db2 == db3: %v\n", db1 == db2, db2 == db3)
}
```

<Callout kind="warn" title="Globals are usually the wrong answer">

A package-level singleton is globally mutable shared state. Tests cannot run in parallel without races. You cannot inject a fake. The moment you want two different databases in a test, you're stuck. **Prefer injection**: create the dependency once in `main`, inject it everywhere it's needed. Reserve `sync.Once` for genuinely expensive one-time initialization (a connection pool, a compiled regex) where construction cost is real.

</Callout>

### Factory — just a constructor function

In Java, a Factory is a class whose job is to create other classes. In Go, that's just a function. `NewPaymentClient(...)`, `NewOrderService(...)` — you've been writing factories this entire chapter.

If you need a *family* of factories keyed by a string (e.g., `"stripe"` → Stripe client, `"paypal"` → PayPal client), a map of constructor functions is idiomatic:

```go
package main

import "fmt"

type Gateway interface {
	Name() string
}

type StripeGateway struct{}
func (s *StripeGateway) Name() string { return "Stripe" }

type PayPalGateway struct{}
func (p *PayPalGateway) Name() string { return "PayPal" }

// Factory map: a string → a constructor function.
var gatewayFactory = map[string]func() Gateway{
	"stripe": func() Gateway { return &StripeGateway{} },
	"paypal": func() Gateway { return &PayPalGateway{} },
}

func NewGateway(provider string) (Gateway, error) {
	fn, ok := gatewayFactory[provider]
	if !ok {
		return nil, fmt.Errorf("unknown payment provider %q", provider)
	}
	return fn(), nil
}

func main() {
	gw, err := NewGateway("stripe")
	fmt.Println(gw.Name(), err)
	gw, err = NewGateway("paypal")
	fmt.Println(gw.Name(), err)
	_, err = NewGateway("venmo")
	fmt.Println(err)
}
```

### Strategy — just an interface (or a function)

The Strategy pattern says: define a family of algorithms, encapsulate each, make them interchangeable. In Go, a one-method interface *is* the strategy pattern. You've already seen this: `ChargeGateway` is a strategy. `OrderStore` is a strategy.

If the strategy has exactly one method, consider making it a function type instead:

```go
// Strategy as a function type — no interface needed for one method.
type FeeCalculator func(amountCents int) int

func flatFee(amount int) int      { return 30 }          // $0.30 flat
func percentFee(amount int) int   { return amount / 100 } // 1%

func ApplyFee(amount int, calc FeeCalculator) int {
	return amount + calc(amount)
}
```

### Observer — channels

The Observer pattern: when an event happens, notify all subscribers. In Go, that's a channel. Interested goroutines range over the channel; when you're done, close it. No `Subscribe`/`Unsubscribe` machinery required.

For multi-subscriber fan-out (each subscriber gets every event), a `sync.Map` of channels or a dedicated broker type works. But the idiomatic Go first instinct is always: **can I just use a channel?**

### Adapter — a wrapper struct or a function

When you need a type to satisfy an interface it wasn't designed for, write a thin wrapper struct (or a function type conversion, like `http.HandlerFunc`). This is the Adapter pattern, and in Go it costs almost nothing:

```go
// LegacyMailer has a different method signature than our Notifier interface.
type LegacyMailer struct{}
func (m *LegacyMailer) SendEmail(to, subject, body string) error { return nil }

// Notifier is what our service expects.
type Notifier interface {
	Notify(ctx context.Context, to, message string) error
}

// MailerAdapter wraps LegacyMailer to satisfy Notifier.
type MailerAdapter struct{ m *LegacyMailer }
func (a *MailerAdapter) Notify(ctx context.Context, to, message string) error {
	return a.m.SendEmail(to, "Notification", message)
}
```

### Command — a func, or a struct with one method

<Define term="Command pattern (GoF)" since="Design Patterns, the Go Way (Part 1, Chapter 13 — this chapter)">
The **Command** pattern packages "a thing to do" as an object so you can queue it, log it, retry it, or undo it. The GoF version is an `interface` with an `Execute()` method plus a concrete command class per action. In Go, a command is usually just a `func() error` — a first-class value you can put on a channel, store in a slice, or replay from a write-ahead log. **Why it matters:** a payment processor that retries failed charges, replays a backlog after an outage, or supports undo needs to treat each action as data, not as a hard-coded call site.
</Define>

A `func() error` *is* a command. You only reach for a struct when the command also needs to carry metadata — an idempotency key, a name for logging, an `Undo` counterpart. Here a Meridian transfer queue stores commands and replays them:

<GoPlayground>

```go
package main

import (
	"errors"
	"fmt"
)

// Command is just a function value: a unit of work to run later.
type Command func() error

// Queue records commands so they can be replayed (e.g. after an outage).
type Queue struct {
	log []Command
}

func (q *Queue) Submit(c Command) { q.log = append(q.log, c) }

// Replay runs every queued command, collecting failures.
func (q *Queue) Replay() []error {
	var errs []error
	for i, c := range q.log {
		if err := c(); err != nil {
			errs = append(errs, fmt.Errorf("command %d: %w", i, err))
		}
	}
	return errs
}

func transfer(from, to string, cents int64) Command {
	return func() error {
		if cents <= 0 {
			return errors.New("amount must be positive")
		}
		fmt.Printf("transfer %d cents: %s -> %s\n", cents, from, to)
		return nil
	}
}

func main() {
	var q Queue
	q.Submit(transfer("acct-001", "acct-002", 5000))
	q.Submit(transfer("acct-001", "acct-003", -10)) // will fail
	q.Submit(transfer("acct-004", "acct-005", 2500))

	for _, err := range q.Replay() {
		fmt.Println("FAILED:", err)
	}
}
```

</GoPlayground>

The GoF `Command` interface with one `ConcreteCommand` class per action is pure ceremony here — a closure captures the receiver and arguments for free. Reach for a struct *only* when you need `Undo()` alongside `Execute()`.

### State — a method field, not a class hierarchy

<Define term="State pattern (GoF)" since="Design Patterns, the Go Way (Part 1, Chapter 13 — this chapter)">
The **State** pattern lets an object change its behavior when its internal state changes — a payment that behaves differently while `pending`, `authorized`, `captured`, or `refunded`. The GoF version gives each state its own class implementing a shared `State` interface, and the context delegates to the current state object. In Go, a small state machine is usually clearer as a typed constant plus a transition table (a `map`), or a single field holding a behavior func. **Why it matters:** a transaction's allowed transitions *are* the business rules — encoding them as data makes the illegal moves obvious and testable.
</Define>

A `map` from `(state, event)` to the next state captures the whole machine in one readable block — no class per state:

<GoPlayground>

```go
package main

import "fmt"

// State is a typed constant — not a class.
type State string

const (
	Pending    State = "pending"
	Authorized State = "authorized"
	Captured   State = "captured"
	Refunded   State = "refunded"
)

type Event string

const (
	Authorize Event = "authorize"
	Capture   Event = "capture"
	Refund    Event = "refund"
)

// transitions IS the state machine: (state, event) -> next state.
// A missing key means the transition is illegal.
var transitions = map[State]map[Event]State{
	Pending:    {Authorize: Authorized},
	Authorized: {Capture: Captured, Refund: Refunded},
	Captured:   {Refund: Refunded},
}

type Payment struct{ state State }

func (p *Payment) Fire(e Event) error {
	next, ok := transitions[p.state][e]
	if !ok {
		return fmt.Errorf("cannot %q a %s payment", e, p.state)
	}
	p.state = next
	return nil
}

func main() {
	p := &Payment{state: Pending}
	for _, e := range []Event{Authorize, Capture, Refund} {
		if err := p.Fire(e); err != nil {
			fmt.Println("rejected:", err)
			continue
		}
		fmt.Println("->", p.state)
	}
	// An illegal move from a terminal state:
	fmt.Println("refund again:", p.Fire(Capture))
}
```

</GoPlayground>

A `State` interface with four state classes would scatter the transition rules across four files. The transition map keeps every legal and illegal move on one screen — that *is* the spec.

### Template Method — a func field, not inheritance

<Define term="Template Method pattern (GoF)" since="Design Patterns, the Go Way (Part 1, Chapter 13 — this chapter)">
The **Template Method** pattern fixes the skeleton of an algorithm and lets subclasses fill in specific steps. The GoF version uses an abstract base class with `final` template method and abstract hook methods. Go has no inheritance, so you compose: a function holds the invariant steps and calls **hook functions** (or a small interface) for the variable ones. **Why it matters:** every payment rail (ACH, card, wire) runs the same pipeline — validate, reserve, settle, notify — but settles differently. The shared skeleton lives once; only the rail-specific step varies.
</Define>

The skeleton calls injected hooks; each rail supplies just its `settle` step:

<GoPlayground>

```go
package main

import (
	"errors"
	"fmt"
)

// settleFn is the one step that varies per payment rail.
type settleFn func(cents int64) error

// runPipeline is the fixed skeleton (the "template method").
// Only the settle step is injected — validate and notify are invariant.
func runPipeline(cents int64, settle settleFn) error {
	if cents <= 0 { // invariant step: validate
		return errors.New("amount must be positive")
	}
	if err := settle(cents); err != nil { // the varying step
		return fmt.Errorf("settle: %w", err)
	}
	fmt.Printf("notify: %d cents settled\n", cents) // invariant step: notify
	return nil
}

func achSettle(cents int64) error {
	fmt.Printf("  ACH: queued %d cents for next batch\n", cents)
	return nil
}

func cardSettle(cents int64) error {
	if cents > 1_000_000 {
		return errors.New("card limit exceeded")
	}
	fmt.Printf("  card: captured %d cents instantly\n", cents)
	return nil
}

func main() {
	fmt.Println("ACH:", runPipeline(5000, achSettle))
	fmt.Println("card:", runPipeline(2500, cardSettle))
	fmt.Println("card too big:", runPipeline(2_000_000, cardSettle))
}
```

</GoPlayground>

No abstract base class, no `protected` overrides — the skeleton is a plain function and the variable step is a parameter. When several steps vary together, group them into a small interface instead of passing five funcs.

### The rest of the catalog, the Go way

The classic *Design Patterns* book lists twenty-three. We've covered the ones that matter daily; the remaining structural and behavioral patterns deflate into Go idioms just as hard. Here's the whole rest of the catalog, each collapsed to the Go thing it really is — so when an interviewer or an old Java colleague names one, you can translate on the spot:

<ConceptGrid cols={2}>
  <ConceptCard label="Composite">A tree where leaves and branches share one interface — so a caller treats a single account and a group of accounts the same. In Go: one interface (`Balancer{ Balance() int64 }`), a leaf type and a slice-holding branch type that both implement it. No abstract base. (Runnable example below.)</ConceptCard>
  <ConceptCard label="Facade">One simplified type in front of several messy subsystems. In Go this is just a struct with a few methods that orchestrate the internals — `type PaymentService struct{ ledger; fraud; notifier }` with a `Charge()` that calls all three. You already write these; the GoF just gave it a name.</ConceptCard>
  <ConceptCard label="Proxy">A stand-in with the same interface as the real thing, adding caching, lazy-loading, access control, or remoting. In Go: a wrapper struct that satisfies the same interface and forwards (or short-circuits) to the wrapped value. A caching client is a proxy; an RPC client stub is a proxy.</ConceptCard>
  <ConceptCard label="Chain of Responsibility">A request walks a chain until one handler deals with it. In Go this **is** the middleware pattern you built earlier — `func(Handler) Handler` wrappers, each choosing to handle or call `next`. Same shape as `net/http` middleware.</ConceptCard>
  <ConceptCard label="Visitor">Decouples an operation from the structure it runs over, so you add operations without touching the types. In Go, prefer a **type switch** over the concrete types, or an interface method per operation. Reach for the full double-dispatch dance only when the type set is closed and operations multiply.</ConceptCard>
  <ConceptCard label="Bridge">Splits an abstraction from its implementation so they vary independently. In Go: hold an interface field. A `Notifier` that takes a `Transport` interface (email, SMS, push) is a bridge — swap the transport without touching the notifier. It's composition, which Go pushes you toward anyway.</ConceptCard>
  <ConceptCard label="Flyweight">Share immutable common state instead of duplicating it across many objects. In Go: intern the shared value (a package-level `map[string]*Currency` you look up) and store a pointer, not a copy. The `sync.Pool` and string interning are flyweight in spirit.</ConceptCard>
  <ConceptCard label="Mediator">A hub that coordinates components so they don't all reference each other. In Go this is the **event bus / actor** model (Part 3) — components publish to and subscribe from one mediator rather than holding pointers to each other.</ConceptCard>
  <ConceptCard label="Memento">Capture an object's state so you can restore it later (undo). In Go: a plain snapshot **value** — copy the state struct, keep it, assign it back to roll forward/back. No special "originator/caretaker" classes; a struct copy is the memento.</ConceptCard>
</ConceptGrid>

```go
package main

import "fmt"

// Composite: a leaf and a group share ONE interface, so a caller totals a
// single account and a whole department of accounts the same way.
type Balancer interface {
	Balance() int64
	Name() string
}

// Account is a leaf — a single balance in cents.
type Account struct {
	name  string
	cents int64
}

func (a Account) Balance() int64 { return a.cents }
func (a Account) Name() string   { return a.name }

// Group is a branch — a named bag of Balancers (which may themselves be Groups).
type Group struct {
	name     string
	children []Balancer
}

func (g Group) Name() string { return g.name }
func (g Group) Balance() int64 {
	var sum int64
	for _, c := range g.children {
		sum += c.Balance() // recursion: leaf or group, same call
	}
	return sum
}

func main() {
	// A tree: the company holds two departments; each holds accounts.
	tree := Group{
		name: "meridian-corp",
		children: []Balancer{
			Group{name: "payments", children: []Balancer{
				Account{"ops-float", 5_000_00},
				Account{"settlement", 12_500_00},
			}},
			Group{name: "treasury", children: []Balancer{
				Account{"reserve", 80_000_00},
			}},
		},
	}

	// The caller doesn't know or care whether it holds a leaf or a group.
	for _, node := range tree.children {
		fmt.Printf("%-12s ₦%d.%02d\n", node.Name(), node.Balance()/100, node.Balance()%100)
	}
	fmt.Printf("%-12s ₦%d.%02d (whole tree)\n", tree.Name(), tree.Balance()/100, tree.Balance()%100)
}
```

</GoPlayground>

One interface, a leaf, and a branch that recurses — no abstract base class, no `getChildren()` ceremony. That's Composite, and it's the shape of every file tree, org chart, and nested-account total you'll model.

## Error Wrapping

One more pattern that is distinctly Go: **wrapping errors to add context without losing the original**. This is not a GoF pattern — it is a Go-specific discipline.

The problem: your service's `PlaceOrder` returns an error. The caller wants to log it with enough context to debug it. But they also want to test for *specific* error types (e.g., "is this a card decline vs. a DB error?").

```go
package main

import (
	"errors"
	"fmt"
)

// Sentinel errors — named, comparable values your callers can check with errors.Is.
var ErrCardDeclined = errors.New("card declined")

// GatewayError is a typed error your callers can inspect with errors.As.
type GatewayError struct {
	Provider string
	Code     string
	Wrapped  error
}

func (e *GatewayError) Error() string {
	return fmt.Sprintf("gateway %s error %s: %v", e.Provider, e.Code, e.Wrapped)
}

// Unwrap lets errors.Is and errors.As traverse the chain.
func (e *GatewayError) Unwrap() error { return e.Wrapped }

// charge simulates a payment gateway call.
func charge(amountCents int) error {
	if amountCents > 50000 {
		// Wrap the sentinel with provider context.
		return &GatewayError{Provider: "stripe", Code: "card_declined", Wrapped: ErrCardDeclined}
	}
	return nil
}

// placeOrder wraps gateway errors with business context.
func placeOrder(amountCents int) error {
	if err := charge(amountCents); err != nil {
		// %w makes the error unwrappable — errors.Is and errors.As can traverse it.
		return fmt.Errorf("placeOrder: %w", err)
	}
	return nil
}

func main() {
	err := placeOrder(75000)
	if err != nil {
		fmt.Println("error:", err)

		// errors.Is walks the whole chain for the sentinel.
		if errors.Is(err, ErrCardDeclined) {
			fmt.Println("→ it's a card decline")
		}

		// errors.As extracts the typed error from anywhere in the chain.
		var gwErr *GatewayError
		if errors.As(err, &gwErr) {
			fmt.Printf("→ provider=%s code=%s\n", gwErr.Provider, gwErr.Code)
		}
	}
}
```

## Builder & Fluent APIs

<Define term="Builder / Fluent API" since="Design Patterns, the Go Way (Part 1, Chapter 13 — this chapter)">
A **builder** is a mutable object that accumulates state across method calls and produces a finished value with a final `Build()`. A **fluent API** is the style that makes it read like a sentence: every step returns the receiver, so calls chain. The GoF Builder needs a director plus a builder class hierarchy; in Go it's one struct whose methods `return q`. **Why it matters:** functional options are *one-shot* — every option sees the same config and they can't react to each other. When construction is *staged* (each step depends on prior state), *conditional* (add a clause only sometimes), or *accumulative* (build a list across a loop), a builder is clearer than juggling a slice of options.
</Define>

You learned functional options first because they're the right default. But options have a ceiling: they all run against one config in one pass, blind to each other. The moment you need to *branch on what's been built so far* — add a `WHERE` only if a filter exists, append a join inside a loop — a mutable builder reads better.

The classic Go builder defers all errors to `Build()`, so the chain stays clean — no error check after every call (the same trick `bufio.Scanner` uses with `Err()`):

<GoPlayground>

```go
package main

import (
	"fmt"
	"strings"
)

// QueryBuilder accumulates clauses; Build validates and renders once.
// Errors are deferred to Build so the chain never needs mid-call checks.
type QueryBuilder struct {
	table string
	cols  []string
	conds []string
	err   error
}

func NewQuery(table string) *QueryBuilder {
	qb := &QueryBuilder{table: table}
	if table == "" {
		qb.err = fmt.Errorf("table is required")
	}
	return qb
}

func (q *QueryBuilder) Select(cols ...string) *QueryBuilder {
	q.cols = append(q.cols, cols...)
	return q // return the receiver -> fluent chaining
}

func (q *QueryBuilder) Where(cond string) *QueryBuilder {
	q.conds = append(q.conds, cond)
	return q
}

func (q *QueryBuilder) Build() (string, error) {
	if q.err != nil {
		return "", q.err
	}
	if len(q.cols) == 0 {
		q.cols = []string{"*"}
	}
	var sb strings.Builder
	fmt.Fprintf(&sb, "SELECT %s FROM %s", strings.Join(q.cols, ", "), q.table)
	if len(q.conds) > 0 {
		fmt.Fprintf(&sb, " WHERE %s", strings.Join(q.conds, " AND "))
	}
	return sb.String(), nil
}

func main() {
	sql, err := NewQuery("accounts").
		Select("id", "balance_cents").
		Where("currency = 'USD'").
		Where("balance_cents > 0").
		Build()
	fmt.Println(sql)
	fmt.Println("err:", err)

	_, err = NewQuery("").Select("id").Build()
	fmt.Println("empty table:", err)
}
```

</GoPlayground>

<UnderTheHood title="Fluent chaining and the deferred-error trick">

Two mechanics make this work. First, every mutating method ends with `return q` — it hands back the same `*QueryBuilder` pointer, so the next call in the chain operates on the same instance. There's no copying; the dot just keeps landing on one heap object.

Second, errors are *stored, not returned*. `NewQuery` records a problem in `q.err` and keeps going; each step is free to add to it; only `Build()` surfaces it. This is exactly how `bufio.Scanner` works — you loop on `Scan()` without checking errors, then call `Err()` once at the end. It trades a little immediacy for a chain that reads like prose.

Reach for a builder over options when steps are ordered, conditional, or accumulative. Reach for options when the knobs are independent. Don't build both for the same type.

</UnderTheHood>

## Advanced Functional Options

<Define term="Self-Referential & Interface Options" since="Design Patterns, the Go Way (Part 1, Chapter 13 — this chapter)">
Two refinements of the options pattern. A **self-referential option** has the signature `func(*T) Option` — applying it *returns the option that undoes it*, so callers can set a value temporarily and restore the old one (Rob Pike's original design). An **interface option** replaces `func(*config)` with an `Option` interface whose concrete types each `apply` themselves — so options become *named types* that appear in godoc, can carry their own `String()`, and can be inspected or logged. **Why it matters:** the func form is perfect for write-and-forget config; the self-referential and interface forms add undo and introspection when you need them.
</Define>

The plain `func(*config)` option you already know is the 90% case. Here are the two upgrades for the other 10%.

### Self-referential options: set, then restore

Rob Pike's original options design returned the *previous* value as a new option, so any temporary change is trivially reversible — crank verbose logging for one request, then put it back:

<GoPlayground>

```go
package main

import "fmt"

type Server struct {
	verbosity int
	maxConns  int
}

// Option mutates the Server AND returns an Option that undoes the change.
// This is Rob Pike's self-referential options trick.
type Option func(*Server) Option

func Verbosity(v int) Option {
	return func(s *Server) Option {
		prev := s.verbosity
		s.verbosity = v
		return Verbosity(prev) // the returned option restores the old value
	}
}

func MaxConns(n int) Option {
	return func(s *Server) Option {
		prev := s.maxConns
		s.maxConns = n
		return MaxConns(prev)
	}
}

// Option applies opts and returns a single Option that restores everything.
func (s *Server) Option(opts ...Option) (restore Option) {
	for _, opt := range opts {
		restore = opt(s)
	}
	return restore
}

func main() {
	s := &Server{}
	s.Option(Verbosity(3), MaxConns(100))
	fmt.Printf("base: verbosity=%d maxConns=%d\n", s.verbosity, s.maxConns)

	// Temporarily crank verbosity, capture the undo, then restore.
	restore := s.Option(Verbosity(9))
	fmt.Printf("temp: verbosity=%d\n", s.verbosity)
	s.Option(restore)
	fmt.Printf("restored: verbosity=%d\n", s.verbosity)
}
```

### Options as an interface: named, inspectable, documented

When you want options to show up in godoc with real names, carry a `String()` for logging, or be stored and compared, make `Option` an interface instead of a bare func. Each option becomes a small named type:

<GoPlayground>

```go
package main

import (
	"fmt"
	"strconv"
	"time"
)

type options struct {
	cache bool
	ttl   time.Duration
}

// Option as an interface, not a func: each option is a named type, so it
// shows up in godoc, can carry its own String(), and can be inspected.
type Option interface {
	apply(*options)
	fmt.Stringer
}

type cacheOption bool

func (c cacheOption) apply(o *options) { o.cache = bool(c) }
func (c cacheOption) String() string   { return "cache=" + strconv.FormatBool(bool(c)) }

func WithCache(on bool) Option { return cacheOption(on) }

type ttlOption time.Duration

func (t ttlOption) apply(o *options) { o.ttl = time.Duration(t) }
func (t ttlOption) String() string   { return "ttl=" + time.Duration(t).String() }

func WithTTL(d time.Duration) Option { return ttlOption(d) }

func New(opts ...Option) options {
	o := options{ttl: time.Minute}
	for _, opt := range opts {
		fmt.Println("applying", opt) // options are inspectable/loggable
		opt.apply(&o)
	}
	return o
}

// Must turns a (value, error) pair into just value, panicking on error.
// Use only at init / package scope where failure is a programmer error.
func Must[T any](v T, err error) T {
	if err != nil {
		panic(err)
	}
	return v
}

func main() {
	o := New(WithCache(true), WithTTL(30*time.Second))
	fmt.Printf("result: cache=%v ttl=%s\n", o.cache, o.ttl)

	n := Must(strconv.Atoi("42"))
	fmt.Println("Must parsed:", n)
}
```

</GoPlayground>

<Callout kind="warn" title="Must: only at init, never on a request path">

The generic `Must[T](v T, err error) T` collapses a `(value, error)` pair to just the value by panicking on error. It's the right tool for things that are programmer errors if they fail — `var schema = Must(Compile(...))` at package scope, where a bad pattern means the binary should never have shipped. The stdlib does this with `regexp.MustCompile` and `template.Must`. **Never** use it on a request path or for I/O that can fail at runtime: a panic there kills the goroutine and, unrecovered, the process. Must is for startup invariants, not error handling.

</Callout>

## Type-Safe Idioms

<Define term="Type-Safe Domain Idioms" since="Design Patterns, the Go Way (Part 1, Chapter 13 — this chapter)">
Three idioms that push bugs from runtime to compile time. **Newtype IDs** (`type AccountID string`) give distinct domain types so the compiler rejects mixing an `AccountID` with a `CustomerID`. **Bit-flag enums** (`1 << iota`) pack a set of booleans into one integer you combine with `|` and test with `&`. **Sealed sum types** (an interface with an unexported method) define a *closed* set of variants so a type switch can be exhaustively checked. **Why it matters:** a payments codebase drowns in `string` IDs and `bool` flags; giving them real types turns whole classes of mistake — swapped arguments, illegal states — into compile errors.
</Define>

### Newtype IDs: make the compiler catch swapped arguments

A function taking `(from, to string)` happily accepts a customer ID where an account ID belongs. Define distinct named types and that bug stops compiling:

<GoPlayground>

```go
package main

import "fmt"

// Distinct string types: the compiler refuses to mix them up.
type AccountID string
type CustomerID string

type Ledger struct {
	balances map[AccountID]int64
}

// Transfer can ONLY be called with AccountID values. Passing a CustomerID
// or a raw string is a compile error -- the bug never reaches runtime.
func (l *Ledger) Transfer(from, to AccountID, cents int64) error {
	if l.balances[from] < cents {
		return fmt.Errorf("insufficient funds in %s", from)
	}
	l.balances[from] -= cents
	l.balances[to] += cents
	return nil
}

func main() {
	l := &Ledger{balances: map[AccountID]int64{"acct-001": 10000, "acct-002": 0}}

	var src AccountID = "acct-001"
	var dst AccountID = "acct-002"
	if err := l.Transfer(src, dst, 2500); err != nil {
		fmt.Println("err:", err)
	}
	fmt.Println("acct-002 balance:", l.balances["acct-002"])

	// The following would NOT compile -- distinct types:
	//   var cust CustomerID = "cust-9"
	//   l.Transfer(cust, dst, 100)   // cannot use cust (CustomerID) as AccountID
	//   l.Transfer("acct-001", dst, 100) // untyped string literal is fine, a string VAR is not
	fmt.Println("argument-swap and wrong-ID bugs are caught at compile time")
}
```

</GoPlayground>

### Bit-flag enums: a set of booleans in one integer

`1 << iota` gives each flag its own bit. Combine with `|`, test with `&`, clear with `&^`. One `uint8` holds eight independent toggles, and a `String()` method makes it print legibly:

<GoPlayground>

```go
package main

import (
	"fmt"
	"strings"
)

// Perm is a bit-set: each permission is one bit, combined with OR.
type Perm uint8

const (
	Read    Perm = 1 << iota // 1
	Write                    // 2
	Execute                  // 4
)

func (p Perm) Has(flag Perm) bool { return p&flag != 0 }

func (p Perm) String() string {
	if p == 0 {
		return "none"
	}
	var parts []string
	type nf struct {
		f Perm
		n string
	}
	// fixed order so the output is deterministic
	for _, x := range []nf{{Read, "read"}, {Write, "write"}, {Execute, "execute"}} {
		if p.Has(x.f) {
			parts = append(parts, x.n)
		}
	}
	return strings.Join(parts, "|")
}

func main() {
	perms := Read | Write
	fmt.Println("perms:", perms)                 // read|write
	fmt.Println("can write?", perms.Has(Write))  // true
	fmt.Println("can exec?", perms.Has(Execute)) // false

	perms |= Execute
	fmt.Println("after grant exec:", perms) // read|write|execute

	perms &^= Write                           // clear the Write bit
	fmt.Println("after revoke write:", perms) // read|execute
}
```

</GoPlayground>

### Sealed sum types: a closed set of variants

Go has no `enum` of structs, but an interface with an *unexported* method is a **sealed** type: only the declaring package can satisfy it, so the set of implementations is closed and known. A type switch over it is provably exhaustive — and the `exhaustive` linter will fail your build if you forget a case:

<GoPlayground>

```go
package main

import "fmt"

// Event is a SEALED interface: the unexported isEvent method means only
// THIS package can implement it. The set of events is closed and known.
type Event interface {
	isEvent()
}

type Authorized struct{ AmountCents int64 }
type Captured struct{ AmountCents int64 }
type Refunded struct {
	AmountCents int64
	Reason      string
}

func (Authorized) isEvent() {}
func (Captured) isEvent()   {}
func (Refunded) isEvent()   {}

// Apply handles every case. Because Event is sealed, an exhaustive switch
// is provably complete -- the exhaustive linter can enforce it.
func Apply(balance int64, e Event) int64 {
	switch ev := e.(type) {
	case Authorized:
		return balance // authorization holds funds, doesn't move them
	case Captured:
		return balance - ev.AmountCents
	case Refunded:
		return balance + ev.AmountCents
	default:
		panic(fmt.Sprintf("unhandled event %T", e))
	}
}

func main() {
	events := []Event{
		Authorized{AmountCents: 5000},
		Captured{AmountCents: 5000},
		Refunded{AmountCents: 2000, Reason: "partial"},
	}
	var balance int64 = 10000
	for _, e := range events {
		balance = Apply(balance, e)
		fmt.Printf("%-22T balance=%d\n", e, balance)
	}
}
```

</GoPlayground>

<UnderTheHood title="How an unexported method seals an interface">

`Event` declares one method, `isEvent()`, and it's lowercase — unexported. To satisfy `Event`, a type must have an `isEvent()` method, but a type in *another* package literally cannot write one: it can't name the unexported method from outside the declaring package. So the only `Event` implementations that can ever exist are the ones in this file. The set is closed.

That closure is what makes the type switch trustworthy. With an open interface, some other package could add a variant tomorrow and your `switch` would silently fall through to `default`. With a sealed one, the compiler-plus-`exhaustive`-linter combination guarantees every case is handled — Go's nearest equivalent to the sum types (`enum`/`sealed`) of Rust and Swift. The `default: panic` is a belt-and-suspenders guard for the unreachable case.

</UnderTheHood>

## Lazy Init & Generic Helpers

<Define term="Lazy Init & Generic Decorators" since="Design Patterns, the Go Way (Part 1, Chapter 13 — this chapter)">
**Lazy initialization** defers expensive setup until first use, done exactly once even under concurrency. Go 1.21 added `sync.OnceValue`, `sync.OnceFunc` and `sync.OnceValues` — they wrap a function and memoize its result, replacing the older `sync.Once` + package-var dance. A **generic decorator** wraps a function in another function of the *same signature*, adding behavior (caching, retries, timing) the caller can't see. **Why it matters:** these are the modern, boilerplate-free forms of two patterns you already met — the lazy Singleton and the wrapper — now that generics and the `Once*` helpers exist.
</Define>

### sync.OnceValue: the modern lazy singleton

Earlier you saw the lazy singleton with `sync.Once` plus a package-level variable. Go 1.21's `sync.OnceValue` collapses that into one line — the function runs at most once, its result is cached, and it's safe under concurrent first-callers:

<GoPlayground>

```go
package main

import (
	"fmt"
	"sync"
)

type Config struct{ MaxConns int }

// sync.OnceValue (Go 1.21) wraps a function so it runs at most once and
// caches its result. No package-level var, no sync.Once boilerplate, and
// it is safe to call from many goroutines.
var loadConfig = sync.OnceValue(func() Config {
	fmt.Println("  (loading config -- happens exactly once)")
	return Config{MaxConns: 100}
})

// OnceValues handles a (value, error) pair.
var compile = sync.OnceValues(func() (string, error) {
	fmt.Println("  (compiling -- happens exactly once)")
	return "compiled", nil
})

func main() {
	var wg sync.WaitGroup
	for i := 0; i < 5; i++ {
		wg.Add(1)
		go func() {
			defer wg.Done()
			_ = loadConfig() // all 5 goroutines race; loader runs once
		}()
	}
	wg.Wait()
	fmt.Println("MaxConns:", loadConfig().MaxConns)

	v, err := compile()
	fmt.Println(v, err)
	v, err = compile()
	fmt.Println(v, err)
}
```

</GoPlayground>

<Callout kind="tip" title="The Once* family (Go 1.21)">

Three helpers, picked by what your init returns: `sync.OnceFunc(f)` wraps a `func()` that returns nothing (run once for its side effect); `sync.OnceValue(f)` wraps a `func() T` and caches the one value; `sync.OnceValues(f)` wraps a `func() (T, error)` (or any two results). All three are goroutine-safe and run the wrapped function exactly once. Prefer them over a hand-rolled `sync.Once` + guard variable — fewer moving parts, nothing to forget.

</Callout>

### Generic decorators: wrap a function, keep its shape

The middleware pattern wrapped `http.Handler`. Generics let you wrap *any* function while preserving its exact signature. Here `Memoize` turns a pure `func(K) V` into a caching version — the caller can't tell the difference:

<GoPlayground>

```go
package main

import (
	"fmt"
	"sync"
)

// Memoize is a generic decorator: it wraps any pure func(K) V and caches
// results per key. The wrapped function keeps its exact signature, so
// callers can't tell it's decorated.
func Memoize[K comparable, V any](fn func(K) V) func(K) V {
	var mu sync.Mutex
	cache := make(map[K]V)
	return func(k K) V {
		mu.Lock()
		defer mu.Unlock()
		if v, ok := cache[k]; ok {
			return v
		}
		v := fn(k)
		cache[k] = v
		return v
	}
}

func main() {
	calls := 0
	slowFee := func(amountCents int) int {
		calls++ // count real computations
		return amountCents / 100
	}

	fee := Memoize(slowFee)
	fmt.Println(fee(5000))                   // computes
	fmt.Println(fee(5000))                   // cached
	fmt.Println(fee(9900))                   // computes
	fmt.Println(fee(9900))                   // cached
	fmt.Println("real computations:", calls) // 2, not 4
}
```

</GoPlayground>

### Generic containers: a real Set, finally

The `map[T]struct{}` set idiom (from the DSA appendix) becomes a reusable, type-safe `Set[T]` with generics — `struct{}` keys cost zero bytes, so it's as cheap as the raw map:

<GoPlayground>

```go
package main

import (
	"fmt"
	"sort"
)

// Set is a generic set built on the map[T]struct{} idiom -- struct{} costs
// zero bytes, so the map stores only keys.
type Set[T comparable] map[T]struct{}

func NewSet[T comparable](items ...T) Set[T] {
	s := make(Set[T], len(items))
	for _, it := range items {
		s[it] = struct{}{}
	}
	return s
}

func (s Set[T]) Add(v T)      { s[v] = struct{}{} }
func (s Set[T]) Has(v T) bool { _, ok := s[v]; return ok }
func (s Set[T]) Len() int     { return len(s) }

func (s Set[T]) Intersect(other Set[T]) Set[T] {
	out := NewSet[T]()
	for v := range s {
		if other.Has(v) {
			out.Add(v)
		}
	}
	return out
}

func main() {
	a := NewSet("acct-001", "acct-002", "acct-003")
	b := NewSet("acct-002", "acct-003", "acct-004")

	fmt.Println("a has acct-001?", a.Has("acct-001"))
	fmt.Println("a has acct-009?", a.Has("acct-009"))

	common := a.Intersect(b)
	got := make([]string, 0, common.Len())
	for v := range common {
		got = append(got, v)
	}
	sort.Strings(got)
	fmt.Println("in both:", got)
}
```

## More Behavioral Patterns

<Define term="Null Object, Pub/Sub & Iterators" since="Design Patterns, the Go Way (Part 1, Chapter 13 — this chapter)">
Three more behavioral idioms. The **Null Object** is a do-nothing implementation of an interface you return instead of `nil`, so callers never nil-check. **Pub/Sub** (the Observer pattern done right) is a broker that fans one event out to many subscriber channels. A **custom iterator** is a `func(yield func(V) bool)` — Go 1.23's range-over-func — that the `for/range` statement can drive, with `iter.Pull` to step it by hand. **Why it matters:** Null Object kills nil-guard clutter, a generic broker is the clean Observer, and range-over-func lets your own types be ranged over like slices and maps.
</Define>

### Null Object: a do-nothing default instead of nil

If `metrics` might be unconfigured, the wrong fix is `if s.metrics != nil` scattered everywhere. The right one is a no-op implementation that's always safe to call:

<GoPlayground>

```go
package main

import "fmt"

// Metrics is a dependency a service uses everywhere.
type Metrics interface {
	Incr(name string)
}

// nopMetrics is the Null Object: a do-nothing implementation. Callers that
// don't configure metrics still get a valid Metrics -- never a nil to guard.
type nopMetrics struct{}

func (nopMetrics) Incr(string) {}

type realMetrics struct{ counts map[string]int }

func (m *realMetrics) Incr(name string) { m.counts[name]++ }

type Service struct{ metrics Metrics }

// NewService falls back to the Null Object when no metrics are injected.
func NewService(m Metrics) *Service {
	if m == nil {
		m = nopMetrics{} // no nil checks anywhere in the hot path
	}
	return &Service{metrics: m}
}

func (s *Service) Pay() {
	s.metrics.Incr("payments") // always safe -- never nil
}

func main() {
	// No metrics wired: Null Object keeps the code branch-free.
	s1 := NewService(nil)
	s1.Pay()
	fmt.Println("no-metrics service ran without a nil panic")

	// Real metrics injected:
	rm := &realMetrics{counts: map[string]int{}}
	s2 := NewService(rm)
	s2.Pay()
	s2.Pay()
	fmt.Println("payments counted:", rm.counts["payments"])
}
```

</GoPlayground>

### Pub/Sub: the Observer pattern, done right

The GoF section noted "Observer is a channel." Scaled up to many subscribers, that's a **broker**: subscribers each get their own channel; publish fans out to all of them, non-blocking so one slow consumer can't stall the rest. Generics make it work for any event type:

<GoPlayground>

```go
package main

import (
	"fmt"
	"sort"
	"sync"
)

// Broker is a generic publish/subscribe hub -- the Observer pattern done
// right: many subscribers, each on its own channel, non-blocking publish.
type Broker[T any] struct {
	mu   sync.RWMutex
	subs map[chan T]struct{}
}

func NewBroker[T any]() *Broker[T] {
	return &Broker[T]{subs: make(map[chan T]struct{})}
}

func (b *Broker[T]) Subscribe() chan T {
	ch := make(chan T, 8)
	b.mu.Lock()
	b.subs[ch] = struct{}{}
	b.mu.Unlock()
	return ch
}

func (b *Broker[T]) Unsubscribe(ch chan T) {
	b.mu.Lock()
	delete(b.subs, ch)
	close(ch)
	b.mu.Unlock()
}

// Publish fans out to every subscriber. The default in the select makes the
// send non-blocking: a slow subscriber drops the message instead of stalling
// the publisher and everyone else.
func (b *Broker[T]) Publish(v T) {
	b.mu.RLock()
	defer b.mu.RUnlock()
	for ch := range b.subs {
		select {
		case ch <- v:
		default: // subscriber buffer full -> drop, never block
		}
	}
}

func main() {
	b := NewBroker[string]()
	s1 := b.Subscribe()
	s2 := b.Subscribe()

	b.Publish("txn-1 authorized")
	b.Publish("txn-2 captured")

	read := func(ch chan string, n int) []string {
		out := make([]string, 0, n)
		for i := 0; i < n; i++ {
			out = append(out, <-ch)
		}
		sort.Strings(out)
		return out
	}
	fmt.Println("s1 got:", read(s1, 2))
	fmt.Println("s2 got:", read(s2, 2))

	b.Unsubscribe(s1)
	b.Unsubscribe(s2)
}
```

### Custom iterators: make your type range-able

Go 1.23's range-over-func lets you write a function the `for/range` loop can consume. Return an `iter.Seq[V]` — a `func(yield func(V) bool)` — call `yield` per element, and *stop the instant it returns false* (that's how the consumer's `break` reaches you). `iter.Pull` flips a push iterator into one you advance by hand:

<GoPlayground>

```go
package main

import (
	"fmt"
	"iter"
)

// Lines is a push iterator (iter.Seq): it calls yield for each line and
// returns the moment yield reports false (consumer broke out early).
func Lines(s string) iter.Seq[string] {
	return func(yield func(string) bool) {
		start := 0
		for i := 0; i < len(s); i++ {
			if s[i] == '\n' {
				if !yield(s[start:i]) {
					return // MUST honor a false return, or `break` won't work
				}
				start = i + 1
			}
		}
		if start < len(s) {
			yield(s[start:])
		}
	}
}

func main() {
	log := "txn-1 ok\ntxn-2 ok\ntxn-3 fail\ntxn-4 ok"

	// Consume with for/range -- the language drives the iterator.
	for line := range Lines(log) {
		fmt.Println("line:", line)
		if line == "txn-3 fail" {
			break // tells the iterator to stop; yield returns false
		}
	}

	// iter.Pull converts a push iterator into a pull iterator you call by
	// hand -- useful to advance two sequences in lockstep (zip/merge).
	next, stop := iter.Pull(Lines("a\nb\nc"))
	defer stop()
	for {
		v, ok := next()
		if !ok {
			break
		}
		fmt.Println("pulled:", v)
	}
}
```

</GoPlayground>

<UnderTheHood title="The yield contract and the !yield rule">

A push iterator is `func(yield func(V) bool)`. For each value you produce, you call `yield(v)`. `yield` returns `true` to mean "keep going" and `false` to mean "the consumer is done" — which happens when the `for/range` body hits a `break`, `return`, or `panic`. **You must check that return and stop immediately.** Forget the `if !yield(v) { return }` and the consumer's `break` can't take effect; worse, calling `yield` again *after* it returned false makes the runtime panic.

`iter.Pull(seq)` drives the push iterator in the background (the current implementation parks it on a goroutine, resumed on demand) and hands you `next()` and `stop()`. Each `next()` resumes the iterator until the next `yield`, returning `(value, true)`; when the sequence ends you get `(zero, false)`. Always `defer stop()` — it tells the background iterator to shut down and run its deferred cleanup (closing a file, say) even if you quit early. Pull is exactly what you want to merge or zip two sequences in lockstep.

</UnderTheHood>

### Method values and method expressions

A last sharp trick: a **method value** (`acct.Deposit`) is a method already bound to its receiver — a `func(int64)` you can pass as a callback. A **method expression** (`(*Account).Deposit`) leaves the receiver unbound, becoming a `func(*Account, int64)` you supply the receiver to at call time:

<GoPlayground>

```go
package main

import "fmt"

type Account struct {
	ID      string
	balance int64
}

func (a *Account) Deposit(cents int64) { a.balance += cents }

func main() {
	acct := &Account{ID: "acct-001"}

	// METHOD VALUE: bound to a specific receiver. acct is captured;
	// deposit has signature func(int64) and can be passed as a callback.
	deposit := acct.Deposit
	for _, amt := range []int64{1000, 2500, 500} {
		deposit(amt)
	}
	fmt.Println("after method-value deposits:", acct.balance)

	// METHOD EXPRESSION: receiver becomes the FIRST argument. Unbound;
	// you pass which account to act on at call time.
	depositTo := (*Account).Deposit // func(*Account, int64)
	other := &Account{ID: "acct-002"}
	depositTo(other, 9900)
	fmt.Println("after method-expression deposit:", other.balance)
}
```

</GoPlayground>

```go
type config struct {

		}

	fmt.Println(err)
```

<Exercise n={3} title="Three-stage middleware chain" level="medium">

Build a three-layer middleware chain: `RecoveryMiddleware` (recover from panics and return 500), `LoggingMiddleware` (log method + path), `AuthMiddleware` (require `X-API-Key: secret`). Apply them to a `CheckoutHandler`. Use `httptest` to demonstrate a successful request, an unauthorized request, and a panicking handler.

<Solution>

```go
package main

import (
	"fmt"
	"log"
	"net/http"
	"net/http/httptest"
	"time"
)

func RecoveryMiddleware(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		defer func() {
			if rec := recover(); rec != nil {
				log.Printf("[PANIC] %v", rec)
				http.Error(w, "internal server error", http.StatusInternalServerError)
			}
		}()
		next.ServeHTTP(w, r)
	})
}

func LoggingMiddleware(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		start := time.Now()
		next.ServeHTTP(w, r)
		log.Printf("[LOG] %s %s %v", r.Method, r.URL.Path, time.Since(start))
	})
}

func AuthMiddleware(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		if r.Header.Get("X-API-Key") != "secret" {
			http.Error(w, "unauthorized", http.StatusUnauthorized)
			return
		}
		next.ServeHTTP(w, r)
	})
}

func Chain(h http.Handler, mws ...func(http.Handler) http.Handler) http.Handler {
	for i := len(mws) - 1; i >= 0; i-- {
		h = mws[i](h)
	}
	return h
}

func CheckoutHandler(w http.ResponseWriter, r *http.Request) {
	fmt.Fprintln(w, "checkout ok")
}

func PanicHandler(w http.ResponseWriter, r *http.Request) {
	panic("database exploded")
}

func main() {
	chain := Chain(http.HandlerFunc(CheckoutHandler), RecoveryMiddleware, LoggingMiddleware, AuthMiddleware)
	panicChain := Chain(http.HandlerFunc(PanicHandler), RecoveryMiddleware, LoggingMiddleware, AuthMiddleware)

	// Good request
	req := httptest.NewRequest("POST", "/checkout", nil)
	req.Header.Set("X-API-Key", "secret")
	rr := httptest.NewRecorder()
	chain.ServeHTTP(rr, req)
	fmt.Printf("checkout: %d %q\n", rr.Code, rr.Body.String())

	// Unauthorized
	req2 := httptest.NewRequest("POST", "/checkout", nil)
	rr2 := httptest.NewRecorder()
	chain.ServeHTTP(rr2, req2)
	fmt.Printf("unauth: %d %q\n", rr2.Code, rr2.Body.String())

	// Panic (with key, but handler panics)
	req3 := httptest.NewRequest("POST", "/checkout", nil)
	req3.Header.Set("X-API-Key", "secret")
	rr3 := httptest.NewRecorder()
	panicChain.ServeHTTP(rr3, req3)
	fmt.Printf("panic recovered: %d %q\n", rr3.Code, rr3.Body.String())
}
```

Recovery wraps the outermost deferred cleanup. The chain processes: Recovery → Logging → Auth → handler; panics unwind through Recovery's deferred function before the logger finishes.

</Solution>

</Exercise>

<Exercise n={4} title="Bounded worker pool with context cancellation" level="medium">

Extend the `RunWorkerPool` from this chapter to accept a `context.Context` with a deadline. When the deadline fires, workers should drain in-flight jobs but not start new ones, and the collector should return partial results with a note about how many jobs were skipped.

<Solution>

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"time"
)

type Job struct{ ID int }
type Result struct {
	JobID   int
	Skipped bool
}

func RunPool(ctx context.Context, jobs []Job, workers int) ([]Result, int) {
	jobCh := make(chan Job, len(jobs))
	resultCh := make(chan Result, len(jobs))
	var wg sync.WaitGroup

	for i := 0; i < workers; i++ {
		wg.Go(func() { // Go 1.25: Add(1) + launch in one call
			for job := range jobCh {
				select {
				case <-ctx.Done():
					resultCh <- Result{JobID: job.ID, Skipped: true}
					continue
				default:
				}
				time.Sleep(20 * time.Millisecond) // simulate work
				resultCh <- Result{JobID: job.ID}
			}
		})
	}

	for _, j := range jobs { jobCh <- j }
	close(jobCh)

	go func() { wg.Wait(); close(resultCh) }()

	var results []Result
	skipped := 0
	for r := range resultCh {
		results = append(results, r)
		if r.Skipped { skipped++ }
	}
	return results, skipped
}

func main() {
	jobs := make([]Job, 10)
	for i := range jobs { jobs[i] = Job{ID: i + 1} }

	// Very tight deadline — most jobs will be skipped.
	ctx, cancel := context.WithTimeout(context.Background(), 50*time.Millisecond)
	defer cancel()

	results, skipped := RunPool(ctx, jobs, 3)
	fmt.Printf("total=%d skipped=%d processed=%d\n", len(results), skipped, len(results)-skipped)
}
```

The key: workers check `ctx.Done()` with a `select` before starting work. Jobs that arrive after the deadline fire are still received from the channel (preventing a goroutine from blocking forever), but they are marked skipped and returned.

</Solution>

</Exercise>

<Exercise n={5} title="Error wrapping chain" level="hard">

Define a `StorageError` typed error and a `ValidationError` typed error, each implementing `Unwrap()`. Write a `SavePayment` function that: validates the amount (must be positive), calls a fake store that always returns a `StorageError`. Wrap both errors with `%w` and demonstrate that `errors.Is` and `errors.As` correctly traverse a three-level chain.

<Solution>

```go
package main

import (
	"errors"
	"fmt"
)

// Sentinel
var ErrInvalidAmount = errors.New("invalid amount")

type ValidationError struct {
	Field   string
	Wrapped error
}

func (e *ValidationError) Error() string {
	return fmt.Sprintf("validation error on %s: %v", e.Field, e.Wrapped)
}
func (e *ValidationError) Unwrap() error { return e.Wrapped }

type StorageError struct {
	Op      string
	Wrapped error
}

func (e *StorageError) Error() string {
	return fmt.Sprintf("storage error on %s: %v", e.Op, e.Wrapped)
}
func (e *StorageError) Unwrap() error { return e.Wrapped }

func validateAmount(cents int) error {
	if cents <= 0 {
		return &ValidationError{
			Field:   "amount_cents",
			Wrapped: ErrInvalidAmount,
		}
	}
	return nil
}

var ErrStorageFull = errors.New("storage full")

func store(cents int) error {
	return &StorageError{Op: "INSERT", Wrapped: ErrStorageFull}
}

func SavePayment(cents int) error {
	if err := validateAmount(cents); err != nil {
		return fmt.Errorf("SavePayment: %w", err)
	}
	if err := store(cents); err != nil {
		return fmt.Errorf("SavePayment: %w", err)
	}
	return nil
}

func main() {
	// Validation path
	err := SavePayment(-100)
	fmt.Println(err)
	fmt.Println("Is ErrInvalidAmount:", errors.Is(err, ErrInvalidAmount))
	var ve *ValidationError
	fmt.Println("As ValidationError:", errors.As(err, &ve), "field:", ve.Field)

	// Storage path
	err = SavePayment(9900)
	fmt.Println(err)
	fmt.Println("Is ErrStorageFull:", errors.Is(err, ErrStorageFull))
	var se *StorageError
	fmt.Println("As StorageError:", errors.As(err, &se), "op:", se.Op)
}
```

`errors.Is` unwraps through `fmt.Errorf("%w")` → `ValidationError.Unwrap()` → `ErrInvalidAmount`. Three levels traversed with one call. `errors.As` extracts the typed error from anywhere in that chain.

</Solution>

<Exercise n={6} title="Bit-flag permissions with a Stringer" level="easy">

Define a `Perm uint8` bit-flag type with `Read`, `Write`, `Execute` (use `1 << iota`). Add a `Has(flag Perm) bool` method and a `String()` that renders combined flags as `read|write|execute` (or `none`). In `main`, build `Read | Write`, grant `Execute` with `|=`, then revoke `Write` with `&^=`, printing the permission set at each step.

<Solution>

```go
package main

import (
	"fmt"
	"strings"
)

// Perm is a bit-set: each permission is one bit, combined with OR.
type Perm uint8

const (
	Read    Perm = 1 << iota // 1
	Write                    // 2
	Execute                  // 4
)

func (p Perm) Has(flag Perm) bool { return p&flag != 0 }

func (p Perm) String() string {
	if p == 0 {
		return "none"
	}
	var parts []string
	type nf struct {
		f Perm
		n string
	}
	// fixed order so the output is deterministic
	for _, x := range []nf{{Read, "read"}, {Write, "write"}, {Execute, "execute"}} {
		if p.Has(x.f) {
			parts = append(parts, x.n)
		}
	}
	return strings.Join(parts, "|")
}

func main() {
	perms := Read | Write
	fmt.Println("perms:", perms)                 // read|write
	fmt.Println("can write?", perms.Has(Write))  // true
	fmt.Println("can exec?", perms.Has(Execute)) // false

	perms |= Execute
	fmt.Println("after grant exec:", perms) // read|write|execute

	perms &^= Write                           // clear the Write bit
	fmt.Println("after revoke write:", perms) // read|execute
}
```

`1 << iota` gives `Read=1`, `Write=2`, `Execute=4` — each its own bit. `|` sets a bit, `&` tests one, and the AND-NOT operator `&^` clears one. The `String()` method is what makes `fmt.Println` print `read|write` instead of a bare `3`.

</Solution>

</Exercise>

<Exercise n={7} title="A generic memoizing decorator" level="medium">

Write `Memoize[K comparable, V any](fn func(K) V) func(K) V` that returns a function with the *same signature* but caches results per key, so the wrapped function runs at most once per distinct input. Make it safe for concurrent callers with a `sync.Mutex`. Prove it works by counting how many times the underlying function actually runs.

<Solution>

```go
package main

import (
	"fmt"
	"sync"
)

// Memoize is a generic decorator: it wraps any pure func(K) V and caches
// results per key. The wrapped function keeps its exact signature, so
// callers can't tell it's decorated.
func Memoize[K comparable, V any](fn func(K) V) func(K) V {
	var mu sync.Mutex
	cache := make(map[K]V)
	return func(k K) V {
		mu.Lock()
		defer mu.Unlock()
		if v, ok := cache[k]; ok {
			return v
		}
		v := fn(k)
		cache[k] = v
		return v
	}
}

func main() {
	calls := 0
	slowFee := func(amountCents int) int {
		calls++ // count real computations
		return amountCents / 100
	}

	fee := Memoize(slowFee)
	fmt.Println(fee(5000))                   // computes
	fmt.Println(fee(5000))                   // cached
	fmt.Println(fee(9900))                   // computes
	fmt.Println(fee(9900))                   // cached
	fmt.Println("real computations:", calls) // 2, not 4
}
```

The decorator preserves the `func(K) V` signature, so callers are oblivious to the cache. The `sync.Mutex` makes the whole check-then-fill atomic — without it, two goroutines could miss the cache for the same key and both run `fn`. Four calls, two distinct keys, two real computations.

</Solution>

</Exercise>

<Exercise n={8} title="A sealed sum type for fee tiers" level="hard">

Define a **sealed** `Tier` interface (an unexported `isTier()` method) with two variants: `Standard{}` and `Premium{ DiscountBps int64 }` (`DiscountBps` is basis points off the base fee). Write `Fee(t Tier, cents int64) int64` as an exhaustive type switch: `Standard` charges 1% (`cents / 100`); `Premium` charges the same base fee minus `DiscountBps` basis points of it. Include a `default: panic` for the unreachable case.

<Solution>

```go
package main

import "fmt"

// Sealed Tier: the unexported isTier() means only this package adds variants.
type Tier interface{ isTier() }

type Standard struct{}
type Premium struct{ DiscountBps int64 } // basis points off the base fee

func (Standard) isTier() {}
func (Premium) isTier()  {}

// Fee is exhaustive over the sealed set of tiers.
func Fee(t Tier, cents int64) int64 {
	switch v := t.(type) {
	case Standard:
		return cents / 100 // 1%
	case Premium:
		base := cents / 100
		return base - base*v.DiscountBps/10000
	default:
		panic(fmt.Sprintf("unhandled tier %T", t))
	}
}

func main() {
	fmt.Println("standard:", Fee(Standard{}, 100000))                    // 1000
	fmt.Println("premium 20%:", Fee(Premium{DiscountBps: 2000}, 100000)) // 800
}
```

Because `isTier()` is unexported, no other package can add a `Tier`, so the switch is provably complete — the `default: panic` only fires if *this* package adds a variant and forgets a case (which the `exhaustive` linter would catch first). Premium's 2000 bps = 20% off the $10.00 base fee: `1000 - 1000*2000/10000 = 800`.

</Solution>

<Recap>

- **Functional options** (`Option func(*config)`) replace telescoping constructors with composable, zero-overhead configuration. Define sensible defaults in the constructor; let callers override with `With*` functions.
- **Accept interfaces, return structs**: accept the narrowest interface your function needs (defined at the consumer); return the concrete type so callers get the full API. Never return an interface unless the concrete type is truly an implementation detail.
- **Dependency injection** is just passing the dependency as a parameter — no framework needed. Inject interfaces; test with fakes. Never reach for a global.
- **Worker pools** bound parallelism: `numWorkers` goroutines share a buffered job channel. `close(jobCh)` signals completion; `wg.Go(func(){...})` (Go 1.25) launches each worker and tracks it; always close `resultCh` from a single goroutine after `wg.Wait()`.
- **Fan-out / fan-in**: distribute one stream across N parallel goroutines, then merge with `sync.WaitGroup` + a goroutine that closes the merged channel.
- **Middleware via closures** (`func(http.Handler) http.Handler`) is the decorator pattern for free: each middleware captures `next` in a closure and calls it inside the new handler. Apply with a `Chain` helper. Request flows in, response flows out.
- **GoF patterns** mostly collapse into Go idioms: Singleton → package-level var or `sync.Once`; Factory → a function; Strategy → a one-method interface or function type; Observer → a channel; Adapter → a thin wrapper struct.
- **Error wrapping** with `%w` and `Unwrap()` lets `errors.Is` (sentinel check) and `errors.As` (typed extraction) traverse the whole chain. Add context at each layer; never discard.
- **Builder & fluent APIs**: a mutable struct whose methods `return q`, with errors deferred to `Build()`. Beats options when construction is staged, conditional, or accumulative.
- **Advanced options**: the self-referential form (`func(*T) Option`) returns the option that undoes it (set-and-restore); the interface form makes options named, documented, and inspectable. `Must` belongs only at init.
- **Type-safe idioms**: newtype IDs (`type AccountID string`) catch swapped arguments at compile time; `1 << iota` bit-flags pack a boolean set into one int; an unexported method *seals* an interface into a closed sum type with an exhaustive switch.
- **Lazy init & generics**: `sync.OnceValue`/`OnceFunc`/`OnceValues` (Go 1.21) are the modern lazy singleton; generic decorators wrap any func keeping its signature (memoize, retry); `Set[T comparable]` is the `map[T]struct{}` idiom made reusable.
- **More behavioral patterns**: the Null Object returns a no-op instead of nil; a generic Pub/Sub broker is the Observer at scale (non-blocking fan-out); range-over-func (`iter.Seq`) makes your type range-able — always honor the `!yield` stop — and `iter.Pull` steps it by hand; method values and expressions turn methods into first-class funcs.
- All the concurrency patterns here (fan-out/fan-in, worker pools, pipelines) get the full, deep treatment in Part 2 — **Concurrency Patterns** (Part 2, Chapter 6). Look forward.

</Recap>
