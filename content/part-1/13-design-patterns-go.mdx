## Functional Options

<Define term="Functional Options" since="Design Patterns, the Go Way (Part 1, Chapter 11 — this chapter)">
A **functional option** is a function with the signature `func(*Config)` that mutates a private configuration struct. Instead of a constructor that takes fifteen arguments, you define one constructor plus a set of `With*` functions — each returning an option. Callers compose exactly what they need; the rest stays at its safe default. **Why it matters:** telescoping constructors (`NewClientWithTimeoutAndRetries`) explode combinatorially and cannot be composed at runtime. Functional options scale to any number of knobs with zero breaking changes to existing call sites.
</Define>

Picture this: you are building an HTTP client for your payment gateway. You need timeouts, retry counts, a base URL, optional tracing, maybe a custom transport. The naive approach is a struct with fifteen fields and a constructor that takes fifteen arguments. The *slightly-less-naive-but-still-wrong* approach is fifteen separate `NewClientWith*` constructors.

Both are embarrassing. Let me show you the right way.

### The telescoping constructor problem

The **functional options** pattern replaces a proliferating family of constructors with a single constructor that accepts a variadic list of `Option` functions, each of which mutates a private `config` struct. Here is the full, runnable implementation:

```go
package main

import (
	"fmt"
	"net/http"
	"time"
)

// config holds every tunable knob for our payment client.
// It is unexported — callers never touch it directly.
type config struct {
	baseURL    string
	timeout    time.Duration
	retries    int
	httpClient *http.Client
}

// Option is a function that mutates a config.
// This is the type alias that makes the pattern legible.
type Option func(*config)

// WithTimeout returns an Option that sets the request timeout.
func WithTimeout(d time.Duration) Option {
	return func(c *config) {
		c.timeout = d
	}
}

// WithRetries returns an Option that caps retry attempts.
func WithRetries(n int) Option {
	return func(c *config) {
		if n < 0 {
			n = 0
		}
		c.retries = n
	}
}

// WithHTTPClient injects a custom *http.Client (useful in tests).
func WithHTTPClient(hc *http.Client) Option {
	return func(c *config) {
		c.httpClient = hc
	}
}

// PaymentClient wraps a configured HTTP client for our gateway.
type PaymentClient struct {
	cfg *config
}

// NewPaymentClient builds a PaymentClient from a base URL
// plus any number of functional options.
func NewPaymentClient(baseURL string, opts ...Option) *PaymentClient {
	// Start from safe, production-ready defaults.
	cfg := &config{
		baseURL: baseURL,
		timeout: 10 * time.Second,
		retries: 3,
	}
	// Apply each option in order — last one wins on conflicts.
	for _, o := range opts {
		o(cfg)
	}
	if cfg.httpClient == nil {
		cfg.httpClient = &http.Client{Timeout: cfg.timeout}
	}
	return &PaymentClient{cfg: cfg}
}

func main() {
	// Production client: tight timeout, more retries.
	prod := NewPaymentClient(
		"https://api.stripe.com",
		WithTimeout(30*time.Second),
		WithRetries(5),
	)
	fmt.Printf("prod: base=%s timeout=%s retries=%d\n",
		prod.cfg.baseURL, prod.cfg.timeout, prod.cfg.retries)

	// Test client: zero retries, custom transport (you'd mock http.Client here).
	test := NewPaymentClient(
		"http://localhost:8080",
		WithRetries(0),
	)
	fmt.Printf("test: base=%s timeout=%s retries=%d\n",
		test.cfg.baseURL, test.cfg.timeout, test.cfg.retries)
}
```

<UnderTheHood title="How closures capture state">

Each `WithTimeout(d)` call allocates a new function value on the heap — a **closure**. The closure captures the variable `d` (in this case, the `time.Duration` argument) by reference at the moment `WithTimeout` returns. When the constructor loops over `opts` and calls `o(cfg)`, the closure's captured `d` is read and written into `cfg.timeout`.

The compiler performs **escape analysis** to decide whether the closed-over variable lives on the stack or must be heap-allocated. A closure that outlives the function that created it (as our `Option` values do — they're passed to the constructor) causes its captures to escape to the heap. This is one or two small allocations per option, which is entirely acceptable; the composability and testability you get in return are worth far more.

The `func(*config)` signature is the *entire* abstraction. No interface, no reflection, no registry — just a first-class function type. Go's type system makes this as lightweight as it gets.

</UnderTheHood>

## Accept Interfaces Return Structs

<Define term="Accept Interfaces, Return Structs" since="Structs, Methods, Interfaces & Errors (Part 1, Chapter 2)">
**Accept interfaces** in function parameters — your function asks for the narrowest behavior it needs (e.g. `io.Reader`), so callers can pass any type that satisfies it. **Return structs** (concrete types) from constructors — so callers get the full API without artificial restriction. **Why it matters:** accepting a concrete `*sql.DB` couples your function to one implementation forever and blocks testing. Returning an interface hides methods the concrete type has, forcing callers into type assertions they should never need.
</Define>

This is the single most-quoted Go design proverb, and the most consistently misunderstood. Let me fix that right now.

The rule has two halves:

1. **Accept interfaces** — your function parameters should be interface types where possible, so callers can pass anything that satisfies the contract. This is where you *consume* behavior.
2. **Return structs** (or concrete types) — your function's return type should be the concrete thing it actually creates, so callers get the full API without artificial restriction.

Here is the anti-pattern that violates both:

The reason returning an interface is harmful: it *hides* the return type. If you return `io.ReadCloser` but the concrete type also implements `io.Seeker`, callers can never use `Seek` without a type assertion — and you've forced them into that corner for no reason. Return the concrete struct; let callers decide what interface to store it in.

```go
package main

import (
	"bytes"
	"fmt"
	"io"
	"strings"
)

// PaymentLogProcessor reads a payment log line-by-line.
// Its only requirement: something it can read bytes from.
type PaymentLogProcessor struct {
	r       io.Reader // private: we only need to read
	lineNum int
}

// NewPaymentLogProcessor accepts any io.Reader — file, buffer, network conn.
// It returns the concrete *PaymentLogProcessor so callers get the full API.
func NewPaymentLogProcessor(r io.Reader) *PaymentLogProcessor {
	return &PaymentLogProcessor{r: r}
}

// Next reads the next line from the log. Returns ("", io.EOF) when done.
func (p *PaymentLogProcessor) Next() (string, error) {
	buf := make([]byte, 0, 64)
	b := make([]byte, 1)
	for {
		_, err := p.r.Read(b)
		if err != nil {
			if len(buf) > 0 {
				p.lineNum++
				return string(buf), nil
			}
			return "", err
		}
		if b[0] == '\n' {
			p.lineNum++
			return string(buf), nil
		}
		buf = append(buf, b[0])
	}
}

// LineNumber reports which line was last read.
func (p *PaymentLogProcessor) LineNumber() int { return p.lineNum }

func main() {
	// In a unit test we'd use bytes.NewReader or strings.NewReader — no file needed.
	log := strings.NewReader("txn=1 amount=9900\ntxn=2 amount=4500\n")
	proc := NewPaymentLogProcessor(log)

	for {
		line, err := proc.Next()
		if err == io.EOF {
			break
		}
		fmt.Printf("line %d: %s\n", proc.LineNumber(), line)
	}

	// bytes.Buffer also satisfies io.Reader:
	proc2 := NewPaymentLogProcessor(bytes.NewBufferString("txn=3 amount=2000\n"))
	line, _ := proc2.Next()
	fmt.Println("from buffer:", line)
}
```

<Callout kind="pro" title="Define interfaces at the consumer, not the producer">

The idiomatic Go way: the *caller* defines the interface it needs, right next to where it uses it. The implementation never declares "I implement X" — it just has the right methods. This is the opposite of Java, where the producer declares `implements Serializable` and you drag that declaration everywhere.

A one-method interface is a feature, not a failure of ambition. `io.Reader`, `io.Writer`, `fmt.Stringer` — the smallest useful contracts in the entire standard library are one method each. Match that discipline.

</Callout>

## Dependency Injection

<Define term="Dependency Injection (via interfaces)" since="Software Design & Architecture (Part 1, Chapter 12)">
**Dependency injection** means passing a service's collaborators in from the outside — as constructor arguments — instead of reaching for package-level globals or calling `New*()` internally. In Go the idiomatic form is: define a minimal interface next to the consumer, accept that interface in the constructor, and inject real or fake implementations at the call site. **Why it matters:** global deps are invisible (you can't see what a function depends on), untestable (no substitute without a real DB/network), and cause race conditions in parallel tests. Injected interfaces make every dependency explicit, swappable, and mockable with a five-line fake.
</Define>

Dependency injection sounds like a framework. In Go it is not. It is just: **pass the thing as a parameter instead of reaching for a global**.

The real-world scenario: your `OrderService` needs a database, a payment gateway client, and a mailer. The wrong way is to call package-level globals from inside the service methods. The right way is to put those dependencies in the struct and inject them at construction time.

Here is the testable pattern in full:

```go
package main

import (
	"context"
	"errors"
	"fmt"
)

// --- Domain ---

type Order struct {
	ID          string
	AmountCents int
	Token       string
}

// --- Consumer-defined interfaces (defined HERE, next to the consumer) ---

type OrderStore interface {
	SaveOrder(ctx context.Context, o Order) error
}

type ChargeGateway interface {
	Charge(ctx context.Context, amountCents int, token string) error
}

// --- The service ---

type OrderService struct {
	store   OrderStore
	gateway ChargeGateway
}

func NewOrderService(store OrderStore, gw ChargeGateway) *OrderService {
	return &OrderService{store: store, gateway: gw}
}

func (s *OrderService) PlaceOrder(ctx context.Context, o Order) error {
	// Charge first — if it fails, we never persist the order.
	if err := s.gateway.Charge(ctx, o.AmountCents, o.Token); err != nil {
		return fmt.Errorf("charge failed: %w", err)
	}
	if err := s.store.SaveOrder(ctx, o); err != nil {
		return fmt.Errorf("save failed: %w", err)
	}
	return nil
}

// --- Fake implementations for tests (or for main, here) ---

type fakeStore struct{ saved []Order }

func (f *fakeStore) SaveOrder(_ context.Context, o Order) error {
	f.saved = append(f.saved, o)
	return nil
}

type fakeGateway struct{ shouldFail bool }

func (f *fakeGateway) Charge(_ context.Context, amountCents int, token string) error {
	if f.shouldFail {
		return errors.New("card declined")
	}
	fmt.Printf("  charged %d cents on token %s\n", amountCents, token)
	return nil
}

func main() {
	ctx := context.Background()
	store := &fakeStore{}
	gw := &fakeGateway{}
	svc := NewOrderService(store, gw)

	err := svc.PlaceOrder(ctx, Order{ID: "ord_1", AmountCents: 9900, Token: "tok_visa"})
	fmt.Println("place order err:", err)
	fmt.Println("orders saved:", len(store.saved))

	// Now simulate a declined card:
	gw.shouldFail = true
	err = svc.PlaceOrder(ctx, Order{ID: "ord_2", AmountCents: 4500, Token: "tok_bad"})
	fmt.Println("declined err:", err)
	fmt.Println("orders saved (should still be 1):", len(store.saved))
}
```

<UnderTheHood title="Interface values — the two-word secret">

An interface value in Go is exactly **two machine words**: a pointer to the *type descriptor* (also called the itab for non-empty interfaces) and a pointer to the *concrete data*. When you assign `var gw ChargeGateway = &fakeGateway{}`, Go writes the address of the `fakeGateway` type's method table into word one, and the address of your `fakeGateway` instance into word two.

This is why Go interfaces have *zero overhead* for dependency injection: you are not building a vtable at runtime, not allocating a proxy object, not using reflection. A method call through an interface does one pointer indirection (itab → method pointer) and then a direct call. That is the entire cost.

It also explains the **typed nil trap**: if you return a `*fakeGateway` that happens to be nil inside an interface, the interface value's type word is non-nil even though the data word is nil — so `err != nil` is `true` even though the wrapped pointer is zero. The error-handling chapter covers this in full depth; bookmark it.

</UnderTheHood>

## Worker Pools

<Define term="Worker Pool / Fan-In / Fan-Out" since="Concurrency Patterns (Part 2, Chapter 6)">
A **worker pool** is a fixed set of N goroutines that all read from one shared job channel, bounding how much memory and CPU you use regardless of how many jobs arrive. **Fan-out** is distributing one stream of work to multiple goroutines in parallel. **Fan-in** is merging the results from multiple parallel goroutines back into one output channel. **Why it matters:** spawning one goroutine per job works fine at 100 jobs; at 50,000 it exhausts memory. Processing jobs sequentially misses the overnight window. A pool gives you the throughput without the blowup.
</Define>

Your payment batch processor needs to reconcile 50,000 transactions overnight. Spawning 50,000 goroutines would exhaust memory. Doing them one-by-one would miss the window. You need **bounded parallelism**: a fixed-size pool of worker goroutines, each pulling from a shared job queue.

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"time"
)

// ReconcileJob is one unit of work — one transaction to reconcile.
type ReconcileJob struct {
	TxnID       string
	AmountCents int
}

// ReconcileResult carries the outcome back to the coordinator.
type ReconcileResult struct {
	TxnID string
	Err   error
}

// RunWorkerPool launches numWorkers goroutines, fans out jobs,
// collects results, and returns when all jobs are done.
func RunWorkerPool(
	ctx context.Context,
	jobs []ReconcileJob,
	numWorkers int,
) []ReconcileResult {
	jobCh := make(chan ReconcileJob, len(jobs))   // buffered: won't block senders
	resultCh := make(chan ReconcileResult, len(jobs))

	// --- Fan out: start N workers ---
	// wg.Go (Go 1.25) calls Add(1) and launches the goroutine in one step.
	var wg sync.WaitGroup
	for i := 0; i < numWorkers; i++ {
		wg.Go(func() {
			for job := range jobCh { // blocks until a job arrives or channel closes
				select {
				case <-ctx.Done():
					resultCh <- ReconcileResult{TxnID: job.TxnID, Err: ctx.Err()}
					continue
				default:
				}
				// Simulate reconciliation work (network call, DB write, etc.)
				time.Sleep(5 * time.Millisecond)
				resultCh <- ReconcileResult{TxnID: job.TxnID}
			}
		})
	}

	// --- Send all jobs ---
	for _, j := range jobs {
		jobCh <- j
	}
	close(jobCh) // signal workers: no more jobs

	// --- Wait for workers, then close results ---
	go func() {
		wg.Wait()
		close(resultCh)
	}()

	// --- Collect ---
	var results []ReconcileResult
	for r := range resultCh {
		results = append(results, r)
	}
	return results
}

func main() {
	jobs := make([]ReconcileJob, 12)
	for i := range jobs {
		jobs[i] = ReconcileJob{TxnID: fmt.Sprintf("txn_%02d", i+1), AmountCents: 1000 * (i + 1)}
	}

	ctx := context.Background()
	results := RunWorkerPool(ctx, jobs, 4) // 4 workers, 12 jobs
	fmt.Printf("processed %d jobs with 4 workers\n", len(results))
	for _, r := range results {
		if r.Err != nil {
			fmt.Printf("  FAIL %s: %v\n", r.TxnID, r.Err)
		}
	}
}
```

```go
	"context"
	"fmt"
	"sync"
	"time"

type ReconcileJob struct {
	TxnID       string
	AmountCents int
}
type ReconcileResult struct {
	TxnID string
	Err   error
}

func RunWorkerPool(ctx context.Context, jobs []ReconcileJob, numWorkers int) []ReconcileResult {
	jobCh := make(chan ReconcileJob, len(jobs))
	resultCh := make(chan ReconcileResult, len(jobs))
	var wg sync.WaitGroup
	for i := 0; i < numWorkers; i++ {
		wg.Go(func() { // wg.Go (Go 1.25): Add(1) + launch in one call
			for job := range jobCh {
				select {
				case <-ctx.Done():
					resultCh <- ReconcileResult{TxnID: job.TxnID, Err: ctx.Err()}
					continue
				default:
				}
				time.Sleep(5 * time.Millisecond)
				resultCh <- ReconcileResult{TxnID: job.TxnID}
			}
		})
	}
	for _, j := range jobs {
		jobCh <- j
	}
	close(jobCh)
	go func() { wg.Wait(); close(resultCh) }()
	var results []ReconcileResult
	for r := range resultCh {
		results = append(results, r)
	}
	return results
}

func main() {
	jobs := make([]ReconcileJob, 12)
	for i := range jobs {
		jobs[i] = ReconcileJob{TxnID: fmt.Sprintf("txn_%02d", i+1), AmountCents: 1000 * (i + 1)}
	}
```

<Callout kind="tip" title="sync.WaitGroup.Go — new in Go 1.25">

Before Go 1.25, launching a pooled goroutine required three lines: `wg.Add(1)`, then `go func() { defer wg.Done(); ... }()`. The boilerplate was easy to get wrong — forget the `Add` and `Wait` returns early; forget the `defer Done` and the pool never shuts down.

As of Go 1.25, `wg.Go(func() { ... })` does both in one call: it increments the counter and starts the goroutine. The examples in this chapter use this form. If you are reading code written before Go 1.25, the three-line pattern is correct — just more verbose.

</Callout>

## Fan-In and Fan-Out

**Fan-out** splits one stream of work across multiple goroutines. **Fan-in** merges multiple streams back into one. Together they are the pipeline architecture for every high-throughput Go service.

Real scenario: your fraud-detection pipeline ingests a stream of payment events, fans them out to three parallel analyzers (velocity check, geo-anomaly check, device fingerprint check), and fans their verdicts back into one decision stream.

```go
package main

import (
	"fmt"
	"sync"
)

type PaymentEvent struct {
	TxnID  string
	UserID string
	Amount int
}

type Verdict struct {
	TxnID   string
	Checker string
	Flagged bool
}

// fanOut distributes events from `in` to `n` output channels.
func fanOut(in <-chan PaymentEvent, n int) []<-chan PaymentEvent {
	outs := make([]chan PaymentEvent, n)
	for i := range outs {
		outs[i] = make(chan PaymentEvent, 4)
	}
	go func() {
		defer func() {
			for _, o := range outs { close(o) }
		}()
		i := 0
		for e := range in {
			outs[i%n] <- e // round-robin
			i++
		}
	}()
	result := make([]<-chan PaymentEvent, n)
	for i, o := range outs { result[i] = o }
	return result
}

// checker simulates one fraud analysis lane.
func checker(name string, in <-chan PaymentEvent) <-chan Verdict {
	out := make(chan Verdict, 4)
	go func() {
		defer close(out)
		for e := range in {
			// Stub: flag anything over $500 (50000 cents) as suspicious.
			out <- Verdict{TxnID: e.TxnID, Checker: name, Flagged: e.Amount > 50000}
		}
	}()
	return out
}

// fanIn merges multiple verdict channels into one.
func fanIn(channels ...<-chan Verdict) <-chan Verdict {
	merged := make(chan Verdict, 8)
	var wg sync.WaitGroup
	// wg.Go (Go 1.25) combines Add(1) + goroutine launch.
	for _, ch := range channels {
		ch := ch
		wg.Go(func() {
			for v := range ch {
				merged <- v
			}
		})
	}
	go func() { wg.Wait(); close(merged) }()
	return merged
}

func main() {
	// Source: a stream of payment events.
	source := make(chan PaymentEvent, 5)
	events := []PaymentEvent{
		{TxnID: "t1", UserID: "u1", Amount: 9900},
		{TxnID: "t2", UserID: "u2", Amount: 75000}, // suspicious
		{TxnID: "t3", UserID: "u1", Amount: 2500},
		{TxnID: "t4", UserID: "u3", Amount: 99999}, // suspicious
		{TxnID: "t5", UserID: "u4", Amount: 14999},
	}
	for _, e := range events { source <- e }
	close(source)

	// Fan out to 3 checker lanes.
	lanes := fanOut(source, 3)
	velocity := checker("velocity", lanes[0])
	geo      := checker("geo-anomaly", lanes[1])
	device   := checker("device-fp", lanes[2])

	// Fan in all verdicts.
	verdicts := fanIn(velocity, geo, device)

	for v := range verdicts {
		if v.Flagged {
			fmt.Printf("FLAGGED by %s: %s\n", v.Checker, v.TxnID)
		}
	}
}
```

<Define term="Middleware / Decorator (via closures)" since="HTTP Servers: JSON, Streaming & WebSockets (Part 1, Chapter 17)">
A **middleware** is a function with the signature `func(http.Handler) http.Handler`. It takes the next handler, returns a *new* handler that does something before or after calling the original. This is the **decorator pattern**: each middleware *wraps* the previous one, forming a chain. In Go, closures make it effortless — the returned handler captures `next` in its environment and calls it when the request arrives. **Why it matters:** logging, auth, rate limiting, and tracing are *cross-cutting concerns* — they need to run on every request. Without middleware you copy that logic into every handler. With a chain, each concern lives in one place, is independently testable, and can be added or removed without touching handlers.
</Define>

Every HTTP service needs cross-cutting concerns applied to every handler: logging, auth checks, rate limiting, request tracing. Doing this inside each handler is a crime. The Go way: **middleware as a function that wraps a handler function**.

The type is `func(http.Handler) http.Handler`. That's it. A middleware takes a handler, returns a *new* handler that does something before or after calling the original.

```go
package main

import (
	"fmt"
	"log"
	"net/http"
	"time"
)

// Handler is the type we're decorating — a standard http.HandlerFunc.
// We use http.Handler (the interface) for maximum composability.

// LoggingMiddleware wraps a handler and logs the request duration.
// It is a closure: `next` is captured and called inside the returned handler.
func LoggingMiddleware(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		start := time.Now()
		next.ServeHTTP(w, r)  // call the INNER handler
		log.Printf("[LOG] %s %s took %v", r.Method, r.URL.Path, time.Since(start))
	})
}

// AuthMiddleware checks for a valid API key before calling the next handler.
func AuthMiddleware(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		key := r.Header.Get("X-API-Key")
		if key != "secret-key-abc" {
			http.Error(w, "unauthorized", http.StatusUnauthorized)
			return // short-circuit — next is never called
		}
		next.ServeHTTP(w, r)
	})
}

// Chain applies middleware in declaration order (outermost first).
// The request passes through each layer before reaching the handler.
func Chain(h http.Handler, middlewares ...func(http.Handler) http.Handler) http.Handler {
	// Apply in reverse so the first middleware listed is the outermost.
	for i := len(middlewares) - 1; i >= 0; i-- {
		h = middlewares[i](h)
	}
	return h
}

// PaymentsHandler is the real business logic — clean, no cross-cutting noise.
func PaymentsHandler(w http.ResponseWriter, r *http.Request) {
	fmt.Fprintln(w, "Payment accepted")
}

func main() {
	// Compose: every request hits Logging → Auth → PaymentsHandler.
	handler := Chain(
		http.HandlerFunc(PaymentsHandler),
		LoggingMiddleware,
		AuthMiddleware,
	)

	// In a real server: http.Handle("/payments", handler)
	// Here we simulate a request manually.
	fmt.Println("Middleware chain built. In production: http.Handle(\"/payments\", handler)")
	fmt.Println("Chain: LoggingMiddleware → AuthMiddleware → PaymentsHandler")
	_ = handler
}
```

    { lane: "auth", kind: "done", label: "AuthMiddleware returns", note: "Auth has nothing to do after the inner call. It returns." },
    { lane: "log", kind: "done", label: "log duration, return", note: "Logging captures time.Since(start) and writes the duration log line. Request complete." }

/>

<UnderTheHood title="Why closures make the decorator pattern effortless">

Each middleware function `LoggingMiddleware(next http.Handler) http.Handler` returns a new closure — an anonymous function value that *captures `next`* in its environment. The `next` variable lives on the closure's heap-allocated environment, not on any stack. When `ServeHTTP` is called later (possibly from a completely different goroutine), the closure reads `next` from that environment and calls it.

This is the **decorator pattern** from the GoF book — but in Go it costs exactly one function allocation per middleware level, no interface boilerplate, no anonymous inner class. The same closure mechanism that powers functional options powers middleware chains. Both patterns exploit the same language feature: first-class function values that capture their lexical environment.

Closures are allocated on the heap when they escape (as middleware closures always do — they outlive the function that created them). The escape is cheap, and the function-call overhead is a single indirect call through the captured `next` pointer — negligible compared to any real handler work.

</UnderTheHood>

## GoF Patterns in Go

Let me be direct: most of the Gang of Four patterns exist to solve problems that Go's language features simply do not have. Go has first-class functions, implicit interface satisfaction, and composition over inheritance. Several GoF patterns collapse into nothing.

### Singleton — and why you almost certainly don't need one

The Java Singleton's entire job is to ensure a class is instantiated exactly once. In Go, **package-level variables are already initialized exactly once** by the runtime. `sync.Once` handles the lazy case.

```go
package main

import (
	"fmt"
	"sync"
)

// --- Package-level singleton: initialized once by the runtime. ---
// Fine for truly global, immutable config. Still better to inject it.
var defaultLogger = newLogger("INFO")

type Logger struct{ level string }

func newLogger(level string) *Logger { return &Logger{level: level} }
func (l *Logger) Log(msg string)     { fmt.Printf("[%s] %s\n", l.level, msg) }

// --- Lazy singleton with sync.Once (for expensive initialization) ---
var (
	dbOnce     sync.Once
	dbInstance *fakeDB
)

type fakeDB struct{ dsn string }

func GetDB() *fakeDB {
	dbOnce.Do(func() {
		// This runs exactly once, even across a thousand goroutines.
		dbInstance = &fakeDB{dsn: "postgres://..."}
		fmt.Println("DB connected (runs once)")
	})
	return dbInstance
}

func main() {
	defaultLogger.Log("using package-level logger")

	// All three calls to GetDB return the same instance.
	db1 := GetDB()
	db2 := GetDB()
	db3 := GetDB()
	fmt.Printf("db1 == db2: %v, db2 == db3: %v\n", db1 == db2, db2 == db3)
}
```

<Callout kind="warn" title="Globals are usually the wrong answer">

A package-level singleton is globally mutable shared state. Tests cannot run in parallel without races. You cannot inject a fake. The moment you want two different databases in a test, you're stuck. **Prefer injection**: create the dependency once in `main`, inject it everywhere it's needed. Reserve `sync.Once` for genuinely expensive one-time initialization (a connection pool, a compiled regex) where construction cost is real.

</Callout>

### Factory — just a constructor function

In Java, a Factory is a class whose job is to create other classes. In Go, that's just a function. `NewPaymentClient(...)`, `NewOrderService(...)` — you've been writing factories this entire chapter.

If you need a *family* of factories keyed by a string (e.g., `"stripe"` → Stripe client, `"paypal"` → PayPal client), a map of constructor functions is idiomatic:

```go
package main

import "fmt"

type Gateway interface {
	Name() string
}

type StripeGateway struct{}
func (s *StripeGateway) Name() string { return "Stripe" }

type PayPalGateway struct{}
func (p *PayPalGateway) Name() string { return "PayPal" }

// Factory map: a string → a constructor function.
var gatewayFactory = map[string]func() Gateway{
	"stripe": func() Gateway { return &StripeGateway{} },
	"paypal": func() Gateway { return &PayPalGateway{} },
}

func NewGateway(provider string) (Gateway, error) {
	fn, ok := gatewayFactory[provider]
	if !ok {
		return nil, fmt.Errorf("unknown payment provider %q", provider)
	}
	return fn(), nil
}

func main() {
	gw, err := NewGateway("stripe")
	fmt.Println(gw.Name(), err)
	gw, err = NewGateway("paypal")
	fmt.Println(gw.Name(), err)
	_, err = NewGateway("venmo")
	fmt.Println(err)
}
```

### Strategy — just an interface (or a function)

The Strategy pattern says: define a family of algorithms, encapsulate each, make them interchangeable. In Go, a one-method interface *is* the strategy pattern. You've already seen this: `ChargeGateway` is a strategy. `OrderStore` is a strategy.

If the strategy has exactly one method, consider making it a function type instead:

```go
// Strategy as a function type — no interface needed for one method.
type FeeCalculator func(amountCents int) int

func flatFee(amount int) int      { return 30 }          // $0.30 flat
func percentFee(amount int) int   { return amount / 100 } // 1%

func ApplyFee(amount int, calc FeeCalculator) int {
	return amount + calc(amount)
}
```

### Observer — channels

The Observer pattern: when an event happens, notify all subscribers. In Go, that's a channel. Interested goroutines range over the channel; when you're done, close it. No `Subscribe`/`Unsubscribe` machinery required.

For multi-subscriber fan-out (each subscriber gets every event), a `sync.Map` of channels or a dedicated broker type works. But the idiomatic Go first instinct is always: **can I just use a channel?**

### Adapter — a wrapper struct or a function

When you need a type to satisfy an interface it wasn't designed for, write a thin wrapper struct (or a function type conversion, like `http.HandlerFunc`). This is the Adapter pattern, and in Go it costs almost nothing:

```go
// LegacyMailer has a different method signature than our Notifier interface.
type LegacyMailer struct{}
func (m *LegacyMailer) SendEmail(to, subject, body string) error { return nil }

// Notifier is what our service expects.
type Notifier interface {
	Notify(ctx context.Context, to, message string) error
}

// MailerAdapter wraps LegacyMailer to satisfy Notifier.
type MailerAdapter struct{ m *LegacyMailer }
func (a *MailerAdapter) Notify(ctx context.Context, to, message string) error {
	return a.m.SendEmail(to, "Notification", message)
}
```

### Command — a func, or a struct with one method

<Define term="Command pattern (GoF)" since="Design Patterns, the Go Way (Part 1, Chapter 13 — this chapter)">
The **Command** pattern packages "a thing to do" as an object so you can queue it, log it, retry it, or undo it. The GoF version is an `interface` with an `Execute()` method plus a concrete command class per action. In Go, a command is usually just a `func() error` — a first-class value you can put on a channel, store in a slice, or replay from a write-ahead log. **Why it matters:** a payment processor that retries failed charges, replays a backlog after an outage, or supports undo needs to treat each action as data, not as a hard-coded call site.
</Define>

A `func() error` *is* a command. You only reach for a struct when the command also needs to carry metadata — an idempotency key, a name for logging, an `Undo` counterpart. Here a Meridian transfer queue stores commands and replays them:

<GoPlayground>

```go
package main

import (
	"errors"
	"fmt"
)

// Command is just a function value: a unit of work to run later.
type Command func() error

// Queue records commands so they can be replayed (e.g. after an outage).
type Queue struct {
	log []Command
}

func (q *Queue) Submit(c Command) { q.log = append(q.log, c) }

// Replay runs every queued command, collecting failures.
func (q *Queue) Replay() []error {
	var errs []error
	for i, c := range q.log {
		if err := c(); err != nil {
			errs = append(errs, fmt.Errorf("command %d: %w", i, err))
		}
	}
	return errs
}

func transfer(from, to string, cents int64) Command {
	return func() error {
		if cents <= 0 {
			return errors.New("amount must be positive")
		}
		fmt.Printf("transfer %d cents: %s -> %s\n", cents, from, to)
		return nil
	}
}

func main() {
	var q Queue
	q.Submit(transfer("acct-001", "acct-002", 5000))
	q.Submit(transfer("acct-001", "acct-003", -10)) // will fail
	q.Submit(transfer("acct-004", "acct-005", 2500))

	for _, err := range q.Replay() {
		fmt.Println("FAILED:", err)
	}
}
```

</GoPlayground>

The GoF `Command` interface with one `ConcreteCommand` class per action is pure ceremony here — a closure captures the receiver and arguments for free. Reach for a struct *only* when you need `Undo()` alongside `Execute()`.

### State — a method field, not a class hierarchy

<Define term="State pattern (GoF)" since="Design Patterns, the Go Way (Part 1, Chapter 13 — this chapter)">
The **State** pattern lets an object change its behavior when its internal state changes — a payment that behaves differently while `pending`, `authorized`, `captured`, or `refunded`. The GoF version gives each state its own class implementing a shared `State` interface, and the context delegates to the current state object. In Go, a small state machine is usually clearer as a typed constant plus a transition table (a `map`), or a single field holding a behavior func. **Why it matters:** a transaction's allowed transitions *are* the business rules — encoding them as data makes the illegal moves obvious and testable.
</Define>

A `map` from `(state, event)` to the next state captures the whole machine in one readable block — no class per state:

<GoPlayground>

```go
package main

import "fmt"

// State is a typed constant — not a class.
type State string

const (
	Pending    State = "pending"
	Authorized State = "authorized"
	Captured   State = "captured"
	Refunded   State = "refunded"
)

type Event string

const (
	Authorize Event = "authorize"
	Capture   Event = "capture"
	Refund    Event = "refund"
)

// transitions IS the state machine: (state, event) -> next state.
// A missing key means the transition is illegal.
var transitions = map[State]map[Event]State{
	Pending:    {Authorize: Authorized},
	Authorized: {Capture: Captured, Refund: Refunded},
	Captured:   {Refund: Refunded},
}

type Payment struct{ state State }

func (p *Payment) Fire(e Event) error {
	next, ok := transitions[p.state][e]
	if !ok {
		return fmt.Errorf("cannot %q a %s payment", e, p.state)
	}
	p.state = next
	return nil
}

func main() {
	p := &Payment{state: Pending}
	for _, e := range []Event{Authorize, Capture, Refund} {
		if err := p.Fire(e); err != nil {
			fmt.Println("rejected:", err)
			continue
		}
		fmt.Println("->", p.state)
	}
	// An illegal move from a terminal state:
	fmt.Println("refund again:", p.Fire(Capture))
}
```

</GoPlayground>

A `State` interface with four state classes would scatter the transition rules across four files. The transition map keeps every legal and illegal move on one screen — that *is* the spec.

### Template Method — a func field, not inheritance

<Define term="Template Method pattern (GoF)" since="Design Patterns, the Go Way (Part 1, Chapter 13 — this chapter)">
The **Template Method** pattern fixes the skeleton of an algorithm and lets subclasses fill in specific steps. The GoF version uses an abstract base class with `final` template method and abstract hook methods. Go has no inheritance, so you compose: a function holds the invariant steps and calls **hook functions** (or a small interface) for the variable ones. **Why it matters:** every payment rail (ACH, card, wire) runs the same pipeline — validate, reserve, settle, notify — but settles differently. The shared skeleton lives once; only the rail-specific step varies.
</Define>

The skeleton calls injected hooks; each rail supplies just its `settle` step:

<GoPlayground>

```go
package main

import (
	"errors"
	"fmt"
)

// settleFn is the one step that varies per payment rail.
type settleFn func(cents int64) error

// runPipeline is the fixed skeleton (the "template method").
// Only the settle step is injected — validate and notify are invariant.
func runPipeline(cents int64, settle settleFn) error {
	if cents <= 0 { // invariant step: validate
		return errors.New("amount must be positive")
	}
	if err := settle(cents); err != nil { // the varying step
		return fmt.Errorf("settle: %w", err)
	}
	fmt.Printf("notify: %d cents settled\n", cents) // invariant step: notify
	return nil
}

func achSettle(cents int64) error {
	fmt.Printf("  ACH: queued %d cents for next batch\n", cents)
	return nil
}

func cardSettle(cents int64) error {
	if cents > 1_000_000 {
		return errors.New("card limit exceeded")
	}
	fmt.Printf("  card: captured %d cents instantly\n", cents)
	return nil
}

func main() {
	fmt.Println("ACH:", runPipeline(5000, achSettle))
	fmt.Println("card:", runPipeline(2500, cardSettle))
	fmt.Println("card too big:", runPipeline(2_000_000, cardSettle))
}
```

</GoPlayground>

No abstract base class, no `protected` overrides — the skeleton is a plain function and the variable step is a parameter. When several steps vary together, group them into a small interface instead of passing five funcs.

## Error Wrapping

One more pattern that is distinctly Go: **wrapping errors to add context without losing the original**. This is not a GoF pattern — it is a Go-specific discipline.

The problem: your service's `PlaceOrder` returns an error. The caller wants to log it with enough context to debug it. But they also want to test for *specific* error types (e.g., "is this a card decline vs. a DB error?").

```go
package main

import (
	"errors"
	"fmt"
)

// Sentinel errors — named, comparable values your callers can check with errors.Is.
var ErrCardDeclined = errors.New("card declined")

// GatewayError is a typed error your callers can inspect with errors.As.
type GatewayError struct {
	Provider string
	Code     string
	Wrapped  error
}

func (e *GatewayError) Error() string {
	return fmt.Sprintf("gateway %s error %s: %v", e.Provider, e.Code, e.Wrapped)
}

// Unwrap lets errors.Is and errors.As traverse the chain.
func (e *GatewayError) Unwrap() error { return e.Wrapped }

// charge simulates a payment gateway call.
func charge(amountCents int) error {
	if amountCents > 50000 {
		// Wrap the sentinel with provider context.
		return &GatewayError{Provider: "stripe", Code: "card_declined", Wrapped: ErrCardDeclined}
	}
	return nil
}

// placeOrder wraps gateway errors with business context.
func placeOrder(amountCents int) error {
	if err := charge(amountCents); err != nil {
		// %w makes the error unwrappable — errors.Is and errors.As can traverse it.
		return fmt.Errorf("placeOrder: %w", err)
	}
	return nil
}

func main() {
	err := placeOrder(75000)
	if err != nil {
		fmt.Println("error:", err)

		// errors.Is walks the whole chain for the sentinel.
		if errors.Is(err, ErrCardDeclined) {
			fmt.Println("→ it's a card decline")
		}

		// errors.As extracts the typed error from anywhere in the chain.
		var gwErr *GatewayError
		if errors.As(err, &gwErr) {
			fmt.Printf("→ provider=%s code=%s\n", gwErr.Provider, gwErr.Code)
		}
	}
}
```

<Exercise n={1} title="Functional option: WithBaseURL" level="easy">

Given the `NewPaymentClient` and `Option` types from this chapter, add a `WithBaseURL(url string) Option` function that validates the URL is non-empty and returns an error option if it is empty. The constructor should return `(*PaymentClient, error)` to surface validation failures.

<Solution>

```go
package main

import (
	"errors"
	"fmt"
	"time"
)

type config struct {
	baseURL string
	timeout time.Duration
	retries int
	err     error // carries the first validation error
}

type Option func(*config)

func WithBaseURL(url string) Option {
	return func(c *config) {
		if url == "" {
			c.err = errors.New("baseURL must not be empty")
			return
		}
		c.baseURL = url
	}
}

func WithTimeout(d time.Duration) Option {
	return func(c *config) { c.timeout = d }
}

type PaymentClient struct{ cfg *config }

func NewPaymentClient(opts ...Option) (*PaymentClient, error) {
	cfg := &config{timeout: 10 * time.Second, retries: 3}
	for _, o := range opts {
		o(cfg)
		if cfg.err != nil {
			return nil, cfg.err
		}
	}
	return &PaymentClient{cfg: cfg}, nil
}

func main() {

	fmt.Println(c != nil, err)
```

<Exercise n={3} title="Three-stage middleware chain" level="medium">

Build a three-layer middleware chain: `RecoveryMiddleware` (recover from panics and return 500), `LoggingMiddleware` (log method + path), `AuthMiddleware` (require `X-API-Key: secret`). Apply them to a `CheckoutHandler`. Use `httptest` to demonstrate a successful request, an unauthorized request, and a panicking handler.

<Solution>

```go
package main

import (
	"fmt"
	"log"
	"net/http"
	"net/http/httptest"
	"time"
)

func RecoveryMiddleware(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		defer func() {
			if rec := recover(); rec != nil {
				log.Printf("[PANIC] %v", rec)
				http.Error(w, "internal server error", http.StatusInternalServerError)
			}
		}()
		next.ServeHTTP(w, r)
	})
}

func LoggingMiddleware(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		start := time.Now()
		next.ServeHTTP(w, r)
		log.Printf("[LOG] %s %s %v", r.Method, r.URL.Path, time.Since(start))
	})
}

func AuthMiddleware(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		if r.Header.Get("X-API-Key") != "secret" {
			http.Error(w, "unauthorized", http.StatusUnauthorized)
			return
		}
		next.ServeHTTP(w, r)
	})
}

func Chain(h http.Handler, mws ...func(http.Handler) http.Handler) http.Handler {
	for i := len(mws) - 1; i >= 0; i-- {
		h = mws[i](h)
	}
	return h
}

func CheckoutHandler(w http.ResponseWriter, r *http.Request) {
	fmt.Fprintln(w, "checkout ok")
}

func PanicHandler(w http.ResponseWriter, r *http.Request) {
	panic("database exploded")
}

func main() {
	chain := Chain(http.HandlerFunc(CheckoutHandler), RecoveryMiddleware, LoggingMiddleware, AuthMiddleware)
	panicChain := Chain(http.HandlerFunc(PanicHandler), RecoveryMiddleware, LoggingMiddleware, AuthMiddleware)

	// Good request
	req := httptest.NewRequest("POST", "/checkout", nil)
	req.Header.Set("X-API-Key", "secret")
	rr := httptest.NewRecorder()
	chain.ServeHTTP(rr, req)
	fmt.Printf("checkout: %d %q\n", rr.Code, rr.Body.String())

	// Unauthorized
	req2 := httptest.NewRequest("POST", "/checkout", nil)
	rr2 := httptest.NewRecorder()
	chain.ServeHTTP(rr2, req2)
	fmt.Printf("unauth: %d %q\n", rr2.Code, rr2.Body.String())

	// Panic (with key, but handler panics)
	req3 := httptest.NewRequest("POST", "/checkout", nil)
	req3.Header.Set("X-API-Key", "secret")
	rr3 := httptest.NewRecorder()
	panicChain.ServeHTTP(rr3, req3)
	fmt.Printf("panic recovered: %d %q\n", rr3.Code, rr3.Body.String())
}
```

Recovery wraps the outermost deferred cleanup. The chain processes: Recovery → Logging → Auth → handler; panics unwind through Recovery's deferred function before the logger finishes.

</Solution>

</Exercise>

<Exercise n={4} title="Bounded worker pool with context cancellation" level="medium">

Extend the `RunWorkerPool` from this chapter to accept a `context.Context` with a deadline. When the deadline fires, workers should drain in-flight jobs but not start new ones, and the collector should return partial results with a note about how many jobs were skipped.

<Solution>

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"time"
)

type Job struct{ ID int }
type Result struct {
	JobID   int
	Skipped bool
}

func RunPool(ctx context.Context, jobs []Job, workers int) ([]Result, int) {
	jobCh := make(chan Job, len(jobs))
	resultCh := make(chan Result, len(jobs))
	var wg sync.WaitGroup

	for i := 0; i < workers; i++ {
		wg.Go(func() { // Go 1.25: Add(1) + launch in one call
			for job := range jobCh {
				select {
				case <-ctx.Done():
					resultCh <- Result{JobID: job.ID, Skipped: true}
					continue
				default:
				}
				time.Sleep(20 * time.Millisecond) // simulate work
				resultCh <- Result{JobID: job.ID}
			}
		})
	}

	for _, j := range jobs { jobCh <- j }
	close(jobCh)

	go func() { wg.Wait(); close(resultCh) }()

	var results []Result
	skipped := 0
	for r := range resultCh {
		results = append(results, r)
		if r.Skipped { skipped++ }
	}
	return results, skipped
}

func main() {
	jobs := make([]Job, 10)
	for i := range jobs { jobs[i] = Job{ID: i + 1} }

	// Very tight deadline — most jobs will be skipped.
	ctx, cancel := context.WithTimeout(context.Background(), 50*time.Millisecond)
	defer cancel()

	results, skipped := RunPool(ctx, jobs, 3)
	fmt.Printf("total=%d skipped=%d processed=%d\n", len(results), skipped, len(results)-skipped)
}
```

The key: workers check `ctx.Done()` with a `select` before starting work. Jobs that arrive after the deadline fire are still received from the channel (preventing a goroutine from blocking forever), but they are marked skipped and returned.

</Solution>

<Exercise n={5} title="Error wrapping chain" level="hard">

Define a `StorageError` typed error and a `ValidationError` typed error, each implementing `Unwrap()`. Write a `SavePayment` function that: validates the amount (must be positive), calls a fake store that always returns a `StorageError`. Wrap both errors with `%w` and demonstrate that `errors.Is` and `errors.As` correctly traverse a three-level chain.

<Solution>

```go
package main

import (
	"errors"
	"fmt"
)

// Sentinel
var ErrInvalidAmount = errors.New("invalid amount")

type ValidationError struct {
	Field   string
	Wrapped error
}

func (e *ValidationError) Error() string {
	return fmt.Sprintf("validation error on %s: %v", e.Field, e.Wrapped)
}
func (e *ValidationError) Unwrap() error { return e.Wrapped }

type StorageError struct {
	Op      string
	Wrapped error
}

func (e *StorageError) Error() string {
	return fmt.Sprintf("storage error on %s: %v", e.Op, e.Wrapped)
}
func (e *StorageError) Unwrap() error { return e.Wrapped }

func validateAmount(cents int) error {
	if cents <= 0 {
		return &ValidationError{
			Field:   "amount_cents",
			Wrapped: ErrInvalidAmount,
		}
	}
	return nil
}

var ErrStorageFull = errors.New("storage full")

func store(cents int) error {
	return &StorageError{Op: "INSERT", Wrapped: ErrStorageFull}
}

func SavePayment(cents int) error {
	if err := validateAmount(cents); err != nil {
		return fmt.Errorf("SavePayment: %w", err)
	}
	if err := store(cents); err != nil {
		return fmt.Errorf("SavePayment: %w", err)
	}
	return nil
}

func main() {
	// Validation path
	err := SavePayment(-100)
	fmt.Println(err)
	fmt.Println("Is ErrInvalidAmount:", errors.Is(err, ErrInvalidAmount))
	var ve *ValidationError
	fmt.Println("As ValidationError:", errors.As(err, &ve), "field:", ve.Field)

	// Storage path
	err = SavePayment(9900)
	fmt.Println(err)
	fmt.Println("Is ErrStorageFull:", errors.Is(err, ErrStorageFull))
	var se *StorageError
	fmt.Println("As StorageError:", errors.As(err, &se), "op:", se.Op)
}
```

`errors.Is` unwraps through `fmt.Errorf("%w")` → `ValidationError.Unwrap()` → `ErrInvalidAmount`. Three levels traversed with one call. `errors.As` extracts the typed error from anywhere in that chain.

</Solution>

</Exercise>

<Recap>

- **Functional options** (`Option func(*config)`) replace telescoping constructors with composable, zero-overhead configuration. Define sensible defaults in the constructor; let callers override with `With*` functions.
- **Accept interfaces, return structs**: accept the narrowest interface your function needs (defined at the consumer); return the concrete type so callers get the full API. Never return an interface unless the concrete type is truly an implementation detail.
- **Dependency injection** is just passing the dependency as a parameter — no framework needed. Inject interfaces; test with fakes. Never reach for a global.
- **Worker pools** bound parallelism: `numWorkers` goroutines share a buffered job channel. `close(jobCh)` signals completion; `wg.Go(func(){...})` (Go 1.25) launches each worker and tracks it; always close `resultCh` from a single goroutine after `wg.Wait()`.
- **Fan-out / fan-in**: distribute one stream across N parallel goroutines, then merge with `sync.WaitGroup` + a goroutine that closes the merged channel.
- **Middleware via closures** (`func(http.Handler) http.Handler`) is the decorator pattern for free: each middleware captures `next` in a closure and calls it inside the new handler. Apply with a `Chain` helper. Request flows in, response flows out.
- **GoF patterns** mostly collapse into Go idioms: Singleton → package-level var or `sync.Once`; Factory → a function; Strategy → a one-method interface or function type; Observer → a channel; Adapter → a thin wrapper struct.
- **Error wrapping** with `%w` and `Unwrap()` lets `errors.Is` (sentinel check) and `errors.As` (typed extraction) traverse the whole chain. Add context at each layer; never discard.
- All the concurrency patterns here (fan-out/fan-in, worker pools, pipelines) get the full, deep treatment in Part 2 — **Concurrency Patterns** (Part 2, Chapter 5). Look forward.

</Recap>
