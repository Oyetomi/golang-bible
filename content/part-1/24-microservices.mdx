## Monolith vs Microservices

*Stop 1 of 5.*

Meet **Meridian**: a payments backend built by you and two other engineers. One binary, one Postgres, one deploy. It handles accounts, payments and email notifications. Traffic is growing, and someone says the magic word: *microservices*. Before choosing, understand what you'd be choosing between.

### Step 1: a monolith doesn't mean a mess

A **monolith** is a single deployable unit. It can be beautifully organised, exactly like Gator: domains in separate packages with one-way dependencies, compiled into one binary.

```text
meridian/
├── cmd/server/main.go       the only place that wires everything
├── accounts/                account state and balances
├── payments/                transfers and the ledger
└── notifications/           emails and pushes
```

Calling from `payments` into `accounts` is a **function call**: no network, no serialisation, no partial failure, and the compiler checks every argument's type. Rolling back is one `git revert` and one deploy. This shape has a name, the **modular monolith**, and for most teams it's not a stepping stone but the destination.

<Define term="Monolith vs. Microservices">
A **monolith** is one deployable binary containing every domain; calls between domains are function calls. A **microservices** architecture splits domains into separate binaries that talk over a network. That hop changes the failure model, the latency and the operational work. Neither is better in general; the question is whether independence is worth the cost of distribution for *your* team *now*.
</Define>

### Step 2: what a network hop actually costs

Here is the same question, "is account `acc_1` active?", asked two ways: as a function call, and as an HTTP request to a server on the same machine. No real network, no TLS, the best case a network call will ever have:

<GoPlayground>

```go
package main

import (
	"encoding/json"
	"fmt"
	"net/http"
	"net/http/httptest"
	"time"
)

type Account struct {
	ID     string `json:"id"`
	Active bool   `json:"active"`
}

// In one process, "asking Accounts" is a function call.
//
//go:noinline
func getAccount(id string) Account { return Account{ID: id, Active: true} }

func main() {
	const n = 2000

	start := time.Now()
	for range n {
		_ = getAccount("acc_1")
	}
	inProcess := time.Since(start) / n

	// Across services it's an HTTP request, even on the same machine.
	mux := http.NewServeMux()
	mux.HandleFunc("GET /v1/accounts/{id}", func(w http.ResponseWriter, r *http.Request) {
		json.NewEncoder(w).Encode(getAccount(r.PathValue("id")))
	})
	srv := httptest.NewServer(mux)
	defer srv.Close()
	client := srv.Client()

	start = time.Now()
	for range n {
		resp, err := client.Get(srv.URL + "/v1/accounts/acc_1")
		if err != nil {
			panic(err)
		}
		var a Account
		json.NewDecoder(resp.Body).Decode(&a)
		resp.Body.Close()
	}
	overHTTP := time.Since(start) / n

	fmt.Println("function call:    ", inProcess)
	fmt.Println("HTTP on localhost:", overHTTP)
}
```

</GoPlayground>

```text

HTTP on localhost: 55.774µs
```

### Step 3: Conway's Law

In 1967 Melvin Conway submitted a paper (published in 1968) with an observation now called **Conway's Law**: organisations build systems whose structure copies their communication structure. One team builds one system; three teams that rarely talk end up with three pieces that meet at narrow, formal interfaces.

It's a description, not a recipe. **Don't split into services "for team autonomy" if you don't have autonomous teams.** Three engineers running three services pay the whole operational cost while still messaging each other about the same schema.

### Step 4: when a split is justified

A realistic story: on day one, one team and one binary is right. By month six there are three teams, and their deploys block each other. Notification fan-out spikes during settlement windows and competes with payments for CPU. A bug in notifications forces a rollback that also reverts an urgent payments fix. Now there's a case, and **notifications** is the natural first thing to extract: it's already mostly asynchronous, its interface is small, and its failure shouldn't touch payments.

Consider splitting when **at least two** of these are true, and measurably so:

**Recap.** A modular monolith gives you function calls: nanoseconds, type-checked, unable to half-fail. A split turns them into network calls that are ~10⁴× slower even on one machine and can fail in new ways. Split for measured reasons: scaling, team autonomy, isolation, compliance.

## Service Boundaries

*Stop 2 of 5.*

Suppose the pain is real. Where do you cut? This is the most consequential decision, and the most rushed. A bad cut produces a **distributed monolith**: the worst of both worlds.

### Step 1: bounded contexts

<Define term="Bounded Context" since="Software Design & Architecture (ch14)">
A **bounded context** is a part of the system inside which one model of the domain is consistent and authoritative, with its own vocabulary. Outside it, the same word can mean something else. The idea comes from Eric Evans's *Domain-Driven Design* (2003); you don't need the whole book to use the lens.
</Define>

For Meridian, the contexts are:

- **Accounts**: identities, account status, KYC. An "account" here is a customer's financial account.
- **Payments/Ledger**: transfers and double-entry journal entries (Part 3 goes deep on ledgers).
- **Notifications**: emails, pushes, SMS. It needs to know *that* a payment happened, not how the ledger recorded it.

Each context owns its own model. Payments' `Transfer` and Notifications' "payment happened" event are different types with different fields, and that's correct: they answer different questions.

The test for a good boundary: **can each side be deployed without coordinating with the other?** If a change in one always forces a change in the other, the boundary is in the wrong place.

### Step 2: the distributed monolith

<Define term="The Distributed Monolith (anti-pattern)">
Separate deployables that are still tightly coupled: they share a database, call each other synchronously for everything, or must be deployed together. You get all the operational cost of microservices and none of the independence. The tell: you can't deploy A without coordinating with B.
</Define>

<ConceptGrid cols={2}>
  <ConceptCard label="Shared database">Two services read and write the same tables. A schema change in one breaks the other, at runtime.</ConceptCard>
  <ConceptCard label="Synchronous chains">A calls B calls C calls D, waiting each time. A is now as slow as the sum and as available as the product (the PredictLab above).</ConceptCard>
  <ConceptCard label="Chatty interfaces">One business operation needs ten sequential calls across services. The domain wasn't decomposed; a function was shredded across a network.</ConceptCard>
  <Gotcha>A shared database between services is a monolith in a trenchcoat. Each service owns its data; others ask through its API.</Gotcha>
</ConceptGrid>

When Payments needs to know whether an account is active, it calls Accounts' API. When Payments posts a transfer, it publishes a `TransferPosted` event that Notifications consumes. Nobody reaches into anyone else's schema.

**Recap.** Cut along bounded contexts; test a boundary by asking whether each side deploys alone. Each service owns its database, and others use its API or its events. You give up cross-service transactions in exchange.

## Talking Between Services

*Stop 3 of 5.*

### Step 1: wait for an answer, or don't

<Define term="Synchronous vs. asynchronous" since="Messaging & Pub/Sub Foundations (Part 3)">
**Synchronous** (HTTP, gRPC): the caller waits for the callee's answer. Simple, but the caller is now only as fast and as available as the callee. **Asynchronous** (a queue or event stream such as Kafka or NATS): the caller publishes a message and moves on; the callee handles it later. The caller keeps working when the callee is down, but can't know the outcome immediately.
</Define>

The rule of thumb: synchronous when you **need the answer to continue** (is this account active?), asynchronous for work that **can happen after you reply** (send the receipt email, update analytics).

### Step 2: a proper HTTP client

For most synchronous calls, plain HTTP and JSON with `net/http` is the right start: debuggable with `curl`, no new dependencies. Here is the client Payments uses to ask Accounts about an account. Everything in it is ch16, applied:

<GoPlayground>

```go
package main

import (
	"context"
	"encoding/json"
	"fmt"
	"net/http"
	"net/http/httptest"
	"net/url"
	"time"
)

type AccountInfo struct {
	ID     string `json:"id"`
	Active bool   `json:"active"`
}

// AccountsClient is Payments' view of the Accounts service.
type AccountsClient struct {
	base string
	http *http.Client
}

func NewAccountsClient(baseURL string) *AccountsClient {
	return &AccountsClient{
		base: baseURL,
		http: &http.Client{Timeout: 2 * time.Second}, // never DefaultClient: it has no timeout
	}
}

func (c *AccountsClient) GetAccount(ctx context.Context, id string) (*AccountInfo, error) {
	// ctx carries the caller's deadline and cancellation into the request.
	req, err := http.NewRequestWithContext(ctx, http.MethodGet, c.base+"/v1/accounts/"+url.PathEscape(id), nil)
	if err != nil {
		return nil, fmt.Errorf("accounts: build request: %w", err)
	}
	resp, err := c.http.Do(req)
	if err != nil {
		return nil, fmt.Errorf("accounts: get account: %w", err)
	}
	defer resp.Body.Close()
	if resp.StatusCode != http.StatusOK { // a 503 page is not an account
		return nil, fmt.Errorf("accounts: status %d", resp.StatusCode)
	}
	var info AccountInfo
	if err := json.NewDecoder(resp.Body).Decode(&info); err != nil {
		return nil, fmt.Errorf("accounts: decode: %w", err)
	}
	return &info, nil
}

func main() {
	// A fake Accounts service, in-process.
	mux := http.NewServeMux()
	mux.HandleFunc("GET /v1/accounts/{id}", func(w http.ResponseWriter, r *http.Request) {
		if r.PathValue("id") != "acc_123" {
			http.Error(w, "no such account", http.StatusNotFound)
			return
		}
		json.NewEncoder(w).Encode(AccountInfo{ID: "acc_123", Active: true})
	})
	srv := httptest.NewServer(mux)
	defer srv.Close()

	client := NewAccountsClient(srv.URL)
	for _, id := range []string{"acc_123", "acc_999"} {
		info, err := client.GetAccount(context.Background(), id)
		fmt.Printf("%s -> %+v, err=%v\n", id, info, err)
	}
}
```

</GoPlayground>

```text
acc_123 -> &{ID:acc_123 Active:true}, err=<nil>
acc_999 -> <nil>, err=accounts: status 404
```

Three details carry the weight. The `http.Client` has a `Timeout`. The context goes into the request with `NewRequestWithContext`, so if Payments' own caller gives up, this call is cancelled too. And a non-200 status is an error: without that check, a 503 error page decodes into a zero `AccountInfo` and "Accounts is down" silently becomes "account inactive". (That exact bug is in this chapter's lab.)

When you want the contract checked by a compiler rather than by convention (typed schemas, generated clients, streaming), the answer is **gRPC**: Part 2, Chapter 18.

### Step 3: finding the other service

In development, Accounts is at `localhost:8081`. In production it's several replicas whose IP addresses change on every deploy and restart, so nothing can hard-code them.

<Define term="Service Discovery" since="Deployment & Infra: CI/CD + Kubernetes (ch27)">
How a service finds another's address at runtime. **DNS-based:** each service has a stable name (in Kubernetes, `accounts.meridian.svc.cluster.local`) that resolves to a load balancer or to the healthy replicas. **Registry-based:** instances register with a registry such as Consul or etcd, and clients ask it for live instances.
</Define>

A **load balancer** in front of the replicas spreads requests, drops replicas that fail health checks, and often terminates TLS. So Payments is configured with one stable base URL (from configuration, not code: Part 2, Chapter 16) and never learns an individual replica's address. One user request can still cross several of these hops:

A Go `context` deadline is not sent over plain HTTP. ### Step 2: know which failure you got

"The call failed" isn't enough to act on. A timeout suggests the callee is overloaded, so don't hammer it with retries. A refused connection means nothing is listening. A 404 is an answer, not a failure. `errors.AsType` (Go 1.26) finds the `*url.Error` inside the chain without a separate target variable:

<GoPlayground>

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"net/http"
	"net/http/httptest"
	"net/url"
	"time"
)

func classify(err error) string {
	if ue, ok := errors.AsType[*url.Error](err); ok && ue.Timeout() {
		return "timeout: callee is slow; answer 503, don't retry immediately"
	}
	if err != nil {
		return "transport error: " + err.Error()
	}
	return "ok"
}

func main() {
	slow := httptest.NewServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		select {
		case <-time.After(2 * time.Second):
		case <-r.Context().Done():
		}
	}))
	defer slow.Close()

	client := &http.Client{Timeout: 100 * time.Millisecond}
	_, err := client.Get(slow.URL)
	fmt.Println("Client.Timeout:  ", classify(err))

	ctx, cancel := context.WithTimeout(context.Background(), 100*time.Millisecond)
	defer cancel()
	req, _ := http.NewRequestWithContext(ctx, "GET", slow.URL, nil)
	_, err = http.DefaultClient.Do(req)
	fmt.Println("context deadline:", classify(err), "| DeadlineExceeded:", errors.Is(err, context.DeadlineExceeded))

	_, err = client.Get("http://127.0.0.1:1") // nothing listens on port 1
	fmt.Println("refused:         ", classify(err))
}
```

</GoPlayground>

```text
refused:          transport error: Get "http://127.0.0.1:1": dial tcp 127.0.0.1:1: connect: connection refused
```

Both kinds of limit, `Client.Timeout` and a context deadline, report `Timeout() == true`. Use `Client.Timeout` as a ceiling for every call to a dependency, and a context deadline for "this whole user request has 2 seconds, however many calls it makes". The shorter one wins.

### Step 3: the third outcome, and the double charge

```go
	"crypto/rand"
	"fmt"
	"net/http"
	"net/http/httptest"
	"sync"
	"time"
)

// The ledger charges, then is slow to answer: the charge happens, but the
// caller's timeout fires before the response arrives.
type ledger struct {
	mu      sync.Mutex
	charges int
	seen    map[string]bool // idempotency keys already applied
}

func (l *ledger) ServeHTTP(w http.ResponseWriter, r *http.Request) {
	key := r.Header.Get("Idempotency-Key")
	l.mu.Lock()
	if key == "" || !l.seen[key] { // claim the key and charge, together (ch20)
		l.seen[key] = key != ""
		l.charges++
	}
	l.mu.Unlock()
	time.Sleep(150 * time.Millisecond) // the response is late
	w.WriteHeader(http.StatusCreated)
}

// pay retries up to 3 times on error, like any reasonable client.
func pay(url string, client *http.Client, key string) {
	for range 3 {
		req, _ := http.NewRequest("POST", url+"/charges", nil)
		if key != "" {
			req.Header.Set("Idempotency-Key", key) // the SAME key on every retry
		}
		resp, err := client.Do(req)
		if err == nil {
			resp.Body.Close()
			return
		}
		time.Sleep(20 * time.Millisecond)
	}
}

func main() {
	client := &http.Client{Timeout: 100 * time.Millisecond}

	for _, useKey := range []bool{false, true} {
		l := &ledger{seen: map[string]bool{}}
		srv := httptest.NewServer(l)
		key := ""
		if useKey {
			key = rand.Text() // one key per logical payment, made once
		}
		pay(srv.URL, client, key)
		srv.Close()
		fmt.Printf("idempotency key: %-5v -> customer charged %d time(s)\n", useKey, l.charges)
	}
}
```

The key is created **once per logical operation**, before the first try, and reused on every retry. A new key per retry protects nothing. ch20 built the server side properly (claim the key atomically, store the response); Part 3, Chapter 4 takes it to exactly-once processing.

### Step 4: the containment checklist

1. **Every outbound call has a timeout.** A `Client.Timeout` per dependency, plus the request's context.
2. **Answer fast when a dependency fails.** A quick 503 lets the caller (or the user) retry later; a hung request just spreads the problem.
3. **Retry only what's safe,** with exponential backoff and jitter, and never retry a timeout from an overloaded service in a tight loop. Writes carry an idempotency key.
4. **Move non-critical work off the request path.** The receipt email goes on a queue; it doesn't block the transfer's response.
5. **Circuit breakers** stop calling a dependency that keeps failing, for a while, and fail immediately instead (Part 2, Chapter 12).
6. **Decide fail-open vs fail-closed per call.** Can't load the customer's display name? Show "there". Can't check the account is active? Refuse the transfer.

## The Operational Cost

*Stop 5 of 5.*

### Step 1: following one request through many services

In a monolith, a slow request shows up in one process's profile and logs. Across services, one click touches five processes, each with its own logs and clock. To see the whole request you need **distributed tracing**.

The standard is **OpenTelemetry**. Each service records **spans** (a named piece of work with a start, an end and attributes), and every span carries the request's **trace ID**, passed between services in the W3C `traceparent` header. A backend such as Jaeger or Grafana Tempo stitches the spans into one timeline. The mechanism underneath is small enough to write by hand:

<GoPlayground>

```go
package main

import (
	"crypto/rand"
	"encoding/hex"
	"fmt"
	"net/http"
	"net/http/httptest"
	"strings"
)

func randHex(n int) string {
	b := make([]byte, n)
	rand.Read(b)
	return hex.EncodeToString(b)
}

// W3C Trace Context: traceparent = version-traceid-parentid-flags.
// The trace id stays the same across every service; each hop gets a new span id.
func childOf(traceparent string) string {
	parts := strings.Split(traceparent, "-")
	if len(parts) != 4 || len(parts[1]) != 32 {
		return "00-" + randHex(16) + "-" + randHex(8) + "-01" // no valid parent: start a trace
	}
	return "00-" + parts[1] + "-" + randHex(8) + "-" + parts[3]
}

// service logs with the trace id and hands the traceparent on.
func service(name string, next func(tp string)) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		tp := childOf(r.Header.Get("traceparent"))
		fmt.Printf("%-9s trace=%s span=%s\n", name, tp[3:35], tp[36:52])
		if next != nil {
			next(tp)
		}
	})
}

func call(url, tp string) {
	req, _ := http.NewRequest("GET", url, nil)
	req.Header.Set("traceparent", tp) // forget this line and the trace breaks here
	resp, err := http.DefaultClient.Do(req)
	if err == nil {
		resp.Body.Close()
	}
}

func main() {
	accounts := httptest.NewServer(service("accounts", nil))
	defer accounts.Close()
	payments := httptest.NewServer(service("payments", func(tp string) { call(accounts.URL, tp) }))
	defer payments.Close()
	gateway := httptest.NewServer(service("gateway", func(tp string) { call(payments.URL, tp) }))
	defer gateway.Close()

	call(gateway.URL, "") // a request arrives with no trace yet
}
```

### Step 2: data that's briefly out of date

With one database, a read after a write sees the write. When services share data through events, Notifications may not have processed `TransferPosted` yet when the user refreshes. That's **eventual consistency**: the services converge, just not instantly.

- Model states explicitly (`pending` → `settled` or `failed`) instead of pretending everything is instant.
- Put what consumers need **in the event** (the payee's name and email in `TransferPosted`) so they don't call back to a service that may have moved on.
- Run **reconciliation** jobs that compare services' views and flag drift. They're a safety net, not an admission of defeat.

### Step 3: two versions at once

With N services there's no single "the version". During a rolling deploy, old and new replicas of one service run side by side, talking to fixed versions of everything else. So:

- **API changes are backward compatible** until every caller has moved: add fields freely, never remove or rename one that someone still reads.
- **Expand, migrate, contract**: the same pattern as ch18's schema migrations, applied to APIs. Add the new field, move callers over, then remove the old one.
- **Versioned paths** (`/v1/`, `/v2/`) give a clean migration route, at the cost of running both until `/v1` is retired.

### Step 4: the honest summary

<ConceptGrid cols={2}>
  <ConceptCard label="What services give you">Independent deploys, independent scaling, fault isolation between processes, team autonomy, freedom to choose tools per domain.</ConceptCard>
  <ConceptCard label="What they cost you">Network latency and partial failure on every call, tracing, eventual consistency, versioning discipline, and a platform (containers, orchestration, observability) to run it all.</ConceptCard>
  <ConceptCard label="The break-even point">Several autonomous teams, a product that has found its market, and measured scaling or isolation needs. Before that, the costs arrive and the benefits don't.</ConceptCard>

</ConceptGrid>

**Recap.** Propagate a trace ID through every call from the first split. Accept and design for eventual consistency: explicit states, fat events, reconciliation. Keep APIs backward compatible across rolling deploys, and split only when the benefits are measured.

```go
		{"503", func(w http.ResponseWriter, r *http.Request) { http.Error(w, "busy", http.StatusServiceUnavailable) }, true},
		{"slow", func(w http.ResponseWriter, r *http.Request) {
			select {
			case <-time.After(2 * time.Second):
			case <-r.Context().Done(): // stop when the client gives up
			}
		}, true},
	}
	for _, tc := range cases {
		srv := httptest.NewServer(tc.handler)
		active, err := FetchAccountStatus(context.Background(), client, srv.URL, "acc_1")
		srv.Close()
		ok := (err != nil) == tc.wantErr && (tc.wantErr || active)
		fmt.Printf("%-8s ok=%v (active=%v err=%v)\n", tc.name, ok, active, err)
	}
}
```

`httptest.NewServer` runs a real HTTP server on a loopback port inside your process. `Close` waits for in-flight handlers to finish, which is why the slow handler watches `r.Context()`: without that, the program would wait the full 2 seconds at `srv.Close()`. In a real project this table goes in a `_test.go` file with `t.Run` per case (ch9).

</Solution>

</Exercise>

<Exercise n={3} title="Fail open for a nice-to-have" level="medium">

The transfer receipt shows the payee's display name, fetched from Accounts. If that lookup fails for any reason, the receipt should still go out, addressed "Hi there". Write `DisplayName(ctx, c, baseURL, id string) string` that returns the name, or `"there"` on any failure, logging the reason with `slog`. Then explain why the same fallback would be wrong for "is the source account active?".

<Solution>

```go
package main

import (
	"context"
	"encoding/json"
	"fmt"
	"log/slog"
	"net/http"
	"net/http/httptest"
	"time"
)

const fallbackName = "there"

func DisplayName(ctx context.Context, c *http.Client, baseURL, id string) string {
	req, err := http.NewRequestWithContext(ctx, http.MethodGet, baseURL+"/v1/accounts/"+id, nil)
	if err != nil {
		slog.Warn("display name: build request", "err", err)
		return fallbackName
	}
	resp, err := c.Do(req)
	if err != nil {
		slog.Warn("display name: using fallback", "account", id, "err", err)
		return fallbackName
	}
	defer resp.Body.Close()
	var body struct {
		Name string `json:"name"`
	}
	if resp.StatusCode != http.StatusOK || json.NewDecoder(resp.Body).Decode(&body) != nil || body.Name == "" {
		slog.Warn("display name: using fallback", "account", id, "status", resp.StatusCode)
		return fallbackName
	}
	return body.Name
}

func main() {
	slow := httptest.NewServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		select {
		case <-time.After(2 * time.Second):
			fmt.Fprint(w, `{"name":"Ada"}`)
		case <-r.Context().Done():
		}
	}))
	defer slow.Close()

	client := &http.Client{Timeout: 300 * time.Millisecond}
	fmt.Printf("Hi %s, your transfer was sent.\n", DisplayName(context.Background(), client, slow.URL, "acc_1"))
}
```

Falling back is right when a wrong or missing answer is harmless: a generic greeting costs nothing. "Is the account active?" is a guard on moving money. Falling back to `true` there (fail open) would let transfers from frozen accounts through whenever Accounts is slow, which is exactly when attackers like to try. That check must fail closed: refuse with a 503 and let the client retry.

</Solution>

</Exercise>

<Exercise n={4} title="Spot the distributed monolith" level="medium">

Two designs for Meridian's transfers. Which is the distributed monolith, and why?

**Design A:** Payments holds a `*sql.DB` for `accounts_db` as well as its own `payments_db`. Posting a transfer, it updates the balance in `accounts_db` and inserts a journal entry in `payments_db`, and describes this as "one transaction".

**Design B:** Payments calls `POST /v1/accounts/{id}/holds` on Accounts with an idempotency key, then writes the journal entry in `payments_db`. If the second step fails, it releases the hold; a reconciliation job catches anything left over.

<Solution>

**Design A is the distributed monolith.**

- `accounts_db` now has two writers. Any schema change by the Accounts team can break Payments at runtime, with no compiler or contract to warn anyone.
- Accounts can't be deployed, migrated or scaled on its own.
- It isn't one transaction. Two `*sql.DB` handles to two databases mean two independent transactions: if the process dies between the commits, the balance moved and no journal entry exists. Making it atomic would need two-phase commit (in Postgres, `PREPARE TRANSACTION`), which is slow, operationally painful, and still couples the two.

**Design B** accepts the real cost of separation: no cross-service transaction, so it needs an idempotency key for safe retries, a compensating step (release the hold), and reconciliation. In return each service owns its data and deploys alone. This is a small **saga** (Part 3, Chapter 3).

</Solution>

</Exercise>

<Exercise n={5} title="Review two proposals" level="hard">

The team proposes two things after splitting Meridian into accounts, payments and notifications services:

1. A new `fraud-service` that reads recent transactions from `payments_db` and KYC status from `accounts_db` directly, "for performance".
2. A job in `notifications-service` that copies the whole accounts table every 5 minutes, so emails can include names.

Identify the problem with each and propose a design that respects ownership.

<Solution>

**1. `fraud-service` reading two databases.** It owns nothing and depends on two other teams' schemas: a distributed monolith with a third member. Instead, call `GET /accounts/{id}/kyc` and `GET /payments/accounts/{id}/recent` through their APIs, **concurrently** (an `errgroup` with a context, ch4 and ch7), so the latency is the slower of the two rather than the sum. If that's still too slow, cache in `fraud-service` (ch22) or have Payments and Accounts publish events that `fraud-service` uses to maintain its own read model: data it owns, shaped for its own queries.

**2. Copying the accounts table.** A full-table copy every 5 minutes is stale by up to 5 minutes, costs a full scan every time, silently drifts if the job fails, and couples Notifications to Accounts' schema anyway. Better: put what the email needs (payee name and address) **in the `TransferPosted` event**, captured at the moment of the transfer. If an event can't carry it, call `GET /accounts/{id}/contact` when sending: one targeted request instead of a copy of everything.

</Solution>

</Exercise>

<Recap>

- A **modular monolith** gives you function calls: nanoseconds, type-checked, unable to half-fail. Start there; split for measured reasons.
- A network call is ~10⁴× slower even on one machine, and can time out, be refused, return garbage, or succeed silently.
- Cut along **bounded contexts**. Each service owns its database; others use its API or events. A shared database is a **distributed monolith**.
- **Synchronous** when you need the answer to continue; **asynchronous** for work that can follow the reply. Chains add latency and multiply unavailability.
- An inter-service client has a **timeout**, passes the **context**, and treats non-200 as an error.
- Without a timeout, a slow callee's latency becomes the caller's pile-up (900 goroutines vs 6). With one, cancellation reaches the callee too.
- **Partial failure** plus retries charges customers twice unless writes carry an **idempotency key** made once per operation.
- The operational tax: **tracing** (`traceparent` everywhere), **eventual consistency**, **backward-compatible APIs** during rolling deploys.

</Recap>
