## Goroutines

*Stop 1 of 6.*

Here's the scene: a customer hits "Buy Now." Your checkout service needs prices from twelve vendor APIs — sequentially, that's 12 × 80ms = 960ms. Your SLA is 200ms. Sequential is a death sentence. You need concurrency.

Go's answer is the **goroutine**: a function call that runs *alongside* the rest of your program instead of making the caller wait for it. You start one by writing `go` in front of a call, and the Go runtime decides when and where it actually runs.

<Define term="Goroutine" since="The Go Scheduler (GMP), In Depth (Part 2)">
A **goroutine** is a function running independently of the code that started it. You start one with `go f()`: the call to `f` begins, and the line after `go` runs *immediately*, without waiting for `f` to finish. Goroutines are managed by the Go runtime, not the operating system, and each starts with a tiny stack (about 2 KB, growing as needed), so a program can run hundreds of thousands of them. **Production hazard:** "cheap" isn't "free". Starting one goroutine per incoming item with no limit can still exhaust memory or hammer a database. Stop 5 shows how to cap them.
</Define>

Two things to take from this before moving on:

1. **`go` gives you nothing back.** You don't get a return value or a handle to wait on. `fetchPrice` can't even *return* its price to anyone, which is why this version only prints. Getting results back is exactly what channels (Stop 2) are for.
2. **Order isn't guaranteed.** In the fixed version the prices can print in any order (globex before acme is completely normal). Concurrent goroutines run in whatever order the scheduler picks, and it can differ on every run.

Don't "fix" this by adding `time.Sleep` at the end of `main`. It works on your laptop and fails in production the day a vendor takes longer than your guess. Waiting has to be *for the work*, not for a guessed amount of time.

### Step 2: What `go` gives you, and what it doesn't

The only syntax is `go` in front of a function call:

```go
go fetchPrice("acme")   // run fetchPrice in a new goroutine; don't wait
go func() { /* … */ }() // same, with an anonymous function
```

Three facts to hold on to:

1. **The caller continues immediately.** `go` never waits.
2. **You get nothing back.** No return value, no handle to wait on. To get a result, use a channel (Stop 2). To know it finished, use a `sync.WaitGroup` (Stop 4).
3. **The arguments are evaluated now, by the caller.** `go fetchPrice(vendor)` reads `vendor` at the moment of the `go` statement, not later when the goroutine starts running.

- **Concurrency** is about *structure*: splitting work into independent pieces that can be in progress at the same time. You can have it on one CPU.
- **Parallelism** is about *execution*: pieces running at the exact same instant on different CPUs.

For **waiting** work like Stop 1's vendor calls, concurrency alone is enough. A goroutine that's waiting on the network isn't using a CPU, so even one CPU can overlap a thousand waits. Parallelism only speeds up **CPU-heavy** work, and only up to the number of CPUs.

### Step 4: Why goroutines are cheap

Why not just start an operating-system thread per task? Because goroutines cost far less:

| | OS thread | Goroutine |
|---|---|---|
| Starting stack | fixed, typically 1–8 MB reserved | about 2 KB, grows and shrinks as needed |
| Switching between them | done by the OS kernel, on the order of microseconds | done by the Go runtime in user space, on the order of 100–200 ns |
| How many is realistic | thousands | hundreds of thousands to millions |
| While waiting on the network | the thread sits blocked | the goroutine parks and its thread runs other goroutines |

<Gotcha>Network waits park cheaply, but a goroutine stuck in a *blocking system call* (reading a regular file, a cgo call into C) holds on to its OS thread the whole time, and the runtime starts another thread so the rest keep running. A thousand goroutines doing slow file reads at once can mean hundreds of OS threads.</Gotcha>

<UnderTheHood title="The GMP Scheduler — physical machine reality and why M:N">

Every goroutine runs on a thread managed by Go's **GMP scheduler**. Three letters, three physical machine concepts:

- **G** — a Goroutine. The unit of concurrent work. Begins with a tiny 2 KB dynamically growable stack that expands and shrinks contiguously in memory. Carries its program counter (`PC`), stack bounds, and local variables.
- **M** — a Machine (OS thread). A kernel-level thread created via `clone()` on Linux or `pthread_create()` on macOS. There are usually `GOMAXPROCS` active Ms executing Go code.
- **P** — a Processor (logical processor). Think of it as a *permit to run Go code*, plus a queue of goroutines waiting for that permit. There are exactly `GOMAXPROCS` Ps. An M must hold a P to run Go code. (Go compiles to native machine code, so there's no bytecode or interpreter involved. The P is purely a scheduling token.)

### 1. Physical Machine Reality: Kernel Thread vs Goroutine Context Switch
Why can Go run 1,000,000 goroutines while an OS crashes with 10,000 threads?
- **OS thread switch (on the order of a microsecond):** switching threads means entering the kernel, saving the full register set (including floating-point/vector registers), running the kernel's scheduler, and restoring another thread. Threads of the *same* process share an address space, so the page tables stay put, but the trip into the kernel and the cache disruption still cost far more than a function call.
- **Goroutine switch (on the order of 100–200 ns):** no kernel involved. The runtime saves a handful of values (stack pointer, program counter, and a few others) into the goroutine's `g.sched` field, picks the next goroutine, and jumps to it. Because goroutine switches happen at well-defined points (a channel op, a function call, a preemption check), the compiler already knows most registers don't need saving.

The exact numbers depend on the CPU and OS. The *ratio* is what matters: roughly an order of magnitude, plus a far smaller memory footprint per goroutine. That's why a million goroutines is realistic and a million threads isn't.

### 2. The Deep "Why": Why M:N Dynamic Stacks over Async/Await
Languages like JavaScript, Python, and Rust use `async/await` state machines. Why did Go reject `async/await`?
- **Eliminating the "Function Coloring Problem":** In `async/await` languages, async functions return promises/futures and **cannot be called directly from synchronous functions**. The entire codebase gets split into two incompatible worlds ("colored" functions).
- **In Go, all functions are written identically as straightforward synchronous code.** When a goroutine calls a network socket or channel, the Go runtime intercepts the call, parks the goroutine via the netpoller (`epoll`/`kqueue`), and hands the OS thread to another goroutine — without changing function signatures or infecting the call hierarchy.

The scheduler maintains:
1. **Local run queues** (one per P, 256 slots): lock-free ring buffers for goroutines ready to run on this P.
2. **Global run queue**: overflow queue protected by a mutex for work arriving from external events.
3. **Work stealing**: when a P's local queue is empty, it checks the global queue and the network poller, then steals half the goroutines from another P's local queue. This keeps idle cores from sitting around while other cores have a backlog.

</UnderTheHood>

## Channels

*Stop 2 of 6.* Stop 1 ended with a problem: `go` gives you nothing back, and `main` has no way to wait. Channels solve both at once.

### Step 1: A pipe between goroutines

<Define term="Channel" since="Concurrency Patterns (Part 2)">
A **channel** is a typed pipe that one goroutine sends values into and another receives them from. `make(chan int)` creates one that carries `int`s. `ch <- v` sends `v` into it, and `v := <-ch` receives from it. The arrow always points the way the data moves. Channels are safe to use from many goroutines at once, so you never need a lock around them.
</Define>

That's the whole API: make, send, receive. The part that takes a moment to absorb is **when things wait**, so we'll look at only that before anything else.

<Define term="blocking / parked">
An operation **blocks** when the goroutine can't continue until something else happens, such as a send waiting for a receiver. The runtime then **parks** the goroutine: it takes the goroutine off the CPU and sets it aside, costing almost nothing, until the thing it's waiting for happens. A parked goroutine isn't spinning or burning CPU. It's asleep.
</Define>

The Go proverb: **"Don't communicate by sharing memory; share memory by communicating."** Instead of two goroutines both touching one variable (Stop 4 shows why that goes wrong), one goroutine *sends* the value to the other. Whoever holds the value owns it.

### Step 2: An unbuffered channel is a handshake

`make(chan int)`, with no size, makes an **unbuffered** channel. It has no storage at all. A value can't sit *in* it. It can only pass *through* at the instant a sender and a receiver are both there. So whichever side arrives first has to wait for the other:

```go
package main

import (
	"fmt"
	"time"
)

type quote struct {
	vendor string
	cents  int
}

// fetchPrice simulates a 50ms vendor API call, then SENDS its answer.
func fetchPrice(vendor string, out chan<- quote) {
	time.Sleep(50 * time.Millisecond)
	out <- quote{vendor, 999}
}

func main() {
	vendors := []string{"acme", "globex", "initech"}
	quotes := make(chan quote) // one channel shared by every vendor goroutine

	start := time.Now()
	for _, v := range vendors {
		go fetchPrice(v, quotes) // all three start now; nobody waits
	}

	// Receive exactly one quote per vendor. Each receive waits for a sender.
	for range vendors {
		q := <-quotes
		fmt.Printf("%s: %d cents\n", q.vendor, q.cents)
	}
	fmt.Printf("concurrent: %v\n", time.Since(start).Round(10*time.Millisecond))
}
```

#### Watch the runtime run it

Diagrams of "goroutines" usually show boxes on a line. Real goroutines *move*: into queues, onto CPUs, into a channel's waiting room, into the timer heap, and back. This stage runs the program above on a machine with **two CPUs** (`GOMAXPROCS=2`), and every move is what Go's scheduler actually does. Press Play, then drag the timeline back and forth. Watch several gophers at once, because several things *are* happening at once.

<Define term="P, run queue, parked">
A **P** ("processor") is a permit to run Go code. There are `GOMAXPROCS` of them, so at most that many goroutines run *simultaneously*. Each P has a **run queue**: goroutines that are ready and waiting for a turn on a CPU. A **parked** goroutine is in no run queue at all. It's waiting for something (a channel partner, a timer), and it costs no CPU until that thing happens and puts it back in a run queue.
</Define>

Four things to take from the stage, because they explain everything else in this chapter:

1. **`go` only queues work.** The new goroutine waits in a run queue until a CPU is free.
2. **Blocking means parking.** A goroutine blocked on a channel or a timer isn't spinning. It sits in that channel's or timer's queue and costs no CPU.
3. **Waking means going back to a run queue**, not straight onto a CPU. "Runnable" and "running" are different states.
4. **An unbuffered send meets its receiver in one of two ways.** Either the receiver is already parked (instant handoff), or the sender parks until a receiver comes (G3 in `sendq`).

<Callout kind="warn" title="Collect exactly as many as you sent">
Receive one fewer time than you sent and a vendor goroutine stays parked on its send forever. That's a **goroutine leak** (more on this below). Receive one MORE time than you sent and `main` parks forever waiting for a quote that will never come. If every goroutine is stuck like that, Go stops the program with `fatal error: all goroutines are asleep - deadlock!`.
</Callout>

### Step 4: Buffered channels

```go
ch1 := make(chan int)    // unbuffered: capacity 0. send blocks until someone receives.
ch2 := make(chan int, 3) // buffered: capacity 3. send only blocks when the buffer is full.
```

A **buffered channel** decouples sender and receiver. The sender can drop up to `cap(ch)` values and keep going — no waiting — as long as the buffer isn't full. The receiver can drain those values even if the sender is long gone.

### Step 5: Channel direction

A function can promise to use only one side of a channel. The compiler then rejects a send where only receiving was promised, and vice versa.

**How to read the types:** follow the arrow relative to the word `chan`.

- `chan<- int`: the arrow points **into** `chan`, so this is **send-only**. You can put ints in.
- `<-chan int`: the arrow comes **out of** `chan`, so this is **receive-only**. You can take ints out.
- `chan int`: no arrow, so both.

```go
// send-only: caller passes in a chan<- int, this func can only send
func producePrice(vendor string, out chan<- int) {
	out <- fetchVendorPrice(vendor)
}

// receive-only: caller passes in a <-chan int, this func can only receive
func consumePrices(in <-chan int) {
	for price := range in {
		fmt.Println(price)
	}
}
```

You create a normal `chan int` and pass it to both functions. Go converts it to the narrower type automatically at each call, so each function only gets the half it needs. (It doesn't work the other way: a `<-chan int` can't be turned back into a `chan int`.)

### Step 6: Closing a channel and ranging over it

When a sender is *done* sending, it closes the channel. Receivers can detect this:

```go
ch := make(chan int, 5)
ch <- 100
ch <- 200
close(ch) // no more sends allowed; already-buffered values remain readable

v, ok := <-ch // ok=true means a real value; ok=false means closed and empty
```

The idiomatic pattern is `range` over a channel — it loops until the channel is closed and empty:

<GoPlayground>

```go
package main

import "fmt"

// generatePrices returns a receive-only channel and fills it from its own goroutine.
func generatePrices(vendors []string) <-chan string {
	out := make(chan string, len(vendors)) // room for every value
	go func() {
		for _, v := range vendors {
			out <- v + ": 999 cents" // pretend we fetched it
		}
		close(out) // signal: no more prices are coming
	}()
	return out
}

func main() {
	for price := range generatePrices([]string{"acme", "globex", "initech"}) {
		fmt.Println(price)
	}
	fmt.Println("channel closed, loop done")
}
```

Two operations panic: **closing a channel twice** (`panic: close of closed channel`), and **sending on a closed channel** (`panic: send on closed channel`). With several senders, nobody closes until all of them are done, which is exactly the `wg.Wait(); close(results)` pattern in Stop 4.

### Step 7: Nil channels

A `nil` channel (a `chan int` that was never initialized with `make`) blocks forever on both send and receive. This sounds useless, but it's a deliberate tool in `select` (next section) — you can disable a case by setting its channel to `nil`.

<Define term="Deadlock" since="Advanced Concurrency &amp; Correctness (Part 2)">
A **deadlock** is an unrecoverable state where two or more goroutines are mutually blocked waiting for each other to release a lock, send a channel message, or perform a state transition. **Why it matters:** the Go runtime detects global program deadlocks (where *every* goroutine in the process is parked) and terminates with `fatal error: all goroutines are asleep - deadlock!`. **Production hazard:** partial deadlocks (e.g. 5 worker goroutines deadlocked while HTTP handlers continue receiving requests) are **not** caught by the runtime deadlock detector — they silently freeze individual request lifecycles until worker pools starve and connections exhaust.
</Define>

```go
var ch chan int // nil channel
// ch <- 1       // would block forever (goroutine leak if nobody else is running)
// <-ch          // would block forever
```

<UnderTheHood title="The hchan struct — what a channel really is">

When you call `make(chan int, 5)`, the runtime allocates an `hchan` struct on the heap. The key fields (simplified from `runtime/chan.go`):

```
hchan {
    qcount   uint           // number of elements currently in the buffer
    dataqsiz uint           // buffer capacity (0 for unbuffered)
    buf      unsafe.Pointer // circular buffer (nil for unbuffered)
    elemsize uint16         // size of one element (8 bytes for int64)
    closed   uint32         // 1 when closed, 0 otherwise
    sendq    waitq          // queue of goroutines blocked on send
    recvq    waitq          // queue of goroutines blocked on receive
    lock     mutex          // protects all fields above
}
```

When a goroutine sends on a full channel (or an unbuffered channel with no receiver ready), the runtime:
1. Locks the `hchan`.
2. Creates a `sudog` (a goroutine/value pair) and enqueues it on `sendq`.
3. Parks the goroutine (marks it not-runnable, removes it from the P's run queue).
4. Unlocks the `hchan` and calls the scheduler.

When a receiver arrives and dequeues that `sudog`, the scheduler marks the sender goroutine as runnable again. **The scheduler is the channel's blocking mechanism** — no OS mutex, no kernel involvement for the blocking itself. This is why channel operations are cheap even when they block: the runtime's user-space scheduler handles it, not the OS.

The `lock` field protects the struct from concurrent access — `hchan` is safe to use from multiple goroutines because all mutations go through that internal mutex. That's the synchronization guarantee you get for free.

</UnderTheHood>

<Define term="Goroutine leak" since="Advanced Concurrency &amp; Correctness (Part 2)">
A **goroutine leak** occurs when a goroutine is launched but becomes permanently parked waiting on an unbuffered channel, mutex, or network socket that will never resolve. **Why it matters:** unlike unreachable heap objects, the garbage collector **cannot** collect a parked goroutine; it retains its stack memory, local variables, and all heap objects reachable from its stack. **Production hazard:** accumulated leaked goroutines steadily consume gigabytes of RAM, triggering Out-Of-Memory container evictions. Inspect via `/debug/pprof/goroutine` or the Go 1.26 `/debug/pprof/goroutineleak` endpoint.
</Define>

<ConceptGrid cols={2}>
  <ConceptCard label="Goroutine leak">A goroutine blocked forever on a channel nobody reads (or writes) — it sits in memory doing nothing, forever. In a long-running service, this is a slow memory leak. The standard fix: always provide a way out — a done channel, a context cancellation, or a buffered channel large enough that the sender can always proceed.</ConceptCard>
  <Gotcha>⚠ Classic goroutine leak: you launch a goroutine that sends on `results`, but the receiver returned early (e.g. on a timeout or error). </ConceptGrid>

### Step 1: Waiting on several channels at once

So far every receive waited on ONE channel. Now checkout wants a different rule: *take whichever vendor answers first, but give up after 100 ms.* That's three things to wait on at once: acme's channel, globex's channel, and a timer. A plain `<-ch` can only wait on one. `select` waits on all of them.

<Define term="select">
**`select`** looks like a `switch`, but every `case` is a channel operation. It waits until **one** of the cases can proceed, runs that one case, and skips the rest. If several are ready at the same instant, it picks one at random (never "the first one written"), so no case can starve the others. With a `default:` case, it never waits at all.
</Define>

### Step 2: The default case — non-blocking channel ops

Add a `default` case and the `select` never blocks — if no channel is ready right now, it takes default immediately:

```go
select {
case price := <-results:
	process(price)
default:
	// no price ready right now — do other work or return
	fmt.Println("no price yet, moving on")
}
```

This is the idiom for *checking* a channel without blocking — a non-blocking read/write.

### Step 3: Timeout pattern with `time.After`

`time.After(d)` returns a `<-chan time.Time` that sends a single value after duration `d`. It's the idiomatic timeout in a `select`:

```go
select {
case result := <-work:
	// got the result in time
case <-time.After(5 * time.Second):
	// deadline exceeded — do cleanup
}
```

<Callout kind="warn" title="time.After allocation in hot loops">

`time.After` creates a new timer every call, not a goroutine. Since Go 1.23, unreferenced timers can be garbage-collected before they fire, so this is no longer the old "timer leak" trap. In a loop that calls it thousands of times per second, though, you're still allocating thousands of timers. In hot paths, reuse a `time.Timer` with `Reset()` — or better, use `context.WithTimeout`. We'll see context in full in **Part 1 · Chapter 7**.

</Callout>

### Step 4: Done channels — telling many goroutines to stop at once

Checkout runs background workers that re-check prices every 40 ms. On shutdown you need ALL of them to stop, and you don't know which one is doing what at that moment.

The trick uses the rule from Stop 2: **receiving from a closed channel never waits.** So give every worker the same `done` channel and have each one `select` on it. Closing `done` makes that case ready in every worker at once. It's a broadcast, with a single `close`. The channel's element type is `struct{}` (zero bytes) because no value is ever sent; only the close matters.

<GoPlayground>

```go
package main

import (
	"fmt"
	"time"
)

func worker(id int, done <-chan struct{}, exited chan<- int) {
	ticker := time.NewTicker(40 * time.Millisecond)
	defer ticker.Stop()
	for {
		select {
		case <-ticker.C: // every 40 ms: do a unit of work
			fmt.Printf("worker %d: re-checked prices\n", id)
		case <-done: // closed: time to stop
			fmt.Printf("worker %d: stopping\n", id)
			exited <- id
			return
		}
	}
}

func main() {
	done := make(chan struct{})
	exited := make(chan int)
	for id := 1; id <= 3; id++ {
		go worker(id, done, exited)
	}

	time.Sleep(100 * time.Millisecond) // the service runs for a while (simulated)
	close(done)                        // one close stops every worker

	for range 3 { // wait for each worker to confirm, like the fan-out collect
		<-exited
	}
	fmt.Println("all workers stopped")
}
```

## sync Primitives

*Stop 4 of 6.* Channels pass values *between* goroutines. But sometimes many goroutines need to update the *same* value: a running total, a cache, an account balance. Before the fix, you need to see the problem, because it's invisible in the code.

### Step 1: Watch a data race lose money

Meridian credits 100 deposits of 100 cents into one balance, one goroutine per deposit. The line `balance += 100` *looks* like one step. It isn't. The CPU does it as three:

1. **READ** the current balance into a register (the CPU's private scratch space).
2. **ADD** 100 to the register.
3. **WRITE** the register back to `balance`.

If a second goroutine reads *between* the first one's READ and WRITE, both start from the same old value, and one deposit simply disappears:

<Define term="Data race" since="Advanced Concurrency &amp; Correctness (Part 2)">
A **data race** happens when two goroutines access the same variable at the same time, at least one of them writes, and nothing orders the two accesses (no lock, no channel handoff). The result is undefined: you can lose updates, read half-written values, or see changes in an order that never happened in your code. That's partly because the compiler and CPU are allowed to reorder memory operations that nothing synchronizes. **Production hazard:** races are silent. The code usually works, and then under load an account balance comes out wrong. Go's race detector (`go test -race`, `go run -race`) finds them at runtime. Maps are the one case where the runtime sometimes catches it for you, with `fatal error: concurrent map writes`.
</Define>

You don't have to spot races by eye. Run the program with `-race` and Go watches every memory access and reports the conflicting pair, down to the line:

```text
$ go run -race main.go
==================
WARNING: DATA RACE
Read at 0x00c00009e028 by goroutine 8:
  main.main.func1()
      /s/main.go:15 +0x2c

Previous write at 0x00c00009e028 by goroutine 9:
  main.main.func1()
      /s/main.go:17 +0x44
==================
```

Line 15 is the read (`b := balance`) and line 17 is the write (`balance = b + 100`). Run your tests with `-race` in CI, always.

### Step 2: The fix — a mutex makes READ-ADD-WRITE one step

### Step 3: Mutexes in real code

Back to our checkout: after collecting vendor prices, several goroutines record them into one summary struct. In real code the mutex usually lives *inside* the struct it protects, right next to the fields, so nobody can forget it:

A `sync.Mutex` is a binary lock: held or not held. Only one goroutine can hold it at a time. Everyone else blocks until it's released.

<Define term="sync.Mutex" since="Advanced Concurrency &amp; Correctness (Part 2)">
A **`sync.Mutex`** ("mutual exclusion") lets only one goroutine at a time run the code between `mu.Lock()` and `mu.Unlock()`, the **critical section**. Under the hood it's a small integer the runtime updates atomically. A goroutine that finds it locked spins for a moment in case it frees up quickly, then parks until it's woken. Unlocking also publishes everything written inside, so the next goroutine to lock sees those writes. A **`sync.RWMutex`** allows many readers at once (`RLock`) or one writer (`Lock`). **Production hazard:** copying a mutex (passing the struct by value) copies its lock state and silently breaks it (`go vet` warns about this). Forgetting `Unlock` on an early `return` freezes every later caller, which is why you'll almost always see `defer mu.Unlock()`.
</Define>

<GoPlayground>

```go
package main

import (
	"fmt"
	"sync"
)

type PriceSummary struct {
	mu    sync.Mutex // guards the fields below
	min   int
	max   int
	total int
	count int
}

func (ps *PriceSummary) Record(price int) {
	ps.mu.Lock()         // acquire the lock
	defer ps.mu.Unlock() // release when this function returns — always use defer

	ps.total += price
	ps.count++
	if ps.count == 1 || price < ps.min {
		ps.min = price
	}
	if price > ps.max {
		ps.max = price
	}
}

func main() {
	var ps PriceSummary
	var wg sync.WaitGroup

	prices := []int{999, 1499, 799, 1299, 899}
	for _, price := range prices {
		wg.Go(func() { // Go 1.25: replaces wg.Add(1) + go func(){defer wg.Done()...}()
			ps.Record(price) // Go 1.22+: per-iteration price, no `price := p` shadow needed
		})
	}
	wg.Wait()
	fmt.Printf("min=%d max=%d avg=%d\n", ps.min, ps.max, ps.total/ps.count)
}
```

</GoPlayground>

**`sync.RWMutex`** is a reader-writer lock: multiple goroutines can hold the read lock simultaneously, but a writer needs exclusive access:

```go
var mu sync.RWMutex
var cache map[string]int

// Multiple goroutines can read concurrently.
func read(key string) (int, bool) {
	mu.RLock()
	defer mu.RUnlock()
	v, ok := cache[key]
	return v, ok
}

// Only one goroutine writes at a time, blocking all readers.
func write(key string, value int) {
	mu.Lock()
	defer mu.Unlock()
	cache[key] = value
}
```

Use `RWMutex` when reads heavily outnumber writes — a price cache, a config snapshot. If writes are frequent, a plain `Mutex` is often faster (less bookkeeping).

### Step 4: `sync.WaitGroup`

A `WaitGroup` lets a goroutine wait for a collection of goroutines to finish.

<Define term="sync.WaitGroup">

It's the tool for "wait for all of these to finish" when you don't need their results back (use a channel when you do).

**Go 1.25 added `wg.Go(func())`** — a single call that does `wg.Add(1)`, spawns the goroutine, and wires up `wg.Done()` automatically. This is now the idiomatic way to launch tracked goroutines:

```go
var wg sync.WaitGroup

for _, vendor := range vendors {
	// Go 1.22+: `vendor` is a fresh variable each iteration, so the closure
	// captures the right value — no `v := vendor` copy needed anymore.
	wg.Go(func() {
		doWork(vendor) // wg.Add(1) and defer wg.Done() are handled for you
	})
}

wg.Wait() // block here until counter reaches zero
```

If you're reading pre-1.25 code, you'll see the manual three-step pattern:

```go
// Pre-Go 1.25 idiom — still valid, but more verbose:
for _, vendor := range vendors {
	wg.Add(1) // increment counter BEFORE spawning
	go func(v string) {
		defer wg.Done() // decrement when the goroutine exits
		doWork(v)
	}(vendor)
}
```

Critical rule for the manual form: **call `wg.Add(1)` in the parent, before the `go` statement**, never inside the new goroutine. If `Add` runs inside the goroutine, `main` can reach `wg.Wait()` before that goroutine has even started. The counter is still 0, so `Wait` returns immediately and `main` carries on without the result: Stop 1's vanishing work all over again. (Calling `Done` more times than `Add` is a different bug, and it panics with `sync: negative WaitGroup counter`.) `wg.Go` removes the whole question: it does the `Add` for you, in the right place.

```go
	for _, vendor := range vendors {

			results <- fetchVendorPrice(vendor) // Go 1.22+ per-iteration vendor

	go func() {
		wg.Wait()

		total += price
```

### Step 5: `sync.Once`

`sync.Once` runs a function *exactly once*, even if called from thousands of goroutines simultaneously. The canonical use is lazy initialization of a shared resource:

<GoPlayground>

```go
package main

import (
	"fmt"
	"sync"
)

var (
	once        sync.Once
	vendorCache map[string]int
)

func initCache() {
	// Expensive setup — only want to do this once.
	vendorCache = map[string]int{
		"acme":   999,
		"globex": 1499,
	}
	fmt.Println("cache initialized")
}

func getCache() map[string]int {
	once.Do(initCache) // safe to call from N goroutines — runs exactly once
	return vendorCache
}

func main() {
	var wg sync.WaitGroup
	for range 5 {
		wg.Go(func() { // Go 1.25: wg.Go instead of Add+go+Done
			c := getCache()
			fmt.Println(c["acme"])
		})
	}
	wg.Wait()
}
```

</GoPlayground>

  <Gotcha>⚠ Never copy a Mutex, WaitGroup, or Once after first use. They contain internal state. Pass them by pointer or embed them in a struct that's always used via a pointer. If you see `func foo(mu sync.Mutex)` — that's a copy, and the lock is now broken.</Gotcha>

## Core Patterns

*Stop 5 of 6.* You have the primitives. Now the patterns — the idiomatic compositions that show up in every production Go service. We'll cover two here; the full catalog (fan-in/fan-out, pipelines, errgroup, singleflight, semaphores, heartbeats) lives in **Part 2 · Chapter 6 (Concurrency Patterns)**.

### Step 1: Worker pool — cap how much runs at once

A cart with 500 products needs 500 vendor price lookups. One goroutine per lookup would fire 500 HTTP calls at the vendor at once. They'd rate-limit you, and your memory would spike. A **worker pool** caps it: start a fixed number of workers (say 3), feed them jobs through a channel, and collect results through another. At most 3 lookups are ever in flight.

<GoPlayground>

```go
package main

import (
	"fmt"
	"sync"
	"time"
)

type PriceLookup struct {
	ProductID string
}

type PriceResult struct {
	ProductID string
	Price     int
}

// worker takes jobs until the jobs channel is closed and empty.
func worker(id int, jobs <-chan PriceLookup, results chan<- PriceResult) {
	for job := range jobs {
		time.Sleep(10 * time.Millisecond) // the vendor HTTP call
		results <- PriceResult{ProductID: job.ProductID, Price: 999}
		fmt.Printf("worker %d: priced %s\n", id, job.ProductID)
	}
}

func main() {
	const numWorkers = 3
	const numJobs = 9
	jobs := make(chan PriceLookup, numJobs)
	results := make(chan PriceResult, numJobs)

	// 1. Start a FIXED number of workers.
	var wg sync.WaitGroup
	for id := 1; id <= numWorkers; id++ {
		wg.Go(func() { worker(id, jobs, results) })
	}

	// 2. Hand out all the jobs, then close: "no more work is coming".
	for i := 1; i <= numJobs; i++ {
		jobs <- PriceLookup{ProductID: fmt.Sprintf("SKU-%03d", i)}
	}
	close(jobs)

	// 3. When every worker has exited, close results so the loop below ends.
	go func() {
		wg.Wait()
		close(results)
	}()

	total := 0
	for r := range results {
		total += r.Price
	}
	fmt.Printf("total for %d products: %d cents\n", numJobs, total)
}
```

### Step 2: Generator / pipeline (intro)

A **generator** is a goroutine that produces a stream of values on demand, exposing them as a `<-chan T`. Chain generators together — the output of one becomes the input of the next — and you have a **pipeline**:

<GoPlayground>

```go
package main

import "fmt"

// generate returns a channel that emits the given values then closes.
func generate(vals ...int) <-chan int {
	out := make(chan int)
	go func() {
		for _, v := range vals {
			out <- v
		}
		close(out)
	}()
	return out
}

// applyDiscount reads prices and emits discounted prices.
func applyDiscount(in <-chan int, discountPct int) <-chan int {
	out := make(chan int)
	go func() {
		for price := range in {
			discounted := price - (price * discountPct / 100)
			out <- discounted
		}
		close(out)
	}()
	return out
}

func main() {
	// Pipeline: prices → apply 10% discount → collect
	prices := generate(999, 1499, 799, 2499)
	discounted := applyDiscount(prices, 10)

	for p := range discounted {
		fmt.Printf("discounted price: %d cents\n", p)
	}
}
```

</GoPlayground>


Each stage is a goroutine that reads from its input channel and writes to its output channel. Data flows through, one value at a time. Stages can be composed freely, run at their own pace, and shut down cleanly by closing the channel. **The full pipeline and fan-in/fan-out catalog — including cancellation, error propagation with `errgroup`, and bounded parallelism — lives in Part 2 · Chapter 6 (Concurrency Patterns).**

<ConceptGrid cols={2}>
  <Gotcha>⚠ Goroutine leak — the classic case: you launch a goroutine that sends on a channel. The receiver returns early (timeout, error, `select` picked a different case). The sender is now blocked on a channel nobody reads, forever. Fix: use a buffered channel so sends never block, OR add a done channel to your select so the sender can exit when signaled.</Gotcha>
  <Gotcha>⚠ Loop variable capture (pre-Go 1.22): in a loop like `for _, v := range vendors { go func() { use(v) }() }`, all goroutines captured the same `v` — the last iteration's value. Fix in older code: pass `v` as a parameter (`go func(v string) { use(v) }(v)`). In Go 1.22+, loop variables are per-iteration so this bug is gone — but you'll encounter pre-1.22 code in the wild. Know it.</Gotcha>
</ConceptGrid>

<Callout kind="note" title="Finding leaks in production: the goroutineleak profile">

Go can find leaked goroutines for you. The `goroutineleak` profile reports goroutines blocked on something that can never happen again, like a send on a channel nobody else can reach. It was an experiment in Go 1.26 (`GOEXPERIMENT=goroutineleakprofile`). In Go 1.27, which this book targets, it's built in. Serve it at `/debug/pprof/goroutineleak` with `net/http/pprof`, or look it up directly:

```go
for range 3 {
	ch := make(chan int) // unbuffered, and nobody will ever receive
	go func() { ch <- 999 }()
}
runtime.GC()
pprof.Lookup("goroutineleak").WriteTo(os.Stdout, 1)
```

```text
goroutineleak profile: total 3
3 @ …
#	main.main.func1+0x27	main.go:14
```

It found all three, and line 14 is the stuck `ch <- 999`. The check runs as part of collecting the profile, so a leak shows up when the profile is *written*, not in an earlier `Count()`. More in **Part 2 · Chapter 9 (Debugging Go)**.

</Callout>

<Exercise n={1} title="Hello, goroutine" level="easy">

Write a program that launches three goroutines. Each goroutine prints a greeting with its ID (1, 2, 3). Use a `sync.WaitGroup` to wait for all three before `main` returns.

<Solution>

```go
package main

import (
	"fmt"
	"sync"
)

func main() {
	var wg sync.WaitGroup
	for id := 1; id <= 3; id++ {
		wg.Go(func() { // Go 1.25: wg.Add(1) + spawn + defer wg.Done() in one call
			fmt.Printf("goroutine %d: hello!\n", id)
		})
	}
	wg.Wait()
}
```

`wg.Go` (Go 1.25) handles `wg.Add(1)` and `defer wg.Done()` automatically — one call, no footguns. And since Go 1.22, `id` is a fresh variable each iteration, so the closure captures the value you expect — no `id := i` copy needed (that copy was the pre-1.22 workaround).

</Solution>

</Exercise>

<Exercise n={2} title="Fan-out price lookup" level="easy">

Write a `fanOutPrices(vendors []string) []int` function that launches one goroutine per vendor (each sleeps 20ms and returns 999), collects results into a buffered channel, and returns a slice of all prices. Demonstrate it runs in ~20ms total, not `N×20ms`.

<Solution>

```go
package main

import (
	"fmt"
	"sync"
	"time"
)

func fanOutPrices(vendors []string) []int {
	results := make(chan int, len(vendors))
	var wg sync.WaitGroup

	for range vendors { // one goroutine per vendor; the name itself isn't needed here
		wg.Go(func() { // Go 1.25: replaces wg.Add(1) + go func() + defer wg.Done()
			time.Sleep(20 * time.Millisecond) // simulate the vendor API call
			results <- 999
		})
	}

	go func() {
		wg.Wait()
		close(results)
	}()

	var prices []int
	for p := range results {
		prices = append(prices, p)
	}
	return prices
}

func main() {
	vendors := []string{"acme", "globex", "initech", "umbrella", "weyland"}
	start := time.Now()
	prices := fanOutPrices(vendors)
	fmt.Printf("got %d prices in %v\n", len(prices), time.Since(start))
	// Should print ~20ms, not ~100ms
}
```

The buffered channel (`cap = len(vendors)`) ensures goroutines never block on send. The closer goroutine waits for all workers before closing, enabling the `range` to terminate.

</Solution>

</Exercise>

<Exercise n={3} title="Mutex-protected counter" level="medium">

Build a `SafeCounter` struct with an `Inc()` method and a `Value() int` method, protected by a `sync.Mutex`. Launch 1000 goroutines each calling `Inc()` once, then print the final count. Run it with `go run -race main.go` (the race detector stays silent) and confirm the count is always 1000.

<Solution>

```go
package main

import (
	"fmt"
	"sync"
)

type SafeCounter struct {
	mu    sync.Mutex
	value int
}

func (c *SafeCounter) Inc() {
	c.mu.Lock()
	defer c.mu.Unlock()
	c.value++
}

func (c *SafeCounter) Value() int {
	c.mu.Lock()
	defer c.mu.Unlock()
	return c.value
}

func main() {
	var c SafeCounter
	var wg sync.WaitGroup

	for range 1000 {
		wg.Go(c.Inc) // Go 1.25 wg.Go; no arguments needed since Inc is a method
	}
	wg.Wait()
	fmt.Println("count:", c.Value()) // always 1000 with the mutex
}
```

Without the mutex, the race detector (`go run -race main.go`) would fire — two goroutines reading and writing `value` concurrently is a data race, so the read/write ordering is not guaranteed. With the mutex, it's always 1000.

<Exercise n={4} title="select timeout with cleanup" level="medium">

Write a `fastestVendor(vendors []string, timeout time.Duration) (string, error)` function. It launches one goroutine per vendor (each sleeps a random duration between 10–100ms and returns its name). Use `select` to return the first result or an error if the timeout fires. **No goroutine leaks**: ensure goroutines that didn't win can still send without blocking forever.

<Solution>

```go
package main

import (
	"errors"
	"fmt"
	"math/rand/v2" // Go 1.22: auto-seeded, cleaner API than the old math/rand
	"time"
)

func fastestVendor(vendors []string, timeout time.Duration) (string, error) {
	// Buffered to len(vendors) so every goroutine can send even if we've already returned.
	results := make(chan string, len(vendors))

	for _, vendor := range vendors {
		go func() { // Go 1.22+: `vendor` is per-iteration; no need to pass it as a param
			delay := time.Duration(rand.IntN(90)+10) * time.Millisecond
			time.Sleep(delay)
			results <- vendor // never blocks — buffer ensures it
		}()
	}

	select {
	case winner := <-results:
		return winner, nil
	case <-time.After(timeout):
		return "", errors.New("all vendors timed out")
	}
	// The remaining goroutines will eventually send to the buffered channel and exit cleanly.
}

func main() {
	winner, err := fastestVendor([]string{"acme", "globex", "initech"}, 200*time.Millisecond)
	if err != nil {
		fmt.Println("error:", err)
	} else {
		fmt.Println("fastest vendor:", winner)
	}
}
```

The key insight: a buffered channel of `len(vendors)` means every goroutine can always send, even if nobody is receiving. No goroutine ever blocks forever. This is the standard goroutine-leak fix for the "fan-out with early exit" pattern.

</Solution>

</Exercise>

<Exercise n={5} title="Worker pool with error propagation" level="hard">

Build a worker pool of 4 workers that processes a slice of 20 integer job IDs. Each job computes `jobID * 7`. If `jobID` is divisible by 13, the job returns an error. Collect all successful results and all errors separately. Use channels, `sync.WaitGroup`, and directional channel types. Do not leak any goroutines.

<Solution>

```go
package main

import (
	"fmt"
	"sync"
)

type jobResult struct {
	id    int
	value int
}

type jobError struct {
	id  int
	err error
}

func processJob(id int) (int, error) {
	if id%13 == 0 {
		return 0, fmt.Errorf("job %d: divisible by 13 — vendor rejected", id)
	}
	return id * 7, nil
}

func worker(
	jobs <-chan int,
	results chan<- jobResult,
	errs chan<- jobError,
) {
	for id := range jobs {
		v, err := processJob(id)
		if err != nil {
			errs <- jobError{id: id, err: err}
		} else {
			results <- jobResult{id: id, value: v}
		}
	}
}

func main() {
	const numWorkers = 4
	const numJobs = 20

	jobs := make(chan int, numJobs)
	results := make(chan jobResult, numJobs)
	errs := make(chan jobError, numJobs)

	// wg.Go (Go 1.25) tracks each worker without manual Add/Done.
	var wg sync.WaitGroup
	for range numWorkers {
		wg.Go(func() {
			worker(jobs, results, errs)
		})
	}

	for i := 1; i <= numJobs; i++ {
		jobs <- i
	}
	close(jobs)

	// Close output channels once all workers are done.
	go func() {
		wg.Wait()
		close(results)
		close(errs)
	}()

	// Drain results and errors concurrently using WaitGroup.
	var collectWg sync.WaitGroup

	var successes []jobResult
	collectWg.Go(func() {
		for r := range results {
			successes = append(successes, r)
		}
	})

	var failures []jobError
	collectWg.Go(func() {
		for e := range errs {
			failures = append(failures, e)
		}
	})

	collectWg.Wait()
	fmt.Printf("successes: %d, errors: %d\n", len(successes), len(failures))
	for _, e := range failures {
		fmt.Println("  error:", e.err)
	}
}
```

Two key points: (1) both `results` and `errs` are buffered to `numJobs` so workers never block, and (2) both output channels are closed after `wg.Wait()` so the drain goroutines can `range` to completion cleanly.

<Recap>

You've earned the concurrency chapter. Let's lock in what you own:

- A **goroutine** is a function running alongside yours, started with `go`. `go` never waits and gives you nothing back. **When `main` returns, every goroutine dies**, so starting goroutines is only half the job: you must wait for them (a receive per goroutine, or a WaitGroup), never `time.Sleep`.
- **Concurrency is structure, parallelism is execution.** Waiting work overlaps fine on one CPU; only CPU-heavy work speeds up with more CPUs (up to `GOMAXPROCS`). The scheduler gives each running goroutine about 10 ms before letting another have a turn.
- Goroutines are cheap (a small growable stack, switched without the kernel). The Go runtime's **GMP scheduler** multiplexes huge numbers of them onto a handful of OS threads, with work stealing to keep cores busy.
- **Channels** are typed pipes between goroutines. An **unbuffered** channel has no storage: it's a handshake, and whichever side arrives first parks until the other shows up. **Fan out** with one `go` per task, then **collect** with exactly one receive per task: total time is the slowest task, not the sum. **Buffered** channels let senders run ahead by up to `cap(ch)` values.
- `close(ch)` signals no more sends; `range ch` loops until closed. Only the sender closes. Receiving from a closed-and-empty channel returns the zero value with `ok=false`.
- **Closing a channel wakes every receiver at once**: that's the broadcast behind a `done` channel. A send wakes only one.
- **`select`** parks the goroutine with a ticket in every case's channel; the first to deliver wins and the other tickets are withdrawn. If several cases are ready at once, it picks one at random. Add a `default` for non-blocking. Use `time.After` for timeouts; in hot loops, reuse `time.NewTimer` or use `context`.
- A **data race** is two goroutines touching one variable with no synchronization. `x += 1` is really READ, ADD, WRITE, and interleaved updates silently get lost. Find races with `-race`. Fix them with a **`sync.Mutex`**, which makes the whole read-modify-write one uninterruptible step.
- **`sync.Mutex`** serializes access to shared state. **`sync.RWMutex`** allows concurrent reads. **`sync.WaitGroup`** waits for a collection of goroutines — and as of Go 1.25, `wg.Go(func())` replaces the `wg.Add(1)` + `defer wg.Done()` boilerplate in one safe call. **`sync.Once`** runs setup exactly once.
- The **worker pool** pattern caps concurrency: N workers drain a job channel. The **generator/pipeline** pattern chains stages as goroutines connected by channels.
- Classic footguns: **goroutine leaks** (sender blocked on a channel nobody reads — fix with a buffered channel or done signal; Go 1.26 adds an experimental `goroutineleak` pprof profile, enabled via `GOEXPERIMENT=goroutineleakprofile`, to catch many of these in production), **loop variable capture** in pre-1.22 code (pass the variable as a parameter), and **never copying** `sync` types after first use.
- The full GMP deep-dive and the complete concurrency pattern catalog are in **Part 2 · Chapters 5 and 6**. You've got the foundation.

</Recap>
