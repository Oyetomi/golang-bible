## Goroutines

Here's the scene: a customer hits "Buy Now." Your checkout service needs prices from twelve vendor APIs — sequentially, that's 12 × 80ms = 960ms. Your SLA is 200ms. Sequential is a death sentence. You need concurrency.

Go's answer is the **goroutine**: a lightweight, cooperatively-and-preemptively scheduled function that runs concurrently with everything else. You launch one with the `go` keyword, and the Go runtime handles the rest.

<Define term="Goroutine" since="The Go Scheduler (GMP), In Depth (Part 2)">
A **goroutine** is a function running concurrently with the rest of your program, managed by the Go runtime rather than the OS. It starts with a ~2 KB growable stack (versus ~1–8 MB for an OS thread), so you can run hundreds of thousands of them. You create one with `go f()` — that's the entire syntax. Why it matters: goroutines are what make Go's concurrency model practical at scale; without them, concurrent I/O would require the same number of expensive OS threads as concurrent tasks.
</Define>

```go
package main

import (
	"fmt"
	"time"
)

// fetchPrice simulates a vendor API call with a 50ms delay.
func fetchPrice(vendor string) int {
	time.Sleep(50 * time.Millisecond) // pretend this is an HTTP call
	return 999                        // cents — every vendor charges $9.99 today
}

func main() {
	vendors := []string{"acme", "globex", "initech"}

	// Sequential: each call waits for the previous one to finish.
	start := time.Now()
	for _, v := range vendors {
		price := fetchPrice(v)
		fmt.Printf("%s: %d cents\n", v, price)
	}
	fmt.Printf("sequential: %v\n", time.Since(start)) // ~150ms
}
```

### The `go` keyword

The only syntax you need is `go` in front of a function call:

```go
go fetchPrice("acme")         // fire and forget — main() doesn't wait
go func() { /* ... */ }()     // anonymous function as a goroutine
```

The call happens in a new goroutine. The calling goroutine — `main` in this case — continues *immediately*. There is no blocking, no thread ID to track, no handle returned. If you need the result, you'll use a channel (next section) or a `sync.WaitGroup` (sync section).

<Callout kind="warn" title="main() exiting kills all goroutines">

If `main()` returns, *every goroutine in the program dies instantly*, even ones that haven't finished their work. That's why naive `go` examples sleep at the end — to keep main alive. In real code, you use a `sync.WaitGroup` or a done channel to wait properly.

</Callout>

### Concurrency vs. parallelism

These two words are not synonyms, and mixing them up is the kind of sloppiness I find personally offensive.

- **Concurrency** is the *structure* of your program — multiple things in progress at once, possibly taking turns on a single CPU. You can have concurrency on one core.
- **Parallelism** is *simultaneous physical execution* — multiple things running at the exact same clock tick on multiple CPU cores.

Go's goroutines are concurrent by design. Whether they run in parallel depends on `GOMAXPROCS` — the maximum number of logical processors executing Go code at once. As of Go 1.25, the default is container-aware: it considers logical CPUs, CPU affinity, and Linux cgroup CPU quota. On a 4-core machine with no tighter quota, up to 4 goroutines run in true parallel. The rest take turns.

<Callout kind="note" title="GOMAXPROCS is cgroup-aware as of Go 1.25">

As of Go 1.25, the runtime reads Linux cgroup CPU quotas and sets `GOMAXPROCS` accordingly — so a container with a 2-CPU limit gets 2 Ps without any library tricks. The full details and container deployment guidance are in **Part 2 · Chapter 5 (The Go Scheduler in Depth)**.

</Callout>

### Goroutines vs. OS threads

Why not just use OS threads directly? Because goroutines are dramatically cheaper:

<ConceptGrid cols={3}>
  <ConceptCard label="Stack size">An OS thread starts with a ~1–8 MB fixed stack. A goroutine starts with a small growable stack (about 2 KB in current Go implementations) that expands and contracts as needed. You can run hundreds of thousands of goroutines where threads would exhaust memory.</ConceptCard>
  <ConceptCard label="Scheduling cost">OS thread context switches go through the kernel. Goroutine switches are coordinated in user space by the Go runtime scheduler, so the overhead is much lower and stays practical at very high concurrency.</ConceptCard>
  <ConceptCard label="Creation cost">Spawning an OS thread needs a large stack reservation and kernel work. Spawning a goroutine starts with a small growable stack and runtime bookkeeping, so you can create large numbers of goroutines where threads would run out of memory first.</ConceptCard>
  <ConceptCard label="GOMAXPROCS">Controls how many logical processors execute Go code simultaneously. Default: container-aware since Go 1.25. Setting it to 1 makes your concurrent program single-threaded — useful for debugging races.</ConceptCard>
  <ConceptCard label="Blocking I/O">When a goroutine blocks on a network or disk call, the Go runtime parks it and gives its OS thread to another runnable goroutine. The blocked goroutine costs almost nothing while waiting.</ConceptCard>
  <Gotcha>A goroutine that blocks on a raw OS syscall (like cgo or certain CGO calls) *does* hold onto its OS thread. The runtime creates a new thread for the remaining goroutines. This can cause thread count spikes you don't expect. Stick to stdlib I/O and the runtime stays in control.</Gotcha>
</ConceptGrid>

<UnderTheHood title="The GMP Scheduler — intro (Go 1.14+, asynchronous preemption)">

Every goroutine runs on a thread managed by Go's **GMP scheduler**. Three letters, three concepts:

- **G** — a Goroutine. The unit of concurrent work. Has its own stack (starts at 2 KB, grows/shrinks dynamically). Carries its function pointer, current PC, and local variables.
- **M** — a Machine (OS thread). The actual kernel-scheduled thread. There are usually `GOMAXPROCS` of them running goroutines, plus a few extras for blocking syscalls.
- **P** — a Processor (logical processor). A scheduling context with its own *local run queue* of goroutines waiting to run. There are exactly `GOMAXPROCS` Ps. An M must hold a P to execute Go code.

The scheduler maintains:
1. **Local run queues** (one per P, ~256 slots): goroutines ready to run on this P.
2. **Global run queue**: overflow when a local queue is full, and goroutines coming off blocked I/O.
3. **Work stealing**: when a P's local queue is empty, it steals half the goroutines from another P's queue, keeping all CPUs busy.

When a goroutine blocks on a channel, mutex, or sleep, the runtime *parks* it (removes it from any run queue) and lets the P run something else — no OS thread wasted. When a goroutine blocks on a real syscall (disk, network, cgo), the M parks its P, the blocked M continues the syscall alone, and another M picks up the P to keep running goroutines.

Before Go 1.14, a tight compute loop without a function call could hold a P hostage (no yield point). Go 1.14 added **asynchronous preemption** via POSIX signals — the runtime sends `SIGURG` to a running M, which forces a preemption check. A CPU-bound goroutine can no longer starve everything else.

**The full GMP deep-dive** — work stealing in detail, sysmon, the network poller, and execution traces — lives in **Part 2 · Chapter 5 (The Go Scheduler in Depth)**. We've covered enough here to reason about behavior. More would just be showing off before you've used channels.

</UnderTheHood>

## Channels

Goroutines run concurrently. But how do they *talk* to each other, and how does a goroutine hand off a result without a data race? **Channels** — Go's typed communication pipes. Send a value in, receive it out. The channel handles synchronization for you.

<Define term="Data race" since="Advanced Concurrency &amp; Correctness (Part 2)">
A **data race** happens when two goroutines access the same memory location concurrently and at least one of the accesses is a write — with no synchronization between them. The result is erroneous: you might read a stale or inconsistent value, or crash if the race corrupts a multiword runtime data structure. In Meridian's ledger service, a data race on an account balance could silently corrupt a transfer. Go ships a built-in race detector (`go run -race`) that catches these at runtime.
</Define>

<Define term="Channel" since="Concurrency Patterns (Part 2)">
A **channel** is a typed conduit for passing values between goroutines safely. Sending on a channel (`ch <- v`) and receiving from one (`v := <-ch`) are synchronized — the runtime guarantees no data race on the transferred value. An **unbuffered** channel (`make(chan T)`) forces sender and receiver to meet at the same instant (a rendezvous); a **buffered** channel (`make(chan T, N)`) lets the sender deposit up to N values before blocking, decoupling their speeds. Why it matters: channels are Go's primary tool for goroutines to hand off work and results without shared mutable state.
</Define>

The Go proverb: **"Don't communicate by sharing memory; share memory by communicating."**

Back to our checkout scenario: we need to collect prices from goroutines running in parallel. A channel is how each goroutine sends its result back to the collector.

```go
package main

import "fmt"

func main() {
	// make(chan T) creates an unbuffered channel of type T.
	prices := make(chan int)

	// Launch a goroutine that sends one value on the channel.
	go func() {
		prices <- 999 // send: blocks until someone receives
	}()

	// Receive the value in main().
	p := <-prices // recv: blocks until someone sends
	fmt.Println("price:", p)
}
```

### Unbuffered vs. buffered channels

```go
ch1 := make(chan int)    // unbuffered: capacity 0. send blocks until someone receives.
ch2 := make(chan int, 3) // buffered: capacity 3. send only blocks when the buffer is full.
```

A **buffered channel** decouples sender and receiver. The sender can drop up to `cap(ch)` values and keep going — no waiting — as long as the buffer isn't full. The receiver can drain those values even if the sender is long gone.

### Channel direction

Channels can be restricted to send-only or receive-only in a function signature. This is not a safety theater — it lets the compiler catch you sending where you should only receive, and vice versa. Use it on every function that owns one side of a channel:

```go
// send-only: caller passes in a chan<- int, this func can only send
func producePrice(vendor string, out chan<- int) {
	out <- fetchVendorPrice(vendor)
}

// receive-only: caller passes in a <-chan int, this func can only receive
func consumePrices(in <-chan int) {
	for price := range in {
		fmt.Println(price)
	}
}
```

A bidirectional `chan int` can be passed anywhere a directional channel is expected — the restriction is applied at the usage site.

### Closing a channel and ranging over it

When a sender is *done* sending, it closes the channel. Receivers can detect this:

```go
ch := make(chan int, 5)
ch <- 100
ch <- 200
close(ch) // no more sends allowed; already-buffered values remain readable

v, ok := <-ch // ok=true means a real value; ok=false means closed and empty
```

The idiomatic pattern is `range` over a channel — it loops until the channel is closed and empty:

```go
package main

import "fmt"

func generatePrices(vendors []string) <-chan int {
	out := make(chan int, len(vendors))
	go func() {
		for _, v := range vendors {
			_ = v
			out <- 999 // pretend we fetched from each vendor
		}
		close(out) // signal: no more prices coming
	}()
	return out
}

func main() {
	for price := range generatePrices([]string{"acme", "globex", "initech"}) {
		fmt.Println("price:", price)
	}
	// The range loop exits cleanly when the channel is closed.
}
```

The rule: **the goroutine that creates and sends on a channel is the one that closes it.** The receiver never closes; it just detects the close via the second return value or a `range` loop ending.

### Nil channels

A `nil` channel (a `chan int` that was never initialized with `make`) blocks forever on both send and receive. This sounds useless, but it's a deliberate tool in `select` (next section) — you can disable a case by setting its channel to `nil`.

<Define term="Deadlock" since="Advanced Concurrency &amp; Correctness (Part 2)">
A **deadlock** is a state where every goroutine in a program is blocked waiting for something that will never happen — so nothing can ever run again. Go's runtime detects the simplest case (all goroutines sleeping) and panics with `all goroutines are asleep — deadlock!`. A nil channel receive, two goroutines each waiting for the other to send first, or a `sync.Mutex` locked twice by the same goroutine are all classic deadlock triggers. Why it matters: a deadlock in a Meridian payment handler means the service hangs silently — no crash, no response, just a frozen process until your health check kills it.
</Define>

```go
var ch chan int  // nil channel
// ch <- 1       // would block forever (goroutine leak if nobody else is running)
// <-ch          // would block forever
```

<UnderTheHood title="The hchan struct — what a channel really is">

When you call `make(chan int, 5)`, the runtime allocates an `hchan` struct on the heap. The key fields (simplified from `runtime/chan.go`):

```
hchan {
    qcount   uint           // number of elements currently in the buffer
    dataqsiz uint           // buffer capacity (0 for unbuffered)
    buf      unsafe.Pointer // circular buffer (nil for unbuffered)
    elemsize uint16         // size of one element (8 bytes for int64)
    closed   uint32         // 1 when closed, 0 otherwise
    sendq    waitq          // queue of goroutines blocked on send
    recvq    waitq          // queue of goroutines blocked on receive
    lock     mutex          // protects all fields above
}
```

When a goroutine sends on a full channel (or an unbuffered channel with no receiver ready), the runtime:
1. Locks the `hchan`.
2. Creates a `sudog` (a goroutine/value pair) and enqueues it on `sendq`.
3. Parks the goroutine (marks it not-runnable, removes it from the P's run queue).
4. Unlocks the `hchan` and calls the scheduler.

When a receiver arrives and dequeues that `sudog`, the scheduler marks the sender goroutine as runnable again. **The scheduler is the channel's blocking mechanism** — no OS mutex, no kernel involvement for the blocking itself. This is why channel operations are cheap even when they block: the runtime's user-space scheduler handles it, not the OS.

The `lock` field protects the struct from concurrent access — `hchan` is safe to use from multiple goroutines because all mutations go through that internal mutex. That's the synchronization guarantee you get for free.

</UnderTheHood>

<Define term="Goroutine leak" since="Advanced Concurrency &amp; Correctness (Part 2)">
A **goroutine leak** is a goroutine that is permanently blocked with no way to exit — typically because it is waiting to send or receive on a channel that nobody will ever use. In a long-running Meridian service, leaked goroutines accumulate over time, consuming stack memory and appearing in `/debug/pprof/goroutine` as a growing pile of parked goroutines. The fix is always to give the goroutine an exit path: a buffered channel, a `done` signal, or a `context.Context` cancellation.
</Define>

## select

You have N vendor goroutines, each sending on its own channel. You want a result as soon as one arrives, then move on. That's exactly what `select` does: it waits on multiple channel operations and runs one ready case. If several cases are ready at the same time, Go chooses among them pseudo-randomly.

<Define term="select">
**`select`** is Go's multi-way channel switch. It blocks until one of its `case` channel operations is ready, then executes that case. If multiple cases are ready simultaneously, Go picks one at random (not the first written). A `default` case makes `select` non-blocking — it fires immediately if no channel is ready. Why it matters: `select` is how you implement timeouts, cancellation, and racing multiple concurrent results without spinning — it's the only way to wait on more than one channel at once.
</Define>

```go
package main

import (
	"fmt"
	"time"
)

func vendorQuote(vendor string, delay time.Duration) <-chan int {
	ch := make(chan int, 1)
	go func() {
		time.Sleep(delay)
		ch <- 999 // pretend vendor price
	}()
	return ch
}

func main() {
	acme := vendorQuote("acme", 80*time.Millisecond)
	globex := vendorQuote("globex", 120*time.Millisecond)
	timeout := time.After(100 * time.Millisecond) // <-chan Time

	select {
	case price := <-acme:
		fmt.Println("acme wins:", price)
	case price := <-globex:
		fmt.Println("globex wins:", price)
	case <-timeout:
		fmt.Println("timeout — no price in time")
	}
}
```

### The default case — non-blocking channel ops

Add a `default` case and the `select` never blocks — if no channel is ready right now, it takes default immediately:

```go
select {
case price := <-results:
	process(price)
default:
	// no price ready right now — do other work or return
	fmt.Println("no price yet, moving on")
}
```

This is the idiom for *checking* a channel without blocking — a non-blocking read/write.

### Timeout pattern with `time.After`

`time.After(d)` returns a `<-chan time.Time` that sends a single value after duration `d`. It's the idiomatic timeout in a `select`:

```go
select {
case result := <-work:
	// got the result in time
case <-time.After(5 * time.Second):
	// deadline exceeded — do cleanup
}
```

<Callout kind="warn" title="time.After allocation in hot loops">

`time.After` creates a new timer every call, not a goroutine. Since Go 1.23, unreferenced timers can be garbage-collected before they fire, so this is no longer the old "timer leak" trap. In a loop that calls it thousands of times per second, though, you're still allocating thousands of timers. In hot paths, reuse a `time.Timer` with `Reset()` — or better, use `context.WithTimeout`. We'll see context in full in **Part 1 · Chapter 7**.

</Callout>

### Draining done channels

The canonical way to signal "stop now" across goroutines is a **done channel** — a `chan struct{}` you close when work is finished:

```go
package main

import (
	"fmt"
	"time"
)

func worker(done <-chan struct{}, id int) {
	for {
		select {
		case <-done:
			fmt.Printf("worker %d: shutting down\n", id)
			return
		default:
			fmt.Printf("worker %d: working\n", id)
			time.Sleep(50 * time.Millisecond)
		}
	}
}

func main() {
	done := make(chan struct{})
	go worker(done, 1)
	go worker(done, 2)

	time.Sleep(120 * time.Millisecond) // let them run briefly
	close(done)                        // signal all workers to stop
	time.Sleep(50 * time.Millisecond)  // let them print and exit
}
```

## sync Primitives

Channels are for *communication between goroutines*. When you just need to protect a shared value from concurrent reads and writes, reach for **`sync`** — it's simpler and faster.

Back to our checkout: after collecting all vendor prices, we want to accumulate them into a summary struct from multiple goroutines. That struct needs a lock.

### `sync.Mutex` and `sync.RWMutex`

A `sync.Mutex` is a binary lock: held or not held. Only one goroutine can hold it at a time. Everyone else blocks until it's released.

<Define term="sync.Mutex" since="Advanced Concurrency &amp; Correctness (Part 2)">
A **`sync.Mutex`** (mutual exclusion lock) is a binary lock: exactly one goroutine holds it at a time. Call `mu.Lock()` to acquire — any other goroutine that tries will block until you call `mu.Unlock()`. Always pair with `defer mu.Unlock()` so you can't forget to release it. A **`sync.RWMutex`** extends this to allow many concurrent readers but only one writer. Why it matters: when goroutines share a struct (like Meridian's account balance), a mutex turns a data race into a guarantee — only one goroutine mutates the value at a time.
</Define>

```go
package main

import (
	"fmt"
	"sync"
)

type PriceSummary struct {
	mu    sync.Mutex // guards the fields below
	min   int
	max   int
	total int
	count int
}

func (ps *PriceSummary) Record(price int) {
	ps.mu.Lock()         // acquire the lock
	defer ps.mu.Unlock() // release when this function returns — always use defer

	ps.total += price
	ps.count++
	if ps.count == 1 || price < ps.min {
		ps.min = price
	}
	if price > ps.max {
		ps.max = price
	}
}

func main() {
	var ps PriceSummary
	var wg sync.WaitGroup

	prices := []int{999, 1499, 799, 1299, 899}
	for _, price := range prices {
		wg.Go(func() { // Go 1.25: replaces wg.Add(1) + go func(){defer wg.Done()...}()
			ps.Record(price) // Go 1.22+: per-iteration price, no `price := p` shadow needed
		})
	}
	wg.Wait()
	fmt.Printf("min=%d max=%d avg=%d\n", ps.min, ps.max, ps.total/ps.count)
}
```

**`sync.RWMutex`** is a reader-writer lock: multiple goroutines can hold the read lock simultaneously, but a writer needs exclusive access:

```go
var mu sync.RWMutex
var cache map[string]int

// Multiple goroutines can read concurrently.
func read(key string) (int, bool) {
	mu.RLock()
	defer mu.RUnlock()
	v, ok := cache[key]
	return v, ok
}

// Only one goroutine writes at a time, blocking all readers.
func write(key string, value int) {
	mu.Lock()
	defer mu.Unlock()
	cache[key] = value
}
```

Use `RWMutex` when reads heavily outnumber writes — a price cache, a config snapshot. If writes are frequent, a plain `Mutex` is often faster (less bookkeeping).

### `sync.WaitGroup`

A `WaitGroup` lets a goroutine wait for a collection of goroutines to finish.

<Define term="sync.WaitGroup">
A **`sync.WaitGroup`** is a counter that tracks running goroutines. You increment it before spawning a goroutine (or use `wg.Go` in Go 1.25+, which does this automatically), the goroutine decrements it when done (`wg.Done()`), and the caller blocks on `wg.Wait()` until the counter reaches zero. Why it matters: without a WaitGroup (or a channel), `main()` exits and kills every goroutine before they finish — a silent data loss. The WaitGroup is the idiomatic "wait for all of them" tool when you don't need results (use a channel when you do).
</Define>

**Go 1.25 added `wg.Go(func())`** — a single call that does `wg.Add(1)`, spawns the goroutine, and wires up `wg.Done()` automatically. This is now the idiomatic way to launch tracked goroutines:

```go
var wg sync.WaitGroup

for _, vendor := range vendors {
	// Go 1.22+: `vendor` is a fresh variable each iteration, so the closure
	// captures the right value — no `v := vendor` copy needed anymore.
	wg.Go(func() {
		doWork(vendor) // wg.Add(1) and defer wg.Done() are handled for you
	})
}

wg.Wait() // block here until counter reaches zero
```

If you're reading pre-1.25 code, you'll see the manual three-step pattern:

```go
// Pre-Go 1.25 idiom — still valid, but more verbose:
for _, vendor := range vendors {
	wg.Add(1)              // increment counter BEFORE spawning
	go func(v string) {
		defer wg.Done() // decrement when the goroutine exits
		doWork(v)
	}(vendor)
}
```

Critical rule for both forms: **`wg.Add` or `wg.Go` must be called before the goroutine starts running**, never inside the goroutine. If the goroutine starts and calls `wg.Done()` before `wg.Add(1)` lands, you underflow and panic. `wg.Go` eliminates that footgun by design.

```go
package main

import (
	"fmt"
	"sync"
	"time"
)

func fetchVendorPrice(vendor string) int {
	time.Sleep(50 * time.Millisecond) // simulate I/O
	return 999
}

func main() {
	vendors := []string{"acme", "globex", "initech", "umbrella"}
	results := make(chan int, len(vendors)) // buffer = N so sends never block

	var wg sync.WaitGroup
	for _, vendor := range vendors {
		wg.Go(func() { // Go 1.25: wg.Add(1) + spawn + defer wg.Done() in one call
			results <- fetchVendorPrice(vendor) // Go 1.22+ per-iteration vendor
		})
	}

	// Close the channel once all goroutines finish — safe because we own it.
	go func() {
		wg.Wait()
```

### `sync.Once`

`sync.Once` runs a function *exactly once*, even if called from thousands of goroutines simultaneously. The canonical use is lazy initialization of a shared resource:

```go
	"fmt"
	"sync"

	vendorCache map[string]int

	vendorCache = map[string]int{
		"acme":   999,
		"globex": 1499,

			c := getCache()
			fmt.Println(c["acme"])
		})
	}
	wg.Wait()
}
```

## Core Patterns

You have the primitives. Now the patterns — the idiomatic compositions that show up in every production Go service. We'll cover two here; the full catalog (fan-in/fan-out, pipelines, errgroup, singleflight, semaphores, heartbeats) lives in **Part 2 · Chapter 6 (Concurrency Patterns)**.

### Worker pool

You have a queue of jobs (e.g. price lookups for 500 products in a cart). You don't want 500 goroutines at once — that swamps the vendor APIs and exhausts memory. A **worker pool** caps concurrency: N workers drain a shared job channel.

```go
package main

import (
	"fmt"
	"sync"
	"time"
)

type PriceLookup struct {
	ProductID string
	VendorURL string
}

type PriceResult struct {
	ProductID string
	Price     int
}

// worker reads jobs from the jobs channel and sends results to results.
// It exits cleanly when jobs is closed.
func worker(id int, jobs <-chan PriceLookup, results chan<- PriceResult) {
	for job := range jobs { // range exits when jobs is closed
		time.Sleep(10 * time.Millisecond) // simulate vendor HTTP call
		results <- PriceResult{
			ProductID: job.ProductID,
			Price:     999,
		}
		fmt.Printf("worker %d: priced %s\n", id, job.ProductID)
	}
}

func main() {
	const numWorkers = 3
	const numJobs = 9

	jobs := make(chan PriceLookup, numJobs)
	results := make(chan PriceResult, numJobs)

	// Start the worker pool using wg.Go (Go 1.25) — no wg.Add/defer wg.Done boilerplate.
	var wg sync.WaitGroup
	for id := 1; id <= numWorkers; id++ {
		wg.Go(func() {
			worker(id, jobs, results) // Go 1.22+: `id` is per-iteration, no copy needed
		})
	}

	// Enqueue all jobs, then close to signal no more work.
	for i := 1; i <= numJobs; i++ {
		jobs <- PriceLookup{
			ProductID: fmt.Sprintf("SKU-%03d", i),
			VendorURL: "https://vendor.example.com/price",
		}
	}
	close(jobs) // workers will drain remaining jobs then exit

	// Close results when all workers are done.
	go func() {
		wg.Wait()
		close(results)
	}()

	// Collect all results.
	total := 0
	for r := range results {
		total += r.Price
	}
	fmt.Printf("total for %d products: %d cents\n", numJobs, total)
}
```

### Generator / pipeline (intro)

A **generator** is a goroutine that produces a stream of values on demand, exposing them as a `<-chan T`. Chain generators together — the output of one becomes the input of the next — and you have a **pipeline**:

```go
package main

import "fmt"

// generate returns a channel that emits the given values then closes.
func generate(vals ...int) <-chan int {
	out := make(chan int)
	go func() {
		for _, v := range vals {
			out <- v
		}
		close(out)
	}()
	return out
}

// applyDiscount reads prices and emits discounted prices.
func applyDiscount(in <-chan int, discountPct int) <-chan int {
	out := make(chan int)
	go func() {
		for price := range in {
			discounted := price - (price * discountPct / 100)
			out <- discounted
		}
		close(out)
	}()
	return out
}

func main() {
	// Pipeline: prices → apply 10% discount → collect
	prices := generate(999, 1499, 799, 2499)
	discounted := applyDiscount(prices, 10)

	for p := range discounted {
		fmt.Printf("discounted price: %d cents\n", p)
	}
}
```

  <Gotcha>⚠ Goroutine leak — the classic case: you launch a goroutine that sends on a channel. The receiver returns early (timeout, error, `select` picked a different case).   <Gotcha>⚠ Loop variable capture (pre-Go 1.22): in a loop like `for _, v := range vendors { go func() { use(v) }() }`, all goroutines captured the same `v` — the last iteration's value. Know it.</Gotcha>

<Exercise n={3} title="Mutex-protected counter" level="medium">

Build a `SafeCounter` struct with an `Inc()` method and a `Value() int` method, protected by a `sync.Mutex`. Launch 1000 goroutines each calling `Inc()` once, then print the final count. Run it with `go test -race` (or confirm the count is always 1000).

<Solution>

```go
package main

import (
	"fmt"
	"sync"
)

type SafeCounter struct {
	mu    sync.Mutex
	value int
}

func (c *SafeCounter) Inc() {
	c.mu.Lock()
	defer c.mu.Unlock()
	c.value++
}

func (c *SafeCounter) Value() int {
	c.mu.Lock()
	defer c.mu.Unlock()
	return c.value
}

func main() {

	var wg sync.WaitGroup
```

<Exercise n={4} title="select timeout with cleanup" level="medium">

Write a `fastestVendor(vendors []string, timeout time.Duration) (string, error)` function. It launches one goroutine per vendor (each sleeps a random duration between 10–100ms and returns its name). <Solution>

```go
package main

import (
	"errors"
	"fmt"
	"math/rand/v2" // Go 1.22: auto-seeded, cleaner API than the old math/rand
	"time"
)

func fastestVendor(vendors []string, timeout time.Duration) (string, error) {
	// Buffered to len(vendors) so every goroutine can send even if we've already returned.
	results := make(chan string, len(vendors))

	for _, vendor := range vendors {
		go func() { // Go 1.22+: `vendor` is per-iteration; no need to pass it as a param
			delay := time.Duration(rand.IntN(90)+10) * time.Millisecond
			time.Sleep(delay)
			results <- vendor // never blocks — buffer ensures it
		}()
	}

	select {
	case winner := <-results:
		return winner, nil
	case <-time.After(timeout):
		return "", errors.New("all vendors timed out")
	}
	// The remaining goroutines will eventually send to the buffered channel and exit cleanly.
}

func main() {
	winner, err := fastestVendor([]string{"acme", "globex", "initech"}, 200*time.Millisecond)
	if err != nil {
		fmt.Println("error:", err)
	} else {
		fmt.Println("fastest vendor:", winner)
	}
}
```

The key insight: a buffered channel of `len(vendors)` means every goroutine can always send, even if nobody is receiving. No goroutine ever blocks forever. This is the standard goroutine-leak fix for the "fan-out with early exit" pattern.

<Exercise n={5} title="Worker pool with error propagation" level="hard">

Build a worker pool of 4 workers that processes a slice of 20 integer job IDs. Each job computes `jobID * 7`. If `jobID` is divisible by 13, the job returns an error. Collect all successful results and all errors separately. Use channels, `sync.WaitGroup`, and directional channel types. Do not leak any goroutines.

<Solution>

```go
package main

import (
	"fmt"
	"sync"
)

type jobResult struct {
	id    int
	value int
}

type jobError struct {
	id  int
	err error
}

func processJob(id int) (int, error) {
	if id%13 == 0 {
		return 0, fmt.Errorf("job %d: divisible by 13 — vendor rejected", id)
	}
	return id * 7, nil
}

func worker(
	jobs <-chan int,
	results chan<- jobResult,
	errs chan<- jobError,
) {
	for id := range jobs {
		v, err := processJob(id)
		if err != nil {
			errs <- jobError{id: id, err: err}
		} else {
			results <- jobResult{id: id, value: v}
		}
	}
}

func main() {
	const numWorkers = 4
	const numJobs = 20

	jobs := make(chan int, numJobs)
	results := make(chan jobResult, numJobs)
	errs := make(chan jobError, numJobs)

	// wg.Go (Go 1.25) tracks each worker without manual Add/Done.
	var wg sync.WaitGroup
	for range numWorkers {
		wg.Go(func() {
			worker(jobs, results, errs)
		})
	}

	for i := 1; i <= numJobs; i++ {
		jobs <- i
	}
	close(jobs)

	// Close output channels once all workers are done.
	go func() {
		wg.Wait()
		close(results)
		close(errs)
	}()

	// Drain results and errors concurrently using WaitGroup.
	var collectWg sync.WaitGroup

	var successes []jobResult
	collectWg.Go(func() {
		for r := range results {
			successes = append(successes, r)
		}
	})

	var failures []jobError
	collectWg.Go(func() {
		for e := range errs {
			failures = append(failures, e)
		}
	})

	collectWg.Wait()
	fmt.Printf("successes: %d, errors: %d\n", len(successes), len(failures))
	for _, e := range failures {
		fmt.Println("  error:", e.err)
	}
}
```

Two key points: (1) both `results` and `errs` are buffered to `numJobs` so workers never block, and (2) both output channels are closed after `wg.Wait()` so the drain goroutines can `range` to completion cleanly.

</Solution>

</Exercise>

<Recap>

You've earned the concurrency chapter. Let's lock in what you own:

- A **goroutine** is a lightweight concurrent function started with `go`. It begins with a small growable stack and is vastly cheaper than an OS thread. The Go runtime's **GMP scheduler** multiplexes thousands of goroutines onto a handful of OS threads via work-stealing.
- **Channels** are typed communication pipes between goroutines. **Unbuffered** channels are rendezvous points (both sides block until they meet). **Buffered** channels decouple sender and receiver up to the buffer capacity.
- `close(ch)` signals no more sends; `range ch` loops until closed. Only the sender closes. Receiving from a closed-and-empty channel returns the zero value with `ok=false`.
- **`select`** multiplexes channel operations — it waits until one case can proceed, and if multiple are ready simultaneously it picks pseudo-randomly. Add a `default` for non-blocking. Use `time.After` for timeouts; in hot loops, reuse `time.NewTimer` or use `context`.
- **`sync.Mutex`** serializes access to shared state. **`sync.RWMutex`** allows concurrent reads. **`sync.WaitGroup`** waits for a collection of goroutines — and as of Go 1.25, `wg.Go(func())` replaces the `wg.Add(1)` + `defer wg.Done()` boilerplate in one safe call. **`sync.Once`** runs setup exactly once.
- The **worker pool** pattern caps concurrency: N workers drain a job channel. The **generator/pipeline** pattern chains stages as goroutines connected by channels.
- Classic footguns: **goroutine leaks** (sender blocked on a channel nobody reads — fix with a buffered channel or done signal; Go 1.26 adds an experimental `goroutineleak` pprof profile, enabled via `GOEXPERIMENT=goroutineleakprofile`, to catch many of these in production), **loop variable capture** in pre-1.22 code (pass the variable as a parameter), and **never copying** `sync` types after first use.
- The full GMP deep-dive and the complete concurrency pattern catalog are in **Part 2 · Chapters 5 and 6**. You've got the foundation.
