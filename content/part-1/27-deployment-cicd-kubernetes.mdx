## CI/CD Pipelines

*Stop 1 of 5.*

### Step 1: what a pipeline is for

<Define term="CI/CD pipeline">
An automated sequence that runs on every push. **Continuous integration (CI):** every change is built and tested, so problems appear minutes after they're written. **Continuous delivery/deployment (CD):** a change that passes is packaged and released (automatically, or at the press of a button). Each step is a **gate**: if it fails, nothing after it runs.
</Define>

Without one, deploying is a ritual three people know and one of them just left. With one, pushing ten times a day is boring, which is the goal.

### Step 2: the workflow

GitHub Actions workflows are YAML files under `.github/workflows/`. This is the ledger's, checked with `actionlint`. Watch lines 25–27 and 48–49: `needs:` is what turns three jobs into a chain of gates.

```yaml
name: ci

on:
  push:
    branches: [main]
  pull_request:

env:
  IMAGE: ghcr.io/meridian/ledger

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-go@v7
        with:
          go-version-file: go.mod # the go/toolchain lines decide the version
      - run: go vet ./...
      - uses: golangci/golangci-lint-action@v9
        with:
          version: latest # pin an exact v2.x release in a real project
      - run: go test -race -count=1 -timeout=5m ./...

  image:
    needs: test
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    permissions:
      contents: read
      packages: write
    steps:
      - uses: actions/checkout@v7
      - uses: docker/setup-buildx-action@v4
      - uses: docker/login-action@v4
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}
      - uses: docker/build-push-action@v7
        with:
          push: true
          build-args: VERSION=${{ github.sha }}
          tags: ${{ env.IMAGE }}:${{ github.sha }}
          cache-from: type=gha
          cache-to: type=gha,mode=max

  deploy:
    needs: image
    runs-on: ubuntu-latest
    environment: production # can require a reviewer's approval
    steps:

        run: echo "$KUBECONFIG_DATA" > "$RUNNER_TEMP/kubeconfig"
```

</CodeWalk>

Two rules carry most of the value:

- **Tag images with the commit SHA, never only `latest`.** `latest` is a label that moves; two nodes can pull different images under it, and "roll back to latest" means nothing. A SHA names one image forever and points straight back at the code.
- **Build once, promote the same image.** Staging and production run the identical bytes that passed the tests. Rebuilding per environment reintroduces every difference ch26 removed.

Many teams go one step further with **GitOps**: CI commits the new image tag to a repository of manifests, and a tool running in the cluster (Argo CD, Flux) applies it. The cluster's state is then always a git commit, and rolling back is a `git revert`.

## Reverse Proxies & Load Balancers

*Stop 2 of 5.*

### Step 1: who stands in front of your Go process

Your ledger listens on 8080 over plain HTTP. The internet arrives on 443 over TLS, sometimes as floods, often at replicas that are restarting. Something stands in between.

<Define term="Reverse proxy / load balancer">
A **reverse proxy** accepts client connections on your behalf and forwards requests to your service. It commonly terminates TLS (holds the certificate, decrypts, forwards plain HTTP inside the network). A **load balancer** spreads requests across several replicas and stops sending to ones that fail health checks. nginx, Caddy, Envoy and HAProxy do both; in Kubernetes the role is split between a cloud load balancer, an ingress (or Gateway) controller and the Service.
</Define>

<ConceptGrid cols={3}>
  <ConceptCard label="TLS termination">Certificates and handshakes live at the edge. Your Go code serves plain HTTP inside a private network (or re-encrypts, when policy requires TLS everywhere).</ConceptCard>
  <ConceptCard label="L4 vs L7">An L4 balancer forwards TCP connections by address and port. An L7 balancer reads HTTP and routes by host, path or header. Ingress controllers are L7.</ConceptCard>
  <ConceptCard label="Health-based routing">Replicas failing health checks are taken out of rotation until they pass again.</ConceptCard>
  <ConceptCard label="Per-connection balancing">An L4 balancer (and a Kubernetes Service) balances <em>connections</em>. Long-lived keep-alive or HTTP/2 connections can pin one client to one pod; L7 balancers spread requests.</ConceptCard>
  <ConceptCard label="Client IP">The proxy is the one connecting to you. It passes the original address in <code>X-Forwarded-For</code>, which you may only trust from your own proxy (Step 3).</ConceptCard>
  <Gotcha>Inside a container, listen on <code>:8080</code> (all interfaces), not <code>127.0.0.1:8080</code>. Loopback only accepts connections from inside the same container, so the proxy gets refused and users see 502s.</Gotcha>
</ConceptGrid>

### Step 3: writing a proxy in Go? Use `Rewrite`

When you do need a proxy in Go (an API gateway, a sidecar), `net/http/httputil.ReverseProxy` is the tool. It has two hooks for adjusting the outgoing request, and the older one, `Director`, is marked **deprecated** in the Go 1.27 documentation, for two reasons it lists: headers a `Director` adds can be stripped again by a client (by naming them in `Connection` as hop-by-hop), and incoming `X-Forwarded-For` headers are kept by default, which permits IP spoofing. `Rewrite` (Go 1.20) fixes both. The spoofing difference, run:

<GoPlayground>

```go
package main

import (
	"fmt"
	"io"
	"net/http"
	"net/http/httptest"
	"net/http/httputil"
	"net/url"
)

func main() {
	// The ledger trusts X-Forwarded-For for rate limits and audit logs.
	backend := httptest.NewServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		fmt.Fprintf(w, "X-Forwarded-For=%q", r.Header.Get("X-Forwarded-For"))
	}))
	defer backend.Close()
	upstream, _ := url.Parse(backend.URL)

	oldStyle := &httputil.ReverseProxy{
		Director: func(r *http.Request) { // deprecated
			r.URL.Scheme, r.URL.Host = upstream.Scheme, upstream.Host
		},
	}
	newStyle := &httputil.ReverseProxy{
		Rewrite: func(pr *httputil.ProxyRequest) {
			pr.SetURL(upstream)
			pr.SetXForwarded() // X-Forwarded-For = the address that actually connected
		},
	}

	for _, p := range []struct {
		name  string
		proxy http.Handler
	}{{"Director", oldStyle}, {"Rewrite ", newStyle}} {
		front := httptest.NewServer(p.proxy)
		req, _ := http.NewRequest("GET", front.URL, nil)
		req.Header.Set("X-Forwarded-For", "10.0.0.1") // a client pretending to be internal
		resp, err := http.DefaultClient.Do(req)
		if err != nil {
			panic(err)
		}
		body, _ := io.ReadAll(resp.Body)
		resp.Body.Close()
		front.Close()
		fmt.Printf("%s -> backend saw %s\n", p.name, body)
	}
}
```

</GoPlayground>

```text
Director -> backend saw X-Forwarded-For="10.0.0.1, 127.0.0.1"
Rewrite  -> backend saw X-Forwarded-For="127.0.0.1"
```

With `Director`, the forged `10.0.0.1` reaches the backend first in the list, exactly where naive code looks for "the client IP". `Rewrite` starts the outgoing headers clean and `SetXForwarded` records only what the proxy actually saw. Set exactly one of the two hooks.

## Kubernetes from First Principles

*Stop 3 of 5.*

<ELI5
  concept="What Kubernetes actually does"
  analogy="A building manager you give a standing instruction to, not a switchboard you operate."
  role="reader"
>

Kubernetes isn't a tool you run commands against. You give it a **desired state** ("there should be three copies of this"), and controllers work continuously to make reality match. One copy crashes: a replacement starts. A machine dies: its work moves. You changed nothing; the gap between desired and actual reappeared, and something closed it.

That's why fixing things by hand in a cluster tends not to stick: the controllers undo anything that disagrees with what you declared. You change the declaration instead.

</ELI5>

### Step 1: the objects

<Define term="Pod">
The smallest thing Kubernetes runs: one or more containers sharing a network address and volumes, usually one container. Pods are disposable: they're replaced on every deploy and get new IP addresses each time.
</Define>

<Define term="Deployment">
"Keep N identical pods of this template running." It manages ReplicaSets (one per version of the template) and performs rolling updates between them.
</Define>

<Define term="Service">
A stable name and virtual IP (`ledger.production.svc.cluster.local`) in front of the pods matching a label selector. Its **EndpointSlices** list the pods' addresses and whether each is ready; kube-proxy on every node programs the routing from them.
</Define>

<Define term="Ingress / Gateway">
HTTP routing into the cluster ("`ledger.example.com/api` → Service `ledger`"), implemented by a controller (nginx, Traefik, Envoy-based ones, or your cloud's). The newer **Gateway API** (`Gateway` + `HTTPRoute`) is the successor to Ingress; the widely used community ingress-nginx controller has been retired, so new clusters increasingly start with Gateway API.
</Define>

<ConceptGrid cols={3}>
  <ConceptCard label="ConfigMap">Non-secret configuration, injected as environment variables or files.</ConceptCard>
  <ConceptCard label="Secret">Sensitive values, injected the same way. Stored base64-encoded, which is encoding, not encryption (below).</ConceptCard>
  <ConceptCard label="Namespace">A named partition for access control and quotas: <code>staging</code> and <code>production</code> can share a cluster.</ConceptCard>
  <ConceptCard label="ReplicaSet">Created by a Deployment, one per template version. Rollbacks switch which one is scaled up.</ConceptCard>
  <ConceptCard label="HorizontalPodAutoscaler">Changes a Deployment's replica count from metrics such as CPU. Needs metrics-server (or another metrics API) installed.</ConceptCard>
  <Gotcha>A Secret isn't encrypted by default. Anyone who can read it can decode it; on the test cluster, <code>czNjcmV0</code> came back as <code>s3cret</code> with <code>base64 -d</code>. Restrict who can read Secrets, enable encryption at rest, or sync them from a real secret manager (External Secrets Operator + Vault or your cloud's).</Gotcha>
</ConceptGrid>

<UnderTheHood title="Controllers: observe, compare, act">

Every Kubernetes controller is a Go program running the same loop against the API server (which stores state in etcd):

1. **Observe** the current state (which pods exist, which are ready).
2. **Compare** it with the desired state (the Deployment says 3).
3. **Act** to close the gap (create or delete pods).

`kubectl apply` doesn't deploy anything itself; it writes the desired state and returns. The Deployment controller notices and creates a ReplicaSet; the ReplicaSet controller creates pods; the scheduler assigns them to nodes; the kubelet on each node starts containers; the EndpointSlice controller publishes ready pods; kube-proxy routes to them. When a pod was deleted on the test cluster, its replacement existed within a second, because the ReplicaSet controller saw 2 where it wanted 3.

This is **level-triggered**: controllers act on the state they observe, not on a stream of events they might miss. A dropped notification is corrected on the next pass.

</UnderTheHood>

### Step 3: liveness is not readiness

<Define term="Liveness vs readiness (vs startup)">
**Readiness**: "send me traffic?" Failure takes the pod out of the Service's endpoints and nothing else. **Liveness**: "am I broken beyond repair?" Failure makes the kubelet restart the container. **Startup**: "have I finished starting?" While it hasn't passed, the other two are paused.
</Define>

The classic outage comes from mixing them up: a liveness probe that pings the database. The database has a two-minute hiccup, every pod's liveness fails, and Kubernetes restarts **every pod at once**. Now there's an outage of the ledger on top of the database's, plus a thundering herd of reconnections when it comes back. Rules of thumb:

- **Liveness** checks only the process itself: can it answer HTTP at all? (A deadlocked server can't.) Never a dependency.
- **Readiness** may check dependencies it truly can't work without, and must fail while the pod is shutting down.
- If startup is slow, use a **startup** probe rather than a long `initialDelaySeconds` on liveness.

The lab builds exactly this pair, plus the shutdown behaviour from Stop 4.

### Step 4: resources, and how Go sees them

```yaml
resources:
  requests:        # reserved for scheduling
    cpu: 250m      # a quarter of a core
    memory: 128Mi
  limits:          # enforced
    memory: 256Mi  # exceed it and the container is OOM-killed
```

**Requests** decide where a pod fits: the scheduler only places it on a node with that much unreserved capacity. **Limits** are enforced by the kernel's cgroups (ch25): over the memory limit, the container is killed; over a CPU limit, it's throttled (paused until the next 100 ms period).

What Go makes of a CPU limit, measured with pods on an 8-core node:

| Pod CPU limit | `GOMAXPROCS` |
|---|---|
| 250m | 2 |
| 500m | 2 |
| 1500m | 2 |
| 3 | 3 |

Since Go 1.25 the runtime reads the limit, rounds it up, and doesn't go below 2. The memory limit, as ch25 showed, is not read: set `GOMEMLIMIT` (line 38 of the manifest).

Many teams set a CPU **request** but no CPU **limit** for latency-sensitive services, as the manifest does: a limit throttles the pod even when the node has idle CPU, and throttling shows up as tail latency. Without a limit, `GOMAXPROCS` is the node's core count and the request still guarantees the pod its share under contention. Memory is different: always set a memory limit.

**Recap.** Kubernetes reconciles declared state: Deployments keep pods running, Services give them a stable name through EndpointSlices of ready pods. Readiness gates traffic, liveness restarts, startup protects slow starts. Go follows CPU limits; set `GOMEMLIMIT`; Secrets are only base64.

## Rolling Updates & Rollbacks

*Stop 4 of 5.*

### Step 1: how a rolling update proceeds

<Define term="Rolling update">
Replacing a Deployment's pods a few at a time. **`maxSurge`** is how many pods may exist above the desired count; **`maxUnavailable`** is how many desired pods may be not-ready. With `maxSurge: 1, maxUnavailable: 0`, Kubernetes adds one new pod, waits until it's **ready**, removes one old pod, and repeats. A new version that never becomes ready simply stalls.
</Define>

For the measurements, the ledger ran 3 replicas with a 3-second startup (standing in for opening pools and warming caches), and a load generator inside the cluster sent `POST` requests (so the client wouldn't silently retry them) from 10 workers for 35 seconds, about 16,000 requests, while each rollout ran.

### Step 2: the race nobody draws

| Rollout setup (Kubernetes 1.37, ~16,000 requests each) | Failed requests |
|---|---|
| `strategy: Recreate` (all old pods stop, then new ones start) | **1,133** in one rollout (1,123 connection refused, 10 timeouts) |
| RollingUpdate, Go server calls `Shutdown` as soon as SIGTERM arrives | 0, 2, 0, 2, 0, 3, 6, 2, 6 across **9 rollouts** |
| RollingUpdate, Go server fails readiness and keeps serving 5 s before `Shutdown` | 0 across 6 rollouts |
| RollingUpdate, `preStop: sleep: 5`, Go server unchanged | 0 across 4 rollouts |

Recreate is obviously bad. But the "correct" rolling update still failed requests in six rollouts out of nine, every failure a `connection refused`. Why?

When Kubernetes terminates a pod, two things start **at the same time**: the kubelet sends SIGTERM, and the EndpointSlice is updated to mark the pod `ready=false, terminating=true` (observed on the cluster within a second of deletion). But kube-proxy on every node, the ingress controller and any cloud load balancer each learn about that change on their own schedule. For a moment, some of them still send new connections to a pod whose Go server has already closed its listener.

### Step 3: the Go side

Two fixes, both measured at zero failures. Either keep the server alive in Go:

```go
<-ctx.Done() // SIGTERM (signal.NotifyContext, ch19)

ready.Store(false)          // 1. /readyz now answers 503
time.Sleep(5 * time.Second) // 2. keep serving while proxies catch up

shutdownCtx, cancel := context.WithTimeout(context.Background(), 20*time.Second)
defer cancel()
srv.Shutdown(shutdownCtx) // 3. stop accepting, finish in-flight requests
```

or let Kubernetes delay the SIGTERM with the built-in `preStop` sleep (manifest lines 64–67), and keep the ch19 shutdown code unchanged. Either way the arithmetic must fit: **delay + longest request < `terminationGracePeriodSeconds`**, or SIGKILL arrives mid-request. Here: 5 s + 20 s < 30 s.

Failing readiness during the delay isn't what removes the pod (deletion already did that), but it tells any health-checking proxy outside Kubernetes the same thing, and it's what the lab checks.

## Cloud Provider Tour

*Stop 5 of 5.*

### Step 1: from YAML to a public hostname

The test cluster had no cloud behind it, so this stop describes the path rather than measuring it. On a managed cluster (EKS, GKE, AKS):

1. **The controller asks for a load balancer.** Installing an ingress or Gateway controller creates a Service of `type: LoadBalancer` (or the cloud's own controller reads your Ingress/Gateway directly), and the cloud provisions a load balancer with a public address, typically within a few minutes.
2. **DNS points at it.** An `A` record (for an IP) or `CNAME` (for a hostname like `…elb.amazonaws.com`) for `ledger.example.com`.
3. **A certificate is issued.** cert-manager sees the `tls:` section and the `cert-manager.io/cluster-issuer` annotation, proves control of the domain to Let's Encrypt (ACME HTTP-01 or DNS-01), stores the certificate in the named Secret, and renews it before it expires (Let's Encrypt certificates last 90 days, and are getting shorter).
4. **Traffic flows** along the path in Stop 2.

Two operators remove the manual steps: **external-dns** creates DNS records from your Ingress/Service hostnames, and **cert-manager** handles certificates. The Ingress and autoscaler for the ledger (validated with a server-side dry run on the test cluster):

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: ledger
  namespace: production
  annotations:
    cert-manager.io/cluster-issuer: letsencrypt-prod
spec:
  ingressClassName: nginx
  tls:
    - hosts: [ledger.example.com]
      secretName: ledger-tls # cert-manager fills this Secret
  rules:
    - host: ledger.example.com
      http:
        paths:
          - path: /api
            pathType: Prefix
            backend:
              service:
                name: ledger
                port:
                  number: 80
---
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: ledger
  namespace: production
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: ledger
  minReplicas: 3
  maxReplicas: 10
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70
```

|---|---|---|---|

<Exercise n={1} title="Probes that don't take each other down" level="easy">

Write `/healthz` and `/readyz` handlers for a service with a database. Liveness must never depend on the database; readiness must fail when the database doesn't answer within 500 ms, and while the service is shutting down.

<Solution>

```go
package main

import (
	"context"
	"fmt"
	"net/http"
	"net/http/httptest"
	"sync/atomic"
	"time"
)

type pinger interface {
	PingContext(ctx context.Context) error
}

func probes(db pinger, shuttingDown *atomic.Bool) (healthz, readyz http.HandlerFunc) {
	healthz = func(w http.ResponseWriter, r *http.Request) {
		w.Write([]byte("ok")) // the process can serve HTTP: that's all liveness asks
	}
	readyz = func(w http.ResponseWriter, r *http.Request) {
		if shuttingDown.Load() {
			http.Error(w, "shutting down", http.StatusServiceUnavailable)
			return
		}
		ctx, cancel := context.WithTimeout(r.Context(), 500*time.Millisecond)
		defer cancel()
		if err := db.PingContext(ctx); err != nil {
			http.Error(w, "database unavailable", http.StatusServiceUnavailable)
			return
		}
		w.Write([]byte("ready"))
	}
	return healthz, readyz
}

type downDB struct{}

func (downDB) PingContext(ctx context.Context) error { <-ctx.Done(); return ctx.Err() }

func main() {
	var stopping atomic.Bool
	healthz, readyz := probes(downDB{}, &stopping)
	for _, p := range []struct {
		name string
		h    http.HandlerFunc
	}{{"/healthz", healthz}, {"/readyz", readyz}} {
		rec := httptest.NewRecorder()
		p.h(rec, httptest.NewRequest("GET", p.name, nil))
		fmt.Println(p.name, rec.Code)
	}
}
```

With the database down this prints `/healthz 200` and `/readyz 503`: the pod leaves the Service but isn't restarted. `*sql.DB` satisfies `pinger`, and the small interface keeps the handlers testable.

</Solution>

</Exercise>

<Exercise n={2} title="Spot the pipeline mistakes" level="easy">

What's wrong with this workflow?

```yaml
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - run: go test ./...
  deploy:
    runs-on: ubuntu-latest
    steps:
      - run: kubectl set image deployment/ledger ledger=registry/ledger:latest
```

<Solution>

1. **No `needs: test`.** Jobs run in parallel by default, so the deploy doesn't wait for (or care about) the tests.
2. **`:latest`.** The deploy can't say which code it's shipping, `set image` to the same tag may not even trigger a rollout, and rollback has nothing to point at. Tag with `${{ github.sha }}`.
3. **No image is built** in this workflow, so it deploys whatever `latest` happens to be.
4. **No `rollout status`**, so the job "succeeds" even if the new pods never become ready.
5. **No `-race`** on the tests, and no setup-go (the runner's preinstalled Go version decides).

</Solution>

</Exercise>

<Exercise n={3} title="Budget the grace period" level="medium">

The ledger's slowest endpoint (a statement export) can take 40 seconds. Proxies need about 5 seconds to stop routing to a terminating pod. Choose `terminationGracePeriodSeconds`, the `preStop` sleep and the `Shutdown` timeout, and explain what happens to an export in progress during a rollout.

<Solution>

```yaml
terminationGracePeriodSeconds: 60
lifecycle:
  preStop:
    sleep:
      seconds: 5
```

```go
ctx, cancel := context.WithTimeout(context.Background(), 50*time.Second)
defer cancel()
srv.Shutdown(ctx)
```

The grace period covers everything after the pod starts terminating, including the `preStop` sleep: 5 s + 50 s = 55 s < 60 s, leaving room to exit. An export already running keeps going: `Shutdown` stops new connections and waits for active requests. If it exceeds 50 s, `Shutdown` returns a context error and the process exits; at 60 s the kubelet would SIGKILL anyway. For operations that can run arbitrarily long, a better design is to make them jobs (Part 2, Chapter 13) that survive a restart, rather than stretching every deploy.

</Solution>

</Exercise>

<Exercise n={4} title="Trace a broken rollout" level="medium">

The v2 image crashes on startup because a required environment variable is missing. With 3 replicas, `maxSurge: 1`, `maxUnavailable: 0`, walk through what Kubernetes does, what users see, what CI sees, and how you recover.

<Solution>

1. A v2 pod is created (4 pods). It crashes, restarts, crashes: `CrashLoopBackOff`, with growing delays between restarts.
2. It never becomes ready, so it never joins the Service's endpoints, and `maxUnavailable: 0` means no v1 pod is terminated. The rollout stalls; users see nothing (the stage in Stop 4 measured 0 failures of 20,733 in the equivalent case).
3. `kubectl rollout status --timeout=5m` in CI fails, turning the pipeline red. The Deployment's `progressDeadlineSeconds` (default 600) also marks it `Progressing=False` with reason `ProgressDeadlineExceeded`.
4. Diagnose with `kubectl describe pod` (events, exit code) and `kubectl logs <pod> --previous` (the crashed container's output).
5. Recover by fixing forward (a new commit that sets the variable) or reverting the commit; `kubectl rollout undo` also works but leaves your manifests out of step with the cluster.

</Solution>

</Exercise>

<Exercise n={5} title="Configuration from the environment" level="hard">

Write a ConfigMap with `database_host` and `log_level`, and the container `env:` that injects them plus `DATABASE_PASSWORD` from a Secret. Then write the Go that reads them, failing fast at startup if a required one is missing, and distinguishing "unset" from "set to empty" for `LOG_LEVEL`.

<Solution>

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: ledger-config
  namespace: production
data:
  database_host: postgres.production.svc.cluster.local
  log_level: info
```

```yaml
env:
  - name: DATABASE_HOST
    valueFrom:
      configMapKeyRef: { name: ledger-config, key: database_host }
  - name: LOG_LEVEL
    valueFrom:
      configMapKeyRef: { name: ledger-config, key: log_level, optional: true }
  - name: DATABASE_PASSWORD
    valueFrom:
      secretKeyRef: { name: ledger-secrets, key: database_password }
```

```go
package main

import (
	"errors"
	"fmt"
	"log/slog"
	"os"
)

type config struct {
	DatabaseHost, DatabasePassword string
	LogLevel                       slog.Level
}

func load() (config, error) {
	var c config
	var missing []error
	for _, v := range []struct {
		name string
		dst  *string
	}{{"DATABASE_HOST", &c.DatabaseHost}, {"DATABASE_PASSWORD", &c.DatabasePassword}} {
		if *v.dst = os.Getenv(v.name); *v.dst == "" {
			missing = append(missing, fmt.Errorf("%s is required", v.name))
		}
	}
	c.LogLevel = slog.LevelInfo
	if s, ok := os.LookupEnv("LOG_LEVEL"); ok { // set, possibly to ""
		if err := c.LogLevel.UnmarshalText([]byte(s)); err != nil {
			missing = append(missing, fmt.Errorf("LOG_LEVEL: %w", err))
		}
	}
	return c, errors.Join(missing...)
}

func main() {
	os.Setenv("DATABASE_HOST", "postgres.production.svc.cluster.local")
	os.Setenv("LOG_LEVEL", "debug")
	c, err := load()
	fmt.Printf("host=%s level=%v err=%v\n", c.DatabaseHost, c.LogLevel, err)
}
```

This prints `host=postgres.production.svc.cluster.local level=DEBUG err=DATABASE_PASSWORD is required`. Failing at startup matters: the pod crash-loops and the rollout stalls harmlessly (Exercise 4), instead of starting "ready" and failing on the first real request. Part 2, Chapter 16 goes further with configuration and secrets.

</Solution>

</Exercise>

<Recap>

- **CI/CD** chains gates with `needs:`: vet, lint and `-race` tests, then one image tagged with the **commit SHA**, then a rollout the job waits on. Never deploy `latest`.
- **Reverse proxies** terminate TLS; **load balancers** spread requests over healthy replicas. Listen on all interfaces in containers. In Go, proxy with `ReverseProxy.Rewrite`; `Director` is deprecated and passes spoofed `X-Forwarded-For` through.
- **Kubernetes** reconciles declared state. Services route to **ready** pods via EndpointSlices. Readiness gates traffic, liveness restarts (never check dependencies there), startup protects slow boots. Secrets are base64, not encrypted.
- Go sets `GOMAXPROCS` from the **CPU limit** (rounded up, at least 2); set **`GOMEMLIMIT`** for the memory limit.
- **Rolling updates** (`maxSurge: 1`, `maxUnavailable: 0`) keep capacity and stall harmlessly on a bad release (0 of 20,733 failed). `Recreate` dropped 1,133 requests.
- SIGTERM races the load balancers: shutting down at once dropped requests in 6 of 9 rollouts. **Keep serving ~5 s** (`preStop` sleep or a drain delay) before `Shutdown`: 0 failures in 10.
- Clouds turn an Ingress or Gateway into a public load balancer; cert-manager and external-dns automate certificates and DNS.
