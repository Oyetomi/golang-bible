## CI/CD Pipelines

### The problem a pipeline solves

<Define term="CI/CD pipeline" since="Deployment & Infra: CI/CD + Kubernetes (this chapter)">
A **CI/CD pipeline** is the automated sequence that runs every time you push code: build it, test it, and — if all gates pass — ship it. **CI (Continuous Integration)** means every commit is automatically built and tested. **CD (Continuous Deployment)** means a passing build is automatically deployed to production. The pipeline is the enforcer between a careless keystroke and a production outage. Without one, deployment is a manual ritual that only three people know how to do — and one of them just quit.
</Define>

You push a commit. Within two minutes, every test runs, the binary is built and pushed to a registry, and the cluster pulls the new image. Or — and this is the critical part — it *doesn't*, because the race detector found a data race in the transfer handler, and the build never left the gate.

That's CI/CD: **Continuous Integration** (every commit is automatically built and tested) plus **Continuous Deployment** (a passing build is automatically deployed). The pipeline is the enforcer. It's the thing that stands between a careless keystroke and a production outage.

No pipeline means deployment is a manual, bespoke, undocumented ritual that only three people know how to do and one of them just quit. I've seen it. It's pathetic.

**On the job:** The moment a team skips any of these gates to "ship faster," they stop shipping faster. One production incident — a data race in the transfer handler, a broken config key, a `nil` pointer in the reconciliation job — wipes out weeks of gained time. The pipeline isn't bureaucracy; it's the thing that lets you push ten times a day without fear.

### GitHub Actions: the concrete implementation

GitHub Actions is the standard CI system for most Go projects. A workflow is a YAML file in `.github/workflows/`. Here is the real pipeline for the ledger service:

```yaml
# .github/workflows/ci.yml
name: ci

on:
  push:
    branches: [main]
  pull_request:

env:
  REGISTRY: ghcr.io
  IMAGE_NAME: meridian/ledger-service

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Set up Go
        uses: actions/setup-go@v5
        with:
          go-version: "1.26"
          cache: true          # caches the module download cache and build cache

      - name: go vet
        run: go vet ./...

      - name: golangci-lint
        uses: golangci/golangci-lint-action@v6
        with:
          version: latest

      - name: test (with race detector)
        run: go test -race -count=1 -timeout=120s ./...

  build-push:
    needs: test            # only runs if test job passes
    runs-on: ubuntu-latest
    permissions:
      contents: read
      packages: write      # needed to push to ghcr.io

    steps:
      - uses: actions/checkout@v4

      - name: Log in to registry
        uses: docker/login-action@v3
        with:
          registry: ${{ env.REGISTRY }}
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      - name: Build and push
        uses: docker/build-push-action@v5
        with:
          push: true
          # Build args pass the commit SHA into the binary via -ldflags.
          # See the Building & Shipping Binaries chapter for the full recipe.
          build-args: |
            VERSION=${{ github.sha }}
          tags: |
            ${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}:${{ github.sha }}
            ${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}:latest

  deploy:
    needs: build-push      # only runs after the image is in the registry
    runs-on: ubuntu-latest
    if: github.ref == 'refs/heads/main'   # only deploy from main

    steps:
      - name: Deploy to cluster
        run: |
          kubectl set image deployment/ledger-service \
            ledger-service=${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}:${{ github.sha }} \
            -n production
          kubectl rollout status deployment/ledger-service -n production --timeout=300s
```

A few things to notice:

- **`needs:`** enforces job ordering. `deploy` won't run unless `build-push` succeeds, and `build-push` won't run unless `test` succeeds. The pipeline is a DAG.
- **The image is tagged with the Git commit SHA** (`github.sha`), not just `latest`. This makes every image traceable back to the exact code that built it and makes rollbacks trivial — just point the Deployment at the previous SHA.
- **`kubectl rollout status`** means the deploy job doesn't complete until Kubernetes confirms the new pods are healthy. If the deploy hangs or the pods crash-loop, the CI job fails and pages the team — not a user.

<Callout kind="warn" title="Never tag production images with 'latest'">

`latest` is mutable. It means nothing. If a node restarts and pulls `latest`, it might get a different image than the rest of the cluster. Tag every image with the immutable Git SHA. Use `latest` only for local development convenience.

</Callout>

<Callout kind="pro" title="Cache your Go builds in CI">

The `cache: true` option in `actions/setup-go` persists the Go module cache and the build cache between runs. On a cold cache, a CI run compiles everything from scratch. With the cache, unchanged dependencies aren't re-downloaded or recompiled. On a large service this is the difference between a 3-minute CI run and a 45-second one.

</Callout>

### The pipeline stages, explained

| Stage | Tool | What fails | Why it matters |
|---|---|---|---|
| `go test` | stdlib `testing` | failing assertions | catches regressions immediately |
| `go vet` | Go toolchain | suspicious code patterns | free static analysis from the compiler authors |
| `golangci-lint` | golangci-lint | idiom/style/bug linters | catches what `vet` misses |
| `go test -race` | Go race detector | data races at runtime | the only reliable way to find races |
| `docker build` | Docker | build errors, bad Dockerfile | confirms the artifact is producible |
| `docker push` | registry | auth, quota issues | image must be in registry before deploy |
| `kubectl rollout` | Kubernetes | unhealthy pods | confirms production actually accepted the change |

## Reverse Proxies & Load Balancers

### Why you don't expose your Go service directly to the internet

Your Go service listens on port 8080. The internet connects on port 443. Between them sits a **reverse proxy** — a process that accepts the inbound HTTPS connection, terminates TLS (unwraps the encryption), and forwards the plain HTTP request to your service.

The reverse proxy also does something your Go service shouldn't have to care about: it distributes incoming requests across *multiple replicas* of your service. That's the **load balancer** function. Run three pods of the ledger service, put a load balancer in front, and the 1000 req/s that would have saturated one process now spread across three.

Let me be specific about what lives where.

<Define term="Reverse proxy / load balancer" since="Networking & How the Web Actually Works (Part 1, Chapter 13)">
A **reverse proxy** sits in front of your service: it accepts inbound connections, terminates TLS (unwraps the encryption), and forwards plain HTTP to your backend. Clients talk to the proxy; they never reach your Go process directly. A **load balancer** is a reverse proxy with one extra job: distributing requests across *multiple* backend replicas. In practice these roles are combined — nginx, Caddy, and Envoy all do both. In Kubernetes, the ingress controller is the reverse proxy/load balancer. If a pod is unhealthy, the load balancer stops routing to it; traffic shifts silently to the healthy replicas.
</Define>

<ConceptGrid cols={3}>
  <ConceptCard label="Reverse proxy">Sits in front of your service. Terminates TLS, handles HTTP/2, adds security headers, optionally caches. nginx, Caddy, and Envoy are the common choices.</ConceptCard>
  <ConceptCard label="Load balancer">Distributes requests across multiple backend replicas. In Kubernetes, the Service and ingress controller fill this role. In front of Kubernetes, a cloud load balancer (AWS ALB, GCP Load Balancer) routes traffic to the cluster nodes.</ConceptCard>
  <ConceptCard label="TLS termination">The reverse proxy holds the TLS certificate and handles the handshake. Your Go service receives plain HTTP — no TLS code required. Caddy automates certificate provisioning via Let's Encrypt; nginx needs explicit cert config.</ConceptCard>
  <ConceptCard label="L4 vs L7">Layer 4 (TCP) load balancers route based on IP/port — fast, protocol-agnostic. Layer 7 (HTTP) load balancers route based on HTTP headers, paths, hostnames — smarter routing but more CPU overhead. Kubernetes ingress controllers are L7.</ConceptCard>
  <ConceptCard label="Health-based routing">A load balancer only routes to backends that are passing health checks. A pod that's starting up, or that's overwhelmed, is quietly removed from rotation until it recovers.</ConceptCard>
  <Gotcha>Your Go service must bind to 0.0.0.0 (all interfaces) inside a container, not 127.0.0.1. Binding to localhost means only processes inside the container can connect — the load balancer, arriving over the container network, will be silently refused.</Gotcha>
</ConceptGrid>

**On the job:** Your Go service must bind to `0.0.0.0` (all interfaces) inside a container, not `127.0.0.1`. Binding to loopback means only processes inside the same container can connect — the load balancer, arriving over the container network, will be silently refused. This mistake shows up as a `502 Bad Gateway` with no obvious cause.

### Caddy as a reverse proxy (minimal config)

For smaller deployments — or local staging — Caddy is the fastest way to get HTTPS with automatic certificates:

```
# Caddyfile
ledger.example.com {
    reverse_proxy ledger-service:8080 {
        health_uri      /readyz
        health_interval 10s
    }
}
```

Caddy handles the Let's Encrypt certificate dance automatically. The `health_uri` directive tells Caddy to hit `/readyz` every 10 seconds; any backend that fails is removed from rotation. Your Go service just needs to expose the endpoint — which we'll wire up in the Kubernetes section.

### Writing a Go reverse proxy? Use `Rewrite`, not `Director` (Go 1.20+)

Most teams use nginx, Caddy, or Envoy as their reverse proxy — external tools, not Go code. But when you need a sidecar proxy, a gateway, or an API fan-out layer written in Go, the standard library's `net/http/httputil.ReverseProxy` is the tool.

Since **Go 1.20**, the `Director` field on `ReverseProxy` is deprecated in favour of `Rewrite` (added alongside the `ProxyRequest` type that same release). The difference matters for security:

- `Director` mutates the outbound `*http.Request` after cloning. It's easy to accidentally forward inbound headers (like `X-Forwarded-For`) that an attacker controls, or to forget to strip `Authorization` before proxying to a downstream service.
- `Rewrite` receives a `*httputil.ProxyRequest` that exposes both `In` (the original, read-only inbound request) and `Out` (the outbound request you mutate). The split makes it explicit which headers come from the client and which you're setting yourself.

```go
// Go 1.20+ — use Rewrite, not Director
// upstream is a *url.URL parsed at startup, e.g.:
//   upstream, _ = url.Parse("http://ledger-service:8080")
proxy := &httputil.ReverseProxy{
    Rewrite: func(pr *httputil.ProxyRequest) {
        // Set the target for the Meridian ledger-service upstream.
        pr.SetURL(upstream)
        // Copy safe headers from inbound to outbound explicitly.
        pr.SetXForwarded()
        // Strip any Authorization the client sent — downstream
        // uses its own service-to-service token.
        pr.Out.Header.Del("Authorization")
    },
}
```

If your codebase still uses `Director`, it continues to compile — but the API documentation marks it deprecated, and editors/static analyzers may surface that warning. The migration is mechanical: move the mutation from `Director` into `Rewrite`, replacing `req *http.Request` with `pr.Out`.

<Callout kind="tip" title="Director → Rewrite migration is safe to do incrementally">

If you have a large codebase that uses `Director`, you can migrate one proxy at a time. For each `ReverseProxy`, set **either** `Director` or `Rewrite`; the standard library documents that at most one may be set.

</Callout>

## Kubernetes from First Principles

### The problem Kubernetes solves

You have a Docker image. You have a server. `docker run` gets it running. Now: what happens when the process crashes? What happens when you push a new image? What happens when traffic triples and you need four copies instead of one?

`docker run` alone answers none of these questions. Kubernetes is the answer to all of them — it's a **container orchestrator**: a system that takes your declared intent ("I want three replicas of this image, always running, with these resource limits") and makes it reality, healing itself when reality drifts from intent.

Let's define every term from the bottom up.

<Define term="Pod" since="Deployment & Infra: CI/CD + Kubernetes (this chapter)">
A **pod** is the smallest deployable unit in Kubernetes: one or more containers that share a network interface (same IP address) and storage. Usually one container per pod. Pods are **ephemeral** — they crash, get killed during deploys, and get replaced. Their IP addresses change every time. Never SSH into a pod and patch it; always update the image and let Kubernetes replace it.
</Define>

<Define term="Deployment" since="Deployment & Infra: CI/CD + Kubernetes (this chapter)">
A **Deployment** manages a set of identical pods. You declare intent: "I want 3 replicas of this image, with these resource limits, using a rolling update strategy." The Deployment controller watches the cluster and continuously reconciles reality toward that intent — if a pod crashes, a replacement is created within seconds. A Deployment is the standard way to run a stateless service like Meridian's ledger service.
</Define>

<Define term="Service (Kubernetes)" since="Deployment & Infra: CI/CD + Kubernetes (this chapter)">
A **Service** is a stable network endpoint in front of a set of pods. Because pod IPs change every time a pod is replaced, nothing should talk directly to pod IPs. A Service gets a stable `ClusterIP` and DNS name (`ledger-service.production.svc.cluster.local`) that always resolves to healthy, ready pods. The Service is what the load balancer routes to — not the pods directly.
</Define>

<Define term="Ingress" since="Deployment & Infra: CI/CD + Kubernetes (this chapter)">
An **Ingress** is an L7 (HTTP) routing rule: "traffic for `ledger.example.com/api` → Service `ledger-service`." An Ingress is just a config object; an **Ingress Controller** (nginx, Traefik, Envoy) actually implements it by configuring its proxy layer. The Ingress controller is where TLS terminates — it holds the certificate, handles the handshake, and forwards plain HTTP to your pods.
</Define>

### The Kubernetes object hierarchy

<ConceptGrid cols={3}>
  <ConceptCard label="Pod">The smallest deployable unit. A pod wraps one or more containers that share a network namespace (same IP) and storage. Usually one container per pod. Pods are ephemeral — they die and are replaced; never SSH into a pod and patch it.</ConceptCard>
  <ConceptCard label="Deployment">Manages a set of identical pods. You tell it: image, replica count, update strategy. It creates a ReplicaSet underneath it. Delete a pod — the Deployment notices and creates a replacement. The controller loop never stops watching.</ConceptCard>
  <ConceptCard label="Service">A stable network endpoint that routes to a set of pods. Pods come and go; their IPs change. A Service gets a stable ClusterIP (and optional DNS name) that always routes to healthy pods matching its selector.</ConceptCard>
  <ConceptCard label="Ingress">An L7 routing rule: "traffic for host ledger.example.com, path /api → Service ledger-service". An Ingress is just a config object; an Ingress Controller (nginx, Traefik, Envoy) actually implements it.</ConceptCard>
  <ConceptCard label="ConfigMap & Secret">Configuration and sensitive values, injected into pods as environment variables or mounted files. Secrets are base64-encoded in etcd (not encrypted by default — use a KMS provider for real encryption at rest). Never hardcode config in images.</ConceptCard>
  <ConceptCard label="Namespace">A virtual cluster partition. Team or environment isolation. Resources in one namespace can't accidentally stomp resources in another. Production and staging in the same cluster? Different namespaces.</ConceptCard>
  <Gotcha>A Kubernetes Secret is NOT encrypted by default — it is base64-encoded, which is trivially decoded. In production, enable encryption at rest for etcd, or use an external secrets operator (External Secrets Operator + Vault/AWS Secrets Manager) to manage secret lifecycle properly.</Gotcha>
</ConceptGrid>

### Liveness vs readiness probes

**On the job:** Mis-configuring probes is one of the most common sources of production incidents in Kubernetes. A liveness probe that's too aggressive restarts healthy pods under load; a readiness probe that always passes routes traffic to pods that aren't actually ready. Get the semantics right — this section is the part of Kubernetes worth genuinely understanding.

<Define term="Liveness probe vs readiness probe">
A **liveness probe** asks: "Is this container still alive?" Kubernetes calls it on a timer. If it fails `failureThreshold` times, the container is killed and restarted. Use it to detect unrecoverable states: a deadlocked goroutine, a panicked process that somehow kept its PID. A **readiness probe** asks: "Is this container ready to receive traffic?" Failure removes the pod from the load balancer rotation — no new requests are sent — but the container keeps running. Use it for startup sequencing (not ready until the DB pool is open), temporary degradation (DB is slow, back off), and graceful drain (fail readiness before shutdown to finish in-flight requests). Getting these wrong is one of the most common sources of production incidents in Kubernetes.
</Define>

This is the distinction that separates engineers who understand Kubernetes from engineers who copy-paste manifests and hope.

**Liveness probe** (`/healthz`): "Is this container still alive, or has it deadlocked?" If this probe fails `failureThreshold` times, Kubernetes kills and restarts the container. Use this to detect unrecoverable states — a deadlocked goroutine, a panicked process that somehow kept its PID.

**Readiness probe** (`/readyz`): "Is this container *ready to receive traffic*?" If this probe fails, Kubernetes removes the pod from the Service's endpoints — the load balancer stops sending it requests. The container keeps running; it just isn't in rotation. This is used for: startup (the pod is booting, not ready yet), temporary degradation (the DB connection pool is exhausted, slow down), or graceful drain (signal readyz to fail before termination so you finish in-flight requests before the pod is killed).

The `/healthz` and `/readyz` endpoints are simple HTTP handlers in your Go service. Here's the implementation, wired to a real database ping:

```go
package main

import (
	"database/sql"
	"log/slog"
	"net/http"
	"net/http/httptest"
)

// newProbeHandlers returns liveness and readiness HTTP handlers.
// db may be nil (useful in tests / before the pool is opened).
func newProbeHandlers(db *sql.DB) (liveness, readiness http.HandlerFunc) {
	liveness = func(w http.ResponseWriter, r *http.Request) {
		// /healthz: prove the process is alive and not deadlocked.
		// Keep it dead-simple — a deadlocked process can't even reach here.
		w.WriteHeader(http.StatusOK)
		_, _ = w.Write([]byte("ok"))
	}

	readiness = func(w http.ResponseWriter, r *http.Request) {
		// /readyz: prove we're ready to serve traffic.
		// If the DB is unreachable, we're not ready — tell the LB to stop sending us work.
		if db != nil {
			if err := db.PingContext(r.Context()); err != nil {
				slog.Error("readiness check failed", "err", err)
				http.Error(w, "db unavailable", http.StatusServiceUnavailable)
				return
			}
		}
		w.WriteHeader(http.StatusOK)
		_, _ = w.Write([]byte("ready"))
	}

	return liveness, readiness
}

func main() {
	// In the real service this is a real *sql.DB.
	// Here we pass nil so the probe logic is demonstrable without a database.
	liveness, readiness := newProbeHandlers(nil)

	mux := http.NewServeMux()
	mux.HandleFunc("/healthz", liveness)
	mux.HandleFunc("/readyz", readiness)

	// Demonstrate both probes with httptest — no real server needed.
	for _, tc := range []struct {
		path string
		h    http.HandlerFunc
	}{
		{"/healthz", liveness},
		{"/readyz", readiness},
	} {
		req := httptest.NewRequest(http.MethodGet, tc.path, nil)
		rr := httptest.NewRecorder()
		tc.h(rr, req)
		slog.Info("probe response", "path", tc.path, "status", rr.Code, "body", rr.Body.String())
	}
}
```

### Resource requests and limits

Every container in a Deployment should declare `resources.requests` and `resources.limits`.

**Requests** are what the scheduler uses when placing a pod on a node. A node with 2 CPU cores available can fit 20 pods that each `request` 100m CPU. Requests are a *reservation*, not a hard cap.

**Limits** are the enforcement ceiling. A container that exceeds its memory limit is OOM-killed. A container that exceeds its CPU limit is throttled (not killed). Set limits higher than requests to allow bursting, but don't omit them — a runaway pod can starve its node neighbors.

```yaml
resources:
  requests:
    cpu: "100m"       # 0.1 of a CPU core; 1000m = 1 core
    memory: "128Mi"   # 128 mebibytes
  limits:
    cpu: "500m"
    memory: "256Mi"
```

**On the job:** Set both requests and limits on every container in production. A pod with no requests gets scheduled on any node regardless of actual availability; a pod with no memory limit can OOM-kill its neighbors. The few minutes it takes to tune these numbers can prevent an incident that takes hours to debug.

<Callout kind="note" title="Go 1.25: container-aware GOMAXPROCS">

Before Go 1.25, a Go process inside a CPU-limited pod would read the *host* machine's CPU count as its `GOMAXPROCS`. A pod with a `500m` CPU limit on a 64-core node could create 64 Ps, adding scheduling overhead while the kernel throttled the container to half a CPU. The workaround was the third-party `uber-go/automaxprocs` library.

**As of Go 1.25**, the Go runtime reads cgroup CPU limits directly and folds them into the default `GOMAXPROCS` automatically. The runtime rounds fractional CPU quotas up and, unless CPU affinity or logical CPU count is lower, will not set the default below 2. That means a pod limited to `500m` typically gets `GOMAXPROCS=2`, not 1; a pod limited to `2000m` gets `GOMAXPROCS=2`. No library needed; no manual override needed. Set your CPU limits confidently — the scheduler chapter in Part 2 covers the GMP model in depth.

</Callout>

### Horizontal Pod Autoscaler

<Define term="Horizontal autoscaling (HPA)">
**Horizontal autoscaling** means adding or removing replicas (instances) of your service in response to load — scaling *out* (more pods) rather than *up* (bigger pods). Kubernetes' **HorizontalPodAutoscaler (HPA)** watches a metric — CPU utilization, memory, or a custom signal — and adjusts the Deployment's replica count automatically. When Meridian's ledger service sees a payment surge at end-of-month, the HPA adds replicas; when traffic drops overnight, it removes them. The minimum replica count ensures you're never down to a single point of failure even at baseline load.
</Define>

When traffic spikes, you don't want to manually scale. The HPA watches a metric (CPU, memory, or custom) and adjusts the Deployment's replica count automatically:

```yaml
# k8s/hpa.yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: ledger-service-hpa
  namespace: production
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: ledger-service
  minReplicas: 3
  maxReplicas: 10
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70   # scale up when avg CPU > 70%
```

When average CPU across pods exceeds 70%, the HPA adds replicas (up to 10). When it drops back down, it removes replicas (down to 3). The minimum of 3 ensures we're never down to a single point of failure.

<UnderTheHood title="The Kubernetes control loop — how a Deployment converges">

Kubernetes is a reconciliation engine. Every controller runs a tight loop:

1. **Observe** the current state of the world (what pods are actually running, with what images, passing what probes).
2. **Compare** to the desired state (what the Deployment spec says).
3. **Act** to close the gap (create pods, delete pods, update pod specs).

The Deployment controller is just one of many controllers doing this simultaneously. The ReplicaSet controller, the Endpoints controller, kube-proxy — they all watch for changes to resources in etcd and reconcile. This is called the **level-triggered** model (react to the current state) as opposed to edge-triggered (react to events). It means Kubernetes is self-healing by design: even if a message is dropped, the next reconcile loop will catch the drift.

The scheduler watches for pods in `Pending` state (no node assigned), scores nodes by available resources, taints/tolerations, and affinity rules, then binds the pod to the best-fit node. The kubelet on that node watches for pods assigned to it and actually starts the containers. The container runtime (containerd) pulls the image if not cached.

`kubectl apply` doesn't *do* the deploy directly — it patches the Deployment object in etcd. The controller loop notices the change and does the work. This is why `kubectl apply` is fast: it's a write to a database, not a remote procedure that waits for the deploy to complete.

As of Go 1.26 and Kubernetes 1.30+, the relevant internal machinery is pure Go — the controllers, the scheduler, the kubelet. Reading the Kubernetes source is a masterclass in real-world Go architecture.

</UnderTheHood>

## Rolling Updates & Rollbacks

<Define term="Rolling update">
A **rolling update** replaces old pods with new ones incrementally, never taking the whole service down at once. Two parameters control the pace: **`maxSurge`** — how many extra pods can exist above the desired count during the update (controls resource overhead); **`maxUnavailable`** — how many pods can be removed before a replacement is ready (set to 0 for zero-downtime). The key guarantee: a new pod is only added to the load balancer when its readiness probe passes. A broken new pod that never becomes ready stalls the rollout — but the old pods keep serving. Nothing breaks for users.
</Define>

**On the job:** The most common cause of deploy-induced downtime in Go services isn't bad code — it's a readiness probe that passes before the service is genuinely ready. If your probe just checks that the HTTP port is open, you're routing traffic to pods that haven't connected to the database yet. For Meridian's ledger service, "ready" means the DB pool is up, the connection is validated, and the service can actually execute a transfer.

This is the centerpiece — the mechanism that makes zero-downtime deploys possible. Understand this fully and you'll never sweat a production deploy again.

### What a rolling update does

When you push a new image tag, Kubernetes doesn't restart all pods at once (that would take down the service). It rolls through them: bring up new pods, wait for them to pass readiness, then take down old pods. The `maxSurge` and `maxUnavailable` settings control the pace.

With our settings (`maxSurge: 1`, `maxUnavailable: 0`):
- Never reduce the available pod count below 3 (the desired replica count)
- Allow up to 4 pods total during the update (3 desired + 1 surge)

### The critical guarantee: readiness gating

The key to zero-downtime is this: **a pod is only added to the load balancer rotation when its readiness probe passes.** Until then, the old pods absorb all traffic.

If your new pods are crashing, their readiness probes never pass. The old pods stay in rotation. The rollout hangs. The CI job (which runs `kubectl rollout status --timeout=300s`) reports failure. No traffic was disrupted. You fix the bug and push again.

This is why the readiness probe implementation matters — it needs to reflect *genuine* readiness (database connected, cache warm, ready to process transactions) not just "the HTTP server started."

### Performing a rollout

```bash
# Update the image — triggers rolling update
kubectl set image deployment/ledger-service \
```

### Rolling back

The rollout history is your undo stack. One command:

```bash
# Roll back to the previous revision
kubectl rollout undo deployment/ledger-service -n production

# Roll back to a specific revision
kubectl rollout undo deployment/ledger-service --to-revision=1 -n production
```

Rollback performs the same rolling mechanism in reverse — it's just a rolling update to the previous image. Because `maxUnavailable: 0`, the rollback is also zero-downtime.

<UnderTheHood title="How readiness gating actually prevents traffic to not-ready pods">

When a pod's readiness probe fails (or before it has passed for the first time), the Endpoints controller removes that pod's IP from the `Endpoints` object associated with the Service.

kube-proxy watches the `Endpoints` object. When an IP is removed, kube-proxy updates the iptables/eBPF rules on every node in the cluster. After propagation (typically under 1 second), no new connections are routed to the not-ready pod.

The critical subtlety: **there is a propagation window**. Between the pod's readiness probe failing and kube-proxy updating its rules, a fraction of a second of traffic can still arrive at the pod. This is why graceful shutdown matters:

1. The pod receives `SIGTERM`.
2. It immediately fails its `/readyz` probe (returning 503).
3. It keeps its HTTP server alive for `terminationGracePeriodSeconds` (default 30s), finishing in-flight requests.
4. After the grace period (or when it exits cleanly), Kubernetes sends `SIGKILL`.

Set `terminationGracePeriodSeconds` to comfortably exceed your longest expected request duration. For the ledger service, 30 seconds is generous. For streaming endpoints, you might need more.

The `maxSurge` / `maxUnavailable` math is applied at the ReplicaSet level. With `maxSurge: 1` and `maxUnavailable: 0` on a 3-replica Deployment: the controller maintains at least 3 ready pods at all times, and creates at most 4 total pods (3 desired + 1 surge). The exact pod lifecycle: create new → wait for ready → terminate one old → repeat.

</UnderTheHood>

### The external-dns and cert-manager operators

In production, you don't manually create DNS records or TLS secrets. Two operators do it for you:

**cert-manager** watches for Ingress objects with `tls:` configuration and automatically provisions and rotates TLS certificates from Let's Encrypt (or your internal CA). Zero manual certificate management.

```go
				return
			}
		}
		w.WriteHeader(http.StatusOK)
		_, _ = w.Write([]byte("ready"))
	}

	return liveness, readiness
}
```

The nil check on `db` makes the function testable without a real database. In production, a nil DB would be a startup bug — but having the probe behave correctly regardless means your test suite doesn't need a live Postgres just to test the probe endpoints.

</Solution>

</Exercise>

<Exercise n={2} title="Identify the CI pipeline mistake" level="easy">

This GitHub Actions workflow has a critical mistake. What is it, and what does it risk?

```yaml
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: go test ./...

  deploy:
    runs-on: ubuntu-latest
    steps:
      - run: kubectl set image deployment/ledger-service ledger-service=registry/ledger-service:latest
```

<Solution>

Two mistakes:

1. **No `needs: test`** on the deploy job. Both jobs run concurrently. The deploy can complete before — or even instead of — the test job. A broken commit ships to production.

2. **`:latest` tag** is mutable and untraceable. Every deploy is tagged identically; you can't roll back to a specific commit, and nodes may pull different images if `latest` changed between their cache times.

Fix: add `needs: test` to the deploy job, and tag the image with `${{ github.sha }}`.

</Solution>

</Exercise>

<Exercise n={3} title="Write the Deployment strategy for zero-downtime" level="medium">

Write the `strategy` block for a Deployment with 4 replicas that satisfies: always at least 4 pods serving traffic during a rollout, at most 5 pods total. Explain why `maxUnavailable: 0` is the key setting.

<Solution>

```yaml
strategy:
  type: RollingUpdate
  rollingUpdate:
    maxSurge: 1          # up to 5 pods total (4 desired + 1 surge)
    maxUnavailable: 0    # never reduce below 4 serving
```

`maxUnavailable: 0` is the key setting because it means Kubernetes will not terminate any old pod until a new pod has passed its readiness probe and joined the Service endpoint set. The serving count never drops below the desired replica count — zero-downtime is guaranteed as long as the readiness probe actually reflects genuine readiness.

`maxSurge: 1` limits the overshoot to one extra pod (to control resource usage on the nodes during updates).

</Solution>

</Exercise>

<Exercise n={4} title="Trace a readiness probe failure during rollout" level="medium">

During a rolling update of the ledger-service (3 replicas, `maxUnavailable: 0`, `maxSurge: 1`), the new v2 image has a bug: it always returns 500 from `/readyz`. Walk through what Kubernetes does. Is there any downtime? What does the CI pipeline observe?

<Solution>

1. The controller creates `pod-v2-a` (4 pods total: 3x v1 + 1x v2).
2. `pod-v2-a`'s `/readyz` returns 500. It fails readiness. The Endpoints controller never adds it to the Service. 0 traffic goes to `pod-v2-a`.
3. The controller waits. `maxUnavailable: 0` means it cannot terminate any v1 pod until the new pod is ready. It never is.
4. After `failureThreshold` * `periodSeconds` (e.g. 2 * 5 = 10 seconds), the pod is marked not-ready but stays running.
5. The rollout stalls. `kubectl rollout status` blocks.
6. After the CI timeout (`--timeout=300s`), `kubectl rollout status` exits non-zero. The CI pipeline job fails.
7. The 3 v1 pods continue serving all traffic. **Zero downtime.** The old pods were never touched.
8. The engineer sees the CI failure, investigates (checks `kubectl describe pod pod-v2-a` and `kubectl logs pod-v2-a`), fixes the bug, pushes again.

This is the readiness-gating guarantee in action. A broken deploy cannot displace healthy pods.

</Solution>

</Exercise>

<Exercise n={5} title="Write a ConfigMap and reference it in a container" level="hard">

Write a `ConfigMap` for the ledger service that holds `db_host: postgres.production.svc.cluster.local` and `log_level: info`. Then write the container spec section that injects `DB_HOST` from the ConfigMap and `DB_PASSWORD` from a Secret named `ledger-secrets` with key `db_password`. Include the full `env:` block.

<Solution>

```yaml
# k8s/configmap.yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: ledger-config
  namespace: production
data:
  db_host: "postgres.production.svc.cluster.local"
  log_level: "info"
```

```yaml
# In the Deployment's container spec:
env:
  - name: DB_HOST
    valueFrom:
      configMapKeyRef:
        name: ledger-config
        key: db_host
  - name: LOG_LEVEL
    valueFrom:
      configMapKeyRef:
        name: ledger-config
        key: log_level
  - name: DB_PASSWORD
    valueFrom:
      secretKeyRef:
        name: ledger-secrets
        key: db_password
```

Notice: config values from ConfigMap, sensitive values from Secret. Never put the database password in a ConfigMap — it is not encrypted. And never hardcode either in the container image — configuration belongs in the environment, not the binary. This is the 12-factor app rule, and Kubernetes is built around it.

</Solution>

<Recap>

You just built the full picture — from `git push` to production pods behind Meridian's ingress and load balancer:

- **CI/CD pipelines** enforce quality gates: test → vet → lint → race → build → push → deploy. Every stage is a gate; failure stops the pipeline before code reaches users. Tag images with the Git SHA, never `latest`. The build stage produces a fully static binary (`CGO_ENABLED=0`) from the recipe in the Building & Shipping Binaries chapter.
- **Reverse proxies** (nginx/Caddy) terminate TLS at the edge and forward plain HTTP to your Go service. **Load balancers** distribute requests across replicas and route around unhealthy ones using health checks. Your Go service never handles TLS. If you write a Go reverse proxy, use `httputil.ReverseProxy`'s `Rewrite` field (Go 1.20+) — `Director` is deprecated.
- **Kubernetes** is a reconciliation engine. A Deployment maintains your desired replica count. A Service is a stable endpoint in front of ephemeral pods. An Ingress is an L7 routing rule. ConfigMaps hold config; Secrets hold sensitive values (but are not encrypted by default — use a secrets operator in production).
- **Liveness probes** (`/healthz`) detect deadlocked processes and trigger restarts. **Readiness probes** (`/readyz`) gate traffic — a pod isn't added to the load balancer until it passes readiness. This is the mechanism that makes zero-downtime deploys possible.
- **Rolling updates** (`maxSurge: 1`, `maxUnavailable: 0`) bring up new pods, wait for readiness, then remove old ones. A broken deploy stalls (the new pods never pass readiness) without disrupting the old pods. Rollback is one command.
- **Container-aware GOMAXPROCS** (Go 1.25): the runtime now folds cgroup CPU limits into the default `GOMAXPROCS`, with documented rounding and minimum behavior. No more `uber-go/automaxprocs` workaround for Go 1.25+ services.
- **The cloud chain**: Ingress → cloud LB (provisioned automatically) → DNS record → TLS cert (via cert-manager). external-dns and cert-manager automate the toil.

</Recap>
