Chapters 4 and 5 built Meridian's event handling by hand: an outbox relay, an inbox, consumer groups, acknowledgements, retries, a dead-letter stream. Every one of those was a loop of Redis calls, and every service that handles events needs the same loops again. **Watermill** is the Go library that packages them: one interface for publishing and subscribing over any transport, a router that runs handlers and acknowledges messages, middleware for retries, poison queues and panics, a typed CQRS layer, and the outbox as a component.

This chapter rebuilds Meridian's receipts flow on Watermill 1.5.3 and measures what each piece does, including the places where it quietly does less than its name suggests: a retry hook that doesn't fire on every retry, middleware whose order changes the outcome, and a deduplicator that forgets on restart.

## Pub & Sub

*Stop 1 of 6.*

### Step 1: the message

Everything in Watermill moves as a `*message.Message`: a **UUID** (unique per message), **metadata** (string key-value pairs that travel with it, like HTTP headers: a correlation id, a trace id, the reason a message was poisoned), and a **payload** of bytes. Watermill doesn't care what the payload is; marshalling is yours, or the CQRS component's (stop 5). A message also carries `Ack()` and `Nack()`: the subscriber's way of telling the broker it's done (chapter 5, stop 4), or that it should be redelivered.

### Step 2: two interfaces

Every transport implements two interfaces: `message.Publisher` (`Publish(topic, messages...)`) and `message.Subscriber` (`Subscribe(ctx, topic)` returning a channel of messages). There are implementations for Kafka, NATS, RabbitMQ, Google Pub/Sub, AWS SNS/SQS, Redis streams, PostgreSQL and MySQL, and `GoChannel`, an in-memory one for tests and single-process wiring. So a handler written against them runs on any of those. Here the receipts handler runs on `GoChannel` and then on a Redis stream, unchanged:

```go noverify
// main.go, lines 20–43
// receipts turns a payment.succeeded event into a receipt.requested event.
// It knows nothing about where either comes from or goes to.
func receipts(m *message.Message) ([]*message.Message, error) {
	out := message.NewMessage(watermill.NewUUID(), []byte(`{"template":"receipt","payment":`+string(m.Payload)+`}`))
	return []*message.Message{out}, nil
}

func main() {
	logger := watermill.NopLogger{}
	mem := gochannel.NewGoChannel(gochannel.Config{Persistent: true}, logger)
	run("GoChannel (in memory)", mem, mem)

	rdb := redis.NewClient(&redis.Options{Addr: "127.0.0.1:6395"})
	rdb.Del(context.Background(), "wm:payments.succeeded", "wm:receipts.requested")
	pub, err := redisstream.NewPublisher(redisstream.PublisherConfig{Client: rdb}, logger)
	if err != nil {
		log.Fatal(err)
	}
	sub, err := redisstream.NewSubscriber(redisstream.SubscriberConfig{Client: rdb, ConsumerGroup: "receipts"}, logger)
	if err != nil {
		log.Fatal(err)
	}
	run("Redis stream", pub, sub)
}
```

```text
GoChannel (in memory): 1000 payments in, 1000 receipt requests out, 16ms
                       last one: uuid 80388d46…, correlation_id "checkout-999", payload {"template":"receipt","payment":{"n":999}}
Redis stream:          1000 payments in, 1000 receipt requests out, 2.116s
                       last one: uuid c6898aea…, correlation_id "checkout-999", payload {"template":"receipt","payment":{"n":999}}
```

Same handler, same 1,000 payments, same 1,000 receipt requests. The in-memory run took 16 ms; Redis took 2.1 s, because this Redis instance `fsync`s every write to disk (chapter 4 gave it `appendfsync always` so a restart loses nothing). And the correlation id set on the payment, `checkout-999`, came out on the receipt request: the `CorrelationID` middleware copies it from each consumed message to the messages its handler produces, so one id follows a customer's checkout through every service it touches.

## The Router

*Stop 2 of 6.*

### Step 1: what the router does

A **router** is the loop every consumer from chapter 5 wrote by hand: subscribe to a topic, take each message, call the handler, **acknowledge** it if the handler returns `nil` and **nack** it (ask for redelivery) if it returns an error, publish whatever messages the handler produced, and shut down cleanly. `AddHandler` wires a handler that produces messages (like `receipts` above); `AddConsumerHandler` wires one that only consumes.

### Step 2: kill it

The receipts service is a router on a Redis consumer group. Each receipt takes 5 ms, and the subscriber is configured to take over messages another consumer has held for more than a second:

```go noverify
// main.go, lines 23–44
	sub, err := redisstream.NewSubscriber(redisstream.SubscriberConfig{
		Client:        rdb,
		ConsumerGroup: "receipts",
		Consumer:      *name,
		// Take over messages another consumer has held for a second.
		ClaimInterval: 500 * time.Millisecond,
		MaxIdleTime:   time.Second,
	}, watermill.NopLogger{})
	if err != nil {
		log.Fatal(err)
	}
	router, err := message.NewRouter(message.RouterConfig{}, watermill.NopLogger{})
	if err != nil {
		log.Fatal(err)
	}
	var last atomic.Int64 // when the last receipt was sent, in Unix ns
	last.Store(time.Now().UnixNano())
	router.AddConsumerHandler("receipts", "wm:crash", sub, func(m *message.Message) error {
		time.Sleep(5 * time.Millisecond) // send the receipt
		last.Store(time.Now().UnixNano())
		return rdb.HIncrBy(m.Context(), "wm:crash:receipts", string(m.Payload), 1).Err()
	})
```

2,000 events; the service is killed with `SIGKILL` after 2 seconds, and a second instance, `r2`, finishes the stream. Three runs:

```text
run 1: r1 killed with 3 pending; after r2: 2000 of 2000 events got a receipt, 1 got two, 0 pending
run 2: r1 killed with 3 pending; after r2: 2000 of 2000 events got a receipt, 1 got two, 0 pending
run 3: r1 killed with 3 pending; after r2: 2000 of 2000 events got a receipt, 1 got two, 0 pending
```

Each time: 3 messages pending when `r1` died, all claimed by `r2`, **2,000 of 2,000 receipts sent**, and exactly **one** sent twice. Compare chapter 5's worker, which acknowledged a batch of 50 at the end: 2 to 23 duplicates per crash. The router acknowledges **each message as soon as its handler returns**, so at most the handful in flight can be redelivered, and only one of those had actually finished. Watermill doesn't make handling exactly-once (nothing can, chapter 4, stop 4), but it keeps the window small, and the rest is still the inbox's job.

## Middleware

*Stop 3 of 6.*

### Step 1: wrapping handlers

A Watermill **middleware** is a function that takes a handler and returns a new one, the same shape as HTTP middleware in part 1: it can run code before and after the handler, change its result, or not call it at all. The library ships the ones every consumer needs; three matter most here:

- `Retry`: call the handler again on error, with exponential backoff, up to `MaxRetries` times.
- `PoisonQueue`: when the handler fails, publish the message to a poison topic (with the error in its metadata) and report success, so the broker stops redelivering it. Chapter 5's dead-letter stream, packaged.
- `Recoverer`: turn a panic in the handler into an error, so one bad message can't crash the service.

### Step 2: order changes the outcome

Middleware wraps in the order it's added: **the first one added is the outermost**. The receipts handler fails like real handlers do (every 10th event times out once, event 37 always fails, event 55 panics once), and runs under the same three middleware in two orders:

```go noverify
// main.go, lines 38–73
	poison, err := middleware.PoisonQueue(pubsub, "payments.poison")
	if err != nil {
		log.Fatal(err)
	}
	retry := middleware.Retry{MaxRetries: 3, InitialInterval: 10 * time.Millisecond, Multiplier: 2}.Middleware
	// The first middleware added is the outermost.
	router.AddMiddleware(middleware.CorrelationID)
	if order == "poison, then retry" {
		router.AddMiddleware(poison, retry)
	} else {
		router.AddMiddleware(retry, poison)
	}
	router.AddMiddleware(middleware.Recoverer)

	var mu sync.Mutex
	attempts := map[int]int{}
	var sent, panics atomic.Int64
	router.AddConsumerHandler("receipts", "payments.succeeded", pubsub, func(m *message.Message) error {
		n, _ := strconv.Atoi(string(m.Payload))
		mu.Lock()
		attempts[n]++
		a := attempts[n]
		mu.Unlock()
		switch {
		case n == 37:
			return errors.New("merchant id m-37x does not exist")
		case n == 55 && a == 1:
			panics.Add(1)
			var receipt map[string]string
			receipt["to"] = "m55" // nil map: panics
		case n%10 == 0 && a == 1:
			return errors.New("mail provider: timeout")
		}
		sent.Add(1)
		return nil
	})
```

```text
poison, then retry: receipts sent  999, handler calls 1104, panics recovered 1, poisoned   1 (first: "merchant id m-37x does not exist")
retry, then poison: receipts sent  898, handler calls 1000, panics recovered 1, poisoned 102 (first: "mail provider: timeout")
```

**Poison outside retry** (the right order): 1,104 handler calls (1,000, plus a retry for each of the 100 timeouts and the panic, plus 3 retries of event 37), 999 receipts, and only event 37 poisoned, with its real error as the reason. **Retry outside poison**: the poison queue saw each first failure, published it and returned success, so the retry had nothing to retry. **102 events poisoned**, 101 of which would have succeeded a moment later. The `Recoverer` innermost made the panic an ordinary error that each attempt could retry.

(A detail found while measuring: `Retry`'s `OnRetryHook` is only called after a retry has itself failed, not on the first retry, so it can't be used to count retries. The program counts handler calls instead.)

## Deduplication

*Stop 4 of 6.*

### Step 1: the Deduplicator

Watermill has a `Deduplicator` middleware: it computes a key for each message and drops messages whose key it has seen within a time window. By default the key is an Adler-32 hash of the **payload** (not the UUID), and keys are kept in a map in the process's memory for a minute. Here it runs with SHA-256 and a ten-minute window, over the 3,126 entries stop 6's outbox run produced (3,000 payments, 126 of them published twice):

```go noverify
// main.go, lines 39–49
	// Remember a SHA-256 of each payload for 10 minutes, in this process's memory.
	repo, err := middleware.NewMapExpiringKeyRepository(10 * time.Minute)
	if err != nil {
		log.Fatal(err)
	}
	dedup := &middleware.Deduplicator{KeyFactory: middleware.NewMessageHasherSHA256(math.MaxInt64), Repository: repo}
	router.AddMiddleware(count, dedup.Middleware)
	router.AddConsumerHandler("receipts", "wm:payments.succeeded", sub, func(m *message.Message) error {
		handled.Add(1)
		return nil
	})
```

```text
dedup-1: 3126 delivered, 3000 handled
dedup-2: 3126 delivered, 3000 handled
```

The first run handled **3,000 of 3,126**: every duplicate dropped. The second run is a fresh process reading the same stream again, as a restarted consumer would after a crash: **3,000 handled again**. The map died with the first process, so every event looked new. The library's own documentation says the default repository "does not support distributed operations": two replicas don't share it either.

### Step 2: where it fits

So the Deduplicator is a cheap filter for duplicates that arrive close together, in one process. It isn't a guarantee. The guarantee is still chapter 4's inbox: the event id recorded in the same database transaction as the effect, which survives restarts and is shared by every replica. Two more cautions from the defaults: keying on the payload means two different payments with identical bytes are treated as one (key on an event id in the metadata instead, `NewMessageHasherFromMetadataField`), and a 32-bit hash will eventually collide.

## CQRS

*Stop 5 of 6.*

### Step 1: events and commands

**CQRS** (Command Query Responsibility Segregation) separates the parts of a system that change state from the parts that read it, and in messaging it comes with two kinds of message:

- An **event** says something **happened**: `PaymentSucceeded`. Any number of services may react, and the publisher doesn't know or care which.
- A **command** asks **one** service to **do** something: `SendReceipt`. Exactly one handler owns it.

Watermill's `cqrs` component makes both typed: you publish a Go struct on an `EventBus` or `CommandBus`, and handlers are ordinary functions of that struct, `func(ctx, *PaymentSucceeded) error`. It handles marshalling (JSON here), names (the struct name picks the topic), and wiring handlers to subscribers.

### Step 2: measured

```go noverify
// main.go, lines 19–31

// PaymentSucceeded is an event: something that happened.
type PaymentSucceeded struct {
	PaymentID string
	Merchant  string
	Amount    int64 // minor units
}

// SendReceipt is a command: something one service is asked to do.
type SendReceipt struct {
	PaymentID string
	Merchant  string
}
```

```go noverify
// main.go, lines 64–110

	// Every event handler gets its own consumer group, so each sees every event.
	events, err := cqrs.NewEventProcessorWithConfig(router, cqrs.EventProcessorConfig{
		GenerateSubscribeTopic: func(p cqrs.EventProcessorGenerateSubscribeTopicParams) (string, error) {
			return "cqrs.events." + p.EventName, nil
		},
		SubscriberConstructor: func(p cqrs.EventProcessorSubscriberConstructorParams) (message.Subscriber, error) {
			return redisstream.NewSubscriber(redisstream.SubscriberConfig{Client: rdb, ConsumerGroup: p.HandlerName}, logger)
		},
		Marshaler: marshaler,
	})
	if err != nil {
		log.Fatal(err)
	}
	commands, err := cqrs.NewCommandProcessorWithConfig(router, cqrs.CommandProcessorConfig{
		GenerateSubscribeTopic: func(p cqrs.CommandProcessorGenerateSubscribeTopicParams) (string, error) {
			return "cqrs.commands." + p.CommandName, nil
		},
		SubscriberConstructor: func(p cqrs.CommandProcessorSubscriberConstructorParams) (message.Subscriber, error) {
			return redisstream.NewSubscriber(redisstream.SubscriberConfig{Client: rdb, ConsumerGroup: "mailer"}, logger)
		},
		Marshaler: marshaler,
	})
	if err != nil {
		log.Fatal(err)
	}

	var dashboard, asked, mailed atomic.Int64
	var total atomic.Int64
	err = events.AddHandlers(
		cqrs.NewEventHandler("receipts", func(ctx context.Context, e *PaymentSucceeded) error {
			asked.Add(1)
			return commandBus.Send(ctx, &SendReceipt{PaymentID: e.PaymentID, Merchant: e.Merchant})
		}),
		cqrs.NewEventHandler("dashboard", func(ctx context.Context, e *PaymentSucceeded) error {
			dashboard.Add(1)
			total.Add(e.Amount)
			return nil
		}),
	)
	if err != nil {
		log.Fatal(err)
	}
	err = commands.AddHandlers(cqrs.NewCommandHandler("mailer", func(ctx context.Context, c *SendReceipt) error {
		mailed.Add(1)
		return nil
	}))
```

```text
published 500 PaymentSucceeded events
  receipts handler: 500 events, sent 500 SendReceipt commands
  dashboard handler: 500 events, merchant total $9995.00
  mailer (command handler): 500 receipts sent
```

500 `PaymentSucceeded` events: the **receipts** handler and the **dashboard** handler each got all 500, because each event handler has its own consumer group (chapter 5, stop 2: a topic). Receipts turned each into a `SendReceipt` command, and the **mailer**, the one command handler, sent 500 receipts: a queue. The code never mentions Redis streams, consumer groups or JSON; all of that is in the configuration.

## The Outbox

*Stop 6 of 6.*

### Step 1: the SQL publisher in a transaction

Chapter 4 wrote an outbox table and a relay by hand. Watermill has both parts. `watermill-sql` publishes messages as rows in a PostgreSQL table, and its publisher can be bound to an open database transaction (`TxFromPgx`), so the message's `INSERT` commits or rolls back with everything else in it. The `forwarder` component then wraps each message in an envelope that records its real destination topic, and a `Forwarder` process reads the table and publishes each message to that topic on the real broker:

```go noverify
// main.go, lines 43–90
	case "pay":
		for i := range *n {
			err := pgx.BeginFunc(ctx, db, func(tx pgx.Tx) error {
				t, _ := ledger.NewTransaction("card payment",
					ledger.Leg("assets:card-receivable", money.New(1999, money.USD)),
					ledger.Leg("liabilities:merchant:acme", money.New(-1911, money.USD)),
					ledger.Leg("revenue:fees", money.New(-88, money.USD)))
				id, err := ledger.PostTx(ctx, tx, t)
				if err != nil {
					return err
				}
				// A Watermill publisher bound to this transaction: its INSERT
				// commits or rolls back with the postings.
				sqlPub, err := wsql.NewPublisher(wsql.TxFromPgx(tx), wsql.PublisherConfig{SchemaAdapter: wsql.DefaultPostgreSQLSchema{}}, logger)
				if err != nil {
					return err
				}
				// The forwarder publisher wraps the real destination topic in
				// an envelope and writes it to the outbox table instead.
				pub := forwarder.NewPublisher(sqlPub, forwarder.PublisherConfig{ForwarderTopic: outboxTopic})
				return pub.Publish("wm:payments.succeeded",
					message.NewMessage(watermill.NewUUID(), fmt.Appendf(nil, `{"tx_id":%d,"n":%d}`, id, i)))
			})
			if err != nil {
				log.Fatal(err)
			}
		}
	case "forward":
		sub, err := wsql.NewSubscriber(wsql.BeginnerFromPgx(db), wsql.SubscriberConfig{
			SchemaAdapter:    wsql.DefaultPostgreSQLSchema{},
			OffsetsAdapter:   wsql.DefaultPostgreSQLOffsetsAdapter{},
			InitializeSchema: true,
		}, logger)
		if err != nil {
			log.Fatal(err)
		}
		out, err := redisstream.NewPublisher(redisstream.PublisherConfig{Client: redis.NewClient(&redis.Options{Addr: "127.0.0.1:6395"})}, logger)
		if err != nil {
			log.Fatal(err)
		}
		f, err := forwarder.NewForwarder(sub, out, logger, forwarder.Config{ForwarderTopic: outboxTopic})
		if err != nil {
			log.Fatal(err)
		}
		if err := f.Run(ctx); err != nil {
			log.Fatal(err)
		}
	}
```

### Step 2: kill the forwarder

```text
3000 payments committed, 3000 outbox rows, 3126 stream entries (3000 distinct payments)
```

**3,000 payments, 3,000 outbox rows, all 3,000 on the stream**, and 126 published twice: the messages the forwarder had published but not yet recorded as consumed when it was killed. The same at-least-once result as chapter 4's relay (52 duplicates in three kills there), from about fifty lines of configuration instead of a hand-written loop, and the duplicates are exactly what stop 4 fed to the Deduplicator.

## Exercises

These use the `wm` module, Redis and PostgreSQL from this chapter.

<Exercise n={1} title="Nack with a delay" level="easy">

In `receipts`, return an error for event 7 on its first delivery instead of sleeping. With `NackResendSleep: time.Second` in the subscriber config, how long until it's handled, and what does the handler see?

<Solution>

The router nacks the message, and watermill-redisstream waits `NackResendSleep` before delivering it to the handler again, so event 7 is handled about a second later. Its UUID and payload are the same; only the delivery is new. Without the Retry middleware, every failure costs a full resend cycle; with it, fast retries happen inside one delivery and the nack is the last resort.

</Solution>

</Exercise>

<Exercise n={2} title="Deduplicate by event id" level="easy">

Change stop 4's Deduplicator to key on a metadata field, `event_id`, set by the publisher. Why is that better than hashing the payload?

<Solution>

`KeyFactory: middleware.NewMessageHasherFromMetadataField("event_id")`. The key is then the event's identity, not its bytes: two distinct payments with identical payloads are no longer merged, and a re-serialised duplicate (a field order changed) is still recognised. It's the same reason chapter 4's inbox keyed on `event_id`.

</Solution>

</Exercise>

<Exercise n={3} title="A Redis-backed deduplicator" level="medium">

Implement `middleware.ExpiringKeyRepository` on Redis with `SET key 1 NX PX window`, and rerun stop 4's two processes. What changes, and what still isn't guaranteed?

<Solution>

`IsDuplicate` returns true when `SET NX` finds the key already set. The second process now handles 0: the memory survives restarts and is shared by replicas. What isn't guaranteed: the key is set before the handler runs, so a handler that crashes after the check leaves a key for an event that was never handled, and the retry is dropped as a duplicate. Record the key only after the effect, ideally in the effect's own transaction, which brings you back to the inbox.

</Solution>

</Exercise>

<Exercise n={4} title="Test with GoChannel" level="medium">

Write a Go test for the receipts handler that wires it to a `GoChannel`, publishes a payment, and asserts the `receipt.requested` message and its correlation id, without Redis.

<Solution>

Create `gochannel.NewGoChannel(gochannel.Config{Persistent: true}, logger)`, add the same `AddHandler` and the `CorrelationID` middleware to a router, `Run` it in a goroutine and wait for `Running()`, subscribe to `wm:receipts.requested`, publish a message with `middleware.SetCorrelationID`, and read one message from the subscription with a timeout. Assert the payload and `middleware.MessageCorrelationID`. The production handler, unchanged, is under test; only the transport differs.

</Solution>

</Exercise>

<Exercise n={5} title="Outbox without the envelope" level="hard">

Replace the forwarder with watermill-sql's plain subscriber on a `payments.succeeded` table and a router handler that republishes to Redis. What do you gain and lose compared with the Forwarder?

<Solution>

You gain control (transforming or filtering messages on the way, one table per topic, per-topic consumer groups), and lose the envelope's convenience: the Forwarder lets application code publish to any destination topic through one table and one process. Both are at-least-once for the same reason: publishing to Redis and recording the SQL consumer's offset are two writes to two systems. With several topics and one forwarder, the envelope also keeps one ordering of all outbox messages, which per-topic tables don't.

</Solution>

</Exercise>

<Lab
  title="Wrap It Right"
  archetype="fix-it"
  difficulty="guided"
  points={100}
  hintCost={10}
  verify="self-check"
  expect="ALL CHECKS PASS"
  objective="Fix three middleware and the chain that combines them: retry makes one call too few, the recoverer doesn't recover, and chain puts the poison queue inside the retries, so every first failure is dead-lettered. The chain must retry transient failures, turn panics into retryable errors, and dead-letter only what retries couldn't fix."
  starter={`package main

import (
	"errors"
	"fmt"
	"strconv"
)

type Message struct {
	ID       string
	Payload  string
	Metadata map[string]string
}

type Handler func(*Message) error

type Middleware func(Handler) Handler

// retry calls h again when it fails, up to max retries (so up to max+1
// calls in all), and returns the last error.
func retry(max int) Middleware {
	return func(h Handler) Handler {
		return func(m *Message) error {
			var err error
			for range max {
				if err = h(m); err == nil {
					return nil
				}
			}
			return err
		}
	}
}

// recoverer turns a panic in h into an error, so one bad message can't
// take the service down.
func recoverer(h Handler) Handler {
	return func(m *Message) error {
		return h(m)
	}
}

// poisonQueue sends a message whose handler failed to the dead-letter
// queue, with the error as Metadata["reason"], and reports success so the
// broker stops redelivering it.
func poisonQueue(publish func(*Message)) Middleware {
	return func(h Handler) Handler {
		return func(m *Message) error {
			if err := h(m); err != nil {
				m.Metadata["reason"] = err.Error()
				publish(m)
			}
			return nil
		}
	}
}

// chain wraps the receipts handler. A message should reach the poison
// queue only after its retries are used up, and a panic should be retried
// like any other failure.
func chain(h Handler, publish func(*Message), retries int) Handler {
	return retry(retries)(poisonQueue(publish)(recoverer(h)))
}

// ── below this line: do not edit ──

func main() {
	ok := true
	fail := func(f string, a ...any) { fmt.Printf("FAIL "+f+"\\n", a...); ok = false }

	attempts := map[int]int{}
	sent, panics := 0, 0
	receipts := func(m *Message) error {
		n, _ := strconv.Atoi(m.Payload)
		attempts[n]++
		switch {
		case n == 37:
			return errors.New("merchant id m-37x does not exist")
		case n == 55 && attempts[n] == 1:
			panics++
			var receipt map[string]string
			receipt["to"] = "m55" // nil map: panics
		case n%10 == 0 && attempts[n] == 1:
			return errors.New("mail provider: timeout")
		}
		sent++
		return nil
	}
	var dead []*Message
	h := chain(receipts, func(m *Message) { dead = append(dead, m) }, 3)

	crashed := 0
	for n := range 1000 {
		m := &Message{ID: fmt.Sprintf("evt-%d", n), Payload: strconv.Itoa(n), Metadata: map[string]string{}}
		func() {
			defer func() {
				if recover() != nil {
					crashed++ // the handler panicked through the middleware: the service would have died
				}
			}()
			if err := h(m); err != nil {
				fail("%s: the chain returned %v; after the poison queue nothing should reach the broker as a failure", m.ID, err)
			}
		}()
	}
	calls := 0
	for _, a := range attempts {
		calls += a
	}
	if crashed > 0 {
		fail("%d panics escaped the middleware", crashed)
	}
	if sent != 999 {
		fail("%d receipts sent, want 999 (every event except the poison one)", sent)
	}
	if calls != 1104 {
		fail("%d handler calls, want 1104 (1000 + 100 timeouts retried once + 1 panic retried once + 3 retries of event 37)", calls)
	}
	if len(dead) != 1 || dead[0].ID != "evt-37" || dead[0].Metadata["reason"] != "merchant id m-37x does not exist" {
		reasons := []string{}
		for _, d := range dead {
			reasons = append(reasons, d.ID+": "+d.Metadata["reason"])
		}
		if len(reasons) > 3 {
			reasons = append(reasons[:3], fmt.Sprintf("… %d in all", len(dead)))
		}
		fail("poison queue got %v; want only evt-37, with its error as the reason", reasons)
	}
	if ok {
		fmt.Println("ALL CHECKS PASS")
	}
}`}
  verifier="Runs stop 3's workload in memory: 1,000 events, every 10th failing once, event 37 always failing, event 55 panicking once, with 3 retries. Checks that no panic escapes, 999 receipts are sent, the handler is called exactly 1,104 times, and only event 37 reaches the poison queue, with its error as the reason. Prints ALL CHECKS PASS."
  hints={[
    "retry(max) allows max retries after the first call: call h once, then loop while there's an error and fewer than max retries have been made.",
    "recoverer needs a named error result and a deferred recover() that sets it: func(m *Message) (err error) { defer func() { if r := recover(); r != nil { err = ... } }(); return h(m) }.",
    "In chain, the outermost middleware is applied last: poisonQueue(publish)(retry(n)(recoverer(h))). The poison queue then only sees errors every retry returned, and each retry gets a recovered panic as an ordinary error."
  ]}

This is Watermill's `Retry`, `Recoverer` and `PoisonQueue` in miniature, with the same composition rule as `router.AddMiddleware`: the first one you apply to the handler is the innermost, the first one you add to the router is the outermost.

</Lab>

<Recap>

- **Publisher and Subscriber**: every transport implements two interfaces, so one handler ran unchanged on GoChannel (16 ms) and Redis streams (2.1 s with fsync on every write); the CorrelationID middleware carried `checkout-999` from payment to receipt request.
- **The router**: subscribe, handle, ack on success, nack on error, publish results. Killed mid-run: 2,000 of 2,000 delivered, 1 duplicate per crash, because each message is acknowledged as its handler returns.
- **Middleware**: first added is outermost. PoisonQueue ▸ Retry ▸ Recoverer: 999 receipts, 1 poisoned, 1,104 handler calls. Retry ▸ PoisonQueue: 898 receipts, 102 poisoned. `OnRetryHook` only fires after a retry fails.
- **Deduplication**: the Deduplicator dropped 126 duplicates of 3,126, then a restarted process handled all 3,000 again; it keys on a payload hash in process memory by default. Use it as a filter; use an inbox as the guarantee.
- **CQRS**: typed events to every interested handler (receipts 500, dashboard 500), typed commands to one (mailer 500), with marshalling and topics in configuration.
- **The outbox**: watermill-sql's publisher inside the payment's transaction, and the Forwarder to Redis: 3,000 payments through three kills, none lost, 126 duplicates.

</Recap>
