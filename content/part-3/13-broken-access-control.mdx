## The Most-Exploited Bug Class

Authentication and authorization are not the same word with different spelling. **Authentication** answers *who are you* — a verified token, a session, an mTLS certificate. **Authorization** answers *what may you do* — and it is a per-request, per-resource decision that the authentication layer cannot make for you.

<Define term="Broken Access Control (OWASP A01)">
**Broken access control** is the failure to enforce, on every request, the restrictions on what an authenticated principal is permitted to do. It became OWASP's **number one** application security risk in 2021 and has held the position since. It covers IDOR/BOLA (acting on objects you don't own), missing function-level checks (calling admin operations as a normal user), privilege escalation, and cross-tenant access. It is the most-exploited category because it is invisible to the things teams usually test: the happy path works perfectly for the *legitimate* user, so it ships.
</Define>

The reason it slips through is structural. Your unit tests authenticate as Alice and check that Alice sees Alice's data — green. Nobody writes the test where Alice asks for *Bob's* data and must be refused, because that test never occurred to the author of the feature. The authentication works, the feature works, the demo works. The hole is the *absence* of a check, and absence is the one thing a passing test of present behavior will never reveal.

**On the job:** A fintech security audit almost never finds a broken cipher. What it finds, every single time, is a `GET /accounts/{id}` handler that pulls the row by `id` alone — no `owner_id` in the `WHERE` clause. The authentication is flawless. The authorization is missing. That is the entire bug, and it is worth more to an attacker than any crypto flaw you could ship.

<ConceptGrid cols={2}>
  <ConceptCard label="Authentication ≠ authorization">A valid token proves identity. It says nothing about entitlement. Treating "the token verified" as "the request is allowed" is the root of this entire chapter.</ConceptCard>
  <ConceptCard label="Default deny">Every resource decision must start from *no* and require an explicit, positive grant to become *yes*. A code path that returns "allow" because nothing matched "deny" is a breach waiting for traffic.</ConceptCard>
  <ConceptCard label="Enforce at the data layer">Filtering in the handler, the UI, or the response serializer is decoration. The authorization predicate belongs in the query that fetches the data — where it cannot be bypassed by a different caller.</ConceptCard>
  <ConceptCard label="Test the negative">The check you need is "Bob cannot reach Alice's resource." If that assertion isn't in your suite, you have not tested authorization at all — you've tested the happy path twice.</ConceptCard>
</ConceptGrid>

## BOLA & Object Enumeration

<Define term="BOLA / IDOR">
**Broken Object-Level Authorization** (BOLA), historically called **Insecure Direct Object Reference** (IDOR), is the bug where an endpoint acts on an object identified by a client-supplied reference *without checking the caller is entitled to that specific object*. If `GET /accounts/acc_1002` returns the account whenever `acc_1002` exists — rather than only when the caller owns it — you have BOLA. When object IDs are sequential or guessable, BOLA upgrades from "read one victim" to **enumerate the entire namespace**.
</Define>

This is the single most common shape of the #1 bug. The mechanism is brutally simple: the ID comes from the request (a path parameter, a query string, a body field), the handler trusts it, and the only thing standing between an attacker and every record is whether they can *name* the ID. When IDs increment — `device_1`, `device_2`, `device_3` — naming them is a `for` loop.

**On the job:** Google's Nest endpoint `LookUpByNestId` accepted sequential device IDs and returned the owner's unobfuscated Gaia ID. Those Gaia IDs are *themselves* sequential, and a second endpoint mapped Gaia ID to email. Chain them and you walk from "device #N" to "this person's email" for the entire device population — a complete deanonymization, built entirely out of guessable identifiers and missing ownership checks.

The fix is not "add an `if` after the fetch." An `if` after the fetch still *fetched* the row, and a careless refactor will drop the `if` while leaving the query. The fix is to make ownership part of the lookup itself — the caller's identity is a parameter of the query, so a row the caller doesn't own simply does not exist as far as that call is concerned.

```go
package main

import (
	"errors"
	"fmt"
)

type Account struct {
	ID      string
	OwnerID string
	Balance int64
}

var vault = map[string]Account{
	"acc_1001": {"acc_1001", "usr_mallory", 50000},
	"acc_1002": {"acc_1002", "usr_bob", 12000},
	"acc_1003": {"acc_1003", "usr_alice", 8000},
}

var errNotFound = errors.New("account not found")

// INSECURE: looks up by ID alone. Any caller who can name an ID gets the row.
func getInsecure(id string) (Account, error) {
	a, ok := vault[id]
	if !ok {
		return Account{}, errNotFound
	}
	return a, nil
}

// SECURE: the caller's identity is part of the lookup. Not the owner -> not found.
// In SQL this is the AND owner_id = $2 clause; the principle is identical.
func getSecure(id, callerID string) (Account, error) {
	a, ok := vault[id]
	if !ok || a.OwnerID != callerID {
		return Account{}, errNotFound
	}
	return a, nil
}

func main() {
	const mallory = "usr_mallory"

	// BOLA: enumerate sequential-looking IDs with the insecure lookup.
	fmt.Println("-- insecure (BOLA): Mallory enumerates --")
	for _, id := range []string{"acc_1001", "acc_1002", "acc_1003"} {
		if a, err := getInsecure(id); err == nil {
			fmt.Printf("  leaked %s owner=%s balance=%d\n", a.ID, a.OwnerID, a.Balance)
		}
	}

	// Same enumeration, ownership enforced inside the lookup.
	fmt.Println("-- secure: ownership enforced --")
	hits := 0
	for _, id := range []string{"acc_1001", "acc_1002", "acc_1003"} {
		if _, err := getSecure(id, mallory); err == nil {
			hits++
		}
	}
	fmt.Printf("  Mallory could read %d of 3 accounts\n", hits)
}
```

<Gotcha>
Returning **404, not 403**, for a resource the caller doesn't own is deliberate. A `403 Forbidden` confirms the object *exists* — that alone is an information leak that lets an attacker map your ID space ("which device IDs are real?"). "Not found" reveals nothing: non-existent and not-yours look identical. The previous chapter's row-level authorization exercise made the same call for the same reason.
</Gotcha>

<Callout kind="note" title="Opaque IDs are defense in depth, not the fix">
Swapping sequential integers for UUIDs raises the cost of enumeration — you can't loop a 122-bit random space. But it is *not* the fix. An attacker who obtains one valid UUID (a leaked log line, a shared link, a referrer header) still reads the object if the ownership check is missing. Unguessable IDs slow enumeration; only the ownership check stops access. Do both; rely on the second.
</Callout>

<Callout kind="warn" title="From the field: BOLA isn't only reads — GitLab CI runners">
A bug-hunter reported an IDOR in GitLab's runner API: `POST /api/v4/projects/{projectId}/runners` accepted a **runner ID** belonging to *another* project and attached it to the attacker's own project. Runner IDs are **incremental and guessable**, so an attacker could enumerate them and hijack a victim's CI/CD runner — which has access to that pipeline's source, environment variables, and deploy secrets. The writeup ("From Failure to $32,000") reports a **$32,000** payout for it. The lesson sharpens the section: BOLA is not just *reading* an object you don't own — it's any *action* (attach, transfer, delete) on a resource the server never checked you're entitled to. The fix is identical: the runner's owning project must be part of the authorization decision, not just its ID.
</Callout>

## The List Trap: Collection-Level Authorization

BOLA is about *one* object named by the caller. Its collection-level cousin is more spectacular: an endpoint that returns *every* object because nobody scoped the list. `GET /campaigns` runs `SELECT * FROM campaigns` and ships the lot. The caller never even has to guess an ID — the server volunteers the entire table.

**On the field:** Google's YouTube TV CMS `ListCampaigns` returned every campaign globally, and the mutation endpoints (PATCH, COPY, DELETE) worked on any campaign ID — a $24,000 finding. The Widevine console's `ListOrgs` dumped every partner organization plus their encrypted signing keys. Same bug, two products: the list endpoint forgot that "list" means "list *the caller's*," not "list *everything*."

<BeforeAfter
  badLabel="Leaky list — filter in the handler (or not at all)"
  goodLabel="Scoped list — tenant is a WHERE clause"
  bad={`// returns the whole table; the UI is trusted to "show the right rows"

    return store // every tenant's data, on the wire

        }
    }
    return out

/>

The trap here is subtle and worth naming: teams *do* filter — but they filter in the **presentation layer**. The web UI shows only your campaigns; the mobile app requests `?tenant=me`. So in every screen a human looks at, it's correct. The raw API, hit directly with curl and a valid token, returns the whole table. The filter was never an authorization control — it was a *display preference*, and the attacker isn't using your UI.

```go
package main

import "fmt"

type Report struct {
	ID       string
	TenantID string
	Title    string
}

var store = []Report{
	{"r-1", "acme", "Acme Q1 revenue"},
	{"r-2", "globex", "Globex payroll"},
	{"r-3", "acme", "Acme churn model"},
	{"r-4", "initech", "Initech audit"},
}

// LEAKY: returns every row. If the UI "filters for display," that is a
// presentation choice, not an access control. curl sees all four.
func listAll() []Report {
	return store
}

// SCOPED: the tenant is applied where the data is read. There is no code
// path that returns another tenant's row.
func listForTenant(tenantID string) []Report {
	out := make([]Report, 0)
	for _, r := range store {
		if r.TenantID == tenantID {
			out = append(out, r)
		}
	}
	return out
}

func main() {
	const caller = "acme" // tenant bound from the verified token

	fmt.Printf("listAll leaks %d rows across all tenants:\n", len(listAll()))
	for _, r := range listAll() {
		fmt.Printf("  %s [%s] %s\n", r.ID, r.TenantID, r.Title)
	}

	scoped := listForTenant(caller)
	fmt.Printf("listForTenant(%q) returns %d rows:\n", caller, len(scoped))
	for _, r := range scoped {
		fmt.Printf("  %s %s\n", r.ID, r.Title)
	}
}
```

<Callout kind="pro" title="Make the unscoped query impossible to write">
The durable fix is architectural: don't expose a repository method that *can* return cross-tenant rows. Wrap your data access so every read takes a tenant (or owner) as a required argument — `repo.Reports(ctx).ForTenant(t).List()` — and never ship a bare `repo.AllReports()`. Postgres Row-Level Security (`ENABLE ROW LEVEL SECURITY` plus a policy keyed on a session variable) enforces the same rule one layer deeper, so even an accidental raw query is filtered. Defense in depth: the application scopes, and the database scopes again.
</Callout>

## Multi-Tenant Isolation

A list scoped to a tenant is only safe if the *tenant itself* is trustworthy. The next failure is letting the caller tell you which tenant they are. If `tenant_id` arrives in the request body, the query string, or a header the client controls, then "scope to the tenant" scopes to *whatever tenant the attacker typed*.

<Define term="Confused deputy / cross-tenant access">
A **confused deputy** is a privileged component tricked into misusing its authority on behalf of a less-privileged caller. In multi-tenant systems it shows up as **cross-tenant access**: the service holds broad data access (it can read any tenant), and it decides *which* tenant to act on from attacker-controlled input. The deputy (your service) has the authority; the attacker supplies the target. The fix is to derive the tenant exclusively from the **verified token**, never from request input.
</Define>

**On the field:** Google's Vertex AI Search let *any authenticated user* PATCH another project's `ConversationalSearchCustomizationConfig` — rewriting the system prompt and blocklists of a stranger's AI ($30,000). Translation Hub let any bearer token read translator groups and editing jobs *across tenants* and update another project's config to exfiltrate its cloud storage ($36,500). In both, the caller was authenticated fine; the service simply trusted the project/tenant identifier it was handed.

```go
package main

import (
	"context"
	"errors"
	"fmt"
)

type ctxKey string

const tenantKey ctxKey = "tenant"

// tenantFromContext returns the tenant that auth middleware bound from the
// VERIFIED token. It is the only trustworthy source of the caller's scope.
func tenantFromContext(ctx context.Context) (string, error) {
	t, ok := ctx.Value(tenantKey).(string)
	if !ok || t == "" {
		return "", errors.New("no tenant in context")
	}
	return t, nil
}

// TransferReq is the JSON body. TenantID is attacker-controlled — present in
// the payload but never to be trusted as an authorization input.
type TransferReq struct {
	TenantID string
	Amount   int64
}

// handleTransfer scopes the write to the token's tenant and ignores
// req.TenantID completely. The forged field has no effect.
func handleTransfer(ctx context.Context, req TransferReq) (string, error) {
	tenant, err := tenantFromContext(ctx)
	if err != nil {
		return "", err
	}
	// Use `tenant`, NEVER req.TenantID, as the write scope.
	return fmt.Sprintf("posted %d for tenant=%s", req.Amount, tenant), nil
}

func main() {
	// Auth middleware verified the token and bound tenant = t-attacker.
	ctx := context.WithValue(context.Background(), tenantKey, "t-attacker")

	// The attacker forges the body to name a different tenant.
```

## The Staging Trap

Here is the one that catches even careful teams. Production is hardened: auth enforced, request signatures validated, introspection off. Then someone needs a place to test, and staging is born — pointed at a *copy* of production data, or worse, at production itself, with the controls relaxed "because it's just staging." The attacker doesn't attack production. They attack the staging hostname that reaches the same data with the guard rails down.

**On the field:** This pattern recurred across the Google haul. AdExchange's `test-...sandbox.google.com` staging mirrored production data with missing permission checks. DataHub's staging accepted `SetIamPolicy` with arbitrary bindings — add yourself as owner, then read 1,592 tables of YouTube analytics. The Cloud Console GraphQL staging endpoint *disabled query-signature validation* that production enforced, and left schema introspection on — handing over the full API shape. Same data, weaker environment, wide-open door. The researcher's blunt summary on the *Critical Thinking* podcast: at this scale there is effectively *no such thing as staging* — most "staging" environments point straight at the production database; the relaxed front end is the only difference.

<Gotcha>
**Patching one staging mirror doesn't close the bug — there's usually another.** The same researcher described getting a finding fixed, then **re-exploiting it through a *different* staging environment** (an internal "auto-push" mirror) that reached the same production data with the same controls relaxed — and collected a *second, doubled* bounty for the same root cause. The lesson for defenders: a single resource is often fronted by *several* lower-environments (staging, sandbox, auto-push, canary), and a fix applied to one does nothing for the others. When you harden or retire one mirror, **enumerate every environment that can reach that data store** and apply the control at the data layer, not per-front-end — otherwise you've moved the unlocked door, not closed it.
</Gotcha>

The engineering rule is twofold. First, **non-production must never read production data** — use synthetic or fully anonymized datasets, so a weak staging control exposes nothing real. Second, if environments *must* share controls, those controls cannot be gated on an environment flag that drifts. Auth is not a feature you toggle per environment; it is the floor in all of them. The way you guarantee that in code is **fail-closed**: the authorization function has no "skip" path, so there is no flag for a staging config to flip.

```go
package main

import "fmt"

type Decision int

const (
	Deny Decision = iota
	Allow
)

func (d Decision) String() string {
	if d == Allow {
		return "ALLOW"
	}
	return "DENY"
}

// authorize is DEFAULT-DENY. It only knows how to grant explicit, known-good
// permissions. There is no env parameter, no AUTH_DISABLED branch, no "skip in
// staging" path — so no environment config can turn it off. Unknown role,
// unknown action, anything unexpected: Deny.
func authorize(role, action string) Decision {
	policy := map[string]map[string]bool{
		"admin":     {"read": true, "write": true},
		"initiator": {"read": true, "write": true},
		"viewer":    {"read": true},
	}
	actions, ok := policy[role]
	if !ok {
		return Deny // unknown role
	}
	if !actions[action] {
		return Deny // action not granted to this role
	}
	return Allow
}

func main() {
	// Whatever environment this runs in, the decisions are identical.
	fmt.Println("viewer write :", authorize("viewer", "write"))    // DENY
	fmt.Println("admin write  :", authorize("admin", "write"))     // ALLOW
	fmt.Println("ghost role   :", authorize("superuser", "read"))  // DENY
	fmt.Println("typo action  :", authorize("admin", "delet"))     // DENY
}
```

## IAM Poisoning & the Confused Deputy

The most audacious bugs in the haul weren't reads — they were *grants*. A permission-mutation endpoint that doesn't verify the caller is entitled to mutate permissions lets the attacker grant themselves whatever they want. The mutation authorizes itself: "should I let you add an owner?" "the request says yes." That is **IAM poisoning**.

<Define term="IAM poisoning / privilege escalation via self-grant">
**IAM poisoning** is privilege escalation through a permission-management operation that fails to check the caller's authority to perform the grant. The classic shape is a `SetIamPolicy` / `AddUser` endpoint that accepts arbitrary role bindings and applies them — so an unprivileged (or unrelated) caller adds themselves as **owner** of a resource and inherits everything. The mutation must verify two things the broken versions skipped: that the caller already holds **grant authority** on the resource, and that they are not handing out a role **above their own**.
</Define>

**On the field:** DataHub's staging `SetIamPolicy` accepted arbitrary bindings with no permission check — add yourself as dataset owner, read petabytes of YouTube analytics. AdExchange and Widevine exposed `AddUser` endpoints that let you self-provision into any account with an admin role. The deputy (the IAM service) had the authority to change bindings and never checked whether *this* caller was allowed to ask.

```go
import (
	"errors"
	"fmt"

// bindings: resource -> user -> role. Who currently holds what.
var bindings = map[string]map[string]string{
	"proj/meridian": {
		"usr_alice": "owner",
		"usr_bob":   "editor",

	errNoAuthority = errors.New("caller lacks grant authority on resource")
	errEscalate    = errors.New("cannot grant a role above your own")

// grantRole lets `caller` give `target` a `role` on `resource` ONLY IF the
// caller is already an owner of that resource AND is not handing out more
// power than they hold. This is exactly what the broken SetIamPolicy skipped.
func grantRole(caller, target, resource, role string) error {
	res, ok := bindings[resource]
	if !ok {
		return errNoAuthority
	}
	callerRole, ok := res[caller]
	if !ok || rank[callerRole] < rank["owner"] {
		return errNoAuthority // only owners may grant
	}
	if rank[role] > rank[callerRole] {
		return errEscalate // no granting above your own level
	}
	res[target] = role
	return nil
}

	// Mallory has no binding at all and tries to add herself as owner.
	err := grantRole("usr_mallory", "usr_mallory", "proj/meridian", "owner")

	err = grantRole("usr_bob", "usr_mallory", "proj/meridian", "viewer")
	fmt.Println("editor grants viewer      :", err) // lacks grant authority

	// Alice owns the project and grants Carol viewer — allowed.
	err = grantRole("usr_alice", "usr_carol", "proj/meridian", "viewer")
	fmt.Println("owner grants viewer       :", err) // <nil>
}
```

## Errors as Reconnaissance

Access control isn't only about what you return on success. It's also about what you leak on *failure*. A `500` that echoes the internal exception hands an attacker a map: bucket names, service-account identities, database index structure, internal hostnames. They can't read the data yet, but you've just told them exactly where it lives and what to target next.

**On the field:** The Google research repeatedly used `500`-class responses that disclosed internal service names, GCS bucket IDs, and index structures as the *reconnaissance* step — the error pages narrowed thousands of endpoints down to the few worth attacking. A verbose error is a free architecture diagram for the adversary.

The Go pattern is a deliberate split between what the **client** may see and what you **log**. Carry both on the error; return the public message over the wire, send the internal detail to your logs only.

```go
package main

import (
	"errors"
	"fmt"
	"log"
)

// AppError separates the message the CLIENT may see from the detail we LOG.
// The public string is generic; the internal error carries bucket names,
// service-account identities, query text — the reconnaissance a 500 must
// never hand out.
type AppError struct {
	Public   string // safe to return over the wire
	Internal error  // logged server-side only
}

func (e *AppError) Error() string { return e.Public }

func loadStatement(id string) error {
	// Pretend the object store rejected us with a revealing message.
	internal := errors.New(
		"GCS get gs://meridian-prod-statements/" + id + ".pdf: " +
			"serviceaccount stmts-reader@meridian-prod.iam denied",
	)
	return &AppError{Public: "could not load statement", Internal: internal}
}

// respond is the trust boundary: log the detail, return only the public text.
func respond(err error) string {
	var ae *AppError
	if errors.As(err, &ae) {
		log.Printf("internal: %v", ae.Internal) // stays in server logs
		return ae.Public
	}
	log.Printf("internal: %v", err)
	return "internal error" // unknown errors get a generic message too
}

func main() {
	err := loadStatement("acc_1002")
	client := respond(err)
	fmt.Println("client sees:", client) // "could not load statement"
}
```

## Testing Authorization Exhaustively

Now the constructive payoff. The reason the Google researcher found more than twenty bugs is that they tested authorization the way it must be tested but almost never is: **exhaustively and adversarially**. The AI agent parsed 1,500+ API discovery documents into a list of every endpoint, probed each with 3,600+ collected keys representing different identities, and classified every response — then a relentless loop refused to stop until every endpoint had been tested as *every* identity, including unauthenticated and cross-tenant. That's offense. The exact same matrix is your defense.

<Define term="The authorization test matrix">
An **authorization test matrix** asserts, for every (actor × action × resource) combination, whether the result must be **allow** or **deny** — and crucially includes the **negative** and **cross-principal** cases: Bob acting on Alice's resource, an unknown actor, an unknown action. A single policy function routes all real handlers, and the table tests that function directly. The matrix turns "did we remember the ownership check?" from a hope into a failing test when the answer is no.
</Define>

The keystone assertion is the **two-user test**: create Alice's resource, then assert that *Bob*, fully authenticated as himself, is refused. That one negative case would have caught the BOLA, the global list, and the cross-tenant write all at once. If your suite doesn't have it for every resource type, your authorization is untested.

```go
package main

import "fmt"

type Resource struct {
	ID    string
	Owner string
}

var db = map[string]Resource{
	"doc_a": {"doc_a", "alice"},
	"doc_b": {"doc_b", "bob"},
}

// can is the SINGLE policy function every handler routes through. Centralizing
// the decision means the matrix below tests every handler at once.
func can(actor, action, resourceID string) bool {
	r, ok := db[resourceID]
	if !ok {
		return false // unknown resource: deny
	}
	switch action {
	case "read", "update", "delete":
		return r.Owner == actor // only the owner
	default:
		return false // unknown action: deny
	}
}

func main() {
	type tc struct {
		actor, action, res string
		want               bool
	}
	// The matrix. Note the cross-owner rows: alice must NEVER touch doc_b,
	// bob must NEVER touch doc_a. Those negatives are the whole point.
	cases := []tc{
		{"alice", "read", "doc_a", true},
		{"alice", "update", "doc_a", true},
		{"alice", "read", "doc_b", false},   // cross-owner read denied
		{"alice", "delete", "doc_b", false}, // cross-owner delete denied
		{"bob", "read", "doc_b", true},
		{"bob", "update", "doc_a", false}, // cross-owner write denied
```

<Callout kind="note" title="The tooling that runs the two-user test for you">
The matrix above is the *defensive* form — assertions in your own CI. On the *offensive/QA* side, the same idea is automated by request-replay tools, and knowing how they work sharpens both how you test and what you must defend. The pattern they implement is the **three-lane replay**: capture a request as the resource **owner** (lane A), resend it **byte-for-byte with only the session swapped** to a *second* user (lane B), and resend it with **no credentials** (unauth lane) — method, URL, query, body, and content-type all kept identical, so the *only* variable is identity. A classifier then renders a verdict per request: **BYPASSED** (lane B got the owner's data — a finding), **ENFORCED** (denied — protected), or **UNCLEAR** (manual review). Open-source examples: **bscript/authz-replay** (a Manifest-V3 Chrome extension that captures cookies/`Authorization`/storage tokens per identity, classifies on status codes, body-similarity, and tester-planted "owner markers," and exports copy-as-cURL) and **repplus/rep-chrome** (a Burp-Repeater-style DevTools extension for capturing and replaying a request under modified method/headers/body). The takeaway for *your* code: if a tool can pass the exact same request as Bob and get Alice's data, you didn't have an authorization check — you had a UI that hid the button. Build the two-user assertion into CI so the regression is caught before a replay tool finds it.
</Callout>

<UnderTheHood title="The offense-as-defense methodology, generalized">

The bug haul that frames this chapter scaled a simple idea with automation, and you can run the same playbook against your own services in CI:

1. **Enumerate every endpoint.** The researcher parsed machine-readable discovery documents into a complete endpoint list. Your equivalent: generate the matrix from your OpenAPI/protobuf definitions so a *new* endpoint without authorization tests fails the build. An untested endpoint is the one that ships broken.

2. **Probe as every identity.** They tested each endpoint with thousands of keys spanning capabilities — including unauthenticated. Your equivalent: for each endpoint, run the request as the owner (expect allow), a different tenant (expect deny), and no auth (expect deny). The cross-tenant and unauthenticated rows are where the bugs are.

3. **Classify responses, don't eyeball them.** They mapped raw responses to semantic outcomes — "allowed," "missing visibility label," "denied" — to find access that *should* have been refused. Your assertion is the classifier: `got == want`, where `want` is `deny` for every negative case.

4. **Refuse to stop early.** A loop forced exhaustive coverage — no endpoint skipped. Your equivalent is coverage enforcement: every resource type must have its two-user test, and CI rejects the diff that adds a handler without one.

The asymmetry is the lesson: the attacker has to find *one* missing check; you have to assert *every* present one. The matrix is how you make that tractable — one policy function, one table, every combination, the negatives first.

<Exercise n={1} title="Ownership-scoped fetch" level="easy">

Write `GetDoc(docs map[string]Doc, id, callerID string) (Doc, error)` where `Doc` has `ID`, `OwnerID`, and `Body` fields. Return `ErrNotFound` both when the document doesn't exist *and* when it exists but `callerID` is not the owner — the two cases must be indistinguishable to the caller. Demonstrate that a non-owner gets `ErrNotFound`, not the document.

<Solution>

```go
package main

import (
	"errors"
	"fmt"
)

type Doc struct {
	ID      string
	OwnerID string
	Body    string
}

var ErrNotFound = errors.New("not found")

func GetDoc(docs map[string]Doc, id, callerID string) (Doc, error) {
	d, ok := docs[id]
	if !ok || d.OwnerID != callerID {
		// Same error for "missing" and "not yours" — no existence oracle.
		return Doc{}, ErrNotFound
	}
	return d, nil
}

func main() {
	docs := map[string]Doc{
		"d1": {"d1", "alice", "alice's notes"},
		"d2": {"d2", "bob", "bob's notes"},
	}

	got, err := GetDoc(docs, "d1", "alice")
	fmt.Println("owner:", got.Body, err) // alice's notes <nil>

	_, err = GetDoc(docs, "d1", "mallory")
	fmt.Println("non-owner:", err) // not found

	_, err = GetDoc(docs, "d999", "alice")
	fmt.Println("missing:", err) // not found — identical to non-owner
}
```

Folding ownership into the lookup condition makes "not yours" and "doesn't exist" return the same error. The attacker learns nothing about which IDs are real.

</Solution>

</Exercise>

<Exercise n={2} title="Tenant-scoped list and the two-user test" level="medium">

Write `ListForTenant(rows []Invoice, tenantID string) []Invoice` that returns only the rows whose `TenantID` matches. Then write a check that creates invoices for two tenants and asserts that each tenant's list contains *none* of the other's rows — the two-user test for collections.

<Solution>

```go
package main

import "fmt"

type Invoice struct {
	ID       string
	TenantID string
	Cents    int64
}

func ListForTenant(rows []Invoice, tenantID string) []Invoice {
	out := make([]Invoice, 0)
	for _, r := range rows {
		if r.TenantID == tenantID {
			out = append(out, r)
		}
	}
	return out
}

func leaks(list []Invoice, foreignTenant string) bool {
	for _, r := range list {
		if r.TenantID == foreignTenant {
			return true
		}
	}
	return false
}

func main() {
	rows := []Invoice{
		{"i1", "acme", 1000},
		{"i2", "globex", 2000},
		{"i3", "acme", 3000},
	}

	acme := ListForTenant(rows, "acme")
	globex := ListForTenant(rows, "globex")

	fmt.Printf("acme sees %d rows; leaks globex? %v\n", len(acme), leaks(acme, "globex"))
	fmt.Printf("globex sees %d rows; leaks acme? %v\n", len(globex), leaks(globex, "acme"))
	// acme sees 2 rows; leaks globex? false
	// globex sees 1 rows; leaks acme? false
}
```

The `leaks` helper is the two-user test for a list: it fails the moment a tenant's results contain a foreign row. Run it for every collection endpoint.

</Solution>

<Exercise n={3} title="Default-deny authorizer" level="medium">

Write `Authorize(role, action string) bool` backed by an explicit allow-list map of roles to permitted actions. Unknown roles and unknown actions must return `false`. There must be no `env` parameter and no bypass — prove with a table that a ghost role and a typo'd action both deny.

<Solution>

```go
package main

import "fmt"

var policy = map[string]map[string]bool{
	"admin":   {"read": true, "write": true, "delete": true},
	"clerk":   {"read": true, "write": true},
	"auditor": {"read": true},
}

func Authorize(role, action string) bool {
	actions, ok := policy[role]
	if !ok {
		return false // unknown role

	return actions[action] // missing key -> zero value false
}

func main() {
	cases := []struct {
		role, action string
```

<Exercise n={4} title="Grant guard: no self-authorizing escalation" level="hard">

Implement `Grant(bindings map[string]map[string]string, caller, target, resource, role string) error`. It must reject the grant unless the caller already holds `owner` on the resource, and must reject any attempt to grant a role ranked above the caller's own. Use a rank map `{viewer:1, editor:2, owner:3}`. Prove a stranger and an editor are both refused, and an owner may grant up to (but not above) their level.

<Solution>

```go
package main

import (
	"errors"
	"fmt"
)

var rank = map[string]int{"viewer": 1, "editor": 2, "owner": 3}

var (
	ErrNoAuthority = errors.New("caller lacks grant authority")
	ErrEscalate    = errors.New("cannot grant above your own role")
	ErrBadRole     = errors.New("unknown role")
)

func Grant(bindings map[string]map[string]string, caller, target, resource, role string) error {
	if _, ok := rank[role]; !ok {
		return ErrBadRole
	}
	res, ok := bindings[resource]
	if !ok {
		return ErrNoAuthority
	}
	callerRole, ok := res[caller]
	if !ok || rank[callerRole] < rank["owner"] {
		return ErrNoAuthority
	}
	if rank[role] > rank[callerRole] {
		return ErrEscalate
	}
	res[target] = role
	return nil
}

func main() {
	bindings := map[string]map[string]string{
		"proj/x": {"alice": "owner", "bob": "editor"},
	}

	fmt.Println(Grant(bindings, "mallory", "mallory", "proj/x", "owner")) // no authority
	fmt.Println(Grant(bindings, "bob", "carol", "proj/x", "viewer"))      // no authority (editor)
	fmt.Println(Grant(bindings, "alice", "carol", "proj/x", "owner"))     // <nil> (owner grants owner is allowed: equal, not above)
	fmt.Println(Grant(bindings, "alice", "dave", "proj/x", "superuser"))  // unknown role
}
```

Three gates — authority, role validity, and no-escalation — make the operation impossible to self-authorize. Note "equal" is permitted (`>` not `>=`): an owner may appoint another owner, but no one can mint a role above their own.

</Solution>

</Exercise>

<Exercise n={5} title="Safe error mapper" level="medium">

Write `ToClient(err error) string` that, given an `*AppError` (with `Public string` and `Internal error`), returns the `Public` message; for any other error type it returns a fixed `"internal error"`. The internal detail must never appear in the returned string. Demonstrate with an error whose internal text names a bucket and a service account.

<Solution>

```go
package main

import (
	"errors"
	"fmt"
)

type AppError struct {
	Public   string
	Internal error
}

func (e *AppError) Error() string { return e.Public }

func ToClient(err error) string {
	var ae *AppError
	if errors.As(err, &ae) {
		return ae.Public
	}
	return "internal error"
}

func main() {
	leaky := &AppError{
		Public:   "could not export report",
		Internal: errors.New("gs://meridian-prod-reports denied for svc-export@prod.iam"),
	}
	fmt.Println("client:", ToClient(leaky)) // could not export report

	raw := errors.New("pq: relation \"accounts_owner_idx\" does not exist")
	fmt.Println("client:", ToClient(raw)) // internal error — index name hidden
}
```

`errors.As` recovers the public message when present and collapses everything else to a generic string. The bucket name, the service account, and the Postgres index name all stay server-side.

</Solution>

<Recap>

- **Broken access control is OWASP's #1 risk** and the most expensive class in fintech: the feature works for the legitimate user, so the *absence* of an authorization check ships invisibly. A real $500K bug haul against Google was, end to end, this one category.
- **Authentication is not authorization.** A verified token proves identity and says nothing about entitlement. Every request needs a separate, per-resource decision that starts from **default deny**.
- **BOLA/IDOR**: act on objects by client-supplied ID without an ownership check, and a guessable ID space becomes a database dump. Fold the caller's identity into the lookup, return **404 not 403**, and treat opaque IDs as defense in depth — not the fix.
- **The list trap** is BOLA at scale: a `List` endpoint that returns every tenant's rows. Scope every collection to the caller in the **query**, never in the UI or a request parameter; make the unscoped query method impossible to call.
- **Multi-tenant isolation** fails when the tenant is taken from request input. Bind tenant/owner from the **verified token**, propagate through context, and treat any `tenant_id` in the body as inert — otherwise your service is a confused deputy.
- **The staging trap**: a non-production environment touching production data with relaxed controls is the weakest door to the same vault. Use synthetic data, and make authorization **fail-closed** with no environment-toggleable bypass.
- **IAM poisoning**: permission mutations that don't verify the caller's authority authorize themselves. A grant must check the caller holds **grant authority** on the resource and is **not escalating** above their own role. Pair with **least-privilege service accounts** to contain lateral movement.
- **Errors are reconnaissance.** A verbose `500` leaks bucket names, service accounts, and index structure. Split every error into a **public** message (over the wire) and an **internal** detail (logs only).
- **Test authorization exhaustively.** Centralize the decision in one policy function and assert allow/deny for every actor × action × resource — the **two-user test** (Bob refused Alice's resource) for every resource type catches BOLA, leaky lists, and cross-tenant writes in one assertion. Turn the attacker's enumeration-and-classify methodology inward in CI.

</Recap>
