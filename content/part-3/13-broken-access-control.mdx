<HeroCard label="Part 3 · Chapter 13" title="Broken Access Control">

The last chapter encrypted the vault: AES-GCM, envelope keys, constant-time comparisons. All of it is beside the point if the service hands the vault to anyone who asks with the right URL. **Broken access control** is a service doing the right thing for the wrong person. It has been **#1 in OWASP's Top 10** since 2021 and is still #1 in the 2025 list, which reports that 100% of the applications tested had some form of it.

It survives because it looks like working code. The handler authenticates the caller, runs a valid query and returns a correct row. Nobody notices that the query never asked whose row it was. Every unit test passes, because tests log in as one user and ask for that user's data.

This chapter builds a small Meridian accounts service on a real PostgreSQL 14 database with 3,000 accounts across three banks, breaks it in each of the ways this bug actually shows up, measures what leaks, and fixes it. Seven stops. If you get lost, come back here:

1. **The missing check.** An id-only lookup, and what one caller can read.
2. **Roles are not ownership.** One admin rewriting another admin's password.
3. **The list trap.** A collection endpoint that ignores who is asking.
4. **Whose tenant is it?** A tenant chosen by the request body, and Postgres row-level security as a second lock.
5. **Environments and grants.** Default deny with no off switch, permission changes that authorize themselves, and a rule change while requests are in flight.
6. **Errors as a map.** What a 403, a 404 and a database error tell a stranger.
7. **Testing it properly.** An authorization matrix that fails the leaky version.

Then a short **range** you run on your own machine, and the exercises.

</HeroCard>

## The Missing Check

*Stop 1 of 7.*

### Step 1: the service

Everything here runs against PostgreSQL 14.19 on an Apple M1, from one Go 1.27 module, `acl`, using `github.com/jackc/pgx/v5` v5.11.0. Four tables: `tenants` (three banks: `acme`, `globex`, `initech`), `users` (four per bank, each with a role), `accounts` (250 per user, so 3,000 in all, ids 1001 to 4000, each with an owner) and `grants`. A small HTTP layer sits on top. `run.sh` rebuilds the database and reproduces every number below.

The HTTP layer has one piece of middleware, `Authn`. It stands in for the JWT verification you built in Part 1: it turns the request's credential into a `Principal` (user, tenant and role) and stores it in the request context. Everything after it trusts only that stored principal, never anything the client sends afterwards.

```go noverify
// api.go, lines 15–27
func (s *Store) Authn(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		id := r.Header.Get("Authorization")
		var p Principal
		err := s.Pool.QueryRow(r.Context(),
			`SELECT id, tenant_id, role FROM users WHERE id = $1`, id).Scan(&p.UserID, &p.TenantID, &p.Role)
		if err != nil {
			http.Error(w, "unauthenticated", http.StatusUnauthorized)
			return
		}
		next.ServeHTTP(w, r.WithContext(context.WithValue(r.Context(), ctxKey{}, p)))
	})
}
```

### Step 2: a lookup that asks only about the row

Here is the handler and the query behind it. Read it as a stranger would: what decides which row comes back?

```go noverify
// api.go, lines 41–49
	mux.HandleFunc("GET /v0/accounts/{id}", func(w http.ResponseWriter, r *http.Request) {
		id, _ := strconv.ParseInt(r.PathValue("id"), 10, 64)
		a, err := s.AccountByID(r.Context(), id)
		if errors.Is(err, ErrNotFound) {
			http.Error(w, "not found", 404)
			return
		}
		writeJSON(w, 200, a)
	})
```

```go noverify
// store.go, lines 31–40
func (s *Store) AccountByID(ctx context.Context, id int64) (Account, error) {
	var a Account
	err := s.Pool.QueryRow(ctx,
		`SELECT id, tenant_id, owner_id, balance, memo FROM accounts WHERE id = $1`, id,
	).Scan(&a.ID, &a.TenantID, &a.OwnerID, &a.Balance, &a.Memo)
	if errors.Is(err, pgx.ErrNoRows) {
		return a, ErrNotFound
	}
	return a, err
}
```

The answer is `WHERE id = $1`. The id comes from the URL and that is the only thing that picks the row. The `Principal` that `Authn` built is never used. Every step reads as correct: authenticated, parameterized, row found, row returned.

### Step 3: walk every id

`cmd/enum` plays a caller who owns 250 accounts. It logs in as `acme-u3` and requests every id from 1001 to 4000 through the v0 route, counting what comes back:

```text
v0: caller acme-u3 read 3000 of 3000 accounts; 2750 belong to somebody else map[acme:750 globex:1000 initech:1000]
```

One valid login read all 3,000 accounts: 750 from their own bank that were not theirs, and every account at the other two banks. The loop is nine lines of Go and needs no skill, because the ids are sequential. This is **BOLA**, Broken Object-Level Authorization, the current OWASP API Security name for what used to be called IDOR (Insecure Direct Object Reference).

### Step 4: put the caller in the lookup

The fix is not an `if` after the fetch. An `if` after the fetch has already read the row, and a refactor that drops the `if` leaves a working leak. The fix is to make the caller part of the query, so a row that isn't theirs never comes back:

```go noverify
// store.go, lines 44–54
func (s *Store) AccountFor(ctx context.Context, p Principal, id int64) (Account, error) {
	var a Account
	err := s.Pool.QueryRow(ctx,
		`SELECT id, tenant_id, owner_id, balance, memo FROM accounts
		  WHERE id = $1 AND tenant_id = $2 AND owner_id = $3`, id, p.TenantID, p.UserID,
	).Scan(&a.ID, &a.TenantID, &a.OwnerID, &a.Balance, &a.Memo)
	if errors.Is(err, pgx.ErrNoRows) {
		return a, ErrNotFound
	}
	return a, err
}
```

`AccountFor` takes the `Principal` and adds `tenant_id = $2 AND owner_id = $3`. The values come from the verified principal, not from the request. Nothing is left to check after the fetch, because a foreign row was never fetched. Same walk, v1 route:

```text
v1: caller acme-u3 read 250 of 3000 accounts; 0 belong to somebody else map[]
```

250 of 3,000: exactly their own.

### Step 5: the same id is a second door

An id in a request is an ownership question, and also a value that ends up in SQL. If some code path builds that SQL by concatenating text, the caller is writing part of the query. This lives in the module, marked as a warning:

```go noverify
// store.go, lines 94–106
// CountByIDConcat builds SQL by string concatenation. Never do this.
func (s *Store) CountByIDConcat(ctx context.Context, id string) (int, error) {
	rows, err := s.Pool.Query(ctx, "SELECT id FROM accounts WHERE id = "+id)
	if err != nil {
		return 0, err
	}
	defer rows.Close()
	n := 0
	for rows.Next() {
		n++
	}
	return n, rows.Err()
}
```

```text
concatenated  id="1001"         -> 1 rows, err=<nil>
concatenated  id="1001 OR true" -> 3000 rows, err=<nil>
parameterized id="1001 OR true" -> err=ERROR: invalid input syntax for type bigint: "1001 OR true" (SQLSTATE 22P02)
```

Concatenated, the second value turns a one-row lookup into all 3,000 rows. Parameterized (`$1`), the same text is data: Postgres rejects it as not being a number. So the rule has two halves: **check ownership in the query, and never build the query from text.** Neither replaces the other.

<Gotcha>
**Return 404, not 403, for a row the caller may not see.** A 403 says "this exists, and you can't have it", which lets a stranger sort real ids from fake ones. Step 1 of stop 6 counts exactly how much that gives away. Sequential ids make enumeration cheap, and random UUIDs make it expensive, but a UUID is not a permission check: anyone who obtains one valid UUID (from a log line, a shared link, a referrer) reads the row unless the query asks whose it is.
</Gotcha>

<Recap>

- BOLA is an object fetched by a client-supplied id with no question about the caller. One login read 3,000 of 3,000 accounts, 2,750 of them not theirs.
- The fix belongs in the query (`AND tenant_id = $2 AND owner_id = $3`, values from the verified principal), so the foreign row is never read: 250 of 3,000, 0 foreign.
- An id is also SQL input. Parameterize it: `1001 OR true` returned 3,000 rows concatenated and a type error parameterized.

</Recap>

## Roles Are Not Ownership

*Stop 2 of 7.*

### Step 1: the peer

The BOLA everyone pictures is a low-privilege user reaching high-privilege data. The version that slips through audits is **same-role**: one admin acting on another admin's object. A role check answers "may this kind of user do this kind of thing?". A peer is the right kind of user. The question that catches them is a different one: "may *this* caller act on *this* object?".

Here is a password change written the way it often is, checking the role and nothing else:

```go noverify
// admin.go, lines 16–23
// SetPasswordVuln checks the caller's ROLE only.
func (s *Store) SetPasswordVuln(ctx context.Context, p Principal, target, hash string) error {
	if p.Role != "admin" {
		return ErrForbidden
	}
	_, err := s.Pool.Exec(ctx, `UPDATE users SET password_hash = $2 WHERE id = $1`, target, hash)
	return err
}
```

`globex-u1` and `globex-u2` are both admins at Globex. `globex-u1` calls it with `globex-u2` as the target:

```text
VULN admin globex-u1 -> globex-u2: err=<nil>, stored hash now "h(attacker)"
```

The call succeeded, and the other admin's credential is now the caller's. The role check passed, because `globex-u1` really is an admin, and nothing asked whose password it was.

### Step 2: two questions the fix has to ask

```go noverify
// admin.go, lines 25–39
// SetPasswordSafe requires ownership AND the current password.
func (s *Store) SetPasswordSafe(ctx context.Context, p Principal, target, oldHash, newHash string) error {
	if p.UserID != target {
		return ErrForbidden
	}
	tag, err := s.Pool.Exec(ctx,
		`UPDATE users SET password_hash = $3 WHERE id = $1 AND password_hash = $2`, target, oldHash, newHash)
	if err != nil {
		return err
	}
	if tag.RowsAffected() == 0 {
		return ErrForbidden
	}
	return nil
}
```

Two changes. **Ownership**: the caller must *be* the target (`p.UserID != target`). **Re-authentication**: the update only applies when the caller supplies the current password hash (`AND password_hash = $2`), because a logged-in session is not consent to replace credentials; a stolen session shouldn't be able to. The same peer attack, and the rest of the matrix:

```text
SAFE same call:                          err=forbidden, stored hash "h(pw)"
SAFE owner, wrong current password:      err=forbidden
SAFE owner, right current password:      err=<nil>
```

- A role answers "what kind of user"; ownership answers "whose object". A peer with the right role passes a role check and rewrites another admin's password.
- Fix with ownership in the check, and require the current secret for a sensitive change. A session is not consent.

</Recap>

## The List Trap

*Stop 3 of 7.*

### Step 1: an endpoint that lists

BOLA names one object. Its collection-level cousin is bigger: an endpoint that returns *every* object because nobody scoped the list. It hides well because filtering feels like a feature. The web UI shows only your accounts, the mobile app asks for `?mine=true`. In every screen a person looks at, it's correct. The raw API is the leak.

```go noverify
// store.go, lines 56–58
func (s *Store) ListAll(ctx context.Context) ([]Account, error) {
	return s.list(ctx, `SELECT id, tenant_id, owner_id, balance, memo FROM accounts ORDER BY id`)
}
```

```go noverify
// store.go, lines 60–63
func (s *Store) ListFor(ctx context.Context, p Principal) ([]Account, error) {
	return s.list(ctx, `SELECT id, tenant_id, owner_id, balance, memo FROM accounts
	                     WHERE tenant_id = $1 AND owner_id = $2 ORDER BY id`, p.TenantID, p.UserID)
}
```

The two are the same endpoint, before and after. `TestListSizes` calls both as `acme-u3`:

```text
v0 GET /accounts as acme-u3: 200, 3000 rows, 213677 bytes, 3 tenants visible
v1 GET /accounts as acme-u3: 200, 250 rows, 16976 bytes, 1 tenants visible
```

The v0 response is 213,677 bytes containing three banks' customers. The UI would have shown the caller 250 of them and thrown the rest away, but the rest already crossed the wire. The lesson is where the filter lives: **a control in the presentation layer is not a control.**

<Callout kind="pro" title="Make the unscoped query impossible to write">
The durable fix is architectural: don't expose a repository method that *can* return cross-tenant rows. Make every read take the principal as a required argument (`ListFor(ctx, p)`, never `List(ctx)`), keep the unscoped one out of the package the handlers can import, and back it with a database rule (stop 4) so a forgotten `WHERE` still returns nothing.
</Callout>

- A list endpoint is BOLA at scale: 3,000 rows and 213,677 bytes from one call, against 250 rows and 16,976 bytes when the query is scoped.
- Scope in the query with the principal as an argument; make the unscoped read unavailable to handlers.

## Whose Tenant Is It?

*Stop 4 of 7.*

### Step 1: the tenant in the body

Meridian is multi-tenant: several banks share the database and each must see only its own rows. The failure is letting the *caller* say which tenant they are. The service below has access to every tenant, so it needs someone to tell it which one to use, and it asks the request body:

```go noverify
// api.go, lines 89–108
	mux.HandleFunc("POST /v0/credits", func(w http.ResponseWriter, r *http.Request) {
		var c credit
		json.NewDecoder(r.Body).Decode(&c)
		n, err := s.Credit(r.Context(), c.TenantID, c.AccountID, c.Amount)
		if err != nil {
			http.Error(w, "not found", 404)
			return
		}
		writeJSON(w, 200, map[string]int64{"balance": n})
	})
	mux.HandleFunc("POST /v1/credits", func(w http.ResponseWriter, r *http.Request) {
		var c credit
		json.NewDecoder(r.Body).Decode(&c)
		n, err := s.Credit(r.Context(), Who(r).TenantID, c.AccountID, c.Amount)
		if err != nil {
			http.Error(w, "not found", 404)
			return
		}
		writeJSON(w, 200, map[string]int64{"balance": n})
	})
```

`acme-u3` calls it naming Globex's account 1005 and Globex's tenant in the body:

```text
v0 credit as acme-u3 naming tenant globex: 200 {"balance":1017640}
v1 same request: 404 not found
globex account 1005 balance: before 17641, after 1017640 (v0 moved it by 999999)
```

$9,999.99 arrived in another bank's account from a caller who has no business there. The service is a **confused deputy**: it has authority over every tenant and let the caller choose which one to spend it on. v1 ignores the body's `tenant_id` and uses the tenant `Authn` stored from the login, so account 1005 is simply not in the caller's tenant and the answer is 404.

### Step 2: a second lock in the database

Application code can still forget a `WHERE`. Postgres can enforce the tenant even then, with **row-level security** (RLS). You attach a policy to the table, and the database adds it to every query:

```sql
ALTER TABLE accounts ENABLE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON accounts
  USING      (tenant_id = current_setting('app.tenant', true))
  WITH CHECK (tenant_id = current_setting('app.tenant', true));
```

`USING` filters what a query can see and touch. `WITH CHECK` rejects writes that would land in another tenant. The policy reads a session setting, `app.tenant`, that the application sets. `cmd/rls` measures what that does, from Go, connection by connection:

```text
1a. superuser, no tenant set: sees 3000 rows (always bypasses)
1b. the table owner: sees 3000 rows (bypasses unless FORCE)
1c. same owner after FORCE ROW LEVEL SECURITY: sees 0 rows
2. app role, no tenant set: sees 0 rows (fails closed: current_setting is NULL)
3. inside tx with tenant=acme: sees 1000 rows
   after COMMIT, same pooled connection: sees 0 rows, tenant="" (scope died with the tx)
4. a request runs a session-level SET app.tenant='acme', then returns its connection to the pool
   the NEXT request (any user, any tenant) reuses it: sees 1000 rows, tenant="acme"
5. tenant=acme inserting a globex row: ERROR: new row violates row-level security policy for table "accounts" (SQLSTATE 42501)
```

Five things to take from it:

1. **RLS does not apply to superusers, or to the table's owner unless you `FORCE` it.** If your service connects as the role that created the tables (a very common setup), the policy protects nothing. Connect as a low-privilege role, and `FORCE ROW LEVEL SECURITY` if the owner must be bound too.
2. **It fails closed.** With no tenant set, the app role sees 0 rows, because `current_setting` is `NULL` and `tenant_id = NULL` is never true.
3. **Scope it to the transaction.** `set_config('app.tenant', 'acme', true)` (the same as `SET LOCAL`) ends with the transaction. After the `COMMIT` the same pooled connection sees nothing again.
4. **A session-level setting is a trap.** `set_config(..., false)` (plain `SET`) stays on the connection. Connection pools hand connections back out, so the *next* request, from any user and any tenant, inherits `acme`. That is a cross-tenant leak that no unit test with one user will find.
5. **`WITH CHECK` stops cross-tenant writes**, not just reads.

<UnderTheHood title="How Postgres applies a policy">

A policy is not a filter bolted on after the query runs. Postgres rewrites your query, adding the policy's `USING` expression to it as an ordinary condition, so the planner can use indexes for it. As `meridian_app` with `app.tenant` set to `acme`, `EXPLAIN` shows the policy inside the plan:

```text
 Index Scan using accounts_pkey on accounts  (cost=0.28..8.30 rows=1 width=8)
   Index Cond: (id = 1001)
   Filter: (tenant_id = current_setting('app.tenant'::text, true))

 Aggregate  (cost=28.28..28.29 rows=1 width=8)
   ->  Index Only Scan using accounts_tenant_id_idx on accounts  (cost=0.28..25.78 rows=1000 width=0)
         Index Cond: (tenant_id = current_setting('app.tenant'::text, true))
```

Two consequences. The `Filter:` line is the policy: a query for id 1001 still finds the row by primary key and then discards it if the tenant differs, so a caller asking for another tenant's id gets zero rows, indistinguishable from a missing one (the same 404 rule as stop 1). And because the condition is part of the plan, a `tenant_id` index makes the count above an index-only scan of 1,000 rows instead of a scan of all 3,000. Give every column a policy reads an index.

</UnderTheHood>

## Environments and Grants

*Stop 5 of 7.*

### Step 1: the environment with an off switch

Production has authorization enforced. Then somebody needs a place to test, and staging appears, pointed at a copy of real data, with the checks "temporarily" off. A non-production environment that can read production data *is* production, with the weakest door. Two rules follow: non-production never holds real data (synthetic or anonymized only), and authorization has **no off switch**, so no environment variable can turn it off.

```go noverify
// admin.go, lines 78–84
func Authorize(role, action string) Decision {
	switch role + ":" + action {
	case "admin:read", "admin:write", "initiator:read", "initiator:write", "viewer:read":
		return true
	}
	return false
}
```

`Authorize` takes a role and an action and nothing else: no environment, no `AUTH_DISABLED`. The only `true` is an explicit `(role, action)` pair in a `case`, so anything unknown falls through to `false`. The same call gives the same answer in production, staging and on a laptop:

```text
viewer    write  -> false
admin     write  -> true
superuser read   -> false
admin     delet  -> false
```

A role nobody defined and an action with a typo are both denied. That is **default deny**: the shape of the code makes "allow" the thing that needs a reason.

### Step 2: a grant that authorizes itself

The other place access control is quietly given away is permission management. An endpoint that changes who may do what, without checking that the caller may change it, lets anyone promote themselves. Here is the grant, with three gates:

```go noverify
// admin.go, lines 43–73
// Grant lets caller give target a role on resource. The check and the write share
// one transaction and the caller's own row is locked, so a concurrent revoke can't slip between them.
func (s *Store) Grant(ctx context.Context, caller, target, resource, role string) error {
	if rank[role] == 0 {
		return ErrForbidden
	}
	tx, err := s.Pool.Begin(ctx)
	if err != nil {
		return err
	}
	defer tx.Rollback(ctx)
	var callerRole string
	err = tx.QueryRow(ctx,
		`SELECT role FROM grants WHERE resource = $1 AND user_id = $2 FOR SHARE`, resource, caller).Scan(&callerRole)
	if errors.Is(err, pgx.ErrNoRows) || (err == nil && rank[callerRole] < rank["owner"]) {
		return ErrNoAuthority
	}
	if err != nil {
		return err
	}
	if rank[role] > rank[callerRole] {
		return ErrEscalate
	}
	_, err = tx.Exec(ctx,
		`INSERT INTO grants (resource, user_id, role) VALUES ($1,$2,$3)
		 ON CONFLICT (resource, user_id) DO UPDATE SET role = EXCLUDED.role`, resource, target, role)
	if err != nil {
		return err
	}
	return tx.Commit(ctx)
}
```

1. **Authority.** The caller must already hold `owner` on that resource, looked up in the same transaction. No row, or a lower role, means `ErrNoAuthority`.
2. **No escalation.** The role being granted can't outrank the caller's own.
3. **One transaction, with the caller's row locked.** `FOR SHARE` on the caller's grant row means a concurrent revoke of that authority has to wait until this commit or rollback, so the check and the write can't be separated by a change.

`acme-u1` is owner and `acme-u2` is editor. `globex-u3` has no grants at all:

```text
stranger self-grants owner : caller lacks grant authority on resource
editor grants viewer       : caller lacks grant authority on resource
owner grants viewer        : <nil>
owner grants a role 'god'  : forbidden
```

Only the owner's grant went through, and even the owner can't invent a role that doesn't exist.

### Step 3: a permission change while requests are in flight

Everything above tests a *steady* state: the field is locked and gets refused, or it is open and gets written. There is a bug class that lives only in the moment a rule *changes*, and it needs two mistakes at once. Take a profile service where an admin decides which fields other users may edit (`email` and `address` locked, `first_name` and `last_name` open). `profile.go` in the module has the rules in a `field_rules` table and a small in-memory cache of them, and three ways to write an update.

**Mistake 1: apply, then check.** The first version writes every field and *then* looks at the rules and returns a denial:

```go noverify
// profile.go, lines 57–75
// UpdateApplyThenCheck writes every field, then looks at the rules and reports a denial.
// The caller sees an error; the data has already changed. This is the bug.
func (s *Store) UpdateApplyThenCheck(ctx context.Context, cache *RulesCache, target string, changes map[string]string) error {
	for f, v := range changes {
		col, ok := profileFields[f]
		if !ok {
			return fmt.Errorf("unknown field %q", f)
		}
		if _, err := s.Pool.Exec(ctx, `UPDATE profiles SET `+col+` = $2 WHERE user_id = $1`, target, v); err != nil {
			return err
		}
	}
	for f := range changes {
		if !cache.Editable(ctx, f) {
			return fmt.Errorf("%w: %s", ErrFieldLocked, f)
		}
	}
	return nil
}
```

The caller is told no. The data has already changed. `TestApplyThenCheck` sends `{"email": "attacker@example.com", "first_name": "Renamed"}` for a locked email field:

```text
apply-then-check: returned "field is not editable: email"
   email before: acme-u4@example.com   email after: attacker@example.com   <- the write happened
```

A status code describes what the handler *returned*, not what the database *holds*. If a response body echoes the new value inside an error (a message like "not authorized to modify email on user Renamed"), that echo is the tell that the write came first. Fixing the status code changes nothing: the order is the bug. **Decide first, and only then write.**

**Mistake 2: a decision made from stale state.** The second version checks before writing, but against the cache. The admin opens `email` for a moment, a request warms the cache while it is open, and then the admin locks it again. The cache keeps saying "editable" for the rest of its 400 ms lifetime. Eight goroutines send email updates for 800 ms, and each write records whether it *started after the admin's lock had committed*:

```text
cached check (TTL 400 ms)            1702646 attempts, 1694126 refused,  8520 writes succeeded,  6461 of them started AFTER the lock committed; admin's change took 0 ms
```

The admin's change committed in under a millisecond. After that, **6,461 writes that began after the field was locked still succeeded**, because the cache hadn't heard. Nothing was misconfigured; the cache was doing what a cache does. The window is as long as its TTL, and a browser session that caches permissions until you refresh has a window as long as the session.

**The fixes.** There are two ways to make the rule and the write inseparable. One transaction that reads the rules with `FOR SHARE`, then writes:

```go noverify
// profile.go, lines 92–120
// Update decides and writes in one transaction. The rules are read inside it with FOR SHARE, so an admin
// changing a rule waits for us (or we wait for them): a write can never straddle a rule change.
// Any locked, unknown or unreadable field refuses the whole request, and nothing is written.
func (s *Store) Update(ctx context.Context, target string, changes map[string]string) error {
	tx, err := s.Pool.Begin(ctx)
	if err != nil {
		return err
	}
	defer tx.Rollback(ctx)
	for f := range changes {
		if _, ok := profileFields[f]; !ok {
			return fmt.Errorf("unknown field %q", f)
		}
		var editable bool
		err := tx.QueryRow(ctx, `SELECT editable FROM field_rules WHERE field = $1 FOR SHARE`, f).Scan(&editable)
		if errors.Is(err, pgx.ErrNoRows) || (err == nil && !editable) {
			return fmt.Errorf("%w: %s", ErrFieldLocked, f) // no rule means no permission
		}
		if err != nil {
			return err // fail closed: a lookup error is a refusal, never a pass
		}
	}
	for f, v := range changes {
		if _, err := tx.Exec(ctx, `UPDATE profiles SET `+profileFields[f]+` = $2 WHERE user_id = $1`, target, v); err != nil {
			return err
		}
	}
	return tx.Commit(ctx)
}
```

Or one statement that carries the check inside the write, so there is nothing between them:

```go noverify
// profile.go, lines 128–155
// UpdateGuarded folds the permission check into the write itself. One statement, one snapshot:
// the row is updated only if every field named is present in field_rules AND editable at that instant.
// No lock is held between a check and a write, so an admin's change is never made to wait.
func (s *Store) UpdateGuarded(ctx context.Context, target string, changes map[string]string) error {
	var sets, names []string
	args := []any{target}
	for f, v := range changes {
		col, ok := profileFields[f]
		if !ok {
			return fmt.Errorf("unknown field %q", f)
		}
		args = append(args, v)
		sets = append(sets, fmt.Sprintf("%s = $%d", col, len(args)))
		names = append(names, f)
	}
	args = append(args, names, len(names))
	q := fmt.Sprintf(`UPDATE profiles SET %s WHERE user_id = $1
	    AND (SELECT count(*) FROM field_rules WHERE field = ANY($%d) AND editable) = $%d`,
		strings.Join(sets, ", "), len(args)-1, len(args))
	tag, err := s.Pool.Exec(ctx, q, args...)
	if err != nil {
		return err
	}
	if tag.RowsAffected() == 0 {
		return ErrFieldLocked // a locked field, an unknown rule or an unknown user: refused, nothing written
	}
	return nil
}
```

Same three-way test, all in one run:

```text
cached check (TTL 400 ms)            1702646 attempts, 1694126 refused,  8520 writes succeeded,  6461 of them started AFTER the lock committed; admin's change took 0 ms
check and write in one transaction     8348 attempts,      0 refused,  8348 writes succeeded,     0 of them started AFTER the lock committed; admin's change took 700 ms
one guarded statement                 46564 attempts,  44832 refused,  1732 writes succeeded,     0 of them started AFTER the lock committed; admin's change took 0 ms
```

Both correct designs have **0 writes that began after the lock**, and the difference is the last column. In the transaction version, `FOR SHARE` on the rule row makes the admin's `UPDATE` wait for every in-flight writer, and under constant load there is always one: the admin's change took **700 ms**, and in that time all 8,348 writes went through, because until the lock committed the field really was open. A permission change that lags by the length of your traffic spike is its own kind of bug. The guarded statement holds no lock between check and write: the admin's change took under a millisecond, and after it 44,832 of 46,564 attempts were refused. Reading the rule and applying the write in one statement is the design to reach for; the transaction with `FOR SHARE` is what to use when a single statement can't express the check.

The rules that fall out of this:

1. **Authorize before you mutate.** Never "apply, then validate". A denial that arrives after the write is not a denial.
2. **Fail closed on every path.** In `Update`, an unknown field, a missing rule and a failed lookup all return an error and write nothing. In `UpdateGuarded`, the `count(*) = $n` condition means a field with no rule is refused too. A different error code must never mean a different outcome for the data.
3. **Refuse the whole request** if any field is denied. `TestApplyThenCheck` shows the allowed `first_name` was also left untouched, because a half-applied update is its own inconsistency.
4. **Don't cache a permission longer than you can tolerate being wrong**, and never in a session. If you must cache, put a version on the rules and make the write carry it, so a stale version refuses instead of passing.
5. **Test the transition.** Change the rule while requests are in flight and assert that no write *starts after the change commits and succeeds*. That is the assertion the last column above makes, and a suite that only checks the two steady states passes this bug.

<Gotcha>
A writer that takes a shared lock on a rule can delay the admin who wants to change it, and that is a failure of its own. Whenever you add a lock to close a race, measure what it does to the *other* party. Here it was under 1 ms versus 700 ms.
</Gotcha>

<Callout kind="pro" title="Least privilege for service accounts">
The other half of the story is the service's own identity. A shared service account with broad reach is the confused deputy from stop 4 with a bigger vault: once any request is accepted, it can fetch whatever the account can. Give each service the narrowest role that works (see the `meridian_app` role in this chapter's schema: `SELECT, INSERT, UPDATE`, no `DELETE`), and separate the identity that owns the tables from the one that serves requests.
</Callout>

<Recap>

- Authorization has no environment parameter and no bypass flag; allow only for explicit pairs, deny everything else. Non-production shouldn't see real data at all.
- A grant must check the caller's authority, forbid escalation above their own role, and do both in one transaction with the caller's row locked.
- Decide before you write: apply-then-check changed an email while returning a denial. A cache that lags a rule change let 6,461 writes that started after the lock succeed; a check inside the write refused them, with the admin's change taking under 1 ms instead of 700.

</Recap>

## Errors as a Map

*Stop 6 of 7.*

### Step 1: what a 403 gives away

Access control also decides what you say on *failure*. Compare two versions of the account route. v1 answers 404 for both "doesn't exist" and "not yours". v2 answers 403 for "exists, not yours" and 404 for "doesn't exist", which feels friendlier. `TestOracle` walks ids 1001 to 4100 (the last 100 don't exist) as `acme-u3`, and tallies the status codes:

```text
v1: attacker separates real ids from fake ones via status alone: 0 confirmed-to-exist (403), 2850 404
v2: attacker separates real ids from fake ones via status alone: 2750 confirmed-to-exist (403), 100 404
```

v2 confirmed 2,750 real ids the caller doesn't own, and told them exactly which 100 were fake. That is an **enumeration oracle**: the status code alone maps your id space, which is the first step towards every other attack in this chapter. v1 says the same thing for both cases and reveals nothing.

### Step 2: what the database says

The other leak is the error text. When something inside fails, the raw message names tables, columns, constraints, sometimes hosts. `TestErrorSplit` makes the low-privilege app role attempt a `DELETE` it isn't allowed, and shows what the database said next to what the client should get:

```go noverify
// matrix_test.go, lines 49–54
type AppError struct {
	Public   string
	Internal error
}

func (e *AppError) Error() string { return e.Public }
```

```text
what the database said (log this): ERROR: permission denied for table accounts (SQLSTATE 42501)
what the client gets:              "could not update account"
```

Carry two messages on every error: a **public** one for the wire and an **internal** one for your logs. `Error()` returns only the public text, so even a careless `fmt.Sprint(err)` in a handler can't leak more. Chapter 12 kept secrets out of *logs* with `slog.LogValuer`; this keeps internals out of *responses*, and it is the same habit.

## Testing It Properly

### Step 1: the test nobody writes

Unit tests log in as Alice and check Alice sees Alice's data. Green. Nobody writes the test where Bob, fully logged in as himself, asks for Alice's account and must be refused, because the author of the handler wasn't thinking about Bob. That negative test is the entire subject, so build it as a **matrix**: for every route, every actor and every resource owner, assert allow or deny.

```go noverify
// matrix_test.go, lines 12–46
// One row per (route, actor, resource-owner). Every cross-principal cell must be a denial.
func TestMatrix(t *testing.T) {
	s, srv := newStore(t)
	ctx := context.Background()
	users := []string{"acme-u3", "acme-u4", "globex-u3", "initech-u3"}
	own := map[string]int64{}
	for _, u := range users {
		var id int64
		s.Pool.QueryRow(ctx, `SELECT min(id) FROM accounts WHERE owner_id=$1`, u).Scan(&id)
		own[u] = id
	}
	for _, v := range []string{"v0", "v1"} {
		cells, leaks := 0, 0
		var first string
		for _, actor := range users {
			for _, owner := range users {
				if actor == owner {
					continue
				}
				cells++
				code, _ := do(t, "GET", fmt.Sprintf("%s/%s/accounts/%d", srv.URL, v, own[owner]), actor, nil)
				if code == 200 {
					leaks++
					if first == "" {
						first = fmt.Sprintf("%s read %s's account %d", actor, owner, own[owner])
					}
				}
			}
		}
		t.Logf("GET /%s/accounts/{id}: %d cross-principal cells, %d leaked  %s", v, cells, leaks, first)
		if v == "v1" && leaks != 0 {
			t.Errorf("v1 leaked %d cells", leaks)
		}
	}
}
```

Four users (two at Acme, one at Globex, one at Initech) give 12 cross-principal cells per route: every actor against every other user's account. Run against both routes:

```text
GET /v0/accounts/{id}: 12 cross-principal cells, 12 leaked  acme-u3 read acme-u4's account 1004
GET /v1/accounts/{id}: 12 cross-principal cells, 0 leaked
```

The leaky route fails 12 of 12, and the test names the first violation. The fixed route passes with 0. The v1 half is a real assertion (`t.Errorf` on any leak), so this test breaks the build the day somebody removes an `AND owner_id` in a refactor.

- **Also test the legitimate case**: the owner must still get their own account (the lab below checks it). A test suite that only denies passes a service that denies everyone.
- **Mutation check**: temporarily delete a condition from a query and confirm a matrix cell turns red. If nothing fails, the matrix isn't covering it.

<Exercise n={1} title="Ownership-scoped fetch" level="easy">

Write `GetDoc(docs map[string]Doc, id, callerID string) (Doc, error)` where `Doc` has `ID`, `OwnerID`, and `Body` fields. Return `ErrNotFound` both when the document doesn't exist *and* when it exists but `callerID` is not the owner — the two cases must be indistinguishable to the caller. Demonstrate that a non-owner gets `ErrNotFound`, not the document.

<Solution>

```go
package main

import (
	"errors"
	"fmt"
)

type Doc struct {
	ID      string
	OwnerID string
	Body    string
}

var ErrNotFound = errors.New("not found")

func GetDoc(docs map[string]Doc, id, callerID string) (Doc, error) {
	d, ok := docs[id]
	if !ok || d.OwnerID != callerID {
		// Same error for "missing" and "not yours" — no existence oracle.
		return Doc{}, ErrNotFound
	}
	return d, nil
}

func main() {
	docs := map[string]Doc{
		"d1": {"d1", "alice", "alice's notes"},
		"d2": {"d2", "bob", "bob's notes"},
	}

	got, err := GetDoc(docs, "d1", "alice")
	fmt.Println("owner:", got.Body, err) // alice's notes <nil>

	_, err = GetDoc(docs, "d1", "mallory")
	fmt.Println("non-owner:", err) // not found

	_, err = GetDoc(docs, "d999", "alice")
	fmt.Println("missing:", err) // not found — identical to non-owner
}
```

Folding ownership into the lookup condition makes "not yours" and "doesn't exist" return the same error. The attacker learns nothing about which IDs are real.

<Exercise n={2} title="Tenant-scoped list and the two-user test" level="medium">

Write `ListForTenant(rows []Invoice, tenantID string) []Invoice` that returns only the rows whose `TenantID` matches. Then write a check that creates invoices for two tenants and asserts that each tenant's list contains *none* of the other's rows — the two-user test for collections.

<Solution>

```go
package main

import "fmt"

type Invoice struct {
	ID       string
	TenantID string
	Cents    int64
}

func ListForTenant(rows []Invoice, tenantID string) []Invoice {
	out := make([]Invoice, 0)
	for _, r := range rows {
		if r.TenantID == tenantID {
			out = append(out, r)
		}
	}
	return out
}

func leaks(list []Invoice, foreignTenant string) bool {
	for _, r := range list {
		if r.TenantID == foreignTenant {
			return true
		}
	}
	return false
}

func main() {
	rows := []Invoice{
		{"i1", "acme", 1000},
		{"i2", "globex", 2000},
		{"i3", "acme", 3000},

	globex := ListForTenant(rows, "globex")

	fmt.Printf("globex sees %d rows; leaks acme? %v\n", len(globex), leaks(globex, "acme"))

	// globex sees 1 rows; leaks acme? false
```

The `leaks` helper is the two-user test for a list: it fails the moment a tenant's results contain a foreign row. Run it for every collection endpoint.

<Exercise n={3} title="Default-deny authorizer" level="medium">

Write `Authorize(role, action string) bool` backed by an explicit allow-list map of roles to permitted actions. Unknown roles and unknown actions must return `false`. There must be no `env` parameter and no bypass — prove with a table that a ghost role and a typo'd action both deny.

<Solution>

```go
package main

import "fmt"

var policy = map[string]map[string]bool{
	"admin":   {"read": true, "write": true, "delete": true},
	"clerk":   {"read": true, "write": true},
	"auditor": {"read": true},
}

func Authorize(role, action string) bool {
	actions, ok := policy[role]
	if !ok {
		return false // unknown role
	}
	return actions[action] // missing key -> zero value false
}

func main() {
	cases := []struct {
		role, action string
		want         bool
	}{
		{"admin", "delete", true},
		{"clerk", "delete", false}, // not granted
		{"auditor", "read", true},
		{"ghost", "read", false},    // unknown role
		{"admin", "destory", false}, // typo'd action
	}
	for _, c := range cases {
		got := Authorize(c.role, c.action)
		ok := "ok"
		if got != c.want {
			ok = "MISMATCH"
		}
		fmt.Printf("%-7s %-8s -> %-5v [%s]\n", c.role, c.action, got, ok)
	}
}
```

`actions[action]` returns the zero value `false` for any action not in the map, so default-deny falls out of Go's map semantics. There is no parameter an environment could flip to bypass it.

</Solution>

<Exercise n={4} title="Grant guard: no self-authorizing escalation" level="hard">

Implement `Grant(bindings map[string]map[string]string, caller, target, resource, role string) error`. It must reject the grant unless the caller already holds `owner` on the resource, and must reject any attempt to grant a role ranked above the caller's own. Use a rank map `{viewer:1, editor:2, owner:3}`. Prove a stranger and an editor are both refused, and an owner may grant up to (but not above) their level.

<Solution>

```go
package main

import (
	"errors"
	"fmt"
)

var rank = map[string]int{"viewer": 1, "editor": 2, "owner": 3}

var (
	ErrNoAuthority = errors.New("caller lacks grant authority")
	ErrEscalate    = errors.New("cannot grant above your own role")
	ErrBadRole     = errors.New("unknown role")
)

func Grant(bindings map[string]map[string]string, caller, target, resource, role string) error {
	if _, ok := rank[role]; !ok {
		return ErrBadRole
	}
	res, ok := bindings[resource]
	if !ok {
		return ErrNoAuthority
	}
	callerRole, ok := res[caller]
	if !ok || rank[callerRole] < rank["owner"] {
		return ErrNoAuthority
	}
	if rank[role] > rank[callerRole] {
		return ErrEscalate
	}
	res[target] = role
	return nil
}

func main() {
	bindings := map[string]map[string]string{
		"proj/x": {"alice": "owner", "bob": "editor"},
	}

	fmt.Println(Grant(bindings, "mallory", "mallory", "proj/x", "owner")) // no authority
	fmt.Println(Grant(bindings, "bob", "carol", "proj/x", "viewer"))      // no authority (editor)
	fmt.Println(Grant(bindings, "alice", "carol", "proj/x", "owner"))     // <nil> (owner grants owner is allowed: equal, not above)
	fmt.Println(Grant(bindings, "alice", "dave", "proj/x", "superuser"))  // unknown role
}
```

Three gates — authority, role validity, and no-escalation — make the operation impossible to self-authorize. Note "equal" is permitted (`>` not `>=`): an owner may appoint another owner, but no one can mint a role above their own.

</Solution>

</Exercise>

<Exercise n={5} title="Safe error mapper" level="medium">

Write `ToClient(err error) string` that, given an `*AppError` (with `Public string` and `Internal error`), returns the `Public` message; for any other error type it returns a fixed `"internal error"`. The internal detail must never appear in the returned string. Demonstrate with an error whose internal text names a bucket and a service account.

<Solution>

```go
package main

import (
	"errors"
	"fmt"
)

type AppError struct {
	Public   string
	Internal error
}

func (e *AppError) Error() string { return e.Public }

func ToClient(err error) string {
	var ae *AppError
	if errors.As(err, &ae) {
		return ae.Public
	}
	return "internal error"
}

func main() {
	leaky := &AppError{
		Public:   "could not export report",
		Internal: errors.New("gs://meridian-prod-reports denied for svc-export@prod.iam"),
	}
	fmt.Println("client:", ToClient(leaky)) // could not export report

	raw := errors.New("pq: relation \"accounts_owner_idx\" does not exist")
	fmt.Println("client:", ToClient(raw)) // internal error — index name hidden
}
```

`errors.As` recovers the public message when present and collapses everything else to a generic string. The bucket name, the service account, and the Postgres index name all stay server-side.

</Solution>

</Exercise>

<Recap>

- **Broken access control is OWASP's #1 risk**, and it ships invisibly: the feature works for the legitimate user, and the missing check is absent from every test that logs in as one person.
- **BOLA**: one valid login read 3,000 of 3,000 accounts (2,750 not theirs) through an id-only lookup. Fold the principal into the query (`AND tenant_id AND owner_id`): 250 of 3,000, 0 foreign. Parameterize ids: `1001 OR true` returned 3,000 rows concatenated.
- **Roles are not ownership**: an admin rewrote another admin's password. Check ownership, and require the current secret for sensitive changes.
