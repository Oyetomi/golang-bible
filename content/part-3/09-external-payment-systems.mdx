<HeroCard label="Part 3 · Chapter 9" title="Integrating with External Payment Systems">

Meridian doesn't move money on its own. Card payments go through a **processor** (Stripe, Adyen, Checkout.com and the like), which talks to card networks and banks. Every payment is therefore a conversation with another company's systems, over the internet, in two directions: Meridian **calls** the processor to charge a card, and the processor **calls back** with webhooks as the charge moves from pending to succeeded to captured, or fails, or is refunded.

Both directions fail in ways Meridian's own code doesn't: the processor is slow, or down, or answers after Meridian gave up; webhooks arrive late, twice, out of order, or not at all, and anyone on the internet can send a request that looks like one. This chapter builds both sides and measures each failure against a processor service that behaves the way real ones do, including webhooks signed exactly as Stripe signs them.

Six stops. If you get lost, come back here:

1. **Timeouts.** A call to someone else's system must be able to give up.
2. **Retries and keys.** Trying again without charging twice.
3. **Circuit breakers.** Stopping the calls while the processor is down.
4. **Webhook signatures.** Believing only the processor.
5. **Answer fast.** Why webhooks are stored first and processed later.
6. **Order and truth.** Out-of-order events, state machines, and reconciliation.

## The lab bench

The **processor** is a separate Go HTTP service (`cmd/processor`) that behaves like a card processor seen from outside: `POST /v1/charges` honours `Idempotency-Key`, every charge produces three webhook events (`charge.pending`, `charge.succeeded`, `charge.captured`) delivered to Meridian with retries until it answers 2xx, and flags make it fail on purpose: refuse requests (503), answer late, stop answering, shuffle events, give up on webhooks. Its webhooks are signed with `webhook.ComputeSignature` from `github.com/stripe/stripe-go/v86` v86.4.2, so they're byte-for-byte what Stripe sends. Meridian's side is a Go 1.27 module, `psp`: a client (with `github.com/sony/gobreaker/v2` v2.4.0), a webhook receiver on PostgreSQL 14, and a reconciliation job.

## Timeouts

*Stop 1 of 6.*

### Step 1: no timeout is a timeout of forever

Go's `http.Client{}` has `Timeout: 0`, which means **no limit**. A request to a server that accepts the connection and never answers waits as long as the connection stays open. Each waiting checkout holds a goroutine, a TCP connection and, somewhere, a customer looking at a spinner.

### Step 2: measured

The processor stops answering; 50 checkouts start:

```text
== the processor stops answering
timeout 0s   after 5 s:  0 of 50 checkouts have an answer, 50 still waiting
timeout 2s   after 5 s: 50 of 50 checkouts have an answer,  0 still waiting
```

With the zero value, **all 50 were still waiting** after 5 seconds, and nothing in them would ever give up. With `Timeout: 2 * time.Second`, all 50 got an error at 2 s and could do something about it: show the customer an error, retry, or try another processor. Set a timeout on every client that talks to another system (`http.Client.Timeout`, or a context deadline per request, part 2's context chapter), and choose it from the other side's normal latency, not a round number.

## Retries & Keys

*Stop 2 of 6.*

### Step 1: a timeout creates uncertainty

A timeout ends the wait, but not the doubt: the processor may have charged the card and been slow to say so. Chapter 4 met this problem from the server's side. Here Meridian is the client, and the processor offers the same fix: an **`Idempotency-Key`** header. Meridian generates one key per payment and sends the **same key on every retry**; the processor charges once per key and replays its answer for repeats. Stripe keeps keys for 24 hours.

Retries also need **backoff** (wait longer after each failure, so a struggling processor isn't hit harder) and **jitter** (randomise the wait, so a thousand clients that failed together don't retry together):

```go noverify
// client.go, lines 23–85
// Client calls POST /v1/charges.
type Client struct {
	BaseURL string
	HTTP    *http.Client
	// Retries after the first attempt, on network errors and 5xx.
	Retries int
	// UseKeys sends one Idempotency-Key per charge, the same on every retry.
	UseKeys bool
	// Breaker, if set, fails calls fast while the processor is failing.
	Breaker *gobreaker.CircuitBreaker[Charge]
}

var ErrDeclined = errors.New("charge declined")

// Charge asks the processor to charge amount for merchant, once, however
// many attempts it takes.
func (c *Client) Charge(ctx context.Context, merchant string, amount int64) (Charge, error) {
	key := ""
	if c.UseKeys {
		key = fmt.Sprintf("%x", rand.Uint64())
	}
	var ch Charge
	var err error
	for attempt := 0; attempt <= c.Retries; attempt++ {
		if attempt > 0 {
			// Exponential backoff with full jitter: 0..100ms, 0..200ms, ...
			time.Sleep(time.Duration(rand.Int64N(int64(100*time.Millisecond) << attempt)))
		}
		if c.Breaker != nil {
			ch, err = c.Breaker.Execute(func() (Charge, error) { return c.once(ctx, key, merchant, amount) })
		} else {
			ch, err = c.once(ctx, key, merchant, amount)
		}
		if err == nil || errors.Is(err, ErrDeclined) || errors.Is(err, gobreaker.ErrOpenState) {
			return ch, err
		}
	}
	return ch, err
}

func (c *Client) once(ctx context.Context, key, merchant string, amount int64) (Charge, error) {
	body, _ := json.Marshal(map[string]any{"merchant": merchant, "amount": amount})
	req, err := http.NewRequestWithContext(ctx, "POST", c.BaseURL+"/v1/charges", bytes.NewReader(body))
	if err != nil {
		return Charge{}, err
	}
	if key != "" {
		req.Header.Set("Idempotency-Key", key)
	}
	resp, err := c.HTTP.Do(req)
	if err != nil {
		return Charge{}, err // timeout or connection error: unknown outcome, retry with the same key
	}
	defer resp.Body.Close()
	switch {
	case resp.StatusCode >= 500:
		return Charge{}, fmt.Errorf("processor: %s", resp.Status)
	case resp.StatusCode >= 400:
		return Charge{}, fmt.Errorf("%w: %s", ErrDeclined, resp.Status)
	}
	var ch Charge
	return ch, json.NewDecoder(resp.Body).Decode(&ch)
}
```

### Step 2: measured

The processor refuses 20% of requests with 503 and answers 5% of charges late (after 2 s, having charged). Meridian makes 1,000 payments with a 500 ms timeout and up to 5 retries, without and then with keys:

```text
== 20% of requests fail with 503, 5% are answered late (after 2 s); 500 ms timeout, 5 retries
keys false 1000 charges: 1000 succeeded, 0 failed; processor saw 1303 requests and made 1061 charges
keys true  1000 charges: 1000 succeeded, 0 failed; processor saw 1348 requests and made 1000 charges
```

Both runs: 1,000 of 1,000 succeeded, as far as Meridian could tell. Without keys, the processor **made 1,061 charges**: 61 customers charged twice, because a late answer looked like a failure and the retry was a new charge. With keys: 1,348 requests and **exactly 1,000 charges**. The retries still happened; the key made them harmless. (A 503 is safe to retry even without a key, because the processor refused before doing anything. A timeout never is.)

## Circuit Breakers

*Stop 3 of 6.*

### Step 1: stop calling what's broken

When the processor is down, every checkout still waits for its full timeout before failing, and every retry adds load to a system that's already failing. A **circuit breaker** (named after the electrical one) watches the calls: after enough consecutive failures it **opens**, and calls fail **immediately** without being made. After a pause it lets one call through (**half-open**); if that works, it **closes** again. The customer gets a fast "try again shortly" instead of a slow one, and the processor gets room to recover.

```go noverify
// main.go, lines 76–80
			c.Breaker = gobreaker.NewCircuitBreaker[psp.Charge](gobreaker.Settings{
				Name:        "processor",
				Timeout:     2 * time.Second, // stay open this long, then let one request try
				ReadyToTrip: func(n gobreaker.Counts) bool { return n.ConsecutiveFailures >= 5 },
			})
```

### Step 2: an eight-second outage

20 checkouts a second for 20 seconds, 1 s timeout; the processor stops answering from second 5 to second 13:

```text
== 20 checkouts/s for 20 s; the processor stops answering from 5 s to 13 s; 1 s timeout
breaker false 400 checkouts: 260 ok, 140 timed out, 0 refused fast; processor saw 400 requests; checkouts spent 2m31s waiting in all, p99 1.002s
breaker true  400 checkouts: 215 ok, 67 timed out, 118 refused fast; processor saw 242 requests; checkouts spent 27s waiting in all, p99 1.001s
```

Without the breaker, every one of the 160 checkouts during the outage waited the full second: 140 timed out, **2m31s** of customers waiting in total, and all 400 requests reached the struggling processor. With it, after 5 consecutive failures the breaker opened: 118 checkouts were **refused in microseconds**, the processor saw **242** requests instead of 400, and total waiting fell to **27 s**. The cost is visible too: 215 succeeded instead of 260, because the breaker stayed open for a moment after the processor had recovered (its 2 s timeout before trying again). The breaker's settings are that trade-off: how quickly to open, how long to stay open.

## Signatures

*Stop 4 of 6.*

### Step 1: anyone can call a URL

A webhook endpoint is a public URL that records payments as successful. If it believes every request, anyone who finds it can mark an order paid. So processors **sign** each webhook: Stripe computes an **HMAC-SHA256** of `timestamp.body` with a secret only it and Meridian know, and sends `Stripe-Signature: t=<timestamp>,v1=<hex signature>`. Meridian recomputes it; a match proves the body came from someone holding the secret and wasn't changed. The timestamp is inside the signed message, so it can't be altered, and a **tolerance** (Stripe's default: 5 minutes) rejects old requests replayed by someone who captured one.

```go noverify
// main.go, lines 70–118
	http.HandleFunc("POST /webhooks/processor", func(w http.ResponseWriter, r *http.Request) {
		received.Add(1)
		body, err := io.ReadAll(io.LimitReader(r.Body, 1<<20))
		if err != nil {
			http.Error(w, "read", http.StatusBadRequest)
			return
		}
		if *verify {
			// HMAC-SHA256 over "timestamp.body" with our secret, compared in
			// constant time; rejects timestamps older than 5 minutes.
			if err := webhook.ValidatePayload(body, r.Header.Get("Stripe-Signature"), *secret); err != nil {
				http.Error(w, err.Error(), http.StatusBadRequest)
				return
			}
		}
		var e event
		if err := json.Unmarshal(body, &e); err != nil {
			http.Error(w, "bad json", http.StatusBadRequest)
			return
		}
		if *drop > 0 {
			var n int
			fmt.Sscanf(e.Charge.ID, "ch_%d", &n)
			if n%*drop == 0 {
				http.Error(w, "internal error", http.StatusInternalServerError)
				return
			}
		}
		// Record it once, by the processor's event id.
		tag, err := db.Exec(r.Context(), `INSERT INTO webhook_inbox (event_id, type, payload) VALUES ($1, $2, $3) ON CONFLICT DO NOTHING`, e.ID, e.Type, body)
		if err != nil {
			http.Error(w, "db", http.StatusInternalServerError)
			return
		}
		accepted.Add(1)
		if tag.RowsAffected() == 0 {
			w.WriteHeader(http.StatusOK) // a redelivery: already have it
			return
		}
		if *inline > 0 {
			time.Sleep(*inline) // e.g. update the ledger, email the merchant, call the fraud service
			if err := apply(e); err != nil {
				http.Error(w, "db", http.StatusInternalServerError)
				return
			}
			applied.Add(1)
		}
		w.WriteHeader(http.StatusOK)
	})
```

(`webhook.ValidatePayload` is stripe-go's check: it parses the header, accepts any of several `v1` signatures, as sent during a secret rotation, compares with `hmac.Equal` so the time taken doesn't reveal how much of a guess was right, and enforces the tolerance.)

### Step 2: six requests

A genuine event, its redelivery, and four an attacker could send, first with the check and then without it:

```text
== forged and replayed webhooks, signature checked
genuine event, signed now                          HTTP 200 
the same event again (a redelivery)                HTTP 200 
forged event, no signature                         HTTP 400 webhook has no Stripe-Signature header
forged event, signed with a guessed secret         HTTP 400 webhook had no valid signature
genuine signature, body changed                    HTTP 400 webhook had no valid signature
genuine event, captured and replayed 10 min later  HTTP 400 timestamp wasn't within tolerance
charges recorded: ch_900001 1999
== the same requests, signature not checked
genuine event, signed now                          HTTP 200 
the same event again (a redelivery)                HTTP 200 
forged event, no signature                         HTTP 200
```

With verification, each forgery failed for its own reason: no header, a guessed secret, a body changed after signing, a genuine request replayed ten minutes later. Only `ch_900001` was recorded. Without verification, **every request was accepted**, and a forged `ch_666666` for **$5,000.00** was recorded as a successful charge. (The tampered body was recorded neither time, but only by luck: it reused the genuine event's id, and the inbox had already stored that id.)

## Answer Fast

*Stop 5 of 6.*

### Step 1: the processor is waiting too

A processor gives each webhook delivery a few seconds (this one gives 1 s) and treats anything else as a failure to retry. If the endpoint does its work before answering (updating the ledger, emailing the merchant, calling a fraud service), a slow moment turns into a timeout, and the processor sends the event again, while the first copy is still being processed.

### Step 2: measured

200 charges, 600 events. First the receiver does 1.5 s of work per event before answering; then it stores the event in its inbox (chapter 4) and answers at once, and a worker applies stored events:

```text
== 200 charges; receiver -inline 1500ms
processor: {"charge_requests":200,"charges":200,"events":600,"webhook_deliveries":1200}
receiver:  {"accepted":1200,"applied_inline":600,"received":1200}; charges captured: 200
== 200 charges; receiver stores the event, answers, works later
processor: {"charge_requests":200,"charges":200,"events":600,"webhook_deliveries":600}
receiver:  {"accepted":600,"applied_inline":0,"received":600}; charges captured: 200
```

Working inline: **1,200 deliveries** for 600 events. Every one timed out and was sent again; the inbox recognised the second copies, so nothing was applied twice, but the processor did double the work and, with a slower handler, would have gone on retrying and eventually given up. Storing first: **600 deliveries**, each answered in milliseconds. The rule: **verify, store, answer 200, then work**. The inbox makes the worker safe to run any number of times.

## Order & Truth

*Stop 6 of 6.*

### Step 1: events arrive in any order

Webhooks are sent concurrently and retried independently, so `charge.captured` can arrive before `charge.pending`. A receiver that sets the charge's state to whatever arrived last (**last write wins**) ends up wherever the last delivery happened to land. The fix is a **state machine**: states have an order (pending, then succeeded, then captured, then refunded), and an event may only move a charge forward. Here that rule is in the SQL, so it's checked under the row's lock:

```go noverify
// main.go, lines 49–68
	apply := func(e event) error {
		return pgx.BeginFunc(ctx, db, func(tx pgx.Tx) error {
			var err error
			if *lww {
				_, err = tx.Exec(ctx, `INSERT INTO charges VALUES ($1, $2, $3, $4)
					ON CONFLICT (id) DO UPDATE SET state = $3, state_at = $4`, e.Charge.ID, e.Charge.Amount, e.Type, e.Created)
			} else {
				// State machine: only move forward. Checked in SQL, under the row's lock.
				_, err = tx.Exec(ctx, `INSERT INTO charges VALUES ($1, $2, $3, $4)
					ON CONFLICT (id) DO UPDATE SET state = $3, state_at = $4
					WHERE (CASE charges.state WHEN 'charge.pending' THEN 1 WHEN 'charge.succeeded' THEN 2 ELSE 3 END) < $5`,
					e.Charge.ID, e.Charge.Amount, e.Type, e.Created, rank[e.Type])
			}
			if err != nil {
				return err
			}
			_, err = tx.Exec(ctx, `UPDATE webhook_inbox SET processed_at = now() WHERE event_id = $1`, e.ID)
			return err
		})
	}
```

300 charges, each charge's three events delivered in random order:

```text
== 300 charges, events delivered in random order; receiver -lww
final states: charge.captured 102, charge.pending 84, charge.succeeded 114
== 300 charges, events delivered in random order; receiver uses the state machine
final states: charge.captured 300
```

Last write wins: only **102 of 300** charges ended `captured`; 198 were left `pending` or `succeeded`, though every one had been captured. The state machine: **300 of 300**.

### Step 2: the processor is the source of truth

Webhooks can also simply not arrive: a bug in the endpoint, a deploy at the wrong moment, a processor that gives up. Here Meridian's handler failed every event of every 50th charge, and the processor gave up after 3 attempts. So Meridian also **reconciles**: it regularly fetches the processor's own list of charges and compares it with what it knows:

```go noverify
// main.go, lines 46–60
	var missing, wrong int
	for _, c := range theirs {
		amt, ok := known[c.ID]
		switch {
		case !ok:
			missing++
			// The processor charged it; we never heard. Record it from the processor's data.
			if _, err := db.Exec(ctx, `INSERT INTO charges VALUES ($1, $2, 'charge.captured', 0)`, c.ID, c.Amount); err != nil {
				log.Fatal(err)
			}
		case amt != c.Amount:
			wrong++
		}
	}
	fmt.Printf("processor: %d charges; Meridian knew %d; %d missing (now recorded), %d with a different amount\n", len(theirs), len(ours), missing, wrong)
```

```text
== 500 charges; our handler fails every event of every 50th charge; the processor gives up after 3 attempts
processor: 500 charges; Meridian knew 490; 10 missing (now recorded), 0 with a different amount
```

**10 charges** the processor had made that Meridian had never heard of: money taken from customers and owed to merchants, missing from the books. Reconciliation found every one and recorded it from the processor's data. Webhooks are the fast path; the processor's API, read on a schedule, is the truth, and chapter 10 on auditability builds this into a daily process.

## Exercises

These use the `psp` module, the processor and the database from this chapter.

<Exercise n={1} title="Retry only what's safe" level="easy">

Make the client retry 503s and network errors, but never a 400 or 402 (declined). Why does a declined card need no key to be safe?

<Solution>

`once` already returns `ErrDeclined` for 4xx, and `Charge` stops on it. A 4xx is a definite answer: the processor looked at the request and refused it, so nothing was charged and trying again gets the same answer. Keys protect against *unknown* outcomes, which only timeouts and connection errors produce.

</Solution>

</Exercise>

<Exercise n={2} title="Rotate the webhook secret" level="easy">

Rotate the signing secret without dropping webhooks. What do the processor and the receiver each do during the overlap?

<Solution>

The processor signs with both the old and new secrets for a period (Stripe sends one `v1` per active secret in the same header). The receiver first accepts either (verify against each, or rely on the multiple `v1` values), then, once every delivery carries the new signature, removes the old secret. The lab's rotation check tests the receiver side.

</Solution>

</Exercise>

<Exercise n={3} title="Per-merchant bulkheads" level="medium">

One merchant's traffic spikes and fills every connection to the processor, so other merchants' checkouts time out. Add a semaphore per merchant (or a small pool of them) around `Charge`, and measure other merchants' latency during a spike.

<Solution>

A buffered channel per merchant (capacity, say, 8) acquired before the call and released after caps how many of the processor's connections one merchant can hold. During the spike, the noisy merchant's extra requests queue (or are refused quickly) in its own compartment, and the others keep their usual latency. It's the bulkhead pattern from part 2's reliability chapter, applied per tenant.

</Solution>

</Exercise>

<Exercise n={4} title="Refunds out of order" level="medium">

Add `charge.refunded` as a fourth, later state and have the processor send it for some charges. What happens if the refund arrives before the capture, and what should the receiver do?

<Solution>

With the forward-only machine, refunded (rank 4) is applied, and the late capture (rank 3) is ignored: correct. But a refund can only follow a capture, so a refund for a charge Meridian has never seen captured is also a signal: record it, and let reconciliation confirm the capture from the processor's API rather than assuming. Money-moving states deserve an explicit transition table, not just a rank.

</Solution>

</Exercise>

<Exercise n={5} title="Reconcile amounts too" level="hard">

Extend `reconcile` to compare each charge's amount and state with the processor's, over a date range, in pages. What does it do with a charge whose amounts differ?

<Solution>

Page through `GET /v1/charges?created[gte]=...&starting_after=...` (Stripe's list API pattern) and compare each field. A different amount is never auto-repaired: it means someone's arithmetic or data is wrong, and money has moved on the processor's side for an amount Meridian didn't book. Record a discrepancy for a human, and post nothing to the ledger until it's understood (chapter 10's audit trail records the investigation).

</Solution>

</Exercise>

// some v1 value must equal hex(HMAC-SHA256(secret, "<t>.<body>")), compared
// in constant time, and t must be within 5 minutes of now (either way).
// During a secret rotation the header carries one v1 per active secret.
func verify(header string, body []byte, secret string, now time.Time) error {
	var t, sig string
	for _, part := range strings.Split(header, ",") {
		k, v, _ := strings.Cut(part, "=")
		switch k {
		case "t":
			t = v
		case "v1":
			if sig == "" {
				sig = v
			}
		}
	}
	m := hmac.New(sha256.New, []byte(secret))
	m.Write(body)
	if hex.EncodeToString(m.Sum(nil)) != sig {
		return errors.New("bad signature")
	}
	_ = t
	return nil
}

<Recap>

- **Timeouts**: `http.Client{}` never gives up (0 of 50 checkouts answered after 5 s against a stalled processor); a 2 s timeout answered all 50.
- **Retries and keys**: retry with exponential backoff and jitter, and one Idempotency-Key per payment. Without keys, 1,000 payments became 1,061 charges; with them, exactly 1,000.
- **Circuit breakers**: open after repeated failures, fail fast, probe, close. During an 8 s outage: 242 requests to the processor instead of 400, 27 s of customer waiting instead of 2m31s, at the cost of 45 successes just after recovery.
- **Signatures**: HMAC-SHA256 over timestamp.body, constant-time comparison, 5-minute tolerance, several v1 values during rotation. Without the check, a forged $5,000 charge was recorded.
- **Answer fast**: verify, store in the inbox, answer 200, work later. Inline work doubled deliveries (1,200 for 600 events).
- **Order and truth**: a forward-only state machine (300 of 300 correct, against 102 of 300 with last-write-wins), and reconciliation against the processor's API (found 10 charges webhooks never delivered).

</Recap>
