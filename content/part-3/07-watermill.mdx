## Why Watermill

<Define term="Watermill" since="Event-Driven Architecture & Kafka (Part 3)">
**Watermill** (`github.com/ThreeDotsLabs/watermill`) is a third-party Go library for building event-driven services. It defines a thin `Publisher` / `Subscriber` interface that any message broker can implement, then provides a **Router** that dispatches messages to handler functions with composable middleware. The payoff: swap Kafka for NATS or an in-memory channel by changing one constructor call — your handlers never notice.
</Define>

Here's the problem we're solving, and it's embarrassingly common.

Meridian's payments service publishes a `payment.completed` event to Kafka. The ledger-projection handler, the notification handler, and the fraud-check handler all subscribe to it. Beautiful. Then someone decides that for the settlement flow you need NATS Streaming, and for the test suite you absolutely cannot be spinning up a real Kafka cluster in CI. Now you have three message-broker SDKs, three sets of connection boilerplate, three subtly different delivery semantics to manage, and a handler that reads Kafka-specific `kafka.Message` types instead of a clean domain event. You have built infrastructure coupling into your business logic.

**On the job:** Broker migrations are more common than they sound — compliance mandates, cost changes, cloud provider switches. If your handlers import broker-specific types, every migration is a handler rewrite. That is months of risk for zero business value.

Watermill's answer is the same answer Go always gives: **define an interface and hide the broker behind it.**

## Publisher and Subscriber

<Define term="Publisher / Subscriber abstraction" since="Messaging & Pub/Sub Foundations (Part 3)">
The **Publisher/Subscriber abstraction** is Watermill's core. Two small interfaces — `Publisher` (send messages to a topic) and `Subscriber` (receive messages from a topic) — hide every broker behind the same contract. Kafka, NATS, RabbitMQ, and the in-process `GoChannel` all satisfy the same two interfaces. Your handlers, Router, and middleware operate exclusively against these interfaces and are therefore broker-agnostic.
</Define>

Everything in Watermill descends from two interfaces. If you understand these, you understand everything that follows.

```go
// Publisher publishes messages to a named topic.
// Close releases broker resources.
type Publisher interface {
    Publish(topic string, messages ...*message.Message) error
    Close() error
}

// Subscriber subscribes to a named topic and returns a read-only
// channel of messages. The channel closes when ctx is cancelled or
// Close is called.
type Subscriber interface {
    Subscribe(ctx context.Context, topic string) (<-chan *message.Message, error)
    Close() error
}
```

Two interfaces. That's the whole broker abstraction. Any broker that can publish and consume messages can satisfy these two interfaces, and Watermill ships adapters for the most common ones. But let's look at what travels over those channels.

### The `message.Message`

<Define term="message.Message (Ack/Nack)">
A `message.Message` is Watermill's universal message envelope. It carries a **UUID** (the idempotency key), **Metadata** (a `map[string]string` for trace IDs and headers), and a **Payload** (`[]byte` — usually JSON or Protobuf). Critically, it owns the delivery acknowledgement: calling `msg.Ack()` tells the broker the message was processed successfully; calling `msg.Nack()` asks for redelivery. The Router calls Ack or Nack on your behalf — handlers just return `nil` or an error.
</Define>

A Watermill `message.Message` is a tiny struct with four fields:

```go
// From github.com/ThreeDotsLabs/watermill/message
type Message struct {
    UUID     string          // unique ID for deduplication (idempotency key — see Idempotency & Exactly-Once Semantics, Part 3)
    Metadata Metadata        // map[string]string — correlation IDs, tracing headers, etc.
    Payload  []byte          // the actual body — usually JSON, Protobuf, or Avro
    // unexported: Ack/Nack channels
}

// Ack tells the broker: "I processed this successfully, advance the offset."
func (m *Message) Ack() bool { ... }

// Nack tells the broker: "I failed, redeliver this message."
func (m *Message) Nack() bool { ... }
```

The `Ack()` and `Nack()` calls are the hooks that drive Watermill's at-least-once delivery. We'll animate exactly how the Router uses them in the next section — but the key point right now is that **Ack/Nack are on the message, not the consumer**. Your handler doesn't call any broker-specific API; it just returns `nil` (which the Router translates to Ack) or an error (which the Router translates to Nack and optionally retries).

**On the job:** A handler that swallows errors and returns `nil` always Acks — even on failures. You will silently lose `payment.completed` events and the ledger will be wrong. Return errors honestly; let the Router and middleware decide what to do with them.

### The `GoChannel` — your test double

Watermill ships `github.com/ThreeDotsLabs/watermill/pubsub/gochannel`. It is a fully in-process Publisher/Subscriber backed by Go channels. No network, no broker, no Docker. It implements *exactly* the same `Publisher` and `Subscriber` interfaces as the Kafka adapter, which means:

```go
// In your test:
broker := gochannel.NewGoChannel(
    gochannel.Config{
        OutputChannelBuffer:            0,     // synchronous delivery for tests
        Persistent:                     false, // in-memory only
        BlockPublishUntilSubscriberAck: false,
    },
    watermill.NewStdLogger(false, false),
)

// In production, same interface, different constructor:
broker, err := kafka.NewPublisher(
    kafka.PublisherConfig{
        Brokers: []string{"kafka:9092"},
        // ...
    },
    watermill.NewSlogLogger(slog.Default()),
)
```

The handler doesn't change. The Router doesn't change. The middleware doesn't change. Only the constructor changes. This is the entire value proposition — don't let anyone tell you it's more complicated than that.

## The Router

<Define term="the Router">
The **Router** is Watermill's central dispatcher. You register handlers with it (`AddHandler`), add middleware globally (`AddMiddleware`), then call `router.Run(ctx)`. The Router spawns one goroutine per handler, feeds it messages from the subscribed topic, runs the composed middleware chain, and calls `msg.Ack()` or `msg.Nack()` based on the handler's return value. You do not manage goroutines, channels, or Ack/Nack directly — the Router owns all of that.
</Define>

The `Router` is the heart of Watermill. It's the component that watches subscriber channels, dispatches incoming messages to the right handler, manages the Ack/Nack lifecycle, and runs your middleware chain. Every production Watermill service has exactly one Router.

### Handler registration

```go
router, err := message.NewRouter(
    message.RouterConfig{
        // How long to wait for handlers to finish on graceful shutdown.
        CloseTimeout: 30 * time.Second,
    },
    logger,
)
if err != nil {
    return fmt.Errorf("creating router: %w", err)
}

// AddHandler wires: subscriber → topic → handler → publisher → topic.
// The handler's return value is re-published to the output topic (optional).
router.AddHandler(
    "ledger-projection",       // handler name (used in logs and metrics)
    "payment.completed",       // input topic — subscribed via sub
    sub,                       // the Subscriber (Kafka, GoChannel, etc.)
    "ledger.events",           // output topic — the handler's return is published here
    pub,                       // the Publisher (can be nil if no output)
    handlePaymentCompleted,    // your HandlerFunc
)

// Run blocks until ctx is cancelled (graceful shutdown).
if err := router.Run(ctx); err != nil {
    return fmt.Errorf("router: %w", err)
}
```

The handler signature is one of the cleanest things in Go:

```go
// HandlerFunc is the function signature for a Watermill handler.
// Receive *message.Message, return []*message.Message (or nil), error.
// The returned messages are published to the output topic.
// Return nil, nil for a "consume-only" handler (no output to publish).
type HandlerFunc func(msg *message.Message) ([]*message.Message, error)

func handlePaymentCompleted(msg *message.Message) ([]*message.Message, error) {
    var event PaymentCompletedEvent
    if err := json.Unmarshal(msg.Payload, &event); err != nil {
        // Bad payload — we don't want to retry this forever.
        // Return nil, nil to Ack and discard (or let the poison-queue middleware catch it).
        return nil, err
    }

    // Apply the event to the ledger projection.
    if err := applyToLedger(msg.Context(), event); err != nil {
        return nil, err // Nack → retry (broker redelivers or middleware retries locally)
    }

    // Emit a downstream event to the output topic.
    out := message.NewMessage(watermill.NewUUID(), marshalLedgerEntry(event))
    return message.Messages{out}, nil
}
```

Notice: no broker types, no Kafka offsets, no NATS subjects. Just a function. This is what broker-agnostic looks like in practice.

<UnderTheHood title="How the Router runs: one goroutine per handler registration">

When `router.Run(ctx)` is called, the Router spawns **one goroutine per registered handler**. Each goroutine sits in a loop: `for msg := range subscriberChannel`. When a message arrives, it calls the composed middleware chain (which wraps your HandlerFunc). On success it Acks; on final failure it Nacks.

The key implementation detail: **middleware composition is just function wrapping**. The Router's internal type is:

```go
type HandlerFunc func(msg *message.Message) ([]*message.Message, error)

type HandlerMiddleware func(h HandlerFunc) HandlerFunc
```

When you call `router.AddMiddleware(m1, m2, m3)`, the Router builds a composed handler:

```go
composed := m1(m2(m3(yourHandler)))
```

This is the exact same pattern as Go's `http.Handler` middleware — a decorator chain of functions, each wrapping the next. The outermost middleware runs first on the way in, last on the way out. This is why **middleware order matters**: correlation-ID must be outermost (so it stamps the ID before anything else logs), retry must wrap the inner logic (so it can re-invoke it), and poison-queue must be the innermost wrapper around the handler (so it catches *final* failures after retry gives up).

As of Go 1.26, the goroutine-per-handler model is efficient: goroutines are cheap (a few KB of initial stack, grown dynamically), and the GMP scheduler multiplexes them onto OS threads without you thinking about it. The Router's `CloseTimeout` gives in-flight handlers time to finish their current message before the process exits — this is how you drain gracefully without dropping messages. (This is a simplification of the Router's internal loop; the real source handles more edge cases around subscriber closure and context cancellation.)

</UnderTheHood>

## Middleware

<Define term="middleware (in messaging)" since="Design Patterns, the Go Way (Part 1)">
In Watermill, **middleware** is a function of type `func(HandlerFunc) HandlerFunc` — it wraps a handler with additional behaviour (retry, recovery, tracing) without the handler knowing. Middleware composes by wrapping: `m1(m2(m3(handler)))`. The outermost middleware runs first on the way in and last on the way out, so **order determines behaviour**. This is the same decorator pattern as Go's `http.Handler` middleware chain.
</Define>

**On the job:** Middleware is the correct place for cross-cutting concerns (retry, DLQ, trace IDs). A handler that implements its own retry loop is not testable, not reusable, and silently breaks when you add a second handler that needs the same logic.

Middleware is where Watermill goes from "nice abstraction" to "production-grade infrastructure." The four middlewares you'll use in every payments service:

### 1. Retry

```go
// middleware.Retry retries failed handlers with exponential backoff.
// If the handler still fails after MaxRetries, it returns the last error
// (which the poison-queue middleware or the Router will then Nack).
retryMiddleware := middleware.Retry{
    MaxRetries:      5,
    InitialInterval: 100 * time.Millisecond,
    MaxInterval:     10 * time.Second,
    Multiplier:      2.0,
    // Jitter prevents the thundering-herd problem (covered in "Reliability Patterns (Part 2)").
    MaxElapsedTime:  2 * time.Minute,
    Logger:          logger,
}.Middleware
```

This directly applies the retry-with-backoff-and-jitter pattern from "Reliability Patterns (Part 2)" — but now it's middleware, applied uniformly to every handler in the Router, without each handler needing to implement its own retry loop.

### 2. Poison Queue (Dead-Letter Queue)

```go
// PoisonQueue catches messages that still fail after retry budget is exhausted.
// Instead of Nacking them (which would cause infinite redelivery from the broker),
// it publishes them to a separate "dead letter" topic for human inspection.
poisonQueue, err := middleware.NewPoisonQueue(
    publisher,
    "payment.completed.dlq", // DLQ topic — operators consume this for manual replay
)
if err != nil {
    return fmt.Errorf("poison queue: %w", err)
}
```

This implements the DLQ pattern from "Event-Driven Architecture & Kafka (Part 3)." The key insight: a message that fails repeatedly is **not the same problem** as a message that fails transiently. Transient failures get retried. Poison messages (bad payload, schema mismatch, unexpected data) should be parked for investigation — not looped forever. The PoisonQueue middleware makes this automatic.

**On the job:** Without a DLQ, a single malformed `payment.completed` event can stall an entire consumer group. The partition offset never advances, the handler loops forever on the bad message, and every subsequent event — valid ones — piles up behind it. The DLQ breaks the loop and lets the partition drain.

### 3. Correlation ID

```go
// CorrelationID propagates a trace ID through the message metadata.
// It reads the ID from msg.Metadata["correlation_id"] if present,
// or generates a new UUID if this is the originating message.
// The ID is stored in the context so your handler can attach it to slog/OTEL spans.
router.AddMiddleware(middleware.CorrelationID)
```

The `CorrelationID` middleware stamps every message with a `correlation_id` in its metadata. When your handler publishes downstream messages (e.g. the ledger entry event), those messages inherit the same correlation ID. You now have a chain from the original payment event all the way through every downstream effect — observable across services, for free.

### 4. Recovery

```go
// Recoverer catches panics in handlers and converts them to errors,
// preventing one bad message from killing the entire Router goroutine.
router.AddMiddleware(middleware.Recoverer)
```

Panics in a handler goroutine would crash the goroutine and stall that handler slot forever (messages pile up, offsets never commit). The Recoverer middleware catches panics, logs them as structured errors, and Nacks the message — the Router stays alive and the DLQ catches the bad message.

### Wiring the full middleware stack

Order matters. Here is the correct order, and why:

```go
// Apply middlewares to the router (affects ALL handlers).
// Order: outermost to innermost — first listed runs first on entry.
router.AddMiddleware(
    // 1. Correlation ID — outermost: stamps the ID before anything else runs.
    //    Every subsequent log line, metric, and span carries this ID.
    middleware.CorrelationID,

    // 2. Recoverer — catches panics *after* correlation is stamped,
    //    so the panic log carries the trace ID.
    middleware.Recoverer,

    // 3. Retry — re-invokes the handler on transient errors.
    retryMiddleware,

    // 4. Poison Queue — innermost wrapper around the handler.
    //    It catches errors that *survived* the retry budget.
    poisonQueue.Middleware,
)
```

## CQRS, Event Sourcing and the Outbox

<Define term="CQRS" since="Event-Driven Architecture & Kafka (Part 3)">
**CQRS** (Command Query Responsibility Segregation) splits a service's write path from its read path. A **command** mutates state and has exactly one handler (point-to-point). An **event** announces that state changed and has zero or more handlers (fan-out). In Watermill, the `CommandBus` routes commands to one handler; the `EventBus` fans out events to all subscribers. The result: `ProcessPayment` is a command owned by one service; `PaymentCompleted` is an event that the ledger, notification, and fraud services each handle independently.
</Define>

<Define term="the Forwarder / outbox" since="Idempotency & Exactly-Once Semantics (Part 3)">
The **transactional outbox** pattern solves the dual-write problem: you must write to the DB *and* publish an event, but you cannot do both atomically with a single broker call. The solution: write the event to an **outbox table** in the same DB transaction as your domain write, then have a background process (Watermill's **Forwarder**) poll the outbox and deliver to the broker. If the process crashes before delivery, the outbox record survives and the Forwarder retries. You get atomicity without a distributed transaction.
</Define>

**On the job:** The dual-write problem is the source of "ghost payments" — a payment debited from the account but never reflected in the ledger because the event publish failed after the DB commit. The outbox + Forwarder is the standard fix. If you see a discrepancy between your DB state and your event log, this pattern is missing.

Now we assemble the full pattern stack. This is what the last four chapters have been building toward.

### The Transactional Outbox with Watermill's Forwarder

The transactional outbox pattern ("Idempotency & Exactly-Once Semantics (Part 3)") ensures that writing to your DB and publishing an event are atomic — you write both in one database transaction, then a background process forwards the event to the broker. Watermill ships the `Forwarder` component for exactly this.

```go
import "github.com/ThreeDotsLabs/watermill/components/forwarder"

// The Forwarder polls the outbox table (written in the same DB tx as your domain write)
// and publishes pending messages to the broker, then deletes them.
// It uses the same Publisher/Subscriber abstraction — swap brokers without touching this code.

fwd, err := forwarder.NewForwarder(
    outboxSubscriber, // Subscriber reading from the outbox (e.g. a DB-backed sub)
    publisher,        // Publisher writing to the real broker
    logger,
    forwarder.Config{
        ForwarderTopic: forwarder.TopicPrefix + "payment.completed",
    },
)
if err != nil {
    return fmt.Errorf("forwarder: %w", err)
}

// Run the forwarder alongside the router in a goroutine.
go fwd.Run(ctx)
```

The write path — the "transactional" part:

```go
// In your ProcessPaymentHandler:
func processPayment(
    ctx context.Context,
    tx *sql.Tx,      // the DB transaction for your domain write
    pub message.Publisher, // an outbox publisher that writes INTO the tx
    cmd *ProcessPaymentCommand,
) error {
    // 1. Debit the account — domain write, inside the tx.
    if err := debitAccount(ctx, tx, cmd.AccountID, cmd.AmountCents); err != nil {
        return err
    }

    // 2. Write the event to the outbox — same tx, so it's atomic with step 1.
    //    If the process crashes between step 1 and the broker publish,
    //    the outbox record survives and the Forwarder will retry it.
    outboxMsg := message.NewMessage(cmd.PaymentID, marshalPaymentCompleted(cmd))
    if err := pub.Publish("_outbox.payment.completed", outboxMsg); err != nil {
        return err // tx rolls back — atomicity preserved
    }

    // 3. Commit. Either both changes land, or neither does.
    return tx.Commit()
}
```

This ties together "Idempotency & Exactly-Once Semantics (Part 3)" (idempotency key = `cmd.PaymentID` as `msg.UUID`), "Event-Driven Architecture & Kafka (Part 3)" (the outbox pattern described for Kafka), and now Watermill's `Forwarder` as the Go implementation.

<UnderTheHood title="How the Router's ack/nack drives at-least-once delivery">

Under the hood, the Router's goroutine for each handler runs this loop (simplified from the Watermill source):

```go
for {
    select {
    case msg, ok := <-subscriberChan:
        if !ok {
            return // subscriber closed, Router is shutting down
        }
        // Run the full middleware chain (correlation → recovery → retry → DLQ → handler).
        producedMessages, err := composedHandler(msg)
        if err != nil {
            msg.Nack() // broker will redeliver
            continue
        }
        // Publish output messages before Acking the input.
        // If this publish fails, we Nack so the input is redelivered and re-processed.
        if err := publishOutputs(producedMessages); err != nil {
            msg.Nack()
            continue
        }
        msg.Ack() // only now do we commit the offset

    case <-ctx.Done():
        return // graceful shutdown
    }
}
```

The critical ordering: **output messages are published before the input is Acked**. This ensures at-least-once delivery of the *entire pipeline*: if the process crashes after posting the ledger entry but before Acking the input, the input message is redelivered and the handler runs again. This is why your handlers must be **idempotent** (see "Idempotency & Exactly-Once Semantics (Part 3)") — they will run at least once, and possibly more than once.

The `msg.Ack()` and `msg.Nack()` calls on the `GoChannel` use a simple `select` on a `chan struct{}` inside the message — they're non-blocking once delivered. On the Kafka adapter, `Ack()` commits the consumer-group offset via the underlying Kafka client library (Watermill supports multiple: `sarama`, `confluent-kafka-go`, and others). The broker-specific behaviour is hidden inside the adapter, behind the same two methods. That's the interface abstraction paying for itself.

As of Go 1.26: the GMP scheduler handles the Router's goroutines efficiently. With `GOMAXPROCS` cores available, handler goroutines for different topics run truly in parallel. A slow handler on one topic does not block handlers on other topics. (Deep dive on GMP scheduling: "The Go Scheduler (GMP), In Depth (Part 2)".)

</UnderTheHood>

### A stdlib-only middleware chain illustration

To show the wrapping pattern concretely without any Watermill imports, here is the same decorator-chain idea in pure stdlib:

<GoPlayground>

```go
package main

import (
	"errors"
	"fmt"
	"time"
)

// HandlerFunc mirrors Watermill's handler signature (simplified to one return).
type HandlerFunc func(payload string) error

// Middleware wraps a HandlerFunc with additional behaviour.
type Middleware func(next HandlerFunc) HandlerFunc

// retryMiddleware retries the handler up to maxAttempts times.
func retryMiddleware(maxAttempts int) Middleware {
	return func(next HandlerFunc) HandlerFunc {
		return func(payload string) error {
			var lastErr error
			for attempt := range maxAttempts {
				lastErr = next(payload)
				if lastErr == nil {
					return nil
				}
				fmt.Printf("  [retry] attempt %d failed: %v\n", attempt+1, lastErr)
				time.Sleep(10 * time.Millisecond) // tiny sleep for demo
			}
			return fmt.Errorf("gave up after %d attempts: %w", maxAttempts, lastErr)
		}
	}
}

// correlationIDMiddleware stamps a fake correlation ID.
func correlationIDMiddleware(next HandlerFunc) HandlerFunc {
	return func(payload string) error {
		fmt.Printf("  [correlationID] tracing: corr-abc-123\n")
		return next(payload)
	}
}

// compose builds the chain: first middleware is outermost (runs first).
func compose(h HandlerFunc, middlewares ...Middleware) HandlerFunc {
	// Apply in reverse so the first in the slice is the outermost wrapper.
	for i := len(middlewares) - 1; i >= 0; i-- {
		h = middlewares[i](h)
	}
	return h
}

func main() {
	attempts := 0

	// A handler that fails twice, then succeeds.
	handler := func(payload string) error {
		attempts++
		if attempts < 3 {
			return errors.New("transient error")
		}
		fmt.Printf("  [handler] processed payload: %q\n", payload)
		return nil
	}

	// Wire: correlationID (outermost) → retry → handler (innermost).
	composed := compose(handler,
		correlationIDMiddleware,
		retryMiddleware(5),
	)

	fmt.Println("--- dispatching message ---")
	if err := composed("payment.completed: {id:42, cents:9999}"); err != nil {
		fmt.Println("final error:", err)
	} else {
		fmt.Println("--- message processed successfully ---")
	}
}
```

</GoPlayground>

The `compose` function and the `Middleware` type are structurally identical to what Watermill does internally — just without the `*message.Message` type and the broker plumbing. The wrapping pattern is plain Go closures all the way down.

func CorrelationID(next HandlerFunc) HandlerFunc {

        id := msg.Metadata.Get("correlation_id")

2. Executes `INSERT INTO payments VALUES (...)` inside the tx.

```go
func processPaymentTx(
    ctx context.Context,
    tx *sql.Tx,
    pub message.Publisher,
    cmd *ProcessPaymentCommand,
) error {
    // 1. Domain write — the authoritative record.
    _, err := tx.ExecContext(ctx,
        `INSERT INTO payments (id, account_id, amount_cents, created_at)
         VALUES ($1, $2, $3, NOW())`,
        cmd.PaymentID, cmd.AccountID, cmd.AmountCents,
    )
    if err != nil {
        return fmt.Errorf("insert payment: %w", err)
    }

    // 2. Outbox write — same transaction, guaranteed atomic with step 1.
    //    msg.UUID == cmd.PaymentID: the idempotency key doubles as the
    //    message UUID for deduplication downstream (see "Idempotency & Exactly-Once Semantics (Part 3)").
    payload, err := json.Marshal(PaymentCompletedEvent{
        PaymentID:   cmd.PaymentID,
        AccountID:   cmd.AccountID,
        AmountCents: cmd.AmountCents,
    })
    if err != nil {
        return fmt.Errorf("marshal event: %w", err)
    }

    outboxMsg := message.NewMessage(cmd.PaymentID, payload)
    if err := pub.Publish("_outbox.payment.completed", outboxMsg); err != nil {
        return fmt.Errorf("publish to outbox: %w", err)
    }

    return nil // caller commits — or rolls back if this returned an error
}
```

The two writes (domain + outbox) succeed or fail together because they share the same `*sql.Tx`. If the process crashes after `tx.Commit()` but before the Forwarder delivers to the broker, the outbox record is still in the DB and the Forwarder will deliver it on the next poll. At-least-once delivery, guaranteed. The `msg.UUID = cmd.PaymentID` ties idempotency from "Idempotency & Exactly-Once Semantics (Part 3)" directly to Watermill's deduplication hook.

<Recap>

You now own the full Watermill stack:

- **The abstraction:** `Publisher` and `Subscriber` are two interfaces. Any broker that implements them is interchangeable. The `GoChannel` in-process broker makes your tests fast and deterministic — no Docker required.
- **`message.Message`:** UUID (idempotency key), payload (bytes), metadata (string map for trace IDs), and `Ack()`/`Nack()` for delivery acknowledgement. Return `nil` from your handler to Ack; return an error to Nack.
- **The Router:** one goroutine per handler, runs the composed middleware chain, owns the Ack/Nack lifecycle. Output messages are published *before* the input is Acked — at-least-once semantics enforced by design.
- **Middleware order:** correlation ID outermost (stamps IDs first), then recovery (catch panics), then retry (retry transients), then poison queue innermost (DLQ final failures). The order is not style — it determines behavior.
- **CQRS wiring:** `CommandBus` for point-to-point commands, `EventBus` for fan-out events. Handlers are plain structs with a `Handle(ctx, cmd/event)` method. The Router and broker are injected — your handlers stay broker-free.
- **The outbox:** write domain record + outbox message in one DB transaction. The `Forwarder` polls and delivers. If the process crashes before delivery, the outbox record survives. `msg.UUID == idempotencyKey` ties back to "Idempotency & Exactly-Once Semantics (Part 3)" — the same key deduplicates both the payment and the event.
- **Under the hood:** middleware composition is decorator-chaining of `HandlerFunc` wrappers. The GMP scheduler multiplexes Router goroutines across Ps with no special configuration needed.
