## The lab bench

Kafka **4.3.1** (the `apache/kafka` Docker image) as a real cluster: one **controller** and three **brokers**, each broker a separate container. A broker is a Kafka server that stores data and serves clients; the controller keeps the cluster's metadata (which topics exist, which broker leads which partition). Since Kafka 4.0 that metadata lives in Kafka's own Raft log, called **KRaft**, and ZooKeeper is gone.

The Go side is one module, `kf`, on Go 1.27, using **franz-go v1.22.0** (`github.com/twmb/franz-go/pkg/kgo`, the client, and `pkg/kadm` v1.19.0, its admin helpers) and `pgx` v5.11.0 for the Postgres parts. franz-go is a pure-Go Kafka client (no C library), written against Kafka's protocol directly; `segmentio/kafka-go` and Confluent's `confluent-kafka-go` are the other common choices. Each experiment is a program in `cmd/`, driven by a shell script that starts, stops and kills things.

## The Log

*Stop 1 of 6.*

### Step 1: a file that only grows

Start with the simplest thing that could store events: a file. Each new event is written at the end. Nothing is ever changed in place, and nothing is removed because it was read. Each event gets a number, its position in the file: the first is 0, the next 1, and so on. That number is the event's **offset**.

<Define term="Offset">The position of a record in a Kafka partition's log: 0 for the first, then 1, 2, 3, never reused. A consumer's progress is just "the next offset I haven't read", one number per partition.</Define>

A Kafka **topic** is a named set of such logs. Meridian's topic is called `payments`. The logs inside it are its **partitions** (stop 2 is about why there are several). A **record** is one entry: an optional **key** (here, the merchant id), a **value** (the event's bytes, here JSON), a timestamp and optional headers. Kafka never looks inside the value.

The design is older than Kafka. Databases have always had a write-ahead log, an append-only file of changes that is the real source of truth, with the tables as a view of it. LinkedIn built Kafka in 2010 around the same idea for events between services: in Jay Kreps's words, "the log" as the unifying abstraction. Appending to the end of a file and reading it front to back are the two fastest things a disk does, which is why one broker can take hundreds of thousands of events a second.

### Step 2: readers keep a bookmark

Chapter 5's Redis consumer group tracked each entry: pending under a consumer's name until acknowledged. Kafka tracks much less. For each **consumer group** and each partition, it stores one number: the **committed offset**, the next offset that group should read. A consumer reads from there, and every so often **commits** a new number. Nothing about the records changes. So:

- Four services reading the same topic are four groups with four sets of bookmarks. Nobody's reading affects anybody else's.
- Reading an event twice costs nothing extra: the log still has it. Moving a bookmark back is a **replay**.
- Records are removed only by **retention**, a time or size limit per topic (7 days by default), whether anyone has read them or not.

### Step 3: produce, then read with four groups

The producer (`cmd/produce`) sends 10,000 payment events for 20 merchants, each keyed by its merchant. This is the heart of it: build a record, hand it to the client, and get told later, in a callback, whether the brokers stored it.

Read `cl.Produce(ctx, r, func(...) { ... })` as "queue this record to be sent, and call this function when the broker has answered". `Produce` returns at once. The client collects records into **batches**, one per partition, and sends a batch when it's full or when it has waited `ProducerLinger` (10 ms here). So one program can have thousands of records in flight, and it learns each one's fate in the callback: `err == nil` means stored. `sync.WaitGroup` waits for every callback before the program reports.

Each consumer group runs `cmd/read`: it asks where each partition ends right now, reads from its group's committed offset up to there, and commits once at the end.

```go noverify
// main.go, lines 36–84
	// Where does each partition end right now, and where did this group
	// get to last time? Read from there up to the end.
	adm := kadm.NewClient(cl)
	ends, err := adm.ListEndOffsets(ctx, *topic)
	if err != nil {
		log.Fatal(err)
	}
	want := map[int32]int64{}
	ends.Each(func(o kadm.ListedOffset) { want[o.Partition] = o.Offset })
	committed, err := adm.FetchOffsets(ctx, *group)
	if err != nil {
		log.Fatal(err)
	}
	pos := map[int32]int64{} // next offset to read, per partition
	committed.Each(func(o kadm.OffsetResponse) { pos[o.Partition] = o.At })

	start := time.Now()
	perPart := map[int32]int{}
	var total int64
	n := 0
	done := func() bool {
		for p, end := range want {
			if pos[p] < end {
				return false
			}
		}
		return true
	}
	for !done() {
		fs := cl.PollFetches(ctx)
		if err := fs.Err0(); err != nil {
			log.Fatal(err)
		}
		fs.EachRecord(func(r *kgo.Record) {
			p, err := ev.Decode(r.Value)
			if err != nil {
				log.Fatal(err)
			}
			perPart[r.Partition]++
			pos[r.Partition] = r.Offset + 1
			total += p.Cents
			n++
		})
	}
	if err := cl.CommitUncommittedOffsets(ctx); err != nil {
		log.Fatal(err)
	}
	fmt.Printf("group %-9s read %5d events in %4dms, $%d.%02d; per partition %v\n",
		*group, n, time.Since(start).Milliseconds(), total/100, total%100, perPart)
```

`cl.PollFetches` blocks until the client has fetched some records, then `EachRecord` walks them. Two admin calls from `kadm` bracket the reading: `ListEndOffsets` (where each partition ends) and `FetchOffsets` (where this group left off). `CommitUncommittedOffsets` saves the group's new bookmarks on the broker.

Read it top to bottom:

- The producer handed all 10,000 events over in 64 ms, and waited a median of 52 ms for each acknowledgement. The records went out in a few large batches, so each one waited for its batch.
- **Every group read all 10,000**, with the same total, $1,056,904.98. Four services, one copy of the data.

### Step 4: what a partition is on disk

A partition is a directory on each broker that holds a copy, and the log is really a file in it. Here is partition 3 on broker 1, and the start of its log:

```text
  lastOffset: 2965
  count: 2966

  | offset: 0 keySize: 3 valueSize: 58 sequence: 0 key: m12 payload: {"id":"pay-000001","merchant":"m12","seq":1,"cents":17112}
  | offset: 1 keySize: 3 valueSize: 57 sequence: 1 key: m13 payload: {"id":"pay-000003","merchant":"m13","seq":1,"cents":6894}
  | offset: 2 keySize: 3 valueSize: 57 sequence: 2 key: m19 payload: {"id":"pay-000011","merchant":"m19","seq":1,"cents":2830}
```

- The `.log` file is the records themselves: **60,408 bytes for 2,966 payments**, about 20 bytes each. They're stored as the producer sent them, in **one batch** of 2,966 records, compressed with snappy.
- `producerId: 2000` and the per-record `sequence` numbers are the **idempotent producer** at work (stop 5): the broker uses them to drop a batch it has already written when the producer retries.
- The `.index` maps offsets to byte positions in the `.log`, so a consumer that asks for offset 1,500 doesn't read from the beginning; `.timeindex` does the same for timestamps. Both are preallocated at 10 MB and trimmed when the segment is closed.
- When the `.log` reaches `segment.bytes` (1 GB by default), Kafka closes it and starts a new **segment** named after its first offset. Retention deletes whole old segments, which is why it's cheap.

## Keys & Partitions

*Stop 2 of 6.*

### Step 1: why one log isn't enough

A single log is read in order, by one reader per group, on one broker. That caps a topic at what one broker can store and one consumer can handle. So a topic is split into **partitions**: independent logs, each with its own offsets, spread over the brokers. Different partitions are read in parallel, by different members of a group (stop 3).

The price is order. Each partition has its own order, and there is **no order between partitions**. Offset 10 of partition 2 and offset 11 of partition 4 have nothing to do with each other.

### Step 2: the key chooses the partition

So which partition does a record go to? The producer decides, before sending:

- **With a key**: the partition is `hash(key) mod number-of-partitions`. The hash is **murmur2**, the same one the Java client uses, so a Go producer and a Java producer put the same key in the same place. Same key, same partition, every time.
- **Without a key**: the client fills a batch for one partition, then moves on to another (the "sticky" partitioner). That spreads load evenly, and scatters any sequence across partitions.

Chapter 5's rule was: partition by what must stay in order. For Meridian that's the **merchant**: a payment, its refund and the payout that includes both must be applied in that order. So the key is the merchant id.

### Step 3: measured

`cmd/order` runs a merchant dashboard fed by a consumer group of several members, all applying events to one shared screen. Each event carries its merchant's sequence number (1, 2, 3, … in the order produced), so the dashboard can tell when an event arrives after a later one of the same merchant:

```go noverify
	d.perPart[r.Partition]++
	if d.parts[p.Merchant] == nil {
		d.parts[p.Merchant] = map[int32]bool{}
	}
	d.parts[p.Merchant][r.Partition] = true
	if d.seen[p.ID] {
		d.dups++ // a second copy of an event, not a reordering
		return
	}
	d.seen[p.ID] = true
	if p.Seq < d.latest[p.Merchant] {
		d.late++
		d.hurt[p.Merchant] = true
		return
	}
	d.latest[p.Merchant] = p.Seq
}
```

## Consumer Groups

*Stop 3 of 6.*

### Step 1: sharing the partitions

A service runs several copies (three pods, say) so it can keep up and survive one dying. They form one consumer group, and Kafka divides the topic's partitions among the **members**: each partition is read by exactly one member at a time, and a member may read several. That's what makes stop 2's ordering hold with several members.

Deciding who gets which partition is an **assignment**, and redoing it when a member joins or leaves is a **rebalance**. Membership is tracked by **heartbeats**: each member tells the group coordinator (one of the brokers) "still here" every few seconds. A member that stops for longer than its **session timeout** is declared dead.

There are three ways to rebalance, and they behave very differently:

- **Eager** (the original protocol): every member gives up every partition, then the new assignment is handed out. Simple, and the whole group stops for a moment.
- **Cooperative** (KIP-429, Kafka 2.4): only the partitions that must move are given up, and the rest keep being read. This is franz-go's default (the cooperative-sticky balancer).
- **Broker-driven** (KIP-848, Kafka 4.0): the coordinator computes the assignment itself and tells each member what to give up and take, through heartbeats. franz-go supports it with `kgo.ServerSideBalancer()`, and recommends it from Kafka 4.3.

### Step 4: what to set

- **Session timeout** is a trade: short means a dead pod's partitions are picked up quickly; too short, and a long GC pause or a slow network gets a healthy member thrown out, which rebalances the group for nothing. The broker enforces a floor (`group.min.session.timeout.ms`, 6 s). Stop 4's receipts consumer uses that floor.
- **Shut down with SIGTERM**, and call `Close()`: Kubernetes sends SIGTERM before SIGKILL, so a normal deploy costs a heartbeat, not 45 s.
- **Static membership** (`kgo.InstanceID`) lets a restarted pod come back as the same member without any rebalance, if it returns within the session timeout: useful for rolling deploys.
- **Duplicates after a crash are normal.** Kafka's consumer groups are at-least-once, like chapter 5's streams.

## Committing Offsets

*Stop 4 of 6.*

### Step 1: the bookmark and the work are two different things

A consumer does two things with each event: the **work** (send the receipt) and the **commit** (move the bookmark past it). They can't happen at the same instant, so a crash can fall between them, and the order decides what the crash costs:

- **Commit, then work.** A crash in between leaves the bookmark past events that were never handled. Nobody will ever read them again: **lost**. This is **at-most-once**.
- **Work, then commit.** A crash in between leaves the bookmark before events that were handled. The next owner reads them again: **duplicated**. This is **at-least-once**.

That's chapter 5's ack-before versus ack-after, with one difference: a Kafka commit is one number per partition, so it covers every event before it. Commit offset 500 and you've said "0 to 499 are done", all of them.

### Step 2: what autocommit commits

Most Kafka clients commit for you by default. franz-go's **autocommit** runs every 5 s and commits the offsets of the records your program has **polled**. Not processed: the client can't know when you've finished with a record. It's careful about one thing: it doesn't count the records returned by the most recent poll until you poll again, on the assumption that asking for more means you've finished the last lot.

That assumption is only true if you finish the work before polling again. Hand records to another goroutine, and the poll loop asks for more straight away. Autocommit then commits records that are still sitting in a channel.

### Step 3: four receipts consumers

`cmd/receipts` runs one of four ways, differing only in when the commit happens relative to the work:

- `async`: the poll loop hands each record to a worker goroutine through a channel, and autocommit runs.
- `sync`: the poll loop sends each receipt itself, then polls again; autocommit runs.
- `manual`: autocommit off; send the whole poll's receipts, then `CommitRecords` for exactly those records.
- `inbox`: `manual`, plus chapter 4's inbox: the receipt row and the event id go into Postgres in one transaction.

Sending a receipt takes 2 ms (a stand-in for the email provider's API) plus a Postgres insert. Watch the `switch` near the end: it's the only place the four differ.

### Step 5: the rule

**Commit after the work, and make the work idempotent.** Concretely:

- Do the work for a poll's records, then commit those records (`CommitRecords`), or use `AutoCommitMarks` and mark each record when it's done.
- If you hand records to other goroutines, commit only what they've finished, per partition, in order: offset 500 means everything before 500.
- Expect every event more than once, and dedupe by event id where the effect lands: an inbox row in the same transaction, or an idempotency key passed on to the email provider. The inbox here guards the *database* effect. A real email sent before a crash would go out again unless the provider deduplicates it too, which is why payment and email APIs take idempotency keys (chapter 4).

## Replication & Acks

### Step 1: three copies, one leader

So far the question was what a *consumer* loses or repeats. Now the *broker*: what if the machine holding a partition dies? Kafka's answer is **replication**. Every partition of Meridian's topics has three **replicas**, one per broker. One replica is the **leader**: producers write to it and consumers read from it. The other two are **followers**: they fetch from the leader continuously and append what they get to their own copy.

<Define term="ISR (in-sync replicas)">The replicas of a partition that are caught up with its leader: the leader itself plus every follower that has fetched everything recently (within `replica.lag.time.max.ms`, 30 s by default). Only a member of the ISR can become the next leader.</Define>

If the leader's broker dies, the controller picks a new leader from the ISR. Nothing is copied at that moment: the new leader already has the data, as far as it had fetched. Everything hinges on that last clause.

### Step 2: what `acks` promises

The producer chooses when a write counts as done, with `acks`:

- `acks=0`: done when the record is written to the network. The broker sends no answer at all.
- `acks=1`: done when the **leader** has appended it to its own log. The followers may not have it yet.
- `acks=all`: done when **every replica in the ISR** has it. With `min.insync.replicas=2`, the broker also refuses the write if fewer than 2 replicas are in sync, instead of quietly accepting it on the leader alone.

`acks=all` is the default in franz-go and in the Java client (since Kafka 3.0). Meridian's topics are created with `--replication-factor 3 --config min.insync.replicas=2`: any one broker can die without losing an acknowledged payment or stopping writes.

The producer's side of it, from `cmd/produce`:


### Step 5: the idempotent producer

`acks=all` brings a second problem. A producer that sends a batch and loses the answer (a timeout, a leader change) can't tell whether the write happened, so it retries, and a batch that was in fact stored is stored twice. That's chapter 4's lost-response problem between the producer and the broker.

The fix is chapter 4's fix. The **idempotent producer** gets a **producer id** from the cluster and numbers every batch per partition with a **sequence number**. The leader remembers the last few sequence numbers per producer, and a retried batch whose numbers it has already written is acknowledged without being written again. That's the `producerId: 2000` and `sequence: 0, 1, 2` in stop 1's dump. It's on by default in franz-go and in the Java client since Kafka 3.0, and it needs `acks=all`.

In the runs above, the non-idempotent producer happened to write no duplicates: no answer was lost after a successful write. The idempotent producer makes that a guarantee rather than luck, at no measurable cost here (15.1 s against 15.2 s).

<UnderTheHood title="The high watermark">

A consumer never sees a record that could still disappear. The leader tracks the **high watermark**: the highest offset that every ISR member has. Consumers are only given records below it. With `acks=all`, a record is acknowledged exactly when the high watermark passes it. With `acks=1`, the producer is told "stored" before the high watermark has moved, which is how 6,283 payments could be acknowledged and then truncated. Consumers never saw those 6,283, so no receipt went out for a payment the log no longer has: the loss is silent on both sides.

When a follower becomes leader, each replica compares its log with the new leader's using the **leader epoch** (the `leader-epoch-checkpoint` file in stop 1's directory listing): a counter bumped at every leader change, recorded with the offset where each epoch began. A replica that has records from an epoch the new leader doesn't know about cuts them off. KIP-101 (Kafka 0.11) introduced this, replacing a truncation rule based on the high watermark that could lose or diverge data.

</UnderTheHood>

### Step 1: the whole path

Put the pieces together. Chapter 4's payment API posts each payment to the ledger and writes a `payment.succeeded` row to its **outbox** table in the same database transaction. A **relay** copies outbox rows to Kafka. Consumers read Kafka with an **inbox**. The only step that isn't a database transaction is the hop into Kafka, and it's at-least-once: the relay marks rows published only after Kafka has acknowledged them.

`cmd/relay` takes up to 500 unpublished rows in id order, sends them keyed by merchant, waits for every acknowledgement, and only then marks them published and commits:

```go noverify
// main.go, lines 44–85
func relayBatch(ctx context.Context, db *pgxpool.Pool, cl *kgo.Client) (int, error) {
	n := 0
	err := pgx.BeginFunc(ctx, db, func(tx pgx.Tx) error {
		rows, err := tx.Query(ctx, `SELECT id, payload FROM outbox WHERE published_at IS NULL
			ORDER BY id LIMIT 500 FOR UPDATE SKIP LOCKED`)
		if err != nil {
			return err
		}
		var ids []int64
		var recs []*kgo.Record
		for rows.Next() {
			var id int64
			var e struct {
				EventID  string `json:"event_id"`
				Merchant string `json:"merchant"`
				Amount   int64  `json:"amount"`
			}
			var raw []byte
			if err := rows.Scan(&id, &raw); err != nil {
				return err
			}
			if err := json.Unmarshal(raw, &e); err != nil {
				return err
			}
			m := strings.TrimPrefix(e.Merchant, "liabilities:merchant:")
			p := ev.Payment{ID: e.EventID, Merchant: m, Seq: int(id), Cents: e.Amount}
			ids = append(ids, id)
			recs = append(recs, &kgo.Record{Key: []byte(m), Value: p.Encode()})
		}
		if err := rows.Err(); err != nil {
			return err
		}
		// All or nothing from Kafka's side: wait for every acknowledgement.
		if err := cl.ProduceSync(ctx, recs...).FirstErr(); err != nil {
			return err
		}
		n = len(ids)
		_, err = tx.Exec(ctx, `UPDATE outbox SET published_at = now() WHERE id = ANY($1)`, ids)
		return err
	})
	return n, err
}
```

`FOR UPDATE SKIP LOCKED` lets two relays run without taking the same rows. `ProduceSync` is `Produce` plus waiting for all the callbacks. If the relay dies after Kafka acknowledged a batch but before the `COMMIT`, the rows are still unpublished and go out again.

### Step 3: a compacted topic

One more kind of topic. The dashboard needs every merchant's current balance at startup, and replaying every payment since the beginning to compute it gets slower every day. A **compacted** topic keeps, for each key, only the **latest** record: a table, stored as a log. Kafka's own `__consumer_offsets`, where the committed offsets of stop 1 live, is one.

The log **cleaner**, a background thread on each broker, rewrites old segments keeping only the newest record per key. It never touches the **active** segment, the one being appended to. A record with a key and no value is a **tombstone**: it means "delete this key", and after `delete.retention.ms` (a day by default) the tombstone goes too.

`cmd/balances` writes 10,000 balance updates for 20 merchants ("m07's balance is now X"), then a tombstone for m20, who closed their account, then one more update for m01:

- After the cleaner ran, 6 s later: **21 records**, the old segments merged into one of 464 bytes, and **the same balances**: m01 5,372,548 cents, m02 5,426,646, m03 4,585,316, matching what the producer last wrote. ## Exercises

These use the `kf` module and the cluster from this chapter.

<Exercise n={1} title="Where did my group get to?" level="easy">

While `rebalance.sh` runs, run `kafka-consumer-groups.sh --describe --group <the live group>` every second. Which columns change when member c is killed, and which one would you alert on?

<Solution>

The `CONSUMER-ID` and `HOST` of partitions 2 and 3 keep showing c for 45 s, although it's dead: the coordinator doesn't know yet. `LOG-END-OFFSET` keeps growing on those partitions while `CURRENT-OFFSET` stands still, so `LAG` climbs by about 100 a second each. Then the owner changes to a or b and the lag drains. Alert on lag, per partition and growing, not on member count: a member can look present while doing nothing.

</Solution>

</Exercise>

<Exercise n={2} title="Pick a key" level="easy">

Meridian adds a `refund.issued` event and a `payout.sent` event. For each of these consumers, what should the key be: the per-merchant balance projection; an email sender that doesn't care about order; a per-customer fraud model that looks at a customer's last ten payments?

<Solution>

The balance projection needs each merchant's events in order: key by merchant, on the same topic, so a refund can't be applied before its payment. The email sender needs no order: a key only adds hot-spot risk, but since the same events go to the balance projection, it simply reads the same merchant-keyed topic. The fraud model needs per-customer order, which the merchant key doesn't give (one customer pays many merchants): publish a second topic keyed by customer, or accept that it sees each customer's payments in partition-interleaved order and sorts by timestamp within its window.

</Solution>

</Exercise>

<Exercise n={3} title="Mark, then autocommit" level="medium">

Change the receipts consumer's `sync` mode to use `kgo.AutoCommitMarks()` and call `cl.MarkCommitRecords(r)` after each receipt is recorded. Run `commits.sh`. Where does it land between `sync` and `manual`, and why?

<Solution>

Autocommit then only commits records you've marked as done, every 5 s. Nothing is committed before it's processed, so nothing should be lost. But the commit still happens only every 5 s, so a SIGKILL can repeat up to 5 s of receipts: expect duplicates on the scale of `sync`'s, not `manual`'s. It's useful when committing after every poll is too slow (a commit is a round trip to the coordinator); the cost is a larger replay after a crash, which the inbox absorbs.

</Solution>

</Exercise>

<Exercise n={4} title="Survive two failures" level="medium">

Change the payments topic so that any **two** brokers can fail without losing an acknowledged payment, and say what else has to change and what it costs.

<Solution>

Five replicas with `min.insync.replicas=3` (and at least five brokers): an acknowledged record is on three brokers, so two can die and one copy remains, and with two brokers down there are still three in sync, so writes continue. Three replicas with `min.insync.replicas=3` would also never lose an acknowledged record, but a single broker down would stop all writes. The cost: every write goes to five brokers and waits for three, so more disk, more network and a latency set by the slowest of the three fastest followers. For payments, three replicas and `min.insync.replicas=2` across three availability zones is the usual answer.

</Solution>

</Exercise>

<Exercise n={5} title="Exactly-once inside Kafka" level="hard">

A fraud service reads `payments` and writes a `payment.scored` event to another topic for each one. Using Kafka transactions (`kgo.TransactionalID` and a `kgo.GroupTransactSession`), make "read a payment, write its score, commit the offset" atomic. What does that guarantee, and what doesn't it cover?

<Solution>

A transactional producer writes the score events and the consumer group's new offsets in one Kafka transaction (`GroupTransactSession.Begin`, produce, `End(ctx, kgo.TryCommit)`). Consumers of `payment.scored` with `kgo.FetchIsolationLevel(kgo.ReadCommitted())` see the scores only if the offsets were committed with them, so a crash either repeats both or neither: no duplicate score is ever visible. It covers only effects that are Kafka writes. An email, a database row or an HTTP call made in between is outside the transaction and can still happen twice; for those, the inbox of stop 4 is still the answer. That's why the receipts consumer here uses the inbox, not Kafka transactions.

</Solution>

</Exercise>

<Recap>

- **The log**: a topic is append-only partitions; each consumer group keeps its own committed offsets, so four groups each read all 10,000 events and a reset replayed all 10,000 for one group without touching the others.
- **Keys and partitions**: the key picks the partition (murmur2), and order exists only within a partition. Keyed by merchant: 0 of 10,000 out of order; no key: 4,979 (4,034 with a single reader). A hot key concentrates work (5,826 of 10,000 in one partition), and growing 6 to 8 partitions moved 19 of 20 merchants.
- **Consumer groups**: a joining member cost the moved partitions about half a second (cooperative) or 2.4 s (KIP-848); a clean leave about 3 s; a SIGKILL 45 s of silence, until the session timed out, and 363 to 1,458 records consumed twice.
- **Committing offsets**: autocommit with a worker goroutine lost 123 receipts (507 in an earlier run) because it commits what was polled; doing the work before committing lost none but repeated 2,703 (autocommit) or 1,215 (commit per poll); the inbox made it 0 lost, 0 duplicates, turning away 902 redeliveries.
- **Replication and acks**: a plain leader kill lost nothing with acks=1 or acks=all, and 3,641 events with acks=0. With the followers stalled for 3 s first, acks=1 lost 6,283 acknowledged payments and acks=all none. With two brokers down, acks=all refused writes. Batching (linger) more than paid for acks=all.
- **End to end**: chapter 4's outbox relayed to Kafka lost nothing through ten relay kills and wrote 67 duplicates; the inbox turned away 1,120 redeliveries for exactly 5,000 receipts. A compacted topic rebuilt 19 balances from 21 records instead of 10,002.
