<HeroCard label="Part 3 · Chapter 2" title="Double-Entry Ledgers">

Chapter 1 made sure a single amount can't go wrong. This chapter is about where amounts live, and how money moves between those places without appearing or disappearing. The answer is 700 years old: **double-entry bookkeeping**, in which every movement of money is recorded twice, once where it came from and once where it went, so the books always add up to zero and any mistake shows.

It's also the design almost every payment system converges on (Stripe, Square, Modern Treasury, the open-source TigerBeetle and Formance), usually after trying something simpler and losing track of money. This chapter tries the simpler thing first, measures how it loses money, and then builds Meridian's ledger in Go on PostgreSQL, with the rules enforced where they can't be skipped.

Six stops. If you get lost, come back here:

1. **Single entry breaks.** A balance per account, updated in place, and a crash in the middle.
2. **Double entry.** Accounts, postings, debits and credits, and one card payment booked end to end.
3. **The balance rule, twice.** Enforced in Go, and again by the database.
4. **Append-only.** Nothing is edited or deleted; mistakes are reversed.
5. **Balances.** Deriving them, caching them, and what each costs.
6. **Proving the books.** The trial balance and reconciliation.

### Step 2: kill it

This script starts the transfer loop, kills the process with `SIGKILL` after two seconds (what an out-of-memory kill, a crashed node or a forced deploy does), and counts the money. Five times:

```text

money in the system: 2000.00 (started with 2000.00)
run 2: killed after 17000 transfers
money in the system: 2000.00 (started with 2000.00)
run 3: killed after 17000 transfers
money in the system: 1996.29 (started with 2000.00)
run 4: killed after 16000 transfers
money in the system: 2000.00 (started with 2000.00)
run 5: killed after 16000 transfers
money in the system: 1995.86 (started with 2000.00)
```

In runs 3 and 5, money is gone: $3.71 and $4.14. The kill landed after a subtract had committed and before its add ran. Wrapping both statements in one database transaction fixes that particular crash (the next chapter is about transactions), but the deeper problem remains, and it's the one double entry solves: **the table only knows where money ended up, not how it got there**. There's no record of the transfer that broke, so there's nothing to find, check, or repair. An auditor asking "why is Alice's balance what it is?" gets no answer at all.

## Double Entry

*Stop 2 of 6.*

### Step 1: accounts

A ledger starts with a **chart of accounts**: every place money can be, or come from, or go to. Not just customer wallets, but also Meridian's own bank account, money owed to it by card networks, money it owes merchants, and the fees it has earned. Each account has one of five types:

- **Asset**: what Meridian has or is owed. Its bank account; money the card network will pay it.
- **Liability**: what Meridian owes others. Every merchant's unpaid balance.
- **Equity**: what belongs to Meridian's owners.
- **Revenue**: what Meridian has earned. Fees.
- **Expense**: what Meridian has spent. Card network costs, refunds it absorbed.

### Step 2: postings

Money moves as a **transaction**: a set of **postings**, each adding an amount to one account or taking it from another, that happen together or not at all. The rule that makes it double entry: **in every transaction, the postings sum to zero**. Whatever arrives somewhere left somewhere else.

Accountants call the two directions **debit** and **credit**. For engineers the cleanest convention is a sign: a debit is a positive amount, a credit a negative one. Asset and expense accounts normally hold debit (positive) balances; liability, equity and revenue accounts normally hold credit (negative) ones. So a merchant account at −19.11 means Meridian owes that merchant $19.11. And because every transaction sums to zero, so does the whole ledger: that's the accounting equation, **assets + expenses = liabilities + equity + revenue**, written as "everything sums to zero".

In Go, a posting is an account and a `Money`, and `NewTransaction` refuses anything that isn't double entry:

```go noverify
// ledger.go, lines 18–70
// Posting moves Amount into (positive: debit) or out of (negative:
// credit) one account.
type Posting struct {
	Account string
	Amount  money.Money
}

// Leg is a Posting of amt to account.
func Leg(account string, amt money.Money) Posting { return Posting{Account: account, Amount: amt} }

// Transaction is a set of postings that happen together or not at all.
type Transaction struct {
	Kind     string
	Postings []Posting
	Reverses int64 // the transaction this one undoes, or 0
}

var (
	ErrUnbalanced    = errors.New("postings don't sum to zero")
	ErrTooFewLegs    = errors.New("a transaction needs at least two postings")
	ErrZeroPosting   = errors.New("a posting can't be zero")
	ErrCannotReverse = errors.New("transaction can't be reversed")
)

// NewTransaction checks the double-entry rule before anything reaches the
// database: at least two postings, none zero, and in every currency the
// debits equal the credits.
func NewTransaction(kind string, postings ...Posting) (Transaction, error) {
	if len(postings) < 2 {
		return Transaction{}, ErrTooFewLegs
	}
	sums := map[money.Currency]money.Money{}
	for _, p := range postings {
		if p.Amount.Amount == 0 {
			return Transaction{}, fmt.Errorf("%w: %s", ErrZeroPosting, p.Account)
		}
		s, ok := sums[p.Amount.Currency]
		if !ok {
			s = money.New(0, p.Amount.Currency)
		}
		s, err := s.Add(p.Amount)
		if err != nil {
			return Transaction{}, err
		}
		sums[p.Amount.Currency] = s
	}
	for _, s := range sums {
		if s.Amount != 0 {
			return Transaction{}, fmt.Errorf("%w: %v left over", ErrUnbalanced, s)
		}
	}
	return Transaction{Kind: kind, Postings: postings}, nil
}
```

### Step 3: a card payment, end to end

A customer pays merchant Acme $19.99 by card. Meridian's fee is 2.9% + 30¢, computed with chapter 1's `MulRat`: 58¢ + 30¢ = 88¢. Three transactions follow the money from the card to Acme's bank:

```go noverify

	// 3. We pay Acme what we owe.
	post(l, "merchant payout",
		ledger.Leg("liabilities:merchant:acme", usd(price.Amount-fee.Amount)),
```

## The Balance Rule

*Stop 3 of 6.*

### Step 1: why enforce it twice

`NewTransaction` checks the rule in Go, and that catches bugs early with a clear error. But Go isn't the only way into the database: a migration, a support engineer's SQL, a second service, a bug that builds postings without calling `NewTransaction`. A rule that matters this much should live where every write has to pass it: in the database.

### Step 2: in the schema

The rule is a trigger that runs when the database transaction **commits** (a constraint trigger declared `DEFERRABLE INITIALLY DEFERRED`), so a transaction's postings can be inserted one by one and are checked together at the end. The currency rule needs no code at all: a composite foreign key says a posting's `(account, currency)` must match an account's.

```sql
// schema.sql, lines 4–54
CREATE TABLE accounts (
    id       text PRIMARY KEY,
    name     text NOT NULL,
    type     text NOT NULL CHECK (type IN ('asset', 'liability', 'equity', 'revenue', 'expense')),
    currency char(3) NOT NULL,
    UNIQUE (id, currency) -- lets postings reference (account, currency) together
);

CREATE TABLE transactions (
    id         bigserial PRIMARY KEY,
    kind       text NOT NULL,
    reverses   bigint REFERENCES transactions (id),
    created_at timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE postings (
    id         bigserial PRIMARY KEY,
    tx_id      bigint NOT NULL REFERENCES transactions (id),
    account_id text NOT NULL,
    amount     bigint NOT NULL CHECK (amount <> 0), -- minor units: + debit, - credit
    currency   char(3) NOT NULL,
    -- A posting's currency must be its account's currency.
    FOREIGN KEY (account_id, currency) REFERENCES accounts (id, currency)
);
CREATE INDEX postings_tx ON postings (tx_id);

-- Rule 1: every transaction balances, per currency. Checked when the
-- database transaction commits (DEFERRABLE INITIALLY DEFERRED), so the
-- postings can be inserted one at a time before the check runs.
CREATE FUNCTION check_balanced() RETURNS trigger LANGUAGE plpgsql AS $$
DECLARE
    bad record;
BEGIN
    SELECT currency, sum(amount) AS total INTO bad
    FROM postings WHERE tx_id = NEW.tx_id
    GROUP BY currency HAVING sum(amount) <> 0
    LIMIT 1;
    IF FOUND THEN
        RAISE EXCEPTION 'transaction % does not balance: % postings sum to %',
            NEW.tx_id, bad.currency, bad.total;
    END IF;
    IF (SELECT count(*) FROM postings WHERE tx_id = NEW.tx_id) < 2 THEN
        RAISE EXCEPTION 'transaction % has a single posting', NEW.tx_id;
    END IF;
    RETURN NULL;
END $$;

CREATE CONSTRAINT TRIGGER postings_balanced
    AFTER INSERT ON postings
    DEFERRABLE INITIALLY DEFERRED
    FOR EACH ROW EXECUTE FUNCTION check_balanced();
```

### Step 4: more than one currency

"Sums to zero" is per currency: $100 in and €100 out doesn't balance, whatever the exchange rate. A conversion (chapter 1, stop 6) is booked through a pair of **FX accounts**, one per currency, so each currency balances on its own: €100.00 comes in against `equity:fx-eur`, and $114.03 goes to the merchant against `equity:fx-usd`. The FX accounts then show, in each currency, what Meridian bought and sold, and the difference between their values at today's rate is its foreign-exchange gain or loss. The lab's multi-currency cases use exactly this shape.

## Append-Only

*Stop 4 of 6.*

### Step 1: why nothing is edited

A ledger is evidence. If a posting can be edited, a balance can be changed without leaving a trace, and every report built on the ledger (a merchant's statement, a tax filing, an audit) could have been different yesterday. So postings and transactions are **append-only**: once written, they're never updated or deleted. The schema makes that a rule, not a convention:

```sql
// schema.sql, lines 56–69
-- Rule 2: append-only. Corrections are new, reversing transactions.
CREATE FUNCTION forbid_change() RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
    RAISE EXCEPTION 'the ledger is append-only: % on % is not allowed', TG_OP, TG_TABLE_NAME;
END $$;

CREATE TRIGGER postings_append_only BEFORE UPDATE OR DELETE ON postings
    FOR EACH ROW EXECUTE FUNCTION forbid_change();
CREATE TRIGGER postings_no_truncate BEFORE TRUNCATE ON postings
    FOR EACH STATEMENT EXECUTE FUNCTION forbid_change();
CREATE TRIGGER transactions_append_only BEFORE UPDATE OR DELETE ON transactions
    FOR EACH ROW EXECUTE FUNCTION forbid_change();
CREATE TRIGGER transactions_no_truncate BEFORE TRUNCATE ON transactions
    FOR EACH STATEMENT EXECUTE FUNCTION forbid_change();
```

Both attempts in stop 3's output were stopped: editing the fee and deleting the payment. (A database superuser can still disable triggers; in production the application's role also has no `UPDATE` or `DELETE` privilege on these tables, and chapter 10 on auditability adds tamper evidence.)

### Step 2: mistakes are reversed, not erased

Mistakes still happen. Here the payout job ran twice and paid Acme $19.11 a second time. The fix is a new transaction that is the exact opposite of the wrong one, linked to it:

```go noverify
// ledger.go, lines 114–143
// Reverse posts the exact opposite of transaction id: every posting
// negated. The original stays in the ledger; both are visible forever.
func (l *Ledger) Reverse(ctx context.Context, id int64, currencies map[string]money.Currency) (int64, error) {
	rows, err := l.db.Query(ctx,
		`SELECT account_id, amount, currency FROM postings WHERE tx_id = $1 ORDER BY id`, id)
	if err != nil {
		return 0, err
	}
	var legs []Posting
	for rows.Next() {
		var acct, cur string
		var amt int64
		if err := rows.Scan(&acct, &amt, &cur); err != nil {
			return 0, err
		}
		legs = append(legs, Leg(acct, money.New(-amt, currencies[cur])))
	}
	if err := rows.Err(); err != nil {
		return 0, err
	}
	if len(legs) == 0 {
		return 0, fmt.Errorf("%w: %d has no postings", ErrCannotReverse, id)
	}
	tx, err := NewTransaction("reversal", legs...)
	if err != nil {
		return 0, err
	}
	tx.Reverses = id
	return l.Post(ctx, tx)
}
```

## Balances

*Stop 5 of 6.*

### Step 1: derived, the truth

An account's balance is the sum of its postings. That's the definition, and it can always be recomputed:

```go noverify
// ledger.go, lines 145–159
// Balance is an account's balance derived from its postings: the truth.
func (l *Ledger) Balance(ctx context.Context, account string) (int64, error) {
	var b int64
	err := l.db.QueryRow(ctx,
		`SELECT coalesce(sum(amount), 0) FROM postings WHERE account_id = $1`, account).Scan(&b)
	return b, err
}

// CachedBalance is the balance kept up to date by Post: fast, and only
// trustworthy because it's checked against Balance (see Reconcile).
func (l *Ledger) CachedBalance(ctx context.Context, account string) (int64, error) {
	var b int64
	err := l.db.QueryRow(ctx, `SELECT balance FROM balances WHERE account_id = $1`, account).Scan(&b)
	return b, err
}
```

The question is what it costs. `scale` loads 300,000 card payments (900,000 postings, every one through the balance trigger), then times the derived balance of the busiest account (the card receivable, on every payment) and of one merchant among a thousand:

Without an index, every balance reads the whole table: about 20 ms for any account. With an index on `(account_id) INCLUDE (amount)`, a merchant with 313 postings takes 130 µs (Postgres reads only that account's index entries). The card receivable still takes 17 ms, because it really has 300,000 postings to add up, and it will keep growing.

### Step 2: cached, fast

So `Post` also keeps a **cached balance** per account, updated in the same database transaction as the postings (see `Post` in stop 2's code: `UPDATE balances SET balance = balance + $2`). Reading it is one row: 80 µs, whatever the history. Because the update is in the same transaction, the cache can never disagree with the postings after a crash, and because it's `balance + $2` (not "read, add in Go, write back"), concurrent posts can't lose each other's updates. 16 workers posting 8,000 payments concurrently: reconcile found **0 accounts** that disagree.

### Step 3: the hot row

The cost shows up on the write side. Every card payment updates the same two cached rows (card receivable and fee revenue), and Postgres lets only one transaction at a time hold a row's lock. So 16 workers queue for those two rows: **1,381 payments/s** with cached balances, against **8,586 payments/s** without them. Six times the throughput, lost to one hot row.

### Step 4: choosing

Real ledgers mix the two. Cache the balances of accounts that are read often and written by few (a merchant's balance, a customer's wallet): readers get 80 µs and writers rarely collide. For a handful of very hot internal accounts (a receivable every payment touches), don't lock a single row per write: derive the balance, or keep a checkpoint (the balance as of some posting id) and add the postings since, or split the counter across several rows and sum them. Whatever the cache, the postings stay the truth, and stop 6 checks the cache against them.

## Proving the Books

*Stop 6 of 6.*

### Step 1: two checks

Double entry makes two checks possible that single entry can't do at all:

```go noverify
// ledger.go, lines 161–195
// TrialBalance sums every posting per currency. In a double-entry ledger
// each sum is zero, always; anything else means the ledger is broken.
func (l *Ledger) TrialBalance(ctx context.Context) (map[string]int64, error) {
	rows, err := l.db.Query(ctx, `SELECT currency, sum(amount) FROM postings GROUP BY currency`)
	if err != nil {
		return nil, err
	}
	defer rows.Close()
	sums := map[string]int64{}
	for rows.Next() {
		var cur string
		var sum int64
		if err := rows.Scan(&cur, &sum); err != nil {
			return nil, err
		}
		sums[cur] = sum
	}
	return sums, rows.Err()
}

// Reconcile compares every account's cached balance with the balance
// derived from its postings, and returns the accounts that disagree.
func (l *Ledger) Reconcile(ctx context.Context) ([]string, error) {
	rows, err := l.db.Query(ctx, `
		SELECT b.account_id
		FROM balances b
		LEFT JOIN (SELECT account_id, sum(amount) AS s FROM postings GROUP BY account_id) p
		  ON p.account_id = b.account_id
		WHERE b.balance <> coalesce(p.s, 0)
		ORDER BY 1`)
	if err != nil {
		return nil, err
	}
	return pgx.CollectRows(rows, pgx.RowTo[string])
}
```

- The **trial balance**: every posting, summed per currency. It must be zero, always; anything else means a posting got in that didn't balance, which the schema should make impossible. Over 900,000 postings it took 50 ms.
- **Reconciliation**: every cached balance compared with the one derived from postings. Anything that disagrees names the account to investigate. Over 1,002 accounts it took 48 ms.

Both are cheap enough to run on every deploy and every night, and they're the internal half of what a finance team does daily: the external half compares the bank account in the ledger with the bank's own statement (chapter 9, external payment systems).

## Exercises

<Exercise n={1} title="Refund" level="easy">

A customer disputes the $19.99 payment and Acme agrees to refund it after the payout. Write the transactions, and decide who absorbs the 88¢ fee.

<Solution>

Acme owes the customer the full $19.99 back. If Meridian keeps its fee, Acme's account is debited $19.99 (Acme now owes Meridian the money, a debit balance on a liability) and the card receivable is credited $19.99 (the network will take it back). If Meridian refunds its fee too, add a transaction moving 88¢ from `revenue:fees` (a debit) to Acme's account (a credit), or book it to an expense account. Either way, it's new transactions: the original payment stays.

</Solution>

</Exercise>

<Exercise n={2} title="Idempotent posting" level="easy">

The duplicate payout in stop 4 happened because a job ran twice. Add an idempotency key to `transactions` so that posting the same payout twice stores it once.

<Solution>

Add `idempotency_key text UNIQUE` to `transactions`, and have the payout job derive the key from what it pays (for example `payout:acme:2026-09-27`). The second insert fails with a unique violation (SQLSTATE 23505), which `Post` can turn into "already posted" and return the existing id. Chapter 4 is about exactly-once processing in general.

</Solution>

</Exercise>

<Exercise n={3} title="Balance as of a date" level="medium">

Add `BalanceAt(ctx, account, at time.Time)`. Why is this easy for a ledger and impossible for stop 1's wallet table?

<Solution>

Sum the postings of transactions with `created_at <= at`. The ledger keeps every movement with its time, so any past balance can be recomputed. The wallet table only has the current number: yesterday's balance is gone the moment today's update runs.

</Solution>

</Exercise>

<Exercise n={4} title="A checkpoint for the hot account" level="medium">

Replace the card-receivable's cached row with a checkpoint: a table of (account, balance, up to posting id), written by a job every few seconds, and a `Balance` that adds the postings after the checkpoint. Measure posting throughput and read time.

<Solution>

The job runs `INSERT INTO checkpoints SELECT account_id, sum(amount), max(id) FROM postings WHERE account_id = $1 AND id <= $2` (or adds the postings since the last checkpoint to its balance). Reads take the latest checkpoint and `SELECT sum(amount) FROM postings WHERE account_id = $1 AND id > $2`, which with the index reads only a few seconds of postings. Posting no longer touches a hot row, so throughput returns to the no-cache figure (about 8,500/s here). Take care with ids: a posting with a lower id can commit after a higher one, so checkpoint only up to an id every earlier transaction has finished with (for example, one older than the oldest open transaction).

</Solution>

</Exercise>

<Exercise n={5} title="Multi-currency ledger" level="hard">

Add EUR accounts and book chapter 1's conversion: a customer pays €100.00, Acme is owed $114.03 at 1 EUR = 1.1403 USD. Then, a week later at 1 EUR = 1.1520 USD, compute Meridian's FX gain or loss from the FX accounts.

<Solution>

Book €100.00 into a EUR receivable against `equity:fx-eur` (credit €100.00), and `equity:fx-usd` (debit $114.03) against Acme (credit $114.03): each currency sums to zero. Meridian sold euros it has, €100.00, for dollars it owes, $114.03. A week later, those €100.00 are worth $115.20, so revaluing the EUR position shows a gain of $1.17. Book it with a transaction to a revenue (or expense, for a loss) account in USD. The FX accounts are how a multi-currency ledger keeps each currency balanced and still shows what currency movements earned or cost.

</Solution>

</Exercise>
