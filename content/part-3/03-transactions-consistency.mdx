## ACID & Isolation Levels

Before a single dollar moves, you need to understand the contract your database is making with you. That contract has four clauses. Every professional knows them cold.

<Define term="ACID" since="SQL & Databases in Go (Part 1)">
**ACID** is the set of four guarantees a database transaction makes: **A**tomicity (all operations in the transaction succeed together or none are visible), **C**onsistency (every transaction takes the database from one valid state to another — your invariants hold before and after every commit), **I**solation (concurrent transactions don't see each other's in-progress work), and **D**urability (once a transaction commits, it survives crashes). You care about ACID because without it, concurrent money movement corrupts balances silently — no exception thrown, no error logged.
</Define>

### The four properties

A **transaction** is a group of operations that the database treats as a single unit. You've used them: `BEGIN` → do work → `COMMIT` (or `ROLLBACK`). The database promises four things about that unit:

<ConceptGrid cols={2}>
  <ConceptCard label="Atomicity">All operations in a transaction succeed together, or none of them are visible. A transfer that posts a debit and a credit either completes both or neither. No half-posted transfers. Ever.</ConceptCard>
  <ConceptCard label="Consistency">Every transaction must take the database from one *valid state* to another. Your invariants — like "debits must equal credits" — hold before and after every commit. The DB enforces constraints; you enforce your domain rules in the transaction.</ConceptCard>
  <ConceptCard label="Isolation">Concurrent transactions must not see each other's in-progress work. The *degree* to which they're shielded is the isolation level. This is the one that bites people in fintech.</ConceptCard>
  <ConceptCard label="Durability">Once a transaction commits, it's permanent. A crash, a power cut, a cosmic ray — the committed data survives. The write-ahead log (WAL) is how Postgres makes this true.</ConceptCard>
</ConceptGrid>

Atomicity and durability are either on or off — you don't configure them. Isolation is a dial.

### Isolation levels and the anomalies they prevent

<Define term="Isolation level" since="SQL & Databases in Go (Part 1)">
An **isolation level** controls how much a transaction can see of concurrent in-progress work from other transactions. The SQL standard defines four levels — Read Uncommitted, Read Committed, Repeatable Read, and Serializable — each buying protection against a specific class of anomaly. Higher isolation means fewer anomalies but more contention; lower isolation means more concurrency but more subtle bugs. Postgres defaults to **Read Committed**, which is safe for many workloads but not for concurrent balance updates.
</Define>

The SQL standard defines four isolation levels. Each one buys protection against specific anomalies. Here they are, strongest to weakest:

<ConceptGrid cols={2}>
  <ConceptCard label="Dirty Read">You read a row that a concurrent transaction has modified but not yet committed. If that transaction rolls back, you saw data that never existed. Postgres doesn't allow this at any isolation level.</ConceptCard>
  <ConceptCard label="Non-Repeatable Read">You read a row, a concurrent transaction commits a change to it, you read it again and get a different value. Two reads of the same row in one transaction return different data.</ConceptCard>
  <ConceptCard label="Phantom Read">You run a query with a `WHERE` clause, another transaction inserts rows that would match, you run the same query and get more rows. The "phantom" rows appeared between your reads.</ConceptCard>
  <ConceptCard label="Lost Update">Two transactions both read a value, both compute a new value based on it, both write back. The second write silently overwrites the first. This is the one that destroys balances. We'll animate it next.</ConceptCard>
</ConceptGrid>

Here is how the four isolation levels stack up against these anomalies:

| Isolation Level | Dirty Read | Non-Repeatable Read | Phantom Read | Lost Update |
|---|---|---|---|---|
| Read Uncommitted | possible | possible | possible | possible |
| **Read Committed** (Postgres default) | prevented | possible | possible | possible |
| Repeatable Read | prevented | prevented | prevented* | prevented |
| Serializable | prevented | prevented | prevented | prevented |

*Postgres's Repeatable Read also prevents phantoms, exceeding the SQL standard.

**Postgres defaults to Read Committed.** That means within a single transaction, each statement sees only committed data — but two statements in the same transaction can see different snapshots if another transaction commits between them. For a balance update, that's dangerous enough to deserve a section of its own.

<Callout kind="warn" title="Read Committed is not safe for concurrent balance updates">

At Read Committed, two concurrent transactions can each read the same balance, compute the same new balance, and both write it back — losing one update entirely. This isn't a Postgres bug. It's exactly what Read Committed promises to allow. The fix is locking, not hoping.

</Callout>

<UnderTheHood title="How Postgres makes ACID real (Go 1.26 baseline)">

**Atomicity** is enforced by the write-ahead log (WAL). Every change is written to the WAL before it's applied to the heap. If the database crashes mid-transaction, on restart it replays the WAL and rolls back any uncommitted work — the incomplete transaction vanishes as if it never happened.

**Durability** is also the WAL. When you `COMMIT`, Postgres `fsync`s the WAL record to disk before acknowledging success. Even a crash right after the acknowledgement leaves the data recoverable.

**Isolation** (at Read Committed) is implemented via MVCC — Multi-Version Concurrency Control. Every row has a system column `xmin` (the transaction ID that created it) and `xmax` (the transaction ID that deleted it). When you read, Postgres checks whether each row version was committed before your statement started, using a snapshot of the transaction ID space. Writers and readers don't block each other — readers see old versions, writers create new ones. This is why Postgres reads don't block writes and vice versa at Read Committed.

**`SELECT ... FOR UPDATE`** (coming in the next section) steps *outside* MVCC for one purpose: it acquires a real row-level lock so only one transaction can hold it at a time. This is the bridge between MVCC's snapshot reads and the serial behavior we need for balance updates.

*This is a model, not the full implementation — the real MVCC machinery is more nuanced.* The Go 1.26 `database/sql` package provides `db.BeginTx(ctx, &sql.TxOptions{Isolation: sql.LevelSerializable})` if you want to bump the isolation level for specific transactions.

</UnderTheHood>

## The Lost-Update Problem

Enough theory. Let's watch the disaster happen in real time.

<Define term="The lost-update problem">
The **lost-update problem** occurs when two transactions both read the same value, each independently computes a new value based on that read, and both write back — so the second write silently overwrites the first. No error is raised. No constraint is violated. The database happily commits both transactions. In a balance update, this means real money either disappears or gets created from nothing.
</Define>

**On the job:** At Meridian, `POST /transfers` is hit by payment processors, mobile clients, and batch jobs simultaneously. Any read-compute-write pattern on `accounts.balance_cents` without a lock is a lost-update waiting to happen — and it only manifests under load, not in unit tests.

Two customers are pulling money from the same account simultaneously. Gwendolyn wants to send $30. Marcus wants to send $40. The account has $100. After both transfers succeed, the balance should be $30. Watch what happens without any locking:

That's the lost-update problem. In a real system it means real money either disappears or gets created from nothing. No exception is thrown. No error is logged. The database happily committed both transactions. It was doing exactly what Read Committed isolation allows.

Let's make this concrete at the Go level too, using goroutines and a shared in-memory balance — because we *can* run that:

<GoPlayground>

```go
package main

import (
	"fmt"
	"sync"
)

// balance is shared state — in cents, never a float.
var balance int = 10000 // $100.00

func unsafeTransfer(amount int, name string, wg *sync.WaitGroup) {
	defer wg.Done()
	// Read-modify-write with no synchronization: the lost-update bug.
	current := balance        // Step 1: read
	newBal := current - amount // Step 2: compute
	balance = newBal          // Step 3: write (can overwrite a concurrent write)
	fmt.Printf("%s: read %d, wrote %d\n", name, current, newBal)
}

func main() {
	var wg sync.WaitGroup
	wg.Add(2)
	go unsafeTransfer(3000, "Gwendolyn", &wg) // $30
	go unsafeTransfer(4000, "Marcus", &wg)    // $40
	wg.Wait()
	fmt.Printf("final balance: %d (want 3000)\n", balance)
}
```

</GoPlayground>

Run it a few times. You'll see the final balance bounce between 6000, 7000, and occasionally 3000 — a data race. The race detector will catch it instantly.

Here is what the race test looks like — this is the kind of test you write before you write the fix:

```go
// race_test.go — run with: go test -race ./...
package ledger_test

import (
	"sync"
	"testing"
)

func TestConcurrentTransfersRace(t *testing.T) {
	const workers = 50
	const transferCents = 100 // $1 per transfer
	balance := 100_000        // $1000.00 starting balance — all in cents

	var mu sync.Mutex
	var wg sync.WaitGroup

	for range workers {
		wg.Add(1)
		go func() {
			defer wg.Done()
			mu.Lock()
			defer mu.Unlock()
			// Correct: the mutex serialises the read-modify-write.
			if balance < transferCents {
				return // insufficient funds — skip rather than go negative
			}
			balance -= transferCents
		}()
	}

	wg.Wait()

	// After all transfers the balance must be non-negative and
	// exactly workers*transferCents less than the start.
	want := 100_000 - workers*transferCents
	if balance != want {
		t.Errorf("balance = %d, want %d", balance, want)
	}
	if balance < 0 {
		t.Errorf("balance went negative: %d", balance)
	}
}
```

<Callout kind="note" title="This test is the spec for the Lab">

The `go test -race` flag instruments every memory access and reports concurrent reads/writes without a happens-before edge. A clean `-race` run on this test is the bar. Keep it in mind — it comes back in the Lab. Note: `for range workers` uses Go 1.22's range-over-integer syntax, which works unchanged in Go 1.26.

## Pessimistic Locking

The fix for the lost-update problem at the database level is pessimistic locking: acquire a lock on the row *before* you read it, hold that lock until you commit. No other transaction can read or write that row while you hold the lock. You're pessimistic — you assume someone *will* race you, so you prevent it up front.

<Define term="Pessimistic locking / SELECT ... FOR UPDATE">
**Pessimistic locking** means acquiring an exclusive lock on a resource *before* reading it, holding that lock for the duration of the transaction. In Postgres, the SQL clause is `SELECT ... FOR UPDATE`. It says: "read this row AND lock it — no other transaction may lock or write it until I commit or roll back." You're paying the overhead of lock management on every read, whether or not there's a race. The payoff: zero possibility of a lost update on that row.
</Define>

**On the job:** Use pessimistic locking on Meridian's account rows any time you do a read-compute-write on `balance_cents`. High-volume accounts (a prize pool, a merchant settlement account) can see hundreds of concurrent transfers — `SELECT ... FOR UPDATE` is the only correct tool there.

In Postgres (and most SQL databases), the spell is `SELECT ... FOR UPDATE`.

```sql
-- Instead of this (racy):
SELECT balance_cents FROM accounts WHERE id = $1;

-- Write this (safe):
SELECT balance_cents FROM accounts WHERE id = $1 FOR UPDATE;
```

The `FOR UPDATE` clause does two things:

1. It reads the row *and* acquires an exclusive row-level lock on it.
2. Any other transaction that tries to `SELECT ... FOR UPDATE` the same row will **block** until your transaction commits or rolls back.

The transfers are now effectively serialized — one at a time on that account row, even though they ran concurrently. No money lost. No money created.

In Go, using `pgx` (the idiomatic Postgres driver), the lock query looks like this:

```go
// selectBalanceForUpdate reads the account balance and acquires a row lock.
// Must be called inside an active transaction (tx).
func selectBalanceForUpdate(ctx context.Context, tx pgx.Tx, accountID int64) (int64, error) {
	var balanceCents int64
	err := tx.QueryRow(ctx,
		`SELECT balance_cents FROM accounts WHERE id = $1 FOR UPDATE`,
		accountID,
	).Scan(&balanceCents)
	return balanceCents, err
}
```

<Callout kind="warn" title="FOR UPDATE is a database-level lock — not a Go-level mutex">

`SELECT ... FOR UPDATE` acquires a lock *inside the database*. Other Go processes hitting the same Postgres instance are also blocked — it's not limited to your one service instance. This is exactly what you want for a balance update: the lock must be cluster-wide, not just in-process.

</Callout>

<UnderTheHood title="How SELECT FOR UPDATE acquires a row lock (Go 1.26 / Postgres 16+)">

When Postgres executes `SELECT ... FOR UPDATE`, it does something distinct from a normal MVCC read:

1. It finds the target row via normal index/heap scans.
2. For each row, it calls `LockTuple()` in the lock manager, requesting an `ExclusiveLock` on that specific heap tuple.
3. If another transaction already holds an incompatible lock (another `FOR UPDATE`, a `FOR SHARE`, or a `FOR NO KEY UPDATE`), the requesting transaction is added to a **wait queue** on that lock. The OS puts the waiter to sleep via a condition variable inside `ProcSleep()`. The lock manager is protected by a lightweight `LWLock`, not a heavyweight lock — fast for the common case where there's no contention.
4. When the holding transaction commits or rolls back, Postgres calls `UnlockTuple()`, wakes the first waiter in the queue, and the waiter re-checks the lock before proceeding.

The row lock is held for the rest of the transaction — it's released only at `COMMIT` or `ROLLBACK`. This is why you must keep transactions short when using `FOR UPDATE`: long-held row locks create a queue of waiting transactions, and your throughput tanks.

*This description models the lock manager at a conceptual level; the actual implementation spans multiple source files and is more nuanced.*

**Deadlock detection:** Postgres detects deadlocks by periodically traversing the wait-for graph. If TX A waits for a lock held by TX B, and TX B waits for a lock held by TX A, Postgres picks one victim (the transaction with the lower cost to abort) and rolls it back with `ERROR: deadlock detected`. Go code receives this as an error from `tx.Exec` and must retry the transaction from scratch. We'll show the deadlock-safe lock ordering in the next section.

</UnderTheHood>

## Optimistic Locking

Pessimistic locking is correct, but it serializes all writes to a row. If contention is low — most of the time nobody races you — you're paying the overhead of lock management and blocking for a scenario that rarely happens. **Optimistic locking** assumes you won't be raced, and detects the collision after the fact instead of preventing it up front.

<Define term="Optimistic locking">
**Optimistic locking** lets a transaction proceed without acquiring any lock, then checks at commit time whether the data changed under it. The standard implementation adds a **version column** — an integer that increments on every update. At write time, the `UPDATE` includes `WHERE version = $old_version`: if zero rows are affected, another transaction won the race and changed the version first. The current transaction retries from scratch. Optimistic locking wins when contention is low (most writes don't race); it degrades into a thundering-herd problem when contention is high.
</Define>

**On the job:** Optimistic locking is the right choice for Meridian's user profile updates or currency preferences — fields that are rarely written concurrently. It's the wrong choice for `balance_cents` on a high-volume account.

The pattern uses a **version column**: an integer that increments on every update. The transaction reads the current version, does its work, and then updates only if the version *hasn't changed*. If another transaction beat you, the version has changed and your update affects zero rows — that's your signal to retry.

```sql
-- Schema: add a version column to accounts
ALTER TABLE accounts ADD COLUMN version INT NOT NULL DEFAULT 1;

-- Optimistic update: only succeeds if nobody changed the row since we read it
UPDATE accounts
SET balance_cents = $1, version = version + 1
WHERE id = $2 AND version = $3;
-- If rowsAffected == 0, someone else changed it first → retry the transaction
```

Here's the full Go implementation of an optimistic transfer:

```go
// ErrConflict signals that another transaction committed before us.
// The caller should retry the whole operation.
var ErrConflict = errors.New("optimistic conflict: row was modified by another transaction")

// transferOptimistic attempts a balance debit using optimistic locking.
// It retries up to maxRetries times on conflict.
func transferOptimistic(
	ctx context.Context,
	db *pgxpool.Pool,
	accountID int64,
	amountCents int64,
	maxRetries int,
) error {
	for attempt := range maxRetries {
		err := tryTransferOptimistic(ctx, db, accountID, amountCents)
		if err == nil {
			return nil
		}
		if !errors.Is(err, ErrConflict) {
			return err // real error — don't retry
		}
		// Exponential backoff with jitter would go here in production.
		// For clarity, we just loop.
		_ = attempt
	}
	return fmt.Errorf("transfer failed after %d retries: %w", maxRetries, ErrConflict)
}

func tryTransferOptimistic(
	ctx context.Context,
	db *pgxpool.Pool,
	accountID int64,
	amountCents int64,
) error {
	tx, err := db.Begin(ctx)
	if err != nil {
		return err
	}
	defer tx.Rollback(ctx) //nolint:errcheck — intentional best-effort rollback

	// 1. Read current balance and version — no lock acquired.
	var balanceCents int64
	var version int
	err = tx.QueryRow(ctx,
		`SELECT balance_cents, version FROM accounts WHERE id = $1`,
		accountID,
	).Scan(&balanceCents, &version)
	if err != nil {
		return err
	}

	// 2. Check funds — business logic, not a DB constraint.
	if balanceCents < amountCents {
		return errors.New("insufficient funds")
	}

	// 3. Compare-and-swap: only update if version hasn't changed.
	tag, err := tx.Exec(ctx,
		`UPDATE accounts
		    SET balance_cents = $1, version = version + 1
		  WHERE id = $2 AND version = $3`,
		balanceCents-amountCents, accountID, version,
	)
	if err != nil {
		return err
	}
	if tag.RowsAffected() == 0 {
		// Zero rows updated → someone else changed the version first.
		return ErrConflict
	}

	return tx.Commit(ctx)
}
```

`for attempt := range maxRetries` uses Go 1.22's range-over-integer syntax, unchanged in Go 1.26.

### When to choose optimistic vs. pessimistic

<ConceptGrid cols={2}>
  <ConceptCard label="Use pessimistic (FOR UPDATE) when...">Contention is high — the same account is hit by many concurrent transfers. A payment processing queue where many workers drain one account. You cannot afford retries (strict latency SLAs). The operation has expensive side effects you don't want to repeat.</ConceptCard>
  <ConceptCard label="Use optimistic (version column) when...">Contention is low — most transfers hit different accounts. You're writing a distributed system where lock-holding across network calls would be disastrous. Retries are cheap and safe. The happy path (no conflict) must be as fast as possible.</ConceptCard>
  <Gotcha>Never use optimistic locking for the account balance if your service handles burst traffic on popular accounts (e.g., a prize account hit by 10,000 concurrent claimants). At high contention, every transaction retries repeatedly, and you've turned a locking problem into a thundering-herd problem. Use FOR UPDATE there.</Gotcha>
</ConceptGrid>

## Safe Concurrent Transfers

Now we put it all together. A production transfer between two accounts — with both sides locked, a funds check, and the double-entry ledger posted inside the same transaction.

But first: **deadlocks**.

<Define term="Deadlock">
A **deadlock** occurs when two or more transactions are each waiting for a lock held by the other, forming a cycle in the wait-for graph. Neither can proceed. Example: TX 1 locks account A then waits for account B; TX 2 has locked account B and is waiting for account A. Postgres detects this within `deadlock_timeout` (default 1 second) and aborts one transaction with `ERROR: deadlock detected`. The aborted transaction must be retried from scratch. Prevention is better than detection — lock multiple rows in a deterministic order.
</Define>

**On the job:** Deadlocks between transfers are the most common liveness bug in fintech database code. They're invisible in single-threaded tests and emerge under concurrent load. The fix costs one comparison.

If TX 1 locks account A then tries to lock account B, while TX 2 locks account B then tries to lock account A — they deadlock. The fix is a deterministic lock order: always lock accounts in ascending order of their ID, regardless of which is the sender and which is the receiver.

```go
// TransferCents moves amountCents from senderID to receiverID.
// It posts balanced double-entry ledger entries and updates both
// account balances inside a single ACID transaction.
// Accounts are locked in ascending ID order to prevent deadlocks.
func TransferCents(
	ctx context.Context,
	db *pgxpool.Pool,
	senderID, receiverID int64,
	amountCents int64,
	description string,
) error {
	if amountCents <= 0 {
		return errors.New("transfer amount must be positive")
	}
	if senderID == receiverID {
		return errors.New("sender and receiver must be different")
	}

	tx, err := db.Begin(ctx)
	if err != nil {
		return fmt.Errorf("begin transaction: %w", err)
	}
	defer tx.Rollback(ctx) //nolint:errcheck — rollback on any early return

	// --- Step 1: lock both accounts in a consistent order (lower ID first) ---
	// This is the deadlock prevention. Without it, two concurrent transfers
	// between accounts A and B can deadlock if they lock in opposite orders.
	first, second := senderID, receiverID
	if receiverID < senderID {
		first, second = receiverID, senderID
	}

	type accountRow struct {
		id           int64
		balanceCents int64
	}

	var accs [2]accountRow
	rows, err := tx.Query(ctx,
		`SELECT id, balance_cents
		   FROM accounts
		  WHERE id = ANY($1)
		  ORDER BY id
		  FOR UPDATE`,
		[]int64{first, second},
	)
	if err != nil {
		return fmt.Errorf("lock accounts: %w", err)
	}
	i := 0
	for rows.Next() {
		if err := rows.Scan(&accs[i].id, &accs[i].balanceCents); err != nil {
			rows.Close()
			return err
		}
		i++
	}
	rows.Close()
	if err := rows.Err(); err != nil {
		return fmt.Errorf("read locked accounts: %w", err)
	}
	if i != 2 {
		return errors.New("one or both accounts not found")
	}

	// Map back: which locked row is sender, which is receiver?
	var senderBal, receiverBal int64
	for _, a := range accs {
		if a.id == senderID {
			senderBal = a.balanceCents
		} else {
			receiverBal = a.balanceCents
		}
	}

	// --- Step 2: business rule — sufficient funds ---
	if senderBal < amountCents {
		return fmt.Errorf("insufficient funds: have %d cents, need %d", senderBal, amountCents)
	}

	// --- Step 3: post the balanced double-entry ledger entries ---
	_, err = tx.Exec(ctx,
		`INSERT INTO ledger_entries (account_id, amount_cents, description, created_at)
		 VALUES ($1, $2, $3, NOW()),
		        ($4, $5, $3, NOW())`,
		senderID, -amountCents, description,
		receiverID, amountCents, description,
	)
	if err != nil {
		return fmt.Errorf("post ledger entries: %w", err)
	}

	// --- Step 4: update both balances atomically ---
	_, err = tx.Exec(ctx,
		`UPDATE accounts
		    SET balance_cents = CASE id
		        WHEN $1 THEN balance_cents - $3
		        WHEN $2 THEN balance_cents + $3
		    END
		  WHERE id = ANY($4)`,
		senderID, receiverID, amountCents, []int64{senderID, receiverID},
	)
	if err != nil {
		return fmt.Errorf("update balances: %w", err)
	}

	// Sanity check: no negative balances (belt-and-suspenders; a DB constraint also enforces this)
	if senderBal-amountCents < 0 || receiverBal+amountCents < 0 {
		return errors.New("balance invariant violated — rolling back")
	}

	return tx.Commit(ctx)
}
```

## Sagas & Compensating Actions

ACID transactions are powerful, but they have a hard limit: they work when *all the operations you need to make atomically live inside one database*. Reality is messier.

Consider this Meridian transfer: debit the user's wallet in the ledger service, then credit their external bank account via the ACH network. These are two different systems. You cannot put them in one `BEGIN`/`COMMIT` block. If the ACH call succeeds but the ledger service crashes before recording it, or vice versa — you have a split-brain transfer.

This is the problem **sagas** solve.

<Define term="Saga">
A **saga** is a sequence of local ACID transactions, one per service or system, each of which commits independently. Instead of one global atomic commit across multiple systems (which is impossible without a distributed coordinator), a saga achieves **eventual consistency** — with the guarantee that if any step fails, every preceding step is reversed by a **compensating action**. A saga is not a hack; it's the correct model for multi-system money movement, used in production at every major payments company.
</Define>

**On the job:** Meridian's cross-bank transfer is a saga: debit the wallet (local Postgres), reserve escrow (local Postgres), submit to ACH (external). Any of these can fail independently. A saga with compensating actions is what keeps the books correct when step 3 fails after steps 1 and 2 already committed.

### What a saga is

A saga is a **sequence of local transactions**, where each step commits to its own database. Instead of a global atomic commit, you get eventual consistency — with the guarantee that if any step fails, every *preceding step* is undone by a **compensating action**.

<Define term="Compensating action / transaction">
A **compensating action** (also called a compensating transaction) is a new, committed database transaction that reverses the *business effect* of a previously committed step. It is NOT a `ROLLBACK` — that would make the change invisible. A compensation is a new ledger entry that is permanently visible in the audit log. Example: a debit of $200 is compensated by a credit of $200 — both appear in the ledger, and together they net to zero. This is mandatory for regulated financial systems: auditors need to see what happened and that it was corrected, not a sanitized view where the failure never occurred.
</Define>

Every step has a companion:

| Forward Action | Compensating Action |
|---|---|
| Debit sender wallet | Credit sender wallet (reverse debit) |
| Reserve funds in escrow | Release escrow hold |
| Submit ACH transfer | Initiate ACH return / reversal |
| Notify recipient | Send "transfer failed" notification |

A compensating action is not a rollback — it's a new, committed transaction that reverses the business effect of a previous one. The failed step and the compensation are *both* in the ledger's audit trail. That's a feature, not a bug.

### Orchestration vs. choreography

<Define term="Orchestration vs. choreography">
**Orchestration** uses a central **saga orchestrator** — a dedicated service or state machine — that knows the full step sequence, calls each step, and triggers compensating actions on failure. The orchestrator is the single source of truth for saga state. **Choreography** uses no central coordinator: each service publishes events ("DebitSucceeded") and subscribes to events from others ("ACHFailed"), and the saga emerges from the event flow. Orchestration is easier to reason about and observe; choreography is more decoupled but harder to trace. For money movement at Meridian, prefer orchestration — a money transfer needs a clear, auditable state machine.
</Define>

**On the job:** Choreography sounds elegant until you have to debug a half-executed saga in production at 2am. An orchestrated saga has a `saga_state` table — you can query it. A choreographed saga's state is implicit in a dozen event handlers across five services.

<ConceptGrid cols={2}>
  <ConceptCard label="Orchestration">A central **saga orchestrator** (a dedicated service or state machine) knows the full sequence. It calls step 1, waits for success, calls step 2, and so on. If any step fails, it calls the compensating actions in reverse order. The orchestrator is the single source of truth for saga state. Easier to reason about, easier to observe, but the orchestrator is a bottleneck and a single point of failure.</ConceptCard>
  <ConceptCard label="Choreography">Each service **publishes events** and subscribes to the events of others. "DebitSucceeded" triggers the ACH submission. "ACHFailed" triggers the compensation. No central coordinator — the saga emerges from the event flow. Decoupled and scalable, but harder to trace and debug. The saga's state is implicit in the event stream.</ConceptCard>
</ConceptGrid>

For fintech, **orchestration is usually the right choice for the saga itself** — you want a clear, observable state machine for a money movement, not implicit behavior spread across a dozen event handlers. Use choreography for the notifications and downstream side effects.

### Combining the saga with the transactional outbox

There's a subtle bug lurking in a naive saga implementation: what if the orchestrator successfully calls `DebitSender` but *crashes before it can record that step 1 succeeded* and trigger step 2? On restart, does it retry step 1 (double-debit!) or skip it (inconsistent)?

The answer is the **transactional outbox** — covered in depth in the Idempotency & Exactly-Once Semantics chapter. The short version: every state transition in the saga is written to an `outbox` table inside the *same* local ACID transaction as the saga state update. A separate outbox relay process reads unprocessed outbox records and fires the next saga step (or the compensating action) reliably — with at-least-once delivery and idempotent handlers. If the orchestrator crashes, the relay picks up where it left off, using the outbox as a durable work queue.

```
saga_state table (orchestrator DB)          outbox table (same DB, same TX)
┌─────────────────────────────────┐         ┌──────────────────────────────────┐
│ id │ step    │ status           │         │ id │ saga_id │ event_type        │
│ 42 │ DEBITED │ COMPENSATING ... │  ──TX── │ 7  │ 42      │ debit_compensate  │
└─────────────────────────────────┘         └──────────────────────────────────┘
         ↑ both written in one BEGIN/COMMIT
         Relay reads outbox and calls compensating action exactly once
```

<UnderTheHood title="Why sagas are not rollbacks — and why that matters for auditability">

A database `ROLLBACK` is invisible: it undoes changes as if they never happened, and nothing appears in the audit log. A saga compensation is the opposite: it is a *committed* transaction that explicitly reverses a business effect, and both the original action and the compensation are permanently visible in your ledger.

For a regulated financial system, this is mandatory. Your auditor wants to see that $200 was debited at 14:23:01, an ACH submission failed at 14:23:07, and a compensating credit was posted at 14:23:08. They want the full event history, not a cleaned-up state as if the failure never happened.

This is why Meridian's ledger is **append-only** (see the Double-Entry Ledgers chapter) and why a saga compensation posts a new ledger entry rather than deleting the original one. Immutability of the audit trail is a compliance requirement, not an implementation detail.

</UnderTheHood>

```go
package main

import (
	"errors"
	"fmt"
)

// SagaStep describes one step and its compensation.
type SagaStep struct {
	Name       string
	Forward    func() error
	Compensate func() error
}

// RunSaga executes steps in order.
// If any step fails, it runs compensating actions in reverse order
// for all previously completed steps.
func RunSaga(steps []SagaStep) error {
	completed := make([]SagaStep, 0, len(steps))

	for _, step := range steps {
		fmt.Printf("→ executing: %s\n", step.Name)
		if err := step.Forward(); err != nil {
			fmt.Printf("✗ %s failed: %v — compensating\n", step.Name, err)
			// Unwind in reverse order (LIFO).
			for i := len(completed) - 1; i >= 0; i-- {
				s := completed[i]
				fmt.Printf("  ↩ compensating: %s\n", s.Name)
				if cerr := s.Compensate(); cerr != nil {
					// Compensation failure is a serious problem in production —
					// log it, alert, and queue for manual review. Never silently drop.
					fmt.Printf("  ✗ compensation failed for %s: %v\n", s.Name, cerr)
				}
			}
			return fmt.Errorf("saga failed at step %q: %w", step.Name, err)
		}
		fmt.Printf("✓ %s succeeded\n", step.Name)
		completed = append(completed, step)
	}
	return nil
}

func main() {
	// Simulate a cross-service transfer: debit → escrow → ACH submission.
	// Step 3 (ACH) fails.
	steps := []SagaStep{
		{
			Name:       "Debit sender wallet ($200)",
			Forward:    func() error { return nil }, // succeeds
			Compensate: func() error { fmt.Println("  [ledger] credit $200 back to sender"); return nil },
		},
		{
			Name:       "Reserve escrow hold",
			Forward:    func() error { return nil }, // succeeds
			Compensate: func() error { fmt.Println("  [ledger] release escrow hold"); return nil },
		},
		{
			Name:       "Submit ACH transfer",
			Forward:    func() error { return errors.New("bank account closed") }, // fails
			Compensate: func() error { return nil },                               // nothing to undo — never ran
		},
	}

	if err := RunSaga(steps); err != nil {
		fmt.Println("\nsaga result:", err)
	}
}
```

<Exercise n={1} title="Identify the anomaly" level="easy">

A user's session reads their account balance at 09:00 AM, displaying $500 in the UI. While their session is still open, a scheduled fee deduction commits and reduces the balance to $480. The user's session runs the same balance query again at 09:05 AM and sees $480.

Name the anomaly. Which isolation level prevents it? Which isolation level is this session running at (or lower)?

<Solution>

This is a **non-repeatable read** — the same query in the same transaction returned a different value because another transaction committed between the two reads.

It is prevented by **Repeatable Read** isolation (and Serializable). At Repeatable Read, Postgres takes a snapshot at the start of the transaction, not at the start of each statement, so the balance query at 09:05 would still return $500 even after the fee committed.

The session is running at **Read Committed** (or lower) — because that's the isolation level at which each statement gets a fresh snapshot.

</Solution>

You have a table `accounts(id BIGINT, balance_cents BIGINT)`. Write the SQL query (as a Go string passed to `tx.QueryRow`) that reads the balance for a given account ID *and* acquires a row-level exclusive lock. Explain in a comment why the lock must be acquired before reading the balance.

<Exercise n={3} title="Fix the deadlock" level="medium">

This code runs concurrently for transfers between account pairs. Identify why it can deadlock and rewrite the locking to be deadlock-safe.

```go
// BUGGY — can deadlock if two transfers between the same accounts run concurrently.
func transferBuggy(ctx context.Context, tx pgx.Tx, senderID, receiverID int64) error {
	var senderBal int64
	if err := tx.QueryRow(ctx,
		`SELECT balance_cents FROM accounts WHERE id = $1 FOR UPDATE`, senderID,
	).Scan(&senderBal); err != nil {
		return err
	}
	var receiverBal int64
	return tx.QueryRow(ctx,
		`SELECT balance_cents FROM accounts WHERE id = $1 FOR UPDATE`, receiverID,
	).Scan(&receiverBal)
}
```

<Solution>

The bug: if TX 1 does `lock(A) then lock(B)` while TX 2 does `lock(B) then lock(A)`, they deadlock — each holds what the other needs.

The fix: always lock in ascending ID order, regardless of which is sender and which is receiver.

```go
// transferFixed locks both accounts in ascending ID order to prevent deadlocks.
func transferFixed(ctx context.Context, tx pgx.Tx, senderID, receiverID int64) error {
	// Sort IDs so we always lock the lower ID first.
	ids := []int64{senderID, receiverID}
	if ids[1] < ids[0] {
		ids[0], ids[1] = ids[1], ids[0]
	}

	var bal1, bal2 int64
	if err := tx.QueryRow(ctx,
		`SELECT balance_cents FROM accounts WHERE id = $1 FOR UPDATE`, ids[0],
	).Scan(&bal1); err != nil {
		return err
	}
	return tx.QueryRow(ctx,
		`SELECT balance_cents FROM accounts WHERE id = $1 FOR UPDATE`, ids[1],
	).Scan(&bal2)
	// In a real transfer you'd use the scanned balances to check funds and post entries.
}
```

Two concurrent transfers between accounts 1 and 2 will both try to lock account 1 first. One blocks; the other proceeds and commits; the blocked one then gets the lock. No deadlock.

</Solution>

</Exercise>

<Exercise n={4} title="Optimistic locking with retry" level="medium">

Implement `debitOptimistic(ctx context.Context, db *pgxpool.Pool, accountID int64, amountCents int64) error` using a version column. The function should read `balance_cents` and `version`, check funds, then attempt a compare-and-swap update. If `RowsAffected() == 0` (conflict), return a sentinel `ErrConflict`. Wrap it in a loop that retries up to 3 times.

<Solution>

```go
var ErrConflict = errors.New("optimistic conflict")

func debitOptimistic(ctx context.Context, db *pgxpool.Pool, accountID, amountCents int64) error {
	for attempt := range 3 {
		err := attemptDebit(ctx, db, accountID, amountCents)
		if err == nil {
			return nil
		}
		if !errors.Is(err, ErrConflict) {
			return err
		}
		// Conflict on attempt+1; loop and retry.
		_ = attempt
	}
	return fmt.Errorf("debit failed after 3 retries: %w", ErrConflict)
}

func attemptDebit(ctx context.Context, db *pgxpool.Pool, accountID, amountCents int64) error {
	tx, err := db.Begin(ctx)
	if err != nil {
		return err
	}
	defer tx.Rollback(ctx) //nolint:errcheck

	var bal, ver int64
	err = tx.QueryRow(ctx,
		`SELECT balance_cents, version FROM accounts WHERE id = $1`,
		accountID,
	).Scan(&bal, &ver)
	if err != nil {
		return err
	}
	if bal < amountCents {
		return errors.New("insufficient funds")
	}

	tag, err := tx.Exec(ctx,
		`UPDATE accounts
		    SET balance_cents = $1, version = version + 1
		  WHERE id = $2 AND version = $3`,
		bal-amountCents, accountID, ver,
	)
	if err != nil {
		return err
	}
	if tag.RowsAffected() == 0 {
		return ErrConflict
	}
	return tx.Commit(ctx)
}
```

`for attempt := range 3` uses Go 1.22+'s range-over-integer syntax, unchanged in Go 1.26. The `_ = attempt` suppresses the unused variable; in production you'd use it to compute backoff duration.

</Solution>

</Exercise>

<Exercise n={5} title="Add a compensating action" level="hard">

You have a saga where step 1 debits $50 from account 42 by calling `postLedgerEntry(ctx, db, accountID, -5000)`. Define the compensating action as a function `compensateDebit(ctx context.Context, db *pgxpool.Pool, accountID, amountCents int64) error` and explain: (a) why the compensation must be a new INSERT, not a DELETE; (b) how you ensure the compensation is not applied twice if the saga orchestrator crashes after the compensation commits but before it records the outcome.

<Solution>

```go
// compensateDebit reverses a previously posted debit by inserting a new credit
// entry. It does NOT delete the original debit — the audit trail is immutable.
func compensateDebit(ctx context.Context, db *pgxpool.Pool, accountID, amountCents int64) error {
	// amountCents is the absolute value of the original debit (positive).
	// The compensating entry credits the account (positive amount).
	return postLedgerEntry(ctx, db, accountID, amountCents)
}

// postLedgerEntry inserts one ledger entry and updates the running balance.
// idempotencyKey (omitted here for brevity) prevents double-posting on retry.
func postLedgerEntry(ctx context.Context, db *pgxpool.Pool, accountID, amountCents int64) error {
	// Real implementation uses a transaction and updates balance_cents too.
	_, err := db.Exec(ctx,
		`INSERT INTO ledger_entries (account_id, amount_cents, created_at)
		 VALUES ($1, $2, NOW())`,
		accountID, amountCents,
	)
	return err
}
```

**(a)** The original debit must never be deleted because Meridian's ledger is an immutable audit trail. Regulators and auditors need to see that a debit was posted and then reversed — both events. A DELETE would leave a gap in the audit log that looks like the money never moved. Compensation is a new, committed credit entry; the two entries together net to zero, and both are visible forever.

**(b)** Use an **idempotency key** on the compensation: store the saga step ID (e.g., `saga_id + "_compensate_step1"`) as a unique key on the `ledger_entries` table. If the orchestrator crashes after the compensation commits but before recording the outcome, the relay re-runs the compensation, hits the unique constraint, and knows the compensation already succeeded. The Idempotency & Exactly-Once Semantics chapter covers this pattern in depth.

</Solution>

</Exercise>

<Recap>

- **ACID** is the contract: **A**tomicity (all or nothing), **C**onsistency (invariants hold), **I**solation (concurrent transactions don't see each other's in-progress work), **D**urability (committed data survives crashes).
- **Postgres defaults to Read Committed.** At this level, each SQL statement sees a fresh snapshot of committed data — but two statements in the same transaction can see different snapshots, enabling the lost-update anomaly.
- The **lost-update problem**: two transactions both read the same balance, compute independently, both write back — one update is silently overwritten. No error is raised. Real money vanishes.
- **`SELECT ... FOR UPDATE`** (pessimistic locking) acquires an exclusive row lock before reading, blocking all concurrent lockers until commit. It serializes writes to a row and prevents lost updates.
- **Optimistic locking** uses a version column and a compare-and-swap update. If `RowsAffected() == 0`, another transaction won the race — retry. Best when contention is low.
- **Deadlock prevention**: always lock multiple rows in a deterministic order (ascending ID). Inconsistent lock ordering is the #1 cause of database deadlocks in fintech systems. Postgres detects deadlocks and rolls back one victim; your code must retry.
- A **saga** is a sequence of local ACID transactions, each with a **compensating action** (a new committed transaction that reverses the business effect). Used when a transfer spans services or external systems that can't share one ACID transaction.
- **Compensation is not rollback** — it's a new committed event. Both the forward action and the compensation appear in the audit log. This is a compliance requirement, not a workaround.
- **Orchestration vs. choreography**: orchestration uses a central coordinator (clear state, easier to observe); choreography uses events (decoupled, harder to trace). Use orchestration for saga state machines in fintech.
- Wire the saga to the **transactional outbox** (covered in Idempotency & Exactly-Once Semantics) so saga state transitions and outbox events are committed atomically — no crash can leave the saga in an ambiguous state.

</Recap>
