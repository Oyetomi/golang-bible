<HeroCard label="Part 3 · Chapter 3" title="Transactions, Consistency & Sagas">

Chapter 2's ledger enforces its rules on every write: every transaction balances, and nothing is ever edited. But rules about single writes say nothing about **many writes at once**, or about **a process that dies halfway through a sequence of them**. Meridian pays out thousands of merchants a day, from dozens of workers, through a bank that is sometimes slow and sometimes down. This chapter measures what goes wrong in each of those situations, on the real ledger, and what each fix costs.

It covers two scales. Inside one database, **transactions** and their **isolation levels**, and the locking that decides who waits for whom. Across systems, where no database transaction can reach (Meridian's ledger and the bank's), a **saga**: a sequence of steps, each committed on its own, with a recorded state and a compensating step for when things fail.

Six stops. If you get lost, come back here:

1. **Atomicity.** One transaction, and chapter 2's lost money stops.
2. **Isolation.** What concurrent transactions can see of each other, and two anomalies measured.
3. **Pessimistic locking.** `SELECT ... FOR UPDATE`: wait your turn.
4. **Optimistic locking.** Check at the end, and retry.
5. **Deadlocks.** Two transfers waiting for each other, and the ordering rule that prevents it.
6. **Sagas.** A payout that crosses into the bank, survives timeouts and crashes, and reconciles.

## Atomicity

*Stop 1 of 6.*

### Step 1: all or nothing

A database **transaction** groups statements so they take effect together or not at all: `BEGIN`, the statements, `COMMIT`. If the process dies, the connection drops, or any statement fails before `COMMIT`, Postgres discards everything the transaction did. That's the **A** in ACID (atomicity). The other three: **C**onsistency (the constraints hold after every commit: chapter 2's balance trigger is one), **I**solation (stop 2), and **D**urability (once `COMMIT` returns, the change survives a crash, because it's in the write-ahead log on disk).

### Step 2: chapter 2's loop, in one transaction

The same random transfers between two wallets, but both `UPDATE`s inside `pgx.BeginFunc`, which commits if the function returns `nil` and rolls back otherwise:

```go noverify
// main.go, lines 36–45
			err := pgx.BeginFunc(ctx, db, func(tx pgx.Tx) error {
				if _, err := tx.Exec(ctx, `UPDATE wallets SET balance = balance - $2 WHERE id = $1`, from, amt); err != nil {
					return err
				}
				_, err := tx.Exec(ctx, `UPDATE wallets SET balance = balance + $2 WHERE id = $1`, to, amt)
				return err
			})
			if err != nil {
				log.Fatal(err)
			}
```

Killed with `SIGKILL` after two seconds, ten times:

run 2: killed after 11000 transfers; money in the system: 2000.00 (started with 2000.00)
run 3: killed after 13000 transfers; money in the system: 2000.00 (started with 2000.00)
run 4: killed after 10000 transfers; money in the system: 2000.00 (started with 2000.00)

## Isolation

*Stop 2 of 6.*

### Step 1: what a transaction sees

When transactions run at the same time, **isolation** decides what each sees of the others. The SQL standard defines levels by the anomalies they allow; Postgres implements three:

- **Read Committed** (the default): each statement sees everything committed before *it* started. Two `SELECT`s in one transaction can see different data.
- **Repeatable Read**: the whole transaction sees one **snapshot**, taken at its first statement. Rows updated by others after that are invisible, and updating a row someone else changed and committed meanwhile aborts with a serialization failure (SQLSTATE `40001`).
- **Serializable**: the result is guaranteed to be the same as running the transactions one after another in some order. Postgres does it by watching what each transaction read and wrote (Serializable Snapshot Isolation) and aborting one with `40001` when a dangerous pattern appears. The application must retry.

### Step 2: the lost update

Sixteen workers each add $1.00 to one cached balance 500 times: $8,000.00 in total. Three ways:

```go noverify
// main.go, lines 27–44
	// Read the balance into Go, add, write the result back.
	readModifyWrite := func(iso pgx.TxIsoLevel) func() error {
		return func() error {
			return pgx.BeginTxFunc(ctx, db, pgx.TxOptions{IsoLevel: iso}, func(tx pgx.Tx) error {
				var b int64
				if err := tx.QueryRow(ctx, `SELECT balance FROM counter WHERE id = 1`).Scan(&b); err != nil {
					return err
				}
				_, err := tx.Exec(ctx, `UPDATE counter SET balance = $1 WHERE id = 1`, b+100)
				return err
			})
		}
	}
	// Let the database do the addition.
	increment := func() error {
		_, err := db.Exec(ctx, `UPDATE counter SET balance = balance + 100 WHERE id = 1`)
		return err
	}
```

```text
read-modify-write, read committed    balance $1144.00 of $8000.00; 6856 updates lost; 0 aborted with 40001
read-modify-write, repeatable read   balance $1676.00 of $8000.00; 0 updates lost; 6324 aborted with 40001
balance = balance + 100              balance $8000.00 of $8000.00; 0 updates lost; 0 aborted with 40001
```

At Read Committed, read-modify-write lost **6,856 of 8,000** additions: two workers read the same balance, each wrote back its own "balance + 1", and one overwrote the other. At Repeatable Read, nothing was lost silently, but 6,324 transactions were aborted with `40001` because another had changed the row after their snapshot; without a retry loop that's 6,324 failed requests. `balance = balance + 100` in SQL lost nothing at the default level: the database reads and writes the row under its lock, in one step. (That's why chapter 2's `Post` updates cached balances this way.)

### Step 3: write skew, the anomaly with no shared row

The payout rule reads many rows (a merchant's postings) and writes new ones (a payout's postings). No two payouts update the same row, so nothing in stop 2's list conflicts. Fifty $10.00 payouts race for a merchant's $100.00, five rounds per strategy:

```go noverify
// payouts.go, lines 18–72
var ErrInsufficient = errors.New("insufficient balance")

// available is what Meridian owes the merchant: the negated balance of
// its liability account, derived from the postings.
func available(ctx context.Context, q interface {
	QueryRow(context.Context, string, ...any) pgx.Row
}, merchant string) (int64, error) {
	var b int64
	err := q.QueryRow(ctx, `SELECT coalesce(sum(amount), 0) FROM postings WHERE account_id = $1`, merchant).Scan(&b)
	return -b, err
}

func payoutTx(merchant string, amt int64) ledger.Transaction {
	tx, err := ledger.NewTransaction("payout",
		ledger.Leg(merchant, money.New(amt, money.USD)),
		ledger.Leg("assets:bank:usd", money.New(-amt, money.USD)))
	if err != nil {
		panic(err)
	}
	return tx
}

// Strategy is one way of making "check the balance, then pay out" safe
// (or not) when many payouts run at once.
type Strategy func(ctx context.Context, db *pgxpool.Pool, merchant string, amt int64) (retries int, err error)

// Naive checks and posts in one transaction at the given isolation level,
// with no locks. Read Committed and Repeatable Read both let two payouts
// see the same balance.
func Naive(iso pgx.TxIsoLevel) Strategy {
	return func(ctx context.Context, db *pgxpool.Pool, merchant string, amt int64) (int, error) {
		return 0, pgx.BeginTxFunc(ctx, db, pgx.TxOptions{IsoLevel: iso}, func(tx pgx.Tx) error {
			avail, err := available(ctx, tx, merchant)
			if err != nil {
				return err
			}
			if avail < amt {
				return ErrInsufficient
			}
			_, err = ledger.PostTx(ctx, tx, payoutTx(merchant, amt))
			return err
		})
	}
}

// Serializable runs the same code at SERIALIZABLE and retries when
// Postgres aborts it with a serialization failure (SQLSTATE 40001).
func Serializable(ctx context.Context, db *pgxpool.Pool, merchant string, amt int64) (int, error) {
	for retries := 0; ; retries++ {
		_, err := Naive(pgx.Serializable)(ctx, db, merchant, amt)
		if !isCode(err, "40001") {
			return retries, err
		}
	}
}
```

```text
strategy                       paid out per round (5 rounds; limit $100.00) retries  time/round
read committed, no lock        $150 $500 $500 $500 $500                           0  45ms
repeatable read, no lock       $500 $500 $500 $500 $500                           0  9ms
serializable + retry           $100 $100 $100 $100 $100                         863  27ms
SELECT ... FOR UPDATE          $100 $100 $100 $100 $100                           0  16ms
optimistic (version) + retry   $100 $100 $100 $100 $100                        1173  51ms
```

Read the first two rows. At **Read Committed**, $150 and then $500 paid out from $100. At **Repeatable Read**, $500 every round: all fifty snapshots said $100.00 was available, and all fifty inserted. This is **write skew**: each transaction's decision was correct for the data it read, and together they broke the rule. Repeatable Read can't see it, because it only aborts writes to the *same row*.

**Serializable** paid exactly $100 every round. Postgres tracked that each payout read the merchant's postings and another inserted into them, found the cycle, and aborted the losers with `40001`; `Serializable` retried them (863 retries over five rounds), and the retries saw the new balance and were refused.

## Pessimistic

*Stop 3 of 6.*

### Step 1: lock first, then check

If every payout for a merchant must take the same lock before reading the balance, they run one at a time, and each sees the previous one's postings. `SELECT ... FOR UPDATE` on the merchant's row in `accounts` is that lock: the row isn't changed, it's used as a turnstile:

```go noverify
// payouts.go, lines 74–91
// ForUpdate takes a row lock on the merchant's account first, so payouts
// for one merchant run one at a time.
func ForUpdate(ctx context.Context, db *pgxpool.Pool, merchant string, amt int64) (int, error) {
	return 0, pgx.BeginFunc(ctx, db, func(tx pgx.Tx) error {
		if _, err := tx.Exec(ctx, `SELECT 1 FROM accounts WHERE id = $1 FOR UPDATE`, merchant); err != nil {
			return err
		}
		avail, err := available(ctx, tx, merchant)
		if err != nil {
			return err
		}
		if avail < amt {
			return ErrInsufficient
		}
		_, err = ledger.PostTx(ctx, tx, payoutTx(merchant, amt))
		return err
	})
}
```

In the table above: **$100 every round, no retries, 16 ms a round**. The fifty payouts queue on the lock; each, once in, reads a balance that includes everything committed before it.

### Step 2: what it costs

The lock is held until the transaction commits, so everything the transaction does while holding it (queries, and anything slow a careless handler might do, like calling another service) adds to everyone else's wait. Keep the locked section short, and lock only what the rule is about: one merchant's payouts wait for each other, but not for other merchants'.

## Optimistic

*Stop 4 of 6.*

### Step 1: check at the end

**Optimistic** concurrency control takes no lock while working. It reads a **version** number along with the data, does its work, and commits only if the version is still the same, bumping it in the same statement. If someone else committed first, the version has moved, the update matches no row, and the transaction starts over:

```go noverify
// payouts.go, lines 93–130
// Optimistic takes no lock while reading. It reads a version number with
// the balance, and commits only if nobody bumped the version meanwhile;
// otherwise it starts again.
func Optimistic(ctx context.Context, db *pgxpool.Pool, merchant string, amt int64) (int, error) {
	for retries := 0; ; retries++ {
		err := pgx.BeginFunc(ctx, db, func(tx pgx.Tx) error {
			var version int64
			if err := tx.QueryRow(ctx, `SELECT version FROM account_versions WHERE account_id = $1`, merchant).Scan(&version); err != nil {
				return err
			}
			avail, err := available(ctx, tx, merchant)
			if err != nil {
				return err
			}
			if avail < amt {
				return ErrInsufficient
			}
			if _, err := ledger.PostTx(ctx, tx, payoutTx(merchant, amt)); err != nil {
				return err
			}
			tag, err := tx.Exec(ctx,
				`UPDATE account_versions SET version = version + 1 WHERE account_id = $1 AND version = $2`,
				merchant, version)
			if err != nil {
				return err
			}
			if tag.RowsAffected() == 0 {
				return errConflict
			}
			return nil
		})
		if !errors.Is(err, errConflict) {
			return retries, err
		}
	}
}

var errConflict = errors.New("version changed")
```

In the table: **$100 every round**, and **1,173 retries**. Fifty payouts all started together, all read version 0, and only one could win each time; the rest went round again.

### Step 2: choosing

| strategy | correct? | retries (5 rounds) | time per round |
| :--- | :---: | ---: | ---: |
| Read Committed, no lock | no ($150 to $500 from $100) | 0 | 45 ms |
| Repeatable Read, no lock | no ($500 from $100) | 0 | 9 ms |
| Serializable + retry | yes | 863 | 27 ms |
| `SELECT ... FOR UPDATE` | yes | 0 | 16 ms |
| optimistic version + retry | yes | 1,173 | 51 ms |

With fifty writers aimed at one merchant, the pessimistic lock won: waiting in line is cheaper than doing the work and throwing it away. Optimistic control wins in the opposite case, when conflicts are rare (payouts spread over many merchants) or when the "transaction" spans a user's think time and can't hold a lock that long (an edit form that saves with `WHERE version = $n`). Serializable is the most general (it catches conflicts you didn't think of) and needs every caller to retry on `40001`, and so do the other two retry-based strategies.

## Deadlocks

*Stop 5 of 6.*

### Step 1: two transfers, waiting for each other

Transfers between wallets lock both rows. If a transfer from Alice to Bob locks Alice, and at the same moment a transfer from Bob to Alice locks Bob, each then waits for the row the other holds. Neither can proceed: a **deadlock**. Postgres checks for one when a lock wait passes `deadlock_timeout` (1 second by default), and breaks it by aborting one transaction with SQLSTATE `40P01`.

```go noverify
// main.go, lines 29–44
	// transfer locks the payer's row, then the payee's.
	transfer := func(tx pgx.Tx, from, to string, amt int64) error {
		for _, id := range []string{from, to} {
			if _, err := tx.Exec(ctx, `SELECT 1 FROM wallets WHERE id = $1 FOR UPDATE`, id); err != nil {
				return err
			}
		}
		return move(ctx, tx, from, to, amt)
	}
	// ordered locks both rows in one statement, always in id order.
	ordered := func(tx pgx.Tx, from, to string, amt int64) error {
		if _, err := tx.Exec(ctx, `SELECT 1 FROM wallets WHERE id IN ($1, $2) ORDER BY id FOR UPDATE`, from, to); err != nil {
			return err
		}
		return move(ctx, tx, from, to, amt)
	}
```

Eight workers, random directions, 20 seconds each way, every deadlock retried:

```text
lock payer, then payee       28 transfers in 20 s,   51 deadlocks (each retried), slowest transfer 34.112s
lock both in id order    121312 transfers in 20 s,    0 deadlocks (each retried), slowest transfer 159ms
```

**28 transfers in 20 seconds**, 51 deadlocks, and one transfer that waited 34 seconds, because a retry mostly walked into the next deadlock and the next 1-second detection. Locking both rows in a fixed order (by id) makes a cycle impossible: whoever holds the lower id can always get the higher one eventually. **121,312 transfers, no deadlocks.**

### Step 1: past the edge of the database

A payout ends with a bank transfer, and the bank isn't in Meridian's database: no `BEGIN ... COMMIT` can include both. The bank here is a separate HTTP service (`cmd/bank`) that behaves like a real partner: it deduplicates by transfer id, refuses closed accounts with `422`, answers `503` to about one request in ten, and for about one in twenty **executes the transfer but answers after 2 seconds**, long after Meridian's 500 ms timeout.

A **saga** splits the work into local transactions, each committed on its own, and gives every step that can't be undone by rollback a **compensating** step:

1. **Reserve**: move the amount from the merchant's account to `liabilities:payouts-pending`, and record the payout as `reserved`, in one database transaction.
2. **Send** to the bank with the payout's id.
3. **Settle** (pending → Meridian's bank account; state `settled`) if the bank paid, or **compensate** (pending → back to the merchant; state `compensated`) if it definitely won't.

```go noverify
// saga.go, lines 63–163
const pending = "liabilities:payouts-pending"

// Payouts pays merchants out as a saga: reserve in the ledger, send to the
// bank, then settle or compensate. Each step's postings and the payout's
// state commit together, so a crash between steps leaves a row that says
// exactly where the payout stopped.
type Payouts struct {
	DB   *pgxpool.Pool
	Bank Bank
}

// Pay runs one payout. It returns the state the payout reached.
func (p *Payouts) Pay(ctx context.Context, id, merchant, account string, amt int64) (string, error) {
	// Step 1: reserve. Lock the merchant (stop 3), check, move the money
	// from the merchant's account to payouts-pending, record the payout.
	err := pgx.BeginFunc(ctx, p.DB, func(tx pgx.Tx) error {
		if _, err := tx.Exec(ctx, `SELECT 1 FROM accounts WHERE id = $1 FOR UPDATE`, merchant); err != nil {
			return err
		}
		avail, err := available(ctx, tx, merchant)
		if err != nil {
			return err
		}
		if avail < amt {
			return ErrInsufficient
		}
		if _, err := ledger.PostTx(ctx, tx, legs("payout reserve", merchant, pending, amt)); err != nil {
			return err
		}
		_, err = tx.Exec(ctx, `INSERT INTO payouts (id, merchant, amount, state) VALUES ($1, $2, $3, 'reserved')`, id, merchant, amt)
		return err
	})
	if err != nil {
		return "", err
	}
	return p.send(ctx, id, merchant, account, amt)
}

// send is steps 2 and 3. An unknown outcome is retried with the same id,
// which the bank deduplicates; it is never compensated, because the bank
// may have paid.
func (p *Payouts) send(ctx context.Context, id, merchant, account string, amt int64) (string, error) {
	var err error
	for attempt := range 5 {
		if attempt > 0 {
			time.Sleep(time.Duration(50<<attempt) * time.Millisecond)
		}
		err = p.Bank.Send(ctx, id, account, amt)
		if err == nil {
			return "settled", p.finish(ctx, id, "settled", legs("payout settle", pending, "assets:bank:usd", amt))
		}
		if errors.Is(err, ErrRejected) {
			return "compensated", p.finish(ctx, id, "compensated", legs("payout compensate", pending, merchant, amt))
		}
	}
	return "reserved", nil // still unknown: Recover will try again later
}

// finish posts the step's transaction and moves the payout out of
// 'reserved', together. If another worker already finished it, nothing
// is posted.
func (p *Payouts) finish(ctx context.Context, id, state string, tx ledger.Transaction) error {
	return pgx.BeginFunc(ctx, p.DB, func(dbtx pgx.Tx) error {
		tag, err := dbtx.Exec(ctx, `UPDATE payouts SET state = $2, updated_at = now() WHERE id = $1 AND state = 'reserved'`, id, state)
		if err != nil || tag.RowsAffected() == 0 {
			return err
		}
		_, err = ledger.PostTx(ctx, dbtx, tx)
		return err
	})
}

// Recover finishes every payout a crash left in 'reserved': it sends
// again with the same id (the bank pays each id at most once) and settles
// or compensates.
func (p *Payouts) Recover(ctx context.Context, account func(merchant string) string) (map[string]int, error) {
	rows, err := p.DB.Query(ctx, `SELECT id, merchant, amount FROM payouts WHERE state = 'reserved'`)
	if err != nil {
		return nil, err
	}
	type po struct {
		id, merchant string
		amt          int64
	}
	todo, err := pgx.CollectRows(rows, func(r pgx.CollectableRow) (po, error) {
		var x po
		return x, r.Scan(&x.id, &x.merchant, &x.amt)
	})
	if err != nil {
		return nil, err
	}
	out := map[string]int{}
	for _, x := range todo {
		state, err := p.send(ctx, x.id, x.merchant, account(x.merchant), x.amt)
		if err != nil {
			return out, err
		}
		out[state]++
	}
	return out, nil
}
```

</CodeWalk>

- **State with every step.** The payout row is written in the same database transaction as the step's postings, so after any crash, `state = 'reserved'` lists exactly the payouts that stopped between steps.
- **Unknown is not failure.** A timeout or `503` means the bank *may* have paid. The saga retries with the **same id**, which the bank deduplicates, so a retry never pays twice. It compensates only on a definite refusal (`422`, merchant 7's closed account: 20 payouts).
- **Recovery.** On restart, `Recover` resends every `reserved` payout (same id) and finishes it.

The third scenario above killed the saga after 2 seconds: 8 payouts were `reserved` and $200.00 was pending; the bank had paid 6 of them and the ledger didn't know yet ($150.00 of difference). After `Recover`: 8 settled, nothing pending, **ledger and bank agree to the cent**. Run to completion, the saga settled 380 and compensated 20, again in agreement.

### Step 4: what makes a saga work

Sagas give up isolation: between reserve and settle, the money is visibly in flight, and other transactions can see the intermediate state (which is why it sits in its own pending account, not in the merchant's). In return, each step is short and local. The pattern holds as long as three things do: **every step records its state atomically with its effect, every external call is idempotent** (a retry is harmless), **and every step that can be undone has a compensation**. The first two reappear in the next two chapters: idempotency keys and exactly-once processing (chapter 4), and the transactional outbox, which records "a message must be sent" in the same transaction as the change that caused it (chapters 4 and 5).

<Exercise n={1} title="Retry with backoff" level="easy">

`Serializable` and `Optimistic` retry immediately, forever. Add a cap (say 10 attempts) and exponential backoff with jitter, and rerun the fifty-payout race. What happens to the retry count and the time per round?

<Solution>

Backoff spreads the retries out, so fewer of them collide again: the retry count drops sharply, and time per round may rise slightly (the waiting is now sleep instead of wasted work). The cap matters in production: under a pathological load, unbounded retries turn into unbounded latency. After the cap, return an error the caller can show ("try again") rather than spinning.

</Solution>

</Exercise>

<Exercise n={2} title="Serializable, for real" level="easy">

Run the lost-update experiment's read-modify-write at `pgx.Serializable`, with and without a retry loop. How does it compare with Repeatable Read?

<Solution>

Without retries it behaves like Repeatable Read here: the conflicting updates abort with 40001, and nothing is lost silently. With a retry loop, the balance reaches exactly $8,000.00. For single-row read-modify-write, Repeatable Read already detects the conflict; Serializable's extra value is in cases like stop 2's write skew, where the conflict is between a read and someone else's write.

</Solution>

</Exercise>

<Exercise n={3} title="Advisory locks" level="medium">

Replace `SELECT ... FOR UPDATE` on the accounts row with `pg_advisory_xact_lock(hashtext($1))`. What changes, and what could go wrong?

<Solution>

Advisory locks lock a number, not a row, so they need no row to exist and don't block anything else that reads or updates the accounts table. The transaction-scoped form releases at commit or rollback, like a row lock. What can go wrong: two different merchants' names can hash to the same number and share a lock (harmless but slower), and every code path must remember to take the lock, because Postgres attaches it to nothing.

</Solution>

</Exercise>

<Exercise n={4} title="Crash between send and settle" level="medium">

Make the saga worker exit right after the bank returns 200 and before `finish` commits, for one payout. Show that `Recover` settles it without paying twice.

<Solution>

The payout stays `reserved` with its money in payouts-pending. `Recover` resends with the same id; the bank has it already and answers 200 without paying again; `finish` settles it. Bank total and ledger agree. If the bank didn't deduplicate by id, this recovery would pay the merchant twice, which is why idempotency is part of the saga's design and not an optimisation.

</Solution>

</Exercise>

<Exercise n={5} title="A payout stuck for a day" level="hard">

A payout has been `reserved` for 24 hours: every send has returned 503. Design what should happen, and implement the query that finds such payouts.

<Solution>

`SELECT id, merchant, amount, updated_at FROM payouts WHERE state = 'reserved' AND updated_at < now() - interval '24 hours'`. Don't compensate on age alone: the bank may execute a queued request later. Ask the bank for the transfer's status with the id (`GET /transfers/{id}`, which this bank provides); if it says it has no such transfer, and its API guarantees it won't execute one later (for example, by cancelling it by id first), compensate. Otherwise alert a human: a payout in doubt for a day is an operations problem, and the ledger's pending account shows exactly how much money is in that state.

</Solution>

</Exercise>

<Recap>

- **Atomicity**: one database transaction per transfer; ten SIGKILLed runs kept every cent. A: all or nothing; C: constraints hold; I: stop 2; D: committed means on disk.
- **Isolation**: Read Committed (per statement), Repeatable Read (one snapshot; aborts conflicting row updates with 40001), Serializable (as if one at a time; aborts dangerous patterns, retry needed). Read-modify-write lost 6,856 of 8,000 updates at Read Committed; `balance = balance + x` lost none. Write skew (no shared row) paid $500 from $100 at Read Committed and Repeatable Read.
- **Pessimistic**: `SELECT ... FOR UPDATE` on the merchant's row: $100 exactly, 0 retries, 16 ms per round. Keep the locked section short.
- **Optimistic**: a version checked at commit: $100 exactly with 1,173 retries under heavy contention; best when conflicts are rare or locks can't be held. Serializable + retry: 863 retries.
