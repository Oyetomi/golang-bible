<HeroCard label="Part 3 · Chapter 5" title="Messaging & Pub/Sub Foundations">

Chapter 4 put Meridian's `payment.succeeded` events on a Redis stream and consumed them once, however often they were delivered. That was one broker, used one way. This chapter steps back to the ideas every messaging system is built from, whatever it's called: Redis, RabbitMQ, NATS, SQS, Kafka (chapter 7). Each idea is a choice with a cost, and each is measured here on real Redis from Go.

The questions are the same everywhere. Is a message **kept** if nobody is listening? Does each message go to **one** worker or to **every** interested service? What happens when a consumer is **slower** than the producer? How does the broker know a message was **handled**, and what happens when the handler dies? What **order** do messages arrive in? And what do you do with a message that can **never** be handled?

Six stops. If you get lost, come back here:

1. **Kept or not.** Pub/Sub delivers to whoever is listening; a stream stores.
2. **Queues and topics.** One worker per message, or every service gets every message.
3. **Slow consumers.** Push until something breaks, or pull at your own pace.
4. **Acknowledgements.** How the broker knows a message was handled, and what a crash leaves behind.
5. **Ordering.** Where order holds, and how parallel consumers lose it.
6. **Poison messages.** The message that fails forever, and the dead-letter queue.

## Kept or Not

*Stop 1 of 6.*

### Step 1: two kinds of delivery

A **message broker** sits between the services that produce events and the ones that consume them, so neither has to know about, or wait for, the other. Brokers differ first in one decision: does a message exist only while it's being delivered, or is it **stored** until consumers have it?

**Redis Pub/Sub** is the first kind. `PUBLISH` hands the message to every connection subscribed to the channel at that moment, and forgets it. **Redis streams** are the second kind: `XADD` appends the message to a log that stays in Redis; readers ask for everything after the last id they've seen, whenever they're ready. (Kafka, SQS, RabbitMQ's queues and NATS JetStream all store; plain NATS and Redis Pub/Sub don't.)

### Step 2: a subscriber that goes away

```go noverify
// offline: Meridian publishes 3,000 payment events over 3 seconds. The
// receipts service is disconnected from 1 s to 2 s. Once with Redis
// Pub/Sub, once with a Redis stream.
package main

import (
	"context"
	"fmt"
	"log"
	"time"

	"github.com/redis/go-redis/v9"
)

var ctx = context.Background()

func main() {
	rdb := redis.NewClient(&redis.Options{Addr: "127.0.0.1:6395"})
	rdb.Del(ctx, "offline:stream")

	// Pub/Sub: a message goes to whoever is subscribed at that moment.
	got := 0
	sub := rdb.Subscribe(ctx, "offline:pubsub")
	sub.Receive(ctx) // wait for the subscription to be confirmed
	stop := make(chan struct{})
	go func() {
		ch := sub.Channel()
		for {
			select {
			case <-ch:
				got++
			case <-stop:
				return
			}
		}
	}()
	publish(func(i int) { rdb.Publish(ctx, "offline:pubsub", i) }, func() {
		close(stop)
		sub.Close() // the receipts service restarts...
	}, func() {
		sub = rdb.Subscribe(ctx, "offline:pubsub") // ...and comes back
		sub.Receive(ctx)
		stop = make(chan struct{})
		go func() {
			for range sub.Channel() {
				got++
			}
		}()
	})
	time.Sleep(200 * time.Millisecond)
	fmt.Printf("pub/sub: published 3000, subscriber received %d\n", got)

	// A stream: messages are stored; a reader asks for everything after the
	// last id it saw, so being away costs time, not messages.
	publish(func(i int) {
		rdb.XAdd(ctx, &redis.XAddArgs{Stream: "offline:stream", Values: map[string]any{"n": i}})
	}, func() {}, func() {})
	last, n := "0", 0
	for {
		res, err := rdb.XRead(ctx, &redis.XReadArgs{Streams: []string{"offline:stream", last}, Count: 1000, Block: 100 * time.Millisecond}).Result()
		if err == redis.Nil {
			break
		}
		if err != nil {
			log.Fatal(err)
		}
		for _, m := range res[0].Messages {
			last = m.ID
			n++
		}
	}
	fmt.Printf("stream:  published 3000; a reader that started only after all of them were sent received %d\n", n)
}

// publish sends 3,000 messages, one per millisecond, calling down at 1 s
// and up at 2 s.
func publish(send func(int), down, up func()) {
	for i := range 3000 {
		switch i {
		case 1000:
			down()
		case 2000:
			up()
		}
		send(i)
		time.Sleep(time.Millisecond)
	}
}
```

```text
pub/sub: published 3000, subscriber received 2000
stream:  published 3000; a reader that started only after all of them were sent received 3000
```

With Pub/Sub, the 1,000 events published during the one-second restart **were delivered to nobody**, and no error told the publisher. With the stream, a reader that only started after all 3,000 had been sent still got all 3,000. Being away cost it time, not messages. For payments, where a missed event means a missing receipt or an unreconciled dashboard, only the second kind will do. Pub/Sub fits messages whose value expires in a moment: a live price ticker, a cache-invalidation hint that a missed one only makes slightly stale.

## Queues & Topics

*Stop 2 of 6.*

### Step 1: two ways to share the messages

The second decision is **who gets each message**:

- A **queue**: each message goes to **one** of the consumers. Adding consumers shares the work. (Three receipts workers, each sending a third of the receipts.)
- A **topic** (publish/subscribe): each message goes to **every** subscribing service. Adding a service adds a new, complete copy of the flow. (Receipts and fraud both need every payment.)

Real systems need both at once, and brokers combine them. On a Redis stream, a **consumer group** is a queue: its members share the stream's entries, each entry to one member. Several groups on the same stream are a topic: each group independently gets every entry. Kafka's consumer groups work the same way.

### Step 2: measured

3,000 events; group `receipts` with three consumers, group `fraud` with one:

```go noverify

	} {
		wg.Go(func() {
			for {
				res, err := rdb.XReadGroup(ctx, &redis.XReadGroupArgs{
					Group: c.group, Consumer: c.name, Streams: []string{"groups:payments", ">"}, Count: 10, Block: 200 * time.Millisecond,
				}).Result()
				if err == redis.Nil {
					return
				}

				}
				for _, m := range res[0].Messages {

			}
		})
	}
	wg.Wait()
```

## Slow Consumers

*Stop 3 of 6.*

### Step 1: push and pull

Pub/Sub **pushes**: Redis writes each message into the subscriber's connection as it's published, whether or not the subscriber is ready. A stream consumer **pulls**: it asks for the next batch when it has finished the last. The difference only shows when the consumer is slower than the producer, which, in production, it eventually is: a GC pause, a slow database, a deploy.

### Step 2: a stalled consumer

100,000 events of 1 KB, published as fast as Redis accepts them, to a consumer that stalls for 3 seconds before reading:

```text
pub/sub: published 100000; the stalled subscriber received 8033; Redis disconnected it 1 time(s) for exceeding its output buffer limit
stream:  published 100000; after the stall the group's lag is 100000 events (99 MB in Redis), none lost
         then it caught up: 100000 processed
```

**Pub/Sub**: the messages piled up in Redis's output buffer for that connection. Redis protects itself with a limit (by default, a pub/sub client is disconnected when its buffer passes 32 MB, or stays above 8 MB for 60 s), so it **cut the subscriber off**. go-redis reconnected and resubscribed, but everything in between was gone: the subscriber received 8,033 of 100,000. The publisher never slowed down and never knew.

**Stream**: nothing was pushed, so nothing piled up in a connection. The backlog waited in the stream (99 MB of Redis memory) and was visible as the group's **lag**, 100,000 events. When the consumer came back, it caught up: 100,000 processed. The cost moved to where you can see and manage it: memory in the broker, and a lag metric to alert on. (A stream can be capped, `XADD ... MAXLEN`, which trades old unread events for bounded memory: a decision, not an accident.)

Holding back a fast producer so a slow consumer isn't overwhelmed is **back-pressure**. Pull-based consumers apply it naturally (they don't ask for more than they can handle); push-based systems have to add it (credit windows, prefetch limits) or drop messages, as Pub/Sub did.

## Acknowledgements

*Stop 4 of 6.*

### Step 1: read is not done

A consumer that reads a message might die before handling it. So storing brokers separate **delivering** a message from **finishing** it: the consumer **acknowledges** a message when it's done. In a Redis consumer group, `XREADGROUP` moves entries into the group's **pending entries list** under that consumer's name; `XACK` removes them. Anything still pending belongs to a consumer that hasn't finished it, and if that consumer is gone, another can take it over with `XAUTOCLAIM`.

### Step 2: kill a consumer mid-batch

The receipts worker reads 50 events, sends each receipt, and acknowledges the batch when all 50 are done:

```go noverify
// main.go, lines 27–66
	process := func(msgs []redis.XMessage) {
		ids := make([]string, 0, len(msgs))
		for _, m := range msgs {
			time.Sleep(2 * time.Millisecond) // send the receipt
			rdb.HIncrBy(ctx, "crash:receipts", m.Values["n"].(string), 1)
			ids = append(ids, m.ID)
		}
		rdb.XAck(ctx, stream, group, ids...) // acknowledge the batch
	}

	if *claim {
		start := "0-0"
		claimed := 0
		for {
			msgs, next, err := rdb.XAutoClaim(ctx, &redis.XAutoClaimArgs{
				Stream: stream, Group: group, Consumer: *name, MinIdle: 100 * time.Millisecond, Start: start, Count: 100,
			}).Result()
			if err != nil {
				log.Fatal(err)
			}
			claimed += len(msgs)
			process(msgs)
			if next == "0-0" {
				break
			}
			start = next
		}
		fmt.Printf("%s claimed %d events that another consumer read but never acknowledged\n", *name, claimed)
	}
	for {
		res, err := rdb.XReadGroup(ctx, &redis.XReadGroupArgs{Group: group, Consumer: *name, Streams: []string{stream, ">"}, Count: 50, Block: 300 * time.Millisecond}).Result()
		if err == redis.Nil {
			return
		}
		if err != nil {
			log.Fatal(err)
		}
		process(res[0].Messages)
	}
}
```

A script publishes 1,000 events, starts worker `c1`, kills it with `SIGKILL` after one second, and starts `c2`, which first claims anything left pending. Three runs:

```text

c1 SIGKILLed after 1 s

-- run 2
published 1000 events
c1 SIGKILLed after 1 s
pending (read, not acknowledged): 50

receipts sent: 1000 of 1000 events got at least one; 23 got two; 0 still pending
-- run 3
published 1000 events
c1 SIGKILLed after 1 s

receipts sent: 1000 of 1000 events got at least one; 2 got two; 0 still pending
```

Every time: `c1` died with 50 events pending, `c2` claimed exactly those 50, and **all 1,000 events got a receipt**, none lost. But in each run some events got **two** (18, 23 and 2): `c1` had already sent their receipts when it died, just not acknowledged them yet. Redelivery can't know how far a dead consumer got. This is at-least-once delivery from the consuming side, and it's why chapter 4's inbox exists.

Acknowledging **before** doing the work turns this around: no duplicates, but every event read and not yet handled at the moment of the crash is lost, with nothing pending to recover. For payments, acknowledge after, and make the handler idempotent.

## Ordering

*Stop 5 of 6.*

### Step 1: where order holds

A Redis stream has one total order: entries are read in the order they were appended. But order in the log isn't order of processing. Once several consumers share the work, event 5 can go to a fast worker and event 4 to a slow one, and 5 finishes first. For many events that doesn't matter. For a merchant's own sequence (a payment, then its refund, then a payout) applying the refund before the payment can break the merchant's balance or a state machine.

### Step 2: measured

20 merchants, 100 events each in order, interleaved at random in the stream (as a busy system would produce them); four consumers whose work takes a variable 0 to 2 ms. The program counts events applied after a later event of the same merchant:

```go noverify

							outOfOrder++
						} else {
							last[merchant] = seq
						}
						mu.Unlock()
						rdb.XAck(ctx, stream, "apply", m.ID)
					}
				}
			})
		}
```

```text
one stream, 4 competing consumers          50 of 2000 events applied after a later event of the same merchant
4 streams by merchant, 1 consumer each      0 of 2000 events applied after a later event of the same merchant
```

With four competing consumers on one stream: **50 of 2,000** events applied out of order for their merchant. Partitioned, **0**: four streams, each merchant always hashed to the same one, and one consumer per stream:

```go noverify
// main.go, lines 43–50
			merchant := fmt.Sprintf("m%02d", m)
			s := streams[0]
			if partitioned { // the same merchant always goes to the same stream
				h := fnv.New32a()
				h.Write([]byte(merchant))
				s = streams[h.Sum32()%4]
			}
			rdb.XAdd(ctx, &redis.XAddArgs{Stream: s, Values: map[string]any{"merchant": merchant, "seq": next[m]}})
```

That's the general rule, and Kafka is built around it (chapter 7): **order is kept only within a partition, so choose the partition key by what must stay in order**. Here, the merchant. Different merchants still run in parallel; one merchant's events can't overtake each other. The price is that a partition's events are handled one at a time, so one very busy merchant can't be spread over several consumers.

## Poison Messages

*Stop 6 of 6.*

### Step 1: the event that always fails

Some messages can never be handled: a malformed field, a merchant id that doesn't exist, a bug that one input triggers. With acknowledge-after-work (stop 4), a failure means no acknowledgement, and the message comes back. And back. A **poison message** is retried forever, wasting work, filling logs, and in brokers that deliver strictly in order (a Kafka partition), blocking everything behind it.

### Step 2: count the deliveries, then park it

Redis records how many times each pending entry has been delivered (`XPENDING` shows it). The consumer retries anything unacknowledged every 200 ms; with a **dead-letter** policy, once an entry has been delivered 5 times, it's copied to a separate stream with the error and acknowledged:

```go noverify
// main.go, lines 49–71
			// Then retry anything unacknowledged for 200 ms.
			time.Sleep(200 * time.Millisecond)
			msgs, _, err := rdb.XAutoClaim(ctx, &redis.XAutoClaimArgs{Stream: "poison:payments", Group: "receipts", Consumer: "r1", MinIdle: 200 * time.Millisecond, Start: "0-0", Count: 100}).Result()
			if err != nil {
				log.Fatal(err)
			}
			for _, m := range msgs {
				if handle(m) == nil {
					rdb.XAck(ctx, "poison:payments", "receipts", m.ID)
					continue
				}
				if !dlq {
					continue
				}
				// How many times has Redis delivered it?
				p, _ := rdb.XPendingExt(ctx, &redis.XPendingExtArgs{Stream: "poison:payments", Group: "receipts", Start: m.ID, End: m.ID, Count: 1}).Result()
				if len(p) == 1 && p[0].RetryCount >= 5 {
					rdb.XAdd(ctx, &redis.XAddArgs{Stream: "poison:payments:dlq", Values: map[string]any{
						"n": m.Values["n"], "original_id": m.ID, "error": "malformed merchant id", "deliveries": p[0].RetryCount}})
					rdb.XAck(ctx, "poison:payments", "receipts", m.ID)
				}
			}
		}
```

```text
no dead-letter stream           99 receipts sent; event 37 attempted 18 times in 5 s; 1 still pending; 0 in the dead-letter stream
dead-letter after 5 deliveries  99 receipts sent; event 37 attempted 5 times in 5 s; 0 still pending; 1 in the dead-letter stream
```

Without it, event 37 was attempted **18 times in 5 seconds** and was still pending when the run ended; it would go on forever. With it, after **5** attempts it was parked in `poison:payments:dlq`, with its original id and the error, and nothing is pending. The other 99 receipts were sent either way. The dead-letter stream is where a human (or a fixed deployment) looks: fix the cause, then replay the parked events.

## Exercises

These use the `msg` module and the Redis instance from this chapter.

<Exercise n={1} title="Cap the stream" level="easy">

Add `MaxLen: 10_000, Approx: true` to the stall experiment's `XAdd`. What does the stream hold after the stall, and what did the consumer miss?

<Solution>

The stream keeps only about the newest 10,000 entries (approximate trimming works in whole internal nodes, so slightly more). The consumer group's lag counts entries it can no longer read: they were trimmed before it got to them, so it loses the oldest ~90,000 events. A cap bounds memory, and in exchange a consumer that falls far enough behind loses data: size it by how long a consumer may be down, and alert on lag well before it.

</Solution>

</Exercise>

<Exercise n={2} title="Pending, by consumer" level="easy">

After killing `c1`, run `XPENDING crash:payments receipts - + 10` before starting `c2`. What does each row tell you?

<Solution>

Each row is one pending entry: its id, the consumer that holds it (`c1`), the milliseconds since it was last delivered, and the delivery count (1). That's everything `XAUTOCLAIM` needs to decide what to take over (idle time) and everything stop 6 needs to detect a poison message (delivery count).

</Solution>

</Exercise>

<Exercise n={3} title="Ack before" level="medium">

Change `consume` to acknowledge each batch as soon as it's read, before sending receipts, and rerun the crash script. Count receipts.

<Solution>

`XPENDING` shows 0 after the kill, `c2` claims nothing, and the events `c1` had read but not yet handled (up to a batch of 50) never get a receipt; nothing is sent twice. That's at-most-once. Only choose it where losing a message is cheaper than handling it twice, which for payments is never.

</Solution>

</Exercise>

<Exercise n={4} title="A hot merchant" level="medium">

In the ordering experiment, make one merchant produce half of all events. What happens to throughput with four partitions, and why?

<Solution>

That merchant's events all go to one partition, handled by one consumer, one at a time, so its partition's backlog grows while the other three consumers go idle. Total throughput approaches that of a single consumer. Partitioning keeps order by serialising a key; a key that carries most of the traffic serialises most of the work. Options: a finer key if the order that matters is finer (per merchant and account, say), or accept a separate, faster path for that merchant.

</Solution>

</Exercise>

<Exercise n={5} title="Replay the dead letters" level="hard">

Write `cmd/replay`: it reads `poison:payments:dlq`, lets you fix an event (here, correct its merchant id), and publishes it back to `poison:payments` so the receipts group handles it. What must the replayed event keep, and why?

<Solution>

It must keep its original `event_id` (and the idempotency it carries), so a consumer that had in fact handled it before (a partial success, a timed-out acknowledgement) recognises it in its inbox and doesn't send a second receipt. Record the replay in the dead-letter entry (who, when, what was changed) so the audit trail explains why a payment's receipt arrived hours later, and delete or mark the dead letter only after the replayed event is acknowledged.

</Solution>

</Exercise>

<Recap>

- **Kept or not**: Pub/Sub delivers to current subscribers and stores nothing (a 1 s restart lost 1,000 of 3,000 events); a stream stores and lets readers catch up (3,000 of 3,000).
- **Queues and topics**: within a consumer group each event goes to one member (receipts split 1,000/1,000/1,000); each group gets every event (fraud got 3,000). Queues share work; topics share events.
- **Slow consumers**: push fills the connection until Redis disconnects it (8,033 of 100,000 received after a 3 s stall); pull leaves a visible backlog (lag 100,000, 99 MB) that the consumer drains. Back-pressure is built into pulling.
- **Acknowledgements**: ack after the work; a crash leaves events pending for another consumer to claim (50 claimed, none lost, 2 to 23 receipts sent twice). Ack before means losses instead of duplicates.
- **Ordering**: one stream has one order, but competing consumers reorder (50 of 2,000 merchant events); partitioning by merchant with one consumer per partition kept all 2,000 in order.
- **Poison messages**: count deliveries and park the message in a dead-letter stream (5 attempts, then parked) instead of retrying forever (18 attempts in 5 s and counting).

</Recap>
