<HeroCard label="Part 3 · Chapter 14" title="Resilience & Correctness Under Load">

Any service can be correct when nothing is wrong. The test is what it does at 2 a.m. when one instance is dead, the fraud service is timing out, one account is being hammered by a bot, and the books are twelve cents out. A payments service has two goals that pull apart under stress: **stay up**, and **stay right**. When they conflict, right wins. A slow payment is an inconvenience; a wrong ledger is a loss.

This chapter builds Meridian's payment path as a small Go service over PostgreSQL 14, then breaks it on purpose, six ways, and measures what each failure costs and what each defence buys. The ledger from chapter 2 is the model for the money: every payment is two entries that sum to zero, and one query can check the whole thing.

Six stops. If you get lost, come back here:

1. **Staying up.** Two instances behind a balancer, one killed, and the three things that fix the errors.
2. **One noisy account.** A bot, and why the rate limit has to be per account.
3. **A dependency that lies.** The fraud service slow and down: timeouts, a circuit breaker, and fail open vs fail closed.
4. **Degrading on purpose.** Accept small payments, hold big ones, release them when fraud is back.
5. **Checking the books.** Reconciliation against the bank's file, and corrections that book once.
6. **Proving it stays right.** Invariants after concurrent duplicates and after SIGKILL.

</HeroCard>

## Staying Up

*Stop 1 of 6.*

### Step 1: the service

Everything here runs on one Apple M1 with PostgreSQL 14.19 and Go 1.27, from one module, `resil`, using `pgx` v5.11.0 and `golang.org/x/time`. Three tables: `accounts`, `payments` (one row per payment, keyed by the caller's **idempotency key**) and `entries` (two rows per payment that sum to zero). A payment is one transaction:

```go noverify
// pay.go, lines 21–52
// Pay records a payment as two entries that sum to zero. The key makes it idempotent:
// a repeat returns the stored status instead of moving money twice.
func (s *Store) Pay(ctx context.Context, r PayReq, status string) (string, error) {
	tx, err := s.Pool.Begin(ctx)
	if err != nil {
		return "", err
	}
	defer tx.Rollback(ctx)
	_, err = tx.Exec(ctx,
		`INSERT INTO payments (key, from_acct, to_acct, amount, status) VALUES ($1,$2,$3,$4,$5)`,
		r.Key, r.From, r.To, r.Amount, status)
	var pg *pgconn.PgError
	if errors.As(err, &pg) && pg.Code == "23505" { // duplicate key: seen before
		tx.Rollback(ctx)
		var prev string
		if err := s.Pool.QueryRow(ctx, `SELECT status FROM payments WHERE key=$1`, r.Key).Scan(&prev); err != nil {
			return "", err
		}
		return prev, nil
	}
	if err != nil {
		return "", err
	}
	if status == "posted" {
		if _, err := tx.Exec(ctx,
			`INSERT INTO entries (payment_key, account_id, amount) VALUES ($1,$2,$3),($1,$4,$5)`,
			r.Key, r.From, -r.Amount, r.To, r.Amount); err != nil {
			return "", err
		}
	}
	return status, tx.Commit(ctx)
}
```

Read the shape, not the details. The `INSERT` into `payments` fails with a duplicate-key error when the key was seen before, and then the function returns the *stored* status instead of paying again. That one behaviour is what makes every retry in this chapter safe.

`cmd/payd` wraps `Pay` in an HTTP handler and `cmd/load` sends payments to it: forty **normal** clients, each on its own account at 20 requests a second, and optionally a **bot** hammering one account. `run_all.sh` reproduces every number below. One caveat about the numbers: the machine was shared with another CPU-heavy job while I measured, so **counts** (errors, status codes, rows stored) are exact and repeatable, and **latencies** are only good for comparing runs against each other.

- **No health check, no retry:** 2,141 requests failed (34%). The rest of the pool was fine; the balancer kept sending traffic to the corpse.
- **Health check only:** 84 failed: the requests in flight when A died, plus those during the ≤200 ms before the probe noticed.
- **Health check + retry:** 0 failed. The retry covers the detection window.
- **Retry only:** 0 failed too, but half of every request's first attempts still go to the dead instance and get retried, so every request pays for a wasted attempt. Fine for a short outage, wrong as a plan.

Look at the second line under each run: `payments stored`. Without a health check, 4,177 payments were stored but only 4,174 requests got a 200. **Three payments committed and their callers were told 502.** The instance died after the commit and before the answer. That is why the retry is only safe with idempotency keys: a client that retries one of those three, with the same key, gets the stored result and pays once. Without keys, the retry would pay twice.

<Gotcha>
**Retries are only as safe as the operation is idempotent.** A retry on a payment with no key moves the money again whenever the first attempt actually committed. Put the key in the request, store it with the payment under a unique constraint, and return the stored result on a duplicate. Then retry as much as you like.
</Gotcha>

### Step 3: what a balancer can't fix

Both instances share one PostgreSQL. Killing an instance is survivable because instances are stateless; killing the database is not, and a health check on the instances says nothing about it. Database failover (a replica promoted to primary, and the window in which writes can be lost or duplicated) is its own subject, covered in Part 2's [replication chapter](/part-2/replication). What this chapter's service does about it is what it did above: keep every write idempotent, so the retry after a failover does not double-pay.

## One Noisy Account

*Stop 2 of 6.*

### Step 1: a bot

One account starts sending payments in a tight loop: a bug, a bot, a customer's script gone wrong. `run_ratelimit.sh` runs 100 bot workers on account 7 next to the forty normal clients, against four configurations of the service (a pool of 4 database connections):

```text
== bot, no limit
normal: n=4800   p50=12.7ms   p99=26.6ms   codes=map[200:4800]
bot:    n=49712  p50=11.2ms   p99=27ms     codes=map[200:49712]
== global limit 200/s burst 50
normal: n=4800   p50=1.3ms    p99=27.7ms   codes=map[200:48 429:4752]
bot:    n=287695 p50=800µs    p99=11.4ms   codes=map[200:1199 429:286496]
== per-account 30/s burst 5
normal: n=4760   p50=4.4ms    p99=35.9ms   codes=map[200:4760]
bot:    n=267314 p50=800µs    p99=14ms     codes=map[200:184 429:267130]
```

Three lessons, in the order of the three runs:

1. **No limit:** the bot posted **49,712 payments from one account in six seconds**, about 8,300 a second, and every one was accepted. The honest clients got through, but only because this database is fast enough; each bot payment was still a transaction and two ledger rows.
2. **A global limit** (one shared bucket of 200 a second) protects the database and starves everybody: the bot uses the whole budget, and the normal clients got 48 payments out of 4,800, **1%**. A shared limit lets the loudest caller decide who gets served.
3. **A per-account limit** (30 a second, burst 5) gives every account its own bucket. All 4,760 honest requests succeeded, and the bot got 184 payments through, which is exactly what its bucket allows: 30 × 6 s + a burst of 5. The other 267,130 were rejected with a 429 in under a millisecond, cheaper than serving them.

### Step 2: the limiter

```go noverify
// limiter.go, lines 28–38
func (p *PerAccount) Allow(acct int) bool {
	p.mu.Lock()
	e, ok := p.buckets[acct]
	if !ok {
		e = &entry{l: rate.NewLimiter(p.limit, p.burst)}
		p.buckets[acct] = e
	}
	e.last = time.Now()
	p.mu.Unlock()
	return e.l.Allow()
}
```

It is a map from account to a `golang.org/x/time/rate` limiter, made on first use. `rate.Limiter.Allow` is the token bucket: it holds up to `burst` tokens, refills at `limit` per second, and each call takes one or says no. The mutex protects the *map*; the limiter inside is already safe for concurrent use, so the lock is released before `e.l.Allow()`.

### Step 3: the map that grows forever

Each account seen gets a bucket, and nothing removes it. With a million distinct accounts, that is a million buckets. `TestLimiterMemory` measures it, then sweeps buckets idle for more than 10 ms:

```text
1,000,000 accounts seen: 1000000 buckets, 150 MB of heap (150 bytes per bucket)
Sweep(10ms) removed 1000000; 0 buckets left; heap back to 38 MB above baseline
```

150 MB for a million accounts, so a limiter without a sweep is a slow memory leak that grows with your customer count (and with an attacker who makes up account ids). The sweep removes the entries, but note the second line: the heap stays 38 MB above where it started, because a Go map keeps its bucket array after deletes. If churn is large and permanent, rebuild the map into a fresh one during the sweep, as Part 1's data-semantics chapter showed for maps in general. In production, use a fixed-size cache with eviction, or key the limiter by account *and* expire entries.

## A Dependency That Lies

*Stop 3 of 6.*

### Step 1: the fraud hook

Before a payment posts, Meridian asks a separate **fraud service** whether it looks legitimate. That call is the riskiest line in the handler, because it is a network call to somebody else's process on the critical path of every payment. `cmd/fraudsim` is a stand-in whose behaviour can be changed while it runs: healthy, slow (2 s per call), or returning 503.

The client wraps every call in a deadline, and a `Screen` function decides what to do with the answer, or the lack of one:

```go noverify
// fraud.go, lines 101–105
// Screen combines the breaker, the call and the policy into one decision.
// held=true means "accept now, review later".
func Screen(ctx context.Context, f interface {
	Check(context.Context, PayReq) (Verdict, error)
}, b *Breaker, pol Policy, smallLimit int64, r PayReq) (allow, held bool, reason string) {
```

A verdict, when there is one, is taken as given. When there is not (a timeout, a 503, an open breaker) the **policy** decides: `FailClosed` declines the payment, `FailOpen` allows it, `FailDegrade` allows small payments and holds large ones for review. That is a business decision the code has to make explicitly, because "we didn't hear back" is not a verdict.

### Step 2: a slow dependency is worse than a dead one

First the slow case. The fraud service takes 2 s per call and the client's deadline is 300 ms, with a fail-closed policy. Forty clients each wait for their answer before sending the next payment:

```text
== slow (2s), fail-closed, no breaker
normal: n=800    p50=305.8ms  p99=333.7ms  codes=map[402:800]
== slow (2s), fail-closed, breaker
normal: n=4590   p50=3.3ms    p99=29.8ms   codes=map[402:4590]
```

Without a breaker every payment waits the full timeout and is then declined: p50 306 ms, and in six seconds the forty clients could only complete **800** payments, because each spent 300 ms per attempt waiting for a service that was never going to answer. With a breaker the same outage is answered in 3 ms, and 4,590 attempts got through the door (all declined, because the policy is fail-closed, but declined *fast*, with the service free to serve other work).

```go noverify
// fraud.go, lines 54–92
type Breaker struct {
	mu        sync.Mutex
	fails     int
	threshold int
	cooldown  time.Duration
	openedAt  time.Time
	open      bool
}

func NewBreaker(threshold int, cooldown time.Duration) *Breaker {
	return &Breaker{threshold: threshold, cooldown: cooldown}
}

func (b *Breaker) Allow() bool {
	b.mu.Lock()
	defer b.mu.Unlock()
	if !b.open {
		return true
	}
	if time.Since(b.openedAt) >= b.cooldown { // half-open: let one probe through
		b.openedAt = time.Now()
		return true
	}
	return false
}

func (b *Breaker) Report(err error) {
	b.mu.Lock()
	defer b.mu.Unlock()
	if err == nil {
		b.fails, b.open = 0, false
		return
	}
	b.fails++
	if b.fails >= b.threshold {
		b.open, b.openedAt = true, time.Now()
	}
}

```

The breaker is a little state and two methods. `Report` counts consecutive failures and opens at the threshold (5); `Allow` lets calls through when closed, and once per cooldown when open (the half-open probe). `Screen` asks `Allow` before every call and reports every result back.

### Step 3: when the service is down, what do we say?

Now the 503 case, with each policy. (Each run posts ten percent large payments, 50,000, to make degrade visible.)

```text
== down (503), fail-closed
normal: n=4800   p50=1.5ms    p99=22.3ms   codes=map[402:4800]
== down (503), fail-open
normal: n=4501   p50=6.5ms    p99=118.6ms  codes=map[200:4501]
stored: posted 4501
== down (503), degrade: small allowed, big held
normal: n=4800   p50=6.2ms    p99=22.1ms   codes=map[200:4800]
stored: held 521  stored: posted 4279
```

- **Fail closed:** every payment was declined, 4,800 of 4,800. The ledger is perfectly safe and the business is closed. Right for a bank moving large sums, ruinous for a checkout page.
- **Fail open:** every payment posted, with **no fraud check at all**: 4,501 unscreened. That is what an attacker waits for; a fraud control that can be switched off by making it fail is not a control.
- **Degrade:** the next stop.

<Recap>

- Every dependency call needs a deadline. A 2 s fraud service with a 300 ms deadline still cost every payment 306 ms and cut throughput to 800 payments in six seconds; a breaker made the same outage a 3 ms decline.

- When the dependency gives no answer the code must choose: closed declined 4,800 of 4,800, open posted 4,501 with no screening at all.

</Recap>

## Degrading on Purpose

*Stop 4 of 6.*

### Step 1: correctness first, availability second

When the fraud service is down there are three honest answers: stop (closed), ignore the risk (open), or **serve what is safe and set the rest aside**. The last is the CAP-style choice for money: keep answering, but never claim more than you know. `FailDegrade` allows payments up to a small limit and *holds* the rest. A held payment is recorded with status `held` and **no ledger entries**, so it moves no money.

```go noverify
// pay.go, lines 70–114
// ReleaseHeld re-screens payments that were held while fraud was down. Approved ones are posted:
// the status change and the two entries commit together, and a payment can be released only once.
func (s *Store) ReleaseHeld(ctx context.Context, check func(context.Context, PayReq) (Verdict, error)) (released, stillHeld int, err error) {
	rows, err := s.Pool.Query(ctx, `SELECT key, from_acct, to_acct, amount FROM payments WHERE status='held' ORDER BY created_at`)
	if err != nil {
		return 0, 0, err
	}
	var held []PayReq
	for rows.Next() {
		var r PayReq
		if err := rows.Scan(&r.Key, &r.From, &r.To, &r.Amount); err != nil {
			rows.Close()
			return 0, 0, err
		}
		held = append(held, r)
	}
	rows.Close()
	for _, r := range held {
		v, cerr := check(ctx, r)
		if cerr != nil || !v.Allow {
			stillHeld++
			continue
		}
		tx, err := s.Pool.Begin(ctx)
		if err != nil {
			return released, stillHeld, err
		}
		tag, err := tx.Exec(ctx, `UPDATE payments SET status='posted' WHERE key=$1 AND status='held'`, r.Key)
		if err == nil && tag.RowsAffected() == 1 {
			_, err = tx.Exec(ctx, `INSERT INTO entries (payment_key, account_id, amount) VALUES ($1,$2,$3),($1,$4,$5)`,
				r.Key, r.From, -r.Amount, r.To, r.Amount)
		}
		if err != nil {
			tx.Rollback(ctx)
			return released, stillHeld, err
		}
		if err := tx.Commit(ctx); err != nil {
			return released, stillHeld, err
		}
		if tag.RowsAffected() == 1 {
			released++
		}
	}
	return released, stillHeld, nil
}
```

## Checking the Books

*Stop 5 of 6.*

### Step 1: trust, then verify

Everything so far protects the ledger *inside* your process. But the ledger's amounts also live in someone else's system: the bank's statement, the card network's settlement file. **Reconciliation** compares the two. A nightly job that finds a twelve-cent difference is the reason a payments company can say its numbers are right.

`Reconcile` compares posted payments with the statement, by key, and returns every difference:

```go noverify
// recon.go, lines 24–65
// Reconcile compares posted payments with the statement and returns every difference.
func (s *Store) Reconcile(ctx context.Context, statement []Line) ([]Finding, error) {
	// A payment's effective amount is what was booked plus any corrections that point at it.
	rows, err := s.Pool.Query(ctx, `
		SELECT p.key, p.amount + COALESCE((SELECT sum(CASE WHEN c.to_acct = $1 THEN -c.amount ELSE c.amount END)
		                                     FROM payments c WHERE c.ref = p.key AND c.status = 'posted'), 0)
		  FROM payments p WHERE p.status = 'posted' AND p.ref IS NULL`, Suspense)
	if err != nil {
		return nil, err
	}
	defer rows.Close()
	ledger := map[string]int64{}
	for rows.Next() {
		var k string
		var a int64
		if err := rows.Scan(&k, &a); err != nil {
			return nil, err
		}
		ledger[k] = a
	}
	bank := map[string]int64{}
	for _, l := range statement {
		bank[l.Key] = l.Amount
	}
	var out []Finding
	for k, a := range ledger {
		b, ok := bank[k]
		switch {
		case !ok:
			out = append(out, Finding{k, "missing_in_statement", a, 0})
		case a != b:
			out = append(out, Finding{k, "amount_mismatch", a, b})
		}
	}
	for k, b := range bank {
		if _, ok := ledger[k]; !ok {
			out = append(out, Finding{k, "missing_in_ledger", 0, b})
		}
	}
	sort.Slice(out, func(i, j int) bool { return out[i].Key < out[j].Key })
	return out, rows.Err()
}
```

`TestReconcile` books 1,000 payments, builds a statement from them, and then damages it three ways: the bank moved 12 cents more than we booked on `p0041`, has no line for `p0100`, and has a payment `p9999` we never saw:

```text

finding: missing_in_statement   p0100 ledger=1100 bank=0
finding: missing_in_ledger      p9999 ledger=0 bank=4242
```

Three different failures, three different owners: an amount mismatch is arithmetic (fix by correction), a payment the bank never saw may have failed to settle, and a payment we never saw is the scariest of the three. Only the first is safe to fix automatically. The other two go to a human.

### Step 2: corrections that book once

Fixing the mismatch means booking a **correction**, never editing the original. The original payment and its entries stay exactly as they were, and a new payment through a suspense account makes up the difference:

```go noverify
// recon.go, lines 67–103
// Correct books each mismatch as a new payment through the suspense account. The correction's key is derived
// from the day and the finding, so running the job twice books each correction once.
// Nothing is edited or deleted: the original payment stays exactly as it was.
func (s *Store) Correct(ctx context.Context, day string, fs []Finding) (booked int, err error) {
	for _, f := range fs {
		if f.Kind != "amount_mismatch" {
			continue // the other kinds need a human: a payment we don't know about, or one the bank never saw
		}
		diff := f.Bank - f.Ledger // >0: the bank moved more than we booked
		from, to, amt := Suspense, 1, diff
		if diff < 0 {
			from, to, amt = 1, Suspense, -diff
		}
		key := fmt.Sprintf("recon:%s:%s", day, f.Key)
		tx, err := s.Pool.Begin(ctx)
		if err != nil {
			return booked, err
		}
		tag, err := tx.Exec(ctx, `INSERT INTO payments (key, from_acct, to_acct, amount, status, ref)
		                          VALUES ($1,$2,$3,$4,'posted',$5) ON CONFLICT (key) DO NOTHING`, key, from, to, amt, f.Key)
		if err == nil && tag.RowsAffected() == 1 {
			_, err = tx.Exec(ctx, `INSERT INTO entries (payment_key, account_id, amount) VALUES ($1,$2,$3),($1,$4,$5)`,
				key, from, -amt, to, amt)
		}
		if err != nil {
			tx.Rollback(ctx)
			return booked, err
		}
		if err = tx.Commit(ctx); err != nil {
			return booked, err
		}
		if tag.RowsAffected() == 1 {
			booked++
		}
	}
	return booked, nil
}
```

Look at the correction's key: `recon:<day>:<original key>`. It is built from the day and the finding, so running the job twice produces the same key, and `ON CONFLICT (key) DO NOTHING` books it once. The correction also carries `ref`, the key it corrects, and `Reconcile` adds corrections into a payment's effective amount:

```text
corrections booked: first run 1, second run 0; entries sum 0, unbalanced 0; findings after: 2
```

The first run booked one correction, the second booked none, the books still balance, and the mismatch is gone: two findings left, the two that need a person. A reconciliation job that isn't idempotent turns a twelve-cent problem into a twenty-four-cent problem the second time cron fires.

<Callout kind="pro" title="Make it a habit, not an event">
Run reconciliation on a schedule and alert on any non-empty result. Store each run's findings (they are evidence), keep the corrections append-only, and treat a reconciliation that stops running as an incident: the day it silently stops is the day the drift starts.
</Callout>

<Recap>

- Reconcile against the external statement by key: mismatched amount, missing on either side.
- Correct by appending a payment through a suspense account, never by editing history, with a deterministic key so a rerun books once (first run 1, second run 0).

</Recap>

## Proving It Stays Right

### Step 1: an invariant you can check with one query

The ledger has properties that must hold no matter what happens to the processes around it. Check them:

```go noverify
// pay.go, lines 54–66
// Invariants returns (sum of all entries, payments with a non-zero sum, payments posted without entries).
func (s *Store) Invariants(ctx context.Context) (total int64, unbalanced, missing int, err error) {
	err = s.Pool.QueryRow(ctx, `SELECT COALESCE(sum(amount),0) FROM entries`).Scan(&total)
	if err != nil {
		return
	}
	err = s.Pool.QueryRow(ctx, `SELECT count(*) FROM (SELECT payment_key FROM entries GROUP BY 1 HAVING sum(amount) <> 0) x`).Scan(&unbalanced)
	if err != nil {
		return
	}
	err = s.Pool.QueryRow(ctx, `SELECT count(*) FROM payments p WHERE status='posted' AND NOT EXISTS (SELECT 1 FROM entries e WHERE e.payment_key=p.key)`).Scan(&missing)
	return
}
```

Three questions: does everything sum to zero, does every payment's own entries sum to zero, and does every posted payment have entries? If those three hold after chaos, the books are right, whatever the chaos was.

A rate limiter that runs a goroutine to top up every bucket every so often would need a million goroutines for a million accounts. `golang.org/x/time/rate` does not. 300 ms later, with no goroutine running for it: tokens 5.00 (refilled on demand from the clock)

100,000 buckets, and the goroutine count didn't move. The refill happened when the bucket was next read, from the clock. That is why the per-account limiter costs 150 bytes per account and no CPU while the account is quiet, and why the only maintenance it needs is the sweep in stop 2.

<Exercise n={1} title="Implement Allow with Wait" level="easy">

Extend `AccountLimiter` with a `Wait(ctx context.Context, accountID string) error` method that blocks until a token is available for the account or the context is cancelled. Use `rate.Limiter.Wait`.

<Solution>

```go
package main

import (
	"context"
	"sync"

	"golang.org/x/time/rate"
)

type AccountLimiter struct {
	mu       sync.Mutex
	limiters map[string]*rate.Limiter
	r        rate.Limit
	b        int
}

func NewAccountLimiter(r rate.Limit, b int) *AccountLimiter {
	return &AccountLimiter{
		limiters: make(map[string]*rate.Limiter),
		r:        r,
		b:        b,
	}
}

func (al *AccountLimiter) getLimiter(accountID string) *rate.Limiter {
	al.mu.Lock()
	defer al.mu.Unlock()
	if lim, ok := al.limiters[accountID]; ok {
		return lim
	}
	lim := rate.NewLimiter(al.r, al.b)
	al.limiters[accountID] = lim
	return lim
}

func (al *AccountLimiter) Allow(accountID string) bool {
	return al.getLimiter(accountID).Allow()
}

// Wait blocks until the account has an available token or ctx is done.
// Returns ctx.Err() if the context is cancelled before a token is available.
func (al *AccountLimiter) Wait(ctx context.Context, accountID string) error {
	return al.getLimiter(accountID).Wait(ctx)
}
```

`rate.Limiter.Wait` handles the blocking and context cancellation for you. The key detail is that `getLimiter` must be called once to get the same limiter consistently — never call `getLimiter` twice and get two different objects for the same account (a bug the mutex prevents).

</Solution>

<Exercise n={3} title="Make the reconciler idempotent" level="medium">

The `Reconcile` function currently returns a slice of `Discrepancy` values on every call. In production it writes those to a database. Add an `alreadyFlagged map[string]bool` parameter so that if a discrepancy's `ExternalRef` was already flagged in a previous run, it is skipped (not returned again). This makes the job safe to re-run without creating duplicate alert records.

<Solution>

```go
package main

import "fmt"

func ReconcileIdempotent(
	ledger []LedgerEntry,
	settlement []SettlementRecord,
	alreadyFlagged map[string]bool,
) []Discrepancy {
	ledgerByRef := make(map[string]LedgerEntry, len(ledger))
	for _, e := range ledger {
		ledgerByRef[e.ExternalRef] = e
	}

	var discrepancies []Discrepancy

	emit := func(d Discrepancy) {
		if alreadyFlagged[d.ExternalRef] {
			return // already flagged in a prior run — skip
		}
		discrepancies = append(discrepancies, d)
	}

	settledRefs := make(map[string]struct{}, len(settlement))
	for _, s := range settlement {
		settledRefs[s.ExternalRef] = struct{}{}
		le, ok := ledgerByRef[s.ExternalRef]
		if !ok {
			emit(Discrepancy{
				Kind:        "missing_in_ledger",
				ExternalRef: s.ExternalRef,
				Detail:      fmt.Sprintf("processor settled %d cents; no ledger entry", s.AmountCents),
			})
			continue
		}
		if le.AmountCents != s.AmountCents {
			emit(Discrepancy{
				Kind:        "amount_mismatch",
				ExternalRef: s.ExternalRef,
				Detail: fmt.Sprintf("ledger=%d, processor=%d",
					le.AmountCents, s.AmountCents),
			})
		}
	}

	for _, le := range ledger {
		if _, settled := settledRefs[le.ExternalRef]; !settled {
			emit(Discrepancy{
				Kind:        "missing_in_processor",
				ExternalRef: le.ExternalRef,
				Detail:      fmt.Sprintf("ledger has %d cents; processor has no record", le.AmountCents),
			})
		}
	}

	return discrepancies
}
```

In production, `alreadyFlagged` is populated by a query like `SELECT external_ref FROM reconciliation_discrepancies WHERE run_date = ?` before calling `Reconcile`. New discrepancies are inserted; known ones are skipped. Re-running the job is harmless.

</Solution>

</Exercise>

<Exercise n={4} title="Circuit-breaker-aware fraud check" level="medium">

Write a `CircuitBreakerFraudChecker` that wraps an external `FraudChecker`. When the external checker returns an error, it increments an error counter. If the counter exceeds a threshold (e.g., 5 consecutive errors), it enters an `open` state and returns a configurable fallback `FraudResult` without calling the external checker. After a cool-down period, it re-enters `half-open` and allows one probe call through. Use a mutex for the state.

<Solution>

```go
package main

import (
	"context"
	"sync"
	"time"
)

type cbState int

const (
	cbClosed   cbState = iota // normal: all calls go through
	cbOpen                    // tripped: all calls return the fallback
	cbHalfOpen                // probe: one call allowed through
)

type CircuitBreakerFraudChecker struct {
	inner     FraudChecker
	fallback  FraudResult
	mu        sync.Mutex
	state     cbState
	failures  int
	threshold int
	resetAt   time.Time
	cooldown  time.Duration
}

func NewCBFraudChecker(inner FraudChecker, fallback FraudResult, threshold int, cooldown time.Duration) *CircuitBreakerFraudChecker {
	return &CircuitBreakerFraudChecker{
		inner:     inner,
		fallback:  fallback,
		threshold: threshold,
		cooldown:  cooldown,
	}
}

func (cb *CircuitBreakerFraudChecker) Check(ctx context.Context, t Transfer) (FraudResult, error) {
	cb.mu.Lock()
	switch cb.state {
	case cbOpen:
		if time.Now().After(cb.resetAt) {
			cb.state = cbHalfOpen
		} else {
			cb.mu.Unlock()
			return cb.fallback, nil
		}
	}
	cb.mu.Unlock()

	result, err := cb.inner.Check(ctx, t)

	cb.mu.Lock()
	defer cb.mu.Unlock()
	if err != nil {
		cb.failures++
		if cb.failures >= cb.threshold {
			cb.state = cbOpen
			cb.resetAt = time.Now().Add(cb.cooldown)
		}
		return cb.fallback, nil
	}
	// Success: reset failure counter and close the circuit.
	cb.failures = 0
	cb.state = cbClosed
	return result, nil
}
```

The fallback policy is injected at construction — it might be `FraudResult{Allow: false}` for a strict posture (reject all when the service is down) or `FraudResult{Allow: true}` for a lenient one (allow through, queue for review). The right choice depends on your risk model — encode it explicitly, never guess.

</Solution>

</Exercise>

```go
				{ExternalRef: "t4", AmountCents: 1988, SettledAt: base},
			},
			wantKinds: []string{"amount_mismatch"},
		},
	}

	for _, tc := range tests {
		t.Run(tc.name, func(t *testing.T) {
			got := Reconcile(tc.ledger, tc.settlement)
			if len(got) != len(tc.wantKinds) {
				t.Fatalf("got %d discrepancies, want %d", len(got), len(tc.wantKinds))
			}
			for i, d := range got {
				if d.Kind != tc.wantKinds[i] {
					t.Errorf("discrepancy[%d]: got kind %q, want %q", i, d.Kind, tc.wantKinds[i])
				}
			}
		})
	}

	// Parallel concurrency test — Reconcile must be race-free.
	t.Run("concurrent_race", func(t *testing.T) {
		t.Parallel()
		var wg sync.WaitGroup
		for range 10 {
			wg.Add(1)
			go func() {
				defer wg.Done()
				ledger := []LedgerEntry{
					{ExternalRef: "tx-par", AmountCents: 100, AccountID: "ax"},
				}
				settlement := []SettlementRecord{
					{ExternalRef: "tx-par", AmountCents: 100, SettledAt: time.Now()},
				}
				_ = Reconcile(ledger, settlement)
			}()
		}
		wg.Wait()
	})
}
```

Run with `go test -race -v ./...`. The race detector must be silent. `Reconcile` creates fresh local maps on each call and takes no mutable shared state, so it is inherently safe for concurrent callers — the test confirms it.

  starter={`package main

import (
	"fmt"
	"sync"
)

// Money is always integer cents. Never a float.
type Money int64

type AccountID string

// Ledger is a concurrent in-memory double-entry ledger.
// BUG: Transfer has two bugs — see comments.
type Ledger struct {
	mu       sync.Mutex
	balances map[AccountID]Money
	seen     map[string]bool
}

func NewLedger(initial map[AccountID]Money) *Ledger {
	bal := make(map[AccountID]Money, len(initial))
	for k, v := range initial {
		bal[k] = v
	}
	return &Ledger{balances: bal, seen: make(map[string]bool)}
}

// Transfer has two bugs:
// BUG 1: no idempotency check — duplicate keys are re-applied.
// BUG 2: no insufficient-funds guard — src can go negative.
// Fix: check seen[key] first; check src balance; only then transfer.
func (l *Ledger) Transfer(key string, src, dst AccountID, amount Money) error {
	l.mu.Lock()
	defer l.mu.Unlock()
	// BUG 1: missing: if l.seen[key] { return nil }
	// BUG 2: missing: if l.balances[src] < amount { return ErrInsufficientFunds }
	l.balances[src] -= amount
	l.balances[dst] += amount
	l.seen[key] = true
	return nil
}

// TotalAssets sums all balances.
func (l *Ledger) TotalAssets() Money {
	l.mu.Lock()
	defer l.mu.Unlock()
	var total Money
	for _, b := range l.balances {
		total += b
	}
	return total
}

// ── checks: do not edit. Run to verify your fix. ──
func main() {
	allOK := true

	// Check 1: 200 concurrent transfers — books must balance.
	ledger := NewLedger(map[AccountID]Money{
		"a": 50_000, "b": 50_000, "c": 50_000, "d": 50_000,
	})
	startTotal := ledger.TotalAssets()
	accounts := []AccountID{"a", "b", "c", "d"}
	var wg sync.WaitGroup
	for g := 0; g < 200; g++ {
		g := g
		wg.Add(1)
		go func() {
			defer wg.Done()
			src := accounts[g%4]
			dst := accounts[(g+1)%4]
			key := fmt.Sprintf("tx-%d", g)
			_ = ledger.Transfer(key, src, dst, 100)
			_ = ledger.Transfer(key, src, dst, 100) // duplicate — must be no-op
		}()
	}
	wg.Wait()
	if ledger.TotalAssets() != startTotal {
		fmt.Printf("FAIL check 1: money not conserved: started %d, ended %d\\n",
			startTotal, ledger.TotalAssets())
		allOK = false
	}

	// Check 2: idempotency — same key applied twice changes balance exactly once.
	l2 := NewLedger(map[AccountID]Money{"alice": 10_000, "bob": 0})
	before := l2.TotalAssets()
	_ = l2.Transfer("idem-1", "alice", "bob", 500)
	after1 := l2.TotalAssets()
	_ = l2.Transfer("idem-1", "alice", "bob", 500)
	after2 := l2.TotalAssets()
	if after1 != before || after2 != before {
		fmt.Println("FAIL check 2: idempotency violated")
		allOK = false
	}

	// Check 3: insufficient funds returns error, ledger unchanged.
	l3 := NewLedger(map[AccountID]Money{"broke": 0, "rich": 50_000})
	t3 := l3.TotalAssets()

		fmt.Println("FAIL check 3: expected error on insufficient funds, got nil")
		allOK = false
	} else if l3.TotalAssets() != t3 {
		fmt.Println("FAIL check 3: ledger corrupted after rejected transfer")
		allOK = false
	}

	if allOK {
		fmt.Println("ALL CHECKS PASS")
	}
}`}
