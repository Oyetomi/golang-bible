## Why Floats Are a Crime

Let me set the scene before we touch a single type.

Meridian processes ten million transactions a day. A `float64` fee calculation silently eats fractions of a cent on each one. Three months later the finance team finds a $47,000 discrepancy in the monthly reconciliation. No fraud — just math. That is not a hypothetical. That is Tuesday.

**On the job:** Every time you see money stored as `float64` in a production codebase, a reconciliation job downstream is producing wrong numbers. The error is invisible until the books don't close.

<Define term="IEEE-754 / floating-point" since="this chapter (for financial impact)">
**IEEE-754** is the international standard for binary floating-point arithmetic — the spec your CPU's FPU implements when you write `float64`. It represents numbers as `sign × mantissa × 2^exponent`. Because the exponent is a power of **2**, the only fractions representable exactly are those of the form `N / 2^k` — halves, quarters, eighths. Decimal fractions like `0.1` (= `1/10`) have no exact binary representation and are silently rounded to the nearest 52-bit value. For scientific computation this rounding is fine and expected. For money, where every cent must be exact, it is a defect at the hardware level. The fix is not to avoid IEEE-754 — it's to stop using it for money altogether.
</Define>

### The Binary Representation Problem

Here is the crime, rendered plain:

```go
package main

import "fmt"

func main() {
	a := 0.1
	b := 0.2
	c := a + b

	fmt.Println(c)         // prints 0.30000000000000004
	fmt.Println(c == 0.3)  // prints false

	// Simulate 10 transactions of $0.10, in float64
	total := 0.0
	for range 10 {
		total += 0.10
	}
	fmt.Printf("10 × $0.10 = %.20f\n", total) // not 1.0
}
```

<UnderTheHood title="IEEE-754: why 0.1 can't exist in binary (Go 1.26)">

`float64` is a 64-bit value split into three fields: **1 sign bit**, **11 exponent bits**, **52 mantissa (significand) bits**. The value is `(-1)^sign × 1.mantissa × 2^(exponent-1023)`.

The exponent and mantissa are both **binary** — powers of 2. So the only fractions a `float64` can represent *exactly* are those expressible as `N / 2^k` for some integers `N` and `k`: halves, quarters, eighths, and so on.

`0.1` in decimal is `1/10`. To express `1/10` in binary you need to divide by 10, but 10 = 2 × 5, and **5 has no power-of-two factorization**. So `1/10` becomes a repeating binary fraction — like `1/3` in decimal. The CPU truncates it to 52 mantissa bits and rounds. What you get is:

```
0.1 ≈ 0.1000000000000000055511151231257827021181583404541015625
```

That's the *actual* value your variable holds when you write `x := 0.1`. It's close — but for financial math, "close" is a crime. Go 1.26 follows IEEE-754-2008 for `float64`; the spec makes no apology: exact decimal arithmetic simply isn't what binary floating point is for.

The fix is to stop using binary floating point for money entirely. As of Go 1.26, there is no native decimal floating-point type in the language — you use integer minor units or a decimal library. Both are exact.

This is a model of the mechanism, not a verbatim spec transcript. The behavior is implementation-defined at the hardware level; Go's `float64` is the IEEE-754 double-precision type on every supported platform.

</UnderTheHood>

The fix is elegant and has been industry standard since before most of us were born: **store money as an integer count of the smallest unit your currency supports**.

For USD, that's cents: `$14.99` → `1499`. For JPY (no minor unit), `¥1400` → `1400`. For KWD (Kuwaiti Dinar, three decimal places), `1.500 KWD` → `1500`. Integer arithmetic is **exact** — no rounding, no drift, no surprises.

**On the job:** Meridian's ledger stores every `Transfer` amount as `int64` minor units alongside a three-letter ISO 4217 currency code. Passing a bare `float64` dollars value to a ledger function is a compile-time type error. That's intentional.

<Define term="Integer minor units (cents)" since="this chapter">
The **minor unit** of a currency is its smallest indivisible subdivision: the cent for USD (1/100 of a dollar), the yen for JPY (JPY has no minor unit — ¥1 is the smallest unit), the fil for KWD (1/1000 of a dinar). Storing money as an integer count of minor units means `$14.99` is stored as `1499` (an `int64`), not `14.99` (a `float64`). Because integers have no fractional part, every addition and subtraction is mathematically exact — no IEEE-754 rounding path is involved. This is the foundational rule of financial arithmetic in Go.
</Define>

### The Money Type

Here is the correct foundation for every financial amount in Meridian's service:

```go
// Money represents an exact monetary amount in the currency's minor unit.
// For USD: Amount is cents. For JPY: Amount is yen. For KWD: Amount is fils.
// NEVER store money as float64. You have been warned.
type Money struct {
	Amount   int64  // minor units — always an integer
	Currency string // ISO 4217 code: "USD", "EUR", "JPY", "KWD"
}
```

`int64` holds values from −9,223,372,036,854,775,808 to +9,223,372,036,854,775,807. In USD cents, that's roughly ±92 quadrillion dollars (9.2 quintillion cents ÷ 100). If Meridian's ledger holds more than $92 quadrillion in a single entry, the data type is the least of your problems.

### Arithmetic is Exact

```go
package main

import "fmt"

// Money represents an exact monetary amount in the currency's minor unit.
type Money struct {
	Amount   int64
	Currency string
}

// Add returns a + b. Panics if currencies differ — mixing currencies is a bug.
func Add(a, b Money) Money {
	if a.Currency != b.Currency {
		panic("currency mismatch: " + a.Currency + " + " + b.Currency)
	}
	return Money{Amount: a.Amount + b.Amount, Currency: a.Currency}
}

// Format renders the amount for display. For USD cents, divides by 100.
func (m Money) Format() string {
	switch m.Currency {
	case "USD", "EUR", "GBP":
		return fmt.Sprintf("%s %d.%02d", m.Currency, m.Amount/100, abs(m.Amount%100))
	case "JPY":
		return fmt.Sprintf("%s %d", m.Currency, m.Amount)
	default:
		return fmt.Sprintf("%s %d (minor units)", m.Currency, m.Amount)
	}
}

func abs(x int64) int64 {
	if x < 0 {
		return -x
	}
	return x
}

func main() {
	fee := Money{Amount: 150, Currency: "USD"}   // $1.50
	tax := Money{Amount: 113, Currency: "USD"}   // $1.13

	total := Add(fee, tax)
	fmt.Println(total.Format()) // USD 2.63 — exact, always
}
```

## Decimal Libraries

Integer cents are perfect for storing and adding amounts. But some calculations genuinely need more precision:

- **Interest:** 7.5% annual rate on a balance, accrued daily → fractional cents at each step
- **FX conversion:** 1 USD = 0.9241 EUR → the converted amount has sub-cent precision before you round to storage
- **Tax:** some jurisdictions compute to three decimal places before rounding

For these cases, you need a **decimal arithmetic library** — not floats, a library built specifically for base-10 exact arithmetic.

**On the job:** In Meridian's interest accrual job, every daily calculation goes through `shopspring/decimal` (or `math/big.Rat` in the stdlib version). The result is rounded explicitly to whole cents before being written to the ledger. There is never a stage where a fractional cent lives in an `int64` — it lives in the decimal type until the moment it's rounded.

<Define term="Decimal library (shopspring/decimal, math/big.Rat)" since="this chapter">
A **decimal library** performs arithmetic in base 10 rather than base 2. `shopspring/decimal` represents a number as a `big.Int` mantissa plus an integer scale (number of decimal places), so `0.1` is stored as `1 × 10^-1` — exactly. `math/big.Rat` from the standard library stores a fraction as a numerator and denominator `big.Int` pair, so `1/10` is stored as the pair `(1, 10)` — also exactly. Both are slower than `int64` arithmetic (they allocate on the heap), but they're exact for any precision you need. The usage pattern is always: **compute in decimal precision → round explicitly → store as `int64` minor units**.
</Define>

### `shopspring/decimal`

The community standard for Go decimal arithmetic. Internally it represents a number as a `big.Int` mantissa plus a scale (number of decimal places). All arithmetic is exact up to any precision you specify.

```go
// go get github.com/shopspring/decimal
package main

import (
	"fmt"

	"github.com/shopspring/decimal"
)

func main() {
	balance := decimal.NewFromInt(100000) // 1000.00 USD, stored as cents → 100000
	rate := decimal.NewFromString("0.075") // 7.5% annual rate
	// must handle the error in real code; omitted here for brevity
	days := decimal.NewFromInt(365)

	// Daily interest accrual: balance * rate / 365
	dailyInterest := balance.Mul(rate).Div(days)
	fmt.Println("daily interest (exact):", dailyInterest) // exact decimal

	// Round to cents (whole minor units) using banker's rounding
	rounded := dailyInterest.RoundBank(0) // round to whole cents
	fmt.Println("rounded to cents:", rounded)
}
```

### `math/big.Int` and `math/big.Rat`

The standard library's arbitrary-precision integers and rationals. No external dependency. Slower than `shopspring/decimal` for typical use (more allocations, no caching), but zero-dependency and sufficient for many cases. As of Go 1.26, `math/big` remains the canonical standard-library path for exact arithmetic without external packages.

### When to Use Which

| Situation | Tool |
|---|---|
| Storing amounts in a ledger | `int64` minor units |
| Adding/subtracting amounts | `int64` minor units |
| Comparing amounts | `int64` minor units |
| Computing a percentage fee | `shopspring/decimal` or `big.Rat`, round → `int64` |
| Interest accrual, daily/monthly | `shopspring/decimal` or `big.Rat`, round → `int64` |
| FX conversion | `shopspring/decimal` or `big.Rat`, round → `int64` |
| Everything in storage/wire | `int64` minor units |

The pattern is always: **compute in decimal precision → round explicitly → store as integer minor units.**

## Currency Types and Safety

We've been using a `string` for currency codes. That's a footgun. The type system can prevent an entire class of bugs for free — and in fintech, free bug prevention is the best kind.

**On the job:** Meridian's `Transfer` type has `Amount Money` where `Money.Currency` is a `Currency` struct. A function that adds two `Money` values with different currencies returns `error`. A compile-time phantom-type approach (Exercise 4) goes further and catches mismatches before the binary is built.

### The Problem With Raw Strings

```go
// This compiles. It is also catastrophically wrong.
usdBalance := Money{Amount: 10000, Currency: "USD"}
eurBalance := Money{Amount: 10000, Currency: "EUR"}
// Add is checking the string at runtime. A typo ("usd", "US$") passes
// compilation but blows up at runtime — or worse, doesn't check at all.
```

### A Typed Currency

```go
package main

import "fmt"

// Currency is an ISO 4217 currency code with a known minor-unit exponent.
// Use the package-level constants — never construct one from a raw string
// at call sites.
type Currency struct {
	code       string // ISO 4217, e.g. "USD"
	minorExp   int    // decimal places: USD=2, JPY=0, KWD=3
}

func (c Currency) String() string { return c.code }

// Package-level constants — the only valid values.
var (
	USD = Currency{"USD", 2} // 1 USD = 100 cents
```

### Minor-Unit Exponents

The `minorExp` field tells you how many decimal places separate the major unit from the minor unit. This is codified in **ISO 4217**:

| Currency | Code | minorExp | Example |
|---|---|---|---|
| US Dollar | USD | 2 | 100 cents = $1.00 |
| Euro | EUR | 2 | 100 cents = €1.00 |
| Japanese Yen | JPY | 0 | ¥1 = ¥1 (no minor unit) |
| Kuwaiti Dinar | KWD | 3 | 1000 fils = 1 KWD |
| Bahraini Dinar | BHD | 3 | 1000 fils = 1 BHD |

`minorExp` matters when you convert between display format and storage, when you compute FX rates, and when you interpret amounts from an external API. An API that sends `{"amount": 1000, "currency": "JPY"}` means ¥1,000. The same `{"amount": 1000, "currency": "KWD"}` means 1.000 KWD. Never assume `exp = 2`.

## Rounding Modes

We've arrived at the part that trips up even experienced fintech engineers, because **rounding is not a technical decision — it's a legal one**.

**On the job:** When Meridian computes a 1.5% platform fee on a $9.99 transaction, the fee is `9.99 × 0.015 = 0.14985` — not a whole number of cents. Which direction you round is specified in your contracts, your terms of service, and possibly your regulatory framework. If you haven't checked, you're guessing.

<Define term="Rounding mode (half-up, banker's rounding / half-even)" since="this chapter">
A **rounding mode** determines what happens when an arithmetic result falls exactly halfway between two integers (the `x.5` case). The two modes that matter most in fintech:

- **Half-up** (round half away from zero): `0.5 → 1`, `1.5 → 2`, `2.5 → 3`. What most people call "normal rounding." Simple, but it introduces a systematic upward bias because every tie-break goes the same direction. Common in everyday retail math.
- **Half-even** (banker's rounding): `0.5 → 0` (rounds to even), `1.5 → 2` (rounds to even), `2.5 → 2` (rounds to even), `3.5 → 4` (rounds to even). When a value is exactly halfway, it rounds to the nearest *even* integer. Over a large dataset, half the tie-breaks go up and half go down, so the bias cancels out. Mandated by IEEE-754 as the default rounding mode, and required by many financial regulations for interest and tax calculations.

You do not get to pick the mode based on what's easiest to implement. Check your regulatory context.
</Define>

### The Four Modes You Need to Know

```go
package main

import (
	"fmt"
	"math"
)

// halfUp rounds n to the nearest integer, with 0.5 going up (away from zero).
// Common in retail and everyday math.
func halfUp(n float64) int64 {
	return int64(math.Floor(n + 0.5))
}

// halfEven rounds to nearest, with 0.5 going to the nearest EVEN integer.
// Also called "banker's rounding." Required by many financial regulations.
func halfEven(n float64) int64 {
	floor := math.Floor(n)
	frac := n - floor
	if frac < 0.5 {
		return int64(floor)
	}
	if frac > 0.5 {
		return int64(math.Ceil(n))
	}
	// exactly 0.5: round to even
	if int64(floor)%2 == 0 {
		return int64(floor)
	}
	return int64(math.Ceil(n))
}

func main() {
	cases := []float64{0.5, 1.5, 2.5, 3.5, 4.5}
	fmt.Printf("%-8s  %-8s  %-8s\n", "value", "halfUp", "halfEven")
	for _, v := range cases {
		fmt.Printf("%-8.1f  %-8d  %-8d\n", v, halfUp(v), halfEven(v))
	}
}
```

### The Penny Allocation Problem

Here is a scenario every payment system faces: **splitting a total across multiple recipients where the total doesn't divide evenly**.

Meridian takes a $10.00 payment and splits it to three merchants: 33.33%, 33.33%, 33.34%. Or maybe three equal parts — but `10.00 / 3 = 3.333…`, and you can't store a third of a cent.

**On the job:** If your split function loses a penny, the Meridian ledger's debit and credit sides won't balance. Auditors call that a discrepancy. Regulators call that an incident.

<Define term="The penny-allocation problem" since="this chapter">
The **penny-allocation problem** (also called the largest remainder method) arises when you split an integer total among N recipients and the total is not evenly divisible by N. Naive division truncates, losing the remainder entirely — `1000 / 3 = 333 × 3 = 999`, one cent vanished. The correct algorithm is: give everyone `floor(total/N)`, then distribute one extra minor unit to each of the first `total % N` recipients. The result: every share is either `floor(total/N)` or `floor(total/N) + 1`, and all shares sum to exactly `total`. Not a single minor unit is created or destroyed. This is the only correct way to split an indivisible total.
</Define>

The naive approach:

```go
// WRONG: loses or creates money
func splitNaive(total int64, n int) []int64 {
	share := total / int64(n) // truncates: 1000/3 = 333
	result := make([]int64, n)
	for i := range result {
		result[i] = share
	}
	return result // sum = 999, not 1000 — a penny vanished
}
```

The correct approach — **penny allocation** (also called the largest remainder method):

```go
package main

import "fmt"

// Allocate splits total into n shares such that:
//  1. Every share is either floor(total/n) or floor(total/n)+1
//  2. The shares sum to exactly total — not a single minor unit lost or created
//
// The first (total % n) shares get the extra penny.
func Allocate(total int64, n int) []int64 {
	if n <= 0 {
		panic("allocate: n must be positive")
	}
	base := total / int64(n)
	remainder := total % int64(n) // number of shares that get +1
	shares := make([]int64, n)
	for i := range shares {
		shares[i] = base
		if int64(i) < remainder {
			shares[i]++
		}
	}
	return shares
}

func main() {
	total := int64(1000) // $10.00 in cents
	shares := Allocate(total, 3)
	sum := int64(0)
	for _, s := range shares {
		sum += s
	}
	fmt.Printf("shares: %v\n", shares)   // [334 333 333]
	fmt.Printf("sum: %d (original: %d)\n", sum, total) // 1000 == 1000
}
```

### FX Conversion with Explicit Rounding

```go
package main

import (
	"fmt"
	"math/big"
)

type Currency struct {
	code     string
	minorExp int
}

func (c Currency) String() string { return c.code }

var (
	USD = Currency{"USD", 2}
	EUR = Currency{"EUR", 2}
)

type Money struct {
	Amount   int64
	Currency Currency
}

// Convert converts m to targetCurrency using the given exchange rate.
// rate is expressed as: 1 unit of m.Currency = rate units of targetCurrency.
// Rate is passed as a rational number (numerator/denominator) for exactness.
// The result is rounded to the target currency's minor unit using half-even.
func Convert(m Money, target Currency, rateNum, rateDen int64) Money {
	// Use big.Rat for exact intermediate arithmetic
	amount := new(big.Rat).SetInt64(m.Amount)
	rate := new(big.Rat).SetFrac(
		new(big.Int).SetInt64(rateNum),
		new(big.Int).SetInt64(rateDen),
	)
	converted := new(big.Rat).Mul(amount, rate)

	// Round to integer (half-even) for the target minor unit
	f, _ := converted.Float64()
	rounded := halfEven(f)

	return Money{Amount: rounded, Currency: target}
}

func halfEven(n float64) int64 {
	// Works on the assumption n is very close to an integer
	// after the big.Rat multiplication. In production, use
	// shopspring/decimal's RoundBank for this step.
	floor := int64(n)
	frac := n - float64(floor)
	if frac < 0.5 {
		return floor
	}
	if frac > 0.5 {
		return floor + 1
	}
	if floor%2 == 0 {
		return floor
	}
	return floor + 1
}

func main() {
	usd := Money{Amount: 10000, Currency: USD} // $100.00
	// Rate: 1 USD = 0.9241 EUR, expressed as 9241/10000
	eur := Convert(usd, EUR, 9241, 10000)
	fmt.Printf("$100.00 USD → %d EUR minor units (€%.2f)\n",
		eur.Amount, float64(eur.Amount)/100)
}
```

### Never Mix Currencies in an Arithmetic Expression

The type system prevents this at compile time if you use the `Currency` struct and a checked `Add`. Make your `Add` and `Subtract` functions always return `error` on a currency mismatch. Never silently coerce. Never compare raw amounts across currencies.

<Callout kind="warn" title="FX rates are never exact — document your source">

Every FX conversion has a rate that changes over time. Meridian must record which rate was used, when it was fetched, and from which source. An auditor asking "why did this USD→EUR conversion use rate 0.9241 on March 3rd?" must get a traceable answer from the ledger. Store the rate alongside the conversion entry. This is not optional in a regulated system.

</Callout>

<UnderTheHood title="Why integer minor units are exact: the hardware perspective (Go 1.26)">

Modern 64-bit CPUs implement `int64` addition with a single `ADD` instruction. The result is mathematically exact for all inputs within the `int64` range — no rounding, no approximation. If the mathematical result is outside the representable range, Go integer arithmetic wraps according to the fixed-width integer rules; it does not trap overflow. Size your amounts to stay in range.

By contrast, `float64` addition uses binary floating-point arithmetic and rounds results to the precision of the `float64` representation. That rounding is mandatory — the IEEE spec defines it. It is not a bug in Go or in your CPU. It is exactly what floating-point arithmetic is supposed to do, and it is exactly wrong for money.

As of Go 1.26, there is no `decimal` numeric type in the language spec. The compiler emits the same `FADD`/`FMUL` instructions for `float64` arithmetic that any C compiler would. Integer minor units sidestep the entire FPU rounding path. `big.Int` and `big.Rat` implement their arithmetic in software (in `math/big`), which is slower but exact for any precision you specify.

This is a simplified model — actual CPU and FPU behavior varies by microarchitecture. The key point stands: integer arithmetic has no mantissa rounding step.

</UnderTheHood>

### Fuzz Test for Money Math

The testing mandate for fintech chapters is non-negotiable. Here is a fuzz test that verifies the two invariants every money implementation must uphold: round-trip formatting and penny-perfect allocation.

Run it with `go test -fuzz=FuzzAllocate ./...` in your module. The fuzzer will generate thousands of random inputs and verify the invariant holds on all of them.

```go
package money_test

import (
	"testing"
)

// Allocate splits total into n shares, each differing by at most 1,
// summing to exactly total.
func Allocate(total int64, n int) []int64 {
	if n <= 0 {
		return nil
	}
	base := total / int64(n)
	remainder := total % int64(n)
	shares := make([]int64, n)
	for i := range shares {
		shares[i] = base
		if int64(i) < remainder {
			shares[i]++
		}
	}
	return shares
}

// FuzzAllocate verifies that Allocate always sums back to the original total
// and that no two shares differ by more than 1 minor unit.
func FuzzAllocate(f *testing.F) {
	// Seed corpus: interesting edge cases
	f.Add(int64(1000), 3)
	f.Add(int64(1), 3)
	f.Add(int64(0), 5)
	f.Add(int64(7), 7)
	f.Add(int64(100), 1)

	f.Fuzz(func(t *testing.T, total int64, n int) {
		// Constrain to positive, sensible values
		if total < 0 {
			total = -total
		}
		if n <= 0 || n > 10000 {
			t.Skip()
		}

		shares := Allocate(total, n)

		// Invariant 1: shares must sum to total
		var sum int64
		for _, s := range shares {
			sum += s
		}
		if sum != total {
			t.Errorf("Allocate(%d, %d) sum=%d, want %d", total, n, sum, total)
		}

		// Invariant 2: no two shares differ by more than 1
		for i, s := range shares {
			for j, r := range shares {
				diff := s - r
				if diff < -1 || diff > 1 {
					t.Errorf("Allocate(%d, %d) shares[%d]=%d shares[%d]=%d differ by %d (>1)",
						total, n, i, s, j, r, diff)
				}
			}
		}
	})
}
```

Note: fuzz tests run via `go test -fuzz=FuzzAllocate` — not in the playground. The playground runner executes `go test` without the `-fuzz` flag, which still runs the seeded corpus cases as ordinary tests. Both modes should pass.

```go
		return fmt.Sprintf("¥%s%d", sign, a)
	default:
		return fmt.Sprintf("%s %s%d", m.Currency.code, sign, a)
	}
}

func main() {
	fmt.Println(Money{4999, USD})  // $49.99
	fmt.Println(Money{-150, USD}) // $-1.50
```

<Exercise n={3} title="Compute a platform fee" level="medium">

Write `func PlatformFee(amount Money, basisPoints int) (fee Money, remaining Money, err error)` that computes a fee in basis points (100 bps = 1%). Use `math/big.Rat` for the intermediate calculation and round the fee using half-even. Return the fee and the remaining amount, which must sum to the original. Verify with `fee.Amount + remaining.Amount == amount.Amount`.

<Solution>

```go
package main

import (
	"fmt"
	"math"
	"math/big"
)

type Currency struct {
	code     string
	minorExp int
}

var USD = Currency{"USD", 2}

type Money struct {
	Amount   int64
	Currency Currency
}

func halfEven(n float64) int64 {
	floor := math.Floor(n)
	frac := n - floor
	if frac < 0.5 {
		return int64(floor)
	}
	if frac > 0.5 {
		return int64(math.Ceil(n))
	}
	if int64(floor)%2 == 0 {
		return int64(floor)
	}
	return int64(math.Ceil(n))
}

func PlatformFee(amount Money, basisPoints int) (fee Money, remaining Money, err error) {
	if basisPoints < 0 || basisPoints > 10000 {
		return Money{}, Money{},
			fmt.Errorf("basisPoints %d out of range [0, 10000]", basisPoints)
	}
	// fee = amount * basisPoints / 10000
	rat := new(big.Rat).SetFrac(
		new(big.Int).SetInt64(amount.Amount*int64(basisPoints)),
		new(big.Int).SetInt64(10000),
	)
	f, _ := rat.Float64()
	feeAmt := halfEven(f)
	return Money{feeAmt, amount.Currency},
		Money{amount.Amount - feeAmt, amount.Currency},
		nil
}

func main() {
	amount := Money{10000, USD} // $100.00
	fee, rem, err := PlatformFee(amount, 150) // 1.50%
	if err != nil {
		fmt.Println("error:", err)
		return
	}
	fmt.Printf("amount: %d, fee: %d, remaining: %d\n",
		amount.Amount, fee.Amount, rem.Amount)
	fmt.Printf("balanced: %v\n", fee.Amount+rem.Amount == amount.Amount)
}
```

The invariant `fee + remaining == original` must hold. Half-even rounding eliminates systematic bias.

<Exercise n={4} title="Prevent currency mixing at compile time" level="medium">

Redesign `Add` so that a type mismatch between `Money{Currency: USD}` and `Money{Currency: EUR}` is caught at *compile time*, not runtime. Hint: use generic type parameters with a currency phantom type.

<Solution>

```go
package main

import "fmt"

// Phantom type tags — zero-size structs used only as type parameters.
type usd struct{}
type eur struct{}

// TypedMoney is parameterized on a phantom currency type C.
// You can only add TypedMoney[usd] to TypedMoney[usd] —
// the compiler rejects TypedMoney[usd] + TypedMoney[eur] at build time.
type TypedMoney[C any] struct {
	Amount int64
}

func Add[C any](a, b TypedMoney[C]) TypedMoney[C] {
	return TypedMoney[C]{Amount: a.Amount + b.Amount}
}

func main() {
	walletUSD := TypedMoney[usd]{Amount: 5000}
	feeUSD := TypedMoney[usd]{Amount: 150}
	result := Add(walletUSD, feeUSD)
	fmt.Println("USD total:", result.Amount) // 5150

	// This won't compile:
	// walletEUR := TypedMoney[eur]{Amount: 1000}
	// Add(walletUSD, walletEUR) // type mismatch: usd vs eur
}
```

The phantom type `C` is never stored — it's a zero-size compile-time tag. The `Add` function only accepts two `TypedMoney[C]` values with the *same* `C`. Mixing currencies becomes a type error, not a runtime panic. Trade-off: you need one phantom type per currency code, and dynamic currency (runtime string) falls back to the checked runtime approach.

<Recap>

- **Money is never a float.** `float64` can't represent `0.1` exactly. Binary fractions compound. Across millions of transactions, the error is real money.
- **Store money as `int64` minor units.** For USD: cents. For JPY: yen. For KWD: fils. Integer arithmetic is exact with no FPU rounding.
- **For sub-cent precision** (interest, tax, FX) compute in `shopspring/decimal` or `math/big.Rat`, then round explicitly to minor units before storing.
- **Use a typed `Currency` struct**, not a raw string. Carry `minorExp` (from ISO 4217) so you know how many decimal places the currency uses.
- **Never add different currencies.** Your `Add` function returns `error` on currency mismatch. Phantom-type generics catch it at compile time if you want it there instead.
- **Rounding mode is a legal requirement**, not a technical preference. Half-even (banker's rounding) eliminates systematic bias and is mandated by many financial regulations and by IEEE-754.
- **Penny allocation solves the indivisible-split problem.** `Allocate(total, n)` gives shares that sum to exactly `total`, with each share differing by at most 1 minor unit.
- **For FX conversions**, use exact rational arithmetic for the intermediate step, round explicitly with a documented rounding mode, and record the rate used in the audit log.
- **Fuzz your money math.** `go test -fuzz` will find the edge cases you didn't think of. The two invariants to fuzz: (1) splits sum to total, (2) fee + remainder equals original.
