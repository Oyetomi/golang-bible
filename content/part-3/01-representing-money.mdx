## Why Not float64

*Stop 1 of 6.*

### Step 1: what a float64 stores

A `float64` is a binary fraction: 53 significant bits times a power of two. Numbers like 0.5 or 0.25 (halves, quarters, eighths) are stored exactly. But **0.1 can't be**, for the same reason 1/3 can't be written exactly in decimal: in binary it's a repeating fraction. So `0.1` in a `float64` is really the nearest number that does fit:

```text
0.1 + 0.2 = 0.30000000000000004   (== 0.3? false)
the float64 nearest 0.1 is exactly 0.1000000000000000055511151231257827021181583404541015625
```

That's not a printing problem. It's the value. Every price, fee or rate with cents in it is stored slightly wrong, and every operation on it rounds again to the nearest binary fraction. Each error is tiny. Money is where they stop being tiny, because money gets added up millions of times and has to match to the cent.

### Step 2: four ways it shows, measured

This program does ordinary payment arithmetic twice, in `float64` and in integer cents, and compares:

Four different failures:

1. **Drift.** Ten million $0.10 fees should total exactly $1,000,000.00. The float total is $999,999.99983897: each addition rounded, and the errors piled up in one direction. Integer cents: exact.
2. **Order matters.** The same 100,000 payments summed forwards and backwards give two different totals. Float addition isn't associative, so a report that sums in a different order (a different index, a parallel sum) disagrees with the ledger.
3. **Wrong cent.** 7.5% of $3.00 is exactly 22.5¢, which the rule says rounds to 23¢. In `float64` the product is 22.499999999999996, which rounds to 22. Of the 100,000 prices from $0.01 to $1,000.00, 649 got the wrong cent.
4. **Silent.** None of these produced an error, a panic or a warning. The only way to find them is to reconcile against something exact.

### Step 3: the database does it too

Floats aren't a Go problem; they're the IEEE 754 standard every language and CPU uses. PostgreSQL's `double precision` is the same 64-bit float. Its `numeric` type is exact decimal:

```text
# PostgreSQL 14.19
$ psql -c "SELECT sum(0.10::double precision) FROM generate_series(1, 1000000)"
        sum         
--------------------
 100000.00000133288
$ psql -c "SELECT sum(0.10::numeric) FROM generate_series(1, 1000000)"
    sum    
-----------
 100000.00
$ psql -c "SELECT 0.1::double precision + 0.2::double precision = 0.3::double precision AS float_equal, 0.1::numeric + 0.2::numeric = 0.3::numeric AS numeric_equal"
 float_equal | numeric_equal 
-------------+---------------
 f           | t
$ psql -c "SELECT round(2.5::numeric) AS numeric_2_5, round(2.5::double precision) AS float_2_5, round(3.5::double precision) AS float_3_5"
 numeric_2_5 | float_2_5 | float_3_5 
-------------+-----------+-----------
           3 |         2 |         4
```

A million ten-cent rows summed as `double precision` come to 100000.00000133288; as `numeric`, exactly 100000.00. Note the last query too, which stop 3 comes back to: `round(2.5)` is 3 for `numeric` but 2 for `double precision`, which rounds halves to the even neighbour. Two roundings called `round`, in the same database, disagree.

## Minor Units

*Stop 2 of 6.*

### Step 1: count cents, not dollars

The fix is to stop using fractions at all. Every currency has a smallest unit it's accounted in, its **minor unit**: the cent for dollars and euros, the penny for pounds, the kobo for naira. Count those, as an integer, and addition, subtraction and comparison are exact, because integers are. $12.34 is `1234`. $1,000,000.00 is `100000000`.

An `int64` holds up to 9,223,372,036,854,775,807 minor units: about 92 quadrillion dollars in cents. Totals that could exceed that (never, for a real balance) can be checked, and `Add` below does.

### Step 2: the currency travels with the amount

A bare `1234` doesn't say whether it's dollars or yen, and adding 1234 dollar-cents to 1234 yen is a bug that type-checks. So the amount and its currency go together, in one type:

```go noverify
// money.go, lines 16–54
// Currency is an ISO 4217 currency and the number of decimal places its
// minor unit has.
type Currency struct {
	Code     string
	Exponent int
}

var (
	USD = Currency{"USD", 2}
	EUR = Currency{"EUR", 2}
	GBP = Currency{"GBP", 2}
	JPY = Currency{"JPY", 0}
	KWD = Currency{"KWD", 3}
	NGN = Currency{"NGN", 2}
)

type Money struct {
	Amount   int64 // minor units
	Currency Currency
}

var (
	ErrCurrencyMismatch = errors.New("currency mismatch")
	ErrOverflow         = errors.New("amount overflows int64 minor units")
)

func New(minor int64, c Currency) Money { return Money{minor, c} }

// Add returns m + o, refusing different currencies and overflow.
func (m Money) Add(o Money) (Money, error) {
	if m.Currency != o.Currency {
		return Money{}, fmt.Errorf("%w: %s + %s", ErrCurrencyMismatch, m.Currency.Code, o.Currency.Code)
	}
	sum := m.Amount + o.Amount
	if (o.Amount > 0 && sum < m.Amount) || (o.Amount < 0 && sum > m.Amount) {
		return Money{}, ErrOverflow
	}
	return Money{sum, m.Currency}, nil
}
```

`Add` refuses to mix currencies (an error you can test with `errors.Is(err, ErrCurrencyMismatch)`) and refuses to overflow. There's no `Mul(float64)`: multiplying money by a fraction needs a rounding decision, and stop 3 makes that explicit.

### Step 3: not every currency has cents

The number of decimal places, the currency's **exponent**, comes from the ISO 4217 standard, and it isn't always 2. The Unicode CLDR data (in `golang.org/x/text/currency`) has it, along with a second fact that matters for cash: the smallest amount you can actually pay with coins.

```go noverify
// iso prints, from the Unicode CLDR data in golang.org/x/text/currency,
// how many decimal places each currency uses, and the smallest amount you
// can actually pay in cash.
package main

import (
	"fmt"
	"math"

	"golang.org/x/text/currency"
)

func main() {
	fmt.Printf("%-4s %-9s %s\n", "", "decimals", "smallest cash amount")
	for _, code := range []string{"USD", "EUR", "GBP", "NGN", "JPY", "KWD", "BHD", "CLP", "CHF", "SEK", "HUF"} {
		u := currency.MustParseISO(code)
		scale, _ := currency.Standard.Rounding(u)
		cScale, cInc := currency.Cash.Rounding(u)
		step := fmt.Sprint(cInc)
		if cScale > 0 {
			step = fmt.Sprintf("%.*f", cScale, float64(cInc)/math.Pow10(cScale)) // display only
		}
		fmt.Printf("%-4s %-9d %s\n", code, scale, step)
	}
}
```

```text
     decimals  smallest cash amount
USD  2         0.01
EUR  2         0.01
GBP  2         0.01
NGN  2         0.01
JPY  0         1
KWD  3         0.001
BHD  3         0.001
CLP  0         1
```

The yen and the Chilean peso have no minor unit: an amount of yen is already a whole number. The Kuwaiti and Bahraini dinars have three decimals: 1 dinar is 1,000 fils. And cash can be coarser than accounts: Swiss prices are in centimes, but the smallest coin is 5 centimes, so cash totals round to 0.05; Sweden and Hungary have no coins below one krona or forint. That's why `Currency` carries its exponent, and why "multiply by 100" is a bug waiting for the first yen payment.

### Step 4: parsing, without a float in sight

Amounts arrive as text (`"12.34"` in an API request, a CSV file, a form field). Parsing them with `strconv.ParseFloat` and multiplying by 100 brings every stop-1 problem back. `Parse` splits on the decimal point and works in digits, and rejects anything with more decimals than the currency has:

```go noverify
// money.go, lines 177–195
// Parse reads a decimal amount like "1234.56" in currency c, exactly: no
// more decimal places than the currency has, and no float anywhere.
func Parse(s string, c Currency) (Money, error) {
	neg := strings.HasPrefix(s, "-")
	s = strings.TrimPrefix(s, "-")
	whole, frac, _ := strings.Cut(s, ".")
	if whole == "" || len(frac) > c.Exponent || strings.ContainsAny(whole+frac, "+-eE ") {
		return Money{}, fmt.Errorf("invalid %s amount %q", c.Code, s)
	}
	digits := whole + frac + strings.Repeat("0", c.Exponent-len(frac))
	n, ok := new(big.Int).SetString(digits, 10)
	if !ok || !n.IsInt64() {
		return Money{}, fmt.Errorf("invalid %s amount %q", c.Code, s)
	}
	if neg {
		n.Neg(n)
	}
	return Money{n.Int64(), c}, nil
}
```

`Parse("12.345", USD)` is an error, not 12.34 or 12.35: a third decimal on a dollar amount means something upstream is wrong, and guessing hides it. `Parse("15.5", JPY)` is an error too.

### Step 5: the wire

Part 1's HTTP chapter sent amounts as strings. Here's why, measured: a Go service sends a year's volume, in whole rupiah, to a JavaScript client, which parses JSON numbers into 64-bit floats:

```go
// jsonnum sends a large amount in minor units through JSON: to a
// JavaScript client (Node), and back into Go three ways.
package main

import (
	"bytes"
	"encoding/json"
	"fmt"
	"log"
	"os"
	"os/exec"
)

type Totals struct {
	Currency string `json:"currency"`
	Volume   int64  `json:"volume"` // this year's volume, counted in whole rupiah
}

func main() {
	t := Totals{Currency: "IDR", Volume: 9_007_199_254_740_993} // 2^53 + 1
	b, err := json.Marshal(t)
	if err != nil {
		log.Fatal(err)
	}
	fmt.Printf("Go sends:            %s\n", b)

	cmd := exec.Command("node", "-e", `
		let s = ""; process.stdin.on("data", d => s += d).on("end", () => {
			const t = JSON.parse(s);
			console.log("JavaScript reads:   volume =", t.volume, " (Number.isSafeInteger:", Number.isSafeInteger(t.volume) + ")");
			console.log("JavaScript sends:  ", JSON.stringify(t));
		});`)
	cmd.Stdin = bytes.NewReader(b)
	cmd.Stdout, cmd.Stderr = os.Stdout, os.Stderr
	if err := cmd.Run(); err != nil {
		log.Fatal(err)
	}

	var typed Totals
	_ = json.Unmarshal(b, &typed)
	fmt.Printf("Go into Totals:      %d\n", typed.Volume)

	var loose map[string]any
	_ = json.Unmarshal(b, &loose)
	fmt.Printf("Go into map[string]any: %T %.0f → int64 %d\n", loose["volume"], loose["volume"], int64(loose["volume"].(float64)))

	dec := json.NewDecoder(bytes.NewReader(b))
	dec.UseNumber()
	var num map[string]any
	_ = dec.Decode(&num)
	n, _ := num["volume"].(json.Number).Int64()
	fmt.Printf("Go with UseNumber:   %T %d\n", num["volume"], n)
}
```

```text
Go sends:            {"currency":"IDR","volume":9007199254740993}
JavaScript reads:   volume = 9007199254740992  (Number.isSafeInteger: false)
JavaScript sends:   {"currency":"IDR","volume":9007199254740992}
Go into Totals:      9007199254740993
Go into map[string]any: float64 9007199254740992 → int64 9007199254740992
Go with UseNumber:   json.Number 9007199254740993
```

9,007,199,254,740,993 is 2⁵³ + 1, the first integer a `float64` can't hold. JavaScript read it as ...992, and sent the wrong number back, without an error. Go has the same trap: decoding into `map[string]any` makes every number a `float64`. Decoding into a typed `int64` field, or with `UseNumber`, keeps it exact. Real balances are nowhere near 2⁵³ cents, but volumes, counters and currencies with many units per dollar get closer than you'd think, and the failure is silent. A string on the wire removes the question.

## Rounding

*Stop 3 of 6.*

### Step 1: some operations must round

Adding cents gives cents. Multiplying doesn't: a 2.9% card fee on $19.99 is 57.971 cents, and a ledger can only hold whole cents. So the result has to be rounded, and there's no way around it. What you can control is **how often** it happens (once per operation, at the end), **how exactly** (from the true result, not a float approximation of it), and **which way** (a mode you chose on purpose).

### Step 2: the modes

With an exact result between two cents, the rounding mode decides:

- **Half up** (half away from zero): 22.5 → 23, and −22.5 → −23. What most people learned at school. The EU's rules for converting to and from the euro (Council Regulation 1103/97, Article 5) require it: round to the nearest cent, and exact halves round up.
- **Half even** ("banker's rounding"): 22.5 → 22, 23.5 → 24; halves go to the even neighbour. Over many roundings, half the halves go up and half go down, so the total doesn't drift upwards. It's IEEE 754's default rounding for floats, which is why PostgreSQL's `round(2.5::double precision)` gave 2 in stop 1.
- **Down** (truncate toward zero): 57.971 → 57. Used where the rule is "never charge more than", for example some interest and tax calculations.

Which mode is right isn't a programming question. It's written in a contract, a card network's rules, a tax authority's guidance or a regulation, and it can differ per operation. The code's job is to make the mode an explicit argument, never an accident.

### Step 3: exact, then round once

`MulRat` multiplies an amount by a fraction `num/den` (2.9% is 29/1000; 7.5% is 75/1000) using exact integer arithmetic, then rounds once, in the mode passed in:

```go noverify
// money.go, lines 56–99
// RoundingMode says what to do with an exact result that falls between
// two minor units.
type RoundingMode int

const (
	HalfEven RoundingMode = iota // banker's rounding: ties to the even unit
	HalfUp                       // ties away from zero
	Down                         // toward zero (truncate)
)

// MulRat returns m × num/den, rounded to a minor unit with mode. The
// multiplication is exact (math/big), so the only rounding is the one
// you asked for.
func (m Money) MulRat(num, den int64, mode RoundingMode) (Money, error) {
	if den == 0 {
		return Money{}, errors.New("zero denominator")
	}
	if q, ok := mulRatInt64(m.Amount, num, den, mode); ok {
		return Money{q, m.Currency}, nil
	}
	p := new(big.Int).Mul(big.NewInt(m.Amount), big.NewInt(num))
	d := big.NewInt(den)
	if d.Sign() < 0 {
		p.Neg(p)
		d.Neg(d)
	}
	q, r := new(big.Int).QuoRem(p, d, new(big.Int)) // q truncated toward zero
	if r.Sign() != 0 && mode != Down {
		twice := new(big.Int).Abs(r)
		twice.Lsh(twice, 1)
		switch c := twice.Cmp(d); {
		case c > 0, c == 0 && mode == HalfUp, c == 0 && mode == HalfEven && q.Bit(0) == 1:
			if p.Sign() < 0 {
				q.Sub(q, big.NewInt(1))
			} else {
				q.Add(q, big.NewInt(1))
			}
		}
	}
	if !q.IsInt64() {
		return Money{}, ErrOverflow
	}
	return Money{q.Int64(), m.Currency}, nil
}
```

The product is computed with `math/big`, so there's no intermediate rounding at all: the quotient and remainder of `amount × num / den` are exact, and the remainder alone decides the rounding. Twice the remainder compared with the denominator says whether the result is below, at, or above the halfway point.

### Step 4: making it fast

The first version of `MulRat` was just the `big.Int` code above. It was correct, and it allocated: 7 times, 176 bytes, 104.8 ns per call. For any real amount and rate the product fits in 64 bits, so `MulRat` now tries a fast path first, which multiplies with `bits.Mul64` (a 128-bit product, so it can see whether the result overflowed) and falls back to `big.Int` only when it did:

```go noverify
// money.go, lines 101–126
// mulRatInt64 is MulRat's fast path: exact integer arithmetic when the
// product fits in an int64, which it does for any real-world amount and
// rate. It reports false when it doesn't, and MulRat falls back to big.Int.
func mulRatInt64(a, num, den int64, mode RoundingMode) (int64, bool) {
	if a == math.MinInt64 || num == math.MinInt64 || den == math.MinInt64 {
		return 0, false
	}
	hi, lo := bits.Mul64(uint64(abs(a)), uint64(abs(num)))
	if hi != 0 || lo > math.MaxInt64 {
		return 0, false
	}
	p := int64(lo)
	neg := (a < 0) != (num < 0) != (den < 0)
	d := abs(den)
	q, r := p/d, p%d
	if r != 0 && mode != Down {
		switch {
		case 2*r > d, 2*r == d && mode == HalfUp, 2*r == d && mode == HalfEven && q%2 == 1:
			q++
		}
	}
	if neg {
		q = -q
	}
	return q, true
}
```

### Step 1: parts that don't add up

Meridian splits settlements: a marketplace payment divides between the platform, the seller and a delivery partner, in proportion to agreed weights. The obvious code computes each share and rounds it:

```go noverify
package money

import "math"

// allocateFloat is how allocation is often first written: each part is
// its share, computed in float64 and rounded. The chapter fuzzes it.
func allocateFloat(amount int64, ratios ...int64) []int64 {
	var total int64
	for _, r := range ratios {
		total += r
```

### Step 2: largest remainder

The fix is to hand out the rounding explicitly. Give every part its share rounded down (the floor); count how many units are left over (always fewer than the number of parts); give one extra unit to each of the parts that were rounded down the most, meaning the ones with the largest remainders:

```go noverify
// money.go, lines 128–168
// Allocate splits m in proportion to ratios, so the parts add up exactly
// to m: each part gets its floor share, and the leftover minor units go,
// one each, to the parts with the largest remainders.
func (m Money) Allocate(ratios ...int64) ([]Money, error) {
	var total int64
	for _, r := range ratios {
		if r < 0 {
			return nil, errors.New("negative ratio")
		}
		total += r
	}
	if total == 0 {
		return nil, errors.New("ratios sum to zero")
	}
	parts := make([]Money, len(ratios))
	rems := make([]int64, len(ratios))
	var given int64
	for i, r := range ratios {
		p := new(big.Int).Mul(big.NewInt(m.Amount), big.NewInt(r))
		q, rem := new(big.Int).QuoRem(p, big.NewInt(total), new(big.Int))
		parts[i] = Money{q.Int64(), m.Currency}
		rems[i] = rem.Int64()
		given += q.Int64()
	}
	left := m.Amount - given // how many minor units are still to hand out
	step := int64(1)
	if left < 0 {
		step = -1
	}
	for ; left != 0; left -= step {
		best := -1
		for i := range rems {
			if rems[i] != math.MinInt64 && (best < 0 || abs(rems[i]) > abs(rems[best])) {
				best = i
			}
		}
		parts[best].Amount += step
		rems[best] = math.MinInt64 // one extra unit each
	}
	return parts, nil
}
```

For $100.00 in three equal parts: 33.33 each, one cent left, which goes to the first: 33.34, 33.33, 33.33. Every part is within one unit of its exact share, and the sum is always exact.

## Decimal Libraries

*Stop 5 of 6.*

### Step 1: what they are

A **decimal** type stores a number as an integer and a power of ten: 19.99 is 1999 × 10⁻², and 0.029 is 29 × 10⁻³. Like minor units, it's exact for decimal fractions; unlike minor units, the scale is per value, so it can hold a rate like 0.029, a unit price of $0.004 per API call, or a crypto amount with 18 decimals. Go's standard library has none (only `math/big`'s `Int`, `Float` and `Rat`), so they come from modules. The two most used are `shopspring/decimal` and CockroachDB's `apd`, which implements the General Decimal Arithmetic specification.

```go noverify
// rate parses "1.0856" into 10856/10000: exact.
func rate(s string) (num, den int64) {
	whole, frac, _ := strings.Cut(s, ".")
	den = 1
	for range frac {
		den *= 10
	}
	var n big.Int
	n.SetString(whole+frac, 10)
	return n.Int64(), den
}

// convert moves m into currency to at "1 EUR = eurTo[to] units", via EUR.
// perEUR[c] is the ECB rate for c as num/den (EUR itself is 1/1).
func convert(m money.Money, to money.Currency, perEUR map[string][2]int64) money.Money {
	from := perEUR[m.Currency.Code]
	target := perEUR[to.Code]
	// amount_to = amount_from / from × target, adjusted for the two exponents,
	// computed as one exact fraction and rounded once.
	num := new(big.Int).Mul(big.NewInt(from[1]), big.NewInt(target[0]))
	den := new(big.Int).Mul(big.NewInt(from[0]), big.NewInt(target[1]))
	shift := to.Exponent - m.Currency.Exponent
	for ; shift > 0; shift-- {
		num.Mul(num, big.NewInt(10))
	}
	for ; shift < 0; shift++ {
		den.Mul(den, big.NewInt(10))
	}
	out, err := money.New(m.Amount, to).MulRat(num.Int64(), den.Int64(), money.HalfEven)
	if err != nil {
		log.Fatal(err)
	}
	return out
}
```

### Step 2: never convert back

Rounding to the target currency loses information, so converting back doesn't return the original amount. For every amount from $0.01 to $100.00, a round trip through euros came back different **1,230 times out of 10,000**. $0.04 became €0.04 (really €0.0351, rounded) and then $0.05: a cent created from rounding alone.

That's why a payment in one currency and a payout in another are recorded as two amounts, each in its own currency, with the rate that linked them, and nothing is ever re-derived by converting back. A refund of a converted payment refunds the original amount in the original currency; if the rate has moved since, the difference is a gain or loss that the ledger records explicitly (the next chapter's double-entry ledger has an account for it), not a rounding error nobody sees.

### Step 3: what gets stored

A conversion is a fact to record, not a computation to repeat: the source amount and currency, the target amount and currency, the rate as an exact decimal, its source (ECB, a card network, a provider's quote) and the time it applied. With those, any figure can be audited later; without them, a rate that changed overnight makes yesterday's payouts impossible to explain.

<Exercise n={1} title="Subtract, Neg and Cmp" level="easy">

Add `Sub`, `Neg` and `Cmp` to `Money`, with the same currency and overflow checks as `Add`. What's special about negating `math.MinInt64`?

<Solution>

`Sub` is `Add` of the negation, but only if negating is safe: `-math.MinInt64` overflows back to `math.MinInt64` in two's complement, so `Neg` must return `ErrOverflow` for it (and `Sub` must check it, or subtract directly with its own overflow test). `Cmp` returns -1, 0 or 1 and an error for mismatched currencies: comparing $5 with ¥5 is as meaningless as adding them.

</Solution>

</Exercise>

<Exercise n={2} title="Cash rounding" level="easy">

Add `RoundCash(m Money, increment int64, mode RoundingMode)` that rounds to a multiple of `increment` minor units (5 for Swiss francs in cash). Use it on CHF 12.37 and CHF 12.38.

<Solution>

Divide by the increment with `MulRat(1, increment, mode)`, then multiply the result by the increment. CHF 12.37 (1237 centimes) is 247.4 increments, so half-up gives 247 × 5 = CHF 12.35; 12.38 is 247.6 increments, so 248 × 5 = CHF 12.40. Like any rounding, the difference belongs in the ledger (a cash rounding account), not nowhere.

</Solution>

</Exercise>

<Exercise n={3} title="Store it in Postgres" level="medium">

Write a `Money` column pair (`amount_minor bigint`, `currency char(3)`) and implement `sql.Scanner` and `driver.Valuer` on a type that reads and writes both. Why not one `numeric` column?

<Solution>

A `numeric` holds the amount but not the currency, and it invites arithmetic in SQL that rounds with PostgreSQL's rules rather than yours. Two columns keep the pair together and the arithmetic in the `Money` type. Add a `CHECK (currency ~ '^[A-Z]{3}$')`, and never `SUM(amount_minor)` across currencies: group by currency first.

</Solution>

</Exercise>

<Exercise n={4} title="JSON as a string" level="medium">

Implement `MarshalJSON` and `UnmarshalJSON` for `Money` as `{"amount":"12.34","currency":"USD"}`, using `String` and `Parse`. Test it with JPY and KWD amounts and a negative amount under one unit.

<Solution>

Marshal writes the amount formatted with the currency's exponent (`"1500"` for JPY, `"1.234"` for KWD); unmarshal reads the currency first, then parses the amount with it, so `"12.345"` in USD is rejected rather than rounded. The negative case (`-5` cents must be `"-0.05"`) is the bug part 1's HTTP chapter found in its first `Money` type: format the sign separately from the digits.

</Solution>

</Exercise>

<Exercise n={5} title="Fair rotation" level="hard">

A merchant's monthly platform fee of $100.00 is split between three partners with equal weights, every month. `Allocate` always gives the extra cent to the first. Change it (or wrap it) so that over three months each partner gets the extra cent once, and prove it with a test.

<Solution>

Make the tie-break a parameter: an offset that rotates the order in which equal remainders are considered (partner `(i + offset) % n` first). Pass the month number as the offset. The test allocates for months 0, 1 and 2 and checks each partner's total is exactly 100.00 over the three months (33.34 + 33.33 + 33.33), and that the sum is exact every month. The general lesson: the leftover units are a decision, and whoever decides it should be visible in the code.

</Solution>

</Exercise>

<Recap>

- **float64 is a binary fraction**: 0.1 is stored as 0.1000000000000000055…, and every operation rounds again. Measured: ten million $0.10 fees drifted $0.00016; summing the same payments in a different order changed the total; 649 of 100,000 VAT amounts got the wrong cent. PostgreSQL's `double precision` does the same; `numeric` doesn't.
- **Minor units**: store an integer count of the currency's smallest unit, with the currency attached. Exponents differ (JPY 0, KWD 3), cash can round coarser (CHF 0.05), and parsing goes through digits, never a float. On the wire, send strings: JavaScript turned 2⁵³ + 1 into 2⁵³.
- **Rounding**: multiply exactly, round once, in a mode chosen on purpose (half-up for euro conversions by law, half-even to avoid drift, down where you mustn't overcharge). `MulRat`'s fast path runs in 4.5 ns with no allocations, fuzzed against exact rationals 8.9 million times.
- **Splitting**: rounding each part separately loses or invents units (the fuzzer found 67¢ → 66¢ in six tries). Largest remainder hands out the leftovers explicitly and survived 11.9 million fuzz inputs.
- **Decimal libraries**: exact, with a scale per value; right for rates and sub-cent prices. 130 to 362 ns per fee against 2 to 5 ns for integers.
- **Currencies**: convert with exact rates, round once to the target's exponent, record both amounts and the rate, and never convert back: 1,230 of 10,000 round trips changed the amount.

</Recap>
