**What this service is.** Before a line of code, here is the whole product in one sentence:

> Meridian's payments service moves money between accounts and records every movement in an immutable double-entry ledger so the books always balance — and it does so safely under concurrent load, with retries, and without ever charging twice.

That sentence hides four hard problems. The next four definitions unpack them. A reader who can state all four is ready to build this.

<Define term="Payments & Ledger Service" since="Double-Entry Ledgers (Part 3), Idempotency & Exactly-Once Semantics (Part 3)">
A **payments service** moves money between accounts on behalf of users or other services — it validates, authorises, and records transfers. A **ledger service** records every monetary movement as an immutable, append-only history using double-entry bookkeeping. Together they form the financial core of Meridian: the payments service is the write path (accept a transfer, debit one account, credit another, emit an event); the ledger is the permanent, auditable record that those balances were ever moved. If the ledger and the actual bank balance ever diverge, you have a compliance failure. This service prevents that.
</Define>

<Define term="Idempotency / Idempotency Key" since="Idempotency & Exactly-Once Semantics (Part 3), Auth & API Design (Part 1)">
An operation is **idempotent** if doing it twice has the same effect as doing it once. A payment transfer must be idempotent because networks fail and clients retry: if a client sends a `POST /transfers` and the response never arrives, it will retry — and without idempotency the server charges twice, **creating money from nothing**. An **idempotency key** is a unique string the client generates per logical operation (e.g. `"pay-order-7f3a"`). The server records the key on first execution and on any retry returns the cached result without re-executing. The key deduplicates retried requests at the server so a retried transfer charges exactly once, regardless of how many times the request arrives.
</Define>

<Define term="Double-Entry Ledger" since="Double-Entry Ledgers (Part 3)">
In double-entry bookkeeping, **every transfer posts two entries**: a debit (money leaving an account) and an equal-sized credit (money entering another account) that sum to zero. If Alice sends $50 to Bob, the ledger records `Debit $50 from Alice` and `Credit $50 to Bob` — a net change of zero across all accounts. The invariant — **all entries always sum to zero** — means the books must always balance. The ledger is append-only and immutable: no entry is ever deleted or updated. This is how Meridian proves to regulators and to itself that no money was created or destroyed.
</Define>

<Define term="Kafka" since="Event-Driven Architecture & Kafka (Part 3), Watermill — Event-Driven Go in Practice (Part 3)">
**Kafka** is a distributed, partitioned, append-only event log. Producers publish messages to named **topics** (e.g. `transfer.completed`). Each topic is divided into **partitions** — the unit of ordering and parallelism. Within a partition, messages are strictly ordered by offset. **Consumer groups** allow multiple service instances to share the work of consuming a topic: each partition is assigned to exactly one consumer in the group at a time, giving per-partition ordering guarantees. We key transfer events by account ID so all events for one account land on the same partition and are processed in order. Kafka is the async backbone between Meridian's write path (the transfer use case) and read models (the balance projection).
</Define>

<Define term="Transactional Outbox" since="Idempotency & Exactly-Once Semantics (Part 3), Watermill — Event-Driven Go in Practice (Part 3)">
The **dual-write problem**: if you commit to the database and then publish to Kafka in two separate operations, a crash between them leaves one done and the other not — the ledger and the event log diverge. The **transactional outbox** solves this: write the event into an `outbox` table in the **same DB transaction** as the business change. Either both commit or neither does. A separate relay process polls the outbox and publishes unpublished rows to Kafka, then marks them published. The event is guaranteed to be published **at least once** — and idempotent consumers handle the rare duplicate. No distributed transaction required.
</Define>

<Define term="gRPC" since="gRPC & Service-to-Service Communication (Part 2)">
**gRPC** is a schema-first, high-performance RPC framework that runs over HTTP/2 and uses Protocol Buffers (protobuf) for serialisation. You define the service contract in a `.proto` file; code generation produces type-safe client and server stubs. Service-to-service calls use gRPC because it is faster than JSON/REST, gives you generated types on both sides, and carries deadlines and cancellation automatically over the wire. Meridian's internal services call the payments service over gRPC; the public edge uses HTTP/JSON.
</Define>

<Define term="Watermill" since="Watermill — Event-Driven Go in Practice (Part 3)">
**Watermill** is a Go messaging library that decouples your application logic from the broker. You write `Publisher` and `Subscriber` interfaces; Watermill supplies implementations for Kafka, RabbitMQ, in-memory channels, and others. You swap the backend by changing one line of wiring — the router, middleware, and handler code stay the same. In this service, Watermill's Kafka publisher is what the outbox relay calls to push events; the `GoChannel` publisher is used in tests, giving identical logic without a real broker.
</Define>

## Domain & Money

Before a single byte hits a database, we model the domain. Get this wrong and every layer built on top is lies. Get it right and the compiler enforces the invariants that keep your users from losing money. *(Representing Money — Never Use Floats; Double-Entry Ledgers — Part 3)*

**On the job:** a domain model with floating-point money or mutable `Transaction` values will produce balance discrepancies that appear only at scale — intermittent, hard to reproduce, and career-limiting to explain to a regulator.

**The project layout.** Here is what we're building toward:

```
cmd/
  server/         main.go — wires everything, starts gRPC + HTTP
internal/
  domain/         Money, Account, Transaction, Entry (pure domain, zero deps)
  repository/     Postgres-backed store (interface + pgx impl)
  usecase/        TransferUseCase — the idempotent transfer orchestrator
  grpcapi/        gRPC server implementation + proto
  httpapi/        HTTP/JSON edge + middleware
  messaging/      Watermill router, outbox relay, ledger-projection consumer
  observability/  slog setup, Prometheus metrics
  ratelimit/      per-account token-bucket limiter
migrations/       .sql files managed by golang-migrate
```

**Why `internal/domain` has zero deps.** The domain package imports nothing outside the standard library. No database drivers. No gRPC. No Kafka. Pure Go types and pure invariants. The outside world adapts to the domain — not the other way around. That's ports-and-adapters (Software Design & Architecture — Part 1) enforced at the package boundary by the Go toolchain itself.

### Money: integer cents, never float

<Define term="Money as Integer Cents" since="Representing Money — Never Use Floats (Part 3)">
A `float64` cannot exactly represent most decimal fractions. `0.1 + 0.2` in floating-point is `0.30000000000000004` — not `0.30`. In a ledger, rounding errors **accumulate across millions of transactions** and your books no longer balance. The fix is simple: store money as an **integer count of the smallest currency unit** (`int64` cents for USD, pence for GBP, etc.). `$10.50` is stored as `1050`. There is no rounding; there is no approximation. Integer arithmetic is exact. Every monetary value in Meridian is an `int64` count of cents. Not once, not ever, a float.
</Define>

The rule from Representing Money — Never Use Floats (Part 3), enforced forever:

```go
// internal/domain/money.go

// Money is an immutable value type representing an amount in the smallest
// unit of a currency (e.g. USD cents, EUR cents, GBP pence).
// It is ALWAYS stored as an integer. Never a float. Not once. Never.
type Money struct {
	Amount   int64  // e.g. 1050 for $10.50
	Currency string // ISO 4217, e.g. "USD"
}

// Add returns a new Money summing m and other.
// Panics on currency mismatch — callers must enforce homogeneity upstream.
func (m Money) Add(other Money) Money {
	if m.Currency != other.Currency {
		panic("currency mismatch: " + m.Currency + " vs " + other.Currency)
	}
	return Money{Amount: m.Amount + other.Amount, Currency: m.Currency}
}

// Negate returns the additive inverse (for double-entry credit/debit pairs).
func (m Money) Negate() Money {
	return Money{Amount: -m.Amount, Currency: m.Currency}
}

// IsZero reports whether the amount is exactly zero.
func (m Money) IsZero() bool { return m.Amount == 0 }

// String formats for display only — never parse this back to Money.
func (m Money) String() string {
	abs := m.Amount
	if abs < 0 {
		abs = -abs
	}
	sign := ""
	if m.Amount < 0 {
		sign = "-"
	}
	return fmt.Sprintf("%s%s %d.%02d", sign, m.Currency, abs/100, abs%100)
}
```

<Callout kind="warn" title="Money.String() is display only">
Never parse `Money.String()` back to a `Money` value. That path runs through string formatting and loses precision. Persist `Amount int64` and `Currency string` in the database directly. Display the formatted string only in logs and UI.
</Callout>

### Transaction and Entry: the double-entry invariant

This is the heart. A `Transaction` contains two or more `Entry` values. The invariant: **every transaction must sum to zero**. A debit of $100 from account A creates an equal and opposite credit of $100 to account B. The books always balance. (Double-Entry Ledgers — Part 3)

```go
// internal/domain/ledger.go

type EntryID      string
type TransactionID string

// EntryType distinguishes debits from credits.
type EntryType string

const (
	Debit  EntryType = "debit"
	Credit EntryType = "credit"
)

// Entry is one side of a double-entry posting.
type Entry struct {
	ID            EntryID
	TransactionID TransactionID
	AccountID     AccountID
	Type          EntryType
	Amount        Money
	CreatedAt     time.Time
}

// Transaction is an atomic, balanced double-entry posting.
// Construct only via NewTransaction to enforce the balance invariant.
type Transaction struct {
	ID        TransactionID
	Entries   []Entry
	Memo      string
	CreatedAt time.Time
}

// ErrUnbalanced is returned when a transaction does not sum to zero.
var ErrUnbalanced = errors.New("transaction entries do not sum to zero")

// NewTransaction validates and creates a Transaction.
// It enforces the double-entry invariant: all entries must sum to zero
// when debits are positive and credits are negative.
func NewTransaction(id TransactionID, memo string, entries []Entry) (Transaction, error) {
	if len(entries) < 2 {
		return Transaction{}, errors.New("a transaction requires at least two entries")
	}
	byCurrency := make(map[string]int64)
	for _, e := range entries {
		switch e.Type {
		case Debit:
			byCurrency[e.Amount.Currency] += e.Amount.Amount
		case Credit:
			byCurrency[e.Amount.Currency] -= e.Amount.Amount
		default:
			return Transaction{}, fmt.Errorf("unknown entry type: %s", e.Type)
		}
	}
	for cur, sum := range byCurrency {
		if sum != 0 {
			return Transaction{}, fmt.Errorf("%w: %s imbalance %d", ErrUnbalanced, cur, sum)
		}
	}
	return Transaction{
		ID:        id,
		Entries:   entries,
		Memo:      memo,
		CreatedAt: time.Now().UTC(),
	}, nil
}
```

<UnderTheHood title="Why enforce at construction, not at persistence?">

You could check the balance invariant in the repository layer — right before the `INSERT`. Many systems do. But that means every layer *above* the repository can hold an unbalanced `Transaction` in memory and believe it's valid. A function returns it; another function passes it; a bug upstream creates an imbalance that isn't caught until the database call, buried under a stack trace.

Enforcing in `NewTransaction` makes an unbalanced transaction **unrepresentable as a Go value**. You cannot have one. The type system closes the hole. This is the "make illegal states unrepresentable" principle from functional programming, and Go's value types make it cheap. The repository's job shrinks to *persisting* the invariant, not *discovering* its violation.

As of Go 1.26, there's no compiler-level dependent typing, so `NewTransaction` returning `error` is the idiomatic gate. The key is that the public `Transaction` type has no exported constructor other than `NewTransaction` — outside the `domain` package, there's no way to build one without passing the check.

</UnderTheHood>

```go
package main

import (
	"errors"
	"fmt"
	"sync"
	"time"
)

// ── Money ──────────────────────────────────────────────────────────────────

type Money struct {
	Amount   int64
	Currency string
}

func USD(cents int64) Money { return Money{Amount: cents, Currency: "USD"} }

func (m Money) Add(other Money) Money {
	if m.Currency != other.Currency {
		panic("currency mismatch")
	}
	return Money{Amount: m.Amount + other.Amount, Currency: m.Currency}
}

func (m Money) Negate() Money { return Money{Amount: -m.Amount, Currency: m.Currency} }
func (m Money) IsZero() bool  { return m.Amount == 0 }

func (m Money) String() string {
	abs := m.Amount
	if abs < 0 {
		abs = -abs
	}
	sign := ""
	if m.Amount < 0 {
		sign = "-"
	}
	return fmt.Sprintf("%sUSD %d.%02d", sign, abs/100, abs%100)
}

// ── Domain types ──────────────────────────────────────────────────────────

type AccountID      string
type TransactionID  string
type EntryType      string

const (
	Debit  EntryType = "debit"
	Credit EntryType = "credit"
)

type Entry struct {
	AccountID AccountID
	Type      EntryType
	Amount    Money
}

type Transaction struct {
	ID      TransactionID
	Entries []Entry
	Memo    string
	At      time.Time
}

var ErrUnbalanced = errors.New("transaction does not sum to zero")

func NewTransaction(id TransactionID, memo string, entries []Entry) (Transaction, error) {
	if len(entries) < 2 {
		return Transaction{}, errors.New("need at least two entries")
	}
	var sum int64
	cur := entries[0].Amount.Currency
	for _, e := range entries {
		if e.Amount.Currency != cur {
			return Transaction{}, errors.New("mixed currencies in one transaction")
		}
		switch e.Type {
		case Debit:
			sum += e.Amount.Amount
		case Credit:
			sum -= e.Amount.Amount
		}
	}
	if sum != 0 {
		return Transaction{}, fmt.Errorf("%w: residual %d", ErrUnbalanced, sum)
	}
	return Transaction{ID: id, Entries: entries, Memo: memo, At: time.Now().UTC()}, nil
}

// ── In-memory idempotent ledger ───────────────────────────────────────────

type Ledger struct {
	mu       sync.Mutex
	balances map[AccountID]int64
	seen     map[string]struct{} // idempotency keys
	txns     []Transaction
}

func NewLedger(accounts map[AccountID]int64) *Ledger {
	bal := make(map[AccountID]int64, len(accounts))
	for id, v := range accounts {
		bal[id] = v
	}
	return &Ledger{balances: bal, seen: make(map[string]struct{})}
}

// Transfer posts a balanced double-entry transaction.
// idempotencyKey makes repeat calls a no-op.
func (l *Ledger) Transfer(ikey string, from, to AccountID, amount Money) error {
	l.mu.Lock()
	defer l.mu.Unlock()

	if _, dup := l.seen[ikey]; dup {
		return nil // already applied — idempotent
	}
	entries := []Entry{
		{AccountID: from, Type: Debit, Amount: amount},
		{AccountID: to, Type: Credit, Amount: amount},
	}
	tx, err := NewTransaction(TransactionID(ikey), "transfer", entries)
	if err != nil {
		return err
	}
	// Apply atomically: debit sender, credit receiver.
	if l.balances[from] < amount.Amount {
		return fmt.Errorf("insufficient funds: %s has %d cents", from, l.balances[from])
	}
	l.balances[from] -= amount.Amount
	l.balances[to] += amount.Amount
	l.txns = append(l.txns, tx)
	l.seen[ikey] = struct{}{}
	return nil
}

// TotalAssets sums all balances — must equal the initial total always.
func (l *Ledger) TotalAssets() int64 {
	l.mu.Lock()
	defer l.mu.Unlock()
	var total int64
	for _, b := range l.balances {
		total += b
	}
	return total
}

// ── Race test: N concurrent transfers, books must balance ─────────────────

func main() {
	const (
		initialAlice = int64(100_000) // $1,000.00
		initialBob   = int64(100_000)
		transfers    = 200
		amountCents  = int64(100) // $1.00
	)

	ledger := NewLedger(map[AccountID]int64{
		"alice": initialAlice,
		"bob":   initialBob,
	})
	startTotal := ledger.TotalAssets()

	// wg.Go is new in Go 1.25: spawns a goroutine and calls wg.Add(1) atomically.
	// The loop variable capture is safe since Go 1.22 (each iteration gets its own i).
	var wg sync.WaitGroup
	for i := range transfers {
		wg.Go(func() {
			key := fmt.Sprintf("alice-to-bob-%d", i)
			if err := ledger.Transfer(key, "alice", "bob", USD(amountCents)); err != nil {
				// Insufficient funds is expected when racing — not a bug.
				_ = err
			}
		})
		wg.Go(func() {
			key := fmt.Sprintf("bob-to-alice-%d", i)
			if err := ledger.Transfer(key, "bob", "alice", USD(amountCents)); err != nil {
				_ = err
			}
		})
	}
	wg.Wait()

	endTotal := ledger.TotalAssets()
	if endTotal != startTotal {
		fmt.Printf("INVARIANT VIOLATED: started %d cents, ended %d cents\n",
			startTotal, endTotal)
		return
	}
	fmt.Printf("All %d concurrent transfers completed.\n", transfers*2)
	fmt.Printf("Total assets: %d cents (unchanged from %d). Books balance.\n",
		endTotal, startTotal)
}
```

### The repository interface

### SELECT FOR UPDATE: the concurrent-transfer safety net

<Define term="Pessimistic Locking / SELECT FOR UPDATE" since="Transactions, Consistency & Sagas (Part 3)">
**Pessimistic locking** assumes conflict is likely and acquires a lock *before* reading the data. In Postgres, `SELECT ... FOR UPDATE` locks the selected rows for the duration of the enclosing transaction: any other transaction that tries to `SELECT ... FOR UPDATE` the same rows must wait. The alternative — **optimistic locking** — reads without a lock and checks at write time whether a concurrent writer changed the data (via a version counter), retrying on conflict. For Meridian's transfers we use pessimistic locking: two transfers on the same account are a guaranteed conflict, and the retry cost of optimistic locking is higher than the wait cost of a short row lock.

**On the job:** a missing lock here causes a **lost update** — two goroutines read the same stale balance, both decide the sender has enough funds, and both debit. The account goes negative. Real money is lost.
</Define>

Two transfers hitting the same account simultaneously is the classic fintech race. Thread A reads the balance, Thread B reads the balance, both compute the new balance from the stale read, and one transfer disappears. `SELECT ... FOR UPDATE` prevents it: the first transaction locks the row; the second blocks until the first commits or rolls back. (Transactions, Consistency & Sagas — Part 3)

```go
// internal/repository/postgres.go (excerpt)

func (r *pgxRepo) GetAccount(
	ctx context.Context,
	tx pgx.Tx,
	id AccountID,
	forUpdate bool,
) (Account, error) {
	q := `SELECT id, name FROM accounts WHERE id = $1`
	if forUpdate {
		q += ` FOR UPDATE` // locks this row for the duration of tx
	}
	var acc Account
	row := tx.QueryRow(ctx, q, string(id))
	if err := row.Scan(&acc.ID, &acc.Name); err != nil {
		if errors.Is(err, pgx.ErrNoRows) {
			return Account{}, fmt.Errorf("account %s: %w", id, ErrNotFound)
		}
		return Account{}, fmt.Errorf("GetAccount: %w", err)
	}
	return acc, nil
}
```

## The Transfer Use Case

The use case is where business rules live. It owns the transaction boundary and orchestrates: idempotency check → lock accounts → validate funds → post double-entry → write outbox event. All in one DB transaction. If anything fails, Postgres rolls back — nothing is partially applied. *(Idempotency & Exactly-Once Semantics, Auditability & Compliance — Part 3)*

<Define term="Saga / Compensating Action" since="Transactions, Consistency & Sagas (Part 3)">
A **saga** is a sequence of local transactions where each step is individually committed. If a later step fails, you undo the earlier steps by running **compensating actions** — inverse operations (e.g. if step 2 of a cross-border payment fails after step 1 debited the sender, a compensating action re-credits the sender). Sagas are used when a single atomic DB transaction cannot span the whole operation (e.g. when two services each own their own database). Meridian's single-service transfer fits inside one Postgres transaction and does not need a saga — but if the transfer involved an external payment rail, each leg would be a separate saga step with a compensating action ready to fire on failure.
</Define>

```go
// internal/usecase/transfer.go

type TransferRequest struct {
	IdempotencyKey string
	FromAccount    AccountID
	ToAccount      AccountID
	Amount         Money
	Memo           string
}

type TransferResult struct {
	TransactionID TransactionID
	Duplicate     bool // true if the key was already processed
}

type TransferUseCase struct {
	repo   LedgerRepository
	outbox OutboxWriter
	log    *slog.Logger
}

func NewTransferUseCase(repo LedgerRepository, outbox OutboxWriter, log *slog.Logger) *TransferUseCase {
	return &TransferUseCase{repo: repo, outbox: outbox, log: log}
}

// Execute runs a single idempotent transfer.
// It is safe to call concurrently and safe to retry with the same IdempotencyKey.
func (uc *TransferUseCase) Execute(ctx context.Context, req TransferRequest) (TransferResult, error) {
	dbTx, err := uc.repo.BeginTx(ctx)
	if err != nil {
		return TransferResult{}, fmt.Errorf("begin tx: %w", err)
	}
	defer func() {
		// Rollback is a no-op after commit. Always safe to defer.
		if rb := dbTx.Rollback(ctx); rb != nil && !errors.Is(rb, pgx.ErrTxClosed) {
			uc.log.ErrorContext(ctx, "rollback failed", "err", rb)
		}
	}()

	// 1. Idempotency: record the key atomically. Returns ErrDuplicate if seen before.
	if err := uc.repo.MarkIdempotencyKey(ctx, dbTx, req.IdempotencyKey); err != nil {
		if errors.Is(err, ErrDuplicate) {
			if err2 := dbTx.Commit(ctx); err2 != nil {
				return TransferResult{}, fmt.Errorf("commit (dup): %w", err2)
			}
			return TransferResult{Duplicate: true}, nil
		}
		return TransferResult{}, fmt.Errorf("idempotency key: %w", err)
	}

	// 2. Lock both accounts (always in a deterministic order to avoid deadlocks).
	ids := []AccountID{req.FromAccount, req.ToAccount}
	if req.FromAccount > req.ToAccount {
		ids[0], ids[1] = ids[1], ids[0]
	}
	for _, id := range ids {
		if _, err := uc.repo.GetAccount(ctx, dbTx, id, true /*forUpdate*/); err != nil {
			return TransferResult{}, fmt.Errorf("lock account %s: %w", id, err)
		}
	}

	// 3. Validate funds (by summing entries — authoritative balance).
	senderBal, err := uc.repo.GetBalance(ctx, req.FromAccount)
	if err != nil {
		return TransferResult{}, fmt.Errorf("get balance: %w", err)
	}
	if senderBal.Amount < req.Amount.Amount {
		return TransferResult{}, fmt.Errorf("insufficient funds: have %s, need %s",
			senderBal, req.Amount)
	}

	// 4. Build and validate the double-entry transaction.
	txID := TransactionID("txn-" + req.IdempotencyKey)
	entries := []Entry{
		{AccountID: req.FromAccount, Type: Debit, Amount: req.Amount},
		{AccountID: req.ToAccount, Type: Credit, Amount: req.Amount},
	}
	tx, err := NewTransaction(txID, req.Memo, entries)
	if err != nil {
		return TransferResult{}, fmt.Errorf("build transaction: %w", err)
	}

	// 5. Persist the transaction and entries.
	if err := uc.repo.PostTransaction(ctx, dbTx, tx); err != nil {
		return TransferResult{}, fmt.Errorf("post transaction: %w", err)
	}

	// 6. Write the outbox event (same DB transaction — guaranteed at-least-once delivery).
	if err := uc.outbox.Write(ctx, dbTx, OutboxEvent{
		Topic:   "transfer.completed",
		Payload: req, // serialized to JSON by the OutboxWriter
	}); err != nil {
		return TransferResult{}, fmt.Errorf("outbox: %w", err)
	}

	// 7. Commit. If this fails, the client retries with the same idempotency key — safe.
	if err := dbTx.Commit(ctx); err != nil {
		return TransferResult{}, fmt.Errorf("commit: %w", err)
	}

	uc.log.InfoContext(ctx, "transfer committed",
		"transaction_id", txID,
		"from", req.FromAccount,
		"to", req.ToAccount,
		"amount", req.Amount,
	)
	return TransferResult{TransactionID: txID}, nil
}
```

<Callout kind="pro" title="Always acquire locks in a deterministic order">
When two goroutines each try to lock accounts A then B, they can deadlock: goroutine 1 holds A, waits for B; goroutine 2 holds B, waits for A. Fix it by always acquiring in the same canonical order (e.g. alphabetical by account ID). Then two goroutines with the same pair always reach for the same first lock — one gets it, the other blocks cleanly. This is the classic "philosopher's fork" fix.
</Callout>

## gRPC + HTTP API

The transfer use case is a pure Go function. Now we expose it: gRPC for service-to-service, HTTP/JSON for the edge. *(gRPC & Service-to-Service Communication — Part 2; Auth & API Design — Part 1; Context in Production — Part 2)*

**On the job:** every service-to-service call in a payments system must carry a deadline. Without one, a slow downstream (a locked DB row, a network partition) blocks the caller's goroutine indefinitely — under a load spike, goroutines pile up, memory climbs, and the service falls over. The 5-second context deadline in `handleTransfer` is not a detail; it is structural safety.

### The HTTP/JSON edge

```go
// internal/httpapi/handler.go (illustrative — non-runnable)

type transferRequest struct {
	IdempotencyKey string `json:"idempotency_key"`
	FromAccount    string `json:"from_account"`
	ToAccount      string `json:"to_account"`
	AmountCents    int64  `json:"amount_cents"`
	Currency       string `json:"currency"`
	Memo           string `json:"memo"`
}

func (h *Handler) handleTransfer(w http.ResponseWriter, r *http.Request) {
	ctx := r.Context()

	// Enforce a per-request deadline so a slow DB never holds the connection forever.
	ctx, cancel := context.WithTimeout(ctx, 5*time.Second)
	defer cancel()

	var req transferRequest
	if err := json.NewDecoder(r.Body).Decode(&req); err != nil {
		http.Error(w, "invalid JSON", http.StatusBadRequest)
		return
	}
	if req.IdempotencyKey == "" || req.AmountCents <= 0 {
		http.Error(w, "idempotency_key and positive amount_cents required",
			http.StatusBadRequest)
		return
	}

	result, err := h.uc.Execute(ctx, usecase.TransferRequest{
		IdempotencyKey: req.IdempotencyKey,
		FromAccount:    domain.AccountID(req.FromAccount),
		ToAccount:      domain.AccountID(req.ToAccount),
		Amount:         domain.Money{Amount: req.AmountCents, Currency: req.Currency},
		Memo:           req.Memo,
	})
	if err != nil {
		if errors.Is(err, domain.ErrInsufficientFunds) {
			http.Error(w, err.Error(), http.StatusUnprocessableEntity)
			return
		}
		http.Error(w, "internal error", http.StatusInternalServerError)
		return
	}

	w.Header().Set("Content-Type", "application/json")
	if result.Duplicate {
		w.WriteHeader(http.StatusOK) // idempotent repeat — 200, not 201
	} else {
		w.WriteHeader(http.StatusCreated)
	}
	_ = json.NewEncoder(w).Encode(map[string]any{
		"transaction_id": result.TransactionID,
		"duplicate":      result.Duplicate,
	})
}
```

<UnderTheHood title="How context deadlines propagate across layers">

When `handleTransfer` calls `context.WithTimeout(ctx, 5s)`, it derives a child context with a deadline. That child context flows into `uc.Execute`, then into `repo.BeginTx`, then into every `pgx` call inside the transaction. The pgx driver passes the context's deadline to Postgres as a query timeout. If the 5 seconds expires while the DB is waiting on a lock, Postgres cancels the query, pgx returns a context error, the use case returns, the HTTP handler writes a 503, and the goroutine is freed.

Without that deadline: the handler goroutine can block indefinitely on the DB lock. Under a thundering herd or a slow Postgres, that is a goroutine leak and connection-pool drain — the exact failure mode covered in The context Package, In Depth (Part 1). Context deadlines are not nice-to-have. They are structural safety. `pgx/v5` propagates context cancellation to PostgreSQL's query cancellation path; exact termination latency depends on the driver, network, and server state.

</UnderTheHood>

## Async Events

The transfer committed. Now the rest of the system needs to know. The outbox row we wrote in step 6 is the starting gun. A relay goroutine polls that table, publishes to Kafka via Watermill, and a ledger-projection consumer updates a read-model balance table. *(Watermill — Event-Driven Go in Practice; Event-Driven Architecture & Kafka; Messaging & Pub/Sub Foundations — Part 3)*

**On the job:** the outbox relay's `SELECT ... FOR UPDATE SKIP LOCKED` is critical in a multi-replica deployment — without `SKIP LOCKED`, every relay instance tries to claim the same rows and they serialise on the lock, defeating horizontal scale. With `SKIP LOCKED`, each replica claims a non-overlapping set of rows and they publish in parallel.

```go
// internal/messaging/outbox_relay.go (illustrative — non-runnable)

// OutboxRelay polls the outbox table and publishes pending events.
// It runs as a background goroutine and shuts down cleanly on context cancellation.
type OutboxRelay struct {
	db        *pgxpool.Pool
	publisher message.Publisher // Watermill Publisher (Kafka in prod, GoChannel in tests)
	log       *slog.Logger
}

func (r *OutboxRelay) Run(ctx context.Context) error {
	ticker := time.NewTicker(200 * time.Millisecond)
	defer ticker.Stop()
	for {
		select {
		case <-ctx.Done():
			return ctx.Err()
		case <-ticker.C:
			if err := r.flush(ctx); err != nil {
				r.log.ErrorContext(ctx, "outbox flush failed", "err", err)
				// Don't return — keep retrying. The event stays in the outbox.
			}
		}
	}
}

func (r *OutboxRelay) flush(ctx context.Context) error {
	rows, err := r.db.Query(ctx,
		`SELECT id, topic, payload FROM outbox WHERE published_at IS NULL
		 ORDER BY created_at LIMIT 100 FOR UPDATE SKIP LOCKED`)
	if err != nil {
		return err
	}
	defer rows.Close()
	for rows.Next() {
		var id, topic string
		var payload []byte
		if err := rows.Scan(&id, &topic, &payload); err != nil {
			return err
		}
		msg := message.NewMessage(id, payload)
		if err := r.publisher.Publish(topic, msg); err != nil {
			return fmt.Errorf("publish %s: %w", id, err)
		}
		if _, err := r.db.Exec(ctx,
			`UPDATE outbox SET published_at = now() WHERE id = $1`, id); err != nil {
			return fmt.Errorf("mark published %s: %w", id, err)
		}
	}
	return rows.Err()
}
```

```go
// LedgerProjectionHandler consumes "transfer.completed" events and updates
// a denormalized balance table for fast reads (CQRS read model).
func LedgerProjectionHandler(
	db *pgxpool.Pool,
	log *slog.Logger,
) message.HandlerFunc {
	return func(msg *message.Message) ([]*message.Message, error) {
		var evt struct {
			FromAccount string `json:"FromAccount"`
			ToAccount   string `json:"ToAccount"`
			AmountCents int64  `json:"AmountCents"`
			Currency    string `json:"Currency"`
		}
		if err := json.Unmarshal(msg.Payload, &evt); err != nil {
			return nil, fmt.Errorf("unmarshal projection event: %w", err)
		}
		_, err := db.Exec(msg.Context(),
			`INSERT INTO account_balances (account_id, currency, balance_cents)
			 VALUES ($1, $3, -$2), ($4, $3, $2)
			 ON CONFLICT (account_id, currency)
			 DO UPDATE SET balance_cents = account_balances.balance_cents + EXCLUDED.balance_cents`,
			evt.FromAccount, evt.AmountCents, evt.Currency, evt.ToAccount)
		if err != nil {
			return nil, fmt.Errorf("update projection: %w", err)
		}
		log.InfoContext(msg.Context(), "projection updated",
			"from", evt.FromAccount, "to", evt.ToAccount, "cents", evt.AmountCents)
		msg.Ack()
		return nil, nil
	}
}
```

```go
type AccountLimiter struct {
	mu      sync.Mutex
	buckets map[AccountID]*rate.Limiter
	r       rate.Limit // refill rate per second
	burst   int        // max burst
}

func NewAccountLimiter(r rate.Limit, burst int) *AccountLimiter {
	return &AccountLimiter{
		buckets: make(map[AccountID]*rate.Limiter),
		r:       r,
		burst:   burst,
	}
}

// Allow returns false if the account has exceeded its rate limit.
func (l *AccountLimiter) Allow(id AccountID) bool {
	l.mu.Lock()
	lim, ok := l.buckets[id]
	if !ok {
		lim = rate.NewLimiter(l.r, l.burst)
		l.buckets[id] = lim
	}
	l.mu.Unlock()
	return lim.Allow()
}
```

<Define term="Fuzz Test" since="Testing in Go (Part 1)">
A **fuzz test** generates random inputs automatically to find cases that break your invariants — inputs you would never think to write by hand. You supply a seed corpus (a handful of representative values) and invariants (properties that must always hold). The fuzzer mutates the corpus, exercises your code under thousands of random variants, and reports any input that violates an invariant or causes a panic. In Meridian, fuzzing the `Money` type finds overflow conditions and sign-confusion bugs that a hand-written table test misses. Run with `go test -fuzz=FuzzName ./path/to/pkg`.
</Define>

<Define term="Race Detector" since="Testing in Go (Part 1), Advanced Concurrency & Correctness (Part 2)">
The **race detector** (`go test -race`) instruments every memory load and store with shadow memory that records the last write (goroutine + logical clock). On a concurrent read, it checks whether the last write happened-before this read in Go's memory model. If not — the read and write are unsynchronised — it fires and prints both goroutine stacks. The detector catches real data races with negligible false-positive rate. Cost: 5–10x slower execution and 5–10x more memory — run it in CI, not production. It catches *races on memory*; the balance-invariant assertion catches *logical correctness bugs*. Both checks matter.
</Define>

### The Race Test: N concurrent transfers, books must balance

This is the one that matters. Fire N goroutines at the in-memory ledger simultaneously with `-race` on. When it finishes, assert:

1. Total assets equal the initial total — no money created or destroyed.
2. The race detector is silent — no data races.
3. Every idempotency key is honored — duplicate calls are absorbed.

```go
// internal/domain/ledger_race_test.go

func TestLedger_ConcurrentTransfers_BooksBalance(t *testing.T) {
	t.Parallel()

	const (
		goroutines  = 100
		perG        = 10
		startAlice  = int64(500_000)
		startBob    = int64(500_000)
		amountCents = int64(100)
	)

	ledger := NewLedger(map[AccountID]int64{
		"alice": startAlice,
		"bob":   startBob,
	})
	startTotal := ledger.TotalAssets()

	var wg sync.WaitGroup
	for g := range goroutines {
		wg.Add(1)
		go func() {
			defer wg.Done()
			for i := range perG {
				// Half goroutines send alice→bob, half send bob→alice.
				from, to := AccountID("alice"), AccountID("bob")
				if g%2 == 0 {
					from, to = "bob", "alice"
				}
				key := fmt.Sprintf("g%d-i%d", g, i)
				// Retry on error (e.g. insufficient funds) with a fresh key is
				// intentionally NOT done here — we want to observe that the
				// books balance regardless of which transfers succeed or fail.
				_ = ledger.Transfer(key, from, to, USD(amountCents))

				// Fire the same key twice to verify idempotency.
				_ = ledger.Transfer(key, from, to, USD(amountCents))
			}
		}()
	}
	wg.Wait()

	endTotal := ledger.TotalAssets()
	if endTotal != startTotal {
		t.Fatalf(
			"money created or destroyed: started %d cents, ended %d cents (delta %d)",
			startTotal, endTotal, endTotal-startTotal,
		)
	}
	t.Logf("concurrent race test passed: %d goroutines x %d transfers each, total assets stable at %d cents",
		goroutines, perG, endTotal)
}
```

Run it with `go test -race ./internal/domain/ -run TestLedger_ConcurrentTransfers_BooksBalance`. If the race detector fires, you have a real data race in your ledger. If total assets shift, you have money appearing from nowhere or vanishing — both are production-ending bugs.

<UnderTheHood title="How the race detector actually works (Go 1.26)">

`go test -race` instruments every memory load and store with shadow memory recording the last write (goroutine + logical clock). On a read, it checks whether the last write happened-before this read in the happens-before partial order defined by Go's memory model. If not — both the read and the write are concurrent and unsynchronized — the detector fires and prints both goroutine stacks.

The detector uses ThreadSanitizer (TSan) under the hood, compiled into the binary. As of Go 1.26 it has negligible false-positive rate and catches real races reliably. The cost: 5–10x slower execution and 5–10x more memory. Run it in CI. Don't run it in production. The Ledger in our runnable example is protected by `sync.Mutex` — the race detector should be silent.

One subtlety: the race detector catches *races on memory*, not *logical correctness bugs*. Two goroutines can serialize perfectly through a mutex and still produce a wrong result if the invariant logic is flawed. That's why the balance-invariant assertion in `TestLedger_ConcurrentTransfers_BooksBalance` matters independently of the race detector — they catch different classes of bug.

</UnderTheHood>

```go
// Reconcile checks the entire ledger history for global balance.
// Global invariant: sum(all debits) == sum(all credits).
func Reconcile(txns []Transaction) error {
	byCurrency := make(map[string]int64)
	for _, tx := range txns {
		for _, e := range tx.Entries {
			switch e.Type {
			case Debit:
				byCurrency[e.Amount.Currency] += e.Amount.Amount
			case Credit:
				byCurrency[e.Amount.Currency] -= e.Amount.Amount
			}
		}

		if sum != 0 {
			return fmt.Errorf("reconciliation failed: %s ledger imbalance %d cents", cur, sum)
		}
	}
	return nil
}
```
