<HeroCard label="Part 3 · Chapter 15" title="Fintech Capstone: A Payments & Ledger Service">

Fourteen chapters taught the rules one at a time: money as integer cents, double entry, transactions, idempotency, events, resilience. This chapter builds one service that has to obey all of them at once, so you can see where they fit together and what breaks when one is missing.

The service is **ledgerd**: a small Go HTTP service over PostgreSQL 14. It moves money between accounts. Every transfer is one database transaction that writes double-entry postings, updates balances, remembers its idempotency key and records an event for other systems, and either all of that happens or none of it does. Then we do the things that break payment systems (opposite transfers at the same instant, duplicate requests, a `kill -9` in the middle) and check the books afterwards.

One honest scope note. The design has three edges: HTTP, gRPC and a message broker. The gRPC server from Part 2 and the Kafka and Watermill code from chapters 7 and 8 plug into the same use case unchanged. To keep this project buildable with `go` and a local Postgres alone, it uses HTTP for requests and an outbox relay that posts events to a small HTTP consumer. The core (domain, store, transfer) is identical either way.

## Domain and Money

*Stop 1 of 7.*

### Step 1: the rules that need no database

Start with the code that has to be right no matter what the database does. It lives in `internal/domain` and imports nothing of ours. First the amount. Money is a whole number of **cents** plus a currency, never a float (chapter 1: `0.1 + 0.2` is not `0.3` in floating point, and a ledger that is off by a cent is wrong).

```go noverify
// internal/domain/money.go, lines 12–15
type Money struct {
	Minor    int64
	Currency string
}
```

```go noverify
// internal/domain/money.go, Add: what "add two amounts" must refuse
func (m Money) Add(o Money) (Money, error) {
	if m.Currency != o.Currency {
		return Money{}, fmt.Errorf("%w: %s vs %s", ErrCurrency, m.Currency, o.Currency)
	}
	if (o.Minor > 0 && m.Minor > math.MaxInt64-o.Minor) || (o.Minor < 0 && m.Minor < math.MinInt64-o.Minor) {
		return Money{}, ErrOverflow
	}
	return Money{m.Minor + o.Minor, m.Currency}, nil
}
```

`Add` refuses two things a plain `+` would let through: adding dollars to euros, and overflowing `int64` (which would wrap around to a large negative number and turn a payment into a refund).

### Step 2: splitting without losing a cent

Splitting 67 cents three ways at weights 1 : 174 : 57 by rounding each share gives 0 + 50 + 16 = 66. A cent has vanished. `Allocate` uses the **largest-remainder method**: give everyone the whole part of their share, then hand the leftover cents to the parts with the biggest fractional remainders.

```go noverify
// internal/domain/money.go, lines 41–77
func (m Money) Allocate(weights ...int64) ([]Money, error) {
	var total int64
	for _, w := range weights {
		if w <= 0 {
			return nil, errors.New("weights must be positive")
		}
		total += w
	}
	if total == 0 {
		return nil, errors.New("no weights")
	}
	parts := make([]Money, len(weights))
	rem := make([]int64, len(weights))
	var used int64
	for i, w := range weights {
		q, r := divmod(m.Minor, w, total)
		parts[i] = Money{q, m.Currency}
		rem[i] = r
		used += q
	}
	for left := m.Minor - used; left != 0; {
		best := 0
		for i := range rem {
			if rem[i] > rem[best] {
				best = i
			}
		}
		step := int64(1)
		if left < 0 {
			step = -1
		}
		parts[best].Minor += step
		rem[best] = -1
		left -= step
	}
	return parts, nil
}
```

The test:

```text
money_test.go:42: 67 split 1:174:57 = [{0 USD} {50 USD} {17 USD}] (sum 67)
```

The parts sum to 67 exactly; the extra cent went to the share with the largest remainder.

### Step 3: the balance rule, in Go

A **transaction** is a list of postings (credit positive, debit negative) that must sum to zero. `Validate` checks it, and `Transfer` builds the standard two-posting transaction:

```go noverify
// internal/domain/ledger.go, lines 26–41
func (t Transaction) Validate() error {
	if len(t.Postings) < 2 {
		return ErrTooFew
	}
	var sum int64
	for _, p := range t.Postings {
		if p.Amount == 0 {
			return ErrZero
		}
		sum += p.Amount
	}
	if sum != 0 {
		return fmt.Errorf("%w (sum %d)", ErrUnbalanced, sum)
	}
	return nil
}
```

```go noverify
// internal/domain/ledger.go, lines 44–54
func Transfer(from, to string, amount Money, memo string) (Transaction, error) {
	if amount.Minor <= 0 {
		return Transaction{}, errors.New("amount must be positive")
	}
	if from == to {
		return Transaction{}, errors.New("cannot transfer to the same account")
	}
	return Transaction{Memo: memo, Currency: amount.Currency, Postings: []Posting{
		{from, -amount.Minor}, {to, amount.Minor},
	}}, nil
}
```

Alice sends Bob 25.00: Alice −2500, Bob +2500, sum zero. One more thing to notice: `Validate` is a *check*, and a check in Go can be skipped by other code, or by a hand-typed `INSERT`. Stop 2 enforces the same rule where nothing can skip it.

<Recap>

- Money is integer cents plus a currency. `Add` refuses mixed currencies and overflow.
- `Allocate` splits so the parts sum to the whole: 67 across 1 : 174 : 57 gives 0 + 50 + 17.
- A transaction's postings must sum to zero; `Validate` is the rule in Go.

## Storage

*Stop 2 of 7.*

### Step 1: the schema

Five tables. `accounts` holds a cached balance. A `CHECK` constraint stops a *customer* account going below zero, while a `system` account (the treasury that money is issued from) may. `transactions` and `postings` are the ledger itself: a posting is one leg of a transaction. `idempotency_keys` remembers each key's request and result. `outbox` holds events to publish.

```sql
CREATE TABLE accounts (
  id text PRIMARY KEY,
  currency text NOT NULL CHECK (length(currency) = 3),
  kind text NOT NULL CHECK (kind IN ('customer','system')),
  balance bigint NOT NULL DEFAULT 0,
  CONSTRAINT no_overdraft CHECK (kind = 'system' OR balance >= 0));
```

The `no_overdraft` constraint is a second safety net under the funds check in Go: whatever a bug does, Postgres refuses to commit a customer balance below zero.

### Step 2: the balance rule, again, in the database

The same rule from stop 1, as a **deferred constraint trigger**. It runs when the transaction commits, after all the postings are in, and refuses the commit if the sum isn't zero:

```sql
CREATE FUNCTION check_balanced() RETURNS trigger LANGUAGE plpgsql AS $$
DECLARE s bigint;
BEGIN
  SELECT sum(amount) INTO s FROM postings WHERE transaction_id = NEW.transaction_id;
  IF s <> 0 THEN RAISE EXCEPTION 'transaction % does not balance (sum %)', NEW.transaction_id, s; END IF;
  RETURN NULL;
END $$;
CREATE CONSTRAINT TRIGGER postings_balanced AFTER INSERT ON postings
  DEFERRABLE INITIALLY DEFERRED FOR EACH ROW EXECUTE FUNCTION check_balanced();
```

Try to write an unbalanced transaction by hand, bypassing all the Go:

```text
BEGIN;
INSERT INTO transactions (memo) VALUES ('sneaky') RETURNING id;   -- 21
INSERT INTO postings ... VALUES (21, 'acct-1', -500), (21, 'acct-2', 400);
COMMIT;
ERROR:  transaction 21 does not balance (sum -100)
CONTEXT:  PL/pgSQL function check_balanced() line 5 at RAISE

transactions after the refused commit: 0
```

The commit was refused and nothing was written. **Two layers, one rule**: Go rejects the mistake early with a friendly error, and the database refuses it even when somebody's script, migration or bug goes around the Go.

<Recap>

- The schema encodes the invariants: no customer overdraft (`CHECK`), postings that sum to zero per transaction (a deferred trigger), one row per idempotency key (`PRIMARY KEY`).
- A hand-typed unbalanced insert was refused at COMMIT and left no trace.

</Recap>

## The Transfer

*Stop 3 of 7.*

### Step 1: one transaction, five jobs

`Store.Transfer` is the heart of the service. In one database transaction it (1) checks whether the idempotency key was used, (2) locks both accounts, (3) checks the key again, (4) applies the rules, and (5) writes the transaction, postings, balances, key and outbox event. We'll take it in pieces.

Piece one, the key. A **duplicate request** must return the first result and not move the money again. Two requests with the same key but different contents are a client bug and must be refused, so the store keeps a hash of the request:

```go noverify
// internal/store/store.go, lines 60–72
	// 1. Has this key been used? A duplicate returns the first result without touching the accounts.
	var existing int64
	var prevHash string
	err = tx.QueryRow(ctx, `SELECT transaction_id, request_hash FROM idempotency_keys WHERE key = $1`, r.Key).Scan(&existing, &prevHash)
	if err == nil {
		if prevHash != hash(r) {
			return TransferResult{}, ErrKeyReuse
		}
		return TransferResult{TransactionID: existing, Replayed: true}, nil
	}
	if !errors.Is(err, pgx.ErrNoRows) {
		return TransferResult{}, err
	}
```

### Step 2: locks, in an order

Two transfers touching the same account must take turns, or both could read the balance, both see enough money, and both spend it. `SELECT ... FOR UPDATE` locks a row until the transaction ends. The trap is *which order*:

```go noverify
// internal/store/store.go, lines 74–92
	// 2. Lock both accounts. Always in id order, so two opposite transfers cannot each hold one lock
	//    and wait for the other.
	ids := []string{r.From, r.To}
	if !s.UnorderedLocks {
		sort.Strings(ids)
	}
	bal := map[string]int64{}
	kind := map[string]string{}
	for _, id := range ids {
		var b int64
		var k string
		if err := tx.QueryRow(ctx, `SELECT balance, kind FROM accounts WHERE id = $1 FOR UPDATE`, id).Scan(&b, &k); err != nil {
			if errors.Is(err, pgx.ErrNoRows) {
				return TransferResult{}, fmt.Errorf("%w: %s", ErrNoAccount, id)
			}
			return TransferResult{}, err
		}
		bal[id], kind[id] = b, k
	}
```

Notice `sort.Strings(ids)`. Suppose transfer 1 sends A→B and transfer 2 sends B→A at the same moment. If each locks its *sender* first, transfer 1 holds A and wants B, while transfer 2 holds B and wants A. Neither can ever proceed: a **deadlock**. Sorting the account ids means every transfer locks the lower id first, so the wait is a line, never a circle. `UnorderedLocks` exists only to demonstrate the difference: 16 goroutines, half sending each way, 4 seconds:

```text
4 s window, locks taken in from/to order: 7 transfers ok, 24 deadlocks (Postgres aborted them)
4 s window, locks taken in id order:      3616 transfers ok, 0 deadlocks
```

Unordered: 7 transfers completed and 24 were aborted by Postgres's deadlock detector (each costing a one-second wait first). Ordered: 3,616 transfers and none aborted. Same code, same data, one `sort.Strings`.

### Step 3: the second look, and the rules

With both rows locked, the transfer looks at the key again. Why twice? Another request with the same key might have been waiting on the same locks, committed while we waited, and spent the money we're about to check. Only after the locks does "is the key new?" have a stable answer. Then the rules: the domain check from stop 1, and the funds check:

```go noverify
// internal/store/store.go, lines 94–117
	// 3. Look again now that we hold the locks: a concurrent request with the same key may have
	//    committed while we waited, and it may have spent the money we were about to check.
	err = tx.QueryRow(ctx, `SELECT transaction_id, request_hash FROM idempotency_keys WHERE key = $1`, r.Key).Scan(&existing, &prevHash)
	if err == nil {
		if prevHash != hash(r) {
			return TransferResult{}, ErrKeyReuse
		}
		return TransferResult{TransactionID: existing, Replayed: true}, nil
	}
	if !errors.Is(err, pgx.ErrNoRows) {
		return TransferResult{}, err
	}

	// 4. Rules.
	t, err := domain.Transfer(r.From, r.To, domain.Money{Minor: r.Amount, Currency: "USD"}, "transfer "+r.Key)
	if err != nil {
		return TransferResult{}, err
	}
	if err := t.Validate(); err != nil {
		return TransferResult{}, err
	}
	if kind[r.From] == "customer" && bal[r.From] < r.Amount {
		return TransferResult{}, ErrInsufficient
	}
```

### Step 4: write everything, commit once

```go noverify
// internal/store/store.go, lines 119–148
	// 5. Write.
	var txID int64
	if err := tx.QueryRow(ctx, `INSERT INTO transactions (memo) VALUES ($1) RETURNING id`, t.Memo).Scan(&txID); err != nil {
		return TransferResult{}, err
	}
	for _, p := range t.Postings {
		if _, err := tx.Exec(ctx, `INSERT INTO postings (transaction_id, account_id, amount) VALUES ($1,$2,$3)`, txID, p.Account, p.Amount); err != nil {
			return TransferResult{}, err
		}
		if _, err := tx.Exec(ctx, `UPDATE accounts SET balance = balance + $2 WHERE id = $1`, p.Account, p.Amount); err != nil {
			return TransferResult{}, err
		}
	}
	if _, err := tx.Exec(ctx, `INSERT INTO idempotency_keys (key, request_hash, transaction_id) VALUES ($1,$2,$3)`, r.Key, hash(r), txID); err != nil {
		var pg *pgconn.PgError
		if errors.As(err, &pg) && pg.Code == "23505" { // a concurrent request with the same key won the race
			tx.Rollback(ctx)
			return s.replay(ctx, r)
		}
		return TransferResult{}, err
	}
	ev, _ := json.Marshal(map[string]any{"transaction_id": txID, "from": r.From, "to": r.To, "amount": r.Amount})
	if _, err := tx.Exec(ctx, `INSERT INTO outbox (topic, payload) VALUES ('transfer.completed', $1)`, ev); err != nil {
		return TransferResult{}, err
	}
	if err := tx.Commit(ctx); err != nil {
		return TransferResult{}, err
	}
	return TransferResult{TransactionID: txID}, nil
}
```

Postings, new balances, the idempotency key and the outbox event are all in the same transaction. Either all of them exist or none do, which is what stops a crash from producing a payment with no event, or an event with no payment. The unique-violation branch is a safety net for the rare tie where two requests race past both key checks: the loser rolls back and returns the winner's result.

### Step 5: does it hold?

`TestOverdraftAndIdempotency` and `TestConcurrentBooksBalance` check the behaviour against the real database:

And 64 workers hammering 20 accounts for 19,200 attempts applied 13,918 transfers and refused 4,351 for insufficient funds (the rest were skipped self-transfers), at about 1,600 a second, with the books balanced and no customer account below zero. `Check` is three SQL queries:

```go noverify
// internal/store/store.go, lines 171–182
// Check runs the three questions that prove the books: postings sum to zero, every transaction
// sums to zero, and each cached balance equals the sum of its postings.
func (s *Store) Check(ctx context.Context) (total int64, unbalanced, cacheDrift int, err error) {
	if err = s.Pool.QueryRow(ctx, `SELECT COALESCE(sum(amount),0) FROM postings`).Scan(&total); err != nil {
		return
	}
	if err = s.Pool.QueryRow(ctx, `SELECT count(*) FROM (SELECT 1 FROM postings GROUP BY transaction_id HAVING sum(amount) <> 0) x`).Scan(&unbalanced); err != nil {
		return
	}
	err = s.Pool.QueryRow(ctx, `SELECT count(*) FROM accounts a WHERE a.balance <> COALESCE((SELECT sum(amount) FROM postings p WHERE p.account_id = a.id),0)`).Scan(&cacheDrift)
	return
}
```

### Step 1: the dual write

Other systems need to know a transfer happened: a read model, an email service, analytics. The tempting way is to commit the transfer and then publish the event. That is two writes to two systems with nothing joining them, and a crash between them leaves the ledger and the event log disagreeing. `ledgerd -publish naive` does exactly that; `-publish outbox` is the fix. `run_events.sh` starts each with a consumer, sends `kill -9` to the service 2 seconds into a 3-second load, and compares what the ledger committed with what the consumer received:

### Step 2: the relay, at least once

The relay claims unpublished rows, sends each to the consumer, and marks them published, all inside one transaction:

```go noverify
// internal/outbox/relay.go, lines 26–78
func (r *Relay) Once(ctx context.Context) (n int, crashed bool, err error) {
	tx, err := r.Pool.Begin(ctx)
	if err != nil {
		return 0, false, err
	}
	defer tx.Rollback(ctx)
	rows, err := tx.Query(ctx, `SELECT id, payload FROM outbox WHERE published_at IS NULL ORDER BY id LIMIT $1 FOR UPDATE SKIP LOCKED`, r.Batch)
	if err != nil {
		return 0, false, err
	}
	type ev struct {
		id      int64
		payload []byte
	}
	var evs []ev
	for rows.Next() {
		var e ev
		if err := rows.Scan(&e.id, &e.payload); err != nil {
			rows.Close()
			return 0, false, err
		}
		evs = append(evs, e)
	}
	rows.Close()
	if len(evs) == 0 {
		return 0, false, nil
	}
	c := &http.Client{Timeout: 2 * time.Second}
	for _, e := range evs {
		req, _ := http.NewRequestWithContext(ctx, "POST", r.SinkURL+"/events", bytes.NewReader(e.payload))
		req.Header.Set("X-Event-ID", itoa(e.id))
		resp, err := c.Do(req)
		if err != nil || resp.StatusCode != 200 {
			if resp != nil {
				resp.Body.Close()
			}
			return n, false, err // leave the rest unmarked; they go out on the next pass
		}
		resp.Body.Close()
		n++
		r.Published++
	}
	if r.CrashAfterPublish {
		r.CrashAfterPublish = false
		return n, true, nil // the transaction rolls back: the events stay unmarked and will be re-sent
	}
	for _, e := range evs {
		if _, err := tx.Exec(ctx, `UPDATE outbox SET published_at = now() WHERE id = $1`, e.id); err != nil {
			return n, false, err
		}
	}
	return n, false, tx.Commit(ctx)
}
```

`FOR UPDATE SKIP LOCKED` lets several relays run side by side without claiming the same row at once. Look at the order of operations, because it decides the delivery guarantee: **send, then mark**. If the relay dies after sending and before marking, the rows stay unpublished and get sent again next time. So delivery is **at least once**: never lost, sometimes twice. (Marking first would flip it to at most once, which loses events on a crash.)

### Step 3: the consumer must tolerate repeats

At least once means the consumer will see duplicates, so it has to be idempotent too. The event carries its outbox row id, and the consumer remembers which ids it applied:

```go noverify
// internal/sink/sink.go, lines 34–43
		s.mu.Lock()
		s.Received++
		if s.seen[id] {
			s.Dups++ // already applied: acknowledge without applying twice
		} else {
			s.seen[id] = true
			s.Balances[ev.From] -= ev.Amount
			s.Balances[ev.To] += ev.Amount
		}
		s.mu.Unlock()
```

`TestAtLeastOnceThenDedup` forces the crash: the relay sends a batch of 100 and dies before marking. Then it recovers and drains everything:

```text
pass 1: sent 100 events, then the relay crashed before marking them (crashed=true)
relay sent 600 events for 500 transfers; sink received 600, 100 duplicates, 500 distinct; unpublished left: 0
read model: a=-12750 b=12750   ledger: a=-12750 b=12750
```

<Recap>

- Commit-then-publish loses events on a crash (4,713 committed, 4,711 received, permanently). Writing the event into an `outbox` table in the same transaction delays it at worst (5,304 of 5,304 after restart).
- The relay sends then marks, so it's at-least-once; the consumer dedups by event id: 600 sends, 100 duplicates, 500 applied, read model equal to the ledger.

</Recap>

Graceful shutdown makes the common case clean (a deploy loses nothing). Idempotency keys make the uncommon case safe (a crash, a network cut, a client timeout). You need both: shutdown to keep deploys quiet, keys because `kill -9` and dead networks exist.
</Callout>

<UnderTheHood title="Two relays, one outbox">

The relay's claim query ends in `FOR UPDATE SKIP LOCKED`. `FOR UPDATE` locks the rows it returns until the transaction ends; `SKIP LOCKED` tells a second query to step over rows somebody else has locked instead of waiting for them. So two relays started together split the work without coordinating. `TestTwoRelaysDontOverlap` starts two relays at once over 401 unpublished events with a batch size of 100:

```text
two relays started together on 401 unpublished events, batch 100: one sent 100, the other sent 100; consumer saw 200 (0 duplicates, 200 distinct)
```

Each took a different 100 rows, and the consumer saw no duplicates from the overlap. Duplicates only appear when a relay dies after sending and before marking, which is the at-least-once case in stop 5. The outbox is also why ordering is weaker than it looks: two relays deliver different batches at the same time, so events can arrive out of order across batches. The event carries its transaction id so a consumer that cares can order or reconcile by it.

</UnderTheHood>

<Exercise n={5} title="Reconciliation invariant (hard)" level="hard">

Write a `Reconcile` function that takes the full slice of `Transaction` values from the ledger and returns an error if the sum of all `Debit` entries does not equal the sum of all `Credit` entries across the entire ledger history. Write a property-based test (table or fuzz) that constructs random sequences of balanced transactions and asserts `Reconcile` returns nil, then introduces one unbalanced entry and asserts it returns an error.

<Solution>

```go
// Reconcile checks the entire ledger history for global balance.
// Global invariant: sum(all debits) == sum(all credits).
func Reconcile(txns []Transaction) error {
	byCurrency := make(map[string]int64)
	for _, tx := range txns {
		for _, e := range tx.Entries {
			switch e.Type {
			case Debit:
				byCurrency[e.Amount.Currency] += e.Amount.Amount
			case Credit:
				byCurrency[e.Amount.Currency] -= e.Amount.Amount
			}
		}
	}
	for cur, sum := range byCurrency {
		if sum != 0 {
			return fmt.Errorf("reconciliation failed: %s ledger imbalance %d cents", cur, sum)
		}
	}
	return nil
}
```

The trick: since `NewTransaction` enforces balance at creation, any `[]Transaction` built through the constructor will always reconcile. The test for the error path must *manually* build a `Transaction` with a tampered entry — bypassing `NewTransaction` — to simulate ledger corruption, which is the exact scenario reconciliation guards against.

</Solution>
