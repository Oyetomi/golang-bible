<HeroCard label="Part 3 · Chapter 11" title="Batch & Large-File Processing">

Most of the money Meridian moves is confirmed in bulk, not one event at a time. Every night each card network and bank sends a **settlement file**: every transaction of the day, one per line, with the amounts that will actually move between banks tomorrow. Meridian must read it, check it, load it, and prove its totals match, before the morning.

The file in this chapter has **3,000,000 rows and weighs 276 MB**. The approaches that work for a 20-row test file fail on it: they run out of memory, trust rows they shouldn't, load at a few thousand rows a second, or, when the job dies halfway (and at 3 a.m., it will), load half the day twice. Every claim in this chapter is measured on that file.

Six stops. If you get lost, come back here:

1. **Stream.** Read one record at a time, so memory doesn't grow with the file.
2. **Validate.** Parse every field strictly; put bad rows aside, with their line numbers.
3. **Control totals.** Let the file's own trailer prove nothing was lost.
4. **Bulk load.** Get 3 million rows into PostgreSQL fast: COPY.
5. **Pipeline.** Read and write at the same time, without the reader running away.
6. **Resume and rerun.** Survive `kill -9`, and load the same file twice without loading it twice.

</HeroCard>

## The lab bench

The settlement file is made by a generator in this chapter's Go 1.27 module, `batch` (`cmd/gen`), from a fixed seed, so the same command always writes the same bytes. It's CSV with a header, one detail record per card transaction, and a trailer:

```text
H,SETTLE-20260926-VISA-11,2026-09-26,USD
D,txn_0000000002,2026-09-26T03:16:05Z,m_03324,"The ""Night Owl"" Bar #3324",sale,amex,108.68,USD
D,txn_0000000003,2026-09-26T02:26:44Z,m_03890,"Green & Co, Ltd #3890",sale,visa,27.64,USD
T,3000000,707632327.27
```

A detail record (`D`) is one card transaction: its id, time, merchant, merchant name, `sale` or `refund`, card brand, amount and currency. The trailer (`T`) says how many detail records the sender wrote and what they add up to. Merchant names can contain commas and quotes, so the sender quotes them, as CSV (RFC 4180) requires. The real formats (NACHA files for US bank transfers, the card networks' clearing files, ISO 20022 XML) differ in layout, but they have the same three parts, and the same things go wrong with them.

```text
$ gen -rows 1000000 -o settle-1m.csv
wrote settle-1m.csv: 1000000 detail rows, 0 damaged, 91.9 MB
$ gen -rows 3000000 -o settle-3m.csv
wrote settle-3m.csv: 3000000 detail rows, 0 damaged, 275.6 MB
$ gen -rows 3000000 -faults 24 -o settle-3m-bad.csv
wrote settle-3m-bad.csv: 3000000 detail rows, 24 damaged, 275.6 MB
```

`settle-3m-bad.csv` is a different day with **24 damaged rows**: amounts with three decimal places, a dollar sign, exponent notation or nothing at all, a missing field, the wrong currency, a sale with a negative amount, a time without its `T`. The generator lists each one, with its line number and the amount the sender meant, in a side file, so the chapter can check that the loader finds exactly those rows. The database is PostgreSQL 14; the Go code uses `github.com/jackc/pgx/v5` v5.11.0, `golang.org/x/sync` v0.23.0 (for `errgroup`), and the `money` package from chapter 1. The machine is an 8-core laptop that other work was sharing, so **times varied by up to about 2x between runs**; each timed result below is the median of three runs, and the text gives the spread where it matters. Memory and row counts didn't vary.

## Stream

*Stop 1 of 6.*

### Step 1: load it all

The obvious program reads the whole file into memory and then works on it: `os.ReadFile`, or, for CSV, `csv.Reader.ReadAll`, which returns every record as a `[][]string` (a slice of records, each a slice of field strings). It's short, and on a test file it's fine.

Its memory grows with the file. The number that matters is **peak RSS** (resident set size): the most memory the operating system actually had to give the process at once. If that exceeds what the machine or the container allows, the process is killed. A settlement file gets bigger on a busy day, which is exactly the day the job must not fail.

### Step 2: or one record at a time

The alternative is to **stream**: read one record, handle it, keep only what you need from it (here, a running total), and let it go. The garbage collector reclaims each record's memory, so the process holds a few records and a read buffer at any moment, whatever the size of the file.

### Step 3: measured

`readall` peaked at **336 MB** for the 92 MB file and **890 MB** for the 276 MB one: about 3.2 times the file, growing with it. `stream` and `reuse` peaked at **16–17 MB for both files**. Streaming also wasn't slower: over three runs `readall` took 2.1–3.2 s on the big file and `stream` 1.4–1.6 s, because the program never has to find room for 890 MB.

<UnderTheHood title="Where 890 MB comes from">

`encoding/csv` turns each record into **one string** holding all its fields' text, and a `[]string` whose elements point into it (you can see this in `readRecord`: `str := string(r.recordBuffer)`, then each field is a slice of `str`). A Go string is a 16-byte header (a pointer and a length) plus its bytes.

For this file, per record: about 83 bytes of text (the line without its commas and newline), which the allocator rounds up to a 96-byte block; a backing array of 9 string headers, 9 × 16 = 144 bytes; and a 24-byte slice header in the outer `[][]string`. That's about 264 bytes per record, and 3,000,000 × 264 is about 790 MB. The outer slice also grew by doubling as `ReadAll` appended to it, copying itself each time, and the garbage collector lets the heap grow past what's live before it runs (by default up to twice the live heap, `GOGC=100`). Hence 890 MB of RSS for 276 MB on disk.

Streaming allocates the same strings (804 MB allocated over the run), but only a few are alive at any moment, so the garbage collector reclaims them 235 times instead of 12, and the peak stays at 17 MB.

</UnderTheHood>

### Step 4: bufio.Scanner has a line limit

The usual way to read a file line by line in Go is `bufio.Scanner`. It has a limit you need to know about: by default a line (a *token*) can be at most **64 KB** (`bufio.MaxScanTokenSize`). A longer line doesn't get truncated; `Scan` returns `false` and `Err` returns `bufio.ErrTooLong`, so a loop that only checks `Scan` silently stops early:

<GoPlayground>

```go
package main

import (
	"bufio"
	"fmt"
	"strings"
)

func main() {
	// Three lines; the middle one is 70,000 bytes long.
	file := "H,SETTLE-20260926\n" + "D,txn_1," + strings.Repeat("x", 70_000) + "\n" + "T,1,0.00\n"

	sc := bufio.NewScanner(strings.NewReader(file))
	lines := 0
	for sc.Scan() {
		lines++
	}
	fmt.Println("default buffer:", lines, "line(s) read, then:", sc.Err())

	sc = bufio.NewScanner(strings.NewReader(file))
	sc.Buffer(make([]byte, 0, 64*1024), 1024*1024) // lines up to 1 MB
	lines = 0
	for sc.Scan() {
		lines++
	}
	fmt.Println("1 MB maximum:  ", lines, "line(s) read, then:", sc.Err())
}
```

</GoPlayground>

```text
default buffer: 1 line(s) read, then: bufio.Scanner: token too long
1 MB maximum:   3 line(s) read, then: <nil>
```

With the default buffer the loop read **one line** of three and stopped. `sc.Buffer(buf, max)` raises the limit. Always check `sc.Err()` after the loop: without that check, the loop above would have reported a one-line file as a success.

### Step 5: CSV is not split on commas

`strings.Split(line, ",")` looks like a CSV parser until a field contains a comma. In CSV (RFC 4180) such a field is quoted, and a quote inside it is doubled:

<GoPlayground>

```go
package main

import (
	"encoding/csv"
	"fmt"
	"strings"
)

func main() {
	// One detail record. The merchant's name contains a comma, so the
	// sender quoted it, as CSV requires.
	line := `D,txn_0000000003,2026-09-26T02:26:44Z,m_03890,"Green & Co, Ltd #3890",sale,visa,27.64,USD`

	fields := strings.Split(line, ",")
	fmt.Printf("strings.Split: %d fields, amount field = %q\n", len(fields), fields[7])

	rec, err := csv.NewReader(strings.NewReader(line)).Read()
	fmt.Printf("encoding/csv:  %d fields, amount field = %q, err = %v\n", len(rec), rec[7], err)
}
```

</GoPlayground>

```text
strings.Split: 10 fields, amount field = "visa"
encoding/csv:  9 fields, amount field = "27.64", err = <nil>
```

`strings.Split` cut the quoted name in two, so every field after it moved one place and the "amount" was `visa`. In the measured run, the `split` mode rejected **752,419 of 3,000,000 rows** (the quarter of merchants whose names contain a comma). The rows whose names contain only quotes passed, with the quote characters left in the name. `encoding/csv` read all 3,000,000 correctly.

### Step 6: reuse the record slice

`csv.Reader` has an option, `ReuseRecord`, that makes `Read` return the same `[]string` every time, overwriting it, instead of allocating a new one per record. The field *strings* are still new each time (they're safe to keep); only the slice holding them is reused, so you mustn't keep the slice itself past the next `Read`. This is the reading loop in `cmd/read`:

```go noverify
// cmd/read/main.go, lines 67–85
	case "stream", "reuse":
		// One record at a time with encoding/csv.
		cr := csv.NewReader(bufio.NewReaderSize(f, 1<<16))
		cr.FieldsPerRecord = -1           // H, D and T records have different lengths
		cr.ReuseRecord = *mode == "reuse" // reuse one []string for every record
		for {
			rec, err := cr.Read()
			if err == io.EOF {
				break
			}
			if err != nil {
				log.Fatal(err)
			}
			if isDetail(rec) {
				line, _ := cr.FieldPos(0)
				add(rec, line)
			}
		}
	}
```

Measured: `reuse` allocated **393 MB** over the run instead of 804 MB, and needed 114 garbage collections instead of 235. Its time (1.4–1.7 s) was within the machine's noise of `stream`'s. `cr.FieldPos(0)` gives the line the current record started on, which Stop 2 needs for its error messages.

## Validate

*Stop 2 of 6.*

### Step 1: the file comes from someone else

A settlement file is written by another company's software. It can have a bug, a format change nobody announced, or a row typed by hand into a correction. Every field must be checked, and a row that fails must go somewhere a person will see it, with enough information to find it in the original file: its **line number** and the reason.

Putting a bad row aside, instead of either loading it or stopping, is called **quarantine**. The rest of the file can load; the quarantined rows wait for someone to fix and resubmit them.

### Step 2: floats lie about money

The fastest way to parse an amount wrong is `strconv.ParseFloat` and multiply by 100. A `float64` stores binary fractions, and most decimal amounts, like 0.29, have no exact binary form:

<GoPlayground>

```go
package main

import (
	"fmt"
	"strconv"
)

func main() {
	for _, s := range []string{"0.29", "4.35", "19.99", "1e3", "12.345"} {
		f, err := strconv.ParseFloat(s, 64)
		fmt.Printf("%-7s -> float %-8v -> int64(f*100) = %d cents, err = %v\n", s, f, int64(f*100), err)
	}
}
```

</GoPlayground>

```text
0.29    -> float 0.29     -> int64(f*100) = 28 cents, err = <nil>
4.35    -> float 4.35     -> int64(f*100) = 434 cents, err = <nil>
19.99   -> float 19.99    -> int64(f*100) = 1998 cents, err = <nil>
1e3     -> float 1000     -> int64(f*100) = 100000 cents, err = <nil>
12.345  -> float 12.345   -> int64(f*100) = 1234 cents, err = <nil>
```

`0.29` became **28 cents**, `4.35` became 434, and `19.99` became 1,998, because `0.29 * 100` is 28.999999999999996 and converting to `int64` drops the fraction. Worse, `1e3` and `12.345` were accepted: the float parser reads any number, while a settlement amount has at most two decimal places and no exponent. Chapter 1's `money.Parse` reads the digits as text, so it's exact, and it refuses anything else.

### Step 3: one strict function per row

`ParseRow` checks every field of a detail record and returns a `Row` or an error naming the line and the problem. It never guesses: a row that isn't exactly right is an error.

```go noverify
// settle.go, lines 74–116
// ParseRow checks one D record strictly: every field present and well formed,
// the amount exact in the file's currency, and its sign matching its kind.
// Nothing is guessed or repaired: a row that isn't exactly right is an error.
func ParseRow(f []string, line int, c money.Currency) (Row, error) {
	bad := func(format string, a ...any) (Row, error) {
		return Row{}, fmt.Errorf("%w: line %d: %s", ErrRow, line, fmt.Sprintf(format, a...))
	}
	if len(f) != 9 || f[0] != "D" {
		return bad("want 9 fields starting with D, got %d", len(f))
	}
	r := Row{Line: line, TxnID: f[1], Merchant: f[3], Name: f[4], Kind: f[5], Brand: f[6]}
	if !strings.HasPrefix(r.TxnID, "txn_") {
		return bad("transaction id %q", r.TxnID)
	}
	at, err := time.Parse(time.RFC3339, f[2])
	if err != nil {
		return bad("time %q", f[2])
	}
	r.At = at
	if !strings.HasPrefix(r.Merchant, "m_") {
		return bad("merchant id %q", r.Merchant)
	}
	switch r.Brand {
	case "visa", "mastercard", "amex":
	default:
		return bad("card brand %q", r.Brand)
	}
	if f[8] != c.Code {
		return bad("currency %q in a %s file", f[8], c.Code)
	}
	amt, err := money.Parse(f[7], c)
	if err != nil {
		return bad("%v", err)
	}
	r.Amount = amt
	switch {
	case r.Kind == "sale" && amt.Amount > 0:
	case r.Kind == "refund" && amt.Amount < 0:
	default:
		return bad("%s of %s", r.Kind, f[7])
	}
	return r, nil
}
```

(`bad` is a small function defined inside `ParseRow`, a *closure*, that formats the error with the line number, so each check is one line. `%w` wraps `ErrRow`, so a caller can test `errors.Is(err, batch.ErrRow)`.)

### Step 5: quarantine, or reject the file?

Quarantine is right for a few bad rows. It's wrong when the sender's system is broken: if the format changed, every row is bad, and quarantining 3 million rows one at a time fills a table with noise and delays the phone call that would fix it. So `Scan` takes a limit, `maxBad`, and rejects the **whole file** when it's passed. Here a file with 3,000 damaged rows (0.1%, spread through the file), with the limit at 100:

```text

REJECTED: file rejected: more than 100 bad rows by line 86512: stop and ask the sender
```

It stopped at line 86,512 after reading **8 MB** of 276, in 0.03 s. The right limit is a business decision (per partner, per file size); the point is that there is one.

## Control Totals

*Stop 3 of 6.*

### Step 1: the sender's own count

Checking each row can't tell you that a row is **missing**, or that the file stops early. For that, the sender adds a **trailer** record: how many detail records it wrote, and what their amounts add up to. These are **control totals**. NACHA files, which carry US bank transfers, end with a File Control record holding the entry count, a hash of the routing numbers, and the total debits and credits; card network files have their equivalents. The receiver computes the same numbers from what it read and compares.

A control total isn't a checksum of the bytes (for that, see the SHA-256 in Stop 6). It checks the **meaning**: the rows you'll act on add up to what the sender says it sent.

The trailer rules live in `batch.Scan`, the streaming reader `validate` uses: a trailer must parse, nothing may follow it, and reaching the end of the file without one is an error. Every file-level problem wraps `ErrFile`, so the caller can tell "reject this file" from "the disk failed":

		}

			if s.Trailer, err = ParseTrailer(rec, s.Header.Currency); err != nil {
				return s, fmt.Errorf("%w: line %d: %v", ErrFile, line, err)
			}

			continue
		}

## Bulk Load

*Stop 4 of 6.*

### Step 1: what one row costs

Once rows are validated, they go into PostgreSQL, table `settlement_rows`. Inserting a row costs more than the insert itself. With one `INSERT` per row, each row pays for a **round trip** (the statement travels to the server and the answer travels back, while the Go program waits) and, unless it's inside a larger transaction, a **commit**, which waits for the database's write-ahead log to reach the disk. At 3 million rows those fixed costs are the whole job.

There are three ways to pay them less often:

- **One transaction per chunk** of rows: one commit per 10,000 rows instead of per row. Still one round trip per row.
- **A batch** (`pgx.Batch`): queue the chunk's 10,000 `INSERT`s, send them together, then read the 10,000 answers. One round trip per chunk.
- **COPY**: PostgreSQL's bulk-load command. The client sends one `COPY settlement_rows FROM STDIN` and then streams the rows as data, not as statements; the server answers once at the end. `pgx` does this with `CopyFrom`.

### Step 2: the four ways, in code

`cmd/bulk` reads the file with `batch.Scan`, gathers rows into chunks of 10,000, and hands each chunk to `flush`, which writes it one of four ways:

```go noverify
// cmd/bulk/main.go, lines 44–70
		case "insert": // one INSERT per row, each its own transaction
			for _, r := range rows {
				if _, err := db.Exec(ctx, insert, r.Values(file)...); err != nil {
					return err
				}
			}
			return nil
		case "tx": // one INSERT per row, one transaction per chunk
			return pgx.BeginFunc(ctx, db, func(tx pgx.Tx) error {
				for _, r := range rows {
					if _, err := tx.Exec(ctx, insert, r.Values(file)...); err != nil {
						return err
					}
				}
				return nil
			})
		case "batch": // the chunk's INSERTs sent together, answers read together
			return pgx.BeginFunc(ctx, db, func(tx pgx.Tx) error {
				b := &pgx.Batch{}
				for _, r := range rows {
					b.Queue(insert, r.Values(file)...)
				}
				return tx.SendBatch(ctx, b).Close()
			})
		default: // COPY: one command, the chunk streamed, one answer
			return pgx.BeginFunc(ctx, db, func(tx pgx.Tx) error { return batch.CopyRows(ctx, tx, file, rows) })
		}
```

`batch.CopyRows` is `CopyFrom` with a function that turns each `Row` into its column values, in the table's column order:

```go noverify
// db.go, lines 17–28
// CopyRows writes rows with PostgreSQL's COPY protocol: one command, then
// the rows streamed in binary, then one reply.
func CopyRows(ctx context.Context, tx pgx.Tx, file int64, rows []Row) error {
	return CopyInto(ctx, tx, "settlement_rows", file, rows)
}

// CopyInto is CopyRows into another table with the same columns.
func CopyInto(ctx context.Context, tx pgx.Tx, table string, file int64, rows []Row) error {
	_, err := tx.CopyFrom(ctx, pgx.Identifier{table}, Columns,
		pgx.CopyFromSlice(len(rows), func(i int) ([]any, error) { return rows[i].Values(file), nil }))
	return err
}
```

(`pgx.BeginFunc` begins a transaction, runs the function, and commits if it returns `nil` or rolls back if it returns an error, so no path forgets to do either.)

<Callout kind="note" title="Why a commit is cheap here">

This PostgreSQL runs on macOS with its default `wal_sync_method`, and there `fsync` hands data to the drive without waiting for the drive's own cache to be written (PostgreSQL's `fsync_writethrough` setting forces that, and is slower). On a Linux server with a disk that honours flushes, each commit waits for the disk, so one-transaction-per-row is slower than here and the gap to COPY is larger. Measure on the hardware you run on.

</Callout>

<UnderTheHood title="What COPY skips">

A normal statement in PostgreSQL's wire protocol (the *extended query protocol*, which `pgx` uses) is several messages: Parse (the SQL), Bind (the parameter values), Execute, and Sync, after which the client reads the server's replies. Without a batch, the client waits for those replies before sending the next row, so every row costs a full network round trip, even to `127.0.0.1`.

`pgx.Batch` sends all the chunk's messages and then reads all the replies, which removes the waiting. The server still runs 10,000 statements.

`COPY ... FROM STDIN` is one statement. After it, the client sends `CopyData` messages full of rows (pgx uses PostgreSQL's binary format, so the server doesn't parse text either) and a final `CopyDone`. The server inserts each row straight into the table and its indexes, with no per-row statement, plan or reply. Every row is still written to the write-ahead log and the primary-key index, which is why COPY isn't infinitely fast: at around 280,000 rows a second, that work is the limit.

</UnderTheHood>

## Pipeline

*Stop 5 of 6.*

### Step 1: one reader, several writers

The COPY loader does one thing at a time: parse a chunk, then wait for the database to take it, then parse the next. The database can accept several COPYs at once on separate connections, so a **pipeline** splits the work: one goroutine (a function running concurrently with the rest of the program; `go f()` starts one) reads and parses, and several **writer** goroutines each take a finished chunk and COPY it on their own connection.

A pipeline has one rule that's easy to miss: the reader must **wait** when the writers are busy. The reader parses faster than the database writes. If it doesn't wait, it keeps going, and every chunk it has parsed but no writer has taken yet sits in memory. That's the whole file again, as in Stop 1. Making the reader wait is called **backpressure**, and a limit on how far ahead it can get is what makes a pipeline *bounded*.

### Step 2: the smallest example

Here are 100 chunks, two writer slots (a buffered channel of size 2, used as a *semaphore*: sending takes a slot, and blocks when both are taken; receiving gives one back), and a counter of how many chunks are in memory. The only difference between the two runs is **where the reader waits for a slot**: before reading on, or inside the goroutine it has already started, holding the chunk.

<GoPlayground>

```go
package main

import (
	"fmt"
	"sync"
	"sync/atomic"
	"time"
)

// load reads 100 chunks and hands each to one of two writers. It returns the
// most chunks that were in memory at the same moment.
func load(bounded bool) int64 {
	var inMemory, peak atomic.Int64
	writers := make(chan struct{}, 2) // two free writer slots
	var wg sync.WaitGroup
	for range 100 {
		// The reader parses a chunk: it's in memory now.
		if n := inMemory.Add(1); n > peak.Load() {
			peak.Store(n)
		}
		if bounded {
			writers <- struct{}{} // wait for a free writer before reading on
		}
		wg.Go(func() {
			if !bounded {
				writers <- struct{}{} // wait for a free writer, holding the chunk
			}
			time.Sleep(5 * time.Millisecond) // the database write
			inMemory.Add(-1)
			<-writers
		})
	}
	wg.Wait()
	return peak.Load()
}

func main() {
	fmt.Println("bounded:   at most", load(true), "chunks in memory at once")
	fmt.Println("unbounded: at most", load(false), "chunks in memory at once")
}
```

### Step 3: errgroup

The real pipeline uses `golang.org/x/sync/errgroup`, which is a `WaitGroup` with two more features that a batch job needs:

- **The first error wins.** `g.Wait()` returns the first error any goroutine returned, and `errgroup.WithContext` cancels a context the moment that happens, so the others can stop.
- **A limit.** After `g.SetLimit(n)`, `g.Go` blocks while `n` goroutines are running. That's the bounded version of Step 2, built in.

```go noverify
// cmd/pipeline/main.go, lines 50–82

	if *bounded {
		// g.Go now blocks while this many goroutines are running: the reader
		// can't get more than one chunk ahead of the writers.
		g.SetLimit(*writers + 1) // +1: the reader itself

	g.Go(func() error {
		buf := make([]batch.Row, 0, *chunk)
		send := func() {
			rows := buf
			g.Go(func() error {
				return pgx.BeginFunc(gctx, db, func(tx pgx.Tx) error { return batch.CopyRows(gctx, tx, 1, rows) })
			})
			buf = make([]batch.Row, 0, *chunk) // a new chunk: the old one now belongs to its writer
		}
		_, err := batch.Scan(f, 0, func(r batch.Row) error {
			if err := gctx.Err(); err != nil {
				return err // a writer failed: stop reading
			}
			read++
			if buf = append(buf, r); len(buf) == *chunk {
				send()
			}
			return nil
		}, func(int, []string, error) error { return nil })
		if err == nil && len(buf) > 0 {
			send()
		}
		return err
	})
	err = g.Wait()
```

`g.SetLimit(*writers + 1)` is the bound; the reader's own goroutine counts against the limit, hence the `+ 1`. In `send`, the chunk's slice is handed to the new goroutine and the reader starts a **new** slice for the next chunk: reusing the old one would overwrite rows a writer is still copying. The reader checks `gctx.Err()` before each row, so it stops reading once any writer has failed.

### Step 5: when a writer fails

Here one row that the file contains is inserted in advance, so one chunk's COPY fails on the primary key:

```text
$ pipeline -writers 4 -clash 1500000 settle-3m.csv
writers 4 bounded true   read 1531696 rows, 1490000 in the table  573902 rows/s    2.67s  peak RSS    44 MB  allocated    937 MB  GCs   98
error: ERROR: duplicate key value violates unique constraint "settlement_rows_pkey" (SQLSTATE 23505)
```

The failure cancelled the context, the reader stopped at row 1,531,696, and `g.Wait` returned the error. That part worked. But **1,490,000 rows were already committed**, by the chunks that finished before the failure. Rerunning the job would load them again (or fail on the same key). A batch job that can stop halfway needs to know where it stopped. That's the last stop.

## Resume & Rerun

*Stop 6 of 6.*

### Step 1: kill -9, then start again

A nightly job gets killed: the machine reboots, a deploy restarts it, the container exceeds its memory limit. `kill -9` (the `SIGKILL` signal) is the hardest version: the process stops between two instructions, with no chance to clean up. Whatever the database committed stays; whatever was in flight is rolled back by PostgreSQL when the connection drops.

The simplest recovery is to run the job again from the top. Here `ingest` loads the file in 10,000-row transactions into a table with no key, is killed after 4 seconds, and is run again:

```text
$ ingest -checkpoint none settle-3m.csv
kill -9 after 4 s
$ ingest -checkpoint none settle-3m.csv
this run loaded 3000000 rows in 7.59s; the table holds 4580000 rows for the file: 1580000 duplicated, 0 missing, 0 quarantined
control totals: 4580000 rows, USD 1080262846.67; trailer: 3000000 rows, USD 707632327.27: MISMATCH: the rows don't add up to the trailer's count
```

Before the kill, 1,580,000 rows had committed. The second run loaded all 3,000,000 again, so the table holds **4,580,000**, and the day's total reads **USD 1,080,262,846.67** instead of USD 707,632,327.27. The control totals catch it (MISMATCH), but only after the damage. The job needs to know **where it stopped**, and never do a chunk twice.

### Step 2: a checkpoint is a byte offset

To resume, the job needs two numbers: the **byte offset** in the file where the next unloaded record starts, and that record's **line number** (for error messages). Opening the file and moving to a byte offset (`f.Seek`) is instant, however far into the file it is. `csv.Reader.InputOffset()` (Go 1.19) says how many bytes the reader has consumed, which is exactly the start of the next record, quoted commas and all:

<GoPlayground>

```go
package main

import (
	"encoding/csv"
	"fmt"
	"io"
	"strings"
)

func main() {
	file := "H,SETTLE-20260926,2026-09-26,USD\n" +
		"D,txn_1,\"Corner Cafe, Soho\",12.00\n" +
		"D,txn_2,Harbor Fuel,3.50\n" +
		"D,txn_3,City Cinemas,7.25\n" +
		"T,3,22.75\n"

	// Run 1: read the header and one row, then note where the next record
	// starts. (Then, say, the process is killed.)
	cr := csv.NewReader(strings.NewReader(file))
	cr.FieldsPerRecord = -1
	cr.Read()
	rec, _ := cr.Read()
	checkpoint := cr.InputOffset()
	fmt.Println("run 1 read", rec[1], "and saved checkpoint: byte", checkpoint)

	// Run 2: start reading at that byte. With a real file this is
	// f.Seek(checkpoint, io.SeekStart).
	cr = csv.NewReader(strings.NewReader(file[checkpoint:]))
	cr.FieldsPerRecord = -1
	for {
		rec, err := cr.Read()
		if err == io.EOF {
			break
		}
		fmt.Println("run 2 read", rec)
	}
}
```

</GoPlayground>

```text
run 1 read txn_1 and saved checkpoint: byte 67
run 2 read [D txn_2 Harbor Fuel 3.50]
run 2 read [D txn_3 City Cinemas 7.25]
run 2 read [T 3 22.75]
```

Run 1 read the header and `txn_1` and saved **byte 67**. Run 2 started at byte 67 and read `txn_2` next: nothing skipped, nothing read twice. (Counting lines instead wouldn't be safe: a quoted CSV field may contain a newline, so a record can span two lines. The offset is where the reader actually is.) When the second reader starts mid-file, its offsets and line numbers count from where it started, so `ingest` adds the checkpoint's offset and line to them.

### Step 3: saving the checkpoint after the commit

The obvious place to save the checkpoint is a small file, written after each chunk commits. `-die-after-commit 100` makes `ingest` send itself `SIGKILL` right after chunk 100's commit, the moment between the two writes:

```text
$ ingest -checkpoint file -die-after-commit 100 settle-3m.csv
exit status 137 (killed by SIGKILL)
$ ingest -checkpoint file settle-3m.csv
resuming at line 990002 (byte 90941504)
this run loaded 2010000 rows in 4.85s; the table holds 3010000 rows for the file: 10000 duplicated, 0 missing, 0 quarantined
control totals: 3010000 rows, USD 709976266.28; trailer: 3000000 rows, USD 707632327.27: MISMATCH: the rows don't add up to the trailer's count
```

The checkpoint file still said line 990,002 (after chunk 99), but chunk 100 had committed: **10,000 rows duplicated**. Writing the checkpoint first and committing second would lose chunk 100 instead. Two separate systems (a database and a file) can't be updated at the same instant, and a kill can land between them. It's the **dual-write** problem again, from chapter 4's outbox.

### Step 4: saving it in the same transaction

The fix is to keep the checkpoint **in the database**, in the file's own row (`settlement_files.next_line` and `next_offset`), and update it in the **same transaction** as the chunk's rows. Then the rows and the checkpoint commit together or not at all, and there's no moment in between. Here is the commit function:

```go noverify
// cmd/ingest/main.go, lines 114–153
	// commit writes the chunk and, with -checkpoint tx, where to start next
	// time, in one transaction: both happen or neither does.
	commit := func(next int, off int64, done bool) error {
		err := pgx.BeginFunc(ctx, db, func(tx pgx.Tx) error {
			if err := batch.CopyInto(ctx, tx, table, id, rows); err != nil {
				return err
			}
			if _, err := tx.CopyFrom(ctx, pgx.Identifier{"settlement_rejects"}, []string{"file", "line", "reason", "raw"}, pgx.CopyFromRows(rejects)); err != nil {
				return err
			}
			if *mode == "tx" || done {
				_, err := tx.Exec(ctx, `UPDATE settlement_files SET next_line = $2, next_offset = $3,
					status = CASE WHEN $4 THEN 'loaded' ELSE 'loading' END,
					loaded_at = CASE WHEN $4 THEN now() END WHERE id = $1`, id, next, off, done)
				return err
			}
			return nil
		})
		if err != nil {
			return err
		}
		chunks++
		loaded += int64(len(rows))
		if chunks == *dieAfter {
			syscall.Kill(os.Getpid(), syscall.SIGKILL) // the worst moment: committed, checkpoint not yet saved
		}
		if *mode == "file" {
			// Save the checkpoint after the commit: write a new file, then
			// rename it over the old one, so the file is never half-written.
			tmp := path + ".ckpt.tmp"
			if err := os.WriteFile(tmp, fmt.Appendf(nil, "%d %d", next, off), 0o644); err != nil {
				return err
			}
			if err := os.Rename(tmp, path+".ckpt"); err != nil {
				return err
			}
		}
		rows, rejects = rows[:0], rejects[:0]
		return nil
	}
```

The main loop computes each chunk's checkpoint as the offset where this run started plus `cr.InputOffset()`:

```go noverify
// cmd/ingest/main.go, lines 155–186
	var trailer batch.Trailer
	for {
		rec, err := cr.Read()
		if err == io.EOF {
			log.Fatalf("no trailer: the file is incomplete")
		}
		pos, _ := cr.FieldPos(0)
		line := nextLine - 1 + pos
		if err != nil {
			log.Fatalf("line %d: %v", line, err)
		}
		if rec[0] == "T" {
			if trailer, err = batch.ParseTrailer(rec, h.Currency); err != nil {
				log.Fatal(err)
			}
			if err := commit(line+1, nextOff+cr.InputOffset(), true); err != nil {
				log.Fatal(err)
			}
			break
		}
		r, err := batch.ParseRow(rec, line, h.Currency)
		if err != nil {
			rejects = append(rejects, []any{id, line, err.Error(), append([]string(nil), rec...)})
		} else {
			rows = append(rows, r)
		}
		if len(rows)+len(rejects) == *chunk {
			if err := commit(line+1, nextOff+cr.InputOffset(), false); err != nil {
				log.Fatal(err)
			}
		}
	}
```

$ ingest settle-3m.csv

Each run resumed exactly where the last committed chunk ended: line 1,000,002 after chunk 100, then 2,000,002, then 2,670,002. A kill that lands while a chunk's transaction is open leaves nothing of it: PostgreSQL rolls back an open transaction when its connection drops, checkpoint included, so the next run does that chunk again, once. At the end: **3,000,000 rows, 0 duplicated, 0 missing, BALANCED**. The primary key on `(file, line)` is a second line of defence: had anything tried to load a line twice, the COPY would have failed rather than stored it.

### Step 5: the same file, twice

Partners resend files: after an outage, by mistake, or because someone "just to be sure" pressed the button again. A file's **identity** is its content, not its name, so `ingest` starts by computing the **SHA-256** of every byte and registers the file under that hash (`settlement_files.sha256` is `UNIQUE`):

```go noverify
// cmd/ingest/main.go, lines 40–85
	// Which file is this? The hash of its bytes, not its name: a partner
	// can resend a file under a new name, or a new file under an old one.
	f, err := os.Open(path)
	if err != nil {
		log.Fatal(err)
	}
	defer f.Close()
	hash := sha256.New()
	size, err := io.Copy(hash, f)
	if err != nil {
		log.Fatal(err)
	}
	sum := hash.Sum(nil)
	hashed := time.Since(start)

	// The header, for the currency and the partner's file id.
	f.Seek(0, io.SeekStart)
	cr := csv.NewReader(f)
	cr.FieldsPerRecord = -1
	rec, err := cr.Read()
	if err != nil {
		log.Fatal(err)
	}
	h, err := batch.ParseHeader(rec)
	if err != nil {
		log.Fatal(err)
	}
	firstRow := cr.InputOffset() // where line 2 starts

	// Register the file, or find it: one row per distinct content.
	var id int64
	var status string
	var nextLine int
	var nextOff int64
	err = db.QueryRow(ctx, `INSERT INTO settlement_files (sha256, name, file_id, next_offset) VALUES ($1, $2, $3, $4)
		ON CONFLICT (sha256) DO UPDATE SET sha256 = EXCLUDED.sha256
		RETURNING id, status, next_line, next_offset`, sum, filepath.Base(path), h.FileID, firstRow).Scan(&id, &status, &nextLine, &nextOff)
	if err != nil {
		log.Fatal(err)
	}
	if status == "loaded" {
		var name string
		db.QueryRow(ctx, `SELECT name FROM settlement_files WHERE id = $1`, id).Scan(&name)
		fmt.Printf("%s: already loaded as %s (sha256 %x...); nothing to do. Hashed %.0f MB in %.2fs\n", filepath.Base(path), name, sum[:6], float64(size)/1e6, hashed.Seconds())
		return
	}
```

(`ON CONFLICT (sha256) DO UPDATE SET sha256 = EXCLUDED.sha256` is a no-op update whose only purpose is to make `RETURNING` return the existing row too, so one statement either registers the file or finds it.)

```text
$ ingest settle-3m.csv
settle-3m.csv: already loaded as settle-3m.csv (sha256 c949916c97c3...); nothing to do. Hashed 276 MB in 0.17s
$ cp settle-3m.csv resent-by-partner.csv
$ ingest resent-by-partner.csv
resent-by-partner.csv: already loaded as settle-3m.csv (sha256 c949916c97c3...); nothing to do. Hashed 276 MB in 0.20s
$ ingest settle-3m-bad.csv
this run loaded 2999976 rows in 11.75s; the table holds 2999976 rows for the file: 0 duplicated, 0 missing, 24 quarantined
control totals: 3000000 rows, USD 708033820.07; trailer: 3000000 rows, USD 708039415.48: HELD: USD 5595.41 is in the 24 quarantined rows
```

The same file: **already loaded, nothing to do**, after hashing 276 MB in 0.17 s. The same bytes under a new name: recognised as the same file. And the damaged day loads its 2,999,976 good rows, quarantines 24 in the **same transactions** as their chunks (so a kill can't lose or double a quarantined row either), and is **HELD** for USD 5,595.41, exactly as `validate` said in Stop 3.

<Exercise n={1} title="Quarantine by reason" level="easy">

The operations team wants one line per kind of problem, not 24 lines. Make `validate` count quarantined rows by reason (three decimal places, wrong currency, missing field, and so on) and print the counts. What should the key be?

<Exercise n={2} title="Same name, different file" level="easy">

A partner sends `settle-2026-09-26.csv`, then an hour later a corrected file with the **same name**. What does `ingest` do with the second one, and what should Meridian do about the first?

<Solution>

The corrected file has different bytes, so a different SHA-256: `ingest` registers and loads it as a new file. Now both are in `settlement_rows`, which is right for the audit trail (chapter 10: what was received is never deleted) but wrong for settlement. The header's file id (`SETTLE-20260926-VISA-11`) is the partner's name for the day; add a rule that a new file with the same file id **supersedes** the old one: mark the old file `superseded` in `settlement_files`, in the same transaction that marks the new one `loaded`, and have settlement read only files that are `loaded`.

<Exercise n={3} title="Two loaders, one file" level="medium">

Cron starts `ingest` at 02:00, and at 02:01 an operator starts it by hand on the same file. What happens with the checkpoint in the database? Make it impossible.

<Solution>

Both read the same checkpoint and COPY the same chunk. The second COPY to commit fails on the `(file, line)` primary key, so there are no duplicates, but one job dies with an error and the operator doesn't know why. Take a lock on the file for the whole run: `SELECT pg_try_advisory_lock($1)` with the file's id (a session-level lock, released when the connection closes, including after `kill -9`), and exit with "already being loaded" if it returns false. `SELECT ... FROM settlement_files WHERE id = $1 FOR UPDATE NOWAIT` in a transaction held for the run also works, but a long transaction holds back vacuum; the advisory lock doesn't.

</Solution>

</Exercise>

<Exercise n={4} title="Settle into the ledger" level="medium">

Once a file is `loaded` and BALANCED, post the day to chapter 2's ledger: per merchant, what they're owed from the card network. Make it impossible to post a day twice.

<Solution>

Sum by merchant in SQL, then post one balanced transaction per merchant with `ledger.PostTx`, all in the same database transaction that changes the file's status from `loaded` to `settled`:

```go noverify
err := pgx.BeginFunc(ctx, db, func(tx pgx.Tx) error {
	tag, err := tx.Exec(ctx, `UPDATE settlement_files SET status = 'settled' WHERE id = $1 AND status = 'loaded'`, id)
	if err != nil {
		return err
	}
	if tag.RowsAffected() == 0 {
		return errors.New("not loaded, or already settled")
	}
	rows, err := tx.Query(ctx, `SELECT merchant, sum(amount_minor) FROM settlement_rows WHERE file = $1 GROUP BY merchant`, id)
	if err != nil {
		return err
	}
	owed := map[string]int64{}
	for rows.Next() {
		var m string
		var cents int64
		if err := rows.Scan(&m, &cents); err != nil {
			return err
		}
		owed[m] = cents
	}
	if err := rows.Err(); err != nil {
		return err
	}
	for m, cents := range owed {
		if cents == 0 {
			continue // a zero posting isn't allowed, and nothing is owed
		}
		t, err := ledger.NewTransaction("settlement",
			ledger.Leg("network:visa:receivable", money.New(cents, money.USD)),
			ledger.Leg("merchant:"+m+":payable", money.New(-cents, money.USD)))
		if err != nil {
			return err
		}
		if _, err := ledger.PostTx(ctx, tx, t); err != nil {
			return err
		}
	}
	return nil
})
```

The ledger's accounts must exist first (chapter 2's `accounts` table), so open any merchant's payable account that's missing in the same transaction. The `WHERE status = 'loaded'` in the first statement is the guard: a second run finds no row to update and posts nothing, and because it's the same transaction, a crash halfway posts nothing either. (The rows are read fully before posting, because one connection can't run a new statement while it's still reading a query's results.)

</Solution>

</Exercise>

<Exercise n={5} title="Resume with parallel writers" level="hard">

The checkpoint in Stop 6 is one offset, which works because there's one writer and chunks commit in order. With Stop 5's parallel writers, chunk 7 can commit before chunk 6. Design a checkpoint that still resumes with no duplicates and no gaps.

<Solution>

Record each chunk, not a high-water mark: a table `settlement_chunks (file, chunk, first_line, next_offset, PRIMARY KEY (file, chunk))`, inserted in the same transaction as the chunk's COPY. Chunk boundaries must be deterministic (chunk *k* is always detail rows *k*·10,000 + 1 to (*k*+1)·10,000), so a restart cuts the file the same way. On resume, find the largest *k* such that chunks 0 to *k* are all committed, seek to chunk *k*'s `next_offset`, and read on, skipping (parsing but not writing) any later chunk already in the table. The primary key on `(file, chunk)` rejects a chunk committed twice, and the final control totals prove nothing was skipped. Test it the same way: `kill -9` at random moments, many times, and compare the table with the trailer.

</Solution>

</Exercise>

func parseCents(s string) (int64, error) {

func load(r io.Reader, cp Checkpoint, chunk int, commit func(rows []Row, rejected []int, next Checkpoint) error) error {

	dup      int
	rejected []int
	cp       Checkpoint
	commits  int
	crashAt  int // fail this commit (1-based) as if the process died; 0: never
}

var errCrash = errors.New("kill -9")

func (s *store) commit(rows []Row, rejected []int, next Checkpoint) error {
	s.commits++
	if s.commits == s.crashAt {
		return errCrash
	}
	for _, r := range rows {
		if _, ok := s.rows[r.Line]; ok {
			s.dup++
		}
		s.rows[r.Line] = r
	}
	s.rejected = append(s.rejected, rejected...)
	s.cp = next
	return nil
}

// store currently being loaded.

func checkTrailer(rec []string) error {
	if len(rec) != 3 {
		return fmt.Errorf("%w: bad trailer", ErrControl)
	}

	total, err2 := parseCents(rec[2])
	if err1 != nil || err2 != nil {
		return fmt.Errorf("%w: bad trailer", ErrControl)

	var sum int64
	for _, r := range current.rows {
		sum += r.Cents
	}

		return fmt.Errorf("%w: %d rows + %d rejected, trailer says %d", ErrControl, len(current.rows), len(current.rejected), count)
	}
	if len(current.rejected) == 0 && sum != total {
		return fmt.Errorf("%w: rows add up to %d cents, trailer says %d", ErrControl, sum, total)
	}
	return nil
}

// resuming from the stored checkpoint each time, like a job restarted by
// its scheduler.
func run(file string, chunk int, crashes ...int) (*store, error) {

- **Stream**: read one record at a time. csv `ReadAll` peaked at 890 MB for a 276 MB file; streaming stayed at 16–17 MB for 1 or 3 million rows. `bufio.Scanner` stops at 64 KB lines unless you call `Buffer`, and you must check `Err`. - **Control totals**: the trailer is the sender's count and sum. It showed the USD 5,595.41 sitting in quarantine, and its absence rejected a file cut off at 150 MB.

- **Pipeline**: one reader, several writers, bounded with `errgroup.SetLimit`: 47 MB instead of 893 MB, and the first error stops everything. But chunks already committed stay committed.
- **Resume and rerun**: commit the checkpoint (a byte offset from `csv.Reader.InputOffset`) in the same transaction as its rows. Restarting from the top duplicated 1,580,000 rows; a checkpoint saved after the commit duplicated 10,000; a checkpoint in the transaction survived three `kill -9`s with none duplicated or missing.
