## Why Batch Still Rules

Before you dismiss batch as legacy, let me paint you the actual production picture. The clock hits midnight. Every bank, clearinghouse, and payment processor on the planet starts its settlement run. The Federal Reserve's ACH network cuts a file. Your processor drops a return file on Meridian's SFTP server. Statement generation kicks off. Three separate nightly jobs, all launching within minutes of each other — and not a single one of them is a Kafka consumer.

**On the job:** You hit batch the moment your bank, card network, or clearinghouse drops a file on your SFTP server. If your nightly reconciliation job misses its window because it OOM'd mid-file, you start the next business day with an unreconciled ledger — which means frozen settlements, compliance flags, and an ops team that will not be happy to see you.

**Why batch persists:**

<ConceptGrid cols={3}>
  <ConceptCard label="Settlement windows">ACH, SEPA, and most card networks operate on batch settlement cycles — 2–3 per day. You will never get per-transaction settlement on these rails. Batch is the protocol.</ConceptCard>
  <ConceptCard label="Auditability">A batch run produces a concrete artifact (file, log, report) with a clear start, end, record count, and total. Regulators love a printable ledger. The PCI auditor does not want your event stream's offset range.</ConceptCard>
  <ConceptCard label="Throughput efficiency">A 10 GB file transferred once costs far less in network, parsing, and coordination overhead than 10 million individually sent events. For bulk, bulk wins.</ConceptCard>
  <ConceptCard label="Reconciliation">Batch is *inherently* a reconciliation tool. You compare the file's totals against your ledger's totals. A streaming system requires a separate reconciliation layer anyway — batch already is that layer.</ConceptCard>
  <ConceptCard label="Error isolation">One bad record in a batch can be flagged and quarantined. The rest continue. A streaming failure mid-topic is messier to triage across partitions.</ConceptCard>
  <ConceptCard label="Cost predictability">A nightly job that runs for 90 minutes is cheaper and simpler to capacity-plan than a streaming service that must be right-sized for peak throughout the day.</ConceptCard>
  <Gotcha>Batch vs stream is not a holy war. The real fintech architecture has both. Use streaming for latency-sensitive flows (authorizations, fraud scoring) and batch for settlement, reconciliation, and statement generation. Resilience & Correctness Under Load (Part 3) and Idempotency & Exactly-Once Semantics (Part 3) are your streaming safety net; this chapter is your batch foundation.</Gotcha>
</ConceptGrid>

<Define term="Batch processing" since="Batch & Large-File Processing (Part 3, Chapter 10)">
**Batch processing** means collecting a set of work items — records, transactions, instructions — into a file or queue and processing them in bulk at a scheduled time, rather than one at a time as they arrive. On ACH rails the bank literally drops a file once or twice a day; there is no per-transaction API. Get it wrong and you miss the settlement window entirely.
</Define>

<Define term="Reconciliation" since="Double-Entry Ledgers (Part 3)">
**Reconciliation** is the process of comparing two independent records of the same events and confirming they agree — typically your internal ledger against the bank's file. If Meridian's ledger says a transfer settled but the ACH return file says it was rejected, that discrepancy is a reconciliation break. Undetected breaks turn into compliance findings and, worse, real money losses.
</Define>

### The nightly ACH reconciliation spine

The running scenario for this entire chapter is a real one: **ingesting a nightly ACH return file from your bank and reconciling it against Meridian's ledger.** The bank sends you a NACHA-formatted file containing return entries — transactions that failed (insufficient funds, closed account, etc.). Your job must:

1. Parse the file record by record, streaming — no full load.
2. Checkpoint progress so a crash mid-file restarts where it left off.
3. Apply each return against the ledger exactly once — idempotently.

By the end of this chapter that job will be production-grade. Let's build the foundation.

## File Formats: NACHA and ISO 20022

Fintech's file formats were designed by committee in the 1970s and 1990s. They are not beautiful. They are, however, what your bank sends you, so let's treat them with the respect they deserve: precise parsing, zero float money, careful byte offsets.

### NACHA / ACH — fixed-width positional records

<Define term="NACHA / ACH fixed-width format" since="Batch & Large-File Processing (Part 3, Chapter 10)">
**NACHA** (National Automated Clearing House Association) is the rule-making body for the US **ACH** (Automated Clearing House) network — the rails that move most direct deposits, payroll, and bill payments in the United States. NACHA files use a **fixed-width, positional** format: every line is exactly 94 characters, terminated by a newline, with no delimiters. Fields are identified by byte offset, not by separators. If you parse by splitting on commas or spaces, you will corrupt data. The format has been largely unchanged since the 1970s. It is not charming; it is ubiquitous.
</Define>

**On the job:** You hit this when your bank or payment processor delivers a nightly return file. If you misparse even one byte offset, you will either miss a return (and not reverse the credit) or misidentify the amount (and reverse the wrong amount). Both outcomes are compliance defects.

The ACH network uses NACHA-formatted files. Every line is exactly **94 characters** wide, terminated by a newline. There are no delimiters. Fields are at fixed byte positions. Read that sentence again: **fixed byte positions, no delimiters.** The record type is always the first character.

<ConceptGrid cols={2}>
  <ConceptCard label="Record types">The first byte identifies the record. `1` = File Header, `5` = Batch Header, `6` = Entry Detail, `7` = Addenda, `8` = Batch Control, `9` = File Control. A well-formed file is a stack of these, in order.</ConceptCard>
  <ConceptCard label="The Entry Detail (type 6)">This is the money line. It carries: transaction code (2 chars), routing number (9 chars, position 4–12), account number (17 chars), amount in cents (10 chars, position 30–39), individual name (22 chars), trace number (15 chars), and more — all positional.</ConceptCard>
</ConceptGrid>

Here is a simplified but realistic Entry Detail record laid out by byte offset:

```go
// NACHA Entry Detail (record type "6"), 94 characters wide.
// Positions are 1-based (NACHA spec convention); we subtract 1 for Go slices.
// Amount is in whole cents — never a float. Never.
type EntryDetail struct {
	TransactionCode string // pos  2-3  (2 chars)
	RoutingNumber   string // pos  4-12 (9 chars)
	AccountNumber   string // pos 13-29 (17 chars)
	AmountCents     int64  // pos 30-39 (10 chars, right-justified, zero-padded)
	IndividualName  string // pos 55-76 (22 chars)
	TraceNumber     string // pos 80-94 (15 chars)
}
```

Parsing is just `record[start:end]` — slice the line by byte offset, trim spaces, parse the amount integer. No CSV library, no JSON — straight byte arithmetic.

<GoPlayground>

```go
package main

import (
	"fmt"
	"strconv"
	"strings"
)

// EntryDetail holds the fields we care about from a NACHA Entry Detail record.
// AmountCents is int64 — money is always integer minor units.
type EntryDetail struct {
	TransactionCode string
	RoutingNumber   string
	AccountNumber   string
	AmountCents     int64
	IndividualName  string
	TraceNumber     string
}

// parseEntryDetail parses a single 94-character NACHA Entry Detail line (type "6").
// Positions are converted from 1-based NACHA spec to 0-based Go slice indices.
func parseEntryDetail(line string) (EntryDetail, error) {
	if len(line) < 94 {
		return EntryDetail{}, fmt.Errorf("entry detail too short: %d chars", len(line))
	}
	if line[0] != '6' {
		return EntryDetail{}, fmt.Errorf("not an entry detail record (type %q)", line[0])
	}
	amountStr := strings.TrimSpace(line[29:39])
	cents, err := strconv.ParseInt(amountStr, 10, 64)
	if err != nil {
		return EntryDetail{}, fmt.Errorf("invalid amount %q: %w", amountStr, err)
	}
	return EntryDetail{
		TransactionCode: strings.TrimSpace(line[1:3]),
		RoutingNumber:   strings.TrimSpace(line[3:12]),
		AccountNumber:   strings.TrimSpace(line[12:29]),
		AmountCents:     cents,
		IndividualName:  strings.TrimSpace(line[54:76]),
		TraceNumber:     strings.TrimSpace(line[79:94]),
	}, nil
}

func main() {
	// A synthetic but structurally valid 94-char Entry Detail line.
	// Fields: type=6, txnCode=27 (return), routing=021000021, acct=123456789012345,
	//         amount=0000012500 (=$125.00), individual, trace.
	line := "627021000021123456789012345 0000012500SMITH JOHN           1234567890123456789012345"
	// Pad to exactly 94 chars so the parser is happy.
	line = fmt.Sprintf("%-94s", line)

	e, err := parseEntryDetail(line)
	if err != nil {
		fmt.Println("parse error:", err)
		return
	}
	fmt.Printf("TxnCode:  %s\n", e.TransactionCode)
	fmt.Printf("Routing:  %s\n", e.RoutingNumber)
	fmt.Printf("Amount:   $%d.%02d\n", e.AmountCents/100, e.AmountCents%100)
	fmt.Printf("Name:     %s\n", e.IndividualName)
}
```

### ISO 20022 — XML on modern rails

<Define term="ISO 20022" since="Batch & Large-File Processing (Part 3, Chapter 10)">
**ISO 20022** is the international messaging standard used for modern payment rails — SEPA credit transfers, SWIFT gpi, FedNow, and many central-bank real-time gross settlement systems. Where NACHA is fixed-width plain text, ISO 20022 uses structured XML with a rich schema. The payment initiation message is **pain.001**; a direct debit is **pain.008**. Files for large batch runs can be hundreds of megabytes. You must stream them — `xml.Unmarshal` on a 500 MB file will OOM your process.
</Define>

**On the job:** You hit ISO 20022 when integrating with SEPA, SWIFT, or any modern cross-border rail. The verbose XML is a feature (machine-readable, extensible) and a gotcha (huge files that punish naive parsers equally).

NACHA is the domestic US rail. International wires and SEPA credit transfers run on **ISO 20022**, a newer standard using XML. The payment initiation message is called **pain.001** (don't laugh — it's `Payment Initiation 001`). A wire instruction file might contain thousands of `CdtTrfTxInf` (Credit Transfer Transaction Information) elements, each carrying amounts in a `Ccy` (currency) + decimal amount structure.

ISO 20022 XML is verbose. A real pain.001 file for a batch of 50,000 wire instructions might be hundreds of megabytes. You **cannot** `xml.Unmarshal` the whole thing. We'll stream it — that's the next section.

<Callout kind="note" title="ISO 20022 at a conceptual level">

A pain.001 document has a `GrpHdr` (Group Header) with the batch total, followed by a sequence of `PmtInf` (Payment Information) blocks, each containing one or more `CdtTrfTxInf` transaction elements. When we stream below, we'll step through `PmtInf` elements one at a time, never holding the full document tree in memory. The amount in ISO 20022 is a decimal string with a currency code — always parse it with a decimal library or into integer minor units. In this chapter we'll use integer cents after scaling.

</Callout>

## Streaming Without Loading

<Define term="Streaming parse (vs loading the whole file)" since="Batch & Large-File Processing (Part 3, Chapter 10)">
**Streaming parse** means reading and processing a file one record (or one element) at a time, never holding the full file contents in memory. The alternative — loading the whole file first with `os.ReadFile` or `xml.Unmarshal` — requires memory proportional to the file size (O(n)). Streaming keeps memory O(1) in file size: you hold one record, process it, discard it, and move on. For a 4 GB NACHA file, streaming uses kilobytes; loading uses gigabytes.
</Define>

**On the job:** Every nightly batch job that tries to `os.ReadFile` a multi-GB bank file will OOM the process at 3 a.m. The streaming approach is not a micro-optimization — it is the only approach that survives production file sizes.

Here's where most batch jobs die: someone wrote `data, err := os.ReadFile(path)` on a 4 GB file. The server OOMs at 3 a.m., the reconciliation job crashes, and now you have incomplete ledger entries and a very unhappy ops team. I've seen it. I've fixed it. You're not going to do it.

The rule is non-negotiable: **never load a batch file into memory.** Stream it. Hold one record at a time. Memory usage stays flat no matter how large the file gets — O(1) in file size.

Go's standard library gives you three streaming tools depending on the format:

<ConceptGrid cols={3}>
  <ConceptCard label="bufio.Scanner">Line-by-line streaming for newline-delimited text (NACHA, CSV, NDJSON). Reads in buffered chunks. Handles the file in a simple `for scanner.Scan()` loop.</ConceptCard>
  <ConceptCard label="encoding/csv Reader">Streaming CSV parsing via `r.Read()` (one record) or `r.ReadAll()` (loads everything — avoid). Use `Read()` in a loop.</ConceptCard>
  <ConceptCard label="encoding/xml Decoder">Token-by-token XML streaming via `d.Token()` and `d.DecodeElement()`. The counterpart to `xml.Unmarshal` — same structs, but you control the traversal cursor so you process one element at a time.</ConceptCard>
  <Gotcha>
    `bufio.Scanner` has a default max token size of 64 KiB (`bufio.MaxScanTokenSize`). A NACHA line is 94 bytes — fine. But some XML lines or base64-encoded content can exceed 64 KiB. Call `scanner.Buffer(make([]byte, 256*1024), 256*1024)` before your scan loop to raise the limit. Otherwise `scanner.Err()` returns `bufio.ErrTooLong` and you'll spend an hour confused.
  </Gotcha>
</ConceptGrid>

<Define term="bufio.Scanner token limit" since="Batch & Large-File Processing (Part 3, Chapter 10)">
`bufio.Scanner` returns one "token" per `Scan()` call — by default, one line. The **token limit** is the maximum size of a single token. The default is `bufio.MaxScanTokenSize` = 64 KiB. If any line exceeds this, `Scan()` returns `false` and `scanner.Err()` returns `bufio.ErrTooLong`. It does **not** truncate silently. For NACHA (94-byte lines) the default is fine. For XML or base64-heavy formats, call `scanner.Buffer(buf, maxSize)` before your loop to raise the limit. Always check `scanner.Err()` after the loop exits — EOF and error both cause `Scan()` to return `false`, and you cannot tell which without the explicit check.
</Define>

### Streaming a NACHA file with `bufio.Scanner`

<GoPlayground>

```go
package main

import (
	"bufio"
	"fmt"
	"io"
	"strconv"
	"strings"
)

// sumACHReturns streams a NACHA file line by line through a bufio.Scanner,
// summing the amounts of all return Entry Detail records (transaction codes
// 21, 26, 27, 31, 36, 37). Memory stays flat — one line at a time, regardless
// of file size. In production the io.Reader is an *os.File from os.Open; here
// it's a strings.Reader so the example is self-contained.
func sumACHReturns(r io.Reader) (int64, int, error) {
	returnCodes := map[string]bool{
		"21": true, "26": true, "27": true,
		"31": true, "36": true, "37": true,
	}
	var totalCents int64
	var count int

	scanner := bufio.NewScanner(r)
	for scanner.Scan() {
		line := scanner.Text()
		if len(line) < 94 || line[0] != '6' {
			continue // skip non-entry records
		}
		txnCode := strings.TrimSpace(line[1:3])
		if !returnCodes[txnCode] {
			continue // not a return
		}
		amountStr := strings.TrimSpace(line[29:39])
		cents, err := strconv.ParseInt(amountStr, 10, 64)
		if err != nil {
			return 0, 0, fmt.Errorf("bad amount in trace %s: %w",
				strings.TrimSpace(line[79:94]), err)
		}
		totalCents += cents
		count++
	}
	if err := scanner.Err(); err != nil {
		return 0, 0, fmt.Errorf("scan: %w", err)
	}
	return totalCents, count, nil
}

func main() {
	// Simulate a small NACHA file. In production this io.Reader is an *os.File
	// from os.Open — never os.ReadFile into memory.
	rows := []string{
		"1" + strings.Repeat(" ", 93), // File Header
		"5" + strings.Repeat(" ", 93), // Batch Header
		// Three Entry Detail records, transaction code 27 (debit return):
		"627021000021123456789012345 0000012500SMITH JOHN           1" + strings.Repeat("0", 14),
		"627021000021987654321098765 0000025000JONES MARY           1" + strings.Repeat("1", 14),
		"627021000021111111111111111 0000005075DAVIS BOB            1" + strings.Repeat("2", 14),
		"8" + strings.Repeat(" ", 93), // Batch Control
		"9" + strings.Repeat(" ", 93), // File Control
	}
	file := strings.Join(rows, "\n")

	total, n, err := sumACHReturns(strings.NewReader(file))
	if err != nil {
		fmt.Println("error:", err)
		return
	}
	fmt.Printf("Returns: %d entries, total $%d.%02d\n", n, total/100, total%100)
}
```

</GoPlayground>

### Streaming ISO 20022 XML with `encoding/xml Decoder`

For XML, `bufio.Scanner` won't cut it — XML structure is hierarchical, not line-delimited. Use `encoding/xml`'s `Decoder` in token mode. The key pattern is: call `d.Token()` to advance through the document, and when you hit the start element you want, call `d.DecodeElement` into a local struct — it reads only *that element's subtree*, then the cursor advances past it. The rest of the file hasn't been read yet.

<GoPlayground>

```go
package main

import (
	"encoding/xml"
	"fmt"
	"strconv"
	"strings"
)

// CdtTrfTxInf is a single ISO 20022 credit transfer transaction.
// In a real pain.001, the amount is a decimal string + currency attribute.
// We parse it into integer cents (assuming EUR for this demo).
type CdtTrfTxInf struct {
	EndToEndId string `xml:"PmtId>EndToEndId"`
	AmountStr  string `xml:"Amt>InstdAmt"`
}

// streamISO20022 processes a pain.001 XML document one CdtTrfTxInf at a time.
// It never loads the full document tree — each element is decoded and discarded.
func streamISO20022(data string) error {
	dec := xml.NewDecoder(strings.NewReader(data))

	var totalCents int64
	var count int

	for {
		tok, err := dec.Token()
		if err != nil {
			break // io.EOF or parse error; real code checks err == io.EOF
		}
		se, ok := tok.(xml.StartElement)
		if !ok || se.Name.Local != "CdtTrfTxInf" {
			continue
		}
		// Decode only this element's subtree — the rest of the file is untouched.
		var tx CdtTrfTxInf
		if err := dec.DecodeElement(&tx, &se); err != nil {
			return fmt.Errorf("decode CdtTrfTxInf: %w", err)
		}
		// Amount in ISO 20022 is a decimal like "125.00" — convert to integer cents.
		// Real code uses a decimal library or big.Rat for precision.
		cents, err := parseCents(tx.AmountStr)
		if err != nil {
			return fmt.Errorf("bad amount %q in %s: %w", tx.AmountStr, tx.EndToEndId, err)
		}
		totalCents += cents
		count++
	}

	fmt.Printf("Processed %d transactions, total %d cents ($%d.%02d)\n",
		count, totalCents, totalCents/100, totalCents%100)
	return nil
}

// parseCents converts a decimal string "125.00" to integer cents 12500.
// In production, use shopspring/decimal or math/big for arbitrary precision.
func parseCents(s string) (int64, error) {
	s = strings.TrimSpace(s)
	dot := strings.IndexByte(s, '.')
	if dot < 0 {
		n, err := strconv.ParseInt(s, 10, 64)
		return n * 100, err
	}
	whole := s[:dot]
	frac := s[dot+1:]
	// Ensure exactly 2 decimal places.
	switch len(frac) {
	case 0:
		frac = "00"
	case 1:
		frac += "0"
	default:
```

<UnderTheHood title="Why streaming keeps memory O(1) in file size">

When you call `xml.NewDecoder(f)` and drive it with `d.Token()`, the decoder maintains a small internal read buffer (a few kilobytes) and a tokenizer state machine. It reads from the underlying `io.Reader` in chunks, returning one token at a time. When you call `d.DecodeElement(&tx, &se)`, it allocates a struct for *that element only*, fills it, and returns. The struct goes out of scope at the end of the loop body and is collected on the next GC cycle.

The key invariant: **at no point does the decoder hold more than its internal buffer plus one decoded element in memory, regardless of the total file size.** If your file is 4 GB and contains 2 million transactions, you still hold one `CdtTrfTxInf` at a time — roughly the size of one struct, not two million.

This is in stark contrast to `xml.Unmarshal(data, &doc)`, which must first read the entire document into `data` (one 4 GB allocation), then build a full in-memory DOM tree (another several GB allocation). Both approaches parse the same XML — but streaming is O(1) space and the whole-document approach is O(n) in file size.

As of **Go 1.26**, `io.ReadAll` is roughly 2× faster than it was in 1.25. This is a *trap*: a faster `ReadAll` just means you fill memory faster. For batch files, streaming with `Decoder.Token()` is always the right approach — the speed improvement in `ReadAll` doesn't change the memory equation.

Go 1.26's **Green Tea GC** (the new default garbage collector) improves locality and scalability when marking and scanning many small objects. That can help allocation-heavy jobs, but the real win here is independent of the collector: a streaming batch job never retains the whole file, so live heap stays bounded.

</UnderTheHood>

<Define term="Checkpoint / resumability" since="Batch & Large-File Processing (Part 3, Chapter 10)">
A **checkpoint** is a durable record of how far a batch job has progressed — the byte offset or record number of the last successfully committed record. On a crash or restart, the job reads its checkpoint and resumes from that position instead of starting over. **Resumability** is the property that makes this work: given a valid checkpoint, the job can re-enter the file mid-stream with no loss of correctness. Without a checkpoint, a crash that happens 95% through a 4-hour run costs you the entire 4 hours; with one, it costs you at most one checkpoint interval (typically seconds).
</Define>

**On the job:** Every nightly batch job of meaningful size needs checkpointing. "It never crashes in production" is not a design. A deploy, an OOM kill, or a network partition will interrupt your job, and when it does, the checkpoint is the difference between re-running 30 seconds of work and re-running 4 hours.

You've got a 4 GB NACHA file. You've been streaming for 40 minutes, you've processed 1.8 million records, and the process crashes — OOM killer, network blip, a deploy, someone tripped on a power cord. Without checkpointing, you restart from record 1. With checkpointing, you restart from record 1,800,001.

A **checkpoint** is a durable record of your progress: how far into the file you've successfully processed. The checkpoint store is just a database row (or a file) you update after each committed batch of records. On restart, you read the checkpoint and seek (or skip) to that position.

```go
// Checkpoint records progress through a batch file so the job can resume
// mid-file after a crash without reprocessing records from the start.
type Checkpoint struct {
	JobID          string    // which batch job
	FilePath       string    // which file
	LastRecordNum  int64     // last successfully processed record number (1-based)
	ByteOffset     int64     // byte offset in file after last processed record
	ProcessedCount int64     // total records processed so far
	TotalCents     int64     // running sum (for reconciliation cross-check)
	UpdatedAt      time.Time // when this checkpoint was written
}
```

Two flavors of checkpoint position:

- **Record number**: the count of records processed. Simple; works when records are equal in length (NACHA's 94-byte lines). Skip the first N lines on resume.
- **Byte offset**: the file position *after* the last processed record. More general; works for variable-length records. Use `file.Seek(offset, io.SeekStart)` to jump directly.

For NACHA (fixed-width lines), either works. We'll use byte offset because it's O(1) to seek and avoids re-scanning N lines just to skip them.

```go
package main

import (
	"fmt"
	"strings"
	"time"

// Checkpoint records how far a batch job has progressed through a file.
type Checkpoint struct {
	JobID         string
	FilePath      string
	LastRecordNum int64
	ByteOffset    int64
	TotalCents    int64
	UpdatedAt     time.Time
}

// InMemoryCheckpointStore is a toy store for this demo.
// In production: a Postgres row with a unique job_id, updated in the same
// transaction that commits the batch of ledger entries.
type InMemoryCheckpointStore struct {
	data map[string]*Checkpoint
}

func NewStore() *InMemoryCheckpointStore {
	return &InMemoryCheckpointStore{data: make(map[string]*Checkpoint)}
}

func (s *InMemoryCheckpointStore) Save(cp Checkpoint) {
	cp.UpdatedAt = time.Now()
	s.data[cp.JobID] = &cp
}

func (s *InMemoryCheckpointStore) Load(jobID string) (Checkpoint, bool) {
	cp, ok := s.data[jobID]
	if !ok {
		return Checkpoint{}, false
	}
	return *cp, true
}

// processLines simulates streaming from startLine, checkpointing every 2 records.
func processLines(lines []string, store *InMemoryCheckpointStore, jobID string, startRecord int64) (int64, error) {
	cp, _ := store.Load(jobID)
	var byteOffset int64
	for i, line := range lines[:startRecord] {
		_ = i
		byteOffset += int64(len(line)) + 1 // +1 for newline
	}

	var totalCents int64 = cp.TotalCents
	var recordNum int64 = startRecord

	for i := int(startRecord); i < len(lines); i++ {
		line := lines[i]
		byteOffset += int64(len(line)) + 1

		if len(line) >= 94 && line[0] == '6' {
			// Simulate parsing amount from position 29:39 (using a fixed value here).
			totalCents += 5000 // $50.00 per record in this demo
			recordNum++

			// Checkpoint every 2 records (in production: every 1000-10000).
			if recordNum%2 == 0 {
				store.Save(Checkpoint{
					JobID:         jobID,
					LastRecordNum: recordNum,
					ByteOffset:    byteOffset,
					TotalCents:    totalCents,
				})
				fmt.Printf("[checkpoint] record %d, offset %d, total $%d.%02d\n",
					recordNum, byteOffset, totalCents/100, totalCents%100)
			}
		}
	}
	return totalCents, nil

		"6" + strings.Repeat("C", 93), // Entry 3  ← resume starts here
		"6" + strings.Repeat("D", 93), // Entry 4
		"8" + strings.Repeat(" ", 93), // Batch Control
		"9" + strings.Repeat(" ", 93), // File Control
```

<Callout kind="pro" title="Atomic checkpoint + commit">

The checkpoint must be written in the **same transaction** as the ledger entries it covers. If you write the checkpoint first and then the ledger commit fails, you'll skip those records on resume. If you write the ledger entries first and the checkpoint write fails, you'll re-process them — which is fine only if your handler is idempotent (which it must be; see the next section). The safe default: commit ledger entries and checkpoint in the same DB transaction. This makes the checkpoint a consistent snapshot of progress.

</Callout>

## Idempotent Re-processing

<Define term="Idempotent reprocessing" since="Idempotency & Exactly-Once Semantics (Part 3)">
**Idempotent reprocessing** means running a batch job more than once on the same input — or re-processing a subset of records after a crash — produces the same outcome as running it exactly once. The key mechanism is a **natural dedup key**: a field in the record (like a NACHA Trace Number) that uniquely identifies it. Before posting a return to the ledger, the job checks whether a ledger entry for that key already exists. If it does, the record is silently skipped. If not, it is posted. A pre-insert `ON CONFLICT DO NOTHING` in Postgres does the same thing atomically at the database level. The deep treatment is in Idempotency & Exactly-Once Semantics (Part 3).
</Define>

**On the job:** Idempotent reprocessing is what makes checkpoint + retry safe. Without it, every re-processed record in the window since your last checkpoint double-posts to the ledger — that is a compliance defect and potentially a real-money error. With it, re-processing is harmless.

The checkpoint gives you resumability. But resuming from a checkpoint means you might re-process some records — the ones that were in-flight when you crashed. If re-processing a return entry double-posts to the ledger, you've invented a compliance disaster. The last defense is **idempotency**.

The principle: **running a batch job N times on the same file produces the same result as running it once.** The ledger ends up in the same state whether you ran the job once cleanly or crashed and retried five times.

How? Natural dedup keys. Every NACHA Entry Detail has a **Trace Number** (positions 80–94) — a 15-digit identifier that is unique within an ACH file. Use it as the dedup key. Before posting a return, check whether a ledger entry for that trace number already exists. If it does, skip it. If it doesn't, post and commit.

```go
// applyReturn applies a NACHA return entry to the ledger, idempotently.
// If a ledger entry for this trace number already exists, it skips the insert.
// This makes the function safe to call multiple times for the same record.
func applyReturn(ctx context.Context, db *sql.DB, entry EntryDetail) error {
	// Check for an existing debit entry with this trace number.
	var exists bool
	err := db.QueryRowContext(ctx,
		`SELECT EXISTS(SELECT 1 FROM ledger_entries WHERE trace_number = $1)`,
		entry.TraceNumber,
	).Scan(&exists)
	if err != nil {
		return fmt.Errorf("dedup check for trace %s: %w", entry.TraceNumber, err)
	}
	if exists {
		// Already posted — idempotent skip. Log at debug level for observability.
		return nil
	}
	// Insert the return as a debit to the originator's account.
	_, err = db.ExecContext(ctx, `
		INSERT INTO ledger_entries (trace_number, account_id, amount_cents, entry_type, posted_at)
		VALUES ($1, $2, $3, 'ach_return', NOW())`,
		entry.TraceNumber, entry.AccountNumber, entry.AmountCents,
	)
	return err
}
```

Alternatively — and more efficiently — use a `UNIQUE` constraint on `trace_number` in the database and `INSERT ... ON CONFLICT DO NOTHING`. The database enforces uniqueness; your code just fires and forgets duplicates:

```go
_, err = db.ExecContext(ctx, `
    INSERT INTO ledger_entries (trace_number, account_id, amount_cents, entry_type, posted_at)
    VALUES ($1, $2, $3, 'ach_return', NOW())
    ON CONFLICT (trace_number) DO NOTHING`,
    entry.TraceNumber, entry.AccountNumber, entry.AmountCents,
)
```

This ties directly to what you learned in Idempotency & Exactly-Once Semantics (Part 3): the trace number is your **natural idempotency key** — provided by the domain, not generated by you, and guaranteed unique per ACH file by the NACHA spec. You're not inventing dedup; you're leaning on the protocol's own key.

<Callout kind="warn" title="Append-only corrections, not updates">

When a batch return is applied incorrectly and must be corrected, **do not update the existing ledger entry.** Append a correction entry with the original trace number, the correction amount (positive or negative), and a reference to the original. Mutating ledger entries breaks your audit trail and the double-entry invariant covered in Double-Entry Ledgers (Part 3). Corrections are entries, not mutations. Always.

<UnderTheHood title="Why streaming parse is O(1) memory and how checkpoint + idempotency make restarts safe">

Two separate guarantees combine to make a batch job correctly restartable.

**Memory O(1) in file size:** The `bufio.Scanner` or `encoding/xml` `Decoder` maintains a fixed-size read buffer (kilobytes) independent of file size. Each record is decoded into a stack-allocated or briefly heap-allocated struct, processed, and then becomes unreachable. A later GC cycle can reclaim those objects; Go 1.26's Green Tea GC can reduce the cost of scanning many small objects, but it does not change the O(1) live-memory argument. The heap footprint of a streaming batch job is dominated by your checkpoint store connection and a handful of live structs, not the file.

**Safe restartability:** Checkpoint + idempotency are separate guarantees that combine multiplicatively. The checkpoint ensures you don't re-process records from the beginning (performance + progress guarantee). Idempotency ensures that records you *do* re-process (the in-flight window since the last checkpoint) don't cause duplicate side effects (correctness guarantee). You need both. A checkpoint without idempotency still double-posts the in-flight window. Idempotency without a checkpoint still re-processes the whole file on every restart. Together: you skip what's already committed, and safely re-run what isn't.

The checkpoint granularity is a tuning knob: commit every 1,000 records balances the cost of a checkpoint write against the worst-case re-processing window (up to 1,000 records on restart). The right number depends on how fast you process records and how expensive re-processing is.

As of **Go 1.26**, `slog.NewMultiHandler` (new in 1.26) lets you fan structured log output to multiple destinations simultaneously — useful for a batch job that needs to log to both stdout (for the operator) and a structured audit sink. Pair with `slog.GroupAttrs` (1.25) to attach job ID and checkpoint position to every log line.

</UnderTheHood>

```go
	return os.WriteFile(path, data, 0o600)
}

func Load(path string) (Checkpoint, error) {
	data, err := os.ReadFile(path)
	if err != nil {
		return Checkpoint{}, err
	}
	var cp Checkpoint
	if err := json.Unmarshal(data, &cp); err != nil {
		return Checkpoint{}, fmt.Errorf("unmarshal checkpoint: %w", err)
	}
	return cp, nil
}

func main() {
	cp := Checkpoint{JobID: "ach-2026-06-04", RecordNum: 14500, TotalCents: 982500}
	path := "/tmp/ach_checkpoint.json"
	if err := Save(path, cp); err != nil {
		fmt.Println("save error:", err)
		return
	}
	loaded, err := Load(path)
	if err != nil {
		fmt.Println("load error:", err)
		return
	}
	fmt.Printf("Loaded: job=%s record=%d total=$%d.%02d\n",
		loaded.JobID, loaded.RecordNum, loaded.TotalCents/100, loaded.TotalCents%100)
}
```

The checkpoint file is written with `0o600` permissions — readable only by the process owner. In production, prefer the DB row approach for atomicity with the ledger commit.

</Solution>

Build an `InMemoryLedger` with a `PostReturn(traceNum string, amountCents int64) (bool, error)` method. It should return `(true, nil)` on a new posting and `(false, nil)` if the trace number was already posted (idempotent skip). Store entries in a `map[string]int64`. Write a `main` that posts the same trace number twice and verifies only one entry exists.

<Solution>

```go
package main

import (
	"fmt"
	"sync"
)

// InMemoryLedger is a toy ledger for demonstrating idempotent posting.
// In production: a Postgres table with a UNIQUE constraint on trace_number.
type InMemoryLedger struct {
	mu      sync.Mutex
	entries map[string]int64 // trace_number → amount_cents
}

func NewLedger() *InMemoryLedger {
	return &InMemoryLedger{entries: make(map[string]int64)}
}

// PostReturn posts a return entry idempotently.
// Returns (true, nil) if posted, (false, nil) if already exists.
func (l *InMemoryLedger) PostReturn(traceNum string, amountCents int64) (bool, error) {
	l.mu.Lock()
	defer l.mu.Unlock()
	if _, exists := l.entries[traceNum]; exists {
		return false, nil // idempotent skip
	}
	l.entries[traceNum] = amountCents
	return true, nil
}

func (l *InMemoryLedger) TotalCents() int64 {
	l.mu.Lock()
	defer l.mu.Unlock()
	var total int64
	for _, v := range l.entries {
		total += v
	}
	return total
}

func main() {
	ledger := NewLedger()

	// Post the same trace number three times — only the first should stick.
	traces := []struct {
		trace  string
		amount int64
	}{
		{"091000010000001", 12500},
		{"091000010000001", 12500}, // duplicate
		{"091000010000002", 7500},
		{"091000010000001", 12500}, // duplicate again
	}

	for _, t := range traces {
		posted, err := ledger.PostReturn(t.trace, t.amount)
		if err != nil {
			fmt.Println("error:", err)
			return
		}
		if posted {
			fmt.Printf("posted  %s $%d.%02d\n", t.trace, t.amount/100, t.amount%100)
		} else {
			fmt.Printf("skipped %s (already posted)\n", t.trace)
		}
	}

	total := ledger.TotalCents()
	fmt.Printf("\nledger total: $%d.%02d (2 unique entries)\n", total/100, total%100)
}
```

The `sync.Mutex` protects the map. In the real implementation, the `UNIQUE` constraint on `trace_number` plus `ON CONFLICT DO NOTHING` in Postgres does the same job — at database scope, which is where you want it for a distributed system.

<Recap>

You now own the batch stack:

- **Batch still rules in fintech** — ACH settlement, nightly reconciliation, statement generation, and bank-file ingest are batch workloads by protocol, not by choice. Batch and streaming are complements, not competitors.
- **NACHA / ACH** files are 94-character fixed-width records. Parse by byte offset (1-based positions → 0-based Go slices). Amount is integer cents — never a float. The Trace Number (positions 80–94) is your natural dedup key.
- **ISO 20022 (pain.001)** XML carries modern wire and SEPA payments. Stream it with `encoding/xml`'s `Decoder.Token()` + `DecodeElement` — never `xml.Unmarshal` the whole document.
- **Stream, never load.** `bufio.Scanner` for line-oriented files, `encoding/csv`'s `Read()` for CSV, `encoding/xml`'s `Decoder` for XML. Memory is O(1) in file size — you hold one record, not the file. Set the `bufio.Scanner` buffer if lines might exceed 64 KiB.
- **Checkpointing** records your byte offset / record number after each committed batch. On restart, seek to that offset and resume mid-file. Write the checkpoint in the same transaction as the ledger commit.
- **Idempotent re-processing** ensures crash + retry never double-posts. Use the trace number as a dedup key with `ON CONFLICT DO NOTHING`, or a pre-insert existence check. Append-only corrections — never mutate posted entries.

</Recap>
