## The Coupling Problem

Let's see the weld before we cut it.

Meridian's monolith settles a transfer. The instant `POST /transfers` commits, four things must happen: the **ledger** posts the double-entry lines, the **notifier** emails a receipt, the **fraud** module updates its rolling risk score, and the **analytics** module records the conversion. Today the transfers handler just... calls all four.

```go
// transfers/handler.go — the welded version (do NOT ship this)
func (h *Handler) Complete(ctx context.Context, t Transfer) error {
	if err := h.ledger.Post(ctx, t); err != nil {
		return err // notifier, fraud, analytics never ran
	}
	if err := h.notifier.SendReceipt(ctx, t); err != nil {
		return err // fraud + analytics never ran; ledger already committed
	}
	if err := h.fraud.Observe(ctx, t); err != nil {
		return err
	}
	return h.analytics.Record(ctx, t)
}
```

Look at what this `Handler` now *knows*. It imports `ledger`, `notifier`, `fraud`, and `analytics`. It knows the order they run in. It knows their method names. Add a fifth consumer — a webhook dispatcher — and you edit this function and recompile the transfers module to teach it about a module it has no business knowing. That is the definition of **tight coupling**: a change *there* forces a change *here*.

**On the job:** you hit this the moment a second module cares about something the first module did. The transfers handler should know how to move money. The instant it also has to know who's *watching* it move money, every new feature becomes a surgery on the hottest code path you own — and a slow notifier turns a successful transfer into a timed-out request.

<Define term="Event bus" since="Messaging & Pub/Sub Foundations (Part 3)">
An **event bus** is an in-process publish/subscribe mediator. A component *publishes* a typed event to the bus and returns immediately; it does not know or care who is listening. Other components *subscribe* to the event types they care about and receive a copy of each one. The publisher and subscribers are decoupled completely — they share a type, not a function call. It is the broker pattern from the last chapter, collapsed into a single address space: the "network" is a channel, the "message" is a Go value.
</Define>

The fix: the transfers handler stops calling anyone. It **publishes one event** — `TransferCompleted` — to a bus, and returns. Whoever cares, subscribes. The handler's import list shrinks to one thing: the bus.

## A Naive Channel Bus

Let's build the simplest thing that works, then watch it fail in an instructive way.

You already know channels are Go's in-process pipe. So the crudest possible bus is: keep a slice of subscriber channels; to publish, send the value to each one. Here it is, carrying Meridian's `TransferCompleted` event to a ledger listener and a notifier listener.

```go
package main

import (
	"fmt"
	"sync"
)

// TransferCompleted is the one fact the transfers module announces.
type TransferCompleted struct {
	TransferID string
	Cents      int64
}

// TransferBus carries exactly one event type. No generics, no reflection.
type TransferBus struct {
	mu   sync.Mutex
	subs []chan TransferCompleted
}

// Subscribe hands back a receive-only channel of future events.
func (b *TransferBus) Subscribe() <-chan TransferCompleted {
	ch := make(chan TransferCompleted, 16) // buffered so Publish doesn't block on a slow reader
	b.mu.Lock()
	b.subs = append(b.subs, ch)
	b.mu.Unlock()
	return ch
}

// Publish fans one event out to every subscriber.
func (b *TransferBus) Publish(ev TransferCompleted) {
	b.mu.Lock()
	defer b.mu.Unlock()
	for _, ch := range b.subs {
		ch <- ev // each subscriber gets its own copy
	}
}

func main() {
	bus := &TransferBus{}
	ledger := bus.Subscribe()
	notifier := bus.Subscribe()

	bus.Publish(TransferCompleted{TransferID: "txn-7823", Cents: 4200})

	fmt.Printf("ledger:   post double-entry for %+v\n", <-ledger)
	fmt.Printf("notifier: email receipt for %+v\n", <-notifier)
}
```

That works. It decouples transfers from ledger and notifier — exactly what we wanted. So what's wrong with it?

**It carries one type.** The day the fraud module wants to hear about `AccountFrozen`, and the analytics module wants `LimitRaised`, you are writing `AccountFrozenBus` and `LimitRaisedBus`, each an identical copy-paste with the type swapped. A bus per event type is not a bus — it's a parking lot full of one-seat cars. We want *one* bus that any module can publish *any* event type onto, and subscribers pick out only the types they asked for.

Two instincts are both half-right, and seeing why each fails is the whole lesson:

  <ConceptCard label="“Use generics”">`Bus[T]` is type-safe but it's *still one type per bus instance* — `Bus[TransferCompleted]` and `Bus[AccountFrozen]` are different types that can't share one router. Generics alone can't hold a heterogeneous set of subscribers.</ConceptCard>

The production answer — Tailscale's answer — is to use **both, at different layers**: generics for the *typed edges* the caller touches, and reflection for the *untyped core* that routes. Let's build exactly that.

## Typed Edges with Generics

Here's the design in one sentence: **the caller only ever touches `Publisher[T]` and `Subscriber[T]`; inside, everything is boxed to `any` and routed by `reflect.Type`.**

Start with the typed facades. A `Publisher[T]` is a thin wrapper that knows its event type `T` and forwards values into the untyped bus. A `Subscriber[T]` is a thin wrapper that pulls untyped values out and asserts them back to `T` before the caller sees them. The type safety lives entirely at these two edges.

```go
// Publisher[T] is the typed handle a module uses to emit events of type T.
type Publisher[T any] struct{ bus *Bus }

// Publish[T] registers nothing — it just types a handle onto the shared bus.
func NewPublisher[T any](b *Bus) *Publisher[T] { return &Publisher[T]{bus: b} }

// Emit boxes v into `any` and hands it to the untyped core.
func (p *Publisher[T]) Emit(v T) { p.bus.publish(v) }

// Subscriber[T] is the typed handle a module uses to receive events of type T.
type Subscriber[T any] struct{ ch <-chan T }

// Events is the receive-only channel the module ranges over.
func (s *Subscriber[T]) Events() <-chan T { return s.ch }
```

Notice what the caller sees: `p.Emit(TransferCompleted{...})` won't compile if you hand it an `AccountFrozen`. `for ev := range sub.Events()` gives you a `TransferCompleted`, statically — no assertion, no `, ok`, no switch. The generics buy **compile-time safety at the call site**. The reflection we're about to add buys **runtime routing in the core**. Neither could do the other's job.

## Routing by Type

Now the core. The bus keeps a map from **event type** to the list of subscriber channels that want that type. The key is a `reflect.Type` — Go's runtime handle for "the type `TransferCompleted`," usable as a comparable map key.

```go
package main

import (
	"fmt"
	"reflect"
	"sync"
)

// Bus is the untyped router. One bus carries every event type in the process.
type Bus struct {
	mu   sync.Mutex
	subs map[reflect.Type][]chan any // event type -> subscriber channels
}

func NewBus() *Bus {
	return &Bus{subs: make(map[reflect.Type][]chan any)}
}

// typeOf returns the reflect.Type of T even when T is an interface type.
// reflect.TypeOf(&v).Elem() dereferences a *T, so a nil-interface v still
// yields the right type instead of nil.
func typeOf[T any]() reflect.Type {
	var v T
	return reflect.TypeOf(&v).Elem()
}

// publish boxes v and fans it to every channel registered for v's type.
func (b *Bus) publish(v any) {
	t := reflect.TypeOf(v) // concrete type of the boxed value
	b.mu.Lock()
	// Copy the slice so we hold the lock briefly and never send under it.
	chans := append([]chan any(nil), b.subs[t]...)
	b.mu.Unlock()
	for _, ch := range chans {
		ch <- v // boxed; the Subscriber[T] will unbox it
	}
}

// Publisher[T] / Subscriber[T] — the typed edges.
type Publisher[T any] struct{ bus *Bus }

func NewPublisher[T any](b *Bus) *Publisher[T] { return &Publisher[T]{bus: b} }
func (p *Publisher[T]) Emit(v T)               { p.bus.publish(v) }

type Subscriber[T any] struct{ ch <-chan T }

func (s *Subscriber[T]) Events() <-chan T { return s.ch }

// Subscribe wires a typed subscriber: a raw `chan any` lands in the bus map,
// and a goroutine unboxes each value to T before the caller sees it.
func Subscribe[T any](b *Bus) *Subscriber[T] {
	t := typeOf[T]()
	raw := make(chan any, 16)
	b.mu.Lock()
	b.subs[t] = append(b.subs[t], raw)
	b.mu.Unlock()

	out := make(chan T, 16)
	go func() {
		for v := range raw {
			out <- v.(T) // safe: routing guarantees v's dynamic type is T
		}
	}()
	return &Subscriber[T]{ch: out}
}

// ── Meridian uses it: two event TYPES, one bus ──

type TransferCompleted struct {
	TransferID string
	Cents      int64
}
type AccountFrozen struct {
	AccountID string
	Reason    string
}

func main() {
	bus := NewBus()

	transfers := Subscribe[TransferCompleted](bus)
	freezes := Subscribe[AccountFrozen](bus)

	var wg sync.WaitGroup
	wg.Add(2)
	go func() {
		defer wg.Done()
		ev := <-transfers.Events()
		fmt.Printf("ledger:  post double-entry for %s (%d cents)\n", ev.TransferID, ev.Cents)
	}()
	go func() {
		defer wg.Done()
		ev := <-freezes.Events()
		fmt.Printf("fraud:   account %s frozen: %s\n", ev.AccountID, ev.Reason)
	}()

	// Same bus, two different event types. Each goes only to its subscriber.
	NewPublisher[TransferCompleted](bus).Emit(TransferCompleted{"txn-7823", 4200})
	NewPublisher[AccountFrozen](bus).Emit(AccountFrozen{"acct-19", "velocity rule"})

	wg.Wait()
}
```

<UnderTheHood title="What reflect.Type, interface boxing, and the type assertion actually cost — Go 1.25">

Three mechanics make this work, and each has a price worth knowing.

**1. Boxing into `any`.** When `Emit` passes `v T` to `publish(v any)`, Go puts `v` into an interface value: a two-word pair `(type-pointer, data-pointer)`. The type-pointer references the `*runtime._type` for `TransferCompleted`; the data-pointer references the value (heap-allocated if it escapes, which here it does because it flows through a channel into another goroutine). So each published event is one small interface header plus, usually, one heap allocation for the value. That's the cost of erasing the static type — and it's why a hot path that fires millions of events still measures this.

**2. `reflect.Type` as a map key.** `reflect.TypeOf(v)` reads the type-pointer straight out of that interface header — it's nearly free, just a field read. The returned `reflect.Type` is an interface backed by a single canonical `*rtype` per type, so two `TransferCompleted` values yield the *same* `reflect.Type`, and `==` / map lookup compares one pointer. Routing is an O(1) map probe keyed by a pointer. This is why the map approach is fast despite the word "reflection" scaring people.

**3. The type assertion `v.(T)`.** On the receive side, `out <- v.(T)` checks that the boxed value's type-pointer equals `T`'s and then copies the data word out. Because the bus only ever delivers a value to channels registered under its own type, the assertion *always* succeeds — we could use the comma-ok form defensively, but the invariant is enforced by routing, so the panic form documents "this can't fail." The assertion is a pointer compare plus a copy: cheap.

**Why not skip the extra `out` channel and the goroutine?** Because the bus map must store `chan any` (heterogeneous), but the caller wants `<-chan T`. Something has to unbox. Our teaching version spends a goroutine per subscriber to do it. Tailscale's production bus is smarter: it stores the unboxing *function* (a `dispatchFn` closure) on each subscriber's non-generic core and runs the assertion inside that subscriber's *client* dispatch loop — no per-subscriber, per-event goroutine. We'll see that in the last section. The semantics are identical; the allocation profile is better.

**A cleaner type handle.** Our `typeOf[T]()` helper uses `reflect.TypeOf(&v).Elem()` so it works even when `T` is an interface (a nil interface value would otherwise give a nil type). The real bus uses the purpose-built `reflect.TypeFor[T]()` (Go 1.22+), which returns the `reflect.Type` of `T` directly from the type parameter — no value, no `&`, no `.Elem()` — and caches it once per publisher/subscriber at construction. Same result, less ceremony; prefer `reflect.TypeFor[T]()` in real code.

**Version note:** generics (`[T any]`) are Go 1.18+; `reflect.TypeFor` is Go 1.22+; this all assumes the Go 1.25 runtime. None of the reflection here touches `unsafe` — it's all `reflect`'s safe surface.

</UnderTheHood>

## Backpressure & the Pump

Our teaching bus has a hidden flaw, and it's the same one every real bus must answer: **what happens when a subscriber is slow?**

In our `publish`, the fan-out loop does `ch <- v` for each subscriber. Those channels are buffered (size 16). Fire the seventeenth event at a subscriber that hasn't drained, and `ch <- v` **blocks** — which means the *publisher* blocks, which means the transfers handler that called `Emit` is now stuck waiting on a sluggish analytics module. We've reintroduced the coupling we set out to kill, just dressed as a full channel.

This is **backpressure**, and it is not a bug to be eliminated — it's a force to be *placed deliberately*.

<Define term="Backpressure" since="Messaging & Pub/Sub Foundations (Part 3)">
**Backpressure** is the resistance a slow consumer exerts back on its producer. When a subscriber can't keep up, its buffer fills; once full, the producer must either **block** (wait — preserving every event, at the cost of slowing the producer), **drop** (discard events — protecting the producer's speed, at the cost of losing data), or **grow** an unbounded buffer (preserve everything and stay fast — at the cost of unbounded memory, i.e. an eventual OOM). There is no fourth option; every event bus picks among these three, and the choice *is* the design.
</Define>

The naive answer — make every channel buffer enormous, or unbounded — just trades a stall for an out-of-memory crash under sustained load. The production answer is a **single dispatch goroutine** (call it the *pump*) with a **bounded** internal queue, that imposes a clear ordering and a predictable backpressure point. One goroutine owns the timeline: it reads published events one at a time and hands each to the right subscribers. Because one goroutine sequences everything, you get a property that's otherwise expensive — a **total order** of events.

Here's the bus rebuilt around a pump. Publishers drop events into one inbound channel; the pump owns the subscriber map and does all the sending, so no lock is needed on the hot path and the order is whatever the pump dequeues.

```go
package main

import (
	"fmt"
	"reflect"
	"sync"
)

type envelope struct {
	t reflect.Type
	v any
}

type Bus struct {
	in   chan envelope               // every publish lands here
	subs map[reflect.Type][]chan any // owned solely by the pump goroutine
	done chan struct{}
}

func NewBus() *Bus {
	b := &Bus{
		in:   make(chan envelope, 16), // bounded: the one backpressure point
		subs: make(map[reflect.Type][]chan any),
		done: make(chan struct{}),
	}
	go b.pump()
	return b
}

// pump is the single goroutine that owns subs and sequences delivery.
func (b *Bus) pump() {
	for env := range b.in {
		for _, ch := range b.subs[env.t] {
			ch <- env.v // backpressure: a full subscriber stalls the pump
		}
	}
	close(b.done)
}

func typeOf[T any]() reflect.Type {
	var v T
	return reflect.TypeOf(&v).Elem()
}

// register runs ON the pump goroutine via a tiny control message, so subs is
// never touched concurrently. For brevity here we register before pump work
// begins; the lab makes you handle concurrent registration properly.
func (b *Bus) publish(v any) { b.in <- envelope{t: reflect.TypeOf(v), v: v} }

type Publisher[T any] struct{ bus *Bus }

func NewPublisher[T any](b *Bus) *Publisher[T] { return &Publisher[T]{bus: b} }
func (p *Publisher[T]) Emit(v T)               { p.bus.publish(v) }

type Subscriber[T any] struct{ ch <-chan T }

func (s *Subscriber[T]) Events() <-chan T { return s.ch }

func Subscribe[T any](b *Bus) *Subscriber[T] {
	t := typeOf[T]()
	raw := make(chan any, 16)
	b.subs[t] = append(b.subs[t], raw) // safe here: called before any publish
	out := make(chan T, 16)
	go func() {
		for v := range raw {
			out <- v.(T)
		}
	}()
	return &Subscriber[T]{ch: out}
}

type TransferCompleted struct{ TransferID string }

func main() {
	bus := NewBus()
	led := Subscribe[TransferCompleted](bus)
	ntf := Subscribe[TransferCompleted](bus)

	var wg sync.WaitGroup
	wg.Add(2)
	go func() { defer wg.Done(); fmt.Println("ledger:  ", (<-led.Events()).TransferID) }()
	go func() { defer wg.Done(); fmt.Println("notifier:", (<-ntf.Events()).TransferID) }()

	NewPublisher[TransferCompleted](bus).Emit(TransferCompleted{"txn-7823"})
	wg.Wait()
}
```

## The Actor Model

Step back from channels for a second, because the bus is really a vehicle for a *design discipline*, and that discipline has a name.

<Define term="Actor model">
The **actor model** structures a program as independent **actors**, each owning its own private state, that never touch each other's memory. An actor changes the world in exactly two ways: it **emits** messages, and it **reacts** to messages it receives. There is no shared mutable state to lock, because there is no sharing — coordination happens entirely through message passing. An event bus is the message-passing substrate; each subscribing module is an actor.
</Define>

Tailscale's bus documentation says it plainly: structure each component to **hold authority over its own state and interact with everything else only by emitting and receiving events.** The ledger module owns the ledger. Nobody reaches into it; they publish facts, and it decides what to do. The fraud module owns its risk scores. Nobody mutates them; they publish `TransferCompleted` and fraud updates *itself*.

This is why the bus guarantees a **total order** ("one true timeline," in their docs): if every actor only reacts to a single, agreed sequence of events, then every actor sees the same history, and the system as a whole has one coherent story of what happened — which is exactly what you want when that story is a sequence of money movements.

## Why So Many Parts

Here's the honest thing about reading `util/eventbus` cold: it looks like *overkill*. There's a `Bus`, a `Client`, a `subscribeState`, a `subscriber` interface, a `Subscriber[T]`, a `subscriberCore`, a `SubscriberFunc[T]`, a `PublishedEvent`, a `DeliveredEvent`, and a tangle of methods named `dispatch`, `dispatchFunc`, and `dispatchTyped` that call *each other*. The natural reaction is "why on earth does an event bus need ten types?"

The answer is the best kind of lesson Go has to offer: **every one of those parts exists to fix a specific problem the previous version created.** Nobody designed this all at once. It grew, one forced move at a time. So let's grow it the same way — start from the naive bus you already built, and at each step, break it, see exactly *why* it breaks, and add the one part that fixes it. By the end, all ten types will feel not just sensible but *inevitable*.

We'll keep using Meridian's two event types — `TransferCompleted` and `AccountFrozen` — as our stand-ins for any two unrelated events on one bus.

### Problem 1 → the pump: ordering across publishers

You already met this in "Backpressure & the Pump," but now it's the *first domino*, so look again. In the naive bus, `publish` itself walks the subscriber slice and sends. So if the transfers goroutine and the fraud goroutine both publish at the same instant, each is running `publish` independently, sending to subscribers at its own pace. A subscriber listening to both types can see them **interleaved in any order** — and worse, two different subscribers can disagree on the order. For a stream of money events, "no agreed order" is a non-starter.

**The fix** is the single pump goroutine: publishers stop sending directly and instead drop their event into one channel; *one* goroutine drains that channel and does all the delivery. Because one goroutine decides "next," there is now exactly one order — the "one true timeline."

```go
type Bus struct {
	write chan PublishedEvent // every publisher writes here
	// ...
}

func (b *Bus) pump() {
	for evt := range b.write { // ONE goroutine, so ONE order
		// ... deliver evt to its subscribers ...
	}
}
```

### Problem 2 → non-generic wrappers: the pump can't type-assert

Now the move that shapes *everything else*, and the single most important idea in this whole codebase. Watch what happens when we try to write the delivery step inside `pump`.

To deliver, the pump must take the boxed `any` event and send it on a subscriber's *typed* channel — which means it must do the assertion `evt.(TransferCompleted)`. But to write `evt.(T)`, the code needs `T` in scope. And here's the wall:

<Define term="Type parameter scope">
A **type parameter** like the `T` in `func Subscribe[T any]()` exists *only inside that generic function or method*. A plain, non-generic function has no `T` — there is no type variable for it to name. So you can box a value into `any` anywhere, but you can only *un*box it with `v.(T)` somewhere that `T` is a visible type parameter. This is the constraint the entire bus is built around.
</Define>

The pump is a method on `Bus`. `Bus` is **not** generic — it has to hold subscribers of *many* event types at once, so it can't carry a single `T`. Therefore the pump has no `T`, therefore it **cannot** write `evt.(T)`. The code simply won't compile.

```go
func (b *Bus) pump() {
	for evt := range b.write {
		for _, sub := range b.subs[evt.Type] {
			sub.ch <- evt.Event.(???) // ← what T? The pump has none. Won't compile.
		}
	}
}
```

So the type assertion **cannot happen in the bus**. It can only happen back out at the edges, inside a generic function where `T` is in scope. Every awkward-looking part that follows is a consequence of shuttling events through the non-generic middle and only ever unboxing them at a generic edge.

The first thing this forces: the events moving through the non-generic core must themselves be carried in **non-generic envelopes**. That's exactly what `PublishedEvent` and `DeliveredEvent` are — plain structs whose payload is an `any`:

```go
type PublishedEvent struct {
	Event any      // the boxed event — assertion deferred to a generic edge
	From  *Client  // who published it (for ordering + debugging)
}

type DeliveredEvent struct {
	Event any
	From  *Client
	To    *Client  // which subscriber it's headed to
}
```

The second thing it forces: a **non-generic stand-in for "a subscriber,"** because the non-generic bus can't hold a `Subscriber[T]` (that would require a `T`). Enter `subscribeState` — a plain struct the bus *can* store, with its own delivery channel and its own map of outputs:

```go
type subscribeState struct {
	client  *Client
	write   chan DeliveredEvent          // the bus pump delivers here
	outputs map[reflect.Type]subscriber  // type → the real (generic) subscriber
}
```

So the bus's routing table changes from "type → channels" to **"type → `subscribeState`s"**, and the pump's job shrinks to: look up the `subscribeState`s for the event's type, and hand each one a `DeliveredEvent`. No assertion needed — it's all non-generic structs and channels. The assertion has been pushed one layer further out, to whoever owns the `subscribeState`.

And who owns it? We *still need the generic `Subscriber[T]`*, because the assertion has to land somewhere that `T` is in scope, and `Subscriber[T]` is the only place that is. So the `subscribeState` will route to a `Subscriber[T]`, and the `Subscriber[T]` runs its own little loop that finally does `evt.(T)` and sends on its typed channel.

### Problem 3 → the Client: ordering across subscriptions

We fixed ordering across *publishers* with one pump. But if every call to `Subscribe` spins up its own `subscribeState` with its own goroutine, then a component that subscribes to *both* `TransferCompleted` and `AccountFrozen` has **two** independent goroutines pulling events — and they can fall out of order relative to each other again. The "one true timeline" leaks at the subscription boundary.

**The fix** is the `Client`: a named handle that owns **one** `subscribeState` and therefore **one** dispatch goroutine, no matter how many event types it subscribes to. All of that client's subscriptions are served by that single goroutine, so they're delivered in the one true order.

```go
client := bus.Client("fraud-engine") // one subscribeState, one goroutine
frz := Subscribe[AccountFrozen](client)
tx  := Subscribe[TransferCompleted](client)
// both served in publication order by the SAME goroutine
```

This is also why `Bus.Client(name)` wants a human name: it's the unit of "an actor," and the name shows up in the debugger so you can see which subsystem is behind a slow subscriber.

To make the non-generic `subscribeState` able to call the generic `Subscriber[T]` it routes to, we need a contract between them that doesn't mention `T`. That's the **`subscriber` interface**:

<Define term="Interface (as a non-generic bridge)">
An **interface** is a set of method signatures; any type implementing those methods satisfies it, and you can hold it in a variable whose static type is the interface — *without knowing the concrete type*. Here it's the bridge across the generic boundary: `subscribeState` holds its outputs as the non-generic `subscriber` interface, and the generic `Subscriber[T]` implements that interface. The non-generic side can call `sub.dispatch(...)` without ever naming `T`; the concrete `Subscriber[T]` on the other end *does* know `T` and does the assertion.
</Define>

```go
type subscriber interface {
	subscribeType() reflect.Type
	dispatch(/* queue + control channels */) bool
	Close()
}
```

### Problem 4 → the queue + multi-way select: a slow subscriber can't stall the pump

The `subscribeState` delivers to a `Subscriber[T]` over a single channel. If that subscriber is slow and its channel fills, the send blocks — which blocks the `subscribeState`'s goroutine, which blocks the bus pump feeding it, which blocks **every** publisher. One sluggish handler freezes the whole bus.

**The fix** is to never let the delivering loop get stuck. The dispatch loop runs a **multi-way `select`**: one case tries to send the current event to the subscriber; *another case, in the same select,* keeps **accepting** newly-arriving events into an internal **queue** so the upstream pump is never blocked just because this one subscriber is slow; a third case handles shutdown.

```go
for {
	select {
	case s.read <- t:        // 1. subscriber took the event — done with it
		vals.Drop()
		return true
	case val := <-acceptCh(): // 2. subscriber still busy — buffer the next event
		vals.Add(val)         //    so the pump upstream doesn't stall
	case <-ctx.Done():        // 3. bus closing — bail out cleanly
		return false
	}
}
```

`acceptCh()` is a small function that returns the inbound channel — or `nil` when the queue is full, which (since a receive on a `nil` channel blocks forever) is exactly how you *re-enable* backpressure once the buffer is genuinely exhausted. (In our teaching bus we used a buffered channel for the same effect; this is the grown-up version with an explicit queue and an explicit "still accepting" case.)

### Problem 5 → the subscriberCore: one itab instead of one per event type

Now a pure-Go cost problem, and the reason there's a `subscriberCore` at all. `Subscriber[T]` implements the `subscriber` interface. But `Subscriber[TransferCompleted]` and `Subscriber[AccountFrozen]` are **different concrete types**, so Go generates separate interface plumbing for each.

<Define term="itab (interface table)">
When a concrete type is stored in an interface, Go builds an **itab** — an interface method table mapping the interface's methods to that concrete type's implementations, so a call like `sub.dispatch(...)` can find the right code at runtime. There's one itab per (interface, concrete type) pair. If `Subscriber[T]` implements `subscriber`, you get a *fresh itab for every event type `T` ever used* — plus a generic method body (a "stencil") per type shape. Each is only tens of bytes, but Tailscale's node software ships on every device and defines many event types, so "per-type" overhead in the binary is real and worth removing.
</Define>

**The fix** is to make a *single, non-generic* type implement the interface, so there's exactly **one** itab regardless of how many event types exist. That type is `subscriberCore`:

```go
type subscriberCore struct {
	typ        reflect.Type
	dispatchFn func(/* queue + control channels */) bool // the per-T work, captured
	// ... slow timer, logf, unregister ...
}

// ONE itab for (subscriber, *subscriberCore), no matter how many event types.
func (c *subscriberCore) dispatch(/* ... */) bool { return c.dispatchFn(/* ... */) }
```

But `subscriberCore` is non-generic — it still can't do the assertion itself. So how does its `dispatch` reach the one place that *can*, the generic `Subscriber[T]`? Through a **closure**.

<Define term="Closure">
A **closure** is a function value that *captures* variables from the scope where it was created, and can use them later when it's called elsewhere. Here, inside the generic constructor `newSubscriber[T]` — where `T` *is* in scope — we build a function that calls `s.dispatchTyped(...)` (the per-`T` method that does `evt.(T)`), and store that function in the non-generic core's `dispatchFn` field. The core later calls `dispatchFn()` without any `T`; the captured closure carries the type knowledge with it.
</Define>

```go
func newSubscriber[T any](/* ... */) *Subscriber[T] {
	s := &Subscriber[T]{ /* ... */ read: make(chan T) }
	// We are inside a generic function: T is in scope HERE. Capture it.
	s.core.dispatchFn = func(/* queue + control channels */) bool {
		return s.dispatchTyped(/* ... */) // the only place evt.(T) can happen
	}
	return s
}
```

That's the whole reason for the `dispatch → dispatchFn → dispatchTyped` call chain that looks so redundant at first glance:

1. The non-generic `subscribeState.pump` holds a `subscriber` interface and calls `sub.dispatch(...)`.
2. The single itab routes that to `(*subscriberCore).dispatch`, which calls its captured `dispatchFn(...)` closure.
3. The closure — born inside `newSubscriber[T]` where `T` lived — calls `(*Subscriber[T]).dispatchTyped`, which finally runs `evt.(T)` and sends on the typed channel.

Three hops, each one a deliberate step across the generic ↔ non-generic boundary, paying for **one** itab instead of one per event type.

### Problem 6 → SubscriberFunc: a friendlier API

Last part, and this one's a convenience, not a correctness fix. With `Subscribe[T]`, the caller gets back a `<-chan T` and has to spin up its own goroutine to range over it. Common and a little tedious. So the bus also offers `SubscriberFunc[T]`: you hand it a callback `func(T)`, and *its* `dispatchFn` runs your callback on a goroutine per event, signaling completion through a `callDone` channel so the same multi-way-select machinery knows when the event is finished.

```go
client.SubscribeFunc(func(ev TransferCompleted) {
	ledger.Post(ev) // the bus runs this for you; no goroutine boilerplate
})
```

It reuses *every* piece above — the core, the interface, the queue, the closure trick — and only swaps "send on a typed channel" for "call a typed function." That it slots in with so little new code is the proof the design's bones are good.

```go
// The bus keeps a map from event type to the SUBSCRIBE STATES interested in it.
// Each Client has one subscribeState (and one dispatch goroutine).
type Bus struct {
	router *worker                            // the central routing goroutine
	write  chan PublishedEvent                // every Publish lands here
	topics map[reflect.Type][]*subscribeState // routing table, keyed by type
	// ...
}

// The central router goroutine (Bus.pump) drains a BOUNDED queue of published
// events — `const maxPublishedEvents = 16` — looks up destinations by
// reflect.TypeOf(event), and hands each event to every destination client's
// dispatch loop. When ITS OWN 16-slot queue is full, its accept channel goes
// nil so it stops taking new publishes: that 16-deep central queue is the
// backstop that bounds the whole bus.
//
// Then each Client's subscribeState.pump unboxes and delivers to that client's
// Subscriber[T] channels. Note: as of tailscale/tailscale#18020 these
// per-subscriber DeliveredEvent queues are UNBOUNDED, so a single slow
// subscriber now grows memory rather than immediately stalling publishers.
// doc.go still documents the blocking-backpressure model and explicitly marks
// those semantics "provisional and subject to change" — so treat the exact
// backpressure behavior as in-flux, and the bounded-central-queue + "receive
// fast, offload slow work" discipline as the stable part.
```

## The Saga Pattern

<Define term="Saga pattern" since="In-Process Pub/Sub: Building an Event Bus (Part 3, Chapter 6) — this chapter">
A **saga** is a design pattern for managing distributed transactions across decoupled services or modules without using two-phase commit (2PC). A saga breaks a distributed operation into a sequence of **local transactions** `T1, T2, ..., Tn`. Each local transaction updates an internal database and emits an event or command. If a step fails, the saga executes a series of **compensating transactions** `Cn-1, ..., C1` in reverse order to semantically undo the committed changes.
</Define>

<Define term="Compensating transaction" since="In-Process Pub/Sub: Building an Event Bus (Part 3, Chapter 6) — this chapter">
A **compensating transaction** is a forward-reversing operation that semantically undoes the effect of a previously committed local transaction. Unlike a database `ROLLBACK` (which physically discards uncommitted data), a compensating transaction runs *after* a local transaction has already committed and become visible to the world. It records a corrective entry (such as releasing a balance hold or refunding a charge) rather than erasing historical data.
</Define>

**On the job:** once you decouple Meridian's monolith into separate modules (Transfers, Accounts, Fraud, External Payouts, Notifications), you lose single-database ACID transactions. An operation like `POST /transfers/cross-border` touches three independent systems and an external clearing network. A database `ROLLBACK` cannot undo an HTTP request sent to SWIFT or Stripe. You need a Saga.

### Why distributed transactions (2PC) fail at scale

When modules or microservices own their own databases, traditional ACID transactions across multiple databases require **Two-Phase Commit (2PC)** with an XA coordinator.

In 2PC:
1. The coordinator asks all databases to **prepare** (locking rows across the network).
2. If all vote yes, the coordinator sends **commit**; if any votes no, it sends **abort**.

Why 2PC is avoided in modern financial systems:
- **Lock amplification & blocking:** Rows remain locked across all services throughout network round-trips. If the coordinator or any network link stalls, all locked rows remain unavailable, starving other transactions.
- **Incompatible with external systems:** External payment APIs (Stripe, Adyen, FedNow, SWIFT) do not participate in database 2PC protocols. You cannot ask a card network to "prepare" a charge and hold a lock for 5 seconds.
- **Availability bottleneck:** By the CAP theorem, 2PC sacrifices availability for strict consistency. A single partition brings the entire workflow to a dead stop.

The **Saga pattern** (first formulated by Hector Garcia-Molina and Kenneth Salem in 1987) replaces cross-service locking with **eventual consistency** and **compensating actions**.

### Compensating transactions: semantic rollbacks

In a Saga, every step $T_i$ commits immediately to its own local datastore. Its changes become visible to the rest of the system.

If step $T_3$ (e.g. External Bank Payout) fails, step $T_1$ (Reserve Sender Funds) and step $T_2$ (Log Compliance Entry) have already committed. We cannot run `ROLLBACK`.

Instead, the Saga executes **compensating transactions** $C_2$ and $C_1$ in reverse order:
- Forward Action $T_1$: Hold $500 from sender account $\to$ Compensating Action $C_1$: Release $500 hold back to sender account.
- Forward Action $T_2$: Record compliance screening $\to$ Compensating Action $C_2$: Mark compliance record as voided/cancelled.

#### Three classes of transactions in a Saga

Every production saga categorizes its steps into three distinct phases:

1. **Compensable transactions (`T_1 ... T_k-1`):** Steps that can be semantically undone. Each compensable step `T_i` MUST have a corresponding compensating step `C_i`.
2. **Pivot transaction (`T_pivot`):** The go/no-go point of the saga. If the pivot transaction succeeds, the saga *must* commit forward to the end. If the pivot fails, the saga compensates backward.
3. **Retriable transactions (`T_pivot+1 ... T_n`):** Steps that follow the pivot. They *cannot* fail permanently; they must be idempotent and retried until they succeed (e.g. posting the final double-entry ledger line or sending customer confirmation emails).

#### Rules for compensating transactions

- **Idempotency is mandatory:** A compensating transaction may be called multiple times if the orchestrator crashes during recovery. `ReleaseHold(transferID)` must produce the exact same outcome whether executed once or ten times.
- **Compensation cannot fail permanently:** If a database is unreachable during compensation, the orchestrator must retry with backoff. If an unrecoverable bug occurs, it must alert human operators immediately.
- **Semantic, not physical:** Compensation appends audit entries (e.g. `HOLD_RELEASED`) rather than deleting previous rows, maintaining double-entry ledger integrity.

### Choreography vs Orchestration

There are two primary ways to coordinate a Saga:

<ConceptGrid cols={2}>
  <ConceptCard label="Choreographed Saga (Event-Driven)">
    **No central coordinator.** Each service listens to events published on the bus, performs its local transaction, and publishes the next event. If a step fails, it publishes a failure event, and participating services listen and run their own compensations.
    
    *Best for:* Simple 2-3 step workflows where adding a coordinator is unnecessary overhead.
  </ConceptCard>
  <ConceptCard label="Orchestrated Saga (State Machine)">
    **Central coordinator.** A dedicated Saga Orchestrator executes a state machine. It calls services directly (via RPC or command messages), waits for responses, records progress in a durable store, and explicitly triggers compensating actions if a step fails.
    
    *Best for:* Complex, multi-step financial flows (transfers, disbursements, KYC verification) requiring clear auditing and monitoring.
  </ConceptCard>
</ConceptGrid>

#### Why high-stakes fintech uses Orchestration

In Choreography, the workflow logic is scattered across multiple services. When a cross-border transfer stalls, answering "what step is this transfer currently waiting on?" requires querying distributed logs across five different services. This is commonly referred to as **distributed spaghetti**.

With an **Orchestrated Saga**:
- The state machine is explicit and lives in one place.
- In-flight sagas can be inspected, paused, retried, or resumed after server restarts.
- Adding a new step (e.g. currency conversion fee calculation) only requires editing the orchestrator, rather than re-wiring event listeners across three independent services.

### Building a Saga Orchestrator in Go

Let's build a production-grade, generic Saga Orchestrator with persistent state tracking, exponential retry timers, and reverse-order compensation.

<GoPlayground>

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"sync"
	"time"
)

type SagaState string

const (
	StatePending      SagaState = "PENDING"
	StateExecuting    SagaState = "EXECUTING"
	StateCompensating SagaState = "COMPENSATING"
	StateCompleted    SagaState = "COMPLETED"
	StateFailed       SagaState = "FAILED"
)

// Step defines a single action in the saga and its matching compensating transaction.
type Step[T any] struct {
	Name       string
	Action     func(ctx context.Context, data *T) error
	Compensate func(ctx context.Context, data *T) error // nil for retriable steps
	MaxRetries int
	RetryDelay time.Duration
}

// SagaRecord represents the persisted state of a saga instance.
type SagaRecord[T any] struct {
	ID          string
	State       SagaState
	CurrentStep int
	Data        T
	UpdatedAt   time.Time
}

// MemorySagaStore simulates a persistent database store (e.g. PostgreSQL table).
type MemorySagaStore[T any] struct {
	mu      sync.Mutex
	records map[string]SagaRecord[T]
}

func NewMemorySagaStore[T any]() *MemorySagaStore[T] {
	return &MemorySagaStore[T]{records: make(map[string]SagaRecord[T])}
}

func (s *MemorySagaStore[T]) Save(_ context.Context, rec SagaRecord[T]) error {
	s.mu.Lock()
	defer s.mu.Unlock()
	rec.UpdatedAt = time.Now()
	s.records[rec.ID] = rec
	return nil
}

func (s *MemorySagaStore[T]) Load(_ context.Context, id string) (SagaRecord[T], bool) {
	s.mu.Lock()
	defer s.mu.Unlock()
	rec, ok := s.records[id]
	return rec, ok
}

// SagaOrchestrator executes forward steps and coordinates reverse compensation on failure.
type SagaOrchestrator[T any] struct {
	store *MemorySagaStore[T]
	steps []Step[T]
}

func NewSagaOrchestrator[T any](store *MemorySagaStore[T], steps []Step[T]) *SagaOrchestrator[T] {
	return &SagaOrchestrator[T]{store: store, steps: steps}
}

func (o *SagaOrchestrator[T]) Execute(ctx context.Context, sagaID string, initialData T) error {
	data := initialData
	rec := SagaRecord[T]{
		ID:          sagaID,
		State:       StateExecuting,
		CurrentStep: 0,
		Data:        data,
	}
	_ = o.store.Save(ctx, rec)

	var failedStep int = -1
	var stepErr error

	// Phase 1: Forward execution loop
	for i, step := range o.steps {
		rec.CurrentStep = i
		_ = o.store.Save(ctx, rec)

		fmt.Printf("[SAGA %s] Executing step %d: %s\n", sagaID, i+1, step.Name)

		// Retry loop with backoff timer
		var err error
		attempts := step.MaxRetries + 1
		for attempt := 1; attempt <= attempts; attempt++ {
			err = step.Action(ctx, &data)
			if err == nil {
				break
			}
			fmt.Printf("  -> step '%s' attempt %d/%d failed: %v\n", step.Name, attempt, attempts, err)
			if attempt < attempts && step.RetryDelay > 0 {
				select {
				case <-time.After(step.RetryDelay):
				case <-ctx.Done():
					return ctx.Err()
				}
			}
		}

		if err != nil {
			failedStep = i
			stepErr = err
			break
		}
	}

	// Phase 2: All forward steps succeeded
	if failedStep == -1 {
		rec.State = StateCompleted
		rec.CurrentStep = len(o.steps)
		rec.Data = data
		_ = o.store.Save(ctx, rec)
		fmt.Printf("[SAGA %s] All steps completed successfully!\n", sagaID)
		return nil
	}

	// Phase 3: Failure encountered — execute reverse compensation
	fmt.Printf("[SAGA %s] Step '%s' failed permanently: %v. Initiating compensation...\n",
		sagaID, o.steps[failedStep].Name, stepErr)

	rec.State = StateCompensating
	_ = o.store.Save(ctx, rec)

	// Iterate backwards from the last completed step down to 0
	for i := failedStep - 1; i >= 0; i-- {
		step := o.steps[i]
		if step.Compensate == nil {
			continue
		}
		fmt.Printf("[SAGA %s] Compensating step %d: %s\n", sagaID, i+1, step.Name)

		// Compensation must succeed; retry until success
		for {
			compErr := step.Compensate(ctx, &data)
			if compErr == nil {
				break
			}
			fmt.Printf("  -> compensation for '%s' failed: %v, retrying...\n", step.Name, compErr)
			time.Sleep(50 * time.Millisecond)
		}
	}

	rec.State = StateFailed
	rec.Data = data
	_ = o.store.Save(ctx, rec)
	fmt.Printf("[SAGA %s] Compensation finished. Final state: FAILED\n", sagaID)
	return fmt.Errorf("saga failed at step %s: %w", o.steps[failedStep].Name, stepErr)
}

// ── Meridian Money Transfer Saga Data ──

type TransferSagaData struct {
	TransferID     string
	SenderID       string
	ReceiverID     string
	AmountCents    int64
	FundsReserved  bool
	FraudPassed    bool
	ExternalBankOK bool
	LedgerPosted   bool
}

func main() {
	ctx := context.Background()
	store := NewMemorySagaStore[TransferSagaData]()

	steps := []Step[TransferSagaData]{
		{
			Name: "Reserve Sender Funds",
			Action: func(ctx context.Context, d *TransferSagaData) error {
				d.FundsReserved = true
				fmt.Printf("  [Accounts] Held %d cents from sender %s\n", d.AmountCents, d.SenderID)
				return nil
			},
			Compensate: func(ctx context.Context, d *TransferSagaData) error {
				d.FundsReserved = false
				fmt.Printf("  [Accounts] RELEASED held %d cents back to sender %s\n", d.AmountCents, d.SenderID)
				return nil
			},
			MaxRetries: 1,
			RetryDelay: 10 * time.Millisecond,
		},
		{
			Name: "Fraud & Compliance Screening",
			Action: func(ctx context.Context, d *TransferSagaData) error {
				d.FraudPassed = true
				fmt.Println("  [Fraud] Risk score: 12/100 (APPROVED)")
				return nil
			},
			Compensate: func(ctx context.Context, d *TransferSagaData) error {
				d.FraudPassed = false
				fmt.Println("  [Fraud] Voided screening audit record")
				return nil
			},
			MaxRetries: 0,
		},
		{
			Name: "External Bank Payout",
			Action: func(ctx context.Context, d *TransferSagaData) error {
				// Simulate external network rejection (e.g. invalid IBAN)
				return errors.New("SWIFT network rejected: invalid destination routing number")
			},
			Compensate: func(ctx context.Context, d *TransferSagaData) error {
				// External call failed; nothing to compensate at the bank
				return nil
			},
			MaxRetries: 2,
			RetryDelay: 20 * time.Millisecond,
		},
		{
			Name: "Post Final Ledger Entries",
			Action: func(ctx context.Context, d *TransferSagaData) error {
				d.LedgerPosted = true
				fmt.Println("  [Ledger] Double-entry posting completed")
				return nil
			},
			Compensate: nil, // Retriable step after clearing pivot
			MaxRetries: 3,
		},
	}

	orchestrator := NewSagaOrchestrator(store, steps)

	data := TransferSagaData{
		TransferID:  "txn_crossborder_4091",
		SenderID:    "acct_alice",
		ReceiverID:  "acct_bob_london",
		AmountCents: 50000,
	}

	err := orchestrator.Execute(ctx, data.TransferID, data)
	if err != nil {
		fmt.Printf("\nResult: %v\n", err)
	}

	rec, _ := store.Load(ctx, data.TransferID)
	fmt.Printf("Final Store State: ID=%s State=%s FundsReserved=%v\n",
		rec.ID, rec.State, rec.Data.FundsReserved)
}
```

<Exercise n={2} title="Drop instead of block" level="medium">

Our bus blocks the publisher when a subscriber's buffer is full (the blocking backpressure choice). For a *lossy* event like a metrics tick, you'd rather drop than stall money movement. Write a `publishLossy(v any)` on the routing bus that sends to each subscriber with a non-blocking `select`/`default`, dropping (and counting) when the channel is full. Demonstrate the drop.

<Solution>

```go
func (b *Bus) publishLossy(v any) (dropped int) {
	t := reflect.TypeOf(v)
	b.mu.Lock()
	chans := append([]chan any(nil), b.subs[t]...)
	b.mu.Unlock()
	for _, ch := range chans {
		select {
		case ch <- v: // delivered
		default:
			dropped++ // buffer full — drop this one, keep the publisher fast
		}
	}
	return dropped
}

// Demo: a subscriber that never receives; fill its buffer (16) then overflow.
type MetricTick struct{ N int }

func main() {
	bus := NewBus()
	_ = Subscribe[MetricTick](bus) // subscribes but never drains
	p := NewPublisher[MetricTick](bus)
	dropped := 0
	for i := 0; i < 25; i++ {
		dropped += bus.publishLossy(MetricTick{i})
	}
	fmt.Printf("dropped %d of 25 ticks (buffer was 16)\n", dropped)
}
```

The `select`/`default` is the entire difference between the *blocking* and *dropping* backpressure strategies — one keyword. Note the buffered `out` channel and the unboxing goroutine mean the real fill point is a little fuzzy (two buffers of 16 plus a goroutine in flight), so the exact drop count varies; the lesson is the *mechanism*, not the number. Choose blocking for money, dropping for telemetry.

</Solution>

</Exercise>

<Exercise n={3} title="Unsubscribe without racing the pump" level="medium">

Add `Unsubscribe[T]` that removes a subscriber and closes its channel so its range loop exits cleanly. The trap: the pump (or `publish`) may be ranging the slice concurrently. Explain how Tailscale dodges the lock contention, and implement a safe version for our lock-based bus.

<Solution>

```go
// Safe for the lock-based routing bus: build a NEW slice without the target,
// then swap it in under the lock. Never mutate the slice the pump might read.
func Unsubscribe[T any](b *Bus, raw chan any) {
	t := typeOf[T]()
	b.mu.Lock()
	old := b.subs[t]
	next := make([]chan any, 0, len(old))
	for _, ch := range old {
		if ch != raw {
			next = append(next, ch)
		}
	}
	b.subs[t] = next // atomic-ish swap of the slice header under the lock
	b.mu.Unlock()
	close(raw) // the unboxing goroutine's `range raw` now returns
}
```

The discipline — **replace the whole slice rather than delete in place** — is exactly what Tailscale's bus does on unsubscribe, so the pump goroutine that's mid-iteration is always walking a slice that won't be mutated underneath it. (Our `publish` already copies the slice before sending for the same reason.) Removing the element with `slices.Delete` in place would be a data race against any concurrent reader; rebuilding sidesteps it. This is the slice-aliasing lesson from the Data, Slices & Maps mistakes chapter, applied under concurrency.

</Solution>

</Exercise>

Show that the pump-based bus produces *one* total order (no interleaving corruption, no lost events), and explain why the lock-based fan-out version can't make the same promise as cleanly.

<Solution>

```go
// With the single-pump bus: both publishers send into the ONE `in` channel.
// The channel serializes concurrent sends, so the pump dequeues a single,
// well-defined sequence. A subscriber to both types sees that exact sequence.
func main() {
	bus := NewBus() // pump-based version
	all := Subscribe[any](bus) // (sketch) or two subs feeding one collector

	var got []string
	var mu sync.Mutex
	done := make(chan struct{})
	go func() {
		for range 200 {
			ev := <-all.Events()
			mu.Lock()
			got = append(got, fmt.Sprintf("%T", ev))
			mu.Unlock()
		}
		close(done)
	}()

	var wg sync.WaitGroup
	wg.Add(2)
	go func() { defer wg.Done(); p := NewPublisher[TransferCompleted](bus); for range 100 { p.Emit(TransferCompleted{}) } }()
	go func() { defer wg.Done(); p := NewPublisher[AccountFrozen](bus);   for range 100 { p.Emit(AccountFrozen{}) } }()
	wg.Wait()
	<-done
	fmt.Printf("observed %d events in one total order\n", len(got))
}
```

The key insight: **the single inbound channel is the serialization point.** Go's channel send is safe under concurrency, so two goroutines racing to `Emit` simply line up; the pump then imposes one order on the whole stream. Every subscriber dispatched by that one pump sees events in that one order — the "one true timeline." The lock-based fan-out version *also* serializes (the mutex does it), but each subscriber runs its own unboxing goroutine with its own buffer, so two subscribers can fall arbitrarily far out of step with each other; there's no single object whose progress *is* the canonical clock. The pump makes "now" a thing you can point at. (Subscribing to `any` is a sketch — in the real bus you'd register one collector that both publishers' types route to; the point is the ordering guarantee, not the literal `any` subscription.)

</Solution>

<Exercise n={5} title="Add a pivot step and retriable action to a Saga" level="hard">

In our `SagaOrchestrator`, compensable steps have matching `Compensate` functions. A **pivot transaction** is the decision boundary: once it succeeds, the saga *must* commit forward to completion and never compensate backward. Any step after the pivot is a **retriable transaction** that has `Compensate: nil` and retries indefinitely until success.

Add support for a pivot step in `SagaOrchestrator`. If a retriable step (after the pivot) fails on its initial attempts, verify that the orchestrator retries until success rather than triggering compensation for pre-pivot steps.

<Solution>

```go
// In the Saga Orchestrator:
// A Step with Compensate == nil following a successful pivot step
// is treated as a retriable transaction that retries until success.
func (o *SagaOrchestrator[T]) ExecuteWithPivot(ctx context.Context, sagaID string, data T) error {
	var pivotPassed bool

	for i, step := range o.steps {
		for {
			err := step.Action(ctx, &data)
			if err == nil {
				if step.Compensate == nil {
					pivotPassed = true
				}
				break
			}

			// If pivot has already passed, retriable steps MUST NOT compensate:
			// they retry with backoff until eventual success.
			if pivotPassed {
				fmt.Printf("post-pivot step %s retrying: %v\n", step.Name, err)
				time.Sleep(100 * time.Millisecond)
				continue
			}

			// Pre-pivot failure: trigger reverse compensation
			return o.compensate(ctx, sagaID, i-1, data, err)
		}
	}
	return nil
}
```

Once the pivot transaction commits (e.g. money transferred across SWIFT), pre-pivot operations (like balance reservation) cannot be rolled back without creating a massive reconciliation imbalance. The post-pivot steps (such as posting ledger lines and sending receipts) must be idempotent and retried until successful.

</Solution>

<Recap>

You can now build, and read, an in-process event bus from first principles:

- An **in-process event bus** applies pub/sub within a single binary: channels act as the wire and Go structs as messages. It **decouples modules** with zero network serialization overhead — but it is **not durable**, so it decouples modules within a process, not independent services.
- The production design uses **generics for typed edges** (`Publisher[T]`/`Subscriber[T]`) and **reflection for the untyped core** (`map[reflect.Type][]chan any`). Generics provide compile-time safety at call sites; reflection enables runtime routing across heterogeneous event types.
- A **single pump goroutine** with a bounded queue guarantees a **total event order** ("one true timeline") and provides a predictable backpressure boundary.
- The bus is the substrate for the **actor model**: each module encapsulates its own state and communicates purely via events, eliminating cross-module mutexes and tight coupling.
- **The Saga Pattern** coordinates multi-step business transactions across decoupled event-driven modules without Two-Phase Commit (2PC). It executes a sequence of local transactions and runs **compensating transactions** (semantic rollbacks) in reverse order if a step fails.
- **Orchestrated Sagas** use a centralized state machine with durable persistence and retry timers to manage forward execution and reverse compensation cleanly, avoiding "distributed spaghetti."

</Recap>
