<HeroCard label="Part 3 · Chapter 6" title="In-Process Pub/Sub: Building an Event Bus">

When a payment commits, Meridian's work isn't finished. A receipt has to be written, the merchant's server has to be told, the fraud checker wants to see it, and the merchant's dashboard should tick up. Today the payment handler does all four itself, one after another, while the customer's checkout waits for its answer. Each of those modules is somebody else's code, with its own speed and its own failures, and all of it runs inside the payment request.

Chapter 5 moved messages between programs with a broker. Most of this problem is inside one program, and it doesn't need a network. This chapter builds an **in-process event bus**: the payment module announces what happened, and the modules that care receive it. The bus is built from Go's generics and channels. Every design choice is measured on the real payment API: what it costs the checkout, what happens when a module is slow, when it panics, when the process is killed, and when a subscriber is forgotten. At the end, it reads and runs the bus Tailscale ships in production.

4. **Backpressure.** A burst the slowest subscriber can't keep up with: block, or drop?
5. **Failure.** A panicking handler, a killed process, and a subscription nobody closed.

## The lab bench

Everything in this chapter is measured on a Go module, `meridian` (Go 1.27.0, on an 8-core Apple M1 running macOS). The payment is posted to chapter 2's double-entry ledger on PostgreSQL 14.19, through `github.com/jackc/pgx/v5` v5.11.0. The module's packages:

- `payments`: the `POST /payments` handler. It posts the payment to the ledger and produces a `PaymentSucceeded` event.
- `receipts`, `webhooks`, `fraud`, `dashboard`: the four modules that react to a payment. They're described in stop 1.
- `coupled`: the handler before this chapter, which calls the four modules itself.
- `syncbus` and `bus`: the two event buses this chapter builds.
- `cmd/checkout`: runs the API as a real HTTP server, with the modules wired one of three ways, and sends it payments from many concurrent checkouts at a fixed rate. It reports what the checkouts saw and what each module did.
- `cmd/order`, `cmd/leak`, `cmd/tsbus` and the tests in `bus/`: the other experiments, introduced where they're used.

Stop 6 runs Tailscale's bus, `tailscale.com/util/eventbus` from `tailscale.com` v1.102.5, and the tests use `go.uber.org/goleak` v1.3.0.

The event every module receives is a plain struct:

```go noverify
// events/events.go, lines 1–24
// Package events holds the facts Meridian's modules tell each other.
// An event describes something that has already happened, so it is
// named in the past tense, and nobody can refuse it.
package events

import "time"

// Card is the card a payment was made with.
type Card struct {
	Last4   string
	Country string // where the card was issued (ISO 3166)
}

// PaymentSucceeded is published once a payment has committed to the
// ledger. It is passed by value: every subscriber gets its own copy of
// the struct (but shares what Card points to, so nobody may change it).
type PaymentSucceeded struct {
	ID       string // "pay-<ledger transaction id>"
	Merchant string
	Amount   int64 // cents
	Currency string
	Card     *Card // nil for a bank transfer
	At       time.Time
}
```

The event is passed by value: each subscriber gets its own copy of the struct. `Card` is a pointer, though, so every copy points at the same `Card`, and nobody may change it. The `nil` card on a bank transfer comes back in stop 5.

## Coupling

*Stop 1 of 6.*

### Step 1: what happens after a payment commits

When a payment's ledger transaction commits, the money has moved. Four other parts of Meridian care:

- **receipts** writes a receipt file for the merchant, then calls `fsync` before it reports success. `fsync` asks the operating system to push the file's bytes all the way to the physical disk and wait until they're there. Without it, the bytes can sit in memory for seconds, and a power cut loses them. On macOS, Go's `(*os.File).Sync` uses `F_FULLFSYNC`, which flushes the drive's own cache too.
- **webhooks** tells the merchant's server about the payment: an HTTP `POST` of the event as JSON, to a URL the merchant gave Meridian.
- **fraud** keeps the last minute of payments for each card, and flags a card used more than five times in a minute, or a card issued in another country.
- **dashboard** keeps each merchant's takings and latest payment in memory, for their live dashboard.

### Step 2: the handler that calls them all

Before this chapter, the payment handler calls each module itself. Watch lines 13 to 24: after the payment has committed, the request goroutine does four more jobs, and two of them can fail the request.

```go noverify
// coupled/coupled.go, lines 26–50
func (h *Handler) ServeHTTP(w http.ResponseWriter, r *http.Request) {
	req, err := payments.Decode(r)
	if err != nil {
		http.Error(w, err.Error(), http.StatusBadRequest)
		return
	}
	ev, err := payments.Post(r.Context(), h.DB, req)
	if err != nil {
		http.Error(w, err.Error(), http.StatusInternalServerError)
		return
	}
	// The payment has committed. Everything below is somebody else's job,
	// done on this request's time, and able to fail this request.
	if err := h.Receipts.Write(ev); err != nil {
		http.Error(w, "receipt: "+err.Error(), http.StatusInternalServerError)
		return
	}
	if err := h.Webhooks.Send(r.Context(), ev); err != nil {
		http.Error(w, "webhook: "+err.Error(), http.StatusBadGateway)
		return
	}
	h.Fraud.Check(ev)
	h.Dashboard.Record(ev)
	json.NewEncoder(w).Encode(map[string]string{"id": ev.ID})
}
```

### Step 3: what each step costs

Before measuring the whole thing, `cmd/modcost` times each step on its own, 1,000 times:

```text

receipts: write + fsync    p50   4.152ms   p99   8.276ms
webhooks: HTTP POST        p50      68µs   p99     203µs
fraud: check               p50      <1µs   p99      <1µs
dashboard: record          p50      <1µs   p99      <1µs
```

The payment itself, a real Postgres transaction, takes 0.27 ms at the median. The receipt takes 4.2 ms, fifteen times longer, and almost all of that is `fsync` waiting for the disk. The webhook to a local server takes 68 µs, and fraud and dashboard take under a microsecond each.

`cmd/checkout` starts the API as a real HTTP server and sends it 150 payments a second for 10 seconds. ### Step 6: three kinds of coupling

Two modules are **coupled** when a change or a failure in one forces something on the other. The payment handler is coupled to its four modules in three ways:

- **In code.** `coupled` imports all four packages. Adding a fifth reaction to a payment, say loyalty points, means editing the payment handler:

```text
meridian/coupled imports: meridian/dashboard meridian/fraud meridian/payments meridian/receipts meridian/webhooks
```

- **In time.** The checkout waits for the sum of everything after the commit: 5.72 ms at the median.
- **In failure.** A module's error became the payment's error: 150 times in one second of outage.

The rest of the chapter removes them one at a time, and measures each step.

## A Typed Bus

*Stop 2 of 6.*

### Step 1: announce, don't call

The payment module doesn't need to know who cares about a payment. It needs to say that one happened. That statement is an **event**: a value describing something that has already happened, named in the past tense, `PaymentSucceeded`. Nobody can refuse an event. They can only react to it.

An **event bus** connects the two sides:

- A **publisher** hands the bus an event: `bus.Publish(ev)`.
- A **subscriber** registers a function for a kind of event: `bus.Subscribe(fn)`. The bus calls it for each event of that kind.

The publisher and the subscribers only know the bus and the event type. That's the "code" coupling gone. This pattern is called **publish/subscribe**, and inside one program it needs no network, no broker and no serialisation: an event is a Go value, handed from one function to another.

### Step 2: the kind of event is its Go type

Receipts needs `PaymentSucceeded` and, later, `RefundIssued`. Something has to decide which subscribers get which event. Brokers use topic names, strings like `"payments.succeeded"`. Inside one Go program, the event's own type can do the job, and the compiler then checks that the subscriber and the publisher agree on it.

So the bus keeps a map from a type to the functions subscribed to it:

```go noverify
handlers map[reflect.Type][]func(any)
```

Read it from the outside in:

- `map[K]V` is a hash map from keys of type `K` to values of type `V`.
- The key, `reflect.Type`, is a value that describes a Go type at run time. `reflect.TypeFor[PaymentSucceeded]()` (Go 1.22) returns the one describing `PaymentSucceeded`, and it's equal to every other `reflect.Type` for that same type, so it works as a map key.
- The value, `[]func(any)`, is a list of functions that each take one argument of any type.

Why `func(any)`, when a receipts subscriber is a `func(PaymentSucceeded)`? Because one map holds subscribers for every event type, and a Go map has one value type. So `Subscribe` wraps each function:

```go noverify
func(v any) { fn(v.(T)) }
```

`v.(T)` is a **type assertion**: "`v` holds a `T`; give it to me as a `T`". If `v` held anything else, it would panic. Here it can't: the wrapper is stored under `T`'s key, so only `T` values ever reach it.

### Step 3: generic methods, new in Go 1.27

`Subscribe` has to work for any event type, and keep that type all the way to the subscriber's function. That's what a **type parameter** is for: `Subscribe[T any](fn func(T))` is written once and works for every `T`, and at the call `bus.Subscribe(func(p PaymentSucceeded) { ... })` the compiler works out that `T` is `PaymentSucceeded`.

Until Go 1.27, a **method** (a function with a receiver, like `func (b *Bus) Subscribe`) couldn't have type parameters. Libraries had to write package-level functions instead, `Subscribe[T](bus, fn)`. Tailscale's bus in stop 6 still does, because its module declares `go 1.26.6`. Go 1.27 allows them. The same code under a `go 1.26` directive, with the Go 1.27 toolchain, is rejected:

```text
./main.go:10:24: syntax error: method must have no type parameters
```

Two limits remain. An interface can't declare a generic method (`interface method must have no type parameters`), so a generic method never satisfies an interface. And in go1.27.0, one form of inference crashes the compiler: assigning `bus.Publish` to a struct field of type `func(PaymentSucceeded)`, in a composite literal, reports `internal compiler error: func[T any](ev T) is not assignable to func(string)` in the smallest reproduction. Writing the type argument out, `bus.Publish[events.PaymentSucceeded]`, works, and that's what this chapter's code does.

### Step 4: the whole bus, runnable

Here is the synchronous bus as a complete program. Look at the order of the output: the handlers print *before* `Publish returned`.

<GoPlayground>

```go
// A synchronous, type-safe event bus. Publish calls each subscriber's
// function in turn, on the publisher's goroutine.
package main

import (
	"fmt"
	"reflect"
	"sync"
)

type Bus struct {
	mu       sync.RWMutex
	handlers map[reflect.Type][]func(any) // event type → its subscribers
}

func NewBus() *Bus { return &Bus{handlers: map[reflect.Type][]func(any){}} }

// Subscribe is a generic method (Go 1.27): T is worked out from fn.
func (b *Bus) Subscribe[T any](fn func(T)) {
	b.mu.Lock()
	defer b.mu.Unlock()
	t := reflect.TypeFor[T]()
	b.handlers[t] = append(b.handlers[t], func(v any) { fn(v.(T)) })
}

// Publish calls every subscriber to T, and returns when they all have.
func (b *Bus) Publish[T any](ev T) {
	b.mu.RLock()
	hs := b.handlers[reflect.TypeFor[T]()]
	b.mu.RUnlock()
	for _, h := range hs {
		h(ev)
	}
}

type PaymentSucceeded struct {
	ID     string
	Amount int64 // cents
}

type RefundIssued struct {
	PaymentID string
	Amount    int64
}

func main() {
	bus := NewBus()
	bus.Subscribe(func(p PaymentSucceeded) { fmt.Println("  receipts:  receipt for", p.ID) })
	bus.Subscribe(func(p PaymentSucceeded) { fmt.Printf("  dashboard: +$%d.%02d\n", p.Amount/100, p.Amount%100) })
	bus.Subscribe(func(r RefundIssued) { fmt.Println("  receipts:  refund note for", r.PaymentID) })

	fmt.Println("payments: publish pay-1041")
	bus.Publish(PaymentSucceeded{ID: "pay-1041", Amount: 1999})
	fmt.Println("payments: Publish returned")
	bus.Publish(RefundIssued{PaymentID: "pay-1041", Amount: 1999})
	bus.Publish("pay-1041") // compiles, and reaches nobody: no one subscribed to string
}
```

A synchronous bus decouples code, not time. It also changes failure in one way: a handler is a `func(T)` with nothing to return, so a webhook error can't fail the payment any more. The webhooks module has to deal with its own failures.

## Channels

*Stop 3 of 6.*

### Step 1: a queue and a goroutine for each subscriber

To take the modules off the checkout's clock, each subscriber gets two things of its own:

- a **queue** of events waiting for it, and
- a **goroutine** that takes events off that queue, one at a time, and calls the subscriber's function.

`Publish` then only puts the event into each subscriber's queue and returns. The payment handler answers the checkout, and each module works through its queue in its own time.

The queue is a **buffered channel**. `make(chan any, 64)` makes a channel that can hold 64 values. `ch <- v` (a **send**) puts `v` in, and waits only if all 64 slots are taken. `<-ch` (a **receive**) takes the oldest value out, and waits only if the channel is empty. So a channel is a first-in, first-out queue that goroutines can share safely.

### Step 2: the smallest version

The same idea as a complete program. `receipts` is made busy on purpose, by waiting on a channel `main` controls, so that the output is the same on every run:

<GoPlayground>

```go
// An asynchronous event bus: every subscriber has its own buffered
// channel and its own goroutine.
package main

import (
	"fmt"
	"reflect"
	"sync"
)

type Bus struct {
	mu   sync.Mutex
	subs map[reflect.Type][]chan any
	wg   sync.WaitGroup
}

func NewBus() *Bus { return &Bus{subs: map[reflect.Type][]chan any{}} }

func (b *Bus) Subscribe[T any](buffer int, fn func(T)) {
	ch := make(chan any, buffer)
	b.mu.Lock()
	b.subs[reflect.TypeFor[T]()] = append(b.subs[reflect.TypeFor[T]()], ch)
	b.mu.Unlock()
	b.wg.Go(func() { // the subscriber's goroutine
		for v := range ch {
			fn(v.(T))
		}
	})
}

// Publish puts ev in each subscriber's channel. It waits only if a
// channel is full.
func (b *Bus) Publish[T any](ev T) {
	b.mu.Lock()
	defer b.mu.Unlock()
	for _, ch := range b.subs[reflect.TypeFor[T]()] {
		ch <- ev
	}
}

// Close closes every channel; each goroutine finishes what is queued.
func (b *Bus) Close() {
	b.mu.Lock()
	for _, subs := range b.subs {
		for _, ch := range subs {
			close(ch)
		}
	}
	b.mu.Unlock()
	b.wg.Wait()
}

type PaymentSucceeded struct{ ID string }

func main() {
	bus := NewBus()
	busy := make(chan struct{}) // receipts is busy until we close this
	bus.Subscribe(8, func(p PaymentSucceeded) {
		<-busy
		fmt.Println("  receipts: receipt for", p.ID)
	})

	for _, id := range []string{"pay-1041", "pay-1042", "pay-1043"} {
		bus.Publish(PaymentSucceeded{ID: id})
		fmt.Println("payments: published", id)
	}
	fmt.Println("payments: all three published; receipts hasn't written one yet")
	close(busy)
	bus.Close()
	fmt.Println("payments: Close returned: the queue is drained")
}
```

```go noverify
// bus/bus.go, lines 51–98
// Subscription is one subscriber: its queue, its goroutine, its counts.
type Subscription struct {
	bus    *Bus
	name   string
	typ    reflect.Type
	policy Policy
	ch     chan any      // the queue
	done   chan struct{} // closed by Unsubscribe
	once   sync.Once

	handled, dropped, panics atomic.Int64
}

// Subscribe starts a goroutine that calls fn for each event of type T,
// one at a time, in the order they were published.
func (b *Bus) Subscribe[T any](name string, opts Options, fn func(T)) *Subscription {
	s := &Subscription{
		bus:    b,
		name:   name,
		typ:    reflect.TypeFor[T](),
		policy: opts.Policy,
		ch:     make(chan any, opts.Buffer),
		done:   make(chan struct{}),
	}
	b.mu.Lock()
	defer b.mu.Unlock()
	if b.closed {
		panic("bus: Subscribe after Close")
	}
	b.subs[s.typ] = append(b.subs[s.typ], s)
	b.wg.Go(func() { s.run(func(v any) { fn(v.(T)) }) })
	return s
}

// Publish hands ev to every subscriber to T, as each one's Policy says.
// It holds the bus lock until all of them have it, so every subscriber
// sees every event in the same order. After Close it does nothing.
func (b *Bus) Publish[T any](ev T) {
	b.mu.Lock()
	defer b.mu.Unlock()
	if b.closed {
		return
	}
	v := any(ev) // box once: every subscriber gets the same interface value
	for _, s := range b.subs[reflect.TypeFor[T]()] {
		s.send(v)
	}
}
```

And the subscriber's goroutine:

```go noverify
// bus/bus.go, lines 129–143
// run is the subscriber's goroutine. It returns at Unsubscribe, or, after
// Close, once the queue is empty.
func (s *Subscription) run(fn func(any)) {
	for {
		select {
		case <-s.done:
			return
		case v, ok := <-s.ch:
			if !ok {
				return
			}
			s.deliver(fn, v)
		}
	}
}
```

`select` waits until one of its cases can proceed, and runs that one. Here it takes the next event from the queue, unless `done` has been closed (stop 5). `v, ok := <-s.ch` sets `ok` to `false` when the channel has been closed and is empty; that's how `Close` ends the loop after the queue is drained.

<UnderTheHood title="Why putting a struct in an interface allocates">

An interface value like `any` is two machine words: a pointer to the type's description, and a pointer to the data. A value that doesn't fit in one word, like the 88-byte `PaymentSucceeded`, is copied to the heap and the interface points at the copy. So `s.send(ev)`, where `send` takes `any`, made a new 88-byte copy (rounded up to the allocator's 96-byte size class, the `96 B/op` benchstat reports) for every subscriber. Converting once and passing the interface value around copies only its two words. The queues then hold the same heap copy, which is safe because nobody modifies an event.

### Step 6: the order events arrive in

A channel is first in, first out, so each subscriber handles its events in the order they entered its queue. But Meridian publishes from many goroutines at once, one per HTTP request. What's "the order" then?

## Backpressure

*Stop 4 of 6.*

### Step 1: a buffer absorbs a burst, not overload

Receipts can write about 240 receipts a second (one every 4.2 ms). At 150 payments a second its queue stays nearly empty. At 1,000 a second, 760 more arrive every second than it can write, and a 64-slot queue fills in less than a tenth of a second. A bigger buffer only takes longer to fill. When more arrives than a consumer can handle, for longer than its queue can hold, something has to give, and there are only three choices:

- **Block**: the publisher waits for a free slot. Nothing is lost; the publisher slows down to the subscriber's pace. That slowing, passed back upstream, is called **backpressure**.
- **Drop the newest**: the event being published is thrown away. The publisher never waits; the subscriber misses the latest events.
- **Drop the oldest**: the oldest event in the queue is thrown away to make room. The publisher never waits; the subscriber misses older events and keeps the latest.

### Step 2: dropping, with a select

Both drop policies come from one piece of syntax: a `select` with a `default` case. `default` runs if no other case can proceed *right now*, so the `select` never waits:

<GoPlayground>

```go
// A queue with room for 3, and 5 events arriving while nobody reads it.
package main

import "fmt"

func main() {
	events := []string{"pay-1", "pay-2", "pay-3", "pay-4", "pay-5"}

	fmt.Println("drop newest:")
	q := make(chan string, 3)
	for _, id := range events {
		select {
		case q <- id: // room: queued
		default: // full: this event is lost
			fmt.Println("  dropped", id)
		}
	}
	close(q)
	for id := range q {
		fmt.Println("  kept   ", id)
	}

	fmt.Println("drop oldest:")
	q = make(chan string, 3)
	for _, id := range events {
		for sent := false; !sent; {
			select {
			case q <- id:
				sent = true
			default: // full: throw away the oldest, then try again
				fmt.Println("  dropped", <-q)
			}
		}
	}
	close(q)
	for id := range q {
		fmt.Println("  kept   ", id)
	}
}
```

</GoPlayground>

```text
drop newest:
  dropped pay-4
  dropped pay-5
  kept    pay-1
  kept    pay-2
  kept    pay-3
```

Drop-newest kept the first three and lost the last two. Drop-oldest lost the first two and kept the last three. The second loop takes the oldest value out (`<-q`) to make room, then tries the send again.

### Step 3: in Meridian's bus

Each subscription chooses its policy when it subscribes, and `send` applies it:

```go noverify
// bus/bus.go, lines 100–127
func (s *Subscription) send(v any) {
	switch s.policy {
	case Block:
		select {
		case s.ch <- v:
		case <-s.done: // unsubscribed while we waited
		}
	case DropNewest:
		select {
		case s.ch <- v:
		default:
			s.dropped.Add(1)
		}
	case DropOldest:
		for {
			select {
			case s.ch <- v:
				return
			default:
			}
			select {
			case <-s.ch:
				s.dropped.Add(1)
			default:
			}
		}
	}
}
```

`Block` waits in a `select` for room in the queue, or for the subscriber to unsubscribe (stop 5). The drop policies never wait, and count what they drop, so it shows up in `Stats`. Drop-oldest can safely take from the queue while the subscriber's goroutine is also taking from it, because channel operations are safe between goroutines, and only one `Publish` runs at a time.

### Step 5: choosing, per subscriber

The right policy depends on what a lost or late event costs *that* subscriber:

| Subscriber | A lost event means | A late event means | Policy |
| --- | --- | --- | --- |
| dashboard | a number that's a moment out of date | a dashboard behind the truth | drop oldest: only the latest matters |
| fraud | a payment never checked | a later check | block, with a large buffer: it's fast |
| receipts | a merchant without a receipt | a receipt a bit later | none of the three |
| webhooks | a merchant never told | a merchant told later | none of the three |

Receipts and webhooks can't lose events and mustn't hold up payments. A queue in memory can't give them both: it's bounded, so it either blocks or drops, and stop 5 shows it doesn't survive a crash. What they need is a **durable** queue: an event written to disk with the payment (chapter 4's outbox), or a broker (chapter 5). Receipts could also go faster: `fsync` costs about the same for one file as for a batch, so writing receipts in batches and syncing once per batch would raise its 240 a second a long way. That's a change to the subscriber, not the bus.

Following a `nil` pointer is a **panic**: the goroutine stops what it's doing and unwinds its stack, running each function's deferred calls on the way out.
```go noverify
// bus/bus.go, lines 185–201
// Close stops publishing, lets every subscriber finish its queue, and
// waits for their goroutines to return.
func (b *Bus) Close() {
	b.mu.Lock()
	if b.closed {
		b.mu.Unlock()
		return
	}
	b.closed = true
	for _, subs := range b.subs {
		for _, s := range subs {
			close(s.ch)
		}
	}
	b.mu.Unlock()
	b.wg.Wait()
}
```

`Close` sets `closed`, so later `Publish` calls do nothing, then closes every queue and waits for every subscriber's goroutine. A closed channel still gives up what's in it, so each `run` loop drains its queue and returns. `SIGKILL` can't be caught: the kernel ends the process without running any of its code. It's what `kill -9` sends, and what Linux's out-of-memory killer sends, so it has to be planned for.

`Unsubscribe` itself has an ordering trap:

```go noverify
// bus/bus.go, lines 158–166
// Unsubscribe stops delivery; events still queued are discarded. It is
// safe to call more than once, and from inside the handler.
func (s *Subscription) Unsubscribe() {
	s.once.Do(func() { close(s.done) }) // first: a Publish blocked on us moves on
	b := s.bus
	b.mu.Lock()
	defer b.mu.Unlock()
	b.subs[s.typ] = slices.DeleteFunc(b.subs[s.typ], func(x *Subscription) bool { return x == s })
}
```

It closes `done` *before* taking the lock. A `Publish` might be holding the lock, waiting for room in this subscriber's queue. If `Unsubscribe` took the lock first, it would wait for that `Publish`, which waits for this subscriber to take an event, and a subscriber that unsubscribes from inside its own handler never would. Closing `done` first releases the waiting `Publish` (its `select` has a `case <-s.done`), which then lets go of the lock. `sync.Once` makes a second `Unsubscribe` harmless, since closing a closed channel panics.

```go noverify
// The bus serializes all published events across all publishers, and
// preserves that ordering when delivering to subscribers that are
// attached to the same Client. In more detail:
//
//   - An event is published to the bus at some instant between the
//     start and end of the call to [Publisher.Publish].

//     totally ordered by their publication time. Given two events E1

//

// If you make a Client and subscribe to events, you will receive
// events one at a time, in the same order as the one true
// timeline. You will "skip over" events you didn't subscribe to, but
// your view of the world always moves forward in time, never
// backwards, and you will observe events in the same order as
// everyone else.
```

That's the total order from stop 3: one timeline that every subscriber sees in the same order. Each component gets a `Client`, named for debugging, and makes typed publishers and subscribers from it:

```go noverify
b := eventbus.New()

```

These are package functions, `eventbus.Publish[T](client)`, not methods: `tailscale.com`'s `go.mod` declares `go 1.26.6`, and generic methods need `go 1.27`.

### Step 2: the path of one event

Meridian's `Publish` puts the event into each subscriber's queue itself, holding a lock. Tailscale's `Publish` hands the event to one goroutine, the **pump**, over an unbuffered channel, and returns once the pump has it:

```go noverify
// tailscale.com/util/eventbus/publish.go, lines 85–103
func publish(c *publisherCore, v any) {
	// Check for just a stopped publisher or bus before trying to
	// write, so that once closed Publish consistently does nothing.
	select {
	case <-c.stop.Done():
		return
	default:
	}

	evt := PublishedEvent{
		Event: v,
		From:  c.client,
	}

	select {
	case c.client.publish() <- evt:
	case <-c.stop.Done():
	}
}
```

The pump owns a queue of up to 16 published events. For each one, it delivers a copy to every `Client` subscribed to its type, one client at a time. While it waits on a slow client, it keeps accepting newly published events into its own queue, until that's full:

```go noverify
// tailscale.com/util/eventbus/bus.go, lines 131–191
func (b *Bus) pump(ctx context.Context) {
	// Limit how many published events we can buffer in the PublishedEvent queue.
	//
	// Subscribers have unbounded DeliveredEvent queues (see tailscale/tailscale#18020),
	// so this queue doesn't need to be unbounded. Keeping it bounded may also help
	// catch cases where subscribers stop pumping events completely, such as due to a bug
	// in [subscribeState.pump], [Subscriber.dispatch], or [SubscriberFunc.dispatch]).
	const maxPublishedEvents = 16
	vals := queue[PublishedEvent]{capacity: maxPublishedEvents}
	acceptCh := func() chan PublishedEvent {
		if vals.Full() {
			return nil
		}
		return b.write
	}
	for {
		// Drain all pending events. Note that while we're draining
		// events into subscriber queues, we continue to
		// opportunistically accept more incoming events, if we have
		// queue space for it.
		for !vals.Empty() {
			val := vals.Peek()
			dests := b.dest(reflect.TypeOf(val.Event))

			if b.routeDebug.active() {
				clients := make([]*Client, len(dests))
				for i := range len(dests) {
					clients[i] = dests[i].client
				}
				b.routeDebug.run(RoutedEvent{
					Event: val.Event,
					From:  val.From,
					To:    clients,
				})
			}

			for _, d := range dests {
				evt := DeliveredEvent{
					Event: val.Event,
					From:  val.From,
					To:    d.client,
				}
			deliverOne:
				for {
					select {
					case d.write <- evt:
						break deliverOne
					case <-d.closed():
						// Queue closed, don't block but continue
						// delivering to others.
						break deliverOne
					case in := <-acceptCh():
						vals.Add(in)
						in.From.publishDebug.run(in)
					case <-ctx.Done():
						return
					case ch := <-b.snapshot:
						ch <- vals.Snapshot()
					}
				}
			}
```

One goroutine takes every event in turn, so there's one order, with no lock at all: the order is simply the order the pump received them. Each `Client` has its own goroutine and its own queue, and hands the events to its subscribers. A module reads its events from `sub.Events()`, a channel, in its own loop; `SubscribeFunc` calls a function instead.

### Step 3: measured: a subscriber that stops reading

The package documentation says what a slow subscriber does:

```go noverify
// tailscale.com/util/eventbus/doc.go, lines 68–71
// Subscribers are expected to promptly receive their events on
// [Subscriber.Events]. The bus has a small, fixed amount of internal
// buffering, meaning that a slow subscriber will eventually cause
// backpressure and block publication of all further events.
```

`cmd/tsbus -stuck` subscribes, never reads `sub.Events()`, and publishes a million events:

```text
   250000 published in  467ms, publisher never blocked; heap +35 MiB
   500000 published in  890ms, publisher never blocked; heap +70 MiB
   750000 published in 1.333s, publisher never blocked; heap +106 MiB
  1000000 published in 1.725s, publisher never blocked; heap +139 MiB
waiting 6 s for the bus's slow-subscriber check...
2026/09/27 19:13:28 main main.go:30: subscriber for events.PaymentSucceeded is slow (5.000896083s elapsed)
```

**The publisher never blocked.** All 1,000,000 events were accepted in 1.7 s, and the heap grew by 139 MiB, about 146 bytes per event. After 5 seconds the bus logged that the subscriber was slow. The source says why, in the comment at the top of `pump` above: *"Subscribers have unbounded DeliveredEvent queues (see tailscale/tailscale#18020)"*. Each client's queue is created with no capacity, and in `queue.go` a zero capacity means unbounded:

```go noverify
// tailscale.com/util/eventbus/subscribe.go, lines 69–76
func (s *subscribeState) pump(ctx context.Context) {
	var vals queue[DeliveredEvent]
	acceptCh := func() chan DeliveredEvent {
		if vals.Full() {
			return nil
		}
		return s.write
	}
```

So in v1.102.5 a stuck subscriber costs memory, not publisher time: the policy stop 4 didn't offer, an unbounded buffer. The documentation still describes the older behaviour. When the two disagree, what the code does, measured, is the answer.

### Step 4: what the design costs and buys

- **Per event:** 2.2 µs against Meridian's 198 ns with one subscriber (stop 3's benchmark). An event crosses two goroutines, the pump's and the client's, each through a `select` that also watches for shutdown, snapshots and new events.
- **Panics:** not recovered. A panicking subscriber crashes `tailscaled`, measured in stop 5. Bugs are loud.
- **A stuck subscriber:** never blocks anyone; memory grows; a log line every 5 seconds.
- **Order:** one timeline for every client, from one goroutine, with no lock held while waiting.

Meridian's bus made different choices: `Block` by default, so a stuck subscriber shows up as slow payments rather than growing memory; a lock instead of a pump; recover instead of crash. Neither set is wrong. What matters is knowing which one you have, and the only reliable way to know is to measure it, as the documentation above shows.

### Step 5: when to leave the process

An in-process bus is the cheapest way to decouple modules inside one program: no network, no serialisation, 200 ns an event. Its limits are the process's limits:

| | In-process bus | Broker (chapter 5) | Kafka (chapter 7) |
| --- | --- | --- | --- |
| Survives a crash | no: 1,640 receipts lost to one `kill -9` | yes, if persisted | yes |
| Reaches other programs | no | yes | yes |
| Cost per event | ~200 ns | a network round trip | a network round trip, batched |
| Order | one total order, if the bus holds it | per queue | per partition |
| Replay old events | no | limited | yes, from any offset |

Use the bus for reactions that live and die with the process: a dashboard, a cache to invalidate, a metric. Anything that must happen once a payment has committed, like a receipt or a webhook, needs its event written durably with the payment, and a broker or an outbox to carry it.

<Exercise n={1} title="Refunds, with no change to the bus" level="easy">

Add a `RefundIssued` event (payment id, amount, time). Make the receipts module write a refund note when one is published, and make the payment handler's refund path publish it. Which files change, and which don't?

<Solution>

`events` gets the new type; the refund handler calls `bus.Publish(events.RefundIssued{...})`; the wiring in `main` adds `b.Subscribe("receipt refunds", bus.Options{Buffer: 64}, rw.WriteRefund)` with a new `WriteRefund` method in `receipts`. `bus` doesn't change: `RefundIssued` is a new key in the same `map[reflect.Type][]*Subscription`. And `payments` doesn't learn that receipts exists. One subscription per type: a subscriber interested in two types subscribes twice, and its two handlers run on two goroutines, so if they share state, it needs a mutex.

</Solution>

</Exercise>

<Exercise n={2} title="Pick the policies" level="easy">

Meridian adds two subscribers to `PaymentSucceeded`: a **loyalty** module that credits the customer one point per dollar in Postgres, and a **metrics** module that counts payments per second for a graph. Choose each one's policy and buffer, and say what happens to it during stop 4's burst.

<Solution>

**Metrics**: `DropOldest`, small buffer. A dropped event makes one second's count slightly low; blocking would slow payments for a graph. Better still, count with an atomic in the payment handler and don't subscribe at all. **Loyalty**: points are money-like, so none of the three. Losing one is a customer's lost points, and blocking holds up payments behind a Postgres write. Credit the points in the payment's own transaction, or publish through the outbox (chapter 4) with an idempotent consumer. During the burst, `Block` would have added loyalty's database time to every checkout's wait.

</Solution>

</Exercise>

<Exercise n={3} title="A handler that publishes" level="medium">

Fraud should publish a `PaymentFlagged` event when it flags a payment, for an alerts module. The obvious code calls `b.Publish(PaymentFlagged{...})` inside fraud's handler. Under load, with fraud's queue at 16, what happens? Why, and how would you fix it?

<Solution>

It can deadlock. `cmd/reentrant` does exactly this with 10,000 payments, and gets stuck; its goroutine dump shows the two sides:

```text
stuck after 3 s; where the goroutines are:
  goroutine 35 [select]:
      meridian/bus.(*Subscription).run
      meridian/bus.(*Bus).Subscribe[...].func1()
  goroutine 36 [sync.Mutex.Lock]:
      meridian/bus.(*Bus).Publish[...]
      main.main.func2(…)
      meridian/bus.(*Bus).Subscribe[...].func1.1()
      meridian/bus.(*Subscription).deliver
      meridian/bus.(*Subscription).run
      meridian/bus.(*Bus).Subscribe[...].func1()
  goroutine 37 [select]:
      meridian/bus.(*Subscription).send(...)
      meridian/bus.(*Bus).Publish[...]
      main.main.func3()
exit status 1
```

Goroutine 37 is the payments side: in `Publish`, holding the bus lock, waiting in `send` for room in fraud's queue. Goroutine 36 is fraud's handler: in `Publish(PaymentFlagged)`, waiting for the bus lock. Fraud can't take its next event until its handler returns, and its handler can't return until the payments side lets go of the lock. Fixes: publish from outside the handler (hand the flagged event to another goroutine, or collect it and publish after the handler returns), give the bus a pump goroutine like Tailscale's so `Publish` only enqueues, or use a per-type lock so publishing `PaymentFlagged` doesn't need the lock `PaymentSucceeded` holds (which gives up one total order across types).

</Solution>

</Exercise>

<Exercise n={4} title="Receipts after a crash" level="medium">

After stop 5's `kill -9`, 1,640 committed payments have no receipt. Write the query a reconciliation job would run at startup to find them, and say what the job can't recover.

<Solution>

Every card payment is a ledger transaction, and its receipt file is `pay-<transaction id>.txt`. The ledger has the merchant and the amount:

```sql
SELECT 'pay-' || t.id AS payment,
       substring(m.account_id from 'merchant:(.*)') AS merchant,
       c.amount, t.created_at
FROM transactions t
JOIN postings c ON c.tx_id = t.id AND c.account_id = 'assets:card-receivable'
JOIN postings m ON m.tx_id = t.id AND m.account_id LIKE 'liabilities:merchant:%'
WHERE t.kind = 'card payment'
ORDER BY t.id;
```

The job lists the receipts directory, and writes a receipt for each payment whose file is missing. What it can't recover: the card's last four digits. They were in the event, and the ledger doesn't store them, so they existed only in memory. That's why chapter 4's outbox stores the whole event payload in the same transaction as the payment: anything a subscriber needs must be durable before the payment's answer goes out.

</Solution>

</Exercise>

<Exercise n={5} title="Parallel, and still in order" level="hard">

Stop 3's dashboard with 4 workers handled 10,291 changes out of order. Keep 4 workers, and make every merchant's changes arrive in order.

<Solution>

Give each worker its own channel, and send every event for a merchant to the same worker, chosen by a hash of the merchant:

```go noverify
// cmd/shard/main.go, lines 33–37
	b.Subscribe("dashboard", bus.Options{Buffer: 64}, func(ev events.BalanceChanged) {
		h := fnv.New32a()
		h.Write([]byte(ev.Merchant))
		shards[h.Sum32()%workers] <- ev // one merchant, one worker, one order
	})
```

Each worker then handles one merchant's events in the order they were published, while different merchants still run in parallel. Run with `cmd/order`'s 8 merchants × 10,000 changes:

```text
sharded dashboard, 4 workers: 80000 events, 0 out of order, 0 stale
```

This is how Kafka's partitions keep order (chapter 7): order is kept per key, not globally. The cost is balance: one busy merchant keeps its one worker busy while the others idle.

</Solution>

</Exercise>

- **Channels**: a queue and a goroutine per subscriber; `Publish` only enqueues. Checkouts fell to 1.07 ms, fraud saw payments 30 µs after commit, and a webhook outage stayed with webhooks.
