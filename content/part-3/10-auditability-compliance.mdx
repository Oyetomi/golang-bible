Here's the thing, sport. You're building a payment ledger. A customer calls and says: "You charged me twice on Tuesday." Your operations team opens the database and finds that the second charge row has been deleted — not reversed, *deleted*. The `updated_at` column says yesterday. Nobody knows who did it.

Congratulations: you just learned why you never `UPDATE` or `DELETE` audit rows.

<Define term="Audit log" since="Auditability & Compliance (Part 3, Chapter 9)">
An **audit log** is a dedicated, append-only record of every state-changing event in a system: who did it, what changed, and when. Unlike an application log (which records diagnostic output), an audit log is a **compliance artifact** — it must be immutable, tamper-evident, and retained for regulatory windows. If you can delete or update a row, it is not an audit log; it is a mutable table with a misleading name.
</Define>

**On the job:** Every payment system that has ever faced a regulatory examination has been asked to produce a complete, ordered record of every transfer for a given account and time range. If your audit log has gaps, deletions, or ambiguous ordering, the investigation stalls — and the engineer who built the log is explaining that to a compliance officer.

### What an audit log actually is

An audit log answers three questions for every event, precisely and permanently:

- **WHO** took the action (user, service, or system)
- **WHAT** changed (entity type, entity ID, the before state, the after state)
- **WHEN** it happened (a UTC timestamp with nanosecond resolution from a reliable clock)

That's not a log file. It's not a `last_modified` column. It's a dedicated, **append-only** table (or event stream) where rows are written once and never touched again. The shape of a single audit entry looks like this:

```go
// AuditEntry is one immutable record in the audit log.
// Once written it is NEVER updated or deleted.
type AuditEntry struct {
	ID          int64     // auto-incrementing sequence number
	OccurredAt  time.Time // UTC; stored with timezone
	ActorID     string    // who did it: "user:42", "service:payments"
	Action      string    // what happened: "transfer.created"
	EntityType  string    // "transfer", "account", "card"
	EntityID    string    // the specific record affected
	Before      []byte    // JSON snapshot of state before the action (nil for creates)
	After       []byte    // JSON snapshot of state after (nil for deletes)
	PrevHash    string    // SHA-256 of the previous entry — the chain link
	Hash        string    // SHA-256 of this entry's content + PrevHash
}
```

The `Before` and `After` snapshots are the secret weapon. They let you reconstruct exactly what happened to any record at any point in time — not just that something changed, but precisely *what* changed. Forensic gold.

### Hash chaining: making tampering detectable

<Define term="Hash chain / tamper-evident" since="Auditability & Compliance (Part 3, Chapter 9)">
A **hash chain** links each audit entry to its predecessor by including the previous entry's cryptographic hash (`SHA-256`) in the current entry's own hash input. Altering any entry changes its hash, which invalidates every subsequent entry's `PrevHash` pointer — the chain breaks and verification fails. **Tamper-evident** means tampering cannot go undetected, not that it is impossible; the defenses against undetected rewrites are append-only database permissions and external witnesses (see the Under the Hood note below).
</Define>

**On the job:** A hash chain without append-only database permissions is theater. The chain tells you *that* someone tampered; the database permissions prevent them from rewriting the chain afterward. You need both.

Writing append-only is half the battle. The other half is making it *impossible to tamper with history without being caught*. That's what hash chaining does. Every entry includes the hash of the previous entry. Alter any entry and its hash changes — which means every subsequent entry now has a wrong `PrevHash`, and the entire chain fails verification.

It's a mini-blockchain. No cryptocurrency required.

Here is the complete, runnable hash-chained audit log using only `crypto/sha256` from the standard library:

<GoPlayground>

```go
package main

import (
	"crypto/sha256"
	"encoding/hex"
	"encoding/json"
	"fmt"
	"time"
)

// AuditEntry is one immutable record in the append-only audit log.
type AuditEntry struct {
	ID         int64
	OccurredAt time.Time
	ActorID    string
	Action     string
	EntityType string
	EntityID   string
	Before     json.RawMessage
	After      json.RawMessage
	PrevHash   string
	Hash       string // computed; never supplied by the caller
}

// AuditLog is an in-memory append-only log with hash chaining.
// In production this writes to an append-only table or event stream.
type AuditLog struct {
	entries []*AuditEntry
}

// computeHash produces a SHA-256 fingerprint of an entry's content fields.
// It does NOT hash the Hash field itself (that would be circular).
func computeHash(e *AuditEntry) string {
	h := sha256.New()
	// Write each field in deterministic order so the hash is reproducible.
	fmt.Fprintf(h, "%d|%s|%s|%s|%s|%s|%s|%s|%s",
		e.ID,
		e.OccurredAt.UTC().Format(time.RFC3339Nano),
		e.ActorID,
		e.Action,
		e.EntityType,
		e.EntityID,
		e.Before,
		e.After,
		e.PrevHash,
	)
	return hex.EncodeToString(h.Sum(nil))
}

// Append adds one immutable entry and links it into the chain.
func (log *AuditLog) Append(e *AuditEntry) {
	// Link to the previous entry's hash.
	if n := len(log.entries); n > 0 {
		e.PrevHash = log.entries[n-1].Hash
	}
	e.Hash = computeHash(e)
	log.entries = append(log.entries, e)
}

// Verify walks the entire chain and returns the first tampered entry index,
// or -1 if the chain is intact.
func (log *AuditLog) Verify() int {
	prevHash := ""
	for i, e := range log.entries {
		if e.PrevHash != prevHash {
			return i // PrevHash mismatch: the chain is broken here
		}
		if e.Hash != computeHash(e) {
			return i // content has changed since the hash was computed
		}
		prevHash = e.Hash
	}
	return -1
}

func mustJSON(v any) json.RawMessage {
	b, err := json.Marshal(v)
	if err != nil {
		panic(err)
	}
	return b
}

func main() {
	log := &AuditLog{}

	// Append three legitimate Meridian transfer entries.
	log.Append(&AuditEntry{
		ID:         1,
		OccurredAt: time.Now().UTC(),
		ActorID:    "user:42",
		Action:     "transfer.created",
		EntityType: "transfer",
		EntityID:   "txn-001",
		Before:     nil,
		After:      mustJSON(map[string]any{"amount_cents": 10000, "status": "pending"}),
	})

	log.Append(&AuditEntry{
		ID:         2,
		OccurredAt: time.Now().UTC(),
		ActorID:    "service:settlements",
		Action:     "transfer.settled",
		EntityType: "transfer",
		EntityID:   "txn-001",
		Before:     mustJSON(map[string]any{"amount_cents": 10000, "status": "pending"}),
		After:      mustJSON(map[string]any{"amount_cents": 10000, "status": "settled"}),
	})

	log.Append(&AuditEntry{
		ID:         3,
		OccurredAt: time.Now().UTC(),
		ActorID:    "user:7",
		Action:     "account.viewed",
		EntityType: "account",
		EntityID:   "acc-99",
		Before:     nil,
		After:      nil,
	})

	// Chain should be intact.
	if idx := log.Verify(); idx == -1 {
		fmt.Println("Chain intact — no tampering detected.")
	} else {
		fmt.Printf("TAMPER DETECTED at entry index %d\n", idx)
	}

	// Now tamper with entry 1 (index 0) — simulate an attacker
	// changing the transfer amount after the fact.
	log.entries[0].After = mustJSON(map[string]any{"amount_cents": 1, "status": "pending"})
	// Note: we do NOT recompute log.entries[0].Hash, as an attacker
	// who doesn't know the chain structure wouldn't know to do so.

	if idx := log.Verify(); idx == -1 {
		fmt.Println("Chain intact.")
	} else {
		fmt.Printf("TAMPER DETECTED at entry index %d — every engineer's favorite line.\n", idx)
	}
}
```

<UnderTheHood title="How the hash chain makes tampering detectable (and why it's not magic)">

SHA-256 is a cryptographic hash function: given the same input bytes, it always produces the same 256-bit output, and it is computationally infeasible (as of Go 1.26 and current cryptography) to find two different inputs that produce the same output. That property is called *collision resistance*.

The chain works because each entry's hash covers all its content fields *plus* the previous entry's hash. If you change any content byte anywhere in the chain, you change that entry's hash. That invalidates every subsequent `PrevHash` pointer — the chain breaks and verification fails.

One limitation the security-aware engineer must know: **a hash chain is tamper-evident, not tamper-proof.** An attacker with write access to the store could, in principle, recompute every subsequent hash (rebuild the chain from the altered entry forward). The defenses against that are:

1. **Append-only database permissions** — the application user has `INSERT` only; `UPDATE` and `DELETE` are revoked at the database level.
2. **External witnesses** — periodically publish the tip hash to an external, auditor-controlled store (a blockchain, an HSM log, a regulator's endpoint) so any rewrite of the chain can be compared against the witnessed tip.
3. **Signed entries** — have the service sign each entry with an HSM key. Rewriting history requires access to the private key, which is controlled separately.

For most fintech systems, revoked `UPDATE`/`DELETE` permissions plus periodic external witnessing is sufficient. The hash chain is the first line of evidence; the access controls are the enforcement mechanism.

Go's `crypto/sha256` package (standard library since Go 1.0) is backed by an optimized assembly implementation on amd64 and arm64. As of Go 1.26, no external dependency is needed for production-grade hash chaining. This is a simplification of the full threat model — a dedicated security chapter (Security for Financial Systems, Part 3) goes deeper on signing, HSMs, and key management.

</UnderTheHood>

<Callout kind="warn" title="Never UPDATE or DELETE audit rows — at the database level">

Append-only is a design principle, but it must be enforced at the database permission level, not just in application code. Grant the application user only `INSERT` on the audit table. Revoke `UPDATE` and `DELETE` entirely. Even a compromised application cannot then rewrite history — it doesn't have the database permission to do so. Application code is a policy; database permissions are enforcement.

</Callout>

## Append-Only Event Stores

<Define term="Append-only event store" since="Event-Driven Architecture & Kafka (Part 3, Chapter 6)">
An **append-only event store** is a log where every state change is recorded as an immutable event — events are never updated or deleted, only appended. The current state of any entity is derived by replaying all its events from the beginning. This is the foundation of **event sourcing** (covered in depth in Event-Driven Architecture & Kafka, Part 3). For compliance purposes, the event store and the audit log are the same artifact viewed from different angles: the event store drives domain behavior; the audit log makes that history legible to regulators and investigations.
</Define>

**On the job:** If you've read the Event-Driven Architecture & Kafka chapter, you already know this shape. The event log you built there *is* the audit trail — you just need to treat it as one. The compliance team will ask for the same events your domain already produces; the only extra work is adding the hash chain and retaining the events for the regulatory window.

### The event log as the audit trail

In an event-sourced system (covered in Event-Driven Architecture & Kafka, Part 3), every state change is recorded as an immutable event in an append-only log. That log is exactly the audit trail regulators want:

- Every event has a sequence number (Kafka offset or a monotonically increasing DB sequence) that makes ordering unambiguous.
- Events are never updated or deleted.
- The current state of any entity is derived by replaying events from the beginning — so you can reconstruct the state at any point in time.

The difference between the event store and the audit log from Section 1 is not a technical one — it's a framing one. The event store is the source of truth for your domain. The audit log makes that source of truth legible to compliance, operations, and investigations.

In practice, your Watermill handlers (Watermill — Event-Driven Go in Practice, Part 3) write domain events to Kafka. A compliance-side consumer reads those same events and writes them to the audit log table, adding actor context, before/after snapshots, and the hash chain link. This way:

- The event store drives system behavior.
- The audit log drives investigations and compliance.

### Why sequence numbers beat wall-clock time for ordering

The killer detail: you order events by **sequence number**, not by timestamp. Sequence numbers (a Kafka offset, a database sequence, a logical clock) are strictly monotonic — no two events get the same number, and the order is unambiguous. Timestamps from wall clocks are not: two events on different servers can have the same millisecond timestamp (or even a backward one, if NTP has been adjusting the clock). We'll dissect that in the next section.

## Time and Clocks

This section will save you from a category of bug that only surfaces in production, only under load, and only across distributed systems — which is to say, exactly when it matters most.

<Define term="Monotonic vs wall clock" since="Time, Clocks & Timers (Part 2, Chapter 4)">
A **wall clock** is the human-readable time-of-day reading (what you'd print or store in the database). It is adjusted by NTP and can jump forward or backward. A **monotonic clock** is a counter that only goes forward, used for measuring elapsed time within a single process. It is immune to NTP adjustments. Go's `time.Time` (since Go 1.9) carries *both* readings in a single value — `time.Since` and `Sub` automatically use the monotonic component; serialization to a string or database discards it, which is correct. The full treatment is in Time, Clocks & Timers (Part 2).
</Define>

**On the job:** Using wall-clock time to determine the *order* of events across servers is one of the most persistent bugs in distributed payment systems. Two transfers processed on different pods in the same millisecond will have ambiguous ordering if you sort by `occurred_at`. A database sequence or Kafka offset resolves this unambiguously.

### Wall-clock time is unreliable for ordering

Your servers run NTP (Network Time Protocol) to stay synchronized with reference clocks. Here is what NTP does when it finds your clock is slightly ahead: it *slows down* or *steps back* your system clock. This is called a **clock slew** (gradual) or **clock step** (sudden jump). The result is that `time.Now()` on the same machine, called twice in sequence, can return a time that appears to go *backward*.

Across servers, it's worse. Two servers in the same datacenter can have their clocks differ by hundreds of milliseconds. An event logged on server A at 10:00:00.500 may appear *later* in wall time than an event logged on server B at 10:00:00.400, even if A's event actually happened first.

This is why you never use wall-clock time to determine event *ordering*. You use:

- **Sequence numbers** (database auto-increment, Kafka offsets) for total order within one system.
- **Logical clocks** (Lamport timestamps, vector clocks) for partial order across distributed systems. (Covered in the distributed systems literature; out of scope here but name-checked so you know it exists.)

Wall-clock time is still important — it's what humans, regulators, and courts want to read. You store it. You just don't *sort* by it.

### UTC always — and store timezone information

Every timestamp in a fintech system is stored in UTC. Not local time. Not "server time." **UTC.**

The reason is simple: local time has daylight saving transitions, regional offsets, and political changes. November 7, 2027 at 1:30 AM in the US Eastern timezone happens *twice* — once at UTC-04:00 and once at UTC-05:00. If you store "01:30" without a timezone offset, you don't know which one. A transfer that occurred during the fallback hour is ambiguous — permanently. UTC has no ambiguity.

In Go, call `.UTC()` explicitly after any `time.Time` value you create or parse, and store in a column typed `TIMESTAMPTZ` (Postgres), which stores the UTC offset alongside the timestamp. Never store in `TIMESTAMP WITHOUT TIME ZONE`.

### Go's time.Time carries both wall and monotonic clocks

This is where Go does something genuinely clever. Let me show you:

<GoPlayground>

```go
package main

import (
	"fmt"
	"time"
)

func main() {
	// time.Now() returns a time.Time that carries TWO readings:
	//   1. The wall clock — what you'd print or store in the database.
	//   2. The monotonic clock — a counter that ONLY goes forward,
	//      used for measuring elapsed time.
	start := time.Now()

	// Simulate some work.
	sum := 0
	for i := range 1_000_000 {
		sum += i
	}

	// time.Since uses the monotonic component — immune to NTP clock slews.
	elapsed := time.Since(start)

	fmt.Println("sum:", sum)
	fmt.Printf("elapsed: %v (monotonic — won't lie if NTP adjusts mid-measurement)\n", elapsed)

	// To strip the monotonic reading (for storage or comparison across processes):
	wallOnly := start.Round(0)
	fmt.Println("wall-clock only:", wallOnly.UTC().Format(time.RFC3339Nano))

	// time.Since and Sub use the monotonic reading automatically.
	// time.Equal and Before/After also use the monotonic reading when present.
	// But if you store a time.Time and reload it from a DB, it loses the
	// monotonic component — that's fine, it was only for this process's measurements.
	fmt.Println("has monotonic:", start != wallOnly) // true — they differ in the monotonic component
}
```

<UnderTheHood title="How Go's time.Time stores wall and monotonic together (Go 1.9+)">

Before Go 1.9, `time.Now()` returned only the wall clock. If you measured a duration with `t2.Sub(t1)` and NTP adjusted the clock between `t1` and `t2`, your measurement was wrong — possibly *negative*.

Since Go 1.9, `time.Now()` returns a `time.Time` that internally stores *two* values in a single struct:

1. **Wall seconds** — Unix seconds since January 1, year 1, UTC. Used for printing and storage.
2. **Monotonic nanoseconds** — nanoseconds from an arbitrary process-start reference. Only goes forward. Never adjusted.

`time.Sub`, `time.Since`, and comparison operators use the monotonic reading when both operands have one. The moment you serialize to a string (`time.RFC3339`) or strip with `.Round(0)`, you lose the monotonic reading — which is correct, because a timestamp recovered from a database or a wire format is a wall-clock value and should be compared as one.

This design decision means you never need to choose between `time.Now()` and a special monotonic clock call — Go gives you both in one value and does the right thing automatically. As of Go 1.26, this behavior is stable and well-documented in the `time` package. The full treatment of timers, tickers, and injecting a `Clock` interface for deterministic tests is in Time, Clocks & Timers (Part 2).

The internal struct layout is roughly:

```go
// internal (unexported, simplified — this is a model, not the exact source):
type Time struct {
    wall uint64  // top bit = has monotonic; lower bits = wall seconds or nsec
    ext  int64   // if has-monotonic: monotonic nsec since process start; else: seconds
    loc  *Location
}
```

## Data Retention

The law tells you how long to keep data. Multiple laws, actually, and they disagree with each other.

<Define term="Data retention" since="Auditability & Compliance (Part 3, Chapter 9)">
**Data retention** is the policy that governs how long records must be kept and when they must be deleted or archived. In fintech, at least three regimes apply simultaneously: PCI-DSS (cardholder data audit logs: 12 months, 3 months online), AML/BSA (transaction records: 5 years), and GDPR/CCPA (personal data: no longer than necessary). The engineer's job is to implement automated retention jobs and a schema that separates business records from PII so each can be retained or deleted on an independent schedule.
</Define>

**On the job:** Retention policy failures surface in two ways: a regulator asks for five years of transaction history and you have three, or a user exercises their GDPR erasure right and you delete their audit trail along with their PII. Both are compliance incidents. The schema design that separates business data from PII is the engineering answer.

### The retention landscape

| Regulation | Data type | Typical minimum retention |
|---|---|---|
| PCI-DSS | Cardholder data audit logs | 12 months (3 months online) |
| AML / BSA | Transaction records | 5 years |
| GDPR (EU) | Personal data | As long as necessary — no longer |
| CCPA (California) | Personal data | Varies by category |

The engineer's job is to implement **retention policies** that satisfy all applicable rules. That means:

- An automated job that deletes (or archives to cold storage) records older than the retention window.
- A schema that separates business data (the transfer record: amount, status, timestamps) from PII (the cardholder name, address, account number) so they can be retained or deleted on independent schedules.
- Documented evidence that the policies are running.

### The GDPR right-to-erasure vs. the immutable audit trail

This is the puzzle that trips up every fintech engineer exactly once. GDPR Article 17 gives users the right to be forgotten. Your audit log is immutable and must never be deleted. Contradiction?

No. The engineering answer is **pseudonymization with crypto-shredding**.

<Define term="Crypto-shredding" since="Auditability & Compliance (Part 3, Chapter 9)">
**Crypto-shredding** is the technique of encrypting data with a per-subject key and then deleting the key to render the data permanently indecipherable — without deleting the encrypted bytes themselves. In the GDPR context: PII is stored encrypted with a per-user key; when the user requests erasure, the key is deleted from the key store (Vault, AWS KMS, etc.). The encrypted blobs remain on disk but are now computationally indistinguishable from random noise. The audit trail entries, which reference only a pseudonymous ID (`user:42`), survive intact. This is **not** the same as deletion — it is accepted as equivalent to deletion under most interpretations of GDPR Article 17, but consult your data protection officer.
</Define>

Here is the pattern:

1. **Separate PII from the audit entry.** The audit row stores only a pseudonymous identifier (`user:42`), not the user's name, email, or address.
2. **Store the PII mapping separately**, encrypted with a **per-user symmetric key** (`user_42_key` → `{"name": "Alice Smith", "email": "alice@example.com"}`).
3. **When the user requests erasure**, delete the encryption key. The PII is now indecipherable — it is cryptographically erased, even though the bytes remain on disk.
4. **The audit log entry survives** with its pseudonymous actor ID intact. The chain is unbroken. Regulators can see that `user:42` performed `transfer.created` on date X. They simply cannot learn who `user:42` was — because that mapping is gone.

## PCI-DSS, KYC and AML

Let me be direct: this section tells you what an engineer is responsible for implementing. It is not legal advice. Your company has (or needs) a legal team, a compliance officer, and a qualified security assessor. What I'm giving you is the engineering playbook so you're not blindsided when compliance shows up.

### PCI-DSS — what the engineer builds

<Define term="PCI-DSS" since="Auditability & Compliance (Part 3, Chapter 9)">
**PCI-DSS** (Payment Card Industry Data Security Standard) is a set of security requirements for any system that stores, processes, or transmits cardholder data. As an engineer, the three non-negotiable requirements are: (1) never store a raw PAN — tokenize it at the provider; (2) minimize the number of systems in scope; (3) retain audit logs of all access to cardholder data for 12 months. This chapter covers the engineering touchpoints only — PCI-DSS compliance requires a Qualified Security Assessor (QSA) for formal certification.
</Define>

**On the job:** A PAN (16-digit card number) appearing in a log file is a PCI compliance incident, full stop. It triggers notification obligations, a forensic investigation, and potentially a fine. Use `slog.LogValuer` (shown below) to make sensitive types self-masking. A `fmt.Println` during a debugging session that hits production is all it takes.

PCI-DSS applies to any system that stores, processes, or transmits cardholder data. The engineer's core responsibilities:

**Never store raw PANs.** A PAN (Primary Account Number) is the 16-digit card number. If your system needs to re-use a card, you **tokenize** it: send the raw PAN to a certified token vault (your payment processor's vault, or a dedicated service like HashiCorp Vault with a PCI-certified deployment), receive a token (a synthetic number with no mathematical relationship to the real PAN), and store the token. The raw PAN never lands in your database.

**Scope minimization.** Every system, server, and person that touches cardholder data is "in scope" for PCI-DSS audits. The fewer systems in scope, the smaller the audit surface. Architect so that raw card data flows only to your tokenization provider — no other service touches it.

**Encryption in transit and at rest.** TLS 1.2+ for all cardholder data in transit (TLS 1.3 preferred). Encryption at rest for any token vault or related data store.

**Audit log retention.** PCI-DSS Requirement 10 mandates audit logs of all access to cardholder data — 12 months total, 3 months immediately accessible. Your hash-chained audit log satisfies this if it covers the right events.

**The Go engineer's specific checklist:**
- `crypto/tls` with a minimum TLS version set: `tls.Config{MinVersion: tls.VersionTLS12}`
- Structured logging that **never** logs a PAN, CVV, or full magnetic stripe data. Use a `slog` middleware that redacts sensitive fields before they reach the log handler.
- Payment processor integration via the tokenization API (Integrating with External Payment Systems, Part 3) — the Go client calls the provider's token endpoint, stores the token, and the raw PAN is ephemeral in memory only.

<GoPlayground>

```go
package main

import (
	"crypto/tls"
	"fmt"
	"log/slog"
	"net/http"
	"os"
	"strings"
)

// MaskedPAN is a PAN type that never prints the full number.
// Use this in structs that might end up in log output.
type MaskedPAN string

// String masks all but the last four digits — safe to log.
func (p MaskedPAN) String() string {
	s := string(p)
	if len(s) < 4 {
		return "****"
	}
	return strings.Repeat("*", len(s)-4) + s[len(s)-4:]
}

// LogValue implements slog.LogValuer — slog calls this automatically.
// MaskedPAN will always log as the masked form, even if the caller
// passes it as a raw slog.Any value.
func (p MaskedPAN) LogValue() slog.Value {
	return slog.StringValue(p.String())
}

func newTLSServer() *http.Server {
	return &http.Server{
		Addr: ":8443",
		TLSConfig: &tls.Config{
			// PCI-DSS requires TLS 1.2 minimum; prefer 1.3.
			MinVersion: tls.VersionTLS12,
		},
	}
}

func main() {
	// Demonstrate: MaskedPAN never leaks the full number.
	pan := MaskedPAN("4111111111111111") // a test Visa number
	logger := slog.New(slog.NewJSONHandler(os.Stdout, nil))

	// Even when logged as Any, the LogValue() method is called.
	logger.Info("processing payment",
		slog.Any("pan", pan),  // logs "pan": "************1111"
		slog.String("token", "tok_abc123"),
	)

	// The full PAN should never appear in logs — this prints the masked form.
	fmt.Println("PAN (masked):", pan.String())
	fmt.Println("PAN (raw — store the token instead):", string(pan))

	// In production, you'd pass the raw PAN to the tokenization endpoint,
	// receive a token, discard the PAN, and store only the token.
	_ = newTLSServer() // shows PCI-compliant TLS config
}
```

### KYC — Know Your Customer

<Define term="KYC" since="Auditability & Compliance (Part 3, Chapter 9)">
**KYC** (Know Your Customer) is the regulatory obligation for financial institutions to verify the identity of their customers before allowing them to transact. As an engineer, KYC means: collecting and securely storing identity documents, integrating with a verification provider (Persona, Jumio, Onfido), modeling the verification state machine (`pending` → `approved` / `rejected` / `requires_review`), and auditing every verification decision. KYC records are high-sensitivity PII and are typically subject to the same 5-year retention window as AML records. This chapter covers the engineering touchpoints — KYC compliance requirements vary by jurisdiction and institution type.
</Define>

**On the job:** KYC data (passport scans, selfies, ID documents) is the highest-sensitivity PII in a fintech system. Access to it should require explicit authorization, log every read, and expire URLs quickly. Pre-signed URLs from S3/GCS with short expiry (minutes, not hours) are the standard pattern — never serve identity documents from a persistent public URL.

KYC is the process of verifying who your customers are before they transact. As an engineer, you build:

- **Identity document collection and storage.** Scanned documents (passports, driver's licenses) are high-sensitivity PII. Store them encrypted, with access logs. Use pre-signed URLs from S3/GCS with short expiry — never serve identity documents from a URL that doesn't expire.
- **Integration with KYC verification providers** (Persona, Jumio, Onfido). Same patterns as Integrating with External Payment Systems (Part 3): timeouts, retries with idempotency keys, webhook signature verification, and explicit state modeling (`kyc_status`: `pending` → `approved` / `rejected` / `requires_review`).
- **Audit trail for every verification decision.** Who ran the check, what the provider returned, when. This audit trail may be subpoenaed.
- **Data retention aligned with AML requirements** — KYC records are often subject to the same 5-year retention as transaction records.

### AML — Anti-Money Laundering

<Define term="AML" since="Auditability & Compliance (Part 3, Chapter 9)">
**AML** (Anti-Money Laundering) regulations (BSA in the US, AMLD in the EU) require financial institutions to detect and report suspicious activity. As an engineer, AML means: building reliable event streams so every transaction reaches the monitoring system, modeling account states that support freeze/hold workflows, and making transaction history queryable by time window and account so the compliance team or AML engine can build detection logic on top. The engineer builds the infrastructure — the compliance team builds the rules. This chapter covers engineering touchpoints only; AML compliance requirements are set by regulators and require specialist legal advice.
</Define>

**On the job:** AML monitoring is only as good as the event stream feeding it. A missed transfer event — because a webhook failed and wasn't retried, or a Kafka partition lagged — means a potentially reportable transaction was never screened. The reliability patterns from the Reliability Patterns chapter (Part 2) apply directly here: at-least-once delivery, dead-letter queues, and idempotent consumer handlers.

AML regulations (BSA in the US, AMLD in the EU) require financial institutions to detect and report suspicious activity. As an engineer, you build the **hooks**, not the compliance decisions:

- **Transaction monitoring hooks.** Every posted transfer fires an event (via Watermill/Kafka) that the AML screening system consumes. The AML system is typically a third-party service or an internal rules engine — your job is to make the event stream reliable and complete, with every required field.
- **Suspicious Activity Report (SAR) data model.** When compliance identifies a pattern that requires reporting, the system needs to reconstruct the full transaction history for the relevant accounts. Your immutable audit log is exactly this.
- **Structuring detection support.** Structuring is the practice of breaking large transactions into smaller ones to avoid reporting thresholds. Your data model should expose transaction history queryable by time window and account — the compliance team or AML engine builds the detection logic on top.
- **Freeze and hold workflows.** When an account is flagged, the system needs to block outbound transfers without necessarily closing the account. Model this as an explicit state (`account_status`: `active` | `frozen` | `under_review` | `closed`) and audit every state transition.

Given the `AuditEntry` and `AuditLog` types from the chapter, implement `Append` such that it correctly sets `PrevHash` from the previous entry's `Hash` and computes the new entry's `Hash` using `computeHash`. Write a simple main that appends two entries and prints both hashes.

<Solution>

```go
package main

import (
	"crypto/sha256"
	"encoding/hex"
	"encoding/json"
	"fmt"
	"time"
)

type AuditEntry struct {
	ID         int64
	OccurredAt time.Time
	ActorID    string
	Action     string
	EntityType string
	EntityID   string
	Before     json.RawMessage
	After      json.RawMessage
	PrevHash   string
	Hash       string
}

type AuditLog struct {
	entries []*AuditEntry
}

func computeHash(e *AuditEntry) string {
	h := sha256.New()
	fmt.Fprintf(h, "%d|%s|%s|%s|%s|%s|%s|%s|%s",
		e.ID,
		e.OccurredAt.UTC().Format(time.RFC3339Nano),
		e.ActorID,
		e.Action,
		e.EntityType,
		e.EntityID,
		e.Before,
		e.After,
		e.PrevHash,
	)
	return hex.EncodeToString(h.Sum(nil))
}

func (log *AuditLog) Append(e *AuditEntry) {
	if n := len(log.entries); n > 0 {
		e.PrevHash = log.entries[n-1].Hash
	}
	e.Hash = computeHash(e)
	log.entries = append(log.entries, e)
}

func main() {
	log := &AuditLog{}
	log.Append(&AuditEntry{
		ID:         1,
		OccurredAt: time.Now().UTC(),
		ActorID:    "user:1",
		Action:     "account.opened",
		EntityType: "account",
		EntityID:   "acc-1",
	})
	log.Append(&AuditEntry{
		ID:         2,
		OccurredAt: time.Now().UTC(),
		ActorID:    "user:1",
		Action:     "deposit.created",
		EntityType: "account",
		EntityID:   "acc-1",
	})
	for _, e := range log.entries {
		fmt.Printf("Entry %d: hash=%s prevHash=%s\n", e.ID, e.Hash[:8]+"...", func() string {
			if e.PrevHash == "" {
				return "(genesis)"
			}
			return e.PrevHash[:8] + "..."
		}())
	}
}
```

The first entry's `PrevHash` is empty (the genesis entry). The second entry's `PrevHash` equals the first entry's `Hash`. The chain is linked.

```go
func (log *AuditLog) Verify() int {

	for i, e := range log.entries {
		if e.PrevHash != prevHash {
			return i
		}
		if e.Hash != computeHash(e) {
			return i
		}
		prevHash = e.Hash
	}
	return -1
}
```

<Exercise n={5} title="Crypto-shredding: erase the key, not the data" level="hard">

Model a simple in-memory `KeyStore` that maps `userID` to an encryption key (a `[]byte`). Implement `Erase(userID string)` that deletes the key. Implement `CanDecrypt(userID string) bool` that returns `true` if the key exists and `false` if it has been erased. Write a main demonstrating that after erasure, the PII for that user is undecipherable even though the "encrypted PII blob" (a `[]byte`) still exists in the `UserPII` store.

<Solution>

```go
package main

import (
	"crypto/aes"
	"crypto/cipher"
	"crypto/rand"
	"errors"
	"fmt"
	"io"
)

// KeyStore maps userID → AES encryption key.
// In production, this is a secrets manager (Vault, AWS KMS, etc.).
type KeyStore struct {
	keys map[string][]byte
}

func NewKeyStore() *KeyStore {
	return &KeyStore{keys: make(map[string][]byte)}
}

func (ks *KeyStore) SetKey(userID string, key []byte) {
	ks.keys[userID] = key
}

func (ks *KeyStore) Erase(userID string) {
	delete(ks.keys, userID)
}

func (ks *KeyStore) CanDecrypt(userID string) bool {
	_, ok := ks.keys[userID]
	return ok
}

func (ks *KeyStore) Encrypt(userID string, plaintext []byte) ([]byte, error) {
	key, ok := ks.keys[userID]
	if !ok {
		return nil, errors.New("no key for user")
	}
	block, err := aes.NewCipher(key)
	if err != nil {
		return nil, err
	}
	gcm, err := cipher.NewGCM(block)
	if err != nil {
		return nil, err
	}
	nonce := make([]byte, gcm.NonceSize())
	if _, err := io.ReadFull(rand.Reader, nonce); err != nil {
		return nil, err
	}
	return gcm.Seal(nonce, nonce, plaintext, nil), nil
}

func (ks *KeyStore) Decrypt(userID string, ciphertext []byte) ([]byte, error) {
	key, ok := ks.keys[userID]
	if !ok {
		return nil, errors.New("key erased — PII is cryptographically gone")
	}
	block, _ := aes.NewCipher(key)
	gcm, _ := cipher.NewGCM(block)
	nonceSize := gcm.NonceSize()
	return gcm.Open(nil, ciphertext[:nonceSize], ciphertext[nonceSize:], nil)
}

func main() {
	ks := NewKeyStore()

	// Generate a 256-bit AES key for user 42.
	key := make([]byte, 32)
	rand.Read(key) //nolint:errcheck
	ks.SetKey("user:42", key)

	pii := []byte(`{"name":"Alice Smith","email":"alice@example.com"}`)
	encrypted, err := ks.Encrypt("user:42", pii)
	if err != nil {
		panic(err)
	}
	fmt.Println("PII encrypted. Blob stored. Key exists:", ks.CanDecrypt("user:42"))

	// GDPR erasure request: delete the key.
	ks.Erase("user:42")
	fmt.Println("Key erased. CanDecrypt:", ks.CanDecrypt("user:42"))

	// The encrypted blob still exists — but is now undecipherable.
	_, err = ks.Decrypt("user:42", encrypted)
	fmt.Println("Decrypt attempt:", err) // key erased — PII is cryptographically gone
	fmt.Println("Encrypted blob still exists (bytes):", len(encrypted), "bytes — but unreadable")
}
```

The blob is still there. The bytes are still on disk. But without the key, they are cryptographically indistinguishable from random noise. This is the engineering answer to the GDPR erasure vs. immutable audit trail problem.

<Recap>

You now have the full engineering playbook for auditability and compliance:

- An **immutable audit log** records WHO, WHAT, and WHEN for every state change. Rows are written once, never updated, never deleted — enforced at the database permission level, not just in code.
- **Hash chaining** makes the log tamper-evident: each entry's `Hash` covers all content plus the previous entry's `Hash`. Altering any entry breaks every subsequent chain link. The `crypto/sha256` standard library is all you need (Go 1.26 baseline; no external dependency required).
- **Append-only event stores** are the audit trail: the event log from your Kafka/Watermill architecture is also the compliance record. Order by sequence number, not wall-clock time.
- **Wall-clock time is unreliable for ordering** — NTP slews and clock skew across servers make timestamp ordering ambiguous. Use sequence numbers for ordering; store UTC timestamps for humans and regulators. Go's `time.Time` carries both wall and monotonic clocks since Go 1.9.
- **Data retention** must balance regulatory minimums (PCI-DSS: 12 months, AML: 5 years) against GDPR's right to erasure. The engineering answer is **crypto-shredding**: store PII encrypted with a per-user key, and delete the key on erasure. The audit trail survives; the PII is gone.
- **PCI-DSS**: never store raw PANs — tokenize at the provider. TLS 1.2+ everywhere. Use `slog.LogValuer` to make sensitive types self-masking in logs.
- **KYC**: identity documents are high-sensitivity PII. Short-lived pre-signed URLs, access logs, explicit state machines, and retain for the AML window.
- **AML**: build the hooks — reliable event streams to monitoring systems, queryable transaction history for SAR construction, account freeze/hold state machines. Compliance builds the rules on top; you build the infrastructure underneath.
