<HeroCard label="Part 3 · Chapter 4" title="Idempotency & Exactly-Once Semantics">

A merchant's checkout sends Meridian a payment and waits. The answer doesn't come: the network dropped it, or Meridian was slow, or it crashed. Was the card charged? The checkout can't know. If it doesn't retry, the customer may not be charged for goods they received; if it does, they may be charged twice. Every call over a network has this problem, and in payments both mistakes cost real money.

The answer is to make repeating a request harmless: **idempotency**. This chapter builds it into Meridian's payment API and measures each way to get it wrong: retries without it, a key check with a race, a crash in the middle. Then it follows the payment's *event* out of the database and into a message stream, where the same problem appears twice more: publishing exactly once, and consuming exactly once.

Six stops. If you get lost, come back here:

1. **Retries charge twice.** Late answers, retries, and the duplicates they create.
2. **Idempotency keys.** One key per payment, claimed in the same transaction as the payment.
3. **The race.** Two copies of one request at the same moment.
4. **At-least-once, exactly-once.** What can be guaranteed over a network, and what can't.
5. **The outbox.** Recording and publishing an event without losing it.
6. **The inbox.** Consuming an event once, however often it's delivered.

## The lab bench

Meridian's payment API is a Go HTTP server (`cmd/api`, `POST /payments`) that posts each card payment to chapter 2's ledger (PostgreSQL 14.19) and records a `payment.succeeded` event. A merchant's checkout is `cmd/client`: it sends payments with an `Idempotency-Key` header, 16 at a time, and when a request times out (300 ms), fails with a 5xx, or can't connect, sends the same request again with the same key. Events go to a Redis 8.10 stream (`meridian:payments`), with `github.com/redis/go-redis/v9` v9.22.0; `cmd/relay` and `cmd/consumer` move and read them.

## Retries

*Stop 1 of 6.*

### Step 1: the answer that doesn't arrive

A request can fail in three places: before the server received it, while the server was working, or after the server finished, on the way back. The client sees the same thing in all three cases: no answer. Only in the first two is it safe to assume nothing happened, and it can't tell which case it's in.

### Step 2: measured

The server is told to make 5% of requests take an extra second, either **before** its database transaction commits or **after**, and the client retries anything that times out. No idempotency yet:

```text
== no idempotency, 5% of requests slow before commit
client: 1000 payments, 1227 HTTP attempts, 1000 successes (0 replayed), 0 gave up
ledger: 1000 card payments posted, $104,854.43 charged
== no idempotency, 5% of requests slow after commit
client: 1000 payments, 1050 HTTP attempts, 1000 successes (0 replayed), 0 gave up
ledger: 1050 card payments posted, $111,538.01 charged
```

Slow **before** commit: 227 retries, and still exactly 1,000 payments. When the client gave up, Go's `net/http` cancelled the request's context, the pgx transaction was running on that context, so it rolled back. The retry was then the only payment. (Passing the request's context to the database is what made that safe.)

Slow **after** commit: 50 retries, **1,050 payments**. Those 50 had committed; their answers were merely late. Each retry was charged again, and the client, having received exactly one success per payment, never knew. A late answer is the dangerous case, and no amount of care inside the server prevents it, because the server did nothing wrong.

## Keys

*Stop 2 of 6.*

### Step 1: the design

The fix, used by Stripe, Adyen and most payment APIs, is an **idempotency key**: the client generates a unique key for each payment it means to make (a random 128-bit value, or its own order id) and sends it in a header, `Idempotency-Key`. The same payment, retried, carries the same key. The server remembers each key with the response it produced:

- a **new** key: do the work, store the response;
- a **known** key with the **same** request: return the stored response, marked as a replay, without doing anything;
- a **known** key with a **different** request: refuse (422), because the client has a bug and guessing would be worse.

### Step 2: in one transaction

The key, the payment and the stored response must succeed or fail together, or a crash between them breaks the guarantee (a key stored without its payment makes a retry replay a payment that doesn't exist; a payment without its key gets charged again). So the server claims the key with an `INSERT` in the same database transaction as the payment:

```sql
// extra.sql, lines 7–16
-- One row per Idempotency-Key a client has sent (stop 2). The row is
-- inserted, the payment posted and the response stored in one database
-- transaction.
CREATE TABLE idempotency_keys (
    key          text PRIMARY KEY,
    request_hash bytea NOT NULL,
    status       int,
    response     jsonb,
    created_at   timestamptz NOT NULL DEFAULT now()
);
```

```go noverify
// payments.go, lines 164–196
// atomic claims the key with an INSERT that only one transaction can
// win, does the work and stores the response, all in one transaction. A
// concurrent request with the same key blocks on the INSERT until the
// first commits, then finds the stored response and replays it. A crash
// rolls back the claim with the work, so a retry starts clean.
func (s *Server) atomic(ctx context.Context, key string, req PaymentRequest) (PaymentResponse, bool, error) {
	var resp PaymentResponse
	var replayed bool
	h := hash(req)
	err := pgx.BeginFunc(ctx, s.DB, func(tx pgx.Tx) error {
		tag, err := tx.Exec(ctx, `INSERT INTO idempotency_keys (key, request_hash) VALUES ($1, $2) ON CONFLICT (key) DO NOTHING`, key, h)
		if err != nil {
			return err
		}
		if tag.RowsAffected() == 0 { // someone already committed this key
			var storedHash, stored []byte
			if err := tx.QueryRow(ctx, `SELECT request_hash, response FROM idempotency_keys WHERE key = $1`, key).Scan(&storedHash, &stored); err != nil {
				return err
			}
			if string(storedHash) != string(h) {
				return errMismatch
			}
			replayed = true
			return json.Unmarshal(stored, &resp)
		}
		if resp, err = s.post(ctx, tx, req); err != nil {
			return err
		}
		_, err = tx.Exec(ctx, `UPDATE idempotency_keys SET status = 200, response = $2 WHERE key = $1`, key, resp)
		return err
	})
	return resp, replayed, err
}
```

```text
== idempotency keys, 5% of requests slow after commit
client: 1000 payments, 1053 HTTP attempts, 1000 successes (50 replayed), 0 gave up
ledger: 1000 card payments posted, $104,090.65 charged
```

The same slow-after-commit load as stop 1: 53 retries, **50 replays, 1,000 payments**. The late answers' retries found their keys and got the stored responses.

### Step 3: a crash in the middle

Because the claim is part of the payment's transaction, a crash can't leave one without the other. The server was killed with `SIGKILL` one second into 20,000 payments and restarted a second later; the client retried everything that failed:

```text
== idempotency keys, server SIGKILLed after 1 s and restarted 1 s later
(killed)
client: 20000 payments, 20096 HTTP attempts, 20000 successes (0 replayed), 0 gave up
ledger: 20000 card payments posted, $2,090,543.68 charged
== the same key, a different amount
amount 1999: HTTP 200
amount 2999: HTTP 422
```

96 requests were in flight or refused while the server was down. None was replayed (their transactions had died uncommitted, keys included), all were retried and done once: **20,000 payments, exactly**. Finally, the same key reused for a different amount:

```text
amount 1999: HTTP 200
amount 2999: HTTP 422
```

## The Race

*Stop 3 of 6.*

### Step 1: check, then insert

The obvious implementation looks the key up first, and if it isn't there, does the work and saves the key:

```go noverify
// payments.go, lines 138–162
// checkFirst is the obvious version: is the key known? If so, replay;
// if not, do the work and remember the key. Two requests with the same
// key can both find it unknown.
func (s *Server) checkFirst(ctx context.Context, key string, req PaymentRequest) (PaymentResponse, bool, error) {
	var stored []byte
	err := s.DB.QueryRow(ctx, `SELECT response FROM idempotency_keys WHERE key = $1`, key).Scan(&stored)
	if err == nil {
		var resp PaymentResponse
		return resp, true, json.Unmarshal(stored, &resp)
	}
	if !errors.Is(err, pgx.ErrNoRows) {
		return PaymentResponse{}, false, err
	}
	var resp PaymentResponse
	err = pgx.BeginFunc(ctx, s.DB, func(tx pgx.Tx) error {
		var err error
		if resp, err = s.post(ctx, tx, req); err != nil {
			return err
		}
		_, err = tx.Exec(ctx, `INSERT INTO idempotency_keys (key, request_hash, status, response) VALUES ($1, $2, 200, $3)
			ON CONFLICT (key) DO NOTHING`, key, hash(req), resp)
		return err
	})
	return resp, false, err
}
```

Two copies of one request arriving at the same moment (a double click, or a retry racing a slow original) both look, both find nothing, and both charge. The client sent each of 1,000 payments twice at once:

```text
== double click, check the key first
client: 1000 payments, 2000 HTTP attempts, 2000 successes (1 replayed), 0 gave up
ledger: 1999 card payments posted, $214,071.67 charged
== double click, claim the key atomically
client: 1000 payments, 2000 HTTP attempts, 2000 successes (1000 replayed), 0 gave up
ledger: 1000 card payments posted, $106,330.17 charged
```

Check-first: **999 of 1,000 charged twice**. Claiming the key atomically: 1,000 payments and 1,000 replays. The difference is where the decision happens. In `atomic`, the `INSERT ... ON CONFLICT DO NOTHING` is the check: the primary key lets only one transaction insert the row, and the second one's `INSERT` **waits** for the first to commit (it's the same row), then sees the conflict, reads the stored response and replays it.

## Delivery

*Stop 4 of 6.*

### Step 1: the three guarantees

Messaging systems describe what they promise about delivery with three phrases:

- **At most once**: send, and don't retry. Nothing is ever duplicated; some things are lost. (The checkout that never retries.)
- **At least once**: retry until acknowledged. Nothing is lost; some things arrive more than once. (The checkout in this chapter: 1,053 attempts for 1,000 payments.)
- **Exactly once**: every message processed once. Over a network that can lose messages and answers, **delivery** can't be exactly once: after a lost acknowledgement, the sender must either resend (risking a duplicate) or not (risking a loss), and it can't know which it avoided.

### Step 2: exactly-once effect

What systems actually build is an **exactly-once effect**: at-least-once delivery, plus a receiver that recognises repeats and does nothing for them. That's what stops 2 and 3 built for payments: 1,053 deliveries, 1,000 charges. When a system (Kafka's "exactly-once semantics" included) says it does exactly-once, this is what it means: duplicates are delivered and then filtered by an id, inside a transaction, on the receiving side.

The rest of the chapter applies the same idea one hop further: to the event Meridian publishes when a payment succeeds, and to the service that consumes it.

## Outbox

*Stop 5 of 6.*

### Step 1: the dual write

Other parts of Meridian react to payments: receipts, merchant dashboards, fraud models. So a successful payment should publish a `payment.succeeded` event to a message stream. The obvious code commits the payment, then publishes, as two separate writes to two systems:

```go noverify
// main.go, lines 39–56
		publish := func() error {
			return rdb.XAdd(ctx, &redis.XAddArgs{Stream: "meridian:payments", Values: event}).Err()
		}
		if *publishFirst {
			if err := publish(); err != nil {
				log.Fatal(err)
			}
		}
		err := pgx.BeginFunc(ctx, db, func(tx pgx.Tx) error { _, err := ledger.PostTx(ctx, tx, t); return err })
		if err != nil {
			log.Fatal(err)
		}
		if !*publishFirst {
			if err := publish(); err != nil {
				failed++ // the payment is committed; log it and carry on, as a handler would
			}
		}
	}
```

```text
== commit, then publish (5 runs, each SIGKILLed after 1 s)
run 1: 84 payments committed, 84 events published
run 2: 568 payments committed, 568 events published
run 3: 555 payments committed, 555 events published
run 4: 498 payments committed, 498 events published
run 5: 561 payments committed, 561 events published
== publish, then commit (5 runs, each SIGKILLed after 1 s)
run 1: 648 payments committed, 649 events published
run 2: 618 payments committed, 619 events published
run 3: 287 payments committed, 288 events published
run 4: 306 payments committed, 307 events published
run 5: 253 payments committed, 254 events published
== commit, then publish: Redis stopped for 1 s during 10,000 payments
94 publishes failed and were logged
10000 payments committed, 9907 events published
```

Two orders, two failure modes:

- **Publish, then commit**: killed between the two, 4 runs of 5 published an event for a payment that never committed: a receipt for a charge that doesn't exist.
- **Commit, then publish**: the kill never landed in the tiny gap in five runs, but the gap is still there, and a broker outage widens it. With Redis stopped for one second during 10,000 payments, **93 events were lost**: the payments committed, the publishes failed, and the code logged the errors and moved on, which is all a request handler can do. (94 publishes reported an error; one of them had in fact reached Redis before the connection broke. Even the failures are uncertain.)

There's no order of two writes to two systems that can't be split by a crash between them.

### Step 2: one write, then relay it

The **transactional outbox** removes the second write from the request. The event is written as a row in an `outbox` table **in the same database transaction as the payment** (stop 2's `post` does this); a separate process, the **relay**, publishes unpublished rows and marks them published:

```sql
// extra.sql, lines 18–27
-- Events to publish, written in the same transaction as the change that
-- caused them (stop 5).
CREATE TABLE outbox (
    id           bigserial PRIMARY KEY,
    topic        text NOT NULL,
    payload      jsonb NOT NULL,
    created_at   timestamptz NOT NULL DEFAULT now(),
    published_at timestamptz
);
CREATE INDEX outbox_unpublished ON outbox (id) WHERE published_at IS NULL;
```

```go noverify
// main.go, lines 35–74
// relayBatch publishes up to 100 events. SKIP LOCKED lets several relays
// run at once without taking the same rows. If the process dies after
// XADD and before COMMIT, those events are published again next time:
// at least once, never zero times.
func relayBatch(ctx context.Context, db *pgxpool.Pool, rdb *redis.Client) (int, error) {
	n := 0
	err := pgx.BeginFunc(ctx, db, func(tx pgx.Tx) error {
		rows, err := tx.Query(ctx, `SELECT id, payload FROM outbox WHERE published_at IS NULL
			ORDER BY id LIMIT 100 FOR UPDATE SKIP LOCKED`)
		if err != nil {
			return err
		}
		type ev struct {
			id      int64
			payload map[string]any
		}
		evs, err := pgx.CollectRows(rows, func(r pgx.CollectableRow) (ev, error) {
			var e ev
			var raw []byte
			if err := r.Scan(&e.id, &raw); err != nil {
				return e, err
			}
			return e, json.Unmarshal(raw, &e.payload)
		})
		if err != nil {
			return err
		}
		for _, e := range evs {
			if err := rdb.XAdd(ctx, &redis.XAddArgs{Stream: "meridian:payments", Values: e.payload}).Err(); err != nil {
				return err
			}
			if _, err := tx.Exec(ctx, `UPDATE outbox SET published_at = now() WHERE id = $1`, e.id); err != nil {
				return err
			}
			n++
		}
		return nil
	})
	return n, err
}
```

The payment and its event now commit together or not at all. The relay can crash, fall behind or find the broker down, and the event waits in the table until it's published. What it can't guarantee is *once*: if it dies after `XADD` and before its `COMMIT`, those rows are still unpublished and go out again. 5,000 payments through the API, with the relay killed three times mid-run:

```text
== outbox: 5,000 payments through the API; the relay SIGKILLed three times
client: 5000 payments, 5000 HTTP attempts, 5000 successes (0 replayed), 0 gave up
5000 payments committed, 5000 outbox events, 5052 stream entries
```

5,000 events, **none lost**, and 52 published twice: at-least-once, by design. `FOR UPDATE SKIP LOCKED` lets several relays share the table without taking the same rows; Postgres logical replication (change data capture, Debezium) can replace the polling loop, with the same at-least-once result.

## Inbox

*Stop 6 of 6.*

### Step 1: the consumer's side

A consumer of `payment.succeeded` sends the merchant a receipt. Reading the stream with duplicates in it, a naive consumer sends one per delivery. An **idempotent consumer** keeps an **inbox**: a table of event ids it has applied, written in the same transaction as the effect, so an event's id is recorded if and only if its receipt was sent:

```go noverify
// main.go, lines 44–54
			err := pgx.BeginFunc(ctx, db, func(tx pgx.Tx) error {
				if *inbox {
					tag, err := tx.Exec(ctx, `INSERT INTO inbox (event_id) VALUES ($1) ON CONFLICT DO NOTHING`, id)
					if err != nil || tag.RowsAffected() == 0 {
						return err // seen before: nothing to do
					}
				}
				applied++
				_, err := tx.Exec(ctx, `INSERT INTO receipts VALUES ($1, 1) ON CONFLICT (merchant) DO UPDATE SET sent = receipts.sent + 1`, merchant)
				return err
			})
```

```text
== consumers reading that stream
consumer: read 5052 events, sent 5052 receipts
consumer: read 5052 events, sent 5000 receipts
   and again, from the start of the stream (a consumer restarted without its position):
consumer: read 5052 events, sent 0 receipts
```

Without the inbox: **5,052 receipts** for 5,000 payments. With it: **5,000**. Read again from the start of the stream, as a consumer that lost its position would: **0**, because every id is already in the inbox.

### Step 2: where the id comes from

The inbox only works if a repeated event carries the same id. That's why the id is created with the event, inside the payment's transaction (`pay-<ledger transaction id>`), not by the relay or the broker: Redis gives each `XADD` a new stream id, so the duplicate's stream id differs even though its `event_id` doesn't. The same principle as the idempotency key: **the identity of an operation is decided once, where it's created, and travels with every copy**.

When the effect isn't in the consumer's own database (sending an email, calling another API), the inbox row can't commit atomically with it. Then the consumer passes the event id on as that system's idempotency key, and the chain of idempotency continues one hop further, the way chapter 3's saga did with the bank.

## Exercises

These use the `pay` module, the database and the Redis stream from this chapter.

<Exercise n={1} title="Expire keys" level="easy">

The `idempotency_keys` table grows forever. Stripe keeps keys for 24 hours. Add a job that deletes old keys, and decide what a retry after expiry should get.

<Solution>

`DELETE FROM idempotency_keys WHERE created_at < now() - interval '24 hours'`, in batches, from a scheduled job (chapter 13 of part 2). After expiry, a retry is treated as a new payment; that's acceptable because clients stop retrying long before a day has passed, and it's documented behaviour. Don't expire keys whose response is still null (in progress) by age alone: those belong to a transaction that may still commit.

</Solution>

</Exercise>

<Exercise n={2} title="Scope keys per merchant" level="easy">

Two merchants both use their order number as the key: order 1001 at Acme and order 1001 at Globex. What goes wrong, and how do you fix it?

<Solution>

Globex's payment finds Acme's key and gets a 422 (different request) or, worse, a replay of Acme's response if the amounts match. Keys are only unique within one client, so make the primary key `(merchant_id, key)`, with the merchant taken from the authenticated caller, never from the request body.

</Solution>

</Exercise>

<Exercise n={3} title="In progress" level="medium">

In `atomic`, a second request with the same key waits for the first to commit. With a 30-second payment (a slow card network), that holds a connection and a row lock for 30 seconds. Change the design so the second request returns 409 Conflict immediately while the first is in progress.

<Solution>

Split the claim from the work: commit `INSERT INTO idempotency_keys (key, request_hash, status) VALUES ($1, $2, NULL)` in its own short transaction, do the work, then store the response. A second request finds a row with a null status and returns 409 (Stripe does this). The cost: a crash between the claim and the response leaves a key in progress forever, so add a `locked_until` timestamp and let a retry take over a claim whose time has passed, checking the ledger for a payment with that key before charging again.

</Solution>

</Exercise>

<Exercise n={4} title="Consumer group" level="medium">

Replace `XREAD` with a consumer group (`XREADGROUP`, `XACK`), run two consumers, and kill one mid-stream. Which events get delivered twice, and does the inbox still hold?

<Solution>

A consumer group delivers each entry to one consumer and keeps it in that consumer's pending list until `XACK`. Entries the killed consumer had read but not acknowledged are claimed by the survivor (`XAUTOCLAIM` after an idle time) and delivered again, some of them already applied. The inbox makes those harmless: their ids are in the table, so no second receipt. Acknowledge after the inbox transaction commits, never before, or a crash between them loses the event.

</Solution>

</Exercise>

<Exercise n={5} title="Outbox ordering" level="hard">

Two relays run with `SKIP LOCKED`. Can a merchant's `payment.refunded` event be published before its `payment.succeeded`? When does it matter, and how do you prevent it?

<Solution>

Yes: relay A locks rows 1 to 100 (including the payment) and relay B locks 101 to 200 (including the refund), and B can publish first. It matters to any consumer that treats the sequence as a state machine. Options: one relay (simple, a throughput ceiling); partition the outbox by merchant and give each partition one relay; or have consumers tolerate reordering by checking the ledger's state rather than trusting event order. Kafka's partitions (chapter 7) make the second option the default.

</Solution>

</Exercise>

import (
	"errors"
	"fmt"
	"runtime"
	"sync"
	"sync/atomic"
)

type Request struct {
	Merchant string
	Amount   int64
}

type Response struct {
	TxID   int64
	Amount int64
}

var ErrMismatch = errors.New("idempotency key reused with a different request")

// Store makes a payment handler idempotent. Do runs fn at most once per
// key: later calls with the same key and request get the stored response
// (replayed = true), concurrent calls wait for the first to finish, a
// different request under the same key gets ErrMismatch, and a call whose
// fn fails leaves nothing stored, so a retry runs fn again.
type Store struct {
	mu   sync.Mutex
	done map[string]Response
}

func NewStore() *Store { return &Store{done: map[string]Response{}} }

func (s *Store) Do(key string, req Request, fn func(Request) (Response, error)) (Response, bool, error) {
	s.mu.Lock()
	resp, seen := s.done[key]
	s.mu.Unlock()
	if seen {
		return resp, true, nil
	}
	resp, err := fn(req)
	s.mu.Lock()
	s.done[key] = resp
	s.mu.Unlock()
	return resp, false, err
}

// ── below this line: do not edit ──

func main() {
	ok := true
	fail := func(f string, a ...any) { fmt.Printf("FAIL "+f+"\\n", a...); ok = false }

	// Check 1: 1,000 payments, each sent by 8 callers at once (retries and
	// double clicks). Each must be charged exactly once, and every caller
	// must get the same response.
	s := NewStore()
	var charges sync.Map // key -> *atomic.Int64
	charge := func(key string) func(Request) (Response, error) {
		return func(r Request) (Response, error) {
			c, _ := charges.LoadOrStore(key, new(atomic.Int64))
			n := c.(*atomic.Int64).Add(1)
			runtime.Gosched() // the database round trip
			return Response{TxID: n*1_000_000 + r.Amount, Amount: r.Amount}, nil
		}

		req := Request{Merchant: "acme", Amount: int64(100 + k)}

		for c := range 8 {
			wg.Go(func() {
				resp, replayed, err := s.Do(key, req, charge(key))
				if err != nil {
					fail("%s: %v", key, err)
				}
				if replayed {
					replays.Add(1)
				}
				results[c] = resp
			})
		}

				break
			}
		}

	charges.Range(func(_, v any) bool {

		}
		return true
	})

	}

	}

		attempts++
		if attempts == 1 {
			return Response{}, errors.New("card network timeout")
		}
		return Response{TxID: 42, Amount: r.Amount}, nil
	}
	req := Request{Merchant: "acme", Amount: 1999}

<Recap>

- **Retries**: a client can't tell a lost request from a lost answer. Measured: answers late after commit, and retries charged 50 of 1,000 payments twice. Slow before commit, the cancelled request context rolled the transaction back, and nothing was duplicated.
- **Idempotency keys**: one client-generated key per payment; new key: do and store; known key, same request: replay; known key, different request: 422. Claimed with the payment in one transaction: 50 replays instead of 50 duplicates, and a SIGKILL during 20,000 payments left exactly 20,000.
- **The race**: check-then-insert let 999 of 1,000 double clicks charge twice; `INSERT ... ON CONFLICT DO NOTHING` makes the second wait and replay.
- **Delivery**: at most once, at least once, and no exactly-once delivery over a lossy network; exactly-once *effect* = at-least-once + idempotent receiver.
- **Outbox**: two writes to two systems can always be split: publish-then-commit invented events, commit-then-publish lost 93 in a one-second Redis outage. An outbox row in the payment's transaction plus a relay: none lost, 52 duplicates.
- **Inbox**: event ids recorded with the effect; 5,052 deliveries became 5,000 receipts, and a full replay sent none. The id is created with the event and travels with every copy.

</Recap>
