<HeroCard label="Part 3 · Chapter 12" title="Security for Financial Systems">

Merchants want Meridian to remember their customers' cards, so a returning customer can pay with one click and a subscription can renew every month. That means Meridian will **store card numbers**. A card number is the one piece of data a criminal can turn straight into money, and the card industry's rulebook, **PCI DSS** (the Payment Card Industry Data Security Standard, now at version 4.0.1), puts every system that stores, processes or transmits one under its strictest rules, along with everything connected to those systems.

This chapter builds Meridian's **card vault**: a small service that is the only code allowed to see a whole card number, and the defences around it. Each defence starts from something that goes wrong in a real program and ends with a measurement that shows the fix working. Everything here is defensive: how to protect the system you run.

Five stops. If you get lost, come back here:

1. **Card data.** Where card numbers leak (logs, errors, queues), and a type that can't leak them.
2. **Tokenize.** Keep card numbers in one place; hand everyone else a random token. Least-privilege database roles, and a record of every look.
3. **Envelope encryption.** Encrypt each card with AES-256-GCM under a data key, and keep the key that protects the data keys inside Vault.
4. **Signed requests.** Prove a merchant's API request came from the merchant, unchanged, and only once.
5. **The front door.** Passwords that are slow to guess, accounts that lock, and TLS that only talks to who it should.

## The lab bench

Everything in this chapter runs on one Apple M1 laptop (8 cores) with **Go 1.27.0**. The services it talks to are real:

- **HashiCorp Vault 2.1.1**, in Docker, in *dev mode*: it keeps everything in memory, starts unsealed with a root token, and serves plain HTTP on `127.0.0.1:8212`. That's fine for a lab bench and wrong for anything else; a real Vault runs with TLS, durable storage and no root token in use. Its **transit** engine, which this chapter uses, is also in OpenBao (the open-source fork of Vault) with the same API, and it has the same shape as AWS KMS or Google Cloud KMS.
- **PostgreSQL 14.19**, on `127.0.0.1:55432`. It trusts local connections, so each database role logs in without a password here; in production each role has its own credential, delivered the way Part 2's configuration chapter described.
- **Redis 8.10.2**, in Docker, on `127.0.0.1:6395`.

The card numbers are **synthetic**: 16 digits starting `400000`, the range processors' published test cards use, with a correct check digit, made from a fixed seed by `internal/testcards`. No real card number appears anywhere in this chapter. Timings on a laptop that is also doing other work vary; where it matters, the text gives the spread over several runs.

## Card Data

*Stop 1 of 5.*

### Step 1: what has to be protected

PCI DSS sorts the data on a card into two kinds, and treats them very differently:

- **Cardholder data**: the **PAN** (primary account number, the long number on the front), plus the cardholder's name and the expiry date. It may be stored if there's a business need, but the PAN must be **unreadable wherever it is stored** (requirement 3.5.1) and **masked when displayed**, showing at most the first six and last four digits (3.4.1).
- **Sensitive authentication data**: the **CVC** (the three or four digits on the back), the full magnetic-stripe or chip data, and PINs. These must **not be kept after the payment is authorized, not even encrypted** (3.3.1). Meridian passes the CVC to the card network once and forgets it.

The standard applies to the **cardholder data environment**: every system that stores, processes or transmits card data, and every system connected to those. That last clause is what makes card numbers expensive. A card number that reaches a log file brings the log pipeline, the log storage, and everyone who can search the logs into the environment an assessor has to check. So the first job isn't encryption. It's making sure card numbers only go where they're meant to.

<Define term="PAN">Primary account number: the 13 to 19 digits on the front of a card. The first six (sometimes eight) are the BIN, the issuing bank's identification number; the last digit is a check digit.</Define>

### Step 2: where card numbers go by accident

Nobody writes `log(cardNumber)`. Card numbers leak because they're inside something else that gets logged. `cmd/leak` runs 1,000 checkouts against a real HTTP handler that does three ordinary things with a declined payment:

```go noverify title="cardvault/cmd/leak/main.go · lines 38–57"
// handler decodes the body into a T and declines every fourth checkout.
func handler[T any](log *slog.Logger, queue *bytes.Buffer) http.HandlerFunc {
	n := 0
	return func(w http.ResponseWriter, r *http.Request) {
		var req T
		if err := json.NewDecoder(r.Body).Decode(&req); err != nil {
			http.Error(w, "bad request", 400)
			return
		}
		if n++; n%4 != 0 {
			return
		}
		log.Warn("charge declined", "req", req)               // 1: a log line
		err := fmt.Errorf("charge %+v: %w", req, errDeclined) // 2: an error...
		log.Error("request failed", "err", err)               // ...logged upstream
		b, _ := json.Marshal(req)                             // 3: a retry message
		queue.Write(append(b, '\n'))
		http.Error(w, "payment declined", http.StatusPaymentRequired)
	}
}
```

It logs the request, wraps it in an error that something upstream logs, and puts it on a retry queue as JSON. At the start, the request type is plain strings:

### Step 3: a type that masks itself, first attempt

Go decides how to print a value by asking what methods its type has. `fmt` calls `String()` for `%v` and `%s`, and `GoString()` for `%#v`; `log/slog` calls `LogValue()`; `encoding/json` calls `MarshalJSON()`. So a card number should be its own type, with its digits unexported, and every one of those methods returning the masked form. The first attempt did exactly that, with the digits in an unexported struct field and these methods:

```go noverify title="first attempt: card/pan.go (not kept)"
func (p PAN) String() string               { return p.Masked() } // %v, %s
func (p PAN) GoString() string             { return p.Masked() } // %#v
func (p PAN) LogValue() slog.Value         { return slog.StringValue(p.Masked()) }
func (p PAN) MarshalJSON() ([]byte, error) { return json.Marshal(p.Masked()) }
```

The test that goes with it prints a PAN every way we could think of and fails if the digits appear in any of them: `%v`, `%+v`, `%#v`, `%s`, `%d`, `%x`, inside a struct field, inside an unexported field, in a wrapped error, through slog's text and JSON handlers, and through `json.Marshal`. `go vet`, which `go test` also runs before every test, flagged one of its lines:

```text

```

Four leaks, from two causes:

1. **`%d`** isn't a verb `fmt` uses `String()` for (only `%v`, `%s`, `%x`, `%X` and `%q` are). So it prints the struct's fields itself, with `%d` applied to the string: `%!d(string=4000000000000077)`. The error marker doesn't stop the digits appearing. `go vet` catches a literal `%d` on this type, but not a format string built at run time.
2. **An unexported field.** When `fmt` prints a struct, it calls each field's methods only if the field could be used from outside its package, which an unexported field can't. So `{card PAN}` inside another type is printed by walking into it: `%+v`, `%#v`, and slog's text handler (which uses `%+v` for values it doesn't otherwise understand) all printed the digits. This is the PredictLab at the top of the chapter.

### Step 4: the type that stays masked

Both causes have a fix. For the verbs, `fmt` has one method that takes over every verb: `Format`. For the unexported field, there's a rule in `fmt` to lean on: when it walks into a struct and meets a **pointer** below the top level, it prints the address, not what it points to. So the digits go behind a pointer:

```go noverify title="cardvault/card/pan.go · lines 13–19"
// PAN is a primary account number, the long number on a card. Every way Go
// has of printing a value shows only its last four digits.
type PAN struct {
	n *number // behind a pointer: fmt prints a nested pointer as an address
}

type number struct{ digits string }
```

```go noverify title="cardvault/card/pan.go · lines 81–85"
// Format is used by fmt for every verb: %v, %+v, %#v, %s, %d, %x...
func (p PAN) Format(f fmt.State, verb rune) { fmt.Fprint(f, p.Masked()) }
func (p PAN) String() string                { return p.Masked() }
func (p PAN) LogValue() slog.Value          { return slog.StringValue(p.Masked()) }
func (p PAN) MarshalJSON() ([]byte, error)  { return json.Marshal(p.Masked()) }
```

`Format` is called for `%v`, `%+v`, `%#v`, `%s`, `%d`, `%x` and every other verb, and writes the masked form. `String` stays for code that asks for a string directly, `LogValue` for slog, `MarshalJSON` for JSON. `CVC` gets the same treatment and prints as `•••`. The same test, on this type:

And `cmd/leak`'s second request type, the same fields as `card.PAN` and `card.CVC`, which produced the last three lines of the output in Step 2:

<UnderTheHood title="Why fmt skips methods on unexported fields">

`fmt` finds methods through reflection, and Go's reflection enforces the same visibility rules as ordinary code: a value reached through an unexported field is marked read-only, and `reflect.Value.Interface()` on it panics. `fmt` checks `CanInterface()` before calling `Format`, `String` or any other method on a field, and when it's false it falls back to printing the value's structure. That's a deliberate safety rule (otherwise any package could call methods on another package's hidden fields just by printing them), and it's why the masking has to survive structural printing. A nested pointer is printed as an address, `0xc000012345`, because following pointers inside structures could loop forever on a cyclic structure; that's the rule the pointer fix relies on.

</UnderTheHood>

### Step 5: check it at the door

The other half of handling card data is refusing anything that isn't one. `Parse` accepts exactly 13 to 19 ASCII digits with a correct **Luhn check digit**, and nothing else:

```go noverify title="cardvault/card/pan.go · lines 21–54"
// Parse accepts 13 to 19 ASCII digits whose Luhn check digit is right, and
// nothing else: no spaces, no dashes, no other characters.
func Parse(s string) (PAN, error) {
	if len(s) < 13 || len(s) > 19 {
		return PAN{}, fmt.Errorf("%w: %d digits", ErrInvalid, len(s))
	}
	for i := 0; i < len(s); i++ {
		if s[i] < '0' || s[i] > '9' {
			return PAN{}, fmt.Errorf("%w: character %d is not a digit", ErrInvalid, i+1)
		}
	}
	if !luhn(s) {
		return PAN{}, fmt.Errorf("%w: wrong check digit", ErrInvalid)
	}
	return PAN{n: &number{s}}, nil
}

// luhn reports whether the last digit of s is the right check digit:
// double every second digit from the right, subtract 9 from any result
// over 9, and the sum of all the digits must end in 0.
func luhn(s string) bool {
	sum, double := 0, false
	for i := len(s) - 1; i >= 0; i-- {
		d := int(s[i] - '0')
		if double {
			if d *= 2; d > 9 {
				d -= 9
			}
		}
		sum += d
		double = !double
	}
	return sum%10 == 0
}
```

The Luhn check (ISO/IEC 7812) catches every single mistyped digit and most swaps of two neighbouring digits: that's its job, not security. The test's rejects include `4000000000000078` (last digit wrong) and `4000000000000707` (two digits swapped). Note what it doesn't do: it doesn't strip spaces or dashes to be helpful. A parser that quietly repairs input is a parser whose behaviour someone has to reason about; if the checkout form allows spaces, the form removes them, once, where everyone can see it. `UnmarshalJSON` calls `Parse`, so a request with a bad number fails while it's being decoded, before any handler code runs:

```go noverify title="cardvault/card/pan.go · lines 87–100"
// UnmarshalJSON is the way in: a request's "number" field is parsed, and
// rejected, right at the edge.
func (p *PAN) UnmarshalJSON(b []byte) error {
	var s string
	if err := json.Unmarshal(b, &s); err != nil {
		return fmt.Errorf("%w: not a string", ErrInvalid)
	}
	v, err := Parse(s)
	if err != nil {
		return err
	}
	*p = v
	return nil
}
```

`card.Scan` is the same Luhn check pointed the other way, at text: it counts digit runs that could be card numbers. `cmd/leak` used it to count the leaks, and it belongs in a test that exercises your handlers and fails if their logs contain anything it finds (Exercise 3).

## Tokenize

*Stop 2 of 5.*

### Step 1: keep the number in one place

Masking stops accidents. It doesn't shrink the problem: every service that holds a `card.PAN`, even one that never prints it, is still a system that stores or processes card numbers, so it's still in PCI DSS scope, with its database, its backups, its engineers' access and its deploy pipeline.

**Tokenization** shrinks it. One small service, the **card vault**, receives the card number, stores it, and hands back a **token**: a random string such as `tok_3PI4LHIBG6MKETZ5C7VP3OC3BY` that stands for the card. Everything else in Meridian (the payments service, the ledger, the retry queue, analytics, the logs) stores and passes around tokens. When a card has to be charged, the payments service asks the vault to charge `tok_…`, and only the vault turns it back into a number, on its way to the card network.

For this to take the checkout API out of scope too, the card number must go **straight from the customer's browser to the vault** (a payment form the vault serves, the way processors' hosted fields work), and the browser sends Meridian's API only the token. Then the only systems that ever see a number are the vault and its link to the card network: a few hundred lines of code, one database, one team.

### Step 2: a token is just random

A token must say nothing about the card. The tempting shortcuts, a hash of the number or the number encrypted, both fail: a hash can be recomputed by anyone who guesses the number (Step 3 measures how fast), and a ciphertext is only as safe as a key that would now be spread across every service holding tokens. So a token is **random**, and the only link between it and the number is a row in the vault's database:

```go noverify title="cardvault/vault/vault.go · line 97"
	token = "tok_" + rand.Text() // 128 random bits; nothing to do with the number
```

`crypto/rand.Text`, added in Go 1.24, returns 26 characters of base32 carrying at least 128 bits of randomness, from the operating system's secure generator. (Since Go 1.24 `crypto/rand.Read` can't return an error either: if the operating system can't provide randomness, the program crashes rather than continue with bad keys.) Nobody can guess another card's token, and a stolen token is useless outside Meridian, because only Meridian's vault can turn it into a number.

The vault's table keeps the token, the encrypted number (Stop 3), and two things other code is allowed to know:

```sql title="cardvault/schema.sql · lines 13–21"
CREATE TABLE cards (
    token       text PRIMARY KEY,            -- what the rest of Meridian keeps
    fingerprint bytea NOT NULL UNIQUE,       -- HMAC-SHA256 of the number
    last4       text NOT NULL,
    dek_id      bigint NOT NULL REFERENCES deks,
    nonce       bytea NOT NULL,
    pan         bytea NOT NULL,              -- AES-256-GCM ciphertext + tag
    created_at  timestamptz NOT NULL DEFAULT now()
);
```

### Step 3: finding the same card again

Merchants ask one question the token can't answer: is this the same card as last time? (To offer "pay with your saved card", or to spot one card used across many accounts.) That needs a **fingerprint**: a value computed from the number that's the same every time for the same card and can't be turned back into it.

The obvious fingerprint is SHA-256 of the number. It isn't safe, and the reason is how little of a card number is secret. PCI DSS lets Meridian show the first six and last four digits on receipts and in the dashboard; the last is a check digit. For a 16-digit card that leaves **six unknown digits**: a million possibilities, and the check digit rules out nine in ten of them, leaving **100,000**. A computer can hash 100,000 strings in a blink.

To find out whether that matters in practice, `cmd/fingerprint` checks Meridian's own design: for 100 synthetic cards it stores the first six and last four digits next to a fingerprint, as a copy of the table would contain, and tries every candidate number against it. Once with plain SHA-256 fingerprints, once with HMAC-SHA256 fingerprints whose key stays in the vault:

```text
SHA-256     fingerprints: 100 of 100 card numbers found, 51173 candidates each, 68ms per card
HMAC-SHA256 fingerprints:   0 of 100 card numbers found, 100000 candidates each, 137ms per card
```

**All 100 plain fingerprints gave their card number back, in 68 ms each**, after about 51,000 guesses on average. The keyed ones gave back **none**: without the key, the only thing anyone can compute is a plain hash, and no guess matches. That is exactly why PCI DSS 4.0 added requirement **3.5.1.1**: a hash used to protect a PAN must be a **keyed cryptographic hash** of the entire PAN (HMAC is the usual one), with its key managed like any other cryptographic key. It has been mandatory since 31 March 2025.

<Define term="HMAC">A hash-based message authentication code: a hash computed together with a secret key (RFC 2104). The same input and key always give the same output; without the key, nobody can compute it or check a guess against it. Go's is crypto/hmac.</Define>

The vault's fingerprint:

```go noverify title="cardvault/vault/vault.go · lines 62–68"
// Fingerprint identifies a card without revealing it: HMAC-SHA256 of the
// number under a secret key. Without the key it can't be recomputed.
func (v *Vault) Fingerprint(p card.PAN) []byte {
	m := hmac.New(sha256.New, v.fpKey)
	m.Write([]byte(p.Reveal()))
	return m.Sum(nil)
}
```

`fpKey` is a data key like the ones in Stop 3: made by Vault, stored only in wrapped form, and unwrapped into memory when the vault starts. The `fingerprint` column is `UNIQUE`, so each card is stored once.

### Step 4: tokenize

```go noverify title="cardvault/vault/vault.go · lines 86–109"
// always gets the same token back.
func (v *Vault) Tokenize(ctx context.Context, p card.PAN) (string, error) {
	fp := v.Fingerprint(p)
	var token string
	err := v.db.QueryRow(ctx, `SELECT token FROM cards WHERE fingerprint = $1`, fp).Scan(&token)
	if err == nil {
		return token, nil
	} else if !errors.Is(err, pgx.ErrNoRows) {
		return "", err
	}
	token = "tok_" + rand.Text() // 128 random bits; nothing to do with the number
	id, key, err := v.sealingKey(ctx)

	if err != nil {

	return token, err
}
```

### Step 6: every look is written down

The number comes back out in one place, `Detokenize`, which the vault's own charge and refund handlers call just before they talk to the card network. It checks why the number is wanted against a short list, and records every request, granted or refused:

```go noverify title="cardvault/vault/vault.go · lines 111–144"
// Detokenize returns the card number behind a token, for an allowed
// purpose. Every request is recorded: who asked, for which card, why, and
// whether they got it. A granted one is recorded in the same transaction
// as the read.
func (v *Vault) Detokenize(ctx context.Context, actor, token, purpose string) (card.PAN, error) {
	if !purposes[purpose] {
		_, err := v.db.Exec(ctx, `INSERT INTO card_access (actor, token, purpose, granted)
			VALUES ($1, $2, $3, false)`, actor, token, purpose)
		return card.PAN{}, errors.Join(fmt.Errorf("%w: %q", ErrPurpose, purpose), err)
	}
	var id int64
	var nonce, ct []byte
	err := pgx.BeginFunc(ctx, v.db, func(tx pgx.Tx) error {
		err := tx.QueryRow(ctx, `SELECT dek_id, nonce, pan FROM cards WHERE token = $1`, token).Scan(&id, &nonce, &ct)
		if err != nil {
			return err
		}
		_, err = tx.Exec(ctx, `INSERT INTO card_access (actor, token, purpose, granted)
			VALUES ($1, $2, $3, true)`, actor, token, purpose)
		return err
	})
	if err != nil {
		return card.PAN{}, err
	}
	key, err := v.key(ctx, id)
	if err != nil {
		return card.PAN{}, err
	}
	digits, err := open(key, nonce, ct, []byte(token))
	if err != nil {
		return card.PAN{}, fmt.Errorf("card %s: %w", token, err)
	}
	return card.Parse(string(digits))
}
```

## Envelope Encryption

*Stop 3 of 5.*

### Step 1: encrypting one card number

The vault's `pan` column must be unreadable to anyone who gets a copy of the table: a backup on the wrong disk, a replica, a database administrator. That's encryption, and the right tool in Go's standard library is **AES-256-GCM**:

```go noverify title="cardvault/vault/seal.go · lines 9–24"
// seal encrypts plaintext with AES-256-GCM under a data key. The nonce is
// 12 random bytes, new every time. aad is authenticated but not
// encrypted: the ciphertext only opens again with the same aad.
func seal(key, plaintext, aad []byte) (nonce, ciphertext []byte, err error) {
	block, err := aes.NewCipher(key)
	if err != nil {
		return nil, nil, err
	}
	gcm, err := cipher.NewGCM(block)
	if err != nil {
		return nil, nil, err
	}
	nonce = make([]byte, gcm.NonceSize())
	rand.Read(nonce)
	return nonce, gcm.Seal(nil, nonce, plaintext, aad), nil
}
```

Three things go into GCM besides the key and the card number, and each one matters:

- **The nonce**, 12 bytes, must never repeat under the same key. Reusing one lets anyone who has two ciphertexts learn the XOR of the two plaintexts and forge the authentication tag. Random 12-byte nonces are safe only while a key encrypts a limited number of messages: NIST SP 800-38D caps it at 2^32 encryptions per key. So the nonce is fresh from `crypto/rand` every time, stored next to the ciphertext, and keys are replaced long before that cap (Step 2).
- **The tag**: GCM appends 16 bytes that authenticate the ciphertext. A 16-digit number comes out as 32 bytes. Change one bit, use the wrong key, and `Open` returns `cipher: message authentication failed` instead of garbage.
- **Additional authenticated data (AAD)**: bytes that aren't encrypted or stored with the ciphertext, but must be supplied, identical, to open it. The vault passes the row's **token**. Step 4 shows why.

`TestSeal` checks the first two properties plus the third's effect: the same number sealed twice gives different bytes; it opens with its token and not with another; and it doesn't open after one bit is flipped.

### Step 2: where does the key live?

A key in the vault's config file, next to its database password, protects against very little: whoever can read one can read the other. The key has to live somewhere the database's attackers aren't, and ideally somewhere it can't be copied out of at all. That's a **key management service**: a hardware security module, a cloud KMS, or Vault's **transit** engine. The key, here an AES-256 key named `cards`, is created inside Vault and never leaves it. Programs send Vault data to encrypt or decrypt, and Vault sends back the result.

Sending every card number to Vault works, and for a handful of values it's the simplest design. But each call is a network round trip, and Vault becomes part of every read. **Envelope encryption** splits the work in two:

- A **data encryption key (DEK)** encrypts the card numbers, locally, in the vault's memory, in nanoseconds.
- The **key encryption key (KEK)**, inside Vault, encrypts ("wraps") the DEKs. The database stores each DEK only in its wrapped form, `vault:v1:…`. To use a DEK after a restart, the vault asks Vault to unwrap it.

Vault makes a DEK in one call and returns it twice, in the clear and wrapped:

```go noverify title="cardvault/vault/kms.go · lines 38–47"
// DataKey asks Vault for a new random 256-bit data key. It comes back
// twice: in the clear, to use now, and wrapped by the KEK, to store.
func (k *KMS) DataKey(ctx context.Context) (key []byte, wrapped string, err error) {
	d, err := k.write(ctx, "datakey/plaintext", nil)
	if err != nil {
		return nil, "", err
	}
	key, err = base64.StdEncoding.DecodeString(d["plaintext"].(string))
	return key, d["ciphertext"].(string), err
}
```

The vault uses one DEK for up to 1,000 cards, then asks for a new one. That keeps Vault calls rare, keeps every key far below GCM's limit, and limits what one leaked DEK could expose to 1,000 cards:

```go noverify title="cardvault/vault/vault.go · lines 70–84"
// sealingKey returns the data key for the next card, starting a new one
// every MaxUses cards.
func (v *Vault) sealingKey(ctx context.Context) (int64, []byte, error) {
	v.mu.Lock()
	defer v.mu.Unlock()
	if v.cur == 0 || v.uses >= v.MaxUses {
		id, key, err := v.newKey(ctx, "pan")
		if err != nil {
			return 0, nil, err
		}
		v.cur, v.uses, v.keys[id] = id, 0, key
	}
	v.uses++
	return v.cur, v.keys[v.cur], nil
}
```

Over the three runs: tokenizing 10,000 cards took **1.16–1.48 s** with envelope encryption, **11 calls to Vault**, and that time includes a fingerprint lookup and an `INSERT` per card. Reading all 10,000 back, starting with no keys in memory, took 1.41–1.93 s and **10 calls**. Having Vault encrypt each card, with no database work at all, took **9.19–9.58 s and 10,000 calls**: about 0.95 ms a round trip, against about 0.7 µs to seal a card locally. Vault here is on the same machine; across a real network, each round trip is longer.

The trade-off is visible too: an envelope design keeps plain data keys in the vault's memory. Anyone who can read that process's memory (a core dump, a debugger) can read them. That's why the vault is a small, separate service with few people able to touch its hosts, and why each key only covers 1,000 cards.

### Step 4: why the token is the AAD

Without AAD, a ciphertext opens anywhere its key is available. Consider two rows sealed under the same data key, and someone who can write to the table (a mistaken migration, a stolen administrator login) swapping their ciphertexts:

<UnderTheHood title="What GCM actually does">

GCM (Galois/Counter Mode) is two things fused. **Counter mode** turns AES into a stream cipher: AES encrypts the nonce followed by a counter (1, 2, 3…), producing a keystream that is XORed with the plaintext. That's why the nonce must never repeat: the same key and nonce give the same keystream, and XORing two ciphertexts made with it cancels the keystream and leaves the XOR of the two plaintexts. **GHASH** then computes a polynomial hash over the AAD and the ciphertext in the finite field GF(2^128), keyed by a value derived from the AES key, and encrypts it into the 16-byte tag. `Open` recomputes the tag and compares in constant time before it decrypts anything, so a changed byte, a wrong key or different AAD all produce the same single error.

</UnderTheHood>

### Step 5: rotating the KEK

Keys get rotated: on a schedule, when someone who had access leaves, or when one might have been exposed. With envelope encryption, rotating the KEK is cheap. The key-operations job, with its own Vault token and its own database role, tells Vault to add a new version of the key, then passes each wrapped DEK to Vault's **rewrap**, which unwraps it with the old version and wraps it with the new one, inside Vault, never returning the plain DEK:

The vault service can make and unwrap data keys, but can't rotate the KEK, read its settings or export it. The key-operations job can rotate and rewrap, but **can't unwrap a data key**, so the people who manage the key can't read a single card. (Its `rotate` in this run was real: the key moved to version 3.) Neither can export the key: it was created non-exportable, and no policy could change that. This is **separation of duties**: no single identity can both manage the key and use it to read data. PCI DSS's key-management requirements (3.6 and 3.7) ask for access to keys to be restricted to the fewest custodians necessary, and this is how a program meets that.

### Step 1: what an API key doesn't prove

Merchants call Meridian's API to create payouts, refunds and charges on saved cards. The simplest authentication is an API key sent with every request, like a password: `Authorization: Bearer mk_live_…`. It's what most APIs do, over TLS, and it's reasonable for many of them. Its weakness is that the secret itself travels on every request. Anything that ever sees one request (a logging proxy, a debugging tool, a misconfigured load balancer that writes headers to disk) has the key, and can make any request, forever, until someone notices.

A **signed request** never sends the secret. The merchant and Meridian both hold a signing secret; the merchant computes an **HMAC-SHA256** over the request with it and sends the result. Meridian computes the same HMAC and compares. A captured request reveals a signature for that one request and nothing else. Chapter 9 verified the processor's webhooks exactly this way, using stripe-go's code. This time Meridian designs the scheme, which means deciding what the signature must **cover**.

### Step 2: the canonical request

Everything that could change what a request does must be inside the signed text, in one exact, agreed format: the **canonical request**.

```go noverify title="cardvault/sign/sign.go · lines 29–37"
// Canonical is the exact text that is signed: every part of the request
// that could change what it does, one per line.
func Canonical(method, path, query string, ts int64, nonce string, body []byte) []byte {
	h := sha256.Sum256(body)
	return []byte(strings.Join([]string{
		"MERIDIAN-HMAC-SHA256", method, path, query,
		strconv.FormatInt(ts, 10), nonce, hex.EncodeToString(h[:]),
	}, "\n"))
}
```

The method and path (a payout isn't a refund), the query string (`r.URL.Query().Encode()` sorts the parameters, so both sides produce the same text however the client ordered them), a **timestamp** and a **nonce** (Step 4), and the SHA-256 of the body. For Acme's payout request, signed once in a sample run (`snip/sample` in the lab bench), the text that got signed:

```go noverify title="cardvault/sign/sign.go · lines 45–63"
// Sign adds the four signature headers to r. The secret itself is never
// sent: only the key's id and the signature.
func Sign(r *http.Request, keyID string, secret []byte, now time.Time) error {
	var body []byte
	if r.Body != nil {
		var err error
		if body, err = io.ReadAll(r.Body); err != nil {
			return err
		}
		r.Body = io.NopCloser(bytes.NewReader(body))
	}
	ts, nonce := now.Unix(), rand.Text()
	sig := mac(secret, Canonical(r.Method, r.URL.Path, r.URL.Query().Encode(), ts, nonce, body))
	r.Header.Set("Meridian-Key", keyID)
	r.Header.Set("Meridian-Timestamp", strconv.FormatInt(ts, 10))
	r.Header.Set("Meridian-Nonce", nonce)
	r.Header.Set("Meridian-Signature", hex.EncodeToString(sig))
	return nil
}
```

### Step 3: checking it, in the right order

```go noverify title="cardvault/sign/sign.go · lines 79–110"
func (v *Verifier) Verify(r *http.Request, body []byte) (keyID string, err error) {
	keyID = r.Header.Get("Meridian-Key")
	tsText, nonce := r.Header.Get("Meridian-Timestamp"), r.Header.Get("Meridian-Nonce")
	got, err := hex.DecodeString(r.Header.Get("Meridian-Signature"))
	if keyID == "" || nonce == "" || err != nil || len(got) != sha256.Size {
		return keyID, ErrMissing
	}
	secret, ok := v.Secret(keyID)
	if !ok {
		return keyID, ErrUnknown
	}
	ts, err := strconv.ParseInt(tsText, 10, 64)
	if err != nil {
		return keyID, ErrMissing
	}
	if d := v.Now().Sub(time.Unix(ts, 0)); d > v.Window || d < -v.Window {
		return keyID, ErrStale
	}
	want := mac(secret, Canonical(r.Method, r.URL.Path, r.URL.Query().Encode(), ts, nonce, body))
	if !hmac.Equal(got, want) { // constant time: see Step 3
		return keyID, ErrSignature
	}
	// Only a correctly signed request gets to use up a nonce.
	first, err := v.Nonces.Claim(r.Context(), "nonce:"+keyID+":"+nonce, 2*v.Window)
	if err != nil {
		return keyID, err
	}
	if !first {
		return keyID, ErrReplay
	}
	return keyID, nil
}
```

The order is deliberate. The cheap checks come first: missing headers, an unknown key id, a timestamp more than 5 minutes from Meridian's clock in either direction. Then the HMAC, compared with `hmac.Equal` (Step 5 says why not `==`). Only a request that is correctly signed gets to use up a nonce, so nobody can fill Redis with junk nonces or burn a merchant's future nonces with unsigned requests. The nonce store is Redis, shared by every API server, with one atomic command:

```go noverify title="cardvault/sign/redis.go · lines 10–16"
// RedisNonces keeps seen nonces in Redis, so every API server shares them.
type RedisNonces struct{ R *redis.Client }

// Claim is SET key 1 NX EX ttl: it succeeds only if the key wasn't there.
func (n RedisNonces) Claim(ctx context.Context, key string, ttl time.Duration) (bool, error) {
	return n.R.SetNX(ctx, key, 1, ttl).Result()
}
```

`SET key 1 NX EX 600` sets the key only if it doesn't exist, and reports which happened; a nonce is remembered for twice the timestamp window, after which the timestamp check would reject its request anyway. The middleware gives every failure the same answer, `401 unauthorized`, and keeps the reason for Meridian's own log: telling a caller *which* check failed only helps someone probing the scheme.

```go noverify title="cardvault/sign/sign.go · lines 112–130"
// Middleware lets through only requests that verify. Every failure gets
// the same answer; the reason goes to the log, not to the caller.
func (v *Verifier) Middleware(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		body, err := io.ReadAll(http.MaxBytesReader(w, r.Body, 1<<20))
		if err != nil {
			http.Error(w, "request too large", http.StatusRequestEntityTooLarge)
			return
		}
		key, err := v.Verify(r, body)
		if err != nil {
			v.Log.Warn("request refused", "key", key, "path", r.URL.Path, "reason", err)
			http.Error(w, "unauthorized", http.StatusUnauthorized)
			return
		}
		r.Body = io.NopCloser(bytes.NewReader(body))
		next.ServeHTTP(w, r)
	})
}
```

### Step 5: comparing in constant time

Why `hmac.Equal` and not `bytes.Equal` or `==`? An ordinary comparison stops at the first byte that differs. So a guess that's wrong in its first byte is rejected slightly faster than one that's wrong only in its last. If an attacker could measure that difference precisely enough, they could find a valid signature one byte at a time, trying 256 values for each byte instead of 2^256 for the whole thing. That's a **timing side channel**. `hmac.Equal` (which is `crypto/subtle.ConstantTimeCompare`) looks at every byte whatever it finds, so its time doesn't depend on where the guess went wrong.

How big is the difference? `sign/equal_test.go` benchmarks four ways of comparing a 32-byte HMAC, with a guess wrong in its first byte and with one wrong in its last. Five runs each, median first:

```text
string==/wrong-first       4.78 ns   (5 runs: 5.33, 3.85, 6.21, 4.78, 4.75)
string==/wrong-last        7.36 ns   (5 runs: 7.36, 8.00, 9.20, 6.55, 5.33)
loop/wrong-first           2.91 ns   (5 runs: 2.97, 3.58, 2.45, 2.50, 2.91)
loop/wrong-last           18.78 ns   (5 runs: 20.08, 19.19, 17.99, 18.78, 16.78)
bytes.Equal/wrong-first    2.93 ns   (5 runs: 2.62, 2.66, 2.93, 3.08, 3.17)
bytes.Equal/wrong-last     3.90 ns   (5 runs: 4.88, 4.51, 3.90, 3.53, 3.39)
hmac.Equal/wrong-first    12.78 ns   (5 runs: 12.78, 12.61, 12.63, 16.11, 13.30)
hmac.Equal/wrong-last     13.24 ns   (5 runs: 12.88, 13.26, 13.24, 13.20, 13.27)
```

The **hand-written loop** leaks plainly: **2.91 ns** when the first byte is wrong, **18.78 ns** when only the last is, and every value in between gives something in between. Go's `==` on strings and `bytes.Equal` compare in wide chunks with assembly, so on 32 bytes the difference shrinks to a nanosecond or two, with the runs overlapping. **`hmac.Equal` took about 13 ns either way.** It's slower, because it touches every byte, and 13 ns on a request that already costs milliseconds doesn't matter.

Whether a nanosecond-sized difference can be measured across a network depends on the network's noise and on how many requests an attacker can make; researchers have measured surprisingly small ones with enough samples. The point of `hmac.Equal` is that you don't have to find out. The same rule applies anywhere a secret is compared: API keys, password hashes (Stop 5 uses `subtle.ConstantTimeCompare`), session tokens.

## The Front Door

*Stop 5 of 5.*

### Step 1: passwords, stored so they're slow to guess

Merchants' staff sign in to Meridian's dashboard to see payouts and refund charges. Meridian stores something derived from each password, never the password, and the question is what happens if that table is ever copied. Anyone holding it can try guesses offline, as fast as their hardware allows, against every account at once. The defence is a hash that is **deliberately slow and memory-hungry**, so each guess costs real time.

`cmd/hashcost` measured one hash on this laptop, the median of seven runs each:

```text
SHA-256 (not for passwords)        74ns per hash,  13513514 hashes a second
bcrypt cost 10                   69.6ms per hash,        14 hashes a second
bcrypt cost 12                  275.4ms per hash,         4 hashes a second
argon2id 19 MiB, t=2, p=1        31.7ms per hash,        32 hashes a second
argon2id 64 MiB, t=3, p=4 *      80.9ms per hash,        12 hashes a second
* p=4 runs on four cores at once
```

**SHA-256 took 74 ns**: about 13.5 million guesses a second on one core, which is why a fast hash is the wrong tool for passwords (it's the right tool for Stop 4's HMAC, where the input is a long random secret nobody can guess). **argon2id** with OWASP's minimum settings, 19 MiB of memory and 2 passes, took **31.7 ms**, some 400,000 times longer per guess, and each guess needs its own 19 MiB, which is what makes it expensive to run on graphics cards. bcrypt at cost 10 took 69.6 ms and at cost 12, 275.4 ms. RFC 9106's second recommended setting for argon2id (64 MiB, 3 passes, 4 lanes) took 80.9 ms using four cores at once.

Meridian uses argon2id from `golang.org/x/crypto/argon2`, stored in the standard text format that records its parameters and salt, so the settings can be raised later without breaking old hashes:

```go noverify title="cardvault/login/password.go · lines 16–36"
// OWASP's minimum for argon2id: 19 MiB of memory, 2 passes, 1 thread.
const (
	memKiB  = 19 * 1024
	passes  = 2
	threads = 1
)

var ErrShort = errors.New("password must be at least 12 characters") // PCI DSS 8.3.6

// Hash returns the stored form of a password: the parameters, a random
// salt and the argon2id output, in the same text format other tools use.
func Hash(password string) (string, error) {
	if len(password) < 12 {
		return "", ErrShort
	}
	salt := make([]byte, 16)
	rand.Read(salt)
	sum := argon2.IDKey([]byte(password), salt, passes, memKiB, threads, 32)
	b64 := base64.RawStdEncoding.EncodeToString
	return fmt.Sprintf("$argon2id$v=%d$m=%d,t=%d,p=%d$%s$%s", argon2.Version, memKiB, passes, threads, b64(salt), b64(sum)), nil
}
```

The 16-byte random **salt** means two people with the same password get different hashes, so one guess can only be tested against one account at a time. The 12-character minimum is PCI DSS 8.3.6 for accounts that can reach card data. `Check` reads the parameters back from the stored string, recomputes, and compares with `subtle.ConstantTimeCompare`.

### Step 2: ten wrong passwords, then a lock

A slow hash protects a stolen table. Guessing through the sign-in form is a different problem, and PCI DSS 8.3.4 is specific about it: lock the account after **no more than 10** failed attempts, for **at least 30 minutes** or until the person's identity is confirmed. Meridian keeps the count in Redis, so every dashboard server sees the same one:

```go noverify title="cardvault/login/lockout.go · lines 34–60"
// Login checks a password. Once an account has MaxFails failures in a
// row, it is refused without even looking at the password until the
// counter expires, LockFor after the last failure.
func (s *Service) Login(ctx context.Context, email, password string) error {
	key := "fails:" + email
	n, err := s.R.Get(ctx, key).Int()
	if err != nil && !errors.Is(err, redis.Nil) {
		return err
	}
	if n >= MaxFails {
		return ErrLocked
	}
	stored, known := s.Users[email]
	if !known {
		stored = s.dummy // same work for an unknown email: no timing difference
	}
	if Check(stored, password) && known {
		return s.R.Del(ctx, key).Err()
	}
	pipe := s.R.TxPipeline()
	pipe.Incr(ctx, key)
	pipe.Expire(ctx, key, LockFor)
	if _, err := pipe.Exec(ctx); err != nil {
		return err
	}
	return ErrWrong
}
```

Three details. The lock is checked **before** the password, so a locked account is refused without spending 30 ms of CPU on an argon2id hash. Every failure resets the counter's expiry, so the lock lasts 30 minutes from the last failure. And an **unknown email** is treated exactly like a known one: the same hash work against a dummy, the same message, the same counting, so the sign-in form can't be used to find out which emails have accounts. `cmd/login` makes twelve wrong attempts at Ada's account, then tries her real password:

### Step 3: TLS that only talks to who it should

Every connection in this chapter that carries a card number or a signed request must be encrypted in transit: PCI DSS 4.2.1 requires strong cryptography whenever card numbers cross open, public networks, and inside Meridian the same rule is simply good practice. For the card vault's own API, Meridian goes further: **mutual TLS**, where the client proves who it is with a certificate too, so only services holding a certificate from Meridian's internal certificate authority can even connect.

In Go that's a few fields of `tls.Config` on the server:

```go noverify title="cardvault/cmd/tls/main.go · lines 55–60"
		TLSConfig: &tls.Config{
			MinVersion:   tls.VersionTLS12,
			Certificates: []tls.Certificate{serverCert},
			ClientAuth:   tls.RequireAndVerifyClientCert, // mutual TLS
			ClientCAs:    pool,
		},
```

`MinVersion: tls.VersionTLS12` refuses TLS 1.0 and 1.1, which have known weaknesses. (It's already the default for Go servers since Go 1.22; writing it down documents the requirement, and keeps it if the default ever changes.) `RequireAndVerifyClientCert` with `ClientCAs` refuses any client without a certificate signed by Meridian's CA. `cmd/tls` makes a CA, a server certificate and a certificate for the payments service, all in memory with `crypto/x509`, and connects four ways:

<Exercise n={2} title="A data key leaked" level="medium">

Get a new data key from Vault. </Solution>

</Solution>

</Exercise>

<Exercise n={4} title="Rotating a merchant's signing secret" level="medium">

Acme wants a new signing secret, but its servers can't all switch at the same instant. Change the verifier so a merchant can have two active secrets for a while, and describe the order of steps.

<Solution>

Make `Secret` return a list. `Verify` computes the HMAC with each and accepts if any matches (with `hmac.Equal` each time, never stopping early on which one matched). Steps: Meridian adds the new secret alongside the old one; Acme switches its servers to sign with the new one, one by one; Meridian sees no more requests signed with the old one (log which secret matched) and removes it. Stripe's webhook signatures do the same thing, sending several `v1` signatures during a rotation, which chapter 9 relied on.

</Solution>

</Exercise>

<Exercise n={5} title="Eleven guesses at once" level="hard">

`Login` reads the counter, checks the password, then increments. Twenty wrong guesses sent at the same moment can all read 9 and all get checked. Measure it, then fix it so no more than 10 passwords are ever checked before the lock.

<Solution>

Measure with 20 goroutines against a fresh account and count how many got `ErrWrong` rather than `ErrLocked`: more than 10 means the race is real. Fix it by counting before checking: `n := INCR fails:email` (and `EXPIRE` it, in the same `MULTI`), refuse if `n > 10`, then check the password, and on success `DEL` the counter. Now each attempt reserves its place before any hashing, and exactly 10 hashes run however many arrive at once. The price is that a successful attempt was counted too, which the `DEL` undoes.

</Solution>

// ── 1. The card number ──

// PAN is a card number. Nothing may ever print more than its last four.
type PAN struct {
	digits string
}

// ParsePAN accepts 13 to 19 ASCII digits with a correct Luhn check digit,
// and nothing else.
func ParsePAN(s string) (PAN, error) {
	s = strings.NewReplacer(" ", "", "-", "").Replace(s) // be forgiving
	if len(s) < 13 || len(s) > 19 {
		return PAN{}, ErrInvalid
	}
	for i := 0; i < len(s); i++ {
		if s[i] < '0' || s[i] > '9' {
			return PAN{}, ErrInvalid
		}
	}
	return PAN{s}, nil
}

func (p PAN) Reveal() string { return p.digits }
func (p PAN) Masked() string { return "•••• " + p.digits[len(p.digits)-4:] }

func (p PAN) String() string { return p.Masked() }

// ── 2. Encryption at rest ──

// seal encrypts a card number with AES-256-GCM under a data key, bound to
// the token of the row it's stored in.
func seal(key []byte, p PAN, token string) (nonce, ciphertext []byte) {
	block, _ := aes.NewCipher(key)
	gcm, _ := cipher.NewGCM(block)
	nonce = make([]byte, gcm.NonceSize())
	return nonce, gcm.Seal(nil, nonce, []byte(p.Reveal()), nil)
}

func open(key, nonce, ciphertext []byte, token string) (PAN, error) {
	block, _ := aes.NewCipher(key)
	gcm, _ := cipher.NewGCM(block)
	b, err := gcm.Open(nil, nonce, ciphertext, nil)
	if err != nil {
		return PAN{}, err
	}
	return ParsePAN(string(b))
}

// fingerprint finds the same card again without storing its number.
func fingerprint(key []byte, p PAN) []byte {
	h := sha256.Sum256([]byte(p.Reveal()))
	return h[:]
}

// ── 3. Signed requests ──

type Request struct {
	Method, Path, Query string
	Timestamp           int64
	Nonce               string
	Body                []byte
	Signature           []byte
}

// canonical is the text that is signed.
func canonical(r Request) []byte {
	return []byte(strings.Join([]string{r.Method, r.Path, strconv.FormatInt(r.Timestamp, 10), string(r.Body)}, "\\n"))
}

func Sign(secret []byte, r *Request) {
	m := hmac.New(sha256.New, secret)
	m.Write(canonical(*r))
	r.Signature = m.Sum(nil)
}

// Verify accepts a request only if it is correctly signed, was signed
// within window of now, and its nonce hasn't been used before.
type Verifier struct {
	secret []byte
	now    func() time.Time
	window time.Duration
}

func (v *Verifier) Verify(r Request) error {
	m := hmac.New(sha256.New, v.secret)
	m.Write(canonical(r))
	if !bytes.Equal(r.Signature, m.Sum(nil)) {
		return ErrSignature
	}
	return nil
}

// ── 4. Sign-in ──

const (
	MaxFails = 10
	LockFor  = 30 * time.Minute
)

type Accounts struct {
	check func(email, password string) bool // the (slow) password check
	now   func() time.Time

	fails map[string]int
	last  map[string]time.Time // time of the latest failure
}

// Login locks an account for LockFor after MaxFails failures in a row;
// while it's locked, even the right password is refused.
func (a *Accounts) Login(email, password string) error {
	if a.check(email, password) {
		delete(a.fails, email)
		return nil
	}
	a.fails[email]++
	a.last[email] = a.now()
	if a.fails[email] > MaxFails {
		return ErrLocked
	}
	return ErrWrong
}

<Recap>

- **Card data**: PCI DSS keeps the PAN unreadable where stored and masked where shown, and forbids keeping the CVC after authorization. 1,000 checkouts wrote 750 card numbers and 750 CVCs into logs and a retry queue until the fields became types that mask themselves. A `String` method isn't enough: `%d` and an unexported field still printed the digits. `Format`, plus the digits behind a pointer, closed both. Validate at the edge, with the Luhn check, and scan logs in tests.
- **Tokenize**: one vault holds the numbers; everyone else holds random tokens (`crypto/rand.Text`, 128 bits). A plain SHA-256 fingerprint gave back 100 of 100 card numbers from the first six and last four digits; an HMAC-SHA256 with a vault-held key, none (PCI DSS 3.5.1.1). Database roles kept payments out of card numbers and the vault out of charges and its own access log. Every request for a number, granted or refused, is recorded, the granted ones in the same transaction.
- **Envelope encryption**: AES-256-GCM with a random nonce and the token as AAD, under data keys from Vault, each used for 1,000 cards. 10,000 cards: 1.16–1.48 s and 11 Vault calls, against 9.19–9.58 s and 10,000 calls with Vault encrypting each card. A ciphertext moved to another row refused to open. Rotating the KEK rewrapped 11 keys in 39 ms and changed no card rows; Vault policies let the vault use keys and the key-ops job manage them, never both.
- **Signed requests**: HMAC-SHA256 over method, path, query, timestamp, nonce and body hash, never sending the secret. The full scheme refused a replay, a changed path, query or amount, a stale timestamp and a wrong key id; a body-only signature let five of those six through. Compare with `hmac.Equal`: a byte loop took 2.9 ns or 18.8 ns depending on the wrong byte, `hmac.Equal` 13 ns either way.
- **The front door**: argon2id took 31.7 ms a guess where SHA-256 took 74 ns. Ten failures locked the account for 30 minutes, checked before the password, so even the right one was refused, in under a millisecond. Mutual TLS, TLS 1.2 minimum, refused TLS 1.1 and clients without Meridian's certificate, and negotiated TLS 1.3 with the post-quantum X25519MLKEM768.
