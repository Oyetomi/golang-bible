## Secrets Management for Finance

Let's set the scene: Meridian's payments service needs a private key to sign outbound requests to the card network, an AES master key to decrypt stored bank account numbers, and database credentials. These are not configuration. They are **secrets**, and they carry wildly different risk profiles.

The **Configuration & Secrets Management** chapter (Part 2) covered the baseline: never commit secrets, load them from a secrets manager, keep them out of logs. That baseline is table stakes here. What finance adds on top is a key hierarchy and operational controls that make a compromised secret survivable.

**On the job:** You discover that a rotation script accidentally wrote a data key to a CloudWatch log stream. With envelope encryption, rotating the KEK re-wraps every DEK without touching the ciphertexts — and the exposed DEK protected exactly one record, not the whole database.

### The finance-specific threat model

<ConceptGrid cols={3}>
  <ConceptCard label="Key material vs. config">A database URL is a secret. A 256-bit AES master key is **cryptographic key material** — it must never touch disk unencrypted, must live in a hardware-backed store, and must have a rotation schedule measured in days, not years.</ConceptCard>
  <ConceptCard label="HSM / KMS">A **Hardware Security Module** (HSM) or cloud **Key Management Service** (KMS — AWS KMS, GCP Cloud KMS, Azure Key Vault) stores master keys in tamper-resistant hardware. Your service never sees the raw key bytes for master keys; it calls the KMS API to encrypt or decrypt.</ConceptCard>
  <ConceptCard label="Separation of duties">The service that encrypts data should not be the same identity that can rotate the master key. The engineer who deploys the service should not be the one who approves key access. Separate IAM roles, separate approvals, audited in the append-only log you built in the **Auditability & Compliance** chapter.</ConceptCard>
  <Gotcha>Never put a KMS master key in an environment variable or a config file. You call the KMS — the KMS holds the key. If your service can print its master key bytes to stdout, something is already wrong.</Gotcha>
</ConceptGrid>

### Key rotation without downtime

A key you can't rotate is a liability. The pattern:

1. **Generate** a new data key (or new master key version) in the KMS.
2. **Re-encrypt** the data keys for existing records using the new master key version (the KMS API does this — your service never touches plaintext master key bytes).
3. **Update** the key version reference in every encrypted record.
4. **Revoke** the old key version after a quiet period.

Go's `crypto/aes` and `crypto/cipher` are the implementation layer. The KMS is the root of trust. The next sections cover both in depth.

## `crypto/rand` vs `math/rand`

<Define term="CSPRNG / crypto/rand" since="Application Security Baseline (Part 2)">
A **Cryptographically Secure Pseudo-Random Number Generator** (CSPRNG) produces output that is computationally indistinguishable from true randomness — an attacker who sees past output cannot predict future output. Go's `crypto/rand` package wraps the OS CSPRNG (`/dev/urandom` on Linux, `BCryptGenRandom` on Windows). It is the **only** correct source for keys, nonces, tokens, and any value whose secrecy matters. `math/rand` (and `math/rand/v2`) is a deterministic PRNG seeded by a fixed algorithm — fast, convenient for simulations and tests, and **completely wrong** for security-sensitive values.
</Define>

This is the single most important rule in Go cryptography. If you use `math/rand` to generate a nonce, a session token, or an API key, an attacker who knows (or guesses) the seed can reproduce your entire output stream. The seed for a `math/rand.New(math/rand.NewSource(time.Now().UnixNano()))` call is a 64-bit integer. A motivated attacker can exhaust the entire space in minutes on commodity hardware.

**On the job:** A security audit at a fintech finds that their token-generation library used `math/rand` seeded with `time.Now().UnixNano()`. The library had been in production for two years, passed every code review, and was the source of all idempotency keys, nonces, and HMAC secrets. Predictable keys meant every HMAC signature for the past two years was forgeable given the server's approximate start time.

The rule is absolute: `crypto/rand` for anything security-sensitive; `math/rand` only for non-secret randomness (shuffling a playlist, test fixtures, load simulation).

```go
package main

import (
	"crypto/rand"
	"encoding/hex"
	"fmt"
	"io"
)

// generateToken returns a 32-byte cryptographically random token,
// hex-encoded to 64 characters. Safe for session IDs, API keys, nonces.
func generateToken() (string, error) {
	b := make([]byte, 32)
	if _, err := io.ReadFull(rand.Reader, b); err != nil {
		return "", fmt.Errorf("crypto/rand: %w", err)
	}
	return hex.EncodeToString(b), nil
}

func main() {
	tok, err := generateToken()
	if err != nil {
		fmt.Println("error:", err)
		return
	}
	fmt.Println("token:", tok) // 64 hex chars, unpredictable
}
```

<UnderTheHood title="Always-secure randomness in Go 1.26 — and what changed">

Go 1.25 and 1.26 tightened the relationship between `crypto/*` generators and their randomness source.

**Go 1.20:** `math/rand` global functions are auto-seeded with a random value by default (no longer the fixed seed=1 from older Go). This closed the most egregious `math/rand` footgun for new programs, but `math/rand` is still deterministic given a known seed — it is **not** a CSPRNG and must not be used for security values.

**Go 1.26 (always-secure crypto):** Several functions in `crypto/ecdsa`, `crypto/rsa`, and `crypto/dsa` that previously accepted a `rand io.Reader` parameter now **ignore the supplied reader** and always use `crypto/rand` internally. The signatures are unchanged for backward compatibility, but passing a custom reader no longer has any effect — the implementation silently uses the OS CSPRNG. This means tests that previously passed a seeded `math/rand` reader to `ecdsa.Sign` for determinism will still compile but no longer produce deterministic output. If you need deterministic ECDSA for tests, use RFC 6979 deterministic signing explicitly instead.

**`crypto/hpke` (new in Go 1.26):** The standard library now includes `crypto/hpke`, which implements Hybrid Public Key Encryption (RFC 9180). HPKE combines an asymmetric KEM (key encapsulation mechanism) with a symmetric AEAD for forward-secrecy-friendly encryption without a pre-shared secret. It is more sophisticated than the AES-GCM + RSA pattern and is the recommended primitive for new protocols that need public-key encryption.

**`runtime/secret` (experimental in Go 1.26):** A new experimental package, enabled with `GOEXPERIMENT=runtimesecret` at build time (amd64/arm64 on Linux), that **securely erases the temporaries** used by code handling secret material — registers, stack, and new heap allocations — to make forward secrecy easier to guarantee. It is not a substitute for good key lifecycle discipline, but it shrinks the window during which key material lingers in memory after use. Treat it as defense-in-depth, not a primary control.

`crypto/aes` + `crypto/cipher` for AES-GCM remains canonical and unchanged. These notes are additive, not replacements.

</UnderTheHood>

## Encryption at Rest and in Transit

### In transit: TLS everywhere

TLS is the non-negotiable floor. The **Application Security Baseline** chapter (Part 2) covers TLS enforcement and HSTS. For fintech, two additional rules:

- **Mutual TLS (mTLS)** between internal services — not just server auth, but client auth. Every service presents a certificate; the server rejects any caller that can't prove who it is.
- **Certificate pinning or SPIFFE/SVID** for service-to-service calls in high-assurance environments. A stolen credential on one service should not grant it access to the payments vault.

For the rest of this section we focus on **at rest**: data that lives in your database.

### Symmetric encryption with AES-GCM

<Define term="AES-GCM / AEAD">
**AES-GCM** (Advanced Encryption Standard in Galois/Counter Mode) is an **AEAD** cipher — Authenticated Encryption with Associated Data. It provides two guarantees in one operation: **confidentiality** (the ciphertext reveals nothing about the plaintext) and **integrity** (any modification to the ciphertext is detected before you get plaintext back). In Go, AES-GCM is exposed via the `crypto/aes` and `crypto/cipher` packages through the `cipher.AEAD` interface.
</Define>

<Define term="Nonce">
A **nonce** (number-used-once) is a value that must be unique for every encryption operation under the same key. For AES-GCM, the standard nonce is 12 bytes. If you reuse a nonce with the same key, an attacker who sees both ciphertexts can XOR them to cancel the keystream and recover the XOR of the two plaintexts — confidentiality is completely broken. Generate nonces with `crypto/rand`; never use a counter shared across replicas.
</Define>

**On the job:** A nonce collision in AES-GCM is not hypothetical. In 2016, Böck, Zauner et al. ("Nonce-Disrespecting Adversaries") found deployed **TLS 1.2** servers that reused AES-GCM nonces, allowing a practical plaintext-recovery and forgery attack. In practice, a shared counter nonce under a key used across multiple replicas can collide under load. `crypto/rand` nonces make collision probability negligible (birthday bound at 96 bits is effectively zero for any realistic record count).

AES-GCM gives you two guarantees in one operation: confidentiality and integrity. A tampered ciphertext returns an error — not garbled data, a hard failure.

Here is a complete, runnable implementation of encrypt/decrypt with `crypto/aes` and `crypto/cipher`:

```go
package main

import (
	"crypto/aes"
	"crypto/cipher"
	"crypto/rand"
	"encoding/hex"
	"errors"
	"fmt"
	"io"
)

// encryptAESGCM encrypts plaintext with the given 32-byte AES-256 key.
// Returns: nonce (12 bytes) + ciphertext + GCM tag, all concatenated.
// The nonce is prepended so the decryptor can split it out.
func encryptAESGCM(key, plaintext []byte) ([]byte, error) {
	block, err := aes.NewCipher(key)
	if err != nil {
		return nil, fmt.Errorf("new cipher: %w", err)
	}
	gcm, err := cipher.NewGCM(block)
	if err != nil {
		return nil, fmt.Errorf("new gcm: %w", err)
	}
	// A nonce MUST be unique for every encryption under the same key.
	// crypto/rand gives us a cryptographically random 12-byte nonce.
	nonce := make([]byte, gcm.NonceSize()) // 12 bytes for standard GCM
	if _, err := io.ReadFull(rand.Reader, nonce); err != nil {
		return nil, fmt.Errorf("rand nonce: %w", err)
	}
	// Seal appends the encrypted ciphertext + tag to nonce.
	sealed := gcm.Seal(nonce, nonce, plaintext, nil)
	return sealed, nil
}

// decryptAESGCM decrypts a value produced by encryptAESGCM.
// Returns an error (not garbled plaintext) if the ciphertext was tampered with.
func decryptAESGCM(key, sealed []byte) ([]byte, error) {
	block, err := aes.NewCipher(key)
	if err != nil {
		return nil, fmt.Errorf("new cipher: %w", err)
	}
	gcm, err := cipher.NewGCM(block)
	if err != nil {
		return nil, fmt.Errorf("new gcm: %w", err)
	}
	ns := gcm.NonceSize()
	if len(sealed) < ns {
		return nil, errors.New("ciphertext too short")
	}
	nonce, ciphertext := sealed[:ns], sealed[ns:]
	plaintext, err := gcm.Open(nil, nonce, ciphertext, nil)
	if err != nil {
		// err here means the authentication tag did NOT match —
		// either the key is wrong, or the data was tampered with.
		return nil, fmt.Errorf("authentication failed: %w", err)
	}
	return plaintext, nil
}

func main() {
	// In production this key comes from the KMS (as the plaintext data key).
	// Never hardcode a key — this is demo-only.
	key, _ := hex.DecodeString(
		"0102030405060708090a0b0c0d0e0f101112131415161718191a1b1c1d1e1f20",
	)

	accountNumber := "GB29NWBK60161331926819" // a UK IBAN

	sealed, err := encryptAESGCM(key, []byte(accountNumber))
	if err != nil {
		fmt.Println("encrypt error:", err)
		return
	}
	fmt.Printf("encrypted (%d bytes): %x\n", len(sealed), sealed)

	plaintext, err := decryptAESGCM(key, sealed)
	if err != nil {
		fmt.Println("decrypt error:", err)
		return
	}
	fmt.Println("decrypted:", string(plaintext))

	// Tamper with the ciphertext and see that decryption fails cleanly.
	tampered := make([]byte, len(sealed))
	copy(tampered, sealed)
	tampered[len(tampered)-1] ^= 0xFF // flip a bit in the auth tag

	_, err = decryptAESGCM(key, tampered)
	fmt.Println("tampered decrypt:", err) // authentication failed: cipher: message authentication failed
}
```

<UnderTheHood title="Why AES-GCM gives both confidentiality and integrity — and why nonce reuse is catastrophic (Go 1.26)">

**AES-GCM** is an **AEAD** scheme. Here is what happens under the hood (as of Go 1.26, using the standard `crypto/aes` and `crypto/cipher` packages — this is a conceptual model; the assembly path elides intermediate steps):

1. **Counter mode (CTR)** provides the confidentiality stream. AES-GCM internally runs AES in CTR mode — it never encrypts data directly with the block cipher. Instead, it generates a keystream by encrypting successive counter values (`nonce || counter`), then XORs that stream with your plaintext. Because XOR is symmetric, decryption is the same operation.

2. **GHASH** provides the authentication tag. In parallel with CTR, GCM computes a polynomial hash (GHASH) over the ciphertext (and any additional data you pass). This hash is itself encrypted with AES under a derived subkey and appended as the 16-byte **authentication tag**. `gcm.Open` recomputes the tag over the received ciphertext; if it doesn't match the appended tag, it returns an error *before yielding any plaintext* — a constant-time comparison so timing attacks learn nothing.

3. **The nonce must never repeat.** If you encrypt two different plaintexts with the **same nonce and the same key**, an attacker who sees both ciphertexts can XOR them together and cancel out the keystream — recovering the XOR of the two plaintexts. For a 12-byte random nonce (96 bits), the birthday-bound collision probability is negligible for any realistic record count. But a counter-based nonce under a shared key across replicas *can* collide. Use `crypto/rand` for nonces. Never reuse a key+nonce pair.

4. **Go's implementation uses hardware AES-NI on amd64 and arm64** (Go 1.21+). The `crypto/aes` package probes CPU features at init time; if AES-NI is available, it dispatches to the assembly implementation, making AES-GCM competitive with memory bandwidth rather than CPU-bound. The stdlib pure-Go path is the fallback only.

</UnderTheHood>

## Envelope Encryption with a KMS

### The problem with a single encryption key

Suppose Meridian encrypts a bank account number with a single key and stores the ciphertext. The database is breached — the attacker has the ciphertexts. If they also exfiltrate the application key (from an environment variable, a misconfigured secrets manager, or a side-channel), **every record is decrypted in one operation**. One key, total loss.

The answer is **envelope encryption**.

<Define term="Envelope encryption / DEK / KEK">
**Envelope encryption** is a two-layer key hierarchy. A **Data Encryption Key (DEK)** is a fresh random AES key generated per record (or per small batch) that encrypts the actual sensitive value. A **Key-Encryption Key (KEK)** — the master key, held by the KMS — encrypts the DEK. The encrypted DEK (EncDEK) is stored alongside the ciphertext in the database. To decrypt, you ask the KMS to unwrap the EncDEK, use the resulting plaintext DEK to decrypt the ciphertext, and discard the DEK immediately. An attacker who steals only the database gets ciphertexts and encrypted DEKs — useless without KMS access.
</Define>

<Define term="KMS">
A **Key Management Service** (KMS) is a managed system — hardware-backed in production (AWS KMS, GCP Cloud KMS, Azure Key Vault, HashiCorp Vault) — that stores master keys (KEKs) in tamper-resistant hardware and exposes only an API: `GenerateDataKey`, `Encrypt`, `Decrypt`. Your application never receives the raw KEK bytes; it calls the API. Every call is audited.
</Define>

**On the job:** With envelope encryption, a database breach exposes only encrypted DEKs. A KEK compromise requires KMS access (separate IAM, audited, hardware-backed). The blast radius of losing one is contained — and either can be rotated without the other.

## Field-Level PII Encryption

Envelope encryption scales to individual database columns — a pattern called **field-level encryption**. Sensitive columns (account numbers, national IDs, card numbers) each carry their own EncDEK beside the ciphertext. Everything else in the system uses the opaque row ID; only the service that must display or act on the raw value ever calls the KMS.

**On the job:** In Meridian's architecture, only the payments processor service and the KYC service can call the KMS `Decrypt` API. The ledger service, the notifications service, and the fraud service work with opaque `account_ref` tokens. A compromised notifications service cannot decrypt account numbers — not because of application-layer access control alone, but because it lacks the IAM role to call KMS `Decrypt`.

Here is a `FieldEncryptor` that wraps a `KMSClient` interface:

```go
package main

import (
	"context"
	"crypto/aes"
	"crypto/cipher"
	"crypto/rand"
	"encoding/hex"
	"errors"
	"fmt"
	"io"
)

// KMSClient abstracts AWS KMS / GCP Cloud KMS / Vault — same interface,
// different implementations injected at wire time.
type KMSClient interface {
	GenerateDataKey(ctx context.Context) (plaintext, encrypted []byte, err error)
	Decrypt(ctx context.Context, encryptedKey []byte) ([]byte, error)
}

// EncryptedField is what gets stored in the database column.
// All three fields are required to decrypt.
type EncryptedField struct {
	EncryptedDataKey []byte // DEK wrapped by KMS KEK
	Nonce            []byte // AES-GCM nonce (12 bytes)
	Ciphertext       []byte // AES-GCM ciphertext + tag
}

type FieldEncryptor struct{ kms KMSClient }

func NewFieldEncryptor(kms KMSClient) *FieldEncryptor { return &FieldEncryptor{kms: kms} }

func (fe *FieldEncryptor) Encrypt(ctx context.Context, plaintext []byte) (EncryptedField, error) {
	dk, encDK, err := fe.kms.GenerateDataKey(ctx)
	if err != nil {
		return EncryptedField{}, fmt.Errorf("generate data key: %w", err)
	}
	block, err := aes.NewCipher(dk)
	if err != nil {
		return EncryptedField{}, err
	}
	gcm, err := cipher.NewGCM(block)
	if err != nil {
		return EncryptedField{}, err
	}
	nonce := make([]byte, gcm.NonceSize())
	if _, err = io.ReadFull(rand.Reader, nonce); err != nil {
		return EncryptedField{}, err
	}
	ciphertext := gcm.Seal(nil, nonce, plaintext, nil)
	return EncryptedField{EncryptedDataKey: encDK, Nonce: nonce, Ciphertext: ciphertext}, nil
}

func (fe *FieldEncryptor) Decrypt(ctx context.Context, f EncryptedField) ([]byte, error) {
	dk, err := fe.kms.Decrypt(ctx, f.EncryptedDataKey)
	if err != nil {
		return nil, fmt.Errorf("decrypt data key: %w", err)
	}
	block, err := aes.NewCipher(dk)
	if err != nil {
		return nil, err
	}
	gcm, err := cipher.NewGCM(block)
	if err != nil {
		return nil, err
	}
	if len(f.Nonce) != gcm.NonceSize() {
		return nil, errors.New("bad nonce size")
	}
	return gcm.Open(nil, f.Nonce, f.Ciphertext, nil)
}

// mockKMS uses XOR wrapping for tests — never in production.
type mockKMS struct{ masterKey []byte }

func (m *mockKMS) GenerateDataKey(_ context.Context) (plaintext, encrypted []byte, err error) {
	dk := make([]byte, 32)
	if _, err = rand.Read(dk); err != nil {
		return nil, nil, err
	}
	enc := make([]byte, 32)
	for i := range dk {
		enc[i] = dk[i] ^ m.masterKey[i]
	}
	return dk, enc, nil
}

func (m *mockKMS) Decrypt(_ context.Context, encryptedKey []byte) ([]byte, error) {
	dk := make([]byte, 32)
	for i := range encryptedKey {
		dk[i] = encryptedKey[i] ^ m.masterKey[i]
	}
	return dk, nil
}

func main() {
	masterKey, _ := hex.DecodeString(
		"0102030405060708090a0b0c0d0e0f101112131415161718191a1b1c1d1e1f20",
	)
	enc := NewFieldEncryptor(&mockKMS{masterKey: masterKey})
	ctx := context.Background()

	iban := []byte("GB29NWBK60161331926819")
	field, err := enc.Encrypt(ctx, iban)
	if err != nil {
		fmt.Println("encrypt:", err)
		return
	}

	recovered, err := enc.Decrypt(ctx, field)
	if err != nil {
		fmt.Println("decrypt:", err)
		return
	}
	fmt.Println("recovered:", string(recovered)) // GB29NWBK60161331926819
}
```

<Define term="Constant-time comparison / timing attack">
A **timing attack** exploits the fact that a naive string-equality comparison (`==`, `bytes.Equal`) returns early as soon as it finds a mismatching byte — so comparing an HMAC signature against a series of guesses leaks how many leading bytes are correct via response-time differences. Over many requests, an attacker can recover the expected signature one byte at a time. A **constant-time comparison** (`subtle.ConstantTimeCompare`, `hmac.Equal`) always examines every byte regardless of where the first mismatch occurs, eliminating the timing signal.
</Define>

**On the job:** This is not theoretical. In 2009, a timing attack was used against the HMAC-SHA1 verification in Google's Keyczar library. Requests with a correct first byte took measurably longer to reject than random guesses, allowing reconstruction of the full signature across ~2^16 requests — well within the rate-limit budget for any payment API.

The fix is one word. In any HMAC or secret comparison, replace `bytes.Equal` with `hmac.Equal` (or `subtle.ConstantTimeCompare` for raw byte slices). Both are in the standard library.

```go
package main

import (
	"crypto/hmac"
	"crypto/sha256"
	"crypto/subtle"
	"encoding/hex"
	"fmt"
)

func safeCompareHMAC(secret, message []byte, receivedSig string) bool {
	mac := hmac.New(sha256.New, secret)
	mac.Write(message)
	expected := mac.Sum(nil)

	received, err := hex.DecodeString(receivedSig)
	if err != nil {
		return false
	}
	// hmac.Equal is a convenience wrapper around subtle.ConstantTimeCompare.
	// Both examine every byte regardless of where the first mismatch occurs.
	return hmac.Equal(expected, received)
}

func safeCompareToken(expected, received string) bool {
	// subtle.ConstantTimeCompare works on raw byte slices.
	// It returns 1 (equal) or 0 (not equal) — never short-circuits.
	return subtle.ConstantTimeCompare([]byte(expected), []byte(received)) == 1
}

func main() {
	secret := []byte("meridian-webhook-secret-32bytes!!")
	message := []byte(`{"amount_cents":5000,"to":"GB29NWBK60161331926819"}`)

	mac := hmac.New(sha256.New, secret)
	mac.Write(message)
	sig := hex.EncodeToString(mac.Sum(nil))

	fmt.Println("valid sig:", safeCompareHMAC(secret, message, sig))     // true
	fmt.Println("bad sig:", safeCompareHMAC(secret, message, "deadbeef")) // false

	tok := "correct-token"
	fmt.Println("token match:", safeCompareToken(tok, tok))          // true
	fmt.Println("token mismatch:", safeCompareToken(tok, "wrong"))   // false
}
```

## Request Signing

Meridian's payments service talks to card networks, bank APIs, and internal microservices. How does the receiving end *prove* that the request came from *you* and wasn't modified in transit? TLS protects the channel, but once a request hits the server, TLS is terminated. If there's a reverse proxy, a load balancer, or a compromised internal network hop in between, TLS alone proves nothing about the application-layer origin.

The answer is **request signing**: the caller produces a cryptographic signature over the request, and the server verifies it before doing anything.

### HMAC signing

HMAC (Hash-based Message Authentication Code) uses a shared secret key to produce a fixed-length tag over an arbitrary message. The server holds the same key, recomputes the HMAC, and compares. If they match, the request is authentic and unmodified.

The critical discipline is the **canonical request** — a deterministic serialization of the request elements you want to sign. AWS Signature Version 4 is the canonical reference implementation: method + URL + sorted headers + body hash, concatenated in a defined order. You don't have to implement SigV4, but you do have to define a canonical form and stick to it on both sides.

**On the job:** A Meridian transfer request is signed when it leaves the service. If the load balancer modifies headers (adds `X-Forwarded-For`, normalizes `Content-Type`), the signature still covers the body hash and path — the canonical request is defined to include only the elements you control.

Here is a complete, runnable HMAC request signing implementation:

```go
package main

import (
	"crypto/hmac"
	"crypto/sha256"
	"encoding/hex"
	"fmt"
	"strings"
	"time"
)

// canonicalRequest builds the deterministic string that both sides sign.
// method + "\n" + path + "\n" + timestamp + "\n" + hex(sha256(body))
// In production you would also include selected HTTP headers (e.g. Content-Type).
func canonicalRequest(method, path, timestamp string, body []byte) string {
	bodyHash := sha256.Sum256(body)
	return strings.Join([]string{
		method,
		path,
		timestamp,
		hex.EncodeToString(bodyHash[:]),
	}, "\n")
}

// signRequest returns the HMAC-SHA256 signature over the canonical form.
func signRequest(secret []byte, method, path, timestamp string, body []byte) string {
	canon := canonicalRequest(method, path, timestamp, body)
	mac := hmac.New(sha256.New, secret)
	mac.Write([]byte(canon))
	return hex.EncodeToString(mac.Sum(nil))
}

// verifyRequest checks the incoming signature against the recomputed one.
// It also enforces a ±5-minute clock-skew window.
func verifyRequest(secret []byte, method, path, timestamp, sig string, body []byte, now time.Time) error {
	ts, err := time.Parse(time.RFC3339, timestamp)
	if err != nil {
		return fmt.Errorf("bad timestamp: %w", err)
	}
	skew := now.Sub(ts)
	if skew < -5*time.Minute || skew > 5*time.Minute {
		return fmt.Errorf("timestamp out of window: skew=%v", skew)
	}
	want := signRequest(secret, method, path, timestamp, body)
	// hmac.Equal is constant-time — safe against timing attacks.
	wantBytes, _ := hex.DecodeString(want)
	gotBytes, _ := hex.DecodeString(sig)
	if !hmac.Equal(wantBytes, gotBytes) {
		return fmt.Errorf("signature mismatch")
	}
	return nil
}

func main() {
	secret := []byte("super-secret-shared-key-32bytes!!")
	method := "POST"
	path := "/v1/transfers"
	timestamp := time.Now().UTC().Format(time.RFC3339)
	body := []byte(`{"amount_cents":5000,"currency":"GBP","to_account":"GB29NWBK60161331926819"}`)

	sig := signRequest(secret, method, path, timestamp, body)
	fmt.Println("signature:", sig)

	// Server side: verify the valid request.
	err := verifyRequest(secret, method, path, timestamp, sig, body, time.Now())
	fmt.Println("valid request:", err) // <nil>

	// Server side: verify a tampered body.
	tamperedBody := []byte(`{"amount_cents":999999,"currency":"GBP","to_account":"GB29NWBK60161331926819"}`)
	err = verifyRequest(secret, method, path, timestamp, sig, tamperedBody, time.Now())
	fmt.Println("tampered body:", err) // signature mismatch
}
```

### Clock-skew window

The timestamp in the canonical request is what prevents **replay attacks** — an attacker recording a valid signed request and resending it later. If the server rejects requests where the timestamp is more than ±5 minutes from now, a replayed request eventually expires.

Five minutes is the conventional window. It is large enough to survive reasonable clock drift in distributed systems and small enough that a captured request is useless before the attacker can act on it.

<Callout kind="warn" title="Asymmetric signing for high-value operations">
HMAC requires both parties to know the shared secret. For signing requests *to external parties* (card networks, external bank APIs) where you cannot share a secret, use **asymmetric signing**: sign with your private key (ECDSA P-256 or Ed25519), publish your public key so the receiver can verify. The `crypto/ecdsa` and `crypto/ed25519` packages in stdlib handle both. The canonical-request discipline is identical; only the signing primitive changes. As of Go 1.26, `ecdsa.Sign` ignores any supplied `rand io.Reader` and always uses `crypto/rand` internally.
</Callout>

## Authorization Models

Authentication proves *who you are*. Authorization decides *what you're allowed to do*. In a financial system, getting authorization wrong is often more damaging than getting authentication wrong — an authenticated attacker with over-broad permissions is the worst case.

**On the job:** The most common authorization bug in fintech audits is not a missing role check — it's a missing ownership check in the data layer. An attacker who knows account ID formats can enumerate every account in the database if the `WHERE` clause doesn't include `owner_id`. Role checks protect endpoints; row-level checks protect data.

### RBAC vs. ABAC

<ConceptGrid cols={2}>
  <ConceptCard label="RBAC — Role-Based Access Control">A user has **roles** (`viewer`, `transfer-initiator`, `admin`). Each role grants a fixed set of permissions. Simple to reason about, audit, and explain to compliance. The dominant model for most fintech services.</ConceptCard>
  <ConceptCard label="ABAC — Attribute-Based Access Control">Access decisions use **attributes** of the subject, the resource, and the environment. Example: a user can transfer if `user.kycLevel >= 2` AND `transfer.amount <= user.dailyLimit` AND `user.country == account.country`. More expressive but significantly harder to audit and debug.</ConceptCard>
</ConceptGrid>

The default answer for fintech is RBAC with a thin layer of ABAC rules where the business logic demands it (e.g. per-account limits). Don't reach for full ABAC until RBAC demonstrably can't express what you need.

### Least privilege in practice

A service should only access what it needs *for the specific operation it is performing*. Concretely:

- The read-balance service has a read-only database credential. It cannot insert or delete.
- The transfer service can read and write the `accounts` table. It cannot touch the `audit_events` table directly (it fires events; the audit service writes them).
- The admin CLI has a short-lived credential scoped to a single operation, not a standing superuser role.

### Row-level authorization: a user sees only their own accounts

## Replay and Tamper Protection

You've signed your requests. Now let's talk about what an attacker does when they can't forge a new signature: they reuse a valid one.

### Replay attacks in payments

Scenario: a Meridian customer submits a `POST /v1/transfers` for £50. The request is signed. An attacker captures it (a compromised network hop, a leaked log line, a MITM before TLS terminates). They replay it three hours later. The signature is still valid. Without replay protection, the transfer posts three hours later.

The clock-skew window from the request signing section closes this for the HMAC case — a ±5-minute window means a 3-hour-old request is rejected. But some systems allow longer-lived signatures (OAuth tokens, pre-signed URLs). For those you need a **nonce**.

### Nonces for longer-lived operations

A **nonce** (number-used-once) is a unique value included in the request that the server persists after first use and rejects on any subsequent use. (We defined nonce in the AES-GCM section; the concept is the same — a value that must never repeat.)

The flow:

1. Client generates a random nonce (e.g. a UUID or 16 random bytes — from `crypto/rand`).
2. Client includes the nonce in the signed request payload.
3. Server verifies the signature.
4. Server checks the nonce against a store (Redis, Postgres). If the nonce exists: reject (replay). If not: record it with a TTL matching the signature's validity window, then proceed.

The idempotency key you built in the **Idempotency & Exactly-Once Semantics** chapter is a nonce for payment operations. The difference is intent: an idempotency key is the client's promise that retrying is safe; a nonce is the server's enforcement that no request is processed twice regardless of the client's intent.

**On the job:** A payment processor replays a settled webhook 48 hours after the first delivery due to a network hiccup in their retry logic. The idempotency key in the `FieldEncryptor` demo (previous section) is a nonce — the second delivery hits the nonce store, returns 409, and Meridian's ledger is untouched.

### Detecting tampering after the fact

Signing prevents accepting tampered requests. But what about data that's already stored — could someone with direct database access modify a balance and cover their tracks?

The answer is the **append-only audit log** you built in the **Auditability & Compliance** chapter, combined with periodic reconciliation: recompute balances from the ledger events and compare against stored balances. Any discrepancy is an anomaly worth investigating.

For extra assurance on the audit log itself, you can hash-chain entries: each event's signature includes the hash of the previous event, making it computationally infeasible to insert or modify a historical event without invalidating everything that follows.

## Handling PII

**PII** (Personally Identifiable Information) in fintech includes: name, address, date of birth, national ID numbers, bank account numbers, card numbers, transaction history, device fingerprints, and more. Regulators treat it as a liability. So should you.

The guiding principle is **blast-radius minimization**: if an attacker compromises one component, how much PII can they reach? Every architectural decision should reduce that answer.

**On the job:** After a breach, every second of PII exposure counts. A service whose data contracts were designed around tokenized `account_ref` values rather than raw IBANs means the breach team can say "the compromised service had zero access to account numbers" — a vastly different regulatory conversation than "we're still assessing how many records were exposed."

### The four disciplines

<ConceptGrid cols={2}>
  <ConceptCard label="1. Minimize collection">Only collect what you legally need to collect for the specific function being performed. A savings account doesn't need a user's employer. A money transfer doesn't need a user's medical history. Data you don't collect can't be breached.</ConceptCard>
  <ConceptCard label="2. Tokenize / pseudonymize">Replace high-sensitivity identifiers with opaque tokens. Store the actual bank account number encrypted (with envelope encryption, as above) and use an opaque `account_ref` token everywhere else in your system. Only the payments service that must display or use the actual number decrypts it; every other service uses the token.</ConceptCard>
  <ConceptCard label="3. Encrypt at rest">Sensitive columns (account numbers, national IDs, card numbers) encrypted with AES-GCM via envelope encryption, as covered above. Even with a database dump, the data is useless without KMS access.</ConceptCard>
  <ConceptCard label="4. Redact in logs">Logs are often the widest-distributed artifact in a system — shipped to multiple services, retained for months, readable by many engineers. A bank account number in a log is a breach waiting to happen. Redact at the logging boundary, not at the call site.</ConceptCard>
</ConceptGrid>

### Redacting PII in structured logs

The **Application Security Baseline** chapter (Part 2) covers the principle of keeping secrets out of logs. Here is the concrete Go pattern for `slog`:

```go
package main

import (
	"context"
	"log/slog"
	"os"
)

// Redacted wraps a string that must never appear in logs.
// Its LogValue() method returns a static placeholder instead.
type Redacted string

func (r Redacted) LogValue() slog.Value {
	return slog.StringValue("[REDACTED]")
}

func main() {
	logger := slog.New(slog.NewJSONHandler(os.Stdout, nil))

	accountNumber := Redacted("GB29NWBK60161331926819")

	// Even though accountNumber is passed directly, slog calls LogValue()
	// and logs [REDACTED] — never the actual IBAN.
	logger.InfoContext(context.Background(), "transfer initiated",
		slog.String("account", string(accountNumber)), // WRONG: bypasses LogValue
	)

	// CORRECT: pass the Redacted value as an Any so LogValue() is called.
	logger.InfoContext(context.Background(), "transfer initiated",
		slog.Any("account", accountNumber),
	)
}
```

### The blast-radius mindset in system design

Think of each service as a security boundary. Ask: if this service is completely compromised (code execution on the process, full memory dump), what PII does an attacker obtain?

- The API gateway should see only tokens, never decrypted account numbers.
- The notifications service needs an email address; it does not need a bank account number.
- The fraud service needs transaction amounts and merchant categories; it should not need to know the full payment card number.

Enforce these boundaries with service-to-service authorization (mTLS, SPIFFE) and data minimization in the API contracts between services. The principle of least privilege applied not just to roles, but to data.

<Exercise n={1} title="AES-GCM round-trip" level="easy">

Write `EncryptField(key, plaintext []byte) ([]byte, error)` and `DecryptField(key, sealed []byte) ([]byte, error)` that use `crypto/aes` + `cipher.NewGCM` and prepend the nonce to the ciphertext. <Solution>

```go
package main

import (
	"crypto/aes"
	"crypto/cipher"
	"crypto/rand"
	"errors"
	"fmt"
	"io"
)

func EncryptField(key, plaintext []byte) ([]byte, error) {
	block, err := aes.NewCipher(key)
	if err != nil {
		return nil, err
	}
	gcm, err := cipher.NewGCM(block)
	if err != nil {
		return nil, err
	}
	nonce := make([]byte, gcm.NonceSize())
	if _, err = io.ReadFull(rand.Reader, nonce); err != nil {
		return nil, err
	}
	return gcm.Seal(nonce, nonce, plaintext, nil), nil
}

func DecryptField(key, sealed []byte) ([]byte, error) {
	block, err := aes.NewCipher(key)
	if err != nil {
		return nil, err
	}
	gcm, err := cipher.NewGCM(block)
	if err != nil {
		return nil, err
	}
	ns := gcm.NonceSize()
	if len(sealed) < ns {
		return nil, errors.New("ciphertext too short")
	}
	return gcm.Open(nil, sealed[:ns], sealed[ns:], nil)
}

func main() {
	key := make([]byte, 32) // AES-256
	if _, err := rand.Read(key); err != nil {
		panic(err)
	}
	data := []byte("sensitive IBAN: GB29NWBK60161331926819")

	sealed, err := EncryptField(key, data)
	if err != nil {
		fmt.Println("encrypt error:", err)
		return
	}

	recovered, err := DecryptField(key, sealed)
	if err != nil {
		fmt.Println("decrypt error:", err)
		return
	}
	fmt.Println("recovered:", string(recovered))

	sealed[len(sealed)-1] ^= 0x01
	_, err = DecryptField(key, sealed)
	fmt.Println("tampered decrypt error:", err) // non-nil
}
```

A fresh random nonce per encryption, prepended so the decryptor can split it. The tampered test confirms AES-GCM returns an error rather than corrupt plaintext.

</Solution>

```go
	"crypto/hmac"
```

<Exercise n={4} title="Nonce store" level="hard">

Implement `NonceStore` backed by a `sync.Map` with TTL-based expiry. It should have `Record(nonce string, ttl time.Duration) error` (returns an error if the nonce was already recorded) and `Clean()` (removes expired entries). <Solution>

```go
package main

import (
	"errors"
	"fmt"
	"sync"
	"time"
)

type entry struct {
	expiresAt time.Time
}

type NonceStore struct {
	m sync.Map
}

var ErrNonceReused = errors.New("nonce already used")

func (s *NonceStore) Record(nonce string, ttl time.Duration) error {
	e := entry{expiresAt: time.Now().Add(ttl)}
	_, loaded := s.m.LoadOrStore(nonce, e)
	if loaded {
		// nonce already exists — check if it's expired
		if v, ok := s.m.Load(nonce); ok {
			if existing := v.(entry); time.Now().Before(existing.expiresAt) {
				return ErrNonceReused
			}
			// expired entry: overwrite
			s.m.Store(nonce, e)
			return nil
		}
	}
	return nil
}

func (s *NonceStore) Clean() {
	now := time.Now()
	s.m.Range(func(k, v any) bool {
		if e := v.(entry); now.After(e.expiresAt) {
			s.m.Delete(k)
		}
		return true
	})
}

func main() {
	store := &NonceStore{}

	err := store.Record("nonce-abc", 100*time.Millisecond)
	fmt.Println("first record:", err) // <nil>

	err = store.Record("nonce-abc", 100*time.Millisecond)
	fmt.Println("replay attempt:", err) // nonce already used

	time.Sleep(150 * time.Millisecond)
	store.Clean()

	err = store.Record("nonce-abc", 100*time.Millisecond)
	fmt.Println("after expiry:", err) // <nil>
}
```

`sync.Map.LoadOrStore` is the atomic "set if absent" primitive that makes this race-safe. The `Clean()` sweep uses `Range`, which is safe concurrent with other operations — deleted entries are simply skipped by any concurrent `Load`.

</Solution>

</Exercise>

Implement `VerifyWebhookSignature(secret, payload []byte, receivedSig string) error` that recomputes HMAC-SHA256 over the payload, then compares using `hmac.Equal`. package main

```go
import (
	"crypto/hmac"
	"crypto/sha256"
	"encoding/hex"
	"errors"
	"fmt"
)

var (
	errBadSigFormat = errors.New("signature: invalid hex encoding")
	errSigMismatch  = errors.New("signature: mismatch")
)

// VerifyWebhookSignature verifies an HMAC-SHA256 webhook signature.
// Uses hmac.Equal (constant-time) — safe against timing attacks.
func VerifyWebhookSignature(secret, payload []byte, receivedSig string) error {
	got, err := hex.DecodeString(receivedSig)
	if err != nil {
		return errBadSigFormat
	}
	mac := hmac.New(sha256.New, secret)
	mac.Write(payload)
	want := mac.Sum(nil)
	// hmac.Equal examines every byte regardless of where the first mismatch is.
	if !hmac.Equal(want, got) {
		return errSigMismatch
	}
	return nil
}

func main() {
	secret := []byte("meridian-webhook-secret-32bytes!!")
	payload := []byte(`{"event":"transfer.settled","amount_cents":5000}`)

	mac := hmac.New(sha256.New, secret)
	mac.Write(payload)
	validSig := hex.EncodeToString(mac.Sum(nil))

	fmt.Println("valid:", VerifyWebhookSignature(secret, payload, validSig))

	tampered := []byte(`{"event":"transfer.settled","amount_cents":999999}`)
	fmt.Println("tampered payload:", VerifyWebhookSignature(secret, tampered, validSig))

	fmt.Println("bad hex:", VerifyWebhookSignature(secret, payload, "not-hex!!"))
}
```

`hmac.Equal` is a thin wrapper around `subtle.ConstantTimeCompare` that also checks length equality first (in constant time). Both are in the standard library with no external dependencies.

<Recap>

- **Secrets management for finance** goes beyond the Part 2 baseline: KMS/HSM for cryptographic key material, separation of duties, and key rotation as a first-class operational concern. Your service calls the KMS — it never holds master key bytes.
- **`crypto/rand` is the only correct source** for keys, nonces, tokens, and any security-sensitive value. `math/rand` (and `math/rand/v2`) is deterministic and must never mint a security value. As of Go 1.26, several `crypto/*` functions always use secure randomness regardless of any supplied reader.
- **AES-GCM** (`crypto/aes` + `crypto/cipher`) provides **authenticated encryption** (AEAD) — confidentiality and integrity in one operation. A tampered ciphertext returns an error, not garbled plaintext. The nonce must be unique per encryption under a given key; `crypto/rand` is the safe source. Nonce reuse destroys confidentiality.
- **Envelope encryption** uses a per-record DEK (encrypted by the KMS-held KEK) stored beside the ciphertext. A database breach alone yields nothing without KMS access. DEKs and KEKs can be rotated independently.
- **Field-level PII encryption** applies envelope encryption to individual columns. Only services with the KMS IAM role can decrypt — service isolation is enforced at the infrastructure level, not just the application layer.
- **Constant-time comparison** (`hmac.Equal`, `subtle.ConstantTimeCompare`) is mandatory for any secret comparison. `bytes.Equal` short-circuits and leaks a timing oracle — this is a real attack used against production HMAC implementations. Always use `hmac.Equal` for HMAC tags.
- **Request signing** (HMAC or asymmetric) proves authenticity and integrity at the application layer, independent of TLS. A canonical request serializes the elements being signed deterministically; the clock-skew window closes the basic replay window.
- **Authorization models**: RBAC for most fintech use cases; ABAC for complex attribute-driven rules. Row-level authorization — including the authenticated user's ID in every data-layer query — prevents IDOR (Insecure Direct Object Reference) vulnerabilities.
- **Replay protection** combines the clock-skew window from request signing with nonces for longer-lived operations. The idempotency key from the **Idempotency & Exactly-Once Semantics** chapter is a nonce by another name.
- **PII handling**: minimize collection, tokenize high-sensitivity identifiers, encrypt at rest with envelope encryption, and redact at the logging boundary using `slog.LogValuer` — never rely on call-site discipline to keep PII out of logs.
- **Blast-radius mindset**: every service boundary is a data access boundary. Compromise one service; contain one blast radius. Design data contracts to give each service only the data it needs.

</Recap>
