## 12-Factor Config

<Define term="12-Factor Config" since="Production Project Architecture (Part 2, Chapter 17)">
One of twelve principles from Heroku's platform playbook for building deployable services. The config rule is: **store config in the environment, not the binary or committed files**. The same binary runs unchanged across dev, staging, and production — only the environment differs. If a credential or host name is baked into the binary or sits in a committed file, you cannot rotate it without a rebuild, and you cannot keep it out of Git history.
</Define>

Here's the thing about configuration: most engineers don't think about it until it bites them. A database password checked into version control. A staging URL hardcoded into the binary. A missing environment variable discovered at midnight when the production pod crashes.

The **12-factor app** methodology, from Heroku's platform engineers, has one sentence on config that you should tattoo somewhere: **"Store config in the environment."** Not the binary. Not a file you commit. The environment.

Why? Three reasons, all load-bearing:

1. **The same binary runs everywhere.** Dev, staging, production — the code is identical. Only the environment differs. You don't want to rebuild to change a database host.
2. **Config is not code.** It changes on a different cadence, by different people (ops, not devs), and it must be auditable separately from your Git history.
3. **Credentials must not enter version control.** Ever. Not even once, not even "temporarily." Git remembers everything and so do GitHub's secret scanners.

<ConceptGrid cols={3}>
  <ConceptCard label="Env vars">The 12-factor baseline. `os.Getenv("DB_DSN")` is always available, always overrideable by the deployment environment — Kubernetes, docker-compose, shell, CI all speak it natively.</ConceptCard>
  <ConceptCard label="Config files">TOML/YAML/JSON on disk — fine for non-secret settings like feature flags or log levels. They must be tracked in Git with no credentials. They are a lower precedence than env vars.</ConceptCard>
  <ConceptCard label="Command-line flags">The highest-precedence, most explicit form. Operators can one-shot override anything with `--db-host=...` without touching a file or env var. Good for debugging; noisy for normal operation.</ConceptCard>
  <ConceptCard label="Secrets manager">For credentials only — Vault, AWS Secrets Manager, GCP Secret Manager. Loaded at startup, not stored in any file the binary ships with. Covered in its own section below.</ConceptCard>
  <ConceptCard label="Never: source code">Hardcoded connection strings, API keys, or feature-flag values in `.go` files. I personally find this offensive. The compiler will cheerfully build it and ship it to prod.</ConceptCard>
  <Gotcha>`.env` files are a developer convenience, not a secret store. They must be in `.gitignore`. They are never shipped to production. If you see one committed to main, that's an incident, not a typo.</Gotcha>
</ConceptGrid>

<Callout kind="pro" title="12-factor isn't just an app methodology — it's a contract">

The real value of the 12-factor approach is that it creates a **clear contract** between your binary and its deployment environment. Your binary says: "Give me these env vars and I will work." The platform says: "Here they are." No other coupling. That contract is what makes blue/green deploys, scaling, and rotation possible without rebuilding code.

</Callout>

## Layering Sources

<Define term="Config Precedence (defaults → file → env → flags)">
The rule that determines which value wins when the same setting appears in multiple places. Standard order, lowest to highest: **built-in defaults** (the service runs safely out of the box) → **config file** (service-level settings for non-prod environments) → **environment variables** (deployment-platform intent: what Kubernetes or docker-compose injects) → **command-line flags** (explicit, per-invocation operator override). Higher always wins. Deviating from this order creates surprises that are almost impossible to debug in production because the override you expect isn't the one that took effect.
</Define>

Now let's make it concrete. In the real world, you don't just use env vars. You have built-in defaults, a config file for service-level settings, env vars for deployment-level overrides, and command-line flags for one-shot operator control. The order matters — a lot.

**The standard precedence stack, lowest to highest:**

```
built-in defaults → config file → environment variables → command-line flags
```

Higher wins. If `DB_HOST` is set both in the config file and as an env var, the env var wins. If `--db-host` is passed on the command line, that wins over everything. This is not negotiable or configurable — document it, stamp it in your `README`, and never deviate.

Let's build a minimal but real implementation of this merge in stdlib — no external libraries yet:

```go
package main

import (
	"flag"
	"fmt"
	"os"
)

// Config holds every knob for the ledger service.
// Fields are exported so they can be set by any source.
type Config struct {
	DBHost   string
	DBPort   string
	LogLevel string
}

// defaults returns the Config pre-loaded with safe built-in values.
// Every field MUST have a default here so the service is runnable
// out of the box in development without any external config.
func defaults() Config {
	return Config{
		DBHost:   "localhost",
		DBPort:   "5432",
		LogLevel: "info",
	}
}

// loadConfig merges all sources in precedence order.
func loadConfig() Config {
	cfg := defaults()

	// Layer 2: environment variables overwrite defaults.
	if v := os.Getenv("DB_HOST"); v != "" {
		cfg.DBHost = v
	}
	if v := os.Getenv("DB_PORT"); v != "" {
		cfg.DBPort = v
	}
	if v := os.Getenv("LOG_LEVEL"); v != "" {
		cfg.LogLevel = v
	}

	// Layer 3: CLI flags overwrite everything (define after env so
	// the flag default shows the currently resolved value).
	flag.StringVar(&cfg.DBHost, "db-host", cfg.DBHost, "database hostname")
	flag.StringVar(&cfg.DBPort, "db-port", cfg.DBPort, "database port")
	flag.StringVar(&cfg.LogLevel, "log-level", cfg.LogLevel, "log level")
	flag.Parse()

	return cfg
}

func main() {
	cfg := loadConfig()
	fmt.Printf("DBHost=%q DBPort=%q LogLevel=%q\n",
		cfg.DBHost, cfg.DBPort, cfg.LogLevel)
}
```

## Validate at Startup

<Define term="Fail-Fast Validation">
The discipline of **crashing the process immediately at startup** if anything is wrong with the config — before the service accepts a single request. A required field is empty, a URL is malformed, a port is out of range: crash now with a clear message. The alternative — discovering the problem when a request finally exercises the broken path — means a production incident at an arbitrary time, with a misleading error (a timeout, a nil pointer, a 500) instead of a config error. Fail-fast validation converts "mysterious 3am page" into "clear startup error the engineer sees immediately in CI or on first deploy."
</Define>

A missing `DB_HOST` that crashes the process at 3am because some handler path finally tried to open a connection is a crime I've had to clean up too many times. The rule is simple: **validate at startup, fail fast**.

If the process cannot possibly work correctly — a required field is empty, a URL is malformed, a port is out of range — it must crash *immediately* at boot, before it begins serving any traffic, with a clear message explaining exactly what is wrong and what to set.

```go
package main

import (
	"errors"
	"fmt"
	"net/url"
	"os"
	"strconv"
)

type Config struct {
	DBDSN    string // required: postgres DSN
	DBPort   int    // required: 1–65535
	LogLevel string // optional: defaults to "info"
	APIKey   string // required: payment processor key
}

// ErrConfig wraps validation errors so callers can errors.As them.
type ErrConfig struct {
	Field  string
	Reason string
}

func (e *ErrConfig) Error() string {
	return fmt.Sprintf("config: field %q: %s", e.Field, e.Reason)
}

// validate checks all required fields and formats.
// Returns the first error — production configs catch all of them;
// this form keeps the example compact.
func (c *Config) validate() error {
	if c.DBDSN == "" {
		return &ErrConfig{Field: "DBDSN", Reason: "required: set DB_DSN env var"}
	}
	if _, err := url.Parse(c.DBDSN); err != nil {
		return &ErrConfig{Field: "DBDSN", Reason: "must be a valid URL: " + err.Error()}
	}
	if c.DBPort < 1 || c.DBPort > 65535 {
		return &ErrConfig{Field: "DBPort", Reason: "must be 1–65535"}
	}
	if c.APIKey == "" {
		return &ErrConfig{Field: "APIKey", Reason: "required: load from secrets manager"}
	}
	return nil
}

func mustLoadConfig() Config {
	portStr := os.Getenv("DB_PORT")
	if portStr == "" {
		portStr = "5432"
	}
	port, err := strconv.Atoi(portStr)
	if err != nil {
		fmt.Fprintf(os.Stderr, "config: DB_PORT must be an integer, got %q\n", portStr)
		os.Exit(1)
	}
	cfg := Config{
		DBDSN:    os.Getenv("DB_DSN"),
		DBPort:   port,
		LogLevel: os.Getenv("LOG_LEVEL"),
		APIKey:   os.Getenv("PAYMENT_API_KEY"),
	}
	if cfg.LogLevel == "" {
		cfg.LogLevel = "info"
	}
	if err := cfg.validate(); err != nil {
		var ce *ErrConfig
		if errors.As(err, &ce) {
			fmt.Fprintf(os.Stderr, "startup: invalid config — %s\n", ce)
		} else {
			fmt.Fprintf(os.Stderr, "startup: invalid config — %v\n", err)
		}
		os.Exit(1)
	}
	return cfg
}

func main() {
	cfg := mustLoadConfig()
	fmt.Println("config loaded, log level:", cfg.LogLevel)
}
```

The `mustLoad` naming convention is idiomatic: a function prefixed `must` panics or exits if it fails. Use it only at startup, in `main`, never deep inside request handlers where you want error propagation. At startup, death is the correct response to a broken config.

<UnderTheHood title="Why os.Exit(1) and not panic()">

`os.Exit(1)` and `panic()` both stop the process, but they behave very differently at the runtime level. `panic` unwinds the stack, running all deferred functions on the way down, and then prints a stack trace — useful for unexpected programmer errors during development. `os.Exit` skips all of that: no deferred cleanup, no stack trace, immediate process termination with the given status code.

For config validation at startup, `os.Exit(1)` is correct: deferred cleanup is meaningless when the process hasn't opened any resources yet, and a stack trace is misleading (the "error" isn't a programmer bug — it's a misconfigured deployment). The exit code `1` signals to the process supervisor (systemd, Kubernetes, docker-compose) that the process failed, so it knows whether to restart, alert, or give up.

In Kubernetes specifically, a non-zero exit on startup means the pod enters `CrashLoopBackOff` — which is exactly what you want: it tells the operator "something is wrong with your config, fix it before this pod will run."

As of Go 1.24, `os.Exit` is implemented as a direct `runtime.exit` call that bypasses the deferred function queue and goes straight to the OS `_exit` syscall.

</UnderTheHood>

## Library Landscape

The stdlib gets you surprisingly far. But as your service grows — multiple config files, type coercion, nested structs — you'll want more. Here's the honest landscape.

**Stdlib: `flag` + `os.Getenv`**

Zero dependencies. You write the merge loop yourself. Works perfectly for small services with a handful of settings. Falls apart when you have twenty config fields and want struct-tag-driven binding.

**`envconfig` (kelseyhightower/envconfig)**

The oldest struct-tag-driven env-var loader. You define a struct with `envconfig` tags, call `envconfig.Process`, and it populates everything — including type coercion (string to int, string to bool, string to duration).

```go
type Config struct {
	DBHost  string        `envconfig:"DB_HOST" default:"localhost"`
	DBPort  int           `envconfig:"DB_PORT" default:"5432"`
	Timeout time.Duration `envconfig:"TIMEOUT" default:"30s"`
}
// envconfig.Process("", &cfg) populates it from the environment.
```

Simple, battle-tested, no config files. If you only need env vars, this is the right tool.

**`koanf` (knadh/koanf)**

A modern, provider-based config library. You compose providers — a `file` provider for TOML/YAML, an `env` provider for environment variables, a `posflag` provider for pflag — and they merge in the order you add them. Strict struct unmarshaling, a clean API.

```go
k := koanf.New(".")
k.Load(file.Provider("config.toml", "."), toml.Parser())
k.Load(env.Provider("APP_", ".", func(s string) string {
    return strings.ToLower(strings.TrimPrefix(s, "APP_"))
}), nil)
k.Unmarshal("", &cfg)
```

Koanf is my recommendation for mid-to-large services: explicit, composable, and it does not silently ignore unknown keys.

**Viper (spf13/viper)**

The most popular config library in the Go ecosystem. Layered sources, remote config (etcd/Consul), automatic env-var binding, watching for config file changes. It is feature-rich and widely used. The trade-offs: it is global state by default (use `viper.New()` to avoid this), it is lenient about unknown keys (silent ignore), and it pulls in more transitive dependencies than koanf.

<ConceptGrid cols={2}>
  <ConceptCard label="When to use stdlib flag+env">Small service, few settings, zero external dependencies, env-only config. Write the merge loop in 30 lines and move on.</ConceptCard>
  <ConceptCard label="When to use envconfig">Env-var-only config with type coercion. Clean struct tags. You do not need config files. Tiny dependency footprint.</ConceptCard>
  <ConceptCard label="When to use koanf">Multiple config sources (file + env + flags), layered merge, strict key handling. My recommendation for production services.</ConceptCard>
  <ConceptCard label="When to use Viper">You need remote config (etcd/Consul), dynamic reload, or you are joining an existing project that already uses it. Check global state usage.</ConceptCard>
  <Gotcha>Viper's global default instance is shared across your entire process — tests that call `viper.Set(...)` pollute each other. Always use `viper.New()` in production code and inject the instance as a dependency.</Gotcha>
</ConceptGrid>

Here is a runnable koanf-style merge using only stdlib (we simulate the layering pattern without the external package, so it runs in the playground):

```go
package main

import (
	"fmt"
	"strconv"
	"strings"
)

// SimulatedSource represents one layer of config (file, env, flags).
type SimulatedSource struct {
	name   string
	values map[string]string
}

// merge applies sources in order; later sources overwrite earlier ones.
func merge(sources []SimulatedSource) map[string]string {
	out := make(map[string]string)
	for _, src := range sources {
		for k, v := range src.values {
			out[k] = v
			fmt.Printf("[%s] %s = %q\n", src.name, k, v)
		}
	}
	return out
}

type Config struct {
	DBHost   string
	DBPort   int
	LogLevel string
}

func buildConfig(resolved map[string]string) (Config, error) {
	portStr := resolved["DB_PORT"]
	port, err := strconv.Atoi(portStr)
	if err != nil {
		return Config{}, fmt.Errorf("DB_PORT %q is not an integer", portStr)
	}
	return Config{
		DBHost:   resolved["DB_HOST"],
		DBPort:   port,
		LogLevel: strings.ToLower(resolved["LOG_LEVEL"]),
	}, nil
}

func main() {
	sources := []SimulatedSource{
		{
			name: "defaults",
			values: map[string]string{
				"DB_HOST":   "localhost",
				"DB_PORT":   "5432",
				"LOG_LEVEL": "info",
			},
		},
		{
			name: "config.toml",
			values: map[string]string{
				"DB_HOST": "db.internal",
			},
		},
		{
			name: "env vars",
			values: map[string]string{
				"DB_HOST":   "db.prod.internal",
				"LOG_LEVEL": "warn",
			},
		},
		// CLI flags: none passed this time
```

## Secrets Handling

<Define term="Secret (vs. ordinary config)">
A value that **must never appear in a log, a committed file, a process listing, or a crash dump**. Examples: database credentials, payment-processor API keys, signing keys, OAuth client secrets. Ordinary config (a database hostname, a log level, a feature flag) is safe to commit, safe to log, and safe to grep. A secret is not. The practical test: could this value, if seen by an attacker, let them move money, impersonate users, or decrypt data? If yes, it is a secret. Treat it differently from the first line of code.
</Define>

<Define term="Secrets Manager (Vault / KMS)">
A dedicated service that **stores, versions, and audits access to secrets** — keeping them out of config files, binaries, and environment variables that linger in process listings. At startup, your service authenticates to the secrets manager (via an IAM role, a Vault AppRole, or a workload identity) and fetches only the secrets it needs. The manager records every access in an audit log. Options: **HashiCorp Vault** (self-hosted, dynamic short-lived credentials), **AWS Secrets Manager** (managed, IAM-role auth), **GCP Secret Manager** (same model on Google Cloud). Kubernetes Secrets are base64-encoded values in etcd — not encrypted by default, not a replacement for a real manager in high-compliance environments.
</Define>

<Define term="Secret Rotation">
Replacing a live secret with a new value **without restarting or redeploying the service**. A payment-processor API key that rotates every 90 days should not require a redeploy: the old key stays valid while the new one is written to the secrets manager, the service fetches the new version on its next renewal tick, swaps it into its in-memory cache, and the old version is retired. Rotation without a restart requires the service to hold its secret in a refreshable cache (a `SecretCache` with a background goroutine and a `sync.RWMutex` swap) rather than reading it once at startup and baking it into a struct field.
</Define>

Config and secrets are not the same thing. Config is safe to commit (without credentials), safe to log, safe to grep. Secrets are never any of those things. The discipline of separating them is not pedantry — it is what keeps you off the news.

**The three rules of secrets:**

1. Never commit them to version control — not even in a `.env` that "isn't really committed." Add `.env` to `.gitignore` and add a `.gitignore` check to your CI.
2. Never put them in config files that ship with the binary or live on the filesystem in plaintext.
3. Load them from a **secrets manager** at startup. The secrets manager is the source of truth; your binary is a client.

**The secrets manager options:**

- **HashiCorp Vault** — self-hosted, open source, the standard for on-prem. Supports dynamic secrets (short-lived credentials generated on demand), lease renewal, and audit logs. The Go client is `github.com/hashicorp/vault/api`.
- **AWS Secrets Manager** — managed, tight integration with IAM roles. Your ECS task or EC2 instance authenticates via its instance role — no credentials to fetch credentials. SDK: `github.com/aws/aws-sdk-go-v2/service/secretsmanager`.
- **GCP Secret Manager** — same model on Google Cloud. Cloud Run services authenticate via workload identity.
- **Kubernetes Secrets** — available as env vars or mounted files inside the pod. Easier to consume than a dedicated manager, but stored as base64 (not encrypted) in etcd by default unless you enable envelope encryption. They are not a replacement for Vault for high-compliance environments.

**Rotation without a redeploy:**

The ledger service's payment-processor API key needs to rotate every 90 days. With a secret manager, the process is:

1. Write the new key to the secret manager (the old one still works).
2. The secret manager marks the new version as "current."
3. The service polls or is notified; it fetches the new version and replaces the in-memory copy.
4. Retire the old version after confirming the new one is in use.

No redeploy. No downtime. No restart. Here's how that rotation works, animated:

Here's a self-contained simulation of the rotation pattern — the `SecretCache` that fetches and rotates a secret without touching the request path:

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"time"
)

// SecretCache holds a rotating secret and refreshes it on a ticker.
// In production, Fetch calls your secrets manager (Vault, AWS, GCP).
type SecretCache struct {
	mu      sync.RWMutex
	current string
	fetch   func(ctx context.Context) (string, error)
}

// NewSecretCache initializes the cache, performs the first fetch, and
// starts a background goroutine that refreshes on interval.
// The caller must hold the returned cancel to stop the goroutine.
func NewSecretCache(
	ctx context.Context,
	fetch func(ctx context.Context) (string, error),
	refresh time.Duration,
) (*SecretCache, error) {
	sc := &SecretCache{fetch: fetch}
	secret, err := fetch(ctx)
	if err != nil {
		return nil, fmt.Errorf("initial secret fetch: %w", err)
	}
	sc.current = secret

	go sc.rotate(ctx, refresh)
	return sc, nil
}

func (sc *SecretCache) rotate(ctx context.Context, interval time.Duration) {
	t := time.NewTicker(interval)
	defer t.Stop()
	for {
		select {
		case <-ctx.Done():
			return
		case <-t.C:
			newSecret, err := sc.fetch(ctx)
			if err != nil {
				// Log the error but keep serving with the old secret.
				// Do not crash — availability matters more than freshness here.
				fmt.Println("secret refresh failed, retaining old value:", err)
				continue
			}
			sc.mu.Lock()
			sc.current = newSecret
			sc.mu.Unlock()
			fmt.Println("secret rotated successfully")
		}
	}
}

// Get returns the current secret value. Safe for concurrent use.
func (sc *SecretCache) Get() string {
	sc.mu.RLock()
	defer sc.mu.RUnlock()
	return sc.current
}
```

**Kubernetes Secrets and their real limits:**

Kubernetes Secrets are base64-encoded values stored in etcd. They are mounted as files or injected as env vars into pods. They are convenient and tightly integrated with RBAC. But they are not encrypted at rest unless you configure envelope encryption — and most clusters don't. Anyone with etcd access reads your secrets. Vault is the right answer for high-compliance environments; Kubernetes Secrets are fine for low-sensitivity settings like non-prod API keys.

<Callout kind="warn" title="Kubernetes Secrets are not encrypted by default">

Base64 is an encoding, not encryption. A Kubernetes Secret stored in etcd without envelope encryption is readable by anyone with etcd or Kubernetes API admin access. Enable KMS envelope encryption for any cluster handling real credentials. For payment-processor keys and database credentials, use Vault or a cloud secrets manager and load them at runtime — do not rely on Kubernetes Secrets alone.

## Keeping Secrets Out of Logs

<Define term="Redaction (LogValue / String masking)">
Making a sensitive value **replace itself with a safe placeholder in every output path** — `fmt`, `slog`, errors, `%v`, JSON marshaling — without requiring the caller to remember to redact it. In Go, implement `String() string` (returns `"[REDACTED]"`) to intercept `fmt` formatting, and `LogValue() slog.Value` (returns `slog.StringValue("[REDACTED]")`) to intercept `log/slog`. Both interfaces are called automatically — the log site needs no change. If you rely on callers to remember `myKey.Value()` instead, it will leak eventually. The type enforces the redaction so forgetfulness can't cause a breach.
</Define>

Here is a failure mode I've seen in production: an engineer adds a `slog.Info("config loaded", "cfg", cfg)` line and accidentally ships the payment-processor API key to the log aggregator. From there it ends up in Splunk, in Datadog, in the incident report, and eventually in the breach notification.

The solution is a type that refuses to print itself.

Go's `fmt` package calls the `String() string` method on any value that implements `fmt.Stringer`. Go's `slog` package calls `LogValue() slog.Value` on any value that implements `slog.LogValuer`. If your secret type implements both, it redacts itself from every output surface.

```go
package main

import (
	"fmt"
	"log/slog"
	"os"
)

// Secret wraps a sensitive string value that redacts itself in
// all output: fmt, slog, errors, and %v formatting.
type Secret struct {
	val string
}

// NewSecret constructs a Secret from a plaintext string.
// The plaintext is never stored directly in a log-visible field.
func NewSecret(s string) Secret { return Secret{val: s} }

// Value returns the actual secret for use in API calls.
// The name is deliberate — callers must be explicit about extracting it.
func (s Secret) Value() string { return s.val }

// String implements fmt.Stringer — fmt.Println, %v, %s all see "[REDACTED]".
func (s Secret) String() string { return "[REDACTED]" }

// LogValue implements slog.LogValuer — slog sees "[REDACTED]".
func (s Secret) LogValue() slog.Value {
	return slog.StringValue("[REDACTED]")
}
```

<UnderTheHood title="How String() and slog.LogValuer intercept output">

When `fmt.Println(cfg)` runs, the `fmt` package reflects on each field of the struct. If a field's type implements the `fmt.Stringer` interface — `String() string` — `fmt` calls that method instead of printing the raw value. This is the same mechanism that makes `time.Time` print as a readable timestamp instead of a struct dump.

`slog` goes a step further. When it processes a log attribute whose value implements `slog.LogValuer` — `LogValue() slog.Value` — it calls that method and uses the returned `slog.Value` as the logged representation. This happens *before* the handler (JSON, text, etc.) sees the value, so neither the handler nor any downstream exporter ever sees the plaintext.

As of Go 1.21 (when `log/slog` was promoted to the standard library), `slog.LogValuer` is the idiomatic way to control how sensitive values appear in structured log output. Prior to Go 1.21, teams often used custom `zap.Field` marshalers or `logrus` hooks; `slog` makes this a first-class language concern.

One important subtlety: `String()` is called by `%v` and `%s` but NOT by `%+v` if the type is a struct (the struct expansion ignores `Stringer`). Wrapping the secret in a named type (not embedding a bare `string`) ensures `%+v` on the *containing struct* still calls `String()` on the field's type. Test this with a struct that uses `%+v` to be sure.

Implement a `SecretCache` that: (1) fetches the initial secret at construction and returns an error if the fetch fails, (2) starts a background goroutine that refreshes on a ticker, (3) stops the goroutine cleanly when the context is cancelled, (4) keeps the old value on a failed refresh rather than crashing. Write a `main` that demonstrates a rotation by incrementing a version counter on each fetch.

<Solution>

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"time"
)

type SecretCache struct {
	mu      sync.RWMutex
	current string
	fetch   func(context.Context) (string, error)
}

func NewSecretCache(
	ctx context.Context,
	fetch func(context.Context) (string, error),
	interval time.Duration,
) (*SecretCache, error) {
	val, err := fetch(ctx)
	if err != nil {
		return nil, fmt.Errorf("initial secret fetch: %w", err)
	}
	sc := &SecretCache{current: val, fetch: fetch}
	go sc.run(ctx, interval)
	return sc, nil
}

func (sc *SecretCache) run(ctx context.Context, d time.Duration) {
	t := time.NewTicker(d)
	defer t.Stop()
	for {
		select {
		case <-ctx.Done():
			return
		case <-t.C:
			val, err := sc.fetch(ctx)
			if err != nil {
				fmt.Println("refresh error, keeping old value:", err)
				continue
			}
			sc.mu.Lock()
			sc.current = val
			sc.mu.Unlock()
			fmt.Println("rotated to:", val)
		}
	}
}

func (sc *SecretCache) Get() string {
	sc.mu.RLock()
	defer sc.mu.RUnlock()
	return sc.current
}

func main() {
	ver := 0
	fetch := func(_ context.Context) (string, error) {
		ver++
		return fmt.Sprintf("key-v%d", ver), nil
	}

	ctx, cancel := context.WithTimeout(context.Background(), 2500*time.Millisecond)
	defer cancel()

	cache, err := NewSecretCache(ctx, fetch, 700*time.Millisecond)
	if err != nil {
		fmt.Println("startup failed:", err)
		return
	}

	for i := 0; i < 4; i++ {
		time.Sleep(600 * time.Millisecond)
		fmt.Printf("request %d: %s\n", i+1, cache.Get())
	}
}
```

The `sync.RWMutex` allows concurrent reads (many request goroutines) without blocking each other, while the single writer (the rotation goroutine) takes an exclusive lock only during the swap. On a refresh failure, we log and continue — losing freshness is better than losing availability.

</Solution>

<Recap>

- **12-factor config**: store config in the environment, not the binary or committed files. The same binary runs unchanged across dev/staging/production; only the environment differs.
- **Layered precedence**: built-in defaults → config file → environment variables → command-line flags. Higher wins. Document this and never deviate from it.
- **Validate at startup, fail fast**: a `validate()` method on `Config`, called in `mustLoadConfig()`, crashes the process at boot with a clear message if anything is missing or malformed. `os.Exit(1)` is correct; `panic` is wrong.
- **Library landscape**: stdlib `flag`+`os.Getenv` for small services; `envconfig` for struct-tag-driven env-only loading; `koanf` for layered multi-source config (recommended); Viper when you need remote config or are joining an existing project. Avoid Viper's global default instance.
- **Secrets are not config**: never commit them, never log them, load from a secrets manager (Vault, AWS, GCP). Kubernetes Secrets are base64, not encrypted — use envelope encryption or a real manager for credentials.
- **Rotation without a redeploy**: a `SecretCache` with a background goroutine, a ticker, and a `sync.RWMutex` swap. On refresh failure, keep the old value — availability over freshness.
- **Redacting types**: a `Secret` type implementing `fmt.Stringer` (`String() string`) and `slog.LogValuer` (`LogValue() slog.Value`) redacts itself in every output surface — fmt, slog, errors — without requiring any change at the log site.
