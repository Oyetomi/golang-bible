<HeroCard label="Part 2 · Chapter 19" title="The Model Context Protocol (MCP) in Go">

Alice asks her AI assistant: "find me two seats together for Dune on Friday and hold them". For the assistant to do that, it needs to see the cinema's seats and hold them, as Alice, with nothing more than Alice may do. The **Model Context Protocol** is the standard way to give it that: a small server that describes a few **tools** ("hold a seat"), **resources** ("the seat map") and **prompts**, which any MCP-capable assistant can discover and call.

This chapter builds that server for the cinema with the official Go SDK. It talks to the cinema's gRPC API from chapter 18, and acts for exactly one customer. It shows every message the protocol exchanges, because MCP is only JSON-RPC underneath, and the protocol changed in 2026 in ways that show in the bytes. Then it looks at the part that's genuinely new: the model reads what your tools return, and some of that text was written by strangers.

Six stops. If you get lost, come back here:

1. **JSON-RPC, by the byte.** Requests, responses, notifications and errors, on a real session.
2. **Discovery.** The legacy `initialize` handshake, and the stateless `server/discover` that replaces it.
3. **Tools, resources, prompts.** Typed Go handlers, generated schemas, and two kinds of error.
4. **Transports.** stdio for a local assistant, Streamable HTTP for a remote one.
5. **What the model reads.** A customer's name that carried instructions.
6. **Authority lives in the server.** Why the injected instruction failed, and what to show the model at all.

## The lab bench

The cinema service from chapter 18 (HTTP on one port, gRPC on another), and a new program in its module, `cmd/cinema-mcp`, built on **`github.com/modelcontextprotocol/go-sdk` v1.8.0**. Its only dependency on the cinema is the gRPC client. Two small clients drive it: `mcpclient`, which does what an assistant's host does (start the server, discover it, call its tools) and can log every JSON-RPC message, and `mcpread`, which prints exactly what a model would read.

```text
  assistant host ──stdio or HTTP──▶ cinema-mcp -user alice ──gRPC (x-user: alice)──▶ cinema ──▶ store
```

## JSON-RPC

*Stop 1 of 6.*

### Step 1: four kinds of message

MCP messages are **JSON-RPC 2.0**: small JSON objects, one per line on stdio.

- A **request** has a `method`, `params` and an `id`, and expects exactly one response with the same `id`.
- A **response** has the `id` and either a `result` or an `error` (a `code` and a `message`).
- A **notification** has a `method` and no `id`, and never gets a response.
- **Error codes** are standard: -32700 the line isn't JSON, -32600 not a valid request, -32601 no such method, -32602 invalid params, -32603 internal error.

### Step 2: a real session

`mcpclient` wrapped its transport in the SDK's `LoggingTransport`, which recorded every message. Eight of them, from a session on the newest protocol (the `_meta` contents after the first request are elided; they repeat):

```text
client → {"jsonrpc":"2.0","id":1,"method":"server/discover","params":{"_meta":{"io.modelcontextprotocol/clientCapabilities":{"roots":{"listChanged":true}},"io.modelcontextprotocol/clientInfo":{"name":"mcpclient","version":"v0.1.0"},"io.modelcontextprotocol/protocolVersion":"2026-07-28"}}}
server ← {"jsonrpc":"2.0","id":1,"result":{"resultType":"complete","_meta":{"io.modelcontextprotocol/serverInfo":{"name":"cinema","version":"v1.0.0"}},"ttlMs":0,"cacheScope":"public","supportedVersions":["2026-07-28","2025-11-25","2025-06-18","2025-03-26","2024-11-05"],"capabilities":{"logging":{},"prompts":{"listChanged":true},"resources":{"listChanged":true},"tools":{"listChanged":true}}}}
client → {"jsonrpc":"2.0","id":3,"method":"tools/call","params":{"_meta":"…same three keys…","name":"hold_seat","arguments":{"movie":"inception","seat":"A7"}}}
server ← {"jsonrpc":"2.0","id":3,"result":{"_meta":"…","content":[{"type":"text","text":"{\"held\":true,\"seat\":\"A7\"}"}],"structuredContent":{"held":true,"seat":"A7"},"resultType":"complete"}}
client → {"jsonrpc":"2.0","id":4,"method":"tools/call","params":{"_meta":"…same three keys…","name":"hold_seat","arguments":{"movie":"inception","seat":"A7"}}}
server ← {"jsonrpc":"2.0","id":4,"result":{"_meta":"…","content":[{"type":"text","text":"seat is held or booked by someone else"}],"structuredContent":{"held":false,"seat":"A7"},"isError":true,"resultType":"complete"}}
client → {"jsonrpc":"2.0","id":8,"method":"tools/call","params":{"_meta":"…same three keys…","name":"book_everything","arguments":{}}}
server ← {"jsonrpc":"2.0","id":8,"error":{"code":-32602,"message":"unknown tool \"book_everything\""}}
```

Read them in pairs by `id`. The first pair is discovery (stop 2). `id` 3 holds A7 and gets a result with the answer twice: as text (`content`, which any model can read) and as JSON matching the tool's output schema (`structuredContent`, which code can use). `id` 4 tries A7 again: the tool ran and said no, so it's a **result** with `isError: true`. `id` 8 asks for a tool that doesn't exist: that's a **protocol error**, -32602, and no tool ran at all.

## Discovery

*Stop 2 of 6.*

### Step 1: the legacy handshake

Until 2026, every MCP session began with a three-message handshake. The same client, asked for protocol `2025-11-25`:

```text
client → {"jsonrpc":"2.0","id":1,"method":"initialize","params":{"clientInfo":{"name":"mcpclient","version":"v0.1.0"},"protocolVersion":"2025-11-25","capabilities":{"roots":{"listChanged":true}}}}
server ← {"jsonrpc":"2.0","id":1,"result":{"capabilities":{"logging":{},"prompts":{"listChanged":true},"resources":{"listChanged":true},"tools":{"listChanged":true}},"protocolVersion":"2025-11-25","serverInfo":{"name":"cinema","version":"v1.0.0"}}}
client → {"jsonrpc":"2.0","method":"notifications/initialized","params":{}}
```

The client proposes a protocol version and says what *it* can do (its capabilities: here, it can tell the server about its filesystem roots). The server answers with the version it will speak, its own capabilities (tools, resources, prompts, logging, each noting whether it sends change notifications) and its name. The client then sends a **notification**, `notifications/initialized`, and only now may other requests flow. The connection itself carries the negotiated state: this is a **session**.

### Step 2: the stateless revision

The SDK's default is the **2026-07-28** revision, and its session (stop 1) began differently: a single `server/discover` request, and every request after it carries the same three `_meta` keys (protocol version, client info, client capabilities). The server's answer lists the versions it supports and its capabilities, and nothing about the connection needs remembering. Each request is self-describing.

Why the change? A server behind a load balancer, with a handshake stored per connection, needs sticky sessions: every request of a session must reach the same instance. With the negotiation carried in each request, any instance can answer any request, like an ordinary HTTP API. The SDK tries `server/discover` first and falls back to `initialize` when a server doesn't support the new revision, which is exactly what stop 4 measures over HTTP.

## Tools, Resources, Prompts

*Stop 3 of 6.*

### Step 1: the server

The server is a separate program in the cinema module. It doesn't touch Redis or the seat store: it's a gRPC *client* of chapter 18's seat service, so it can do only what that service lets a customer do. The imports show the three worlds it joins: the MCP SDK, gRPC, and the generated seat-service code:

```go noverify title="cinema/cmd/cinema-mcp/main.go · lines 1–29"
// cinema-mcp lets an AI assistant look at seats and hold them for one
// customer, through the Model Context Protocol. It's a client of the
// cinema's gRPC SeatService (chapter 18), acting with that customer's
// authority and no more.
//
//	cinema-mcp -user alice                 stdio (the assistant starts it)
//	cinema-mcp -user alice -http :8093     Streamable HTTP
package main

import (
	"context"
	"encoding/json"
	"flag"
	"fmt"
	"log"
	"net/http"
	"os"
	"strings"
	"time"

	cinemav1 "cinema/internal/gen/cinema/v1"

	"github.com/modelcontextprotocol/go-sdk/mcp"
	"google.golang.org/grpc"
	"google.golang.org/grpc/codes"
	"google.golang.org/grpc/credentials/insecure"
	"google.golang.org/grpc/metadata"
	"google.golang.org/grpc/status"
```

Its state is two things: a connection to the seat service, and the one customer it acts for. Every gRPC call goes through `as`, which attaches that customer's identity as metadata and a 2-second deadline. The model never supplies a user name; the server decides whose authority it has when it starts:

```go noverify title="cinema/cmd/cinema-mcp/main.go · lines 31–40"
type cinema struct {
	seats cinemav1.SeatServiceClient
	user  string
}

// as gives a gRPC call the customer's identity and a 2 s deadline.
func (c *cinema) as(ctx context.Context) (context.Context, context.CancelFunc) {
	ctx, cancel := context.WithTimeout(ctx, 2*time.Second)
	return metadata.AppendToOutgoingContext(ctx, "x-user", c.user), cancel
}
```

Tool inputs and outputs are ordinary Go structs. `mcp.AddTool` reads them to generate JSON schemas, and the `jsonschema` tags become the descriptions the model reads when deciding what to pass. `SeatMap` deliberately reports other customers' seats only as a count:

```go noverify title="cinema/cmd/cinema-mcp/main.go · lines 42–60"
type MovieArgs struct {
	Movie string `json:"movie" jsonschema:"the film, for example inception or dune"`
}

type SeatArgs struct {
	Movie string `json:"movie" jsonschema:"the film, for example inception or dune"`
	Seat  string `json:"seat" jsonschema:"row letter and number, for example A7"`
}

type SeatMap struct {
	Free     []string `json:"free" jsonschema:"seats anyone can hold"`
	YourHold []string `json:"your_holds" jsonschema:"seats this customer holds, awaiting payment"`
	Taken    int      `json:"taken" jsonschema:"seats held or booked by other customers"`
}

type HoldResult struct {
	Seat string `json:"seat"`
	Held bool   `json:"held"`
}
```

A tool is a typed function: context, the request, the decoded arguments in; a result struct out. `listSeats` asks the seat service and sorts each seat into free, yours or taken. Returning the struct is enough: the SDK sends it as structured content and as JSON text:

```go noverify title="cinema/cmd/cinema-mcp/main.go · lines 62–81"
func (c *cinema) listSeats(ctx context.Context, _ *mcp.CallToolRequest, in MovieArgs) (*mcp.CallToolResult, SeatMap, error) {
	ctx, cancel := c.as(ctx)
	defer cancel()
	resp, err := c.seats.ListSeats(ctx, &cinemav1.ListSeatsRequest{Movie: in.Movie})
	if err != nil {
		return nil, SeatMap{}, err
	}
	var m SeatMap
	for _, s := range resp.Seats {
		switch {
		case s.Status == cinemav1.SeatStatus_SEAT_STATUS_FREE:
			m.Free = append(m.Free, s.Id)
		case s.User == c.user && s.Status == cinemav1.SeatStatus_SEAT_STATUS_HELD:
			m.YourHold = append(m.YourHold, s.Id)
		default:
			m.Taken++
		}
	}
	return nil, m, nil // the SDK sends the struct as structured content, and as JSON text
}
```

`holdSeat` and `releaseSeat` translate gRPC status codes into the two kinds of failure MCP has. An expected problem (the seat is taken, doesn't exist, or you hold too many) becomes a **tool result** with `IsError` and a sentence the model can act on. Anything else is returned as an error. The distinction matters: a tool error is information for the model; a protocol error means the call itself failed:

```go noverify title="cinema/cmd/cinema-mcp/main.go · lines 83–117"
// holdSeat reports "taken" and "no such seat" as tool results with
// IsError set and a plain message the model can act on ("try another
// seat"). Any other error is returned as is; the SDK reports it as an
// IsError result too, with the error's text.
func (c *cinema) holdSeat(ctx context.Context, _ *mcp.CallToolRequest, in SeatArgs) (*mcp.CallToolResult, HoldResult, error) {
	ctx, cancel := c.as(ctx)
	defer cancel()
	_, err := c.seats.Hold(ctx, &cinemav1.HoldRequest{Movie: in.Movie, Seat: in.Seat})
	switch status.Code(err) {
	case codes.OK:
		return nil, HoldResult{Seat: in.Seat, Held: true}, nil
	case codes.AlreadyExists, codes.NotFound, codes.ResourceExhausted:
		return toolError(status.Convert(err).Message()), HoldResult{Seat: in.Seat}, nil
	default:
		return nil, HoldResult{}, err
	}
}

func (c *cinema) releaseSeat(ctx context.Context, _ *mcp.CallToolRequest, in SeatArgs) (*mcp.CallToolResult, HoldResult, error) {
	ctx, cancel := c.as(ctx)
	defer cancel()
	_, err := c.seats.Release(ctx, &cinemav1.ReleaseRequest{Movie: in.Movie, Seat: in.Seat})
	switch status.Code(err) {
	case codes.OK:
		return nil, HoldResult{Seat: in.Seat}, nil
	case codes.FailedPrecondition, codes.NotFound:
		return toolError(status.Convert(err).Message()), HoldResult{Seat: in.Seat}, nil
	default:
		return nil, HoldResult{}, err
	}
}

func toolError(msg string) *mcp.CallToolResult {
	return &mcp.CallToolResult{IsError: true, Content: []mcp.Content{&mcp.TextContent{Text: msg}}}
}
```

The resource is the seat map, addressed by URI. It's built for the model to read, so it contains only IDs and three statuses. The comment says why other customers' names are left out: they're personal data, and they're text anyone can set, which is exactly how an instruction gets smuggled to a model (Stop 5):

```go noverify title="cinema/cmd/cinema-mcp/main.go · lines 119–146"
func (c *cinema) seatMapResource(ctx context.Context, req *mcp.ReadResourceRequest) (*mcp.ReadResourceResult, error) {
	ctx, cancel := c.as(ctx)
	defer cancel()
	movie := strings.TrimSuffix(strings.TrimPrefix(req.Params.URI, "cinema://movies/"), "/seats")
	resp, err := c.seats.ListSeats(ctx, &cinemav1.ListSeatsRequest{Movie: movie})
	if err != nil {
		return nil, mcp.ResourceNotFoundError(req.Params.URI)
	}
	// Other customers' names never reach the model: they're personal data,
	// and they're text anyone can choose, so they can carry instructions.
	type seat struct {
		ID     string `json:"id"`
		Status string `json:"status"` // free, yours, or taken
	}
	var out []seat
	for _, s := range resp.Seats {
		st := "taken"
		switch {
		case s.Status == cinemav1.SeatStatus_SEAT_STATUS_FREE:
			st = "free"
		case s.User == c.user:
			st = "yours"
		}
		out = append(out, seat{s.Id, st})
	}
	b, _ := json.Marshal(out)
	return &mcp.ReadResourceResult{Contents: []*mcp.ResourceContents{{URI: req.Params.URI, MIMEType: "application/json", Text: string(b)}}}, nil
}
```

`newServer` registers everything. The annotations are hints to the host application: `list_seats` is read-only, `release_seat` is destructive, so a careful host asks the user before running it. They're hints, not enforcement: the enforcement is the seat service's own rules:

```go noverify title="cinema/cmd/cinema-mcp/main.go · lines 161–194"
func newServer(c *cinema) *mcp.Server {
	s := mcp.NewServer(&mcp.Implementation{Name: "cinema", Version: "v1.0.0"}, nil)
	t := true
	mcp.AddTool(s, &mcp.Tool{
		Name:        "list_seats",
		Description: "Show which seats are free for a film, which ones you hold, and how many are taken.",
		Annotations: &mcp.ToolAnnotations{ReadOnlyHint: true},
	}, c.listSeats)
	mcp.AddTool(s, &mcp.Tool{
		Name:        "hold_seat",
		Description: "Hold a free seat for you for two minutes while you pay. Fails if someone else has it.",
		Annotations: &mcp.ToolAnnotations{IdempotentHint: false, OpenWorldHint: &t},
	}, c.holdSeat)
	mcp.AddTool(s, &mcp.Tool{
		Name:        "release_seat",
		Description: "Give up a seat you hold, so others can take it.",
		Annotations: &mcp.ToolAnnotations{DestructiveHint: &t},
	}, c.releaseSeat)
	s.AddResourceTemplate(&mcp.ResourceTemplate{
		Name:        "seat-map",
		URITemplate: "cinema://movies/{movie}/seats",
		Description: "Every seat of a film's hall with its status and holder",
		MIMEType:    "application/json",
	}, c.seatMapResource)
	s.AddPrompt(&mcp.Prompt{
		Name:        "plan_night_out",
		Description: "Find seats together for a group",
		Arguments: []*mcp.PromptArgument{
			{Name: "movie", Description: "the film", Required: true},
			{Name: "party_size", Description: "how many people", Required: true},
		},
	}, planNightOut)
	return s
}
```

`main` requires `-user`, connects to the seat service, and serves over one of two transports. Over stdio, the assistant starts the program and talks on its standard input and output, which is why logs are sent to stderr: one stray `fmt.Println` on stdout would corrupt the protocol stream. With `-http` it serves Streamable HTTP, optionally stateless:

```go noverify title="cinema/cmd/cinema-mcp/main.go · lines 196–223"
func main() {
	user := flag.String("user", "", "the customer this server acts for (required)")
	grpcAddr := flag.String("cinema", "127.0.0.1:9091", "the cinema's gRPC address")
	httpAddr := flag.String("http", "", "serve Streamable HTTP on this address instead of stdio")
	stateless := flag.Bool("stateless", false, "HTTP: no sessions; every request stands alone")
	flag.Parse()
	if *user == "" {
		log.Fatal("-user is required: the server acts for exactly one customer")
	}
	conn, err := grpc.NewClient(*grpcAddr, grpc.WithTransportCredentials(insecure.NewCredentials()))
	if err != nil {
		log.Fatal(err)
	}
	server := newServer(&cinema{seats: cinemav1.NewSeatServiceClient(conn), user: *user})

	if *httpAddr != "" {
		h := mcp.NewStreamableHTTPHandler(func(*http.Request) *mcp.Server { return server },
			&mcp.StreamableHTTPOptions{Stateless: *stateless})
		srv := &http.Server{Addr: *httpAddr, Handler: h, ReadHeaderTimeout: 5 * time.Second}
		log.Printf("cinema-mcp for %s on http://%s", *user, *httpAddr)
		log.Fatal(srv.ListenAndServe())
	}
	// stdio: stdout carries only protocol messages; logs go to stderr.
	log.SetOutput(os.Stderr)
	if err := server.Run(context.Background(), &mcp.StdioTransport{}); err != nil {
		log.Fatal(err)
	}
}
```

The three kinds of thing an MCP server offers:

- **Tools** are actions the model may *choose* to call: `list_seats`, `hold_seat`, `release_seat`. Each is a typed Go function; `mcp.AddTool` generates its input schema from the argument struct (the `jsonschema` tags become descriptions the model reads) and its output schema from the result struct. **Annotations** tell the host how careful to be: `list_seats` is read-only; `release_seat` is destructive, so a host should ask the user before running it.
- **Resources** are data the *host or user* chooses to attach to the conversation, addressed by URI: the seat map at `cinema://movies/{movie}/seats`.
- **Prompts** are templates the *user* picks ("plan a night out"), with arguments.

The schema the model sees for `hold_seat` was generated from `SeatArgs`: both fields required, no others allowed:

```text
{"type":"object","properties":{"movie":{"type":"string","description":"the film, for example inception or dune"},
 "seat":{"type":"string","description":"row letter and number, for example A7"}},
 "required":["movie","seat"],"additionalProperties":false}
```

That's why `hold_seat` with only a movie was refused **before the handler ran**: the SDK validated the arguments against the schema. Every error the model can act on came back as a result with `isError`: taken, no such seat, missing argument. The only protocol error was the tool that doesn't exist.

One line should bother you. Alice held A7, then asked again and was told "seat is held or booked by someone else". She holds it herself. That's the in-memory store's answer (chapter 12's idempotent Hold only applies to the Redis store), and a person would shrug; a model may conclude it failed and hold another seat. Tool messages are instructions to a reader who believes them: make them exact.

## Transports

*Stop 4 of 6.*

### Step 1: stdio

Everything so far used **stdio**: the host starts the server as a subprocess and they exchange JSON lines over its stdin and stdout. It's the transport for tools running on the user's own machine: no network, no port, and the server lives exactly as long as the host needs it. One rule follows: stdout belongs to the protocol. A stray `fmt.Println` corrupts the stream, which is why `cinema-mcp` sends its logs to stderr.

### Step 2: Streamable HTTP

For a server other people or other machines use, MCP runs over HTTP: every message is a POST to one endpoint, and the answer comes back as JSON or as a short server-sent-events stream. `cinema-mcp -http` serves it with `mcp.NewStreamableHTTPHandler`, in two modes:

```text
$ mcpclient -http http://127.0.0.1:18193        # cinema-mcp -http, sessions (the default)
connected to cinema v1.0.0, protocol 2025-11-25
$ mcpclient -http http://127.0.0.1:18194        # cinema-mcp -http -stateless
connected to cinema v1.0.0, protocol 2026-07-28
```

With **sessions** (the default), the server hands out an `Mcp-Session-Id` and keeps state per session; its `server/discover` doesn't offer 2026-07-28, so the SDK client fell back to the legacy `initialize`. With **`Stateless: true`**, no session exists, and the new stateless revision is negotiated. A raw call to the stateless server:

```text
$ curl -si localhost:18194 -H 'Content-Type: application/json' -H 'Accept: application/json, text/event-stream' \
    -H 'MCP-Protocol-Version: 2026-07-28' -H 'Mcp-Method: tools/call' -H 'Mcp-Name: list_seats' -d '{"jsonrpc":"2.0","id":1,"method":"tools/call","params":{"_meta":{"io.modelcontextprotocol/protocolVersion":"2026-07-28","io.modelcontextprotocol/clientCapabilities":{}},"name":"list_seats","arguments":{"movie":"dune"}}}'
HTTP/1.1 200 OK
Cache-Control: no-cache, no-transform
Connection: keep-alive
Content-Type: text/event-stream
Transfer-Encoding: chunked

event: message
data: {"jsonrpc":"2.0","id":1,"result":{"_meta":{"io.modelcontextprotocol/serverInfo":{"name":"cinema","version":"v1.0.0"}},"content":[{"type":"text","text":"{\"free\":[\"A1\",\"A2\",\"A3\",\"A4\",\"A5\",\"A6\",\"B1\",\"B2\",\"B3\",\"B4\",\"B5\",\"B6\",\"C1\",\"C2\",\"C3\",\"C4\",\"C5\",\"C6\",\"D1\",\"D2\",\"D3\",\"D4\",\"D5\",\"D6\"],\"taken\":0,\"your_holds\":null}"}],"structuredContent":{"free":["A1","A2","A3","A4","A5","A6","B1","B2","B3","B4","B5","B6","C1","C2","C3","C4","C5","C6","D1","D2","D3","D4","D5","D6"],"taken":0,"your_holds":null},"resultType":"complete"}}
```

Getting there took two refusals, both real, both instructive: the first request, without an `Mcp-Method` header, got `400` and error -32020 "missing required Mcp-Method header"; the second, without `Mcp-Name`, got the same for the tool's name. The 2026 revision requires the method and tool name as **HTTP headers**, repeated from the JSON body (the SDK checks that they match). A proxy or gateway in front of the server can then route, rate-limit or authorize "who may call `release_seat`" from the headers alone, without parsing JSON-RPC.

## What the Model Reads

*Stop 5 of 6.*

### Step 1: text from strangers

Everything a tool or resource returns goes into the model's context, and a model can't reliably tell "data about seats" from "instructions to follow". Which parts of the cinema's data did the cinema not write? The holders' names: `X-User` is whatever the customer's client sends. So a customer holds C5 under a name written for assistants, and dan holds C6:

```text

201
$ curl -X POST -H 'X-User: dan' localhost:18100/movies/inception/seats/C6/hold
201
```

```text
resource   {"ID":"A7","Status":"held","User":"bob"}
```

## Authority

*Stop 6 of 6.*

### Step 1: why the releases failed

The same `mcpread` run ended with the releases a fooled model would attempt:

```text
release_seat C5 as alice → isError=true you don't hold this seat (or your hold expired)
release_seat C6 as alice → isError=true you don't hold this seat (or your hold expired)
```

Nothing in `cinema-mcp` detected the injection. The releases failed because of where authority lives: `cinema-mcp` was started with `-user alice` and sends that identity on every gRPC call, and the cinema's store only lets a hold's holder release it. The model chooses *which* tool to call and with *what* arguments; it never chooses *who* it's acting as. So the worst a fooled model can do is what Alice herself could do: hold or release her own seats. For destructive tools that are within her authority (`release_seat` on her own seat), the tool's `destructiveHint` tells the host to ask Alice before running it.

This is the rule for any MCP server: **the tool's authority is the user's, enforced by the system behind the tool**, never by the prompt, and never by the model's judgement. A server that took `user` as a tool *argument* would let any text the model reads choose whose seats to release.

### Step 2: show less

Authority limits the damage. Data minimisation limits the exposure. The seat map resource had no reason to show other customers' names: they're personal data Alice's assistant doesn't need, and they're exactly the field strangers control. The resource now reports each seat as `free`, `yours` or `taken`:

```text
resource   {"id":"A7","status":"taken"}
resource   {"id":"C5","status":"taken"}
resource   {"id":"C6","status":"taken"}
list_seats  taken=3 your_holds=<nil>
```

The note is gone, and the assistant still has everything it needs to find two seats together. `list_seats` already worked this way (a count of taken seats, never names), which is why its output was clean all along.

The same thinking applies beyond injected text. A remote MCP server is also an OAuth-protected API when users sign in to it; the MCP specification's authorization section describes it, and the usual rules apply: exact redirect URIs, consent per client, and tokens scoped to the MCP server, never passed through to the services behind it.

## Exercises

These use `cinema-mcp`, `mcpclient` and the cinema service from this chapter.

<Exercise n={1} title="Write a tool description" level="easy">

Rewrite `hold_seat`'s description and error messages so a model makes fewer wrong moves. What should the "taken" message say when the caller already holds the seat?

<Solution>

Description: say what it does, the constraints, and what to do on failure: "Hold one seat for the user for 2 minutes. Seats are like A7 (rows A–E, numbers 1–8 for inception). If the seat is taken, pick another free seat from list_seats; don't retry the same one." When the caller already holds the seat, the result should be a success ("you already hold A7; it's reserved until 20:14") rather than "held by someone else", which invites the model to hold a second seat. That needs the idempotent Hold from chapter 12 (return the holder, or treat "held by me" as success) for the memory store too.

</Solution>

</Exercise>

<Exercise n={2} title="Find the untrusted text" level="easy">

List every field `cinema-mcp` returns to the model, and mark who wrote each: the cinema, the user, or a third party.

<Solution>

Seat IDs and statuses: the cinema. Movie names in the resource URI: the user (they're echoed back). Error messages: the cinema's code, but some include inputs (a movie name the user or model typed). Holder names: third parties, removed from the resource in stop 6. The prompt's text: the server's author, with `movie` and `party_size` from the user. Anything third parties control should be omitted, or clearly delimited and treated as data by the host; anything the user controls is lower risk, since the user already controls the conversation.

</Solution>

</Exercise>

<Exercise n={3} title="Sessions or stateless?" level="medium">

Run two instances of `cinema-mcp -http` behind a round-robin load balancer (chapter 12's approach, or two ports and a simple Go reverse proxy). Connect `mcpclient` with sessions, then with `-stateless`. What breaks, and why?

<Solution>

With sessions, the `initialize` handshake lands on instance 1 and the next request on instance 2, which doesn't know the `Mcp-Session-Id` and rejects it (404 for an unknown session): sessions need sticky routing. Stateless mode works on either instance for every request, because each request carries its own protocol version and capabilities. The price: no server-to-client notifications that depend on a session, and no per-session state. The cinema's tools need none, since their state is in the cinema.

</Solution>

</Exercise>

<Exercise n={4} title="A confirmation for release" level="medium">

`release_seat` is marked destructive. Using the go-sdk's elicitation support (the server asks the user a question through the client), make it ask "Release A7 for Dune on Friday?" and only release on yes. What does the host have to support?

<Solution>

In the handler, call the session's elicitation method with a message and a schema for the answer (a boolean), and release only if the user accepts. The client must declare the elicitation capability and implement the handler that shows the question to the user; a client without it gets an error the server should turn into "can't confirm; not released". It's stronger than `destructiveHint`, which is only advice to the host: the server itself refuses to act without an answer from the user, not from the model.

</Solution>

</Exercise>

<Exercise n={5} title="Per-user HTTP" level="hard">

`cinema-mcp -http` acts for one fixed user, so each customer would need their own server. Design a single HTTP server that acts for whoever is signed in. Where does the identity come from, and what must never set it?

<Solution>

From the HTTP request's credentials: an OAuth access token issued to this MCP server for the signed-in user, verified on every request (issuer, audience = this server, expiry), with the user taken from the token's subject. Pass that identity into the tool handlers through the request context (the SDK gives handlers the request, and the stateless handler builds a server per request if needed), and on to the cinema as `x-user`, ideally as a token the cinema verifies itself. What must never set it: tool arguments, prompt text, resource content, or anything else the model produces. The token must also not be forwarded as is to the cinema if it was issued for the MCP server: the cinema should get its own credential (token exchange), so a leaked MCP token can't be replayed elsewhere.

</Solution>

</Exercise>

<Recap>

- **MCP is JSON-RPC 2.0**: requests with ids, responses, notifications without, standard error codes. A real session's wire log showed a tool that failed (a result with `isError`, for the model) next to an unknown tool (a -32602 protocol error, for the programmer).
- **Discovery changed in 2026**: the legacy `initialize` / `notifications/initialized` handshake made each connection a session; the 2026-07-28 revision's `server/discover` and per-request `_meta` let any instance answer any request. The SDK tries the new one and falls back.
- **Tools, resources, prompts** in the go-sdk are typed Go functions; schemas are generated from structs and enforced before the handler runs. Annotations (`readOnlyHint`, `destructiveHint`) guide the host. Tool messages are read by a believer: make them exact (the in-memory store's "held by someone else" for Alice's own seat misleads).
- **Transports**: stdio (stdout is the wire; log to stderr) and Streamable HTTP. With sessions, the new revision wasn't offered; stateless mode negotiated 2026-07-28 and required `Mcp-Method` and `Mcp-Name` headers, so gateways can route by tool without parsing JSON.
