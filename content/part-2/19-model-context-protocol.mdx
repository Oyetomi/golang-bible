<Define term="MCP (Model Context Protocol)" since="The Model Context Protocol (MCP) in Go (Part 2, Chapter 19)">
**MCP** is an open protocol that standardizes how applications give context and capabilities to large language models. A model-facing application (the **host**) connects to one or more **servers**, each of which exposes **tools** (functions the model can call), **resources** (data the model can read), and **prompts** (reusable templates). We need it because every "let the model use our API" integration was being rebuilt from scratch per model and per tool — MCP makes the tool side write the integration once and every MCP-speaking client gets it for free.
</Define>

<Define term="Host / Client / Server" since="The Model Context Protocol (MCP) in Go (Part 2, Chapter 19)">
Three roles. The **host** is the AI application the user interacts with (a chat app, an IDE, an agent). Inside the host runs one **client** per connection — the client manages a single 1:1 session with one server. The **server** is the program that exposes tools/resources/prompts (your `get_balance` server). One host can run many clients, each wired to a different server. Keep the vocabulary straight: *client* and *server* are the two ends of one JSON-RPC session; *host* is the app that owns the clients.
</Define>

<Define term="JSON-RPC 2.0" since="The Model Context Protocol (MCP) in Go (Part 2, Chapter 19)">
**JSON-RPC 2.0** is a tiny, transport-agnostic RPC convention: every message is a JSON object with `"jsonrpc":"2.0"`. A **request** has an `id`, a `method`, and optional `params`, and expects a matching **response** (`result` or `error`). A **notification** is a request with **no `id`** and expects no response. That is the entire format — MCP is JSON-RPC plus an agreed-upon set of method names and parameter shapes.
</Define>

## Why MCP Exists

Before MCP, "let the model call our tools" looked like this: every AI app vendor invented its own function-calling format, and every tool team wrote a bespoke adapter for each app that wanted in. That is the **M×N problem** — M apps times N tools equals a quadratic pile of glue code that nobody owns and everybody breaks.

**On the job:** you wire your ledger into one assistant with a custom HTTP shim, then a second team wants the same data in their IDE agent, then a third in a support bot — and now you maintain three subtly-different shims that all break the day you rename a field.

MCP fixes this the same way gRPC fixed service-to-service contracts: **define the interface once, in a standard, and generate or reuse the plumbing.** Write one MCP server for the ledger and *every* MCP-speaking host — today's and next year's — can use it without you writing another line of integration code.

<Callout kind="note" title="MCP is not a replacement for gRPC">
gRPC connects *your* services to *each other* with a compiled, versioned `.proto`. MCP connects an *AI host* to *tools and data*, with runtime discovery so the model can find capabilities it was never compiled against. Different jobs. A Meridian backend uses gRPC between the payments and ledger services, *and* an MCP server so a support assistant can safely read a balance. They coexist.
</Callout>

## JSON-RPC 2.0

Everything in MCP is a JSON-RPC 2.0 message. Learn the three shapes and you have learned the wire format.

<ConceptGrid cols={3}>
  <ConceptCard label="Request">Has `id`, `method`, optional `params`. Expects exactly one response with the same `id`. Example method: `tools/call`.</ConceptCard>
  <ConceptCard label="Response">Has the request's `id` and EITHER a `result` OR an `error` — never both. The `error` is an object with an integer `code` and a `message`.</ConceptCard>
  <ConceptCard label="Notification">A request with NO `id`. Fire-and-forget — the receiver must not reply. Example: `notifications/initialized`, `notifications/cancelled`.</ConceptCard>
  <Gotcha>The presence of `id` is the only thing that distinguishes a request from a notification. Reply to a notification and you have violated the spec; fail to reply to a request and the client hangs forever. When you decode, check for `id` first.</Gotcha>
</ConceptGrid>

Here is the format made concrete — encode a request, encode a notification, then decode and classify. Notice the request body is identical to a notification except for the `id`:

<GoPlayground>

```go
package main

import (
	"encoding/json"
	"fmt"
)

// A JSON-RPC 2.0 message. A request carries an id and expects a response;
// a notification has the same shape minus the id and expects none.
type Request struct {
	JSONRPC string          `json:"jsonrpc"`
	ID      *int            `json:"id,omitempty"`
	Method  string          `json:"method"`
	Params  json.RawMessage `json:"params,omitempty"`
}

func main() {
	id := 1
	req := Request{
		JSONRPC: "2.0",
		ID:      &id,
		Method:  "tools/call",
		Params:  json.RawMessage(`{"name":"get_balance","arguments":{"account_id":"acct-001"}}`),
	}
	b, _ := json.Marshal(req)
	fmt.Println("request on the wire:")
	fmt.Println(string(b))

	note := Request{JSONRPC: "2.0", Method: "notifications/initialized"}
	nb, _ := json.Marshal(note)
	fmt.Println("\nnotification (no id -> no response expected):")
	fmt.Println(string(nb))

	var in Request
	_ = json.Unmarshal(b, &in)
	fmt.Printf("\ndecoded: method=%s  isNotification=%v\n", in.Method, in.ID == nil)
}
```

</GoPlayground>

The `*int` for `ID` is deliberate: a nil pointer means "the JSON had no `id` key" — i.e. a notification. A plain `int` would default to `0` and you could not tell a notification from a request whose id happens to be `0`. Pointer-or-nil is the idiomatic Go way to model "field may be absent" (and it is exactly why the typed-nil chapter mattered).

<Define term="JSON-RPC error codes" since="The Model Context Protocol (MCP) in Go (Part 2, Chapter 19)">
JSON-RPC reserves a small range of negative integer **error codes**: `-32700` parse error, `-32600` invalid request, `-32601` **method not found**, `-32602` **invalid params**, `-32603` internal error. MCP adds its own, such as `-32002` **resource not found**. These signal *protocol* failures — a method that does not exist, params that do not parse. They are distinct from a *tool* that ran fine but returned a business error (that is `isError` inside a normal `result`, covered later). Confusing the two is the single most common MCP bug.
</Define>

## Lifecycle & Capabilities

An MCP session does not just start sending `tools/call`. It opens with a three-step **handshake** that negotiates the protocol version and tells each side what the other can do. Skip it and a compliant server will refuse every later request.

1. The client sends an **`initialize`** request: its preferred `protocolVersion`, its `capabilities`, and `clientInfo`.
2. The server responds with the `protocolVersion` it will actually use, its own `capabilities`, and `serverInfo`.
3. The client sends an **`initialized`** notification — "handshake done, I'm ready." Only now may normal requests flow.

<Define term="Capability negotiation" since="The Model Context Protocol (MCP) in Go (Part 2, Chapter 19)">
**Capability negotiation** is the part of `initialize` where each side declares which optional features it supports, as a nested object. A server that offers tools advertises `capabilities.tools`; one that can push list-changed notifications advertises `capabilities.tools.listChanged: true`. The client advertises *its* capabilities too — `sampling` (it can run the model on the server's behalf), `roots` (it can expose filesystem roots), `elicitation` (it can ask the user for input). Neither side may use a feature the other did not advertise. It is the same discipline as HTTP content negotiation, but bidirectional.
</Define>

The version is a **date string**, and `2025-06-18` is the revision this chapter targets. Negotiation is simple: the client asks for a version; if the server supports it, it echoes it back; otherwise the server returns its own latest and the client decides whether to proceed. Here is that logic in isolation:

<GoPlayground>

```go
package main

import "fmt"

// negotiateVersion models MCP's initialize handshake: the client asks for a
// protocol version; the server echoes it if supported, else offers its own
// latest. supported is sorted oldest -> newest.
func negotiateVersion(requested string, supported []string) string {
	for _, v := range supported {
		if v == requested {
			return requested
		}
	}
	return supported[len(supported)-1]
}

func main() {
	server := []string{"2024-11-05", "2025-03-26", "2025-06-18"}
	fmt.Println(negotiateVersion("2025-06-18", server)) // exact match -> echo
	fmt.Println(negotiateVersion("2030-01-01", server)) // unknown    -> server latest
	fmt.Println(negotiateVersion("2024-11-05", server)) // older,     -> still echoed
}
```

</GoPlayground>

<Callout kind="warn" title="The version is also an HTTP header (over Streamable HTTP)">
After initialization, MCP-over-HTTP clients must send the negotiated version on every request as the `MCP-Protocol-Version` header. A server that gets a request with a missing or unsupported version header should reject it with `400 Bad Request`. Over stdio there is no header — the version negotiated in `initialize` governs the whole process lifetime.
</Callout>

## Tools, Resources & Prompts

A server exposes three kinds of capability. The distinction is **who is in control** — and getting that wrong is a security and UX bug, not a style choice.

<ConceptGrid cols={3}>
  <ConceptCard label="Tools (model-controlled)">Functions the model decides to call to take an action or fetch live data: `get_balance`, `post_transfer`, `search_transactions`. Discovered via `tools/list`, invoked via `tools/call`. The model chooses when — so tools that mutate state need authorization and human-in-the-loop.</ConceptCard>
  <ConceptCard label="Resources (app-controlled)">Data the host attaches as context, addressed by URI: a file, a record, `ledger://accounts/acct-001`. Listed via `resources/list`, fetched via `resources/read`. The *application* decides what to include — resources are read-only nouns, not verbs.</ConceptCard>
  <ConceptCard label="Prompts (user-controlled)">Reusable, parameterized message templates the user invokes deliberately — a slash-command like "/reconcile-account". Listed via `prompts/list`, expanded via `prompts/get`. The *user* picks them.</ConceptCard>
  <Gotcha>Do not model a state-changing action as a resource, and do not hide a destructive action inside an innocuously-named tool. A `resources/read` must be a side-effect-free GET. `post_transfer` must be a tool, gated behind explicit user approval. The control axis (model/app/user) maps directly onto your authorization model.</Gotcha>
</ConceptGrid>

The Meridian ledger server will offer one tool — `get_balance` — and, as an exercise, one resource — `ledger://accounts/{id}`. We deliberately do **not** expose `post_transfer` as an auto-callable tool; moving money is not something a model gets to do without a human pressing a button.

<Callout kind="note" title="The client side has capabilities too">
Three optional features flow the *other* way, from server to client (the client advertises them at `initialize`): **sampling** lets a server ask the host to run an LLM completion on its behalf (so the server can be "agentic" without its own API key); **roots** let the client expose filesystem boundaries the server may operate within; **elicitation** (added in 2025-06-18) lets a server ask the user for additional input mid-session. We focus on the server primitives, but know these exist — sampling in particular is how an MCP server stays model-agnostic.
</Callout>

## Building a Server

Enough theory. We build an MCP server with the standard library and nothing else — because the best way to understand a protocol is to implement it.

The stdio transport is the simplest: the server reads JSON-RPC messages from `stdin`, one per line, and writes responses to `stdout`, one per line. (The host launches the server as a subprocess and owns those pipes.) `stderr` is free for logging.

Here is a complete, runnable Meridian ledger server. We drive it from an in-memory reader so it runs under `go run` with no live host attached — but `serve` reads from any `io.Reader`, so swapping in `os.Stdin` is a one-line change:

<GoPlayground>

```go
package main

import (
	"bufio"
	"bytes"
	"encoding/json"
	"fmt"
	"io"
	"os"
	"strings"
)

type Request struct {
	JSONRPC string          `json:"jsonrpc"`
	ID      *int            `json:"id,omitempty"`
	Method  string          `json:"method"`
	Params  json.RawMessage `json:"params,omitempty"`
}

type Response struct {
	JSONRPC string    `json:"jsonrpc"`
	ID      *int      `json:"id,omitempty"`
	Result  any       `json:"result,omitempty"`
	Error   *RPCError `json:"error,omitempty"`
}

type RPCError struct {
	Code    int    `json:"code"`
	Message string `json:"message"`
}

type Tool struct {
	Name        string `json:"name"`
	Description string `json:"description"`
}

type Content struct {
	Type string `json:"type"`
	Text string `json:"text"`
}

type CallResult struct {
	Content []Content `json:"content"`
	IsError bool      `json:"isError"`
}

type CallParams struct {
	Name      string         `json:"name"`
	Arguments map[string]any `json:"arguments"`
}

// serve runs the stdio transport loop: one JSON-RPC message per line, in and out.
func serve(r io.Reader, w io.Writer, balances map[string]int64) {
	sc := bufio.NewScanner(r)
	enc := json.NewEncoder(w)
	for sc.Scan() {
		line := sc.Bytes()
		if len(bytes.TrimSpace(line)) == 0 {
			continue
		}
		var req Request
		if err := json.Unmarshal(line, &req); err != nil {
			continue // a real server would emit a -32700 parse error
		}
		resp := handle(req, balances)
		if req.ID == nil {
			continue // a notification gets no response
		}
		_ = enc.Encode(resp) // Encode appends the newline delimiter
	}
}

func handle(req Request, balances map[string]int64) Response {
	resp := Response{JSONRPC: "2.0", ID: req.ID}
	switch req.Method {
	case "initialize":
		resp.Result = map[string]any{
			"protocolVersion": "2025-06-18",
			"serverInfo":      map[string]any{"name": "meridian-ledger", "version": "1.0.0"},
			"capabilities":    map[string]any{"tools": map[string]any{}},
		}
	case "tools/list":
		resp.Result = map[string]any{"tools": []Tool{
			{Name: "get_balance", Description: "Balance (minor units) for a Meridian account."},
		}}
	case "tools/call":
		var p CallParams
		_ = json.Unmarshal(req.Params, &p)
		acct, _ := p.Arguments["account_id"].(string)
		if bal, ok := balances[acct]; ok {
			resp.Result = CallResult{Content: []Content{{Type: "text", Text: fmt.Sprintf("balance: %d", bal)}}}
		} else {
			// A TOOL error (the model can see it), NOT a protocol error.
			resp.Result = CallResult{Content: []Content{{Type: "text", Text: "account not found: " + acct}}, IsError: true}
		}
	default:
		// A PROTOCOL error: this method does not exist.
		resp.Error = &RPCError{Code: -32601, Message: "method not found: " + req.Method}
	}
	return resp
}

func main() {
	// Canned session standing in for the host's stdin. In production:
	//   serve(os.Stdin, os.Stdout, balances)
	in := strings.NewReader(strings.Join([]string{
		`{"jsonrpc":"2.0","id":1,"method":"initialize","params":{}}`,
		`{"jsonrpc":"2.0","method":"notifications/initialized"}`,
		`{"jsonrpc":"2.0","id":2,"method":"tools/list"}`,
		`{"jsonrpc":"2.0","id":3,"method":"tools/call","params":{"name":"get_balance","arguments":{"account_id":"acct-001"}}}`,
		`{"jsonrpc":"2.0","id":4,"method":"tools/call","params":{"name":"get_balance","arguments":{"account_id":"ghost"}}}`,
		`{"jsonrpc":"2.0","id":5,"method":"ledger/drop"}`,
	}, "\n"))
	serve(in, os.Stdout, map[string]int64{"acct-001": 5000, "acct-002": 12345})
}
```

</GoPlayground>

Run it and read the output carefully. Five inputs, **four** responses — the `notifications/initialized` line produced none, exactly as the spec demands. The unknown account came back as a `result` with `"isError":true` (a tool failure the model can reason about). The unknown *method* came back as a JSON-RPC `error` with `-32601` (a protocol failure). That distinction is the whole point.

<UnderTheHood title="stdio framing — why newline-delimited JSON, and what changed in 2025-06-18">

MCP's stdio transport frames messages as **newline-delimited JSON**: one complete JSON-RPC object per line, and a message **may not contain an embedded newline**. That is why `json.Encoder.Encode` is the right tool — it writes the object followed by exactly one `\n`, and a `bufio.Scanner` on the other side reads exactly one object per `Scan()`. No length prefix, no framing header.

This is a deliberate contrast with the **Language Server Protocol** (LSP), which also rides JSON-RPC but frames with HTTP-style `Content-Length:` headers because LSP messages routinely contain newlines (source code). MCP forbids embedded newlines so it can use the simpler line framing. If your tool output needs newlines, they must be *inside* JSON string values (where `json.Marshal` escapes them as `\n`), never raw bytes on the wire.

Two more wire facts worth knowing:
- **Batching was removed.** Earlier MCP revisions inherited JSON-RPC's optional *batch* form (a JSON array of messages). The `2025-06-18` revision **removed** batching — every message is a single object. Do not send arrays.
- **stdout is sacred.** Only valid MCP messages may go to `stdout`. A stray `fmt.Println("debug")` corrupts the stream and breaks the session. Log to `stderr` (or a file) — always. This is the number-one beginner mistake when writing a stdio server in any language.

As of Go 1.26, `bufio.Scanner` defaults to a 64 KB max token size; a tool returning a large payload over stdio needs `scanner.Buffer(...)` to raise it, or it will silently stop at the first oversized line.

</UnderTheHood>

## Building a Client

The client side is the mirror image: it writes requests to the server's stdin and reads responses from its stdout, matching them by `id`. The interesting work is **interpreting the result** — especially honoring `isError`.

<GoPlayground>

```go
package main

import (
	"encoding/json"
	"fmt"
)

type Content struct {
	Type string `json:"type"`
	Text string `json:"text"`
}

func main() {
	// The client opens the session by announcing its protocol version and identity.
	initReq := map[string]any{
		"jsonrpc": "2.0", "id": 1, "method": "initialize",
		"params": map[string]any{
			"protocolVersion": "2025-06-18",
			"capabilities":    map[string]any{},
			"clientInfo":      map[string]any{"name": "meridian-support-bot", "version": "0.1.0"},
		},
	}
	b, _ := json.MarshalIndent(initReq, "", "  ")
	fmt.Println("client -> server (initialize):")
	fmt.Println(string(b))

	// Later, the client decodes a tools/call response and surfaces the result.
	raw := []byte(`{"jsonrpc":"2.0","id":3,"result":{"content":[{"type":"text","text":"balance: 5000"}],"isError":false}}`)
	var resp struct {
		Result struct {
			Content []Content `json:"content"`
			IsError bool      `json:"isError"`
		} `json:"result"`
	}
	_ = json.Unmarshal(raw, &resp)
	fmt.Println("\nclient interprets the tool result:")
	if resp.Result.IsError {
		fmt.Println("  tool reported an error — do NOT trust the text as data")
	}
	for _, c := range resp.Result.Content {
		fmt.Println("  tool said:", c.Text)
	}
}
```

</GoPlayground>

The `isError` check is not optional politeness — it is correctness. When a tool fails, the `content` text is an *error message*, not data. A client that ignores `isError` and feeds "account not found: ghost" to the model as if it were a balance has just hallucinated a fact into a financial conversation. Check the flag, branch on it.

<Callout kind="pro" title="Match responses to requests by id — always">
Over a real transport, responses can arrive out of order (the server may answer a fast request before a slow one). The client must keep a map of in-flight `id -> waiting caller` and dispatch each response by its `id`, not assume FIFO. The official SDK does this for you; if you hand-roll a client, a `map[int]chan Response` guarded by a mutex is the standard pattern (you built exactly this shape in the concurrency chapters).
</Callout>

## stdio & Streamable HTTP

MCP defines two standard transports. Pick by *where the server runs*.

<ConceptGrid cols={2}>
  <ConceptCard label="stdio (local subprocess)">The host launches the server as a child process and talks over its stdin/stdout pipes. Zero network, zero ports, OS-level process isolation, trivial auth (it is your own child process). The default for local tools: a filesystem server, a git server, a local database tool. This is what we built above.</ConceptCard>
  <ConceptCard label="Streamable HTTP (remote)">The server is a web service; the client POSTs JSON-RPC to a single endpoint (e.g. `/mcp`). The server may answer with a plain JSON response OR upgrade to a Server-Sent Events (SSE) stream to push multiple messages and server-initiated requests. The choice for remote, multi-user, or hosted servers.</ConceptCard>
  <Gotcha>Streamable HTTP **replaced** the old "HTTP+SSE" two-endpoint transport from the 2024-11-05 revision. New servers implement Streamable HTTP (one endpoint, optional streaming upgrade). And the moment your MCP server listens on a network socket, every Part 2 security rule applies: authenticate (OAuth 2.1), validate `Origin` to stop DNS-rebinding, and bind to localhost for local servers.</Gotcha>
</ConceptGrid>

<Define term="Streamable HTTP" since="The Model Context Protocol (MCP) in Go (Part 2, Chapter 19)">
**Streamable HTTP** is MCP's transport for remote servers. The client sends each JSON-RPC message as an HTTP `POST` to one endpoint. The server responds either with a single `application/json` body (request/response) or by switching to a `text/event-stream` (SSE) so it can stream many messages back and issue its own server-to-client requests (e.g. sampling). An optional `Mcp-Session-Id` header, minted by the server at `initialize`, ties subsequent requests to a session. It supersedes the deprecated HTTP+SSE transport.
</Define>

The framing differs but the *messages are identical* — the same `initialize`, `tools/list`, `tools/call` JSON objects you already built. That is the elegance: write your tool logic once, and switching transport is a wiring change, not a rewrite.

## The Official Go SDK

You now understand every byte. In production you would not hand-roll the dispatch loop — you would use the official **`github.com/modelcontextprotocol/go-sdk`** (a collaboration between the MCP team and the Go team; stable at v1 as of late 2025). It handles framing, id-matching, capability negotiation, schema generation, and both transports. Your job shrinks to *writing the tool*.

A complete server is a handful of lines. The SDK reflects your typed input struct into a JSON Schema, so the model gets a typed contract for free:

```go
// Non-runnable here: requires github.com/modelcontextprotocol/go-sdk.
package main

import (
	"context"
	"log"

	"github.com/modelcontextprotocol/go-sdk/mcp"
)

// The tool's input. The jsonschema tags become the tool's advertised schema.
type BalanceInput struct {
	AccountID string `json:"account_id" jsonschema:"the Meridian account id, e.g. acct-001"`
}

type BalanceOutput struct {
	MinorUnits int64 `json:"minor_units" jsonschema:"balance in the smallest currency unit"`
}

// A typed tool handler. The SDK decodes arguments into BalanceInput and encodes
// the returned BalanceOutput — no manual json.Unmarshal, no content plumbing.
func getBalance(ctx context.Context, req *mcp.CallToolRequest, in BalanceInput) (
	*mcp.CallToolResult, BalanceOutput, error,
) {
	bal, ok := lookup(in.AccountID) // your real data access
	if !ok {
		// A tool error: returned in the result, visible to the model.
		return &mcp.CallToolResult{IsError: true}, BalanceOutput{}, nil
	}
	return nil, BalanceOutput{MinorUnits: bal}, nil
}

func main() {
	server := mcp.NewServer(&mcp.Implementation{Name: "meridian-ledger", Version: "1.0.0"}, nil)
	mcp.AddTool(server, &mcp.Tool{Name: "get_balance", Description: "Balance for an account."}, getBalance)

	// Run over stdin/stdout until the host disconnects.
	if err := server.Run(context.Background(), &mcp.StdioTransport{}); err != nil {
		log.Fatal(err)
	}
}
```

The client is just as tight — connect over a transport, then call:

```go
// Non-runnable here: requires github.com/modelcontextprotocol/go-sdk.
client := mcp.NewClient(&mcp.Implementation{Name: "meridian-support-bot", Version: "0.1.0"}, nil)

// Launch the server as a subprocess and speak stdio to it.
transport := &mcp.CommandTransport{Command: exec.Command("meridian-ledger")}
session, err := client.Connect(ctx, transport, nil)
if err != nil {
	log.Fatal(err)
}
defer session.Close()

res, err := session.CallTool(ctx, &mcp.CallToolParams{
	Name:      "get_balance",
	Arguments: map[string]any{"account_id": "acct-001"},
})
if err != nil || res.IsError {
	log.Fatal("get_balance failed")
}
for _, c := range res.Content {
	if t, ok := c.(*mcp.TextContent); ok {
		log.Print(t.Text)
	}
}
```

Serving the *same* server over Streamable HTTP for remote clients is one wrapper — the tool code does not change:

```go
// Non-runnable here: requires github.com/modelcontextprotocol/go-sdk.
handler := mcp.NewStreamableHTTPHandler(func(r *http.Request) *mcp.Server {
	return server // reuse one server for every session (or build per-request)
}, nil)
http.Handle("/mcp", handler)
log.Fatal(http.ListenAndServe(":8080", handler))
```

<UnderTheHood title="How AddTool turns a Go struct into a model-visible schema">

`mcp.AddTool(server, tool, getBalance)` does something the hand-rolled version did not: it **reflects** the handler's input type (`BalanceInput`) at registration time and generates a JSON Schema from its fields and `jsonschema:"..."` struct tags. That schema is what `tools/list` returns in each tool's `inputSchema`, and it is how the model knows `get_balance` takes a string `account_id` and what it means.

This is the same generics-and-reflection machinery you met in the sharp-tools chapter, put to elegant use: a single generic `AddTool[In, Out]` constrains the handler signature at compile time, while `reflect` walks the `In` type at runtime to emit the schema. You get a compile-checked Go function *and* a runtime-discoverable contract from one declaration — no `.proto`, no codegen step.

The SDK also enforces the protocol invariants you had to remember by hand: it never replies to a notification, it matches responses to requests by id (so concurrent `CallTool`s are safe), it rejects calls made before `initialize`, and on the HTTP transport it validates the `MCP-Protocol-Version` header. The hand-rolled version taught you *what* it does; the SDK is what you ship. As of the v1 release the API above is stable; track the module's release notes for `2025-06-18`+ revisions.

</UnderTheHood>

## Security & the Confused Deputy

Here is where most MCP deployments get it wrong, and where Meridian cannot afford to. An MCP server is a bridge between an AI model — which will faithfully do whatever a cleverly-worded input tells it — and your real systems. That is a security boundary, and you defend it like one.

<Define term="Confused deputy" since="The Model Context Protocol (MCP) in Go (Part 2, Chapter 19)">
A **confused deputy** is a privileged program tricked into misusing its authority on behalf of a less-privileged party. In MCP: your server holds credentials to the ledger; the model holds none. If the server runs whatever the model asks without checking *whose* authority applies, an attacker who can influence the model's input (prompt injection) can make the server act with the *server's* privileges. The fix is the deputy must check authorization for the *actual end user*, never act on the model's say-so alone.
</Define>

### The other confused deputy: the OAuth proxy itself

The deputy above is confused at the *tool* boundary — the model tricks the server into misusing its ledger credentials. There is a second one a layer down, at the *auth* boundary: the very "OAuth 2.1" the network-surface card told you to bolt on can itself become the confused deputy. This is not hypothetical. It is the [**Confused Deputy Problem** in the MCP security spec](https://modelcontextprotocol.io/specification/2025-06-18/basic/security_best_practices), and it has shipped — `CVE-2026-27124` (High) was exactly this bug in a widely-used MCP framework's OAuth proxy.

Here is the shape. An MCP server rarely runs its own identity provider; it acts as an **OAuth proxy** in front of a real upstream SSO so a tool can call the third-party API *as you*. To let clients like Claude Desktop bootstrap without out-of-band setup, the proxy turns on **Dynamic Client Registration (DCR)** — anyone can `POST /register` a `redirect_uri`. But the proxy is a *single* client to the upstream: it holds **one fixed `client_id`**, and each DCR "registration" is really just a `redirect_uri` stored behind that shared client. The upstream cannot tell the registrations apart — they are all `mcp-proxy`. So the proxy's own consent check is the *only* thing standing between a victim's login and an attacker's callback.

Now the trap. Once a victim has logged in through the proxy once, the upstream sets a **consent cookie** for `mcp-proxy`. An attacker registers `redirect_uri: attacker.example` via open DCR, then sends the victim one link to the proxy's own `/authorize`. The browser rides that cookie: the upstream sees its own client, finds the cookie, **skips the consent screen**, and mints a real code for the victim's account. The proxy receives it and — if it never checks *whether this user approved this client* — redirects it straight to `attacker.example`. One click, no phishing page, no look-alike domain: the victim authenticated on the real SSO with real MFA, which is exactly what makes the stolen token real. (The OAuth mechanics — the code flow and exact `redirect_uri` matching — are in the **OAuth/OIDC chapter** (ch35).)

**And PKCE cannot save you here.** PKCE (ch35) defends a *client* whose code is intercepted by a third party: the interceptor never saw the `code_verifier`, so the stolen code is dead. But in this attack the attacker *is* the registered client. It picks the verifier, hashes it into the `code_challenge` it sends, and presents that same verifier at the token exchange — it owns both halves. The victim never touches the challenge, the verifier, or the code; they are the *authentication material*, not a participant in the handshake. PKCE works exactly as specified and proves nothing about consent. The missing control is not a stronger secret — it is the proxy asking "do you approve *this* client?" and binding the answer to the `redirect_uri` before it ever forwards you upstream.

That binding is the whole fix. Record a per-user, per-client consent decision on the proxy's *own* screen, and refuse to deliver a code unless the callback matches a decision this user actually made:

<GoPlayground>

```go
package main

import "fmt"

// The MCP proxy sits in front of ONE real upstream SSO with a single fixed
// client_id. Dynamic Client Registration lets anyone register a redirect_uri
// behind that shared client, and the upstream — seeing its own cookie — skips
// consent. So the proxy's own consent + redirect_uri check is the ONLY thing
// between a victim's login and an attacker's callback.

type pendingAuth struct {
	userID      string // filled in after the victim authenticates upstream
	clientRegID string // which DCR registration initiated this flow
	redirectURI string // the redirect_uri that registration asked for
	code        string // the code the upstream SSO minted for userID
}

// consent records a per-user, per-client decision the user made on the
// PROXY's OWN screen — not the upstream's cookie-skipped one.
type consent struct{ userID, clientRegID, redirectURI string }

// deliverVuln re-delivers the code to whatever redirect_uri the registration
// carried. No check that THIS user approved THIS client. Confused deputy.
func deliverVuln(p pendingAuth) (string, bool) {
	return p.redirectURI + "?code=" + p.code, true
}

// deliverSafe delivers only if the user granted consent to this client on the
// proxy's own screen, AND the redirect_uri exactly matches the one bound at
// consent time. A mid-flight redirect_uri swap fails the lookup.
func deliverSafe(p pendingAuth, granted map[consent]bool) (string, bool) {
	c := consent{p.userID, p.clientRegID, p.redirectURI}
	if !granted[c] {
		return "", false
	}
	return p.redirectURI + "?code=" + p.code, true
}

func main() {
	// The victim only ever approved the legitimate client on the proxy's own
	// consent screen — codes for it go to the app's own callback.
	granted := map[consent]bool{
		{userID: "victim", clientRegID: "legit-app", redirectURI: "https://app.example/cb"}: true,
	}

	// Attacker used open DCR to register attacker.example behind the shared
	// client, then baited the victim through the REAL SSO. The victim logged
	// in for real; the upstream minted a real code for "victim".
	attack := pendingAuth{"victim", "attacker-reg", "https://attacker.example/cb", "REAL-SSO-CODE"}
	// The legitimate client the victim actually approved.
	legit := pendingAuth{"victim", "legit-app", "https://app.example/cb", "REAL-SSO-CODE"}

	locV, okV := deliverVuln(attack)
	fmt.Printf("vulnerable proxy      -> deliver=%v  %s   <- victim's code lands at attacker\n", okV, locV)

	_, okA := deliverSafe(attack, granted)
	fmt.Printf("consent-gated (attack)-> deliver=%v  (victim never consented to attacker-reg)   <- refused\n", okA)

	locL, okL := deliverSafe(legit, granted)
	fmt.Printf("consent-gated (legit) -> deliver=%v  %s   <- the client the user approved\n", okL, locL)
}
```

</GoPlayground>

The vulnerable proxy hands the victim's real code to `attacker.example`; the consent-gated proxy refuses the attacker's registration because no `(victim, attacker-reg, …)` decision exists, while still delivering to the client the victim actually approved. The differentiator is one record the upstream cookie can never forge.

<Callout kind="pro" title="Real case — the MCP OAuth-proxy confused deputy (CVE-2026-27124, 2026)">
The MCP security spec forbids this outright: a proxy using a static upstream `client_id` **MUST** obtain user consent for **each** dynamically-registered client before forwarding upstream. In practice that means four **MUST**s: (1) a **per-client consent screen owned by the proxy**, shown before the upstream redirect and displaying the client name and the exact `redirect_uri` from the *registration record* (never a query parameter); (2) **exact `redirect_uri` matching**, rejecting any mid-flight change between authorize and callback; (3) a server-side, one-shot **`state`** bound to the consent decision (you cannot set the consent cookie until the user clicks Approve, or an attacker's crafted request gets the same cookie); (4) the consent cookie under the **`__Host-`** prefix with `Secure`, `HttpOnly`, `SameSite=Lax`. Sources: the [MCP Security Best Practices — Confused Deputy Problem](https://modelcontextprotocol.io/specification/2025-06-18/basic/security_best_practices), the [PrefectHQ/fastmcp advisory `GHSA-rww4-4w9c-7733`](https://github.com/PrefectHQ/fastmcp/security/advisories/GHSA-rww4-4w9c-7733) (CVE-2026-27124), and the [full-account-takeover write-up](https://hackt.us/full-account-takeover-on-an-mcp-oauth-proxy-why-pkce-can-t-save-you.md).
</Callout>

<Exercise n={1} title="Tell a notification from a request" level="easy">

A notification is a JSON-RPC message with **no `id`**. Write `isNotification(raw []byte) bool` that reports whether a raw message is a notification — without unmarshalling into a fixed struct (you only care whether the `id` key is present).

<Solution>

```go
package main

import (
	"encoding/json"
	"fmt"
)

// isNotification reports whether a JSON-RPC message lacks an "id" key.
func isNotification(raw []byte) bool {
	var m map[string]json.RawMessage
	_ = json.Unmarshal(raw, &m)
	_, hasID := m["id"]
	return !hasID
}

func main() {
	fmt.Println(isNotification([]byte(`{"jsonrpc":"2.0","method":"notifications/initialized"}`))) // true
	fmt.Println(isNotification([]byte(`{"jsonrpc":"2.0","id":1,"method":"initialize"}`)))         // false
}
```

Decoding into `map[string]json.RawMessage` lets you test for the *presence* of a key without committing to a type or a zero-value trap. A `*int` field also works; the map approach is the most direct expression of "is this key here at all."

```go
package main

import "fmt"

func negotiateVersion(requested string, supported []string) string {
	for _, v := range supported {
		if v == requested {
			return requested
		}
	}
	return supported[len(supported)-1]
}

func main() {
	server := []string{"2024-11-05", "2025-03-26", "2025-06-18"}
	fmt.Println(negotiateVersion("2025-06-18", server)) // 2025-06-18
	fmt.Println(negotiateVersion("2030-01-01", server)) // 2025-06-18 (latest)
	fmt.Println(negotiateVersion("2024-11-05", server)) // 2024-11-05 (still supported)
}
```

The real client then decides whether it can speak the version the server returned; if not, it closes the session rather than risk a mid-call incompatibility.

</Solution>

</Exercise>

<Exercise n={4} title="Protocol error vs tool error" level="medium">

Implement `callGetBalance(args map[string]any, balances map[string]int64) (any, *RPCError)`. A **missing or empty** `account_id` is a *protocol* error: return `nil` result and `-32602` (invalid params). An **unknown** account is a *tool* error: return a `result` with `isError: true` (and `nil` `*RPCError`). A known account returns the balance with `isError: false`.

<Solution>

```go
package main

import "fmt"

type RPCError struct {
	Code    int    `json:"code"`
	Message string `json:"message"`
}

func callGetBalance(args map[string]any, balances map[string]int64) (any, *RPCError) {
	acct, ok := args["account_id"].(string)
	if !ok || acct == "" {
		return nil, &RPCError{Code: -32602, Message: "invalid params: account_id is required"}
	}
	bal, ok := balances[acct]
	if !ok {
		return map[string]any{
			"content": []any{map[string]any{"type": "text", "text": "account not found: " + acct}},
			"isError": true,
		}, nil
	}
	return map[string]any{
		"content": []any{map[string]any{"type": "text", "text": fmt.Sprintf("balance: %d", bal)}},
		"isError": false,
	}, nil
}

func main() {
	bal := map[string]int64{"acct-001": 5000}
	_, e := callGetBalance(map[string]any{}, bal)
	fmt.Println("missing arg ->", e) // -32602
	r, _ := callGetBalance(map[string]any{"account_id": "acct-001"}, bal)
	fmt.Println("known       ->", r) // isError:false
	r2, _ := callGetBalance(map[string]any{"account_id": "ghost"}, bal)
	fmt.Println("unknown     ->", r2) // isError:true
}
```

The split is the heart of MCP error handling: malformed *requests* are protocol errors the client should fix; valid requests that *fail in the domain* are tool errors the model should see and reason about.

</Solution>

</Exercise>

<Exercise n={5} title="Route a resources/read by URI" level="hard">

Implement `readResource(uri string, balances map[string]int64) (any, *RPCError)` for the `ledger://accounts/{id}` scheme. A URI that does not start with `ledger://accounts/` is `-32602` (unsupported). A well-formed URI for an unknown account is `-32002` (MCP resource-not-found). A known account returns `{"contents":[{"uri":..,"mimeType":"text/plain","text":..}]}`.

<Solution>

```go
package main

import (
	"fmt"
	"strings"
)

type RPCError struct {
	Code    int    `json:"code"`
	Message string `json:"message"`
}

func readResource(uri string, balances map[string]int64) (any, *RPCError) {
	const prefix = "ledger://accounts/"
	if !strings.HasPrefix(uri, prefix) {
		return nil, &RPCError{Code: -32602, Message: "unsupported uri: " + uri}
	}
	id := strings.TrimPrefix(uri, prefix)
	bal, ok := balances[id]
	if !ok {
		return nil, &RPCError{Code: -32002, Message: "resource not found: " + uri}
	}
	return map[string]any{"contents": []any{map[string]any{
		"uri": uri, "mimeType": "text/plain", "text": fmt.Sprintf("%d", bal),
	}}}, nil
}

func main() {
	bal := map[string]int64{"acct-001": 5000}
	r, _ := readResource("ledger://accounts/acct-001", bal)
	fmt.Println("ok        ->", r)
	_, e1 := readResource("ledger://accounts/ghost", bal)
	fmt.Println("unknown   ->", e1) // -32002
	_, e2 := readResource("file:///etc/passwd", bal)
	fmt.Println("badscheme ->", e2) // -32602 — and a path-traversal attempt blocked
}
```

That last case is not just a wrong scheme — it is an attacker trying to read an arbitrary file through your resource handler. Whitelisting the scheme prefix is what turns "read any URI" into "read only ledger accounts." Validate the noun before you fetch it.

</Solution>

</Exercise>

<Recap>

You now understand MCP from the wire up:

- **The problem MCP solves:** the M×N integration matrix. One standard protocol turns "every app × every tool" glue into N+M reusable plugs — schema-first thinking applied to AI tooling.
- **JSON-RPC 2.0 is the whole wire format:** request (`id`+`method`+`params`), response (`id`+`result` *or* `error`), notification (no `id`, no reply). The presence of `id` is the only request/notification discriminator.
- **The lifecycle:** `initialize` (request) → `initialize` result → `initialized` (notification). It negotiates the date-string `protocolVersion` (`2025-06-18`) and bidirectional capabilities before any real traffic.
- **Three server primitives by control axis:** **tools** (model-controlled actions), **resources** (app-controlled read-only data by URI), **prompts** (user-invoked templates). Client primitives — sampling, roots, elicitation — flow the other way.
- **You built both ends with the stdlib:** a newline-delimited stdio dispatch loop (`json.Encoder`/`bufio.Scanner`), and a client that matches by `id` and honors `isError`. `stdout` is sacred — log to `stderr`.
- **Two transports:** **stdio** for local subprocesses (zero network, OS isolation) and **Streamable HTTP** for remote servers (one endpoint, optional SSE upgrade; it replaced HTTP+SSE). Same messages, different framing.
- **The official `go-sdk`** shrinks a server to `NewServer` + `AddTool` (reflecting your typed input into a JSON Schema) + `Run`, and a client to `Connect` + `CallTool` — with all the protocol invariants enforced for you.
- **Protocol error vs tool error:** a bad method/params is a JSON-RPC `error` (`-32601`, `-32602`, `-32002`); a valid call that fails in the domain is a normal `result` with `isError: true`. Never conflate them.
- **Security:** the model is not your trust boundary. Validate every argument as hostile input, authorize against the *real end user* (tool-layer confused-deputy defense), gate mutations behind human-in-the-loop, and lock down the HTTP surface (OAuth 2.1, `Origin` checks, TLS). And the OAuth proxy is a *second* confused deputy: a static upstream `client_id` + open DCR + a skipped consent screen lets an attacker's `redirect_uri` steal a real code (`CVE-2026-27124`) — **PKCE can't save you** because the attacker is the client, so bind a per-client consent decision to the `redirect_uri`.
