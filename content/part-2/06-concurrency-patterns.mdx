Goroutines and channels are the parts. This chapter is about the shapes you build from them: pipelines, worker pools, semaphores, errgroup, singleflight and the rest. Each has a name because the same few problems keep coming back: too much work at once, work nobody is waiting for any more, and two goroutines touching the same thing.

## The job this chapter builds

Every night, a bank sends each customer who had activity that day a **statement**: how many transfers, the net amount in their own currency, and the same amount in euros at the European Central Bank's reference rate. Customers receive it as a JSON **webhook**, an HTTP POST to a URL they registered, the way Stripe or GitHub notify you of events.

The job, `statements`, does this for one day:

1. Find every account with transfers that day (Postgres).
2. For each account: total its transfers (Postgres), convert the net to euros (ECB rates, fetched over HTTPS), and POST the statement to its webhook URL.
3. Count what was delivered, refused and failed.

Step 2 is the interesting one. The Postgres part takes about **0.3 ms** per account; the POST takes **20 to 80 ms**, because it's waiting for someone else's server. You can't batch someone else's webhook endpoint into one SQL query, so this is the kind of work concurrency exists for: lots of independent waiting.

### Step 1: the pieces you run

Everything is real and runs on your machine:

- **Postgres**, with a `settlement` database: 50,000 accounts in five currencies, and 2,000 accounts with ten transfers each on 2026-09-25. The seed file is below.
- **The ECB's daily rates** at `https://www.ecb.europa.eu/stats/eurofxref/eurofxref-daily.xml`, a small public XML file the ECB publishes each working day. (It has no rate for the Nigerian naira, which will matter in stop 3.)
- **`hooksink`**, an HTTP server that stands in for the customers' endpoints. It answers each POST after 20 to 80 ms, and, like most load balancers, answers **503 Service Unavailable** when more than 64 requests are in flight. It's our own server, not a customer's, but the behaviour is the real thing: a server with finite capacity that says no.

```sql
-- settlement: 50,000 accounts in six currencies, one day of transfers.
-- createdb settlement && psql -d settlement -f seed.sql
DROP TABLE IF EXISTS deliveries, transfers, accounts;

CREATE TABLE accounts (
    id          bigint PRIMARY KEY,
    currency    char(3) NOT NULL,
    webhook_url text    NOT NULL
);

CREATE TABLE transfers (
    id           bigserial PRIMARY KEY,
    account_id   bigint      NOT NULL REFERENCES accounts(id),
    amount_minor bigint      NOT NULL,  -- negative = money out
    booked_at    timestamptz NOT NULL
);
CREATE INDEX ON transfers (account_id, booked_at);

CREATE TABLE deliveries (
    account_id   bigint      NOT NULL,
    day          date        NOT NULL,
    status       int         NOT NULL,
    delivered_at timestamptz NOT NULL DEFAULT now(),
    PRIMARY KEY (account_id, day)
);

INSERT INTO accounts
SELECT i,
       CASE WHEN i % 50 = 0 THEN 'NGN'
            WHEN i % 10 < 5 THEN 'USD'
            WHEN i % 10 < 8 THEN 'EUR'
            WHEN i % 10 = 8 THEN 'GBP'
            ELSE 'JPY' END,
       'http://127.0.0.1:9090/hooks/' || i
FROM generate_series(1::bigint, 50000) AS i;

-- 2,000 accounts are active on 2026-09-25, ten transfers each.
INSERT INTO transfers (account_id, amount_minor, booked_at)
SELECT a, (random() * 200000 - 80000)::bigint,
       '2026-09-25'::timestamptz + random() * interval '1 day'
FROM generate_series(1::bigint, 45978, 23) AS a,
     generate_series(1, 10);

ANALYZE;
```

```go noverify
// hooksink receives statement webhooks the way customers' endpoints do:
// each takes 20 to 80 ms to answer, and like most load balancers it
// refuses work (503) beyond a fixed number of requests in flight.
package main

import (
	"encoding/json"
	"flag"
	"fmt"
	"io"
	"log"
	"net/http"
	"strconv"
	"sync/atomic"
	"time"
)

func main() {
	addr := flag.String("addr", "127.0.0.1:9090", "listen address")
	limit := flag.Int64("limit", 64, "requests in flight before answering 503")
	hang := flag.Int64("hang", 0, "account whose endpoint never answers")
	flag.Parse()

	var inFlight, peak, ok, refused atomic.Int64

	http.HandleFunc("POST /hooks/{id}", func(w http.ResponseWriter, r *http.Request) {
		id, err := strconv.ParseInt(r.PathValue("id"), 10, 64)
		if err != nil {
			http.Error(w, "bad id", http.StatusBadRequest)
			return
		}
		n := inFlight.Add(1)
		defer inFlight.Add(-1)
		for p := peak.Load(); n > p && !peak.CompareAndSwap(p, n); p = peak.Load() {
		}
		if n > *limit {
			refused.Add(1)
			http.Error(w, "busy", http.StatusServiceUnavailable)
			return
		}
		io.Copy(io.Discard, r.Body)
		if id == *hang {
			<-r.Context().Done() // a customer's server that accepted and went quiet
			return
		}
		time.Sleep(time.Duration(20+id*7919%61) * time.Millisecond)
		ok.Add(1)
		w.WriteHeader(http.StatusNoContent)
	})

	http.HandleFunc("GET /stats", func(w http.ResponseWriter, r *http.Request) {
		json.NewEncoder(w).Encode(map[string]int64{
			"delivered": ok.Load(), "refused_503": refused.Load(), "peak_in_flight": peak.Load(),
		})
	})
	http.HandleFunc("POST /reset", func(w http.ResponseWriter, r *http.Request) {
		ok.Store(0)
		refused.Store(0)
		peak.Store(0)
	})

	fmt.Printf("hooksink on %s, limit %d in flight\n", *addr, *limit)
	log.Fatal(http.ListenAndServe(*addr, nil))
}
```

## Pipelines and Generators

*Stop 1 of 6.*

### Step 1: a generator reads Postgres

A **generator** is a function that starts a goroutine to produce values onto a channel, and closes the channel when there are no more. The consumer just ranges over the channel. The job's generator is `activeAccounts`, and it reads straight from a database cursor:

```go noverify
package main

import (
	"context"
	"database/sql"
)

// activeAccounts is a generator: it streams every account with transfers
// on day, straight from a Postgres cursor, and closes out when done.
// It stops early, and releases the connection, if ctx is cancelled.
func activeAccounts(ctx context.Context, db *sql.DB, day string, out chan<- Account) error {
	defer close(out)
	rows, err := db.QueryContext(ctx, `
		SELECT a.id, a.currency, a.webhook_url
		FROM accounts a
		WHERE a.id IN (SELECT account_id FROM transfers
		               WHERE booked_at >= $1::date AND booked_at < $1::date + 1)
		ORDER BY a.id`, day)
	if err != nil {
		return err
	}
	defer rows.Close()
	for rows.Next() {
		var a Account
		if err := rows.Scan(&a.ID, &a.Currency, &a.WebhookURL); err != nil {
			return err
		}
		select {
		case out <- a:
		case <-ctx.Done():
			return ctx.Err()
		}
	}
	return rows.Err()
}
```

Three details carry the weight:

- **`defer close(out)`.** Closing is how a channel says "no more values"; `for a := range accounts` in the consumer ends when it happens. Only the sender closes, because only the sender knows when it's done; closing a channel twice, or sending on a closed one, panics.
- **`select` on every send.** `out <- a` waits until someone receives. If the consumer has stopped, that wait is forever, and the goroutine and its open database cursor with it. The `case <-ctx.Done()` gives it a way out. Stop 3 measures what happens without one.
- **It streams.** Postgres sends rows as the loop reads them, so the first account reaches a worker before the query has finished, and memory stays flat whether there are 2,000 accounts or 2 million.

The rest of the job's types, for reference:

```go noverify
package main

	ID         int64
	Currency   string

}

// Statement is what we send to the account holder's webhook.

### Step 2: stages

A **pipeline** is generators chained together: each stage reads from the previous stage's channel and writes to its own. The first version of the job has three: the generator, a stage that builds and delivers each statement, and the consumer counting results.

```go noverify
// from run.go
type job struct {
	db     *sql.DB
	client *http.Client
	rates  RateSource
	day    string
}

// from run.go
// process is the per-account work: build the statement, then deliver it.
func (j *job) process(ctx context.Context, a Account) Result {
	st, err := buildStatement(ctx, j.db, j.rates, a, j.day)
	if err != nil {
		return Result{AccountID: a.ID, Err: err}
	}
	return deliver(ctx, j.client, a.WebhookURL, st)
}

// from run.go
// runPipeline: source -> one worker -> results. Stages overlap, but only
// one account is being worked on at a time.
func (j *job) runPipeline(ctx context.Context, results chan<- Result) error {
	defer close(results)
	accounts := make(chan Account)
	go activeAccounts(ctx, j.db, j.day, accounts)
	for a := range accounts {
		results <- j.process(ctx, a)
	}
	return nil
}
```

`process` is `buildStatement` (total the transfers in Postgres and convert to euros; shown in stop 5) followed by `deliver`:

```go noverify
package main

import (
	"bytes"
	"context"
	"encoding/json"
	"io"
	"net/http"
	"time"
)

// deliver POSTs one statement to the account's webhook URL.
func deliver(ctx context.Context, client *http.Client, url string, st Statement) Result {
	start := time.Now()
	res := Result{AccountID: st.AccountID}
	body, _ := json.Marshal(st)
	req, err := http.NewRequestWithContext(ctx, "POST", url, bytes.NewReader(body))
	if err != nil {
		res.Err = err
		return res
	}
	req.Header.Set("Content-Type", "application/json")
	resp, err := client.Do(req)
	res.Took = time.Since(start)
	if err != nil {
		res.Err = err
		return res
	}
	io.Copy(io.Discard, resp.Body)
	resp.Body.Close()
	res.Status = resp.StatusCode
	return res
}
```

A pipeline runs its stages at the same time, so it's as fast as its slowest stage, never faster. Here one stage costs 0.3 ms and the other 52 ms: running them at the same time could save 0.6 seconds out of 104. (`-mode buildonly` runs just the Postgres half, for all 2,000 accounts: 610 ms.) Pipelines pay off when stages cost about the same, like decode, transform and encode over a large file. When one stage dominates, you need several copies of that stage. That's stop 2.

<Callout kind="note" title="Tee and bridge, briefly">

Two more channel shapes you'll see in older code. A **tee** copies one channel into two, for two consumers that each need every value. A **bridge** turns a channel of channels into one flat channel. The job doesn't need either: its one consumer both counts results and writes the audit file (`-audit`), which is simpler than splitting the stream. Reach for a tee when two consumers must run at their own pace.

</Callout>

## Fan-out, Fan-in and Bounded Parallelism

*Stop 2 of 6.*

### Step 1: fan out, fan in

**Fan-out** means several goroutines receiving from the same channel. A channel hands each value to exactly one receiver, so the channel itself is the work queue: no locks, no "who takes what" logic. **Fan-in** means merging their results back into one channel, which has one rule: close it only after every sender is finished.

```go noverify
// from run.go
// runPool: fan out to n workers that share one input channel; fan their
// results back in on one channel, closed when the last worker is done.
func (j *job) runPool(ctx context.Context, n int, results chan<- Result) error {
	accounts := make(chan Account)
	go activeAccounts(ctx, j.db, j.day, accounts)
	var wg sync.WaitGroup
	for range n {
		wg.Go(func() {
			for a := range accounts {
				results <- j.process(ctx, a)
			}
		})
	}
	wg.Wait()
	close(results)
	return nil
}
```

`wg.Go` (Go 1.25) starts a goroutine and counts it in the WaitGroup. `wg.Wait()` returns when all workers have finished, which happens when `accounts` is closed and drained. Only then is it safe to `close(results)`: closing earlier would make a worker's send panic.

Up to the endpoint's limit, time falls almost in proportion: each worker spends nearly all its time waiting, so N workers wait N times as much at once. The "faster" times in those rows are the job failing quickly.

### Step 3: one goroutine per account

The version everyone writes first:

```go noverify
// from run.go
// runUnbounded: one goroutine per account, all at once.
func (j *job) runUnbounded(ctx context.Context, results chan<- Result) error {
	defer close(results)
	accounts := make(chan Account)
	go activeAccounts(ctx, j.db, j.day, accounts)
	var wg sync.WaitGroup
	for a := range accounts {
		wg.Go(func() { results <- j.process(ctx, a) })
	}
	wg.Wait()
	return nil
}
```

Goroutines are cheap, so 2,000 of them is nothing. What they *do* isn't cheap: each one wants a Postgres connection, and `database/sql`'s pool has **no limit by default** (`SetMaxOpenConns(0)`). Measured on the Mac:

```text
$ ./statements -mode unbounded
unbounded: 7.89s
  delivered 873, refused 503 704, failed 423
  error x423: failed to connect to `user=postgres database=settlement`: 127.0.0.1:55432 (127.0.0.1): dial error: timeout: dial tcp 127.0.0.1:55432: connect: operation timed out
```

Hundreds of connection attempts at once overflowed macOS's queue of pending TCP connections (128 by default), and the attempts timed out. The same binary built for Linux and run in a container, against the same database:

```text
$ docker run --rm --cpus=4 -e DATABASE_URL=…host.docker.internal… -v …:/statements alpine:3.22 /statements -mode unbounded
unbounded: 6.43s
  delivered 1556, refused 503 167, failed 277
  error x277: failed to connect to `user=postgres database=settlement`: 192.168.65.254:55432 (host.docker.internal): server error: FATAL: sorry, too many clients already (SQLSTATE 53300)
```

That's Postgres's own refusal: its `max_connections` is 100. **The same bug fails differently on your laptop and in production**, which is one reason it survives testing. Limiting the database pool alone (`-maxconns 20`) removed the database errors but not the underlying problem:

```text
$ ./statements -mode unbounded -maxconns 20
unbounded: 580ms
  delivered 194, refused 503 1806, failed 0
```

Now the database queues the goroutines politely, and they all hit the webhook endpoint at once instead: 1,806 refused.

### Step 4: semaphores and errgroup.SetLimit

A worker pool is one way to bound concurrency. The other keeps "a goroutine per item" and makes each one take a slot first: a **semaphore**. Part 2 chapter 5 built one from a buffered channel. `errgroup` has one built in: after `g.SetLimit(n)`, `g.Go` waits while `n` goroutines are running.

```go noverify
// from run.go
// runLimited: one goroutine per account again, but errgroup's SetLimit
// makes g.Go wait while n are already running: a semaphore built in.
func (j *job) runLimited(ctx context.Context, n int, results chan<- Result) error {
	g, ctx := errgroup.WithContext(ctx)
	g.SetLimit(n)
	accounts := make(chan Account)
	go activeAccounts(ctx, j.db, j.day, accounts)
	for a := range accounts {
		g.Go(func() error {
			select {
			case results <- j.process(ctx, a):
				return nil
			case <-ctx.Done():
				return ctx.Err()
			}
		})
	}
	err := g.Wait()
	close(results)

When you don't control that dependency, it will tell you: 503s and 429s are the signal to slow down, and a real job retries them with backoff rather than dropping them.

</Callout>

## Stopping: Done Channels and errgroup

*Stop 3 of 6.*

A job has to be able to stop in the middle: the caller has seen enough, the deadline has passed, or something went wrong that makes the rest pointless. Stopping is where concurrent code leaks.

### Step 1: a consumer that stops early

`-stop-after 100` makes the job's consumer read 100 results, cancel the context, and stop reading. Here is the pool from stop 2:

```text
$ ./statements -mode pool -workers 64 -stop-after 100
pool workers=64: 2.57s
  delivered 100, refused 503 0, failed 0
  ECB fetches: 1
  run stopped: run function still hasn't returned after 2s
  goroutines still running: 66
```

66 goroutines are stuck: 64 workers, each blocked forever on `results <- …` because nobody reads `results` any more, plus the goroutines around them. Cancelling the context didn't help, because the workers never look at it while sending. In a long-running service, every run like that leaks another 66, each holding its stack and whatever it had open.

The fix is the rule from the generator: **every send that might wait forever needs a way out.**

```go
select {
case results <- res:
case <-ctx.Done():
	return ctx.Err()
}
```

<Define term="Done channel">
A channel that is never sent on, only closed, to tell every goroutine watching it to stop: closing wakes all receivers at once. `ctx.Done()` is exactly this, with deadlines and a parent-child tree added. Older code passes a `done chan struct{}` around; new code passes a `context.Context`.
</Define>

When you consume a channel you don't own and still need to stop, the reusable form is **or-done**: a wrapper that forwards values until either the input closes or the context is cancelled. It's pure channel mechanics, so it runs in the browser:

<GoPlayground>

```go
package main

import (
	"context"
	"fmt"
	"runtime"
	"time"
)

// orDone forwards values from in until in is closed or ctx is cancelled.
// Ranging over its result can't block forever.
func orDone[T any](ctx context.Context, in <-chan T) <-chan T {
	out := make(chan T)
	go func() {
		defer close(out)
		for {
			select {
			case <-ctx.Done():
				return
			case v, ok := <-in:
				if !ok {
					return
				}
				select {
				case out <- v:
				case <-ctx.Done():
					return
				}
			}
		}
	}()
	return out
}

func main() {
	// A producer that never closes its channel: the kind you don't control.
	ticks := make(chan int)
	go func() {
		for i := 0; ; i++ {
			ticks <- i
		}
	}()

	ctx, cancel := context.WithTimeout(context.Background(), 5*time.Millisecond)
	defer cancel()
	n := 0
	for range orDone(ctx, ticks) {
		n++
	}
	fmt.Println("stopped after", n, "values:", ctx.Err())
	time.Sleep(10 * time.Millisecond)
	fmt.Println("goroutines:", runtime.NumGoroutine(), "(main + the producer, which we don't own)")
}
```

</GoPlayground>

### Step 2: errgroup, the whole job stops on the first real error

`golang.org/x/sync/errgroup` packages up what a job like this needs: start goroutines with `g.Go(func() error)`, and `g.Wait()` waits for all of them and returns the first error. With `errgroup.WithContext`, that first error also **cancels the group's context**, so everything using it stops: the generator, the other workers, and every Postgres query and HTTP request in flight.

```go noverify
// from run.go
// runProd: the pool again, under an errgroup. The first fatal error
// cancels ctx, which stops the generator, the workers and every
// in-flight query and HTTP request; Wait returns that error.
func (j *job) runProd(ctx context.Context, n int, hb *Heartbeats, results chan<- Result) error {
	g, ctx := errgroup.WithContext(ctx)
	accounts := make(chan Account)
	g.Go(func() error { return activeAccounts(ctx, j.db, j.day, accounts) })

	var workers sync.WaitGroup
	for i := range n {
		workers.Add(1)
		g.Go(func() error {
			defer workers.Done()
			for a := range accounts {
				hb.Beat(i, a.ID)
				res := j.process(ctx, a)
				if res.Err != nil && ctx.Err() == nil && !isDeliveryErr(res) {
					return res.Err // fatal: stop the whole run
				}
				select {
				case results <- res:
				case <-ctx.Done():
					return ctx.Err()
				}
			}
			hb.Done(i)
			return nil
		})
	}
	go func() { workers.Wait(); close(results) }()
	return g.Wait()
}

// from run.go
// isDeliveryErr reports whether the error came from the customer's
// endpoint rather than from us: those are retried tomorrow, not fatal.
func isDeliveryErr(r Result) bool { return r.Err != nil && r.Status == 0 && isNetErr(r.Err) }
```

### Step 3: which errors should stop the job?

errgroup makes stopping easy, which makes it easy to stop for the wrong reasons. Stopping 2,000 customers' statements because one currency has no ECB rate is a bad trade. So the job's real policy, which you saw in `buildStatement`'s `ErrNoRate` check and in `isDeliveryErr`, is:

- **Fatal, stop everything:** our own failures. The database is unreachable, a query is malformed. Every remaining account would fail the same way.
- **Not fatal, record and carry on:** one customer's problem. Their endpoint timed out or refused; their currency has no euro rate (send the statement without the euro figure). Tomorrow's retry or a human handles it.

Without `-strict-rates` the same data delivers all 2,000, including 40 naira statements without a euro amount. Deciding which errors are which is a design decision, and errgroup only implements it.

## Sharing Results: Confinement, Actors, Mutexes

*Stop 4 of 6.*

64 workers produce results; something has to count them and write the audit file. Three ways to do that safely.

### Step 1: confinement

**Confinement** means making sure only one goroutine ever touches a piece of data, so it needs no lock at all. The job's consumer loop in `main` does exactly this: workers *send* results; only the loop reads them and updates `delivered`, `busy`, `failed`, the error map and the audit file.

```go noverify
// statements sends every account active on -day its daily statement:
// transfers totalled from Postgres, converted to euros at the ECB rate,
// POSTed as JSON to the account's webhook URL.
package main

import (
	"context"
	"database/sql"
	"encoding/json"
	"errors"
	"flag"
	"fmt"
	"log"
	"maps"
	"net"
	"net/http"
	"os"
	"runtime"
	"slices"
	"strings"
	"time"

	_ "github.com/jackc/pgx/v5/stdlib"
)

func isNetErr(err error) bool {
	var ne net.Error
	return errors.As(err, &ne)
}

// errKind groups errors by what went wrong, not which account or URL:
// it keeps the first line and strips "account N: " and `Post "url": `.
func errKind(err error) string {
	msg, _, _ := strings.Cut(err.Error(), "\n")
	for {
		switch {
		case strings.HasPrefix(msg, "account "), strings.HasPrefix(msg, `Post "`):
			_, rest, ok := strings.Cut(msg, ": ")
			if !ok {
				return msg
			}
			msg = rest
		default:
			return msg
		}
	}
}

func main() {
	mode := flag.String("mode", "prod", "pipeline | buildonly | unbounded | pool | limit | prod")
	workers := flag.Int("workers", 32, "workers for pool, limit and prod")
	maxConns := flag.Int("maxconns", 0, "database/sql MaxOpenConns (0 = unlimited, the default)")
	sf := flag.Bool("singleflight", true, "share one ECB fetch between workers")
	ratesImpl := flag.String("rates", "mutex", "rates cache: mutex (+singleflight) | actor")
	audit := flag.String("audit", "", "also append every result to this JSON-lines file")
	day := flag.String("day", "2026-09-25", "statement day")
	stopAfter := flag.Int("stop-after", 0, "stop reading results after this many (0 = read all)")
	flag.BoolVar(&strictRates, "strict-rates", false, "treat a currency without an ECB rate as fatal")
	flag.Parse()

	db, err := sql.Open("pgx", os.Getenv("DATABASE_URL"))
	if err != nil {
		log.Fatal(err)
	}
	db.SetMaxOpenConns(*maxConns)
	defer db.Close()

	j := &job{
		db:     db,
		client: &http.Client{Timeout: 5 * time.Second, Transport: &http.Transport{MaxIdleConnsPerHost: 256}},
		day:    *day,
	}
	ctx, stop := context.WithCancel(context.Background())
	defer stop()

	fetches := &Rates{UseSingleflight: *sf} // also counts ECB fetches
	j.rates = fetches
	if *ratesImpl == "actor" {
		actor := NewRateActor(ctx)
		fetches = actor.rates
		j.rates = actor
	}

	results := make(chan Result)
	runErr := make(chan error, 1)
	start := time.Now()
	hb := NewHeartbeats(*workers)
	go hb.Watch(ctx, os.Stdout, 2*time.Second)
	go func() {
		switch *mode {
		case "pipeline":
			runErr <- j.runPipeline(ctx, results)
		case "unbounded":
			runErr <- j.runUnbounded(ctx, results)
		case "pool":
			runErr <- j.runPool(ctx, *workers, results)
		case "buildonly":
			runErr <- j.runBuildOnly(ctx, results)
		case "limit":
			runErr <- j.runLimited(ctx, *workers, results)
		default:
			runErr <- j.runProd(ctx, *workers, hb, results)
		}
	}()

	// Only this goroutine touches the counters and the audit file:
	// confinement, so none of it needs a lock.
	var enc *json.Encoder
	if *audit != "" {
		f, err := os.Create(*audit)
		if err != nil {
			log.Fatal(err)
		}
		defer f.Close()
		enc = json.NewEncoder(f)
	}
	var delivered, busy, failed, seen int
	firstErrs := map[string]int{}
	for r := range results {
		if seen++; seen > *stopAfter && *stopAfter > 0 {
			stop() // cancel ctx and walk away from the results channel
			break
		}
		switch {
		case r.Err != nil:
			failed++
			firstErrs[errKind(r.Err)]++
		case r.Status == http.StatusServiceUnavailable:
			busy++
		case r.Status < 300:
			delivered++
		default:
			failed++
		}
		if enc != nil {
			enc.Encode(map[string]any{"account": r.AccountID, "status": r.Status, "ms": r.Took.Milliseconds()})
		}
	}
	select {
	case err = <-runErr:
	case <-time.After(2 * time.Second):
		err = errors.New("run function still hasn't returned after 2s")
	}
	elapsed := time.Since(start)

	label := *mode
	if *mode == "pool" || *mode == "limit" || *mode == "prod" {
		label += fmt.Sprintf(" workers=%d", *workers)
	}
	fmt.Printf("%s: %v\n", label, elapsed.Round(10*time.Millisecond))
	fmt.Printf("  delivered %d, refused 503 %d, failed %d\n", delivered, busy, failed)
	kinds := slices.SortedFunc(maps.Keys(firstErrs), func(a, b string) int {
		return firstErrs[b] - firstErrs[a]
	})
	for _, msg := range kinds[:min(3, len(kinds))] {
		fmt.Printf("  error x%d: %s\n", firstErrs[msg], msg)
	}
	fmt.Printf("  ECB fetches: %d\n", fetches.Fetches.Load())
	if err != nil {
		fmt.Printf("  run stopped: %v\n", err)
	}
	// Shut down everything long-lived, so the count below shows leaks only.
	stop()
	j.client.CloseIdleConnections()
	http.DefaultClient.CloseIdleConnections()
	db.Close()
	time.Sleep(100 * time.Millisecond)
	fmt.Printf("  goroutines still running: %d\n", runtime.NumGoroutine())
}
```

There's no mutex anywhere in that file, and `go run -race` stays quiet, because the counters are confined to one goroutine. The channel is what moves each `Result` from a worker to the counter's owner; after the send, the worker doesn't touch it again.

### Step 2: an actor

An **actor** is confinement with a request protocol: one goroutine owns some state, and everyone else asks it through a channel, sending a reply channel along. The rates cache makes a good example, because it needs to fetch once and then answer many lookups:

```go noverify
package main

import (
	"context"
	"fmt"
	"math/big"
)

// RateActor is the same cache as Rates, built as an actor: one goroutine
// owns the table, and everyone else asks it through a channel.
type RateActor struct {
	inbox chan rateReq
	rates *Rates // reused only for its fetch method and fetch counter
}

type rateReq struct {
	ctx      context.Context
	currency string
	reply    chan rateReply // buffered: the actor never waits for a caller
}

type rateReply struct {
	rate *big.Rat
	err  error
}

func NewRateActor(ctx context.Context) *RateActor {
	a := &RateActor{inbox: make(chan rateReq), rates: &Rates{}}
	go a.loop(ctx)
	return a
}

func (a *RateActor) loop(ctx context.Context) {
	var table map[string]*big.Rat // only this goroutine ever touches it
	for {
		select {
		case <-ctx.Done():
			return
		case req := <-a.inbox:
			if table == nil {
				t, err := a.rates.fetch(req.ctx) // the other requests queue meanwhile
				if err != nil {
					req.reply <- rateReply{err: err}
					continue
				}
				table = t
			}
			rate, ok := table[req.currency]
			if !ok {
				req.reply <- rateReply{err: fmt.Errorf("%w for %s", ErrNoRate, req.currency)}
				continue
			}
			req.reply <- rateReply{rate: rate}
		}
	}
}

func (a *RateActor) Get(ctx context.Context, currency string) (*big.Rat, error) {
	if currency == "EUR" {
		return big.NewRat(1, 1), nil
	}
	req := rateReq{ctx: ctx, currency: currency, reply: make(chan rateReply, 1)}
	select {
	case a.inbox <- req:
	case <-ctx.Done():
		return nil, ctx.Err()
	}
	select {
	case r := <-req.reply:
		return r.rate, r.err
	case <-ctx.Done():
		return nil, ctx.Err()
	}
}
```

Two details make it safe. The **reply channel is buffered**, so if a caller gives up (its context is done), the actor's reply doesn't block forever. And the actor **selects on its own context**, so it exits when the job does: `goroutines still running: 1` with `-rates actor`.

The actor deduplicates the ECB fetch without any extra code: while it's fetching, other requests simply wait in the channel. The cost is that *every* lookup, all 2,000, goes through one goroutine. Measured, it made no difference to this job:

$ ./statements -mode prod -workers 64 -rates mutex

## Doing Less: singleflight and Futures

*Stop 5 of 6.*

The fastest work is work you don't do twice, and the fastest wait is one you do while doing something else.

### Step 1: 64 workers, one ECB request

Every worker needs a rate. When the job starts, the cache is empty, so all 64 workers miss at the same moment. Without anything to stop it, each one fetches the ECB file:

```go noverify
package main

import (
	"context"
	"encoding/xml"
	"errors"
	"fmt"
	"math/big"
	"net/http"
	"sync"
	"sync/atomic"

	"golang.org/x/sync/singleflight"
)

const ecbURL = "https://www.ecb.europa.eu/stats/eurofxref/eurofxref-daily.xml"

var ErrNoRate = errors.New("no ECB reference rate")

// Rates fetches the European Central Bank's daily reference rates once and
// caches them. Share one *Rates between all workers.
type Rates struct {
	UseSingleflight bool
	Fetches         atomic.Int64 // how many times we actually hit the ECB

	group singleflight.Group
	mu    sync.Mutex
	table map[string]*big.Rat // nil until the first successful fetch
}

func (r *Rates) Get(ctx context.Context, currency string) (*big.Rat, error) {
	if currency == "EUR" {
		return big.NewRat(1, 1), nil
	}
	r.mu.Lock()
	table := r.table
	r.mu.Unlock()

	if table == nil { // cache miss: fetch
		var err error
		if r.UseSingleflight {
			var v any
			v, err, _ = r.group.Do("ecb", func() (any, error) { return r.fetch(ctx) })
			if err == nil {
				table = v.(map[string]*big.Rat)
			}
		} else {
			table, err = r.fetch(ctx)
		}
		if err != nil {
			return nil, err
		}
		r.mu.Lock()
		r.table = table
		r.mu.Unlock()
	}

	rate, ok := table[currency]
	if !ok {
		return nil, fmt.Errorf("%w for %s", ErrNoRate, currency)
	}
	return rate, nil
}

func (r *Rates) fetch(ctx context.Context) (map[string]*big.Rat, error) {
	r.Fetches.Add(1)
	req, err := http.NewRequestWithContext(ctx, "GET", ecbURL, nil)
	if err != nil {
		return nil, err
	}
	resp, err := http.DefaultClient.Do(req)
	if err != nil {
		return nil, fmt.Errorf("ECB rates: %w", err)
	}
	defer resp.Body.Close()
	if resp.StatusCode != http.StatusOK {
		return nil, fmt.Errorf("ECB rates: %s", resp.Status)
	}

	// <Cube><Cube time="…"><Cube currency="USD" rate="1.1403"/>…
	var doc struct {
		Rates []struct {
			Currency string `xml:"currency,attr"`
			Rate     string `xml:"rate,attr"`
		} `xml:"Cube>Cube>Cube"`
	}
	if err := xml.NewDecoder(resp.Body).Decode(&doc); err != nil {
		return nil, fmt.Errorf("ECB rates: %w", err)
	}
	table := make(map[string]*big.Rat, len(doc.Rates))
	for _, x := range doc.Rates {
		rat, ok := new(big.Rat).SetString(x.Rate)
		if !ok {
			return nil, fmt.Errorf("ECB rates: bad rate %q for %s", x.Rate, x.Currency)
		}
		table[x.Currency] = rat
	}
	return table, nil
}
```

64 identical HTTPS requests to a public service, 63 of them pointless. This is a **cache stampede**, and it's how a cold start or an expired cache entry takes down the service behind it. `singleflight.Group.Do(key, fn)` runs `fn` once for all callers that ask for the same key while it's running; the others wait and share the result. It's different from `sync.Once`: after the call finishes, the next `Do` for that key runs again, which is what you want for data that expires.

The conversion itself uses the rate exactly. `big.Rat` holds `1.1403` as the fraction 11403/10000, so converting 12,345.67 dollars to euros involves no binary floating-point error (Part 1 chapter 1 showed what `float64` does to money), and `FloatString(2)` rounds to cents at the very end:

```go noverify
package main

import (
	"context"
	"database/sql"
	"errors"
	"fmt"
	"math/big"
)

// strictRates makes a missing ECB rate a fatal error (-strict-rates).
var strictRates bool

// minorDigits is how many decimal places each currency's minor unit has.
var minorDigits = map[string]int64{"USD": 2, "EUR": 2, "GBP": 2, "JPY": 0, "NGN": 2}

// RateSource gives units of currency per 1 EUR. *Rates and *RateActor
// both implement it.
type RateSource interface {
	Get(ctx context.Context, currency string) (*big.Rat, error)
}

// buildStatement totals one account's transfers for day and converts the
// net amount to euros at the ECB reference rate.
func buildStatement(ctx context.Context, db *sql.DB, rates RateSource, a Account, day string) (Statement, error) {
	st := Statement{AccountID: a.ID, Day: day, Currency: a.Currency}
	err := db.QueryRowContext(ctx, `
		SELECT count(*), coalesce(sum(amount_minor), 0)
		FROM transfers
		WHERE account_id = $1 AND booked_at >= $2::date AND booked_at < $2::date + 1`,
		a.ID, day).Scan(&st.Transfers, &st.NetMinor)
	if err != nil {
		return st, fmt.Errorf("account %d: %w", a.ID, err)
	}

	rate, err := rates.Get(ctx, a.Currency) // units of a.Currency per 1 EUR
	if errors.Is(err, ErrNoRate) && !strictRates {
		return st, nil // deliver without a euro figure; see "errgroup" for why
	}
	if err != nil {
		return st, fmt.Errorf("account %d: %w", a.ID, err)
	}
	// Exact arithmetic: net / 10^digits / rate, rounded to euro cents.
	eur := new(big.Rat).SetFrac(big.NewInt(st.NetMinor), new(big.Int).Exp(big.NewInt(10), big.NewInt(minorDigits[a.Currency]), nil))
	eur.Quo(eur, rate)
	st.NetEUR = eur.FloatString(2)
	return st, nil
}
```

### Step 2: futures, two waits at once

Before the job starts sending, a report header might need two independent things: the day's ECB rates, and the total volume of the ledger (a sum over two million rows). One after the other, you wait for both in turn. As **futures**, you start both and then collect them:

```go noverify
// futures starts two independent slow calls, the ECB's reference rates and
// a sum over two million transactions, first one after the other, then
// both at once, and prints how long each way took.
package main

import (
	"context"
	"database/sql"
	"fmt"
	"io"
	"log"
	"net/http"
	"os"
	"sync"
	"time"

	_ "github.com/jackc/pgx/v5/stdlib"
)

// async starts f in a goroutine and returns a function that waits for its
// result. The returned function can be called any number of times.
func async[T any](f func() (T, error)) func() (T, error) {
	type result struct {
		v   T
		err error
	}
	ch := make(chan result, 1) // buffered: the goroutine never waits for us
	go func() {
		v, err := f()
		ch <- result{v, err}
	}()
	return sync.OnceValues(func() (T, error) {
		r := <-ch
		return r.v, r.err
	})
}

func main() {
	db, err := sql.Open("pgx", os.Getenv("DATABASE_URL"))
	if err != nil {
		log.Fatal(err)
	}
	defer db.Close()
	ctx := context.Background()
	db.PingContext(ctx) // open the connection up front so it isn't timed

	rates := func() (int, error) {
		req, _ := http.NewRequestWithContext(ctx, "GET", "https://www.ecb.europa.eu/stats/eurofxref/eurofxref-daily.xml", nil)
		resp, err := http.DefaultClient.Do(req)
		if err != nil {
			return 0, err
		}
		defer resp.Body.Close()
		b, err := io.ReadAll(resp.Body)
		return len(b), err
	}
	volume := func() (int64, error) {
		var cents int64
		err := db.QueryRowContext(ctx, `SELECT sum(amount_cents) FROM transactions`).Scan(&cents)
		return cents, err
	}

	for _, concurrent := range []bool{false, true, false, true} {
		http.DefaultClient.CloseIdleConnections() // a fresh TLS handshake every time
		start := time.Now()
		var n int
		var cents int64
		var err1, err2 error
		if concurrent {
			getRates, getVolume := async(rates), async(volume)
			n, err1 = getRates()
			cents, err2 = getVolume()
		} else {
			n, err1 = rates()
			cents, err2 = volume()
		}
		if err1 != nil || err2 != nil {
			log.Fatal(err1, err2)
		}
		fmt.Printf("concurrent=%-5v %4d ms  (rates: %d bytes, volume: %d cents)\n",
			concurrent, time.Since(start).Milliseconds(), n, cents)
	}

	// Each part alone, for reference.
	http.DefaultClient.CloseIdleConnections()
	t := time.Now()
	rates()
	fmt.Printf("rates alone:  %4d ms\n", time.Since(t).Milliseconds())
	t = time.Now()
	volume()
	fmt.Printf("volume alone: %4d ms\n", time.Since(t).Milliseconds())
}
```

```text
$ go run ./futures
concurrent=false  852 ms  (rates: 1547 bytes, volume: 50199055000 cents)
concurrent=true   457 ms  (rates: 1547 bytes, volume: 50199055000 cents)
concurrent=false  494 ms  (rates: 1547 bytes, volume: 50199055000 cents)
concurrent=true   437 ms  (rates: 1547 bytes, volume: 50199055000 cents)
rates alone:   421 ms
volume alone:   68 ms
```

(The first run includes Postgres reading the table from disk; after that it's cached.) Sequentially the time is the **sum**, 421 + 68 ≈ 494 ms; concurrently it's the **maximum**, ≈ 437 ms. Futures save the time of every call except the slowest: here 68 ms. With five independent calls of similar length, they'd save four fifths of the wait.

`async` is ten lines, and two of them matter. The channel is **buffered**, so the goroutine can finish and exit even if nobody ever collects the result. And `sync.OnceValues` (Go 1.21) makes the returned function safe to call more than once. In a real service, pass the request's context into `f` so abandoned futures stop too; errgroup is often the better tool when you need all the results and want the first error to cancel the rest.

## Heartbeats

*Stop 6 of 6.*

A job with 64 workers finishes when its slowest worker does. If one is stuck, how do you find out which one, and on what?

### Step 1: a worker that goes quiet

Restart `hooksink` with `-hang 23001`: the endpoint for account 23001 accepts the request and never answers, like a customer's server with a wedged process. The job's HTTP client has a 5-second timeout. Each worker calls `hb.Beat(i, a.ID)` before every account, and a watchdog goroutine checks the beats every second:

```go noverify
package main

import (
	"context"
	"fmt"
	"io"
	"sync/atomic"
	"time"
)

// Heartbeats records, per worker, when it last started an account and
// which one. A watchdog reads them; workers never block on it.
type Heartbeats struct {
	last    []atomic.Int64 // unix nanos of the last beat, 0 = finished
	account []atomic.Int64
}

func NewHeartbeats(n int) *Heartbeats {
	return &Heartbeats{last: make([]atomic.Int64, n), account: make([]atomic.Int64, n)}
}

func (h *Heartbeats) Beat(worker int, account int64) {
	h.account[worker].Store(account)
	h.last[worker].Store(time.Now().UnixNano())
}

func (h *Heartbeats) Done(worker int) { h.last[worker].Store(0) }

// Watch reports every worker that has been silent for longer than quiet.
func (h *Heartbeats) Watch(ctx context.Context, w io.Writer, quiet time.Duration) {
	tick := time.NewTicker(quiet / 2)
	defer tick.Stop()
	for {
		select {
		case <-ctx.Done():
			return
		case now := <-tick.C:
			for i := range h.last {
				last := h.last[i].Load()
				if last == 0 {
					continue
				}
				if silent := now.Sub(time.Unix(0, last)); silent > quiet {
					fmt.Fprintf(w, "watchdog: worker %d silent for %v on account %d\n",
						i, silent.Round(time.Second), h.account[i].Load())
				}
			}
		}
	}
}
```

`-singleflight` only affects the mutex version. The actor has one goroutine, so while it's fetching, every other request waits in its inbox; by the time it reads the next one, the table is filled. Deduplication comes from serialising.

<Recap>

- **Generators and pipelines.** A generator streams values onto a channel it closes when done; every send selects on `ctx.Done()`. A pipeline is only as fast as its slowest stage: 0.3 ms + 52 ms per account gave 104 s, whatever the overlap.
- **Fan-out, fan-in.** N workers ranging over one channel; results merged on one channel closed after `wg.Wait()`. Waiting work scales with N: 1 → 16 → 64 workers took the job from 104.7 s to 6.9 s to about 2 s.
- **Bounded parallelism.** The limit comes from the dependency. Past the endpoint's 64, 80 workers lost 70% of the statements; one goroutine per account also exhausted Postgres (`too many clients` on Linux, connect timeouts on macOS). `database/sql` has no connection limit until you set one. A pool or `errgroup.SetLimit` bounds it.
- **Stopping.** A plain send can block forever: the pool leaked 66 goroutines when its consumer quit. errgroup with a context stops everything on the first error and cancels in-flight work with that error as the cause; decide which errors deserve that.
- **Sharing.** Confine data to one goroutine when it flows to one owner; use an actor when state needs a protocol; use a mutex or atomic for small shared state. At 38 to 160 ns per operation, pick for clarity.
- **Doing less.** singleflight turned 64 ECB fetches into 1; futures ran two calls in the time of the slower (437 ms, not 494). Heartbeats named the one stuck worker; the timeout ended its wait.
