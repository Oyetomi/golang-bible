## Pipelines

A **pipeline** is a chain of stages. Each stage is a goroutine that reads from an inbound channel, does some work on each item, and emits transformed items onto an outbound channel. The channels are the pipes; the goroutines are the valves.

The key insight: stages are independent goroutines running concurrently. Stage 2 starts processing the first item while Stage 1 is still producing the second. That's the speedup, and it's free once the shape is right.

**On the job:** Pipelines appear wherever you read a large stream and process it in stages — fetching payment records from a DB cursor, validating each one, then enriching before submission. Get the shutdown wrong (forget `defer close(out)`) and the downstream stage range-loops forever; the goroutine leaks until the process restarts.

Here's a three-stage pipeline for Meridian's payment processor. Stage 1 generates raw payment IDs. Stage 2 validates each one. Stage 3 enriches the validated ones before submission.

```go
package main

import (
	"fmt"
)

type Payment struct {
	ID     int
	Amount int64 // cents
	Valid  bool
}

// stage1: emit a stream of payment IDs onto an outbound channel.
// The goroutine closes the channel when done so downstream stages know to stop.
func generate(ids []int) <-chan int {
	out := make(chan int)
	go func() {
		defer close(out) // close broadcasts the "no more items" signal
		for _, id := range ids {
			out <- id
		}
	}()
	return out
}

// stage2: validate each ID; emit Payment structs.
func validate(in <-chan int) <-chan Payment {
	out := make(chan Payment)
	go func() {
		defer close(out)
		for id := range in {
			// Real validation would check amount limits, duplicate detection, etc.
			out <- Payment{ID: id, Amount: int64(id) * 100, Valid: id%2 == 0}
		}
	}()
	return out
}

// stage3: enrich; emit only valid payments.
func enrich(in <-chan Payment) <-chan Payment {
	out := make(chan Payment)
	go func() {
		defer close(out)
		for p := range in {
			if p.Valid {
				out <- p // attach metadata in a real system
			}
		}
	}()
	return out
}

func main() {
	ids := []int{1, 2, 3, 4, 5}
	// Wire the pipeline: generate → validate → enrich
	for p := range enrich(validate(generate(ids))) {
		fmt.Printf("submit payment %d for $%d.%02d\n", p.ID, p.Amount/100, p.Amount%100)
	}
}
```

**Clean shutdown.** The `defer close(out)` in each stage is critical. When `generate` returns, it closes its channel. `validate` sees the close via `range` (which exits when the channel closes) and closes *its* channel. The close propagates downstream automatically. No explicit signaling, no `WaitGroup` here — the channel closure does it all.

<Callout kind="warn" title="Never close a channel from the receiver">
Only the **sender** closes a channel. Closing from the receiver, or closing twice, panics at runtime. The stage that owns the `make(chan T)` is the one that calls `close`. That's the contract — you produce it, you close it.
</Callout>

<UnderTheHood title="How channel close broadcasts to all receivers">

When a goroutine calls `close(ch)`, the runtime sets a flag in the channel's internal `hchan` struct. Any goroutine blocked in a `<-ch` receive immediately unblocks with the zero value of the element type and `ok == false`. Any goroutine in a `range ch` loop exits the loop.

Here is the subtlety: **closing a channel is a broadcast**. Every goroutine waiting on that channel unblocks simultaneously. This is the mechanism behind fan-out shutdown — one `close(done)` wakes every worker at once with no coordination overhead. Under the hood (as of Go 1.26), the scheduler places all goroutines waiting on a channel into a `recvq` linked list inside `hchan`. A `close` walks that list and makes every goroutine runnable in one pass — O(n) in the number of blocked receivers, but a single runtime operation, not N separate signals. This is a model of the mechanism; the scheduler's internal representation is implementation-defined and may change across versions.

An **unbuffered** channel send blocks the sender until a receiver is ready. This means an unbuffered hand-off *synchronizes* two goroutines at that point — the sender's state before the send is visible to the receiver after the receive, guaranteed by the Go memory model's happens-before rule: "a send on a channel happens before the corresponding receive from that channel completes." No mutex needed for this transfer.

A **buffered** channel with capacity N lets up to N sends proceed without a receiver; only the (N+1)th send blocks. This decouples producer and consumer, at the cost of N items of memory and the possibility that a slow receiver builds up a backlog. In Go 1.26 the channel implementation uses a circular buffer (`buf` field in `hchan`) for the elements.

</UnderTheHood>

## Fan-out and Fan-in

**Fan-out:** take one input channel and read from it across N goroutines in parallel.
**Fan-in:** merge N output channels back into one stream.

Together they are the workhorse of Meridian's payment processor: one stream of validated payments, fanned out across eight workers submitting in parallel, results merged back into one results channel for the caller.

**On the job:** You hit fan-out/fan-in the moment one stage becomes the bottleneck — validating payments is fast, but calling an external fraud API is slow. Fan out across N workers to overlap those calls. Get the merger wrong (forget the WaitGroup-gated closer) and merged never closes; the consumer blocks indefinitely.

```go
package main

import (
	"fmt"
	"sync"
)

// fanOut reads from in and launches n workers, each returning their own channel.
func fanOut(in <-chan int, n int, work func(int) string) []<-chan string {
	outs := make([]<-chan string, n)
	for i := range n { // range-over-int, Go 1.22+
		out := make(chan string)
		outs[i] = out
		go func() {
			defer close(out)
			for v := range in {
				out <- work(v)
			}
		}()
	}
	return outs
}

// fanIn merges multiple channels into one. It returns when all inputs close.
// wg.Go (Go 1.25) handles Add(1)+go+Done in one call.
func fanIn(cs []<-chan string) <-chan string {
	merged := make(chan string)
	var wg sync.WaitGroup
	for _, c := range cs {
		wg.Go(func() { // Go 1.25: wg.Go replaces wg.Add(1) + go func + defer wg.Done()
			for v := range c {
				merged <- v
			}
		})
	}
	go func() {
		wg.Wait()
		close(merged) // close merged only after ALL inputs are done
	}()
	return merged
}

func main() {
	in := make(chan int, 5)
	for _, id := range []int{101, 102, 103, 104, 105} {
		in <- id
	}
	close(in)

	workers := fanOut(in, 3, func(id int) string {
		return fmt.Sprintf("submitted payment %d", id)
	})

	for result := range fanIn(workers) {
		fmt.Println(result)
	}
}
```

If a worker goroutine is blocked trying to send onto its output channel but nobody is reading the merged channel (because the consumer quit on an error), that goroutine is stuck forever. The fix: every `send` inside a worker must also listen on the done/context channel in a `select`. We'll see the exact pattern in the Done/Or-Done section.

## Done and Or-Done

The **done channel** is Go's original cancellation idiom: a `chan struct{}` that you close to broadcast "stop everything." It predates `context.Context` and is still used internally in many patterns.

The **or-done** wrapper makes consuming a channel cancellation-safe — you never get stuck on a receive when the work is cancelled.

**On the job:** Any pipeline stage that might outlive its consumer needs or-done protection. In Meridian's batch processor, if the fan-in consumer returns early on an error, the upstream stages would block forever trying to send — without or-done, those goroutines leak until the process is killed.

```go
package main

import (
	"context"
	"fmt"
)

// orDone wraps a channel so that reads also respect ctx cancellation.
// Any goroutine reading from the returned channel will unblock if ctx is done.
func orDone[T any](ctx context.Context, in <-chan T) <-chan T {
	out := make(chan T)
	go func() {
		defer close(out)
		for {
			select {
			case <-ctx.Done():
				return
			case v, ok := <-in:
				if !ok {
					return
				}
				select {
				case <-ctx.Done():
					return
				case out <- v:
				}
			}
		}
	}()
	return out
}

	payments <- 1
	payments <- 2
	payments <- 3

	cancel()
```

## Generators

A **generator** is a goroutine that produces a stream of values on demand, emitting them onto a channel it owns. The caller ranges over the channel. The generator runs concurrently to the caller, producing the next item while the caller processes the current one.

Generators are the `generate` stage from the pipeline example, generalized. They're ideal for producing potentially-infinite or expensive-to-compute streams: payment IDs from a database cursor, lines from a file, events from a Kafka consumer.

**On the job:** A DB cursor generating millions of rows for a reconciliation job is a generator. Without the `ctx.Done()` select on every send, cancelling the reconciliation job leaves the generator goroutine alive, holding the DB connection, until it finishes emitting every row.

```go
package main

import (
	"context"
	"fmt"
)

// paymentIDs is a generator: it streams IDs from a simulated DB cursor.
// It respects ctx cancellation so it doesn't leak if the caller stops early.
func paymentIDs(ctx context.Context, batchDate string) <-chan int {
	out := make(chan int)
	go func() {
		defer close(out)
		// Simulate fetching rows from a DB cursor.
		ids := []int{1001, 1002, 1003, 1004, 1005}
		for _, id := range ids {
			select {
			case <-ctx.Done():
				return // caller cancelled; stop producing
			case out <- id:
			}
		}
	}()
	return out
}

func main() {
	ctx, cancel := context.WithCancel(context.Background())
	defer cancel()

	for id := range paymentIDs(ctx, "2026-06-03") {
		fmt.Println("queued payment", id)
	}
}
```

## Tee and Bridge

**Tee** splits one channel into two identical streams, like a T-junction in plumbing. Useful when two consumers need the same events: one for processing, one for auditing.

**Bridge** flattens a channel-of-channels (`<-chan <-chan T`) into a single stream. Useful when you have a sequence of stages, each producing their own channel, and you want a uniform stream at the other end.

```go
package main

import (
	"context"
	"fmt"
)

// tee clones each value from in into two output channels.
// Both outputs must be consumed or the goroutine blocks.
func tee[T any](ctx context.Context, in <-chan T) (<-chan T, <-chan T) {
	out1, out2 := make(chan T), make(chan T)
	go func() {
		defer close(out1)
		defer close(out2)
		for v := range orDone(ctx, in) {
			// Shadow out1/out2 so we can send to one then the other.
			o1, o2 := out1, out2
			for range 2 {
				select {
				case <-ctx.Done():
					return
				case o1 <- v:
					o1 = nil // sent; disable this arm
				case o2 <- v:
					o2 = nil
				}
			}
		}
	}()
	return out1, out2
}

func orDone[T any](ctx context.Context, in <-chan T) <-chan T {
```

## Bounded Parallelism

Unbounded fan-out is a loaded gun. If ten thousand payments arrive and you spawn a goroutine per payment, you've just created ten thousand goroutines hammering a downstream service — which either falls over or rate-limits you, and now you have ten thousand blocked goroutines eating memory. Bounded parallelism caps the concurrency at N.

**On the job:** Meridian's nightly reconciliation touches every active account. Spawning one goroutine per account at 2 million accounts means 2 million goroutines and likely a cascading failure on the downstream ledger DB. A pool of 32 workers is the entire fix.

The worker pool pattern: pre-spawn exactly N workers, feed them all from one shared input channel.

```go
package main

import (
	"context"
	"fmt"
	"sync"
)

type Result struct {
	ID  int
	Err error
}

// boundedWorkerPool fans out work across exactly n workers.
// wg.Go (Go 1.25) replaces the wg.Add(n)+loop+defer wg.Done() boilerplate.
func boundedWorkerPool(
	ctx context.Context,
	in <-chan int,
	n int,
	process func(context.Context, int) Result,
) <-chan Result {
	out := make(chan Result)
	var wg sync.WaitGroup
	for range n {
		wg.Go(func() { // Go 1.25
			for {
				select {
				case <-ctx.Done():
					return
				case id, ok := <-in:
					if !ok {
						return
					}
					select {
					case <-ctx.Done():
						return
					case out <- process(ctx, id):
					}
				}
			}
		})
	}
	go func() {
		wg.Wait()
		close(out)
	}()
	return out
}

func submitPayment(ctx context.Context, id int) Result {
	// Simulate submission: odd IDs succeed, even IDs fail.
	if id%2 == 0 {
		return Result{ID: id, Err: fmt.Errorf("payment %d declined", id)}
	}
	return Result{ID: id}
}

func main() {
	ctx, cancel := context.WithCancel(context.Background())
	defer cancel()

	in := make(chan int, 6)
	for _, id := range []int{1, 2, 3, 4, 5, 6} {
		in <- id
	}
	close(in)

	for r := range boundedWorkerPool(ctx, in, 3, submitPayment) {
		if r.Err != nil {
			fmt.Println("error:", r.Err)
		} else {
			fmt.Println("ok:", r.ID)
		}
	}
}
```

## Semaphores

Sometimes you need to limit concurrency without a pre-spawned pool — you spawn goroutines dynamically but gate them so at most N run their critical section at a time. That's a semaphore.

**On the job:** `errgroup` alone spawns one goroutine per item with no cap. For a 50,000-payment batch, that's 50,000 goroutines. Gate each `g.Go` behind a semaphore to keep concurrency bounded even when using errgroup.

**Option 1: buffered channel as semaphore.** Acquire = send into a buffered channel (blocks when full). Release = receive from it.

## errgroup

`errgroup` is fan-out where **any error from any goroutine cancels the rest and propagates up**. It's from `golang.org/x/sync/errgroup` and it's the right tool for Meridian's payment batch processor: if one payment's submission fails with a hard error, cancel the whole batch.

**On the job:** Without errgroup you'd need to manually wire a WaitGroup, a mutex for the first error, and a cancel function — three things that all have to be correct simultaneously. Get any one wrong and you either swallow errors, panic on concurrent writes, or let the batch run past a fatal failure.

```go
package main

import (
	"context"
	"fmt"

	"golang.org/x/sync/errgroup"
)

func submitBatch(ctx context.Context, ids []int) error {
	g, ctx := errgroup.WithContext(ctx)

	for _, id := range ids {
		g.Go(func() error {
			// Go 1.22+: loop variables are per-iteration, no capture needed.
			if id == 3 {
				return fmt.Errorf("payment %d: hard decline from processor", id)
			}
			fmt.Printf("submitted payment %d\n", id)
			return nil
		})
	}

	// Wait blocks until all goroutines complete or one returns an error.
	// If an error occurs, the derived ctx is cancelled for the others.
	return g.Wait()
}

func main() {
	ctx := context.Background()
	if err := submitBatch(ctx, []int{1, 2, 3, 4, 5}); err != nil {
		fmt.Println("batch failed:", err)
	}
}
```

```go
package main

import (
	"context"
	"fmt"
	"sync"
)

// errgroup-style implementation using stdlib only (no external dep in playground).
type Group struct {
	cancel func()
	wg     sync.WaitGroup
	mu     sync.Mutex
	err    error
}

func WithContext(ctx context.Context) (*Group, context.Context) {
	ctx, cancel := context.WithCancel(ctx)
	return &Group{cancel: cancel}, ctx
}

func (g *Group) Go(f func() error) {
	g.wg.Add(1)
	go func() {
		defer g.wg.Done()
		if err := f(); err != nil {
			g.mu.Lock()
			if g.err == nil {
				g.err = err
				g.cancel()
			}
			g.mu.Unlock()
		}
	}()
}

func (g *Group) Wait() error {
	g.wg.Wait()
	g.cancel()
	return g.err
}

func submitBatch(ctx context.Context, ids []int) error {
	g, ctx := WithContext(ctx)
	_ = ctx

	for _, id := range ids {
		g.Go(func() error {
			if id == 3 {
				return fmt.Errorf("payment %d: hard decline", id)
			}
			fmt.Printf("submitted payment %d\n", id)
			return nil
		})
	}
	return g.Wait()
}

func main() {
	if err := submitBatch(context.Background(), []int{1, 2, 3, 4, 5}); err != nil {
		fmt.Println("batch failed:", err)
	}
}
```

## Futures

A **future** (or promise) is a pattern for a single asynchronous result: kick off one goroutine, get back a channel that will receive exactly one value when that goroutine is done. The caller can do other work and then block on the channel when it needs the result.

**On the job:** Before submitting a payment, Meridian calls a fraud scoring service and a sanctions-check service. Both are independent. Fire them as futures, do any CPU-bound prep work, then block on both results — total latency is `max(fraud, sanctions)` instead of `fraud + sanctions`.

```go
package main

import (
	"context"
	"fmt"
	"time"
)

type FutureResult struct {
	Value string
	Err   error
}

// future starts work in a goroutine and returns a channel for the single result.
func future(ctx context.Context, f func(context.Context) (string, error)) <-chan FutureResult {
	ch := make(chan FutureResult, 1) // buffer of 1: sender never blocks
	go func() {
		v, err := f(ctx)
		ch <- FutureResult{Value: v, Err: err}
	}()
	return ch
}

func main() {
	ctx, cancel := context.WithTimeout(context.Background(), 2*time.Second)
	defer cancel()

	// Kick off fraud check asynchronously while we do other work.
	fraudCheck := future(ctx, func(ctx context.Context) (string, error) {
		// Simulate calling a fraud scoring service.
		return "PASS", nil
	})

	// Do other prep work concurrently.
	fmt.Println("preparing enriched payment record...")

	// Now block on the fraud result.
	result := <-fraudCheck
	if result.Err != nil {
		fmt.Println("fraud check failed:", result.Err)
		return
	}
	fmt.Println("fraud check:", result.Value)
```

## Confinement

**Confinement** is the practice of keeping data entirely on one goroutine so it never needs a lock. If a value is only ever touched by one goroutine, there is no race — by definition. There are two kinds:

**On the job:** Meridian's ledger balance map is a natural candidate for confinement — all reads and writes are channeled through a single `ledgerLoop` goroutine. The race detector never fires, there is no lock contention, and the throughput scales with message throughput, not with lock wait time.

**Lexical confinement:** the data's scope makes sharing impossible. A slice created inside a goroutine, used only there, passed nowhere else.

**Ad-hoc confinement:** a convention enforced by the team ("the `accounts` map is only touched by the ledgerLoop goroutine") documented with comments.

```go
package main

import (
	"fmt"
)

// ledgerLoop owns the ledger map exclusively — no other goroutine touches it.
// Operations arrive as messages on the ops channel. No mutex needed.
func ledgerLoop(ops <-chan func(map[int]int64)) {
	ledger := make(map[int]int64) // lexically confined to this goroutine
	for op := range ops {
		op(ledger) // the caller sends a closure; this goroutine applies it
	}
}

func main() {
	ops := make(chan func(map[int]int64), 10)

	go ledgerLoop(ops)

	// Credit account 42 with 5000 cents.
	ops <- func(l map[int]int64) {
		l[42] += 5000
		fmt.Println("balance after credit:", l[42])
	}
	// Debit account 42 by 1000 cents.
	ops <- func(l map[int]int64) {
		l[42] -= 1000
		fmt.Println("balance after debit:", l[42])
	}

	close(ops)
}
```

## Heartbeats

A **heartbeat** is a periodic signal a goroutine emits on a side channel to prove it's alive and making progress. Without one, a stalled worker is indistinguishable from a working one.

**On the job:** In Meridian's batch processor, if a worker stops emitting results for 30 seconds, is it processing a slow payment or is it deadlocked waiting for a hung TCP connection to the downstream processor? A heartbeat tells you — and lets a supervisor restart the worker instead of waiting for a two-hour batch timeout.

```go
package main

import (
	"context"
	"fmt"
	"time"
)

// workerWithHeartbeat processes items and ticks a heartbeat on each iteration.
func workerWithHeartbeat(
	ctx context.Context,
	in <-chan int,
	interval time.Duration,
) (<-chan int, <-chan struct{}) {
	out := make(chan int)
	heartbeat := make(chan struct{}, 1)

	go func() {
		defer close(out)
		defer close(heartbeat)
		ticker := time.NewTicker(interval)
		defer ticker.Stop()

		for {
			select {
			case <-ctx.Done():
				return
			case <-ticker.C:
				select {
				case heartbeat <- struct{}{}:
				default: // non-blocking: if nobody is reading, skip
				}
			case v, ok := <-in:
				if !ok {
					return
				}
				// Emit heartbeat on each successful item too.
				select {
				case heartbeat <- struct{}{}:
				default:
				}
				select {
				case <-ctx.Done():
					return
				case out <- v * 2:
				}
			}
		}
	}()
	return out, heartbeat
}

func main() {
	ctx, cancel := context.WithTimeout(context.Background(), 200*time.Millisecond)
	defer cancel()

	in := make(chan int, 3)
	in <- 1
	in <- 2
	in <- 3
	close(in)

	out, hb := workerWithHeartbeat(ctx, in, 50*time.Millisecond)

	for {
		select {
		case v, ok := <-out:
			if !ok {
				fmt.Println("worker done")
				return
			}
			fmt.Println("result:", v)
		case <-hb:
			fmt.Println("heartbeat: worker alive")
		case <-ctx.Done():
			fmt.Println("timeout")
			return
		}
	}
}
```

## Singleflight

Here's the scenario: it's 9am. Meridian's payment processor warms up and ten goroutines simultaneously call `fetchExchangeRates()` — all for the same `USD/EUR` pair. Without protection, ten concurrent HTTP requests hit the ECB API. Nine of them are wasted. If the API rate-limits you, you've just broken your own startup.

**On the job:** The cache stampede. A warm entry expires at the same instant ten requests arrive. Without singleflight, ten goroutines miss the cache and all fire the upstream call simultaneously — overloading the rate-limited external API and potentially returning ten inconsistent values. See "Caching & Redis" for the full cache-aside pattern; singleflight is the sharp fix for the in-flight collision slice of that problem.

**`singleflight`** collapses duplicate concurrent calls for the same key into one. The first call executes; the other nine block and share its result. From `golang.org/x/sync/singleflight`:

```go
package main

import (
	"fmt"
	"sync"

	"golang.org/x/sync/singleflight"
)

var sf singleflight.Group

// fetchExchangeRate simulates a slow external API call.
func fetchExchangeRate(pair string) (float64, error) {
	fmt.Printf(">>> actual fetch for %s\n", pair)
	// In production: HTTP call to ECB or similar.
	return 1.0823, nil
}

// getRate uses singleflight to collapse duplicate concurrent fetches.
func getRate(pair string) (float64, error) {
	v, err, _ := sf.Do(pair, func() (any, error) {
		return fetchExchangeRate(pair)
	})
	if err != nil {
		return 0, err
	}
	return v.(float64), nil
}

func main() {
	var wg sync.WaitGroup
	for range 10 {
		wg.Add(1)
		go func() {
			defer wg.Done()
			rate, err := getRate("USD/EUR")
			if err != nil {
				fmt.Println("error:", err)
				return
			}
			fmt.Printf("rate: %.4f\n", rate)
		}()
	}
	wg.Wait()
}
```

```go
package main

// singleflight-style implementation using stdlib only.
type call struct {
	wg  sync.WaitGroup
	val float64
	err error
}

type Group struct {
	mu sync.Mutex
	m  map[string]*call
}

func (g *Group) Do(key string, fn func() (float64, error)) (float64, error) {
	g.mu.Lock()
	if g.m == nil {
		g.m = make(map[string]*call)
	}
	if c, ok := g.m[key]; ok {
		g.mu.Unlock()
		c.wg.Wait()
		return c.val, c.err
	}
	c := &call{}
	c.wg.Add(1)
	g.m[key] = c
	g.mu.Unlock()

	c.val, c.err = fn()
	c.wg.Done()

	g.mu.Lock()
	delete(g.m, key)
	g.mu.Unlock()
	return c.val, c.err
}

var fetchCount atomic.Int64

func fetchExchangeRate(pair string) (float64, error) {
	fetchCount.Add(1)
	fmt.Printf(">>> actual fetch #%d for %s\n", fetchCount.Load(), pair)
	return 1.0823, nil
}

var sg Group

func getRate(pair string) (float64, error) {
	return sg.Do(pair, func() (float64, error) {
		return fetchExchangeRate(pair)
	})
}

	var wg sync.WaitGroup
	for range 10 {
		wg.Add(1)
		go func() {
			defer wg.Done()
			rate, err := getRate("USD/EUR")
			if err != nil {
				fmt.Println("error:", err)
				return
			}
			fmt.Printf("rate: %.4f\n", rate)
		}()
	}
	wg.Wait()
	fmt.Printf("total fetches: %d (out of 10 concurrent calls)\n", fetchCount.Load())
```

<UnderTheHood title="How sync.Once guarantees exactly-one execution">

`sync.Once` contains a `uint32` flag and a `sync.Mutex`. The fast path: the flag starts at 0. `once.Do(f)` checks the flag with an atomic load. If it's 1, return immediately — no lock, branch-predicted correctly because after the first call it's always 1. If it's 0, the goroutine acquires the mutex, checks again (the classic double-check), calls `f()`, atomically stores 1, and releases the mutex. All goroutines that lost the race to get the mutex block until `f` completes; they then see flag=1 and return.

The happens-before guarantee: the call to `f` inside `once.Do` happens before any return from `once.Do`. So the initialization `f` does is visible to every goroutine that subsequently calls `once.Do` — no additional synchronization needed. As of Go 1.26, this is implemented in `sync/once.go` using `atomic.Uint32` and the same pattern. The cost of the slow path (when `f` actually runs) is one mutex acquire/release. The fast path cost is one atomic load — extremely cheap.

</UnderTheHood>

## When to Use a Mutex

Here's the counterpoint I promised, and I'm going to say it plainly: **not everything needs a channel**.

Go's famous proverb is "don't communicate by sharing memory; share memory by communicating." It's a guiding principle, not a law. Channels are excellent for ownership transfer and coordination between goroutines. But for plain shared state — a cache, a counter, a map — a mutex is often simpler, faster, and clearer.

Use a **channel** when:
- You're transferring ownership of data between goroutines.
- You need to signal or synchronize across goroutines.
- You're composing pipeline stages.
- You need the backpressure that a blocked send provides.

Use a **mutex** when:
- You're protecting simple read/write access to shared state.
- Multiple goroutines need to read the same data (use `sync.RWMutex`).
- The pattern would be awkward as a pipeline (e.g., an in-memory cache).

If you find yourself building a goroutine just to own a map or counter, reach for `sync.Mutex` or `sync.Map` instead. The channel adds a goroutine, a scheduling hop, and an allocation. A mutex is a pair of atomic operations. For state, the mutex wins on every axis.

<Exercise n={3} title="Bounded worker pool with errgroup" level="medium">

Implement `processBatch(ctx context.Context, ids []int, maxWorkers int) error` using `golang.org/x/sync/errgroup` and a buffered channel semaphore (`make(chan struct{}, maxWorkers)`) to cap concurrency. Each "worker" should return an error if `id%7 == 0` (simulate a bad payment). The function should return the first error encountered. Use `errgroup.WithContext` so the derived context is cancelled on the first error.

<Solution>

```go
package main

import (
	"context"
	"fmt"
	"sync"
)

// stdlib-only errgroup substitute for illustration.
type Group struct {
	cancel func()
	wg     sync.WaitGroup
	mu     sync.Mutex
	err    error
}

func withContext(ctx context.Context) (*Group, context.Context) {
	ctx, cancel := context.WithCancel(ctx)
	return &Group{cancel: cancel}, ctx
}

func (g *Group) Go(f func() error) {
	g.wg.Add(1)
	go func() {
		defer g.wg.Done()
		if err := f(); err != nil {
			g.mu.Lock()
			if g.err == nil {
				g.err = err
				g.cancel()
			}
			g.mu.Unlock()
		}
	}()
}

func (g *Group) Wait() error {
	g.wg.Wait()
	g.cancel()
	return g.err
}

func processBatch(ctx context.Context, ids []int, maxWorkers int) error {
	g, ctx := withContext(ctx)
	sem := make(chan struct{}, maxWorkers)

	for _, id := range ids {
		select {
		case sem <- struct{}{}:
		case <-ctx.Done():
			break
		}
		g.Go(func() error {
			defer func() { <-sem }()
			if id%7 == 0 {
				return fmt.Errorf("payment %d rejected (divisible by 7)", id)
			}
			fmt.Printf("processed %d\n", id)
			return nil
		})
	}
	return g.Wait()
}

func main() {
	ids := make([]int, 20)
	for i := range ids {
		ids[i] = i + 1
	}
	if err := processBatch(context.Background(), ids, 4); err != nil {
		fmt.Println("batch error:", err)
	}
}
```

The semaphore `make(chan struct{}, maxWorkers)` is acquired before `g.Go` and released inside the goroutine with `defer`. The `select { case sem <- ...; case <-ctx.Done(): break }` stops the outer loop from sending new work once the context is cancelled.

</Solution>

```go
}

type RateCache struct {
	mu      sync.RWMutex
	data    map[string]entry
	sf      sfGroup
	fetch   func(ctx context.Context, pair string) (float64, error)
	ttl     time.Duration
}

func NewRateCache(fetch func(context.Context, string) (float64, error), ttl time.Duration) *RateCache {
	return &RateCache{data: make(map[string]entry), fetch: fetch, ttl: ttl}
}

func (rc *RateCache) Get(ctx context.Context, pair string) (float64, error) {
	rc.mu.RLock()
	e, ok := rc.data[pair]
	rc.mu.RUnlock()
	if ok && time.Now().Before(e.expires) {
		return e.val, nil
	}

	return rc.sf.Do(pair, func() (float64, error) {
		val, err := rc.fetch(ctx, pair)
		if err != nil {
			return 0, err
		}
		rc.mu.Lock()
		rc.data[pair] = entry{val: val, expires: time.Now().Add(rc.ttl)}
		rc.mu.Unlock()
		return val, nil
	})
}

func main() {
	var fetchCount atomic.Int64
	upstream := func(ctx context.Context, pair string) (float64, error) {
		fetchCount.Add(1)
		fmt.Printf("upstream fetch #%d for %s\n", fetchCount.Load(), pair)
		return 1.0823, nil
	}

	rc := NewRateCache(upstream, 5*time.Second)

	var wg sync.WaitGroup
	for range 10 {
		wg.Add(1)
		go func() {
			defer wg.Done()
			v, _ := rc.Get(context.Background(), "USD/EUR")
			fmt.Printf("rate: %.4f\n", v)
		}()
	}
	wg.Wait()
	fmt.Printf("total fetches for 10 concurrent calls: %d\n", fetchCount.Load())
}
```

The TTL check uses a read lock (fast path for warm cache), singleflight collapses concurrent cold-cache fetches, and the write lock only blocks while updating the cache entry. Three concurrency tools, each doing exactly one job.

<Recap>

- **Pipelines** chain goroutines via channels. `defer close(out)` in each stage propagates shutdown automatically.
- **Fan-out** reads one channel across N goroutines. **Fan-in** merges N channels via a `WaitGroup` and a separate closer goroutine.
- **Done/or-done** wraps channels with context cancellation so no goroutine blocks on a receive after the work is abandoned.
- **Generators** stream values on demand. They must use `select` with `ctx.Done()` on every send or they leak when the consumer stops early.
- **Tee** duplicates a stream to two consumers. **Bridge** flattens a channel-of-channels into one stream.
- **Bounded parallelism**: pre-spawn N workers sharing one input channel, or use a buffered channel semaphore to cap dynamically spawned goroutines.
- **`errgroup`** is bounded fan-out with first-error propagation and automatic context cancellation. Compose it with a semaphore for bounded errgroup.
- **Futures** hand back a single async result on a buffered-1 channel. The buffer prevents a goroutine leak when the caller times out.
- **Confinement** eliminates the need for locks by keeping data on one goroutine. Channels carry operations in, not raw data.
- **Heartbeats** prove a worker is alive and making progress. The supervisor reacts when they stop.
- **`sync.Once`** initializes once, safely, across any number of concurrent calls. **`singleflight`** collapses concurrent duplicate calls — the cache-stampede fix.
- **When to use a mutex instead**: plain shared state (caches, counters, maps) reads cleaner and runs faster with `sync.Mutex` or `sync.RWMutex` than with a channel-based actor.

</Recap>
