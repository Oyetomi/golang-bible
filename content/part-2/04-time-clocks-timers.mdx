Let me set the scene. Your payments service needs to measure how long the settlement processor takes — if it runs over 5 seconds, you fire an alert. You write the obvious code:

```go
start := time.Now()
runSettlementProcessor(ctx)
elapsed := time.Since(start) // is this safe? Depends on which clock.
```

Simple. Correct. Or is it? The answer is: **it depends on which clock `elapsed` used**, and that's the whole story of this section.

### Two clocks in one struct

Since Go 1.9, a `time.Time` value carries **two separate readings**:

<Define term="Wall clock" since="Auditability & Compliance (Part 3)">
The **wall clock** (`CLOCK_REALTIME` on Linux) reports civil time — "2026-06-04 15:04:05 UTC". It is what you display to users and store in databases. The OS adjusts it at any moment: NTP can step it forward or backward by arbitrary amounts; DST transitions shift it by an hour. **Never use raw wall-clock arithmetic to measure elapsed time** — a negative or inflated duration is the result, and in Meridian's settlement engine that means wrong SLA alerts or negative-duration charges.
</Define>

<Define term="Monotonic clock">
The **monotonic clock** (`CLOCK_MONOTONIC`) is a nanosecond counter that only ever moves forward. It has no relationship to civil time and is immune to NTP steps and DST transitions. It is the only correct clock for measuring durations — how long the settlement processor ran, how long a lock was held, whether an SLA was breached.
</Define>

<Define term="time.Now()" since="Testing in Go (Part 1)">
`time.Now()` returns a `time.Time` that carries **both** a wall-clock reading and a monotonic reading packed into a single struct. Subtraction via `t2.Sub(t1)` or `time.Since(t)` automatically picks the monotonic readings when both operands have them — so durations computed from two `time.Now()` calls are always correct. The monotonic reading is **stripped** the moment a `time.Time` crosses a serialization boundary (JSON, SQL, Redis, protobuf), so a `time.Time` reconstructed from a database row is wall-only.
</Define>

- A **wall-clock reading** — the civil time reported by the OS (`CLOCK_REALTIME` on Linux). This is what you display to users: "2026-06-04 15:04:05 UTC". The OS can — and does — adjust it: NTP can step it forward or backward, and DST transitions shift it by an hour.
- A **monotonic reading** — a nanosecond counter from a clock that only ever moves forward (`CLOCK_MONOTONIC`). It has no relationship to civil time. It can't be stepped by NTP or warped by DST. It's the right clock for measuring elapsed time.

`time.Now()` fills in **both**. The struct carries them together so that when you subtract two `time.Time` values obtained from `time.Now()`, Go automatically uses the monotonic readings — giving you an elapsed duration that is immune to NTP adjustments and DST.

You don't have to take that on trust. This program measures three seconds of work and, one second in, really steps the system clock back ten seconds with the `settimeofday` system call, which is what a time daemon does when it corrects a fast clock:

```go noverify
// Measures 3 seconds of work while the system clock is stepped back
// 10 seconds, as a time daemon correcting a fast clock would do.
// Linux only; needs CAP_SYS_TIME (run in a container with --cap-add SYS_TIME).
package main

import (
	"fmt"
	"syscall"
	"time"
)

func stepClock(d time.Duration) error {
	tv := syscall.NsecToTimeval(time.Now().Add(d).UnixNano())
	return syscall.Settimeofday(&tv)
}

func main() {
	t0 := time.Now()
	wall0 := t0.Round(0) // same instant, wall clock only: what a database or JSON gives back

	time.Sleep(1 * time.Second)
	fmt.Println("step clock back 10s:", stepClock(-10*time.Second))
	time.Sleep(2 * time.Second)

	t1 := time.Now()
	fmt.Println("time.Since(t0)         (monotonic):", time.Since(t0).Round(time.Millisecond))
	fmt.Println("t1.Sub(wall0)          (wall only):", t1.Sub(wall0).Round(time.Millisecond))
	fmt.Println("t1 wall clock went from", t0.Format("15:04:05"), "to", t1.Format("15:04:05"))

	stepClock(10 * time.Second) // put it back
}
```

Changing the clock needs the `CAP_SYS_TIME` capability, so it runs in a Linux container that grants it:

```text
$ GOOS=linux CGO_ENABLED=0 go build -o ntpdemo .
$ docker run --rm --cap-add SYS_TIME -v $PWD/ntpdemo:/ntpdemo alpine:3.22 /ntpdemo
step clock back 10s: <nil>
time.Since(t0)         (monotonic): 3.008s
t1.Sub(wall0)          (wall only): -6.992s
t1 wall clock went from 15:40:41 to 15:40:34
```

Three seconds really passed. The monotonic reading says so; the wall clock says the work took *minus seven* seconds, because the second reading is seven seconds earlier than the first. Without `--cap-add SYS_TIME` the step fails with `operation not permitted`, which is also why ordinary programs can't do this to your server.

`time.Since(start)` is just `time.Now().Sub(start)` — it uses the monotonic clock too. You're safe.

### When the monotonic reading is stripped

The monotonic reading is stripped in **four important situations**:

1. **Marshaling / unmarshaling** — `MarshalJSON`, `MarshalText`, `MarshalBinary`, `Format()` and `AppendFormat()` only encode the wall-clock reading. (`String()` is the exception: it prints the monotonic reading as `m=+0.001500085`, which is how you can spot it in debug output.) When you deserialize a `time.Time` from a database, JSON payload, or log line, you get **wall only**.
2. **`time.Unix(sec, nsec)` and `time.Date(...)`** — constructing a `time.Time` from parts gives you wall-only.
3. **`t.Round()` and `t.Truncate()`** — these strip the monotonic reading as a side-effect (documented, but people forget). `t.Round(0)` is the idiomatic way to drop monotonic without changing the wall value.
4. **Timezone and calendar operations** — `t.UTC()`, `t.Local()`, `t.In(loc)`, and `t.AddDate(y, m, d)` all strip the monotonic reading too. This catches people who store `parsed.UTC()` and assume the result still carries monotonic. (The package rule: any operation whose result has no meaning outside the current process drops the monotonic part.)

This is the source of the negative-duration bugs people see in production. A common example: a worker picks a `time.Time` off a Redis queue where it was serialized as a Unix timestamp. It subtracts that from `time.Now()`, and during an NTP step the wall clock jumps backward — the result goes negative.

<Callout kind="warn" title="Serialization boundary = monotonic stripped">

Every time a `time.Time` crosses a serialization boundary — JSON, protobuf, SQL, Redis, gob — it loses its monotonic reading. A `time.Time` reconstructed from a database column is **wall-only**. Subtracting a wall-only time from `time.Now()` is fine for an age ("how long ago was this payment initiated?"), but it's exposed to clock steps like the one above.

A database can take something else away too: precision. Postgres stores timestamps to the **microsecond**; Go on Linux reads the clock to the **nanosecond**. Round-tripping a real `time.Now()` through Postgres:

```go noverify
// Stores a time.Time in Postgres and reads it back.
package main

import (
	"database/sql"
	"encoding/json"
	"fmt"
	"log"
	"os"
	"time"

	_ "github.com/jackc/pgx/v5/stdlib"
)

func main() {
	db, err := sql.Open("pgx", os.Getenv("DATABASE_URL"))
	if err != nil {
		log.Fatal(err)
	}
	defer db.Close()

	created := time.Now()
	var back time.Time
	if err := db.QueryRow(`SELECT $1::timestamptz`, created).Scan(&back); err != nil {
		log.Fatal(err)
	}

	fmt.Println("sent:     ", created)
	fmt.Println("read back:", back)
	fmt.Println("equal (==):     ", created == back)
	fmt.Println("Equal():        ", created.Equal(back))
	fmt.Println("lost precision: ", created.Sub(back))
	fmt.Println("Truncate(µs).Equal:", created.Truncate(time.Microsecond).Equal(back))

	b, _ := json.Marshal(created)
	var fromJSON time.Time
	json.Unmarshal(b, &fromJSON)
	fmt.Println("\nJSON:", string(b))
	fmt.Println("JSON round trip Equal:", created.Equal(fromJSON), "| has monotonic:", fromJSON != fromJSON.Round(0))
}
```

<UnderTheHood title="How time.Time packs two clocks into one struct">

`time.Time` is a three-field struct (as of Go 1.9+):

```go
// Simplified from src/time/time.go
type Time struct {
	wall uint64 // packed: hasMonotonic bit + wall seconds (33 bits) + nanoseconds (30 bits)
	ext  int64  // if hasMonotonic=1: monotonic nanoseconds since process start
	// if hasMonotonic=0: seconds since Jan 1 year 1 (full range)
	loc *Location
}
```

When `hasMonotonic=1` (i.e., came from `time.Now()`), the `wall` field stores the wall-clock seconds since Jan 1 2006 in 33 bits (enough until ~2157), and `ext` holds the monotonic nanoseconds since process start. When `hasMonotonic=0` (constructed or deserialized), `wall` stores nanoseconds only and `ext` holds the full wall seconds from year 1.

`Sub()` checks the `hasMonotonic` bit on both operands. If **both** have it, it subtracts `ext` values — monotonic, perfect. If either is missing the bit, it falls back to wall arithmetic. This is why mixing a `time.Now()` value with a `time.Unix()` value silently degrades to wall-based subtraction.

`t.Monotonic()` is not exported (there's no public `t.MonotonicNanos()` accessor), but `t.String()` and `fmt` will print `m=+0.012345678` when the monotonic reading is present.

**Go version note:** Monotonic clock support was added in Go 1.9. The `time.Time` struct layout (wall/ext) has been stable since then. As of Go 1.26, there are no changes to this layout.

</UnderTheHood>

<ELI5
  concept="Why a ticker must be stopped"
  analogy="An alarm that keeps ringing in an empty room because nobody switched it off."
  role="timekeeper"
>

`time.Ticker` runs on a goroutine inside the runtime that keeps firing forever. Nothing stops it when the function that created it returns — the runtime has no idea you have lost interest.

So a ticker created per request, without `defer ticker.Stop()`, leaks a runtime timer and its goroutine for every single request. Under load that is a slow, silent climb that ends in memory exhaustion.

`time.After` used to be the same trap wearing a friendlier face, and the fix it needs today is different from the one you will find in older writing:

```go
select {
case v := <-ch:
	return v
case <-time.After(time.Hour): // allocates a timer on every call
	return ErrTimeout
}
```

**Before Go 1.23** the abandoned timer stayed alive until it fired, so taking the first branch left an hour-long timer holding memory — a real leak. **Since 1.23** an unreferenced timer can be garbage collected before firing, so that leak is gone.

What did not go away is the **allocation**. Every call still creates a fresh timer, so putting `time.After` inside a hot `select` loop is avoidable churn even though nothing leaks. The fix is the same either way: create one `time.NewTimer` outside the loop and `Reset` it.

The habit that still matters unconditionally is the ticker one: `defer ticker.Stop()` at creation, always. A ticker fires forever and the runtime has no way to know you lost interest, so nothing collects it for you.

</ELI5>

## Timers and Tickers Without Leaks

*Stop 2 of 4.*

Here's where I watch engineers casually leak timer work like they're being paid by the leak. Let me fix that.

### time.Timer: Stop, Reset, and stale values

`time.NewTimer(d)` returns a `*Timer` with a channel `C`. After duration `d`, the runtime sends one value on `C`. Simple. But stopping it correctly is not simple.

```go
retry := time.NewTimer(5 * time.Second) // retry the payment in 5s
if paymentSucceeded {
	retry.Stop() // returns false if it had already fired or been stopped
}
```

For Go 1.23 and later, channel-based timers use a synchronous channel: after `Stop` or `Reset` returns, a later receive from `C` cannot observe a stale value from the old timer setting. Before Go 1.23, `Timer.C` was buffered and a stopped timer could leave a stale value waiting in the channel.

If you support older Go versions, use the compatibility stop-and-drain idiom and make the drain non-blocking:

```go
retry := time.NewTimer(5 * time.Second)
if !retry.Stop() {
	select {
	case <-t.C:
	default:
	}
}
```

`Stop()` returns `false` if the timer has already expired or already been stopped. In Go 1.23+, `false` does **not** mean there is exactly one value waiting in `C`; the non-blocking drain is what keeps the old compatibility pattern safe.

**Go 1.23 change:** Before Go 1.23, `Timer.C` was buffered with capacity 1, and unexpired timers were not garbage-collected until they fired or were stopped. As of Go 1.23 (and in Go 1.26), `Timer.C` is synchronous (capacity 0), `Stop`/`Reset` eliminate stale channel values for channel timers, and unreferenced timers are GC-eligible even before firing. Call `Stop` when you want to cancel the timer's action, not as a GC requirement.

### time.After: the subtle loop allocation

This one is insidious. People write it constantly:

```go
// WASTEFUL — allocates a new timer in a hot select loop
func processOrders(ctx context.Context, orders <-chan Order) {
	for {
		select {
		case <-ctx.Done():
			return
		case <-time.After(30 * time.Second): // allocates a timer per iteration
			runReconciliation()
		case o := <-orders:
			handle(o)
		}
	}
}
```

`time.After(d)` creates a new timer every call. In a `select` loop, if the `orders` case fires before the 30-second timer expires, the timer is abandoned. Since Go 1.23, an unreferenced abandoned timer can be collected before it fires, so this is no longer the old pre-Go 1.23 timer-retention trap. It is still a needless allocation in a hot loop.

The fix: use `time.NewTimer` outside the loop and reset it:

```go
// CORRECT — one timer, reset each iteration
func processOrders(ctx context.Context, orders <-chan Order) {
	reconcileTicker := time.NewTicker(30 * time.Second)
	defer reconcileTicker.Stop()
	for {
		select {
		case <-ctx.Done():
			return
		case <-reconcileTicker.C:
			runReconciliation()
		case o := <-orders:
			handle(o)
		}
	}
}
```

**Go 1.23 timer GC change:** Before Go 1.23, an unreferenced timer created by `time.After` would NOT be GC'd until it fired — the runtime held a reference internally. This made `time.After` in tight loops a genuine leak. As of Go 1.23 (stable in Go 1.26), **unreferenced timers are GC-eligible even if they haven't fired**. The runtime no longer prevents collection. So `time.After` in a hot loop is less catastrophic than it used to be — but it still allocates a new timer on every iteration, which is wasteful. Use `time.NewTicker` or `time.NewTimer`+`Reset` anyway.

### time.Ticker: stop it or it runs forever

<Define term="time.Ticker — and the leak">
`time.NewTicker(d)` returns a `*Ticker` whose channel `C` receives a value every `d`. Unlike a one-shot `Timer`, a Ticker fires repeatedly until you call `Stop()`. **If you keep a ticker reachable and forget `Stop()`, it keeps firing.** Since Go 1.23, an unreachable ticker can be garbage-collected, but reachable tickers in long-lived services and tests still need explicit cleanup. The fix costs one line: `defer t.Stop()` immediately after `NewTicker`. **On the job:** Meridian's reconciliation service once processed 10 ms of statements per tick but never stopped its ticker between tests; under load, it accumulated thousands of live tickers and OOM'd the pod.
</Define>

```go
t := time.NewTicker(1 * time.Second)
// BUG: forgot defer t.Stop()
// The ticker fires forever, even if no one reads C.
// The goroutine and channel are never reclaimed.
go func() {
	for range t.C {
		doWork()
	}
}()
```

Always `defer t.Stop()` immediately after creating a ticker when you control its lifetime. Stopping a ticker does not close `t.C`; it just stops future ticks.

```go
		case <-time.After(time.Minute):
		default:
		}
	})
	reuse := time.NewTimer(time.Minute)

		reuse.Reset(time.Minute)
		select {
```

<UnderTheHood title="How the runtime manages timers (and the Go 1.23 heap change)">

Internally, the Go runtime maintains a **timer heap** — a min-heap of pending timers keyed by their fire time. Before Go 1.23, this heap was global (per-P since Go 1.14, but still runtime-held), and the runtime kept a reference to every timer in the heap regardless of whether user code still held a reference. This meant an abandoned `time.After` timer was **not** eligible for GC until it fired and was popped from the heap.

In Go 1.23, the timer implementation was rewritten. The key change: the runtime no longer prevents GC of timer objects. If user code drops all references to a `*Timer`, the GC can collect it even before it fires. This makes `time.After` in a loop far less damaging than before, though it still allocates.

The other Go 1.23 change: `Timer.C` became synchronous, and `Timer.Stop` and `Timer.Reset` now guarantee that later receives will not observe stale values from the previous timer state. Before 1.23 there was a narrow race window. As of Go 1.26, these guarantees hold.

**Practical takeaway for Go 1.26:** for channel timers, you no longer drain after every `Stop`/`Reset` to avoid stale values. Keep the non-blocking drain only when writing compatibility code for older Go versions. The catastrophic pre-1.23 "timer leaks until it fires" scenario is gone once the timer becomes unreachable and GC runs.

</UnderTheHood>

## Injecting a Clock for Tests

*Stop 3 of 4.*

<Define term="Clock interface (injectable for tests)" since="Software Design & Architecture (Part 1)">
A **Clock interface** is a tiny interface — typically `Now() time.Time` and optionally `After(d time.Duration) <-chan time.Time` — that wraps the real `time.Now()` and `time.After()` calls. In production you inject a `realClock` that delegates straight to the stdlib. In tests you inject a `FakeClock` you control: pin the time to 16:59:59, assert one settlement date; advance 2 seconds, assert the next day. No `time.Sleep`. No flakiness. **Why it matters:** a settlement engine that calls `time.Now()` directly cannot be tested at exact DST boundaries or cutoff edges — every test that needs specific times either sleeps (slow, flaky) or gets lucky. The interface costs twenty lines and makes the tests deterministic forever.
</Define>

Here's the problem. Your payments service has a settlement window: funds cleared before 5 p.m. UTC settle same day; after 5 p.m. they roll to the next day. You write the logic using `time.Now()`:

```go
func settlementDay(now time.Time) time.Time {
	cutoff := time.Date(now.Year(), now.Month(), now.Day(),
		17, 0, 0, 0, time.UTC)
	if now.Before(cutoff) {
		return now.UTC().Truncate(24 * time.Hour)
	}
	return now.UTC().Truncate(24 * time.Hour).Add(24 * time.Hour)
}
```

`settlementDay` takes a `time.Time` argument, so it's already testable — great. But the *caller* probably calls `time.Now()` directly, and you want to test that the caller correctly threads the current time through, including across DST transitions and at the exact cutoff boundary. You need to **inject** the clock.

### The Clock interface

Define a minimal interface at the point of use (consumer-defined, per the Go proverb):

```go
// Clock abstracts time.Now() and time.After() for testability.
type Clock interface {
	Now() time.Time
	After(d time.Duration) <-chan time.Time
}
```

Your real production clock is a thin wrapper:

```go
type realClock struct{}

func (realClock) Now() time.Time                         { return time.Now() }
func (realClock) After(d time.Duration) <-chan time.Time { return time.After(d) }
```

Your settlement engine takes the interface:

```go
type SettlementEngine struct {
	clock Clock
}

func NewSettlementEngine(clock Clock) *SettlementEngine {
	return &SettlementEngine{clock: clock}
}

func (e *SettlementEngine) SettlementDay() time.Time {
	return settlementDay(e.clock.Now())
}
```

### The fake clock

For tests, build a `FakeClock` you can wind forward deterministically:

```go
type FakeClock struct {
	now time.Time
}

func NewFakeClock(t time.Time) *FakeClock { return &FakeClock{now: t} }

func (f *FakeClock) Now() time.Time { return f.now }

func (f *FakeClock) After(d time.Duration) <-chan time.Time {
	ch := make(chan time.Time, 1)
	ch <- f.now.Add(d) // fake: send immediately
	return ch
}

func (f *FakeClock) Advance(d time.Duration) { f.now = f.now.Add(d) }
```

Now your test is deterministic, fast, and exercises the exact boundary:

```go
func TestSettlementDayAtCutoff(t *testing.T) {
	// One second before the 5 p.m. cutoff.
	before := time.Date(2026, 6, 4, 16, 59, 59, 0, time.UTC)
	fc := NewFakeClock(before)
	engine := NewSettlementEngine(fc)

	day := engine.SettlementDay()
	want := time.Date(2026, 6, 4, 0, 0, 0, 0, time.UTC)
	if !day.Equal(want) {
		t.Errorf("before cutoff: got %v, want %v", day, want)
	}

	// One second after the 5 p.m. cutoff — should roll to next day.
	fc.Advance(2 * time.Second)
	day = engine.SettlementDay()
	want = time.Date(2026, 6, 5, 0, 0, 0, 0, time.UTC)
	if !day.Equal(want) {
		t.Errorf("after cutoff: got %v, want %v", day, want)
	}
}
```

No `time.Sleep`. No flakiness. No waiting for real wall-clock boundaries.

## Wall-Clock Correctness

*Stop 4 of 4.*

Now the part that bites fintech engineers specifically. Wall-clock correctness — timezones, DST, the reference-time layout, and how to store and serialize `time.Time` without data loss.

### The IANA timezone database

<Define term="Timezone / IANA database">
A **timezone** is a named set of rules that maps UTC offsets to calendar ranges, including DST transitions (e.g. `"America/New_York"` is UTC-5 in winter, UTC-4 in summer). The **IANA timezone database** (also called `tzdata` or the Olson database) is the authoritative, globally maintained registry of these rules. Go embeds it directly in the stdlib (`time/tzdata`, Go 1.15+) so your binary carries correct timezone rules even in a scratch Docker image with no `/usr/share/zoneinfo`. **Never use abbreviations** like `"EST"` or `"PST"` — they're ambiguous (multiple countries use them with different DST rules) and Go's parser rejects many; always use `"Continent/City"` IANA names.
</Define>

Go ships the IANA timezone database embedded in the standard library (Go 1.15+). You don't need to install `tzdata` on your deployment image, and you don't need to worry about the host OS's timezone files being stale. Load a location with `time.LoadLocation`:

```go
nyc, err := time.LoadLocation("America/New_York")
if err != nil {
	return fmt.Errorf("load location: %w", err)
}
now := time.Now().In(nyc)
```

The IANA database name is always of the form `"Continent/City"` (e.g., `"Europe/London"`, `"Asia/Tokyo"`, `"America/Sao_Paulo"`). Never use abbreviations like `"EST"` or `"PST"` — they're ambiguous and don't encode DST rules.

### DST pitfalls

DST transitions are where "add 24 hours" silently does the wrong thing.

```go
// WRONG: adding 24 hours across a DST boundary
loc, _ := time.LoadLocation("America/New_York")
// 2026-03-08 02:00 is the spring-forward cutoff in New York.
start := time.Date(2026, 3, 7, 12, 0, 0, 0, loc) // noon on March 7
nextDay := start.Add(24 * time.Hour)             // noon on March 8? NO.
// Spring forward skips one hour — so nextDay lands at 13:00, not 12:00.

// CORRECT: use AddDate for "same time next day"
tomorrow := start.AddDate(0, 0, 1) // noon on March 8 in local time
```

`AddDate` respects the timezone's DST rules. `Add(24 * time.Hour)` adds exactly 24 hours of elapsed time, which crosses the DST boundary wrong.

### The reference-time layout

<Define term="Reference-time layout (2006-01-02)">
Go formats and parses times by **example, not by format codes**. Instead of `%Y-%m-%d`, you write the **reference time** — `Mon Jan 2 15:04:05 MST 2006` — formatted exactly the way you want your output to look. That specific moment (January 2, 2006, 15:04:05 UTC-7) was chosen because each component is a unique number: year=2006, month=01, day=02, hour=15, minute=04, second=05, timezone offset=-0700. Go recognises them by position and value, so `"2006-01-02"` is ISO date format and `"01/02/06"` is US date format. **Getting it wrong silently produces garbage output** — writing `2006-02-01` instead of `2006-01-02` swaps month and day without error. Use `time.RFC3339` and `time.RFC3339Nano` stdlib constants for API timestamps.
</Define>

Go's time formatting does not use `%Y-%m-%d` strftime codes. Instead, you write the reference time — `Mon Jan 2 15:04:05 MST 2006` — formatted as you want output:

```go
// The reference time is: Mon Jan 2 15:04:05 MST 2006
// Which in numeric form is: 01/02 03:04:05PM '06 -0700
// Each number is unique:
//   year:   2006
//   month:  01
//   day:    02
//   hour:   15 (24h) or 03 (12h)
//   minute: 04
//   second: 05
//   timezone offset: -0700

t := time.Now().UTC()
fmt.Println(t.Format("2006-01-02 15:04:05"))        // ISO 8601 datetime
fmt.Println(t.Format("2006-01-02T15:04:05Z07:00"))  // RFC 3339
fmt.Println(t.Format(time.RFC3339Nano))             // stdlib constant
```

The predefined `time.RFC3339` and `time.RFC3339Nano` constants cover the most common formats. For payment records, store RFC 3339 in databases and APIs — it's unambiguous, includes timezone, and parses everywhere.

### Storage and serialization rules

<ConceptGrid cols={3}>
  <ConceptCard label="Store UTC at the boundary">Convert to UTC before writing to a database, queue, or log. Reconstruct local time for display only — not for storage. Use `t.UTC()` before `time.Time.MarshalJSON()` or before inserting to SQL.</ConceptCard>
  <ConceptCard label="Monotonic is dropped by marshaling">Any marshaling (JSON, gob, SQL) drops the monotonic reading. That's fine — you don't need monotonic on stored times. Never try to preserve it across a serialization boundary.</ConceptCard>
  <ConceptCard label="Parse with time.Parse or time.ParseInLocation">Use `time.Parse(layout, value)` for timezone-included strings (RFC 3339). Use `time.ParseInLocation(layout, value, loc)` when the string has no timezone and you know the intended one.</ConceptCard>
  <Gotcha>Never store a `time.Time` as a Unix timestamp integer in a language-agnostic API without also storing the precision (seconds vs milliseconds vs nanoseconds). Payment timestamps need nanosecond precision — use RFC 3339 Nano or a `TIMESTAMPTZ` column.</Gotcha>
</ConceptGrid>

<UnderTheHood title="The IANA tz database in Go and DST disambiguation">

Go embeds the IANA timezone database in `time/tzdata` (Go 1.15+). Importing `_ "time/tzdata"` in your `main` package forces the embedded DB into the binary, making `time.LoadLocation` work even in scratch Docker images with no `/usr/share/zoneinfo`. If you don't import it explicitly, Go falls back to the OS's zoneinfo files; if those are absent, `LoadLocation` returns an error.

DST transitions introduce an ambiguity problem: during the "fall back" transition, a local time like `01:30:00 America/New_York` occurs **twice** — once in EDT (UTC-4) and once in EST (UTC-5). Measured on Go 1.27, both `time.Date(2026, 11, 1, 1, 30, 0, 0, ny)` and `time.ParseInLocation` of `2026-11-01 01:30` chose EDT, the earlier instant, but the documentation explicitly says the choice is **not guaranteed**. The opposite case, the spring-forward gap, is just as surprising: 02:30 on 8 March 2026 doesn't exist in New York, and `time.Date` returned `01:30:00 EST`. For financial systems, always store and exchange UTC timestamps — never local times — to avoid this ambiguity entirely.

`time.Time.Round(0)` is the idiomatic way to strip the monotonic reading without changing the wall-clock value. It's used frequently in tests to compare stored times (which have no monotonic reading) to computed times.

```go
	"fmt"
	"time"
```

```go
func settlementDay(now time.Time, cutoffHour int, loc *time.Location) time.Time {
```

```go
}
```

`defer ticker.Stop()` runs whether we return due to context cancellation or any other path. The `select` has two cases — the ticker and the context — so the loop exits immediately when the context is done, no matter where in the tick interval we are.

</Solution>

<Recap>

You now own the time package at the level it deserves:

- `time.Now()` returns a `time.Time` carrying **both** a wall-clock reading and a **monotonic** reading. `Sub` and `Since` use monotonic when both operands have it — immune to NTP steps and DST transitions.
- The monotonic reading is **stripped** by marshaling, `time.Unix()`, `time.Date()`, `Round()`, `Truncate()`, `In()`, `Local()`, `UTC()`, and `AddDate()`. A `time.Time` from a database or JSON is wall-only. Subtracting it from `time.Now()` uses wall arithmetic — safe for ages, vulnerable to NTP in tight timing loops.
- **Timers:** call `Stop()` when you need to cancel a timer's action. In Go 1.23+, channel timers no longer require stop-and-drain to avoid stale values; use a non-blocking compatibility drain only for older Go support. Avoid `time.After` inside hot select loops — use `time.NewTicker` or a reusable timer outside the loop instead.
- **Go 1.23:** unreferenced timers are GC-eligible even before firing. `Stop`/`Reset` semantics tightened. The catastrophic pre-1.23 `time.After` leak is gone, but allocating a timer on every loop iteration is still wasteful.
- **Clock injection:** define a two-method `Clock` interface, use `realClock` in production, and drive a `FakeClock` in tests. No flakiness, no sleeps, deterministic boundary coverage.
- **Wall-clock correctness:** use IANA names (`"America/New_York"`), never abbreviations. Use `AddDate` not `Add(24*time.Hour)` for "next day" across DST. Store UTC at every serialization boundary. Format with Go's reference time `2006-01-02 15:04:05`.
- **Go 1.25:** `testing/synctest` is the stdlib answer for virtual-time concurrency tests — see the Testing chapter for the full treatment.
