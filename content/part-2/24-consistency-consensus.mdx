<HeroCard label="Part 2 · Chapter 24" title="Consistency & Consensus">

Chapter 23 ended with a rule: no single machine can trust its own view, so let a majority decide. This chapter is how. **Consensus** is the problem of getting several machines to agree on a sequence of decisions (seat A7 went to Alice; then B4 to Bob) such that once any of them treats a decision as final, all of them always will, even as machines crash, pause, and get cut off.

Raft is the consensus algorithm most systems use today, and etcd is the most-used Raft implementation: Kubernetes keeps its entire state in it. This chapter runs a real three-member etcd cluster and puts the cinema's hardest question to it (who gets the seat?), then partitions it, kills its leader, and watches what the guarantees cost. The lab builds the one rule at the heart of Raft's safety.

Six stops. If you get lost, come back here:

1. **Linearizability.** The promise that a cluster behaves like one copy.
2. **One seat, one buyer.** Compare-and-swap on a linearizable store, across three members.
3. **The price (CAP).** A partition: which side keeps working, and which answers go stale.
4. **Raft.** Terms, leaders, a replicated log, and what a leader's death costs.
5. **Commit safely.** The majority rule, and the trap it avoids.
6. **Consensus in practice.** What to put in etcd, and what not to.

## The lab bench

Three etcd v3.7.2 members, `e1`, `e2` and `e3`, in Docker. They reach each other only over a network called `raft`; clients reach them over a network called `clients`. Disconnecting a member from `raft` partitions it from its peers while clients can still talk to it, which is what a real network partition looks like from a client that happens to be on the wrong side. A small tool, `kv`, uses the official Go client (`go.etcd.io/etcd/client/v3`) and runs in a container on the `clients` network.

```text
$ etcdctl endpoint status -w table
|  e1:2379 | 5649caf7824fc517 |   3.7.2 | … |      true |      false |         2 |         11 | …
|  e2:2379 | ea98180f58bfa761 |   3.7.2 | … |     false |      false |         2 |         11 | …
|  e3:2379 | 916ba04abc9fac6c |   3.7.2 | … |     false |      false |         2 |         11 | …
```

(The columns shown: endpoint, member ID, version, is leader, is learner, Raft term, Raft index.) e1 is the leader, in term 2, and all three have the same log up to index 11.

## Linearizability

*Stop 1 of 6.*

### Step 1: the promise

Chapter 20's replica answered from the past: a booking made on the primary wasn't there when the page read from the replica. **Linearizability** is the strongest promise a replicated store can make instead: **it behaves as if there were one copy**, and every operation takes effect at a single instant between when it was sent and when it returned. In particular, once any read has returned a value, every later read (by anyone, from any member) returns that value or a newer one. No going back in time.

### Step 2: in etcd

etcd's reads are linearizable by default: the member handling a read confirms with the leader that it has everything committed up to that moment (a "ReadIndex" round trip through a majority) before answering. A **serializable** read skips that and answers from the member's own copy: cheaper, and possibly stale. Both are one option apart in the Go client, and stop 3 measures the difference when it matters.

## One Seat, One Buyer

*Stop 2 of 6.*

### Step 1: three box offices, three members

Uniqueness ("this seat is sold at most once") is exactly the kind of decision that needs linearizability: two buyers each checking a stale copy would both see "free". `kv sell` has three box offices, each connected to a **different** member, race for each of 200 seats with an etcd transaction: "if the seat key doesn't exist yet (its create revision is 0), create it with my name". A compare-and-swap, decided by the cluster:

```go noverify
// main.go, lines 85–125
	case "sell":
		// Each box office talks to a different member. For every seat, all
		// three try at once: "create seat key only if it doesn't exist".
		offices := []*clientv3.Client{client("e1"), client("e2"), client("e3")}
		multi, none := 0, 0
		revs := map[int64]bool{}
		for i := range *rounds {
			key := fmt.Sprintf("sale/inception/show-%03d/A7", i)
			var wg sync.WaitGroup
			var mu sync.Mutex
			won := 0
			for o, oc := range offices {
				wg.Go(func() {
					resp, err := oc.Txn(context.Background()).
						If(clientv3.Compare(clientv3.CreateRevision(key), "=", 0)).
						Then(clientv3.OpPut(key, fmt.Sprintf("office-%d", o+1))).
						Commit()
					if err != nil {
						log.Fatal(err)
					}
					if resp.Succeeded {
						mu.Lock()
						won++
						revs[resp.Header.Revision] = true
						mu.Unlock()
					}
				})
			}
			wg.Wait()
			switch won {
			case 0:
				none++
			case 1:
			default:
				multi++
			}
		}
		fmt.Printf("%d seats, three offices on three members racing for each: sold twice %d times, never sold %d times, %d distinct revisions for %d sales\n",
			*rounds, multi, none, len(revs), *rounds-none)

	case "writer":
```

```text
200 seats, three offices on three members racing for each: sold twice 0 times, never sold 0 times, 200 distinct revisions for 200 sales
```

**Every seat sold exactly once**, 200 of 200, though the three requests for each arrived at three different machines at the same moment. Each transaction goes to the leader, which puts them in one order in its log; the first to be applied creates the key, and the others find it exists.

### Step 2: a fencing token with every sale

Every successful sale also got a distinct **revision**: etcd's revision is a single counter for the whole cluster, incremented by every write, so it's strictly ordered across all members. That's chapter 23's fencing token without extra work: store the sale's revision with the booking, and a storage system can refuse any write carrying an older one. (etcd's own leases and locks work this way: the lock key's creation revision is the token.)

## The Price

*Stop 3 of 6.*

### Step 1: partition a member

```text
put seat/A7=free via e1,e2,e3: ok, revision 208, in 5ms
$ docker network disconnect raft e3        # e3 loses its peers; clients can still reach it
put seat/A7=booked:alice via e1: ok, revision 209, in 4ms
get seat/A7 from e3 (serializable): free, in 4ms
get seat/A7 from e3 (linearizable): error after 3.002s: context deadline exceeded
put seat/A7=booked:bob via e3: error after 3.003s: context deadline exceeded
get seat/A7 from e2 (linearizable): booked:alice, in 7ms
$ docker network connect --alias peer-e3 raft e3   # the partition heals
        (e3 rejoined its peers after 3.7 s)
get seat/A7 from e3 (serializable): free, in 5ms
        (e3's own copy caught up 5.3 s after the partition healed)
get seat/A7 from e3 (serializable): booked:alice, in 3ms
```

Step by step:

- e3 is cut off from e1 and e2. The **majority side** (e1, e2) carries on: A7 is booked for Alice through e1 in 4 ms, and a linearizable read from e2 returns it.
- A **serializable read from e3 returns `free`**: its own copy, frozen when the partition started. Fast, and wrong.
- A **linearizable read from e3 fails** after the client's 3 s deadline: e3 can't confirm with a majority that it's current, so it doesn't answer.
- A **write through e3 fails** too: nothing can be committed without a majority, so Bob can't book A7 from the wrong side.
- After the partition heals, e3 rejoined its peers in **3.7 s** and its own copy showed the booking **5.3 s** after the heal: it had to hear from the leader, then receive and apply the entries it missed.

### Step 2: CAP, measured

This is the **CAP theorem** in practice: when the network **P**artitions, a system must choose between **C**onsistency (every answer is the latest: linearizable) and **A**vailability (every member answers). etcd chooses consistency: the minority side refuses rather than answer from the past or accept writes the majority doesn't know about. Chapter 20's leaderless store with W=1 chose availability, and got a conflict. Neither is wrong; for a seat that can be sold once, consistency is the one you want.

One detail from e3's log: when it rejoined, it sent a **PreVote** request at term 2 before trying to become a candidate, and stayed a follower when the others said they had a leader. Without PreVote, a member that spent the partition timing out and incrementing its term would disrupt the healthy leader the moment it came back.

## Raft

*Stop 4 of 6.*

### Step 1: how Raft works, in four ideas

- **Terms**: time is divided into numbered terms. Each term has at most one leader. Terms only go up, and every message carries its sender's term, so a stale leader (from a lower term) is recognised and ignored the moment it speaks: a fencing token built into the protocol.
- **Elections**: members expect regular heartbeats from the leader. A member that hears nothing for its **election timeout** (randomised, around 1 s in etcd's defaults) starts a new term and asks for votes. A member votes for at most one candidate per term, and only for one whose log is at least as up to date as its own. Whoever gets a majority is leader.
- **The replicated log**: the leader appends every write to its log and sends it to the followers. An entry is **committed** once it's stored on a majority, and only then applied to the key-value store and acknowledged to the client.
- **Safety**: any two majorities overlap, so every future leader's majority includes a member that has every committed entry, and the voting rule makes sure only such a member can win.

### Step 2: kill the leader

```text
before:
  e1:2379  leader=False term=3 index=1097
  e2:2379  leader=False term=3 index=1097
  e3:2379  leader=True  term=3 index=1097
$ docker kill e3     # the leader dies, at about 3 s
  3.54s  writes start failing: context deadline exceeded
  4.58s  writes succeed again, after 1.039s without
497 writes succeeded, 3 failed
after:
  e1:2379  leader=False term=4 index=1595
  e2:2379  leader=True  term=4 index=1595
```

A writer commits a heartbeat every 10 ms. At about 3 s the leader, e3, is killed. Writes failed from 3.54 s and succeeded again at 4.58 s: **1.04 s without writes**, the election timeout plus one election. e2 became leader in **term 4** (up from 3), and the log carried on from where the committed entries left it; **3 of about 500 writes** failed, and none was lost: each either committed or reported an error. (The same experiment earlier, with e1 as the leader: 1.038 s, also term 3 to 4 in its run.)

The 1 s is a choice. A shorter election timeout means faster failover and more false elections when the network is slow (chapter 23's detector, again); etcd's tuning guide sizes the heartbeat interval from the round-trip time between members, and the election timeout at several times the heartbeat interval.

## Commit Safely

*Stop 5 of 6.*

### Step 1: the rule

The leader keeps, for every member, the highest log index that member has stored (`matchIndex`). The commit index is the largest index stored on a majority. With one extra condition, and it's the subtle heart of Raft:

> A leader only commits an entry **from its own term** by counting replicas. Earlier-term entries become committed only because a later, current-term entry after them is committed.

### Step 2: why (Figure 8)

Raft's paper shows why in its Figure 8. An entry from term 2 can end up on a majority of members *after* its leader has crashed, via a later leader in term 4 re-sending it. If that leader counted replicas and marked it committed, and then crashed, a member that never received it but has an entry from term 3 could win the next election (its last entry's term, 3, is higher than 2) and **overwrite** the "committed" entry. A seat sold, then unsold. Requiring a current-term entry to commit closes that window: once the term-4 entry is on a majority, no member without it can win an election. The lab implements the rule, Figure 8 included.

## In Practice

*Stop 6 of 6.*

### Step 1: what belongs in a consensus store

Consensus is expensive: every write waits for a majority, and during an election nothing is written. So systems keep **small, critical, decision-shaped** data in it and everything else elsewhere:

- **Leader election and locks** for the cinema's services (the hold sweeper of chapter 13, done with an etcd lease instead of a Redis key: the lease's revision is its fencing token).
- **Configuration and membership**: which replicas exist, which shard lives where (chapter 21's slot map is exactly this kind of data; Kubernetes stores its whole desired state in etcd).
- **Uniqueness decisions** that must never be wrong, as in stop 2.

Not the seat maps under opening-night load (chapter 21's Redis Cluster), not the bookings table (Postgres), not metrics. etcd's own guidance is a few gigabytes at most, with a default quota of 2 GB (visible in the status table above).

### Step 2: what the chain of chapters built

Replication (20) copies data and can lose it on failover. Sharding (21) splits it and loses cross-shard atomicity. Storage engines (22) decide how it's written. Chapter 23 showed that no node can trust its own view. Consensus, here, is how a group decides anyway: a majority, a log, terms that fence out the past. Most production systems combine them: consensus for the few decisions that must be single and final, and faster, weaker machinery for everything else.

## Exercises

These use the etcd cluster and the `kv` tool from this chapter.

<Exercise n={1} title="Partition the leader" level="easy">

Disconnect the **leader** from the `raft` network (instead of a follower) and run `kv writer` through all three members. What happens to writes, and what does the old leader do?

<Solution>

The two followers stop hearing heartbeats, one times out after about a second, wins an election in a new term with the other's vote, and writes resume through it (a gap of about a second, as when the leader was killed). The old leader, still running, can't reach a majority: etcd's CheckQuorum makes it step down after an election timeout, so it stops accepting writes, and a client talking only to it gets errors, not a split brain. When the partition heals, it sees the higher term and becomes a follower.

</Solution>

</Exercise>

<Exercise n={2} title="Serializable, on purpose" level="easy">

When is a serializable read the right choice? Give one cinema read that can use it and one that must not.

<Solution>

The public seat map can: a copy that's a moment old is fine, and serializable reads keep working on a member that's partitioned or while an election runs, which spreads load across all members. The check inside a sale must not: "is A7 free?" must be linearizable (or better, part of the compare-and-swap itself, as in stop 2), or two buyers on different members could both see "free".

</Solution>

</Exercise>

<Exercise n={3} title="Lock the sweeper with etcd" level="medium">

Replace chapter 13's Redis lease with `go.etcd.io/etcd/client/v3/concurrency`: a `Session` (a lease with keep-alives) and an `Election`. Kill the leader process with SIGKILL and time how long until another replica leads. Then freeze it with SIGSTOP: what stops the frozen leader's writes?

<Solution>

After SIGKILL, keep-alives stop and the lease expires after its TTL (the session's, 60 s by default; set it to a few seconds), then the next campaigner's key becomes the oldest and it wins: the takeover time is about the TTL. After SIGSTOP the same happens, but the frozen process still thinks it leads. The defence is chapter 23's: every write it makes carries the election key's revision (`election.Rev()` / the leader key's create revision) and is guarded, in etcd itself with a transaction comparing that the leader key's create revision is still ours, so writes from a replaced leader fail.

</Solution>

</Exercise>

<Exercise n={4} title="Five members" level="medium">

Rebuild the cluster with five members. How many can fail before writes stop, and what happens to write latency? Why not four?

<Solution>

A majority of 5 is 3, so two members can fail and the cluster still commits; with three, only one can fail. Write latency rises slightly: each write waits for the third-fastest acknowledgement instead of the second. Four members tolerate only one failure (a majority of 4 is 3), like three, while adding a member to wait for: even sizes buy nothing. That's why clusters are 3, 5 or 7 members.

</Solution>

</Exercise>

<Exercise n={5} title="Linearizability checker" level="hard">

Record a history from `kv`: for each operation, its start time, end time, kind (read or write), and value. Write a checker that decides whether the history is linearizable for a single key, and run it on histories taken during a partition with serializable and with linearizable reads.

<Solution>

A history is linearizable if you can pick, for each operation, one instant inside its [start, end] interval, such that reading the operations in that order is a valid sequence for one register (each read returns the latest write before it). The brute-force checker tries orders consistent with real time (an operation that ended before another started must come first) with backtracking; tools like Porcupine and Knossos do this efficiently. With serializable reads during the partition, the checker finds a read of 'free' that started after the write of 'booked:alice' had ended: no valid order exists, so the history isn't linearizable. With linearizable reads, the stale answers never happen (they time out instead), and every history passes.

</Solution>

</Exercise>

<Recap>

- **Linearizability**: a replicated store that behaves like one copy; no read goes back in time. etcd reads are linearizable by default (confirmed through a majority), serializable on request.
- **Uniqueness**: three box offices on three members raced for 200 seats with compare-and-swap transactions; every seat sold exactly once, each sale with a distinct cluster-wide revision, a ready-made fencing token.
- **CAP, measured**: a member partitioned from its peers answered serializable reads with a stale `free`, refused linearizable reads and writes (timeouts), while the majority side kept selling; after healing, it rejoined in 3.7 s (PreVote kept the term steady) and caught up in 5.3 s.
- **Raft**: terms, randomized election timeouts, a replicated log committed by a majority. Killing the leader cost 1.04 s of writes and one term (3 to 4); 3 of about 500 writes failed, none was lost.
- **The commit rule**: count replicas only for current-term entries, or Figure 8's scenario can undo a "committed" entry. The lab implements it.
- **In practice**: keep small, decision-shaped state in consensus (leaders, locks, config, uniqueness); keep high-volume state in faster stores.
