## Backpressure under load

**On the job:** Every `POST /transfers` endpoint at Meridian runs behind a bounded worker pool. When a settlement batch hits at midnight, requests arrive faster than workers can process them. Without an explicit shed policy, the queue grows without bound — gigabytes of goroutine stacks and channel items accumulate until OOM kills the process. You define the policy, or the OS defines it for you.

Let me set the scene. You're running Meridian's payment-processing service. A flash sale hits — 50 000 checkout requests per second instead of the usual 5 000. Your worker pool is configured for 100 goroutines. What happens to the other 49 900 requests that can't be served right now?

If you didn't answer that question deliberately in your architecture, the runtime answered it for you. And it probably answered it badly.

**Backpressure** is the mechanism by which a system *signals to its caller that it's full* rather than silently accepting unlimited work. In Go, the primary tool is the **bounded channel** — a channel with a capacity. It applies backpressure the moment it's full.

The three options when you're full:

1. **Block** — the sender blocks until a slot opens. Simple, but can cascade a stall upstream.
2. **Drop** — the sender discards the work item and moves on. Fast; you lose some work intentionally.
3. **Shed** — return an explicit error or HTTP 503 so the *client* knows to back off. The most honest signal.

Here's the pattern in code — a bounded job queue with a non-blocking try-send and explicit shedding:

```go
package main

import (
	"fmt"
	"sync"
	"time"
)

const workers = 3

// processPayments spins up a bounded worker pool.
// The channel IS the queue; capacity IS the backpressure knob.
func processPayments(jobs <-chan int, maxQueue int) {
	queue := make(chan int, maxQueue) // bounded buffer
	var wg sync.WaitGroup

	// Start fixed pool of workers.
	for range workers {
		wg.Add(1)
		go func() {
			defer wg.Done()
			for job := range queue {
				// Simulate processing time (e.g. card network call).
				time.Sleep(20 * time.Millisecond)
				fmt.Printf("processed payment %d\n", job)
			}
		}()
	}

	// Forward from inbound stream; shed if full.
	for job := range jobs {
		select {
		case queue <- job:
			// Slot available — accepted.
		default:
			// Buffer full — shed with an explicit signal.
			fmt.Printf("shed payment %d (queue full)\n", job)
		}
	}
	close(queue) // signal workers to drain and exit
	wg.Wait()
}

func main() {
	jobs := make(chan int, 20)
	for i := 1; i <= 10; i++ {
		jobs <- i
	}
	close(jobs)
	processPayments(jobs, 4) // only 4 slots behind 3 workers
}
```

<UnderTheHood title="How the Go runtime implements channel sends (hchan internals)">

A channel is a `runtime.hchan` struct containing a **circular ring buffer** (the internal queue), a mutex (`lock`), two goroutine queues (`sendq` and `recvq`), and the current buffer fill count (`qcount`). As of Go 1.26, this struct lives on the heap — `make(chan T, n)` allocates the `hchan` and its backing array together. The description below is a simplified model; the actual runtime source is in `runtime/chan.go`.

When you `select { case ch <- v: default: }`, the runtime:
1. Acquires the `hchan` lock.
2. Checks `qcount < dataqsiz` (is there room in the ring buffer?).
3. If yes → copies `v` into the ring buffer, increments `qcount`, releases the lock. O(1).
4. If no → and there's a blocked receiver in `recvq` → hands off directly (the "direct send" fast path). Otherwise, with the `default` branch present, releases the lock and jumps to `default`. No goroutine is parked, no context switch — that's why the `select/default` pattern is the idiomatic shedding mechanism rather than a length check followed by a separate send.

The ring buffer is cache-friendly for small element types. For large structs, the copy cost matters — consider channel-of-pointer instead. This tradeoff is covered in the performance chapter (Part 2, Ch 8).

</UnderTheHood>

## The race detector

**On the job:** Meridian's `POST /transfers` handler spawns a goroutine per request. Two transfers hitting the same account concurrently — both reading the balance, both computing the new value, both writing back — corrupt the ledger silently. No panic, no error. The books are wrong and the race detector is the only tool that catches it before it ships.

Here's the scene in code: two goroutines update the same account balance at the same time. Both read it, both add their transfer amount, both write back. One write silently overwrites the other. Money appears from thin air — or disappears into it. That's a **data race**, and Go ships a tool that catches it before it ever sees production.

Run any Go command with `-race` and the runtime wraps every memory access in **shadow memory tracking**. When two goroutines touch the same address without any synchronization between them, it fires an alarm.

First, let's see the race — and what `-race` reports:

```go
package main

import (
	"fmt"
	"sync"
)

// balance is shared state — the bug is that nothing protects it.
var balance int

func deposit(amount int, wg *sync.WaitGroup) {
	defer wg.Done()
	// BUG: read-modify-write is not atomic.
	// Two goroutines can both read 1000, both add, both write —
	// and one write silently wins, losing a deposit.
	balance = balance + amount
}

func main() {
	var wg sync.WaitGroup
	balance = 1000

	for range 5 {
		wg.Add(1)
		go deposit(100, &wg) // five concurrent deposits of $1.00 each
	}
	wg.Wait()
	// Expected: 1500. Actual: unpredictable (and wrong).
	fmt.Println("final balance:", balance)
}
```

<UnderTheHood title="How -race works: shadow memory and vector clocks">

The race detector is implemented in the Go runtime using **ThreadSanitizer v2** (TSan), compiled in when you pass `-race`. As of Go 1.26, the instrumentation works at two levels. This is a simplified model of the mechanism; the full implementation is in `runtime/race.go` and the upstream TSan library.

**Shadow memory.** Every 8 bytes of your program's memory gets a corresponding 32-byte "shadow" cell in a parallel region. Each shadow cell stores the last 4 access records: goroutine ID, logical time (a vector-clock epoch), read/write flag, and whether synchronization happened around it. This is why `-race` uses 5–10× more memory — the shadow map is proportional to your heap+stack.

**Vector clocks.** Every synchronization event (channel send/receive, mutex lock/unlock, `sync.Once.Do`, etc.) advances a logical clock for each goroutine. When goroutine G2 receives from a channel that G1 sent on, G2's clock is updated to reflect everything G1 had done before the send. This is the happens-before relation encoded numerically.

**The detection.** On each memory access, the compiler-inserted instrumentation checks: does the shadow cell record a conflicting access (opposite read/write, or both writes) by a *different* goroutine whose clock epoch is *not* happens-before this access? If yes → race detected. The check is O(1) per access — it's fast enough to run in staging, though the 2–20× slowdown makes it unsuitable for production hot paths.

The source lives in `runtime/race.go` (the Go shim) and the upstream TSan library. If you want to go deeper: Serebryany & Iskhodzhanov, "ThreadSanitizer: Data Race Detection in Practice," Proceedings of the Workshop on Binary Instrumentation and Applications, 2009.

</UnderTheHood>

## Designing for zero races

**On the job:** The race detector only fires on paths that actually execute during a test run. A transfer path that requires a specific timing window may never trigger it in CI but will in production under load. Design the data structures to make races impossible, not just hard to trigger.

The race detector finds races *after* they exist. The real goal is to design code so races *cannot* exist. There are four techniques, and I'll tell you exactly when to reach for each one.

### Confinement

The cleanest solution: don't share at all. If only one goroutine ever touches a value, no synchronization is needed — the risk surface is zero.

```go
package main

import "fmt"

// processTransfer runs entirely within a single goroutine.
// Each invocation gets its own local copy of the ledger state.
// No sharing, no synchronization needed.
func processTransfer(fromBalance, amount int) (int, error) {
	if fromBalance < amount {
		return fromBalance, fmt.Errorf("insufficient funds: have %d, need %d",
			fromBalance, amount)
	}
	return fromBalance - amount, nil // local variable, not shared
}

func main() {
	bal, err := processTransfer(5000, 1500)
	if err != nil {
		fmt.Println("error:", err)
		return
	}
	fmt.Println("remaining balance:", bal)
}
```

The Go proverb here: **"Don't communicate by sharing memory; share memory by communicating."** Confinement is the purest form — nothing to communicate, nothing to share.

### Immutability

If data can never change after creation, any number of goroutines can read it simultaneously — reads never race with reads. In Go, you implement immutability by returning values (not pointers) and never exposing mutation methods.

### Atomics for counters and flags

For simple numeric values — counters, flags, version stamps — `sync/atomic` is faster than a mutex and race-free by construction. Use `atomic.Int64` (Go 1.19+), not the old `atomic.AddInt64` function form.

```go
package main

import (
	"fmt"
	"sync"
	"sync/atomic"
)

func main() {
	var requestCount atomic.Int64 // zero value is 0 — ready to use
	var wg sync.WaitGroup

	// 1000 concurrent requests, each incrementing the counter.
	// wg.Go (Go 1.25) calls wg.Add(1) and launches the goroutine atomically.
	for range 1000 {
		wg.Go(func() {
			requestCount.Add(1)
		})
	}
	wg.Wait()
	fmt.Println("total requests:", requestCount.Load()) // always 1000
}
```

### Mutex discipline

When the shared state is complex (a struct, a map, a slice), a mutex is the right tool. The rules for getting it right:

<ConceptGrid cols={3}>
  <ConceptCard label="Lock the data, not the code">The mutex protects a specific piece of data, not a vague "critical section." Embed the mutex with the data it guards so the relationship is obvious.</ConceptCard>
  <ConceptCard label="defer mu.Unlock()">Always defer the unlock on the line after the lock. It fires even when the function panics. Forgetting it causes a deadlock that won't show until your first burst of real traffic.</ConceptCard>
  <ConceptCard label="Don't hold locks across I/O">Calling a database, HTTP endpoint, or anything that blocks while holding a lock means all other goroutines that need that lock are parked for the duration of the network call. Release the lock; use local variables.</ConceptCard>
  <Gotcha>Never copy a mutex. A `sync.Mutex` contains internal state; copying it copies that state and the copy won't unlock the original. Embed it by value in a struct, and pass the struct by pointer. `go vet` catches this — run it.</Gotcha>
</ConceptGrid>

Here's an account struct that puts these rules together:

```go
package main

import (
	"fmt"
	"sync"
)

// Account embeds its mutex with the data it guards.
// The zero value is safe to use — both mu and balance start at zero.
type Account struct {
	mu      sync.Mutex
	balance int // cents; protected by mu
}

// Deposit adds amount to the balance. Safe for concurrent use.
func (a *Account) Deposit(amount int) {
	a.mu.Lock()
	defer a.mu.Unlock()
	a.balance += amount
}

// Balance returns the current balance. Safe for concurrent use.
func (a *Account) Balance() int {
	a.mu.Lock()
	defer a.mu.Unlock()
	return a.balance
}

func main() {
	acc := &Account{balance: 10000} // $100.00 in cents
	var wg sync.WaitGroup

	// Ten concurrent deposits of $10.00 each.
	// wg.Go (Go 1.25) adds 1 and spawns the goroutine in one call.
	for range 10 {
		wg.Go(func() {
			acc.Deposit(1000)
		})
	}
	wg.Wait()
	fmt.Printf("final: $%d.%02d\n", acc.Balance()/100, acc.Balance()%100)
}
```

<UnderTheHood title="What atomics compile to: LOCK-prefixed instructions and barriers">

`atomic.Int64.Add` compiles to a single `LOCK XADDQ` instruction on amd64 (or equivalent on arm64). The `LOCK` prefix tells the CPU to hold the memory bus for the duration of the read-modify-write, making it *hardware-atomic* — no other core can interleave between the read and the write.

This is substantially cheaper than a `sync.Mutex`, which involves a futex syscall when there's contention (a full OS round-trip). For a simple counter touched by hundreds of goroutines, the difference between `atomic.Int64` and `sync.Mutex` can be 5–10× in throughput.

However, atomics don't compose. If you need to atomically update *two* related values (e.g. a balance *and* a transaction count together, consistently), you need a mutex — there's no hardware instruction for multi-field atomicity. The moment the invariant spans more than one word, reach for a mutex.

On arm64, the compiler emits `STLXR`/`LDAXR` (load-acquire / store-release) sequences. These carry **memory ordering barriers**: the CPU guarantees that all prior memory operations are visible to other cores before the store completes. This is what makes atomics safe across cores — not just hardware-atomic, but *sequentially consistent* for the operations they protect.

</UnderTheHood>

<UnderTheHood title="How a mutex is actually built: spinlock → futex → starvation mode">

A `sync.Mutex` looks like a black box, but it's three layers, each solving the failure of the one below. Knowing them explains why a mutex is cheap when uncontended and expensive when hot.

**Layer 1 — the spinlock.** The simplest lock is a single integer and an atomic compare-and-swap: "if the lock is 0, set it to 1." If the CAS fails (someone holds it), you *spin* — loop and retry. A **spinlock** is correct and, for a lock held for a handful of nanoseconds, fast: the waiter stays hot on its CPU core and grabs the lock the instant it's free, with no trip into the kernel. The catch: a spinning goroutine **burns a whole CPU doing nothing**. Spin for a lock held across a slow operation and you waste millions of cycles. Spinning only pays when the wait is shorter than the cost of parking.

**Layer 2 — the futex.** So you can't *only* spin. The kernel offers a **futex** ("fast userspace mutex"): in the uncontended case the lock is taken and released entirely in userspace with one atomic op — *zero* syscalls, which is why an uncontended `Lock()`/`Unlock()` is nearly free. Only when a goroutine actually has to *wait* does it make a syscall to **park** (sleep) until the holder's `Unlock` issues a wake. No CPU burned while parked. The cost is that syscall round-trip — the "futex syscall" the atomics note above referred to — which is why contention, not locking itself, is what makes a mutex slow.

**Go's blend.** `sync.Mutex` combines both: on contention it **spins a few times** (cheap, in case the lock frees immediately), and only then **parks** the goroutine via the runtime (Go parks the *goroutine*, not the OS thread, so the M stays free to run others — a futex-like park one level up from the kernel). Two pieces of real internal state make this robust: a **spin count** bounding the busy-wait, and, since Go 1.9, a **starvation mode** — if a goroutine waits more than **1ms** for the lock, the mutex flips to handing the lock *directly* to the front of the wait queue instead of letting a freshly-arriving goroutine barge in. That barging is great for throughput but can leave an unlucky waiter starved forever; starvation mode trades a little throughput for the guarantee that no waiter waits unboundedly. As of Go 1.26 this lives in `sync/mutex.go` (`lockSlow`/`unlockSlow`). The takeaway: a mutex is fast precisely *because* it avoids the kernel until it must, and fair precisely *because* it gives up that speed under sustained contention.

</UnderTheHood>

## The Go memory model

**On the job:** Meridian's ledger workers cache an account's balance in a local variable before processing a batch. Without a synchronization event between the writer goroutine and the reader goroutine, the cached value may be stale — even on a single machine. This is not a theoretical concern: the compiler and CPU both reorder memory operations for performance, and they do so aggressively.

The Go memory model (last revised 2022) is the authoritative answer to the question: "If goroutine A writes to a variable, is goroutine B guaranteed to see that write?" The answer — and this surprises a lot of people — is **not necessarily, unless there's a synchronization event between them.**

Here's the foundational rule:

> **A write to a variable by one goroutine is guaranteed to be observed by a read of that variable in a different goroutine only if the write happens-before the read.**

**Happens-before** is a strict partial order. It's not about wall-clock time. It's about *logical ordering enforced by synchronization*. Without synchronization, the compiler and CPU are free to reorder memory operations for performance — and they do.

The events that establish happens-before in Go (as of the 2022 memory model):

  <ConceptCard label="Mutex Unlock → Lock">An `mu.Unlock()` call happens-before any subsequent `mu.Lock()` call returns. This is why mutex-guarded data is visible to the next locker.</ConceptCard>
  <ConceptCard label="sync.Once.Do">The completion of `f` inside `once.Do(f)` happens-before the return of any call to `once.Do(f)`. The initialization is guaranteed visible to all callers.</ConceptCard>
  <ConceptCard label="Goroutine creation">The `go` statement that creates goroutine G happens-before G's execution begins. Arguments evaluated before the `go` are visible inside the goroutine.</ConceptCard>

Here's the classic trap — unsynchronized access looks fine in testing but is still a data race:

```go
package main

import "fmt"

// WARNING: this code has a data race.
// Do not use this pattern. Shown for educational purposes.
var ready bool   // no synchronization
var data int

func setup() {
	data = 42    // write 1
	ready = true // write 2
}

func observe() {
	if ready {        // read 2 — may see true...
		fmt.Println(data) // read 1 — ...but may NOT see 42!
	}
}

func main() {
	// This program has a data race. The result is not synchronized.
	// The compiler or CPU may reorder writes in setup(),
	// and the goroutine running observe() has no happens-before
	// guarantee from setup()'s writes.
	go setup()
	go observe()
	// Without synchronization, we cannot reason about the output.
	fmt.Println("(race — unsynchronized behavior)")
}
```

The Go memory model was substantially revised in 2022 to align with how the language actually behaves and to match the C++ memory model's formalism. The key addition: **package-level `sync` primitives** (`sync.Mutex`, `sync.WaitGroup`, `sync.Once`, `sync.Map`, `sync.Pool`, `sync.Cond`) all now have formally documented happens-before guarantees in the spec. ## Bugs that survive review

**On the job:** Lost wakeups, goroutine leaks, and deadlocks survive code review because they require specific interleavings that tests almost never reproduce. At Meridian, a goroutine leak in the settlement job accumulated 400 MB of orphaned goroutine stacks over six hours before an OOM killed the process. The code looked fine in review.

These are the four bugs that your code reviewer will miss, your unit tests won't catch, and `-race` may not trigger deterministically. I've seen each one take down a service. You will recognize all of them today.

### Lost wakeup

A goroutine waits on a condition — but the signal fires *before* the wait begins. The goroutine waits forever for a signal that already happened.

```go
package main

import (
	"fmt"
	"sync"
)

// BUG: processOrder signals before the monitor goroutine is ready to wait.
// The cond.Signal() fires into the void; cond.Wait() then blocks forever.
func buggyVersion() {
	var mu sync.Mutex
	cond := sync.NewCond(&mu)
	orderReady := false

	// "Producer": marks order ready and signals.
	go func() {
		mu.Lock()
		orderReady = true
		cond.Signal() // fires before the consumer calls Wait — lost!
		mu.Unlock()
	}()

	// "Consumer": supposed to wait until order is ready.
	// But if the goroutine above runs first, Signal() is lost.
	mu.Lock()
	// FIX: always check the condition in a loop.
	for !orderReady {
		cond.Wait() // blocks here forever if Signal() already fired
	}
	mu.Unlock()
	fmt.Println("order processed") // may never print in the buggy version
}

func main() {
	// The fixed version: check the condition in a loop.
	// cond.Wait() atomically releases mu and parks the goroutine.
	// If the signal already fired, orderReady is true and we skip Wait entirely.
	var mu sync.Mutex
	cond := sync.NewCond(&mu)
	orderReady := false

	go func() {
		mu.Lock()
		orderReady = true
		cond.Signal()
		mu.Unlock()
	}()

	mu.Lock()
	for !orderReady { // loop: re-check after every wakeup (also handles spurious wakeups)
		cond.Wait()
	}
	mu.Unlock()
	fmt.Println("order processed — guaranteed")
}
```

### Goroutine leak

A goroutine that's launched but can never exit. It stays alive, consuming memory (goroutine stacks start small and grow dynamically), until the process dies. At 1 000 leaking goroutines per minute, you have 30 minutes before OOM.

The canonical leak: a goroutine blocked on a channel send with no receiver.

```go
package main

import (
	"context"
	"fmt"
	"time"
)

// leaked: worker sends on results but the caller only reads one value
// and then returns. The goroutine is permanently blocked on the send.
func leaked(ctx context.Context) <-chan string {
	results := make(chan string) // unbuffered — blocks until read
	go func() {
		// Simulate two results found.
		results <- "transfer-001" // first read consumed by caller
		results <- "transfer-002" // NOBODY READS THIS — goroutine leaks here
	}()
	return results
}

// fixed: worker respects context cancellation.
func fixed(ctx context.Context) <-chan string {
	results := make(chan string)
	go func() {
		defer close(results) // always close to signal completion
		items := []string{"transfer-001", "transfer-002"}
		for _, item := range items {
			select {
			case results <- item:
			case <-ctx.Done():
				return // context cancelled — exit cleanly, no leak
			}
		}
	}()
	return results
}

func main() {
	ctx, cancel := context.WithTimeout(context.Background(), 50*time.Millisecond)
	defer cancel()

	ch := fixed(ctx)
	// Read only the first result; context timeout covers the rest.
	if v, ok := <-ch; ok {
		fmt.Println("got:", v)
	}
	// cancel() fires; worker goroutine sees ctx.Done() and exits cleanly.
	time.Sleep(10 * time.Millisecond) // let the goroutine exit
	fmt.Println("no leak — goroutine exited via context")
}
```

### Deadlock

Two goroutines each hold a lock the other needs. Both wait forever. Go's runtime detects the total-deadlock case (all goroutines blocked) and panics with "all goroutines are asleep — deadlock!" but partial deadlocks — where a subset of goroutines are stuck and the rest keep running — go undetected.

```go
package main

import (
	"fmt"
	"sync"
)

// Transfer between two accounts — classic lock ordering bug.
// Always lock in the same order to prevent deadlock.
type SafeAccount struct {
	id      int
	mu      sync.Mutex
	balance int
}

// transferFixed always locks the lower-ID account first.
// Consistent ordering prevents the circular wait that causes deadlock.
func transferFixed(from, to *SafeAccount, amount int) error {
	// Establish a canonical lock order by account ID.
	first, second := from, to
	if from.id > to.id {
		first, second = to, from
	}

	first.mu.Lock()
	defer first.mu.Unlock()
	second.mu.Lock()
	defer second.mu.Unlock()

	if from.balance < amount {
		return fmt.Errorf("insufficient funds")
	}
	from.balance -= amount
	to.balance += amount
	return nil
}

func main() {
	a := &SafeAccount{id: 1, balance: 5000}
	b := &SafeAccount{id: 2, balance: 3000}

	var wg sync.WaitGroup

	// wg.Go (Go 1.25) — no wg.Add(1) / defer wg.Done() boilerplate.
	wg.Go(func() {
		if err := transferFixed(a, b, 1000); err != nil {
			fmt.Println("a→b error:", err)
		}
	})
	wg.Go(func() {
		if err := transferFixed(b, a, 500); err != nil {
			fmt.Println("b→a error:", err)
		}
	})

	wg.Wait()
	fmt.Printf("a: %d  b: %d  total: %d\n", a.balance, b.balance, a.balance+b.balance)
}
```

### Livelock and starvation

Deadlock is the *quiet* failure — everyone's asleep. Its two cousins are the *loud* ones, and they're nastier precisely because the goroutines look healthy. CPU's pegged, the trace shows goroutines running, your dashboards are green-ish. And yet nothing actually finishes. Charming, isn't it?

<Define term="Livelock" since="Advanced Concurrency (Part 2)">Goroutines aren't blocked — they're actively running and *reacting to each other* — but make zero forward progress. The classic image: two people in a corridor, each politely stepping aside, both stepping the same way, forever. Fix: break the symmetry.</Define>

**On the job:** Meridian's transfer code was "clever." To avoid the deadlock you just learned about, each transfer would *try* to grab both account locks, and if it couldn't get the second one, it would release the first and retry. Sounds defensive. But when two opposite transfers (`A→B` and `B→A`) collide, both detect the conflict on the same beat, both back off on the same beat, both retry on the same beat — and collide again. No one is blocked. Everyone is busy. The books never move. That's a **livelock**.

The cure is to **destroy the symmetry**. Two ways: a single canonical lock order (the deadlock fix from above — no retry needed at all, which is why it's the better answer), or, if you must retry, **randomized backoff (jitter)** so the two goroutines stop landing on the same beat:

```go
package main

import (
	"fmt"
	"math/rand/v2"
)

// Two transfers that, on detecting contention, both back off and retry.
// With NO jitter they retry in perfect lockstep — a livelock: always busy,
// never progressing. With jitter, one waits a different amount, breaks the
// symmetry, and progress is made. We model each "attempt" as a round.
func tryWithBackoff(name string, jitter bool) int {
	rounds := 0
	for {
		rounds++
		collide := true // both land on the same beat → they conflict
		if jitter {
			// Random backoff desynchronizes the two retriers.
			collide = rand.IntN(2) == 0
		}
		if !collide {
			fmt.Printf("%s: acquired after %d round(s)\n", name, rounds)
			return rounds
		}
		fmt.Printf("%s: collision on round %d — backing off\n", name, rounds)
		if rounds >= 6 {
			fmt.Printf("%s: LIVELOCK — gave up after %d lockstep retries\n", name, rounds)
			return rounds
		}
	}
}

func main() {
	fmt.Println("=== No jitter: lockstep retries → livelock ===")
	tryWithBackoff("transfer-A", false)

	fmt.Println("\n=== Randomized backoff: jitter breaks the symmetry ===")
	tryWithBackoff("transfer-B", true)
}
```

Now the other cousin.

<Define term="Starvation" since="Advanced Concurrency (Part 2)">A goroutine never gets a resource because other goroutines keep winning it. No deadlock, no livelock — just one perpetually-unlucky goroutine waiting while the queue jumps it indefinitely.</Define>

Starvation is why `sync.Mutex` has the **starvation mode** from the under-the-hood note above. A plain mutex lets a freshly-arriving goroutine *barge* in and grab a just-freed lock ahead of a goroutine that's been waiting — great for throughput, but under sustained contention the barging newcomers can starve the patient waiter forever. So since Go 1.9, if a waiter has been queued for more than **1ms**, the mutex flips to handing the lock *directly* to the front of the wait queue. That single rule is the difference between "fast on average" and "fast on average *and* no waiter waits unboundedly."

`sync.RWMutex` faces the mirror image: **reader-starvation vs. writer-starvation.** A naive read-write lock that always admits readers will starve any writer the moment readers arrive continuously — the writer never sees a gap. Go's `RWMutex` defends the writer: once a writer is waiting, **new readers are blocked** behind it even if the lock is currently held by other readers. That guarantees the writer eventually runs, at the cost of making some readers wait. Fairness, like everything in concurrency, is a trade.

<Callout kind="note" title="Deadlock vs. livelock vs. starvation — the one-line test">

All three mean "no useful progress," but they fail differently. **Deadlock:** everyone is *blocked* (asleep), waiting on each other — the runtime can sometimes detect the total case and panic. **Livelock:** everyone is *running* and reacting to each other, but no state advances — undetectable by the runtime, looks like 100% CPU doing nothing. **Starvation:** *most* goroutines progress fine, but one (or a class) never gets its turn — looks like a latency outlier, not an outage. Ask: "is the stuck goroutine asleep, spinning, or just always last?"

</Callout>

  <ConceptCard label="Goroutine leak">Goroutine blocked on channel with no consumer, or no exit signal. Fix: pass `context.Context`, select on `ctx.Done()`, always `close()` channels you own.</ConceptCard>
  <ConceptCard label="Deadlock">Circular lock acquisition. Fix: canonical lock ordering by a stable key (ID, pointer address), or a single mutex over both resources.</ConceptCard>
  <ConceptCard label="Livelock / starvation">Livelock: actors retry in lockstep, never progressing — fix with jitter or canonical ordering. Starvation: one goroutine never wins the resource — Go's mutex (1ms) starvation mode and `RWMutex` writer-priority exist to prevent it.</ConceptCard>
</ConceptGrid>

The following function is supposed to build a list of processed order IDs from 10 concurrent goroutines. It has a data race. Identify it and fix it with a mutex. Verify your fix by reasoning about what `-race` would report.

	"fmt"

func collectOrders() []int {

	var wg sync.WaitGroup

		wg.Add(1)
		go func() {
			defer wg.Done()

<Solution>

```go
package main

import (
	"fmt"
	"sync"
)

func collectOrders() []int {
	var (
		mu      sync.Mutex
		results []int
	)
	var wg sync.WaitGroup

	for i := range 10 {
		wg.Add(1)
		go func() {
			defer wg.Done()
			mu.Lock()
			results = append(results, i)
			mu.Unlock()
		}()
	}
	wg.Wait()
	return results
}

func main() {
	fmt.Println(collectOrders())
}
```

The race: `append` reads the slice header (pointer, len, cap), may reallocate, and writes the new header back. Multiple goroutines doing this concurrently on the same `results` variable race on the slice header. `-race` would report conflicting reads and writes at the `append` line. The fix: protect with a mutex. Alternatively, pre-allocate a fixed-size slice and write to pre-assigned indices — but the mutex approach is simpler and correct here.

<Exercise n={3} title="Happens-before with WaitGroup" level="medium">

Write a program that spawns 5 goroutines, each computing the square of its index and storing it in a pre-allocated `[]int`. The main goroutine prints all results after all goroutines complete. Explain in a comment why the reads in `main` are guaranteed to see the correct values (cite the happens-before rule that makes it safe).

<Solution>

```go
package main

import (
	"fmt"
	"sync"
)

func main() {
	results := make([]int, 5) // each goroutine owns one index — no sharing
	var wg sync.WaitGroup

	// wg.Go (Go 1.25): no wg.Add/defer wg.Done boilerplate.
	// Loop variables are per-iteration since Go 1.22, so i is captured correctly.
	for i := range 5 {
		wg.Go(func() {
			results[i] = i * i // each goroutine writes a distinct slot
		})
	}

	// wg.Wait() returns only after all goroutines launched via wg.Go complete.
	// The memory model guarantees: with wg.Go, each function return synchronizes before
	// any wg.Wait() return that it unblocks.
	// Therefore: all writes to results happen-before the reads below.
	// No mutex needed because each goroutine writes a distinct index (no sharing).
	wg.Wait()

	fmt.Println(results) // guaranteed to see [0 1 4 9 16]
}
```

Key happens-before chain: each goroutine launched via `wg.Go` completes before `wg.Wait()` returns. Since the writes to `results[i]` happen inside those goroutines, and `wg.Wait()` returns after all of them, the reads in `main` are guaranteed to see the written values. No data sharing occurs because each goroutine touches a unique index.

</Solution>

</Exercise>

<Exercise n={4} title="Fix the goroutine leak" level="hard">

The function below leaks a goroutine. Identify the leak, then rewrite the function so it is context-aware and the goroutine always exits. Add a comment explaining the fix.

```go
func fetchAccountStatus(accountID string) <-chan string {
	out := make(chan string)
	go func() {
		// Simulate slow external API call.
		time.Sleep(2 * time.Second)
		out <- "active"
		out <- "verified" // second send — who reads this?
	}()
	return out
}
```

<Solution>

```go
package main

import (
	"context"
	"fmt"
	"time"
)

// fetchAccountStatus returns account status strings on the channel.
// The goroutine exits when ctx is cancelled or all values are sent.
func fetchAccountStatus(ctx context.Context, accountID string) <-chan string {
	out := make(chan string)
	go func() {
		defer close(out) // always signal completion to callers

		statuses := []string{"active", "verified"}
		for _, s := range statuses {
			// Simulate work per status.
			select {
			case <-time.After(100 * time.Millisecond):
				// work done — try to send
			case <-ctx.Done():
				return // caller cancelled — exit without leaking
			}

			select {
			case out <- s:
			case <-ctx.Done():
				return // nobody reading and caller cancelled — exit
			}
		}
	}()
	return out
}

func main() {
	// Caller only wants the first result; cancels after getting it.
	ctx, cancel := context.WithTimeout(context.Background(), 500*time.Millisecond)
	defer cancel()

	ch := fetchAccountStatus(ctx, "acct-42")
	if v, ok := <-ch; ok {
		fmt.Println("status:", v)
	}
	cancel() // goroutine sees ctx.Done() and exits cleanly
	time.Sleep(50 * time.Millisecond)
	fmt.Println("done — no leak")
}
```

The original leak: the goroutine sends two values but the caller only reads one. The second `out <- "verified"` blocks forever because nobody receives it. Fix: (1) select on `ctx.Done()` at every blocking point so the goroutine exits when the caller is done; (2) `defer close(out)` to signal completion and unblock any ranging callers. The golden rule: every goroutine must have a path to exit.

</Solution>

</Exercise>

<Exercise n={5} title="Total-balance invariant under concurrent transfers" level="hard">

Write a function `transferAll` that performs 500 random transfers between 4 accounts concurrently. Each transfer picks two random accounts and moves a random amount between 1 and 100 cents. After all transfers complete, verify that the sum of all balances equals the initial total. Use proper mutex discipline. Your solution must be silent under `go test -race`.

<Solution>

```go
package main

import (
	"fmt"
	"math/rand/v2"
	"sync"
)

type Account struct {
	id      int
	mu      sync.Mutex
	balance int
}

func transfer(from, to *Account, amount int) {
	// Canonical lock order prevents deadlock.
	first, second := from, to
	if from.id > to.id {
		first, second = to, from
	}
	first.mu.Lock()
	defer first.mu.Unlock()
	second.mu.Lock()
	defer second.mu.Unlock()

	if from.balance < amount {
		return // insufficient funds — skip, no partial update
	}
	from.balance -= amount
	to.balance += amount
}

func main() {
	accounts := []*Account{
		{id: 1, balance: 1000},
		{id: 2, balance: 2000},
		{id: 3, balance: 3000},
		{id: 4, balance: 4000},
	}
	initial := 0
	for _, a := range accounts {
		initial += a.balance
	}

	var wg sync.WaitGroup
	for range 500 {
		wg.Go(func() {
			i := rand.IntN(len(accounts))
			j := rand.IntN(len(accounts))
			if i == j {
				return
			}
			transfer(accounts[i], accounts[j], rand.IntN(100)+1)
		})
	}
	wg.Wait()

	total := 0
	for _, a := range accounts {
		total += a.balance
	}
	if total != initial {
		fmt.Printf("INVARIANT VIOLATED: initial %d, final %d\n", initial, total)
	} else {
		fmt.Printf("Invariant holds: total = %d cents\n", total)
	}
}
```

Two correctness properties: (1) mutex discipline — each transfer acquires both account locks in a canonical order (by ID) to prevent deadlock; (2) balance invariant — no money is created or destroyed because we only perform `from -= amount; to += amount` as an atomic unit under both locks. Under `-race`, this is clean because all reads and writes to `balance` fields are protected by the respective mutex.

</Solution>

<Recap>

- **Backpressure** is a bounded channel + a `select/default` shed path. An unbounded channel is unlimited memory. Size your queues; own your shed policy.
- **The race detector** (`-race`) uses shadow memory and vector clocks to catch data races at runtime. Always run it in CI. Read the report: it gives you the exact address, lines, and goroutines involved.
- **Zero races by design**: confinement (don't share), immutability (don't mutate), `atomic.Int64` for counters, `sync.Mutex` for complex state. Embed the mutex with the data it guards.
- **The Go memory model** (revised 2022): a write is only guaranteed visible to another goroutine if a happens-before event connects them — channel send/receive, mutex unlock/lock, `sync.Once.Do`, goroutine creation. Without synchronization, the program has a data race; reads can observe surprising values, and compiler/runtime reordering is allowed within the memory model's constraints.
- **Lost wakeups**: always `for !condition { cond.Wait() }` — never bare `cond.Wait()`.
- **Goroutine leaks**: every goroutine must have a path to exit. Pass `context.Context`, select on `ctx.Done()`, close channels you own.
- **Deadlocks**: canonical lock ordering (by stable key) breaks the circular-wait cycle. Two goroutines, two locks, opposite order = guaranteed deadlock.

</Recap>
