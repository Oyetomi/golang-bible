## Backpressure under load

*Stop 1 of 5.*

### Step 1: a service with a limit it doesn't admit to

`intake` is a small transfer service in front of Postgres. Each `POST /transfers` goes through a fixed pool of 8 workers, and each worker does two real things: runs the fraud rule from Part 2 chapter 3 (a 24-hour velocity query that scans the ledger's two million transactions, because `from_account` has no index) and then moves the money between two wallets in one transaction, locking the lower id first (you'll see why in stop 5).

```go noverify
// intake accepts POST /transfers. A fixed pool of workers runs the fraud
// rule from chapter 3 on each (a velocity query that scans the ledger's
// two million transactions) and then applies it to the wallets table. -queue 0 makes every request wait for a worker
// however long that takes; -queue N keeps at most N waiting and answers
// 503 to the rest.
package main

import (
	"context"
	"database/sql"
	"encoding/json"
	"errors"
	"flag"
	"log"
	"math/rand/v2"
	"net/http"
	"os"
	"runtime"
	"runtime/metrics"
	"sync/atomic"

	_ "github.com/jackc/pgx/v5/stdlib"
)

type job struct {
	sender   string // ledger account whose 24-hour velocity is checked
	from, to int
	cents    int64
	done     chan error // buffered: a worker never waits for a departed client
}

// velocity: how much has this account sent in 24 hours? There is no index
// on from_account, so Postgres scans every transaction (about 70 ms).
const velocity = `
	SELECT coalesce(sum(amount_cents), 0) FROM transactions
	WHERE from_account = $1 AND created_at > now() - interval '24 hours'`

var accepted, shed, applied atomic.Int64

// apply moves cents between two wallets in one transaction, locking the
// lower id first so opposite transfers can't deadlock.
func apply(ctx context.Context, db, ledger *sql.DB, j job) error {
	var sent int64
	if err := ledger.QueryRowContext(ctx, velocity, j.sender).Scan(&sent); err != nil {
		return err
	}
	if sent > 5_000_000 {
		return errors.New("velocity limit exceeded")
	}
	tx, err := db.BeginTx(ctx, nil)
	if err != nil {
		return err
	}
	defer tx.Rollback()
	first, second := j.from, j.to
	d1, d2 := -j.cents, j.cents
	if second < first {
		first, second, d1, d2 = second, first, d2, d1
	}
	const q = `UPDATE wallets SET balance_minor = balance_minor + $1 WHERE id = $2`
	if _, err := tx.ExecContext(ctx, q, d1, first); err != nil {
		return err
	}
	if _, err := tx.ExecContext(ctx, q, d2, second); err != nil {
		return err
	}
	return tx.Commit()
}

func main() {
	workers := flag.Int("workers", 8, "transfers applied at once")
	queue := flag.Int("queue", 0, "max transfers waiting for a worker; 0 = no limit")
	flag.Parse()

	db, err := sql.Open("pgx", os.Getenv("DATABASE_URL"))
	if err != nil {
		log.Fatal(err)
	}
	db.SetMaxOpenConns(*workers)
	ledger, err := sql.Open("pgx", os.Getenv("LEDGER_URL"))
	if err != nil {
		log.Fatal(err)
	}
	ledger.SetMaxOpenConns(*workers)
	ctx := context.Background()
	var senders []string
	rows, err := ledger.QueryContext(ctx, `SELECT id FROM accounts LIMIT 2000`)
	if err != nil {
		log.Fatal(err)
	}
	for rows.Next() {
		var id string
		rows.Scan(&id)
		senders = append(senders, id)
	}
	rows.Close()
	if _, err := db.ExecContext(ctx, `
		CREATE TABLE IF NOT EXISTS wallets (id int PRIMARY KEY, balance_minor bigint NOT NULL);
		INSERT INTO wallets SELECT i, 1000000 FROM generate_series(1, 1000) i
		ON CONFLICT (id) DO UPDATE SET balance_minor = 1000000`); err != nil {
		log.Fatal(err)
	}

	jobs := make(chan job, *queue) // queue 0: unbuffered, senders wait in line
	for range *workers {
		go func() {
			for j := range jobs {
				err := apply(ctx, db, ledger, j)
				applied.Add(1)
				j.done <- err
			}
		}()
	}

	http.HandleFunc("POST /transfers", func(w http.ResponseWriter, r *http.Request) {
		j := job{sender: senders[rand.IntN(len(senders))], from: 1 + rand.IntN(1000), to: 1 + rand.IntN(1000), cents: 1, done: make(chan error, 1)}
		if *queue > 0 {
			select {
			case jobs <- j:
			default: // full: say so now, instead of making the client wait
				shed.Add(1)
				http.Error(w, "busy, retry later", http.StatusServiceUnavailable)
				return
			}
		} else {
			jobs <- j // waits for a free worker, however long
		}
		accepted.Add(1)
		if err := <-j.done; err != nil {
			http.Error(w, err.Error(), http.StatusInternalServerError)
			return
		}
		w.WriteHeader(http.StatusNoContent)
	})

	http.HandleFunc("GET /stats", func(w http.ResponseWriter, r *http.Request) {
		s := []metrics.Sample{{Name: "/memory/classes/total:bytes"}}
		metrics.Read(s)
		json.NewEncoder(w).Encode(map[string]any{
			"goroutines": runtime.NumGoroutine(),
			"memory_mb":  s[0].Value.Uint64() >> 20,
			"accepted":   accepted.Load(), "shed": shed.Load(), "applied": applied.Load(),
		})
	})
	log.Fatal(http.ListenAndServe("127.0.0.1:6063", nil))
}
```

The line that decides this stop is `jobs := make(chan job, *queue)`. With `-queue 0` the channel is unbuffered and the handler does a plain `jobs <- j`: every request waits for a worker, however long that takes. With `-queue 16`, the handler tries to send inside a `select` with a `default`: if 16 are already waiting, it answers **503** immediately.

`flood` is the load generator. It is **open-loop**: it sends at a fixed rate whether or not earlier requests have been answered, the way real users arrive.

```go noverify
// flood sends -rate POST /transfers per second for -for seconds, whether
// or not earlier requests have been answered (as real users do), and
// reports the server's goroutines and memory once a second.
package main

import (
	"flag"
	"fmt"
	"io"
	"net/http"
	"slices"
	"sync"
	"time"
)

func main() {
	rate := flag.Int("rate", 1000, "requests per second")
	dur := flag.Duration("for", 10*time.Second, "how long to send")
	flag.Parse()
	base := "http://127.0.0.1:6063"
	client := &http.Client{Timeout: 60 * time.Second, Transport: &http.Transport{MaxIdleConnsPerHost: 2000}}

	var mu sync.Mutex
	statuses := map[int]int{}
	var ok []time.Duration
	var wg sync.WaitGroup

	go func() {
		for sec := 1; ; sec++ {
			time.Sleep(time.Second)
			resp, err := http.Get(base + "/stats")
			if err != nil {
				continue
			}
			b, _ := io.ReadAll(resp.Body)
			resp.Body.Close()
			fmt.Printf("  t=%2ds server %s", sec, b)
		}
	}()

	tick := time.NewTicker(time.Second / time.Duration(*rate))
	start := time.Now()
	for time.Since(start) < *dur {
		<-tick.C
		wg.Go(func() {
			t := time.Now()
			resp, err := client.Post(base+"/transfers", "", nil)
			code := 0
			if err == nil {
				io.Copy(io.Discard, resp.Body)
				resp.Body.Close()
				code = resp.StatusCode
			}
			mu.Lock()
			statuses[code]++
			if code == http.StatusNoContent {
				ok = append(ok, time.Since(t))
			}
			mu.Unlock()
		})
	}
	sentFor := time.Since(start)
	wg.Wait()
	slices.Sort(ok)
	fmt.Printf("sent for %v, last answer after %v\n", sentFor.Round(time.Second), time.Since(start).Round(time.Second))
	fmt.Printf("statuses: %v\n", statuses)
	if len(ok) > 0 {
		fmt.Printf("204 latency: p50 %v  p99 %v  max %v\n",
			ok[len(ok)/2].Round(time.Millisecond), ok[len(ok)*99/100].Round(time.Millisecond), ok[len(ok)-1].Round(time.Millisecond))
	}
}
```

### Step 2: the measurements

Measured capacity is about 30 transfers a second (8 workers, each running a query that takes a few hundred milliseconds when eight run at once). Normal traffic is 20 a second:

```text
$ ./intake -queue 0 &    # flood -rate 20 -for 10s
statuses: map[204:200]
204 latency: p50 53ms  p99 164ms  max 178ms
```

Now a burst: 100 a second for 10 seconds, over three times capacity. With no limit:

```text
$ ./intake -queue 0 &    # flood -rate 100 -for 10s
  t= 1s server {"accepted":33,"applied":25,"goroutines":163,"memory_mb":12,"shed":0}
  t= 5s server {"accepted":162,"applied":154,"goroutines":708,"memory_mb":21,"shed":0}
  t=10s server {"accepted":329,"applied":321,"goroutines":1373,"memory_mb":29,"shed":0}
  t=20s server {"accepted":623,"applied":615,"goroutines":1078,"memory_mb":33,"shed":0}
  t=33s server {"accepted":987,"applied":979,"goroutines":714,"memory_mb":33,"shed":0}
sent for 10s, last answer after 34s
statuses: map[204:1000]
204 latency: p50 10.582s  p99 23.679s  max 23.946s
```

Every request was eventually served, and that's the problem. A 10-second burst took 34 seconds to clear. The median transfer waited 10.6 seconds, far past the point where any real client would still be waiting (their requests would have timed out and been retried, adding to the pile). 1,373 goroutines sat in line. Memory only grew from 12 to 33 MB: goroutines are cheap, so at this scale the damage is latency, not memory. With bigger payloads or longer bursts, memory goes too.

With a bounded queue of 16:

```text
$ ./intake -queue 16 &   # flood -rate 100 -for 10s
  t= 1s server {"accepted":49,"applied":26,"goroutines":61,"memory_mb":12,"shed":50}
  t= 5s server {"accepted":165,"applied":141,"goroutines":64,"memory_mb":12,"shed":335}
  t=10s server {"accepted":315,"applied":291,"goroutines":63,"memory_mb":16,"shed":684}
sent for 10s, last answer after 11s
statuses: map[204:315 503:684]
204 latency: p50 733ms  p99 1.26s  max 1.38s
```

The same machine served about the same number of transfers in those 10 seconds (315 against 329). The difference: those 315 got answers in about a second, the other 684 were told "503, try later" at once, and the service was back to normal the moment the burst ended. At 20 a second, the queue changes nothing (p99 78 ms, no 503s): a bound only acts when it's needed.

### Step 3: the three answers to "we're full"

<ConceptGrid cols={3}>
  <ConceptCard label="Block">`jobs <- j`. Nothing is lost, but the wait moves upstream: into handler goroutines here, into clients' timeouts, into the load balancer. Right for internal pipelines where the producer should slow down, as in chapter 6's generator.</ConceptCard>
  <ConceptCard label="Shed">`select { case jobs <- j: default: 503 }`. The caller learns immediately and can retry with backoff. Right at service boundaries: this is what `hooksink` did to the statements job in chapter 6.</ConceptCard>
  <ConceptCard label="Drop">Same `select`, but discard silently. Only for data where losing some is acceptable and counted: metrics samples, debug logs. Never for money.</ConceptCard>
  <Gotcha>A limit you don't set is still a limit, just one you didn't choose: CPU, the database's connections, the client's patience. Unbounded queues hide which one you hit until it's too late.</Gotcha>
</ConceptGrid>

<UnderTheHood title="Why select with default is the right way to try a send">

A channel is a `runtime.hchan` (`runtime/chan.go`): a lock, a ring buffer of `dataqsiz` slots with `qcount` in use, and queues of waiting senders and receivers. A `select` with a `default` case compiles to `selectnbsend`, which calls `chansend` with `block = false`. Under the channel's lock, it hands the value straight to a waiting receiver if there is one, puts it in the buffer if there's room, and otherwise returns false without parking the goroutine. That's why "check `len(ch) < cap(ch)`, then send" is wrong and the `select` is right: the check and the send happen under one lock, so no other goroutine can fill the last slot in between.

</UnderTheHood>

## The race detector

*Stop 2 of 5.*

### Step 1: a race that loses money

A **data race** is two goroutines accessing the same memory at the same time, at least one of them writing, with nothing ordering the two accesses. Here is the smallest one that costs money:

```go
// 100 goroutines each deposit 1 cent 10,000 times into one balance.
// Nothing protects balance: this program has a data race.
package main

import (
	"fmt"
	"sync"
)

var balance int64 // cents

func deposit(cents int64) {
	balance = balance + cents // read, add, write: three steps
}

func main() {
	var wg sync.WaitGroup
	for range 100 {
		wg.Go(func() {
			for range 10_000 {
				deposit(1)
			}
		})
	}
	wg.Wait()
	fmt.Printf("expected 1000000, got %d: %d cents lost\n", balance, 1_000_000-balance)
}
```

`balance = balance + cents` is three steps: load `balance` into a register, add, store it back. Two goroutines that both load 500 both store 501, and one deposit is gone. Five runs on the 8-core Mac:

```text
$ go run .
expected 1000000, got 149077: 850923 cents lost
expected 1000000, got 275823: 724177 cents lost
expected 1000000, got 160017: 839983 cents lost
expected 1000000, got 140001: 859999 cents lost
expected 1000000, got 137404: 862596 cents lost
```

Not a rare edge case: most of the money is gone, and a different amount each time.

### Step 2: what -race says

Build or run with `-race` and the compiler instruments every memory access; the runtime then reports any two accesses from different goroutines that aren't ordered by synchronization. The real report for this program (paths shortened):

```text
$ go run -race .
==================
WARNING: DATA RACE
Read at 0x0001004b2410 by goroutine 16:
  main.deposit()
      balance/main.go:13 +0x38
  main.main.func1()
      balance/main.go:21 +0x2c

Previous write at 0x0001004b2410 by goroutine 8:
  main.deposit()
      balance/main.go:13 +0x50
  main.main.func1()
      balance/main.go:21 +0x2c

Goroutine 16 (running) created at:
  sync.(*WaitGroup).Go()
      sync/waitgroup.go:238 +0x6c
==================
…
expected 1000000, got 614162: 385838 cents lost
Found 2 data race(s)
$ echo $?
66
```

Read it from the top: **what** (a read racing with an earlier write), **where** (both at `main.go:13`, the `balance = balance + cents` line, reached from line 21), and **who** (goroutines 16 and 8, both started by `WaitGroup.Go`). The exit status is **66**, not 0, so `go test -race` in CI fails the build. Each distinct race is reported once, however many times it happens.

The cost is real but affordable for tests: the same program used 4.6 MB of memory normally and 25 MB under `-race`. The Go documentation puts typical overhead at 5 to 10 times the memory and 2 to 20 times the run time. Run it in CI and in staging, not in production.

<Callout kind="warn" title="-race only sees what runs">

The detector watches accesses that actually happen during the run. A racy path your tests never exercise, or never exercise concurrently, stays invisible. That's why the race tests that matter are the ones that hammer the same object from many goroutines at once.

</Callout>

### Step 3: the same race in Postgres, where -race can't look

Most services don't keep balances in a Go variable; they keep them in a database. The race moves with them. `wallet` makes 50 goroutines each deposit 1 cent 100 times into the same Postgres row, in four ways:

```go noverify
// wallet: 50 goroutines each deposit 1 cent 100 times into the same
// Postgres row, using one of four ways to do "balance = balance + 1".
package main

import (
	"context"
	"database/sql"
	"errors"
	"flag"
	"fmt"
	"log"
	"os"
	"sync"
	"sync/atomic"
	"time"

	"github.com/jackc/pgx/v5/pgconn"
	_ "github.com/jackc/pgx/v5/stdlib"
)

// deposit adds cents to wallet 1. mode picks how.
func deposit(ctx context.Context, db *sql.DB, mode string, cents int64, retries *atomic.Int64) error {
	switch mode {
	case "read-then-write": // what an ORM's load, modify, save does
		var bal int64
		if err := db.QueryRowContext(ctx, `SELECT balance_minor FROM wallets WHERE id = 1`).Scan(&bal); err != nil {
			return err
		}
		_, err := db.ExecContext(ctx, `UPDATE wallets SET balance_minor = $1 WHERE id = 1`, bal+cents)
		return err

	case "atomic-update": // let Postgres do the arithmetic on the current row
		_, err := db.ExecContext(ctx, `UPDATE wallets SET balance_minor = balance_minor + $1 WHERE id = 1`, cents)
		return err

	case "for-update": // lock the row, then read-then-write inside the transaction
		tx, err := db.BeginTx(ctx, nil)
		if err != nil {
			return err
		}
		defer tx.Rollback()
		var bal int64
		if err := tx.QueryRowContext(ctx, `SELECT balance_minor FROM wallets WHERE id = 1 FOR UPDATE`).Scan(&bal); err != nil {
			return err
		}
		if _, err := tx.ExecContext(ctx, `UPDATE wallets SET balance_minor = $1 WHERE id = 1`, bal+cents); err != nil {
			return err
		}
		return tx.Commit()

	case "serializable": // read-then-write, but Postgres refuses to let it go wrong
		for {
			err := func() error {
				tx, err := db.BeginTx(ctx, &sql.TxOptions{Isolation: sql.LevelSerializable})
				if err != nil {
					return err
				}
				defer tx.Rollback()
				var bal int64
				if err := tx.QueryRowContext(ctx, `SELECT balance_minor FROM wallets WHERE id = 1`).Scan(&bal); err != nil {
					return err
				}
				if _, err := tx.ExecContext(ctx, `UPDATE wallets SET balance_minor = $1 WHERE id = 1`, bal+cents); err != nil {
					return err
				}
				return tx.Commit()
			}()
			var pgErr *pgconn.PgError
			if errors.As(err, &pgErr) && pgErr.Code == "40001" { // serialization_failure
				retries.Add(1)
				continue
			}
			return err
		}
	}
	return fmt.Errorf("unknown mode %q", mode)
}

func main() {
	mode := flag.String("mode", "read-then-write", "read-then-write | atomic-update | for-update | serializable")
	flag.Parse()
	ctx := context.Background()
	db, err := sql.Open("pgx", os.Getenv("DATABASE_URL"))
```

## Designing for zero races

*Stop 3 of 5.*

The race detector finds races after you've written them. Better to make them impossible to write. There are four ways, and chapter 6 already used three of them in a real job.

### Step 1: confinement and immutability

**Confinement**: only one goroutine ever touches the data. Chapter 6's results loop owned every counter, so nothing needed a lock, and `-race` was silent across all its modes. Local variables are confined by default: `bal` in `wallet` was never shared, which is exactly why the race had to be in Postgres.

**Immutability**: data that never changes after it's built can be read by any number of goroutines at once. The ECB rates table in chapter 6 was built once, then only read. The rule that makes this safe: finish building before you publish it (store it under a lock, send it on a channel, or put it in an `atomic.Pointer`), and never modify it afterwards; to change it, build a new one and swap the pointer.

### Step 2: atomics

For a single number or pointer, `sync/atomic` types (`atomic.Int64`, `atomic.Bool`, `atomic.Pointer[T]`) make each operation indivisible, and they're the cheapest option: 38 ns per add under 64-way contention in chapter 6's benchmark, against 120 ns for a mutex. The fix for the balance program is one type:

```go
var balance atomic.Int64

func deposit(cents int64) {
	balance.Add(cents) // one indivisible read-add-write
}
```

Atomics don't compose. Two atomic operations in a row are two operations, and another goroutine can run between them. As soon as an invariant involves two values ("move money from A to B", "balance and transaction count agree"), you need a lock around both.

### Step 3: mutex discipline

<ConceptGrid cols={3}>
  <ConceptCard label="Lock the data, not the code">Put the mutex in the struct next to the fields it guards and say so in a comment (`balance int64 // guarded by mu`). Every access to those fields holds that lock.</ConceptCard>
  <ConceptCard label="Check and act under one lock">If you check a condition and then act on it, both must happen while holding the lock. The lab's second bug is a check and a debit in two separate critical sections: 88 to 238,556 overdrafts.</ConceptCard>
  <ConceptCard label="No I/O while holding a lock">A lock held across a network call makes everyone who needs it wait for the network. Read what you need, unlock, call, lock again and recheck.</ConceptCard>
  <Gotcha>Never copy a struct that contains a mutex after first use: the copy's lock is unrelated to the original's. `go vet`'s copylocks check catches most cases. Pass such structs by pointer.</Gotcha>
</ConceptGrid>

<UnderTheHood title="How sync.Mutex works: spin, park, and starvation mode">

An uncontended `Lock` is one atomic compare-and-swap on the mutex's state word, with no system call, which is why an uncontended lock costs nanoseconds. On contention, `lockSlow` (in `internal/sync/mutex.go` since Go 1.24) first spins briefly on multicore machines, in case the holder is about to release; then it parks the goroutine on a runtime semaphore, freeing its thread for other goroutines. `Unlock` wakes a waiter.

By default a woken waiter has to compete with goroutines that are just arriving, and newcomers usually win: they're already running on a CPU. That's good for throughput, but a waiter could lose over and over. So if a waiter has waited more than 1 ms (`starvationThresholdNs = 1e6`), the mutex switches to **starvation mode**: `Unlock` hands ownership directly to the waiter at the front of the queue, and newcomers queue behind it. It switches back once the queue drains or a waiter got the lock quickly.

`sync.RWMutex` has the mirror problem: a steady stream of readers could keep a writer waiting forever. Go's version blocks new readers once a writer is waiting, so the writer gets in after the current readers finish.

</UnderTheHood>

## The Go memory model

*Stop 4 of 5.*

### Step 1: the rule

It's tempting to picture all goroutines reading and writing one shared memory, instantly and in program order. Real hardware doesn't work like that. Each core has its own caches and store buffers, and both the CPU and the compiler reorder memory operations that look independent. The **Go memory model** (`go.dev/ref/mem`, current version June 6, 2022) is the contract that says what you can rely on anyway:

> If a program has no data races, it behaves as if its goroutines' operations were interleaved in some order: sequential consistency. To get there, every conflicting pair of accesses must be ordered by a **happens-before** edge.

<ConceptGrid cols={2}>
  <ConceptCard label="Channels">A send happens before the matching receive completes. A close happens before a receive that returns because of it. For a buffered channel of capacity C, the k-th receive happens before the (k+C)-th send completes, which is why a buffered channel works as a semaphore.</ConceptCard>
  <ConceptCard label="Locks">The n-th `Unlock` of a mutex happens before the (n+1)-th `Lock` returns. So everything written under a lock is visible to the next goroutine that takes it.</ConceptCard>
  <ConceptCard label="Once, WaitGroup, go">`once.Do(f)`'s call of `f` happens before any `Do` returns. `wg.Done` happens before the `Wait` it unblocks returns. A `go` statement happens before the new goroutine starts.</ConceptCard>
  <ConceptCard label="Atomics">Since the 2022 revision, `sync/atomic` operations are sequentially consistent: if an atomic load observes an atomic store, the store happens before the load.</ConceptCard>
</ConceptGrid>

### Step 2: breaking it on real hardware

The classic test is message passing: a writer stores `data`, then `ready`; a reader loads `ready`, then `data`. If the reader sees the new `ready`, surely it sees the new `data`? This program checks 20 million times, with nothing synchronizing the two plain variables:

```go noverify
// The message-passing test. A writer stores data, then ready.
// A reader that sees the new ready expects the new data too.
// Nothing synchronises the two stores and the two loads: this program
// has a data race, on purpose, to see what the hardware does with it.
package main

import (
	"fmt"
	"runtime"
	"sync/atomic"
)

type slot struct {
	data  int64
	_     [56]byte // keep data and ready on different cache lines
	ready int64
}

func main() {
	runtime.GOMAXPROCS(2)
	const trials = 20_000_000
	var s slot
	var arrived atomic.Int64 // a barrier: both goroutines start each trial together

	barrier := func(i int) {
		arrived.Add(1)
		for arrived.Load() < int64(2*(i+1)) {
		}
	}

	done := make(chan int, 2)
	go func() { // writer
		for i := range trials {
			barrier(i)
			v := int64(i + 1)
			s.data = v
			s.ready = v
		}
		done <- 0
	}()
	go func() { // reader
		stale := 0
		for i := range trials {
			barrier(i)
			v := int64(i + 1)
			r := s.ready
			d := s.data
			if r == v && d != v {
				stale++
			}
		}
		done <- stale
	}()
	stale := <-done + <-done
	fmt.Printf("%d trials: reader saw the new ready but old data %d times\n", trials, stale)
}
```

On the Apple Silicon Mac (arm64), three runs:

```text
$ go run .
20000000 trials: reader saw the new ready but old data 7933 times
20000000 trials: reader saw the new ready but old data 1063 times
20000000 trials: reader saw the new ready but old data 754 times
```

The reader saw `ready` set and `data` not yet written, hundreds to thousands of times. ARM CPUs (Apple's, and AWS Graviton servers) are allowed to make stores visible, or perform loads, out of program order. The same program built for x86-64 and run under Docker's x86 emulation, which keeps x86's stricter ordering:

```text
$ GOOS=linux GOARCH=amd64 go build -o mp-amd64 .
$ docker run --rm --platform linux/amd64 -v $PWD/mp-amd64:/mp alpine:3.22 /mp
20000000 trials: reader saw the new ready but old data 0 times
```

Zero. That's the trap: code with this race can pass every test on an x86 laptop and CI runner, then fail on ARM servers. Making `ready` an `atomic.Int64` (`s.ready.Store(v)`, `s.ready.Load()`) creates the happens-before edge, and on arm64:

```text
$ go run ./fixed
20000000 trials: reader saw the new ready but old data 0 times
20000000 trials: reader saw the new ready but old data 0 times
20000000 trials: reader saw the new ready but old data 0 times
```

<Callout kind="note" title="What we tried that did NOT break">

A popular claim is that the compiler turns `for !stop {}` into an infinite loop by reading `stop` once. We tried it on Go 1.27 with a global, with an empty loop body, and with a field read through a pointer: each loop saw the change within about 100 ms. Today's compiler doesn't hoist those loads. That doesn't make the code correct: the memory model doesn't promise the load is repeated, and a future compiler may hoist it. "It works on this version" is exactly what the memory model tells you not to rely on.

</Callout>

## Bugs that survive review

*Stop 5 of 5.*

These bugs look fine in a diff, pass tests, and wait for the right timing. Each one here was reproduced for real, along with the tool that finds it.

### Step 1: the lost wakeup

`sync.Cond` lets goroutines wait until some state changes. Its trap: a `Signal` wakes only a goroutine that is *already waiting*. Signal first and wait second, and the wake-up is lost:

<GoPlayground>

```go
// The settlement file is ready before anyone starts waiting for it.
package main

import (
	"fmt"
	"os"
	"sync"
	"time"
)

func main() {
	var mu sync.Mutex
	ready := sync.NewCond(&mu)
	fileReady := false

	go func() { // the producer finishes quickly
		mu.Lock()
		fileReady = true
		ready.Signal() // nobody is waiting yet: this wakes no one
		mu.Unlock()
	}()

	time.Sleep(10 * time.Millisecond) // the consumer is busy with something else first

	mu.Lock()
	if len(os.Args) > 1 && os.Args[1] == "fixed" {
		for !fileReady { // check the state, and wait only if it isn't true yet
			ready.Wait()
		}
	} else {
		ready.Wait() // BUG: waits for a signal that has already been sent
	}
	mu.Unlock()
	fmt.Println("processing the settlement file")
}
```

</GoPlayground>

```text
$ go run .
fatal error: all goroutines are asleep - deadlock!

goroutine 1 [sync.Cond.Wait]:
$ go run . fixed
processing the settlement file
```

The fix is the pattern `sync.Cond`'s documentation insists on: keep the state in a variable guarded by the lock, and `for !condition { cond.Wait() }`. If the state is already true, you never wait; if you're woken and it isn't true (another goroutine got there first), you wait again. In new code, a closed channel is usually simpler: closing is permanent, so a late receiver still sees it.

### Step 2: the goroutine leak

`/rate` asks two FX sources at once and answers with whichever replies first. It works, fast, every time:

```go noverify
// /rate asks two FX sources at once and answers with whichever replies first.
package main

import (
	"fmt"
	"log"
	"math/rand/v2"
	"net/http"
	_ "net/http/pprof"
	"runtime"
	"time"
)

// quote stands in for an HTTP call to an FX provider: it takes 5 to 50 ms.
func quote(source string) string {
	time.Sleep(time.Duration(5+rand.IntN(45)) * time.Millisecond)
	return source + ": 1.1403"
}

func rate(w http.ResponseWriter, r *http.Request) {
	answers := make(chan string) // BUG: unbuffered, and only one answer is read
	go func() { answers <- quote("ecb") }()
	go func() { answers <- quote("backup") }()
	fmt.Fprintln(w, <-answers) // the slower goroutine blocks on its send forever

func main() {
	http.HandleFunc("/rate", rate)
	http.HandleFunc("/goroutines", func(w http.ResponseWriter, r *http.Request) {

	log.Fatal(http.ListenAndServe("127.0.0.1:6062", nil))
```

The slower source's goroutine then tries to send on an unbuffered channel nobody will ever read again, and waits forever. Go 1.27 has a built-in profile that finds exactly this: `goroutineleak` reports goroutines blocked on a channel or lock that no running goroutine can reach any more (in Go 1.26 it needed `GOEXPERIMENT=goroutineleakprofile`). After 1,000 requests:

<Callout kind="pro" title="Testing time-dependent code: testing/synctest">

Code like this, which depends on which goroutine finishes first, is hard to test deterministically. `testing/synctest` (Go 1.25) runs a test inside a "bubble" with a fake clock: `synctest.Test(t, func(t *testing.T) { … })`. Inside, `time.Sleep` and timers advance only when every goroutine in the bubble is blocked, and `synctest.Wait()` waits until they all are. You can make the backup source "slower" by sleeping for a second without the test taking a second.

</Callout>

### Step 3: deadlock, in Go and in Postgres

A transfer that locks its source account, then its destination, is correct on its own. Two in opposite directions can each hold the lock the other needs:

```go noverify
// Transfers lock the source account, then the destination.
// Two transfers in opposite directions can each hold the lock the other needs.
package main

import (
	"fmt"
	"net/http"
	_ "net/http/pprof" // serves /debug/pprof/ on the default mux
	"os"
	"sync"
	"sync/atomic"
	"time"
)

type Account struct {
	ID      int
	mu      sync.Mutex
	balance int64 // cents; guarded by mu
}

func transfer(from, to *Account, cents int64) {
	from.mu.Lock()
	defer from.mu.Unlock()
	to.mu.Lock() // BUG: which lock is taken first depends on the direction
	defer to.mu.Unlock()
	from.balance -= cents
	to.balance += cents
}

func main() {
	a, b := &Account{ID: 1, balance: 100_000}, &Account{ID: 2, balance: 100_000}
	var moved [2]atomic.Int64

	if len(os.Args) > 1 && os.Args[1] == "serve" {
		// A real service has other goroutines alive: an HTTP server, tickers.
		go http.ListenAndServe("127.0.0.1:6061", nil)
		go func() {
			for range time.Tick(time.Second) {
				fmt.Printf("progress: a→b %d, b→a %d\n", moved[0].Load(), moved[1].Load())
			}
		}()
	}

	var wg sync.WaitGroup
	for dir := range 2 {
		wg.Go(func() {
			for range 1_000_000 {
				if dir == 0 {
					transfer(a, b, 1)
				} else {
					transfer(b, a, 1)
				}
				moved[dir].Add(1)
			}
		})
	}
	wg.Wait()
	fmt.Println("finished:", a.balance, b.balance)
}
```

With nothing else running, the runtime notices that every goroutine is blocked and stops the program:

```text
$ ./dl
fatal error: all goroutines are asleep - deadlock!

goroutine 1 [sync.WaitGroup.Wait]:
…
goroutine 6 [sync.Mutex.Lock]:
```

In a real service there's always something else alive, an HTTP server or a ticker, so that check never fires. With `serve`, the program simply stops making progress, and stays up:

```text
$ ./dl serve
progress: a→b 0, b→a 5688
progress: a→b 0, b→a 5688
progress: a→b 0, b→a 5688
```

The goroutine profile (`net/http/pprof`, the same endpoint as the leak profile) shows both transfer goroutines parked in `sync.(*Mutex).Lock` called from `main.transfer` at `main.go:24`, the `to.mu.Lock()` line. When two goroutines are stuck on each other's lock, it's a lock-order problem.

Postgres has the same problem with row locks, and a detector for it. `pgdeadlock` runs two transfers in opposite directions, each updating its source row, pausing 50 ms, then its destination:

```go noverify
// Two transfers between wallets 1 and 2, in opposite directions, at the
// same moment. Each updates its source row first, then its destination.
package main

import (
	"context"
	"database/sql"
	"fmt"
	"log"
	"os"
	"sync"
	"time"

	_ "github.com/jackc/pgx/v5/stdlib"
)

func transfer(ctx context.Context, db *sql.DB, from, to int, cents int64, ordered bool) error {
	tx, err := db.BeginTx(ctx, nil)
	if err != nil {
		return err
	}
	defer tx.Rollback()

	type step struct {
		id    int
		delta int64
	}
	steps := []step{{from, -cents}, {to, +cents}}
	if ordered && to < from { // the fix: always touch the lower id first
		steps[0], steps[1] = steps[1], steps[0]
	}

	for i, s := range steps {
		if _, err := tx.ExecContext(ctx,
			`UPDATE wallets SET balance_minor = balance_minor + $1 WHERE id = $2`, s.delta, s.id); err != nil {
			return fmt.Errorf("transfer %d→%d, updating wallet %d: %w", from, to, s.id, err)
		}
		if i == 0 {
			time.Sleep(50 * time.Millisecond) // give the other transfer time to lock its first row
		}
	}
	return tx.Commit()
}

func main() {
	ctx := context.Background()
	db, err := sql.Open("pgx", os.Getenv("DATABASE_URL"))
	if err != nil {
		log.Fatal(err)
	}
	defer db.Close()
	db.ExecContext(ctx, `INSERT INTO wallets VALUES (1, 100000), (2, 100000)
		ON CONFLICT (id) DO UPDATE SET balance_minor = 100000`)

	for _, ordered := range []bool{false, true} {
		fmt.Printf("ordered=%v\n", ordered)

		for _, dir := range [][2]int{{1, 2}, {2, 1}} {
			done.Go(func() {
				err := transfer(ctx, db, dir[0], dir[1], 500, ordered)
				fmt.Printf("  %d→%d after %v: %v\n", dir[0], dir[1], time.Since(t0).Round(time.Millisecond), err)
			})
		}
		done.Wait()
	}
	var total int64
	db.QueryRowContext(ctx, `SELECT sum(balance_minor) FROM wallets WHERE id IN (1, 2)`).Scan(&total)
	fmt.Println("total in wallets 1 and 2:", total)
}
```

Postgres waits `deadlock_timeout` (1 s by default) before checking, finds the cycle, and aborts one transaction so the other can finish. Your code must treat SQLSTATE `40P01` like `40001`: roll back and retry. With `ordered=true` both transfers touch the lower id first, so there's no cycle: the second waits 50 ms for the first and both succeed. That's the same rule `intake` follows, and the lab's first fix: **one global order for taking locks**.

### Step 4: livelock and starvation

A tempting way to avoid deadlock: take the first lock, *try* the second (`sync.Mutex.TryLock`, Go 1.18), and if it's busy, release the first and start over. Two opposite transfers can then keep colliding and backing off in step, always busy, never finishing: a **livelock**. In practice, Go's scheduler is random enough that a perfect livelock rarely lasts, but the wasted work is real. Two goroutines, 200,000 opposite transfers each:

```go noverify
// Two goroutines move money between the same two accounts in opposite
// directions, 200,000 times each, three ways.
package main

import (
	"fmt"
	"math/rand/v2"
	"sync"
	"sync/atomic"
	"time"
)

type Account struct {
	ID      int
	mu      sync.Mutex
	balance int64
}

var retries atomic.Int64

// backOff: take from, try to take to; if it's busy, let go and start over.
func backOff(from, to *Account, jitter bool) {
	for {
		from.mu.Lock()
		if to.mu.TryLock() {
			from.balance--
			to.balance++
			to.mu.Unlock()
			from.mu.Unlock()
			return
		}
		from.mu.Unlock()
		retries.Add(1)
		if jitter {
			time.Sleep(time.Duration(rand.IntN(1000)) * time.Nanosecond)
		}
	}
}

// ordered: always lock the lower ID first. Nothing to retry.
func ordered(from, to *Account) {
	first, second := from, to
	if to.ID < from.ID {
		first, second = to, from
	}
	first.mu.Lock()
	second.mu.Lock()
	from.balance--
	to.balance++
	second.mu.Unlock()
	first.mu.Unlock()
}

func main() {
	for _, name := range []string{"back off, no jitter", "back off, jitter", "lock order"} {
		a, b := &Account{ID: 1}, &Account{ID: 2}
		retries.Store(0)
		start := time.Now()
		var wg sync.WaitGroup
		for _, pair := range [][2]*Account{{a, b}, {b, a}} {
			wg.Go(func() {
				for range 200_000 {
					switch name {
					case "back off, no jitter":
						backOff(pair[0], pair[1], false)
					case "back off, jitter":
						backOff(pair[0], pair[1], true)
					default:
						ordered(pair[0], pair[1])
					}
				}
			})
		}
		wg.Wait()
		fmt.Printf("%-20s %8v  retries %9d  balances %d %d\n",
			name, time.Since(start).Round(time.Millisecond), retries.Load(), a.balance, b.balance)
	}
}
```

```text
$ go run .
back off, no jitter      51ms  retries     96923  balances 0 0
back off, jitter         18ms  retries      4464  balances 0 0
lock order               28ms  retries         0  balances 0 0
```

Without jitter, up to 170,000 retries across three runs for 400,000 transfers. A random pause of up to a microsecond before retrying broke the symmetry and cut retries to about 3,000 to 4,500 (and on this machine was even the fastest, because the pause also reduced contention). Lock ordering needed no retries at all and is the easiest of the three to reason about, which is why it's the default answer.

**Starvation** is the quieter cousin: everything makes progress except one unlucky goroutine that keeps losing. It's why `sync.Mutex` has the 1 ms starvation mode and `RWMutex` blocks new readers behind a waiting writer (stop 3).

<Callout kind="note" title="Deadlock, livelock, starvation: the one-line test">

Look at the stuck goroutines. **Asleep**, each waiting for something another holds: deadlock (goroutine profile, `pg_locks`). **Running**, retrying, CPU busy, nothing finishing: livelock (retry counters, CPU profile). **Most finish, one class never does**: starvation (latency outliers, mutex profile).

</Callout>

## Exercises

<Exercise n={1} title="Pick the queue size" level="easy">

`intake` served 315 transfers in the 10 s burst with `-queue 16`. Predict what `-queue 1000` would do to the p99 latency and the number of 503s during the same burst, then explain which setting you'd ship.

<Solution>

With a queue of 1,000, the 1,000 requests of the burst would all fit, so there would be no 503s, and the service would behave like the unbounded run: the last requests wait behind everyone else, so p99 goes back towards the 23.7 s measured with no limit. A queue is only useful if it's short enough that a request at the back still finishes in time. Rough rule: queue length ≈ throughput × the latency you can accept. At about 30 transfers a second and a 1 s budget, that's about 30, the same order as the 16 used here.

</Solution>

</Exercise>

<Exercise n={2} title="Fix the balance three ways" level="easy">

Fix the `balance` program with (a) `atomic.Int64`, (b) a `sync.Mutex`, (c) confinement: one goroutine owns the balance and receives deposits on a channel. Run each with `-race` and check it prints `0 cents lost`.

<Solution>

```go
// (a)
var balance atomic.Int64
func deposit(cents int64) { balance.Add(cents) }

// (b)
var (
	mu      sync.Mutex
	balance int64 // guarded by mu
)
func deposit(cents int64) {
	mu.Lock()
	balance += cents
	mu.Unlock()
}

// (c)
deposits := make(chan int64)
total := make(chan int64)
go func() {
	var balance int64 // only this goroutine touches it
	for c := range deposits {
		balance += c
	}
	total <- balance
}()
// workers: deposits <- 1; after wg.Wait(): close(deposits); fmt.Println(<-total)
```

All three print `expected 1000000, got 1000000: 0 cents lost` with no race reports. (a) is the natural choice for one number; (b) as soon as a second field must stay consistent with it; (c) when the owner has more to do than add, such as writing each deposit to a log in order.

</Solution>

</Exercise>

<Exercise n={3} title="Which fix for which query?" level="medium">

For each, choose between an atomic `UPDATE`, `SELECT … FOR UPDATE`, and `SERIALIZABLE` with retry, and say why: (a) add a deposit; (b) withdraw, but only if the balance stays at or above zero; (c) approve a transfer only if the customer's total sent today, across all their accounts, stays under a limit.

<Solution>

(a) **Atomic update**: `balance = balance + $1` has no decision in Go, so let Postgres do it: 482 ms and nothing lost in the measurement. (b) Either **`UPDATE … SET balance = balance - $1 WHERE id = $2 AND balance >= $1`** and check the rows affected (still one atomic statement), or `FOR UPDATE` if the rule is too complex for SQL. (c) **`SERIALIZABLE` with retry**: the decision depends on many rows, some of which may not exist yet (today's new transfers), and row locks can't lock rows that don't exist. Serializable isolation detects the conflict; your code retries on `40001`. On a hot row it's expensive (55,113 retries in the benchmark), so use it where the invariant really spans rows.

</Solution>

</Exercise>

<Exercise n={4} title="Find the leak with the profile" level="medium">

Change the leak fix to `make(chan string, 1)` instead of 2. Predict how many goroutines leak after 1,000 requests, then check with the `goroutineleak` profile.

<Solution>

None. With a buffer of 1, the first sender's value goes into the buffer and the handler receives it; the second sender's value also fits into the buffer, which is now empty again, so its send completes too. The profile reports `total 0`. The rule is "enough buffer for every sender that might not be received from", and here one slot is enough because the handler always receives exactly one value first. Two makes the code obviously right without that reasoning, which is why the chapter uses it.

</Solution>

</Exercise>

<Exercise n={5} title="Make the deadlock program safe" level="hard">

Fix `transfer` in the deadlock program so `./dl serve` finishes and prints `finished: 100000 100000`. Then say what else in a real transfer function would need the same ordering.

<Solution>

```go
func transfer(from, to *Account, cents int64) {
	first, second := from, to
	if to.ID < from.ID {
		first, second = to, from
	}
	first.mu.Lock()
	defer first.mu.Unlock()
	second.mu.Lock()
	defer second.mu.Unlock()
	from.balance -= cents
	to.balance += cents
}
```

Each direction moves 1 cent a million times, so both accounts end where they started. Everything that takes more than one of these locks must use the same order: fee accounts, currency pools, and, if balances live in Postgres, the order of the `UPDATE`s inside the transaction (`intake` sorts by id for exactly this reason). A transfer from an account to itself would also deadlock on a non-reentrant mutex (it locks the same one twice): reject `from == to` before locking.

</Solution>

</Exercise>

<Recap>

- **Backpressure.** An unbounded wait turned a 10 s burst into p50 10.6 s, 1,373 goroutines and 34 s to recover; a queue of 16 served about as many with p99 1.26 s and told 684 callers to retry. Size queues from throughput × acceptable latency.
- **Races.** A lock-free `balance += 1` lost 72% to 86% of a million deposits. `-race` named the line and both goroutines and exited with status 66. The same read-then-write in Postgres lost 96%, and `-race` was silent: use atomic `UPDATE`s, `FOR UPDATE`, or `SERIALIZABLE` with retry.
- **Zero races by design.** Confine, make immutable, use atomics for one value, and mutexes for invariants across values, with check and act under the same lock.
- **Memory model.** Only happens-before edges (channels, locks, Once, WaitGroup, atomics) guarantee visibility. The message-passing race returned old data 754 to 7,933 times per 20 million on arm64, 0 on x86 emulation: tests on one architecture can't clear a race.
- **Bugs that survive review.** A lost wakeup killed the program with `all goroutines are asleep`; a first-answer-wins handler leaked 1,000 goroutines, found by Go 1.27's `goroutineleak` profile; opposite lock orders deadlocked in Go (silently, in a live service) and in Postgres (`40P01` after 1 s); `TryLock` back-off wasted up to 170,000 retries. One global lock order fixes the last two.

</Recap>
