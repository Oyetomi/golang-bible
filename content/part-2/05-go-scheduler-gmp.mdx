You type `go f()` and it runs. Most of the time that's all you need to know. This chapter is about the times it isn't: when a service with idle database connections and plenty of memory answers a one-row lookup in 744 ms, and nothing in your code explains why.

5. **CPU-bound vs I/O-bound in a real service.** The 744 ms lookup, the one-channel fix, and how to see it coming.

## The system this chapter measures

Before the theory, the thing we'll keep coming back to. `ledgerapi` is a small HTTP service in front of the `ledger` Postgres database used in the last two chapters (one million accounts). It has two endpoints:

- `GET /balance?id=…` looks up one row by primary key. It spends almost all its time **waiting**: for the request bytes, for Postgres, for the socket to accept the response. That's **I/O-bound**.
- `POST /login` loads a salt and hash from a `credentials` table, then runs **PBKDF2-SHA256 with 600,000 iterations** (the OWASP recommendation) over the submitted password with `crypto/pbkdf2`. That's tens of milliseconds of pure arithmetic per request. That's **CPU-bound**.

A load generator sends 100 `/balance` requests per second for 8 seconds, while 32 clients call `/login` back to back. The service runs in Docker with `--cpus=4`. Here's what `/balance` latency looked like:

| run | `/balance` p50 | `/balance` p99 |
|---|---|---|
| no logins | 2.6 ms | 13.8 ms |
| 32 logins at once | **744.2 ms** | **975.2 ms** |
| 32 logins, at most 2 hashing at a time | 0.9 ms | 4.0 ms |

Same code, same database, same machine. The balance query didn't get slower. What changed is how long the goroutine serving it waited for a turn on a CPU. By the end of the chapter you'll be able to explain each number in that table, and the third row is one `select` statement.

## The G/M/P Model

*Stop 1 of 5.*

The runtime has to run perhaps 100,000 goroutines on a machine with 4 cores, using the operating system's threads, which are expensive (each has a kernel structure and a stack of its own, typically reserving megabytes). It does that with three kinds of object.

### Step 1: the three letters

<ConceptGrid cols={3}>
  <ConceptCard label="G: goroutine">A function you started with `go`, plus everything needed to pause and resume it: its stack (starting at 2 KB, grown by copying when needed), the saved program counter and stack pointer, and a status such as runnable, running or waiting. The runtime's struct is `g` in `runtime/runtime2.go`. Starting and finishing an empty one took about 165 ns in a benchmark on the machine used here.</ConceptCard>
  <ConceptCard label="M: machine (OS thread)">A real operating-system thread, the thing the kernel schedules onto a CPU core. An M runs one G at a time. The runtime creates Ms when it needs them and parks idle ones for reuse. It refuses to go past 10,000 (you'll see the crash in stop 3).</ConceptCard>
  <ConceptCard label="P: processor (a permit)">Not hardware. A P is the right to run Go code, plus the per-P state that goes with it: a local queue of up to 256 runnable Gs, a memory-allocation cache, timers. An M must hold a P to run Go code. There are exactly `GOMAXPROCS` Ps.</ConceptCard>
  <Gotcha>There is no fixed pairing of goroutine and thread. A goroutine can start on one thread, wait for the network, and continue on another. That's why thread-local tricks from other languages don't exist in Go.</Gotcha>
</ConceptGrid>

In one sentence: **a P holds a queue of runnable Gs; an M holds a P and runs the G at the front of the queue.** When that G has to wait, the M puts it aside and runs the next one. When the M itself gets stuck in the kernel, the P moves to another M.

Why a middle layer at all? Before Go 1.1 there were only Gs and Ms, with one global queue protected by one lock, and every thread fought over it. Dmitry Vyukov's 2012 redesign added P so each one could have its own queue and allocation cache that its M uses without locking. The number of Ps, not the number of threads, is what bounds parallelism.

### Step 3: GOMAXPROCS, the number of Ps

`runtime.GOMAXPROCS(n)` sets the number of Ps and returns the old value; `runtime.GOMAXPROCS(0)` just reads it. You can also set the `GOMAXPROCS` environment variable before starting the program. With 1 P your goroutines take turns on one core: concurrent, not parallel. With 8, up to 8 run at the same instant.

What's the default? For years it was the number of logical CPUs the machine reports, `runtime.NumCPU()`. In a container that's the host's CPUs, not the container's limit. So a pod limited to 2 CPUs on a 64-core node got 64 Ps; the kernel's CPU controller then throttled it every time those 64 threads used their 2 CPUs' worth of time, which showed up as latency spikes. The standard fix was the `go.uber.org/automaxprocs` package, imported for its side effect.

Go 1.25 made the runtime read the limit itself. This program prints what it gets:

```go noverify
// Prints how many Ps the runtime chose, then watches for changes.
package main

import (
	"fmt"
	"os"
	"runtime"
	"time"
)

func main() {
	fmt.Printf("NumCPU=%d GOMAXPROCS=%d\n", runtime.NumCPU(), runtime.GOMAXPROCS(0))
	if len(os.Args) > 1 && os.Args[1] == "watch" {
		last := runtime.GOMAXPROCS(0)
		for range 30 {
			time.Sleep(time.Second)
			if now := runtime.GOMAXPROCS(0); now != last {
				fmt.Printf("GOMAXPROCS changed %d -> %d\n", last, now)
				last = now
			}
		}
	}
}
```

Built twice for Linux with the same Go 1.27 toolchain, once with `go 1.24` in `go.mod` and once with `go 1.27`, and run under different Docker limits on an 8-CPU machine:

```text
$ GOOS=linux CGO_ENABLED=0 go build -o procs .
$ docker run --rm --cpus=2 -v $PWD/procs:/p alpine:3.22 /p
```

| `docker run` flags | `go 1.24` in go.mod | `go 1.27` in go.mod |
|---|---|---|
| (no limit) | NumCPU=8 GOMAXPROCS=8 | NumCPU=8 GOMAXPROCS=8 |
| `--cpus=2` | NumCPU=8 GOMAXPROCS=8 | NumCPU=8 GOMAXPROCS=**2** |
| `--cpus=1.5` | NumCPU=8 GOMAXPROCS=8 | NumCPU=8 GOMAXPROCS=**2** |
| `--cpus=0.5` | NumCPU=8 GOMAXPROCS=8 | NumCPU=8 GOMAXPROCS=**2** |

Three things to read out of that table:

- **The `go` line decides, not the toolchain.** A module that says `go 1.24` keeps the old behaviour even when built with Go 1.27, through the `GODEBUG` settings `containermaxprocs=0` and `updatemaxprocs=0` that Go applies for older modules. Upgrading your toolchain changes nothing until you bump that line.
- **Fractional limits round up, and the floor is 2.** 1.5 CPUs gives 2 Ps, and so does 0.5: the runtime never picks fewer than 2 from a CPU limit, because a limit is an average over time, not a core count.
- **`NumCPU` still reports the host.** Only GOMAXPROCS follows the quota. Code that sizes a worker pool from `runtime.NumCPU()` will still make 8 workers in a 2-CPU container. Size it from `runtime.GOMAXPROCS(0)`.

Two more runs with `go 1.27`:

```text
$ docker run --rm --cpus=2 -e GOMAXPROCS=6 -v $PWD/procs:/p alpine:3.22 /p
NumCPU=8 GOMAXPROCS=6
$ docker run --rm --cpuset-cpus=0-2 -v $PWD/procs:/p alpine:3.22 /p
NumCPU=3 GOMAXPROCS=3
```

An explicit `GOMAXPROCS` environment variable wins over the limit. Pinning the container to three specific cores (`--cpuset-cpus`) changes the process's CPU affinity mask, and that one `NumCPU` does see.

The default isn't only computed at startup. Run the program with `watch`, then change the running container's limit:

```text
$ docker run -d --name procwatch --cpus=4 -v $PWD/procs:/p alpine:3.22 /p watch
$ docker update --cpus=2 procwatch
$ docker update --cpus=6 procwatch
$ docker logs procwatch
NumCPU=8 GOMAXPROCS=4
GOMAXPROCS changed 4 -> 2
GOMAXPROCS changed 2 -> 6
```

The runtime rechecks the limit in the background and resizes the set of Ps. If you call `runtime.GOMAXPROCS(n)` yourself or set the environment variable, those automatic updates stop; `runtime.SetDefaultGOMAXPROCS()` (Go 1.25) turns them back on.

<Callout kind="pro" title="Do you still need automaxprocs?">

Not once your `go.mod` says `go 1.25` or later: delete the import. Until then it still does its job. One difference to know about: Kubernetes CPU *requests* don't set a limit, so a pod with a request but no limit gets the node's CPU count either way.

</Callout>

<UnderTheHood title="The g, m and p structs">

All three are in `runtime/runtime2.go`. A `g` holds its stack bounds (`stack.lo`, `stack.hi`), a `gobuf` with the saved stack pointer and program counter used when it's switched out, its `atomicstatus` (`_Grunnable`, `_Grunning`, `_Gwaiting`, `_Gsyscall`, `_Gpreempted`, `_Gdead`…), and the `m` it's running on. New goroutines start with a 2 KB stack (down from 8 KB in Go 1.4); since Go 1.19 the runtime may start them larger, at the average stack size it has observed, to avoid repeated growth.

An `m` holds `g0` (a special goroutine with its own system stack, where the scheduler code runs), `curg` (the user goroutine it's running), and `p`, the P it holds.

A `p` holds `runq`, a fixed ring of 256 `guintptr`s, with `runqhead` and `runqtail`; `runnext`, a single slot for the goroutine that should run next; and `schedtick`, incremented every time it schedules a goroutine. All Ps live in the slice `allp`; changing GOMAXPROCS resizes it while the world is stopped.

These are implementation details. They change between releases (Go 1.26 removed the P state `_Psyscall`, for instance), so treat this as a map of Go 1.27, not an API.

</UnderTheHood>

## Run Queues and Work-Stealing

*Stop 2 of 5.*

A goroutine that's ready to run but not running is **runnable**, and it has to wait somewhere. There are three places.

### Step 1: where runnable goroutines wait

- **`runnext`**: one slot per P. When a goroutine starts another (with `go`) or wakes one (by sending on a channel it was waiting on), the woken one usually goes here and runs next on the same P, while the data it needs is still in that core's cache.
- **The local run queue**: each P's ring of 256 slots. Its own M takes from it without a lock.
- **The global run queue**: one list for the whole program, protected by a lock. Goroutines land here when a local queue overflows (half the local queue moves over at once), and, as stop 4 shows, when they're preempted.

Each P normally takes work from its own queue. To make sure the global queue isn't starved, every 61st time a P schedules (`schedtick%61 == 0` in `runtime/proc.go`), it checks the global queue first.

You can watch these queues fill. `GODEBUG=schedtrace=1000` makes the runtime print one line a second. Here's `ledgerapi` four seconds into the 32-login run:

```text
SCHED 5020ms: gomaxprocs=4 idleprocs=0 threads=6 spinningthreads=0 needspinning=1 idlethreads=1 runqueue=28 [ 3 8 0 11 ] schedticks=[ 604 518 489 532 ]
```

`runqueue=28` is the global queue; `[ 3 8 0 11 ]` are the four local queues. That's 50 runnable goroutines for 4 Ps, `idleprocs=0`. The same second with logins capped at 2:

```text
SCHED 5022ms: gomaxprocs=4 idleprocs=2 threads=6 spinningthreads=0 needspinning=0 idlethreads=1 runqueue=0 [ 0 0 0 0 ] schedticks=[ 348 330 376 366 ]
```

Nothing waiting and two Ps idle. The two lines together are the whole diagnosis of the 744 ms.

### Step 2: when a P runs out of work

Notice P2's local queue was `0` in the first line while P3's was `11`. Queues get uneven all the time, because goroutines wake up wherever their waker happened to be. An idle P doesn't wait to be given work; it goes looking.

That search lives in `findRunnable` in `runtime/proc.go`. In order, a P with nothing to do:

1. checks the global queue (a few goroutines at a time, under its lock);
2. polls the netpoller without blocking, for goroutines whose sockets are now ready;
3. **steals** from other Ps, up to four passes over them in a random order, taking half of a victim's local queue (and on the last pass, its `runnext` too);
4. if all that fails, gives up its P and puts its M to sleep. The last M to go idle blocks in the netpoller (`epoll_wait`) so network events still wake someone.

M's that are searching are **spinning**; that's the `spinningthreads` column in the trace. Spinning costs CPU, so the runtime keeps at most half the busy Ps' worth of Ms spinning.

<Callout kind="note" title="Stealing can't fix a full house">

Work-stealing moves work to idle Ps. In the 32-login run there were no idle Ps (`idleprocs=0`), so stealing had nothing to do: every P already had more than it could run. Uneven queues are the scheduler's problem. Too much CPU work for the Ps you have is yours, and stop 5 is about that.

</Callout>

## Blocking Syscalls and the Netpoller

*Stop 3 of 5.*

A goroutine that waits must not take a thread with it, or 10,000 waiting clients would need 10,000 threads. How the runtime avoids that depends on **what** the goroutine is waiting for, and the difference is large enough to measure.

### Step 1: measure it

This program parks 1,000 goroutines on TCP connections that never receive a byte, then 1,000 more in a raw `read(2)` on pipes that never receive a byte. After each batch it prints the runtime's own thread count (`/sched/threads/total:threads`, added in Go 1.26) and the kernel's (`Threads:` in `/proc/self/status`).

```go noverify
// 1,000 goroutines waiting on sockets, then 1,000 waiting in a blocking
// read(2) on a pipe: how many OS threads does each cost?
package main

import (
	"fmt"
	"net"
	"os"
	"runtime/debug"
	"runtime/metrics"
	"strings"
	"syscall"
	"time"
)

func report(label string) {
	s := []metrics.Sample{
		{Name: "/sched/goroutines:goroutines"},
		{Name: "/sched/threads/total:threads"},
	}
	metrics.Read(s)
	status, _ := os.ReadFile("/proc/self/status")
	var kernel string
	for _, line := range strings.Split(string(status), "\n") {
		if strings.HasPrefix(line, "Threads:") {
			kernel = strings.TrimSpace(strings.TrimPrefix(line, "Threads:"))
		}
	}
	fmt.Printf("%-34s goroutines=%-5d runtime threads=%-5d kernel threads=%s\n",
		label, s[0].Value.Uint64(), s[1].Value.Uint64(), kernel)
}

func main() {
	report("start")

	// A server that accepts connections and never writes to them.
	ln, err := net.Listen("tcp", "127.0.0.1:0")
	if err != nil {
		panic(err)
	}
	go func() {
		for {
			c, err := ln.Accept()
			if err != nil {
				return
			}
			_ = c // held open, never written to
		}
	}()
	for range 1000 {
		c, err := net.Dial("tcp", ln.Addr().String())
		if err != nil {
			panic(err)
		}
		go func() {
			buf := make([]byte, 1)
			c.Read(buf) // waits forever for a byte that never comes
		}()
	}
	time.Sleep(500 * time.Millisecond)
	report("1000 goroutines in conn.Read")

	// Now the same number waiting in a raw, blocking read(2).
	for range 1000 {
		var fds [2]int
		if err := syscall.Pipe(fds[:]); err != nil {
			panic(err)
		}
		go func() {
			buf := make([]byte, 1)
			syscall.Read(fds[0], buf) // the thread sleeps in the kernel
		}()
	}
	time.Sleep(500 * time.Millisecond)
	report("+1000 goroutines in syscall.Read")

	if len(os.Args) > 1 && os.Args[1] == "limit" {
		debug.SetMaxThreads(1100)
		for range 200 {
			var fds [2]int
			syscall.Pipe(fds[:])
			go func() {
				buf := make([]byte, 1)
				syscall.Read(fds[0], buf)
			}()
		}
		time.Sleep(time.Second)
		report("unreachable?")
	}
}
```

### Step 2: the netpoller, why sockets are cheap

When package `net` opens a socket it puts it in **non-blocking** mode and registers it with the **netpoller**: the runtime's wrapper around the operating system's readiness API (`epoll` on Linux, `kqueue` on macOS and the BSDs, I/O completion ports on Windows).

A `conn.Read` then goes like this:

1. Try the `read` system call. On a non-blocking socket with no data, the kernel answers immediately with `EAGAIN` ("try again later") instead of sleeping.
2. On `EAGAIN`, record this goroutine as the one waiting to read that socket, and **park** it: status `_Gwaiting`, off every queue. The M goes back to the scheduler and runs something else.
3. Later, some M asks the kernel which registered sockets became ready: the non-blocking poll in `findRunnable`, sysmon's periodic poll, or an idle M blocked in `epoll_wait`. Each ready socket's waiting goroutine is made runnable.
4. The goroutine runs, retries the `read`, and gets its data. From its point of view, `conn.Read` simply returned.

That's what you saw in stop 1's second stage. It's also why "one goroutine per connection" is the normal way to write a Go server: a waiting goroutine costs its stack (a few KB) and nothing else.

<Define term="Netpoller">
The part of the runtime that waits for many file descriptors at once through `epoll`, `kqueue` or IOCP, and turns "this socket is ready" into "this goroutine is runnable". Package `net` uses it for every socket, and package `os` uses it for pipes and terminals. **Why it matters:** a goroutine waiting on the network costs no thread. **What doesn't use it:** regular disk files, which are always "ready" as far as `epoll` is concerned, and raw calls through package `syscall`.
</Define>

### Step 3: system calls, why `read(2)` is expensive

The hand-off in that stage is `retake` in `runtime/proc.go`. Go 1.27's source says it takes the P back "if it's there for more than 1 sysmon tick (at least 20us)", and it skips that when there's no other work waiting and the call is under 10 ms, since then nobody needs the P. Calls the runtime knows will block for a long time use `entersyscallblock`, which hands the P off immediately.

### Step 4: the thread limit

Each stuck system call holds a thread, and the runtime has a ceiling: 10,000 threads by default, adjustable with `debug.SetMaxThreads`. Run the same program with `limit`, which sets the ceiling to 1,100 and then starts 200 more blocking reads:

## Async Preemption and sysmon

*Stop 4 of 5.*

The netpoller and the P hand-off deal with goroutines that wait. The opposite problem is a goroutine that never waits: it holds its P until it's done. How long can it keep others waiting?

### Step 1: a loop with nothing in it

This program has one P. One goroutine adds up squares, a loop with no function calls, no allocation and no channel operations. Meanwhile `main` tries to wake up every millisecond and records how late it wakes.

<GoPlayground>

```go
// One P. One goroutine sums squares in a loop with no function calls.
// Another wants to wake up every millisecond. How late does it wake?
package main

import (
	"fmt"
	"runtime"
	"time"
)

//go:noinline
func sumSquares(n int) int {
	total := 0
	for i := range n {
		total += i * i // no calls, no allocations, no channel operations
	}
	return total
}

func main() {
	runtime.GOMAXPROCS(1)

	done := make(chan int)
	go func() { done <- sumSquares(1_000_000_000) }()

	var worst time.Duration
	wakeups := 0
	for {
		start := time.Now()
		select {
		case total := <-done:
			fmt.Printf("loop finished (total %d)\n", total)
			fmt.Printf("1ms sleeps completed while it ran: %d, worst wake-up delay: %v\n",
				wakeups, worst.Round(100*time.Microsecond))
			return
		case <-time.After(time.Millisecond):
			wakeups++
			if late := time.Since(start) - time.Millisecond; late > worst {
				worst = late
			}
		}
	}
}
```

</GoPlayground>

### Step 2: how the runtime interrupts a goroutine

Go can pause a goroutine in two ways.

**Cooperatively.** The compiler adds a check at the start of most functions (it's there anyway to see whether the stack needs to grow). To ask a goroutine to stop, the runtime makes that check fail; the next function call notices and hands control to the scheduler. Channel operations, locks and system calls are also points where the scheduler gets control. `sumSquares`'s loop has none of these, which is why Go 1.13 and earlier could hang on it.

**Asynchronously**, since Go 1.14. This is what the stage shows.

Why `SIGURG`? The runtime needed a signal it could send without disturbing programs that use signals themselves. `SIGURG` ("urgent data on a socket") is almost never used, and it's harmless if something else sees an extra one. On Windows, where there are no signals, the runtime suspends the thread instead.

### Step 3: sysmon, the scheduler's watchdog

`sysmon` is started when the program starts and runs on its own thread **without a P**, so it keeps running when every P is busy (that's exactly when it's needed). It sleeps 20 µs between checks, doubling up to 10 ms while nothing is happening. On each pass it:

<ConceptGrid cols={2}>
  <ConceptCard label="Preempts long runners">Any P that has run the same goroutine for 10 ms gets a preemption request (and a `SIGURG`). That's the stage above.</ConceptCard>
  <ConceptCard label="Retakes Ps from system calls">A P whose thread has been in the same system call since the last check is handed to another thread: stop 3's hand-off.</ConceptCard>
  <ConceptCard label="Polls the network">If no one has polled the netpoller for 10 ms, sysmon does it, so ready sockets don't wait even when every P is busy with CPU work.</ConceptCard>
  <ConceptCard label="Forces a GC every 2 minutes">Normally a GC cycle starts because the heap grew; allocation triggers it, not sysmon. But if none has run for two minutes (`forcegcperiod`), sysmon wakes a helper goroutine that starts one.</ConceptCard>
</ConceptGrid>

<Callout kind="warn" title="What preemption can't reach">

A goroutine running C code through cgo, or assembly that isn't marked safe to interrupt, can't be stopped by the signal. It holds its thread until it returns. For the garbage collector, which has to pause every goroutine briefly, that can stretch a pause.

</Callout>

<UnderTheHood title="What happens inside the signal handler">

`preemptone` in `runtime/proc.go` marks the goroutine's preemption flag and, if async preemption is on, calls `preemptM`, which sends `SIGURG` to that specific thread. The signal handler (`sighandler` in `runtime/signal_unix.go`) calls `doSigPreempt`, which checks with `isAsyncSafePoint` that the thread is in Go code at an instruction where the stack and registers can be described to the garbage collector. If it isn't (in a runtime function that must not be interrupted, or in cgo), it gives up and the next check tries again.

If it is, the handler rewrites the thread's saved context so that, on return from the signal, it calls `asyncPreempt`, an assembly function that saves every register on the goroutine's stack and calls into the scheduler. The goroutine goes through `gopreempt_m` to `goschedImpl`, which puts it on the **global** run queue (unless a stop-the-world is pending, in which case it stays in its P's `runnext`). When it next runs, `asyncPreempt` restores the registers and the loop continues from the same instruction.

</UnderTheHood>

<ELI5
  concept="Why a tight loop used to freeze the whole program"
  analogy="A worker who never looks up can't be tapped on the shoulder, so Go 1.14 started ringing a bell instead."
  role="reader"
>

Before Go 1.14, the only way to stop a goroutine was to ask it at its next function call, and a loop like `for { i++ }` never makes one. With one P, nothing else would ever run. With many Ps, the garbage collector, which needs every goroutine to stop for a moment, would wait forever for that one, and every other goroutine would wait with it.

Since Go 1.14 the runtime sends the thread a signal. The goroutine doesn't have to cooperate: it's stopped from outside, at whatever instruction it had reached, if that instruction is safe.

</ELI5>

## CPU-Bound vs I/O-Bound in Practice

*Stop 5 of 5.*

Back to `ledgerapi`, now with the whole picture. The `/balance` goroutine spends almost its whole life parked, and needs a P for a few microseconds at a time, three or four times per request. Each time it becomes runnable, it waits for a P. With 32 logins each wanting a P for most of a second, and preemption only every 10 ms or more, each of those waits is long, and they add up to 744 ms.

### Step 1: the service

Here is all of it. It needs the `ledger` database from the previous chapters; `go run . seed` creates a `credentials` table with 50 users, hashed by the same function the handler uses.

```go noverify
// ledgerapi serves two endpoints from the ledger database:
//
//	GET  /balance?id=<uuid>  one indexed row lookup (I/O-bound)
//	POST /login              PBKDF2-SHA256, 600,000 iterations (CPU-bound)
//
// LOGIN_CAP limits how many logins may hash at once (0 = no limit).
package main

import (
	"context"
	"crypto/pbkdf2"
	"crypto/rand"
	"crypto/sha256"
	"crypto/subtle"
	"encoding/json"
	"fmt"
	"log"
	"net/http"
	"os"
	"runtime"
	"runtime/metrics"
	"strconv"
	"time"

	"github.com/jackc/pgx/v5/pgxpool"
)

const iterations = 600_000 // OWASP's 2023 recommendation for PBKDF2-HMAC-SHA256

func hashPassword(password string, salt []byte) []byte {
	key, err := pbkdf2.Key(sha256.New, password, salt, iterations, 32)
	if err != nil {
		panic(err) // only fails for invalid parameters
	}
	return key
}

type server struct {
	db    *pgxpool.Pool
	slots chan struct{} // nil means no limit
}

func (s *server) balance(w http.ResponseWriter, r *http.Request) {
	var cents int64
	err := s.db.QueryRow(r.Context(),
		`SELECT balance_cents FROM accounts WHERE id = $1`, r.URL.Query().Get("id")).Scan(&cents)
	if err != nil {
		http.Error(w, err.Error(), http.StatusNotFound)
		return
	}
	fmt.Fprintf(w, "%d\n", cents)
}

func (s *server) login(w http.ResponseWriter, r *http.Request) {
	email, password := r.FormValue("email"), r.FormValue("password")
	var salt, stored []byte
	err := s.db.QueryRow(r.Context(),
		`SELECT salt, hash FROM credentials WHERE email = $1`, email).Scan(&salt, &stored)
	if err != nil {
		http.Error(w, "unknown user", http.StatusUnauthorized)
		return
	}
	if s.slots != nil {
		select {
		case s.slots <- struct{}{}:
			defer func() { <-s.slots }()
		case <-r.Context().Done():
			return // the client gave up while queued: don't burn CPU for nobody
		}
	}
	if subtle.ConstantTimeCompare(hashPassword(password, salt), stored) != 1 {
		http.Error(w, "wrong password", http.StatusUnauthorized)
		return
	}
	fmt.Fprintln(w, "ok")
}

// sched reports what the runtime knows about scheduling delay.
func sched(w http.ResponseWriter, r *http.Request) {
	s := []metrics.Sample{
		{Name: "/sched/latencies:seconds"},
		{Name: "/sched/goroutines/runnable:goroutines"},
		{Name: "/sched/gomaxprocs:threads"},
	}
	metrics.Read(s)
	h := s[0].Value.Float64Histogram()
	json.NewEncoder(w).Encode(map[string]any{
		"gomaxprocs":        s[2].Value.Uint64(),
		"runnable_now":      s[1].Value.Uint64(),
		"sched_latency_p99": percentile(h, 0.99).String(),
	})
}

// percentile returns the upper bound of the bucket holding quantile q.
func percentile(h *metrics.Float64Histogram, q float64) time.Duration {
	var total uint64
	for _, c := range h.Counts {
		total += c
	}
	target := uint64(float64(total) * q)
	var seen uint64
	for i, c := range h.Counts {
		seen += c
		if seen >= target {
			return time.Duration(h.Buckets[i+1] * float64(time.Second))
		}
	}
	return 0
}

func seed(ctx context.Context, db *pgxpool.Pool) error {
	if _, err := db.Exec(ctx, `CREATE TABLE IF NOT EXISTS credentials (
		email text PRIMARY KEY, salt bytea NOT NULL, hash bytea NOT NULL)`); err != nil {
		return err
	}
	for i := range 50 {
		salt := make([]byte, 16)
		rand.Read(salt)
		email := fmt.Sprintf("user%d@example.com", i)
		_, err := db.Exec(ctx, `INSERT INTO credentials VALUES ($1, $2, $3)
			ON CONFLICT (email) DO NOTHING`, email, salt, hashPassword("correct horse "+strconv.Itoa(i), salt))
		if err != nil {
			return err
		}
	}
	return nil
}

func main() {
	ctx := context.Background()
	db, err := pgxpool.New(ctx, os.Getenv("DATABASE_URL"))
	if err != nil {
		log.Fatal(err)
	}
	if len(os.Args) > 1 && os.Args[1] == "seed" {
		if err := seed(ctx, db); err != nil {
			log.Fatal(err)
		}
		return
	}

	s := &server{db: db}
	if n, _ := strconv.Atoi(os.Getenv("LOGIN_CAP")); n > 0 {
		s.slots = make(chan struct{}, n)
	}
	http.HandleFunc("GET /balance", s.balance)
	http.HandleFunc("POST /login", s.login)
	http.HandleFunc("GET /debug/sched", sched)
	log.Printf("GOMAXPROCS=%d LOGIN_CAP=%d", runtime.GOMAXPROCS(0), cap(s.slots))
	log.Fatal(http.ListenAndServe(":8080", nil))
}
```

The fix is the `slots` channel in `login`. A buffered channel of capacity *n* is a **semaphore**: sending takes one of *n* slots and blocks when they're all taken; receiving gives one back. The `select` waits for a slot **or** for the client to give up, whichever comes first, so a request whose client has gone never burns CPU. A login waiting for a slot is parked on a channel, not runnable: it doesn't compete for Ps.

<Callout kind="note" title="One more check you might want">

If the client gives up at the same instant a slot frees, both `select` cases are ready and Go picks one at random, so occasionally a login hashes for a client who just left. Adding `if r.Context().Err() != nil { return }` after taking the slot closes that gap. The lab makes you think about it.

</Callout>

### Step 3: choosing the cap

Here are all the runs, varying only `LOGIN_CAP`, with 32 login clients each time:

| `LOGIN_CAP` | `/balance` p50 | `/balance` p99 | logins done in 8 s | login p50 | runtime's scheduling p99 |
|---|---|---|---|---|---|
| no cap | 744.2 ms | 975.2 ms | 198 | 1.44 s | 167.8 ms |
| 4 (= GOMAXPROCS) | 22.3 ms | 46.9 ms | 200 | 1.48 s | 14.7 ms |
| 3 | 1.0 ms | 2.4 ms | 164 | 1.97 s | 0.13 ms |
| 2 | 0.9 ms | 2.7 ms | 122 | 2.79 s | 0.16 ms |
| 1 | 0.9 ms | 2.9 ms | 79 | 5.39 s | 0.11 ms |

What the table says:

- **A cap equal to GOMAXPROCS isn't enough.** Four logins still fill all four Ps, so `/balance` still waits for preemption: 22 ms. The cap has to leave at least one P free.
- **The cost moves to the logins.** Uncapped, the machine completed 198 logins; with a cap of 2 it completed 122, and each took twice as long. You haven't made anything faster; you've decided who waits. For a login endpoint, a couple of seconds may be fine; for a checkout it may not.
- **Past a point there's nothing to win.** Caps of 3, 2 and 1 give the same `/balance` latency, while logins keep getting slower. With 4 Ps, 3 is the sweet spot here: `GOMAXPROCS - 1`, or `GOMAXPROCS/2` if other CPU work shares the process.
- **The idle baseline was slower than the capped runs** (2.6 ms against 0.9 ms). Most likely that's the cost of waking up: with nothing to do, the runtime's threads and the VM's CPUs go to sleep, and each request pays to wake them. Under load they're already awake.

Throwing more goroutines at CPU-bound work never helps past the number of Ps. That's the practical version of Amdahl's law, below.

### Step 4: seeing it coming

The last column of the table comes from `runtime/metrics`, read by the service's `/debug/sched` handler. `/sched/latencies:seconds` is a histogram of how long goroutines spent runnable before they got to run. It went from 0.16 ms to 168 ms between the capped and uncapped runs, and it rises before your request latency does, because it's the cause. Export it along with `/sched/goroutines/runnable:goroutines` and alert on it.

### Amdahl's law: the ceiling on speedup

A cap raises the question: if more goroutines stop helping at some point, why? Part of the answer is Ps. The rest is arithmetic, and it applies to any parallel work.

<Define term="Amdahl's law" since="The Go Scheduler (Part 2)">
For a fixed job where a fraction `p` can run in parallel and `1-p` can't, the best speedup on `n` cores is `1 / ((1-p) + p/n)`. As `n` grows, that approaches `1/(1-p)`. **Why it matters:** the serial part sets a ceiling no number of cores or goroutines can break. **In practice:** a job that funnels through one lock, one database row or one output file hits that ceiling early.
</Define>

A job that is **95% parallel** can never run more than **20×** faster, because `1/(1 - 0.95) = 20`. The serial 5% (read the input, take the lock, write the result) can't be split, so once the parallel part has shrunk, it's all that's left. At 90% parallel the ceiling is 10×; at 75%, 4×.

<GoPlayground>

```go
package main

import "fmt"

// amdahl returns the maximum speedup on n cores when fraction p of the
// work is parallelizable (and 1-p is irreducibly serial):
//
//	speedup = 1 / ((1-p) + p/n)
//
// As n grows without bound the term p/n vanishes, so the ceiling is 1/(1-p).
func amdahl(p float64, n int) float64 {
	return 1 / ((1 - p) + p/float64(n))
}

func main() {
	parallel := []float64{0.50, 0.75, 0.90, 0.95}
	cores := []int{2, 8, 64, 1024}

	fmt.Printf("%-10s", "p% \\ n")
	for _, n := range cores {
		fmt.Printf("%10d", n)
	}
	fmt.Printf("%12s\n", "ceiling")

	for _, p := range parallel {
		fmt.Printf("%-10.0f", p*100)
		for _, n := range cores {
			fmt.Printf("%10.2f", amdahl(p, n))
		}
		// 1/(1-p) is the n -> infinity ceiling.
		fmt.Printf("%12.1f\n", 1/(1-p))
	}
}
```

</GoPlayground>

```text
p% \ n             2         8        64      1024     ceiling
50              1.33      1.78      1.97      2.00         2.0
75              1.60      2.91      3.82      3.99         4.0
90              1.82      4.71      8.77      9.91        10.0
95              1.90      5.93     15.42     19.64        20.0
```

Look at the `95` row: 1,024 cores still don't reach 20×.

### Gustafson's law: scale the work, not just the cores

Amdahl assumes the job stays the same size. Usually it doesn't: with more cores you process more data. Gustafson and Barsis pointed out in 1988 that if the parallel part grows with the machine while the serial part stays fixed, the serial *fraction* shrinks, and speedup grows almost linearly.

<Define term="Gustafson's law" since="The Go Scheduler (Part 2)">
If the problem grows with the number of cores while the serial part stays constant, the scaled speedup is `n - (1-p)(n-1)`, which is nearly linear in `n`. **Why it matters:** it's why more cores do pay off for growing batches, like a nightly job whose input doubles. **Where it doesn't apply:** a single request whose time is dominated by sequential network round trips.
</Define>

<ConceptGrid cols={2}>
  <ConceptCard label="Amdahl: fixed problem">Same job, more cores. Speedup is capped at `1/(1-p)`. Answers "how much faster does *this* job get?"</ConceptCard>
  <ConceptCard label="Gustafson: growing problem">Bigger job, more cores, same serial part. Scaled speedup is close to `n`. Answers "how much *more* work can I do in the same time?"</ConceptCard>
  <Gotcha>They answer different questions. Before adding cores, decide which one you're asking: finishing a fixed job faster (mind the ceiling), or doing more work in the same time (scale away).</Gotcha>
</ConceptGrid>

<Exercise n={4} title="Does the cap really stop wasted work?" level="medium">

Run `ledgerapi` with `LOGIN_CAP=2` and 32 login clients, then add a client with a short timeout: `curl -m 0.2 -d 'email=user1@example.com&password=correct horse 1' localhost:18080/login`. Explain why the login it abandoned is never hashed, and describe the case where it could still be.

<Solution>

With two slots taken and 30 logins queued, the request parks in the `select` inside `login`. When `curl` gives up after 200 ms it closes the connection; `net/http` notices the closed connection and cancels `r.Context()`, which makes the `<-r.Context().Done()` case ready, and the handler returns without hashing. (Part 2 chapter 3 measured this cancellation on a real connection.)

It can still be hashed if a slot frees at the moment the context is cancelled: with both cases ready, `select` picks one at random. Checking `r.Context().Err()` after taking the slot handles that. Without the `select`, a plain `slots <- struct{}{}` would wait for a slot and then hash for nobody, which is the second bug in the lab.

</Solution>

</Exercise>

<Lab
  title="Starving Handlers: Cap the Password Hashing"
  archetype="find-it"
  difficulty="guided"
  points={80}
  hintCost={15}
  verify="self-check"
  expect="ALL CHECKS PASS"
  objective="A real HTTP login handler (served by httptest) runs PBKDF2 for every request, however many are already hashing. Edit only login: (1) take a slot from the slots channel before calling checkPassword, and give it back when done, so no more than cap(slots) logins hash at once; (2) if the client gives up while waiting for a slot, return without hashing. main runs the checks: a burst of 8 logins, then a client that waits 100 ms with every slot busy and leaves."
  starter={`package main

import (
	"context"
	"crypto/pbkdf2"
	"crypto/sha256"
	"crypto/subtle"
	"fmt"
	"net/http"
	"net/http/httptest"
	"net/url"
	"runtime"
	"sync"
	"sync/atomic"
	"time"
)

// slots limits how many logins may hash at the same time: half the Ps,
// so the other half stay free for cheap requests like /balance.
var slots = make(chan struct{}, max(1, runtime.GOMAXPROCS(0)/2))

var salt = []byte("per-user-salt-16")
var stored = derive("correct horse")

// login is the handler under test. It is the only function you edit.
//
// BUG 1: every request hashes immediately, however many are already
// hashing. A burst of logins takes every P and /balance waits behind them.
// BUG 2: once you add a limit, a client that gives up while waiting for
// a slot must not be hashed for anyway (watch r.Context()).
func login(w http.ResponseWriter, r *http.Request) {
	if !checkPassword(r.FormValue("password")) {
		http.Error(w, "wrong password", http.StatusUnauthorized)
		return
	}
	fmt.Fprintln(w, "ok")
}

// ── below this line: do not edit ──

var hashing, peak, hashed atomic.Int64

func derive(password string) []byte {
	key, err := pbkdf2.Key(sha256.New, password, salt, 200_000, 32)
	if err != nil {
		panic(err)
	}
	return key
}

// checkPassword runs PBKDF2 (pure CPU work) and records how many run at once.
func checkPassword(password string) bool {
	now := hashing.Add(1)
	defer hashing.Add(-1)
	for {
		p := peak.Load()
		if now <= p || peak.CompareAndSwap(p, now) {
			break
		}
	}
	ok := subtle.ConstantTimeCompare(derive(password), stored) == 1
	hashed.Add(1)
	return ok
}

func main() {
	srv := httptest.NewServer(http.HandlerFunc(login))
	defer srv.Close()
	form := url.Values{"password": {"correct horse"}}
	allOK := true

	// Check 1: a burst of 8 logins never has more than cap(slots) hashing.
	var wg sync.WaitGroup
	var failed atomic.Int64
	for range 8 {
		wg.Go(func() {
			resp, err := http.PostForm(srv.URL, form)
			if err != nil || resp.StatusCode != 200 {
				failed.Add(1)
				return
			}
			resp.Body.Close()
		})
	}
	wg.Wait()
	if failed.Load() > 0 {
		fmt.Printf("FAIL burst: %d of 8 logins did not return 200\\n", failed.Load())
		allOK = false
	}
	if peak.Load() > int64(cap(slots)) {
		fmt.Printf("FAIL burst: %d logins hashed at once, want at most %d\\n", peak.Load(), cap(slots))
		allOK = false
	}

	// Check 2: every slot is busy; a client waits 100ms, then gives up.
	for range cap(slots) {
		slots <- struct{}{}
	}
	before := hashed.Load()
	ctx, cancel := context.WithTimeout(context.Background(), 100*time.Millisecond)
	req, _ := http.NewRequestWithContext(ctx, "POST", srv.URL+"?"+form.Encode(), nil)
	if resp, err := http.DefaultClient.Do(req); err == nil {
		resp.Body.Close()
		fmt.Println("FAIL give-up: request answered while every slot was busy")
		allOK = false
	}
	cancel()
	time.Sleep(100 * time.Millisecond) // the busy logins finish a little later
	for range cap(slots) {
		<-slots
	}
	time.Sleep(500 * time.Millisecond)
	if n := hashed.Load() - before; n != 0 {
		fmt.Printf("FAIL give-up: hashed %d password(s) for a client that had already left\\n", n)

<Recap>

- **G, M, P.** A G is a goroutine; an M is an OS thread; a P is the permit to run Go code, with its own run queue. There are `GOMAXPROCS` Ps, and that, not the number of goroutines or threads, bounds parallelism.
- **GOMAXPROCS in containers.** With `go 1.25` or later in `go.mod`, the default follows the CPU limit (rounded up, at least 2) and updates when the limit changes: measured 4 → 2 → 6 with `docker update`. `NumCPU` still reports the host. With an older `go` line you get the old behaviour on any toolchain.
- **Run queues.** Runnable goroutines wait in `runnext`, their P's 256-slot local queue, or the global queue. Idle Ps steal half of another P's queue. `GODEBUG=schedtrace=1000` shows all of it: `runqueue=28 [ 3 8 0 11 ]` was the 744 ms incident.
- **Waiting costs.** Sockets (and `os.Pipe`) go through the netpoller: 1,000 waiting goroutines cost 2 extra threads. A blocking system call holds its thread; sysmon moves its P to another thread: 1,000 of them cost 1,000 threads, and past `SetMaxThreads` the process dies with `fatal error: thread exhaustion`.
- **Preemption.** sysmon asks any goroutine running for 10 ms to stop and sends `SIGURG`, so a loop without calls can't hold a P forever. It still held it long enough to make a 1 ms sleep 24 ms late; with preemption off, 327 ms.
- **CPU-bound work in a service.** Too much of it makes cheap requests wait for a P. A channel semaphore that leaves at least one P free (here `GOMAXPROCS - 1`) took `/balance` from 744 ms to 1 ms, at the cost of slower logins. Watch `/sched/latencies:seconds`: it moved from 0.16 ms to 168 ms before anyone looked at a trace.
