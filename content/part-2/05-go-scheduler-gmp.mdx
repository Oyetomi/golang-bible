## The G/M/P Model

Let's set the scene. Meridian's ledger service handles hundreds of concurrent `POST /transfers` requests at peak, each one querying Postgres, calling a fraud-check service, and updating account balances. Go is handling all of this with goroutines. But how? You've spawned thousands of goroutines — you certainly haven't spawned thousands of OS threads. Something in the middle is doing the translation.

That something is the **GMP scheduler**, and it's built from three interlocking concepts.

<ConceptGrid cols={3}>
  <ConceptCard label="G — Goroutine">A goroutine: a lightweight, independently scheduled function. A `G` struct in the runtime tracks its stack (starting at 2 KB, growing as needed), its program counter, and its scheduling state. There can be millions of Gs. They cost almost nothing to create.</ConceptCard>
  <ConceptCard label="M — Machine (OS Thread)">An OS thread — the actual thing the operating system schedules onto a CPU core. An `M` runs exactly one `G` at a time. The runtime creates and parks Ms as needed. You'll typically have far fewer Ms than Gs.</ConceptCard>
  <ConceptCard label="P — Processor (Logical Processor)">A scheduling context that sits between G and M. Each P owns a local run queue of ready-to-run Gs. An M must acquire a P to do any useful Go work. `GOMAXPROCS` sets the number of Ps — and therefore the maximum parallelism.</ConceptCard>
  <Gotcha>A goroutine (G) does NOT map 1:1 to an OS thread (M). The runtime multiplexes many Gs onto a smaller number of Ms using Ps as the intermediary. This is the whole trick: goroutines are cheap because they live in user space and the runtime schedules them, not the OS.</Gotcha>
</ConceptGrid>

The relationship in a sentence: **a P holds a queue of Gs ready to run; an M holds a P and runs the G at the head of that queue.** When a G blocks, the M can release the P so another M can run the next G in the queue. This is what makes goroutines so much cheaper than threads.

**On the job:** You hit the GMP model the moment you ask "why isn't my service using all CPU cores?" or "why did spawning 10,000 goroutines not make things faster?" Misunderstanding it leads to wrong GOMAXPROCS settings, CPU starvation of I/O handlers, and mis-diagnosed latency spikes.

### GOMAXPROCS: the dial for parallelism

`GOMAXPROCS` is the number of Ps. It caps how many goroutines can actually run simultaneously. Set it to 1 and your program is concurrent but not parallel — goroutines take turns on one CPU core. Set it to 8 and up to 8 goroutines can run simultaneously on 8 cores.

The default changed in Go 1.25. The runtime now chooses from the number of logical CPUs, the process CPU-affinity mask, and on Linux the cgroup CPU quota. You can query and change it at runtime:

```go
package main

import (
	"fmt"
	"runtime"
)

func main() {
	// Query the current GOMAXPROCS setting.
	current := runtime.GOMAXPROCS(0) // 0 = query without changing
	fmt.Printf("GOMAXPROCS: %d (logical CPUs: %d)\n", current, runtime.NumCPU())

	// Temporarily set to 2 Ps (regardless of CPU count).
	prev := runtime.GOMAXPROCS(2)
	fmt.Printf("Was %d, now %d\n", prev, runtime.GOMAXPROCS(0))

	// Restore.
	runtime.GOMAXPROCS(prev)
	fmt.Printf("Restored to %d\n", runtime.GOMAXPROCS(0))
}
```

### Container-aware GOMAXPROCS (Go 1.25)

In containerised deployments (Docker, Kubernetes), the host's CPU count reported by the OS may be 64 while your container's cgroup limit is 2. Before Go 1.25, the runtime read the host CPU count, spawned 64 Ps, and wasted memory and scheduling overhead for zero gain. The community workaround was the `uber-go/automaxprocs` library, which read the cgroup CPU quota and called `runtime.GOMAXPROCS` at startup.

**As of Go 1.26 (with the feature landing in Go 1.25), this is no longer necessary.** The runtime now considers the cgroup CPU quota directly when choosing the default `GOMAXPROCS`, and periodically updates the default if the logical CPU count, CPU-affinity mask, or cgroup quota changes. The old `automaxprocs` workaround is obsolete for new services.

The new `runtime.SetDefaultGOMAXPROCS` function (Go 1.25) restores the runtime default from code, even if automatic updates were disabled by an earlier `runtime.GOMAXPROCS` call or by the `GOMAXPROCS` environment variable:

```go
// runtime.SetDefaultGOMAXPROCS restores the runtime default,
// using logical CPUs, CPU affinity, and cgroup CPU quota.
runtime.SetDefaultGOMAXPROCS()

// After the call, runtime.GOMAXPROCS(0) returns the container-aware value.
fmt.Println(runtime.GOMAXPROCS(0)) // 2, if cgroup limit is 2.0 CPUs
```

Meridian's ledger service runs with a Kubernetes CPU limit of `4.0`. With Go 1.25+, `GOMAXPROCS` defaults to `4` inside the container without any configuration — no `automaxprocs` import, no Dockerfile `ENV`, no init trick needed. If you pin an explicit `GOMAXPROCS=N` environment variable, the runtime starts with that value and disables automatic updates; a later call to `runtime.SetDefaultGOMAXPROCS()` deliberately opts back into the runtime default, as if the environment variable had not been set.

<Callout kind="pro" title="GOMAXPROCS in a container (Go 1.25+)">

Go 1.25 made container-aware `GOMAXPROCS` the default. You no longer need `uber-go/automaxprocs` for new services — remove it from your `go.mod`. If you're on Go 1.24 or earlier, `automaxprocs` is still the correct workaround. For services that need to guarantee correct behaviour on older toolchains, keep it until you pin Go 1.25+ in your `go.work` or CI matrix.

</Callout>

<UnderTheHood title="The G, M, and P structs in runtime/proc.go">

Every goroutine is a `g` struct (defined in `runtime/runtime2.go`) that holds: the goroutine's stack bounds (`stack.lo`, `stack.hi`), a `gobuf` for saving/restoring registers and the program counter when switching, a status word (`_Grunnable`, `_Grunning`, `_Gwaiting`, `_Gdead`, etc.), a pointer to its current `m`, and scheduling-related fields (like `preempt` and `park`). A goroutine starts with a 2 KB stack (since Go 1.4 reduced the default from 8 KB) that grows automatically — the runtime detects stack overflows, allocates a larger segment, and copies the old contents, adjusting all pointers. Stacks are managed in a pool to avoid repeated allocation.

An `m` struct tracks the OS thread: its `g0` (the goroutine that runs scheduler code), the `p` it currently holds, the `curg` (currently running goroutine), and a `park` semaphore for sleeping when idle.

A `p` struct is the scheduling context: its `runq` (a circular buffer of `*g`, capacity 256 — the local run queue), a `runnext` field for the one goroutine the P wants to run next (bypasses the queue for freshly-spawned goroutines), and links to the global run queue (`sched.runq`). The set of all Ps is stored in `runtime.allp`, and `runtime.GOMAXPROCS` resizes that slice.

As of Go 1.26, the scheduler is a work-stealing, M:N scheduler with both cooperative yield points and asynchronous preemption. The "M:N" terminology means M goroutines are multiplexed onto N OS threads. Note that these struct layouts are implementation details of the Go runtime and may change between versions; treat this as a model grounded in Go 1.26 source, not a guaranteed API.

</UnderTheHood>

## Run Queues and Work-Stealing

Every P owns a **local run queue** — a circular ring buffer of up to 256 runnable goroutines. When a goroutine becomes runnable (newly spawned, woken from a channel op, returned from a syscall), the scheduler tries to put it in the current P's local queue first. Fast, no lock needed.

But what happens when one P's queue is full, or when one P finishes its queue and goes idle while another P is drowning in work? This is where **work-stealing** comes in, and it's one of the cleverest parts of the Go runtime.

**On the job:** Work-stealing is why Meridian's settlement job doesn't permanently starve handlers on other Ps — the scheduler rebalances automatically. You hit the limits of work-stealing when all Ps are simultaneously saturated by CPU-bound work, which is exactly what the semaphore pattern in the final section addresses.

*This animation is a simplified model: in practice, the idle P first checks the global queue and netpoller before attempting to steal, and the victim P is chosen pseudo-randomly from all Ps, not just the busiest one.*

There is also a **global run queue** (`sched.runq` in the runtime). Goroutines land there when a P's local queue is full (the overflow path), or when they're woken up without a clear home P. Every N scheduler ticks, a P checks the global queue first (to prevent starvation of goroutines stuck there).

<UnderTheHood title="The work-stealing algorithm in detail">

The stealing logic lives in `runtime/proc.go` in the function `stealWork`. When a P goes idle, it runs a spinning loop (briefly, to avoid immediate thread parking): it checks the global queue, polls the netpoller for network-ready goroutines, then randomly scans up to `gomaxprocs` other Ps. When it finds a victim P with more than one goroutine in its queue, it locks the victim's `runqhead` and `runqtail` (it's a lock-free ring buffer with atomic operations), copies half the entries to its own queue, and returns.

The "steal half" heuristic was chosen deliberately: stealing one goroutine at a time is wasteful (you pay locking cost for minimal gain); stealing all of them is unfair. Half is the balance.

The global queue check happens roughly every `schedtick%61 == 0` in `schedule()` — the `61` is a prime chosen to avoid rhythmic collisions with other periodic work.

Work-stealing with per-P run queues has been part of the scheduler since the scalable scheduler landed in Go 1.1 (Go 1.14 added *asynchronous preemption*, a different mechanism), with successive refinements over the years to the idle-thread parking mechanism to reduce unnecessary thread wakeups under light load. This is a conceptual model; the precise locking primitives and atomic ordering are implementation details subject to change.

</UnderTheHood>

Here's a runnable demo that illustrates GOMAXPROCS and goroutine counts. Watch how the runtime spawns many goroutines but only runs `GOMAXPROCS` of them simultaneously:

```go
package main

import (
	"fmt"
	"runtime"
	"sync"
	"sync/atomic"
)

func main() {
	procs := runtime.GOMAXPROCS(0)
	fmt.Printf("GOMAXPROCS=%d, NumCPU=%d\n", procs, runtime.NumCPU())

	const n = 10000
	var wg sync.WaitGroup
	var peak atomic.Int64
	var running atomic.Int64

	for range n {
		wg.Add(1)
		go func() {
			defer wg.Done()
			cur := running.Add(1)
			// Track peak concurrent goroutines (approximate — racy by design).
			for {
				old := peak.Load()
				if cur <= old || peak.CompareAndSwap(old, cur) {
					break
				}
			}
			// Simulate lightweight work.
			_ = 1 + 1
			running.Add(-1)
		}()
	}

	wg.Wait()
	fmt.Printf("Spawned %d goroutines; peak concurrent (approx): %d\n", n, peak.Load())
	fmt.Printf("Final goroutine count: %d\n", runtime.NumGoroutine())
}
```

## Blocking Syscalls and the Netpoller

Here's where things get interesting. And by interesting, I mean this is the difference between a Go service that handles 50,000 concurrent connections and one that handles 50.

When a goroutine makes a **blocking syscall** — like reading from a file descriptor that isn't ready, or a `time.Sleep`, or waiting on a mutex — the natural disaster scenario is: the OS thread blocks, the P sits idle with its goroutines, and you've just wasted a CPU. The Go runtime refuses to let this happen.

**On the job:** Meridian's payment webhook receiver makes dozens of outbound HTTPS calls per second to notify merchants. If those calls blocked OS threads, you'd cap out at `GOMAXPROCS` concurrent notifications. The netpoller lets you have 10,000 in-flight with no thread overhead. Get this wrong and your thread count balloons, your container OOMs, and your on-call phone rings at 3am.

*This animation is a simplified model. The actual handoff distinguishes between short and long syscalls — very short syscalls may not trigger a full P handoff at all; sysmon handles reclaiming Ps from syscalls that run long. The `entersyscallblock` path is used for known-blocking calls.*

This handoff is managed by the `entersyscall` and `exitsyscall` functions in `runtime/proc.go`. The key insight: **the M blocks, but the P doesn't.** The P is a portable context that can be picked up by any M.

### Network I/O: the netpoller

Blocking syscalls for file I/O work with the P handoff above. But **network I/O** is handled differently and even more efficiently.

The Go runtime integrates a **netpoller** — a background mechanism built on the OS's non-blocking I/O primitives: `epoll` on Linux, `kqueue` on macOS/BSD, `IOCP` on Windows. When a goroutine does a network read or write (via `net.Conn`, `http.Request`, etc.), the runtime:

1. Checks if the socket is ready. If yes, proceeds immediately.
2. If not ready, registers the file descriptor with the netpoller and **parks the goroutine** (`_Gwaiting`) without blocking any OS thread.
3. The netpoller runs in the background. When the OS signals readiness (via `epoll_wait`), the netpoller marks the goroutine runnable and puts it back in a run queue.

The result: **a goroutine blocked on network I/O consumes no OS thread.** You can have 100,000 goroutines all waiting for network responses and you're using roughly `GOMAXPROCS` OS threads.

<UnderTheHood title="The netpoller internals and integration points">

The netpoller lives in `runtime/netpoll.go` (platform-agnostic) and `runtime/netpoll_epoll.go` / `runtime/netpoll_kqueue.go` (platform specific). The key function is `netpoll(delay int64) gList` — it calls `epoll_wait` (or equivalent) with the given timeout and returns a list of goroutines that are now ready to run.

The netpoller is integrated into the scheduler at three points (as of Go 1.26):
1. **`schedule()`** — each time a P picks a new goroutine to run, it may call `netpoll(0)` (non-blocking poll) to drain any ready network goroutines.
2. **`sysmon`** — the background monitor thread (covered in the next section) calls `netpoll` periodically when no threads are running, ensuring network goroutines get unblocked even under low load.
3. **`findRunnable()`** — when a P is looking for work, it explicitly polls the netpoller after checking its local queue, the global queue, and before attempting to steal.

The netpoller uses `EPOLLET` (edge-triggered epoll) on Linux for efficiency — it only wakes up once per readiness event rather than repeatedly while data is available.

File I/O does NOT go through the netpoller on most platforms. `os.File.Read/Write` on a regular file goes through the blocking syscall + P handoff path. If you need non-blocking file I/O, use `io.Pipe` with a goroutine, or `aio` wrappers. Regular files on Linux are always "ready" from epoll's perspective (they don't support `O_NONBLOCK` in the network sense), so the runtime doesn't bother with the netpoller for them.

## Async Preemption and sysmon

Before Go 1.14, there was a subtle problem. The scheduler was **cooperative**: a goroutine would only yield to the scheduler at certain safe points — function calls (which check for stack growth), channel operations, system calls. A goroutine in a tight loop with no function calls could run forever, starving every other goroutine on that P.

**On the job:** Meridian's annual settlement computation is exactly this pattern — a tight arithmetic loop over millions of ledger rows. Before Go 1.14, it would silently starve the HTTP handlers sharing that P. Since Go 1.14, sysmon preempts it after ~10ms, but the ~10ms window means you can still see latency spikes under heavy CPU load — which is why the semaphore pattern matters even today.

Here's the kind of code that would bring a pre-1.14 server to its knees:

```go
// This loop had NO safe preemption points before Go 1.14.
// On a single-P program, it would starve every other goroutine.
func computeSettlement(entries []int64) int64 {
	var sum int64
	for _, v := range entries {
		sum += v * v // tight arithmetic loop, no function calls
	}
	return sum
}
```

In a server with `GOMAXPROCS=1`, calling this concurrently with HTTP handlers meant the HTTP handlers never ran until the computation finished. That's not acceptable.

### Async preemption (Go 1.14+)

Go 1.14 introduced **asynchronous preemption**. The runtime can now stop a goroutine mid-instruction using OS signals (`SIGURG` on Unix). Here's how it works:

`sysmon` is a runtime monitor thread that runs without a P — directly on an M with no P attached. It never stops. Its jobs (as of Go 1.26):

### Cooperative yield points

Even with async preemption, idiomatic Go still uses cooperative yield points for most scheduling. These are places where the scheduler naturally gets control:

- **Function call prologues** — every function call checks the goroutine's `stackguard` for stack growth; if preemption is requested, it cooperates here.
- **`runtime.Gosched()`** — explicitly yields the processor, letting other goroutines run.
- **Channel operations** — send/receive may block, yielding the P.
- **`sync.Mutex.Lock()`** — if the lock is contended, the goroutine parks.
- **System calls** — enter/exit syscall always goes through the scheduler.

```go
package main

import (
	"fmt"
	"runtime"
	"sync"
)

func main() {
	var wg sync.WaitGroup

	// Without runtime.Gosched(), a tight loop would be uncooperative
	// (though async preemption handles it since Go 1.14).
	for i := range 3 {
		wg.Add(1)
		go func(id int) {
			defer wg.Done()
			for j := range 5 {
				fmt.Printf("goroutine %d: step %d\n", id, j)
				runtime.Gosched() // explicit cooperative yield
			}
		}(i)
	}

	wg.Wait()
}
```

<UnderTheHood title="How async preemption works at the signal level">

The async preemption mechanism (added in Go 1.14) uses `SIGURG` on Unix because SIGURG was historically unused by most programs (and by the Go runtime itself prior to 1.14). When `sysmon` decides to preempt a goroutine, it calls `preemptone(p)` which calls `signalM(mp, sigPreempt)` — sending SIGURG to the specific OS thread running that goroutine.

The signal handler (`runtime/signal_unix.go`) is already registered by the runtime at startup. When the thread receives SIGURG, it checks if it was in Go code (vs. C or assembly). If so, it arranges for the goroutine to call `asyncPreempt` — a small assembly stub (`runtime/preempt_amd64.s`, etc.) that saves all registers into the goroutine's `asyncPreemptBuf`, transitions the goroutine to `_Gpreempted`, and calls back into the scheduler.

The goroutine is then placed back in the global run queue and will resume from the exact instruction it was interrupted at. From the goroutine's perspective, it looks like it returned from a function call — the whole mechanism is invisible to Go code.

On Windows, `SIGURG` isn't available; Windows uses `SuspendThread`/`ResumeThread` instead, which is less efficient but achieves the same effect.

Note: async preemption can only interrupt goroutines in Go code at certain "async-safe" points — it cannot interrupt goroutines in C code (via cgo) or in assembly that isn't annotated as safe. This is why tight cgo loops are harder to preempt.

</UnderTheHood>

## CPU-Bound vs I/O-Bound in Practice

Here's the money question. You have a financial reporting service. At peak hours it handles hundreds of HTTP requests per second — account summaries, transaction histories, balance checks. One of the endpoints (`/api/reports/annual`) triggers a CPU-intensive computation over millions of rows. And you're getting complaints that during the report job, everything else slows to a crawl.

This is the CPU-bound vs I/O-bound story in production, and it plays out very differently depending on which side you're on.

<ConceptGrid cols={2}>
  <ConceptCard label="I/O-bound goroutines">Spend most of their time waiting: network reads, DB queries, disk reads. They park themselves (via the netpoller or syscall P handoff) and consume NO OS thread while waiting. You can have millions of them. GOMAXPROCS barely matters — they're not competing for CPU cycles, they're waiting for I/O.</ConceptCard>
  <ConceptCard label="CPU-bound goroutines">Spend all their time computing: crunching numbers, sorting, encrypting. They hold their P continuously. With GOMAXPROCS=N, at most N goroutines run simultaneously. More CPU-bound goroutines than Ps means scheduling competition. GOMAXPROCS matters enormously here.</ConceptCard>
  <ConceptCard label="The mixed case (your service)">Most real services are mixed: I/O-bound handlers + occasional CPU-bound work. The danger: one CPU-bound goroutine on a P starves the handler goroutines waiting in that P's queue — even with async preemption, there's still a ~10ms preemption latency window.</ConceptCard>
  <Gotcha>Async preemption (Go 1.14+) prevents infinite starvation, but it does NOT eliminate CPU competition. A report goroutine still holds its P for up to ~10ms at a time, and with GOMAXPROCS=4, four report goroutines can monopolize all four Ps for 10ms chunks, making handler latency spiky even if throughput is preserved.</Gotcha>
</ConceptGrid>

### Isolating CPU-bound work

The right answer for the reporting service is to **limit concurrent CPU-bound goroutines** using a semaphore or worker pool. Here's a concrete pattern:

```go
package main

import (
	"context"
	"fmt"
	"runtime"
	"sync"
)

// reportWorkerPool limits concurrent CPU-bound report computations
// to GOMAXPROCS workers — no point having more, they'd just compete.
type reportWorkerPool struct {
	sem chan struct{}
}

func newReportPool() *reportWorkerPool {
	return &reportWorkerPool{
		// Buffer size = number of Ps. Each slot = one CPU core's worth of work.
		sem: make(chan struct{}, runtime.GOMAXPROCS(0)),
	}
}

// Run blocks until a worker slot is free, then runs fn in the caller's goroutine.
// I/O-bound callers (HTTP handlers) call this; they park while waiting for a slot.
func (p *reportWorkerPool) Run(ctx context.Context, fn func() error) error {
	select {
	case p.sem <- struct{}{}: // acquire slot
		defer func() { <-p.sem }() // release on return
		return fn()
	case <-ctx.Done():
		return ctx.Err()
	}
}

func computeAnnualReport(accountID int64, rows []int64) int64 {
	var total int64
	for _, v := range rows {
		total += v
	}
	return total
}

func main() {
	pool := newReportPool()
	var wg sync.WaitGroup

	// Simulate 20 concurrent report requests — only GOMAXPROCS run at once.
	for i := range 20 {
		wg.Add(1)
		go func(id int) {
			defer wg.Done()
			rows := make([]int64, 100_000)
			for j := range rows {
				rows[j] = int64(j)
			}
			err := pool.Run(context.Background(), func() error {
				result := computeAnnualReport(int64(id), rows)
				fmt.Printf("report %d: total=%d\n", id, result)
				return nil
			})
			if err != nil {
				fmt.Printf("report %d cancelled: %v\n", id, err)
			}
		}(i)
	}

	wg.Wait()
}
```

### Amdahl's law: the ceiling on speedup

Capping the report pool at `GOMAXPROCS` raises an obvious question: if more goroutines stop helping past that point, *why*? You met the symptom back in the opening — "why didn't spawning 10,000 goroutines make it faster?" Here's the theory that answers it, and it's not a Go thing. It's arithmetic, and it's merciless.

<Define term="Amdahl's law" since="The Go Scheduler (Part 2)">For a fixed task where fraction `p` is parallelizable and `1-p` is irreducibly serial, the maximum speedup on `n` cores is `1 / ((1-p) + p/n)`. As `n → ∞` the parallel term vanishes and speedup is capped at `1/(1-p)` — the serial fraction sets a hard ceiling no number of cores can beat.</Define>

Read that ceiling slowly: a task that is **95% parallel** can *never* run more than **20×** faster, no matter how many cores you throw at it — because `1/(1 - 0.95) = 20`. The serial 5% (parse the request, acquire one lock, write the final row) cannot be split, so eventually it's *all* that's left and it dominates. Drop to 90% parallel and the ceiling is 10×. At 75% it's 4×. The serial sliver, not the core count, decides your fate.

This is exactly why Meridian's settlement job stops getting faster once concurrent workers pass a handful: the parallel matrix-crunch shrinks toward zero as you add Ps, but the serial setup/teardown is a fixed cost that every run pays. Past the knee, extra goroutines just add scheduling overhead and contention — the same lesson as [Go Mistakes: Concurrency](/appendix/mistakes-concurrency) mistake #56, *"concurrency isn't always faster."* Sometimes the honest move is fewer goroutines, not more.

Let's make the ceiling visceral. This program computes Amdahl speedup for a few `(p, n)` pairs and prints the table — watch the rows flatten as cores climb:

```go
package main

import "fmt"

// amdahl returns the maximum speedup on n cores when fraction p of the
// work is parallelizable (and 1-p is irreducibly serial):
//
//	speedup = 1 / ((1-p) + p/n)
//
// As n grows without bound the term p/n vanishes, so the ceiling is 1/(1-p).
func amdahl(p float64, n int) float64 {
	return 1 / ((1 - p) + p/float64(n))
}

func main() {
	parallel := []float64{0.50, 0.75, 0.90, 0.95}
	cores := []int{2, 8, 64, 1024}

	fmt.Printf("%-10s", "p% \\ n")
	for _, n := range cores {
		fmt.Printf("%10d", n)
	}
	fmt.Printf("%12s\n", "ceiling")

	for _, p := range parallel {
		fmt.Printf("%-10.0f", p*100)
		for _, n := range cores {
			fmt.Printf("%10.2f", amdahl(p, n))
		}
		// 1/(1-p) is the n -> infinity ceiling.
		fmt.Printf("%12.1f\n", 1/(1-p))
	}
}
```

### Gustafson's law: scale the work, not just the cores

Amdahl is a bleak picture, and for years it was used to argue parallel computing was a dead end. Then Gustafson and Barsis pointed out the hidden assumption: Amdahl holds the **problem size fixed**. In real systems you almost never do that — when you get more cores, you process *more data*, not the same data faster.

<Define term="Gustafson's law" since="The Go Scheduler (Part 2)">If the problem grows with the resources (bigger datasets on bigger machines) while the serial work stays roughly constant, the *scaled* speedup is `n - (1-p)(n-1)`, which is close to linear in `n`. Amdahl assumes a fixed problem; Gustafson assumes a growing one — both are correct for the question each asks.</Define>

The intuition: the serial 5% in Amdahl's example was a *fixed* cost. But if you double the dataset, the parallel matrix-crunch doubles while the fixed setup stays the same — so the serial *fraction* shrinks, and the ceiling rises with it. A graphics engine is the textbook case: a faster GPU doesn't render last year's frame in half the time; it renders this year's frame with twice the detail. Same wall-clock budget, more work done.

For Meridian, this is the difference between two honest questions. *"Will adding cores make tonight's settlement finish sooner?"* is an Amdahl question — fixed batch, hard ceiling, cap your pool. *"If we onboard 10× more merchants, can more cores keep settlement inside the nightly window?"* is a Gustafson question — growing batch, near-linear scaling, the cores genuinely pay off.

<ConceptGrid cols={2}>
  <ConceptCard label="Amdahl — fixed problem">Same task, more cores. Speedup is capped at `1/(1-p)`. Answers: "how much faster does *this* job get?" Usually pessimistic — and why a worker pool capped near `GOMAXPROCS` is the right call for a fixed batch.</ConceptCard>
  <ConceptCard label="Gustafson — growing problem">Bigger task, more cores, constant serial part. Scaled speedup `n - (1-p)(n-1)` is near-linear. Answers: "how much *more work* can I do in the same time?" Usually optimistic — and why throwing hardware at growing datasets actually works.</ConceptCard>
  <Gotcha>The two laws don't contradict — they answer different questions. Before you add cores, decide which one you're in: are you trying to finish a *fixed* job faster (Amdahl: mind the ceiling), or do *more* work in the same budget (Gustafson: scale away)? Picking the wrong frame is how teams overspend on cores that the serial fraction was always going to waste.</Gotcha>
</ConceptGrid>

### Reading a scheduler trace

When you suspect scheduler problems, `go tool trace` is your X-ray machine. The detailed treatment is in **Performance Engineering**, but the key steps are:

```go
import "runtime/trace"

// In main or a test:
f, _ := os.Create("trace.out")
trace.Start(f)
defer trace.Stop()
// ... run your program ...
```

Then: `go tool trace trace.out` opens a browser UI. Look for:
- **Goroutine analysis** — goroutines spending more time in "scheduler wait" than "running" signals P contention.
- **Processor view** — P lanes sitting idle while others are overloaded points to work-stealing opportunities.
- **Blocking profiles** — long `syscall` blocks show where P handoffs are happening frequently.

<Callout kind="note" title="Execution tracer vs. pprof">

`go tool trace` (the execution tracer) and `pprof` answer different questions. The tracer shows *when* goroutines run, block, and switch — scheduler-level timing. `pprof` shows *what* code is consuming CPU or allocating memory — profiler-level sampling. For scheduler starvation, start with the tracer. For a hot function, start with pprof. Both tools are covered in full in **Performance Engineering**.

</Callout>

<UnderTheHood title="scheduler-level GODEBUG knobs">

Two `GODEBUG` environment variables expose scheduler internals at runtime:

**`GODEBUG=schedtrace=N`** — prints a scheduler summary every N milliseconds to stderr:
```
SCHED 1000ms: gomaxprocs=4 idleprocs=1 threads=6 spinningthreads=1 idlethreads=2 runqueue=3 [1 0 2 0]
```
- `gomaxprocs`: number of Ps
- `idleprocs`: Ps with no goroutine to run
- `threads`: total OS threads
- `spinningthreads`: Ms spinning looking for work (before parking)
- `runqueue`: global run queue length
- `[1 0 2 0]`: local run queue sizes per P

**`GODEBUG=scheddetail=1`** (combined with `schedtrace`) — prints every goroutine's state. Use sparingly in production — it's very verbose.

These knobs don't require recompilation — set them in environment variables before launching your binary. They're invaluable for diagnosing "why is my service not using all CPUs?" without adding any instrumentation code.

As of Go 1.26, these knobs remain stable and are the canonical way to inspect scheduler state without the full trace overhead.

</UnderTheHood>

### Scheduler metrics via runtime/metrics

`GODEBUG=schedtrace` writes to stderr — handy for development but awkward to integrate with Meridian's Prometheus pipeline. The `runtime/metrics` package exposes scheduler-level metrics you can read programmatically and export to any metrics backend. The two used below are long-standing (`/sched/goroutines:goroutines` since Go 1.16, `/sched/latencies:seconds` since 1.17); Go 1.26 adds *more* scheduler metrics on top — per-state goroutine counts, `/sched/threads:threads`, and `/sched/goroutines-created:goroutines`:

```go
package main

import (
	"fmt"
	"runtime/metrics"
)

func main() {
	// /sched/goroutines:goroutines — current live goroutine count (since Go 1.16).
	// /sched/latencies:seconds — goroutine scheduling-latency distribution (since 1.17).
	descs := []metrics.Sample{
		{Name: "/sched/goroutines:goroutines"},
		{Name: "/sched/latencies:seconds"},
	}
	metrics.Read(descs)

	goroutines := descs[0].Value.Uint64()
	fmt.Printf("live goroutines: %d\n", goroutines)

	// The latencies histogram tells you how long goroutines wait in run queues
	// before getting a P — a leading indicator of P saturation.
	hist := descs[1].Value.Float64Histogram()
	fmt.Printf("scheduling latency buckets: %d\n", len(hist.Buckets))
}
```

<Exercise n={1} title="GOMAXPROCS detective" level="easy">

Write a program that prints the current `GOMAXPROCS` value and `runtime.NumCPU()`. Then set `GOMAXPROCS` to 1, spawn 4 goroutines that each print their ID, and observe that they run sequentially (interleaved but on one P). Use a `sync.WaitGroup` to wait for all.

<Solution>

```go
package main

import (
	"fmt"
	"runtime"
	"sync"
)

func main() {
	fmt.Printf("NumCPU=%d, GOMAXPROCS=%d\n", runtime.NumCPU(), runtime.GOMAXPROCS(0))

	runtime.GOMAXPROCS(1) // single P: goroutines interleave, not truly parallel

	var wg sync.WaitGroup
	for i := range 4 {
		wg.Add(1)
		go func(id int) {
			defer wg.Done()
			fmt.Printf("goroutine %d running\n", id)
		}(i)
	}
	wg.Wait()
	fmt.Println("done")
}
```

With `GOMAXPROCS=1`, only one goroutine runs at a time. The output order is non-deterministic (the scheduler chooses), but you'll never see two goroutines executing simultaneously. In production, prefer the Go 1.25+ runtime default unless you have measured evidence for a manual setting.

</Solution>

<Exercise n={2} title="Spot the blocking pattern" level="easy">

Which of the following operations goes through the **netpoller** (goroutine parks, no thread blocked) and which goes through the **blocking syscall + P handoff** path? Write a program that demonstrates one of each using `net.Dial` and `os.Open`, and add comments explaining which path each takes.

<Solution>

```go
package main

import (
	"fmt"
	"net"
	"os"
)

func main() {
	// PATH: netpoller — goroutine parks, M stays free.
	// The runtime uses epoll/kqueue under the hood.
	conn, err := net.Dial("tcp", "golang.org:80")
	if err != nil {
		fmt.Println("net.Dial (netpoller path):", err)
	} else {
		fmt.Println("net.Dial succeeded via netpoller")
		conn.Close()
	}

	// PATH: blocking syscall + P handoff.
	// os.File is a regular file — not epoll-capable.
	// M blocks on read; P is handed off to another M.
	f, err := os.Open(os.DevNull)
	if err != nil {
		fmt.Println("os.Open error:", err)
		return
	}
	defer f.Close()
	buf := make([]byte, 1)
	f.Read(buf) // blocking syscall path — M parks, P handed off
	fmt.Println("os.Read succeeded via blocking syscall path")
}
```

The distinction matters when profiling: if you see many threads in syscall state in `schedtrace`, you have heavy file I/O on the blocking path. Heavy network I/O won't show this — those goroutines park without consuming threads.

</Solution>

</Exercise>

<Exercise n={3} title="Cooperative yield" level="medium">

Write a program with `GOMAXPROCS=1` and two goroutines: one prints "ping" in a loop 5 times, the other prints "pong" 5 times. Without `runtime.Gosched()`, they may not interleave (the first goroutine runs to completion). Add `runtime.Gosched()` after each print and observe that they interleave. Explain why this worked before Go 1.14 and why async preemption in 1.14+ changes the answer.

<Solution>

```go
package main

import (
	"fmt"
	"runtime"
	"sync"
)

func main() {
	runtime.GOMAXPROCS(1)

	var wg sync.WaitGroup
	wg.Add(2)

	go func() {
		defer wg.Done()
		for range 5 {
			fmt.Println("ping")
			runtime.Gosched() // yield so pong gets a turn
		}
	}()

	go func() {
		defer wg.Done()
		for range 5 {
			fmt.Println("pong")
			runtime.Gosched()
		}
	}()

	wg.Wait()
}
```

**Before Go 1.14:** without `Gosched()`, this loop has a function call (`fmt.Println`) so the scheduler *can* preempt at each call — but there's no guarantee it will. In practice, one goroutine often runs to completion before the other starts. `Gosched()` makes interleaving reliable.

**Go 1.14+ async preemption:** even without `Gosched()`, sysmon will eventually send SIGURG if one goroutine runs more than ~10ms. But for short loops like this (much less than 10ms), async preemption won't fire. `Gosched()` is still the right tool for deliberate cooperative yielding.

</Solution>

</Exercise>

<Exercise n={4} title="Counting goroutines" level="medium">

Write a function `goroutineStorm(n int)` that spawns `n` goroutines, each sleeping for 100ms then decrementing a counter. Before waiting for them, print `runtime.NumGoroutine()`. After they all finish, print it again. Use `sync.WaitGroup`. Explain what `NumGoroutine()` actually counts (hint: it's not just yours).

<Solution>

```go
package main

import (
	"fmt"
	"runtime"
	"sync"
	"time"
)

func goroutineStorm(n int) {
	var wg sync.WaitGroup
	for range n {
		wg.Add(1)
		go func() {
			defer wg.Done()
			time.Sleep(100 * time.Millisecond)
		}()
	}

	// NumGoroutine includes: main goroutine, all spawned goroutines,
	// the runtime's internal goroutines (GC, finalizer, sysmon-adjacent, etc.)
	// Typically 2-4 extra goroutines from the runtime itself.
	fmt.Printf("goroutines during storm: %d (spawned %d + runtime overhead)\n",
		runtime.NumGoroutine(), n)

	wg.Wait()

	fmt.Printf("goroutines after: %d (runtime overhead only)\n",
		runtime.NumGoroutine())
}

func main() {
	goroutineStorm(100)
}
```

`runtime.NumGoroutine()` counts ALL goroutines the runtime knows about: yours plus the runtime's own background goroutines (the GC goroutine, the finalizer goroutine, etc.). On a fresh program you'll see 1-3 extra. This is useful for leak detection — if the count keeps growing after requests complete, you have a goroutine leak. The full leak-detection story is in **Debugging Go**.

</Solution>

</Exercise>

<Exercise n={5} title="CPU-bound fairness with a semaphore" level="hard">

Write a service simulator: 8 "HTTP handler" goroutines that each do 1ms of work (use `time.Sleep`) and print their latency, plus 4 "report" goroutines that each do 50ms of CPU-busy work (tight loop adding integers). Run them all concurrently with `GOMAXPROCS=4`. First, run without any rate-limiting and measure handler latency. Then, add a semaphore (`chan struct{}` buffered at 2) to limit concurrent report goroutines to 2. Show that handler p99 latency improves. (Use `time.Since` for measurements.)

<Solution>

```go
package main

import (
	"fmt"
	"runtime"
	"sync"
	"time"
)

func cpuWork(ms int) {
	// Tight loop approximating ms milliseconds of CPU work.
	// Not precise, but close enough for demonstration.
	deadline := time.Now().Add(time.Duration(ms) * time.Millisecond)
	var x int64
	for time.Now().Before(deadline) {
		x += x*x + 1
	}
	_ = x
}

func runSimulation(reportSem chan struct{}) {
	var wg sync.WaitGroup
	var mu sync.Mutex
	var handlerLatencies []time.Duration

	// 8 handler goroutines — fast I/O-bound work.
	for i := range 8 {
		wg.Add(1)
		go func(id int) {
			defer wg.Done()
			start := time.Now()
			time.Sleep(1 * time.Millisecond) // simulated I/O wait
			lat := time.Since(start)
			mu.Lock()
			handlerLatencies = append(handlerLatencies, lat)
			mu.Unlock()
		}(i)
	}

	// 4 report goroutines — CPU-bound, optionally rate-limited.
	for i := range 4 {
		wg.Add(1)
		go func(id int) {
			defer wg.Done()
			if reportSem != nil {
				reportSem <- struct{}{}
				defer func() { <-reportSem }()
			}
			cpuWork(50)
		}(i)
	}

	wg.Wait()

	var maxLat time.Duration
	for _, l := range handlerLatencies {
		if l > maxLat {
			maxLat = l
		}
	}
	fmt.Printf("handler p99 (max of 8): %v\n", maxLat)
}

func main() {
	runtime.GOMAXPROCS(4)

	fmt.Println("=== Without semaphore ===")
	runSimulation(nil)

	fmt.Println("=== With semaphore (max 2 concurrent reports) ===")
	sem := make(chan struct{}, 2)
	runSimulation(sem)
}
```

Without the semaphore, all 4 report goroutines compete for 4 Ps simultaneously with the handler goroutines, causing handler latency spikes. With the semaphore limiting concurrent reports to 2, two Ps are always available for handler goroutines. Run it a few times — the improvement is consistent, though exact numbers vary by machine.

</Solution>

</Exercise>

<Recap>

You now understand the engine under every goroutine. Let's lock it in:

- **G (goroutine)** — lightweight, user-space, starts at 2 KB. Millions can exist. **M (OS thread)** — the actual thread; there are few of these. **P (logical processor)** — the scheduling context that glues G to M. `GOMAXPROCS` = number of Ps = maximum true parallelism.
- Each P has a **local run queue** (ring buffer, capacity 256). There's also a **global run queue** for overflow. When a P empties its local queue, it **steals half** of a random busy P's queue — automatic load balancing, no orchestrator.
- **Blocking syscalls** trigger a **P handoff**: the M blocks but the P is picked up by another M, keeping goroutines in the queue running. **Network I/O** uses the **netpoller** (epoll/kqueue) — goroutines park without needing one OS thread each. Runnable Go code is still limited by `GOMAXPROCS`, while the runtime may keep extra threads for syscalls and internal work.
- Before Go 1.14, a tight CPU loop with no function calls could starve everything on its P. **Go 1.14 added async preemption** via `SIGURG`: sysmon sends a signal after ~10ms of continuous running, saving registers and parking the goroutine. **`sysmon`** is a P-less background thread that also polls the netpoller, retakes Ps from long-blocked syscalls, and triggers GC.
- **Go 1.25: container-aware GOMAXPROCS.** The runtime now reads the cgroup CPU limit directly — no `uber-go/automaxprocs` needed. `runtime.SetDefaultGOMAXPROCS()` reapplies the container-aware runtime default, even after an explicit env var or earlier `runtime.GOMAXPROCS` call disabled automatic updates. Remove `automaxprocs` from new services targeting Go 1.25+.
- **`runtime/metrics` scheduler metrics.** `/sched/goroutines:goroutines`, `/sched/latencies:seconds`, and the Go 1.26 goroutine-state additions let you feed scheduling health into your Prometheus pipeline. P99 scheduling latency above the service's normal baseline can signal P saturation before it becomes a latency incident.
- **CPU-bound goroutines** compete for Ps. **I/O-bound goroutines** don't (they park). In a mixed service like Meridian's, use a **semaphore or worker pool** to cap concurrent CPU-bound goroutines to `GOMAXPROCS/2`, leaving room for handlers. Use `GODEBUG=schedtrace=1000` and `go tool trace` to diagnose scheduler problems — full trace treatment in **Performance Engineering**.
