## Errors are values

Here is the thing that separates Go engineers from everyone else: in Go, `error` is just an interface.

```go
type error interface {
    Error() string
}
```

That is the entire definition. Any type that has an `Error() string` method satisfies the `error` interface. No magic. No hidden control flow. No "unchecked" category. When a function can fail, it returns an `error` as a plain second return value — and you deal with it.

The *philosophy* matters here, so let's ground it in a real scenario.

You're on the payments team at Meridian. A `chargeCard` function calls the card network, which can fail for a dozen reasons — insufficient funds, an expired card, a network timeout, a fraud hold. In Python, you'd `raise` an exception and hope something upstream catches the right type. In Go, you *return* the error:

```go
// charge.go — Meridian payment domain layer
func chargeCard(ctx context.Context, amountCents int, token string) error {
    resp, err := cardNetwork.Charge(ctx, amountCents, token)
    if err != nil {
        return fmt.Errorf("chargeCard: %w", err)
    }
    if resp.Declined {
        return ErrInsufficientFunds // sentinel — we'll define this shortly
    }
    return nil
}
```

Two disciplines are already in play. The caller *must* check the return value — the compiler won't let it float. And by returning `nil` on success, the function signals clearly: no error, no ambiguity.

**On the job:** In Meridian's ledger service, this pattern is the difference between a clean 402 response and an opaque 500 that leaves the client retrying a declined card forever.

### Handling vs. propagating

Every time you see an error, you face a binary choice:

- **Handle it** — you know what to do (log it, return a fallback, map it to an HTTP status code). The error stops here.
- **Propagate it** — you don't have enough context to do anything useful. Wrap it with context and send it upward.

<ConceptGrid cols={2}>
  <ConceptCard label="Handle">You have enough context. Transform the error into action: return a fallback value, respond with a 4xx, log and continue. The error chain ends here.</ConceptCard>
  <ConceptCard label="Propagate">You're in the wrong layer to decide. Add context (`fmt.Errorf("chargeCard: %w", err)`) and return. Do NOT log AND propagate — you'll get duplicate log lines.</ConceptCard>
  <Gotcha>Never both log and propagate the same error. Pick one. If you log it, handle it (the chain ends). If you propagate it, let the handler at the top log it once with the full context from the chain.</Gotcha>
  <ConceptCard label="nil means success">An `error` return of `nil` is your function's promise: everything worked. Make that promise reliable — only return `nil` when you mean it.</ConceptCard>
</ConceptGrid>

## Wrapping with %w

In Go 1.13, the `errors` package gained the concept of **error wrapping** — a standard way to attach context to an error while keeping the original accessible for later inspection.

The `%w` verb in `fmt.Errorf` is the mechanism:

```go
// Before Go 1.13: you lost the original error type
return fmt.Errorf("repo.FindAccount: %v", err) // %v embeds the string — type gone

// Go 1.13+: %w wraps — the original is still inspectable
return fmt.Errorf("repo.FindAccount %s: %w", accountID, err)
```

The difference is enormous. `%v` gives you a string. `%w` gives you a **chain** — a linked list of error values where every wrapper points to the one inside it.

**On the job:** Every layer that wraps with `%w` instead of `%v` is paying a small forward — the handler that eventually maps the error to a 402 or 404 can inspect the whole chain, not just the outermost message.

<UnderTheHood title="How %w builds a linked chain (Go 1.26)">

`fmt.Errorf` with `%w` returns a `*fmt.wrapError` (an unexported concrete type). (Go 1.26's `fmt` allocation improvement is on the *no-verb* path — `fmt.Errorf("plain message")` with no formatting directive now allocates as cheaply as `errors.New`; the `%w` wrapping path here is unchanged.)

```go
// Simplified internals (conceptual model based on Go stdlib, go1.26)
type wrapError struct {
    msg string
    err error // the wrapped error — the "next link"
}

func (e *wrapError) Error() string { return e.msg }
func (e *wrapError) Unwrap() error { return e.err }
```

The `Unwrap() error` method is the protocol. `errors.Is` and `errors.As` walk this chain by calling `Unwrap()` repeatedly until they either find a match or reach `nil`. The chain is a singly-linked list of error values, each pointing inward.

As of Go 1.20, you can also wrap *multiple* errors simultaneously with `fmt.Errorf("...: %w; %w", err1, err2)` — the returned error satisfies `interface{ Unwrap() []error }` and `errors.Is`/`errors.As` fan out across both branches. Useful for join/multi-error types in validation pipelines.

*This diagram is a conceptual model — it faithfully represents the chain protocol while abstracting over implementation details like GC word layout and inlining decisions.*

</UnderTheHood>

### `errors.Is` vs `errors.As`

These are your two forensic tools for inspecting a chain:

- **`errors.Is(err, target)`** — walks the chain comparing each error to `target` using `==`. Use this for **sentinel** comparison.
- **`errors.As(err, &target)`** — walks the chain looking for an error that *can be assigned* to `target`'s type. Use this when you need **fields** from a typed error.

```go
// errors.Is: sentinel comparison — does this chain contain ErrInsufficientFunds?
if errors.Is(err, ErrInsufficientFunds) {
    w.WriteHeader(http.StatusPaymentRequired) // 402
    return
}

// errors.As: typed extraction — is there a *CardNetworkError anywhere in the chain?
var cardErr *CardNetworkError
if errors.As(err, &cardErr) {
    // cardErr now holds the concrete value with its fields
    log.Error("card network error", "decline_code", cardErr.DeclineCode)
}
```

As of Go 1.26, the standard library also ships **`errors.AsType[T]`** — a generic, type-safe alternative to `errors.As` that eliminates the `var target *T; errors.As(err, &target)` ceremony:

```go
// Go 1.26: errors.AsType[T] — generic, no pointer-to-pointer dance
if cardErr, ok := errors.AsType[*CardNetworkError](err); ok {
    log.Error("card network error", "decline_code", cardErr.DeclineCode)
}
```

`errors.AsType[T]` walks the same chain as `errors.As` — it's the same semantics, just without the temporary variable. Use it for new code; both forms are correct.

```go
type CardNetworkError struct {
	DeclineCode string
	Retryable   bool

func findAndCharge() error {
```

## Sentinel vs typed errors

You have two fundamental tools for defining errors that callers can inspect: **sentinel values** and **typed errors**. Neither is always right — the choice is design.

### Sentinel errors

A sentinel is a package-level `error` variable, defined once, compared by identity:

```go
// payments/errors.go — Meridian domain layer
var (
    ErrInsufficientFunds = errors.New("insufficient funds")
    ErrCardExpired       = errors.New("card expired")
    ErrFraudHold         = errors.New("fraud hold — contact your bank")
)
```

Callers use `errors.Is` to check for them:

```go
if errors.Is(err, payments.ErrInsufficientFunds) {
    return http.StatusPaymentRequired
}
```

Sentinels are simple and cheap. Their weakness: they carry no data. You can't attach the account ID, or the fraud score, or whether the error is retryable. The moment you need fields, reach for a typed error.

**On the job:** `ErrInsufficientFunds` is the right tool when Meridian's handler only needs to know *that* the funds were short — not by how much. When the SRE on-call needs to know account, balance, and shortfall in the log, you need a typed error.

### Typed errors

A typed error is a struct that implements the `error` interface:

```go
// payments/errors.go — Meridian domain layer
type InsufficientFundsError struct {
    AccountID string
    Available int // cents
    Requested int // cents
}

func (e *InsufficientFundsError) Error() string {
    return fmt.Sprintf(
        "insufficient funds on account %s: have %d cents, need %d",
        e.AccountID, e.Available, e.Requested,
    )
}
```

Callers use `errors.As` (or the Go 1.26 `errors.AsType[T]`) to extract the value and read its fields:

```go
var fundsErr *InsufficientFundsError
if errors.As(err, &fundsErr) {
    log.Info("payment declined",
        "account", fundsErr.AccountID,
        "shortfall_cents", fundsErr.Requested-fundsErr.Available,
    )
    return http.StatusPaymentRequired
}
```

### When to use which

<ConceptGrid cols={2}>
  <ConceptCard label="Use sentinels when">The error is a condition, not data. `io.EOF`, `sql.ErrNoRows`, `ErrNotFound`. The caller only needs to know *which* condition occurred, not the details.</ConceptCard>
  <ConceptCard label="Use typed errors when">The caller needs data to act: amounts, IDs, codes, retry hints. Typed errors are especially valuable at package boundaries where internal types shouldn't leak.</ConceptCard>
  <Gotcha>Define errors in the package that *owns* the concept, not the one that *produces* them. `payments.ErrInsufficientFunds` lives in the payments package; every layer above imports it from there. Scattering error definitions across layers creates import cycles and muddy ownership.</Gotcha>
  <ConceptCard label="Combining both">A sentinel and a typed error are not exclusive. You can define both `ErrInsufficientFunds` and `InsufficientFundsError`, where the typed error's `Is` method compares against the sentinel — letting callers use `errors.Is` for simple checks and `errors.As` for rich ones.</ConceptCard>
</ConceptGrid>

```go
package main

import (
	"errors"
	"fmt"
)

// Sentinel — fast identity check.
var ErrInsufficientFunds = errors.New("insufficient funds")

// Typed error — rich data for the layers that need it.
type InsufficientFundsError struct {
	AccountID string
	Available int
	Requested int
}

func (e *InsufficientFundsError) Error() string {
	return fmt.Sprintf(
		"account %s: need %d cents, have %d",
		e.AccountID, e.Requested, e.Available,
	)
}

// Is makes errors.Is(err, ErrInsufficientFunds) work even for the typed error.
func (e *InsufficientFundsError) Is(target error) bool {
	return target == ErrInsufficientFunds
}

func debit(accountID string, available, requested int) error {
	if requested > available {
		return &InsufficientFundsError{
			AccountID: accountID,
			Available: available,
			Requested: requested,
		}
	}
	return nil
}

func main() {
	err := debit("acc_42", 5000, 9999)

	// Simple check — sentinel identity via the Is method.
	fmt.Println("is insufficient funds?", errors.Is(err, ErrInsufficientFunds))

	// Rich check — typed extraction.
	var fundsErr *InsufficientFundsError
	if errors.As(err, &fundsErr) {
		shortfall := fundsErr.Requested - fundsErr.Available
		fmt.Printf("account %s is short by %d cents\n", fundsErr.AccountID, shortfall)
	}
}
```

## When to panic

Short answer: almost never. Especially not in a library.

A panic tears through the call stack, unwinding frames and running deferred functions, until something calls `recover` — or until the program crashes. In a web server, an unrecovered panic in one goroutine kills the *entire process*, taking every other request with it. That is not graceful; that is a crater.

Here are the legitimate uses, stated precisely:

<ConceptGrid cols={2}>
  <ConceptCard label="Programmer errors — init time">Broken invariants that no caller can recover from: a nil required argument, an impossible enum value in a `switch`, an invalid regex that was hardcoded in the binary. Panic at `init()` or in a constructor — the error must be caught in development, not shipped.</ConceptCard>
  <ConceptCard label="Genuinely unrecoverable state">Corrupted memory, a broken runtime invariant. These are rare to the point of theoretical. If you're reaching for panic because something is "unexpected," you're probably wrong — return an error.</ConceptCard>
  <ConceptCard label="Goroutine boundaries">A goroutine that panics kills the program if nothing recovers it. Libraries that spawn goroutines must install a `recover()` at the top of each — otherwise a bug in the goroutine body takes down the caller's whole process. This is the subject of the next section.</ConceptCard>
  <ConceptCard label="Never in a library">A library panicking forces the application to install a recovery layer around every call. That is an unreasonable contract. Return an error. Every time. No exceptions.</ConceptCard>
  <Gotcha>The `recover()` built-in only works when called *directly* inside a deferred function in the **same goroutine** that panicked. `defer func() { recover() }()` works. A `recover()` in a parent goroutine cannot catch a panic in a goroutine it spawned — the spawned goroutine's panic is separate and will crash the process if unrecovered.</Gotcha>
</ConceptGrid>

### `recover` in middleware

The one pattern where `recover` shines is a top-level HTTP middleware that converts unexpected panics into 500 responses, so a bug in a single handler doesn't crater the server:

```go
// middleware/recovery.go
func RecoveryMiddleware(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        defer func() {
            if rec := recover(); rec != nil {
                // Log the stack trace for debugging.
                buf := make([]byte, 4096)
                n := runtime.Stack(buf, false)
                slog.Error("panic recovered",
                    "panic", rec,
                    "stack", string(buf[:n]),
                    "path", r.URL.Path,
                )
                http.Error(w, "internal server error", http.StatusInternalServerError)
            }
        }()
        next.ServeHTTP(w, r)
    })
}
```

```go
package main

import (
	"fmt"
	"runtime"
)

// safeCall runs fn and converts any panic into a returned error.
// This is the pattern for wrapping third-party code you don't trust.
func safeCall(fn func() error) (err error) {
	defer func() {
		if rec := recover(); rec != nil {
			buf := make([]byte, 1024)
			n := runtime.Stack(buf, false)
			err = fmt.Errorf("recovered panic: %v\n%s", rec, buf[:n])
		}
	}()
	return fn()
}

func riskyOperation(val int) error {
	if val == 0 {
		panic("division by zero — this should have been an error return")
	}
	fmt.Println("result:", 100/val)
	return nil
}

func main() {
	// Safe call — no panic.
	if err := safeCall(func() error { return riskyOperation(5) }); err != nil {
		fmt.Println("error:", err)
	}

	// Panic recovered — becomes a normal error.
	if err := safeCall(func() error { return riskyOperation(0) }); err != nil {
		fmt.Println("recovered:", err)
	}

	fmt.Println("program continues normally after recovery")
}
```

## Structured error responses for services

An HTTP API is a contract. The client trusts you to tell them what went wrong clearly enough to act on it — without exposing your internal implementation to the world.

The pattern: every error response has a consistent JSON envelope, and internal errors are mapped to status codes + error codes at the handler layer. Nothing internal leaks.

```go
// api/errors.go — Meridian API layer

// APIError is the JSON envelope every error response uses.
type APIError struct {
    Code    string `json:"code"`
    Message string `json:"message"`
}

// errorCode maps internal domain errors to API codes.
// Only the handler layer knows about this mapping.
func errorCode(err error) (int, APIError) {
    switch {
    case errors.Is(err, payments.ErrInsufficientFunds):
        return http.StatusPaymentRequired, APIError{
            Code:    "insufficient_funds",
            Message: "Your account has insufficient funds for this transaction.",
        }
    case errors.Is(err, payments.ErrCardExpired):
        return http.StatusPaymentRequired, APIError{
            Code:    "card_expired",
```

## The typed-nil trap

This is the one. The bug that has humiliated more Go engineers than any other. The one where `err != nil` *lies to your face*.

Let me set the scene.

You have a database repository layer in Meridian's account service. The function returns an `error` interface — sensible. You define a concrete error type `*DBError` for structured database errors. On the happy path, you return `nil`. Or so you think.

```go
// BROKEN — this is the trap
func findAccount(id string) *DBError {
    // on success — we return nil, right?
    return nil
}

func callFindAccount(id string) error {
    return findAccount(id) // THE BUG IS HERE
}
```

You call `callFindAccount`, check `err != nil`, and it's `true`. Even though `findAccount` returned `nil`. How?

The answer is in the interface representation.

<UnderTheHood title="The interface's (type, value) word — why the nil check lies (Go 1.26)">

Every interface value in Go is secretly a **two-word structure**:

```
┌───────────────────────────────────┐
│  word 1: type pointer (itable)    │  → points to the concrete type's method table
│  word 2: data pointer             │  → points to the concrete value (or is nil)
└───────────────────────────────────┘
```

An interface is `nil` (in the Go sense, the one `err != nil` checks) **only when BOTH words are nil** — when the interface holds no type information at all.

When you write `return findAccount(id)` inside a function that returns `error`, Go must convert the `*DBError` return value to the `error` interface. It does this by filling in word 1 with the type pointer for `*DBError`.

So even though `findAccount` returned a nil `*DBError` pointer (word 2 is nil), **word 1 is NOT nil** — it points to `*DBError`'s method table. The interface now holds:

```
word 1: → *DBError itable   (non-nil — type is known)
word 2: nil                 (no value)
```

`err != nil` checks "is this interface zero?" — and it isn't. The type word is set. The check returns true, even though there is nothing useful inside.

As of Go 1.26, `go vet` with the `nilness` analyzer catches more instances of this pattern than earlier versions, but it cannot catch every case — the fix is always structural: return a bare `nil`, not a typed nil pointer.

*This is a simplification of the actual iface/eface layout — the runtime distinguishes interface-with-methods from empty interfaces, and may use pointer tagging in some cases. The key point — both words must be zero for `== nil` to be true — holds in all Go versions.*

</UnderTheHood>

## The goroutine-panic footgun

Here is the single rule that takes down more Go production services than data races: **an unrecovered panic in ANY goroutine crashes the WHOLE process**. No exceptions. No isolation. Every in-flight request on that instance dies with it.

And here is the part that trips up everyone who knows about `recover`: **`recover` only works inside a `defer` in the SAME goroutine that panicked**. A parent goroutine cannot catch a panic from a goroutine it spawned. The spawned goroutine's panic propagates independently, and if nothing in *that* goroutine catches it, the runtime calls `os.Exit(2)`.

**On the job:** One panic in a background worker — a settlement reconciler, a webhook dispatcher, a metrics flusher — takes down every in-flight Meridian request on that instance. No warning. All transfers in progress get a connection reset. The client retries. Depending on your idempotency story, you may or may not be in trouble.

### Why the parent cannot catch it

This is the canonical trap:

```go
func main() {
    defer func() {
        if r := recover(); r != nil {
            fmt.Println("caught:", r) // THIS NEVER RUNS
        }
    }()

    go func() {
        panic("spawned goroutine panics") // crashes the process
    }()

    time.Sleep(time.Second) // waiting won't help
}
```

The `defer`/`recover` in `main` is installed in `main`'s goroutine stack. The spawned goroutine has its own stack. When it panics, the runtime unwinds *its* stack — `main`'s stack is never touched. The process dies.

### The fix: recover-per-goroutine

Every long-lived or per-request goroutine you spawn needs its own deferred recovery. The idiomatic wrapper:

```go
// safeGo launches fn in a goroutine with a deferred recover.
// If fn panics, the error is sent to the provided channel instead of crashing.
func safeGo(errCh chan<- error, fn func()) {
    go func() {
        defer func() {
            if r := recover(); r != nil {
                buf := make([]byte, 4096)
                n := runtime.Stack(buf, false)
                errCh <- fmt.Errorf("goroutine panic: %v\n%s", r, buf[:n])
            }
        }()
        fn()
    }()
}
```

For Meridian's background workers (settlement reconciler, webhook dispatcher, ledger compactor), the wrapper looks like this:

```go
// worker/reconciler.go
func (w *ReconcilerWorker) Start(ctx context.Context) {
    go func() {
        defer func() {
            if r := recover(); r != nil {
                buf := make([]byte, 4096)
                n := runtime.Stack(buf, false)
                slog.Error("reconciler panic — restarting",
                    "panic", r,
                    "stack", string(buf[:n]),
                )
                // Optionally: signal a supervisor to restart the worker.
            }
        }()
        w.run(ctx)
    }()
}
```

### When NOT to recover

Recovery is not always the right answer. Some panics signal truly unrecoverable state — a corrupted data structure, a broken internal invariant, an out-of-memory condition. Recovering from those and continuing means operating on bad state, which is often worse than a clean crash-and-restart.

The rule of thumb:

- **Recover** from panics in request handlers and per-goroutine workers where the panic is isolated and the rest of the system is fine.
- **Do NOT recover** from panics that indicate corrupted shared state. Let the process crash, let the supervisor restart it, and let the monitoring page wake someone up.

```go
		return 401
	default:
		return 500
	}
}

func main() {
	cases := []struct {
		label string
		err   error
	}{
		{"direct not found", ErrNotFound},
		{"wrapped not found", fmt.Errorf("repo.FindAccount: %w", ErrNotFound)},
		{"double-wrapped unauth", fmt.Errorf("handler: %w", fmt.Errorf("auth: %w", ErrUnauthorized))},
		{"unknown error", errors.New("some internal failure")},
	}

	for _, c := range cases {
		fmt.Printf("%-38s → %d\n", c.label, statusCode(c.err))
	}
}
```

`errors.Is` walks all wrapping layers, so `statusCode` returns the correct code regardless of how many layers deep the sentinel is buried.

</Solution>

</Exercise>

```go
		return &RecordError{Msg: "id required"}
```

<Exercise n={5} title="Build a payments error pipeline" level="hard">

Build a complete mini payments pipeline: a `dbLayer` that can return a `*DBError` (with a `Code string` field), a `serviceLayer` that wraps errors with context, and an `apiLayer` that maps `DBError` with code `"NOT_FOUND"` to HTTP 404, code `"DUPLICATE"` to HTTP 409, and anything else to 500. Use `errors.As` to extract the `*DBError` in `apiLayer`. Demonstrate all three cases in `main`.

<Solution>

```go
package main

import (
	"errors"
	"fmt"
)

// Domain error type.
type DBError struct {
	Code    string
	Message string
}

func (e *DBError) Error() string {
	return fmt.Sprintf("db[%s]: %s", e.Code, e.Message)
}

// dbLayer — returns error (not *DBError — never the concrete type).
func dbLayer(code string) error {
	if code != "" {
		return &DBError{Code: code, Message: "simulated db failure"}
	}
	return nil
}

// serviceLayer — wraps with context.
func serviceLayer(code string) error {
	if err := dbLayer(code); err != nil {
		return fmt.Errorf("service.processTransfer: %w", err)
	}
	return nil
}

// apiLayer — maps to HTTP status codes.
func apiLayer(code string) int {
	err := serviceLayer(code)
	if err == nil {
		return 200
	}
	var dbErr *DBError
	if errors.As(err, &dbErr) {
		switch dbErr.Code {
		case "NOT_FOUND":
			return 404
		case "DUPLICATE":
			return 409
		}
	}
	return 500
}

func main() {
	fmt.Println("success:  ", apiLayer(""))            // 200
	fmt.Println("not found:", apiLayer("NOT_FOUND"))   // 404
	fmt.Println("duplicate:", apiLayer("DUPLICATE"))   // 409
	fmt.Println("unknown:  ", apiLayer("CONSTRAINT"))  // 500
}
```

`errors.As` walks the full chain from `apiLayer` through `serviceLayer`'s `%w` wrapper straight to the `*DBError`, extracting its `Code` field. The return type of `dbLayer` is `error` (never `*DBError`) — otherwise you'd have planted a typed-nil trap.

</Solution>

</Exercise>

<Recap>

- **Errors are values** — the `error` interface is `Error() string`. Return `nil` for success, an error value for failure. Handle or propagate — never both for the same error.
- **`%w` wraps, `%v` doesn't** — `fmt.Errorf("context: %w", err)` builds a linked chain. `errors.Unwrap` walks it link by link. (Go 1.26 made the *no-verb* `fmt.Errorf("plain message")` allocate as cheaply as `errors.New`; the `%w` path is unchanged.)
- **`errors.Is`** compares by identity down the chain — use for sentinels. **`errors.As`** matches by type and extracts the concrete value — use when you need fields. **`errors.AsType[T]`** (Go 1.26) is the generic, type-safe form of `errors.As`.
- **Sentinels** (`errors.New`) for conditions; **typed errors** (structs implementing `error`) for data. Define errors in the package that owns the concept. Combine both with a custom `Is` method.
- **Panic almost never** — not in libraries, not for expected failures. Use `recover` in goroutine-boundary middleware only. Return an error. Every time.
- **Structure your HTTP errors** — map internals to opaque codes at the handler layer. Never leak internal error text to clients. Log the full chain on your side.
- **The typed-nil trap** — an `error` interface is nil only when BOTH its type word and data word are zero. Returning a nil concrete pointer from a function that returns `error` sets the type word and makes `err != nil` lie. **Fix: always return `error`, never a concrete pointer type, from functions whose callers will check `err != nil`.**
- **The goroutine-panic footgun** — an unrecovered panic in ANY goroutine crashes the WHOLE process. `recover` only works in the same goroutine — a parent cannot catch a spawned goroutine's panic. Every long-lived or per-request goroutine needs its own deferred recover. Install HTTP panic-recovery middleware. When state is truly corrupted, let the process crash rather than continuing on bad state.

</Recap>
