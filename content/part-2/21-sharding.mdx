<HeroCard label="Part 2 · Chapter 21" title="Sharding: Splitting Data Across Machines">

Replication (chapter 20) copies all the data to every machine. That helps reads and survives failures, but every copy still holds everything and every write still goes everywhere. When the data, or the writes, outgrow one machine, you **shard**: split the data into pieces and give each machine some of them.

The cinema's seats live in Redis. This chapter runs them on a **Redis Cluster**, a real sharded store: 16,384 hash slots divided among the masters, clients that route each key to its node, and resharding while the service runs. The cinema's own store code meets it unchanged, and immediately breaks: its seat map reads 40 keys in one command, and those 40 keys are now on three machines. Fixing that is a choice about what to keep together, and every choice has a cost that shows up under load.

Six stops. If you get lost, come back here:

1. **Keys to slots to nodes.** How a key finds its machine, and what happens when a client asks the wrong one.
2. **Keep a film together.** The seat map breaks across shards; hash tags fix it.
3. **Hot spots.** Opening night, and what co-location does to the load.
4. **Rebalancing.** Add a machine under load: how much data moves, and what fails.
5. **Modulo versus slots.** Why `hash % N` is the wrong way to place keys.
6. **Indexes across shards.** "All of Alice's holds" when her holds are everywhere.

## The lab bench

Four Redis 8.10 containers in cluster mode on a Docker network; three form the cluster at first, and the fourth joins in stop 4. Container addresses aren't reachable from the macOS host, so the experiments (`shardlab`, in the cinema module) are cross-compiled for Linux and run in a container on the same network. The cinema's Redis store gets two changes: it accepts `redis.UniversalClient` (a single server *or* a cluster client), and an optional `HashTag` setting.

## Keys to Slots

*Stop 1 of 6.*

### Step 1: 16,384 slots

A Redis Cluster doesn't assign keys to nodes directly. Every key belongs to one of **16,384 hash slots**: CRC16 of the key, modulo 16384. Each master owns ranges of slots. Creating a three-master cluster splits them evenly:

```text
M: 172.21.0.2:6379   slots:[0-5460] (5461 slots) master
M: 172.21.0.3:6379   slots:[5461-10922] (5462 slots) master
M: 172.21.0.4:6379   slots:[10923-16383] (5461 slots) master
[OK] All 16384 slots covered.
```

### Step 2: asking the wrong node

```text
$ redis-cli -h rc1 CLUSTER KEYSLOT seat:inception:A7
7008
$ redis-cli -h rc1 SET seat:inception:A7 held:alice        # without -c: not cluster-aware
MOVED 7008 172.21.0.3:6379

$ redis-cli -c -h rc1 SET seat:inception:A7 held:alice     # -c follows redirects
OK
```

`seat:inception:A7` is in slot 7008, which the second master owns. Sent to the first, the command isn't forwarded: the node answers **MOVED 7008 172.21.0.3:6379**, telling the client where the slot lives. A cluster-aware client (`redis-cli -c`, or go-redis's `ClusterClient`) follows the redirect, and remembers the slot map so its next request for slot 7008 goes straight there. Routing is the client's job; the nodes only say "not here, there".

## Keep a Film Together

*Stop 2 of 6.*

### Step 1: the seat map breaks

The cinema's store, unchanged, on the cluster:

```text
$ shardlab crossslot     # the cinema's Redis store, on a 3-master Redis Cluster
== HashTag=false
  seat:inception:A1      slot 15270
  seat:inception:A7      slot  7008
  seat:inception:C3      slot 15750
  Hold(A7): <nil>
  Seats(inception): 0 seats, err: CROSSSLOT Keys in request don't hash to the same slot
== HashTag=true
  seat:{inception}:A1    slot  6229
  seat:{inception}:A7    slot  6229
  seat:{inception}:C3    slot  6229
  Hold(A7): <nil>
  Seats(inception): 40 seats, err: <nil>
```

With plain keys, `Hold(A7)` works (one key, one slot), and **the seat map fails with CROSSSLOT**: A1 is in slot 15270, A7 in 7008, C3 in 15750, and an `MGET` must run on one node, atomically. The service's most frequent request, broken by the change of deployment alone.

### Step 2: hash tags

Redis's answer is the **hash tag**: if a key contains `{…}`, only the part inside the braces is hashed. `seat:{inception}:A7` hashes `inception`, so every seat of the film lands in slot 6229, on one node, and `MGET` works again (the second half of the output above). The store keeps both spellings behind a setting:

```go noverify
// redisstore.go, lines 37–47
func seatKey(movie, seat string) string { return "seat:" + movie + ":" + seat }

// key names a seat. With HashTag, the film's name is the key's hash tag
// ("seat:{inception}:A7"), so on a Redis Cluster all of a film's seats are
// in one hash slot: one node, and multi-key commands (MGET) work.
func (s *Store) key(movie, seat string) string {
	if s.HashTag {
		return "seat:{" + movie + "}:" + seat
	}
	return seatKey(movie, seat)
}
```

Changing the key format of a running service is a **migration**: existing holds under the old names are invisible under the new ones. For holds that expire within minutes you can switch at a quiet moment; for durable data you'd dual-read (new name, then old) until the old keys are gone.

### Step 3: or read across shards

The alternative is to leave the keys spread and read them with one `GET` per seat. go-redis's cluster client splits a **pipeline** by node, so it's one round trip per node rather than per key:

```go noverify
// redisstore.go, lines 105–129
// mget reads keys in one round trip per node: one MGET when they share a
// slot (one server, or hash-tagged keys on a cluster), otherwise a
// pipeline of GETs, which the cluster client splits by node.
func (s *Store) mget(ctx context.Context, keys []string) ([]any, error) {
	if _, cluster := s.rdb.(*redis.ClusterClient); !cluster || s.HashTag {
		return s.rdb.MGet(ctx, keys...).Result()
	}
	cmds := make([]*redis.StringCmd, len(keys))
	_, err := s.rdb.Pipelined(ctx, func(p redis.Pipeliner) error {
		for i, k := range keys {
			cmds[i] = p.Get(ctx, k)
		}
		return nil
	})
	if err != nil && !errors.Is(err, redis.Nil) {
		return nil, err
	}
	vals := make([]any, len(keys))
	for i, c := range cmds {
		if v, err := c.Result(); err == nil {
			vals[i] = v
		}
	}
	return vals, nil
}
```

Both now work. Which is better is stop 3's question.

## Hot Spots

*Stop 3 of 6.*

### Step 1: opening night

On opening night almost everyone wants the same film. `shardlab load` runs 32 workers fetching seat maps for 5 seconds, 90% for *inception* and 10% for *dune*, and counts the commands each master processed:

```text
$ shardlab load -tag=false -for 5s     # 32 workers; 90% of seat maps are for inception
HashTag=false: 114040 seat maps in 5s (0 errors), p50 884µs, p99 7.533ms
  172.21.0.2:6379    slots 0-5460         1209226 commands   27.6%  ███████████
  172.21.0.3:6379    slots 5461-10922     1540020 commands   35.2%  ██████████████
  172.21.0.4:6379    slots 10923-16383    1631409 commands   37.2%  ██████████████
$ shardlab load -tag=true -for 5s     # 32 workers; 90% of seat maps are for inception
HashTag=true: 502616 seat maps in 5s (0 errors), p50 206µs, p99 1.942ms
  172.21.0.2:6379    slots 0-5460               1 commands    0.0%  
  172.21.0.3:6379    slots 5461-10922      452197 commands   89.9%  ███████████████████████████████████
  172.21.0.4:6379    slots 10923-16383      50603 commands   10.1%  ████
```

**Spread keys** (no tag): the load is shared by all three masters (28%, 35%, 37%), but each seat map is 40 `GET`s over three nodes: about 38 commands per seat map, 114,040 seat maps in 5 s, p99 7.5 ms.

**Hash-tagged**: each seat map is one `MGET` to one node. **4.4 times the throughput** (502,616 seat maps), p50 206 µs, p99 1.9 ms. And **90% of the load on one master**, 10% on another, and the third doing nothing: *inception*'s slot is on one node, *dune*'s on another, and there's no third film.

### Step 2: what a hot spot means

Co-location made each request cheaper and the cluster lopsided. Today the hot node copes, because one MGET is so cheap. But the cluster's capacity for *inception* is now one node's capacity, and adding masters won't help, because the film is one slot and a slot can't be split. That's the fundamental sharding trade-off: **keys you keep together for atomicity or efficiency are keys you can't spread for load**. The usual remedies:

- **Choose the partition key for your hottest access pattern.** The cinema reads whole seat maps constantly: per-film co-location is right, and a film's 40 seats are small.
- **Split a hot key further** when one partition outgrows a node: per-film-per-showing (`seat:{inception:2026-09-27T20:00}:A7`) spreads a film's showings across slots while keeping each hall together.
- **Replicate hot partitions for reads**: a Redis Cluster master can have replicas, and read-only commands can go to them (with chapter 20's lag).

## Rebalancing

*Stop 4 of 6.*

### Step 1: add a node under load

`reshard.sh` writes 10,000 booking keys, starts `shardlab churn` (16 workers holding seats and reading seat maps, both films, for 30 s), adds a fourth master while that runs, and rebalances:

```text
   1 Moving 1365 slots from 172.21.0.4:6379 to 172.21.0.5:6379
   1 Moving 1366 slots from 172.21.0.3:6379 to 172.21.0.5:6379
rebalance took 3.1 s

  172.21.0.2:6379     2502 booking keys
  172.21.0.3:6379     2524 booking keys
  172.21.0.4:6379     2500 booking keys

  mod-N placement (slot % N): going from 3 to 4 nodes would move 7508 of 10000 keys (75%)
```

The rebalance moved **1,365–1,366 slots from each master** to the new one, in 3.1 s, and afterwards each master holds about 2,500 of the 10,000 keys. Only the keys in the moved slots traveled: **2,474 of 10,000 (25%)**, the minimum possible for going from three nodes to four.

### Step 2: what the clients saw

Of about 574,700 rounds of holds and seat maps, **94 failed**, all with `CLUSTERDOWN The cluster is down`, clustered in the moments when the new node joined and the slot configuration changed. Everything else went through: while a slot migrates, a node answers requests for keys already moved with **ASK** (a one-time redirect, "this key is over there for now"), and go-redis follows it. Resharding is online, but not invisible: clients need retries for transient cluster errors, like chapter 12's retries for a slow Redis.

## Modulo versus Slots

*Stop 5 of 6.*

### Step 1: the obvious scheme

Why the indirection through 16,384 slots? The obvious scheme is **`hash(key) % N`**: node number = hash modulo the number of nodes. `shardlab where` computes, for the same 10,000 keys, how many would change node if placement were `slot % N` and N went from 3 to 4 (the last line of each part of the output above):

```text
mod-N placement (slot % N): going from 3 to 4 nodes would move 7508 of 10000 keys (75%)
```

**75%**, against the 25% the cluster actually moved. With modulo, changing N changes almost every key's remainder, so adding one machine reshuffles nearly all the data, all at once, while you're adding the machine because you're short of capacity. Going from 10 nodes to 11 would move about 91%.

### Step 2: the fix, two ways

Both widely used fixes keep most keys in place when nodes come and go:

- **Fixed slots** (Redis Cluster, Elasticsearch shards, Couchbase vBuckets): hash keys into a fixed, large number of slots that never changes, and move *slots* between nodes. Adding a node takes a fair share of slots from the others.
- **Consistent hashing** (Dynamo, Cassandra's token ring): place nodes and keys on the same hash ring; each key belongs to the next node clockwise. Adding a node takes over only the arc before it; virtual nodes (many points per node) keep the arcs even.

## Indexes Across Shards

*Stop 6 of 6.*

### Step 1: "all of Alice's holds"

The seats are partitioned by film. A customer page needs the reverse: every seat *Alice* holds, across all films. Two designs:

- A **local index**, one per partition: `holds:{inception}:alice`, a set on the same shard as the film's seats. Updating it with the hold is atomic. Answering "all Alice's holds" means asking every film's partition: a **scatter-gather** query to every shard, as slow as the slowest shard.
- A **global index**, partitioned by customer: `holds:{alice}`, one set on whichever shard Alice's slot is on. Answering is one read. But is updating it atomic with the hold?

```text
$ shardlab index
MULTI SET seat:{inception}:A7 (slot 6229) + SADD holds:{alice} (slot 749): CROSSSLOT Keys in request don't hash to the same slot
MULTI SET seat:{inception}:A7 (slot 6229) + SADD holds:{inception}:alice (slot 6229): <nil>
```

It isn't. `seat:{inception}:A7` is in slot 6229, `holds:{alice}` in slot 749, and a `MULTI` across slots fails with **CROSSSLOT**. The local index, tagged by film, commits with the hold.

### Step 2: living with a global index

A global index updated separately is **eventually consistent** with the data: hold the seat, then add it to the index, and between the two (or if the second fails) the index is wrong. Systems that offer global secondary indexes (DynamoDB's GSIs, Cassandra's materialized views) update them asynchronously and say so. The cinema's options: the local index plus scatter-gather (two films today: cheap), or a global index written after the hold, with the seat data as the source of truth and a periodic repair. What doesn't exist, on a sharded store, is "both, atomically, for free".

For each access pattern, pick the partition key (hash tag) for the cinema's data and say what it costs: (a) the seat map of one showing; (b) a customer's booking history; (c) nightly sales per film; (d) a customer's loyalty points balance, updated with every booking.

<Solution>

(a) **The showing** (`{inception:2026-09-27T20:00}`): one MGET, atomic holds within the hall; a hot showing is one slot. (c) Not a key lookup at all: aggregate from bookings asynchronously (a job or a stream into a warehouse). (d) **The customer**: the balance must change atomically, but with the booking in another slot you need an idempotent follow-up write (chapter 13's queue) rather than one transaction.

</Solution>

</Exercise>

<Exercise n={2} title="Split the hot film" level="medium">

Change the hash tag to include the showing time and rerun `shardlab load -tag=true` with six showings of *inception*. How does the per-node distribution change, and what does it cost?

<Solution>

Six showings are six slots, which land on different masters (by their hash), so the 90% spreads across nodes roughly in proportion to how the six slots fall: with three masters, likely all three get some. Each seat map is still one MGET. The cost: anything that spans showings (a film's total occupancy, "all inception seats Alice holds") becomes a multi-slot operation, handled by scatter-gather or a separate aggregate.

</Solution>

</Exercise>

<Exercise n={3} title="Replicas for the hot shard" level="medium">

Add a replica to each master (`redis-cli --cluster add-node … --cluster-slave`) and set go-redis's `ReadOnly: true` and `RouteRandomly: true`. What happens to the hot master's load, and what new problem does it bring?

<Solution>

Read-only commands (the seat map's MGET) can go to the replicas, so the hot slot's reads are shared by the master and its replica: the hot node's load roughly halves. The new problem is chapter 20's: replica reads are asynchronous, so a customer who just held a seat may read a seat map (from the replica) without their hold. The cinema would read its own holds from the master, or accept a moment of staleness for the public map.

</Solution>

</Exercise>

<Exercise n={4} title="Measure consistent hashing" level="medium">

Write a consistent-hash ring with 100 virtual nodes per server and place the 10,000 booking keys on 3 servers, then 4. How many keys move? How even is the load with 1, 10 and 100 virtual nodes per server?

<Solution>

With a ring, adding the fourth server moves only the keys on the arcs it takes over: close to 25%, like the slots. With **one** point per server, the arcs are uneven, so one server can own far more than a third (tens of percent off); with 10 points the imbalance shrinks, and with 100 it's within a few percent. Virtual nodes are to a ring what many small slots are to Redis Cluster: fine-grained units that can be divided evenly.

</Solution>

</Exercise>

<Exercise n={5} title="A resharding-safe client" level="hard">

`churn` saw 94 CLUSTERDOWN errors while the fourth node joined. Wrap the cinema's store calls so that transient cluster errors (CLUSTERDOWN, TRYAGAIN, a connection reset during failover) are retried, and prove with `reshard.sh` that no customer request fails. What must not be retried blindly?

<Solution>

Retry with backoff and jitter (chapter 12) on errors whose message starts with CLUSTERDOWN or TRYAGAIN and on network errors, within the request's deadline; go-redis already follows MOVED and ASK. Rerunning `reshard.sh` should show 0 failures. What must not be retried blindly: `Hold` after an ambiguous failure (the SET NX may have applied, as chapter 12 measured), so use the idempotent Hold that recognises its own earlier success, and never retry business answers like "seat taken".

<Recap>

- **Slots**: Redis Cluster hashes each key (CRC16) into one of 16,384 slots and gives each master ranges of slots. A node asked about someone else's slot answers MOVED; cluster-aware clients follow and remember.
- **Multi-key operations** must stay within one slot: the cinema's seat-map MGET failed with CROSSSLOT until **hash tags** (`seat:{inception}:A7`) put a film's seats in one slot (6229). Changing key names on a live system is a migration.
- **Co-location vs balance**: tagged seat maps were one MGET each, **4.4x** the throughput (502,616 vs 114,040 in 5 s), p99 1.9 ms vs 7.5 ms, and put **90%** of the load on one master on opening night. A slot can't be split; split the key design instead.
- **Rebalancing** a fourth master in under load moved **25%** of keys (only the slots that changed owner) in 3.1 s; 94 of about 574,700 client operations saw `CLUSTERDOWN` while it joined. Modulo placement would have moved **75%**.
- **Global indexes** span shards: writing the hold and `holds:{alice}` atomically failed with CROSSSLOT; a film-local index commits with the hold but needs scatter-gather to answer per-customer queries.

</Recap>
