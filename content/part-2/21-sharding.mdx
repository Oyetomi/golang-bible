<HeroCard label="Part 2 · Chapter 20" title="Sharding: Splitting Data Across Machines">

Last chapter you kept **copies** of Meridian's data on several machines — replication. That solves "what if a machine dies." It does *nothing* for a different problem: what if the data is simply **too big for any one machine**, or the writes come in faster than one machine can absorb them? You can copy a 50-terabyte database onto ten machines all day; every copy is still 50 terabytes. Copies don't shrink anything.

So you do the other thing: you **split** the data. Machine A holds some accounts, machine B holds others, machine C the rest. No machine holds all of it. That's **sharding** (also called partitioning), and I'm going to teach it to you from absolute zero — no assumed knowledge of databases, hashing, or any of the vocabulary people use to sound clever. By the end you'll know exactly how a request finds the one machine holding *your* account out of a thousand, why a single celebrity can melt one shard while nine others nap, and the little trick that lets you add a machine without shuffling the entire dataset across the network. We shard Meridian's ledger the whole way. Let's go.

</HeroCard>

## Why Shard

Let's pin the word down before anything else.

<Define term="Sharding (partitioning)" since="Sharding (Part 2)">
**Sharding** means splitting one dataset into smaller pieces called **shards** (or **partitions**), and storing different shards on different machines, so that each record lives in exactly **one** shard. Why it matters: replication copies the *whole* dataset onto each machine — great for surviving failures, useless when the dataset itself is too big. Sharding is how a system grows past what a single machine can hold or how fast it can write, by spreading the load across many machines that each handle a slice.
</Define>

The two techniques are easy to confuse, so hold them apart:

<ConceptGrid cols={3}>
  <ConceptCard label="Replication = copies">Every machine holds the *same* data. Buys you availability (survive a dead machine) and read-scaling (spread reads over copies). Does not reduce how much data each machine stores.</ConceptCard>
  <ConceptCard label="Sharding = splits">Every machine holds a *different slice*. Buys you size and write-throughput — ten machines hold ten times the data and absorb ten times the writes. Does not, by itself, survive a machine dying.</ConceptCard>
  <Gotcha>⚠ Use both. A shard with no replica is a single point of failure for *that slice*. Production = sharded **and** each shard replicated (a leader + followers, like last chapter). They're independent choices.</Gotcha>
</ConceptGrid>

The whole game rests on one decision: how do you decide which record goes in which shard? You pick a **partition key**.

<Define term="Partition key" since="Sharding (Part 2)">
The **partition key** is the field whose value decides a record's shard. All records sharing a partition key land in the same shard. For Meridian's ledger the natural key is the **account ID** — every transaction for an account lives with that account. Why it matters: if a request knows the partition key, it goes straight to the one shard that can answer — fast. If it *doesn't* know the key (e.g. "find every transaction over ₦10,000"), it has to ask *every* shard and combine the answers — slow. Choosing the partition key is the most consequential and hardest-to-undo decision in a sharded system.
</Define>

<Callout kind="warn" title="Don't shard until you have to">

Sharding is a heavyweight solution. A single modern machine holds a *lot* and commits a *lot* of writes — often more than you think. Sharding adds permanent complexity: cross-shard queries are slow, a write that touches two accounts on two shards needs a **distributed transaction** (Chapter 23's territory, and far slower than a single-machine one), and the sharding scheme is painful to change later. The senior move is to stay on one (replicated) machine as long as it copes, and reach for sharding only when data volume or write throughput genuinely outgrow it. Meridian shards the ledger because it's at hundreds of millions of accounts — not because sharding is fashionable.

</Callout>

## Key-Range

The first way to split: hand each shard a **contiguous range** of keys, sorted. Think of a printed encyclopedia — volume 1 is *A–B*, volume 7 is *M–N*, volume 12 is *T–Z*. To find "Meridian," you reach straight for the *M–N* volume. No searching the others.

<Define term="Key-range sharding" since="Sharding (Part 2)">
**Key-range sharding** assigns each shard a sorted, contiguous range of partition keys — shard 0 owns keys `aardvark`…`carrot`, shard 1 owns `carter`…`forest`, and so on. Within a shard, keys stay **sorted**. Why it matters: sorting makes **range scans** cheap — "every transaction for account 7 in March" is one sweep of one shard, because those rows sit next to each other. The catch (next paragraph) is that sorted ranges invite **hot spots**.
</Define>

The boundaries can't be evenly spaced by *letter* — far more words start with *S* than *X*, so an even split has to give *X–Z* a wide range and *S* a narrow one. **The boundaries adapt to the data, not the alphabet.** Same with Meridian: if account IDs cluster, the ranges must too.

The benefit is real — sorted keys give you free range queries:

The downside is the flip side of the same coin. If writes cluster on **nearby keys**, they all hit the **same shard** while the others idle:

<Callout kind="warn" title="The classic hot-shard trap: a timestamp partition key">

Say you shard by *timestamp* (one shard per month). As transactions happen *right now*, every single write lands on the "this month" shard. That one shard is on fire; the eleven older shards sit idle. You sharded across twelve machines and your write bottleneck is still **one** machine. The fix is to not put the clustering field first: make the key `(account_id, timestamp)` instead of `timestamp`. Now writes for thousands of active accounts spread across all shards, and you *keep* the efficient "one account's March" range scan. The cost: "all accounts in March" is no longer one scan. You trade the query you rarely run for the write spread you always need.

</Callout>

Rebalancing a key-range scheme is intuitive: when a shard gets too big, **split its range in two**; when adjacent shards shrink, **merge** them. (HBase splits at ~10 GB by default.) The split is expensive — it rewrites all that data into new files — and the shard that needs splitting is often the busy one, so you pay the cost at the worst time. Bigtable, HBase, CockroachDB, and MongoDB's range mode all shard this way.

## Hash Sharding

If you don't need range scans and you just want an **even spread**, run the key through a **hash function** first. A hash takes any input and returns a seemingly-random number — but the *same* input always gives the *same* number. Similar inputs (account 1000, account 1001) get wildly different hashes, so they scatter.

<Define term="Hash sharding" since="Sharding (Part 2)">
**Hash sharding** computes `hash(partition_key)` and uses the hash — not the raw key — to pick the shard. A good hash turns skewed, clustered keys into a uniform spread, so each shard gets a fair share. Why it matters: it kills the hot-shard problem that sorted key ranges have (sequential signups no longer pile on the last shard). The price: it **destroys ordering**, so range scans now have to hit every shard. You're trading cheap range queries for even load.
</Define>

Watch the difference. Five brand-new accounts, IDs assigned sequentially at signup — key-range dumps them all on one shard; hash scatters them:

<GoPlayground>

```go
package main

import (
	"fmt"
	"hash/fnv"
)

// Meridian shards its ledger across 4 nodes; the partition key is the account ID.

// byRange: IDs 0..999 -> shard 0, 1000..1999 -> shard 1, ... (sorted ranges).
func byRange(accountID, perShard int) int { return accountID / perShard }

// byHash: hash the ID first, then map onto the shards -> uniform spread.
func byHash(accountID, shards int) int {
	h := fnv.New32a()
	fmt.Fprintf(h, "%d", accountID)
	return int(h.Sum32()) % shards
}

func main() {
	const shards = 4
	newAccounts := []int{4000, 4001, 4002, 4003, 4004} // sequential signups

	fmt.Println("key-range: every new signup piles onto ONE shard (hot)")
	for _, id := range newAccounts {
		fmt.Printf("  account %d -> shard %d\n", id, byRange(id, 1000))
	}
	fmt.Println("hash: the same signups scatter across ALL shards (even)")
	for _, id := range newAccounts {
		fmt.Printf("  account %d -> shard %d\n", id, byHash(id, shards))
	}
}
```

</GoPlayground>

So hashing spreads the load. But *which* shard does a hash map to? Your first instinct — `hash(key) % numberOfNodes` — is a trap, and it's worth feeling the pain to understand why every real system avoids it.

<Define term="The mod-N rebalancing trap" since="Sharding (Part 2)">
Mapping a key to a node with `hash(key) % N` (where **N is the number of nodes**) seems natural — but when N changes, almost every key maps to a *different* node, so nearly the whole dataset has to move across the network. Why it matters: adding one machine to relieve load triggers a stampede that *adds* load — the opposite of what you wanted. The fix is to stop tying the math to the node count.
</Define>

Count the damage. Going from 3 nodes to 4 with `% N` relocates most of the dataset:

<GoPlayground>

```go
package main

import "fmt"

// How many of 1000 keys land on a DIFFERENT node when we grow 3 -> 4 nodes,
// using the naive node = hash % numberOfNodes scheme?
func main() {
	const keys = 1000
	moved := 0
	for k := 0; k < keys; k++ {
		if k%3 != k%4 { // before: k%3 nodes,  after: k%4 nodes
			moved++
		}
	}
	fmt.Printf("mod-N, 3 -> 4 nodes: %d of %d keys moved (%.0f%%)\n",
		moved, keys, 100*float64(moved)/float64(keys))
	// ~75%. Adding ONE node reshuffles three-quarters of the data. Unusable at scale.
}
```

</GoPlayground>

The fix used by virtually every sharded database: **decouple keys from nodes**. Create *many more shards than nodes* and pin a key to a shard with a constant — `hash(key) % numberOfShards`, where the shard count **never changes**. Then a key's shard is fixed for life. Rebalancing just **reassigns whole shards to nodes** — you move a few shards' worth of data, never recompute individual keys:

<UnderTheHood title="Consistent hashing, hash-range sharding, and a Go footgun">

The "fixed shard count" scheme has cousins. **Hash-range sharding** assigns each shard a *range of hash values* (shard 0 owns hashes 0–16383, etc.) so shards can split when they grow — Cassandra and ScyllaDB chop the hash space into many small ranges per node (16 and 256 respectively) with random boundaries, so imbalances average out. **Consistent hashing** (the Karger et al. 1997 algorithm, plus rendezvous and jump hashing) is a family of functions designed so that changing the number of shards moves the *minimum* possible keys — that's all "consistent" means here, nothing to do with replica or ACID consistency.

**The Go footgun:** do **not** shard with Go's built-in map hash. As of Go 1.14+, the runtime seeds map hashing with a per-process random value (and `hash/maphash` is explicitly per-process random), so the *same key hashes differently in different processes* — exactly what you don't want when every node must agree on where a key lives. (It's the Go counterpart to the well-known "a language's built-in `hashCode` isn't safe for distributed sharding" warning.) Use a **stable, explicit** hash: `hash/fnv` or `hash/crc32` for speed, or a real hash like SHA-256 (`crypto/sha256`) when you need quality. We assume Go 1.26 throughout; the `slices`/`maps` helpers (Go 1.21/1.22) are handy for managing the shard table, but the hash itself must be deterministic across machines.

</UnderTheHood>

## Hot Spots & Rebalancing

Hashing spreads keys evenly — but **even key distribution is not even load**. If one *single key* is hammered, hashing doesn't help: that key is on one shard, and that shard burns.

<Define term="Hot spot / hot key" since="Sharding (Part 2)">
A **hot spot** (or **hot shard**) is a shard with disproportionately high load while others sit idle — your bottleneck collapses back to one machine. A **hot key** is a single partition key so busy it overwhelms its shard. Why it matters: a uniform hash can't save you, because all traffic for one key lands on one shard by definition. For Meridian, a giant merchant account taking thousands of payments a second is a hot key — its shard melts while the rest nap.
</Define>

One mitigation: **split the hot key** by appending a small random suffix, turning one scorching key into many lukewarm ones across different shards. The cost is that **reads must now fan out** to every suffix and merge:

<GoPlayground>

```go
package main

import (
	"fmt"
	"math/rand"
)

// A megastore merchant account gets a storm of writes -> one hot shard.
// Spread the WRITES by appending a random suffix 00..09: one hot key becomes
// 10 sub-keys that (via hashing) land on different shards.
func writeKey(account string, hot bool) string {
	if hot {
		return fmt.Sprintf("%s#%02d", account, rand.Intn(10))
	}
	return account
}

func main() {
	counts := map[string]int{}
	for i := 0; i < 1000; i++ {
		counts[writeKey("acct_megastore", true)]++
	}
	fmt.Printf("1000 writes to one hot account spread across %d sub-keys\n", len(counts))
	fmt.Println("each sub-key now ~100 writes instead of 1000 hammering a single shard")
	fmt.Println("tradeoff: a READ of this account must query all 10 sub-keys and merge")
}
```

</GoPlayground>

Note the asymmetry: splitting relieves **write** load but not read load (you still read all the pieces), and it only makes sense for the *few* keys that are actually hot — you don't want this bookkeeping on every key. Load also shifts over time (a viral post is hot for two days, then calm), so you need a way to detect hot keys and promote/demote them. Cloud databases automate this (DynamoDB's "adaptive capacity," S3's "heat management").

That brings up the operational question: should splitting and moving shards happen **automatically** or with a **human in the loop**?

<Callout kind="warn" title="Automatic rebalancing + automatic failure detection = cascading failure">

Fully automatic rebalancing is convenient — DynamoDB autoscales shards in minutes. But it's dangerous when combined with automatic failure detection. Picture it: one node gets briefly overloaded and slow. The failure detector concludes it's *dead* and automatically rebalances its shards onto the other nodes — moving a large amount of data across the network. That extra load slows down *those* nodes, so the detector decides *they're* dead too, and rebalances again. Now you have a **cascading failure**: the automation chasing a phantom outage takes the whole cluster down. This is why a human in the loop, though slower, often prevents the worst operational surprises — and why you'd manually pre-rebalance before a known surge (Cyber Monday, a payroll run) rather than letting automation react mid-storm.

</Callout>

## Request Routing

You've split the data and you can rebalance it. Now the question every client faces: *I want account 7 — which machine (which IP and port) do I actually connect to?* This is **request routing**, and unlike stateless service load-balancing (any instance will do), a sharded request can only be served by the node holding that key's shard.

<Define term="Request routing" since="Sharding (Part 2)">
**Request routing** is the problem of directing a read or write for a given key to the specific node that holds that key's shard. Why it matters: the mapping (key → shard → node) changes as shards split and rebalance, so *something* must track it and keep every router up to date. Get it wrong and requests hit the wrong node — or a node that no longer owns the shard.
</Define>

There are three places to put the routing knowledge:

<ConceptGrid cols={3}>
  <ConceptCard label="1. Any node forwards">Client hits any node (round-robin). If that node owns the shard, it answers; otherwise it forwards to the right node and relays the reply. Simple clients, extra hops.</ConceptCard>
  <ConceptCard label="2. Routing tier">A shard-aware load balancer sits in front. It owns no data — it just looks up key → node and forwards. (MongoDB's `mongos` works this way.)</ConceptCard>
  <ConceptCard label="3. Shard-aware client">The client itself knows the shard map and connects straight to the right node — no middleman, lowest latency, smartest client.</ConceptCard>
</ConceptGrid>

All three need the same thing: a **trustworthy, up-to-date map** of shards to nodes. Who keeps it? Most systems use a separate **coordination service** — ZooKeeper or etcd — that holds the authoritative map and **notifies** routers when it changes:

<Callout kind="note" title="This is why consensus matters — and where we're headed">

Why a whole dedicated service just to store a small map? Because that map *must not* disagree with itself. If two routers think different nodes own shard 113, writes split-brain and you corrupt data. Keeping a tiny piece of state perfectly agreed-upon across machines, even as machines fail, is the **consensus** problem — and it's hard enough to deserve its own chapter. ZooKeeper, etcd, and the built-in Raft in Kafka/TiDB/CockroachDB exist to solve exactly this. We tackle it head-on in **Consistency & Consensus** (Chapter 23). For now: the shard map is sacred, and a consensus system guards it.

</Callout>

## Secondary Indexes

Everything so far assumed you look records up **by their partition key** — "give me account 7." But applications also ask "find all transactions over ₦10,000," or "find all *failed* payments." Those filter by a **secondary** attribute, not the partition key, and secondary indexes don't split as cleanly. Two designs, opposite trade-offs:

<Define term="Local vs global secondary index" since="Sharding (Part 2)">
A **local (document-partitioned) secondary index** lives *inside each shard* and indexes only that shard's own records. A **global (term-partitioned) secondary index** is a separate index, itself sharded by the *indexed value* rather than the primary key. Why it matters: local indexes make **writes** cheap (one shard updated) but **reads** expensive (you must ask every shard and merge — "scatter/gather"); global indexes flip it — **reads** of one term hit one shard, but **writes** fan out to update many index shards. You're choosing which operation pays.
</Define>

<ConceptGrid cols={2}>
  <ConceptCard label="Local (document-partitioned)">Each shard indexes its own rows. Write: touch one shard — cheap. Read "all failed payments": ask **every** shard and combine, because matches are scattered. Prone to tail-latency amplification (the slowest shard sets your latency). Used by MongoDB, Cassandra, Elasticsearch.</ConceptCard>
  <ConceptCard label="Global (term-partitioned)">One index across all data, sharded by the indexed value (`amount`, `status`). Read one term: hit one shard — cheap. Write one record: update **several** index shards (each field may live elsewhere), often asynchronously, so the index can be briefly stale. Used by CockroachDB, TiDB, DynamoDB's global indexes.</ConceptCard>
</ConceptGrid>

## Exercises

Build the primitives. Each is a real sharding mechanism in miniature.

<Exercise n={1} title="Detect a hot shard" level="easy">

Given a slice of per-shard request counts, write `hotShard(counts []int) (idx int, skewed bool)` returning the busiest shard's index and whether the load is **skewed** — define skewed as the max being more than 2× the average. Why does skew make sharding "less effective"?

<Solution>

```go
func hotShard(counts []int) (idx int, skewed bool) {
	total, max := 0, -1
	for i, c := range counts {
		total += c
		if c > max {
			max, idx = c, i
		}
	}
	avg := float64(total) / float64(len(counts))
	return idx, float64(max) > 2*avg
}
```

Skew means some shards do far more work than others. In the extreme, all load lands on one shard, so 9 of 10 machines are idle and your throughput is capped by the single busy one — you paid for ten machines and got the capacity of one. The point of sharding is an *even* spread; skew defeats the point.

</Solution>

</Exercise>

<Exercise n={2} title="Generalize the mod-N stampede" level="easy">

Write `fractionMoved(keys, fromN, toN int) float64` returning the fraction of `keys` (numbered `0..keys-1`) that change node when `hash%N` goes from `fromN` to `toN`. Use the key number itself as the "hash." Print it for 3→4 and 100→101.

<Solution>

```go
func fractionMoved(keys, fromN, toN int) float64 {
	moved := 0
	for k := 0; k < keys; k++ {
		if k%fromN != k%toN {
			moved++
		}
	}
	return float64(moved) / float64(keys)
}
// 3 -> 4:    ~0.75 (three-quarters move)
// 100 -> 101: ~0.99 (almost everything moves!)
```

The bigger the cluster, the *worse* mod-N gets — going 100→101 nodes moves ~99% of keys to relieve 1% more load. That's why mod-N is unusable at scale and why fixed-shard or consistent-hashing schemes exist: they move only the minimal slice the new node should own.

</Solution>

</Exercise>

<Exercise n={3} title="Hot-key splitter with read fan-out" level="medium">

Implement `splitWrite(key string, fanout int) string` (append `#NN` for a random suffix `0..fanout-1`) and `readKeys(key string, fanout int) []string` returning every sub-key a reader must query. Why must `readKeys` return *all* of them?

<Solution>

```go
func splitWrite(key string, fanout int) string {
	return fmt.Sprintf("%s#%02d", key, rand.Intn(fanout))
}

func readKeys(key string, fanout int) []string {
	out := make([]string, fanout)
	for i := range out {
		out[i] = fmt.Sprintf("%s#%02d", key, i)
	}
	return out
}
```

Writes were randomly sprinkled across the `fanout` sub-keys, so the data for the logical key is spread over all of them. A read has no way to know which sub-keys received writes, so it must query every sub-key and merge. That's the cost of splitting a hot key: cheaper writes, more expensive reads. Only worth it for genuinely hot keys.

</Solution>

</Exercise>

<Exercise n={4} title="Stable shard, unstable node" level="medium">

Show the fixed-shard guarantee concretely. Write `shardOf(key string, numShards int) int` (FNV hash `% numShards`) and demonstrate that for `numShards = 256` held constant, a key's shard is identical whether the cluster has 3 nodes or 30. Then explain what *does* change when nodes are added.

<Solution>

```go
func shardOf(key string, numShards int) int {
	h := fnv.New32a()
	h.Write([]byte(key))
	return int(h.Sum32()) % numShards
}
// shardOf("acct_7", 256) is the SAME number regardless of node count,
// because numShards never changes. The key's shard is fixed for life.
```

What changes when you add nodes is **only the shard→node assignment table** — a small map saying "shard 113 now lives on node 5 instead of node 2." The data inside a shard never gets re-hashed or re-bucketed; whole shards just get reassigned to nodes. That decoupling (keys→shards fixed, shards→nodes flexible) is what makes rebalancing cheap.

</Solution>

</Exercise>

<Exercise n={5} title="Local vs global index query cost" level="hard">

Model both index types over `S` shards. For a single-term query (e.g. `status = failed`), write `localCost(S int) int` (shards touched by a **local** index) and `globalCost() int` (shards touched by a **global** index, to fetch the postings list). For a write of one record, give `localWriteCost()` and `globalWriteCost(terms int)`. Summarize who pays what.

<Solution>

```go
func localCost(S int) int  { return S } // read: ask EVERY shard, scatter/gather
func globalCost() int      { return 1 } // read: one index shard owns the term

func localWriteCost() int        { return 1 }     // write: only the record's own shard
func globalWriteCost(terms int) int { return terms } // write: one index shard per term
```

Local indexes push the cost onto **reads** (every shard queried, tail-latency amplification) and keep **writes** cheap (one shard). Global indexes flip it: a single-term read hits one shard, but a write fans out to update one index shard per indexed term, and to stay correct may need a distributed transaction (or accept a briefly stale index). The right choice depends on your read/write ratio: read-heavy filtering → global; write-heavy with rare ad-hoc filters → local.

</Solution>

</Exercise>

<Recap>

You can now split a dataset bigger than any single machine — and route, rebalance, and index it:

- **Sharding splits** data so each machine holds a slice (survive *size*); **replication copies** data so each machine holds all of it (survive *failure*). Production does **both** — each shard is replicated. They're independent choices.
- The **partition key** decides a record's shard. Know it → go straight to one shard. Don't know it → query every shard and merge. It's the hardest decision to undo. Meridian shards the ledger by **account ID**.
- **Key-range** sharding keeps keys sorted → cheap range scans, but **hot shards** when writes cluster (a timestamp key dumps all writes on "this month"). Fix: put a spreading field first, like `(account_id, timestamp)`.
- **Hash** sharding spreads load evenly but **destroys ordering** (range scans now hit every shard). Never map keys with `hash % numberOfNodes` — that **mod-N stampede** moves ~75% of data on a 3→4 resize. Use a **fixed shard count** (or consistent hashing) so keys never change shard; rebalance by moving **whole shards**.
- Don't shard with Go's built-in/`maphash` hash — it's per-process random. Use a stable hash (`hash/fnv`, `crc32`, `crypto/sha256`).
- Even hashing can't fix a **hot key**; split it with a random suffix (cheaper writes, fan-out reads) — only for the few keys that are truly hot. **Automatic rebalancing + automatic failure detection** risks **cascading failure**; keep a human in the loop.
- **Request routing** (any-node-forwards / routing tier / shard-aware client) needs an authoritative shard→node map, guarded by a **consensus**-backed coordination service (ZooKeeper, etcd, Raft) — the subject of Chapter 23.
- **Secondary indexes** must be sharded too: **local** (cheap writes, scatter/gather reads) vs **global** (one-shard reads, fan-out writes). Choose by your read/write ratio.

</Recap>
