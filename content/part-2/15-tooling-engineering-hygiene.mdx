## Static Analysis

Your compiler catches type errors. But there's a whole category of bugs — shadowed errors, misused `sync` primitives, reachable SQL injection vectors — that compile fine and blow up at 3 a.m. That's what static analysis is for.

The scenario: the ledger service's repo just onboarded three new engineers. Each one has their own linting opinions and no shared config. Bugs are shipping. We're going to fix that.

### `go vet`

<Define term="go vet">
**`go vet`** is a static analyser that ships with the Go toolchain. It examines your source for a curated set of **high-confidence bugs that the compiler lets through** — mismatched `fmt` verbs, copied mutexes, unreachable code. Zero config, no install, runs in milliseconds. If `go vet ./...` is not in your CI pipeline, you're flying blind.
</Define>

`go vet` is the tool you get for free — zero configuration, ships with the Go toolchain, catches a curated set of high-confidence bugs that the compiler deliberately doesn't stop:

```shell
go vet ./...
```

What it catches:

<ConceptGrid cols={3}>
  <ConceptCard label="printf mismatches">`fmt.Sprintf("%d", "not an int")` — wrong format verb for the argument type.</ConceptCard>
  <ConceptCard label="unreachable code">A `return` before the end of a function, code after it that can never run.</ConceptCard>
  <ConceptCard label="sync.Mutex copies">`sync.Mutex` and `sync.WaitGroup` must never be copied after first use. Passing by value is a bug.</ConceptCard>
  <ConceptCard label="loop variable capture">Goroutines capturing a loop variable by address instead of value (still flagged for older patterns).</ConceptCard>
  <ConceptCard label="struct tag syntax">Malformed `json:"name"` tags that silently cause serialization failures.</ConceptCard>
  <Gotcha>Running `go vet` on its own is not enough. It catches only the highest-confidence bugs. For anything resembling a real CI pipeline, you want `golangci-lint` running `vet` as one linter among many.</Gotcha>
</ConceptGrid>

Here's a snippet `go vet` will refuse to pass — a `printf` mismatch and a mutex copy that compiles cleanly:

```go
package main

import (
	"fmt"
	"sync"
)

type Transfer struct {
	mu     sync.Mutex
	amount int
}

func process(t Transfer) { // BUG: copies the mutex
	t.mu.Lock()
	defer t.mu.Unlock()
	fmt.Printf("amount: %s\n", t.amount) // BUG: %s for an int
}

func main() {
	t := Transfer{amount: 5000}
	process(t)
}
```

Run `go vet ./...` and it shouts both errors before the binary ever runs. Good. Make the compiler do the work.

### `golangci-lint` — the meta-linter

<Define term="golangci-lint">
**`golangci-lint`** is a meta-linter — a single binary that runs dozens of Go linters **in parallel** and merges their output into one report. It includes `go vet` internally, so you replace both with one CI step. The critical detail: **pin its version** in CI. A floating linter version means a linter upgrade can break your build on someone else's schedule.
</Define>

`golangci-lint` is the industry standard: a single binary that runs dozens of linters in parallel and collapses them into one clean report. It runs `go vet` internally, so you only need one tool in CI.

Install (use the official binary; don't `go install` it — version pinning matters):

```shell
# download the installer script from golangci-lint.run, then:
golangci-lint run ./...
```

The linters you actually want wired in for the ledger service:

<ConceptGrid cols={2}>
  <ConceptCard label="errcheck">Flags every place you silently discarded an error with `_`. If you wrote `rows.Close()` without checking the error, this finds it.</ConceptCard>
  <ConceptCard label="staticcheck">The deepest static analyser in the Go ecosystem — catches deprecated API uses, impossible conditions, redundant code, and much more. Think of it as `go vet` at graduate level.</ConceptCard>
  <ConceptCard label="ineffassign">Catches assignments to variables whose value is never read afterwards — often a sign of a logic error or a forgotten `return`.</ConceptCard>
  <ConceptCard label="gosec">Security-focused: flags things like integer overflows in crypto, use of `math/rand` instead of `crypto/rand` for secrets, hard-coded credentials, and weak TLS configs.</ConceptCard>
  <ConceptCard label="govet">The standard `go vet` suite, run as part of the meta-linter so you get one unified report.</ConceptCard>
  <ConceptCard label="revive">A fast, configurable drop-in replacement for `golint`; catches naming and style issues the compiler ignores.</ConceptCard>
</ConceptGrid>

A minimal `.golangci.yml` for the ledger service repo:

```yaml
linters:
  enable:
    - errcheck
    - staticcheck
    - ineffassign
    - gosec
    - govet
    - revive

linters-settings:
  errcheck:
    check-type-assertions: true
    check-blank: true
  gosec:
    severity: medium

issues:
  exclude-rules:
    # Test files: allow errcheck on defer in tests
    - path: "_test\\.go"
      linters: [errcheck]

run:
  timeout: 5m
```

Wire it into CI (we'll build the full pipeline in the CI section):

```yaml
- name: Lint
  run: golangci-lint run ./...
```

<UnderTheHood title="How staticcheck analyses your code">

`staticcheck` (and `golangci-lint` when running it) builds a **full type-checked SSA (Static Single Assignment)** representation of your package graph. SSA flattens control flow so every variable is assigned exactly once — making data-flow analysis tractable.

From that representation, `staticcheck` can reason across package boundaries: it knows that `io.Reader.Read` has a documented contract (never call it again after it returns `0, io.EOF`), so violating that contract is flagged even if the violation spans multiple functions.

This is distinct from pattern-matching on AST nodes (what simpler linters do). SSA-based analysis can follow values through function calls and closures, which is why it catches things like: "this context was already cancelled before being passed to this function." As of Go 1.24, `staticcheck` targets the same Go version as your `go.mod` `go` directive, so it accounts for language-version-specific semantics automatically.

</UnderTheHood>

## Code Generation

Go has no macros and no template metaprogramming. What it has is `go generate` — a convention for running arbitrary tools on your source that produce Go source files before the compiler sees them.

The scenario: the ledger service has a `TransferStatus` type with five states. Every time a developer adds a new state, they forget to update the `String()` method, and log lines start printing `TransferStatus(4)` instead of `"settled"`. We fix that with generation.

### `go generate` directives

<Define term="go generate">
**`go generate`** is a code-generation convention built into the Go toolchain. You annotate a source file with a `//go:generate <command>` comment; running `go generate ./...` executes those commands and produces new `.go` files before the compiler ever runs. The generated files carry a `// Code generated ... DO NOT EDIT.` header. Why it matters: **generated code is correct by construction** — no hand-written `String()` methods that silently fall behind a growing iota enum at 2 a.m.
</Define>

A `//go:generate` comment is a directive — not a compiler directive, just a convention. When you run `go generate ./...`, the tool reads every `//go:generate` line in every `.go` file in scope and executes the command verbatim:

```go
// in ledger/status.go
//go:generate stringer -type=TransferStatus -linecomment
```

The directive lives right next to the type it describes. When someone adds a new constant, they run `go generate ./...` and the `String()` method is regenerated. The generated file gets a `// Code generated ... DO NOT EDIT.` header so tools (and humans) know not to touch it.

### `stringer`

`stringer` is the canonical first `go:generate` tool. Install it:

```shell
go install golang.org/x/tools/cmd/stringer@latest
```

Define the type and its constants:

```go
package ledger

//go:generate stringer -type=TransferStatus -linecomment

// TransferStatus is the lifecycle state of a ledger transfer.
type TransferStatus int

const (
	StatusPending  TransferStatus = iota // pending
	StatusSettled                        // settled
	StatusFailed                         // failed
	StatusReturned                       // returned
	StatusReversed                       // reversed
)
```

After `go generate ./...`, `stringer` emits `transferstatus_string.go` — a `String() string` method that satisfies `fmt.Stringer`. Now `fmt.Println(StatusSettled)` prints `"settled"`, forever, no matter how many states you add — as long as you remember to re-run the generator.

<GoPlayground>

```go
package main

import "fmt"

type TransferStatus int

	switch s {

```

### Mocks and sqlc

Two more generators you'll wire into a real service:

- **`mockery`** or **`moq`**: generate interface mocks from your own service interfaces. Keep mocks out of the repo by regenerating them in CI rather than committing them.
- **`sqlc`**: compile SQL queries into type-safe Go. You write `-- name: GetTransfer :one` in a `.sql` file; `sqlc generate` produces a `GetTransfer(ctx, id)` method with the exact return type the query produces. No string soup, no runtime reflection. (Covered in depth in the SQL & Databases chapter.)

<Callout kind="pro" title="When generation beats reflection">

Reflection is dynamic — it pays a runtime cost every call and loses static type safety. Generation is static — the code is checked at compile time and has zero runtime overhead. Use generation when: (1) you have a finite, enumerable set of variants (statuses, command types, error codes), (2) the generated code would be tedious but mechanical to write by hand, or (3) you're generating from a schema (SQL, proto, OpenAPI) that is the source of truth. Use reflection when the set is open and unknown at compile time.

</Callout>

## Build Tags

Go has a clean, explicit mechanism for conditional compilation: **build constraints** (also called build tags). They tell the Go toolchain to include or exclude a file based on the target platform, Go version, or a custom label you define.

The scenario: the ledger service has slow integration tests that spin up a real Postgres container. You don't want them running on every `go test ./...` — only in CI or when a developer explicitly opts in.

<Define term="build tags (//go:build constraints)">
A **build tag** is a `//go:build <expr>` comment on the first line of a `.go` file that tells the compiler whether to **include or exclude that file** from a given build. The expression uses `&&`, `||`, and `!` over tag names, OS identifiers (`linux`, `darwin`), architecture names (`amd64`), and Go version identifiers. Files excluded by a constraint are never compiled — zero runtime overhead. Why it matters: the right tool for gating slow integration tests, platform-specific code, and debug-only instrumentation. The old `// +build` form was removed in Go 1.25; write only `//go:build`.
</Define>

### The `//go:build` syntax

As of Go 1.17 (and required as of Go 1.17 alongside the old `// +build` form, which was removed in 1.25), the constraint is a comment on the very first line of the file, before the `package` declaration, with a blank line separating them:

```go
//go:build integration

package ledger_test
```

Build that file only when you pass `-tags integration`:

```shell
go test -tags integration ./...
```

Without the tag, the file is invisible to the compiler. With it, it's included. Dead simple, and no runtime overhead — excluded files are never compiled at all.

### Platform-specific files

The Go toolchain also reads constraints from filenames. A file named `db_linux.go` is included only on Linux; `db_darwin.go` only on macOS; `db_windows.go` only on Windows. The naming convention is `name_GOOS.go` or `name_GOOS_GOARCH.go`.

You can combine file naming with explicit `//go:build` constraints for fine-grained control:

```go
//go:build linux && amd64

package sys
```

This file is compiled only on Linux/amd64. Anything not matching is silently skipped.

<GoPlayground>

```go
package main

import (
	"fmt"
	"runtime"
)

// In a real project, platform-specific behavior lives in separate files.
// Here we show the runtime equivalent to understand what build tags enforce
// at compile time.
func platformInfo() string {
	return fmt.Sprintf("running on %s/%s", runtime.GOOS, runtime.GOARCH)
}

func main() {
	fmt.Println(platformInfo())
	fmt.Println("In production: platform-specific files are selected at compile time,")
	fmt.Println("not at runtime. The wrong platform's file never enters the binary.")
}
```

</GoPlayground>

### Integration test tags in CI

Here's the pattern for the ledger service. Regular tests run on every PR, integration tests run in a dedicated CI job:

```yaml
# .github/workflows/ci.yml (excerpt)
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-go@v5
        with:
          go-version-file: go.mod
      - name: Unit tests
        run: go test -race -count=1 ./...
      
  integration:
    runs-on: ubuntu-latest
    services:
      postgres:
        image: postgres:16
        env:
          POSTGRES_PASSWORD: test
        ports: ["5432:5432"]
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-go@v5
        with:
          go-version-file: go.mod
      - name: Integration tests
        run: go test -race -tags integration -count=1 ./...
```

<Callout kind="note" title="The //go:build constraint vs. the old // +build form">

Before Go 1.17, constraints used `// +build linux,amd64` with comma for AND and space for OR — a truly forgettable syntax. Go 1.17 introduced `//go:build` with proper boolean expressions (`&&`, `||`, `!`). Go 1.17 through 1.24 accepts both; the `gofmt` tool rewrites old-style tags to the new form. Write only `//go:build` in new code.

</Callout>

## Go Workspaces

Here's a scenario that bites every team eventually: you're developing the ledger service and its logging library — `ledger-slog-handler` — in tandem. You're making breaking changes to the library's interface. You need to test them together *before* tagging a release.

The old answer was `replace` directives in `go.mod`:

```
require github.com/myorg/ledger-slog-handler v0.3.1
replace github.com/myorg/ledger-slog-handler => ../ledger-slog-handler
```

That works, but you have to remember to remove the `replace` before you commit. Miss it once and you've shipped a module that points at a local path — it breaks every build that doesn't have that path. Not acceptable.

**Go workspaces** (`go work`), introduced in Go 1.18, are the right answer.

<Define term="Go workspaces (go work)">
A **Go workspace** is a `go.work` file that tells the toolchain: "resolve these module import paths from local directories instead of the module registry." Created with `go work init ./module-a ./module-b`. Why it matters: it lets you develop two interdependent modules in tandem — changing a library and testing it in a consuming service — **without `replace` directives in `go.mod`**. Add `go.work` to `.gitignore`; it's a local developer override, not something that should affect CI or other developers' machines. Introduced in Go 1.18.
</Define>

### How `go.work` works

A `go.work` file sits at the root of a directory that contains multiple modules. It tells the Go toolchain: "when resolving these module paths, prefer the local directory over the registry."

```
go 1.24

use (
    ./ledger-service
    ./ledger-slog-handler
)
```

Create it:

```shell
go work init ./ledger-service ./ledger-slog-handler
# or add a module to an existing workspace:
go work use ./ledger-slog-handler
```

Now, inside `./ledger-service`, any import of `github.com/myorg/ledger-slog-handler` resolves to `./ledger-slog-handler` — no `replace` directive, no manual cleanup. The individual `go.mod` files are untouched.

<Callout kind="warn" title="Commit go.work.sum, not go.work">

`go.work.sum` is the checksum database for workspace-mode downloads. Commit it. `go.work` itself is a local developer override — add it to `.gitignore` so CI always resolves modules from the registry and nobody gets a surprise `replace`-equivalent on their machine.

</Callout>

<UnderTheHood title="How workspace mode overrides module resolution">

Go's module resolution normally runs **MVS (Minimal Version Selection)** — a pure function over your `go.sum` and the dependency graph that always picks the minimum version satisfying all constraints. (More on MVS in the next section.)

Workspace mode inserts a step *before* MVS: the toolchain builds a **workspace module map** from the `use` directives. When the dependency graph walker asks "where is `github.com/myorg/ledger-slog-handler@v0.3.1`?", the workspace map short-circuits: "I have that module locally at `./ledger-slog-handler`; use that." The version in the `require` statement is ignored for resolution purposes (though not for minimum-version bookkeeping when workspace mode is off).

This is implemented in `cmd/go/internal/modload`. The workspace file is parsed into a `WorkspaceFile` struct, and the loader passes a `WorkspaceModules` map to the MVS graph traversal. Outside workspace mode, that map is empty and everything goes through the normal registry + checksum flow.

As of Go 1.24, `go env GOWORK` tells you whether workspace mode is active and which `go.work` file is being used. `GOWORK=off` disables workspace mode even if a `go.work` file is present — useful for CI to verify the published module is self-consistent.

</UnderTheHood>

## Module Versioning

Modules are how Go manages dependencies. Understanding the machinery — not just the commands — is what separates engineers who ship reproducible builds from engineers who ship surprises.

### `go.mod` and `go.sum`

Every module starts with `go.mod`:

```
module github.com/myorg/ledger-service

go 1.24

toolchain go1.24.3

require (
    github.com/jackc/pgx/v5 v5.7.2
    golang.org/x/sync v0.10.0
)
```

- **`module`**: the import path for this module. Everything in this repo is imported under this prefix.
- **`go`**: the minimum Go version the module requires.
- **`toolchain`**: (Go 1.21+) the specific toolchain to use, enabling reproducible builds. More in the CI section.
- **`require`**: the *minimum* version of each dependency.

`go.sum` records the cryptographic hash (SHA-256) of every module zip the build has ever downloaded. The Go toolchain verifies these hashes against the checksum database (`sum.golang.org`) before using a module. A tampered module that matches the declared version but not the hash fails the build — immediately and loudly.

```
github.com/jackc/pgx/v5 v5.7.2 h1:mLoDIY/...==
github.com/jackc/pgx/v5 v5.7.2/go.mod h1:ncY89...==
```

Never edit `go.sum` by hand. Run `go mod tidy` and let the toolchain manage it.

### MVS — Minimal Version Selection

MVS is Go's dependency algorithm. The rule is deliberately simple: **given a set of `require` statements across all modules in the build, always pick the *minimum* version that satisfies all constraints.**

This is radically different from npm's `^` ranges or Python's pip. In Go, `require foo v1.2.0` means "at minimum v1.2.0" — but nothing picks a higher version without an explicit `go get` command or another dependency pulling it up. The result is **reproducible by construction**.

### Semantic import versioning (v2+)

Go modules encode major version bumps in the import path itself. If a module makes a breaking change, it bumps to `v2` — and the import path changes to reflect it:

```go
import "github.com/myorg/ledger-slog-handler/v2"
```

This is not optional. A module at `v2` and a module at `v1` can coexist in the same build — they're different import paths, and thus different packages. This is the **semantic import versioning** rule: **if you break the API, change the path.**

The `go.mod` for a v2 module:

```
module github.com/myorg/ledger-slog-handler/v2

go 1.24
```

<Callout kind="note" title="go mod tidy is your friend">

`go mod tidy` does two things: (1) adds any `require` entries that your code imports but `go.mod` doesn't list, and (2) removes any `require` entries for packages your code no longer imports. Run it before every commit. Add a CI step that runs `go mod tidy` and asserts no diff — a tidy check catches the "someone added a dependency without updating go.mod" failure mode.

</Callout>

## CI Essentials

A pipeline that doesn't run the race detector and doesn't enforce reproducible builds is not a CI pipeline. It's a linter. Let's build the real thing.

### The race detector in CI

The race detector (`-race`) instruments every memory access and reports data races at runtime. It has roughly 2–5× CPU overhead and 5–10× memory overhead — acceptable in CI, never ship it to production. Always run it on your test suite:

```shell
go test -race -count=1 ./...
```

`-count=1` disables test result caching, so the race detector actually runs every time rather than using a cached green result.

### Coverage in CI

```shell
go test -race -count=1 -coverprofile=coverage.out ./...
go tool cover -func=coverage.out
```

For the ledger service, enforce a minimum coverage threshold as a CI step — not as a percentage-of-lines goal (that's gameable), but as: "every package that touches money arithmetic has at least one fuzz test." More on fuzz testing in the Testing chapter; here we wire coverage output into the pipeline.

<Define term="reproducible build">
A **reproducible build** produces a **bit-for-bit identical binary** every time, given the same source and toolchain. Why it matters: if two builds of the same commit produce different binaries, you can't verify what you shipped, you can't trust your artifact cache, and a supply-chain attacker can inject a binary that no source diff would reveal. Go gives you the ingredients — pinned `toolchain` in `go.mod`, `-trimpath`, `CGO_ENABLED=0` — but you have to combine them deliberately.
</Define>

### Reproducible builds

A reproducible build produces bit-for-bit identical output given the same source. Go gives you the tools; you have to use them:

```shell
CGO_ENABLED=0 \
  go build \
  -trimpath \
  -ldflags="-s -w" \
  -o ledger-service \
  ./cmd/ledger-service
```

- **`-trimpath`**: strips all local filesystem paths from the binary (no `/home/abbey/go/src/...` in stack traces). Critical for reproducibility and for not leaking your directory structure.
- **`CGO_ENABLED=0`**: disables C interop, producing a fully static binary.
- **`-ldflags="-s -w"`**: strips debug symbols and the DWARF table, shrinking the binary.
- **Pinned toolchain** in `go.mod` (`toolchain go1.24.3`): ensures everyone — CI, every developer, every docker build — uses the same compiler.

The full CI pipeline for the ledger service:

```yaml
name: CI

on:
  push:
    branches: [main]
  pull_request:

jobs:
  ci:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-go@v5
        with:
          go-version-file: go.mod   # honours the toolchain directive

      - name: Verify tidy
        run: |
          go mod tidy
          git diff --exit-code go.mod go.sum

      - name: Lint
        uses: golangci/golangci-lint-action@v6
        with:
          version: v1.62.2   # pinned — never float your linter version

      - name: Vet
        run: go vet ./...

      - name: Test (race + coverage)
        run: go test -race -count=1 -coverprofile=coverage.out ./...

      - name: Vulncheck
        run: |
          go install golang.org/x/vuln/cmd/govulncheck@v1.1.3
          govulncheck ./...

      - name: Build (reproducible)
        run: |
          CGO_ENABLED=0 go build -trimpath \
            -ldflags="-s -w" \
            -o ledger-service \
            ./cmd/ledger-service
```

## Supply-Chain Security

A dependency is code you didn't write but you're shipping. That's a supply-chain. And the supply chain for Go services has specific, well-understood attack surfaces.

### `govulncheck` — Go's official vulnerability scanner

<Define term="govulncheck (supply-chain security)" since="Application Security Baseline (Part 2)">
**`govulncheck`** is the Go team's official vulnerability scanner. Unlike generic SBOM scanners that flag every CVE in every module you depend on, `govulncheck` builds a **call graph** of your program and only reports vulnerabilities in functions **your code actually reaches**. A CVE in a function you never call — no finding. Why it matters: call-graph precision kills the false-positive noise that causes engineers to start ignoring security scans. A scanner you ignore is worse than no scanner.
</Define>

`govulncheck` is maintained by the Go team. It does something most vulnerability scanners don't: **call-graph analysis**. It doesn't just flag "this module has a known CVE" — it flags "your code *calls the vulnerable function* in this module." The difference matters enormously.

A module might have a SQL injection vulnerability in a function you never call. A naive scanner flags the CVE and blocks your build. `govulncheck` looks at your call graph and says: "You import that module but you don't reach the vulnerable symbol — no finding." That precision kills most of the false-positive noise that makes engineers start ignoring security scans.

```shell
go install golang.org/x/vuln/cmd/govulncheck@latest
govulncheck ./...
```

Output when a real vulnerability is found:

```
Vulnerability #1: GO-2024-2887
    Uncontrolled resource consumption in golang.org/x/net
  More info: https://pkg.go.dev/vuln/GO-2024-2887
  Module: golang.org/x/net
    Found in: golang.org/x/net@v0.25.0
    Fixed in: golang.org/x/net@v0.26.0
    Example traces found:
      #1: cmd/ledger-service/main.go:42:14:
            main.startServer calls net/http.ListenAndServeTLS,
            which eventually calls golang.org/x/net/http2.(*serverConn).serve
```

That trace tells you exactly why this vulnerability is reachable: your `startServer` → `ListenAndServeTLS` → the vulnerable `http2` code. Fix it:

```shell
go get golang.org/x/net@v0.26.0
go mod tidy
```

<UnderTheHood title="How govulncheck uses call-graph analysis">

`govulncheck` builds a **call graph** of your entire program — a directed graph where each node is a function and each edge is a call site. It does this using the same SSA representation that `staticcheck` uses, but then runs a **points-to analysis** (specifically, a variant of the VTA — Variable Type Analysis — algorithm) to determine which concrete types flow to interface call sites.

It then intersects that call graph with the **Go vulnerability database** (`vuln.go.dev`), which maps CVEs to specific package-path and symbol combinations. A vulnerability is "reachable" if there is any path in the call graph from a main function or test function to a vulnerable symbol.

This is fundamentally different from the SBOM-scanning approach used by tools like `trivy` or `grype`, which operate at the module level: "you depend on module X, module X has CVE Y, therefore you are vulnerable." That produces false positives whenever the vulnerable code path is in a function you never call.

`govulncheck` in call-graph mode (`./...`, the default) uses binary analysis when called with a binary path or SSA analysis when called on source. As of Go 1.24, it's fully integrated with the module graph via `go mod download`, so it works correctly in monorepos and with Go workspaces.

</UnderTheHood>

### SBOM scanning in CI

`govulncheck` is the primary gate. SBOM (Software Bill of Materials) scanning adds a complementary layer: it generates a machine-readable inventory of every dependency in your binary and optionally checks it against external CVE databases (including OSV, NVD, and GitHub Advisory).

Generate a CycloneDX SBOM with `syft`:

```shell
syft packages . -o cyclonedx-json > sbom.json
grype sbom:sbom.json
```

Wire both into CI after the build step:

```yaml
- name: Generate SBOM
  run: |
    syft packages . -o cyclonedx-json > sbom.json

- name: Scan SBOM
  run: grype sbom:sbom.json --fail-on medium
```

`--fail-on medium` fails the build if any dependency has a medium-or-higher CVSS score — this is the gate that blocks a known-vulnerable module from shipping.

<Exercise n={5} title="Run govulncheck and fix a finding" level="hard">

Given a `go.mod` that requires `golang.org/x/net v0.25.0` (a version with known issues in its HTTP/2 implementation), run `govulncheck ./...` against a small HTTP server that calls `http.ListenAndServe`. <Solution>

package main

import (
	"fmt"
	"net/http"

<Recap>

The engineering that keeps a production Go service healthy:

- **`go vet`** is the free, zero-config, compiler-adjacent safety net. Run it always.
- **`golangci-lint`** is the meta-linter: `errcheck`, `staticcheck`, `gosec`, `ineffassign` wired into one CI step. Pin its version.
- **`go generate`** + `stringer` turns repetitive, error-prone manual code into correct generated code. Checked via `git diff` in CI.

- **Go workspaces (`go.work`)** let you develop interdependent local modules without `replace` directives. Add `go.work` to `.gitignore`; commit `go.work.sum`.
- **MVS** makes dependency resolution a pure, reproducible function. `-trimpath` + pinned `toolchain` in `go.mod` + `CGO_ENABLED=0` makes builds reproducible at the binary level.
- **`govulncheck`** uses call-graph analysis to find only vulnerabilities you actually reach. Not call-graph aware = false positives = ignored scanner = shipped CVEs.
- The full CI pipeline — tidy check → lint → vet → race tests → govulncheck → reproducible build — is the non-negotiable standard for production Go.
