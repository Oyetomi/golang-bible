<HeroCard label="Part 2 · Chapter 18" title="gRPC & Service-to-Service Communication">

The cinema's customers use the HTTP/JSON API from their browsers. But the cinema now has other *services* that need seats: the box office's terminals, the jobs worker from chapter 13, a future loyalty service. Between services you control both ends, and you want different things: a schema both sides are compiled from, so a renamed field is a build error rather than a 3 a.m. surprise; smaller messages; deadlines and cancellation that travel with the call; and streams that push changes instead of polling.

That's what **gRPC** is for: a service defined in a **Protocol Buffers** schema, code generated for both sides, carried over HTTP/2. This chapter adds a gRPC interface to the cinema service next to its HTTP one, calls it every way gRPC allows, and measures what's different, including three failures you only meet in production: a panic in one call that kills every other caller, a stream that holds up shutdown, and a schema change an old client decodes without an error and without its data.

Six stops. If you get lost, come back here:

1. **The schema.** A `.proto` file, linted and compiled with buf, and why the zero value of an enum matters.
2. **The server.** One domain, a second transport, and status codes that mean something.
3. **Four kinds of call.** Unary, server streaming, client streaming, bidirectional, on real seats.
4. **Deadlines and failures.** A deadline that crosses the wire, and a panic that shouldn't cross the process.
5. **Speed and shutdown.** Bytes and requests per second against HTTP/JSON, and the stream that never ends.
6. **Changing the schema.** What `buf breaking` catches, and what an old client does with a changed field.

## The lab bench

The restructured cinema module from chapter 17. The new code is a `proto/` directory, generated code under `internal/gen`, and an `internal/grpcapi` package; `app.Run` serves gRPC on its own port next to HTTP. The tools:

- **buf** (1.73) lints the schema, runs the code generators and checks for breaking changes.
- **protoc-gen-go** and **protoc-gen-go-grpc** generate the Go code.
- **grpcurl** is curl for gRPC.

Pinning them all with `go get -tool` in the service's module grew its `go.mod` from 9 requirements to 112 (buf alone brings a compiler's worth of dependencies), although the service binary still links 7 modules. So the two generators, whose versions must match the protobuf and gRPC runtimes the service links, stay in the service's `go.mod`, and buf and grpcurl moved to a separate `tools/go.mod`: 15 requirements for the service, 106 for the tools, and `go tool -modfile=tools/go.mod buf …` to run them.

## The Schema

*Stop 1 of 6.*

### Step 1: a first draft

A `.proto` file declares the service's methods and the messages they take and return. A first attempt, the way it tends to come out:

```text
syntax = "proto3";

package seats;

import "google/protobuf/empty.proto";

option go_package = "naive/gen/seats";

service Seats {
  rpc Hold(Seat) returns (google.protobuf.Empty);
  rpc List(Movie) returns (SeatList);
}

enum Status {
  FREE = 0;
  HELD = 1;
  BOOKED = 2;
}

message Seat {
  string movie = 1;
  string id = 2;
  Status status = 3;
}

message Movie {
  string name = 1;
}

message SeatList {
  repeated Seat seats = 1;
}
```

`buf lint` rejects ten things:

```text

proto/seats/seats.proto:15:3:Enum value name "FREE" should be prefixed with "STATUS_".
proto/seats/seats.proto:15:3:Enum zero value name "FREE" should be suffixed with "_UNSPECIFIED".
proto/seats/seats.proto:16:3:Enum value name "HELD" should be prefixed with "STATUS_".

```

Most are conventions that pay off later: a **versioned package** (`seats.v1`) so a v2 can live next to it; **one request and one response message per method**, so each can grow a field without changing the others (`Hold(Seat)` would tie the hold request to the seat's shape forever); enum values prefixed with the enum's name, since proto enum values share a namespace with everything else in the package.

### Step 2: the zero value

One rule is about correctness. In proto3, every field has a default, and **a field set to its default isn't sent at all**. For an enum the default is the value numbered 0. So what does a receiver see when the sender never set the status (a bug, or a client built before the field existed)?

```go noverify
// zero sends a seat whose status was never set (a bug, or a client built
// before the field existed) and shows what the receiver reads.
package main

import (
	"fmt"

	"naive/gen/seats"

	"google.golang.org/protobuf/proto"
)

func main() {
	b, _ := proto.Marshal(&seats.Seat{Movie: "inception", Id: "A7"}) // Status not set
	var got seats.Seat
	if err := proto.Unmarshal(b, &got); err != nil {
		panic(err)
	}
	fmt.Printf("on the wire: % x  (%d bytes; no status field at all)\n", b, len(b))
	fmt.Printf("received:    seat %s, status %v\n", got.Id, got.Status)
}
```

```text
on the wire: 0a 09 69 6e 63 65 70 74 69 6f 6e 12 02 41 37  (15 bytes; no status field at all)
received:    seat A7, status FREE
```

The wire carries no status, and the receiver reads **FREE**: a seat of unknown state shown as available. That's why buf insists the zero value be `…_UNSPECIFIED`: "not set" must be distinguishable from every real state.

### Step 3: the schema the cinema uses

```text
syntax = "proto3";

// The cinema's seat service, for other services (the box office, the jobs
// worker). Customers' browsers keep using the HTTP/JSON API.
package cinema.v1;

option go_package = "cinema/internal/gen/cinema/v1;cinemav1";

service SeatService {
  // Hold reserves a seat for the caller (metadata "x-user") while they pay.
  rpc Hold(HoldRequest) returns (HoldResponse);
  rpc Confirm(ConfirmRequest) returns (ConfirmResponse);
  rpc Release(ReleaseRequest) returns (ReleaseResponse);
  rpc ListSeats(ListSeatsRequest) returns (ListSeatsResponse);

  // WatchSeats streams the seat map every time it changes (server streaming).
  rpc WatchSeats(WatchSeatsRequest) returns (stream WatchSeatsResponse);

  // HoldGroup holds several seats for one party: the client streams seats,
  // the server answers once with what it got (client streaming).
  rpc HoldGroup(stream HoldGroupRequest) returns (HoldGroupResponse);

  // BoxOffice is a terminal's session: each request is answered as soon as
  // it's done, in either direction at any time (bidirectional streaming).
  rpc BoxOffice(stream BoxOfficeRequest) returns (stream BoxOfficeResponse);
}

enum SeatStatus {
  SEAT_STATUS_UNSPECIFIED = 0;
  SEAT_STATUS_FREE = 1;
  SEAT_STATUS_HELD = 2;
  SEAT_STATUS_BOOKED = 3;
}

message Seat {
  string id = 1;
  SeatStatus status = 2;
  string user = 3;
}

message HoldRequest {
  string movie = 1;
  string seat = 2;
}
message HoldResponse {}

message ConfirmRequest {
  string movie = 1;
  string seat = 2;
}
message ConfirmResponse {}

message ReleaseRequest {
  string movie = 1;
  string seat = 2;
}
message ReleaseResponse {}

message ListSeatsRequest {
  string movie = 1;
}
message ListSeatsResponse {
  repeated Seat seats = 1;
}

message WatchSeatsRequest {
  string movie = 1;
}
message WatchSeatsResponse {
  repeated Seat seats = 1;
}

message HoldGroupRequest {
  string movie = 1;
  string seat = 2;
}
message HoldGroupResponse {
  repeated string held = 1;
  repeated string failed = 2;
}

message BoxOfficeRequest {
  string movie = 1;
  string seat = 2;
  string customer = 3;
}
message BoxOfficeResponse {
  string seat = 1;
  string customer = 2;
  bool held = 3;
  string error = 4;
}
```

`buf lint`: no findings. `buf generate` runs both generators (configured in `buf.gen.yaml` to run through `go tool`, so the versions come from `go.mod`) and writes `internal/gen/cinema/v1/seats.pb.go` (the messages, 951 lines) and `seats_grpc.pb.go` (a client and a server interface, 355 lines). With this schema, the unset status arrives as what it is:

```text
unset status received as: SEAT_STATUS_UNSPECIFIED

seat map, 40 seats, 20 held:
  HTTP API's JSON       1456 bytes
  protobuf (binary)      495 bytes
  protojson             1946 bytes

first seat, as bytes on the wire: 0a 0e 0a 02 41 31 10 02 1a 06 75 73 65 72 2d 30 0a 06 0a 02 41 32
```

The same seat map is **495 bytes** as protobuf against 1,456 as the HTTP API's JSON: field names are replaced by numbers (the `0a`, `10`, `1a` bytes are field 1, 2 and 3 with their wire types), and the status is one byte. `protojson`, the canonical JSON form of a protobuf message, is larger still (1,946 bytes: it spells enum values out in full).

### Step 1: the same domain, another transport

`grpcapi` implements the generated `SeatServiceServer` interface over the same `booking.Store` that `httpapi` uses:

The package imports the domain (`booking`), the code `buf generate` wrote from the `.proto` file, and three gRPC packages: status codes, metadata and statuses:

```go noverify title="cinema/internal/grpcapi/grpcapi.go · lines 1–20"
// Package grpcapi serves booking.Store over gRPC (cinema.v1.SeatService),
// for the cinema's other services. It's the same domain as httpapi, with a
// different transport.
package grpcapi

import (
	"context"
	"errors"
	"io"
	"slices"
	"sync"
	"time"

	"cinema/internal/booking"
	cinemav1 "cinema/internal/gen/cinema/v1"

	"google.golang.org/grpc/codes"
	"google.golang.org/grpc/metadata"
	"google.golang.org/grpc/status"
)
```

`Server` embeds `UnimplementedSeatServiceServer`, generated code that answers `Unimplemented` for every method. That's what lets the `.proto` gain a new method without breaking this build: the embedded type supplies it until you write the real one. `Drain` closes a channel once, and every open watch stream sees it:

```go noverify title="cinema/internal/grpcapi/grpcapi.go · lines 22–39"
type Server struct {
	cinemav1.UnimplementedSeatServiceServer
	store      booking.Store
	hold       time.Duration
	WatchEvery time.Duration // how often WatchSeats checks for changes

	draining  chan struct{} // closed by Drain
	drainOnce sync.Once
}

func New(store booking.Store, hold time.Duration) *Server {
	return &Server{store: store, hold: hold, WatchEvery: 200 * time.Millisecond, draining: make(chan struct{})}
}

// Drain ends every WatchSeats stream with Unavailable, so watchers
// reconnect (to another replica) instead of holding up shutdown:
// GracefulStop waits for streams, and a watch never ends by itself.
func (s *Server) Drain() { s.drainOnce.Do(func() { close(s.draining) }) }
```

gRPC has no HTTP headers in your handler, but it has **metadata**, the same idea: key-value pairs sent with the call. The customer arrives as `x-user`, as the HTTP API reads `X-User`, and a missing one is `Unauthenticated`:

```go noverify title="cinema/internal/grpcapi/grpcapi.go · lines 41–50"
// user reads the caller's customer from the "x-user" metadata (gRPC's
// headers), as the HTTP API reads X-User.
func user(ctx context.Context) (string, error) {
	if md, ok := metadata.FromIncomingContext(ctx); ok {
		if u := md.Get("x-user"); len(u) == 1 && u[0] != "" {
			return u[0], nil
		}
	}
	return "", status.Error(codes.Unauthenticated, "x-user metadata required")
}
```

`toStatus` is the one place domain errors become gRPC status codes. Clients switch on the code, never on the message, so the choice of code is the API: `AlreadyExists` means someone has the seat, `FailedPrecondition` means you don't hold it, and `Unavailable` tells a client this is worth retrying elsewhere:

```go noverify title="cinema/internal/grpcapi/grpcapi.go · lines 52–73"
// toStatus maps domain errors to gRPC status codes. The code is what the
// client's code switches on; the message is for people.
func toStatus(err error) error {
	switch {
	case err == nil:
		return nil
	case errors.Is(err, booking.ErrTaken):
		return status.Error(codes.AlreadyExists, err.Error())
	case errors.Is(err, booking.ErrNotHolder):
		return status.Error(codes.FailedPrecondition, err.Error())
	case errors.Is(err, booking.ErrNoSeat):
		return status.Error(codes.NotFound, err.Error())
	case errors.Is(err, booking.ErrTooManyHolds):
		return status.Error(codes.ResourceExhausted, err.Error())
	case errors.Is(err, context.DeadlineExceeded):
		return status.Error(codes.DeadlineExceeded, err.Error())
	case errors.Is(err, context.Canceled):
		return status.Error(codes.Canceled, err.Error())
	default: // the store failed: worth retrying elsewhere or later
		return status.Error(codes.Unavailable, err.Error())
	}
}
```

The unary methods are three lines each: find the caller, call the store, translate the error. Everything that's specific to seats lives in `booking`, so the HTTP and gRPC APIs can't disagree about the rules:

```go noverify title="cinema/internal/grpcapi/grpcapi.go · lines 75–105"

func (s *Server) ListSeats(ctx context.Context, r *cinemav1.ListSeatsRequest) (*cinemav1.ListSeatsResponse, error) {

		return nil, toStatus(err)
	}

```

`WatchSeats` is a **server-streaming** method: one request, many responses. It checks the seat map every `WatchEvery` and sends only when it changed. The `select` has three ways out: the next tick, the client going away (`ctx.Done()`), and `Drain`, which ends the stream with `Unavailable` so the client reconnects to another replica instead of holding up shutdown for 20 s:

```go noverify title="cinema/internal/grpcapi/grpcapi.go · lines 107–133"
// WatchSeats sends the seat map now, and again every time it changes,
// until the client goes away.
func (s *Server) WatchSeats(r *cinemav1.WatchSeatsRequest, stream cinemav1.SeatService_WatchSeatsServer) error {
	ctx := stream.Context()
	tick := time.NewTicker(s.WatchEvery)
	defer tick.Stop()
	var last []booking.Seat
	for {
		seats, err := s.store.Seats(ctx, r.GetMovie())
		if err != nil {
			return toStatus(err)
		}
		if last == nil || !slices.Equal(seats, last) {
			if err := stream.Send(&cinemav1.WatchSeatsResponse{Seats: toProto(seats)}); err != nil {
				return err
			}
			last = seats
		}
		select {
		case <-tick.C:
		case <-ctx.Done():
			return nil
		case <-s.draining:
			return status.Error(codes.Unavailable, "server is shutting down; reconnect")
		}
	}
}
```

`HoldGroup` is **client-streaming**: the client sends seats one by one, and gets one answer when it's done. `io.EOF` from `Recv` is the client saying 'that's all', and `SendAndClose` sends the single reply:

```go noverify title="cinema/internal/grpcapi/grpcapi.go · lines 135–157"
// HoldGroup holds each seat the client streams, and answers once the
// client has sent them all.
func (s *Server) HoldGroup(stream cinemav1.SeatService_HoldGroupServer) error {
	u, err := user(stream.Context())
	if err != nil {
		return err
	}
	resp := &cinemav1.HoldGroupResponse{}
	for {
		r, err := stream.Recv()
		if errors.Is(err, io.EOF) {
			return stream.SendAndClose(resp)
		}
		if err != nil {
			return err
		}
		if err := s.store.Hold(stream.Context(), r.GetMovie(), r.GetSeat(), u, s.hold); err != nil {
			resp.Failed = append(resp.Failed, r.GetSeat())
			continue
		}
		resp.Held = append(resp.Held, r.GetSeat())
	}
}
```

`BoxOffice` is **bidirectional**: requests and answers flow independently. Each request is handled in its own goroutine, so a slow hold doesn't delay the next, and answers can come back in a different order than the requests. A stream's `Send` isn't safe for concurrent use, hence `sendMu`:

```go noverify title="cinema/internal/grpcapi/grpcapi.go · lines 159–183"
// BoxOffice handles each request as it arrives, concurrently, and sends
// each answer as soon as it's ready: answers can overtake each other.
func (s *Server) BoxOffice(stream cinemav1.SeatService_BoxOfficeServer) error {
	var sendMu sync.Mutex // Send isn't safe for concurrent use
	var wg sync.WaitGroup
	defer wg.Wait()
	for {
		r, err := stream.Recv()
		if errors.Is(err, io.EOF) {
			return nil
		}
		if err != nil {
			return err
		}
		wg.Go(func() {
			resp := &cinemav1.BoxOfficeResponse{Seat: r.GetSeat(), Customer: r.GetCustomer(), Held: true}
			if err := s.store.Hold(stream.Context(), r.GetMovie(), r.GetSeat(), r.GetCustomer(), s.hold); err != nil {
				resp.Held, resp.Error = false, err.Error()
			}
			sendMu.Lock()
			defer sendMu.Unlock()
			_ = stream.Send(resp) // if the client is gone, Recv reports it
		})
	}
}
```

Finally, the conversion from the domain's seat to the generated protobuf message. The domain type never imports protobuf; this function is the only place the two meet:

```go noverify title="cinema/internal/grpcapi/grpcapi.go · lines 185–198"
func toProto(seats []booking.Seat) []*cinemav1.Seat {
	out := make([]*cinemav1.Seat, len(seats))
	for i, s := range seats {
		st := cinemav1.SeatStatus_SEAT_STATUS_FREE
		switch s.Status {
		case booking.Held:
			st = cinemav1.SeatStatus_SEAT_STATUS_HELD
		case booking.Booked:
			st = cinemav1.SeatStatus_SEAT_STATUS_BOOKED
		}
		out[i] = &cinemav1.Seat{Id: s.ID, Status: st, User: s.User}
	}
	return out
}
```

It's the chapter 17 layout paying off: the gRPC package is a second adapter on the same port (`booking.Store`), and the domain didn't change. Two details:

- **Metadata** is gRPC's name for headers. The caller's customer arrives as `x-user` metadata, like the HTTP API's `X-User` header.
- **`toStatus`** maps domain errors to gRPC **status codes**. Clients switch on the code, not the message: `AlreadyExists` for a taken seat, `NotFound` for a seat that doesn't exist, `FailedPrecondition` for confirming a seat you don't hold, and `Unavailable` for a failing store, the code gRPC clients and proxies treat as safe to retry.

## Four Kinds of Call

*Stop 3 of 6.*

`grpcdemo` calls the service each way the schema defines. All four share one client, `grpc.NewClient`, which holds one HTTP/2 connection, and each call or stream is an HTTP/2 **stream** multiplexed on it.

### Step 1: unary, server streaming

`Hold` is **unary**: one request, one response, like the HTTP API. `WatchSeats` is **server streaming**: one request, then the server sends the seat map every time it changes, until the client goes away. While it watches, `grpcdemo` holds three seats as other customers:

```text
$ grpcdemo watch
 0.032s  update: 40 seats, held: []
 0.333s  (someone holds A1: OK)
 0.433s  update: 40 seats, held: [A1]
 0.835s  (someone holds A2: OK)
 1.032s  update: 40 seats, held: [A1 A2]
 1.536s  (someone holds B5: OK)
 1.633s  update: 40 seats, held: [A1 A2 B5]
 2.001s  stream ended: DeadlineExceeded
```

Each hold is followed by an update about 0.1 s later (the server checks for changes every 200 ms). No polling on the client, and the stream ended cleanly at the client's 2 s deadline. With the HTTP API, a watcher would request the whole seat map again and again; chapter 8's page used server-sent events for the same reason.

### Step 2: client streaming

`HoldGroup` is **client streaming**: a family of four sends its seats one by one, and gets one answer when it has sent them all. A1 was taken by the watch demo a moment earlier:

```text
$ grpcdemo group      # a party of four; A1 is already held by someone else

 0.075s  send C4
 0.075s  send A1
 0.075s  send C5
 0.077s  answer: held [C3 C4 C5], failed [A1]
```

### Step 3: bidirectional

`BoxOffice` is a terminal's session: requests go out as walk-ins arrive, and each answer comes back as soon as its hold finishes, in either order. With Redis replies taking 150 ms ± 140 ms (Toxiproxy's jitter), and two walk-ins asking for D1:

## Deadlines and Failures

*Stop 4 of 6.*

### Step 1: a deadline crosses the wire

Every gRPC call can carry a deadline. The client sets it on the context; gRPC sends the time remaining as the `grpc-timeout` header; the server's handler gets a context with that deadline. With Redis replying after 2 s and the client allowing 150 ms (the last lines of the `redisdemos` run above):

```text
Hold with a 150ms deadline: DeadlineExceeded after 152ms
grpc /cinema.v1.SeatService/Hold Canceled in 100.824ms (deadline on arrival: 99ms)
```

The client gave up at 152 ms. The **server** gave up too, 100.8 ms after the call arrived: its context expired and cancelled the Redis call (chapter 12's `ContextTimeoutEnabled` at work), so it stopped spending a goroutine and a connection on an answer nobody would read. Without a deadline on the wire, the server would have waited the full 2 s.

Note the arrival time: **99 ms left of 150**. It was the program's first call, and `grpc.NewClient` connects lazily, so dialing the server came out of the first call's budget. A service's first request after starting pays for its connections; create clients at startup and, if the first call is latency-critical, warm them.

### Step 2: one panic, every caller

The logging interceptor above is one of two in the service. The other exists because of this:

```go noverify
package grpcapi

import (
	"context"
	"log"
	"runtime/debug"
	"time"

	"google.golang.org/grpc"
	"google.golang.org/grpc/codes"
	"google.golang.org/grpc/status"
)

// Recover turns a panic in a handler into codes.Internal for that one
// call. Without it, a panic in any handler kills the whole process, and
// every other caller's calls and streams with it.
func Recover(logger *log.Logger) (grpc.UnaryServerInterceptor, grpc.StreamServerInterceptor) {
	unary := func(ctx context.Context, req any, info *grpc.UnaryServerInfo, h grpc.UnaryHandler) (resp any, err error) {
		defer func() {
			if p := recover(); p != nil {
				logger.Printf("panic in %s: %v\n%s", info.FullMethod, p, debug.Stack())
				err = status.Error(codes.Internal, "internal error")
			}
		}()
		return h(ctx, req)
	}
	stream := func(srv any, ss grpc.ServerStream, info *grpc.StreamServerInfo, h grpc.StreamHandler) (err error) {
		defer func() {
			if p := recover(); p != nil {
				logger.Printf("panic in %s: %v\n%s", info.FullMethod, p, debug.Stack())
				err = status.Error(codes.Internal, "internal error")
			}
		}()
		return h(srv, ss)
	}
	return unary, stream
}

// Log records each unary call's method, status code and duration.
func Log(logger *log.Logger) grpc.UnaryServerInterceptor {
	return func(ctx context.Context, req any, info *grpc.UnaryServerInfo, h grpc.UnaryHandler) (any, error) {
		start := time.Now()
		deadline := "none"
		if d, ok := ctx.Deadline(); ok { // set by the client's deadline, sent as grpc-timeout
			deadline = time.Until(d).Round(time.Millisecond).String()
		}
		resp, err := h(ctx, req)
		logger.Printf("grpc %s %s in %v (deadline on arrival: %s)", info.FullMethod, status.Code(err), time.Since(start).Round(time.Microsecond), deadline)
		return resp, err
	}
}
```

`panicdemo` runs a SeatService whose store has a real kind of bug (a map that was never created) on `ListSeats("dune")`, while another client watches inception's seats:

```text
== panicdemo serve 
 0.00s  another client is watching inception's seats

 0.01s  ListSeats(inception): Unavailable

  server stderr, first 3 lines:
    panic: assignment to entry in nil map
    
    goroutine 4 [running]:
== panicdemo serve -recover

 0.00s  ListSeats(dune): Internal
 0.00s  ListSeats(inception): OK

  server: still running
  server stderr, first 3 lines:
    panic in /cinema.v1.SeatService/ListSeats: assignment to entry in nil map

```

Without the interceptor, **the whole server exited**: the bad call, a good call made right after it, and the other client's stream all got `Unavailable`. `net/http` recovers panics in handlers (and logs them); **grpc-go does not**, and an unrecovered panic in any goroutine ends a Go program. With `Recover`, the bad call got `Internal`, the next call succeeded, and the watcher never noticed.

### Step 1: requests per second

### Step 2: the stream that never ends

`app.Run` stops gRPC with `GracefulStop`, which waits for in-flight calls **and streams**. A `WatchSeats` stream only ends when its client leaves:

```text
SIGTERM with a WatchSeats stream open: the service exited after 20.0 s
the watcher saw: ERROR:   Code: Unavailable   Message: closing transport due to: connection error: desc = "error reading from server: EOF", received prior goaway: code: NO_ERROR, debug data: "graceful_stop" 
cinema on http://127.0.0.1:18100 (grpc 127.0.0.1:19100, admin 127.0.0.1:16100), store=locked
shutting down: terminated signal received
stopped
```

Twenty seconds: the whole shutdown budget, after which `stopGRPC` fell back to `Stop` and cut the stream. Every deploy of a service with a watcher attached would take 20 s per instance. The fix is to end long-lived streams deliberately: `Drain` makes every `WatchSeats` return `Unavailable` ("server is shutting down; reconnect"), which a well-behaved client treats as a cue to reconnect, to another replica. `Run` calls it right after readiness fails:

```go noverify
// app.go, lines 148–175
		api.Draining.Store(true) // 1. readiness fails: stop receiving new traffic
		seats.Drain()            //    and gRPC watchers are told to reconnect elsewhere
		sctx, cancel := context.WithTimeout(context.WithoutCancel(ctx), 20*time.Second)
		defer cancel()
		err := srv.Shutdown(sctx) // 2. finish in-flight requests, HTTP and gRPC
		err = errors.Join(err, stopGRPC(sctx, grpcSrv), adminSrv.Shutdown(sctx))
		err = errors.Join(err, closeRedis(rdb)) // 3. only now close what they used
		logger.Printf("stopped")
		return err
	})
	return g.Wait()
}

// stopGRPC waits for in-flight calls and streams to finish, but no longer
// than ctx allows: GracefulStop alone would wait forever for a stream
// that never ends (WatchSeats).
func stopGRPC(ctx context.Context, s *grpc.Server) error {
	done := make(chan struct{})
	go func() { s.GracefulStop(); close(done) }()
	select {
	case <-done:
		return nil
	case <-ctx.Done():
		s.Stop() // cancels the remaining streams
		<-done
		return nil
	}
}
```

```text
SIGTERM with a WatchSeats stream open: the service exited after 0.0 s
the watcher saw: ERROR:   Code: Unavailable   Message: server is shutting down; reconnect 
cinema on http://127.0.0.1:18100 (grpc 127.0.0.1:19100, admin 127.0.0.1:16100), store=locked
shutting down: terminated signal received
stopped
```

**From 20.0 s to under 0.1 s**, and the watcher was told why.

## Changing the Schema

*Stop 6 of 6.*

### Step 1: what buf breaking catches

Services are deployed one at a time, so for a while old clients talk to new servers and new clients to old ones. Three plausible changes to the cinema's schema: customers get numeric IDs (`string user = 3` becomes `int64 user_id = 3`), `movie` is renamed `film` in `HoldRequest`, and `HoldGroupResponse.failed` is removed as unused. `buf breaking` compares the working copy with the committed schema:

```text
$ buf breaking --against '.git#branch=layout'
proto/cinema/v1/seats.proto:38:3:Field "3" with name "user_id" on message "Seat" changed option "json_name" from "user" to "userId".
proto/cinema/v1/seats.proto:38:3:Field "3" with name "user_id" on message "Seat" changed type from "string" to "int64". See https://developers.google.com/protocol-buffers/docs/proto3#updating for wire compatibility rules and https://developers.google.com/protocol-buffers/docs/proto3#json for JSON compatibility rules.
proto/cinema/v1/seats.proto:38:9:Field "3" on message "Seat" changed name from "user" to "user_id".
proto/cinema/v1/seats.proto:42:3:Field "1" with name "film" on message "HoldRequest" changed option "json_name" from "movie" to "film".
proto/cinema/v1/seats.proto:42:10:Field "1" on message "HoldRequest" changed name from "movie" to "film".
proto/cinema/v1/seats.proto:77:1:Previously present field "2" with name "failed" on message "HoldGroupResponse" was deleted without reserving the name "failed".
proto/cinema/v1/seats.proto:77:1:Previously present field "2" with name "failed" on message "HoldGroupResponse" was deleted without reserving the number "2".

```

Seven findings (the config asks for `WIRE_JSON`: compatibility for both the binary encoding and JSON):

- **Field 3's type changed**: incompatible on the wire.
- **Renames** (`user` → `user_id`, `movie` → `film`) are harmless on the binary wire, where only numbers travel, but break JSON, where the names *are* the keys, so they matter to anything using `protojson` or a gateway.
- **A deleted field without `reserved`**: a later change could reuse number 2 for something else, and old clients would read the new field as `failed`. `reserved 2; reserved "failed";` prevents that forever.

### Step 2: what an old client actually does

Why is a type change "incompatible" if nothing crashes? The bytes a new server sends for `Seat{id: "A7", status: HELD, user_id: 42}`, decoded by today's generated code:

```text
bytes:        0a 02 41 37 10 02 18 2a
decode error: <nil>
old client:   id="A7" status=SEAT_STATUS_HELD user=""
kept as unknown fields: 18 2a
```

**No error.** Field 3 arrived as a number where the old code expects a string, so the decoder kept it aside as an unknown field (`18 2a`: field 3, varint, 42), and `user` is empty. The seat is held by nobody the old client can name, and nothing logged a problem. That's the worst kind of incompatibility: silent. The safe change is additive: add `int64 user_id = 4;`, fill both for a while, move clients over, then remove `user` with `reserved 3; reserved "user";`, the expand-contract pattern Part 1 chapter 18 uses for database columns.

`buf breaking --against '.git#branch=main'` belongs in the CI pipeline from chapter 15, next to `go generate`'s diff check, so these changes are caught in review, not in production.

<Exercise n={5} title="A gateway for browsers" level="hard">

The box office wants a browser page for the same `SeatService`. Compare three options: grpc-gateway (generated HTTP/JSON handlers from annotations in the proto), gRPC-Web (a proxy or middleware translating for browsers), and keeping the hand-written HTTP API. What does each cost?

<Solution>

**grpc-gateway** generates a reverse proxy from `google.api.http` annotations: one schema, JSON for browsers, but another generator, annotations in every method, and JSON field names become part of your compatibility surface (stop 6's renames now break the browser). **gRPC-Web** keeps protobuf on the wire to the browser (smaller, typed), but needs a translating proxy (Envoy) or middleware, a JavaScript client generated from the proto, and it supports server streaming but not client or bidirectional streaming. **The hand-written API** (what the cinema has) costs duplicate code, but lets the browser API and the service API evolve separately, which is often what you want: customers and services have different needs. Connect-go is a fourth option: one handler that serves gRPC, gRPC-Web and a simple HTTP/JSON protocol together.

</Solution>

</Exercise>

// encodeTimeout writes d as a grpc-timeout value: the finest unit whose
// value fits in 8 digits, rounding up (a deadline must never get earlier).
// d <= 0 encodes as "0n".
func encodeTimeout(d time.Duration) string {
	return strconv.FormatInt(d.Milliseconds(), 10) + "m"
}

// 1–8 digits followed by one of the six units.
func decodeTimeout(s string) (time.Duration, error) {

<Recap>

- **Schema first**: buf lint rejected ten things in a first draft; with `FREE = 0`, an unset status decoded as FREE, so zero must be `…_UNSPECIFIED`. Generators pinned in the service's `go.mod`, heavy tools (buf, grpcurl) in `tools/go.mod`: 15 requirements instead of 112.
- **Same domain, second transport**: `grpcapi` is another adapter on `booking.Store`, with metadata for identity and status codes the caller can act on (`AlreadyExists`, `NotFound`, `Unauthenticated`, `Unavailable`).
- **Four call types**, one HTTP/2 connection: unary Hold, a WatchSeats stream pushing changes, HoldGroup's client stream, and a BoxOffice session where answers overtook each other (walk-in-4 got D1 before walk-in-1).
- **Deadlines travel**: a 150 ms client deadline arrived with 99 ms left (the first call paid for connecting), and the server cancelled its Redis call at 100.8 ms. **Panics don't recover by themselves** in grpc-go: one nil-map bug took down every caller until a recovery interceptor made it one `Internal`.

A watch stream held shutdown for 20.0 s; draining streams first: under 0.1 s. The benchmark also exposed `Status` missing `UnmarshalText`.
- **Schema changes**: `buf breaking` flagged a retyped field, renames (JSON) and an unreserved deletion. The retyped field decoded with no error and an empty value in an old client. Evolve by adding fields, and reserve what you remove.

</Recap>
