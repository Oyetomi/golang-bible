## Scheduled Work

Let me paint the picture, sport. You're on the payments team. Every night at 2 a.m. your service has to reconcile your internal ledger against your payment processor's settlement files — compare every transaction, flag mismatches, and wake up the on-call engineer if the books don't balance. It runs on a schedule. It runs on a wall clock. And if it fires more than once you've got a very awkward morning conversation.

We're going to start simple — in-process scheduling — before we earn the right to talk about the distributed version.

<Define term="Cron / Ticker (scheduled work)" since="Time, Clocks &amp; Timers (Part 2)">
A **ticker** fires at a fixed interval regardless of wall-clock time — "every 5 minutes from when the process started." A **cron** fires at a wall-clock moment — "every day at 02:00 UTC" — using a Unix cron expression. Use a ticker for polling loops; use a cron when the schedule must align to a real clock. Both run inside the process and fire on every replica unless you add coordination (see leader election below).
</Define>

### time.Ticker: fixed intervals

A `time.Ticker` fires on a fixed interval, independent of when the last tick was handled. It's the heartbeat of a polling loop.

```go title="ticker.go"
package main

import (
	"context"
	"fmt"
	"time"
)

// reconcile simulates a ledger reconciliation job.
func reconcile(ctx context.Context) {
	fmt.Println("reconciling ledger:", time.Now().Format(time.RFC3339))
	// imagine hitting a DB and external API here
}

func main() {
	ctx, cancel := context.WithCancel(context.Background())
	defer cancel()

	ticker := time.NewTicker(5 * time.Second)
	defer ticker.Stop()

	for {
		select {
		case <-ctx.Done():
			fmt.Println("ticker stopped cleanly")
			return
		case t := <-ticker.C:
			fmt.Println("tick at", t.Format(time.RFC3339))
			reconcile(ctx)
		}
	}
}
```

<Callout kind="warn" title="The drift gotcha">

A `time.Ticker` fires every N nanoseconds from the moment it was created, regardless of how long your handler takes. If `reconcile` takes 4s and your ticker fires every 5s, you get 1s of idle time — fine. But if reconcile takes 6s, the *next* tick fired during that run is dropped (the channel's one-slot buffer is already full), so the effective interval is 11s. For jobs where the wall-clock schedule matters (run at 02:00 exactly, not "roughly every 24 hours"), use `robfig/cron` instead.

</Callout>

### robfig/cron: wall-clock schedules

`time.Ticker` is for intervals ("every 5 minutes"). `robfig/cron` is for wall-clock schedules ("every day at 02:00 UTC"). It speaks a Unix cron expression and parks execution until the next scheduled wall-clock moment.

```go title="cron_setup.go"
// NOTE: requires github.com/robfig/cron/v3 — not runnable in playground.
package main

import (
	"fmt"
	"time"

	"github.com/robfig/cron/v3"
)

func main() {
	c := cron.New(
		// WithSeconds enables the 6-field expression (seconds field first).
		cron.WithSeconds(),
	)

	// "0 0 2 * * *" — at 02:00:00 UTC every day, every month, every weekday.
	_, err := c.AddFunc("0 0 2 * * *", func() {
		fmt.Println("nightly reconciliation at", time.Now().UTC())
		// call reconcile(ctx) here — but we need an app-level ctx, not a
		// per-request one. Inject it via closure, not a global.
	})
	if err != nil {
		panic(err)
	}

	c.Start()            // starts in its own goroutine
	defer c.Stop()       // blocks until any running job finishes — safe shutdown

	select {} // wait forever (in a real service: wait for SIGTERM)
}
```

## Job Queues

<Define term="Job Queue (Asynq / River)" since="Messaging &amp; Pub/Sub Foundations (Part 3)">
A **job queue** is a durable store of units of work ("jobs") that producers enqueue and workers consume asynchronously. The HTTP handler enqueues quickly and returns; a separate worker process picks up the job, executes it, and acknowledges it. If the worker crashes before the ack, the job reappears for retry — that durability is what makes the queue more than just a channel. **Asynq** backs jobs in Redis; **River** stores them in a Postgres table inside your own database, enabling transactional enqueue. Without a queue, slow or flaky work blocks your HTTP response and drops work on crashes.
</Define>

Now we get to the good stuff. Here's the scenario: a user completes a payment. Your handler records the transaction in the database. It should *also* send a receipt email and notify your fraud-detection pipeline — but those operations are slow, flaky, and if they block the HTTP response the user is sitting there watching a spinner while your email provider has a hiccup. The answer is a **job queue**: enqueue the work as a small serialized record, return the `200` immediately, and let a separate worker process it asynchronously, with retries.

### Asynq — Redis-backed job queue

**Asynq** (`github.com/hibiken/asynq`) is the de-facto Redis-backed job queue for Go. Workers long-poll a sorted set of pending tasks and execute them with configurable concurrency. It gives you delayed jobs, scheduled cron, per-queue priorities, and a built-in web UI (Asynqmon).

```go title="asynq_enqueue.go"
// NOTE: requires Redis + github.com/hibiken/asynq — not runnable in playground.
package payments

import (
	"context"
	"encoding/json"
	"fmt"

	"github.com/hibiken/asynq"
)

const TypeReceiptEmail = "email:receipt"

// ReceiptPayload is the job's serialized payload.
// Keep it small and self-contained — IDs, not full objects.
type ReceiptPayload struct {
	TransactionID string
	UserEmail     string
	AmountCents   int64
}

// EnqueueReceipt pushes a receipt email job onto the queue.
// Called from the HTTP handler after a successful payment write.
func EnqueueReceipt(ctx context.Context, client *asynq.Client, p ReceiptPayload) error {
	payload, err := json.Marshal(p)
	if err != nil {
		return fmt.Errorf("marshal receipt payload: %w", err)
	}
	task := asynq.NewTask(TypeReceiptEmail, payload,
		asynq.MaxRetry(5),             // retry up to 5 times
		asynq.Timeout(30*time.Second), // per-execution timeout
	)
	info, err := client.EnqueueContext(ctx, task)
	if err != nil {
		return fmt.Errorf("enqueue receipt task: %w", err)
	}
	slog.InfoContext(ctx, "receipt job enqueued",
		"id", info.ID,
		"queue", info.Queue,
	)
	return nil
}
```

```go title="asynq_worker.go"
// NOTE: requires Redis + github.com/hibiken/asynq — not runnable in playground.
package payments

import (
	"context"
	"encoding/json"
	"fmt"

	"github.com/hibiken/asynq"
)

// HandleReceiptEmail is the worker handler for TypeReceiptEmail jobs.
// It MUST be idempotent — Asynq is at-least-once; this can run twice.
func HandleReceiptEmail(ctx context.Context, t *asynq.Task) error {
	var p ReceiptPayload
	if err := json.Unmarshal(t.Payload(), &p); err != nil {
		return fmt.Errorf("unmarshal receipt payload: %w", err) // won't retry a bad payload
	}

	// Idempotency: check if we already sent this receipt before calling the
	// email provider. A Redis SET NX or a DB unique constraint works fine.
	alreadySent, err := markReceiptSent(ctx, p.TransactionID)
	if err != nil {
		return fmt.Errorf("check idempotency: %w", err)
	}
	if alreadySent {
		slog.InfoContext(ctx, "receipt already sent, skipping", "tx_id", p.TransactionID)
		return nil // returning nil acks the job; duplicate is absorbed
	}

	return sendEmail(ctx, p.UserEmail, p.AmountCents)
}
```

### Sending the actual email — `net/smtp`

The handler above bottoms out in `sendEmail`, which we kept abstract. Here it is for real — and it's the *same* mailer the verification email from **Auth & API Design (Part 1)** needs. Every transactional message at Meridian — verify-address, receipt, settlement notice — funnels through one `Mailer`:

```go title="mailer.go"
// NOTE: dials a network — not runnable in the playground.
package payments

import (
	"context"
	"fmt"
	"net/smtp"
)

// Mailer submits messages to a provider's SMTP endpoint (SES, Postmark, …).
type Mailer struct {
	addr string // "smtp.provider.com:587"
	auth smtp.Auth
	from string
}

func NewMailer(host, port, user, pass, from string) *Mailer {
	return &Mailer{
		addr: host + ":" + port,
		auth: smtp.PlainAuth("", user, pass, host),
		from: from,
	}
}

// Send delivers one message. smtp.SendMail negotiates STARTTLS on the
// submission port (587) automatically. Note: net/smtp predates context — it
// ignores ctx and can't be cancelled mid-send. That alone is why most teams
// reach for a provider's context-aware HTTP SDK in production.
func (m *Mailer) Send(ctx context.Context, to, subject, body string) error {
	msg := fmt.Sprintf(
		"From: %s\r\nTo: %s\r\nSubject: %s\r\nMIME-Version: 1.0\r\n"+
			"Content-Type: text/plain; charset=UTF-8\r\n\r\n%s\r\n",
		m.from, to, subject, body)
	if err := smtp.SendMail(m.addr, m.auth, m.from, []string{to}, []byte(msg)); err != nil {
		return fmt.Errorf("smtp send to %s: %w", to, err)
	}
	return nil
}

// sendEmail formats the receipt. Money is integer cents — format to dollars
// only at the very edge, on the way out. Never store or compute money as float.
func sendEmail(ctx context.Context, mailer *Mailer, to string, amountCents int64) error {
	subject := "Your Meridian payment receipt"
	body := fmt.Sprintf("We received your payment of $%d.%02d. Thank you.",
		amountCents/100, amountCents%100)
	return mailer.Send(ctx, to, subject, body)
}
```

The handler holds its `*Mailer` as a dependency (inject it via a handler struct — `mux.HandleFunc(TypeReceiptEmail, h.Handle)` — not a package global). The reason all of this lives behind a queue instead of inline in the payment handler: **sending mail is slow, flaky, and third-party.** Block the HTTP request on it and your checkout p99 becomes your mail provider's p99.

But "behind a queue" means **at-least-once** — the handler *will* sometimes run twice (a retry after a timeout that actually delivered). So the send must be idempotent: record that this receipt went out, and a re-run skips it. That dedup is the part you can actually run:

<GoPlayground>

```go
package main

import (
	"fmt"
	"sync"
)

// receiptBody formats integer cents into a dollar string at the edge.
func receiptBody(amountCents int64) string {
	return fmt.Sprintf("We received your payment of $%d.%02d. Thank you.",
		amountCents/100, amountCents%100)
}

// sentLedger stands in for a Redis SET NX or a DB unique constraint: it records
// which transactions we've already emailed, so an at-least-once retry that
// re-runs the handler does NOT bill the customer's inbox twice.
type sentLedger struct {
	mu   sync.Mutex
	seen map[string]bool
}

func (s *sentLedger) markSent(txID string) (already bool) {
	s.mu.Lock()
	defer s.mu.Unlock()
	if s.seen[txID] {
		return true
	}
	s.seen[txID] = true
	return false
}

func main() {
	ledger := &sentLedger{seen: map[string]bool{}}
	// The SAME receipt job runs twice — a retry after a delivery timeout.
	for attempt := 1; attempt <= 2; attempt++ {
		if ledger.markSent("tx_42") {
			fmt.Printf("attempt %d: tx_42 already sent — skip (idempotent)\n", attempt)
			continue
		}
		fmt.Printf("attempt %d: sending → %s\n", attempt, receiptBody(1999))
	}
}
```

</GoPlayground>

<Callout kind="note" title="Where retries, backoff, and dead-letters come in">

`smtp.SendMail` returning an error is a *transient* failure most of the time — the provider hiccuped. You don't drop the receipt; you let the queue retry it with exponential backoff, and after max attempts it lands in the dead-letter queue for a human. That machinery is the next section — the email send is precisely the job it's built for.

</Callout>

**On the job:** the receipt and the verification email are the same job shape, but their failure modes differ. A dropped receipt is a support ticket; a dropped verification email is a lost signup. For the verification email, surface a "resend link" button so a transient failure isn't a dead end the user can't escape — the queue retries automatically, but give the human an escape hatch too.

### River — Postgres-backed job queue

**River** (`github.com/riverqueue/river`) stores jobs in a Postgres table inside your application's own database. You get ACID guarantees around enqueue (enqueue inside the same transaction as your business write — the job only exists if the payment row does), Postgres-native job inspection, and zero new infrastructure if you're already on Postgres.

```go title="river_enqueue.go"
// NOTE: requires Postgres + github.com/riverqueue/river — not runnable in playground.
package payments

import (
	"context"

	"github.com/riverqueue/river"
)

// ReceiptArgs implements river.JobArgs — the job's typed payload.
type ReceiptArgs struct {
	TransactionID string `json:"transaction_id"`
	UserEmail     string `json:"user_email"`
	AmountCents   int64  `json:"amount_cents"`
}

func (ReceiptArgs) Kind() string { return "receipt_email" }

// EnqueueReceiptTx enqueues a receipt job inside an existing Postgres transaction.
// If the outer transaction rolls back, the job is never created. No phantom jobs.
func EnqueueReceiptTx(ctx context.Context, tx pgx.Tx, client *river.Client[pgx.Tx], args ReceiptArgs) error {
	_, err := client.InsertTx(ctx, tx, args, &river.InsertOpts{
		MaxAttempts: 5,
	})
	return err
}
```

<ConceptGrid cols={2}>
  <ConceptCard label="Asynq (Redis)">Fast, fire-and-forget style. Sub-millisecond enqueue. Best when you already have Redis and want minimal Postgres load. At-least-once via visibility timeout.</ConceptCard>
  <ConceptCard label="River (Postgres)">Transactional enqueue — the job only exists if your business write commits. Great for payments where the job and the row must be atomic. Uses `SKIP LOCKED` for worker polling.</ConceptCard>
  <Gotcha>Neither Asynq nor River gives you exactly-once processing — they both guarantee at-least-once. Your handler WILL run more than once on retries or network partitions. Design every handler to be idempotent from day one, not as an afterthought.</Gotcha>
</ConceptGrid>

<UnderTheHood title="How Redis at-least-once actually works (visibility timeout + ZADD)">

Asynq stores jobs in Redis sorted sets (ZSETs) keyed by state: `asynq:{queue}:pending`, `asynq:{queue}:active`, `asynq:{queue}:scheduled`, and `asynq:{queue}:retry`. When a worker claims a job, Asynq atomically moves the task record from the `pending` ZSET into the `active` ZSET and records a **deadline** — the `score` in the ZSET is a Unix timestamp meaning "if this job is still active past this time, it crashed without an ack." A background goroutine (`reaper`) scans the `active` set for expired entries and moves them back to `pending` (or to `retry` if `MaxRetry` is exhausted, or to `dead` if attempts are exceeded). The worker calls `asynq.Heartbeat` during long jobs to extend the deadline and prevent false recovery. All of the state transitions use Lua scripts executed atomically on the Redis server — no TOCTOU races between worker discovery and reaping.

River uses Postgres's `SELECT ... FOR UPDATE SKIP LOCKED` on a `river_jobs` table. Each worker issues a single query that finds unlocked jobs in state `available`, locks them, and flips their state to `running` in one atomic statement. The row-level lock prevents two workers from claiming the same job. If the worker crashes without committing, Postgres releases the lock and a background rescuer query marks overdue `running` jobs back to `available`. River uses Go 1.24+ generics so your worker handler is typed directly against your `JobArgs` struct — no `interface{}` marshaling boilerplate.

Both systems guarantee **at-least-once** by relying on an explicit acknowledgment: the job is only permanently removed when the worker commits success. Skipping the ack (a panic, a kill signal, a timeout) always results in a retry.

## Retries & Resilience

<Define term="Retryable Job (backoff + max attempts)">
A **retryable job** is a job whose handler, on failure, is automatically re-queued after a delay instead of being dropped. The delay grows exponentially on each attempt (**exponential backoff**) to avoid hammering a recovering downstream. **Max attempts** caps the total tries so a permanently broken job doesn't loop forever. Without retries, a transient email-provider hiccup silently drops the receipt and the user never hears from you.
</Define>

Your email provider had a hiccup. The fraud API was behind a gateway timeout. These things happen in production every single day. A job queue without retries is just a buffer — a job queue *with* retries is an actual resilience layer.

### Backoff, max-attempts, and dead letters

When a job handler returns a non-nil error, the queue schedules a retry. The retry should not happen immediately (you'd hammer a broken service), and it should not retry forever (a truly broken job shouldn't clog the queue). The standard pattern is **exponential backoff with jitter**.

```go title="backoff.go"
package jobs

import (
	"math/rand/v2"
	"time"
)

// RetryDelay returns the delay before the nth retry attempt (1-indexed).
// Base is 1s, max cap is 1 hour. Jitter ±20% prevents thundering herds.
func RetryDelay(attempt int) time.Duration {
	base := time.Second
	exp := time.Duration(1 << min(attempt-1, 10)) // 1s, 2s, 4s … capped at 1024s ≈ 17m
	delay := base * exp
	if delay > time.Hour {
		delay = time.Hour
	}
	// Add ±20% jitter.
	jitter := float64(delay) * 0.2
	delta := time.Duration(rand.Float64()*jitter*2 - jitter)
	return delay + delta
}
```

<Define term="Idempotent Handler (job may run twice)" since="Idempotency &amp; Exactly-Once Semantics (Part 3)">
A **handler is idempotent** if calling it a second time with the same job produces the same outcome as calling it once — no double email, no double charge, no duplicate ledger entry. Job queues are at-least-once: a crash between execution and acknowledgment will re-deliver the job. Every handler must be designed idempotent from day one, not retrofitted later. The standard technique is a **deduplication key**: record that this `txID` was processed; on the second delivery, detect the record and skip the side effect.
</Define>

### Idempotent handlers

Because retries are guaranteed, a job handler WILL run more than once for the same logical job. An idempotent handler produces the same outcome whether it runs once or ten times. There are two practical techniques:

**Deduplication key in your own store:**

```go title="idempotent_handler.go"
package jobs

import (
	"context"
	"fmt"
)

// ReceiptStore is the interface our handler depends on — small, consumer-defined.
type ReceiptStore interface {
	MarkSent(ctx context.Context, txID string) (alreadySent bool, err error)
}

// HandleReceipt sends a receipt email exactly once per transaction ID.
// Safe to call multiple times with the same payload.
func HandleReceipt(ctx context.Context, store ReceiptStore, mailer Mailer, p ReceiptPayload) error {
	// Atomic "mark as sent if not already sent" — returns true if we won the race.
	alreadySent, err := store.MarkSent(ctx, p.TransactionID)
	if err != nil {
		return fmt.Errorf("idempotency check: %w", err)
	}
	if alreadySent {
		// Duplicate delivery — absorb it silently.
		return nil
	}
	return mailer.Send(ctx, p.UserEmail, p.AmountCents)
}
```

<Define term="Dead-Letter Handling (DLQ)">
When a job exhausts all retry attempts the queue moves it to the **dead-letter queue (DLQ)** — a separate holding area, not a trash can. The job's payload is preserved for human inspection. A good DLQ has alerting on depth (non-zero depth = something is systematically broken), tooling for manual re-queue after a root-cause fix, and post-incident test coverage for the failure mode. Ignoring the DLQ means silently dropped work — missed receipts, unprocessed settlements, phantom transactions.
</Define>

### Dead-letter queues

When a job exhausts all retry attempts, it moves to the **dead-letter queue** (DLQ). The DLQ is not a trash can — it is a holding pen for human triage. A good DLQ workflow looks like:

1. Job exceeds `MaxAttempts` → moves to DLQ state.
2. Alerting fires (monitor the DLQ depth as a metric).
3. On-call engineer inspects the payload, fixes the root cause, and manually re-queues or discards the job.
4. Post-incident: add a test for that failure mode.

### Graceful shutdown that drains in-flight jobs

When a SIGTERM arrives (your Kubernetes rolling update, a scale-down), the worst thing you can do is `os.Exit(0)`. A job is running. It's halfway through marking a payment as settled. `os.Exit` kills it mid-flight, the job is not acked, and it reappears for retry in an inconsistent state.

The right move: stop accepting new jobs, finish the ones in flight.

```go title="graceful_shutdown.go"
package main

import (
	"context"
	"log/slog"
	"os"
	"os/signal"
	"syscall"

	"github.com/hibiken/asynq"
)

func main() {
	srv := asynq.NewServer(
		asynq.RedisClientOpt{Addr: "localhost:6379"},
		asynq.Config{
			Concurrency: 10,
			// Give in-flight jobs up to 30s to finish after SIGTERM.
			ShutdownTimeout: 30 * time.Second,
		},
	)

	mux := asynq.NewServeMux()
	mux.HandleFunc(TypeReceiptEmail, HandleReceiptEmail)

	// Start the server in a goroutine.
	go func() {
		if err := srv.Run(mux); err != nil {
			slog.Error("asynq server stopped", "error", err)
			os.Exit(1)
		}
	}()

	// Wait for a shutdown signal.
	quit := make(chan os.Signal, 1)
	signal.Notify(quit, syscall.SIGTERM, syscall.SIGINT)
	<-quit

	slog.Info("shutting down: draining in-flight jobs")
	// Shutdown stops accepting new tasks and waits for in-flight tasks to finish.
	srv.Shutdown()
	slog.Info("all jobs drained, exiting")
}
```

## Distributed Reality

<Define term="Leader Election (singleton across replicas)">
**Leader election** is the process by which a fleet of identical replicas agree that exactly one of them — the **leader** — will perform a privileged action (e.g., run the nightly reconciliation job) while the others stand down. All replicas race to acquire a **lease** — a short-TTL key in a shared store (Redis `SET NX`, etcd, or the Kubernetes Lease API). The winner is leader. If the leader crashes, the TTL expires automatically and the next election fires. Without leader election, a scheduled job on a 3-replica service runs three times simultaneously — triple processing, triple alerts, and a very confused on-call rotation.
</Define>

Here's where the chapter earns its keep, and where a frightening number of engineers stop thinking. You have a nightly reconciliation job. You deploy it. It runs perfectly on one pod. Then you scale to three replicas because traffic is growing. Congratulations. Your reconciliation now fires three times every night, each one trying to reconcile the same ledger against the same settlement files. Three sets of mismatch alerts. Three angry on-call pages. Three very confused engineers. That's not a production system — that's a hazing ritual.

The fix is **leader election**: exactly one replica wins a distributed lock and runs the job. The other replicas see the lock is taken and skip their attempt.

### The lease model

Leader election in a distributed system works by having all replicas race to acquire a **lease** — a key in a shared store (Redis, etcd, or Kubernetes' `coordination.k8s.io/v1 Lease`) with a short TTL. The replica that wins the race owns the lease and is the **leader**. It must **renew** the lease before it expires. If the leader crashes, the lease expires and a new election fires automatically.

```go title="redis_lease.go"
package election

import (
	"context"
	"fmt"
	"time"

	"github.com/redis/go-redis/v9"
)

const (
	leaseKey = "reconciliation:leader"
	leaseTTL = 30 * time.Second
)

// TryAcquireLease attempts to win the leader lease using SET NX EX.
// Returns true if this instance is now the leader.
func TryAcquireLease(ctx context.Context, rdb *redis.Client, instanceID string) (bool, error) {
	ok, err := rdb.SetNX(ctx, leaseKey, instanceID, leaseTTL).Result()
	if err != nil {
		return false, fmt.Errorf("redis SET NX: %w", err)
	}
	return ok, nil
}

// RenewLease extends the lease TTL, keeping this instance as leader.
// Must be called before the TTL expires.
func RenewLease(ctx context.Context, rdb *redis.Client, instanceID string) error {
	// Use a Lua script for atomic check-and-extend: only renew if we still own it.
	script := redis.NewScript(`
		if redis.call("GET", KEYS[1]) == ARGV[1] then
			return redis.call("PEXPIRE", KEYS[1], ARGV[2])
		end
		return 0
	`)
	ttlMs := leaseTTL.Milliseconds()
	res, err := script.Run(ctx, rdb, []string{leaseKey}, instanceID, ttlMs).Int()
	if err != nil {
		return fmt.Errorf("renew lease script: %w", err)
	}
	if res == 0 {
		return fmt.Errorf("lease lost: another instance owns it")
	}
	return nil
}
```

<UnderTheHood title="How a lease-based election actually works (TTL + renewal + fencing)">

**The core primitive is `SET key value NX PX ttl_ms`** — Redis's atomic "set if not exists with expiry." Only one caller in a fleet succeeds; all others get a null reply. This is implemented inside Redis as a single-threaded operation — there is no concurrent write window.

**The TTL is the safety valve.** If the leader process is OOM-killed, the lease expires automatically after `ttl` milliseconds and a new election fires at the next cron tick. This bounds the outage to at most one missed run window — acceptable for "run once" jobs.

**Renewal keeps the leader healthy.** The leader runs a background goroutine that calls the check-and-extend Lua script every `ttl/3` to keep the lease alive. The Lua script is atomic — it only extends the TTL if the current owner matches, preventing a zombie (a slow leader that lost its lease but woke up later) from reclaiming ownership.

**Fencing tokens for correctness.** In high-stakes scenarios (writing to a database under the leader's authority), a race can still happen: the leader takes a long GC pause, the lease expires, a new leader is elected and starts writing, and *then* the original leader wakes up and also writes. The fix is a **fencing token**: a monotonically increasing integer embedded in the lease (Redis INCR). Workers pass the fencing token with every write; the storage layer rejects any write with a token lower than the last seen. As of Go 1.24, you can implement this cleanly with a thin wrapper around `go-redis` and an atomic Lua increment. This is out of scope for this chapter but is explored in the fintech sections of Part 3 when we handle concurrent balance updates.

**Kubernetes Lease API** (`coordination.k8s.io/v1/leases`) is the cloud-native alternative: the same TTL+renewal model but stored in etcd via the Kubernetes API server. The `k8s.io/client-go/tools/leaderelection` package implements it. Prefer it over a Redis lease if you're already on Kubernetes — it uses your existing auth and audit trail.

</UnderTheHood>

<Callout kind="pro" title="Schedules and concurrency as configuration">

Hard-coding `"0 0 2 * * *"` in source code is a smell. The cron schedule, the worker concurrency, the max-retry count, the lease TTL — these are **operational knobs** that change without requiring a code change or a redeploy. Load them from environment variables or a config file at startup, validate them eagerly, and fail fast if a value is missing or malformed. The full story lives in the Configuration & Secrets chapter, but the principle applies here: every scheduling constant you hardcode is a 2 a.m. redeploy waiting to happen.

</Callout>

<Callout kind="note" title="Ties back to reliability patterns">

The retry-with-backoff and jitter you saw in this chapter is the same pattern as the HTTP retry in the Reliability Patterns chapter — the queue is just the delivery mechanism. The idempotency key is the same concept as HTTP idempotency keys for payment APIs. And the circuit breaker lives between your job handler and the external service it calls. These patterns compose. The queue doesn't replace reliability thinking — it shifts the retry boundary from the caller to the worker.

</Callout>

```go
	"errors"
	"fmt"
)

	Payload     string
	Attempts    int
	MaxAttempts int

type Queue struct {
	jobs []Job
}

func (q *Queue) Enqueue(j Job) {
	q.jobs = append(q.jobs, j)
}

func (q *Queue) Process(handler func(Job) error) {
	if len(q.jobs) == 0 {
		return
	}
	j := q.jobs[0]
	q.jobs = q.jobs[1:]
	j.Attempts++
	err := handler(j)
	if err != nil {

			q.Enqueue(j)
		}
	} else {
		fmt.Printf("done: %s (attempt %d)\n", j.Payload, j.Attempts)
	}
```

```go
		select {
		case <-ctx.Done():
			// Stop accepting. Wait for the in-flight job to finish.
			wg.Wait()
			fmt.Println("worker drained and stopped")
			return
		case fn := <-w.jobs:
			wg.Add(1)
			go func() {
				defer wg.Done()
				fn()
			}()
		}
	}
}

func main() {
	w := NewWorker(5)
	ctx, cancel := context.WithCancel(context.Background())

	go w.Start(ctx)

	w.Submit(func() {
		time.Sleep(200 * time.Millisecond)
		fmt.Println("job 1 done")
	})
	w.Submit(func() {
		time.Sleep(100 * time.Millisecond)
		fmt.Println("job 2 done")
	})

	time.Sleep(50 * time.Millisecond)
	cancel() // signal shutdown while jobs are still running
	time.Sleep(400 * time.Millisecond) // wait for demo output
}
```

The critical path: `ctx.Done()` fires, but the `wg.Wait()` call keeps the function alive until both goroutines call `wg.Done()`. No in-flight job is dropped. In a real system replace the `time.Sleep` wait at the end with a done channel or a `sync.WaitGroup` on the outer scope.

</Solution>

</Exercise>

<Exercise n={5} title="Leader election simulation" level="hard">

Simulate leader election for a scheduled job across three replicas using an in-memory store with a TTL-like expiry. Each replica runs a goroutine that tries to acquire the lease, runs the job if it won, and releases the lease afterward. Verify that across 10 election rounds the simulation records one successful lease-holder per round regardless of goroutine scheduling order.

<Solution>

```go
package main

import (
	"fmt"
	"sync"
	"sync/atomic"
)

type LeaseStore struct {
	mu    sync.Mutex
	owner string
}

func (s *LeaseStore) TryAcquire(id string) bool {
	s.mu.Lock()
	defer s.mu.Unlock()
	if s.owner != "" {
		return false
	}
	s.owner = id
	return true
}

func (s *LeaseStore) Release(id string) {
	s.mu.Lock()
	defer s.mu.Unlock()
	if s.owner == id {
		s.owner = ""
	}
}

func main() {
	const rounds = 10
	for round := range rounds {
		store := &LeaseStore{}
		var executions atomic.Int32

		var wg sync.WaitGroup
		for _, id := range []string{"pod-a", "pod-b", "pod-c"} {
			wg.Add(1)
			go func(id string) {
				defer wg.Done()
				if store.TryAcquire(id) {
					executions.Add(1)
					// simulate job work
					store.Release(id)
				}
			}(id)
		}
		wg.Wait()

		n := executions.Load()
		if n != 1 {
			fmt.Printf("round %d: BUG — job fired %d times\n", round+1, n)
		} else {
			fmt.Printf("round %d: ok — fired once\n", round+1)
		}
	}
}
```

`atomic.Int32` lets us safely count executions across goroutines without a mutex. The outer loop resets the store each round, simulating a new lease window. The assertion `n != 1` is your verifier.

<Recap>

- **`time.Ticker`** fires at fixed intervals; if your work outlasts the interval the next tick is silently dropped. Use it for polling. Use **`robfig/cron`** when you need wall-clock schedule precision (daily at 02:00).
- **Job queues** decouple slow/retryable work from the request path. **Asynq** (Redis-backed, fast enqueue) and **River** (Postgres-backed, transactional enqueue) are the two main options. Both are at-least-once — your handler WILL run more than once.
- **Idempotent handlers** are not optional. Use a deduplication key (a `SET NX` in Redis or a unique constraint in Postgres) to absorb duplicate deliveries without double-processing.
- **Exponential backoff with jitter** schedules retries without stampeding a recovering downstream service. `min()/max()` builtins (Go 1.21+) make the cap calculation clean.
- **Dead-letter queues** are a triage holding pen, not a trash can. Alert on DLQ depth; don't ignore it.
- **Graceful shutdown** means calling `srv.Shutdown()` (or equivalent drain logic) on SIGTERM — never `os.Exit(0)` with jobs in flight.
- **Naive in-process cron fires on every replica.** The fix is a distributed **lease** (Redis `SET NX`, etcd, or the Kubernetes Lease API): exactly one replica wins, the others skip. The lease TTL is your safety valve if the leader crashes.
- **Schedules and concurrency are operational knobs** — load them from config, validate at startup, never hardcode.

</Recap>
