<HeroCard label="Part 2 · Chapter 13" title="Background Jobs, Scheduling & Async Work">

When Alice books seat A7, she expects an email: "Booking bk-0007: seat A7 is yours." The booking request shouldn't wait for that email. Mail servers are slow, sometimes down, and the customer doesn't need to watch the email being sent. So the request records the booking and leaves a note: *send this email*. Something else, later, does the sending. That note is a **job**, and the something else is a **worker**.

The cinema also has work that nobody requested: every second, release seat holds whose payment never arrived. That's a **scheduled job**, and once the service runs as three replicas, it runs three times unless you stop it.

This chapter builds both, for real: **Asynq** (a job queue on Redis) and **River** (a job queue on Postgres) sending emails to **Mailpit** (a real SMTP server that keeps what it receives, with an API to count it). Then it breaks them: stops the mail server, kills workers with `kill -9`, crashes between two writes, and freezes a leader. Every number below was measured.

Six stops. If you get lost, come back here:

1. **Scheduling in a process.** A sleep loop, a ticker and cron each mean something different by "every second".
2. **A job queue.** Enqueue in the request, send in a worker, check the inbox.
3. **Retries and dead letters.** When the mail server is down: back off, give up, keep the job for a human.
4. **At least once.** A worker killed at the wrong moment means a second email, unless the handler recognises its own work. And stopping a worker politely.
5. **Enqueue with the booking.** The booking in Postgres and the job in Redis are two writes; a crash between them loses one. Put both in one transaction.
6. **Once across replicas.** Three replicas, one sweep per second: a lease in Redis picks a leader, and the leader must stop trusting itself when its lease runs out.

## Scheduling

*Stop 1 of 6.*

### Step 1: three meanings of "every second"

Before queues, the simplest background work: a goroutine that does something on a schedule, inside the service. Three ways to run a 300 ms job "every second":

```go noverify
// Three ways to "run every second" a job that takes 300 ms. When does
// each run actually start?
package main

import (
	"fmt"
	"time"

	"github.com/robfig/cron/v3"
)

func work() { time.Sleep(300 * time.Millisecond) } // e.g. publish sales stats

func main() {
	start := time.Now()
	at := func() string { return fmt.Sprintf("%6.3fs", time.Since(start).Seconds()) }

	fmt.Println("sleep loop: work, then sleep 1s")
	for range 4 {
		fmt.Println("  run at", at())
		work()
		time.Sleep(time.Second)
	}

	start = time.Now()
	fmt.Println("time.Ticker(1s)")
	t := time.NewTicker(time.Second)
	for range 4 {
		<-t.C
		fmt.Println("  run at", at())
		work()
	}
	t.Stop()

	start = time.Now()
	fmt.Println("cron \"* * * * * *\" (every wall-clock second)")
	c := cron.New(cron.WithSeconds())
	runs := make(chan string, 8)
	c.AddFunc("* * * * * *", func() {
		runs <- fmt.Sprintf("  run at %s (wall clock %s)", at(), time.Now().Format("15:04:05.000"))
		work()
	})
	c.Start()
	for range 4 {
		fmt.Println(<-runs)
	}
	<-c.Stop().Done()
}
```

```text
sleep loop: work, then sleep 1s
  run at  0.000s
  run at  1.302s
  run at  2.607s
  run at  3.910s
time.Ticker(1s)
  run at  1.001s
  run at  2.002s
  run at  3.001s
  run at  4.001s
cron "* * * * * *" (every wall-clock second)
  run at  0.515s (wall clock 07:04:01.002)
  run at  1.517s (wall clock 07:04:02.004)
  run at  2.516s (wall clock 07:04:03.003)
  run at  3.516s (wall clock 07:04:04.002)
```

- **The sleep loop drifts.** It waits a second *after* each 300 ms job, so runs are 1.3 s apart, and after an hour it has run 2,770 times, not 3,600.
- **`time.Ticker` keeps the rate.** It fires every second measured from when it was created, whatever the job takes (if a job takes longer than the period, ticks are dropped, not queued up).
- **Cron follows the wall clock.** It fires at each whole second on the clock (`.002`, `.004`), so the first run came 0.515 s after start, when the clock reached the next second. That's what "at 03:00 every night" needs.

### Step 2: what in-process scheduling can't do

All three live inside one process. If the process is restarting at 03:00, the 03:00 run doesn't happen. If the service runs as three replicas, each runs it. And if the job fails halfway, nothing retries it. Those three problems are the rest of this chapter: stops 2–5 move work into a **queue** that survives restarts and retries failures, and stop 6 makes a schedule run **once** across replicas.

## A Job Queue

*Stop 2 of 6.*

### Step 1: the job

A job is a type name and a payload. The confirmation email's payload is the booking:

```go noverify
// Package email defines the booking-confirmation job: its payload, how to
// enqueue it, and how a worker sends it.
package email

import (
	"context"
	"encoding/json"
	"errors"
	"fmt"
	"net/smtp"
	"time"

	"github.com/hibiken/asynq"
	"github.com/redis/go-redis/v9"
)

const TypeConfirmation = "email:confirmation"

type Confirmation struct {
	BookingID string `json:"booking_id"`
	To        string `json:"to"`
	Movie     string `json:"movie"`
	Seat      string `json:"seat"`
}

// NewConfirmation builds the task. TaskID makes the queue itself reject a
// second task for the same booking while the first is still known to it.
func NewConfirmation(c Confirmation) (*asynq.Task, error) {
	payload, err := json.Marshal(c)
	if err != nil {
		return nil, err
	}
	return asynq.NewTask(TypeConfirmation, payload,
		asynq.TaskID("confirm-"+c.BookingID),
		asynq.MaxRetry(4),
		asynq.Timeout(10*time.Second),
	), nil
}

// Sender sends confirmation emails over SMTP.
type Sender struct {
	SMTPAddr string
	// Dedup, if set, records each booking that has been emailed, so a job
	// that is delivered twice sends once.
	Dedup *redis.Client
	// AfterSend runs after the email has gone out (the chapter uses it to
	// widen the window in which a crash causes a duplicate).
	AfterSend func()
}

// Handle is the Asynq handler.
func (s *Sender) Handle(ctx context.Context, t *asynq.Task) error {
	var c Confirmation
	if err := json.Unmarshal(t.Payload(), &c); err != nil {
		return fmt.Errorf("bad payload: %v: %w", err, asynq.SkipRetry) // retrying won't fix it
	}
	return s.Send(ctx, c)
}

// ErrInProgress means another delivery of the same job is sending it now.
var ErrInProgress = errors.New("another delivery of this job is sending it")

// Send emails one confirmation. With Dedup, it first claims the booking
// with SET NX, so of any number of deliveries exactly one sends.
func (s *Sender) Send(ctx context.Context, c Confirmation) error {
	key := "emailed:" + c.BookingID
	if s.Dedup != nil {
		// The claim expires, so a worker that dies mid-send doesn't block
		// the job forever (the price: that one case can still send twice).
		ok, err := s.Dedup.SetNX(ctx, key, "sending", time.Minute).Result()
		if err != nil {
			return err
		}
		if !ok {
			if v, err := s.Dedup.Get(ctx, key).Result(); err == nil && v == "sent" {
				return nil // an earlier delivery sent it
			}
			return ErrInProgress // retry later: the other delivery may yet fail
		}
	}
	msg := fmt.Sprintf("From: tickets@cinema.example\r\nTo: %s\r\nSubject: Your seat %s for %s\r\n"+
		"Message-ID: <%s@cinema.example>\r\n\r\nBooking %s: seat %s is yours.\r\n",
		c.To, c.Seat, c.Movie, c.BookingID, c.BookingID, c.Seat)
	if err := smtp.SendMail(s.SMTPAddr, nil, "tickets@cinema.example", []string{c.To}, []byte(msg)); err != nil {
		if s.Dedup != nil {
			s.Dedup.Del(context.WithoutCancel(ctx), key) // release, so the retry can send
		}
		return fmt.Errorf("send to %s: %w", c.To, err)
	}
	if s.Dedup != nil {
		s.Dedup.Set(context.WithoutCancel(ctx), key, "sent", 7*24*time.Hour) // remember for a week
	}
	if s.AfterSend != nil {
		s.AfterSend()
	}
	return nil
}
```

Three things in `NewConfirmation` matter later. **`TaskID("confirm-" + booking)`**: the queue rejects a second job with the same ID. **`MaxRetry(4)`**: how many times to retry before giving up (stop 3). **`Timeout(10s)`**: the handler's context is cancelled after 10 s, so a hung SMTP connection can't hold a worker forever. `Send`'s `Dedup` claim is stop 4's fix; ignore it for now.

### Step 2: the worker

The worker is a server, but instead of HTTP requests it takes jobs from Redis:

```go noverify
// worker processes confirmation-email jobs from the Redis-backed queue.
package main

import (
	"context"
	"flag"
	"log"
	"time"

	"jobs/email"

	"github.com/hibiken/asynq"
	"github.com/redis/go-redis/v9"
)

func main() {
	redisAddr := flag.String("redis", "127.0.0.1:6390", "Redis")
	smtpAddr := flag.String("smtp", "127.0.0.1:1025", "SMTP server")
	idempotent := flag.Bool("idempotent", false, "skip bookings already emailed")
	slow := flag.Duration("slow", 0, "pause after sending each email")
	flag.Parse()

	s := &email.Sender{SMTPAddr: *smtpAddr}
	if *idempotent {
		s.Dedup = redis.NewClient(&redis.Options{Addr: *redisAddr})
	}
	if *slow > 0 {
		s.AfterSend = func() { time.Sleep(*slow) }
	}

	srv := asynq.NewServer(asynq.RedisClientOpt{Addr: *redisAddr}, asynq.Config{
		Concurrency: 4,
		// Retry after 1 s, 2 s, 4 s, 8 s (short, so the chapter can watch).
		RetryDelayFunc: func(n int, err error, t *asynq.Task) time.Duration {
			return time.Second << n // n = retries so far: 0, 1, 2, 3
		},
		// Check every 250 ms for retries that are due (default 5 s).
		DelayedTaskCheckInterval: 250 * time.Millisecond,
		ShutdownTimeout:          10 * time.Second, // on SIGTERM, wait this long for running jobs
		ErrorHandler: asynq.ErrorHandlerFunc(func(ctx context.Context, t *asynq.Task, err error) {
			id, _ := asynq.GetTaskID(ctx)
			n, _ := asynq.GetRetryCount(ctx)
			max, _ := asynq.GetMaxRetry(ctx)
			log.Printf("job %s failed (retried %d of %d): %v", id, n, max, err)
		}),
	})
	mux := asynq.NewServeMux()
	mux.HandleFunc(email.TypeConfirmation, s.Handle)
	log.Printf("worker: idempotent=%v slow=%v", *idempotent, *slow)
	if err := srv.Run(mux); err != nil { // Run returns after SIGTERM/SIGINT and draining
		log.Fatal(err)
	}
}
```

`Concurrency: 4` means four jobs at once (four goroutines). The handler returns `nil` for done, or an error for "retry me".

### Step 3: run it

`run1.sh` enqueues 20 bookings, enqueues the same 20 again, runs a worker until Mailpit has 20 messages, then asks Mailpit what arrived:

```text
enqueued 20, rejected as duplicates 0
enqueued 0, rejected as duplicates 20
queue: pending 20, active 0, retry 0, archived 0, completed 0, processed 0, failed 0
emails in Mailpit: 20
  customer20@example.com | Your seat C4 for inception
  customer19@example.com | Your seat C3 for inception
  customer18@example.com | Your seat C2 for inception
queue: pending 0, active 0, retry 0, archived 0, completed 0, processed 20, failed 0
--- the same 20 bookings, enqueued again after they were processed
enqueued 20, rejected as duplicates 0
2026/09/27 07:01:05 worker: idempotent=false slow=0s
```

**20 emails for 20 bookings**, and the second enqueue of the same bookings was rejected by the task ID. But look at the last line: once the jobs were processed, Asynq deleted them, and **the same 20 bookings were accepted again**. A task ID only deduplicates while the queue still remembers the task (you can extend that with `asynq.Retention`). It protects against double-enqueueing at the same moment, not against a job running twice. Stop 4 is about that.

## Retries and Dead Letters

*Stop 3 of 6.*

### Step 1: the mail server goes down

`retry.sh` stops Mailpit, enqueues two bookings, and watches. Read the worker's log at the bottom first: attempts at :07, :08, :10, :14, :23, each one the previous gap doubled (the timestamps are cut to the second). Between attempts the jobs sit in the **retry** set with a `next` time. After `MaxRetry` (4) retries, five attempts in all, Asynq logs "Retry exhausted" and moves both jobs to the **archived** set: a dead-letter queue. They're kept, with their last error, but nothing will run them again by itself.

Then Mailpit comes back, and `inspect -requeue` (Asynq's `RunAllArchivedTasks`) moves them back to pending: **2 emails**. In production that's a person, looking at the archive after an incident, deciding the jobs are still worth running (a confirmation email three hours late is fine; a "your seat is held for 10 minutes" email is not).

### Step 2: what not to retry

A job whose payload can't be decoded will fail the same way on every attempt. `Handle` wraps that error with **`asynq.SkipRetry`**, which archives the job at once instead of burning five attempts. The same goes for an address the mail server rejects permanently (SMTP 5xx). The rule from chapter 12 applies: retry transient failures (connection refused, 4xx "try later", timeouts), not answers.

## At Least Once

### Step 1: kill -9 between send and done

How does Asynq know a worker is still working on a job? The worker holds a **lease** on each job it has taken, and renews it with heartbeats. If the worker dies, the heartbeats stop, the lease expires (30 s), and a recoverer (it runs every minute, and allows 30 s for clock skew) puts the job back to be retried. That's the only safe choice: the queue can't tell "died before sending" from "died after sending".

`crash.sh` enqueues 10 bookings and starts worker A with `-slow 3s`, a pause *after* each email is sent (widening the window a real worker has between `SendMail` returning and the ack reaching Redis). At 1.5 s it kills A with SIGKILL and starts worker B:

### Step 2: make the handler recognise its own work

The queue can't give you exactly-once, but the handler can make running twice *harmless*: record that booking `bk-0001` has been emailed, and skip it the second time. The obvious version (check a mark, send, set the mark) has a hole: two deliveries of the same job running at once (a lease expiring while the first worker is merely slow, not dead) both find no mark and both send. So `Send` **claims** the booking first, with one atomic `SET NX`:

```go noverify
// email.go, lines 60–97
// ErrInProgress means another delivery of the same job is sending it now.
var ErrInProgress = errors.New("another delivery of this job is sending it")

// Send emails one confirmation. With Dedup, it first claims the booking
// with SET NX, so of any number of deliveries exactly one sends.
func (s *Sender) Send(ctx context.Context, c Confirmation) error {
	key := "emailed:" + c.BookingID
	if s.Dedup != nil {
		// The claim expires, so a worker that dies mid-send doesn't block
		// the job forever (the price: that one case can still send twice).
		ok, err := s.Dedup.SetNX(ctx, key, "sending", time.Minute).Result()
		if err != nil {
			return err
		}
		if !ok {
			if v, err := s.Dedup.Get(ctx, key).Result(); err == nil && v == "sent" {
				return nil // an earlier delivery sent it
			}
			return ErrInProgress // retry later: the other delivery may yet fail
		}
	}
	msg := fmt.Sprintf("From: tickets@cinema.example\r\nTo: %s\r\nSubject: Your seat %s for %s\r\n"+
		"Message-ID: <%s@cinema.example>\r\n\r\nBooking %s: seat %s is yours.\r\n",
		c.To, c.Seat, c.Movie, c.BookingID, c.BookingID, c.Seat)
	if err := smtp.SendMail(s.SMTPAddr, nil, "tickets@cinema.example", []string{c.To}, []byte(msg)); err != nil {
		if s.Dedup != nil {
			s.Dedup.Del(context.WithoutCancel(ctx), key) // release, so the retry can send
		}
		return fmt.Errorf("send to %s: %w", c.To, err)
	}
	if s.Dedup != nil {
		s.Dedup.Set(context.WithoutCancel(ctx), key, "sent", 7*24*time.Hour) // remember for a week
	}
	if s.AfterSend != nil {
		s.AfterSend()
	}
	return nil
}
```

- `SET emailed:bk-0001 sending NX EX 60`: exactly one delivery wins. A loser that finds `sent` returns `nil` (done); one that finds `sending` returns an error, so the queue retries it later, in case the winner's send fails.
- If the send fails, the claim is **deleted**, so the retry can send.
- On success, the key becomes `sent` for a week, longer than any retry could arrive.

```text

t=1s   worker A killed with SIGKILL; emails so far: 4
queue: pending 6, active 4, retry 0, archived 0, completed 0, processed 0, failed 0
       worker B started

2026/09/27 07:08:06 worker: idempotent=true slow=0s
```

<Callout kind="warn" title="The window that's left">

A worker killed between `SendMail` returning and `SET … sent` still leaves `sending`, which expires after a minute, and then the retry sends a second email. You can shrink that window, not close it: the send and the record are two systems (the mail server and Redis) and no transaction spans both. The only full fix is at the receiver: here the email carries a `Message-ID` built from the booking, which is what mail systems use to drop duplicates. For payments, the same idea is the idempotency key the payment provider stores (Part 1 chapter 24).

</Callout>

### Step 2: River, a queue in your database

**River** stores jobs in a Postgres table (`river_job`) and has workers claim them with `SELECT … FOR UPDATE SKIP LOCKED`. Because the job is a row, it can be inserted by the same transaction as the booking: `rq.InsertTx(ctx, tx, …)`. The worker is the same handler with a different wrapper:

```go noverify
	s *email.Sender
}

	return w.s.Send(ctx, job.Args.Confirmation)
}

func main() {
	ctx, stop := signal.NotifyContext(context.Background(), syscall.SIGTERM, syscall.SIGINT)
	defer stop()
	db, err := pgxpool.New(ctx, "postgres://postgres@127.0.0.1:55432/cinema_jobs")
	if err != nil {
		log.Fatal(err)
	}
	workers := river.NewWorkers()
	river.AddWorker(workers, &ConfirmationWorker{s: &email.Sender{SMTPAddr: "127.0.0.1:1025"}})

		Queues:            map[string]river.QueueConfig{river.QueueDefault: {MaxWorkers: 4}},
```

The tables come from River's own migrations (`rivermigrate`, run by `cmd/migrate`). River also retries with backoff (25 attempts by default), discards to a dead state, and rescues jobs from dead workers, like Asynq: it's still at-least-once, so `Send` keeps its claim.

If your queue can't live in your database (the job must go to Redis, Kafka, SQS), the same idea is the **transactional outbox**: write the message to an `outbox` table in the booking's transaction, and have a separate process copy outbox rows to the queue and mark them sent. That relay is at-least-once too, so the consumer still deduplicates.

### Step 2: a lease picks a leader

A **lease** is a key in Redis that says who the leader is, with an expiry. Replicas try `SET leader:sweeper <me> NX PX 3000` every second: the one that succeeds is the leader, and it renews with `SET … IFEQ <me>` (only if the key is still its own; Redis 8.4+). If the leader dies, it stops renewing, the key expires, and the next replica to try takes over:

```go noverify
package main

import (
	"context"
	"errors"
	"log"
	"sync"
	"time"

	"github.com/redis/go-redis/v9"
)

// Lease is leader election on one Redis key: whoever set the key is the
// leader until it stops renewing and the key expires.
type Lease struct {
	rdb *redis.Client
	key string
	me  string
	ttl time.Duration

	// trustFlag makes Held ignore the deadline and trust the last answer
	// from Redis (the chapter's broken version).
	trustFlag bool

	mu    sync.Mutex
	until time.Time // our own deadline; read with time.Now (monotonic)
}

// Run tries to take or renew the lease every ttl/3 until ctx ends.
func (l *Lease) Run(ctx context.Context) {
	t := time.NewTicker(l.ttl / 3)
	defer t.Stop()
	for {
		l.try(ctx)
		select {
		case <-ctx.Done():
			return
		case <-t.C:
		}
	}
}

func (l *Lease) try(ctx context.Context) {
	start := time.Now()
	held := l.Held()
	var err error
	if held {
		// Renew only if the key still holds our name (Redis 8.4+ IFEQ).
		err = l.rdb.Do(ctx, "SET", l.key, l.me, "IFEQ", l.me, "PX", l.ttl.Milliseconds()).Err()
	} else {
		err = l.rdb.SetArgs(ctx, l.key, l.me, redis.SetArgs{Mode: "NX", TTL: l.ttl}).Err()
	}
	l.mu.Lock()
	defer l.mu.Unlock()
	switch {
	case err == nil:
		if !held {
			log.Printf("%s: became leader", l.me)
		}
		// Count the lease from before we sent the command, so our deadline
		// is never later than Redis's.
		l.until = start.Add(l.ttl)
	case errors.Is(err, redis.Nil):
		if held {
			log.Printf("%s: lost the lease", l.me)
		}
		l.until = time.Time{}
	default:
		log.Printf("%s: redis: %v", l.me, err) // keep l.until: it runs out by itself
	}
}

// Held reports whether our lease is still valid by our own clock.
func (l *Lease) Held() bool {
	l.mu.Lock()
	defer l.mu.Unlock()
	if l.trustFlag {
		return !l.until.IsZero() // "Redis said yes last time"
	}
	return time.Now().Before(l.until)
}

// Release gives the lease up early (only if it is still ours).
func (l *Lease) Release(ctx context.Context) {
	l.rdb.Do(ctx, "DELEX", l.key, "IFEQ", l.me)
}
```

The important line is `Held`: the leader decides whether to run from **its own clock**, not from the last thing Redis told it. The lease counts from *before* the SET was sent, so the leader's deadline is never later than Redis's. ### Step 4: when the leader's work leaves the process

`Held` protects the decision to *start* a run. It can't stop a run that has started and then freezes: the leader checks `Held`, begins deleting holds, pauses for 5 s, and resumes deleting after another replica has become leader. For work that writes somewhere, the fix is a **fencing token**: each new lease gets a higher number (`INCR` alongside the lease), the leader sends it with every write, and the storage rejects writes carrying a number lower than one it has already seen. Chapter 23 builds it.

For many schedules there's a simpler answer: don't elect a leader, **deduplicate the run**. Each replica enqueues the tick's job with a task ID naming the tick (`sweep-2026-09-27T05:03:18`), the queue accepts one of the three, and one worker runs it, with retries and dead letters for free. That's what Asynq's `Scheduler` and River's periodic jobs are for; River runs its periodic jobs only on its elected leader.

<Exercise n={1} title="Pick the schedule" level="easy">

For each job, choose a sleep loop, `time.Ticker` or cron, and say why: (a) refresh an in-memory cache of film listings roughly every 30 s; (b) send the daily sales report at 07:00; (c) poll a payment provider for pending payments every 5 s, where each poll can take up to 4 s.

<Solution>

(a) **Ticker** (or even a sleep loop): the exact phase doesn't matter, only roughly the rate, and a ticker keeps it. (b) **Cron**: "07:00" is a wall-clock time; a ticker would fire 24 h after whenever the process started. With replicas, it also needs stop 6 (a lease, or a task ID per day). (c) A **sleep loop** is actually right here: "wait 5 s after each poll finishes" can never overlap polls. A ticker keeps a 5 s rate regardless: a 4 s poll leaves 1 s of quiet before the next, and when the provider is slow and a poll takes 6 s, the ticker's buffered tick fires the next poll the instant this one ends, so a struggling provider gets polled back to back.

</Solution>

</Exercise>

<Exercise n={2} title="Which errors to retry" level="easy">

For each failure of the email handler, say retry or `asynq.SkipRetry`, and why: (a) `connection refused` to the SMTP server; (b) SMTP `550 mailbox does not exist`; (c) the payload's JSON can't be decoded; (d) the Redis `SET NX` claim times out.

<Solution>

(a) **Retry**: the server may be restarting. (b) **Skip**: 5xx is a permanent answer; retrying sends the same doomed request five more times. Record it on the booking so support can ask for a new address. (c) **Skip**: the bytes won't change between attempts. (d) **Retry**: a Redis timeout is transient, and returning the error before sending anything is safe. The rule: retry what might succeed later, skip what will fail identically.

</Solution>

</Exercise>

<Exercise n={3} title="Measure the lease gap" level="medium">

Change `leaseTTL` in the sweeper to 10 s and 1 s, rerun `./sweep.sh lease`, and count the skipped ticks after the kill -9. What's the trade-off in choosing the TTL?

<Solution>

The skipped ticks after a kill are roughly the TTL (the dead leader's key must expire): about 10 with 10 s, about 1 with 1 s. A short TTL means fast failover, but the leader must renew more often (ttl/3 here), and any pause longer than the TTL (a GC pause, a slow Redis, a network blip) costs it the lease, so leadership flaps between replicas. A long TTL means stable leadership and long gaps when a leader dies. Pick it from how late the job may run: a hold sweep can be a few seconds late; a TTL of seconds is fine.

</Solution>

</Exercise>

<Exercise n={4} title="Why not exactly once?" level="medium">

A colleague proposes making the queue exactly-once: "the worker acks the job before sending the email, so a crash can never cause a second send." What happens, and what's the real guarantee you can get?

<Solution>

Ack-then-send is **at-most-once**: a crash after the ack and before (or during) the send loses the email, and nothing retries it, because the queue thinks it's done. You've swapped duplicates for silent losses. Across two systems (the queue and the mail server) no ordering gives exactly-once. What you can build is **effectively once**: at-least-once delivery (never lose) plus an idempotent handler (the claim in `Send`) so repeats have no effect, and, where the receiver supports it, an idempotency key it deduplicates on (the `Message-ID`, a payment provider's idempotency key).

</Solution>

</Exercise>

<Exercise n={5} title="Outbox relay" level="hard">

Design a transactional outbox for the cinema if confirmations must go through Asynq, not River: the table, what the booking transaction writes, what the relay does, and what happens if the relay crashes after enqueueing a row but before marking it sent.

<Solution>

Table `outbox(id bigserial primary key, kind text, payload jsonb, created_at timestamptz, sent_at timestamptz)`. The booking transaction inserts the booking and an outbox row (`kind = 'confirmation'`) together. The relay loops: `SELECT … FROM outbox WHERE sent_at IS NULL ORDER BY id LIMIT 100 FOR UPDATE SKIP LOCKED`, enqueues each to Asynq with `TaskID("confirm-" + booking)`, then sets `sent_at`. If it crashes after enqueueing and before updating, the row is picked up again and enqueued again: the task ID rejects it while Asynq still holds the task, and after that `Send`'s claim (`emailed:<booking>` is `sent`) skips it. At-least-once at every hop, deduplicated at the end. Delete old sent rows on a schedule so the table stays small.

</Solution>

</Exercise>

<Recap>

- **Schedules**: a sleep loop drifts (runs 1.3 s apart for a 300 ms job), a ticker keeps the rate (1.001, 2.002…), cron follows the wall clock. In-process schedules die with the process and run once per replica.
- **A job queue** lets the request answer at once and the work survive restarts: 20 bookings, 20 jobs, 20 emails in Mailpit. A task ID stops double-enqueueing only while the queue remembers the task.
- **Retries and dead letters**: with the mail server down, attempts came 1, 2, 4, 8 s apart, then the jobs were archived with their last error; requeued after the outage, 2 emails. Skip retrying what can't succeed.
- **At least once**: kill -9 after sending, before acking, and the lease brings the job back a minute later: 14 emails for 10 bookings. Claiming the booking with SET NX before sending: 10. SIGTERM drains: 4 jobs finished in 2 s, 6 left pending, none lost.
- **Dual writes**: commit-then-enqueue lost booking 4's email; enqueue-then-commit emailed a booking that never existed. River's job in the booking's transaction: neither.
- **Once across replicas**: no lease, 3 runs per tick; a Redis lease, 1 run per tick, with 2–3 ticks skipped at each failover. The leader must check its own deadline: trusting the last answer from Redis ran a tick twice after a freeze.

</Recap>
