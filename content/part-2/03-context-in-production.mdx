### Step 3: the rules, in the fraud service

Two rules carry most of the discipline:

1. **Every call that can block takes the context as its first argument**, and passes it on.
2. **Every goroutine you start watches that context**, so it can stop when the request is over.

The fraud service follows rule 1 in one line: it passes `r.Context()`, the context `net/http` created for this request, to the query. Watch line 23:

```go noverify
package main

import (
	"database/sql"
	"encoding/json"
	"net/http"
	"time"
)

// velocity is the fraud rule: how much has this account sent in 24 hours?
// transactions has no index on from_account, so this scans ~2M rows (~70 ms).
const velocity = `
	SELECT count(*), coalesce(sum(amount_cents), 0)
	FROM transactions
	WHERE from_account = $1 AND created_at > now() - interval '24 hours'`

// fraudService is a separate HTTP service. It uses r.Context(), so when the
// caller hangs up or its deadline passes, the query is cancelled in Postgres.
func fraudService(db *sql.DB) http.HandlerFunc {
	return func(w http.ResponseWriter, r *http.Request) {
		start := time.Now()
		var n, sum int64
		err := db.QueryRowContext(r.Context(), velocity, r.URL.Query().Get("account")).Scan(&n, &sum)
		log := logger(r.Context()).With("service", "fraud", "took", time.Since(start).Round(time.Millisecond))
		if err != nil {
			log.Warn("velocity query stopped", "err", err)
			http.Error(w, "fraud check unavailable", http.StatusServiceUnavailable)
			return
		}
		log.Info("velocity query finished", "sent_24h_cents", sum)
		json.NewEncoder(w).Encode(map[string]bool{"approve": sum < 5_000_000})
	}
}
```

</CodeWalk>

### Step 4: what happens when the client hangs up

Scenario 3 in `main.go` calls checkout with a generous 500 ms budget, but the *client* gives up after 30 ms, as a phone losing signal would. The real output:

```text
=== 3. the client hangs up after 30ms (budget 500ms)
client: gave up after 31ms: Post "http://127.0.0.1:63959/checkout?…": context deadline exceeded
level=WARN msg="velocity query stopped" req=AN7FRIL6 service=fraud took=31ms err="context canceled"
level=WARN msg="checkout failed" req=AN7FRIL6 status=502 err="Get \"http://127.0.0.1:63947?…\": context canceled"
postgres: 0 fraud scan process(es) still running
postgres: balance 97500 -> 97500 cents, audit rows +1
```

Read it in order:

- The client gave up at 31 ms and closed its connection.
- `net/http` in the checkout service noticed and cancelled `r.Context()`. Checkout's context, derived from it, closed its `Done` channel, which cancelled the in-flight HTTP call to the fraud service.
- That closed the fraud service's connection, so *its* `r.Context()` was cancelled, and the pgx driver sent Postgres a cancel request: `velocity query stopped … took=31ms`.
- A check of `pg_stat_activity` found **no scan still running**. No money moved.

One disconnect crossed two HTTP hops and stopped a query inside the database, because every call passed the context along.

## Deadlines & Budgets

*Stop 2 of 5.*

### Step 1: one ceiling per request

A client disconnect is one way a request ends. The other is running out of time. Checkout sets one deadline for everything it does:

```go
ctx, cancel := context.WithTimeout(r.Context(), budget) // one ceiling for the whole request
defer cancel()
```

Everything below it uses `ctx` (or a child of it), so nothing can outlive the budget. Scenario 2 gives checkout 40 ms, less than the fraud scan needs:

```text
=== 2. budget 40ms: the fraud scan can't finish
level=WARN msg="checkout failed" req=6Z2HS5PN status=504 err="Get \"http://127.0.0.1:63947?…\": context deadline exceeded"
level=WARN msg="velocity query stopped" req=6Z2HS5PN service=fraud took=41ms err="context canceled"
client: 504 Gateway Timeout after 45ms
postgres: 0 fraud scan process(es) still running
postgres: balance 97500 -> 97500 cents, audit rows +1
```

Checkout answered in 45 ms with **504 Gateway Timeout**, the fraud query was stopped at 41 ms, and nothing was left running. Notice the two different errors: checkout's own context reports `context deadline exceeded`, while the fraud service, which only saw its connection close, reports `context canceled`. Across a process boundary, a deadline arrives as a plain cancellation (Stop 4 explains why).

### Step 2: children can only shorten a deadline

When you derive a context with its own timeout, its deadline is the **earlier** of its own and its parent's:

```go
package main

import (
	"context"
	"fmt"
	"time"
)

func main() {
	parent, cancel := context.WithTimeout(context.Background(), 250*time.Millisecond)
	defer cancel()

	tight, c1 := context.WithTimeout(parent, 80*time.Millisecond)
	defer c1()
	loose, c2 := context.WithTimeout(parent, 500*time.Millisecond)
	defer c2()

	d1, _ := tight.Deadline()
	d2, _ := loose.Deadline()
	dp, _ := parent.Deadline()
	fmt.Println("tight deadline before parent's:", d1.Before(dp))
	fmt.Println("loose deadline equals parent's:", d2.Equal(dp))

	start := time.Now()
	<-loose.Done()
	fmt.Printf("loose child ended after %v: %v\n", time.Since(start).Round(10*time.Millisecond), loose.Err())
}
```

### Step 3: budgets per hop

With one ceiling, the first slow call can eat the whole budget and leave nothing for payment. A common refinement gives each hop a share of **what's left**:

```go
// Give the fraud check at most 60% of the remaining budget.
if deadline, ok := ctx.Deadline(); ok {
	fraudCtx, cancel := context.WithTimeout(ctx, time.Until(deadline)*6/10)
	defer cancel()
	// … call fraud with fraudCtx …
}
```

Because children can only shorten deadlines, this can never extend the request past its ceiling. Exercise 1 adds it to checkout.

**Recap.** One `WithTimeout` per request sets the ceiling; everything uses that context or a child. Measured with a 40 ms budget: 504 in 45 ms and the query stopped at 41 ms. Children take the earlier deadline; per-hop budgets are fractions of what remains.

## Request-Scoped Values Done Right

*Stop 3 of 5.*

### Step 1: what goes in a context

`context.WithValue` attaches a value that every function receiving the context can read. It's tempting to use it for everything. Don't: values in a context are invisible in function signatures, unchecked by the compiler, and looked up by walking a chain. Keep them to **request-scoped** data that crosses API boundaries:

<ConceptGrid cols={2}>
  <ConceptCard label="Belongs in a context">A request or trace ID. The authenticated user. A logger already tagged with those. Values that exist for one request and are needed by code many layers down.</ConceptCard>
  <ConceptCard label="Doesn't">Database handles, HTTP clients, configuration, feature flags, optional parameters. Anything that lives longer than one request goes in a struct field or a function parameter, where the compiler can check it's there.</ConceptCard>
</ConceptGrid>

### Step 2: the checkout's middleware

All three services wrap their handlers in `withRequestID`. It reuses an incoming `X-Request-ID` header or makes one, and stores the ID and a logger that prints it. Outgoing requests carry the ID via a small `http.RoundTripper`, so the other services log the same ID.

<CodeWalk
  title="middleware.go"
  steps={[
    { lines: "11-16", note: "Keys are an unexported type, so no other package can create the same key and collide with (or read) these values.", pose: "blocked", role: "guard" },
    { lines: "27-40", note: "The middleware: take the caller's X-Request-ID if there is one, otherwise create one, then put the ID and a logger tagged with it into the request's context.", pose: "carry", role: "scribe", beat: "solution" },

    { lines: "54-64", note: "The outbound half: a RoundTripper that copies the ID from the request's context onto the outgoing request. Plug it into the http.Client and every call carries it.", pose: "run", role: "courier", beat: "solution" }

```go noverify
package main

import (
	"context"
	"crypto/rand"
	"log/slog"
	"net/http"
	"os"
)

type ctxKey int

const (
	requestIDKey ctxKey = iota
	loggerKey
)

var base = slog.New(slog.NewTextHandler(os.Stdout, &slog.HandlerOptions{
	ReplaceAttr: func(_ []string, a slog.Attr) slog.Attr {
		if a.Key == slog.TimeKey {
			return slog.Attr{} // keep the demo output short
		}
		return a
	},
}))

// withRequestID reuses an incoming X-Request-ID or makes one, and puts both
// the ID and a logger that always prints it into the request's context.
func withRequestID(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		id := r.Header.Get("X-Request-ID")
		if id == "" {
			id = rand.Text()[:8]
		}
		ctx := context.WithValue(r.Context(), requestIDKey, id)
		ctx = context.WithValue(ctx, loggerKey, base.With("req", id))
		w.Header().Set("X-Request-ID", id)
		next.ServeHTTP(w, r.WithContext(ctx))
	})
}

func requestID(ctx context.Context) string {
	id, _ := ctx.Value(requestIDKey).(string)
	return id
}

func logger(ctx context.Context) *slog.Logger {
	if l, ok := ctx.Value(loggerKey).(*slog.Logger); ok {
		return l
	}
	return base
}

// propagateID copies the request ID onto outgoing requests, so the fraud and
// payments services log the same ID as checkout.
type propagateID struct{ next http.RoundTripper }

func (p propagateID) RoundTrip(r *http.Request) (*http.Response, error) {
	if id := requestID(r.Context()); id != "" {
		r = r.Clone(r.Context())
		r.Header.Set("X-Request-ID", id)
	}
	return p.next.RoundTrip(r)
}
```

</CodeWalk>

It works across all three services. From scenario 1:

```text
level=INFO msg="velocity query finished" req=KHBPH6NE service=fraud took=458ms sent_24h_cents=0
level=INFO msg="transfer committed" req=KHBPH6NE service=payments cents=2500
```

Two different services, one ID: `grep KHBPH6NE` across every service's logs now shows the whole request. (That first query took 458 ms because the database had just been restarted and nothing was cached; later runs took 60–80 ms.)

<UnderTheHood title="How context.Value walks the chain">

Each `context.WithValue` wraps its parent in a new node holding one key and one value. `ctx.Value(key)` checks the newest node, then its parent, and so on to the root: a linked-list walk, O(depth). The keys are compared with `==`, which is why they must be comparable, and why an unexported key type is safest: nothing outside your package can build an equal key.

In practice a request's chain has a handful of values and the walk costs nanoseconds. It becomes a smell when dozens of values are stacked in, usually because the context is being used to pass dependencies. Bundle related values into one struct under one key instead.

</UnderTheHood>

**Recap.** Put only request-scoped data in a context: an ID, the user, a tagged logger. Use unexported key types and typed accessors. Carry the ID across services in a header, added by a `RoundTripper`; then one `grep` finds a request in every service's logs.

## Propagating Through HTTP, gRPC & DB

*Stop 4 of 5.*

### Step 1: HTTP: two directions

**Incoming**, `net/http` gives each request a context in `r.Context()`. It's cancelled when the client's connection closes, when an HTTP/2 stream is reset, or when the handler returns.

**Outgoing**, you create requests with `http.NewRequestWithContext(ctx, …)`. When `ctx` ends, the client stops waiting and closes that connection (or resets the stream).

What does **not** cross the wire is the deadline itself. HTTP has no standard header for "the caller will stop waiting at 12:00:00.250". The fraud service only learns the caller is gone when the connection closes, which is why its log said `context canceled` while checkout's said `context deadline exceeded`. If a downstream service needs to know its budget (to skip work it can't finish in time), pass it yourself, for example in a header, and derive a context from it on the other side.

### Step 2: gRPC: the deadline does cross

gRPC is different: the Go client sends `ctx`'s deadline in a `grpc-timeout` header, and the server turns it back into a context deadline for the handler. So a gRPC server sees `context deadline exceeded` at the right moment, with no extra code. Part 2, Chapter 18 builds a real gRPC service and shows it.

### Step 3: the database: every call, in a transaction too

`database/sql` takes the context in every method: `QueryContext`, `QueryRowContext`, `ExecContext`, `BeginTx`. The payments service's `transfer` uses it for every statement in the transaction:

```go noverify
package main

import (
	"context"
	"database/sql"
	"errors"
	"fmt"
	"net/http"
	"strconv"
)

// paymentsService moves money in one transaction, using the caller's context.
func paymentsService(db *sql.DB) http.HandlerFunc {
	return func(w http.ResponseWriter, r *http.Request) {
		q := r.URL.Query()
		cents, _ := strconv.ParseInt(q.Get("cents"), 10, 64)
		err := transfer(r.Context(), db, q.Get("from"), q.Get("to"), cents)
		log := logger(r.Context()).With("service", "payments")
		if err != nil {
			log.Warn("transfer rolled back", "err", err)
			http.Error(w, "transfer failed", http.StatusServiceUnavailable)
			return
		}
		log.Info("transfer committed", "cents", cents)
		w.WriteHeader(http.StatusCreated)
	}
}

func transfer(ctx context.Context, db *sql.DB, from, to string, cents int64) error {
	tx, err := db.BeginTx(ctx, nil)
	if err != nil {
		return fmt.Errorf("begin: %w", err)
	}
	defer tx.Rollback() // no-op after Commit; undoes everything otherwise

	var balance int64
	if err := tx.QueryRowContext(ctx, `SELECT balance_cents FROM accounts WHERE id = $1 FOR UPDATE`, from).Scan(&balance); err != nil {
		return fmt.Errorf("lock source: %w", err)
	}
	if balance < cents {
		return errors.New("insufficient funds")
	}
	if _, err := tx.ExecContext(ctx, `UPDATE accounts SET balance_cents = balance_cents - $1 WHERE id = $2`, cents, from); err != nil {
		return fmt.Errorf("debit: %w", err)
	}
	if _, err := tx.ExecContext(ctx, `UPDATE accounts SET balance_cents = balance_cents + $1 WHERE id = $2`, cents, to); err != nil {
		return fmt.Errorf("credit: %w", err)
	}
	if _, err := tx.ExecContext(ctx, `INSERT INTO transactions (from_account, to_account, amount_cents, note) VALUES ($1, $2, $3, 'checkout')`, from, to, cents); err != nil {
		return fmt.Errorf("record: %w", err)
	}
	return tx.Commit()
}
```

## Failure Modes at Scale

*Stop 5 of 5.*

### Failure 1: `context.Background()` in the middle of a request

Scenario 4 runs checkout with one mistake: it calls the fraud and payments services with `context.Background()` instead of its request context. Same 40 ms budget as scenario 2, which failed properly with a 504:

```text
=== 4. budget 40ms, downstream called with context.Background()
level=INFO msg="velocity query finished" req=GEQE26BW service=fraud took=79ms sent_24h_cents=2500
level=INFO msg="transfer committed" req=AZNZZFOG service=payments cents=2500
client: 200 OK after 83ms
postgres: 0 fraud scan process(es) still running
postgres: balance 97500 -> 95000 cents, audit rows +1
```

Three things went wrong, and only one is the one people expect:

1. **The budget was ignored.** The request took 83 ms and succeeded. Nothing below checkout knew there was a 40 ms deadline.
2. **Money moved on a request that should have timed out.** In a real system with a caller-side timeout, the caller would have given up, told the customer it failed, and possibly retried, while this transfer committed anyway.
3. **The request ID was lost.** `Background()` carries no values, so the fraud and payments services each invented their own IDs (`GEQE26BW`, `AZNZZFOG`). Their logs can no longer be tied to each other or to checkout.

<Callout kind="warn" title="Where Background() belongs">

`context.Background()` is for the top of a program: `main`, initialisation, tests, and the root of long-lived background workers. Inside a request, derive from the request's context. When work must deliberately outlive the request, use `context.WithoutCancel(ctx)`, which keeps the values (like the request ID) and drops only the cancellation, then give it its own timeout (Failure 4).

</Callout>

### Failure 2: forgetting `cancel`

`context.WithTimeout` and `WithCancel` return a `cancel` function. Until it's called, or the deadline passes, the child stays registered with its parent, together with its timer. With a long-lived parent (a server's base context) and a long timeout, forgotten cancels pile up:

```go novet
	"context"
	"fmt"
	"runtime"
	"time"

func heapMB() float64 {
	runtime.GC()
	var m runtime.MemStats
	runtime.ReadMemStats(&m)
	return float64(m.HeapInuse) / (1 << 20)
}

func handle(callCancel bool) {
	ctx, cancel := context.WithTimeout(server, 5*time.Second)
	if callCancel {
		defer cancel()
	}
	_ = ctx // the request finishes in microseconds
}

func main() {
	for _, callCancel := range []bool{true, false} {
		before := heapMB()
		for range 100_000 {
			handle(callCancel)
		}
```

### Failure 3: losing the cancellation signal in errors

When a call fails because the context ended, wrap the error with `%w` so callers can still ask `errors.Is(err, context.Canceled)` or `errors.Is(err, context.DeadlineExceeded)`. Checkout uses its own `ctx.Err()` to choose the status code:

```go
status := http.StatusBadGateway
if errors.Is(ctx.Err(), context.DeadlineExceeded) {
	status = http.StatusGatewayTimeout
}
```

That's why scenario 2 (out of time) answered 504 but scenario 3 (client gone) logged 502: the client had already left, so the status is only for the logs, but it records *why*. Exercise 3 makes that clearer with `context.WithTimeoutCause`.

### Failure 4: work that must survive the request

Checkout records an audit row for every attempt, including failed ones. If it used the request's context, a timed-out request couldn't write its own audit row: the context is already done. Look at `audit` in `checkout.go` (below): it uses `context.WithoutCancel(ctx)`, which keeps the request ID but ignores cancellation, plus its own two-second timeout so it can't hang forever. In every scenario above, including the timeouts and the client hang-up, the database showed **audit rows +1**.

```go noverify
package main

import (
	"context"
	"database/sql"
	"encoding/json"
	"errors"
	"fmt"
	"net/http"
	"strconv"
	"time"

	"golang.org/x/sync/errgroup"
)

type Checkout struct {
	db          *sql.DB
	fraudURL    string
	paymentsURL string
	client      *http.Client
	background  bool // the bug: call downstream with context.Background()
}

func (c *Checkout) ServeHTTP(w http.ResponseWriter, r *http.Request) {
	q := r.URL.Query()
	budget, _ := time.ParseDuration(q.Get("budget"))
	ctx, cancel := context.WithTimeout(r.Context(), budget) // one ceiling for the whole request
	defer cancel()

	// Whatever happens, record that a checkout was attempted, even if the
	// request's context is already done. WithoutCancel keeps the request ID.
	defer c.audit(ctx, q.Get("from"), "checkout attempted")

	callCtx := ctx
	if c.background {
		callCtx = context.Background()
	}

	// Two reads that don't depend on each other, run concurrently.
	g, gctx := errgroup.WithContext(callCtx)
	var approved bool
	var balance int64
	g.Go(func() error {
		return c.getJSON(gctx, c.fraudURL+"?account="+q.Get("from"), &struct{ Approve *bool }{&approved})
	})
	g.Go(func() error {
		return c.db.QueryRowContext(gctx, `SELECT balance_cents FROM accounts WHERE id = $1`, q.Get("from")).Scan(&balance)
	})
	if err := g.Wait(); err != nil {
		c.fail(w, ctx, err)
		return
	}
	if !approved {
		http.Error(w, "declined by fraud check", http.StatusForbidden)
		return
	}
	if cents, _ := strconv.ParseInt(q.Get("cents"), 10, 64); balance < cents {
		http.Error(w, "insufficient funds", http.StatusPaymentRequired)
		return
	}

	url := fmt.Sprintf("%s?from=%s&to=%s&cents=%s", c.paymentsURL, q.Get("from"), q.Get("to"), q.Get("cents"))
	req, _ := http.NewRequestWithContext(callCtx, http.MethodPost, url, nil)
	resp, err := c.client.Do(req)
	if err != nil {
		c.fail(w, ctx, err)
		return
	}
	resp.Body.Close()
	if resp.StatusCode != http.StatusCreated {
		c.fail(w, ctx, fmt.Errorf("payments: %s", resp.Status))
		return
	}
	w.Write([]byte("paid\n"))
}

func (c *Checkout) getJSON(ctx context.Context, url string, v any) error {
	req, err := http.NewRequestWithContext(ctx, http.MethodGet, url, nil)
	if err != nil {
		return err
	}
	resp, err := c.client.Do(req)
	if err != nil {
		return err
	}
	defer resp.Body.Close()
	if resp.StatusCode != http.StatusOK {
		return fmt.Errorf("%s: %s", url, resp.Status)
	}
	return json.NewDecoder(resp.Body).Decode(v)
}

func (c *Checkout) fail(w http.ResponseWriter, ctx context.Context, err error) {
	status := http.StatusBadGateway
	if errors.Is(ctx.Err(), context.DeadlineExceeded) {
		status = http.StatusGatewayTimeout
	}
	logger(ctx).Warn("checkout failed", "status", status, "err", err)
	http.Error(w, http.StatusText(status), status)
}

// audit must be written even after the request's deadline has passed.
func (c *Checkout) audit(ctx context.Context, account, event string) {
	actx, cancel := context.WithTimeout(context.WithoutCancel(ctx), 2*time.Second)
	defer cancel()
	_, err := c.db.ExecContext(actx, `INSERT INTO audit_log (request_id, account, event) VALUES ($1, $2, $3)`, requestID(ctx), account, event)
	if err != nil {
		logger(ctx).Error("audit write failed", "err", err)
	}
}
```

<UnderTheHood title="How cancellation propagates through the context tree">

A context made by `WithCancel`, `WithTimeout` or `WithDeadline` is a `cancelCtx`. It registers itself with its nearest cancellable ancestor, which keeps a set of its children. When `cancel` runs (or the timer fires):

1. It closes its `done` channel, which wakes every goroutine blocked on `<-ctx.Done()` at once.
2. It cancels each registered child, recursively.
3. It removes itself from its parent's set, so it can be garbage-collected.

Each `cancelCtx` has its own mutex; there's no global lock over the tree. The `Done` channel is created lazily on first use, so contexts nobody waits on never allocate one.

Three newer tools round out the package:

- **`context.WithoutCancel(ctx)`** (Go 1.21): keeps the values, drops cancellation and the deadline. Used above for the audit write.
- **`context.AfterFunc(ctx, f)`** (Go 1.21): runs `f` in its own goroutine when `ctx` is done, and returns a `stop` function to unregister it. Tidier than a goroutine blocked on `<-ctx.Done()`.
- **`WithCancelCause` / `WithTimeoutCause` and `context.Cause`** (Go 1.20/1.21): record *why* a context ended. Since Go 1.26, `signal.NotifyContext` sets a cause too; Exercise 4 prints it after a real SIGTERM: `terminated signal received`.

The package's source (`src/context/context.go`, about 800 lines in Go 1.27) is short enough to read in one sitting.

</UnderTheHood>

<Exercise n={1} title="A per-hop budget" level="easy">

Give the fraud check at most 60% of whatever time the request has left, so a slow fraud service can't consume the whole budget. Where does the code go, and why can't it ever make the request longer?

<Solution>

In `ServeHTTP`, before starting the errgroup, derive a shorter context for the fraud call only:

```go
fraudCtx := gctx
if deadline, ok := gctx.Deadline(); ok {
	var cancelFraud context.CancelFunc
	fraudCtx, cancelFraud = context.WithTimeout(gctx, time.Until(deadline)*6/10)
	defer cancelFraud()
}
g.Go(func() error {
	return c.getJSON(fraudCtx, c.fraudURL+"?account="+q.Get("from"), &struct{ Approve *bool }{&approved})
})
```

`fraudCtx` is a child of `gctx`, whose deadline is the request's budget. A child's deadline is the earlier of its own and its parent's, so this can only shorten the fraud call. If `gctx` has no deadline (for example, the bug path with `Background()`), `Deadline` reports `ok == false` and nothing changes.

Run scenario 2 after this change and something changes that you might not expect: checkout answers **502**, not 504. The fraud hop's own deadline (24 ms, 60% of 40) fires while checkout's context is still alive, so `fail`'s check of `ctx.Err()` finds nothing. The timeout is inside the returned error instead, so check that too:

```go
if errors.Is(ctx.Err(), context.DeadlineExceeded) || errors.Is(err, context.DeadlineExceeded) {
	status = http.StatusGatewayTimeout
}
```

`http.Client` wraps the context's error, so `errors.Is` finds it. With both changes, scenario 2 answered `504 Gateway Timeout after 30ms`, with the fraud call cut off earlier than before.

</Solution>

</Exercise>

```text
level=WARN msg="checkout failed" req=EOTXCYOX status=504 cause="checkout budget of 40ms exceeded" …
level=WARN msg="checkout failed" req=HBDPDEFV status=502 cause="context canceled" …
```

`ctx.Err()` is still `context.DeadlineExceeded` in the first case, so existing `errors.Is` checks keep working; the cause is extra information. In the second, the parent (`r.Context()`) was cancelled by the client leaving, so the cause is the parent's plain `context canceled`.

</Solution>

</Exercise>

<Exercise n={4} title="Shut down and say why" level="medium">

Write a server that shuts down gracefully on SIGTERM or SIGINT and logs which signal stopped it. Build it, send it a request, then stop it with `kill -TERM`.

<Solution>

```go
package main

import (
	"context"
	"errors"
	"log/slog"
	"net"
	"net/http"
	"os"
	"os/signal"
	"syscall"
	"time"
)

func main() {
	ctx, stop := signal.NotifyContext(context.Background(), syscall.SIGTERM, syscall.SIGINT)
	defer stop()

	srv := &http.Server{
		Addr: "127.0.0.1:8090",
		Handler: http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
			w.Write([]byte("ok\n"))
		}),
		BaseContext: func(net.Listener) context.Context { return ctx }, // requests see shutdown too
	}
	go func() {
		if err := srv.ListenAndServe(); !errors.Is(err, http.ErrServerClosed) {
			slog.Error("listen", "err", err)
			os.Exit(1)
		}
	}()
	slog.Info("listening", "addr", srv.Addr, "pid", os.Getpid())

	<-ctx.Done()
	slog.Info("shutting down", "cause", context.Cause(ctx))

	shutdownCtx, cancel := context.WithTimeout(context.WithoutCancel(ctx), 10*time.Second)
	defer cancel()
	if err := srv.Shutdown(shutdownCtx); err != nil {
		slog.Error("shutdown", "err", err)
	}
	slog.Info("stopped")
}
```

```text
$ go build -o srv . && ./srv &
2026/09/26 16:24:20 INFO listening addr=127.0.0.1:8090 pid=74419
$ curl 127.0.0.1:8090
ok
$ kill -TERM 74419
2026/09/26 16:24:28 INFO shutting down cause="terminated signal received"
2026/09/26 16:24:28 INFO stopped
```

`context.Cause` reporting the signal is new in Go 1.26; before that you only got `context canceled`. The shutdown context is derived with `WithoutCancel`, because `ctx` is already cancelled at this point and `Shutdown` needs time to let in-flight requests finish.

</Solution>

</Exercise>

<Exercise n={5} title="Test the decline path" level="hard">

Write a test proving that a declined checkout never calls payments. Use the real database for the balance, and a stand-in fraud service that declines everything. This is a legitimate use of a test double: the thing under test is checkout's decision, not the fraud rule.

```go noverify
	}
```

<Recap>

- **Pass the request's context to every blocking call**, and derive from it; never `context.Background()` mid-request. Measured: a client hang-up at 30 ms stopped a Postgres scan at 31 ms across two HTTP hops.
- **One budget per request** with `WithTimeout(r.Context(), …)`; children can only shorten it; per-hop budgets are fractions of what's left. A 40 ms budget answered 504 in 45 ms.
- **Context values**: only request-scoped data (an ID, the user, a tagged logger), under unexported key types; carry the ID across services in a header.
- **HTTP** carries cancellation but not deadlines; **gRPC** carries both; **databases** need the context on every call, inside transactions too: a transfer cancelled between debit and credit rolled back cleanly.
- **Failure modes**: `Background()` mid-request ignored the budget, moved money on a request that should have failed, and lost the request ID; forgotten `cancel` held 30.6 MB per 100,000 requests (`go vet` flags it); use `%w` and `ctx.Err()` to keep the reason; `WithoutCancel` + a timeout for work that must outlive the request.

</Recap>
