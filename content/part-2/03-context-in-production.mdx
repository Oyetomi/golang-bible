## Cancellation Discipline

Here's the scenario I want you to live in for the first section. Your team ships a `/checkout` endpoint. A user on a flaky mobile connection initiates a purchase — `POST /checkout` hits your service, which fans out to three downstreams: a **fraud service**, a **payment processor**, and an **inventory service**. Each downstream has its own network call, its own DB query underneath. The client drops the connection after 80ms because the signal cut out.

Without rigorous cancellation discipline, here is what happens: the three downstream goroutines keep running. The DB connections stay open inside the transaction. The fraud service finishes its ML scoring. The payment service sends the charge to the card network. None of that work matters — the client is gone. But your service doesn't know that, because nobody propagated the disconnect signal.

That's the problem. Here's the discipline that prevents it.

### Rule 1: Every blocking or I/O call takes ctx as its first argument

If a function makes a network call, touches a database, waits on a goroutine, or calls another function that does any of those things — `ctx context.Context` is argument zero. No exceptions. No "it's a quick call." No "it's internal."

```go
// Every function signature in a production service looks like this.
func fetchFraudScore(ctx context.Context, accountID string) (FraudResult, error)
func chargeCard(ctx context.Context, charge ChargeRequest) (ChargeResult, error)
func reserveInventory(ctx context.Context, sku string, qty int) error
func postLedgerEntry(ctx context.Context, tx *sql.Tx, entry LedgerEntry) error
```

The context is the thread that connects a client request to every unit of work it spawns. Break that thread once and the cancellation signal can't reach the work that needs to stop.

### Rule 2: Every goroutine you spawn must watch ctx.Done()

Spawning a goroutine without wiring it to the context is the same as saying "this work should run forever, regardless of what the caller decides." That is almost never what you mean.

The pattern is always a `select` racing the goroutine's work channel against `ctx.Done()`:

```go
package main

import (
	"context"
	"fmt"
	"time"
)

// FraudResult holds the outcome of a fraud check.
type FraudResult struct {
	Score int
	Pass  bool
}

// checkFraud calls the fraud service with full cancellation discipline.
// The inner goroutine wraps the actual work so we can select on ctx.Done().
func checkFraud(ctx context.Context, accountID string) (FraudResult, error) {
	type outcome struct {
		res FraudResult
		err error
	}
	done := make(chan outcome, 1)

	go func() {
		// Simulate the fraud service taking 120ms.
		select {
		case <-time.After(120 * time.Millisecond):
			done <- outcome{FraudResult{Score: 12, Pass: true}, nil}
		case <-ctx.Done():
			// Context fired before the work finished — don't send a stale result.
			return
		}
	}()

	select {
	case out := <-done:
		return out.res, out.err
	case <-ctx.Done():
		return FraudResult{}, fmt.Errorf("fraud check: %w", ctx.Err())
	}
}

func main() {
	ctx, cancel := context.WithTimeout(context.Background(), 200*time.Millisecond)
	defer cancel()

	result, err := checkFraud(ctx, "acc-8821")
	if err != nil {
		fmt.Println("fraud check aborted:", err)
		return
	}
	fmt.Printf("fraud score: %d, pass: %v\n", result.Score, result.Pass)
}
```

## Deadlines & Budgets

Here's where production context discipline gets genuinely interesting. A request doesn't just have *one* deadline — it has a **budget** that must be apportioned across every downstream hop.

Scenario: your checkout endpoint has a 250ms SLA. That 250ms must cover fraud scoring, payment processing, and inventory reservation — potentially in parallel, but each with their own network latency and tail risk. How do you carve up the budget?

### The request-wide deadline pattern

The handler sets the ceiling — 250ms total. Each downstream call gets its own child context with a tighter deadline that fits within the remaining budget.

```go
package main

import (
	"context"
	"fmt"
	"time"
)

// checkout runs the full checkout flow against a 250ms request budget.
// Each downstream gets a share of the budget, not the full 250ms.
func checkout(ctx context.Context, accountID, sku string, cents int64) error {
	// The request-wide ceiling: 250ms from now.
	// If the incoming ctx has a sooner deadline, that one wins.
	ctx, cancel := context.WithTimeout(ctx, 250*time.Millisecond)
	defer cancel()

	// Fraud check: 80ms budget. Must finish before payment starts.
	fraudCtx, fraudCancel := context.WithTimeout(ctx, 80*time.Millisecond)
	defer fraudCancel()
	if err := checkFraud(fraudCtx, accountID); err != nil {
		return fmt.Errorf("fraud: %w", err)
	}

	// Remaining budget: ~170ms. Payment gets up to 120ms.
	// The parent ctx still has its 250ms ceiling — this is an additional constraint.
	payCtx, payCancel := context.WithTimeout(ctx, 120*time.Millisecond)
	defer payCancel()
	if err := chargeCard(payCtx, cents); err != nil {
		return fmt.Errorf("payment: %w", err)
	}

	// Inventory: whatever is left of the 250ms (roughly 30ms at best).
	// We don't add a new timeout here — the parent ctx deadline already covers it.
	if err := reserveInventory(ctx, sku, 1); err != nil {
		return fmt.Errorf("inventory: %w", err)
	}

	return nil
}

func checkFraud(ctx context.Context, accountID string) error {
	select {
	case <-time.After(60 * time.Millisecond): // simulates 60ms fraud check
		return nil
	case <-ctx.Done():
		return ctx.Err()
	}
}

func chargeCard(ctx context.Context, cents int64) error {
	select {
	case <-time.After(100 * time.Millisecond): // simulates 100ms payment
		return nil
	case <-ctx.Done():
		return ctx.Err()
	}
}

func reserveInventory(ctx context.Context, sku string, qty int) error {
	select {
	case <-time.After(20 * time.Millisecond): // simulates 20ms inventory lock
		return nil
	case <-ctx.Done():
		return ctx.Err()
	}
}

func main() {
	ctx := context.Background()
	if err := checkout(ctx, "acc-8821", "SKU-4892", 4999); err != nil {
		fmt.Println("checkout failed:", err)
		return
	}
	fmt.Println("checkout OK — total latency within 250ms budget")
}
```

### How child deadlines interact with parent deadlines

**On the job:** Meridian's checkout has a 250ms SLA. If an engineer gives the fraud sub-call a 500ms child deadline thinking "safety margin," they've silently achieved nothing — the parent's 250ms still wins. Understanding this is the difference between correct budget allocation and SLA violations that look mysterious in the traces.

This interaction trips up experienced engineers. Commit it to memory:

**A child context always inherits the *sooner* of its own deadline and the parent's deadline.**

If the parent has a 250ms deadline and you call `WithTimeout(parent, 500*time.Second)`, the child's effective deadline is still 250ms — the parent's. Your 500ms is silently ignored. The runtime picks the earlier one.

## Request-Scoped Values Done Right

Part 1 introduced the typed-key pattern. Here we go deeper — into exactly what belongs in context, what does not, and the production-ready patterns for the three values that almost every service needs.

### The three values that belong in context

In every real backend service, there are exactly three categories of value that legitimately belong in a context:

1. **Request ID / trace ID** — for correlating logs and traces across services without threading it through every function signature.
2. **Authenticated principal** — the identity of the caller, established by auth middleware before the handler runs.
3. **Logger or trace span** — a request-scoped logger already carrying the request ID, so every `slog.InfoContext` in the call stack automatically includes the right fields.

Everything else — database connections, HTTP clients, feature flags, configuration, service dependencies — belongs in struct fields or function parameters. Those are not request-scoped; they live for the lifetime of the service, not one request.

### Production-grade context key and accessor pattern

**On the job:** A request ID set in middleware must surface in every log line from every downstream service call — without threading an extra parameter through 15 function signatures. If you skip the typed-key pattern and use a bare string key instead, any package can accidentally overwrite it, and you spend an incident debugging why correlation IDs are missing from exactly half your logs.

Here's the full, production-ready pattern. One file per type. Unexported key, exported constructors and accessors with typed ok returns.

```go
package main

import (
	"context"
	"fmt"
	"log/slog"
	"os"
)

// ─── Request ID ───────────────────────────────────────────────────────────────

// requestIDKey is unexported. No other package can construct this type,
// so no key collision is possible even if they use the same string "requestID".
type requestIDKey struct{}

// WithRequestID attaches a request ID to the context.
// Call this in your outermost middleware, before any handler runs.
func WithRequestID(ctx context.Context, id string) context.Context {
	return context.WithValue(ctx, requestIDKey{}, id)
}

// RequestID retrieves the request ID. Returns ("", false) if not set.
// The caller decides what to do with a missing ID — don't panic, don't default.
func RequestID(ctx context.Context) (string, bool) {
	id, ok := ctx.Value(requestIDKey{}).(string)
	return id, ok
}

// ─── Auth Principal ───────────────────────────────────────────────────────────

// Principal represents the authenticated caller identity.
type Principal struct {
	UserID   int64
	Role     string
	TenantID string
}

type principalKey struct{}

// WithPrincipal attaches the authenticated principal to the context.
// Set by auth middleware after token validation.
func WithPrincipal(ctx context.Context, p Principal) context.Context {
	return context.WithValue(ctx, principalKey{}, p)
}

// PrincipalFromContext retrieves the auth principal.
// ok=false means the request was not authenticated — callers must check.
func PrincipalFromContext(ctx context.Context) (Principal, bool) {
	p, ok := ctx.Value(principalKey{}).(Principal)
	return p, ok
}

// ─── Request-scoped logger ────────────────────────────────────────────────────

type loggerKey struct{}

// WithLogger attaches a pre-decorated slog.Logger to the context.
// The logger should already carry request-scoped fields (request_id, user_id).
func WithLogger(ctx context.Context, l *slog.Logger) context.Context {
	return context.WithValue(ctx, loggerKey{}, l)
}

// Logger retrieves the request-scoped logger, or the default if none is set.
// Never returns nil — safe to call anywhere.
func Logger(ctx context.Context) *slog.Logger {
	if l, ok := ctx.Value(loggerKey{}).(*slog.Logger); ok {
		return l
	}
	return slog.Default()
}

// ─── Middleware wiring ────────────────────────────────────────────────────────

// enrichContext simulates what your auth + logging middleware does before
// the handler sees the request.
func enrichContext(ctx context.Context, reqID string, userID int64) context.Context {
	ctx = WithRequestID(ctx, reqID)
	ctx = WithPrincipal(ctx, Principal{UserID: userID, Role: "member", TenantID: "tenant-42"})

	// Build a logger that carries request-scoped fields permanently.
	l := slog.New(slog.NewJSONHandler(os.Stdout, nil)).With(
		"request_id", reqID,
		"user_id", userID,
	)
	ctx = WithLogger(ctx, l)
	return ctx
}

func handleCheckout(ctx context.Context) {
	log := Logger(ctx) // always decorated with request_id + user_id

	p, ok := PrincipalFromContext(ctx)
	if !ok {
		log.Error("unauthenticated request reached checkout handler")
		return
	}

	reqID, _ := RequestID(ctx)
	log.Info("processing checkout",
		"account_id", fmt.Sprintf("acc-%d", p.UserID),
		"req_id", reqID,
	)
}

func main() {
	ctx := context.Background()
	ctx = enrichContext(ctx, "req-f4a9b2c1", 1042)
	handleCheckout(ctx)
}
```

### What belongs in context vs what does not

<ConceptGrid cols={2}>
  <ConceptCard label="Belongs in context">Request ID / trace ID. Authenticated user identity. Request-scoped logger or trace span. Locale or timezone when it's genuinely per-request. These are cross-cutting concerns that would require threading a parameter through dozens of call sites.</ConceptCard>
  <ConceptCard label="Does NOT belong in context">Database connections, HTTP clients, Redis clients. Service-layer dependencies. Feature flags fetched once at startup. Configuration values. Optional function parameters. Anything with a lifetime longer than one request. These belong in struct fields, dependency injection, or explicit function parameters.</ConceptCard>
  <Gotcha>Using context as a dependency-injection mechanism is a code smell. `ctx.Value(dbKey{})` to retrieve a database connection means the compiler cannot enforce that the DB is present — you get nil at runtime instead of a compile error. Pass dependencies as struct fields or constructor arguments.</Gotcha>
</ConceptGrid>

<UnderTheHood title="How context.Value walks the chain — and why it costs O(depth) (Go 1.26)">

Every `context.WithValue` call creates a new `valueCtx` node:

```go
// From src/context/context.go (simplified).
type valueCtx struct {
    Context        // parent — the linked list spine
    key, val any
}

func (c *valueCtx) Value(key any) any {
    if c.key == key {
        return c.val  // found at this node — O(1) in the best case
    }
    return value(c.Context, key)  // recurse to parent — O(depth) worst case
}
```

Each `WithValue` adds one node. A `Value(key)` lookup walks from the tip of the chain toward the root until it finds a match or hits `emptyCtx`. That walk is **O(depth)** — if you have 20 `WithValue` calls stacked in middleware, every `ctx.Value` call walks up to 20 nodes.

The key comparison uses `==`. This is why your key must be a **comparable** type — and why a zero-size unexported struct like `type requestIDKey struct{}` is ideal: it's comparable, zero allocation, and impossible for an external package to construct.

`context.WithValue` panics at construction time if the key is nil or not comparable — an early catch instead of a mysterious nil at lookup time, a guard the package has carried since its early days. Each `cancelCtx` uses its own mutex (there is no global cancel-tree lock; see "The context Package, In Depth" in Part 1), and the `valueCtx` chain semantics are unchanged through Go 1.26.

**Implication for production:** keep your `WithValue` chain shallow. If you're stacking more than four or five context values, it's usually a sign that some of those values should be bundled into a single struct and attached as one `WithValue` call. That cuts the lookup depth and clarifies the data model.

</UnderTheHood>

## Propagating Through HTTP, gRPC & DB

This section is the plumbing chapter. You know the theory — now here is exactly how to wire cancellation through each layer you'll encounter in a real microservice stack.

### HTTP: r.Context() and context-aware outbound requests

**Inbound requests:** `r.Context()` is already wired. The `http.Server` creates a cancellable context for each request and attaches it. When the client disconnects, the server cancels it. You get this for free — just thread `r.Context()` through.

**Outbound requests:** use `http.NewRequestWithContext`. A bare `http.NewRequest` creates a request with `context.Background()` — the outbound call will never be cancelled, even if the inbound client disconnects.

```go
package main

import (
	"context"
	"fmt"
	"net/http"
	"net/http/httptest"
	"time"
)

// callFraudAPI makes a context-aware outbound HTTP call to the fraud service.
// If ctx is cancelled before the response arrives, the underlying TCP connection
// is closed and the function returns ctx.Err() wrapped in a meaningful error.
func callFraudAPI(ctx context.Context, client *http.Client, accountID string) error {
	// http.NewRequestWithContext — the only correct way to make cancellable HTTP calls.
	req, err := http.NewRequestWithContext(ctx, http.MethodGet,
		"https://fraud.internal/v1/score?account="+accountID, nil)
	if err != nil {
		return fmt.Errorf("build request: %w", err)
	}

	resp, err := client.Do(req)
	if err != nil {
		// If ctx was cancelled, err wraps the context error.
		// errors.Is(err, context.DeadlineExceeded) is true.
		return fmt.Errorf("fraud API: %w", err)
	}
	defer resp.Body.Close()

	if resp.StatusCode != http.StatusOK {
		return fmt.Errorf("fraud API: unexpected status %d", resp.StatusCode)
	}
	return nil
}

// checkoutHandler wires r.Context() through the entire call stack.
func checkoutHandler(w http.ResponseWriter, r *http.Request) {
	ctx, cancel := context.WithTimeout(r.Context(), 200*time.Millisecond)
	defer cancel()

	client := &http.Client{Timeout: 30 * time.Second} // transport-level safety net
	if err := callFraudAPI(ctx, client, r.URL.Query().Get("account")); err != nil {
		if ctx.Err() != nil {
			http.Error(w, "request timed out", http.StatusGatewayTimeout)
			return
		}
		http.Error(w, "fraud check failed", http.StatusBadGateway)
		return
	}
	fmt.Fprintln(w, "checkout OK")
}

func main() {
	// Use httptest to drive the handler without a live server.
	ts := httptest.NewServer(http.HandlerFunc(checkoutHandler))
	defer ts.Close()

	ctx, cancel := context.WithTimeout(context.Background(), 500*time.Millisecond)
	defer cancel()

	req, _ := http.NewRequestWithContext(ctx, http.MethodGet,
		ts.URL+"/checkout?account=acc-8821", nil)
	resp, err := http.DefaultClient.Do(req)
	if err != nil {
		fmt.Println("request failed:", err)
		return
	}
	defer resp.Body.Close()
	fmt.Println("status:", resp.Status)
}
```

### gRPC: deadlines and metadata propagate over the wire

gRPC has first-class deadline support: when you pass a context with a deadline to a gRPC call, the deadline is serialized into the gRPC metadata headers and sent to the server. The server reconstructs the deadline in its own context — without any explicit deadline forwarding code on your part. This is one of the most compelling reasons to prefer gRPC for internal service-to-service calls.

### Database: QueryContext, ExecContext, BeginTx — every call, every time

The `database/sql` package has context-aware variants of every operation. Use them unconditionally.

```go
package main

import (
	"context"
	"database/sql"
	"fmt"
	"time"
)

// postTransfer executes a double-entry transfer inside a context-aware transaction.
// If ctx fires mid-transaction, BeginTx / ExecContext return immediately and
// the deferred Rollback cleans up the connection.
func postTransfer(ctx context.Context, db *sql.DB, fromID, toID string, cents int64) error {
	// BeginTx: the transaction inherits ctx's deadline and cancellation.
	// If ctx fires before the DB responds, BeginTx returns ctx.Err().
	tx, err := db.BeginTx(ctx, &sql.TxOptions{Isolation: sql.LevelReadCommitted})
	if err != nil {
		return fmt.Errorf("begin tx: %w", err)
	}
	// Rollback is a safe no-op after a successful Commit.
	defer tx.Rollback()

	// Debit the sender. ExecContext cancels the network write if ctx fires.
	if _, err = tx.ExecContext(ctx,
		`UPDATE accounts SET balance_cents = balance_cents - $1
		 WHERE id = $2 AND balance_cents >= $1`,
		cents, fromID,
	); err != nil {
		return fmt.Errorf("debit %s: %w", fromID, err)
	}

	// Credit the receiver.
	if _, err = tx.ExecContext(ctx,
		`UPDATE accounts SET balance_cents = balance_cents + $1 WHERE id = $2`,
		cents, toID,
	); err != nil {
		return fmt.Errorf("credit %s: %w", toID, err)
	}

	// Commit also respects ctx — if the deadline fires during commit,
	// the transaction is rolled back by the server.
	if err = tx.Commit(); err != nil {
		return fmt.Errorf("commit: %w", err)
	}
	return nil
}

func main() {
	// Illustrative: no live DB in playground.
	// In production, db is injected — never a global.
	ctx, cancel := context.WithTimeout(context.Background(), 500*time.Millisecond)
	defer cancel()

	fmt.Printf("BeginTx, ExecContext, Commit — all honour the %v deadline\n",
		func() time.Duration {
			d, _ := ctx.Deadline()
			return time.Until(d).Round(time.Millisecond)
		}(),
	)
	_ = postTransfer // illustrative
}
```

## Failure Modes at Scale

This section is the autopsy report. These are the bugs that survive code review, slip through testing, and show up in your service at 10 000 req/s. Each one is a Gotcha you will now recognize on sight.

### Failure mode 1: Missing cancel() — the silent resource accumulator

**On the job:** Code that creates a timeout context but discards the cancel function is one of the most common context leaks in production Go — it survives code review, passes tests (which don't run long enough to see the accumulation), and only surfaces as gradual memory and timer overhead at sustained load. With a long-lived parent that does not cancel first, Meridian's 10 000 req/s and a 5-second timeout would mean roughly 50 000 retained timeout contexts at steady state.

Every `WithCancel`, `WithTimeout`, and `WithDeadline` call registers the child in the parent's cancel list and (for `WithTimeout`/`WithDeadline`) registers a timer. If you never call `cancel()`, those resources accumulate until the deadline fires or the *parent* context is cancelled — which for a long-running service may be much later than the work itself.

<ConceptGrid cols={1}>
  <Gotcha>Discarding the cancel function — `ctx, _ = context.WithTimeout(parent, d)` — is the single most common context leak in production Go. The linter `go vet` catches this with the `lostcancel` check. Wire `go vet` (or `golangci-lint`) into CI and treat it as a hard failure. You should never see this in merged code.</Gotcha>
</ConceptGrid>

```go
// DO NOT SHIP THIS.
func leakyMiddleware(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		// cancel is discarded — cleanup waits for timeout or r.Context() cancellation.
		ctx, _ := context.WithTimeout(r.Context(), 5*time.Second)
		next.ServeHTTP(w, r.WithContext(ctx))
		// 10 000 requests/s × 5s timeout = roughly 50 000 retained timeout contexts at steady state.
	})
}

// CORRECT.
func cleanMiddleware(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		ctx, cancel := context.WithTimeout(r.Context(), 5*time.Second)
		defer cancel() // fires when the handler returns — always within one request lifetime
		next.ServeHTTP(w, r.WithContext(ctx))
	})
}
```

### Failure mode 2: Deadline already exceeded before work starts

At high load, there is a real probability that by the time a goroutine is scheduled and begins work, the context it received has *already* expired. If you don't check `ctx.Err()` before starting expensive operations, you do unnecessary work and generate misleading errors.

```go
package main

import (
	"context"
	"fmt"
	"time"
)

// processJob checks the context before beginning expensive work.
// At high load, the context may already be expired by the time this runs.
func processJob(ctx context.Context, jobID string) error {
	// Fast-path: check before doing anything expensive.
	if err := ctx.Err(); err != nil {
		return fmt.Errorf("job %s: context already done before start: %w", jobID, err)
	}

	// Now safe to begin expensive work.
	select {
	case <-time.After(50 * time.Millisecond):
		return nil
	case <-ctx.Done():
		return fmt.Errorf("job %s: %w", jobID, ctx.Err())
	}
}

func main() {
	// Simulate a context that expires before the worker is scheduled.
	ctx, cancel := context.WithTimeout(context.Background(), 1*time.Millisecond)
	defer cancel()

	time.Sleep(5 * time.Millisecond) // simulate scheduler delay / queue depth

	err := processJob(ctx, "ledger-post-4892")
	if err != nil {
		fmt.Println("job aborted:", err)
		return
	}
	fmt.Println("job done")
}
```

### Failure mode 4: Goroutines outliving the request

A goroutine that holds a reference to request-scoped resources (a DB connection from a transaction, an open file, a streaming response writer) must not outlive the request. If it does, you get use-after-free on the response writer, connection leaks, and corrupted state.

The fix is `errgroup` or explicit signaling:

```go
package main

import (
	"context"
	"fmt"
	"time"

	"golang.org/x/sync/errgroup"
)

// fanOutCheckout uses errgroup to fan out to three services and cancel all
// if any one fails or the context expires. No goroutine outlives the call.
func fanOutCheckout(ctx context.Context, accountID string, cents int64) error {
```

<UnderTheHood title="How cancellation propagates through the context tree — Go 1.26 internals">

When `cancel()` is called on a `cancelCtx`, the runtime executes the following (simplified from `src/context/context.go`):

1. **Close `c.done`** — the `chan struct{}` is closed with `close(c.done)`. This is O(1): the runtime scheduler walks the blocked-receiver list and makes each goroutine runnable. Every goroutine `select`-ing on `<-c.done` wakes up simultaneously.
2. **Cancel children** — `c.children` is a `map[canceler]struct{}` of registered child contexts. Each is called `.cancel(false, err, cause)` recursively. The recursion depth equals the depth of the child subtree.
3. **Remove self from parent** — the node removes itself from its parent's `c.children` map, allowing the garbage collector to reclaim the subtree.

There is **no** global lock over the context tree. Each `cancelCtx` carries its own `sync.Mutex`, and a cancel propagates by locking only the contexts directly involved — the node being cancelled and the parent/child it registers with — never an ancestor-wide lock. (`cancelCtxKey` is just the sentinel key `parentCancelCtx` uses to find the nearest `*cancelCtx` ancestor; it is not a lock.) That per-context locking is what keeps cancellation cheap even for services handling 50 000+ req/s each with a multi-hop context tree.

The **`Done()` channel is lazily allocated.** The first call to `Done()` on a `cancelCtx` creates the channel and stores it. Subsequent calls return the same channel. A context that is derived but whose `Done()` is never read pays no channel allocation cost — an optimization for contexts used purely for value propagation.

**`context.WithoutCancel(parent)`** (added Go 1.21) returns a child that preserves the parent's `Value` chain but has **no deadline and is never cancelled** — its `Done()` is nil and `Err()` is nil even after the parent cancels. (Per the docs: it "returns a copy of parent that is not canceled when parent is canceled… has no Deadline or Err, and its Done channel is nil.") Use this sparingly: a goroutine started with a `WithoutCancel` context must manage its own lifetime. The typical use case is an audit-log write that must commit even if the HTTP handler times out.

**`context.AfterFunc(ctx, f)`** (added Go 1.21) registers `f` to run in a new goroutine when `ctx` is done. Returns a stop function. More composable than `go func() { <-ctx.Done(); f() }()` because it supports multiple registrations and the stop function prevents `f` from running if you call it before `ctx` fires.

**`os/signal.NotifyContext` cause (Go 1.26):** As of Go 1.26, if a signal cancels the context returned by `signal.NotifyContext`, `context.Cause(ctx)` returns an error describing the signal — for example `SIGTERM` or `SIGINT`. Before 1.26, `ctx.Err()` returned `context.Canceled` and you had to track the signal separately. Now graceful-shutdown code can log the termination reason without a parallel channel:

```go
ctx, stop := signal.NotifyContext(context.Background(), syscall.SIGTERM, syscall.SIGINT)
defer stop()
<-ctx.Done()
// As of Go 1.26: context.Cause(ctx) describes the signal that canceled ctx.
log.Info("shutting down", "cause", context.Cause(ctx))
```

As of **Go 1.26**, these internals are stable. The `context` package's source is short (~600 lines) and highly readable — `src/context/context.go` in the stdlib is worth one careful read.

</UnderTheHood>

Use `errgroup.WithContext` to fan out three parallel calls — fraud (70ms), payment (90ms), inventory (50ms) — under a 200ms total budget. Return the first error. Verify with a 150ms budget that the payment goroutine causes a timeout.

```go
import (
	"context"
	"fmt"
	"time"

	"golang.org/x/sync/errgroup"

func fraud(ctx context.Context) error {

	case <-time.After(70 * time.Millisecond):

}

	g.Go(func() error { return inventory(gctx) })

}

	// payment (90ms) is still running at 150ms → DeadlineExceeded.
	ctx150, cancel150 := context.WithTimeout(context.Background(), 150*time.Millisecond)
```

Design a small `reqctx` package (single file is fine) with typed keys and accessor functions for: `RequestID string`, `TenantID string`, and `Principal struct{UserID int64; Role string}`. 	return tid, ok

```go
func WithPrincipal(ctx context.Context, p Principal) context.Context {

		id := r.Header.Get("X-Request-ID")
		if id == "" {
			id = "auto-generated-id" // in prod: use a UUID library
		}
		ctx := WithRequestID(r.Context(), id)
		next.ServeHTTP(w, r.WithContext(ctx))

}
```

<Exercise n={4} title="Detect deadline-exceeded before work starts" level="medium">

Write a `processJob(ctx context.Context, jobID string, workDuration time.Duration) error` that:
1. checks `ctx.Err()` immediately and returns early if already expired
2. otherwise performs the work (simulate with `time.Sleep` inside a select)

Run it with three scenarios: context already expired, context expires during work, work completes in time.

<Solution>

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"time"
)

func processJob(ctx context.Context, jobID string, workDuration time.Duration) error {
	// Fast-path: don't start expensive work if ctx is already done.
	if err := ctx.Err(); err != nil {
		return fmt.Errorf("job %s: already expired: %w", jobID, err)
	}

	select {
	case <-time.After(workDuration):
		return nil
	case <-ctx.Done():
		return fmt.Errorf("job %s: interrupted: %w", jobID, ctx.Err())
	}
}

func main() {
	// Scenario 1: context already expired.
	ctx1, c1 := context.WithTimeout(context.Background(), 1*time.Millisecond)
	defer c1()
	time.Sleep(5 * time.Millisecond)
	err := processJob(ctx1, "job-1", 50*time.Millisecond)
	fmt.Println("scenario 1:", err, "| is DeadlineExceeded:", errors.Is(err, context.DeadlineExceeded))

	// Scenario 2: expires during work.
	ctx2, c2 := context.WithTimeout(context.Background(), 30*time.Millisecond)
	defer c2()
	err = processJob(ctx2, "job-2", 100*time.Millisecond)
	fmt.Println("scenario 2:", err)

	// Scenario 3: completes in time.
	ctx3, c3 := context.WithTimeout(context.Background(), 200*time.Millisecond)
	defer c3()
	err = processJob(ctx3, "job-3", 50*time.Millisecond)
	fmt.Println("scenario 3:", err) // nil
}
```

The fast-path `ctx.Err()` check is critical for worker pools and job queues: by the time a goroutine is dequeued from a worker pool and scheduled, the context that created the job may already be expired. Checking first avoids doing any work for an already-dead request.

</Solution>

<Exercise n={5} title="Audit log that survives a handler timeout" level="hard">

A checkout handler must post an audit log entry *even if the handler times out*. Use `context.WithoutCancel` (Go 1.21+) to give the audit write its own context that outlives the request context. Use `context.AfterFunc` to trigger the audit write when the request context fires. Verify that the audit log is written even when the handler returns a 504.

<Solution>

```go
package main

import (
	"context"
	"fmt"
	"net/http"
	"net/http/httptest"
	"sync"
	"time"
)

var auditLog []string
var auditMu sync.Mutex

func writeAudit(ctx context.Context, entry string) {
	// This runs in a goroutine started by AfterFunc.
	// The ctx here is a WithoutCancel child — it won't be cancelled
	// when the request ctx fires. Give it its own timeout.
	writeCtx, cancel := context.WithTimeout(ctx, 500*time.Millisecond)
	defer cancel()

	select {
	case <-time.After(20 * time.Millisecond): // simulate async DB write
		auditMu.Lock()
		auditLog = append(auditLog, entry)
		auditMu.Unlock()
		fmt.Println("audit written:", entry)
	case <-writeCtx.Done():
		fmt.Println("audit write timed out:", writeCtx.Err())
	}
}

func checkoutHandler(w http.ResponseWriter, r *http.Request) {
	ctx, cancel := context.WithTimeout(r.Context(), 50*time.Millisecond)
	defer cancel()

	// WithoutCancel: the audit context won't be cancelled when ctx fires.
	auditCtx := context.WithoutCancel(ctx)

	// AfterFunc: when ctx is done (timeout or cancel), write the audit.
	context.AfterFunc(ctx, func() {
		writeAudit(auditCtx, fmt.Sprintf("checkout attempted for %s", r.URL.Query().Get("account")))
	})

	// Simulate slow checkout — will exceed the 50ms deadline.
	select {
	case <-time.After(200 * time.Millisecond):
		fmt.Fprintln(w, "checkout OK")
	case <-ctx.Done():
		http.Error(w, "request timed out", http.StatusGatewayTimeout)
	}
}

func main() {
	req := httptest.NewRequest("GET", "/checkout?account=acc-8821", nil)
	rr := httptest.NewRecorder()
	checkoutHandler(rr, req)
	fmt.Println("handler status:", rr.Code)

	// Give the AfterFunc goroutine time to run.
	time.Sleep(100 * time.Millisecond)

	auditMu.Lock()
	fmt.Println("audit log entries:", len(auditLog))
	auditMu.Unlock()
}
```

`context.WithoutCancel` is the correct tool here — not `context.Background()`. `WithoutCancel` preserves the parent's `Value` chain (request ID, principal, etc.) while severing the cancellation signal. The audit write can log the correct request metadata without being killed when the handler times out.

<Recap>

You now wield context at production depth — the level that separates services that degrade gracefully from ones that slowly choke:

- **Cancellation discipline**: every blocking and I/O function takes `ctx context.Context` as its first argument. Every goroutine you spawn watches `ctx.Done()`. Passing `context.Background()` to a goroutine inside a request severs the cancellation chain.
- **Deadlines and budgets**: set a request-wide ceiling with `WithTimeout`, then carve per-hop budgets with nested child contexts. A child always inherits the sooner of its own deadline and the parent's — a 500ms child on a 100ms parent fires at 100ms.
- **Request-scoped values**: three things belong in context — request ID, authenticated principal, and a pre-decorated logger. Everything else is a function parameter or struct field. Typed unexported key structs prevent collisions; `ctx.Value` walks the chain in O(depth).
- **Propagation layers**: `r.Context()` for inbound HTTP (auto-cancelled on disconnect); `http.NewRequestWithContext` for outbound calls; gRPC serializes `ctx.Deadline()` as `grpc-timeout` automatically; `QueryContext`/`ExecContext`/`BeginTx` for every database operation.
- **Failure modes**: missing `cancel()` accumulates child contexts and deadline timers at steady state; check `ctx.Err()` before starting expensive work at high queue depth; preserve the `context.Canceled`/`context.DeadlineExceeded` signal through error wrapping; use `errgroup.WithContext` to guarantee no goroutine outlives the fan-out call.
- **Cancel-tree internals**: each `cancelCtx` has its own mutex — there is no global cancel-tree lock — and `Done()` is lazily allocated. `context.WithoutCancel` (1.21) and `context.AfterFunc` (1.21) round out the toolkit for production patterns like audit writes that must survive a request timeout. **Go 1.26** adds signal causes to `os/signal.NotifyContext` — `context.Cause(ctx)` reports the signal that triggered shutdown, making graceful-shutdown logging clearer.

</Recap>
