<HeroCard label="Part 2 · Chapter 22" title="The Trouble with Distributed Systems">

Everything you've built across this track — replicas, shards, storage engines — quietly assumed the machines mostly *behave*. They don't. Once your data lives on more than one computer connected by a network, you inherit a whole zoo of failures that simply cannot happen on a single machine: a request that vanishes without a trace, a clock that lies to your face, a process that freezes for thirty seconds in the middle of a function and wakes up thinking no time passed. This is the chapter where we turn the pessimism up to maximum and look the danger dead in the eye.

I'll teach it from absolute zero — no assumed knowledge of networks, clocks, or operating systems. By the end you'll understand why, when Meridian asks a bank "did that payment go through?" and gets silence, *the honest answer is "we cannot know,"* and why that single fact reshapes how you build payment systems. You'll see how two servers can both believe they're the leader and corrupt the ledger, and the beautiful little counter — the **fencing token** — that stops them. The good news at the end: from these unreliable parts, we *can* build reliable systems. But first you have to respect what's actually going wrong. Let's go.

</HeroCard>

## Partial Failure

On a single machine, software is mostly deterministic: it works or it crashes. A hardware fault usually takes the *whole* machine down — a kernel panic, a blue screen — because computers are *deliberately* designed to fail completely rather than return wrong answers. One machine is either fully working or fully dead. Comforting.

The moment you add a network, that comfort is gone.

<Define term="Partial failure" since="Distributed Systems (Part 2)">
A **partial failure** is when *some* parts of a distributed system are broken while others work perfectly — and crucially, it's **nondeterministic**: the same operation across the network may succeed, fail, or hang, unpredictably, from one moment to the next. Why it matters: you can no longer reason "it works or it doesn't." You might issue a request and *never find out whether it succeeded*. That uncertainty — not raw failure — is what makes distributed systems hard, and it's the root of nearly every bug in this chapter.
</Define>

<Callout kind="pro" title="The mindset shift: suspicion, pessimism, paranoia pay off">

The tempting path is to code the *happy path* and treat faults as rare edge cases. In a large enough system, that's fatal — "one in a million" happens every day when you have millions of operations. The professional reframe: assume the network will drop, delay, and reorder your messages; assume nodes will pause and clocks will lie; then design so the system stays *correct* anyway. The payoff is real: a system that tolerates partial failure can do a **rolling upgrade** (reboot nodes one at a time while serving traffic) and survive a dead machine without an outage. You build a *reliable* whole from *unreliable* parts — but only if you respect the parts.

</Callout>

The networks Meridian runs on — the internet, datacenter Ethernet — are **asynchronous packet networks**. One node sends a packet to another; the network promises *nothing* about whether or when it arrives. Send a request expecting a reply, and a depressing number of things can go wrong, all of which look the same to you.

<Callout kind="warn" title="'Reliable' TCP does not save you">

You might think TCP — with its retransmission, ordering, and checksums — makes the network reliable. It doesn't, for your purposes. TCP retransmits lost packets, but if the cable is unplugged it can't plug it back in; after a timeout it gives up and errors. And a TCP acknowledgement only means the remote *kernel* received the bytes — the application may have crashed before handling them. **If you want to know a request succeeded, you need a positive response from the application itself**, not from the transport. TCP solves "big messages over packets," not "did my operation happen."

</Callout>

The only tool you have is a **timeout** — wait a while, then give up. But a timeout is a guess, and choosing its length is a genuine dilemma with no correct answer:

<Define term="Timeout & unbounded delay" since="Distributed Systems (Part 2)">
A **timeout** is a fixed wait after which you *assume* a node is dead. The trouble: asynchronous networks have **unbounded delays** — there's no upper limit on how long a packet may take (cross-region round-trips of *minutes* have been observed during congestion). Why it matters: a **short** timeout detects real failures fast but falsely declares slow-but-alive nodes dead; a **long** timeout avoids false alarms but makes everyone wait. And falsely declaring a node dead is dangerous — its work gets done twice, and shifting its load onto already-busy nodes can trigger a **cascading failure** where the whole cluster topples.
</Define>

Most network delay variability comes from **queueing** — packets waiting at a congested switch, requests waiting for a busy CPU, a VM paused while a neighbor uses the core. Like traffic on a road, queues build fastest exactly when the system is near capacity — which is precisely when you can least afford a false "it's dead." There's no magic constant; production systems *measure* the round-trip distribution and adapt (e.g. the Phi Accrual failure detector in Cassandra).

## Unreliable Clocks

Surely the *clock* is dependable? It is not. Each machine has its own quartz oscillator that **drifts** (runs fast or slow with temperature), nudged back toward reality by **NTP** (the Network Time Protocol) — which is itself only as accurate as the flaky network it syncs over. And there are *two different clocks*, for two different jobs, that beginners constantly confuse:

<Define term="Time-of-day vs monotonic clock" since="Distributed Systems (Part 2)">
A **time-of-day (wall) clock** returns calendar time (e.g. "2026-06-05 14:03:21 UTC"). It's synced by NTP and can **jump backward** (when NTP corrects drift) or skip (leap seconds, DST). A **monotonic clock** only ever moves *forward* at a steady rate; its absolute value is meaningless (nanoseconds since boot) but the *difference* between two readings is a trustworthy elapsed duration. Why it matters: use the **wall clock** for "*when* did this happen" (timestamps, expiry dates) and the **monotonic clock** for "*how long* did this take" (timeouts, response times). Measuring a duration with the wall clock is a classic bug — an NTP correction mid-measurement can make time appear to run backward.
</Define>

This connects straight back to the replication chapter. Remember **last-writer-wins** resolving conflicts by keeping the higher timestamp? Now watch what unreliable clocks do to it — a causally *later* write can carry an *earlier* timestamp, so LWW silently drops the newer value:

<GoPlayground>

```go
package main

import (
	"fmt"
	"time"
)

// Two nodes accept writes to the same balance. Node 3's clock is skewed ~3ms
// BEHIND node 1. Client B's write happens AFTER client A's (it's causally later)
// but lands with an EARLIER timestamp. Last-writer-wins keeps the wrong one.
type write struct {
	value int64
	ts    time.Time
}

func lww(a, b write) write {
	if a.ts.After(b.ts) {
		return a
	}
	return b
}

func main() {
	base := time.Now()
	// Node 1 (accurate clock): client A writes balance = 1, at 42.004s.
	a := write{value: 1, ts: base.Add(42004 * time.Millisecond)}
	// Node 3 (clock 3ms slow): client B increments to 2 LATER in real time,
	// but its clock stamps it 42.003s — earlier than A.
	b := write{value: 2, ts: base.Add(42003 * time.Millisecond)}

	winner := lww(a, b)
	fmt.Printf("LWW keeps value = %d (higher timestamp)\n", winner.value) // 1
	fmt.Println("but B's increment to 2 happened LATER — it was silently lost to clock skew")
}
```

</GoPlayground>

This is why timestamps are a dangerous way to order events across machines, and why systems that need *correct* ordering use **logical clocks** (counters, not quartz) — the subject of the next chapter. A clock reading isn't really a point in time at all; it's a *range*. Google's Spanner faces this honestly with its **TrueTime** API, which returns `[earliest, latest]` instead of a single instant, and waits out the uncertainty before committing — so it never orders two transactions wrong.

<UnderTheHood title="How Go handles the two clocks — and why GC pauses still exist">

Go gets this unusually right. As of Go 1.9, `time.Now()` captures **both** a wall-clock reading *and* a monotonic reading in the same `time.Time`. When you compute `time.Since(start)` or `end.Sub(start)`, Go uses the **monotonic** component — so your duration measurements are immune to NTP jumps automatically. The catch: operations that strip the monotonic reading — `t.Round(0)`, marshaling to JSON, sending over the wire — leave only the wall clock, so a duration computed across a serialization boundary is back to being unsafe. Rule: measure durations from a single in-process `time.Now()` with `time.Since`; never subtract two wall-clock timestamps that came from different machines.

For timeouts across the network, don't hand-roll clock math at all — use `context.Context` with `context.WithTimeout` (Part 1's context chapter), which the whole stdlib respects. And note the next section's villain is partly Go's own: even with the Green Tea GC (default in Go 1.26), stop-the-world pauses are workload-dependent, and the scheduler can park a goroutine — so "very little time passes between these two lines" is never guaranteed.

</UnderTheHood>

## Process Pauses

Here's the failure that breaks the most "obviously correct" code. A running process can be **frozen** — mid-function, between any two lines — for an arbitrary length of time, *without noticing*. While it's frozen, the rest of the world moves on and may declare it dead. Causes are everywhere: a garbage-collection stop-the-world pause, a VM suspended for live migration, the OS swapping a page in from disk, the scheduler context-switching it out, even a stray `SIGSTOP`.

Why is that catastrophic? Consider a leader that holds a **lease** (a lock with a timeout) so only it may write Meridian's settlement file:

The deep lesson: the single-machine tools you know — mutexes, atomic counters — assume threads share memory and a common clock. **None of that holds across machines.** A distributed node must assume it can be paused at any instant and that the world will have moved on when it wakes. So you can't prevent zombies; you have to make sure they can't do damage. Which brings us to the fix.

## Fencing Tokens

A node that's been paused or partitioned but still thinks it holds the lease is a **zombie**. You can't always shut a zombie down in time (its delayed write might already be in flight). Instead you **fence** it: make the storage itself reject anything from a stale leaseholder.

<Define term="Fencing token" since="Distributed Systems (Part 2)">
A **fencing token** is a number the lock/lease service returns with every grant, and it **increases every time** a lease is handed out. Every write to the protected resource must include the writer's token, and the storage service **remembers the highest token it has seen and rejects any write with a lower one**. Why it matters: when a zombie wakes up and writes with its old token, the storage has already seen a *higher* token from the new leaseholder — so the zombie's write is refused, automatically, with no need to detect the zombie or trust any clock. (Same idea as Raft's *term number*, Paxos's *ballot*, Kafka's *epoch*.)
</Define>

Watch it reject a zombie:

<GoPlayground>

```go
package main

import "fmt"

// The storage service fences stale writers: it tracks the highest fencing token
// it has accepted and refuses any write carrying a lower token. No clocks, no
// zombie detection — just a monotonically increasing number.
type Storage struct {
	highestToken int
	value        string
}

func (s *Storage) write(token int, value string) bool {
	if token < s.highestToken {
		fmt.Printf("  REJECT token %d (already saw %d) — zombie fenced off\n", token, s.highestToken)
		return false
	}
	s.highestToken = token
	s.value = value
	fmt.Printf("  accept token %d -> %q\n", token, value)
	return true
}

func main() {
	store := &Storage{}

	store.write(33, "server1: settle batch") // leader 1, token 33
	// server 1 freezes; its lease expires; server 2 takes over with token 34.
	store.write(34, "server2: settle batch") // leader 2, token 34
	// server 1 wakes as a zombie and tries to write with its STALE token 33:
	store.write(33, "server1-zombie: corrupt!")

	fmt.Printf("final value: %q (zombie could not corrupt it)\n", store.value)
}
```

</GoPlayground>

The elegance: the storage service needs no idea *who* is a zombie and no working clock. It just enforces "tokens only go up." A leaseholder writes immediately on acquiring the lease, and from that moment every older holder is permanently fenced. (If your storage supports an atomic compare-and-set or "conditional write" — S3, Azure Blob, GCS all do — you can get the same guarantee directly.)

## Truth & Quorums

Step back to the disorienting core: a node can know *nothing* for certain about other nodes — only guess from messages it does or doesn't receive. And it can't even fully trust *itself* (it might be a paused zombie). So distributed systems stop relying on any single node's judgment and instead take a **vote**.

<Define term="Majority quorum" since="Distributed Systems (Part 2)">
A **majority quorum** is a decision that requires agreement from **more than half** the nodes. Why it matters: there can only ever be *one* majority at a time, so two conflicting decisions can't both win — that's what makes it *safe*. And it removes dependence on any single node: a majority can declare a node dead and that node **must step down**, even if it feels perfectly alive (it might be a zombie). With 3 nodes you tolerate 1 failure; with 5, you tolerate 2. This voting is the seed of consensus — the entire next chapter.
</Define>

<GoPlayground>

```go
package main

import "fmt"

// No single node decides truth. A node is declared dead only if a MAJORITY of
// nodes vote that it's unreachable. One node's opinion (even its own) is not enough.
func declaredDead(votesDead, totalNodes int) bool {
	return votesDead > totalNodes/2 // strictly more than half
}

func main() {
	const nodes = 5
	fmt.Println("2 of 5 say node-3 is unreachable ->", declaredDead(2, nodes)) // false (not a majority)
	fmt.Println("3 of 5 say node-3 is unreachable ->", declaredDead(3, nodes)) // true  (majority rules)
	// Even if node-3 feels alive, once a majority votes it dead, it MUST step down.
	// Only one majority can exist, so two halves can't both 'win' and split-brain.
}
```

</GoPlayground>

<Callout kind="note" title="Byzantine faults: out of scope (on purpose), and system models">

Everything here assumes nodes are **unreliable but honest** — they may be slow, paused, or stale, but if they answer, they're telling the truth as they know it. A node that *lies* — sends arbitrary or malicious messages, casts contradictory votes — is a **Byzantine fault**, and tolerating it (the *Byzantine Generals Problem*) is far more expensive. You need it for aerospace (radiation flips bits) and cryptocurrencies (mutually untrusting parties), but **not** inside Meridian's datacenter: your nodes run your software behind your firewall, so you trust them and defend the *edges* with the usual tools (input validation, auth, TLS). Formally, we model real systems as **partially synchronous** (well-behaved most of the time, occasionally not) with **crash-recovery** faults (nodes crash and may return, keeping disk but losing memory) — and we demand **safety** properties (nothing bad ever happens, like "no two writers corrupt the file") hold *always*, while **liveness** properties (something good eventually happens, like "the request eventually gets a response") may wait for the network to recover.

</Callout>

<Exercise n={1} title="What does a timeout tell you?" level="easy">

Write `knownOutcome(gotResponse bool) string` returning what you actually know about whether a remote operation succeeded. For `gotResponse == false`, list the indistinguishable cases. Why does this push you toward idempotent operations?

<Solution>

```go
func knownOutcome(gotResponse bool) string {
	if gotResponse {
		return "succeeded (positive application-level response received)"
	}
	return "UNKNOWN: (a) request lost, (b) node down, (c) processed but reply lost"
}
```

A positive application response is the *only* thing that confirms success. A timeout collapses three very different realities — never sent, never processed, or fully processed with a lost reply — into one indistinguishable signal. Because you can't tell "did nothing" from "did everything," the only safe design is to make the operation **idempotent**: safe to retry, because if it already happened, doing it "again" is a no-op. That's why payment APIs use idempotency keys.

</Solution>

</Exercise>

<Exercise n={2} title="Measure a duration safely" level="easy">

Write `elapsed(start time.Time) time.Duration` that returns how long has passed since `start`, and explain why you must use `time.Since` (monotonic) rather than subtracting two `time.Now()` wall-clock readings taken from different machines.

<Solution>

```go
func elapsed(start time.Time) time.Duration {
	return time.Since(start) // uses Go's monotonic reading — immune to NTP jumps
}
```

`time.Since(start)` uses the monotonic clock embedded in the `time.Time` (Go 1.9+), which only moves forward at a steady rate, so the duration is always sane. Subtracting wall-clock readings is unsafe two ways: an NTP correction can move the wall clock *backward* mid-measurement (negative duration), and readings from *different machines* aren't comparable at all because their clocks drift independently. Durations are a monotonic-clock job; calendar timestamps are a wall-clock job.

</Solution>

</Exercise>

<Exercise n={3} title="Clock skew loses a write" level="medium">

Model two writes where the causally-later one has the earlier timestamp (clock skew). Write `lww(a, b Write) Write` (keep the higher timestamp) and show it discards the newer value. Then state the fix.

<Solution>

```go
type Write struct {
	Value int64
	TS    int64 // millisecond timestamp from the writer's (skewed) clock
}

func lww(a, b Write) Write {
	if a.TS >= b.TS {
		return a
	}
	return b
}
// a = {Value:1, TS:42004}  (earlier, but higher timestamp)
// b = {Value:2, TS:42003}  (LATER in real time, lower timestamp)
// lww(a,b) returns a -> value 1; b's newer write is silently lost.
```

LWW trusts timestamps to mean "recency," but a slow clock makes a later write look older, so LWW drops it with no error. The fixes: don't order cross-node events by physical clocks — use **logical clocks / version vectors** (next chapter) that track causality directly; or for money, avoid the conflict entirely with a single leader and append-only model (the replication chapter's lesson).

</Solution>

</Exercise>

<Exercise n={4} title="Fence off a zombie" level="medium">

Implement `write(token int, value string) bool` on a storage type that accepts a write only if `token` is not below the highest token seen, updating state on accept. Show a zombie with an old token gets rejected after a newer leaseholder has written.

<Solution>

```go
func (s *Storage) write(token int, value string) bool {
	if token < s.highestToken {
		return false // stale token — fence off the zombie
	}
	s.highestToken = token
	s.value = value
	return true
}
// write(33,...) -> true   (leader 1)
// write(34,...) -> true   (leader 2 takes over; highest is now 34)
// write(33,...) -> false  (zombie leader 1; 33 < 34, rejected)
```

Because tokens strictly increase with each lease grant, "highest seen" is a perfect filter: any actor still using an old token has, by definition, been superseded. The storage service enforces correctness with one integer comparison — no clock, no zombie detection, no trust required. Once the new leaseholder writes (bumping the token), every older holder is fenced for good.

</Solution>

</Exercise>

<Exercise n={5} title="Majority and the safety/liveness split" level="hard">

Write `majority(votes, total int) bool` (strictly more than half). Then classify each as safety or liveness: (a) "no two leaders are ever elected simultaneously," (b) "a request eventually receives a response," (c) "two writes never get the same fencing token." Explain the distinction.

<Solution>

```go
func majority(votes, total int) bool { return votes > total/2 }

// (a) no two simultaneous leaders  -> SAFETY  (a violation is a specific bad moment)
// (b) a request eventually responds -> LIVENESS (note the word "eventually")
// (c) fencing tokens are unique     -> SAFETY  (uniqueness can be pinpointed if broken)
```

A **safety** property says *nothing bad ever happens*; if it's violated you can point to the exact instant (two leaders at time T, a duplicate token returned), and the damage can't be undone — so we require safety to hold in *all* situations, even total network failure. A **liveness** property says *something good eventually happens* (note "eventually"); it can be temporarily unmet and still be satisfied later, so we're allowed to condition it on the network recovering and a majority surviving. Majority quorum is what makes the safety properties achievable: only one majority can exist, so conflicting decisions can't both be "true."

</Solution>

</Exercise>

<Recap>

You now know what actually goes wrong once data lives on more than one machine — and how to stay correct anyway:

- **Partial failure** is the core difference: parts break while others work, **nondeterministically**, so you may never learn whether an operation succeeded. Code the unhappy path; suspicion pays off.
- **Networks are unreliable.** A non-response is **indistinguishable** across "request lost," "node down," and "processed but reply lost." TCP doesn't fix this — only an *application-level* response confirms success. Timeouts are guesses against **unbounded delays**; too-eager ones cause cascading failures.
- **Clocks are unreliable.** Use the **monotonic** clock for durations (timeouts, latencies) and the **wall** clock for calendar timestamps — never mix them. NTP drift and jumps make timestamps a dangerous way to order cross-node events (LWW can silently drop the newer write).
- **Processes pause.** GC, VM suspend, paging, or the scheduler can freeze a node mid-function for seconds; it wakes assuming no time passed. So a node can't trust that "no time passed" between a check and an action — which turns a lease holder into a **zombie** and causes **split-brain**.
- **Fencing tokens** stop zombies: an ever-increasing number per lease grant, and storage rejects any write with a lower token. One integer comparison, no clock, no trust — the same idea as Raft terms and Kafka epochs.
- **Trust a majority, not a node.** A node can't trust its own judgment; decisions need a **majority quorum** (only one majority can exist → no split-brain). We assume **honest-but-faulty** nodes (not **Byzantine**), model systems as **partially synchronous / crash-recovery**, and require **safety** always while allowing **liveness** to wait for recovery.

</Recap>
