Last chapter's cinema service got three new features: a limit of four held seats per customer, a dashboard counting holds per film, and a live seat map pushed to viewers' browsers. All three shipped with a bug. This chapter finds each one with the tool that fits it, on the real service, and shows you exactly what each tool printed.

- A **test fails** and you can't see why: step into the code with **Delve**.
- A **request dies** with an empty reply: read the **panic** the server logged, and check what it left half-done.

## Delve, the Go Debugger

*Stop 1 of 3.*

### Step 1: the failing test

The cinema store now refuses a fifth hold per customer. The code, in `booking/memory.go`:

```go noverify
// memory.go, lines 59–85
func (s *MemoryStore) Hold(_ context.Context, movie, seat, user string, ttl time.Duration) error {
	if !validSeat(movie, seat) {
		return ErrNoSeat
	}
	key := movie + "/" + seat
	s.lock()
	defer s.unlock()
	if _, taken := s.current(key); taken { // check…
		return ErrTaken
	}
	if s.holdsBy(user) > MaxHolds {
		return ErrTooManyHolds
	}
	s.seats[key] = entry{status: Held, user: user, expires: s.now().Add(ttl)} // …then act
	return nil
}

// holdsBy counts the seats user currently holds. The caller holds the lock.
func (s *MemoryStore) holdsBy(user string) int {
	n := 0
	for key := range s.seats {
		if e, ok := s.current(key); ok && e.status == Held && e.user == user {
			n++
		}
	}
	return n
}
```

And the test that says it doesn't work: one customer tries to hold B1 to B8.

```go noverify
package booking

	"context"
	"fmt"
	"testing"
	"time"

			held++
		}
```


Five instead of four. You could stare at the code, or add `fmt.Println`s, rebuild and rerun. Or you can stop the program at the moment it goes wrong and look.

Read it top to bottom:

- **`break booking/memory.go:69`** sets breakpoint 1 on the limit check, and **`condition 1 seat == "B5"`** makes it stop only for that seat. The first four calls run straight through.
- **`print seat`**, **`print user`** read local variables: `"B5"`, `"greedy"`.
- **`call s.holdsBy(user)`** runs a function inside the stopped program and prints its result: 4. (`print` refuses function calls, because running code can change the program's state; `call` is the explicit way.)
- **`print MaxHolds`** is 4. So `4 > 4` is false, and **`next`** (run one line, stepping over calls) lands on line 72, the write. That's the bug.
- **`stack`** shows how we got here: `Hold` called from `TestHoldLimit` at `limit_test.go:14`.

The fix is one character, `>=`, and `go test ./booking/` passes. `--init` ran the commands from a file so this transcript is exactly reproducible; normally you type them at the `(dlv)` prompt. The other everyday commands: `continue` (run to the next breakpoint), `step` (go into the called function), `stepout` (finish the current function), `locals`, `args`, and `frame N` to inspect a caller's variables.

### Step 4: attaching and debugging remotely

`dlv attach <pid>` stops a running process and debugs it in place: everything in it pauses, so use it on a copy you can afford to freeze, never a production instance serving traffic. For a process in a container or on another machine, run Delve **headless** next to it and connect from your laptop:

```text
# next to the program: serve Delve's API on a local port
$ dlv exec ./cinema --headless --listen=127.0.0.1:2345 --api-version=2 --accept-multiclient
# on your laptop, through an SSH tunnel (ssh -L 2345:127.0.0.1:2345 host)
$ dlv connect 127.0.0.1:2345
```

<Callout kind="warn" title="Never expose Delve's port">

Anyone who can reach a headless Delve can read and write the process's memory and call any function in it. Bind it to `127.0.0.1` and reach it through an SSH tunnel or `kubectl port-forward`; never listen on `0.0.0.0`.

</Callout>

<UnderTheHood title="How a breakpoint works">

The Go linker writes **DWARF** debugging information into the binary (DWARF version 5 since Go 1.25): tables that map each source line to machine-code addresses, and describe every variable's type and location. For `break memory.go:69`, Delve looks up the address of line 69 and overwrites the first instruction there with a trap: `INT3` (one byte, `0xCC`) on amd64, `BRK` on arm64. When the CPU reaches it, the kernel stops the thread and tells Delve (via `ptrace` on Linux; on macOS Delve goes through Apple's `debugserver`). Delve puts the original instruction back, and you're at the prompt.

A condition doesn't change that mechanism: the trap fires on every pass, Delve evaluates `seat == "B5"`, and resumes silently if it's false. That's why a conditional breakpoint in a hot loop slows the program noticeably. `goroutines` works by reading the runtime's own list of goroutines (`runtime.allgs`) out of the process's memory and translating each one's saved program counter back to a source line through DWARF. Optimizations would move and eliminate variables, which is why `dlv debug` and `dlv test` build with `-gcflags='all=-N -l'`.

</UnderTheHood>

### Step 1: a panic in a handler

The dashboard counts holds per film in a map on the server:

Read a panic in this order:

1. **The message.** `assignment to entry in nil map`: take it literally. Something wrote to a map that was never made.
2. **The first frame that's your code.** Skip the runtime and `net/http` frames at the top: `main.newMux.func2` at **`main.go:86`**. `func2` means "the second function literal inside `newMux`", the hold closure; line 86 is `a.holdsByMovie[movie]++`.
3. **Who called it.** `seatAction.func1` at `main.go:62`, the wrapper, called by the `ServeMux`, called by `net/http.(*conn).serve`: an ordinary request.
4. **The first line of the log.** `http: panic serving 127.0.0.1:52760` means `net/http` recovered the panic (the deferred `recover` from the quiz above, at `server.go:1939`), closed that one connection (hence curl's empty reply) and kept serving everyone else.

The hex values in the frames are arguments and offsets; you rarely need them.

<Callout kind="note" title="Why the goroutineleak profile said 0">

Go 1.27's `goroutineleak` profile (Part 2 chapter 7) reported **`total 0`** for this server. It finds goroutines blocked forever on a channel or lock nothing can reach any more. These goroutines aren't blocked: they sleep, wake, and loop, so to the runtime they look busy and healthy. A leak that keeps *doing* things needs the plain goroutine profile and your judgement: "50 goroutines on a stream nobody is watching" is only a leak because you know nobody is watching.

</Callout>

The fix: a ticker instead of `Sleep`, a `select` that also watches `r.Context().Done()` (net/http cancels it when the client disconnects), and stopping on the first write error:

```go noverify
// main.go, lines 94–115
	// Live seat map: server-sent events, one snapshot a second.
	mux.HandleFunc("GET /movies/{movie}/events", func(w http.ResponseWriter, r *http.Request) {
		w.Header().Set("Content-Type", "text/event-stream")
		tick := time.NewTicker(time.Second)
		defer tick.Stop()
		for {
			seats, err := a.store.Seats(r.Context(), r.PathValue("movie"))
			if err != nil {
				return
			}
			b, _ := json.Marshal(seats)
			if _, err := fmt.Fprintf(w, "data: %s\n\n", b); err != nil {
				return // the viewer has gone
			}
			w.(http.Flusher).Flush()
			select {
			case <-tick.C:
			case <-r.Context().Done(): // closed tab, lost connection, server shutdown
				return
			}
		}
	})
```

Same test after the fix: `goroutine profile: total 4`.

### Step 4: the other signals

- **All goroutines asleep.** When every goroutine is blocked, the runtime stops the program with `fatal error: all goroutines are asleep - deadlock!` and dumps them all (chapter 7 reproduced it). With an HTTP server running, that check never fires, so the goroutine profile is how you find a deadlock too.
- **A dump on demand.** `kill -QUIT <pid>` makes a Go program print every goroutine's stack to stderr and exit. On a fatal panic, the default `GOTRACEBACK=single` prints only the goroutine that panicked; `GOTRACEBACK=all` prints every goroutine; `crash` also writes a core dump (stop 3).

### Step 1: a private debug listener

```go noverify

	// /debug/pprof/ (net/http/pprof) and /debug/vars (expvar), both
```

Importing `net/http/pprof` for its side effect registers `/debug/pprof/…` on `http.DefaultServeMux`; importing `expvar` registers `/debug/vars`. Serving `DefaultServeMux` on a **separate listener bound to 127.0.0.1** keeps those endpoints off the public port: the customer-facing server uses its own mux, so none of them leak there. ### Step 2: expvar, counters you can read live

The dashboard counter, fixed: an `expvar.Map` instead of a plain map. It's created at package level (so it's never nil), it's safe to update from many goroutines at once (the plain map was also a data race), and it's published automatically:

<Exercise n={5} title="Read a gctrace line" level="hard">

From `gc 533 @3.143s 3%: … 3->3->1 MB, 4 MB goal …`, how much memory was live after the collection, and why is the collector running about 170 times a second?

<Solution>

1 MB was live after collection 533 (the third number). The goal is computed from the live heap and `GOGC` (100 by default: collect when the heap reaches about twice what was live, with a 4 MB minimum), so it's 4 MB. Every request allocates a few kilobytes of JSON that's garbage a moment later, and at tens of thousands of requests a second that fills 3 MB of new allocation in a few milliseconds: 533 cycles in 3.14 s. It costs 3% of CPU, so it's fine. Raising `GOGC` (or setting a `GOMEMLIMIT` and `GOGC=off`) would trade memory for fewer cycles if it mattered.

Note what `main` does not do: it never calls `srv.Close()`. `httptest.Server.Close` waits for every handler to return, and with the starter's leaked stream handlers it would wait forever, which is exactly what a leaking handler does to a graceful shutdown in production.

</Lab>
