## The Go Proverbs & Mindset

*Stop 1 of 5.*

In 2015 Rob Pike gave a talk listing the **Go proverbs**: short sayings that capture how the language is meant to be used. The compiler enforces none of them. They're heuristics for noticing when code is fighting the language. Five matter most day to day.

### Step 1: "Clear is better than clever."

<BeforeAfter
  badLabel="clever"
  goodLabel="clear"
  bad={`// pack two results into one int
func firstLast(s []int) int {
	return s[0]<<32 | s[len(s)-1]
}`}
  good={`// two results, two return values
func firstLast(s []int) (first, last int) {
	return s[0], s[len(s)-1]
}`}
/>

The clever version packs two numbers into one with bit shifts. It's unreadable, and it's wrong: a negative `last` sign-extends and overwrites `first`'s bits, and on a platform with 32-bit `int` the shift discards `first` entirely. Go has multiple return values; use them. Code is read far more often than it's written, usually by someone tired.

### Step 2: "A little copying is better than a little dependency."

Every dependency brings its own dependencies, upgrades, licences and security advisories. For a ten-line helper, copying the ten lines is often cheaper than importing a module. Go's standard library (`strings`, `slices`, `maps`, `strconv`, `bytes`, `io`, `sync`, `context`, `net/http`, `encoding/json`…) covers far more than most people check before reaching for a package.

### Step 3: "The bigger the interface, the weaker the abstraction."

An interface is only as useful as the number of types that can satisfy it. `io.Reader` has one method:

```go
type Reader interface {
	Read(p []byte) (n int, err error)
}
```

so files, network connections, HTTP bodies, byte buffers, strings, compressors and test fixtures all satisfy it, and a function that accepts an `io.Reader` works with every one of them. An interface with eleven methods is satisfied by one type and its mock; it has renamed a concrete type rather than abstracted it. Stop 3 is about this.

### Step 4: "Make the zero value useful."

```go
var buf bytes.Buffer  // an empty buffer, ready to write
var mu sync.Mutex     // unlocked, ready to Lock
var wg sync.WaitGroup // count 0; Wait returns immediately
```

No constructor to forget, no `Init()` to call first. When you design a type, ask what its sensible empty state is, and whether the zero value can be that.

### Step 5: "Errors are values."

Errors are ordinary values you return, inspect, wrap and combine; not exceptions that jump up the stack. Using `panic` and `recover` as a way to return failures fights the language:

<BeforeAfter
  badLabel="panic as control flow"
  goodLabel="the error is a value"
  bad={`func parse(s string) int {
	defer func() { recover() }()
	return mustParse(s) // panics on bad input
}                       // and silently returns 0`}
  good={`func parse(s string) (int, error) {
	v, err := strconv.Atoi(s)
	if err != nil {
		return 0, fmt.Errorf("parse %q: %w", s, err)
	}
	return v, nil
}`}
/>

The next chapter is entirely about errors at scale.

**Recap.** Clear over clever; a little copying over a little dependency; small interfaces; useful zero values; errors as values. Heuristics, not rules, for noticing when code fights the language.

## Naming & API Design

*Stop 2 of 5.*

### Step 1: the size of a name follows the size of its scope

A variable used for three lines can be `i`, `n` or `tx`: the surrounding code explains it. A name visible across a package, or exported, has to carry its meaning alone.

```go
for i, tx := range transactions { // short: the loop is the context
	total += tx.AmountCents
}

type Transaction struct { // exported: says exactly what it is
	ID          string
	AmountCents int64
	AccountID   string
	CreatedAt   time.Time
}
```

Package names are part of every call, so don't repeat them: `http.Handler`, not `http.HTTPHandler`; `json.Decoder`, not `json.JSONDecoder`. Avoid meaningless names (`util`, `common`, `Manager`, `Mgr`, `Helper`): a name should say what something does or is.

### Step 2: export as little as you can

Every exported name is a promise to your callers. Unexported names you can change freely.

<BeforeAfter
  badLabel="everything exported"
  goodLabel="a deliberate surface"
  bad={`type Ledger struct {
	DB     *sql.DB          // callers can run anything on it
	Cache  map[string]int64 // callers can write it unlocked
	Logger *log.Logger
	mu     sync.Mutex
}`}
  good={`type Ledger struct {
	db    *sql.DB
	cache map[string]int64
	log   *slog.Logger
	mu    sync.Mutex
}

func NewLedger(db *sql.DB, log *slog.Logger) *Ledger { … }`}
/>

With the fields unexported, callers can only use the ledger through its methods, which is where the locking and validation live.

### Step 3: accept interfaces, return structs

**Accept interfaces** so a function works with whatever the caller has. **Return concrete types** so the caller gets every field and method without type assertions.

```go
// Works with a file, an HTTP body, a bytes.Buffer, a strings.Reader…
// Returns the concrete *Transaction, so callers see every field.
func ParseTransaction(r io.Reader) (*Transaction, error) {
	var tx Transaction
	if err := json.NewDecoder(r).Decode(&tx); err != nil {
		return nil, fmt.Errorf("parse transaction: %w", err)
	}
	return &tx, nil
}
```

<GoPlayground>

The exceptions are when the interface *is* the whole point: returning `error`, or an `http.Handler`, or when you must hide which of several implementations you chose.

## Small Interfaces & When Not to Abstract

```go

	PostEntry(ctx context.Context, e Entry) error
```

### Step 2: one method is the ideal

<ConceptGrid cols={3}>
  <ConceptCard label="io.Reader">`Read`. Anything that produces bytes.</ConceptCard>
  <ConceptCard label="io.Writer">`Write`. Anything that consumes bytes.</ConceptCard>
  <ConceptCard label="fmt.Stringer">`String() string`. Anything that can describe itself.</ConceptCard>
  <ConceptCard label="error">`Error() string`. Anything that can be an error.</ConceptCard>
  <ConceptCard label="http.Handler">`ServeHTTP`. Anything that can answer a request.</ConceptCard>

### Step 3: don't abstract early

Before declaring an interface, ask:

1. **Is there a second implementation now?** A real one, or a test fake you actually need. If not, write the concrete type; extract the interface when the second one appears. You'll know which methods matter by then.
2. **Does it make tests simpler?** A good interface shrinks what a test must fake.
3. **Does it hide something callers need?** If callers type-assert back to the concrete type often, it hides too much.

<UnderTheHood title="What an interface call costs">

A non-empty interface value is two words: a pointer to an **itab** (the concrete type plus a table of its method addresses for this interface) and a data word. Calling a method loads the address from the itab and makes an indirect call. Measured on the machine used for this book, with inlining disabled on both sides: a direct call took 2.17 ns and the same method through an interface 2.80 ns. The bigger costs are indirect: an interface call usually can't be inlined (unless the compiler can prove the concrete type, or profile-guided optimisation devirtualises a hot call site), and putting a value in an interface may allocate.

On that last point, measured with `testing.AllocsPerRun` when the interface value escapes to the heap:

| Stored in an `any` | Allocations |
|---|---|
| a pointer (`*Pair`) | 0: pointers fit in the data word |
| an `int` between 0 and 255 | 0: the runtime keeps a table of them |
| an `int` like 1000 | 1 |
| a two-field struct | 1 |

Values that don't escape are often kept on the stack, and then cost nothing either. None of this is a reason to avoid interfaces; it's a reason not to box values in hot loops without measuring.

</UnderTheHood>

**Recap.** Declare interfaces in the package that uses them, with only the methods it calls. Prefer one method. Extract an interface when a second implementation exists, not before.

## Implementing Stdlib Interfaces

*Stop 4 of 5.*

Meridian's types start plain:

```go
type Money struct {
	Cents    int64
	Currency string
}

type Account struct {
	ID      string
	Name    string
	Balance Money
}
```

`fmt.Println` of an account prints `{acc_001 Operating Account {125000 USD}}`. Let's make them fit into the standard library.

### Step 1: `fmt.Stringer`, and the lost minus sign

Any type with `String() string` satisfies `fmt.Stringer`, and every `fmt` print function (and `%v`/`%s`) calls it. Here's a version from an earlier draft of this chapter. It looks careful: it even takes the absolute value of the cents.

<GoPlayground>

```go
package main

import "fmt"

type Money struct {
	Cents    int64
	Currency string
}

func (m Money) StringDraft() string {
	major := m.Cents / 100
	minor := m.Cents % 100
	if minor < 0 {
		minor = -minor
	}
	return fmt.Sprintf("%s %d.%02d", m.Currency, major, minor)
}

func (m Money) String() string {
	c, sign := m.Cents, ""
	if c < 0 {
		c, sign = -c, "-"
	}
	return fmt.Sprintf("%s %s%d.%02d", m.Currency, sign, c/100, c%100)
}

func main() {
	for _, c := range []int64{4999, -4299, -50} {
		m := Money{Cents: c, Currency: "USD"}
		fmt.Printf("%6d cents  draft: %-11s fixed: %v\n", c, m.StringDraft(), m)
	}
}
```

</GoPlayground>

```text
  4999 cents  draft: USD 49.99   fixed: USD 49.99
 -4299 cents  draft: USD -42.99  fixed: USD -42.99
   -50 cents  draft: USD 0.50    fixed: USD -0.50
```

A 50-cent refund printed as a 50-cent charge. The draft relied on the minus sign surviving in the whole-units part, which it doesn't when that part is zero. Take the sign once, then work with the absolute value. (`fmt.Println(m)` and `%v` call `String` automatically; that's the point of the interface.)

### Step 2: `error`, with fields

```go
type TransferError struct {
	From, To string
	Amount   Money
	Reason   string
}

func (e *TransferError) Error() string {
	return fmt.Sprintf("transfer %s→%s %s: %s", e.From, e.To, e.Amount, e.Reason)
}
```

A caller can pull it out with `errors.As`, or `errors.AsType[*TransferError](err)` since Go 1.26, and decide what to do from the fields instead of matching message text. The next chapter goes deep.

### Step 3: sorting

`sort.Interface` has three methods (`Len`, `Less`, `Swap`). Since Go 1.21, the `slices` package usually does the job with one comparison function:

```go
slices.SortFunc(accounts, func(a, b Account) int {
	return cmp.Compare(b.Balance.Cents, a.Balance.Cents) // b before a: descending
})
```

It returns negative, zero or positive, like `cmp.Compare`. For a stable sort (equal elements keep their order) use `slices.SortStableFunc`. Implementing `sort.Interface` on a named slice type is still useful for a sort order you want to name and reuse:

```go
type ByBalanceDesc []Account

func (s ByBalanceDesc) Len() int           { return len(s) }
func (s ByBalanceDesc) Swap(i, j int)      { s[i], s[j] = s[j], s[i] }
func (s ByBalanceDesc) Less(i, j int) bool { return s[i].Balance.Cents > s[j].Balance.Cents }

sort.Sort(ByBalanceDesc(accounts))
```

`Less` with `>` gives descending order. Get it backwards and the sort still runs, just the wrong way, so test the order.

### Step 4: `io.Reader` and `io.Writer`, and a broken contract

`io.Copy(dst, src)` moves bytes from any reader to any writer in chunks, holding one buffer (32 KB) rather than the whole content, which is how a 2 GB statement file can stream through a 32 KB buffer. That only works if both sides keep their **contracts**, and the contract for `Write` is precise: it returns how many bytes *of `p`* it wrote, between 0 and `len(p)`.

An earlier draft of this chapter had an audit logger that added a timestamp and returned the length of what *it* wrote:

```go
func (a *AuditLog) Write(p []byte) (int, error) {
	line := fmt.Appendf(nil, "[%s] %s", a.now().Format(time.RFC3339), p)
	return a.w.Write(line) // returns len(line), which is more than len(p)
}
```

Run through `io.Copy`, it failed:

```text
[2026-09-26T15:23:30+01:00] acc_001,Checking,USD 500.00
copy error: invalid write result
```

and when the source was a `strings.Reader` (which copies via its own `WriteTo` method), it panicked with `strings.Reader.WriteTo: invalid WriteString count`.

The fix is one line: after writing, return `len(p), nil` (or an error if the inner write failed). The full, working pipeline:

<GoPlayground>

```go
package main

import (
	"fmt"
	"io"
	"os"
	"time"
)

type Account struct {
	ID, Name string
	Cents    int64
}

// TransactionReport is an io.Reader that produces one CSV line per account.
type TransactionReport struct {
	accounts []Account
	idx      int
	buf      []byte // the part of the current line not yet handed out
}

func (r *TransactionReport) Read(p []byte) (int, error) {
	for len(r.buf) == 0 {
		if r.idx >= len(r.accounts) {
			return 0, io.EOF
		}
		a := r.accounts[r.idx]
		r.idx++
		r.buf = fmt.Appendf(nil, "%s,%s,%d\n", a.ID, a.Name, a.Cents)
	}
	n := copy(p, r.buf) // p may be smaller than a line: keep the rest for next time
	r.buf = r.buf[n:]
	return n, nil
}

// AuditLog is an io.Writer that timestamps each chunk it's given.
type AuditLog struct {
	w   io.Writer
	now func() time.Time
}

func (a *AuditLog) Write(p []byte) (int, error) {
	line := fmt.Appendf(nil, "[%s] %s", a.now().Format(time.RFC3339), p)
	if _, err := a.w.Write(line); err != nil {
		return 0, err
	}
	return len(p), nil // the contract: how many bytes OF p were consumed
}

func main() {
	report := &TransactionReport{accounts: []Account{
		{"acc_001", "Checking", 50000},
		{"acc_002", "Savings", 250000},
	}}
	fixed := func() time.Time { return time.Date(2026, 9, 26, 9, 0, 0, 0, time.UTC) }
	n, err := io.Copy(&AuditLog{w: os.Stdout, now: fixed}, report)
	fmt.Println("copied", n, "bytes, err =", err)
}
```

</GoPlayground>

```text
[2026-09-26T09:00:00Z] acc_001,Checking,50000
[2026-09-26T09:00:00Z] acc_002,Savings,250000
copied 46 bytes, err = <nil>
```

One timestamp per line, but only because this `Read` hands out one line per call. `io.Copy` passes along whatever chunk `Read` returned; a different source (a file, a `strings.Reader`) can deliver two lines, or half of one, in a single `Write`. A writer sees chunks, not lines: if you need one timestamp per line, split on newlines inside `Write`. And `copied 46 bytes` counts the report's bytes, not the timestamps, because that's what `Write` now reports. The injectable `now` is what made the output reproducible.

### Step 5: JSON, and a parser that invented cents

Meridian's API sends money as `{"amount":"49.99","currency":"USD"}`. `json.Marshaler` and `json.Unmarshaler` let `Money` control its own encoding. The earlier draft parsed the amount with `fmt.Sscanf(raw.Amount, "%d.%02d", &major, &minor)`. Fed a few realistic inputs:

```text
49.99  -> cents=4999  err=<nil>
49.5   -> cents=4905  err=<nil>      $49.50 became $49.05
49     -> cents=0     err=bad amount "49": unexpected EOF
-0.50  -> cents=50    err=<nil>      a refund became a charge
1.234  -> cents=123   err=<nil>      the extra digit silently dropped
```

`%02d` in a *scan* doesn't mean "two digits, padded"; it means "at most two characters", so "5" is read as 5 cents. And `-0` is just 0, so the sign vanishes. A parser for money should demand exactly the format it expects and reject everything else:

<GoPlayground>

```go
package main

import (
	"encoding/json"
	"errors"
	"fmt"
	"strconv"
	"strings"
)

type Money struct {
	Cents    int64
	Currency string
}

func (m Money) String() string {
	c, sign := m.Cents, ""
	if c < 0 {
		c, sign = -c, "-"
	}
	return fmt.Sprintf("%s %s%d.%02d", m.Currency, sign, c/100, c%100)
}

// parseCents accepts "49.99" or "-0.50": digits, a dot, exactly two decimals.
func parseCents(s string) (int64, error) {
	neg := strings.HasPrefix(s, "-")
	whole, frac, ok := strings.Cut(strings.TrimPrefix(s, "-"), ".")
	if !ok || len(frac) != 2 || whole == "" {
		return 0, fmt.Errorf("amount %q: want digits, a dot, and exactly two decimals", s)
	}
	w, err1 := strconv.ParseUint(whole, 10, 63)
	f, err2 := strconv.ParseUint(frac, 10, 8)
	if err := errors.Join(err1, err2); err != nil {
		return 0, fmt.Errorf("amount %q: %w", s, err)
	}
	c := int64(w)*100 + int64(f)
	if neg {
		c = -c
	}
	return c, nil
}

// MarshalJSON has a value receiver, so it works for Money values and pointers alike.
func (m Money) MarshalJSON() ([]byte, error) {
	return json.Marshal(struct {
		Amount   string `json:"amount"`
		Currency string `json:"currency"`
	}{strings.TrimPrefix(m.String(), m.Currency+" "), m.Currency})
}

// UnmarshalJSON has a pointer receiver, so it can change the Money it decodes into.
func (m *Money) UnmarshalJSON(data []byte) error {
	var raw struct {
		Amount   string `json:"amount"`
		Currency string `json:"currency"`
	}
	if err := json.Unmarshal(data, &raw); err != nil {
		return err
	}
	c, err := parseCents(raw.Amount)
	if err != nil {
		return err
	}
	m.Cents, m.Currency = c, raw.Currency
	return nil
}

func main() {
	b, _ := json.Marshal(Money{Cents: -50, Currency: "USD"})
	fmt.Println(string(b))
	for _, in := range []string{"49.99", "-0.50", "49.5", "49", "1.234"} {
		var m Money
		err := json.Unmarshal([]byte(`{"amount":"`+in+`","currency":"USD"}`), &m)
		fmt.Printf("%-6s -> cents=%-5d err=%v\n", in, m.Cents, err)
	}
}
```

</GoPlayground>

```text
-0.50  -> cents=-50   err=<nil>
49.5   -> cents=0     err=amount "49.5": want digits, a dot, and exactly two decimals
49     -> cents=0     err=amount "49": want digits, a dot, and exactly two decimals
```

<Callout kind="warn" title="Receivers for JSON methods">

Put `MarshalJSON` on the **value** receiver: then it's used for `Money` values and `*Money` alike, including values stored in maps and interfaces. Put `UnmarshalJSON` on the **pointer** receiver, because it must change the value.

Get the second one wrong and the failure is silent. With `func (m Money) UnmarshalJSON(…)`, `*Money` still has the method (a pointer's method set includes value methods), so `encoding/json` **does** call it, on a copy. Decoding `{"B":{"Cents":7}}` into a struct using such a type left `Cents` at 0 with a nil error: the method ran, changed its copy, and the copy was thrown away.

</Callout>

## Type Assertions & Type Switches

*Stop 5 of 5.*

### Step 1: getting the concrete type back

<Define term="Type assertion and type switch">
`v, ok := x.(T)` asks whether interface value `x` holds a `T` (or, if `T` is an interface, something that satisfies it); `ok` says whether it did. `switch v := x.(type) { case A: … case B: … }` checks several types in turn, with `v` of the matching type in each case.
</Define>

```go
f := r.(*os.File)     // panics if r doesn't hold an *os.File
f, ok := r.(*os.File) // never panics; ok is false instead
```

The single-result form panics with a message like `interface conversion: io.Reader is *bytes.Buffer, not *os.File`. Use it only when a mismatch really is a bug; otherwise use the two-result form.

Assertions to an **interface** type are how Go discovers optional abilities. `io.Copy` itself does this: it checks whether the source has a `WriteTo` method or the destination a `ReadFrom` method, and uses them if so (that's why the `strings.Reader` case above failed differently):

```go
func rewindIfPossible(r io.Reader) error {
	if s, ok := r.(io.Seeker); ok {
		_, err := s.Seek(0, io.SeekStart)
		return err
	}
	return nil // can't seek: fine, carry on
}
```

### Step 2: switching on type

<GoPlayground>

```go
package main

import "fmt"

type DepositEvent struct {
	AccountID string
	Cents     int64
}

type WithdrawalEvent struct {
	AccountID string
	Cents     int64
}

type TransferEvent struct {
	FromID, ToID string
	Cents        int64
}

func describe(e any) string {
	switch ev := e.(type) {
	case *DepositEvent:
		return fmt.Sprintf("deposit  %s +%d", ev.AccountID, ev.Cents)
	case *WithdrawalEvent:
		return fmt.Sprintf("withdraw %s -%d", ev.AccountID, ev.Cents)
	case *TransferEvent:
		return fmt.Sprintf("transfer %s → %s %d", ev.FromID, ev.ToID, ev.Cents)
	default:
		return fmt.Sprintf("unknown event %T", e)
	}
}

func main() {
	for _, e := range []any{
		&DepositEvent{"acc_001", 10000},
		&TransferEvent{"acc_001", "acc_002", 5000},
		&WithdrawalEvent{"acc_002", 2500},
		"a string by mistake",
	} {
		fmt.Println(describe(e))
	}
}
```

</GoPlayground>

```text
deposit  acc_001 +10000
transfer acc_001 → acc_002 5000
withdraw acc_002 -2500
unknown event string
```

### Step 3: when a method is better than a switch

Add a `FeeEvent` and forget to update `describe`, and nothing complains: it falls into `default`. If you own the types and the behaviour belongs to them, make it a method, and the compiler checks every type has it:

<BeforeAfter
  badLabel="switch: new types slip through"
  goodLabel="method: new types must implement it"
  bad={`func apply(e any, l *Ledger) error {
	switch ev := e.(type) {
	case *DepositEvent:
		return l.deposit(ev)
	case *WithdrawalEvent:
		return l.withdraw(ev)
	}
	return nil // FeeEvent? silently ignored
}`}
  good={`type LedgerEvent interface {
	Apply(*Ledger) error
}

// A FeeEvent without Apply can't be
// passed as a LedgerEvent: compile error.
func apply(e LedgerEvent, l *Ledger) error {
	return e.Apply(l)
}`}
/>

Keep type switches for when you **don't** own the types, or the logic genuinely belongs to the caller (encoding, formatting, converting `any` from `encoding/json`).

<QuickCheck
  question="You add FeeEvent. Where does the compiler tell you something needs handling it?"
  options={[

  explain="Type switches never produce errors for missing cases. An interface does: using a FeeEvent where a LedgerEvent is required fails to compile until FeeEvent implements Apply."
/>

**Recap.** Use `v, ok := x.(T)` unless a mismatch is truly a bug. Assert to interfaces to discover optional abilities. Type switches suit types you don't own; methods on an interface make the compiler enforce new cases.

<Exercise n={2} title="Two ways to sort" level="easy">

Sort a `[]Account` by name, ascending, first with `slices.SortFunc` and `cmp.Compare`, then with a `ByNameAsc` type implementing `sort.Interface`. Which would you use in new code?

<Solution>

```go
package main

import (
	"cmp"
	"fmt"
	"slices"
	"sort"
)

type Account struct {
	Name  string
	Cents int64
}

type ByNameAsc []Account

func (s ByNameAsc) Len() int           { return len(s) }
func (s ByNameAsc) Swap(i, j int)      { s[i], s[j] = s[j], s[i] }
func (s ByNameAsc) Less(i, j int) bool { return s[i].Name < s[j].Name }

func main() {
	a := []Account{{"Savings", 25000}, {"Checking", 5000}, {"Reserve", 100000}}
	b := slices.Clone(a)

	slices.SortFunc(a, func(x, y Account) int { return cmp.Compare(x.Name, y.Name) })
	sort.Sort(ByNameAsc(b))
	fmt.Println(a)
	fmt.Println(b)
}
```

Both print `[{Checking 5000} {Reserve 100000} {Savings 25000}]`. In new code `slices.SortFunc` is shorter and needs no extra type; a named `sort.Interface` type is worth it when the same order is used in many places.

</Solution>

</Exercise>

<Exercise n={3} title="A typed error" level="medium">

Define `ValidationError{Field, Message string}` implementing `error`. Make `validateTransfer(cents int64) error` return one (wrapped with context) for non-positive amounts, and extract `Field` in `main` with `errors.AsType`.

<Solution>

```go
package main

import (
	"errors"
	"fmt"
)

type ValidationError struct {
	Field, Message string
}

func (e *ValidationError) Error() string {
	return fmt.Sprintf("invalid %s: %s", e.Field, e.Message)
}

func validateTransfer(cents int64) error {
	if cents <= 0 {
		return fmt.Errorf("validate transfer: %w", &ValidationError{Field: "amount", Message: "must be positive"})
	}
	return nil
}

func main() {
	err := validateTransfer(-100)
	fmt.Println(err) // validate transfer: invalid amount: must be positive
	if ve, ok := errors.AsType[*ValidationError](err); ok {
		fmt.Println("field:", ve.Field) // field: amount
	}
}
```

`errors.AsType` finds the `*ValidationError` through the wrapping; a plain type assertion `err.(*ValidationError)` would fail because `err` is the wrapper.

</Solution>

</Exercise>

<Exercise n={4} title="A writer that keeps its contract" level="medium">

Write `LineCounter`, an `io.Writer` that counts newline characters passing through it and forwards everything to another writer. Check it with `io.Copy` from a `strings.Reader` (which uses the `WriteTo` fast path) and from a reader that doesn't have it.

<Solution>

```go
package main

import (
	"bytes"
	"fmt"
	"io"
	"os"
	"strings"
)

type LineCounter struct {
	W     io.Writer
	Lines int
}

func (c *LineCounter) Write(p []byte) (int, error) {
	n, err := c.W.Write(p)
	c.Lines += bytes.Count(p[:n], []byte("\n")) // count only what was actually written
	return n, err
}

type plainReader struct{ r io.Reader } // hides strings.Reader's WriteTo

func (p plainReader) Read(b []byte) (int, error) { return p.r.Read(b) }

func main() {
	text := "a,1\nb,2\nc,3\n"
	for _, src := range []io.Reader{strings.NewReader(text), plainReader{strings.NewReader(text)}} {
		lc := &LineCounter{W: io.Discard}
		n, err := io.Copy(lc, src)
		fmt.Fprintln(os.Stdout, n, err, lc.Lines) // 12 <nil> 3, both times
	}
}
```

Returning exactly what the inner writer reports keeps the contract (`0 <= n <= len(p)`) whatever it does, so both `io.Copy` paths work.

</Solution>

</Exercise>

<Exercise n={5} title="Switch or interface?" level="hard">

Events `DepositEvent`, `WithdrawalEvent` and `FeeEvent` each carry `Cents`. Write `summarize(events []any)` with a type switch that totals each kind, then a version over `[]LedgerEvent` where `LedgerEvent` has `Cents() int64` and `Kind() string`. Add a `RefundEvent`: what does each version do?

<Solution>

```go
package main

import "fmt"

type DepositEvent struct{ C int64 }
type WithdrawalEvent struct{ C int64 }
type FeeEvent struct{ C int64 }

func summarize(events []any) map[string]int64 {
	t := map[string]int64{}
	for _, e := range events {
		switch ev := e.(type) {
		case *DepositEvent:
			t["deposit"] += ev.C
		case *WithdrawalEvent:
			t["withdrawal"] += ev.C
		case *FeeEvent:
			t["fee"] += ev.C
		}
	}
	return t
}

type LedgerEvent interface {
	Cents() int64
	Kind() string
}

func (e *DepositEvent) Cents() int64    { return e.C }
func (e *DepositEvent) Kind() string    { return "deposit" }
func (e *WithdrawalEvent) Cents() int64 { return e.C }
func (e *WithdrawalEvent) Kind() string { return "withdrawal" }
func (e *FeeEvent) Cents() int64        { return e.C }
func (e *FeeEvent) Kind() string        { return "fee" }

func summarizeIface(events []LedgerEvent) map[string]int64 {
	t := map[string]int64{}
	for _, e := range events {
		t[e.Kind()] += e.Cents()
	}
	return t
}

func main() {
	fmt.Println(summarize([]any{&DepositEvent{10000}, &WithdrawalEvent{3000}, &FeeEvent{50}}))
	fmt.Println(summarizeIface([]LedgerEvent{&DepositEvent{10000}, &WithdrawalEvent{3000}, &FeeEvent{50}}))
}
```

Both print `map[deposit:10000 fee:50 withdrawal:3000]`. Add `RefundEvent` and pass one in: `summarize` silently ignores it (the totals are just wrong), while putting it in a `[]LedgerEvent` doesn't compile until it has `Cents` and `Kind`, and once it does, `summarizeIface` handles it with no changes.

</Solution>

</Exercise>
