## The Go Proverbs & Mindset

Here's the scene. You've just joined the backend team at Meridian. The repo is a mix of two eras: old code written by engineers who came from Java and Python, crammed with layered abstractions, six-interface inheritance chains, and helper packages for everything; and new code written by whoever read half of Effective Go and got excited. Neither codebase is Go. Your job is to fix that.

The first tool is the **Go proverbs** — a set of aphorisms Rob Pike delivered in 2015 that crystallize the language's design philosophy. They aren't rules the compiler enforces. They're *heuristics* that, when you've internalized them, let you feel when code is fighting the language. Let me walk through the ones that matter most for production Go.

### "Clear is better than clever."

Clever code is code where the author had a good time and the reader has a bad one.

<BeforeAfter
  badLabel="Clever"
  goodLabel="Clear"
  bad={`// "clever": pack two results in one int
func minMax(s []int) int {
    return s[0]<<32 | s[len(s)-1]
}`}
  good={`// clear: two named returns, reads itself
func minMax(s []int) (min, max int) {
    return s[0], s[len(s)-1]
}`}
/>

The clever version bit-packs two ints into one. Brilliant! It's also unreadable, broken on 32-bit ints, and the person debugging the 3am incident will not find it charming. The clear version returns two values because it has two values. Go gives you multiple returns — *use them*.

**On the job:** Clever bit-packing shows up in ledger hot-paths every six months. It survives exactly one incident before someone rewrites it in plain arithmetic at 3am.

### "A little copying is better than a little dependency."

Before you reach for a library, ask whether the ten-line helper you need is worth the transitive dependencies, the upgrade treadmill, and the supply-chain surface area that comes with it. Often, the honest answer is: just copy the twenty lines. Go's standard library is massive and battle-tested. Exhaust it first.

<Callout kind="pro" title="The standard library is the benchmark">

If `strings`, `strconv`, `bytes`, `slices`, `maps`, `sync`, `context`, `io`, `fmt`, or `net/http` already do what you need, use them. A dependency on a popular utility library is often a statement that you didn't read the standard library carefully enough.

</Callout>

**On the job:** Every transitive dependency is a supply-chain risk, an upgrade treadmill entry, and a potential CVE. Meridian's security reviews catch this; your dependency graph review will too.

### "The bigger the interface, the weaker the abstraction."

This one is *load-bearing* and we'll unpack it for the whole chapter. The short version: a type that satisfies a 10-method interface tells you almost nothing about what the concrete thing is. A type that satisfies a 1-method interface is a *precise claim* about a single capability. Small interfaces compose; big interfaces constrain.

```go
// io.Reader: one method, infinite power
type Reader interface {
    Read(p []byte) (n int, err error)
}
```

That single-method interface is implemented by files, network connections, HTTP response bodies, bytes buffers, strings, and a thousand third-party types. A function that accepts an `io.Reader` works with all of them — automatically. We'll see this in full when we implement it ourselves.

**On the job:** A 10-method `AccountRepository` defined in a shared package is the single most common reason Meridian's service-layer tests take 45 minutes to write a two-line fake for.

### "Make the zero value useful."

A type whose zero value is already valid — needs no constructor, no `New()`, no `Init()` — is a gift to every caller. `sync.Mutex`, `bytes.Buffer`, `sync.WaitGroup` all work correctly straight out of a `var` declaration. When you design a type, ask: *what is the sensible empty state, and can I make the zero value be that?*

```go
var buf bytes.Buffer       // zero value: empty buffer, ready to write
var mu  sync.Mutex         // zero value: unlocked, ready to Lock()
var wg  sync.WaitGroup     // zero value: count 0, Wait() returns immediately
```

No constructor needed. No "did you call Init() first?" footgun. The zero value *is* the correct starting state.

**On the job:** Types that require `Init()` calls produce subtle bugs in Meridian's worker pools when someone forgets to initialize before goroutine launch. The zero value sidesteps the whole class of problem.

### "Errors are values."

In Go, errors are plain values of type `error`. They're not exceptions that unwind the stack through hidden machinery. You have them in your hands, you inspect them, you transform them, you return them. This means you can *compute* with errors — wrap them, collect them, retry on specific ones, log them with context.

<BeforeAfter
  badLabel="Fighting the language"
  goodLabel="Errors as values"
  bad={`// panic/recover as control flow: no

    defer func() { recover() }()
    return mustParse(s) // panics on bad input

  good={`// return the error; caller decides

    v, err := strconv.Atoi(s)

/>

We have an entire chapter on error handling at scale (the Error Handling at Scale chapter). For now: errors are values. Return them. Handle them. Never swallow them with `_`.

## Naming & API Design

Meridian's ledger service has a problem. A new engineer opened `account.go` and found names like `ProcessTxn`, `GetBal`, `UpdateAcctInfo`, and a type called `Mgr`. He asked what `Mgr` manages. Nobody could remember.

Good Go naming isn't about length — it's about **precision and scope**.

### Short names in small scopes

The rule: the larger the scope, the more descriptive the name needs to be. A variable used for three lines in a loop body can be `n`, `i`, `v`. A type exported at package level needs a name that carries its meaning without context.

```go
// Inside a tight loop: short is fine — scope makes it clear
for i, tx := range transactions {
    sum += tx.AmountCents
}

// Package-level exported type: full, precise name
type Transaction struct {
    ID          string
    AmountCents int64
    AccountID   string
    CreatedAt   time.Time
}
```

Go's own standard library is the model: `io.Reader`, `http.Handler`, `json.Decoder`. Short packages, precise type names, no stutter (`http.HTTPHandler` would be stutter — the package already says `http`).

### Exported API surface

**Don't export what you don't have to.** Unexported types, functions, and fields are internal contracts you can change freely. Exported names are public promises you're stuck with. Keep the exported surface small and intentional.

<BeforeAfter
  badLabel="Over-exported"
  goodLabel="Minimal surface"
  bad={`// exports internals that callers
// never need to touch directly
type Ledger struct {
    DB       *sql.DB
    Cache    map[string]int64
    Logger   *log.Logger
    mu       sync.Mutex
}`}
  good={`// only the constructor and
// business methods are exported
type Ledger struct {
    db    *sql.DB
    cache map[string]int64
    log   *slog.Logger
    mu    sync.Mutex
}

func NewLedger(db *sql.DB) *Ledger {…}`}
/>

Callers get `NewLedger` and the business methods. The internals — the DB handle, the cache, the mutex — are yours to change without breaking anyone.

**On the job:** Exported `DB *sql.DB` fields were the root cause of a Meridian outage: a runaway integration test grabbed the handle and ran a `DROP TABLE` in the wrong env. Unexported fields make that impossible.

### Accept interfaces, return structs

This is the most repeated piece of Go API advice, and it bears the full treatment because it's often applied mechanically without understanding *why*.

**Accept interfaces** so your function works with anything that satisfies the contract — not just the one concrete type you thought of on Tuesday.

**Return structs** (or concrete types) so callers get the full rich type and don't have to type-assert their way back to reality.

```go
// Good: accepts io.Reader — works with files,
// HTTP bodies, strings, buffers — whatever the
// caller has. Returns a concrete *Transaction
// so callers get every field.
func ParseTransaction(r io.Reader) (*Transaction, error) {
    var tx Transaction
    if err := json.NewDecoder(r).Decode(&tx); err != nil {
        return nil, fmt.Errorf("parse transaction: %w", err)
    }
    return &tx, nil
}
```

The exception: return an interface when the interface *is* the full contract and you genuinely need to hide the concrete type (e.g., returning `error`, or an `http.Handler`). When in doubt, return the struct.

<GoPlayground>


## Small Interfaces & When Not to Abstract

Meridian's ledger service also has an `AccountRepository` interface with eleven methods. I've seen this pattern in every Go codebase written by engineers who came from Java. The interface was defined in the domain layer, implemented by a Postgres adapter, and now every test needs a mock of all eleven methods even when the test only exercises one. This is the cost of premature abstraction.

### Define interfaces at the consumer

The Go way: interfaces live in the package that *uses* them, not the package that *provides* the implementation. This is the opposite of what most OOP languages teach.

```go
// WRONG: interface in the storage package,
// forcing every consumer to import it
package storage

type AccountRepository interface {
    GetByID(ctx context.Context, id string) (*Account, error)
    Create(ctx context.Context, a *Account) error
    Update(ctx context.Context, a *Account) error
    Delete(ctx context.Context, id string) error
    List(ctx context.Context, filter Filter) ([]*Account, error)
    // … six more methods …
}
```

```go
// RIGHT: interface defined in the package
// that needs it, for exactly what it needs
package transfer

// Transferer only needs to read a balance
// and post a debit/credit. That's the contract.
type accountReader interface {
    GetByID(ctx context.Context, id string) (*Account, error)
}
```

Now the `transfer` package's test just needs a two-line fake, not a mock of eleven methods. And the Postgres `AccountStore` satisfies `accountReader` automatically — no registration, no `implements` keyword.

**On the job:** Meridian's transfer service went from a 300-line test setup file to a 20-line fake the day the team defined `accountStore` at the consumer. That's not a small win — that's the difference between tests people skip and tests people trust.

### One-method interfaces are the ideal

Rob Pike has said that the interface with a single method is the most powerful abstraction in Go. Look at the standard library:

<ConceptGrid cols={3}>
  <ConceptCard label="io.Reader">One method: `Read`. Everything that produces bytes — files, network, buffers — satisfies it.</ConceptCard>
  <ConceptCard label="io.Writer">One method: `Write`. Everything that consumes bytes satisfies it. `io.Copy` chains them.</ConceptCard>
  <ConceptCard label="fmt.Stringer">One method: `String() string`. Anything that can represent itself as a string gets formatted by `fmt` for free.</ConceptCard>
  <ConceptCard label="error">One method: `Error() string`. Any type with this method is a first-class Go error.</ConceptCard>
  <ConceptCard label="http.Handler">One method: `ServeHTTP`. Any struct that handles an HTTP request becomes middleware-composable.</ConceptCard>
  <Gotcha>Defining a 10-method interface in a shared package and implementing it everywhere is the Java DAO pattern wearing Go clothing. It looks like abstraction. It is actually coupling — every implementation is locked to the full contract, and every change requires touching both sides.</Gotcha>
</ConceptGrid>

### The cost of premature abstraction

Before you define an interface, ask three questions:

1. **Do I have more than one implementation right now?** If not, the interface is speculative. Write the concrete type and extract the interface later when the second implementation appears.
2. **Does abstracting this make the tests simpler or more complex?** A good interface reduces the test surface. A bad one multiplies it.
3. **Am I hiding something useful?** If callers need to type-assert back to the concrete type 30% of the time, the interface is hiding too much.

<UnderTheHood title="How the compiler checks interface satisfaction (structural typing & the itable)">

*This section describes Go 1.26 behavior. The itable layout has been stable since Go 1.0; devirtualization improvements are ongoing each release.*

Go uses **structural typing**: a type satisfies an interface if it has all the required methods — period. No `implements` declaration, no registration. The compiler checks this at the point of assignment or function call.

When you write:

```go
var r io.Reader = os.Stdin
```

The compiler verifies at compile time that `*os.File` has a `Read([]byte)(int, error)` method. If it doesn't, you get a compile error. This check is **zero-cost at runtime** for the declaration — it's entirely static.

At runtime, an interface value is a **two-word structure**: a pointer to the **itable** (interface table) and a pointer to the **data** (the concrete value, or a pointer to it if it doesn't fit in a word).

The itable contains:
- A pointer to the concrete type's type descriptor (used by `reflect`, type switches, etc.)
- A slot for each method in the interface, holding a function pointer to the concrete type's implementation

So when you call `r.Read(buf)`, the runtime:
1. Loads the itable pointer from the interface value.
2. Indexes into the itable to find the `Read` function pointer.
3. Calls it with the data pointer as the receiver.

This is one extra indirection compared to a direct method call. The cost is real but small — typically one cache miss for the itable lookup. Go's compiler performs **devirtualization** when it can prove at compile time which concrete type is behind the interface, eliminating the indirection entirely. As of Go 1.26, escape analysis and inliner improvements make devirtualization more aggressive than ever — treat this as a conceptual model; the optimizer may already have eliminated the dispatch in your hot path. (This is a simplification of the real pipeline — PGO-guided devirtualization adds another layer beyond static analysis.)

The key insight: **interface satisfaction is a compile-time invariant, not a runtime registration**. If your code compiles, every interface assignment is guaranteed correct. The runtime only pays for the call dispatch, not for checking.

</UnderTheHood>

## Implementing Stdlib Interfaces

Now we build. Meridian's ledger service has a `Money` type and an `Account` type. Right now they're plain structs that know nothing about the ecosystem. By the end of this section, `Money` will format itself beautifully in logs, sort correctly in slices, marshal to JSON the way the API spec requires, and flow through any `io.Writer` pipeline — all for free, because we hook into the right interfaces.

### The scenario: Meridian's ledger service

```go
// Money represents a monetary amount in minor units (cents).
// money is never a float — this is the law.
type Money struct {
    Cents    int64
    Currency string // "USD", "EUR", …
}

// Account is a ledger account.
type Account struct {
    ID      string
    Name    string
    Balance Money
}
```

### `fmt.Stringer` — hooking into fmt

Any type with a `String() string` method satisfies `fmt.Stringer`. Every `fmt` function — `Println`, `Printf %v`, `Sprintf`, `log`, `slog` — calls `String()` automatically if it exists.

```go
// Money implements fmt.Stringer.
func (m Money) String() string {
    major := m.Cents / 100
    minor := m.Cents % 100
    if minor < 0 {
        minor = -minor
    }
    return fmt.Sprintf("%s %d.%02d", m.Currency, major, minor)
}

// Account implements fmt.Stringer.
func (a Account) String() string {
    return fmt.Sprintf("Account(%s %q balance=%s)",
        a.ID, a.Name, a.Balance)
}
```

Now `fmt.Println(a)` outputs `Account(acc_001 "Operating Account" balance=USD 1250.00)`. The `fmt` package found `String()` on `Account`, which called `String()` on `Money`. All automatic.

**On the job:** Without `Stringer`, every `slog` line in Meridian's settlement job printed `{125000 USD}` raw. After adding `String()`, the ops team could read logs without a decoder ring. Three minutes of work; hours of debugging saved.

### `error` — the simplest interface

`error` is defined in the universe block as:

```go
type error interface {
    Error() string
}
```

Any type with an `Error() string` method is a valid Go error. This means you can carry rich context on your errors — not just a string, but typed fields the caller can inspect.

```go
// TransferError is a typed error for failed transfers.
// It satisfies the error interface.
type TransferError struct {
    From   string
    To     string
    Amount Money
    Reason string
}

func (e *TransferError) Error() string {
    return fmt.Sprintf("transfer %s→%s %s: %s",
        e.From, e.To, e.Amount, e.Reason)
}
```

Callers can check for `*TransferError` specifically using `errors.As` — we'll dissect that fully in the Error Handling at Scale chapter. As of **Go 1.26**, there is also a generic convenience function `errors.AsType[T]` that eliminates the temporary variable:

```go
// Go 1.26+: errors.AsType[T] returns (T, bool)
if te, ok := errors.AsType[*TransferError](err); ok {
    fmt.Printf("transfer failed from=%s reason=%s\n", te.From, te.Reason)
}
```

The two forms are equivalent in power — `errors.AsType[T]` is purely ergonomic, useful when you want the typed value inline without pre-declaring a variable. For now: implement `Error() string` on your error types instead of returning generic `fmt.Errorf` strings when callers need to react to specific failure modes.

**On the job:** Meridian's reconciliation job distinguishes `*InsufficientFundsError` from `*FXRateError` using `errors.As` to decide whether to retry or dead-letter. A stringly-typed error would force brittle string matching.

### `sort.Interface` — sorting your types

`sort.Interface` has three methods:

```go
type Interface interface {
    Len() int
    Less(i, j int) bool
    Swap(i, j int)
}
```

Implement it on a slice type and you get `sort.Sort`, `sort.Stable`, and `sort.Search` for free. Meridian's ledger service needs to sort accounts by balance descending (for a reporting dashboard) and by name ascending (for display lists).

```go
// ByBalanceDesc sorts accounts by balance, largest first.
type ByBalanceDesc []Account

func (s ByBalanceDesc) Len() int      { return len(s) }
func (s ByBalanceDesc) Swap(i, j int) { s[i], s[j] = s[j], s[i] }
func (s ByBalanceDesc) Less(i, j int) bool {
    return s[i].Balance.Cents > s[j].Balance.Cents // note: > for descending
}
```

As of **Go 1.21**, the `slices` package gives you `slices.SortFunc` with a comparison closure using `cmp.Compare` — the idiomatic default for one-off sorts in Go 1.26:

```go
import (
    "cmp"
    "slices"
)

// Idiomatic Go 1.26: slices.SortFunc with cmp.Compare
slices.SortFunc(accounts, func(a, b Account) int {
    return cmp.Compare(b.Balance.Cents, a.Balance.Cents) // descending
})
```

Implementing `sort.Interface` is still the right move when you want a **named, reusable sort order** — particularly for `sort.Stable`, which has no generic counterpart. The lab uses the explicit interface so you practice implementing it.

**On the job:** Meridian's reporting dashboard sorts 50,000 accounts by balance on every request. `slices.SortFunc` with `cmp.Compare` is measurably faster than `sort.Sort` with a type assertion, because the generic version avoids the interface dispatch overhead on every comparison.

### `io.Reader` and `io.Writer` — the pipeline interfaces

`io.Reader` and `io.Writer` are the connective tissue of the Go ecosystem. Any type that can produce bytes is a Reader; any type that can consume bytes is a Writer. `io.Copy(dst, src)` chains them: it reads from `src` in chunks and writes each chunk to `dst`, with no intermediate buffering of the full content.

**On the job:** Meridian's nightly reconciliation job streams 2GB statement files through `io.Copy` without ever holding more than a 32KB buffer. Before the rewrite, it loaded the whole file into a `[]byte` and ran out of memory in prod at 1am. `io.Reader` is not academic — it's the difference between a job that runs and one that OOMs.

Let's make an `AuditLog` that implements `io.Writer` and a `TransactionReport` that implements `io.Reader`:

```go
// AuditLog is an io.Writer that prefixes each write with a timestamp.
type AuditLog struct {
    w   io.Writer
    now func() time.Time
}

func (a *AuditLog) Write(p []byte) (int, error) {
    line := fmt.Appendf(nil, "[%s] %s",
        a.now().Format(time.RFC3339), p)
    return a.w.Write(line)
}
```

And a `TransactionReport` that implements `io.Reader`, streaming its lines on demand:

```go
// TransactionReport streams Account records as lines.
type TransactionReport struct {
    accounts []Account
    idx      int
    buf      []byte
}

func (r *TransactionReport) Read(p []byte) (int, error) {
    // fill buf if empty
    for len(r.buf) == 0 {
        if r.idx >= len(r.accounts) {
            return 0, io.EOF
        }
        a := r.accounts[r.idx]
        r.idx++
        r.buf = fmt.Appendf(nil, "%s,%s,%s\n",
            a.ID, a.Name, a.Balance)
    }
    n := copy(p, r.buf)
    r.buf = r.buf[n:]
    return n, nil
}
```

Now `io.Copy(auditLog, report)` pipes the whole report through the audit log, one chunk at a time, without ever holding the full report in memory. That's the pipeline.

### `json.Marshaler` and `json.Unmarshaler` — custom JSON

The API spec says `Money` must serialize as `{"amount": "1250.00", "currency": "USD"}` — a string for the amount, not an integer. The default JSON encoding would produce `{"Cents":125000,"Currency":"USD"}`. We need `json.Marshaler` and `json.Unmarshaler`.

```go
// json.Marshaler
func (m Money) MarshalJSON() ([]byte, error) {
    s := fmt.Sprintf(`{"amount":"%d.%02d","currency":%q}`,
        m.Cents/100, abs(m.Cents%100), m.Currency)
    return []byte(s), nil
}

// json.Unmarshaler
func (m *Money) UnmarshalJSON(data []byte) error {
    var raw struct {
        Amount   string `json:"amount"`
        Currency string `json:"currency"`
    }
    if err := json.Unmarshal(data, &raw); err != nil {
        return err
    }
    // parse "1250.00" → 125000 cents
    var major, minor int64
    _, err := fmt.Sscanf(raw.Amount, "%d.%02d", &major, &minor)
    if err != nil {
        return fmt.Errorf("Money.UnmarshalJSON: bad amount %q: %w",
            raw.Amount, err)
    }
    m.Cents = major*100 + minor
    m.Currency = raw.Currency
    return nil
}
```

Now `json.Marshal(account)` and `json.Unmarshal(data, &account)` use our custom format automatically — no special encoder, no configuration. The interface hook does the wiring.

**On the job:** Meridian's `POST /transfers` API accepts `{"amount":"49.99","currency":"USD"}` from clients and must persist it as integer cents. Without `UnmarshalJSON`, every handler would parse the string manually — a conversion bug waiting to happen. With `UnmarshalJSON` on `Money`, the parsing is centralized and tested once.

## Type Assertions & Type Switches

The `io.Reader` pipeline just sent a `TransactionReport` through an `AuditLog`. Both are concrete types hiding behind interfaces. Sometimes you need to reach back through the interface and get the concrete type — or dispatch different behavior based on what the concrete type actually is. That's what type assertions and type switches are for.

### Type assertions: `x.(T)`

A type assertion takes an interface value and extracts the concrete value of type `T`:

```go
var r io.Reader = os.Stdin

// form 1: panics if r doesn't hold *os.File
f := r.(*os.File)

// form 2: comma-ok — safe, never panics
f, ok := r.(*os.File)
if ok {
    fmt.Println("reading from file:", f.Name())
}
```

**Always use the comma-ok form** unless you are *certain* the assertion will succeed (and even then, be suspicious of that certainty). A panicking type assertion in production is an outage.

**On the job:** A bare `r.(*os.File)` in Meridian's report pipeline caused a panic in staging when someone passed a `bytes.Buffer` instead of a file. The comma-ok form would have gracefully skipped the seek. One prod incident, avoidable.

The ledger use case: a function that accepts an `io.Reader` but wants to seek back to the start if the reader supports it.

```go
func resetIfSeekable(r io.Reader) {
    // io.ReadSeeker extends io.Reader with Seek()
    if rs, ok := r.(io.ReadSeeker); ok {
        rs.Seek(0, io.SeekStart)
    }
    // if it can't seek, we just move on — that's fine
}
```

### Type switches: `switch v := x.(type)`

When you have multiple possible concrete types to handle differently, a type switch is cleaner than a chain of assertions:

```go
// A ledger event can be one of several concrete types.
type DepositEvent struct { AccountID string; Amount Money }
type WithdrawalEvent struct { AccountID string; Amount Money }
type TransferEvent struct { FromID, ToID string; Amount Money }

func processEvent(e any) {
    switch ev := e.(type) {
    case *DepositEvent:
        fmt.Printf("deposit to %s: %s\n", ev.AccountID, ev.Amount)
    case *WithdrawalEvent:
        fmt.Printf("withdrawal from %s: %s\n", ev.AccountID, ev.Amount)
    case *TransferEvent:
        fmt.Printf("transfer %s→%s: %s\n",
            ev.FromID, ev.ToID, ev.Amount)
    default:
        fmt.Printf("unknown event type: %T\n", e)
    }
}
```

In each `case`, `ev` is automatically the concrete type — `*DepositEvent`, `*WithdrawalEvent`, etc. No further assertion needed.

### When type switches are a design smell

A type switch that dispatches behavior is essentially a form of polymorphism — but without the compiler helping you when you add a new type. If you add `FeeEvent` to the ledger and forget to update `processEvent`, the compiler says nothing. The `default` case catches it silently.

The idiomatic alternative: **define a method on the interface**.

```go
type LedgerEvent interface {
    Apply(ledger *Ledger) error
}
```

Now each event type implements `Apply`. When you add `FeeEvent`, the compiler forces you to implement `Apply` before it compiles. The type switch becomes a for loop:

```go
for _, e := range events {
    if err := e.Apply(ledger); err != nil {
        return err
    }
}
```

**The rule:** use a type switch when the dispatching logic is truly external to the types (you can't add a method because you don't own the types, or the behavior is inherently caller-side). Prefer polymorphism via interfaces when you control the types and the dispatch pattern recurs.

Create a `Money` struct with `Cents int64` and `Currency string`. Implement `fmt.Stringer` so that `fmt.Println(Money{Cents: 9999, Currency: "EUR"})` prints `EUR 99.99`. Handle negative cents correctly (e.g., `Money{Cents: -500, Currency: "USD"}` → `USD -5.00`).

<Solution>

```go
package main

import "fmt"

type Money struct {
	Cents    int64
	Currency string
}

func (m Money) String() string {
	sign := ""
	c := m.Cents
	if c < 0 {
		sign = "-"
		c = -c
	}
	return fmt.Sprintf("%s %s%d.%02d", m.Currency, sign, c/100, c%100)
}

func main() {
	fmt.Println(Money{Cents: 9999, Currency: "EUR"})  // EUR 99.99
	fmt.Println(Money{Cents: -500, Currency: "USD"})  // USD -5.00
	fmt.Println(Money{Cents: 0, Currency: "GBP"})     // GBP 0.00
}
```

The key: handle the sign separately, then work with the absolute value. `%02d` zero-pads the minor unit to always show two digits.

</Solution>

</Exercise>

<Exercise n={2} title="sort.Interface on a ledger slice" level="easy">

Given a `[]Account` (where `Account` has `Name string` and `Balance Money`), implement `sort.Interface` as a named type `ByNameAsc` that sorts accounts alphabetically by name. Demonstrate with `sort.Sort`.

<Solution>

```go
package main

import (
	"fmt"
	"sort"
)

type Money struct{ Cents int64 }

type Account struct {
	Name    string
	Balance Money
}

type ByNameAsc []Account

func (s ByNameAsc) Len() int           { return len(s) }
func (s ByNameAsc) Swap(i, j int)      { s[i], s[j] = s[j], s[i] }
func (s ByNameAsc) Less(i, j int) bool { return s[i].Name < s[j].Name }

func main() {
	accounts := []Account{
		{Name: "Savings", Balance: Money{Cents: 25000}},
		{Name: "Checking", Balance: Money{Cents: 5000}},
		{Name: "Reserve", Balance: Money{Cents: 100000}},
	}
	sort.Sort(ByNameAsc(accounts))
	for _, a := range accounts {
		fmt.Println(a.Name)
	}
	// Checking, Reserve, Savings
}
```

`sort.Sort` requires only these three methods. The named type `ByNameAsc` makes the sort intent explicit and reusable.

</Solution>

</Exercise>

<Exercise n={3} title="Typed error with errors.As" level="medium">

Define a `ValidationError` struct with fields `Field string` and `Message string`. Implement the `error` interface. Write a `validateTransfer(amount Money) error` that returns a `*ValidationError` when `amount.Cents <= 0`. In `main`, call it and use `errors.As` to extract the `*ValidationError` and print its `Field`.

<Solution>

```go
package main

import (
	"errors"
	"fmt"
)

type Money struct{ Cents int64 }

type ValidationError struct {
	Field   string
	Message string
}

func (e *ValidationError) Error() string {
	return fmt.Sprintf("validation error on %s: %s", e.Field, e.Message)
}

func validateTransfer(amount Money) error {
	if amount.Cents <= 0 {
		return &ValidationError{
			Field:   "amount",
			Message: "must be positive",
		}
	}
	return nil
}

func main() {
	err := validateTransfer(Money{Cents: -100})
	if err != nil {
		fmt.Println(err)

		var ve *ValidationError
		if errors.As(err, &ve) {
			fmt.Println("failed field:", ve.Field)
		}
	}
}
```

`errors.As` unwraps the error chain looking for a `*ValidationError`. Because `validateTransfer` returns the concrete pointer directly (not wrapped), `errors.As` finds it on the first try.

</Solution>

</Exercise>

<Exercise n={4} title="json.Marshaler for Money" level="medium">

Implement `MarshalJSON` on `Money` (value receiver) so that `json.Marshal(Money{Cents: 4999, Currency: "USD"})` produces `{"amount":"49.99","currency":"USD"}`. Then implement `UnmarshalJSON` (pointer receiver) that can round-trip the value correctly. Write a short `main` that marshals and then unmarshals a `Money` and asserts the `Cents` are identical.

<Solution>

```go
package main

import (
	"encoding/json"
	"fmt"
)

type Money struct {
	Cents    int64
	Currency string
}

func (m Money) MarshalJSON() ([]byte, error) {
	c := m.Cents
	sign := ""
	if c < 0 {
		sign = "-"
		c = -c
	}
	s := fmt.Sprintf(`{"amount":"%s%d.%02d","currency":%q}`,
		sign, c/100, c%100, m.Currency)
	return []byte(s), nil
}

func (m *Money) UnmarshalJSON(data []byte) error {
	var raw struct {
		Amount   string `json:"amount"`
		Currency string `json:"currency"`
	}
	if err := json.Unmarshal(data, &raw); err != nil {
		return err
	}
	var major, minor int64
	if _, err := fmt.Sscanf(raw.Amount, "%d.%02d", &major, &minor); err != nil {
		return fmt.Errorf("bad amount %q: %w", raw.Amount, err)
	}
	m.Cents = major*100 + minor
	m.Currency = raw.Currency
	return nil
}

func main() {
	original := Money{Cents: 4999, Currency: "USD"}
	b, _ := json.Marshal(original)
	fmt.Println(string(b))

	var decoded Money
	if err := json.Unmarshal(b, &decoded); err != nil {
		fmt.Println("unmarshal error:", err)
		return
	}
	if decoded.Cents != original.Cents {
		fmt.Println("round-trip mismatch!")
		return
	}
	fmt.Println("round-trip OK: Cents =", decoded.Cents)
}
```

`MarshalJSON` on a value receiver, `UnmarshalJSON` on a pointer receiver — this is the required pattern. The pointer receiver lets `json.Unmarshal` modify the `Money` value through the pointer.

</Solution>

</Exercise>

<Exercise n={5} title="Type switch to process a mixed event log" level="hard">

Define three event types: `DepositEvent{AccountID string; AmountCents int64}`, `WithdrawalEvent{AccountID string; AmountCents int64}`, and `FeeEvent{AmountCents int64; Reason string}`. Write `summarize(events []any) (deposits, withdrawals, fees int64)` that uses a type switch to total the amounts for each category. Then refactor it to use a `LedgerEvent interface{ amountCents() int64; category() string }` — what changes, and what do you gain?

<Solution>

```go
package main

import "fmt"

// Part 1: type switch approach
type DepositEvent struct {
	AccountID  string
	AmountCents int64
}

type WithdrawalEvent struct {
	AccountID  string
	AmountCents int64
}

type FeeEvent struct {
	AmountCents int64
	Reason      string
}

func summarize(events []any) (deposits, withdrawals, fees int64) {
	for _, e := range events {
		switch ev := e.(type) {
		case *DepositEvent:
			deposits += ev.AmountCents
		case *WithdrawalEvent:
			withdrawals += ev.AmountCents
		case *FeeEvent:
			fees += ev.AmountCents
		}
	}
	return
}

// Part 2: interface approach
type LedgerEvent interface {
	amountCents() int64
	category() string
}

func (e *DepositEvent) amountCents() int64 { return e.AmountCents }
func (e *DepositEvent) category() string   { return "deposit" }

func (e *WithdrawalEvent) amountCents() int64 { return e.AmountCents }
func (e *WithdrawalEvent) category() string   { return "withdrawal" }

func (e *FeeEvent) amountCents() int64 { return e.AmountCents }
func (e *FeeEvent) category() string   { return "fee" }

func summarizeIface(events []LedgerEvent) map[string]int64 {
	totals := map[string]int64{}
	for _, e := range events {
		totals[e.category()] += e.amountCents()
	}
	return totals
}

func main() {
	events := []any{
		&DepositEvent{AccountID: "acc_001", AmountCents: 10000},
		&WithdrawalEvent{AccountID: "acc_001", AmountCents: 3000},
		&FeeEvent{AmountCents: 50, Reason: "monthly fee"},
		&DepositEvent{AccountID: "acc_002", AmountCents: 5000},
	}

	d, w, f := summarize(events)
	fmt.Printf("type-switch: deposits=%d withdrawals=%d fees=%d\n", d, w, f)

	iEvents := []LedgerEvent{
		&DepositEvent{AccountID: "acc_001", AmountCents: 10000},
		&WithdrawalEvent{AccountID: "acc_001", AmountCents: 3000},
		&FeeEvent{AmountCents: 50, Reason: "monthly fee"},
		&DepositEvent{AccountID: "acc_002", AmountCents: 5000},
	}
	totals := summarizeIface(iEvents)
	fmt.Println("interface: totals =", totals)
}
```

What you gain with the interface approach: if you add `RefundEvent`, the compiler refuses to build until it implements `amountCents()` and `category()`. The type switch silently drops unknown types into the ether.

</Solution>

</Exercise>

<Recap>

You've absorbed the Go mindset — not just the rules, but the *reasoning*:

- The **Go proverbs** are design heuristics: clear over clever, copy over a dependency, small interfaces, useful zero values, errors as values. Internalize them and you'll feel when code is fighting the language.
- **Naming**: short names in tight scopes, precise names at the package boundary, no stutter. Keep the exported surface minimal and intentional.
- **Accept interfaces, return structs**: widens what your function works with; gives callers the full concrete type without assertion gymnastics.
- **Define interfaces at the consumer**, not the provider. One-method interfaces are the most powerful. Extract an interface when the second implementation appears — not before.
- **Interface satisfaction is structural and compile-time**: Go checks it at the point of assignment. The itable is a two-word runtime structure: type pointer + method function pointers. Call dispatch is one indirection; the compiler devirtualizes when the concrete type is statically known (Go 1.26 baseline — PGO-guided devirtualization adds further wins in production binaries).
- **Implementing stdlib interfaces** gives your types free machinery: `fmt.Stringer` → automatic formatting in logs; `error` → first-class error with typed fields (extract with `errors.As`, or the Go 1.26 `errors.AsType[T]` generic shorthand); `sort.Interface` → plugs into `sort.Sort`/`sort.Stable`; `slices.SortFunc` + `cmp.Compare` is the idiomatic one-off alternative as of Go 1.21+; `io.Reader`/`io.Writer` → chains into any pipeline via `io.Copy`; `json.Marshaler`/`Unmarshaler` → full control over your wire format.
- **Type assertions** (`x.(T)`) extract a concrete type from an interface — always use the comma-ok form in production. **Type switches** dispatch on multiple concrete types — powerful when types are external; prefer polymorphism via interface methods when you control the types and adding a new one should be a compiler error.

</Recap>
