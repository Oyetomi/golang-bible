<HeroCard label="Part 2 · Chapter 10" title="Performance Engineering">

The cinema's busiest endpoint is the seat map: every open browser tab asks for it every second, and in chapter 9 one laptop served about 54,000 of them a second. This chapter makes it faster, and uses it to learn every performance tool Go has, in the order you'd actually reach for them.

The rule the whole chapter follows: **measure, change one thing, measure again.** Several things that "should" help didn't, and you'll see those numbers too.

Seven stops. If you get lost, come back here:

1. **pprof.** Where does the time go, and where do the allocations come from?
2. **Benchmarking.** A benchmark of the real handler, and benchstat to tell a real change from noise.
3. **Escape analysis and allocations.** What the compiler put on the heap, why, and the change that removed 41 of 54 allocations.
4. **GC tuning.** `GOGC` and `GOMEMLIMIT` against the same load: collections, CPU, memory, throughput.
5. **Mechanical sympathy.** A cache line is 128 bytes on this machine, and eight "independent" counters were 20× slower because of it.
6. **The execution tracer.** Seeing goroutines wait, and why removing a wait didn't make the server faster.
7. **Profile-guided optimization.** Feeding a production profile back to the compiler, and what it bought.

The code under test is chapter 8's seat map: `GET /movies/inception/seats` asks the store for all 40 seats and encodes them as JSON. Rather than profile the whole server (where 76% is the network), benchmark the handler through the real mux and store, with no network:

```go noverify
package main

import (
	"context"
	"net/http"
	"net/http/httptest"
	"testing"
	"time"

	"cinema/booking"
)

// BenchmarkSeatMap measures one GET /movies/inception/seats through the real
// mux and store: build the seat list, encode it as JSON, write it.
func BenchmarkSeatMap(b *testing.B) {
	store := booking.NewMemoryStore()
	for _, s := range []string{"A7", "B3", "C4", "D1", "E8"} {
		store.Hold(context.Background(), "inception", s, "alice", time.Hour)
	}
	mux := newMux(&api{store: store, hold: time.Minute})
	req := httptest.NewRequest("GET", "/movies/inception/seats", nil)
	b.ReportAllocs()
	for b.Loop() {
		w := httptest.NewRecorder()
		mux.ServeHTTP(w, req)
		if w.Code != http.StatusOK {
			b.Fatal(w.Code)
		}
	}
}
```

`b.Loop()` (Go 1.24) runs the body as many times as needed for a stable measurement, and keeps the compiler from optimizing the work away. `b.ReportAllocs()` adds bytes and allocations per operation.

How to read them:

- **flat** is time (or allocations) in the function itself; **cum** includes everything it called. `SeatIDs` has little flat CPU but 10% cumulative: the cost is in what it calls.
- **The CPU profile of a benchmark includes the runtime's background work.** `kevent` and `madvise` are the scheduler waiting and the GC returning memory; they're noise for our question.
- **The allocation profile is clearer.** The biggest single allocator is `fmt.Sprintf` at 23.5%, and `SeatIDs` accounts for 28.5% cumulatively. `httptest.NewRecorder` and the header clones are the benchmark's own harness, not the server's work.

That points at one function: `SeatIDs` builds the same 40 strings, A1 to E8, on every request.

<Callout kind="warn" title="Profiles over HTTP are for your eyes only">

`net/http/pprof` (chapter 9) lets you take the same profiles from a running server: `go tool pprof http://127.0.0.1:6060/debug/pprof/profile?seconds=30`. Keep it on a localhost-only listener; a profile endpoint on the public port lets anyone burn your CPU.

</Callout>

<UnderTheHood title="How the CPU profiler samples">

When profiling starts, the runtime asks the OS for a timer signal (`SIGPROF`) about 100 times a second per thread using CPU (Go 1.18+ uses per-thread timers on Linux). The signal handler records the goroutine's current stack. A function's share of samples is its estimated share of CPU time, so short runs are noisy: 3 s at 100 Hz is only a few hundred samples per core. The allocation profile is sampled too: by default about one record per 512 KB allocated (`runtime.MemProfileRate`), scaled back up in the report, which is why its counts are estimates.

</UnderTheHood>

## Benchmarking

*Stop 2 of 7.*

### Step 1: one change

Seat names never change, so build them once, when the program starts:

```go noverify
// booking.go, lines 49–74
// seatIDs holds every hall's seat names, built once at startup: they never
// change, so there's no reason to format 40 strings on every request.
var seatIDs = func() map[string][]string {
	m := make(map[string][]string, len(Halls))
	for movie, h := range Halls {
		ids := make([]string, 0, h.Rows*h.Cols)
		for r := range h.Rows {
			for c := range h.Cols {
				ids = append(ids, fmt.Sprintf("%c%d", 'A'+r, c+1))
			}
		}
		m[movie] = ids
	}
	return m
}()

// SeatIDs lists a hall's seats in order: A1, A2, … B1, … The slice is
// shared: callers must not modify it.
func SeatIDs(movie string) ([]string, error) {
	ids, ok := seatIDs[movie]
	if !ok {
		return nil, ErrNoSeat
	}
	return ids, nil
}

```

`SeatIDs` now returns a shared slice, so the comment says callers mustn't modify it: that's the price of sharing, and it has to be written down.

### Step 2: benchstat, not eyeballs

Benchmark numbers wobble by several percent from run to run. `benchstat` (`go install golang.org/x/perf/cmd/benchstat@latest`) compares two sets of runs and says whether the difference is bigger than the noise:

```text
$ go test -run '^$' -bench SeatMap -count 6 ./cmd/cinema/ > before.txt   # old SeatIDs
$ go test -run '^$' -bench SeatMap -count 6 ./cmd/cinema/ > after1.txt   # precomputed
$ benchstat before.txt after1.txt
goos: darwin
goarch: arm64
pkg: cinema/cmd/cinema
cpu: Apple M1
          │ before.txt  │             after1.txt             │
          │   sec/op    │   sec/op     vs base               │
SeatMap-8   9.153µ ± 3%   6.843µ ± 7%  -25.24% (p=0.002 n=6)

          │  before.txt  │             after1.txt              │
          │     B/op     │     B/op      vs base               │
SeatMap-8   5.006Ki ± 0%   4.237Ki ± 0%  -15.35% (p=0.002 n=6)

          │ before.txt │            after1.txt             │
          │ allocs/op  │ allocs/op   vs base               │
SeatMap-8   54.00 ± 0%   13.00 ± 0%  -75.93% (p=0.002 n=6)
```

**−25% time, −76% allocations.** Each column is a median with its spread (`± 3%`); `p=0.002` means a difference this large would almost never appear by chance if nothing had changed, and `n=6` is how many runs it used. When benchstat prints `~` instead of a percentage, the change is within the noise, and you'll see one in stop 3.

## Escape Analysis & Allocations

*Stop 3 of 7.*

### Step 1: ask the compiler

Every value lives either on a goroutine's **stack** (freed automatically when the function returns, no GC involved) or on the **heap** (freed only when the garbage collector proves nothing refers to it). The compiler decides which, by **escape analysis**, and will tell you:

```text
$ go build -gcflags=-m ./booking      # the original SeatIDs and Seats
booking/booking.go:55:13: make([]string, 0, h.Rows * h.Cols) escapes to heap
booking/booking.go:58:45: 65 + r escapes to heap
booking/booking.go:58:50: c + 1 escapes to heap
booking/booking.go:58:16: append escapes to heap
booking/memory.go:118:13: make([]Seat, len(ids)) escapes to heap
booking/memory.go:121:37: movie + "/" + id does not escape
```

- **`65 + r escapes to heap`**: `'A'+r` (65 is `'A'`) is passed to `Sprintf` as an `any`. Putting an integer in an interface usually means storing it somewhere the interface can point to, and since `Sprintf` might keep it, the compiler can't prove it doesn't: heap. That's two allocations per seat before `Sprintf` even builds its string.
- **`make([]Seat, …) escapes`**: the slice is returned to the caller, so it must outlive `Seats`' stack frame. That one is unavoidable without changing the API.
- **`movie + "/" + id does not escape`**: a short concatenation used only inside the function gets a buffer on the stack. It costs CPU (`concatstrings` appeared in the profile) but no allocation. Not every line that looks expensive is.

### Step 2: sync.Pool, where it didn't help

The next idea: the JSON encoder writes into a buffer; reuse buffers across requests with a `sync.Pool`:

```go
var bufs = sync.Pool{New: func() any { return new(bytes.Buffer) }}

func writeJSON(w http.ResponseWriter, status int, v any) {
	buf := bufs.Get().(*bytes.Buffer)
	buf.Reset()
	defer bufs.Put(buf)
	if err := json.NewEncoder(buf).Encode(v); err != nil {
		http.Error(w, "encoding failed", http.StatusInternalServerError)
		return
	}
	w.Header().Set("Content-Type", "application/json")
	w.WriteHeader(status)
	w.Write(buf.Bytes())
}
```

```text
$ benchstat after1.txt after2.txt

          │   sec/op    │   sec/op     vs base         │

SeatMap-8   13.00 ± 0%   13.00 ± 0%  ~ (p=1.000 n=6) ¹
```

Nothing. The original `json.NewEncoder(w).Encode(v)` already streamed into the response writer's own buffer, so there was no big buffer to save. The change came out again: more code, no measured benefit.

### Step 3: sync.Pool, where it's worth it

A pool pays off when the object is **expensive to create** and short-lived. The textbook case is compression: say the seat map is served gzipped. A `gzip.Writer` carries about a megabyte of compressor state.

```go noverify
// Compressing a seat-map response: a new gzip.Writer per response,
// or one reused from a sync.Pool.
package gzpool

import (
	"bytes"
	"compress/gzip"
	"encoding/json"
	"io"
	"sync"
	"testing"

	"cinema/booking"
)

var body = func() []byte {
	ids, _ := booking.SeatIDs("inception")
	seats := make([]booking.Seat, len(ids))
	for i, id := range ids {
		seats[i] = booking.Seat{ID: id, Status: booking.Free}
	}
	b, _ := json.Marshal(seats)
	return b
}()

func BenchmarkGzipNew(b *testing.B) {
	b.ReportAllocs()
	for b.Loop() {
		zw := gzip.NewWriter(io.Discard)
		zw.Write(body)
		zw.Close()
	}
}

var writers = sync.Pool{New: func() any { return gzip.NewWriter(nil) }}

func BenchmarkGzipPool(b *testing.B) {
	b.ReportAllocs()
	for b.Loop() {
		zw := writers.Get().(*gzip.Writer)
		zw.Reset(io.Discard)
		zw.Write(body)
		zw.Close()
		writers.Put(zw)
	}
}

func TestSameOutput(t *testing.T) {
	var a, c bytes.Buffer
	zw := gzip.NewWriter(&a)
	zw.Write(body)
	zw.Close()
	zp := writers.Get().(*gzip.Writer)
	zp.Reset(&c)
	zp.Write(body)
	zp.Close()
	if !bytes.Equal(a.Bytes(), c.Bytes()) {
		t.Fatal("pooled writer produced different bytes")
	}
}
```

```text
$ go test -run '^$' -bench Gzip -count 6 ./gzpool
BenchmarkGzipNew-8    	   20078	     60014 ns/op	 1076000 B/op	      14 allocs/op
BenchmarkGzipPool-8   	  192762	      6233 ns/op	       5 B/op	       0 allocs/op
$ benchstat -col /name gz.txt
           │    sec/op    │
GzipNew-8    61.70µ ± 69%
GzipPool-8   6.291µ ±  1%
```

**10× faster, from 1 MB per response to nothing.** `Reset(w)` points a pooled writer at a new destination, and `TestSameOutput` checks the pooled writer produces byte-identical output. (The ±69% on the first line is the first run paying for page faults: 104 µs, then about 61 µs.)

<Define term="sync.Pool">
A cache of temporary objects that goroutines can take (`Get`) and give back (`Put`). The runtime may drop pooled objects during any garbage collection, so a pool is for reducing allocation of reusable scratch objects, never for state that must survive. Each P has its own local pool, so `Get` and `Put` are usually lock-free. Always reset an object after `Get`, before use.
</Define>

## GC Tuning

*Stop 4 of 7.*

### Step 1: what the collector does

Go's garbage collector finds live objects by following pointers from the roots (globals and every goroutine's stack) and frees the rest. It runs **concurrently** with your goroutines, pausing them only briefly at the start and end of each cycle (0.067 ms and 0.011 ms in chapter 9's trace).

Since Go 1.26 the default collector is **Green Tea**, which scans small objects page by page for better memory locality (it's still on by default in 1.27). You don't configure it; just know it when comparing GC numbers across versions.

### Step 2: the two knobs, measured

- **`GOGC`** (default 100): start the next collection when the heap has grown by this percentage over what was live after the last one. The minimum goal is 4 MB.
- **`GOMEMLIMIT`** (Go 1.19): a soft ceiling on the Go runtime's total memory. The collector runs harder as memory approaches it. With `GOGC=off`, collection happens *only* as memory approaches the limit.

The same server and load (`browse`, 32 clients, 4 s), `gctrace` on, two runs each:

| setting | collections in 4 s | GC CPU | RSS | seat maps / s |
|---|---|---|---|---|
| `GOGC=100` (default) | 543–594 | 3% | 23 MB | 65,000–71,000 |
| `GOGC=400` | 95–97 | 0% | 35 MB | 77,000–79,000 |
| `GOGC=off GOMEMLIMIT=64MiB` | 27–29 | 0% | 69 MB | 74,000–80,000 |

```text
GOGC=400:            gc 97 @4.123s 0%: …, 15->15->1 MB, 16 MB goal, …
GOGC=off, 64MiB:     gc 29 @3.972s 0%: …, 48->48->1 MB, 50 MB goal, …
```

The live heap is 1 MB in every case. What changes is how much garbage the collector lets accumulate before cleaning up: 4 MB, 16 MB, or ~50 MB. With such a small live heap, the goal comes from the minimum heap size, which scales with `GOGC`: 4 MB × 400/100 = 16 MB. With `GOGC=off`, the goal is set by the memory limit instead. Fewer collections cost less CPU and bought roughly 10% more throughput, paid for in memory: 23, 35 and 69 MB. (The throughput spread is wide because the load generator shares the laptop.)

<ConceptGrid cols={2}>
  <ConceptCard label="When to raise GOGC">Plenty of memory, GC showing up in CPU profiles or gctrace (this server: 3%). Doubling GOGC roughly halves collections.</ConceptCard>
  <ConceptCard label="When to set GOMEMLIMIT">In a container with a hard memory limit: set it a bit below the limit so the runtime collects harder instead of being OOM-killed. With GOGC=off it also means "use the memory, collect only near the limit".</ConceptCard>
  <Gotcha>GOMEMLIMIT is soft. If the live heap itself exceeds it, the GC runs constantly (the runtime caps GC at about 50% CPU to avoid a total death spiral) and you still run out. It is not a substitute for fixing a leak.</Gotcha>
</ConceptGrid>

## Mechanical Sympathy

*Stop 5 of 7.*

### Step 1: memory moves in cache lines

CPUs don't read single bytes from memory; they move fixed-size **cache lines** between memory and their private caches. When one core writes to a line, every other core's copy of that line is invalidated, and they must fetch it again. On this machine:

```text
$ sysctl hw.cachelinesize hw.l1dcachesize hw.l2cachesize
hw.cachelinesize: 128
hw.l1dcachesize: 65536
hw.l2cachesize: 4194304
```

128-byte lines on Apple Silicon (most x86 CPUs use 64).

### Step 2: eight counters that aren't shared, but are

Each delivery worker counts its own deliveries with an atomic add, so a metrics endpoint can read them any time. No worker ever touches another's counter:

```go noverify
// Eight workers each count their own deliveries with an atomic add, so a
// metrics endpoint can read the counters at any time. No counter is shared
// between workers, in the program. Is anything shared in the hardware?
package falseshare

import (
	"sync"
	"sync/atomic"
	"testing"
)

const workers = 8

type packed struct {
	n [workers]atomic.Int64 // 8 × 8 bytes: all in one 128-byte cache line
}

type padded struct {
	n [workers]struct {
		atomic.Int64
		_ [120]byte // 8 + 120 = 128 bytes: one cache line per counter
	}
}

func run(add func(w int)) {
	var wg sync.WaitGroup
	for w := range workers {
		wg.Go(func() {
			for range 1_000_000 {
				add(w)
			}
		})
	}
	wg.Wait()
}

func BenchmarkPacked(b *testing.B) {
	var c packed
	for b.Loop() {
		run(func(w int) { c.n[w].Add(1) })
	}
}

func BenchmarkPadded(b *testing.B) {
	var c padded
	for b.Loop() {
		run(func(w int) { c.n[w].Add(1) })
	}
}
```

```text
$ go test -run '^$' -bench . -count 6 ./falseshare
$ benchstat -col /name fs.txt
         │   sec/op    │
Packed-8   275.0m ± 1%
Padded-8   13.79m ± 4%
```

**20× slower** when the eight counters sit side by side. Eight `int64`s are 64 bytes: all in one 128-byte line. Every `Add` by one worker invalidates the line in the other seven cores' caches, so the line bounces between cores millions of times. That's **false sharing**: the program shares nothing, the hardware shares a cache line. Padding each counter to its own 128 bytes costs 1 KB and removes it.

## The Execution Tracer

*Stop 6 of 7.*

### Step 1: a trace of the live server

A CPU profile says where CPU time goes. The **execution tracer** records *events*: every goroutine start, block, wake-up, syscall, GC phase, and what each P was running, with timestamps. `net/http/pprof` serves it too:

```text
$ curl -o trace.out 'localhost:6060/debug/pprof/trace?seconds=2'    # while browse runs
$ ls -la trace.out
12820819 trace.out
$ go tool trace trace.out          # opens the viewer in a browser
```

The viewer shows a timeline per P and per goroutine. For a quick answer without it, `go tool trace -pprof=TYPE` turns the trace into a profile of where goroutines *waited*: `sync` (locks and channels), `net`, `syscall`, `sched` (runnable but not running):

```text
$ go tool trace -pprof=sync trace.out > sync.prof && go tool pprof -top -nodecount 6 sync.prof
      flat  flat%   sum%        cum   cum%
     5.05s 34.05% 34.05%      5.05s 34.05%  sync.(*Mutex).Lock
     3.29s 22.15% 56.19%      3.29s 22.15%  sync.(*Cond).Wait
     2.90s 19.57% 75.77%      2.90s 19.57%  runtime.chanrecv1
        2s 13.48% 89.25%         2s 13.48%  runtime.selectgo
     1.58s 10.63% 99.88%      1.58s 10.63%  runtime.gcMarkDone
         0     0% 99.88%      5.06s 34.11%  cinema/booking.(*MemoryStore).Seats
```

Across all goroutines, **5.05 s** of waiting in `Mutex.Lock`, all from `MemoryStore.Seats`: 32 clients reading the seat map, queueing on the store's one mutex, although reads never conflict.

### Step 2: removing the wait, and measuring what it bought

Seats only reads, so give it a read lock: `sync.RWMutex`, with `RLock` in `Seats`. The trace confirms the wait is gone:

```text
     3.21s 27.49% 56.98%      3.21s 27.49%  sync.(*Cond).Wait

        2s 17.13% 99.17%         2s 17.13%  runtime.selectgo
```

**No difference beyond the noise.** The waiting was real, but it wasn't the bottleneck: the server is CPU-bound on socket syscalls (chapter 9's profile), so while some goroutines waited for the mutex, others used every CPU. <Callout kind="note" title="This is not distributed tracing">

</Callout>

<UnderTheHood title="What the tracer records">

Since Go 1.21 the tracer is cheap enough for production use (a few percent overhead): each P writes events to its own buffer, with timestamps from the CPU's counter and stacks recorded on demand. </UnderTheHood>

## Profile-Guided Optimization

*Stop 7 of 7.*

### Step 1: feed a real profile to the compiler

The compiler decides what to inline and how to lay out code without knowing which paths are hot. **PGO** (Go 1.21) gives it a CPU profile from real traffic: it inlines hot functions more aggressively, and turns hot interface calls into direct calls when one concrete type dominates. The loop:

1. Collect a CPU profile from production (or a realistic load).
2. Save it as `default.pgo` in the main package's directory.
3. Build normally: `go build` uses `-pgo=auto`, which picks up `default.pgo`.

```text
$ go build -o cinema ./cmd/cinema && ./cinema -store locked &
$ ./browse -clients 32 -for 12s &
$ curl -o cmd/cinema/default.pgo 'localhost:6060/debug/pprof/profile?seconds=10'
$ ls -la cmd/cinema/default.pgo
23743 cmd/cinema/default.pgo
```

### Step 2: what it bought

```text
$ go test -run '^$' -bench SeatMap -count 10 -pgo=off  ./cmd/cinema/ > pgo-off.txt
$ go test -run '^$' -bench SeatMap -count 10 -pgo=auto ./cmd/cinema/ > pgo-on.txt
$ benchstat pgo-off.txt pgo-on.txt
          │ pgo-off.txt │             pgo-on.txt             │
          │   sec/op    │   sec/op     vs base               │
SeatMap-8   6.742µ ± 1%   6.609µ ± 2%  -1.97% (p=0.004 n=10)
$ go build -pgo=off -o c-off ./cmd/cinema && go build -pgo=auto -o c-on ./cmd/cinema
$ ls -la c-off c-on
12894322 c-off
12943810 c-on
$ go version -m c-on | grep pgo
	build	-pgo=…/cmd/cinema/default.pgo
```

**−2%**, statistically real, for a 49 KB (0.4%) bigger binary and no code change. That's at the low end of the Go team's reported 2–14%, and the profile explains why: this service's hot path is socket syscalls and the standard library's JSON encoder, not inlinable code of ours. PGO does most for CPU-bound code with hot interface calls and small hot functions. The build records which profile it used (`go version -m`), so a binary can always be traced back to its profile.

<ConceptGrid cols={2}>
  <ConceptCard label="Commit default.pgo">It's a build input, like go.sum. Refresh it from production every release or two; a stale profile still helps, it just helps less.</ConceptCard>
  <ConceptCard label="Measure it like any change">benchstat on a real benchmark, or throughput under realistic load. −2% here; your service may get more or less.</ConceptCard>
</ConceptGrid>

The cinema server runs in a container with a 256 MiB memory limit. Choose `GOGC` and `GOMEMLIMIT`, and explain what happens if a bug makes the live heap grow to 300 MB.

<Solution>

`GOMEMLIMIT=230MiB` (about 90% of the container limit, leaving room for non-Go memory like thread stacks and the binary) with the default `GOGC=100`, or `GOGC=off` if you want to use the memory freely and collect only near the limit: measured above, that cut collections from ~570 to ~28 per 4 s. This is stop 3's change in miniature, measured the same way. With the fix, `AllocsPerRun` may even report 0: when the call is inlined into a caller that doesn't keep the result, the compiler can put the buffer on the stack.

- **Profile first.** The allocation profile pointed at `fmt.Sprintf` in `SeatIDs` (23.5% of objects), not at anything a guess would have picked. In a benchmark's CPU profile, runtime background work (`kevent`, `madvise`) is noise.
- **Benchmark and compare with benchstat.** Precomputing seat names: −25% time, −76% allocations (54 → 13), p=0.002. `~` means noise; the pooled JSON buffer got `~` and was removed.
- **Escape analysis** (`-gcflags=-m`) explains allocations: boxed `Sprintf` arguments and returned slices escape; a short local concatenation doesn't. `sync.Pool` pays when creation is expensive: pooled gzip writers were 10× faster (61.7 µs → 6.3 µs, 1 MB → 0).
- **GC knobs trade memory for CPU.** `GOGC=400` cut collections ~6× (23 → 35 MB RSS); `GOGC=off` with `GOMEMLIMIT=64MiB` ~20× (69 MB); both gained about 10% throughput. `GOMEMLIMIT` is soft.
- **Hardware matters.** A 128-byte cache line made eight "independent" atomic counters 20× slower until padded.
- **Trace, then measure the outcome.** The tracer found 5 s of mutex waiting; removing it didn't change throughput, because the CPU was never idle. **PGO** gave −2% for free: the ceiling is set by what's hot.
