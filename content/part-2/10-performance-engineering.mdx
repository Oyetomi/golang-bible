## pprof

Let me set the scene: it's a Monday morning and your on-call page fires. Meridian's ledger-report endpoint — the one that aggregates transaction history per account — is timing out at the 99th percentile. Your CEO is watching the dashboard. You have twenty minutes.

The amateur opens their editor and starts guessing. You open a profiler.

**On the job:** You hit the profiler the moment a latency SLO breach or an unexplained throughput drop lands in your inbox. Skipping it and editing code by instinct means fixing the wrong thing — and the page fires again next week.

### What pprof gives you

`pprof` is Go's built-in profiling framework. It collects four kinds of profiles, and you need to know all four because they point at different problems:

<ConceptGrid cols={2}>
  <ConceptCard label="CPU profile">Where is the CPU spending its time? Samples the current goroutine's call stack every 10ms (by default). Points you to hot functions. The first profile to reach for when things are *slow*.</ConceptCard>
  <ConceptCard label="Heap profile">What is live on the heap? Also called the allocation profile — shows inuse objects and cumulative allocation sites. Points you to memory hogs and GC pressure.</ConceptCard>
  <ConceptCard label="Block profile">Where are goroutines blocking on synchronization (channels, mutexes, `select`)? Essential for diagnosing contention. Disabled by default — you must call `runtime.SetBlockProfileRate`.</ConceptCard>
  <ConceptCard label="Mutex profile">Which mutexes are being contested? Finer-grained than block for `sync.Mutex`/`sync.RWMutex` contention. Also disabled by default — call `runtime.SetMutexProfileFraction`.</ConceptCard>
  <Gotcha>The goroutine profile (`/debug/pprof/goroutine`) shows a stack trace for every live goroutine. It's not a performance profile — it's a leak detector. If you see 50,000 goroutines where you expect 20, you have a leak, not a speed problem.</Gotcha>
</ConceptGrid>

### Three ways to collect a profile

**1. In a test or benchmark (the easiest)**

```go
go test -bench=. -cpuprofile=cpu.out -memprofile=mem.out ./...
```

This is the cleanest path: `go test` drives the workload, dumps the profiles, and you inspect them offline. We'll use this form for most of the chapter.

**2. In a long-running server with `net/http/pprof`**

Drop one import and the endpoints appear on your HTTP mux, ready to sample whenever you need them — no restart required:

```go
package main

import (
	"net/http"
	_ "net/http/pprof" // side-effect import registers handlers on http.DefaultServeMux
)

func main() {
	// Your real mux...
	http.ListenAndServe(":6060", nil)
}
```

Then from a terminal:

```
go tool pprof http://localhost:6060/debug/pprof/profile?seconds=30
```

This connects, collects 30 seconds of CPU samples, and drops you into an interactive REPL.

<Callout kind="warn" title="Never expose pprof endpoints publicly">

`net/http/pprof` must be gated behind auth or bound only to a private interface. It lets anyone see your call stack, your heap layout, and your goroutine count — that is, everything an attacker needs. Expose it on a separate internal port (e.g. `:6060`) or protect it with `http.BasicAuth`.

</Callout>

**3. Programmatically with `runtime/pprof`**

For precise control — profile only the hot section of a request, not the entire server lifetime:

```go
package main

import (
	"os"
	"runtime/pprof"
)

func profiledSection() error {
	f, err := os.Create("cpu.out")
	if err != nil {
		return err
	}
	defer f.Close()

	if err := pprof.StartCPUProfile(f); err != nil {
		return err
	}
	defer pprof.StopCPUProfile()

	// The work you want to profile.
	generateLedgerReport()
	return nil
}
```

### Reading a profile: top, list, web

Once you have a `.out` file, `go tool pprof` is your Swiss Army knife:

```
$ go tool pprof cpu.out
(pprof) top10          # top 10 functions by self CPU time
(pprof) top10 -cum     # top 10 by cumulative (self + callees)
(pprof) list generateLedgerReport  # annotate source with per-line counts
(pprof) web            # open a call graph in the browser (needs graphviz)
```

The two most important columns in `top` output:

- **`flat`** — CPU time spent *inside* this function, not in its callees. A high `flat` means *this function* is the problem.
- **`cum`** (cumulative) — time spent in this function *plus everything it calls*. A high `cum` with low `flat` means the function is just a pass-through into something deeper.

### Reading a flame graph

`go tool pprof -http=:8080 cpu.out` opens a web UI with a **flame graph** — the most information-dense view in profiling. As of Go 1.26, the flame graph is the default view when you open the pprof web UI (previously it opened a call-graph).

<UnderTheHood title="How the CPU profiler actually works (Go 1.26)">

The CPU profiler works via **SIGPROF signals**. When you call `pprof.StartCPUProfile`, the runtime installs a signal handler and asks the OS to deliver `SIGPROF` at 100 Hz (every 10ms). When the signal fires, the runtime captures the current goroutine's call stack — a snapshot of the program counter chain from the leaf frame up to the root. These stack snapshots are counted and accumulated in a data structure. `StopCPUProfile` flushes it to the writer in pprof binary format.

Because the profiler is **sample-based**, it introduces statistical error: a function that takes 8ms but runs rarely might never be sampled. The practical effect is that functions faster than ~1ms are invisible at 100 Hz — they never live long enough to be caught. For those you need **microbenchmarks**, not CPU profiles.

The heap profiler is different: it instruments `mallocgc` directly, recording a stack sample every `N` bytes allocated (default: once per 512 KB, controlled by `runtime.MemProfileRate`). This makes the heap profile accurate even for fast, small allocations — it sees *every* allocation site, just subsampled.

Both profiles write to the **pprof binary format**, a simple protocol buffer containing (count, stack-trace) pairs — which is why `go tool pprof` can read profiles from different architectures and machines.

</UnderTheHood>

## Benchmarking

Profiling tells you where the fire is. Benchmarks tell you whether your fix actually put it out — and by how much. They're your before/after measurement instrument.

**On the job:** Always write a benchmark before you optimize and run it again after. Without a before/after number you cannot know whether your change helped, hurt, or did nothing. Gut feel is not evidence.

### `testing.B` and the benchmark loop

A Go benchmark is a test function named `BenchmarkXxx` that accepts `*testing.B`. The framework auto-tunes the iteration count so the total measured time is statistically meaningful.

**Go 1.24+: prefer `b.Loop()` over `for range b.N`.**  
Go 1.24 introduced `testing.B.Loop()`, which avoids the footgun of forgetting `b.ResetTimer()` in common patterns. Go 1.26 removed the inlining barrier inside `b.Loop` bodies, so it is suitable for micro-benchmarks. When you write `for b.Loop()`, the framework handles timer resets around the loop automatically. Use it for new benchmarks:

```go
func BenchmarkLedgerReport(b *testing.B) {
	rows := generateTestRows(1000) // setup outside the measured loop
	for b.Loop() {                 // Go 1.24+: preferred over for range b.N
		_ = summarizeRows(rows)
	}
}
```

If you're on an older toolchain or need compatibility, the classic form still works:

```go
func BenchmarkLedgerReportCompat(b *testing.B) {
	rows := generateTestRows(1000)
	b.ResetTimer()       // required with for range b.N
	for range b.N {
		_ = summarizeRows(rows)
	}
}
```

Run it:

```
$ go test -bench=BenchmarkLedgerReport -benchmem ./...
BenchmarkLedgerReport-8   12304   97.3 µs/op   45312 B/op   312 allocs/op
```

Let's read that output:

  <ConceptCard label="12304">Number of iterations `b.N` ran. The framework chose this so the total run time is about 1 second — enough for a stable measurement.</ConceptCard>
  <ConceptCard label="97.3 µs/op">Time per operation — what you're optimizing. This is wall-clock time divided by `b.N`.</ConceptCard>
  <ConceptCard label="45312 B/op">Bytes allocated from the heap per operation. Enabled by `-benchmem` or `b.ReportAllocs()`. Your target for this chapter.</ConceptCard>

  <Gotcha>Never compare benchmarks run on different machines, under different load, or at different `GOMAXPROCS`. The only trustworthy comparison is two runs on the same machine back to back, analyzed with `benchstat`.</Gotcha>

### `b.ReportAllocs()` — make the allocations visible

Call `b.ReportAllocs()` at the top of any benchmark to force allocation reporting without needing `-benchmem` on the command line. Make it a habit: allocation regressions are invisible otherwise.

### The optimize-away pitfall — always use a sink

The Go compiler is smart enough to eliminate a computation whose result is never used. A benchmark that computes a value and throws it away may be benchmarking *nothing*. The fix: assign results to a package-level variable ("the sink"):

The sink pattern is idiomatic and costs nothing at runtime — the compiler can't optimize across package boundaries.

### `benchstat` — reading before/after with confidence

A single benchmark run has noise. `benchstat` aggregates multiple runs and computes statistical significance:

```
$ go test -bench=BenchmarkLedgerReport -benchmem -count=10 . > before.txt
# make your optimization
$ go test -bench=BenchmarkLedgerReport -benchmem -count=10 . > after.txt
$ benchstat before.txt after.txt
```

Output:

```
name              old time/op    new time/op    delta
LedgerReport-8    97.3µs ± 2%   14.1µs ± 1%   -85.51%  (p=0.000 n=10+10)
```

The `±` is the variance, `p=0.000` means the improvement is statistically significant, and `-85.51%` is real. That's what a measurement-driven optimization looks like.

```go
package main

import (
	"fmt"
	"strings"
)

// ledgerRow mimics one row of a report query result.
type ledgerRow struct {
	AccountID string
	AmountCents int64
	Description string
}

// naiveSummarize builds a report string the slow way — lots of small allocs.
func naiveSummarize(rows []ledgerRow) string {
	var out string
	for _, r := range rows {
		out += fmt.Sprintf("%s: %d\n", r.Description, r.AmountCents)
	}
	return out
}

// fastSummarize uses a strings.Builder to avoid O(n²) string concatenation.
func fastSummarize(rows []ledgerRow) string {
	var b strings.Builder
	b.Grow(len(rows) * 30) // preallocate a reasonable estimate
	for _, r := range rows {
		fmt.Fprintf(&b, "%s: %d\n", r.Description, r.AmountCents)
	}
	return b.String()
}

func main() {
	rows := make([]ledgerRow, 1000)
	for i := range rows {
		rows[i] = ledgerRow{
			AccountID:   fmt.Sprintf("acc-%d", i),
			AmountCents: int64(i * 100),
			Description: "transfer",
		}
	}

	naive := naiveSummarize(rows)
	fast := fastSummarize(rows)

	fmt.Printf("naive output length:  %d bytes\n", len(naive))
	fmt.Printf("fast  output length:  %d bytes\n", len(fast))
	fmt.Println("outputs match:", naive == fast)
}
```

## Escape Analysis & Allocations

Here's the thing that separates a senior Go engineer from someone who just writes Go: **knowing where your memory lives**.

**On the job:** Allocation pressure is the most common source of GC CPU overhead in Go services. Every extra allocation in a hot path means more GC work, more STW pause risk, and more latency tail. Fix the allocation count before reaching for `GOGC` tuning.

### Stack vs. heap — the two places your data can be

Every value in a Go program lives on the **stack** or the **heap**:

- **Stack**: memory owned by a single goroutine. Allocation is extremely cheap, often just a pointer bump. Freed automatically when the function returns. Goroutine stacks start small (about 2 KB in current Go implementations) and grow dynamically up to runtime limits. *This is a simplified model; the runtime's actual stack management is more nuanced.*
- **Heap**: shared memory managed by the GC. Allocation goes through `mallocgc`, which is lockless via per-P memory caches (mcache/mcentral) but still heavier than a stack bump. Freed asynchronously by the garbage collector — which costs CPU.

Stack allocation is orders of magnitude cheaper than heap allocation. The goal of escape analysis is to keep as many values on the stack as possible.

### `go build -gcflags=-m` — reading escape analysis output

Pass `-gcflags=-m` (or `-gcflags="-m -m"` for more detail) to see the compiler's escape decisions:

```
$ go build -gcflags=-m ./...
./report.go:14:6: moved to heap: report
./report.go:23:12: new(LedgerRow) escapes to heap
./report.go:31:18: []byte literal does not escape
```

- **"moved to heap"** — the compiler decided this value must outlive its stack frame, so it heap-allocates it.
- **"does not escape"** — stays on the stack. This is what you want.
- **"escapes to heap"** — same as "moved to heap" but for explicit allocations.

### Why values escape

Values escape to the heap when the compiler cannot prove they're safe to free when the function returns. Common triggers:

<ConceptGrid cols={2}>
  <ConceptCard label="Returning a pointer">If you return `&thing`, `thing` must outlive the function — it escapes. Return the value instead when you can.</ConceptCard>
  <ConceptCard label="Storing in an interface">Assigning a concrete value to an interface can force a heap allocation when the compiler cannot keep the boxed value on the stack. The smaller the value, the more this hurts proportionally.</ConceptCard>
  <ConceptCard label="Closure over a variable">A goroutine closure that captures a variable forces that variable to the heap so both the goroutine and the enclosing function can see it.</ConceptCard>
  <ConceptCard label="Large values">Large local values are more likely to be moved to the heap when the compiler decides stack allocation is not a good fit. Keep large reusable buffers behind pointers or in `sync.Pool`.</ConceptCard>
  <Gotcha>Passing a value to `fmt.Println` or any function that takes `any` (interface) will escape that value to the heap. In a hot inner loop, this is death by a thousand allocations. Use `slog` with typed fields, not `fmt.Printf`, in production hot paths.</Gotcha>
</ConceptGrid>

### Reducing allocations: slice and map preallocation

The most common source of unnecessary heap pressure is **growing containers from nothing**. Every time `append` outgrows a slice's backing array, it allocates a new one and copies the old contents. The fix is trivially cheap: tell Go the size upfront.

<BeforeAfter
  badLabel="Many reallocations and copies"
  goodLabel="One allocation, right-sized"
  bad={`rows := []LedgerRow{}
for _, r := range dbResult {
  rows = append(rows, r)
}`}
  good={`rows := make([]LedgerRow, 0, len(dbResult))
for _, r := range dbResult {
  rows = append(rows, r)
}`}
/>

Same rule for maps — if you know the approximate size, pass it to `make`:

```go
seen := make(map[string]struct{}, len(accountIDs)) // one backing array, not 8 doublings
```

### `sync.Pool` — reusing expensive scratch buffers

`sync.Pool` is a per-goroutine (actually per-P) cache of reusable objects. It's the right tool when you're allocating and discarding the same types of short-lived objects in a hot path — think byte buffers, encoder objects, or temporary slices.

```go
var bufPool = sync.Pool{
	New: func() any {
		// called only when the pool is empty
		b := make([]byte, 0, 64*1024) // 64 KB scratch buffer
		return &b
	},
}

func generateLedgerReport(rows []LedgerRow) []byte {
	bp := bufPool.Get().(*[]byte)
	buf := (*bp)[:0] // reset length, keep capacity

	for _, r := range rows {
		buf = append(buf, r.Description...)
		buf = append(buf, '\n')
	}

	result := append([]byte(nil), buf...) // copy out before returning

	*bp = buf
	bufPool.Put(bp) // return to pool for next caller
	return result
}
```

<UnderTheHood title="How sync.Pool avoids lock contention (Go 1.26)">

*This is a simplified model of the pool internals; the actual implementation has additional complexity around victim caches and lock-free fast paths.*

`sync.Pool` maintains **one local pool per P** (logical processor in the GMP model — covered in depth in the "The Go Scheduler (GMP), In Depth" chapter). A `Get` call first checks the local P's pool: no mutex needed, zero contention. Only if the local pool is empty does it fall through to the global shared pool (which does need a lock) and then calls `New`.

This design means that in a server handling many concurrent requests, each goroutine typically gets a buffer from its own P's pool without ever contending with others — O(1) effectively lock-free in the common case.

The sharp edge: **the GC clears all pool contents at every GC cycle** (during the STW setup phase). If your pool holds a 64 MB buffer and the GC fires, that buffer is gone — the next `Get` calls `New` and re-allocates. This is intentional: the pool is not a cache for permanent objects. It's a mechanism for *amortizing* transient allocations. Don't store objects in a pool that must survive GC cycles.

As of Go 1.26, `sync.Pool` is one of the cheapest inter-goroutine object-sharing mechanisms available. A hand-rolled channel-based pool is slower and more complex. Prefer `sync.Pool`.

</UnderTheHood>

## GC Tuning

Now let's talk about the engine running underneath everything: Go's garbage collector.

**On the job:** GC tuning is a last resort, not a first instinct. First cut allocations (previous section). Only reach for `GOGC`/`GOMEMLIMIT` when profiling confirms GC CPU is a meaningful fraction of your service's budget.

### Tri-color mark-sweep — the 90-second version

Go's GC uses a **concurrent tri-color mark-sweep** algorithm. You don't need to memorize the algorithm — you need to understand the two costs it imposes, because that's what you're tuning:

1. **CPU cost**: the GC runs concurrently with your goroutines, using CPU cycles for marking and scanning.
2. **Stop-the-world (STW) pauses**: short STW phases still exist around a GC cycle. Go is designed to keep these pauses small, but the exact numbers are workload-dependent. Measure them with `gctrace`, `runtime/metrics`, pprof, or the execution tracer.

### `GOGC` — the headroom knob

`GOGC` controls when the GC triggers. Its value is a **percentage**: the next GC fires when the heap has grown by `GOGC%` since the last collection.

- Default: `GOGC=100` — GC fires when live heap doubles.
- `GOGC=200` — GC fires when live heap triples (less frequent, more memory used).
- `GOGC=off` — GC disabled (dangerous; only for benchmarks or batch jobs with bounded memory).

The math: if your live heap after last GC is 100 MB, and `GOGC=100`, the next GC fires at ~200 MB. Setting `GOGC=200` lets it grow to ~300 MB before the collector fires — less CPU spent on GC, but more RSS used.

```go
// Set programmatically (rarely needed; prefer the env var)
import "runtime/debug"

debug.SetGCPercent(200) // equivalent to GOGC=200
```

### `GOMEMLIMIT` — the hard ceiling (Go 1.19+)

`GOGC` is a relative knob. In a container or a Kubernetes pod where you have a hard memory limit, you need an absolute ceiling. That's `GOMEMLIMIT`:

```
GOMEMLIMIT=512MiB ./ledger-service
```

With `GOMEMLIMIT` set, the GC will aggressively collect to stay *under* the limit, even if `GOGC` says it's not time yet. Think of it as: "`GOGC` controls the comfortable operating zone; `GOMEMLIMIT` prevents OOM kills."

In practice: set `GOMEMLIMIT` to ~90% of your container's memory limit, so the OOM killer doesn't fire before the GC gets a chance to clean up.

```go
import "runtime/debug"

// Set in code (prefer the env var in production)
debug.SetMemoryLimit(512 << 20) // 512 MB
```

<UnderTheHood title="Tri-color mark-sweep and write barriers (Go 1.26)">

*This is a simplified model of GC internals. Go 1.26 ships the Green Tea GC, which changes some of the internal phases described below — treat these as a conceptual guide, not a precise specification.*

Go's GC runs **mostly concurrently** with your goroutines. Here's the simplified model (baseline Go 1.26):

1. **STW start**: all goroutines pause briefly so the GC can establish a consistent view of the heap roots (stacks, global variables, runtime structures).
2. **Concurrent marking**: GC goroutines (running on a fraction of your P's) trace the object graph. They color objects: white (not yet seen), grey (seen but children not scanned), black (fully scanned).
3. **Write barrier active**: while marking runs concurrently, your program keeps mutating pointers. The **tri-color invariant** (no black object may point directly to a white object) must hold. The write barrier records pointer writes so the GC doesn't miss a newly-created live object. You may see this cost in CPU profiles as `runtime.gcWriteBarrier`. Pointer-heavy layouts (linked lists, `[]*T` slices) amplify this cost; flat `[]T` slices largely avoid it.
4. **STW finish**: goroutines pause again so the GC can drain the final grey queue and confirm marking is complete.
5. **Concurrent sweep**: dead (white) objects are swept asynchronously. Memory is returned to span freelists; spans are returned to the OS lazily.

The GC has a **pacer** that models your allocation rate and schedules cycles to meet the `GOGC` target. In practice, verify pause time with your own workload instead of relying on a universal number.

## Mechanical Sympathy

This is where it gets beautiful. You've cut allocations. You've tuned the GC. Now we go one level deeper — to the hardware your Go binary runs on.

**On the job:** False sharing is a common culprit in concurrent Go services where throughput fails to scale with `GOMAXPROCS`. The race detector stays silent — it's not a data race — but the hardware contention is just as real. Profile throughput under different `GOMAXPROCS` values; if adding cores helps less than expected, false sharing is a prime suspect.

### CPU caches and cache lines

Your CPU has multiple levels of cache (L1, L2, L3). L1 is tiny (~32 KB) and fast (~1 ns). DRAM is large and slow (~100 ns, a 100× difference). The CPU fetches data from RAM in **cache lines** — fixed 64-byte chunks on every modern x86 and ARM64 processor. When the CPU reads one byte, it loads the entire 64-byte line into cache. This has two profound consequences:

**1. Contiguous data is fast.**  
If your data is laid out as a flat slice of structs, the CPU prefetches the next cache line speculatively — you get near-zero memory latency after the first access. If your data is a slice of *pointers to* structs, each access dereferences the pointer to an arbitrary location in RAM — a **cache miss** every time. This is why the "Data Semantics & Data-Oriented Design" chapter matters so much: it pays off right here.

**2. False sharing is a goroutine performance trap.**  
If two goroutines running on separate CPU cores both read and write variables that live in the **same 64-byte cache line**, they fight over that cache line. Core A writes → invalidates Core B's copy → Core B reloads from L2/L3 → latency spike. The variable writes don't overlap, so there's no data race — the race detector stays silent. But the cache thrashing is very real, and it can cost 40× throughput.

### Data layout for the hardware

The payoff of the "Data Semantics & Data-Oriented Design" chapter is right here. If you designed your structs with access patterns in mind — keeping hot fields together, using flat `[]T` slices instead of `[]*T` — the hardware prefetcher can predict your access pattern and pre-load cache lines before you need them.

A practical rule: **if you iterate over a slice of structs touching only some fields, consider splitting the struct into two slices** (one per field group). This is the "structure of arrays" (SoA) layout, and it's dramatically better for cache utilization in data-heavy loops like Meridian's ledger aggregation.

## The Execution Tracer

`pprof` tells you *what* is slow. The execution tracer tells you *why* by recording a precise event log of everything the runtime does — goroutine scheduling, GC pauses, syscalls, network I/O — over time.

**On the job:** Reach for the execution tracer when `pprof` shows healthy CPU utilization but your latency p99 is still high. Scheduling stalls, GC interference, and goroutine pile-ups are invisible to the CPU profiler but obvious in a trace.

### `runtime/trace` — collecting a trace

```go
package main

import (
	"os"
	"runtime/trace"

func main() {
	f, _ := os.Create("trace.out")
	defer f.Close()

	trace.Start(f)
	defer trace.Stop()

	// your workload here
	runLedgerBatch()
}
```

```
$ go test -bench=. -trace=trace.out ./...
```

### Micro vs. macro framing

Before we close, the framing that makes you an actual performance engineer and not just someone who knows the tools:

**Microbenchmarks** (`testing.B`) measure a single function in isolation. They're excellent for validating that a specific change — preallocation, using `sync.Pool`, removing an allocation — actually helped. They're terrible for measuring end-to-end latency, because they don't include the actual workload mix, concurrency, or memory pressure of production.

**Macro profiling** (`pprof` on a real server, execution traces from integration tests) tells you what actually matters in the full system. A function that's 50% of CPU time in a microbenchmark might be 2% of wall time in production because it's dwarfed by database I/O.

The workflow is: **macro profile first to find the hotspot → microbenchmark to measure the fix → macro profile again to confirm the win carried through**.

<UnderTheHood title="What the execution tracer actually records (Go 1.26)">

*The event names below are illustrative; the actual event schema is internal to the runtime and changes across versions. Treat this as a conceptual map.*

The execution tracer works by having the runtime emit **structured events** into an in-memory ring buffer at every significant transition:

- Goroutine lifecycle: start, stop, schedule, preempt, block, unblock
- GC events: cycle start/done, sweep phases, STW start/stop
- Heap: allocation and release events
- Network poller and syscall enter/exit

Each event is timestamped with the CPU's hardware counter (`RDTSC` on x86). The trace binary is compact — events are a few bytes each — but at high event rates (millions of goroutine switches per second) it can add measurable overhead (~5–10% CPU). Collect traces for short durations (1–30 seconds) under a realistic load sample, not continuously in production.

**Go 1.25: `runtime/trace.FlightRecorder` is now stable.** Introduced as a proposal in Go 1.22 and stabilized in Go 1.25, `FlightRecorder` runs a continuously-spinning, fixed-size ring buffer — always collecting trace data but keeping only the last N seconds in memory. When something goes wrong in production, you call `fr.WriteTo(w)` to capture the recent history, without the cost of writing a trace file at all times. This is the right tool for "always-on but cheap" production tracing on Meridian's ledger service.

```go
fr := trace.NewFlightRecorder()
fr.Start()
// ... at incident time:
f, _ := os.Create("incident.trace")
fr.WriteTo(f)
```

The `go tool trace` browser UI parses the binary and renders goroutines as colored rectangles on time axes: running (blue), runnable (green), blocked (red). A healthy server trace shows dense blue — goroutines running, not waiting.

</UnderTheHood>

## Profile-Guided Optimization

Everything in this chapter so far runs one loop: **you** measure, **you** read the profile, **you** change the code. Profile-guided optimization — PGO — closes a second loop most engineers never touch: the profile goes back into `go build`, and the **compiler** changes *its* decisions. Same source, faster binary. The machine does the work. That's how I like my machines.

**On the job:** PGO is the cheapest real win in Go performance. The Go team measured **2–7%** CPU reduction on representative benchmarks when it shipped in Go 1.21, and the devirtualization work in 1.22 pushed some dispatch-heavy workloads past 10%. The price is one committed file and a refresh habit. If your service already exposes `net/http/pprof` — and after the first section of this chapter, it does — you are one `curl` away from the input.

<Define term="Profile-guided optimization (PGO)">
**PGO** feeds a CPU profile from a real run back into the compiler, which uses the sample weights to optimize the paths your program *actually* takes — more aggressive inlining of hot functions, and devirtualization of hot interface calls. `go build` activates it automatically when a pprof file named `default.pgo` sits in the main package's directory. Stable since Go 1.21.
</Define>

### Why the compiler guesses without you

The compiler's static heuristics are tuned for the *average* of all Go programs, because at compile time that's all it can know. The inliner has a fixed cost budget per call site — small functions inline, anything past the budget stays a call. Interface method calls go through the itable indirection (the two-word interface header from the Idiomatic Go chapter) unless the compiler can statically prove the concrete type. Sane defaults — but your ledger service is not average. Production says most of its CPU lives in a handful of functions under `POST /transfers`: decode, validate, balance check. The compiler has no idea. The profile is how you tell it.

The history explains the design. Classic PGO — GCC, MSVC, LLVM — demanded an **instrumented build**: compile a special counting binary, run a synthetic benchmark against it, rebuild using the recorded counts. Two builds, plus a benchmark that has to stay representative of production forever. In practice the benchmark rotted, the second build annoyed everyone, and teams quietly turned the whole thing off. Google's AutoFDO work flipped the model: *sample the production binary you already run* with an ordinary profiler, and accept slightly fuzzier counts in exchange for data that is true by construction. Go adopted the AutoFDO shape wholesale — the input is a stock pprof CPU profile, the exact bytes `/debug/pprof/profile` already serves. No instrumented build, no synthetic benchmark. Your fleet *is* the benchmark.

### Feeding the compiler

```shell
# 1. Sample CPU during representative load — peak, not idle
curl -o cpu-1.pprof 'https://ledger-1:6060/debug/pprof/profile?seconds=30'
curl -o cpu-2.pprof 'https://ledger-2:6060/debug/pprof/profile?seconds=30'

# 2. Merge pods into one profile (sample weights add)
go tool pprof -proto cpu-1.pprof cpu-2.pprof > default.pgo

# 3. It lives next to package main, versioned like source
mv default.pgo cmd/ledger/
git add cmd/ledger/default.pgo

# 4. go build auto-detects it — no flag needed
go build ./cmd/ledger

# Audit what any binary was built with
go version -m ledger | grep -- -pgo
```

`-pgo=off` builds without it; `-pgo=path/to/profile.pprof` overrides the default. The filename convention is deliberate: the profile is a **build input**, so it belongs in version control, goes through code review, and is recorded in the binary's build metadata — the same provenance discipline as the `-ldflags` build stamping from the Building & Shipping chapter.

### What actually changes: the hot interface call

Here's the optimization PGO unlocks that you cannot cleanly write by hand — not without wrecking your interface-based design. Watch the call site:

<GoPlayground>

```go
package main

import "fmt"

// Validator is what the handler sees — an interface, so every call
// is indirect: load the itable, load the method pointer, jump.
type Validator interface {
	Validate(amountCents int64) error
}

type TransferValidator struct{ maxCents int64 }

func (v TransferValidator) Validate(amountCents int64) error {
	if amountCents <= 0 || amountCents > v.maxCents {
		return fmt.Errorf("amount %d out of range", amountCents)
	}
	return nil
}

func validateBatch(v Validator, amounts []int64) (ok int) {
	for _, a := range amounts {
		// The hot call. Statically, the compiler can't prove which
		// concrete type is behind v. A production profile can:
		// 99.8% of samples here hit TransferValidator.Validate.
		// PGO specializes this exact call site.
		if v.Validate(a) == nil {
			ok++
		}
	}
	return ok
}

func main() {
	amounts := []int64{4_999, -3, 12_000, 999_999_999}
	v := TransferValidator{maxCents: 500_000_00}
	fmt.Printf("%d of %d transfers pass validation\n",
		validateBatch(v, amounts), len(amounts))
}
```

</GoPlayground>

Statically, the compiler usually can't prove which concrete type hides behind `Validator` at that call site — the value crosses a function boundary and could be anything. So it emits indirect dispatch. Cheap, but it blocks **inlining**, and inlining is the gateway optimization: once a body is inlined, escape analysis, bounds-check elimination, and constant propagation all get to see through it.

With a profile showing one type dominating the site, the compiler emits a **guarded devirtualization**:

```go
// Conceptually, what the compiled hot path becomes:
if tv, ok := v.(TransferValidator); ok {
	err = tv.Validate(a) // direct call — now inlinable
} else {
	err = v.Validate(a) // rare path: normal interface dispatch
}
```

The fast path is one type-descriptor comparison, then a direct — now inlinable — call. The slow path still handles the other 0.2% correctly. Your interfaces stay clean; the binary gets concrete-call speed where it counts. This is the "PGO-guided devirtualization" the Idiomatic Go chapter promised when it showed you the itable.

<UnderTheHood title="What the compiler does with default.pgo (Go 1.26)">

*The thresholds below are internal tuning constants, not API — treat the numbers as illustrative.*

1. **Parse and weight.** The pprof file decodes into a weighted call graph: nodes are functions, edge weights are stack-sample counts. Built once per `go build`, consulted as every package compiles.
2. **Hot-callsite inlining (Go 1.21+).** Call edges in roughly the hottest few percent of cumulative weight get a raised inlining budget — a function too big to inline under the static rules inlines anyway *at hot call sites only*. Cold sites keep the default budget. That asymmetry is the point: the binary grows single-digit percent, not 2×.
3. **Devirtualization (Go 1.22+).** Interface-call sites with a dominant concrete type in the profile compile to the guarded direct call you saw above. The guard costs one comparison; a miss falls back to ordinary dispatch.
4. **Name-based matching.** Samples are keyed by symbol name. Rename or heavily reshape a function and its weight is silently orphaned — that call site just reverts to static heuristics. A stale, partial, or even corrupt-ish profile **never breaks a build**; the worst case is a slightly slower binary. That graceful-degradation contract is what makes committing `default.pgo` safe.
5. **Iterative stability.** Profiles collected from a PGO-built binary attribute inlined frames back to their source functions, so feeding `profile(build(profile))` around the loop doesn't oscillate or compound. You can run the loop forever, release after release.
6. **Cost.** Builds with a profile run more analysis — expect mid-single-digit-percent slower compiles. The runtime cost is zero; everything happens at compile time.

</UnderTheHood>

<Exercise n={1} title="Add pprof to a server" level="easy">

Write a minimal HTTP server that:
1. Has one handler `/report` that does some work (a loop summing 100,000 integers).
2. Exposes `net/http/pprof` endpoints on a **separate** listener at `:6060`.

<Solution>

```go
package main

import (
	"fmt"
	"net/http"
	_ "net/http/pprof"
)

func reportHandler(w http.ResponseWriter, r *http.Request) {
	var sum int64
	for i := range 100_000 {
		sum += int64(i)
	}
	fmt.Fprintf(w, "sum: %d\n", sum)
}

func main() {
	// Public mux — no pprof here.
	pub := http.NewServeMux()
	pub.HandleFunc("/report", reportHandler)

	// Internal mux — pprof registers on http.DefaultServeMux.
	// Run both concurrently.
	go func() {
		if err := http.ListenAndServe(":6060", nil); err != nil {
			panic(err)
		}
	}()

	if err := http.ListenAndServe(":8080", pub); err != nil {
		panic(err)
	}
}
```

Key insight: `_ "net/http/pprof"` registers handlers on `http.DefaultServeMux`. The public server uses an *explicit* `http.NewServeMux()` — so pprof is only reachable on the internal `:6060` listener. Never expose pprof publicly.

<Exercise n={3} title="Diagnose an escape with -gcflags=-m" level="medium">

Given this function:

```go
func newLedgerEntry(desc string, amount int64) *LedgerEntry {
	e := LedgerEntry{Description: desc, AmountCents: amount}
	return &e
}
```

Run `go build -gcflags=-m` and explain:
1. Why does `e` escape to the heap?
2. Rewrite the function to return a value instead of a pointer. Does the escape disappear?
3. When would returning a pointer still be the right design choice despite the allocation?

<Solution>

```go
package main

import "fmt"

type LedgerEntry struct {
	Description string
	AmountCents int64
}

// Returns value: e stays on the stack.
func newLedgerEntry(desc string, amount int64) LedgerEntry {
	return LedgerEntry{Description: desc, AmountCents: amount}
}

func main() {
	e := newLedgerEntry("transfer", 5000)
	fmt.Println(e.Description, e.AmountCents)
}
```

1. `&e` returns a pointer to a local variable. The compiler sees that `e` must outlive the function frame (the caller holds a reference), so it heap-allocates `e`.
2. Returning `LedgerEntry` directly: `e` is copied to the caller's frame — no heap allocation. `-gcflags=-m` will no longer report the escape.
3. Returning a pointer is still right when: (a) the struct is large enough that copying it is expensive and the pointer is passed widely; (b) the struct is intentionally mutable through the pointer (e.g. a `*sync.Mutex` embedded for a reason); (c) it implements an interface that requires a pointer receiver. Allocation isn't always wrong — it's only wrong when it's unnecessary and frequent.

</Solution>

</Exercise>

<Exercise n={4} title="Fix false sharing" level="medium">

A service tracks cache hit and miss counters. Two goroutines increment them concurrently. The current layout causes false sharing. Fix it:

```go
type CacheMetrics struct {
	Hits   int64
	Misses int64
}
```

Add padding so `Hits` and `Misses` each occupy their own 64-byte cache line. Write a test that increments both fields from separate goroutines 1,000,000 times each and asserts the final counts are correct.

<Solution>

```go
package cache_test

import (
	"sync"
	"sync/atomic"
	"testing"
)

const cacheLineSize = 64

type paddedInt64 struct {
	val int64
	_   [cacheLineSize - 8]byte
}

type CacheMetrics struct {
	Hits   paddedInt64
	Misses paddedInt64
}

func TestCacheMetrics(t *testing.T) {
	const n = 1_000_000
	var m CacheMetrics
	var wg sync.WaitGroup
	wg.Add(2)

	go func() {
		defer wg.Done()
		for range n {
			atomic.AddInt64(&m.Hits.val, 1)
		}
	}()
	go func() {
		defer wg.Done()
		for range n {
			atomic.AddInt64(&m.Misses.val, 1)
		}
	}()

	wg.Wait()

	if got := atomic.LoadInt64(&m.Hits.val); got != n {
		t.Errorf("Hits: want %d got %d", n, got)
	}
	if got := atomic.LoadInt64(&m.Misses.val); got != n {
		t.Errorf("Misses: want %d got %d", n, got)
	}
}
```

Each `paddedInt64` occupies exactly 64 bytes. `Hits.val` is at offset 0; `Misses.val` is at offset 64. Different cache lines, different cores, zero invalidation. The atomics are still needed for correctness — padding removes the false sharing, not the data race.

</Solution>

</Exercise>

<Recap>

You now own the full performance engineering stack:

- **pprof** gives you four profiles — CPU, heap, block, mutex — each pointing at a different class of problem. Collect them from tests, running servers (`net/http/pprof`), or precise sections (`runtime/pprof`). Read them with `top`, `list`, and flame graphs.
- **Benchmarks** (`testing.B`, `b.N`, `b.ReportAllocs`) are your before/after measurement instrument. Always use a **sink** variable to defeat dead-code elimination. Use `benchstat` over multiple runs for statistical confidence.
- **Escape analysis** (`go build -gcflags=-m`) shows stack vs. heap decisions. Values escape when their lifetime exceeds their function frame — returning pointers, storing in interfaces, goroutine closures. Slice and map **preallocation** and `sync.Pool` cut heap pressure.
- **GC tuning**: `GOGC` sets the relative headroom (default 100 = GC fires at 2× live heap). `GOMEMLIMIT` (Go 1.19+) sets the hard ceiling — always pair them in containers. Go's collector still has short STW phases and runs most tracing work concurrently.
- **Mechanical sympathy**: data lives in 64-byte **cache lines**. Contiguous flat slices are cache-friendly; pointer-chased linked structures are cache-hostile. **False sharing** between goroutines on the same cache line causes constant invalidation — fix with padding to 64-byte boundaries. The payoff of data-oriented design (Part 1, Chapter 3).
- **The execution tracer** (`runtime/trace`, `go tool trace`) records goroutine scheduling, GC pauses, and I/O events on a precise timeline — not to be confused with distributed tracing. Use it to find scheduler stalls and GC interference. The new flight recorder (Go 1.23+) keeps a ring buffer always ready.
- **PGO** (`default.pgo`, stable since Go 1.21): a merged production CPU profile committed next to `package main` makes `go build` raise inlining budgets on hot call sites and devirtualize hot interface calls — 2–7% CPU typical, zero source changes. Matching is by function name, so stale profiles degrade silently and never break the build. Refresh per release.
- The **micro vs. macro** discipline: profile the whole system first, benchmark the specific fix, then profile again to confirm the win carried through. Never optimize what the profiler hasn't pointed at.
