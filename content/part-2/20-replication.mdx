<HeroCard label="Part 2 · Chapter 20" title="Replication: Copies, Lag & Quorums">

Every booking the cinema confirms is a row in Postgres. One database server is one machine that can fail, and one machine that every seat-map request must reach. So you keep **copies**: a replica that can take over if the primary dies, and that can answer reads so the primary isn't answering all of them.

Copies are never quite the same, though, and the gap is where the bugs live. A customer books a seat and the page, reading from a replica, says it's still free. A failover promotes a replica that never received the last ten bookings. Two machines both believe they're the primary. This chapter builds a real primary and replica, makes each of those things happen, measures them, and fixes the ones that can be fixed. Then it goes leaderless: three nodes, no primary, and quorums.

Six stops. If you get lost, come back here:

1. **A replica.** Postgres streaming replication, set up and watched.
2. **Lag and stale reads.** How often a read from the replica misses a booking just made.
3. **Read your own writes.** Wait for the replica to catch up, precisely, and the bug in the first attempt.
4. **Synchronous replication.** Four levels of "committed", their price, and what happens when the standby dies.
5. **Failover.** Promote the replica: lost bookings, and two primaries.
6. **No leader.** Quorums on three nodes, stale reads, and conflicts you can see.

## The lab bench

Two Postgres 17 containers on a Docker network: `pg-primary` and `pg-replica`, the replica created from the primary with `pg_basebackup` and streaming its WAL. The cinema's `bookings` table (movie, seat, customer, booked_at). For stop 6, three Redis 8.10 containers, each behind its own Toxiproxy proxy so a node can be cut off. The experiments are Go programs in one module, `repl`.

## A Replica

*Stop 1 of 6.*

### Step 1: how Postgres replicates

Postgres writes every change to its **write-ahead log** (WAL) before changing the data files: that's what makes a committed transaction survive a crash. A **streaming replica** is a second server that receives the primary's WAL as it's written and **replays** it, so its data files follow the primary's. It can answer read-only queries while it does (`hot_standby`). Setting one up:

```text
$ docker run -d --name pg-primary --network repl … postgres:17 -c wal_level=replica -c max_wal_senders=5
$ psql primary -c "CREATE ROLE replicator WITH REPLICATION LOGIN PASSWORD '…'"
$ docker run --rm --network repl -v pgrepl:/var/lib/postgresql/data postgres:17 \
    pg_basebackup -h pg-primary -U replicator -D /var/lib/postgresql/data -R -X stream -C -S replica1
$ docker run -d --name pg-replica --network repl -v pgrepl:/var/lib/postgresql/data postgres:17
```

`pg_basebackup` copies the primary's data files; `-R` writes the settings that make the copy start as a standby that connects back to the primary; `-S replica1` creates a **replication slot**, so the primary keeps any WAL the replica hasn't received yet. On the primary:

```text
$ psql primary -xc "SELECT client_addr, state, sync_state, write_lag, replay_lag FROM pg_stat_replication"
-[ RECORD 1 ]----------------
client_addr | 172.20.0.3
state       | streaming
sync_state  | async
write_lag   | 00:00:00.000281
replay_lag  | 00:00:00.000281
```

**async**: the primary commits without waiting for the replica. The lag, 0.28 ms, is on one machine with nothing else to do.

## Lag and Stale Reads

*Stop 2 of 6.*

### Step 1: book, then look

The cinema's page, after a booking, asks "is this seat booked?" If that read goes to the replica (the point of having one), will it see the booking? `stale` books 200 seats on the primary, one at a time, and reads each back from the replica immediately:

```go noverify
// stale books seats on the primary and immediately reads them back from
// the replica, the way the cinema's page would after a booking: "is my
// seat booked?". -ryw waits for the replica to replay the booking first.
package main

import (
	"context"
	"flag"
	"fmt"
	"log"
	"slices"
	"time"

	"github.com/jackc/pgx/v5"
	"github.com/jackc/pgx/v5/pgxpool"
)

func main() {
	n := flag.Int("n", 200, "bookings")
	ryw := flag.Bool("ryw", false, "read-your-writes: wait for the replica to replay the booking's LSN")
	flag.Parse()
	ctx := context.Background()
	primary, err := pgxpool.New(ctx, "postgres://postgres:cinema@127.0.0.1:55501/cinema")
	if err != nil {
		log.Fatal(err)
	}
	replica, err := pgxpool.New(ctx, "postgres://postgres:cinema@127.0.0.1:55502/cinema")
	if err != nil {
		log.Fatal(err)
	}
	if _, err := primary.Exec(ctx, "TRUNCATE bookings"); err != nil {
		log.Fatal(err)
	}
	time.Sleep(time.Second) // let the replica catch up with the TRUNCATE

	stale := 0
	var visibleAfter []time.Duration // how long until the replica showed the booking
	var readLatency []time.Duration
	for i := range *n {
		seat := fmt.Sprintf("%c%d", 'A'+i/40%26, 1+i%40)
		if _, err := primary.Exec(ctx, "INSERT INTO bookings (movie, seat, customer) VALUES ('inception', $1, $2)",
			seat, fmt.Sprint("customer-", i)); err != nil {
			log.Fatal(err)
		}
		// The WAL position after the commit: it includes the commit record,
		// which is what makes the booking visible. (Read inside the
		// transaction, it would be before the commit record.)
		var lsn string
		if err := primary.QueryRow(ctx, "SELECT pg_current_wal_lsn()::text").Scan(&lsn); err != nil {
			log.Fatal(err)
		}
		committed := time.Now()
		if *ryw {
			// Wait until the replica has replayed at least this LSN.
			for {
				var caughtUp bool
				if err := replica.QueryRow(ctx, "SELECT pg_last_wal_replay_lsn() >= $1::pg_lsn", lsn).Scan(&caughtUp); err != nil {
					log.Fatal(err)
				}
				if caughtUp {
					break
				}
				time.Sleep(time.Millisecond)
			}
		}
		var found bool
		if err := replica.QueryRow(ctx, "SELECT EXISTS (SELECT 1 FROM bookings WHERE movie = 'inception' AND seat = $1)", seat).Scan(&found); err != nil {
			log.Fatal(err)
		}
		readLatency = append(readLatency, time.Since(committed))
		if !found {
			stale++
		}
		// Measure how long until the replica shows it at all.
		for !found {
			if err := replica.QueryRow(ctx, "SELECT EXISTS (SELECT 1 FROM bookings WHERE movie = 'inception' AND seat = $1)", seat).Scan(&found); err != nil && err != pgx.ErrNoRows {
				log.Fatal(err)
			}
		}
		visibleAfter = append(visibleAfter, time.Since(committed))
	}
	q := func(d []time.Duration, p float64) time.Duration {
		s := slices.Clone(d)
		slices.Sort(s)
		return s[int(p*float64(len(s)-1))].Round(10 * time.Microsecond)
	}
	fmt.Printf("%d bookings: %d reads from the replica didn't show the booking just made (%.0f%%)\n", *n, stale, 100*float64(stale)/float64(*n))
	fmt.Printf("  time from commit to the read's answer: p50 %v, p99 %v\n", q(readLatency, 0.5), q(readLatency, 0.99))
	fmt.Printf("  time from commit until the replica showed it: p50 %v, p99 %v, max %v\n", q(visibleAfter, 0.5), q(visibleAfter, 0.99), q(visibleAfter, 1))
}
```

</CodeWalk>

**3% of the reads missed the booking just made**, on an idle laptop with a replica 0.3 ms behind. That's the nature of asynchronous replication: the primary answers "committed" and the replica catches up after; any read in between sees the past.

### Step 2: a replica that's behind

Real replicas fall behind: a long query holds up replay, a burst of writes, a replica in another region. `recovery_min_apply_delay` makes a replica apply each commit a set time late, which reproduces that on purpose:

```text
$ psql replica -c "ALTER SYSTEM SET recovery_min_apply_delay = '300ms'"; stale -n 50
50 bookings: 50 reads from the replica didn't show the booking just made (100%)
  time from commit to the read's answer: p50 360µs, p99 3.64ms
  time from commit until the replica showed it: p50 300.87ms, p99 304.18ms, max 305.97ms
$ stale -n 50 -ryw        # wait for the replica to replay the booking's LSN before reading
50 bookings: 50 reads from the replica didn't show the booking just made (100%)
  time from commit to the read's answer: p50 650µs, p99 13.47ms
  time from commit until the replica showed it: p50 300.76ms, p99 303.22ms, max 303.41ms
```

Look at the first run only for now: 300 ms behind, **every** read missed the booking, and each booking appeared 300–306 ms after it was confirmed. The second run is stop 3's first attempt at a fix.

## Read Your Own Writes

*Stop 3 of 6.*

### Step 1: wait for the replica, precisely

Customers don't mind that *other* people's bookings take a moment to appear. They do mind that *their own* booking vanishes after the confirmation page. That guarantee is called **read-your-writes**, and Postgres makes it exact: every commit has a position in the WAL (an **LSN**, log sequence number); the replica reports how far it has replayed (`pg_last_wal_replay_lsn()`). Remember the LSN after your write; before reading from the replica, wait until it has replayed at least that far.

### Step 2: the first attempt was wrong

The first version of `stale -ryw` read the LSN in the same statement as the insert:

```sql
WITH b AS (INSERT INTO bookings … RETURNING 1) SELECT pg_current_wal_lsn()::text FROM b
```

And it didn't help: the second run in stop 2's output, `-ryw`, still missed **50 of 50**. That LSN was taken *inside* the transaction, before its **commit record** was written. The replica replayed up to it (the inserted row's WAL) and reported itself caught up, but the row only becomes visible when the commit record is replayed, and `recovery_min_apply_delay` holds exactly the commit records back. The fix is to read the LSN **after** the commit:

```go noverify
// main.go, lines 41–65
		if _, err := primary.Exec(ctx, "INSERT INTO bookings (movie, seat, customer) VALUES ('inception', $1, $2)",
			seat, fmt.Sprint("customer-", i)); err != nil {
			log.Fatal(err)
		}
		// The WAL position after the commit: it includes the commit record,
		// which is what makes the booking visible. (Read inside the
		// transaction, it would be before the commit record.)
		var lsn string
		if err := primary.QueryRow(ctx, "SELECT pg_current_wal_lsn()::text").Scan(&lsn); err != nil {
			log.Fatal(err)
		}
		committed := time.Now()
		if *ryw {
			// Wait until the replica has replayed at least this LSN.
			for {
				var caughtUp bool
				if err := replica.QueryRow(ctx, "SELECT pg_last_wal_replay_lsn() >= $1::pg_lsn", lsn).Scan(&caughtUp); err != nil {
					log.Fatal(err)
				}
				if caughtUp {
					break
				}
				time.Sleep(time.Millisecond)
			}
		}
```

```text
$ stale -n 50 -ryw        # LSN read after the commit
50 bookings: 0 reads from the replica didn't show the booking just made (0%)
  time from commit to the read's answer: p50 301.3ms, p99 311.64ms
  time from commit until the replica showed it: p50 301.3ms, p99 311.64ms, max 311.66ms
$ stale -n 50             # the same, without waiting
50 bookings: 50 reads from the replica didn't show the booking just made (100%)
  time from commit to the read's answer: p50 310µs, p99 680µs
  time from commit until the replica showed it: p50 300.49ms, p99 301.84ms, max 301.88ms
```

**0 of 50 stale.** The reads now wait out the lag (p50 301 ms), which is honest: the data isn't on the replica yet. In a real service you'd keep the LSN in the customer's session after a booking, and send their reads to the primary, or wait, only while the replica is behind it. Everyone else reads the replica freely.

## Synchronous Replication

*Stop 4 of 6.*

### Step 1: what "committed" waits for

Postgres can make a commit wait for the standby. With `synchronous_standby_names = '*'`, the `synchronous_commit` setting (per transaction, even) chooses how much:

- **`local`**: flushed to the primary's disk only (asynchronous).
- **`remote_write`**: the standby has received it and written it to its OS.
- **`on`**: the standby has flushed it to disk. A committed booking now survives losing the primary.
- **`remote_apply`**: the standby has *applied* it, so a read there sees it.

`synclat` books 100 seats at each level, with the replica still applying 300 ms late, and reads each from the replica straight away:

```text
# replica applies WAL 300 ms late; synchronous_standby_names = '*'
synchronous_  commit p50/p99 stale reads
local         620µs  /15.49ms 100 of 100
remote_write  570µs  /7.67ms  100 of 100
on            710µs  /8.02ms  100 of 100
remote_apply  305.86ms/313.77ms 0 of 100
```

`remote_write` and `on` cost almost nothing here (the standby is on the same machine; across regions they'd add a network round trip to every commit), and they make bookings **durable** on two machines, but they don't make the replica **current**: still 100 of 100 stale. Only `remote_apply` does, and it pays the whole apply delay, **306 ms**, on every commit.

### Step 2: when the standby dies

Synchronous replication has a failure mode that asynchronous doesn't:

```text
$ docker stop pg-replica          # the synchronous standby goes away
$ psql primary -c "SET statement_timeout = '3s'" -c "INSERT INTO bookings VALUES ('inception', 'A1', 'alice')"
SET
WARNING:  canceling wait for synchronous replication due to user request
DETAIL:  The transaction has already committed locally, but might not have been replicated to the standby.
INSERT 0 1
(returned after 135.1 s: statement_timeout never fired; another session ran pg_cancel_backend)
$ psql primary -c "SELECT seat, customer FROM bookings"
 seat | customer 
------+----------
 A1   | alice
(1 row)


[exited with code 0]
```

With the synchronous standby stopped, a commit **waited 135 seconds**, and `statement_timeout = '3s'` never fired: the statement had finished, and the timeout doesn't cover the wait for replication at commit. It only returned because another session cancelled it. Then read the warning: the transaction **had already committed locally**. The client got a warning after two minutes; a driver with its own timeout would have reported an error for a booking that exists. "Synchronous" means one machine's failure stops every writer, so production setups name two or more standbys (`ANY 1 (a, b)`) so that one can fail without stopping writes.

## Failover

*Stop 5 of 6.*

### Step 1: promote the replica

When the primary dies, a replica is **promoted**: it stops following and starts accepting writes. With asynchronous replication, anything the primary committed but hadn't sent is gone. `failover.sh` makes that happen deliberately:

```text
10 bookings made; the replica has 10
$ docker network disconnect repl pg-replica     # the replica loses contact
10 more bookings made and confirmed to customers; the primary has 20
$ docker kill pg-primary                         # the primary crashes
$ psql replica -c 'SELECT pg_promote()'           # failover: the replica becomes the primary
t
the new primary has 10 bookings; row B: 0
$ # new customers book B1–B3, which the new primary says are free
  B1 booked for newcomer-1
  B2 booked for newcomer-2
  B3 booked for newcomer-3
$ docker start pg-primary                        # the old primary comes back, as a primary
old primary: in recovery? f; B1 belongs to customer-11
new primary: in recovery? f; B1 belongs to newcomer-1
the old primary still accepts writes: C1 booked on it
```

Read it in order. Ten bookings reached both servers. The replica lost contact, and the primary confirmed **ten more**. The primary crashed; the replica was promoted: **it has 10 bookings, and row B is empty**. Ten customers hold confirmations the cinema no longer knows about, and the new primary cheerfully sold B1–B3 to newcomers.

### Step 2: two primaries

Then the old primary was restarted, and it came back **as a primary**: nothing told it that it had been replaced. Seat B1 belongs to `customer-11` there and to `newcomer-1` on the new primary, and the old one accepted a new booking (C1). This is **split brain**: two servers accepting writes for the same data, diverging with every write. Any client still pointed at the old primary (a stale DNS entry, a connection pool that reconnects to the old address) writes into a history that will be thrown away or has to be merged by hand.

Preventing it takes more than Postgres itself: the failover tooling (Patroni, or a managed database's control plane) must **fence** the old primary, making sure it's stopped, or can't accept connections, before the new one takes writes, and clients must find the primary through something the failover updates. Chapter 23 builds fencing tokens; chapter 24, the consensus that decides who the leader is.

## No Leader

### Step 1: quorums

Leader-based replication funnels every write through one server. **Leaderless** replication (Amazon's Dynamo, Cassandra, Riak) sends each write to all **N** copies and treats it as done when **W** acknowledge; each read asks the copies and uses the first **R** answers. If **R + W > N**, every read quorum overlaps every write quorum, so some copy in every read has the latest write. `quorum` is a small implementation over three independent Redis servers, each value carrying a **version vector** (which writer wrote how many times) so a read can tell newer from concurrent:

A `Store` is just a list of independent Redis servers and a timeout for each call. None of them knows about the others; the quorum logic lives entirely in this client:

```go noverify title="repl/quorum/quorum.go · lines 1–21"
// Package quorum is a leaderless, Dynamo-style replicated register over N
// independent Redis nodes: a write goes to every node and succeeds when W
// acknowledge; a read asks every node and returns when R have answered.
// Each value carries a version vector, so a read can tell "newer" from
// "concurrent" (a conflict).
package quorum

import (
	"context"
	"encoding/json"
	"errors"
	"fmt"
	"time"

	"github.com/redis/go-redis/v9"
)

type Store struct {
	Nodes   []*redis.Client
	Timeout time.Duration // per node
}
```

Each stored value is a `Version`: the value, a **version vector** (for each writer, how many writes it has made), and a wall-clock time. `descends(a, b)` asks whether `a` has seen everything `b` has: if so, `a` is at least as new. If neither descends from the other, the two were written **concurrently**, without either writer knowing about the other:

```go noverify title="repl/quorum/quorum.go · lines 23–41"
// Version is one write: a value, the vector clock it was written with
// (writer → count), and the writer's wall-clock time (for last-writer-wins).
type Version struct {
	Value string         `json:"value"`
	Clock map[string]int `json:"clock"`
	At    time.Time      `json:"at"`
}

// descends reports whether a has seen everything b has.
func descends(a, b map[string]int) bool {
	for k, n := range b {
		if a[k] < n {
			return false
		}
	}
	return true
}

var ErrQuorum = errors.New("quorum not reached")
```

`Put` sends the write to every node at once, one goroutine each, and counts answers as they come back on a channel. It returns as soon as **W** nodes have acknowledged, without waiting for the slowest. It also gives up early: once more than N − W nodes have failed, W acknowledgements are impossible. The goroutines that haven't answered yet still finish; the channel has room for all of them, so none blocks:

```go noverify title="repl/quorum/quorum.go · lines 43–70"
// Put writes v to every node in parallel and returns once w of them have
// acknowledged (or fails when that becomes impossible).
func (s *Store) Put(ctx context.Context, key string, v Version, w int) (acked int, err error) {
	b, _ := json.Marshal(v)
	results := make(chan error, len(s.Nodes))
	for _, n := range s.Nodes {
		go func() {
			ctx, cancel := context.WithTimeout(ctx, s.Timeout)
			defer cancel()
			results <- n.Set(ctx, key, b, 0).Err()
		}()
	}
	failed := 0
	for range s.Nodes {
		if err := <-results; err != nil {
			failed++
		} else {
			acked++
		}
		if acked >= w {
			return acked, nil
		}
		if failed > len(s.Nodes)-w {
			break
		}
	}
	return acked, fmt.Errorf("%w: %d of %d acknowledged, needed %d", ErrQuorum, acked, len(s.Nodes), w)
}
```

`Get` is the mirror image: ask every node, stop after **R** answers. A node that doesn't have the key answers with nothing, which counts as an answer (it's a real, current state), and only errors count as failures:

```go noverify title="repl/quorum/quorum.go · lines 72–118"
// Get asks every node and returns the versions from the first r replies,
// reduced to those no other reply has superseded: one version normally,
// several if they were written concurrently.
func (s *Store) Get(ctx context.Context, key string, r int) ([]Version, error) {
	type reply struct {
		v   *Version
		err error
	}
	replies := make(chan reply, len(s.Nodes))
	for _, n := range s.Nodes {
		go func() {
			ctx, cancel := context.WithTimeout(ctx, s.Timeout)
			defer cancel()
			b, err := n.Get(ctx, key).Bytes()
			if errors.Is(err, redis.Nil) {
				replies <- reply{}
				return
			}
			if err != nil {
				replies <- reply{err: err}
				return
			}
			var v Version
			replies <- reply{v: &v, err: json.Unmarshal(b, &v)}
		}()
	}
	var got []Version
	answered, failed := 0, 0
	for range s.Nodes {
		rp := <-replies
		if rp.err != nil {
			failed++
			if failed > len(s.Nodes)-r {
				return nil, fmt.Errorf("%w: %d of %d answered, needed %d", ErrQuorum, answered, len(s.Nodes), r)
			}
			continue
		}
		answered++
		if rp.v != nil {
			got = append(got, *rp.v)
		}
		if answered >= r {
			break
		}
	}
	return latest(got), nil
}
```

`latest` is where version vectors pay off. It drops every version that another one descends from, and drops duplicates. What remains is one version normally, or several if writers raced. Returning several, rather than silently picking one, is what lets the caller see a **conflict** instead of losing a write:

```go noverify title="repl/quorum/quorum.go · lines 120–142"
// latest drops every version another one descends from.
func latest(vs []Version) []Version {
	var out []Version
	for i, v := range vs {
		superseded := false
		for j, o := range vs {
			if i != j && descends(o.Clock, v.Clock) && !descends(v.Clock, o.Clock) {
				superseded = true
				break
			}
		}
		dup := false
		for _, o := range out {
			if descends(o.Clock, v.Clock) && descends(v.Clock, o.Clock) {
				dup = true
			}
		}
		if !superseded && !dup {
			out = append(out, v)
		}
	}
	return out
}
```

### Step 2: measured

Node 3 is cut off (its Toxiproxy proxy disabled) while Alice holds A7 with W=2; then node 3 comes back, without her hold:

```text
== N=3. Node 3 is cut off while alice holds A7 with W=2.
put alice W=2: 2 acknowledged, err=<nil>
300 reads with R=1 (R+W=3, N=3): 116 said nobody holds A7
300 reads with R=2 (R+W=4, N=3): 0 said nobody holds A7

== A partition splits node 1 from nodes 2 and 3. Two customers hold B4, one on each side.
web-1 (sees node 1 only):   put bob   W=1: 1 acknowledged, err=<nil>
                            put bob   W=2: err=quorum not reached: 1 of 3 acknowledged, needed 2
web-2 (sees nodes 2 and 3): put carol W=2: 2 acknowledged, err=<nil>
partition healed; read R=3: CONFLICT: carolmap[web-2:1] bobmap[web-1:1]
last-writer-wins would keep "carol" and silently drop the other hold
```

With **R=1** (R+W = N, no guaranteed overlap), **116 of 300 reads said nobody holds A7**: whenever node 3 answered first. With **R=2** (R+W > N), **0**: at least one of any two nodes has the hold, and the version vectors pick it.

The first version of this experiment used `docker pause` to cut node 3 off, and saw **no** stale reads at all. The write to the paused node didn't fail: it sat in the connection's buffers, and was applied the moment the node resumed. The client had timed out and counted it as not acknowledged, but the write happened anyway. That's chapter 12's lost reply again, and the reason leaderless stores also need **read repair** and **anti-entropy** (writing newer versions back to stale nodes): "not acknowledged" doesn't mean "not written".

### Step 3: concurrent writes

Now a partition splits node 1 from nodes 2 and 3. Bob's server can reach only node 1; Carol's can reach 2 and 3. Both hold B4. Bob's W=2 write fails (only one node answered), so he retries with **W=1**, and it succeeds. After the partition heals, a read of all three returns **a conflict**: two versions, `bob {web-1:1}` and `carol {web-2:1}`, neither of which has seen the other. The version vectors *know* these are concurrent.

**Last-writer-wins** (keep the one with the later timestamp) would quietly keep Carol and drop Bob's hold; Cassandra does exactly that by default. A seat can't be held twice, so the cinema must choose, and tell the loser. And the real lesson is one step earlier: with **W=2 on both sides**, only one side of a partition can reach a majority, so only one of Bob and Carol can succeed. Dropping to W=1 bought availability during the partition and paid for it with a conflict.

<Exercise n={1} title="Route the reads" level="easy">

Design the cinema's read routing: which queries go to the primary and which to the replica, for (a) the public seat map; (b) a customer's "my bookings" page right after booking; (c) the box-office occupancy report; (d) the Hold that must check the seat is free.

<Solution>

(a) **Replica**: a second-old seat map is fine, and it's most of the traffic. (b) **Replica with read-your-writes**: remember the LSN of the customer's last write in their session; read from the replica only once it has replayed that far, otherwise from the primary. (c) **Replica**, or a dedicated reporting replica, so a long report never slows the primary. (d) **Primary, inside the write**: the check and the hold must be one atomic operation on the source of truth (chapter 8's lesson). A check on a replica followed by a write on the primary is a race with lag added.

</Solution>

</Exercise>

<Exercise n={2} title="Measure your lag" level="easy">

Using `pg_stat_replication` on the primary and `pg_last_xact_replay_timestamp()` on the replica, write a query for each that an alert could use. Which one keeps growing when the primary is idle?

<Solution>

On the primary: `SELECT application_name, replay_lag FROM pg_stat_replication`, which is measured per standby from WAL positions and stops advancing (the view shows NULL after a while) when there's nothing new to replicate. On the replica: `SELECT now() - pg_last_xact_replay_timestamp()`, the age of the last replayed commit, which **keeps growing when the primary is idle**, since no new commits arrive. So alert on replay_lag (or the byte gap `pg_wal_lsn_diff(pg_current_wal_lsn(), replay_lsn)`) rather than on replay-timestamp age, or combine the age with a check that the primary actually committed something.

</Solution>

</Exercise>

<Exercise n={3} title="Two synchronous standbys" level="medium">

Add a second replica and set `synchronous_standby_names = 'ANY 1 (walreceiver, replica2)'` (use `application_name` in each standby's `primary_conninfo` to tell them apart). Repeat stop 4's experiment with one standby stopped. What changes, and what does it cost?

<Solution>

Commits wait for **any one** of the two standbys, so stopping one no longer stops writes: the other acknowledges. Durability stays "on two machines" as long as one standby is up. The cost is a third server, and commit latency becomes that of the faster standby (good). With `FIRST 1 (a, b)` instead, `a` is preferred and `b` takes over only when `a` is gone. Either way, a single standby failure no longer turns into a 135-second stall.

</Solution>

</Exercise>

<Exercise n={4} title="Lose less on failover" level="medium">

Repeat stop 5 with `synchronous_commit = on` and a synchronous standby. What happens to the ten bookings made after the replica loses contact?

<Solution>

They never complete: each commit waits for the standby that can't be reached, and the customers see a hang instead of a confirmation (stop 4). When the primary is killed, those transactions had committed locally but were never acknowledged, so nobody holds a confirmation for them, and the promoted replica has every booking that *was* confirmed. That's the trade: synchronous replication turns "lost confirmed writes" into "writes that couldn't be confirmed", which is far better for bookings, at the cost of availability while the standby is unreachable.

</Solution>

</Exercise>

<Exercise n={5} title="Resolve the conflict" level="hard">

Extend `quorum` so a write carries the clock of the version it read (a context), and a read with siblings returns them all. Then write the cinema's resolution for two concurrent holds on one seat, and the read repair that writes the resolved value back to every node.

<Solution>

`Put` takes the clock from the last read, merges it (max per writer), and increments its own writer's entry, so a write made after reading both siblings descends from both and supersedes them. For seats: pick the hold with the earlier `At` (first come, first served: arguably fairer than LWW's "latest wins"), give the loser a clear error and, if they already saw a confirmation, an apology and a hold on a nearby seat. Read repair: after resolving, `Put` the winner with the merged clock to all N nodes (W can be low: it's a background fix). Riak and Dynamo's descendants work this way; Cassandra instead resolves by timestamp per column, which is why conditional writes (lightweight transactions, using Paxos) are what you'd use for a seat.

</Solution>

</Exercise>

The chapter's `quorum` package is the same logic over real Redis nodes. Here the nodes are in-process stand-ins that can be slow or down, which is all the client logic can observe of a real node anyway.

<Recap>

- **Streaming replication** ships the WAL to a replica that replays it. Asynchronous by default: the primary commits alone, the replica follows (0.28 ms behind on an idle machine).
- **Stale reads**: 6 of 200 reads right after a booking missed it with no delay; 50 of 50 with the replica 300 ms behind.
- **Read-your-writes** by waiting for the replica to replay past the write's LSN: 0 of 50 stale. The LSN must be read **after** the commit; read inside the transaction, it's before the commit record and the fix silently doesn't work (50 of 50).
- **Synchronous commit** levels: `local`, `remote_write` and `on` cost almost nothing on one machine but left 100 of 100 reads stale; `remote_apply` made them fresh at 306 ms a commit. With the only synchronous standby down, a commit **hung 135 s**, ignoring `statement_timeout`, and had committed locally.
- **Async failover** lost **10 confirmed bookings**, and the restarted old primary accepted writes as a second primary: split brain, B1 sold twice. Fencing and client redirection are the failover system's job.
- **Leaderless quorums** over three Redis nodes: R=1 missed a W=2 hold 116 times in 300; R=2 never (R+W>N). `docker pause` hid staleness because the "failed" write landed later. W=1 during a partition produced a conflict the version vectors detected and last-writer-wins would have hidden.
