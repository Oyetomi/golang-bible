## Timeouts Everywhere

<Define term="Timeout" since="The context Package, In Depth (Part 1)">
A **timeout** is an upper bound on how long your code will wait for an operation to complete. Without one, a blocked goroutine waits forever — holding a connection, a goroutine stack, and any downstream resources with it. In Go, timeouts are expressed as a `context.WithTimeout` deadline that propagates cancellation through the entire call tree when time is up. **On the job:** the absence of a timeout turns a flaky downstream into a full service freeze — the goroutine pile-up blocks new requests until the whole process looks down.
</Define>

Here's the scenario. It's Black Friday. Your checkout service calls an external payment processor. The processor doesn't respond. Not an error — it just… says nothing. The goroutine handling that request sits there, blocking, holding a connection from your pool, occupying a slot in your server's goroutine table. More requests come in. More goroutines block. The connection pool drains. New requests start waiting for a free connection. The whole thing seizes up, and now *your* service looks down to upstream callers — even though the processor is the sick one. This is called a **cascading failure**, and the root cause is embarrassingly simple: you made a network call without a timeout.

**Every network call, every I/O operation, every blocking operation must have a deadline.** No exceptions. Not "probably." Not "the SDK handles it." You handle it.

### The Default-No-Timeout Trap

Go's `net/http` package has a trap waiting for anyone who uses the zero-value client:

```go
// This is the trap. Do NOT do this in production.
resp, err := http.Get("https://payments.example.com/charge")
```

`http.Get` uses `http.DefaultClient`, whose `Timeout` field is zero — meaning **no timeout at all**. A request to a hung server will block forever.

The fix is a `http.Client` with an explicit `Timeout`, or better still, a `context` with a deadline so the timeout is composable and cancellation propagates through your whole call tree:

The `context.WithTimeout` approach is superior to the `http.Client.Timeout` field because:

1. The timeout is **per-request** — different endpoints get different budgets.
2. Cancellation **propagates** — if the parent handler is cancelled (e.g. the end user closed the browser), the outbound HTTP call is cancelled too, freeing the connection immediately.
3. The same context flows into DB calls, cache calls, and any goroutine you spawn — one deadline covers the whole operation.

### Timeout Sizing

Every external call needs its own budget. A quick rules-of-thumb grid:

<ConceptGrid cols={3}>
  <ConceptCard label="Intra-service (same DC)">50–200ms. If your own database or cache isn't responding in under a second, something is broken — don't mask it with a generous timeout.</ConceptCard>
  <ConceptCard label="External payment APIs">2–5s. Card networks have their own SLAs. Match your timeout to the documented p99 + a small buffer — not to "infinity just in case."</ConceptCard>
  <ConceptCard label="Read vs. write">Writes (a POST to create a charge) usually need more time than reads. But they should still have a timeout. Unbounded writes are just unbounded blocking with extra steps.</ConceptCard>
  <ConceptCard label="DB queries">Each query should carry the parent request context. Set `SetConnMaxLifetime` and `SetConnMaxIdleTime` on the pool too — that's the pool-level backstop.</ConceptCard>
  <ConceptCard label="Total request budget">The server-side handler timeout (set on `http.Server.ReadHeaderTimeout`, `WriteTimeout`, or via middleware) is the outer envelope. Each downstream call's timeout must fit inside it.</ConceptCard>
  <Gotcha>Never set a database context deadline that is longer than your HTTP server's `WriteTimeout`. The client will have disconnected long before your DB query returns, and you'll have spent resources on a result nobody will ever read.</Gotcha>
</ConceptGrid>

Here's a complete, runnable checkout client that shows the right pattern: `http.Client` with no global timeout, `context.WithTimeout` per-call, `http.NewRequestWithContext`, and deliberate error handling on deadline exceeded:

<GoPlayground>

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"net/http"
	"net/http/httptest"
	"time"
)

// slowServer simulates a payment processor that takes too long.
func slowServer() *httptest.Server {
	return httptest.NewServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		// Hang for longer than the client's timeout.
		select {
		case <-time.After(10 * time.Second):
			w.WriteHeader(http.StatusOK)
		case <-r.Context().Done():
			// Server-side: the client cancelled — stop working.
		}
	}))
}

func chargeCard(ctx context.Context, client *http.Client, url string) error {
	req, err := http.NewRequestWithContext(ctx, http.MethodPost, url, nil)
	if err != nil {
		return fmt.Errorf("build request: %w", err)
	}
	resp, err := client.Do(req)
	if err != nil {
		// Unwrap to check for deadline/cancellation.
		if errors.Is(err, context.DeadlineExceeded) ||
			errors.Is(ctx.Err(), context.DeadlineExceeded) {
			return fmt.Errorf("payment processor timed out: %w", err)
		}
		return fmt.Errorf("payment call failed: %w", err)
	}
	defer resp.Body.Close()
	if resp.StatusCode != http.StatusOK {
		return fmt.Errorf("payment rejected: status %d", resp.StatusCode)
	}
	return nil
}

func main() {
	srv := slowServer()
	defer srv.Close()

	// Shared client — no Timeout field. Timeout lives on the context instead.
	client := &http.Client{}

	ctx, cancel := context.WithTimeout(context.Background(), 2*time.Second)
	defer cancel()

	start := time.Now()
	err := chargeCard(ctx, client, srv.URL+"/charge")
	elapsed := time.Since(start).Round(10 * time.Millisecond)

	if err != nil {
		fmt.Printf("charge failed after %v: %v\n", elapsed, err)
	} else {
		fmt.Println("charge succeeded")
	}
}
```

</GoPlayground>

<UnderTheHood title="How context cancellation actually interrupts a blocked network call">

When `context.WithTimeout` fires, it closes the `ctx.Done()` channel. The `net/http` transport watches that channel via a select inside its internal I/O loop. The moment `Done()` closes, the transport **cancels the in-flight request** by calling `CancelRequest` on the underlying `*http.Transport` (Go 1.7+) or setting a deadline directly on the TCP connection via `conn.SetDeadline(time.Now())`. The OS returns an error from the blocked `read`/`write` syscall, which bubbles up as a `*url.Error` wrapping `context.DeadlineExceeded`.

The key insight: **a context cancellation is not a goroutine kill signal.** It sets a deadline on the underlying file descriptor, which causes the OS syscall to return with an error. Your goroutine is never forcibly killed — it unblocks from the syscall and walks the error path normally. This is why proper error handling (`errors.Is(err, context.DeadlineExceeded)`) is required: the error *looks like* a normal network error unless you inspect it.

`http.Transport` also propagates cancellation to HTTP/2 streams via RST_STREAM frames, so the server is notified promptly and can abort its own work — saving resources on both sides.

</UnderTheHood>

## Retries with Backoff and Jitter

<Define term="Retry with exponential backoff and jitter">
A **retry** re-sends a failed request automatically, but naive immediate retries can make a struggling downstream worse. **Exponential backoff** grows the wait between retries (`base × 2ⁿ`) so each successive attempt gives the downstream more breathing room. **Jitter** adds randomness to that wait so a fleet of services doesn't all retry at the same instant (the *thundering herd*). Together they turn a wall of hammering retries into a gentle, spread-out drizzle. **On the job:** retries without jitter on a 500-instance fleet can convert a 10 % failure rate into a 100 % failure rate by stampeding the recovering downstream.
</Define>

You applied a timeout and now your payment call fails fast. Great. But sometimes failure is transient — the processor had a brief hiccup, a pod restarted, a network blip. Failing fast and returning 500 to your customer *every* time is almost as bad as hanging. The right answer is **retrying** — but *only the right operations*, and *only in the right way*.

### Only Retry Idempotent, Safe Operations

This is the rule that separates good retries from catastrophic ones: **you may only blindly retry an operation if retrying it twice produces the same result as retrying it once.**

- A `GET /orders/123` is safe to retry — reading data doesn't change it.
- A `POST /charge` is **not** safe to retry without an idempotency key — retrying a charge might charge the customer twice.

We'll cover idempotency keys in depth in section 6. For now: before you add a retry loop around anything, ask yourself "if this runs twice, does the customer lose money or data?" If yes, add an idempotency key *first*, then add the retry.

### Exponential Backoff

**Naive retry:** retry immediately, N times. This is almost always wrong. If the downstream service is overwhelmed, hammering it with immediate retries makes the situation worse for everyone.

**Exponential backoff:** after each failure, wait longer before the next attempt. The wait time grows exponentially — typically `base * 2^(attempt-1)`:

| Attempt | Wait (base=200ms) |
|---------|-------------------|
| 1 (fail) | 0ms (first try) |
| 2 (retry) | 200ms |
| 3 (retry) | 400ms |
| 4 (retry) | 800ms |

But here's the problem with pure exponential backoff: if 500 instances of your service all fail at the same time (say, a pod restart), they will all compute the *same* wait time and retry at the *same* moment — a perfectly synchronized stampede that overwhelms the recovering downstream. This is called the **thundering herd**.

### Full Jitter: Why It Prevents the Thundering Herd

The fix is **jitter** — randomness added to the backoff delay. The most effective form is **full jitter**: pick a random value in the range `[0, exponential_cap)` rather than waiting the full exponential time.

```go
// Full jitter: sleep a random duration in [0, base * 2^attempt)
func backoffDuration(attempt int, base, cap time.Duration) time.Duration {
	exp := base * (1 << min(attempt, 30)) // 2^attempt, capped to avoid overflow
	if exp > cap {
		exp = cap
	}
	// rand.N is the modern, goroutine-safe form (Go 1.22+, no seed needed)
	return time.Duration(rand.N(int64(exp)))
}
```

With full jitter, 500 instances retrying simultaneously will now retry at *random* times spread across the backoff window — the thundering herd dissolves into a gentle drizzle.

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"math/rand/v2"
	"time"
)

// ErrMaxRetries is returned when the retry budget is exhausted.
var ErrMaxRetries = errors.New("max retries exceeded")

// backoffDuration computes a full-jitter exponential backoff duration.
// attempt is 0-indexed (0 = first retry, not the original attempt).
func backoffDuration(attempt int, base, cap time.Duration) time.Duration {
	// 2^attempt, guarded against shift overflow
	shift := attempt
	if shift > 30 {
		shift = 30
	}
	exp := base << shift // base * 2^attempt
	if exp > cap {
		exp = cap
	}
	// Full jitter: random in [0, exp)
	return time.Duration(rand.N(int64(exp)))
}

// withRetry calls op up to maxAttempts times using full-jitter backoff.
// It only retries when op returns a retryable error (checked via isRetryable).
func withRetry(
	ctx context.Context,
	maxAttempts int,
	base, capDur time.Duration,
	isRetryable func(error) bool,
	op func(ctx context.Context) error,
) error {
	var lastErr error
	for attempt := range maxAttempts {
		lastErr = op(ctx)
		if lastErr == nil {
			return nil
		}
		if !isRetryable(lastErr) {
			return lastErr // non-retryable (e.g. 400 Bad Request) — fail fast
		}
		if attempt == maxAttempts-1 {
			break // last attempt failed; don't sleep before returning
		}
		wait := backoffDuration(attempt, base, capDur)
		fmt.Printf("attempt %d failed (%v); retrying in %v\n", attempt+1, lastErr, wait.Round(time.Millisecond))
		select {
		case <-time.After(wait):
		case <-ctx.Done():
			return ctx.Err()
		}
	}
	return fmt.Errorf("%w: %v", ErrMaxRetries, lastErr)
}

func main() {
	attempts := 0
	// Simulated flaky operation: fails the first two times, succeeds on the third.
	flakyOp := func(ctx context.Context) error {
		attempts++
		if attempts < 3 {
			return fmt.Errorf("transient 503 (attempt %d)", attempts)
		}
		return nil
	}

	isRetryable := func(err error) bool {
		// In real code: check HTTP status or error type — never retry 4xx.
		return err != nil && !errors.Is(err, context.Canceled)
	}

	err := withRetry(
		context.Background(),
		5,
		100*time.Millisecond,
		2*time.Second,
		isRetryable,
		flakyOp,
	)
	if err != nil {
		fmt.Println("final error:", err)
	} else {
		fmt.Printf("succeeded on attempt %d\n", attempts)
	}
}
```

<Callout kind="warn" title="The retry budget: don't let retries amplify load">

Each retry multiplies your outbound request rate. Three retries with three replicas means a single user action can produce nine calls to the downstream. Under a high-error-rate event, this is how a retry storm turns a 10% failure rate into a 100% failure rate.

**Fix:** track a *retry budget* — a cap on the total fraction of outbound calls that are retries. If more than (say) 10% of your payment calls are retries, stop retrying entirely and fail fast. The circuit breaker in the next section is the production-grade implementation of this idea.

</Callout>

<Define term="Circuit breaker (Closed / Open / Half-Open)">
A **circuit breaker** is a state machine that sits between your service and a downstream. **Closed** — normal; calls flow through and failures are counted. **Open** — the failure threshold was hit; all calls fail immediately with a sentinel error, no network call made, giving the downstream time to recover. **Half-Open** — after a cooldown, one probe call is allowed through; if it succeeds the circuit closes, if it fails the circuit re-opens. **On the job:** retrying against a genuinely down downstream wastes resources and prolongs its recovery — the circuit breaker is what turns that retry storm into a controlled pause.
</Define>

A retry loop is the right tool for *transient* failures — brief hiccups that clear on their own. But what about a downstream that is genuinely down for minutes? Retrying against it wastes resources and keeps your users waiting through three doomed attempts on every request. Worse, it prolongs the recovery of the downstream by hammering it while it's trying to come back.

The **circuit breaker** is the solution. It's a state machine that sits between your service and a downstream. When failures pile up past a threshold, it *trips* — opens the circuit — and subsequent calls fail immediately without ever hitting the downstream. After a cooldown period, it lets one probe through. If the probe succeeds, the circuit closes again. If not, it stays open.

### The Three States

<ConceptGrid cols={3}>
  <ConceptCard label="Closed (healthy)">Calls flow normally. The breaker counts failures. Below the threshold, everything passes through. This is the normal operating state.</ConceptCard>
  <ConceptCard label="Open (tripped)">The failure threshold was exceeded. All calls fail immediately with a sentinel error — no network call is made. The downstream gets breathing room to recover.</ConceptCard>
  <ConceptCard label="Half-Open (probing)">After the cooldown expires, one probe call is allowed through. If it succeeds, the circuit closes. If it fails, the circuit opens again and the cooldown resets.</ConceptCard>
  <Gotcha>Don't set the failure threshold too low or the cooldown too short. A threshold of 1 failure means a single transient error trips the breaker. A cooldown of 1 second means you're probing a downstream that's been down for 30 seconds every second — still hammering it. Start with threshold≥5, cooldown≥10s.</Gotcha>
</ConceptGrid>

### A Runnable Circuit Breaker State Machine

<GoPlayground>

```go
package main

import (
	"errors"
	"fmt"
	"sync"
	"time"
)

// State represents one of the three circuit breaker states.
type State int

const (
	StateClosed   State = iota // normal: calls flow through
	StateOpen                  // tripped: calls fail immediately
	StateHalfOpen              // probing: one call allowed through
)

func (s State) String() string {
	switch s {
	case StateClosed:
		return "CLOSED"
	case StateOpen:
		return "OPEN"
	case StateHalfOpen:
		return "HALF-OPEN"
	default:
		return "UNKNOWN"
	}
}

// ErrCircuitOpen is returned when the circuit is open and a call is rejected.
var ErrCircuitOpen = errors.New("circuit breaker open")

// CircuitBreaker is a simple three-state circuit breaker.
type CircuitBreaker struct {
	mu           sync.Mutex
	state        State
	failures     int
	threshold    int           // failures before opening
	cooldown     time.Duration // how long to stay open before half-opening
	openAt       time.Time     // when the circuit opened
}

// NewCircuitBreaker creates a breaker with the given threshold and cooldown.
func NewCircuitBreaker(threshold int, cooldown time.Duration) *CircuitBreaker {
	return &CircuitBreaker{
		state:     StateClosed,
		threshold: threshold,
		cooldown:  cooldown,
	}
}

// Call executes op through the circuit breaker.
func (cb *CircuitBreaker) Call(op func() error) error {
	cb.mu.Lock()
	switch cb.state {
	case StateOpen:
		if time.Since(cb.openAt) >= cb.cooldown {
			// Cooldown expired: allow one probe through.
			cb.state = StateHalfOpen
			fmt.Println("  [CB] → HALF-OPEN: sending probe")
		} else {
			cb.mu.Unlock()
			return ErrCircuitOpen
		}
	}
	cb.mu.Unlock()

	err := op()

	cb.mu.Lock()
	defer cb.mu.Unlock()
	if err != nil {
		cb.failures++
		if cb.state == StateHalfOpen || cb.failures >= cb.threshold {
			cb.state = StateOpen
			cb.openAt = time.Now()
			fmt.Printf("  [CB] → OPEN (failures: %d)\n", cb.failures)
		}
		return err
	}
	// Success: reset.
	cb.failures = 0
	cb.state = StateClosed
	fmt.Println("  [CB] → CLOSED: downstream healthy")
	return nil
}

func main() {
	cb := NewCircuitBreaker(3, 50*time.Millisecond)

	callDownstream := func(healthy bool) func() error {
		return func() error {
			if !healthy {
				return errors.New("downstream error")
			}
			return nil
		}
	}

	fmt.Println("--- Phase 1: failures accumulate ---")
	for range 4 {
		if err := cb.Call(callDownstream(false)); err != nil {
			fmt.Println(" call result:", err)
		}
	}

	fmt.Println("\n--- Phase 2: circuit is open, calls fast-fail ---")
	for range 2 {
		if err := cb.Call(callDownstream(false)); err != nil {
			fmt.Println(" call result:", err)
		}
	}

	fmt.Println("\n--- Phase 3: cooldown expires, probe succeeds ---")
	time.Sleep(60 * time.Millisecond) // wait for cooldown
	if err := cb.Call(callDownstream(true)); err != nil {
		fmt.Println(" probe failed:", err)
	} else {
		fmt.Println(" probe succeeded, circuit closed")
	}

	fmt.Println("\n--- Phase 4: normal calls flow again ---")
	for range 2 {
		if err := cb.Call(callDownstream(true)); err != nil {
			fmt.Println(" call result:", err)
		} else {
			fmt.Println(" call result: ok")
		}
	}
}
```

<UnderTheHood title="The circuit breaker state machine under the hood">

The circuit breaker above uses a `sync.Mutex` to protect the state transitions. This is the correct tool here: the state (`State`, `failures`, `openAt`) is **shared across goroutines** (every concurrent request consults the same breaker) and the transitions are compound operations (read state, maybe change state, update timestamp) that must be atomic. An `atomic.Int32` for `failures` alone wouldn't be enough — you'd have a TOCTOU race between reading `failures` and writing `state`.

In production libraries like [`sony/gobreaker`](https://github.com/sony/gobreaker) (the de facto standard in Go), the same mutex pattern is used, with some additions:

- **Sliding window** counting instead of a simple consecutive-failure counter, so a brief burst of errors in an otherwise-healthy service doesn't trip the breaker permanently.
- **A `OnStateChange` callback** for emitting a metrics event when the state changes — critical for dashboards and alerting.
- **Half-open call limiting**: some implementations only allow one goroutine to probe, blocking others with a semaphore so a thundering probe herd doesn't form.

As of Go 1.24, there is no circuit breaker in the standard library. `sony/gobreaker` is the common choice; it's small, dependency-free, and worth reading.

</UnderTheHood>

## Bulkhead Isolation

<Define term="Bulkhead isolation">
**Bulkhead isolation** partitions a system's concurrent capacity into isolated resource pools per downstream dependency. If one downstream slows down or crashes, it only exhausts its own dedicated bulkhead pool — preventing resource starvation from cascading to the rest of the application. **On the job:** without bulkheads, a slow third-party analytics API can tie up all 2,000 HTTP client goroutines, causing high-priority credit card checkouts to fail.
</Define>

The name comes from naval architecture: a ship is partitioned into watertight compartments called bulkheads. If the hull is breached in compartment 3, water fills compartment 3, but the bulkheads prevent water from flooding the rest of the ship. The ship stays afloat.

In a Go microservice, your shared resources are **goroutines, open TCP connections, memory, and CPU cycles**. When you make outbound HTTP, gRPC, or SQL calls, you are borrowing capacity from these shared resources.

```
Without Bulkheads (Shared Pool):
┌──────────────────────────────────────────────────────────────┐
│ All Outbound Requests (Shared Pool: 100 slots)               │
│                                                              │
│ [Analytics API (HUNG)]  ████████████████████████ 95 slots    │
│ [Payment API]           ██ 2 slots                           │
│ [New Requests]          ❌ REJECTED (Pool Exhausted!)        │
└──────────────────────────────────────────────────────────────┘

With Bulkheads (Isolated Partitions):
┌──────────────────────────────────────────────────────────────┐
│ Payment Bulkhead (Cap: 50)       [████                  ] 8  │
│ Fraud Bulkhead (Cap: 25)         [██████████            ] 10 │
│ Analytics Bulkhead (Cap: 10)     [████████████████████] 10   │
│                                   └─> Extra calls fast-fail  │
│                                       or degrade gracefully! │
└──────────────────────────────────────────────────────────────┘
```

### Semaphore-Bounded Bulkheads in Go

In languages like Java, bulkheads are often implemented using dedicated OS thread pools (e.g. Netflix Hystrix). In Go, goroutines are multiplexed by the M:N scheduler, so creating separate OS thread pools is unnecessary and counterproductive. Instead, Go implements bulkheads using **semaphore channels (`chan struct{}`)** or `golang.org/x/sync/semaphore.Weighted`.

A production Go bulkhead provides:
1. **Concurrency Limit:** Max in-flight goroutines allowed for that dependency.
2. **Bounded Queue (Optional):** Small backlog buffer before fast-failing.
3. **Execution Gating:** Non-blocking `TryAcquire()` for immediate fast-fail or `Acquire(ctx)` with a strict queue deadline.
4. **Metrics Instrumentation:** Observability into active concurrency, rejected requests, and queue wait times.

<GoPlayground>

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"sync"
	"sync/atomic"
	"time"
)

var (
	ErrBulkheadFull     = errors.New("bulkhead capacity reached: fast-failing")
	ErrBulkheadTimeout  = errors.New("bulkhead acquisition timed out")
)

// Bulkhead gates concurrency for a specific downstream dependency.
type Bulkhead struct {
	name      string
	semaphore chan struct{}
	queue     chan struct{}
	active    int64
	rejected  int64
	completed int64
}

// NewBulkhead creates an isolated capacity partition.
// maxConcurrent: max in-flight calls allowed.
// maxQueue: max pending calls allowed before fast-failing.
func NewBulkhead(name string, maxConcurrent int, maxQueue int) *Bulkhead {
	return &Bulkhead{
		name:      name,
		semaphore: make(chan struct{}, maxConcurrent),
		queue:     make(chan struct{}, maxQueue),
	}
}

// Execute runs fn within the bulkhead partition.
func (b *Bulkhead) Execute(ctx context.Context, fn func(ctx context.Context) error) error {
	// 1. Try immediate acquisition (no queuing)
	select {
	case b.semaphore <- struct{}{}:
		return b.run(ctx, fn)
	default:
	}

	// 2. Try entering the wait queue
	select {
	case b.queue <- struct{}{}:
		defer func() { <-b.queue }()
	default:
		atomic.AddInt64(&b.rejected, 1)
		return fmt.Errorf("%s: %w", b.name, ErrBulkheadFull)
	}

	// 3. Wait for a concurrency permit or context cancellation
	select {
	case b.semaphore <- struct{}{}:
		return b.run(ctx, fn)
	case <-ctx.Done():
		atomic.AddInt64(&b.rejected, 1)
		return fmt.Errorf("%s: %w (%v)", b.name, ErrBulkheadTimeout, ctx.Err())
	}
}

func (b *Bulkhead) run(ctx context.Context, fn func(ctx context.Context) error) error {
	atomic.AddInt64(&b.active, 1)
	defer func() {
		atomic.AddInt64(&b.active, -1)
		atomic.AddInt64(&b.completed, 1)
		<-b.semaphore
	}()
	return fn(ctx)
}

func (b *Bulkhead) Stats() (active, rejected, completed int64) {
	return atomic.LoadInt64(&b.active), atomic.LoadInt64(&b.rejected), atomic.LoadInt64(&b.completed)
}

func main() {
	// Bulkhead 1: Core Payment Gateway (High priority, cap 5)
	paymentBulkhead := NewBulkhead("PaymentGW", 5, 2)

	// Bulkhead 2: Third-Party Fraud Analytics (Prone to lag, cap 2, queue 1)
	analyticsBulkhead := NewBulkhead("FraudAnalytics", 2, 1)

	var wg sync.WaitGroup

	// Scenario: Analytics service slows down drastically (takes 500ms).
	// We fire 6 concurrent requests to Analytics.
	fmt.Println("=== Flooding Slow Analytics Bulkhead ===")
	for i := 1; i <= 6; i++ {
		wg.Add(1)
		go func(reqID int) {
			defer wg.Done()
			ctx, cancel := context.WithTimeout(context.Background(), 200*time.Millisecond)
			defer cancel()

			err := analyticsBulkhead.Execute(ctx, func(ctx context.Context) error {
				time.Sleep(400 * time.Millisecond) // Slow response!
				return nil
			})
			if err != nil {
				fmt.Printf("Analytics req %d: %v\n", reqID, err)
			} else {
				fmt.Printf("Analytics req %d: succeeded\n", reqID)
			}
		}(i)
	}

	// Simultaneously, critical Payment requests arrive.
	// Because Payment has its OWN bulkhead, it is NOT starved by the analytics outage!
	time.Sleep(50 * time.Millisecond)
	fmt.Println("\n=== Executing Critical Payment Requests ===")
	for i := 1; i <= 3; i++ {
		wg.Add(1)
		go func(reqID int) {
			defer wg.Done()
			ctx, cancel := context.WithTimeout(context.Background(), 200*time.Millisecond)
			defer cancel()

			err := paymentBulkhead.Execute(ctx, func(ctx context.Context) error {
				time.Sleep(20 * time.Millisecond) // Fast response
				return nil
			})
			if err != nil {
				fmt.Printf("Payment req %d: %v\n", reqID, err)
			} else {
				fmt.Printf("Payment req %d: processed successfully!\n", reqID)
			}
		}(i)
	}

	wg.Wait()

	aActive, aRej, aComp := analyticsBulkhead.Stats()
	pActive, pRej, pComp := paymentBulkhead.Stats()

	fmt.Printf("\nFinal Stats:\n")
	fmt.Printf("Analytics -> Active: %d, Rejected: %d, Completed: %d\n", aActive, aRej, aComp)
	fmt.Printf("Payment   -> Active: %d, Rejected: %d, Completed: %d\n", pActive, pRej, pComp)
}
```

</GoPlayground>

<UnderTheHood title="Bulkheads in Go: Why Channel Semaphores Beat Thread Pools">

In traditional multi-threaded runtimes (Java, C++, .NET), bulkheads require allocating distinct OS thread pools (e.g., 20 threads for Service A, 10 threads for Service B). This incurs huge overhead:
- Each OS thread costs 1–2 MB of stack memory.
- Context switching between OS threads incurs kernel transition and TLB cache invalidation overhead.

In Go's M:N runtime:
- Goroutines are multiplexed across `GOMAXPROCS` OS threads.
- A channel semaphore (`chan struct{}`) costs only the channel allocation (~96 bytes) and uses Go's internal runtime wait-queue (`sudog`).
- Blocked goroutines park without consuming OS threads or CPU cycles.

Therefore, you can comfortably create hundreds of granular bulkheads across a large Go service mesh with near-zero memory footprint.

</UnderTheHood>

## Graceful Degradation and Fallback Caches

<Define term="Graceful degradation & stale fallback cache">
**Graceful degradation** is the architectural practice of maintaining partial service functionality when dependencies fail. A **stale fallback cache** stores the last known successful response from an upstream dependency with an extended stale-grace TTL; when the dependency fails or its circuit breaker opens, the system serves the cached stale data rather than returning an error. **On the job:** if Meridian's currency conversion API goes down, the checkout service serves exchange rates cached 15 minutes ago (flagged as degraded) instead of aborting customer purchases.
</Define>

When an upstream dependency fails, times out, or trips an open circuit breaker, you have three options:
1. **Hard Failure (Fail-Stop):** Return an HTTP 500 / 503 error to the client. This breaks user journeys.
2. **Feature Omission (Silent Drop):** Return the response without the failed component (e.g. render user profile without the "recommended friends" sidebar).
3. **Stale Fallback Caching (Serve Stale):** Serve the most recently cached valid response stamped with `stale: true` metadata.

```
Incoming Request
      │
      ▼
┌───────────────┐        Cache HIT (Age < FreshTTL)
│ Check Cache   ├─────────────────────────────────────────> Return Fresh Data
└───────┬───────┘
        │ Cache MISS or Expired
        ▼
┌───────────────┐      Circuit CLOSED & HTTP 200
│ Call Upstream ├─────────────────────────────────────────> Cache & Return New
└───────┬───────┘
        │ Upstream FAILED or Circuit OPEN
        ▼
┌──────────────────┐     Entry exists (Age < StaleGraceTTL)
│ Fallback Cache   ├──────────────────────────────────────> Return Stale Data (Degraded: true)
└───────┬──────────┘
        │ No cached entry
        ▼
   Return Error (503 Service Unavailable)
```

### Stale-While-Revalidate Dual-TTL Architecture

A resilient fallback cache uses two distinct TTL thresholds:
- **`freshTTL` (e.g. 1 minute):** Within this window, cached data is considered completely fresh and returned immediately without contacting upstream.
- **`staleGraceTTL` (e.g. 24 hours):** Beyond `freshTTL`, the data is stale. Normal requests will attempt to fetch fresh data from upstream. But if upstream fails, times out, or the circuit breaker is OPEN, the cache falls back to serving this stale data.

<GoPlayground>

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"sync"
	"time"
)

var (
	ErrUpstreamDown = errors.New("upstream service unavailable")
	ErrCacheMiss    = errors.New("no cached data available")
)

type CacheItem[T any] struct {
	Value     T
	UpdatedAt time.Time
}

type StaleFallbackCache[K comparable, V any] struct {
	mu            sync.RWMutex
	items         map[K]CacheItem[V]
	freshTTL      time.Duration
	staleGraceTTL time.Duration
}

func NewStaleFallbackCache[K comparable, V any](freshTTL, staleGraceTTL time.Duration) *StaleFallbackCache[K, V] {
	return &StaleFallbackCache[K, V]{
		items:         make(map[K]CacheItem[V]),
		freshTTL:      freshTTL,
		staleGraceTTL: staleGraceTTL,
	}
}

func (c *StaleFallbackCache[K, V]) Set(key K, val V) {
	c.mu.Lock()
	defer c.mu.Unlock()
	c.items[key] = CacheItem[V]{
		Value:     val,
		UpdatedAt: time.Now(),
	}
}

// Get evaluates fresh vs stale availability.
// Returns (value, isStale, found).
func (c *StaleFallbackCache[K, V]) Get(key K) (val V, isStale bool, found bool) {
	c.mu.RLock()
	defer c.mu.RUnlock()

	item, exists := c.items[key]
	if !exists {
		return val, false, false
	}

	age := time.Since(item.UpdatedAt)
	if age <= c.freshTTL {
		return item.Value, false, true // Fresh
	}
	if age <= c.staleGraceTTL {
		return item.Value, true, true // Stale fallback eligible
	}
	return val, false, false // Expired past grace period
}

// ExchangeRateService fetches rates with resilient fallback caching.
type ExchangeRateService struct {
	cache       *StaleFallbackCache[string, float64]
	circuitOpen bool
	mu          sync.Mutex
}

func NewExchangeRateService() *ExchangeRateService {
	return &ExchangeRateService{
		// Fresh for 200ms, fallback grace for 5 seconds
		cache: NewStaleFallbackCache[string, float64](200*time.Millisecond, 5*time.Second),
	}
}

func (s *ExchangeRateService) SetSimulatedOutage(open bool) {
	s.mu.Lock()
	defer s.mu.Unlock()
	s.circuitOpen = open
}

func (s *ExchangeRateService) fetchUpstream(ctx context.Context, currency string) (float64, error) {
	s.mu.Lock()
	open := s.circuitOpen
	s.mu.Unlock()

	if open {
		return 0, ErrUpstreamDown
	}
	// Normal simulated rate
	return 1.0850, nil // EUR/USD
}

func (s *ExchangeRateService) GetRate(ctx context.Context, currency string) (rate float64, degraded bool, err error) {
	// 1. Check fresh cache
	val, isStale, found := s.cache.Get(currency)
	if found && !isStale {
		return val, false, nil
	}

	// 2. Attempt upstream call
	freshVal, err := s.fetchUpstream(ctx, currency)
	if err == nil {
		s.cache.Set(currency, freshVal)
		return freshVal, false, nil
	}

	// 3. Upstream failed: check if stale fallback is available
	if found && isStale {
		fmt.Printf("  [Degradation] Upstream failed (%v). Serving stale cached rate.\n", err)
		return val, true, nil
	}

	// 4. No cache exists and upstream failed: hard error
	return 0, false, fmt.Errorf("failed to fetch rate: %w", err)
}

func main() {
	svc := NewExchangeRateService()
	ctx := context.Background()

	// Step 1: Initial fetch (populates cache)
	rate, degraded, err := svc.GetRate(ctx, "EUR")
	fmt.Printf("1. Initial fetch: Rate=%.4f (Degraded=%v, Err=%v)\n", rate, degraded, err)

	// Step 2: Immediate second fetch (served from fresh cache)
	rate, degraded, err = svc.GetRate(ctx, "EUR")
	fmt.Printf("2. Cached fetch:  Rate=%.4f (Degraded=%v, Err=%v)\n", rate, degraded, err)

	// Step 3: Wait until freshTTL expires (250ms), and simulate upstream outage!
	time.Sleep(250 * time.Millisecond)
	svc.SetSimulatedOutage(true)
	fmt.Println("\n--- Upstream Outage Occurred (Circuit Breaker Tripped) ---")

	// Step 4: Fetch during outage -> Serves stale fallback
	rate, degraded, err = svc.GetRate(ctx, "EUR")
	fmt.Printf("3. Outage fetch:  Rate=%.4f (Degraded=%v, Err=%v)\n", rate, degraded, err)

	// Step 5: Restore upstream
	svc.SetSimulatedOutage(false)
```

## Graceful Shutdown

<Define term="Graceful shutdown">
**Graceful shutdown** means stopping a service in an ordered way: stop accepting new work, finish work already in progress, then release resources and exit. The alternative — an abrupt exit on `SIGTERM` — sends a TCP RST to every in-flight connection, which the caller sees as an error. **On the job:** a checkout service that exits immediately on deploy drops every payment in flight; graceful shutdown is the difference between zero dropped requests and a spike of 503s in your error budget on every deploy.
</Define>

Your service is running. You push a new version. Kubernetes sends `SIGTERM`. If your binary exits immediately, every in-flight request gets a TCP RST — the user sees an error. That's not acceptable for a checkout flow. **Graceful shutdown** means: stop accepting new work, finish the work already in progress, then exit.

The pattern has four ordered steps:

1. **Receive the signal** — `signal.NotifyContext` gives you a context that's cancelled when `SIGTERM` or `SIGINT` arrives.
2. **Stop accepting new requests** — call `server.Shutdown(ctx)`. This closes the listener so no new TCP connections are accepted.
3. **Drain in-flight requests** — `server.Shutdown` waits for active requests to complete (up to the shutdown timeout).
4. **Release resources in reverse order** — close the DB pool, flush metrics, etc. Last opened, first closed.

```go
// cmd/checkout/main.go — complete graceful shutdown skeleton
package main

import (
	"context"
	"log/slog"
	"net/http"
	"os"
	"os/signal"
	"syscall"
	"time"
)

func main() {
	// signal.NotifyContext cancels ctx on SIGINT or SIGTERM.
	ctx, stop := signal.NotifyContext(context.Background(), syscall.SIGINT, syscall.SIGTERM)
	defer stop()

	mux := http.NewServeMux()
	mux.HandleFunc("/checkout", checkoutHandler)

	srv := &http.Server{
		Addr:         ":8080",
		Handler:      mux,
		ReadTimeout:  5 * time.Second,
		WriteTimeout: 10 * time.Second,
		IdleTimeout:  120 * time.Second,
	}

	// Serve in a goroutine so main can wait for the signal.
	go func() {
		slog.Info("server listening", "addr", srv.Addr)
		if err := srv.ListenAndServe(); err != http.ErrServerClosed {
			slog.Error("server error", "err", err)
			os.Exit(1)
		}
	}()

	// Block until SIGTERM/SIGINT arrives.
	<-ctx.Done()
	slog.Info("shutdown signal received; draining...")

	// Give in-flight requests 30 seconds to complete.
	shutdownCtx, cancel := context.WithTimeout(context.Background(), 30*time.Second)
	defer cancel()

	if err := srv.Shutdown(shutdownCtx); err != nil {
		slog.Error("forced shutdown", "err", err)
	}

	// Release other resources in reverse-open order.
	// db.Close()
	// redisClient.Close()
	slog.Info("shutdown complete")
}

func checkoutHandler(w http.ResponseWriter, r *http.Request) {
	// A real handler; in-flight when SIGTERM arrives, it will complete.
	w.WriteHeader(http.StatusOK)
}
```

<Callout kind="pro" title="Set ReadTimeout and WriteTimeout on every http.Server">

An `http.Server` with no timeouts is the server-side equivalent of `http.DefaultClient`. A misbehaving client that sends a request header 1 byte at a time holds a goroutine and a connection open forever. `ReadHeaderTimeout` (the most important one — cap how long you'll wait for headers), `ReadTimeout`, `WriteTimeout`, and `IdleTimeout` are all load-bearing fields, not optional extras.

<Gotcha title="srv.Shutdown does NOT drain your background goroutines">

Here's the trap that bites teams who think they've nailed graceful shutdown. `srv.Shutdown(ctx)` drains *in-flight HTTP requests* — and nothing else. Say a checkout handler returns `202 Accepted` to the customer and fires the welcome email (or the audit webhook) off into a background goroutine to keep the response fast. The instant the HTTP response is written, that request is no longer "in-flight" as far as `Shutdown` is concerned. It returns, your `main` releases resources and exits — and the half-sent email goroutine is killed mid-flight. The customer exists in your DB but never gets their email.

The fix: launch every async task through a shared `sync.WaitGroup`, then **after** `srv.Shutdown(ctx)` returns, call `wg.Wait()` before exiting — so HTTP requests drain first, *then* the background senders finish. The ordered shutdown becomes: signal → stop listener → drain HTTP → wait for background goroutines → release resources → exit.

</Gotcha>

<GoPlayground>

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"time"
)

// background: every async task (welcome email, webhook) is launched through
// here so the WaitGroup can track it and shutdown can wait for it.
func background(wg *sync.WaitGroup, name string, work func()) {
	wg.Add(1)
	go func() {
		defer wg.Done()
		work()
		fmt.Println("  background task finished:", name)
	}()
}

func main() {
	var wg sync.WaitGroup

	// A real handler kicked off two async senders just before the signal hit.
	background(&wg, "welcome-email", func() { time.Sleep(40 * time.Millisecond) })
	background(&wg, "audit-webhook", func() { time.Sleep(70 * time.Millisecond) })

	// Simulate SIGTERM: signal.NotifyContext would cancel this ctx for real.
	ctx, stop := context.WithCancel(context.Background())
	stop() // "signal" arrives
	<-ctx.Done()
	fmt.Println("1. signal received; stop accepting new requests")

	// srv.Shutdown(ctx) drains in-flight HTTP requests. Simulated here.
	fmt.Println("2. srv.Shutdown: in-flight HTTP requests drained")

	// Shutdown does NOT wait for background goroutines — we must.
	fmt.Println("3. waiting for background senders...")
	wg.Wait()

	fmt.Println("4. clean exit")
}
```

Use `wg.Add(1)`/`defer wg.Done()` (shown above) for portability; `sync.WaitGroup.Go` arrived in Go 1.25.

## Health and Readiness

<Define term="Health check (liveness) and readiness check">
A **liveness check** (`/healthz`) answers "is this process alive?" — it should be fast, cheap, and check only the process itself. Kubernetes kills and restarts the container if liveness fails. A **readiness check** (`/readyz`) answers "is this instance ready to serve traffic?" — it should verify external dependencies (DB, cache). Kubernetes removes the pod from the load balancer pool if readiness fails, with no restart. **On the job:** conflating liveness and readiness — putting a DB ping on `/healthz` — causes Kubernetes to restart your pod every time the database hiccups, turning a brief DB slowdown into cascading pod restarts.
</Define>

You have two endpoints to build: `/healthz` (liveness) and `/readyz` (readiness). They sound similar. They do completely different jobs, and conflating them is one of the most common Kubernetes foot-guns I've seen — and I've seen a lot.

### Liveness vs. Readiness

**Liveness** (`/healthz`): "Is this process alive and not stuck in a deadlock or infinite loop?" If liveness fails, Kubernetes kills and restarts the container. The check must be **fast, cheap, and almost never fail** — a failed liveness check is a hard restart with potential request loss. It should check the process itself, not external dependencies.

**Readiness** (`/readyz`): "Is this instance ready to receive traffic?" If readiness fails, Kubernetes removes the pod from the load balancer's backend pool. The check *should* verify that dependencies (DB, cache) are reachable. A failed readiness check is gentle — no restart, just traffic rerouting.

## Idempotency

<Define term="Idempotency" since="Idempotency & Exactly-Once Semantics (Part 3)">
An operation is **idempotent** if executing it twice produces the same result as executing it once. A `GET /orders/123` is naturally idempotent — reading changes nothing. A `POST /charge` is not — sending it twice charges the customer twice. An **idempotency key** is a unique token the client generates once and attaches to the request; the server stores the result against the key and returns the stored result on any duplicate request instead of re-executing. **On the job:** without idempotency keys, every retry of a failed payment is a potential double-charge — networks always retry, so you must design writes to survive being sent more than once.
</Define>

Here's a scenario: the customer clicks "Pay." Your service posts to the payment processor. The network hiccups on the response. Did the charge go through? You don't know. If you retry the `POST /charge` naively, you might charge the customer twice.

The solution is an **idempotency key** — a unique token the client generates and sends with the request. The server stores it alongside the result. If the same key arrives again (a retry), the server returns the stored result without re-executing the operation.

```go
// POST /charge with an idempotency key header.
// The key is generated by the caller (a UUID), not the server.
req.Header.Set("Idempotency-Key", "ord_9f2a-user_42-ts_1716480000")
```

The deep implementation — how to store keys with atomic upsert, how to handle concurrent duplicate requests, the expiry window, and how this integrates with the transactional outbox — lives in **Part 3 (Idempotency & Exactly-Once Semantics)**. What belongs here is the pattern: **before you add retries to any write operation, add an idempotency key.** The retry loop and the idempotency key are a pair — one without the other is incomplete.

<Callout kind="warn" title="Idempotency keys belong on the client, not the server">

The server stores and honors idempotency keys. The *client* generates them — once, before the first attempt — and reuses the same key on every retry of the same logical operation. If the server auto-generates a new key per request, retries will get new keys and the protection is lost.

</Callout>

## Rate Limiting in Depth

<Define term="Rate limiting — token bucket vs leaky bucket">
**Rate limiting** caps how many requests a caller (or the whole service) can make in a time window, protecting capacity from a single bad actor or burst. **Token bucket:** a bucket holds up to N tokens; each request consumes one; tokens refill at a fixed rate. It allows short bursts (draining the bucket) then enforces the fill rate — this is what `golang.org/x/time/rate` implements. **Leaky bucket:** requests queue up and exit at a fixed constant rate regardless of arrival — useful for smoothing output to a downstream that can't absorb bursts. **On the job:** without per-client rate limits, a single misbehaving API key can saturate your entire connection pool and take down the service for everyone else.
</Define>

Rate limiting answers the question: "how do I prevent one caller from consuming all available capacity?" The choice of algorithm dictates how your service behaves during bursts, how much memory is consumed per active client key, and whether rate limiting remains accurate across multi-replica clusters.

### Algorithm Comparison Matrix

| Algorithm | Memory per Key | CPU Cost | Burst Handling | Boundary Spike Risk | Primary Use Case |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **Token Bucket** | $O(1)$ (~32 bytes) | $O(1)$ (lazy time math) | Allows bursts up to bucket capacity $B$ | None (continuous refill) | Inbound API gateway protection, client quotas |
| **Leaky Bucket** | $O(1)$ (~24 bytes) | $O(1)$ (scheduled delay) | Zero burst (strictly meters output rate) | None (uniform spacing) | Outbound traffic shaping to sensitive/legacy APIs |
| **Fixed Window** | $O(1)$ (~8 bytes) | $O(1)$ (atomic increment) | Resets at boundary | High (2× burst at window edge) | Simple bulk DDoS damping, coarse metrics |
| **Sliding Window Log** | $O(N)$ (stores $N$ timestamps) | $O(\log N)$ (sorted set range) | Enforces exact rate limit over rolling window | Zero (mathematically exact) | High-stakes fintech limits (e.g. max 5 transfers/min) |
| **Sliding Window Counter** | $O(1)$ (2 counter integers) | $O(1)$ (weighted multiplication) | Smooth sliding blend | Low (under 0.05% variance) | High-throughput distributed rate limiting in Redis |

### 1. Token Bucket: Standard vs. Custom In-Memory

The **Token Bucket** algorithm models a bucket of capacity $B$ that accumulates tokens at rate $R$ tokens/second. A request consumes 1 token. If the bucket is empty, the request is rejected or queued.

<GoPlayground>

```go
package main

import (
	"context"
	"fmt"
	"math"
	"sync"
	"time"

	"golang.org/x/time/rate"
)

// CustomTokenBucket implements a zero-goroutine, nanosecond-precision token bucket.
type CustomTokenBucket struct {
	mu           sync.Mutex
	rate         float64   // tokens added per second
	capacity     float64   // maximum burst capacity
	tokens       float64   // current available tokens
	lastRefilled time.Time // last calculation timestamp
}

func NewCustomTokenBucket(ratePerSec float64, burstCap float64) *CustomTokenBucket {
	return &CustomTokenBucket{
		rate:         ratePerSec,
		capacity:     burstCap,
		tokens:       burstCap, // starts completely full
		lastRefilled: time.Now(),
	}
}

// refill calculates virtual token accumulation based on elapsed nanoseconds.
// Must be called with tb.mu held.
func (tb *CustomTokenBucket) refill(now time.Time) {
	elapsed := now.Sub(tb.lastRefilled).Seconds()
	tb.lastRefilled = now
	tb.tokens = math.Min(tb.capacity, tb.tokens+(elapsed*tb.rate))
}

// Allow attempts to consume 1 token immediately (non-blocking).
func (tb *CustomTokenBucket) Allow() bool {
	return tb.AllowN(time.Now(), 1.0)
}

// AllowN attempts to consume n tokens at time 'now'.
func (tb *CustomTokenBucket) AllowN(now time.Time, n float64) bool {
	tb.mu.Lock()
	defer tb.mu.Unlock()

	tb.refill(now)
	if tb.tokens >= n {
		tb.tokens -= n
		return true
	}
	return false
}

// Wait blocks until 1 token is available or context is cancelled.
func (tb *CustomTokenBucket) Wait(ctx context.Context) error {
	for {
		tb.mu.Lock()
		now := time.Now()
		tb.refill(now)

		if tb.tokens >= 1.0 {
			tb.tokens -= 1.0
			tb.mu.Unlock()
			return nil
		}

		// Calculate sleep time needed to accrue 1 full token
		missing := 1.0 - tb.tokens
		sleepDur := time.Duration((missing / tb.rate) * float64(time.Second))
		tb.mu.Unlock()

		timer := time.NewTimer(sleepDur)
		select {
		case <-ctx.Done():
			timer.Stop()
			return ctx.Err()
		case <-timer.C:
		}
	}
}

func main() {
	fmt.Println("=== 1. Custom In-Memory Token Bucket ===")
	// 5 tokens/sec, max burst of 3
	tb := NewCustomTokenBucket(5, 3)

	for i := 1; i <= 5; i++ {
		if tb.Allow() {
			fmt.Printf("Req %d: ALLOWED\n", i)
		} else {
			fmt.Printf("Req %d: REJECTED (bucket empty)\n", i)
		}
	}

	time.Sleep(300 * time.Millisecond) // refills ~1.5 tokens
	fmt.Printf("After 300ms pause -> Allow: %v\n", tb.Allow())

	fmt.Println("\n=== 2. golang.org/x/time/rate Standard Limiter ===")
	stdLimiter := rate.NewLimiter(rate.Limit(10), 2)
	for i := 1; i <= 4; i++ {
		fmt.Printf("Standard limiter req %d: %v\n", i, stdLimiter.Allow())
	}
}
```

</GoPlayground>

<UnderTheHood title="How x/time/rate and Custom Token Buckets eliminate background goroutines">

A naive token bucket implementation might launch a background goroutine with `time.NewTicker` to add tokens every millisecond. With 100,000 active API keys, that would spawn 100,000 tickers waking up the Go runtime scheduler millions of times per second.

Instead, both `x/time/rate` and our custom bucket use **lazy arithmetic evaluation**:
```
newTokens = rate * (now - lastRefilled)
tokens    = min(capacity, tokens + newTokens)
```
On every invocation of `Allow()` or `Wait()`, the current timestamp is recorded, the delta time is computed, and tokens are updated synchronously under a `sync.Mutex`. If a key remains idle for an hour, zero CPU cycles are spent — when the client finally calls again, the math instantly computes `tokens = capacity`.

</UnderTheHood>

### 2. Leaky Bucket: Egress Traffic Shaping

While Token Bucket controls *inbound burst capacity*, **Leaky Bucket** controls *outbound spacing*. It guarantees that requests leave at a constant, uniform rate $\Delta t = 1/R$, completely flattening any burst.

**On the job:** Meridian integrates with an older card-network settlement mainframe that hard-crashes if it receives more than 5 requests in any 100ms interval. A token bucket with burst=5 would let all 5 through in 1ms. A Leaky Bucket Shaper forces exactly 20ms between outbound requests, protecting the downstream mainframe.

<GoPlayground>

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"time"
)

// LeakyBucketShaper shapes egress traffic to a constant rate (fixed time interval).
type LeakyBucketShaper struct {
	mu          sync.Mutex
	interval    time.Duration // Time between consecutive releases: 1 / rate
	lastRelease time.Time
}

func NewLeakyBucketShaper(ratePerSec float64) *LeakyBucketShaper {
	return &LeakyBucketShaper{
		interval:    time.Duration(float64(time.Second) / ratePerSec),
		lastRelease: time.Now(),
	}
}

// Take blocks until the exact scheduled egress timestamp is reached.
func (lb *LeakyBucketShaper) Take(ctx context.Context) error {
	lb.mu.Lock()
	now := time.Now()

	// If idle and lastRelease is in past, reset schedule to now
	if lb.lastRelease.Before(now) {
		lb.lastRelease = now
	}

	// Schedule the next slot strictly at lastRelease + interval
	nextSlot := lb.lastRelease.Add(lb.interval)
	lb.lastRelease = nextSlot
	sleepDur := time.Until(nextSlot)
	lb.mu.Unlock()

	if sleepDur <= 0 {
		return nil
	}

	timer := time.NewTimer(sleepDur)
	defer timer.Stop()

	select {
	case <-ctx.Done():
		return ctx.Err()
	case <-timer.C:
		return nil
	}
}

func main() {
	// Shape traffic to exactly 5 requests/sec (1 request every 200ms)
	shaper := NewLeakyBucketShaper(5)
	ctx := context.Background()

	start := time.Now()
	fmt.Println("Dispatching 4 bursty requests through Leaky Bucket Shaper:")
	for i := 1; i <= 4; i++ {
		_ = shaper.Take(ctx)
		fmt.Printf("Req %d dispatched at +%v (strictly spaced)\n", i, time.Since(start).Round(time.Millisecond))
	}
}
```

### 3. Sliding Window Log vs. Sliding Window Counter

Fixed-window limiters suffer from a severe **boundary double-burst vulnerability**: if a client is allowed 100 req/min, they can send 100 requests at 00:59 and 100 requests at 01:01 — totaling 200 requests within a 2-second interval without violating either fixed window.

Two sliding window algorithms solve this problem:

```
Fixed Window Spike (200 requests in 2 seconds):
Window 1 [00:00 - 01:00]          Window 2 [01:00 - 02:00]
                     ████ (100)  │  ████ (100)
─────────────────────────────────┼──────────────────────────────
                              00:59 01:01

Sliding Window (Rolling 60s window eliminates the boundary):
                [───── Rolling 60s Window (Max 100) ─────]
                                 ████  ████ ❌ REJECTED!
```

#### Sliding Window Log (Exact Timestamp Tracking)

The **Sliding Window Log** maintains a list of timestamps for every request made within the rolling window. On each request:
1. Evict timestamps older than `now - windowSize`.
2. If remaining count is less than `limit`, append `now` and allow; else reject.

**Pros:** 100% mathematically exact; zero edge anomalies.  
**Cons:** High memory overhead ($O(N)$ entries per active user).

In Redis, this is implemented using a **Sorted Set (`ZSET`)** and executed via an atomic Lua script:

```lua
-- sliding_window_log.lua
-- KEYS[1] = "rl:log:user:42"
-- ARGV[1] = current timestamp (unix epoch in ms)
-- ARGV[2] = window size in ms (e.g. 60000 for 1 minute)
-- ARGV[3] = max requests allowed in window
local key = KEYS[1]
local now = tonumber(ARGV[1])
local window = tonumber(ARGV[2])
local limit = tonumber(ARGV[3])
local clearBefore = now - window

-- 1. Evict timestamps older than the sliding cutoff
redis.call("ZREMRANGEBYSCORE", key, "-inf", clearBefore)

-- 2. Count current elements in window
local currentCount = redis.call("ZCARD", key)

-- 3. Check limit and record timestamp
if currentCount < limit then
    redis.call("ZADD", key, now, now .. ":" .. math.random(100000))
    redis.call("PEXPIRE", key, window)
    return 1 -- Allowed
else
    return 0 -- Rejected
end
```

#### Sliding Window Counter (Memory-Optimized Weighted Average)

Instead of storing individual timestamps, the **Sliding Window Counter** divides time into fixed windows and estimates the rolling request count using a **weighted average**:

```
Estimated Count = (Previous Window Count * (Window Size - Time into Current Window) / Window Size) + Current Window Count
```

**Pros:** Constant $O(1)$ memory per key (only 2 integers stored!).  
**Cons:** Small mathematical approximation assuming uniform request distribution in the previous window (under 0.05% variance in production).

In Redis, this is implemented using two simple string keys with atomic Lua execution:

```lua
-- sliding_window_counter.lua
-- KEYS[1] = current window key (e.g. "rl:cnt:user:42:1700000060")
-- KEYS[2] = previous window key (e.g. "rl:cnt:user:42:1700000000")
-- ARGV[1] = window size in seconds (e.g. 60)
-- ARGV[2] = weight of previous window (fraction 0.0 to 1.0)
-- ARGV[3] = max requests allowed
local curr_key = KEYS[1]
local prev_key = KEYS[2]
local window = tonumber(ARGV[1])
local weight = tonumber(ARGV[2])
local limit = tonumber(ARGV[3])

local prev_count = tonumber(redis.call("GET", prev_key) or "0")
local curr_count = tonumber(redis.call("GET", curr_key) or "0")

local estimated = math.floor(prev_count * weight) + curr_count
if estimated < limit then
    local new_count = redis.call("INCR", curr_key)
    if new_count == 1 then
        redis.call("EXPIRE", curr_key, window * 2)
    end
    return 1 -- Allowed
else
    return 0 -- Rejected
end
```

Here is a side-by-side runnable Go implementation comparing both Sliding Window Log and Sliding Window Counter:

<GoPlayground>

```go
package main

import (
	"fmt"
	"sync"
	"time"
)

// SlidingWindowLog maintains exact timestamps in memory (O(N) space).
type SlidingWindowLog struct {
	mu         sync.Mutex
	window     time.Duration
	limit      int
	timestamps []time.Time
}

func NewSlidingWindowLog(window time.Duration, limit int) *SlidingWindowLog {
	return &SlidingWindowLog{window: window, limit: limit}
}

func (s *SlidingWindowLog) Allow() bool {
	s.mu.Lock()
	defer s.mu.Unlock()

	now := time.Now()
	cutoff := now.Add(-s.window)

	valid := s.timestamps[:0]
	for _, t := range s.timestamps {
		if t.After(cutoff) {
			valid = append(valid, t)
		}
	}
	s.timestamps = valid

	if len(s.timestamps) < s.limit {
		s.timestamps = append(s.timestamps, now)
		return true
	}
	return false
}

// SlidingWindowCounter approximates moving window counts in O(1) space.
type SlidingWindowCounter struct {
	mu         sync.Mutex
	window     time.Duration
	limit      int64
	currWindow int64
	currCount  int64
	prevCount  int64
}

func NewSlidingWindowCounter(window time.Duration, limit int64) *SlidingWindowCounter {
	return &SlidingWindowCounter{window: window, limit: limit}
}

func (s *SlidingWindowCounter) Allow() bool {
	s.mu.Lock()
	defer s.mu.Unlock()

	now := time.Now()
	windowNanos := s.window.Nanoseconds()
	currentWindowIdx := now.UnixNano() / windowNanos

	if currentWindowIdx > s.currWindow {
		if currentWindowIdx == s.currWindow+1 {
			s.prevCount = s.currCount
		} else {
			s.prevCount = 0
		}
		s.currCount = 0
		s.currWindow = currentWindowIdx
	}

	offset := now.UnixNano() % windowNanos
	weight := float64(windowNanos-offset) / float64(windowNanos)
	estimated := int64(float64(s.prevCount)*weight) + s.currCount

	if estimated < s.limit {
		s.currCount++
		return true
	}
	return false
}

func main() {
	// Window: 100ms, Limit: 3 requests
	logLimiter := NewSlidingWindowLog(100*time.Millisecond, 3)
	cntLimiter := NewSlidingWindowCounter(100*time.Millisecond, 3)

	fmt.Println("=== Testing Sliding Window Log (Exact) ===")
	for i := 1; i <= 5; i++ {
		fmt.Printf("Req %d -> Allowed: %v\n", i, logLimiter.Allow())
	}

	fmt.Println("\n=== Testing Sliding Window Counter (Weighted O(1)) ===")
	for i := 1; i <= 5; i++ {
		fmt.Printf("Req %d -> Allowed: %v\n", i, cntLimiter.Allow())
	}
}
```

### Per-Key Rate Limiting with TTL Eviction

In production systems handling millions of distinct API keys, IP addresses, or account IDs, storing limiters in a plain `map[string]*rate.Limiter` causes an **unbounded memory leak** because stale keys from one-off callers never get deleted.

A production per-key limiter tracks access timestamps and runs a background sweeper to evict inactive limiters:

<GoPlayground>

```go
package main

import (
	"fmt"
	"sync"
	"time"

	"golang.org/x/time/rate"
)

type keyEntry struct {
	limiter  *rate.Limiter
	lastSeen time.Time
}

// TTLPerKeyLimiter prevents memory leaks by automatically sweeping stale keys.
type TTLPerKeyLimiter struct {
	mu            sync.Mutex
	entries       map[string]*keyEntry
	r             rate.Limit
	b             int
	ttl           time.Duration
	stopClean     chan struct{}
}

func NewTTLPerKeyLimiter(r rate.Limit, b int, ttl time.Duration, sweepInterval time.Duration) *TTLPerKeyLimiter {
	lim := &TTLPerKeyLimiter{
		entries:   make(map[string]*keyEntry),
		r:         r,
		b:         b,
		ttl:       ttl,
		stopClean: make(chan struct{}),
	}
	go lim.cleanupLoop(sweepInterval)
	return lim
}

func (l *TTLPerKeyLimiter) Allow(key string) bool {
	l.mu.Lock()
	defer l.mu.Unlock()

	entry, exists := l.entries[key]
	if !exists {
		entry = &keyEntry{
			limiter: rate.NewLimiter(l.r, l.b),
		}
		l.entries[key] = entry
	}
	entry.lastSeen = time.Now()
	return entry.limiter.Allow()
}

func (l *TTLPerKeyLimiter) cleanupLoop(interval time.Duration) {
	ticker := time.NewTicker(interval)
	defer ticker.Stop()
	for {
		select {
		case <-l.stopClean:
			return
		case <-ticker.C:
			l.mu.Lock()
			cutoff := time.Now().Add(-l.ttl)
			for k, entry := range l.entries {
				if entry.lastSeen.Before(cutoff) {
					delete(l.entries, k)
				}
			}
			l.mu.Unlock()
		}
	}
}

func (l *TTLPerKeyLimiter) Stop() {
	close(l.stopClean)
}

func main() {
	// 2 req/s per key, burst 2, key TTL 100ms, sweep every 50ms
	limiter := NewTTLPerKeyLimiter(rate.Limit(2), 2, 100*time.Millisecond, 50*time.Millisecond)
	defer limiter.Stop()

	fmt.Printf("API Key 1 (Attempt 1): Allowed=%v\n", limiter.Allow("key_1"))
	fmt.Printf("API Key 1 (Attempt 2): Allowed=%v\n", limiter.Allow("key_1"))
	fmt.Printf("API Key 1 (Attempt 3): Allowed=%v (Burst exhausted)\n", limiter.Allow("key_1"))

	fmt.Printf("API Key 2 (Attempt 1): Allowed=%v (Separate quota)\n", limiter.Allow("key_2"))

	// Wait for TTL expiration
	time.Sleep(160 * time.Millisecond)
	fmt.Printf("\nAfter TTL sweep -> Inactive keys evicted from memory safely.\n")
}
```

<Callout kind="note" title="When distributed rate limiting is actually needed">

Don't reach for Redis rate limiting before you need it. A single Go service with a per-process `x/time/rate` or in-memory sliding window limiter handles **millions of requests per second** — it's fast, zero-dependency, and correct for a single instance. You only need distributed limiting when:

1. You run multiple replicas and the per-key quota must be enforced globally across all of them.
2. You need rate limit state to survive service restarts and deployments.
3. Different services in your mesh share a unified quota pool (e.g. both the API gateway and the background webhook worker consume the same customer API quota).

In fintech fraud prevention (such as "no user may initiate more than 5 wire transfers per minute"), Redis Sliding Window Counter is mandatory because transfer requests may hit any replica.

</Callout>

<Exercise n={2} title="Backoff calculator" level="easy">

Implement `ExponentialBackoff(attempt int, base, cap time.Duration) time.Duration` that returns a full-jitter backoff duration. `attempt` is zero-indexed (0 = first retry). The result must be in the range `[0, min(base*2^attempt, cap))`. Write a `main` that prints the duration for attempts 0 through 4 with `base=100ms` and `cap=2s`.

<Solution>

```go
package main

import (
	"fmt"
	"math/rand/v2"
	"time"
)

func ExponentialBackoff(attempt int, base, cap time.Duration) time.Duration {
	shift := attempt
	if shift > 30 {
		shift = 30
	}
	exp := base << shift
	if exp > cap {
		exp = cap
	}
	return time.Duration(rand.N(int64(exp)))
}

func main() {
	base := 100 * time.Millisecond
	capDur := 2 * time.Second
	for i := range 5 {
		d := ExponentialBackoff(i, base, capDur)
		fmt.Printf("attempt %d: wait up to %v, got %v\n",
			i, min(base<<i, capDur).Round(time.Millisecond),
			d.Round(time.Millisecond))
	}
}
```

`base << attempt` is equivalent to `base * 2^attempt` using a bit-shift, which avoids `math.Pow` and floating-point. `rand.N` (Go 1.22+) is goroutine-safe with no seeding required.

<Exercise n={3} title="Circuit breaker with state log" level="medium">

Extend the `CircuitBreaker` from the chapter so it records a `[]StateChange` (each with a `From`, `To` `State`, and `At time.Time`). Add a `StateHistory() []StateChange` method. Write a test scenario that drives the breaker through Closed → Open → Half-Open → Closed and asserts the history has exactly 3 transitions.

<Solution>

```go
package main

import (
	"errors"
	"fmt"
	"sync"
	"time"
)

type State int

const (
	StateClosed State = iota
	StateOpen
	StateHalfOpen
)

func (s State) String() string {
	return [...]string{"CLOSED", "OPEN", "HALF-OPEN"}[s]
}

var ErrCircuitOpen = errors.New("circuit open")

type StateChange struct {
	From, To State
	At       time.Time
}

type CircuitBreaker struct {
	mu        sync.Mutex
	state     State
	failures  int
	threshold int
	cooldown  time.Duration
	openAt    time.Time
	history   []StateChange
}

func NewCircuitBreaker(threshold int, cooldown time.Duration) *CircuitBreaker {
	return &CircuitBreaker{threshold: threshold, cooldown: cooldown}
}

func (cb *CircuitBreaker) transition(to State) {
	cb.history = append(cb.history, StateChange{From: cb.state, To: to, At: time.Now()})
	cb.state = to
}

func (cb *CircuitBreaker) StateHistory() []StateChange {
	cb.mu.Lock()
	defer cb.mu.Unlock()
	out := make([]StateChange, len(cb.history))
	copy(out, cb.history)
	return out
}

func (cb *CircuitBreaker) Call(op func() error) error {
	cb.mu.Lock()
	if cb.state == StateOpen {
		if time.Since(cb.openAt) >= cb.cooldown {
			cb.transition(StateHalfOpen)
		} else {
			cb.mu.Unlock()
			return ErrCircuitOpen
		}
	}
	cb.mu.Unlock()

	err := op()

	cb.mu.Lock()
	defer cb.mu.Unlock()
	if err != nil {
		cb.failures++
		if cb.state == StateHalfOpen || cb.failures >= cb.threshold {
			cb.openAt = time.Now()
			cb.transition(StateOpen)
		}
		return err
	}
	cb.failures = 0
	cb.transition(StateClosed)
	return nil
}

func main() {
	cb := NewCircuitBreaker(2, 20*time.Millisecond)
	fail := func() error { return errors.New("err") }
	succeed := func() error { return nil }

	// Drive Closed → Open (2 failures)
	_ = cb.Call(fail)
	_ = cb.Call(fail)
	// Drive Open → Half-Open (wait cooldown)
	time.Sleep(30 * time.Millisecond)
	// Drive Half-Open → Closed (probe succeeds)
	_ = cb.Call(succeed)

	history := cb.StateHistory()
	fmt.Printf("transitions: %d\n", len(history))
	for _, h := range history {
		fmt.Printf("  %s → %s\n", h.From, h.To)
	}
	if len(history) != 3 {
		fmt.Println("FAIL: expected 3 transitions")
	} else {
		fmt.Println("PASS")
	}
}
```

The key is keeping `transition` private and calling it only under the mutex, so the history slice is never written concurrently.

</Solution>

Write an `http.Handler` middleware `RateLimit(next http.Handler, r rate.Limit, burst int) http.Handler` that uses `golang.org/x/time/rate`.
```go
package main

import (
	"fmt"
	"net/http"
	"net/http/httptest"

	"golang.org/x/time/rate"
)

func RateLimit(next http.Handler, r rate.Limit, burst int) http.Handler {
	limiter := rate.NewLimiter(r, burst)
	return http.HandlerFunc(func(w http.ResponseWriter, req *http.Request) {
		if !limiter.Allow() {
			w.Header().Set("Retry-After", "1")
			http.Error(w, "rate limit exceeded", http.StatusTooManyRequests)
			return
		}
		next.ServeHTTP(w, req)
	})
}

func main() {
	base := http.HandlerFunc(func(w http.ResponseWriter, _ *http.Request) {
		w.WriteHeader(http.StatusOK)
	})

	// burst=3, very low rate so tokens don't refill during the test
	handler := RateLimit(base, rate.Limit(0.01), 3)

		want int
	}{
		{200}, {200}, {200}, // burst of 3 passes
		{429},               // 4th is rejected
	}

	for i, tt := range tests {
		rec := httptest.NewRecorder()
		req := httptest.NewRequest(http.MethodGet, "/", nil)
		handler.ServeHTTP(rec, req)
		status := "PASS"
		if rec.Code != tt.want {
			status = fmt.Sprintf("FAIL (got %d, want %d)", rec.Code, tt.want)
		}
```

<Recap>

- **Timeouts everywhere**: every I/O call carries a `context.WithTimeout`. `http.DefaultClient` has zero timeout — never use it in production. The context propagates cancellation down the whole call tree.
- **Retries with full jitter**: only retry idempotent operations. Exponential backoff slows retries; full jitter (`rand.N(int64(cap))`) randomizes them to prevent the thundering herd. A retry budget caps amplification.
- **Circuit breakers**: three states — Closed (pass through), Open (fail fast), Half-Open (probe). Protects a flaky downstream and gives it space to recover. `sony/gobreaker` is the standard Go library.
- **Graceful shutdown**: `signal.NotifyContext` → `srv.Shutdown(drainCtx)` → release resources in reverse order. Always set `ReadHeaderTimeout`, `WriteTimeout`, and `IdleTimeout` on every `http.Server`.
- **Liveness vs. readiness**: liveness checks the process (cheap, never fails), readiness checks dependencies (returns 503 to pull traffic). Conflating them causes restart loops.
- **Idempotency keys**: generated by the client, honored by the server. Required on any write operation before you add a retry loop.
- **Rate limiting in depth**: token bucket allows bursts, leaky bucket smooths output, fixed/sliding window counts calls. `golang.org/x/time/rate` uses lazy timestamp math — no background goroutine. Per-key limiting isolates clients. Distributed limiting across replicas requires Redis.

</Recap>
