<HeroCard label="Part 2 · Chapter 12" title="Reliability Patterns">

In chapter 11, Redis stopped and customers couldn't book. Stopping is the easy failure: things fail fast and loudly. The hard ones are **slow** (Redis answers, after two seconds), **flaky** (some replies are lost), and **overloaded** (one customer's script sends 200 requests at once). Each has a pattern, and each pattern has a way to get it wrong.

This chapter puts **Toxiproxy** (the fault-injection proxy teams use for exactly this) between the cinema service and Redis, injects real latency, lost replies and silence, and measures what each pattern changes. Some results aren't the ones you'd guess: a timeout that didn't time out, retries that told customers their own seat was taken.

Six stops. If you get lost, come back here:

1. **Timeouts.** Every call to something else gets a deadline, and the Redis client needs one option to honour it.
2. **Retries and idempotency.** Retry transient failures with jittered backoff, and only operations that are safe to repeat.
3. **Circuit breakers and bulkheads.** Stop calling a dependency that's down, and keep one failure from taking everything.
4. **Degradation and health.** Serve something useful when a dependency fails, and tell the load balancer the truth.
5. **Graceful shutdown.** Finish the requests you started before you exit.
6. **Rate limiting.** One customer can't take everyone's capacity, and a limit must hold across replicas.

Every pattern in this chapter is a flag on the service, so each can be switched on alone and measured. The patterns live in one wrapper around the store:

```go noverify
package main

import (
	"context"
	"errors"
	"math/rand/v2"
	"sync"
	"sync/atomic"
	"time"

	"cinema/booking"

	"github.com/sony/gobreaker/v2"
)

// resilientStore wraps a Store with the chapter's patterns. Each is
// optional, so the experiments can switch them on one at a time.
type resilientStore struct {
	booking.Store
	timeout time.Duration // per attempt; 0 = none
	retries int           // extra attempts after a failure
	breaker *gobreaker.CircuitBreaker[struct{}]
	stale   bool // serve the last good seat map if the store fails

	attempts atomic.Int64 // calls that actually reached the store

	mu       sync.Mutex
	lastGood map[string][]booking.Seat // guarded by mu
}

// businessErr reports errors that are answers, not failures: retrying
// them won't change them, and they say nothing about the store's health.
func businessErr(err error) bool {
	return errors.Is(err, booking.ErrTaken) || errors.Is(err, booking.ErrNotHolder) || errors.Is(err, booking.ErrNoSeat)
}

// call runs fn with a per-attempt timeout, retries failures with
// exponential backoff and full jitter, all inside the circuit breaker.
func (s *resilientStore) call(ctx context.Context, fn func(context.Context) error) error {
	run := func() error {
		var err error
		for attempt := 0; ; attempt++ {
			actx, cancel := ctx, context.CancelFunc(func() {})
			if s.timeout > 0 {
				actx, cancel = context.WithTimeout(ctx, s.timeout)
			}
			s.attempts.Add(1)
			err = fn(actx)
			cancel()
			if err == nil || businessErr(err) || attempt >= s.retries || ctx.Err() != nil {
				return err
			}
			// Full jitter: sleep a random time up to 20ms, 40ms, 80ms, …
			// so clients that failed together don't retry together.
			backoff := time.Duration(rand.Int64N(int64(20*time.Millisecond) << attempt))
			select {
			case <-time.After(backoff):
			case <-ctx.Done():
				return ctx.Err()
			}
		}
	}
	if s.breaker == nil {
		return run()
	}
	_, err := s.breaker.Execute(func() (struct{}, error) { return struct{}{}, run() })
	return err
}

func newBreaker() *gobreaker.CircuitBreaker[struct{}] {
	return gobreaker.NewCircuitBreaker[struct{}](gobreaker.Settings{
		Name:        "redis",
		MaxRequests: 1,               // half-open: let one request test the store
		Timeout:     2 * time.Second, // stay open this long before testing
		ReadyToTrip: func(c gobreaker.Counts) bool {
			return c.ConsecutiveFailures >= 5
		},
		IsSuccessful: func(err error) bool { return err == nil || businessErr(err) },
	})
}

func (s *resilientStore) Hold(ctx context.Context, movie, seat, user string, ttl time.Duration) error {
	return s.call(ctx, func(ctx context.Context) error { return s.Store.Hold(ctx, movie, seat, user, ttl) })
}

func (s *resilientStore) Confirm(ctx context.Context, movie, seat, user string) error {
	return s.call(ctx, func(ctx context.Context) error { return s.Store.Confirm(ctx, movie, seat, user) })
}

// SeatsStale returns the seat map, and whether it came from the last-good
// copy because the store is failing.
func (s *resilientStore) SeatsStale(ctx context.Context, movie string) ([]booking.Seat, bool, error) {
	var seats []booking.Seat
	err := s.call(ctx, func(ctx context.Context) error {
		var err error
		seats, err = s.Store.Seats(ctx, movie)
		return err
	})
	s.mu.Lock()
	defer s.mu.Unlock()
	if err == nil {
		if s.lastGood == nil {
			s.lastGood = map[string][]booking.Seat{}
		}
		s.lastGood[movie] = seats
		return seats, false, nil
	}
	if last, ok := s.lastGood[movie]; ok && s.stale && !businessErr(err) {
		return last, true, nil
	}
	return nil, false, err
}

func (s *resilientStore) Seats(ctx context.Context, movie string) ([]booking.Seat, error) {
	seats, _, err := s.SeatsStale(ctx, movie)
	return seats, err
}
```

### Step 1: what "no timeout" does

Replies from Redis now take 2 seconds. `hammer` sends 50 holds and 200 seat maps a second for 5 seconds, with no timeouts anywhere in the service:

### Step 2: a timeout that didn't work

Add a per-attempt timeout (`-store-timeout 150ms`, the `context.WithTimeout` in `call`):

```text
$ ./exp.sh "-ctx-timeouts=false -store-timeout 150ms" "$LATENCY_2S" "-holds 50 -seats 200 -for 5s"
hold    250 requests  201:8 409:9 500:233          p50 150.8ms  p99 6.0123s  max 6.017s
seats   999 requests  200:67 500:932               p50 150.8ms  p99 6.0116s  max 6.021s
```

The median is 150 ms, but the p99 is **6 seconds**. The deadline is honoured while a request waits for a pooled connection, but not once it's waiting on the socket: go-redis v9 only applies context deadlines to socket reads and writes when the client is created with **`ContextTimeoutEnabled: true`**. Without it, it uses its own `ReadTimeout` (3 s by default), and a command can wait through two of those. The smallest reproduction:

```go noverify
// Does a context deadline stop a slow Redis call?
package main

import (
	"context"
	"fmt"
	"time"

	"github.com/redis/go-redis/v9"
)

func main() {
	for _, enabled := range []bool{false, true} {
		rdb := redis.NewClient(&redis.Options{Addr: "127.0.0.1:26379", ContextTimeoutEnabled: enabled})
		rdb.Ping(context.Background()) // connect before the toxic matters
		ctx, cancel := context.WithTimeout(context.Background(), 150*time.Millisecond)
		start := time.Now()
		err := rdb.Get(ctx, "seat:inception:A7").Err()
		cancel()
		fmt.Printf("ContextTimeoutEnabled=%-5v  150ms deadline: returned after %v: %v\n",
			enabled, time.Since(start).Round(time.Millisecond), err)
		rdb.Close()
	}
}
```

```text
ContextTimeoutEnabled=false  150ms deadline: returned after 2.006s: redis: nil
ContextTimeoutEnabled=true   150ms deadline: returned after 152ms: context deadline exceeded
```

With the option (`rdb = redis.NewClient(&redis.Options{Addr: *redisAddr, ContextTimeoutEnabled: *ctxTimeouts})`):

```text
$ ./exp.sh "-store-timeout 150ms" "$LATENCY_2S" "-holds 50 -seats 200 -for 5s"
hold    250 requests  500:250                      p50 150.7ms  p99 154.2ms  max 159ms
seats   999 requests  500:999                      p50 150.7ms  p99 154.1ms  max 159ms
```

Every request answered within **154 ms**, all with a clean error, and 86 goroutines instead of 1,257. Failing is still failing, but now it's fast and it doesn't spread.

## Retries and Idempotency

*Stop 2 of 6.*

### Step 1: a timeout doesn't mean it didn't happen

When a call times out, you don't know whether the other side did the work. For a hold, Redis may have stored `held:alice` and only the reply was lost. `idem` makes 40 customers each hold a different seat, then compares what each was told with who holds the seat. Toxiproxy delays replies by 300 ms for the first 150 ms of the run (after the connection pool is warm), so first attempts time out after Redis has applied them:

```text
$ ./idem.sh "-store-timeout 150ms"
== -store-timeout 150ms
  told 201, holds it                 20
  told 500 (error), but holds it     19
  told 500, doesn't hold it          1
```

**19 customers were told their hold failed, though they hold the seat.** They'll try another seat, or give up, while their seat stays locked for two minutes.

### Step 2: retry, with backoff and jitter

Retrying transient failures is the answer, but how you retry matters:

- **Only transient failures.** "Seat taken" is an answer, not a failure: retrying it changes nothing (`businessErr` in `call`).
- **Bounded.** At most 3 extra attempts, and stop as soon as the request's context is done.
- **Backoff with full jitter.** Wait a *random* time up to 20, 40, 80 ms. If 40 clients failed at the same instant and all retried after exactly 20 ms, they'd hit Redis together again. Randomness spreads them out.

```text
$ ./idem.sh "-store-timeout 150ms -retries 3"
== -store-timeout 150ms -retries 3
  told 201, holds it                 35
  told 409 (taken), but holds it     5
```

No more 500s, but **5 customers were told "taken" for the seat they hold**. Their first `SET … NX` succeeded and its reply was lost; the retry's `SET … NX` found the key already there. It *was* taken: by them.

### Step 3: make the operation idempotent

An operation is **idempotent** if doing it twice has the same effect as doing it once, *and* gives the same answer. Holding a seat you already hold should say "yes, it's yours". So `Hold`, when `SET NX` fails, checks whose it is:

```go noverify
// redis.go, lines 34–52
func (s *RedisStore) Hold(ctx context.Context, movie, seat, user string, ttl time.Duration) error {
	if !validSeat(movie, seat) {
		return ErrNoSeat
	}
	err := s.rdb.SetArgs(ctx, seatKey(movie, seat), "held:"+user, redis.SetArgs{Mode: "NX", TTL: ttl}).Err()
	if errors.Is(err, redis.Nil) {
		if s.Idempotent {
			v, err := s.rdb.Get(ctx, seatKey(movie, seat)).Result()
			if err != nil && !errors.Is(err, redis.Nil) {
				return err // couldn't check: a real failure, worth retrying
			}
			if v == "held:"+user {
				return nil // an earlier attempt already held it for this user
			}
		}
		return ErrTaken
	}
	return err
}
```

(If that `GET` itself fails, it returns the error, which is retryable, rather than guessing "taken": the first version of this code guessed, and was wrong under exactly these conditions.) `Confirm` gets the same treatment: a retried confirm that finds `booked:<user>` reports success.

```text
$ ./idem.sh "-store-timeout 150ms -retries 3 -idempotent"
== -store-timeout 150ms -retries 3 -idempotent
  told 201, holds it                 40
```

**40 of 40**, in both runs. Retries make failures invisible only if the operation is safe to repeat. For operations that can't check their own effect this way (charging a card), the client sends an **idempotency key** and the server remembers the result per key (Part 1 chapter 24 measured a double charge without one).

## Circuit Breakers and Bulkheads

*Stop 3 of 6.*

### Step 1: stop calling a dependency that's down

Now Redis goes silent: connections accepted, nothing ever answered (Toxiproxy's `timeout` toxic). With timeouts, each request costs 150 ms and a Redis attempt:

```text
$ ./exp.sh "-store-timeout 150ms" "$SILENT" "-holds 50 -seats 200 -for 5s"
hold    250 requests  500:250                      p50 150.7ms  p99 154ms    max 154ms
seats  1000 requests  500:1000                     p50 150.7ms  p99 154ms    max 155ms
  server goroutines mid-run: 83   store attempts: 1290
```

Every request pays the full 150 ms to learn what the previous thousand already learned, and **1,290 attempts** keep hammering a dependency that's struggling. A **circuit breaker** remembers: after 5 consecutive failures it **opens** and fails calls immediately without trying; after a cool-down (2 s here) it goes **half-open** and lets one call through as a test; success **closes** it, failure opens it again. `newBreaker` configures `sony/gobreaker` that way, counting only real failures (a "taken" seat is an answer).

```text
$ ./exp.sh "-store-timeout 150ms -breaker" "$SILENT" "-holds 50 -seats 200 -for 5s"
hold    250 requests  500:250                      p50 500µs    p99 150.9ms  max 154ms
seats  1000 requests  500:1000                     p50 500µs    p99 151ms    max 154ms
  server goroutines mid-run: 46   store attempts: 84
```

Median **0.5 ms** instead of 150, and **84 attempts** instead of 1,290 (about 40 of those were the warm-up before the fault). The failures are the same; they're just cheap, and Redis gets room to recover.

### Step 2: bulkheads

A ship's bulkheads split the hull into compartments, so one leak floods one compartment. In a service, a **bulkhead** gives each kind of work its own limited share of a resource, so one slow or greedy kind can't use it all. You've already measured one: chapter 5's `LOGIN_CAP`, a 2-slot channel that kept password hashing from taking every P, took `/balance` from **744 ms to 0.9 ms**. Chapter 6's worker pool was one for the statements endpoint. The same shape applies to connection pools (a separate Redis client, with its own pool, for seat maps and for holds), goroutines (a semaphore per dependency), and whole services (separate deployments for the booking API and the reporting jobs).

## Degradation and Health

*Stop 4 of 6.*

### Step 1: the seat map, slightly out of date

When holds can't work, nothing sensible replaces them. The seat map is different: showing the seats as they were a few seconds ago is far better than an error page. `SeatsStale` keeps the last good map per film and serves it, marked `X-Stale: true`, when the store fails:

```text
$ ./exp.sh "-store-timeout 150ms -breaker -stale" "$SILENT" "-holds 50 -seats 200 -for 5s"
hold    250 requests  500:250                      p50 500µs    p99 151.2ms  max 154ms
seats   999 requests  200:999                      p50 400µs    p99 151.1ms  max 155ms  stale:999
```

**999 of 999 seat maps served**, every one flagged stale so the page can say "seat availability may be out of date; booking is temporarily unavailable". Decide deliberately what may be stale: a seat map, a film's description, yes; a balance or "your booking is confirmed", never.

### Step 2: liveness and readiness

Orchestrators (Kubernetes) and load balancers ask two different questions:

```go noverify
// main.go, lines 132–152
	// Liveness: is this process able to serve at all? Never checks
	// dependencies: restarting the process won't fix Redis.
	mux.HandleFunc("GET /livez", func(w http.ResponseWriter, r *http.Request) {
		w.WriteHeader(http.StatusOK)
	})
	// Readiness: should the load balancer send us traffic right now?
	mux.HandleFunc("GET /readyz", func(w http.ResponseWriter, r *http.Request) {
		if a.draining.Load() {
			http.Error(w, "shutting down", http.StatusServiceUnavailable)
			return
		}
		if p, ok := a.pinger.(interface{ Ping(context.Context) error }); ok {
			ctx, cancel := context.WithTimeout(r.Context(), 100*time.Millisecond)
			defer cancel()
			if err := p.Ping(ctx); err != nil {
				http.Error(w, "store unavailable: "+err.Error(), http.StatusServiceUnavailable)
				return
			}
		}
		w.WriteHeader(http.StatusOK)
	})
```

With Redis disabled in Toxiproxy:

```text
== Redis up
$ curl -i localhost:8091/livez
HTTP/1.1 200 OK
$ curl -i localhost:8091/readyz
HTTP/1.1 200 OK
== Redis down
$ curl -i localhost:8091/livez
HTTP/1.1 200 OK
$ curl -i localhost:8091/readyz
HTTP/1.1 503 Service Unavailable
store unavailable: context deadline exceeded
```

**Readiness** fails, so the load balancer sends traffic to replicas that can serve it. **Liveness** stays 200: if liveness checked Redis, Kubernetes would restart every replica during a Redis outage, which fixes nothing and adds startup load at the worst moment. Liveness asks only "is this process stuck?".

## Graceful Shutdown

*Stop 5 of 6.*

Every deploy stops the old process. Kubernetes sends SIGTERM, waits (30 s by default), then SIGKILL. What happens to the requests it's in the middle of?

```go noverify
// main.go, lines 207–228
	srv := &http.Server{Addr: *addr, Handler: h, ReadHeaderTimeout: 5 * time.Second}
	log.Printf("cinema on http://%s, store=%s", *addr, *kind)

	if !*graceful {
		log.Fatal(srv.ListenAndServe()) // SIGTERM kills the process mid-request
	}
	ctx, stop := signal.NotifyContext(context.Background(), syscall.SIGTERM, os.Interrupt)
	defer stop()
	go func() {
		if err := srv.ListenAndServe(); err != http.ErrServerClosed {
			log.Fatal(err)
		}
	}()
	<-ctx.Done()
	log.Printf("shutting down: %v", context.Cause(ctx))
	a.draining.Store(true) // readiness fails, so the load balancer stops sending
	sctx, cancel := context.WithTimeout(context.Background(), 20*time.Second)
	defer cancel()
	if err := srv.Shutdown(sctx); err != nil { // stop accepting, wait for in-flight requests
		log.Printf("shutdown: %v", err)
	}
	log.Printf("drained")
```

`drain.sh` starts 20 holds whose Redis replies take 1 s, then sends SIGTERM 600 ms later:

```text
== -graceful=false
  error: EOF             20
  server exit status: 143
== -graceful
  201 Created            20
  server exit status: 0
  log: shutting down: terminated signal received
  log: drained
```

Without it, the process dies on the signal and all **20 customers** get a dropped connection (`EOF`), with their holds perhaps applied, perhaps not. With it, `signal.NotifyContext` turns SIGTERM into a cancelled context (whose cause, since Go 1.26, names the signal), readiness starts failing so a load balancer stops sending, and `srv.Shutdown` stops accepting new connections and waits for all 20 in-flight requests: **20 × 201**, exit 0. Part 1 chapter 27 measured the same thing across Kubernetes rolling updates: naive shutdown failed requests in 6 of 9 rollouts, draining in none.

<Callout kind="warn" title="Shutdown doesn't wait for your goroutines">

`srv.Shutdown` waits for HTTP handlers to return, not for goroutines they started. Anything in the background (a statement delivery, a metrics flush) needs its own signal and its own wait, in the shutdown sequence, before main returns.

</Callout>

## Rate Limiting

*Stop 6 of 6.*

### Step 1: a token bucket per customer

A scalper's script refreshes the seat map 200 times at once. Everyone else pays for it. A **token bucket** gives each customer a bucket that refills at a steady rate (5 tokens a second) up to a maximum (10: the burst). Each request takes a token; no token, 429 Too Many Requests. `golang.org/x/time/rate` implements it:

```go noverify
package main

import (
	"fmt"
	"net/http"
	"sync"
	"time"

	"github.com/redis/go-redis/v9"

	"golang.org/x/time/rate"
)

// limitPerUser gives every customer (X-User) a token bucket: perSecond
// tokens a second, up to burst saved up. Requests without a token get 429.
// (A real service would evict idle customers' buckets; this map only grows.)
func limitPerUser(next http.Handler, perSecond float64, burst int) http.Handler {
	var mu sync.Mutex
	buckets := map[string]*rate.Limiter{}
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		user := r.Header.Get("X-User")
		mu.Lock()
		lim, ok := buckets[user]
		if !ok {
			lim = rate.NewLimiter(rate.Limit(perSecond), burst)
			buckets[user] = lim
		}
		mu.Unlock()
		if !lim.Allow() {
			w.Header().Set("Retry-After", "1")
			http.Error(w, "too many requests", http.StatusTooManyRequests)
			return
		}
		next.ServeHTTP(w, r)
	})
}

// limitPerUserRedis enforces perSecond requests per customer across every
// replica: one Redis counter per customer per second. INCR is atomic, so
// all replicas count against the same number.
func limitPerUserRedis(next http.Handler, rdb *redis.Client, perSecond int) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		key := fmt.Sprintf("rl:%s:%d", r.Header.Get("X-User"), time.Now().Unix())
		pipe := rdb.TxPipeline()
		n := pipe.Incr(r.Context(), key)
		pipe.Expire(r.Context(), key, 2*time.Second)
		if _, err := pipe.Exec(r.Context()); err != nil {
			next.ServeHTTP(w, r) // fail open: a limiter outage shouldn't take the service down
			return
		}
		if n.Val() > int64(perSecond) {
			w.Header().Set("Retry-After", "1")
			http.Error(w, "too many requests", http.StatusTooManyRequests)
			return
		}
		next.ServeHTTP(w, r)
	})
}
```

```text
$ ./rate.sh "-rate 5" 1
== -rate 5, 1 replica(s)
  bot: 200 requests in 22ms over 1 replica(s): 200 x10, 429 x190
  alice: 3 requests in 1ms over 1 replica(s): 200 x3, 429 x0
```

The bot got its burst of **10** and 190 refusals; Alice, a normal customer, noticed nothing.

### Step 2: three replicas, three buckets

Behind a load balancer there are three replicas, each with its own map of buckets:

```text
$ ./rate.sh "-rate 5" 3
== -rate 5, 3 replica(s)
  bot: 200 requests in 27ms over 3 replica(s): 200 x30, 429 x170
```

**30**: three times the limit, because each replica gave the bot a full bucket. Chapter 8's lesson again: state that must be shared can't live in each process. `limitPerUserRedis` keeps one counter per customer per second in Redis (`INCR` is atomic, so every replica counts against the same number):

```text
$ ./rate.sh "-rate 5 -rate-redis" 3
== -rate 5 -rate-redis, 3 replica(s)
  bot: 200 requests in 67ms over 3 replica(s): 200 x5, 429 x195
  alice: 3 requests in 1ms over 3 replica(s): 200 x3, 429 x0
```

Exactly **5**. The cost: a Redis round trip per request (the flood took 67 ms instead of 27), and it's a fixed one-second window (no burst; up to 2× the rate across a window boundary). If the limiter's Redis call fails, the code **fails open**, lets the request through: a limiter outage shouldn't take the service down. Whether to fail open or closed is a decision; for login attempts you'd fail closed.

## Exercises

These use the `cinema` module and Toxiproxy from this chapter.

<Exercise n={1} title="Find the timeout you don't have" level="easy">

List every place the cinema service waits on something external, and the timeout each one has after this chapter.

<Solution>

Inbound: `http.Server{ReadHeaderTimeout: 5s}` (headers; bodies are tiny here, but a service reading uploads also needs `ReadTimeout`). Outbound to Redis: `-store-timeout` per attempt via context, made effective by `ContextTimeoutEnabled: true`; the readiness ping has its own 100 ms. The Redis rate limiter uses the request's context, which has *no* deadline of its own: a slow limiter call would slow every request. Give it one (for example 50 ms) and fail open when it fires.

</Solution>

</Exercise>

<Exercise n={2} title="Why full jitter?" level="easy">

Two retry schedules: every retry waits exactly 20, 40, 80 ms; or a random time up to 20, 40, 80 ms. With 40 clients failing at the same moment, what happens to Redis under each?

<Solution>

With fixed delays, all 40 retry at 20 ms, then all at 60 ms, then at 140 ms: three synchronized spikes of 40 requests, each capable of failing the same way and restarting the cycle (a "thundering herd"). With full jitter, the 40 retries are spread uniformly over each window, so Redis sees a trickle instead of spikes. The total number of retries is the same; the peak load is much lower. That's why `call` uses `rand.Int64N(20ms << attempt)`.

</Solution>

</Exercise>

<Exercise n={3} title="Make Release idempotent" level="medium">

`Release` returns `ErrNotHolder` if the seat isn't `held:<user>`. What happens when a customer's release is retried after its reply was lost, and how would you fix it?

<Solution>

The first `DELEX … IFEQ held:alice` deleted the key; the retry finds nothing (or someone else's new hold) and returns `ErrNotHolder`, so Alice sees an error for a release that worked. Treat "the key no longer holds held:alice" as success *for release*: the goal state (Alice doesn't hold the seat) is reached. Concretely, when `DELEX` returns 0, `GET` the key; if it's not `held:alice` (missing, or someone else's hold), return nil. Never delete someone else's key: the `IFEQ` already guarantees that.

</Solution>

</Exercise>

<Exercise n={4} title="Break the breaker" level="medium">

With `-breaker`, what happens if the breaker counted `ErrTaken` as a failure? Predict it for opening night, when most holds are "taken".

<Solution>

On opening night most hold attempts return "taken" (chapter 11 measured ~23/s taken against ~0.1/s successful). Five in a row would open the breaker, and every customer, including ones asking for free seats, would get fast 500s while Redis was perfectly healthy. That's why `newBreaker` sets `IsSuccessful` to count business answers (`businessErr`) as successes: the breaker measures the dependency's health, not the customers' luck.

</Solution>

</Exercise>

<Exercise n={5} title="Fail open or closed?" level="hard">

For each limiter, decide what should happen when Redis (the shared counter) is unavailable, and why: (a) seat-map refreshes per customer; (b) login attempts per account; (c) holds per customer.

<Solution>

(a) **Fail open**: letting some extra refreshes through is harmless, and a limiter outage mustn't take down the page everyone needs. (b) **Fail closed**, or fall back to a strict per-replica limit: the limit exists to stop password guessing, and "unlimited during an outage" is exactly when an attacker would push. (c) **Fall back to the per-replica bucket**: holds are real inventory, so some limit must remain, and a per-replica limit (3× too generous with 3 replicas) is far better than none. The general rule: fail open for protection of capacity, closed for protection of security.

</Solution>

</Exercise>

<Recap>

- **Timeouts** turn slow failures into fast ones: with Redis 2 s slow, no timeouts meant p50 10 s and 1,257 goroutines; a 150 ms timeout that really worked meant p99 154 ms and 86 goroutines. go-redis needs `ContextTimeoutEnabled: true`, or the socket ignores the deadline (p99 was 6 s).
- **Retries** need **idempotency**. A timeout means "unknown": without retries 19 of 40 customers were told they'd failed while holding the seat; naive retries told 5 their own seat was taken; retries plus an idempotent Hold got 40 of 40 right. Retry only transient failures, bounded, with full jitter.
- **Circuit breakers** make failure cheap and protect the dependency: p50 150 ms → 0.5 ms, Redis attempts 1,290 → 84, then half-open → closed when Redis returned. **Bulkheads** (chapter 5's LOGIN_CAP) keep one kind of work from starving the rest.
- **Degrade**: 999 of 999 seat maps served stale during the outage, flagged `X-Stale`. **Readiness** failed (503) and **liveness** didn't, so traffic moves without pointless restarts.
- **Graceful shutdown**: SIGTERM mid-request dropped 20 of 20 without draining, completed 20 of 20 with it.
- **Rate limits** must be shared: per-replica buckets let a bot through 30 times with 3 replicas; a Redis counter held it to exactly 5.

</Recap>
