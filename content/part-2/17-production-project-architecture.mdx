<HeroCard label="Part 2 · Chapter 17" title="Production Project Architecture">

The cinema service grew one chapter at a time: a store in chapter 8, resilience in 12, a box-office report in 15, configuration in 16. It works, it's tested, and CI checks it. But its shape is an accident. `main.go` is 242 lines that build everything and handle signals. The domain package imports the Redis client. Any other module can import anything. And nothing about the layout says what depends on what.

This chapter rebuilds its structure without changing what it does, and measures each decision: what the compiler now refuses, what the domain no longer drags in, what a test can now start, and what a wrong shutdown order costs under load. Then it packages the service as a container image.

Five stops. If you get lost, come back here:

1. **Layout.** `cmd/`, `internal/`, and a domain that doesn't know about Redis.
2. **Wiring.** One function builds the dependencies, innermost first, and passes them in.
3. **A testable main.** `main` calls `app.Run`, and a test runs the whole service the same way.
4. **Shutdown order.** Stop taking traffic, finish what's in flight, then close what it used.
5. **The image.** A multi-stage build: 25.6 MB instead of 1.59 GB.

</HeroCard>

- **`cmd/<name>/`** holds one directory per program. `cmd/cinema/main.go` is now 31 lines. The load-testing tools from earlier chapters (`hammer`, `rush`…) stay alongside it: they're programs too.
- **`internal/`** holds everything else. The go command refuses to let code outside the directory that contains `internal/` import anything under it. That's the only access rule Go enforces between packages, and it's enforced by the compiler.
- **Packages by what they are, not by layer names**: `booking` (the domain: seats, statuses, rules, the `Store` interface and the in-memory store), `booking/redisstore` (the Redis implementation), `httpapi` (HTTP handlers), `resilience` (chapter 12's wrapper), `config` (chapter 16), `app` (wiring).

There's no `pkg/` directory. It's a convention some projects use for "importable by others", but it means nothing to the compiler; in a service, nearly everything should be internal, and anything genuinely public deserves its own deliberate package at the module root.

### Step 3: what the compiler now enforces

The jobs module's `enqueue` imported the seat names from the cinema. With the package now internal:

```text
$ cd jobs && go build ./cmd/enqueue     # jobs imports cinema/internal/booking
package jobs/cmd/enqueue
	cmd/enqueue/main.go:12:2: use of internal package cinema/internal/booking not allowed
```

The cinema's team can now rename, split or delete anything in `booking` without breaking another module. If jobs genuinely needs the seat names, that's a decision to publish something small and stable (a `cinema/halls` package with just the hall layouts), made on purpose, not an accident of what happened to be importable.

### Step 4: the domain without Redis

The Redis store moved to `internal/booking/redisstore`, which imports `booking`, not the other way round:

```text
$ go list -deps -f '{{if not .Standard}}{{.ImportPath}}{{end}}' ./internal/booking
cinema/internal/booking
  all packages it depends on (std included), before → after: 196 → 59
```

The domain package now depends on **no module outside the standard library**, and on 59 packages in all instead of 196. Its tests compile faster and run without Redis. It also makes the architecture visible in the import graph: `booking` defines the `Store` interface (a **port**, in hexagonal-architecture terms), and `redisstore` and the in-memory store are **adapters** that satisfy it. Dependencies point inward, to the domain. That's all "clean" or "hexagonal" architecture asks for in Go: no framework, just which package imports which.

## Wiring

*Stop 2 of 5.*

### Step 1: one place that knows everything

Somewhere, something must know that the service uses Redis, wraps it in retries, serves it over HTTP and rate-limits it. In the new layout that's `internal/app`, and nothing else does:

The imports are the point of this package: it's the only one that imports every other package in the module, plus Redis, `errgroup`, `expvar` and `pprof`. Everything else knows only its own neighbours:

```go noverify title="cinema/internal/app/app.go · lines 1–30"

// context ends. main does nothing else but call Run, so tests can start
// the whole service in-process, exactly as production does.

import (
	"context"
	"errors"
	"expvar"
	"fmt"
	"io"
	"log"
	"net"
	"net/http"
	_ "net/http/pprof" //nolint:gosec // served only on the loopback admin listener
	"os"
	"strings"
	"sync"
	"sync/atomic"
	"time"

	"cinema/internal/booking"
	"cinema/internal/booking/redisstore"
	"cinema/internal/config"
	"cinema/internal/httpapi"

	"github.com/redis/go-redis/v9"
```

Two package-level values and a type. `ErrConfig` lets `main` tell a bad configuration (exit 2) from a runtime failure. `shutdownOrder` exists only so the chapter can build the wrong order on purpose and measure it. `Hooks` lets a test learn which ports `:0` picked:

```go noverify title="cinema/internal/app/app.go · lines 32–44"
// ErrConfig wraps every configuration problem, so main can exit 2 for them.
var ErrConfig = errors.New("invalid configuration")

// shutdownOrder exists for the chapter's experiment only: building with
// -ldflags "-X cinema/internal/app.shutdownOrder=redis-first" closes Redis
// before draining HTTP, the order this package must never use.
var shutdownOrder = "drain-first"

// Hooks are optional callbacks. Ready, if set, is called with the public and admin addresses once both
// listeners are open (tests use it to learn the ports chosen for :0).
type Hooks struct {
	Ready func(public, admin string)
}
```

`Run` takes everything a process gets from outside (arguments, environment, stdout, stderr) as parameters instead of reading `os.Args` and `os.Stdout` itself. That's what makes it testable: a test calls `Run` with its own arguments and buffers, and gets the whole service in-process. First, the configuration from chapter 16:

```go noverify title="cinema/internal/app/app.go · lines 46–58"
// Run loads the configuration from args and environ, starts the service
// and blocks until ctx ends, then shuts down in order: stop being ready,
// drain HTTP, stop the admin listener, close Redis.
func Run(ctx context.Context, args, environ []string, stdout, stderr io.Writer, hooks Hooks) error {
	logger := log.New(stderr, "", log.LstdFlags)
	cfg, sources, err := config.Load(args, environ)
	if err != nil {
		return fmt.Errorf("%w:\n%w", ErrConfig, err)
	}
	if cfg.PrintConfig {
		_, err := fmt.Fprint(stdout, config.Table(cfg, sources))
		return err
	}
```

Then the dependencies, innermost first: the store (in memory or Redis), wrapped in the resilience layer from chapter 12, handed to the HTTP API, and the handler wrapped in a rate limiter if one is configured. Each package receives what it needs as arguments; none of them builds its own dependencies:

```go noverify title="cinema/internal/app/app.go · lines 60–92"
	// ── dependencies, innermost first ─────────────────────────────────
	var store booking.Store
	var pinger interface{ Ping(context.Context) error }
	var rdb *redis.Client
	switch cfg.Store {
	case "locked":
		store = booking.NewMemoryStore()
	case "redis":
		rdb = newRedis(cfg)
		if err := rdb.Ping(ctx).Err(); err != nil {
			return fmt.Errorf("redis %s: %w", cfg.Redis.Addr, err)
		}
		rs := redisstore.New(rdb)
		rs.Idempotent = cfg.Idempotent
		store, pinger = rs, rs
	}
	res := resilience.Wrap(store, resilience.Options{
		Timeout: cfg.StoreTimeout, Retries: cfg.Retries, Breaker: cfg.Breaker, Stale: cfg.Stale,
	})
	publishOnce.Do(func() {
		expvar.Publish("store_attempts", expvar.Func(func() any { return current.Load().Attempts() }))
		expvar.Publish("breaker", expvar.Func(func() any { return current.Load().BreakerState() }))
	})
	current.Store(res)
	api := httpapi.New(res, cfg.Hold, pinger)

	h := api.Handler()
	switch {
	case cfg.Rate > 0 && cfg.RateRedis:
		h = httpapi.LimitPerUserRedis(h, rdb, int(cfg.Rate))
	case cfg.Rate > 0:
		h = httpapi.LimitPerUser(h, cfg.Rate, int(cfg.Rate)*2)
	}
```

Both listeners are opened before anything is served. If the admin address is taken, `Run` fails immediately, instead of serving the public port and failing a moment later. `Ready` reports the real addresses, which a test needs when it asked for port 0:

```go noverify title="cinema/internal/app/app.go · lines 94–110"
	// ── listeners: open both before serving, so a bad address fails Run ─
	var lc net.ListenConfig
	publicLn, err := lc.Listen(ctx, "tcp", cfg.Addr)
	if err != nil {
		return err
	}
	adminLn, err := lc.Listen(ctx, "tcp", cfg.Admin)
	if err != nil {
		_ = publicLn.Close() // we're returning the Listen error; this one adds nothing
		return err
	}
	srv := &http.Server{Handler: h, ReadHeaderTimeout: 5 * time.Second}
	adminSrv := &http.Server{Handler: http.DefaultServeMux, ReadHeaderTimeout: 5 * time.Second} // pprof, expvar
	logger.Printf("cinema on http://%s (admin %s), store=%s", publicLn.Addr(), adminLn.Addr(), cfg.Store)
	if hooks.Ready != nil {
		hooks.Ready(publicLn.Addr().String(), adminLn.Addr().String())
	}
```

The last part runs the servers and shuts them down in order. `errgroup` runs the two servers and a third goroutine that waits for the context to end (SIGTERM) or for a server to fail. Then the order that turned 212 failed requests into none: readiness fails first, so the load balancer stops sending traffic; in-flight requests finish, with 20 seconds to do it; only then is Redis closed, because those requests were still using it. `context.WithoutCancel` gives the shutdown a fresh deadline, since the original context is already cancelled:

```go noverify title="cinema/internal/app/app.go · lines 112–135"
	// ── run until ctx ends, then shut down in order ─────────────────────
	g, gctx := errgroup.WithContext(ctx)
	g.Go(func() error { return serve(srv, publicLn) })
	g.Go(func() error { return serve(adminSrv, adminLn) })
	g.Go(func() error {
		<-gctx.Done() // ctx cancelled (SIGTERM), or a server failed
		logger.Printf("shutting down: %v", context.Cause(ctx))
		if !cfg.Graceful {
			return errors.Join(srv.Close(), adminSrv.Close(), closeRedis(rdb))
		}
		if shutdownOrder == "redis-first" {
			_ = closeRedis(rdb) // wrong: requests still in flight need it
		}
		api.Draining.Store(true) // 1. readiness fails: stop receiving new traffic
		sctx, cancel := context.WithTimeout(context.WithoutCancel(ctx), 20*time.Second)
		defer cancel()
		err := srv.Shutdown(sctx) // 2. finish in-flight requests
		err = errors.Join(err, adminSrv.Shutdown(sctx))
		err = errors.Join(err, closeRedis(rdb)) // 3. only now close what they used
		logger.Printf("stopped")
		return err
	})
	return g.Wait()
}
```

Two small helpers. `serve` turns the expected `ErrServerClosed` into success; `closeRedis` tolerates a client that was already closed:

```go noverify title="cinema/internal/app/app.go · lines 137–153"
func serve(srv *http.Server, ln net.Listener) error {
	if err := srv.Serve(ln); !errors.Is(err, http.ErrServerClosed) {
		return err
	}
	return nil
}

func closeRedis(rdb *redis.Client) error {
	if rdb == nil {
		return nil
	}
	err := rdb.Close()
	if errors.Is(err, redis.ErrClosed) {
		return nil // already closed (the redis-first experiment)
	}
	return err
}
```

`newRedis` is where chapter 16's password file is used: with a credentials provider, the file is read on every new connection, so a rotated password takes effect without a restart:

```go noverify title="cinema/internal/app/app.go · lines 155–168"
func newRedis(cfg *config.Config) *redis.Client {
	opts := &redis.Options{Addr: cfg.Redis.Addr, ContextTimeoutEnabled: true}
	if cfg.Redis.PasswordFile != "" {
		// Read the file on every new connection, so a rotated password
		// is picked up without a restart (chapter 16).
		opts.CredentialsProviderContext = func(ctx context.Context) (string, string, error) {
			pw, err := os.ReadFile(cfg.Redis.PasswordFile) //nolint:gosec // the operator names the secret file
			return cfg.Redis.Username, strings.TrimSpace(string(pw)), err
		}
	} else {
		opts.Username, opts.Password = cfg.Redis.Username, cfg.Redis.Password.Reveal()
	}
	return redis.NewClient(opts)
}
```

And one wrinkle of wiring in-process: `expvar` names are global and publishing one twice panics, so tests that call `Run` more than once would crash. They're published once, reading whichever store the latest `Run` built:

```go noverify title="cinema/internal/app/app.go · lines 170–175"
// expvar names are process-global and Publish panics on a duplicate, so
// they're published once and read whichever store Run built last.
var (
	publishOnce sync.Once
	current     atomic.Pointer[resilience.Store]
)
```

Read `Run` top to bottom: configuration, then dependencies **innermost first** (the Redis client, the store on it, the resilience wrapper around that, the HTTP API on top), then listeners, then serving until the context ends, then shutting down in the reverse order. Each constructor takes what it needs as arguments: `httpapi.New(res, cfg.Hold, pinger)` gets a `booking.Store`, and has no idea whether that's Redis, memory, or a wrapper around either. That's **dependency injection**. In Go it needs no framework: it's calling functions with arguments, in the right order.

### Step 2: when a framework helps

Frameworks like Uber's **fx** (a runtime container that resolves constructors by type and runs lifecycle hooks) or **Wire** (which generates the wiring code at build time) earn their keep when a service has dozens of components and several binaries sharing them. The cinema's `Run` is 87 lines and reads in order; a framework would replace that readable sequence with type-driven resolution you debug through its error messages. Start by hand, and reach for one when the hand-written wiring becomes the thing people get wrong.

### Step 3: the globals that fought back

Two things in the service were process-wide, and the restructure made them visible:

- **expvar names.** `expvar.Publish` panics if a name is published twice, so a `Run` that publishes its metrics can only run once per process, and the test in stop 3 runs it twice. `Run` now publishes once (`sync.Once`) and reads whichever store it built last through an `atomic.Pointer`.
- **pprof's handlers** register themselves on `http.DefaultServeMux` when the package is imported. That's why the admin server serves `DefaultServeMux`, on its own loopback listener. A service with its own admin mux would register the pprof handlers explicitly instead.

Globals are fine for one process running one service. They're the first thing that breaks when you want to run the service twice: in a test, or two instances in one process.

## A Testable Main

*Stop 3 of 5.*

### Step 1: main does nothing

```go noverify
// cinema serves the seat map and the hold → confirm → release API.
//
//	go run ./cmd/cinema -store redis
package main

import (
	"context"
	"errors"
	"flag"
	"fmt"
	"os"
	"os/signal"
	"syscall"

	"cinema/internal/app"
)

func main() {
	ctx, stop := signal.NotifyContext(context.Background(), syscall.SIGTERM, os.Interrupt)
	defer stop()
	err := app.Run(ctx, os.Args[1:], os.Environ(), os.Stdout, os.Stderr, app.Hooks{})
	switch {
	case err == nil, errors.Is(err, flag.ErrHelp):
	case errors.Is(err, app.ErrConfig):
		fmt.Fprintln(os.Stderr, "cinema:", err)
		os.Exit(2)
	default:
		fmt.Fprintln(os.Stderr, "cinema:", err)
		os.Exit(1)
	}
}
```

It turns signals into a context, calls `Run` with the real arguments, environment and output streams, and turns the error into an exit code (2 for configuration, 1 for anything else). Everything `Run` needs comes in as a parameter, so a test can supply different ones.

### Step 2: the whole service in a unit test

```go noverify
package app

import (
	"context"
	"errors"
	"io"
	"net/http"
	"strings"
	"testing"
	"time"
)

// TestRun starts the whole service in-process, as main does, on ports the
// OS picks, uses it over real HTTP, then cancels its context and checks
// that it shuts down cleanly.
func TestRun(t *testing.T) {
	ctx, cancel := context.WithCancel(t.Context())
	defer cancel()
	ready := make(chan string, 1)
	done := make(chan error, 1)
	go func() {
		done <- Run(ctx, []string{"-addr", "127.0.0.1:0", "-admin", "127.0.0.1:0"}, nil, io.Discard, io.Discard,
			Hooks{Ready: func(public, _ string) { ready <- "http://" + public }})
	}()
	base := <-ready

	for _, step := range []struct {
		method, path, user string
		want               int
	}{
		{"GET", "/readyz", "", 200},
		{"POST", "/movies/inception/seats/A7/hold", "alice", 201},
		{"POST", "/movies/inception/seats/A7/hold", "bob", 409},
	} {
		req, _ := http.NewRequestWithContext(ctx, step.method, base+step.path, nil)
		req.Header.Set("X-User", step.user)
		resp, err := http.DefaultClient.Do(req)
		if err != nil {
			t.Fatal(err)
		}
		resp.Body.Close()
		if resp.StatusCode != step.want {
			t.Errorf("%s %s as %q: %d, want %d", step.method, step.path, step.user, resp.StatusCode, step.want)
		}
	}

	start := time.Now()
	cancel()
	if err := <-done; err != nil {
		t.Fatalf("Run: %v", err)
	}
	t.Logf("shut down in %v", time.Since(start).Round(time.Microsecond))
}

func TestRunRejectsBadConfig(t *testing.T) {
	err := Run(t.Context(), []string{"-hold", "0s"}, nil, io.Discard, io.Discard, Hooks{})
	if !errors.Is(err, ErrConfig) || !strings.Contains(err.Error(), "hold: 0s") {
		t.Fatalf("got %v, want the hold problem", err)
	}
}
```

```text
    app_test.go:51: shut down in 85µs
--- PASS: TestRun (0.00s)
=== RUN   TestRunRejectsBadConfig
--- PASS: TestRunRejectsBadConfig (0.00s)
PASS
ok  	cinema/internal/app	1.107s
```

The test starts the **real** service, with the real configuration loader, the real wiring and real HTTP listeners on ports the OS picks (`127.0.0.1:0`; the `Ready` hook reports which). ## Shutdown Order

*Stop 4 of 5.*

### Step 1: an experiment with the wrong order

`Run`'s shutdown does three things in order: fail readiness, drain HTTP, close Redis. To measure why the order matters, the service can be built with the order reversed, through a variable set at link time:

```text
$ go build -ldflags "-X cinema/internal/app.shutdownOrder=redis-first" -o cinema-redis-first ./cmd/cinema
```

`order.sh` slows every Redis reply to 300 ms with Toxiproxy, sends 50 holds and 200 seat-map requests a second, and sends SIGTERM 1.9 s in. Draining first:

### Step 2: the rule behind it

Start dependencies innermost first; stop them outermost first. The HTTP server depends on the store, the store on the Redis client, so they start client → store → server and stop server → store → client. `Run`'s code says it three times in comments because it's easy to get wrong when a new component is added at the end of `main` "because that's where the code is". The lab builds a small lifecycle runner that enforces the rule for any list of components.

## The Image

*Stop 5 of 5.*

### Step 1: two stages

The build needs the Go toolchain; running needs only the binary. A **multi-stage** Dockerfile builds in one image and copies the result into another:

```text
# syntax=docker/dockerfile:1

# ── build: the full Go toolchain, discarded after this stage ───────────
FROM golang:1.27 AS build
WORKDIR /src
# Dependencies first: this layer is cached until go.mod or go.sum change.
COPY go.mod go.sum ./
RUN go mod download
COPY . .
# Static binary (no cgo, no libc), no local paths (chapter 15). The cache
# mount keeps Go's build cache between image builds.
RUN --mount=type=cache,target=/root/.cache/go-build \
    CGO_ENABLED=0 go build -trimpath -o /out/cinema ./cmd/cinema

# ── run: just the binary, CA certificates and a non-root user ───────────
FROM gcr.io/distroless/static-debian12:nonroot
COPY --from=build /out/cinema /cinema
USER nonroot:nonroot
EXPOSE 8091
ENTRYPOINT ["/cinema"]
```

- `go mod download` runs before the source is copied, so the dependency layer is reused until `go.mod` or `go.sum` change.
- `CGO_ENABLED=0` produces a static binary, which needs no C library in the final image; `-trimpath` makes it reproducible (chapter 15).
- `distroless/static:nonroot` contains CA certificates, time zone data and a non-root user, and nothing else: no shell, no package manager.

### Step 2: measured

```text
$ docker images cinema
cinema:single  1.59GB
cinema:multi  25.6MB
$ docker inspect cinema:multi --format '{{.Config.User}}'
nonroot:nonroot
$ docker run -d --name cinema-app --network obs -p 127.0.0.1:18099:8091 \
    -e CINEMA_ADDR=:8091 -e CINEMA_STORE=redis -e CINEMA_REDIS_ADDR=cinema-redis:6379 cinema:multi
$ curl -s -o /dev/null -w "%{http_code}\n" -XPOST -H "X-User: alice" localhost:18099/movies/inception/seats/A1/hold
201
$ time docker stop cinema-app
  stopped in 0.23 s
$ docker logs cinema-app
  cinema on http://[::]:8091 (admin 127.0.0.1:6060), store=redis
  shutting down: terminated signal received
  stopped
```

**25.6 MB** instead of 1.59 GB for the same service built and run in the `golang` image (`Dockerfile.single`): smaller to push and pull on every deploy, and with no compiler, shell or package manager for an attacker to use. The container runs as `nonroot`, takes its configuration from `CINEMA_*` variables (chapter 16's environment layer), holds a seat, and stops in **0.23 s**: the binary is PID 1 (the exec-form `ENTRYPOINT`), receives SIGTERM directly, and runs the ordered shutdown. A process that ignores SIGTERM is killed by `docker stop` after 10 seconds instead.

### Step 3: fast rebuilds

The first version of the Dockerfile rebuilt the whole service after any code change, **13.4 s**, because each image build starts with an empty Go build cache. A **cache mount** keeps the build cache between builds (it's not part of any image):

```text
rebuild after a code change, with the cache mount: 2.1 s
rebuild after a code change, with the cache mount: 2.0 s
```

The CI workflow from chapter 15 builds this image as its last step; the same Dockerfile serves laptops and CI.

<Exercise n={1} title="Draw the import graph" level="easy">

Run `go list -f '{{.ImportPath}}: {{join .Imports " "}}' ./internal/...` and draw the graph of `cinema/internal/...` packages only. Which packages does nothing import, and which does everything import?

<Exercise n={2} title="Enforce the direction" level="medium">

Write a test in `internal/booking` that fails if the package ever imports `net/http` or `github.com/redis/go-redis/v9`, directly or indirectly.

</Solution>

</Exercise>

<Exercise n={3} title="Add a component" level="medium">

Chapter 13's hold sweeper should run inside the service. Where does it go in `Run`, and where in the shutdown order?

<Solution>

Construct it after the store (it uses the store) and start it with the HTTP servers, as another `g.Go` that runs until `gctx` is done. It depends on the store, like the handlers, so it must stop **before** Redis closes: cancel it, wait for its current sweep to finish, then close Redis. In the lab's terms: store, then sweeper, then HTTP to start; HTTP, then sweeper, then store to stop. If it runs on several replicas, it needs chapter 13's lease too.

</Solution>

</Exercise>

<Exercise n={4} title="A version in the binary" level="easy">

Make `cinema -version` print a version stamped at build time with `-ldflags -X`, and compare it with what `debug.ReadBuildInfo` already provides without any flags.

<Solution>

`var version = "dev"` in `main`, and `go build -ldflags "-X main.version=v1.4.0"`. But `debug.ReadBuildInfo()` already has `Main.Version` (a pseudo-version or tag derived from git since Go 1.24) and the `vcs.revision`, `vcs.time` and `vcs.modified` settings (chapter 15), with no build flags at all. <Exercise n={5} title="Shut down behind a load balancer" level="hard">

Change `Run` so that, on SIGTERM, it fails readiness, keeps serving for a configurable delay, then drains. Measure it by running two replicas behind a load balancer that polls `/readyz` every second (chapter 12's `rate.sh` setup, or Part 1 chapter 27's kind cluster), and count failed requests during a rolling restart with a delay of 0 and 5 s.

<Solution>

Add a `drain-delay` setting (default 5 s, validated 0–25 s so the total stays under Kubernetes' 30 s grace period). After `api.Draining.Store(true)`, `select` on `time.After(delay)` or a second signal, then call `Shutdown`. With delay 0, requests the balancer routes in the instant between readiness failing and it noticing hit a closed listener: connection errors. With a delay longer than the balancer's polling interval, they're all served, and the instance is idle by the time it drains. Part 1 chapter 27 measured this on Kubernetes: failures in 6 of 9 rollouts without draining, none with it.

</Solution>

</Exercise>

// Component is one part of a service with a lifecycle: a database pool, a
// cache, an HTTP server. Start must return once the component is running.
type Component struct {
	Name  string
	Start func(ctx context.Context) error
	Stop  func(ctx context.Context) error

// runAll starts comps in order, runs until ctx is done, then stops them.
// It is the only function you edit (you may add helpers above the line).
//
// The rules the checks hold it to:
//   - Stop in reverse order of starting: the HTTP server (started last)
//     must finish its in-flight requests before the store they use closes.
//   - If a Start fails, stop the components already started (in reverse)
//     and return the error, naming the component.
//   - Stop every component even if another's Stop fails, and return all
//     the errors (errors.Join).
//   - Give each Stop a context with stopTimeout, so a Stop that hangs
//     can't hang the shutdown.

	for _, c := range comps {
		c.Start(ctx)
	}
	<-ctx.Done()
	for _, c := range comps {
		if err := c.Stop(context.Background()); err != nil {
			return err
		}
	}
	return nil
}

	}
	return nil
}

	mu     sync.Mutex
	events []string
