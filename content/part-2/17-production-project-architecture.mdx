Before the first line of Go, you need to know *where* every file lives. Here is the structure that scales without giving you a PhD in archaeology:

```
ledger/
├── cmd/
│   └── ledger/
│       └── main.go          ← composition root; wires everything
├── internal/
│   ├── config/
│   │   └── config.go        ← validated config struct
│   ├── ledger/              ← domain layer (pure Go, zero HTTP, zero SQL)
│   │   ├── service.go       ← LedgerService: business logic
│   │   └── service_test.go
│   ├── postgres/            ← adapter: concrete repository using pgx
│   │   └── repo.go
│   ├── http/                ← transport adapter: handlers + router
│   │   ├── server.go
│   │   └── handler.go
│   └── secrets/
│       └── loader.go        ← Vault / env secret loading
├── migrations/              ← SQL migration files (golang-migrate / goose)
├── Makefile                 ← build / test / lint / run
├── Dockerfile
├── .golangci.yml
└── go.mod
```

Three zones, and they carry different rules.

**`cmd/`** — one directory per binary, one `main.go` each. This is the *only* place that knows how all the pieces fit together. It imports from `internal/`, reads config, constructs dependencies in order, and starts the server. Its job is pure *wiring*, not logic. If you find business logic in `main.go`, that's a bug in your architecture, not your program.

**`internal/`** — the workhorse. The `internal` visibility constraint (Go enforces it at the module boundary) means nothing outside this module can import these packages. That's a feature: it keeps the blast radius of any internal refactor contained to your own codebase. Inside `internal/`, the layering rules apply — see the next section.

**No `pkg/` directory.** The `pkg/` convention from the pre-module era is a vestige. In a single-module service there's no reason to have it. If something is genuinely reusable across binaries, it lives in its own module. If it's internal, it lives in `internal/`. Don't let cargo-cult layout slow you down.

**On the job:** You'll encounter this layout on your first day at a Go shop. The real failure mode is finding business logic in `cmd/` — "just a quick thing" that becomes a permanent load-bearing wall. Anything in `cmd/` that you can't unit-test in isolation is a future 3 a.m. problem.

## Dependency Injection

<Define term="Dependency Injection" since="Software Design & Architecture (Part 1)">
**Dependency injection** means a type receives its dependencies from the outside — passed in via a constructor — rather than creating or looking them up itself. Instead of `var db = openDB()` at package scope, your service accepts a `Repository` interface in `NewService(repo Repository)`. The caller (the composition root) decides which concrete implementation to pass. This lets tests pass a fast in-memory fake; production passes the real Postgres adapter. You get testability, swappability, and zero globals — for free.
</Define>

Here's the thing, sport: **global state is the enemy of testability.** The moment you write `var db *pgx.Conn` at package scope, you've welded that concrete implementation into every function that touches it. Swap it for a test double? You can't — it's in everyone's bloodstream. Write a test that runs in parallel? Now you're fighting for the one global. That's not engineering; that's amateur hour.

The Go solution is disarmingly simple: **constructor injection at the composition root.** Accept interfaces, return concrete structs, build everything in `main`, and pass it down.

**On the job:** Globals bite hardest in integration tests and on-call. When two test workers share one global DB connection and one of them runs a migration, the other's queries return nonsense. Injected deps mean each test worker constructs its own fake — parallel-safe, instant, no flakes.

Here is the canonical shape for a service type:

```go
// internal/ledger/service.go

package ledger

import (
	"context"
	"fmt"
	"time"
)

// Repository is defined by the *consumer* (the domain layer),
// not by the implementation. The Postgres package implements it;
// the test uses a fake.
type Repository interface {
	PostTransfer(ctx context.Context, t Transfer) (TransferID, error)
	GetBalance(ctx context.Context, accountID AccountID) (int64, error)
}

// EventBus is also defined here, at the consumer.
type EventBus interface {
	Publish(ctx context.Context, topic string, payload []byte) error
}

// Service holds only interfaces. It knows nothing about Postgres or Kafka.
type Service struct {
	repo Repository
	bus  EventBus
	now  func() time.Time // injected clock — testable without time.Sleep
}

// NewService is the constructor. Every dep is required; we fail fast in main
// if anything is nil rather than discovering it at the first request.
func NewService(repo Repository, bus EventBus) *Service {
	if repo == nil {
		panic("ledger.NewService: repo must not be nil")
	}
	return &Service{repo: repo, bus: bus, now: time.Now}
}
```

The interface lives *in the package that uses it* — not in the package that implements it. This is the "accept interfaces at consumers" proverb in action, and it's what lets you swap the concrete Postgres repo for a thin in-memory fake in tests without changing a single line of domain code.

```go
package main

import (
	"context"
	"fmt"
	"time"
)

// Domain interfaces — defined at the consumer.
type Ledger interface {
	PostTransfer(ctx context.Context, from, to int64, cents int64) error
}

// Concrete implementation (would normally be in internal/postgres/).
type postgresLedger struct {
	dsn string
}

func (p *postgresLedger) PostTransfer(_ context.Context, from, to, cents int64) error {
	fmt.Printf("postgres: transfer %d cents from acct %d to acct %d\n", cents, from, to)
	return nil
}

// In-memory fake for tests — same interface, zero infrastructure.
type fakeLedger struct{ calls int }

func (f *fakeLedger) PostTransfer(_ context.Context, _, _, _ int64) error {
	f.calls++
	return nil
}

// Service depends only on the interface — not the concrete type.
type TransferService struct {
	ledger Ledger
	now    func() time.Time
}

func NewTransferService(l Ledger) *TransferService {
	return &TransferService{ledger: l, now: time.Now}
}

func (s *TransferService) Transfer(ctx context.Context, from, to, cents int64) error {
	if cents <= 0 {
		return fmt.Errorf("amount must be positive, got %d", cents)
	}
	return s.ledger.PostTransfer(ctx, from, to, cents)
}

func main() {
	ctx := context.Background()

	// Production wiring: real Postgres adapter.
	prod := NewTransferService(&postgresLedger{dsn: "postgres://..."})
	_ = prod.Transfer(ctx, 1001, 1002, 5000)

	// Test wiring: in-memory fake — no DB, no container, instant.
	fake := &fakeLedger{}
	svc := NewTransferService(fake)
	_ = svc.Transfer(ctx, 1001, 1002, 5000)
	fmt.Println("fake ledger calls:", fake.calls) // 1
}
```

### Manual DI vs. Wire/fx

You've probably seen `google/wire` or `uber-go/fx` mentioned in the same breath as dependency injection. Here's my honest take.

For a service with 5–15 constructors, **manual wiring in `main` is better.** It's readable — you can follow the construction order with your eyes. It's debuggable — the stack trace goes straight to `main`. And it has zero magic: no code generation to troubleshoot, no reflection at startup, no framework to update.

`wire` or `fx` earn their keep once a service has 30+ constructors and a human can't reliably maintain the wiring by hand. Until then, the framework adds complexity faster than it removes it. Start manual. Migrate if the pain genuinely arrives.

<UnderTheHood title="Why the composition root in main keeps everything testable">

The key insight is **where knowledge of concrete types lives**. In an injected design, only `main.go` (the composition root) imports both `internal/ledger` (the domain) and `internal/postgres` (the adapter). The domain package imports neither `pgx` nor `net/http`. The HTTP handler imports only the domain interface.

This means:

- Testing the domain service: instantiate `Service` with a `fakeLedger` — no DB, no network, instant, parallel-safe.
- Testing the HTTP handler: wrap a `fakeService` — no DB, no Kafka, no secrets.
- Testing the Postgres adapter: use `testcontainers` to spin up a real DB — this is the only test that needs infrastructure.

Each test only needs exactly the infrastructure its layer actually uses. This is the payoff of having no globals and no concrete imports in the inner layers. The composition root knows everything; the inner layers know nothing outside their own interface. The Go compiler enforces this at the module boundary (Go 1.26 baseline): if your domain package imports `pgx`, it fails to compile when you ban that import — the architecture becomes a compile-time guarantee, not a convention.

</UnderTheHood>

## Layered Architecture

<Define term="Hexagonal Architecture (Ports and Adapters)" since="Software Design & Architecture (Part 1)">
**Hexagonal architecture** (also called ports and adapters) organizes a service into three rings. The **domain** (the center) holds business rules — pure Go, no HTTP, no SQL. The **ports** are interfaces the domain defines: a `Repository` port for storage, an `EventBus` port for messaging. The **adapters** are concrete implementations that plug into those ports: the Postgres adapter, the Kafka adapter, the HTTP transport. Crucially, the domain never imports an adapter — the dependency arrow always points *inward*. This means you can replace Postgres with SQLite or swap Kafka for a test fake without touching a single line of business logic.
</Define>

The ledger service has three layers, and their dependency rule is non-negotiable: **dependencies point inward only.**

- **Transport** (`internal/http/`) — decodes HTTP requests, encodes responses, validates input shape, enforces auth. Imports the domain layer via interfaces. Never imports `pgx` or any SQL package.
- **Domain** (`internal/ledger/`) — the business rules. Pure Go structs, methods, and interfaces. Imports nothing from transport or storage. This is where Meridian's accounting invariants live.
- **Adapters** (`internal/postgres/`, `internal/kafka/`, etc.) — concrete implementations of the domain's interfaces. They import `pgx`, `confluent-kafka-go`, whatever they need. But they are *imported* by `main`, not by the domain.

This is hexagonal architecture (also called "ports and adapters"), and in Go it maps perfectly to the interface pattern: the domain defines the *port* (an interface), and each adapter provides a *plug* (a concrete implementation). The transport layer is also an adapter — it adapts HTTP to domain calls.

**On the job:** The layer boundary violation that kills teams: a handler importing `pgx` directly "just to run one query." Now your handler test needs a database container. Now your handler owns SQL that nobody else can reuse. The rule is non-negotiable precisely because "just this once" is how layers collapse.

```go
// internal/http/handler.go — transport layer

package http

import (
	"context"
	"encoding/json"
	"net/http"

	"github.com/myco/ledger/internal/ledger"
)

// The handler depends on the domain interface only — not on postgres or kafka.
type TransferHandler struct {
	svc ledger.Transferer // interface defined in internal/ledger
}

func NewTransferHandler(svc ledger.Transferer) *TransferHandler {
	return &TransferHandler{svc: svc}
}

type transferRequest struct {
	FromAccountID int64 `json:"from_account_id"`
	ToAccountID   int64 `json:"to_account_id"`
	AmountCents   int64 `json:"amount_cents"`
}

func (h *TransferHandler) ServeHTTP(w http.ResponseWriter, r *http.Request) {
	var req transferRequest
	if err := json.NewDecoder(r.Body).Decode(&req); err != nil {
		http.Error(w, "bad request", http.StatusBadRequest)
		return
	}
	if err := h.svc.Transfer(r.Context(), req.FromAccountID, req.ToAccountID, req.AmountCents); err != nil {
		http.Error(w, err.Error(), http.StatusUnprocessableEntity)
		return
	}
	w.WriteHeader(http.StatusCreated)
}
```

## Config and Secret Wiring

We spent all of the Configuration & Secrets Management chapter learning *how* to load config and secrets. Now we wire them into the service at startup. The rule is unchanged: **fail fast, before the first request.**

```go
// cmd/ledger/main.go (excerpt: config phase)

package main

import (
	"log/slog"
	"os"

	"github.com/myco/ledger/internal/config"
	"github.com/myco/ledger/internal/secrets"
)

func main() {
	// 1. Load and validate config — exits with a clear message if anything
	//    is missing or malformed.
	cfg, err := config.Load()
	if err != nil {
		slog.Error("config invalid, refusing to start", "err", err)
		os.Exit(1)
	}

	// 2. Load secrets from Vault (or env in dev).
	//    Rotation is handled by the secrets loader; the rest of the service
	//    never touches raw secret values directly.
	sec, err := secrets.Load(cfg.VaultAddr, cfg.VaultToken)
	if err != nil {
		slog.Error("secret load failed", "err", err)
		os.Exit(1)
	}

	// 3. Open DB with the DSN from secrets (never from config files — DSNs
	//    contain passwords).
	pool, err := openDB(sec.PostgresDSN, cfg.DB)
	if err != nil {
		slog.Error("could not open database", "err", err)
		os.Exit(1)
	}
	defer pool.Close()

	// … build the rest of the deps and start the server.
}
```

Two points worth hammering:

**Config and secrets are separate concerns.** Config (port, timeout, feature flags) travels through environment variables or a config file and is fine to log at startup. Secrets (passwords, API keys, signing keys) come from a secrets manager and are **never logged, never exposed in `/debug/vars`, never in error messages.** The `secrets.Loader` type should implement `fmt.Stringer` with a redacted output so a careless `slog.Info("loaded", "sec", sec)` doesn't leak the DSN.

**Open infra connections before building business objects.** You can't hand a nil pool to the Postgres adapter. Order matters: infra first, then adapters, then services, then transport, then `ListenAndServe`. If any step fails, `os.Exit(1)` — the service is not partially up, it's just dead.

**On the job:** A service that starts with a missing secret and serves 500s for an hour is worse than one that refuses to start at all. Hard fail at startup. Your orchestrator will restart it when the secret is available; your users won't see a wall of 500s in the meantime.

```go
		return
	}

	// Notice: logging the secret struct prints REDACTED, not the DSN.
	fmt.Printf("secrets loaded: %v\n", sec)

}
```

<Define term="Graceful Shutdown" since="Reliability Patterns (Part 2)">
**Graceful shutdown** means the process finishes what it's already doing before it exits. When Kubernetes sends `SIGTERM` (pod is being stopped), a naive service calls `os.Exit` immediately — dropping every in-flight HTTP request mid-write. A service with graceful shutdown stops accepting new connections, waits for in-flight requests to complete (typically up to 30 seconds), closes background workers, then closes infrastructure connections in reverse order, and exits 0. The caller gets their response; no cascading retries; no open transactions left dangling in Postgres.
</Define>

A service that terminates badly drops in-flight requests, leaves DB transactions open, and triggers cascading retries from callers. That's not a Kubernetes outage; it's a management problem. Here is the lifecycle every production Go service must have:

1. **Open infrastructure** (DB pool, Kafka client, Redis) — in dependency order.
2. **Build application objects** (repos, services, handlers) via constructors.
3. **Start background workers** (job queue consumers, metrics exporters).
4. **Start the HTTP server** — but don't block; run it in a goroutine.
5. **Block on signal** — `signal.NotifyContext` wakes you on `SIGTERM` or `SIGINT`.
6. **Graceful shutdown** — drain in-flight HTTP requests, stop background workers, close infra in reverse order.

**On the job:** Kubernetes sends `SIGTERM` then waits `terminationGracePeriodSeconds` (default 30 s) before sending `SIGKILL`. If your drain window is longer than 30 s, the pod is force-killed and you drop requests anyway. Match your drain timeout to the Kubernetes grace period — or configure both explicitly.

Here is a complete, runnable graceful shutdown skeleton. As of Go 1.26, when a signal cancels the context returned by `signal.NotifyContext`, `context.Cause(ctx)` reports an error describing that signal. This is useful for distinguishing a SIGTERM drain from a timeout drain in your logs:

```go
// cmd/ledger/main.go — graceful lifecycle (Go 1.26)

package main

import (
	"context"
	"errors"
	"fmt"
	"log/slog"
	"net/http"
	"os"
	"os/signal"
	"syscall"
	"time"
)

func run() error {
	// Phase 1: config (omitted here — see previous section).

	// Phase 2: build the router (your real handler wiring goes here).
	mux := http.NewServeMux()
	mux.HandleFunc("GET /health", func(w http.ResponseWriter, r *http.Request) {
		w.WriteHeader(http.StatusOK)
	})

	srv := &http.Server{
		Addr:         ":8080",
		Handler:      mux,
		ReadTimeout:  5 * time.Second,
		WriteTimeout: 10 * time.Second,
		IdleTimeout:  60 * time.Second,
	}

	// Phase 3: context that cancels on SIGTERM / SIGINT.
	// Go 1.26: context.Cause(ctx) reports the signal that canceled it.
	ctx, stop := signal.NotifyContext(context.Background(), syscall.SIGTERM, syscall.SIGINT)
	defer stop()

	// Phase 4: start server in background goroutine.
	srvErr := make(chan error, 1)
	go func() {
		slog.Info("server starting", "addr", srv.Addr)
		if err := srv.ListenAndServe(); !errors.Is(err, http.ErrServerClosed) {
			srvErr <- err
		}
	}()

	// Phase 5: block until signal or server error.
	select {
	case err := <-srvErr:
		return fmt.Errorf("server error: %w", err)
	case <-ctx.Done():
		slog.Info("shutdown signal received", "cause", context.Cause(ctx))
	}

	// Phase 6: graceful drain — allow 30 s for in-flight requests to finish.
	drainCtx, cancel := context.WithTimeout(context.Background(), 30*time.Second)
	defer cancel()
	if err := srv.Shutdown(drainCtx); err != nil {
		return fmt.Errorf("shutdown: %w", err)
	}
	slog.Info("server stopped cleanly")
	return nil
}

func main() {
	if err := run(); err != nil {
		slog.Error("fatal", "err", err)
		os.Exit(1)
	}
}
```

<UnderTheHood title="Why signal.NotifyContext and how Shutdown drains">

`signal.NotifyContext` (added in Go 1.16) registers the process to catch OS signals and returns a `context.Context` that is canceled when a signal arrives. The underlying mechanism is `signal.Notify` delivering to a buffered channel, which the context machinery watches via a goroutine. When the context cancels, your `<-ctx.Done()` unblocks — no polling, no timer, no goroutine leak. As of Go 1.26, if a signal cancels the context, `context.Cause` returns an error describing that signal, so you can distinguish a SIGTERM shutdown from a timeout-driven cancel in structured log output.

`(*http.Server).Shutdown` works by:

1. Closing the listener — no new connections are accepted.
2. Closing idle keep-alive connections immediately.
3. Waiting for in-flight requests (those with an active `ResponseWriter`) to complete, up to the deadline on the context you pass in.

Under the hood, each active handler holds a reference tracked in the server's `activeConn` map. `Shutdown` polls that map (with a 500 ms ticker) until it's empty or the context times out. If you pass a 30-second drain context, you give up to 30 seconds for every concurrent request to finish normally before forcing a close. This is exactly what Kubernetes expects: it sends `SIGTERM`, waits for `terminationGracePeriodSeconds` (default 30 s), then sends `SIGKILL`. Your 30 s drain window matches that window. `Shutdown` also calls `RegisterOnShutdown` hooks — useful for stopping WebSocket connections or background goroutines that the server doesn't track. Note: the `activeConn` polling is an implementation detail of the Go runtime as of Go 1.26 and may change; the guaranteed behavior is the contract described in the `net/http` package documentation.

</UnderTheHood>

## CI/CD-Ready Layout

A production service needs more than Go files. It needs repeatable build commands, a multi-stage Docker image, and a lint/test/race pipeline that blocks the merge button on bad code.

### Makefile

```makefile
# Makefile — repeatable commands for humans and CI alike.

BINARY   := ledger
VERSION  ?= dev
GOFLAGS  := -trimpath -ldflags="-X main.version=$(VERSION)"

.PHONY: build test lint race docker

build:
	go build $(GOFLAGS) -o bin/$(BINARY) ./cmd/$(BINARY)

test:
	go test ./... -count=1 -timeout=120s

race:
	go test ./... -race -count=1 -timeout=120s

lint:
	golangci-lint run ./...

docker:
	docker build -t $(BINARY):$(VERSION) .

migrate-up:
	migrate -path migrations/ -database "$$DATABASE_URL" up
```

Every engineer and every CI runner calls the same targets. No "works on my machine" — the `Makefile` is the contract.

### Dockerfile (multi-stage)

```dockerfile
# Stage 1: build — full Go toolchain, creates a static binary.
FROM golang:1.26-bookworm AS build
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 go build -trimpath -ldflags="-s -w" \
    -o /bin/ledger ./cmd/ledger

# Stage 2: run — no toolchain, no source, just the binary.
FROM gcr.io/distroless/static-debian12:nonroot
COPY --from=build /bin/ledger /ledger
ENTRYPOINT ["/ledger"]
```

The distroless image is ~2 MB. No shell, no package manager, no attack surface. `CGO_ENABLED=0` produces a fully static binary that runs in it without any shared-library dependencies. Multi-stage builds are covered in depth in Docker & Containerization (Part 1).

### GitHub Actions pipeline

```yaml
# .github/workflows/ci.yml
name: CI
on: [push, pull_request]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-go@v5
        with:
          go-version: "1.26"
          cache: true
      - run: make test
      - run: make race
      - run: make lint
      - run: make build
```

Four lines of `make` targets. CI runs the same commands you run locally — no divergence, no "but it worked on my laptop."

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"net/http"
	"os"
	"os/signal"
	"sync"
	"syscall"
	"time"
)

func run() error {
	mux := http.NewServeMux()
	mux.HandleFunc("GET /health", func(w http.ResponseWriter, r *http.Request) {
		w.WriteHeader(http.StatusOK)
	})

	defer stop()

	workerCtx, workerCancel := context.WithCancel(context.Background())
	var wg sync.WaitGroup
	wg.Add(1)
	go func() {
		defer wg.Done()
		t := time.NewTicker(time.Second)
		defer t.Stop()
		for {
			select {
			case <-workerCtx.Done():
				fmt.Println("worker stopped")
				return
			case <-t.C:
				fmt.Println("worker tick")
			}
		}
	}()

	srvErr := make(chan error, 1)
	go func() {
		if err := srv.ListenAndServe(); !errors.Is(err, http.ErrServerClosed) {
			srvErr <- err
		}
	}()

	select {
	case err := <-srvErr:
		workerCancel()
		wg.Wait()
		return err
	case <-ctx.Done():
		fmt.Println("signal received")
	}

	// Cancel the worker first, wait for it to exit.
	workerCancel()
	wg.Wait()

	// Then drain the HTTP server.
	drainCtx, cancel := context.WithTimeout(context.Background(), 10*time.Second)
	defer cancel()
	if err := srv.Shutdown(drainCtx); err != nil {
		return err
	}
	fmt.Println("server stopped cleanly")
	return nil
}

func main() {
	if err := run(); err != nil {
		fmt.Fprintln(os.Stderr, "fatal:", err)
		os.Exit(1)
	}
```
