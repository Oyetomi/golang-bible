## Structured logging with slog

Here's the scenario. Your ledger service processes fund transfers. A transfer fails at 02:47 UTC and you get paged. You crack open the logs and see:

```
2024/11/15 02:47:22 transfer failed: insufficient funds
```

Splendid. Which transfer? Which account? Which user? Which service instance? You have *nothing*. This is what printf logging looks like in production, and it's the engineering equivalent of leaving a crime scene note that says "something happened."

Structured logging is the fix. Instead of a free-form string, you emit a **machine-readable record** — key/value pairs alongside the message, written as JSON. Every downstream system — log aggregators, alerting rules, dashboards — can filter, group, and index those fields instantly.

<Define term="Structured logging (slog)" since="this chapter">
A log record that carries **named fields** (key/value attributes) alongside the message, serialised as JSON or another machine-readable format. Without it, a log line is a string only a human can parse; with it, every aggregator, alert rule, and dashboard can filter on `level`, `transfer_id`, `error`, or any other field in milliseconds. **`log/slog`** (added in Go 1.21) is the standard-library implementation — your default for any Go service from here on.
</Define>

Go 1.21 shipped `log/slog` as the official structured logging package. It is your default from here on; the old `log` package is for scripts, not services.

### The three-line mental model

1. A **Logger** emits records.
2. A **Handler** formats and routes them (JSON to stdout, text to stderr, both, whatever).
3. Every record carries a **level**, a **message**, and zero or more **attributes** (the key/value pairs).

```go
package main

import (
	"context"
	"log/slog"
	"os"
)

func main() {
	// JSON handler → structured output your log aggregator loves
	logger := slog.New(slog.NewJSONHandler(os.Stdout, nil))

	// A plain message at Info level
	logger.Info("server starting", "addr", ":8080", "version", "1.4.2")

	// With a Context — slog will extract trace IDs from it
	// if your handler is wired to do so (more on that shortly)
	ctx := context.Background()
	logger.InfoContext(ctx, "transfer accepted",
		"from_account", "acc_001",
		"to_account",   "acc_002",
		"amount_cents", 5000,
	)

	// Errors deserve their own level — they're actionable
	logger.Error("transfer rejected",
		"from_account", "acc_001",
		"reason",        "insufficient_funds",
		"balance_cents", 2300,
		"amount_cents",  5000,
	)
}
```

Run it and notice the output: each line is a valid JSON object with `time`, `level`, `msg`, and every extra attribute you passed. Copy it into `jq` and you can filter `select(.level == "ERROR")` in milliseconds. Do that with a printf string.

### Levels

`slog` has four built-in levels, lowest to highest: `Debug`, `Info`, `Warn`, `Error`. Your handler's minimum level gates what actually gets written. In production you almost always set `Info` as the floor — `Debug` is noise at scale.

```go
opts := &slog.HandlerOptions{Level: slog.LevelInfo}
logger := slog.New(slog.NewJSONHandler(os.Stdout, opts))
// Debug calls now produce no output
logger.Debug("database query", "sql", "SELECT …") // silent
logger.Info("transfer accepted", "id", "tx_999")   // emitted
```

### `With` — context fields that stick

Decorating every log call with `"service", "ledger"` would be maddening. `With` creates a **child logger** that permanently carries extra attributes. Inject it once at startup; every call inherits the fields:

```go
base := slog.New(slog.NewJSONHandler(os.Stdout, nil))

// Service-wide fields
serviceLogger := base.With(
	"service", "ledger",
	"env",     "production",
	"region",  "us-east-1",
)

// Request-scoped fields — make one per incoming HTTP request
func handleTransfer(w http.ResponseWriter, r *http.Request, log *slog.Logger) {
	reqLog := log.With(
		"request_id", r.Header.Get("X-Request-ID"),
		"user_id",    userFromContext(r.Context()),
	)
	// Every log inside this handler carries request_id + user_id automatically
	reqLog.Info("processing transfer")
}
```

The child logger does not copy the parent's attributes on every call — it holds a slice of attr groups and the JSON handler renders them left-to-right. The `slog.LogValuer` interface, part of `log/slog` since Go 1.21, lets you defer expensive attribute resolution until the record is actually written.

<Callout kind="warn" title="Never log secrets or PII">

Structured logs are *more* dangerous than printf logs for one reason: they make it trivially easy to accidentally log a struct that contains a password, a card number, or a social security number. Implement `slog.LogValuer` on any type that holds sensitive data and return a redacted representation. Define a `redact` helper and use it at the logging boundary — never patch it after the fact. This connects directly to the Application Security chapter; a log line in an aggregator is just another attack surface.

</Callout>

### Text vs. JSON handler

`NewTextHandler` produces `key=value` pairs — friendlier for humans reading a local terminal, wrong for a production aggregator that ingests JSON. Use text in development, JSON in production. A twelve-factor config flag (`LOG_FORMAT=json|text`) makes this switchable at deploy time:

<UnderTheHood title="How slog avoids allocations (Go 1.21+)">

`slog.Attr` values use a `Value` type that stores the most common kinds (`Int64`, `String`, `Bool`, `Float64`, `Time`, `Duration`) inline as a discriminated union — a `kind` byte plus a 64-bit slot — with no heap allocation. Only `Any` (which boxes an arbitrary `interface{}`) allocates. The `Record` itself preallocates five attr slots inline (a `[5]Attr` array in the struct); the sixth and beyond spill to a heap slice. In practice, most log calls carry fewer than five attributes and touch zero heap. This is why `slog` is faster than `zap` on the hot path for low-attribute records as of Go 1.21. Check `go doc log/slog.Value` for the internals — the design is a masterclass in the data-oriented principles from Data Semantics & Data-Oriented Design (Part 1).

## Metrics with Prometheus

Logs tell you *what* happened on individual requests. Metrics tell you *how* the system is doing *in aggregate* — requests per second, error rate, 99th-percentile latency — across every request for the past hour. You cannot derive those from logs efficiently. You need metrics.

**Prometheus** is the de facto metrics standard for Go services. It works on a pull model: your service exposes a `/metrics` HTTP endpoint; a Prometheus server scrapes it on a schedule; dashboards and alerting rules query the scraped time-series data.

### The three types you actually use

<Define term="Metric (counter / gauge / histogram)" since="this chapter">
A **metric** is a numeric measurement sampled over time — the aggregate view of what's happening across all requests, not any single one. Three shapes cover almost everything: a **counter** counts events (total transfers, total errors) and only goes up; a **gauge** records a current value that can rise or fall (active connections, queue depth); a **histogram** buckets observations by magnitude so you can derive percentiles (p99 latency). If structured logs are your microscope, metrics are your thermometer — cheap to read at any scale, instant to query.
</Define>

<ConceptGrid cols={3}>
  <ConceptCard label="Counter">Monotonically increasing. Only goes up. Use for: total requests, total errors, total bytes sent. Never use a counter for a value that can decrease.</ConceptCard>
  <ConceptCard label="Gauge">A value that goes up and down. Use for: active connections, queue depth, goroutine count, memory in use. The current value is what matters.</ConceptCard>
  <ConceptCard label="Histogram">Records observations in configurable buckets and computes percentiles. Use for latency, request sizes. This is the type that powers your p99 SLO. Expensive but essential.</ConceptCard>
  <Gotcha>High-cardinality labels will destroy your Prometheus. A label with one value per user ID, order ID, or URL path will create millions of time series and OOM your server. Labels must have a bounded, low cardinality set of values — status codes, service names, method names. Never a raw ID.</Gotcha>
</ConceptGrid>

Here is a minimal, self-contained instrumented handler using `prometheus/client_golang`. The `/metrics` scrape endpoint won't run in the playground (it requires a live HTTP server), but the counter increment does — this example exercises the counter and prints the current value:

```go
package main

import (
	"fmt"

	"github.com/prometheus/client_golang/prometheus"
	"github.com/prometheus/client_golang/prometheus/promauto"
)

var (
	// promauto registers automatically — no manual Register call.
	transfersTotal = promauto.NewCounterVec(
		prometheus.CounterOpts{
			Name: "ledger_transfers_total",
			Help: "Total number of transfer attempts, by result.",
		},
		[]string{"result"}, // label: "success" | "insufficient_funds" | "error"
	)

	transferDuration = promauto.NewHistogramVec(
		prometheus.HistogramOpts{
			Name:    "ledger_transfer_duration_seconds",
			Help:    "Latency of transfer processing.",
			Buckets: prometheus.DefBuckets, // .005 .01 .025 .05 .1 .25 .5 1 2.5 5 10
		},
		[]string{"result"},
	)
)

func processTransfer(fromAcc, toAcc string, amountCents int) error {
	// In real code: timer := prometheus.NewTimer(...)
	// Here we just increment the counter to demonstrate the API.
	if amountCents <= 0 {
		transfersTotal.WithLabelValues("error").Inc()
		return fmt.Errorf("invalid amount: %d", amountCents)
	}
	transfersTotal.WithLabelValues("success").Inc()
	return nil
}

func main() {
	// Simulate a batch of transfers
	_ = processTransfer("acc_001", "acc_002", 5000)
	_ = processTransfer("acc_001", "acc_002", 3000)
	_ = processTransfer("acc_001", "acc_002", -1) // will error

	// In production: expose prometheus.Handler() on /metrics.
	// NOTE: This playground snippet can't run an HTTP server.
	// The counter is registered in the default registry.
	fmt.Println("transfers processed (see /metrics for full output)")
}
```

<Callout kind="note" title="The /metrics endpoint in production">

In a real service you add one route: `http.Handle("/metrics", promhttp.Handler())`. The Prometheus server scrapes it every 15 seconds. The handler serializes every registered metric's current state in the Prometheus text format. That's the whole integration — the rest is configuration in your Prometheus server (`prometheus.yml`).

</Callout>

### RED and USE — what to measure

Two mental models tell you *which* metrics matter:

**RED** (for request-driven services): **R**ate (requests/sec), **E**rror rate (errors/sec or error %), **D**uration (latency percentiles). These are what *users* experience. Wire all three for every meaningful operation.

**USE** (for resources — CPU, memory, disk, goroutine pool): **U**tilization (how busy is it?), **S**aturation (how much backlog is queuing?), **E**rrors (hard failures). Use this lens on your infrastructure.

<UnderTheHood title="How histogram buckets work internally">

A `prometheus.Histogram` with the default 11 buckets (`DefBuckets`) stores 11 atomic `uint64` counters plus a sum and count — one counter per upper boundary. When you call `Observe(v)`, the library walks the bucket boundaries and atomically increments every counter whose boundary is `>= v`. The median and percentile queries in PromQL (`histogram_quantile`) reconstruct an approximation using linear interpolation between buckets. This means your bucket boundaries determine accuracy — if all your transfers take 50–100ms but your buckets jump from 0.025s to 0.1s, the p99 estimate is coarse. Choose buckets that match your actual latency distribution. `prometheus.LinearBuckets` and `prometheus.ExponentialBuckets` help. As of Go 1.24, the Prometheus Go client uses `sync/atomic` operations throughout; no mutex on the hot `Observe` path.

</UnderTheHood>

### expvar: zero-dependency metrics

Before you reach for a third-party client, know that the standard library already ships a metrics endpoint. The `expvar` package publishes application variables — plus a free dump of `runtime.MemStats`, the goroutine count, and your command line — as JSON on `/debug/vars`. Zero dependencies, three lines of wiring. For a small internal ledger tool, or for "is this thing even alive and how much memory is it eating," that's often all the visibility you need.

<Define term="expvar (/debug/vars)" since="Observability (Part 2)">
**`expvar`** is the standard library's built-in metrics exporter. Calling `expvar.NewInt("name")` registers a concurrency-safe counter; `expvar.Publish("name", expvar.Func(fn))` wires a live function (re-evaluated on every read) into the output. Mounting `expvar.Handler()` on `GET /debug/vars` serves every registered variable — alongside `memstats` and `cmdline`, which it exposes for free — as a single JSON object. No client library, no scrape config, no allocation on the hot path beyond an atomic add.
</Define>

So when do you pick which? `expvar` is built-in, instant, and perfect for quick visibility on a small service or a debugging session. **Prometheus is still the production standard** — it gives you the pull model with a real time-series database behind it, *dimensional labels* (`result="success"` vs `result="insufficient_funds"` on one metric), `histogram_quantile` for percentiles, and an alerting pipeline. `expvar` is a flat JSON blob: no labels, no history, no alerts. Use `expvar` for "show me the current numbers"; use Prometheus for "page me when the numbers go wrong."

The snippet below registers a counter and a live goroutine gauge, then reads them back *in the same process* via `expvar.Get(...).String()` — so it runs offline under `go run` with no HTTP server. In a real service you'd instead mount `expvar.Handler()` and let a browser or a scraper hit `/debug/vars`.

<GoPlayground>

```go
package main

import (
	"expvar"
	"fmt"
	"runtime"
)

func main() {
	// expvar.NewInt registers a named, concurrency-safe counter and
	// publishes it on the default expvar map (served at /debug/vars).
	transfers := expvar.NewInt("ledger_transfers_total")
	transfers.Add(3) // three transfers processed

	// expvar.Publish wires a live function into the JSON output — it's
	// re-evaluated on every read, so the goroutine count is always current.
	expvar.Publish("goroutines", expvar.Func(func() any {
		return runtime.NumGoroutine()
	}))

	// In a real service you'd mount expvar.Handler() on GET /debug/vars.
	// Here we read the same published values back in-process so it runs
	// offline under `go run`, no HTTP server required.
	fmt.Println("ledger_transfers_total =", expvar.Get("ledger_transfers_total").String())
	fmt.Println("goroutines             =", expvar.Get("goroutines").String())
}
```

</GoPlayground>

<Callout kind="warn" title="/debug/vars is a public endpoint by default">

Mounting `expvar.Handler()` registers `/debug/vars` on `http.DefaultServeMux` and dumps `cmdline` (your full argv, which may include flags or paths you'd rather not leak) and detailed `memstats`. In production, put it behind auth, bind it to a private admin port, or restrict it to localhost via your reverse proxy. The default `expvar` map also panics if you register the same name twice — pick stable names and register once at startup.

</Callout>

## Distributed Tracing with OpenTelemetry

Logs and metrics answer "what happened" and "how much." **Tracing** answers "what *path* did this request take, and where did the time go?" In a system with three or more services, a single user action touches multiple processes — and when the latency on one request spikes, you need to know *which span* on *which service* is to blame.

### Vocabulary: spans, traces, and context propagation

<Define term="Distributed trace (span / trace ID)" since="this chapter">
A **distributed trace** is the end-to-end record of one request as it crosses multiple services. It is made of **spans** — each span is one unit of work (an HTTP handler, a DB query, a gRPC call) with a start time, end time, status, and attributes. Every span shares a **trace ID** (a 128-bit value that identifies the whole request) and carries its own **span ID** plus the span ID of its parent, forming a call tree. When latency spikes, the trace waterfall shows you *exactly which span* on *which service* is slow — information that logs and metrics alone cannot give you.
</Define>

- A **trace** is the end-to-end story of one request, from the user's HTTP call to the final database write.
- A **span** is one unit of work within that trace — an HTTP handler, a database query, a gRPC call. Each span has a start time, end time, status, and arbitrary attributes.
- Every span carries a **trace ID** (identifies the whole trace) and a **span ID** (identifies this specific span). A child span records its parent's span ID, forming a tree.
- **Context propagation** is how the trace IDs travel across service boundaries — embedded in HTTP headers (the W3C `traceparent` standard) so a downstream service can attach its spans to the same trace.

Go's `context.Context` is the carrier. You propagate a span's context down the call chain; when a span opens a child (a downstream call, a DB query), it reads the parent from the context. No globals, no thread-local magic.

### Correlation IDs: tying logs + traces + metrics together

<Define term="Correlation ID" since="this chapter">
A **correlation ID** (also called a request ID or trace ID) is a single identifier threaded through every log line, trace span, and metric label for one request. Without it, a log error and its trace are two unrelated needles in a haystack. With it, `grep correlation_id=abc123` instantly surfaces every log line, the trace waterfall, and the exact metric observations for that request — even across three services. In practice, the OpenTelemetry trace ID *is* your correlation ID when OTel is wired; without OTel, a UUID injected in the outermost middleware and carried through `context.Context` does the same job.
</Define>

A correlation ID (also called a request ID or trace ID in many systems) is the key that lets you join a log line to the trace to the metric observation for the same request. In practice, **the OTel trace ID is your correlation ID** — you inject it into every log record at the handler level.

Here's the idiomatic pattern for wiring them together in a single HTTP server:

```go
package main

import (
	"context"
	"log/slog"
	"net/http"

	"go.opentelemetry.io/otel"
	"go.opentelemetry.io/otel/trace"
)

// traceLogger extracts the active span from ctx and injects
// trace_id + span_id into every log record — zero cost if no span.
func traceLogger(ctx context.Context, base *slog.Logger) *slog.Logger {
	span := trace.SpanFromContext(ctx)
	if !span.SpanContext().IsValid() {
		return base
	}
	sc := span.SpanContext()
	return base.With(
		"trace_id", sc.TraceID().String(),
		"span_id",  sc.SpanID().String(),
	)
}

func transferHandler(base *slog.Logger) http.HandlerFunc {
	tracer := otel.Tracer("ledger")
	return func(w http.ResponseWriter, r *http.Request) {
		ctx, span := tracer.Start(r.Context(), "handle_transfer")
		defer span.End()

		log := traceLogger(ctx, base)
		log.Info("transfer handler started",
			"from_account", r.FormValue("from"),
			"to_account",   r.FormValue("to"),
		)
		// … do work …
		log.Info("transfer handler complete")
	}
}

func main() {
	logger := slog.New(slog.NewJSONHandler(nil, nil))
	_ = logger
	// Real init: configure OTel exporter (OTLP/gRPC to collector),
	// register the tracer provider, and start the HTTP server.
}
```

<Callout kind="pro" title="Correlation IDs without OpenTelemetry">

If you're not ready for full OTel, generate a UUID in your outermost middleware, store it in the request context with a typed key (never a plain string), and thread it into every `slog.With` call. That single ID lets you `grep` every log line for a failing request. Simple and enormously effective. OTel trace IDs are the production-grade version of the same idea.

</Callout>

<UnderTheHood title="How the W3C traceparent header propagates context">

The W3C Trace Context specification defines a `traceparent` header with the format `00-{trace_id}-{parent_span_id}-{flags}`. `00` is the version; `{trace_id}` is a 128-bit hex value (32 chars); `{parent_span_id}` is the caller's 64-bit span ID; `{flags}` is a bitmask where bit 0 (`01`) means "sampled."

When the OTel HTTP client transport injects outgoing calls, it calls `propagators.Inject(ctx, carrier)` where `carrier` wraps the request's `http.Header`. On the receiving side, middleware calls `propagators.Extract(ctx, carrier)`, which reads the header and calls `trace.ContextWithRemoteSpanContext(ctx, sc)` to attach the parent. All of this is in `go.opentelemetry.io/otel/propagation`. The `context.Context` is the in-process propagation mechanism; HTTP headers are the inter-process mechanism. Neither requires a sidecar or agent — the library handles both.

Sampling flag `01` tells the downstream service that the root decided to keep this trace. A downstream service should *respect* the sampling decision from upstream, not make its own, to ensure all spans from a single trace either all land in storage or all get dropped. Inconsistent sampling produces broken waterfall views.

</UnderTheHood>

## The Consumption Side

You've emitted the signal. Now what? This is the section most observability courses quietly omit, which is extraordinary because it's the half that actually keeps users happy.

### SLIs — what to measure

<Define term="SLI / SLO" since="this chapter">
An **SLI** (Service Level Indicator) is a metric that measures something a *user actually notices* — request success rate, latency percentile, error rate. An **SLO** (Service Level Objective) is the numeric target you commit to for an SLI: "99.9% of transfers succeed, measured over a 28-day window." The SLO is the contract — between your team and your users, and between reliability work and feature work. Without an SLO you cannot answer "is this broken?" — you can only answer "is this different?" The difference matters enormously at 3 a.m.
</Define>

An **SLI** (Service Level Indicator) is a quantitative measure of service quality. Not every metric is an SLI — an SLI specifically measures something a *user notices*. The canonical SLI set for a request-driven API:

- **Availability**: fraction of requests that succeeded (HTTP 2xx / total requests).
- **Latency**: fraction of requests faster than a threshold (e.g. p99 < 200ms).
- **Error rate**: fraction of requests that returned a server error (5xx).
- **Throughput**: requests processed per second.

An SLI is *not* CPU utilization. A user does not experience CPU utilization. A user experiences a slow or failed request. Design your SLIs around the user's experience, not the machine's state.

### SLOs — the target

An **SLO** (Service Level Objective) puts a number on your SLI: "99.9% of requests succeed" or "99% of requests respond in under 200ms, measured over a 30-day rolling window." This is a commitment — to your users, your on-call team, and your business.

For the ledger service: `SLO: 99.9% of POST /transfers respond in < 500ms, measured over a 28-day window.`

That single sentence is worth more than a hundred dashboards without one, because now everyone agrees on what "broken" means.

### Error budgets — what burning one means

<Define term="Error budget" since="this chapter">
An **error budget** is the inverse of your SLO target — the fraction of requests that are *allowed* to fail or be slow. A 99.9% availability SLO means a 0.1% error budget: over 28 days of 10 million requests, that's 10,000 failures permitted. The budget is a shared resource owned jointly by product and engineering. While budget remains, shipping new features is allowed — risk is acceptable. When the budget hits zero, all hands pivot to reliability. This is not a cultural norm; it is a mechanical forcing function. It prevents "it's probably fine" from becoming "we're down on Friday."
</Define>

An error budget is the flip side of an SLO. If your SLO is 99.9% success, your error budget is 0.1% — the fraction of requests that are *allowed to fail*. Over a 28-day window of 10 million requests, your budget is 10,000 failing requests.

Once you've spent your error budget, you stop shipping new features and focus entirely on reliability. This is not optional — it is the mechanism that prevents the engineering team from treating "always on" as someone else's problem.

<Define term="Burn-rate alert" since="this chapter">
A **burn-rate alert** fires when your service is consuming its error budget *faster than it can afford to*. A burn rate of 1x means you'll exhaust the monthly budget in exactly 30 days — on target. A burn rate of 14.4x means you'll exhaust it in roughly 50 hours. Alerting at 14.4x over a 1-hour window is the standard fast-page threshold (Google SRE Workbook): it catches serious incidents early, with enough remaining budget to respond calmly. The key insight is that burn-rate alerts fire on the *rate of SLO consumption*, not a raw error percentage — so a 2% error rate that would exhaust your budget in 14 hours pages immediately, while a 0.05% blip during low-traffic hours stays silent.
</Define>

### Alerting on symptoms, not causes

The single biggest source of alert fatigue is alerting on *causes* — internal metrics that may or may not matter to a user. CPU at 80%? The service might be perfectly fast. Disk iops elevated? Who cares if latency is fine?

**Page on what users feel. Investigate causes from there.**

The table:

| Alert type | Example | Problem |
|---|---|---|
| Symptom (correct) | p99 latency > 500ms for 5 min | Users are experiencing it right now |
| Symptom (correct) | Error rate > 1% for 5 min | Users are getting errors right now |
| Cause (noisy) | CPU > 80% | May not affect users at all |
| Cause (noisy) | DB connections > 50 | Not a user-visible metric |

The burn-rate model from the timeline above is the gold standard — it converts a slow SLO degradation (a problem that's real but not yet catastrophic) into a page that fires early with the right urgency.

### Dashboards that answer "is it broken and why"

A good dashboard has three layers:

1. **The answer layer** (top): Is the service healthy? The RED metrics — one number each — with a traffic-light color. Anyone can read it in five seconds.
2. **The where layer** (middle): Which component is degraded? Latency breakdown by endpoint. Error rate by error type. These narrow the blast radius.
3. **The why layer** (bottom): Linked traces for slow/errored requests. The slog JSON stream filtered to errors. This is where you go once you know *where*.

A dashboard that shows 40 graphs and no traffic lights is not observability — it's data hoarding. If you can't answer "is it broken?" in under 10 seconds without knowing where to look, the dashboard has failed.

### The on-call / incident-response loop

Incidents follow a predictable arc. Running it well is a learnable skill.

**1. Triage** — Is this real? Is it user-impacting? What is the blast radius? Check the SLO dashboard first — it gives you the scope immediately. Declare an incident early rather than late.

**2. Mitigation** — Make the pain stop. This is *not* the time to find the root cause. Roll back the deploy. Scale up the replicas. Toggle the feature flag. Restore service; investigate afterward.

**3. Root cause analysis + blameless postmortem** — After service is restored, write a postmortem. The "blameless" part is not optional — if you blame a person, you learn nothing about the system that allowed the failure. A good postmortem has: timeline, impact, what went well, what went wrong, and concrete action items with owners and due dates. The action items are the feedback loop that makes the system more resilient over time.

<Callout kind="pro" title="The postmortem is a reliability engineering tool, not a punishment">

Every incident is a free lesson the system paid for. A blameless postmortem converts that payment into a documented weakness and a concrete fix. Teams that skip postmortems replay the same incidents. Teams that write good ones raise their SLO floor systematically. The ledger service we've been instrumenting all chapter exists precisely so the postmortem can say "we detected the anomaly in 3 minutes, p99 trace attached, budget consumed 0.3%" instead of "we noticed it when a customer called."

</Callout>

func correlationMiddleware(logger *slog.Logger, next http.Handler) http.Handler {

<Recap>

The full observability stack, end to end:

- **`log/slog`** (Go 1.21+) is your structured logging standard. JSON handler in production, text in dev. Use `With` for service-wide and request-scoped fields. Never log secrets or PII — implement `slog.LogValuer` to redact sensitive types at the boundary.
- **Prometheus** metrics: counters for totals, gauges for current-value, histograms for latency. Wire RED metrics (Rate / Error rate / Duration) on every meaningful operation. Avoid high-cardinality labels — they will OOM your Prometheus server.
- **OpenTelemetry** tracing: spans form a tree under one trace ID; context propagates across services via the W3C `traceparent` HTTP header; inject the trace ID into every log record for correlation. The OTel SDK's gRPC and HTTP instrumentation libraries handle propagation automatically once you register a `TracerProvider`.
- **Correlation IDs** tie logs + traces + metrics for a single request. If you're not on full OTel yet, a UUID in `X-Correlation-ID` threaded through context and `slog.With` is a powerful, simple alternative.
- **SLIs** are user-facing quality signals (availability, latency, error rate). **SLOs** are the numerical targets you commit to. **Error budgets** are what SLOs buy you — when the budget is gone, reliability work takes priority over new features.
- **Alert on symptoms** (latency high, error rate elevated) — not causes (CPU, DB connections). Burn-rate alerting gives you early warning with context. Every alert fires with a link to the relevant dashboard and trace.
- **The incident-response loop**: triage (scope it) → mitigation (stop the bleeding) → blameless postmortem (learn from it). The postmortem's action items are the feedback mechanism that makes the system better over time.
