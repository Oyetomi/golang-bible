## Bytes on a Connection

*Stop 1 of 4.*

### Step 1: a connection is a stream of bytes

A **TCP connection** is a two-way pipe of bytes between two programs, usually on different machines. TCP makes sure the bytes arrive complete and in order, and that's all it does: it has no idea where one message ends and the next begins. That's up to the **protocol** the two programs agree on. So before writing a server, we need to know exactly what bytes a Redis client sends and what bytes Redis sends back.

### Step 2: a tool to see them

`cmd/talk` connects to a server, sends each line it reads from standard input, and prints whatever comes back with Go's `%q` verb, which shows invisible characters like carriage return (`\r`) and newline (`\n`) as escapes:

```go noverify title="kv/cmd/talk/main.go · lines 25–44"
	in := bufio.NewScanner(os.Stdin)
	buf := make([]byte, 4096)
	for in.Scan() {
		fmt.Printf("> %s\n", in.Text())
		if _, err := conn.Write([]byte(in.Text() + "\r\n")); err != nil {
			log.Fatal(err)
		}
		// Read whatever arrives in the next 200 ms: this tool doesn't parse
		// replies yet, so it can't know where one ends.
		conn.SetReadDeadline(time.Now().Add(200 * time.Millisecond))
		var reply strings.Builder
		for {
			n, err := conn.Read(buf)
			reply.Write(buf[:n])
			if err != nil {
				break
			}
		}
		fmt.Printf("< %q\n", reply.String())
	}
```

It can't know where a reply ends (it doesn't understand the protocol yet), so it reads whatever arrives within 200 ms. `net.Dial("tcp", addr)` is the client side of a connection; the value it returns, a `net.Conn`, has `Read` and `Write` methods like a file.

### Step 3: talk to real Redis

Redis accepts **inline commands**: a line of words separated by spaces, ending in `\r\n`, the same thing you'd type in a terminal. Here are eight of them, the lines of `session.txt`, sent to Redis 8.10.2 with `go run ./cmd/talk -addr 127.0.0.1:6399 < session.txt`:

```text
> PING
< "+PONG\r\n"
> SET user:1:name Ada
< "+OK\r\n"
> GET user:1:name
< "$3\r\nAda\r\n"
> GET nobody
< "$-1\r\n"
> INCR visits
< ":1\r\n"
> DEL user:1:name
< ":1\r\n"
> GET
< "-ERR wrong number of arguments for 'get' command\r\n"
> FLY away
< "-ERR unknown command 'FLY', with args beginning with: 'away' \r\n"
```

Every reply starts with one character that says what **type** of reply it is, and ends with `\r\n`:

| First byte | Type | Example |
|---|---|---|
| `+` | simple string | `+OK` |
| `-` | error | `-ERR wrong number of arguments for 'get' command` |
| `:` | integer | `:1` |
| `$` | bulk string: the length in bytes, then the bytes | `$3\r\nAda` |
| `$-1` | null: no value | `GET nobody` |

This is **RESP**, the Redis Serialization Protocol. The next lesson covers the half we skipped (how `redis-cli` sends commands); this lesson makes our server give exactly these replies.

## Listen, Accept, Handle

*Stop 2 of 4.*

### Step 1: the server's shape

Every Go TCP server has the same three parts:

- **Listen**: `net.Listen("tcp", "127.0.0.1:6380")` asks the operating system for a port. From then on, clients can connect to it.
- **Accept**: `l.Accept()` waits for the next client to connect and returns a `net.Conn` for that one client.
- **Handle**: read commands from that connection and write replies, until the client hangs up.

The program that starts it all is short:

```go noverify title="kv/cmd/kv-server/main.go"
// kv-server serves a kv.Store over TCP, speaking Redis's protocol.
package main

import (
	"flag"
	"log"
	"net"

	"kv"
	"kv/server"
)

func main() {
	addr := flag.String("addr", "127.0.0.1:6380", "address to listen on")
	flag.Parse()

	l, err := net.Listen("tcp", *addr)
	if err != nil {
		log.Fatal(err)
	}
	log.Printf("listening on %s", l.Addr())
	log.Fatal(server.New(kv.New()).Serve(l))
}
```

### Step 2: the accept loop, first version

The obvious first version accepts a client and handles it, then accepts the next:

```go noverify title="kv/server/server.go · the first version of Serve"
func (s *Server) Serve(l net.Listener) error {
	for {
		conn, err := l.Accept()
		if err != nil {
			return err
		}
		s.handle(conn)
	}
}
```

`cmd/twoclients` tests it: client A connects and says nothing (like a real client between commands), then client B sends `PING` and waits up to 2 seconds for an answer:

```go noverify title="kv/cmd/twoclients/main.go · lines 17–37"

	a, err := net.Dial("tcp", *addr) // A: connected, idle
	if err != nil {
		log.Fatal(err)
	}
	defer a.Close()

	b, err := net.Dial("tcp", *addr)
	if err != nil {
		log.Fatal(err)
	}
	defer b.Close()
	start := time.Now()
	fmt.Fprint(b, "PING\r\n")
	b.SetReadDeadline(time.Now().Add(2 * time.Second))
	reply, err := bufio.NewReader(b).ReadString('\n')
	if err != nil {
		fmt.Printf("B: no reply after %v (%v)\n", time.Since(start).Round(time.Millisecond), err)
		return
	}
	fmt.Printf("B: %q after %v\n", reply, time.Since(start).Round(time.Microsecond))
```

```text
B: no reply after 2s (read tcp 127.0.0.1:64512->127.0.0.1:6381: i/o timeout)
```

**No reply.** The server was inside `handle(A)`, waiting for A to send something, so it never went back to `Accept` to pick up B. One idle client blocks everyone.

### Step 3: a goroutine per connection

The fix is one word:

```go noverify title="kv/server/server.go · lines 24–34"
// Serve accepts connections on l until l is closed, and serves each one
// in its own goroutine.
func (s *Server) Serve(l net.Listener) error {
	for {
		conn, err := l.Accept()
		if err != nil {
			return err
		}
		go s.handle(conn)
	}
}
```

`go s.handle(conn)` starts `handle` in a new **goroutine** and returns immediately, so the loop is straight back at `Accept`. Each client gets its own goroutine, and a goroutine waiting on a quiet connection costs a few kilobytes of stack and no CPU. The same test:

```text
B: "+PONG\r\n" after 1.772ms
```

B's `PING` answered in under 2 ms while A sat idle. This is how Go network servers are normally written, including `net/http`: a goroutine per connection, with the blocking hidden inside simple sequential code.

### Step 4: reading one command per line

```go noverify title="kv/server/server.go · lines 36–50"
// handle reads one command per line and writes one reply for each, until
// the client hangs up.
func (s *Server) handle(conn net.Conn) {
	defer conn.Close()
	lines := bufio.NewScanner(conn)
	for lines.Scan() {
		args := strings.Fields(lines.Text())
		if len(args) == 0 {
			continue
		}
		if _, err := io.WriteString(conn, s.do(args)); err != nil {
			return
		}
	}
}
```

`bufio.Scanner` splits the connection's bytes into lines (it drops the `\n`, and `strings.Fields` drops the `\r` along with the spaces). A blank line gives no fields and is skipped, as Redis does. `Scan` returns false when the client hangs up, the loop ends, and `defer conn.Close()` releases the connection. If writing a reply fails, the client has gone, so `handle` returns too.

## Replies, Byte for Byte

*Stop 3 of 4.*

### Step 1: one function per reply type

Each reply type from the table in stop 1 becomes a one-line function:

```go noverify title="kv/server/commands.go · lines 54–59"
// The reply types a client can tell apart by their first byte.
func simple(s string) string     { return "+" + s + "\r\n" }
func errorReply(s string) string { return "-ERR " + s + "\r\n" }
func integer(n int64) string     { return ":" + strconv.FormatInt(n, 10) + "\r\n" }
func bulk(s string) string       { return "$" + strconv.Itoa(len(s)) + "\r\n" + s + "\r\n" }
func null() string               { return "$-1\r\n" }
```

`bulk` writes `len(s)`, and `len` of a Go string is its length in **bytes**, which is what RESP counts. That matters for any text that isn't plain ASCII. Real Redis, given a Yoruba name:

```text
> SET user:2:name Ọlá
< "+OK\r\n"
> GET user:2:name
< "$6\r\nỌlá\r\n"
```

`Ọlá` is three letters but **six bytes** in UTF-8 (`Ọ` takes three, `á` two). A server that counted letters would send `$3`, and the client would read three bytes and then treat the rest of the name as the start of the next reply.

### Step 2: running a command

```go noverify title="kv/server/commands.go · lines 14–52"
func (s *Server) do(args []string) string {
	s.mu.Lock()
	defer s.mu.Unlock()

	name := strings.ToUpper(args[0])
	switch {
	case name == "PING" && len(args) == 1:
		return simple("PONG")
	case name == "SET" && len(args) == 3:
		s.store.Set(args[1], args[2])
		return simple("OK")
	case name == "GET" && len(args) == 2:
		v, ok := s.store.Get(args[1])
		if !ok {
			return null()
		}
		return bulk(v)
	case name == "DEL" && len(args) >= 2:
		n := 0
		for _, k := range args[1:] {
			if s.store.Del(k) {
				n++
			}
		}
		return integer(int64(n))
	case name == "INCR" && len(args) == 2:
		n, err := s.store.Incr(args[1])
		switch {
		case errors.Is(err, kv.ErrNotInteger):
			return errorReply(kv.ErrNotInteger.Error())
		case errors.Is(err, kv.ErrOverflow):
			return errorReply(kv.ErrOverflow.Error())
		}
		return integer(n)
	case name == "PING" || name == "SET" || name == "GET" || name == "DEL" || name == "INCR":
		return errorReply(fmt.Sprintf("wrong number of arguments for '%s' command", strings.ToLower(name)))
	}
	return unknown(args)
}
```

`do` upper-cases the command name (Redis accepts `get`, `GET` and `Get`), and each `case` checks the name and the number of arguments together. A known command with the wrong number of arguments falls through to the second-to-last case and gets Redis's exact message; anything else is an unknown command. `INCR` uses lesson 4's sentinel errors with `errors.Is`, and sends their messages, which were copied from Redis in the first place.

## One Store, Many Clients

*Stop 4 of 4.*

### Step 1: two goroutines, one map

With a goroutine per connection, two clients' commands can now run **at the same time**, and both reach the same `kv.Store`, which is a Go map. A Go map is not safe for concurrent use: if one goroutine writes while another reads or writes, the map's internal state can be corrupted. Before adding the lock (the `mu` field you may have noticed), here's what happens without it. `cmd/hammer` opens 50 connections that each send `INCR hits` 1,000 times. ### Step 3: one command at a time

The fix for now is a **mutex**, `sync.Mutex`, a lock that only one goroutine can hold at a time:

```go noverify title="kv/server/server.go · lines 14–22"
// Server serves one store to many clients at once.
type Server struct {
	mu    sync.Mutex // one command at a time: kv.Store isn't safe for concurrent use
	store *kv.Store
}

func New(store *kv.Store) *Server {
	return &Server{store: store}
}
```

```go noverify title="kv/server/commands.go · lines 12–17"
// do runs one command and returns its reply, encoded the way Redis
// encodes it (RESP).
func (s *Server) do(args []string) string {
	s.mu.Lock()
	defer s.mu.Unlock()

```

All 50,000 increments counted, and the race detector found nothing. One lock around everything is the simplest correct answer, not the fastest: Module 3 measures how much it costs under load and splits it up.

<UnderTheHood title="Why a goroutine per connection is cheap">

A goroutine starts with a small stack (a few kilobytes) that grows only if it needs to, so ten thousand idle connections cost tens of megabytes, not the gigabytes that ten thousand OS threads would. And a goroutine blocked in `conn.Read` doesn't hold a thread: Go's runtime puts every socket in non-blocking mode and registers it with the operating system's event notifier (epoll on Linux, kqueue on macOS). When `Read` would block, the goroutine is parked and its thread runs other goroutines; when the OS reports that the socket is readable, the goroutine is made runnable again. So the code reads like one blocking thread per client, and runs like an event loop.

</UnderTheHood>

## Exercises

<Exercise n={1} title="PING with a message" level="easy">

Real Redis answers `PING hello` with the bulk string `hello`. Add it, and add the case to `TestRepliesMatchRedis` after checking the exact reply with `cmd/talk` against Redis.

<Solution>

Add `case name == "PING" && len(args) == 2: return bulk(args[1])`, above the wrong-arguments case. Redis replies `$5\r\nhello\r\n`; `PING a b` is still the wrong-number-of-arguments error.

</Solution>

</Exercise>

<Exercise n={2} title="EXPIRE and TTL over the wire" level="medium">

Add `EXPIRE key seconds` and `TTL key` using lesson 6's methods. What should `EXPIRE key abc` reply? Check Redis first.

<Solution>

Parse the seconds with `strconv.Atoi`; on failure Redis replies `-ERR value is not an integer or out of range`. `EXPIRE` returns `:1` if the key existed, `:0` if not; `TTL` returns the seconds left as an integer, or `:-1` / `:-2`. Convert with `int64(ttl / time.Second)` for the positive case, and send -1 and -2 directly.

</Solution>

</Exercise>

<Exercise n={3} title="Too many clients" level="medium">

Limit the server to 100 concurrent connections: the 101st should be accepted and immediately sent `-ERR max number of clients reached`, then closed, as Redis does when it hits `maxclients`.

<Solution>

A buffered channel as a semaphore: `sem := make(chan struct{}, 100)`. In the accept loop, `select { case sem <- struct{}{}: go func() { s.handle(conn); <-sem }() ; default: io.WriteString(conn, "-ERR max number of clients reached\r\n"); conn.Close() }`. The slot is released when `handle` returns.

</Solution>

</Exercise>

<Exercise n={4} title="Close idle clients" level="medium">

Redis's `timeout` setting closes a connection that has been idle for that many seconds. Add it with `conn.SetReadDeadline`.

<Solution>

Before each `lines.Scan()`, call `conn.SetReadDeadline(time.Now().Add(idle))`. When the deadline passes, `Scan` returns false with a timeout error, `handle` returns, and the deferred `Close` hangs up. Resetting it before every read makes it an idle timeout rather than a total connection lifetime.

</Solution>

</Exercise>

<Lab

  starter={`package main

import (
	"bufio"
	"fmt"
	"io"
	"net"
	"strconv"
	"strings"
	"unicode/utf8"
)

// A tiny store: this lab is about the replies, not the storage.
var data = map[string]string{}

// handle reads one inline command per line and writes one reply for each.
func handle(conn net.Conn) {
	defer conn.Close()
	lines := bufio.NewScanner(conn)
	for lines.Scan() {
		args := strings.Fields(lines.Text())
		io.WriteString(conn, do(args))
	}
}

// do must answer exactly as Redis does: command names in any case,
// bulk strings prefixed with their length in BYTES, a missing key as the
// null bulk string $-1, and DEL counting only the keys that existed.
func do(args []string) string {
	switch args[0] {
	case "PING":
		return "+PONG\\r\\n"
	case "SET":
		data[args[1]] = args[2]
		return "+OK\\r\\n"
	case "GET":
		v, ok := data[args[1]]
		if !ok {
			return "$0\\r\\n\\r\\n"
		}
		return "$" + strconv.Itoa(utf8.RuneCountInString(v)) + "\\r\\n" + v + "\\r\\n"
	case "DEL":
		for _, k := range args[1:] {
			delete(data, k)
		}
		return ":" + strconv.Itoa(len(args)-1) + "\\r\\n"
	}
	return "-ERR unknown command '" + args[0] + "'\\r\\n"
}

// ── below this line: do not edit ──

func main() {
	ok := true
	fail := func(f string, a ...any) { fmt.Printf("FAIL "+f+"\\n", a...); ok = false }

	client, server := net.Pipe() // an in-memory connection: no network needed
	go handle(server)
	r := bufio.NewReader(client)
	send := func(line string) string {
		fmt.Fprint(client, line+"\\r\\n")
		got, err := r.ReadString('\\n')
		if err != nil {
			return "(connection closed: " + err.Error() + ")"
		}
		if got[0] == '$' && got != "$-1\\r\\n" {
			n, _ := strconv.Atoi(strings.TrimSpace(got[1:]))
			body := make([]byte, n+2)
			io.ReadFull(r, body)
			got += string(body)
		}
		return got
	}

	for _, c := range []struct{ cmd, want string }{
		{"PING", "+PONG\\r\\n"},
		{"ping", "+PONG\\r\\n"},
		{"SET user:1:name Ọlá", "+OK\\r\\n"},
		{"get user:1:name", "$6\\r\\nỌlá\\r\\n"},
		{"GET nobody", "$-1\\r\\n"},
		{"", ""},
		{"SET a 1", "+OK\\r\\n"},
		{"DEL a b c", ":1\\r\\n"},
		{"PING", "+PONG\\r\\n"},
	} {
		if c.cmd == "" {
			fmt.Fprint(client, "\\r\\n") // a blank line: Redis ignores it
			continue
		}
		if got := send(c.cmd); got != c.want {
			fail("%s: got %q, want %q", c.cmd, got, c.want)
			if strings.HasPrefix(got, "(connection closed") {
				break
			}
		}
	}

	if ok {
		fmt.Println("ALL CHECKS PASS")
	}
}`}

Each of these bugs was found in a real Redis clone at some point: clients are unforgiving, because they trust the length prefix completely.

<Recap>

- A TCP connection carries bytes, not messages; **RESP** says where each reply starts and ends: `+` simple, `-` error, `:` integer, `$len` bulk, `$-1` null.
- A Go server: **Listen**, loop on **Accept**, and **handle each connection in its own goroutine**. Measured: handling in the loop left a second client unanswered after 2 s; with `go`, it got `+PONG` in 1.772 ms.
- Bulk lengths are in **bytes**: `Ọlá` is `$6`. Our replies matched Redis 8.10.2 byte for byte, and a test keeps them that way.
- Goroutines sharing a map without a lock: `fatal error: concurrent map read and map write`, and under `-race`, 1,184 of 1,600 increments.
- A `sync.Mutex` around each command fixed both: 50,000 of 50,000, race detector quiet.

</Recap>
