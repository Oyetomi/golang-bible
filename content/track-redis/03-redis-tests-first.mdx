<HeroCard label="Build Your Own Redis · Lesson 3" title="Tests First">

The store works, as far as the demo in lesson 2 could tell. But every lesson from here on changes it: expiry, limits, a lock, a network in front of it. Each change risks breaking something that used to work, and clicking through a demo after every edit doesn't scale. So before the store grows, we pin down what it does with **tests**, and we add the next feature, Redis's `INCR`, the other way round: test first, code second.

Three stops:

1. **A table of cases.** One test function, many inputs, each with a name.
2. **Red.** Writing the test for `INCR` before `INCR` exists.
3. **Green.** The smallest code that makes it pass, and what the test is worth afterwards.

</HeroCard>

## A Table of Cases

*Stop 1 of 3.*

### Step 1: the shape of a Go test

A Go test is a function named `TestXxx` taking a `*testing.T`, in a file ending `_test.go`, in the same package as the code. `go test` finds and runs them. There's no assertion library: a test checks a condition with an ordinary `if` and reports a failure with `t.Errorf` (keep going) or `t.Fatalf` (stop this test).

### Step 2: a table

Most of the store's behaviour is "after these operations, `Get` should say this". Writing one test function per case repeats the same lines six times. A **table-driven test** writes the cases as data, a slice of structs, and runs one loop over them:

```go noverify
package kv

import "testing"

func TestStore(t *testing.T) {
	tests := []struct {
		name   string
		setup  func(s *Store)
		key    string
		want   string
		wantOK bool
	}{
		{"missing key", func(s *Store) {}, "a", "", false},
		{"set then get", func(s *Store) { s.Set("a", "1") }, "a", "1", true},
		{"set twice keeps the last value", func(s *Store) { s.Set("a", "1"); s.Set("a", "2") }, "a", "2", true},
		{"empty string is a value", func(s *Store) { s.Set("a", "") }, "a", "", true},
		{"deleted key is gone", func(s *Store) { s.Set("a", "1"); s.Del("a") }, "a", "", false},
		{"other keys are untouched", func(s *Store) { s.Set("b", "2") }, "a", "", false},
	}
	for _, tc := range tests {
		t.Run(tc.name, func(t *testing.T) {
			s := New()
			tc.setup(s)
			got, ok := s.Get(tc.key)
			if got != tc.want || ok != tc.wantOK {
				t.Errorf("Get(%q) = %q, %v; want %q, %v", tc.key, got, ok, tc.want, tc.wantOK)
			}
		})
	}
}
```

Each case has a `setup` function that puts the store in some state, and the expected result of `Get`. `t.Run` gives each case its own named **subtest**, so a failure says which case failed, and one case can be run on its own with `go test -run 'TestStore/empty'`:

```text
=== RUN   TestStore
=== RUN   TestStore/missing_key
=== RUN   TestStore/set_then_get
=== RUN   TestStore/set_twice_keeps_the_last_value
=== RUN   TestStore/empty_string_is_a_value
=== RUN   TestStore/deleted_key_is_gone
=== RUN   TestStore/other_keys_are_untouched
--- PASS: TestStore (0.00s)
    --- PASS: TestStore/missing_key (0.00s)
    --- PASS: TestStore/set_then_get (0.00s)
    --- PASS: TestStore/set_twice_keeps_the_last_value (0.00s)
    --- PASS: TestStore/empty_string_is_a_value (0.00s)
    --- PASS: TestStore/deleted_key_is_gone (0.00s)
    --- PASS: TestStore/other_keys_are_untouched (0.00s)

```

Note the fourth case: an empty string is a value. It's easy to get wrong and easy to break later, which is exactly what a test is for.

## Red

*Stop 2 of 3.*

### Step 1: describe INCR before writing it

Redis's `INCR key` adds one to the integer stored at a key and returns the new value; a missing key counts as 0; a value that isn't an integer is an error. That's a precise description, so it can be written down as a test before any code exists:

```go noverify
// incr_test.go, lines 1–21
package kv

import "testing"

// INCR adds one to the integer stored at key. A missing key counts as 0.
func TestIncr(t *testing.T) {
	s := New()
	for want := int64(1); want <= 3; want++ {
		got, err := s.Incr("visits")
		if err != nil || got != want {
			t.Fatalf("Incr = %d, %v; want %d, nil", got, err, want)
		}
	}
	if v, _ := s.Get("visits"); v != "3" {
		t.Fatalf("stored value %q, want \"3\"", v)
	}
	s.Set("name", "Ada")
	if _, err := s.Incr("name"); err == nil {
		t.Fatal("Incr on a non-integer: want an error")
	}
}
```

### Step 2: watch it fail

```text
# kv [kv.test]
./incr_test.go:9:17: s.Incr undefined (type *Store has no field or method Incr)
./incr_test.go:18:17: s.Incr undefined (type *Store has no field or method Incr)
FAIL	kv [build failed]
FAIL
```

It doesn't even compile: `s.Incr undefined`. That's the first **red** step of test-driven development (TDD), and it's useful: the test is already telling us the method's name and signature, as a caller will use it. Writing the test first makes you design the API from the caller's side.

## Green

*Stop 3 of 3.*

### Step 1: the smallest thing that passes

```go noverify
// store.go, lines 42–55
// Incr adds one to the integer stored at key and returns the new value. A
// missing key counts as 0. A value that isn't a base-10 integer is an error.
func (s *Store) Incr(key string) (int64, error) {
	n := int64(0)
	if v, ok := s.data[key]; ok {
		var err error
		if n, err = strconv.ParseInt(v, 10, 64); err != nil {
			return 0, fmt.Errorf("value at %q is not an integer: %w", key, err)
		}
	}
	n++
	s.data[key] = strconv.FormatInt(n, 10)
	return n, nil
}
```

```text
=== RUN   TestIncr
--- PASS: TestIncr (0.00s)
PASS
ok  	kv	0.693s
```

**Green.** The implementation parses the stored string with `strconv.ParseInt` (base 10, 64 bits), adds one, and stores it back as a string, because Redis stores numbers as strings too: `INCR` is a string command that happens to understand digits.

### Step 2: what the test is worth now

From here on, every change to the store runs these tests. The next lesson changes how `Incr` reports errors and the one after changes how values are stored altogether; each time, `go test` says in under a second whether `INCR` still counts, whether an empty value is still a value, and whether a deleted key is still gone. The third TDD step, **refactor**, is safe only because of this: you can reshape the code freely while the tests stay green.

<UnderTheHood title="How go test runs your tests">

`go test` compiles your package together with its `_test.go` files into a temporary test binary, with a generated `main` that calls every `TestXxx` in turn, and runs it. A test fails when it calls `t.Error`, `t.Fatal` or panics; `t.Fatal` stops only that test (it calls `runtime.Goexit` on the test's goroutine), so the others still run. Results of a passing package are cached: run it again with no changes and you see `(cached)`, which is why the earlier output shows a time only the first time.

</UnderTheHood>

## Exercises

<Exercise n={1} title="DECR" level="easy">

Add a test for `Decr` (subtract one), watch it fail, then implement it by calling a shared helper with `Incr`.

<Solution>

Write `TestDecr` mirroring `TestIncr` with expected values -1, -2, -3. It fails to compile until `Decr` exists. Then extract the body of `Incr` into `incrBy(key string, delta int64)` and make both `Incr` and `Decr` one-line calls to it; the existing `TestIncr` proves the refactor didn't break `Incr`.

</Solution>

</Exercise>

<Exercise n={2} title="Test Del's answer" level="easy">

Add a case to the table (or a new small test) that checks `Del`'s return value: true for a key that existed, false after it's gone.

<Solution>

The table checks `Get`; `Del`'s own answer needs its own assertion. A small `TestDel` that sets a key, checks `Del` returns true, then checks a second `Del` returns false covers it. Tests should pin down every answer the Redis command gives, because the network lessons will send those answers to real clients.

</Solution>

</Exercise>

<Exercise n={3} title="Fuzz the table" level="medium">

Write `FuzzSetGet(f *testing.F)`: for any key and value the fuzzer invents, `Set` then `Get` must return exactly that value. Run it for 20 seconds with `go test -fuzz FuzzSetGet -fuzztime 20s`.

<Solution>

`f.Add("a", "1")` seeds it; `f.Fuzz(func(t *testing.T, k, v string) { s := New(); s.Set(k, v); if got, ok := s.Get(k); !ok || got != v { t.Fatal(...) } })`. It should pass: a map stores any string, including empty ones and invalid UTF-8. Fuzzing earns its keep later, on the protocol parser, where inputs come from strangers.

</Solution>

</Exercise>

## The Lab

<Lab
  title="INCRBY, By the Table"
  archetype="fix-it"
  difficulty="guided"
  points={70}
  hintCost={5}
  verify="self-check"
  expect="ALL CHECKS PASS"
  objective="The table of cases below the line is the specification for IncrBy. The starter ignores parse errors and lets the result wrap around. Make every case pass: missing keys count as 0, non-integers are an error, overflow in either direction is an error, and a failed IncrBy leaves the value as it was."
  starter={`package main

import (
	"errors"
	"fmt"
	"math"
	"strconv"
)

type Store struct{ data map[string]string }

func New() *Store                              { return &Store{data: make(map[string]string)} }
func (s *Store) Set(key, value string)         { s.data[key] = value }
func (s *Store) Get(key string) (string, bool) { v, ok := s.data[key]; return v, ok }

var (
	ErrNotInteger = errors.New("value is not an integer or out of range")
	ErrOverflow   = errors.New("increment or decrement would overflow")
)

// IncrBy adds delta to the integer stored at key and returns the result,
// like Redis's INCRBY. A missing key counts as 0. It returns ErrNotInteger
// for a value that isn't a base-10 integer, and ErrOverflow if the result
// wouldn't fit in an int64; a failed IncrBy leaves the value unchanged.
func (s *Store) IncrBy(key string, delta int64) (int64, error) {
	v, _ := s.Get(key)
	n, _ := strconv.Atoi(v)
	result := int64(n) + delta
	s.Set(key, strconv.FormatInt(result, 10))
	return result, nil
}

var _ = math.MaxInt64 // math is imported for you to use

// ── below this line: do not edit ──

func main() {
	ok := true
	fail := func(f string, a ...any) { fmt.Printf("FAIL "+f+"\\n", a...); ok = false }
	tests := []struct {
		name    string
		start   string // "" means the key is missing
		delta   int64
		want    int64
		wantErr bool
	}{
		{"missing key counts as 0", "", 5, 5, false},
		{"adds to an integer", "10", 5, 15, false},
		{"negative delta", "10", -15, -5, false},
		{"zero delta", "7", 0, 7, false},
		{"not an integer", "ada", 1, 0, true},
		{"a float is not an integer", "1.5", 1, 0, true},
		{"up to the largest int64", "9223372036854775806", 1, 9223372036854775807, false},
		{"past the largest int64", "9223372036854775807", 1, 0, true},
		{"down to the smallest int64", "-9223372036854775807", -1, -9223372036854775808, false},
		{"past the smallest int64", "-9223372036854775808", -1, 0, true},
		{"a big jump past the top", "100", 9223372036854775807, 0, true},
	}
	for _, tc := range tests {
		s := New()
		if tc.start != "" {
			s.Set("k", tc.start)
		}
		got, err := s.IncrBy("k", tc.delta)
		switch {
		case tc.wantErr && err == nil:
			fail("%s: IncrBy = %d, nil; want an error", tc.name, got)
		case !tc.wantErr && err != nil:
			fail("%s: unexpected error %v", tc.name, err)
		case !tc.wantErr && got != tc.want:
			fail("%s: IncrBy = %d, want %d", tc.name, got, tc.want)
		}
		if tc.wantErr {
			if v, _ := s.Get("k"); v != tc.start {
				fail("%s: a failed IncrBy changed the value from %q to %q", tc.name, tc.start, v)
			}
		}
	}
	if ok {
		fmt.Println("ALL CHECKS PASS")
	}
}`}
  verifier="Runs eleven cases through IncrBy: a missing key, positive, negative and zero deltas, a word and a float, the largest and smallest int64 with and without room, and a big jump past the top. For every error case it also checks the stored value is unchanged. Prints ALL CHECKS PASS."
  hints={[
    "Parse with strconv.ParseInt(v, 10, 64) and return ErrNotInteger if it fails. strconv.Atoi silently gives 0 when you ignore its error.",
    "Check for overflow before adding: for a positive delta, n > math.MaxInt64-delta means n+delta won't fit; for a negative delta, n < math.MinInt64-delta.",
    "Only call Set after every check has passed, so a failed IncrBy never changes the value."
  ]}
  flag="GO{incrby_by_the_table}"
>

The table is the kind of test stop 1 describes, written first. When all of it passes, you've done TDD's green step for a real Redis command.

</Lab>

- A **table-driven test** lists cases as data and runs one loop; `t.Run` makes each a named subtest.

- Writing the test first designs the API from the caller's side.
- Redis stores numbers as strings; `INCR` parses, adds and stores back.
- `go test` builds a test binary, runs every `TestXxx`, and caches passing results.

</Recap>
