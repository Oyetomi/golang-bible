## Errors Are Values

*Stop 1 of 3.*

### Step 1: what error is

`error` is not a special language feature. It's an ordinary interface, built in:

```go
type error interface {
	Error() string
}
```

Any type with an `Error() string` method is an error. A function that can fail returns one as its last result, and `nil` means it didn't fail. `Incr` has the signature `func (s *Store) Incr(key string) (int64, error)`: a number when things go well, an error when they don't.

### Step 2: why not exceptions

Many languages throw exceptions, which jump out of the function to some `catch` further up. Go chose not to. An error is a value you get back and handle where the call is, with an ordinary `if`:

```go
n, err := s.Incr("visits")
if err != nil {
	return err
}
```

That `if err != nil` shows up often in Go code, and it's deliberate: every line that can fail is visible, and what happens next is written right there. When our server calls `Incr` for a client, the error is just another value it can inspect and turn into a reply.

## Sentinels & Wrapping

*Stop 2 of 3.*

### Step 1: name the errors a caller can act on

A caller who gets an error from `Incr` wants to know **which** failure it was, because a client needs to hear different things for "that's not a number" and "that would overflow". So the store declares each one as a package-level variable, called a **sentinel error**:

```go noverify
// store.go, lines 11–17
// ErrNotInteger is returned when an integer command meets a value that
// isn't one. Callers check for it with errors.Is; the message it wraps
// says which key.
var ErrNotInteger = errors.New("value is not an integer or out of range")

// ErrOverflow is returned when an increment would pass the largest int64.
var ErrOverflow = errors.New("increment or decrement would overflow")
```

The messages are Redis's own, so the server can pass them on unchanged.

### Step 2: add context with %w

A bare `ErrNotInteger` doesn't say which key failed, and when a client sends fifty commands at once, that matters. `fmt.Errorf` builds a new error with more context, and the `%w` verb **wraps** the sentinel inside it:

```go noverify
// store.go, lines 52–68
// Incr adds one to the integer stored at key and returns the new value. A
// missing key counts as 0. A value that isn't a base-10 integer is an error.
func (s *Store) Incr(key string) (int64, error) {
	n := int64(0)
	if v, ok := s.data[key]; ok {
		var err error
		if n, err = strconv.ParseInt(v, 10, 64); err != nil {
			return 0, fmt.Errorf("INCR %q: %w", key, ErrNotInteger)
		}
	}
	if n == math.MaxInt64 {
		return 0, fmt.Errorf("INCR %q: %w", key, ErrOverflow)
	}
	n++
	s.data[key] = strconv.FormatInt(n, 10)
	return n, nil
}
```

The new error prints as `INCR "name": value is not an integer or out of range`, and it keeps a link to `ErrNotInteger` inside it. The caller can still find the sentinel through that link, even after more context has been wrapped around it.

### Step 3: check with errors.Is, not ==

Here are the checks a caller might try, run against the real error from `Incr`:

```go noverify
// wrap compares three ways of checking an error that has been wrapped.
package main

import (
	"errors"
	"fmt"

	"kv"
)

func main() {
	s := kv.New()
	s.Set("name", "Ada")
	_, err := s.Incr("name") // wrapped with %w

	fmt.Printf("err:                       %v\n", err)
	fmt.Printf("err == ErrNotInteger:      %v\n", err == kv.ErrNotInteger)
	fmt.Printf("errors.Is(err, ...):       %v\n", errors.Is(err, kv.ErrNotInteger))
	fmt.Printf("errors.Unwrap(err) == ...: %v\n", errors.Unwrap(err) == kv.ErrNotInteger)

	// The same message, but formatted with %v instead of %w: the text
	// survives, the link to ErrNotInteger doesn't.
	flat := fmt.Errorf("INCR %q: %v", "name", kv.ErrNotInteger)
	fmt.Printf("flat:                      %v\n", flat)
	fmt.Printf("errors.Is(flat, ...):      %v\n", errors.Is(flat, kv.ErrNotInteger))
}
```

```text
err:                       INCR "name": value is not an integer or out of range
err == ErrNotInteger:      false
errors.Is(err, ...):       true
errors.Unwrap(err) == ...: true
flat:                      INCR "name": value is not an integer or out of range
errors.Is(flat, ...):      false
```

- `err == ErrNotInteger` is **false**: `err` is the wrapper, a different value.
- `errors.Is` is **true**: it unwraps one layer at a time, comparing each against the target, until it finds it or runs out.
- The same message built with `%v` looks identical when printed, but `errors.Is` gives **false**: `%v` copies the text and keeps no link to the sentinel.

### Step 4: errors.As for errors that carry data

Sometimes the caller wants the error's **data**, not just to know which error it is. `strconv.ParseInt` returns a `*strconv.NumError` holding the function name, the input and the cause. `errors.As` walks the same chain looking for an error of a given **type**, and if it finds one, stores it in your variable:

```go noverify
// errs shows what a caller can do with each kind of error value.
package main

import (
	"errors"
	"fmt"
	"strconv"

	"kv"
)

func main() {
	s := kv.New()
	s.Set("name", "Ada")
	s.Set("big", "9223372036854775807") // the largest int64

	for _, key := range []string{"name", "big", "visits"} {
		n, err := s.Incr(key)
		switch {
		case errors.Is(err, kv.ErrNotInteger), errors.Is(err, kv.ErrOverflow):
			// The caller can tell exactly what went wrong, and still see which key.
			fmt.Printf("INCR %-6s -> client error: %v\n", key, err)
		case err != nil:
			fmt.Printf("INCR %-6s -> unexpected: %v\n", key, err)
		default:
			fmt.Printf("INCR %-6s -> %d\n", key, n)
		}
	}

	// The error strconv returned is still there, one level down, if we want it.
	_, err := strconv.ParseInt("9223372036854775808", 10, 64)
	var numErr *strconv.NumError
	fmt.Printf("strconv says: %v (errors.As: %v, overflow: %v)\n",
		err, errors.As(err, &numErr), errors.Is(err, strconv.ErrRange))
}
```

```text
INCR name   -> client error: INCR "name": value is not an integer or out of range
INCR big    -> client error: INCR "big": increment or decrement would overflow
INCR visits -> 1
strconv says: strconv.ParseInt: parsing "9223372036854775808": value out of range (errors.As: true, overflow: true)
```

The first three lines are the `switch` on `errors.Is`: each failure is recognised by name and still shows its key. The last line shows `errors.As` finding the `*strconv.NumError`, and `errors.Is` finding `strconv.ErrRange` wrapped inside it, one level down.

<UnderTheHood title="How errors.Is walks the chain">

`errors.Is(err, target)` first checks `err == target`. If that fails, and `err` has an `Is(error) bool` method, it asks that. Then it calls `err`'s `Unwrap() error` method and repeats on the result, until `Unwrap` returns `nil`. The error `fmt.Errorf` makes for `%w` is a small struct, `*fmt.wrapError`, whose `Unwrap` returns the wrapped error. Since Go 1.20 an error can wrap several at once (`fmt.Errorf` with two `%w`, or `errors.Join`); then `Unwrap` returns a `[]error` and `errors.Is` searches it depth-first. With `%v`, `fmt.Errorf` returns a plain error with no `Unwrap` at all, so there is nothing to walk.

</UnderTheHood>

## The Bug a Test Found

*Stop 3 of 3.*

### Step 1: a test for the edge

Lesson 3's test checked that INCR counts and that a word is an error. It didn't test the largest possible number. Real Redis refuses to go past the largest 64-bit integer, 9,223,372,036,854,775,807, with `ERR increment or decrement would overflow`. So, test first, we added that case to `TestIncr`, along with a check that a failed INCR leaves the value alone:

```go noverify
// incr_test.go, lines 24–30
	s.Set("big", "9223372036854775807")
	if _, err := s.Incr("big"); !errors.Is(err, ErrOverflow) {
		t.Fatalf("Incr past MaxInt64: %v, want ErrOverflow", err)
	}
	if v, _ := s.Get("big"); v != "9223372036854775807" {
		t.Fatalf("a failed Incr changed the value to %q", v)
	}
```

### Step 2: red

Run against lesson 3's `Incr`, which had no overflow check:

```text
--- FAIL: TestIncr (0.00s)
    incr_test.go:26: Incr past MaxInt64: <nil>, want ErrOverflow
FAIL
FAIL	kv	0.894s
?   	kv/cmd/demo	[no test files]
?   	kv/cmd/errs	[no test files]
FAIL
```

The test failed with `<nil>`: `Incr` didn't return an error at all. The same run through the `errs` program showed what it returned instead:

```text
INCR name   -> client error: INCR "name": value is not an integer or out of range
INCR big    -> -9223372036854775808
INCR visits -> 1
strconv says: strconv.ParseInt: parsing "9223372036854775808": value out of range (errors.As: true, overflow: true)
```

`INCR big -> -9223372036854775808`. Adding one to the largest `int64` gave the **smallest** one, silently, with no error. A counter at the top of its range would have jumped to minus nine quintillion. Lesson 5, a sidequest, explains why Go does this.

### Step 3: green

The fix is the `if n == math.MaxInt64` check in the `Incr` above: refuse before adding, and don't touch the stored value.

```text
=== RUN   TestIncr
--- PASS: TestIncr (0.00s)
PASS
ok  	kv	0.740s
```

This is why tests pay: nobody running the demo would have tried `INCR` on 9,223,372,036,854,775,807, and the store would have shipped with a silent wraparound.

## Exercises

<Exercise n={1} title="A typed error" level="medium">

Replace `ErrNotInteger` with a type `NotIntegerError struct{ Key, Value string }` whose `Error` method gives the same message. How does a caller now get the key: `errors.Is` or `errors.As`?

<Solution>

`errors.As(err, &nie)` with `var nie *NotIntegerError` (return `&NotIntegerError{...}` from `Incr`). `errors.Is` can't help, since each failure is a new value; you'd need an `Is` method on the type. A typed error is worth it when callers need the data; a sentinel is simpler when they only need to know which failure it was.

</Solution>

</Exercise>

<Exercise n={2} title="Join two errors" level="easy">

`MSET`-style code sets several keys and may hit several errors. Collect them with `errors.Join` and check that `errors.Is` finds each one in the result.

<Solution>

`err := errors.Join(err1, err2)`; `errors.Is(err, ErrNotInteger)` and `errors.Is(err, ErrOverflow)` are both true, because the joined error's `Unwrap() []error` lets `errors.Is` search every branch. Printing it shows each message on its own line.

</Solution>

</Exercise>

<Exercise n={3} title="DECR's other edge" level="easy">

If you did lesson 3's `DECR` exercise, write the test for the smallest `int64` first, watch it fail, then fix it.

<Solution>

`s.Set("small", "-9223372036854775808")`; `Decr` must return `ErrOverflow` and leave the value. The check is `n == math.MinInt64` before subtracting. Without it, `Decr` wraps round to the largest `int64`, the mirror image of the INCR bug.

</Solution>

</Exercise>

	"fmt"
	"math"
	"os"
	"strconv"
	"strings"

func New() *Store                      { return &Store{data: make(map[string]string)} }

	ErrNotInteger = errors.New("value is not an integer or out of range")
	ErrOverflow   = errors.New("increment or decrement would overflow")
)

// Incr adds one to the integer at key. Its errors must name the key AND
// still match ErrNotInteger or ErrOverflow with errors.Is.
func (s *Store) Incr(key string) (int64, error) {

		}

		return 0, fmt.Errorf("INCR %q: %v", key, ErrOverflow)

// the two errors a client can act on get Redis's own messages, and anything
// else becomes "ERR internal error", so no internal detail leaks out.
func Reply(err error) string {
	switch err {
	case ErrNotInteger:
		return "ERR value is not an integer or out of range"
	case ErrOverflow:
		return "ERR increment or decrement would overflow"
	}
	return "ERR " + err.Error()

		fail("INCR visits = %d, %v; want 1, nil", n, err)
	}

		fail("errors.Is(INCR name, ErrNotInteger) = false; wrap with %%w")

		fail("errors.Is(INCR big, ErrOverflow) = false; wrap with %%w")

<Recap>

- `error` is a one-method interface; a function that can fail returns it last, and `nil` means success.
- **Sentinel errors** (`var ErrOverflow = errors.New(...)`) name the failures a caller can act on.
- `fmt.Errorf("INCR %q: %w", key, err)` adds context and **wraps**: measured, `==` gave false, `errors.Is` true; with `%v`, `errors.Is` gave false.
- `errors.As` finds an error of a given type in the chain, to read its data.
- A test for the largest `int64` found a real bug: INCR returned `-9223372036854775808` with no error. Checking `n == math.MaxInt64` first fixed it.

</Recap>
