In lesson 4, a test caught `INCR` turning the largest `int64` into the smallest one, with no error. The fix was one `if`. This sidequest is about **why** it happened, because the same thing lurks anywhere a program adds, multiplies or averages integers: memory sizes, counters, array indexes. ## Fixed Bits

*Stop 1 of 3.*

### Step 1: an odometer

A car's odometer has a fixed number of wheels. With five wheels, after 99,999 comes 00,000: the carry falls off the left end and nothing remembers it. A computer integer is the same, with wheels that only show 0 or 1. An `int8` has 8 of them, an `int64` has 64. However many there are, there's a largest number they can show, and one more than that rolls over.

### Step 2: where the negatives are

For **unsigned** integers (`uint8`, `uint64`) the wheels count from 0 upward: 8 bits hold 0 to 255. For **signed** integers, Go (like almost every processor) uses **two's complement**: the leftmost bit counts as a **negative** amount. In an `int8` it's worth −128 instead of +128, so:

- `01111111` is 64+32+16+8+4+2+1 = **127**, the largest `int8`.
- `10000000` is −128 and nothing else: **−128**, the smallest.
- `11111111` is −128+127 = **−1**.

The trick of two's complement is that adding works the same way for signed and unsigned numbers: the processor has one adder, and only the reading of the top bit differs. That's also exactly why 127 + 1 lands on −128: the carry flows into the top bit, and the top bit means −128.

## Go Wraps

*Stop 2 of 3.*

### Step 1: measured

```go noverify
// wrap shows what Go's fixed-size integers do when a result doesn't fit.
package main

import (
	"fmt"
	"math"
	"math/bits"
)

func main() {
	// The bug from lesson 4, on its own.
	var n int64 = math.MaxInt64
	fmt.Printf("int64: %d + 1 = %d\n", n, n+1)

	// The same thing in 8 bits, where the bit patterns fit on a line.
	var b int8 = 127
	fmt.Printf("int8:  %4d = %08b\n", b, uint8(b))
	b++
	fmt.Printf("  +1:  %4d = %08b\n", b, uint8(b))

	// Unsigned integers wrap to zero.
	var u uint8 = 255
	u++
	fmt.Printf("uint8: 255 + 1 = %d\n", u)

	// The smallest int64 has no positive partner: negating it gives itself.
	m := int64(math.MinInt64)
	fmt.Printf("-(%d) = %d\n", m, -m)

	// Detecting it: math/bits reports the carry out of the top bit.
	sum, carry := bits.Add64(math.MaxUint64, 1, 0)
	fmt.Printf("bits.Add64(MaxUint64, 1) = %d, carry %d\n", sum, carry)
}
```

```text
int64: 9223372036854775807 + 1 = -9223372036854775808
int8:   127 = 01111111
  +1:  -128 = 10000000
uint8: 255 + 1 = 0
-(-9223372036854775808) = -9223372036854775808
bits.Add64(MaxUint64, 1) = 0, carry 1
```

Line by line:

- `int64`: the lesson 4 bug on its own. Largest plus one is smallest.
- `int8`: the same thing where the bits fit on a line: `01111111` plus one is `10000000`, which reads as −128.
- `uint8`: unsigned numbers wrap to 0.
- Negating the smallest `int64` gives **itself**: there's one more negative number than positive ones (zero takes a slot on the positive side), so +9,223,372,036,854,775,808 doesn't exist.
- `math/bits.Add64` is how you see the carry that fell off: it returns the sum **and** the carry bit.

### Step 2: this is the language, not a bug in Go

The Go spec says it plainly: for signed integers, operations "may legally overflow and the resulting value exists and is deterministically defined by the signed integer representation". So Go never panics on overflow, and it never lets the compiler assume overflow can't happen. (C is different: signed overflow there is undefined behaviour, and compilers do surprising things with it.) Wrapping is fast, because it's what the processor does anyway, but it means **checking is your job**.

### Step 3: constants are checked

There's one place Go does refuse. Constant expressions are computed exactly, with no fixed size, and only checked when they're given a type:

```go noverify
// const shows that the compiler checks constant arithmetic exactly.
package main

import (
	"fmt"
	"math"
)

func main() {
	var n int64 = math.MaxInt64 + 1
	fmt.Println(n)
}
```

```text
# sq/cmd/const
cmd/const/main.go:10:16: cannot use math.MaxInt64 + 1 (untyped int constant 9223372036854775808) as int64 value in variable declaration (overflows)
```

That program doesn't compile. The compiler can catch overflow when it knows the numbers; at run time, with values from a client, only your code can.

## Check First

*Stop 3 of 3.*

### Step 1: what real Redis does

Against Redis 8.10.2, in a container:

```text
127.0.0.1:6379> SET big 9223372036854775807
OK
127.0.0.1:6379> INCR big
(error) ERR increment or decrement would overflow
127.0.0.1:6379> GET big
"9223372036854775807"
127.0.0.1:6379> SET small -9223372036854775808
OK
127.0.0.1:6379> DECR small
(error) ERR increment or decrement would overflow
127.0.0.1:6379> SET name Ada
OK
127.0.0.1:6379> INCR name
(error) ERR value is not an integer or out of range
```

Both edges are refused, the value is untouched (`GET big` still gives the largest number), and the messages are the ones our store now returns. Redis is written in C, where overflow isn't even safe to try, so it checks **before** adding. This is the check in Redis's `incrDecrCommand` (in `src/t_string.c`):

```c
if ((incr < 0 && oldvalue < 0 && incr < (LLONG_MIN-oldvalue)) ||
    (incr > 0 && oldvalue > 0 && incr > (LLONG_MAX-oldvalue))) {
    addReplyError(c,"increment or decrement would overflow");
    return;
}
```

The idea: to test whether `a + b` is too big, don't compute it. Move `b` to the other side: `a > MaxInt64 - b`. When `b` is positive, `MaxInt64 - b` can't overflow, so the test itself is safe. Negative `b` mirrors it with `MinInt64`. Lesson 3's lab (`IncrBy`) was exactly this check.

### Step 2: the average that broke binary search

Overflow also hides in code that doesn't look like arithmetic on big numbers. A binary search computes the middle of a range as `(lo + hi) / 2`. With large enough indexes, `lo + hi` overflows before the division:

```go noverify
// mid finds the middle of two large indexes, the naive way and the safe way.
package main

import (
	"fmt"
	"math"
)

func main() {
	lo, hi := int64(math.MaxInt64-10), int64(math.MaxInt64-2)
	fmt.Println("lo            =", lo)
	fmt.Println("hi            =", hi)
	fmt.Println("(lo+hi)/2     =", (lo+hi)/2)
	fmt.Println("lo+(hi-lo)/2  =", lo+(hi-lo)/2)
}
```

```text
lo            = 9223372036854775797
hi            = 9223372036854775805
(lo+hi)/2     = -7
lo+(hi-lo)/2  = 9223372036854775801
```

The middle of two huge positive numbers came out as −7. This bug sat in Java's `Arrays.binarySearch` for about nine years until Joshua Bloch wrote it up in 2006 ("Nearly All Binary Searches and Mergesorts are Broken"); it only bit once arrays grew past a billion elements. The fix is `lo + (hi-lo)/2`, which never exceeds `hi`. Go's standard library uses a different trick, in `sort.Search` and `slices.BinarySearch`:

```go
h := int(uint(i+j) >> 1) // avoid overflow when computing h
```

`i+j` can wrap as an `int`, but two non-negative `int`s always add up to less than the largest `uint`, so the same bits read as a `uint` are the correct sum, and shifting right by one halves it.

### Step 3: multiplication

Later in this track the store estimates memory as `count * size`. Multiplication overflows much sooner than addition, and can land anywhere, including on exactly 0: the lab's starter returns 0 for 2⁴⁰ × 2⁴⁰. The check is the same idea with division: `count * size` fits if `size <= MaxInt64 / count` (for positive numbers). `math/bits.Mul64` gives the full 128-bit product when you need it.

<UnderTheHood title="What the processor does">

On amd64 and arm64, adding two 64-bit registers produces 64 bits of result and sets **flags**: a carry flag for unsigned overflow and an overflow flag for signed overflow. Go's `+` ignores both, which is why it's one instruction. `bits.Add64` is compiled to an add that reads the carry flag, still one or two instructions, so checking is cheap. Languages that trap on overflow (Rust in debug builds, Swift always) add a conditional branch after each arithmetic operation; Go chose wrapping and leaves the check to code that needs it.

</UnderTheHood>

## Exercises

<Exercise n={1} title="Why the two's complement trick works" level="medium">

Show on paper that in `int8`, `−x` has the same bits as `^x + 1` (flip every bit, add one), using x = 5.

<Solution>

5 is `00000101`; flipped, `11111010`; plus one, `11111011`. Reading it: −128 + 64+32+16+8+2+1 = −128 + 123 = −5. It works because x + ^x is all ones (−1), so ^x + 1 = −x. This is also why negating −128 gives −128: flip `10000000` to `01111111`, add one, back to `10000000`.

</Solution>

</Exercise>

<Exercise n={2} title="Saturating add" level="easy">

Write `SatAdd(a, b int64) int64` that clamps to the largest or smallest `int64` instead of wrapping. When is that better than an error?

<Solution>

Use the same checks as the lab's `Add`, returning `math.MaxInt64` or `math.MinInt64` instead of an error. Saturating suits values that are estimates or limits (a byte counter for statistics, a backoff delay); an error suits values that must be exact, like INCR, where a client would rather hear "no" than get a wrong number.

</Solution>

</Exercise>

<Exercise n={3} title="Let a fuzzer check Add" level="medium">

Write `FuzzAdd` that compares the lab's `Add` against `math/big`, which never overflows: whenever the big-integer sum fits in an `int64`, `Add` must return it; whenever it doesn't, `Add` must return `ErrOverflow`.

<Solution>

In `f.Fuzz(func(t *testing.T, a, b int64) {...})`, compute `want := new(big.Int).Add(big.NewInt(a), big.NewInt(b))` and test `want.IsInt64()`. If it fits, require `err == nil` and `got == want.Int64()`; if not, require `errors.Is(err, ErrOverflow)`. Seed it with `f.Add(int64(math.MaxInt64), int64(1))`. Against the starter it fails at once; against the fix it runs clean. Checking against a slow but obviously correct reference is a good way to fuzz arithmetic.

</Solution>

</Exercise>

import (
	"errors"
	"fmt"
	"math"
)

var ErrOverflow = errors.New("increment or decrement would overflow")

// Add returns a+b, or ErrOverflow if the true sum doesn't fit in an int64.
// Either argument may be negative.
func Add(a, b int64) (int64, error) {
	return a + b, nil
}

// Mul returns count*size for a memory estimate, or ErrOverflow if the
// product doesn't fit in an int64. Both arguments are 0 or more.
func Mul(count, size int64) (int64, error) {
	return count * size, nil
}

// Mid returns the index halfway between lo and hi (0 <= lo <= hi),
// rounded down, without overflowing for any such lo and hi.
func Mid(lo, hi int64) int64 {
	return (lo + hi) / 2
}

var _ = math.MaxInt64 // math is imported for you to use

// ── below this line: do not edit ──

func main() {
	ok := true
	fail := func(f string, a ...any) { fmt.Printf("FAIL "+f+"\\n", a...); ok = false }
	const max, min = math.MaxInt64, math.MinInt64

	adds := []struct {
		a, b    int64
		want    int64
		wantErr bool
	}{
		{2, 3, 5, false}, {-2, -3, -5, false}, {max, -1, max - 1, false},
		{max - 1, 1, max, false}, {max, 1, 0, true}, {max, max, 0, true},
		{min + 1, -1, min, false}, {min, -1, 0, true}, {min, min, 0, true},
		{max, min, -1, false},
	}
	for _, c := range adds {
		got, err := Add(c.a, c.b)
		if c.wantErr != (err != nil) || (!c.wantErr && got != c.want) || (c.wantErr && !errors.Is(err, ErrOverflow)) {
			fail("Add(%d, %d) = %d, %v", c.a, c.b, got, err)
		}
	}

	muls := []struct {
		a, b    int64
		want    int64
		wantErr bool
	}{
		{0, max, 0, false}, {max, 0, 0, false}, {1, max, max, false},
		{1 << 31, 1 << 31, 1 << 62, false}, {1 << 32, 1 << 31, 0, true},
		{3, max/3 + 1, 0, true}, {max / 2, 2, max - 1, false}, {1 << 40, 1 << 40, 0, true},
	}
	for _, c := range muls {
		got, err := Mul(c.a, c.b)
		if c.wantErr != (err != nil) || (!c.wantErr && got != c.want) || (c.wantErr && !errors.Is(err, ErrOverflow)) {
			fail("Mul(%d, %d) = %d, %v", c.a, c.b, got, err)

	for _, c := range mids {
		if got := Mid(c[0], c[1]); got != c[2] {
			fail("Mid(%d, %d) = %d, want %d", c[0], c[1], got, c[2])
		}
	}

	if ok {
		fmt.Println("ALL CHECKS PASS")
	}
}`}
  verifier="Checks Add on ten pairs including both edges and MaxInt64 + MinInt64, Mul on eight pairs including 2^31 × 2^31 (fits) and 2^32 × 2^31 (doesn't), and Mid on six ranges including two near MaxInt64. Prints ALL CHECKS PASS."

No test in lesson 4's table would have caught these: they all need numbers near the edge. That's where overflow lives, so that's where tests belong.

<Recap>

- An integer has a fixed number of bits; **two's complement** makes the top bit negative, so the largest value plus one is the smallest.
- Go **wraps** silently at run time (measured: `9223372036854775807 + 1 = -9223372036854775808`); only constant expressions are checked, by the compiler.
- Check **before** the operation, rearranged so the check can't overflow: `a > MaxInt64 - b`. Real Redis does exactly that.
- `(lo+hi)/2` overflows for large indexes (measured: −7); use `lo + (hi-lo)/2`.
- `math/bits.Add64` and `Mul64` expose the carry and the full product when you need them.

</Recap>
