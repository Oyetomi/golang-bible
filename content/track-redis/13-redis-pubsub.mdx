<HeroCard label="Build Your Own Redis · Lesson 13" title="Publish and Subscribe: Channels All the Way Down">

Redis isn't only a store. It's also a **message bus**: a client can `SUBSCRIBE` to a named channel, and every message any other client `PUBLISH`es to that channel is pushed to it the moment it's sent. Chat rooms, live price feeds and "tell every server to clear its cache" are built on it.

It's also the first thing in our server where one client's command sends data to *other* clients' connections, which makes it the perfect place for Go's own channels. And for one of the classic concurrency failures: one slow client holding everyone else up.

Three stops:

1. **What pub/sub is.** The conversation with real Redis, byte by byte.
2. **Building it.** A queue and a writer goroutine per subscriber, and matching Redis exactly.
3. **The subscriber that never reads.** Wait for it, and everyone waits. Drop it, and nobody does.

</HeroCard>

## What Pub/Sub Is

*Stop 1 of 3.*

### Step 1: a conversation with real Redis

**Publish/subscribe** is a way of sending messages where the sender doesn't know who receives them. A **publisher** sends a message to a named **channel**; every client **subscribed** to that channel gets a copy; the publisher only learns how many that was. Nothing is stored: a message published when nobody is subscribed is gone.

To see exactly what Redis sends, `cmd/pubtalk` opens two connections to real Redis 8.10.2, one subscriber and one publisher, sends commands on each in turn, and prints every byte each one receives:

```text
$ go run ./cmd/pubtalk -addr 127.0.0.1:6399
sub> SUBSCRIBE news sport
  sub got "*3\r\n$9\r\nsubscribe\r\n$4\r\nnews\r\n:1\r\n*3\r\n$9\r\nsubscribe\r\n$5\r\nsport\r\n:2\r\n"
pub> PUBLISH news hello
  sub got "*3\r\n$7\r\nmessage\r\n$4\r\nnews\r\n$5\r\nhello\r\n"
  pub got ":1\r\n"
pub> PUBLISH weather sunny
  pub got ":0\r\n"
sub> GET x
  sub got "-ERR Can't execute 'get': only (P|S)SUBSCRIBE / (P|S)UNSUBSCRIBE / PING / QUIT / RESET are allowed in this context\r\n"
sub> PING
  sub got "*2\r\n$4\r\npong\r\n$0\r\n\r\n"
pub> PUBLISH sport goal
  sub got "*3\r\n$7\r\nmessage\r\n$5\r\nsport\r\n$4\r\ngoal\r\n"
  pub got ":1\r\n"
sub> UNSUBSCRIBE news
  sub got "*3\r\n$11\r\nunsubscribe\r\n$4\r\nnews\r\n:1\r\n"
pub> PUBLISH news anyone?
  pub got ":0\r\n"
sub> UNSUBSCRIBE
  sub got "*3\r\n$11\r\nunsubscribe\r\n$5\r\nsport\r\n:0\r\n"
sub> GET x
  sub got "$-1\r\n"
```

Reading it from the top:

- **`SUBSCRIBE news sport`** gets one reply *per channel*: a three-element array `subscribe`, the channel name, and how many channels this connection is now subscribed to (1, then 2).
- **`PUBLISH news hello`** from the other connection: the publisher gets `:1` (one subscriber received it), and the subscriber gets a message it never asked for, a three-element array `message`, `news`, `hello`. That's the key thing: Redis **pushes** data to a client that's just sitting there.
- **`PUBLISH weather sunny`**: `:0`. Nobody is subscribed to `weather`, so the message is simply gone.
- **`GET x`** on the subscriber is refused: a subscribed connection is in **subscribed mode**, where only the subscribe commands, `PING`, `QUIT` and `RESET` work. (The error mentions `PSUBSCRIBE`, patterns, and `SSUBSCRIBE`, sharded channels, which we won't build.)
- **`PING`** in subscribed mode answers with an array, `pong` and an empty string, not the usual `+PONG`: it has to look like the other things arriving on that connection.
- **`UNSUBSCRIBE news`**, then a message to `news` reaches nobody (`:0`), then **`UNSUBSCRIBE`** with no names leaves every channel. At a count of 0 the connection is back to normal, and `GET x` works (`$-1`, no such key).

## Building It

*Stop 2 of 3.*

### Step 1: the problem with pushing

Until now, each connection's goroutine did everything in a loop: read a command, write the reply. A subscriber breaks that. Its goroutine sits in `ReadCommand`, waiting for the client's next command, which may never come. Meanwhile a `PUBLISH` on *another* connection's goroutine needs to send it a message.

Two goroutines could both write to the subscriber's socket, but then their bytes could interleave, a message landing in the middle of a reply. And the publisher's goroutine would be doing a network write to someone else's client, at that client's speed.

The Go answer is the proverb: *don't communicate by sharing memory; share memory by communicating.* Give each subscriber:

- a **queue**, a buffered Go **channel** of strings, where anyone may put a reply or a message, and
- one **writer goroutine**, the only code that ever writes to that socket, which takes things off the queue in order and sends them.

The publisher only puts a message in a queue, which takes nanoseconds. What happens when a queue is full is stop 3.

### Step 2: the subscriber

In `server/pubsub.go`:

```go noverify title="kv/server/pubsub.go · lines 11–23"
// subscriberBuffer is how many replies and messages a subscriber may have
// waiting to be written before we decide it can't keep up and drop it.
const subscriberBuffer = 1024

// subscriber is a connection that has run SUBSCRIBE. From then on its
// replies and its messages all go through out, in order, to one writer
// goroutine, so a publisher never writes to a client's socket itself.
type subscriber struct {
	conn     net.Conn
	out      chan string
	channels map[string]bool // guarded by Server.psMu
	closed   bool            // out is closed; guarded by Server.psMu
}
```

- `out` is the queue: `chan string`, made with a buffer of `subscriberBuffer` (1,024) so a publisher can put that many things in it without anyone taking them out.
- `channels` is the set of channel names this connection is subscribed to, for the count in each reply and for cleaning up.
- `closed` records that `out` has been closed, because sending on a closed channel **panics** in Go, and so does closing it twice.

The server keeps the other direction, from a channel name to its subscribers, in `server/server.go`, guarded by its own lock:

```go noverify title="kv/server/server.go · lines 32–33"
	psMu sync.Mutex                          // guards subs and every subscriber's channels
	subs map[string]map[*subscriber]struct{} // channel name → its subscribers
```

### Step 3: switching into subscribed mode

`handle` changes in one place. When a connection sends its first `SUBSCRIBE`, it gets a subscriber and a writer goroutine, and from then on every command goes to `subscribed` instead of `do`:

```go noverify title="kv/server/server.go · lines 199–216"
		if len(args) == 0 {
			continue
		}
		s.commands.Add(1)
		if sub == nil && strings.EqualFold(args[0], "SUBSCRIBE") {
			// From now on a second goroutine writes to this connection, so
			// messages can arrive while we wait for the client's next command.
			w.Flush()
			sub = &subscriber{conn: conn, out: make(chan string, subscriberBuffer), channels: map[string]bool{}}
			written = make(chan struct{})
			go writeLoop(sub, w, written)
		}
		if sub != nil {
			s.subscribed(sub, args)
			continue
		}
		w.WriteString(s.do(args))
		if r.Buffered() == 0 { // nothing more waiting: send what we have
```

`w.Flush()` first sends anything this goroutine still had buffered: after this, `w` belongs to the writer goroutine, and exactly one goroutine may use a `bufio.Writer`. The writer is short:

```go noverify title="kv/server/pubsub.go · lines 155–166"
// writeLoop is a subscriber's only writer: it sends everything queued on
// out, flushing when the queue is empty, until out is closed.
func writeLoop(sub *subscriber, w *bufio.Writer, done chan<- struct{}) {
	defer close(done)
	for frame := range sub.out {
		w.WriteString(frame)
		if len(sub.out) == 0 {
			w.Flush() // an error means the connection is gone; keep draining
		}
	}
	w.Flush()
}
```

`for frame := range sub.out` takes things off the queue in order, waiting when it's empty, and **ends when the channel is closed** and drained: that's how the writer learns to stop. It flushes when the queue is empty, the same rule as lesson 10's pipelining, so a burst of messages goes out in one write. If a flush fails the client is gone, but it keeps draining so nobody sending to `out` is ever surprised.

### Step 4: SUBSCRIBE, UNSUBSCRIBE and friends

`subscribed` runs a command from a subscribed connection:

```go noverify title="kv/server/pubsub.go · lines 43–93"
// subscribed runs one command from a connection in subscribed mode, and
// sends its reply the same way messages are sent.
func (s *Server) subscribed(sub *subscriber, args []string) {
	name := strings.ToUpper(args[0])
	switch {
	case name == "SUBSCRIBE" && len(args) >= 2:
		for _, ch := range args[1:] {
			s.psMu.Lock()
			if !sub.channels[ch] {
				sub.channels[ch] = true
				if s.subs[ch] == nil {
					s.subs[ch] = map[*subscriber]struct{}{}
				}
				s.subs[ch][sub] = struct{}{}
			}
			s.sendLocked(sub, "*3\r\n"+bulk("subscribe")+bulk(ch)+integer(int64(len(sub.channels))))
			s.psMu.Unlock()
		}
	case name == "UNSUBSCRIBE":
		s.psMu.Lock()
		chans := args[1:]
		if len(chans) == 0 { // no names: every channel it's in
			for ch := range sub.channels {
				chans = append(chans, ch)
			}
			sort.Strings(chans)
		}
		if len(chans) == 0 {
			s.sendLocked(sub, "*3\r\n"+bulk("unsubscribe")+null()+integer(0))
		}
		for _, ch := range chans {
			delete(sub.channels, ch)
			delete(s.subs[ch], sub)
			if len(s.subs[ch]) == 0 {
				delete(s.subs, ch)
			}
			s.sendLocked(sub, "*3\r\n"+bulk("unsubscribe")+bulk(ch)+integer(int64(len(sub.channels))))
		}
		s.psMu.Unlock()
	case s.inChannels(sub) && name == "PING":
		arg := ""
		if len(args) > 1 {
			arg = args[1]
		}
		s.send(sub, "*2\r\n"+bulk("pong")+bulk(arg))
	case s.inChannels(sub):
		s.send(sub, errorReply("Can't execute '"+strings.ToLower(args[0])+"': only (P|S)SUBSCRIBE / (P|S)UNSUBSCRIBE / PING / QUIT / RESET are allowed in this context"))
	default: // subscribed to nothing any more: an ordinary command
		s.send(sub, s.do(args))
	}
}
```

Each reply is built with the same `bulk` and `integer` helpers `do` uses, then **queued** with `send`, never written directly, so replies and messages reach the client in the order they happened. `UNSUBSCRIBE` with no names leaves every channel, in sorted order so the replies are predictable. Once the connection is in no channels, `default` passes the command to the ordinary `do`, as Redis does.

### Step 5: PUBLISH, and checking it against Redis

`PUBLISH` is one more case in `do`:

```go noverify title="kv/server/commands.go · lines 65–66"
	case name == "PUBLISH" && len(args) == 3:
		return integer(int64(s.publish(args[1], args[2])))
```

and `publish` puts the message on each subscriber's queue (stop 3 explains the `select`):

```go noverify title="kv/server/pubsub.go · lines 25–41"
// publish queues msg for every subscriber of channel and returns how many
// there were. It never waits: a subscriber whose queue is full is dropped.
func (s *Server) publish(channel, msg string) int {
	frame := "*3\r\n" + bulk("message") + bulk(channel) + bulk(msg)
	s.psMu.Lock()
	defer s.psMu.Unlock()
	n := 0
	for sub := range s.subs[channel] {
		n++
		select {
		case sub.out <- frame:
		default: // its queue is full: it isn't reading
			s.dropLocked(sub)
		}
	}
	return n
}
```

The same `cmd/pubtalk` conversation against our server, compared with Redis's:

```text
$ go run ./cmd/pubtalk > ours.txt
$ diff redis.txt ours.txt && echo IDENTICAL
IDENTICAL
```

Every byte the same, including the error text and the `pong` array. `server/pubsub_test.go` pins that conversation down as a test with Redis's bytes, and the real `redis-cli` works too: `redis-cli -p 6380 SUBSCRIBE news` in one terminal prints each `PUBLISH news …` from another as it arrives.

## The Subscriber That Never Reads

*Stop 3 of 3.*

### Step 1: the first version

The first version of `publish` put each message on each queue with a plain send:

```go noverify title="kv/server/pubsub.go · the first version"
	for sub := range s.subs[channel] {
		n++
		sub.out <- frame // wait for room in its queue
	}
```

A send on a buffered channel waits when the buffer is full. That's harmless while every subscriber reads. `cmd/fanout` tests what happens when one doesn't: 10 subscribers that read everything, one that subscribes and never reads again, and a publisher sending `PUBLISH prices <n>` one at a time for 3 seconds.


The first three runs are the first version. After about a second, the publisher got **no reply** and stopped, at 17,286, 19,471 and 17,918 messages, and the ten healthy subscribers got nothing after that either. The stuck subscriber's queue filled (its writer was blocked, because the kernel's socket buffers were full), so `sub.out <- frame` waited. And it waited *while holding `s.psMu`*, so every other `PUBLISH`, `SUBSCRIBE` and `UNSUBSCRIBE` on the server waited behind it. One client that stopped reading froze pub/sub for everyone.

### Step 2: never wait

The fix is a **`select` with a `default`**:

```go noverify title="kv/server/pubsub.go · lines 32–38"
	for sub := range s.subs[channel] {
		n++
		select {
		case sub.out <- frame:
		default: // its queue is full: it isn't reading
			s.dropLocked(sub)
		}
```

A `select` runs the first case that's ready; `default` runs if none is. So `case sub.out <- frame` happens only if there's room *right now*, and otherwise the subscriber is **dropped**: removed from every channel, its queue closed and its connection closed.

```go noverify title="kv/server/pubsub.go · lines 119–135"
// dropLocked removes sub from every channel, closes its queue (which ends
// its writer) and its connection (which ends its reader).
func (s *Server) dropLocked(sub *subscriber) {
	if sub.closed {
		return
	}
	for ch := range sub.channels {
		delete(s.subs[ch], sub)
		if len(s.subs[ch]) == 0 {
			delete(s.subs, ch)
		}
	}
	log.Printf("dropped subscriber %s: %d replies and messages waiting, not reading", sub.conn.RemoteAddr(), len(sub.out))
	sub.closed = true
	close(sub.out)
	sub.conn.Close()
}
```

The order matters. The log line reads `len(sub.out)` before the close. `close(sub.out)` ends the writer's `range` once it has drained what's left; `sub.conn.Close()` makes the blocked writer's `Write` fail at once, and makes the connection's reader goroutine get an error and return. Every step runs with `s.psMu` held, so no publisher can send on `out` after it's closed.

The last three runs above are this version: the stuck subscriber was dropped with its **1,024** queued messages, publishing never stopped (**46,404 to 48,989** messages in 3 seconds), and every healthy subscriber got **every** message. Without the stuck subscriber at all, the numbers are the same:

<Callout kind="note" title="What real Redis does">
Redis has the same rule, with a bigger and more careful limit: `client-output-buffer-limit pubsub 32mb 8mb 60`. A pub/sub client is disconnected when its unsent output reaches 32 MB, or stays above 8 MB for 60 seconds. It's measured in bytes, not messages, and it has a *soft* limit so a short burst doesn't cost a client its connection. Our 1,024-message queue is the simplest version of the same idea: **a server can't let one slow client decide how fast everyone else goes.** (The same `cmd/fanout` against Redis in Docker published 5,315 messages in 3 s: every `PUBLISH` there crosses Docker's network, so its numbers measure the round trip, not Redis.)
</Callout>

<UnderTheHood title="Channels, select and the runtime">

A buffered channel is a small struct in the runtime (`hchan`): a ring buffer of the element type, a lock, and two queues of waiting goroutines, senders and receivers. A send that finds room copies the value into the ring and returns. A send that finds the buffer full parks the sending goroutine on the channel's send queue until a receiver makes room, which is what froze the first version's publisher. A `select` with a `default` checks each case once, in a random order, without parking: if none is ready it takes `default` and moves on. `close` wakes every parked receiver (they get the zero value and `ok == false`, which is how `range` ends) and makes any later send panic, which is why every send and the close here happen under `psMu`.

</UnderTheHood>

<Exercise n={1} title="Counting subscribers" level="easy">

Redis has `PUBSUB NUMSUB channel…`, which replies with each channel's name and its number of subscribers. Implement it, checking the reply's shape against real Redis with `cmd/raw` first.

</Solution>

<Exercise n={2} title="A soft limit" level="medium">

Dropping a subscriber the moment its queue is full is harsh on a client that was only briefly slow. Add Redis's idea of a soft limit: drop a subscriber if its queue stays more than three-quarters full for more than 5 seconds, as well as when it's full.

<Solution>

Give `subscriber` a `slowSince time.Time`. In `publish`, after a successful send, if `len(sub.out) > cap(sub.out)*3/4`, set `slowSince` if it's zero, and drop the subscriber if `time.Since(sub.slowSince) > 5*time.Second`; otherwise reset `slowSince` to zero. Test it with `synctest` (lesson 6), where 5 seconds pass instantly, and a subscriber that reads slowly on purpose.

</Solution>

</Exercise>

<Exercise n={3} title="Shutdown with subscribers" level="medium">

Run `redis-cli -p 6380 SUBSCRIBE news` and then Ctrl-C the server. Does lesson 12's `Shutdown` still finish at once? Trace why, through `handle`'s error path and `leave`.

<Solution>

It does. The read deadline wakes the subscriber's reader goroutine; its `ReadCommand` fails, so `handle` calls `leave`, which removes it from its channels and closes `out`. The writer goroutine sends anything still queued, sees the channel closed, and closes `written`; `handle` has been waiting on `<-written`, so it returns, and `Shutdown`'s `WaitGroup` reaches zero. A subscriber whose writer is blocked on a stuck socket is covered by the context deadline, exactly like lesson 12's stuck client.

</Solution>

</Exercise>

import (
	"fmt"
	"sync"
	"time"

// Hub delivers every published message to every subscriber, through a
// buffered channel per subscriber.
type Hub struct {
	mu   sync.Mutex
	subs map[chan string]struct{}
}

func NewHub() *Hub { return &Hub{subs: map[chan string]struct{}{}} }

// Subscribe returns a channel that receives every message published from
// now on. It is closed when the subscriber is unsubscribed or dropped.
func (h *Hub) Subscribe() chan string {
	ch := make(chan string, 256)
	h.mu.Lock()
	h.subs[ch] = struct{}{}
	h.mu.Unlock()
	return ch
}

// Unsubscribe stops deliveries to ch and closes it.
func (h *Hub) Unsubscribe(ch chan string) {
	close(ch)
	h.mu.Lock()
	delete(h.subs, ch)
	h.mu.Unlock()
}

// Publish delivers msg to every subscriber and returns how many there
// were. It must never wait for a slow subscriber: one whose buffer is
// full is dropped (removed, and its channel closed).
func (h *Hub) Publish(msg string) int {
	h.mu.Lock()
	defer h.mu.Unlock()
	for ch := range h.subs {
		ch <- msg
	}
	return len(h.subs)
}

		}

					return
				}

			}

<Recap>

- **Pub/sub**: `SUBSCRIBE` puts a connection in subscribed mode; `PUBLISH` pushes a `message` array to every subscriber and replies with how many; nothing is stored. Our server's bytes matched **Redis 8.10.2's** for a whole conversation.
- Each subscriber gets a **queue** (a buffered Go channel) and **one writer goroutine**, the only code that writes to its socket. `range` over the channel ends when it's closed.
- A plain send on a full queue **waits**, and the first version waited while holding the pub/sub lock: one subscriber that never read froze the publisher at **17,286–19,471** messages and starved ten healthy subscribers.
- **`select` with `default`** never waits: a full subscriber is dropped (its 1,024 queued messages with it), publishing carried on at **46,404–48,989** messages in 3 s, and every healthy subscriber got every one. Redis does the same with `client-output-buffer-limit`.

</Recap>
