<HeroCard label="Build Your Own Redis · Lesson 1" title="What We're Building">

Over this track you'll build a small Redis in Go: a server that stores keys and values in memory, speaks Redis's network protocol, and answers the real `redis-cli` and the real `go-redis` client as if it were Redis. Each lesson adds one piece and teaches the Go it needs, and everything is measured, not assumed.

This first lesson has no store code. It sets up the project folder you'll add to in every lesson after, and explains how its parts fit together, so that when a later lesson says "in `store.go`" or "a new program in `cmd/leak`", you know where that is and why.

Three stops:

1. **The target.** What Redis does, and the plan for the track.
2. **The folder.** Creating the project, and what goes where.
3. **How Go finds the code.** Modules, packages, `import "kv"` and `./...`.

## The Target

*Stop 1 of 3.*

### Step 1: what Redis does

Redis is a database that keeps everything in memory. A program connects to it over the network and sends short text commands; Redis answers each one immediately. Here's a session with the real thing, Redis 8.10.2, running in a container:

```text
127.0.0.1:6379> PING
PONG
127.0.0.1:6379> SET user:1:name Ada
OK
127.0.0.1:6379> GET user:1:name
"Ada"
127.0.0.1:6379> INCR visits
(integer) 1
127.0.0.1:6379> INCR visits
(integer) 2
127.0.0.1:6379> EXPIRE visits 60
(integer) 1
127.0.0.1:6379> TTL visits
(integer) 60
127.0.0.1:6379> DEL user:1:name
(integer) 1
127.0.0.1:6379> GET user:1:name
(nil)
```

`SET` stores a value under a key, `GET` reads it back, `INCR` treats a value as a counter, `EXPIRE` gives a key a lifetime in seconds and `TTL` says how long it has left, and `DEL` removes it. People put sessions, caches, counters, rate limits and queues in Redis because each of these answers in well under a millisecond.

### Step 2: the plan

Our Redis grows in four modules. Each one is a real part of how Redis works:

| Module | What we build | The Go it teaches |
|---|---|---|
| 1. The Store | The dictionary itself: `SET`, `GET`, `DEL`, `INCR`, expiry, eviction | structs, methods, maps, tests, errors, `time`, `container/list` |
| 2. Talking RESP | A TCP server that speaks Redis's protocol, so `redis-cli` works against it | `net`, `bufio`, `io.Reader` and interfaces, parsing, fuzzing |
| 3. Many Clients | Hundreds of connections at once, safely | goroutines, the race detector, `sync.Mutex`, sharding, channels, `context` |
| 4. Durability | Surviving a crash by logging every write to disk | files, `fsync`, replaying a log, benchmarking against real Redis |

By the end, `redis-benchmark`, the tool Redis ships to measure itself, will run against our server, and we'll compare the numbers.

## The Folder

*Stop 2 of 3.*

### Step 1: create the project

Everything lives in one folder, called `kv` (short for key-value). Make it and turn it into a **Go module**:

```text
$ go version
go version go1.27.0 darwin/arm64
$ mkdir kv && cd kv
$ go mod init kv
go: creating new go.mod: module kv
$ cat go.mod
module kv

go 1.27.0
```

`go mod init kv` wrote one file, `go.mod`. It says two things: this folder is the module named **`kv`**, and the code in it needs Go **1.27**. (The lessons' own `go.mod` says `go 1.27`, which means the same thing as `1.27.0`.) A module is the unit Go builds and versions: a folder with a `go.mod`, plus every folder inside it.

A real project published for others to use would have a module name like `github.com/yourname/kv`, so that `go get` can download it. For a project that only lives on your machine, a short name like `kv` is fine.

### Step 2: what goes where

Two kinds of Go code will live in this folder, and they go in different places:

- **The library**: the store itself, which other code uses but which does nothing on its own. It goes in the **top folder**, in files that start `package kv`: `store.go` first, then more files as it grows. Tests for it sit right next to it, in files ending `_test.go`.
- **Programs**: things you run, like a demo, a measurement, and later the server. Each one is a `package main` with a `func main`, and each gets **its own folder under `cmd/`**: `cmd/demo/main.go`, `cmd/leak/main.go`, `cmd/server/main.go`.

Why a folder per program? Go builds one program per folder: every `.go` file in a folder must belong to the same package, and a folder with `package main` becomes one executable. Two programs in one folder would be two `main` functions in one package, which doesn't compile. `cmd/<name>/` is the convention almost every Go project uses, including Go's own source tree.

## How Go Finds the Code

*Stop 3 of 3.*

### Step 1: a package is a folder

Go's rule is simple: **one folder is one package**, and a package's **import path** is the module name followed by the folder's path inside the module. So in the finished project:

- the top folder is the package with import path `kv` (module name, no subfolder);
- `cmd/demo` is the package with import path `kv/cmd/demo`.

`go list` asks the Go tool what it sees. Run in the finished Module 1 project:

```text
$ go list ./...
kv
kv/cmd/demo
kv/cmd/errs
kv/cmd/hitrate
kv/cmd/leak
kv/cmd/mem
kv/cmd/wrap

$ go list -f '{{.ImportPath}}: package {{.Name}}, files {{.GoFiles}}' ./...
kv: package kv, files [lru.go sampled.go store.go]
kv/cmd/demo: package main, files [main.go]
kv/cmd/errs: package main, files [main.go]
kv/cmd/hitrate: package main, files [main.go]
kv/cmd/leak: package main, files [main.go]
kv/cmd/mem: package main, files [main.go]
kv/cmd/wrap: package main, files [main.go]
```

Every folder with Go files is one package. `kv` is one package made of three files, `lru.go`, `sampled.go` and `store.go`: files in the same package share everything, so a type in one file can be used in another with no import. Each `cmd/...` folder is a separate `package main` with one file. (`go list` leaves the `_test.go` files out of `GoFiles`; they're only compiled by `go test`.)

That's why the `cmd/` programs can say `import "kv"` and use `kv.New()`: the name before the dot is the **package name** (`package kv`), and the import path tells the tool which folder it's in.

### Step 3: `./...` means everything

The last piece of notation you'll see in every lesson: `go test ./...`. The three dots mean "this folder and every folder below it". So `go test ./...` runs the tests of every package in the project, and `go vet ./...` checks all of them. It's what you run after every change.

<UnderTheHood title="Why Go doesn't need a build file">

Many languages need a build file listing the source files and their dependencies. Go gets all of that from the code itself: the folder layout gives the packages, each file's `package` line and `import` block give the dependency graph, and `go.mod` gives the module name and the versions of any outside modules. That's why `go build` needs no arguments beyond a folder, and why every Go project looks alike. A package that imports itself, directly or through others, is a compile error ("import cycle not allowed"), so the graph is always a tree the tool can build from the bottom up.

</UnderTheHood>

## Exercises

<Exercise n={1} title="Set it up" level="easy">

Create the `kv` folder with `go mod init kv`, then run `go version` inside it. If it doesn't say 1.27, what does `go.mod`'s `go` line do about that?

<Solution>

Since Go 1.21, the `go` line is a minimum: if your installed Go is older, the `go` command downloads the 1.27 toolchain and uses it automatically (unless `GOTOOLCHAIN=local` is set). That's why `go version` inside the folder can report a newer version than outside it.

</Solution>

</Exercise>

<Exercise n={2} title="See the import graph" level="easy">

After lesson 2, run `go list -deps ./cmd/demo`. Which packages does the demo depend on, and where does `kv` appear in the list?

<Solution>

It prints every package the demo needs, standard library first (`fmt`, `errors` and what they use), then `kv`, then `kv/cmd/demo` itself last. The order is dependencies before the packages that use them: the order the tool compiles them in.

</Solution>

</Exercise>

<Exercise n={3} title="Break it on purpose" level="easy">

Put a second file in `cmd/demo/` that says `package kv`. What does `go build ./cmd/demo` say?

<Solution>

It refuses: `found packages main (main.go) and kv (other.go) in .../cmd/demo`. One folder, one package, enforced by the tool.

</Solution>

</Exercise>

<Lab
  title="One Folder, One Package"
  archetype="fix-it"
  difficulty="guided"
  points={60}
  hintCost={5}
  verify="self-check"
  expect="ALL CHECKS PASS"
  objective="Write down the Go tool's own rules as code. ImportPath must turn a module name and a folder into the import path go list prints, however the folder is written. Programs must list each folder that builds a program once, sorted, and refuse a folder whose files disagree on their package, ignoring _test.go files."
  starter={`package main

import (
	"fmt"
	"path"
	"slices"
	"strings"
)

// A File is one .go file in a module: its path from the module's top
// folder, and the name on its package line.
type File struct {
	Path    string // e.g. "cmd/demo/main.go"
	Package string // e.g. "main"
}

// ImportPath returns the import path of the package in folder dir of
// module mod, the way go list prints it: "kv" for the top folder,
// "kv/cmd/demo" for cmd/demo. dir may be written ".", "./cmd/demo" or
// "cmd/demo/".
func ImportPath(mod, dir string) string {
	return mod + "/" + dir
}

// Programs checks the Go tool's rule, one folder = one package, and
// returns the import paths of the folders that build a program
// (package main), sorted, one per folder. A folder whose files disagree
// on the package name is an error. _test.go files are left out of the
// check, as go build leaves them out.
func Programs(mod string, files []File) ([]string, error) {
	var progs []string
	for _, f := range files {
		if f.Package == "main" {
			progs = append(progs, ImportPath(mod, path.Dir(f.Path)))
		}
	}
	return progs, nil
}

var _ = strings.TrimPrefix // strings and slices are imported for you to use
var _ = slices.Sort[[]string]

// ── below this line: do not edit ──

func main() {
	ok := true
	fail := func(f string, a ...any) { fmt.Printf("FAIL "+f+"\\n", a...); ok = false }

	for _, c := range [][3]string{
		{"kv", ".", "kv"},
		{"kv", "", "kv"},
		{"kv", "cmd/demo", "kv/cmd/demo"},
		{"kv", "./cmd/demo", "kv/cmd/demo"},
		{"kv", "cmd/demo/", "kv/cmd/demo"},
		{"github.com/ada/kv", "cmd/server", "github.com/ada/kv/cmd/server"},
	} {
		if got := ImportPath(c[0], c[1]); got != c[2] {
			fail("ImportPath(%q, %q) = %q, want %q", c[0], c[1], got, c[2])
		}
	}

	project := []File{
		{"store.go", "kv"}, {"lru.go", "kv"}, {"store_test.go", "kv"},
		{"cmd/demo/main.go", "main"}, {"cmd/leak/main.go", "main"},
		{"cmd/leak/report.go", "main"}, {"cmd/errs/main.go", "main"},
	}
	progs, err := Programs("kv", project)
	want := []string{"kv/cmd/demo", "kv/cmd/errs", "kv/cmd/leak"}
	if err != nil || !slices.Equal(progs, want) {
		fail("Programs(project) = %q, %v; want %q, nil (one entry per folder, sorted)", progs, err, want)
	}

	mixed := append(slices.Clone(project), File{"cmd/demo/other.go", "kv"})
	if _, err := Programs("kv", mixed); err == nil {
		fail("cmd/demo mixes package main and package kv: want an error")
	} else if !strings.Contains(err.Error(), "cmd/demo") {
		fail("the error should name the folder: %v", err)
	}

	withTests := append(slices.Clone(project), File{"cmd/demo/main_test.go", "main_test"})
	if _, err := Programs("kv", withTests); err != nil {
		fail("_test.go files don't count towards a folder's package: %v", err)
	}

	if ok {
		fmt.Println("ALL CHECKS PASS")
	}
}`}
  verifier="Checks ImportPath for the top folder written three ways, for cmd/demo written three ways, and for a github.com module; then runs Programs on the Module 1 project, on the same project with a stray package kv file in cmd/demo, and with a main_test file added. Prints ALL CHECKS PASS."
