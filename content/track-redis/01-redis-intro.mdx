## The Target

*Stop 1 of 3.*

### Step 1: the problem Redis solves

Before building Redis, it helps to see the problem it solves. Picture an online shop. Every product page shows four things: the product's name, its price, how many reviews it has, and its average star rating. The data lives in PostgreSQL, a normal database that keeps everything on disk: a `products` table with 1,000 products and a `reviews` table with 2,000,000 reviews, 2,000 per product.

To draw one page, the shop's Go server asks Postgres a question: *join this product to its reviews, count them, average the stars.* Postgres does that work on every visit, even though the answer is the same for every visitor until somebody writes a new review.

Redis is the other way to answer. The first time a page is built, the server saves the finished answer in Redis under a name, a **key**, such as `page:1000`. Redis keeps it in memory. The next visitor's page is one lookup of that key: no join, no counting, no averaging. This is called a **cache**: a fast copy of an answer that's slow to compute.

Two rules make a cache safe. Postgres stays the **truth**: Redis only holds copies, and if Redis lost everything, the shop could rebuild each page from Postgres. And every copy gets a lifetime, here 60 seconds, after which Redis deletes it. A copy can be out of date, but never for more than a minute.

Here is that program. It's not part of our Redis: it's a small experiment against the real Redis, to show what Redis is for. First, the Postgres way, the question the shop asks for every page:

```go noverify title="why/main.go · lines 25–33"
const query = `SELECT p.name, p.price_cents, count(r.id), coalesce(avg(r.stars), 0)
FROM products p LEFT JOIN reviews r ON r.product_id = p.id
WHERE p.id = $1 GROUP BY p.id`

func fromPostgres(ctx context.Context, db *pgxpool.Pool, id int) (Page, error) {
	var p Page
	err := db.QueryRow(ctx, query, id).Scan(&p.Name, &p.Price, &p.Reviews, &p.AvgStars)
	return p, err
}
```

`count(r.id)` counts the product's reviews and `avg(r.stars)` averages their stars. Postgres has to find all 2,000 of that product's reviews to answer (an index takes it straight to them, so it doesn't read all two million), and it does this again for every visitor.

Next, the Redis way. The program builds each page once and stores it with `Set`, which sends Redis the command `SET page:1000 <json> EX 60`. Then it reads pages back with `Get`:

```go noverify title="why/main.go · lines 60–78"
	// Store every page in Redis once, as JSON, for 60 seconds.
	for id := 1; id <= 1000; id++ {
		p, _ := fromPostgres(ctx, db, id)
		b, _ := json.Marshal(p)
		rdb.Set(ctx, fmt.Sprintf("page:%d", id), b, 60*time.Second)
	}

	var rd []time.Duration
	for i := range n {
		start := time.Now()
		b, err := rdb.Get(ctx, fmt.Sprintf("page:%d", 1+i%1000)).Bytes()
		if err != nil {
			log.Fatal(err)
		}
		if err := json.Unmarshal(b, &page); err != nil {
			log.Fatal(err)
		}
		rd = append(rd, time.Since(start))
	}
```

`fmt.Sprintf("page:%d", id)` makes the key: `page:1`, `page:2` and so on. `rdb.Get(...)` sends `GET page:1000` and gets back the bytes that were stored; `json.Unmarshal` turns them back into a `Page`. The program times 1,000 reads each way, one at a time, then 50 shoppers at once for 3 seconds each way:

```text
$ go run .
last page: {Name:Product 1000 Price:9000 Reviews:2000 AvgStars:4}
Postgres (join + count + avg): median 970µs
Redis (GET one key):           median 286µs
Redis was 3x faster
50 users, Postgres: 4519 pages/s
50 users, Redis:    31998 pages/s
```

A second run gave 4,467 and 36,535 pages a second. One page at a time, Redis was about three times faster. With 50 shoppers at once it served seven to eight times as many pages, because Postgres does real work for every page and Redis does almost none. That's the reason Redis exists: **it keeps answers in memory, under a key, so reading one costs almost nothing.**

<Callout kind="note" title="Redis is not the main database">
Redis keeps its data in memory. Memory is fast, but it's small next to a disk, and it's lost when the machine stops unless Redis also writes to disk (Module 4 of this track builds exactly that). So in most systems Redis sits *beside* the real database, holding copies and short-lived data, and the real database stays the truth.
</Callout>

### Step 2: what else people use it for

Caching is the most common job. Four more, run on the real Redis, show why it's everywhere. Each is a key with a value, some with a lifetime:

```text
127.0.0.1:6379> SET session:9f2c user=42 EX 1800
OK
127.0.0.1:6379> GET session:9f2c
"user=42"
127.0.0.1:6379> TTL session:9f2c
(integer) 1800

127.0.0.1:6379> INCR ratelimit:42:minute
(integer) 1
127.0.0.1:6379> EXPIRE ratelimit:42:minute 60
(integer) 1
127.0.0.1:6379> INCR ratelimit:42:minute
(integer) 2
127.0.0.1:6379> INCR ratelimit:42:minute
(integer) 3

127.0.0.1:6379> ZADD leaderboard 3100 ada 2800 bayo 3350 chioma
(integer) 3
127.0.0.1:6379> ZREVRANGE leaderboard 0 2 WITHSCORES
1) "chioma"
2) "3350"
3) "ada"
4) "3100"
5) "bayo"
6) "2800"

127.0.0.1:6379> LPUSH emails welcome:42 receipt:1017
(integer) 2
127.0.0.1:6379> RPOP emails
"welcome:42"
```

- **Sessions.** When you log in, the site stores who you are under a random key (`session:9f2c`), and `EX 1800` makes it delete itself after 30 minutes. Every request looks you up with one `GET`.
- **Rate limits.** "At most 100 requests a minute per user": `INCR` adds one to a counter on each request, and `EXPIRE` makes the counter vanish after 60 seconds, so it starts again from zero.
- **Leaderboards.** A *sorted set* (`ZADD`) keeps players ordered by score, so the top three is one command.
- **Queues.** A *list* (`LPUSH` to add, `RPOP` to take) holds jobs, such as emails to send, for a worker to pick up.

Our Redis does the first two: strings, counters and lifetimes, the heart of Redis. Sorted sets and lists are extra data types on the same server; once the server exists, adding one is a matter of more commands.

### Step 3: talking to Redis

You can also talk to Redis directly, the way our Go program did. A program connects to it over the network and sends short text commands; Redis answers each one immediately. Here's a session with the real thing, Redis 8.10.2, running in a container:

```text
127.0.0.1:6379> PING
PONG
127.0.0.1:6379> SET user:1:name Ada
OK
127.0.0.1:6379> GET user:1:name
"Ada"
127.0.0.1:6379> INCR visits
(integer) 1
127.0.0.1:6379> INCR visits
(integer) 2
127.0.0.1:6379> EXPIRE visits 60
(integer) 1
127.0.0.1:6379> TTL visits
(integer) 60
127.0.0.1:6379> DEL user:1:name
(integer) 1
127.0.0.1:6379> GET user:1:name
(nil)
```

`SET` stores a value under a key, `GET` reads it back, `INCR` treats a value as a counter, `EXPIRE` gives a key a lifetime in seconds and `TTL` says how long it has left, and `DEL` removes it. People put sessions, caches, counters, rate limits and queues in Redis because each of these answers in well under a millisecond.

### Step 4: the plan

Our Redis grows in four modules. Each one is a real part of how Redis works:

| Module | What we build | The Go it teaches |
|---|---|---|
| 1. The Store | The dictionary itself: `SET`, `GET`, `DEL`, `INCR`, expiry, eviction | structs, methods, maps, tests, errors, `time`, `container/list` |
| 2. Talking RESP | A TCP server that speaks Redis's protocol, so `redis-cli` works against it | `net`, `bufio`, `io.Reader` and interfaces, parsing, fuzzing |
| 3. Many Clients | Hundreds of connections at once, safely | goroutines, the race detector, `sync.Mutex`, sharding, channels, `context` |
| 4. Durability | Surviving a crash by logging every write to disk | files, `fsync`, replaying a log, benchmarking against real Redis |

By the end, `redis-benchmark`, the tool Redis ships to measure itself, will run against our server, and we'll compare the numbers.

### Step 1: create the project

Everything lives in one folder, called `kv` (short for key-value). Make it and turn it into a **Go module**:

$ go mod init kv

`go mod init kv` wrote one file, `go.mod`. It says two things: this folder is the module named **`kv`**, and the code in it needs Go **1.27**. (The lessons' own `go.mod` says `go 1.27`, which means the same thing as `1.27.0`.) A module is the unit Go builds and versions: a folder with a `go.mod`, plus every folder inside it.

### Step 2: what goes where

Two kinds of Go code will live in this folder, and they go in different places:

- **The library**: the store itself, which other code uses but which does nothing on its own. It goes in the **top folder**, in files that start `package kv`: `store.go` first, then more files as it grows. Tests for it sit right next to it, in files ending `_test.go`.
- **Programs**: things you run, like a demo, a measurement, and later the server. Each one is a `package main` with a `func main`, and each gets **its own folder under `cmd/`**: `cmd/demo/main.go`, `cmd/leak/main.go`, `cmd/server/main.go`.

Why a folder per program? Go builds one program per folder: every `.go` file in a folder must belong to the same package, and a folder with `package main` becomes one executable. Two programs in one folder would be two `main` functions in one package, which doesn't compile. `cmd/<name>/` is the convention almost every Go project uses, including Go's own source tree.

## How Go Finds the Code

*Stop 3 of 3.*

### Step 1: a package is a folder

Go's rule is simple: **one folder is one package**, and a package's **import path** is the module name followed by the folder's path inside the module. So in the finished project:

- the top folder is the package with import path `kv` (module name, no subfolder);
- `cmd/demo` is the package with import path `kv/cmd/demo`.

`go list` asks the Go tool what it sees. Run in the finished Module 1 project:

```text
$ go list ./...
kv
kv/cmd/demo
kv/cmd/errs
kv/cmd/hitrate
kv/cmd/leak
kv/cmd/mem
kv/cmd/wrap

$ go list -f '{{.ImportPath}}: package {{.Name}}, files {{.GoFiles}}' ./...
kv: package kv, files [lru.go sampled.go store.go]
kv/cmd/demo: package main, files [main.go]
kv/cmd/errs: package main, files [main.go]
kv/cmd/hitrate: package main, files [main.go]
kv/cmd/leak: package main, files [main.go]
kv/cmd/mem: package main, files [main.go]
kv/cmd/wrap: package main, files [main.go]
```

Every folder with Go files is one package. `kv` is one package made of three files, `lru.go`, `sampled.go` and `store.go`: files in the same package share everything, so a type in one file can be used in another with no import. Each `cmd/...` folder is a separate `package main` with one file. (`go list` leaves the `_test.go` files out of `GoFiles`; they're only compiled by `go test`.)

That's why the `cmd/` programs can say `import "kv"` and use `kv.New()`: the name before the dot is the **package name** (`package kv`), and the import path tells the tool which folder it's in.

### Step 3: `./...` means everything

The last piece of notation you'll see in every lesson: `go test ./...`. The three dots mean "this folder and every folder below it". So `go test ./...` runs the tests of every package in the project, and `go vet ./...` checks all of them. It's what you run after every change.

<UnderTheHood title="Why Go doesn't need a build file">

Many languages need a build file listing the source files and their dependencies. Go gets all of that from the code itself: the folder layout gives the packages, each file's `package` line and `import` block give the dependency graph, and `go.mod` gives the module name and the versions of any outside modules. That's why `go build` needs no arguments beyond a folder, and why every Go project looks alike. A package that imports itself, directly or through others, is a compile error ("import cycle not allowed"), so the graph is always a tree the tool can build from the bottom up.

</UnderTheHood>

Since Go 1.21, the `go` line is a minimum: if your installed Go is older, the `go` command downloads the 1.27 toolchain and uses it automatically (unless `GOTOOLCHAIN=local` is set). That's why `go version` inside the folder can report a newer version than outside it.
