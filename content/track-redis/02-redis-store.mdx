<HeroCard label="Build Your Own Redis · Lesson 2" title="A Store: Structs, Methods and Maps">

Redis is, at its heart, a very fast dictionary: you give it a key, it gives you the value you stored under it. Everything else in this track (the network protocol, expiring keys, concurrency, persistence) is built around that one idea. So the first thing we build is the dictionary itself: a `Store` type that can set, get and delete values, in plain Go, with no network yet.

Three stops:

1. **A type for the store.** A struct that owns a map, and a constructor.
2. **Methods.** Set, Get and Del, and why they take a pointer.
3. **The map underneath.** What a Go map does, and the one trap it sets.

## A Type

*Stop 1 of 3.*

### Step 1: what the store needs to hold

For now, a key and a value are both strings (Redis's simplest type is a string; later lessons add expiry and limits). The store needs somewhere to keep pairs and find them again by key. Go's built-in answer is a **map**: `map[string]string` stores values of one type under keys of another and finds any of them in about the same time, however many there are.

### Step 2: a struct around the map

We could pass a bare map around, but a **struct** gives the store a name and a place to grow: later lessons add expiry times, a size limit and a lock, as more fields in the same struct, and nothing that uses the store has to change.

```go noverify title="kv/store.go · lines 1–12"
// Package kv is an in-memory key-value store: the heart of our Redis.
package kv

// Store holds string values by key.
type Store struct {
	data map[string]string
}

// New returns an empty store, ready to use.
func New() *Store {
	return &Store{data: make(map[string]string)}
}
```

`New` is a **constructor**: an ordinary function, by convention named `New`, that returns a ready-to-use value. It exists for one reason, which stop 3 shows: a map must be created with `make` before anything can be stored in it.

## Methods

*Stop 2 of 3.*

### Step 1: behaviour attached to the type

A **method** is a function with a **receiver**: `func (s *Store) Set(...)` means "Set belongs to `*Store`, and inside it, `s` is the store it was called on". Callers write `store.Set("k", "v")`, which reads like the Redis command it mirrors:

```go noverify title="kv/store.go · lines 14–35"
// Set stores value under key, replacing anything already there.
func (s *Store) Set(key, value string) {
	s.data[key] = value
}

// Get returns the value stored under key, and whether there was one.
func (s *Store) Get(key string) (string, bool) {
	v, ok := s.data[key]
	return v, ok
}

// Del removes key and reports whether it existed.
func (s *Store) Del(key string) bool {
	_, ok := s.data[key]
	delete(s.data, key)
	return ok
}

// Len reports how many keys are stored.
func (s *Store) Len() int {
	return len(s.data)
}
```

`Get` returns two values: the value, and a boolean that says whether the key was there at all. That's the **comma-ok** form of a map lookup (`v, ok := s.data[key]`), and it matters: an empty string is a perfectly good value, so the empty string alone can't mean "missing".

### Step 2: why a pointer receiver

The receiver is `*Store`, a pointer. A method with a **value** receiver (`func (s Store)`) gets a copy of the struct. Here that would happen to work, because a map value is itself a small reference to the real table, so the copy points at the same data. But it's fragile: as soon as the store gains a field that isn't a reference (a counter, a size limit, a lock), changes made through a copy would be lost, and a copied lock is a bug `go vet` reports. The rule most Go code follows: if any method needs a pointer receiver, give them all one.

### Step 3: using it

```go noverify title="kv/cmd/demo/main.go"
// demo uses the store the way a Redis client would: set, get, delete.
package main

import (
	"fmt"

	"kv"
)

func main() {
	s := kv.New()
	s.Set("user:1:name", "Ada")
	s.Set("user:1:city", "Lagos")
	s.Set("user:1:city", "Abuja") // replaces the old value

	name, ok := s.Get("user:1:name")
	fmt.Printf("GET user:1:name -> %q (found: %v)\n", name, ok)
	city, _ := s.Get("user:1:city")
	fmt.Printf("GET user:1:city -> %q\n", city)
	missing, ok := s.Get("user:2:name")
	fmt.Printf("GET user:2:name -> %q (found: %v)\n", missing, ok)

	fmt.Printf("DEL user:1:city -> %v, then again -> %v\n", s.Del("user:1:city"), s.Del("user:1:city"))
	fmt.Printf("keys stored: %d\n", s.Len())

	var broken kv.Store // the zero value: no map yet
	defer func() { fmt.Println("zero-value Store:", recover()) }()
	broken.Set("k", "v")
}
```

```text
GET user:1:name -> "Ada" (found: true)
GET user:1:city -> "Abuja"
GET user:2:name -> "" (found: false)
DEL user:1:city -> true, then again -> false
keys stored: 1
zero-value Store: assignment to entry in nil map
```

Setting `user:1:city` twice kept the last value, `user:2:name` came back as not found (not as an empty value), and deleting a key twice reported `true` then `false`, exactly the answers Redis's `DEL` gives (1, then 0).

## The Map

*Stop 3 of 3.*

### Step 1: a hash table

A Go map is a **hash table**. To store a key, it runs the key through a hash function (a fast scramble that turns any string into a number), uses part of that number to pick a slot, and puts the pair there. To find a key, it hashes it again and looks in the same slot. That's why lookups take about the same time for ten keys or ten million. Since Go 1.24 the table is a "Swiss table" design, which checks several slots at once using small per-slot fingerprints.

Two consequences you'll meet in this track: **iteration order is random** (Go deliberately randomises it, so no code comes to depend on an order it never promised), and **a map never shrinks** once it has grown (lesson 6 measures what that costs).

### Step 2: the nil map

A map variable that was never created with `make` is `nil`. Reading from a nil map is fine (every lookup finds nothing). **Writing** to one panics. That's what the last line of the demo did: `var broken kv.Store` is a store whose map field is `nil`, and its first `Set` failed with `assignment to entry in nil map`. That's the reason for `New`: it's the one place the map is made, so every store handed out is ready.

<UnderTheHood title="Why Go randomises map iteration">

Early Go maps iterated in a stable-looking order for small maps, and programs quietly came to depend on it. When the implementation changed, those programs broke. Since Go 1, the runtime starts each `range` over a map at a random position, so any code that relies on order fails early, in testing, instead of later, in production. If you need an order (the lab asks for sorted keys), collect the keys and sort them with `slices.Sort`.

</UnderTheHood>

## Exercises

<Exercise n={1} title="Exists" level="easy">

Add `Exists(keys ...string) int`, which counts how many of the given keys are stored, like Redis's `EXISTS`.

<Solution>

Loop over `keys` and count those for which `_, ok := s.data[k]` is true. Note that Redis counts a repeated key each time it appears: `EXISTS a a` returns 2 if `a` exists, and the loop does the same.

</Solution>

</Exercise>

<Exercise n={2} title="Rename" level="easy">

Add `Rename(from, to string) error` that moves a value to a new key, replacing whatever `to` held, and returns an error if `from` doesn't exist.

<Solution>

Look up `from` with comma-ok; if it's missing, return an error (Redis replies `ERR no such key`). Otherwise set `s.data[to] = v` and `delete(s.data, from)`. Renaming a key to itself should succeed and change nothing.

</Solution>

</Exercise>

<Exercise n={3} title="A value receiver, broken" level="medium">

Add a field `writes int` to `Store` that `Set` increments, then change `Set` to a value receiver. What happens to `writes`, and to the map?

<Solution>

Every `Set` increments `writes` on a copy, so the store's own counter stays 0. The values still land in the map, because the copy's `data` field points at the same table. That split behaviour (some changes stick, some vanish) is exactly why types with any pointer-receiver method should use pointer receivers throughout.

</Solution>

</Exercise>

<Recap>

- A **struct** gives the store a name and room to grow; `New` is the one place its map is made.
- **Methods** with pointer receivers (`func (s *Store)`) act on the store itself; mixing value receivers in leads to changes that silently vanish.
- **Comma-ok** (`v, ok := m[k]`) separates a missing key from an empty value; measured, `GET user:2:name` gave `"", false`.
- A Go **map** is a hash table: constant-time lookups, random iteration order, and it never shrinks.
- A **nil map** can be read but not written: the zero-value `Store` panicked with `assignment to entry in nil map`.

</Recap>
