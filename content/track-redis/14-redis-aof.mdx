<HeroCard label="Build Your Own Redis · Lesson 14" title="Surviving a Crash: The Append-Only File">

Everything our server stores lives in memory. Stop the process, for a deploy or a crash, and every key is gone. That's fine for a cache. It's not fine for anything you'd be upset to lose.

Redis's answer is the **append-only file**, the AOF: every command that changes data is also written to a file, and when the server starts it replays that file to rebuild its data. The idea is simple. The hard part is the promise behind it: when a client is told "OK", is that write really safe? Safe from what? This lesson measures both kinds of crash.

Three stops:

1. **The log.** What goes in the file, and replaying it.
2. **kill -9.** When the reply is sent matters: the bug that lost confirmed writes, and the rule that fixed it.
3. **fsync.** Surviving a power cut, what it costs, and the group commit that made ours as fast as Redis.

</HeroCard>

## The Log

*Stop 1 of 3.*

### Step 1: what goes in the file

Only commands that **change** data: `SET`, `INCR` and `DEL`. A `GET` changes nothing, so replaying it would be pointless. And they're written in **RESP**, the exact bytes a client would send, so replaying the file is just reading commands with the parser we already have (lesson 9) and running them. After `SET user:1 ada`, `GET user:1`, `INCR visits` and `DEL user:1 nobody`:

```text
$ cat kv.aof      # each \r\n written out
*3\r\n
$3\r\n
SET\r\n
$6\r\n
user:1\r\n
$3\r\n
ada\r\n
*2\r\n
$4\r\n
INCR\r\n
$6\r\n
visits\r\n
*2\r\n
$3\r\n
DEL\r\n
$6\r\n
user:1\r\n
```

Three commands, not four: the `GET` isn't there. And the `DEL` names only `user:1`, because deleting `nobody`, which didn't exist, changed nothing. Real Redis 8.10.2 writes its AOF the same way: after the same `SET`, its file held the same bytes, preceded by `SELECT 0` (Redis has 16 numbered databases; we have one). It even records an `EXPIRE` as an absolute time, which is exercise 1.

### Step 2: appending

`server/aof.go` holds the file, and a buffer in front of it:

```go noverify title="kv/server/aof.go · lines 16–30"
// AOF is the append-only file: every command that changes data is written
// to it, in RESP, the same bytes a client would send. Replaying the file
// rebuilds the data after a restart.
type AOF struct {
	mu      sync.Mutex
	f       *os.File
	w       *bufio.Writer // commands appended since the last Commit
	policy  string        // when to fsync: "always", "everysec" or "no"
	written int64         // bytes written to the file so far; guarded by mu

	syncMu sync.Mutex // one fsync at a time
	synced int64      // bytes known to be on disk; guarded by syncMu
	stop   chan struct{}
	done   chan struct{}
}
```

Commands are **appended** to the buffer `w`, in memory. Writing them to the file is a separate step, `Commit`, and **when** that happens is the whole lesson. `Append` itself just encodes:

```go noverify title="kv/server/aof.go · lines 59–67"
// Append adds one command to the buffer. It doesn't touch the file: Commit does.
func (a *AOF) Append(args []string) {
	a.mu.Lock()
	defer a.mu.Unlock()
	a.w.WriteString("*" + strconv.Itoa(len(args)) + "\r\n")
	for _, arg := range args {
		a.w.WriteString(bulk(arg))
	}
}
```

Each write command logs itself in `server/commands.go`, **while its shard's lock is still held**:

```go noverify title="kv/server/commands.go · lines 19–25"
	case name == "SET" && len(args) == 3:
		sh := s.shardFor(args[1])
		sh.mu.Lock()
		defer sh.mu.Unlock()
		sh.store.Set(args[1], args[2])
		s.log(args)
		return simple("OK")
```

That detail matters. If two clients `INCR` the same key, the one that runs first must be logged first, or replaying the file would apply them in a different order from the one the clients saw. Logging under the lock that ordered them keeps the file in the same order.

### Step 3: replaying

At start, `kv-server` replays the file before accepting any connections:

```go noverify title="kv/cmd/kv-server/main.go · lines 38–49"
	if *aofPath != "" {
		start := time.Now()
		n, err := srv.Replay(*aofPath)
		if err != nil {
			log.Fatalf("loading %s: %v", *aofPath, err)
		}
		log.Printf("loaded %d commands from %s in %v", n, *aofPath, time.Since(start).Round(time.Millisecond))
		if srv.AOF, err = server.OpenAOF(*aofPath, *fsync); err != nil {
			log.Fatal(err)
		}
		defer srv.AOF.Close()
	}
```

and `Replay` feeds each command through the same `do` that clients use:

```go noverify title="kv/server/aof.go · lines 134–158"
// Replay runs every command in the file at path against s, and returns how
// many there were. A missing file is an empty one.
func (s *Server) Replay(path string) (int, error) {
	f, err := os.Open(path)
	if errors.Is(err, os.ErrNotExist) {
		return 0, nil
	}
	if err != nil {
		return 0, err
	}
	defer f.Close()
	r := resp.NewReader(f)
	n := 0
	for {
		args, err := r.ReadCommand()
		if err == io.EOF {
			return n, nil
		}
		if err != nil {
			return n, fmt.Errorf("command %d: %w", n+1, err)
		}
		s.do(args)
		n++
	}
}
```

`s.AOF` is still `nil` while `Replay` runs, so the replayed commands aren't logged a second time, which would double the file on every restart.

## kill -9

*Stop 2 of 3.*

### Step 1: two kinds of crash

A write has three places it can be on its way to the disk:

1. **The process's buffer**: our `bufio.Writer`, memory owned by `kv-server`.
2. **The kernel's page cache**: after a `write` system call, the bytes belong to the operating system, which keeps them in RAM and writes them to the drive when it chooses, usually within seconds.
3. **The disk.**

That gives two different crashes. **`kill -9`** (SIGKILL; also a panic or an out-of-memory kill) ends the *process*. Its buffer is gone, but the kernel is fine, and it still writes everything in its page cache to the disk. A **power cut** or a kernel crash ends the *machine*: the page cache is gone too. Only what reached the disk survives.

### Step 2: the first version

The first version had no `Commit` in `handle`. Replies went out as soon as the commands ran, and the buffer reached the file in two ways: when it filled up (64 KB) and once a second, from the `everysec` goroutine:

```go noverify title="kv/server/aof.go · lines 102–121"
// everySecond is the "everysec" policy: fsync once a second, in the
// background, whatever the clients are doing.
func (a *AOF) everySecond() {
	defer close(a.done)
	t := time.NewTicker(time.Second)
	defer t.Stop()
	for {
		select {
		case <-a.stop:
			return
		case <-t.C:
			if a.policy == "everysec" {
				a.mu.Lock()
				a.w.Flush()
				a.f.Sync()
				a.mu.Unlock()
			}
		}
	}
}
```

It looks durable: a file on disk, fsynced every second. To test it, `cmd/acked` runs 20 clients that pipeline `INCR hits` 100 at a time and count every reply they get, until the server dies:

### Step 3: write before you reply

The rule is **never confirm a write that isn't in the file yet.** In `handle`, before the replies are flushed:

```go noverify title="kv/server/server.go · lines 219–232"

			if s.AOF != nil {

				if err := s.AOF.Commit(); err != nil {
```

## fsync

*Stop 3 of 3.*

### Step 1: the three policies

**`fsync`** (`f.Sync()` in Go) asks the kernel to write a file's cached bytes to the drive, and waits until the drive says they're stored. It's the only thing that survives a power cut, and it's slow: the drive has to actually do the work. Redis offers three policies, and so does our `-appendfsync` flag:

- **`always`**: fsync before every reply. A confirmed write survives a power cut. Slowest.
- **`everysec`**: fsync once a second in the background. A power cut can lose up to about a second of confirmed writes. Redis's default.
- **`no`**: never fsync; the kernel writes to disk when it likes (Linux: usually within 30 seconds). Fastest.

All three survive `kill -9`, as stop 2 measured, because all three `write` before replying.

### Step 2: measured against Redis

The same fair setup as lessons 10 and 11: each server in its own container on one Docker network, and `redis-benchmark` from a third, 50 clients sending `SET` on 10,000 random keys, without pipelining (`-P 1`) and with 16 per round trip (`-P 16`), three runs each. Real Redis ran with `--appendonly yes --appendfsync <policy>`. In thousands of `SET`s a second, the median of three (all runs are in `out/s14-bench-raw.txt`):

| | no AOF | `no` | `everysec` | `always` |
|---|---|---|---|---|
| ours, `-P 1` | 129.5 | 105.0 | 94.0 | **4.5** |
| Redis 8.10.2, `-P 1` | 138.1 | 156.7 | 101.2 | 38.6 |
| ours, `-P 16` | 531.9 | 378.8 | 387.6 | **31.8** |
| Redis 8.10.2, `-P 16` | 943.4 | 833.3 | 602.4 | 188.7 |

(Laptop benchmarks wobble. Redis with `no` ranged from 379k to 847k pipelined across its three runs, so read small differences with care.) Logging costs us something, as expected. But look at **`always`**: ours managed **4,500** `SET`s a second, Redis **38,600**. Eight times slower, with the same disk.

### Step 3: one fsync for everyone

The first `Commit` did an fsync per call. With 50 connections, 50 handlers each wanted their own fsync, and since a file's fsyncs happen one at a time, they queued: the 50th client waited for 49 other fsyncs before its own. But an fsync doesn't sync *one caller's bytes*: it syncs **everything written to the file so far**. When the first fsync finishes, many of the waiting handlers' commands were already written before it started, so they're already on disk.

Redis gets this for free: one thread handles all clients, so one pass of its event loop writes everyone's commands and does one fsync for all of them. The same idea in Go is called **group commit**, and databases like PostgreSQL use it too:

```go noverify title="kv/server/aof.go · lines 69–100"
// Commit writes everything appended so far to the file, so it survives the
// process being killed, and with "always" also fsyncs it, so it survives
// the machine losing power. Replies must not be sent before it returns.
func (a *AOF) Commit() error {
	a.mu.Lock()
	if err := a.w.Flush(); err != nil {
		a.mu.Unlock()
		return err
	}
	mine := a.written // everything up to here includes this caller's commands
	a.mu.Unlock()
	if a.policy != "always" {
		return nil
	}

	// Group commit: while one goroutine fsyncs, others queue here. When a
	// queued one gets its turn, the fsync that just finished may already
	// have covered its bytes, and then it has nothing to do.
	a.syncMu.Lock()
	defer a.syncMu.Unlock()
	if a.synced >= mine {
		return nil
	}
	a.mu.Lock()
	upTo := a.written // everyone's bytes written so far: one fsync covers them all
	a.mu.Unlock()
	if err := a.f.Sync(); err != nil {
		return err
	}
	a.synced = upTo
	return nil
}
```

- `written` counts bytes written to the file. A tiny wrapper around the file, `countingWriter`, adds to it on every write.
- Each caller writes its buffer, then notes `mine`: how far the file reached, including its own commands.
- Callers queue for `syncMu`. When one gets it, if the last fsync already reached past `mine` (`a.synced >= mine`), its commands are on disk and it returns **without an fsync**.
- Otherwise it fsyncs, but first it notes `upTo`, **everything** written so far, including other handlers' commands that arrived while it waited. When the fsync returns, all of those are safe, and their handlers will skip theirs.

The same benchmark for `always` with group commit:

```text

kv-always-group P1 run 2: SET: 33156.50 requests per second, p50=1.295 msec
kv-always-group P1 run 3: SET: 29603.31 requests per second, p50=1.375 msec
kv-always-group P16 run 1: SET: 210084.03 requests per second, p50=3.367 msec
kv-always-group P16 run 2: SET: 194552.53 requests per second, p50=3.415 msec

```

From **4,500 to 33,200** `SET`s a second without pipelining (Redis: 38,600), and from **31,800 to 194,600** pipelined (Redis: 188,700). Same fsyncs, same drive: they're just shared. On the Mac, where Go's `Sync` uses the stronger `F_FULLFSYNC` (it waits for the drive's own cache too), `cmd/acked` confirmed about 29,000 `INCR`s in 1.2 seconds before group commit and 82,000 to 89,000 after, still with none lost.

<UnderTheHood title="Why fsync is slow, and why F_FULLFSYNC is slower">

A write to a file normally just copies bytes into the kernel's page cache and marks those pages dirty; the kernel's writeback threads send them to the drive later. `fsync` makes the kernel send this file's dirty pages, and its metadata, to the drive **now**, and wait for the drive to acknowledge them. On an SSD that's tens of microseconds to milliseconds, in a VM it goes through the hypervisor's virtual disk too. But drives have caches of their own, and a plain fsync may return once the data is in the *drive's* volatile cache. On macOS, `fsync` promises only that much, so Go's `File.Sync` on darwin calls `fcntl(F_FULLFSYNC)` instead, which asks the drive to flush its cache as well. That's the only way to be sure on a Mac, and it's why every fsync number there is slower than on Linux.

</UnderTheHood>

## Exercises

<Exercise n={1} title="Log EXPIRE" level="medium">

Lesson 6's store has expiry, but the server has no `EXPIRE` command yet. Add it, and log it. Why must the AOF store the absolute time a key expires rather than the number of seconds, and what does Redis write? Check with real Redis and `cat` its AOF.

<Solution>

`EXPIRE session 60` replayed an hour later would give the key another 60 seconds, from the replay. Redis logs expiries as absolute times: its AOF contains `PEXPIREAT session <milliseconds since 1970>`, whatever the client sent. Log `PEXPIREAT` with `time.Now().Add(d).UnixMilli()` and implement `PEXPIREAT` for replay; a key whose time has passed is simply expired when it's next read.

</Solution>

</Exercise>

<Exercise n={2} title="Power cut, simulated" level="hard">

`kill -9` can't show `everysec` losing data, because the kernel survives it. Simulate a power cut: in a test, write to the AOF through a wrapper that keeps bytes written but not yet `Sync`ed in a separate slice, and "cut the power" by dropping them. How many confirmed writes do `no`, `everysec` and `always` lose?

<Solution>

Make the file a small interface (`Write`, `Sync`) so the test can substitute a fake whose `Write` appends to an unsynced slice and whose `Sync` moves it to a synced one. Run many `INCR`s through the server with a fake clock (`testing/synctest`) so `everysec`'s ticker fires on schedule, then drop the unsynced slice and replay only the synced bytes. `always` should lose nothing confirmed, `everysec` up to one second's worth, `no` everything since the last `Sync`, which for our `no` is never.

</Solution>

</Exercise>

<Exercise n={3} title="Bigger batches" level="easy">

Run `redis-benchmark -t set -c 50 -P 64` against `-appendfsync always` with group commit. Does throughput keep rising with the pipeline depth? Why does group commit help more the more clients there are?

<Solution>

Measure it. Each fsync covers everything written before it started, so its cost is shared by every command written in the meantime: more clients and deeper pipelines mean more commands per fsync. Throughput rises until something else (parsing, the locks, the network) becomes the limit, and latency rises with it, because every reply waits for the next fsync.

</Solution>

</Exercise>

  starter={`package main

import (
	"bufio"
	"fmt"
	"os"
	"path/filepath"
	"strings"
	"sync"
)

// DB is a key-value store that logs every Set to an append-only file and
// rebuilds itself from that file when opened.
type DB struct {
	mu   sync.Mutex
	data map[string]string
	f    *os.File
	w    *bufio.Writer
}

// Open replays the file at path (if it exists) and opens it for appending.
func Open(path string) (*DB, error) {
	db := &DB{data: map[string]string{}}
	f, err := os.OpenFile(path, os.O_CREATE|os.O_RDWR|os.O_APPEND, 0o644)
	if err != nil {
		return nil, err
	}
	db.f, db.w = f, bufio.NewWriter(f)
	sc := bufio.NewScanner(f)
	for sc.Scan() {
		parts := strings.Fields(sc.Text()) // SET key value
		if len(parts) == 3 {
			db.Set(parts[1], parts[2])
		}
	}
	return db, sc.Err()
}

// Set stores value under key. When it returns, the write must be in the
// file: the caller is about to tell a client it succeeded.
func (db *DB) Set(key, value string) {
	db.mu.Lock()
	defer db.mu.Unlock()
	db.data[key] = value
	fmt.Fprintf(db.w, "SET %s %s\\n", key, value)
}

func (db *DB) Get(key string) string {
	db.mu.Lock()
	defer db.mu.Unlock()
	return db.data[key]
}

func (db *DB) Close() error {
	db.w.Flush()
	return db.f.Close()
}

// ── below this line: do not edit ──

func main() {
	ok := true
	fail := func(f string, a ...any) { fmt.Printf("FAIL "+f+"\\n", a...); ok = false }
	path := filepath.Join(os.TempDir(), fmt.Sprintf("lab-aof-%d.aof", os.Getpid()))
	defer os.Remove(path)

	db, err := Open(path)
	if err != nil {
		fmt.Println("FAIL", err)
		return
	}
	values := map[string]string{
		"user:1":   "ada",
		"greeting": "hello world",
		"note":     "two\\nlines",
		"empty":    "",
	}
	for k, v := range values {
		db.Set(k, v)
		// Set has returned: a kill -9 now must not lose it. Check the file
		// itself, as a fresh process would see it.
		if fresh := replayFresh(path); fresh[k] != v {
			fail("Set(%q) returned, but a restart right now would read %q", k, fresh[k])
		}
	}
	db.Close()

	size1 := fileSize(path)
	db, err = Open(path)
	if err != nil {
		fmt.Println("FAIL", err)
		return
	}
	for k, v := range values {
		if got := db.Get(k); got != v {
			fail("after a restart, %s = %q, want %q", k, got, v)
		}
	}
	db.Close()
	if size2 := fileSize(path); size2 != size1 {
		fail("opening the database changed the file from %d to %d bytes: replaying must not log again", size1, size2)
	}
	if ok {
		fmt.Println("ALL CHECKS PASS")
	}
}

// replayFresh opens the file in a second DB, as a restarted process would,
// and returns its data.
func replayFresh(path string) map[string]string {
	cp := path + ".copy"
	b, _ := os.ReadFile(path)
	os.WriteFile(cp, b, 0o644)
	defer os.Remove(cp)
	db, err := Open(cp)
	if err != nil {
		return nil
	}
	defer db.f.Close()
	db.mu.Lock()
	defer db.mu.Unlock()
	return db.data
}

func fileSize(path string) int64 {
	st, err := os.Stat(path)
	if err != nil {
		return -1
	}
	return st.Size()
}`}

<Recap>

- The **AOF** logs every command that changes data, in RESP, and the server **replays** it at start. Commands log themselves under their shard's lock, so the file's order is the order they ran.
- **kill -9** wipes the process's memory, not the kernel's. The first version replied before writing its buffer and lost **2,609** and **976** confirmed `INCR`s in 2 of 5 runs. **Write to the file before replying**: none lost in 9 runs.
- **fsync** is what survives a power cut. `always` fsyncs before replying, `everysec` once a second, `no` never. Measured in Docker, `always` gave **4,500** `SET`s a second against Redis's **38,600**.
- **Group commit**: an fsync covers everything written before it, so handlers that were already covered skip theirs. `always` rose to **33,200** (pipelined **194,600**, Redis **188,700**).

</Recap>
