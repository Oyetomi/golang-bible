## Round Trips

*Stop 1 of 4.*

### Step 1: waiting for the network

A client that sends one command and waits for the reply before sending the next pays one **round trip** per command: the time for its bytes to reach the server and the reply to come back. On one machine that's tens of microseconds; across a data centre, a fraction of a millisecond; across a continent, tens of milliseconds. The server can be infinitely fast and the client still does at most one command per round trip.

**Pipelining** is sending many commands without waiting, then reading all the replies. RESP makes it free: every command and every reply says exactly where it ends, so the server can read commands back to back and the client can match the replies up in order.

## redis-benchmark

*Stop 2 of 4.*

### Step 1: a fair race

For a fair comparison, both servers run in containers on the same Docker network, with our server cross-compiled for Linux (`GOOS=linux GOARCH=arm64 go build ./cmd/kv-server`), and `redis-benchmark` runs from a third container. It opens 50 connections (`-c 50`) and sends 200,000 `SET`s, then 200,000 `GET`s (`-n 200000 -t set,get`), once without pipelining and once with 16 commands per round trip (`-P 16`). The first run against Redis 8.10.2 and against lesson 9's server:

GET: 1680672.25 requests per second, p50=0.303 msec

GET: 173611.12 requests per second, p50=0.159 msec

(`WARNING: Could not fetch server CONFIG` is `redis-benchmark` asking our server for its settings with `CONFIG GET`, which we don't have. It carries on without them.)

### Step 2: the results

Benchmarks on a shared laptop wobble, so each configuration ran three times. The medians, in thousands of requests per second (all three runs in brackets):

| | no pipelining, SET | no pipelining, GET | `-P 16`, SET | `-P 16`, GET |
|---|---|---|---|---|
| Redis 8.10.2 | 177 (187, 170, 177) | 208 (207, 208, 209) | 1,299 (1,460, 1,290, 1,299) | 1,754 (1,754, 1,681, 2,198) |
| lesson 9's server | 160 (164, 154, 160) | 173 (175, 166, 173) | 495 (495, 524, 489) | 658 (658, 604, 714) |

Without pipelining we're 9–17% behind Redis: every command costs a round trip, and the round trip dominates for both. With pipelining, Redis does **2.6 to 2.7 times** as much as ours. The round trips are gone, so what's left is the work each server does per command, and ours is doing something expensive.

## One Write per Pipeline

*Stop 3 of 4.*

### Step 1: watch the system calls

A **system call** is a request from a program to the operating system kernel: reading from a socket, writing to one. Each costs far more than an ordinary function call, because the CPU switches into the kernel and back. `strace -c` counts them. Running each server under strace while `redis-benchmark` sent 100,000 `GET`s, pipelined 16 at a time, on one connection:

```text
== s09
GET: 11158.22 requests per second, p50=0.167 msec
% time     seconds  usecs/call     calls    errors syscall
------ ----------- ----------- --------- --------- ----------------
 94.93    1.649899          16    100004           write
  5.07    0.088182          13      6325        65 read
------ ----------- ----------- --------- --------- ----------------
100.00    1.738081          16    106329        65 total
== s10
GET: 86355.79 requests per second, p50=0.159 msec
% time     seconds  usecs/call     calls    errors syscall
------ ----------- ----------- --------- --------- ----------------
 62.70    0.121577          19      6255           write
 37.30    0.072332          11      6333        71 read
------ ----------- ----------- --------- --------- ----------------
100.00    0.193909          15     12588        71 total
```

Lesson 9's server made **100,004 `write` calls for 100,000 replies**: one per reply, because `handle` wrote each one straight to the connection. It only made about 6,300 `read`s, because `bufio.Reader` already reads a whole pipeline at once. The second server, from this lesson, made **6,255 writes**: one per pipeline of 16 (100,000 ÷ 16 = 6,250). (strace slows every system call down, which is why both throughputs here are far lower than in the benchmark table. The counts are the point.)

### Step 2: a buffer that knows when to flush

The fix is a **`bufio.Writer`**: replies are written into a buffer in memory, and `Flush` sends everything in it with one `write`. The question is **when** to flush. Too rarely, and a client that sent one command waits forever for a reply sitting in our buffer. Too often, and we're back to one write per reply.

The answer is the reader's buffer. After a command is handled, if the `bufio.Reader` still holds unread bytes, the client has already sent another command, so there's no hurry. If it's empty, the client is waiting for us, so flush. `resp.Reader` gets one small method to ask:

```go noverify title="kv/resp/resp.go · lines 88–93"
// Buffered reports how many bytes have been read from the connection but
// not yet parsed: more than 0 means the client has already sent another
// command (it is pipelining).
func (r *Reader) Buffered() int {
	return r.br.Buffered()
}
```

and `handle` uses it:

```go noverify title="kv/server/server.go · lines 36–63"
// handle reads commands, as RESP arrays or inline lines, and writes one
// reply for each, until the client hangs up or breaks the protocol.
// Replies collect in a buffer that is sent when the client has no more
// commands waiting: one write for a whole pipeline, not one per reply.
func (s *Server) handle(conn net.Conn) {
	defer conn.Close()
	r := resp.NewReader(conn)
	w := bufio.NewWriter(conn)
	for {
		args, err := r.ReadCommand()
		if errors.Is(err, resp.ErrProtocol) {
			w.WriteString(errorReply(err.Error())) // then hang up, as Redis does
			w.Flush()
			return
		}
		if err != nil {
			return // the client hung up
		}
		if len(args) > 0 {
			w.WriteString(s.do(args))
		}
		if r.Buffered() == 0 { // nothing more waiting: send what we have
			if err := w.Flush(); err != nil {
				return
			}
		}
	}
}
```

Redis does the same thing in its own way: replies go into a per-client output buffer, and its event loop writes all of a client's pending replies at once before waiting for more input.

### Step 3: measured

The same three runs per configuration, adding this lesson's server:

| | no pipelining, SET | no pipelining, GET | `-P 16`, SET | `-P 16`, GET |
|---|---|---|---|---|
| Redis 8.10.2 | 177 | 208 | 1,299 | 1,754 |
| lesson 9's server | 160 | 173 | 495 | 658 |
| **this lesson's server** | 155 (158, 142, 155) | 176 (175, 176, 176) | **1,031** (976, 1,031, 1,143) | **1,143** (885, 1,266, 1,143) |

Pipelined throughput roughly **doubled**: `SET` from 495 to 1,031 thousand a second, `GET` from 658 to 1,143 thousand. Without pipelining nothing changed, as expected: with one command per round trip there's only ever one reply to send. Redis is still ahead on pipelined `GET`, and part of the gap is the single `sync.Mutex` every command takes, which Module 3 measures and splits.

<UnderTheHood title="Why a write system call costs so much">

A `write` on a socket traps into the kernel, checks the file descriptor, copies the bytes into the socket's send buffer, and may run the TCP stack to send a segment right away (Go sets `TCP_NODELAY` on every connection by default, turning off Nagle's algorithm, so small writes go out immediately rather than waiting to be combined). Then it returns to user space. Each step is small, but together they cost far more than appending a reply to a buffer in memory, and the strace counts above show how many of them one-write-per-reply makes. Batching is how every fast server handles it: nginx, databases, Redis.

</UnderTheHood>

## go-redis

*Stop 4 of 4.*

### Step 1: the real Go client

**go-redis** is the most widely used Redis client for Go. Pointing it at our server is the real test of compatibility: it wasn't written with our server in mind. `cmd/gopipe` sends 10,000 `INCR`s one at a time, then 10,000 more in pipelines of 100:

```go noverify title="kv/cmd/gopipe/main.go · lines 15–43"
func main() {
	addr := flag.String("addr", "127.0.0.1:6380", "server address")
	flag.Parse()
	ctx := context.Background()
	rdb := redis.NewClient(&redis.Options{Addr: *addr, Protocol: 2})
	defer rdb.Close()

	const n = 10_000
	rdb.Del(ctx, "hits")

	start := time.Now()
	for range n {
		if err := rdb.Incr(ctx, "hits").Err(); err != nil {
			log.Fatal(err)
		}
	}
	oneByOne := time.Since(start)

	start = time.Now()
	for i := 0; i < n; i += 100 {
		pipe := rdb.Pipeline()
		for range 100 {
			pipe.Incr(ctx, "hits")
		}
		if _, err := pipe.Exec(ctx); err != nil { // sends all 100, then reads 100 replies
			log.Fatal(err)
		}
	}
	pipelined := time.Since(start)
```

`rdb.Pipeline()` collects commands; `Exec` sends them all, then reads all the replies. Against our server, on this machine:

```text
one at a time: 10000 INCR in 235ms (23.5 µs each)
pipelined:     10000 INCR in 9ms (0.9 µs each), 100 per round trip
hits = 20000
```

Pipelined, each `INCR` cost **0.9 µs** against **23.5 µs** one at a time: about 26 times faster, on a connection whose round trip is only tens of microseconds. Over four runs the one-at-a-time figure ranged from 23.0 to 34.6 µs and the pipelined one from 0.8 to 0.9 µs. And `hits = 20000`: every increment counted.

### Step 2: the handshake we don't speak

The program sets `Protocol: 2`. Without it, go-redis starts every connection with a newer handshake. Through `cmd/spy`, that looked like this:

```text
client → "*2\r\n$5\r\nhello\r\n$1\r\n3\r\n"
← server "-ERR unknown command 'hello', with args beginning with: '3' \r\n"
client → "*4\r\n$6\r\nclient\r\n$7\r\nsetinfo\r\n$8\r\nLIB-NAME\r\n$19\r\ngo-redis(,go1.27.0)\r\n*4\r\n$6\r\nclient\r\n$7\r\nsetinfo\r\n$7\r\nLIB-VER\r\n$6\r\n9.22.0\r\n"
← server "-ERR unknown command 'client', with args beginning with: 'setinfo' 'LIB-NAME' 'go-redis(,go1.27.0)' \r\n-ERR unknown command 'client', with args beginning with: 'setinfo' 'LIB-VER' '9.22.0' \r\n"
client → "*2\r\n$3\r\ndel\r\n$4\r\nhits\r\n"
← server ":0\r\n"
```

go-redis first asks for RESP3, the newer version of the protocol, with `HELLO 3`. Our server doesn't know `HELLO`, and go-redis treats that error as "this server only speaks RESP2" and carries on. Then it sends two `CLIENT SETINFO` commands to tell the server its name and version, **pipelined in one write**, and both error replies came back in one write too: the buffered writer at work. go-redis ignores those errors as well, and then the program's commands run normally. Well-written clients degrade gracefully, which is what let us get this far without implementing either command.

## Exercises

<Exercise n={1} title="HELLO" level="medium">

Implement `HELLO` for protocol version 2: reply with the array of server details Redis sends (check it with `cmd/raw` against Redis first), and `-NOPROTO` for version 3. Does go-redis's handshake change?

<Solution>

Redis 8.10.2 answers `HELLO 2` with an array of 14 elements, seven field/value pairs starting `server`, `redis`, `version`; reply with at least `server`, `version` and `proto` (`2`). For a version it doesn't support, Redis replies `-NOPROTO unsupported protocol version` (it said that for `HELLO 4`); ours should say it for `HELLO 3`. go-redis then gets a proper refusal instead of an unknown command, and still falls back to RESP2.

</Solution>

</Exercise>

<Exercise n={2} title="How deep a pipeline?" level="easy">

Run `redis-benchmark -t get -n 400000 -c 50 -q` with `-P 1, 4, 16, 64, 256` against this lesson's server. What happens to throughput, and to latency?

<Solution>

Measured on this machine, `GET` with 50 clients: 168k, 537k, 889k, 1,538k and 1,703k requests a second for depths 1, 4, 16, 64 and 256 (the 889k at depth 16 sits inside the 885–1,266k spread of stop 3's three runs: laptop benchmarks wobble). Each step up gains less (64 to 256 added only 11%), while the median latency went from 0.159 ms to 5.839 ms: each reply now waits for its whole batch to be read and answered. Once round trips are rare, the per-command work (parsing, the lock, the map) is the limit. That trade is why clients batch in the tens to hundreds, not millions.

</Solution>

</Exercise>

<Exercise n={3} title="Count the allocations" level="medium">

Write `BenchmarkPipelinedGET` in `server/server_test.go` over `net.Pipe`, run it with `-benchmem`, and find the biggest source of allocations with `go test -bench . -memprofile mem.out` and `go tool pprof`.

<Solution>

Read the code first, then check it against the profile: each command allocates a `[]string` for its arguments and a string per argument in `resp`, and `do` builds each reply as a new string by concatenation. Those should dominate `pprof -top`. Writing replies straight into the `bufio.Writer` (with `strconv.AppendInt` into a reused buffer) instead of building strings is the usual way to remove the reply allocations; re-run the benchmark to see what it bought.

</Solution>

## The Lab

<Lab
  title="When to Flush"
  archetype="fix-it"
  difficulty="guided"
  points={80}
  hintCost={5}
  verify="self-check"
  expect="ALL CHECKS PASS"
  objective="This handler buffers its replies and only flushes when the buffer passes 4 KB, so a pipeline's replies never arrive and an interactive client waits forever. Flushing after every reply would fix that and cost one write per reply. Flush at the right moment: a pipeline of 200 commands must get all its replies in at most 5 writes, and a client sending one PING at a time must get each PONG at once."
  starter={`package main

import (
	"bufio"
	"fmt"
	"io"
	"net"
	"strings"
	"time"
)

// handle answers inline commands (PING and ECHO) on conn, one reply per
// command. Replies must be buffered so that a pipeline of commands gets its
// replies in as few writes as possible, but a client that sends one command
// and waits must get its reply straight away.
func handle(conn io.ReadWriter) {
	r := bufio.NewReader(conn)
	w := bufio.NewWriter(conn)
	for {
		line, err := r.ReadString('\\n')
		if err != nil {
			return
		}
		args := strings.Fields(line)
		if len(args) == 0 {
			continue
		}
		switch strings.ToUpper(args[0]) {
		case "PING":
			w.WriteString("+PONG\\r\\n")
		case "ECHO":
			w.WriteString("$" + fmt.Sprint(len(args[1])) + "\\r\\n" + args[1] + "\\r\\n")
		}
		if w.Buffered() > 4096 {
			w.Flush()
		}
	}
}

// ── below this line: do not edit ──

// countingConn is a connection made of a fixed input and a recorded output,
// which counts how many Write calls the server makes.
type countingConn struct {
	in     io.Reader
	out    strings.Builder
	writes int
}

func (c *countingConn) Read(p []byte) (int, error) { return c.in.Read(p) }
func (c *countingConn) Write(p []byte) (int, error) {
	c.writes++
	return c.out.Write(p)
}

func main() {
	ok := true
	fail := func(f string, a ...any) { fmt.Printf("FAIL "+f+"\\n", a...); ok = false }

	// 1. A pipeline: 200 commands arrive at once. All 200 replies, in few writes.
	var pipeline strings.Builder
	for i := range 200 {
		fmt.Fprintf(&pipeline, "ECHO msg%d\\r\\n", i)
	}
	c := &countingConn{in: strings.NewReader(pipeline.String())}
	handle(c)
	if got := strings.Count(c.out.String(), "\\r\\nmsg"); got != 200 {
		fail("pipeline of 200 ECHOs: %d replies arrived, want 200", got)
	}
	if c.writes > 5 {
		fail("pipeline of 200 ECHOs took %d writes, want at most 5", c.writes)
	}

	// 2. An interactive client: one command, then it waits for the reply.
	client, server := net.Pipe()
	go handle(server)
	defer client.Close()
	br := bufio.NewReader(client)
	for i := range 3 {
		fmt.Fprint(client, "PING\\r\\n")
		client.SetReadDeadline(time.Now().Add(time.Second))
		reply, err := br.ReadString('\\n')
		if err != nil || reply != "+PONG\\r\\n" {
			fail("interactive PING %d: got %q, %v; the reply never came", i+1, reply, err)
			break
		}
	}

	if ok {
		fmt.Println("ALL CHECKS PASS")
	}
}`}
  verifier="Feeds 200 pipelined ECHO commands through a connection that counts Write calls, and checks all 200 replies arrive in at most 5 writes; then sends PING three times over net.Pipe, waiting up to a second for each reply. Prints ALL CHECKS PASS."
  hints={[
    "The signal is the reader, not the writer: r.Buffered() is how many bytes the client has sent that you haven't read yet.",
    "After handling a command, if r.Buffered() == 0, the client has nothing else in flight and is waiting: call w.Flush().",
    "When ReadString returns an error (the client closed its side), flush whatever is still buffered before returning."
  ]}
  flag="GO{when_to_flush}"
>

Flushing after every reply passes the interactive check and fails the pipeline one with 200 writes. The lab is built so that only the right signal passes both.

</Lab>

<Recap>

- Without pipelining, every command costs a **round trip**; the server's speed barely matters. Pipelining sends many commands before reading the replies, and RESP supports it for free.
- `redis-benchmark` against Redis 8.10.2: close without pipelining (177/208k against our 160/173k SET/GET per second), far behind with `-P 16` (1,299/1,754k against 495/658k).
- `strace -c` found it: **100,004 writes for 100,000 replies**. A `bufio.Writer` flushed when the reader has nothing buffered made it **6,255**, and doubled pipelined throughput to 1,031/1,143k.
- **go-redis** worked against our server: pipelined `INCR`s cost 0.9 µs against 23.5 µs one at a time. Its `HELLO 3` handshake failed and it fell back to RESP2 on its own.

</Recap>
