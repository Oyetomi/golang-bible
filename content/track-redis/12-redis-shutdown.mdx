<HeroCard label="Build Your Own Redis · Lesson 12" title="Stopping Cleanly: Shutdown with context">

Every server is stopped eventually: a new version is deployed, a machine is drained, someone presses Ctrl-C. So far ours simply dies when told to stop, in the middle of whatever it was doing. This lesson measures what that does to the clients, then teaches the server to stop *cleanly*, using the tool Go provides for "stop, and here's how long you've got": `context`.

Three stops:

1. **Pulling the plug.** What SIGTERM does to our server and its clients, measured.
2. **Shutdown.** Stop accepting, finish what's in hand, wait, with a deadline from a `context`.
3. **The stuck client, and a bug.** A deadline that fires, and a test that caught lost replies.

## Pulling the Plug

*Stop 1 of 3.*

### Step 1: how a server is told to stop

A program is stopped with a **signal**: a small numbered message the operating system delivers to a process. Two matter here:

- **SIGINT** is what Ctrl-C in a terminal sends.
- **SIGTERM** is what `kill`, `docker stop` and Kubernetes send when they want a process to end. It means "please stop". If the process is still running some seconds later (10 for Docker, 30 by default for Kubernetes), they send **SIGKILL**, which can't be caught: the process just vanishes.

A Go program that doesn't ask for signals gets Go's default: on SIGINT or SIGTERM it exits immediately, wherever it is. The shell reports that as exit status **143**, which is 128 + 15, SIGTERM's number.

### Step 2: a busy client

To see what "immediately" means for clients, `cmd/busy` opens 20 connections and has each one pipeline `INCR`s, 100 at a time, as fast as it can, until the server goes away:

```go noverify title="kv/cmd/busy/main.go · lines 26–57"
	endings := map[string]int{} // how each connection ended
	var wg sync.WaitGroup
	for range *clients {
		wg.Go(func() {
			conn, err := net.Dial("tcp", *addr)
			if err != nil {
				log.Fatal(err)
			}
			defer conn.Close()
			r := bufio.NewReader(conn)
			req := strings.Repeat("INCR hits\r\n", *batch)
			var end string
			for end == "" {
				if _, err := io.WriteString(conn, req); err != nil {
					end = "write: " + short(err)
					break
				}
				sent.Add(int64(*batch))
				for range *batch {
					if _, err := r.ReadString('\n'); err != nil {
						end = "read: " + short(err)
						break
					}
					replies.Add(1)
				}
			}
			mu.Lock()
			endings[end]++
			mu.Unlock()
		})
	}
	wg.Wait()
```

Each connection writes a batch of 100 `INCR hits` lines, then reads 100 replies. It counts every command it **sent** and every reply it **got**, and when the connection ends, it records how. A shell script starts lesson 11's server, starts `busy`, and one second later sends the server SIGTERM:

```text
$ ./stop.sh s11
kv-server exit status 143
== client
sent 969800 INCRs, got 967800 replies: 2000 unanswered
20 connections ended with read: EOF (the server closed the connection)
== server
listening on 127.0.0.1:6391
```

The server died with status 143 and said nothing. Every client was in the middle of a batch: **2,000 `INCR`s were sent and never answered**, 100 per connection. (In other runs some connections ended with `connection reset by peer` instead of EOF: when a process dies with unread bytes in a socket, the kernel answers with a TCP *reset* rather than a normal close.)

### Step 3: what the client can't know

Here is the real problem. Each client has 100 commands without replies. **Did they run?** Some may have: the server may have run them and died before sending the replies (lesson 10's replies wait in a buffer until the pipeline is done). Others were never read. The client can't tell which. For `INCR`, retrying one that already ran counts it twice; not retrying one that never ran loses it. There's no safe choice, because the server left without saying where it stopped.

## Shutdown

*Stop 2 of 3.*

### Step 1: what "cleanly" means

A clean stop, a **graceful shutdown**, has three steps:

1. **Stop accepting** new connections: close the listener.
2. **Finish what's in hand**: every command a connection has already received gets run and answered. Then that connection closes.
3. **Don't wait forever**: if some connection won't finish (a client that stopped reading, say), give up after a deadline and close it anyway.

After that, any command the client didn't get a reply for **did not run**, so it's safe to send again, to this server after its restart or to another one.

### Step 2: knowing the connections

To wake or close connections, the server has to know which are open. `Server` gets a few new fields:

```go noverify title="kv/server/server.go · lines 21–39"
type Server struct {
	shards []*shard
	seed   maphash.Seed

	// ReadLocks lets GETs on the same shard run at the same time, under a
	// read lock. Writes still take the lock alone.
	ReadLocks bool

	commands atomic.Int64 // commands run, for Commands

	mu       sync.Mutex // guards the three fields below
	listener net.Listener
	conns    map[net.Conn]struct{}
	closing  bool
	handlers sync.WaitGroup // one per open connection
}

// ErrServerClosed is what Serve returns after Shutdown.
var ErrServerClosed = errors.New("server closed")
```

- `conns` is a **set** of open connections: a map whose values carry nothing (`struct{}` takes no memory), used only for its keys.
- `closing` records that shutdown has begun.
- `handlers` is a `sync.WaitGroup`, a counter of running goroutines: `Add(1)` when one starts, `Done()` when it ends, and `Wait()` blocks until it's back to zero.
- `mu` guards `listener`, `conns` and `closing`, because `Serve`, every handler and `Shutdown` all touch them from different goroutines.
- `ErrServerClosed` is a sentinel error (lesson 4) so the caller can tell "stopped because I asked" from a real failure. `net/http` has the same thing with the same name.

`Serve` records each connection before handing it to a goroutine:

```go noverify title="kv/server/server.go · lines 72–113"
// Serve accepts connections on l and serves each one in its own
// goroutine, until Shutdown.
func (s *Server) Serve(l net.Listener) error {
	s.mu.Lock()
	s.listener = l
	s.mu.Unlock()
	for {
		conn, err := l.Accept()
		if err != nil {
			if s.isClosing() {
				return ErrServerClosed
			}
			return err
		}
		if !s.track(conn) {
			conn.Close() // accepted just as Shutdown began
			continue
		}
		go s.handle(conn)
	}
}

// track records an open connection, unless the server is shutting down.
func (s *Server) track(conn net.Conn) bool {
	s.mu.Lock()
	defer s.mu.Unlock()
	if s.closing {
		return false
	}
	if s.conns == nil {
		s.conns = map[net.Conn]struct{}{}
	}
	s.conns[conn] = struct{}{}
	s.handlers.Add(1)
	return true
}

func (s *Server) isClosing() bool {
	s.mu.Lock()
	defer s.mu.Unlock()
	return s.closing
}
```

`track` refuses a connection that arrives after shutdown began, so no new handler can start while `Shutdown` is waiting for the old ones. When `Shutdown` closes the listener, `Accept` returns an error; `Serve` sees `closing` and returns `ErrServerClosed`.

And each handler removes itself when it ends, in a `defer`, so it happens however the loop exits:

```go noverify title="kv/server/server.go · lines 158–167"
func (s *Server) handle(conn net.Conn) {
	defer func() {
		conn.Close()
		s.mu.Lock()
		delete(s.conns, conn)
		s.mu.Unlock()
		s.handlers.Done()
	}()
	r := resp.NewReader(conn)
	w := bufio.NewWriter(conn)
```

### Step 3: Shutdown

```go noverify title="kv/server/server.go · lines 115–149"
// Shutdown stops the server gracefully. It stops accepting connections,
// then lets every connection finish the commands it has already received
// and send their replies. If ctx ends first, it closes the connections
// that are left and returns ctx's error.
func (s *Server) Shutdown(ctx context.Context) error {
	s.mu.Lock()
	s.closing = true
	if s.listener != nil {
		s.listener.Close()
	}
	for conn := range s.conns {
		// Wake any handler waiting for its client's next command: its read
		// now fails at once, but bytes already buffered are still served.
		conn.SetReadDeadline(time.Now())
	}
	s.mu.Unlock()

	done := make(chan struct{})
	go func() {
		s.handlers.Wait()
		close(done)
	}()
	select {
	case <-done:
		return nil
	case <-ctx.Done():
		s.mu.Lock()
		for conn := range s.conns {
			conn.Close() // unblocks handlers stuck writing to slow clients
		}
		s.mu.Unlock()
		<-done
		return ctx.Err()
	}
}
```

Line by line:

- **Close the listener.** No new clients.
- **`conn.SetReadDeadline(time.Now())`** on every connection. A **deadline** makes a read fail with a timeout error if it hasn't finished by that time; a deadline of *now* makes the next read that actually has to wait for the network fail at once. A handler blocked waiting for its client's next command wakes up and returns. A handler in the middle of a pipeline is unaffected while its reader still has buffered bytes to parse: it finishes those commands first.
- **Wait for the handlers**, but in a goroutine that closes a channel `done` when `Wait` returns, because `Wait` itself can't be interrupted.
- **`select`** on two channels: whichever is ready first wins. If `done` closes, every connection finished: return `nil`. If **`ctx.Done()`** closes first, the deadline passed: close the remaining connections by force, wait for their handlers to notice, and return `ctx.Err()`.

`ctx` is a **`context.Context`**: Go's standard way to pass "stop by this time, or when told" into a function. `ctx.Done()` is a channel that closes when the context ends, and `ctx.Err()` says why: `context.DeadlineExceeded` for a deadline, `context.Canceled` for a cancel. `Shutdown` doesn't pick a deadline itself; the caller does.

### Step 4: main listens for the signal

`cmd/kv-server` asks for SIGINT and SIGTERM, and calls `Shutdown` when one arrives:

```go noverify title="kv/cmd/kv-server/main.go · lines 37–54"
	// ctx ends when the process gets Ctrl-C (SIGINT) or SIGTERM, the signal
	// docker stop, kill and Kubernetes send.
	ctx, stop := signal.NotifyContext(context.Background(), os.Interrupt, syscall.SIGTERM)
	defer stop()
	go func() {
		if err := srv.Serve(l); !errors.Is(err, server.ErrServerClosed) {
			log.Fatal(err)
		}
	}()

	<-ctx.Done()
	log.Printf("shutting down: %d commands run so far", srv.Commands())
	start := time.Now()
	sctx, cancel := context.WithTimeout(context.Background(), *grace)
	defer cancel()
	err = srv.Shutdown(sctx)
	log.Printf("shut down in %v (%v): %d commands run", time.Since(start).Round(time.Millisecond), err, srv.Commands())
}
```

**`signal.NotifyContext`** returns a context that is cancelled when the process receives one of the listed signals, and stops Go's default "exit now" for them. `Serve` moves into a goroutine, and `main` blocks on `<-ctx.Done()` until the signal comes. Then it makes a *second* context with **`context.WithTimeout`**, which ends by itself after `-grace` (5 seconds by default), and hands that to `Shutdown`. `defer cancel()` releases the timer if `Shutdown` finishes early.

## The Stuck Client

*Stop 3 of 3.*

### Step 1: a client that never reads

Waiting for every connection to finish assumes every client cooperates. `cmd/stuck` doesn't: it sends a million `PING`s, 6 MB of requests, and never reads a reply:

```go noverify title="kv/cmd/stuck/main.go · lines 14–27"
func main() {
	addr := flag.String("addr", "127.0.0.1:6380", "server address")
	flag.Parse()
	conn, err := net.Dial("tcp", *addr)
	if err != nil {
		log.Fatal(err)
	}
	// 1,000,000 PINGs is 6 MB of requests and 7 MB of replies: far more than
	// the kernel's socket buffers hold, so the server's writes soon block.
	req := strings.Repeat("PING\r\n", 1_000_000)
	go conn.Write([]byte(req))
	fmt.Println("sent a million PINGs; not reading any replies")
	time.Sleep(time.Hour)
}
```

The server answers `PONG`s until the socket's send buffer in the kernel is full, and then its `Flush` blocks: there's nowhere to put more bytes until the client reads. A handler blocked in a write never gets back to its read, so the read deadline doesn't reach it. Without a limit on the wait, `Shutdown` would wait for this client forever. With `-grace 2s`:

```text
$ ./stuck.sh
sent a million PINGs; not reading any replies
kv-server exit status 0
listening on 127.0.0.1:6392
shutting down: 78994 commands run so far
shut down in 2.002s (context deadline exceeded): 79112 commands run
```

`Shutdown` gave up after **2.002 seconds** and returned `context deadline exceeded`, having closed the stuck connection by force; the server still exited normally. It ran 118 more commands during those two seconds, whatever fitted into the socket buffers. This is exactly what the context is for: the caller decides how long a clean stop may take, and `Shutdown` enforces it. Keep `-grace` shorter than the time your orchestrator waits before SIGKILL, so the server finishes on its own terms.

### Step 2: the test, and the bug it found

`server/shutdown_test.go` checks the promise directly: a client pipelines 20,000 `INCR`s, the server shuts down mid-pipeline, and the number of replies the client receives must equal the number of commands the server ran:

```go noverify title="kv/server/shutdown_test.go · lines 16–67"
// Shutdown with an idle client and a client mid-pipeline: the pipeline's
// replies all arrive, then both connections close, well inside the deadline.
func TestShutdown(t *testing.T) {
	l, err := net.Listen("tcp", "127.0.0.1:0")
	if err != nil {
		t.Fatal(err)
	}
	s := New(kv.New())
	served := make(chan error, 1)
	go func() { served <- s.Serve(l) }()

	idle, err := net.Dial("tcp", l.Addr().String())
	if err != nil {
		t.Fatal(err)
	}
	defer idle.Close()
	busy, err := net.Dial("tcp", l.Addr().String())
	if err != nil {
		t.Fatal(err)
	}
	defer busy.Close()
	fmt.Fprint(busy, strings.Repeat("INCR hits\r\n", 20_000))
	r := bufio.NewReader(busy)
	if _, err := r.ReadString('\n'); err != nil { // the server is working on it
		t.Fatal(err)
	}

	ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
	defer cancel()
	start := time.Now()
	if err := s.Shutdown(ctx); err != nil {
		t.Fatalf("Shutdown: %v", err)
	}
	t.Logf("shut down in %v", time.Since(start))
	if err := <-served; !errors.Is(err, ErrServerClosed) {
		t.Errorf("Serve returned %v, want ErrServerClosed", err)
	}

	got := 1
	for {
		if _, err := r.ReadString('\n'); err != nil {
			break // closed by the server
		}
		got++
	}
	if int64(got) != s.Commands() {
		t.Errorf("server ran %d commands, client got %d replies", s.Commands(), got)
	}
	if _, err := net.Dial("tcp", l.Addr().String()); err == nil {
		t.Error("the server still accepts connections after Shutdown")
	}
}
```

The first version of `handle` failed it, some runs and not others:

```text
--- FAIL: TestShutdown (0.00s)
    shutdown_test.go:49: shut down in 148.583µs
    shutdown_test.go:62: server ran 1116 commands, client got 700 replies
FAIL
FAIL	kv/server	0.819s
FAIL
```

The server ran 1,116 commands; the client got 700 replies. 416 answers were lost. The cause was a line from lesson 10: `handle` only flushes when `r.Buffered() == 0`, that is, when the reader holds no more bytes. But the reader reads the socket in chunks of 4,096 bytes, and `INCR hits\r\n` is 11 bytes, so a chunk often ends in the middle of a command. With half a command buffered, `Buffered()` isn't zero, so no flush; the reader then needs more bytes, the read deadline makes that read fail, and the handler returned, **with the replies to every complete command still sitting in `w`**. (An earlier version of the test used an 8-byte command, which divides 4,096 exactly, so chunks never split one, and it passed every time. The bug only showed up once the test's commands were an awkward size.)

The fix is to flush before returning, however the loop ends:

```go noverify title="kv/server/server.go · lines 168–191"
	for {
		args, err := r.ReadCommand()
		if errors.Is(err, resp.ErrProtocol) {
			w.WriteString(errorReply(err.Error())) // then hang up, as Redis does
			w.Flush()
			return
		}
		if err != nil {
			// The client hung up, or Shutdown woke us. Replies may still be
			// waiting in w: if the reader held part of a command, we didn't
			// flush after the last full one. Send them before closing.
			w.Flush()
			return
		}
		if len(args) > 0 {
			w.WriteString(s.do(args))
			s.commands.Add(1)
		}
		if r.Buffered() == 0 { // nothing more waiting: send what we have
			if err := w.Flush(); err != nil {
				return
			}
		}
	}
```

After it, the test passed 100 runs out of 100, and under `-race`:

```text
$ go test -run Shutdown -v ./server
    shutdown_test.go:49: shut down in 72.333µs
--- PASS: TestShutdown (0.00s)
PASS
ok  	kv/server	(cached)
```

<UnderTheHood title="How a read deadline wakes a blocked goroutine">

A goroutine blocked in `conn.Read` isn't blocking an OS thread. Go's network poller registers the socket with the kernel (kqueue on macOS, epoll on Linux) and parks the goroutine. `SetReadDeadline` sets a timer inside the runtime tied to that socket. When the timer fires, the runtime marks the socket's read side as timed out and makes the parked goroutine runnable again; its `Read` returns an error that satisfies `errors.Is(err, os.ErrDeadlineExceeded)`. That's why one goroutine can safely interrupt another's read: nothing is killed, the read simply ends with an error, and the handler's own code decides what to do next. `Close` from another goroutine works the same way, with a "use of closed network connection" error instead.

</UnderTheHood>

## Exercises

<Exercise n={1} title="A second Ctrl-C" level="easy">

While `Shutdown` waits for a stuck client, pressing Ctrl-C again does nothing, because `signal.NotifyContext` already caught it. Make a second SIGINT or SIGTERM exit at once.

<Solution>

After `<-ctx.Done()`, call `stop()`: it stops the context from catching the signals, so Go's default behaviour returns and a second signal kills the process straight away. This is common in real servers ("press Ctrl-C again to force"). Test it with `cmd/stuck` and a long `-grace`.

</Solution>

</Exercise>

<Exercise n={2} title="Idle timeout" level="medium">

Real Redis has a `timeout` setting: close a client that sends nothing for that many seconds. Add `-idle 30s` to `kv-server`, using a read deadline set before each blocking read. Test it with `redis-cli` left idle.

<Solution>

In `handle`, before each `ReadCommand` that will have to wait (when `r.Buffered() == 0`), call `conn.SetReadDeadline(time.Now().Add(idle))`. A read that times out returns an error and the handler closes the connection, flushing first. Careful: `Shutdown` also uses the read deadline; set it only if `closing` is false, under `s.mu`, or `Shutdown`'s "now" could be overwritten by "now + 30 s".

</Solution>

</Exercise>

<Exercise n={3} title="docker stop" level="medium">

Build the server into an image (as in Part 4's containers chapter), run it, put `cmd/busy` on it, and run `docker stop`. What exit status does `docker ps -a` show, with and without this lesson's signal handling? What happens with `docker stop -t 1` and `cmd/stuck`?

<Solution>

Without handling, SIGTERM kills it at once: `Exited (143)`. With it: `Exited (0)`, after about a millisecond. With `cmd/stuck` and the default `-grace 5s`, `docker stop -t 1` sends SIGKILL after 1 second, before `Shutdown`'s deadline, so the container ends `Exited (137)` (128 + 9, SIGKILL): the grace period has to be shorter than the orchestrator's. Also check that the server is PID 1 or started with `exec`, or the signal never reaches it (Part 4, Linux chapter).

</Solution>

</Exercise>

// Server answers every line with a count of the lines it has answered so
// far: ":1\\r\\n", ":2\\r\\n", and so on.
type Server struct {
	answered atomic.Int64

	mu       sync.Mutex
	listener net.Listener
	conns    map[net.Conn]struct{}
	handlers sync.WaitGroup
}

func (s *Server) Serve(l net.Listener) error {
	s.mu.Lock()
	s.listener = l
	s.conns = map[net.Conn]struct{}{}
	s.mu.Unlock()
	for {
		conn, err := l.Accept()
		if err != nil {
			return err
		}
		s.mu.Lock()
		s.conns[conn] = struct{}{}
		s.handlers.Add(1)
		s.mu.Unlock()
		go s.handle(conn)
	}
}

func (s *Server) handle(conn net.Conn) {
	defer func() {
		conn.Close()
		s.mu.Lock()
		delete(s.conns, conn)
		s.mu.Unlock()
		s.handlers.Done()
	}()
	r := bufio.NewReader(conn)
	w := bufio.NewWriter(conn)
	for {
		if _, err := r.ReadString('\\n'); err != nil {
			return
		}
		fmt.Fprintf(w, ":%d\\r\\n", s.answered.Add(1))
		if r.Buffered() == 0 {
			if w.Flush() != nil {
				return
			}
		}
	}
}

// has already received and send their answers, and give up when ctx ends.
func (s *Server) Shutdown(ctx context.Context) error {
	s.mu.Lock()
	defer s.mu.Unlock()
	s.listener.Close()
	for conn := range s.conns {
		conn.Close()
	}
	s.handlers.Wait()
	return nil
}

<Recap>

- **SIGTERM** is how `kill`, Docker and Kubernetes ask a process to stop; Go's default is to exit at once (status **143**). Killed mid-pipeline, our server left 2,000 `INCR`s unanswered, and the clients couldn't know which had run.
- A **graceful shutdown**: close the listener, wake idle handlers with a **read deadline of now**, let busy ones finish and flush, wait for all of them with a `sync.WaitGroup`, and give up when the **`context`** ends.
- **`signal.NotifyContext`** turns a signal into a cancelled context; **`context.WithTimeout`** bounds the wait. Measured: the server ran **1,876,000** commands and the clients got **1,876,000** replies; shutdown took about **1 ms**.
- A client that never reads blocks its handler in a write; the context deadline closed it after **2.002 s**.
- The test found a real bug: with half a command buffered, `handle` returned without flushing, and lost **416 of 1,116** replies. Flush before returning.

</Recap>
