<HeroCard label="Appendix · Tooling" title="Burp Suite: How It Works & How to Use It">

Here's the thing, sport. Every web hacker you've ever read a writeup from used the same tool, and it isn't magic — it's a **proxy**. Burp Suite sits *between* your browser and the target, and every request your browser makes flows *through* Burp first. That one fact — that Burp is a **man-in-the-middle** you point at yourself — is the whole foundation. Once a request is paused in Burp, you can read it, change it, replay it a thousand times with different values, and watch what comes back. That's how you find an IDOR (change the `id`), test an auth bypass (drop the token), or fuzz a parameter (Intruder). The browser is just where the request *starts*; Burp is where you *attack* it.

This chapter explains Burp from the **mechanism up**, the way the rest of the Bible does — not a button tour, but *why* it works. We'll prove the interception model with a **runnable Go proxy** that does exactly what Burp does at its core (intercept a request and modify it in flight), explain the **TLS story** (why you install Burp's CA certificate and what that actually means), then walk each tool — **Proxy**, **Repeater**, **Intruder**, **Decoder**, **Comparer**, **Sequencer**, **Scanner** — and *when* you reach for it. We finish with the real hunting workflow and a map from every attack class in this course onto the Burp tool that exercises it. By the end you won't see Burp as a wall of tabs; you'll see a proxy you own, and know exactly which tab does what. (Authorized targets only — your own labs, a program in scope, the PortSwigger Academy.) Let's wire it up, sport.

## What Burp Is

Strip the marketing and Burp Suite is two things glued together: a **proxy** that captures your traffic, and a **toolkit** that operates on captured requests.

<Define term="Burp Suite">
**Burp Suite** is an integrated platform for testing web application security, built around an **intercepting proxy**. You configure your browser to send all its traffic *through* Burp; Burp records every request and response (building a **sitemap** of the target), and lets you **pause, inspect, modify, and replay** any of them. Around that proxy sit specialized tools: **Repeater** (resend and tweak a single request by hand), **Intruder** (resend a request many times with automated payloads — for fuzzing, brute-forcing, enumeration), **Decoder/Inspector** (encode/decode data), **Comparer** (diff two responses), **Sequencer** (analyze the randomness of tokens), and — in the paid **Professional** edition — an automated **Scanner**. The free **Community** edition includes the proxy, Repeater, Decoder, and a rate-limited Intruder, which is enough to learn every technique in this course. Burp is **not** an exploit; it's a precision instrument for *seeing and manipulating* HTTP, which is where almost every web vulnerability lives.
</Define>

<ConceptGrid cols={2}>
  <ConceptCard label="The proxy is the heart">Everything starts here: your browser → Burp → the target. Burp logs all of it and is where you pause a request to edit it. The other tools all operate on requests the proxy captured.</ConceptCard>
  <ConceptCard label="Community vs Professional">**Community** (free): proxy, Repeater, Decoder, Comparer, throttled Intruder — enough for all manual testing and learning. **Professional** (paid): full-speed Intruder, the automated **Scanner**, **Collaborator** (out-of-band detection for SSRF/blind bugs), and saved projects.</ConceptCard>
  <ConceptCard label="It sees, it doesn't exploit">Burp shows and edits HTTP; *you* supply the attack idea (change this id, drop this token, fuzz this param). The skill is knowing what to change — which is what the rest of this course teaches.</ConceptCard>
  <ConceptCard label="Authorized use only">Proxying traffic is only legitimate against targets you're allowed to test — your own apps, a bug-bounty program in scope, or deliberately-vulnerable labs (PortSwigger Web Security Academy, your own Go servers). Intercepting other people's traffic is illegal.</ConceptCard>
</ConceptGrid>

## How Interception Works

The one concept to truly understand: Burp is a **man-in-the-middle proxy** you deliberately insert into your *own* connection. Your request doesn't go to the target — it goes to Burp, which can read and change it, then forwards it on. Don't take it on faith; here's that exact mechanism in runnable Go.

<Define term="Intercepting (MITM) proxy">
An **intercepting proxy** sits **between** a client and a server so that all traffic passes through it: the client sends its request to the proxy, the proxy may **read and modify** it, then forwards it to the real server — and does the same to the response on the way back. Burp is such a proxy, pointed at your own browser. For plain HTTP this is trivial (the bytes are right there). For **HTTPS**, the traffic is encrypted end-to-end, so to read it Burp performs a deliberate man-in-the-middle: it **terminates TLS itself**, generating an on-the-fly certificate for the target's domain **signed by Burp's own Certificate Authority**. Your browser would normally reject that cert (it isn't from a real CA) — which is why you **install Burp's CA certificate** into your browser's trust store as a one-time setup. After that, the browser trusts Burp's generated certs, Burp decrypts the traffic, and you can read and edit HTTPS like plain HTTP. Installing that CA is exactly why you must do it only in your own testing browser: anything that can MITM your TLS can read your secrets.
</Define>

<GoPlayground>

```go
package main

import (
	"fmt"
	"io"
	"net/http"
	"net/http/httptest"
	"net/http/httputil"
	"net/url"
)

func main() {
	// The "origin" is the real target. It reports what it ACTUALLY received,
	// so we can prove the proxy modified the request in flight.
	origin := httptest.NewServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		fmt.Fprintf(w, "origin saw: role=%q x-tampered=%q",
			r.URL.Query().Get("role"), r.Header.Get("X-Tampered"))
	}))
	defer origin.Close()
	originURL, _ := url.Parse(origin.URL)

	// THIS is Burp at its core: a man-in-the-middle proxy. It receives the
	// client's request, can READ and MODIFY it, then forwards it on.
	proxy := httputil.NewSingleHostReverseProxy(originURL)
	proxy.Director = func(req *http.Request) {
		req.URL.Scheme = originURL.Scheme
		req.URL.Host = originURL.Host
		// Intercept-and-modify, exactly like editing in Burp's intercept tab
		// or a "match & replace" rule:
		q := req.URL.Query()
		if q.Get("role") == "user" {
			q.Set("role", "admin") // tamper: escalate the role mid-flight
		}
		req.URL.RawQuery = q.Encode()
		req.Header.Set("X-Tampered", "by-the-proxy")
	}
	front := httptest.NewServer(proxy)
	defer front.Close()

	// The client thinks it's sending role=user with no special header.
	resp, _ := http.Get(front.URL + "/account?role=user")
	body, _ := io.ReadAll(resp.Body)
	resp.Body.Close()
	fmt.Println("client sent: /account?role=user")
	fmt.Println(string(body))
}
```

<Gotcha>
**Installing Burp's CA certificate gives Burp the power to read all your HTTPS — so do it only in a dedicated testing browser/profile.** That CA is what lets Burp forge a trusted certificate for *any* site and decrypt the traffic; it's the same capability a real attacker would need, granted to Burp on purpose. Never install it in your everyday browser, never leave Burp proxying when you're doing normal browsing, and remove/segregate it when you're done. The flip side is the defender's lesson: this is exactly why **certificate pinning** exists (an app that pins its server's cert refuses Burp's forged one), why you keep your CA trust store clean, and why "just click through the cert warning" is dangerous advice — a cert warning can mean someone is doing to you what Burp does for you.
</Gotcha>

<UnderTheHood title="TLS Interception, MITM Cert Generation & HTTP Proxying">

An intercepting proxy does not simply forward packets at layer 4; it terminates, re-encrypts, and rewrites layer 7 HTTP/1.1, HTTP/2, and TLS state machines simultaneously.

### 1. The HTTP `CONNECT` Tunneling Lifecycle

When a browser configured with an explicit proxy attempts to navigate to `https://target.example.com`, the connection handshake proceeds as follows:

1. **The Plaintext Handshake (`CONNECT`):** The browser establishes a plain TCP connection to Burp (e.g. `127.0.0.1:8080`) and issues:
   ```http
   CONNECT target.example.com:443 HTTP/1.1
   Host: target.example.com:443
   User-Agent: Mozilla/5.0 ...
   ```
2. **Proxy Hijacking & 200 Connection Established:** The proxy calls `http.Hijacker.Hijack()`, detaches the raw TCP socket from `net/http`, and sends:
   ```http
   HTTP/1.1 200 Connection Established\r\n\r\n
   ```
3. **Downstream TLS Termination:** The proxy now treats the client socket as a TLS server connection (`tls.Server(conn, tlsConfig)`), expecting a TLS `ClientHello` with SNI `target.example.com`.

### 2. On-the-Fly X.509 Leaf Certificate Minting (`crypto/x509`)

To satisfy the client's TLS handshake without triggering a certificate validation error:

- **The Root CA Pair:** Burp generates a long-lived RSA-2048/ECDSA CA private key and self-signed root certificate (`PortSwigger CA`), installed in the user's OS/browser trust store (`/Library/Keychains` on macOS or `cert9.db` in Firefox).
- **Dynamic SAN Generation:** When the client sends `ClientHello` with SNI `target.example.com`, the proxy's `GetCertificate` callback dynamically creates an `x509.Certificate` template:
  ```go
  template := &x509.Certificate{
      SerialNumber: big.NewInt(time.Now().UnixNano()),
      Subject:      pkix.Name{CommonName: sniHost},
      DNSNames:     []string{sniHost},
      NotBefore:    time.Now().Add(-1 * time.Hour),
      NotAfter:     time.Now().Add(24 * time.Hour),
      KeyUsage:     x509.KeyUsageDigitalSignature | x509.KeyUsageKeyEncipherment,
      ExtKeyUsage:  []x509.ExtKeyUsage{x509.ExtKeyUsageServerAuth},
  }
  derBytes, err := x509.CreateCertificate(rand.Reader, template, caCert, leafPubKey, caPrivKey)
  ```
- **Leaf Key Caching:** To avoid burning CPU generating new asymmetric keypairs for every TCP connection, the proxy reuses a single shared ephemeral leaf private key across all minted host certs, caching signed DER certificates in an in-memory LRU map.

### 3. Upstream Dialing & Hop-by-Hop Header Stripping (Go 1.22+)

- **Independent Upstream TLS Handshake:** Simultaneously, the proxy dials `target.example.com:443` using a standard `tls.Dialer`, performing authentic public certificate validation against Mozilla's root store.
- **Hop-by-Hop Header Sanitization:** RFC 7230 requires proxies to strip hop-by-hop headers (`Connection`, `Keep-Alive`, `Proxy-Authenticate`, `Proxy-Authorization`, `TE`, `Trailers`, `Transfer-Encoding`, `Upgrade`) before forwarding the sanitized request to the upstream target. In Go 1.22+, `httputil.ReverseProxy` handles hop-by-hop cleanup automatically via `Rewrite` hooks.

</UnderTheHood>

## Proxy & Intercept

The Proxy tab is where you live. Two modes, a sitemap, and a scope — that's the daily reality.

<ConceptGrid cols={2}>
  <ConceptCard label="Intercept on/off">With **intercept on**, each request *pauses* in Burp so you can edit it before it's forwarded (or drop it). With **intercept off**, traffic flows through normally but is still *logged* — which is how you browse the app to build a sitemap without stopping every request. Most hunting is done with intercept *off*, sending interesting requests to Repeater.</ConceptCard>
  <ConceptCard label="HTTP history / sitemap">Every request the proxy sees is recorded in **HTTP history** and organized into a **sitemap** (a tree of the target's paths). This is your map of the app's attack surface — every endpoint, parameter, and hidden path you've touched. You mine it for interesting requests.</ConceptCard>
  <ConceptCard label="Scope">**Target → Scope** limits Burp to the host(s) you're allowed to test, so you don't accidentally proxy or attack out-of-bounds domains (analytics, CDNs, third parties). Set scope *first* — it keeps you legal and your sitemap clean.</ConceptCard>
  <ConceptCard label="Match & replace">Automatic rules that rewrite requests/responses as they pass through — e.g. always set a header, swap a user-agent, or strip a security header for testing. The automated version of the in-flight edit you saw in the Go demo.</ConceptCard>
</ConceptGrid>

<Callout kind="pro" title="The send-to-Repeater reflex">
The single most common Burp action: in HTTP history you spot a request worth probing — one with an `id`, a token, a role, a redirect — right-click → **Send to Repeater** (Ctrl/Cmd-R). Now you have that exact request isolated in a tab where you can change one value and resend, over and over, without re-triggering it in the browser. Almost every manual finding starts with this move. The browser drives the app to *generate* the request; Repeater is where you *attack* it.
</Callout>

## Repeater

Repeater is the manual workhorse — and the tool that maps most directly onto the attack classes in this course. One request, edited and resent by hand, response shown side by side.

<Define term="Burp Repeater">
**Repeater** holds a single HTTP request that you can **edit and resend** as many times as you like, showing the response each time. It's the manual-testing core of Burp: you send an interesting request here from the proxy, then change *one thing* and observe the effect — change an object `id` to test **IDOR/BOLA**, remove or swap the session cookie/`Authorization` header to test **broken authentication/authorization**, alter a `role` or `price` field to test **business-logic** flaws, inject a `'` or `SLEEP(5)` to probe **SQL injection**, change the `Host` header to test **host-header** attacks, add `../` to test **path traversal**. Repeater is deliberately one-request-at-a-time and human-driven — it's for *understanding* a single endpoint deeply, forming and testing one hypothesis at a time. When you want to test *many* values automatically, you graduate the request to Intruder.
</Define>

<ConceptGrid cols={2}>
  <ConceptCard label="What you change">Method, path, any header (cookie, `Authorization`, `Host`, `X-Forwarded-For`), query params, and the body. Change one thing per resend so you know what caused a difference.</ConceptCard>
  <ConceptCard label="What you watch">Status code, response length, timing, and body. A different length or status for a tweaked value is the tell — e.g. the same `200` but a *longer* body when you change an `id` means you read someone else's record.</ConceptCard>
  <ConceptCard label="The course mapping">IDOR (ch13): change the id. Auth (ch20): drop/swap the token. Logic (ch12/14): tamper a field. SQLi/traversal/host-header (ch14, this appendix): inject the payload. Repeater is the bench for all of them.</ConceptCard>
  <ConceptCard label="Why not just the browser">The browser re-runs the whole app flow and re-renders; Repeater isolates the *one* request, so you change exactly one byte and compare responses cleanly. Precision and speed.</ConceptCard>
</ConceptGrid>

## Intruder

When you've found *what* to change in Repeater and now want to try **many values**, you hand the request to Intruder. It marks positions in the request and substitutes payloads automatically.

<Define term="Burp Intruder">
**Intruder** automates sending a request many times with **payloads** substituted into marked **positions**. You pick the spots to vary (a parameter, a header value), supply a payload list (a wordlist, a number range, a charset), and Intruder fires the request once per payload, tabulating status/length/timing so anomalies stand out. Its four **attack types** differ in how payloads map to positions: **Sniper** (one position at a time, one payload set — the default, for fuzzing a single field); **Battering ram** (the same payload in *all* positions at once); **Pitchfork** (multiple positions, each with its *own* payload list, advanced in lockstep — e.g. matched username/password pairs); and **Cluster bomb** (every *combination* of multiple payload lists — e.g. all usernames × all passwords). Intruder is how you do enumeration (user IDs, endpoints), fuzzing (parameter values, injection payloads), and brute-forcing — at scale, with the results sortable to spot the one response that's different. (The free Community edition throttles Intruder heavily; Professional runs it at full speed.)
</Define>

## Decoder & Friends

The supporting tools — small, but you reach for them constantly.

<ConceptGrid cols={2}>
  <ConceptCard label="Decoder / Inspector">Encode and decode data between formats — URL, base64, hex, HTML, and more — and decode tokens. You'll use it to read a base64 cookie, decode a JWT's payload, or URL-encode an injection payload so it survives transit. The modern **Inspector** panel does this inline next to the request.</ConceptCard>
  <ConceptCard label="Comparer">**Diffs** two responses (or two requests) byte by byte or word by word. Invaluable when a tiny difference matters — e.g. comparing the response for a valid vs invalid username to spot **user enumeration**, or a tampered vs clean request.</ConceptCard>
  <ConceptCard label="Sequencer">Analyzes the **randomness** of a set of tokens (session ids, reset tokens, CSRF tokens). Capture a few hundred and Sequencer estimates their entropy — weak, predictable tokens are a real finding (a guessable session id is account takeover).</ConceptCard>
  <ConceptCard label="Scanner + Collaborator (Pro)">**Scanner** crawls and automatically tests for many vuln classes (Professional only). **Collaborator** gives you an external server to catch **out-of-band** interactions — the way you confirm blind SSRF, blind XXE, or blind injection that produces no visible response but does call out to a URL you control.</ConceptCard>
</ConceptGrid>

What Decoder does is just encoding algebra — here it is in Go, so the transforms are concrete:

<GoPlayground>

```go
package main

import (
	"encoding/base64"
	"fmt"
	"net/url"
	"strings"
)

func main() {
	// URL-encode a payload so special chars survive transit (and decode back).
	raw := "a b&c=d"
	enc := url.QueryEscape(raw)
	dec, _ := url.QueryUnescape(enc)
	fmt.Printf("url:    %q -> %q -> %q\n", raw, enc, dec)

	// base64 a value (e.g. reading/forging a cookie's contents).
	b64 := base64.StdEncoding.EncodeToString([]byte("user:42"))
	back, _ := base64.StdEncoding.DecodeString(b64)
	fmt.Printf("base64: %q -> %q -> %q\n", "user:42", b64, string(back))

	// Decode a JWT's payload — the part a hunter reads first (header.payload.sig).
	tok := "eyJhbGciOiJub25lIn0.eyJyb2xlIjoiYWRtaW4ifQ."
	payload, _ := base64.RawURLEncoding.DecodeString(strings.Split(tok, ".")[1])
	fmt.Printf("jwt payload: %s\n", payload)
}
```

<Exercise n={1} title="Dynamic X.509 Leaf Certificate Generation" level="easy">

Write `MintLeafCertTemplate(hostname string) *x509.Certificate` that configures a valid X.509 certificate template with the specified hostname as both `CommonName` and in `DNSNames`, valid for 24 hours starting 1 hour in the past.

<Solution>

```go
package main

import (
	"crypto/x509"
	"crypto/x509/pkix"
	"fmt"
	"math/big"
	"time"
)

func MintLeafCertTemplate(hostname string) *x509.Certificate {
	now := time.Now()
	return &x509.Certificate{
		SerialNumber: big.NewInt(now.UnixNano()),
		Subject:      pkix.Name{CommonName: hostname},
		DNSNames:     []string{hostname},
		NotBefore:    now.Add(-1 * time.Hour),
		NotAfter:     now.Add(24 * time.Hour),
		KeyUsage:     x509.KeyUsageDigitalSignature | x509.KeyUsageKeyEncipherment,
		ExtKeyUsage:  []x509.ExtKeyUsage{x509.ExtKeyUsageServerAuth},
	}
}

func main() {
	tmpl := MintLeafCertTemplate("api.target.com")
	fmt.Println("CN:", tmpl.Subject.CommonName)
	fmt.Println("SANs:", tmpl.DNSNames)
	fmt.Println("Valid hours:", tmpl.NotAfter.Sub(tmpl.NotBefore).Hours())
}
```

Dynamic TLS interception proxies must configure exact Subject Alternative Names (SANs) matching the client's SNI to avoid browser certificate domain mismatch errors.

</Solution>

</Exercise>

<Exercise n={2} title="Strip Hop-by-Hop Headers in Proxy Middleware" level="medium">

Write `StripHopByHop(h http.Header)` that removes standard RFC 7230 hop-by-hop headers (`Connection`, `Proxy-Connection`, `Keep-Alive`, `Proxy-Authenticate`, `Proxy-Authorization`, `Te`, `Trailer`, `Transfer-Encoding`, `Upgrade`) from an `http.Header` map in place.

<Solution>

```go
package main

import (
	"fmt"
	"net/http"
)

var hopByHop = []string{
	"Connection",
	"Proxy-Connection",
	"Keep-Alive",
	"Proxy-Authenticate",
	"Proxy-Authorization",
	"Te",
	"Trailer",
	"Transfer-Encoding",
	"Upgrade",
}

func StripHopByHop(h http.Header) {
	for _, k := range hopByHop {
		h.Del(k)
	}
}

func main() {
	headers := http.Header{
		"Authorization":    {"Bearer secret123"},
		"Proxy-Connection": {"keep-alive"},
		"Upgrade":          {"websocket"},
		"Content-Type":     {"application/json"},
	}

	StripHopByHop(headers)
	fmt.Println("Remaining headers:")
	for k, v := range headers {
		fmt.Printf("  %s: %v\n", k, v)
	}
}
```

Forwarding hop-by-hop headers across proxy boundaries creates proxy confusion and socket synchronization errors.

</Solution>

</Exercise>

<Exercise n={3} title="Intruder Sniper Payload Generation" level="medium">

Write `GenerateSniperRequests(template string, marker string, payloads []string) []string` that replaces each occurrence of `marker` in `template` with a payload, generating a slice of customized raw HTTP requests.

<Solution>

```go
package main

import (
	"fmt"
	"strings"
)

func GenerateSniperRequests(template string, marker string, payloads []string) []string {
	var requests []string
	for _, p := range payloads {
		req := strings.ReplaceAll(template, marker, p)
		requests = append(requests, req)
	}
	return requests
}

func main() {
	tmpl := "GET /api/user/§ID§ HTTP/1.1\r\nHost: target.com\r\n\r\n"
	payloads := []string{"101", "102", "103"}

	reqs := GenerateSniperRequests(tmpl, "§ID§", payloads)
	for i, r := range reqs {
		fmt.Printf("Req %d: %s", i+1, strings.ReplaceAll(r, "\r\n", " | "))
	}
}
```

Intruder's Sniper attack iterates sequentially over a payload list, substituting each value into marked positions while leaving the surrounding request structure intact.

</Solution>

</Exercise>

<Exercise n={4} title="Decode JWT Claims in Proxy Pipeline" level="hard">

Write `ExtractJWTClaims(authHeader string) (string, error)` that extracts the bearer token from `authHeader`, base64URL-decodes the middle payload segment (without verifying cryptographic signature, simulating Burp Inspector behavior), and returns the raw JSON string.

<Solution>

```go
package main

import (
	"encoding/base64"
	"errors"
	"fmt"
	"strings"
)

func ExtractJWTClaims(authHeader string) (string, error) {
	parts := strings.Split(strings.TrimSpace(authHeader), " ")
	if len(parts) != 2 || strings.ToLower(parts[0]) != "bearer" {
		return "", errors.New("invalid authorization header")
	}

	jwtParts := strings.Split(parts[1], ".")
	if len(jwtParts) != 3 {
		return "", errors.New("malformed JWT")
	}

	payloadBytes, err := base64.RawURLEncoding.DecodeString(jwtParts[1])
	if err != nil {
		return "", fmt.Errorf("base64url decode error: %w", err)
	}

	return string(payloadBytes), nil
}

func main() {
	auth := "Bearer eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiIxMjM0NTYiLCJyb2xlIjoiYWRtaW4ifQ.signature"
	claims, err := ExtractJWTClaims(auth)
	if err != nil {
		fmt.Println("Error:", err)
		return
	}
	fmt.Println("Decoded claims:", claims)
}
```

Inspecting token payloads in-flight allows security analysts to detect privilege levels, embedded tenant IDs, and algorithm tampering vectors (`alg: none`).

</Solution>

</Exercise>

<Recap>

- **Burp Suite is an intercepting proxy plus a toolkit.** You point your browser through Burp; it records, and lets you pause, edit, and replay any request. Everything else operates on captured requests.
- **Interception is a man-in-the-middle proxy you insert into your own connection** — proven with a runnable Go proxy that rewrote `role=user` to `role=admin` in flight. For HTTPS, Burp terminates TLS with certs signed by **its own CA**, which is why you **install Burp's CA** (and why you do it only in a dedicated testing browser — that CA can read all your TLS).
- **Proxy & intercept**: browse with intercept *off* to build the **sitemap**; set **scope** first; send interesting requests to Repeater. Match & replace automates in-flight edits.
- **Repeater** is the manual workhorse — one request, edited and resent by hand. It maps onto nearly every attack class: change an `id` (IDOR), drop a token (authz), tamper a field (logic), inject a payload (SQLi/traversal/host-header).
- **Intruder** scales a request across many **payloads** in marked **positions**: **Sniper** (one field), **Battering ram** (same value everywhere), **Pitchfork** (paired lists), **Cluster bomb** (every combination). For enumeration, fuzzing, brute-forcing.
- **Decoder/Inspector** (encode/decode, read tokens), **Comparer** (diff responses), **Sequencer** (token randomness), and **Scanner**/**Collaborator** (Pro — automated scan + out-of-band detection).
- **The workflow**: setup (proxy + CA + scope) → map (browse → sitemap) → probe (Repeater, one hypothesis at a time) → scale (Intruder) → confirm (Decoder/Comparer/Sequencer/Collaborator) → reproduce + report. Burp is the instrument; the loop is the method.

</Recap>
