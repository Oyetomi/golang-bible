<HeroCard label="Appendix · Security Track" title="Bug Bounty Recon & Methodology">

Here's the thing, sport. Beginners think bug hunting is about exotic payloads. It isn't. It's about **attack surface** — finding the forgotten staging subdomain, the API endpoint that shipped in a JavaScript bundle but never in the docs, the object ID nobody thought you'd guess. The hunters who get paid aren't the ones who know the most payloads; they're the ones who *see the most surface* and probe it methodically. Recon is 80% of the game, and almost nobody teaches it as a system.

This chapter is that system, drawn from the patterns across **6,400+ real disclosed writeups** (the pentester.land corpus you'll see referenced throughout this track). We'll map an attack surface the way a pro does — subdomain enumeration, content and endpoint discovery, mining JavaScript for hidden routes and leaked keys — then run the **hunt loop** (map → probe → escalate → chain), pick targets by **bug-class ROI** (the corpus tells you exactly where the bugs are), triage findings with **CVSS**, and write the report that actually gets paid. Every recon helper is runnable stdlib Go — because the best way to understand a tool is to build a small one. By the end you'll have a repeatable methodology, not a bag of tricks.

</HeroCard>

<Callout kind="warn" title="Authorized targets only — read this first">
Everything here is for **authorized** testing: a bug bounty program's defined scope, a signed penetration test, or your own lab. Recon against a system you don't own or haven't been authorized to test can be a crime (in the US, the CFAA; in the UK, the Computer Misuse Act), regardless of intent. Always read the program's scope and rules of engagement *first*, stay inside it, and never test third parties caught in the blast radius. The runnable code in this chapter operates on in-process test servers and local strings — it never touches a real target. The methodology is portable; the authorization is not.

**Authorization comes from a program, not from a finding.** A target with **no bug bounty program and no VDP** (Vulnerability Disclosure Program) has authorized *nothing* — so "I found a hole in a bank that has no bounty platform" is not a brag, it's a description of unauthorized access. The absence of a program is the reason **not** to test and **not** to access data, full stop. If you spot something on an out-of-scope or no-program target, the only safe move is to report it through a coordinated channel (the org's security contact, a national CERT) **without accessing the data** — and accept that there may be no reward. Touching the data to "prove impact" on a target that never invited you is where research becomes a crime.
</Callout>

## The Attack Surface

A finding starts with surface. The more of a target's surface you can see, the more places a missing check can hide. Pros think in terms of *expanding* the surface — every subdomain, path, parameter, and endpoint is a new place to test.

<Define term="Attack surface">
The **attack surface** is the complete set of points where an untrusted actor can interact with a system: every hostname and subdomain, every URL path and API endpoint, every request parameter, header, and input field, every third-party integration, and every piece of client-side code that reveals any of those. Recon is the disciplined expansion of your *visible* attack surface — turning "the main website" into a map of hundreds of hostnames and thousands of endpoints. **Why it dominates:** a vulnerability you can't reach can't be exploited; most high-value bugs in disclosed reports were on surface the target *forgot they had* (a staging host, a legacy API, an admin endpoint left in a JS bundle).
</Define>

## Subdomain Enumeration

The first multiplier. A program scoped as `*.example.com` is really hundreds of hosts, and the interesting ones are the ones the security team forgot: `staging`, `dev`, `admin`, `legacy`, `vpn`, `internal`. Two techniques dominate: **passive** (query public datasets — certificate transparency logs, DNS aggregators — no packets to the target) and **active** (resolve candidate names from a wordlist).

<Define term="Subdomain enumeration">
**Subdomain enumeration** discovers the hostnames under a domain. **Passive** enumeration mines public sources that already recorded them — most powerfully **Certificate Transparency (CT) logs**, the public append-only logs every TLS certificate is published to, so every host that ever got an HTTPS cert is discoverable by querying `crt.sh` and similar. **Active** enumeration (DNS brute-forcing) takes a wordlist of likely names (`api`, `dev`, `staging`, …), prepends each to the domain, and checks which resolve. Passive is quiet and finds real historical hosts; active finds names not in any public record but generates DNS traffic. Pros do both, then probe which hosts are alive (respond to HTTP).
</Define>

Here's the core of active enumeration — generate candidates and check which resolve — in runnable stdlib Go (resolving public names, no target touched):

<GoPlayground>

```go
package main

import (
	"fmt"
	"net"
)

// resolves reports whether a hostname has any DNS record — the active-enum check.
// In a real tool you'd run these concurrently with a worker pool and rate limit.
func resolves(host string) bool {
	addrs, err := net.LookupHost(host)
	return err == nil && len(addrs) > 0
}

func main() {
	// A tiny wordlist of the names that hide the juiciest forgotten apps.
	words := []string{"www", "api", "mail", "dev", "staging", "admin", "blog"}
	domain := "example.com" // a safe, reserved demo domain

	fmt.Printf("enumerating %d candidates under %s:\n", len(words), domain)
	for _, w := range words {
		host := w + "." + domain
		status := "—"
		if resolves(host) {
			status = "RESOLVES (alive — probe it)"
		}
		fmt.Printf("  %-22s %s\n", host, status)
	}
}
```

</GoPlayground>

<Callout kind="pro" title="Certificate Transparency is the recon superpower">
The single highest-yield passive source is **CT logs**. Every publicly-trusted TLS certificate issued since ~2018 is published to public append-only logs (so misissued certs are detectable). The side effect for hunters: querying `https://crt.sh/?q=%25.example.com` (or the CT log APIs) returns *every hostname that ever got a cert* — including internal-sounding names a company never meant to expose, captured the moment they enabled HTTPS on them. It's passive (you query crt.sh, not the target), historical (finds decommissioned hosts still pointing at live infra — see subdomain takeover), and free. Most disclosed recon-driven findings started here.
</Callout>

Once you have hosts, **probe which are alive** — resolve + HTTP request, record status and title. A dozen subdomains might be 3 live apps, and those 3 are your hunting ground.

## Content & Endpoint Discovery

This is how forgotten admin panels and exposed config files get found.

```go
package main

import (
	"fmt"
	"io"
	"net/http"
	"net/http/httptest"
)

func main() {
	// An in-process target with paths the nav never links (stands in for a real
	// host — runnable, touches nothing external).
	secret := map[string]bool{
		"/admin":             true,
		"/.git/config":       true,
		"/api/swagger.json":  true,
	}
	srv := httptest.NewServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		if secret[r.URL.Path] {
			w.WriteHeader(http.StatusOK)
			io.WriteString(w, "found")
			return
		}
		w.WriteHeader(http.StatusNotFound)
	}))
	defer srv.Close()

	// The wordlist of candidate paths.
	words := []string{"/", "/about", "/admin", "/login", "/.git/config",
		"/api/swagger.json", "/backup.zip", "/nonexistent"}

	var hits []string
	for _, p := range words {
		resp, err := http.Get(srv.URL + p)
		if err != nil {
			continue
		}
		resp.Body.Close()
		if resp.StatusCode == http.StatusOK {
			hits = append(hits, p)
		}
		fmt.Printf("  %-22s %d\n", p, resp.StatusCode)
	}

	fmt.Println("\nDISCOVERED (new attack surface):")
	for _, h := range hits {
		fmt.Println("  →", h)
	}
}
```

</GoPlayground>

</CodeWalk>

<Callout kind="pro" title="Rotate the HTTP method — one path is several endpoints">
A path is not one endpoint — it's one endpoint *per method*. The same URL can `404` on `GET` but accept a `PUT` or `POST`, because frameworks route `(method, path)` pairs and developers often guard the method they expect a browser to use while leaving the others wide open. So when you fuzz, **fuzz the method too**: try `GET, POST, PUT, PATCH, DELETE` (and `OPTIONS`/`HEAD`) on each candidate path. A `GET /v1/accounts/{id}` that returns `403` might have a `PUT /v1/accounts/{id}` that updates with no auth check at all — the broken-access-control bugs in this track hide exactly there. Two cheap habits: start path fuzzing at `/v1/FUZZ` (versioned API roots are where the undocumented endpoints live), and **never conclude an endpoint is safe from one method's response** — re-test it under every verb. (`OPTIONS` also frequently leaks the allowed methods in its `Allow` header — free reconnaissance.)
</Callout>

## The Recon Pipeline: `anew`, Liveness & the Outlier Hunt

Watch any experienced hunter do live recon and you'll notice it's not a tool — it's a **Unix pipeline**. Domains flow through a chain of small programs, each doing one thing, joined by `|`, with results appended to flat files you grep later. And here's the part for *this* book: the canonical toolkit for this — `assetfinder`, `httprobe`, `anew`, `fff`, `meg`, `gf`, `waybackurls`, `unfurl` — is almost entirely written in **Go** (mostly by one person, [tomnomnom](https://github.com/tomnomnom)). They're small, fast, composable Go binaries: exactly the philosophy the rest of this course teaches, pointed at recon. Let's build the *mechanism* of the two that change how you work.

### `anew` — the diffing pipeline

The workflow problem: you enumerate subdomains with *several* tools (`assetfinder`, `findomain`, `subfinder`, CT logs) because each finds things the others miss, and you re-run them over time. You don't want to re-process the thousands you already have — you want *only the new ones* each run, so you can pipe just those into the next stage (liveness, fetching). That's **`anew`**: it reads lines, appends only the ones not already in your file, and **prints only what was new**.

<Define term="anew (append-new, the diffing primitive)">
**`anew`** reads lines from stdin and appends each one to a file **only if that line isn't already in the file** — and crucially, it **prints to stdout only the lines that were new**. It's `tee -a` that de-duplicates and reports the delta. This one behavior is what makes the recon pipeline *incremental*: `assetfinder example.com | anew domains.txt` adds any newly-discovered domains to `domains.txt` and emits just those, so you can chain `| httprobe | anew live.txt` and **only probe the domains you hadn't seen before**. Re-run the same tool an hour later and `anew` emits nothing (everything's known); run a *different* tool and it emits only that tool's unique finds. It turns a pile of overlapping tool outputs into a clean, growing, no-duplicates dataset — and tells you exactly what each run discovered.
</Define>

It's about fifteen lines of Go, and seeing it makes the whole pipeline click:

<GoPlayground>

```go
package main

import (
	"fmt"
	"strings"
)

// anew: append each incoming line to the known set only if it's new, and return
// just the new lines — the delta you pipe into the next stage of the pipeline.
func anew(known map[string]bool, incoming []string) []string {
	var added []string
	for _, line := range incoming {
		line = strings.TrimSpace(line)
		if line == "" || known[line] {
			continue // already have it → don't re-emit, don't re-process
		}
		known[line] = true
		added = append(added, line)
	}
	return added
}

func main() {
	// the running set so far (e.g. from a previous assetfinder run)
	known := map[string]bool{"shop.example.com": true, "api.example.com": true}

	// a second tool (findomain) reports its finds — only the NEW ones come out
	fromFindomain := []string{"api.example.com", "staging.example.com", "shop.example.com", "admin.example.com"}
	fmt.Println("new this run:", anew(known, fromFindomain)) // [staging admin]

	// re-run the same input → nothing new (the pipeline is incremental)
	fmt.Println("re-run:      ", anew(known, fromFindomain)) // []
}
```

</GoPlayground>

<Callout kind="pro" title="The pipeline, end to end">
The shape of a real subdomain-to-surface run, every stage a small Go tool joined by pipes:
`assetfinder --subs-only example.com | anew domains.txt | httprobe -c 80 | anew live.txt | fff -d 50 -o out/`
— enumerate, keep only new domains, probe which are alive (concurrency 80), keep only newly-live hosts, fetch the root page of each into `out/`. Add `findomain example.com | anew domains.txt | …` and you fold a second tool's unique finds into the *same* incremental flow. **`httprobe`** answers "what's actually listening on 80/443?" (a domain in DNS isn't a live web server); a common wrapper prefers the HTTPS result so you don't double-process `http://` and `https://` of the same host. **`fff`** fetches a list of URLs you already have and saves each response's body + headers to disk; **`meg`** is the other side — it sprays *one path* (say `/.git/config`) across *thousands* of hosts at once for content discovery at scale. Reach for `fff` when you have URLs and want their contents; reach for `meg` when you have hosts and want to test one endpoint across all of them.
</Callout>

### The outlier hunt — find the host that's *different*

Once you've fetched the root of every host, you have a pile of response headers — thousands of them. The naive move is to read them all. The expert move is to **find the host that doesn't look like the others**. Big organizations run configuration management, so their fleet is *consistent* — the same `Server`, the same `X-Powered-By`, the same custom headers everywhere. A host with a header almost nothing else has is a host built **differently** — maybe outside the standard build pipeline, maybe an acquisition, maybe a one-off someone stood up and forgot. That inconsistency is a strong signal: it's where the non-standard, less-reviewed, **more-likely-vulnerable** service lives.

<Define term="The inconsistency heuristic">
In a large, well-managed target, **consistency is the norm and inconsistency is the lead**. Configuration management and a standard SDLC make most hosts look identical — same headers, same framework fingerprints, same error pages. So instead of auditing every host, you **hunt the outlier**: the host with a response header (or server banner, or error format) that appears on *only one* host out of thousands. That singular host was probably built outside the standard process — a forgotten side project, an acquired company's infra, a quick internal tool — which means it's likely had *less* security review than the flagship app. The technique is mechanical: collect a feature (e.g. every response header name) across all hosts, count occurrences, and surface the ones with a count of **one**. The rare feature points at the interesting host.
</Define>

The mechanism is a frequency count — surface the headers that appear exactly once:

<GoPlayground>

```go
package main

import (
	"fmt"
	"sort"
)

// rareHeaders surfaces header names that appear on only ONE host — the outlier
// signal: a host unlike all the others is where the non-standard (and often
// less-reviewed) service lives.
func rareHeaders(hostHeaders map[string][]string) []string {
	count := map[string]int{}    // header name → how many hosts send it
	where := map[string]string{} // header name → the (last) host that sent it
	for host, headers := range hostHeaders {
		for _, h := range headers {
			count[h]++
			where[h] = host
		}
	}
	var rare []string
	for h, n := range count {
		if n == 1 {
			rare = append(rare, fmt.Sprintf("%s — only on %s", h, where[h]))
		}
	}
	sort.Strings(rare)
	return rare
}

func main() {
	// the fleet is consistent (Server, CF-Ray, X-Shop-Id everywhere) — except one.
	hosts := map[string][]string{
		"www.example.com":  {"Server", "CF-Ray", "X-Shop-Id"},
		"api.example.com":  {"Server", "CF-Ray", "X-Shop-Id"},
		"cdn.example.com":  {"Server", "CF-Ray", "X-Shop-Id"},
		"docs.example.com": {"Server", "Server-Timing", "X-Powered-By"}, // the odd one out
	}
	for _, line := range rareHeaders(hosts) {
		fmt.Println("outlier:", line)
	}
}
```

</GoPlayground>

<Gotcha>
**Recon is a search for signal in noise, and the signal is usually the exception, not the rule.** Don't try to read every header, every host, every endpoint — you'll drown. Build mechanical filters that surface what *stands out*: the header on one host, the subdomain that doesn't match the naming convention, the JS file that's different from its siblings, the endpoint that responds when its neighbors `404`. The same `anew` trick that dedupes domains also diffs *anything* line-based (sort a feature, find the singletons). The hunter's edge isn't running more tools — it's the filters and the instinct for "that one's not like the others," because the inconsistent thing was built outside the process that secured everything else.
</Gotcha>

### Going back in time, and into the source

Two more high-yield sources the pipeline feeds:

<ConceptGrid cols={2}>
  <ConceptCard label="Old JavaScript via the Wayback Machine">`waybackurls` / `gau` pull every URL the archive has ever seen for a domain — including **historical versions** of JS bundles. An old `site.js` from 2018 often references **API endpoints that were removed from the current app but are still live on the server** (and unmonitored). Filter the archive output to `.js`, fetch the old versions (`fff`, 200-only), and grep them for endpoints and keys. Removed-in-the-UI ≠ removed-on-the-server.</ConceptCard>
  <ConceptCard label="GitHub history via `git dump`">Find repos that mention the target, clone them, and run a **`git dump`** (extract every object in `.git` to plain files — *every file that ever existed in the history*, not just the current tree). A secret or internal URL deleted in a later commit is still sitting in an old object. Grep the dumped history for in-scope URLs (filter with an `inscope` tool) and credentials. The current `HEAD` is the tip of an iceberg; the history is the rest.</ConceptCard>
</ConceptGrid>

## Mining JavaScript

The richest source of *hidden* surface is the target's own JavaScript. Modern single-page apps ship their entire API map, route table, feature flags, and — too often — secrets in the JS bundle. Hunters download every `.js`, then grep it for endpoints and keys. A route that exists only in client code is surface the docs and the sitemap will never show.

<Define term="JavaScript reconnaissance">
**JS recon** extracts attack surface from a target's client-side code. Single-page apps bundle their API calls (`fetch('/api/internal/users/' + id)`), route definitions, and config into JavaScript that ships to every visitor. Mining it with regexes surfaces: **endpoints** (paths and full URLs the app calls), **parameters** (the shape of requests), and — the jackpot — **leaked secrets** (API keys, tokens, internal hostnames accidentally compiled in). An internal admin endpoint referenced in JS but protected only by the UI hiding the button is a classic broken-access-control finding. The corpus is full of bugs that started "I read their JavaScript."
</Define>

Endpoint and secret extraction is just pattern-matching over the bundle text — runnable here over a sample bundle:

<GoPlayground>

```go
package main

import (
	"fmt"
	"regexp"
	"sort"
)

// A snippet of a typical JS bundle — API calls, an internal route, a leaked key.
const bundle = `
const API = "/api/v1";
async function getUser(id){ return fetch("/api/v1/users/"+id); }
async function adminPanel(){ return fetch("/api/internal/admin/metrics"); }
fetch("https://payments.example.com/api/charge", {method:"POST"});
```

<Gotcha>
**A secret in a JS bundle is a real, often critical finding — but handle it carefully.** If you find a live API key or token in client-side JS, do **not** use it to access data — that turns a clean disclosure into unauthorized access. Document *that it's exposed* (the file, the line, the key prefix), report it, and let the program rotate it. The finding is "a live API secret key is compiled into your public bundle," not "and here's the customer data I pulled with it." The first is a paid bug; the second is a crime. Same key, opposite outcomes — the line is whether you *used* it.
</Gotcha>

## Search-Engine Dorking

The purest passive recon: let a search engine do the crawling, then ask it precise questions. A **dork** is a query built from advanced operators that surfaces things that are *public but never meant to be found* — exposed config files, login panels, indexed backups, documents whose metadata leaks PII. You touch the search engine, not the target, so it's about as low-risk as recon gets.

<Define term="Search-engine dorking">
**Dorking** (a.k.a. Google hacking) uses a search engine's **advanced operators** to filter its index down to exposed, sensitive surface. Core operators (broadly shared across Google, Bing, and Yandex, with syntax differences): **`site:`** restricts to a domain; **`filetype:`** / **`mime:`** filters by file type (Yandex uses `mime:`); **`inurl:`** matches a term in the URL; **`intitle:`** matches the page title (`intitle:"index of"` finds open directory listings); Yandex adds **`host:`** and **`url:`**. Combine them — `site:target.com mime:pdf`, `site:target.com inurl:.env` — to pull every indexed PDF or stray config file on a scope. It's passive: you query the engine, never the target, which is why it's a first-move recon source alongside Certificate Transparency.
</Define>

<Callout kind="pro" title="Why hunters reach for Yandex (and Bing), not just Google">
Different search engines crawl, rank, and **de-index** differently — so a file Google scrubbed or buried may still be sitting in Yandex's or Bing's index. Yandex in particular is known for indexing open directory listings, cloud storage, and document files that Google quietly drops, and (because fewer hunters dork it) the results are less picked-over — hence the "zero competition" hype. The practical takeaway: **run the same dork across multiple engines.** The exposure that's invisible on one is often the first result on another. None of this is exotic — it's the same surface, seen through a different index.
</Callout>

Two exposure classes dominate dork findings, and both are *your* bug to prevent:

The single most important server-side defense: **a sensitive file must never be web-reachable in the first place.** Don't rely on "nobody will guess the URL" or even `robots.txt` (which only asks crawlers not to *index* — it does not block *access*, and it advertises the paths you're hiding). <GoPlayground>

```go
package main

import (
	"fmt"
	"io"
	"net/http"
	"net/http/httptest"
	"strings"
)

// blockSensitive denies any request whose path targets a file a dork hunts:
// dotfiles (.env, .git), backups, dumps, framework config. These must never be
// web-reachable — and a 404 (not 403) refuses to even confirm they exist.
func blockSensitive(next http.Handler) http.Handler {
	bad := []string{"/.env", "/.git", "/.aws", "/backup", "/dump", ".sql", ".bak", "/config.php"}
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		p := strings.ToLower(r.URL.Path)
		for _, b := range bad {
			if strings.Contains(p, b) {
				http.NotFound(w, r)
				return
			}
		}
		next.ServeHTTP(w, r)
	})
}

func main() {
	app := http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		io.WriteString(w, "ok: "+r.URL.Path)
	})
	srv := httptest.NewServer(blockSensitive(app))
	defer srv.Close()

	for _, p := range []string{"/", "/about", "/.env", "/.git/config", "/db_backup.sql", "/api/health"} {
		resp, _ := http.Get(srv.URL + p)
		resp.Body.Close()
		fmt.Printf("  %-18s %d\n", p, resp.StatusCode)
	}
	// /.env, /.git/config, /db_backup.sql → 404; real paths → 200
}
```

</GoPlayground>

<Callout kind="note" title="The dork defense checklist (for the team shipping the app)">
A dork can only find what you've exposed. Close the door at every layer: **(1)** never deploy `.env`, `.git`, backups, or DB dumps into the web root — keep secrets in the environment or a secrets manager, outside any served directory; **(2)** disable directory listing (`Options -Indexes` / framework equivalent) so `intitle:"index of"` finds nothing; **(3)** put auth on anything sensitive — indexing-by-obscurity is not access control; **(4)** **strip document metadata** (author, internal paths, GPS, revision history) from PDFs/images before publishing — the metadata, not the visible content, is what leaks PII; **(5)** treat any secret that was *ever* indexed as compromised and **rotate it** — a removed file lives on in caches and engine indexes; **(6)** **dork your own domains** on a schedule (and across multiple engines) to find your exposures before a hunter does. Same query, pointed inward.
</Callout>

<Callout kind="warn" title="Search engines aren't the only index — public scanners leak too">
A document doesn't have to be on *your* site to be discoverable. **Public file-scanning and sandbox services** — VirusTotal, online AV scanners, URL/PDF analyzers — retain and make *searchable* much of what's uploaded to them. Someone (an employee, a vendor, even an attacker triaging your file) uploads a payroll PDF, an invoice, or a config to "just check if it's safe," and that document becomes a permanently searchable artifact outside your control. It's the same exposure class as dorking — surface you didn't realize you published — just hosted by a third party. The defenses: **never upload sensitive documents to public scanners** (use an offline/enterprise tier that doesn't share samples), include this in data-handling policy, and — defensively — search those services for your own domain names and document identifiers to catch leaks early. For the hunter, the ethics are identical to a dork: finding a leaked file is a report; downloading and mining its contents from a target that never authorized you is not.
</Callout>

## Triage & CVSS

You found something. Before reporting, you must say *how bad* it is — programs pay by severity, and an inflated severity gets your report rejected. The industry standard is **CVSS**.

<Define term="CVSS (Common Vulnerability Scoring System)">
**CVSS** produces a 0–10 severity score from a vector of metrics. The core **Base** metrics: **Attack Vector** (Network/Adjacent/Local/Physical — how remote), **Attack Complexity** (Low/High), **Privileges Required** (None/Low/High), **User Interaction** (None/Required), **Scope** (Unchanged/Changed — does it break out of its security boundary?), and the **Impact** triad **Confidentiality / Integrity / Availability** (None/Low/High). The score maps to bands: 0.1–3.9 Low, 4.0–6.9 Medium, 7.0–8.9 High, 9.0–10.0 Critical. **Why it matters for hunters:** programs triage and pay by CVSS, and *justifying* your score honestly (an unauthenticated RCE is 9.8; a self-XSS is ~2) is the difference between a fast payout and a "won't fix." Score the bug you can *prove*, not the worst case you can imagine.
</Define>

A simplified CVSS-style severity bander — the banding logic, runnable:

<GoPlayground>

```go
package main

import "fmt"

// severity maps a 0.0–10.0 CVSS base score to its band — the cut you cite in a report.
func severity(score float64) string {
	switch {
	case score == 0:
		return "None"
	case score < 4.0:
		return "Low"
	case score < 7.0:
		return "Medium"
	case score < 9.0:
		return "High"
	default:
		return "Critical"
	}
}

func main() {
	// Representative findings and their (published) CVSS base scores.
	findings := []struct {
		name  string
		score float64
	}{
		{"Self-XSS (victim must paste payload)", 2.4},
		{"Reflected XSS, no auth", 6.1},
		{"IDOR exposing other users' PII", 7.5},
		{"Account takeover via password-reset flaw", 8.8},
		{"Unauthenticated RCE", 9.8},
	}
	for _, f := range findings {
		fmt.Printf("  %4.1f  %-9s  %s\n", f.score, severity(f.score), f.name)
	}
}
```

</GoPlayground>

<Callout kind="pro" title="Severity is a negotiation you win with honesty">
The fastest way to *lose* a triager's trust is to report a self-XSS as "Critical account takeover." The fastest way to *earn* it is to score conservatively and clearly: state the exact CVSS vector, what an attacker can actually do *today* with no extra assumptions, and the realistic impact. Triagers reward hunters who make their job easy. A well-justified High beats an over-claimed Critical that gets downgraded and sours the relationship — and the relationship is what gets your *next* report read first.
</Callout>

<Callout kind="note" title="The report skeleton">
**Title** — class + location + impact in one line. **Summary** — two sentences a non-expert manager understands. **Steps to Reproduce** — numbered, exact, copy-pasteable (accounts, IDs, requests). **Proof of Concept** — the minimal request/screenshot that proves it; never more access than needed to demonstrate. **Impact** — what an attacker actually achieves. **Severity** — CVSS vector + score, honestly. **Remediation** — the concrete fix. **Stay in scope** — only the authorized target, only the access needed to prove the bug, and stop the moment it's proven. </Callout>

<Callout kind="warn" title="Using AI to write the report — draft tool, not author">
An LLM is a genuine time-saver for the *tedious* parts of a report — structuring the skeleton above, tightening prose, turning rough notes into clean reproduction steps. But it is a **drafting assistant, never the author**, and the failure modes are specific: LLMs **hallucinate payloads and PoCs that look right but don't actually fire**, write **reproduction steps that don't match the real target**, and pad reports with confident, unproven claims. The discipline: **(1)** use it to draft, never to submit — every payload, step, and impact claim must be *you* re-running it against the real target and confirming it works; **(2)** verify the PoC in a production-like config, not just a friendly local one; **(3)** strip speculative attack vectors and "this could also lead to…" claims you haven't proven; **(4)** don't let it write your *replies to triagers* — that exchange needs your judgment and your knowledge of the program's rules; **(5)** check the draft against the program's policy before sending (an LLM will happily suggest something out of scope); **(6)** keep it concise — AI loves verbose paragraphs that add nothing. The triager rewards a short, true, reproducible report; AI helps you write it faster, not think for you.
</Callout>

<Exercise n={1} title="Subdomain candidate generator" level="easy">

Write `candidates(domain string, words []string) []string` that prefixes each word with `word.domain`. Given `example.com` and `["api","dev","admin"]`, it returns the three FQDNs. (Generating candidates is step one of active enumeration.)

<Solution>

```go
package main

import "fmt"

func candidates(domain string, words []string) []string {
	out := make([]string, len(words))
	for i, w := range words {
		out[i] = w + "." + domain
	}
	return out
}

func main() {
	for _, c := range candidates("example.com", []string{"api", "dev", "admin"}) {
		fmt.Println(c)
	}
}
```

The generator is trivial; the value is in the wordlist quality and (in a real tool) resolving thousands concurrently with a rate limit. Candidate generation is the cheap part — interpretation is the skill.

</Solution>

<Exercise n={2} title="Keep the non-404s" level="easy">

Write `discovered(results map[string]int) []string` returning the paths whose status code is 200, sorted. Given `{"/admin":200, "/x":404, "/api":200}` it returns `["/admin","/api"]` — the content-discovery filter.

<Solution>

```go
package main

import (
	"fmt"
	"sort"
)

func discovered(results map[string]int) []string {
	var out []string
	for path, code := range results {
		if code == 200 {
			out = append(out, path)
		}
	}
	sort.Strings(out)
	return out
}

func main() {
	r := map[string]int{"/admin": 200, "/x": 404, "/api": 200, "/secret": 403}
	fmt.Println(discovered(r)) // [/admin /api]
}
```

The interesting judgment call in real tools: a 403 (forbidden) often means "this exists but you can't reach it" — itself a lead. A 200 is a hit; a 403 is a hint; a 404 is nothing.

</Solution>

</Exercise>

<Exercise n={3} title="Extract endpoints from JS" level="medium">

Write `endpoints(js string) []string` that uses a regex to pull quoted path-like strings (`"/api/..."`) out of a JS bundle, de-duplicated and sorted. Run it over a small bundle and confirm it finds the API paths.

<Solution>

```go
package main

import (
	"fmt"
	"regexp"
	"sort"
)

func endpoints(js string) []string {
	re := regexp.MustCompile(`["'](/[a-zA-Z0-9_/{}.-]+)["']`)
	set := map[string]bool{}
	for _, m := range re.FindAllStringSubmatch(js, -1) {
		set[m[1]] = true
	}
	var out []string
	for e := range set {
		out = append(out, e)
	}
	sort.Strings(out)
	return out
}

func main() {
	js := `fetch("/api/v1/users/"+id); fetch("/api/internal/admin"); x="/api/v1/users/"`
	for _, e := range endpoints(js) {
		fmt.Println(e)
	}
	// /api/internal/admin and /api/v1/users/ (de-duped)
}
```

The regex is a starting point — real JS recon tools layer many patterns (full URLs, template literals, base + path concatenation). The principle: the client code is a map of the server's surface, and `/api/internal/admin` referenced in JS is a lead even if no UI button reaches it.

</Solution>

</Exercise>

<Exercise n={4} title="CVSS severity band" level="easy">

Write `band(score float64) string` mapping a CVSS base score to None/Low/Medium/High/Critical using the standard cuts (`0` / under `4.0` / under `7.0` / under `9.0` / `≥9.0`). Verify 9.8 → Critical, 7.5 → High, 6.1 → Medium.

<Solution>

```go

func band(s float64) string {
	switch {
	case s == 0:
		return "None"
	case s < 4.0:
		return "Low"
	case s < 7.0:
		return "Medium"
	case s < 9.0:
		return "High"
	default:
		return "Critical"
	}
}

func main() {
	for _, s := range []float64{0, 2.4, 6.1, 7.5, 9.8} {
		fmt.Printf("%.1f → %s\n", s, band(s))
	}
}
```

Memorize the cuts — you'll cite them in every report. The boundary cases (exactly 4.0, 7.0, 9.0 round *up* into the higher band) are where over- and under-claiming happen.

</Solution>

</Exercise>

<Exercise n={5} title="Rank targets by ROI" level="medium">

Given bug classes with a `frequency` (corpus count) and your `skill` (0–1), write `rank()` that sorts classes by `frequency × skill` descending — your personal hunting priority. Show that a common class you're skilled at outranks a rare class you're not.

<Solution>

```go
package main

import (
	"fmt"
	"sort"
)

type class struct {
	name      string
	frequency int
	skill     float64 // your proficiency 0..1
}

func main() {
	classes := []class{
		{"IDOR", 467, 0.8},
		{"RCE", 884, 0.2},
		{"XSS", 570, 0.6},
		{"SSRF", 286, 0.5},
	}
	sort.Slice(classes, func(i, j int) bool {
		return float64(classes[i].frequency)*classes[i].skill >
			float64(classes[j].frequency)*classes[j].skill
	})
	fmt.Println("your hunting priority (frequency × skill):")
	for _, c := range classes {
		fmt.Printf("  %-6s score=%.0f\n", c.name, float64(c.frequency)*c.skill)
	}
}
```

RCE is the most frequent class but if your skill there is 0.2, IDOR (467 × 0.8 = 374) outranks it (884 × 0.2 = 177). ROI is frequency *times your edge* — go where you can actually convert surface into findings.

</Solution>

</Exercise>

<Recap>

- **Recon is the job.** Most high-value disclosed bugs were on surface the target *forgot they had*. Expand your visible attack surface — hosts, endpoints, parameters, client code — and the bugs appear on the map.
- **Subdomain enumeration** multiplies one domain into hundreds of hosts. **Passive** (Certificate Transparency / `crt.sh` — every host that ever got a TLS cert, queried without touching the target) is the highest-yield source; **active** (DNS brute-force from a wordlist) finds names not in any public record.
- **Content discovery** brute-forces paths from a wordlist and keeps the non-404s — surfacing admin panels, exposed `.git`/`.env`, undocumented APIs. It expands the map; it doesn't exploit.
- **Mining JavaScript** extracts endpoints, parameters, and (critically) leaked secrets from the app's own bundle — surface that exists only in client code. A found secret is a finding to *report*, never to *use*.
- **The hunt loop** — map → probe → escalate → chain — turns surface into findings. Probe each point against the class checklist, escalate any hit to its worst case, and **chain** low bugs (open redirect + OAuth = account takeover) into high ones. Discipline beats cleverness.
- **Pick targets by ROI** — frequency × impact × your skill. The corpus shows RCE/InfoLeak/XSS/ATO/IDOR dominate by volume; new hunters get the best ROI from IDOR/access-control; ATO is the high-value goal reached by chaining. Go deep in one class.
- **Triage with CVSS** and score *honestly* — the bug you can prove today, not the worst case you can imagine. A well-justified High beats an over-claimed Critical that gets downgraded.
- **The report pays, not the bug.** Title + one-line impact → numbered reproducible steps → impact/CVSS/remediation. Reproducible in two minutes, impact undeniable, scope respected, only the access needed to prove it.

</Recap>
