## The Same-Origin Policy

You cannot understand CORS until you understand the rule it bends. That rule is the **same-origin policy (SOP)**, and it is the single most important security boundary in your browser.

<Define term="Origin">
An **origin** is the triple of **scheme + host + port** — for example, the scheme `https`, host `app.example.com`, and port `443`. Two URLs have the *same origin* only if all three match exactly. `https://app.example.com/login` and `https://app.example.com/account` are same-origin (only the path differs, and the path is **not** part of the origin). But `http://app.example.com` (different scheme), `https://api.example.com` (different host), and `https://app.example.com:8443` (different port) are each a **different** origin. The common mistake is thinking "same domain = same origin"; the scheme and port count too, and a subdomain is a different host.
</Define>

<Define term="Same-Origin Policy (SOP)">
The **same-origin policy** is a browser rule: JavaScript running on one origin may *send* a request to another origin, but it generally may **not read the response** unless that other origin explicitly permits it. Without SOP, any website you visited could quietly make requests to `mail.yourbank.com` *using the cookies already in your browser* and read your inbox or balance. SOP is what stops `evil.com`'s JavaScript from reading `yourbank.com`'s authenticated responses. The crucial subtlety: SOP blocks the **read**, not always the send — the request may still reach the server (and may still have side effects, which is the separate CSRF problem). CORS is the controlled, opt-in way for a server to say "actually, *this* other origin **is** allowed to read me."
</Define>

Here's the part that surprises people: **the same-origin policy is enforced by the browser, not your server.** Your Go handler happily responds to anyone. The browser is the one that, after receiving the response, decides whether the *JavaScript that made the request* is allowed to read it — based on a header your server did or didn't send. CORS is how your server tells the browser "let this origin read me."

<Gotcha>
**SOP blocks reading, not sending — and that distinction is two different vulnerabilities.** Because the request still *reaches* your server (with the user's cookies), a state-changing cross-origin request can have effects even though the attacker can't read the response — that's **CSRF** (covered in the auth chapter, defended with tokens / SameSite cookies / `CrossOriginProtection`). CORS is the *other* side: controlling who can **read** your responses. A common confusion is thinking CORS protects against CSRF — it does not. CORS governs reads; CSRF defenses govern unwanted writes. You need both, for different reasons.
</Gotcha>

## What CORS Actually Is

Strip away the mystique: **CORS is a set of HTTP response headers** your server sends, plus a handshake the browser runs on its own. There is no magic, no library requirement, no framework. CORS is your server answering one question for the browser: *"Is the origin that made this request allowed to read my response, and if it's a risky request, is it even allowed to send it?"*

<Define term="CORS (Cross-Origin Resource Sharing)">
**CORS** is a W3C/Fetch standard that lets a server **selectively relax** the same-origin policy for chosen origins, using HTTP headers. When a browser makes a cross-origin request, it adds an **`Origin`** request header naming the page's origin. The server's response includes **`Access-Control-Allow-Origin`** (and friends) saying which origin(s) may read the response. The browser compares the two: if the response permits the requesting origin, JavaScript gets to read it; if not, the browser throws the famous CORS error and hides the response. CORS is **opt-in by the server and enforced by the browser** — a server with no CORS headers simply can't be read cross-origin (the safe default), and a server can open up to specific partners by echoing their origin.
</Define>

## Simple vs Preflight

Not all cross-origin requests are treated the same. The browser splits them into two kinds, and the second one sends a **second, hidden request first** — the thing that confuses everyone the first time they open the Network tab and see an `OPTIONS` they never wrote.

<Define term="Simple request vs preflighted request">
A **simple request** is one the browser considers low-risk enough to send directly (and only *then* check the response's CORS headers). To qualify it must use a safe method (`GET`, `HEAD`, or `POST`), carry only "CORS-safelisted" headers, and — for `POST` — a safelisted `Content-Type` (`text/plain`, `application/x-www-form-urlencoded`, or `multipart/form-data`). Anything else — a `PUT`/`DELETE`/`PATCH`, an `Authorization` header, a `Content-Type: application/json`, a custom header like `X-API-Key` — makes it a **preflighted request**: before sending the real request, the browser sends a **preflight** — an `OPTIONS` request asking "may I send a *PUT* with an *Authorization* header from this origin?" Only if the server's preflight response approves does the browser send the real request. The preflight exists so a server can *refuse a dangerous cross-origin request before it ever happens*, protecting servers that predate CORS.
</Define>

Your server has to *handle* the preflight — answer the `OPTIONS` with the right `Access-Control-Allow-*` headers — or the real request never fires. Here is a preflight handled correctly, runnable:

<GoPlayground>

```go
package main

import (
	"fmt"
	"net/http"
	"net/http/httptest"
)

func handler(w http.ResponseWriter, r *http.Request) {
	w.Header().Set("Access-Control-Allow-Origin", "https://app.example.com")
	// A preflight is an OPTIONS with Access-Control-Request-Method set.
	if r.Method == http.MethodOptions {
		w.Header().Set("Access-Control-Allow-Methods", "GET, POST, PUT, DELETE")
		w.Header().Set("Access-Control-Allow-Headers", "Authorization, Content-Type")
		w.Header().Set("Access-Control-Max-Age", "600") // cache this preflight 10 min
		w.WriteHeader(http.StatusNoContent)             // 204, empty body
		return
	}
	fmt.Fprint(w, `{"ok":true}`)
}

func main() {
	srv := httptest.NewServer(http.HandlerFunc(handler))
	defer srv.Close()

	// Simulate the browser's preflight for a PUT + Authorization.
	pf, _ := http.NewRequest(http.MethodOptions, srv.URL, nil)
	pf.Header.Set("Origin", "https://app.example.com")
	pf.Header.Set("Access-Control-Request-Method", "PUT")
	pf.Header.Set("Access-Control-Request-Headers", "authorization")
	resp, _ := http.DefaultClient.Do(pf)
	resp.Body.Close()

	fmt.Println("preflight status:", resp.StatusCode)
	fmt.Println("Allow-Methods:   ", resp.Header.Get("Access-Control-Allow-Methods"))
	fmt.Println("Allow-Headers:   ", resp.Header.Get("Access-Control-Allow-Headers"))
	fmt.Println("Max-Age:         ", resp.Header.Get("Access-Control-Max-Age"))
}
```

## The CORS Headers

CORS is just headers. Learn these and you've learned CORS. The **request** headers are set by the browser (you can't fake them from script); the **response** headers are what *you* control on the server.

<ConceptGrid cols={2}>
  <ConceptCard label="Origin (request)">Set by the browser on every cross-origin request (and most same-origin ones). Names the calling page's origin, e.g. `https://app.example.com`. Your server reads this to decide. The script **cannot** set or spoof it.</ConceptCard>
  <ConceptCard label="Access-Control-Request-Method (request)">Sent on the **preflight** only. Tells the server which method the real request wants to use (`PUT`, `DELETE`, …). Your preflight response approves it via Allow-Methods.</ConceptCard>
  <ConceptCard label="Access-Control-Request-Headers (request)">Preflight only. Lists the non-safelisted headers the real request wants to send (`authorization`, `x-api-key`). You approve via Allow-Headers.</ConceptCard>
  <ConceptCard label="Access-Control-Allow-Origin (response)">**The big one.** Either a single exact origin (`https://app.example.com`) or `*`. The browser allows the read only if this matches the request's Origin (or is `*`, when credentials aren't involved). This is your access decision.</ConceptCard>
  <ConceptCard label="Access-Control-Allow-Credentials (response)">`true` if the browser may send/receive cookies and HTTP auth on this cross-origin request. Combining it with `Allow-Origin: *` is **forbidden** by the spec — you must echo an exact origin when credentials are on.</ConceptCard>
  <ConceptCard label="Access-Control-Allow-Methods (response)">Preflight response. The methods this endpoint permits cross-origin (`GET, POST, PUT, DELETE`). The browser checks the real request's method against this list.</ConceptCard>
  <ConceptCard label="Access-Control-Allow-Headers (response)">Preflight response. The non-safelisted request headers permitted (`Authorization, Content-Type`). Must include every custom header the client sends, or the real request is blocked.</ConceptCard>
  <ConceptCard label="Access-Control-Max-Age (response)">How many seconds the browser may **cache this preflight result**, so it doesn't re-OPTIONS every call. Set it (e.g. 600) to cut the preflight overhead in half for chatty APIs.</ConceptCard>
  <ConceptCard label="Access-Control-Expose-Headers (response)">By default cross-origin JS can read only a handful of response headers. List any *custom* response headers (`X-Request-Id`, `X-RateLimit-Remaining`) you want the client to be able to read here.</ConceptCard>
  <ConceptCard label="Vary: Origin (response)">**Easy to forget, important.** When your ACAO depends on the request's Origin (an allowlist echo), you MUST add `Vary: Origin` so caches/CDNs don't serve one origin's `Allow-Origin` to a different origin — which would either leak access or break it.</ConceptCard>
</ConceptGrid>

<Callout kind="pro" title="Read the headers off a real request in Go">
Everything you need is in `net/http`: `r.Header.Get("Origin")` is your input; `w.Header().Set("Access-Control-Allow-Origin", origin)` is your decision. A preflight is simply `r.Method == http.MethodOptions` with an `Access-Control-Request-Method` header present — answer it with the `Allow-*` headers and a `204`, and return early. That's the entire surface area. No middleware library is *required*; the popular ones (`rs/cors`, framework built-ins) just wrap exactly this logic with an allowlist and sensible defaults.
</Callout>

## Credentials & Cookies

This is where CORS gets dangerous, and where the worst misconfigurations live. By default, cross-origin `fetch` does **not** send cookies. But the moment credentials enter the picture, the rules tighten — and getting them wrong is how a CORS header becomes an account takeover.

<Define term="CORS credentials mode">
By default a cross-origin `fetch` sends **no cookies, no HTTP auth, no client certs** — so even a wide-open `Access-Control-Allow-Origin: *` only exposes *public* data. Credentials are sent only when the client opts in (`fetch(url, {credentials: 'include'})`) **and** the server opts in with **`Access-Control-Allow-Credentials: true`**. Critically, when credentials are allowed, the spec **forbids the wildcard**: `Access-Control-Allow-Origin` must be a **specific echoed origin**, never `*`. The reason is exactly the danger — credentialed cross-origin reads expose *authenticated* data (the user's inbox, balance, tokens), so the browser refuses to let "any origin" (`*`) read them; the server must name the *one* origin it trusts. The lethal bug is a server that **reflects** the request's Origin into Allow-Origin *and* sends Allow-Credentials: true — that's "any origin, with the user's cookies," the wildcard the spec forbids, achieved by hand.
</Define>

```go
package main

import (
	"fmt"
	"net/http"
	"net/http/httptest"
)

// VULNERABLE: reflects the request's Origin and allows credentials → any site
// can read the victim's authenticated response.
func corsVuln(next http.HandlerFunc) http.HandlerFunc {
	return func(w http.ResponseWriter, r *http.Request) {
		w.Header().Set("Access-Control-Allow-Origin", r.Header.Get("Origin"))
		w.Header().Set("Access-Control-Allow-Credentials", "true")
		next(w, r)
	}
}

var allowed = map[string]bool{"https://app.example.com": true}

// SAFE: exact-match allowlist; credentials only for a named origin.
func corsSafe(next http.HandlerFunc) http.HandlerFunc {
	return func(w http.ResponseWriter, r *http.Request) {
		if origin := r.Header.Get("Origin"); allowed[origin] {
			w.Header().Set("Access-Control-Allow-Origin", origin)
			w.Header().Set("Access-Control-Allow-Credentials", "true")
			w.Header().Add("Vary", "Origin")
		}
		next(w, r)
	}
}

func secret(w http.ResponseWriter, r *http.Request) { fmt.Fprint(w, `{"email":"victim@example.com"}`) }

func canRead(h http.HandlerFunc, origin string) bool {
	srv := httptest.NewServer(h)
	defer srv.Close()
	req, _ := http.NewRequest("GET", srv.URL, nil)
	req.Header.Set("Origin", origin)
	resp, _ := http.DefaultClient.Do(req)
	resp.Body.Close()
	// the browser allows the read iff ACAO echoes the origin AND credentials are on
	return resp.Header.Get("Access-Control-Allow-Origin") == origin &&
		resp.Header.Get("Access-Control-Allow-Credentials") == "true"
}

func main() {
	evil := "https://evil.attacker.com"
	fmt.Println("VULN: evil can read credentialed response:", canRead(corsVuln(secret), evil))
	fmt.Println("SAFE: evil can read credentialed response:", canRead(corsSafe(secret), evil))
	fmt.Println("SAFE: trusted origin can read:            ", canRead(corsSafe(secret), "https://app.example.com"))
}
```

## Misconfigurations

Every high-severity CORS bug is a flawed answer to "which origin do I trust?" Here are the ones that recur in bug-bounty reports, each a way an allowlist check goes wrong.

<ConceptGrid cols={2}>
  <ConceptCard label="Reflecting the Origin">The headline bug. `Allow-Origin: <whatever Origin sent>` + `Allow-Credentials: true` = every origin trusted with the user's cookies. Found by sending `Origin: https://evil.com` and checking it's echoed back. **Fix:** exact-match allowlist, never reflect.</ConceptCard>
  <ConceptCard label="Trusting null">Some servers allowlist the literal string `null` (it appears in errors and tutorials). But a sandboxed iframe (or a `data:`/`file:` document) sends `Origin: null` — so an attacker embeds your API call in a sandboxed iframe and *is* the null origin. **Fix:** never put `null` in your allowlist.</ConceptCard>
  <ConceptCard label="Suffix matching">`strings.HasSuffix(origin, "example.com")` to allow all subdomains also allows `https://evil-example.com` and `https://example.com.evil.com`. A substring/`Contains` check is even worse. **Fix:** match the full origin, or validate the parsed host against an exact set / a strict subdomain rule.</ConceptCard>
  <ConceptCard label="Sloppy regex">`^https://.*\.example\.com$` looks safe but an unanchored or dot-unescaped variant (`https://example.com` matching `.example.com`, or `evilexample.com` via an unescaped `.`) opens it up. Regex origin checks are a minefield. **Fix:** prefer an exact-set lookup; if you must allow subdomains, parse the URL and check `host == "example.com" || strings.HasSuffix(host, ".example.com")` (note the leading dot).</ConceptCard>
  <ConceptCard label="Wildcard with credentials">`Allow-Origin: *` plus `Allow-Credentials: true`. Browsers reject the combo, so devs "fix" it by reflecting — recreating the bug. **Fix:** if you need credentials, you need a real allowlist; if the data is public, use `*` and *don't* send credentials.</ConceptCard>
  <ConceptCard label="Pre-prod origins left in">An allowlist that still trusts `http://localhost:3000`, a staging domain, or a dead vendor origin an attacker can claim (see subdomain takeover). **Fix:** environment-specific allowlists; never ship dev/staging origins to production.</ConceptCard>
</ConceptGrid>

The suffix-match trap is worth seeing run, because it looks so reasonable:

<GoPlayground>

```go
package main

import (
	"fmt"
	"net/url"
	"strings"
)

// BAD: "allow any *.example.com" via suffix on the raw origin string.
func allowedBad(origin string) bool {
	return strings.HasSuffix(origin, "example.com")
}

// GOOD: parse the URL and check the HOST against an exact base or a real
// subdomain (note the leading dot — ".example.com").
func allowedGood(origin string) bool {
	u, err := url.Parse(origin)
	if err != nil || (u.Scheme != "https") {
		return false
	}
	host := u.Hostname()
	return host == "example.com" || strings.HasSuffix(host, ".example.com")
}

func main() {
	tests := []string{
		"https://app.example.com",        // legit subdomain
		"https://evil-example.com",       // lookalike — NOT a subdomain
		"https://example.com.evil.com",   // suffix attacker domain
		"https://example.com",            // the base
	}
	for _, o := range tests {
		fmt.Printf("%-30s bad=%-5v good=%v\n", o, allowedBad(o), allowedGood(o))
	}
}
```

</GoPlayground>

<Gotcha>
**An allowlist check operates on the *parsed host*, never the raw origin string.** Every suffix/substring/regex bug above comes from matching the origin as text. The instant you `url.Parse` it and compare `u.Hostname()` against an exact set (or a leading-dot subdomain rule), the lookalike (`evil-example.com`) and the suffix attacker (`example.com.evil.com`) both fail — because their *host* isn't `example.com` or `*.example.com`. String matching on origins is the root of nearly every CORS CVE; host matching kills it.
</Gotcha>

Put it together: a single, reusable CORS middleware that does the whole job correctly — exact-origin allowlist, preflight handling, credentials done safely, `Vary: Origin`, and a clean deny for unknown origins. This is the thing you actually ship.

```go
package main

import (
	"fmt"
	"net/http"
	"net/http/httptest"
)

// allowedOrigins is the exact set permitted to read credentialed responses.
// In production this comes from config and varies by environment.
var allowedOrigins = map[string]bool{
	"https://app.example.com": true,
}

func cors(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		origin := r.Header.Get("Origin")
		if origin != "" && allowedOrigins[origin] {
			h := w.Header()
			h.Set("Access-Control-Allow-Origin", origin) // exact echo, never *
			h.Set("Access-Control-Allow-Credentials", "true")
			h.Add("Vary", "Origin")
			if r.Method == http.MethodOptions { // preflight
				h.Set("Access-Control-Allow-Methods", "GET, POST, PUT, DELETE")
				h.Set("Access-Control-Allow-Headers", "Authorization, Content-Type")
				h.Set("Access-Control-Max-Age", "600")
				w.WriteHeader(http.StatusNoContent)
				return
			}
		} else if r.Method == http.MethodOptions {
			w.WriteHeader(http.StatusForbidden) // unknown-origin preflight: deny
			return
		}
		next.ServeHTTP(w, r) // unknown-origin non-preflight: served, but no ACAO
	})
}

func main() {
	app := http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) { fmt.Fprint(w, "data") })
	srv := httptest.NewServer(cors(app))
	defer srv.Close()

	probe := func(method, origin string) {
		req, _ := http.NewRequest(method, srv.URL, nil)
		req.Header.Set("Origin", origin)
		if method == http.MethodOptions {
			req.Header.Set("Access-Control-Request-Method", "PUT")
		}
		resp, _ := http.DefaultClient.Do(req)
		resp.Body.Close()
		fmt.Printf("%-7s %-26s → %d  ACAO=%q\n",
			method, origin, resp.StatusCode, resp.Header.Get("Access-Control-Allow-Origin"))
	}
	probe(http.MethodOptions, "https://app.example.com")
	probe(http.MethodGet, "https://app.example.com")
	probe(http.MethodOptions, "https://evil.com")
	probe(http.MethodGet, "https://evil.com")
}
```

<UnderTheHood title="Browser Preflight Mechanics & Go CORS Middleware Internals">

While CORS manifests on the wire as a collection of ASCII response headers, its browser runtime lifecycle and backend middleware execution path involve strict protocol invariants, edge caching pitfalls, and handler chain ordering rules.

### 1. The Preflight Decision Tree in Web Engines (Chromium & WebKit)

A browser determines whether to trigger an `OPTIONS` preflight before dispatching a cross-origin network request based on the Fetch Specification:

- **Simple Request Criteria:** A request bypasses preflight *only* if the HTTP method is `GET`, `HEAD`, or `POST`, and all custom headers belong to the CORS-safelisted set (`Accept`, `Accept-Language`, `Content-Language`, `Content-Type`), with `Content-Type` restricted to `application/x-www-form-urlencoded`, `multipart/form-data`, or `text/plain`.
- **Preflight Cache Partitioning (`Access-Control-Max-Age`):** Browsers maintain a preflight cache keyed on `(origin, url, method, request-headers)`. Chromium caps `Max-Age` at 7,200 seconds (2 hours), while Firefox allows up to 86,400 seconds (24 hours).
- **The Critical `Vary: Origin` Header:** When a Go server dynamically inspects `r.Header.Get("Origin")` against an allowlist and responds with `Access-Control-Allow-Origin: https://trusted.example.com`, it **must** attach `Vary: Origin`. Without `Vary: Origin`, reverse proxies (Cloudflare, Fastly, Nginx) or browser disk caches will cache the response for Origin A and serve it to Origin B, causing CORS failures or leaking authenticated JSON responses across origins.

### 2. Go CORS Middleware Execution Semantics (Go 1.22+)

Writing production-grade CORS middleware in Go requires careful management of the `http.Handler` pipeline:

- **Handler Pipeline Ordering:** CORS middleware must wrap *outside* authentication, authorization, and rate-limiting middleware. If an authentication handler sits ahead of the CORS handler, incoming browser preflight `OPTIONS` requests (which never carry credentials like cookies or `Authorization: Bearer ...`) will be rejected with `401 Unauthorized` or `403 Forbidden`, breaking client-side execution before the actual request can run.
- **Short-Circuiting Preflights:** When `r.Method == http.MethodOptions` and `r.Header.Get("Access-Control-Request-Method") != ""`, the middleware writes CORS response headers and terminates the request pipeline with `w.WriteHeader(http.StatusNoContent)` (or `200 OK`) without delegating to `next.ServeHTTP(w, r)`.
- **Header Canonicalization & MIME Keys:** Go's `http.Header.Set` and `http.Header.Get` internally normalize keys using `textproto.CanonicalMIMEHeaderKey`. However, values such as origin URLs must be parsed via `net/url` or matched with an exact hash set (`map[string]bool`) rather than naive string prefixes or substring searches (`strings.Contains`), which introduce subdomain takeover and regex injection vulnerabilities.

</UnderTheHood>

## When CORS Won't Save You

The most dangerous misconceptions about CORS are about what it *doesn't* do. Internalize these or you'll trust it for protection it never provides.

<ConceptGrid cols={2}>
  <ConceptCard label="CORS is not server-side access control">CORS is enforced by the **browser**. A non-browser client — `curl`, a Go program, a script — ignores it completely and reads your response regardless of any `Allow-Origin` header. CORS controls what *other websites* can do in a *victim's browser*. It is **not** authentication or authorization. Your real access control (auth tokens, ownership checks) still has to be there.</ConceptCard>
  <ConceptCard label="CORS does not stop CSRF">CORS governs **reads**; CSRF is about unwanted **writes**. A simple cross-origin `POST` still *reaches* your server with the user's cookies even with no CORS headers — the attacker just can't read the response. If that POST has a side effect, you have CSRF. Defend it separately (SameSite cookies, CSRF tokens, `CrossOriginProtection`).</ConceptCard>
  <ConceptCard label="A permissive policy is a real finding">`Allow-Origin: *` on a public, unauthenticated endpoint is fine. The same on an endpoint that returns user data with credentials is a serious vulnerability. The bug isn't the wildcard itself — it's the combination with credentials/sensitive data. Scope the judgment to what the endpoint returns.</ConceptCard>
  <ConceptCard label="The Origin header is trustworthy (from a browser)">A browser sets `Origin` and a script can't forge it — so for *browser-based* attacks, you can trust the Origin you see. But a non-browser attacker can send any Origin they like; that's fine, because CORS only matters in a browser anyway. Don't use Origin as auth for non-browser clients.</ConceptCard>
</ConceptGrid>

<Callout kind="warn" title="Real chain — Zoho account takeover">
A disclosed Zoho ATO chained a permissive **CORS** policy with a DOM-XSS and an unvalidated `postMessage` handler: the attacker's page read the victim's `mail.zoho.com` inbox **cross-origin** (the CORS bug), intercepted the login **OTP** from the incoming email, and logged in as the victim — full takeover from one click. The CORS half is the lesson here: a too-permissive cross-origin read of *authenticated* email data was the linchpin. An exact-match allowlist (this chapter) denies that read and breaks the chain. The other halves (don't `eval` untrusted input; always check `event.origin` on `postMessage`) are browser-side, but the server's CORS policy was the part that made the inbox readable at all.
</Callout>

<Exercise n={1} title="Same origin?" level="easy">

Write `sameOrigin(a, b string) bool` that returns true only if two URLs share scheme **and** host **and** port (defaulting 443 for https, 80 for http). Verify `https://x.com/a` vs `https://x.com/b` is true, but different-port and different-scheme pairs are false.

<Solution>

```go
package main

import (
	"fmt"
	"net/url"
)

func port(u *url.URL) string {
	if p := u.Port(); p != "" {
		return p
	}
	if u.Scheme == "https" {
		return "443"
	}
	return "80"
}

func sameOrigin(a, b string) bool {
	ua, e1 := url.Parse(a)
	ub, e2 := url.Parse(b)
	if e1 != nil || e2 != nil {
		return false
	}
	return ua.Scheme == ub.Scheme && ua.Hostname() == ub.Hostname() && port(ua) == port(ub)
}

func main() {
	fmt.Println(sameOrigin("https://x.com/a", "https://x.com/b"))     // true (path ignored)
	fmt.Println(sameOrigin("https://x.com", "https://x.com:8443"))    // false (port)
	fmt.Println(sameOrigin("http://x.com", "https://x.com"))          // false (scheme)
	fmt.Println(sameOrigin("https://x.com", "https://api.x.com"))     // false (host)
}
```

The path is deliberately not compared — it isn't part of the origin. The default-port normalization is what makes `https://x.com` and `https://x.com:443` the same origin.

</Solution>

</Exercise>

<Exercise n={2} title="Allowlist check, done right" level="medium">

Write `allow(origin string, set map[string]bool) bool` that returns true only for an **exact** origin match — and show it rejects `https://evil-example.com` and `https://app.example.com.evil.com` even when `https://app.example.com` is allowed.

package main

<Exercise n={3} title="Detect the reflected-origin bug" level="medium">

Write `vulnerable(setHeaders func(origin string) (acao, acac string)) bool` that probes a CORS policy with `Origin: https://attacker.test` and reports true if the policy reflects that origin into `acao` **and** sets `acac == "true"` (the dangerous combo). Test it against a reflecting policy and an allowlist policy.

<Solution>

```go
package main

import "fmt"

func vulnerable(setHeaders func(origin string) (acao, acac string)) bool {
	const probe = "https://attacker.test"
	acao, acac := setHeaders(probe)
	return acao == probe && acac == "true" // reflected + credentials = bug
}

func main() {
	reflecting := func(o string) (string, string) { return o, "true" } // echoes anything
	allowlist := func(o string) (string, string) {
		if o == "https://app.example.com" {
			return o, "true"
		}
		return "", "" // unknown origin → no headers
	}
	fmt.Println("reflecting policy vulnerable:", vulnerable(reflecting)) // true
	fmt.Println("allowlist policy vulnerable: ", vulnerable(allowlist))  // false
}
```

This is exactly the automated check a CORS scanner runs: send an arbitrary origin, see if it's echoed back with credentials on. A `true` here is a high-severity finding.

<Exercise n={4} title="Answer a preflight" level="medium">

Write an `http.HandlerFunc` that, for an allowed origin's `OPTIONS` request, returns `204` with `Access-Control-Allow-Methods: GET, POST, PUT, DELETE` and `Access-Control-Max-Age: 600`; for an unknown origin's `OPTIONS`, returns `403`. Drive it with `httptest`.

	"fmt"
	"net/http"
	"net/http/httptest"

<Exercise n={5} title="Subdomain rule without the suffix bug" level="hard">

Write `allowSubdomain(origin, base string) bool` that allows `base` itself and any direct/nested subdomain of `base` (over https), but rejects lookalikes (`evil-base`) and suffix attackers (`base.evil.com`). Test against `example.com`.

<Solution>

```go
package main

import (
	"fmt"
	"net/url"
	"strings"
)

func allowSubdomain(origin, base string) bool {
	u, err := url.Parse(origin)
	if err != nil || u.Scheme != "https" {
		return false
	}
	host := u.Hostname()
	// the base itself, OR something ending in "." + base (a real subdomain)
	return host == base || strings.HasSuffix(host, "."+base)
}

func main() {
	for _, o := range []string{
		"https://example.com",          // base
		"https://app.example.com",      // subdomain
		"https://a.b.example.com",      // nested subdomain
		"https://evil-example.com",     // lookalike → reject
		"https://example.com.evil.com", // suffix attacker → reject
		"http://app.example.com",       // wrong scheme → reject
	} {
		fmt.Printf("%-30s %v\n", o, allowSubdomain(o, "example.com"))
	}
}
```

The leading dot in `"."+base` is the whole defense: `evil-example.com` doesn't end in `.example.com`, and `example.com.evil.com`'s host is `example.com.evil.com` (ends in `.evil.com`, not `.example.com`). Matching the parsed host, not the string, is what makes it safe.

</Solution>

<Recap>

- An **origin** is **scheme + host + port** — all three. Same domain isn't same origin if the scheme, port, or subdomain differs. The path is not part of the origin.
- The **same-origin policy** lets a page *send* a cross-origin request but blocks its JavaScript from *reading* the response — enforced by the **browser**, not your server. It stops `evil.com` from reading `bank.com`'s authenticated responses with your cookies.
- **CORS** is just HTTP headers: the browser stamps `Origin`, your server answers with `Access-Control-Allow-Origin` (and friends), and the browser allows the read only if they match. Opt-in by the server, enforced by the browser.
- **Simple** requests (safe method + safelisted headers/content-type) go straight through; **non-simple** ones (PUT/DELETE, `Authorization`, `application/json`, custom headers) trigger a **preflight** `OPTIONS` the server must answer with `Allow-Methods`/`Allow-Headers` before the real request is sent.
- **Credentials change everything**: cross-origin `fetch` sends no cookies by default; only `Allow-Credentials: true` + the client's `credentials: 'include'` does. With credentials, **`*` is forbidden** — you must echo an exact origin — because credentialed reads expose *authenticated* data.
- The headline bug is **reflecting the Origin** into `Allow-Origin` with credentials on — "any origin + cookies", the forbidden wildcard by hand. Plus trusting `null`, suffix/substring matching, and sloppy regex. **Fix: match the parsed host against an exact set** (or a leading-dot subdomain rule), never the raw string.
- A **correct middleware** allowlists exact origins, echoes (never wildcards) for credentials, handles and caches the preflight, denies unknown-origin preflights, and adds `Vary: Origin`.
- **CORS is not** server-side access control (non-browser clients ignore it), and it does **not** stop CSRF (which is about writes, not reads). It controls what *other websites* can read in a *victim's browser* — your auth and CSRF defenses are separate and still required.

</Recap>
