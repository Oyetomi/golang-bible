## The Distributed Locking Lie

Let us begin by exposing the fundamental difference between an in-memory lock (`sync.Mutex`) and a distributed lock.

When you lock a `sync.Mutex` in Go:
1. The memory address lives in the same process address space.
2. The operating system thread or goroutine scheduler coordinates directly with CPU cache coherency protocols (`MESI` / atomic compare-and-swap).
3. If the process crashes, everything dies together. There is no partial failure.

In a distributed system, every single one of those assumptions is false:

```
┌──────────────────────────────────────────────────────────────┐
│                    THE ASYNCHRONOUS NETWORK                 │
│                                                              │
│   Worker Node 1                  Worker Node 2               │
│  ┌──────────────┐               ┌──────────────┐             │
│  │ GC Pause 10s │               │ Running Fast │             │
│  └──────┬───────┘               └──────┬───────┘             │
│         │                              │                     │
│         │ (Stale write)                │ (Valid write)       │
│         ▼                              ▼                     │
│    ┌────────────────────────────────────────┐                │
│    │      Shared Database / Ledger          │                │
│    │    "WHO ACTUALLY HOLDS THE LOCK?"      │                │
│    └────────────────────────────────────────┘                │
└──────────────────────────────────────────────────────────────┘
```

Distributed locks serve two completely different objectives, and confusing them causes multi-million dollar outages:

1. **Efficiency (Optimization)**: Preventing redundant expensive computation. If two workers render the same monthly PDF statement twice, it wastes CPU cycles, but nobody loses money. A simple Redis lock with a TTL is completely fine here.
2. **Correctness (Safety)**: Preventing data corruption, double-transfers, or split-brain mutations. If two workers disburse the same settlement batch, the ledger is corrupted. **A time-bounded lease ALONE cannot provide correctness.**

<Define term="Distributed Lock">
A synchronization mechanism coordinating access to a shared resource across multiple independent network nodes. Because nodes can crash or disconnect, all distributed locks use time-bounded leases (TTLs) to prevent permanent deadlocks, making them vulnerable to expiration while work is still ongoing.
</Define>

## Monotonic Fencing Tokens

How do we solve the Kleppmann hazard?

You cannot fix it at the lock server alone. **The storage engine must participate in mutual exclusion.**

The solution is **Monotonic Fencing Tokens**.

```
  Lock Server (etcd/Consul)                   Database / Storage Engine
┌───────────────────────────┐               ┌───────────────────────────┐
│ Token Generator:          │               │ UPDATE accounts           │
│   Acquire() -> Token 42   │               │ SET balance = ...,        │
│   Acquire() -> Token 43   │               │     last_token = 43       │
│   Acquire() -> Token 44   │               │ WHERE id = 101            │
│                           │               │   AND last_token < 43;    │
└───────────────────────────┘               └───────────────────────────┘
```

### The Fencing Protocol

1. When a worker requests a lock, the lock manager grants the lease AND a **monotonically increasing integer** (Token: `1, 2, 3...` or etcd `Raft Revision`).
2. Every write request sent to the storage system (PostgreSQL, MySQL, S3 object storage) must attach the current `fencing_token`.
3. The storage engine validates that the incoming `fencing_token` is **strictly greater** than the highest token it has ever committed.
4. If a stale worker wakes up from a GC pause and tries to write with an older token, the database rejects the write (`0 rows updated`).

<Define term="Fencing Token">
A strictly monotonically increasing number generated by a consensus-backed lock manager upon each lock grant. Downstream storage systems verify that incoming operations have a higher token than previously seen operations, rejecting stale writes from expired lock holders.
</Define>

<GoPlayground>

```go
package main

import (
	"errors"
	"fmt"
	"sync"
	"sync/atomic"
)

// LedgerAccount represents a bank account protected by fencing tokens
type LedgerAccount struct {
	mu               sync.Mutex
	AccountID        string
	BalanceCents     int64
	LastFencingToken uint64
}

var ErrStaleFencingToken = errors.New("storage: rejected write with stale fencing token")

// UpdateBalanceFenced enforces monotonic token verification in storage
func (acc *LedgerAccount) UpdateBalanceFenced(deltaCents int64, fencingToken uint64) error {
	acc.mu.Lock()
	defer acc.mu.Unlock()

	// Storage invariant: incoming token MUST be strictly greater than last committed
	if fencingToken <= acc.LastFencingToken {
		return fmt.Errorf("%w: token %d <= last seen %d",
			ErrStaleFencingToken, fencingToken, acc.LastFencingToken)
	}

	if acc.BalanceCents+deltaCents < 0 {
		return errors.New("insufficient funds")
	}

	acc.BalanceCents += deltaCents
	acc.LastFencingToken = fencingToken
	return nil
}

// LockManager simulates etcd/Raft generating monotonic fencing tokens
type LockManager struct {
	currentToken atomic.Uint64
}

func (lm *LockManager) AcquireLock() uint64 {
	return lm.currentToken.Add(1)
}

func main() {
	lm := &LockManager{}
	acc := &LedgerAccount{AccountID: "ACC-MERIDIAN-99", BalanceCents: 50_000_00} // $50,000.00

	// Step 1: Worker 1 acquires lock -> gets Token 1
	tokenW1 := lm.AcquireLock()
	fmt.Printf("Worker 1 acquired lock with Fencing Token: %d\n", tokenW1)

	// Step 2: Worker 1 pauses (GC / network freeze). Lock expires.
	// Worker 2 acquires lock -> gets Token 2
	tokenW2 := lm.AcquireLock()
	fmt.Printf("Worker 2 acquired lock with Fencing Token: %d\n", tokenW2)

	// Step 3: Worker 2 commits payout $10,000 with Token 2
	err := acc.UpdateBalanceFenced(-10_000_00, tokenW2)
	fmt.Printf("Worker 2 write status: err=%v | Balance: $%d\n", err, acc.BalanceCents/100)

	// Step 4: Worker 1 wakes up and attempts to commit payout $10,000 with Token 1
	err = acc.UpdateBalanceFenced(-10_000_00, tokenW1)
	if errors.Is(err, ErrStaleFencingToken) {
		fmt.Printf("SUCCESS: Storage rejected Worker 1's stale write! Error: %v\n", err)
	}

	fmt.Printf("Final Account Balance: $%d (Double payout prevented!)\n", acc.BalanceCents/100)
}
```

## PostgreSQL Advisory Locks

If your application already uses PostgreSQL as its source of truth, you don't need Redis or etcd for many distributed locking workflows. PostgreSQL provides built-in application-level locks known as **Advisory Locks**.

```
┌─────────────────────────────────────────────────────────────┐
│                   PostgreSQL Server                         │
│  ┌───────────────────────────────────────────────────────┐  │
│  │                   pg_locks Catalog                    │  │
│  │   - locktype: 'advisory'                              │  │
│  │   - objid: 4294967296 (64-bit BigInt key)             │  │
│  │   - pid: 14022 (Bound to backend connection)          │  │
│  │   - granted: true                                     │  │
│  └───────────────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────────────┘
```

Postgres advisory locks come in two distinct scopes:
1. **Transaction-Level (`pg_advisory_xact_lock`)**: Held strictly for the duration of the SQL transaction (`BEGIN ... COMMIT`). Automatically released when the transaction ends (commit or rollback).
2. **Session-Level (`pg_advisory_lock`)**: Held for the lifetime of the database connection until explicitly released with `pg_advisory_unlock` or when the TCP connection closes.

<Define term="PostgreSQL Advisory Lock">
An application-controlled mutual exclusion primitive managed directly by PostgreSQL's in-kernel lock table (`pg_locks`). They lock arbitrary 64-bit integer numbers rather than table rows or pages, incurring zero disk I/O.
</Define>

### The Go `database/sql` Connection Pool Trap ⚠

Here is the single most dangerous bug in Go database programming:

Go's `sql.DB` is a **connection pool**, not a single connection. When you execute `db.Exec("SELECT pg_advisory_lock(123)")`, Go checks out a connection from the pool, runs the query, and **immediately returns the connection to the pool**.

If another goroutine later checks out that same connection, it unintentionally inherits your lock! If your goroutine tries to unlock on a different connection, the unlock fails or unlocks someone else's resource.

```go
// ❌ BROKEN: Session lock leaks across sql.DB connection pool
func BrokenLock(db *sql.DB, lockID int64) {
    // Checked out Conn A, acquired lock, returned Conn A to pool!
    db.Exec("SELECT pg_advisory_lock($1)", lockID) 
    
    // ... do work ...
    
    // Checked out Conn B, tried to unlock! Conn B DOES NOT HOLD THE LOCK!
    db.Exec("SELECT pg_advisory_unlock($1)", lockID) 
}

// ✅ IDIOMATIC 1: Transaction-level advisory lock (Always safe)
func SafeTxLock(ctx context.Context, db *sql.DB, lockID int64, fn func(tx *sql.Tx) error) error {
    tx, err := db.BeginTx(ctx, nil)
    if err != nil {
        return err
    }
    defer tx.Rollback()

    // Lock automatically released on Commit or Rollback
    if _, err := tx.ExecContext(ctx, "SELECT pg_advisory_xact_lock($1)", lockID); err != nil {
        return err
    }

    if err := fn(tx); err != nil {
        return err
    }
    return tx.Commit()
}

// ✅ IDIOMATIC 2: Dedicated sql.Conn for session locks
func SafeSessionLock(ctx context.Context, db *sql.DB, lockID int64) (*sql.Conn, error) {
    conn, err := db.Conn(ctx) // Checkout dedicated connection
    if err != nil {
        return nil, err
    }
    if _, err := conn.ExecContext(ctx, "SELECT pg_advisory_lock($1)", lockID); err != nil {
        conn.Close()
        return nil, err
    }
    return conn, nil // Caller MUST defer conn.Close() and unlock
}
```

  <ConceptCard label="pg_advisory_xact_lock">Transaction-scoped. Zero risk of connection leaks. Automatically unlocked when transaction commits or fails.</ConceptCard>
  <ConceptCard label="64-Bit Integer Keys">Advisory locks accept a single bigint (`int64`). Use deterministic hashing (e.g. FNV-1a or Murmur3) to convert entity strings (`settlement:101`) to int64.</ConceptCard>
  <ConceptCard label="Zero Disk I/O">Advisory locks live entirely in PostgreSQL shared memory (`pg_locks`). They create no WAL logs and generate no table bloat.</ConceptCard>

## etcd Leases & Revision Mutexes

When building distributed systems outside a single PostgreSQL database, **etcd** (the consensus engine behind Kubernetes) is the gold standard.

etcd implements distributed locks using the **Raft consensus algorithm**, guaranteeing linearizable consistency even across server crashes and network splits.

### How `etcd/clientv3/concurrency` Works

```
1. Create Lease with TTL (e.g. 10s)
         │
         ▼
2. Background KeepAlive Goroutine (Heartbeat)
         │
         ▼
3. Create Sequential Key in etcd:
   Key:   /meridian/locks/settlement/75878252274987
   Value: empty
         │
         ▼
4. Raft Consents: Key gets a global 64-bit `CreateRevision` (e.g. Rev #1042)
         │
         ▼
5. Is our Revision the LOWEST under /meridian/locks/settlement/?
   ├── YES: We hold the lock! Rev #1042 IS OUR FENCING TOKEN.
   └── NO:  Watch the preceding revision key until it is deleted.
```

<Define term="etcd Revision Fencing">
Using etcd's 64-bit globally monotonic Raft store revision number as an unforgeable, consensus-backed fencing token for downstream storage checks.
</Define>

```go
package main

import (
	"context"
	"fmt"
	"log"
	"time"

	clientv3 "go.etcd.io/etcd/client/v3"
	"go.etcd.io/etcd/client/v3/concurrency"
)

func RunWithEtcdLock(ctx context.Context, client *clientv3.Client, lockPrefix string) error {
	// 1. Create a session with a 10-second lease (manages heartbeat automatically)
	session, err := concurrency.NewSession(client, concurrency.WithTTL(10))
	if err != nil {
		return fmt.Errorf("failed to create etcd session: %w", err)
	}
	defer session.Close()

	// 2. Create distributed mutex under prefix
	mutex := concurrency.NewMutex(session, lockPrefix)

	// 3. Acquire lock (blocks until lowest revision in Raft log)
	log.Println("Acquiring etcd distributed lock...")
	if err := mutex.Lock(ctx); err != nil {
		return fmt.Errorf("failed to acquire lock: %w", err)
	}
	defer mutex.Unlock(context.Background())

	// 4. EXTRACT MONOTONIC FENCING TOKEN: etcd's Raft Header Revision!
	fencingToken := mutex.Header().Revision
	log.Printf("Lock ACQUIRED! Consensus Fencing Token (Raft Revision): %d\n", fencingToken)

	// 5. Execute critical section passing fencingToken to database
	return processSettlementWithFencing(ctx, fencingToken)
}

func processSettlementWithFencing(ctx context.Context, token int64) error {
	log.Printf("Executing critical section with Fencing Token %d...\n", token)
	time.Sleep(500 * time.Millisecond)
	return nil
}
```

## The Redlock Debate & Redis Realities

No discussion of distributed locks is complete without addressing **Redlock**, the multi-node Redis locking algorithm created by Salvatore Sanfilippo (Antirez).

### The Redlock Algorithm

To avoid single-point-of-failure issues with a single Redis instance, Redlock uses N independent Redis masters (typically N = 5, with no replication between them):
1. The client gets the current timestamp in milliseconds.
2. It attempts to acquire the lock in all N instances sequentially using `SET resource token NX PX ttl`.
3. The client considers the lock acquired if it successfully locks a **majority** (at least (N/2)+1 = 3 nodes out of 5) within a total time less than the lock validity time.
4. The remaining validity time is: `validity = TTL - elapsed_time - clock_drift`.

<UnderTheHood title="The Physics of Distributed Locking: Clock Drift, Consensus & Connection Pools">

Distributed locking is where hardware physics and network realities collide with programmatic guarantees:

1. **The Physical Impossibility of Synchronized Clocks**: Standard server hardware uses quartz crystal oscillators that drift by 1–5 seconds per week due to thermal fluctuation. Network Time Protocol (NTP) synchronizes clocks with unpredictable network jitter (±5ms to ±50ms). Crucially, NTP can jump backwards during synchronization steps unless monotonic time (`time.Since`) is used exclusively.
2. **TrueTime vs. Raft Consensus**: Google Spanner achieves external consistency by using GPS receivers and atomic clocks with bounded uncertainty (around 7ms), waiting out the uncertainty window before committing. Systems like `etcd` bypass physical clocks entirely by using logical Raft consensus terms and store revision numbers.
3. **Database Connection Pool Hazards**: PostgreSQL advisory locks are bound to physical backend server processes (`PGPROC`). If your Go service executes `pg_advisory_lock` on a generic `*sql.DB` pool without holding a dedicated `*sql.Conn` or wrapping inside `sql.Tx`, subsequent queries may execute on different pooled connections, silently bypassing the lock and leaking locks indefinitely.

</UnderTheHood>

## Production Fenced Lock Engine in Go

Let's assemble a complete, production-grade distributed lock manager with monotonic fencing token tracking, simulated network pauses, and storage validation in pure Go.

```go
package main

import (
	"context"
	"crypto/rand"
	"encoding/hex"
	"errors"
	"fmt"
	"sync"
	"sync/atomic"
	"time"
)

// FencedLock represents an acquired lock with a monotonic token
type FencedLock struct {
	Key          string
	OwnerUUID    string
	FencingToken uint64
	LeaseExpiry  time.Time
}

// LockManagerEngine manages distributed leases and monotonic tokens
type LockManagerEngine struct {
	mu           sync.Mutex
	locks        map[string]*FencedLock
	tokenCounter atomic.Uint64
}

func NewLockManagerEngine() *LockManagerEngine {
	return &LockManagerEngine{
		locks: make(map[string]*FencedLock),
	}
}

// Acquire attempts to acquire a named lock with a time-to-live
func (lm *LockManagerEngine) Acquire(ctx context.Context, key string, ttl time.Duration) (*FencedLock, error) {
	lm.mu.Lock()
	defer lm.mu.Unlock()

	now := time.Now()
	existing, exists := lm.locks[key]

	// If lock exists and has not expired, acquisition fails
	if exists && now.Before(existing.LeaseExpiry) {
		return nil, errors.New("lock already held by another worker")
	}

	// Generate random owner ID and monotonic fencing token
	b := make([]byte, 8)
	rand.Read(b)
	ownerID := hex.EncodeToString(b)

	token := lm.tokenCounter.Add(1)
	lock := &FencedLock{
		Key:          key,
		OwnerUUID:    ownerID,
		FencingToken: token,
		LeaseExpiry:  now.Add(ttl),
	}

	lm.locks[key] = lock
	return lock, nil
}

// Release safely releases a lock using atomic CAS comparison
func (lm *LockManagerEngine) Release(key string, ownerUUID string) bool {
	lm.mu.Lock()
	defer lm.mu.Unlock()

	existing, exists := lm.locks[key]
	if !exists {
		return false
	}

	// CAS check: only the true owner can release the lock!
	if existing.OwnerUUID == ownerUUID {
		delete(lm.locks, key)
		return true
	}
	return false // Owned by someone else (lease had expired)
}
```

	lastTokens map[string]uint64

	}

<Exercise n={3} title="Automatic Lease KeepAlive Heartbeat" level="hard">

Implement a Go background lease refresher `StartHeartbeat(ctx context.Context, renewFn func() error, interval time.Duration) <-chan error` that continually extends a distributed lease until context cancellation or a heartbeat renewal error occurs.

<Solution>

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"sync/atomic"
	"time"
)

func StartHeartbeat(ctx context.Context, renewFn func() error, interval time.Duration) <-chan error {
	errChan := make(chan error, 1)

	go func() {
		defer close(errChan)
		ticker := time.NewTicker(interval)
		defer ticker.Stop()

		for {
			select {
			case <-ctx.Done():
				return
			case <-ticker.C:
				if err := renewFn(); err != nil {
					errChan <- fmt.Errorf("heartbeat failed: %w", err)
					return
				}
			}
		}
	}()

	return errChan
}

func main() {
	ctx, cancel := context.WithTimeout(context.Background(), 100*time.Millisecond)
	defer cancel()

	var renewCount atomic.Int32
	renewFn := func() error {
		renewCount.Add(1)
		return nil
	}

	errChan := StartHeartbeat(ctx, renewFn, 20*time.Millisecond)

	for err := range errChan {
		if err != nil {
			fmt.Println("Error:", err)
		}
	}
	fmt.Printf("Heartbeat finished cleanly. Total renewals: %d\n", renewCount.Load())
}
```

A robust lease manager uses a background ticker running at roughly one-third (1/3) of the total TTL duration to refresh the lease, ensuring transient network hiccups don't cause premature expiration while work is actively executing.

</Solution>

## Recap

- **Distributed locks require leases (TTLs)** to prevent infinite deadlocks on node failure, but leases can expire silently during GC pauses, hypervisor stalls, or network partitions.
- The **Martin Kleppmann GC Hazard** proves that client-side lock checks cannot protect against split-brain writes when processes freeze.
- **Monotonic Fencing Tokens** provide the only mathematically sound defense: storage engines must reject incoming writes where `fencing_token <= last_seen_token`.
- **PostgreSQL Advisory Locks** provide zero-overhead transactional mutual exclusion, but require using `pg_advisory_xact_lock` inside a transaction to prevent connection-pool leaks.
- **etcd** utilizes the Raft consensus algorithm to provide linearizable distributed mutexes, where the Raft store revision number acts as an unforgeable fencing token.
- **Redis single-instance locks** require atomic Lua CAS scripts for safe release, and should be reserved for efficiency optimization rather than financial correctness unless combined with storage fencing.

<Recap>
- **Efficiency vs. Correctness**: Efficiency locks (single-instance Redis) avoid duplicated work like cron runs. Correctness locks (financial settlement, ledger writes) require linearizable consensus and storage-level validation.
- **The Kleppmann Hazard**: No distributed lock based on time leases can guarantee mutual exclusion on asynchronous networks when clients experience stop-the-world GC pauses, CPU starvation, or hypervisor freezes.
- **Fencing Tokens**: Every lock acquisition returns a strictly monotonically increasing counter ($Token = N+1$). Storage engines enforce `WHERE fencing_token > highest_seen_token`, deterministically discarding stale writes.
- **PostgreSQL Advisory Locks**: Session-level (`pg_advisory_lock`) vs Transaction-level (`pg_advisory_xact_lock`). Transaction-level locks auto-release on `COMMIT`/`ROLLBACK` and are safe for Go connection pools.
- **etcd Consensus Leases**: Built on Raft linearizability. etcd generates monotonic 64-bit store revision numbers on every mutation, providing native fencing tokens directly out of the box.
