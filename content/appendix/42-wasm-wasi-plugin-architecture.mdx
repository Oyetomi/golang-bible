## The Extensibility Dilemma

Every software engineer tries to solve backend extensibility with one of three flawed patterns before finding WebAssembly:

<ConceptGrid cols={3}>
  <ConceptCard label="1. Go Native Plugins (plugin.Open)">
    **The Nightmare.** Requires CGO, only works reliably on Linux with identical Go compiler patch versions and dependencies. A single crash in the plugin terminates the entire host server.
  </ConceptCard>
  <ConceptCard label="2. Dynamic Script Engines (Goja / Lua)">
    **The Performance Crawl.** JavaScript and Lua interpreters written in Go suffer high GC allocation overhead, poor CPU performance, and lack type safety or language flexibility.
  </ConceptCard>
  <ConceptCard label="3. Microservice / Container Isolation">
    **The Latency Wall.** Starting a container per call takes far too long for a payment path, and calling a sidecar service costs a network round trip and serialization on every transaction.
  </ConceptCard>
</ConceptGrid>

<Define term="WebAssembly (Wasm)">
**WebAssembly (Wasm)** is a binary instruction format designed as a portable, sandboxed compilation target for languages like Go, Rust, C++, and Zig. It executes in a memory-safe, isolated virtual stack machine at near-native execution speed with startup times measured in **microseconds**.
</Define>

<Define term="WASI (WebAssembly System Interface)">
**WASI** is a standardized set of capability-oriented POSIX-like system calls (clocks, files, random numbers, stdio) for running WebAssembly outside the browser. In WASI, **modules have zero ambient authority**: they cannot access the network, read files, or check the system clock unless the host explicitly grants that capability.
</Define>

## Compiling Go to WASI

Since Go 1.21, Go has official support for compiling to WASI with **`GOOS=wasip1 GOARCH=wasm`**.

### Toolchain Comparison: Standard Go vs TinyGo

When compiling Go to Wasm plugins, you have two compiler options:

| Feature | Standard Go (`go build`) | TinyGo (`tinygo build`) |
| :--- | :--- | :--- |
| **Command** | `GOOS=wasip1 GOARCH=wasm go build` | `tinygo build -target=wasi` |
| **Binary Size** | 2.5 MB for the small fee guest below (it carries the full runtime and GC) | much smaller, typically tens to hundreds of KB (not measured here) |
| **Startup Time** | 1.7–3.1 ms per fresh instance, including running it (measured below) | shorter, with far less runtime to initialize (not measured here) |
| **Standard Library** | 100% full Go stdlib | Embedded subset (optimized for micro-controllers & Wasm) |
| **Ideal Use Case** | Complex modules with heavy reflection/crypto | High-frequency plugins, dynamic fee rules, risk filters |

<UnderTheHood title="The Wasm Module Binary Structure">
A compiled `.wasm` file is a compact binary bytecode container divided into sections:
- **Type Section**: Function signatures (parameters and return types).
- **Import Section**: Host functions declared by the host and imported into the guest.
- **Function Section**: Internal function declarations.
- **Memory Section**: Linear memory page definitions (1 page = 64 KiB = 65,536 bytes).
- **Export Section**: Functions and memory buffers exported by the guest for the host to invoke.
- **Code Section**: Compiled bytecode instructions executed on the virtual stack.
</UnderTheHood>

Let's write a self-contained Go guest module that exports a mathematical fee calculation function:

```go
// guest/fee_plugin.go
package main

//export CalculateTieredFee
func CalculateTieredFee(amountCents int64, merchantTier int32) int64 {
	var basisPoints int64
	switch merchantTier {
	case 1: // Enterprise
		basisPoints = 15 // 0.15%
	case 2: // Preferred
		basisPoints = 25 // 0.25%
	default: // Standard
		basisPoints = 50 // 0.50%
	}

	fee := (amountCents * basisPoints) / 10000
	if fee < 30 { // 30 cents minimum fee
		fee = 30
	}
	return fee
}

func main() {
	// main is required for WASI initialization
}
```

Compiling this with standard Go or TinyGo:
```bash
# Standard Go
GOOS=wasip1 GOARCH=wasm go build -o fee_plugin.wasm guest/fee_plugin.go

# TinyGo (Micro-binary)
tinygo build -target=wasi -o fee_plugin.wasm guest/fee_plugin.go
```

## The Wazero Pure-Go Runtime

Most WebAssembly runtimes in Go (such as `wasmtime-go` or `wasmer-go`) wrap large C/Rust libraries using **CGO**. That introduces the same fatal pitfalls: C toolchains required at build time, difficult cross-compilation, and memory bugs in C that bypass Go's memory safety.

**`tetratelabs/wazero`** is the gold standard for Go: a **100% pure Go WebAssembly runtime with zero CGO**.

```text
┌────────────────────────────────────────────────────────┐
│               Go Application (Host)                    │
│                                                        │
│  ┌──────────────────────────────────────────────────┐  │
│  │             wazero Runtime Engine                │  │
│  │   • Compiler JIT (x86_64 / ARM64 native ASM)     │  │
│  │   • WASI Snapshot Preview 1 Builtin              │  │
│  │   • Sandboxed Linear Memory (64KB Pages)         │  │
│  └──────────────────────────┬───────────────────────┘  │
│                             │                          │
└─────────────────────────────┼──────────────────────────┘
                              ▼
            ┌──────────────────────────────────┐
            │       Guest Wasm Module          │
            │    (Untrusted User Plugin)       │
            └──────────────────────────────────┘
```

<ConceptGrid cols={2}>
  <ConceptCard label="Zero CGO Dependency">
    Compiles cleanly on any platform (`CGO_ENABLED=0`) and cross-compiles effortlessly for Linux AMD64, ARM64, Windows, and macOS.
  </ConceptCard>
  <ConceptCard label="JIT Compilation to Native Assembly">
    Wazero compiles Wasm bytecode directly into native x86-64 and AArch64 machine instructions at runtime in pure Go, achieving near-native performance.
  </ConceptCard>
  <ConceptCard label="Resource Quotas & Timeouts">
    Supports `context.WithTimeout` to abort long-running or infinite loops, and caps maximum memory pages to prevent RAM exhaustion.
  </ConceptCard>
  <Gotcha>
    ⚠ Wasm guest functions can only pass basic numeric types (`i32`, `i64`, `f32`, `f64`) natively! Passing strings, structs, or JSON requires the Host-Guest Shared Memory Protocol.
  </Gotcha>
</ConceptGrid>

## Host-Guest Shared Memory ABI

WebAssembly has a fundamental constraint: **its function signatures only accept and return 32-bit and 64-bit numbers**.

How do you pass a complex JSON payload like `{"transaction_id": "tx-99", "amount": 5000}` to a guest Wasm plugin, and receive a rich risk evaluation result back?

You use **Host-Guest Linear Memory Exchange**.

<Define term="Wasm Linear Memory">
**Linear memory** is a contiguous, flat array of raw bytes allocated by the Wasm module and accessible to both host and guest. Memory is organized into **64 KiB pages**. The host can read and write directly into this buffer using 32-bit pointer offsets (`uint32`).
</Define>

### The Packed Pointer-Length ABI Pattern

Instead of making multiple function calls to return both a result pointer and a length, guest modules pack both 32-bit integers into a single **64-bit integer (`uint64`)**:

```text
64-Bit Return Value:
┌────────────────────────────────┬────────────────────────────────┐
│   Pointer Offset (High 32)     │       Length (Low 32)          │
│   (result >> 32) & 0xFFFFFFFF  │       result & 0xFFFFFFFF      │
└────────────────────────────────┴────────────────────────────────┘
```

The playground can't run wazero, so this program **simulates** the linear-memory ABI with a byte slice standing in for guest memory. The real host, running real WebAssembly, is further down:

<GoPlayground>

```go
package main

import (
	"encoding/binary"
	"errors"
	"fmt"
)

// SimulatedLinearMemory models Wasm 64KB linear memory page.
type SimulatedLinearMemory struct {
	data []byte
	off  uint32
}

func NewSimulatedLinearMemory(pages int) *SimulatedLinearMemory {
	return &SimulatedLinearMemory{
		data: make([]byte, pages*65536),
		off:  1024, // Start past null page
	}
}

// Guest Malloc: Reserves memory inside guest linear buffer
func (m *SimulatedLinearMemory) GuestMalloc(size uint32) uint32 {
	ptr := m.off
	m.off += size
	return ptr
}

// Host Write: Writes input data to guest linear memory
func (m *SimulatedLinearMemory) Write(ptr uint32, b []byte) error {
	if int(ptr)+len(b) > len(m.data) {
		return errors.New("memory out of bounds")
	}
	copy(m.data[ptr:], b)
	return nil
}

// Host Read: Reads output data from guest linear memory
func (m *SimulatedLinearMemory) Read(ptr, length uint32) ([]byte, error) {
	if int(ptr+length) > len(m.data) {
		return nil, errors.New("memory out of bounds")
	}
	res := make([]byte, length)
	copy(res, m.data[ptr:ptr+length])
	return res, nil
}

// PackPtrLen encodes ptr and len into a single 64-bit return integer
func PackPtrLen(ptr, length uint32) uint64 {
	return (uint64(ptr) << 32) | uint64(length)
}

// UnpackPtrLen extracts ptr and len from a packed 64-bit integer
func UnpackPtrLen(val uint64) (uint32, uint32) {
	ptr := uint32(val >> 32)
	length := uint32(val & 0xFFFFFFFF)
	return ptr, length
}

// Simulated Guest Plugin function
func GuestEvaluateRisk(mem *SimulatedLinearMemory, inputPtr, inputLen uint32) uint64 {
	inBytes, _ := mem.Read(inputPtr, inputLen)
	amount := binary.BigEndian.Uint64(inBytes)

	// Business Logic: If amount > $10,000 (1,000,000 cents), flag HIGH RISK
	var riskScore byte = 10 // Low risk
	if amount > 1000000 {
		riskScore = 95 // High risk!
	}

	// Write 1-byte result to new guest memory
	resPtr := mem.GuestMalloc(1)
	mem.Write(resPtr, []byte{riskScore})

	return PackPtrLen(resPtr, 1)
}

func main() {
	mem := NewSimulatedLinearMemory(1) // 1 page (64KB)

	// Step 1: Host prepares $15,000 transaction (1,500,000 cents)
	payload := make([]byte, 8)
	binary.BigEndian.PutUint64(payload, 1500000)

	// Step 2: Host allocates space in guest & writes input
	inputPtr := mem.GuestMalloc(uint32(len(payload)))
	mem.Write(inputPtr, payload)

	// Step 3: Host invokes guest Wasm rule
	packedRes := GuestEvaluateRisk(mem, inputPtr, uint32(len(payload)))

	// Step 4: Host unpacks result pointer & reads risk score
	resPtr, resLen := UnpackPtrLen(packedRes)
	resBytes, err := mem.Read(resPtr, resLen)
	if err != nil {
		panic(err)
	}

	fmt.Printf("Wasm Guest Execution Complete!\n")
	fmt.Printf("Input Ptr: %d, Result Ptr: %d, Risk Score: %d/100\n", inputPtr, resPtr, resBytes[0])
}
```

## Sandboxing Risk & Financial Scripts

When executing user-submitted scripts in production, you must establish four impenetrable defense layers:

<ConceptGrid cols={2}>
  <ConceptCard label="1. Memory Page Capping">
    Limit guest memory to a strict quota (e.g. 16 pages = 1MB). If the script allocates more, the runtime rejects the growth and prevents host out-of-memory crashes.
  </ConceptCard>
  <ConceptCard label="2. Hard Execution Timeouts">
    Pass `context.WithTimeout(ctx, 10*time.Millisecond)` to every guest function invocation. If a script executes an infinite loop (`for {}`), Wazero interrupts the stack machine immediately.
  </ConceptCard>
  <ConceptCard label="3. Zero Ambient System Capabilities">
    Do not mount host directories or network interfaces to the WASI environment unless strictly necessary. Untrusted scripts cannot touch disk or sockets.
  </ConceptCard>
  <ConceptCard label="4. Host Function Injection">

<UnderTheHood title="Wazero JIT Architecture & Stack Machine Safety">
How does Wazero execute WebAssembly code at near-native speed without CGO?
1. **Decoding**: wazero decodes the Wasm binary into its module structure: types, functions, memory, imports and exports.
2. **Intermediate Representation (IR)**: It converts Wasm stack-machine opcodes (`i32.add`, `call_indirect`, `local.get`) into an internal SSA-based IR.
3. **Machine Code Generation**: Wazero's built-in pure-Go assembler emits native CPU instructions (`x86-64` or `ARM64`) directly into an executable memory page allocated via OS `mmap` (`PROT_READ | PROT_WRITE | PROT_EXEC`).
4. **Bounds Checking**: the compiled code checks every memory load and store against the size of the guest's linear memory. An access outside it stops the guest with a trap, which the host sees as an error; the host's memory is never touched.
</UnderTheHood>

<Exercise n={1} title="Safe Linear Memory String Reader" level="easy">

Implement a safe linear memory string extraction helper `ReadMemoryString(mem []byte, ptr, length uint32) (string, error)` that verifies bounds before constructing a zero-copy string.

<Solution>

```go
package main

import (
	"errors"
	"fmt"
	"unsafe"
)

func ReadMemoryString(mem []byte, ptr, length uint32) (string, error) {
	if int(ptr+length) > len(mem) || ptr > uint32(len(mem)) {
		return "", errors.New("memory access out of bounds")
	}
	if length == 0 {
		return "", nil
	}
	return unsafe.String(&mem[ptr], length), nil
}

func main() {
	linearMemory := make([]byte, 65536)
	msg := "MERIDIAN_SETTLEMENT_OK"
	copy(linearMemory[500:], msg)

	str, err := ReadMemoryString(linearMemory, 500, uint32(len(msg)))

		panic(err)
	}
	fmt.Printf("Extracted Memory String: %s\n", str)

	_, err = ReadMemoryString(linearMemory, 65500, 100)
	if err != nil {
		fmt.Printf("Caught Expected Error: %v\n", err)
	}
}
```

<Exercise n={2} title="Packed 64-Bit Pointer-Length ABI Encoder" level="medium">

Write an encoder `PackResult(ptr, length uint32) uint64` and decoder `UnpackResult(val uint64) (uint32, uint32)` that handles arbitrary 32-bit address spaces and validates against edge cases (such as pointer 0 or length 0).

<Solution>

```go
package main

import "fmt"

func PackResult(ptr, length uint32) uint64 {
	return (uint64(ptr) << 32) | uint64(length)
}

func UnpackResult(val uint64) (uint32, uint32) {
	ptr := uint32(val >> 32)
	length := uint32(val & 0xFFFFFFFF)
	return ptr, length
}

func main() {
	originalPtr := uint32(8192)
	originalLen := uint32(256)

	packed := PackResult(originalPtr, originalLen)
	ptr, length := UnpackResult(packed)

	fmt.Printf("Original: Ptr=%d, Len=%d\n", originalPtr, originalLen)
	fmt.Printf("Packed uint64: 0x%X\n", packed)
	fmt.Printf("Unpacked: Ptr=%d, Len=%d\n", ptr, length)

	if ptr == originalPtr && length == originalLen {
		fmt.Println("SUCCESS: Packed ABI Encoding Verified!")
	}
}
```

**Explanation**: High 32 bits store the pointer offset; low 32 bits store the byte slice length. Bitwise shifting and masking provide sub-nanosecond encoding and decoding.
</Solution>
</Exercise>

<Recap>

- **WebAssembly Extensibility**: WebAssembly (Wasm) provides a hermetic, memory-safe, near-native sandbox for executing untrusted user-defined code inside Go systems.
- **WASI Capability Security**: In WASI, guest modules have zero ambient access to the filesystem, network, or OS environment unless explicitly granted by the host.
- **Wazero Pure-Go Engine**: Wazero runs WebAssembly with zero CGO dependencies, compiling bytecode into native machine code directly in Go and supporting all architectures cleanly.
- **Host-Guest Memory ABI**: Because Wasm only accepts and returns numeric values, complex strings and structs are exchanged via linear memory using the packed pointer-length `(ptr << 32) | len` protocol.
- **Sandboxing & Defense-in-Depth**: Always enforce linear memory page limits, context execution timeouts, and strict parameter validation on all exposed host functions.
