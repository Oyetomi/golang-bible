<HeroCard label="Appendix · The Response Envelope" title="HTTP Response Headers You Must Get Right">

Here's the thing, sport. When your Go handler calls `fmt.Fprint(w, "...")`, you think you sent a *page*. You didn't. You sent a **page wrapped in instructions** — a stack of `Name: value` lines that tell the browser and **every cache between you and the user** what to do with that page: how long to keep it, who's allowed to see the copy, whether scripts may run, whether the cookie rides along on the next request. Get the page right and the *instructions* wrong, and you leak a user's data into a shared cache, you hand an XSS payload a place to run, you let another site frame your bank page. The body is the easy part. The envelope is where the security lives.

This chapter teaches the envelope from **zero** — no assumed knowledge of any of these headers. We'll start at "what even is a header" and how Go's `net/http` reads and writes them, then build the three families that matter most: **caching** (the `Cache-Control` vocabulary, revalidation, `Vary`), **cookies** (`Set-Cookie` and every attribute), and the **security headers** Go ships *none* of by default. Every single behavior here was **measured against `go1.24`** — printed off a real connection, not recalled from memory — because the whole point of headers is that the machine does *exactly* what the bytes say, and the only way to know what the bytes say is to make the machine show you. Let's read the envelope, sport.

## What a Header Is

Forget Go for one paragraph. An HTTP response is **text on a wire**, in a fixed shape: a status line, then a block of headers, then a blank line, then the body.

<Define term="HTTP header">
An **HTTP header** is a single `Name: value` line of metadata attached to a request or response, sitting *before* the body. The response from a server looks literally like this on the wire:

```text
HTTP/1.1 200 OK            ← status line
Content-Type: text/html    ← a header
Cache-Control: no-store    ← a header
Set-Cookie: session=abc     ← a header
                           ← blank line: headers end here
<html>…</html>             ← the body
```

The **body** is the content (the HTML, the JSON). The **headers** are instructions *about* that content — its type, how long it may be cached, what cookies to store, what security rules apply. A **request header** (sent by the browser) and a **response header** (sent by the server) are the same shape; this chapter is about the *response* headers your Go server emits, because those are the ones that carry your security decisions. Header **names are case-insensitive** (`Content-Type` and `content-type` are the same header); a single header name can carry **multiple values** (you can send two `Set-Cookie` lines, or one `Vary` with several entries).
</Define>

### How Go reads and writes headers

In Go, the response headers live in `w.Header()`, which is an `http.Header` — and an `http.Header` is just a **`map[string][]string`** (a map from a header name to a *list* of values, because a header can repeat). Three methods do almost everything: **`Set`** replaces, **`Add`** appends another value, **`Get`** reads the first value, **`Values`** reads them all. And Go **canonicalizes** the name for you — `content-type` is stored and sent as `Content-Type`.

### The one ordering rule: headers before the body

Here's the rule that trips up everyone once: **you must set every header before you write the status line or any body byte.** The moment you call `w.WriteHeader(code)` — or the first `w.Write`/`fmt.Fprint`, which calls `WriteHeader(200)` for you — Go **serializes the header block onto the wire**. Anything you set *after* that is too late: the bytes are already gone.

<Gotcha>
**`httptest.ResponseRecorder` will lie to you about this.** Run the exact same handler against a `ResponseRecorder` instead of a real connection and `X-After` shows up as `"lost"` — *present* — because the Recorder is an in-memory fake that keeps a live reference to the header map and never actually serializes at `WriteHeader`. So a unit test using a Recorder can pass while the real server drops the header. When a header's *timing* matters, test it against `httptest.NewServer` (a real connection over loopback), not a bare Recorder. This is the same lesson as the rest of the Bible's testing material: a fake that's too forgiving hides the bug you're testing for.
</Gotcha>

## The Caching Family

A **cache** is any box between your server and the user that keeps a copy of a response so the next request can be answered without bothering your server. There are two kinds, and the difference is the whole security story.

<Define term="Private cache vs shared cache">
A **private cache** belongs to *one user* — the browser's own on-disk cache. A copy stored there is only ever served back to that same person, so caching their account page there is harmless. A **shared cache** sits in front of *many* users — a CDN edge node, a reverse proxy, a corporate proxy — and serves one stored copy to *whoever* asks for that URL next. Caching a user-specific page in a **shared** cache is the dangerous case: the next visitor gets the previous user's data (that's web cache deception, ch32). The caching headers exist to tell each kind of cache, precisely, *whether* it may store a response and *for how long* — and several directives target the shared cache specifically.
</Define>

### The `Cache-Control` vocabulary

`Cache-Control` is the master switch, and it's a comma-separated list of **directives**. Here's the full working vocabulary — read it as "what each word tells a cache to do":

| directive | what it tells caches |
|---|---|
| `no-store` | **Never store this, anywhere.** The strongest. Use on every authenticated/sensitive response. |
| `private` | Browsers may cache it; **shared caches (CDN/proxy) must NOT.** The targeted fix for cache deception. |
| `no-cache` | May be stored, but **must revalidate with the origin before each reuse** (a 304 check). A misnomer — it means "always re-check," not "don't cache." |
| `public` | Explicitly cacheable by shared caches, **even** for responses they'd normally skip (e.g. ones with `Authorization`). |
| `max-age=N` | Fresh for **N seconds**; after that it's stale and must be revalidated or refetched. |
| `s-maxage=N` | Like `max-age` but **for shared caches only**, and it overrides `max-age` there. |
| `must-revalidate` | Once stale, a cache **may not** serve the stale copy on a whim (e.g. during an origin outage) — it must revalidate. |
| `stale-while-revalidate=N` | May serve a stale copy for up to N seconds **while** fetching a fresh one in the background. Hides latency. |
| `immutable` | This won't change during its freshness lifetime, so the browser **won't even revalidate** on a reload. For fingerprinted static assets. |

Two combinations cover most real needs. For an **authenticated page**: `Cache-Control: no-store` (or `private, no-cache` as a belt-and-suspenders) — nothing sensitive should sit in a shared cache. For a **fingerprinted static asset** (`app.9f3a1c.js`): `Cache-Control: public, max-age=31536000, immutable` — cache it for a year, because a new build gets a new filename anyway.

<Callout kind="note" title="Cache-Control vs the old Expires header">
Before `Cache-Control` there was **`Expires`**, an absolute date (`Expires: Wed, 21 Oct 2026 07:28:00 GMT`) saying when a response goes stale. It still works and you'll see it, but it's clock-dependent (server and cache must agree on time) and coarse. `Cache-Control: max-age=N` is the modern, relative form and **wins** when both are present. Reach for `Cache-Control`; treat `Expires` as legacy.
</Callout>

### Revalidation: `ETag` / `If-None-Match` and the 304

"Stale" doesn't mean "throw it away" — it means "check if it's still good." That check is a **conditional request**, and it's how a cache avoids re-downloading something that hasn't changed.

<Define term="Conditional request (ETag / If-None-Match → 304)">
An **`ETag`** ("entity tag") is a short fingerprint the server attaches to a response — change the content, change the ETag. When a cache holds a copy and wants to know if it's still current, it sends the fingerprint back in an **`If-None-Match`** request header: *"I have the version tagged `"v1"` — is that still right?"* If it is, the server replies **`304 Not Modified`** with **no body** — a tiny response that says "your copy is fine, keep it." If it's changed, the server sends `200` with the new body and a new ETag. The sibling pair is **`Last-Modified`** (a timestamp) and **`If-Modified-Since`**. Either way, revalidation turns "this is stale" into a cheap round-trip instead of a full re-download. In Go, `http.ServeContent` and `http.ServeFile` implement the whole conditional dance for you.
</Define>

### `Vary`: telling caches what changes the response

A cache stores a response under a **key** — by default just the method and URL. But what if the *same* URL returns different bytes depending on a request header (gzip vs plain, English vs French, logged-in vs not)? Then a single key isn't enough, and `Vary` is how you say so.

<Define term="Vary">
The **`Vary`** response header lists the **request headers that change this response**, so a cache adds them to its key instead of serving one variant to everyone. `Vary: Accept-Encoding` says "the gzipped and plain versions are different — key on the client's `Accept-Encoding`." `Vary: Cookie` says "this response depends on the cookie, so don't share it across users." Omitting `Vary` when a response *does* depend on a request header is precisely the mistake behind **web cache poisoning** (an unkeyed header gets reflected and cached for everyone) and contributes to **deception** (a per-user page shared across users). The rule: if a request header changes the bytes, either name it in `Vary` or don't let it change a *cacheable* response at all.
</Define>

<Gotcha>
**Go's file helpers set `ETag`/`Last-Modified` but never set `Cache-Control` for you.** `http.ServeContent`/`http.ServeFile`/`http.FileServer` give you correct *revalidation* (the 304 dance above) out of the box, but they do **not** decide cacheability — there's no `Cache-Control` on their responses unless you add one. So a static file server with no extra config will make browsers revalidate on every load (a request per asset) instead of serving from cache for an hour. If you want assets actually cached, set `Cache-Control: public, max-age=...` yourself (typically in a wrapping handler). Conversely, if you serve anything sensitive through a file helper, *you* must add `no-store` — the helper won't.
</Gotcha>

## The Cookie Family

A **cookie** is a small named value the server tells the browser to store and **send back automatically** on every subsequent request to that site. It's how a stateless protocol remembers who you are between requests — and because the browser attaches it *automatically*, every one of its attributes is a security decision.

<Define term="Cookie / Set-Cookie">
A server sets a cookie with a **`Set-Cookie`** response header (`Set-Cookie: session=abc; HttpOnly; Secure`); the browser stores `session=abc` and, from then on, **automatically** includes `Cookie: session=abc` on requests back to that site. That automatic attachment is the cookie's superpower (seamless sessions) and its danger (the browser sends it even on requests *another site* triggered — the root of CSRF, and the cookie ride-along behind web cache deception). The attributes after the value are the controls: who may read it (`HttpOnly`), over what transport (`Secure`), on which cross-site requests it rides (`SameSite`), its scope (`Path`, `Domain`), and its lifetime (`Max-Age`/`Expires`). In Go a cookie is the `http.Cookie` struct, written with `http.SetCookie(w, c)` and read with `r.Cookie("name")`.
</Define>

### The attribute vocabulary

| attribute | what it controls |
|---|---|
| `Secure` | The cookie is **only sent over HTTPS** — never plaintext HTTP. Mandatory for anything sensitive. |
| `HttpOnly` | **JavaScript cannot read it** (`document.cookie` won't show it) — so an XSS payload can't steal the session. |
| `SameSite=Strict` | **Never** sent on a cross-site request, even a top-level link click. The strongest anti-CSRF / anti-deception value. |
| `SameSite=Lax` | Sent on **top-level GET navigations** but not cross-site `POST`/`fetch`/subresources. The browser's default when no `SameSite` is given. |
| `SameSite=None` | Sent on **all** cross-site requests — **requires `Secure`**. Only for cookies that truly must work third-party. |
| `Path=/x` | Only sent for request paths under `/x`. A scope limiter, not a security boundary. |
| `Domain=...` | Which host(s) the cookie is sent to. Omit it to scope to the exact host (the safer default). |
| `Max-Age=N` / `Expires=date` | Lifetime. `Max-Age` is seconds-from-now (modern); `Expires` is an absolute date (legacy). `Max-Age` wins if both are set. |

The hardened session cookie that the auth chapter (ch20) builds is just these turned to their safe positions: `Secure`, `HttpOnly`, `SameSite=Strict`. The **`__Host-` name prefix** (`Set-Cookie: __Host-session=...`) is a browser-enforced bonus — a cookie whose *name* starts with `__Host-` is only accepted if it's `Secure`, has `Path=/`, and has **no** `Domain`, which pins it to the exact origin and blocks a class of subdomain-injection attacks.

```text
SameSiteStrictMode     (int=3) → "session=abc; HttpOnly; Secure; SameSite=Strict"
SameSiteNoneMode       (int=4) → "session=abc; HttpOnly; Secure; SameSite=None"
```

If you want `Strict`, you must write `SameSite: http.SameSiteStrictMode` explicitly. Leaving the field at its zero value is *not* a safe default — it's the absence of a decision.
</Gotcha>

## Security Headers

Now the family with the bluntest rule of all: **Go sets none of these for you.** There is no middleware on by default, no secure baseline — if you don't emit a Content-Security-Policy, your response simply doesn't have one. Each of these headers is a one-line instruction that switches on a specific browser protection.

<ConceptGrid cols={2}>
  <ConceptCard label="Content-Security-Policy (CSP)">An allowlist of where scripts/styles/images may load from. `default-src 'self'` says "only load resources from my own origin." This is the **strongest defense against XSS**: even if an attacker injects a `<script>`, the browser refuses to run inline or off-origin code the policy doesn't permit. The single most valuable header here.</ConceptCard>
  <ConceptCard label="Strict-Transport-Security (HSTS)">`max-age=31536000; includeSubDomains` tells the browser "for the next year, only ever reach me over HTTPS — never plaintext, no exceptions." Defeats **SSL-stripping** (an attacker downgrading the first request to HTTP). Only emit it once HTTPS is solid everywhere; it's sticky.</ConceptCard>
  <ConceptCard label="X-Content-Type-Options: nosniff">Tells the browser **stop guessing the content type** — trust my `Content-Type` exactly. Without it, a browser may "sniff" a response that *says* `text/plain` but *looks* like HTML and run it as HTML — turning a file upload or a JSON endpoint into stored XSS. One value, always: `nosniff`.</ConceptCard>
  <ConceptCard label="X-Frame-Options / CSP frame-ancestors">`X-Frame-Options: DENY` (or the modern `Content-Security-Policy: frame-ancestors 'none'`) stops other sites from putting your page in an `<iframe>`. Defeats **clickjacking** — an attacker framing your bank's transfer page invisibly under a decoy button.</ConceptCard>
  <ConceptCard label="Referrer-Policy">Controls how much of the current URL is sent in the `Referer` header when the user clicks away. `no-referrer` or `strict-origin-when-cross-origin` stops you **leaking path/query secrets** (a password-reset token in the URL) to third-party sites the user navigates to.</ConceptCard>
  <ConceptCard label="Permissions-Policy">An allow/deny list for powerful browser features — camera, microphone, geolocation, etc. `Permissions-Policy: camera=(), microphone=()` switches off features your app doesn't use, shrinking what an injected script (or an embedded third party) could ask the browser to do.</ConceptCard>
</ConceptGrid>

```go
package main

import (
	"fmt"
	"net/http"
	"net/http/httptest"
)

// secureHeaders wraps any handler and adds the baseline security headers Go
// does NOT set for you. Order: set headers, THEN call the inner handler
// (which writes status+body) — so the headers are in place before WriteHeader.
func secureHeaders(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		h := w.Header()
		h.Set("Content-Security-Policy", "default-src 'self'")
		h.Set("Strict-Transport-Security", "max-age=31536000; includeSubDomains")
		h.Set("X-Content-Type-Options", "nosniff")
		h.Set("X-Frame-Options", "DENY")
		h.Set("Referrer-Policy", "no-referrer")
		next.ServeHTTP(w, r)
	})
}

// account is an AUTHENTICATED page: per-user data + a token in the body.
// It marks itself non-cacheable so no shared cache can store it (WCD fix).
func account(w http.ResponseWriter, r *http.Request) {
	w.Header().Set("Cache-Control", "no-store")
	http.SetCookie(w, &http.Cookie{
		Name: "session", Value: "opaque", Path: "/",
		Secure: true, HttpOnly: true, SameSite: http.SameSiteStrictMode,
	})
	fmt.Fprint(w, `<script>var token="eyJ.user"</script>`)
}

func main() {
	srv := httptest.NewServer(secureHeaders(http.HandlerFunc(account)))
	defer srv.Close()
	resp, _ := http.Get(srv.URL)
	for _, k := range []string{
		"Cache-Control", "Content-Security-Policy", "Strict-Transport-Security",
		"X-Content-Type-Options", "X-Frame-Options", "Referrer-Policy", "Set-Cookie",
	} {
		fmt.Printf("%-27s %s\n", k+":", resp.Header.Get(k))
	}
}
```

## How They Interlock

None of these families is the *whole* defense for any one attack — the attacks live in the gaps *between* them. This is the chapter's payoff: read an attack as "which header was missing."

<ConceptGrid cols={2}>
  <ConceptCard label="Web cache deception → caching + cookie">A per-user page leaks because it was **cacheable** (no `Cache-Control: no-store`/`private`) *and* its cookie was sendable cross-site (`SameSite=Lax`, the default). Two missing instructions from two different families. Fix either: `no-store` on the response, or `SameSite=Strict` on the cookie. (ch32)</ConceptCard>
  <ConceptCard label="Web cache poisoning → caching">An unkeyed request header gets reflected into a **cacheable** response and served to everyone. The missing instruction is `Vary` (key on it) — or better, don't reflect request input into a cacheable response at all. (ch32)</ConceptCard>
  <ConceptCard label="CSRF → cookie">A forged cross-site request rides the browser's automatic cookie attachment. The defending instruction is `SameSite=Strict`/`Lax` on the session cookie (plus Go 1.25+ `CrossOriginProtection`). Header-based `Authorization: Bearer` auth has no ambient cookie, so it's largely immune. (ch20)</ConceptCard>
  <ConceptCard label="XSS → cookie + security header">Two layers: `HttpOnly` stops an injected script *reading* the session cookie, and **CSP** stops the injected script *running* in the first place. Defense in depth across the cookie and security-header families. (ch14 / ch20)</ConceptCard>
  <ConceptCard label="Clickjacking → security header">Your page gets framed invisibly under a decoy UI. The single missing instruction is `X-Frame-Options: DENY` (or CSP `frame-ancestors 'none'`).</ConceptCard>
  <ConceptCard label="MIME-sniffing XSS → security header">A response the browser *guesses* is HTML gets executed as HTML. The missing instruction is `X-Content-Type-Options: nosniff` — plus an explicit, correct `Content-Type` so there's nothing to guess.</ConceptCard>
</ConceptGrid>

## Defaults & Gotchas

The catalog — the things that bite precisely because Go is quiet about them.

<ConceptGrid cols={2}>
  <ConceptCard label="No secure defaults">Go emits `Content-Type`, `Content-Length`, `Date` — and nothing else. No `Cache-Control`, no security headers, not even a `Server` header. Every protective instruction is opt-in. Centralize them in middleware so "on" is the default.</ConceptCard>
  <ConceptCard label="Headers before the body">`WriteHeader` (or the first `Write`) commits the header block. Anything `Set` after that is silently dropped on a real connection. Set all headers first; in middleware, set then call `next`.</ConceptCard>
  <ConceptCard label="ResponseRecorder hides the ordering bug">A `ResponseRecorder` keeps a live header-map reference and never serializes, so a header set *after* `WriteHeader` still shows up in a Recorder test — masking a bug a real connection would expose. Test header timing against `httptest.NewServer`.</ConceptCard>
  <ConceptCard label="Sniffing fills Content-Type">Don't set `Content-Type` and Go guesses it with `http.DetectContentType`. Convenient, but a guess — set it explicitly and pair it with `nosniff` so the browser doesn't guess either.</ConceptCard>
  <ConceptCard label="File helpers set no Cache-Control">`ServeContent`/`ServeFile`/`FileServer` give you `ETag`/304 revalidation but never `Cache-Control`. Add `public, max-age=...` for assets you want cached — and `no-store` for anything sensitive you serve through them.</ConceptCard>
  <ConceptCard label="Unset SameSite ≠ Strict">The zero-value `SameSite` (and `SameSiteDefaultMode`) emit no attribute, so the browser uses its own default (`Lax`). For top-level-navigation protection you must set `SameSiteStrictMode` explicitly.</ConceptCard>
  <ConceptCard label="Set vs Add for repeatable headers">`Set` replaces; `Add` appends. For headers that legitimately repeat — `Set-Cookie`, `Vary` — use `Add` (or `http.SetCookie`, which appends). Reading them back, prefer `Values` over `Get` so you don't drop all but the first.</ConceptCard>
  <ConceptCard label="no-cache is not no-store">`no-cache` means "store but always revalidate"; `no-store` means "never store." For sensitive data you want `no-store`. Confusing the two leaves a copy in the cache that a `304` will happily keep serving.</ConceptCard>
</ConceptGrid>

<UnderTheHood title="Header Canonicalization & Security Header Enforcement">

Understanding how Go serializes HTTP response headers into TCP socket buffers and manages canonical key lookup tables prevents silent header loss and security bypasses.

### 1. Key Canonicalization in `net/textproto` (Go 1.22+)

When you invoke `w.Header().Set("x-custom-key", "value")`, Go converts the header key using `textproto.CanonicalMIMEHeaderKey`:

- **The Canonicalization Algorithm:** The algorithm capitalizes the first letter and any letter following a hyphen (`-`), converting all other ASCII characters to lowercase (e.g. `content-security-policy` $\to$ `Content-Security-Policy`).
- **Direct Map Access Hazard:** Because `http.Header` is defined as `type Header map[string][]string`, indexing the map directly via `h["content-type"]` fails if the key was stored under its canonicalized form `h["Content-Type"]`. Always use `h.Get()`, `h.Set()`, or `h.Values()`, which normalize keys through `CanonicalMIMEHeaderKey` automatically.

### 2. Header Lifecycle and `response.wroteHeader`

Inside Go's standard library (`net/http/server.go`):

```go
type response struct {
    conn             *conn
    req              *Request
    wroteHeader      bool
    header           Header
    status           int
    ...
}
```

- **The Commit Point:** When `w.WriteHeader(code)` or the first `w.Write(bytes)` executes, Go inspects `w.wroteHeader`. If `false`, it marks `wroteHeader = true`, writes the status line (`HTTP/1.1 200 OK\r\n`), formats the header map into `response.bufw` (`*bufio.Writer`), and appends the trailing CRLF (`\r\n\r\n`).
- **Post-Commit Silent Drop:** If subsequent application code or deferred middleware calls `w.Header().Set("X-Security", "true")`, Go modifies the in-memory map, but `response.Write` never re-serializes headers. The added headers are completely invisible on the wire.

### 3. Dynamic CSP Nonce Generation & HSTS Preloading

- **Cryptographic CSP Nonces:** Static CSP policies often struggle with inline analytics or hydration scripts. Secure Go servers mint dynamic single-use 128-bit cryptographic nonces per request via `crypto/rand`, inject them into the response context, and attach `Content-Security-Policy: script-src 'nonce-<base64>' 'strict-dynamic'`.
- **HSTS Preload Standards:** Strict-Transport-Security requires `max-age=63072000; includeSubDomains; preload` (2 years) to qualify for Chrome and Mozilla's hardcoded browser HSTS preload list, ensuring clients never attempt an initial unencrypted HTTP connection.

</UnderTheHood>

```go
package main

import (
	"fmt"
	"strings"
)

func CanonicalMIMEHeaderKey(s string) string {
	parts := strings.Split(s, "-")
	for i, p := range parts {
		if len(p) == 0 {
			continue
		}
		parts[i] = strings.ToUpper(p[:1]) + strings.ToLower(p[1:])
	}
	return strings.Join(parts, "-")
}

func main() {
	fmt.Println(CanonicalMIMEHeaderKey("content-type"))             // Content-Type
	fmt.Println(CanonicalMIMEHeaderKey("x-content-type-options"))   // X-Content-Type-Options
	fmt.Println(CanonicalMIMEHeaderKey("STRICT-TRANSPORT-SECURITY")) // Strict-Transport-Security
}
```

<Exercise n={3} title="Generate Dynamic CSP Nonce" level="medium">

```go
package main

import (
	"crypto/rand"
	"encoding/base64"
	"fmt"
)

func GenerateCSPHeader() (csp string, nonce string, err error) {
	b := make([]byte, 16)
	if _, err := rand.Read(b); err != nil {
		return "", "", fmt.Errorf("crypto/rand error: %w", err)
	}
	nonce = base64.StdEncoding.EncodeToString(b)
	csp = fmt.Sprintf("default-src 'self'; script-src 'self' 'nonce-%s' 'strict-dynamic'; object-src 'none'", nonce)
	return csp, nonce, nil
}

	if err != nil {
		panic(err)
	}
	fmt.Println("Nonce: ", nonce)
	fmt.Println("CSP:   ", csp)
}
```

<Recap>

- An HTTP response is a **body wrapped in headers** — `Name: value` instruction lines that tell the browser and every cache what to do with it. In Go they live in `w.Header()`, a `map[string][]string`: **`Set`** replaces, **`Add`** appends, **`Get`** reads the first, **`Values`** reads all, and names are **canonicalized** for you.
- **Set every header before the body.** `WriteHeader` (or the first `Write`) commits the header block; a header set afterward is silently dropped on a real connection — and a `ResponseRecorder` will *hide* that bug because it never serializes.
- **Go has no secure defaults.** A bare handler emits only `Content-Type` (sniffed), `Content-Length`, and `Date`. Every caching rule, cookie attribute, and security header is yours to add.
- **Caching family:** `Cache-Control` is the master switch — `no-store` (never store), `private` (no shared caches), `no-cache` (store but revalidate), `max-age`/`s-maxage` (freshness), `immutable`/`stale-while-revalidate` (tuning). `ETag` + `If-None-Match` give cheap **304** revalidation (Go's `ServeContent` does it), and **`Vary`** tells caches which request headers change the response.
- **Cookie family:** `Set-Cookie` plus attributes — `Secure` (HTTPS only), `HttpOnly` (no JS), `SameSite=Strict/Lax/None` (cross-site sending), `Path`/`Domain` (scope), `Max-Age` (lifetime), and the `__Host-` prefix. In Go it's the `http.Cookie` struct; **an unset `SameSite` is `Lax`, not `Strict`** — set it explicitly.
- **Security headers — Go sets none:** CSP (XSS), HSTS (SSL-strip), `nosniff` (MIME-sniff XSS), `X-Frame-Options`/`frame-ancestors` (clickjacking), `Referrer-Policy` (URL-secret leak), `Permissions-Policy` (feature lockdown). Set them once in a `secureHeaders` middleware.
- **The attacks are missing instructions:** deception = cacheable + `Lax`; poisoning = no `Vary`; CSRF = no `SameSite`; XSS = no `HttpOnly`/CSP; clickjacking = no `X-Frame-Options`. Read a bug as "which header wasn't there."

</Recap>

The skill that ties it together is the one this chapter was built on — don't trust your memory of what a header does, **make the machine print it**. `go run` a ten-line handler, read the bytes off the wire, and you'll never wonder again whether the cookie said `Strict` or the page said `no-store`. Go set your headers, sport.
