## The OpenTelemetry Collector Pipeline

Consider the reality of a modern financial architecture like Meridian Financial. Meridian operates eighty microservices across three Kubernetes clusters handling deposit verification, card authorizations, real-time fraud scoring, and ACH settlement. Every incoming HTTP request or gRPC call generates an OpenTelemetry trace context. Spans fan out across twenty downstream RPC hops.

During a routine payment service rollout, an application developer attempts to debug a intermittent authorization failure. To inspect the payload, they inject the raw incoming request map into the active OpenTelemetry span:

```go
// The catastrophic developer shortcut:
span.SetAttributes(
    attribute.String("payment.pan", req.CardNumber),
    attribute.String("payment.cvv", req.CVV),
    attribute.String("bank.routing_number", req.RoutingNumber),
    attribute.Float64("payment.amount", req.AmountUSD),
)
```

If those spans are transmitted directly from the microservice to a commercial cloud observability vendor (such as Datadog, Honeycomb, or Grafana Cloud), Meridian has committed a critical breach of **PCI-DSS Requirement 3.4** (rendering Primary Account Numbers unreadable anywhere they are stored or transmitted) and **Gramm-Leach-Bliley Act (GLBA)** privacy controls. Fines start at $100,000 per month, merchant processing privileges are revoked, and the engineering director spends the next quarter testifying before regulatory commissions.

You cannot rely on eighty separate development teams to never make a logging mistake. You need an architectural firewall. You need the OpenTelemetry Collector.

<Define term="OpenTelemetry Collector" since="Observability & Telemetry Pipelines (Appendix, ch53)">
A high-performance, vendor-agnostic proxy service deployed as a sidecar or centralized gateway that receives, processes, filters, transforms, batches, and exports telemetry data (traces, metrics, logs) across heterogeneous distributed systems.
</Define>

<Define term="Telemetry Pipeline" since="Observability & Telemetry Pipelines (Appendix, ch53)">
A directed acyclic processing graph inside the OpenTelemetry Collector consisting of one or more Receivers, a sequential chain of Processors, and one or more Exporters dedicated to a specific telemetry signal type (traces, metrics, or logs).
</Define>

<Define term="Receiver" since="Observability & Telemetry Pipelines (Appendix, ch53)">
An ingestion component at the entrance of a collector pipeline that accepts telemetry data via push protocols (such as OTLP/gRPC on port 4317 or OTLP/HTTP on port 4318) or pull scrapers (such as Prometheus HTTP scrape targets).
</Define>

<Define term="Processor" since="Observability & Telemetry Pipelines (Appendix, ch53)">
An in-memory transformation node in a telemetry pipeline that inspects, mutates, filters, samples, or aggregates batches of data before passing them downstream. Processors run sequentially in the exact order defined in configuration.
</Define>

<Define term="Exporter" since="Observability & Telemetry Pipelines (Appendix, ch53)">
An egress component at the termination of a collector pipeline that translates internal telemetry representations into target backend protocols (such as OTLP, Jaeger, Prometheus, or Kafka) and transmits them over network connections.
</Define>

<Define term="Connector" since="Observability & Telemetry Pipelines (Appendix, ch53)">
An hybrid pipeline component that joins two distinct telemetry pipelines, acting simultaneously as an exporter for one signal (e.g. traces) and a receiver for another signal (e.g. generating count and duration metrics from spans via the spanmetrics connector).
</Define>

### Pipeline Configuration Architecture

The OpenTelemetry Collector is configured via YAML, but every YAML block directly models concrete Go structs and interfaces instantiated by the Collector service engine:

```yaml
receivers:
  otlp:
    protocols:
      grpc:
        endpoint: 0.0.0.0:4317
      http:
        endpoint: 0.0.0.0:4318

processors:
  memory_limiter:
    check_interval: 250ms
    limit_percentage: 80
    spike_limit_percentage: 20

  meridian_pii_redactor:
    mask_character: "*"
    redact_pan: true
    redact_cvv: true
    redact_routing: true

  batch:
    send_batch_size: 8192
    timeout: 200ms
    send_batch_max_size: 10240

exporters:
  otlp/clickhouse:
    endpoint: clickhouse.internal.meridian.bank:4317
    tls:
      insecure: false
      ca_file: /etc/ssl/certs/meridian-internal-ca.pem

service:
  pipelines:
    traces:
      receivers: [otlp]
      processors: [memory_limiter, meridian_pii_redactor, batch]
      exporters: [otlp/clickhouse]
```

Notice the critical ordering under `service.pipelines.traces.processors`:
1. `memory_limiter` **must come first**. If the Collector process is facing memory starvation, you must drop or reject incoming data before spending CPU cycles and memory buffers parsing attributes or queuing batches.
2. `meridian_pii_redactor` comes next. Telemetry must be sanitized **before** entering batch buffers or queue storage.
3. `batch` comes immediately before exporters. Batching aggregates thousands of individual small spans into large contiguous payloads, drastically reducing network syscalls and TLS handshake overhead on egress connections.

## Building a Custom Go Processor

To build custom telemetry logic into the OpenTelemetry Collector, you write a Go module that implements the Collector's component interfaces and compile it using the OpenTelemetry Collector Builder (`ocb`) or as a native Go binary.

### The Component Model

Every component in the Collector implements the fundamental lifecycle interface:

```go
type Component interface {
    // Start is called during collector boot, passing the Host interface
    // for discovering other extensions or report telemetry.
    Start(ctx context.Context, host component.Host) error

    // Shutdown is called during graceful termination to flush buffers
    // and release OS resources (sockets, worker pools, goroutines).
    Shutdown(ctx context.Context) error
}
```

For trace processing, your custom processor must implement `processor.Traces`, which extends `Component` and `consumer.Traces`:

```go
type Traces interface {
    Component
    consumer.Traces
}

type TracesConsumer interface {
    // ConsumeTraces receives a batch of traces, mutates or filters them,
    // and forwards them to the next consumer in the pipeline.
    ConsumeTraces(ctx context.Context, td ptrace.Traces) error

    // Capabilities reports whether the processor mutates data in-place.
    Capabilities() consumer.Capabilities
}
```

<Define term="Pdata" since="Observability & Telemetry Pipelines (Appendix, ch53)">
The high-performance internal data model (`go.opentelemetry.io/collector/pdata`) used by the OpenTelemetry Collector. Unlike standard Protobuf structs, pdata provides zero-copy accessors, pooled memory allocation, and value-type wrappers for traces, metrics, and logs.
</Define>

<Define term="Span Attribute" since="Observability & Telemetry Pipelines (Appendix, ch53)">
A key-value pair attached to an OpenTelemetry span representing structured contextual metadata (e.g., `http.status_code: 200`, `user.id: "usr_429"`). In pdata, attributes are stored within a specialized `pcommon.Map` optimized for zero-allocation mutations.
</Define>

<UnderTheHood title="OTel Pdata Memory Layout, Zero-Alloc Mutators & Goroutine Worker Pools">

Why does the OpenTelemetry Collector maintain its own data layer (`pdata`) instead of directly passing standard generated Google Protobuf Go structs (`pb.TracesData`) through the pipeline?

In standard Google Protobuf generated Go code, every field is represented as a pointer to a struct or an interface. A single `Span` struct contains dozens of individual pointers: `*Resource`, `*InstrumentationScope`, `*Status`, and a slice of pointers to `*KeyValue` attribute structs:

```
Standard Protobuf (Pointer Spaghetti):
[ResourceSpans] ---> [*Resource] ---> [*Attributes Slice] ---> [*KeyValue] -> [*Value]
                ---> [*ScopeSpans] ---> [*Span] ---> [*Attributes Slice] ---> [*KeyValue]
```

At 100,000 spans per second, decoding standard Protobuf structures allocates millions of tiny objects on the Go heap every second. The Go runtime Garbage Collector spends all its time tracing object pointers, running mutator Mark Assist, and freezing threads.

The OpenTelemetry project engineered `pdata` to solve this exact bottleneck. `pdata` structs (`ptrace.Traces`, `ptrace.ResourceSpans`, `ptrace.Span`, `pcommon.Map`) are **value wrappers** around flat internal memory buffers. When you pass `ptrace.Span` by value, you are passing a lightweight 16-byte header consisting of an internal pointer to a shared buffer and an index:

```
pdata Zero-Copy Layout:
[ptrace.Traces (Header: 16 bytes)]
   │
   ▼
[Internal Flat Slices & String Buffers (Contiguous Memory)]
   ├── Resource 0 (Pre-allocated slice slot)
   │     └── Attribute Map (Flat array of Key-Value pairs)
   └── Span 0...N (Contiguous array of span descriptors)
```

When you mutate an attribute using `pdata`:
```go
span.Attributes().PutStr("payment.pan", maskedString)
```
The internal map checks if the key already exists in its pre-allocated array. If it exists, it overwrites the underlying value representation directly without allocating a new map node or pointer header!

### Concurrency & Worker Pools

The Collector pipeline utilizes an asynchronous fan-in / fan-out execution model. Receivers spawn goroutines that parse incoming network packets (gRPC HTTP/2 streams or HTTP/1.1 POSTs). The receiver calls `processor.ConsumeTraces(ctx, td)`.

If your custom processor launches an unconstrained goroutine per span (`go processSpan(span)`), you will flood the Go runtime scheduler with 100,000 runnable goroutines per second. In Go 1.25+, the runtime automatically sets `GOMAXPROCS` to match container CPU quotas (cgroup limits) via `runtime.SetDefaultGOMAXPROCS`. Spawning hundreds of thousands of goroutines induces devastating context-switch churn.

Instead, a production custom processor executes in one of two ways:
1. **Synchronous in-place mutation on the caller's goroutine**: Since the receiver already allocated a goroutine to read the connection, mutating `ptrace.Traces` directly on that goroutine requires **zero channel sends, zero synchronization locks, and zero scheduler overhead**.
2. **Fixed worker pool with bounded ring buffers**: For CPU-heavy transformations or cryptographic hashing, the processor dispatches batches into pre-sized channel buffers consumed by a static pool of `runtime.GOMAXPROCS(0)` worker goroutines.

Combined with the **Green Tea GC** default introduced in Go 1.26, maintaining zero-allocation mutations in `ConsumeTraces` ensures that minor garbage collection pauses stay strictly under 100 microseconds, even under sustained line-rate saturation.

</UnderTheHood>

### Implementing the Custom Processor Factory

In the OpenTelemetry Collector framework, every component exposes a `Factory` that registers its configuration type and instantiates components. Here is how a custom processor factory is wired:

```go
package redactorprocessor

import (
	"context"
	"errors"

	"go.opentelemetry.io/collector/component"
	"go.opentelemetry.io/collector/consumer"
	"go.opentelemetry.io/collector/processor"
)

var (
	typeStr = component.MustNewType("meridian_pii_redactor")
)

type Config struct {
	MaskCharacter string `mapstructure:"mask_character"`
	RedactPAN     bool   `mapstructure:"redact_pan"`
	RedactCVV     bool   `mapstructure:"redact_cvv"`
	RedactRouting bool   `mapstructure:"redact_routing"`
}

func (cfg *Config) Validate() error {
	if len(cfg.MaskCharacter) != 1 {
		return errors.New("mask_character must be exactly one ASCII character (e.g. '*')")
	}
	return nil
}

func NewFactory() processor.Factory {
	return processor.NewFactory(
		typeStr,
		createDefaultConfig,
		processor.WithTraces(createTracesProcessor, component.StabilityLevelBeta),
	)
}

func createDefaultConfig() component.Config {
	return &Config{
		MaskCharacter: "*",
		RedactPAN:     true,
		RedactCVV:     true,
		RedactRouting: true,
	}
}

func createTracesProcessor(
	ctx context.Context,
	set processor.Settings,
	cfg component.Config,
	nextConsumer consumer.Traces,
) (processor.Traces, error) {
	oCfg := cfg.(*Config)
	return newRedactorProcessor(set.Logger, oCfg, nextConsumer)
}
```

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"time"
)

// TelemetrySpan models an in-flight trace span
type TelemetrySpan struct {
	TraceID    string
	SpanID     string
	Operation  string
	Attributes map[string]string
}

// Consumer represents downstream telemetry consumers (Processors and Exporters)
type Consumer interface {
	Consume(ctx context.Context, spans []TelemetrySpan) error
}

// MemoryLimiterProcessor enforces heap safety
type MemoryLimiterProcessor struct {
	Next       Consumer
	MaxSpans   int
	mu         sync.Mutex
	activeCount int
}

func (m *MemoryLimiterProcessor) Consume(ctx context.Context, spans []TelemetrySpan) error {
	m.mu.Lock()
	if m.activeCount+len(spans) > m.MaxSpans {
		m.mu.Unlock()
		return fmt.Errorf("memory_limiter: shed load (active %d + new %d > max %d)",
			m.activeCount, len(spans), m.MaxSpans)
	}
	m.activeCount += len(spans)
	m.mu.Unlock()

	defer func() {
		m.mu.Lock()
		m.activeCount -= len(spans)
		m.mu.Unlock()
	}()

	return m.Next.Consume(ctx, spans)
}

// SimpleMockExporter stores accepted spans
type SimpleMockExporter struct {
	mu            sync.Mutex
	ExportedCount int
}

func (e *SimpleMockExporter) Consume(ctx context.Context, spans []TelemetrySpan) error {
	e.mu.Lock()
	defer e.mu.Unlock()
	e.ExportedCount += len(spans)
	fmt.Printf("[Exporter] Successfully flushed batch of %d spans to storage\n", len(spans))
	return nil
}

func main() {
	ctx, cancel := context.WithTimeout(context.Background(), 2*time.Second)
	defer cancel()

	exporter := &SimpleMockExporter{}
	limiter := &MemoryLimiterProcessor{
		Next:     exporter,
		MaxSpans: 5,
	}

	batchA := []TelemetrySpan{
		{TraceID: "t1", SpanID: "s1", Operation: "AuthorizePayment"},
		{TraceID: "t1", SpanID: "s2", Operation: "FraudScore"},
	}

	batchB := []TelemetrySpan{
		{TraceID: "t2", SpanID: "s3", Operation: "LedgerDeposit"},
		{TraceID: "t2", SpanID: "s4", Operation: "NotifyCustomer"},
		{TraceID: "t2", SpanID: "s5", Operation: "AuditLog"},
		{TraceID: "t2", SpanID: "s6", Operation: "AuditLogMirror"}, // Exceeds MaxSpans 5
	}

	fmt.Println("--- Ingesting Batch A (2 spans) ---")
	if err := limiter.Consume(ctx, batchA); err != nil {
		fmt.Printf("Batch A failed: %v\n", err)
	}

	fmt.Println("--- Ingesting Batch B (4 spans, capacity 5) ---")
	if err := limiter.Consume(ctx, batchB); err != nil {
		fmt.Printf("Batch B rejected: %v\n", err)
	}

	fmt.Printf("Total spans safely exported: %d\n", exporter.ExportedCount)
}
```

## In-Flight Zero-Alloc PII Redaction

Now we confront the central challenge: stripping sensitive financial identifiers from trace attributes in-flight without grinding our throughput to a crawl.

In a banking environment complying with PCI-DSS, NACHA (for ACH routing numbers), and GLBA, our custom processor must enforce three uncompromising masking rules:
1. **Primary Account Numbers (PANs)**: Standard credit card numbers issued by Visa, MasterCard, Discover, and American Express range from 13 to 19 digits (predominantly 16 digits). We must mask all digits except the first 6 (the Issuer Identification Number / BIN) and the last 4 (customer verification digits), replacing the middle digits with asterisks: `411111******1111`. Furthermore, we must run the **Luhn Algorithm (MOD 10)** checksum over the candidate digits. If a 16-digit number fails Luhn, it is not a credit card—it may be an internal database order ID or UUID timestamp; we must leave it untouched!
2. **Card Verification Values (CVVs)**: Any attribute labeled `payment.cvv`, `card.cvv`, or `cvv` containing 3 or 4 digits must be completely masked to `***`.
3. **ABA Routing Transit Numbers**: 9-digit identifiers used in Fedwire and ACH transfers (`bank.routing_number`). We mask the first five routing digits: `*****6789`.

### The Zero-Allocation Luhn Check

The Luhn algorithm validates card numbers by doubling every second digit from right to left, subtracting 9 if the result exceeds 9, and summing all digits.

Here is the zero-allocation implementation operating directly on ASCII bytes without string allocations:

```go
func ValidateLuhnASCII(b []byte) bool {
    if len(b) != 16 {
        return false
    }
    var sum int
    alternate := false
    for i := len(b) - 1; i >= 0; i-- {
        c := b[i]
        if c < '0' || c > '9' {
            return false
        }
        digit := int(c - '0')
        if alternate {
            digit *= 2
            if digit > 9 {
                digit -= 9
            }
        }
        sum += digit
        alternate = !alternate
    }
    return sum%10 == 0
}
```

## Batching, Memory Limiter & Backpressure

A telemetry collector that does not batch will saturate its egress network interfaces with thousands of small, uncompressed TCP frames. A collector that batches without backpressure will crash its process when the downstream network hiccups.

### The Batch Processor

<Define term="Memory Limiter" since="Observability & Telemetry Pipelines (Appendix, ch53)">
A specialized circuit-breaker processor that continuously samples the Go runtime memory usage. If memory consumption exceeds configured hard thresholds, it drops incoming data and returns backpressure errors to halt upstream producers.
</Define>

The batch processor aggregates incoming spans across multiple requests until one of two conditions is satisfied:
1. **Size trigger (`send_batch_size`)**: The accumulated spans reach the batch threshold (e.g. 8,192 spans). It flushes immediately.
2. **Timer trigger (`timeout`)**: The configured duration elapses (e.g. 200ms) since the oldest span in the batch arrived. It flushes whatever spans are currently buffered.

```
Incoming Spans ----> [ Batch Queue Buffer ] ───┬───> (Size == 8192?) ──> FLUSH
                             ▲                 └───> (Timer >= 200ms) ──> FLUSH
                             │
                      [ time.Ticker ]
```

### Memory Ballast vs Modern Go Memory Management

In legacy Collector deployments (prior to Go 1.19), engineers used a notorious hack known as **memory ballast**: allocating a massive byte slice (e.g. `ballast := make([]byte, 1<<30)`) at startup to artificially inflate the Go heap base. This delayed GC frequency under load.

Today, that hack is obsolete and dangerous. Modern Go provides precise runtime memory controls:
- **`GOMEMLIMIT`**: Introduced in Go 1.19 and refined in Go 1.25/1.26. It establishes a soft memory ceiling for the Go runtime. As memory approaches `GOMEMLIMIT`, the runtime garbage collector runs more aggressively to reclaim dead objects.
- **Container-Aware `GOMAXPROCS`**: Go 1.25 natively interrogates cgroup CPU quotas, eliminating thread over-subscription inside Kubernetes pods.
- **Collector `memory_limiter`**: Works in lockstep with `GOMEMLIMIT`. You set `GOMEMLIMIT` to 90% of your Kubernetes container memory limit, and configure the collector `memory_limiter` at 80%. When memory spikes to 80%, the `memory_limiter` actively sheds load by returning `codes.ResourceExhausted` to upstream clients, preventing the process from ever touching the container limit or triggering kernel OOMKiller.

### Building a Thread-Safe Batch Processor with Dual Triggers

Here is a fully runnable, concurrent batch processor implementing the dual-trigger mechanism (size threshold and timer ticker) alongside memory-budgeted load shedding:

<GoPlayground>

```go
package main

import (
	"errors"
	"fmt"
	"sync"
	"sync/atomic"
	"time"
)

var ErrLoadShed = errors.New("memory_limiter: capacity exhausted, shedding load")

type BatchItem struct {
	ID        string
	Payload   string
	SizeBytes int
}

type ProductionBatcher struct {
	mu           sync.Mutex
	batchSize    int
	timeout      time.Duration
	maxMemory    int
	currentBytes int
	buffer       []BatchItem
	sink         func([]BatchItem)
	droppedTotal atomic.Int64
	stopChan     chan struct{}
	wg           sync.WaitGroup
}

func NewProductionBatcher(batchSize int, timeout time.Duration, maxMemory int, sink func([]BatchItem)) *ProductionBatcher {
	b := &ProductionBatcher{
		batchSize: batchSize,
		timeout:   timeout,
		maxMemory: maxMemory,
		buffer:    make([]BatchItem, 0, batchSize),
		sink:      sink,
		stopChan:  make(chan struct{}),
	}
	b.wg.Add(1)
	go b.timerLoop()
	return b
}

func (b *ProductionBatcher) Ingest(item BatchItem) error {
	b.mu.Lock()
	defer b.mu.Unlock()

	// Memory limiter check
	if b.currentBytes+item.SizeBytes > b.maxMemory {
		b.droppedTotal.Add(1)
		return ErrLoadShed
	}

	b.buffer = append(b.buffer, item)
	b.currentBytes += item.SizeBytes

	// Size trigger
	if len(b.buffer) >= b.batchSize {
		b.flushLocked("SIZE_TRIGGER")
	}
	return nil
}

func (b *ProductionBatcher) flushLocked(reason string) {
	if len(b.buffer) == 0 {
		return
	}
	flushed := make([]BatchItem, len(b.buffer))
	copy(flushed, b.buffer)
	b.buffer = b.buffer[:0]
	b.currentBytes = 0

	if b.sink != nil {
		b.sink(flushed)
	}
	fmt.Printf("[Batcher] Flushed %d items via %s\n", len(flushed), reason)
}

func (b *ProductionBatcher) timerLoop() {
	defer b.wg.Done()
	ticker := time.NewTicker(b.timeout)
	defer ticker.Stop()

	for {
		select {
		case <-ticker.C:
			b.mu.Lock()
			if len(b.buffer) > 0 {
				b.flushLocked("TIMER_TRIGGER")
			}
			b.mu.Unlock()
		case <-b.stopChan:
			b.mu.Lock()
			if len(b.buffer) > 0 {
				b.flushLocked("SHUTDOWN_DRAIN")
			}
			b.mu.Unlock()
			return
		}
	}
}

func (b *ProductionBatcher) Close() {
	close(b.stopChan)
	b.wg.Wait()
}

func main() {
	var totalProcessed atomic.Int64

	sink := func(batch []BatchItem) {
		totalProcessed.Add(int64(len(batch)))
	}

	// Max 4 items per batch, 100ms timeout, 1000 bytes memory ceiling
	batcher := NewProductionBatcher(4, 100*time.Millisecond, 1000, sink)
	defer batcher.Close()

	// 1. Ingest 4 items -> triggers size flush immediately
	fmt.Println("--- Ingesting 4 items (Hits Size Threshold) ---")
	for i := 1; i <= 4; i++ {
		_ = batcher.Ingest(BatchItem{
			ID:        fmt.Sprintf("span-%d", i),
			Payload:   "telemetry data",
			SizeBytes: 50,
		})
	}

	// 2. Ingest 2 items -> waits for timer flush
	fmt.Println("\n--- Ingesting 2 items (Waits for Timer) ---")
	for i := 5; i <= 6; i++ {
		_ = batcher.Ingest(BatchItem{
			ID:        fmt.Sprintf("span-%d", i),
			Payload:   "telemetry data",
			SizeBytes: 50,
		})
	}
	time.Sleep(150 * time.Millisecond) // Allow ticker to fire

	// 3. Attempt memory exhaustion
	fmt.Println("\n--- Attempting Memory Overflow (Capacity 1000 bytes) ---")
	err := batcher.Ingest(BatchItem{
		ID:        "massive-span",
		Payload:   "huge payload",
		SizeBytes: 1200, // Exceeds 1000 byte limit
	})
	if errors.Is(err, ErrLoadShed) {
		fmt.Printf("Successfully shed load: %v\n", err)
	}

	fmt.Printf("\nTotal items successfully processed: %d\n", totalProcessed.Load())
	fmt.Printf("Total items shed by memory guard: %d\n", batcher.droppedTotal.Load())
}
```

Build a thread-safe batching accumulator struct `BatchBuffer` that accumulates strings. It must flush whenever:

```go
package main

import (
	"fmt"
	"sync"
)

type BatchBuffer struct {
	mu     sync.Mutex
	limit  int
	items  []string
	sink   func([]string)
}

func NewBatchBuffer(limit int, sink func([]string)) *BatchBuffer {
	return &BatchBuffer{
		limit: limit,
		items: make([]string, 0, limit),
		sink:  sink,
	}
}

func (b *BatchBuffer) Add(item string) {
	b.mu.Lock()
	defer b.mu.Unlock()

	b.items = append(b.items, item)
	if len(b.items) >= b.limit {
		b.flushLocked()
	}
}

func (b *BatchBuffer) Flush() {
	b.mu.Lock()
	defer b.mu.Unlock()
	b.flushLocked()
}

func (b *BatchBuffer) flushLocked() {
	if len(b.items) == 0 {
		return
	}
	batch := make([]string, len(b.items))
	copy(batch, b.items)
	b.items = b.items[:0] // Retains backing capacity!

	if b.sink != nil {
		b.sink(batch)
	}
}

	buf.Add("span-1")
	buf.Add("span-2")
	buf.Add("span-3") // Triggers automatic flush

	buf.Add("span-4")
	buf.Flush()       // Manual flush

	fmt.Printf("Produced %d batches. Batch 1: %v, Batch 2: %v\n",
		len(batches), batches[0], batches[1])
```

```go
	activeBytes atomic.Int64
}

func NewMemoryCircuitBreaker(maxBytes int64) *MemoryCircuitBreaker {
	return &MemoryCircuitBreaker{maxBytes: maxBytes}
}

func (m *MemoryCircuitBreaker) Acquire(bytes int64) error {
	for {
		cur := m.activeBytes.Load()
		if cur+bytes > m.maxBytes {
			return ErrLimitExceeded
		}
		if m.activeBytes.CompareAndSwap(cur, cur+bytes) {
			return nil
		}
	}
}

func (m *MemoryCircuitBreaker) Release(bytes int64) {
	m.activeBytes.Add(-bytes)
}

func main() {
	breaker := NewMemoryCircuitBreaker(1000)

	if err := breaker.Acquire(600); err != nil {
		fmt.Println("Error:", err)
	} else {
		fmt.Println("Acquired 600 bytes successfully")
	}

	if err := breaker.Acquire(500); errors.Is(err, ErrLimitExceeded) {
		fmt.Println("Correctly rejected 500 bytes (600 + 500 > 1000)")
	}

	breaker.Release(600)
	if err := breaker.Acquire(500); err == nil {
		fmt.Println("Acquired 500 bytes after releasing previous allocation")
	}
}
```

**Explanation:**
Lock-free compare-and-swap (`CompareAndSwap`) on an `atomic.Int64` enables hundreds of concurrent worker goroutines to acquire memory quotas without lock contention.
