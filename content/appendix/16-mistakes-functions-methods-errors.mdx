## Receivers

A method's **receiver** is the value the method is attached to — `func (c Customer) Validate()`. It can be a **value** (`c Customer`, a copy) or a **pointer** (`c *Customer`, an address). Mistake #42 is not knowing which to reach for — and, worse, mixing both on the same type.

<Define term="Value vs pointer receiver" since="Go Mistakes (Appendix)">
A **value receiver** gets a *copy* of the value; mutations inside the method are local and vanish when it returns. A **pointer receiver** gets the *address*, so mutations persist on the original. Why it matters: pick value when the method only reads and the type is small; pick pointer when the method must **mutate** the receiver, when the struct is **large** (copying is wasteful), or when the type contains something that **must not be copied** (a `sync.Mutex`, or any embedded sync type). The hard rule: **don't mix receiver kinds on one type** — if any method needs a pointer, give them *all* pointer receivers, so the method set stays consistent.
</Define>

Here's the trap in miniature: Meridian's `Account.Deposit` *looks* like it works, but a value receiver copies the account, mutates the copy, and throws it away. The balance never moves.

<GoPlayground>

```go
package main

import "fmt"

type Account struct {
	Cents int64
}

// BUG: value receiver — Deposit mutates a COPY of the account.
func (a Account) Deposit(c int64) { a.Cents += c }

// Fix: pointer receiver — mutates the original account.
func (a *Account) DepositFixed(c int64) { a.Cents += c }

func main() {
	acct := Account{Cents: 100}
	acct.Deposit(50)
	fmt.Println("after value-receiver Deposit:", acct.Cents) // still 100 — lost!

	acct.DepositFixed(50)
	fmt.Println("after pointer-receiver Deposit:", acct.Cents) // 150 — persisted
}
```

</GoPlayground>

<ConceptGrid cols={3}>
  <ConceptCard label="Pointer — MUST">The method mutates the receiver, or the receiver embeds a type that can't be copied (`sync.Mutex`, `sync.WaitGroup`). A value receiver here is a silent bug or a `go vet` warning.</ConceptCard>
  <ConceptCard label="Pointer — SHOULD">The struct is large enough that copying it on every call costs real CPU. "Large" is fuzzy — benchmark when in doubt — but a fat config struct or a slice-of-structs field leans pointer.</ConceptCard>
  <ConceptCard label="Value — fine">Small, immutable types where a copy is cheap and you *want* the call to be side-effect free (a `Money{Cents, Currency}`, a `time.Time`). Reads only.</ConceptCard>
  <Gotcha>⚠ Never mix value and pointer receivers on the **same type**. A pointer-receiver method means `Account` (the value) doesn't satisfy an interface that the method set requires — only `*Account` does. Inconsistency breeds interface-satisfaction surprises. Pick one per type.</Gotcha>
</ConceptGrid>

Two related features, two related mistakes. **Named result parameters** (#43) let you name your return values in the signature; they're pre-initialized to zero and enable a *naked* `return`. **Unintended side effects** (#44) is what happens when a named return interacts badly with `defer`.

<Define term="Named result parameter" since="Go Mistakes (Appendix)">
A **named result parameter** is a return value given a name in the signature: `func get(addr string) (lat, lng float32, err error)`. It's a real variable, **initialized to its zero value** when the function begins, and a bare `return` (a *naked return*) returns whatever those named results currently hold. Why it matters: names document the return order (which `float32` is latitude?), and a deferred closure can *read and modify* the named result before the function actually returns — which is the whole basis of clean `defer`-based error handling. The cost: naked returns in a long function force the reader to track invisible state.
</Define>

Use named results when they genuinely add clarity — multiple results of the **same type** (so the names disambiguate order), or when you need a `defer` to touch the return value. Don't slap a name on a lone `(err error)` just because you can; `func Store(c Customer) error` is plenty clear, and naming it buys nothing.

<BeforeAfter

}`}
  good={`// Names document order at the

Now the footgun. Named results are *pre-initialized to zero*, which means code that returns the named `err` **compiles even when you forgot to assign it** — silently returning `nil`. Watch this geocoding method always claim success on a cancelled context:

<GoPlayground>

```go
package main

import (
	"context"
	"errors"
	"fmt"
)

// BUG: returns the named `err`, but err is never assigned from ctx.Err().
// It's still its zero value (nil), so a cancelled context returns no error.
func atBad(ctx context.Context) (lat, lng float32, err error) {
	if ctx.Err() != nil {
		return 0, 0, err // err is still nil!
	}
	return 6.52, 3.37, nil
}

// Fix: assign the named err from ctx.Err() before returning it.
func atGood(ctx context.Context) (lat, lng float32, err error) {
	if err = ctx.Err(); err != nil {
		return // naked return: lat=0, lng=0, err=ctx.Err()
	}
	return 6.52, 3.37, nil
}

func main() {
	ctx, cancel := context.WithCancel(context.Background())
	cancel() // context is now cancelled

	_, _, errBad := atBad(ctx)
	fmt.Println("atBad  on cancelled ctx -> err:", errBad) // <nil> — wrong!
	_, _, errGood := atGood(ctx)
	fmt.Println("atGood on cancelled ctx -> err:", errGood) // context canceled ✓
	_ = errors.Is(errGood, context.Canceled)
}
```

</GoPlayground>

The genuinely *useful* version of this interaction is a deferred closure that mutates the named return — the idiomatic way to wrap an error or capture a `Close` failure on the way out (we'll use it for real in the last section). But the same power means a `defer` can rewrite your return value behind your back:

## The Typed-Nil Trap

Mistake #45, and the most infamous gotcha in the language. You return a `nil` pointer as an `error`, your caller checks `if err != nil` — and it's *true*. A clean validation reports failure. A successful operation gets rolled back.

<Define term="Typed nil" since="Go Mistakes (Appendix)">
An **interface value is a pair**: a *type* and a *value*. An interface is `nil` only when *both* are nil. A **typed nil** is a nil pointer (value = nil) carrying a concrete type (type = `*MultiError`) — so when you assign it to an interface like `error`, the interface holds `(type: *MultiError, value: nil)`. The type half is non-nil, so the **interface is not nil**. Why it matters: returning a `var m *MultiError` as an `error` makes `err != nil` true even when `m` is nil — your success path is reported as a failure. Fix: return the **nil interface** explicitly (`return nil`), never a typed nil pointer.
</Define>

Here is Meridian's customer validator. It returns `nil` errors for a clean customer — except it doesn't, because it returns a typed-nil `*MultiError`. The demo prints output instead of dying, so you can see the lie:

<GoPlayground>

```go
package main

import (
	"errors"
	"fmt"
	"strings"
)

// MultiError collects several validation failures.
type MultiError struct {
	errs []string
}

func (m *MultiError) Add(err error) { m.errs = append(m.errs, err.Error()) }
func (m *MultiError) Error() string { return strings.Join(m.errs, "; ") }

// BUG: returns m, a *MultiError. For a clean customer m is nil — but it's a
// TYPED nil, so the returned error interface is NOT nil.
func validateBad(age int, name string) error {
	var m *MultiError
	if age < 0 {
		m = &MultiError{}
		m.Add(errors.New("age is negative"))
	}
	return m // typed nil when clean -> err != nil lies
}

// Fix: return the nil interface explicitly.
func validateGood(age int, name string) error {
	var m *MultiError
	if age < 0 {
		m = &MultiError{}
		m.Add(errors.New("age is negative"))
	}
	if m != nil {
		return m
	}
	return nil // a true nil error interface
}

func main() {
	if err := validateBad(33, "John"); err != nil {
		fmt.Println("validateBad:  err != nil (WRONG — customer is valid!) ->", err)
	}
	if err := validateGood(33, "John"); err != nil {
		fmt.Println("validateGood: err != nil")
	} else {
		fmt.Println("validateGood: err == nil (correct — customer is valid)")
	}
}
```

</GoPlayground>

Why does it happen? A method is sugar for a function whose first argument is the receiver, and **a nil pointer is a perfectly valid receiver** — `(*MultiError)(nil).Error()` doesn't crash, it just operates on a nil `m`. So Go is happy to put that nil pointer in the interface. The pointer is nil; the interface wrapping it is not.

## io.Reader & Panic

Two design mistakes that sit on either side of "how do functions talk to the outside world."

**#46: taking a filename as input.** A function that accepts a `filename string` and opens it itself is welded to the filesystem — you can't feed it an HTTP body, a string, a gRPC stream, or a test fixture without writing a temp file. Accept an **`io.Reader`** instead and the data source becomes the caller's problem.

<Define term="io.Reader as a parameter" since="Go Mistakes (Appendix)">
**`io.Reader`** is the one-method interface `Read(p []byte) (n int, err error)` — "give me bytes from somewhere." Accepting an `io.Reader` instead of a filename **abstracts the source**: a file (`*os.File`), an HTTP body (`req.Body`), an in-memory string (`strings.NewReader`), or a network socket all satisfy it. Why it matters: the function becomes reusable across every byte source and **trivially testable** — a unit test feeds `strings.NewReader("...")` with no temp file, no disk, no cleanup. Open the file at the *edge* of your program; pass the reader inward.
</Define>

<BeforeAfter
  bad={`// Welded to the filesystem.
// Tests must create real files.
func CountTxns(path string) (int, error) {
  f, err := os.Open(path)
  if err != nil {
    return 0, err
  }
  defer f.Close()
  return scan(f)
}`}
  good={`// Any byte source works; tests
// pass strings.NewReader(...).
func CountTxns(r io.Reader) (int, error) {
  return scan(r)
}
// caller opens the file:
//   f, _ := os.Open(path)
//   defer f.Close()
//   CountTxns(f)`}

  goodLabel="io.Reader input (reusable)"
/>

**#47: how `defer` evaluates its arguments and receiver.** A `defer`'s arguments — and its method receiver — are evaluated **at the `defer` statement**, not when the deferred call finally runs. So `defer notify(status)` captures `status` *now*, even though the call happens at return time. The fix is a **closure**, whose body reads the variable when it executes.

<GoPlayground>

```go
package main

import "fmt"

func record() {
	status := "pending"

	// BUG: status is evaluated NOW ("pending") and frozen into the deferred call.
	defer fmt.Println("deferred arg captured:", status)

	// Fix: a closure reads status when it RUNS, after the updates below.
	defer func() { fmt.Println("deferred closure reads:", status) }()

	status = "settled" // both defers run after this line...
}

func main() {
	record()
	// Prints (defers run LIFO):
	//   deferred closure reads: settled   <- closure sees the final value
	//   deferred arg captured: pending    <- arg was frozen at the defer stmt
}
```

</GoPlayground>

The same rule governs receivers: `defer conn.Close()` evaluates `conn` at the `defer` line, so if you reassign `conn` afterward, the deferred `Close` still targets the original. Capture late with a closure when the value will change.

Now **panic** (#48). Panicking is *not* error handling. Go returns errors as values; reaching for `panic`/`recover` to fake try/catch is a code smell. Reserve `panic` for genuinely exceptional, unrecoverable conditions:

<ConceptGrid cols={2}>
  <ConceptCard label="Panic is appropriate">A **programmer error** the program can't sanely continue past — an impossible enum value, a corrupt invariant — or a **mandatory dependency that fails to initialize at startup** (e.g. `regexp.MustCompile` for a hardcoded pattern, registering a `database/sql` driver). The stdlib panics in exactly these spots.</ConceptCard>
  <ConceptCard label="Return an error instead">Anything that can happen at runtime from outside input: a bad request, a failed DB query, a malformed amount, a timeout. These are *expected* failures — return an `error` as the last value and let the caller decide. Panicking here turns a 400 into a crashed process.</ConceptCard>
  <Gotcha>⚠ `recover()` only does anything inside a **deferred** function. Calling `recover()` directly in normal flow returns nil and has no effect. And recovering should be rare — usually only at a goroutine or request boundary to stop one bad request from killing the whole server.</Gotcha>
</ConceptGrid>

## Wrapping & Checking Errors

The modern error machinery, and the three mistakes people make once they start using it (#49, #50, #51). Since Go 1.13, `fmt.Errorf` with the **`%w`** verb *wraps* an error — adds context while keeping the original reachable. With `%v` it merely *transforms* — adds context but severs the chain.

<Define term="Error wrapping" since="Go Mistakes (Appendix)">
**Wrapping** an error packs it inside another error that still exposes the original via an `Unwrap()` method — produced by `fmt.Errorf("context: %w", err)` (the **`%w`** verb, since Go 1.13). The wrapper adds context ("charging account 42:") while the **source error stays reachable** down the chain, so callers can still match it with `errors.Is`/`errors.As`. Using `%v` instead *transforms* the error: you get the context string but the chain is cut and the source is gone. Why it matters: wrap (`%w`) when callers should be able to detect the underlying cause; transform (`%v`) when the cause is an implementation detail you don't want to leak as part of your API.
</Define>

<BeforeAfter
  bad={`// %v transforms: context kept,
// but the source error is GONE.
// Callers can't match the cause.
return fmt.Errorf(
  "charge %s: %v", id, err)
// errors.Is(out, sql.ErrNoRows)
//   -> always false`}
  good={`// %w wraps: context kept AND the
// source stays in the chain, so
// callers can match it.
return fmt.Errorf(
  "charge %s: %w", id, err)
// errors.Is(out, sql.ErrNoRows)
//   -> true when that's the cause`}
  badLabel="%v (transform, chain cut)"
  goodLabel="%w (wrap, chain intact)"
/>

Once you wrap, you **must** change how you check. The naive `==` for a sentinel and a type assertion for a typed error both look only at the *outermost* error — so wrapping breaks them. The right tools walk the chain:

- **`errors.Is(err, target)`** — for **sentinel** errors (a known *value* like `sql.ErrNoRows`, `io.EOF`, `context.Canceled`). It unwraps `err` repeatedly looking for `target`. Never use `==`.
- **`errors.As(err, &target)`** — for **typed** errors (a custom struct like `*TransientError`). It unwraps looking for one that matches the *type* of `target` and assigns it. Never use a type assertion or a `switch err.(type)`.

<Define term="Sentinel error" since="Go Mistakes (Appendix)">
A **sentinel error** is a predeclared error *value* used as a known marker — `var ErrNotFound = errors.New("not found")`, or stdlib's `io.EOF` and `sql.ErrNoRows`. Callers detect it to branch on a specific outcome. Why it matters: once any layer wraps it with `%w`, a direct `err == ErrNotFound` comparison fails (the outer error isn't the sentinel). Use **`errors.Is(err, ErrNotFound)`**, which unwraps the chain until it finds the sentinel. Reserve sentinels for a small, stable set of conditions callers genuinely branch on — each one is part of your public API.
</Define>

This Meridian handler maps DB failures to HTTP status codes. It wraps with `%w`, then checks the chain with `errors.As` and `errors.Is` — both find the cause even three layers deep:

<GoPlayground>

```go
package main

import (
	"errors"
	"fmt"
)

// Sentinel: a known marker value.
var ErrNoSuchAccount = errors.New("no such account")

// Typed error: marks a retryable/transient failure.
type TransientError struct{ inner error }

func (t *TransientError) Error() string { return "transient: " + t.inner.Error() }

// queryDB fails transiently; getAmount wraps with %w (keeps the chain).
func queryDB(id string) error { return &TransientError{inner: errors.New("conn reset")} }
func getAmount(id string) error {
	if err := queryDB(id); err != nil {
		return fmt.Errorf("get amount %s: %w", id, err) // %w wraps
	}
	return nil
}

func statusFor(err error) int {
	var te *TransientError
	if errors.As(err, &te) { // walks the chain, matches the TYPE
		return 503 // service unavailable — safe to retry
	}
	if errors.Is(err, ErrNoSuchAccount) { // walks the chain, matches the VALUE
		return 404
	}
	return 400
}

func main() {
	err := getAmount("AC100")
	fmt.Println("wrapped error:", err)
	fmt.Println("HTTP status (errors.As found TransientError):", statusFor(err)) // 503
	// A bare type assertion would FAIL here because the error is wrapped:
	_, ok := err.(*TransientError)
	fmt.Println("err.(*TransientError) directly succeeds?", ok) // false — that's the trap
}
```

## Handling Errors Once

The last cluster (#52–54) is about discipline: handle each error exactly **once**, never ignore one silently, and never let a deferred `Close` swallow its own failure.

**#52: handling an error twice.** Logging an error *and* returning it means it gets logged again by every caller up the stack — the same failure smeared across a dozen log lines, making one incident look like ten. Do **one**: either handle it here (log/recover and stop), or add context and return it for someone above to handle. Not both.

<BeforeAfter
  bad={`// Logged here AND returned -> the
// caller logs it again, and so on.
// One failure, N noisy log lines.
if err != nil {
  log.Printf("charge failed: %v", err)
  return err
}`}
  good={`// Add context and return. The ONE
// place that finally handles it
// (the top) logs it once.
if err != nil {
  return fmt.Errorf("charge %s: %w", id, err)
}`}
  badLabel="Log AND return (double noise)"
  goodLabel="Wrap and return (handle once)"
/>

**#53: not handling an error.** The blank-identifier ignore — `_ = doThing()` or just dropping the returned error — discards information about a real failure. If you *truly* mean to ignore it, make that intent explicit and loud: assign to `_` *with a comment* explaining why it's safe. Most of the time, "I'll ignore this" is "I forgot to handle this."

**#54: not handling defer errors.** The classic: `defer f.Close()` throws away whatever `Close` returns. For a read that's usually fine; for a **write**, `Close` is where buffered data gets flushed — and where the disk-full or network error actually surfaces. Swallowing it means a "successful" write that never landed. Capture it via a **named return** and a deferred closure:

<GoPlayground>

```go
package main

import (
	"errors"
	"fmt"
)

type file struct{ name string }

// Close reports a flush failure — the kind defer f.Close() silently drops.
func (f *file) Close() error { return errors.New("flush failed: disk full") }

// BUG: the Close error is discarded. A failed flush looks like success.
func writeBad(f *file) error {
	defer f.Close() // error swallowed
	return nil
}

// Fix: named return + deferred closure captures Close's error (without
// clobbering a real error from the body).
func writeGood(f *file) (err error) {
	defer func() {
		if cerr := f.Close(); cerr != nil && err == nil {
			err = fmt.Errorf("closing %s: %w", f.name, cerr)
		}
	}()
	return nil // body succeeded; the Close error now surfaces
}

func main() {
	f := &file{name: "ledger.dat"}
	fmt.Println("writeBad  ->", writeBad(f))  // <nil> — the failed flush vanished!
	fmt.Println("writeGood ->", writeGood(f)) // closing ledger.dat: flush failed: disk full
}
```

</GoPlayground>

  <ConceptCard label="#52 Handle once">Log *or* return, never both. Wrap with context and return; let the top of the stack log it a single time. Double-handling turns one incident into a wall of duplicate logs.</ConceptCard>
  <ConceptCard label="#53 Don't ignore">A dropped error is a hidden failure. If ignoring is genuinely correct, `_ = x()` *with a why-comment*. `errcheck` / `golangci-lint` flags the unchecked ones in CI.</ConceptCard>
  <ConceptCard label="#54 Defer + Close">`defer f.Close()` swallows the close error — fatal for writes (that's where the flush fails). Capture it through a named return in a deferred closure, only if the body didn't already fail.</ConceptCard>

<UnderTheHood title="Interface layout, the typed-nil mechanics, and the errors package since 1.13">

An interface value in Go's runtime is two words: a pointer to a **type descriptor** (an `itab` for non-empty interfaces, holding the dynamic type and its method table) and a pointer to the **data**. The empty-interface form (`any`) uses `eface` — `{type, data}`. The nil-interface test compares the *whole pair* against the zero pair `{nil, nil}`. A **typed nil** sets the type word (to `*MultiError`'s descriptor) while the data word is nil — so the pair is `{*MultiError, nil}`, which is *not* `{nil, nil}`. That's the entire mechanism behind the typed-nil trap: the type word being set is enough to make the interface non-nil. It's not a special case for errors — it's how every interface conversion works.

The error machinery is younger than the language. Go 1.13 (2019) added the **`%w`** verb to `fmt.Errorf`, the `Unwrap() error` convention, and **`errors.Is`** / **`errors.As`**, which loop calling `Unwrap()` to walk the chain (`Is` also honors a custom `Is(error) bool` method; `As` honors `As(any) bool`). Go 1.20 added **multi-error wrapping**: `fmt.Errorf` accepts multiple `%w`, and **`errors.Join`** combines errors into a tree that `Is`/`As` traverse via an `Unwrap() []error` method. As of **Go 1.26**, prefer the generic **`errors.AsType[T]`** over `errors.As` — it's type-safe and returns the value directly:

```go
if te, ok := errors.AsType[*TransientError](err); ok {
	return 503, te
}
```

No out-pointer, no pre-declared variable, and the compiler checks `T` — the modern form of the `errors.As` pattern shown above. (Go 1.26 also lowered `fmt.Errorf`'s allocation cost.) For the full treatment of error design, sentinels vs typed errors, and wrapping strategy across service boundaries, see [Error Handling at Scale](/part-2/error-handling-at-scale); for receivers, methods, and how interfaces dispatch, see [Structs, Methods, Interfaces & Errors](/part-1/intermediate-go).

</UnderTheHood>

<Exercise n={1} title="Pick the receiver" level="easy">

`Wallet` has a `Cents int64` field and a `Mu sync.Mutex`. Write `Credit(n int64)` correctly, and say why the receiver kind is forced here.

<Solution>

```go
type Wallet struct {
	Cents int64
	Mu    sync.Mutex
}

func (w *Wallet) Credit(n int64) {
	w.Mu.Lock()
	defer w.Mu.Unlock()
	w.Cents += n
}
```

The receiver **must** be a pointer for two independent reasons. First, `Credit` *mutates* `w.Cents` — a value receiver would update a copy and discard it. Second, `Wallet` embeds a `sync.Mutex`, which must not be copied (copying a mutex breaks its locking; `go vet` flags it). Either reason alone forces a pointer receiver; together they make it unambiguous. And by the consistency rule, *every* method on `Wallet` should then take `*Wallet`.

</Solution>

</Exercise>

<Exercise n={2} title="Kill the typed nil" level="medium">

This factory returns a typed-nil when no config is needed, so callers' `if h != nil` wrongly passes. Fix it.

```go
func newHook(enabled bool) Hook { // Hook is an interface
	var h *traceHook
	if enabled {
		h = &traceHook{}
	}
	return h // BUG
}
```

<Solution>

```go
func newHook(enabled bool) Hook {
	if !enabled {
		return nil // a true nil interface
	}
	return &traceHook{}
}
```

Returning `h` (a `*traceHook`) when it's nil produces an interface of `(type: *traceHook, value: nil)` — non-nil, so the caller's `h != nil` guard passes and then dereferences a nil pointer. The fix is to return the **nil interface literally** when there's nothing to return, so the interface's type half is also nil. Restructuring to `return nil` on the disabled path (and the concrete pointer otherwise) guarantees a genuine nil interface. The trap applies to any interface, not just `error`.

</Solution>

</Exercise>

<Exercise n={3} title="Filename → io.Reader" level="medium">

Refactor `sumAmounts(path string) (int64, error)` (which opens and reads the file) to be testable without touching disk. Show the test setup.

func sumAmounts(r io.Reader) (int64, error) {
	// ... read from r, sum the amounts ...
	return total, nil

Production opens the file at the program's edge and passes the reader in; the test passes an in-memory reader with no temp file, no disk I/O, and no cleanup. The function is now reusable for HTTP bodies and network streams too.

</Solution>

<Exercise n={4} title="Is vs As" level="medium">

A query returns errors wrapped with `%w`. You need to (a) detect a `sql.ErrNoRows` sentinel and (b) extract a custom `*RetryableError` to read its `RetryAfter`. Which tool for each, and why not `==` / type assertion?

<Solution>

```go
// (a) sentinel VALUE -> errors.Is
if errors.Is(err, sql.ErrNoRows) {
	return notFound()
}

// (b) typed error -> errors.As (or AsType in 1.26+)
var re *RetryableError
if errors.As(err, &re) {
	return retryAfter(re.RetryAfter)
}
// Go 1.26 form:
// if re, ok := errors.AsType[*RetryableError](err); ok { ... }
```

Because the error is wrapped, `err` is the outer `*fmt.wrapError`, not the sentinel or the custom type — so `err == sql.ErrNoRows` is false and `err.(*RetryableError)` fails. `errors.Is` unwraps the chain to match a **value**; `errors.As` unwraps to match a **type** and assigns it so you can read its fields. Both survive any amount of wrapping; the naive forms break the moment a layer wraps.

</Solution>

</Exercise>

<Exercise n={5} title="Capture the Close error" level="hard">

`export(w io.WriteCloser) error` writes a report and closes `w`. A failed `Close` (flush) must surface as the returned error — but must not clobber a real write error. Write it.

<Solution>

```go
func export(w io.WriteCloser, data []byte) (err error) {
	defer func() {
		if cerr := w.Close(); cerr != nil && err == nil {
			err = fmt.Errorf("close export: %w", cerr)
		}
	}()
	if _, werr := w.Write(data); werr != nil {
		return fmt.Errorf("write export: %w", werr) // body error wins
	}
	return nil
}
```

The named result `err` lets the deferred closure set the return value at the last moment. The closure always calls `Close` (so the resource is released), captures its error, but only promotes it **if the body didn't already fail** (`err == nil`) — so a flush error surfaces on success, while a genuine write error from the body is preserved and not masked. `defer w.Close()` alone would discard the flush failure entirely, reporting a broken export as successful.

</Solution>

</Exercise>

<Recap>

The function, method, and error mistakes — they compile, they look fine, they lie:

- **Receivers** (#42): **pointer** to mutate, for large structs, or when a field can't be copied (`sync.Mutex`); **value** for small read-only types. Never mix kinds on one type.
- **Named results** (#43): name them when they document order (same-typed returns) or feed a `defer`; don't name a lone `err`. Pre-initialized to zero means a forgotten assignment silently returns nil (#44).
- **Typed nil** (#45): an interface is nil only if its **type and value** are both nil. Returning a nil *pointer* as an `error` (or any interface) makes `err != nil` true. **Return `nil` explicitly.**
- **io.Reader** (#46): accept `io.Reader`, not a filename — reusable and testable with `strings.NewReader`. **defer** (#47) evaluates its args and receiver at the `defer` statement; capture late with a closure. **Panic** (#48) only for programmer errors / failed mandatory init — return errors otherwise.
- **Wrapping** (#49): `%w` keeps the source error in the chain; `%v` cuts it. **Check the chain** (#50–51): `errors.As` for typed errors, `errors.Is` for sentinels — never type-assert or `==` once anything wraps.
- **Handle once** (#52): log *or* return, not both. **Don't ignore** (#53): no silent `_ =`. **Defer + Close** (#54): capture the close error via a named return, or a failed flush ships as success.

</Recap>
