## Shadowing & Nesting

Two readability mistakes that cause real bugs. First, **variable shadowing** — re-declaring a name in an inner block so writes never reach the outer one.

<Define term="Variable shadowing" since="Go Mistakes (Appendix)">
**Shadowing** happens when a variable declared in an inner block has the **same name** as one in an outer block — the inner one *hides* the outer for that block. The trap: writing `x, err := f()` inside an `if` creates a **new** `x` (because `:=` declares), so assignments never reach the outer `x`. Why it matters: the outer variable keeps its zero value (often `nil`), and you ship a nil client, an empty config, or a dropped result — with zero compiler complaint.
</Define>

Watch the outer `client` stay `nil` because the tracing branch quietly shadowed it:

<GoPlayground>

```go
package main

import "fmt"

// BUG: the tracing branch uses `:=`, declaring a NEW inner client that shadows
// the outer one. The outer client is never assigned, so it stays nil.
func buildClient(tracing bool) *string { // pretend *string is *http.Client
	var client *string
	if tracing {
		client := traced() // := => new variable, scoped to this block only
		_ = client         // used here; the OUTER client is untouched
	} else {
		client = plain() // = => assigns the outer variable (correct)
	}
	return client
}

func traced() *string { s := "traced-client"; return &s }
func plain() *string  { s := "plain-client"; return &s }

func main() {
	if buildClient(true) == nil {
		fmt.Println("tracing=true  -> client is NIL (shadowed!)")
	}
	fmt.Println("tracing=false -> client is", *buildClient(false))
}
```

</GoPlayground>

The scopes make the bug obvious once you see them — the inner `client` is born and dies inside the `if`, leaving the outer untouched:

The second mistake is **deep nesting**. Code that drifts rightward — `if ok { ... } else { ... }` pyramids — is hard to read because the happy path is buried. Flatten with early returns and handle the unhappy path first:

<BeforeAfter
  bad={`func process(p *Payment) error {
  if p != nil {
    if p.Amount > 0 {
      if p.Account != "" {
        return submit(p)
      } else {
        return errNoAccount
      }
    } else {
      return errBadAmount
    }
  }
  return errNil
}`}
  good={`func process(p *Payment) error {
  if p == nil {
    return errNil
  }
  if p.Amount <= 0 {
    return errBadAmount
  }
  if p.Account == "" {
    return errNoAccount
  }
  return submit(p) // happy path, left-aligned
}`}
  badLabel="Nested (pyramid of doom)"
  goodLabel="Early returns (flat)"
/>

## init & Accessors

<Define term="init function misuse" since="Go Mistakes (Appendix)">
An `init()` function runs automatically at package load, before `main`. The mistakes: using it for work that can **fail** (it can't return an error — you're forced to panic), for things that need **ordering** or **configuration** (init order across files is fragile), or for setting up global state that makes the package **hard to test**. Why it matters: `init` hides setup and removes your ability to handle failure gracefully. Prefer an explicit constructor (`NewX() (*X, error)`) you call from `main`, where you control order and errors.
</Define>

`init` has real uses (registering a database driver via blank import, setting up `//go:embed` data), but "open the DB connection in `init`" is a classic trap — if it fails, your whole binary panics on startup with no recourse. Make it explicit instead:

<ConceptGrid cols={2}>
  <ConceptCard label="init() — avoid for fallible setup">Can't return an error → must panic. Runs implicitly, so failures are invisible and order across files is brittle. Hard to test (no way to skip it). Reserve for driver registration and trivial table setup.</ConceptCard>
  <Gotcha>⚠ Don't put `db.Open` / network calls in `init`. Use `func NewStore(ctx) (*Store, error)` and call it from `main`, where you can log, retry, and fail cleanly.</Gotcha>
</ConceptGrid>

Mistake #4 is **overusing getters and setters**. Go is not Java — a plain exported field is idiomatic. Don't auto-generate `GetAmount()/SetAmount()` for every field; add accessors only when they *do* something (validation, computed values, interface satisfaction). See [Idiomatic Go & the Go Mindset](/part-2/idiomatic-go-mindset).

## Interface Pollution

The single most common Go API mistake. Engineers coming from other languages create an interface for *everything*, "just in case" — one interface, one implementation, mock for tests. That's **interface pollution**, and it adds indirection that buys nothing.

<Define term="Interface pollution & where to declare interfaces" since="Go Mistakes (Appendix)">
**Interface pollution** is creating interfaces with no real abstraction value — typically one interface per concrete type, defined preemptively. Go's rule is the opposite of nominal languages: **discover** interfaces, don't design them up front. And declare an interface on the **consumer** side (the package that *uses* the behavior), not the **producer** side (the package that implements it). Why it matters: producer-side interfaces force every consumer to depend on the producer's abstraction; consumer-side interfaces stay small (often one method) and let any type satisfy them implicitly. The proverb: **accept interfaces, return structs.**
</Define>

<BeforeAfter
  bad={`// PRODUCER side defines a fat interface
// for its one concrete type. Every caller
// now depends on this abstraction.
package store

type Store interface {
  Get(id string) (*Account, error)
  Put(a *Account) error
  Delete(id string) error
  List() ([]*Account, error)
}
func New() Store { return &pgStore{} }`}
  good={`// PRODUCER returns the concrete struct.
package store
func New() *PGStore { return &PGStore{} }

// CONSUMER declares the tiny interface it
// actually needs — one method.
package billing
type accountGetter interface {
  Get(id string) (*Account, error)
}
func Charge(g accountGetter, id string) {…}`}
  badLabel="Producer-side fat interface"
  goodLabel="Consumer-side minimal interface"
/>

Two siblings of this mistake: **returning interfaces** (#7) — return the concrete type so callers keep full access and you don't lock the abstraction; and **`any` says nothing** (#8) — next section. Most Go code needs *far* fewer interfaces than people write. When you do need one, it'll be small and it'll appear where it's used. Deep dive: [Software Design & Architecture](/part-1/software-design-architecture).

## any & Generics

`any` (the alias for `interface{}`) is sometimes necessary, but reaching for it to mean "some type" throws away everything the compiler can do for you. Since Go 1.18, **generics** give you "some type" *with* type safety.

<BeforeAfter
  bad={`// any: the compiler knows nothing. Callers
// can pass junk; you type-assert at runtime
// and pray.
func first(s []any) any {
  if len(s) == 0 {
    return nil
  }
  return s[0]
}
// v := first(accounts) // v is any — cast it`}
  good={`// generics: "some type T", checked at
// compile time. No assertions, no nil-any.
func first[T any](s []T) (T, bool) {
  var zero T
  if len(s) == 0 {
    return zero, false
  }
  return s[0], true
}
// a, ok := first(accounts) // a is *Account`}
  badLabel="any (runtime, unsafe)"
  goodLabel="generics (compile-time, safe)"
/>

<Callout kind="warn" title="...but don't overuse generics either (#9)">

Generics are not free and not always clearer. Use them when you're writing the *same* logic over many types — generic data structures (a typed `Set[T]`, a `Heap[T]`), or functions over `slices`/`maps`/`cmp`. **Don't** use them when an interface with a method already expresses the behavior (if you only ever call `w.Write`, take an `io.Writer`, not a type parameter), or for a one-off. The smell: a type parameter that appears once, or constraints that just re-state an existing interface. Rule of thumb — reach for generics for *containers and algorithms*, interfaces for *behavior*. Full treatment: [Generics in Go, In Depth](/part-1/generics).

</Callout>

<QuickCheck
  question="You're writing a function that returns the maximum of a slice of any ordered type (ints, floats, strings). What's the idiomatic Go 1.18+ choice?"
  options={[
    "Take []any and type-switch on the element type at runtime",
    "A generic function with a constraint, e.g. func Max[T cmp.Ordered](s []T) T — same logic over many types, checked at compile time and returning the concrete type",
    "Write three copies, one per type",
    "Return interface{} and let the caller assert"
  ]}
  answer={1}
  explain="This is the textbook case FOR generics: identical logic over many types. `[T cmp.Ordered]` constrains T to types supporting `<`, the compiler checks calls, and the return type is concrete (no assertions). `[]any` would discard type safety and force runtime switches; three copies is duplication. (Go 1.21+ even ships a builtin `max`, but the generic form is the pattern to know.)"
/>

## Embedding & Options

**Type embedding** (#10) promotes an embedded type's fields and methods to the outer type. Powerful, but two traps: you can **accidentally promote** methods you didn't mean to expose (embedding a `sync.Mutex` makes `Lock`/`Unlock` part of your public API), and you can **leak** an embedded type's behavior in ways that break invariants.

<ConceptGrid cols={2}>
  <ConceptCard label="Embed deliberately">Embedding is for *is-a* composition where promoting the methods is the point (embedding `io.Reader` in a wrapper). It is not a shortcut for "give me these fields."</ConceptCard>
  <Gotcha>⚠ Embedding `sync.Mutex` exports `Lock()`/`Unlock()` on your struct — callers can now lock your internals. Make it a **named field** (`mu sync.Mutex`), not embedded.</Gotcha>
</ConceptGrid>

The positive pattern in this group is **#11: functional options** — the idiomatic way to build a configurable constructor without a giant parameter list or a mutable, half-built config struct:

<GoPlayground>

```go
package main

import (
	"fmt"
	"time"
)

// Functional options: defaults + variadic Option funcs. Callers set only what
// they care about; adding a new option never breaks existing call sites.
type server struct {
	port    int
	timeout time.Duration
}

type Option func(*server)

func WithPort(p int) Option              { return func(s *server) { s.port = p } }
func WithTimeout(d time.Duration) Option { return func(s *server) { s.timeout = d } }

func newServer(opts ...Option) *server {
	s := &server{port: 8080, timeout: 30 * time.Second} // sane defaults
	for _, opt := range opts {
		opt(s)
	}
	return s
}

func main() {
	s := newServer(WithPort(9000)) // timeout keeps its default
	fmt.Printf("server on :%d, timeout %s\n", s.port, s.timeout)
}
```

</GoPlayground>

This is the pattern behind so many real Go libraries (gRPC, the AWS SDK, `slog` handlers). It beats a `Config` struct (which can be passed half-initialized) and a builder (more ceremony). Deep dive: [Design Patterns, the Go Way](/part-1/design-patterns-go).

## Packages & Tooling

The last cluster (#12–16) is hygiene — boring, and the difference between a codebase people enjoy and one they dread.

<ConceptGrid cols={3}>
  <ConceptCard label="#12 Project structure">Don't cargo-cult a deep `pkg/`/`internal/` tree on day one. Start flat; grow structure when the package boundaries actually emerge. Organize by *domain*, not by technical layer.</ConceptCard>
  <ConceptCard label="#13 Utility packages">A package named `utils`, `common`, or `helpers` is a code smell — it's a junk drawer with no cohesion. Name packages for what they *provide* (`money`, `ledger`), and the contents follow.</ConceptCard>
  <ConceptCard label="#14 Name collisions">Don't shadow a package name with a variable (`json := ...` then you can't call `json.Marshal`). And avoid two imported packages with the same name without an alias.</ConceptCard>
  <ConceptCard label="#15 Missing docs">Exported identifiers need doc comments, starting with the name (`// Charge debits...`). It's not bureaucracy — it's what `go doc` and your editor show.</ConceptCard>
  <ConceptCard label="#16 Skipping linters">`go vet` + `golangci-lint` catch a huge fraction of this chapter automatically — shadowing, unchecked errors, suspicious constructs. Not running them is choosing to ship known bugs.</ConceptCard>
  <Gotcha>⚠ Wire the linters into CI, not just your laptop. A check that's optional is a check that's skipped under deadline.</Gotcha>
</ConceptGrid>

<UnderTheHood title="Why the compiler doesn't catch shadowing — and the tooling that does">

Shadowing is *legal* Go: re-declaring a name in a nested scope is a deliberate feature (it's how `if v, ok := m[k]; ok` works). So the compiler can't reject it without breaking the language. The cost is that the dangerous case (shadowing a variable you *meant* to assign) looks identical to the useful case. That's why it's a **linter's** job, not the compiler's.

The detector lives in `golang.org/x/tools/go/analysis/passes/shadow`. It isn't in the default `go vet` set (too many false positives on intentional shadows), so you enable it explicitly — via `golangci-lint` (the `govet` linter with `shadow` enabled, or the `predeclared`/`shadow` linters) or `go vet -vettool=$(which shadow)`. As of Go 1.26, also lean on `go vet`'s built-in analyzers (the `waitgroup` and `hostport` passes landed in 1.25) and run `golangci-lint` in CI. The lesson of this whole chapter: the compiler enforces *types*, linters enforce *intent* — you need both. See [Tooling & Engineering Hygiene](/part-2/tooling-engineering-hygiene).

</UnderTheHood>

## Exercises

<Exercise n={1} title="Spot and fix the shadow" level="easy">

This function returns `nil` when `useCache` is true. Find the shadow and fix it so the outer `store` is assigned.

```go
func build(useCache bool) (*Store, error) {
	var store *Store
	var err error
	if useCache {
		store, err := newCached() // BUG
		if err != nil {
			return nil, err
		}
		_ = store
	} else {
		store, err = newPlain()
	}
	return store, err
}
```

<Solution>

```go
func build(useCache bool) (*Store, error) {
	var store *Store
	var err error
	if useCache {
		store, err = newCached() // = assigns the OUTER store (err already declared)
	} else {
		store, err = newPlain()
	}
	return store, err
}
```

The bug was `store, err :=` inside the `if`: because both `store` and `err` already exist in the outer scope, `:=` created shadows of *both*, local to the block. Switching to `=` assigns the outer variables. (You don't even need the inner `_ = store` anymore.) A shadow linter flags this instantly.

</Solution>

</Exercise>

<Exercise n={2} title="Flatten the nesting" level="easy">

Rewrite this with early returns so the happy path is left-aligned.

```go
func transfer(t *Tx) error {
	if t != nil {
		if t.From != t.To {
			if t.Amount > 0 {
				return commit(t)
			}
			return errAmount
		}
		return errSameAccount
	}
	return errNil
}
```

<Solution>

```go
func transfer(t *Tx) error {
	if t == nil {
		return errNil
	}
	if t.From == t.To {
		return errSameAccount
	}
	if t.Amount <= 0 {
		return errAmount
	}
	return commit(t) // happy path, no nesting
}
```

Guard clauses handle each failure first and return immediately, so the success case falls through to the bottom at the lowest indentation. Reading top-to-bottom now reads like a checklist of preconditions, and there's no `else` to track. This is the single highest-leverage readability habit in Go.

</Solution>

</Exercise>

<Exercise n={3} title="any → generics" level="medium">

Rewrite `contains(s []any, target any) bool` as a type-safe generic function. What constraint do you need for `==`?

<Solution>

```go
func contains[T comparable](s []T, target T) bool {
	for _, v := range s {
		if v == target {
			return true
		}
	}
	return false
}
```

The `comparable` constraint is required because the body uses `==`, which isn't defined for every type (e.g. slices, maps, funcs). `comparable` admits exactly the types that support `==`/`!=`. The generic version checks at compile time that `s` and `target` share a type and that the type is comparable — the `any` version would compile even for nonsense calls and panic or misbehave at runtime.

</Solution>

</Exercise>

<Exercise n={4} title="Consumer-side interface" level="medium">

The `notify` package needs only to *send* a message. Define the minimal interface on the consumer side, and explain why it shouldn't import the concrete `smtp` package.

<Solution>

```go
// package notify (the CONSUMER) declares only what it uses:
type sender interface {
	Send(to, body string) error
}

func Alert(s sender, to string) error {
	return s.Send(to, "your transfer settled")
}

// package smtp (the PRODUCER) just returns its concrete type:
//   func New() *Client { ... }   // *Client has a Send method
// notify never imports smtp; any type with Send(to, body) satisfies `sender`.
```

Declaring the one-method `sender` interface in `notify` means `notify` depends on *behavior it needs*, not on a concrete implementation. `smtp` (or a test fake, or a future `sns` package) satisfies it implicitly — no import from consumer to producer, no fat shared interface. That's "accept interfaces, return structs," and it keeps the dependency arrows pointing the right way.

</Solution>

</Exercise>

<Exercise n={5} title="Functional options" level="medium">

Give `newClient` functional options for `retries int` and `baseURL string`, with defaults `retries=3`, `baseURL="https://api.meridian.test"`. Show a call that sets only `retries`.

<Solution>

```go
type client struct {
	retries int
	baseURL string
}
type Option func(*client)

func WithRetries(n int) Option   { return func(c *client) { c.retries = n } }
func WithBaseURL(u string) Option { return func(c *client) { c.baseURL = u } }

func newClient(opts ...Option) *client {
	c := &client{retries: 3, baseURL: "https://api.meridian.test"}
	for _, o := range opts {
		o(c)
	}
	return c
}

// c := newClient(WithRetries(5)) // baseURL keeps its default
```

Each option is a closure that mutates the half-built `client`; the constructor applies defaults first, then the options. The caller sets only what it cares about, and adding a future option (say `WithTimeout`) never breaks existing call sites — the killer feature over a positional constructor or a mutable `Config`.

</Solution>

</Exercise>

<Recap>

The structural and API mistakes — they compile, they look fine, they rot the codebase:

- **Shadowing** (#1): `:=` on an existing name in an inner block makes a *new* variable; the outer keeps its zero value. Use `=` to assign the outer; run the shadow linter.
- **Nesting** (#2): flatten with **early returns** / guard clauses — handle failures first, keep the happy path left-aligned.
- **init** (#3): don't put fallible setup in `init()` (can't return errors, hard to test); use an explicit `New…() (*X, error)`. **Accessors** (#4): plain exported fields are fine; add getters/setters only when they *do* something.
- **Interface pollution** (#5–7): don't make an interface per type. **Accept interfaces, return structs**; declare the small interface on the **consumer** side.
- **`any`** (#8) discards type safety — use **generics** for "some type." But don't overuse generics (#9): containers/algorithms yes, behavior-via-interface no.
- **Embedding** (#10): promotes methods to your public API — embed deliberately; keep a `sync.Mutex` a *named* field. **Functional options** (#11) beat config structs and builders for extensible constructors.
- **Hygiene** (#12–16): organize by domain, no `utils` junk drawers, avoid name collisions, document exported names, and run `go vet` + `golangci-lint` **in CI**.

</Recap>
