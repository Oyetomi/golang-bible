## Big-O & Big-Θ Intuition

Here's the thing, sport: interviewers don't care whether you memorized a formula. They want to know if you can *look at code and immediately feel* how it scales. That feeling has a name — asymptotic analysis — and once you have it, you can't turn it off.

Let me build you that intuition from scratch. One step at a time.

### The core idea: growth rate, not wall-clock time

Suppose you're analyzing a service's `/search` endpoint. On a 10-item catalog it runs in 1ms. On a 10,000-item catalog? That depends entirely on *how the code grows with the input size*. Big-O formalizes that growth.

<Define term="Big-O notation">
**Big-O (written `O(...)`)** describes how an algorithm's resource use grows as the input size `n` grows — ignoring constant factors. `O(n)` means "linear": double the input, double the work. `O(n²)` means "quadratic": double the input, quadruple the work. It's the **upper bound** (worst case). You need it because a function that's fast at n=100 can be unusable at n=100,000 — and the interviewer will ask you to prove which one you have.
</Define>

**Big-O (O)** gives you the **upper bound** — worst case. "This will never be slower than this." It's the ceiling.

**Big-Θ (big-Theta)** gives you the **tight bound** — exact growth rate, up to constant factors. "This grows like exactly this." Most algorithm discussions use big-O even when they mean big-Θ. You'll do the same, but knowing the distinction saves you when an interviewer pushes.

**Big-Ω (Omega)** is the lower bound — best case. You'll rarely need it in interviews, but the interviewer who asks is usually testing whether you know the vocabulary.

The key insight: **constant factors don't matter for big-O.** `2n` and `1000n` are both `O(n)`. An `O(n)` loop that runs 5 times per element is still `O(n)`. We care about the shape of the curve, not where it starts.

### The common complexity classes — with a feel for each

### Worst, average, and amortized — three different questions

**Worst case** (`O`) is what you quote to an interviewer unless they ask otherwise. It's the guarantee. "Even if the input is adversarially bad, this won't take more than this."

**Average case** is what the algorithm typically does. Hash map lookup is `O(1)` average because hash collisions are rare with a good hash function — but worst case is `O(n)` under pathological collisions or adversarial inputs.

<Define term="Amortized O(1) — slice append">
**Amortized** means "the average cost per operation over a long run, even when individual operations vary." Go's `append` is the textbook example: most appends write one value in `O(1)`, but when the backing array is full, the runtime allocates a 2× array and copies everything — `O(n)` for that one call. Because doubling is exponential, that expensive copy happens exponentially rarely. Spread across all appends, the cost per append averages to `O(1)`. The interviewer hears "amortized `O(1)`" and knows you understand the mechanism, not just the label.
</Define>

**Amortized** is the per-operation cost *averaged over a long sequence of operations*. The famous example is `append` to a Go slice: most appends are `O(1)` (write the value), but occasionally the backing array is full and must be copied, costing `O(n)`. Amortized over all appends, the cost per append is `O(1)`. We'll animate this exactly when we get to the slice section.

### How to analyze a loop nest on the spot

The interview technique is mechanical once you practice it. Work from the innermost loop outward, multiply nested loops, and add sequential blocks.

**One loop over the input → `O(n)`:**

```go
// O(n) — one pass over all prices
for _, price := range prices {
    total += price
}
```

**Two nested loops, both over n → `O(n²)`:**

```go
// O(n²) — every pair of items
for i := range items {
    for j := range items {
        process(items[i], items[j])
    }
}
```

**Binary search inside a loop → `O(n log n)`:**

```go
// O(n log n) — for each of n items, do O(log n) work
for _, target := range queries {
    idx := sort.SearchInts(sortedList, target)
    // ...use idx
}
```

**Sequential blocks → add, not multiply:**

```go
// O(n) + O(n log n) = O(n log n)
// The sort dominates; the linear scan after it doesn't change the class.
slices.Sort(prices)                    // O(n log n)
for _, p := range prices { total += p } // O(n)
```

## Time vs Space Trade-offs

Let's talk about the single most important trade-off in interview prep — one you will use in almost every medium or hard problem.

The setup: you have an interview problem with an `O(n²)` brute-force solution. You know there's something faster. The key question is: **what information am I computing repeatedly that I could just store?**

That question leads to the canonical upgrade: **trade memory for time by caching intermediate results in a hash map.**

### The two-sum canonical example

You're building a payment-matching service. Given a list of transaction amounts and a target total, find the two transactions that sum to the target. Return their indices.

**Brute force — `O(n²)` time, `O(1)` space:**

```go
// O(n²) brute force: check every pair
func twoSumBrute(amounts []int, target int) (int, int) {
    for i := range amounts {
        for j := i + 1; j < len(amounts); j++ {
            if amounts[i]+amounts[j] == target {
                return i, j
            }
        }
    }
    return -1, -1
}
```

At 100,000 transactions, that's 5 billion comparisons. A production payment system would fall over.

**Hash map — `O(n)` time, `O(n)` space:**

```go
package main

import "fmt"

// twoSum returns the indices of the two amounts that sum to target.
// Time: O(n). Space: O(n) — we trade memory for the ability to look up
// "have I already seen the complement?" in O(1).
func twoSum(amounts []int, target int) (int, int) {
    // seen maps each amount to the index we saw it at.
    seen := make(map[int]int)
    for i, a := range amounts {
        complement := target - a
        if j, ok := seen[complement]; ok {
            return j, i // found: seen[complement] + amounts[i] == target
        }
        seen[a] = i
    }
    return -1, -1
}

func main() {
    // Payment matching: which two transactions sum to 7500 cents ($75.00)?
    amounts := []int{2000, 4500, 3000, 5500, 1500}
    i, j := twoSum(amounts, 7500)
    fmt.Printf("indices %d and %d: %d + %d = %d\n",
        i, j, amounts[i], amounts[j], amounts[i]+amounts[j])
}
```

### When to pay the memory cost — and when not to

Not every problem benefits from a map. The framework:

- **Pay memory when**: you need to look up whether something exists (dedup, complement search, frequency count), and the lookup is currently inside a loop (turning `O(n²)` into `O(n)`).
- **Don't pay memory when**: the data is already sorted (binary search gives you `O(log n)` for free), the interviewer asks for `O(1)` space, or the problem only has a constant number of distinct values (a fixed-size array beats a map).
- **Two-pointer / sliding window**: often `O(1)` extra space with `O(n)` time — the best of both worlds, but requires sorted data or a monotone property.

## The Go DSA Toolbox

Every language has primitives that map onto classic data structures. Go's are different from Python's lists and dicts, and *nothing* kills an interview faster than fighting the language. Know these cold.

### Slices as dynamic arrays and stacks

<Define term="Slice as a dynamic array / stack">
A Go **slice** is a three-word header — `(pointer, length, capacity)` — backed by an array that may live on the stack or heap depending on escape analysis. As a **dynamic array** it grows on demand via `append`; current Go doubles small slices and transitions toward ~1.25x growth for larger ones, giving amortized `O(1)` append. As a **stack** it uses `append` to push and reslice (`s = s[:len(s)-1]`) to pop, both `O(1)`. You need it because Go has no built-in list or stack type — the slice idiom IS the interview-standard tool for both.
</Define>

A Go slice is the closest thing to a Python list or Java `ArrayList`. Under the hood it's three words: a pointer to a backing array, a length, and a capacity.

```go
s := make([]int, 0, 4) // len=0, cap=4 — reserve space for 4 ints
s = append(s, 10)      // len=1, cap=4
s = append(s, 20, 30)  // len=3, cap=4 — still in the same array
s = append(s, 40)      // len=4, cap=4 — full!
s = append(s, 50)      // len=5, cap=8 — REALLOCATION: new backing array
```

The last `append` copies the old 4 elements to a new 8-element array and then writes 50. That copy is `O(n)` for that call — but it happens so rarely (every doubling) that the **amortized** cost per append is `O(1)`. Here's the animation:

<UnderTheHood title="Slice header layout and the doubling-to-1.25x growth strategy">

A slice is three machine words at runtime: a pointer `ptr` (8 bytes on 64-bit), `len int`, and `cap int`. The compiler decides where the header and backing array live; small non-escaping backing arrays can stay on the stack, while escaping or dynamically sized backing arrays usually live on the heap.

**Growth strategy (as of Go 1.24):** For small slices (cap below ~256), the runtime doubles capacity on each reallocation. For larger slices it shifts to a 1.25× factor, which trades a slightly higher allocation rate for less memory waste on very large slices. The exact threshold and formula live in `runtime/slice.go` and have been tuned across Go versions — the key invariant that matters for interviews is that growth is **exponential** (doubling family), which ensures amortized `O(1)` append.

Why not always double? If your slice is 512 MB, doubling wastes 512 MB right before the GC can collect the old array. The 1.25× factor keeps a 40 GB slice from needing 40 GB of head-room. Pragmatic.

The other critical point: **two slices can share the same backing array**. `b := a[1:3]` gives `b` its own header pointing into `a`'s array. Appending to `b` within capacity will **mutate `a`'s elements.** Once `b`'s append crosses capacity and reallocates, they diverge. This bites you in interview solutions that slice and then mutate. When in doubt, `copy`.

</UnderTheHood>

<Define term={`map[T]struct{} — the Go set`}>

<UnderTheHood title="Go map internals: Swiss tables and unspecified iteration">

Go's `map` is a hash table. As of Go 1.24, the standard runtime uses a Swiss Table-style implementation: groups of eight key-value slots plus control bytes that let the runtime reject non-matching entries quickly. This is open addressing/probing, not separate linked-list chaining.

When a table gets too full for efficient probing, the runtime grows or splits internal storage and spreads that cost across operations. Treat exact load thresholds as implementation details, not promises.

**Why is map iteration order unsafe to depend on?** The Go spec says iteration order over maps is not specified. The standard runtime deliberately varies the order, which prevents you from writing code that accidentally relies on deterministic map order. In interviews: never depend on range-over-map order without sorting first.

**Thread safety:** Go maps are *not* goroutine-safe. Concurrent reads are fine only when there are no concurrent writes. A concurrent write with another read or write is a data race; the runtime often detects map races as fatal errors, but you must not rely on that as a correctness mechanism. Use `-race`, `sync.Map`, or a `sync.Mutex`-guarded regular map.

### `container/heap` — priority queues the Go way

<Define term="container/heap — priority queue">
A **priority queue** is a data structure where `Pop` always removes the element with the highest (or lowest) priority, not just any element. Go's standard library implements this via `container/heap`: it maintains a **binary heap** — a complete binary tree stored in a slice where each parent is smaller (min-heap) or larger (max-heap) than its children. Push and Pop are both `O(log n)`. You need it for "Top K" problems, merge-K-sorted-lists, and Dijkstra's algorithm — anywhere you repeatedly need the extreme element of a changing set.
</Define>

Go's standard library includes `container/heap`, and using it is… a rite of passage. It's correct and efficient (`O(log n)` push and pop), but you must implement a four-method interface to use it. Interviewers test this specifically for "Top K" and "Merge K sorted lists" patterns.

The interface you implement:

```go
// heap.Interface embeds sort.Interface (Len, Less, Swap) plus Push and Pop.
// You provide all five. heap.Push and heap.Pop are the functions you call.
type Interface interface {
    sort.Interface   // Len() int; Less(i, j int) bool; Swap(i, j int)
    Push(x any)      // append x to the underlying collection
    Pop() any        // remove and return the last element
}
```

Here's a min-heap of integers — the exact structure you need for "find the K smallest prices":

```go
package main

import (
    "container/heap"
    "fmt"
)

// IntHeap is a min-heap of ints.
type IntHeap []int

func (h IntHeap) Len() int           { return len(h) }
func (h IntHeap) Less(i, j int) bool { return h[i] < h[j] } // min at root
func (h IntHeap) Swap(i, j int)      { h[i], h[j] = h[j], h[i] }

func (h *IntHeap) Push(x any) {
    *h = append(*h, x.(int))
}

func (h *IntHeap) Pop() any {
    old := *h
    n := len(old)
    x := old[n-1]
    *h = old[:n-1]
    return x
}

func main() {
    // Find the 3 cheapest items from a stream of prices (cents).
    prices := []int{4999, 999, 2499, 1499, 3999, 599}

    h := &IntHeap{}
    heap.Init(h)
    for _, p := range prices {
        heap.Push(h, p)
    }

    fmt.Println("3 cheapest prices (cents):")
    for i := 0; i < 3; i++ {
        fmt.Println(heap.Pop(h))
    }
}
```

### `sort.Slice` and the `slices` package (Go 1.21+)

`sort.Slice` is the workhorse for arbitrary comparisons. The `slices` package (Go 1.21, stable in Go 1.22+) provides type-safe, generic alternatives that are slightly faster because they avoid interface boxing.

### Generics for reusable structures

In Part 1 we learned Go generics in depth. Here's where they pay off for DSA: writing a type-safe `Stack[T]` and `Set[T]` instead of repeating the slice/map pattern in every solution.

```go
package main

import "fmt"

// Stack[T] is a generic LIFO stack backed by a slice.
// All operations are O(1) amortized.
type Stack[T any] struct {
    data []T
}

func (s *Stack[T]) Push(v T) {
    s.data = append(s.data, v)
}

func (s *Stack[T]) Pop() (T, bool) {
    if len(s.data) == 0 {
        var zero T
        return zero, false
    }
    top := s.data[len(s.data)-1]
    s.data = s.data[:len(s.data)-1]
    return top, true
}

func (s *Stack[T]) Peek() (T, bool) {
    if len(s.data) == 0 {
        var zero T
        return zero, false
    }
    return s.data[len(s.data)-1], true
}

func (s *Stack[T]) Len() int { return len(s.data) }

// Set[T] is a generic set backed by map[T]struct{}.
// Add, Contains, and Remove are all O(1) average.
type Set[T comparable] struct {
    m map[T]struct{}
}

func NewSet[T comparable]() *Set[T] {
    return &Set[T]{m: make(map[T]struct{})}
}

func (s *Set[T]) Add(v T)          { s.m[v] = struct{}{} }
func (s *Set[T]) Remove(v T)       { delete(s.m, v) }
func (s *Set[T]) Contains(v T) bool {
    _, ok := s.m[v]
    return ok
}
func (s *Set[T]) Len() int { return len(s.m) }

func main() {
    // Generic Stack[string] — tracking a path in a graph traversal
    var path Stack[string]
    path.Push("root")
    path.Push("childA")
    path.Push("leaf")

    for path.Len() > 0 {
        node, _ := path.Pop()
        fmt.Println("visited:", node)
    }

    // Generic Set[int] — deduplicating transaction amounts
    unique := NewSet[int]()
    amounts := []int{1000, 2000, 1000, 3000, 2000}
    for _, a := range amounts {
        unique.Add(a)
    }
    fmt.Println("unique count:", unique.Len()) // 3
}
```

<UnderTheHood title="How Go generics are compiled: GC shape stenciling">

Go compiles generics via **GC shape stenciling** (as of Go 1.24): the compiler groups types by their "GC shape" — their memory layout and pointer structure — and generates one machine-code instantiation per shape, not per type.

For `Stack[int]` and `Stack[int64]`: both are pointer-free 8-byte values with the same GC shape, so they share one compiled body. A dictionary (essentially a vtable) carries type-specific behavior (zero value, `==`) as a runtime argument. For `Stack[*Transaction]`: all pointer types share one shape too.

The practical impact for you in interviews: generic Go code has **near-zero overhead** for concrete types (the compiler inlines and specializes), but calling a method through a generic constraint backed by an interface adds one dictionary indirection. For stack/set/heap structures over `int` or `string`, generics are essentially free. This is the opposite of Java generics (type erasure + boxing).

<Exercise n={1} title="Analyze the nested loop" level="easy">

Given this function:

```go
func pairwiseSum(prices []int) int {
    total := 0
    for i := range prices {
        for j := i + 1; j < len(prices); j++ {
            total += prices[i] + prices[j]
        }
    }
    return total
}
```

State the time complexity and the space complexity, and explain your reasoning in one sentence each. Then identify whether this can be improved to `O(n)` with a mathematical observation (hint: how many times does `prices[i]` appear in the sum?).

<Solution>

**Time: `O(n²)`** — the outer loop runs `n` times; the inner loop runs up to `n-1` times for `i=0`, shrinking by one each time. Total iterations: `n(n-1)/2 ≈ n²/2`, which is `O(n²)`.

**Space: `O(1)`** — only a constant number of extra variables (`total`, `i`, `j`). No data structure grows with input.

**`O(n)` improvement:** `prices[i]` appears exactly `n-1` times in the full sum (once paired with each other element). So `pairwiseSum = (n-1) × sum(prices)`. Compute the sum in one pass, multiply — `O(n)` time, `O(1)` space.

```go
func pairwiseSumFast(prices []int) int {
    sum := 0
    for _, p := range prices {
        sum += p
    }
    return (len(prices) - 1) * sum
}
```

<Exercise n={2} title="Slice as a stack — valid parentheses" level="easy">

Implement `isValid(s string) bool` using a `[]byte` slice as a stack. The function returns `true` if every opening bracket in `s` has a matching closing bracket in the correct order. Valid pairs: `()`, `[]`, `{}`. Example: `"([{}])"` → `true`, `"([)]"` → `false`.

State the time and space complexity.

<Solution>

```go
package main

import "fmt"

func isValid(s string) bool {
	var stack []byte
	match := map[byte]byte{
		')': '(',
		']': '[',
		'}': '{',
	}
	for i := 0; i < len(s); i++ {
		c := s[i]
		if c == '(' || c == '[' || c == '{' {
			stack = append(stack, c)
		} else {
			// closing bracket — stack must be non-empty and top must match
			if len(stack) == 0 || stack[len(stack)-1] != match[c] {
				return false
			}
			stack = stack[:len(stack)-1] // pop
		}
	}
	return len(stack) == 0 // must have consumed all openers
}

func main() {
	fmt.Println(isValid("([{}])")) // true
	fmt.Println(isValid("([)]"))   // false
	fmt.Println(isValid("{[]()}")) // true
}
```

**Time: `O(n)`** — one pass over the string.
**Space: `O(n)`** — worst case the stack holds all `n` characters (e.g., `"(((("`).

<Exercise n={3} title="Set intersection" level="medium">

Implement `intersection(a, b []string) []string` that returns a slice of strings present in both `a` and `b`, with no duplicates in the result. Use `map[string]struct{}` for `O(n+m)` time complexity. State the complexity.

<Solution>

```go
package main

import "fmt"

func intersection(a, b []string) []string {
	// Build a set from a — O(n)
	setA := make(map[string]struct{}, len(a))
	for _, v := range a {
		setA[v] = struct{}{}
	}

	// Walk b and collect matches — O(m)
	// seen prevents duplicates in the result
	seen := make(map[string]struct{})
	var result []string
	for _, v := range b {
		if _, inA := setA[v]; inA {
			if _, already := seen[v]; !already {
				result = append(result, v)
				seen[v] = struct{}{}
			}
		}
	}
	return result
}

func main() {
	a := []string{"tx-1", "tx-2", "tx-3", "tx-2"}
	b := []string{"tx-2", "tx-4", "tx-1", "tx-2"}
	fmt.Println(intersection(a, b)) // [tx-2 tx-1] (order may vary)
}
```

**Time: `O(n + m)`** — one pass to build `setA`, one pass over `b`.
**Space: `O(n + k)`** — `setA` is `O(n)`, result is `O(k)` where `k` is the intersection size.

<Exercise n={4} title="Top-K frequent elements" level="medium">

Given `[]int` of transaction amounts and an integer `k`, return the `k` most frequently occurring amounts. Use a `map[int]int` frequency counter and a `container/heap` min-heap to keep only the top `k`. State the complexity.

<Solution>

```go
package main

import (
	"container/heap"
	"fmt"
)

// freqHeap is a min-heap ordered by frequency.
type freqItem struct{ val, freq int }
type freqHeap []freqItem

func (h freqHeap) Len() int           { return len(h) }
func (h freqHeap) Less(i, j int) bool { return h[i].freq < h[j].freq } // min at root
func (h freqHeap) Swap(i, j int)      { h[i], h[j] = h[j], h[i] }
func (h *freqHeap) Push(x any)        { *h = append(*h, x.(freqItem)) }
func (h *freqHeap) Pop() any {
	old := *h
	n := len(old)
	x := old[n-1]
	*h = old[:n-1]
	return x
}

func topKFrequent(amounts []int, k int) []int {
	// Count frequencies — O(n)
	freq := make(map[int]int)
	for _, a := range amounts {
		freq[a]++
	}

	// Keep a min-heap of size k — O(n log k)
	h := &freqHeap{}
	heap.Init(h)
	for val, f := range freq {
		heap.Push(h, freqItem{val, f})
		if h.Len() > k {
			heap.Pop(h) // remove the least frequent
		}
	}

	result := make([]int, k)
	for i := k - 1; i >= 0; i-- {
		result[i] = heap.Pop(h).(freqItem).val
	}
	return result
}

func main() {
	amounts := []int{1000, 500, 1000, 2000, 500, 1000, 2000, 2000, 500}
	fmt.Println(topKFrequent(amounts, 2)) // [1000 2000] or [2000 1000]
}
```

**Time: `O(n log k)`** — counting is `O(n)`; each of the `n` distinct values does one heap push and occasionally one pop, each `O(log k)`.
**Space: `O(n + k)`** — the frequency map is `O(n)`; the heap holds at most `k` items.

Why `O(n log k)` beats full sort `O(n log n)`: when `k << n`, `log k` is much smaller than `log n`. For "top 10 out of a million," that's a massive win.

</Solution>

```go
package main

import (
	"errors"
	"fmt"
)

var (
	ErrFull  = errors.New("stack is full")
	ErrEmpty = errors.New("stack is empty")
)

type BoundedStack[T any] struct {
	data []T
	cap  int
}

func NewBoundedStack[T any](capacity int) *BoundedStack[T] {
	return &BoundedStack[T]{
		data: make([]T, 0, capacity),
		cap:  capacity,
	}
}

func (s *BoundedStack[T]) Push(v T) error {
	if len(s.data) >= s.cap {
		return ErrFull
	}
	s.data = append(s.data, v)
	return nil
}

func (s *BoundedStack[T]) Pop() (T, error) {
	if len(s.data) == 0 {
		var zero T
		return zero, ErrEmpty
	}
	top := s.data[len(s.data)-1]
	s.data = s.data[:len(s.data)-1]
	return top, nil
}

func (s *BoundedStack[T]) Peek() (T, error) {
	if len(s.data) == 0 {
		var zero T
		return zero, ErrEmpty
	}
	return s.data[len(s.data)-1], nil
}

func (s *BoundedStack[T]) Len() int { return len(s.data) }

func main() {
	st := NewBoundedStack[int](2)

	fmt.Println(st.Push(10))           // <nil>
	fmt.Println(st.Push(20))           // <nil>
	fmt.Println(st.Push(30))           // stack is full
	top, err := st.Peek()
	fmt.Println(top, err)              // 20 <nil>
	v, err := st.Pop()
	fmt.Println(v, err)                // 20 <nil>
	v, err = st.Pop()
	fmt.Println(v, err)                // 10 <nil>
	v, err = st.Pop()
	fmt.Println(v, err)                // 0 stack is empty
}
```

**Complexity:** Push/Pop/Peek all `O(1)`. The pre-allocated backing array (`make([]T, 0, capacity)`) ensures the first `capacity` pushes never reallocate.

<Recap>

You now own the chapter's core:

- **Big-O** is the upper bound on growth rate; **big-Θ** is the tight bound. Constant factors are irrelevant — only the shape of the curve matters. Quote worst case unless asked otherwise, and always be ready for "can you do better?"
- **Worst, average, amortized** are three different things. `append` is `O(1)` amortized because the doubling strategy makes reallocations exponentially rare.
- **Analyzing loops**: multiply nested loops, add sequential blocks, keep the dominant term. Two nested `O(n)` loops → `O(n²)`. A sort followed by a scan → `O(n log n)`.
- **The map trade-off**: trading `O(n)` space for `O(1)` lookup, turning `O(n²)` brute force into `O(n)`. This is the most useful single move in interview prep.
- **The Go toolbox**: slices as dynamic arrays and stacks (`append`/reslice, amortized `O(1)`); `map[T]struct{}` as the zero-waste set; `container/heap` for `O(log n)` priority queues (implement the five-method interface); `sort.Slice` and `slices.SortFunc` for arbitrary ordering; generics (`Stack[T]`, `Set[T]`) for reusable, type-safe structures.
- **Slice header** is `(ptr, len, cap)`. Growth is about 2× for small slices and trends toward ~1.25× for large slices. Two slices can share backing arrays — copy when in doubt.
- **Map internals**: Swiss Table-style groups and probing in current Go, amortized growth, unspecified iteration order, not goroutine-safe.
