Now tell me, what happens when Step 4 fails because the SWIFT gateway returns HTTP 504 Gateway Timeout? Or worse: what if the worker process running Step 4 runs out of memory and crashes while the HTTP socket is still open?

Did SWIFT receive the wire or not?
Is the \$10,000,000 gone?
Did you debit the customer without sending the money?
If you retry, will you send \$20,000,000?

In traditional systems, you try to solve this with what I affectionately call the **Amateur Distributed Toolkit**:
- You set up a cron job that runs every two minutes, running `SELECT * FROM transfers WHERE status = 'PENDING'`.
- You add a `locked_at` column in Postgres, which immediately creates deadlocks under concurrent write traffic.
- You wrap calls in Redis distributed locks with an arbitrary 30-second TTL—and when your network hiccups for 31 seconds, the lock expires, two workers process the same transfer, and you just double-spent ten million dollars of corporate capital.

<Define term="Durable Execution">
A distributed programming paradigm where an application's execution state—including its local variables, call stack, thread scheduling, timers, and pending promises—is transparently persisted to an immutable event store. If the underlying process, server, container, or network fails, the program automatically reconstructs its exact memory state and resumes execution from the point of failure without loss of state or duplication of side effects.
</Define>

### The Temporal Architecture: Brains vs. Brawn

Temporal cleanly decouples your system into two distinct planes:

1. **The Temporal Cluster (The Orchestrator / Brains)**:
   A distributed, horizontally scalable cluster consisting of four internal services:
   - **Frontend**: Stateless gRPC gatekeeper handling incoming client requests and worker long-polling.
   - **Matching**: High-throughput distributed queue manager routing Workflow Tasks and Activity Tasks to worker queues.
   - **History**: Sharded state engine responsible for appending events to the immutable log, managing distributed timers, and locking workflow executions.
   - **Worker**: Internal background manager for cluster maintenance, batch operations, and system workflows.
   Crucially: **The Temporal Cluster never executes your application code.** It does not know Go, it does not run your business logic, and it never touches your private VPC resources. It only records and orchestrates events.

2. **The Temporal Workers (Your Application Code / Brawn)**:
   Standard Go binaries written by you, running in your Kubernetes clusters, serverless containers, or bare-metal instances. Workers establish long-polling gRPC connections to the Temporal Cluster over port 7233. When a task is ready, the cluster pushes the task to an available worker.

<Define term="Event History">
An append-only, sequentially ordered log of state transitions for a single workflow execution. Every decision taken by the workflow, every activity scheduled or completed, every timer fired, and every external signal received is immutably recorded with a monotonically increasing event ID.
</Define>

### Workflows vs. Activities: The Sacred Separation

To build fault-tolerant systems in Temporal, you must respect the absolute division of responsibility between Workflows and Activities:

- **Workflows (The Conductor)**:
  A workflow is a Go function that orchestrates business logic. It expresses *what* should happen, in what order, and how errors must be compensated. It can sleep for five minutes, wait three weeks for a loan officer's signature, or loop for ten years. However, a workflow must be **100% deterministic**. It cannot execute network calls, read the filesystem, or interact directly with the physical world.

- **Activities (The Side-Effect Workers)**:
  An activity is a Go function that actually performs real-world, non-deterministic I/O: executing SQL queries, calling third-party REST APIs, reading files, generating cryptographic keys, or dispatching emails. Activities are given automated retry policies, heartbeats, and timeouts.

Here is what a production Meridian wire transfer workflow looks like in idiomatic Temporal Go:

```go
package workflow

import (
	"time"

	"go.temporal.io/sdk/temporal"
	"go.temporal.io/sdk/workflow"
)

type WireTransferRequest struct {
	TransferID    string
	SenderAccount string
	TargetAccount string
	AmountCents   int64
	Currency      string
	TargetSwift   string
}

type WireTransferResult struct {
	ConfirmationNumber string
	SettledAt          time.Time
}

// MeridianWireWorkflow coordinates the multi-step international wire settlement.
// This function MUST be strictly deterministic.
func MeridianWireWorkflow(ctx workflow.Context, req WireTransferRequest) (*WireTransferResult, error) {
	// Configure retry policy for transient activity failures
	ao := workflow.ActivityOptions{
		StartToCloseTimeout: 30 * time.Second,
		HeartbeatTimeout:    5 * time.Second,
		RetryPolicy: &temporal.RetryPolicy{
			InitialInterval:    1 * time.Second,
			BackoffCoefficient: 2.0,
			MaximumInterval:    30 * time.Second,
			MaximumAttempts:    5,
			NonRetryableErrorTypes: []string{
				"ErrSanctionsViolation",
				"ErrAccountFrozen",
				"ErrInsufficientFunds",
			},
		},
	}
	ctx = workflow.WithActivityOptions(ctx, ao)

	// Step 1: Hold Source Funds
	var holdID string
	err := workflow.ExecuteActivity(ctx, HoldFundsActivity, req.SenderAccount, req.AmountCents).Get(ctx, &holdID)
	if err != nil {
		return nil, err
	}

	// Step 2: Sanctions & OFAC Screening
	var cleared bool
	err = workflow.ExecuteActivity(ctx, SanctionsScreenActivity, req.SenderAccount, req.TargetAccount).Get(ctx, &cleared)
	if err != nil || !cleared {
		// Compensating action: release held funds if sanctions fail
		_ = workflow.ExecuteActivity(ctx, ReleaseFundsActivity, holdID).Get(ctx, nil)
		return nil, err
	}

	// Step 3: Dispatch SWIFT MT103 wire
	var swiftConfirmation string
	err = workflow.ExecuteActivity(ctx, DispatchSwiftActivity, req, holdID).Get(ctx, &swiftConfirmation)
	if err != nil {
		// Downstream failure: trigger compensating rollback
		_ = workflow.ExecuteActivity(ctx, ReleaseFundsActivity, holdID).Get(ctx, nil)
		return nil, err
	}

	return &WireTransferResult{
		ConfirmationNumber: swiftConfirmation,
		SettledAt:          workflow.Now(ctx),
	}, nil
}
```

Look at that code, sport. Clean, linear, readable Go code. No database status polling. No callback hell. No distributed transaction monitors. If the host machine crashes during `DispatchSwiftActivity`, the Temporal cluster waits for the timeout, re-assigns the task, and resumes execution seamlessly.

## The Replay Engine & Determinism

Now we step inside the engine room. How does Temporal achieve this sorcery without checkpointing the entire multi-gigabyte memory image of the Go runtime?

The answer is **Event History Replay**.

When a worker crashes, Temporal does not save the CPU registers or RAM heap of your Go process. Instead, Temporal stores the sequence of events that occurred. When another worker takes over the workflow execution, it starts running your workflow function from line 1.

Every time your code calls `workflow.ExecuteActivity` or `workflow.Sleep`, the Temporal SDK intercepts the call. It looks up the current step in the Event History. If an `ActivityTaskCompleted` event is already recorded for that step, the SDK **does not call the activity again**. Instead, it unpacks the recorded result from the event log, unblocks the future immediately, and lets the Go coroutine race forward to the next line of code.

Introducing non-deterministic logic into a workflow function causes history verification mismatches and crashes the execution.
</Define>

### The Seven Deadly Sins of Workflow Non-Determinism

Because replay relies on your code taking the exact same branch every time it runs, any deviation in execution path will corrupt the state machine. The Temporal Go SDK monitors this vigilantly. If your code produces a different command than what the Event History expects, the SDK immediately throws a `NonDeterministicWorkflowError` and halts the workflow task.

Commit these seven prohibitions to memory:

1. **Never call `time.Now()`**:
   The system clock changes every nanosecond. During replay, `time.Now()` would return a time hours or days later than the original run. Use `workflow.Now(ctx)` instead, which returns the deterministic timestamp recorded in the current `WorkflowTaskStarted` event.
2. **Never call `time.Sleep()`**:
   `time.Sleep` blocks the physical OS thread, freezing the worker. Use `workflow.Sleep(ctx, duration)` instead, which registers a durable timer with the Temporal cluster and yields the coroutine.
3. **Never spawn native goroutines with `go func()`**:
   Native goroutines are scheduled non-deterministically by the Go runtime's GMP scheduler. Use `workflow.Go(ctx, func(ctx workflow.Context))` instead, which runs inside the SDK's deterministic cooperative coroutine scheduler.
4. **Never iterate over native Go maps directly**:
   The Go runtime deliberately randomizes map iteration order by seeding the hash seed on each iteration. If you iterate over a map to schedule activities, they will be scheduled in a random order on each replay, instantly breaking determinism. Always extract keys, sort them with `slices.Sort()`, and iterate the sorted slice.
5. **Never read mutable global variables or environment configurations**:
   If a feature flag or global variable changes while a workflow is in flight, the replayed execution might take a different `if/else` branch than the original execution, triggering a fatal non-determinism error.
6. **Never generate random numbers or UUIDs directly**:
   Calling `rand.Int()` or `uuid.New()` generates different values on replay. If you need a random value or UUID, generate it inside an Activity or wrap it in `workflow.SideEffect(ctx, func(ctx workflow.Context) interface{} { return uuid.NewString() })`.
7. **Never perform direct network, database, or disk I/O**:
   No `http.Get()`, no `sql.Open()`, no `os.ReadFile()` inside workflow functions. All I/O operations belong exclusively inside **Activities**.

<UnderTheHood title="Temporal Replay Mechanics, Coroutines & Non-Determinism Detection">

How does the Temporal Go SDK actually control goroutine execution without hacking the Go compiler?

Inside `go.temporal.io/sdk/internal`, Temporal implements its own user-space cooperative coroutine scheduler (`coroutine.go`). When a workflow task arrives:

1. **The Single-Threaded Turn Invariant**:
   A workflow execution turn is strictly single-threaded. When the SDK evaluates your workflow, it runs on an internal coroutine backed by a native Go channel handshake. When you call `workflow.Go`, the SDK does *not* invoke the runtime `go` statement. It registers a child coroutine in an internal scheduler run queue.
2. **Channel and Future Virtualization**:
   Every synchronization primitive in the SDK (`workflow.Channel`, `workflow.Selector`, `workflow.Future`) is virtualized. When your code calls `future.Get(ctx, &result)`, the SDK checks if the result is already available in the Event History. If it is, the value is deserialized and the coroutine continues immediately. If the result is pending, the SDK parks the current coroutine and yields control back to the task dispatcher.
3. **Workflow History Hash Verification**:
   As the workflow function executes, every call to schedule an activity, start a timer, or complete execution generates an internal **Command** (`ScheduleActivityTaskCommand`, `StartTimerCommand`). The SDK compares the generated command stream with the expected events in the downloaded Event History. If event #14 in history is `ActivityTaskScheduled{Name: "DispatchSwift"}` but your replayed code emitted `ActivityTaskScheduled{Name: "SendEmail"}`, the SDK detects a command mismatch. It immediately aborts with:
   ```
   workflow task failed with non-deterministic error:
   event 14 is ActivityTaskScheduled with name 'DispatchSwift',
   but workflow generated command 'ScheduleActivityTask' with name 'SendEmail'
   ```
4. **Virtual Time vs. Physical Time**:
   Notice the conceptual parallel between Temporal's virtual workflow clock and the `testing/synctest` package introduced in Go 1.25. Just as `testing/synctest` isolates goroutines inside a virtualized time bubble where timers advance instantaneously when all goroutines are idle, the Temporal SDK ties `workflow.Now(ctx)` directly to the timestamp of the current `WorkflowTaskStarted` event. During replay of a workflow that started three weeks ago, `workflow.Now(ctx)` yields the exact historical timestamp from three weeks ago, preserving mathematical determinism.

</UnderTheHood>

## Activities & Heartbeating

Now let us focus on the workers doing the heavy lifting: **Activities**.

While workflows are fragile, deterministic conductors, activities are battle-hardened workhorses. An activity is where you talk to PostgreSQL, query Redis, invoke third-party REST endpoints, send gRPC messages, and generate PDF mortgage contracts.

<Define term="Activity">
A function representing a single, non-deterministic unit of work in a distributed system. Activities interact with external resources, undergo automated retries with exponential backoff, emit liveness heartbeats, and are executed by worker processes listening on specific Task Queues.
</Define>

### The Four Activity Timeouts

When you invoke an activity, you must configure its timeout constraints. If you misconfigure these, your distributed system will either fail prematurely or hang silently for hours.

1. **`ScheduleToStart`**:
   The maximum duration an activity task can sit in the Temporal Matching Task Queue waiting for an available worker to poll it.
   *What it detects*: Worker fleet starvation, unassigned task queues, or severe cluster backpressure.
2. **`StartToClose`**:
   The maximum duration a single worker can take to execute the activity once it picks up the task.
   *What it detects*: Deadlocks, infinite loops, or hanging network sockets inside the activity implementation.
3. **`ScheduleToClose`**:
   The total overall time allowed for the activity from initial scheduling to final completion, encompassing all retries and queue wait times.
   *What it detects*: Overall failure of an activity to succeed within an end-to-end business SLA.
4. **`HeartbeatTimeout`**:
   The maximum time allowed between heartbeats emitted by an actively executing activity worker.
   *What it detects*: Hard worker crashes, OOM kills, kernel panics, and network partitions in near real-time.

<Define term="Heartbeat">
A periodic liveness notification sent from an active activity worker back to the Temporal Cluster. A heartbeat proves that the worker is making forward progress and can carry an optional progress payload (such as batch offsets), enabling fast failure detection and checkpointed recovery.
</Define>

### The Fatal Footgun: Missing HeartbeatTimeout

Consider this production horror story:
At Meridian, a nightly reconciliation activity reconciles 500,000 corporate ledger entries against the Federal Reserve clearing file. Because this job takes 90 minutes to complete under normal load, a junior engineer configures:
`StartToCloseTimeout = 2 * time.Hour`

At minute 4 of the job, the Kubernetes pod running the activity is OOM-killed because another process on the same node spiked memory.

Because no `HeartbeatTimeout` was configured, what does the Temporal cluster do?
**It waits. It waits for one hour and fifty-six minutes.**
The cluster cannot distinguish between a healthy worker computing complex math and a dead worker whose physical container ceased to exist. Only after the full two hours elapse does `StartToCloseTimeout` fire and schedule a retry.

Now observe the professional approach:
```go
ao := workflow.ActivityOptions{
	StartToCloseTimeout: 2 * time.Hour,
	HeartbeatTimeout:    30 * time.Second, // Crash detected in 30 seconds!
}
```
If the worker crashes, the cluster notices the missing heartbeat within 30 seconds and re-dispatches the activity to a healthy worker immediately.

### Checkpointed Progress via Heartbeats

Heartbeats do more than signal liveness—they preserve progress checkpoints. If an activity is processing a large batch of 100,000 records, you do not want a failure on record 99,999 to restart the entire batch from zero.

```go
func ReconcileLedgerBatchActivity(ctx context.Context, batchID string) error {
	// Check if this activity is a retry and has a previous heartbeat checkpoint
	var lastProcessedIndex int
	if activity.HasHeartbeatDetails(ctx) {
		_ = activity.GetHeartbeatDetails(ctx, &lastProcessedIndex)
	}

	records := loadRecords(batchID)
	for i := lastProcessedIndex; i < len(records); i++ {
		// Check if the workflow requested activity cancellation
		select {
		case <-ctx.Done():
			return ctx.Err()
		default:
		}

		processRecord(records[i])

		// Emit heartbeat every 100 items with current progress checkpoint
		if i%100 == 0 {
			activity.RecordHeartbeat(ctx, i)
		}
	}
	return nil
}
```

### Writing Idempotent Activities

Because activities can and will be retried when networks flap or hosts die, **every activity that produces a side effect must be idempotent**.

If an activity debits a bank account:
- Bad: `UPDATE accounts SET balance = balance - 100 WHERE id = 42;` (Running this twice steals \$200!)
- Good: Use an idempotency key generated by the deterministic workflow:
  ```sql
  INSERT INTO account_transactions (idempotency_key, account_id, amount_cents)
  VALUES ($1, $2, $3)
  ON CONFLICT (idempotency_key) DO NOTHING;
  ```

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"math"
	"math/rand/v2"
	"time"
)

// RetryPolicy defines automated retry behavior for activities.
type RetryPolicy struct {
	InitialInterval    time.Duration
	BackoffCoefficient float64
	MaximumInterval    time.Duration
	MaximumAttempts    int
}

// ActivityTask encapsulates the unit of work and its heartbeat state.
type ActivityTask struct {
	ID                 string
	LastCheckpoint     int
	HeartbeatTimeout   time.Duration
	LastHeartbeatTime  time.Time
}

// ExecuteWithRetry simulates the Temporal activity execution harness.
func ExecuteWithRetry(ctx context.Context, policy RetryPolicy, task *ActivityTask, fn func(checkpoint int, recordHeartbeat func(int)) (string, error)) (string, error) {
	attempt := 0
	currInterval := policy.InitialInterval

	for {
		attempt++
		fmt.Printf(">> Attempt %d/%d for Activity [%s] (Resuming from checkpoint: %d)...
",
			attempt, policy.MaximumAttempts, task.ID, task.LastCheckpoint)

		// Heartbeat callback supplied to the activity implementation
		recordHeartbeat := func(progress int) {
			task.LastCheckpoint = progress
			task.LastHeartbeatTime = time.Now()
			fmt.Printf("   [HEARTBEAT] Progress recorded at checkpoint: %d
", progress)
		}

		result, err := fn(task.LastCheckpoint, recordHeartbeat)
		if err == nil {
			fmt.Printf(">> Activity [%s] SUCCEEDED on attempt %d!
", task.ID, attempt)
			return result, nil
		}

		fmt.Printf("   [FAILURE] Attempt %d failed with error: %v
", attempt, err)
		if attempt >= policy.MaximumAttempts {
			return "", fmt.Errorf("activity exceeded max attempts (%d): %w", policy.MaximumAttempts, err)
		}

		// Calculate exponential backoff with full jitter
		jitterFactor := 0.5 + rand.Float64()*0.5
		sleepDuration := time.Duration(float64(currInterval) * jitterFactor)
		fmt.Printf("   [BACKOFF] Sleeping for %v before next attempt...

", sleepDuration)
		time.Sleep(sleepDuration)

		// Increment backoff up to maximum
		currInterval = time.Duration(math.Min(
			float64(currInterval)*policy.BackoffCoefficient,
			float64(policy.MaximumInterval),
		))
	}
}

func main() {
	task := &ActivityTask{
		ID:               "ReconcileBatch-8821",
		LastCheckpoint:   0,
		HeartbeatTimeout: 100 * time.Millisecond,
	}

	policy := RetryPolicy{
		InitialInterval:    10 * time.Millisecond,
		BackoffCoefficient: 2.0,
		MaximumInterval:    100 * time.Millisecond,
		MaximumAttempts:    4,
	}

	executionCount := 0

	// Simulating an activity that fails halfway through on attempt 1, then succeeds on attempt 2
	result, err := ExecuteWithRetry(context.Background(), policy, task, func(startOffset int, heartbeat func(int)) (string, error) {
		executionCount++
		records := []string{"tx1_valid", "tx2_valid", "tx3_valid", "tx4_valid", "tx5_valid"}

		for i := startOffset; i < len(records); i++ {
			// Simulate progress heartbeat
			heartbeat(i + 1)

			// Simulate crash at record 3 on first attempt
			if executionCount == 1 && i == 2 {
				return "", errors.New("transient database connection reset by peer")
			}
		}

		return "BATCH_RECONCILED_SUCCESS", nil
	})

	if err != nil {
		fmt.Printf("Final result: ERROR %v
", err)
	} else {
		fmt.Printf("Final result: OK %s
", result)
	}
}
```

## Signals & Human-in-the-Loop Gates

Not all distributed processes complete in milliseconds. Some workflows need to pause for days, weeks, or months waiting for external real-world events.

Consider the **Meridian Commercial Mortgage Underwriting Workflow**:
1. An applicant applies for a \$5,000,000 commercial mortgage loan.
2. The workflow executes automated underwriting activities in 3 seconds (credit history, title search, tax record verification).
3. Under federal banking regulations, a loan of this magnitude **requires explicit manual sign-off from a Senior Risk Officer**.
4. The workflow must suspend execution and wait up to **14 days** for a human officer to inspect the application in an internal dashboard and click **Approve** or **Reject**.
5. If the officer approves within 14 days, the workflow proceeds to disburse funds.
6. If the 14-day window expires without a response, the application is automatically cancelled and an expiration notice is dispatched.

In an amateur architecture, you would maintain an `approvals` SQL table, run periodic cron polling jobs, and pray that when the webhook arrives, your state machine transitions cleanly without race conditions.

In Temporal, you do this with a **Signal** and a **Selector**.

<Define term="Signal">
An asynchronous message sent from an external client or system into a running workflow execution. Signals deliver payloads and trigger state transitions in the workflow without disturbing its durable execution history.
</Define>

<Define term="Query">
A synchronous, read-only operation that interrogates the live in-memory state of a workflow execution from an external client. Queries return immediately and do not append events to the Event History.
</Define>

<Define term="Continue-As-New">
An atomic orchestration primitive that completes the current workflow execution and immediately initiates a new execution with the same Workflow ID but a fresh, truncated Event History. This prevents unbounded event log growth in perpetual or high-throughput workflows.
</Define>

### Coordinating Signals and Timers with Selectors

The Temporal Go SDK provides `workflow.NewSelector(ctx)`, a deterministic counterpart to Go's native `select` statement. A selector allows a workflow coroutine to wait concurrently on multiple channels, activity futures, and durable timers:

```go
type ApprovalDecision struct {
	Approved  bool
	OfficerID string
	Notes     string
}

func CommercialMortgageWorkflow(ctx workflow.Context, appID string) error {
	// Initialize workflow query handler so internal web portal can inspect status
	status := "PENDING_OFFICER_REVIEW"
	err := workflow.SetQueryHandler(ctx, "GetStatus", func() (string, error) {
		return status, nil
	})
	if err != nil {
		return err
	}

	// Prepare signal channel for human officer input
	signalChan := workflow.GetSignalChannel(ctx, "OfficerDecisionSignal")

	// Set up durable 14-day timer
	timerFuture := workflow.NewTimer(ctx, 14*24*time.Hour)

	var decision ApprovalDecision
	hasDecision := false
	timedOut := false

	// Build deterministic Selector
	selector := workflow.NewSelector(ctx)

	// Branch 1: Human-in-the-loop signal received
	selector.AddReceive(signalChan, func(c workflow.ReceiveChannel, more bool) {
		c.Receive(ctx, &decision)
		hasDecision = true
	})

	// Branch 2: 14-day timeout expired
	selector.AddFuture(timerFuture, func(f workflow.Future) {
		timedOut = true
	})

	// Wait until EITHER the signal arrives OR the 14-day timer expires
	selector.Select(ctx)

	if timedOut {
		status = "EXPIRED"
		return workflow.ExecuteActivity(ctx, SendExpirationNoticeActivity, appID).Get(ctx, nil)
	}

	if decision.Approved {
		status = "APPROVED"
		return workflow.ExecuteActivity(ctx, DisburseLoanFundsActivity, appID, decision.OfficerID).Get(ctx, nil)
	}

	status = "REJECTED"
	return workflow.ExecuteActivity(ctx, SendRejectionNoticeActivity, appID, decision.Notes).Get(ctx, nil)
}
```

Look at that beauty, sport. The workflow pauses at `selector.Select(ctx)`. While waiting for two weeks:
- No CPU is consumed.
- No OS threads are blocked.
- No database connection pools are held open.
- The workflow state is saved as an idle record in the Temporal cluster.
- When the loan officer clicks "Approve" in the internal React portal on Day 9, the portal backend calls `temporalClient.SignalWorkflow(...)`. The cluster wakes up a worker, replays the workflow state, fires the receive callback, and disburses the funds.

### Preventing History Bloat with Continue-As-New

Every signal received, activity completed, and timer triggered appends an entry to the workflow's Event History.

Temporal recommends keeping the event count for a single workflow execution under **10,000 events** (with a hard warning threshold at 50,000 events or 50MB). If a workflow runs continuously—such as an automated Meridian fraud monitoring loop that processes daily account statements indefinitely—the Event History will eventually become too massive to replay efficiently.

The solution is **`workflow.NewContinueAsNewError`**. When invoked, it atomically terminates the current execution and immediately starts a new execution with the same Workflow ID, a new Run ID, and a completely fresh, empty Event History:

```go
func AccountMonitoringWorkflow(ctx workflow.Context, accountID string, iteration int) error {
	// Periodic monitoring logic...
	workflow.Sleep(ctx, 24*time.Hour)

	// Clean rollover after 500 daily iterations to prevent event log bloat
	if iteration >= 500 {
		return workflow.NewContinueAsNewError(ctx, AccountMonitoringWorkflow, accountID, 0)
	}

	return AccountMonitoringWorkflow(ctx, accountID, iteration+1)
}
```

### The Distributed Saga Pattern in Temporal

In distributed systems where Two-Phase Commit is impossible, we manage failure with **Sagas**. A Saga is a sequence of local transactions where every forward action has a matching **compensating transaction**.

If a transfer requires three forward steps:
1. `HoldFunds` $ightarrow$ Compensating Action: `ReleaseFunds`
2. `LockFXRate` $ightarrow$ Compensating Action: `UnlockFXRate`
3. `DispatchSwift` $ightarrow$ Point of No Return

If Step 3 fails because the destination bank code is invalid, the workflow catches the error and executes the compensating actions in **strict reverse order (LIFO: Last In, First Out)**.

Here is a runnable pure Go Distributed Saga Coordinator. It registers forward steps alongside reverse compensation handlers. When a downstream step fails, it automatically unwinds previously completed steps in reverse order, verifying that account balances balance to zero.

<GoPlayground>

```go
package main

import (
	"context"
	"errors"
	"fmt"
)

// SagaStep defines an action and its corresponding rollback compensation.
type SagaStep struct {
	Name       string
	Execute    func(ctx context.Context) error
	Compensate func(ctx context.Context) error
}

// DistributedSagaCoordinator manages forward execution and reverse compensation.
type DistributedSagaCoordinator struct {
	steps       []SagaStep
	completed   []SagaStep
	compensated []string
}

func NewSagaCoordinator() *DistributedSagaCoordinator {
	return &DistributedSagaCoordinator{
		steps:       make([]SagaStep, 0),
		completed:   make([]SagaStep, 0),
		compensated: make([]string, 0),
	}
}

func (s *DistributedSagaCoordinator) AddStep(step SagaStep) {
	s.steps = append(s.steps, step)
}

// Execute runs all forward steps. On error, it rolls back completed steps in reverse LIFO order.
func (s *DistributedSagaCoordinator) Execute(ctx context.Context) error {
	for _, step := range s.steps {
		fmt.Printf(">> [FORWARD] Executing step: %s
", step.Name)
		err := step.Execute(ctx)
		if err != nil {
			fmt.Printf("!! [FAILURE] Step '%s' failed: %v. Initiating SAGA ROLLBACK...
", step.Name, err)
			s.rollback(ctx)
			return fmt.Errorf("saga aborted at step '%s': %w", step.Name, err)
		}
		s.completed = append(s.completed, step)
	}
	fmt.Println(">> All forward saga steps completed successfully!")
	return nil
}

func (s *DistributedSagaCoordinator) rollback(ctx context.Context) {
	// Unwind completed steps in reverse order (LIFO)
	for i := len(s.completed) - 1; i >= 0; i-- {
		step := s.completed[i]
		if step.Compensate != nil {
			fmt.Printf("   << [COMPENSATE] Rolling back step: %s
", step.Name)
			err := step.Compensate(ctx)
			if err != nil {
				fmt.Printf("   CRITICAL: Compensation for '%s' failed: %v
", step.Name, err)
			}
			s.compensated = append(s.compensated, step.Name)
		}
	}
}

func main() {
	ctx := context.Background()

	// Simulated Bank Accounts
	senderBalance := 10_000_000 // $100,000.00
	escrowBalance := 0
	destBalance := 0
	transferAmount := 2_500_000 // $25,000.00

	saga := NewSagaCoordinator()

	// Step 1: Hold Source Funds
	saga.AddStep(SagaStep{
		Name: "HoldFunds",
		Execute: func(ctx context.Context) error {
			if senderBalance < transferAmount {
				return errors.New("insufficient balance")
			}
			senderBalance -= transferAmount
			escrowBalance += transferAmount
			fmt.Printf("      Balances: Sender=$%d, Escrow=$%d
", senderBalance, escrowBalance)
			return nil
		},
		Compensate: func(ctx context.Context) error {
			escrowBalance -= transferAmount
			senderBalance += transferAmount
			fmt.Printf("      Balances Restored: Sender=$%d, Escrow=$%d
", senderBalance, escrowBalance)
			return nil
		},
	})

	// Step 2: FX Currency Lock
	saga.AddStep(SagaStep{
		Name: "ReserveFX",
		Execute: func(ctx context.Context) error {
			fmt.Println("      FX Desk: Reserved rate 1 USD = 0.92 EUR")
			return nil
		},
		Compensate: func(ctx context.Context) error {
			fmt.Println("      FX Desk: Released rate reservation")
			return nil
		},
	})

	// Step 3: Dispatch SWIFT MT103 (Fails with external bank rejection)
	saga.AddStep(SagaStep{
		Name: "DispatchSwift",
		Execute: func(ctx context.Context) error {
			return errors.New("SWIFT Reject: Beneficiary account invalid or frozen")
		},
		Compensate: nil, // Point of failure; no compensation needed for unexecuted step
	})

	// Execute the Saga
	err := saga.Execute(ctx)
	if err != nil {
		fmt.Printf("
Saga finished with expected compensation error: %v
", err)
	}

	fmt.Printf("
Final Account Audit:
  Sender: $%d
  Escrow: $%d
  Destination: $%d
",
		senderBalance, escrowBalance, destBalance)

	if senderBalance == 10_000_000 && escrowBalance == 0 && destBalance == 0 {
		fmt.Println("SUCCESS: Account books balanced with 0 balance leakage.")
	} else {
		fmt.Println("ERROR: Ledger mismatch detected!")
	}
}
```

```go
package solution

import (
	"context"
	"errors"
	"fmt"
)

type SagaStep struct {
	Name       string
	Execute    func(ctx context.Context) error
	Compensate func(ctx context.Context) error
}

func ExecuteWireSaga(ctx context.Context, steps []SagaStep) (err error) {
	executed := make([]SagaStep, 0, len(steps))

	// Ensure recovery if a forward action panics
	defer func() {
		if r := recover(); r != nil {
			panicErr := fmt.Errorf("step panicked: %v", r)
			rollbackErr := rollback(ctx, executed)
			err = errors.Join(panicErr, rollbackErr)
		}
	}()

	for _, step := range steps {
		if step.Execute != nil {
			stepErr := step.Execute(ctx)
			if stepErr != nil {
				rollbackErr := rollback(ctx, executed)
				return errors.Join(fmt.Errorf("step '%s' failed: %w", step.Name, stepErr), rollbackErr)
			}
		}
		executed = append(executed, step)
	}

	return nil
}

func rollback(ctx context.Context, executed []SagaStep) error {
	var compErrs []error

	// Reverse LIFO unwind
	for i := len(executed) - 1; i >= 0; i-- {
		step := executed[i]
		if step.Compensate != nil {
			if err := step.Compensate(ctx); err != nil {
				compErrs = append(compErrs, fmt.Errorf("compensation for '%s' failed: %w", step.Name, err))
			}
		}
	}

	if len(compErrs) > 0 {
		return errors.Join(compErrs...)
	}
	return nil
}
```

**Explanation**:
Combining reverse LIFO iteration with `errors.Join` guarantees that if a compensation fails, the operator receives full visibility into both the original failure and any subsequent compensation anomalies without masking errors.

- **Durable Execution**: Eliminates ad-hoc database polling and cron jobs by persisting code execution state, local variables, and call stacks to an append-only event log.
- **The Determinism Law**: Workflow functions must produce identical commands given identical event history. Never use `time.Now()`, `time.Sleep()`, native goroutines, or unsorted map iteration in workflows.
- **Event History Replay**: Restores coroutine state by matching scheduled activities against historical events, instantly returning cached results for completed steps.
- **Activity Timeouts & Heartbeats**: Always configure `HeartbeatTimeout` alongside `StartToCloseTimeout` to detect worker crashes in seconds rather than hours.
- **Signals & Selectors**: Use `workflow.NewSelector` to coordinate external asynchronous human-in-the-loop signals with durable multi-week timers without consuming CPU or OS threads.
- **Continue-As-New**: Truncate event history in perpetual workflows before reaching the 10,000-event threshold to preserve sub-millisecond replay speeds.
- **Distributed Sagas**: Implement backward compensating transactions executed in reverse LIFO order to unwind partial distributed mutations when external services fail.
