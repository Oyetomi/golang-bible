## Stacks

Here's the thing about stacks: Go gives you one for free, and it's sitting in plain sight. A slice *is* a stack. You don't need a library, you don't need a struct — you need `append` and a re-slice.

<Define term="Stack (LIFO, slice-backed)" since="Big-O & the Go Toolbox (Appendix, Chapter 1)">
A **stack** is a Last In, First Out (LIFO) collection: the most recently pushed item is always the first one popped. In Go, a plain `[]T` slice is the idiomatic backing store — `append` to push, re-slice to pop. No wrapper struct needed for the basic case. You reach for a stack when you need to **remember the current context and return to it**: bracket matching (return to the outer bracket after the inner one closes), expression evaluation, DFS traversal (implicit call-stack or explicit stack), and the monotonic-stack problems later in this chapter.
</Define>

### The Pattern

A stack is **LIFO** — Last In, First Out. Think of a browser's back history: the last page you visited is the first one you pop when you hit back.

In Go, the canonical idiom is:

```go
// push: O(1) amortized — append grows the backing array as needed
stack = append(stack, val)

// pop: O(1) — re-slice and grab the tail
val, stack = stack[len(stack)-1], stack[:len(stack)-1]

// peek: O(1)
top := stack[len(stack)-1]
```

Clean, idiomatic, no wrapper type needed for the basics. When you need a reusable generic stack, Go 1.18+ generics make that a five-liner.

<GoPlayground>

```go
package main

import "fmt"

func main() {
	var stack []int

	// push 1, 2, 3
	for _, v := range []int{1, 2, 3} {
		stack = append(stack, v)
	}
	fmt.Println("after pushes:", stack) // [1 2 3]

	// pop until empty
	for len(stack) > 0 {
		top := stack[len(stack)-1]
		stack = stack[:len(stack)-1]
		fmt.Println("popped:", top)
	}
	// prints 3, then 2, then 1 — LIFO
}
```

</GoPlayground>

### Classic: Valid Parentheses

Your interviewer's favorite warmup. Given a string of brackets — `"()[]{}"` — return `true` if every opener is closed in the right order.

**The pattern:** push every opener; on every closer, check the stack top. If the top doesn't match, it's invalid. If the stack is empty at the end, it's valid.

```go
package main

import "fmt"

func isValid(s string) bool {
	var stack []rune
	match := map[rune]rune{')': '(', ']': '[', '}': '{'}

	for _, ch := range s {
		switch ch {
		case '(', '[', '{':
			stack = append(stack, ch)
		default:
			if len(stack) == 0 || stack[len(stack)-1] != match[ch] {
				return false
			}
			stack = stack[:len(stack)-1]
		}
	}
	return len(stack) == 0
}

func main() {
	cases := []string{"()[]{}", "([{}])", "([)]", "{[}", ""}
	for _, c := range cases {
		fmt.Printf("isValid(%q) = %v\n", c, isValid(c))
	}
}
```

</GoPlayground>

**Complexity:** O(n) time, O(n) space (stack can hold up to n/2 openers).

### Classic: Evaluate RPN

Reverse Polish Notation — `"2 3 + 4 *"` means `(2+3)*4 = 20`. Operands push onto the stack; operators pop two operands, compute, and push the result back.

<GoPlayground>

```go
package main

import (
	"fmt"
	"strconv"
	"strings"
)

func evalRPN(tokens []string) int {
	var stack []int
	for _, tok := range tokens {
		switch tok {
		case "+", "-", "*", "/":
			b, a := stack[len(stack)-1], stack[len(stack)-2]
			stack = stack[:len(stack)-2]
			switch tok {
			case "+":
				stack = append(stack, a+b)
			case "-":
				stack = append(stack, a-b)
			case "*":
				stack = append(stack, a*b)
			case "/":
				stack = append(stack, a/b)
			}
		default:
			n, _ := strconv.Atoi(tok)
			stack = append(stack, n)
		}
	}
	return stack[0]
}

func main() {
	expr := strings.Fields("2 3 + 4 *") // (2+3)*4
	fmt.Println("RPN result:", evalRPN(expr)) // 20
}
```

</GoPlayground>

**Complexity:** O(n) time, O(n) space.

### Classic: Min-Stack

Design a stack that supports `push`, `pop`, `top`, and `getMin` — all O(1). The trick: carry a second "min-stack" in parallel that tracks the running minimum at each level.

<GoPlayground>

```go
package main

import "fmt"

type MinStack struct {
	data []int
	mins []int
}

func (s *MinStack) Push(val int) {
	s.data = append(s.data, val)
	if len(s.mins) == 0 || val <= s.mins[len(s.mins)-1] {
		s.mins = append(s.mins, val)
	} else {
		s.mins = append(s.mins, s.mins[len(s.mins)-1])
	}
}

func (s *MinStack) Pop() {
	s.data = s.data[:len(s.data)-1]
	s.mins = s.mins[:len(s.mins)-1]
}

func (s *MinStack) Top() int { return s.data[len(s.data)-1] }

func (s *MinStack) GetMin() int { return s.mins[len(s.mins)-1] }

func main() {
	ms := &MinStack{}
	ms.Push(5)
	ms.Push(3)
	ms.Push(7)
	fmt.Println("min:", ms.GetMin()) // 3
	ms.Pop()                         // pop 7
	fmt.Println("min:", ms.GetMin()) // 3
	ms.Pop()                         // pop 3
	fmt.Println("min:", ms.GetMin()) // 5
}
```

</GoPlayground>

**Complexity:** O(1) all ops, O(n) space (two parallel slices).

<UnderTheHood title="Why a slice makes such a great stack (as of Go 1.24)">

A Go slice is a three-word header: **pointer** to a backing array, **len**, and **cap**. `append` is O(1) amortized because when `len < cap`, it just writes to the next slot and increments len — *no allocation*. When `len == cap`, the runtime allocates a new backing array roughly **double** the current capacity (the growth factor is actually a smooth curve that starts at 2× for small slices and trends toward 1.25× for large ones, as of Go 1.18's revised growth algorithm), copies the old data, and updates the header. Those rare allocation events are what "amortized O(1)" accounts for.

A pop (`stack = stack[:len(stack)-1]`) is *literally* decrementing the len field — a single integer write. The backing array doesn't shrink, so the memory is still reachable via the slice header's pointer. This means a very deep stack that was then fully popped still holds its backing array in memory. If you want to reclaim it: `stack = nil`.

The compiler performs **escape analysis** on the backing array. If the slice never escapes to the heap (e.g., it stays stack-local inside a function), the backing array lives on the goroutine stack — zero GC pressure, *extremely* fast. The moment you return the slice or store it in a struct, it escapes to the heap. You can check with `go build -gcflags='-m'`.

</UnderTheHood>

## Queues

<Define term="Queue (FIFO)" since="Trees & Recursion (Appendix, Chapter 5)">
A **queue** is a First In, First Out (FIFO) collection: items leave in the same order they arrived. In Go there is no queue in the standard library's `slices` or `sort` packages — you build one. The naive slice implementation (`q[1:]` to dequeue) leaks memory over time; a ring buffer or `container/list` is correct. Queues are the engine of **BFS**: process the front node, enqueue its unvisited neighbors, repeat. They also underpin rate limiters, work queues, and any system where fairness or ordering matters.
</Define>

Alright. This is where the interview separates the people who skimmed a tutorial from the people who actually *understand*. A queue is FIFO — First In, First Out. A line at the bank. BFS needs one. Rate limiters need one. And here's the trap:

**A naive slice queue is O(n) per dequeue.** I've watched candidates burn ten minutes on this in whiteboard interviews, then defend their O(n) solution with confidence. Don't be that person.

### The Naive Slice Queue (and Why It Hurts)

```go
// enqueue: O(1) amortized
q = append(q, val)

// dequeue: O(n) — shifts every remaining element left
val, q = q[0], q[1:]
```

`q[1:]` creates a new slice header pointing one element in — it does *not* copy — but the old `q[0]` is now unreachable through the slice. Over time, the backing array fills up with dead entries on the left side. The GC can't reclaim them because the slice header still holds a reference to the underlying array. You've got a **memory leak masquerading as a queue**.

  goodLabel="Ring buffer O(1)"

### The Ring Buffer Queue

A ring buffer fixes both problems — O(1) enqueue and dequeue, O(1) space reuse — by treating a fixed-size array as a circle. Head chases tail; when either reaches the end, it wraps back to zero.

<GoPlayground>

```go
package main

import "fmt"

// RingQueue is a fixed-capacity FIFO queue backed by a circular buffer.
// Enqueue and Dequeue are both O(1).
type RingQueue struct {
	buf        []int
	head, tail int
	count      int
}

func NewRingQueue(cap int) *RingQueue {
	return &RingQueue{buf: make([]int, cap)}
}

func (q *RingQueue) Len() int { return q.count }

func (q *RingQueue) Enqueue(v int) bool {
	if q.count == len(q.buf) {
		return false // full
	}
	q.buf[q.tail] = v
	q.tail = (q.tail + 1) % len(q.buf)
	q.count++
	return true
}

func (q *RingQueue) Dequeue() (int, bool) {
	if q.count == 0 {
		return 0, false
	}
	v := q.buf[q.head]
	q.head = (q.head + 1) % len(q.buf)
	q.count--
	return v, true
}

func main() {
	q := NewRingQueue(4)
	for _, v := range []int{10, 20, 30} {
		q.Enqueue(v)
	}
	for q.Len() > 0 {
		v, _ := q.Dequeue()
		fmt.Println("dequeued:", v) // 10, 20, 30 — FIFO
	}
}
```

</GoPlayground>

**Complexity:** O(1) enqueue and dequeue, O(capacity) space.

### The Two-Stack Queue

Another classic interview trick: simulate a queue with two stacks. Enqueue into the "inbox" stack; when you dequeue, if the "outbox" stack is empty, reverse the inbox into the outbox (once), then pop from outbox.

<GoPlayground>

```go
package main

import "fmt"

// TwoStackQueue is a FIFO queue built from two LIFO stacks.
// Amortized O(1) enqueue and dequeue.
type TwoStackQueue struct {
	inbox, outbox []int
}

func (q *TwoStackQueue) Enqueue(v int) {
	q.inbox = append(q.inbox, v)
}

func (q *TwoStackQueue) Dequeue() (int, bool) {
	if len(q.outbox) == 0 {
		// pour inbox into outbox — reverses order, making it FIFO
		for len(q.inbox) > 0 {
			n := len(q.inbox)
			q.outbox = append(q.outbox, q.inbox[n-1])
			q.inbox = q.inbox[:n-1]
		}
	}
	if len(q.outbox) == 0 {
		return 0, false
	}
	n := len(q.outbox)
	v := q.outbox[n-1]
	q.outbox = q.outbox[:n-1]
	return v, true
}

func main() {
	var q TwoStackQueue
	for _, v := range []int{1, 2, 3, 4} {
		q.Enqueue(v)
	}
	for {
		v, ok := q.Dequeue()
		if !ok {
			break
		}
		fmt.Println("dequeued:", v) // 1, 2, 3, 4
	}
}
```

</GoPlayground>

**Complexity:** O(1) amortized. Each element crosses from inbox to outbox exactly once.

### `container/list` as a Deque

The standard library's `container/list` is a doubly linked list. It's the Go stdlib's answer to a deque — O(1) push/pop at both ends.

<GoPlayground>

```go
package main

import (
	"container/list"
	"fmt"
)

func main() {
	q := list.New()

	// enqueue at the back
	for _, v := range []int{10, 20, 30} {
		q.PushBack(v)
	}

	// dequeue from the front — O(1)
	for q.Len() > 0 {
		front := q.Front()
		fmt.Println("dequeued:", front.Value.(int))
		q.Remove(front)
	}
}
```

</GoPlayground>

**Complexity:** O(1) all ops; each node is a heap allocation (pointer overhead vs. ring buffer's contiguous array).

<Callout kind="note" title="BFS uses a queue">

Breadth-First Search on a graph or tree processes nodes **level by level**. At each step it dequeues the current node, visits it, and enqueues its unvisited neighbors. The queue's FIFO order is precisely what guarantees you process shallower nodes before deeper ones — that's the whole algorithm. We'll animate this in full in the Trees & Graphs chapters. For now: whenever an interview prompt says "shortest path," "level by level," or "minimum steps," your hand should already be reaching for a queue.

</Callout>

<UnderTheHood title="Slice dequeue memory leak vs. ring buffer (Go 1.24)">

When you do `q = q[1:]`, Go creates a new slice header: pointer advances by one element width, len decrements by 1, cap decrements by 1. The backing array is the same allocation. The GC sees the backing array as still live (there's a pointer to it in the slice header), so it cannot reclaim the dead prefix. After N dequeues with M enqueues, you're carrying up to N dead slots in memory — O(N) wasted space with no way to recover it short of copying the live elements to a fresh slice.

A ring buffer avoids this entirely: the same fixed array is reused in a circular pattern. `head = (head+1) % cap` is the same as `q[1:]` from the header's perspective, but the *array index* wraps around, so slot 0 becomes available again after the buffer cycles past index cap-1. The array never grows a dead prefix.

The two-stack queue has a different memory profile: during the "pour" phase, every element from inbox is appended onto outbox. This is a copy, but it's amortized O(1) per element over the lifetime of the queue. No dead prefix — the inbox slice is reset to `inbox[:0]` (zero len, cap preserved for reuse).

</UnderTheHood>

## Linked Lists

<Define term="Linked List (node/pointer chain)">
A **linked list** is a sequence of nodes where each node holds a value and a pointer to the next node (`Next *ListNode`). There is no backing array — nodes are individual heap allocations connected only by pointers. This gives O(1) insert/delete at a known position (just rewire two pointers) but O(n) traversal with a cache miss at every hop, because nodes are scattered across memory. In production Go, slices almost always beat linked lists for sequences (cache locality wins). In interviews, you hand-roll them because **pointer rewiring under pressure** tests real understanding of references — and because the problems (reverse, cycle-detect, merge) are standard interview staples.
</Define>

I know what you're thinking: "We have slices. Why are we here?" You're here because **every major tech interview** asks you to reverse a linked list, detect a cycle, or merge two sorted lists. Not because linked lists beat slices in production Go — they don't, usually — but because pointer rewiring under pressure *reveals* whether you actually understand references.

Buckle up.

### Singly Linked List

A singly linked list is a chain of nodes, each holding a value and a pointer to the next. The last node's next is `nil`.

```go
type ListNode struct {
	Val  int
	Next *ListNode
}
```

Build one:

<GoPlayground>

```go
package main

import "fmt"

type ListNode struct {
	Val  int
	Next *ListNode
}

// buildList creates a linked list from a slice — handy for tests.
func buildList(vals []int) *ListNode {
	dummy := &ListNode{}
	cur := dummy
	for _, v := range vals {
		cur.Next = &ListNode{Val: v}
		cur = cur.Next
	}
	return dummy.Next
}

func printList(head *ListNode) {
	for head != nil {
		fmt.Print(head.Val, " -> ")
		head = head.Next
	}
	fmt.Println("nil")
}

func main() {
	head := buildList([]int{1, 2, 3, 4, 5})
	printList(head)
}
```

</GoPlayground>

package main

import "fmt"

type ListNode struct {
	Val  int
	Next *ListNode
}

func reverseList(head *ListNode) *ListNode {
	var prev *ListNode
	curr := head
	for curr != nil {
		next := curr.Next // save before overwriting
		curr.Next = prev  // reverse the link
		prev = curr       // advance prev
		curr = next       // advance curr
	}
	return prev // prev is the new head
}

func buildList(vals []int) *ListNode {
	dummy := &ListNode{}
	cur := dummy
	for _, v := range vals {
		cur.Next = &ListNode{Val: v}
		cur = cur.Next
	}
	return dummy.Next
}

func printList(head *ListNode) {
	for head != nil {
		fmt.Print(head.Val)
		if head.Next != nil {
			fmt.Print(" -> ")
		}
		head = head.Next
	}
	fmt.Println()
}

func main() {
	head := buildList([]int{1, 2, 3, 4, 5})
	fmt.Print("before: ")
	printList(head)
	head = reverseList(head)
	fmt.Print("after:  ")
	printList(head) // 5 -> 4 -> 3 -> 2 -> 1
}

### Floyd's Cycle Detection (Fast & Slow Pointers)

Two pointers: slow moves one step at a time; fast moves two. If there's a cycle, fast will eventually lap slow — they'll meet inside the cycle. If fast reaches `nil`, there's no cycle.

<GoPlayground>

```go
package main

import "fmt"

type ListNode struct {
	Val  int
	Next *ListNode
}

func hasCycle(head *ListNode) bool {
	slow, fast := head, head
	for fast != nil && fast.Next != nil {
		slow = slow.Next
		fast = fast.Next.Next
		if slow == fast { // same pointer value — same node
			return true
		}
	}
	return false
}

func main() {
	// build: 1 -> 2 -> 3 -> 4 -> 2 (cycle back to node 2)
	n1 := &ListNode{Val: 1}
	n2 := &ListNode{Val: 2}
	n3 := &ListNode{Val: 3}
	n4 := &ListNode{Val: 4}
	n1.Next = n2
	n2.Next = n3
	n3.Next = n4
	n4.Next = n2 // cycle!

	fmt.Println("has cycle:", hasCycle(n1)) // true

	// acyclic list
	acyclic := &ListNode{Val: 1, Next: &ListNode{Val: 2, Next: &ListNode{Val: 3}}}
	fmt.Println("has cycle:", hasCycle(acyclic)) // false
}
```

</GoPlayground>

**Complexity:** O(n) time, O(1) space. **Variations:** find cycle start (extend with phase 2), find cycle length.

### Merge Two Sorted Lists

A classic recursion-or-iteration problem. Compare the two heads; take the smaller one; recurse (or loop). The dummy-head trick eliminates the "what's the head?" special case.

<GoPlayground>

```go
package main

import "fmt"

type ListNode struct {
	Val  int
	Next *ListNode
}

func mergeTwoLists(l1, l2 *ListNode) *ListNode {
	dummy := &ListNode{} // sentinel head — eliminates edge cases
	cur := dummy
	for l1 != nil && l2 != nil {
		if l1.Val <= l2.Val {
			cur.Next = l1
			l1 = l1.Next
		} else {
			cur.Next = l2
			l2 = l2.Next
		}
		cur = cur.Next
	}
	// attach the non-exhausted remainder — O(1) pointer assignment
	if l1 != nil {
		cur.Next = l1
	} else {
		cur.Next = l2
	}
	return dummy.Next
}

func buildList(vals []int) *ListNode {
	dummy := &ListNode{}
	cur := dummy
	for _, v := range vals {
		cur.Next = &ListNode{Val: v}
		cur = cur.Next
	}
	return dummy.Next
}

func printList(head *ListNode) {
	for head != nil {
		fmt.Print(head.Val)
		if head.Next != nil {
			fmt.Print(" -> ")
		}
		head = head.Next
	}
	fmt.Println()
}

func main() {
	a := buildList([]int{1, 3, 5, 7})
	b := buildList([]int{2, 4, 6})
	merged := mergeTwoLists(a, b)
	printList(merged) // 1 -> 2 -> 3 -> 4 -> 5 -> 6 -> 7
}
```

</GoPlayground>

**Complexity:** O(m+n) time, O(1) space (iterative). The dummy-head sentinel is idiomatic — use it whenever "what is the new head?" is a question.

### Find the Middle of a Linked List

Fast/slow again: when fast reaches the end, slow is at the middle. Even-length lists: slow lands on the *second* middle (adjust by stopping when `fast.Next == nil` for the first middle).

<GoPlayground>

```go
package main

import "fmt"

type ListNode struct {
	Val  int
	Next *ListNode
}

func middleNode(head *ListNode) *ListNode {
	slow, fast := head, head
	for fast != nil && fast.Next != nil {
		slow = slow.Next
		fast = fast.Next.Next
	}
	return slow
}

func buildList(vals []int) *ListNode {
	dummy := &ListNode{}
	cur := dummy
	for _, v := range vals {
		cur.Next = &ListNode{Val: v}
		cur = cur.Next
	}
	return dummy.Next
}

func main() {
	odd := buildList([]int{1, 2, 3, 4, 5})
	fmt.Println("middle of [1..5]:", middleNode(odd).Val) // 3

	even := buildList([]int{1, 2, 3, 4, 5, 6})
	fmt.Println("middle of [1..6]:", middleNode(even).Val) // 4 (second middle)
}
```

</GoPlayground>

**Complexity:** O(n) time, O(1) space.

<UnderTheHood title="Why hand-rolled lists lose to slices in production Go">

A Go `*ListNode` is a heap allocation per node: 16 bytes of `ListNode` struct plus the allocator header. For a list of N integers, that's N separate heap allocations, scattered across memory, each reachable only via a pointer. Traversal is a cache-miss-per-node on any real dataset, because sequential list nodes are rarely adjacent in memory.

A `[]int` of the same N values is *one* allocation — a contiguous array. Traversal is a sequential memory read, which hardware prefetchers and cache lines handle with ease. For N=1000, a slice traversal may be 10-50× faster than a linked list traversal on modern hardware, purely due to cache behavior.

This is why production Go almost never uses `container/list` for sequences. Slices win. The cases where linked lists win in Go: O(1) mid-list insert/delete when you already have a pointer to the node (e.g., an LRU cache evicting an element — this is the `container/list` use case); or when elements are very large and copying them on reallocation is expensive.

For interviews, write the linked list. In production, reach for the slice and profile before you do anything clever.

</UnderTheHood>

## Monotonic Stacks

<Define term="Monotonic Stack">
A **monotonic stack** is a regular slice-based stack with one extra rule: the invariant that elements stay in sorted order (strictly increasing bottom-to-top, or strictly decreasing) is maintained on every push. Before pushing a new element, pop everything that would violate the order. The pop event is not waste — it is the answer: the element being pushed is the **next greater (or smaller) element** for each thing it evicts. Every element is pushed once and popped at most once, giving O(n) total work for problems that look O(n²) at first glance. Classic applications: next-greater-element, daily temperatures, largest rectangle in histogram, trapping rainwater.
</Define>

Here is where I separate the people who *practiced* from the people who merely *read*. The monotonic stack is a stack with an invariant: it stays sorted (either always increasing or always decreasing) by popping elements that violate the order before pushing a new one. It sounds simple. It unlocks a family of O(n) problems that look O(n²) at first glance.

### The Invariant

A **monotonic increasing** stack: before pushing `x`, pop everything ≥ `x`. The stack is strictly increasing bottom to top.

A **monotonic decreasing** stack: before pushing `x`, pop everything ≤ `x`. The stack is strictly decreasing bottom to top.

The pop event is the signal: when `x` causes an element to be popped, `x` is the **next greater (or smaller) element** for that popped element. That's the answer, arriving exactly when needed.

### Classic: Next Greater Element

Given an array, for each element find the index of the next element to its right that is strictly greater. Return -1 if none exists.

<GoPlayground>

```go
package main

import "fmt"

// nextGreaterElement returns, for each index i, the index j > i
// where nums[j] > nums[i], or -1 if none exists.
// Time: O(n). Space: O(n).
func nextGreaterElement(nums []int) []int {
	n := len(nums)
	result := make([]int, n)
	for i := range result {
		result[i] = -1
	}
	var stack []int // indices, not values; stack is decreasing by nums[i]

	for i, v := range nums {
		// pop everything that the current element is greater than
		for len(stack) > 0 && nums[stack[len(stack)-1]] < v {
			idx := stack[len(stack)-1]
			stack = stack[:len(stack)-1]
			result[idx] = i // i is the next-greater index for idx
		}
		stack = append(stack, i)
	}
	return result
}

func main() {
	nums := []int{4, 1, 2, 5, 3}
	nge := nextGreaterElement(nums)
	for i, idx := range nge {
		if idx == -1 {
			fmt.Printf("nums[%d]=%d → no next greater\n", i, nums[i])
		} else {
			fmt.Printf("nums[%d]=%d → next greater is nums[%d]=%d\n",
				i, nums[i], idx, nums[idx])
		}
	}
}
```

</GoPlayground>

**Complexity:** O(n) time — each element is pushed and popped at most once. O(n) space.

### Classic: Daily Temperatures

Given a list of daily temperatures, return an array where `result[i]` is the number of days until a warmer day. Classic monotonic stack application — same pattern as next-greater, but the answer is the index *difference*, not the index itself.

<GoPlayground>

```go
package main

import "fmt"

func dailyTemperatures(temps []int) []int {
	result := make([]int, len(temps))
	var stack []int // indices of temperatures awaiting a warmer day

	for i, t := range temps {
		for len(stack) > 0 && temps[stack[len(stack)-1]] < t {
			j := stack[len(stack)-1]
			stack = stack[:len(stack)-1]
			result[j] = i - j // days until warmer
		}
		stack = append(stack, i)
	}
	// anything left on the stack stays 0 (no warmer day)
	return result
}

func main() {
	temps := []int{73, 74, 75, 71, 69, 72, 76, 73}
	waits := dailyTemperatures(temps)
	for i, w := range waits {
		fmt.Printf("day %d (%d°): wait %d days\n", i, temps[i], w)
	}
}
```

</GoPlayground>

**Complexity:** O(n) time, O(n) space. **Pattern name:** "monotonic decreasing stack on indices."

### Classic: Largest Rectangle in Histogram

Given bar heights, find the largest rectangle that fits entirely within the histogram. This is the hard version — it still uses a monotonic stack (increasing), but the pop event triggers an area calculation, not just a lookup.

When a shorter bar `h` arrives and forces popping a taller bar `popped`, the rectangle bounded by `popped`'s height extends left to the new stack top's index and right to the current index.

<GoPlayground>

```go
package main

import "fmt"

// largestRectangleArea returns the area of the largest rectangle
// fitting within a histogram. O(n) time, O(n) space.
func largestRectangleArea(heights []int) int {
	// append a sentinel 0 so every bar gets popped and measured
	heights = append(heights, 0)
	var stack []int // indices; stack is increasing by height
	maxArea := 0

	for i, h := range heights {
		for len(stack) > 0 && heights[stack[len(stack)-1]] > h {
			top := stack[len(stack)-1]
			stack = stack[:len(stack)-1]
			width := i
			if len(stack) > 0 {
				width = i - stack[len(stack)-1] - 1
			}
			area := heights[top] * width
			if area > maxArea {
				maxArea = area
			}
		}
		stack = append(stack, i)
	}
	return maxArea
}

func main() {
	heights := []int{2, 1, 5, 6, 2, 3}
	fmt.Println("largest rectangle:", largestRectangleArea(heights)) // 10
	// The 5×2 rectangle using bars at index 2 and 3
}
```

</GoPlayground>

**Complexity:** O(n) time — each bar is pushed and popped exactly once. O(n) space. This is the canonical O(n) solution; naive O(n²) just won't cut it on large inputs.

<UnderTheHood title="Why monotonic stacks give amortized O(n)">

The key insight is the **work-accounting argument**: every element is pushed onto the stack *exactly once* and popped *at most once*. The total number of push + pop operations is bounded by 2n, regardless of how many times the inner `for` loop fires on any given outer iteration.

This is the same argument that makes `append` O(1) amortized. The expensive step (popping multiple elements in one outer loop iteration) is "paid for" by the cheap steps (pushes) that happened earlier. Sum across all N outer iterations: O(1) per push × N pushes + O(1) per pop × at most N pops = O(n) total.

The invariant maintenance is free — you're not *sorting* the stack on each push; you're popping violations *once* and then pushing once. The stack is always sorted because you maintain it incrementally.

Pattern recognition: any problem asking "for each element, find the nearest X to the left/right where X satisfies some comparison" is likely a monotonic stack problem. Daily temperatures, next-greater, stock span, largest rectangle, trapping rainwater — all the same family.

</UnderTheHood>

<Exercise n={1} title="Implement a Generic Stack" level="easy">

Write a generic `Stack[T any]` type backed by a `[]T` slice with `Push(T)`, `Pop() (T, bool)`, and `Peek() (T, bool)` methods. All methods O(1) amortized.

<Solution>

```go
package main

import "fmt"

type Stack[T any] struct {
	items []T
}

func (s *Stack[T]) Push(v T) {
	s.items = append(s.items, v)
}

func (s *Stack[T]) Pop() (T, bool) {
	var zero T
	if len(s.items) == 0 {
		return zero, false
	}
	n := len(s.items)
	v := s.items[n-1]
	s.items = s.items[:n-1]
	return v, true
}

func (s *Stack[T]) Peek() (T, bool) {
	var zero T
	if len(s.items) == 0 {
		return zero, false
	}
	return s.items[len(s.items)-1], true
}

func main() {
	var s Stack[string]
	s.Push("a")
	s.Push("b")
	s.Push("c")
	for {
		v, ok := s.Pop()
		if !ok {
			break
		}
		fmt.Println(v) // c, b, a
	}
}
```

The zero-value trick (`var zero T`) safely returns the zero value of any type when the stack is empty — the Go 1.18+ generics way. No interface boxing, no reflection.

</Solution>

</Exercise>

<Exercise n={2} title="LRU Cache with container/list" level="medium">

Implement an LRU (Least Recently Used) cache with `Get(key int) int` and `Put(key, val int)` methods. Both O(1). Capacity is fixed at construction. Evict the least-recently-used entry when full.

<Solution>

```go
package main

import (
	"container/list"
	"fmt"
)

type entry struct{ key, val int }

type LRUCache struct {
	cap   int
	ll    *list.List
	items map[int]*list.Element
}

func NewLRUCache(capacity int) *LRUCache {
	return &LRUCache{
		cap:   capacity,
		ll:    list.New(),
		items: make(map[int]*list.Element),
	}
}

func (c *LRUCache) Get(key int) int {
	el, ok := c.items[key]
	if !ok {
		return -1
	}
	c.ll.MoveToFront(el)
	return el.Value.(*entry).val
}

func (c *LRUCache) Put(key, val int) {
	if el, ok := c.items[key]; ok {
		el.Value.(*entry).val = val
		c.ll.MoveToFront(el)
		return
	}
	if c.ll.Len() == c.cap {
		back := c.ll.Back()
		c.ll.Remove(back)
		delete(c.items, back.Value.(*entry).key)
	}
	el := c.ll.PushFront(&entry{key, val})
	c.items[key] = el
}

func main() {
	cache := NewLRUCache(2)
	cache.Put(1, 10)
	cache.Put(2, 20)
	fmt.Println(cache.Get(1)) // 10 — also marks 1 as recently used
	cache.Put(3, 30)          // evicts key 2 (LRU)
	fmt.Println(cache.Get(2)) // -1 — evicted
	fmt.Println(cache.Get(3)) // 30
}
```

`container/list` earns its keep here: O(1) move-to-front on a doubly linked list. The map stores the `*list.Element` directly, giving O(1) lookup. This is the exact pattern used in production caches and the canonical Go LRU implementation.

</Solution>

</Exercise>

<Exercise n={3} title="Remove Nth Node from End" level="medium">

Given a linked list and integer `n`, remove the nth node from the end in one pass. No second traversal. Use two pointers spaced n apart.

<Solution>

```go
package main

import "fmt"

type ListNode struct {
	Val  int
	Next *ListNode
}

func removeNthFromEnd(head *ListNode, n int) *ListNode {
	dummy := &ListNode{Next: head}
	fast, slow := dummy, dummy

	// advance fast n+1 steps so the gap between fast and slow is n
	for i := 0; i <= n; i++ {
		fast = fast.Next
	}
	// move both until fast falls off
	for fast != nil {
		fast = fast.Next
		slow = slow.Next
	}
	// slow.Next is the node to remove
	slow.Next = slow.Next.Next
	return dummy.Next
}

func buildList(vals []int) *ListNode {
	dummy := &ListNode{}
	cur := dummy
	for _, v := range vals {
		cur.Next = &ListNode{Val: v}
		cur = cur.Next
	}
	return dummy.Next
}

func printList(head *ListNode) {
	for head != nil {
		fmt.Print(head.Val)
		if head.Next != nil {
			fmt.Print(" -> ")
		}
		head = head.Next
	}
	fmt.Println()
}

func main() {
	head := buildList([]int{1, 2, 3, 4, 5})
	head = removeNthFromEnd(head, 2) // remove 4
	printList(head)                  // 1 -> 2 -> 3 -> 5
}
```

The dummy head absorbs the edge case of removing the actual head (n == length). The two-pointer gap trick gives O(n) time, O(1) space, single pass.

</Solution>

<Exercise n={4} title="Decode String with Stack" level="medium">

Decode a string like `"3[a2[c]]"` → `"accaccacc"`. Brackets can be nested. Use two stacks: one for counts, one for partial strings.

<Solution>

```go
package main

import (
	"fmt"
	"strings"
	"unicode"
)

func decodeString(s string) string {
	var countStack []int
	var strStack []string // stack of strings, NOT strings.Builder —
	// a strings.Builder must never be copied (it panics), and pushing one
	// onto a slice copies it. Stack the finished strings instead.
	var current strings.Builder
	count := 0

	for _, ch := range s {
		switch {
		case unicode.IsDigit(ch):
			count = count*10 + int(ch-'0')
		case ch == '[':
			countStack = append(countStack, count)
			strStack = append(strStack, current.String())
			current.Reset()
			count = 0
		case ch == ']':
			k := countStack[len(countStack)-1]
			countStack = countStack[:len(countStack)-1]
			prev := strStack[len(strStack)-1]
			strStack = strStack[:len(strStack)-1]
			seg := current.String()
			current.Reset()
			current.WriteString(prev)
			current.WriteString(strings.Repeat(seg, k))
		default:
			current.WriteByte(byte(ch))
		}
	}
	return current.String()
}

func main() {
	fmt.Println(decodeString("3[a2[c]]"))  // accaccacc
	fmt.Println(decodeString("2[abc]3[cd]ef")) // abcabccdcdcdef
}
```

Two stacks — one for the repeat count at each nesting level, one for the accumulated string above — mirror the recursive structure of the grammar without actual recursion. O(n × max_repeat) time, O(n) space.

</Solution>

</Exercise>

Given an elevation map as `[]int`, compute how many units of water it can trap after rain. Classic hard monotonic-stack (or two-pointer) problem.

```go
package main

import "fmt"

// trapWater computes trapped rainwater using a monotonic stack.
// O(n) time, O(n) space.
func trapWater(height []int) int {
	var stack []int
	water := 0

	for i, h := range height {
		for len(stack) > 0 && height[stack[len(stack)-1]] < h {
			bottom := stack[len(stack)-1]
			stack = stack[:len(stack)-1]
			if len(stack) == 0 {
				break
			}
			left := stack[len(stack)-1]
			width := i - left - 1
			boundedHeight := min(height[left], h) - height[bottom]
			water += width * boundedHeight
		}
		stack = append(stack, i)
	}
	return water
}

func main() {
	fmt.Println(trapWater([]int{0, 1, 0, 2, 1, 0, 1, 3, 2, 1, 2, 1})) // 6
	fmt.Println(trapWater([]int{4, 2, 0, 3, 2, 5}))                    // 9
}
```

The monotonic stack tracks "candidate walls." When a taller bar arrives, it traps water against each shorter bar on the stack up to itself. `min` is the Go 1.21 builtin — no helper needed. The two-pointer approach (O(1) space) is also worth knowing; this stack version makes the trapping geometry explicit.

<Recap>

- **Stacks** are slices in Go — `append` to push, `stack[:n-1]` to pop. O(1) amortized both directions. Backed by the slice's three-word header and a contiguous array. Pop events on a monotonic stack signal next-greater/smaller relationships.
- **Queues** are where the naive slice fails — `q[1:]` dequeues in O(1) but *leaks* the backing array. Use a ring buffer for O(1) amortized with bounded memory; two-stack queue for the interview pattern; `container/list` for a ready-made deque.
- **Linked lists** are pointer chains: one heap allocation per node, cache-miss per traversal. You hand-roll them in interviews, not production. Master: reverse (three pointers, O(1) space), cycle detection (Floyd's fast/slow, O(1) space), merge two sorted (dummy head, O(1) space), find middle (fast/slow).
- **Monotonic stacks** maintain a sorted invariant by popping violators before each push. Each element is pushed and popped at most once → O(n) amortized total. The pop event *is* the answer. Pattern: next-greater-element, daily-temperatures, largest-rectangle, trapping-rainwater.
- **Pattern recognition:** brackets/nesting → stack; FIFO/BFS/level-order → queue; pointer rewiring/cycle/merge → linked list; "nearest X in direction" → monotonic stack.
