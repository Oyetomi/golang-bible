## Race Conditions

The bug that money systems fear most. A **race condition** (specifically TOCTOU — time-of-check to time-of-use) is when two operations interleave between a *check* and the *action* that depends on it, so the check passes for both. Fire enough concurrent requests and you overrun a limit that was only ever checked once per request.

<Define term="Race condition (TOCTOU limit overrun)">
A **TOCTOU race** exists when code checks a condition (balance ≥ amount, coupon unused, withdrawal under daily limit) and then acts on it (deduct, redeem, transfer) as two separate, non-atomic steps. Between the check and the act, a *concurrent* request can slip in: both requests read the same "valid" state, both pass the check, both act — and the limit is overrun. On the web you trigger it by firing many identical requests **simultaneously** (the same race a multithreaded program has, but over HTTP). Real impact: withdraw a balance twice, redeem a one-time coupon N times, brute a "3 attempts" code by sending all guesses at once. The fix is **atomicity** — make check-and-act a single indivisible operation (a lock, an atomic compare-and-swap, or a database transaction with the right isolation / a conditional `UPDATE ... WHERE balance >= amount`).
</Define>

<Callout kind="note" title="Real case — race-condition account & balance bugs">
The corpus is full of these. *"How I Could Have Hacked Any Instagram Account"* (thezerohack, **$30,000**) raced the password-reset code verification to brute-force it. *"Race conditions on the web"* (Josip Franjković) is the canonical writeup of redeeming gift cards and invitations multiple times by parallelizing the request. The shape is always the same: a check that's correct sequentially, broken concurrently.
</Callout>

```go
package main

import (
	"fmt"
	"sync"
)

type account struct {
	mu      sync.Mutex
	balance int
}

// VULNERABLE: check and deduct are separate, non-atomic steps.
func (a *account) withdrawRacy(amount int) bool {
	if a.balance >= amount { // CHECK
		// a concurrent goroutine can pass the same check here, before we deduct
		a.balance -= amount // USE
		return true
	}
	return false
}

// SAFE: the lock makes check-and-deduct one indivisible operation.
func (a *account) withdrawSafe(amount int) bool {
	a.mu.Lock()
	defer a.mu.Unlock()
	if a.balance >= amount {
		a.balance -= amount
		return true
	}
	return false
}

func run(withdraw func(*account, int) bool) (succeeded, finalBalance int) {
	a := &account{balance: 10}
	var wg sync.WaitGroup
	var cmu sync.Mutex
	for i := 0; i < 100; i++ {
		wg.Add(1)
		go func() {
			defer wg.Done()
			if withdraw(a, 1) {
				cmu.Lock()
				succeeded++
				cmu.Unlock()
			}
		}()
	}
	wg.Wait()
	return succeeded, a.balance
}

func main() {
	s1, b1 := run((*account).withdrawRacy)
	fmt.Printf("RACY: %d succeeded, final balance %d  (should be 10 / 0)\n", s1, b1)
	s2, b2 := run((*account).withdrawSafe)
	fmt.Printf("SAFE: %d succeeded, final balance %d\n", s2, b2)
}
```

</GoPlayground>

</CodeWalk>

<Gotcha>
**A per-request check is not a limit.** "We check the daily withdrawal limit on every request" is exactly the vulnerable pattern if the check and the debit aren't atomic. The defense in a real system is at the **database**: a single `UPDATE accounts SET balance = balance - $amt WHERE id = $id AND balance >= $amt` (which the DB executes atomically and returns rows-affected = 0 if it would go negative), or `SELECT ... FOR UPDATE` inside a transaction, or a unique constraint that makes the second redemption fail. An application-level `if` around a `read` and a `write` is a race waiting for a hunter with a parallel-request tool.
</Gotcha>

## Account Takeover via OAuth

**Account takeover (ATO)** is the corpus's highest-value reachable class (~532 reports). One of the most common routes is a flaw in the **OAuth** redirect — and it usually comes down to one weak check: `redirect_uri` validation.

<Define term="OAuth redirect_uri takeover">
In OAuth, after you authorize an app, the provider redirects back to the app's `redirect_uri` carrying a **code** or **token**. The provider must verify that `redirect_uri` **exactly matches** a pre-registered value — because whoever receives that redirect receives the credential. If the check is weak (allows arbitrary subdomains, does a prefix/substring match, permits open-redirect-style `//evil.com`, or ignores the path), an attacker crafts an authorization link with *their* `redirect_uri`, the victim clicks it while logged in, and the **code/token is delivered to the attacker** — instant account takeover. The companion bug is a missing/unchecked `state` parameter (CSRF on the OAuth flow). The fix: **exact-match** `redirect_uri` against a strict allowlist, and require a `state` value bound to the session.
</Define>

The validation logic — broken vs correct — is small, and the difference is everything:

<GoPlayground>

```go
package main

import (
	"fmt"
	"strings"
)

var registered = map[string]bool{
	"https://app.example.com/callback": true,
	"https://app.example.com/oauth/cb": true,
}

// VULNERABLE: prefix match — app.example.com.evil.com/callback passes.
func validRedirectRacy(uri string) bool {
	return strings.HasPrefix(uri, "https://app.example.com")
}

// SAFE: exact match against the registered allowlist.
func validRedirectSafe(uri string) bool {
	return registered[uri]
}

func main() {
	tests := []string{
		"https://app.example.com/callback",           // legit
		"https://app.example.com.evil.com/callback",  // lookalike domain
		"https://app.example.com@evil.com/callback",  // userinfo trick
		"https://evil.com/?x=https://app.example.com", // substring trick
	}
	for _, u := range tests {
		fmt.Printf("racy=%-5v safe=%-5v  %s\n",
			validRedirectRacy(u), validRedirectSafe(u), u)
	}
}
```

## Password Reset Flaws

The other main road to account takeover: the **forgot-password** flow. It hands out a credential (a reset token) by email — and every weakness in how that token is generated, delivered, or validated is a takeover.

<Define term="Password reset token flaws">
A password-reset flow emails a one-time token that authorizes setting a new password. The classic flaws: **predictable tokens** (sequential IDs, timestamps, weak PRNGs — guessable, so an attacker resets *your* password without the email); **host-header poisoning** (the reset link's domain is built from the request's `Host` header, so an attacker sets `Host: evil.com` and the victim's reset link points at the attacker's server, leaking the token when clicked); **token leakage** (the token returned in an API response, or sent to a `redirect_uri`/Referer); and **no expiry / reuse** (an old token still works). The fixes: generate tokens with a **CSPRNG** (`crypto/rand`), never trust the `Host` header for link construction (use a configured base URL), single-use and short-expiry, and compare in **constant time**.
</Define>

The token-generation difference — predictable vs cryptographically secure — is the heart of it:

<GoPlayground>

```go
package main

import (
	"crypto/rand"
	"crypto/subtle"
	"encoding/hex"
	"fmt"
	mrand "math/rand/v2"
)

// VULNERABLE: predictable token from a non-crypto PRNG. The space is small
// and seed/structure is recoverable — an attacker can guess it.
func weakToken() string {
	return fmt.Sprintf("%06d", mrand.IntN(1_000_000)) // 6 digits: 1M guesses
}

// SAFE: 256 bits from the OS CSPRNG. No seed, no feasible brute force.
func strongToken() string {
	b := make([]byte, 32)
	rand.Read(b) // crypto/rand: cryptographically secure
	return hex.EncodeToString(b)
}

func main() {
	fmt.Println("WEAK (guessable):")
	for i := 0; i < 3; i++ {
		fmt.Println("  ", weakToken())
	}
	fmt.Println("STRONG (crypto/rand):")
	for i := 0; i < 3; i++ {
		fmt.Println("  ", strongToken())
	}

	// Validate in constant time — never ==, which can leak via timing.
	issued := strongToken()
	supplied := issued
	ok := subtle.ConstantTimeCompare([]byte(issued), []byte(supplied)) == 1
	fmt.Println("constant-time match:", ok)
}
```

The reset flow is a credential dispenser — every weakness in it is an account takeover, which is why it's one of the most lucrative areas to audit.

## SSRF to Cloud Metadata

**Server-Side Request Forgery (SSRF)** makes the *server* fetch a URL the attacker controls. On its own it's useful; pointed at a cloud provider's **metadata endpoint**, it becomes credential theft — the single highest-impact SSRF escalation.

<Define term="SSRF to cloud metadata (169.254.169.254)">
**SSRF** occurs when an app fetches a user-supplied URL without restriction (an image-from-URL feature, a webhook, a PDF renderer, a URL preview). The devastating escalation: cloud VMs expose an **instance metadata service** at the link-local address **169.254.169.254**, which returns the VM's configuration *and its IAM credentials*. If an attacker can make the server request `http://169.254.169.254/latest/meta-data/iam/security-credentials/`, they get the server's cloud credentials — often the keys to the whole account. **IMDSv1** served these to any request that reached the endpoint; **IMDSv2** requires a `PUT` to fetch a session token first (with a TTL and a hop limit), which most SSRF can't do — so enforcing IMDSv2 is a key mitigation. The app-side fix: validate the fetch target against an **allowlist**, resolve the hostname and **block private/link-local IP ranges** (including 169.254.0.0/16, 10/8, 172.16/12, 192.168/16, 127/8), and re-check after redirects.
</Define>

The defensive core is an SSRF guard that blocks internal addresses — runnable:

<GoPlayground>

```go
package main

import (
	"fmt"
	"net"
	"net/url"
)

// safeFetchTarget reports whether a user-supplied URL is safe to fetch:
// it must be http(s) and must NOT resolve to a private/link-local/loopback IP.
// This blocks the SSRF→metadata escalation (169.254.169.254 is link-local).
func safeFetchTarget(raw string) (bool, string) {
	u, err := url.Parse(raw)
	if err != nil || (u.Scheme != "http" && u.Scheme != "https") {
		return false, "bad scheme"
	}
	ips, err := net.LookupIP(u.Hostname())
	if err != nil {
		return false, "unresolvable"
	}
	for _, ip := range ips {
		if ip.IsPrivate() || ip.IsLoopback() || ip.IsLinkLocalUnicast() || ip.IsUnspecified() {
			return false, "resolves to internal IP " + ip.String()
		}
	}
	return true, "ok"
}

func main() {
	for _, raw := range []string{
		"https://example.com/avatar.png",            // ok (public)
		"http://169.254.169.254/latest/meta-data/",  // cloud metadata — block
		"http://127.0.0.1:6379/",                    // loopback (Redis) — block
		"http://10.0.0.5/admin",                     // private range — block
		"file:///etc/passwd",                        // bad scheme — block
	} {
		ok, why := safeFetchTarget(raw)
		fmt.Printf("allow=%-5v  %-45s %s\n", ok, raw, why)
	}
}
```

</GoPlayground>

<Callout kind="note" title="Real case — SSRF, including the Capital One breach">
*"We Hacked Apple for 3 Months"* (Sam Curry et al., **$288,500** across the project) chained SSRF among many bugs. The most consequential real-world SSRF is the **2019 Capital One breach** (covered in the OWASP field-guide chapter): an SSRF reached the AWS metadata endpoint, retrieved the IAM role's credentials, and exfiltrated 100M+ records from S3 — the textbook SSRF→metadata→credentials chain, and the reason IMDSv2 exists.
</Callout>

<Gotcha>
**Blocking by hostname or a single DNS lookup isn't enough — beware DNS rebinding and redirects.** An attacker can register a domain that resolves to a public IP on the first lookup (passing your check) and to 169.254.169.254 on the *second* (the actual fetch) — DNS rebinding. Or give a public URL that **302-redirects** to the metadata IP. Robust defenses: resolve once and **connect to that exact IP** (don't re-resolve), disable or re-validate redirects, and enforce **IMDSv2** at the infrastructure layer so even a successful SSRF can't grab credentials with a simple GET. App-side validation and infra hardening together.
</Gotcha>

## Subdomain Takeover

A quieter but common high-value bug: **subdomain takeover**, where a forgotten DNS record points at a cloud resource that no longer exists — so the attacker creates that resource and *becomes* the subdomain.

<Define term="Subdomain takeover (dangling DNS)">
A **subdomain takeover** happens when a DNS record (usually a `CNAME`) points a subdomain at a third-party service (`shop.example.com → example.myshopify.com`, or an S3 bucket, Heroku app, GitHub Pages site) that has since been **deprovisioned** — but the DNS record was never removed. The target is now a **dangling pointer**: it references a name on a platform where *anyone* can claim that name. The attacker registers `example.myshopify.com` (or the S3 bucket, etc.), and now controls content served from `shop.example.com` — a *trusted* origin. That trust is the prize: serve phishing on a real subdomain, steal cookies scoped to `*.example.com`, bypass CORS/CSP, or complete an OAuth flow against the trusted host. Detection: enumerate subdomains (recon chapter), check which CNAME to a third party, and test which of those return the platform's "no such app/bucket" fingerprint. The fix: remove DNS records as part of deprovisioning, and claim or monitor dangling ones.
</Define>

The detection heuristic — does a CNAME'd host return a known takeover fingerprint — modeled in runnable Go:

<GoPlayground>

```go
package main

import (
	"fmt"
	"strings"
)

// Known "unclaimed resource" fingerprints per platform (abbreviated).
var fingerprints = map[string]string{
	"herokuapp.com":  "No such app",
	"github.io":      "There isn't a GitHub Pages site here",
	"s3.amazonaws.com": "NoSuchBucket",
}

// vulnerable reports whether a subdomain CNAME'd to `target` is takeoverable,
// given the body its target currently returns.
func vulnerable(cname, body string) (bool, string) {
	for platform, fp := range fingerprints {
		if strings.Contains(cname, platform) && strings.Contains(body, fp) {
			return true, "dangling " + platform + " — claimable"
		}
	}
	return false, "no takeover fingerprint"
}

func main() {
	cases := []struct{ cname, body string }{
		{"shop123.herokuapp.com", "<html>No such app</html>"},     // takeoverable
		{"cdn.example.s3.amazonaws.com", "NoSuchBucket"},          // takeoverable
		{"app.example.com", "<html>Welcome</html>"},              // live, safe
	}
	for _, c := range cases {
		v, why := vulnerable(c.cname, c.body)
		fmt.Printf("takeover=%-5v  %-32s %s\n", v, c.cname, why)
	}
}
```

## Business Logic Flaws

The subtlest class, and the one scanners never find: **business-logic flaws**. There's no malformed payload — the application does exactly what it was coded to do, and that behavior is the bug.

<Define term="Business logic flaw">
A **business-logic flaw** is a vulnerability in the *rules* of the application, not its technical handling of input. The request is well-formed and "valid"; the logic simply permits something it shouldn't: a **negative quantity** that turns a purchase into a credit, a **skipped step** (jump straight to the order-confirmation endpoint without paying), **role/state confusion** (apply a one-per-customer coupon via multiple accounts, or change a price the client shouldn't control), or an **integer underflow** on a refund. Scanners can't find these because nothing is malformed — finding them requires *understanding the intended workflow* and asking "what if I do this step out of order / with a value the designer didn't expect?" That's why they're high-value and human-only.
</Define>

A canonical example — a refund/quantity flaw where a negative value flips the sign of the money — and its guard:

<GoPlayground>

```go
package main

import (
	"errors"
	"fmt"
)

// VULNERABLE: trusts the quantity. A negative quantity makes the total
// negative — the "purchase" CREDITS the attacker instead of charging them.
func chargeRacy(unitPriceCents, qty int) int {
	return unitPriceCents * qty // qty = -5 → negative total → refund
}

// SAFE: validate the business rule — quantity must be a positive, sane integer.
func chargeSafe(unitPriceCents, qty int) (int, error) {
	if qty <= 0 {
		return 0, errors.New("quantity must be positive")
	}
	if qty > 1000 {
		return 0, errors.New("quantity exceeds per-order limit")
	}
	return unitPriceCents * qty, nil
}

func main() {
	fmt.Println("VULNERABLE charge with qty=-5:", chargeRacy(999, -5), "cents (a credit!)")

	if total, err := chargeSafe(999, -5); err != nil {
		fmt.Println("SAFE rejects qty=-5:", err)
	} else {
		fmt.Println("charged", total)
	}
	total, _ := chargeSafe(999, 3)
	fmt.Println("SAFE charge with qty=3:", total, "cents")
}
```

</GoPlayground>

<Callout kind="note" title="Real case — business-logic & access-logic flaws">
*"Hacking CloudKit — How I accidentally deleted your Apple Shortcuts"* (Detectify, **$64,000**) was a logic/permission flaw in how CloudKit scoped access, not an injection. *"Facebook Business Takeover"* (Philippe Harewood, **$27,500**) and *"Workplace by Facebook — Unauthorized access to companies' environments"* (**$27,500**) are pure logic: the app let you reach states and objects you shouldn't, with perfectly valid requests. These pay well precisely because no tool finds them — only someone who maps the workflow and tests its assumptions.
</Callout>

## Exercises

<Exercise n={1} title="Reproduce the withdrawal race" level="medium">

Write a `racy` withdraw (check-then-deduct, no lock) and a `safe` withdraw (mutex), run 50 concurrent withdrawals of 1 against a balance of 5, and show the racy version lets more than 5 succeed (or goes negative) while the safe version stops at exactly 5.

<Solution>

```go
package main

import (
	"fmt"
	"sync"
)

type acct struct {
	mu  sync.Mutex
	bal int
}

func (a *acct) racy() bool {
	if a.bal >= 1 {
		a.bal--
		return true
	}
	return false
}
func (a *acct) safe() bool {
	a.mu.Lock()
	defer a.mu.Unlock()
	if a.bal >= 1 {
		a.bal--
		return true
	}
	return false
}

func run(f func(*acct) bool) (int, int) {
	a := &acct{bal: 5}
	var wg sync.WaitGroup
	var m sync.Mutex
	ok := 0
	for i := 0; i < 50; i++ {
		wg.Add(1)
		go func() {
			defer wg.Done()
			if f(a) {
				m.Lock()
				ok++
				m.Unlock()
			}
		}()
	}
	wg.Wait()
	return ok, a.bal
}

func main() {
	o, b := run((*acct).racy)
	fmt.Printf("racy: %d ok, bal %d\n", o, b)
	o, b = run((*acct).safe)
	fmt.Printf("safe: %d ok, bal %d (should be 5 / 0)\n", o, b)
}
```

The lock turns check-and-deduct into one atomic step. In a real system you'd push this atomicity to the database (`UPDATE ... WHERE bal >= 1`), but the principle is identical.

</Solution>

</Exercise>

<Exercise n={2} title="Exact-match redirect validation" level="easy">

Write `validRedirect(uri string, allow map[string]bool) bool` that exact-matches against an allowlist (no prefix, no substring). Show it accepts a registered URI and rejects `https://app.example.com.evil.com/cb`.

<Solution>

```go
package main

import "fmt"

func validRedirect(uri string, allow map[string]bool) bool {
	return allow[uri] // exact match only
}

func main() {
	allow := map[string]bool{"https://app.example.com/cb": true}
	for _, u := range []string{
		"https://app.example.com/cb",
		"https://app.example.com.evil.com/cb",
		"https://app.example.com/cb/../evil",
	} {
		fmt.Printf("%-5v %s\n", validRedirect(u, allow), u)
	}
}
```

Exact map lookup is immune to every prefix/substring/lookalike trick. The moment you reach for `HasPrefix` or `Contains` on a redirect URI, you've created an account-takeover primitive.

</Solution>

</Exercise>

<Exercise n={3} title="CSPRNG token" level="easy">

Write `token() string` returning 32 bytes from `crypto/rand`, hex-encoded. Generate three and confirm they're 64 hex chars and all different. (This is the only acceptable way to mint a reset token.)

<Solution>

```go
package main

import (
	"crypto/rand"
	"encoding/hex"
	"fmt"
)

func token() string {
	b := make([]byte, 32)
	rand.Read(b)
	return hex.EncodeToString(b)
}

func main() {
	seen := map[string]bool{}
	for i := 0; i < 3; i++ {
		t := token()
		fmt.Printf("len=%d %s\n", len(t), t)
		seen[t] = true
	}
	fmt.Println("all distinct:", len(seen) == 3)
}
```

`crypto/rand` reads the OS CSPRNG — no seed to recover, 256 bits of entropy. Never `math/rand` for anything a security decision depends on.

</Solution>

</Exercise>

<Exercise n={4} title="SSRF internal-IP guard" level="medium">

Write `blocked(host string) bool` that resolves a hostname and returns true if any resolved IP is private, loopback, or link-local. Verify it blocks `localhost` and allows a public name.

<Solution>

```go
package main

import (
	"fmt"
	"net"
)

func blocked(host string) bool {
	ips, err := net.LookupIP(host)
	if err != nil {
		return true // unresolvable → don't fetch
	}
	for _, ip := range ips {
		if ip.IsPrivate() || ip.IsLoopback() || ip.IsLinkLocalUnicast() || ip.IsUnspecified() {
			return true
		}
	}
	return false
}

func main() {
	for _, h := range []string{"localhost", "example.com"} {
		fmt.Printf("blocked(%s) = %v\n", h, blocked(h))
	}
}
```

The link-local check (`IsLinkLocalUnicast`) is what stops `169.254.169.254`. Remember the deeper defenses too: connect to the resolved IP (no re-resolve), block redirects, and enforce IMDSv2 at the infra layer.

</Solution>

</Exercise>

<Exercise n={5} title="Reject the negative-quantity charge" level="easy">

Write `charge(unitCents, qty int) (int, error)` that errors on `qty <= 0` (and over a sane max), else returns `unitCents*qty`. Show `qty = -3` is rejected, not turned into a credit.

<Solution>

```go
package main

import (
	"errors"
	"fmt"
)

func charge(unitCents, qty int) (int, error) {
	if qty <= 0 {
		return 0, errors.New("quantity must be positive")
	}
	if qty > 1000 {
		return 0, errors.New("quantity exceeds limit")
	}
	return unitCents * qty, nil
}

func main() {
	if _, err := charge(500, -3); err != nil {
		fmt.Println("rejected:", err)
	}
	t, _ := charge(500, 4)
	fmt.Println("charged:", t)
}
```

Validating the business rule (quantity is a positive, bounded integer) is the entire fix. Logic flaws are invisible to scanners — only a human checking "what value did the designer assume here?" catches the negative-quantity credit.

</Solution>

</Exercise>

<Recap>

- **Race conditions (TOCTOU)** break a check that's correct sequentially by interleaving a concurrent request between check and act. Trigger: fire identical requests in parallel. Fix: **atomicity** — a lock, an atomic CAS, or a conditional `UPDATE ... WHERE balance >= amount` in the DB. A per-request `if` around a read and a write is not a limit.
- **Account takeover via OAuth** usually hinges on weak `redirect_uri` validation: a prefix/substring/subdomain match lets an attacker's lookalike domain receive the victim's auth code. Fix: **exact-match** against a registered allowlist, plus a session-bound `state`.
- **Password-reset flaws** turn "forgot password" into "take any account": predictable tokens, host-header-poisoned links, leaked or reusable tokens. Fix: **`crypto/rand`** tokens, never trust the `Host` header for links, single-use + short expiry, constant-time compare.
- **SSRF to cloud metadata** escalates a server-side fetch into credential theft via `169.254.169.254`. Fix: allowlist targets, resolve and **block private/link-local/loopback IPs**, connect to the resolved IP (defeat DNS rebinding), block redirects, and enforce **IMDSv2** at the infra layer.
- **Subdomain takeover** claims a dangling DNS record pointing at a deprovisioned cloud resource, giving the attacker a **trusted origin** to phish, steal cookies, or bypass SSO. Fix: remove DNS records as part of deprovisioning; monitor for takeover fingerprints.
- **Business-logic flaws** are valid requests that violate the app's rules — negative quantities, skipped steps, role/state confusion. Scanners can't find them; only mapping the intended workflow and questioning its assumptions does. Fix: **validate the business rule** (positive bounded quantities, enforced step order, server-side prices).
- **The through-line:** these are the corpus's money-makers because they're *reachable* and often *human-only*. Each has a small, specific Go fix — and writing the broken and fixed versions side by side is how you learn to spot the shape instantly.

</Recap>
