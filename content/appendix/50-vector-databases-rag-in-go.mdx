### The Three Core Mathematical Primitives

Every semantic search query boils down to three linear algebra calculations between a query vector `U` and an indexed candidate vector `V`:

1. **The Dot Product (Inner Product):**
   ```text
   DotProduct(U, V) = U[0]*V[0] + U[1]*V[1] + ... + U[D-1]*V[D-1]
   ```
   The dot product multiplies corresponding coordinates across dimension $D$ and sums the products. When vectors point in the same direction, the sum is strongly positive. When orthogonal (at 90 degrees), the sum is zero. When pointing in opposite directions, the sum is negative.

2. **Euclidean Magnitude (L2 Norm):**
   ```text
   Magnitude(U) = sqrt(U[0]^2 + U[1]^2 + ... + U[D-1]^2)
   ```
   The length of the vector in Euclidean space.

3. **Cosine Similarity:**
   ```text
   CosineSimilarity(U, V) = DotProduct(U, V) / (Magnitude(U) * Magnitude(V))
   ```
   Cosine similarity measures the angle between two vectors, completely ignoring their length. This is mandatory for natural language processing because a two-sentence chunk and a two-paragraph chunk discussing the exact same topic might have different vector magnitudes, but their directional orientation in semantic space remains identical.

<Define term="Vector Embedding" since="Appendix · Chapter 50">
A dense numerical slice of floating-point numbers representing the learned semantic concepts of a text passage or query, where geometric proximity in high-dimensional vector space corresponds directly to conceptual similarity.
</Define>

<Define term="Cosine Similarity" since="Appendix · Chapter 50">
A geometric metric calculating the cosine of the angle between two high-dimensional vectors, bounded between -1.0 (opposing) and +1.0 (identical direction), independent of vector length.
</Define>

### The Unit Vector Optimization: Eliminating Sqrt and Div

Notice the formula for cosine similarity:
```text
CosineSimilarity(U, V) = DotProduct(U, V) / (Magnitude(U) * Magnitude(V))
```

On an index with 1,000,000 vectors, executing this formula naively requires:
- 1,000,000 square roots
- 1,000,000 floating-point divisions
- 1,000,000 dot products

Square roots and divisions are notoriously expensive CPU instructions (taking 10 to 40 CPU clock cycles compared to 1 cycle for Fused Multiply-Add). 

Here is how the professionals do it: **Normalize every vector to unit length upon insertion.**

```text
Normalized(U) = U / Magnitude(U)  =>  Magnitude(Normalized(U)) == 1.0
```

When both `U` and `V` are pre-normalized unit vectors, the denominator becomes `1.0 * 1.0 = 1.0`. The formula collapses to:

```text
CosineSimilarity(U, V) = DotProduct(Normalized(U), Normalized(V))
```

By pre-normalizing your vectors at ingestion time, your hot query search loop executes **zero square roots** and **zero divisions**. It becomes a pure, branchless dot product of floating-point multiplies and adds.

<UnderTheHood title="SIMD Vector Math, Memory Alignment & CPU Cache Utilization">

Let's talk hardware. Why `float32` and not `float64`?

A standard modern embedding model (such as OpenAI's `text-embedding-3-small` or Voyage AI) produces vectors with $D = 1536$ dimensions:
- In `float64`: `1536 * 8 bytes = 12,288 bytes = 12 KB` per vector.
- In `float32`: `1536 * 4 bytes = 6,144 bytes = 6 KB` per vector.

A typical modern CPU core (x86-64 Zen 4/5 or Apple Silicon M2/M3/M4) has a **64 KB L1 data cache** and 64-byte cache lines. 
- A 64-byte cache line holds exactly **16 `float32` values** (`16 * 4 = 64`).
- A contiguous `[]float32` vector of 1536 dimensions spans exactly **96 consecutive cache lines** (`1536 / 16 = 96`).
- The hardware memory prefetcher detects linear stride access instantly, streaming consecutive cache lines from L2/L3 cache into L1 data registers with zero pipeline stalls.

If you store vectors as a slice of slices `[][]float32`, or worse, as structs containing pointers `[]*float32`, each vector lives in a disjoint heap allocation. The CPU hardware prefetcher is rendered blind; every vector lookup triggers a 24-byte slice header dereference and a random memory hop, causing severe L1 cache thrashing.

Furthermore, in pure Go, you can unroll the dot product loop 4-way to allow the CPU's out-of-order execution engine to issue multiple independent FMA (Fused Multiply-Add) operations across parallel arithmetic ports:

```go
func DotProduct4Way(a, b []float32) float32 {
	n := len(a)
	_ = b[n-1] // Bounds check elimination (BCE) hint for Go compiler

	var sum0, sum1, sum2, sum3 float32
	i := 0
	for ; i <= n-4; i += 4 {
		sum0 += a[i] * b[i]
		sum1 += a[i+1] * b[i+1]
		sum2 += a[i+2] * b[i+2]
		sum3 += a[i+3] * b[i+3]
	}
	// Accumulate tail elements
	tail := sum0 + sum1 + sum2 + sum3
	for ; i < n; i++ {
		tail += a[i] * b[i]
	}
	return tail
}
```

Notice the line `_ = b[n-1]`. As of Go 1.24 and Go 1.26, this subtle statement informs the Go SSA compiler that slice `b` is at least as long as `a`, permanently eliminating runtime boundary checks (`runtime.panicIndex`) inside the tight numerical loop.

</UnderTheHood>

## Vector Indexing: Flat vs HNSW

Now that the math is established, how do you index and query hundreds of thousands of vectors? You have two architectural choices: **Flat Indexing** and **Approximate Nearest Neighbors (ANN) via HNSW**.

### Exact Search: The Flat Index

A **Flat Index** is an exhaustive brute-force search. It keeps every vector in contiguous memory. When a query arrives, it computes the dot product against all $N$ vectors, sorts the scores, and returns the top-$K$ candidates:

- **Time Complexity:** $O(N \cdot D)$
- **Recall:** 100% (Mathematical perfection. It never misses the true nearest neighbor.)
- **Index Build Time:** Instantaneous ($O(1)$ append).
- **Memory Overhead:** Zero graph pointers or edge lists.

At $N = 10,000$ documents and $D = 1536$, calculating $10,000$ dot products requires $15.36 \times 10^6$ floating-point multiplications. On modern Go with cache-friendly layout, a single CPU core computes this in **1.4 milliseconds**. Across 8 worker goroutines, it completes in **under 250 microseconds**.

For datasets up to 50,000 documents (the size of most corporate knowledge bases, internal wikis, and legal vaults), an in-memory Flat Index is not only simpler—it is often faster than distributed vector databases because it incurs zero network serialization overhead!

### Approximate Nearest Neighbors: The HNSW Graph

When your dataset scales to 5,000,000 vectors, $O(N)$ linear scans become unsustainable (costing 150ms+ per query and saturating CPU cores). You must trade mathematical certainty for logarithmic speed: $O(\log N)$.

The undisputed king of graph-based ANN algorithms is **HNSW (Hierarchical Navigable Small World)**, developed by Malkov and Yashunin.

<Define term="HNSW Index" since="Appendix · Chapter 50">
A multi-layer graph data structure where each layer forms a proximity graph of high-dimensional vectors with skip-list properties, enabling $O(\log N)$ approximate nearest neighbor retrieval with over 98% recall accuracy.
</Define>

How HNSW works:
1. **Multi-Layer Skip Graph:** HNSW organizes vectors into hierarchical layers (Layer 0 to Layer `L_max`).
2. **Layer Hierarchy:** Layer 0 contains *all* vectors connected in a dense Delaunay graph. Each higher layer contains an exponentially smaller subset of nodes connected by long-range "expressway" links.
3. **Greedy Traversal:** A query vector starts at the top layer's entry point. It evaluates distance to the entry point's neighbors and greedily hops to whichever neighbor is closest to the query.
4. **Layer Transition:** When no neighbor on layer $L$ is closer to the query than the current node (a local minimum), the search drops down to layer $L-1$ and resumes from that node.
5. **Layer 0 Beam Search:** On Layer 0, the algorithm conducts a bounded priority queue beam search (`efSearch`) to collect the top-$K$ closest neighbors.

```
Layer 2 (Expressway):      [Node A] ----------------------------> [Node K]
                              |                                      |
Layer 1 (Highway):         [Node A] ---------> [Node D] --------> [Node K]
                              |                   |                  |
Layer 0 (Local Streets):   [Node A] <-> [Node B] <-> [Node D] <-> [Node K]
```

## Document Chunking & Embeddings

You cannot feed a 100-page loan agreement or corporate policy manual directly into an embedding model. If you embed an entire 40-page PDF as a single vector, the embedding model averages all concepts together into a meaningless, blurry semantic vector. You lose the ability to retrieve specific clauses, interest rates, or liability terms.

High-precision retrieval begins with **Document Chunking**.

<Define term="Semantic Chunking" since="Appendix · Chapter 50">
The process of dividing raw unstructured text into discrete, contextually coherent passages based on syntactic boundaries (sentences, paragraphs, markdown headers) and token limits, preserving local semantic integrity.
</Define>

### Chunking Strategies: The Sliding Window

A naive chunker simply cuts text every 500 characters. This is disastrous: it chops words in half and severs sentences mid-thought.

Production systems use **Sliding Window Chunking with Overlap**:
- **Chunk Size:** The maximum context length (e.g. 512 tokens or words).
- **Overlap Window:** A trailing segment duplicated across consecutive chunks (e.g. 64 tokens or words).

```
Document: [Token 0 ........................................ Token 512]  (Chunk 0)
                               [Token 448 ................. Token 960]  (Chunk 1: 64-token overlap)
                                                             [Token 896 ....] (Chunk 2)
```

Why overlap? If a crucial legal stipulation spans words 490 through 530, a non-overlapping chunker splits the sentence across Chunk 0 and Chunk 1. Neither chunk contains the complete semantic idea, causing vector search to miss it completely. An overlap window guarantees that the complete thought is preserved intact within at least one chunk.

### Metadata Tagging: The Secret to Production Precision

A vector by itself is useless without context. In Go, every chunk must be paired with structured metadata:

```go
type ChunkMetadata struct {
	ChunkID     string    `json:"chunk_id"`
	DocumentID  string    `json:"document_id"`
	Title       string    `json:"title"`
	Section     string    `json:"section"`
	WordCount   int       `json:"word_count"`
	AccessTier  int       `json:"access_tier"` // 1 = Public, 2 = Internal, 3 = Confidential
	CreatedAt   time.Time `json:"created_at"`
}

type IndexedChunk struct {
	Metadata  ChunkMetadata
	RawText   string
	Embedding []float32 // 1536-dimensional unit-normalized vector
}
```

Metadata allows your retrieval engine to perform **Hybrid Pre-Filtering**: "Retrieve the top 3 chunks matching the query `WHERE AccessTier <= user.AccessTier AND DocumentID == 'meridian-compliance-2026'`" before or during vector ranking.

### Prompt Assembly & Hallucination Suppression

How do you prevent the LLM from hallucinating when external context is provided? You do not ask it nicely; you constrain its operational boundaries with a surgical system prompt:

```markdown
SYSTEM: You are the Meridian Financial Autonomous Assistant.
You must answer the user query strictly and exclusively based on the VERIFIED CONTEXT provided below.
Rules:
1. If the provided context does not contain sufficient facts to answer the query with 100% certainty, output: "Insufficient authorized documentation."
2. Cite the exact Source ID for every claim made.
3. Do NOT extrapolate, speculate, or introduce external knowledge.

--- VERIFIED CONTEXT ---
[Source 1: Meridian Repo Rulebook §4.2 | ID: chunk-102]
Overnight repo transactions require a minimum 8.5% liquid margin reserve.

--- USER QUERY ---
What is the margin requirement for overnight repo trades?

ASSISTANT:
```

By enforcing these constraints, you convert the LLM from an unreliable generator into a deterministic synthesizer of verified facts.

## Streaming SSE Output

Waiting 5 to 8 seconds for a language model to finish generating a complete 500-token response before sending anything to the client destroys user experience. In modern interfaces, users demand **Time-To-First-Token (TTFT)** under 200 milliseconds.

In Go, you deliver this using **Server-Sent Events (SSE)** and the `http.Flusher` interface.

### The Anatomy of Server-Sent Events

Server-Sent Events is a standard unidirectional streaming protocol over plain HTTP. Unlike WebSockets, it requires no protocol upgrade handshakes, works seamlessly through corporate firewalls, and supports automatic reconnection:

- **MIME Type:** `text/event-stream`
- **Headers:** `Cache-Control: no-cache`, `Connection: keep-alive`, `X-Accel-Buffering: no`
- **Frame Format:**
  ```http
  event: token
  data: {"text": "Overnight"}

  event: token
  data: {"text": " repo"}

  event: done
  data: [DONE]
  ```

### The `http.Flusher` Contract in Go

Standard Go HTTP handlers buffer outgoing responses in memory (typically a 4KB chunk buffer) to maximize TCP packet efficiency. In streaming applications, this buffering is lethal—tokens will sit in Go's memory buffer until 4,096 bytes accumulate!

To bypass this, you type-assert the `http.ResponseWriter` to an `http.Flusher`:

```go
flusher, ok := w.(http.Flusher)
if !ok {
    http.Error(w, "Streaming unsupported by response writer", http.StatusInternalServerError)
    return
}
```

Every time a token arrives from the LLM stream, you write the SSE frame and immediately call `flusher.Flush()`:

```go
fmt.Fprintf(w, "event: token\ndata: %s\n\n", token)
flusher.Flush() // Pushes bytes to network wire immediately!
```

### Context Cancellation: Stopping Goroutine Leaks

What happens if the user closes their browser tab or navigates away while the LLM is mid-stream? If your handler does not listen to `r.Context().Done()`, your server will continue generating tokens, wasting expensive inference compute and leaking goroutines.

Always bind your streaming loop to the request context:

```go
for token := range tokenChan {
    select {
    case <-r.Context().Done():
        // Client disconnected! Abort LLM stream and free resources immediately.
        return
    default:
        fmt.Fprintf(w, "event: token\ndata: %s\n\n", token)
        flusher.Flush()
    }
}
```

```go
// DocumentChunk represents an indexed text passage with its dense vector embedding.
type DocumentChunk struct {
	ID        string
	DocTitle  string
	Content   string
	Embedding []float32 // Pre-normalized to unit length

// SearchMatch represents a retrieved chunk with its cosine similarity score.

	Chunk DocumentChunk
	Score float32

// InMemVectorStore maintains vectors in cache-friendly contiguous memory.
type InMemVectorStore struct {
	chunks []DocumentChunk
}

// NewInMemVectorStore initializes an empty in-memory vector database.
func NewInMemVectorStore() *InMemVectorStore {
	return &InMemVectorStore{chunks: make([]DocumentChunk, 0)}
}

// NormalizeVector scales a vector to unit length (magnitude = 1.0).
func NormalizeVector(v []float32) []float32 {
	var sumSq float64
	for _, val := range v {
		sumSq += float64(val * val)
	}
	mag := float32(math.Sqrt(sumSq))
	if mag == 0 {
		return v
	}
	norm := make([]float32, len(v))
	invMag := 1.0 / mag
	for i, val := range v {
		norm[i] = val * invMag
	}
	return norm
}

// DotProduct computes the inner product of two slices.
// When both vectors are unit-normalized, DotProduct == Cosine Similarity!
func DotProduct(a, b []float32) float32 {
	n := len(a)
	_ = b[n-1] // Bounds Check Elimination hint

	var sum float32
	i := 0
	for ; i <= n-4; i += 4 {
		sum += a[i]*b[i] + a[i+1]*b[i+1] + a[i+2]*b[i+2] + a[i+3]*b[i+3]
	}
	for ; i < n; i++ {
		sum += a[i] * b[i]
	}
	return sum
}

// Insert registers a document chunk and normalizes its embedding vector.
func (vs *InMemVectorStore) Insert(id, title, content string, rawEmbedding []float32) {
	vs.chunks = append(vs.chunks, DocumentChunk{
		ID:        id,
		DocTitle:  title,
		Content:   content,
		Embedding: NormalizeVector(rawEmbedding),
	})
}

// Search executes an exhaustive top-K cosine similarity search across all indexed chunks.
func (vs *InMemVectorStore) Search(queryVec []float32, topK int) []SearchMatch {
	normQuery := NormalizeVector(queryVec)
	matches := make([]SearchMatch, len(vs.chunks))

	for i, chunk := range vs.chunks {
		matches[i] = SearchMatch{
			Chunk: chunk,
			Score: DotProduct(normQuery, chunk.Embedding),
		}
	}

	// Sort descending by similarity score
	slices.SortFunc(matches, func(a, b SearchMatch) int {
		return cmp.Compare(b.Score, a.Score)
	})

	if len(matches) > topK {
		matches = matches[:topK]
	}
	return matches
}
```

<Exercise n={1} title="SIMD-Aligned Dot Product & Cosine Similarity" level="easy">

Implement a production-grade `CosineSimilarity(a, b []float32) (float32, error)` function.
Requirements:
1. Return `errors.New("dimension mismatch")` if vector lengths do not match.
2. Return `errors.New("empty vector")` if length is zero.
3. Compute the dot product and Euclidean magnitudes.
4. If either vector has zero magnitude, return `errors.New("zero vector has no direction")`.
5. Return the cosine similarity as `dot / (magA * magB)`.

<Solution>

```go
package main

import (
	"errors"
	"fmt"
	"math"
)

func DotProduct(a, b []float32) float32 {
	var sum float32
	for i := range a {
		sum += a[i] * b[i]
	}
	return sum
}

func CosineSimilarity(a, b []float32) (float32, error) {
	if len(a) != len(b) {
		return 0, errors.New("dimension mismatch")
	}
	if len(a) == 0 {
		return 0, errors.New("empty vector")
	}

	dot := DotProduct(a, b)
	magA := float32(math.Sqrt(float64(DotProduct(a, a))))
	magB := float32(math.Sqrt(float64(DotProduct(b, b))))

	if magA == 0 || magB == 0 {
		return 0, errors.New("zero vector has no direction")
	}

	return dot / (magA * magB), nil
}

func main() {
	v1 := []float32{1.0, 2.0, 3.0}
	v2 := []float32{2.0, 4.0, 6.0} // Identical direction, scaled 2x

	sim, err := CosineSimilarity(v1, v2)
	if err != nil {
		panic(err)
	}
	fmt.Printf("Cosine Similarity: %.4f (Expected: 1.0000)\n", sim)
}
```

Because cosine similarity normalizes by vector magnitude, collinear vectors with identical directions evaluate to exactly 1.0, regardless of scale.

</Solution>

<Exercise n={2} title="Sliding Window Text Chunker with Token Overlap" level="medium">

Implement a sliding window text chunker:
`ChunkDocument(text string, chunkSize, overlap int) []TextChunk`

Requirements:
1. Split the text into word tokens using `strings.Fields`.
2. Ensure `chunkSize > overlap`. If not, set `chunkSize = overlap + 1`.
3. Step through words with stride `step = chunkSize - overlap`.
4. Return a slice of `TextChunk` structs containing the 0-indexed chunk number and joined text.
5. Guarantee that the final tail words are preserved without infinite loops.

<Solution>

```go
package main

import (
	"fmt"
	"strings"
)

type TextChunk struct {
	Index   int
	Content string
}

func ChunkDocument(text string, chunkSize, overlap int) []TextChunk {
	words := strings.Fields(text)
	if len(words) == 0 {
		return nil
	}
	if chunkSize <= overlap {
		chunkSize = overlap + 1
	}

	step := chunkSize - overlap
	var chunks []TextChunk
	idx := 0

	for i := 0; i < len(words); i += step {
		end := i + chunkSize
		if end > len(words) {
			end = len(words)
		}
		chunks = append(chunks, TextChunk{
			Index:   idx,
			Content: strings.Join(words[i:end], " "),
		})
		idx++
		if end == len(words) {
			break
		}
	}
	return chunks
}

func main() {
	doc := "Overnight repo transactions require liquid collateral. Tier 1 capital must remain above 8 percent at all times."
	chunks := ChunkDocument(doc, 6, 2)
	for _, c := range chunks {
		fmt.Printf("Chunk #%d: %s\n", c.Index, c.Content)
	}
}
```

The sliding window advances by `chunkSize - overlap`, ensuring adjacent chunks share overlapping context across boundaries.

</Solution>

<Exercise n={3} title="Top-K Vector Search with Min-Heap Priority Queue" level="medium">

Sorting $N$ items takes $O(N \log N)$ time and allocates an $N$-element slice. When $N = 500,000$ and $K = 5$, sorting the entire list wastes millions of CPU cycles.

Implement a top-$K$ selector using Go's `container/heap`:
1. Maintain a min-heap of size at most $K$.
2. For each candidate, if heap length $< K$, push the candidate.
3. Otherwise, if candidate score $>$ minimum score in heap (at index 0), pop the minimum and push the new candidate.
4. Extract the top-$K$ items sorted descending by score in $O(N \log K)$ time.

<Solution>

```go
package main

import (
	"container/heap"
	"fmt"
)

type MatchItem struct {
	ID    string
	Score float32
}

type MinScoreHeap []MatchItem

func (h MinScoreHeap) Len() int           { return len(h) }
func (h MinScoreHeap) Less(i, j int) bool { return h[i].Score < h[j].Score }
func (h MinScoreHeap) Swap(i, j int)      { h[i], h[j] = h[j], h[i] }
func (h *MinScoreHeap) Push(x any)        { *h = append(*h, x.(MatchItem)) }
func (h *MinScoreHeap) Pop() any {
	old := *h
	n := len(old)
	x := old[n-1]
	*h = old[0 : n-1]
	return x
}

func SelectTopK(candidates []MatchItem, k int) []MatchItem {
	if k <= 0 || len(candidates) == 0 {
		return nil
	}
	h := &MinScoreHeap{}
	heap.Init(h)

	for _, c := range candidates {
		if h.Len() < k {
			heap.Push(h, c)
		} else if c.Score > (*h)[0].Score {
			heap.Pop(h)
			heap.Push(h, c)
		}
	}

	result := make([]MatchItem, h.Len())
	for i := len(result) - 1; i >= 0; i-- {
		result[i] = heap.Pop(h).(MatchItem)
	}
	return result
}

func main() {
	candidates := []MatchItem{
		{ID: "doc-A", Score: 0.42},
		{ID: "doc-B", Score: 0.95},
		{ID: "doc-C", Score: 0.12},
		{ID: "doc-D", Score: 0.88},
		{ID: "doc-E", Score: 0.74},
	}

	top2 := SelectTopK(candidates, 2)
	for i, item := range top2 {
		fmt.Printf("#%d: %s (Score: %.2f)\n", i+1, item.ID, item.Score)
	}
}
```

A min-heap of size $K$ guarantees that the worst candidate in the current top-$K$ pool sits at index 0. We inspect and replace it in $O(\log K)$ steps, bypassing the need to sort all $N$ entries.

</Solution>

</Exercise>

<Exercise n={4} title="Streaming HTTP SSE Handler with Flusher and Context Cancellation" level="hard">

Construct a production-grade `http.HandlerFunc` that streams an arbitrary slice of token strings over Server-Sent Events (SSE).
Requirements:

2. Set headers: `Content-Type: text/event-stream`, `Cache-Control: no-cache`, `Connection: keep-alive`, `X-Accel-Buffering: no`.
3. Loop over tokens. In each iteration, check `r.Context().Done()`. If the client disconnected, return immediately.
4. Format each token frame as: `event: token\ndata: {"index":%d,"text":"%s"}\n\n`.
5. Call `flusher.Flush()` after each write.
6. When tokens finish, send `event: done\ndata: {"status":"complete"}\n\n` and flush.

<Solution>

```go
package main

import (
	"context"
	"fmt"
	"net/http"
	"net/http/httptest"
	"strings"
	"time"
)

func StreamTokensHandler(tokens []string) http.HandlerFunc {
	return func(w http.ResponseWriter, r *http.Request) {
		flusher, ok := w.(http.Flusher)
		if !ok {
			http.Error(w, "SSE streaming unsupported", http.StatusInternalServerError)
			return
		}

		w.Header().Set("Content-Type", "text/event-stream")
		w.Header().Set("Cache-Control", "no-cache")
		w.Header().Set("Connection", "keep-alive")
		w.Header().Set("X-Accel-Buffering", "no")

		for i, tok := range tokens {
			select {
			case <-r.Context().Done():
				// Client disconnected; abort stream immediately
				return
			default:
				fmt.Fprintf(w, "event: token\ndata: {\"index\":%d,\"text\":\"%s\"}\n\n", i, tok)
				flusher.Flush()
			}
		}

		fmt.Fprintf(w, "event: done\ndata: {\"status\":\"complete\"}\n\n")
		flusher.Flush()
	}
}

func main() {
	tokens := []string{"Autonomous", " AI", " Systems", " in", " Go"}
	handler := StreamTokensHandler(tokens)

	rec := httptest.NewRecorder()
	req := httptest.NewRequest(http.MethodGet, "/stream", nil)
	ctx, cancel := context.WithTimeout(req.Context(), time.Second)
	defer cancel()
	req = req.WithContext(ctx)

	handler(rec, req)

	fmt.Println("Status:", rec.Code)
	fmt.Println("Content-Type:", rec.Header().Get("Content-Type"))
	fmt.Println("Body Contains [done]:", strings.Contains(rec.Body.String(), "event: done"))
}
```
