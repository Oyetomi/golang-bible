<HeroCard label="Appendix · Deep Dive" title="TLS Fingerprinting & Browser Impersonation">

Here's the thing, sport. You think your Go HTTP client is anonymous — that if you set a believable `User-Agent`, a server can't tell you apart from Chrome. You are wrong, and a server proves it **before your client sends a single header**. The very first packet of the TLS handshake — the *ClientHello* — carries a list of cipher suites, extensions, and curves in a specific order, and that order is as unique to your TLS library as a handwriting sample. Anti-bot systems hash it into a string called **JA3** (or the newer **JA4**), look it up against a database of known browsers, and flag "this is a Go program pretending to be Chrome" in microseconds. No header you set can fix it, because the tell is *underneath* the headers.

This chapter demystifies that tell completely, from the bytes up, and the two Go libraries built to defeat it: **`bogdanfinn/tls-client`** and **`enetx/surf`**, both standing on **uTLS**. You'll learn exactly what's in a ClientHello, how JA3 and JA4 are computed (and compute them yourself, in runnable Go), why Go's `crypto/tls` is instantly identifiable, how uTLS *forges* a ClientHello before `crypto/tls` ever sees it, and the second fingerprint layer most people never reach: the **HTTP/2 Akamai fingerprint**, built from the SETTINGS frame and the order of your pseudo-headers. Nothing assumed. By the end you'll read a JA3 string like a sentence and know precisely which byte to change to look like a real browser.

</HeroCard>

<Callout kind="warn" title="What this is for — and what it isn't">
This chapter teaches you **how fingerprinting works** — knowledge that is essential on both sides of the wire. You need it to **build** bot-detection and scraping defenses (you cannot defend against a fingerprint you don't understand), to **test** your own anti-bot stack, to **research** how anti-bot systems like Cloudflare, Akamai, and DataDome classify clients, and to build legitimate API clients for services you are **authorized** to access. Impersonating a browser to evade access controls on systems you don't own — or to violate a site's terms — is a different matter, and not what this is about. The mechanism is dual-use; the framing here is understanding and defense. Use it on systems you own or are authorized to test.

## The Tell

Start with the thing that breaks the illusion. You write a careful Go scraper: a real Chrome `User-Agent`, the same `Accept`, `Accept-Language`, `Accept-Encoding` headers Chrome sends, in the same order. You send a request. The server returns a CAPTCHA — or a 403, or a block page — and a real Chrome from the same IP sails through. **What gave you away?**

<Define term="TLS fingerprinting" since="Networking & Web Fundamentals (Part 1)">
**TLS fingerprinting** identifies a client from the structure of its TLS handshake — specifically the **ClientHello** message, the first thing a client sends. The ClientHello advertises which cipher suites, TLS extensions, elliptic curves, and signature algorithms the client supports, **in a library-specific order**. Because every TLS implementation builds that list differently (and most never change it), the ClientHello is a stable, passive signature: the server reads it during the handshake, before any HTTP data is exchanged, and before it has to send anything back. No header you set in your HTTP request can alter it, because it happens one layer down, in the TLS library.
</Define>

The headers you so carefully spoofed live in the HTTP layer, *inside* the encrypted tunnel. The fingerprint is in the TLS layer, the tunnel's own setup handshake — it travels in the clear, and it's decided entirely by your TLS library (`crypto/tls`), not your application code. Chrome's TLS library produces Chrome's fingerprint; Go's produces Go's. Setting `User-Agent: Chrome` while sending Go's ClientHello is like mailing a letter signed "Chrome" in an envelope with your own return address printed on it — the envelope is read first.

<Callout kind="note" title="The fields that matter, in ClientHello order">
JA3 reads exactly five things from the ClientHello: the **TLS version**, the **cipher suites** (ordered list), the **extensions** (ordered list), the **supported elliptic curves** (the `supported_groups` extension), and the **EC point formats**. JA4 reads more (ALPN, SNI presence, signature algorithms) and treats some of it differently — covered below. Everything is just 16-bit numbers (`uint16`) defined by IANA; the fingerprint is those numbers, decimal-encoded and joined.
</Callout>

## JA3 — the MD5 Fingerprint

JA3 (Salesforce, 2017) is the original and still the most widely deployed TLS-client fingerprint. The algorithm is small enough to hold in your head, and you're about to compute it by hand.

<Define term="JA3">
**JA3** builds one string from five ClientHello fields, in this exact order: `SSLVersion,Ciphers,Extensions,EllipticCurves,ECPointFormats`. Fields are separated by **commas**; the values within a field (each a decimal `uint16`) are separated by **hyphens**. That string is then **MD5-hashed** into a 32-character hex fingerprint. Crucially, **GREASE values are removed first** (more below), so a browser's deliberately-random GREASE entries don't change its fingerprint. JA3 captures *which* parameters a client offers **and the order** it offers them in.
</Define>

Here is the canonical JA3 string and its hash — the example from Salesforce's reference — and the same computation in runnable Go:

```go
package main

import (
	"crypto/md5"
	"encoding/hex"
	"fmt"
	"strconv"
	"strings"
)

// ja3 builds the JA3 string from the five ClientHello fields and MD5s it.
// Order: SSLVersion,Ciphers,Extensions,EllipticCurves,ECPointFormats
//   - fields joined by ","   - values within a field joined by "-"
//   - all values are decimal uint16
func ja3(version uint16, ciphers, extensions, curves, formats []uint16) (string, string) {
	join := func(xs []uint16) string {
		parts := make([]string, len(xs))
		for i, x := range xs {
			parts[i] = strconv.Itoa(int(x))
		}
		return strings.Join(parts, "-")
	}
	raw := strings.Join([]string{
		strconv.Itoa(int(version)),
		join(ciphers),
		join(extensions),
		join(curves),
		join(formats),
	}, ",")
	sum := md5.Sum([]byte(raw))
	return raw, hex.EncodeToString(sum[:])
}

func main() {
	// The canonical Salesforce JA3 example (a TLS 1.2 client).
	raw, fp := ja3(
		769, // TLS 1.2
		[]uint16{47, 53, 5, 10, 49161, 49162, 49171, 49172, 50, 56, 19, 4},
		[]uint16{0, 10, 11},
		[]uint16{23, 24, 25},
		[]uint16{0},
	)
	fmt.Println("JA3 string:", raw)
	fmt.Println("JA3 MD5:   ", fp) // ada70206e40642a3e4461f35503241d5
}
```

<Gotcha>
**Order is everything.** JA3 hashes the cipher and extension lists *in the order the client sent them*. Two clients that support the identical set of ciphers but list them in a different order get **different** JA3 hashes. This is why you can't just configure Go's `crypto/tls` with "Chrome's cipher suites" — Go re-orders and re-shapes the ClientHello its own way. Matching the *set* isn't enough; you must match the *sequence*, byte for byte. Only a library that lets you emit a raw, ordered ClientHello (uTLS) can do that.
</Gotcha>

### GREASE — the randomness JA3 must ignore

Chrome deliberately inserts **GREASE** values (Generate Random Extensions And Sustain Extensibility, RFC 8701) — reserved fake cipher/extension/curve IDs — into its ClientHello, in random slots, to keep servers from ossifying on a fixed set. If JA3 hashed those, Chrome's fingerprint would change every connection. So **JA3 strips GREASE first**. The GREASE values are the 16 patterns `0x0a0a, 0x1a1a, 0x2a2a … 0xfafa` — both bytes equal, low nibble `0xa`:

<GoPlayground>

```go
package main

import "fmt"

// isGREASE reports whether a uint16 is one of the 16 reserved GREASE values
// (RFC 8701): 0x0a0a, 0x1a1a, ... 0xfafa. Pattern: the two bytes are equal
// AND the low nibble of each is 0xa.
func isGREASE(v uint16) bool {
	return v&0x0f0f == 0x0a0a && byte(v>>8) == byte(v)
}

// stripGREASE removes GREASE values before fingerprinting — without this,
// Chrome's random GREASE would change its JA3 every single connection.
func stripGREASE(xs []uint16) []uint16 {
	out := xs[:0:0]
	for _, x := range xs {
		if !isGREASE(x) {
			out = append(out, x)
		}
	}
	return out
}

func main() {
	// A Chrome-like cipher list with two GREASE values injected (0x3a3a, 0x8a8a).
	raw := []uint16{0x3a3a, 0x1301, 0x1302, 0x1303, 0x8a8a, 0xc02b, 0xc02f}
	fmt.Printf("raw     (%d): %#x\n", len(raw), raw)
	clean := stripGREASE(raw)
	fmt.Printf("cleaned (%d): %#x\n", len(clean), clean)

	for _, v := range []uint16{0x0a0a, 0x3a3a, 0xfafa, 0x1301, 0xc02b} {
		fmt.Printf("  %#04x GREASE? %v\n", v, isGREASE(v))
	}
}
```

</GoPlayground>

This is the first reason naive impersonation fails: a real browser *has* GREASE in its raw ClientHello, in random positions, and the fingerprinter strips it. Your forged ClientHello must include GREASE in browser-correct slots too, or a deeper inspection notices its absence.

## JA4 — the Modern Fingerprint

JA3's weakness is exactly its strength: it depends on **order**. Attackers learned to randomize their cipher order ("cipher stunting") to get a fresh JA3 every connection and slip past hash blocklists. **JA4** (FoxIO, 2023) is the answer — and it's what modern anti-bot stacks increasingly use.

<Define term="JA4 (TLS client)">
**JA4** is a newer, more robust TLS-client fingerprint with a human-readable `a_b_c` structure. The **`a`** part is plaintext: protocol (`t`=TCP, `q`=QUIC), TLS version, SNI present (`d`) or not (`i`), a 2-digit cipher count, a 2-digit extension count, and the first ALPN value (e.g. `h2`). The **`b`** part is a 12-hex truncated **SHA-256** of the **sorted** cipher list. The **`c`** part is a truncated SHA-256 of the **sorted** extension list plus the signature algorithms. Two changes from JA3 matter most: it **sorts** ciphers and extensions (so reordering them no longer changes the hash — defeating cipher stunting and GREASE-shuffling), and it uses **SHA-256** instead of MD5. GREASE is removed before hashing, and signature algorithms are folded in for extra resolution.
</Define>

Here is JA4's structure assembled in runnable Go — the plaintext `a` part plus the two sorted SHA-256 hashes:

```go
package main

import (
	"crypto/sha256"
	"encoding/hex"
	"fmt"
	"sort"
	"strings"
)

// hex2 lowercases each uint16 to a 4-char hex token, e.g. 0x1301 -> "1301".
func hex2(xs []uint16) []string {
	out := make([]string, len(xs))
	for i, x := range xs {
		out[i] = fmt.Sprintf("%04x", x)
	}
	return out
}

// sortedHash sorts the hex tokens, joins with ",", SHA-256s them, and returns
// the first 12 hex chars — exactly how JA4 derives its `b` and `c` parts.
// Sorting is the whole point: reordering the input can no longer change output.
func sortedHash(tokens []string) string {
	sort.Strings(tokens)
	sum := sha256.Sum256([]byte(strings.Join(tokens, ",")))
	return hex.EncodeToString(sum[:])[:12]
}

func main() {
	// A TLS 1.3 client over TCP, SNI present, ALPN "h2".
	ciphers := []uint16{0x1301, 0x1302, 0x1303, 0xc02b, 0xc02f, 0xc02c, 0xc030}
	exts := []uint16{0x0000, 0x0017, 0x000a, 0x000b, 0x0010, 0x0023, 0x002b}

	// JA4_a: t = TCP, 13 = TLS 1.3, d = SNI present, then 2-digit counts, then ALPN.
	a := fmt.Sprintf("t13d%02d%02dh2", len(ciphers), len(exts))
	b := sortedHash(hex2(ciphers)) // sorted cipher hash
	c := sortedHash(hex2(exts))    // sorted extension (+ sig-alg) hash

	fmt.Printf("JA4 = %s_%s_%s\n", a, b, c)

	// Prove sort-invariance: shuffle the ciphers, hash again — same `b`.
	shuffled := []uint16{0xc030, 0x1303, 0xc02b, 0x1301, 0xc02f, 0x1302, 0xc02c}
	fmt.Println("cipher hash, original order:", sortedHash(hex2(ciphers)))
	fmt.Println("cipher hash, shuffled order:", sortedHash(hex2(shuffled)))
	fmt.Println("equal (shuffle defeated):  ", sortedHash(hex2(ciphers)) == sortedHash(hex2(shuffled)))
}
```

package main

	"crypto/sha256"
	"encoding/hex"
	"fmt"
	"sort"
	"strings"

## uTLS — Forging the Hello

**uTLS** (`github.com/refraction-networking/utls`) is a fork of `crypto/tls` whose entire reason to exist is letting you control the ClientHello. It still does real TLS — the handshake, key exchange, and encryption are the standard, audited `crypto/tls` machinery — but it **swaps in your chosen ClientHello before that machinery serializes and sends it.**

The mechanism, in uTLS's own API (this needs the external `utls` module, so it's shown illustratively, not as a runnable playground):

```go
// Requires github.com/refraction-networking/utls — illustrative, not a playground.
package main

import (
	"net"

	utls "github.com/refraction-networking/utls"
)

func dialChrome(addr, sni string) (*utls.UConn, error) {
	tcp, err := net.Dial("tcp", addr)
	if err != nil {
		return nil, err
	}
	// UClient wraps the TCP conn. HelloChrome_Auto = "parrot the latest Chrome".
	// The config carries policy (ServerName for SNI); the ClientHelloID carries
	// the byte layout. crypto/tls never builds its own Hello here.
	uconn := utls.UClient(tcp, &utls.Config{ServerName: sni}, utls.HelloChrome_Auto)
	if err := uconn.Handshake(); err != nil { // forged Hello goes out here
		return nil, err
	}
	return uconn, nil // a real, secure TLS conn — fingerprinted as Chrome
}

// For exact control, use HelloCustom + a ClientHelloSpec you build (or one
// captured from a real browser via utls.Fingerprinter), then uconn.ApplyPreset(spec).
// The Roller cycles HelloIDs until one connects and reuses the winner — so you
// don't suspiciously change fingerprints mid-session.
```

<Callout kind="pro" title="ClientHelloID vs ClientHelloSpec vs Fingerprinter">
Three levels of control, increasing in precision: a **`ClientHelloID`** (`HelloChrome_Auto`, `HelloFirefox_120`) is a named preset uTLS maintains for a real browser version — easiest, and what you want 95% of the time. A **`ClientHelloSpec`** (with `HelloCustom` + `ApplyPreset`) is a hand-built struct of `CipherSuites`, `Extensions`, curves, ALPN — full manual control for a fingerprint uTLS doesn't ship. The **`Fingerprinter`** captures a real browser's raw ClientHello bytes and produces a `ClientHelloSpec` you can replay — copy a fingerprint you observed in the wild exactly. `tls-client` and `surf` are built on the first level, maintaining their own up-to-date preset library.
</Callout>

## The HTTP/2 Fingerprint

Forging the ClientHello defeats the TLS-layer fingerprint — but there's a second layer waiting, and it trips up most people. Once the tunnel is open and the client speaks HTTP/2, the **way it sets up the HTTP/2 connection** is itself a fingerprint: the **Akamai HTTP/2 fingerprint**.

<Define term="HTTP/2 (Akamai) fingerprint">
Akamai's HTTP/2 fingerprint (2017 white paper) identifies a client from how it opens an HTTP/2 connection, in four pipe-separated sections: **(1)** the **SETTINGS** frame parameters as `id:value` pairs joined by `;`; **(2)** the **WINDOW_UPDATE** increment on stream 0 (or `0` if none); **(3)** the **PRIORITY** frames as `streamID:exclusive:dep:weight` (or `0`); **(4)** the **pseudo-header order** as the letters `m`, `a`, `s`, `p` (`:method`, `:authority`, `:scheme`, `:path`). Browsers send distinctive, stable values here — Chrome's pseudo-header order is `m,a,s,p`; Go's `net/http2` sends a different SETTINGS frame and header order — so this fingerprints the client just like JA3 does at the TLS layer.
</Define>

You can parse a SETTINGS frame and emit the Akamai string from stdlib — the frame is a simple binary format (a 9-byte HTTP/2 frame header, then 6-byte `id:value` entries):

<GoPlayground>

```go
package main

import (
	"encoding/binary"
	"fmt"
	"strings"
)

// HTTP/2 SETTINGS parameter names (RFC 9113).
var settingName = map[uint16]string{
	1: "HEADER_TABLE_SIZE", 2: "ENABLE_PUSH", 3: "MAX_CONCURRENT_STREAMS",
	4: "INITIAL_WINDOW_SIZE", 5: "MAX_FRAME_SIZE", 6: "MAX_HEADER_LIST_SIZE",
}

// parseSettings reads an HTTP/2 SETTINGS frame's payload (6 bytes per entry:
// 2-byte id, 4-byte value) and returns the Akamai first-section string:
// "id:value;id:value;..." in the order sent.
func parseSettings(payload []byte) string {
	var parts []string
	for i := 0; i+6 <= len(payload); i += 6 {
		id := binary.BigEndian.Uint16(payload[i : i+2])
		val := binary.BigEndian.Uint32(payload[i+2 : i+6])
		parts = append(parts, fmt.Sprintf("%d:%d", id, val))
	}
	return strings.Join(parts, ";")
}

func main() {
	// A Chrome-like SETTINGS payload: HEADER_TABLE_SIZE=65536, ENABLE_PUSH=0,
	// INITIAL_WINDOW_SIZE=6291456, MAX_HEADER_LIST_SIZE=262144.
	var payload []byte
	put := func(id uint16, v uint32) {
		b := make([]byte, 6)
		binary.BigEndian.PutUint16(b[0:2], id)
		binary.BigEndian.PutUint32(b[2:6], v)
		payload = append(payload, b...)
	}
	put(1, 65536)
	put(2, 0)
	put(4, 6291456)
	put(6, 262144)

	settings := parseSettings(payload)
	windowUpdate, priority, pseudoOrder := "15663105", "0", "m,a,s,p"
	akamai := strings.Join([]string{settings, windowUpdate, priority, pseudoOrder}, "|")

	fmt.Println("SETTINGS section:", settings)
	for i := 0; i+6 <= len(payload); i += 6 {
		id := binary.BigEndian.Uint16(payload[i : i+2])
		val := binary.BigEndian.Uint32(payload[i+2 : i+6])
		fmt.Printf("  %d (%s) = %d\n", id, settingName[id], val)
	}
	fmt.Println("\nAkamai HTTP/2 fingerprint:")
	fmt.Println(" ", akamai)
}
```

</GoPlayground>

<Gotcha>
Go's standard `golang.org/x/net/http2` sends its **own** SETTINGS frame and orders pseudo-headers its **own** way — neither matches any browser. So even with a perfectly forged TLS ClientHello (Chrome JA3), Go's stock HTTP/2 layer betrays you: a server sees "Chrome's TLS, Go's HTTP/2" — a combination no real Chrome produces, and a *stronger* bot signal than either layer alone. This is why `tls-client` ships a forked HTTP stack (`fhttp`) with `HeaderOrderKey` and `PHeaderOrderKey`, and `surf` exposes `HTTP2Settings()` — you have to control *both* layers or you've only solved half the fingerprint.
</Gotcha>

## tls-client & surf

Now it assembles. Both libraries do the same core job — emit a browser-accurate ClientHello *and* a browser-accurate HTTP/2 connection — over uTLS, but with different ergonomics.

### bogdanfinn/tls-client — profiles + a forked HTTP stack

`tls-client` pairs uTLS with **`fhttp`** (a fork of `net/http` that exposes header and pseudo-header ordering). You pick a **profile** — a maintained, versioned pairing of a uTLS ClientHello with the matching HTTP/2 settings — via functional options:

```go
// Requires github.com/bogdanfinn/tls-client — illustrative.
package main

import (
	http "github.com/bogdanfinn/fhttp"
	tls_client "github.com/bogdanfinn/tls-client"
	"github.com/bogdanfinn/tls-client/profiles"
)

func newChromeClient() (tls_client.HttpClient, error) {
	jar := tls_client.NewCookieJar()
	opts := []tls_client.HttpClientOption{
		tls_client.WithTimeoutSeconds(30),
		tls_client.WithClientProfile(profiles.Chrome_133), // TLS + HTTP/2 fp together
		tls_client.WithCookieJar(jar),
		tls_client.WithNotFollowRedirects(),
		// tls_client.WithProxyUrl("http://user:pass@host:port"),
	}
	return tls_client.NewHttpClient(tls_client.NewNoopLogger(), opts...)
}

func main() {
	client, _ := newChromeClient()
	req, _ := http.NewRequest(http.MethodGet, "https://example.com", nil)
	// fhttp's HeaderOrderKey controls the HTTP/2 pseudo + regular header order —
	// the fourth section of the Akamai fingerprint.
	req.Header = http.Header{
		"accept":               {"text/html,application/xhtml+xml,*/*"},
		"accept-language":      {"en-US,en;q=0.9"},
		"user-agent":           {"Mozilla/5.0 (...) Chrome/133.0 Safari/537.36"},
		http.HeaderOrderKey:    {"accept", "accept-language", "user-agent"},
		http.PHeaderOrderKey:   {":method", ":authority", ":scheme", ":path"},
	}
	resp, _ := client.Do(req)
	_ = resp
}
```

<Callout kind="note" title="Why a 'profile' is one unit">
`profiles.Chrome_133` is not just a TLS fingerprint — it bundles the uTLS ClientHello spec **and** the matching HTTP/2 settings (SETTINGS values, window update, header-priority behavior) for that exact Chrome version. That pairing is the point: as the earlier Gotcha showed, mixing Chrome's TLS with non-Chrome HTTP/2 is *more* suspicious than either alone. A profile keeps the two layers consistent, and the library maintainers update profiles as browsers ship new versions (`Chrome_144`, `Firefox_135`, `Safari_16_0`, `Okhttp4Android13`, …). Your job is to pick a current one, not to assemble the bytes by hand.
</Callout>

### enetx/surf — a fluent impersonation builder

`surf` wraps the same uTLS foundation behind a fluent builder and an `Impersonate()` API that chains a platform with a browser, plus middleware, retries, and HTTP/3:

```go
// Requires github.com/enetx/surf — illustrative.
package main

import (
	"time"

	"github.com/enetx/surf"
)

func main() {
	cli := surf.NewClient().
		Builder().
		Impersonate().Windows().Chrome(). // platform persona + browser TLS/H2 fp
		Retry(3, 2*time.Second).
		Session(). // shared cookie jar + connection reuse across requests
		Build()

	resp := cli.Get("https://example.com").Do()
	if resp.IsOk() {
		body := resp.Ok().Body.String()
		_ = body
	}
	// .Impersonate().IOS().Firefox(), .RandomOS(), .HTTP2Settings()....Set(),
	// .ForceHTTP3() (QUIC + JA4QUIC), .Std() to hand a fingerprinted *http.Client
	// to a third-party library — all on the same builder.
}
```

<UnderTheHood title="The full path of one impersonated request">

When you fire an impersonated request through either library, here is everything that happens, top to bottom — now that you know each piece:

1. **DNS + TCP** — resolve the host and open a raw TCP connection (optionally through a proxy via a `ContextDialer`).
2. **Forged ClientHello** — uTLS materializes the chosen browser's exact ClientHello: GREASE in the right slots, the browser's cipher order, its extension list and order, its curves and key shares. This is what a passive **JA3/JA4** read sees — and it now says "Chrome", not "Go".
3. **Real handshake** — the standard `crypto/tls`-derived core completes the TLS handshake and ALPN-negotiates `h2`. The cryptography is genuine and secure; only the advertised fingerprint was substituted.
4. **HTTP/2 setup** — the forked HTTP stack sends the browser's **SETTINGS** frame, **WINDOW_UPDATE**, and priority behavior, so the **Akamai HTTP/2 fingerprint** matches too. The earlier "Chrome TLS + Go HTTP/2" contradiction is avoided because the profile pairs them.
5. **Headers in browser order** — your regular headers and the **pseudo-header order** (`m,a,s,p`) are emitted exactly as the browser would, via `HeaderOrderKey` / `PHeaderOrderKey` (tls-client) or the builder's ordered headers (surf).
6. **Response** — cookies land in the jar, redirects follow your policy, and the connection is pooled for reuse — reusing the *same* fingerprinted connection rather than re-handshaking with a fresh one.

Every layer that could fingerprint you — TLS ClientHello, HTTP/2 connection setup, header order — is made to agree on one consistent browser identity. That consistency, not any single spoofed value, is what defeats (or, defensively, what you must detect to build) modern anti-bot fingerprinting.

</UnderTheHood>

<Exercise n={1} title="JA3 from a ClientHello" level="easy">

Write `JA3(version uint16, ciphers, exts, curves, formats []uint16) string` that returns the 32-char MD5 JA3 fingerprint. Verify it produces `ada70206e40642a3e4461f35503241d5` for the canonical input (version 769; ciphers `47-53-5-10-49161-49162-49171-49172-50-56-19-4`; exts `0-10-11`; curves `23-24-25`; formats `0`).

<Solution>

```go
package main

import (
	"crypto/md5"
	"encoding/hex"
	"fmt"
	"strconv"
	"strings"
)

func JA3(version uint16, ciphers, exts, curves, formats []uint16) string {
	dash := func(xs []uint16) string {
		p := make([]string, len(xs))
		for i, x := range xs {
			p[i] = strconv.Itoa(int(x))
		}
		return strings.Join(p, "-")
	}
	raw := strconv.Itoa(int(version)) + "," + dash(ciphers) + "," +
		dash(exts) + "," + dash(curves) + "," + dash(formats)
	sum := md5.Sum([]byte(raw))
	return hex.EncodeToString(sum[:])
}

func main() {
	fp := JA3(769,
		[]uint16{47, 53, 5, 10, 49161, 49162, 49171, 49172, 50, 56, 19, 4},
		[]uint16{0, 10, 11}, []uint16{23, 24, 25}, []uint16{0})
	fmt.Println(fp)
	fmt.Println("matches canonical:", fp == "ada70206e40642a3e4461f35503241d5")
}
```

The whole algorithm is string assembly + MD5. The exact byte-for-byte match against the published hash is your proof the field order and delimiters are right.

</Solution>

</Exercise>

<Exercise n={2} title="Strip GREASE before fingerprinting" level="easy">

Write `IsGREASE(v uint16) bool` (the 16 values `0x0a0a…0xfafa`: both bytes equal, low nibble `0xa`) and `StripGREASE([]uint16) []uint16`. Show that a list with GREASE injected and the same list without it produce the *same* result after stripping.

<Solution>

```go
package main

import "fmt"

func IsGREASE(v uint16) bool { return v&0x0f0f == 0x0a0a && byte(v>>8) == byte(v) }

func StripGREASE(xs []uint16) []uint16 {
	out := make([]uint16, 0, len(xs))
	for _, x := range xs {
		if !IsGREASE(x) {
			out = append(out, x)
		}
	}
	return out
}

func main() {
	withG := []uint16{0x7a7a, 0x1301, 0x1302, 0xdada, 0x1303}
	clean := []uint16{0x1301, 0x1302, 0x1303}
	fmt.Println("stripped:", fmt.Sprint(StripGREASE(withG)) == fmt.Sprint(clean))
	for _, v := range []uint16{0x0a0a, 0x7a7a, 0xfafa, 0x1301} {
		fmt.Printf("%#04x GREASE %v\n", v, IsGREASE(v))
	}
}
```

GREASE is detected purely from the bit pattern — no table lookup. Stripping it first is why a browser's random GREASE doesn't change its fingerprint, and why your forged Hello must place GREASE in browser-correct slots.

</Solution>

<Exercise n={3} title="JA4 sorted cipher hash" level="medium">

Write `JA4CipherHash(ciphers []uint16) string` that strips GREASE, formats each as 4-hex, **sorts**, joins with `,`, SHA-256s, and returns the first 12 hex chars. Prove that two shuffles of the same cipher set give the same hash (the property that beats cipher stunting).

<Solution>

```go
package main

import (
	"crypto/sha256"
	"encoding/hex"
	"fmt"
	"sort"
	"strings"
)

func isGREASE(v uint16) bool { return v&0x0f0f == 0x0a0a && byte(v>>8) == byte(v) }

func JA4CipherHash(ciphers []uint16) string {
	var toks []string
	for _, c := range ciphers {
		if !isGREASE(c) {
			toks = append(toks, fmt.Sprintf("%04x", c))
		}
	}
	sort.Strings(toks)
	sum := sha256.Sum256([]byte(strings.Join(toks, ",")))
	return hex.EncodeToString(sum[:])[:12]
}

func main() {
	a := []uint16{0x1301, 0x1302, 0x1303, 0xc02b, 0xc02f}
	b := []uint16{0xc02f, 0x1303, 0x1301, 0xc02b, 0x1302} // shuffled
	fmt.Println(JA4CipherHash(a))
	fmt.Println(JA4CipherHash(b))
	fmt.Println("equal:", JA4CipherHash(a) == JA4CipherHash(b))
}
```

The sort makes the hash depend on the *set*, not the *sequence* — so reordering (the trick that defeats JA3) does nothing to JA4.

</Solution>

</Exercise>

<Exercise n={4} title="Akamai HTTP/2 string" level="medium">

Write `AkamaiH2(settings [][2]uint32, windowUpdate uint32, pseudoOrder []string) string` that builds the fingerprint `SETTINGS|WINDOW_UPDATE|PRIORITY|pseudo`, where `settings` is a list of `{id,value}`, PRIORITY is `0`, and `pseudoOrder` is letters like `["m","a","s","p"]`. Produce Chrome's `1:65536;2:0;4:6291456;6:262144|15663105|0|m,a,s,p`.

<Solution>

```go
package main

import (
	"fmt"
	"strings"
)

func AkamaiH2(settings [][2]uint32, windowUpdate uint32, pseudoOrder []string) string {
	var s []string
	for _, kv := range settings {
		s = append(s, fmt.Sprintf("%d:%d", kv[0], kv[1]))
	}
	return strings.Join([]string{
		strings.Join(s, ";"),
		fmt.Sprintf("%d", windowUpdate),
		"0", // no standalone PRIORITY frames
		strings.Join(pseudoOrder, ","),
	}, "|")
}

func main() {
	fp := AkamaiH2(
		[][2]uint32{{1, 65536}, {2, 0}, {4, 6291456}, {6, 262144}},
		15663105,
		[]string{"m", "a", "s", "p"},
	)
	fmt.Println(fp)
	fmt.Println("matches Chrome:", fp == "1:65536;2:0;4:6291456;6:262144|15663105|0|m,a,s,p")
}
```

Four pipe-separated sections, the SETTINGS in send-order. Reproduce this *and* the TLS ClientHello and you match a browser at both fingerprint layers.

</Solution>

</Exercise>

<Exercise n={5} title="Detect a fingerprint mismatch" level="hard">

You're on the *defensive* side now. Write `Verdict(tlsJA3Browser, h2PseudoOrder string) string` that returns `"likely bot"` when the TLS fingerprint claims one browser but the HTTP/2 pseudo-header order doesn't match that browser's known order, and `"consistent"` otherwise. Use a small table: Chrome → `m,a,s,p`, Firefox → `m,p,a,s`. Test a Chrome-TLS client sending Go-like `m,a,s,p`-but-claiming-Firefox.

<Solution>

```go
package main

import "fmt"

// knownH2 maps a browser (as identified by its TLS fingerprint) to the
// HTTP/2 pseudo-header order it MUST also use. A mismatch means the two
// layers disagree — a classic impersonation tell.
var knownH2 = map[string]string{
	"chrome":  "m,a,s,p",
	"firefox": "m,p,a,s",
}

func Verdict(tlsBrowser, h2PseudoOrder string) string {
	want, ok := knownH2[tlsBrowser]
	if !ok {
		return "unknown browser"
	}
	if want != h2PseudoOrder {
		return "likely bot" // TLS says one browser, HTTP/2 says another
	}
	return "consistent"
}

func main() {
	// A real Chrome: TLS=chrome, H2 order=m,a,s,p → consistent.
	fmt.Println("real chrome:  ", Verdict("chrome", "m,a,s,p"))
	// A bot: forged Chrome TLS but its HTTP/2 layer orders like Chrome while
	// the request CLAIMS Firefox elsewhere — the layers contradict.
	fmt.Println("mismatched:   ", Verdict("firefox", "m,a,s,p"))
}
```

The defensive insight that pays for this whole chapter: you don't catch a good impersonator with any single fingerprint — you catch them with **inconsistency across layers**. A forged TLS that doesn't match the HTTP/2 setup, or a User-Agent that doesn't match the JA4, is the seam. Build your detection on cross-layer agreement, not one magic value.

</Solution>

</Exercise>

<Recap>

- **The tell is below your headers.** A server fingerprints your TLS **ClientHello** — sent in the clear, before any HTTP — so no `User-Agent` or header order can fix a fingerprint that says "Go". The handshake's first message betrays the library that built it.
- **JA3** joins five ClientHello fields (`version,ciphers,extensions,curves,formats`) with commas and hyphens and **MD5**s them. It captures the parameter *set and order*; **GREASE is stripped first** so a browser's random GREASE doesn't change its hash. You computed the canonical `ada70206…` yourself.
- **JA4** is the modern answer: a readable `a_b_c` form with **sorted**, **SHA-256** cipher and extension hashes. Sorting defeats the order-shuffling ("cipher stunting") that evaded JA3, so impersonation must now match a browser's true capability set.
- **Go's `crypto/tls` leaks** because its ClientHello is a fixed, GREASE-free, library-specific layout shared by every Go program and published in every anti-bot database. `tls.Config` tunes policy, not the ClientHello's bytes.
- **uTLS forges the ClientHello** — it substitutes a stored browser spec (via a `ClientHelloID`, a custom `ClientHelloSpec`, or a captured `Fingerprinter` spec) right before the real, audited `crypto/tls` handshake runs. You change the fingerprint, not the cryptography.
- **The HTTP/2 (Akamai) fingerprint** is a second layer: `SETTINGS|WINDOW_UPDATE|PRIORITY|pseudo-header-order`. Go's `net/http2` matches no browser, so a forged TLS with stock HTTP/2 is *more* suspicious — the two layers must agree.
- **`tls-client`** pairs uTLS with the `fhttp` fork and ships versioned **profiles** (`profiles.Chrome_133`) that bundle the TLS and HTTP/2 fingerprints, plus `HeaderOrderKey`/`PHeaderOrderKey`. **`surf`** wraps the same foundation in a fluent `Impersonate().Windows().Chrome()` builder with middleware, retries, and HTTP/3/JA4QUIC.
- **Defensively, the seam is inconsistency.** No single fingerprint catches a careful impersonator; **cross-layer disagreement** does — a TLS that claims Chrome but an HTTP/2 setup or header order that doesn't. Build detection on agreement across layers, not one magic value.

</Recap>
