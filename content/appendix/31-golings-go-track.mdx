<HeroCard label="Appendix · Practice" title="Golings: The Fix-It Track">

Here's the thing. You don't learn a language by reading about it — you learn it by *making broken code work* and feeling the compiler push back. That's the whole idea behind **rustlings**, the beloved Rust exercise series: a pile of tiny programs that *don't compile* (or compile but do the wrong thing), and your job is to fix each one until it passes. No projects, no setup, just **fix → run → green → next**.

This is that, for Go, **right here in the page**. Below is an ordered track of small broken programs — one concept each, from `variables` up through `channels`. You edit the code, hit **Run**, and it executes on the *real Go sandbox* — not a simulation. An exercise turns green only when your fix **compiles cleanly and prints the expected output**. Your progress is saved in the browser, so you can close the tab and pick up where you left off. Use the hint if you're stuck; read the one-line *why* when you pass. Do them in order — each is a reflex the rest of the Bible assumes you have. Now go make some red turn green.

</HeroCard>

<UnderTheHood title="What the Run button actually talks to (measured)">

Clicking **Run** does not execute Go in your browser. The page loads Codapi's `snippet.js` and each drill renders a `<codapi-snippet sandbox="go">`; the click POSTs your source to Codapi's public API at `api.codapi.org/v1/exec`, which builds and runs it inside a Docker-based sandbox and returns JSON (`ok`, `duration`, `stdout`, `stderr`).

I probed that endpoint directly instead of describing a sandbox from imagination. On the day of writing:

```text
runtime.Version()            go1.27.0
GOMAXPROCS / NumCPU          2 / 4
net.Dial("tcp","1.1.1.1:80")  connect: network is unreachable
os.WriteFile("/tmp/x", ...)   succeeds (writable scratch space)
hello world, end to end       ok, ~1.1 s (duration: 1077 ms)
for {} (infinite loop)        killed at 8003 ms: "code execution timeout"
allocate 16 MB chunks         killed ("Kill") after printing 464 MB
```

What that tells you as a learner:

- **The toolchain is real Go 1.27**, the same compiler the book targets, so output you see is what `go run` prints.
- **No network.** `net/http` calls to the outside world fail with "network is unreachable"; drills that need a server must start one in-process.
- **Two Ps, not one.** `GOMAXPROCS` is 2, so concurrent code can genuinely run in parallel. Do not rely on single-core scheduling to make a racy drill "deterministic".
- **Runs are not instant.** A trivial program takes about a second round trip (compile plus container start plus network), so keep drills small.
- **Hard limits exist.** An infinite loop is killed after 8 seconds and memory is capped (the process was killed a little under half a gigabyte). Any deadlock or runaway loop in a drill ends with a timeout, not a hang.

The runner only does `go run`. It does not run `go test`, `-race`, fuzzing or benchmarks, which is why drills here print `PASS`/`FAIL` from `main` and the check is the expected stdout. Details that Codapi does not publish, such as its exact cgroup, seccomp and filesystem settings, are deliberately not claimed here.

</UnderTheHood>

## Exercises

<Exercise n={1} title="Fix Slice Mutation in Functions" level="easy">

The function `AppendValue` below attempts to append an integer to a caller's slice, but because slice headers are passed by value, the caller's slice remains unchanged. Fix the function signature and implementation so the caller receives the updated slice.

<Solution>

```go
package main

import "fmt"

// Fix: Return the updated slice header from append.
func AppendValue(nums []int, val int) []int {
	return append(nums, val)
}

func main() {
	numbers := []int{1, 2, 3}
	numbers = AppendValue(numbers, 4)
	fmt.Println("Numbers:", numbers) // [1 2 3 4]
}
```

A Go slice is a 24-byte header `(Data *T, Len int, Cap int)` passed by value. Modifying `Len` or reallocating `Data` during an `append` requires returning the updated header to the caller.

</Solution>

</Exercise>

<Exercise n={2} title="Fix Struct Mutation with Pointer Receivers" level="medium">

The `Increment` method below is declared with a value receiver `(c Counter)`, meaning it operates on a copy of the struct and fails to mutate the original instance. Fix the method receiver so that calling `Increment` modifies the counter in place.

<Solution>

```go
package main

import "fmt"

type Counter struct {
	Value int
}

// Fix: Use a pointer receiver (*Counter) to mutate the caller's struct fields.
func (c *Counter) Increment() {
	c.Value++
}

func main() {
	c := &Counter{Value: 10}
	c.Increment()
	c.Increment()
	fmt.Println("Counter value:", c.Value) // 12
}
```

Methods that modify struct fields or methods on structs containing synchronization primitives (`sync.Mutex`) must use pointer receivers `*T` to avoid mutating a transient stack copy.

</Solution>

</Exercise>

<Exercise n={3} title="Fix Channel Deadlock in Producer-Consumer" level="hard">

The following code sends three messages to an unbuffered channel before starting the receiver loop, causing an immediate deadlock. Fix the coordination by using a buffered channel or launching a background producer goroutine.

<Solution>

```go
package main

import (
	"fmt"
	"sync"
)

func main() {
	// Fix: Launch producer in a goroutine and close channel when done
	ch := make(chan int)
	var wg sync.WaitGroup

	wg.Add(1)
	go func() {
		defer wg.Done()
		defer close(ch)
		for i := 1; i <= 3; i++ {
			ch <- i
		}
	}()

	// Consumer drains channel until closed
	for val := range ch {
		fmt.Println("Received:", val)
	}

	wg.Wait()
	fmt.Println("Processing complete")
}
```

Sending to an unbuffered channel blocks until a receiver is actively ready. Running the producer in a separate goroutine and closing the channel when production finishes allows the consumer's `for val := range ch` loop to terminate cleanly.

</Solution>

</Exercise>

## The Lab

Time to put your concurrency and memory reflexes to the test in a self-contained debugging challenge.

I've written a concurrent worker pool that processes tasks and aggregates sum results. However, it contains **two subtle bugs**: it fails to wait for all workers to finish before reading the results, and worker results are written to an unclosed channel, resulting in a deadlock. Fix the worker coordination so that all task results are collected and the program prints `ALL CHECKS PASS`.

<Lab
  title="Fix the Concurrency Worker Pool"
  archetype="fix-it"
  difficulty="guided"
  points={80}
  hintCost={15}
  verify="self-check"
  expect="ALL CHECKS PASS"
  objective="Fix two concurrency bugs in the worker pool: (1) Ensure all worker goroutines complete their work using sync.WaitGroup before closing the results channel. (2) Drain the results channel cleanly and verify the aggregated sum equals 550. When all workers finish and the sum matches, the program prints ALL CHECKS PASS."
  starter={`package main

import (
	"fmt"
	"sync"
)

func worker(id int, tasks <-chan int, results chan<- int, wg *sync.WaitGroup) {
	defer wg.Done()
	for t := range tasks {
		results <- t * 10
	}
}

func main() {
	tasks := make(chan int, 10)
	results := make(chan int, 10)
	var wg sync.WaitGroup

	numWorkers := 3
	for i := 1; i <= numWorkers; i++ {
		wg.Add(1)
		go worker(i, tasks, results, &wg)
	}

	// Send 10 tasks (values 1..10, sum of t*10 = 550)
	for i := 1; i <= 10; i++ {
		tasks <- i
	}
	close(tasks)

	// BUG: nothing ever closes results, so the range loop below never ends
	// (once every worker has finished, main waits forever for an 11th result).
	// Close results once every worker is done, without blocking main.

	total := 0
	for res := range results {
		total += res
	}

	if total == 550 {
		fmt.Println("ALL CHECKS PASS")
	} else {
		fmt.Printf("FAIL: expected 550, got %d\\n", total)
	}
}`}
  verifier="main distributes 10 tasks across 3 worker goroutines, closes the tasks channel, waits for all workers to finish in a separate closer goroutine, and accumulates the total sum. The flag unlocks when the program runs cleanly and prints ALL CHECKS PASS."
  hints={[
    "Workers finish when the tasks channel is closed and drained.",
    "Launch a background goroutine to wg.Wait() and then close(results) so the main thread can range over results without deadlocking.",
    "The sum of (1..10) * 10 is 55 * 10 = 550.",
  ]}
  flag="GO{concurrency_patterns_mastered_in_sandboxes}"
>

Coordinate the worker pool with `sync.WaitGroup`, close the input and output channels properly, and drain the accumulated results without deadlocking the runtime scheduler.

</Lab>

<Recap>

- **Drills build reflexes:** Reading syntax rules is necessary, but true fluency comes from diagnosing compiler errors, type mismatches, and channel deadlocks in real code.
- **Value vs. pointer semantics:** Slices, maps, and channels are descriptors/headers passed by value. Modifying backing data requires understanding when a pointer receiver or returned slice header is required.
- **Sandbox facts (measured):** real Go 1.27, no network, 2 Ps, about a second per run, an 8-second timeout and a memory cap. It runs `go run` only, so drills self-check by printing `PASS`.
- **Structured concurrency:** Always define the lifecycle of goroutines and channels — use `sync.WaitGroup` to coordinate worker completion and close channels from the producer side.

</Recap>
