Here's the thing, sport. You don't learn a language by reading about it — you learn it by *making broken code work* and feeling the compiler push back. That's the whole idea behind **rustlings**, the beloved Rust exercise series: a pile of tiny programs that *don't compile* (or compile but do the wrong thing), and your job is to fix each one until it passes. No projects, no setup, just **fix → run → green → next**.

This is that, for Go, **right here in the page**. Below is an ordered track of small broken programs — one concept each, from `variables` up through `channels`. You edit the code, hit **Run**, and it executes on the *real Go sandbox* — not a simulation. An exercise turns green only when your fix **compiles cleanly and prints the expected output**. Your progress is saved in the browser, so you can close the tab and pick up where you left off. Use the hint if you're stuck; read the one-line *why* when you pass. Do them in order — each is a reflex the rest of the Bible assumes you have. Now go make some red turn green, sport.

<UnderTheHood title="Codapi Runner & In-Browser Go Sandbox Internals">

When you click **Run** in any interactive playground or Golings drill, your browser does not execute a client-side WebAssembly emulator. Instead, it dispatches an asynchronous HTTP request to an isolated, ephemeral backend container runner (Codapi / Go Playground architecture).

### 1. Ephemeral Container Isolation & Linux Cgroups

To run untrusted user-submitted Go code safely and instantly, sandbox runners employ a hardened execution environment:

- **Linux Cgroups v2 Resource Constraints:** Every execution is isolated within a lightweight container bounded by strict kernel cgroups — typically capped at `cpu.max = 100000 100000` (1 vCPU core), `memory.max = 64MB`, and `pids.max = 64` to prevent fork bombs and memory exhaustion.
- **Seccomp Syscall Filtering:** The runner drops Linux capabilities (`CAP_NET_RAW`, `CAP_SYS_ADMIN`) and restricts syscalls via a custom BPF filter. Raw socket creation (`AF_INET`, `AF_PACKET`) and arbitrary disk I/O are blocked; file writes are restricted to an ephemeral, in-memory `tmpfs` volume that is wiped upon process exit.
- **Strict Execution Timeouts:** A hard timeout (usually 3.0 to 5.0 seconds) is enforced at the kernel level via `SIGKILL` if code encounters an infinite loop or deadlock.

### 2. Fast Compilation Semantics & Pre-Warmed Toolchains

Compiling Go code in sub-100ms response windows requires bypassing standard `go build` cold-start penalties:

- **Pre-Compiled Standard Library Cache:** The standard library (`fmt`, `net/http`, `sync`, `os`, `crypto/...`) is pre-compiled into Go's build cache (`GOCACHE` and `pkg/linux_amd64`). When the runner compiles `main.go`, the compiler only tokenizes and generates machine code for your single file, linking against the pre-warmed archive objects (`.a` files).
- **In-Memory Compilation:** The source file is written directly to a tmpfs RAM disk (`/tmp/sandbox/main.go`), eliminating disk controller latency. The compiler emits an in-memory ELF executable that is directly invoked with `syscall.Exec`.

### 3. Runtime Determinism & Output Capture (Go 1.22+)

- **Buffered Standard Stream Interleaving:** Output from `os.Stdout` and `os.Stderr` is buffered through non-blocking Linux pipes. The runner captures stdout and stderr concurrently, returning a unified JSON payload containing the exit code, execution duration, and combined output string.
- **Deterministic Scheduling:** Under sandboxed single-core execution (`GOMAXPROCS=1`), goroutine preemption occurs primarily at function prologues and runtime scheduler checkpoints, making concurrent test assertions reliable and deterministic.

</UnderTheHood>

## Exercises

<Exercise n={1} title="Fix Slice Mutation in Functions" level="easy">

The function `AppendValue` below attempts to append an integer to a caller's slice, but because slice headers are passed by value, the caller's slice remains unchanged. Fix the function signature and implementation so the caller receives the updated slice.

<Solution>

```go
package main

import "fmt"

// Fix: Return the updated slice header from append.
func AppendValue(nums []int, val int) []int {
	return append(nums, val)
}

func main() {
	numbers := []int{1, 2, 3}
	numbers = AppendValue(numbers, 4)
	fmt.Println("Numbers:", numbers) // [1 2 3 4]
}
```

A Go slice is a 24-byte header `(Data *T, Len int, Cap int)` passed by value. Modifying `Len` or reallocating `Data` during an `append` requires returning the updated header to the caller.

</Solution>

</Exercise>

<Exercise n={2} title="Fix Struct Mutation with Pointer Receivers" level="medium">

The `Increment` method below is declared with a value receiver `(c Counter)`, meaning it operates on a copy of the struct and fails to mutate the original instance. Fix the method receiver so that calling `Increment` modifies the counter in place.

<Solution>

```go
package main

import "fmt"

type Counter struct {
	Value int
}

// Fix: Use a pointer receiver (*Counter) to mutate the caller's struct fields.
func (c *Counter) Increment() {
	c.Value++
}

func main() {
	c := &Counter{Value: 10}
	c.Increment()
	c.Increment()
	fmt.Println("Counter value:", c.Value) // 12
}
```

Methods that modify struct fields or methods on structs containing synchronization primitives (`sync.Mutex`) must use pointer receivers `*T` to avoid mutating a transient stack copy.

</Solution>

</Exercise>

<Exercise n={3} title="Fix Channel Deadlock in Producer-Consumer" level="hard">

The following code sends three messages to an unbuffered channel before starting the receiver loop, causing an immediate deadlock. Fix the coordination by using a buffered channel or launching a background producer goroutine.

<Solution>

```go
package main

import (
	"fmt"
	"sync"
)

func main() {
	// Fix: Launch producer in a goroutine and close channel when done
	ch := make(chan int)
	var wg sync.WaitGroup

	wg.Add(1)
	go func() {
		defer wg.Done()
		defer close(ch)
		for i := 1; i <= 3; i++ {
			ch <- i
		}
	}()

	// Consumer drains channel until closed
	for val := range ch {
		fmt.Println("Received:", val)
	}

	wg.Wait()
	fmt.Println("Processing complete")
}
```

Sending to an unbuffered channel blocks until a receiver is actively ready. Running the producer in a separate goroutine and closing the channel when production finishes allows the consumer's `for val := range ch` loop to terminate cleanly.

</Solution>

</Exercise>

<Recap>

- **Drills build reflexes:** Reading syntax rules is necessary, but true fluency comes from diagnosing compiler errors, type mismatches, and channel deadlocks in real code.
- **Value vs. pointer semantics:** Slices, maps, and channels are descriptors/headers passed by value. Modifying backing data requires understanding when a pointer receiver or returned slice header is required.
- **Sandbox isolation:** Sandboxed code runs inside cgroup-constrained Linux containers with seccomp filtering, pre-warmed compiler caches, and sub-100ms execution times.
- **Structured concurrency:** Always define the lifecycle of goroutines and channels — use `sync.WaitGroup` to coordinate worker completion and close channels from the producer side.

</Recap>
