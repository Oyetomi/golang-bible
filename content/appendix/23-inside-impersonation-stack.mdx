## The TLSExtension Interface

Everything in uTLS hangs off one small interface. A ClientHello is a list of **extensions**, and every extension type — SNI, ALPN, supported_curves, key_share, the GREASE placeholder — implements the same contract. Get this interface and the entire library unfolds from it.

<Define term="TLSExtension (uTLS)">
In uTLS, a **`TLSExtension`** is any type that can (a) report its serialized byte length, (b) write its serialized bytes into a buffer, and (c) apply its values into the connection's handshake state. The first two come from implementing `io.Reader`-style methods — `Len() int` and `Read([]byte) (int, error)` — so an extension can be *read out* as bytes. The third, `writeToUConn(*UConn) error`, lets the extension push its data (e.g. the curve list) into the `Hello` struct that crypto/tls will use. A `ClientHelloSpec` is just an ordered `[]TLSExtension` plus a cipher list — so the ClientHello's byte layout is literally the concatenation of each extension reading itself out, in order.
</Define>

Here is the real interface from uTLS, and a faithful stdlib mirror you can build against:

```go
// From refraction-networking/utls (u_tls_extensions.go), the contract every
// extension implements. Len + Read make an extension serialize itself to bytes;
// writeToUConn pushes its values into the handshake state.
type TLSExtension interface {
	writeToUConn(*UConn) error
	Len() int
	Read([]byte) (int, error) // io.Reader: fill b with the extension's wire bytes
}
```

<Callout kind="note" title="Why Read, of all methods?">
Making an extension an `io.Reader` is the elegant trick. To marshal the whole ClientHello, uTLS doesn't need a giant switch over extension types — it just calls `Read` on each one in order and concatenates. A `bufio`-style writer `ReadFrom`s each extension straight into the message buffer. Adding a brand-new extension means writing one type with `Len`/`Read`/`writeToUConn` — no change to the marshaller. That's the Go idiom from the **Design Patterns** chapter (small interfaces, composition) doing real work in production security code.
</Callout>

## Serializing an Extension

Now the concrete payoff: how a `[]CurveID` becomes the exact bytes of the `supported_curves` extension. This is the real uTLS `SupportedCurvesExtension`, and it is small enough to understand completely.

```go
// From refraction-networking/utls — the REAL SupportedCurvesExtension.
type SupportedCurvesExtension struct {
	Curves []CurveID // e.g. {GREASE, X25519, CurveP256, CurveP384}
}

// Len: a 6-byte header (ext type 2 + ext len 2 + list len 2) plus 2 bytes/curve.
func (e *SupportedCurvesExtension) Len() int {
	return 6 + 2*len(e.Curves)
}

// Read serializes the extension into b, big-endian, and returns io.EOF when done.
func (e *SupportedCurvesExtension) Read(b []byte) (int, error) {
	if len(b) < e.Len() {
		return 0, io.ErrShortBuffer
	}
	// bytes 0-1: extension TYPE (supported_curves = 0x000a)
	b[0] = byte(extensionSupportedCurves >> 8)
	b[1] = byte(extensionSupportedCurves)
	// bytes 2-3: extension LENGTH (everything after this field)
	b[2] = byte((2 + 2*len(e.Curves)) >> 8)
	b[3] = byte(2 + 2*len(e.Curves))
	// bytes 4-5: the curve LIST length
	b[4] = byte((2 * len(e.Curves)) >> 8)
	b[5] = byte(2 * len(e.Curves))
	// then each curve as a big-endian uint16
	for i, curve := range e.Curves {
		b[6+2*i] = byte(curve >> 8)
		b[7+2*i] = byte(curve)
	}
	return e.Len(), io.EOF
}

// writeToUConn pushes the curves into the handshake state crypto/tls reads.
func (e *SupportedCurvesExtension) writeToUConn(uc *UConn) error {
	uc.config.CurvePreferences = e.Curves
	uc.HandshakeState.Hello.SupportedCurves = e.Curves
	return nil
}
```

## GREASE in the Source

The most important thing to internalize about GREASE: it is **not special**. To the serializer, a GREASE extension is an ordinary extension that happens to carry a reserved random type value. Here is the real uTLS `UtlsGREASEExtension`:

```go
// From refraction-networking/utls — GREASE serializes EXACTLY like any extension.
type UtlsGREASEExtension struct {
	Value uint16 // a reserved GREASE type, e.g. 0x?a?a
	Body  []byte // usually empty
}

func (e *UtlsGREASEExtension) Read(b []byte) (int, error) {
	if len(b) < e.Len() {
		return 0, io.ErrShortBuffer
	}
	b[0] = byte(e.Value >> 8) // 2-byte type — same slot as any extension
	b[1] = byte(e.Value)
	b[2] = byte(len(e.Body) >> 8) // 2-byte length
	b[3] = byte(len(e.Body))
	if len(e.Body) > 0 {
		copy(b[4:], e.Body)
	}
	return e.Len(), io.EOF
}
```

<Callout kind="pro" title="Why GREASE looks like a real extension on purpose">
GREASE (RFC 8701) exists so servers *can't* ossify on a fixed extension set — browsers send unknown, reserved values that a correct server must ignore. For that to work, a GREASE extension has to be **indistinguishable in structure** from a real one: same 2-byte-type, 2-byte-length framing. That's exactly what the code shows — `UtlsGREASEExtension.Read` writes the identical layout as `SupportedCurvesExtension.Read`. This is also why faking Chrome means *including* GREASE in the right slots: a real Chrome ClientHello has GREASE extensions interleaved, and a fingerprinter that strips GREASE before hashing expects to find it there to strip. Omit it and your spec doesn't match Chrome's structure even after the strip.
</Callout>

The GREASE *value* itself is generated at runtime — uTLS picks one of the 16 reserved values per connection (via a function like `GetBoringGREASEValue`), so the placeholder `GREASE_PLACEHOLDER` you'll see in the spec is replaced with a concrete `0x?a?a` when the Hello is built. The JA3/JA4 fingerprinter then strips it back out, so the *fingerprint* is stable even though the *bytes* vary per connection — exactly the design goal.

<Gotcha>
**This is why you can't hand-roll Chrome from `crypto/tls`.** Look at that list: GREASE bookends, ALPS, compress_certificate, a speculative GREASE'd key share, GREASE'd ECH, computed padding — `crypto/tls` emits *none* of these and exposes no API to add them. Matching Chrome means emitting this exact ordered set with the right GREASE slots — which is the entire reason uTLS maintains a hand-built spec per browser version, updated as Chrome ships changes. The spec *is* the fingerprint, in source form.

```go
package main

import (
	"fmt"
	"io"
)

// The extension contract — Len + Read, exactly uTLS's TLSExtension (minus
// writeToUConn, which we don't need just to marshal bytes).
type Ext interface {
	Len() int
	Read([]byte) (int, error)
}

type GREASE struct{ Value uint16 }

func (e *GREASE) Len() int { return 4 }
func (e *GREASE) Read(b []byte) (int, error) {
	b[0], b[1], b[2], b[3] = byte(e.Value>>8), byte(e.Value), 0, 0
	return 4, io.EOF
}

type Curves struct{ IDs []uint16 }

func (e *Curves) Len() int { return 6 + 2*len(e.IDs) }
func (e *Curves) Read(b []byte) (int, error) {
	b[0], b[1] = 0x00, 0x0a // supported_curves
	b[2], b[3] = byte((2+2*len(e.IDs))>>8), byte(2+2*len(e.IDs))
	b[4], b[5] = byte((2*len(e.IDs))>>8), byte(2*len(e.IDs))
	for i, id := range e.IDs {
		b[6+2*i], b[7+2*i] = byte(id>>8), byte(id)
	}
	return e.Len(), io.EOF
}

type ALPN struct{ Protos []string }

func (e *ALPN) Len() int {
	n := 7 // type(2)+extlen(2)+listlen(2)+... actually: 2+2+2 header, then 1 len byte per proto
	for _, p := range e.Protos {
		n += 1 + len(p)
	}
	return n
}
func (e *ALPN) Read(b []byte) (int, error) {
	var list []byte
	for _, p := range e.Protos {
		list = append(list, byte(len(p)))
		list = append(list, p...)
	}
	b[0], b[1] = 0x00, 0x10 // application_layer_protocol_negotiation
	b[2], b[3] = byte((2+len(list))>>8), byte(2+len(list))
	b[4], b[5] = byte(len(list)>>8), byte(len(list))
	copy(b[6:], list)
	return e.Len(), io.EOF
}

// marshalBody builds the cipher block + extensions block of a ClientHello.
func marshalBody(ciphers []uint16, exts []Ext) []byte {
	extLen := 0
	for _, e := range exts {
		extLen += e.Len()
	}
	var out []byte
	// cipher suites: 2-byte length, then each suite big-endian
	out = append(out, byte((2*len(ciphers))>>8), byte(2*len(ciphers)))
	for _, c := range ciphers {
		out = append(out, byte(c>>8), byte(c))
	}
	// extensions: 2-byte total length, then each extension's bytes
	out = append(out, byte(extLen>>8), byte(extLen))
	for _, e := range exts {
		buf := make([]byte, e.Len())
		e.Read(buf)
		out = append(out, buf...)
	}
	return out
}

func main() {
	body := marshalBody(
		[]uint16{0x1301, 0x1302}, // TLS_AES_128_GCM, TLS_AES_256_GCM
		[]Ext{
			&GREASE{Value: 0x3a3a},
			&Curves{IDs: []uint16{0x3a3a, 0x001d, 0x0017, 0x0018}},
			&ALPN{Protos: []string{"h2", "http/1.1"}},
		},
	)
	fmt.Printf("ClientHello body (% x)\n", body)
	fmt.Printf("(%d bytes: 2-len cipher block, then 2-len extensions block)\n", len(body))
}
```

## ShuffleChromeTLSExtensions

You may have noticed the spec wraps its extensions in `ShuffleChromeTLSExtensions(...)`. Modern Chrome **randomizes the order of most of its extensions per connection** — its own anti-ossification move, the extension-level cousin of GREASE. uTLS mirrors it.

<Callout kind="note" title="What shuffles, what stays put">
`ShuffleChromeTLSExtensions` permutes the *middle* of the extension list but holds certain positions fixed: the **leading GREASE** stays first, the **padding extension stays last** (its length is computed from everything before it, so it can't move), and **pre-shared-key** (when present) must be last per the TLS spec. Everything between is shuffled. The defensive consequence is large: **extension *order* is no longer a reliable Chrome signal** — which is precisely why JA4 sorts extensions before hashing (last chapter). A detector keying on a fixed Chrome extension order will false-positive on real Chrome; a detector keying on the sorted *set* (JA4) won't. The library and the fingerprint format co-evolved against each other.
</Callout>

This is the deepest reason the JA3→JA4 shift happened, seen from the source side: the browser itself started shuffling, so an order-sensitive fingerprint (JA3) became unstable for the *real* browser, and a set-based one (JA4) became necessary for both detection and impersonation.

```go
func (im *Impersonate) applyVariant(v profiles.Variant) *Builder {
	im.builder.headersApplier = v.Headers
	im.builder.Boundary(v.Boundary)

	if v.HelloSpec != nil {

	v.ConfigureH3(h3adapter{h3}) // QUIC / HTTP/3 fingerprint
	h3.Set()

	return im.builder.SetHeaders(*v.BuildHeaders(im.os)) // headers, ordered, per OS
```

<Exercise n={1} title="Implement an extension's Read" level="medium">

Implement `SupportedPointsExtension` (the `ec_point_formats` extension, type `0x000b`): a struct holding `Formats []byte`, a `Len()` returning `5 + len(Formats)` (2-byte type, 2-byte ext length, 1-byte list length, then the formats), and a `Read([]byte)` that serializes it. For Chrome's `Formats: []byte{0x00}` (uncompressed), the bytes should be `00 0b 00 02 01 00`.

<Solution>

```go
package main

import (
	"fmt"
	"io"
)

const extPointFormats = 0x000b

type SupportedPointsExtension struct{ Formats []byte }

func (e *SupportedPointsExtension) Len() int { return 5 + len(e.Formats) }

func (e *SupportedPointsExtension) Read(b []byte) (int, error) {
	if len(b) < e.Len() {
		return 0, io.ErrShortBuffer
	}
	b[0] = byte(extPointFormats >> 8)
	b[1] = byte(extPointFormats)
	b[2] = byte((1 + len(e.Formats)) >> 8) // ext length = 1 (list-len byte) + formats
	b[3] = byte(1 + len(e.Formats))
	b[4] = byte(len(e.Formats)) // 1-byte list length (note: not 2 bytes here)
	copy(b[5:], e.Formats)
	return e.Len(), io.EOF
}

func main() {
	e := &SupportedPointsExtension{Formats: []byte{0x00}}
	buf := make([]byte, e.Len())
	e.Read(buf)
	fmt.Printf("ec_point_formats (% x)\n", buf)
	fmt.Println("matches Chrome:", fmt.Sprintf("% x", buf) == "00 0b 00 02 01 00")
}
```

Note the asymmetry from supported_curves: `ec_point_formats` uses a **1-byte** list-length, not 2. The TLS spec varies the length-prefix width per extension — reading the real uTLS source is how you learn each one's exact framing.

</Solution>

</Exercise>

<Exercise n={3} title="The GREASE extension" level="easy">

Implement `GREASEExt{ Value uint16 }` with `Len()` = 4 (2-byte type, 2-byte length, empty body) and a `Read` that writes the value as the type and a zero length. Show it serializes to `3a 3a 00 00` for value `0x3a3a` — structurally identical to any real extension.

<Solution>

```go
package main

import (
	"fmt"
	"io"
)

type GREASEExt struct{ Value uint16 }

func (e *GREASEExt) Len() int { return 4 }
func (e *GREASEExt) Read(b []byte) (int, error) {
	if len(b) < 4 {

	b[0], b[1] = byte(e.Value>>8), byte(e.Value) // type slot carries the GREASE value
	b[2], b[3] = 0, 0                            // zero-length body
```

<Exercise n={4} title="Marshal a ClientHello body" level="hard">

Combine the pieces: write `marshal(ciphers []uint16, exts []Ext)` (where `Ext` has `Len()` and `Read([]byte)`) that emits the cipher block (2-byte length + suites) followed by the extensions block (2-byte total length + each extension's bytes). Feed it two ciphers and a GREASE + curves extension and print the hex.

<Solution>

```go
package main

import (
	"fmt"
	"io"
)

type Ext interface {
	Len() int
	Read([]byte) (int, error)
}

type GREASE struct{ V uint16 }

func (e *GREASE) Len() int                 { return 4 }
func (e *GREASE) Read(b []byte) (int, error) { b[0], b[1] = byte(e.V>>8), byte(e.V); return 4, io.EOF }

type Curves struct{ IDs []uint16 }

func (e *Curves) Len() int { return 6 + 2*len(e.IDs) }
func (e *Curves) Read(b []byte) (int, error) {
	b[0], b[1] = 0x00, 0x0a
	b[2], b[3] = byte((2+2*len(e.IDs))>>8), byte(2+2*len(e.IDs))
	b[4], b[5] = byte((2*len(e.IDs))>>8), byte(2*len(e.IDs))
	for i, id := range e.IDs {
		b[6+2*i], b[7+2*i] = byte(id>>8), byte(id)
	}
	return e.Len(), io.EOF
}

func marshal(ciphers []uint16, exts []Ext) []byte {
	total := 0
	for _, e := range exts {
		total += e.Len()
	}
	out := []byte{byte((2 * len(ciphers)) >> 8), byte(2 * len(ciphers))}
	for _, c := range ciphers {
		out = append(out, byte(c>>8), byte(c))
	}
	out = append(out, byte(total>>8), byte(total))
	for _, e := range exts {
		buf := make([]byte, e.Len())
		e.Read(buf)
		out = append(out, buf...)
	}
	return out
}

func main() {
	body := marshal([]uint16{0x1301, 0x1302},
		[]Ext{&GREASE{0x3a3a}, &Curves{[]uint16{0x3a3a, 0x001d, 0x0017, 0x0018}}})
	fmt.Printf("ClientHello body (% x)\n", body)
}
```

You've now written, in stdlib, the core of what uTLS's `MarshalClientHello` does: size by `Len()`, serialize by `Read()`, cipher block then extensions block. The bytes you print are a real ClientHello body.

</Solution>

</Exercise>

<Recap>

- **One small interface drives everything.** A uTLS `TLSExtension` has `Len()`, `Read([]byte)`, and `writeToUConn(*UConn)`. `Len`+`Read` serialize the extension to wire bytes (it's an `io.Reader`); `writeToUConn` pushes its values into the handshake state. A `ClientHelloSpec` is an ordered `[]TLSExtension` plus a cipher list — so the ClientHello's bytes are just each extension reading itself out, in order.
- **You can serialize an extension by hand.** `SupportedCurvesExtension.Read` writes the nested-length TLS framing (type, ext-length, list-length) then each curve big-endian — your stdlib version emits the identical `00 0a 00 0a 00 08 …` bytes uTLS sends.
- **GREASE is structurally a normal extension** — same type/length framing — by design (RFC 8701), so servers ignore it and fingerprinters strip it; an impersonator must include it in the browser's slots. The value is randomized per connection but stripped before hashing, so the fingerprint stays stable.
- **Chrome's real `ClientHelloSpec`** is a hand-built ordered list: GREASE bookends, SNI, supported_curves (GREASE+X25519+P256+P384), ALPN (`h2`,`http/1.1`), a speculative GREASE'd key share, supported_versions (GREASE+1.3+1.2), Brotli cert-compression, ALPS, GREASE'd ECH, and computed padding — none of which `crypto/tls` can emit, which is why uTLS maintains the spec per version.
- **The build pipeline is four steps:** `buildHandshakeState` → `applyPresetByID` (load the spec) → `ApplyConfig` (`writeToUConn` each extension into `Hello`) → `MarshalClientHello` (sum `Len()`, `Read()` each into the buffer; padding last). The bytes land in `hello.Raw` and go out unchanged.
- **`ShuffleChromeTLSExtensions`** randomizes the *middle* of Chrome's extension order per connection (GREASE first, padding/PSK last stay fixed) — Chrome's own anti-ossification, and the deepest reason JA4 sorts before hashing.
- **`tls-client`'s `ClientProfile`** bundles the uTLS `ClientHelloID` (TLS fingerprint) with the HTTP/2 `settings`, `settingsOrder`, `connectionFlow`, `pseudoHeaderOrder`, and `priorities` (Akamai fingerprint) in one struct — so picking `profiles.Chrome_133` gives a consistent identity at both layers. **`surf`'s `applyVariant`** does the same job through a fluent builder: OS persona → Variant → set HelloSpec/HelloID + ConfigureH2/H3 + ordered headers.
- **Anywhere order is fingerprinted, the source carries an explicit order slice** (`settingsOrder`, ordered header maps) because Go's native map can't preserve it — a recurring tell when you read this kind of code.

</Recap>
