## Path Traversal / LFI

**Corpus frequency: ~652 reports (the *information-disclosure* class it feeds).** A *limited* read primitive is not low-severity — it chains. A `filename` param confined to one directory (with `/etc/passwd` blocked) is still traversal: `../` walks to a sibling config (`/WEB-INF/web.xml`), which names a hidden endpoint, whose real-time logs leak admin credentials, which unlock an authenticated Groovy console — **LFI escalated to RCE**, its output exfiltrated back through the very same log sink. The Go defenses are already in your kit: confine every user-named read with **`os.Root`** (Go 1.24) *and scope the root tightly* — root the receipts directory, not the whole app, or siblings like `WEB-INF` stay reachable; keep secrets **out of logs**; and treat any report/log endpoint that reflects input or command output as an exfiltration channel. Taught in the **application-security-baseline** chapter.

## CVE Highlights: VDP Disclosures, Mapped to Go Defenses

The bounty tables above are *programs paying hunters*. A **VDP** (Vulnerability Disclosure Program) is the sibling: a "see something, say something" channel with **no bounty**, where researchers report and the vendor publishes a **CVE**. The reports skew toward *deployed software* — the monitoring and security tooling that sits in everyone's infrastructure — which makes them a goldmine of *infrastructure-class* patterns you rarely see in web-app bounty writeups: cluster-protocol trust, file-write-to-RCE, secret exposure, and resource-exhaustion DoS.

Here's a recent VDP digest across three widely-deployed tools — Nagios Log Server, Wazuh, MISP — with each CVE mapped to the **class** this track teaches and the **Go-side defense** that prevents the same shape in code you write. (These are *security and monitoring* products — the watchers getting watched — which is exactly why their bugs are so instructive: a flaw in the thing that's supposed to detect flaws has outsized blast radius.)

| CVE (severity) | Class | Mechanism | Go-side defense → chapter |
|---|---|---|---|
| **CVE-2025-29471** (8.3 High) | Stored XSS → privesc | Nagios Log Server: a stored script runs when a *higher-privilege* admin opens the log view — authenticated XSS escalates by waiting for a better viewer. | Escape by context with `html/template` (auto-escapes; never `text/template` for HTML), and ship `Content-Security-Policy: default-src 'self'` so an injected `<script>` can't run at all. → **application-security-baseline**, **http-response-headers** |
| **CVE-2025-44824** (8.5 High) | Broken access control (BFLA) | Nagios Log Server: a function-level authorization check is missing or wrong — being *authenticated* was mistaken for being *authorized*. | Authorize the **actor's role** on every handler, not just authentication; centralize the check in middleware; deny by default. → **broken-access-control** |
| **CVE-2025-44823** (9.9 Critical) | Info disclosure / secret exposure | Nagios Log Server: API keys are returned to lower-privilege authenticated users — secrets serialized straight into a response. | Never put secrets in a response body; keep keys server-side and scope visibility by role. Same rule as the response-envelope chapter — **no tokens in the body**. → **http-response-headers** |
| **CVE-2026-25769** (9.1 Critical) | RCE over cluster protocol | Wazuh 4.14.3 cluster mode: an authenticated node-to-node message reaches a code-execution path — the inter-node channel was trusted. | Treat **inter-node traffic as a trust boundary**: authenticate peers (mTLS), validate every message, and never decode untrusted peer data into executable behavior. → **owasp-bug-hunters-field-guide** |
| **CVE-2026-25770** (9.1 Critical) | Arbitrary file write → privesc | Wazuh 4.14.3: the cluster protocol writes a file at an attacker-influenced path — a network-driven write becomes code execution. | Never join network input into a filesystem path; confine writes with `os.Root`/`os.OpenRoot` (Go 1.24+) and reject `..` / absolute paths. → **application-security-baseline** (path traversal) |
| **CVE-2026-25771** (7.5 High) | Unauthenticated DoS | Wazuh 4.14.3 API: an unauthenticated request exhausts server resources. | Bound every unauthenticated endpoint: `http.MaxBytesReader` on bodies, read/write timeouts on the `http.Server`, rate-limit, cap concurrency. → **reliability-patterns** |
| **CVE-2026-9136** (8.3 High) | IDOR (bulk import) | MISP 2.5.37: shadow-attribute *batch* import checks the request actor once but not ownership of **each object** in the batch. | Validate ownership of **every element** in a batch, not the caller a single time — the per-object check is the whole fix. Batch endpoints are an IDOR multiplier. → **broken-access-control** |
| **CVE-2026-9137** (7.5 High) | Unauthenticated DoS (report sink) | MISP 2.5.37: the **CSP violation-report** endpoint parses attacker JSON without limits — the reporting channel is itself attack surface. | The CSP `report-uri`/`report-to` sink is unauthenticated: wrap it in `http.MaxBytesReader`, decode strictly (`Decoder.DisallowUnknownFields`), validate the report shape, and rate-limit. → **http-response-headers** (CSP) |

The throughline: **every one of these maps to a class you already know** — XSS, broken access control, info disclosure, injection/RCE, path traversal, IDOR, DoS — just wearing infrastructure clothes. A cluster protocol is still untrusted input; a batch import is still per-object authorization; a report endpoint is still a body you must bound. Learn the shape once and you recognize it whether it's a login form or a node-to-node heartbeat.

## Exploitation Chains: From Primitive to Impact

Disclosed reports highlight that high-payout vulnerabilities are rarely single isolated bugs. They are **exploit chains** that link low-severity primitives into full system compromise.

<UnderTheHood title="Exploitation Mechanics & State Reconstruction">

Analyzing 6,400+ disclosed security writeups reveals fundamental engineering truths about how systems fail and how Go's design influences vulnerability lifecycles.

### 1. The Vulnerability Chaining Graph
In real-world security assessments, critical vulnerabilities almost never manifest as a single, textbook exploit. Instead, attackers model targets as directed state graphs:

```
[S0: Recon & Discovery] 
       ↓ (Find forgotten endpoint)
[S1: Attack Surface] 
       ↓ (Path traversal / log read)
[S2: Credential / Config Leak] 
       ↓ (State-skip / batch IDOR)
[S3: Elevated Privileges] 
       ↓ (Insecure cluster protocol)
[S4: Full Remote Code Execution]
```

Each intermediate finding escalates the attacker's authorization level or expands their available execution primitives. A "low severity" path traversal that only leaks `.env` or `config.json` becomes critical the moment that config contains an encryption key, database password, or inter-service cluster token.

### 2. Memory Safety vs. Logic & State Invariants in Go
Go is a memory-safe language: unless code imports `unsafe` or calls into Cgo, buffer overflows, use-after-free (UAF), and dangling pointer exploits are eliminated by the compiler and runtime GC.

Consequently, **95%+ of vulnerabilities in Go-based backends fall into state and semantic failures**:
- **Business Logic Flaws:** State machines that permit invalid transitions (e.g. going from `Created` $\to$ `Fulfilled` without passing through `Paid`).
- **Authorization Gaps (BFLA/IDOR):** Handlers that verify that a JWT token is valid (Authentication), but fail to assert that `token.Subject == resource.OwnerID` (Object-Level Authorization).
- **Concurrency TOCTOU:** In-memory check-then-act operations that yield during database I/O, allowing concurrent goroutines to overrun limits.

### 3. Parser Differentials & Grammar Discrepancies
When two components in a microservice pipeline parse the same payload using slightly different RFC interpretations, a **parser differential** vulnerability emerges.

#### The Duplicate Key JSON Flaw
Consider a request evaluated by a WAF/proxy and then processed by a Go backend:
```json
{"role": "user", "role": "admin"}
```
- A WAF written in Python/C might validate the *first* key (`role: user`) and allow the request through.
- Go's standard library `encoding/json.Unmarshal` iterates through keys in sequence and **overwrites** earlier values with later values, ending with `role: admin`.
- **Defense:** In security-critical paths (e.g. permission or role assignments), use `json.NewDecoder` with token-by-token validation to reject duplicate keys explicitly before unmarshaling.

### 4. Deterministic State Machines in Go
To eradicate skip-step and business logic vulnerabilities, model stateful workflows using explicit, closed transition tables rather than ad-hoc boolean flags in HTTP handlers:

```go
type State int
const (
    StateDraft State = iota
    StatePendingPayment
    StatePaid
    StateDispatched
)

type TransitionTable map[State]map[State]bool

var orderFSM = TransitionTable{
    StateDraft:          {StatePendingPayment: true},
    StatePendingPayment: {StatePaid: true},
    StatePaid:           {StateDispatched: true},
    StateDispatched:     {},
}

func (s State) CanTransitionTo(next State) bool {
    return orderFSM[s][next]
}
```
Enforcing state transitions through a centralized FSM turns business logic rules into deterministic, statically verifiable code invariants.

<Exercise n={2} title="Strict FSM state transition guard" level="medium">

Write a state transition validator `Transition(current, target State) error` using a strict transition graph. The allowed flow is `draft` $\to$ `pending_payment` $\to$ `paid` $\to$ `fulfilled` (or `cancelled` from draft/pending). Verify that attempting to skip payment directly from `pending_payment` to `fulfilled` returns `ErrInvalidTransition`.

<Solution>

```go
package main

import (
	"errors"
	"fmt"
)

type State string

const (
	StateDraft     State = "draft"
	StatePending   State = "pending_payment"
	StatePaid      State = "paid"
	StateFulfilled State = "fulfilled"
	StateCancelled State = "cancelled"
)

var allowedTransitions = map[State]map[State]bool{
	StateDraft:     {StatePending: true, StateCancelled: true},
	StatePending:   {StatePaid: true, StateCancelled: true},
	StatePaid:      {StateFulfilled: true},
	StateFulfilled: {},
	StateCancelled: {},
}

var ErrInvalidTransition = errors.New("illegal state transition")

func Transition(current, target State) error {
	valid, ok := allowedTransitions[current]
	if !ok || !valid[target] {
		return fmt.Errorf("%w: cannot transition from %s to %s", ErrInvalidTransition, current, target)
	}
	return nil
}

func main() {
	// Valid flow
	fmt.Println("draft -> pending:", Transition(StateDraft, StatePending))
	fmt.Println("pending -> paid:", Transition(StatePending, StatePaid))
	// Illegal skip-step attempt
	fmt.Println("pending -> fulfilled:", Transition(StatePending, StateFulfilled))
}
```

<Exercise n={3} title="Per-object batch authorization guard" level="medium">

Write `AuthorizeBatch(viewerID string, itemIDs []string, db map[string]Item) ([]Item, error)` that verifies every single item in a batch request belongs to `viewerID`. If any item belongs to another owner or does not exist, refuse the entire request with `ErrUnauthorized`.

<Solution>

```go
package main

import (
	"errors"
	"fmt"
)

type Item struct {
	ID      string
	OwnerID string
	Content string
}

var ErrUnauthorized = errors.New("unauthorized batch element access")

func AuthorizeBatch(viewerID string, itemIDs []string, db map[string]Item) ([]Item, error) {
	result := make([]Item, 0, len(itemIDs))
	for _, id := range itemIDs {
		item, exists := db[id]
		if !exists || item.OwnerID != viewerID {
			return nil, fmt.Errorf("%w: access denied for item %q", ErrUnauthorized, id)
		}
		result = append(result, item)
	}
	return result, nil
}

func main() {
	db := map[string]Item{
		"item_1": {"item_1", "alice", "Alice Secret Doc"},
		"item_2": {"item_2", "alice", "Alice Financial Report"},
		"item_3": {"item_3", "bob", "Bob Audit Log"},
	}

	// Alice requests her own items
	items, err := AuthorizeBatch("alice", []string{"item_1", "item_2"}, db)
	fmt.Printf("Alice access: %d items, err: %v\n", len(items), err)

	// Alice attempts to batch-smuggle Bob's item_3
	_, err = AuthorizeBatch("alice", []string{"item_1", "item_3"}, db)
	fmt.Printf("Alice mixed access: err: %v\n", err)
}
```

<Exercise n={4} title="Duplicate-key JSON stream validator" level="hard">

Write `ValidateStrictJSON(data []byte) error` using `json.Decoder.Token()` that traverses a top-level JSON object and returns `ErrDuplicateKey` if any key is defined more than once in the payload, preventing parser differential deserialization exploits.

<Solution>

```go
package main

import (
	"bytes"
	"encoding/json"
	"errors"
	"fmt"
)

var ErrDuplicateKey = errors.New("duplicate JSON key detected")

func ValidateStrictJSON(data []byte) error {
	dec := json.NewDecoder(bytes.NewReader(data))
	tok, err := dec.Token()
	if err != nil {
		return err
	}
	delim, ok := tok.(json.Delim)
	if !ok || delim != '{' {
		return errors.New("expected JSON object start '{'")
	}

	seenKeys := make(map[string]bool)
	for dec.More() {
		tok, err := dec.Token()
		if err != nil {
			return err
		}
		key, ok := tok.(string)
		if !ok {
			return errors.New("expected string key")
		}
		if seenKeys[key] {
			return fmt.Errorf("%w: key %q", ErrDuplicateKey, key)
		}
		seenKeys[key] = true

		var val json.RawMessage
		if err := dec.Decode(&val); err != nil {
			return err
		}
	}
	_, err = dec.Token()
	return err
}

func main() {
	valid := []byte(`{"role":"user","name":"alice"}`)
	attack := []byte(`{"role":"user","role":"admin"}`)

	fmt.Printf("valid payload: err=%v\n", ValidateStrictJSON(valid))
	fmt.Printf("attack payload: err=%v\n", ValidateStrictJSON(attack))
}
```

</Solution>
