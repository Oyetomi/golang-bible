## Core NATS vs JetStream Persistence

To understand NATS, you must first understand the clean line between **Core NATS** and **JetStream**.

Most developers entering the distributed systems space are brainwashed by Apache Kafka. They believe that every message published to a cluster must be written to an append-only commit log on an NVMe SSD before anything else can happen. They accept 5-millisecond write latencies and multi-gigabyte disk footprints as the unavoidable tax of distributed computing.

Core NATS laughs at that assumption.

<Define term="JetStream">
The built-in, Go-native persistence and streaming engine of NATS. Built directly into the single `nats-server` binary, JetStream adds at-least-once delivery, temporal message replay, deduplication windows, durable consumer cursors, and Raft-replicated streams without external coordination services.
</Define>

Core NATS is an ultra-high-speed, in-memory publish/subscribe messaging engine. It behaves like a high-performance network switch for your software services. A publisher sends a message on a subject; if three subscribers are listening, NATS immediately fans the bytes out across their TCP sockets. If nobody is listening, the message evaporates into the ether.

The result? Throughput exceeding **10,000,000 messages per second per node** with p99 latency sitting at **3 to 5 microseconds**. For telemetry, ephemeral price ticks, heartbeats, and live order book quote feeds, Core NATS is unbeatable.

Now, imagine you are building the core settlement pipeline for **Meridian Payments**. A high-value interbank wire transfer arrives:

That is a $25,000,000 wire transfer. That is twenty-five million dollars vanished into thin air, an audit nightmare, and an immediate visit from federal regulators.

This is where **JetStream** takes the stage.

JetStream is not a separate application. It is not an external cluster like ZooKeeper or an operational nightmare like KRaft. It is compiled directly into the Go source of the NATS server. When enabled, JetStream captures messages published to defined subject spaces, persists them to disk or memory in an append-only commit log, enforces Raft consensus across cluster nodes, and allows consumers to pull, replay, and acknowledge messages at their own pace.

### Writing Production JetStream in Go

Modern Go applications interact with JetStream using the modern v2 client API (`github.com/nats-io/nats.go/jetstream`). Unlike the legacy `js.Publish` API, the v2 API is context-aware, type-safe, and structured around clean interfaces.

Here is how a production Meridian payment engine establishes a connection, initializes a JetStream context, and provisions a replicated wire settlement stream:

```go
package main

import (
	"context"
	"fmt"
	"log"
	"time"

	"github.com/nats-io/nats.go"
	"github.com/nats-io/nats.go/jetstream"
)

func main() {
	// Connect to NATS cluster
	nc, err := nats.Connect("nats://127.0.0.1:4222",
		nats.Timeout(5*time.Second),
		nats.PingInterval(20*time.Second),
		nats.MaxPingsOutstanding(3),
	)
	if err != nil {
		log.Fatalf("Failed to connect to NATS: %v", err)
	}
	defer nc.Close()

	ctx, cancel := context.WithTimeout(context.Background(), 10*time.Second)
	defer cancel()

	// Initialize the modern JetStream interface
	js, err := jetstream.New(nc)
	if err != nil {
		log.Fatalf("Failed to initialize JetStream: %v", err)
	}

	// Declare the Meridian Wires Stream
	streamConfig := jetstream.StreamConfig{
		Name:        "MERIDIAN_WIRES",
		Description: "High-value interbank wire transfers and settlements",
		Subjects:    []string{"meridian.wires.>"},
		Storage:     jetstream.FileStorage, // Durable disk storage
		Retention:   jetstream.LimitsPolicy, // Retain until max limits or age
		MaxAge:      7 * 24 * time.Hour,     // 7-day compliance retention
		Duplicates:  2 * time.Minute,         // Deduplication window
		Replicas:    3,                       // 3-node Raft consensus quorum
	}

	stream, err := js.CreateOrUpdateStream(ctx, streamConfig)
	if err != nil {
		log.Fatalf("Failed to create stream: %v", err)
	}

	info, _ := stream.Info(ctx)
	fmt.Printf("Stream %s initialized! Messages: %d, Bytes: %d
",
		info.Config.Name, info.State.Msgs, info.State.Bytes)
}
```

```go
package main

import (
	"fmt"
	"sync"
)

// CoreNATS simulates an ephemeral in-memory pub/sub router.
type CoreNATS struct {
	mu   sync.RWMutex
	subs map[string][]chan string
}

func NewCoreNATS() *CoreNATS {
	return &CoreNATS{subs: make(map[string][]chan string)}
}

func (c *CoreNATS) Subscribe(subj string) <-chan string {
	c.mu.Lock()
	defer c.mu.Unlock()
	ch := make(chan string, 16)
	c.subs[subj] = append(c.subs[subj], ch)
	return ch
}

func (c *CoreNATS) Publish(subj string, msg string) {
	c.mu.RLock()
	defer c.mu.RUnlock()
	for _, ch := range c.subs[subj] {
		select {
		case ch <- msg:
		default:
		}
	}
}

// JetStreamLog simulates a persistent append-only stream.
type JetStreamMessage struct {
	Seq  uint64
	Subj string
	Data string
}

type JetStreamLog struct {
	mu   sync.RWMutex
	msgs []JetStreamMessage
	seq  uint64
}

func NewJetStreamLog() *JetStreamLog {
	return &JetStreamLog{}
}

func (js *JetStreamLog) Publish(subj string, data string) uint64 {
	js.mu.Lock()
	defer js.mu.Unlock()
	js.seq++
	js.msgs = append(js.msgs, JetStreamMessage{Seq: js.seq, Subj: subj, Data: data})
	return js.seq
}

func (js *JetStreamLog) ReplayFrom(startSeq uint64) []JetStreamMessage {
	js.mu.RLock()
	defer js.mu.RUnlock()
	var out []JetStreamMessage
	for _, m := range js.msgs {
		if m.Seq >= startSeq {
			out = append(out, m)
		}
	}
	return out
}

func main() {
	fmt.Println("=== 1. Core NATS: Ephemeral Pub/Sub ===")
	core := NewCoreNATS()
	core.Publish("meridian.wires.us", "Wire $5M (Published BEFORE subscriber connects)")

	// Late subscriber joins
	subCh := core.Subscribe("meridian.wires.us")
	core.Publish("meridian.wires.us", "Wire $10M (Published AFTER subscriber connects)")

	select {
	case msg := <-subCh:
		fmt.Printf("Core NATS received: %s
", msg)
	default:
		fmt.Println("Core NATS received nothing!")
	}

	fmt.Println("
=== 2. JetStream: Persistent Replayable Stream ===")
	js := NewJetStreamLog()
	js.Publish("meridian.wires.us", "Wire $5M - Settlement 101")
	js.Publish("meridian.wires.us", "Wire $10M - Settlement 102")

	// Late subscriber joins now and replays from the very beginning (Seq 1)
	replayed := js.ReplayFrom(1)
	fmt.Printf("JetStream replayed %d messages for late subscriber:
", len(replayed))
	for _, m := range replayed {
		fmt.Printf("  [Seq %d] %s -> %s
", m.Seq, m.Subj, m.Data)
	}
}
```

## Subject Hierarchies & Wildcard Routing

In Apache Kafka, routing is rigid. You configure a topic named `wires`, and every producer writes to that single topic. If your downstream compliance engine only cares about New York wire settlements, what does it do? It must read every single wire transfer for Tokyo, London, Singapore, and Frankfurt, decode the JSON payload, check `region == "NY"`, and discard the rest.

Think of the wasted CPU cycles, the garbage collection overhead, and the saturated network bandwidth.

NATS replaces this stone-age model with **Subject Hierarchies**.

<Define term="Subject Hierarchy">
A dot-delimited string representing an addressable destination in NATS (e.g., `meridian.wires.us.ny.settled`). Subjects form hierarchical token trees that allow publishers to specify granular routing coordinates and subscribers to filter messages at the network layer.
</Define>

<Define term="Token Wildcard (*)">
A single-level wildcard token in NATS subject routing. The asterisk (`*`) matches exactly one token at that specific position within the hierarchy, allowing targeted multi-tenant or regional pattern subscriptions.
</Define>

<Define term="Full Wildcard (>)">
A multi-level terminal wildcard token in NATS subject routing. The greater-than symbol (`>`) matches one or more tokens from its position to the end of the subject string. It can only appear as the final token in a subscription subject.
</Define>

### Subject Syntax and Semantics

Subjects are composed of alphanumeric tokens separated by dots (`.`):
- Case-sensitive (`meridian` is distinct from `MERIDIAN`).
- Cannot contain spaces or non-printable ASCII characters.
- Tokens can be combined with wildcards:

```
meridian.wires.us.ny.settled
───┬──── ──┬── ┬─ ┬─ ───┬───
   │       │   │  │     └── Status (settled, pending, failed)
   │       │   │  └──────── City / Desk (ny, sfo, lon)
   │       │   └─────────── Country (us, ca, uk)
   │       └─────────────── Domain (wires, fx, cards)
   └─────────────────────── Organization (meridian)
```

Consider the filtering power this gives your architecture:

1. **`meridian.wires.us.ny.settled`**: Matches only settled wires originating from the New York desk.
2. **`meridian.wires.*.ny.>`**: Matches wires from any country entering the New York desk, regardless of their subsequent hierarchy depth.
3. **`meridian.wires.>`**: Matches all wire transfers everywhere across the entire organization.
4. **`meridian.*.us.>`**: Matches all US operations across wires, foreign exchange, and card processing.

### The Radix Tree: Zero-Allocation Matching

How does NATS evaluate tens of thousands of wildcard subscriptions against millions of messages per second without burning the CPU to the ground?

If you implement subject matching using regular expressions or `strings.Split()`, your server will buckle under GC pressure. `strings.Split()` allocates a slice and a new string object for every token in the subject. At 1,000,000 messages per second with 5 tokens each, that is **6,000,000 heap allocations per second**.

Internally, the NATS server organizes subscriptions into a **Radix Trie**. Each node in the trie represents a token. Specific tokens branch into child nodes, `*` routes to a shared single-token node, and `>` branches into a terminal subscription bucket. When a message arrives, the routing engine walks the trie using raw byte offsets from the incoming TCP socket buffer.

Let us build and run a pure Go implementation of a Subject Trie matcher:

<GoPlayground>

```go
package main

import (
	"fmt"
	"strings"
)

type TrieNode struct {
	children map[string]*TrieNode
	star     *TrieNode
	gtSubs   []string
	subs     []string
}

func NewTrieNode() *TrieNode {
	return &TrieNode{children: make(map[string]*TrieNode)}
}

type SubjectTrie struct {
	root *TrieNode
}

func NewSubjectTrie() *SubjectTrie {
	return &SubjectTrie{root: NewTrieNode()}
}

func (t *SubjectTrie) Insert(pattern, subscriberID string) {
	tokens := strings.Split(pattern, ".")
	curr := t.root

	for i, token := range tokens {
		if token == ">" {
			curr.gtSubs = append(curr.gtSubs, subscriberID)
			return
		}
		if token == "*" {
			if curr.star == nil {
				curr.star = NewTrieNode()
			}
			curr = curr.star
		} else {
			if _, exists := curr.children[token]; !exists {
				curr.children[token] = NewTrieNode()
			}
			curr = curr.children[token]
		}
		if i == len(tokens)-1 {
			curr.subs = append(curr.subs, subscriberID)
		}
	}
}

func (t *SubjectTrie) Match(subject string) []string {
	tokens := strings.Split(subject, ".")
	var matched []string
	matchRecursive(t.root, tokens, 0, &matched)
	return matched
}

func matchRecursive(node *TrieNode, tokens []string, idx int, matched *[]string) {
	if node == nil {
		return
	}

	// Any '>' registered at this level matches this token and all subsequent tokens
	*matched = append(*matched, node.gtSubs...)

	if idx == len(tokens) {
		*matched = append(*matched, node.subs...)
		return
	}

	token := tokens[idx]

	// 1. Exact match branch
	if next, exists := node.children[token]; exists {
		matchRecursive(next, tokens, idx+1, matched)
	}

	// 2. Wildcard '*' branch
	if node.star != nil {
		matchRecursive(node.star, tokens, idx+1, matched)
	}
}

func main() {
	trie := NewSubjectTrie()

	// Register subscriptions across Meridian payment domains
	trie.Insert("meridian.wires.>", "Sub-Global-Wires-Auditor")
	trie.Insert("meridian.wires.*.ny.settled", "Sub-NY-Settlement-Desk")
	trie.Insert("meridian.wires.us.ca.settled", "Sub-CA-Settlement-Desk")
	trie.Insert("meridian.market.fx.>", "Sub-FX-Liquidity-Engine")

	testSubject := "meridian.wires.us.ny.settled"
	matches := trie.Match(testSubject)

	fmt.Printf("Evaluating Subject: %s
```

## Stream Storage & Retention Policies

In JetStream, a **Stream** is the persistence container. A stream acts as an abstraction over one or more subjects. Multiple subjects are consumed into a single ordered stream, persisted according to storage rules, and pruned according to retention policies.

<Define term="Stream Retention Policy">
The strategy governing how JetStream prunes messages from an append-only stream. The three policies—LimitsPolicy (FIFO pruning on size/count/age), InterestPolicy (pruning when all active consumers have acknowledged), and WorkQueuePolicy (pruning immediately after the first consumer acknowledges)—determine message lifecycle.
</Define>

<Define term="Deduplication Window">
A server-side rolling time window during which JetStream tracks client-provided message IDs (`Nats-Msg-Id`). If a publisher resends a message with an identical ID within this window, JetStream skips disk persistence and returns the existing sequence number, enforcing idempotency.
</Define>

### Retention Policy Architecture

When defining a stream, you choose one of three retention policies depending on your workload:

```
1. LimitsPolicy (Default: Event Store & Audit Log)
   [ Msg 1 ] [ Msg 2 ] [ Msg 3 ] [ Msg 4 ] [ Msg 5 ] ──> FIFO Drop when MaxAge / MaxBytes hit
   All messages retained regardless of whether consumers have seen them.

2. InterestPolicy (Smart Event Distribution)
   [ Msg 1 (Acked by all) ] ──> DELETED FROM STREAM!
   [ Msg 2 (Pending Cons B) ] ──> Retained until Consumer B acknowledges.

3. WorkQueuePolicy (Strict Single-Worker Queue)
   [ Msg 1 ] ──> Fetched by Worker A ──> Worker A calls msg.Ack() ──> PURGED IMMEDIATELY!
   Guarantees each task is processed exactly once across worker pools.
```

### The Deduplication Window: Eliminating Double Debits

In payment processing, network connections are untrusted. Consider a network timeout during a wire transfer:

1. Meridian Core sends wire transaction `wire-9081` to JetStream.
2. JetStream writes the wire to disk and assigns sequence `501`.
3. JetStream sends an acknowledgment back over TCP, but a network router blips and drops the ACK packet.
4. Meridian Core's publish client hits a 2-second timeout. It assumes the write failed and retries sending `wire-9081`.

Without deduplication, the recipient gets credited twice: $2,000,000 transferred instead of $1,000,000.

JetStream solves this at the protocol level. Every publish can include a `Nats-Msg-Id` header. JetStream maintains an in-memory sliding window of message IDs (e.g., `Duplicates: 2 * time.Minute`). When the retry arrives:

```go
	Timestamp time.Time

	mu         sync.Mutex
	window     time.Duration
	dedupTable map[string]DedupEntry
	messages   []string
	seqCounter uint64

		window:     window,
		dedupTable: make(map[string]DedupEntry),
	}

	s.mu.Lock()
	defer s.mu.Unlock()

	// 1. Check deduplication window
	if entry, found := s.dedupTable[msgID]; found {

			// Duplicate hit: return existing sequence without writing!
			return entry.Seq, true

	s.seqCounter++
	s.messages = append(s.messages, payload)
	s.dedupTable[msgID] = DedupEntry{
		Seq:       s.seqCounter,
		Timestamp: now,
	}

	return s.seqCounter, false
}

", seq1, dup1)

	// Simulated network timeout retry with identical Nats-Msg-Id
	seq2, dup2 := stream.Publish(txID, payload)
	fmt.Printf("Publish 2: Seq=%d, Duplicate=%v (Suppressed by deduplication window)
", seq2, dup2)
```

## Durable Pull Consumers & Batch Fetching

If you have ever used legacy messaging queues, you are familiar with **Push Consumers**. The broker maintains a connection to your application and blasts messages down the socket as fast as it can.

Push consumers are a relic of the past. When your downstream worker experiences a temporary latency spike (such as an intensive fraud calculation or database row lock), its in-memory buffer balloons, the TCP receive window collapses, and the broker either crashes your worker with memory exhaustion or severs the connection with a `Slow Consumer` error.

Modern JetStream architectures use **Durable Pull Consumers**.

<Define term="Durable Consumer">
A stateful consumer cursor managed on the JetStream cluster. Durable consumers persist their delivery position, unacknowledged message IDs, and redelivery counters on disk, surviving worker restarts, redeployments, and network partitions.
</Define>

<Define term="AckPolicy">
The acknowledgment contract governing message delivery in JetStream. The standard `AckExplicit` requires consumers to explicitly acknowledge every message, while `AckNone` provides fire-and-forget, and `AckAll` allows cumulative stream offset acknowledgments.
</Define>

### Why Pull Consumers Dominate

With Pull Consumers, **the client governs the flow of time**. The worker asks the cluster for work only when it has available CPU capacity:

```
Worker: "Give me up to 50 messages, or wait up to 2 seconds for them to arrive."
JetStream: [Delivers 50 messages] -> Starts AckWait timer for each message.
Worker: Processes messages concurrently -> Explicitly calls msg.Ack() on each.
```

If the worker crashes halfway through the batch, the unacknowledged messages exceed their `AckWait` deadline (e.g., 30 seconds). JetStream automatically returns them to the stream and redelivers them to the next available worker.

```
┌─────────────────────────────────────────────────────────────────────────┐
│                    Durable Pull Consumer Cycle                          │
│                                                                         │
│   Worker Goroutines                        JetStream Cluster            │
│   ─────────────────                        ─────────────────            │
│          │                                         │                    │
│          │─── 1. Fetch(Batch: 100, MaxWait: 2s) ──>│                    │
│          │                                         │                    │
│          │<── 2. Deliver Messages [Seq 101..200] ──│ (AckWait: 30s)    │
│          │                                         │                    │
│          │─── 3. msg.InProgress() ────────────────>│ (Resets AckWait)   │
│          │       (For long-running AML check)      │                    │
│          │                                         │                    │
│          │─── 4. msg.Ack() ───────────────────────>│ (Advances AckFloor)│
│          │                                         │                    │
│          │─── 5. msg.Nak() ───────────────────────>│ (Requeues instant) │
│          │       (Transient DB deadlock)           │                    │
│          │                                         │                    │
│          │─── 6. msg.Term() ──────────────────────>│ (Drops poison pill)│
│          │       (Malformed payload)               │                    │
└─────────────────────────────────────────────────────────────────────────┘
```

```go
	"context"
	"fmt"

func RunSettlementWorker(ctx context.Context, js jetstream.JetStream) error {
	// Create or attach to a durable pull consumer
	consumer, err := js.CreateOrUpdateConsumer(ctx, "MERIDIAN_WIRES", jetstream.ConsumerConfig{
		Durable:       "settlement-processor-v1",
		Description:   "Interbank wire settlement processor",
		AckPolicy:     jetstream.AckExplicitPolicy,
		AckWait:       10 * time.Second,
		MaxDeliver:    5, // Requeue up to 5 times before sending to dead-letter
		FilterSubject: "meridian.wires.*.*.settled",
	})
	if err != nil {
		return fmt.Errorf("failed to bind durable consumer: %w", err)
	}

	// Pull batches of work dynamically
	for {
		select {
		case <-ctx.Done():
			return ctx.Err()
		default:
		}

		// Fetch up to 50 messages, waiting up to 2 seconds
		batch, err := consumer.Fetch(50, jetstream.FetchMaxWait(2*time.Second))
		if err != nil {
			log.Printf("Fetch error: %v", err)
			continue
		}

		for msg := range batch.Messages() {
			processWire(msg)
		}
	}
}

func processWire(msg jetstream.Msg) {
	// 1. Check if processing will take longer than AckWait
	// If so, send in-progress pulse to prevent redelivery
	_ = msg.InProgress()

	// 2. Perform business logic
	err := executeSettlement(msg.Data())
	if err != nil {
		// Transient failure: request immediate redelivery with Nak
		log.Printf("Settlement transient failure, sending NAK: %v", err)
		_ = msg.Nak()
		return
	}

	// 3. Success: explicitly acknowledge
	if err := msg.Ack(); err != nil {
		log.Printf("Failed to ACK message: %v", err)
	}
}
```

```go
package main

import (
	"fmt"
	"sync"
	"time"
)

type Msg struct {
	Seq      uint64
	Payload  string
	Attempts int
}

type InFlightMsg struct {
	Msg       Msg
	Delivered time.Time
}

type PullConsumer struct {
	mu          sync.Mutex
	durableName string
	ackWait     time.Duration
	unprocessed []Msg
	inFlight    map[uint64]InFlightMsg
}

func NewPullConsumer(name string, ackWait time.Duration, items []string) *PullConsumer {
	var msgs []Msg
	for i, item := range items {
		msgs = append(msgs, Msg{Seq: uint64(i + 1), Payload: item, Attempts: 0})
	}
	return &PullConsumer{
		durableName: name,
		ackWait:     ackWait,
		unprocessed: msgs,
		inFlight:    make(map[uint64]InFlightMsg),
	}
}

func (c *PullConsumer) Fetch(batchSize int) []Msg {
	c.mu.Lock()
	defer c.mu.Unlock()

	var batch []Msg
	count := min(batchSize, len(c.unprocessed))
	now := time.Now()

	for i := 0; i < count; i++ {
		m := c.unprocessed[i]
		m.Attempts++
		c.inFlight[m.Seq] = InFlightMsg{Msg: m, Delivered: now}
		batch = append(batch, m)
	}
	c.unprocessed = c.unprocessed[count:]
	return batch
}

func (c *PullConsumer) Ack(seq uint64) {
	c.mu.Lock()
	defer c.mu.Unlock()
	delete(c.inFlight, seq)
}

func (c *PullConsumer) CheckTimeouts() int {
	c.mu.Lock()
	defer c.mu.Unlock()

	now := time.Now()
	reclaimed := 0
	for seq, item := range c.inFlight {
		if now.Sub(item.Delivered) > c.ackWait {
			c.unprocessed = append(c.unprocessed, item.Msg)
			delete(c.inFlight, seq)
			reclaimed++
		}
	}
	return reclaimed
}

func main() {
	c := NewPullConsumer("meridian-wire-puller", 100*time.Millisecond, []string{
		"Wire #101 ($500,000 USD)",
		"Wire #102 ($1,200,000 EUR)",
		"Wire #103 ($3,400,000 GBP)",
	})

	// 1. Fetch first batch of 2 items
	batch := c.Fetch(2)
	fmt.Printf("Fetched %d messages from consumer:
", len(batch))
	for _, m := range batch {
		fmt.Printf("  -> [Seq %d] %s (Attempt %d)
", m.Seq, m.Payload, m.Attempts)
	}

	// 2. Worker acknowledges Wire #101 immediately
	c.Ack(batch[0].Seq)
	fmt.Printf("Worker successfully acknowledged Seq %d
", batch[0].Seq)

	// 3. Worker stalls on Wire #102; sleep past AckWait (100ms)
	fmt.Println("Worker sleeping... simulating crash on Wire #102")
	time.Sleep(120 * time.Millisecond)

	// 4. Cluster timeout check reclaims unacknowledged Wire #102
	reclaimed := c.CheckTimeouts()
	fmt.Printf("AckWait expired! Cluster reclaimed %d unacknowledged messages
", reclaimed)

	// 5. Subsequent fetch receives Wire #103 and the redelivered Wire #102
	nextBatch := c.Fetch(2)
	fmt.Printf("
Next Fetch retrieved %d messages:
", len(nextBatch))
	for _, m := range nextBatch {
		fmt.Printf("  -> [Seq %d] %s (Attempt %d)
", m.Seq, m.Payload, m.Attempts)
		c.Ack(m.Seq)
	}
}
```

## Embedded Distributed Key-Value Store

Here is a common engineering mistake: a team adopts NATS for streaming, but then spins up a 3-node Redis cluster for session state and an etcd cluster for configuration flags. Now they have three distributed stateful systems to back up, monitor, upgrade, and secure.

NATS eliminates this insanity with its **Embedded Key-Value (KV) Store**.

<Define term="KV Bucket">
A distributed Key-Value store backed natively by a NATS JetStream Stream. Keys map directly to subject tokens (e.g., `$KV.<bucket>.<key>`), values are stored as message payloads, and revisions provide atomic Compare-And-Swap (CAS) capabilities with zero external dependencies.
</Define>

### How NATS KV Works Under the Hood

A NATS KV bucket is not a separate engine. It is a specialized JetStream stream!

When you call `js.CreateKeyValue(ctx, jetstream.KeyValueConfig{Bucket: "meridian_configs"})`:
1. JetStream creates a stream named `KV_meridian_configs`.
2. The stream binds to subjects `$KV.meridian_configs.*`.
3. The stream retention policy is configured to keep only the last message for each subject (or the last `N` messages if `History` is enabled).
4. When you `Put("max_wire_usd", []byte("10000000"))`, JetStream publishes a message to subject `$KV.meridian_configs.max_wire_usd`.
5. When you `Get("max_wire_usd")`, JetStream reads the latest message for that subject from the stream log.
6. When you `Delete("max_wire_usd")`, JetStream writes a tombstone message with the header `KV-Operation: DEL`.

Because it is built on JetStream, **your KV store inherits Raft replication, disk durability, and sub-millisecond read latency for free.**

### Optimistic Concurrency Control (CAS)

In distributed finance, balance updates must never race. If two workers read an account balance of $1,000,000 simultaneously and both attempt to deduct $200,000, naive writes will result in a balance of $800,000 instead of $600,000.

NATS KV provides native **Compare-And-Swap (CAS)** via stream sequence numbers:

```go

    // Another worker modified the balance first! Re-read and retry.
}
```

<UnderTheHood title="JetStream Append-Only Storage, Raft Consensus & Zero-Copy Framing">

Let us peel back the metal and inspect how NATS JetStream achieves 10,000,000+ messages per second with single-digit microsecond latencies while Apache Kafka struggles to break 1,000,000 messages per second on identical hardware.

### 1. The Go-Native Append-Only Storage Engine

JetStream avoids third-party embedded databases like RocksDB or Badger. Foreign C++ engines introduce cgo bridge crossing penalties (roughly 50–100 nanoseconds per call) and obscure memory management outside the Go runtime.

Instead, JetStream implements a Go-native block storage engine:
- **Segment Files (`.dat`)**: Messages are written to append-only segment files (typically 128MB chunks). Appends are purely sequential, maximizing NVMe SSD controller parallelism and leveraging the Linux kernel page cache.
- **Index Files (`.idx`)**: A companion fixed-size binary index maps stream sequence numbers to physical byte offsets in the `.dat` file. Reading sequence `N` is an $O(1)$ arithmetic seek: `offset = N * sizeof(IndexRecord)`.
- **Zero-Random-Disk I/O**: Compactions and retention prunes simply unlink ancient `.dat` files from the filesystem directory, avoiding expensive B-tree rebalancing or LSM-tree compaction storms.

```
/data/jetstream/streams/MERIDIAN_WIRES/
├── 1.dat        # 128MB raw append-only message frame log
├── 1.idx        # Binary fixed-stride offset table
├── 2.dat        # Active append head
└── 2.idx        # Active index head
```

### 2. Multi-Raft Stream Consensus

In traditional distributed logs, a single consensus ring coordinates the entire cluster (e.g., KRaft or ZooKeeper). When write volume spikes, the consensus coordinator becomes the global bottleneck.

NATS JetStream uses **Multi-Raft**:
- Every stream and every consumer can form an independent Raft consensus group.
- In a 5-node NATS cluster, Node A can be the Raft leader for stream `MERIDIAN_WIRES`, while Node B is leader for stream `MERIDIAN_MARKET_DATA`, and Node C is leader for bucket `KV_CONFIGS`.
- Raft heartbeats and append entries run across lightweight Go goroutines multiplexed over existing cluster TCP connections. Write throughput scales horizontally with the number of streams.

### 3. Zero-Copy TCP Socket Framing

The NATS wire protocol is an ASCII-delimited binary envelope designed to minimize CPU parsing overhead:

```
PUB meridian.wires.us.ny.settled 64

{"wire_id":"tx-991","amount_cents":100000000,"status":"settled"}

```

When a packet hits the network interface:
1. The NATS server reads the TCP stream into a pre-allocated byte buffer.
2. The parser scans for `
` without allocating strings or parsing JSON.
3. The subject token is matched against the in-memory Radix Trie using byte slices pointing directly into the TCP receive buffer.
4. When fanning out to subscribers, JetStream uses **vectored I/O (`writev`)** via Go's `net.Buffers`. The server passes pointers to the protocol header and the original payload buffer directly to the Linux kernel socket, bypassing intermediate application copies.

### 4. Why NATS Smokes the JVM

Why does NATS consistently deliver single-digit microsecond latencies while Kafka experiences multi-millisecond spikes?

1. **Memory Representation**: In the JVM, a simple 24-byte payload wrapped in an `Object` overhead costs 48–64 bytes, fragmented across heap memory. In Go, structs and byte buffers are laid out contiguously in flat memory arrays, maximizing CPU L1/L2 cache prefetching.
2. **Garbage Collection**: Kafka brokers allocate millions of ephemeral JVM objects, triggering GC Mark-Sweep cycles that pause mutator threads. NATS reuses byte buffer pools (`sync.Pool`) and allocates long-lived streams on the stack or in large contiguous arenas. In Go 1.26, the default **Green Tea GC** keeps runtime pause times strictly below 50 microseconds even under gigabit network load.
3. **Memory Footprint**: A 3-node NATS JetStream cluster handling 1,000,000 msgs/sec consumes roughly 150MB of RAM total. The equivalent Kafka cluster requires 12GB to 24GB of RAM just to satisfy JVM heap minimums.

<Exercise n={1} title="Zero-Allocation Subject Token Matcher" level="easy">

Implement `MatchSubject(pattern, subject string) bool` that evaluates whether a dot-separated subject matches a pattern containing `*` (single token wildcard) and `>` (terminal multi-token wildcard) without allocating slices or strings via `strings.Split()`.

<Solution>

```go
package main

import "fmt"

func MatchSubject(pattern, subject string) bool {
	pStart, sStart := 0, 0
	pLen, sLen := len(pattern), len(subject)

	for pStart < pLen && sStart < sLen {
		pEnd := pStart
		for pEnd < pLen && pattern[pEnd] != '.' {
			pEnd++
		}
		pToken := pattern[pStart:pEnd]

		if pToken == ">" {
			return true
		}

		sEnd := sStart
		for sEnd < sLen && subject[sEnd] != '.' {
			sEnd++
		}
		sToken := subject[sStart:sEnd]

		if pToken != "*" && pToken != sToken {
			return false
		}

		if pEnd < pLen {
			pStart = pEnd + 1
		} else {
			pStart = pEnd
		}
		if sEnd < sLen {
			sStart = sEnd + 1
		} else {
			sStart = sEnd
		}
	}

	if pStart < pLen && pattern[pStart:] == ">" {
		return true
	}
	return pStart == pLen && sStart == sLen
}

func main() {
	tests := []struct {
		pattern, subject string
		expected         bool
	}{
		{"meridian.wires.>", "meridian.wires.us.ny.settled", true},
		{"meridian.wires.*.ny.settled", "meridian.wires.us.ny.settled", true},
		{"meridian.wires.*.ny.settled", "meridian.wires.us.ca.settled", false},
		{"meridian.*", "meridian.wires.us", false},
		{"meridian.>", "meridian.wires.us", true},
	}

	for _, tt := range tests {
		matched := MatchSubject(tt.pattern, tt.subject)
		fmt.Printf("Pattern %s vs %s: %v (expected %v)
", tt.pattern, tt.subject, matched, tt.expected)
	}
}
```

**Explanation**: The function walks both strings simultaneously using two sliding index pointers (`pStart` and `sStart`). Tokens are demarcated by `.` without calling `strings.Split()`, completely eliminating heap allocations during subject evaluation.
</Solution>
</Exercise>

<Exercise n={2} title="Sliding-Window Deduplication Engine" level="medium">

Build a thread-safe `RingDedupWindow` struct backed by a fixed-capacity circular ring buffer and a map index. When an incoming message ID is checked, return whether it was seen within `window`. If the ring buffer fills up, evict the oldest entry to bound memory usage.

<Solution>

```go
package main

import (
	"fmt"
	"sync"
	"time"
)

type DedupEntry struct {
	ID        string
	Seq       uint64
	Timestamp time.Time
}

type RingDedupWindow struct {
	mu      sync.Mutex
	window  time.Duration
	entries []DedupEntry
	head    int
	count   int
	cap     int
	index   map[string]int
}

func NewRingDedupWindow(capacity int, window time.Duration) *RingDedupWindow {
	return &RingDedupWindow{
		window:  window,
		entries: make([]DedupEntry, capacity),
		cap:     capacity,
		index:   make(map[string]int),
	}
}

func (r *RingDedupWindow) CheckOrInsert(id string, seq uint64, now time.Time) (existingSeq uint64, isDup bool) {
	r.mu.Lock()
	defer r.mu.Unlock()

	if idx, exists := r.index[id]; exists {
		entry := r.entries[idx]
		if now.Sub(entry.Timestamp) <= r.window {
			return entry.Seq, true
		}
	}

	if r.count == r.cap {
		oldest := r.entries[r.head]
		delete(r.index, oldest.ID)
	} else {
		r.count++
	}

	insertIdx := r.head
	r.entries[insertIdx] = DedupEntry{ID: id, Seq: seq, Timestamp: now}
	r.index[id] = insertIdx
	r.head = (r.head + 1) % r.cap

	return seq, false
}

func main() {
	r := NewRingDedupWindow(100, 2*time.Minute)
	now := time.Now()

	seq, dup := r.CheckOrInsert("msg-101", 1, now)
	fmt.Printf("Msg 1: Seq=%d, Dup=%v
", seq, dup)

	seq, dup = r.CheckOrInsert("msg-101", 999, now.Add(30*time.Second))
	fmt.Printf("Msg 1 Retry: Seq=%d, Dup=%v
", seq, dup)

	seq, dup = r.CheckOrInsert("msg-102", 2, now.Add(40*time.Second))
	fmt.Printf("Msg 2: Seq=%d, Dup=%v
", seq, dup)
}
```

**Explanation**: Combining a fixed-size ring buffer with an in-memory hash map bounds memory consumption while providing $O(1)$ lookup times. Expired or overwritten entries are automatically pruned from the map index when the ring buffer overwrites slots.
</Solution>
</Exercise>

<Exercise n={3} title="Durable Pull Consumer with Redelivery Queue" level="medium">

Implement a thread-safe `ConsumerQueue` with an `AckWait` duration. Workers call `Fetch(max)` to pull items and `Ack(seq)` to complete them. A `ReclaimExpired()` method scans in-flight items and moves unacknowledged items whose deadlines expired back to the front of the pending queue.

<Solution>

```go
package main

import (
	"fmt"
	"sync"
	"time"
)

type WorkItem struct {
	Seq         uint64
	Body        string
	AckDeadline time.Time
}

type ConsumerQueue struct {
	mu       sync.Mutex
	ackWait  time.Duration
	pending  []WorkItem
	inFlight map[uint64]WorkItem
}

func NewConsumerQueue(ackWait time.Duration) *ConsumerQueue {
	return &ConsumerQueue{
		ackWait:  ackWait,
		inFlight: make(map[uint64]WorkItem),
	}
}

func (q *ConsumerQueue) Enqueue(seq uint64, body string) {
	q.mu.Lock()
	defer q.mu.Unlock()
	q.pending = append(q.pending, WorkItem{Seq: seq, Body: body})
}

func (q *ConsumerQueue) Fetch(max int) []WorkItem {
	q.mu.Lock()
	defer q.mu.Unlock()

	n := min(max, len(q.pending))
	var batch []WorkItem
	now := time.Now()

	for i := 0; i < n; i++ {
		item := q.pending[i]
		item.AckDeadline = now.Add(q.ackWait)
		q.inFlight[item.Seq] = item
		batch = append(batch, item)
	}
	q.pending = q.pending[n:]
	return batch
}

func (q *ConsumerQueue) Ack(seq uint64) {
	q.mu.Lock()
	defer q.mu.Unlock()
	delete(q.inFlight, seq)
}

func (q *ConsumerQueue) ReclaimExpired() int {
	q.mu.Lock()
	defer q.mu.Unlock()

	now := time.Now()
	count := 0
	for seq, item := range q.inFlight {
		if now.After(item.AckDeadline) {
			q.pending = append(q.pending, item)
			delete(q.inFlight, seq)
			count++
		}
	}
	return count
}

func main() {
	q := NewConsumerQueue(50 * time.Millisecond)
	q.Enqueue(1, "Settlement Batch Alpha")
	q.Enqueue(2, "Settlement Batch Beta")

	batch := q.Fetch(2)
	fmt.Printf("Fetched %d batches for processing
", len(batch))

	q.Ack(batch[0].Seq)
	fmt.Printf("Worker 1 acked batch Seq %d
", batch[0].Seq)

	time.Sleep(60 * time.Millisecond)
	reclaimed := q.ReclaimExpired()
	fmt.Printf("Reclaimed %d unacknowledged items back to queue
", reclaimed)
}
```

**Explanation**: Pull consumers protect system stability by bounding in-flight work. In-flight items are assigned absolute timestamps, and expired leases are automatically returned to the pending queue for re-assignment.
</Solution>
</Exercise>

<Exercise n={4} title="Atomic CAS Key-Value Bucket with Revision Fencing" level="hard">

Create an atomic balance store `BalanceStore` supporting `Init`, `Get`, and `TransferDebitCAS(account string, debitCents int64, expectedRev uint64) (uint64, error)`. The method must check revision alignment, verify sufficient funds, increment a global revision counter, and reject conflicting writes with an error.

<Solution>

```go
package main

import (
	"errors"
	"fmt"
	"sync"
)

var (
	ErrNotFound = errors.New("key not found")
	ErrConflict = errors.New("CAS conflict: revision mismatch")
)

type AccountBalance struct {
	Cents    int64
	Revision uint64
}

type BalanceStore struct {
	mu       sync.RWMutex
	accounts map[string]AccountBalance
	revSeq   uint64
}

func NewBalanceStore() *BalanceStore {
	return &BalanceStore{accounts: make(map[string]AccountBalance)}
}

func (s *BalanceStore) Init(account string, cents int64) uint64 {
	s.mu.Lock()
	defer s.mu.Unlock()
	s.revSeq++
	s.accounts[account] = AccountBalance{Cents: cents, Revision: s.revSeq}
	return s.revSeq
}

func (s *BalanceStore) Get(account string) (AccountBalance, error) {
	s.mu.RLock()
	defer s.mu.RUnlock()
	bal, exists := s.accounts[account]
	if !exists {
		return AccountBalance{}, ErrNotFound
	}
	return bal, nil
}

func (s *BalanceStore) TransferDebitCAS(account string, debitCents int64, expectedRev uint64) (uint64, error) {
	s.mu.Lock()
	defer s.mu.Unlock()

	bal, exists := s.accounts[account]
	if !exists {
		return 0, ErrNotFound
	}
	if bal.Revision != expectedRev {
		return 0, ErrConflict
	}
	if bal.Cents < debitCents {
		return 0, errors.New("insufficient funds")
	}

	s.revSeq++
	s.accounts[account] = AccountBalance{
		Cents:    bal.Cents - debitCents,
		Revision: s.revSeq,
	}
	return s.revSeq, nil
}

func main() {
	store := NewBalanceStore()
	store.Init("acct-meridian-prime", 1000000)

	bal, _ := store.Get("acct-meridian-prime")
	fmt.Printf("Initial: %d cents at Rev %d
", bal.Cents, bal.Revision)

	newRev, err := store.TransferDebitCAS("acct-meridian-prime", 200000, bal.Revision)
	if err != nil {
		fmt.Printf("Debit error: %v
", err)
	} else {
		fmt.Printf("Debit approved! New Rev: %d
", newRev)
	}

	_, err = store.TransferDebitCAS("acct-meridian-prime", 100000, bal.Revision)
	fmt.Printf("Stale CAS attempt: %v
", err)
}
```

**Explanation**: Optimistic concurrency control uses unforgeable monotonic revision numbers to guard state mutations. If another transaction modifies the record in the interim, the revision check fails and guarantees balance integrity without distributed locks.
</Solution>
</Exercise>

<Recap>

- **Core NATS vs JetStream**: Core NATS provides ephemeral, at-most-once in-memory pub/sub routing at 10M+ msgs/sec with microsecond latency. JetStream adds persistent append-only logs, at-least-once delivery, temporal replay, and Raft consensus—compiled directly into the same single Go binary.
- **Subject Hierarchies & Wildcards**: Subjects are dot-delimited routing coordinates. `*` matches a single token at a specific position; `>` matches all remaining tokens to the end of the subject. NATS routes them using an in-memory Radix Trie with zero heap allocations.
- **Retention & Deduplication**: Streams capture subject sets. Retention policies (`LimitsPolicy`, `InterestPolicy`, `WorkQueuePolicy`) dictate pruning rules. Sliding deduplication windows track `Nats-Msg-Id` headers to eliminate double-writes from network retries.
- **Durable Pull Consumers**: Invert flow control by allowing workers to fetch message batches dynamically. Durable consumers persist cursors on disk, support explicit ACKs, and redeliver unacknowledged messages after `AckWait` deadlines.
- **Embedded Distributed Key-Value Store**: Built natively on JetStream streams (`$KV.<bucket>.*`). Keys are subjects, values are payloads, and monotonic revisions provide lock-free, atomic Compare-And-Swap (CAS) state synchronization.

</Recap>
