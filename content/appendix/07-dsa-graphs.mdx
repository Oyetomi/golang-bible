## Representing Graphs

Before you can traverse a graph, you need to hold one in memory. There are exactly two standard representations, and the choice matters.

**The setup.** Imagine you're building the dependency resolver for a Go module system. Packages are nodes. A directed edge from package A to package B means "A imports B." You need to figure out which packages to compile first — and whether there's a circular dependency that would make compilation impossible. This graph problem is the spine of every section in this chapter.

<Define term="Graph (adjacency list)" since="this chapter">
A **graph** is a set of nodes (vertices) connected by edges. An **adjacency list** represents it by storing, for each node, the list of nodes it connects to — in Go, either `[][]int` (nodes numbered 0…N-1) or `map[int][]int` (arbitrary node IDs). Space is O(V+E), making it the right default for any graph where edges are far fewer than V². Without a graph structure you cannot express dependency order, reachability, or routing — all of which come up constantly in distributed backend systems.
</Define>

### Adjacency List vs. Adjacency Matrix

An **adjacency list** stores, for each node, the list of its neighbors. In Go that's either `map[int][]int` (sparse graphs, arbitrary IDs) or `[][]int` (dense graphs, nodes numbered 0…N-1).

An **adjacency matrix** is a 2-D boolean (or weight) array: `matrix[u][v] = true` if there's an edge from u to v.

<ConceptGrid cols={3}>
  <ConceptCard label="Adjacency list — space">O(V + E). Each edge stored once (directed) or twice (undirected). The right default for sparse graphs (most real ones).</ConceptCard>
  <ConceptCard label="Adjacency matrix — space">O(V²). Even if there are only 10 edges in a 1000-node graph, you allocate a million cells. Wasteful when edges are sparse.</ConceptCard>
  <ConceptCard label="Edge lookup">List: O(degree) — scan neighbors. Matrix: O(1) — just index in. Matrix wins for dense graphs where you ask "does edge u→v exist?" millions of times.</ConceptCard>
  <ConceptCard label="Iteration over neighbors">List: O(degree) — exactly as many steps as you have neighbors. Matrix: O(V) — you must scan an entire row even if only two cells are set.</ConceptCard>
  <ConceptCard label="Weighted graphs">Add a weight: list stores `[]Edge` where `Edge` has `to int` and `weight int`. Matrix stores the weight directly at `matrix[u][v]`.</ConceptCard>
  <Gotcha>Never use adjacency matrix for graphs where V is large and edges are sparse — the O(V²) allocation alone will TLE or OOM. In interviews, state your choice and justify it.</Gotcha>
</ConceptGrid>

Here is how you build both representations from an edge list in idiomatic Go 1.24:

```go
package main

import "fmt"

// Edge describes a directed weighted edge.
type Edge struct {
	To, Weight int
}

// buildAdjList builds a directed weighted adjacency list from pairs [u, v, w].
func buildAdjList(n int, edges [][3]int) [][]Edge {
	g := make([][]Edge, n)
	for _, e := range edges {
		u, v, w := e[0], e[1], e[2]
		g[u] = append(g[u], Edge{To: v, Weight: w})
	}
	return g
}

// buildMatrix builds a directed adjacency matrix (0 = no edge).
func buildMatrix(n int, edges [][3]int) [][]int {
	mat := make([][]int, n)
	for i := range mat {
		mat[i] = make([]int, n)
	}
	for _, e := range edges {
		u, v, w := e[0], e[1], e[2]
		mat[u][v] = w
	}
	return mat
}

func main() {
	// 4-node directed graph: 0→1 (w=2), 0→2 (w=5), 1→3 (w=1), 2→3 (w=3)
	edges := [][3]int{{0, 1, 2}, {0, 2, 5}, {1, 3, 1}, {2, 3, 3}}

	g := buildAdjList(4, edges)
	fmt.Println("Adjacency list:")
	for u, neighbors := range g {
		fmt.Printf("  %d → %v\n", u, neighbors)
	}

	mat := buildMatrix(4, edges)
	fmt.Println("Matrix row 0:", mat[0])
}
```

<UnderTheHood title="Slice of slices vs. map — when each wins">

In Go, `[][]Edge` (slice of slices) gives you cache-friendly sequential memory for nodes numbered 0…N-1 — exactly what contest-style problems use. Each inner slice is a separate heap allocation, but iterating neighbors is sequential and the outer slice header is tiny.

`map[int][]Edge` trades the sequential addressing for arbitrary node IDs at the cost of hash indirection per lookup (O(1) average, not constant). Use it when node IDs are non-contiguous strings or large integers — think usernames as node keys in a social graph.

As of Go 1.24, `map` iteration order remains unspecified by the language, and the standard runtime deliberately varies it. This catches bugs that accidentally depend on insertion order. Your BFS/DFS must use an explicit `visited` set, never the iteration order of the map.

</UnderTheHood>

## BFS and DFS

Two traversals. Every graph problem is secretly one of these — or a clever hybrid.

**The scenario.** Your module graph is loaded. You want two things: (1) the minimum number of hops from package `main` to any dependency (to prioritize shallow compilation), and (2) whether any connected component is an island (never reachable from `main`). BFS answers (1). DFS answers (2).

<Define term="BFS — Breadth-First Search">
BFS explores a graph **level by level**, visiting all nodes at distance d before any node at distance d+1. It uses a FIFO queue, and the first time a node is dequeued its recorded distance is the shortest possible. That property makes BFS the go-to algorithm for **shortest paths in unweighted graphs**. If you skip BFS and use DFS for shortest-path, you'll get a path — just not the shortest one, and the bug will be silent.
</Define>

### BFS — Breadth-First Search

BFS explores the graph **level by level**, starting from a source. It visits all nodes at distance 1 before any at distance 2 — which is exactly why it finds shortest paths in **unweighted** graphs. The data structure driving it is a **queue** (FIFO).

In Go, a slice used as `queue[0]` (dequeue front) + `append` (enqueue back) is the standard BFS queue. It's O(1) amortized append and O(n) overall dequeue, which is fine for interview use; `container/list` gives true O(1) dequeue if allocations matter.

```go
// bfs returns the shortest distances from src to all reachable nodes.
// -1 means unreachable.
func bfs(g [][]int, src int) []int {
	dist := make([]int, len(g))
	for i := range dist {
		dist[i] = -1
	}
	dist[src] = 0
	queue := []int{src}

	for len(queue) > 0 {
		u := queue[0]
		queue = queue[1:]
		for _, v := range g[u] {
			if dist[v] == -1 {
				dist[v] = dist[u] + 1
				queue = append(queue, v)
			}
		}
	}
	return dist
}
```

```go
package main

import "fmt"

// bfsShortestPaths returns shortest hop-counts from src.
// g is an unweighted undirected adjacency list ([][]int).
func bfsShortestPaths(g [][]int, src int) []int {
	dist := make([]int, len(g))
	for i := range dist {
		dist[i] = -1
	}
	dist[src] = 0
	queue := []int{src}

	for len(queue) > 0 {
		u := queue[0]
		queue = queue[1:]
		for _, v := range g[u] {
			if dist[v] == -1 {
				dist[v] = dist[u] + 1
				queue = append(queue, v)
			}
		}
	}
	return dist
}

// numIslands counts connected components of '1's in a 2-D grid.
func numIslands(grid [][]byte) int {
	if len(grid) == 0 {
		return 0
	}
	rows, cols := len(grid), len(grid[0])
	count := 0
	dirs := [][2]int{{0, 1}, {0, -1}, {1, 0}, {-1, 0}}

	var bfsFlood func(r, c int)
	bfsFlood = func(r, c int) {
		queue := [][2]int{{r, c}}
		grid[r][c] = '0'
		for len(queue) > 0 {
			cur := queue[0]
			queue = queue[1:]
			for _, d := range dirs {
				nr, nc := cur[0]+d[0], cur[1]+d[1]
				if nr >= 0 && nr < rows && nc >= 0 && nc < cols && grid[nr][nc] == '1' {
					grid[nr][nc] = '0'
					queue = append(queue, [2]int{nr, nc})
				}
			}
		}
	}

	for r := range rows {
		for c := range cols {
			if grid[r][c] == '1' {
				count++
				bfsFlood(r, c)
			}
		}
	}
	return count
}

func main() {
	// Unweighted graph: 0-1, 0-2, 1-3, 2-3
	g := [][]int{{1, 2}, {0, 3}, {0, 3}, {1, 2}}
	fmt.Println("BFS distances from 0:", bfsShortestPaths(g, 0))
	// [0 1 1 2]

	grid := [][]byte{
		{'1', '1', '0', '0'},
		{'1', '0', '0', '1'},
		{'0', '0', '0', '1'},
	}
	fmt.Println("Number of islands:", numIslands(grid)) // 2
}
```

<Define term="DFS — Depth-First Search">
DFS follows one path to its end before backtracking to try another. It runs naturally on the call stack (recursive) or an explicit stack (iterative). DFS does **not** guarantee shortest paths, but it excels at **cycle detection**, **connectivity**, and **topological ordering** — problems where you need to know whether a path exists, not how short it is. Miss a cycle in a dependency graph and you compile forever; miss it in a payment DAG and you get circular settlement references.
</Define>

### DFS — Depth-First Search

DFS dives as deep as possible along one path before backtracking. It's naturally recursive and naturally expresses problems about **connectivity**, **cycle detection**, and **ordering**.

**Recursive DFS** is cleaner and the default in interviews. **Iterative DFS** (explicit stack) avoids stack overflow for extremely deep graphs.

```go
// dfsComponents assigns a component ID to each node.
func dfsComponents(g [][]int) (numComp int, comp []int) {
	comp = make([]int, len(g))
	for i := range comp {
		comp[i] = -1
	}
	var dfs func(u, id int)
	dfs = func(u, id int) {
		comp[u] = id
		for _, v := range g[u] {
			if comp[v] == -1 {
				dfs(v, id)
			}
		}
	}
	for u := range g {
		if comp[u] == -1 {
			dfs(u, numComp)
			numComp++
		}
	}
	return
}
```

**Cycle detection in an undirected graph:** During DFS, if you reach a neighbor that is already visited and is *not* the parent of the current node, you've found a back edge — a cycle.

**Cycle detection in a directed graph:** Track three states per node: unvisited (0), in-stack (1), done (2). If you reach a node that's `in-stack`, the graph has a cycle.

<GoPlayground>

```go
package main

import "fmt"

// hasCycleDirected returns true if the directed graph has a cycle.
func hasCycleDirected(g [][]int) bool {
	n := len(g)
	// state: 0=unvisited, 1=in-stack, 2=done
	state := make([]int, n)

	var dfs func(u int) bool
	dfs = func(u int) bool {
		state[u] = 1
		for _, v := range g[u] {
			if state[v] == 1 {
				return true // back edge → cycle
			}
			if state[v] == 0 && dfs(v) {
				return true
			}
		}
		state[u] = 2
		return false
	}

	for u := range n {
		if state[u] == 0 && dfs(u) {
			return true
		}
	}
	return false
}

func main() {
	// DAG: 0→1, 1→2, 0→2
	dag := [][]int{{1, 2}, {2}, {}}
	fmt.Println("DAG has cycle:", hasCycleDirected(dag)) // false

	// Cyclic: 0→1, 1→2, 2→0
	cyclic := [][]int{{1}, {2}, {0}}
	fmt.Println("Cyclic graph has cycle:", hasCycleDirected(cyclic)) // true
}
```

<UnderTheHood title="Why BFS finds shortest paths but DFS does not">

BFS works by expanding a **frontier** — all nodes at distance d are settled before any node at distance d+1 is enqueued. The moment you enqueue a node, you record its distance, and since it's the first time you've touched it via BFS, that distance is the minimum. No node at a shorter distance is waiting behind it in the queue — BFS's FIFO property guarantees this.

DFS, by contrast, dives arbitrarily deep along one path. It might find a path of length 10 to a node before discovering a path of length 2. The traversal order has nothing to do with distance.

**This is why BFS → unweighted shortest path; Dijkstra → weighted shortest path with non-negative weights.** Dijkstra is essentially BFS with a min-heap as the queue — instead of "nearest in hops," it greedily processes "nearest in accumulated weight." More on that in the Dijkstra section.

</UnderTheHood>

## Topological Sort

<Define term="Topological Sort">
A **topological sort** of a Directed Acyclic Graph (DAG) is a linear ordering of all nodes such that for every directed edge u→v, u appears before v in the result. It only exists when the graph has **no cycles** — a cycle means "A depends on B depends on A," which has no valid ordering. In production: your build system, package manager, and database migration runner all need topological order. Get it wrong and you compile a package before its dependency compiles, or run a migration that references a table that doesn't exist yet.
</Define>

A **topological sort** of a Directed Acyclic Graph (DAG) is an ordering of nodes such that for every directed edge u→v, u comes before v. It only exists if the graph has no cycles.

**The scenario.** Your Go module resolver needs to compile packages in dependency order. If package A imports B and C, and B imports C, then C must be compiled first, then B, then A. That ordering is a topological sort. The algorithm also doubles as cycle detection: if the graph has a cycle, no valid ordering exists and the build fails.

### Kahn's Algorithm (BFS-based, in-degree method)

**In-degree** of a node is the count of edges pointing *into* it. Nodes with in-degree 0 have no unresolved dependencies — they can go first.

The algorithm:
1. Compute in-degrees for all nodes.
2. Enqueue all nodes with in-degree 0.
3. While the queue is non-empty: dequeue a node, append it to the result, decrement the in-degree of each neighbor. If a neighbor's in-degree drops to 0, enqueue it.
4. If the result length equals V, you have a valid topological order. If not, a cycle exists.

```go
// topoSortKahn returns a topological ordering of n nodes, or nil if a cycle exists.
// g is a directed adjacency list.
func topoSortKahn(n int, g [][]int) []int {
	inDeg := make([]int, n)
	for u := range n {
		for _, v := range g[u] {
			inDeg[v]++
		}
	}

	queue := []int{}
	for u := range n {
		if inDeg[u] == 0 {
			queue = append(queue, u)
		}
	}

	result := make([]int, 0, n)
	for len(queue) > 0 {
		u := queue[0]
		queue = queue[1:]
		result = append(result, u)
		for _, v := range g[u] {
			inDeg[v]--
			if inDeg[v] == 0 {
				queue = append(queue, v)
			}
		}
	}

	if len(result) != n {
		return nil // cycle detected
	}
	return result
}
```

```go
import "fmt"

// topoSortKahn returns a topological ordering or nil on cycle.
func topoSortKahn(n int, g [][]int) []int {
	inDeg := make([]int, n)
	for u := range n {
		for _, v := range g[u] {
			inDeg[v]++
		}
	}

	queue := []int{}
	for u := range n {
		if inDeg[u] == 0 {
			queue = append(queue, u)
		}
	}

	result := make([]int, 0, n)
	for len(queue) > 0 {
		u := queue[0]
		queue = queue[1:]
		result = append(result, u)
		for _, v := range g[u] {
			inDeg[v]--
			if inDeg[v] == 0 {
				queue = append(queue, v)
			}
		}
	}

	if len(result) != n {
		return nil // cycle
	}
	return result
}

// canFinish solves LeetCode "Course Schedule" — can you finish all n courses?
func canFinish(numCourses int, prerequisites [][2]int) bool {
	g := make([][]int, numCourses)
	for _, pre := range prerequisites {
		// pre[1] must come before pre[0]
		g[pre[1]] = append(g[pre[1]], pre[0])
	}
	return topoSortKahn(numCourses, g) != nil
}

func main() {
	// DAG: 0→1, 0→2, 1→3, 2→3
	dag := [][]int{{1, 2}, {3}, {3}, {}}
	fmt.Println("Topo order:", topoSortKahn(4, dag)) // [0 1 2 3] or [0 2 1 3]

	// Cyclic: 0→1, 1→0
	cycle := [][]int{{1}, {0}}
	fmt.Println("Cycle result:", topoSortKahn(2, cycle)) // nil

	// Course schedule
	fmt.Println("Can finish [[1,0],[0,1]]:", canFinish(2, [][2]int{{1, 0}, {0, 1}})) // false
	fmt.Println("Can finish [[1,0]]:", canFinish(2, [][2]int{{1, 0}}))                 // true
}
```

</GoPlayground>

<Callout kind="note" title="DFS post-order topological sort">

An alternative to Kahn's is DFS post-order: run DFS, and after fully exploring a node (all descendants visited), push it onto a stack. Reverse the stack at the end. Both give valid topological orderings. Kahn's is preferred in interviews because it naturally surfaces the cycle (the count check) and is easier to reason about under pressure. The DFS version is elegant but the cycle detection is subtler.

</Callout>

## Union-Find (DSU)

**Disjoint Set Union** (also called Union-Find) answers one question with near-O(1) amortized speed: **do two nodes belong to the same connected component?**

**The scenario.** You're processing Kafka events that represent new "package imports" appearing live. After each event, you need to answer: "Is package X in the same compilation unit as package Y?" Union-Find lets you answer this in effectively constant time, even after thousands of merges.

### Find + Union with Path Compression + Union by Rank

Every node starts as its own "root." `find(x)` returns the root of x's component, applying **path compression** on the way back — every node on the path is attached directly to the root, flattening the tree. `union(x, y)` merges two components by **rank** (tree height) — always attaching the shorter tree under the taller one to keep the trees flat.

Together, path compression + union by rank give **amortized O(α(n))** per operation, where α is the inverse Ackermann function — effectively constant for any input size you'll ever see in practice.

```go
type DSU struct {
	parent []int
	rank   []int
}

func newDSU(n int) *DSU {
	p := make([]int, n)
	for i := range p {
		p[i] = i // each node is its own parent
	}
	return &DSU{parent: p, rank: make([]int, n)}
}

// find returns the root of x's component, with path compression.
func (d *DSU) find(x int) int {
	if d.parent[x] != x {
		d.parent[x] = d.find(d.parent[x]) // path compression
	}
	return d.parent[x]
}

// union merges the components of x and y. Returns false if already same.
func (d *DSU) union(x, y int) bool {
	px, py := d.find(x), d.find(y)
	if px == py {
		return false
	}
	// union by rank
	switch {
	case d.rank[px] < d.rank[py]:
		d.parent[px] = py
	case d.rank[px] > d.rank[py]:
		d.parent[py] = px
	default:
		d.parent[py] = px
		d.rank[px]++
	}
	return true
}
```

```go
	fmt.Println("Redundant edge:", red) // [2 3]
```

<UnderTheHood title="Why path compression gives near-constant amortized time">

Without any optimization, `find` could traverse a chain of n nodes — O(n) worst case if every union makes a linked list. **Path compression** flattens that chain: every node encountered during `find` is re-attached directly to the root. The next `find` on any of those nodes is O(1).

**Union by rank** prevents the chain from forming in the first place. The rank is an upper bound on the tree height. By always merging the shorter tree under the taller one, the maximum height grows only as log(n). With both optimizations, the amortized cost per operation is O(α(n)) — the inverse Ackermann function. For any realistic n (up to 10^80), α(n) ≤ 4. It's effectively constant.

As of Go 1.24, there is no `sync.Map`-backed or concurrent DSU in the standard library. For concurrent union-find you'd need locks around `find` and `union` — typically a global `sync.RWMutex` protecting the arrays, or a lock-free design using `sync/atomic` on the parent array (complex; stick to single-threaded in interviews).

</UnderTheHood>

## Dijkstra

<Define term="Dijkstra — weighted shortest path">
Dijkstra's algorithm finds the shortest path from a source node to every reachable node in a **weighted graph with non-negative edge weights**. It is BFS with a min-heap (priority queue) replacing the plain FIFO queue — instead of "fewest hops," it greedily processes "lowest accumulated cost." The crucial constraint: **all edge weights must be non-negative**. One negative edge breaks the greedy assumption and silently produces wrong answers. In production: route optimisation (cheapest transfer corridor between settlement banks), network latency modelling, CDN path selection. Use BFS when edges are unweighted; Bellman-Ford when weights can be negative.
</Define>

Dijkstra's algorithm finds the shortest path from a source to all nodes in a **weighted graph with non-negative weights**. It's BFS with a **min-heap** instead of a plain queue — each time you pull the next node, it's the globally closest unvisited node.

**The scenario.** Your package manager needs to minimize the total "download cost" (bandwidth × latency weighted by file size) to install a set of dependencies. The dependency graph is weighted. BFS gives you hop counts; Dijkstra gives you minimum weighted cost.

### The Algorithm

1. Initialize `dist[src] = 0`, all others `= ∞`. Push `(0, src)` onto a min-heap.
2. While the heap is non-empty: pop the node u with the smallest tentative distance.
3. If `dist[u]` has already been finalized (we've popped u before with a smaller dist), skip — this is a stale entry.
4. For each neighbor v of u: if `dist[u] + weight(u,v) < dist[v]`, **relax** the edge — update `dist[v]` and push `(dist[v], v)` onto the heap.
5. Repeat until heap is empty. `dist` holds the shortest path from src to every reachable node.

**Complexity:** O((V + E) log V) with a binary min-heap.

In Go, Dijkstra uses `container/heap` — the same heap interface covered in the heaps chapter. Review it there if the interface is unfamiliar.

```go
package main

import (
	"container/heap"
	"fmt"
	"math"
)

// Edge is a weighted directed edge.
type Edge struct {
	To, Weight int
}

// Item is a min-heap element: (cost, node).
type Item struct {
	cost, node int
}

type MinHeap []Item

func (h MinHeap) Len() int            { return len(h) }
func (h MinHeap) Less(i, j int) bool  { return h[i].cost < h[j].cost }
func (h MinHeap) Swap(i, j int)       { h[i], h[j] = h[j], h[i] }
func (h *MinHeap) Push(x any)         { *h = append(*h, x.(Item)) }
func (h *MinHeap) Pop() any {
	old := *h
	n := len(old)
	x := old[n-1]
	*h = old[:n-1]
	return x
}

// dijkstra returns shortest distances from src; math.MaxInt means unreachable.
func dijkstra(g [][]Edge, src int) []int {
	dist := make([]int, len(g))
	for i := range dist {
		dist[i] = math.MaxInt
	}
	dist[src] = 0

	h := &MinHeap{{cost: 0, node: src}}
	heap.Init(h)

	for h.Len() > 0 {
		cur := heap.Pop(h).(Item)
		u, cost := cur.node, cur.cost

		if cost > dist[u] {
			continue // stale entry
		}
		for _, e := range g[u] {
			if next := dist[u] + e.Weight; next < dist[e.To] {
				dist[e.To] = next
				heap.Push(h, Item{cost: next, node: e.To})
			}
		}
	}
	return dist
}

func main() {
	// 4-node graph: 0→1 (2), 0→2 (5), 1→3 (1), 2→3 (3)
	g := [][]Edge{
		{{To: 1, Weight: 2}, {To: 2, Weight: 5}},
		{{To: 3, Weight: 1}},
		{{To: 3, Weight: 3}},
		{},
	}
	dist := dijkstra(g, 0)
	fmt.Println("Shortest distances from 0:", dist)
	// [0 2 5 3]
}
```

<Callout kind="warn" title="When NOT to use Dijkstra">

Dijkstra requires **non-negative edge weights**. A single negative edge breaks the greedy assumption — once you pop a node as "settled," a cheaper path via a negative edge might exist. For **negative weights**, use **Bellman-Ford** (O(VE), can detect negative cycles). For **unweighted graphs**, use **BFS** (O(V+E), conceptually simpler and faster). For **very dense graphs**, Dijkstra with a Fibonacci heap is O(E + V log V), but the Go stdlib has no Fibonacci heap — use the binary heap version (above) in all interviews.

</Callout>

<ConceptGrid cols={2}>
  <ConceptCard label="BFS vs Dijkstra">BFS for unweighted shortest paths (O(V+E)). Dijkstra for weighted non-negative (O((V+E) log V)). Same mental model; different priority queue.</ConceptCard>
  <ConceptCard label="Dijkstra vs Bellman-Ford">Dijkstra is faster but requires non-negative weights. Bellman-Ford handles negative weights and detects negative cycles, at O(VE) cost.</ConceptCard>
  <ConceptCard label="Stale entries">Dijkstra with a lazy heap may push the same node multiple times. The `if cost > dist[u] { continue }` guard skips stale pops. This is correct and avoids a decrease-key operation.</ConceptCard>
  <Gotcha>Dijkstra on a graph with a negative edge silently produces wrong answers — no panic, no error. Always confirm edge weights are non-negative before reaching for Dijkstra.</Gotcha>
</ConceptGrid>

<UnderTheHood title="Why Go's container/heap is clunky — and why you use it anyway">

Go's `container/heap` requires you to implement a 5-method interface on your own slice type. There's no generic `heap.New[T]` in the standard library (as of Go 1.24 — this is a known gap). The pattern is: define your slice type, implement `Len`, `Less`, `Swap`, `Push`, `Pop`, call `heap.Init`, then `heap.Push`/`heap.Pop` with the package-level functions that call your methods via interface dispatch.

Why interface dispatch instead of generics? The `container/heap` package predates Go generics (it's been there since Go 1.0). The `Less` method is the only way to inject a custom ordering. A future generic heap is on the Go team's radar, but as of 1.24 it hasn't landed. `golang.org/x/exp/heap` exists experimentally; don't use it in interviews.

The practical consequence: in a Dijkstra implementation, your `Less` method controls whether you have a min-heap (return `h[i].cost < h[j].cost`) or max-heap. Getting `Less` backwards produces a max-heap Dijkstra that processes the *farthest* node first — it'll run without error and produce completely wrong distances. Double-check `Less`.

</UnderTheHood>

<Exercise n={1} title="BFS shortest path in an unweighted graph" level="easy">

Given an unweighted undirected graph as `[][]int` and a source node, write `shortestPath(g [][]int, src, dst int) int` that returns the minimum hop count from `src` to `dst`, or `-1` if unreachable. Test with a 6-node graph where node 5 is unreachable.

<Solution>

```go
package main

import "fmt"

func shortestPath(g [][]int, src, dst int) int {
	if src == dst {
		return 0
	}
	dist := make([]int, len(g))
	for i := range dist {
		dist[i] = -1
	}
	dist[src] = 0
	queue := []int{src}

	for len(queue) > 0 {
		u := queue[0]
		queue = queue[1:]
		for _, v := range g[u] {
			if dist[v] == -1 {
				dist[v] = dist[u] + 1
				if v == dst {
					return dist[v]
				}
				queue = append(queue, v)
			}
		}
	}
	return -1
}

func main() {
	g := [][]int{{1, 2}, {0, 3}, {0, 3}, {1, 2, 4}, {3}, {}} // node 5 isolated
	fmt.Println(shortestPath(g, 0, 4)) // 3
	fmt.Println(shortestPath(g, 0, 5)) // -1
}
```

Early return when `v == dst` avoids exploring the full graph when you only need one destination — an optimization that matters on large graphs.

```go
package main

import "fmt"

type DSU struct {
	parent, rank []int
}

func newDSU(n int) *DSU {
	p := make([]int, n)
	for i := range p {
		p[i] = i
	}
	return &DSU{parent: p, rank: make([]int, n)}

func (d *DSU) find(x int) int {
	if d.parent[x] != x {
		d.parent[x] = d.find(d.parent[x])
	}
	return d.parent[x]

func (d *DSU) union(x, y int) bool {
	px, py := d.find(x), d.find(y)
	if px == py {
		return false
	}
	if d.rank[px] < d.rank[py] {
		d.parent[px] = py
	} else if d.rank[px] > d.rank[py] {
		d.parent[py] = px
	} else {
		d.parent[py] = px
		d.rank[px]++
	}
	return true
}

	d := newDSU(n)
	comps := n
	for _, e := range edges {
		if d.union(e[0], e[1]) {
			comps--
		}
	}
	return comps
}

	fmt.Println(countComponents(5, [][2]int{{0, 1}, {1, 2}, {2, 3}, {3, 4}})) // 1
```

<Exercise n={3} title="Course schedule II — return the order" level="medium">

```go
package main

import "fmt"

func findOrder(numCourses int, prerequisites [][2]int) []int {
	g := make([][]int, numCourses)
	inDeg := make([]int, numCourses)

	for _, pre := range prerequisites {
		course, prereq := pre[0], pre[1]
		g[prereq] = append(g[prereq], course)
		inDeg[course]++
	}

	queue := []int{}
	for i := range numCourses {
		if inDeg[i] == 0 {
			queue = append(queue, i)
		}
	}

	result := make([]int, 0, numCourses)
	for len(queue) > 0 {
		u := queue[0]
		queue = queue[1:]
		result = append(result, u)
		for _, v := range g[u] {
			inDeg[v]--
			if inDeg[v] == 0 {
				queue = append(queue, v)
			}
		}
	}

	if len(result) != numCourses {
		return []int{} // cycle
	}
	return result
}
```

<Exercise n={4} title="Dijkstra — cheapest flights within K stops" level="hard">

You have `n` cities, a list of `[from, to, price]` flights, and you start at city `src` with destination `dst`. Find the cheapest price using **at most `k` stops** (k+1 edges). Return `-1` if unreachable. Use a modified Dijkstra or BFS with a cost+stops state.

<Solution>

```go
package main

import (
	"container/heap"
	"fmt"
	"math"
)

type State struct{ cost, node, stops int }
type PQ []State

func (h PQ) Len() int            { return len(h) }
func (h PQ) Less(i, j int) bool  { return h[i].cost < h[j].cost }
func (h PQ) Swap(i, j int)       { h[i], h[j] = h[j], h[i] }
func (h *PQ) Push(x any)         { *h = append(*h, x.(State)) }
func (h *PQ) Pop() any {
	old := *h
	n := len(old)
	x := old[n-1]
	*h = old[:n-1]
	return x
}

func findCheapestPrice(n int, flights [][3]int, src, dst, k int) int {
	g := make([][][2]int, n)
	for _, f := range flights {
		g[f[0]] = append(g[f[0]], [2]int{f[1], f[2]})
	}

	// dist[node][stops] — minimum cost to reach node in exactly `stops` stops
	dist := make([][]int, n)
	for i := range dist {
		dist[i] = make([]int, k+2)
		for j := range dist[i] {
			dist[i][j] = math.MaxInt
		}
	}
	dist[src][0] = 0

	h := &PQ{{cost: 0, node: src, stops: 0}}
	heap.Init(h)

	for h.Len() > 0 {
		cur := heap.Pop(h).(State)
		if cur.node == dst {
			return cur.cost
		}
		if cur.stops > k {
			continue
		}
		for _, e := range g[cur.node] {
			to, price := e[0], e[1]
			nextCost := cur.cost + price
			nextStops := cur.stops + 1
			if nextCost < dist[to][nextStops] {
				dist[to][nextStops] = nextCost
				heap.Push(h, State{cost: nextCost, node: to, stops: nextStops})
			}
		}
	}
	return -1
}

func main() {
	flights := [][3]int{{0, 1, 100}, {1, 2, 100}, {0, 2, 500}}
	fmt.Println(findCheapestPrice(3, flights, 0, 2, 1)) // 200
	fmt.Println(findCheapestPrice(3, flights, 0, 2, 0)) // 500
}
```

The trick: the state is `(cost, node, stops)`. The stop count prevents pruning valid paths that are more expensive but use fewer stops — we can't skip them because they enable future cheaper paths. The first time `dst` is popped from the min-heap, that's the answer.

</Solution>

</Exercise>

<Exercise n={5} title="Word ladder — BFS on an implicit graph" level="hard">

Given `beginWord`, `endWord`, and a `wordList`, find the length of the shortest transformation sequence from `beginWord` to `endWord`, changing one letter at a time. Each intermediate word must be in `wordList`. Return 0 if no sequence exists.

<Solution>

```go
package main

import "fmt"

func ladderLength(beginWord, endWord string, wordList []string) int {
	wordSet := make(map[string]bool, len(wordList))
	for _, w := range wordList {
		wordSet[w] = true
	}
	if !wordSet[endWord] {
		return 0
	}

	queue := []string{beginWord}
	visited := map[string]bool{beginWord: true}
	depth := 1

	for len(queue) > 0 {
		nextQueue := []string{}
		for _, word := range queue {
			bs := []byte(word)
			for i := range bs {
				orig := bs[i]
				for c := byte('a'); c <= byte('z'); c++ {
					if c == orig {
						continue
					}
					bs[i] = c
					next := string(bs)
					if next == endWord {
						return depth + 1
					}
					if wordSet[next] && !visited[next] {
						visited[next] = true
						nextQueue = append(nextQueue, next)
					}
					bs[i] = orig
				}
			}
		}
		queue = nextQueue
		depth++
	}
	return 0
}

func main() {
	words := []string{"hot", "dot", "dog", "lot", "log", "cog"}
	fmt.Println(ladderLength("hit", "cog", words)) // 5
}
```

The graph is implicit — nodes are words, edges connect words differing by one letter. BFS on this implicit graph finds the shortest transformation. Building the graph explicitly would cost O(N²·L); mutating a byte slice per character position is O(N·L·26) — far better.

</Solution>

<Recap>

Five algorithms. Five patterns. Here's the one-paragraph version I expect you to recite in your sleep:

- **Adjacency list** (`[][]int` or `[][]Edge`) is the default graph representation. O(V+E) space. Use `map[int][]int` when node IDs are non-contiguous.
- **BFS** explores level by level. Use it for **unweighted shortest paths** and connected-component problems. O(V+E).
- **DFS** dives deep before backtracking. Use it for **cycle detection** (three-color state for directed, parent-skip for undirected), **connected components**, and **topological sort** (post-order). O(V+E).
- **Topological sort** (Kahn's algorithm) orders a DAG by repeatedly removing zero-in-degree nodes. Cycle detection is built in — if the result is shorter than V, a cycle exists. O(V+E).
- **Union-Find (DSU)** with path compression + union by rank answers "same component?" in amortized O(α(n)) ≈ O(1). Use for dynamic connectivity, redundant connections, and Kruskal's MST.
- **Dijkstra** finds shortest weighted paths on graphs with **non-negative weights** using a min-heap. O((V+E) log V). For negative weights, use Bellman-Ford. For unweighted, use BFS.
- **When to use which:** unweighted shortest path → BFS; weighted non-negative → Dijkstra; negative weights or negative-cycle detection → Bellman-Ford; ordering a DAG → topo sort; dynamic connectivity → union-find.

</Recap>
