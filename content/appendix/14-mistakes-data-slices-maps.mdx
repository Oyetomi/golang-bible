## Numbers

Three quick traps before the slices. **Integer overflow** (#18): Go's fixed-width integers *wrap* silently — no panic. **Float imprecision** (#19): binary floats can't represent most decimals exactly. And **octal literals** (#17): a leading `0` means octal, so `0o600`/`0600` is 384, not 600.

<GoPlayground>

```go
package main

import (
	"fmt"
	"math"
)

func main() {
	var n int8 = math.MaxInt8        // 127
	n++                              // wraps silently — no panic
	fmt.Println("int8 127 + 1 =", n) // -128

	fmt.Println("0.1 + 0.2 =", 0.1+0.2)     // 0.30000000000000004
	fmt.Println("== 0.3 ?", 0.1+0.2 == 0.3) // false — never compare floats with ==

	const perms = 0o600                      // octal literal
	fmt.Println("0o600 as decimal =", perms) // 384
}
```

</GoPlayground>

<Callout kind="warn" title="This is why money is never a float">

`0.1 + 0.2 != 0.3` is not a Go bug — it's how IEEE-754 binary floating point works in every language. For a ledger, that imprecision is *catastrophic*: fractions of a cent drift, and the books stop balancing. The rule, shouted throughout Part 3: **represent money as integer minor units** (cents, kobo) in `int64`, or a decimal library — never `float64`. And when you do arithmetic on user-supplied integers (a transfer amount × a quantity), check for overflow on the way in. See [Representing Money — Never Use Floats](/part-3/representing-money).

</Callout>

## Length & Capacity

The foundation for everything that follows. A slice is not an array — it's a small **header** describing a window onto one.

<Define term="Slice length vs capacity" since="Go Mistakes (Appendix)">
A slice header is three words: a **pointer** to a backing array, a **length** (how many elements you can index, `len`), and a **capacity** (how many elements exist from the pointer to the end of the backing array, `cap`). Why it matters: `len` is what you iterate; `cap` is the spare room `append` can fill **without allocating**. When `append` fits within `cap`, it writes **in place** into the shared array (fast — but it can clobber another slice viewing the same array). When it exceeds `cap`, it **allocates a new array** and copies. Almost every slice bug comes from not tracking `cap`.
</Define>

A related efficiency mistake (#21) is growing a slice from empty when you know the size: preallocate with `make([]T, 0, n)` so `append` doesn't reallocate-and-copy repeatedly as it grows.

<BeforeAfter
  bad={`// Grows from cap 0; append reallocates the
// backing array several times as it doubles.
func amounts(txs []Tx) []int64 {
  var out []int64
  for _, t := range txs {
    out = append(out, t.Cents)
  }
  return out
}`}
  good={`// Preallocate len 0, cap len(txs): one alloc,
// no reallocation during the loop.
func amounts(txs []Tx) []int64 {
  out := make([]int64, 0, len(txs))
  for _, t := range txs {

  }

  goodLabel="Preallocate cap (one alloc)"

## nil vs Empty

A `nil` slice and an empty slice both have length 0, but they are *not* identical — and confusing them causes JSON bugs and pointless `nil` checks.

<ConceptGrid cols={2}>
  <ConceptCard label="nil slice (`var s []int`)">Pointer is nil, len 0, cap 0. Marshals to JSON `null`. Perfectly usable — you can `append` to it, `range` it, take its `len`.</ConceptCard>
  <ConceptCard label="empty slice (`[]int{}` or `make([]int, 0)`)">Non-nil pointer, len 0, cap 0. Marshals to JSON `[]`. Behaves the same for `len`/`range`/`append`.</ConceptCard>
  <Gotcha>⚠ Check emptiness with `len(s) == 0`, **never** `s == nil` — an empty-but-non-nil slice is also "empty," and `s == nil` would miss it.</Gotcha>
</ConceptGrid>

<GoPlayground>

```go
package main

import (
	"encoding/json"
	"fmt"
)

func main() {
	var nilSlice []int    // nil:     len 0, cap 0
	emptySlice := []int{} // non-nil: len 0, cap 0

	fmt.Println("nilSlice == nil  :", nilSlice == nil)                            // true
	fmt.Println("emptySlice == nil:", emptySlice == nil)                          // false
	fmt.Println("both empty?      :", len(nilSlice) == 0 && len(emptySlice) == 0) // true

	a, _ := json.Marshal(nilSlice)
	b, _ := json.Marshal(emptySlice)
	fmt.Printf("nil -> %s, empty -> %s\n", a, b) // null vs []
	// Lesson: test len(s)==0 for "is it empty"; choose nil vs []T{} for the JSON you want.
}
```

</GoPlayground>

## Append & Aliasing

The big one. Because `append` reuses spare capacity **in place**, appending to a slice that shares a backing array with another slice can **silently overwrite** the other's elements.

<GoPlayground>

```go
package main

import "fmt"

func main() {
	all := []int64{10, 20, 30, 40} // ledger amounts; len 4, cap 4

	// Take the first two as a batch. It SHARES all's backing array: len 2, cap 4.
	batch := all[:2]
	fmt.Printf("batch len=%d cap=%d\n", len(batch), cap(batch)) // len 2 cap 4

	// append has spare capacity (cap 4 > len 2), so it writes IN PLACE at index 2,
	// clobbering all[2]!
	batch = append(batch, 99)
	fmt.Println("batch:", batch) // [10 20 99]
	fmt.Println("all:  ", all)   // [10 20 99 40] — all[2] was overwritten!

	// FIX: full slice expression all[:2:2] caps the batch at 2, so append must
	// allocate a fresh array and can't touch `all`.
	all2 := []int64{10, 20, 30, 40}
	safe := all2[:2:2] // len 2, cap 2
	safe = append(safe, 99)
	fmt.Println("safe:", safe) // [10 20 99]
	fmt.Println("all2:", all2) // [10 20 30 40] — untouched
}
```

And **#24, copying correctly**: `copy(dst, src)` copies only `min(len(dst), len(src))` elements — so copying into a `nil` or too-short `dst` silently copies *nothing* or fewer than you think. Size the destination: `dst := make([]T, len(src))`.

## Memory Leaks

Slices and maps both pin memory in non-obvious ways.

<Define term="Slice capacity leak" since="Go Mistakes (Appendix)">
Re-slicing keeps the **entire backing array** alive, even if your slice views only a few elements — because the slice header still points into that array, the garbage collector can't free it. So returning `huge[:3]` from a function **pins all of `huge`** in memory. Why it matters: a long-lived small slice carved from a short-lived huge buffer leaks the whole buffer. Fix: **copy** the few elements you need into a right-sized slice (`out := make([]T, n); copy(out, huge)`), so the big array becomes collectible. The same applies to substrings (a substring shares the original string's bytes — covered next chapter).
</Define>

<GoPlayground>

```go
package main

import "fmt"

// Returns a 3-element view of a 1MB buffer. The view's pointer keeps the WHOLE
// 1MB array alive — it can't be garbage collected while `leak` exists.
func head(huge []byte) []byte { return huge[:3] }

// Copy into a right-sized slice; now the 1MB array is freeable.
func headCopy(huge []byte) []byte {
	out := make([]byte, 3)
	copy(out, huge)
	return out
}

func main() {
	huge := make([]byte, 1_000_000)
	leak := head(huge)
	safe := headCopy(huge)
	fmt.Printf("leak: len=%d cap=%d  (pins ~1MB)\n", len(leak), cap(leak))
	fmt.Printf("safe: len=%d cap=%d  (~1MB freeable)\n", len(safe), cap(safe))
}
```

</GoPlayground>

Maps have their own leak (#28): deleting entries does **not** shrink a map's internal storage back to its small form. If a map grows to a million entries and you delete all but ten, it can still retain storage sized for the high-water mark. If you have a map that spikes huge then shrinks, periodically **recreate** it (copy the survivors into a fresh map) to actually release memory.

<ConceptGrid cols={2}>
  <ConceptCard label="Slice leak">A small re-slice pins the whole backing array. Copy out the elements you keep. Watch for this when caching a few bytes/items carved from a large buffer or response.</ConceptCard>
  <ConceptCard label="Map leak">`delete` removes entries but does not compact a map's internal storage. A map that ballooned can stay big. Rebuild a fresh map from the survivors to reclaim it.</ConceptCard>
</ConceptGrid>

## Maps & Comparisons

Two more. **Map initialization** (#27): like slices, give `make(map[K]V, hint)` a size hint when you know roughly how many entries you'll add, to avoid repeated rehashing as it grows. And **comparing values** (#29): `==` works on comparable types (numbers, strings, booleans, pointers, and structs/arrays of comparable fields) but **does not compile** for slices, maps, or functions.

<GoPlayground>

```go
package main

import (
	"fmt"
	"reflect"
	"slices"
)

type Money struct {
	Cents    int64
	Currency string
}

func main() {
	a := Money{4999, "USD"}
	b := Money{4999, "USD"}
	fmt.Println("structs via == :", a == b) // true — all fields comparable

	x := []int{1, 2, 3}
	y := []int{1, 2, 3}
	// fmt.Println(x == y) // COMPILE ERROR: slices are not comparable
	fmt.Println("slices via slices.Equal :", slices.Equal(x, y))      // true (fast, typed)
	fmt.Println("slices via DeepEqual    :", reflect.DeepEqual(x, y)) // true (reflection)
}
```

</GoPlayground>

<UnderTheHood title="The slice header, how append grows, and why maps don't shrink">

A slice value is literally a 3-word struct — `{ptr *T, len int, cap int}` — passed by value (so a slice argument is a *copy of the header* sharing the *same* backing array; that's why a function can mutate your elements but not your length). When `append` exceeds `cap`, the runtime allocates a bigger array: historically it **doubled** capacity for small slices and grew by ~**1.25×** once large (the exact threshold has shifted across versions; don't rely on a specific factor — rely on preallocating). That growth-and-copy is why `make([]T, 0, n)` matters in a hot loop.

Maps are hash tables; deleting entries removes mappings but does not compact the map's internal storage back to its small form, so a map can retain memory sized for its high-water mark — hence the "rebuild to reclaim" trick. As of Go 1.21+, prefer the `slices` and `maps` packages (`slices.Equal`, `slices.Contains`, `maps.Clone`) over hand-rolled loops and `reflect.DeepEqual` — they're type-safe and far faster (no reflection). Reserve `reflect.DeepEqual` for comparing nested heterogeneous structures in tests. See [Data Semantics & Data-Oriented Design](/part-1/data-semantics).

</UnderTheHood>

## Exercises

<Exercise n={1} title="Stop the aliasing" level="medium">

`window(s, n)` should return the first `n` elements as a slice that callers can `append` to **without** corrupting `s`. Write it.

<Solution>

```go
func window[T any](s []T, n int) []T {
	return s[:n:n] // full slice expression: len n, cap n
}
```

The third index in `s[:n:n]` sets the capacity to `n`, equal to the length. Now the returned slice has *no* spare capacity, so the caller's first `append` must allocate a brand-new backing array and copy — it can never reach back into `s`. (Equivalently, `out := make([]T, n); copy(out, s)` returns a fully independent copy.) Without the cap, the returned slice inherits `s`'s capacity and an append clobbers `s`'s tail.

</Solution>

</Exercise>

<Exercise n={2} title="Release the big array" level="medium">

`firstID(resp []byte)` returns the first 8 bytes of a 2 MB response but must not pin the whole buffer. Fix the leak.

<Solution>

```go
func firstID(resp []byte) []byte {
	out := make([]byte, 8)
	copy(out, resp) // copy the 8 bytes into an independent slice
	return out
}
// NOT: return resp[:8]  — that keeps the entire 2MB backing array alive
// for as long as the returned slice is reachable.
```

`resp[:8]` shares `resp`'s backing array, so the garbage collector can't free the 2 MB while your 8-byte slice lives. Copying the 8 bytes into a fresh `make([]byte, 8)` severs the link to the big buffer, which then becomes collectible. This matters whenever you keep a small piece of a large, transient allocation (a header from a big HTTP body, an ID from a big row).

</Solution>

</Exercise>

<Exercise n={3} title="nil or empty?" level="easy">

Write `isEmpty(s []int) bool` that is correct for both nil and non-nil empty slices, and say which one you'd return from a JSON API and why.

<Solution>

```go
func isEmpty(s []int) bool { return len(s) == 0 }
```

`len(s) == 0` is true for both a nil slice and a non-nil empty slice — the only correct emptiness test (`s == nil` would wrongly report a non-nil empty slice as "not empty"). For a JSON API, return a **non-nil empty slice** (`[]int{}`) so the field serializes to `[]` rather than `null`, which is what array-expecting clients want. Use nil internally where you don't care; choose deliberately at the serialization boundary.

</Solution>

</Exercise>

<Exercise n={4} title="Reclaim map memory" level="medium">

A `sessions map[string]Session` spiked to millions of entries during an incident and is now nearly empty but still huge. Write `compact(m)` that returns a fresh map with the same contents so the old internal storage can be freed.

<Solution>

```go
func compact(m map[string]Session) map[string]Session {
	out := make(map[string]Session, len(m))
	for k, v := range m {
		out[k] = v
	}
	return out
}
// Replace the old map with compact(old); once the old map is unreachable,
// its oversized internal storage is collected. delete() alone does not compact it.
```

A Go map does not compact its internal storage just because entries were deleted, so deleting entries can leave the high-water-mark allocation in place. Copying the survivors into a freshly `make`'d map (sized to the current count) and dropping the reference to the old one lets the GC reclaim the oversized storage. Do this deliberately for maps with a spiky size profile — not on every delete.

</Solution>

</Exercise>

<Exercise n={5} title="Compare the right way" level="easy">

You need to compare two `[]string` for equality and two `Point{X, Y int}` structs. Which tool for each, and why can't you use `==` on the slices?

<Solution>

```go
// Structs of comparable fields: == works and is idiomatic.
equalPoints := p1 == p2

// Slices are NOT comparable with == (compile error). Use slices.Equal:
equalTags := slices.Equal(a, b) // Go 1.21+, typed and fast
```

`==` is defined for structs whose fields are all comparable (here two `int`s), so `p1 == p2` compiles and compares field-by-field. Slices, maps, and functions are *not* comparable with `==` (only against `nil`) because equality would have to be deep and is ambiguous — so the compiler rejects `a == b` for slices. Use `slices.Equal` (preferred, type-safe, no reflection) or `reflect.DeepEqual` (general but slow) for element-wise slice comparison.

</Solution>

</Exercise>

<Recap>

The data-type mistakes that lose or corrupt data:

- **Numbers**: integers **overflow silently** (wrap, no panic) — check on untrusted input; **floats** can't represent decimals exactly (`0.1+0.2 != 0.3`) — **money is `int64` minor units, never float**; a leading `0` is **octal**.
- **Slices are headers** (ptr, len, **cap**). `len` is what you index; `cap` is spare room `append` fills **in place**. Preallocate `make([]T, 0, n)` when you know the size.
- **nil vs empty**: both len 0, but nil marshals to `null` and empty to `[]`. Test emptiness with `len(s) == 0`, never `s == nil`; pick the right one at the JSON boundary.
- **Append aliasing** (the big one): appending to a sub-slice with spare `cap` **overwrites the shared backing array**. Isolate with a full slice expression `s[:n:n]` or a copy. `copy` only moves `min(len(dst), len(src))` — size the destination.
- **Memory leaks**: a small re-slice **pins the whole backing array** (copy out what you keep); a large map can retain high-water internal storage after deletes (rebuild a fresh map to reclaim).
- **Maps & comparisons**: size maps with `make(map[K]V, hint)`. `==` works on comparable structs but **not slices/maps/funcs** — use `slices.Equal` (preferred) or `reflect.DeepEqual`.
