## Concurrency vs Parallelism

Before a single channel, the two foundational confusions. People use "concurrency" and "parallelism" as synonyms. They are not, and getting this wrong is why people reach for goroutines that make their code *slower*.

<Define term="Concurrency vs parallelism" since="Go Mistakes (Appendix)">
**Concurrency** is about *structure*: dealing with many things at once — decomposing a program into independently-executing tasks (goroutines) that can make progress in overlapping time windows. **Parallelism** is about *execution*: doing many things at the same instant — tasks literally running on separate CPU cores. Concurrency is a design property; parallelism is a runtime property. Why it matters: concurrency *enables* parallelism but doesn't guarantee it. You can have concurrency on a single core (the scheduler interleaves goroutines), and a well-structured concurrent program will *scale* to more cores — but a badly-structured one won't, no matter how many cores you throw at it. As Rob Pike put it: concurrency is dealing with lots of things at once; parallelism is doing lots of things at once.
</Define>

The second confusion is the dangerous one for performance: **assuming concurrency is always faster** (#56). Goroutines aren't free. Each one costs a stack, scheduling overhead, and — if it communicates — synchronization. For a *small* workload, that overhead dwarfs the work, and the concurrent version loses to the plain sequential loop.

The classic demonstration is parallel merge sort. The naive "spin a goroutine for every recursive split" version is *slower* than sequential sort, because you spawn goroutines to sort two-element slices:

<ConceptGrid cols={2}>
  <ConceptCard label="Naive parallel merge sort">A goroutine per recursive call. At the leaves you're spawning goroutines to sort 1–2 elements — pure overhead. Often slower than the sequential version on real inputs.</ConceptCard>
  <Gotcha>⚠ Concurrency adds cost: stack allocation, scheduling, and synchronization. Below a threshold, it never pays for itself. Parallelize only when the *work per task* exceeds the *overhead per task*.</Gotcha>
</ConceptGrid>

The fix is a **threshold**: parallelize only the large splits, and fall back to a sequential sort once a sub-slice is small. Above the threshold the work dominates the overhead; below it, you skip the goroutine entirely.

<GoPlayground>

```go
package main

import (
	"fmt"
	"sort"
	"sync"
)

const threshold = 2048 // below this, sequential beats the goroutine overhead

func parallelSort(s []int) {
	if len(s) <= threshold {
		sort.Ints(s) // small slice: do it sequentially, no goroutine
		return
	}
	mid := len(s) / 2
	var wg sync.WaitGroup
	wg.Add(2) // Go 1.25's wg.Go(fn) bundles Add+go+Done; shown portable here
	go func() { defer wg.Done(); parallelSort(s[:mid]) }()
	go func() { defer wg.Done(); parallelSort(s[mid:]) }()
	wg.Wait()
	merge(s, mid)
}

func merge(s []int, mid int) {
	left := append([]int(nil), s[:mid]...) // copy so we don't read while writing
	right := s[mid:]
	i, j, k := 0, 0, 0
	for i < len(left) && j < len(right) {
		if left[i] <= right[j] {
			s[k] = left[i]
			i++
		} else {
			s[k] = right[j]
			j++
		}
		k++
	}
	for i < len(left) {
		s[k] = left[i]
		i, k = i+1, k+1
	}
}

func main() {
	data := []int{9, 3, 7, 1, 8, 2, 6, 4, 5, 0}
	parallelSort(data)
	fmt.Println(data) // sorted; this tiny input stays sequential (< threshold)
}
```

</GoPlayground>

<Callout kind="warn" title="#59 — match the goroutine count to the workload type">

How many goroutines you should run depends on whether the work is **CPU-bound** or **I/O-bound**.

- **CPU-bound** (hashing, sorting, crypto): the work *is* the CPU. More goroutines than cores just adds context-switching. Bound your worker pool to `GOMAXPROCS` (whose Go 1.25+ default considers logical CPUs, CPU affinity, and Linux cgroup CPU quota — see Under the Hood).
- **I/O-bound** (calling Meridian's payment processor, querying Postgres, reading a socket): each goroutine spends most of its life *blocked*, not computing. The scheduler parks blocked goroutines for free, so you can run *thousands* — the limit is set by the external system (connection pool size, downstream rate limits), not the CPU count.

The mistake is using one number for both: a 4-goroutine pool throttles 10,000 concurrent I/O calls to a crawl, and a 10,000-goroutine pool for CPU work thrashes the scheduler. See [Concurrency Patterns](/part-2/concurrency-patterns).

</Callout>

## Races & the Memory Model

The heart of the chapter. Two terms people use interchangeably — and they are *not* the same bug.

<Define term="Data race vs race condition" since="Go Mistakes (Appendix)">
A **data race** occurs when two or more goroutines access the *same* memory location *concurrently*, at least one access is a *write*, and there's no synchronization ordering the accesses. Data races are serious program errors: Go may report the race and terminate, and otherwise the memory model gives only limited guarantees about what a racing read may observe. A **race condition** is broader: the program's *correctness* depends on the relative *timing* or *interleaving* of goroutines, even if every individual access is properly synchronized. Why it matters: you can eliminate every data race (lock everything) and *still* have a race condition (the lost-update bug from the Scene — each access is atomic, but the read-modify-write as a whole isn't). Fixing data races is mechanical (synchronize). Fixing race conditions requires thinking about *which interleavings are valid*.
</Define>

Here's the lost-update race condition as an interleaving. Both goroutines synchronize each individual read and write — there's no *data* race — yet the result is still wrong, because the read and the write aren't atomic *together*:

Now the load-bearing point most people miss: **why** is the unsynchronized version undefined and not just "sometimes wrong"? Because of the **Go memory model**.

<Define term="The Go memory model & happens-before" since="Go Mistakes (Appendix)">
The **Go memory model** specifies when a read of a variable in one goroutine is *guaranteed* to observe a write from another goroutine. The key relation is **happens-before**: if event A happens-before event B, then B is guaranteed to see A's effects. Within a single goroutine, happens-before is just program order. *Across* goroutines, you only get a happens-before edge from an explicit synchronization: a channel send happens-before the corresponding receive completes; a `sync.Mutex` Unlock happens-before a later Lock; `wg.Done` happens-before a `wg.Wait` that it releases; the start of a goroutine happens-before its body runs. Why it matters: with **no** happens-before edge between a write and a read, the read may see the old value, a partially-written value, or nothing — *even on x86*, because the compiler and CPU are free to reorder. "It worked on my machine" means "the schedule happened to give me an order"; it is **not** a guarantee.
</Define>

The synchronized fix — a mutex makes the read-modify-write atomic, and Unlock/Lock establishes happens-before so every goroutine sees the latest balance:

<GoPlayground>

```go
package main

import (
	"fmt"
	"sync"
)

// Account guards its balance with a mutex. The mutex makes deposit's
// read-modify-write atomic AND establishes happens-before between goroutines.
type Account struct {
	mu      sync.Mutex
	balance int64 // kobo (minor units) — never a float
}

func (a *Account) Deposit(amount int64) {
	a.mu.Lock()
	a.balance += amount // read-modify-write, now atomic as a whole
	a.mu.Unlock()
}

func main() {
	acc := &Account{balance: 100_000}
	var wg sync.WaitGroup
	// 100 goroutines each deposit 1,000 — 100 * 1,000 = 100,000 added.
	for range 100 {
		wg.Add(1)
		go func() { defer wg.Done(); acc.Deposit(1_000) }()
	}
	wg.Wait()
	fmt.Println("final balance:", acc.balance) // always 200000 — never less
}
```

</GoPlayground>

Run that under `go run -race ./...` (the **race detector**) and the *unsynchronized* version lights up red; the locked version is silent. The detector is your single most important concurrency tool — wire it into CI, because a data race that doesn't fire today fires under production load tomorrow.

<Callout kind="note" title="Codapi runs plain `go run` — no -race here">

The playground runner executes `go run` without the `-race` flag, so it won't *report* a data race; it'll just print whatever value the schedule produced. That's why the snippets above are written to show the **correct deterministic result** (the locked version always prints 200000). To actually *catch* races, run locally with `-race`. Every concurrency snippet in this chapter is built to terminate cleanly under plain `go run` — the teaching is in the result and the timelines, not in the detector firing.

</Callout>

### #57 — channels or mutexes?

Both synchronize. Choosing wrong makes code awkward, not incorrect — but the awkwardness compounds. The rule of thumb:

<ConceptGrid cols={2}>
  <ConceptCard label="Mutex — guard shared state">Use a `sync.Mutex` (or `RWMutex`) when goroutines access **shared memory in place**: a counter, a cache map, a balance. The data stays put; you serialize access to it. Smallest, fastest tool for "many goroutines touch one struct."</ConceptCard>
  <ConceptCard label="Channel — transfer ownership / coordinate">Use a channel when you're **passing data between** goroutines, signaling, or orchestrating a pipeline/stages. "Don't communicate by sharing memory; share memory by communicating" — when the design is about *flow* and ownership handoff, a channel is clearer than locks.</ConceptCard>
  <Gotcha>⚠ A channel is not a "better mutex." Using a buffered channel of size 1 as a lock works but is slower and obscures intent. Guarding a plain field? Reach for the mutex.</Gotcha>
</ConceptGrid>

## Context & Cancellation

A `context.Context` is how Go propagates **deadlines, cancellation, and request-scoped values** across API boundaries and goroutines. Misunderstanding it (#60) and propagating the *wrong* one (#61) are two of the most common real-world concurrency bugs.

<Define term="context.Context — cancellation signal" since="Go Mistakes (Appendix)">
A **context** carries three things down a call tree: a **deadline** (cancel automatically at a time / after a duration), a **cancellation** signal (cancel manually via a `cancel` func, e.g. the client disconnected), and **request-scoped values** (a request ID, an auth subject). The cancellation arrives as a channel: `ctx.Done()` returns a receive-only channel that's *closed* when the context is cancelled or its deadline passes; `ctx.Err()` then tells you which. Why it matters: any function doing blocking work (a DB query, an HTTP call, a long loop) should take `ctx` as its **first argument** and watch `ctx.Done()`, so when the caller gives up, the work stops instead of running to completion against a client that's already gone.
</Define>

The whole point is the `select` on `ctx.Done()` — it lets a blocking operation bail out the instant the context is cancelled:

Now the subtle one — **#61, propagating an inappropriate context.** A request's context is cancelled when the request ends. So if your handler kicks off a *background* job (write to an audit log, publish a Kafka event) using the *request's* context, that job gets cancelled the moment you return the HTTP response — it dies half-done.

<Callout kind="pro" title="context.WithoutCancel (Go 1.21) — keep the values, drop the cancellation">

Before Go 1.21 you had to build a fresh `context.Background()` and manually copy over request-scoped values (request ID, trace span). `context.WithoutCancel(ctx)` does it cleanly: the returned context **keeps the parent's values** but is **never cancelled** by the parent. Perfect for "fire this off and let it finish even though the request is over." Give the background job its *own* timeout if it needs one (`context.WithTimeout(bg, 30*time.Second)`). Full treatment: [The context Package, In Depth](/part-1/context-package).

</Callout>

## Goroutine Leaks

The signature concurrency bug. Goroutines are so cheap to start that people start them without a plan for when they *stop* (#62) — and a goroutine that never stops is a leak.

<Define term="Goroutine leak" since="Go Mistakes (Appendix)">
A **goroutine leak** is a goroutine that never terminates — it's blocked forever on a channel send/receive, a mutex, or an infinite loop with no exit. Why it matters: each leaked goroutine pins its stack (minimum 2 KB, growable) *plus* every variable it references on the heap *plus* any resources it holds open — a DB connection, an HTTP body, a file. A handler that leaks one goroutine per request leaks memory and file descriptors *linearly with traffic*, until the process is OOM-killed or runs out of FDs. Leaks don't crash on the test that creates them; they crash the box hours later under load, far from the cause. Every goroutine you start must have a guaranteed exit path.
</Define>

The classic leak: a goroutine sends on an unbuffered channel, but the receiver gave up early (returned on an error, or its context was cancelled). With no one to receive, the sender blocks on that send **forever**:

Here's the leak and both fixes, made runnable. We detect the leak deterministically with a counter — no `-race` needed:

<GoPlayground>

```go
package main

import (
	"context"
	"fmt"
	"sync/atomic"
	"time"
)

var finished atomic.Int64 // counts workers that actually reached their exit

// LEAKY: sends on an unbuffered channel; if the receiver is gone, blocks forever.
func leaky(ch chan int) {
	time.Sleep(10 * time.Millisecond)
	ch <- 42        // blocks forever when nobody receives — never reaches the next line
	finished.Add(1) // unreachable in the leak case
}

// FIXED: selects on ctx.Done() so it abandons the send if the receiver gave up.
func fixed(ctx context.Context, ch chan int) {
	time.Sleep(10 * time.Millisecond)
	select {
	case ch <- 42: // delivered to a waiting receiver
	case <-ctx.Done(): // receiver gone — bail out instead of blocking forever
	}
	finished.Add(1) // always reached: either branch completes
}

func main() {
	// Leaky worker: we "give up" by never receiving. The goroutine blocks on send.
	go leaky(make(chan int))

	// Fixed worker: same "give up", but it exits via ctx.Done().
	ctx, cancel := context.WithCancel(context.Background())
	go fixed(ctx, make(chan int))
	cancel() // receiver gives up immediately

	time.Sleep(50 * time.Millisecond) // let both attempt their send
	fmt.Println("workers that reached their exit:", finished.Load())
	fmt.Println("(leaky never increments; only the ctx-aware worker exits cleanly)")
}
```

</GoPlayground>

<Callout kind="pro" title="#63 — loop variables and goroutines (the bug Go 1.22 deleted)">

For years, the most-stepped-on Go landmine was capturing a loop variable in a goroutine. Pre-1.22, the loop variable was **shared across all iterations**, so `for _, id := range ids { go func() { process(id) }() }` would have every goroutine read whatever `id` happened to be when it *ran* — usually the last value, processing the same record N times. The old fix was the `id := id` shadow inside the loop.

**As of Go 1.22, loop variables are per-iteration** — each iteration gets a fresh `id`, so the capture does the right thing and the `id := id` dance is gone. But you still meet the old pattern in pre-1.22 code and in interview questions, so know *why* it was wrong: a goroutine captures a variable by *reference*, and the old loop reused one variable. Targeting Go 1.26, you can delete the shadow. See [Concurrency: Goroutines, Channels & Select](/part-1/concurrency).

</Callout>

## Channels & select

Channels are the part everyone thinks they understand and quietly doesn't. Four mistakes that bite even experienced people.

**#64 — `select` with multiple ready channels is nondeterministic.** People write the "priority" case first and assume it wins. It doesn't: when more than one case is ready, `select` picks one via a **uniform pseudo-random selection**. Ordering the cases means nothing.

<GoPlayground>

```go
package main

import "fmt"

func main() {
	// Both channels are ready (buffered and pre-filled). One might expect the
	// "first" case to always win — it does NOT. select chooses at random.
	high := make(chan string, 1)
	low := make(chan string, 1)
	high <- "HIGH"
	low <- "low"

	counts := map[string]int{}
	for range 1000 {
		// Re-fill each round so both are always ready.
		select {
		case v := <-high:
			counts[v]++
			high <- "HIGH"
		case v := <-low:
			counts[v]++
			low <- "low"
		}
	}
	// Roughly 50/50 — proof that case order does NOT imply priority.
	fmt.Printf("HIGH picked %d times, low picked %d times\n", counts["HIGH"], counts["low"])
	fmt.Println("(near 50/50: select is uniformly random among ready cases)")
}
```

</GoPlayground>

To get real priority, you nest selects: try the high-priority channel alone first (with a `default`), then fall back to selecting on both.

**#65 — use a notification channel (`chan struct{}`) for signals with no data.** When a channel exists only to *signal* an event — "shutdown now," "this is done" — the value carried is meaningless. Don't use `chan bool` (a reader wonders: does `false` mean something?). Use the empty struct.

<Define term="Notification channel" since="Go Mistakes (Appendix)">
A **notification channel** is a channel used purely for *signaling*, carrying no data — declared `chan struct{}`. The empty struct `struct{}` occupies **zero bytes**, so the channel communicates only the *fact* of a send or, more often, a *close*. The idiom: `close(done)` to broadcast a one-time signal to every receiver at once (a closed channel is *always* receivable, immediately, for all goroutines). Why it matters: `chan struct{}` documents intent — "no payload, just a signal" — where `chan bool` invites the reader to hunt for a meaning in the value that isn't there. This is exactly what `context.Done()` returns: `<-chan struct{}`.
</Define>

**#66 — a nil channel blocks forever, and that's *useful*.** Receiving from or sending to a `nil` channel blocks the goroutine permanently. Most people learn this as a bug. The pro move: in a `select`, a `nil` channel case is *never selected* — so setting a channel variable to `nil` **disables that case** dynamically. The canonical use is merging two channels and "turning off" each one as it closes, so you don't busy-loop on a closed channel that's always ready.

**#67 — channel size: default to unbuffered.** An unbuffered channel (`make(chan T)`) is a **synchronization point** — send and receive rendezvous, giving you a happens-before guarantee. A buffered channel (`make(chan T, n)`) decouples sender and receiver up to `n` queued items. The mistake is picking a buffer size by feel.

<ConceptGrid cols={3}>
  <ConceptCard label="Unbuffered (default)">Send blocks until a receiver is ready — a rendezvous *and* a happens-before edge. Your default: it's the most synchronized and the easiest to reason about. Choose this unless you can *name* why you need a buffer.</ConceptCard>
  <ConceptCard label="Buffered = 1">A single slot. Useful to avoid a leak on a send when the receiver may have left (the worker fits its one result and exits), or for a "latest value" / signal that mustn't block the sender once.</ConceptCard>
  <ConceptCard label="Buffered = N">Only when N is a *justified* number: a worker pool of N, a known batch size, a rate-limit token bucket of N. An arbitrary `make(chan T, 100)` is a guess that hides backpressure problems until the buffer fills.</ConceptCard>
</ConceptGrid>

<Gotcha>⚠ A buffer doesn't make backpressure disappear — it *delays* it. When the buffer fills, the sender blocks anyway. A too-large buffer just means you discover the overload later, with more in-flight work to lose. Size buffers to a real quantity, not a vibe.</Gotcha>

**#68 — string-formatting side effects.** A subtle data race that bit etcd: a `String()` method (or any code in a logging/format path) that reads shared state *without* the lock can race with a writer — or, if it grabs a lock the caller *already holds*, deadlock. The lesson: methods on the formatting path must be side-effect-free and lock-aware. Don't read mutable shared state inside `String()` without synchronization.

## sync, WaitGroup & errgroup

The `sync` package and its friends. Powerful, and full of foot-shaped holes.

**#71 — misusing `sync.WaitGroup`: call `Add` in the parent, before the goroutine.** A `WaitGroup` waits for *n* operations. The classic bug is calling `wg.Add(1)` *inside* the goroutine — which races with `wg.Wait()`: if `Wait` runs before the goroutine's `Add`, the counter is still 0 and `Wait` returns immediately, before the work is done.

<BeforeAfter
  bad={`// Add(1) runs INSIDE the goroutine — it
// races with Wait(). Wait may see counter 0
// and return before the work even starts.
for range 3 {
  go func() {
    wg.Add(1)        // TOO LATE — races Wait
    defer wg.Done()
    work()
  }()
}
wg.Wait()`}
  good={`// Go 1.25: wg.Go does Add(1) in the parent
// (before the goroutine starts) and Done on
// return. No race, no manual bookkeeping.
for range 3 {
  wg.Go(func() {
    work()
  })
}
wg.Wait()`}
  badLabel="Add inside goroutine (races Wait)"
  goodLabel="wg.Go (Add before spawn)"
/>

As of Go 1.25, `wg.Go(func(){...})` is the idiom: it increments the counter **before** launching the goroutine and calls `Done` when the function returns, so the "Add too late" race is impossible by construction. The Go 1.25 `vet` `waitgroup` analyzer also flags an `Add` call inside a goroutine.

**#72 — forgetting `sync.Cond`.** Sometimes you need to *broadcast* "this condition changed" to *many* waiting goroutines, repeatedly. A channel send goes to only **one** receiver (round-robin), so it can't fan out an update to N listeners. A `close` broadcasts but only *once*. `sync.Cond` is the right tool: waiters call `Wait()` (which atomically releases the lock and sleeps), and the updater calls `Broadcast()` to wake them all.

<GoPlayground>

```go
package main

import (
	"fmt"
	"sync"
)

// Donation goal tracker: many listeners wait for the balance to cross a goal.
// sync.Cond lets the updater BROADCAST each change to all waiters at once —
// something a single channel send (one receiver) can't do.
type Donation struct {
	cond    *sync.Cond
	balance int
}

func main() {
	d := &Donation{cond: sync.NewCond(&sync.Mutex{})}
	var wg sync.WaitGroup

	listen := func(goal int) {
		d.cond.L.Lock()
		for d.balance < goal { // re-check in a loop: Wait can wake spuriously
			d.cond.Wait() // releases the lock, sleeps, re-acquires on wake
		}
		fmt.Printf("goal %d reached at balance %d\n", goal, d.balance)
		d.cond.L.Unlock()
	}
	wg.Add(2)
	go func() { defer wg.Done(); listen(10) }()
	go func() { defer wg.Done(); listen(15) }()

	// Updater: bump the balance and broadcast to every waiter.
	for range 15 {
		d.cond.L.Lock()
		d.balance++
		d.cond.L.Unlock()
		d.cond.Broadcast() // wake ALL waiters; each re-checks its goal
	}
	wg.Wait()
}
```

</GoPlayground>

**#73 — not using `errgroup`.** When you fan out N goroutines that can each fail and you want the *first* error plus automatic cancellation of the rest, hand-rolling that with a `WaitGroup` + an error channel + a context is fiddly and easy to get wrong. `golang.org/x/sync/errgroup` does exactly this: `g.Go(func() error {...})`, and `g.Wait()` returns the first non-nil error; the `errgroup.WithContext` variant cancels the shared context on the first failure so siblings stop early.

<BeforeAfter
  bad={`// Manual: WaitGroup + error channel +
// sync.Once + context, all hand-wired.
// Easy to leak or drop the first error.
var wg sync.WaitGroup
errCh := make(chan error, len(ids))
for _, id := range ids {
  wg.Go(func() {
    errCh <- fetch(ctx, id)
  })
}
wg.Wait()
close(errCh)
// ...drain errCh, find first non-nil...`}
  good={`// errgroup: first error wins, ctx cancels
// the rest, Wait returns that error.
g, ctx := errgroup.WithContext(ctx)
for _, id := range ids {
  g.Go(func() error {
    return fetch(ctx, id)
  })
}
if err := g.Wait(); err != nil {
  return err // the first failure
}`}
  badLabel="Hand-rolled fan-out"
  goodLabel="errgroup.WithContext"

**#74 — copying a `sync` type (the bug `go vet` catches).** `sync.Mutex`, `sync.WaitGroup`, `sync.Cond`, `sync.Once` and friends **must not be copied after first use** — a copy duplicates the lock's internal state, so the copy and the original are *different* locks that don't exclude each other. The trap hides in plain sight: copying a *struct that contains* a mutex (passing it by value, returning it, ranging over a slice of them) copies the lock.

<GoPlayground>

```go
package main

import (
	"fmt"
	"sync"
)

type Counter struct {
	mu sync.Mutex
	n  int
}

func (c *Counter) Inc() { // pointer receiver — operates on the original's mutex
	c.mu.Lock()
	c.n++
	c.mu.Unlock()
}

func main() {
	c := &Counter{}
	var wg sync.WaitGroup
	for range 100 {
		wg.Add(1)
		go func() { defer wg.Done(); c.Inc() }() // all share ONE Counter, ONE mutex — correct
	}
	wg.Wait()
	fmt.Println("count:", c.n) // always 100

	// The TRAP (don't do this): a value receiver, or `copy := *c`, would copy
	// the mutex. `go vet` reports: "assignment copies lock value to copy: Counter
	// contains sync.Mutex". vet catches it at build time — heed it.
}
```

</GoPlayground>

<Gotcha>⚠ Always use a **pointer receiver** on methods that lock, and pass mutex-bearing structs by **pointer**. If `go vet` says "copies lock value," you have a copied mutex — that's not a false positive, it's a real broken lock. The `copylocks` analyzer is in the default `go vet` set, so it fires on every build that runs vet.</Gotcha>

**#69 — data races with `append` on a shared slice**, and **#70 — mutexes that don't actually protect slices/maps.** Two slice-flavored races. First: a slice header copied across goroutines shares the *same backing array*, so concurrent `append`s race on that memory even though each goroutine has "its own" slice variable. Second: copying a struct that holds a mutex *and* a slice — the mutex copy doesn't exclude, and worse, the slice header copy still points at shared backing memory, so you've "locked" two different locks over one piece of data.

<ConceptGrid cols={2}>
  <ConceptCard label="#69 append races">A `[]T` value is a 3-word header over a shared array. Passing it to multiple goroutines and appending concurrently races on the backing array (and the length word). Give each goroutine its own slice, or guard the shared one with a mutex, or collect results via a channel.</ConceptCard>
  <ConceptCard label="#70 'protecting' a slice by value">A mutex guards memory only if every accessor uses the *same* mutex over the *same* memory. Copy the struct (mutex + slice header) and you get two locks over one backing array — the lock protects nothing. Keep the mutex and the data behind one pointer.</ConceptCard>
</ConceptGrid>

<UnderTheHood title="The race detector, happens-before, container-aware GOMAXPROCS, and the tools that find leaks">

**How `-race` works.** The race detector compiles in *shadow memory* and instruments every memory access and synchronization event to build a happens-before graph at runtime (the ThreadSanitizer algorithm). When it sees two accesses to the same address, at least one a write, with **no** happens-before edge between them, it reports a race with both stacks. It has near-zero false positives — if `-race` fires, you *have* a race — but it only catches races on *executed* schedules, so it's as good as your test coverage. Cost is real (≈2–20× slower, more memory), so run it in CI and load tests, not production.

**Why happens-before is the whole game.** The memory model gives the clean DRF-SC guarantee only to data-race-free programs. Synchronization edges come from channel ops, mutexes, `sync.Once`, `sync/atomic`, `wg.Wait`, and goroutine start. Absent one of those edges between a write and a read, the program has a race; the implementation may report and halt, and otherwise the read has only the limited guarantees spelled out by the memory model. "Works on x86" is meaningless; the compiler can still reorder.

**Container-aware `GOMAXPROCS` (Go 1.25).** Historically `GOMAXPROCS` defaulted to the host's logical CPU count, which was *wrong* in a container limited to, say, 2 CPUs on a 64-core node — the runtime exposed far more Ps than the container could use efficiently. The fix used to be the third-party `uber/automaxprocs`. **As of Go 1.25, the runtime considers logical CPUs, CPU affinity, and Linux cgroup CPU quota, then updates the default dynamically if those limits change** — so `automaxprocs` is no longer needed for Go 1.25+ services. Opt out with `GODEBUG=containermaxprocs=0`; override programmatically with `runtime.SetDefaultGOMAXPROCS`.

**Finding leaks.** Beyond `pprof`'s goroutine profile (`/debug/pprof/goroutine?debug=2` shows every goroutine's stack — a pile blocked on the same line is your leak), Go 1.26 ships an **experimental `goroutineleak` pprof profile** (`/debug/pprof/goroutineleak`) that reports goroutines the runtime believes are permanently blocked. For *tests*, **`testing/synctest` (Go 1.25)** runs concurrent code in a virtual-time "bubble" where the fake clock only advances when every goroutine is blocked — making timeout/cancellation tests deterministic and instant instead of flaky and slow. Deep dives: [Advanced Concurrency & Correctness](/part-2/advanced-concurrency-correctness) and [Concurrency Patterns](/part-2/concurrency-patterns).

</UnderTheHood>

<Exercise n={1} title="Lost update → atomic" level="easy">

This `Counter.Inc` has a data race and loses increments. Fix it two ways: with a `sync.Mutex`, and with `sync/atomic`.

```go
type Counter struct{ n int }
func (c *Counter) Inc() { c.n++ } // racy read-modify-write
```

<Solution>

```go
// Option A: mutex around the whole read-modify-write.
type Counter struct {
	mu sync.Mutex
	n  int
}
func (c *Counter) Inc() {
	c.mu.Lock()
	c.n++
	c.mu.Unlock()
}

// Option B: a lock-free atomic counter (simpler when you only need a counter).
type AtomicCounter struct{ n atomic.Int64 }
func (c *AtomicCounter) Inc() { c.n.Add(1) }
```

`c.n++` is a read, an add, and a write — three steps, not atomic. Two goroutines can both read the old value and both write back `old+1`, losing one increment (the lost-update race). The mutex makes the whole sequence atomic *and* establishes happens-before. `atomic.Int64.Add` does the read-modify-write as one indivisible hardware operation — fewer moving parts when a counter is all you need. Either is correct under `-race`.

</Solution>

</Exercise>

<Exercise n={2} title="Plug the goroutine leak" level="medium">

`fetch` starts a goroutine that sends the result on an unbuffered channel, but the caller returns on timeout without receiving — leaking the goroutine. Fix it so the goroutine always exits.

```go
func fetch(ctx context.Context) (int, error) {
	ch := make(chan int)
	go func() { ch <- slowWork() }() // leaks if ctx times out first
	select {
	case v := <-ch:
		return v, nil
	case <-ctx.Done():
		return 0, ctx.Err()
	}
}
```

<Solution>

```go
func fetch(ctx context.Context) (int, error) {
	ch := make(chan int, 1) // buffer of 1: the send never blocks
	go func() { ch <- slowWork() }()
	select {
	case v := <-ch:
		return v, nil
	case <-ctx.Done():
		return 0, ctx.Err() // goroutine's send still fits in the buffer; it exits
	}
}
```

The bug: when `ctx.Done()` wins the `select`, the function returns and stops receiving, but the goroutine still tries `ch <- slowWork()` on an *unbuffered* channel with no receiver — it blocks forever. Giving `ch` a **buffer of 1** lets that send complete into the buffer even with no receiver, so the goroutine reaches its end and is collected. (Alternative: have the goroutine `select` its send against `ctx.Done()`.) A buffer of 1 is the textbook fix for "send to a receiver that might have left."

</Solution>

</Exercise>

<Exercise n={3} title="Disable a select case with nil" level="hard">

Merge `a` and `b` into `out`, closing `out` when both inputs are closed — and don't busy-loop when one closes early. Use the nil-channel trick.

<Solution>

```go
func merge(a, b <-chan int) <-chan int {
	out := make(chan int)
	go func() {
		defer close(out)
		for a != nil || b != nil { // loop until BOTH are drained
			select {
			case v, ok := <-a:
				if !ok {
					a = nil // disable this case; a nil channel is never selected
					continue
				}
				out <- v
			case v, ok := <-b:
				if !ok {
					b = nil
					continue
				}
				out <- v
			}
		}
	}()
	return out
}
```

A closed channel is *always* ready (`ok=false` instantly), so without intervention its `select` case fires nonstop — a 100%-CPU busy loop. Setting the variable to `nil` on close makes that case unselectable (a nil channel blocks forever, so `select` skips it), and the loop condition `a != nil || b != nil` exits once both are nil. No boolean flags, no spin. This is *the* idiomatic merge.

</Solution>

</Exercise>

<Exercise n={4} title="errgroup fan-out" level="medium">

You must fetch quotes for several symbols concurrently; if any fetch fails, cancel the rest and return the first error. Write it with `errgroup`.

<Solution>

```go
func fetchAll(ctx context.Context, symbols []string) ([]Quote, error) {
	g, ctx := errgroup.WithContext(ctx)
	quotes := make([]Quote, len(symbols)) // index-per-goroutine: no shared append
	for i, sym := range symbols {
		g.Go(func() error {
			q, err := fetchQuote(ctx, sym)
			if err != nil {
				return err // first error cancels ctx, stopping siblings
			}
			quotes[i] = q // distinct index — safe without a lock
			return nil
		})
	}
	if err := g.Wait(); err != nil {
		return nil, err
	}
	return quotes, nil
}
```

`errgroup.WithContext` gives a group whose context is cancelled the instant any `g.Go` returns a non-nil error, so the other in-flight fetches see `ctx.Done()` and bail. `g.Wait()` returns that first error. Each goroutine writes a **distinct index** of `quotes`, so there's no shared-`append` data race and no mutex needed — the classic safe pattern for "collect N results in order." (Loop variables are per-iteration as of Go 1.22, so no `i := i` shadow is needed.)

</Solution>

</Exercise>

<Exercise n={5} title="Spot the copied mutex" level="medium">

Why does `go vet` flag this, and what's the fix?

```go
type Registry struct {
	mu      sync.Mutex
	entries map[string]int
}
func (r Registry) Add(k string) { // value receiver
	r.mu.Lock()
	r.entries[k]++
	r.mu.Unlock()
}
```

<Solution>

```go
func (r *Registry) Add(k string) { // pointer receiver — operate on the original
	r.mu.Lock()
	r.entries[k]++
	r.mu.Unlock()
}
```

The **value receiver** `(r Registry)` copies the whole struct — including the `sync.Mutex` — on every call. `go vet` reports "Add passes lock by value: Registry contains sync.Mutex" via the `copylocks` analyzer. The copy's mutex is a *different* lock from any other caller's, so it excludes nothing: two goroutines can lock their own copies and stomp the shared `entries` map (which, being a reference type, *is* shared even through a struct copy — so you get an unprotected concurrent map write, which Go panics on). Switching to a **pointer receiver** makes every call lock the same mutex over the same map. Rule: methods that lock take a pointer receiver, always.

</Solution>

</Exercise>

<Recap>

The concurrency mistakes — the ones that pass every test and then page you at 3 a.m.:

- **Concurrency ≠ parallelism** (#55): concurrency is structure, parallelism is execution. Concurrency *enables* a speedup; it doesn't guarantee one (#56) — below a threshold, goroutine overhead loses to a sequential loop. Match goroutine count to workload (#59): CPU-bound → ~`GOMAXPROCS`; I/O-bound → many.
- **Data race vs race condition** (#58): a data race is unsynchronized concurrent access (≥1 write) — a serious memory-model violation caught by `-race`; a race condition is correctness depending on interleaving. The **memory model**'s *happens-before* edges come from synchronization. **Channels** transfer/coordinate; **mutexes** guard shared state (#57).
- **Context** (#60): take `ctx` first, watch `ctx.Done()`. Don't leak a request ctx into a background job (#61) — detach with `context.WithoutCancel`.
- **Goroutine leaks** (#62): every goroutine needs a guaranteed exit (buffer of 1, or `select` on `ctx.Done()`). Loop-variable capture (#63) is fixed in Go 1.22+ (per-iteration).
- **Channels/select**: `select` among ready cases is **random** (#64) — order ≠ priority. Use `chan struct{}` for signals (#65); a **nil** channel disables a select case (#66); default to **unbuffered** (#67); keep `String()` side-effect-free and lock-aware (#68).
- **sync & friends**: `wg.Add` in the parent before the goroutine — or just use **`wg.Go`** (#71); `sync.Cond.Broadcast` to wake many waiters (#72); **`errgroup`** for fail-fast fan-out (#73); never **copy a sync type** — `go vet`'s `copylocks` catches it (#74). Watch shared-`append` races (#69) and "protecting" a slice through a struct copy (#70).
