## RBAC vs ABAC vs ReBAC (Google Zanzibar)

To understand why traditional authorization architectures crumble under enterprise load, we must analyze the three dominant authorization paradigms:

<ConceptGrid cols={3}>
  <ConceptCard label="1. RBAC (Role-Based)">
    **Static Coarse Buckets.** Users belong to roles (`Admin`, `Editor`, `Auditor`).
    
    *Failure point:* Role explosion. Multi-tenancy and resource hierarchies force hundreds of synthetic roles (`meridian_apac_wire_editor_restricted`).
  </ConceptCard>
  <ConceptCard label="2. ABAC (Attribute-Based)">
    **Dynamic Logic Engine.** Policies inspect arbitrary attributes (e.g. `request.time < 17:00 && user.department == resource.department`).
    
    *Failure point:* Opaque complexity, CPU latency spikes, and cannot perform reverse queries (*"List all records user X can access"*).
  </ConceptCard>
  <ConceptCard label="3. ReBAC (Relationship-Based)">
    **Directed Graph Traversal.** Authorization is modeled exclusively as relationships between entities (`user:alice` → `member` → `org:meridian` → `owner` → `program:soc2`).
    
    *Advantage:* Sub-millisecond evaluation, infinite composability, unified cross-service access graphs.
  </ConceptCard>
</ConceptGrid>

<Define term="ReBAC (Relationship-Based Access Control)">
**ReBAC** is an authorization model where permissions are computed by traversing a directed graph of relationships between **subjects** (users or groups), **relations** (roles or permissions), and **objects** (resources, organizations, files, transactions).
</Define>

<Define term="Google Zanzibar">
**Google Zanzibar** is the globally distributed authorization system built by Google to power permissions across Google Drive, YouTube, Google Cloud, and Maps. It evaluates trillions of access checks per day with sub-5ms p95 latency by storing permissions as relationship tuples and performing distributed graph resolution over specialized caching indexes.
</Define>

<Gotcha>
**The "New Enemy" Problem in Distributed Authorization:**

## OpenFGA DSL Schema Modeling

**OpenFGA** (hosted by the Cloud Native Computing Foundation) is the premier open-source implementation of Google Zanzibar. It introduces a human-readable Domain Specific Language (DSL) to define authorization models.

<Define term="OpenFGA (Open Fine-Grained Authorization)">
**OpenFGA** is an open-source, high-performance authorization engine based on Zanzibar principles. It allows engineering teams to define authorization models using declarative schema DSLs and evaluate access checks (`Check`), batch validations (`BatchCheck`), and resource discovery queries (`ListObjects`).
</Define>

### OpenFGA Primitive Mechanics

An OpenFGA schema defines **types** and **relations** using three core primitives:

1. **Direct Relation (`[type]`):** A direct assignment of a user or userset to an object relation.
   ```openfga
   define admin: [user]
   ```
2. **Computed Userset (`or`, `and`, `but not`):** Derives a relation from other relations on the *same* object.
   ```openfga
   define viewer: member or admin
   ```
3. **Tuple-to-Userset (`relation from tupleset`):** Traverses a relation on a *linked* object to inherit permissions across boundaries.
   ```openfga
   define can_approve: approver from control
   ```

<Define term="Direct Relation">
A direct link stored as an explicit tuple in the database, declaring that a specific subject has a specific relation on an object (e.g. `user:alice is member of org:meridian`).
</Define>

<Define term="Computed Userset">
A relation calculated dynamically from other relations on the *same target object* without looking up additional tuples (e.g. `editor` automatically includes `owner`).
</Define>

<Define term="Tuple-to-Userset">
A relation computed by looking up a set of linked objects via a **tupleset relation**, and then checking if the subject holds a **computed relation** on those linked objects.
</Define>

<Define term="Contextual Tuple">
An ephemeral relationship tuple supplied directly in the payload of a `Check` or `ListObjects` request. It exists solely for the duration of that request and is never committed to persistent storage (e.g. step-up MFA verification, temporary time-bound auditor delegation).
</Define>

### The Complete Meridian Governance & Banking OpenFGA Schema

Here is the production OpenFGA 1.1 model powering Meridian's compliance and wire transfer systems:

```openfga
model
  schema 1.1

type user

type organization
  relations
    define admin: [user]
    define member: [user] or admin

type audit_program
  relations
    define parent_org: [organization]
    define owner: [user] or admin from parent_org
    define auditor: [user] or member from parent_org
    define can_edit: owner
    define can_view: auditor or owner

type audit_control
  relations
    define program: [audit_program]
    define owner: [user] or owner from program
    define approver: [user] or owner
    define can_assess: approver or auditor from program

type evidence
  relations
    define control: [audit_control]
    define uploader: [user]
    define can_approve: approver from control
    define can_view: uploader or can_assess from control

type wire_transfer
  relations
    define org: [organization]
    define initiator: [user]
    define approver: [user]
    define org_risk_officer: admin from org
    define can_execute: (approver or org_risk_officer) but not initiator
```

## Tuple Stores & Graph Traversal

At the core of every ReBAC system is the **Tuple Store**. 

<Define term="Tuple">
A **Tuple** is an immutable relationship statement formatted as: `Object#Relation@Subject`.

For example: `organization:meridian#admin@user:alice` declares that `user:alice` has the `admin` relation on `organization:meridian`.
</Define>

<UnderTheHood title="Zanzibar Graph Expansion, Leopard Index & Distributed Evaluation">

Google Zanzibar achieves 95th-percentile latencies under 5 milliseconds across billions of access checks by employing four foundational architectural patterns:

### 1. The Recursive Expansion Engine & Parallel Fan-Out
When evaluating an authorization check for a relation composed of unions (`or`), the engine spawns concurrent goroutines to evaluate each branch independently. As soon as any branch resolves to `true`, a root `context.CancelCauseFunc` is triggered to cancel remaining evaluations immediately, minimizing wasted CPU.

### 2. The Leopard Index (Transitive Reachability Flattening)
Deep group hierarchies (e.g. `user:alice` ∈ `group:americas_compliance` ∈ `group:global_risk` ∈ `group:all_employees`) create long search paths. Zanzibar maintains the **Leopard Index** — an offline-computed reachability set that flattens transitive group-to-group relationships into ordered lists of integer set IDs. Set intersection `(A ∩ B)` executes in CPU registers in tens of nanoseconds.

### 3. Zookies & TrueTime Snapshot Consistency
To eliminate the "New Enemy Problem" (where stale caches permit unauthorized access after revocation), Zanzibar generates an encrypted consistency token called a **Zookie**. A Zookie encodes a lower-bound timestamp `T_m` corresponding to the latest ACL write. When an evaluation request arrives with token `Z`, the storage layer reads snapshot data at timestamp `T >= T_m`, ensuring strict causal consistency across global replicas.

### 4. Zero-Allocation Traversal in Modern Go 1.26
In Go, high-throughput ReBAC engines avoid heap allocation during graph traversal by:
- Storing interned `uint32` symbol IDs instead of string objects (`"organization:meridian"` → `ID(4021)`).
- Reusing traversal path buffers via `sync.Pool` to eliminate GC pressure during recursive depth searches.
- Employing Go 1.26 `testing.B.Loop()` to inline benchmark validation routines.

</UnderTheHood>

### Building a Complete In-Process ReBAC Graph Engine in Go

Let's build a fully functional, thread-safe ReBAC engine supporting Direct Relations, Computed Usersets, Tuple-to-Userset resolution, Cycle Detection, and Contextual Tuples:

<GoPlayground>

```go
package main

import (
	"context"
	"fmt"
	"strings"
	"sync"
)

// Tuple represents a Zanzibar relationship tuple: (Object#Relation@User)
type Tuple struct {
	User     string // e.g. "user:alice" or "organization:meridian#member"
	Relation string // e.g. "admin", "owner", "approver"
	Object   string // e.g. "organization:meridian", "audit_program:soc2"
}

// RelationDef describes how a relation rule is computed
type RelationDef struct {
	ComputedUserset string             // Inherits from relation on same object
	TupleToUserset  *TupleToUsersetDef // Inherits from relation on linked object
}

type TupleToUsersetDef struct {
	TuplesetRelation string // e.g. "control"
	ComputedRelation string // e.g. "approver"
}

// Schema stores type definitions and relation rules
type Schema struct {
	Types map[string]map[string]RelationDef
}

func NewSchema() *Schema {
	return &Schema{Types: make(map[string]map[string]RelationDef)}
}

func (s *Schema) Define(objectType, relation string, def RelationDef) {
	if _, ok := s.Types[objectType]; !ok {
		s.Types[objectType] = make(map[string]RelationDef)
	}
	s.Types[objectType][relation] = def
}

// Engine evaluates ReBAC permissions
type Engine struct {
	mu     sync.RWMutex
	tuples []Tuple
	schema *Schema
}

func NewEngine(schema *Schema) *Engine {
	return &Engine{schema: schema, tuples: make([]Tuple, 0)}
}

func (e *Engine) WriteTuple(user, relation, object string) {
	e.mu.Lock()
	defer e.mu.Unlock()
	e.tuples = append(e.tuples, Tuple{User: user, Relation: relation, Object: object})
}

// Check evaluates whether user has relation on object
func (e *Engine) Check(ctx context.Context, user, relation, object string, contextual ...Tuple) (bool, error) {
	visited := make(map[string]bool)
	return e.checkRecursive(ctx, user, relation, object, visited, contextual)
}

func (e *Engine) checkRecursive(
	ctx context.Context,
	user, relation, object string,
	visited map[string]bool,
	contextual []Tuple,
) (bool, error) {
	select {
	case <-ctx.Done():
		return false, ctx.Err()
	default:
	}

	// 1. Cycle Detection Guard
	cycleKey := fmt.Sprintf("%s#%s@%s", object, relation, user)
	if visited[cycleKey] {
		return false, nil // Terminate circular loop safely
	}
	visited[cycleKey] = true
	defer delete(visited, cycleKey)

	// 2. Direct Tuple Match (Storage + Contextual)
	if e.hasDirect(user, relation, object, contextual) {
		return true, nil
	}

	parts := strings.SplitN(object, ":", 2)
	if len(parts) != 2 {
		return false, fmt.Errorf("invalid object identifier: %s", object)
	}
	objectType := parts[0]

	relDef, exists := e.schema.Types[objectType][relation]
	if !exists {
		return false, nil
	}

	// 3. Computed Userset (e.g. member is satisfied by admin)
	if relDef.ComputedUserset != "" {
		ok, err := e.checkRecursive(ctx, user, relDef.ComputedUserset, object, visited, contextual)
		if err != nil {
			return false, err
		}
		if ok {
			return true, nil
		}
	}

	// 4. Tuple-to-Userset (e.g. can_approve inherits approver from linked control)
	if relDef.TupleToUserset != nil {
		ttu := relDef.TupleToUserset
		linkedObjects := e.findLinked(object, ttu.TuplesetRelation, contextual)
```

## High-Throughput Go Auth Middleware

In high-volume banking systems, sending every HTTP authorization check across a network socket to a remote Zanzibar cluster adds intolerable latency. To achieve sub-millisecond authorization, production Go services employ:

1. **In-Memory Request Coalescing (Singleflight)**: Prevents thundering herds when 50 concurrent requests check permissions for the same hot resource.
2. **Context-Driven Policy Enforcement**: Middleware extracts authenticated principals and URL parameters into normalized Zanzibar object identifiers.
3. **Structured Audit Logging**: Emits Go 1.25 `slog.GroupAttrs` security events containing decision latency and traversed relation paths.

Here is a complete, production-grade Go HTTP authorization middleware:

```go
import (
	"context"
	"fmt"
	"log/slog"
	"net/http"
	"net/http/httptest"
	"os"
	"sync"
	"time"

// SingleflightGroup deduplicates concurrent in-flight Check requests
type SingleflightGroup struct {
	mu sync.Mutex
	m  map[string]*call
}

type call struct {
	wg  sync.WaitGroup
	val bool
	err error
}

func NewSingleflight() *SingleflightGroup {
	return &SingleflightGroup{m: make(map[string]*call)}
}

func (g *SingleflightGroup) Do(key string, fn func() (bool, error)) (bool, error) {
	g.mu.Lock()
	if c, ok := g.m[key]; ok {
		g.mu.Unlock()
		c.wg.Wait()
		return c.val, c.err
	}
	c := new(call)
	c.wg.Add(1)
	g.m[key] = c
	g.mu.Unlock()

	c.val, c.err = fn()
	c.wg.Done()

	g.mu.Lock()
	delete(g.m, key)
	g.mu.Unlock()

	return c.val, c.err
}

// Authorizer interface for permission evaluation
type Authorizer interface {
	Check(ctx context.Context, user, relation, object string) (bool, error)
}

		return true, nil

	return false, nil

// ReBACMiddleware enforces fine-grained authorization
func ReBACMiddleware(auth Authorizer, sfg *SingleflightGroup, relation string, getObjectID func(r *http.Request) string) func(http.Handler) http.Handler {
	logger := slog.New(slog.NewTextHandler(os.Stdout, nil))

	return func(next http.Handler) http.Handler {
		return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
			start := time.Now()
			user := r.Header.Get("X-User-ID")
			if user == "" {
				http.Error(w, "Unauthorized: missing X-User-ID", http.StatusUnauthorized)
				return
			}

			objectID := getObjectID(r)
			userKey := fmt.Sprintf("user:%s", user)
			objectKey := fmt.Sprintf("evidence:%s", objectID)
			dedupeKey := fmt.Sprintf("%s#%s@%s", objectKey, relation, userKey)

			// Execute permission check with singleflight deduplication
			allowed, err := sfg.Do(dedupeKey, func() (bool, error) {
				return auth.Check(r.Context(), userKey, relation, objectKey)
			})

			duration := time.Since(start)
			logger.Info("ReBAC Authorization Check",
				slog.String("user", userKey),
				slog.String("relation", relation),
				slog.String("object", objectKey),
				slog.Bool("allowed", allowed),
				slog.Duration("latency", duration),
			)

			if err != nil || !allowed {
				http.Error(w, "Forbidden: insufficient permissions", http.StatusForbidden)
				return
			}

			next.ServeHTTP(w, r)
		})
	}
}

	sfg := NewSingleflight()

		return "ev_101"

	protectedRoute := middleware(evidenceHandler)

	reqAlice.Header.Set("X-User-ID", "alice")
```

<Exercise n={4} title="Concurrent Multi-Branch Evaluator with Cycle Detection" level="hard">

Build a concurrent Go permission evaluator that launches independent goroutines for each `or` branch, utilizes `context.WithCancel` to short-circuit upon the first successful branch, and tracks a visited set to prevent infinite loops on circular relationship graphs.

<Solution>

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"time"
)

type ConcurrentEvaluator struct {
	tuples map[string]bool
}

func (e *ConcurrentEvaluator) EvaluateBranches(ctx context.Context, checks []func(ctx context.Context) bool) bool {
	ctx, cancel := context.WithCancel(ctx)
	defer cancel()

	resultChan := make(chan bool, len(checks))
	var wg sync.WaitGroup

	for _, checkFn := range checks {
		wg.Add(1)
		go func(fn func(ctx context.Context) bool) {
			defer wg.Done()
			if fn(ctx) {
				select {
				case resultChan <- true:
					cancel() // Short-circuit other branches immediately
				case <-ctx.Done():
				}
			}
		}(checkFn)
	}

	// Closer goroutine
	go func() {
		wg.Wait()
		close(resultChan)
	}()

	for res := range resultChan {
		if res {
			return true
		}
	}
	return false
}

func main() {
	evaluator := &ConcurrentEvaluator{
		tuples: map[string]bool{"org:meridian#admin@user:alice": true},
	}

	ctx := context.Background()

	// Three candidate branches evaluated concurrently
	slowBranch := func(ctx context.Context) bool {
		select {
		case <-time.After(100 * time.Millisecond):
			return false
		case <-ctx.Done():
			return false
		}
	}

	fastSuccessBranch := func(ctx context.Context) bool {
		return evaluator.tuples["org:meridian#admin@user:alice"]
	}

	branches := []func(ctx context.Context) bool{slowBranch, fastSuccessBranch}

	start := time.Now()
	allowed := evaluator.EvaluateBranches(ctx, branches)
	fmt.Printf("Access Allowed: %v (Resolved in %v)\n", allowed, time.Since(start))
}
```
