## Mapping a Black-Box API

Before any bug, you map the API. A modern API looks opaque from the outside — binary protobuf, obfuscated IDs, no docs — but it leaks its own structure if you know where to look. brutecat's *"Decoding Google"* is the methodology: turn a black box into a white box.

<Define term="API surface mapping">
**API surface mapping** reconstructs an undocumented API's endpoints, parameters, and types from the outside. The richest sources: **discovery documents** (machine-readable API specs, like Swagger/OpenAPI, that many platforms publish — sometimes staging variants leak internal endpoints and comments); **embedded API keys** in public web/mobile clients (which often grant access to *internal* APIs); **error messages** that name the parameter or type they rejected; and **client code** (JS bundles, decompiled Android apps) that reveals endpoints and request shapes. The goal is to move from "I can call this one documented endpoint" to "I know every endpoint, every field, and every type the service accepts" — because you cannot attack a parameter you don't know exists.
</Define>

<Callout kind="pro" title="Field notes from the Pwning Google podcast">
On the *Critical Thinking* podcast, the researcher described the recon machinery behind the haul — three concrete, transferable moves beyond the diagram above:

- **Harvest API keys from old client builds, at scale.** Many "internal" endpoints are gated only by an **API key**, not real auth — `"you just need a key; I guess nobody found the key."` The researcher kept a tracked corpus of **~700–800 keys**, most pulled from **old Android APKs**, and tried them against undocumented endpoints. One ungated provider/admin API took only a key plus an *incrementable* account ID and dumped phone numbers, Voice numbers, emails, and PINs. **Defense:** an API key is an identifier, not an authorization; every endpoint must still authenticate *and* authorize the caller, and keys in shipped clients must be scoped to exactly what that client needs.
- **Fuzz for debug/status handlers ("Z-handlers").** After spotting a stray proxy error, fuzzing the host surfaced internal **debug handlers** (e.g. a `/...Z` or status handler) that respond with **no auth** and leak internal info useful for later attacks. **Defense:** debug/status handlers must never be reachable from the internet — bind them to an internal interface and authenticate them; treat their exposure as a finding.
- **Look behind feature flags for unreleased endpoints.** A not-yet-launched assistant feature had **no UI**, but introspection revealed it and a JavaScript **debugger breakpoint** was used to flip the enabling flag and reach it. The rapid AI-era release cycle pushes code to production well before launch. **Defense:** unreleased functionality behind a flag is still *deployed and reachable* — it must carry the same authn/authz as shipped features, not rely on the UI hiding the button.
</Callout>

## ProtoJSON Schema Fuzzing

The sharpest mapping technique deserves its own section, because it's a pure oracle and fully demonstrable. Many gRPC/protobuf services accept a **ProtoJSON** encoding where fields can be sent **positionally** (by field number, as a JSON array). Send `[1, 2, 3, ...]` and the server's *error messages* leak each field's name and type — one request at a time, the whole schema falls out.

<Define term="ProtoJSON positional fuzzing">
Protobuf messages number their fields (`field 1`, `field 2`, …). Some services accept a JSON-encoded protobuf (`application/json+protobuf`) where a message is an **array indexed by field number**. If you send a value of the wrong type at position *N*, the server replies with an error like `field 'browse_id' (2): expected string, got number` — **leaking the field's name and expected type**. Iterate position by position and the error oracle reconstructs the entire message schema, including nested types — no source access, no docs. brutecat used exactly this against YouTube's InnerTube API to extract field names like `browse_id` and `continuation`. The fix: **generic error messages** that never echo internal field names or types.
</Define>

<GoPlayground>

```go
package main

import (
	"fmt"
	"sort"
)

// The server's REAL schema (field number → name + type). The attacker can't see this.
type field struct {
	name string
	typ  string
}

var schema = map[int]field{
	1: {"context", "message"},
	2: {"browse_id", "string"},
	3: {"continuation", "string"},
	4: {"params", "string"},
}

// VULNERABLE server: a wrong-typed field error ECHOES the field name and type.
func probe(pos int, sentNumber bool) (string, bool) {
	f, ok := schema[pos]
	if !ok {
		return "no such field", false
	}
	if sentNumber && f.typ != "number" {
		// the leak: the error names the field and its expected type
		return fmt.Sprintf("field '%s' (%d): expected %s, got number", f.name, pos, f.typ), true
	}
	return "ok", true
}

func main() {
	// Attacker fuzzes positions 1..6 with a number, reading the error oracle.
	recovered := map[int]field{}
	for pos := 1; pos <= 6; pos++ {
		msg, exists := probe(pos, true) // send a number to force a type error
		if !exists {
			continue
		}
		var name, typ string
		fmt.Sscanf(msg, "field '%[^']' (%d): expected %s", &name, new(int), &typ)
		recovered[pos] = field{name, typ}
		fmt.Printf("pos %d → %s\n", pos, msg)
	}

	fmt.Println("\nRECOVERED SCHEMA (no docs, no source):")
	var keys []int
	for k := range recovered {
		keys = append(keys, k)
	}
	sort.Ints(keys)
	for _, k := range keys {
		fmt.Printf("  field %d: %s (%s)\n", k, recovered[k].name, recovered[k].typ)
	}
}
```

</GoPlayground>

</CodeWalk>

<Gotcha>
**Verbose error messages are a vulnerability, not a convenience.** Every error that echoes an internal field name, type, SQL fragment, stack frame, or proto definition is a free gift to a schema-mapper. The fix is uncomfortable for developers who love helpful errors: **externally, return a generic, opaque error** (`400 invalid request`, a correlation ID for support) and log the detail *server-side only*. The same principle killed the most damaging part of brutecat's recon — and it's the same reason the **errors-as-reconnaissance** section of the OWASP field guide warns against detailed error responses. Help your developers in the logs, not on the wire.
</Gotcha>

## ID → PII Over-Disclosure

The YouTube-emails hunt is a perfect, simple lesson: an endpoint that converts an **obfuscated identifier** into **personal data** without checking whether the caller should be allowed to. The obfuscation felt like security; it wasn't.

<Define term="ID-to-PII over-disclosure">
Systems use **obfuscated/opaque IDs** (a Gaia ID, a UUID, a hashed token) to refer to users internally, on the assumption that an attacker can't link them to a real person. The vulnerability: some *other* endpoint accepts that opaque ID and returns **PII** (an email, phone, name) without verifying the caller is authorized to learn it. If the attacker can obtain the opaque ID through one feature (YouTube live-chat leaked Gaia IDs) and resolve it to PII through another (Pixel Recorder's share endpoint returned the email for a Gaia ID), the obfuscation is defeated end to end. The root cause is **missing authorization on the resolution endpoint** — an opaque ID is not an access-control boundary. The fix: every endpoint that returns PII must check that *this caller* is allowed to see *this subject's* data, regardless of how the ID was obtained.
</Define>

<GoPlayground>

```go
package main

import (
	"errors"
	"fmt"
)

type user struct {
	gaiaID string
	email  string
}

var users = map[string]user{
	"gaia_8f2a": {"gaia_8f2a", "alice@example.com"},
	"gaia_3c91": {"gaia_3c91", "bob@example.com"},
}

// VULNERABLE: resolves an opaque ID to email with NO authorization check.
// The obfuscated ID is treated as if knowing it implies permission — it doesn't.
func resolveEmailRacy(gaiaID string) (string, error) {
	u, ok := users[gaiaID]
	if !ok {
		return "", errors.New("not found")
	}
	return u.email, nil // anyone with the ID gets the email
}

// SAFE: the caller must be authorized to learn THIS subject's PII.
func resolveEmailSafe(callerID, gaiaID string, sharedWith map[string]bool) (string, error) {
	if callerID != gaiaID && !sharedWith[callerID] {
		return "", errors.New("forbidden: not authorized for this subject")
	}
	u, ok := users[gaiaID]
	if !ok {
		return "", errors.New("not found")
	}
	return u.email, nil
}

func main() {
	// Attacker obtained alice's Gaia ID from another feature (e.g. live chat).
	email, _ := resolveEmailRacy("gaia_8f2a")
	fmt.Println("VULNERABLE leaks:", email)

	// The fix rejects an unrelated caller, even though they know the ID.
	_, err := resolveEmailSafe("gaia_attacker", "gaia_8f2a", map[string]bool{})
	fmt.Println("SAFE rejects attacker:", err)

	// Only an authorized caller (self, or explicitly shared-with) succeeds.
	ok, _ := resolveEmailSafe("gaia_8f2a", "gaia_8f2a", map[string]bool{})
	fmt.Println("SAFE allows self:", ok)
}
```

</GoPlayground>

<Callout kind="note" title="Real case — leaking any YouTube channel's email ($10,633)">
brutecat's *"Leaking the email of any YouTube user"* chained exactly this: YouTube's live-chat **Internal People API** leaked any channel's obfuscated **Gaia ID**, and Pixel Recorder's `WriteShareList` endpoint **resolved that Gaia ID to the account's email** with no authorization check. The obfuscated ID was assumed unguessable and therefore safe to resolve — the classic mistake. (The notification that would have tipped off the victim was suppressed separately — see the Notification Suppression section.) Two endpoints, each "fine" alone, composed into a full email-disclosure for ~4 billion accounts.
</Callout>

## Rate Limits at Scale

To brute-force anything against a giant, you must defeat the rate limit. The phone-number hunt shows the two ways attackers do it: **token reuse** (a token meant for a hard path accepted on an easy one) and — the big one — **IP rotation via IPv6**. An IP-based limiter assumes IPs are scarce. With IPv6, they aren't.

<Define term="IPv6 rate-limit bypass">
Rate limiters often key their counters on the client **IP address** — *N* requests per IP per window. This assumes addresses are scarce, which is true for IPv4. But an attacker with an IPv6 allocation typically controls an entire **/64 subnet** — that's 2⁶⁴ (over 18 quintillion) addresses, all theirs. If the limiter keys on the full 128-bit address, the attacker simply **uses a fresh source address for every request**, and every request looks like a brand-new client — the limit never triggers. The fix: for IPv6, **rate-limit by the /64 (or shorter) prefix**, not the full address, because a /64 is the smallest unit normally assigned to a single customer. Keying on the prefix collapses the attacker's 18 quintillion addresses back into one bucket.
</Define>

<GoPlayground>

```go
package main

import (
	"fmt"
	"net/netip"
)

// keyFull buckets by the entire IPv6 address — the VULNERABLE choice.
func keyFull(addr netip.Addr) string { return addr.String() }

// keySafe buckets IPv6 by the /64 prefix — the smallest unit a single
// customer is normally assigned, so an attacker can't rotate out of it.
func keySafe(addr netip.Addr) string {
	if addr.Is6() {
		p, _ := addr.Prefix(64)
		return p.String()
	}
	return addr.String()
}

func main() {
	// The attacker sends from many addresses in ONE /64 they control.
	attacker := []string{
		"2001:db8:abcd:1234::1",
		"2001:db8:abcd:1234::2",
		"2001:db8:abcd:1234::dead",
		"2001:db8:abcd:1234::beef",
	}
	full, safe := map[string]int{}, map[string]int{}
	for _, s := range attacker {
		a := netip.MustParseAddr(s)
		full[keyFull(a)]++
		safe[keySafe(a)]++
	}
	fmt.Printf("keyed on full address: %d distinct buckets (limit never fires)\n", len(full))
	fmt.Printf("keyed on /64 prefix:   %d bucket  (all %d requests counted together)\n",
		len(safe), len(attacker))
}
```

## The Masked-Value Oracle

Rate limit defeated, you still need to *shrink the search space*. Recovery flows helpfully show a **masked** version of the secret (`•• ••••••03`), and a separate endpoint acts as an **oracle** telling you hit-or-miss. Together they make brute force tractable.

<Define term="Masked-value oracle">
A **masked-value oracle** combines two leaks. First, a UI shows a **partial secret** to help a legitimate user recognize it — a masked phone (`•• ••••••03`), masked email (`a••••@gmail.com`), or last-4 of a card. This reveals some digits and the *length*, collapsing the search space (a 9-digit number with 2 known digits is ~10⁷, not 10⁹). Second, a separate endpoint behaves as a **boolean oracle**: it responds differently for a correct vs incorrect guess (a 302 to `…/challenge` vs `…/noaccountsfound`), so the attacker can test candidates. Mask shrinks the space; oracle searches it. The fix: don't reveal mask details to unauthenticated callers, and make the oracle **indistinguishable** (identical response + timing whether or not the account/value exists).
</Define>

<GoPlayground>

```go
package main

import "fmt"

// oracle: returns true if a candidate matches the secret (models the distinct
// 302 redirects that leaked hit/miss in the real phone-recovery flow).
func oracle(secret, candidate string) bool { return secret == candidate }

func main() {
	secret := "0612345603" // a 10-digit number we're trying to recover
	// The recovery UI masked it as "•• ••••••03" → we know length 10 and last 2 = "03".
	// That fixes 2 digits; we brute the middle. (Tiny range here for the demo.)
	known := "06123456" // suppose recon also gave the prefix; brute the rest before "03"
	tries := 0
	for d := 0; d <= 99; d++ {
		candidate := fmt.Sprintf("%s%02d", known, d) // ...NN, but last 2 are fixed "03"
		// apply the mask constraint: last two digits must be "03"
		if candidate[len(candidate)-2:] != "03" {
			continue
		}
		tries++
		if oracle(secret, candidate) {
			fmt.Printf("recovered %s in %d oracle queries (mask cut the space)\n", candidate, tries)
			return
		}
	}
	fmt.Println("not found in masked range")
}
```

</GoPlayground>

<Callout kind="note" title="Real case — brute-forcing any Google account's phone ($5,000)">
brutecat's *"Leaking the phone number of any Google account"* combined all of it: a Looker Studio ownership-transfer leaked the target's **display name** (needed to validate guesses), the password-recovery flow showed a **masked phone**, the no-JS username-recovery endpoint was a **hit/miss oracle** (distinct 302s), a **BotGuard token** from the JS form was accepted on the no-JS path (bypassing its anti-automation), and **IPv6 /64 rotation** defeated the rate limit. Result: ~40,000 checks/second, recovering a US number in ~20 minutes, a Netherlands number in ~15 seconds — silently, with no victim interaction. Five separate weaknesses, each minor, composing into total phone disclosure.
</Callout>

## IDOR by Binary Search

The Google Cloud hunt has the most beautiful primitive in the set: extracting a secret 32-character UUID you're *not* allowed to read, using only a **filter that supports comparison operators**. It's IDOR meets binary search — and it needs only ~128 requests.

<Define term="IDOR UUID extraction via comparison filters">
A list endpoint with a **filter** supporting comparison operators (`workflow_id > "x"`, `workflow_id <= "y"`) is a boolean oracle over the secret value: "is the hidden ID greater than my probe?" Each query answers one comparison. Because a UUID is a hex string, you can **binary-search each character**: 4 comparisons pin down each of the 32 hex digits (a binary search over 16 possibilities is ⌈log₂16⌉ = 4), so the full 32-character UUID falls in **32 × 4 = 128 requests** — even though you were never authorized to read it directly. brutecat used this on the Application Integration API's `ListTestCases` filter to reconstruct victims' workflow UUIDs, then IDOR'd the full integration definitions. The fix: **don't expose comparison filters over sensitive identifiers**, and enforce per-resource ownership (not just per-project authorization) so the list never reflects other tenants' IDs at all.
</Define>

```go
const hexDigits = "0123456789abcdef"

// oracle models a filter that supports `>`: it reveals only whether the
// hidden secret is lexicographically greater than the attacker's probe.
func oracle(secret, probe string) bool { return secret > probe }

func extract(secret string) (string, int) {
	var known strings.Builder
	queries := 0
	for pos := 0; pos < len(secret); pos++ {
		lo, hi := 0, len(hexDigits)-1
		for lo < hi {
			mid := (lo + hi) / 2
			// probe: known prefix + candidate digit + 'f' padding to the end
			probe := known.String() + string(hexDigits[mid]) + strings.Repeat("f", len(secret)-pos-1)
			queries++
			if oracle(secret, probe) {
				lo = mid + 1 // secret is higher → digit is above mid
			} else {
				hi = mid // secret is at or below mid
			}
		}
		known.WriteByte(hexDigits[lo])
	}
	return known.String(), queries
}

func main() {
	secret := "9a3f1c0044e2bb7788ff00112233abcd" // a 32-char hex UUID we can't read
	got, queries := extract(secret)
	fmt.Println("secret   :", secret)
	fmt.Println("extracted:", got)
	fmt.Println("match    :", got == secret)
	fmt.Printf("queries  : %d  (32 chars × 4 comparisons)\n", queries)
}
```

## Notification Suppression

A small but devastating trick from the YouTube hunt: the email-resolution would have **emailed the victim** ("X shared a recording with you"), tipping them off. brutecat suppressed it by making a *different* field — the recording title — **2.5 million characters**, which broke the notification path while the resolution still succeeded silently.

<Define term="Notification suppression via unbounded fields">
Many sensitive actions fire a **notification** (email/SMS) so the victim notices ("a new device signed in", "X shared with you"). An attacker who can make that notification *fail* gets to act **silently**. A common way: find an **unbounded input field** the notification depends on (a title, a display name) and supply a value so large it breaks the notification pipeline (a template that can't render, a downstream size limit that throws) **after** the core action has already committed. The action succeeds; the alert never sends. Root causes: **no length validation** on the field, and a notification path that fails *open* (silently) instead of *closed*. The fixes: bound every input field, and treat a failed security notification as a failed operation (roll back or alert), never a silent no-op.
</Define>

<GoPlayground>

```go
package main

import (
	"errors"
	"fmt"
)

// VULNERABLE: shares the recording (commits the action) and THEN tries to
// notify — but an oversized title breaks the notifier, which fails silently.
func shareRacy(title string) (shared bool, notified bool) {
	shared = true // the action commits first
	if len(title) > 1_000_000 {
		// notification template blows up on the huge title; error swallowed
		return shared, false // victim never alerted
	}
	return shared, true
}

// SAFE: validate the field BEFORE committing, and require the notification
// to succeed (fail closed) — no silent shares.
func shareSafe(title string) (bool, error) {
	if len(title) > 200 {
		return false, errors.New("title too long") // bound the field
	}
	if !sendNotification(title) {
		return false, errors.New("notification failed — share aborted") // fail closed
	}
	return true, nil
}

func sendNotification(title string) bool { return len(title) <= 200 }

func main() {
	huge := make([]byte, 2_500_000)
	shared, notified := shareRacy(string(huge))
	fmt.Printf("RACY: shared=%v notified=%v  (silent — victim never told)\n", shared, notified)

	_, err := shareSafe(string(huge))
	fmt.Println("SAFE rejects oversized title:", err)

	ok, _ := shareSafe("Q3 planning recording")
	fmt.Println("SAFE normal share:", ok)
}
```

## Exercises

<Exercise n={1} title="Schema-fuzzing oracle" level="medium">

Given a `schema map[int]field` (field number → name/type), write `recover()` that probes each position with a wrong-typed value and reconstructs the `{name, type}` for each field from the (leaky) error string. Confirm it rebuilds the schema with no direct access to the map's contents beyond the error oracle.

<Solution>

```go
package main

import "fmt"

type field struct{ name, typ string }

func leakyError(f field) string {
	return fmt.Sprintf("field '%s': expected %s", f.name, f.typ)
}

func main() {
	schema := map[int]field{1: {"browse_id", "string"}, 2: {"count", "int"}}
	recovered := map[int]field{}
	for pos, f := range schema {
		var name, typ string
		fmt.Sscanf(leakyError(f), "field '%[^']' expected %s", &name, &typ)
		recovered[pos] = field{name, typ}
	}
	fmt.Println(len(recovered), "fields recovered from error oracle")
}
```

The error message *is* the vulnerability. The fix is a generic error that names nothing — recon dies without the oracle.

</Solution>

</Exercise>

<Exercise n={2} title="Authorize the PII resolution" level="easy">

Write `resolveEmail(caller, subject string, authorized map[string]bool) (string, error)` that returns the subject's email only if `caller == subject` or `authorized[caller]`. Show it rejects an attacker who knows the subject's opaque ID but isn't authorized.

<Solution>

```go
package main

import (
	"errors"
	"fmt"
)

var emails = map[string]string{"gaia_8f2a": "alice@example.com"}

func resolveEmail(caller, subject string, authorized map[string]bool) (string, error) {
	if caller != subject && !authorized[caller] {
		return "", errors.New("forbidden")
	}
	return emails[subject], nil
}

func main() {
	_, err := resolveEmail("attacker", "gaia_8f2a", map[string]bool{})
	fmt.Println("attacker:", err)
	e, _ := resolveEmail("gaia_8f2a", "gaia_8f2a", nil)
	fmt.Println("self:", e)
}
```

Knowing the opaque ID is not authorization. Every PII-returning endpoint must check the caller against the subject — the obfuscation is not a boundary.

</Solution>

</Exercise>

<Exercise n={3} title="Rate-limit by /64" level="medium">

Write `bucket(addr netip.Addr) string` returning the full address for IPv4 but the `/64` prefix for IPv6. Show that four addresses in one `/64` map to a single bucket.

<Solution>

```go
package main

import (
	"fmt"
	"net/netip"
)

func bucket(a netip.Addr) string {
	if a.Is6() {
		p, _ := a.Prefix(64)
		return p.String()
	}
	return a.String()
}

func main() {
	b := map[string]int{}
	for _, s := range []string{
		"2001:db8:aa:bb::1", "2001:db8:aa:bb::2",
		"2001:db8:aa:bb::ffff", "2001:db8:aa:bb:1::1",
	} {
		b[bucket(netip.MustParseAddr(s))]++
	}
	fmt.Println("distinct buckets:", len(b)) // 1 — all share the /64
}
```

Keying on the /64 collapses an attacker's entire allocation into one counter. The full-address key is the bug; the prefix key is the fix.

</Solution>

</Exercise>

<Exercise n={4} title="Extract a secret via a > oracle" level="hard">

Given `oracle(secret, probe string) bool` returning `secret > probe`, write `extract(secret string) (string, int)` that binary-searches each hex character and returns the reconstructed value and the query count. Confirm a 16-char secret is recovered in 64 queries.

<Solution>

```go
package main

import (
	"fmt"
	"strings"
)

const hexd = "0123456789abcdef"

func oracle(secret, probe string) bool { return secret > probe }

func extract(secret string) (string, int) {
	var b strings.Builder
	q := 0
	for pos := 0; pos < len(secret); pos++ {
		lo, hi := 0, 15
		for lo < hi {
			mid := (lo + hi) / 2
			probe := b.String() + string(hexd[mid]) + strings.Repeat("f", len(secret)-pos-1)
			q++
			if oracle(secret, probe) {
				lo = mid + 1
			} else {
				hi = mid
			}
		}
		b.WriteByte(hexd[lo])
	}
	return b.String(), q
}

func main() {
	got, q := extract("0a1b2c3d4e5f6789")
	fmt.Printf("%s in %d queries\n", got, q) // 64 = 16 × 4
}
```

⌈log₂16⌉ = 4 queries per hex char. A comparison filter over a secret ID is a full read primitive — never expose one.

</Solution>

</Exercise>

<Exercise n={5} title="Bound the field, fail closed" level="easy">

Write `share(title string) error` that rejects titles over 200 chars and treats a failed notification as a failed share (return an error), so an oversized field can never produce a silent action.

<Solution>

```go
package main

import (
	"errors"
	"fmt"
)

func notify(title string) bool { return len(title) <= 200 }

func share(title string) error {
	if len(title) > 200 {
		return errors.New("title too long")
	}
	if !notify(title) {
		return errors.New("notification failed — share aborted")
	}
	return nil // shared AND notified
}

func main() {
	fmt.Println("oversized:", share(string(make([]byte, 5000))))
	fmt.Println("normal:", share("standup recording"))
}
```

Two fixes in one: bound the field (no oversize), and fail closed (a silent share is impossible because the notification must succeed). A security notification that fails open is an attacker's stealth button.

</Solution>

</Exercise>

<Recap>

- **Map before you attack.** APIs leak their own structure through discovery documents, embedded keys, client code, and error messages. brutecat's *Decoding Google* turns a binary black box into a white-box schema — the prerequisite for everything else.
- **Verbose errors are an oracle.** Positional **ProtoJSON fuzzing** reconstructs a full message schema from type-mismatch errors that echo field names. Fix: generic external errors that name nothing; detail in logs only.
- **An opaque ID is not authorization.** ID→PII over-disclosure (obfuscated Gaia ID → email) happens when a resolution endpoint skips the access check, trusting that the ID is unguessable. Fix: every PII endpoint checks caller-vs-subject, however the ID was obtained.
- **IP rate limits assume scarcity.** With an IPv6 **/64** (2⁶⁴ addresses), an attacker rotates the source per request and per-address limits never fire. Fix: key the limiter on the **/64 prefix**, not the full address.
- **Mask + oracle = tractable brute force.** A masked secret shrinks the space; a hit/miss endpoint searches it. Fix: don't reveal masks to unauthenticated callers, and make the oracle response (and timing) identical for hit and miss.
- **A comparison filter over a secret is a read primitive.** `id > probe` lets you **binary-search** a 32-char UUID in 128 requests. Fix: no comparison operators over sensitive IDs, and per-resource ownership so the list never reflects other tenants' IDs.
- **Unbounded fields suppress alerts.** An oversized title broke the notification while the action committed — silent exploitation. Fix: bound every field, and fail **closed** (a failed security notification fails the operation).
- **Mediums chain into a P0.** Disclosure → IDOR → privilege escalation (ACL bypass via a second account) → arbitrary RPC under a production identity = RCE. No single bug was critical; the composition was. Defense means breaking any link **and** least-privileging the internal task system that became the execution sink.

</Recap>
