### The Anatomy of the ReAct Cycle

Every individual agent inside that swarm runs a cognitive loop known as **ReAct** (Reasoning + Acting, Yao et al., 2022).

<Define term="ReAct">
A cognitive orchestration framework where an autonomous agent alternates cyclically between **Thought** (reasoning over internal state and goal progress), **Action** (invoking an external tool with structured arguments), and **Observation** (receiving the external environment's response into its context window) until reaching a definitive conclusion or timeout.
</Define>

<Define term="Tool Calling">
The structured protocol whereby a language model halts text generation and produces a deterministic, machine-readable payload (typically JSON) specifying a registered function name and schema-validated arguments to be executed by the host application runtime.
</Define>

Every turn of a ReAct agent in Go follows six rigid, deterministic stages:

1. **Context & History Assembly**: The agent collates system instructions, the prompt, tool definitions, and prior turns into a request payload.
2. **Inference Invocation**: The agent calls the LLM endpoint with a bounded `context.Context` deadline (`context.WithTimeout`).
3. **Structured Thought & Action Parsing**: The model outputs internal reasoning followed by either a final text answer or a structured tool call.
4. **Tool Lookup & Execution**: The agent resolves the function name in its registry, parses arguments into typed structs, and runs the handler.
5. **Observation Injection**: The tool's output string (or domain error) is appended to message history as an `Observation` turn.
6. **Cycle Evaluation**: The loop checks termination invariants: did the model emit a final answer? Has `maxIterations` been reached? Has the deadline expired?

Amateur developers implement agents as unconstrained `for {}` loops. If the LLM enters a hallucination loop (e.g. attempting to run a nonexistent tool or repeating an invalid parameter), the process burns tokens indefinitely, exhausting quotas and stalling the thread.

### In-Memory ReAct Agent in Go

Here is a complete, self-contained, and production-ready in-memory ReAct engine. It demonstrates context propagation, structured tool invocation, observation injection, and multi-step reasoning:

<GoPlayground>

```go
package main

import (
	"context"
	"encoding/json"
	"fmt"
	"time"
)

// Message represents a single chat turn.
type Message struct {
	Role    string `json:"role"`
	Content string `json:"content"`
}

// ToolCall represents a structured action requested by the model.
type ToolCall struct {
	Name string          `json:"name"`
	Args json.RawMessage `json:"args"`
}

// ModelResponse simulates the LLM's structured generation.
type ModelResponse struct {
	Thought  string    `json:"thought"`
	ToolCall *ToolCall `json:"tool_call,omitempty"`
	Final    string    `json:"final,omitempty"`
}

// Tool defines the execution interface for an agent capability.
type Tool interface {
	Name() string
	Description() string
	Execute(ctx context.Context, args json.RawMessage) (string, error)
}

// LedgerBalanceTool inspects account balance.
type LedgerBalanceTool struct{}

func (t *LedgerBalanceTool) Name() string { return "get_balance" }
func (t *LedgerBalanceTool) Description() string {
	return "Retrieve account balance in integer cents by account_id."
}
func (t *LedgerBalanceTool) Execute(ctx context.Context, args json.RawMessage) (string, error) {
	var input struct {
		AccountID string `json:"account_id"`
	}
	if err := json.Unmarshal(args, &input); err != nil {
		return "", fmt.Errorf("invalid arguments: %w", err)
	}
	if input.AccountID == "ACC-4092" {
		return `{"account_id": "ACC-4092", "balance_cents": 142050000, "status": "FLAGGED"}`, nil
	}
	return `{"error": "account not found"}`, nil
}

// FreezeAccountTool locks down an account flagged for risk.
type FreezeAccountTool struct{}

func (t *FreezeAccountTool) Name() string { return "freeze_account" }
func (t *FreezeAccountTool) Description() string {
	return "Freeze an account given account_id and security justification."
}
func (t *FreezeAccountTool) Execute(ctx context.Context, args json.RawMessage) (string, error) {
	var input struct {
		AccountID string `json:"account_id"`
		Reason    string `json:"reason"`
	}
	if err := json.Unmarshal(args, &input); err != nil {
		return "", fmt.Errorf("invalid arguments: %w", err)
	}
	return fmt.Sprintf(`{"status": "FROZEN", "account_id": %q, "reason": %q}`, input.AccountID, input.Reason), nil
}

// Agent coordinates the ReAct loop.
type Agent struct {
	tools         map[string]Tool
	maxIterations int
	step          int
}

func NewAgent(tools ...Tool) *Agent {
	tm := make(map[string]Tool, len(tools))
	for _, tool := range tools {
		tm[tool.Name()] = tool
	}
	return &Agent{
		tools:         tm,
		maxIterations: 5,
	}
}

// simulateLLM returns deterministic ReAct steps for demonstration.
func (a *Agent) simulateLLM(history []Message) (ModelResponse, error) {
	a.step++
	switch a.step {
	case 1:
		return ModelResponse{
			Thought: "Suspicious activity detected on ACC-4092. I must inspect the account balance and flag state first.",
			ToolCall: &ToolCall{
				Name: "get_balance",
				Args: json.RawMessage(`{"account_id": "ACC-4092"}`),
			},
		}, nil
	case 2:
		return ModelResponse{
			Thought: "ACC-4092 has $1,420,500.00 USD and is marked FLAGGED. Corporate policy mandates freezing the account immediately.",
			ToolCall: &ToolCall{
				Name: "freeze_account",
				Args: json.RawMessage(`{"account_id": "ACC-4092", "reason": "High-risk unverified outflow"}`),
			},
		}, nil
	default:
		return ModelResponse{
			Thought: "Account freeze confirmed. I can now emit the final incident report.",
			Final:   "Incident triage resolved: Account ACC-4092 successfully frozen under policy rule POL-88. Incident ticket INC-904 filed.",
		}, nil
	}
}

// Run executes the bounded ReAct loop with context cancellation.
func (a *Agent) Run(ctx context.Context, prompt string) (string, error) {
	history := []Message{
		{Role: "system", Content: "You are an autonomous incident triage agent for Meridian Financial Services."},
		{Role: "user", Content: prompt},
	}

	for iter := 1; iter <= a.maxIterations; iter++ {
		select {
		case <-ctx.Done():
			return "", ctx.Err()
		default:
		}

		fmt.Printf("--- [Cycle %d] Invoking Inference Engine ---
", iter)
		resp, err := a.simulateLLM(history)
		if err != nil {
			return "", fmt.Errorf("llm inference failure: %w", err)
		}

		fmt.Printf("THOUGHT: %s
", resp.Thought)

		if resp.Final != "" {
			fmt.Printf("FINAL ANSWER: %s
", resp.Final)
			return resp.Final, nil
		}

		if resp.ToolCall == nil {
			return "", fmt.Errorf("malformed agent step: neither final answer nor tool call provided")
		}

		tool, exists := a.tools[resp.ToolCall.Name]
		var observation string
		if !exists {
			observation = fmt.Sprintf("Error: tool %q is not registered", resp.ToolCall.Name)
		} else {
			fmt.Printf("ACTION: Executing %q with args: %s
", resp.ToolCall.Name, string(resp.ToolCall.Args))
			obs, execErr := tool.Execute(ctx, resp.ToolCall.Args)
			if execErr != nil {
				observation = fmt.Sprintf("Tool execution error: %v", execErr)
			} else {
				observation = obs
			}
		}

		fmt.Printf("OBSERVATION: %s

", observation)
		history = append(history,
			Message{Role: "assistant", Content: fmt.Sprintf("Thought: %s
Action: %s", resp.Thought, resp.ToolCall.Name)},
			Message{Role: "observation", Content: observation},
		)
	}

	return "", fmt.Errorf("agent exceeded max iterations (%d) without resolution", a.maxIterations)
}

func main() {
	ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
	defer cancel()

	agent := NewAgent(&LedgerBalanceTool{}, &FreezeAccountTool{})
	resolution, err := agent.Run(ctx, "Audit account ACC-4092 and secure funds if suspicious.")
	if err != nil {
		fmt.Printf("Agent run failed: %v
", err)
		return
	}
	fmt.Printf("
SUCCESS: %s
", resolution)
}
```

## Fan-Out / Fan-In Agent Swarms

A single ReAct agent running in isolation is fundamentally limited. When triaging a complex financial incident, investigating the case sequentially—auditing the ledger database (400ms), checking OFAC sanctions lists (600ms), analyzing client device telemetry (500ms), and reviewing historical transaction graphs (800ms)—compounds into a 2,300ms serial latency bottleneck.

In high-frequency fintech, 2.3 seconds is an eternity. We solve this by fanning out specialized subagents concurrently into an **Agent Swarm**.

<Define term="Agent Swarm">
A coordinated collection of autonomous agents that execute concurrently on decomposed subtasks, communicating partial discoveries through channels or message queues, and aggregating their findings to reach consensus faster and with higher fidelity than a single monolithic prompt.
</Define>

### Concurrency Mechanics: errgroup and Bounded Worker Pools

Firing off unthrottled goroutines for every agent task is the quickest way to crash your service. If a supervisor spawns 500 subagents simultaneously, you will instantly hit provider rate limits (`HTTP 429 Too Many Requests`), exhaust local ephemeral TCP ports, and starve CPU resources.

We orchestrate agent swarms using two core primitives:
1. **`golang.org/x/sync/errgroup`**: Coordinates goroutines, propagates context cancellation on failure, and captures the first fatal error.
2. **Counting Semaphore (`chan struct{}`)**: Strictly bounds concurrent active LLM invocations to match provider rate limits.

```go
type SwarmCoordinator struct {
	sem chan struct{} // bounded concurrency semaphore
}

func NewSwarmCoordinator(maxConcurrent int) *SwarmCoordinator {
	return &SwarmCoordinator{
		sem: make(chan struct{}, maxConcurrent),
	}
}

func (s *SwarmCoordinator) ExecuteSwarm(ctx context.Context, tasks []AgentTask) ([]TaskResult, error) {
	g, ctx := errgroup.WithContext(ctx)
	results := make([]TaskResult, len(tasks))

	for i, task := range tasks {
		g.Go(func() error {
			// Acquire semaphore slot or abort on context cancellation
			select {
			case s.sem <- struct{}{}:
				defer func() { <-s.sem }()
			case <-ctx.Done():
				return ctx.Err()
			}

			res, err := task.Agent.Run(ctx, task.Prompt)
			if err != nil {
				// Distinguish between fatal and non-critical agent errors
				if task.Critical {
					return fmt.Errorf("critical subagent %q failed: %w", task.Name, err)
				}
				results[i] = TaskResult{TaskID: task.ID, Error: err.Error()}
				return nil
			}

			results[i] = TaskResult{TaskID: task.ID, Output: res}
			return nil
		})
	}

	if err := g.Wait(); err != nil {
		return nil, err
	}
	return results, nil
}
```

<ConceptGrid cols={3}>
  <ConceptCard label="Bounded Semaphore">
    A buffered channel `make(chan struct{}, limit)` enforces an upper bound on active LLM API calls, preventing HTTP 429 rate limit bans.
  </ConceptCard>
  <ConceptCard label="Error Segregation">
    Critical subagents (e.g. OFAC Sanctions) cancel the entire swarm on failure. Advisory subagents (e.g. Market Sentiment) fail gracefully without aborting the audit.
  </ConceptCard>
  <Gotcha>
    Never send subagent results to an unbuffered channel without selecting on `ctx.Done()`. If the supervisor exits early on an error, remaining subagents will deadlock forever.
  </Gotcha>
</ConceptGrid>

## Supervisor & Worker Routing

Complex financial goals cannot be solved by flat fan-out alone. If the task is "Investigate transaction TX-882, verify compliance, calculate tax adjustments, and propose settlement", the subtasks form a **Directed Acyclic Graph (DAG)**: tax adjustments cannot be calculated until transaction facts are verified.

This requires the **Supervisor Pattern**.

<Define term="Supervisor Pattern">
An architectural topology where a centralized executive agent dynamically analyzes a high-level goal, partitions it into a dependency graph of discrete subtasks, routes those tasks to specialized worker agents with private communication channels, and synthesizes the outputs into a coherent resolution.
</Define>

### Dynamic DAG Partitioning

The Supervisor does not hardcode workflow steps. Instead, it prompts an executive LLM with structured output constraints to generate a dynamic execution plan:

```go
type SubTask struct {
	ID           string   `json:"id"`
	WorkerType   string   `json:"worker_type"` // "researcher", "auditor", "coder"
	Instruction  string   `json:"instruction"`
	Dependencies []string `json:"dependencies"` // Task IDs that must finish first
}

type ExecutionPlan struct {
	Rationale string    `json:"rationale"`
	Tasks     []SubTask `json:"tasks"`
}
```

### Channel-Based Worker Topology

Each specialized worker agent runs in its own isolated goroutine, consuming jobs from a private channel and emitting results to a shared supervisor bus. This decouples worker lifecycles from supervisor scheduling:

```
[Client Request]
       │
       ▼
[Supervisor Agent]
   │       │       │
   │ task1 │ task2 │ task3
   ▼       ▼       ▼
[Researcher] [Auditor] [Coder]
 (Worker 1)  (Worker 2) (Worker 3)
   │       │       │
   └───────┼───────┘
           ▼
     [Result Bus]
           │
           ▼
  [Aggregator / Final]
```

### Deadlock Prevention in Worker Channels

When dispatching tasks across channels, deadlocks arise when a supervisor attempts to send to a worker whose input queue is full, or when a worker tries to write back to an unread results channel.

Modern Go solves this with non-blocking selects and buffered boundaries:

```go
type WorkerPool struct {
	tasks   chan AgentTask
	results chan AgentResult
	quit    chan struct{}
}

func (w *WorkerPool) Start(ctx context.Context, numWorkers int) {
	for range numWorkers { // Go 1.22+ range over integer
		go func() {
			for {
				select {
				case <-ctx.Done():
					return
				case <-w.quit:
					return
				case task, ok := <-w.tasks:
					if !ok {
						return
					}
					out, err := task.Execute(ctx)
					select {
					case w.results <- AgentResult{TaskID: task.ID, Output: out, Err: err}:
					case <-ctx.Done():
						return
					}
				}
			}
		}()
	}
}
```

## Type-Safe Tool Calling

In dynamically typed languages, developers parse tool arguments with arbitrary dictionaries and pray the keys exist at runtime. When an LLM passes `"amount": "1000"` (a string) instead of `1000` (an integer), untyped code crashes with a runtime type exception.

In Go, we demand static type safety, schema generation, and strict deserialization boundaries.

<Define term="Type-Safe Tool Execution">
The practice of binding LLM tool definitions directly to strongly typed Go structs and method signatures, using reflection to auto-generate standard JSON Schemas for the model and unmarshaling incoming JSON payloads with strict field validation.
</Define>

### The Tool Contract

A production tool in Go must expose its name, description, JSON Schema definition, and an execution handler:

```go
type ToolDefinition struct {
	Name        string          `json:"name"`
	Description string          `json:"description"`
	Parameters  json.RawMessage `json:"parameters"` // JSON Schema object
}

type ExecutableTool interface {
	Definition() ToolDefinition
	Execute(ctx context.Context, rawArgs json.RawMessage) (string, error)
}
```

### Zero-Allocation Typed Dispatch with Generics

Rather than writing repetitive boilerplate for every tool, we can write a generic constructor `NewTypedTool` that converts any typed function `func(context.Context, Req) (Resp, error)` into an `ExecutableTool`:

```go
type TypedTool[Req any, Resp any] struct {
	name        string
	description string
	schema      json.RawMessage
	handler     func(context.Context, Req) (Resp, error)
}

func NewTypedTool[Req any, Resp any](
	name string,
	description string,
	schema json.RawMessage,
	handler func(context.Context, Req) (Resp, error),
) *TypedTool[Req, Resp] {
	return &TypedTool[Req, Resp]{
		name:        name,
		description: description,
		schema:      schema,
		handler:     handler,
	}
}

func (t *TypedTool[Req, Resp]) Definition() ToolDefinition {
	return ToolDefinition{
		Name:        t.name,
		Description: t.description,
		Parameters:  t.schema,
	}
}

func (t *TypedTool[Req, Resp]) Execute(ctx context.Context, rawArgs json.RawMessage) (string, error) {
	var req Req
	// Strict decoding: reject unknown fields to catch model hallucinations early
	dec := json.NewDecoder(bytes.NewReader(rawArgs))
	dec.DisallowUnknownFields()
	if err := dec.Decode(&req); err != nil {
		return "", fmt.Errorf("invalid arguments schema for tool %s: %w", t.name, err)
	}

	resp, err := t.handler(ctx, req)
	if err != nil {
		return "", err
	}

	outBytes, err := json.Marshal(resp)
	if err != nil {
		return "", fmt.Errorf("failed marshaling tool response: %w", err)
	}
	return string(outBytes), nil
}
```

### System Errors vs. Domain Observations

A critical design rule in tool execution: **never return a Go error to the caller when the tool successfully executed but the domain operation was rejected.**

- **System Error (Go `error`)**: Database connection pool exhausted, network timeout, memory allocation failure. Action: Abort the tool step or cancel the agent.
- **Domain Observation (Payload String)**: "Account ACC-101 has insufficient funds ($42.00 available, $500.00 requested)". Action: Return this text as an Observation so the LLM can reason about alternative actions.

## Human-in-the-Loop Approval Gates

An autonomous agent with read-only tools is a research assistant. An autonomous agent with write access to financial ledgers, wire transfer gateways, or production databases is a loaded weapon.

Unchecked autonomy in enterprise systems is criminal negligence. Every mutating, destructive, or high-capital action must pass through a **Human-in-the-Loop Approval Gate**.

<Define term="Human-in-the-Loop">
A deterministic safety gate where an autonomous agent intercepts high-impact or mutating tool invocations, suspends execution, and awaits cryptographically verified human authorization before committing state transitions.
</Define>

### Suspending and Resuming Agent Goroutines

When an agent decides to invoke a dangerous tool (e.g. `ExecuteWireTransfer($2,500,000)`), the tool executor must:
1. Generate a cryptographically secure `ApprovalRequest`.
2. Push the pending approval request to an administrative queue (via PostgreSQL, Redis, or WebSockets).
3. Suspend the agent's goroutine on a private response channel.
4. Enforce a strict timeout deadline: if the human operator does not approve the request within 5 minutes, the action times out and is cleanly aborted.

```go
type ApprovalDecision struct {
	Approved  bool
	Operator  string
	Reason    string
	Signature string
}

type ApprovalGate struct {
	mu      sync.Mutex
	pending map[string]chan ApprovalDecision
}

func NewApprovalGate() *ApprovalGate {
	return &ApprovalGate{
		pending: make(map[string]chan ApprovalDecision),
	}
}

func (g *ApprovalGate) RequestApproval(ctx context.Context, requestID string) (ApprovalDecision, error) {
	ch := make(chan ApprovalDecision, 1)

	g.mu.Lock()
	g.pending[requestID] = ch
	g.mu.Unlock()

	// Guarantee cleanup of the pending map to prevent memory leaks!
	defer func() {
		g.mu.Lock()
		delete(g.pending, requestID)
		g.mu.Unlock()
	}()

	select {
	case decision := <-ch:
		return decision, nil
	case <-ctx.Done():
		return ApprovalDecision{}, ctx.Err()
	}
}

func (g *ApprovalGate) ResolveApproval(requestID string, decision ApprovalDecision) bool {
	g.mu.Lock()
	ch, exists := g.pending[requestID]
	g.mu.Unlock()

	if !exists {
		return false
	}

	select {
	case ch <- decision:
		return true
	default:
		return false
	}
}
```

<UnderTheHood title="Agent Concurrency, Context Cancellation & Goroutine Leak Prevention">

In production agent orchestration, the most common source of system instability is **goroutine leaks triggered by stalled LLM calls or abandoned channels**.

### The Anatomy of an Agent Goroutine Leak

Consider what happens when a user cancels an HTTP request or navigates away while a multi-agent swarm is running:
1. If your HTTP client does not bind the incoming request's `r.Context()` to outgoing LLM client calls, the subagent goroutine remains active in the background, consuming memory and compute.
2. If your subagents send their findings to an unbuffered channel and the supervisor exits early due to an error, every remaining worker goroutine blocks on `ch <- result` forever.

In Go runtime terms, a blocked goroutine is kept alive by the scheduler (`runtime.g`). Its 2KB to 8KB stack cannot be garbage collected, nor can any heap objects reachable from its stack frames (such as 100KB conversation history buffers and HTTP transport buffers). If your service processes 10,000 agent queries per hour and leaks 3 goroutines per query, you accumulate 30,000 dead goroutines per hour, eventually triggering out-of-memory (OOM) pod evictions.

### Cascading Cancellation with context.WithCancelCause (Go 1.26)

As of Go 1.26, `context.WithCancelCause` allows parent orchestrators to cancel child trees while attaching the exact domain error:

```go
ctx, cancel := context.WithCancelCause(parentCtx)

// If an auditor detects sanctions violation:
cancel(fmt.Errorf("OFAC violation on account %s: transfer blocked", accID))

// The supervisor inspects why the swarm collapsed:
if cause := context.Cause(ctx); cause != nil {
    slog.Error("swarm terminated", "cause", cause)
}
```

### Detecting Leaks with the Go 1.26 goroutineleak Profile

In Go 1.26, the runtime introduces the experimental `goroutineleak` pprof profile (`/debug/pprof/goroutineleak`). Unlike the standard `/debug/pprof/goroutine` endpoint which dumps all active goroutines, `goroutineleak` specifically flags goroutines that have been blocked on channel operations or network pollers with zero scheduler wakeups over an extended sliding window.

Furthermore, you can monitor `/sched/goroutines:goroutines` via `runtime/metrics`. If this gauge monotonically rises during steady-state traffic, an unbuffered channel or uncancelled LLM context is leaking agent workers.

</UnderTheHood>

<Callout kind="pro" title="Container-Aware GOMAXPROCS in Go 1.25+">
In Kubernetes, CPU limits are enforced via Linux cgroups. Prior to Go 1.25, `runtime.GOMAXPROCS` defaulted to the physical node's total CPU core count, leading to massive CPU throttling when running inside a 2-core container on a 64-core host. Engineers were forced to import `go.uber.org/automaxprocs`.

As of Go 1.25, the Go runtime is natively **container-aware**. It queries cgroup quotas at startup and dynamically adjusts `GOMAXPROCS` to match the container's CPU quota. In high-concurrency agent swarms, this ensures the Go scheduler's work-stealing queues match your exact allocated container compute without third-party dependencies.
</Callout>

<Exercise n={2} title="Context-Bounded Fan-Out Swarm" level="medium">

Build a concurrent swarm runner that executes 3 worker agents in parallel with a strict 200ms context timeout. Collect all completed results into a thread-safe slice using `sync.Mutex`. Ensure that if a worker fails or exceeds the timeout, the error is recorded without panicking.

<Solution>

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"time"
)

type WorkerResult struct {
	WorkerID string
	Payload  string
	Err      error
}

func RunWorker(ctx context.Context, id string, delay time.Duration) (string, error) {
	select {
	case <-time.After(delay):
		return fmt.Sprintf("Worker %s successfully completed analysis", id), nil
	case <-ctx.Done():
		return "", ctx.Err()
	}
}

func main() {
	ctx, cancel := context.WithTimeout(context.Background(), 200*time.Millisecond)
	defer cancel()

	workers := []struct {
		id    string
		delay time.Duration
	}{
		{"worker-fast", 50 * time.Millisecond},
		{"worker-medium", 100 * time.Millisecond},
		{"worker-slow", 500 * time.Millisecond}, // Will exceed 200ms timeout!
	}

	var mu sync.Mutex
	var results []WorkerResult
	var wg sync.WaitGroup

	for _, w := range workers {
		wg.Add(1)
		go func(id string, d time.Duration) {
			defer wg.Done()
			payload, err := RunWorker(ctx, id, d)
			mu.Lock()
			results = append(results, WorkerResult{WorkerID: id, Payload: payload, Err: err})
			mu.Unlock()
		}(w.id, w.delay)
	}

	wg.Wait()

	fmt.Printf("Swarm execution completed with %d results:
", len(results))
	for _, res := range results {
		if res.Err != nil {
			fmt.Printf("- [%s] FAILED: %v
", res.WorkerID, res.Err)
		} else {
			fmt.Printf("- [%s] SUCCESS: %s
", res.WorkerID, res.Payload)
		}
	}
}
```

Each worker runs in its own goroutine, synchronized by `sync.WaitGroup`. The `sync.Mutex` protects concurrent writes to the shared results slice, while `ctx.Done()` ensures slow workers abort cleanly.

import (
	"context"
	"errors"
	"fmt"
	"sync"
	"time"
)

type GateDecision struct {
	Approved bool
	Approver string
}

type Gate struct {
	mu      sync.Mutex
	pending map[string]chan GateDecision
}

func NewGate() *Gate {
	return &Gate{pending: make(map[string]chan GateDecision)}
}

func (g *Gate) AwaitApproval(ctx context.Context, id string) (GateDecision, error) {

	g.mu.Lock()
	g.pending[id] = ch
	g.mu.Unlock()

	// Guarantee cleanup regardless of outcome
	defer func() {
		g.mu.Lock()
		delete(g.pending, id)
		g.mu.Unlock()
	}()

	select {
	case decision := <-ch:
		return decision, nil
	case <-ctx.Done():
		return GateDecision{}, ctx.Err()
	}
}

func (g *Gate) SubmitDecision(id string, decision GateDecision) error {
	g.mu.Lock()
	ch, exists := g.pending[id]
	g.mu.Unlock()

	if !exists {
		return errors.New("approval request not found or expired")
	}

	select {
	case ch <- decision:
		return nil
	default:
		return errors.New("decision already registered")
	}
}

	gate := NewGate()
	ctx, cancel := context.WithTimeout(context.Background(), 100*time.Millisecond)
	defer cancel()

	// Simulate human approving asynchronously after 30ms

", err)

	}
	fmt.Printf("Approval granted by %s: %v
", decision.Approver, decision.Approved)

	// Verify pending map is clean
	gate.mu.Lock()
	pendingLen := len(gate.pending)
	gate.mu.Unlock()
	fmt.Printf("Active pending approvals remaining: %d
", pendingLen)
}

<Recap>

- **The Autonomous ReAct Loop**: Alternates between Thought, Action (tool invocation), and Observation (result feedback). In Go, loops must be bounded by iteration limits and context deadlines to prevent infinite token spin and billing disasters.
- **Fan-Out / Fan-In Swarms**: Concurrent subagents orchestrated via `errgroup.Group` or worker pools reduce multi-source investigation latency from serial seconds to parallel milliseconds. Bounded semaphores prevent HTTP 429 rate limit bans.
- **Supervisor-Worker Routing**: Supervisors dynamically partition objectives into Directed Acyclic Graphs (DAGs) and route tasks across private worker channels, eliminating synchronization bottlenecks.
- **Type-Safe Tool Calling**: Go struct binding and `json.NewDecoder(r).DisallowUnknownFields()` enforce static validation on LLM payloads. System errors abort execution; domain errors are returned as observations to allow the agent to self-correct.
- **Human-in-the-Loop Gates**: High-risk mutating actions suspend agent goroutines on private channels, awaiting human operator authorization with strict timeout deadlines and deterministic cleanup.
- **Goroutine Leak Prevention**: Never send to unbuffered channels without selecting on `ctx.Done()`. Audit active agent goroutines with the Go 1.26 `goroutineleak` profile and monitor `/sched/goroutines:goroutines`.
