## A01 · Broken Access Control — First American Financial

<Define term="A01 Broken Access Control">
Failure to enforce what an authenticated (or unauthenticated) principal may do — IDOR/BOLA, missing function-level checks, privilege escalation, cross-tenant access. OWASP's **#1** risk since 2021. The **Broken Access Control** chapter covers the full taxonomy; this is the canonical breach.
</Define>

**The case — First American Financial, 2019 (~885,000,000 files).** A real-estate title insurer published document images at URLs like `…/DocumentLink?id=000000075`. The ID was **sequential**, and there was **no authentication** on the page at all. Change the number up or down and you got someone else's document — and the documents held Social Security numbers, bank statements, driver's licenses, mortgage and tax records, and wire receipts. The lowest valid ID pointed at a 2003 transaction; the highest was around **885 million**. A bug-hunter's entire exploit was a `for` loop over an integer. (Reported by Brian Krebs.)

That is the loop from the last section in its purest form: recon found one document URL, mapping noticed the ID was sequential, probing as "not the owner" returned the file anyway, and the impact was the entire archive.

<Callout kind="warn" title="Hunt tip">
Whenever an object ID appears in a URL, a hidden field, or a JSON body, the first test is: log in as user B and request user A's ID. If it returns the object, that is A01. Sequential or guessable IDs turn one leak into a full enumeration — but unguessable IDs are not the fix; the ownership check is. See the **Broken Access Control** chapter for the Go patterns in depth.
</Callout>

## A02 · Cryptographic Failures — Adobe

<Define term="A02 Cryptographic Failures">
Sensitive data protected by the wrong primitive, a weak mode, a reused key, or — worst — not protected at all. Includes storing passwords reversibly, using ECB mode, hardcoding keys, and weak randomness (covered in **Security for Financial Systems**).
</Define>

**The case — Adobe, 2013 (153,000,000 accounts).** Adobe stored passwords with **3DES in ECB mode**, using **the same key for every password**, and stored each user's **password hint in plaintext**. Three compounding errors. ECB enciphers each block independently, so two users with the same password got the *same ciphertext* — and the plaintext hints ("name of my dog", "all zeros") gave researchers a crib. With one key, identical ciphertexts, and millions of known plaintexts, the community reconstructed a top-100 password list from the dump. The lesson isn't "use a stronger cipher." It's that **passwords must never be encrypted at all** — they must be slow-hashed with a salt, so there is no key to steal and nothing to decrypt.

This snippet shows the ECB failure directly: identical plaintext blocks leak as identical ciphertext.

```go
package main

import (
	"crypto/aes"
	"encoding/hex"
	"fmt"
)

// ecbEncrypt enciphers each 16-byte block independently — no chaining, no IV.
// Identical plaintext blocks therefore produce identical ciphertext blocks.
// This is structurally how Adobe stored 153M passwords (3DES-ECB, one key).
func ecbEncrypt(key, data []byte) []byte {
	block, _ := aes.NewCipher(key)
	bs := block.BlockSize()
	out := make([]byte, len(data))
	for i := 0; i < len(data); i += bs {
		block.Encrypt(out[i:i+bs], data[i:i+bs])
	}
	return out
}

func main() {
	key := make([]byte, 16) // all-zero demo key — never do this anywhere

	// Two records whose first 16 bytes are identical ("password1234567 ").
	a := []byte("password1234567 likes cats here!")
	b := []byte("password1234567 hates dogs there")

	ca := ecbEncrypt(key, a)
	cb := ecbEncrypt(key, b)

	fmt.Println("record A block0:", hex.EncodeToString(ca[:16]))
	fmt.Println("record B block0:", hex.EncodeToString(cb[:16]))
	fmt.Println("first block identical:", hex.EncodeToString(ca[:16]) == hex.EncodeToString(cb[:16]))
	// true — ECB leaks that both records share their first 16 plaintext bytes.
	// For passwords the fix is not a better cipher: slow-hash (bcrypt/argon2),
	// salt per user, and never decrypt — you verify a hash, you don't recover it.
}
```

## A03 · Injection — Heartland Payment Systems

<Define term="A03 Injection">
Untrusted input interpreted as code or structure rather than data — SQL, OS command, LDAP, path traversal, XSS. The **Application Security Baseline** chapter (Part 2) covers the family; this is the most expensive instance.
</Define>

**The case — Heartland Payment Systems, 2008 (~130,000,000 cards).** Albert Gonzalez and accomplices used **SQL injection** against web applications to get a foothold, then planted packet sniffers that captured card data flowing across the network. Across Heartland, Hannaford, 7-Eleven and others, the indictment put it at **130 million** card numbers — at the time the largest such case in US history. Gonzalez was sentenced to 20 years. The entry point — the thing that turned a public website into network access — was untrusted input concatenated into a query.

The mechanism is always the same: a value the user controls lands inside the query *string*, so the attacker ends the data and starts writing SQL. The fix is a **parameterized query**, where the template and the values travel separately and the driver guarantees the value is never parsed as SQL.

<Callout kind="warn" title="Hunt tip — how SQLi is actually found (incl. the blind kind)">
You rarely see "SQL error" on a page anymore, so detection is indirect, and it works on *every* input — not just the obvious search box. A real €3,500 first-bounty SQLi was in a health site's **BMI calculator**, in the `unitWeight` field of a POST body — a parameter nobody expects to touch a database. The hunting steps:

1. **Break the quote.** Inject a single `'` into each parameter. A `500` (or any behavior change) means your quote reached the SQL string and unbalanced it.
2. **Balance it back.** Send `''` (or a valid `'...'`). If the error *disappears*, you've confirmed your input is being parsed as SQL, not treated as data — that toggle is the tell.
3. **Go time-based when there's no output.** If you can't see errors or results (**blind** SQLi), prove execution with a delay payload — the classic MySQL form is `'XOR(if(now()=sysdate(),sleep(10),0))XOR'Z`, which makes the response hang ~10 seconds *only if* the injection runs. A reproducible delay that tracks your `sleep(N)` is proof.

The defensive lesson cuts through all of it: **a parameterized query makes every one of these probes inert**, because the value is never parsed as SQL — there's no quote to break, no string to delay. Detection technique doesn't matter when the value can't reach the parser. (And note where it was found — an unglamorous calculator field. Fuzz *every* parameter, not just the search bar.)
</Callout>

<Gotcha>
"We escape the input" is not the fix — escaping is a blocklist you will eventually get wrong (encodings, edge cases, second-order injection). Parameterized queries are an allow-list by construction: the value is *data*, full stop. Go's `database/sql` placeholders (`$1`, `?`) and `os/exec`'s argument slice are the right tools. The **Application Security Baseline** chapter walks SQL, command, and path-traversal injection with runnable Go.
</Gotcha>

### A03 deep cut · Template/Expression injection (SSTI) — and why a WAF won't save you

SQL injection has a sibling that hits *templating and expression engines*: **SSTI** (server-side template injection). It happens when **user input becomes part of the template itself**, not the data the template renders. The template engine then evaluates the attacker's input as code — leaking fields, and in expression languages with reflection, reaching **RCE**.

<Define term="SSTI (server-side template injection)">
**SSTI** is injection into a template or expression engine: untrusted input is compiled *as template/expression source* rather than passed *as data* to a fixed template. The engine evaluates it — so the attacker can read in-scope variables, call methods, and (in powerful engines like Spring's **SpEL**, Jinja2, Freemarker) reach arbitrary code execution via reflection. The tell during hunting: inject `${7*7}` / `{{7*7}}` / `#{7*7}` and look for `49` in the response — arithmetic evaluating means the engine is parsing your input. The fix is the same shape as parameterized SQL: **never compile user input as a template; pass it as data to a fixed template.**
</Define>

**The case — Spring SpEL + Akamai WAF bypass → RCE (a 2024-era disclosed writeup).** A Spring Boot app rendered exception messages through **SpEL** with recursive evaluation, so a request parameter was evaluated as an expression (`${x*y}` returned the product). Akamai's WAF blocked the obvious payloads — `T(java.lang.Runtime)`, quotes, string literals. The hunter bypassed it by **building strings without quotes**: reach a class via a primitive (`${2.class}` → `Integer`), turn ASCII numbers into characters (`Character.toString(99)` → `c`), `+`-concatenate them into method/command names, and invoke `Runtime.getRuntime().exec(...)` through **reflection** — dodging every signature the WAF matched. Cost: ~45 bytes of expression per character, a >3KB final payload, ~500 attempts over 14 hours. The lesson isn't the Java syntax — it's that **a signature WAF matches *syntax*, and any expression language has infinite equivalent syntaxes.**

Go has its own SSTI footgun, and it's a one-character difference — `text/template` (no auto-escaping) vs `html/template` (contextual auto-escaping), and worst of all, **compiling user input as the template text**:

<GoPlayground>

```go
package main

import (
	"bytes"
	"fmt"
	htmpl "html/template"
	ttmpl "text/template"
)

type page struct {
	User   string
	secret string // unexported → a template CANNOT reach this ({{.secret}} errors)
	APIKey string // exported → an attacker-controlled template CAN print this
}

func render(engine string, tmplText string, data page) string {
	var b bytes.Buffer
	switch engine {
	case "html":
		t, err := htmpl.New("p").Parse(tmplText)
		if err != nil {
			return "parse error: " + err.Error()
		}
		t.Execute(&b, data)
	default:
		t, err := ttmpl.New("p").Parse(tmplText)
		if err != nil {
			return "parse error: " + err.Error()
		}
		t.Execute(&b, data)
	}
	return b.String()
}

func main() {
	data := page{User: "<script>alert(1)</script>", APIKey: "sekret-key-123"}

	// SAFE pattern: fixed template, user value is DATA. html/template escapes it.
	fmt.Println("html (escapes XSS):", render("html", "Hi {{.User}}", data))
	// text/template does NOT escape — the script tag passes through (stored XSS).
	fmt.Println("text (no escape):  ", render("text", "Hi {{.User}}", data))

	// SSTI: the USER controls the template text. They print fields they shouldn't.
	attacker := "{{.APIKey}}" // attacker-supplied "template"
	fmt.Println("SSTI leaks field:  ", render("text", attacker, data))
}
```

<Gotcha>
**A WAF in front of an injection is a speed bump, not a wall.** The SpEL case is the proof: every payload the WAF knew, the hunter rewrote in equivalent syntax it didn't. Signature filters match *what an attack looks like*, and injection has unbounded equivalent forms (reflection, numeric→char, concatenation, encoding). Treat a WAF as defense-in-depth that buys time and raises noise — never as *the* control. The real fixes are structural and the same across the injection family: **don't compile untrusted input as code** (template, expression, SQL, shell), pass it as **data** to a fixed structure, use `html/template` for HTML output, and pick expression libraries that don't expose reflection to user input. If your defense is "the WAF blocks that," you don't have a fix — you have a delay.
</Gotcha>

## A04 · Insecure Design — Starbucks Gift Cards

<Define term="A04 Insecure Design">
A flaw in the logic itself — not a missing patch but a design that is exploitable as built. Business-logic bypasses, missing rate limits as a design choice, and **race conditions** (TOCTOU: time-of-check to time-of-use) all live here.
</Define>

**The case — Starbucks gift cards, 2015 (Egor Homakov).** Homakov bought three $5 gift cards and found that transferring a balance between cards was a **check-then-act** sequence — check the source balance, credit the destination, debit the source — performed in a multi-threaded environment **without a lock**. By firing the transfer from two browser sessions at once, both passed the balance check against the *same* $5 before either debit landed, and the money was duplicated. He turned $15 into $20 of spendable balance and proved it by buying coffee. The flaw wasn't a bug in one line; it was the *design* — a non-atomic money movement. (Starbucks' response was to threaten him rather than thank him.)

The Go fix makes the check and both updates **atomic** — one lock (or one database transaction with `SELECT … FOR UPDATE`) around the whole movement, so two transfers can never both pass the check on the same funds.

```go
package main

import (
	"fmt"
	"sync"
)

type Wallet struct {
	mu  sync.Mutex
	bal map[string]int64
}

// transfer is ATOMIC: the balance check and BOTH updates happen under one
// lock. Two concurrent transfers can never both pass the check on the same
// funds — which is exactly the Starbucks bug, performed without the lock.
func (w *Wallet) transfer(from, to string, amt int64) bool {
	w.mu.Lock()
	defer w.mu.Unlock()
	if w.bal[from] < amt {
		return false
	}
	w.bal[from] -= amt
	w.bal[to] += amt
	return true
}

func (w *Wallet) total() int64 {
	w.mu.Lock()
	defer w.mu.Unlock()
	var s int64
	for _, v := range w.bal {
		s += v
	}
	return s
}

func main() {
	w := &Wallet{bal: map[string]int64{"card_A": 500, "card_B": 0, "card_C": 0}}
	start := w.total()

	// Hammer the same source card from many goroutines at once.
	var wg sync.WaitGroup
	for i := 0; i < 100; i++ {
		wg.Add(1)
		go func() {
			defer wg.Done()
			w.transfer("card_A", "card_B", 5)
			w.transfer("card_A", "card_C", 5)
		}()
	}
	wg.Wait()

	fmt.Printf("total before=%d after=%d conserved=%v\n", start, w.total(), start == w.total())
	// conserved=true — money is never created. Drop the lock and the
	// check-then-act race lets two transfers spend the same balance.
}
```

	"fmt"

	mu  sync.Mutex
	bal map[string]int64

	w.mu.Lock()
	defer w.mu.Unlock()
	if w.bal[from] < amt {
		return false
	}
	w.bal[from] -= amt
	w.bal[to] += amt
	return true
}

func (w *Wallet) total() int64 {
	w.mu.Lock()
	defer w.mu.Unlock()
	var s int64
	for _, v := range w.bal {
		s += v
	}
	return s
}

			defer wg.Done()
			w.transfer("card_A", "card_B", 5)
			w.transfer("card_A", "card_C", 5)
		}()
	}

## A06 · Vulnerable & Outdated Components — Equifax

## A07 · Identification & Authentication Failures — Instagram

<Define term="A07 Identification & Authentication Failures">
Weak or bypassable proof of identity — credential stuffing, weak session handling, and brute-forceable verification codes. Often the rate limit exists but is keyed wrong.
</Define>

**The case — Instagram, 2019 (Laxman Muthiyah, $30,000).** Instagram's mobile password reset sent a **six-digit code** (a million possibilities) and rate-limited guesses. Muthiyah found the limit was effectively **per source IP**: of 1,000 requests from one IP, ~250 went through and the rest were blocked. So he rotated IPs — a race condition plus thousands of source addresses — and showed that with enough IPs an attacker could burn through the entire code space inside the validity window and take over any account. Facebook paid **$30,000**. The fix is to rate-limit the **action against the target account**, not the source IP, so rotating IPs buys the attacker nothing.

```go
package main

import (
	"fmt"
	"sync"
)

// attemptLimiter caps verification-code attempts PER ACCOUNT, not per IP.
// Instagram's flaw: the budget was effectively per source IP, so rotating
// across thousands of IPs reset it and brute-forced the 6-digit code.
// Keying the counter on the target account makes IP rotation useless.
type attemptLimiter struct {
	mu  sync.Mutex
	n   map[string]int
	max int
}

func newLimiter(max int) *attemptLimiter {
	return &attemptLimiter{n: map[string]int{}, max: max}
}

func (l *attemptLimiter) allow(account string) bool {
	l.mu.Lock()
	defer l.mu.Unlock()
	if l.n[account] >= l.max {
		return false
	}
	l.n[account]++
	return true
}

func verify(code, guess string) bool { return code == guess }

func main() {
	const realCode = "428913"
	lim := newLimiter(5) // 5 attempts per account, full stop
	account := "victim@example.com"

	// The attacker rotates IPs, but every guess targets the SAME account.
	guesses := []string{"000000", "111111", "222222", "333333", "444444", "555555", "428913"}
	cracked := false
	for i, g := range guesses {
		if !lim.allow(account) {
			fmt.Printf("attempt %d (%s): BLOCKED — account budget exhausted\n", i+1, g)
			continue
		}
		if verify(realCode, g) {
			cracked = true
			fmt.Printf("attempt %d (%s): CRACKED\n", i+1, g)
		} else {
			fmt.Printf("attempt %d (%s): wrong\n", i+1, g)
		}
	}
	fmt.Println("account compromised:", cracked) // false — blocked before the real code
}
```

## A08 · Software & Data Integrity Failures — event-stream

<Define term="A08 Software & Data Integrity Failures">
Trusting code or data whose integrity you never verified — a compromised dependency, an unsigned update, an unprotected CI/CD pipeline. The supply chain becomes the attack.
</Define>

**The case — event-stream / flatmap-stream, 2018 (npm; targeted Copay).** The maintainer of the popular npm package `event-stream` — ~1,600 dependents — **handed ownership to a stranger** (`right9ctrl`) who'd offered to help maintain it. So the malware only activated inside Copay's build, where it tried to steal wallet keys from balances over 100 BTC. It sat undetected for **2.5 months**. No server was hacked; the *trust* in a dependency was.

## A09 · Security Logging & Monitoring Failures — Target

<Define term="A09 Security Logging & Monitoring Failures">
Not detecting, alerting on, or responding to an attack in progress — either because the events aren't logged, the alerts don't fire, or (the cruelest) they fire and no one acts.
</Define>

**The case — Target, 2013 (40,000,000 cards; ~70M PII records).** Target had a **FireEye** detection system, monitored around the clock by a team in Bangalore. When the exfiltration malware was installed, it **fired alerts** — and the Bangalore team escalated to Target's security team in Minneapolis. **No action was taken.** The detection worked perfectly; the *response* did not. The US Senate Commerce Committee's "Kill Chain" analysis laid out every missed off-ramp. A09 is the only category where the tooling can be flawless and you still lose — because a log nobody reads and an alert nobody actions are not controls.

This snippet shows the minimum: log security-relevant events *and* trip a distinct, escalatable alert at a threshold — the line that must page a human or trigger automation.

```go
package main

import (
	"fmt"
	"log/slog"
	"os"
)

// securityMonitor counts denied-access events per actor and RAISES A DISTINCT
// ALERT when an actor crosses a threshold — the signal Target's tools produced
// and humans ignored. Logging the denial is step one; the alert (and acting on
// it) is the control. A log nobody reads is not security.
type securityMonitor struct {
	denials   map[string]int
	threshold int
	log       *slog.Logger
}

func (m *securityMonitor) recordDenial(actor, resource string) {
	m.denials[actor]++
	m.log.Warn("access_denied", "actor", actor, "resource", resource, "count", m.denials[actor])
	if m.denials[actor] == m.threshold {
		// This line must page a human / trigger automation — not just log.
		m.log.Error("SECURITY_ALERT", "actor", actor, "reason", "denial_threshold_exceeded", "count", m.denials[actor])
	}
}

func main() {
	m := &securityMonitor{
		denials:   map[string]int{},
		threshold: 3,
		log:       slog.New(slog.NewTextHandler(os.Stdout, &slog.HandlerOptions{Level: slog.LevelWarn})),
	}

	// An attacker enumerates resources they do not own — exactly the pattern
	// an A01 probe produces. Each denial is logged; the third trips the alert.
	for _, res := range []string{"acc_1", "acc_2", "acc_3", "acc_4"} {
		m.recordDenial("usr_mallory", res)
	}
	fmt.Println("done — alert fired at the threshold; now a human must act")
}
```

## A10 · Server-Side Request Forgery — Capital One

<Define term="A10 Server-Side Request Forgery (SSRF)">
Tricking a server into making a request the attacker controls — typically to reach internal services the attacker can't reach directly, most dangerously the cloud **metadata endpoint** at `169.254.169.254`, which hands out IAM credentials.
</Define>

**The case — Capital One, 2019 (106,000,000 applicants; Paige Thompson).** A misconfigured **WAF** was vulnerable to SSRF. The attacker made it request the AWS **instance metadata service** at `http://169.254.169.254/…/iam/security-credentials/`, which returned temporary credentials for the WAF's IAM role (`ISRM-WAF-Role`). Those credentials could list and read **S3 buckets** — and out came the personal data of **106 million** credit-card applicants across the US and Canada. One forged internal request, pointed at the metadata IP, escalated a web-layer bug into a full data breach. The defender's job is to **validate the destination of every outbound request** and block the metadata IP and all internal ranges.

package main

import (
	"errors"
	"fmt"
	"net"
	"net/url"
)

var errBlocked = errors.New("destination blocked")

// resolve is a stub DNS for this offline demo. In production use net.LookupIP,
// apply the SAME checks to EVERY returned address, and re-check after the
// connection resolves to defeat DNS rebinding.
func resolve(host string) net.IP {
	stub := map[string]string{
		"metadata.internal": "169.254.169.254",
		"db.internal":       "10.0.0.5",
		"localhost":         "127.0.0.1",
		"api.partner.com":   "93.184.216.34", // a public address
	}
	if ip, ok := stub[host]; ok {
		return net.ParseIP(ip)
	}
	return net.ParseIP(host) // already a literal IP, or nil
}

// checkTarget validates a user-supplied URL BEFORE any outbound request.
// It blocks loopback, private, and link-local ranges — and the cloud metadata
// IP 169.254.169.254, the exact endpoint Capital One's SSRF reached.
func checkTarget(raw string) error {
	u, err := url.Parse(raw)
	if err != nil {
		return err
	}
	ip := resolve(u.Hostname())
	if ip == nil {
		return errors.New("cannot resolve host")
	}
	if ip.IsLoopback() || ip.IsPrivate() || ip.IsLinkLocalUnicast() {
		return errBlocked
	}
	if ip.Equal(net.ParseIP("169.254.169.254")) {
		return errBlocked // cloud metadata service (also link-local)
	}
	return nil
}

func main() {
	targets := []string{
		"http://metadata.internal/latest/meta-data/iam/security-credentials/",
		"http://db.internal/admin",
		"http://localhost:6443/",
		"https://api.partner.com/webhook",
	}
	for _, t := range targets {
		status := "ALLOW"
		if err := checkTarget(t); err != nil {
			status = "BLOCK"
		}
		fmt.Printf("%-58s -> %s\n", t, status)
	}
}

<UnderTheHood title="HTTP Parsing & Vulnerability Internals in Go">

Understanding how Go's `net/http` parses wire protocols and manages connection states reveals why certain vulnerability classes behave uniquely in Go systems.

### 1. The Per-Connection Goroutine & Slowloris Resistance
When `http.Server.Serve(l net.Listener)` accepts a TCP connection, it allocates a dedicated `http.conn` struct and launches a new goroutine: `go c.serve(connCtx)`. 
- **Memory footprint:** Go goroutines begin with a 2 KB stack (dynamically growable), making idle connections significantly cheaper than in thread-per-connection runtimes (e.g., Apache with 1–8 MB thread stacks).
- **Timeout pitfalls:** Without explicit timeouts, an attacker can hold thousands of goroutines open by streaming request headers byte-by-byte (Slowloris). Go defends against this via `ReadHeaderTimeout` and `ReadTimeout`:
```go
srv := &http.Server{
    Addr:              ":8443",
    ReadHeaderTimeout: 5 * time.Second,  // Closes slow-header attacks
    ReadTimeout:       15 * time.Second, // Caps entire request body read
    WriteTimeout:      30 * time.Second, // Caps response transmission
    IdleTimeout:       120 * time.Second,// Reclaims keep-alive sockets
    MaxHeaderBytes:    1 << 20,          // 1 MB limit against header flood
}
```

### 2. Header Canonicalization & Smuggling Defense
Go parses MIME headers in `net/textproto.Reader.ReadMIMEHeader` using `CanonicalMIMEHeaderKey`, which transforms keys into Title-Case format (e.g., `content-length` $\to$ `Content-Length`).
- **Duplicate & Ambiguous Headers:** In RFC 7230, sending both `Transfer-Encoding: chunked` and `Content-Length` is a primary vector for HTTP Request Smuggling (CL.TE / TE.CL). Go's standard library parser strips `Content-Length` when `Transfer-Encoding` is present, eliminating ambiguous message framing before application middleware ever touches the request.
- **Header normalization quirks:** If upstream proxies or WAFs rely on raw header casing or unconventional whitespace (e.g. `Content-Length : 10` or `Transfer-Encoding:\tchunked`), discrepancies between the frontend proxy's parser and Go's RFC-strict parser can introduce desync vulnerabilities.

### 3. URL Routing: Path vs. RawPath & Traversal Traps
Go's `net/url.URL` struct separates the parsed, unescaped path (`r.URL.Path`) from the exact raw wire string (`r.URL.RawPath`).
- `http.ServeMux` canonicalizes paths by running `path.Clean` on `r.URL.Path` before route matching, automatically redirecting `/v1/../v1/doc` to `/v1/doc`.
- **The Reverse-Proxy Traversal Trap:** When building a reverse proxy or file handler, using `r.URL.Path` directly in string concatenations or naive prefix checks can fail against percent-encoded traversal characters (e.g., `%2e%2e%2f`). Always resolve and validate targets using `filepath.Clean` along with explicit directory boundary verification:
```go
// Safe path containment validation
cleanRel := filepath.Clean(filepath.FromSlash(userSuppliedPath))
if strings.HasPrefix(cleanRel, "..") || filepath.IsAbs(cleanRel) {
    return nil, ErrAccessDenied
}
targetPath := filepath.Join(baseDir, cleanRel)
if !strings.HasPrefix(targetPath, filepath.Clean(baseDir)+string(filepath.Separator)) {
    return nil, ErrAccessDenied
}
```

### 4. Transport-Level SSRF & DNS Rebinding Elimination
Application-level URL checking (parsing the hostname, resolving the IP, and then invoking `http.Get(url)`) creates a **Time-of-Check to Time-of-Use (TOCTOU)** race window. An attacker with a custom DNS server responds with a public IP on the first lookup and returns `169.254.169.254` or `127.0.0.1` milliseconds later when `http.Client` connects.

The robust Go solution intercepts the connection at the `net.Dialer.Control` level inside `http.Transport`:
```go
dialer := &net.Dialer{
    Timeout: 5 * time.Second,
    Control: func(network, address string, c syscall.RawConn) error {
        host, _, err := net.SplitHostPort(address)
        if err != nil {
            return err
        }
        ip := net.ParseIP(host)
        if ip == nil {
            return errors.New("unparseable destination IP")
        }
        if ip.IsLoopback() || ip.IsPrivate() || ip.IsLinkLocalUnicast() {
            return errors.New("blocked internal destination IP")
        }
        return nil
    },
}
client := &http.Client{
    Transport: &http.Transport{
        DialContext: dialer.DialContext,
    },
}
```
Because `Control` executes synchronously after the socket address is resolved and assigned, DNS rebinding cannot bypass the policy.

</UnderTheHood>

<Exercise n={1} title="IDOR-proof fetch (A01)" level="easy">

Write `LoadDoc(docs map[string]Doc, id, viewerID string) (Doc, error)` where `Doc` has `ID`, `OwnerID`, `Body`. Return `ErrNotFound` both when the doc is missing and when the viewer is not the owner — the two must be indistinguishable. Show that incrementing through IDs as a non-owner reveals nothing.

<Solution>

```go
package main

import (
	"errors"
	"fmt"
)

type Doc struct {
	ID      string
	OwnerID string
	Body    string
}

var ErrNotFound = errors.New("not found")

func LoadDoc(docs map[string]Doc, id, viewerID string) (Doc, error) {
	d, ok := docs[id]
	if !ok || d.OwnerID != viewerID {
		return Doc{}, ErrNotFound
	}
	return d, nil
}

func main() {
	docs := map[string]Doc{
		"000000001": {"000000001", "alice", "deed A"},
		"000000002": {"000000002", "bob", "deed B"},
		"000000003": {"000000003", "carol", "deed C"},
	}
	// Mallory walks the sequential IDs, First American style.
	got := 0
	for _, id := range []string{"000000001", "000000002", "000000003"} {
		if _, err := LoadDoc(docs, id, "mallory"); err == nil {
			got++
		}
	}
	fmt.Printf("Mallory enumerated %d of 3 documents\n", got) // 0 of 3
}
```

Folding the viewer into the lookup makes "not yours" and "doesn't exist" return the same error. A sequential ID space is no longer an enumeration oracle.

</Solution>

<Exercise n={2} title="Spot the ECB leak (A02)" level="easy">

Write `firstBlockRepeats(blocks [][]byte) bool` that returns true if any two 16-byte ciphertext blocks in the slice are identical — the signature of ECB mode over structured plaintext. Demonstrate it returning true for a list containing a duplicate block.

<Solution>

```go
package main

import (
	"bytes"
	"fmt"
)

func firstBlockRepeats(blocks [][]byte) bool {
	for i := 0; i < len(blocks); i++ {
		for j := i + 1; j < len(blocks); j++ {
			if bytes.Equal(blocks[i], blocks[j]) {
				return true
			}
		}
	}
	return false
}

func main() {
	a := []byte("0123456789abcdef")
	b := []byte("FFFFFFFFFFFFFFFF")
	blocks := [][]byte{a, b, a} // a repeats — ECB tell
	fmt.Println("ECB leak detected:", firstBlockRepeats(blocks)) // true
}
```

Repeated ciphertext blocks mean repeated plaintext blocks under ECB — the detector pen-testers run on captured ciphertext. The real fix upstream is an authenticated mode (GCM) with a unique nonce, and for passwords, a salted slow hash.

</Solution>

<Exercise n={3} title="Atomic transfer invariant (A04)" level="medium">

Write a `Bank` with a mutex-guarded `Move(from, to string, amt int64) bool` and a `Total()` method. Fire many concurrent `Move` calls from goroutines and assert the total is conserved (no money created), proving the TOCTOU race is closed.

<Solution>

```go
package main

import (
	"fmt"
	"sync"
)

type Bank struct {
	mu  sync.Mutex
	acc map[string]int64
}

func (b *Bank) Move(from, to string, amt int64) bool {
	b.mu.Lock()
	defer b.mu.Unlock()
	if b.acc[from] < amt {
		return false
	}
	b.acc[from] -= amt
	b.acc[to] += amt
	return true
}

func (b *Bank) Total() int64 {
	b.mu.Lock()
	defer b.mu.Unlock()
	var s int64
	for _, v := range b.acc {
		s += v
	}
	return s
}

func main() {
	b := &Bank{acc: map[string]int64{"a": 1000, "b": 0}}
	before := b.Total()
	var wg sync.WaitGroup
	for i := 0; i < 200; i++ {
		wg.Add(1)
		go func() { defer wg.Done(); b.Move("a", "b", 10) }()
	}
	wg.Wait()
	fmt.Printf("conserved: %v (before=%d after=%d)\n", before == b.Total(), before, b.Total())
}
```

The lock makes check-and-update atomic, so concurrent moves serialize and the conservation invariant holds. In a database, the equivalent is one transaction with `SELECT … FOR UPDATE`.

</Solution>

</Exercise>

<Exercise n={4} title="Per-account rate limiter (A07)" level="medium">

Implement `Allow(account string) bool` capping attempts per account at a max, and show that exhausting the budget blocks all further attempts regardless of how many distinct "IPs" (callers) try.

<Solution>

```go
package main

import (
	"fmt"
	"sync"
)

type Limiter struct {
	mu  sync.Mutex
	n   map[string]int
	max int
}

func NewLimiter(max int) *Limiter { return &Limiter{n: map[string]int{}, max: max} }

func (l *Limiter) Allow(account string) bool {
	l.mu.Lock()
	defer l.mu.Unlock()
	if l.n[account] >= l.max {
		return false
	}
	l.n[account]++
	return true
}

func main() {
	l := NewLimiter(3)
	// Ten "IPs" all attack the same account; the budget is the account's.
	allowed := 0
	for ip := 0; ip < 10; ip++ {
		if l.Allow("victim") {
			allowed++
		}
	}
	fmt.Printf("allowed %d attempts across 10 IPs\n", allowed) // 3
}
```

Because the counter is keyed on the account, ten different sources share one budget of three. Keying on IP would have given each source its own budget — the Instagram bypass.

</Solution>

</Exercise>

<Exercise n={5} title="SSRF destination guard (A10)" level="hard">

Write `SafeDestination(rawURL string, resolve func(string) net.IP) error` that parses the URL, resolves the host with the injected resolver, and returns an error for loopback, private, link-local, or the metadata IP `169.254.169.254`. Prove it blocks the metadata target and allows a public one.

<Solution>

```go
package main

import (
	"errors"
	"fmt"
	"net"
	"net/url"
)

var ErrBlocked = errors.New("blocked destination")

func SafeDestination(rawURL string, resolve func(string) net.IP) error {
	u, err := url.Parse(rawURL)
	if err != nil {
		return err
	}
	ip := resolve(u.Hostname())
	if ip == nil {
		return errors.New("unresolved host")
	}
	if ip.IsLoopback() || ip.IsPrivate() || ip.IsLinkLocalUnicast() ||
		ip.Equal(net.ParseIP("169.254.169.254")) {
		return ErrBlocked
	}
	return nil
}

func main() {
	resolve := func(h string) net.IP {
		m := map[string]string{"meta": "169.254.169.254", "pub": "93.184.216.34"}
		return net.ParseIP(m[h])
	}
	fmt.Println("metadata:", SafeDestination("http://meta/creds", resolve)) // blocked destination
	fmt.Println("public:  ", SafeDestination("https://pub/api", resolve))   // <nil>
}
```

Injecting the resolver keeps the test hermetic and forces the rule that matters: decide on the resolved IP, not the hostname string, and re-resolve/re-check after connect in production to defeat DNS rebinding.

<Recap>

- **A01 Broken Access Control** (First American, 885M files): sequential IDs + no ownership check = enumerate the archive with a `for` loop. Fold the viewer's identity into the lookup; return 404 not 403.
- **A02 Cryptographic Failures** (Adobe, 153M): 3DES-ECB + one key + plaintext hints made the password table decryptable. Passwords are *hashed* (bcrypt/argon2 + salt), never encrypted; use authenticated modes (GCM) with unique nonces elsewhere.
- **A03 Injection** (Heartland, 130M cards): SQL injection was the foothold for a $200M+ heist. Parameterized queries and `os/exec` argument slices make input *data*, never code.
- **A04 Insecure Design** (Starbucks): a check-then-act money transfer with no lock let two sessions spend the same balance. Make the check-and-update atomic — one lock or one DB transaction with `SELECT … FOR UPDATE`.
- **A05 Security Misconfiguration** (Tesla): an internet-facing Kubernetes console with no auth, holding AWS keys. Admin surfaces fail closed; secrets never live inside the surface they protect.
- **A06 Vulnerable & Outdated Components** (Equifax, 147M; CVE-2017-5638): a patch existed; the scan missed the host. `govulncheck` (call-graph aware) in CI, a patch SLA, and an SBOM turn inventory into data.
- **A07 Authentication Failures** (Instagram, $30K): a per-IP rate limit on a six-digit code fell to IP rotation. Limit the sensitive action against the *target account*, not the source.
- **A08 Software & Data Integrity** (event-stream): an ownership handoff slipped a target-keyed payload into ~1,600 dependents. Pin, verify (`go mod verify`, `-mod=readonly`), and *review the dependency diff* — integrity tooling protects bytes, humans protect the decision to trust.
- **A09 Logging & Monitoring Failures** (Target, 40M cards): the alert fired and no one acted. Log security events, alert on thresholds, and *rehearse the response* — detection without response is theater.
- **A10 SSRF** (Capital One, 106M): a forged request to `169.254.169.254` returned IAM credentials. Validate every outbound destination by resolved IP, block internal ranges and the metadata IP, re-check after DNS, and use IMDSv2.
