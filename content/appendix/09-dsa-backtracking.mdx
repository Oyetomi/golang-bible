## The Backtracking Template

### The scenario: generating PIN codes under a constraint

You're on the fraud team at a payments startup. A compromised POS terminal issued PINs following a now-known pattern: no digit appears more than once. You need to enumerate *every valid 4-digit PIN* from a given digit pool so your security scanner can cross-reference against transaction logs. The search space is manageable — but you need **all** of them, correct and fast. That's backtracking.

<Define term="Backtracking (choose / explore / un-choose)" since="this chapter">
A systematic search strategy that **commits to one choice, recurses into the remaining search space, then undoes that choice** before trying the next option. It is the correct algorithm whenever you need to enumerate all valid configurations (every valid PIN, every permutation, every placement of N-queens) and there is no shortcut that avoids examining each possibility. **Why it matters:** without the un-choose step, you cannot reuse the same path variable across branches — each branch would see the side effects of all previous branches.
</Define>

<Define term="Decision tree" since="this chapter">
The conceptual tree that backtracking traverses depth-first. **Each node is a partial state** (a path built so far); **each edge is one choice** (append digit 3). Leaves are either complete solutions (record them) or dead ends (backtrack). The tree is never materialized in memory — the call stack *is* the path from root to the current node, which is why space complexity is `O(depth)`, not `O(total nodes)`.
</Define>

### Three moves, one recursion

Every backtracking algorithm is exactly three moves repeated until the answer space is drained:

1. **Choose** — pick one option from the available choices at the current decision point.
2. **Explore** — recurse deeper, making the next choice inside the reduced search space.
3. **Un-choose** — undo the choice after the recursion returns, restoring the state for the next option.

The mental picture is a **decision tree**. Each node is a partial state; each edge is one choice. You walk depth-first from the root toward the leaves. When you hit a leaf (a complete solution) you record it. When you hit a dead end (constraint violated, no options left), you backtrack — climb back up one level and take the next branch. You exhaust the entire tree.

### The universal Go skeleton

```go
// path is the in-progress sequence of choices.
// result accumulates complete solutions.
func backtrack(path []int, choices []int, result *[][]int) {
	// Base case: path is a complete solution — record it.
	// COPY the path before appending — it is mutated in place below!
	*result = append(*result, append([]int{}, path...))

	for _, c := range choices {
		// 1. Choose
		path = append(path, c)
		remaining := removeChoice(choices, c) // shrink the choice set

		// 2. Explore (recurse with the updated state)
		backtrack(path, remaining, result)

		// 3. Un-choose (backtrack)
		path = path[:len(path)-1]
	}
}
```

The `append([]int{}, path...)` copy on the base-case line is **the most important line in this entire chapter.** Go slices are headers over a shared backing array. If you write `*result = append(*result, path)`, every collected result ends up pointing at the same underlying array — and you'll watch your answers silently corrupt as later mutations overwrite earlier ones. We'll show this trap live in the UnderTheHood block.

<Define term="Slice-aliasing trap (copy the path before collecting)">
A Go slice is a three-word value: `(pointer, length, capacity)`. Backtracking mutates the **same underlying array** in-place across every recursive call — appending to grow `path`, then shrinking `len` to un-choose. If you store the slice header without copying (`result = append(result, path)`), every stored result shares that same array and will be overwritten by future mutations. **Fix:** `slices.Clone(path)` or `append([]int{}, path...)` allocates a fresh array snapshot that backtracking can never touch. **Why it bites everyone:** the bug is invisible when you look at results immediately — they look correct. It only manifests after later calls overwrite earlier ones, which is exactly what the verifier's aliasing check exposes.
</Define>

<UnderTheHood title="DFS on an implicit decision tree — and the slice aliasing trap">

**Backtracking is DFS on an implicit graph.** The nodes are states (partial solutions); the edges are choices. We never materialize the whole tree — we generate one branch at a time, walk it to a leaf or a dead end, then back up. This is why the space complexity is often just `O(depth)` for the call stack — we reuse the same `path` slice the whole time.

**Time complexity = branching factor ^ depth.** At the root you have `b` choices; at the next level `b-1`; and so on. The total number of leaves (complete solutions) drives the complexity. For permutations of `n` elements it's `O(n!)`. For subsets of `n` elements it's `O(2^n)`. Both are exponential — that's not a performance failure, it's the nature of "enumerate all." Pruning (Section 5) cuts branches early so you visit fewer nodes without changing the worst-case asymptote, but it destroys TLE in practice.

**The slice aliasing trap — why you MUST copy path before collecting.**

In Go, a slice value is a three-word header: `(pointer, len, cap)`. When you `append` to `path`, you extend the length. When you backtrack with `path = path[:len(path)-1]`, you shrink the length — but the underlying array is **never reset**. The bytes are still there; you just moved the length pointer.

```go
// WRONG — every entry in result shares the same backing array:
*result = append(*result, path)

// RIGHT — allocate a fresh []int copying the current elements:
*result = append(*result, append([]int{}, path...))
```

The `append([]int{}, path...)` idiom allocates a new backing array of exactly `len(path)` and copies the current elements into it. That snapshot is immutable from backtracking's perspective — future mutations to `path` won't touch it. This bites everyone at least once in an interview. It's biting no one in *my* class. As of Go 1.24, you can also use `slices.Clone(path)` from the `slices` package — same result, more readable.

**Call-stack depth** equals the depth of the decision tree (the length of one solution). For well-bounded inputs (n ≤ 20 in most interview problems), this is safe. For truly unbounded recursion, convert to an explicit stack — but you will never see that in a backtracking interview question.

</UnderTheHood>

### Generate all subsets (the power set)

**Scenario:** An options-pricing engine needs to evaluate the PnL impact of every possible subset of a risk-factor set. Given `n` factors, that's `2^n` subsets. Small `n`, enormous business value — enumerate them all.

**Pattern:** At each element, make a binary choice — include it or exclude it. Use a `start` index to march forward through the array without revisiting earlier elements (prevents duplicates).

```go
package main

import (
	"fmt"
	"slices"
)

func subsets(nums []int) [][]int {
	result := [][]int{}
	var bt func(start int, path []int)
	bt = func(start int, path []int) {
		// Every partial state is a valid subset — collect it.
		result = append(result, slices.Clone(path))

		for i := start; i < len(nums); i++ {
			path = append(path, nums[i])  // choose
			bt(i+1, path)                 // explore (i+1 prevents reuse)
			path = path[:len(path)-1]     // un-choose
		}
	}
	bt(0, []int{})
	return result
}

func main() {
	fmt.Println(subsets([]int{1, 2, 3}))
}
```

**Complexity:** Time `O(2^n * n)` — `2^n` subsets, each takes `O(n)` to clone. Space `O(n)` call stack + `O(2^n * n)` for results.

**Variations:**
- **Subsets with duplicates** (LeetCode 90): sort first, then skip duplicates at the same recursion level with `if i > start && nums[i] == nums[i-1] { continue }`.
- **Subsets of a given size k**: add `if len(path) == k` as your leaf condition.

### Combinations: choose k from n

**Pattern:** Same `start`-index trick, but only record when `len(path) == k`.

```go
package main

import (
	"fmt"
	"slices"
)

// combine returns all combinations of k numbers chosen from [1..n].
func combine(n, k int) [][]int {
	result := [][]int{}
	var bt func(start int, path []int)
	bt = func(start int, path []int) {
		if len(path) == k {
			result = append(result, slices.Clone(path))
			return
		}
		for i := start; i <= n; i++ {
			path = append(path, i)
			bt(i+1, path)
			path = path[:len(path)-1]
		}
	}
	bt(1, []int{})
	return result
}

func main() {
	fmt.Println(combine(4, 2))
}
```

**Complexity:** Time `O(C(n,k) * k)` — number of combinations times the clone cost. Space `O(k)` call stack.

### Combination Sum: reuse allowed

**Scenario:** A cashier system needs every way to make exact change for a target amount using a given coin denominations set, with unlimited coins per denomination.

**Key difference from combinations:** pass `i` (not `i+1`) to allow reusing the same element.

```go
package main

import (
	"fmt"
	"slices"
)

func combinationSum(candidates []int, target int) [][]int {
	result := [][]int{}
	var bt func(start, remaining int, path []int)
	bt = func(start, remaining int, path []int) {
		if remaining == 0 {
			result = append(result, slices.Clone(path))
			return
		}
		for i := start; i < len(candidates); i++ {
			c := candidates[i]
			if c > remaining {
				break // candidates are sorted; no point continuing
			}
			path = append(path, c)
			bt(i, remaining-c, path) // i (not i+1): reuse allowed
			path = path[:len(path)-1]
		}
	}
	// Sort so the pruning break above works.
	slices.Sort(candidates)
	bt(0, target, []int{})
	return result
}

func main() {
	fmt.Println(combinationSum([]int{2, 3, 6, 7}, 7))
}
```

**Complexity:** Time `O(N^(T/M))` where `T` is target and `M` is the smallest candidate — roughly exponential in depth. Space `O(T/M)` call stack.

## Permutations

### All orderings of distinct elements

**Scenario:** A payments router needs to try every ordering of settlement channels to find which sequence has the lowest total fee. Given `n` channels, there are `n!` orderings.

**Pattern:** Unlike subsets, permutations care about order. Use a `used` boolean array (indexed by position in `nums`) to track which elements are already on the path.

```go
package main

import (
	"fmt"
	"slices"
)

func permute(nums []int) [][]int {
	result := [][]int{}
	used := make([]bool, len(nums))
	var bt func(path []int)
	bt = func(path []int) {
		if len(path) == len(nums) {
			result = append(result, slices.Clone(path))
			return
		}
		for i, n := range nums {
			if used[i] {
				continue
			}
			used[i] = true
			path = append(path, n)
			bt(path)
			path = path[:len(path)-1]
			used[i] = false
		}
	}
	bt([]int{})
	return result
}

func main() {
	fmt.Println(permute([]int{1, 2, 3}))
```

### Permutations with duplicates

When `nums` contains repeated elements, the naive algorithm generates duplicate permutations. The fix: sort first, then skip an unused element if it equals its predecessor (and that predecessor is unused at this level).

```go
package main

import (
	"fmt"
	"slices"
)

func permuteUnique(nums []int) [][]int {
	slices.Sort(nums) // must sort so duplicates are adjacent
	result := [][]int{}
	used := make([]bool, len(nums))
	var bt func(path []int)
	bt = func(path []int) {
		if len(path) == len(nums) {
			result = append(result, slices.Clone(path))
			return
		}
		for i, n := range nums {
			if used[i] {
				continue
			}
			// Skip duplicate: same value as previous, and previous is NOT used
			// at this recursion level (meaning we already explored that branch).
			if i > 0 && nums[i] == nums[i-1] && !used[i-1] {
				continue
			}
			used[i] = true
			path = append(path, n)
			bt(path)
			path = path[:len(path)-1]
			used[i] = false
		}
	}
	bt([]int{})
	return result
}

func main() {
	fmt.Println(permuteUnique([]int{1, 1, 2}))
}
```

**Complexity:** Time `O(n! * n)` worst case, but pruning eliminates duplicate branches early. Space `O(n)`.

## Constraint Problems

### N-Queens: the classic

**Scenario:** A hardware security module (HSM) needs to place `n` independent signing threads on an `n x n` grid of processing slots such that no two threads share a row, column, or diagonal — to prevent timing-based side-channel attacks. Model it as N-queens.

**Pattern:** Place one queen per row. For each row, try every column; skip columns/diagonals already attacked. No need for a full board matrix — three boolean arrays (or sets) track which columns and diagonals are occupied.

```go
package main

import (
	"fmt"
	"strings"
)

func solveNQueens(n int) [][]string {
	result := [][]string{}
	// cols, diag1 (row-col), diag2 (row+col) track attacked lines.
	cols := make([]bool, n)
	diag1 := make([]bool, 2*n) // top-left to bottom-right
	diag2 := make([]bool, 2*n) // top-right to bottom-left
	board := make([]int, n)    // board[row] = column where queen sits

	var bt func(row int)
	bt = func(row int) {
		if row == n {
			// Build string representation and record.
			snapshot := make([]string, n)
			for r, c := range board {
				row := strings.Repeat(".", c) + "Q" + strings.Repeat(".", n-c-1)
				snapshot[r] = row
			}
			result = append(result, snapshot)
			return
		}
		for col := range n { // range over int (Go 1.22+)
			d1 := row - col + n // shift to keep index non-negative
			d2 := row + col
			if cols[col] || diag1[d1] || diag2[d2] {
				continue // attacked — skip this column
			}
			// Place queen.
			cols[col] = true
			diag1[d1] = true
			diag2[d2] = true
			board[row] = col

			bt(row + 1)

			// Remove queen.
			cols[col] = false
			diag1[d1] = false
			diag2[d2] = false
		}
	}
	bt(0)
	return result
}

func main() {
	solutions := solveNQueens(4)
	fmt.Printf("%d solutions for 4-queens:\n", len(solutions))
	for _, sol := range solutions {
		for _, row := range sol {
			fmt.Println(row)
		}
		fmt.Println()
	}
}
```

**Complexity:** Time `O(n!)` — at row 0 you have `n` choices, row 1 at most `n-1`, and so on. Space `O(n)` for the three mark arrays plus call stack.

### Word Search on a grid

**Scenario:** A document-scanning pipeline checks whether a keyword appears in an `m x n` character grid — used to flag redacted content that was only partially obscured.

**Pattern:** DFS from each cell. Mark cells as visited by temporarily overwriting them (the classic Go trick to avoid an extra visited array), then restore on backtrack.

```go
package main

import "fmt"

func exist(board [][]byte, word string) bool {
	rows, cols := len(board), len(board[0])
	var bt func(r, c, idx int) bool
	bt = func(r, c, idx int) bool {
		if idx == len(word) {
			return true // matched every character
		}
		if r < 0 || r >= rows || c < 0 || c >= cols {
			return false
		}
		if board[r][c] != word[idx] {
			return false
		}
		// Mark visited by overwriting with a sentinel.
		tmp := board[r][c]
		board[r][c] = '#'

		found := bt(r+1, c, idx+1) ||
			bt(r-1, c, idx+1) ||
			bt(r, c+1, idx+1) ||
			bt(r, c-1, idx+1)

		board[r][c] = tmp // restore — this is the "un-choose"
		return found
	}
	for r := range rows {
		for c := range cols {
			if bt(r, c, 0) {
				return true
			}
		}
	}
	return false
}

func main() {
	board := [][]byte{
		{'A', 'B', 'C', 'E'},
		{'S', 'F', 'C', 'S'},
		{'A', 'D', 'E', 'E'},
	}
	fmt.Println(exist(board, "ABCCED")) // true
	fmt.Println(exist(board, "SEE"))    // true
	fmt.Println(exist(board, "ABCB"))   // false
}
```

**Complexity:** Time `O(m * n * 4^L)` where `L` is the word length — we start from every cell and explore 4 directions for each character. Space `O(L)` call stack.

## Pruning

### The difference between TLE and AC

<Define term="Pruning" since="this chapter — Pruning section">
Skipping an entire subtree of the decision tree **the moment you can prove no leaf in it can be valid**. Example: in combination sum, once the current candidate exceeds the remaining target (and candidates are sorted), every subsequent candidate also exceeds it — break immediately rather than recurse into each one. **Why it matters:** pruning does not change the worst-case complexity, but it destroys the constant factor. The difference between TLE and AC on a backtracking problem is almost always a missing pruning condition.
</Define>

Pruning is cutting branches off the decision tree *before* exploring them — because you can already tell they cannot lead to a valid solution. Without pruning, backtracking is correct but often laughably slow. With it, the same skeleton goes from TLE to milliseconds on real input.

**The rule:** any time you can prove that no leaf reachable from the current node can be valid, return immediately without recursing.

### Pruning techniques

**1. Bound-based pruning (combination sum pattern)**

Sort the candidates. When the current candidate already exceeds the remaining target, all further candidates (which are larger or equal) also exceed it — break immediately.

**2. Count-based pruning (combinations)**

If `(n - i + 1) + len(path) < k`, there aren't enough elements left to fill a combination of size `k` — skip. This cuts the lower tail of the search dramatically.

```go
package main

import (
	"fmt"
	"slices"
)

// combine with aggressive count-based pruning.
func combine(n, k int) [][]int {
	result := [][]int{}
	var bt func(start int, path []int)
	bt = func(start int, path []int) {
		if len(path) == k {
			result = append(result, slices.Clone(path))
			return
		}
		// Pruning: elements left = n-i+1; need k-len(path) more.
		// If elements left < need, no valid combination possible.
		for i := start; i <= n-(k-len(path))+1; i++ {
			path = append(path, i)
			bt(i+1, path)
			path = path[:len(path)-1]
		}
	}
	bt(1, []int{})
	return result
}

func main() {
	fmt.Println(combine(4, 2))
}
```

<Callout kind="pro" title="Pruning is not an optimization — it's a correctness multiplier">

For inputs where the answer space is huge (e.g., combination sum with large target and many small candidates), an unpruned backtracker times out before finishing. Pruning doesn't change the *algorithm* — it changes which subtrees get visited. The big-O worst case is the same, but the practical constant factor drops by orders of magnitude. Always sort + break for sum-based problems. Always add the count guard for combination/subset-with-size problems.

</Callout>

<Exercise n={2} title="Palindrome partitioning" level="medium">

Given a string `s`, return all possible ways to partition it such that every substring in the partition is a palindrome. Example: `"aab"` → `[["a","a","b"],["aa","b"]]`.

**Pattern:** backtracking where at each index you try every prefix ending at positions `[start..n-1]`, check if it's a palindrome, and recurse on the remainder.

<Solution>

```go
package main

import "fmt"

func partition(s string) [][]string {
	result := [][]string{}
	var bt func(start int, path []string)
	bt = func(start int, path []string) {
		if start == len(s) {
			cp := make([]string, len(path))
			copy(cp, path)
			result = append(result, cp)
			return
		}
		for end := start + 1; end <= len(s); end++ {
			sub := s[start:end]
			if isPalin(sub) {
				path = append(path, sub)
				bt(end, path)
				path = path[:len(path)-1]
			}
		}
	}
	bt(0, []string{})
	return result
}

func isPalin(s string) bool {
	for l, r := 0, len(s)-1; l < r; l, r = l+1, r-1 {
		if s[l] != s[r] {
			return false
		}
	}
	return true
}

func main() {
	fmt.Println(partition("aab"))
}
```

<Exercise n={3} title="Subsets II (with duplicates)" level="medium">

Given an integer array `nums` that may contain duplicates, return all possible subsets without duplicate subsets. Example: `[1,2,2]` → `[[],[1],[1,2],[1,2,2],[2],[2,2]]`.

**Pattern:** sort, then skip duplicates at the same recursion level with `if i > start && nums[i] == nums[i-1]`.

<Solution>

```go
package main

import (
	"fmt"
	"slices"
)

func subsetsWithDup(nums []int) [][]int {
	slices.Sort(nums)
	result := [][]int{}
	var bt func(start int, path []int)
	bt = func(start int, path []int) {
		result = append(result, slices.Clone(path))
		for i := start; i < len(nums); i++ {
			// Skip duplicate at the same depth.
			if i > start && nums[i] == nums[i-1] {
				continue
			}
			path = append(path, nums[i])
			bt(i+1, path)
			path = path[:len(path)-1]
		}
	}
	bt(0, []int{})
	return result
}

func main() {
	fmt.Println(subsetsWithDup([]int{1, 2, 2}))
}
```

The `i > start` guard is critical: it allows the same value to appear in different positions across depths (e.g., both `[2]` and `[1,2]`) while skipping the duplicate branch at the *current* level (preventing two `[2]` entries).

<Exercise n={5} title="Combination Sum II (no reuse, no duplicate results)" level="hard">

Given `candidates` (may contain duplicates) and a `target`, find all unique combinations that sum to `target`. Each candidate may only be used once. Example: `candidates=[10,1,2,7,6,1,5]`, `target=8` → `[[1,1,6],[1,2,5],[1,7],[2,6]]`.

**Pattern:** sort + `i+1` (no reuse) + skip duplicate at same level.

<Solution>

```go
package main

import (
	"fmt"
	"slices"
)

func combinationSum2(candidates []int, target int) [][]int {
	slices.Sort(candidates)
	result := [][]int{}
	var bt func(start, remaining int, path []int)
	bt = func(start, remaining int, path []int) {
		if remaining == 0 {
			result = append(result, slices.Clone(path))
			return
		}
		for i := start; i < len(candidates); i++ {
			c := candidates[i]
			if c > remaining {
				break // pruning: sorted, so all further candidates also exceed
			}
			// Skip duplicates at the same depth.
			if i > start && candidates[i] == candidates[i-1] {
				continue
			}
			path = append(path, c)
			bt(i+1, remaining-c, path) // i+1: no reuse
			path = path[:len(path)-1]
		}
	}
	bt(0, target, []int{})
	return result
}

func main() {
	fmt.Println(combinationSum2([]int{10, 1, 2, 7, 6, 1, 5}, 8))
}
```

This problem is the hardest combination of all the techniques: sort, no reuse (`i+1`), skip duplicates at the same level, and break on sort-based pruning. If you can write this clean in an interview, you know backtracking.

</Solution>

</Exercise>

<Recap>

- **Every backtracking algorithm is three moves:** choose → explore → un-choose. The decision tree makes this concrete: DFS, leaf = solution, dead end = backtrack.
- **The universal Go skeleton:** a closure `bt(state)` that collects, loops over choices, recurses, and pops. The `start` index prevents duplicate sets; the `used` array enables permutations.
- **Copy before collecting:** `slices.Clone(path)` (or `append([]int{}, path...)`) is non-negotiable. Storing the slice header aliases the mutable backing array and silently corrupts every result.
- **Subsets** — collect at every node, use `start` index, `i+1` to prevent reuse.
- **Combinations of size k** — collect only at `len(path)==k`, same `start`/`i+1` discipline.
- **Combination sum** — pass `i` (not `i+1`) for reuse; sort and `break` for free pruning.
- **Permutations** — `used[]bool` array, no `start` index. Sort + skip adjacent duplicates for `permuteUnique`.
- **Constraint problems (N-queens, word search)** — boolean mark arrays for `O(1)` constraint checks; grid sentinel (`#`) to avoid an extra visited array.
- **Pruning** turns TLE into AC: sort + `break`, count guards, and early `return true` for existence problems.
- **Complexity is exponential** — `O(n!)` for permutations, `O(2^n)` for subsets. Be honest about it. Pruning reduces the practical constant factor, not the asymptote.

</Recap>
