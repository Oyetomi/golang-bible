## Two Pointers

Here's the thing about nested loops — they're comfortable. You've got a problem, you loop over everything, inside you loop over everything again, done. O(n²). Safe. Boring. Wrong.

The **two-pointer pattern** is the antidote. The core insight: when your data is sorted, or when you're scanning inward from both ends, you don't need to try every pair. Two indices — typically `left` and `right` — march toward each other (or chase each other) so the inner loop simply disappears.

Real scenario: a fintech API returns a sorted list of transaction amounts. You need to find two transactions that sum to a target amount (for reconciliation). The naive approach checks every pair — quadratic. Two pointers do it in a single pass.

<Define term="Two pointers" since="Arrays & Strings: Two Pointers & Sliding Windows (Appendix, Ch. 2)">
Two indices — typically named `left` and `right` — that each move through an array at most once, eliminating impossible pairs as they go. **Why it works:** when data is sorted (or has a monotone property), moving one pointer inward definitively rules out an entire class of pairs, so you never revisit a discarded index. Net cost: O(n) instead of O(n²). Two variants: **converging** (start at opposite ends, march inward — used for pair sums, palindromes, container problems) and **fast/slow** (both start at the left, one chases the other — used for dedup in-place, cycle detection, partition).
</Define>

### The Converging Pattern

Start `left` at index 0, `right` at the last index. Examine the pair. If the sum is too big, shrink it by moving `right` left. If the sum is too small, grow it by moving `left` right. The only way both pointers can be wrong at the same time is if no solution exists.

```go
// TwoSumSorted finds indices i, j (0-indexed) such that nums[i]+nums[j]==target.
// REQUIRES: nums is sorted in ascending order.
// Time: O(n)  Space: O(1)
func TwoSumSorted(nums []int, target int) (int, int, bool) {
	left, right := 0, len(nums)-1
	for left < right {
		sum := nums[left] + nums[right]
		switch {
		case sum == target:
			return left, right, true
		case sum < target:
			left++
		default:
			right--
		}
	}
	return 0, 0, false
}
```

```go
import "fmt"

// TwoSumSorted finds indices i, j such that nums[i]+nums[j]==target.
// REQUIRES: nums is sorted ascending.
// Time: O(n)  Space: O(1)
func TwoSumSorted(nums []int, target int) (int, int, bool) {
	left, right := 0, len(nums)-1
	for left < right {
		sum := nums[left] + nums[right]
		switch {
		case sum == target:
			return left, right, true
		case sum < target:
			left++
		default:
			right--
		}
	}
	return 0, 0, false
}

func main() {
	// Sorted transaction amounts (in cents).
	txns := []int{100, 400, 600, 900, 1100}
	i, j, ok := TwoSumSorted(txns, 1000)
	if ok {
		fmt.Printf("found pair: txns[%d]=%d + txns[%d]=%d = %d\n",
			i, txns[i], j, txns[j], txns[i]+txns[j])
	} else {
		fmt.Println("no pair found")
	}
}
```

### Reverse In-Place

The same converging motion lets you reverse a slice in place — swap `left` and `right`, then march both inward until they meet.

```go
// Reverse reverses a []byte in place.
// Time: O(n)  Space: O(1)
func Reverse(b []byte) {
	for left, right := 0, len(b)-1; left < right; left, right = left+1, right-1 {
		b[left], b[right] = b[right], b[left]
	}
}
```

### Is Palindrome

A string is a palindrome if it reads the same forward and backward. Two pointers, converging: if the characters at `left` and `right` ever differ, it's not a palindrome.

```go
// IsPalindrome checks if s is a palindrome (ASCII letters and digits only,
// case-insensitive). Skips non-alphanumeric characters.
// Time: O(n)  Space: O(1)
func IsPalindrome(s string) bool {
	left, right := 0, len(s)-1
	for left < right {
		for left < right && !isAlphanumeric(s[left]) {
			left++
		}
		for left < right && !isAlphanumeric(s[right]) {
			right--
		}
		if toLower(s[left]) != toLower(s[right]) {
			return false
		}
		left++
		right--
	}
	return true
}

func isAlphanumeric(c byte) bool {
	return (c >= 'a' && c <= 'z') ||
		(c >= 'A' && c <= 'Z') ||
		(c >= '0' && c <= '9')
}

func toLower(c byte) byte {
	if c >= 'A' && c <= 'Z' {
		return c + 32
	}
	return c
}
```

### Remove Duplicates In-Place

The **fast/slow** variant: one pointer (`slow`) marks the write position of the de-duplicated prefix; the other (`fast`) scans forward. When `fast` finds a new value, copy it into the `slow` slot and advance `slow`. No extra space.

```go
// RemoveDuplicates removes duplicates from a sorted slice in-place and returns
// the new length. Elements beyond the returned length are undefined.
// Time: O(n)  Space: O(1)
func RemoveDuplicates(nums []int) int {
	if len(nums) == 0 {
		return 0
	}
	slow := 0
	for fast := 1; fast < len(nums); fast++ {
		if nums[fast] != nums[slow] {
			slow++
			nums[slow] = nums[fast]
		}
	}
	return slow + 1
}
```

<UnderTheHood title="Why O(n²) → O(n): the elimination argument">

The nested-loop approach checks every possible pair: for each index `i`, it tries every `j > i`. That's n*(n-1)/2 comparisons — O(n²).

Two pointers work because the **sorted invariant** lets each comparison eliminate an entire half of the remaining search space. When `nums[left] + nums[right] > target`, every pair `(left, right)`, `(left, right-1)`, ... `(left, left+1)` with the current `left` produces a sum that's too big — so we move `right` inward and skip all those pairs at once, not one by one. The same logic in reverse when the sum is too small. Every step eliminates at least one index permanently, so the total work is bounded by how many steps either pointer can take: at most `n` combined. O(n).

This "sorted + monotone decision" argument is the heart of the pattern. If the data isn't sorted but you need the same complexity, often you sort it first (O(n log n)) and then run two pointers on the sorted copy — still better than O(n²) for large n.

The standard library's `slices.Sort` (added when the `slices` package joined the stdlib in Go 1.21) uses pdqsort (pattern-defeating quicksort) — the same algorithm that has backed `sort.Sort` since Go 1.19 — running in O(n log n) average and O(n) for nearly-sorted inputs. Prefer it over a hand-rolled sort.

</UnderTheHood>

**Pattern variations:**

- **Three-sum:** fix one element with an outer loop, then two-pointer on the rest. O(n²) total, but that's optimal for three-sum.
- **Container with most water:** converge pointers, always move the shorter wall — classic greedy two-pointer.
- **Trapping rain water:** the "max from left / max from right" pre-scan is a two-pointer scan variant.
- **Fast/slow on linked lists:** detect a cycle (`slow` advances one step, `fast` advances two; they meet if a cycle exists). Same pattern, different data structure.

## Sliding Window

Now we level up. Two pointers gave us O(n) for pairs. Sliding window gives us O(n) for contiguous subarrays — and it works even when the data isn't sorted.

<Define term="Sliding window (fixed vs. variable)" since="Arrays & Strings: Two Pointers & Sliding Windows (Appendix, Ch. 2)">
A **sliding window** is a contiguous subarray bounded by a `left` and `right` pointer that expand or contract as they move across the array. Instead of recomputing the window's value from scratch each time, you update it incrementally — add the element entering on the right, remove the element falling off the left. **Fixed window:** size stays constant at `k`; `left` always trails `right` by exactly `k`. Cost: O(1) per slide, O(n) total. **Variable window:** size grows when you expand looking for a condition and shrinks when you overshoot — `left` chases `right`. Still O(n) by amortization: each element enters once and leaves at most once across the entire scan, so total work is O(2n) = O(n) regardless of how many shrink steps any single outer iteration takes.
</Define>

The scenario: a rate-limiting system needs to find the maximum number of API requests in any rolling window of size `k`. Naive: re-sum every window — O(n·k). Sliding window: maintain a running sum, add the new element entering the window, subtract the one that falls off the back. O(n).

### Fixed-Size Window

The window size stays constant at `k`. Compute the first window, then slide: at each step, add `nums[right]` and subtract `nums[right-k]`.

```go
// MaxSumSubarray returns the maximum sum of any contiguous subarray of length k.
// Time: O(n)  Space: O(1)
func MaxSumSubarray(nums []int, k int) int {
	if len(nums) < k {
		return 0
	}
	windowSum := 0
	for i := range k {
		windowSum += nums[i]
	}
	maxSum := windowSum
	for i := k; i < len(nums); i++ {
		windowSum += nums[i] - nums[i-k]
		if windowSum > maxSum {
			maxSum = windowSum
		}
	}
	return maxSum
}
```

### Variable-Size Window

When the window size isn't fixed — when you expand it looking for a condition and shrink it when you overshoot — you need a `left` pointer that chases `right`. This is still O(n) because each element enters the window once and leaves once.

**Longest substring without repeating characters** is the textbook example. Expand `right`; if the character at `right` is already in the window, shrink from `left` until it isn't.

```go
// LongestUniqueSubstring returns the length of the longest substring
// of s that contains no repeated characters.
// Time: O(n)  Space: O(k) where k is the character-set size (≤256 for byte)
func LongestUniqueSubstring(s string) int {
	seen := make(map[byte]int) // byte → last-seen index
	best := 0
	left := 0
	for right := range len(s) {
		ch := s[right]
		if idx, ok := seen[ch]; ok && idx >= left {
			// ch is in the window — shrink from left past its last occurrence.
			left = idx + 1
		}
		seen[ch] = right
		if w := right - left + 1; w > best {
			best = w
		}
	}
	return best
}
```

### Minimum Window Substring

The hardest classic variable-window problem: find the shortest substring of `s` that contains all characters of `t`. Expand until the window is valid (contains all of `t`), then contract from the left as far as possible while keeping it valid. Record the best valid window.

```go
// MinWindow returns the minimum window substring of s that contains all
// characters of t, or "" if none exists.
// Time: O(|s| + |t|)  Space: O(|t|)
func MinWindow(s, t string) string {
	if len(t) == 0 {
		return ""
	}
	need := make(map[byte]int)
	for i := range len(t) {
		need[t[i]]++
	}
	have := make(map[byte]int)
	formed := 0
	required := len(need)

	left := 0
	bestLen := len(s) + 1
	bestLeft := 0

	for right := range len(s) {
		ch := s[right]
		have[ch]++
		if cnt, ok := need[ch]; ok && have[ch] == cnt {
			formed++
		}
		for formed == required {
			if w := right - left + 1; w < bestLen {
				bestLen = w
				bestLeft = left
			}
			lch := s[left]
			have[lch]--
			if cnt, ok := need[lch]; ok && have[lch] < cnt {
				formed--
			}
			left++
		}
	}
	if bestLen > len(s) {
		return ""
	}
	return s[bestLeft : bestLeft+bestLen]
}
```

<UnderTheHood title="The two-pointer amortization argument">

Why is the variable sliding window O(n) and not O(n²)? Because of **amortization**: each index is visited at most twice — once when `right` advances over it, and once when `left` passes it. Two visits total means O(2n) = O(n) work across the entire loop, regardless of how many times the inner `for formed == required` loop fires on any given outer iteration.

This is the same argument that makes append amortized O(1): not every operation is cheap, but the *total* work across all operations is linear.

The hidden cost is the map lookups. For a fixed character set (e.g., ASCII bytes, size 256), the map can be replaced with a `[256]int` array — cache-friendly and zero-allocation. In Go, `var freq [256]int` is stack-allocated and indexed by the byte value directly. For Unicode-correct character windows, you'd need a `map[rune]int` and to iterate the string with `range` rather than indexing by byte. As of Go 1.24, the compiler does not escape small fixed-size arrays to the heap, so the array approach truly allocates nothing.

</UnderTheHood>

- **Permutation in string:** fixed window of size `len(p)`; compare frequency snapshots.

## Prefix Sums

Two pointers and sliding window both do O(n) work to answer one query. Prefix sums do O(n) *upfront* work so that every subsequent range-sum query costs O(1). If you need to answer many queries on the same array, that trade is a steal.

<Define term="Prefix sum" since="Arrays & Strings: Two Pointers & Sliding Windows (Appendix, Ch. 2)">
A **prefix sum array** `pre` where `pre[i]` holds the sum of all elements from index `0` through `i-1`. Build it once in O(n): `pre[i+1] = pre[i] + nums[i]`. Then any range sum `nums[l..r]` becomes a single subtraction: `pre[r+1] - pre[l]`, costing O(1). **Why it matters:** a naive range-sum query re-traverses the subarray each time — O(n) per query. With a prefix sum table, you pay the O(n) build cost once and answer every subsequent query in O(1), so m queries costs O(n + m) instead of O(n·m). The same idea extends to 2D grids, XOR, and — combined with a hash map — powers the O(n) "subarray sum equals k" complement trick.
</Define>

The scenario: a bank's audit system needs to answer thousands of queries of the form "what is the total transaction value between index `l` and index `r` inclusive?" If you sum the subarray each time, that's O(n) per query. Build the prefix sum once, answer in O(1) forever.

### Building and Querying

A prefix sum array `pre` has `pre[i]` = sum of all elements from index 0 through index `i-1`. With one-based indexing of `pre`, the range sum from `l` to `r` (both 0-indexed, inclusive) is `pre[r+1] - pre[l]`.

```go
// PrefixSums builds the prefix-sum table for nums.
// pre[i] = sum of nums[0..i-1]. pre[0] = 0.
// Time: O(n)  Space: O(n)
func PrefixSums(nums []int) []int {
	pre := make([]int, len(nums)+1)
	for i, v := range nums {
		pre[i+1] = pre[i] + v
	}
	return pre
}

// RangeSum returns the sum of nums[l..r] inclusive in O(1).
// pre must be the prefix-sum table for nums.
func RangeSum(pre []int, l, r int) int {
	return pre[r+1] - pre[l]
}
```

### Subarray Sum Equals K

Prefix sums power one of the trickiest medium problems: count subarrays that sum to exactly `k`. Without prefix sums, O(n²). With them, you use the complement trick: a subarray `[l..r]` sums to `k` if and only if `pre[r+1] - pre[l] == k`, i.e., `pre[r+1] - k == pre[l]`. So as you build the prefix sum, look up how many times you've seen that complement in a hash map.

```go
// SubarraySumK counts subarrays with sum exactly k.
// Time: O(n)  Space: O(n)
func SubarraySumK(nums []int, k int) int {
	counts := map[int]int{0: 1} // prefix sum → frequency; seed with 0
	sum := 0
	result := 0
	for _, v := range nums {
		sum += v
		result += counts[sum-k]
		counts[sum]++
	}
	return result
}
```

## In-Place Tricks

Interviewers love in-place operations because they test whether you understand how memory works, not just the algorithm. The constraint: O(1) extra space. The tools: swapping, partitioning, and the classic "use the array as its own auxiliary structure."

### The Swap Without Extra Space

You already saw swapping in the reverse. In Go, multi-assignment makes it zero-ceremony:

```go
a, b = b, a // no temp variable needed — Go evaluates both sides first
```

Go's spec guarantees the right-hand side is fully evaluated before any assignment happens, so this is always safe — even when `a` and `b` are elements of the same slice.

### Rotate Array

To rotate a slice right by `k` positions: reverse the whole slice, then reverse the first `k` elements, then reverse the rest. Three reverses, O(n) time, O(1) space.

```go
// RotateRight rotates nums right by k positions in-place.
// Time: O(n)  Space: O(1)
func RotateRight(nums []int, k int) {
	n := len(nums)
	if n == 0 {
		return
	}
	k = k % n // handle k >= n
	reverse(nums, 0, n-1)
	reverse(nums, 0, k-1)
	reverse(nums, k, n-1)
}

func reverse(nums []int, left, right int) {
	for left < right {
		nums[left], nums[right] = nums[right], nums[left]
		left++
		right--
	}
}
```

### Dutch National Flag Partition

Three-way partitioning: given an array of values 0, 1, and 2, sort it in-place in one pass with three pointers — `lo`, `mid`, `hi`. This is Dijkstra's Dutch National Flag algorithm, and it generalizes to any three-bucket partition.

```go
// DutchFlag sorts nums containing only 0, 1, 2 in-place.
// Time: O(n)  Space: O(1)
func DutchFlag(nums []int) {
	lo, mid, hi := 0, 0, len(nums)-1
	for mid <= hi {
		switch nums[mid] {
		case 0:
			nums[lo], nums[mid] = nums[mid], nums[lo]
			lo++
			mid++
		case 1:
			mid++
		case 2:
			nums[mid], nums[hi] = nums[hi], nums[mid]
			hi--
			// do NOT increment mid — the swapped element is unexamined
		}
	}
}
```

## []byte vs string vs []rune

This section is *not* optional. Every year, people fail interviews because they write a string solution that silently corrupts multi-byte characters, or they convert strings to runes when they don't need to and get a memory hit they can't explain. Let me fix you before an interviewer has to.

<Define term="[]byte vs string vs []rune" since="Arrays & Strings: Two Pointers & Sliding Windows (Appendix, Ch. 2)">
Three distinct types for "text" in Go, each with a different cost model. **`string`** — an immutable two-word header `(ptr, len)` over bytes, commonly UTF-8 but not required to be valid UTF-8. `s[i]` gives a raw byte, `len(s)` counts bytes. Zero-allocation slicing in current implementations. **`[]byte`** — a mutable three-word slice `(ptr, len, cap)`. Converting from a string (`[]byte(s)`) allocates and copies all bytes; converting back (`string(b)`) allocates again. Use when you must mutate content in-place — e.g., in-place reverse, cipher, URL encode. **`[]rune`** — a mutable slice of 32-bit Unicode code points. `[]rune(s)` decodes the string as UTF-8 into one `int32` per decoded rune; `len(runes)` is then the rune count and `runes[i]` is the i-th rune. Costs 4× the memory of the byte slice. Use when you need correct rune-level indexing on non-ASCII input. **The rule:** keep `string` unless you need mutation (`[]byte`) or Unicode-correct indexing (`[]rune`).
</Define>

### The Mental Model

In Go, a `string` is an **immutable, read-only byte sequence**. It is a two-word header: a pointer and a length in bytes. That's it. Text is usually UTF-8, but the type itself permits arbitrary bytes.

- `len(s)` counts **bytes**, not characters.
- `s[i]` gives you a **byte** (`uint8`), not a character.
- Indexing a string to get a character is a bug for any non-ASCII input.

```go
s := "café"
fmt.Println(len(s))      // 5, not 4 — 'é' is 2 bytes in UTF-8
fmt.Println(s[3])        // 195 — the first byte of 'é', not 'é' itself
fmt.Printf("%c\n", s[3]) // Ã — garbage if you try to print it as a rune
```

### The Interview Decision Tree

```
Do you need to MUTATE the content?
  YES → []byte(s), work on the byte slice, string(b) when done
  NO  → keep it a string

Do you need CHARACTER-LEVEL indexing or length? (i.e., "i-th char")
  YES → []rune(s) — correct, costs O(n) time and 4× space
  NO  → stay as string; use range for iteration

Is the input guaranteed to be ASCII-only?
```

### Practical: Reverse a String Correctly

Reversing "hello" by byte works fine. Reversing "café" by byte produces garbage. Reverse by rune to be correct.

```go
// ReverseString reverses a string, correctly handling multi-byte Unicode chars.
// Time: O(n)  Space: O(n) — must allocate a rune slice
func ReverseString(s string) string {
	r := []rune(s)
	for left, right := 0, len(r)-1; left < right; left, right = left+1, right-1 {
		r[left], r[right] = r[right], r[left]
	}
	return string(r)
}
```

### In-Place ASCII Work With []byte

For interview problems that are explicitly ASCII (e.g., "given a string of digits and lowercase letters"), `[]byte` lets you do the in-place work an interviewer expects without Unicode overhead:

```go
// ReverseWords reverses the words in a byte slice in-place (ASCII, space-delimited).
// Time: O(n)  Space: O(1)
func ReverseWords(s []byte) {
	// Step 1: reverse the entire slice.
	reverseB(s, 0, len(s)-1)
	// Step 2: reverse each word back.
	start := 0
	for i := range len(s) {
		if s[i] == ' ' {
			reverseB(s, start, i-1)
			start = i + 1
		}
	}
	reverseB(s, start, len(s)-1)
}

func reverseB(s []byte, left, right int) {
	for left < right {
		s[left], s[right] = s[right], s[left]
		left++
		right--
	}
}
```

<UnderTheHood title="string, []byte, []rune memory model">

A `string` in Go is a two-word struct — call it `(ptr *byte, len int)`. The bytes it points to are immutable. The string header itself is a value type: copying a string copies only the 16-byte header, not the bytes. That's why string slicing is O(1) and zero-allocation — `s[l:r]` just creates a new header with an adjusted pointer and a smaller length, sharing the same underlying bytes.

`[]byte` is a three-word struct — `(ptr *byte, len int, cap int)`. When you write `[]byte(s)`, Go allocates a fresh backing array and copies the bytes into it. That's a real allocation and a real copy. When you write `string(b)`, it allocates *again* and copies back. The compiler is allowed (but not required) to optimize away the copy in some specific, limited cases — when the `[]byte` is used immediately in a comparison or as a map key inside a single expression. Don't count on it in general.

`[]rune` is also a three-word slice header, but the backing array holds `int32` values (4 bytes each). `[]rune(s)` walks the entire UTF-8 string, decoding each code point, and stores it as an `int32`. For a 100-byte string that's 100 ASCII characters, the `[]rune` takes 400 bytes. For "café" (5 UTF-8 bytes, 4 characters), the `[]rune` takes 16 bytes.

As of Go 1.24, the `strings` package uses `unsafe` internally for some hot paths to avoid copies that the type system would otherwise require — but that's implementation detail you should never replicate in application code. The rule remains: `string` for immutable text, `[]byte` for mutable bytes, `[]rune` for Unicode-correct character indexing.

</UnderTheHood>

<Exercise n={1} title="Valid palindrome (ASCII)" level="easy">

Write `IsPalindromeASCII(s string) bool` that returns `true` if `s` is a palindrome after keeping only lowercase ASCII letters. Ignore all other characters, convert uppercase to lowercase. Do it with two pointers and O(1) extra space (work directly on the string bytes — it's ASCII-only).

<Solution>

```go
package main

import "fmt"

func IsPalindromeASCII(s string) bool {
	left, right := 0, len(s)-1
	for left < right {
		for left < right && !(s[left] >= 'a' && s[left] <= 'z' ||
			s[left] >= 'A' && s[left] <= 'Z') {
			left++
		}
		for left < right && !(s[right] >= 'a' && s[right] <= 'z' ||
			s[right] >= 'A' && s[right] <= 'Z') {
			right--
		}
		l, r := s[left], s[right]
		if l >= 'A' && l <= 'Z' {
			l += 32
		}
		if r >= 'A' && r <= 'Z' {
			r += 32
		}
		if l != r {
			return false
		}
		left++
		right--
	}
	return true
}

func main() {
	fmt.Println(IsPalindromeASCII("racecar"))     // true
	fmt.Println(IsPalindromeASCII("Race Car!"))   // true
	fmt.Println(IsPalindromeASCII("hello"))       // false
}
```

Indexing by byte is correct here because the problem is explicitly ASCII-only. Two pointers converge; no extra allocation. O(n) time, O(1) space.

</Solution>

<Exercise n={2} title="Max average subarray of size k" level="easy">

Write `MaxAvgSubarray(nums []float64, k int) float64` that returns the maximum average of any contiguous subarray of length `k`. Use a fixed sliding window. Return `0` if `len(nums) < k`.

<Solution>

```go
package main

import "fmt"

// MaxAvgSubarray returns the maximum average of any subarray of length k.
// Time: O(n)  Space: O(1)
func MaxAvgSubarray(nums []float64, k int) float64 {
	if len(nums) < k {
		return 0
	}
	var sum float64
	for i := range k {
		sum += nums[i]
	}
	best := sum
	for i := k; i < len(nums); i++ {
		sum += nums[i] - nums[i-k]
		if sum > best {
			best = sum
		}
	}
	return best / float64(k)
}

func main() {
	fmt.Println(MaxAvgSubarray([]float64{1, 12, -5, -6, 50, 3}, 4)) // 12.75
	fmt.Println(MaxAvgSubarray([]float64{5}, 1))                     // 5.0
}
```

Sum the first window, then slide: add incoming, subtract outgoing. Divide by `k` at the end — dividing on each step would be wasteful and introduce floating-point churn.

</Solution>

</Exercise>

<Exercise n={3} title="Count subarrays with product less than k" level="medium">

Write `SubarrayProductLessThanK(nums []int, k int) int` that counts the number of contiguous subarrays whose product of elements is strictly less than `k`. All elements are positive integers. Use a sliding window. Expected: O(n) time, O(1) space.

<Solution>

```go
package main

import "fmt"

// SubarrayProductLessThanK counts subarrays with product < k.
// Time: O(n)  Space: O(1)
// Key insight: when the window [left..right] has product < k, every subarray
// ending at right and starting anywhere in [left..right] is valid — that's
// (right - left + 1) new subarrays.
func SubarrayProductLessThanK(nums []int, k int) int {
	if k <= 1 {
		return 0
	}
	product := 1
	left := 0
	count := 0
	for right, v := range nums {
		product *= v
		for product >= k {
			product /= nums[left]
			left++
		}
		count += right - left + 1
	}
	return count
}

func main() {
	fmt.Println(SubarrayProductLessThanK([]int{10, 5, 2, 6}, 100)) // 8
	fmt.Println(SubarrayProductLessThanK([]int{1, 2, 3}, 0))       // 0
}
```

The counting trick is the hard part: once `product < k` for window `[left..right]`, every subarray ending at `right` with start in `[left..right]` is valid — that's `right-left+1` subarrays added at once.

</Solution>

</Exercise>

<Exercise n={4} title="Longest subarray of ones after deleting one element" level="medium">

Given a binary array `nums`, delete one element and return the length of the longest subarray containing only `1`s. Use a sliding window that tracks the number of zeros allowed (`≤1`). Time: O(n), Space: O(1).

<Solution>

```go
package main

import "fmt"

// LongestOnesAfterDeletion returns the length of the longest subarray of 1s
// after removing exactly one element.
// Time: O(n)  Space: O(1)
func LongestOnesAfterDeletion(nums []int) int {
	left := 0
	zeros := 0
	best := 0
	for right, v := range nums {
		if v == 0 {
			zeros++
		}
		for zeros > 1 {
			if nums[left] == 0 {
				zeros--
			}
			left++
		}
		// Window size minus the one deleted element (at most one zero in window).
		if w := right - left; w > best {
			best = w
		}
	}
	return best
}

func main() {
	fmt.Println(LongestOnesAfterDeletion([]int{1, 1, 0, 1}))          // 3
	fmt.Println(LongestOnesAfterDeletion([]int{0, 1, 1, 1, 0, 1, 1})) // 5
	fmt.Println(LongestOnesAfterDeletion([]int{1, 1, 1}))             // 2
}
```

Allow at most one zero in the window (the "deleted" element). Window size is `right-left+1`, but we always delete one element, so the length of the resulting subarray is `right-left`. The case of all-ones still works: the window contains one "deleted" `1`, so the answer is `len-1`.

</Solution>

</Exercise>

<Exercise n={5} title="Longest common prefix of []rune slices" level="hard">

Write `LongestCommonPrefix(words []string) string` that finds the longest string that is a prefix of every word in `words`. Return `""` if there is none. Solve it by iterating column by column (comparing characters across all words at position `i`). Use `[]rune` to be Unicode-correct. Time: O(n·m) where n is number of words and m is the length of the shortest word.

<Solution>

```go
package main

import "fmt"

// LongestCommonPrefix finds the longest common prefix of all words.
// Uses []rune for Unicode correctness.
// Time: O(n*m)  Space: O(m) for the rune slices
func LongestCommonPrefix(words []string) string {
	if len(words) == 0 {
		return ""
	}
	runes := make([][]rune, len(words))
	for i, w := range words {
		runes[i] = []rune(w)
	}
	// Find shortest word length.
	minLen := len(runes[0])
	for _, r := range runes[1:] {
		if len(r) < minLen {
			minLen = len(r)
		}
	}
	// Scan column by column.
	for col := range minLen {
		ch := runes[0][col]
		for _, r := range runes[1:] {
			if r[col] != ch {
				return string(runes[0][:col])
			}
		}
	}
	return string(runes[0][:minLen])
}

func main() {
	fmt.Printf("%q\n", LongestCommonPrefix([]string{"flower", "flow", "flight"})) // "fl"
	fmt.Printf("%q\n", LongestCommonPrefix([]string{"dog", "racecar", "car"}))    // ""
	fmt.Printf("%q\n", LongestCommonPrefix([]string{"café", "caféine", "cafés"})) // "café"
}
```

The "café" case shows why `[]rune` matters: the common prefix is 4 *characters*, but comparing byte-by-byte would give you 5 bytes, and any variation in how `é` was encoded could corrupt the prefix. With `[]rune`, column `i` is always the i-th character.

</Solution>

</Exercise>

You now have the three core array/string interview patterns, fully implemented in Go:

- **Two pointers** — converging from both ends on sorted data (two-sum, palindrome, remove duplicates) or fast/slow on unsorted data. Turns O(n²) into O(n) by eliminating pairs with the sorted invariant.
- **Sliding window** — fixed size (max-sum subarray) or variable size (longest unique substring, min window). Each element enters and exits once — amortized O(n). Expand until valid, shrink until tight.
- **Prefix sums** — O(n) upfront to build `pre[]`, then O(1) per range-sum query via `pre[r+1] - pre[l]`. The complement trick (`counts[sum-k]`) turns subarray-count problems from O(n²) to O(n).
