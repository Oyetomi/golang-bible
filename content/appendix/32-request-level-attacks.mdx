<HeroCard label="Appendix · Web Security Academy" title="Request-Level Attacks: Smuggling, Host Header & Cache Poisoning">

Here's the thing, sport. Most vulnerabilities live *inside* a request — a bad parameter, a missing check. This chapter is about a stranger class: bugs that live in the **request itself**, in how the machines along its path *disagree* about what it even is. A modern web request passes through a chain — CDN, load balancer, reverse proxy, your Go server — and each one re-parses it. When two of them read the **same bytes differently**, an attacker slips into the gap. That's the whole family: **request smuggling** (the front-end and back-end disagree where one request *ends* and the next begins), **Host header attacks** (your server trusts a header the client controls to decide *who it is*), and **web cache poisoning** (a shared cache stores one attacker's poisoned response and serves it to *everyone*).

These are PortSwigger Web Security Academy signature topics, and they reward understanding HTTP at the byte level — which is exactly where Go is interesting. We'll *empirically* test how strictly Go's `net/http` parses ambiguous `Content-Length`/`Transfer-Encoding` (the answer is reassuring, and precise), then build the Host-header and cache-poisoning bugs and their fixes, every server-side behavior runnable and verified. By the end you'll see a request not as a blob but as bytes that several machines must agree on — and you'll know where they stop agreeing. Let's get into the gaps, sport.

## The Disagreement

Every attack in this chapter has the same shape: **two machines parse one request differently.** Name that shape and the whole family clicks into place.

<Define term="Parser disagreement (the request-level bug pattern)">
A request travels through a **chain** of HTTP intermediaries — CDN, load balancer, reverse proxy, application server — and **each one re-parses the raw bytes**. They're *supposed* to agree, because they all implement the same HTTP spec. A **request-level attack** exploits a case where two of them **disagree**: they read the same bytes and reach different conclusions about where a request ends (**smuggling**), which site it's for (**Host header**), or what may be cached and reused (**cache poisoning**). The attacker crafts bytes that are *ambiguous* — valid to read one way by the front-end and another way by the back-end — and lives in the gap. The defense theme is equally consistent: **eliminate the ambiguity** (strict, identical parsing everywhere) and **never trust a request-controlled value** (framing headers, `Host`, forwarded headers) for a security decision without validating it.
</Define>

## Request Smuggling

The canonical disagreement is over a request's **length**. HTTP/1.1 gives two ways to say how long a body is — `Content-Length` (a byte count) and `Transfer-Encoding: chunked` (length-prefixed chunks). Send *both*, contradictorily, and you've handed the front-end and back-end a choice to disagree on.

<Define term="HTTP request smuggling (CL.TE / TE.CL)">
**HTTP request smuggling** desynchronizes a front-end proxy and a back-end server by making them disagree about where one request ends and the next begins. The body length of an HTTP/1.1 request can be declared by **`Content-Length`** (CL) or **`Transfer-Encoding: chunked`** (TE). If a request includes **both**, the two servers may resolve the conflict differently: in **CL.TE**, the front-end uses Content-Length while the back-end uses Transfer-Encoding; in **TE.CL**, the reverse. Either way, one server thinks the request ended where the other thinks it's still going — so bytes the attacker placed after the "end" get **prepended to the next request** on that shared connection. That smuggled prefix can poison another user's request: stealing their session, bypassing front-end security rules, or routing them to attacker content. The root cause is *ambiguous framing tolerated by at least one parser*; the cure is for every hop to parse identically and **reject** ambiguity rather than guess.
</Define>

<Callout kind="warn" title="Why this is a desync, not a single-server bug">
Smuggling needs **two** parsers and a **reused** connection. Front-ends keep a pool of keep-alive connections to the back-end and pipeline many users' requests over them. If the front-end forwards what it thinks is one complete request but the back-end thinks the request ended earlier, the attacker's leftover bytes sit at the *front* of the buffer — and the **next** request to arrive (a real victim's) gets those bytes glued onto it. That's why the victim, not the attacker, is the one whose request is corrupted. A single server parsing consistently can't smuggle against itself; the bug is born in the gap between the front-end and the back-end.
</Callout>

## Why Go Resists It

So where does a Go server sit in this? The reassuring, *precise* answer: Go's `net/http` is strict and deterministic about ambiguous framing — which means a Go **origin** doesn't disagree with itself, and is a hard back-end to desync. Don't take my word for it — let's send raw ambiguous requests down a TCP socket to a real Go server and watch how it responds.

```go
import (
	"bufio"
	"fmt"
	"net"
	"net/http"
	"net/http/httptest"
	"strings"
	"time"
)

func main() {
	// A plain Go origin server.
	srv := httptest.NewServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		fmt.Fprint(w, "ok")
	}))
	defer srv.Close()
	addr := strings.TrimPrefix(srv.URL, "http://")
	host := "Host: " + addr + "\r\n"

	send := func(label, raw string) {
		conn, _ := net.Dial("tcp", addr)
		defer conn.Close()
		conn.SetDeadline(time.Now().Add(2 * time.Second))
		fmt.Fprint(conn, raw)
		status, _ := bufio.NewReader(conn).ReadString('\n')
		fmt.Printf("%-32s → %s\n", label, strings.TrimSpace(status))
	}

	// Smuggling needs two parsers to DISAGREE about where a request ends.
	// Watch how strictly Go's net/http handles each ambiguous case:
	send("Content-Length + Transfer-Encoding",
		"POST / HTTP/1.1\r\n"+host+"Content-Length: 6\r\nTransfer-Encoding: chunked\r\n\r\n0\r\n\r\nX")
	send("duplicate Content-Length",
		"POST / HTTP/1.1\r\n"+host+"Content-Length: 6\r\nContent-Length: 5\r\n\r\nhello")
	send("obfuscated Transfer-Encoding",
		"POST / HTTP/1.1\r\n"+host+"Transfer-Encoding: xchunked\r\nContent-Length: 6\r\n\r\n0\r\n\r\n")
	send("clean request (control)",
		"POST / HTTP/1.1\r\n"+host+"Content-Length: 5\r\n\r\nhello")
}
```

<Gotcha>
**A strict Go origin is not the same as a safe deployment.** Go follows TE-over-CL, rejects duplicate `Content-Length` (400), and rejects unknown `Transfer-Encoding` (501) — so it parses ambiguity *consistently*, which is exactly what a back-end needs to resist smuggling. But smuggling lives in the **disagreement** between hops, so your safety also depends on the front-end. If a CDN/proxy ahead of Go is *less* strict — say it honors `Content-Length` while Go honors `Transfer-Encoding` — the two disagree and the desync happens regardless of how clean Go is. The robust fixes are architectural: prefer **HTTP/2 end-to-end** (its length framing is unambiguous, killing the CL/TE class), ensure **every hop parses identically and rejects ambiguity**, and avoid reusing a single back-end connection across different users where you can. Go gives you a strong back-end; the chain has to be strict too.
</Gotcha>

## Host Header Attacks

Next disagreement: not about *length*, but about *identity*. Your server often needs to know "what host am I serving right now?" to build absolute URLs or route. The only source for that is the `Host` header — which the **client** sends and can set to anything.

<Define term="Host header injection / poisoning">
The HTTP **`Host`** header tells a server which virtual host a request is for; in Go it surfaces as **`r.Host`** (from the `Host` header, or the `:authority` pseudo-header on HTTP/2). It is **client-controlled** — an attacker can send any value. A **Host header attack** exploits code that *trusts* `r.Host` for a security-relevant decision. The classic is **password-reset poisoning**: the reset email builds its link from `r.Host`, so an attacker triggering a reset for a victim — with `Host: evil.attacker.com` — causes the victim's email to contain a link to the attacker's domain carrying the **real reset token**; when the victim clicks, the token leaks. The same trust enables cache-key confusion, routing bypasses, and SSRF-via-routing. The fix is to **never derive security-relevant values from `r.Host` unchecked**: validate it against an **allowlist** of expected hosts, or build absolute URLs from a **configured base URL** held in server config, not from the request.
</Define>

<GoPlayground>

```go
package main

import (
	"fmt"
	"net/http"
	"net/http/httptest"
)

// VULNERABLE: builds the password-reset link from the client-controlled Host.
func resetVuln(w http.ResponseWriter, r *http.Request) {
	link := "https://" + r.Host + "/reset?token=SECRET123"
	fmt.Fprint(w, link)
}

var allowedHosts = map[string]bool{"app.example.com": true}

// SAFE: validate Host against an allowlist before using it (or build the URL
// from a configured base URL and ignore r.Host entirely).
func resetSafe(w http.ResponseWriter, r *http.Request) {
	if !allowedHosts[r.Host] {
		w.WriteHeader(http.StatusBadRequest)
		fmt.Fprint(w, "400 bad host")
		return
	}
	link := "https://" + r.Host + "/reset?token=SECRET123"
	fmt.Fprint(w, link)
}

func main() {
	// Attacker triggers a reset with a forged Host header.
	req := httptest.NewRequest("POST", "/reset", nil)
	req.Host = "evil.attacker.com"

	wv := httptest.NewRecorder()
	resetVuln(wv, req)
	fmt.Println("VULN link in victim email:", wv.Body.String())

	ws := httptest.NewRecorder()
	resetSafe(ws, req)
	fmt.Printf("SAFE response: %d %s\n", ws.Code, ws.Body.String())
}
```

## Web Cache Poisoning

The third disagreement is about *reuse*. A shared cache stores a response under a **key** (usually method + path + a few headers) and serves it to everyone who asks for that key. If the response depends on an input the cache **doesn't** include in its key, an attacker can save a poisoned response once and have it served to every later visitor.

<Define term="Web cache poisoning (unkeyed input)">
A **web cache** speeds things up by storing a response under a **cache key** — typically the request method and URL path, plus a small set of headers — and replaying it for every subsequent request with the same key. A **keyed** input is part of that key (different value → different cache entry); an **unkeyed** input is *not* (the cache ignores it). **Web cache poisoning** happens when a response **reflects an unkeyed input** into its body: the attacker sends a request whose unkeyed header (say `X-Forwarded-Host: evil.attacker.com`) gets reflected into, e.g., a `<script src>`, the cache stores that poisoned response under the *normal* key, and **every later victim** requesting that path is served the attacker's version — a stored, cache-amplified XSS/redirect affecting everyone. The defenses: don't reflect request inputs into cacheable responses at all; if a response legitimately varies by a header, include it in the cache key (and announce it with **`Vary`**); and don't honor forwarded headers you don't actually use.
</Define>

<GoPlayground>

```go
package main

import (
	"fmt"
	"net/http"
	"net/http/httptest"
)

// render builds the page. BUG: it reflects X-Forwarded-Host (attacker-controlled
// AND unkeyed by the cache) into a <script src> — a poisoning primitive.
func render(r *http.Request) string {
	host := r.Host
	if xfh := r.Header.Get("X-Forwarded-Host"); xfh != "" {
		host = xfh
	}
	return `<script src="https://` + host + `/app.js"></script>`
}

// A trivial shared cache keyed only on method+path (X-Forwarded-Host is unkeyed).
type cache struct{ store map[string]string }

func (c *cache) get(k string) (string, bool) { v, ok := c.store[k]; return v, ok }
func (c *cache) set(k, v string)             { c.store[k] = v }

func main() {
	c := &cache{store: map[string]string{}}
	const key = "GET /home" // the cache key — note: no X-Forwarded-Host in it

	// 1) Attacker primes the cache with a poisoned response.
	atk := httptest.NewRequest("GET", "/home", nil)
	atk.Host = "app.example.com"
	atk.Header.Set("X-Forwarded-Host", "evil.attacker.com")
	if _, ok := c.get(key); !ok {
		c.set(key, render(atk)) // poisoned response stored under the NORMAL key
	}

	// 2) A normal victim requests /home — no special headers.
	victim := httptest.NewRequest("GET", "/home", nil)
	victim.Host = "app.example.com"
	cached, _ := c.get(key)
	fmt.Println("victim is served from cache:")
	fmt.Println(" ", cached)
}
```

## Defenses

The three attacks share one cure and a few specifics. Internalize the pattern and you defend the whole class.

<ConceptGrid cols={2}>
  <ConceptCard label="Smuggling — kill the ambiguity">Prefer **HTTP/2 end-to-end** (unambiguous length framing eliminates the CL/TE class). Ensure **every hop parses identically and rejects ambiguity** — Go's origin already 400s duplicate `Content-Length` and 501s unknown `Transfer-Encoding`; demand the same strictness from your CDN/proxy. Avoid sharing one back-end connection across different users where feasible.</ConceptCard>
  <ConceptCard label="Host header — don't trust r.Host">Build absolute URLs (reset links, redirects, canonical links) from a **configured base URL** in server config, *not* from `r.Host`. Where you must use the request's host, validate it against an **allowlist** of expected hosts and reject the rest. Treat `X-Forwarded-Host`/`X-Forwarded-For` as untrusted unless set by a proxy *you* control.</ConceptCard>
  <ConceptCard label="Cache poisoning — don't reflect unkeyed input">Never reflect a request input into a **cacheable** response. If a response legitimately varies by a header, include that header in the **cache key** and announce it with **`Vary`**. Strip forwarded headers your app doesn't use so a cache can't be tricked into keying (or not keying) on them.</ConceptCard>
  <ConceptCard label="The unifying rule">Every one is a request-controlled value trusted too far across a parser boundary. **Make parsers agree, and validate request-derived values before any security decision** — framing headers, `Host`, forwarded headers, cache keys. Same discipline as the rest of the security baseline, applied to the request envelope itself.</ConceptCard>

The reset link is a security boundary — built from `r.Host`, it lets an attacker's forged Host header carry the real token to their domain. Reject any host not in `allowedHosts` (return `""`) and the poison never reaches the victim's email, while the legitimate host still works. Get the flag.

</Lab>

<Recap>

- Request-level attacks exploit **parser disagreement**: a request crosses a chain of intermediaries (CDN, proxy, Go origin) that each re-parse it, and the attacker crafts bytes that two of them read differently.
- **Request smuggling** is a disagreement about a request's **length**: send both `Content-Length` and `Transfer-Encoding` (or duplicates), and a CL.TE/TE.CL desync prepends the attacker's leftover bytes to the *next* user's request on a shared connection.
- Measured, not assumed: Go's `net/http` is **strict and deterministic** — it follows `Transfer-Encoding` over `Content-Length` per RFC 7230, **400s** duplicate `Content-Length`, and **501s** an unknown `Transfer-Encoding`. A Go origin parses ambiguity consistently, so it's a poor smuggling back-end — but smuggling lives in the *gap between hops*, so the front-end must be strict too (and HTTP/2 end-to-end removes the class).
- **Host header attacks** trust `r.Host` (client-controlled) for a security decision. The classic is **password-reset poisoning** — the reset link built from a forged `Host` mails the victim a token-stealing link. Fix: validate `r.Host` against an **allowlist**, or build URLs from a **configured base URL**.
- **Web cache poisoning** reflects an **unkeyed** input (e.g. `X-Forwarded-Host`) into a cacheable response; the poisoned response is stored under the normal key and served to **every** later victim. Fix: don't reflect request inputs into cacheable responses; key (and `Vary`) on anything a response depends on; drop forwarded headers you don't use.
- The unifying rule: **make every parser agree, and validate any request-derived value before a security decision** — framing headers, `Host`, forwarded headers, cache keys.

</Recap>
