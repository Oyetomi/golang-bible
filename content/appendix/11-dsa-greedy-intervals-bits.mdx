## Greedy Algorithms

<Define term="Greedy algorithm" since="this chapter">
A greedy algorithm makes the **locally-optimal choice at each step** and never revisits it. No table. No backtracking. It bets that local optima compose into a global optimum — a bet that is mathematically provable for some problems and catastrophically wrong for others. At Meridian, the daily settlement scheduler is greedy: it always dispatches the earliest-deadline transfer first. If two transfers share a window, it picks the one that ends soonest and moves on. That works because the problem has the greedy-choice property (proved below). Coin change with arbitrary denominations does not.

**When greedy fails vs DP:** if an early "good" choice closes off a later "better" path, greedy produces the wrong answer and you need dynamic programming. The tell: can you write an exchange argument showing that swapping a greedy pick for any other pick never improves the outcome? If not, reach for DP.
</Define>

Here's the scenario: you're building a rate-limiter scheduler for a fintech API. You have N pending jobs, each with a deadline, and you can only run one at a time. You want to complete as many as possible without missing a single deadline. There is no time to evaluate every possible ordering — the server is hot, the clock is ticking. You need to make a choice *right now*, and it has to be the right one.

That's greedy. Make the locally-optimal choice at each step, and trust that those choices compose into a globally-optimal answer.

### When greedy works — and when it lies to you

Not every problem lets you greedy your way to the optimum. Two conditions must hold simultaneously:

1. **The greedy-choice property** — a globally-optimal solution can always be extended by a locally-optimal choice. The thing you pick now never invalidates an optimal future choice.
2. **Optimal substructure** — the problem's optimal solution contains optimal solutions to its sub-problems (same as DP, but greedy doesn't need to *explore* them; it just commits).

When those hold: greedy wins. O(n log n) at worst. No table. No memoization.

When they don't hold, greedy lies to you beautifully. The **coin-change** problem is the textbook execution. With US denominations (25, 10, 5, 1) greedy works: pick the largest coin that fits, repeat. With arbitrary denominations — say `{1, 3, 4}` and a target of `6` — greedy picks `4`, then `1+1`, totaling **three** coins. But `3+3` is **two**. Greedy failed because the locally-optimal coin (4) closed off the better global path (two 3s). That problem needs dynamic programming.

The golden intuition: **greedy commits, DP explores**. If the problem's choices don't paint each other into corners, commit. If they do, explore with DP.

### Classic: Jump Game

You're on index 0 of an array. Each element is the max jump length from that position. Can you reach the last index?

**Pattern:** greedily track the furthest reachable index. At each position, if you're past the furthest reachable, you're stuck.

**Complexity:** O(n) time, O(1) space.

```go
// canJump reports whether the last index is reachable from index 0.
// nums[i] is the maximum jump length from position i.
func canJump(nums []int) bool {
	maxReach := 0
	for i, n := range nums {
		if i > maxReach {
			return false // stranded — can't reach index i
		}
		if i+n > maxReach {
			maxReach = i + n
		}
	}
	return true
}
```

**Variation — Jump Game II:** find the *minimum* number of jumps to the last index. Same greedy sweep, but now you count level "boundaries" like a BFS frontier: track the current level's right edge and the furthest reach; when you step past the edge, increment jumps. Still O(n).

### Classic: Gas Station

A circuit of gas stations. At station `i` you gain `gas[i]` fuel and pay `cost[i]` to reach the next. Can you complete the circuit, and from which station?

**Greedy insight:** if total gas ≥ total cost, a solution exists. Among all starting points, the valid one is the first position after any prefix whose running total goes negative.

**Complexity:** O(n) time, O(1) space.

```go
// canCompleteCircuit returns the starting station index, or -1 if impossible.
func canCompleteCircuit(gas, cost []int) int {
	total, tank, start := 0, 0, 0
	for i := range gas {
		diff := gas[i] - cost[i]
		total += diff
		tank += diff
		if tank < 0 {
			// this prefix is toxic — start fresh after i
			start = i + 1
			tank = 0
		}
	}
	if total < 0 {
		return -1 // no solution exists
	}
	return start
}
```

### Classic: Assign Cookies

Each child has a greed factor; each cookie has a size. Assign at most one cookie per child, satisfying as many children as possible (a child is satisfied if the cookie size ≥ greed factor).

**Greedy:** sort both. For each child in ascending greed order, assign the smallest cookie that satisfies them. Two-pointer sweep.

**Complexity:** O(n log n) for the sort; O(n) sweep.

```go
// findContentChildren returns the maximum number of satisfied children.
func findContentChildren(greed, sizes []int) int {
	// slices.Sort requires Go 1.21+
	slices.Sort(greed)
	slices.Sort(sizes)
	child, cookie := 0, 0
	for child < len(greed) && cookie < len(sizes) {
		if sizes[cookie] >= greed[child] {
			child++ // this child is satisfied
		}
		cookie++ // try the next cookie regardless
	}
	return child
}
```

<Define term="Interval scheduling / merging" since="this chapter">
An **interval** is a pair `[start, end]` representing a window of time (or any ordered range). **Interval merging** folds overlapping windows into one: if window A ends at or after window B starts, they share time and collapse into `[min(A.start, B.start), max(A.end, B.end)]`. At Meridian, every ACH settlement run has a processing window `[open, close]`; windows from the same counterparty often overlap, and the reconciliation job must merge them before computing net positions. Getting merging wrong means counting the same transfer twice — or missing one entirely.

**On the job:** you hit interval problems whenever two events share a time range — meeting rooms, lock hold times, DB transaction windows, streaming time-series gaps. The merge/overlap check is everywhere; the pattern is always sort-then-sweep.
</Define>

New scenario: the interview scheduling system at a high-frequency trading firm. Hundreds of conference rooms, hundreds of interview slots. You need to merge overlapping blocks, find the minimum number of rooms, and cancel the fewest interviews possible so nobody double-books. Interval problems. Every one of them uses the same two moves.

**The two moves:**
1. **Sort** — by start time, or end time, depending on the problem.
2. **Sweep** — walk left to right, maintaining a running state (the "current merged interval," or a heap of room end-times, or a count of open intervals).

Sorting makes the overlap check local: if the next interval doesn't overlap the last one you touched, nothing after it will either.

### Classic: Merge Intervals

Given a list of intervals, merge all overlapping ones.

**Sort by start.** Sweep: if the current interval's start ≤ last merged interval's end, extend the merged end. Otherwise, push and start fresh.

**Complexity:** O(n log n) sort + O(n) sweep = **O(n log n)**.

```go
// merge returns a new slice of non-overlapping intervals covering the same range.
// Each interval is [start, end] where start ≤ end.
func merge(intervals [][]int) [][]int {
	if len(intervals) == 0 {
		return nil
	}
	// sort by start time
	slices.SortFunc(intervals, func(a, b []int) int {
		return a[0] - b[0]
	})
	out := [][]int{intervals[0]}
	for _, iv := range intervals[1:] {
		last := out[len(out)-1]
		if iv[0] <= last[1] {
			// overlapping — extend the merged interval's end if needed
			if iv[1] > last[1] {
				last[1] = iv[1]
			}
		} else {
			out = append(out, iv)
		}
	}
	return out
}
```

### Classic: Insert Interval

Given a sorted, non-overlapping list and a new interval, insert it in the right place, merging as needed.

**No re-sort needed.** Three phases: copy everything that ends before the new interval starts; merge everything that overlaps; copy the rest.

**Complexity:** O(n) — single pass, no sort.

```go
// insert inserts newInterval into the sorted, non-overlapping intervals slice.
func insert(intervals [][]int, newInterval []int) [][]int {
	out := make([][]int, 0, len(intervals)+1)
	i := 0
	n := len(intervals)

	// phase 1: copy all intervals that end before newInterval starts
	for i < n && intervals[i][1] < newInterval[0] {
		out = append(out, intervals[i])
		i++
	}
	// phase 2: merge all overlapping intervals into newInterval
	for i < n && intervals[i][0] <= newInterval[1] {
		if intervals[i][0] < newInterval[0] {
			newInterval[0] = intervals[i][0]
		}
		if intervals[i][1] > newInterval[1] {
			newInterval[1] = intervals[i][1]
		}
		i++
	}
	out = append(out, newInterval)
	// phase 3: copy the remainder
	out = append(out, intervals[i:]...)
	return out
}
```

### Classic: Non-Overlapping Intervals (erase fewest)

Remove the minimum number of intervals so that the rest don't overlap.

**Sort by end time.** Greedy: always keep the interval that ends earliest — it leaves maximum room for future intervals. Count every interval you skip.

**Complexity:** O(n log n).

```go
// eraseOverlapIntervals returns the minimum number of intervals to remove.
func eraseOverlapIntervals(intervals [][]int) int {
	if len(intervals) == 0 {
		return 0
	}
	// sort by end time — greedy: keep intervals that end soonest
	slices.SortFunc(intervals, func(a, b []int) int {
		return a[1] - b[1]
	})
	removed := 0
	lastEnd := intervals[0][1]
	for _, iv := range intervals[1:] {
		if iv[0] < lastEnd {
			// overlap — remove this one (keep the one with smaller end, already chosen)
			removed++
		} else {
			lastEnd = iv[1]
		}
	}
	return removed
}
```

### Classic: Meeting Rooms II (minimum rooms)

Given meeting intervals, find the minimum number of conference rooms required.

**Approach 1 — min-heap:** sort by start. Maintain a min-heap of room end-times. For each meeting: if the earliest-ending room is free (its end ≤ current start), reuse it (update the heap). Otherwise, open a new room. Heap size at any point = rooms in use. Answer = max heap size ever reached.

**Approach 2 — sweep line:** split into start-events (+1) and end-events (-1), sort all events by time (ends before starts on ties), sweep and track the running count.

We'll implement the heap approach — it maps directly to `container/heap`.

**Complexity:** O(n log n).

```go
// minMeetingRooms returns the minimum number of rooms needed.
func minMeetingRooms(intervals [][]int) int {
	if len(intervals) == 0 {
		return 0
	}
	slices.SortFunc(intervals, func(a, b []int) int {
		return a[0] - b[0]
	})
	// min-heap of room end-times
	h := &minHeap{intervals[0][1]}
	heap.Init(h)
	for _, iv := range intervals[1:] {
		if (*h)[0] <= iv[0] {
			// earliest-ending room is free; reuse it
			heap.Pop(h)
		}
		heap.Push(h, iv[1])
	}
	return h.Len()
}

// minHeap is a min-heap of ints (room end-times).
type minHeap []int

func (h minHeap) Len() int            { return len(h) }
func (h minHeap) Less(i, j int) bool  { return h[i] < h[j] }
func (h minHeap) Swap(i, j int)       { h[i], h[j] = h[j], h[i] }
func (h *minHeap) Push(x any)         { *h = append(*h, x.(int)) }
func (h *minHeap) Pop() any {
	old := *h
	n := len(old)
	x := old[n-1]
	*h = old[:n-1]
	return x
}
```

<UnderTheHood title="Why sort-then-sweep makes interval problems O(n log n)">

When intervals are unsorted, checking whether any two intervals overlap is O(n²) — you compare every pair. Sorting by start time turns the problem local: after sorting, the only interval that can overlap interval `i` is interval `i+1` (or the current "active" set). You never need to look backwards.

Formally: after sorting, for intervals `A[i]` and `A[j]` with `i < j`, we know `A[i].start ≤ A[j].start`. The only overlap question left is whether `A[j].start ≤ A[i].end`. The start ordering means any interval `A[k]` with `k > j` has `A[k].start ≥ A[j].start ≥ A[i].end` — so you can stop checking once the gap opens. That's why the sweep is O(n): every interval is touched exactly once.

The heap in Meeting Rooms II (O(log n) per push/pop) bumps the sweep from O(n) to O(n log n), but sorting dominates at O(n log n) anyway, so the overall complexity stays the same. As of Go 1.24, `slices.SortFunc` uses pattern-defeating quicksort (pdqsort) — typically faster than mergesort in practice for the random inputs common in interviews.

</UnderTheHood>

## Bit Manipulation

<Define term="Bit manipulation (AND / OR / XOR / shift)" since="this chapter">
**Bit manipulation** operates directly on the binary representation of integers using CPU-native instructions — no loops, no allocations. The four operators: `&` (AND — both bits must be 1), `|` (OR — either bit is 1), `^` (XOR — bits differ), and `<<`/`>>` (left/right shift — multiply or divide by powers of two). At Meridian, each transfer record carries a `flags uint32` bitmask: bit 0 = settled, bit 1 = reconciled, bit 2 = disputed. Checking `flags & (1 << 2)` tells you in one instruction whether the transfer is disputed — no string parse, no struct field lookup.

**Why it matters:** bitmask operations are O(1) and branch-free. They show up in permission systems, set membership, hashing, and interview problems alike. Misusing them (signed integers, wrong operator precedence) produces silent wrong results.
</Define>

<Define term="XOR trick — cancels pairs" since="this chapter">
XOR has two key properties: `a ^ a == 0` (any value XORed with itself is zero) and `a ^ 0 == a` (zero is the identity). XOR all values in a list; every value that appears **an even number of times** cancels to zero; whatever appears **an odd number of times** survives. At Meridian this detects the single transaction ID that appears without a matching pair in a de-duplication pass — one loop, O(n) time, O(1) space, no hash map. The trick generalises: XOR `0..n` against all elements in a slice to find a missing number by the same cancellation logic.
</Define>

New scenario: you're reviewing audit logs for a payment processor. Each transaction is flagged with a bitmask of permission categories. You need to check which permissions are set, toggle experimental flags without touching the others, and find the one transaction ID that appears without a pair (every other ID is duplicated). All in O(1) space, all in one pass. This is why bit manipulation exists.

### The fundamental operations

Every trick reduces to four operators: `&` (AND), `|` (OR), `^` (XOR), `~` (NOT for bitwise complement — in Go, `^x` for a single operand), and the shifts `<<` (left) and `>>` (right).

### Power-of-two check

`x & (x-1) == 0` — if x is a power of two, it has exactly one bit set. Subtracting 1 flips that bit to 0 and sets all lower bits. ANDing the two gives zero. O(1).

```go
// isPowerOfTwo reports whether x is a positive power of two.
func isPowerOfTwo(x int) bool {
	return x > 0 && x&(x-1) == 0
}
```

### Count set bits (popcount) — Brian Kernighan's algorithm

`x & (x-1)` clears the lowest set bit. Repeat until zero, counting iterations.

**Complexity:** O(k) where k = number of set bits (not O(32)).

```go
// countBits returns the number of 1-bits in x.
func countBits(x int) int {
	count := 0
	for x != 0 {
		x &= x - 1 // clear lowest set bit
		count++
	}
	return count
}
```

### XOR tricks — single number

Every integer in a slice appears exactly twice, except one. Find it. O(n) time, O(1) space.

**Why XOR works:** `a ^ a == 0` (same value cancels), `a ^ 0 == a` (identity). XOR all values; every duplicate cancels, leaving the single.

```go
// singleNumber returns the element that appears exactly once.
// All others appear exactly twice.
func singleNumber(nums []int) int {
	result := 0
	for _, n := range nums {
		result ^= n
	}
	return result
}
```

### XOR swap (no temp variable)

```go
// swap exchanges a and b using XOR — no temporary variable needed.
func swap(a, b *int) {
	*a ^= *b // a = a XOR b
	*b ^= *a // b = b XOR (a XOR b) = original a
	*a ^= *b // a = (a XOR b) XOR original a = original b
}
```

### Missing number

Find the missing number in `[0..n]` given n elements. XOR `0..n` against all elements in the slice — everything cancels except the missing one.

```go
// missingNumber finds the missing number in [0..n].
func missingNumber(nums []int) int {
	n := len(nums)
	result := n // XOR with n itself
	for i, v := range nums {
		result ^= i ^ v
	}
	return result
}
```

### Bitmask for subsets

To enumerate all subsets of an n-element set, iterate masks from `0` to `(1<<n)-1`. Bit i of the mask says whether element i is included.

```go
// allSubsets prints every subset of items using a bitmask.
func allSubsets(items []string) {

			if mask&(1<<i) != 0 {
				subset = append(subset, item)
			}
		}
		fmt.Println(subset)
	}
}
```

<UnderTheHood title="Why XOR is addition without carry, and why x & (x-1) clears the lowest set bit">

**XOR as carryless addition.** In binary, addition is `a + b = (a XOR b) + 2*(a AND b)`. The `XOR` term gives the sum bits where no carry occurs; the `AND` term produces the carry. XOR alone is addition where the carry is always discarded — so `1 XOR 1 = 0` (they cancel) instead of `10` in binary. That's why pairs XOR to zero: they have identical bits, so every position cancels.

**Why `x & (x-1)` clears the lowest set bit.** Consider any integer `x` whose lowest set bit is at position `k`. In binary, `x` ends with `...1 followed by k zeros`. Subtracting 1 borrows from position `k`: it clears the bit at `k` and sets all bits below it — so `x-1` ends with `...0 followed by k ones`. The AND of these two patterns gives `...0 followed by k zeros` at the low end: all bits below `k` cancelled (one side has 0s, the other has 1s), and bit `k` itself became `1 & 0 = 0`. Every bit above `k` is unchanged in both, so the AND preserves them. Net result: exactly the lowest set bit of `x` was cleared, and nothing else changed. Count how many times you can do this before reaching zero — that's the popcount.

Both tricks hold in Go's `int` (two's-complement, 64-bit on modern hardware as of Go 1.24) and in any unsigned integer type. Prefer `uint` for bitmasks to avoid sign-extension on `>>`.

</UnderTheHood>

```go
import (
	"fmt"
	"slices"
)

func minMeetingRoomsSweep(intervals [][]int) int {
	n := len(intervals)
	if n == 0 {
		return 0
	}
	starts := make([]int, n)
	ends := make([]int, n)
	for i, iv := range intervals {
		starts[i] = iv[0]
		ends[i] = iv[1]
	}
	slices.Sort(starts)
	slices.Sort(ends)

	rooms, endPtr := 0, 0
	for i := range n {
		if starts[i] < ends[endPtr] {
			rooms++ // new meeting starts before any room frees up
		} else {
			endPtr++ // a room freed — reuse it (don't increment rooms)
		}
	}
	return rooms
}

func main() {
	fmt.Println(minMeetingRoomsSweep([][]int{{0, 30}, {5, 10}, {15, 20}})) // 2
	fmt.Println(minMeetingRoomsSweep([][]int{{7, 10}, {2, 4}}))            // 1
}
```

Decoupling start and end arrays lets you compare them cleanly without a heap. When a new meeting starts before any end-time fires, a new room is needed. When an end-time fires first, a room is freed and reused.

- **Greedy** works when you have the **greedy-choice property** (local optimal never blocks global optimal) and **optimal substructure**. It commits; DP explores. The litmus test: coin change with arbitrary denominations breaks greedy — reach for DP when an early choice can close off a better path.
- **Interval problems** use two moves: **sort** (by start or end depending on what you're optimizing), then **sweep** left to right, maintaining just the current merged boundary or a heap of room end-times. Sorting makes the overlap check O(1) per interval; the whole solution is O(n log n).
- **Bit manipulation** building blocks: check bit i with `x & (1 << i)`, set with `x | (1 << i)`, clear with `x &^ (1 << i)`, toggle with `x ^ (1 << i)`. Power-of-two: `x & (x-1) == 0`. - All solutions in this chapter are **stdlib only**: `slices.Sort`, `slices.SortFunc`, `container/heap`, `range`-over-int (Go 1.22+). No dependencies.
