<HeroCard label="Appendix · Real-Time Systems" title="Real-Time Go: WebSocket Hubs & Outbound Webhooks">

Here's the thing, sport. Your server knows something — a payment cleared, a price moved, a job finished — and *someone else needs to know now*. Not on their next poll. Now. There are two ways a Go server pushes an event out into the world, and this chapter builds **both**, properly.

The first is the **WebSocket Hub**: a long-lived, full-duplex pipe to *many* connected clients — a live dashboard, a trading feed, a chat room — where your server fans one event out to thousands of browsers at once. You've seen a *single* WebSocket connection (the HTTP-servers chapter). That's not a real-time app; that's an echo. The real thing is the **Hub pattern** — one goroutine owning the whole client set, broadcasting over channels, and (the part everyone gets wrong) surviving the *one slow client* that would otherwise freeze the fan-out for everybody.

The second is the **outbound webhook**: instead of holding a connection open, you `POST` the event to a URL the *other* system gave you — how Stripe tells your backend a charge succeeded, how GitHub tells your CI a push happened. You've seen the *receiving* end (the payments chapter — verify the signature, dedup). This is the **sending** end: sign the payload so the receiver can trust it, deliver it with retries and backoff because their server *will* be down sometimes, dead-letter it when it's down too long, and accept that "at-least-once" means *they* must dedup. We build a real delivery engine, runnable, verified. By the end you can push events both ways — the held-open pipe and the fire-and-confirm POST — and you'll know exactly which one a problem wants. Let's build, sport.

</HeroCard>

## Two Ways to Push

Both patterns solve the same problem — *get an event from my server to someone else, promptly* — but they make opposite trade-offs, and picking the wrong one is a design smell you'll feel for months.

<Define term="Server push: WebSocket vs webhook">
A server has two fundamental ways to **push** an event outward. A **WebSocket** holds a single TCP connection **open** between your server and a connected client (typically a browser) and sends frames over it in both directions, for as long as the connection lives — ideal when the *client is online now* and wants a *stream* of low-latency updates (a live feed, a chat, a dashboard). An **outbound webhook** keeps **no** connection: when an event happens, your server makes a brand-new HTTP `POST` to a URL another *server* registered in advance, then hangs up — ideal for *server-to-server* notifications where the recipient may be offline, behind a queue, or processing asynchronously (a payment processor telling your backend a charge cleared). The rule of thumb: **WebSocket when a user's screen needs live updates; webhook when another system needs to be notified of an event.** One is a held-open pipe to a present client; the other is a fire-and-retry message to an absent server.
</Define>

<ConceptGrid cols={2}>
  <ConceptCard label="WebSocket — held-open pipe">Full-duplex, low-latency, client usually a browser that's **online right now**. You pay for it with a long-lived goroutine + connection per client and the work of fanning out to all of them. Best for: live dashboards, chat, trading, collaborative editing, presence.</ConceptCard>
  <ConceptCard label="Webhook — fire-and-confirm POST">No held connection; a fresh `POST` per event to a URL the recipient gave you. The recipient may be **offline** — so you sign, retry, and dead-letter. Best for: server-to-server events (payment cleared, build finished, row changed) consumed asynchronously.</ConceptCard>
  <ConceptCard label="What this chapter adds">The **producer** side of both. You've met a single WebSocket connection (ch19) and inbound webhook *verification* (ch9). Here: the **Hub** that broadcasts to many, and the **delivery engine** that sends webhooks reliably.</ConceptCard>
  <ConceptCard label="The shared discipline">Both fan an event out to consumers you don't control, so both must survive a *bad consumer*: the WebSocket Hub drops the slow client; the webhook sender retries then dead-letters the down receiver. Never let one bad consumer break delivery for the rest.</ConceptCard>
</ConceptGrid>

## The WebSocket Hub

A single WebSocket connection is easy. The *app* is the hard part: when an event fires, every connected client must get it — and clients connect and disconnect constantly. The answer is the **Hub**: one goroutine that owns the entire set of clients, so the set is mutated from exactly one place and needs no lock.

<Define term="The Hub pattern">
The **Hub pattern** is the canonical Go design for broadcasting to many WebSocket clients. A single **hub goroutine** owns a `map` of connected clients and `select`s over three channels: **register** (a new client joined), **unregister** (a client left), and **broadcast** (an event to send to everyone). Because only the hub goroutine ever touches the client map, there is **no mutex** — concurrency is handled by *communication*, not shared memory (the Go proverb). Each client gets its own buffered **send channel**; the hub writes a broadcast into every client's send channel, and a per-client writer goroutine drains that channel to the socket. This cleanly separates *who is connected* (the hub's job) from *writing bytes to one socket* (each client's job), and it's the structure under essentially every Go chat/live-feed/dashboard server.
</Define>

```go
package main

import (
	"fmt"
	"sort"
	"sync"
)

// A client is one connected socket: an id and its OWN buffered send channel.
// If that channel fills up, the client is too slow and we drop messages to it.
type client struct {
	id   int
	send chan string
}

// The Hub owns the client set. Only the hub goroutine touches `clients`,
// so there is NO mutex — coordination is by channels, not shared memory.
type Hub struct {
	register   chan *client
	unregister chan *client
	broadcast  chan string
	clients    map[*client]bool
}

func newHub() *Hub {
	return &Hub{
		register:   make(chan *client),
		unregister: make(chan *client),
		broadcast:  make(chan string),
		clients:    make(map[*client]bool),
	}
}

func (h *Hub) run(done chan struct{}) {
	for {
		select {
		case c := <-h.register:
			h.clients[c] = true
		case c := <-h.unregister:
			if h.clients[c] {
				delete(h.clients, c)
				close(c.send) // ends this client's writer goroutine
			}
		case msg := <-h.broadcast:
			for c := range h.clients {
				select {
				case c.send <- msg: // fast client: queued
				default: // buffer full → slow client → drop (never block the hub)
				}
			}
		case <-done:
			return
		}
	}
}

func main() {
	h := newHub()
	done := make(chan struct{})
	go h.run(done)

	var wg sync.WaitGroup
	var mu sync.Mutex
	got := map[int][]string{}

	fast1 := &client{id: 1, send: make(chan string, 8)}
	fast2 := &client{id: 2, send: make(chan string, 8)}
	slow := &client{id: 3, send: make(chan string)} // unbuffered, undrained → drops

	for _, c := range []*client{fast1, fast2} {
		wg.Add(1)
		go func(c *client) {
			defer wg.Done()
			for m := range c.send { // ends when the hub closes c.send
				mu.Lock()
				got[c.id] = append(got[c.id], m)
				mu.Unlock()
			}
		}(c)
	}

	h.register <- fast1
	h.register <- fast2
	h.register <- slow
	for i := 1; i <= 3; i++ {
		h.broadcast <- fmt.Sprintf("event-%d", i)
	}
	h.unregister <- fast1
	h.unregister <- fast2
	h.unregister <- slow
	close(done)
	wg.Wait()

	for _, id := range []int{1, 2} {
		sort.Strings(got[id])
		fmt.Printf("fast client %d received: %v\n", id, got[id])
	}
	fmt.Printf("slow client 3 received: %d msgs (dropped to protect the hub)\n", len(got[3]))
}
```

## Slow Clients

That non-blocking send is not a detail — it's the entire reason a hub survives production. Get it wrong and a single phone on a flaky connection takes down your broadcast for *every* user.

<Gotcha>
**A blocking broadcast lets one slow client freeze everyone.** The naive hub writes `c.send <- msg` directly in the broadcast loop. The moment one client's buffer fills — a mobile client on bad cell signal, a paused browser tab, a debugger-stopped connection — that send *blocks the hub goroutine*. And because the hub is the single goroutine handling register/unregister/broadcast for **all** clients, a block there freezes the whole system: no one gets messages, no one can connect or disconnect. The fix is the `select { case c.send <- msg: default: }` — a **non-blocking** send that drops the message (or, in production, disconnects the client after N drops) rather than waiting. You give each client a buffered channel for normal bursts, and you treat a *full* buffer as the signal "this client can't keep up — protect everyone else from it." Backpressure handled at the slowest consumer, never propagated up to the hub.
</Gotcha>

## Ping/Pong & Lifecycle

A WebSocket can sit open for hours. Two things will bite you: connections that die silently (no FIN packet — the client's laptop just slept), and writes that block forever on a stuck socket. Keepalives and deadlines handle both.

<ConceptGrid cols={2}>
  <ConceptCard label="Ping/pong keepalive">The server periodically sends a **ping** frame; a healthy client auto-replies **pong**. No pong within a deadline → the connection is dead (silently dropped, asleep, gone), so you close it and `unregister`. Without this, dead connections accumulate as zombie goroutines forever. `coder/websocket` and `gorilla/websocket` both expose this.</ConceptCard>
  <ConceptCard label="Write deadlines">After the HTTP upgrade, `net/http`'s `WriteTimeout` no longer applies — the connection was **hijacked** out of its control (you saw this in ch19). So *you* set a deadline on every write (a context timeout, e.g. 5–10s). A slow client that can't accept a write is closed instead of pinning its writer goroutine until the TCP stack gives up minutes later.</ConceptCard>
  <ConceptCard label="Clean unregister">Every exit path — read error, failed ping, write deadline, server shutdown — must funnel to `hub.unregister`, which deletes the client and closes its send channel. That close is what ends the writer goroutine (a `range` over a closed channel returns). Miss it and you leak a goroutine per dead connection.</ConceptCard>
  <ConceptCard label="Bounded everything">A long-lived endpoint is a Slowloris target: cap the message size, set read/write deadlines, and limit connections per IP. The same hardening the HTTP-servers chapter applies to requests, applied to *connections that never end*.</ConceptCard>
</ConceptGrid>

<Callout kind="pro" title="The two-goroutine-per-connection shape">
In a real hub, each connection runs **two** goroutines: a **reader** (`for { read frame; handle or unregister on error }`) and a **writer** (`for msg := range client.send { set write deadline; write frame }`), plus a ticker in the writer that sends periodic pings. The hub never writes to a socket directly — it only writes to `client.send`, and the writer goroutine owns the actual socket write *and* the deadline. This is why the hub stays fast: its job is set-management and a non-blocking channel send, never blocking I/O. The reader's only hub interaction is sending itself on `unregister` when the connection dies.
</Callout>

## Outbound Webhooks

Switch models. The recipient isn't a browser holding a connection — it's another company's server, and it gave you a URL. When your event fires, you `POST` to that URL. Simple in the happy path; the entire engineering is in the failure path, because **their server will be down sometimes and you must not lose the event.**

<Define term="Outbound webhook delivery">
An **outbound webhook** is your server notifying another *server* of an event by making an HTTP `POST` to a URL that server **registered with you in advance**, carrying the event as a JSON body. Unlike a WebSocket there is no persistent connection: each event is a fresh, independent request. Because the receiver is an external system you don't control — it may be deploying, overloaded, or briefly offline — reliable delivery is not "send and forget." It requires four things: **signing** the payload (so the receiver can verify it really came from you and wasn't tampered with), **retrying** on failure with backoff (their `503` is usually transient), **dead-lettering** after you exhaust retries (so a permanently-down receiver doesn't block or lose everything), and accepting **at-least-once** semantics (a retry after a network timeout may deliver twice, so the receiver must dedup). A production webhook sender is a small reliable-delivery system, not a single `http.Post`.
</Define>

## Signing

The receiver needs to know the POST *really* came from you and wasn't forged or modified in transit. You don't share a password on every request — you **sign** the payload with a shared secret, and they recompute the signature to check it. (This is the exact mechanism you *verified* on the inbound side in the payments chapter — now you're the one producing it.)

<Define term="HMAC payload signing">
**HMAC signing** proves a webhook's authenticity and integrity without sending the secret. You and the receiver share a secret out of band (when they register the webhook). For each delivery you compute **`HMAC-SHA256(secret, rawBody)`** and send it in a header (e.g. `X-Signature: sha256=…`). The receiver recomputes the same HMAC over the **exact raw bytes** it received and compares — using a **constant-time** comparison (`hmac.Equal`) to avoid timing attacks. If they match, the body is authentic (only someone with the secret could produce that MAC) and untampered (any change to the body changes the MAC). Two non-negotiables: sign the **raw bytes**, not a re-serialized struct (re-marshaling can reorder keys and break the signature), and compare in constant time. Real providers sign a provider-specific string (Stripe signs `timestamp + "." + body` and you check the timestamp to stop replay); always follow the documented canonicalization byte-for-byte.
</Define>

## Retries & Dead-Letters

Now the delivery engine itself — the part that turns "POST once and hope" into reliable delivery. We send the signed payload, retry transient failures with backoff, and give up into a dead-letter queue after a bounded number of attempts.

```go
package main

import (
	"bytes"
	"crypto/hmac"
	"crypto/sha256"
	"encoding/hex"
	"fmt"
	"io"
	"net/http"
	"net/http/httptest"
)

// sign computes the provider-style HMAC-SHA256 of the raw body. The receiver
// recomputes it with the shared secret and compares in constant time.
func sign(secret, body []byte) string {
	mac := hmac.New(sha256.New, secret)
	mac.Write(body)
	return "sha256=" + hex.EncodeToString(mac.Sum(nil))
}

// deliver POSTs the signed payload, retrying on non-2xx up to maxAttempts.
// A real sender sleeps backoff(attempt) + jitter between tries.
func deliver(url string, secret, body []byte, maxAttempts int) (int, bool) {
	for attempt := 1; attempt <= maxAttempts; attempt++ {
		req, _ := http.NewRequest("POST", url, bytes.NewReader(body))
		req.Header.Set("Content-Type", "application/json")
		req.Header.Set("X-Signature", sign(secret, body))
		req.Header.Set("X-Webhook-Id", "evt_123") // stable id → receiver dedups
		resp, err := http.DefaultClient.Do(req)
		if err == nil {
			io.Copy(io.Discard, resp.Body)
			resp.Body.Close()
			if resp.StatusCode/100 == 2 {
				return attempt, true
			}
		}
		// else: sleep backoff(attempt)+jitter, then retry
	}
	return maxAttempts, false // exhausted → dead-letter queue
}

func main() {
	secret := []byte("whsec_test")
	body := []byte(`{"event":"payment.succeeded","amount":5000}`)

	// flaky receiver: verifies the signature, fails twice (503), then succeeds.
	var hits int
	recv := httptest.NewServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		hits++
		raw, _ := io.ReadAll(r.Body)
		if !hmac.Equal([]byte(r.Header.Get("X-Signature")), []byte(sign(secret, raw))) {
			w.WriteHeader(http.StatusUnauthorized) // bad signature → reject
			return
		}
		if hits < 3 {
			w.WriteHeader(http.StatusServiceUnavailable) // transient
			return
		}
		w.WriteHeader(http.StatusOK)
	}))
	defer recv.Close()
	attempts, ok := deliver(recv.URL, secret, body, 5)
	fmt.Printf("flaky receiver: ok=%v after %d attempts\n", ok, attempts)

	// permanently-down receiver: exhausts retries → dead-letter.
	down := httptest.NewServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		w.WriteHeader(http.StatusInternalServerError)
	}))
	defer down.Close()
	a2, ok2 := deliver(down.URL, secret, body, 3)
	fmt.Printf("down receiver:  ok=%v after %d attempts → dead-letter\n", ok2, a2)

	// a signature from the wrong secret never matches.
	fmt.Printf("tampered signature accepted? %v\n",
		hmac.Equal([]byte(sign([]byte("wrong"), body)), []byte(sign(secret, body))))
}
```

<Callout kind="warn" title="Backoff needs jitter — the reliability chapter">
The retry loop above just says "sleep backoff(attempt)". Get that backoff wrong and you build a self-inflicted outage: if every sender retries on the *same* exponential schedule, a receiver that blips comes back to a synchronized **thundering herd** — every pending webhook from every sender hitting it at the identical instant, knocking it back down. The fix is **exponential backoff *plus jitter*** (randomize each delay) so retries spread out instead of resonating. This is exactly the time/backoff/jitter material — reuse it here; a webhook sender is one of its highest-value applications.
</Callout>

## At-Least-Once

The last truth about webhooks, and the one that surprises people: **you cannot guarantee exactly-once delivery, so you guarantee at-least-once and make the receiver dedup.** This is the same lesson as idempotency in distributed systems, applied to your delivery engine.

<Define term="At-least-once delivery and receiver dedup">
**At-least-once** means every event is delivered *one or more* times — never zero, possibly twice. It's unavoidable: if your `POST` times out, you don't know whether the receiver processed it before the network dropped the response, so you must retry — and if it *had* succeeded, that retry is a duplicate. You can't tell the two cases apart, so you choose at-least-once (retry, risk a dupe) over at-most-once (don't retry, risk a loss) — losing a "payment succeeded" event is far worse than processing it twice. The contract that makes this safe is a **stable event id** (e.g. `X-Webhook-Id: evt_123`) sent identically on every retry of the same event. The receiver records processed ids and **ignores** any it has already seen, so a duplicate delivery is a no-op. You provide the stable id and the retries; the receiver provides the dedup. (You implemented the *receiver's* side — store-and-check the id — in the inbound-webhook section; this is why the sender must keep the id constant across retries.)
</Define>

<Gotcha>
**Exactly-once is a fantasy; at-least-once + idempotency is the real system.** Don't try to make delivery exactly-once — across a network it's provably impossible, and code that claims it is hiding a bug. Instead: the **sender** retries (accepting it may double-deliver) and sends a **stable event id** on every attempt of the same event; the **receiver** dedups on that id (process once, ignore repeats). The same id must survive every retry — generate it when the event is *created*, not per attempt, or each retry looks like a new event and dedup fails. This is the idempotency-key pattern from the distributed-systems and payments chapters, now spanning the gap between your sender and someone else's receiver.
</Gotcha>

<UnderTheHood title="WebSocket Framing, Hijacking & TCP Buffer Semantics">

Underneath high-level WebSocket libraries (`nhooyr.io/websocket` or `gorilla/websocket`), Go performs low-level connection hijacking, framing byte manipulation, and socket buffer management.

### 1. The HTTP Connection Hijack (`http.Hijacker`)

Standard `net/http` handlers manage the request-response lifecycle and automatically close connections on return. Upgrading to a persistent WebSocket requires seizing direct ownership of the underlying TCP socket:

```go
hijacker, ok := w.(http.Hijacker)
if !ok {
    http.Error(w, "websocket: response writer does not support hijacking", http.StatusInternalServerError)
    return
}
conn, bufrw, err := hijacker.Hijack()
if err != nil {
    return
}
// From this moment, net/http's ReadTimeout and WriteTimeout no longer apply.
// You own conn (net.Conn) and must manage read/write deadlines and conn.Close().
```

Calling `Hijack()` detaches the connection from `http.Server`. Go returns a `*bufio.ReadWriter` (`bufrw`) holding any bytes already buffered from the client handshake. Any subsequent writes bypass `net/http`'s response formatting.

### 2. RFC 6455 Framing & The Client Masking Invariant

A WebSocket message is split into one or more binary frames on the wire:
- **Byte 0:** `FIN` (1 bit indicating final frame), `RSV1-3` (3 extension bits, usually 0), `Opcode` (4 bits: `0x1` Text, `0x2` Binary, `0x8` Close, `0x9` Ping, `0xA` Pong).
- **Byte 1:** `MASK` bit (1 bit) + 7-bit Payload Length.
  - If length $\le 125$, the 7-bit value is the exact length.
  - If length $= 126$, the next 2 bytes encode an unsigned 16-bit integer length.
  - If length $= 127$, the next 8 bytes encode an unsigned 64-bit integer length.
- **Masking Key (4 bytes):** Mandated by RFC 6455 for all **client-to-server** frames (and strictly forbidden for server-to-client frames). Why? To prevent **cache poisoning attacks** against intermediary transparent proxies: if an attacker's script in a browser could send unmasked predictable raw HTTP request bytes inside a WebSocket payload, an unsuspecting intermediate proxy might misinterpret the stream as pipelined HTTP requests.

### 3. TCP Buffer Bloat, `SO_SNDBUF`, and Netpoll Semantics

When a Go server writes to a WebSocket (`conn.Write(b)`):
- Bytes enter the OS kernel socket send buffer (`SO_SNDBUF`, typically 64KB–256KB).
- If a slow client stops acknowledging TCP packets (window size collapses to 0), the kernel buffer fills.
- When `SO_SNDBUF` is full, `conn.Write` would block the calling goroutine. In Go's runtime, `net.Conn` delegates to the runtime network poller (`netpoll` via `epoll`/`kqueue`), parking the goroutine until the socket is writable.
- If the Hub sends directly to slow sockets without buffered channels and `select` with `default`, every active sender goroutine parks in `netpoll`, stalling the entire broadcast system. Per-client buffered channels decouple the Hub's broadcast loop from kernel socket backpressure.

</UnderTheHood>

<Exercise n={1} title="Calculate RFC 6455 Frame Header Size" level="easy">

Write `FrameHeaderSize(payloadLen int, isClient bool) int` that computes the exact number of header bytes on the wire for an unfragmented RFC 6455 frame, taking into account the 2 initial bytes, extended length bytes (16-bit or 64-bit), and the mandatory 4-byte mask for client frames.

<Solution>

```go
package main

import "fmt"

func FrameHeaderSize(payloadLen int, isClient bool) int {
	// Base header: 1 byte (FIN+Opcode) + 1 byte (MASK+7-bit len)
	size := 2
	if payloadLen > 65535 {
		size += 8 // 64-bit extended payload length
	} else if payloadLen > 125 {
		size += 2 // 16-bit extended payload length
	}
	if isClient {
		size += 4 // Client frames must include a 4-byte masking key
	}
	return size
}

func main() {
	fmt.Println("Server 50 bytes:", FrameHeaderSize(50, false))       // 2
	fmt.Println("Client 50 bytes:", FrameHeaderSize(50, true))        // 6
	fmt.Println("Server 1000 bytes:", FrameHeaderSize(1000, false))   // 4
	fmt.Println("Client 70000 bytes:", FrameHeaderSize(70000, true))  // 14
}
```

Client frames always incur 4 additional bytes for the random XOR mask key, while large payloads append 2 or 8 bytes of extended length indicators.

</Solution>

</Exercise>

<Exercise n={2} title="Non-Blocking Hub Fan-Out" level="medium">

Write `NonBlockingBroadcast(clients []chan string, message string) (sent, dropped int)` that delivers `message` to all provided client channels without blocking. If a client's channel is full or unbuffered and cannot receive immediately, increment `dropped` and proceed to the next client.

<Solution>

```go
package main

import "fmt"

func NonBlockingBroadcast(clients []chan string, message string) (sent, dropped int) {
	for _, ch := range clients {
		select {
		case ch <- message:
			sent++
		default:
			dropped++
		}
	}
	return sent, dropped
}

func main() {
	fast := make(chan string, 2)
	slow := make(chan string) // unbuffered, will block if no active receiver

	sent, dropped := NonBlockingBroadcast([]chan string{fast, slow}, "live_event")
	fmt.Printf("Broadcast result: sent=%d, dropped=%d\n", sent, dropped)
}
```

The `select` with `default` prevents the broadcaster from parking on saturated or unresponsive consumer channels, isolating slow clients from degrading system throughput.

</Solution>

</Exercise>

<Exercise n={3} title="Timestamped Webhook Signature" level="medium">

Implement `SignStripeStyle(secret []byte, payload []byte, timestamp int64) string` that returns a header string formatted as `t=<timestamp>,v1=<hmac-sha256(secret, "<timestamp>.<payload>")>`.

<Solution>

```go
package main

import (
	"crypto/hmac"
	"crypto/sha256"
	"encoding/hex"
	"fmt"
)

func SignStripeStyle(secret []byte, payload []byte, timestamp int64) string {
	signedPayload := fmt.Sprintf("%d.%s", timestamp, string(payload))
	mac := hmac.New(sha256.New, secret)
	mac.Write([]byte(signedPayload))
	sig := hex.EncodeToString(mac.Sum(nil))
	return fmt.Sprintf("t=%d,v1=%s", timestamp, sig)
}

func main() {
	secret := []byte("whsec_live_abcdef123456")
	payload := []byte(`{"id":"evt_001","type":"charge.captured"}`)
	header := SignStripeStyle(secret, payload, 1700000000)
	fmt.Println("Header:", header)
}
```

Prefixing the signed payload with the UNIX timestamp prevents replay attacks by enabling the receiver to reject signatures created outside a defined tolerance window (e.g. 5 minutes).

</Solution>

</Exercise>

<Exercise n={4} title="Idempotent Receiver Deduplication" level="hard">

Write `IsDuplicate(seen map[string]int64, eventID string, now int64, ttl int64) bool` that checks if an incoming `eventID` has already been processed within the given `ttl` window. If not seen, record `eventID` with `now` and return `false`. Also purge any stale entries in `seen` older than `now - ttl`.

<Solution>

```go
package main

import "fmt"

func IsDuplicate(seen map[string]int64, eventID string, now int64, ttl int64) bool {
	// 1. Evict expired entries
	cutoff := now - ttl
	for id, timestamp := range seen {
		if timestamp < cutoff {
			delete(seen, id)
		}
	}

	// 2. Check if already processed
	if _, exists := seen[eventID]; exists {
		return true
	}

	// 3. Mark as processed
	seen[eventID] = now
	return false
}

func main() {
	cache := make(map[string]int64)
	ttl := int64(300) // 5 minutes

	fmt.Println("First delivery:", IsDuplicate(cache, "evt_1", 1000, ttl))     // false
	fmt.Println("Duplicate delivery:", IsDuplicate(cache, "evt_1", 1050, ttl)) // true
	fmt.Println("After TTL expiry:", IsDuplicate(cache, "evt_1", 1400, ttl))   // false (evicted & accepted)
}
```

At-least-once delivery guarantees that duplicate webhooks will arrive. Maintaining an expiring bounded deduplication cache at the receiver ensures idempotency without unbounded memory growth.

</Solution>

</Exercise>

<Recap>

- A server **pushes** events two ways: a **WebSocket** (held-open, full-duplex pipe to a client that's online *now* — live feeds, chat, dashboards) and an **outbound webhook** (a fresh, retrying `POST` to another *server's* URL — server-to-server event notifications). Pick WebSocket when a screen needs live updates, webhook when a system needs to be notified.
- The **WebSocket Hub** is one goroutine owning the client set, `select`ing over **register / unregister / broadcast** — so the set is mutated from one place with **no mutex** (communicate, don't share). Each client has its **own buffered send channel** drained by its own writer goroutine.
- The broadcast must be a **non-blocking** send (`select { case c.send <- m: default: }`): a slow client's full buffer means the message is **dropped for that client**, never blocking the hub — otherwise one stalled connection freezes everyone.
- Long-lived connections need **ping/pong** keepalives (detect silently-dead clients) and **write deadlines** (after the upgrade, `net/http`'s `WriteTimeout` is gone — the connection was hijacked), and every exit path must funnel to **unregister** (which closes `send` and ends the writer goroutine) or you leak goroutines.
- An **outbound webhook** sender is a small reliable-delivery system: **sign** the raw payload (`HMAC-SHA256(secret, body)` → `X-Signature`), **retry** transient failures with **exponential backoff + jitter** (no jitter → thundering herd), and **dead-letter** after exhausting attempts so a down receiver never silently loses events.
- Delivery is **at-least-once**, never exactly-once (a timed-out `POST` must be retried, risking a duplicate). Send a **stable event id** on every retry of the same event; the **receiver dedups** on it. Generate the id when the event is created, not per attempt.
- Both producers must survive a **bad consumer** without breaking delivery for the rest: the Hub drops the slow client; the sender retries-then-dead-letters the down receiver.

</Recap>
