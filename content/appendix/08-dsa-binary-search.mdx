## Classic Search & Boundary Discipline

### The scenario

You're a backend engineer at a trading platform. You have a sorted slice of `int64` timestamps representing when limit orders were placed (millions of them, sorted ascending). A client asks: "Does order with timestamp `T` exist?" A linear scan is O(n) — that's millions of comparisons on every request. The market moves in microseconds. You need O(log n).

That's binary search. The idea: the array is **sorted**, so at any point you can look at the middle element and *eliminate half the remaining search space* in one comparison. Repeat until you find it or run out.

**On the job:** every sorted data lookup that needs sub-millisecond latency — index lookups, sorted caches, range queries on sorted IDs — reaches for this. Get the boundary wrong and the service either returns stale data or spins in an infinite loop under load.

<Define term="Binary search (on sorted data)">
**Binary search** finds a target in a sorted collection in **O(log n)** by repeatedly halving the live search interval. At each step, compare the middle element to the target: if equal, done; if the middle is smaller, the target must be in the right half; if larger, the left half. Because the data is sorted, one comparison eliminates half the remaining candidates. Without sortedness the halving logic is invalid — binary search is the wrong tool on unsorted data.
</Define>

Simple? Yes. Correct first try under interview pressure? Almost never. Let me show you why — and give you the one template to rule them all.

### The three things that kill attempts

<ConceptGrid cols={3}>
  <ConceptCard label="Loop condition">Is it `lo <= hi` or `lo < hi`? The answer depends on what `lo` and `hi` *mean* in your template. Pick one meaning, stick with it every time. We'll use the closed-interval `[lo, hi]` model: both endpoints are valid candidates. That gives us `lo <= hi`.</ConceptCard>
  <ConceptCard label="Mid calculation">`mid := (lo + hi) / 2` *overflows* when `lo` and `hi` are both large `int` values close to `math.MaxInt`. The safe form — always — is `mid := lo + (hi-lo)/2`. In Go, `int` is 64 bits on modern hardware, so overflow is rarer than in C, but write the safe form anyway: it's the same typing cost and it's always correct.</ConceptCard>
  <ConceptCard label="How you update lo/hi">When `nums[mid]` is too small, you set `lo = mid + 1` — because `mid` itself is eliminated. When it's too big, `hi = mid - 1` — same reason. If you write `lo = mid` instead of `lo = mid + 1`, the interval can stop shrinking and you spin forever on two equal elements.</ConceptCard>
  <Gotcha>The infinite-loop trap: `mid := lo + (hi-lo)/2` rounds *down*, so when `lo == hi - 1`, mid equals lo. If your update says `lo = mid` (not `lo = mid + 1`), the loop never makes progress. Always write `lo = mid + 1` and `hi = mid - 1` — both sides eliminate `mid` from future consideration.</Gotcha>
</ConceptGrid>

<Define term="Boundary discipline (lo<=hi, safe mid, lo=mid+1 / hi=mid-1)">
The three rules that make binary search correct every time: **(1) Loop condition** — use `lo <= hi` with the closed `[lo, hi]` model where both endpoints are live candidates; or `lo < hi` with a half-open `[lo, hi)` model for lower-bound variants. Pick one and never mix them. **(2) Safe mid** — always compute `mid := lo + (hi-lo)/2`, never `(lo+hi)/2`, to avoid integer overflow when both values are near `math.MaxInt`. **(3) Elimination** — always move the boundary past mid: `lo = mid+1` or `hi = mid-1`. Writing `lo = mid` stalls the loop when `lo == hi-1` because mid rounds down to lo, and the interval never shrinks. Every binary search bug in an interview traces back to one of these three violations.
</Define>

### The canonical template

Pick this template, internalize it, never deviate:

```go
// binarySearch returns the index of target in a sorted slice,
// or -1 if not present. Uses the closed [lo, hi] interval.
func binarySearch(nums []int, target int) int {
	lo, hi := 0, len(nums)-1
	for lo <= hi {
		mid := lo + (hi-lo)/2 // safe mid: no overflow
		switch {
		case nums[mid] == target:
			return mid
		case nums[mid] < target:
			lo = mid + 1 // target is to the right; mid is gone
		default:
			hi = mid - 1 // target is to the left; mid is gone
		}
	}
	return -1 // not found
}

func main() {
	orders := []int{100, 200, 350, 500, 720, 980, 1100}
	fmt.Println(binarySearch(orders, 500))  // 3
	fmt.Println(binarySearch(orders, 999))  // -1
}
```

<UnderTheHood title="Why binary search is O(log n) — and what 'invariant' means">

At each iteration the search space `[lo, hi]` has `hi - lo + 1` elements. After one comparison we reduce that to at most `⌊(hi-lo)/2⌋` elements — less than half. Starting from `n` elements:

- After 1 step: ≤ `n/2`
- After 2 steps: ≤ `n/4`
- After k steps: ≤ `n/2^k`

The loop terminates when the space reaches 0 (`lo > hi`). That happens when `n/2^k < 1`, i.e., `k > log₂(n)`. So the loop runs at most `⌊log₂(n)⌋ + 1` times — O(log n).

The **invariant** is the claim that holds at the *top* of every loop iteration: "if `target` exists in `nums`, it lives somewhere in `[lo, hi]`." Prove it:

1. **Base case:** `lo = 0, hi = len-1` — obviously the whole array contains `target` if it exists.
2. **Inductive step:** we branch on `nums[mid]`. If `nums[mid] < target`, target can't be at index ≤ mid (sorted order), so `lo = mid + 1` preserves the invariant. Symmetric for `hi`. If `nums[mid] == target`, we return immediately.
3. **Termination:** when `lo > hi` the interval is empty, so target doesn't exist — return -1.

The invariant is *why* `lo = mid + 1` (not `lo = mid`) is mandatory: `lo = mid` doesn't eliminate anything, stalls the shrinkage, and the loop spins forever when `lo == hi`. As of Go 1.26, the compiler won't save you — this is a logic error, not a type error.

</UnderTheHood>

## Finding Boundaries

### The scenario

Same order-timestamp system. Now the client asks: "Give me the *first* order placed at or after timestamp T, and the *last* order placed at or before T." That's lower-bound and upper-bound — the pair of building blocks that make every boundary query possible.

### Lower bound: first occurrence (or insert position)

The lower bound answers: **"What is the leftmost index where `nums[i] >= target`?"** This is also called the "search-insert position" — if target isn't present, it's where you'd insert it to keep the array sorted.

Reframe: we want the leftmost position where the predicate `nums[i] >= target` is **true**. The structure: the array looks like `[false, false, …, false, true, true, …, true]` — all the falses on the left, all the trues on the right. Binary search finds the boundary.

```go
// lowerBound returns the first index where nums[i] >= target,
// or len(nums) if all elements are less than target.
func lowerBound(nums []int, target int) int {
	lo, hi := 0, len(nums) // note: hi = len(nums), not len-1
	for lo < hi {           // note: strict < because hi is one past the end
		mid := lo + (hi-lo)/2
		if nums[mid] < target {
			lo = mid + 1 // mid is definitely not the answer
		} else {
			hi = mid // mid could still be the answer; keep it in play
		}
	}
	return lo // lo == hi; this is the boundary
}
```

Notice the template changed: `hi = len(nums)` (not `len-1`) and the condition is `lo < hi` (not `lo <= hi`). Why? Because the answer could be "insert at position len" — one past the end — and we need `hi` to be able to hold that. The invariant is now: **"the answer is somewhere in [lo, hi]"** where both endpoints are possible, and we stop when `lo == hi`.

### Upper bound: last occurrence

Upper bound answers: **"What is the leftmost index where `nums[i] > target`?"** Then the last occurrence of target is at index `upperBound - 1`.

```go
// upperBound returns the first index where nums[i] > target,
// i.e., one past the last occurrence of target.
func upperBound(nums []int, target int) int {
	lo, hi := 0, len(nums)
	for lo < hi {
		mid := lo + (hi-lo)/2
		if nums[mid] <= target {
			lo = mid + 1
		} else {
			hi = mid
		}
	}
	return lo
}

// firstAndLast returns the first and last indices of target,
// or (-1, -1) if not present.
func firstAndLast(nums []int, target int) (int, int) {
	first := lowerBound(nums, target)
	if first == len(nums) || nums[first] != target {
		return -1, -1
	}
	return first, upperBound(nums, target) - 1
}
```

<Define term="Lower bound, upper bound, and sort.Search">
A **lower bound** is the first index where `nums[i] >= target` — the leftmost place the target could sit. An **upper bound** is the first index where `nums[i] > target` — one past the last occurrence. Together they bracket the exact range of any value in a sorted slice, including duplicates. Go's `sort.Search(n, f)` is the stdlib spelling of lower bound: it finds the smallest index in `[0, n)` where a caller-supplied monotone predicate `f` first becomes true. If `f` is false for every index, `sort.Search` returns `n` — a past-the-end sentinel, not `-1`. You must always guard the result: `if i == len(nums) || nums[i] != target { /* not found */ }`.
</Define>

### Go's stdlib: `sort.Search`

Go's standard library gives you a generic lower-bound via `sort.Search(n, f)`. It returns the smallest index `i` in `[0, n)` for which `f(i)` is true, assuming `f` is false for indices before the answer and true after. It uses the same `lo < hi` invariant internally.

```go
import (
	"fmt"
	"sort"
)

func main() {
	orders := []int{100, 200, 350, 350, 350, 500, 720}
	target := 350

	// First occurrence of 350
	i := sort.Search(len(orders), func(i int) bool {
		return orders[i] >= target
	})
	fmt.Println(i) // 2
}
```

## Rotated & Modified Arrays

### The scenario

Your trading platform archives order books. At midnight it rotates the sorted timestamp array into a new partition. During rotation, the array gets written starting at some pivot — so the final stored array might look like `[500, 720, 980, 100, 200, 350]`: sorted, but rotated. You still need to find timestamps in O(log n).

### Search in rotated sorted array

The key insight: even though the whole array isn't sorted, **at least one half of `[lo, hi]` is always fully sorted** after any split at `mid`. You can determine which half is sorted in O(1) and then decide whether your target falls inside it.

```go
// searchRotated finds target in a sorted-then-rotated array.
// Returns index or -1. Assumes no duplicates.
func searchRotated(nums []int, target int) int {
	lo, hi := 0, len(nums)-1
	for lo <= hi {
		mid := lo + (hi-lo)/2
		if nums[mid] == target {
			return mid
		}
		// Left half [lo..mid] is sorted when nums[lo] <= nums[mid].
		if nums[lo] <= nums[mid] {
			// Is target inside the sorted left half?
			if nums[lo] <= target && target < nums[mid] {
				hi = mid - 1 // yes: search left
			} else {
				lo = mid + 1 // no: search right
			}
		} else {
			// Right half [mid..hi] must be sorted.
			if nums[mid] < target && target <= nums[hi] {
				lo = mid + 1 // target inside sorted right half
			} else {
				hi = mid - 1 // search left
			}
		}
	}
	return -1
}
```

### Find minimum in rotated sorted array

A companion problem: find the minimum element (i.e., find the rotation pivot). The minimum is the only element where `nums[i] < nums[i-1]`. Binary search on the sorted right half:

```go
// findMin returns the minimum element in a sorted-then-rotated slice.
func findMin(nums []int) int {
	lo, hi := 0, len(nums)-1
	for lo < hi {
		mid := lo + (hi-lo)/2
		if nums[mid] > nums[hi] {
			// Minimum is in the right half (past mid).
			lo = mid + 1
		} else {
			// nums[mid] <= nums[hi]: mid could be the min; keep it.
			hi = mid
		}
	}
	return nums[lo]
}
```

## Search on the Answer Space

### The scenario — and the big idea

Your platform needs to split a giant log file of `n` order events into `k` sequential chunks for parallel processing, minimizing the size of the largest chunk. Or: given a cargo ship with capacity `W`, find the minimum number of days to ship all packages when you load packages in order. Or: Koko the bear eats bananas from `n` piles — at speed `s` bananas/hour — and you need the *minimum* speed that lets her finish all piles within `h` hours.

These problems look nothing like "search a sorted array." But they share one structure: **the answer is a number, and the feasibility of a given answer is monotone.** If speed `s` is fast enough for Koko, then any speed `> s` is also fast enough. That's a binary-searchable predicate on the answer space.

<Define term="Binary search on the answer space">
Instead of searching a sorted array for a value, you **binary-search the range of possible answers** for the minimum (or maximum) that satisfies a feasibility condition. The condition must be **monotone**: if answer `x` works, then every answer larger than `x` also works (or every answer smaller, depending on direction). You define `lo` = smallest conceivable answer and `hi` = largest conceivable answer, write a `canDo(mid)` check in O(n), and binary-search for the boundary. Total complexity: O(n log(answer_range)). The unlock: it turns "try every possible answer" O(n·m) brute force into O(n log m), which is often the difference between a TLE and an accepted submission. The trap: if `canDo` is not truly monotone, binary search silently returns a wrong answer — always verify monotonicity first.
</Define>

**The pattern:**
1. Establish the answer's possible range `[lo, hi]`.
2. Write a `canDo(x)` predicate: "Is answer `x` feasible?"
3. `canDo` is monotone: if `x` works, so does anything larger (or anything smaller, depending on direction).
4. Binary-search for the leftmost `x` where `canDo(x)` is true.

This is called **binary search on the answer space**, and it turns O(n²) or O(n·m) brute-force problems into O(n log m).

### Classic: Koko eating bananas (minimum eating speed)

Koko has `piles []int` piles of bananas and `h` hours to eat them all. Each hour she eats at most `speed` bananas from one pile. Find the minimum integer `speed` such that she can finish all piles within `h` hours.

```go
import "math"

// hoursNeeded returns how many hours Koko needs at a given speed.
// Each pile takes ceil(pile / speed) hours.
func hoursNeeded(piles []int, speed int) int {
	hours := 0
	for _, p := range piles {
		hours += (p + speed - 1) / speed // ceiling division without float
	}
	return hours
}

// minEatingSpeed finds the minimum speed for Koko to finish in h hours.
func minEatingSpeed(piles []int, h int) int {
	lo := 1 // minimum possible speed (at least 1 banana/hour)
	hi := 0
	for _, p := range piles {
		hi = max(hi, p) // max speed needed is the largest pile
	}
	for lo < hi {
		mid := lo + (hi-lo)/2
		if hoursNeeded(piles, mid) <= h {
			hi = mid // mid is feasible; try to do better (slower)
		} else {
			lo = mid + 1 // mid is too slow; need more speed
		}
	}
	return lo
}
```

```go
			hi = mid
		} else {
			lo = mid + 1
		}
	}
	return lo
}
```

### Variant: integer square root

`sqrt(n)` (integer floor). Answer space `[0, n]`; predicate `mid*mid <= n`. Classic binary-search-on-answer in its simplest form.

```go
// mySqrt returns the floor of the square root of n.
func mySqrt(n int) int {
	if n < 2 {
		return n
	}
	lo, hi := 1, n/2 // hi = n/2 is enough: sqrt(n) <= n/2 for n >= 4
	for lo < hi {
		mid := lo + (hi-lo)/2 + 1 // bias mid UP to avoid infinite loop
		if mid <= n/mid {          // mid*mid <= n, avoids overflow
			lo = mid
		} else {
			hi = mid - 1
		}
	}
	return lo
}
```

<UnderTheHood title="Why ceil-division avoids float and why it's correct">

The expression `(p + speed - 1) / speed` computes `⌈p / speed⌉` using integer arithmetic only. Why it works: `p = q * speed + r` where `0 <= r < speed`. Adding `speed - 1` to `p` gives `q * speed + r + speed - 1`. Integer division by `speed` gives `q + (r + speed - 1) / speed`. When `r == 0`, `(speed-1)/speed == 0`, result is `q`. When `r > 0`, `(r+speed-1)/speed == 1`, result is `q+1 = ⌈p/speed⌉`. No `math.Ceil`, no `float64`, no precision drama. This is the correct production pattern in Go 1.26 for ceiling integer division.

For the sqrt overflow guard: instead of checking `mid*mid <= n` (which overflows for large `n` and large `mid`), we check `mid <= n/mid`. Integer division truncates, so `n/mid == ⌊n/mid⌋`. If `mid <= ⌊n/mid⌋` then `mid * mid <= n` (exactly). Safe and correct.

</UnderTheHood>

Given a sorted array `nums` of distinct integers and a `target`, return the index where `target` is found, or the index where it would be inserted to keep the array sorted. O(log n). This is pure `lowerBound` — implement it from scratch without calling `sort.Search`.

```go
package main

import "fmt"

func searchInsert(nums []int, target int) int {
	lo, hi := 0, len(nums) // hi = len, not len-1
	for lo < hi {
		mid := lo + (hi-lo)/2
		if nums[mid] < target {
			lo = mid + 1
		} else {
			hi = mid // mid is a candidate; keep it
		}
	}
	return lo // lo == hi: the insert/found position
}

func main() {
	fmt.Println(searchInsert([]int{1, 3, 5, 6}, 5)) // 2
	fmt.Println(searchInsert([]int{1, 3, 5, 6}, 2)) // 1
	fmt.Println(searchInsert([]int{1, 3, 5, 6}, 7)) // 4
	fmt.Println(searchInsert([]int{1, 3, 5, 6}, 0)) // 0
}
```

<Exercise n={2} title="Find first and last position" level="medium">

Given a sorted array `nums` that may contain duplicates, and a `target`, return a two-element slice `[first, last]` with the first and last indices of `target`. Return `[-1, -1]` if not present. O(log n) — two binary searches.

Example: `nums = [5,7,7,8,8,10], target = 8` → `[3, 4]`. `target = 6` → `[-1, -1]`.

<Solution>

```go
package main

import "fmt"

func lowerBound(nums []int, target int) int {
	lo, hi := 0, len(nums)
	for lo < hi {
		mid := lo + (hi-lo)/2
		if nums[mid] < target {
			lo = mid + 1
		} else {
			hi = mid
		}
	}
	return lo
}

func upperBound(nums []int, target int) int {
	lo, hi := 0, len(nums)
	for lo < hi {
		mid := lo + (hi-lo)/2
		if nums[mid] <= target {
			lo = mid + 1
		} else {
			hi = mid
		}
	}
	return lo
}

func searchRange(nums []int, target int) [2]int {
	first := lowerBound(nums, target)
	if first == len(nums) || nums[first] != target {
		return [2]int{-1, -1}
	}
	return [2]int{first, upperBound(nums, target) - 1}
}

func main() {
	fmt.Println(searchRange([]int{5, 7, 7, 8, 8, 10}, 8)) // [3 4]
	fmt.Println(searchRange([]int{5, 7, 7, 8, 8, 10}, 6)) // [-1 -1]
	fmt.Println(searchRange([]int{1}, 1))                  // [0 0]
}
```

Two binary searches, each O(log n). The only non-obvious piece: `upperBound` returns the first index *past* the last occurrence (one-past-end), so subtract 1 to get the last index. Guard on `first == len(nums)` before dereferencing.

</Solution>

```go
			lo = mid + 1
		} else {
			// nums[mid] <= nums[hi]: the right side is sorted,
			// and mid could be the minimum.
			hi = mid
		}
	}
	return nums[lo]
}

func main() {
	fmt.Println(findMin([]int{3, 4, 5, 1, 2}))             // 1
	fmt.Println(findMin([]int{4, 5, 6, 7, 0, 1, 2}))       // 0
	fmt.Println(findMin([]int{11, 13, 15, 17}))             // 11 (not rotated)
}
```

Compare `nums[mid]` with `nums[hi]` (not `nums[lo]`). If `nums[mid] > nums[hi]`, the minimum hasn't been seen yet — it's in `(mid, hi]`. Otherwise the minimum is at or before mid. When `lo == hi`, that's the minimum.

</Solution>

</Exercise>

<Exercise n={4} title="Koko eating bananas" level="medium">

Implement `minEatingSpeed(piles []int, h int) int`. Koko can eat at most one pile per hour. At speed `s`, she eats min(s, pile) bananas from the chosen pile and moves on. Find the minimum integer speed to finish all piles in `h` hours. O(n log max(piles)).

<Solution>

```go
package main

import "fmt"

func hoursNeeded(piles []int, speed int) int {
	total := 0
	for _, p := range piles {
		total += (p + speed - 1) / speed // ceiling division
	}
	return total
}

func minEatingSpeed(piles []int, h int) int {
	lo := 1
	hi := 0
	for _, p := range piles {
		if p > hi {
			hi = p // max pile: eating the whole largest pile in one hour
		}
	}
	for lo < hi {
		mid := lo + (hi-lo)/2
		if hoursNeeded(piles, mid) <= h {
			hi = mid // feasible; try slower
		} else {
			lo = mid + 1 // too slow
		}
	}
	return lo
}

func main() {
	fmt.Println(minEatingSpeed([]int{3, 6, 7, 11}, 8))  // 4
	fmt.Println(minEatingSpeed([]int{30, 11, 23, 4, 20}, 5)) // 30
}
```

Answer range: `[1, max(piles)]`. Ceiling division avoids float. Predicate `hoursNeeded <= h` is monotone in speed (more speed = fewer hours). Classic answer-space binary search.

</Solution>

</Exercise>

<Exercise n={5} title="Aggressive cows (hard allocation)" level="hard">

You have `n` stalls at positions given in `stalls []int` (unsorted) and `c` cows. Place the cows in stalls to maximize the minimum distance between any two cows. Return that maximum minimum distance. O(n log n + n log(max_gap)).

Example: `stalls = [1, 2, 8, 4, 9], c = 3` → `3` (place at 1, 4, 9).

<Solution>

```go
package main

import (
	"fmt"
	"sort"
)

// canPlace checks if we can place c cows with minimum distance >= minDist.
func canPlace(stalls []int, c int, minDist int) bool {
	placed := 1
	last := stalls[0]
	for i := 1; i < len(stalls); i++ {
		if stalls[i]-last >= minDist {
			placed++
			last = stalls[i]
		}
	}
	return placed >= c
}

func aggressiveCows(stalls []int, c int) int {
	sort.Ints(stalls)
	lo := 1 // minimum possible distance
	hi := stalls[len(stalls)-1] - stalls[0] // maximum possible distance
	for lo < hi {
		mid := lo + (hi-lo)/2 + 1 // bias up: we want the maximum feasible
		if canPlace(stalls, c, mid) {
			lo = mid // mid distance is feasible; try larger
		} else {
			hi = mid - 1 // not feasible; try smaller
		}
	}
	return lo
}

func main() {
	fmt.Println(aggressiveCows([]int{1, 2, 8, 4, 9}, 3)) // 3
	fmt.Println(aggressiveCows([]int{0, 3, 4, 7, 10, 9}, 4)) // 3
}
```

Here we *maximize* the feasible answer (opposite of Koko). The predicate `canPlace(c, minDist)` is monotone: if we can place cows at distance ≥ D, we can also place them at any distance ≥ D' for D' ≤ D. So we want the *rightmost* feasible D — bias `mid` upward with `+ 1` and update `lo = mid` when feasible (not `hi = mid`). This is the "find rightmost true" variant of answer-space binary search.

</Solution>

</Exercise>

<Recap>

You now own the full binary search toolkit:

- **One template, internalized:** the closed-interval `[lo, hi]` model with `lo <= hi`, `mid = lo+(hi-lo)/2`, and `lo = mid+1` / `hi = mid-1` — eliminates mid every time, never stalls.
- **Overflow is always your problem:** `mid = lo + (hi-lo)/2`, not `(lo+hi)/2`. Every time. No exceptions.
- **Lower bound and upper bound:** the `lo < hi` variant with `hi = len(nums)` finds the leftmost true on a monotone predicate. First occurrence = `lowerBound`. Last occurrence = `upperBound - 1`. Go's `sort.Search` is the stdlib spelling.
- **Rotated arrays:** "which half is sorted?" — compare `nums[lo]` with `nums[mid]` to determine which half is intact, then check if target falls inside it.
- **Search on the answer space:** when the answer is a number and feasibility is monotone, binary-search the answer itself. `lo = smallest valid answer`, `hi = largest valid answer`, predicate = `canDo(mid)`. O(n log m) beats O(n·m) brute force.
- **Ceiling division without float:** `(p + speed - 1) / speed` — clean, correct, idiomatic Go.

</Recap>
