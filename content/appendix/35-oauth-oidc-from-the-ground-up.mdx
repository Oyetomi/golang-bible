## Authn vs Authz

Every system on the internet answers **two** questions about every request — and conflating them is where most auth bugs are born.

<Define term="Authentication vs authorization">
**Authentication** answers *who are you?* — the login, the password check, the session cookie, the token in the header. Anything that proves you're not a stranger off the street. **Authorization** answers *what are you allowed to do?* — the permission check, the ownership check, the scope enforcement that decides whether *this* user may perform *this* action on *this* resource. They're two separate decisions, and most companies get the first right and the second wrong — because authentication is a **solved, reusable** problem (use a library, hash the password, issue a session) while authorization is **custom code on every endpoint**, written by hand, easy to forget. That's why the bugs live there. Every broken-access-control bug you've read — the IDOR where you swap a user ID, the privilege escalation where a regular user hits an admin route, the OAuth scope bypass where a `read` token writes — is the **same shape**: *authentication passed, authorization failed.* The bug is never in the login; it's in the **gap** between knowing who you are and knowing what you can do.
</Define>

Why is this hard at all? Because **HTTP is stateless**. Designed in 1991 to serve documents, it forgets you the moment a request finishes — the next request is a fresh stranger. Every auth mechanism you've ever seen exists to paper over that one fact: the client **carries proof of identity on every request**, and the server uses that proof to remember you. A session cookie, a Bearer token, a JWT, a SAML assertion — same trick, different envelope. And every envelope bakes in **assumptions**: places a developer trusted something they shouldn't. Those trust gaps are the whole game.

<Callout kind="note" title="The two questions to carry into every flow">
For every request you intercept, ask: **how does the server know who I am here?** and **how does the server know I'm allowed to do this?** If you can answer both with confidence, the surface is solid. If either answer is *"the server is trusting the client,"* you've already found the seam. (Foundations — session IDs, the `HttpOnly`/`Secure`/`SameSite` cookie flags, JWT structure — are in the **auth & API design** chapter; we build on them here.)
</Callout>

## OAuth's Roles & Tokens

Sessions and JWTs answer *how does one app remember me?* **OAuth** answers something different: *how do two apps work together on my behalf, without me handing one the keys to the other?*

<Define term="OAuth 2.0 — delegated authorization">
Before OAuth, if Calendly needed your Google Calendar, you gave Calendly your **Google password** — the "password anti-pattern": a third party holding your master credential, able to read your email, change your password, impossible to revoke without breaking everything. **OAuth 2.0** (2010) fixed exactly this: it lets you **delegate a specific capability without delegating your identity**. Calendly gets *calendar read access*, scoped to what it needs, revocable in one click — never your password. The single biggest misconception: **OAuth is *not* an authentication protocol.** It answers *what is this app allowed to do with my data* (authorization), not *who is this user* (identity). "Sign in with Google" *feels* like authentication, but that's OAuth **plus** a second layer — OIDC — bolted on. Apps that treat raw OAuth as login get taken over, because the protocol was never designed to tell the app who the user is.
</Define>

Every OAuth flow has **four roles** — memorize them, because every bug lives between two of them:

<ConceptGrid cols={2}>
  <ConceptCard label="Resource Owner">**You** — the user who owns the protected data (your Google Calendar).</ConceptCard>
  <ConceptCard label="Client">The app that wants access (**Calendly**). Any "Connect your Google account" / "Sign in with GitHub" button is a client.</ConceptCard>
  <ConceptCard label="Authorization Server">The entity that knows the user, authenticates them, and issues tokens (**accounts.google.com**).</ConceptCard>
  <ConceptCard label="Resource Server">The API that holds the data and enforces access on it (**googleapis.com/calendar**).</ConceptCard>
</ConceptGrid>

After a flow completes, the client walks away with **two tokens**. The **access token** is what you actually call the API with — sent as `Authorization: Bearer <token>` — and it's **short-lived** (minutes to an hour) so a leak has a small blast radius. The **refresh token** is **long-lived** and has exactly one job: when the access token expires, you trade the refresh token at the auth server's token endpoint for a fresh access token, silently, no new login. Short-lived security *and* long-lived UX, both at once.

### Refresh-token rotation turns a backdoor into a tripwire

The refresh token is now the long-lived secret — steal it and you mint access tokens for months. So modern OAuth makes refresh tokens **single-use with rotation**: every redemption issues a *new* refresh token and kills the old one. The payoff is **reuse detection** — if a token that was already redeemed is presented again, that's the fingerprint of theft, and the server revokes the **entire token family**.

Here's that model, runnable and verified — the reuse of a spent token revokes the family:

<GoPlayground>

```go
package main

import "fmt"

type store struct {
	live    map[string]string // active token -> familyID
	used    map[string]string // already-redeemed token -> familyID
	revoked map[string]bool   // killed familyIDs
	seq     int
}

func newStore() *store {
	return &store{live: map[string]string{}, used: map[string]string{}, revoked: map[string]bool{}}
}

func (s *store) issue(family string) string {
	s.seq++
	tok := fmt.Sprintf("rt-%d", s.seq)
	s.live[tok] = family
	return tok
}

// redeem rotates the token. Redeeming an ALREADY-USED token is the fingerprint
// of theft -> revoke the whole family so attacker and victim are both kicked.
func (s *store) redeem(tok string) (string, string) {
	if fam, reused := s.used[tok]; reused {
		s.revoked[fam] = true
		return "", "REUSE DETECTED -> family " + fam + " revoked"
	}
	fam, ok := s.live[tok]
	if !ok {
		return "", "unknown token"
	}
	if s.revoked[fam] {
		return "", "family revoked"
	}
	delete(s.live, tok)  // old token dies on use (single-use)
	s.used[tok] = fam
	return s.issue(fam), "rotated" // fresh token in its place
}

func main() {
	s := newStore()
	rt0 := s.issue("famA") // the user's original refresh token

	atk, m1 := s.redeem(rt0) // attacker steals rt0 and redeems first
	fmt.Printf("attacker redeems stolen rt0  -> %s (%s)\n", atk, m1)

	_, m2 := s.redeem(rt0) // real user later replays the same rt0
	fmt.Printf("user redeems rt0 again       -> (%s)\n", m2)

	_, m3 := s.redeem(atk) // attacker's rotated token is in the dead family
	fmt.Printf("attacker tries rotated token -> (%s)\n", m3)
}
```

</GoPlayground>

Finally, **scopes**: a scope is a string (`calendar:read`) bound to the token at consent time. The catch is in the word *supposed to* — **the resource server is supposed to check the scope on every call.** That check is custom logic on every endpoint, so it's exactly what gets forgotten. And any scope check done **client-side** (a hidden button) is decorative — the attacker calls the API directly. The only check that matters is the one on the server.

## The Code Flow

OAuth defines several flows; one dominates the modern web. The **Authorization Code Flow** is what every "Sign in with X" button fires. It has **six steps**, and each is a place a developer can get something subtly wrong.

<Define term="The Authorization Code Flow (six steps)">
**(1) The redirect.** The client sends the browser to the auth server's `/authorize` with five parameters: `response_type=code`, `client_id`, `redirect_uri` (where to come back), `scope`, and `state` (a random value bound to the user's session). **(2) Login + consent.** The user authenticates and approves the consent screen — entirely on the auth server's domain; the client never sees the password. **(3) Redirect back with a code.** The auth server redirects to `redirect_uri` with `code` (a short-lived, single-use ticket — *not* a token) and the same `state` echoed back. **(4) The back-channel exchange.** The client's **backend** POSTs `code` + `client_id` + `redirect_uri` + **`client_secret`** to the token endpoint — server-to-server, the browser never sees it. **(5) Tokens returned.** The auth server returns the access token, refresh token, and granted scopes, as JSON. **(6) Call the API.** The client uses the access token (`Authorization: Bearer`) at the resource server. The genius is step 4: the browser only ever holds the **code**, which is useless without the `client_secret` that never leaves the backend — so intercepting the code in transit gains the attacker nothing.
</Define>

That design — keeping the most sensitive credential off the browser — is what makes the flow secure **for confidential clients** (apps with a backend). Three assumptions have to hold, and each maps to a classic bug:

<ConceptGrid cols={2}>
  <ConceptCard label="state must be validated">`state` binds the callback to the user's original session. If the client doesn't compare the returned `state` to what it sent, an attacker can stitch their own captured code into the victim's session (or vice-versa) — an OAuth-CSRF **account-linking** takeover. Missing `state` validation = the door is open.</ConceptCard>
  <ConceptCard label="redirect_uri must match exactly">If the auth server allows wildcards, prefixes, or "loose" matching, an attacker registers a look-alike URL that passes the check and the **code is delivered to the attacker's host**. Code theft → token theft. OAuth 2.1 mandates exact string matching to close this.</ConceptCard>
  <ConceptCard label="code must be single-use">The first exchange redeems it; every later one must fail. If the same code can be redeemed twice, anyone who captures it (a Referer leak, a log, browser history sync) has a window to redeem it before the real client does.</ConceptCard>
</ConceptGrid>

The `redirect_uri` bug is the most consequential, and it's one line of code. Watch exact matching reject a look-alike host that loose prefix matching waves through — verified:

<GoPlayground>

```go
package main

import (
	"fmt"
	"strings"
)

func exactMatch(registered, got string) bool  { return registered == got }
func prefixMatch(registered, got string) bool { return strings.HasPrefix(got, registered) } // BUG

func main() {
	const registered = "https://app.example.com/callback"
	good := "https://app.example.com/callback"
	evil := "https://app.example.com.evil.com/callback" // attacker-owned look-alike host

	fmt.Println("== exact match (OAuth 2.1 mandate) ==")
	fmt.Printf("legit -> %v   attacker -> %v\n", exactMatch(registered, good), exactMatch(registered, evil))

	fmt.Println("== loose prefix match (the bug) ==")
	fmt.Printf("legit -> %v   attacker -> %v  <- code leaks to attacker host\n",
		prefixMatch("https://app.example.com", good), prefixMatch("https://app.example.com", evil))
}
```

</GoPlayground>

`app.example.com.evil.com` is a domain the **attacker** owns (it's a subdomain of `evil.com`), yet `strings.HasPrefix` against `https://app.example.com` happily accepts it. Exact match is the only safe comparison — `registered == got`, character for character.

## PKCE

The `client_secret` works for apps with a backend. But OAuth is also used by **public clients** — mobile apps and single-page apps that have **no backend** and can't keep a secret (anyone can unzip the APK or open DevTools and read it). For them the `client_secret` protection evaporates, and on mobile there's a real way to steal the code: a **malicious app registers the same custom URI scheme** (`legitapp://callback`) and the OS may hand it the redirect. **PKCE** ("pixie") was built to make that theft useless.

<Define term="PKCE — Proof Key for Code Exchange">
PKCE adds a **per-flow secret the attacker can't intercept**. (1) Before starting, the client generates a high-entropy random **`code_verifier`** (43–128 chars). (2) It hashes it: **`code_challenge` = BASE64URL(SHA256(verifier))** — a one-way derivation. (3) It sends the *challenge* (and `code_challenge_method=S256`) in the authorization request. (4) The auth server stores the challenge next to the code it issues. (5–6) At the token exchange, the client sends the **original verifier** — the raw string that has been sitting in its memory the whole time, *never on the wire*. (7) The server hashes the presented verifier and compares it to the stored challenge; match → tokens, mismatch → rejected. A malicious app that intercepted the **code** still can't exchange it, because it never saw the **verifier**. PKCE is now **mandatory for all clients** in OAuth 2.1 — even confidential ones — because it costs nothing and closes the entire code-interception class.
</Define>

<GoPlayground>

```go
package main

import (
	"crypto/rand"
	"crypto/sha256"
	"encoding/base64"
	"fmt"
)

// The client generates a high-entropy random verifier (43–128 chars).
func newVerifier() string {
	b := make([]byte, 32) // 32 bytes -> 43-char base64url
	rand.Read(b)
	return base64.RawURLEncoding.EncodeToString(b)
}

// challenge = BASE64URL(SHA256(verifier)). One-way: you can't recover the verifier.
func challengeS256(verifier string) string {
	sum := sha256.Sum256([]byte(verifier))
	return base64.RawURLEncoding.EncodeToString(sum[:])
}

// What the auth server does at the token exchange: recompute and compare.
func verifyPKCE(method, storedChallenge, presentedVerifier string) bool {
	switch method {
	case "S256":
		return challengeS256(presentedVerifier) == storedChallenge
	case "plain":
		return presentedVerifier == storedChallenge // challenge IS the verifier — no protection
	default:
		return false // unknown method: reject
	}
}

func main() {
	v := newVerifier()
	ch := challengeS256(v)
	fmt.Printf("verifier (len %d): %s\n", len(v), v)
	fmt.Printf("challenge:         %s\n", ch)

	fmt.Println("\nS256 (correct verifier):     ", verifyPKCE("S256", ch, v))         // true
	fmt.Println("S256 (attacker has code only):", verifyPKCE("S256", ch, newVerifier())) // false

	// plain mode: the auth request carried challenge==verifier, so any observer has both.
	fmt.Println("plain (observer replays it):  ", verifyPKCE("plain", v, v))           // true -> defeated
}
```

</GoPlayground>

</CodeWalk>

<Gotcha>
**PKCE only protects you if the server *enforces* it.** Two ways it silently doesn't: (1) the server accepts `code_challenge_method=plain`, where the challenge equals the verifier — anyone who saw the authorization request has both halves; and (2) the **PKCE downgrade**: the legitimate client sends a challenge, but the server doesn't actually *require* a matching verifier at the token endpoint — it issues tokens without checking. An attacker who intercepts the code just omits the verifier and the server hands over tokens anyway. So when you intercept a flow: if there's **no `code_challenge`** in the authorization request, that's interesting (older/weaker client); and even if there is, you test whether the server rejects an exchange with a *wrong* or *missing* verifier. PKCE on the request but not on the server is no protection at all.
</Gotcha>

### The other four flows — recognition, not memorization

You don't need to exploit each from memory; you need to **recognize** it in a proxy and know whether it's modern, situational, or shouldn't-exist:

| Flow | Recognize it by | Status |
|---|---|---|
| **Authorization Code (+ PKCE)** | `response_type=code`, then a token-exchange POST with a `code_verifier` | The modern default — what you want to see |
| **Implicit** | `response_type=token`; token returned in the URL **fragment** (`#access_token=…`), no exchange POST | **Deprecated** (removed in 2.1) — token-in-URL leaks via history/Referer/JS |
| **Client Credentials** | POST to `/token` with `grant_type=client_credentials`, no user/redirect | Legit for machine-to-machine; leaked client creds = mintable tokens |
| **Device** | a short user code + a `/activate` URL on one device, polling the token endpoint | Legit for TVs/CLIs; watch for code-phishing and weak rate limits |
| **ROPC** | POST to `/token` with `grant_type=password` + username/password in the body | **Shouldn't exist** — the client sees the password; undoes OAuth's whole point |

### OAuth 2.1 — a decade of bug reports, baked into the spec

OAuth 2.1 is what you get when fifteen years of real-world takeovers are fed back into the protocol. Treat it as your **safety baseline** — anything in the wild that violates one of these is potentially reportable:

<ConceptGrid cols={2}>
  <ConceptCard label="PKCE everywhere">Mandatory for **all** clients, public and confidential — closes the code-interception class across every code-using flow.</ConceptCard>
  <ConceptCard label="Implicit & ROPC removed">Neither is a valid grant type anymore. A server that still supports `response_type=token` or `grant_type=password` is running 2.0, not 2.1 — a sign of an older implementation.</ConceptCard>
  <ConceptCard label="Refresh rotation required">For public clients, the single-use + reuse-detection model is mandatory, not optional.</ConceptCard>
  <ConceptCard label="No bearer tokens in URLs + exact redirect_uri">Tokens go in the `Authorization` header (not query strings — they leak to logs/Referer), and `redirect_uri` must match the registered value **character for character**. The redirect change is the most important hardening — loose matching was behind countless account takeovers.</ConceptCard>
</ConceptGrid>

## JWTs & OIDC

OAuth carries *permission*. To carry *identity*, you need one more layer. But first the token format both lean on — the JWT — and its single most important seam. (The JWT *structure* — three base64url parts: header, payload, signature; payload is **readable, not encrypted** — is covered in ch20; here we focus on the validation chain and where it breaks.)

When a JWT arrives, the server is supposed to: **decode the header**, **verify the signature with the correct key**, **check `exp`** (expiry), **check `iss`/`aud`/`nbf`** (right issuer, right audience, valid yet), and only then **trust the payload**. That last step is the power and the danger: once the chain passes, the role/scope/identity in the payload *is* ground truth. One weak link and the server is trusting whatever the attacker wrote.

<Callout kind="warn" title="The seam: the server trusts the algorithm the client tells it to use">
The signing algorithm is named in the **header** (`{"alg":"HS256"}`) — and the header is part of the token, which comes from the **client**. So the algorithm the server verifies with is, technically, a value the *attacker controls*. That's the whole bug class. Its most famous form is **`alg:none`**, where an old library sees `"alg":"none"`, concludes "no signature to check," and accepts the token. There's also **RS256→HS256 confusion** (the server uses the *public* key as an HMAC secret) and **`kid`/`jku`/`x5u` abuse** (tricking the server into fetching the attacker's key). The fix is the same for all of them: **never read the algorithm from the token — pin it server-side to an allowlist.**
</Callout>

import (
	"crypto/hmac"
	"crypto/sha256"
	"encoding/base64"
	"encoding/json"
	"fmt"
	"strings"
)

func b64(b []byte) string  { return base64.RawURLEncoding.EncodeToString(b) }
func b64s(s string) string { return b64([]byte(s)) }

// signHS256 builds header.payload.signature with HMAC-SHA256.
func signHS256(payload string, secret []byte) string {
	head := b64s(`{"alg":"HS256","typ":"JWT"}`)
	body := b64s(payload)
	mac := hmac.New(sha256.New, secret)
	mac.Write([]byte(head + "." + body))
	return head + "." + body + "." + b64(mac.Sum(nil))
}

// NAIVE verify: trusts the alg field in the (attacker-controlled) header.
func verifyNaive(token string, secret []byte) (map[string]any, bool) {
	parts := strings.Split(token, ".")
	hdrJSON, _ := base64.RawURLEncoding.DecodeString(parts[0])
	var hdr map[string]any
	json.Unmarshal(hdrJSON, &hdr)
	if hdr["alg"] == "none" { // <- the trap: honor "none", skip signature
		bodyJSON, _ := base64.RawURLEncoding.DecodeString(parts[1])
		var claims map[string]any
		json.Unmarshal(bodyJSON, &claims)
		return claims, true
	}
	return verifyStrict(token, secret) // (for HS256 it would do the same as strict)
}

// STRICT verify: pin the algorithm to a server-side allowlist; never read it from the token.
func verifyStrict(token string, secret []byte) (map[string]any, bool) {
	parts := strings.Split(token, ".")
	if len(parts) != 3 {
		return nil, false
	}
	mac := hmac.New(sha256.New, secret)
	mac.Write([]byte(parts[0] + "." + parts[1]))
	if !hmac.Equal([]byte(parts[2]), []byte(b64(mac.Sum(nil)))) {
		return nil, false
	}
	bodyJSON, _ := base64.RawURLEncoding.DecodeString(parts[1])
	var claims map[string]any
	json.Unmarshal(bodyJSON, &claims)
	return claims, true
}

func main() {
	secret := []byte("server-side-secret")
	legit := signHS256(`{"sub":"alice","role":"user"}`, secret)
	fmt.Println("legit token verifies (strict):", func() bool { _, ok := verifyStrict(legit, secret); return ok }())

	// Attacker forges an alg:none token granting admin, no signature.
	forged := b64s(`{"alg":"none","typ":"JWT"}`) + "." + b64s(`{"sub":"alice","role":"admin"}`) + "."
	cNaive, okNaive := verifyNaive(forged, secret)
	fmt.Printf("alg:none vs NAIVE  -> accepted=%v role=%v  (FORGERY WINS)\n", okNaive, cNaive["role"])
	_, okStrict := verifyStrict(forged, secret)
	fmt.Printf("alg:none vs STRICT -> accepted=%v                 (rejected)\n", okStrict)
}

### Lab: pin the algorithm

The naive verifier above reads `alg` from the token. Here's a verifier that trusts **any** well-formed token — so an `alg:none` forgery (and even a token with a garbage signature) sails through. A test harness checks three things: a correctly signed token verifies, an `alg:none` forgery is rejected, and a wrong-signature token is rejected. Fix `verify` so it **pins HS256 server-side** — never reading `alg` from the token — recomputes the HMAC, and compares with `hmac.Equal`.

### OpenID Connect: the identity layer OAuth was missing

Apps hacked identity on top of OAuth for years (call the `/userinfo` endpoint and *guess*) until **OpenID Connect (OIDC)**, 2014, standardized it. OIDC is **a layer on top of OAuth** — same redirects, same code exchange — that adds one thing: the **`id_token`**.

<Define term="ID token vs access token (OIDC)">
The **access token** says *"this app may do X"* — it's a key to an API, validated by the **resource server**. The **`id_token`** says *"this user is who they say they are"* — a statement of identity, a **JWT** validated by the **client**. You turn an OAuth flow into OIDC by adding the **`openid`** scope (usually `openid email profile`); the auth server then returns an `id_token` alongside the access token. Its standardized claims: **`iss`** (which provider minted it — must match what you expect), **`sub`** (the permanent, opaque, unique user id *within that issuer* — not the email), **`aud`** (the `client_id` it was minted for — must match yours, or it's a token-confusion attack), **`exp`/`iat`** (expiry/issued-at), **`nonce`** (echoes the client's random value, replay protection), and profile claims like **`email`** and **`email_verified`**. The client must verify the signature (via the provider's JWKS endpoint), `iss`, `aud`, `exp`, and `nonce` — and *only then* trust the claims.
</Define>

The single most under-checked claim — and the most common SSO takeover in the wild — is **`email_verified`**. Apps store users by email; when an OIDC login arrives they look up the account by the `email` claim and sign you in. But email is just a *profile attribute* — an attacker can register at a sloppy provider, put the **victim's** email in their profile, and (if the provider didn't verify it) get an `id_token` with that email and `email_verified: false`. Link by email and you've handed over the victim's account:

### When the issuer itself is the bug — the $100,000 Sign in with Apple zero-day

The `email_verified` gate in `loginSafe` quietly assumes one thing: that when a provider asserts `email_verified: true`, it actually **checked ownership**. In April 2020 that assumption broke at the very top of the trust chain. Bhavuk Jain found that Apple's own authorization server would mint a **fully valid `id_token` for *any* email an attacker named in the request** — signed by Apple's real key, carrying the trusted issuer (`https://appleid.apple.com`), every claim looking exactly as legitimate as a genuine login. The server never confirmed the requester owned the address. Any app that offered "Sign in with Apple" and then **linked the session to its local account by the `email` claim** was exposed to full account takeover from a single forged token, zero victim interaction — and major consumers like Dropbox, Spotify, and Airbnb integrate Sign in with Apple. Apple paid **$100,000** and, on investigation, reported no evidence the flaw had been abused in the wild.

This is the *hard* case the section has been building toward. A sloppy provider sending `email_verified: false` is the easy one — the gate above already rejects it. Here a **top-tier** provider sent `email_verified: true` for an email the real user never owned, and **no claim-level check can catch that**, because every claim is genuinely valid. What still holds is the **`sub`**: Apple mints a stable, opaque, per-app user id for each real account, and the attacker's forged token carried the **attacker's** `sub`, not the victim's. An app that anchors each existing account to the `(iss, sub)` pair — and treats `email` as display data, never the lookup key — never matches the forged token to the victim, valid signature or not. Email-by-fallback is for *first-time account creation only*, with its own out-of-band verification; it must never select an account that already exists.

<Callout kind="pro" title="The rule the $100k bug pays for">
A validated signature, a trusted `iss`, and `email_verified: true` together prove the token is *authentic* — **not** that the email belongs to the person in front of you, because that last step lives inside the issuer and you can't audit it. Anchor identity on **`sub` scoped to `iss`**; demote `email` to a display attribute. The forged Apple token had the right email and a real Apple signature — and the wrong `sub`, the one field that would have stopped it. Source: Bhavuk Jain, *[Zero-day in Sign in with Apple](https://bhavukjain.com/blog/2020/05/30/zeroday-signin-with-apple/)* (2020) — also in the **bug-bounty case bank** (ch27).
</Callout>

<Callout kind="note" title="OIDC's enterprise cousin: SAML">
OIDC dominates the consumer web ("Sign in with Google/Apple/Microsoft"). Its older cousin **SAML** (XML-based, 2005) still dominates enterprise SSO (Okta/Entra into Salesforce/Workday). Recognize it in a proxy instantly: big **base64-encoded XML** in fields named `SAMLRequest`/`SAMLResponse`, endpoints like `/saml/sso` or `/saml/acs` — *no JWT, no `/token`, no five-parameter `/authorize`*. The bug classes differ too: OIDC bugs live in JWT validation, audience confusion, and claim trust; SAML bugs live in **XML signature wrapping**, **XXE** (see ch14), and assertion replay. You don't need to exploit SAML here — just know which one you're looking at: *JWT/JSON/`id_token` → OIDC; XML/auto-submit form/`SAMLResponse` → SAML.*
</Callout>

### The canonicalization seam: normalize *before* you decide

A real $6,000 finding: an app with **enforced** SAML SSO let a hunter authenticate with a password instead, by appending a single **encoded trailing space** (`%20`) to the email. The mechanism is pure order-of-operations — and it generalizes far past SSO.

<Define term="Canonicalization mismatch (decide-then-normalize)">
Software constantly **canonicalizes** input — trims whitespace, lowercases, URL-decodes, Unicode-normalizes — so that `Alice@Example.com `, `alice@example.com`, and `alice@example.com%20` all resolve to one account. The bug appears when a **security decision is made on one form of the input and the action is taken on a *different*, later-normalized form.** In the SSO case: the server checks *"is this email's account SSO-enforced?"* against the **raw** request value, then a downstream lookup **trims** the email. Append a trailing space and the two forms disagree — the raw `victim@example.com%20` (decoded: a trailing space) **misses** the SSO-enforced set, so the server skips SSO and offers the **legacy password** path, while the account lookup trims back to the real victim. The enforcement check and the resolved identity refer to **different strings**. It's the same shape as request smuggling and JWT `alg` confusion: two parts of the system read one input differently, and the attacker lives in the gap. The cure is a one-liner of discipline: **canonicalize once, up front, and make every decision on that single normalized form.**
</Define>

**The hunter's takeaway: always test auth endpoints with encoded whitespace and alternate encodings.** A trailing `%20`, a leading space, a `%00`, a Unicode look-alike, a different case, a `%2e` in a path — each probes whether the server *decides* and *acts* on the same canonical form. In the real report this was rated **High, not Critical**, because it still required knowing the victim's password (the attacker chained it with a separate flaw that let an SSO-only user set one via password reset) — a reminder that **impact, honestly argued, sets the bounty**: the same primitive with zero interaction would have been a critical account takeover. The defensive rule never changes: **one canonicalization, up front, before any security decision** — for emails, usernames, paths, hostnames, and tokens alike.
</Gotcha>

## The Protection Map

Here's the payoff — the shift from *reading the protocol* to *reading the implementation*. Every protection in the auth stack exists because someone broke a real system and a fix got added. So if you can answer two questions about each protection — **what attack does it prevent?** and **what happens if it's missing?** — you've inverted the problem. You stop hunting bugs by trial and error and start **scanning for absences**: you look at a flow, notice the protection that should be there but isn't, and you *already know* the bug.

| Protection | Prevents | When it's missing |
|---|---|---|
| **`HttpOnly`** cookie | JS reading the session | every XSS becomes session theft → account takeover |
| **`SameSite`** cookie | cross-site cookie ride-along | every state-changing endpoint without its own token is CSRF-exposed |
| **JWT signature verification** | token tampering | the JWT is a base64 string the attacker rewrites (roles, identity, scope) |
| **Algorithm allowlist** (pin server-side) | `alg:none` / RS256→HS256 confusion | header-declared `alg` lets the attacker choose how you "verify" |
| **`state`** validation | OAuth-CSRF / account linking | attacker stitches their code into the victim's session → takeover |
| **Exact `redirect_uri` match** | code redirection | a look-alike URL passes → code & token theft |
| **PKCE** (enforced, `S256`) | authorization-code interception | an intercepted code is exchanged without the verifier |
| **Back-channel exchange** | tokens on the browser | tokens leak via history, Referer, and page JS |
| **`client_secret`** secrecy | client impersonation | leaked/bundled secret lets an attacker mint tokens as the app |
| **Short-lived access tokens** | long leak windows | one stolen token is a long-term backdoor |
| **Refresh rotation + reuse detection** | silent long-lived theft | a stolen refresh token works for the full original lifetime, invisibly |
| **Server-side scope enforcement** | over-broad token use | every token becomes a full-access pass; consent is meaningless |
| **`email_verified` check (OIDC)** | unverified-email identity | attacker sets the victim's email → SSO account takeover |
| **Canonicalize before deciding** | decide-then-normalize mismatch | an encoded trailing space (`%20`) dodges the SSO-enforced check → legacy password fallback |

<Gotcha>
**This is how the best auth hunters actually work.** They don't memorize payloads — they hold this map in their head and read flows for missing pieces. Intercept a flow, scan: `state`? `PKCE`? exact `redirect_uri`? `SameSite`? `HttpOnly`? signature verification (test it)? refresh rotation (watch a refresh cycle)? scope enforcement (probe with a mismatched scope)? Every check that passes, the surface is solid. The moment one **fails**, you don't ask *what kind of bug is this* — you read the gap and match it straight to its row. The protocol tells you what *should* be there; the implementation tells you what *is*. The gap between the two is the bug.
</Gotcha>

<UnderTheHood title="PKCE Cryptography, Token Introspection & JWT Validation Internals">

While OAuth 2.1 and OpenID Connect simplify distributed authorization for client applications, the underlying cryptographic operations, token introspection mechanics, and JWT verification paths require strict implementation discipline.

### 1. PKCE Mathematical Construction & Invariants (RFC 7636)

The Proof Key for Code Exchange protocol defends against authorization code interception in public clients (mobile applications, SPAs) where client secrets cannot be securely stored:

- **Entropy & Character Set:** The `code_verifier` is a high-entropy cryptographically random string generated using `crypto/rand` containing between 43 and 128 characters from the unreserved URI character set `[A-Za-z0-9-._~]`:
  ```go
  // Minimum 32 bytes of raw cryptographic entropy -> 43 base64url characters
  b := make([]byte, 32)
  rand.Read(b)
  verifier := base64.RawURLEncoding.EncodeToString(b)
  ```
- **The S256 Transformation:**
  `code_challenge = BASE64URL-ENCODE(SHA256(ASCII(code_verifier)))`
- **Constant-Time Verification:** When the authorization server receives the `code_verifier` at the token endpoint, it recomputes the SHA-256 digest and validates it against the stored `code_challenge` using `crypto/subtle.ConstantTimeCompare` (or `hmac.Equal`) to eliminate timing side-channel leaks.
- **Why OAuth 2.1 Forbids `plain`:** Under the legacy `plain` method, `code_challenge = code_verifier`. Any passive eavesdropper on the authorization request obtains the raw verifier, defeating the entire protection.

### 2. Token Introspection (RFC 7662) vs. Local JWT Cryptographic Verification

Resource servers must validate incoming `Bearer` access tokens using one of two models:

- **Opaque Reference Tokens (RFC 7662):** The resource server issues an authenticated back-channel HTTP `POST` to the authorization server's `/introspect` endpoint. While this guarantees instant revocation awareness, it incurs network latency on every API call.
- **Self-Contained JSON Web Tokens (RFC 7519 / RFC 7515):** The resource server fetches the public key set (`/.well-known/jwks.json`) and verifies signatures locally.
  - **Key ID (`kid`) Routing:** The JWT header specifies which key in the JWKS signed the token. Keys must be cached with an in-memory TTL and rotated gracefully.
  - **Algorithm Pinning:** The verification engine must **ignore** the algorithm declared in the JWT header (`alg`) when selecting verification algorithms. Hardcoding the expected algorithm (e.g. `jwt.WithValidMethods([]string{"RS256"})` or checking `alg == "RS256"` before calling `rsa.VerifyPKCS1v15`) blocks both `alg:none` and RSA-to-HMAC public key confusion attacks.

### 3. OpenID Connect Claim Validation Pipeline (Go 1.22+)

A production-grade OIDC validation pipeline enforces five mandatory temporal and identity assertions:
1. **Issuer Check:** `claims["iss"] == expectedIssuer` (exact string match including protocol and trailing slashes).
2. **Audience Check:** `claims["aud"]` contains the client's `client_id`.
3. **Temporal Invariants:** `now >= claims["nbf"]` (not before) and `now < claims["exp"]` (expiration), allowing for a small clock skew (typically 1–2 minutes).
4. **Subject Anchoring:** User account records are keyed by the compound primary key `(iss, sub)`, never by `email` alone.
5. **Nonce Binding:** In authorization code flows with OIDC, the `nonce` claim in the `id_token` must match the cryptographic hash of the client session's initial authorization state.

</UnderTheHood>

<Exercise n={1} title="RFC 7636 S256 PKCE Challenge Computation" level="easy">

Write `ComputePKCEChallenge(verifier string) string` that computes the RFC 7636 `S256` code challenge from an ASCII code verifier string using SHA-256 and unpadded Base64URL encoding.

<Solution>

```go
package main

import (
	"crypto/sha256"
	"encoding/base64"
	"fmt"
)

func ComputePKCEChallenge(verifier string) string {
	h := sha256.Sum256([]byte(verifier))
	return base64.RawURLEncoding.EncodeToString(h[:])
}

func main() {
	verifier := "dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk"
	challenge := ComputePKCEChallenge(verifier)
	fmt.Println("Verifier: ", verifier)
	fmt.Println("Challenge:", challenge)
	fmt.Println("Matches RFC 7636 vector:", challenge == "E9Melhoa2OwvFrGMTJguCH5rtG6uMgbU6TxA00ZTJaU")
}
```

The SHA-256 digest is encoded with `base64.RawURLEncoding` (no `=` padding characters, `-` and `_` replacing `+` and `/`) per RFC 7636 §3.

</Solution>

<Exercise n={2} title="Constant-Time PKCE Verifier Validation" level="medium">

Write `VerifyPKCE(verifier, challenge, method string) bool` that verifies a submitted `verifier` against an existing `challenge`. It must reject unknown methods (only `"S256"` allowed) and compare the computed challenge against the expected challenge in constant time.

<Solution>

```go
package main

import (
	"crypto/hmac"
	"crypto/sha256"
	"encoding/base64"
	"fmt"
)

func VerifyPKCE(verifier, challenge, method string) bool {
	if method != "S256" {
		return false // Reject plain or unsupported methods
	}
	h := sha256.Sum256([]byte(verifier))
	computed := base64.RawURLEncoding.EncodeToString(h[:])
	return hmac.Equal([]byte(computed), []byte(challenge))
}

func main() {
	v := "dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk"
	c := "E9Melhoa2OwvFrGMTJguCH5rtG6uMgbU6TxA00ZTJaU"

	fmt.Println("Valid S256:", VerifyPKCE(v, c, "S256"))    // true
	fmt.Println("Wrong verifier:", VerifyPKCE("wrong", c, "S256")) // false
	fmt.Println("Rejected plain:", VerifyPKCE(v, v, "plain"))      // false
}
```

Using `hmac.Equal` or `subtle.ConstantTimeCompare` avoids side-channel timing leaks during authorization code redemption.

</Solution>

</Exercise>

<Exercise n={3} title="Validate Essential OIDC Claims" level="medium">

Write `ValidateOIDCClaims(claims map[string]any, expectedIss, expectedAud string, now int64) error` that validates that the issuer matches `expectedIss`, audience matches `expectedAud`, and the current time `now` is strictly between `nbf` and `exp`.

<Solution>

```go
package main

import (
	"errors"
	"fmt"
)

func ValidateOIDCClaims(claims map[string]any, expectedIss, expectedAud string, now int64) error {
	iss, ok := claims["iss"].(string)
	if !ok || iss != expectedIss {
		return errors.New("invalid issuer")
	}

	aud, ok := claims["aud"].(string)
	if !ok || aud != expectedAud {
		return errors.New("invalid audience")
	}

	exp, ok := claims["exp"].(int64)
	if !ok || now >= exp {
		return errors.New("token expired")
	}

	if nbf, ok := claims["nbf"].(int64); ok && now < nbf {
		return errors.New("token not yet valid")
	}

	return nil
}

func main() {
	claims := map[string]any{
		"iss": "https://accounts.google.com",
		"aud": "my-client-app-id",
		"exp": int64(2000),
		"nbf": int64(1000),
	}

	err := ValidateOIDCClaims(claims, "https://accounts.google.com", "my-client-app-id", 1500)
	fmt.Println("Validation error:", err) // nil
}
```

Rigorous claim validation prevents tokens minted for other applications (`aud` confusion) or expired tokens from granting unauthorized access.

</Solution>

</Exercise>

<Exercise n={4} title="Safe Account Linking via Sub and Verified Email" level="hard">

Write `SafeAccountLink(iss, sub, email string, emailVerified bool, subStore, emailStore map[string]string) (string, bool)` that first checks the compound `iss+"|"+sub` in `subStore`, falls back to `emailStore[email]` only if `emailVerified` is `true`, and returns `("", false)` if unverified or unmatched.

<Solution>

```go
package main

import "fmt"

func SafeAccountLink(iss, sub, email string, emailVerified bool, subStore, emailStore map[string]string) (string, bool) {
	// 1. Primary identity anchor: (iss, sub)
	subKey := iss + "|" + sub
	if uid, exists := subStore[subKey]; exists {
		return uid, true
	}

	// 2. Verified email fallback
	if emailVerified && email != "" {
		if uid, exists := emailStore[email]; exists {
			return uid, true
		}
	}

	return "", false
}

func main() {
	subStore := map[string]string{"https://auth.com|sub_123": "USER_1"}
	emailStore := map[string]string{"alice@target.com": "USER_1"}

	// Existing sub match
	u1, ok1 := SafeAccountLink("https://auth.com", "sub_123", "attacker@evil.com", false, subStore, emailStore)
	// New provider linking with verified email
	u2, ok2 := SafeAccountLink("https://google.com", "google_999", "alice@target.com", true, subStore, emailStore)
	// Attacker trying unverified email takeover
	u3, ok3 := SafeAccountLink("https://evil.com", "evil_666", "alice@target.com", false, subStore, emailStore)

	fmt.Printf("Sub match: %s (ok=%v)\n", u1, ok1)        // USER_1 (ok=true)
	fmt.Printf("Verified email: %s (ok=%v)\n", u2, ok2)   // USER_1 (ok=true)
	fmt.Printf("Unverified email: %s (ok=%v)\n", u3, ok3) //  (ok=false)
}
```

Linking accounts by `email` without asserting `email_verified: true` allows any user who registers a matching email on an external identity provider to take over existing accounts.

</Solution>

<Recap>

- **Authentication is identity; authorization is permission.** The bug is never in the login — it's in the **gap**: authentication passed, authorization failed. HTTP's statelessness is why auth exists at all (the client carries proof every request), and every mechanism bakes in a trustable assumption.
- **OAuth is delegated authorization, not authentication** — four roles (resource owner, client, auth server, resource server), two tokens (short-lived **access**, long-lived **refresh**). Refresh-token **rotation + reuse detection** turns a stolen refresh token from an invisible backdoor into a tripwire that burns the whole family. **Scopes** only matter if the **resource server** enforces them on every call.
- **The Authorization Code Flow** (six steps) keeps the most sensitive credential — the `client_secret` — off the browser via the **back-channel exchange**, so an intercepted `code` is useless. Three assumptions: **validate `state`**, **match `redirect_uri` exactly** (loose prefix matching leaks the code to a look-alike host), **single-use `code`**.
- **PKCE** protects **public clients** (no `client_secret`) with a per-flow secret: `challenge = BASE64URL(SHA256(verifier))` sent up front, the raw `verifier` sent at exchange. It only works if the server **enforces** it — reject `plain`, and require the verifier (or it's a **downgrade**). Mandatory for everyone in **OAuth 2.1**, which also kills **Implicit** and **ROPC** and mandates exact `redirect_uri` matching.
- **JWT validation**'s seam: the `alg` is attacker-controlled because it rides in the token — **`alg:none`** and RS256→HS256 confusion. Fix: **pin the algorithm to a server-side allowlist**, never read it from the header.
- **OIDC** adds the **`id_token`** (identity, validated by the client) alongside the access token (API key, validated by the resource server). Trust **`sub` scoped to `iss`** as identity — never the **`email`** alone, and only trust an email when **`email_verified` is true** (the most common SSO account-takeover). The **$100,000 Sign in with Apple** zero-day is the proof at the limit: Apple itself minted a valid, real-signature `id_token` for an attacker-supplied email, so even `email_verified: true` from a top-tier issuer is no guarantee of ownership — only apps that anchored accounts on **`sub`** survived.
- **Canonicalize before you decide.** Making a security decision on the raw input and acting on a later-normalized form is a mismatch an attacker splits with an encoded trailing space (`%20`), a leading space, or a Unicode look-alike — bypassing enforced SSO into a legacy password path. Normalize **once, up front**, then decide on that single form (emails, usernames, paths, hosts, tokens).
- **The Protection Map** is the skill: hold the table of protections ↔ absences in your head and **scan flows for what's missing**. The gap between what the protocol says should be there and what the implementation actually does is the bug.

</Recap>
