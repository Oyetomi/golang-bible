# Accuracy audit — performance-engineering

Chapter: `content/part-2/10-performance-engineering.mdx`
Tier 1 (internals). REPORT ONLY — no edits applied to the chapter.

Every falsifiable claim was checked against a freshly fetched primary source. The CPU-profiler internals, escape analysis, GC model, GOGC/GOMEMLIMIT, slice/map preallocation, sync.Pool, and PGO/version attributions were all confirmed against go.dev. Two real defects found (both sync.Pool clearing), plus several minor imprecisions and unverifiable-by-this-source numbers.

## Audit log

| # | Claim (as written) | Verdict | Source | Action proposed |
|---|---|---|---|---|
| 1 | "the GC clears all pool contents at every GC cycle (during the STW setup phase). If your pool holds a 64 MB buffer and the GC fires, that buffer is gone — the next Get calls New and re-allocates." (UnderTheHood, sync.Pool) | **WRONG** | go1.13 release notes: "Pool no longer needs to be completely repopulated after every GC. It now retains some objects across GCs, as opposed to releasing all objects, reducing load spikes for heavy users of Pool." (victim cache) | Fix: pool is NOT fully cleared every cycle since Go 1.13. It uses a two-generation victim cache: on GC, the current local pool is moved to the "victim" set; objects survive one extra GC before being dropped. Reword to "objects can survive at most ~two GC cycles" — not "gone" on the first GC. |
| 2 | "The GC may clear the pool at any GC cycle; that is intentional, not a bug." | 3 | "Go 1.26 ships Green Tea as the default collector ...
